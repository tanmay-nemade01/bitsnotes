Architectural Patterns for Machine Learning Systems

Lecture Summary

This session provides a comprehensive exploration of architectural patterns in machine learning systems, beginning with a detailed recapitulation of the Retrieval-Augmented Generation (RAG) architecture and its implementation using the Command Query Responsibility Segregation (CQRS) pattern. It examines how multimodal inputs (images, PPTs, PDFs) are handled through OCR pipelines or direct multimodal LLM processing before chunking, embedding, and ingestion into vector databases like ChromaDB.

The lecture then transitions into a systematic comparison of monolithic and microservices architectures, tracing their origins in traditional software engineering and mapping them directly to ML system design. A hands-on demonstration using the Iris dataset, FastAPI, and a pickled logistic regression model illustrates the monolithic ML pattern—where preprocessing, model loading, and prediction are tightly coupled into a single deployable unit. This is contrasted with a microservices implementation where the API Gateway, Model Service, and Logging Service run as independent processes on separate ports, each adhering to the Single Responsibility Principle. The discussion extends to synchronous communication protocols (REST, GraphQL, gRPC) and their trade-offs in terms of speed, data format, and protocol overhead.

The session culminates with an introduction to event-driven architecture, where the publish-subscribe model and message brokers (RabbitMQ, Apache Kafka, cloud-based alternatives) enable truly asynchronous, loosely coupled communication between producers and consumers. The design of logging as an asynchronous service is motivated by practical considerations of latency, reliability, and separation of concerns. Finally, the model registry pattern is introduced as a cornerstone of MLOps, covering version control evolution from file-level systems to distributed Git, and surveying modern tools such as MLflow, DVC, and Weights & Biases for tracking models, datasets, experiments, and code throughout the ML lifecycle.

  • Compare monolithic and microservices architectural patterns, understanding their impact on scalability, deployment velocity, technology flexibility, and fault isolation in ML systems
  • Design a multi-service ML application with an API Gateway routing layer, independent model inference and logging services, and appropriate inter-service communication
  • Evaluate REST, GraphQL, and gRPC for synchronous service communication based on data format, protocol overhead, and use-case requirements

Chapter 1: Retrieval-Augmented Generation (RAG) Architecture with CQRS

Core Idea: The RAG architecture can be architecturally modeled using two distinct patterns—the Pipe-and-Filter pattern for its sequential data processing pipeline, and the Command Query Responsibility Segregation (CQRS) pattern to cleanly separate the write (ingestion) pipeline from the read (query) pipeline.

1.1 Handling Multimodal Inputs in RAG

The canonical RAG architecture presented earlier was designed primarily for text documents. However, real-world enterprise documents rarely consist of text alone. Presentation slides, product manuals, research reports, and technical documentation all intermix images, diagrams, charts, tables, and text. Extending RAG to handle these multimodal inputs is critical for practical deployments.

1.1.1 Approach 1: OCR-Based Text Extraction

In this approach, images embedded in documents (PDFs, PPTs, Word files) are first isolated using document parsing libraries such as pdfplumber, python-pptx, or pdf2image. The extracted images then undergo Optical Character Recognition (OCR) through libraries like Tesseract or cloud-based services such as AWS Textract. The recognized text is merged with any existing textual content from the document, and the combined text corpus proceeds through the standard RAG pipeline: chunking, embedding generation, and vector database storage.

Example: Processing a Presentation Slide
Consider a slide containing a bar chart labeled "Q4 Revenue by Region" with axis labels and a caption reading "Revenue grew 12% year-over-year." The pipeline would:
1. Extract the slide image using python-pptx or by converting PPT to PDF and rasterizing.
2. Run Tesseract OCR on the image to extract axis labels, legend entries, and any embedded text annotations.
3. Concatenate the OCR output with the slide's text caption.
4. Feed the combined text through the chunking and embedding stages of the ingestion pipeline.

1.1.2 Approach 2: Direct Multimodal LLM Processing

Modern large language models—including GPT-4o, GPT-4V, Gemini Pro Vision, and open-source alternatives like LLaVA—natively support multimodal inputs. Instead of performing OCR as a separate preprocessing step, the image is passed directly to the multimodal LLM with a prompt instructing it to generate a textual description or summary:

Prompt: "You are a document analysis assistant. Describe the following slide image in 150 words, capturing all visible text, data trends, chart types, and the key message being conveyed."

The LLM responds with a 100–200 word structured summary that captures both the visual content and any semantic relationships present in the image. This summary is then stored in the vector database alongside the document's other textual chunks.

The multimodal approach has the advantage of capturing semantic context that pure OCR would miss—for instance, understanding that a declining line on a revenue chart represents a negative trend, or that two adjacent diagrams are contrasting "before" and "after" states.

1.2 CQRS Implementation of RAG

CQRS separates the system into two distinct pipelines:

1.2.1 The Write (Ingest/Command) Pipeline

This pipeline is implemented in a file conventionally named ingest.py. It performs three sequential activities, each corresponding to a filter in the pipe-and-filter pattern:

Step 1 — Document Loading: Uses LangChain document loaders suited to the input format. For PDFs: PyPDFLoader. For PPTs: UnstructuredPowerPointLoader. For Word documents: Docx2txtLoader. The output is a collection of Document objects, each representing a page or logical section.

Step 2 — Text Splitting (Chunking): Employs RecursiveCharacterTextSplitter with configurable parameters—typically chunk_size=1000 characters and chunk_overlap=200 characters. The overlap ensures that semantic context spanning chunk boundaries is preserved. The splitter recursively attempts to break text at natural boundaries: paragraphs, sentences, then words.

Step 3 — Embedding & Vector Store Persistence: Each chunk is passed through an embedding model (e.g., OpenAI's text-embedding-3-small) to produce a dense vector representation. The chunk text and its embedding vector are then stored in a vector database—in this implementation, ChromaDB. The persist() method ensures the index is written to disk for subsequent reads.

1.2.2 The Read (Query) Pipeline

The read pipeline is triggered by a user-facing interface (Streamlit in the demonstration). When a user submits a prompt:

  1. The query is embedded using the same embedding model used during ingestion.
  2. A similarity search is performed against the ChromaDB vector store to retrieve the top-\(k\) most semantically relevant chunks.
  3. The retrieved chunks serve as a grounding context for the LLM (GPT-4o-mini), which synthesizes a coherent response.
  4. The response includes source citations, indicating which document and page contributed to the answer.
Design Insight: The system does not use the LLM for any generative task during ingestion. The LLM is invoked only at the final stage of the read pipeline, where it rephrases raw retrieved data into grammatically coherent, contextually appropriate answers. This includes capabilities like summarization ("summarize in 50 words") and tone adaptation based on the prompt's phrasing.

1.3 Semantic Search vs. Keyword Search

A critical question arises: why are embeddings necessary when an LLM could theoretically answer questions directly from retrieved documents?

Without embeddings, document retrieval relies on keyword matching—searching for exact or near-exact occurrences of query terms in the document corpus. This approach fails when:

  • The query uses synonyms or semantically related terms not present in the documents (e.g., querying "goal requirements" when the document only mentions "GR" or "business objectives").
  • The query requires semantic understanding of relationships (e.g., understanding that "king is to male as queen is to female" involves gender relationships, not just co-occurrence of words).
  • The documents use domain-specific abbreviations or jargon that the query paraphrases in plain language.

Embeddings encode semantic proximity in a high-dimensional vector space. Documents about "monolithic architecture scalability issues" will have vectors close to queries about "challenges in scaling single-unit deployments," even when they share few keywords, because the embedding model has learned that these phrases describe the same underlying concept.

Limitation: Standard RAG does not dynamically fetch information missing from the document corpus. If a user asks "What is GR for ML?" but the ingested documents never define this abbreviation, RAG cannot answer. This gap is addressed by Agentic RAG, where an agent layer can invoke external tools or APIs to supplement the retrieved context. The agentic layer can be inserted at multiple points in the pipeline: before chunking (to preprocess or enrich documents), during retrieval (to augment results with external knowledge), or before response generation (to validate and expand the LLM's answer).

Chapter 2: Monolithic Architecture

Definition: Monolithic architecture is an application design where all components—user interface, business logic, data access layer, and integration adapters—are packaged and deployed as a single, indivisible unit.

2.1 The Food-to-Go Case Study

Consider implementing a Swiggy/Zomato-style food delivery application as a monolith. The system involves three primary actors:

  • Consumer (Customer): Browses restaurants, places orders, makes payments, tracks deliveries.
  • Courier (Delivery Agent): Receives delivery assignments, navigates to restaurants and customers, updates delivery status.
  • Restaurant: Receives orders, manages menus, updates preparation status.

Despite being a single deployable unit, the application is internally modularized into functional domains:

  • Restaurant Management Module: Handles menu creation, item availability, pricing.
  • Order Management Module: Manages the order lifecycle from placement to fulfillment.
  • Delivery Management Module: Assigns couriers, tracks GPS location, estimates ETAs.
  • Payment Module: Integrates with third-party payment gateways (Stripe, Razorpay) via dedicated adapters.
  • Notification Module: Sends SMS and push notifications through Twilio or similar adapters.
  • Billing Module: Generates invoices and receipts, sends confirmation emails via SES or similar email adapters.

All modules share a single relational database (e.g., MySQL) and are developed in a uniform technology stack (e.g., Java with Spring Boot). Third-party cloud services—Twilio for SMS, AWS SES for email, Stripe for payments—are accessed through adapter interfaces that abstract the external dependencies.

2.1.1 Advantages

Shared Memory and Process Space: Because the entire application runs as a single operating system process on a single compute instance (e.g., an AWS EC2 virtual machine), function calls between modules are in-process and therefore extremely fast. Data sharing between modules can occur through shared memory structures without serialization or network overhead.

End-to-End Testing Simplicity: A tester can execute a complete user journey—login, browse, place order, process payment, dispatch courier, confirm delivery—within a single test run against a single deployed instance. Integration testing becomes straightforward because there are no network boundaries between components.

Low Operational Overhead: Early-stage projects benefit from a single codebase, single deployment pipeline, and single monitoring surface. For prototypes, proofs of concept, and applications with predictable, low-scale usage patterns, the monolithic approach minimizes DevOps complexity.

2.1.2 Disadvantages

Scalability Bottleneck: The defining failure mode of monolithic architecture is the inability to scale individual components independently. When the 2014 Flipkart "Big Billion Day" sale experienced traffic surges, the entire application had to be scaled horizontally, even though only the order placement and payment modules were under strain. Scaling the entire monolith is resource-inefficient and subject to diminishing returns as shared resources (database connections, memory pools) become contention points.

Technology Lock-In: Once an application is monolithic and developed in a specific language (e.g., Java), all subsequent development, enhancements, and bug fixes must use that same language and framework. A team cannot decide to implement a new recommendation module in Python to leverage modern ML libraries without either rewriting the entire application or introducing awkward inter-process communication layers.

Increased Cognitive Load Over Time: As a monolith grows (e.g., to 660 database tables and hundreds of thousands of lines of code, as in some legacy enterprise systems), no single developer can hold a complete mental model of the application. Making even trivial changes becomes risky due to unforeseen side effects. New team members face an insurmountable onboarding curve.

Deployment Granularity: Any change—even a one-line bug fix in the notification module—requires rebuilding, retesting, and redeploying the entire application. This creates a deployment bottleneck where small, low-risk changes are batched together, increasing the blast radius of any deployment failure.

Single Point of Failure: A memory leak in the restaurant management module, an unhandled null pointer in the billing module, or a deadlock in the database connection pool—any of these can bring down the entire application, including unaffected modules.

2.2 Quality Requirements Drive Architecture Design

The fundamental insight of software architecture is that a system's quality requirements should be considered early and should drive fundamental design decisions. Once architectural decisions are locked into implementation, they become extremely difficult to change—fixing qualities like scalability, security, or changeability in an existing system often requires a substantial rewrite. Architecture is the binding element that guides implementation to meet the quality requirements of the system.

In the design process, we often cannot equally achieve all desired requirements and must make hard trade-off decisions. By deliberately considering alternatives at the design stage, we can make deliberate choices, rather than locking in trade-offs from ad hoc implementation decisions. This is especially important for ML-enabled systems, where additional quality concerns such as prediction accuracy, training and inference costs, reproducibility, fairness, data provenance, and explainability must be balanced against traditional software quality attributes.

2.3 Case Study: Twitter's Monolithic Crisis and Redesign

Twitter (now X) provides an illustrative real-world example of monolithic failure at scale. Twitter was originally designed as a monolithic database-backed web application written in Ruby on Rails by a small team. Once Twitter became popular, it became slow and hard to scale. Developers introduced caches throughout the application and bought more hardware, but they could not handle traffic spikes. Worse, changes that marginally improved performance often made the system harder to maintain and debug—it became increasingly harder to fix bugs or implement new features. Since scaling was mostly achieved by buying more hardware, operating costs became unsustainable for the business.

After 2010, Twitter undertook the rare and expensive step of redesigning and reimplementing the entire system. For the redesign, they explicitly considered four primary quality goals:

  1. Improve latency and operating cost
  2. Improve reliability by isolating failures
  3. Improve maintainability with clearer boundaries between modules
  4. Improve modifiability to allow small teams to quickly release new features

None of these goals could be achieved with the existing monolithic design. The redesign adopted a microservices architecture (each functionality isolated in separate, independently scalable processes), replaced Ruby on Rails with Scala for performance, designed a new storage solution that avoided a single bottleneck, and built reliability and scalability strategies (automated failover, monitoring, load balancing) into the infrastructure. This case illustrates how architectural decisions are driven by explicit quality goals and how the inability to change fundamental architectural decisions later can force a complete rewrite.

Architecture vs. Agility: There is a well-documented tension between architectural planning and agility. On one hand, architecture helps avoid costly mistakes and builds the system with the right qualities for future evolution. On the other hand, too much architecture may slow down a project racing toward a minimal viable product, investing in qualities not relevant until the project is truly successful—at which point more resources for a redesign may be available. When Twitter was first started, scalability was less important than releasing a prototype quickly to gain users, so the monolithic Ruby application was appropriate at the time. Experienced software engineers navigate this space by focusing on key qualities early while preserving enough flexibility for later change. This skill is equally or even more important when introducing machine learning with its many additional design decisions and new quality requirements.

Chapter 3: Monolithic ML Pattern

3.1 Architecture Overview

In the monolithic ML pattern, all components of a machine learning application—preprocessing logic, model loading, inference computation, and API serving—are tightly coupled and deployed as a single unit. This is the natural starting point for most ML projects and remains appropriate for low-complexity, low-scale use cases.

Components in a Typical Monolithic ML Application:
  • API Layer: FastAPI (or Flask/Django) endpoints exposing prediction functionality.
  • Model Loading: Deserialization of a trained model from a pickle file, ONNX format, or similar serialized artifact.
  • Preprocessing: Input validation, feature engineering, normalization, and encoding.
  • Prediction Logic: Forward-pass computation through the model.
  • Post-processing: Formatting predictions into API responses, applying decision thresholds.

3.2 Iris Dataset Classification Demo

The demonstration uses the Iris dataset—a classic machine learning benchmark introduced by Ronald Fisher in 1936. The dataset contains 150 samples across three species of Iris flowers, with four measured features per sample:

\[ \begin{aligned} x_1 &= \text{sepal length (cm)} \\ x_2 &= \text{sepal width (cm)} \\ x_3 &= \text{petal length (cm)} \\ x_4 &= \text{petal width (cm)} \\ y &\in \{0, 1, 2\} \quad \text{where } 0 = \text{Setosa},\; 1 = \text{Versicolor},\; 2 = \text{Virginica} \end{aligned} \]

3.2.1 Logistic Regression for Multi-Class Classification

The underlying model is a multinomial logistic regression (softmax regression). For a given input feature vector \(\mathbf{x} = [x_1, x_2, x_3, x_4]^T\), the model computes class probabilities using the softmax function:

\[ P(y = k \mid \mathbf{x}) = \frac{e^{\mathbf{w}_k^T \mathbf{x} + b_k}}{\sum_{j=0}^{2} e^{\mathbf{w}_j^T \mathbf{x} + b_j}} \]

where \(\mathbf{w}_k\) is the weight vector for class \(k\) and \(b_k\) is the bias term. The predicted class is the argmax over the probability distribution:

\[ \hat{y} = \arg\max_{k \in \{0,1,2\}} P(y = k \mid \mathbf{x}) \]

The model parameters (\(\mathbf{w}_k, b_k\) for \(k \in \{0,1,2\}\)) are learned during training by minimizing the cross-entropy loss function. The trained model is serialized using Python's pickle module into logistic_regression_model.pkl.

3.2.2 FastAPI Implementation

The monolithic application uses FastAPI served by UVicorn:

from fastapi import FastAPI
import pickle
import numpy as np

app = FastAPI()

# Load the pre-trained model at application startup
with open("logistic_regression_model.pkl", "rb") as f:
    model = pickle.load(f)

@app.post("/predict")
async def predict(features: list[float]):
    """
    Accepts a list of 4 float values:
    [sepal_length, sepal_width, petal_length, petal_width]
    Returns the predicted class index (0, 1, or 2).
    """
    input_array = np.array(features).reshape(1, -1)
    prediction = model.predict(input_array)
    return {"prediction": int(prediction[0])}
Line-by-Line Analysis:
Line 5: FastAPI app instance is created. This is the central application object that registers routes, middleware, and event handlers.
Lines 8–9: The pickled model is loaded once at import time. In a production WSGI/ASGI server with multiple worker processes, each worker loads its own copy into memory. This is acceptable for a monolithic prototype but becomes a memory concern at scale.
Line 11: The @app.post("/predict") decorator registers a POST endpoint. POST is semantically appropriate for prediction because the operation is non-idempotent in principle (different inputs produce different outputs) and involves submitting data to the server.
Line 17: reshape(1, -1) ensures the input list is converted to a 2D array with one row and four columns, matching scikit-learn's expected input shape of (n_samples, n_features).
Line 19: The prediction is cast to a native Python int because NumPy integers are not JSON-serializable by default in FastAPI's response model.

3.2.3 Running and Testing

The application is started with uvicorn app:app --port 5000. FastAPI automatically generates an interactive Swagger UI at /docs, where the /predict endpoint can be tested by submitting a feature array:

# Request
POST /predict
Content-Type: application/json
[5.1, 3.5, 1.4, 0.2]

# Response
{"prediction": 0}  # Setosa
Critical Limitation of Monolithic ML: If the prediction traffic grows from 10 requests per second to 10,000, the entire application must be scaled. This includes the model loading logic (which is idempotent and compute-light) and the API server (which handles request parsing). In a microservices architecture, only the inference service would be scaled. Furthermore, any model update—even a minor version bump from v5.0 to v5.1—requires the entire application to be rebuilt, tested, and redeployed.

Chapter 4: Microservices Architecture

Definition: Microservices architecture decomposes an application into a collection of small, autonomous services, each responsible for a single business capability (the Single Responsibility Principle), each independently deployable, and each owning its own data storage.

4.1 The Role of Abstraction in Architectural Design

Software architecture tends to focus on the big important decisions, while abstracting away less important details. To reason effectively at scale, abstractions are necessary. Different abstractions—called architectural views in the software architecture community—are useful for different design goals.

Consider different maps of a city: a street map, a cycling map, a tourist map, and a flood-zone map. They are all abstractions of the same city, each highlighting different details relevant to different tasks. Similarly, architectural views provide different lenses: a process view shows processes, message exchanges, and timing to find performance bottlenecks; a module view shows component boundaries and plug-in interfaces to reason about modifiability; a deployment view shows networks and trust boundaries to reason about security. Architects deliberately choose which abstractions to use based on which qualities they are optimizing for.

For example, in a self-driving car system like Apollo, an architectural diagram might depict various ML models and how they exchange information—useful for debugging feedback loops between perception and planning models. However, the same diagram would not have enough information to reason about real-time properties or GPU capacities, for which different abstractions would be designed.

4.2 Common System Structures (Architectural Styles)

At the highest level of organizing components in a system architecture, there are common system structures shared by many systems, also known as architectural styles. Understanding these common structures is useful for deciding how to fit ML components into a system:

  • Client-Server Architecture: Computations are split across multiple machines. A server provides functionality to multiple clients, typically over a network connection. Clients initiate communication with the server.
  • Multi-Tier Architecture: Computation and data storage are organized into multiple layers or tiers. The most common is the three-tier architecture with a presentation tier (UI), a logic tier (business logic), and a data tier (storage). This separates concerns regarding user interface, request processing, and data storage—a structure conceptually extensible with ML components.
  • Service-Oriented Architectures and Microservices: The system is organized into multiple self-contained services that call each other through remote procedure calls. Each service is independently deployable, versioned, and scaled, with its own data storage.
  • Event-Based Architecture: Components listen to messages broadcast by other components through a message bus. This strongly decouples components since publishers don't need to know who consumes their messages, making it easy to add new components. Many robotics systems follow this design.
  • Data-Flow (Pipe-and-Filter) Architecture: The system is organized around sequential data processing, where data produced by one component is used as input by the next. ML pipelines naturally follow this style, as do batch processing systems for large datasets and Unix shell command compositions.
  • Monolithic System: A single unit where internals are interwoven rather than clearly separated. ML components may be integrated as libraries rather than services. Development is initially simple without distributed system complexity, but the system becomes hard to evolve and scale as it grows.
Design Patterns and Design Knowledge: In software engineering, codified design knowledge is best known in the form of design patterns. A design pattern names and describes a common solution to a known design problem along with its known advantages and pitfalls. For example, the observer pattern (also known as publish-subscribe) defines a one-to-many dependency between objects so that when one object changes state, all dependents are notified without strongly coupling them. At the architectural scale, patterns like heartbeat (dead-man timer) detect when a component is unavailable to trigger mitigations. Establishing widely shared names for patterns enables more efficient communication—instead of describing a solution in detail, teams can simply reference "the observer pattern" and all participants immediately understand the structure, implications, and trade-offs. For ML-enabled systems, the pattern catalog is still emerging, with patterns like feature store (reuse features across projects by decoupling feature creation from model development and serving) and Retrieval-Augmented Generation (RAG) becoming increasingly established.

4.3 Deployment Velocity and Industry Metrics

The shift from monolith to microservices is driven by quantifiable operational benefits. Industry leaders report deployment frequencies that would be impossible under monolithic architectures:

  • Amazon: Approximately 23,000 micro-deployments per day across its e-commerce platform, AWS services, and internal tools. The ability to deploy individual services independently means that a team can ship a feature at any time without coordinating with other teams or waiting for a synchronized release window.
  • Google: Approximately 5,500 deployments per day, with deployment lead times measured in minutes rather than hours or days.
  • Industry Average: Organizations adopting microservices report roughly 500 micro-deployments per day on average, with high reliability and rapid customer feedback loops.

4.4 Microservices Architecture for the Food-to-Go Use Case

Revisiting the food delivery application under a microservices architecture:

Architectural Components:

API Gateway: All client requests (from mobile apps, web browsers) arrive at a single entry point. The API Gateway authenticates requests, performs rate limiting, and routes each request to the appropriate backend service. It does not contain business logic.

Order Service: Manages the order lifecycle. Owns its dedicated database (could be PostgreSQL). Exposes REST endpoints for order creation, status updates, and history retrieval.

Restaurant Service: Manages restaurant profiles, menus, and availability. Owns its own database (could be MongoDB for flexible menu schemas).

Accounting/Payment Service: Handles payment processing via adapters to Stripe or Razorpay. Owns a transaction database.

Notification Service: Sends SMS, push notifications, and emails via adapters to Twilio, Firebase Cloud Messaging, and AWS SES respectively.

Delivery Service: Manages courier assignment, GPS tracking, and ETA computation.

4.4.1 Communication Patterns

Services communicate through two broad categories of patterns:

Synchronous Communication: Service A sends a request to Service B and blocks (waits) until Service B returns a response. The primary synchronous protocols are:

  • REST (Representational State Transfer): Uses HTTP/1.1 with JSON payloads. Stateless, resource-oriented, and the de facto standard for public-facing APIs. Each operation is an independent request-response cycle.
  • GraphQL: Also over HTTP/1.1 with JSON, but with a fundamentally different query model. Instead of multiple REST endpoints (GET /posts, GET /posts/{id}/comments, GET /posts/{id}/likes), a single GraphQL endpoint accepts a structured query specifying exactly what data is needed. The resolver executes all sub-queries and returns a unified, nested response.
  • gRPC (Google Remote Procedure Call): Uses HTTP/2 as the transport and Protocol Buffers (Protobuf) as the binary serialization format. Both client and server must implement a shared .proto contract file defining service methods and message structures. HTTP/2 provides multiplexing (multiple concurrent streams over one connection), header compression, and server push, making gRPC significantly faster than REST or GraphQL in resource-constrained or high-throughput scenarios.

Asynchronous Communication: Service A emits a message (event) to a message broker and immediately continues processing. This is covered in detail in Chapter 6.

4.5 Detailed Protocol Comparison

GraphQL in Practice: Consider Facebook's news feed. When a user opens the app, the client needs: the user's own posts, comments on each post, likes on each post, and friend suggestions. With REST, this would require at least 4 separate HTTP requests, each with its own round-trip latency. With GraphQL, a single query specifies all required data:

query {
  user(id: "123") {
    posts {
      content
      comments { author text }
      likes { user }
    }
    friendSuggestions { name }
  }
}
The GraphQL server resolves all fields in one pass, reducing N sequential round trips to one. The trade-off is server-side complexity: the resolver must efficiently batch and optimize the underlying data fetches (the N+1 query problem).
gRPC Performance Characteristics:
  • Binary Format: Protobuf encodes data as compact binary, typically 3–10× smaller than equivalent JSON. This reduces network bandwidth and parsing CPU overhead.
  • HTTP/2 Multiplexing: Multiple request-response pairs share a single TCP connection without head-of-line blocking. This is critical in microservices environments where a service may have hundreds of concurrent calls.
  • Strongly Typed Contracts: The .proto file serves as both documentation and code generation source. Breaking changes to the API are caught at compile time rather than runtime.
  • Streaming Support: gRPC natively supports four communication patterns: unary (single request, single response), server streaming, client streaming, and bidirectional streaming.
The primary adoption barrier is the requirement that both communicating services implement the Protobuf contract. This makes gRPC ideal for internal service-to-service communication but less suitable for public-facing APIs where clients are diverse and outside the organization's control.

4.5.1 When to Use Each Protocol

ProtocolBest For
RESTPublic APIs, broad client compatibility, 90%+ of ML serving endpoints
GraphQLMobile/web apps with complex, nested data requirements; social media feeds; dashboards aggregating multiple data sources
gRPCHigh-throughput internal service-to-service communication; resource-constrained environments; streaming data pipelines; real-time ML inference with low latency requirements

4.6 Independent Database per Service

A fundamental principle of microservices is that each service owns its data. The Order Service might use a relational PostgreSQL database for transactional integrity on orders, while the Restaurant Service uses MongoDB for flexible menu document schemas, and the Delivery Service uses Redis for real-time courier location caching. This polyglot persistence approach lets each team choose the optimal storage technology for their domain, but it introduces the challenge of maintaining data consistency across services—typically addressed through eventual consistency patterns like the Saga pattern or event sourcing.

Chapter 5: Microservices ML Pattern

5.1 Architecture and Single Responsibility Principle

The microservices ML pattern applies the Single Responsibility Principle (SRP) to machine learning pipelines. Each service focuses on exactly one ML function:

  • Data Ingestion Service: Reads raw data from sources (CSV, SQL, S3 buckets) and publishes it for downstream processing.
  • Preprocessing Service: Performs feature engineering, normalization, encoding, and missing value imputation.
  • Model Training Service: Accepts preprocessed data, trains a model, and registers the trained artifact in a model registry.
  • Model Inference (Prediction) Service: Loads a specific model version and serves predictions via an API.
  • Logging/Monitoring Service: Captures prediction inputs, outputs, latencies, and drift metrics.

5.1.1 Divide and Conquer: The Role of Interfaces

A fundamental architectural decision is how to decompose the system so different teams can work on different components. The various ML and non-ML components in a system interact, often in subtle ways. For example, predictions of a model are used in non-ML business logic, influencing user interactions, which produce telemetry, which may be used for monitoring and updating models. Local design decisions in individual components influence other components—a small model enabling different deployment choices than a large one.

A component's interface plays a crucial role as a negotiation and collaboration point between teams building the system. It is where teams negotiate how to divide work and assign responsibilities. Ideally, interfaces are defined early based on what is assumed to remain stable, because changes to interfaces later are expensive and require involvement of multiple teams. ML introduces additional interfaces that must be explicitly negotiated and documented, such as: who is responsible for data quality—the component providing the data or the ML pipeline consuming it? Who owns the feature definitions used during both training and serving?

While the machine-learned model itself is relatively straightforward to integrate as an isolated inference component with a clear interface (input features → prediction), the ML pipeline may interact with other components in more intricate ways. Planning these interfaces early through architectural design provides a strong foundation that supports desired quality requirements and guides implementation.

Microservices vs. Pipe-and-Filter: Both patterns decompose processing into sequential stages. The key difference is deployment granularity. In pipe-and-filter, all filters typically execute within the same process space (a form of logical separation within a monolith). In microservices, each filter is an independently deployable service that communicates via network protocols (REST, gRPC, or message queues). This means microservices can be developed by different teams, in different languages, and scaled independently—but it also introduces network latency and distributed system complexity.

5.2 Three-Service Iris Classification Demo

The demonstration decomposes the monolithic Iris classifier into three independent services:

5.2.1 Service Architecture

ServicePortResponsibility
API Gateway8000Receives client requests, routes to appropriate services, orchestrates the prediction flow, and publishes logs
Model Service8001Loads the pickled logistic regression model, accepts feature vectors, returns class predictions
Logging Service8002Receives input features and prediction outputs, persists them for audit and analysis

5.2.2 Request Flow

  1. Client sends a POST request to http://localhost:8000/predict with a JSON array of four float features.
  2. API Gateway parses the request, extracts the feature list, and forwards it to the Model Service via POST http://localhost:8001/predict.
  3. Model Service deserializes logistic_regression_model.pkl (on startup), runs model.predict() on the input array, and returns the predicted class index.
  4. API Gateway receives the prediction, then forwards both the original input and the prediction to the Logging Service via POST http://localhost:8002/log.
  5. Logging Service appends {"features": [...], "prediction": 0} to an in-memory log list (extensible to database persistence).
  6. API Gateway returns the prediction to the client.
Architectural Discussion — Gateway vs. Service Publishing: In the demonstrated implementation, the API Gateway orchestrates both the prediction call and the logging call. An alternative design—favoring stricter adherence to the API Gateway's routing-only purpose—would have the Model Service directly publish results to the Logging Service (or to a message broker). This offloads the gateway and prevents it from becoming a "smart gateway" anti-pattern where orchestration logic accumulates over time. The demonstrated approach was chosen to minimize code changes compared to the monolithic version, making the architectural transition clearer for learning purposes. In production, the direct service-to-broker approach is generally preferred.

5.2.3 Code Analysis: API Gateway

from fastapi import FastAPI
import requests

app = FastAPI()

MODEL_SERVICE_URL = "http://localhost:8001/predict"
LOG_SERVICE_URL = "http://localhost:8002/log"

@app.post("/predict")
async def predict(features: list[float]):
    # Step 1: Call Model Service
    model_response = requests.post(
        MODEL_SERVICE_URL,
        json={"features": features}
    )
    prediction = model_response.json()["prediction"]

    # Step 2: Log the transaction
    requests.post(
        LOG_SERVICE_URL,
        json={
            "features": features,
            "prediction": prediction
        }
    )

    return {"prediction": prediction}
Startup Sequence Requirement: The Model Service (port 8001) and Logging Service (port 8002) must be started before the API Gateway (port 8000). The API Gateway depends on both downstream services being available when it receives its first request. In production, this dependency would be managed through service discovery (Consul, Eureka), health checks with retry logic, and circuit breakers (e.g., via resilience patterns like the Circuit Breaker pattern from Michael Nygard's "Release It!").

5.2.4 Independent Scaling Benefits

If the prediction load increases from 10 to 10,000 requests per second, only the Model Service needs to be scaled horizontally (e.g., from 1 to 10 instances behind a load balancer). The API Gateway remains at its original scale since its routing logic is lightweight, and the Logging Service scales independently based on log volume. If a new model version (v5.0 to v5.1) is released, only the Model Service is redeployed—the API Gateway and Logging Service remain untouched, preserving their stability.

Chapter 6: Event-Driven Architecture for ML Systems

Definition: Event-Driven Architecture (EDA) is a design paradigm where system components communicate by producing and consuming events—immutable records of state changes or occurrences—through an intermediary message broker, enabling asynchronous, loosely coupled interaction. EDA is one of the fundamental architectural styles (alongside client-server, multi-tier, microservices, pipe-and-filter, and monolithic) that organizes how components interact in a system.

6.1 Design for Change: Why Asynchronous Decoupling Matters

A core design principle in software engineering is to anticipate change and design software such that it is easy to change. The central idea is to encapsulate the part of the system that is likely to change within a module, but design module interfaces such that changes do not affect the interface. In ML-enabled systems, we can anticipate that models will change regularly and that components (logging, monitoring, notification) will be added or modified over time. EDA directly supports this by making it easy to add new consumers without modifying producers—the essence of loose coupling.

Traditional software engineering strategies for designing for change rely on modularity and strong abstractions at module interfaces. In ML systems, models are natural modules that encapsulate internals behind a simple and stable interface. The typical design of ML pipelines as sequential stages maps naturally to the data-flow architectural style. EDA extends this modularity across components at runtime, allowing new consumers to be added dynamically without reconfiguring producers.

Connection to the Observer Pattern: Event-driven architecture at the system level is essentially the observer pattern (also known as publish-subscribe) applied at the architectural scale. The pattern defines a one-to-many dependency between components so that when one component changes state, all dependents are notified and updated automatically. This is the same pattern used in object-oriented programming for GUI event handling, scaled up to distributed system components communicating through message brokers.

6.2 Events, Producers, and Consumers

An event is a record of something that happened in the system. Examples include:

  • A user logs in (event: UserLoggedIn)
  • An order is placed (event: OrderPlaced)
  • A model generates a prediction (event: PredictionGenerated)
  • A new training dataset is uploaded (event: DatasetUploaded)
  • A sensor reports a temperature reading (event: TemperatureReading)

Each event carries a payload—the contextual data needed for downstream processing. For example, an OrderPlaced event payload includes the ordered items, quantities, restaurant ID, customer ID, and timestamp.

In the EDA model:

  • Producers (Publishers): Components that detect state changes and emit events to a message broker. Producers have no knowledge of which consumers will process the events, how many consumers exist, or when they will process them.
  • Consumers (Subscribers): Components that register interest in specific event types or topics and process events as they arrive. Consumers have no knowledge of which producers generated the events.
  • Message Broker: The intermediary that receives events from producers, durably stores them, and delivers them to interested consumers. The broker guarantees reliable delivery, maintains message ordering when required, and persists events until all registered consumers have acknowledged receipt.
Real-World Analogy: IoT Air Quality Monitoring in New Delhi

Air quality sensors (producers) are deployed across the city, each measuring pollutants like PM2.5, PM10, CO, NO2, and SO2 at regular intervals. Each sensor publishes readings as events to a central message broker (e.g., Apache Kafka).

Multiple consumers subscribe to these events:
  • A real-time dashboard consumes events to display current air quality indices.
  • A data warehouse consumes events for historical trend analysis and regulatory reporting.
  • An alerting service consumes events and triggers notifications when pollutant levels exceed safety thresholds.
  • A ML prediction service consumes events to forecast pollution levels for the next 24 hours.
The sensors (producers) are unaware of these consumers. New consumers can be added at any time without modifying or reconfiguring the sensors.

6.3 Synchronous vs. Asynchronous Communication

In synchronous communication (REST, gRPC), the caller blocks until the callee responds:

# Synchronous (REST)
response = requests.post("http://log-service:8002/log", json=data)
# Execution blocks here until log-service responds
# ... continue processing only after response is received

This creates a temporal coupling: the caller's latency is the sum of its own processing time plus the callee's processing time plus network round-trip time. If the logging service is slow or unavailable, the prediction endpoint becomes slow or fails—even though logging is auxiliary to the core prediction function.

In asynchronous communication, the caller emits an event and proceeds immediately:

# Asynchronous (Event-Driven)
message_broker.publish("inference_log", data)
# Execution continues immediately without waiting
# Logging service will process the event when it's ready

The caller's latency is independent of the consumer's processing time. This is the primary motivation for using event-driven architecture for logging, notifications, and other non-critical-path operations in ML systems.

6.4 The Publish-Subscribe Pattern

Publish-subscribe (pub-sub) supports four cardinality patterns between producers and consumers:

  • 1:1: One producer, one consumer. Simplest case; functionally equivalent to a point-to-point queue.
  • 1:N: One producer, multiple consumers. Example: a single prediction event is consumed by a logging service, a monitoring service, and a real-time dashboard simultaneously.
  • N:1: Multiple producers, one consumer. Example: multiple model services (different model versions) all publish to a single logging consumer.
  • N:N: Multiple producers, multiple consumers. The fully decoupled scenario where any producer can reach any interested consumer without mutual awareness.

Producers and consumers can be added or removed dynamically without affecting the other side of the equation—this is the essence of loose coupling.

6.5 Message Brokers

The message broker is the critical infrastructure component that makes pub-sub reliable. It must provide:

  • Durable Storage: Events are persisted to disk until all registered consumers have acknowledged receipt, preventing data loss if a consumer crashes.
  • Message Ordering: Within a given partition or queue, events are delivered in the order they were produced—critical when event A (order placed) must be processed before event B (order shipped).
  • Delivery Guarantees: At-least-once, at-most-once, or exactly-once semantics, depending on the broker and configuration.
  • Scalability: The ability to handle millions of events per second through partitioning and horizontal scaling.

6.5.2 Broker Selection Criteria

Choosing a message broker involves evaluating three primary axes:

  1. Open-Source vs. Commercial/Managed: Kafka and RabbitMQ are free and open-source but require operational expertise to deploy, configure, monitor, and scale. Cloud-managed services (SQS, Azure Service Bus) eliminate operational overhead but incur per-message costs and vendor lock-in.
  2. Distributed Architecture Requirements: If the system spans multiple data centers or requires partitioned, replicated event logs with horizontal scalability, Kafka's distributed design (with ZooKeeper/KRaft for coordination) is the natural choice. RabbitMQ supports clustering but is not as inherently distributed as Kafka.
  3. Cloud Ecosystem Alignment: AWS-native organizations default to SQS and Kinesis; Azure-native organizations use Service Bus and Event Hubs; GCP-native organizations use Pub/Sub. Multi-cloud or on-premises deployments favor Kafka for its portability.

6.6 Event-Driven ML Logging Design

The event-driven architecture for the Iris classification system modifies the microservices demo by replacing the synchronous HTTP call to the Logging Service with an asynchronous publish to a RabbitMQ message broker:

6.6.1 Architecture

  1. API Gateway (Producer): Receives the client's prediction request, calls the Model Service synchronously (this remains synchronous because the client is waiting for the prediction), and upon receiving the prediction, publishes the input features and output prediction as an InferenceLog event to a RabbitMQ queue named inference_log. The API Gateway does not wait for acknowledgment from the logging consumer.
  2. RabbitMQ (Message Broker): Runs as a Docker container, exposing port 5672 for AMQP (Advanced Message Queuing Protocol) and port 15672 for the management UI. The inference_log queue persists events until consumed.
  3. Logging Service (Consumer): Subscribes to the inference_log queue and asynchronously consumes events, appending each to its log store (in-memory list in the demo, extensible to a database).
AMQP Protocol: RabbitMQ uses AMQP 0-9-1, a binary application-layer protocol distinct from HTTP. AMQP models messaging in terms of exchanges (which receive messages from producers), queues (which buffer messages for consumers), and bindings (which define routing rules from exchanges to queues). This provides more flexible routing than simple point-to-point queues—a single exchange can route messages to multiple queues based on routing keys, headers, or topic patterns.

6.6.2 Deployment Considerations

RabbitMQ is deployed as a Docker container:

docker run -d --name rabbitmq \
  -p 5672:5672 \
  -p 15672:15672 \
  rabbitmq:3-management

This command pulls the official RabbitMQ image with the management plugin enabled, maps port 5672 (AMQP protocol) and port 15672 (web management UI) to the host, and runs the container in detached mode.

Architectural Refinement: As discussed during the session, the demonstrated design has the API Gateway publishing to the message broker. A more architecturally pure approach would have the Model Service directly publish inference results to the broker, keeping the API Gateway focused solely on routing. The API Gateway would then only need to call the Model Service and return the result to the client, without any awareness of logging infrastructure. This offloads the gateway and adheres more strictly to the Single Responsibility Principle. Both designs are valid; the choice depends on whether one prioritizes minimal code changes (gateway-publishes) or architectural purity (model-service-publishes).

Chapter 7: Model Registry Pattern and Version Control for ML

Definition: The Model Registry pattern provides a centralized repository for versioning, tracking, managing, and governing machine learning models throughout their entire lifecycle—from experimentation through production deployment and eventual retirement.

7.1 The Registry Pattern Origin

The registry pattern originates from traditional software engineering, where a "registry" serves as a central hub for storing and discovering code artifacts (e.g., Docker images in a container registry, Java libraries in Maven Central, Python packages in PyPI). In ML, the registry concept is extended to encompass not just code but also trained model artifacts, their associated metadata, and the experimental context that produced them.

The need for robust model versioning and registry infrastructure becomes critical when ML pipelines move from exploratory notebook code to automated production pipelines. A set-and-forget approach—where a model is trained once and never updated—is rarely advisable for production systems and is considered an antipattern. Most ML-enabled systems need continuous learning with new data, retraining to handle drift, and regular experimentation with improved features and hyperparameters. The model registry is the infrastructure that makes this continuous evolution manageable.

7.2 Pipeline Antipatterns That Motivate Registries

Before understanding why registries and versioning are essential, it's important to recognize the common antipatterns they solve:

  • Big-Ass Script Architecture: A pipeline consisting of one or a few ad hoc scripts where all stages are entangled in a single codebase. Changes to one stage risk breaking others, and understanding the data flow between stages requires reading the entire script. Modularization with clear inputs and outputs per stage is the standard remedy.
  • Pipeline Jungle: A collection of scripts whose execution order and dependencies are undocumented and unclear. Team members may not know which scripts need to run in which order, or what temporary files must exist. Dedicated workflow orchestration infrastructure (Airflow, Kubeflow, Metaflow) addresses this by explicitly declaring dependencies and execution order.
  • Undeclared Consumers: Scripts or services that depend on the output of a pipeline stage without this dependency being explicitly documented or tracked. When the producing stage changes its output format, silent failures occur downstream.
  • Dead Experimental Code Paths: Code branches from past experiments that were never cleaned up, creating confusion about which code path is actually in production. Explicit experiment tracking and version control (both for code and artifacts) are the standard countermeasures.
  • Set and Forget: Training a model once and never updating it, even as data distributions drift and better techniques become available. This ignores the fundamental need for continuous learning and model improvement in production ML systems.

All of these antipatterns point toward the need for systematic artifact tracking, which the model registry pattern directly addresses.

7.3 Three Generations of Version Control

7.3.1 First Generation: File-Level Systems (1970s–1980s)

Early version control systems like RCS (Revision Control System) and SCCS (Source Code Control System) operated on individual files. A developer would "check out" a single file, make changes, and "check in" the modified version. Only one developer could work on a given file at a time (pessimistic locking). These systems had no concept of atomic changes spanning multiple files—each file was versioned independently. While obsolete today, they established the foundational concept of maintaining a change history with the ability to revert to previous versions.

7.3.2 Second Generation: Centralized Systems (1990s–2000s)

CVS (Concurrent Versions System) and later Subversion (SVN) introduced the centralized repository model. All version history was stored on a single server, and developers checked out working copies. Key advances included:

  • Multi-file atomic commits: Changes spanning multiple files could be committed as a single, indivisible unit.
  • Concurrent development: Multiple developers could modify the same file simultaneously; conflicts were resolved at commit time (optimistic locking).
  • Branching and tagging: Developers could create branches for experimental work and tags to mark release points.

Subversion remains in use in some organizations today, particularly those with strong centralized governance requirements.

7.3.3 Third Generation: Distributed Systems (2005–Present)

Git, created by Linus Torvalds for Linux kernel development, represents a paradigm shift to fully distributed version control. Every developer's working copy is a complete repository with full history. Key characteristics:

  • Local operations: Most operations (commit, diff, log, branch) are local and instantaneous because they don't require network access to a central server.
  • Flexible workflows: Teams can adopt centralized, feature-branch, GitFlow, or forking workflows depending on their collaboration model.
  • Staging area: The index (staging area) allows developers to craft commits with surgical precision, including only specific changes.
  • Cryptographic integrity: Every object (commit, tree, blob) is identified by a SHA-1 hash of its contents, making history tamper-evident.

The core Git workflow:

# Clone a remote repository to a local working copy
git clone https://github.com/org/repo.git

# Stage changes for the next commit
git add model.py data_loader.py

# Commit staged changes to the local repository
git commit -m "Add feature engineering for categorical variables"

# Push local commits to the remote repository
git push origin main
Git in ML Context: While Git excels at versioning code, it has fundamental limitations for ML workflows. Git is designed for text files (source code); it struggles with large binary artifacts like trained model weights (which can be hundreds of megabytes to gigabytes) and large datasets. This limitation motivated the development of specialized ML versioning tools that either wrap Git (DVC, which stores data and model hashes in Git while keeping the actual artifacts in remote storage) or bypass it entirely (MLflow, which maintains its own artifact store).

7.4 Modern Model Registry Tools

7.4.1 MLflow

MLflow is an open-source platform for the complete ML lifecycle, with four core components:

  • MLflow Tracking: Logs and queries experiments—parameters, metrics, code versions, and output artifacts. Each run is recorded with a unique ID, timestamp, and git commit hash, enabling full reproducibility.
  • MLflow Projects: Packages ML code in a reusable, reproducible format using a standardized project structure and Conda/Docker environments.
  • MLflow Models: Provides a standard format for packaging models that can be deployed across diverse serving environments (Docker, Azure ML, AWS SageMaker, Apache Spark).
  • MLflow Model Registry: A centralized model store with versioning, stage transitions (Staging → Production → Archived), annotations, and access controls. This is the "registry" component that directly implements the model registry pattern.

7.4.2 DVC (Data Version Control)

DVC extends Git's versioning capabilities to large files by storing metadata (file hashes, locations) in Git while keeping the actual data and model files in remote storage (S3, GCS, Azure Blob, or local filesystems). Commands like dvc add data.csv and dvc push parallel the Git workflow, making the transition intuitive for teams already using Git. DVC also provides pipeline definition and execution capabilities through dvc.yaml files, enabling reproducible ML pipelines with dependency tracking.

7.4.3 Weights & Biases (W&B)

W&B focuses on experiment tracking and visualization, providing real-time dashboards for monitoring training metrics, comparing runs, and collaborating on model development. It excels in deep learning workflows where visual inspection of loss curves, gradient distributions, and sample predictions is critical. W&B integrates model registry capabilities for versioning and lineage tracking.

7.4.4 Amazon SageMaker Model Registry

A fully managed service within the AWS ecosystem, SageMaker Model Registry catalogs models with versioning, metadata (training metrics, evaluation results), and approval workflows. It integrates natively with SageMaker training jobs, endpoints, and the broader AWS security model (IAM, VPC). The managed approach eliminates operational overhead but incurs AWS costs and creates vendor dependency.

7.5 The Four Artifact Streams in ML Versioning

A comprehensive ML versioning strategy must track four parallel streams of artifacts that evolve independently yet are interdependent:

  1. Code: The training scripts, preprocessing logic, model architecture definitions, and evaluation code. Versioned with Git.
  2. Data: The training, validation, and test datasets, including their provenance (where the data came from), preprocessing steps applied, and any data splits. Versioned with DVC, Delta Lake, or data catalogs.
  3. Models: The trained model artifacts—serialized weights, architecture graphs (TensorFlow SavedModel, ONNX), and associated metadata (hyperparameters, training duration, hardware used). Versioned with MLflow Model Registry, SageMaker Model Registry, or DVC.
  4. Experiments: The configuration that produced a given model: which code version, which dataset version, what hyperparameters, what random seed, what environment (Docker image, Python version, CUDA version). Tracked with MLflow Tracking, W&B, or experiment management platforms.
Reproducibility Scenario: A model deployed six months ago (v3.2) begins producing anomalous predictions. To diagnose the issue, the team needs to exactly recreate the conditions under which v3.2 was trained:
  • Checkout the code at the git commit recorded in the experiment tracker (git checkout a1b2c3d).
  • Retrieve the exact dataset version from DVC (dvc checkout dataset-v2.1.dvc).
  • Load the model artifact from the registry (MLflow run ID: mlflow models serve -m runs:/abc123/model).
  • Recreate the training environment from the recorded Conda environment or Docker image.
Only when all four streams are versioned in lockstep is true reproducibility achievable.

7.6 From Pipeline to Registry: The Automation Connection

The model registry does not exist in isolation—it is the hub that connects automated ML pipeline execution with model serving and monitoring. When a pipeline is fully automated, the registry becomes the handoff point where trained models are promoted through stages (Staging → Production → Archived) and where serving infrastructure discovers which model version to deploy:

  1. Pipeline executes (triggered by a scheduler, new data arrival, or manual command) → Data collection → Data cleaning → Feature engineering → Model training → Model evaluation.
  2. Model is registered in the registry with metadata (run ID, parameters, metrics, artifacts).
  3. Evaluation gate checks if the new model outperforms the current production model on held-out data and/or fairness criteria.
  4. Stage transition promotes the model to Staging for integration testing, then to Production upon approval (manual or automated).
  5. Serving infrastructure discovers the new production model version from the registry and begins routing traffic to it—often via canary releases where the new model initially serves only a subset of users while monitoring for degradations.
  6. Monitoring component observes the model in production and may trigger retraining or rollback if issues are detected.

Workflow orchestration tools like Apache Airflow, Kubeflow Pipelines, Netflix's Metaflow, and Spotify's Luigi explicitly enforce modular pipeline stages and manage their execution order, dependencies, error handling, and retries. These tools integrate with model registries to form a complete MLOps automation fabric.

Designing for Experimentation: While building automated, robust pipelines requires substantial engineering investment, it pays off through improved ability to experiment. Orchestration systems can schedule multiple offline experiments in parallel with different hyperparameters and feature sets. Automated pipelines remove manual steps and common error handling that otherwise slow down experiments. Investments in telemetry, system monitoring, and A/B testing infrastructure allow data scientists to evaluate models in production with fast feedback from real production data. This closed-loop intelligence pattern—where production data continuously feeds back into model improvement—is a key competitive advantage of mature ML organizations.

Q: What are the three core activities that take place in the write (ingest) pipeline of a CQRS-based RAG architecture?

Explanation: In the write pipeline (ingest.py), the three core activities are: (1) loading and chunking documents using a text splitter like RecursiveCharacterTextSplitter with configurable chunk size and overlap, (2) generating embeddings for each chunk using a model like OpenAI's text-embedding-3-small, and (3) persisting the document chunks with their embeddings into a vector database such as ChromaDB. These operations happen independently of the read/query pipeline.

Q: A company's ML application experiences a 10x surge in prediction requests but the model itself rarely needs updating. Which architectural pattern best addresses this scaling requirement?

Explanation: Under the microservices ML pattern, the prediction (inference) service is deployed independently from the model service. A surge in prediction requests can be addressed by scaling only the prediction service horizontally (adding more instances), without needing to scale the model loading or preprocessing components. In a monolithic architecture, the entire application would need to be scaled as a single unit, which is inefficient when only one component is under load.

Q: Which protocol is most suitable for high-speed, resource-constrained inter-service communication in a microservices ML system?

Explanation: gRPC uses Protocol Buffers (Protobuf) as its binary serialization format and HTTP/2 as its transport protocol. The binary format is significantly more compact than JSON, reducing payload size and parsing overhead. HTTP/2 provides multiplexing, header compression, and bidirectional streaming. These properties make gRPC the fastest option among the listed protocols, ideal for resource-constrained or latency-sensitive environments. The trade-off is that both communicating services must implement the same Protobuf contract (proto file).

Q: In the event-driven architecture for ML logging, what is the role of RabbitMQ between the API Gateway and Logging Service?

Explanation: RabbitMQ serves as a message broker implementing the Advanced Message Queuing Protocol (AMQP). When the API Gateway publishes inference log data (input features and prediction output) to a named queue (e.g., 'inference_log'), RabbitMQ persists and reliably holds that data. The Logging Service, acting as a consumer, subscribes to the queue and asynchronously retrieves events as they become available. This decouples the producer from the consumer: the API Gateway does not wait for the logging operation to complete, reducing request latency.

Q: What is the primary architectural advantage of keeping the API Gateway focused solely on request routing, rather than embedding logging or business logic within it?

Explanation: The API Gateway's primary responsibility is routing—accepting client requests and forwarding them to the appropriate backend service. Embedding logging logic, data transformation, or business rules inside the gateway violates the Single Responsibility Principle and creates a 'smart gateway' anti-pattern. A bloated gateway becomes a development bottleneck (every team needs changes there), a performance bottleneck (all traffic passes through it), and a single point of failure. Instead, logging should be delegated to a dedicated service or handled asynchronously via a message broker.

Q: Which of the following artifacts must be tracked by a comprehensive model registry in an MLOps workflow?

Explanation: A complete model registry must track four parallel streams of artifacts: (1) the model itself (serialized weights, architecture definition), (2) the training code that produced it, (3) the exact dataset version used for training (often tracked via DVC or similar data versioning tools), and (4) the experiment configuration including hyperparameters, evaluation metrics, and environment details. Tools like MLflow provide this comprehensive tracking, enabling full reproducibility—you can return to any past experiment and recreate its exact conditions and outputs.
