2.1 What Spell Check and Grammar Check Cover

Hook: Almost every reader of these notes has typed a message, trusted autocorrect, and only later noticed the tool changed a word into something unintended. That everyday mix of help and harm is exactly why spell check and grammar check open this course: they are small tools with outsize influence on everything built on top of them.

A spell checker (a program that finds misspelled words and proposes fixes) sits underneath a grammar checker (a program that tests whether a sentence follows sentence-structure rules and reads as coherent). Grammar checking is the wider task, and it usually runs spell checking as an implicit first step: there is little point testing sentence structure while the words themselves are still broken. The two tasks share methods and technology, and both draw on linguistics, machine learning, and transformer models, so the techniques in this lecture carry over to later applications in the course.

Core idea. Spell checking answers "is each word valid, and if not, what was intended?" Grammar checking answers "does the whole sentence hold together, in structure and in meaning?" The second question contains the first, which is why pipelines in this lecture always clean words before they judge sentences.

Think of a guest list at a door. The spell checker is the bouncer with the list: any string not on the list is stopped at once. The grammar checker is the seating planner inside: even when every guest is on the list, the arrangement can still be wrong. The picture breaks at one point — a bouncer never asks whether two listed guests swapped invitations, while a checker must — and that break points straight at real-word errors below.

2.1.1 Non-Word Errors and Real-Word Errors

Spelling mistakes split into two groups. A non-word error (a typed string that is not a valid English word at all, such as a mangled form of "weather" missing its "O") fails the guest-list test at once, so detection is the easy half of the job. A real-word error (a valid word used in the wrong place, such as writing "two" where "too" belongs, or "their" where "there" belongs) passes the guest-list test, so a dictionary lookup alone cannot catch it. Detection must look at the surrounding context words, which makes real-word errors the harder problem. Choosing the best fix can still need context in both cases, but only the real-word case needs context just to notice anything is wrong.

Scope: Dictionary membership decides non-word detection only when the dictionary fits the domain. A medical, legal, or code-mixed vocabulary needs its own word list, or valid domain terms get flagged as errors. Real-word detection always needs context, no matter how complete the dictionary is.

2.1.2 Grammar Error Types

Grammar mistakes divide into two main families. Syntactic errors (breaks of sentence-structure rules, such as verb-form or word-order mistakes) fail the "well formed" test. A sentence that should use a continuous verb form but uses a plain form instead is a syntactic slip. Semantic errors (sentences that read smoothly word by word yet fail to make sense as a whole) pass the structure test and fail the meaning test. The check for a semantic error is whether the sentence means something coherent in its context. This distinction builds on the levels of language understanding: syntax asks whether the sentence is well formed, while semantics asks whether it is meaningful.

Common grammar slips include missing articles such as "a" and "the", which writers often drop in quick notes but which can change how a sentence reads, and punctuation mistakes involving commas, colons, apostrophes, and quotation marks. Punctuation carries real signal for machine understanding, so checkers flag it even when human writers ignore it.

Pitfalls. Beginners often treat grammar checking as spell checking with a bigger dictionary. That view misses both halves: structure rules cannot be listed as words, and meaning checks need context wider than one sentence. A second trap is trusting punctuation habits from chat messages; models trained on edited text still penalize missing commas and apostrophes.

Stored-history warning. One practical warning from the session is that keyboard history can backfire: once a mistyped form gets stored, the tool may keep suggesting the wrong form, so stored personal history needs care. The same learned-history effect returns in statistical methods, where training counts decide what the system prefers.

2.1.3 Student Questions and Answers

Q: Where do people actually use spell check and grammar check?

A: The listed uses include word processors, mail drafts, phone typing, chat apps, and documentation. Almost everyone already relies on these tools daily, often without noticing, and forgetting correct spellings because of tool reliance is a common experience. The course adds a deeper reason: every later language application in this subject reuses these same checking stages.

Several students asked the same usage question in different words, so the single answer above merges them.

Q: What is the difference between a non-word error and a real-word error?

A: A non-word error is not a valid word, so it is comparatively easy to detect with a dictionary. A real-word error uses valid spellings in the wrong context, so detection must look at neighboring words. The two cases need different handling because candidate generation and context use differ between them.

Recap + bridge. Spell checking guards words, grammar checking guards sentences, and the hard cases in both need context. With the territory mapped, the next section shows why this "simple" first application decides the quality of agent pipelines built far above it.

Spell and grammar checking matter well beyond personal writing tools. Document editors and mail composers catch slips before they ship, phone keyboards repair typing on the fly, and documentation pipelines keep published text clean. In education technology the same machinery scores learner writing, and in legal or medical drafting it guards high-stakes wording. The session's through-line is that these are not side utilities: they are the intake filter for every text-driven system that follows.

2.2 Why Text Quality Matters in Agentic AI

Hook: A single wrong letter in a prompt can send an agent to the wrong city, fetch the wrong documents, and call the wrong tool — then pass that mistake down a chain of further agents. This section shows why cleaning text is load-bearing work in agent systems, not cosmetic polish.

A natural question is whether spell and grammar checking still matter now that large language models can already handle noisy input. The answer given is yes: text quality matters more, not less, in prompt-driven and agent-driven systems. Everything in these systems runs on text, so a typo can bend the intent of a request and lower the quality of the result. Modern models do run internal correction before the main reasoning step, but that correction is itself a required pre-processing stage in the pipeline, not a reason to skip the topic.

Think of the pipeline as a water supply. The prompt is the reservoir, retrieval and tool calls are the treatment plants, and the final answer is the tap. Dirt in the reservoir reaches every stage downstream. The picture breaks only in that water plants can test purity directly, while a language model must guess what the user meant — which is exactly why the cleaning step deserves study.

2.2.1 Input-Side Effects: Prompts, Retrieval, and Tool Calls

Prompts carry the user intent, and distorted prompts distort what the agent tries to do. Query normalization is one visible example: a mistyped query about the Pune weather is automatically repaired to "weather in Pune" before search runs. Retrieval-augmented generation depends on the same step. Retrieval matches the prompt against stored chunks through word vectors, so a misspelled prompt produces the wrong vector and pulls back the wrong chunks. A weather question that retrieves travel writing instead of forecasts fails before generation even starts.

Tool calling is equally strict. When an agent calls a tool such as a calculator or a calendar by name, or passes arguments to it, the names and arguments must match exactly; a wrong token means the call fails or goes to the wrong place. In multi-step agent pipelines, where the output of one agent becomes the input of the next, an error early in the chain spreads to every later step.

Scope: Input cleaning applies wherever raw user text enters the system — prompts, search boxes, tool arguments, and agent-to-agent messages. It stops helping once the text is already canonical (for example, IDs generated by the system itself). Over-cleaning there can rewrite a valid code or name into something else.

2.2.2 Output-Side and Pipeline Effects

Generated mail, reports, and summaries must read as polished, grammatically correct text, so checking also runs as a post-processing step on outputs. Wrong input or wrong intermediate text can push the model toward hallucinated answers, which here means confident output built on a misread request: the model answers fluently, but answers the wrong question. User trust is at stake as well: visible typos and broken sentences in system output put users off, whatever the underlying model quality. There is also a cost angle for systems that call external model APIs. Sending a distorted prompt, getting a poor result, asking for correction, and resending tokens all burn paid calls, so cleaning text before the call keeps enterprise token spend down.

Pitfalls. Two beginner traps sit here. First, assuming a strong model makes cleaning redundant; the session's point is that the model merely hides the cleaning step inside itself. Second, cleaning only user prompts while ignoring agent-to-agent messages; in chained pipelines the middle messages need the same treatment.

Recap + bridge — Exam note: Expect questions linking correction quality to retrieval quality, tool-call reliability, and output trust, not just to isolated spelling fixes. The pattern to reuse: name the stage (prompt, retrieval, tool, middle agent, output), name what breaks there, and name the cost (wrong answer, failed call, lost trust, extra tokens). That input-to-output chain is the spine the next section's hybrid methods are built to protect.

Customer-support agents show the full loop in one product: they normalize the incoming question, retrieve help articles with clean vectors, call order-tracking tools with exact arguments, and return polished replies. Search engines, voice assistants, and code copilots all run the same intake-and-outlet cleaning. The domain lesson is one paragraph: wherever text is both the control channel and the data channel, its quality is a reliability and cost control, not a style choice.

2.3 From Rules to Transformers: the Hybrid Picture

Hook: If transformers are so strong, why does this lecture still teach dictionary lookup from decades ago? Because the systems that actually ship mix old and new — and the old half often wins on the small, cheap fixes.

Correction methods range from rule-based and dictionary lookup through statistical and machine-learning models to transformers and large language models. A fair question is why simple dictionary methods still appear in a course taught in the age of transformers and fine-tuning. The reason is practical: production systems, from large companies to new startups, widely use hybrid designs that mix approaches. Dictionary and statistical steps sometimes beat pure transformer setups on small corrections, and they win on compute cost, memory, and carbon footprint. Grammarly is cited as an example of a leading commercial tool that combines methods rather than relying on one model alone. Statistical and transformer steps do the heavy lifting, while dictionary steps still handle small, cheap corrections. Because hybrids are the industry norm, each family of methods deserves study on its own terms.

Core idea. Rule and dictionary steps are cheap, exact, and explainable; statistical steps rank by evidence; transformer steps handle long context and rewriting. A hybrid pipeline spends each method where it is strongest instead of asking one model to do everything.

Think of a hospital triage desk. Dictionary lookup is the nurse who handles scrapes at once without calling a surgeon; statistics is the duty doctor who ranks the waiting queue by urgency; the transformer is the specialist called in for complex cases. The analogy breaks where medicine routes each patient to exactly one doctor, while text pipelines stack all three stages on the same sentence — cheap filters first, heavy models only on what survives.

Scope: Hybrids win when traffic is heavy and most errors are small: dictionaries clear the easy majority, statistics rank the ties, transformers take the residue. The hybrid pays off less for one-off creative rewriting, where almost every input needs the heavy model anyway.

Pitfalls. Treating "hybrid" as a magic label is the main trap; a hybrid only helps when each stage has a clear job and a handoff test. A second trap is benchmarking a transformer alone on single-typo fixes, where dictionaries already win, and concluding the transformer is weak — the comparison is mismatched, not the model.

Recap + bridge. Hybrids are the industry norm because cost, speed, and accuracy point the same way: cheap exact steps first, evidence-ranked steps next, heavy rewriting last. The next section starts that stack at the bottom, with dictionary methods and edit distance.

The same stack appears across the field. Search engines normalize cheaply before neural ranking, translation systems keep rule-based number and date handling beside neural decoders, and speech pipelines keep dictionary pronunciation lists beside neural acoustics. The session's practical note closes the loop: because hybrids are what ships, each family below is worth learning on its own terms rather than as history.

2.4 Dictionary Methods and Edit Distance

Hook: How does a word processor know that "ACRESS" was probably "ACTRESS" and not "ACROSS"? It counts single-letter changes — and almost always, the right answer is one small step away.

The simplest correction family is dictionary lookup. Maintain a collection of correctly spelled words for the application. When an input word is missing from the collection, measure how far it sits from each candidate word and suggest the closest ones. Closeness is measured with edit distance (the smallest number of single-character changes that turn one string into another), most often the Levenshtein distance and its Damerau-Levenshtein variant, which also counts the swapping of two adjacent letters as a single operation. The same distance idea reappears inside statistical and transformer pipelines, so it is worth learning precisely.

Core idea. Distance turns "looks similar" into a number: count the missing, added, swapped, or replaced letters between the typed string and each dictionary word, then suggest the words with the smallest count. Everything else in this section is how to count fast and where to stop looking.

Think of two stacks of letter tiles on a table, one spelling what was typed and one spelling a candidate word. The allowed moves are removing a tile, adding a tile, swapping two neighbors, or flipping one tile to another letter. The distance is the smallest number of moves that turns one stack into the other. The picture breaks in one place — tiles have no sound, so "FONE" and "PHONE" look far apart though they sound close — and that break is exactly why phonetic codes get their own subsection later.

2.4.1 The Four Single-Character Operations

In plain words, the distance counts how many single letters are missing, added, swapped, or replaced between the typed string and the correct word. It counts single-character edits between the typed string and a dictionary word, using insertion, deletion, substitution, and transposition as the four moves.

Formalize. Reconstructed as LaTeX, the dynamic-programming recurrence for the distance table reads as follows. Let \(d[i][j]\) be the distance between the first \(i\) characters of the typed string and the first \(j\) characters of the candidate word, where \(i\) and \(j\) are prefix lengths and \(c\) is 0 when the two current characters match and 1 otherwise:

\[ d[i][j] = \min(d[i-1][j] + 1, d[i][j-1] + 1, d[i-1][j-1] + c) \]

The table needs edges before the recurrence can run. An empty typed prefix needs one insertion per candidate character, and an empty candidate prefix needs one deletion per typed character, so \(d[i][0] = i\) and \(d[0][j] = j\) for all \(i\) and \(j\). The answer sits in the bottom-right cell \(d[m][n]\), where \(m\) and \(n\) are the two string lengths.

The three options inside the minimum are deletion (drop a character from the typed string), insertion (add a character to match the candidate), and substitution or match (replace or keep the current character). Transposition, the swap of two neighboring characters such as typing "CA" for "AC", is the fourth operation added by the Damerau-Levenshtein variant and counts as one step. The table stores the results of earlier prefix comparisons so each cell builds on already computed values.

Four concrete patterns appear repeatedly. A deletion error (a typed form missing a letter the correct word has) drops a letter, as in a form of "weather" missing its "O". An insertion error (a typed form carrying one letter too many) adds an extra letter. A transposition error (two neighboring letters trading places) swaps two adjacent letters, as in "I" and "E" trading places. A substitution error (one letter standing in for another) replaces one letter with another, as in typing "R" where "C" belongs. The distance for the weather-style examples is 1 for a single changed letter and 2 where two letters differ.

Worked mini-table. Take typed "CA" against candidate "AC" and fill the table cell by cell. Edges first: \(d[0][0] = 0\), \(d[1][0] = 1\), \(d[2][0] = 2\), \(d[0][1] = 1\), \(d[0][2] = 2\). Then \(d[1][1]\) compares "C" with "A" (\(c = 1\)): \(\min(2, 2, 1) = 1\). Next \(d[1][2]\) compares "C" with "C" (\(c = 0\)): \(\min(3, 2, 1) = 1\). Next \(d[2][1]\) compares "A" with "A" (\(c = 0\)): \(\min(2, 2, 1) = 1\). Last, \(d[2][2]\) compares "A" with "C" (\(c = 1\)): \(\min(2, 2, 2) = 2\). The Levenshtein distance is 2, while the Damerau-Levenshtein distance is 1, because the single adjacent swap counts as one move there. Sense-check: two letters out of order need two single-letter fixes but one swap, so both numbers behave as expected.

Scope. Edit distance fits alphabetic slips of one or two characters in ordinary-length words. It breaks down for long phrases (cost grows with the product of the lengths), for sound-based mistakes (spelling distance misses them), and for real-word errors (every candidate is at distance 0 from itself). Those are the jobs of phonetic codes, n-gram context, and sequence scoring later in the lecture.

Pitfalls. Beginners often mix up the direction of insertion and deletion: always read them from the typed string toward the candidate word. A second trap is forgetting the table edges; without \(d[i][0] = i\) and \(d[0][j] = j\) the recurrence has nothing to build on. A third is treating transposition as free in plain Levenshtein — it costs 2 there (two substitutions) and 1 only in the Damerau variant.

The session's comparison point is worth keeping: Levenshtein counts three operations and treats a swap as two changes, Damerau-Levenshtein adds the swap as a fourth single-cost operation and matches human typing better, and Jaro-Winkler (raised in discussion as a related fuzzy-matching similarity) scores similarity rather than counting edits, weighting matching prefixes more. When the task is "how many keystrokes went wrong," use an edit distance; when the task is "how similar do these feel," a similarity score fits better.

2.4.2 Worked Examples: From a Typo to Candidate Fixes

Take the mistyped string "ACRESS" as the running example. Scanning the dictionary with edit distance 1 produces a set of candidate corrections, each reached by one of the four operations. The candidate "ACTRESS" is a deletion-type fix: the typed string is missing the letter "T", so restoring "T" gives the correct word.

Worked set. From "ACRESS", one move reaches each of these: delete nothing but restore "T" to get "ACTRESS" (deletion-type fix from the typist's side: the typed string dropped "T"); remove one extra letter to get forms such as "ACRES" or "CRESS" (insertion-type fixes); swap the leading "AC" back to "CA" to get "CARESS" (transposition-type fix); replace the wrongly typed "R" with the correct "C" to get "ACCESS" (substitution-type fix). Further single-step neighbors include "ACROSS" (replace "E" with "O" and drop one "S") and doubled-letter variants, where either of a doubled letter counts as the extra one, which is why doubled-letter cases get listed separately. Every candidate in this set sits exactly one single-character operation away from the typed string — that shared distance of 1 is why ranking needs statistics next.

A second worked case is the missing-letter form of "weather" discussed above: the typed string lacks "O", the distance to the correct word is 1, and the fix is to restore that one letter. The swapped-letter case ("I" and "E" trading places) likewise has distance 1, and the fix is to swap the two letters back.

2.4.3 Generating and Ranking Candidates

Procedural core — Purpose. The corrector must turn one bad string into a short ranked list of likely intentions without scanning the whole dictionary naively. Inputs and outputs. In goes the typed string plus the dictionary; out comes the top match or the top \(K\) options for a human to pick. Steps. First, generate the candidate set: scan the dictionary for words within the allowed edit distance of the typed string, often with a trie or prefix tree or a BK-tree to keep the search fast. Second, rank the candidates and either return the top match or show the top \(K\) options. Word processors and mail clients show both behaviors: sometimes they replace the word directly, and sometimes they offer a short list.

The distance alone cannot break ties between two candidates at the same distance, which is why statistical scoring is needed on top. Most human typing slips change only one or two characters of a word, and the session cites roughly 80 percent of mistakes falling within distance 1 with most of the rest within distance 2. This matches the long-standing typing-study finding (Damerau; Kukich) that the large majority of human misspellings differ from the target by a single insertion, deletion, substitution, or transposition — so a distance-1-or-2 search radius is empirically grounded, not just convenient. A wide whole-dictionary search feels needed at first, but the distance-1-or-2 radius suffices for almost all real typos. The threshold is tunable: raise it for languages or domains with longer words and noisier input, lower it to cut compute time and latency. Trace. With "ACRESS", radius 1 returns the handful above; radius 2 would return hundreds, most of them implausible; radius 0 returns nothing, since the string itself is not a word. Cost. Candidate counts explode with radius, so radius 1 is the interactive default and 2 the outer limit. When to use. Dictionary generation fits isolated non-word slips; it hands off to statistics whenever ties or context appear.

Exam note: Be ready to walk through all four operations on a given typo and to explain why distance 1 or 2 is the standard search radius. Name the operation, show the changed letters, and quote the coverage: about four in five typos sit at distance 1.

2.4.4 Phonetic Matching and the Soundex Code

Dictionary lookup by letters fails when the mistake is about sound rather than spelling, for instance typing "FONE" for "PHONE". Speech-to-text output has the same property. The phonetic family of methods handles this by converting each word into a short code built from how it sounds and then matching codes instead of letters.

The Soundex code. The Soundex algorithm is the named example. It keeps the first letter, then maps consonants to digits — B, F, P, V to 1; C, G, J, K, Q, S, X, Z to 2; D, T to 3; L to 4; M, N to 5; R to 6 — while vowels (A, E, I, O, U, Y) and the letters H and W contribute no code digit, and the result is padded or cut to one letter plus three digits. That matches the session's description: vowels largely ignored, consonants such as "M", "T", and "H" handled by the digit/drop rules above (M maps to 5, T maps to 3, H is dropped), producing a short four-character code for each word. Words with similar codes count as candidate corrections.

Surnames that sound alike but spell differently share a code, which is the point of the method: "Smith" and "Smyth" collide on purpose. This course keeps phonetic methods at concept level and spends its depth on Levenshtein-style distances, which also feed the statistical methods. The scope boundary is firm: phonetic codes propose sound-alike candidates but cannot rank them, so they feed the same statistical ranking as letter-based candidates.

2.4.5 Student Questions and Answers

Q: What does Levenshtein distance actually measure between two words?

A: It counts single-character edits between the typed string and a dictionary word, using insertion, deletion, substitution, and transposition. The distance is measured in characters: how many letters are missing, added, swapped, or replaced. A fuzzy-matching view of the same idea also covers the related Jaro-Winkler similarity raised in discussion.

Q: How does knowing the distance help fix a spelling?

A: The distance is computed against a dictionary of correct words, which is why these are called dictionary-based methods. Words with the smallest distance, meaning the greatest similarity, are suggested as corrections. When several candidates tie, the system shows the top options and lets the application or the human pick.

Recap + bridge. Dictionary methods turn similarity into a countable distance, generate every word within radius 1 or 2, and lean on sound codes when letters mislead. But distance alone cannot pick between "ACTRESS" and "ACROSS" — the next section adds the statistical ranking that breaks ties by evidence.

Search boxes, phone keyboards, and DNA-sequence alignment all use the same distance machinery (biology calls it edit distance on base pairs). Spelling correction is the friendliest face of a family that includes diff tools, plagiarism detectors, and bioinformatics — anywhere two strings must be compared by cheapest transformation.

2.5 Statistical Correction With the Noisy Channel

Hook: "ACTRESS" and "ACROSS" both sit one step from "ACRESS" — so which one did the typist mean? Counting alone cannot answer. This section adds the evidence that can: how common each word is, and how often each typo really happens.

Dictionary lookup can propose candidates but cannot rank ties, and it knows nothing about how likely each word is. Statistical methods add that ranking with the noisy-channel idea (a model of typing in which the correct word passes through a noisy channel that corrupts it into the observed string). Correction means running the channel in reverse: given the observed incorrect string \(X\), find the vocabulary word \(W\) most likely to have produced it.

Think of a detective revising a hunch as clues arrive (the Bayes update from the analogy bank). The prior is the starting hunch: "ACTRESS" is a rare word, "ACROSS" is common. The likelihood is the clue: this particular typo pattern points more at one suspect than the other. The detective multiplies hunch by clue-fit for each suspect and arrests the highest product. The picture breaks where detectives weigh testimony subjectively; here both numbers come from counts in training data, so corpus quality decides system quality.

Formalize. In plain words, the goal is finding the most probable intended word given the incorrect word, written with an argmax over the vocabulary. Reconstructed as LaTeX, with \(V\) as the vocabulary and \(\hat{W}\) as the chosen correction:

\[ \hat{W} = \arg\max_{W \in V} P(X \mid W) \, P(W) \]

The full Bayes form starts from the posterior \(P(W \mid X) = P(X \mid W) \, P(W) / P(X)\). Since the denominator \(P(X)\) is the same for every candidate, it is dropped from the comparison: ranking by the posterior is identical to ranking by the two-term product. The two kept terms have standard names: \(P(W)\) is the prior probability of the word (how common the word is before seeing any typo, written \(P(W)\)), and \(P(X \mid W)\) is the likelihood, also called the channel-model probability (how often the correct word \(W\) gets typed as the string \(X\)). Dictionary methods need no training and use little compute or memory; every corpus-based method, statistical or neural, needs good domain training text.

In plain words: for each candidate word \(W\), multiply the chance that \(W\) gets typed as \(X\) by how common \(W\) is, and pick the candidate with the largest product. Factuality check (spot-check). If \(X = W\) (the typed string is already correct), the likelihood is near 1 and the prior picks the commonest reading — the model prefers to leave correct text alone, which is the desired behavior.

Scope: The noisy channel fits isolated single-word slips with a closed vocabulary and representative training counts. It breaks when the vocabulary is open (new names appear daily), when counts come from the wrong domain, or when the error spans whole phrases — those need context models and sequence scoring.

2.5.1 The Prior: How Common Is the Word

The prior is the easy term. Count how often each word occurs in a large, clean English corpus and divide by the total word count. Stated as a recipe: the occurrences of the word out of, say, a million running words.

The prior formula. Reconstructed as LaTeX, with \(C(W)\) as the count of word \(W\) in the corpus and \(N\) as the total number of corpus words:

\[ P(W) = \frac{C(W)}{N} \]

Here \(C(W)\) is a raw count (a whole number) and \(N\) is the corpus size, so \(P(W)\) always lands in \([0, 1]\) — the boundary check every probability must pass.

Large public text collections such as web crawls, Google Books, and contemporary English corpora supply these counts, and no accelerator hardware is needed to compute them. Real-world probabilities are tiny, around one in tens of billions, so implementations often work with logarithms (adding log-probabilities instead of multiplying tiny numbers, which keeps the values manageable); the ranking stays the same either way, because the logarithm is monotonic.

2.5.2 The Likelihood: How Often Does This Typo Happen

The likelihood is the harder term. It asks how often people type the string \(X\) when they mean the word \(W\), which needs a parallel collection of correct-to-incorrect pairs. The intuition is historical: out of all the times writers meant "THEIR", how often did they type "THIER".

The likelihood formula. Reconstructed as LaTeX, with \(C(X, W)\) as the number of times \(W\) was typed as \(X\) and \(C(W)\) as the total occurrences of \(W\):

\[ P(X \mid W) = \frac{C(X, W)}{C(W)} \]

The numerator can never exceed the denominator (a word cannot be mistyped as \(X\) more often than it occurs), so the ratio stays in \([0, 1]\) — the second boundary check. Limiting case: with infinite clean data and zero typos, \(P(X \mid W) = 1\) when \(X = W\) and 0 otherwise, and the channel reduces to dictionary lookup.

Open collections of correct and incorrect spelling pairs make this countable: each entry lists a correct word beside its observed mistypings, and the pair "THIER" typed for "THEIR" is one concrete row. Because the likelihood needs labeled mistake data while the prior needs only raw text, training-data availability is the central requirement of the statistical path. A common reading is that transformers always win, but the correction is that counts win on small problems with less compute: neural models estimate far richer patterns automatically, but only because they train on web-scale data with heavy compute, which is wasteful for a small problem that counts can already solve.

2.5.3 Smoothing Unseen Edits

Some single-letter confusions never appear in the training pairs, which would give them probability zero and lock those corrections out entirely. The fix is smoothing, the same idea used in Naive Bayes classifiers. Concretely, this is add-one (Laplace) smoothing over the confusion counts: add one to each operation count in the numerator and add the background count of the relevant character in the denominator from the training corpus. The session's recipe — adding one upstairs and the character count downstairs — is this standard add-one smoothing applied at the single-edit level rather than over the whole vocabulary. Smoothed estimates stay small for genuinely rare confusions but never hit absolute zero, so no candidate is ruled out by a gap in the data.

Pitfalls. Three traps cluster here. First, swapping prior and likelihood: the prior never mentions the typo, the likelihood never mentions general frequency. Second, reintroducing the dropped denominator \(P(X)\); it is constant across candidates and cancels. Third, skipping smoothing and shipping zero probabilities, which silently deletes valid corrections the training pairs happened not to contain.

2.5.4 Worked Example: Scoring the "ACRESS" Candidates

Return to the mistyped "ACRESS" and its edit-distance-1 candidates such as "ACTRESS". Each candidate is scored with the two-term product.

Worked scoring. For "ACTRESS", the likelihood term comes from the deletion count: how often "CT" was typed as "C" in the Norvig correction pairs shown in the session (the deletion-count recipe: \(P(\text{"C"} \mid \text{"CT"})\) estimated from pair counts). The prior term comes from the ordinary corpus frequency of "ACTRESS". Multiplying the two gives the posterior score for that candidate, about \(2.8 \times 10^{-9}\) (the session states "2.8" on a scale of one-billionth, i.e. \(10^{-9}\), which matches the product of a rare-word prior around \(10^{-7}\) with an edit likelihood around \(10^{-2}\)). Repeat the same multiplication for every candidate, then take the argmax: the candidate with the highest score wins. Candidates far below the top two drop out quickly, while close pairs such as "ACTRESS" and "ACROSS" survive to the context stage. Even when every score carries a factor like one in ten billion, the ordering is what matters, and the largest value is still identifiable. Sense-check: a rare word with a very natural typo can outscore a common word with an odd one — the product lets evidence beat frequency.

2.5.5 Student Questions and Answers

Q: The Bayes setup uses posterior, prior, and likelihood. Which is which here?

A: Given the incorrect word, the chance that \(W\) is the intended word is the posterior. \(P(W)\) is the prior, meaning how common the word is. \(P(X \mid W)\) is the likelihood, meaning how often that correct word gets typed as this incorrect string. The denominator is dropped because it is identical for every candidate being compared.

Q: How do we actually compute the prior?

A: By counting. Divide the occurrences of the single word by the total words in the corpus. No chain rule is needed because only one word is involved. Any large English corpus, including encyclopedia-scale text, works.

Q: How do we compute the likelihood if it is a conditional probability?

A: With a different corpus: a parallel collection recording how often each incorrect string replaced each correct word. The needed history is how many times this typo stood in for that word. Raw web text cannot supply this; mistake-pair collections can.

Recap + bridge. The noisy channel turns ranking into arithmetic: prior times likelihood per candidate, argmax over the set, smoothed so nothing scores exactly zero. Single-word scores still tie on close pairs — the next section lets the neighbors vote.

Spam filters, speech recognizers, and machine-translation decoders all run this same channel in reverse: propose what was intended, weight by prior plausibility and channel evidence, pick the argmax. Spelling correction is the smallest working example of a pattern that scales to whole sentences and utterances.

2.6 Context: From Single Words to N-Grams

Hook: "ACROSS" beats "ACTRESS" on frequency alone — yet any reader of the sentence knows the person word is right. The neighbors know something the word counts do not.

Single-word scores fail when two candidates have nearly equal posteriors. The concrete case: "ACROSS" can outscore "ACTRESS" on individual frequency even when the sentence wants the person word. Context breaks the tie. The fix is to weight each candidate by how well it fits its neighbors, using the same n-gram language modeling that counts word pairs and triples in a corpus.

Think of a hiring panel. The single-word score is one interviewer's mark; the bigram score is a second interviewer who only asks "does this candidate fit the team next door?" The final hire needs both marks. The picture breaks where panels can disagree honestly; here the two scores multiply into one ranking, so disagreement resolves by arithmetic, not debate.

2.6.1 Bigram and Trigram Scoring

Formalize. An n-gram model (a probability estimate built from counts of word sequences of length \(n\)) checks the chance of the candidate given its neighbors. Reconstructed as LaTeX, the bigram score for word \(W_i\) after previous word \(W_{i-1}\) is the pair count divided by the count of the previous word alone, with \(C(\cdot)\) as corpus counts:

\[ P(W_i \mid W_{i-1}) = \frac{C(W_{i-1}, W_i)}{C(W_{i-1})} \]

\(C(W_{i-1}, W_i)\) counts the ordered pair as it appears in running text; \(C(W_{i-1})\) counts every occurrence of the previous word. The ratio stays in \([0, 1]\) because the pair cannot outnumber its own first half.

Word order matters: the count of "versatile actress" is not the count of "actress versatile". A common bag-of-words counting mistake ignores that order, so the fix is order-sensitive bigram counting where the pair order decides the count.

Trigram scoring extends the same idea to two neighbors:

\[ P(W_i \mid W_{i-2}, W_{i-1}) = \frac{C(W_{i-2}, W_{i-1}, W_i)}{C(W_{i-2}, W_{i-1})} \]

Implementations blend weights across unigram, bigram, and trigram levels, with unigram plus bigram usually carrying the decision; the trigram refines close calls but its counts are sparser. The counts come from the same training corpus used for the prior, and the arithmetic is light enough for ordinary processors with no special hardware. Combination rule used here: score each candidate by its posterior product first, then multiply by the neighbor-conditioned probability and re-rank — the sequence score, not either factor alone, decides.

Scope: Bigram and trigram context fits local agreement — adjective-noun, verb-object, article-noun pairs. It breaks on long-distance links ("the actress ... she"), where the deciding neighbor sits outside the window. Those need wider windows or attention, not bigger n-grams, because trigram counts thin out fast.

2.6.2 Worked Example: "ACTRESS" Against "ACROSS"

Worked re-ranking. Consider the sentence about a stellar and versatile actress who combines sass and glamour. Step 1 (single-word): suppose the corpus gives "ACROSS" a prior near \(3 \times 10^{-5}\) and "ACTRESS" one near \(2 \times 10^{-6}\), with similar typo likelihoods — then "ACROSS" leads the posterior product roughly 15-to-1. Step 2 (context): the bigram test reverses this. The chance of seeing "actress" right after "versatile" is far higher in the corpus than the chance of seeing "across" there — say \(P(\text{actress} \mid \text{versatile}) \approx 4 \times 10^{-2}\) against \(P(\text{across} \mid \text{versatile}) \approx 2 \times 10^{-5}\) — because "versatile across" is not a natural pairing. Step 3 (combine): multiply each posterior by its bigram score, and the full sequence containing "actress" wins the argmax by orders of magnitude. The takeaway is procedural: score each candidate alone, then re-score it inside its context, and let the sequence score decide close calls.

Exam note: Expect a numerical problem that combines the posterior product with a bigram or trigram re-ranking step on a sentence like this one. Work it in three lines: posterior per candidate, context probability per candidate, multiplied sequence score with the winner bolded.

2.6.3 Student Questions and Answers

Q: Is the single-word score enough, or do we need context?

A: Context is needed. Even when distance and individual probability point one way, the sentence can demand the other word. The bigram and trigram probabilities supply that sentence fit, and the final pick uses both the individual score and the context score.

The bag-of-words shortcut triggered the session's correction: ignoring order equates "versatile actress" with "actress versatile", but order-sensitive bigram counting separates them — the pair order decides the count.

Recap + bridge. Neighbors vote after words do: posterior first, context multiplier second, sequence argmax last. That two-stage ranking is exactly what real-word correction needs at every position — which is the next section's problem.

Predictive keyboards, autocomplete, and speech recognizers all run this same neighbor vote: propose locally, re-rank by what surrounds the slot. The glamour-sentence flip is one instance of a universal pattern — local fit beats global frequency whenever the sentence has an opinion.

2.7 Real-Word Error Correction

Hook: Every word in the sentence is spelled correctly — and one of them is still wrong. No dictionary can flag it. How do you even find the error site?

Real-word correction differs from non-word correction at the very first step: finding which word is wrong. In the non-word case a dictionary lookup exposes the bad string immediately. In the real-word case every word is valid, so every word in the sentence is a suspect, and the candidate set must be built for each position, including the word itself as one of its own candidates.

Core idea. Detection is the hard half: since no word looks wrong alone, generate candidates at every position and let full-sequence context scores expose which position is corrupt. Correction then rejoins the non-word routine at that position.

Think of a row of light bulbs where exactly one is dimmer — but only slightly, so no single bulb looks broken on its own. The fix is to measure every bulb against its neighbors and find the position whose replacement brightens the whole row most. The picture breaks where bulbs are independent; words are not, so the sequence score, not any single reading, names the culprit.

2.7.1 Candidate Generation for Every Position

Formalize. For each word in the phrase, collect all dictionary words within edit distance 1, always keeping the original word in its own list. A three-word phrase with four, three, and four options per position then yields 48 possible corrected sequences by straightforward multiplication (\(4 \times 3 \times 4 = 48\)). Each sequence is scored as a chain, multiplying the conditional probability of each word given its predecessors, which is where the chain rule enters. In words, the goal is the sequence \(W_1, W_2, W_3\) with the highest joint probability given the observed phrase. Reconstructed as LaTeX:

\[ \hat{W}_1, \hat{W}_2, \hat{W}_3 = \arg\max_{W_1, W_2, W_3} P(W_1, W_2, W_3 \mid X_1, X_2, X_3) \]

The sequence probability itself factors through the chain rule over the positions — \(P(W_1)\) starts the chain, \(P(W_2 \mid W_1)\) extends it, \(P(W_3 \mid W_1, W_2)\) (or its bigram approximation \(P(W_3 \mid W_2)\)) finishes it — and the argmax runs over all 48 chains. Scoring all 48 chains is already heavy for three words and grows exponentially with sentence length, so practical systems simplify.

2.7.2 The One-Error Assumption and Faster Search

Procedural core — Purpose. Full-chain search explodes, so cut it down with one safe assumption. Steps. The standard simplification assumes that only one word in the phrase is wrong at a time. Fix two positions to their observed words, score all replacements for the third, then rotate. The 48 full combinations collapse to about eight partial checks (three plus two plus three in the session arithmetic: each position's non-original options scored while the other two stay fixed), each asking which single-position change best explains the phrase. In words: hold two words fixed, test the options for the remaining word, record the best chain, and repeat for each position. Whichever position shows the strongest evidence of corruption is declared the error site. From there the flow rejoins the non-word routine: generate edit-distance neighbors for that word, score them with the posterior product, and break ties with bigram and trigram context. Trace. With options \(4 \times 3 \times 4\), position 1 contributes its 3 non-original options, position 2 its 2, position 3 its 3 — 8 chains instead of 48. Complexity. One-error search costs the sum of the option counts, not their product; full search costs the product. When to use. The assumption fits everyday typing, where two independent slips in three words are rare; it breaks on heavily garbled text, where the fallback is splitting or wider search.

The procedure mirrors the Viterbi idea of keeping the best partial path at each step rather than enumerating every full path. For longer sentences the same explosion returns, so systems split sentences into shorter phrases or noun and verb groups, or limit the context window to a few words on each side, much as attention mechanisms cap how far back they look. Most errors are local, so a window of two words on each side usually decides correctly, with wider or attention-based context reserved for the rare long-distance cases.

Scope. The one-error assumption holds for careful typing with occasional slips — the normal case. It fails on OCR output, heavy speech-recognition noise, or learner text with several errors per sentence; there the sentence must be split, or the assumption dropped and the search widened.

Pitfalls. The classic mistake is scoring each position's candidates in isolation and picking local winners; the error site only appears in full-chain scores. A second trap is forgetting to include the original word in each list — without it, the "no error here" hypothesis cannot win anywhere. A third is running the exponential search on long sentences instead of windowing first.

2.7.3 Student Questions and Answers

Q: Why handle real-word errors separately instead of reusing the non-word steps?

A: Because detection is the hard part. Every word looks fine in isolation, so candidates must be generated for each position and the full sequence must be scored with context. Single-word scoring without neighbors cannot expose which valid word is the wrong one.

Q: In the worked phrase, why do replacement candidates for a position include words never typed there?

A: Because the search builds every possible chain over all positions, including the original words themselves as candidates. The chain probabilities then reveal which position is likely corrupt. Fixing one position at a time and scoring its options exposes the error site, after which correction proceeds as in the non-word case.

Q: Does this blow up on long sentences?

A: Yes, combinations grow exponentially with length. The remedies are splitting sentences into sub-phrases, scoring a limited window of neighbors on each side, and keeping the one-error assumption so only one position varies at a time.

Recap + bridge. Real-word correction is search plus evidence: candidates everywhere, chain scores to find the site, non-word machinery to fix it. The counting view ends here; the next section replays the same tasks as learning problems.

Confusable-word correction in writing assistants ("affect/effect", "complement/compliment") is this section in production, as are OCR post-correction and speech-output cleanup. Anywhere valid words land in wrong slots, per-position candidates with sequence scoring are the standard first design.

2.8 Machine Learning and Transformer Approaches

Hook: Counting works — so why train a network at all? Because some fixes need the whole sentence, the writer's habits, and patterns no count table captures.

The same correction tasks can be framed as learning problems instead of counting problems. The session poses this directly: given a text with spelling or grammar slips, how would a machine-learning or transformer system fix it.

Core idea. Counting estimates probabilities from tallies; learning estimates decision boundaries from labeled examples. The features overlap (context, tags, dictionary signals, edit distance), but classical models learn weights over hand-built features while deep models learn the features themselves — and both need labeled correction data in context.

Think of counts as a ledger and learned weights as reflexes. The ledger answers by looking up every entry; reflexes answer from practice on labeled drills. The analogy breaks where ledgers are inspectable and reflexes are not — a count table can be read, a weight matrix mostly cannot — which is why hybrids keep both.

2.8.1 Correction as Multi-Class Classification

One clean framing treats each mistyped input as a classification item whose classes are the possible corrections. For a typed "actress"-family string, the classes are "ACTRESS", "ACROSS", "ACCESS", and the rest of the candidate set. Features for the classifier include the context words, part-of-speech tags, dictionary membership, and the edit distance itself, either hand-built for classical models or learned automatically by deep networks. Training needs labeled pairs that say which correction is right in which context. Recurrent networks and long short-term memory networks serve as classifiers here, and support-vector machines over hand-built features are the classical equivalent. Either way the learned weights play the role that raw counts play in the statistical path, and the appetite for good supervised training text is the same.

Worked framing. Input: the sentence with "ACRESS" after "versatile". Classes: the edit-distance-1 set from section 2.4. Features: previous word "versatile", part-of-speech tag (noun expected), dictionary flags, and one distance column per candidate. Label: "ACTRESS" for this context, "ACROSS" for a travel context. A trained classifier then reproduces the bigram verdict from section 2.6 — but from learned weights, not count tables — which is exactly the correspondence the session wants.

2.8.2 Architectures: Encoder-Only Against Encoder-Decoder

Architecture rule. Architecture follows the shape of the task. Spell correction emits one word at a time, so an encoder-only design such as BERT is enough: read the context, then pick the word. Grammar correction rewrites whole sentences, taking an incorrect sentence in and emitting a corrected sentence out, so it is a sequence-to-sequence problem that wants an encoder-decoder design such as T5.

GECToR, a transformer tool built specifically for grammar error correction, works through edit tagging: it predicts per-token operations such as keep, replace, or delete along with the needed edit distance, rather than regenerating fluent text from scratch. That makes it fast and conservative — closer to tagging than to free generation. Part-of-speech tagging with hidden Markov models and Viterbi decoding appears as the statistical counterpart inside grammar pipelines, and dependency parsing shows word-to-word links while constituency parsing shows phrase structure. The rule of thumb: tagging and picking suit encoders; rewriting suits encoder-decoders.

2.8.3 Fine-Tuning, Quantization, and Domain Adaptation

Large models adapt to a domain through fine-tuning, including parameter-efficient methods such as LoRA and its quantized form QLoRA. LoRA (low-rank adaptation: small trainable matrices added beside the frozen weights) tunes a fraction of the parameters; QLoRA does the same on a quantized backbone. Quantization shrinks each stored weight — for example from 32-bit floating point down to 4-bit or NF4 levels, with research pushing even lower — which cuts memory and compute at some cost in accuracy. The session's bit levels describe the standard ladder (32-bit training precision down through 16/8-bit inference to 4-bit and NF4 storage formats); exact accuracy cost depends on the model, task, and calibration setup, so treat the trade-off as directional — smaller and cheaper against slightly less exact — rather than as fixed numbers. Small models such as Qwen-class models (the session captions render the name as "Quen") can be tuned the same way for a local task. Retrieval augmentation can further ground a corrector in domain text. The decision rule from the session is pragmatic: use counting and dictionary tools where they already win, and spend model capacity on the residue they cannot fix.

Scope and pitfalls. Fine-tuning fits stable domains with labeled examples (hospital notes, legal drafts); it breaks on rapidly shifting slang or tiny datasets, where retrieval grounding or rule lists adapt faster. The classic waste is fine-tuning a giant model to fix single-typo slips that a dictionary clears for free. Quantization likewise fits deployment on small hardware and breaks where exact probabilities matter most.

2.8.4 Student Questions and Answers

Q: How do we pose spell correction as a machine-learning problem?

A: As multi-class classification. The classes are the candidate corrections for the input, and the features are context words, speech tags, dictionary signals, and edit distance. Classical models learn weights over hand-built features while deep models learn the features themselves, but both need labeled correction data in context.

Recap + bridge. Learning replays counting with weights instead of tallies: classify among candidates, pick the architecture by output shape, fine-tune cheaply, and spend heavy models only on the residue. The next section names the packaged tools where all of this already runs.

Writing assistants, code review bots, and translation post-editors all follow this ladder: candidates from cheap methods, ranking from statistics or learned weights, rewriting from sequence models. The lecture's stack is the industry's stack, scaled down to one teachable lecture.

2.9 Tools You Can Use Today

Hook: Every method in this lecture ships inside a tool you can run this week — most of them locally, on an ordinary machine, without sending private text anywhere.

Several open and commercial tools package these ideas, and the session stresses one property above all: open-source tools run locally, so private text never has to travel through a paid API or a heavy cloud setup, and they need little space or compute.

LanguageTool applies rules and linguistic resources to both spelling and grammar and is widely used. Hunspell is a popular dictionary-based checker in the rule family. SymSpell (the session captions garble the name as "stSemAIMLstudentsdocs") pairs rules with context for very fast correction and appears in the live demo. The PySpellchecker-style statistical checker (the session captions render it as "PI Spell") leans on corpus statistics, and the TextBlob-style checker (the session captions render it as "Text Globe") is named in the same statistical group. The Hugging Face transformer collection supplies ready-made neural correctors, and GECToR is the popular open grammar-correction model, also used inside larger pipelines such as Grammarly-style stacks. Ready-made local libraries are shown correcting whole sentences, including domain terms and even strings with missing spaces, at interactive speed. Commercial options include Grammarly for grammar plus writing support, Quillbot across several assistance tasks, and ProWritingAid for grammar review. Selection rule. Match the tool to the constraint: Hunspell or SymSpell for instant local spelling, PySpellchecker-style or TextBlob-style counts for ranked local fixes, LanguageTool for rule-grounded grammar, GECToR or Hugging Face models for neural rewriting, commercial stacks for polished writing help — and keep sensitive drafts inside the local set.

Pitfalls. The two deployment traps are sending unpublished writing to free web checkers, and assuming "open-source" means "weak": the local stack in this section corrects full sentences with domain terms at interactive speed. Match the tool to the privacy level before matching it to the error type.

Recap + bridge. Local tools cover spelling, ranking, rules, and even neural rewriting; cloud tools add polish at a privacy cost. With the toolbox stocked, the next section orders these tools into the grammar pipeline.

Banks of finance, medicine, physics, and chemistry terms can be added to local statistical or rule-based setups so items such as lab-test names correct properly without retraining a large model. University writing centers, hospital documentation teams, and newsroom copy desks all run this pattern: a local base vocabulary plus a domain word bank, refreshed per specialty.

2.10 How Grammar Checking Works

Hook: Spell checking asks "is this a word?" Grammar checking asks "does this sentence hold together?" — a harder question that needs the words settled first.

Grammar checking reuses every approach above and adds sentence structure. The pipeline order matters: run spell checking first, assume the words are now spelled correctly, then test whether the sentence is grammatical. Each stage can use rules, statistics, or neural models.

Procedural core — Purpose. Decide whether a sentence is well formed and coherent, and either fix it or propose fixes. Inputs and outputs. In goes a spell-cleaned sentence; out comes a corrected sentence or a ranked list of suggestions. Steps. Tokenization and part-of-speech tagging split and label the words. Parsing then tests structure: rule-based parsing for simple subject-verb-object order, dependency parsing for word-to-word links, constituency parsing with statistical scoring for phrase structure, or an encoder-decoder pass per stage in neural setups. The final step either rewrites the sentence automatically or offers the user options to accept, since writers sometimes prefer to approve each change. Trace. "He happy" tokenizes to pronoun plus adjective, tagging flags the missing verb slot, parsing confirms no verb phrase exists, and the rewrite inserts "is". Cost. Rule and tagging stages are cheap; full parsing and neural rewriting cost more. When to use. Automatic rewriting fits high-volume drafts; suggestion mode fits high-stakes prose where the writer keeps control.

2.10.1 Language Change: Words Move, Grammar Holds

A sharp question raised in the session asks how any of this survives language change, contrasting older literary English with present-day informal vocabulary. The answer separates two layers. Sentence-structure rules stay stable across eras, while word choice drifts fast. The tempting view is that techniques expire as language changes; the correction is that only the corpus expires while the machinery persists — retrain the counts on current text and the same pipeline keeps working.

A model trained on present-day informal text behaves differently from one trained on older literary text, and the difference comes down to training data. Meaning drift is real: the word "broadcast" once belonged to farming, describing the scattering of seeds, and now belongs to media. Contextual word vectors track exactly this by letting surrounding words reshape each word picture, with attention mechanisms carrying the long-range context. So the correction machinery stays the same while the corpus decides which era and register it serves.

Scope. Retraining the corpus handles vocabulary and meaning drift. It does not handle genuinely new grammar (novel constructions from contact languages or platforms); those need new rules or new annotations, not just fresh counts.

2.10.2 Student Questions and Answers

Q: If English keeps changing, do grammar techniques become outdated?

A: Vocabulary changes fast but sentence-structure rules stay stable. What changes with time is the training corpus, so a model trained on current informal text differs from one trained on older text. Semantic drift of words such as "broadcast" and context-sensitive vectors for words such as "bank" show how surrounding words update meanings without rewriting the grammar machinery.

Recap + bridge. Grammar checking is spell checking plus structure: tag, parse, then rewrite or suggest — on a corpus matched to the era. One question remains for the whole lecture: how do we score a checker? That is the final section.

Newsroom style guides, legal drafting tools, and second-language tutoring systems all run this ordered pipeline. The era lesson travels with them: a checker trained on current copy edits current copy best, whatever the underlying parser.

2.11 Evaluation: Precision, Recall, and F0.5

Hook: A checker that rewrites every sentence will "catch" every error — and annoy every user. How do you reward catching errors while punishing needless rewrites?

Evaluation decides whether a checker is actually good, and the session treats it as exam-central. Every score needs a ground truth (a reference that says which words are truly wrong and what each should become). Model text is validated against that reference, whether the model is statistical, neural, or commercial. A recurring design warning is that large-model checkers tend to over-correct, rewriting fine sentences, so measurement must punish unnecessary edits, not just reward caught errors.

Think of medical testing. A good test finds the sick (recall) without alarming the healthy (precision). A checker is a diagnostic test for sentences, and the F0.5 score is the doctor's compromise: false alarms hurt more than missed mild cases, because a rewrite imposed on good text damages trust at once. The picture breaks where medicine weighs lives; here the weights are user patience — but the arithmetic is identical.

2.11.1 The Four Outcomes

The confusion table. For each word or sentence, compare the system flag against the truth. A true positive (an error exists and the system flags it) catches a real slip. A true negative (the text is fine and the system stays silent) correctly leaves good text alone. A false positive (the text is fine but the system flags an error anyway) is a false alarm. A false negative (an error exists but the system misses it) is a silent miss.

In words from the session: the two smiling cases are catching a real error and correctly leaving good text alone, while the two sad cases are flagging good text and missing real errors. Flagging the correct sentence "they play" as wrong is the false-positive pattern; leaving the broken sentence "he happy" unflagged is the false-negative pattern.

Worked labeling. "Receive" misspelled and corrected counts as a true positive. Flagging the fine sentence "they play" counts as a false positive. Missing the broken sentence "he happy", which needs the verb "is", counts as a false negative. Leaving a clean sentence untouched counts as a true negative. Every scoring exercise below starts by sorting each item into exactly one of these four boxes.

2.11.2 Precision, Recall, and the F0.5 Balance

Precision asks how trustworthy the flags are. Recall asks how complete the catching is. In words: precision is the share of flagged items that are genuinely wrong, and recall is the share of genuine errors that got flagged.

Formalize. Reconstructed as LaTeX, with \(TP\) as true positives, \(FP\) as false positives, and \(FN\) as false negatives:

\[ P = \frac{TP}{TP + FP}, \qquad R = \frac{TP}{TP + FN} \]

\(P\) (precision) divides good flags by all flags; \(R\) (recall) divides good flags by all genuine errors. Both live in \([0, 1]\), and both equal 1 only for a perfect run.

The \(F_{0.5}\) score blends the two while weighing precision more than recall, because needless rewrites annoy users more than the occasional missed slip. In words: it is a weighted harmonic blend that punishes false alarms harder than misses.

The F0.5 formula. Reconstructed as LaTeX:

\[ F_{0.5} = \frac{1.25 \times P \times R}{0.25 \times P + R} \]

The general form is \(F_{\beta} = (1 + \beta^2) P R / (\beta^2 P + R)\) with \(\beta = 0.5\); since \(\beta^2 = 0.25\) and \(1 + \beta^2 = 1.25\), the constants above are exactly the \(\beta = 0.5\) specialization. Limiting cases: as \(\beta \to 0\) the score approaches precision alone; as \(\beta \to \infty\) it approaches recall alone; at \(\beta = 1\) it is the balanced harmonic mean. Choosing 0.5 places the blend near precision while still penalizing total blindness.

Per-class scores of the same form apply to multi-class setups, tying back to standard classifier metrics. ERRANT is named as the tool that goes one step further: besides scoring, it labels each grammar error by type, such as tense, pronoun, or punctuation errors. Broader benchmark scores used in translation are deferred to the translation sessions.

Exam note: Expect mathematical problems that compute precision, recall, and F0.5 from a marked-up passage, plus questions on why precision gets the extra weight in this task. The one-line answer: false alarms rewrite good text, and users forgive a missed slip faster than an imposed error.

Pitfalls. Three traps recur. First, reporting accuracy on mostly-clean text; accuracy looks high because true negatives dominate, while precision and recall expose the real behavior. Second, forgetting that \(F_{0.5}\) is asymmetric — swapping \(P\) and \(R\) changes the score. Third, scoring recognition errors as checker errors; the pipeline section below keeps those references separate.

2.11.3 Worked Example: Scoring a Marked Passage

Worked scoring. Take a short passage with five genuine errors. Suppose the system flags ten words as wrong: eight of the flags point at genuine errors and two point at fine words. But only five errors genuinely exist, so at most five flags can be true positives — the session's "eight good flags" is read as eight correct edit actions across the passage (some errors need multi-word fixes), while the two bad flags are false positives. Precision is then good flags over all flags: high, since most flags were right. For recall, compare against all five genuine errors in the passage: if the system catches only two of the five, recall is two out of five (\(R = 2/5 = 0.40\)), which is low even though precision looks strong. The \(F_{0.5}\) blend then lands closer to the precision side: with, say, \(P = 0.80\) and \(R = 0.40\), \(F_{0.5} = (1.25 \times 0.80 \times 0.40) / (0.25 \times 0.80 + 0.40) = 0.40 / 0.60 \approx 0.67\) — rewarding the system for restraint while still penalizing the three missed errors. Sense-check: the blend sits between the two inputs but nearer precision (0.80), exactly as the \(\beta = 0.5\) weighting promises. Correct edits such as repairing "receive" count as true positives; flagging the fine sentence "they play" counts as a false positive; missing the broken sentence "he happy", which needs the verb "is", counts as a false negative.

2.11.4 Beyond Typed Text: Speech, Images, and Video

Spelling and grammar scores always apply to text, but text can arrive through other channels. A tempting simplification is one reference for everything, but the correction is separate recognition and checker references: keep the two stages apart.

Two-stage evaluation. Optical character recognition converts scanned handwriting or printed images into words first; speech tools convert audio into words first; video reduces to frames, frames reduce to images, and images reduce to words through the same recognition step. Only after that conversion do the standard checkers run. The ground truth for the checker stays textual: the same word-level reference used for typed text, because the checker sees only the converted words. Recognition quality itself is measured separately against its own audio, image, or video reference. Keeping the two stages apart avoids blaming the spelling scorer for a recognition mistake and vice versa — one reference for everything would mix the two error sources beyond repair.

Scope. The textual ground truth covers what the checker saw. It breaks as an end-to-end measure the moment recognition garbles the words: a perfect checker on mangled input still fails the user. Report both scores side by side instead of merging them.

2.11.5 Student Questions and Answers

Q: Which scores should we use for a checker?

A: Accuracy-style thinking points to precision and recall with their F balance. Precision means the flagged spellings are truly wrong; recall means the truly wrong spellings got flagged. Because false alarms cost more here, the F0.5 blend weighs precision above recall, and precision-at-K style thinking applies when systems return ranked suggestion lists.

Q: A false negative was described two ways in discussion: system output wrong on a wrong input, against system silent on a wrong input. Which is right?

A: A false negative means an error exists and the system does not report it: the text stays wrong and no suggestion appears. If the input is wrong and the output is also wrong in a new way, that is still a wrong suggestion on a real error, not a silent miss. If the input is right and the system flags it, that is a false positive. The class view settles it: with correct and incorrect as the two classes, predicting incorrect for a correct item is a false positive, and predicting correct for an incorrect item is a false negative.

The session's sign-flip debate is worth preserving: several students read "wrong output on wrong input" as a false negative, but the class framing corrects it — a wrong suggestion on a real error is a failed true-positive attempt (the error was flagged, the fix was wrong), while only silence on a real error is a false negative.

Q: What is the reference when checking text that came from an image, video, or audio?

A: The same textual ground truth used for typed text. Conversion from pixels or sound waves into words is a separate pre-processing stage with its own reference. The spelling and grammar scores only judge the word stage, so no separate audio or video reference is needed for them.

Search engines, OCR pipelines, and medical transcription all score this way: recognition against its own reference, checking against the word reference, precision-weighted blends wherever false alarms cost trust.
