Lecture Summary

This lecture makes the rational-agent concept practical by defining what an agent is, how to specify its task, and how problem-solving agents search for solutions. An agent is anything that perceives through sensors and acts through actuators — examples range from vacuum cleaners to medical diagnosis systems and trading bots. The lecture also clarifies the distinction between an AI agent (a perceive–act loop with goals) and marketing buzzword 'agentic AI' (tool orchestration layers).

The PEAS framework — Performance measure, Environment, Actuators, Sensors — provides a systematic checklist for agent design, with worked examples including taxi drivers, medical diagnosis, and game playing. Environments are classified along six axes: fully vs partially observable, deterministic vs stochastic, episodic vs sequential, static vs dynamic, discrete vs continuous, and single vs multi-agent. These properties directly determine which algorithms are appropriate.

Agent architectures progress in sophistication: from table lookup (infeasible at scale) through simple reflex, model-based reflex, goal-based, utility-based, to learning agents that improve from experience. The lecture then introduces problem-solving agents, which reduce tasks to search by defining an initial state, actions, transition model, goal test, and path cost. Both uninformed strategies (BFS, DFS, uniform-cost) and informed strategies (greedy best-first, A*) are previewed as the computational core for subsequent lectures.

Key Learning Objectives

  • Define agents, sensors, actuators, and rational versus bounded rational behaviour.
  • Write complete PEAS specifications for standard and exam-style agent scenarios.
  • Classify environments using observability, determinism, episodicity, dynamics, discreteness, and agent count.
  • Compare agent architectures from table-based to learning agents.
  • Formulate a problem-solving task with five components and relate it to uninformed and informed search.

1. Recap: The Four Quadrants of AI

In the previous lecture, the history and definitions of Artificial Intelligence were introduced. The field has coalesced around four canonical definitions, often visualized as two axes: thinking vs. acting, and human-like vs. rational.

The Four Definitions of AI
  1. Thinking Humanly — Mimicking the internal cognitive processes of humans (emotions, habits, past experiences, biases).
  2. Acting Humanly — Mimicking externally observable human behavior (showing empathy, holding conversation).
  3. Thinking Rationally — Following logical, step-by-step deduction independent of emotion (rule-based reasoning).
  4. Acting Rationally — Taking actions that maximize the chance of achieving a goal, regardless of internal process.

Which quadrant dominates today? The fourth — acting rationally — has become the most prominent. The goal of an AI system is not merely to mimic humans, but to do the right thing: to perceive the environment and select actions that best achieve its objectives. This lecture builds directly on that insight.

Anthropomorphism (added for context). Some AI systems are deliberately designed to act humanly — e.g., chatbots that say "That sounds stressful; want to talk about it?" Users may then attribute human-like characteristics to non-human entities, a phenomenon called anthropomorphism. This is ethically debatable and will be revisited in a later class on AI ethics.

Examples for each quadrant
  • Thinking Humanly: "This looks similar to one I saw yesterday; the answer would be around 50" — driven by past experience, not pure logic.
  • Thinking Rationally: "All assignments are due tomorrow → must complete them today. I have an AI assignment due tomorrow → I must complete it today." — pure logical deduction.
  • Acting Humanly: A chatbot responds "That sounds stressful; want to talk about it?" — empathetic behavior without genuine emotion.
  • Acting Rationally: Checking traffic on maps, choosing the fastest route, booking a cab — maximizing the goal of reaching the office quickly.

2. What Is an Agent?

Agent — Core Definition
An agent is anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators.

Every agent has two fundamental capabilities:

  1. Perception (via sensors) — gathering information about the environment.
  2. Action (via actuators) — changing something in the environment.

The Agent Function vs. Agent Program. Inside every agent is an agent function — an abstract mathematical description that maps from percept sequences (complete histories of everything the agent has ever perceived) to actions. This mapping is the "brain" of the agent. An agent program is the concrete software realization of this function running on a physical computing architecture. The key distinction: the agent function depends on the entire percept history, while the agent program takes only the current percept as input — it must maintain its own memory of past percepts. Mathematically: agent = architecture + program. The architecture (sensors, actuators, computing device) makes percepts available and feeds actions to actuators; the program implements the agent function. Formally, we use the term percept (singular) for the content of a single sensor reading and percept sequence for the complete history. An agent's choice of action can depend on its built-in knowledge and on the entire percept sequence observed to date — but not on anything it hasn't perceived.

[Added from textbook: The notion of an agent is a tool for analyzing systems, not an absolute characterization that divides the world into agents and non-agents. A hand-held calculator could be viewed as an agent that displays "4" when given "2 + 2 =" — but that analysis wouldn't aid understanding. AI operates at the end of the spectrum where the task environment requires nontrivial decision making.]

2.1 Examples of Agents

  • Human agent: Sensors = eyes, ears, skin; Actuators = hands, legs, mouth.
  • Robotic agent: Sensors = cameras, IR sensors, range-finders; Actuators = motors, grippers.
  • Software agent (AI agent): Sensors = text/voice input; Actuators = text display, API calls.
  • Intelligent building: Sensors = temperature, motion; Actuators = HVAC, lighting.

Q&A. Is a human an agent? Yes — humans perceive through sensory organs and act through body parts, fitting the definition perfectly. A system of agents working together constitutes Agentic AI.

3. Rational Agents and Ideal Rational Agents

Rational Agent
A rational agent is one that strives to do the right thing based on what it can perceive and the actions it can perform. The "right" action is the one that causes the agent to be most successful, measured by a predefined performance measure.

Performance measure — an objective criterion for evaluating the success of an agent's behavior. For a vacuum-cleaner agent, possible performance measures include: amount of dirt cleaned, time taken, electricity consumed, noise generated.

[Added from textbook: Warning: "What you ask for is what you get." It can be surprisingly hard to formulate a performance measure correctly. If the vacuum-cleaner's measure is "amount of dirt cleaned," a rational agent could maximize it by cleaning dirt, then dumping it back on the floor, then cleaning it again — forever. A better measure would reward having a clean floor (e.g., one point per clean square per time step, minus penalties for electricity and noise). As a general rule: design performance measures according to what you actually want achieved in the environment, not according to how you think the agent should behave. This is the King Midas problem — getting exactly what you asked for, not what you wanted.]

Ideal Rational Agent
For each possible percept sequence, an ideal rational agent selects the action expected to maximize its performance measure, based on (a) the evidence perceived so far and (b) its built-in knowledge.

Four things rationality depends on: (1) The performance measure defining success; (2) the agent's prior knowledge of the environment; (3) the actions the agent can perform; (4) the agent's percept sequence to date. All four must be considered when judging whether an agent's action was rational.

Crucial distinction: Rationality ≠ Omniscience. An ideal rational agent does not know everything. It acts optimally given what it knows at that moment. Consider the textbook's Champs-Élysées example: you see an old friend across the street, no traffic nearby, so being rational, you start crossing. Meanwhile, at 33,000 feet, a cargo door falls off a passing airliner and flattens you before you make it. Were you irrational to cross? No — rationality maximizes expected performance, not actual performance. Perfection retroactively requires crystal balls. If we demanded agents to do what turns out after the fact to be best, it would be impossible to design them — unless we improve time machines.

Information gathering. Agents can perform actions to modify future percepts and obtain useful information. For example, an LLM-based assistant may ask clarifying questions before executing a complex task — this exploration improves the quality of its eventual action. Looking before crossing a road is information gathering too: the percept "I looked both ways and saw nothing" is far more useful than just walking blindly.

Autonomy. An agent is autonomous if its behavior is determined by its own experience, with the ability to learn and adapt, rather than relying solely on built-in knowledge. The textbook illustrates this with two striking examples:

  • Dung beetle: After digging its nest and laying eggs, it fetches a dung ball from a nearby heap to plug the entrance. If the dung ball is removed en route, the beetle continues pantomiming plugging the nest with the nonexistent ball, never noticing. Evolution built an assumption into its behavior, and when violated, unsuccessful behavior results.
  • Sphex wasp: The female digs a burrow, stings a caterpillar, drags it to the burrow, checks inside, drags the caterpillar in, and lays eggs. If an entomologist moves the caterpillar a few inches while the sphex checks, it will drag it back to the entrance and repeat the checking routine — dozens of times, never learning. It cannot modify its innate plan.

Both examples show the fragility of purely pre-programmed behavior. A rational agent should be autonomous — it should learn what it can to compensate for partial or incorrect prior knowledge. As a practical matter, one seldom requires complete autonomy from the start: just as evolution provides animals with enough built-in reflexes to survive until they learn for themselves, it is reasonable to provide an AI agent with some initial knowledge plus an ability to learn.

Exam Tip / Common Pitfall
The three-tier progression is critical for exams:
  1. Agent = perceives + acts.
  2. Rational Agent = strives to do the right thing (requires a performance measure).
  3. Ideal Rational Agent = maximizes expected performance based on all evidence so far + built-in knowledge.

4. The Vacuum-Cleaner Agent Example

This classic toy example illustrates the fundamental agent concepts.

Setup. Two rooms, A (left) and B (right). A vacuum-cleaner agent resides in one room. It can perceive: [A, Clean], [A, Dirty], [B, Clean], [B, Dirty].

Legal actions:

  • Left — move to the left room (illegal if already in A).
  • Right — move to the right room (illegal if already in B).
  • Suck — clean the dirt in the current room.
  • NoOp — do nothing.

Percept-action mapping (designer-configured):

Percept(s)Action
[A, Clean] (once)NoOp (wait, do not rush to change rooms)
[A, Clean], [A, Clean] (twice)Right (now go check room B)
[A, Clean], [A, Dirty]Suck (clean the dirt that appeared)
[A, Dirty]Suck
[B, Clean]Left
[B, Dirty]Suck
[A, Clean], [B, Clean]NoOp (both rooms clean; keep waiting/looping)

[Added for clarity: The designer configures how long the agent waits (e.g., 5 seconds or multiple percept cycles) before deciding to move. The key idea: based on percepts, an agent selects actions; some actions are illegal in certain states.]

5. PEAS Specification

To design any agent, we must first specify its PEAS:

PEAS Framework
  • P — Performance measure: What defines success? (safety, speed, accuracy, profit, etc.)
  • E — Environment: Where does the agent operate? (roads, hospital, factory, etc.)
  • A — Actuators: What actions can the agent take? (steering, display, robotic arm, etc.)
  • S — Sensors: How does the agent perceive? (cameras, keyboard, GPS, etc.)

Mnemonic. "Every agent uses its S to know the input, acts in E, optimizes P using A."

5.1 PEAS Examples

Automated Taxi (Self-Driving Car)
  • P: Safety, speed, legality, comfort, maximize profit.
  • E: Roads, traffic signals, pedestrians, other vehicles, weather.
  • A: Steering wheel, accelerator, brake, turn signal, horn.
  • S: Cameras, GPS, sonar, engine sensors, keyboard/microphone.
Medical Diagnostic System
  • P: Healthy patient, accuracy, minimize costs, minimize lawsuits.
  • E: Patient, hospital, hospital staff.
  • A: Screen display (showing questions, tests, diagnoses).
  • S: Keyboard (symptoms, findings, patient answers).
Part-Picking Robot (Conveyor Belt)
  • P: Percentage of parts in correct bins, classification accuracy, number of items picked.
  • E: Conveyor belt with parts, sorting bins.
  • A: Robotic arm (jointed manipulator).
  • S: Camera, color sensors, joint-angle sensors.
Exam Tip / Common Pitfall
PEAS is a guaranteed exam topic. For any agent described, you must be able to list plausible (not unique) entries for all four components. The answers need not be exhaustive, but must be contextually plausible — e.g., the environment of a conveyor-belt robot cannot be "a hospital."
Q&A. Can PEAS answers differ between students? Yes. There is no single correct answer as long as the entries are reasonable and contextually appropriate. The designer ultimately decides which performance measure to optimize, which sensors and actuators to use, and what assumptions to make about the environment.

6. Properties of Environments

The environment type largely determines the agent design. Before building an agent, we must characterize its environment along six dimensions:

6.1 Observability

Observability
How much of the environment's state can the agent's sensors access at each point in time?
  • Fully observable: The agent has complete access to the state. Example: Chess — all pieces are visible.
  • Partially observable: The agent has limited or noisy access. Example: Autonomous driving — cannot see vehicles kilometers away; Poker — own cards known, others' hidden.
  • Unobservable: The agent has no sensor data at all. Rare extreme: sensor failure, database crash, person in coma.

[Added for clarity: A fully observable environment need not be small — it only means that all relevant state information is accessible. A task environment is effectively fully observable if the sensors detect all aspects that are relevant to the choice of action. Relevance depends on the performance measure. Fully observable environments are convenient because the agent need not maintain internal state to keep track of the world.]

6.2 Deterministic vs. Stochastic

Determinism
  • Deterministic: The next state is completely determined by the current state and the agent's action. Same action → same result. Example: Calculator, chess (moving a bishop always moves diagonally).
  • Stochastic: The next state involves uncertainty. Same action → potentially different results. Example: Rolling a die, weather prediction, robot football.
Exam Tip / Common Pitfall
Determinism is about whether the same action can produce different outcomes — not about whether different actions produce different outcomes. In chess, different moves naturally lead to different states, but each specific move always behaves the same way; hence chess is deterministic. Rolling a die is stochastic because the same roll action can yield 2, 5, or 6.

Nomenclature note from the textbook: The word stochastic is used when a model explicitly deals with probabilities (e.g., "25% chance of rain"). Nondeterministic is used when possibilities are listed without quantification (e.g., "a chance of rain"). Also, if the environment is partially observable, it can appear nondeterministic even if the underlying dynamics are deterministic — because the agent cannot see the hidden parts of the state that influence outcomes.

6.3 Episodic vs. Sequential

Episodicity
  • Episodic: The agent's experience is divided into independent atomic episodes. Each episode's action depends only on that episode. Example: Spam filter — classifying one email does not affect the next; "Is there a cat in this image?"
  • Sequential: Current decisions affect future decisions or rely on previous ones. Long-term planning is required. Example: Chess, Pac-Man, investment portfolio bot.

[Added for clarity: Episodic tasks do not require persistent memory of past episodes (though they may still use RAM for the current computation). Sequential tasks inherently need context/memory.]

6.4 Static vs. Dynamic vs. Semi-Dynamic

Dynamism
  • Static: The environment does not change while the agent is deliberating. Example: Rubik's cube, crossword puzzle.
  • Dynamic: The environment can change while the agent is thinking. Example: Driving — traffic signals change; weather.
  • Semi-dynamic: The environment itself does not change, but the performance score degrades with time. Example: Timed chess — the board is static, but your score depends on clock usage.

6.5 Discrete vs. Continuous

Discreteness
  • Discrete: Finite, countable states and percepts/actions. Example: Chess (finite moves), crossword puzzle.
  • Continuous: Infinite possibilities; states/actions are real-valued. Example: Taxi driving — speed, position, angle are continuous variables.

[Added for clarity: Episodic vs. discrete are different concepts. Episodic describes whether past influences future (the overall behavior). Discrete describes whether the states/values themselves are finite and countable.]

6.6 Single-Agent vs. Multi-Agent

Agent Count
  • Single-agent: One agent operates alone in the environment. Example: Crossword puzzle solver.
  • Multi-agent: Other agents (human or AI) are present, each sensing and acting. Example: Car-manufacturing robots, football-playing robots (RobotCup).

Competitive vs. Cooperative Multi-Agent. The key distinction in multi-agent environments is whether the other entities are best described as maximizing a performance measure whose value depends on agent A's behavior. If B is trying to maximize a performance measure that minimizes A's — as in chess — the environment is competitive. If avoiding collisions maximizes the performance of all agents — as in taxi driving — the environment is partially cooperative. Communication often emerges as rational behavior in multi-agent environments; in competitive settings, randomized behavior can be rational because it avoids the pitfalls of predictability.

[Added from textbook: The agent-design problems in multiagent environments are often quite different from those in single-agent environments. Randomization — which is usually not rational in single-agent settings — becomes rational in multi-agent competitive environments to avoid predictability. For example, in poker, randomizing betting patterns (bluffing) prevents the opponent from exploiting deterministic behavior.]

6.7 Known vs. Unknown

Knowledge of the Environment's Rules
Strictly speaking, this distinction refers not to the environment itself but to the agent's (or designer's) state of knowledge about the "laws of physics" of the environment.
  • Known: The outcomes (or outcome probabilities if stochastic) for all actions are given. Example: Chess — the rules are fully known.
  • Unknown: The agent must learn how the environment works through experience. Example: A new video game where you don't know what the buttons do.

Known ≠ Fully Observable. It is quite possible for a known environment to be partially observable: in solitaire card games, you know the rules perfectly but cannot see the cards that haven't been turned over. Conversely, an unknown environment can be fully observable: a new video game may show the entire game state on screen, but you still don't know what buttons do what.

Unknown Performance Measure. The performance measure itself may be unknown — a taxi driver won't know whether a new passenger prefers a leisurely or speedy journey. A virtual personal assistant starts out knowing nothing about its new owner's preferences. In such cases, the agent may need to learn the performance measure from user interactions, effectively making the task a multi-agent problem.

6.8 The Real World as an Environment

To solidify understanding, consider the real world through each lens:

  • Partially observable (we cannot know everything).
  • Stochastic (life involves probability, not certainty).
  • Sequential (yesterday's decisions affect today).
  • Dynamic (the world changes while we deliberate).
  • Continuous (infinite possible states — climate, economy, etc.).
  • Multi-agent (billions of other humans and systems).

7. Agent Architectures (Types)

Recall that inside every agent there is a "question mark" — the mapping from percepts to actions. Different architectures fill this gap in different ways:

7.1 Table-Lookup Agent

The earliest approach (1970s): maintain a giant table mapping every percept sequence to its action. The agent simply looks up the current percept and returns the prescribed action.

Drawbacks: Huge table required; long build time; no autonomy; if a percept is not in the table, the agent cannot act.

7.2 Simple Reflex Agent

Simple Reflex Agent
Selects actions based on the current percept only, using condition–action rules (if–then rules). It ignores percept history.

Example rule for the vacuum cleaner:

if status == Dirty then return Suck
else if location == A then return Right
else if location == B then return Left

Drawback: For a complex agent, the number of if–else rules becomes unmanageable. The agent has no memory of past states.

[Added from textbook: Even a little bit of unobservability can cause serious trouble for reflex agents. Consider the braking example — if the car in front has non-standard tail-lights, a single video frame may not distinguish braking from regular taillights. The reflex agent would either brake continuously or never brake at all. Infinite loops are often unavoidable for simple reflex agents in partially observable environments. Escape is possible through randomization: if the vacuum agent perceives [Clean] but doesn't know its location, flipping a coin between Left and Right ensures it will reach the other room in an average of 2 steps. Randomized simple reflex agents can outperform deterministic ones — but only in limited situations; more sophisticated deterministic agents can do much better.]

7.3 Model-Based Reflex Agent

Model-Based Reflex Agent
Maintains an internal state (model) that tracks:
  • How the world evolves (independently of the agent).
  • What the agent's own actions do.
This internal model is updated with each new percept and used alongside condition–action rules to select actions.

Updating internal state requires two kinds of knowledge encoded in the agent program:

  • Transition model — knowledge about "how the world works": the effects of the agent's actions AND how the world evolves independently. Example: turning the steering wheel clockwise makes the car turn right; when it's raining, cameras get wet.
  • Sensor model — knowledge about how the state of the world is reflected in percepts. Example: when the car in front brakes, illuminated red regions appear in the camera image; when the camera gets wet, droplet-shaped objects appear partially obscuring the road.

Together, the transition model and sensor model allow the agent to keep track of the state of the world — to the extent possible given sensor limitations. It is seldom possible for the agent to determine the current state of a partially observable environment exactly; its internal state represents a "best guess."

7.4 Goal-Based Agent

Goal-Based Agent
In addition to the model and reflex rules, the agent has an explicit goal. It evaluates "What will the world be like if I do action A?" and selects actions that move it closer to the goal.

Example: Navigation — "I am at Arad; my goal is Bucharest. If I go to Sibiu, am I closer to the goal?"

[Added for clarity: The goal is derived from the Performance measure in PEAS. The agent knows what "success" looks like.]

7.5 Utility-Based Agent

Utility-Based Agent
Extends goal-based agents by using a utility function that quantifies how happy the agent is in a given state. The agent chooses the action that maximizes expected utility, not just any action that reaches the goal.

Example: Going from home to office: reaching the office is the goal, but among multiple routes, the utility-based agent picks the best route (fastest, least traffic, most comfort).

[Added for clarity: Key distinction: Goal-based = "Get me to the office" (any route). Utility-based = "Get me to the office via the best possible route" (optimize the outcome, not just achieve the goal).]

Why utility over goals? Two kinds of cases make goals inadequate:

  1. Conflicting goals — only some can be achieved (e.g., speed vs. safety). A utility function specifies the appropriate tradeoff.
  2. Uncertain goal achievement — when several goals can be aimed for but none can be achieved with certainty, utility weighs the likelihood of success against the importance of the goals.

Technically, a rational utility-based agent chooses the action that maximizes the expected utility — the utility the agent expects to derive, on average, given the probabilities and utilities of each outcome. An agent's utility function is essentially an internalization of the performance measure. Provided the internal utility function and the external performance measure agree, an agent that maximizes utility will be rational. Chapter 15 of the textbook shows that any rational agent must behave as if it possesses a utility function whose expected value it tries to maximize. However, perfect rationality is usually unachievable in practice due to computational complexity.

[Added from textbook: Not all utility-based agents are model-based. A model-free agent can learn what action is best in a particular situation without ever learning exactly how that action changes the environment. This is the basis of modern reinforcement learning, covered in Chapters 23 and 26.]

7.6 Learning Agent

Learning Agent
Has four conceptual components:
  • Performance element: The agent's current action-selection mechanism (could be any of the above).
  • Critic: Provides feedback on the agent's performance (positive or negative).
  • Learning element: Uses critic feedback to improve the performance element.
  • Problem generator: Suggests exploratory (suboptimal) actions to discover better strategies.

Concrete example — braking at a red signal:

  1. Percept: Red traffic signal at 50 meters.
  2. Performance element: Apply 17k Newton brake force.
  3. Result: Car stops past the zebra crossing.
  4. Critic: Negative feedback — "You should have stopped before the crossing."
  5. Learning: Next time at 50 meters with a red signal, apply more force (e.g., 19k Newtons) to stop earlier.

[Added for clarity: The critic can be external (e.g., a user saying "this answer is bad") or internal (a predefined reward function). The learning agent uses this signal to improve itself over time, unlike a utility-based agent which optimizes outcomes but does not modify its own logic.]

Fixed Performance Standard. The critic tells the learning element how well the agent is doing with respect to a fixed performance standard. This standard is crucial — the percepts themselves provide no indication of success. A chess program perceives "checkmate," but it needs the performance standard to know that checkmating the opponent is a good thing. Critically, the performance standard must be fixed and outside the agent — the agent must not modify it to fit its own behavior.

The Problem Generator (Exploration). The problem generator is responsible for suggesting exploratory actions — actions that may be suboptimal in the short run but lead to new and informative experiences for long-term improvement. If the performance element had its way, it would keep doing what it knows is best. But without exploration, the agent would never discover potentially better strategies. The textbook likens this to Galileo dropping rocks from the Tower of Pisa — the value was not in breaking rocks, but in modifying his own brain with a better theory of motion. The problem generator identifies parts of the model that need improvement and suggests experiments.

Rewards and Penalties. The performance standard distinguishes part of the incoming percept as a reward (or penalty) that provides direct feedback on behavior quality. The learning element can make changes to any knowledge component: it can learn "What my actions do" by observing pairs of successive states, learn a reflex component from user feedback, or learn to improve the utility function itself. The textbook's summary: learning in intelligent agents is a process of modification of each component to bring them into closer agreement with available feedback information, thereby improving overall performance.

Exam Tip / Common Pitfall
These architectures are not strictly hierarchical — they represent the historical evolution of ideas. For simple tasks, a reflex agent may suffice. For complex, uncertain environments, combining model + goal + utility + learning is appropriate. The fastest type is the simple reflex agent (only rule-matching, no model lookups or optimization), but it is not guaranteed to be optimal in performance.
Q&A. What is the difference between "optimize" (utility-based) and "improve" (learning-based)?
Utility-based optimizes the outcome (choosing the best route to reach the goal). Learning-based improves the agent itself (changing its internal logic based on feedback). A utility-based agent may fail when the environment changes dynamically; a learning agent can adapt to the change. Example: a roadblock suddenly appears — the utility-based agent's "best route" fails; a learning agent learns to avoid that route in the future.

8. Problem-Solving Agents (PSA)

Much early AI work focused on Problem-Solving Agents — agents that formulate a task as a search problem and then solve it using search algorithms.

8.1 The PSA Loop (Four-Phase Process)

A Problem-Solving Agent follows four phases:

  1. Goal Formulation — The agent adopts a goal. Goals organize behavior by limiting the objectives and hence the actions to be considered. Example: "Reach Bucharest."
  2. Problem Formulation — The agent devises an abstract description of the states and actions necessary to reach the goal — what to consider and what to ignore. This is where PEAS analysis meets practical implementation.
  3. Search — Before taking any action in the real world, the agent simulates sequences of actions in its model, searching until it finds a path that reaches the goal. Such a sequence is called a solution. The agent may have to simulate multiple sequences that do not reach the goal before finding one that does — or determining that no solution is possible.
  4. Execution — The agent carries out the actions in the solution, one at a time.

High-level pseudo-code:

  1. Maintain a state (current world description), a goal, and an empty action_sequence.
  2. On receiving a new percept, update the state.
  3. If action_sequence is empty: formulate the problem → search for a solution → store the resulting action sequence.
  4. Return the first action from the sequence and remove it.
  5. If no solution is found, return failure.

Open-Loop vs. Closed-Loop. In a fully observable, deterministic, known environment, the solution to any problem is a fixed sequence of actions. Once the agent has found a solution, it can ignore its percepts while executing — this is an open-loop system (breaking the loop between agent and environment). If there is a chance the model is incorrect or the environment is nondeterministic, the agent should use a closed-loop approach that monitors percepts during execution. In partially observable or nondeterministic environments, a solution would be a branching strategy (contingency plan) that recommends different future actions depending on what percepts arrive.

Abstraction: The Art of Leaving Things Out. Problem formulation is fundamentally about abstraction — removing irrelevant detail from the representation. Compare the simple atomic state "Arad" to the actual experience of a cross-country trip: traveling companions, current radio program, scenery, proximity of law enforcement, road conditions, weather, traffic — all are left out because they are irrelevant to finding a route to Bucharest. The abstraction is valid if any abstract solution can be elaborated into a solution in the more detailed world. It is useful if carrying out each abstract action is easier than solving the original problem. The choice of a good abstraction involves removing as much detail as possible while retaining validity. Were it not for the ability to construct useful abstractions, intelligent agents would be completely swamped by the real world.

8.2 The Five Components of a Search Problem

Problem Formulation — 5 Components (Formal Definition)
To model any task as a search problem, define:
  1. Initial State — Where the agent starts.
  2. Possible Actions — For any given state s, ACTIONS(s) returns the finite set of applicable actions. An action is applicable in s if it can be executed there.
  3. Transition Model (successor function) — RESULT(s, a) returns the state reached by performing action a in state s. This is the agent's "what happens if I do X?" knowledge.
  4. Goal Test — IS-GOAL(s) returns true if s is a goal state. The goal may be a single state, a small set of alternative states, or a property that applies to many states (e.g., "no dirt anywhere").
  5. Path Cost — A numeric cost function ACTION-COST(s, a, s′) that gives the cost of applying action a in state s to reach state s′. The total path cost is the sum of individual action costs along the path. A problem-solving agent should use a cost function that reflects its own performance measure; the textbook assumes all action costs are positive.

A solution is a sequence of actions leading from the initial state to a goal state. An optimal solution has the lowest path cost among all solutions.

8.3 State, State Space, and Graphs

  • State: All information about the environment necessary to make a decision for the task at hand. (Equivalent to the "current world description.")
  • State Space: The set of all states reachable from the initial state by any sequence of actions.
  • State Space Graph: Nodes = states; arcs (edges) = actions. A path is a sequence of states connected by actions.
  • The solution is a path in this graph from the initial state to any goal state.

[Added for clarity: The state-space representation forms the foundation of most classical AI methods. If a problem can be cast as a graph, it can be solved by graph-search algorithms.]

Problem formulation is the process of deciding which actions and states to consider, given a goal. This involves abstraction — ignoring irrelevant details (e.g., the agent's radio, exact GPS coordinates within Arad) to focus only on what matters for reaching the goal.

9. Worked Examples of Problem Formulation

9.1 Route-Finding: Arad to Bucharest

Consider a map of Romanian cities with distances (path costs) on each road segment.

Arad to Bucharest — Formulation
  1. Initial State: In(Arad) — the agent is in Arad.
  2. Possible Actions: From any city s, ACTIONS(s) = {Go(c) | c is a neighboring city of s}.
    From Arad: {Go(Zerind), Go(Sibiu), Go(Timisoara)}.
  3. Transition Model: RESULT(In(s), Go(c)) = In(c).
    E.g., RESULT(In(Arad), Go(Sibiu)) = In(Sibiu).
  4. Goal Test: IS-GOAL(In(s)) = true iff s = Bucharest.
  5. Path Cost: Sum of road distances along the path. E.g., Arad → Sibiu costs 140 units; Arad → Zerind costs 75 units; etc.

9.2 The Vacuum-Cleaner World (Revisited)

Vacuum Cleaner — Formal Formulation
  1. States: 8 possible combinations of {agent position (A/B)} × {A clean/dirty} × {B clean/dirty}.
  2. Initial State: Any state; typically both rooms dirty, agent in A.
  3. Actions: {Left, Right, Suck}.
  4. Transition Model:
    • Left moves agent to the left room, unless already in the leftmost room (A) → stays in A.
    • Right moves agent to the right room, unless already in the rightmost room (B) → stays in B.
    • Suck cleans the current room (makes it Clean) without changing position.
  5. Goal Test: Both rooms are Clean.
  6. Path Cost: Each action costs 1; total path cost = number of steps.

[Added for clarity: The transition diagram for the vacuum world has 8 nodes (states) with directed edges for each legal action. From the state (A=Clean, B=Dirty, agent in A), taking Right leads to (A=Clean, B=Dirty, agent in B); taking Suck in (A=Dirty, B=Clean, agent in A) leads to (A=Clean, B=Clean, agent in A) — the goal state.]

9.3 The 8-Puzzle

8-Puzzle — Formulation

The 8-puzzle is a 3 × 3 grid with tiles numbered 1–8 and one blank space. Tiles adjacent to the blank can slide into it.

  1. States: All possible permutations of tiles 1–8 and the blank on the 3 × 3 grid.
  2. Initial State: A given scrambled configuration.
  3. Goal State: 
    1 2 3
4 5 6
7 8 □
    where □ denotes the blank. Equivalently: each tile t is in position (t−1) ÷ 3 row, (t−1) mod 3 column.
  4. Actions: {Up, Down, Left, Right} — moving the blank space.
  5. Transition Model: Swapping the blank with the adjacent tile in the chosen direction.
  6. Path Cost: Each move costs 1; total = number of moves.

[Added for clarity: The 8-puzzle state space forms a graph where nodes are board configurations and edges are legal tile slides. This is a classic benchmark for search algorithms.]

10. Search Strategies: Uninformed vs. Informed

Once a problem is formulated as a search problem, we apply a search strategy (algorithm) to find the solution path. The textbook presents this through the unifying framework of best-first search.

10.0 The Best-First Search Framework

All the search algorithms in this chapter are instances of best-first search, which works as follows:

  1. Start with a frontier (a priority queue) containing just the initial state.
  2. Maintain a reached table mapping states to their lowest-cost nodes found so far.
  3. On each iteration: pop the node with the minimum evaluation function f(n) from the frontier.
  4. If it's a goal, return it. Otherwise, EXPAND it — generate all child nodes via ACTIONS and RESULT.
  5. For each child: if the state hasn't been reached before, or we found a cheaper path, update the reached table and add the child to the frontier.

By choosing different f(n) functions, we get different algorithms. A key data structure is the node: node.STATE, node.PARENT, node.ACTION, node.PATH-COST (denoted g(n) in formulas). Following PARENT pointers back from a goal node gives the solution path.

Search Tree vs. State-Space Graph. The state space describes the set of all states in the world and the actions that allow transitions between them. The search tree describes paths superimposed on this graph, reaching toward the goal. A search tree may have multiple nodes for the same state (via different paths), but each node has a unique path back to the root. The frontier separates two regions: an interior where every state has been expanded, and an exterior of states not yet reached.

Redundant Paths. A cycle (loopy path) occurs when a state is revisited — e.g., Arad → Sibiu → Arad. More generally, a redundant path is any path to a state already reached via a better path (e.g., Arad → Sibiu at 140 miles vs. Arad → Zerind → Oradea → Sibiu at 297 miles). Three approaches: (1) Graph search — track all reached states to avoid all redundant paths. (2) Tree-like search — don't track reached states; uses less memory but may revisit. (3) Cycle checking — check parent chain for loops only. As the textbook says: "algorithms that cannot remember the past are doomed to repeat it."

Measuring Search Performance (4 criteria):

  • Completeness: Is the algorithm guaranteed to find a solution when one exists, and correctly report failure when it doesn't?
  • Cost optimality: Does it find the lowest path-cost solution?
  • Time complexity: How long (in states/actions considered)?
  • Space complexity: How much memory? Typically characterized in terms of b (branching factor), d (depth of optimal solution), and m (maximum depth).

10.1 Uninformed (Blind) Search

Uninformed Search
Uses only the information available in the problem definition (states, actions, goal test, path cost). No additional knowledge about which states are more "promising." Also called blind search.

Common uninformed strategies:

  • BFS (Breadth-First Search): Expands nodes level by level — root first, then all depth-1 nodes, then depth-2, etc. Uses a FIFO queue. When all actions have equal cost, BFS is cost-optimal (finds solution with minimal actions) and complete even on infinite state spaces. Can use an early goal test (checking at generation time) because once a state is reached, no better path to it can ever be found. Time/space complexity: O(bd). The memory requirement is typically the bigger problem — a search with b=10, d=10 needs ~10 TB.
  • DFS (Depth-First Search): Expands the deepest node first. Typically implemented as a tree-like search (no reached table) using a LIFO queue (stack). Not cost-optimal — returns the first solution found. Incomplete on infinite state spaces (can get stuck going down an infinite path). Key advantage: memory — only O(bm) instead of O(bd). A variant called backtracking search uses even less memory by generating only one successor at a time and modifying the current state in place — memory drops to O(m).
  • UCS (Uniform-Cost Search): Expands the node with the lowest path cost g(n). Spreading out in waves of uniform path-cost rather than uniform depth. Implemented with a priority queue ordered by PATH-COST. Key nuance: uses late goal test — checks for goals when expanding, not when generating — because a goal generated via a more expensive path should not be returned if a cheaper path is still being explored. Complete and cost-optimal for positive action costs. Complexity: O(b1+⌊C*/ϵ⌋), where C* is optimal solution cost and ϵ is minimum action cost.
  • Depth-Limited Search: DFS with a cut-off depth ℓ — treats nodes at depth ℓ as having no successors. Incomplete if ℓ is chosen poorly.
  • Iterative Deepening Search (IDS): Repeatedly runs depth-limited search with increasing depth limits (0, 1, 2, …). Combines DFS's modest memory (O(bd)) with BFS's completeness and cost-optimality (for uniform costs). The repeated work at shallower levels is asymptotically negligible — nodes at depth d are generated once, depth d−1 twice, etc., giving the same O(bd) time as BFS. With b=10, d=5, IDS generates 123,450 nodes vs. BFS's 111,110 — only ~11% overhead.

[Added for clarity: These are standard computer science topics covered in Data Structures courses. Students unfamiliar with BFS/DFS should review the textbook animations and supplementary materials. They are foundational but not directly examined as AI-specific content.]

Drawback: Uninformed searches are slow for large state spaces — they have no guidance on which direction to explore. Exponential-complexity search problems cannot be solved by uninformed search for any but the smallest instances. At b=10, processing 1M nodes/second: depth d=10 takes under 3 hours but needs 10 TB of memory; d=14 takes 3.5 years even with infinite memory.

Systematic Search for Completeness. To be complete, a search algorithm must be systematic — it must eventually reach every state connected to the initial state. In infinite state spaces, this requires careful design. Simply going deeper along one path (like repeatedly applying factorial in Knuth's "4" problem) never explores wide expanses of the state space. On an infinite grid, one systematic approach is a spiral path covering all cells s steps from origin before moving to s+1 steps away. If no solution exists in an infinite space, a sound algorithm must keep searching forever — it can't know the next state won't be a goal.

10.2 Informed (Heuristic) Search

Informed Search
Uses heuristics — extra domain-specific knowledge that estimates which non-goal states are "more promising" (closer to the goal). The heuristic function h(n) estimates the cheapest cost from node n to a goal.
Exam Tip / Common Pitfall
A heuristic is an intuition, not guaranteed knowledge. It may be wrong. Informed search algorithms that use heuristics are not always optimal. Some (like A* with admissible heuristics) guarantee optimality, but the heuristic itself is only an estimate.

Common informed strategies:

  • Best-First Search: Expands the node with the lowest heuristic value h(n).
  • A* Search: Expands the node with the lowest f(n) = g(n) + h(n), where g(n) is the path cost so far and h(n) is the heuristic estimate to the goal.
  • AO*: Variant for AND-OR graphs (problem decomposition).
Exam Tip / Common Pitfall
Cost-based search is not automatically informed. If a graph comes with edge costs as part of the problem definition, those costs are just problem data. A search using only those costs (like UCS) is still uninformed. It becomes informed only when you add extra heuristic knowledge beyond the problem definition.

11. Key Terms / Glossary

Agent
Anything that perceives its environment through sensors and acts upon it through actuators.
Agent Function
The mapping from percept histories to actions.
Agent Program
The concrete implementation of the agent function running on a physical architecture.
Rational Agent
An agent that strives to do the "right thing" as measured by a performance criterion.
Ideal Rational Agent
An agent that, for each percept sequence, selects the action expected to maximize its performance measure, based on all evidence so far and built-in knowledge.
Performance Measure
An objective criterion for evaluating the success of an agent's behavior.
PEAS
Performance, Environment, Actuators, Sensors — the framework for specifying an agent's design context.
Fully Observable
The agent's sensors give access to the complete state of the environment at all times.
Partially Observable
The agent has limited or noisy access to the environment state.
Deterministic
The next state is completely determined by the current state and action.
Stochastic
The next state involves uncertainty; the same action may lead to different outcomes.
Episodic
Each decision episode is independent of past and future episodes.
Sequential
Current decisions affect or depend on past/future decisions.
Static
The environment does not change while the agent deliberates.
Dynamic
The environment can change while the agent deliberates.
Semi-Dynamic
The environment is static, but performance degrades with time.
Discrete
Finite, countable states and actions.
Continuous
States and/or actions are real-valued (infinite possibilities).
Simple Reflex Agent
Selects actions based only on the current percept using condition–action rules.
Model-Based Agent
Maintains an internal state (model) of how the world evolves.
Goal-Based Agent
Has explicit goal states and selects actions that move toward the goal.
Utility-Based Agent
Uses a utility function to choose the best among goal-reaching actions.
Learning Agent
Improves its performance element over time using feedback from a critic.
Problem-Solving Agent
An agent that formulates tasks as search problems and solves them via search algorithms.
State
All information about the environment needed to make a decision for the task.
State Space
The set of all states reachable from the initial state.
Transition Model
Function RESULT(s,a) giving the state reached after action a in state s.
Goal Test
Function that determines whether a state is a goal state.
Path Cost
Sum of step costs along a path from the initial state to a given state.
Uninformed Search
Search using only problem-definition information (BFS, DFS, UCS).
Informed Search
Search guided by heuristics — extra domain knowledge about promise of states (Best-First, A*, AO*).
Heuristic
A function h(n) that estimates the cheapest cost from node n to a goal; an intuition, not guaranteed correct.
AI Agent
A single software agent powered by LLMs with predefined scripts and limited autonomy.
Agentic AI
A network of AI agents with higher autonomy, capable of orchestration, tool-calling, and coordination.

13. One-Page Summary / Cheat Sheet

Quick Reference

Agent Definition: Perceives via sensors → Acts via actuators.

PEAS: Performance (what to optimize), Environment (where it operates), Actuators (how it acts), Sensors (how it perceives).

Environment Properties (6 axes):

PropertyValuesKey Question
ObservabilityFull / Partial / NoneCan it see everything?
DeterminismDeterministic / StochasticSame action = same result?
EpisodicityEpisodic / SequentialDoes past affect future?
DynamismStatic / Semi-Dynamic / DynamicDoes world change while thinking?
DiscretenessDiscrete / ContinuousAre states countable?
AgentsSingle / MultiIs it alone?

Agent Architectures (evolution, not hierarchy):

  1. Table-Lookup — giant table, no autonomy.
  2. Simple Reflex — condition–action rules, no memory. Fastest.
  3. Model-Based — internal state tracks world evolution.
  4. Goal-Based — explicit goal; checks "what if I do A?"
  5. Utility-Based — maximizes happiness (utility), not just goal achievement.
  6. Learning — critic + learning element improve the agent over time.

Search Problem — 5 Components:

  1. Initial State
  2. ACTIONS(s) — set of possible actions in state s
  3. RESULT(s,a) — transition model
  4. IS-GOAL(s) — goal test
  5. Path Cost g(n) — sum of step costs from start to node n

Search Strategies:

  • Uninformed: BFS, DFS, UCS — no extra knowledge.
  • Informed: Best-First, A* (f = g + h), AO* — guided by heuristic h(n).

Key Distinctions:

  • Rational ≠ Omniscient — agent acts on what it knows, not on infinite knowledge.
  • Utility-based ≠ Learning — utility optimizes outcome; learning improves the agent itself.
  • Deterministic ≠ "different actions have different results" — deterministic means same action always yields same result.
  • Heuristic ≠ Knowledge — a heuristic is an intuition that may be wrong.

Explanation: PEAS stands for Performance measure, Environment, Actuators, Sensors — the standard Russell & Norvig framework for describing an agent task before designing the agent program.

Explanation: Chess moves depend on prior positions (sequential), the board is visible (fully observable), rules are fixed (deterministic), the clock makes the world change during play (dynamic), moves are discrete, and two players interact.

Explanation: Classical problem-solving formulates search over states using an initial state, applicable actions, a model of results, a goal test, and a path-cost function — enabling algorithms like BFS, UCS, and A*.
