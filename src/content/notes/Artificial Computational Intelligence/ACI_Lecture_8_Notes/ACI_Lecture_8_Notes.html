1. Adversarial Search and the Minimax Algorithm

8.1 What is adversarial search?

Hook. Imagine playing chess. You spot a move that captures the opponent's queen in three turns. But then you pause — what if your opponent sees it too? What if they have a counter that traps your queen instead? In adversarial settings, your best move depends entirely on what the other player will do about it. This is the central tension of adversarial search.

In many AI problems, a single agent solves a problem alone — find the shortest path, schedule the tasks, classify the image. But in games, there are two or more players with opposing goals. This changes everything.

In an adversarial search, one player's gain is another player's loss. This is called a zero-sum game. What one wins, the other loses exactly. Think of it as a fixed pie: if I get a bigger slice, you get a smaller one. There is no "we both win."

Intuition + Analogy. Think of adversarial search like two people fighting over the last slice of pizza. You don't just think "which move gets me the pizza?" — you think "if I reach for it, will they grab it first? Should I distract them?" Each decision depends on predicting the other person's response. That prediction depends on their goal (get the pizza), not on your goal. This is exactly how minimax thinks: MAX wants the highest score, MIN wants the lowest score for MAX, and MAX knows MIN will aim low.

Where the analogy breaks: In pizza, you might share. In zero-sum games, sharing is impossible — every gain for you is an equal loss for them. Also, real pizza fights have emotions and bluffing; minimax assumes pure cold rationality from both sides.

8.2 The Minimax Algorithm

Formal definition. Minimax is the foundational algorithm for two-player, deterministic, perfect-information, zero-sum games. The two players are called MAX and MIN. MAX wants to maximize the utility (score). MIN wants to minimize MAX's utility — which is the same as maximizing their own, since it's zero-sum.

The minimax value of a state \(s\), written MINIMAX(\(s\)), is the utility MAX can guarantee from that state, assuming both players play optimally from there to the end:

\[ \text{MINIMAX}(s) = \begin{cases} \text{UTILITY}(s, \text{MAX}) & \text{if IS-TERMINAL}(s) \\ \max_{a \in \text{Actions}(s)} \text{MINIMAX}(\text{RESULT}(s,a)) & \text{if TO-MOVE}(s) = \text{MAX} \\ \min_{a \in \text{Actions}(s)} \text{MINIMAX}(\text{RESULT}(s,a)) & \text{if TO-MOVE}(s) = \text{MIN} \end{cases} \]

Every symbol:

  • \(s\): the current game state (board position).
  • \(\text{Actions}(s)\): all legal moves from state \(s\).
  • \(\text{RESULT}(s, a)\): the state you reach after taking action \(a\) from state \(s\).
  • \(\text{IS-TERMINAL}(s)\): true if the game is over in state \(s\).
  • \(\text{UTILITY}(s, \text{MAX})\): the final numeric payoff to MAX in terminal state \(s\).

At terminal states, you just read off the utility. At MAX nodes, you pick the child with the highest minimax value. At MIN nodes, you pick the child with the lowest minimax value.

Worked Example — Two-ply game tree.

         MAX (root)
        /    |    \
      B     C     D    ← MIN nodes
     /|\   /|\   /|\
    3 12 8 2 x y 14 5 2  ← terminal utilities (from MAX's view)

Step through in-order (DFS):

  1. B's children: B is MIN. Leaf values: 3, 12, 8. MIN picks the smallest → 3.
  2. C's children: Leaf values: 2, x, y. Without looking at x and y yet, MIN would pick at most 2. So C's value ≤ 2.
  3. D's children: Leaf values: 14, 5, 2. MIN picks smallest → 2.
  4. Root (MAX): Children have backed-up values: B=3, C≤2, D=2. MAX picks the largest → 3.

Final answer: 3. Even without knowing x and y, we already know C cannot beat B's 3.

Sense check: MAX gets 3, not the 14 or 12 that appear at leaves — because MIN would never allow MAX to reach those. That's the whole point of minimax. MIN fights back.

What Minimax guarantees. Minimax does not promise to get you the best possible reward. It promises to keep you away from the worst possible outcome. If you attend every class, the instructor does not promise you will top the course — but they promise you will not fail. That is the Minimax guarantee: it ensures you avoid the worst-case scenario, assuming your opponent plays optimally.

Traversal method. Minimax uses depth-first search (DFS), specifically in-order traversal. You go all the way down the leftmost branch to a leaf, compute its utility, then back up. You repeat for each sibling, then back up to the parent. This is why the leftmost path is always fully explored — there is nothing to compare against yet.

8.3 Why not search the entire tree?

The size problem. Tic-tac-toe has about \(9! \approx 362,\!880\) terminal nodes — manageable. Chess has over \(10^{40}\) nodes. The average chess game lasts about 80 ply (one ply = one player's move), with a branching factor around 35. That's \(35^{80} \approx 10^{123}\) states — more than atoms in the observable universe. Even world champions calculate only 3 to 7 ply deep in their minds. No computer can search to the end.

The solution: depth limit + evaluation. We search only a few levels deep, using a depth limit. At the cutoff, instead of true terminal utilities, we call a static evaluation function — a heuristic that estimates how good the board position is without looking further ahead.

Minimax searches a game tree depth-first, alternating between MAX (picks highest child) and MIN (picks lowest child). It guarantees avoiding the worst case, not achieving the best. For large games like chess, the full tree is too big — we must cut off search early and estimate positions with an evaluation function.

2. Static Evaluation Functions

8.4 What is a static evaluation value?

Hook. You're playing chess. It's the middle game. Neither side has won yet. But you can feel who's ahead — you count pieces, check who controls the center, see whose king is exposed. A static evaluation function does exactly this, but with math instead of gut feeling. It gives a number: positive = MAX is ahead, negative = MIN is ahead.

The numbers shown at leaf nodes in minimax tree diagrams are not final utilities (win/loss/draw). They are static evaluation values (SEV). They estimate the utility of a non-terminal game state — a board where the game is not yet over.

A static evaluation function evaluates the board "statically" — as a snapshot, without looking ahead at future moves. It's like judging a chess position from a single photograph rather than playing out the rest of the game.

8.5 What makes a good evaluation function?

Intuition + Analogy. Think of a real-estate appraiser estimating a house's value. They don't simulate 20 years of the house's future. They look at static features: square footage, number of bedrooms, school district, recent sales nearby. A good appraiser gives higher values to better houses and is fast. A chess evaluation function does the same: it looks at piece counts, board control, pawn structure — and assigns a number.

Where the analogy breaks: A house's value doesn't depend on what a hostile opponent will do to it. Chess evaluation must account for the opponent's pieces and threats too.

A good evaluation function must satisfy four properties:

  1. Order-preserving: Give higher values to better states for MAX.
  2. Order-reversing for MIN: Give lower values to states that favor MIN.
  3. Fast to compute: Must evaluate thousands or millions of positions per second.
  4. Correlated with winning: The ranking produced by the evaluation function should match (as closely as possible) the ranking that would come from playing the game to completion.

8.6 The general formula

The static evaluation value for a board position is:

\[ \text{SEV} = \sum U(\text{MAX}) - \sum U(\text{MIN}) \]

That is: add up the utility scores of all features favorable to MAX, then subtract the sum of all features favorable to MIN.

  • Positive SEV → the position is good for MAX.
  • Negative SEV → the position is good for MIN.
  • Zero → roughly balanced.

Weighted variant. When some features matter more than others, assign weights:

\[ \text{SEV} = \sum w_i \cdot U_i(\text{MAX}) - \sum w_j \cdot U_j(\text{MIN}) \]

Each \(w_i\) is a weight telling you how important feature \(i\) is. For example, in chess, controlling the center might get a higher weight than having a pawn on the edge.

These values reflect how powerful each piece is. A queen controls many squares and can move in any direction — worth 9. A pawn moves only forward, one square at a time — worth 1.

Board 1:

  • White (MAX): Knight (3) + Bishop (3) = 6
  • Black (MIN): Knight (3) + Pawn (1) + Queen (9) = 13
  • \(\text{SEV} = 6 - 13 = \mathbf{-7}\) → Bad for White.

Board 2:

  • White: Knight (3) + Bishop (3) + Pawn (1) = 7
  • Black: Knight (3) + Bishop (3) = 6
  • \(\text{SEV} = 7 - 6 = \mathbf{+1}\) → Slight edge for White.

Board 3:

  • White: Knight (3) + Pawn (1) + Bishop (3) = 7
  • Black: Knight (3) + Pawn (1) = 4
  • \(\text{SEV} = 7 - 4 = \mathbf{+3}\) → White advantage.

Board 4:

  • White: Knight (3) + Pawn (1) = 4
  • Black: Queen (9) + Knight (3) + Pawn (1) = 13
  • \(\text{SEV} = 4 - 13 = \mathbf{-9}\) → Worst for White among the four.

Sense check: Board 4 is the worst because White has no queen while Black does. The queen's value (9) dwarfs the difference. If you are White, minimax with these SEVs will steer you away from positions like Board 4.

Visual intuition. Imagine a bar chart with four bars: Board 1 at −7, Board 2 at +1, Board 3 at +3, Board 4 at −9. The bars above zero (green) are good for White. The bars below zero (red) are good for Black. Board 4's bar plunges deepest into the red. A MAX player scanning these bars will immediately avoid Board 4 and prefer Board 3. That's what minimax does — it scans the SEV bars of all children and picks the tallest one.

8.8 Tic-tac-toe static evaluation

Why piece-counting fails here. In tic-tac-toe, pieces are never captured. Both X and O get equal chances to fill the 9 squares. Counting X's and O's doesn't tell you who is winning — both always have similar counts. You need a different metric.

Method: Win-configuration counting. For a given board state:

  1. For X (MAX): Fill every empty cell with X. Count how many winning lines (3-in-a-row: rows, columns, diagonals) are completed.
  2. For O (MIN): From the same original board, fill every empty cell with O. Count how many winning lines would be completed.
  3. Compute SEV: \(\text{SEV} = (\text{wins possible for X}) - (\text{wins possible for O})\)

Worked tic-tac-toe example. Given a partially filled board:

 X | O | X
---+---+---
   | X |
---+---+---
 O |   | O

Step 1 — Fill empty cells with X:

 X | O | X
---+---+---
 X | X | X   ← row 2 becomes a win for X (3 X's)
---+---+---
 O | X | O

X has 1 horizontal win (middle row). Check diagonals: main diagonal has X-O-X (not a win), anti-diagonal has X-X-O (not a win). Total X wins = 1.

Step 2 — Fill empty cells with O (from original board):

 X | O | X
---+---+---
 O | X | O   ← no row/column/diagonal has 3 O's
---+---+---
 O | O | O   ← row 3 becomes a win for O

O has 1 horizontal win (bottom row). Total O wins = 1.

Step 3: \(\text{SEV} = 1 - 1 = \mathbf{0}\) — Balanced position.

Now consider a different board where X is stronger:

 X |   |
---+---+---
 X | O | O
---+---+---
 X |   |

Filling with X gives the left column (already 3 X's). Filling with O gives no completed line. \(\text{SEV} = 3 - 0 = \mathbf{+3}\). X is clearly ahead.

Sense check: In the second board, X already has the left column locked. X can win on the next move in multiple ways. O cannot block all of them. The +3 SEV correctly signals X's advantage.

Common pitfalls with static evaluation:

  1. Forgetting to state who is MAX. The formula is always (your advantage) − (opponent's advantage). If you flip MAX and MIN, the sign of the SEV flips. Always declare: "I am MAX and I am X" at the start.
  2. Confusing SEV with final utility. SEV is an estimate of a non-terminal position — not the final win/loss result. A position with SEV = +3 might still be lost if the opponent has a forced checkmate sequence the evaluation missed.
  3. Bad evaluation functions mislead minimax. If your evaluation function says a losing position is winning, minimax will confidently steer you into that losing position. The algorithm is only as good as its evaluation function.
  4. Computing SEVs for the wrong player's turn. Always compute from the perspective stated at the start. Don't switch perspective mid-problem.

8.9 Where SEVs come from in exam problems

In exam problems, SEV values may be given directly as leaf values in the tree — you just propagate them up with minimax. Alternatively, a description of the evaluation function plus any piece-value tables are provided, and you must compute the SEVs for each leaf yourself before propagating.

8.10 Domain connection

Static evaluation functions are the "eyes" of every chess engine. Deep Blue, the IBM computer that beat world champion Garry Kasparov in 1997, used a hand-crafted evaluation function with over 8,000 features. These included piece values, pawn structure, king safety, center control, rook on open files, and more. Modern engines like Stockfish still use carefully tuned evaluation functions, though they are now augmented with neural networks. The same principle scales beyond chess. In any adversarial domain where you must estimate position quality without searching to the end — from military strategy simulations to automated negotiation agents — you need a fast, correlated evaluation function.

A static evaluation function estimates how good a non-terminal board position is. The general formula is SEV = ΣU(MAX) − ΣU(MIN). For chess, use piece-value tables. For tic-tac-toe, use win-configuration counting. The evaluation must be fast, order-preserving, and correlated with actual winning chances.

3. Alpha-Beta Pruning

8.11 Motivation

Hook. You're shopping for the cheapest phone. You check Store A: $600. Store B: you see a $700 model and walk out — you already know Store A is cheaper, so who cares about Store B's other models? That's alpha-beta pruning. You stop looking when the current option is already worse than something you've already found.

In standard minimax, you inspect every leaf in the tree. For a tree with branching factor \(b\) and depth \(d\), that's \(O(b^d)\) nodes. This is computationally expensive and often impossible for real games.

Alpha-beta pruning is minimax with an added intelligence: you skip evaluating branches that cannot possibly affect the final decision. It is not a new algorithm — it is minimax, made smarter by noticing when further search is pointless.

Key fact: Alpha-beta pruning gives the exact same answer as full minimax. The only difference is performance — alpha-beta inspects fewer nodes, sometimes as few as \(O(b^{d/2})\) in the best case (effectively doubling the search depth for the same time budget).

8.12 What are alpha and beta?

Every node in the tree carries one of two variables:

  • Alpha (\(\alpha\)): The best value found so far that MAX can guarantee at this node or above. Initialized to \(-\infty\). Think: "MAX can get at least this much." Alpha lives at MAX nodes.
  • Beta (\(\beta\)): The best value found so far that MIN can force MAX to accept at this node or above. Initialized to \(+\infty\). Think: "MIN can hold MAX to at most this much." Beta lives at MIN nodes.

The roles never change: MAX nodes always carry alpha. MIN nodes always carry beta. If the root is MIN, the root carries beta — but alpha and beta still mean exactly the same things.

8.13 The pruning conditions

When you update a value, you check the corresponding pruning condition. If the condition is true, you immediately prune (skip) the remaining children.

Alpha-update pruning condition (triggered when alpha increases at a MAX node):

\[ \beta(\text{parent}) \leq \alpha(\text{current}) \]

If true → prune remaining siblings. The MIN parent already has a better (lower) option than anything this MAX child can offer.

Beta-update pruning condition (triggered when beta decreases at a MIN node):

\[ \beta(\text{current}) \leq \alpha(\text{parent}) \]

If true → prune remaining siblings. This MIN node's best value is already worse (higher) for MAX than what the MAX parent already has available elsewhere.

8.14 The core intuition - contradiction between parent and child

The one insight that makes alpha-beta click. Forget the formulas for a moment and understand this:

  • A MIN node (beta) is always hunting for a value less than its current beta. It wants to minimize.
  • A MAX node (alpha) is always hunting for a value greater than its current alpha. It wants to maximize.

When a MIN node has beta = 6 and its MAX child has alpha = 8:

  • The MIN parent wants something under 6.
  • The MAX child wants something over 8.
  • Even if the MAX child finds 100, the MIN parent will never pick it — because MIN only accepts values under 6.

The child's goal contradicts the parent's goal. Exploring the child's remaining siblings is wasted effort. Prune them.

This is the core question: "Why are you looking for something greater than 8 when I want less than 6?"

Analogy. Imagine a parent (MIN) looking for the cheapest car — budget: under $6,000. The child (MAX) is at a dealership finding cars that cost $8,000+. The parent is never buying from that dealership. Stop looking at that dealership's other cars.

8.15 Complete worked example 1

Tree setup. MAX at root, MIN at level 2, MAX at level 3 (leaves). Leaf values are given at the bottom.

              [α=root] MAX
             /            \
      [β=B] MIN          [β=C] MIN
      /    \             /    \
  [α=D]  [α=E]      [α=F]  [α=G]  MAX
  / \    / \         / \    / \
 6   5  8  10       2  1   7  3     ← leaves (SEVs)

Step-by-step (DFS, in-order):

Step 1: Go to leftmost leaf = 6.

  • D (MAX): α was −∞. 6 > −∞, so α = 6. Alpha update.
  • Check: β(parent B) ≤ α(current D)? β(B) = +∞. +∞ ≤ 6? No. No pruning.

Step 2: Next leaf under D = 5.

  • 5 < 6. α stays 6. D's subtree done. D = 6.

Step 3: Propagate D=6 up to parent B (MIN).

  • B: β was +∞. Now β = 6. Beta update.
  • Check: β(current B)=6 ≤ α(parent root)=−∞? No. No pruning.

Step 4: Go to E's left child = 8.

  • E (MAX): α = −∞ → 8. Alpha update.
  • Check: β(parent B)=6 ≤ α(current E)=8? Yes! 6 ≤ 8. → PRUNE E's right child (10).

Why? B (MIN) already has a path to value 6 (via D). B wants the minimum. E is already at 8, which means E's value will be ≥ 8. B will never pick ≥ 8 when it already has 6. E's remaining children are irrelevant.

Step 5: B's subtree done. B = min(6, 8) = 6. Propagate to root.

  • Root: α = −∞ → 6. Alpha update. No parent to check.

Step 6: Go to F's left child = 2.

  • F (MAX): α = −∞ → 2. Alpha update.
  • Check: β(C)=+∞ ≤ 2? No.

Step 7: F's right child = 1.

  • 1 < 2, α stays 2. F = 2.

Step 8: Propagate to C (MIN). β = +∞ → 2. Beta update.

  • Check: β(C)=2 ≤ α(root)=6? Yes! 2 ≤ 6. → PRUNE G and all its children.

Why? The root already has α=6 (via B). C's value is at most 2 (via F). The root MAX wants the maximum. It will never pick ≤2 when it already has 6. C's remaining subtree (G) is irrelevant.

Final root value: 6.

Sense check: Pruned branches (10, and entire G subtree) cannot change the answer. If we had evaluated them, G's value would be max(7,3)=7, C=min(2,7)=2, root=max(6,2)=6 — same answer. Alpha-beta saved us from evaluating 10, 7, and 3.

8.16 Complete worked example 2 (simpler, step-by-step)

Tree: MAX root, MIN at level 2, MAX at level 3. Leaf values: 3, 4, 2, 1, 7, 8, 2, 11, 1.

                  [α] MAX (root)
              /          |          \
        [β] MIN        [β] MIN      [β] MIN
        /    \         /    \        /    \
    [α]MAX [α]MAX [α]MAX [α]MAX [α]MAX [α]MAX
     / \    / \    / \    / \    / \
    3   4  2   1  7   8  2  11  1  ?   ← leaves

Setup: α nodes = −∞, β nodes = +∞. ■ = MAX, ● = MIN.

Step 1: Root → left → left → left. Leaf = 3.

  • MIN node β: +∞ → 3. Beta update.
  • Check: β=3 ≤ α(parent)=−∞? No.

Step 2: Next leaf = 4. 4 not < 3. β stays 3. MIN subtree done → β=3.

  • Propagate to parent MAX (leftmost): α = −∞ → 3. Alpha update.
  • Check: β(parent)=+∞ ≤ α=3? No.

Step 3: Next MIN child. Left → leaf = 2.

  • MIN β: +∞ → 2. Beta update.
  • Check: β=2 ≤ α(parent)=3? Yes! 2 ≤ 3. → PRUNE right child (1).

Intuition: This MIN wants <2. Its MAX parent already has 3 (wants >3). MIN's best (2) is worse than what MAX already has (3). MAX won't pick it.

Step 4: Leftmost MAX done. α = max(3, 2) = 3. Propagate to root: α = −∞ → 3.

Step 5: Go right side. New MIN → left → leaf = 7.

  • MAX α: −∞ → 7. Alpha update. β(parent)=+∞ ≤ 7? No.
  • Next leaf = 8. 8 > 7. α stays 7. MAX = 7.
  • Propagate to MIN: β = +∞ → 7.

Step 6: Next MAX child. Leaf = 2.

  • MAX α: −∞ → 2. Alpha update. β(parent)=7 ≤ 2? No.
  • Next leaf = 11. 11 > 2. α stays 2. MAX = 2.
  • Propagate to MIN: β = min(7, 2) = 2. Beta update.
  • Check: β=2 ≤ α(root)=3? Yes! 2 ≤ 3. → PRUNE third MAX child (1 and its sibling).

Final root value: 3.

Sense check: The pruned values (1, 1, ?) cannot beat the root's existing α=3. Same result as full minimax.

8.17 Important rules about pruning

Critical rules — do NOT violate these:

  1. The left child can never be pruned. You must always explore the first path fully to get an initial α or β before any comparison is possible. Without a baseline, there is nothing to prune against.
  2. Pruning always happens on the right side. Once the left subtree provides a value, right-side siblings may be pruned if the pruning condition fires.
  3. If no pruning conditions trigger, alpha-beta behaves exactly like minimax — you inspect all nodes. Alpha-beta is never worse than minimax. At worst, it has the same complexity.
  4. Alpha is ALWAYS at MAX nodes. Beta is ALWAYS at MIN nodes. What changes is only which one sits at the root. If the root is MIN, the root is a beta node — but the rules don't change.
  5. Initialize correctly every time: α = −∞, β = +∞. No exceptions.
  6. Check the correct formula: Alpha update → check β(parent) ≤ α(current). Beta update → check β(current) ≤ α(parent). Don't swap them.

8.18 Domain connection

Alpha-beta pruning is the backbone of every serious chess engine, from Deep Blue (which beat Kasparov in 1997) to modern engines like Stockfish. Without it, chess engines would search only a handful of ply. With optimal move ordering, alpha-beta can search roughly twice as deep as minimax in the same time — going from 5 ply to 10 ply, which is the difference between amateur and grandmaster play. The technique generalizes beyond games: any adversarial decision problem (cybersecurity attack-defense modeling, auction bidding, negotiation agents) can use alpha-beta pruning when the search space is too large for full minimax.

Alpha-beta pruning is minimax with a pruning rule: stop exploring a branch when the current node's best possible value is already worse than what the parent has available elsewhere. Same answer, fewer nodes. The core intuition: when a parent's goal contradicts a child's goal, the child's remaining work is wasted — prune it.

4. Monte Carlo Tree Search (MCTS)

8.19 Motivation

Hook. Go has a branching factor of 361. Chess has 35. In chess, you can search 10 ply with alpha-beta. In Go, you'd be lucky to search 4 ply. And in Go, there is no simple piece-counting evaluation function — material advantage is a poor predictor of who is winning. So what do you do when the tree is too big AND you can't write a good evaluation function? You simulate random games and count who wins.

In minimax and alpha-beta, we build the full game tree to a depth limit, then evaluate with a static function. For very large games like Go (branching factor ~361, typical game ~250 moves), even this is too expensive.

A naive approach — simulate every possible move, build the full tree, then apply alpha-beta — is far too slow. Chess programs evaluate about 1 million positions per second. Go with naive simulation would manage only about 25 evaluations per second.

8.20 Exploitation vs Exploration

Intuition + Analogy. MCTS balances two life philosophies:

  • Exploitation: Focus on what you know works. If a career path has been rewarding, keep investing in it. If a move has won 8 out of 10 simulations, keep playing it. This is safe, boring, and effective.
  • Exploration: Try something new. Take a course outside your major. Apply for a job you might not get. Try a move that has only been simulated twice — maybe it's secretly amazing. This is risky, but sometimes reveals hidden opportunities.

Life needs both. If you only exploit, you miss the undiscovered genius move. If you only explore, you never capitalize on what you know. MCTS uses a mathematical formula (UCB1) to balance these two forces automatically.

Where the analogy breaks: In life, exploration might lead to complete dead ends with no recovery. In MCTS, a bad simulation just updates counts — you still have all the other branches. Also, MCTS is exploring a game tree, not your career, so the stakes are lower.

8.21 When MCTS applies

MCTS is designed for combinatorial games with perfect information:

  • Two-player (sometimes multiplayer)
  • Sequential — players take turns
  • Finite set of well-defined legal moves
  • Perfect information — both players see the full board state

Examples: Chess, Go, Tic-tac-toe, Checkers, Othello.

MCTS does not work for imperfect-information games (poker, where you don't see opponent's cards) or games with continuous action spaces (physical sports).

8.22 The core insight of MCTS

Key insight. Don't build the full search tree first, then evaluate. Instead, use the results of simulations to guide which parts of the tree to grow. Let the promising paths reveal themselves through random sampling. The tree grows asymmetrically — deep where moves look promising, shallow where they don't.

As the saying goes: "Don't just randomly draw a game tree — use simulation results to guide growth."

8.23 The four phases of MCTS

MCTS repeats four steps until a time budget runs out. Each iteration grows the tree slightly and updates statistics.

8.23.1 Phase 1: Selection

Start at the root. At each level, pick the most promising child node using a formula like UCB1 (Upper Confidence Bound). Continue until you reach a node that still has unexplored children (a node whose children don't yet cover all legal moves).

Each node stores two numbers: wins / plays. These track how many times this path led to a win for the player who moved into this node, out of how many times this node was visited.

UCB1 balances exploitation (high win rate) with exploration (low visit count):

\[ \text{UCB1}(n) = \frac{w_n}{p_n} + C \sqrt{\frac{\ln P}{p_n}} \]

Where:

  • \(w_n\): wins for this node
  • \(p_n\): playouts through this node
  • \(P\): total playouts through the parent
  • \(C\): exploration constant (typically \(\sqrt{2}\))

The first term \(\frac{w_n}{p_n}\) is exploitation — pure win rate. The second term \(C \sqrt{\frac{\ln P}{p_n}}\) is exploration — it's large when few playouts have visited this node, encouraging trying under-explored moves. As a node gets more playouts, the exploration bonus shrinks.

Selection walkthrough. Tree from White's perspective:

              [root] 37/100
             /    |     \
        [A] 2/11 [B] 60/79 [C] 16/53  ← Black's turn
                  /    \
             [D] 27/35 [E] 10/18      ← White's turn

Start at root (White just moved, Black to move). Black's three options:

  • A: 2 wins / 11 plays = 18% win rate, low play count (high uncertainty)
  • B: 60/79 = 76% win rate, high play count (confident)
  • C: 16/53 = 30% win rate, medium play count

B has the best win rate — exploitation picks B. From B, pick the best child. D has 27/35 (77%) vs E's 10/18 (56%). Pick D. D has unexplored children — selection stops here.

Sense check: We exploited (picked the highest win rates) but could have explored A (only 11 playouts — maybe it's secretly better). The UCB1 formula would make this trade-off automatically.

8.23.2 Phase 2: Expansion

At the node reached by selection, if there are still unexplored legal moves, pick one and add it as a new child node. Initialize it as 0/0 — "never played, never won."

This is the exploration step. You are creating a node for a move that hasn't been tried before. It might be terrible. It might be brilliant. You won't know until you simulate from it.

In a tic-tac-toe context: if the selected board has 3 empty cells, MCTS picks one of those unexplored moves and creates a new board state for it — marked 0/0.

8.23.3 Phase 3: Simulation (Rollout)

From the newly expanded node, play the game all the way to a terminal state — until someone wins or the game ends in a draw.

The moves during simulation are not strategic. They can be:

  • Completely random, OR
  • Guided by simple lightweight heuristics (e.g., "prefer capture moves" in chess).

The purpose of simulation is NOT to play perfectly. The purpose is to estimate win/loss/draw — not to find the perfect sequence. The simulation gives a rough statistical signal: does this board tend to lead to a win, a loss, or a draw?

Think of it like polling: you don't ask every voter — you sample a few hundred randomly and the pattern emerges.

Why random play works (surprisingly). In many games, random play from a strong position leads to more wins than random play from a weak position. If you have more pieces, even random moves tend to win more often. The signal from many random simulations accumulates and reveals which positions are truly better — no evaluation function needed.

8.23.4 Phase 4: Backpropagation

Take the result of the simulation (win or loss) and send it back up through every node on the path visited in this iteration — the full selection path plus the new expansion node.

For each node on the path:

  • Increment the play count by 1.
  • If the simulation result was a win from that node's player's perspective, increment the win count by 1.

Key subtlety: A simulation ending in "Black wins" increments the win count for Black nodes but NOT for White nodes on the same path. White nodes only get their play count incremented (because White lost that simulation).

Full MCTS iteration (all four phases together).

Starting from the tree in the selection example above.

Selection: Root → B (60/79) → D (27/35). D has unexplored children.

Expansion: Create new child of D: node N, initialized 0/0.

Simulation: From N, play randomly to the end. Suppose Black wins.

Backpropagation: Update every node on the path root → B → D → N:

  • N: 0/0 → 0/1 (White's perspective: lost, so wins stay 0, plays become 1)
  • D: 27/35 → 27/36 (White node, White lost → only plays increase)
  • B: 60/79 → 61/80 (Black node, Black won → wins AND plays increase)
  • Root: 37/100 → 37/101 (White node, White lost → only plays increase)

Updated tree:

              [root] 37/101
             /    |     \
        [A] 2/11 [B] 61/80 [C] 16/53
                  /    \
             [D] 27/36 [E] 10/18
                |
              [N] 0/1

Sense check: Only B's win count increased (Black won). The root and D only got more playouts. Next iteration's selection will see slightly different UCB1 scores because the play counts changed.

8.24 After MCTS completes

When the time budget runs out, MCTS returns the move whose child node has the highest number of playouts — not necessarily the highest win rate. The most-simulated move is the one MCTS spent the most effort investigating, which is a strong signal that it's the best move.

Visual intuition. Imagine a tree where each node is a circle whose size is proportional to its play count. After many MCTS iterations, the tree looks lopsided — "fat" on the promising paths (many playouts, big circles) and "thin" on the unpromising ones (few playouts, small circles). The root's fattest child is the chosen move. This asymmetric growth is MCTS's signature: it automatically allocates more computation to the parts of the tree that matter.

AspectAlpha-BetaMCTS

Result typeDeterministicProbabilistic (statistical estimate from many rollouts)
Best forModerate branching factor, good evaluation exists (Chess)Huge branching factor, hard to evaluate (Go)
Knowledge neededGood hand-crafted evaluation functionOnly game rules (for legal moves and terminal detection)
Anytime propertyNo — must complete search to depth limitYes — can stop anytime, always has a best-move recommendation

Common pitfalls with MCTS:

  1. Confusing 0/0 with a terminal state. 0/0 means "just created, never simulated" — the game is NOT over at that node.
  2. Thinking win counts go up for all nodes on the path. Only nodes whose perspective matches the simulation winner get their win count incremented. A White node on the path gets only a play-count increment if Black won.
  3. Confusing "highest play count" with "highest win rate" for the final move. MCTS returns the move with the most playouts, not the highest win percentage. A move with 1000/2000 (50%) is preferred over one with 90/100 (90%) — more simulations = more confidence.
  4. Assuming MCTS needs a good evaluation function. It doesn't. That's the point. MCTS was invented precisely because Go has no good static evaluator. The simulations themselves provide the evaluation signal.
  5. Thinking simulations must be purely random. They can use lightweight heuristics. Modern Go programs (AlphaGo, KataGo) use neural networks for both the selection policy and the rollout policy.

8.26 Domain connection

MCTS revolutionized computer Go. Before MCTS (pre-2006), Go programs were weak amateurs. After MCTS, they reached strong amateur level. Combined with deep neural networks (AlphaGo, 2016), MCTS beat the world champion Lee Sedol 4-1 — a milestone in AI history. Beyond games, MCTS is used in chemical synthesis planning (exploring reaction pathways), theorem proving (searching proof trees), and automated algorithm configuration (finding optimal hyperparameters by treating the search as a game against an adversarial objective). Any domain with a huge branching factor and no good heuristic evaluator is a candidate for MCTS.

MCTS grows a search tree selectively: it simulates random games from promising positions, tracks win/loss statistics, and uses those statistics to decide where to search deeper. It balances exploration (trying new moves) with exploitation (focusing on what works). The four phases — Selection, Expansion, Simulation, Backpropagation — repeat until time runs out, producing an asymmetric tree that concentrates computation on the most promising lines of play.

Below is the distilled, exam-ready core of this lecture. Every entry is built from the full textbook notes above. Use this section for rapid review — but if something doesn't make sense, go back to the full explanation in the main content.

Minimax Algorithm

Must-know: Minimax guarantees you avoid the worst case, not achieve the best. It performs depth-first search (in-order traversal) alternating between MAX (picks the highest child value) and MIN (picks the lowest). The minimax value of a state is the utility MAX can guarantee assuming both sides play optimally from there.

\[ \text{MINIMAX}(s) = \begin{cases} \text{UTILITY}(s, \text{MAX}) & \text{if IS-TERMINAL}(s) \\ \max_{a} \text{MINIMAX}(\text{RESULT}(s,a)) & \text{if TO-MOVE}(s) = \text{MAX} \\ \min_{a} \text{MINIMAX}(\text{RESULT}(s,a)) & \text{if TO-MOVE}(s) = \text{MIN} \end{cases} \]

⚠️ Top pitfall: Confusing the guarantee — minimax does not maximize your best possible outcome; it minimizes your worst possible loss. Also, forgetting that in-order DFS means the leftmost path is always fully explored first.

Self-check: In a two-ply game tree where MAX picks among three MIN children with backed-up values 3, 2, and 4, what does MAX choose and why?

Connects to: Static Evaluation Functions, Alpha-Beta Pruning, Monte Carlo Tree Search

Static Evaluation Functions

Must-know: SEV = ΣU(MAX) − ΣU(MIN). The function must be fast, order-preserving, and correlated with actual winning chances. For chess, use piece-value tables (Queen=9, Rook=5, Bishop=3, Knight=3, Pawn=1). For tic-tac-toe, count win-configurations by filling empty cells with each side's pieces separately.

\[ \text{SEV} = \sum U(\text{MAX}) - \sum U(\text{MIN}) \quad\text{or weighted:}\quad \text{SEV} = \sum w_i \cdot U_i(\text{MAX}) - \sum w_j \cdot U_j(\text{MIN}) \]

⚠️ Top pitfall: Forgetting to declare who is MAX before computing. Using piece-counting for tic-tac-toe instead of win-configuration counting (pieces are never captured so counts are always similar). Confusing SEV (estimate) with final utility (win/loss/draw).

Self-check: Given a chess board where White has Queen(9)+Knight(3)=12 and Black has Rook(5)+Bishop(3)+Pawn(1)=9, what is the SEV from White's perspective?

Connects to: Minimax Algorithm, Alpha-Beta Pruning

Alpha-Beta Pruning

Must-know: Alpha-beta gives the exact same answer as minimax but inspects fewer nodes — as few as O(bd/2) in the best case. Alpha (at MAX nodes) stores the best value MAX can guarantee. Beta (at MIN nodes) stores the best value MIN can force. Prune when β(parent) ≤ α(current) on alpha-update, or β(current) ≤ α(parent) on beta-update. Core intuition: when a parent's goal contradicts a child's goal, prune the child's remaining siblings.

\[ \text{Alpha-update prune: } \beta(\text{parent}) \leq \alpha(\text{current}) \qquad \text{Beta-update prune: } \beta(\text{current}) \leq \alpha(\text{parent}) \qquad \text{Init: } \alpha = -\infty,\; \beta = +\infty \]

⚠️ Top pitfall: Thinking you can prune the left child — the first path must always be fully explored to get a baseline. Swapping the two pruning formulas. Forgetting to initialize α=−∞ and β=+∞.

Self-check: A MIN node has β=6. Its MAX child just got α=8. Do we prune the MAX child's remaining siblings? Why?

Connects to: Minimax Algorithm, Static Evaluation Functions

Monte Carlo Tree Search (MCTS)

Must-know: MCTS grows a game tree asymmetrically through four repeating phases. Selection picks the most promising child via UCB1. Expansion adds an unexplored child as 0/0. Simulation plays randomly to a terminal state. Backpropagation updates win/play counts up the path — only the winner's perspective gets a win increment. UCB1 balances exploitation (win rate) with exploration (low visit count). At the end, pick the child with the most playouts, not the highest win rate.

\[ \text{UCB1}(n) = \frac{w_n}{p_n} + C \sqrt{\frac{\ln P}{p_n}} \quad\text{where } w_n = \text{wins, } p_n = \text{playouts, } P = \text{parent playouts, } C \approx \sqrt{2} \]

⚠️ Top pitfall: Confusing 0/0 with a terminal state — it means "just created, never simulated." Incrementing win counts for all nodes on the path during backpropagation (only the winner's perspective gets wins). Returning the move with highest win rate instead of most playouts.

Self-check: After backpropagation, a White node on the path had a Black-win simulation result. What happens to its win and play counts?

Connects to: Minimax Algorithm, Alpha-Beta Pruning, Static Evaluation Functions
