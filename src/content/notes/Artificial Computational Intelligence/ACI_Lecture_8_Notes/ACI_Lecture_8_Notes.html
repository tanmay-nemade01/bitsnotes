Static Evaluation, Alpha-Beta Pruning, and Monte Carlo Tree Search

8.1 Static Evaluation Functions and Values in Game Trees

8.1.1 Definition and Explanation

Hook: Why can't a chess supercomputer simply calculate every possible sequence of moves to guarantee victory? The game tree for chess contains approximately \(10^{120}\) possible board states—vastly exceeding the total number of atoms in the observable universe (\(\approx 10^{80}\)). Evaluating every path to terminal checkmate or draw is computationally impossible.

Intuition & Analogy: Imagine a soccer referee evaluating a match at halftime. The final terminal utility (+1 win, -1 loss, 0 draw) is only awarded when the 90-minute whistle blows. However, at halftime (an intermediate, non-terminal state), a sports analyst estimates who is winning by comparing key metrics: goals scored, possession percentage, and shots on target. A static evaluation function performs this exact halftime analysis for board games—estimating who has the advantage without playing the game out to the final move.

In two-player zero-sum games, an ideal problem-solving agent would construct a complete game tree from the root state down to terminal leaf nodes, computing exact utility values using Minimax search. However, for complex real-world games, expanding the game tree to terminal nodes is computationally intractable due to exponential state explosion.

To overcome this limitation, practical game-playing agents apply a depth limit to the search tree. Instead of searching until the game ends, the agent explores only a few plies (typically 3 to 5 levels in basic engines, or up to 7–15 in grandmaster-level software) and evaluates the resulting non-terminal board configurations. A non-terminal state is any intermediate board configuration where the game is still actively in progress.

A static evaluation function is a heuristic algorithm that estimates the utility of a non-terminal game state without searching further down the tree. The numerical score produced by this function for a given board position is called the static evaluation value (SEV).

Core Properties of Static Evaluation Functions: A high-quality static evaluation function must satisfy four fundamental criteria:

  1. Max Favorability: It must assign higher numerical scores to board states that favor the Max player.
  2. Min Favorability: It must assign lower (or negative) numerical scores to board states that favor the Min player.
  3. Computational Efficiency: It must be fast to compute, as it is executed millions of times during tree search.
  4. Terminal Correlation: It must correlate strongly with the true mathematical probability of winning from that intermediate state.

The static evaluation value is not the true terminal utility of the game. Terminal utility is only awarded at the end of the game (such as \(+1\) for a win, \(-1\) for a loss, or \(0\) for a draw). Instead, the static evaluation value acts as a heuristic metric representing how promising or advantageous a given non-terminal board position is for the active player.

8.1.2 Symbol Registry

Symbol registry — Static evaluation function

  • s — non-terminal game state / board configuration — \(s\) — state in state space \(\mathcal{S}\)
  • U_max — total utility value of Max's active pieces — \(U_{\text{max}}\) — scalar (\(\mathbb{R}\))
  • U_min — total utility value of Min's active pieces — \(U_{\text{min}}\) — scalar (\(\mathbb{R}\))
  • SEV — static evaluation value of state s — \(\text{SEV}(s)\) — scalar (\(\mathbb{R}\))
  • w_i — weight coefficient assigned to feature i — \(w_i\) — scalar (\(\mathbb{R}\))
  • f_i — feature value or count of feature i — \(f_i(s)\) — scalar (\(\mathbb{R}\))

8.1.3 Mathematical Formulation

Standard Static Evaluation Formula: In a classic zero-sum game, the static evaluation value compares the total material utility of Max's remaining pieces against Min's remaining pieces:

\[ \text{SEV}(s) = \sum U_{\text{max}} - \sum U_{\text{min}} \]

Where:

  • \(\sum U_{\text{max}}\) is the sum of heuristic values for all active pieces belonging to Max.
  • \(\sum U_{\text{min}}\) is the sum of heuristic values for all active pieces belonging to Min.

When multiple board features are incorporated (such as material balance, king safety, center control, and mobility), the evaluation function is generalized as a weighted linear combination of feature metrics:

Weighted Linear Evaluation Function: \[ \text{eval}(s) = \sum_{i=1}^{k} w_i \cdot f_i(s) = w_1 f_1(s) + w_2 f_2(s) + \dots + w_k f_k(s) \]

Where:

  • \(f_i(s)\) represents numerical feature values extracted from board state \(s\) (e.g., piece count, open file count).
  • \(w_i\) represents the relative weight coefficient assigned to feature \(i\).

Interpretation of Numerical Scores:

  • \(\text{SEV}(s) > 0\): Max holds the positional/material advantage. The larger the positive score, the stronger Max's position.
  • \(\text{SEV}(s) < 0\): Min holds the positional/material advantage. The more negative the score, the stronger Min's position.
  • \(\text{SEV}(s) = 0\): The state is perfectly balanced between Max and Min.

8.1.4 Worked Examples and Computations

Example 1: Chess Board Static Evaluation

Consider a chess evaluation model where standard empirical point values are assigned to surviving pieces based on domain knowledge:

  • Queen (\(Q\)) = 9 points
  • Rook (\(R\)) = 5 points
  • Bishop (\(B\)) = 3 points
  • Knight / Horse (\(H\)) = 3 points
  • Pawn / Soldier (\(S\)) = 1 point

Let us evaluate three distinct non-terminal board configurations step-by-step:

Board Configuration 1 Walkthrough:
  • Board Setup:
  • Max (White): 1 Knight (\(H\)), 1 Bishop (\(B\)).
  • Min (Black): 1 Knight (\(H\)), 1 Pawn (\(S\)), 1 Queen (\(Q\)).
  • Step 1: Calculate Max Utility:

\[ \sum U_{\text{max}} = \text{Utility}(H) + \text{Utility}(B) = 3 + 3 = 6 \]

  • Step 2: Calculate Min Utility:

\[ \sum U_{\text{min}} = \text{Utility}(H) + \text{Utility}(S) + \text{Utility}(Q) = 3 + 1 + 9 = 13 \]

  • Step 3: Compute SEV:

\[ \text{SEV}(s_1) = \sum U_{\text{max}} - \sum U_{\text{min}} = 6 - 13 = -7 \]

  • Sense Check: The result \(-7\) indicates a severe disadvantage for Max because Min possesses an active Queen (9 points), giving Min a net 7-point lead.
Board Configuration 2 Walkthrough:
  • Board Setup:
  • Max (White): 1 Knight (\(H\)), 1 Bishop (\(B\)), 1 Pawn (\(S\)).
  • Min (Black): 1 Bishop (\(B\)), 1 Pawn (\(S\)).
  • Step 1: Calculate Max Utility:

\[ \sum U_{\text{max}} = \text{Utility}(H) + \text{Utility}(B) + \text{Utility}(S) = 3 + 3 + 1 = 7 \]

  • Step 2: Calculate Min Utility:

\[ \sum U_{\text{min}} = \text{Utility}(B) + \text{Utility}(S) = 3 + 1 = 4 \]

  • Step 3: Compute SEV:

\[ \text{SEV}(s_2) = \sum U_{\text{max}} - \sum U_{\text{min}} = 7 - 4 = +3 \]

  • Sense Check: The score \(+3\) confirms that Max has a net 3-point advantage (holding an extra Knight).
Board Configuration 3 Walkthrough:
  • Board Setup:
  • Max (White): 1 Knight (\(H\)), 1 Bishop (\(B\)), 1 Pawn (\(S\)) \(\rightarrow \sum U_{\text{max}} = 3 + 3 + 1 = 7\).
  • Min (Black): 1 Knight (\(H\)), 1 Pawn (\(S\)) \(\rightarrow \sum U_{\text{min}} = 3 + 1 = 4\).
  • Step 1: Compute SEV:

\[ \text{SEV}(s_3) = 7 - 4 = +3 \]

  • Sense Check: Max maintains a net +3 material advantage over Min.

Example 2: Tic-Tac-Toe Win Possibility Evaluation

In games where pieces are never captured (such as Tic-Tac-Toe), piece counting cannot serve as an evaluation function because piece counts are identical for both players. Instead, the evaluation function counts the number of unblocked winning lines available to each player.

Given a non-terminal Tic-Tac-Toe grid with existing 'X' and 'O' marks:

  1. Max ('X') Evaluation: Temporarily fill all empty grid cells with 'X'. Count all completed rows, columns, or diagonals containing only 'X' marks. For the demonstration board, 'X' achieves 2 open winning paths:

\[ U_{\text{max}} = 2 \]

  1. Min ('O') Evaluation: Reset the board and temporarily fill all empty grid cells with 'O'. Count all completed rows, columns, or diagonals containing only 'O' marks. For the demonstration board, 'O' achieves 1 open winning path:

\[ U_{\text{min}} = 1 \]

  1. SEV Computation:

\[ \text{SEV}(s) = U_{\text{max}} - U_{\text{min}} = 2 - 1 = +1 \]

  • Sense Check: A score of \(+1\) indicates that 'X' has more tactical opportunities to complete a winning line than 'O'.

Example 3: Two-Player N-Tile Puzzle Evaluation

In a competitive two-player tile puzzle game sharing a single grid, the static evaluation function uses the classic out-of-place tile heuristic. Each player has a designated goal configuration. The static evaluation function measures: \[ \text{SEV}(s) = \text{Out-of-place tiles}_{\text{Min}} - \text{Out-of-place tiles}_{\text{Max}} \] The player with fewer out-of-place tiles relative to their target goal receives a higher positive score.

8.1.5 Assumptions and Scope

Scope & Assumptions:

  • Zero-Sum Assumption: The evaluation assumes a strictly zero-sum environment where Max's gain is Min's loss.
  • Horizon Effect Boundary: Depth-limited evaluation suffers from the horizon effect, where an impending catastrophe (e.g., losing a Queen 2 plies beyond the search depth) is hidden behind the search boundary.
  • Static Heuristic Quality: The quality of search decisions depends entirely on the accuracy of piece weights \(w_i\). Flawed feature weights lead to poor move recommendations even with deep search.

8.1.6 Common Pitfalls

Common Pitfalls:

  • Confusing SEV with Utility: Intermediate node values are SEVs, not terminal utility values. Terminal utilities are only assigned at terminal leaf nodes.
  • Unstated Player Roles: Calculating \(\sum U_{\text{min}} - \sum U_{\text{max}}\) instead of \(\sum U_{\text{max}} - \sum U_{\text{min}}\) flips all signs, causing the algorithm to choose optimal moves for the opponent.
  • Tic-Tac-Toe Cell Fill Misunderstanding: Filling empty slots with 'X' or 'O' in Tic-Tac-Toe is a static line-counting heuristic, NOT a valid sequence of legal game moves.

8.1.7 Student Questions and Answers

Q: Can we say that when we cannot finish a game, we use static evaluation to decide who is in a better position? A: Not just when a game cannot finish, but at every non-terminal state during depth-limited search. We have multiple legal moves available; static evaluation estimates which move is most promising—meaning leading towards higher utility for Max while restricting Min.

Q: How do we decide whether X is Max or O is Max in Tic-Tac-Toe calculations? A: The problem definition must specify which symbol corresponds to Max. If it is not explicitly stated in an exam question, you must begin your answer with an explicit assumption: "Assume Max plays as X and Min plays as O." This explicit assumption fixes the subtraction order (\(U_{\text{max}} - U_{\text{min}}\)).

Q: In Tic-Tac-Toe, why do we fill all empty slots with X or O to calculate SEV? Is that valid gameplay? A: Filling empty slots with a player's symbol is a heuristic counting tool used purely to measure potential winning paths remaining open to that player. It is not a sequence of actual moves. It counts rows, columns, and diagonals where a player is not blocked by an opponent mark.

Q: Are piece evaluation values (like Queen = 9, Knight = 3) predefined in exam questions? A: Yes. In exam problems, either the static evaluation values at the leaf nodes will be given directly, or the piece weight table will be provided so you can calculate the SEV for each board configuration.

8.1.8 Industry Applications

In commercial chess engines (such as classic versions of Stockfish or Deep Blue), hand-crafted static evaluation functions evaluate hundreds of positional features including material balance, pawn structure, king safety, center control, and open files. Modern engines combine linear static evaluation functions with deep neural network evaluations (e.g., NNUE) to evaluate non-terminal positions in fractions of a millisecond during search.

8.1.9 Exam Notes

Exam note: Expect exam questions on static evaluation where you are given board configurations or game trees and asked to compute SEVs using \(\text{SEV} = \sum U_{\text{max}} - \sum U_{\text{min}}\). Always write down the explicit sum for Max, the explicit sum for Min, and show the final subtraction. If player roles (Max vs Min) are unstated, write your assumption explicitly before calculating.

8.2 Alpha-Beta Pruning Algorithm

8.2.1 Definition and Explanation

Hook: Why spend time evaluating all possible responses to a bad move when you already have a guaranteed winning alternative? If you are playing chess and discover that a candidate move allows your opponent to checkmate you in one turn, do you need to calculate all 30 other counter-moves they could make? No—you reject the move immediately.

Intuition & Analogy: Imagine shopping for a car. Dealership A offers you a car for \$10,000 (your best guaranteed option so far, \(\alpha = 10,000\)). You visit Dealership B. The salesperson at B starts showing a car and states, "The baseline price is \$12,000, and additional fees will increase it further" (\(\beta = 12,000\)). As the buyer looking to minimize cost, Dealership B's minimum price (\$12,000) is already worse than your guaranteed option from Dealership A (\$10,000). You walk out of Dealership B immediately without wasting time inspecting their other models. This is a beta cutoff.

Standard Minimax search suffers from severe computational inefficiency because it explores every single node in the game tree down to the maximum search depth. For a game tree with branching factor \(b\) and search depth \(m\), Minimax evaluates \(\mathcal{O}(b^m)\) leaf nodes, making it impractical for deep search in games like chess.

Alpha-Beta Pruning is an algorithmic optimization applied to Minimax. It maintains two dynamic scalar bounds—\(\alpha\) and \(\beta\)—during the depth-first traversal of the search tree:

  • \(\alpha\) (Alpha): Represents the highest score (best value) that the Max player is guaranteed to achieve along the current path or any previously explored path.
  • \(\beta\) (Beta): Represents the lowest score (best value) that the Min player is guaranteed to achieve along the current path or any previously explored path.

As the depth-first search traverses the tree, if the algorithm encounters a branch where the Min player can force an outcome worse than (or equal to) a score already guaranteed to Max earlier in the search, Max will never allow game play to reach that branch. Consequently, the algorithm immediately halts search along that subtree. This termination is called pruning or a cutoff.

Mathematical Correctness Guarantee: Alpha-Beta pruning produces the exact same final move decision and minimax root score as full Minimax search. It does not approximate or alter the optimal result; it merely skips evaluating nodes that are mathematically proven to have no impact on the root decision.

8.2.2 Symbol Registry

Symbol registry — Alpha-Beta Pruning

  • alpha — best guaranteed score for Max player — \(\alpha\) — scalar in \([-\infty, +\infty]\)
  • beta — best guaranteed score for Min player — \(\beta\) — scalar in \([-\infty, +\infty]\)
  • v — evaluated utility value at current node — \(v\) — scalar (\(\mathbb{R}\))
  • b — branching factor of the search tree — \(b\) — positive integer (\(\mathbb{N}^+\))
  • m — maximum search depth — \(m\) — positive integer (\(\mathbb{N}^+\))

8.2.3 Algorithmic Formulation and Pruning Rules

Initialization

At the start of search (root node):

  • Every Max node initializes its bound to negative infinity: \(\alpha = -\infty\).
  • Every Min node initializes its bound to positive infinity: \(\beta = +\infty\).

Node Update Rules

As child values \(v\) are returned during depth-first traversal:

Max Node Update Rule: A Max node updates its \(\alpha\) value whenever a child node returns a score higher than the current \(\alpha\): \[ \alpha \leftarrow \max(\alpha, v) \]

Min Node Update Rule: A Min node updates its \(\beta\) value whenever a child node returns a score lower than the current \(\beta\): \[ \beta \leftarrow \min(\beta, v) \]

Pruning Conditions (Cutoff Rules)

Beta Cutoff (Pruning at a Min Node): Pruning occurs during evaluation at a Min node (or child of Max) whenever: \[ \beta \le \alpha \]

Mathematical Rationale: At a Min node, \(\beta\) represents the upper bound on the value Min will allow. If \(\beta \le \alpha\), Min can force an outcome less than or equal to \(\beta\). But Max already has an established search path yielding a guaranteed score of \(\alpha \ge \beta\). Max will never select the ancestor move leading to this Min node. Therefore, evaluating any remaining child branches under this Min node is unnecessary and they are pruned immediately.

Alpha Cutoff (Pruning at a Max Node): Pruning occurs during evaluation at a Max node (or child of Min) whenever: \[ \alpha \ge \beta \]

Mathematical Rationale: At a Max node, \(\alpha\) represents the lower bound Max can achieve. If \(\alpha \ge \beta\), Max can force an outcome at least \(\alpha\). But Min already has an established path guaranteeing a score of \(\beta \le \alpha\). Min will never choose the move leading to this Max node. Remaining children under this Max node are pruned.

Time Complexity and Impact of Move Ordering

Time Complexity Analysis:

  • Standard Minimax Search:

\[ T(b, m) = \mathcal{O}(b^m) \]

  • Alpha-Beta Pruning (Worst Case — Worst Move Ordering):

If child moves are evaluated from worst to best, no pruning occurs: \[ T_{\text{worst}}(b, m) = \mathcal{O}(b^m) \]

  • Alpha-Beta Pruning (Best Case — Optimal Move Ordering):

If the best move is evaluated first at every node, the number of leaf evaluations reduces drastically to: \[ T_{\text{best}}(b, m) = \mathcal{O}(b^{m/2}) = \mathcal{O}\left((\sqrt{b})^m\right) \]

Practical Impact: Best-case pruning reduces the effective branching factor from \(b\) to \(\sqrt{b}\). This effectively doubles the searchable depth in the same computational timeframe.

8.2.4 Worked Examples and Derivations

Complete Step-by-Step Tree Traversal Walkthrough

Consider a 3-level game tree where Node A is the root (Max layer, depth 0), Nodes B and C are Min nodes (depth 1), and Nodes D, E, F, G are leaf nodes evaluated by a static evaluation function (depth 2).

                 A (Max, alpha=-inf, beta=+inf)
                /   \
   (Min)       B     C (Min)
              / \   / \
   (Leaves)  D   E F   G

Let leaf static evaluation values be:

  • \(v_D = 6\)
  • \(v_E = 5\)
  • \(v_F = 2\)
  • Node G is unvisited initially.
Step-by-Step Numerical Execution:
  1. Step 1: Initialize Root Node A (Max)
  • Set \(\alpha_A = -\infty\), \(\beta_A = +\infty\).
  1. Step 2: Traverse to Left Child B (Min)
  • Pass bounds down from parent A: \(\alpha_B = -\infty\), \(\beta_B = +\infty\).
  1. Step 3: Evaluate Leaf D
  • Leaf D returns static value \(v_D = 6\).
  1. Step 4: Update Min Node B
  • Since B is a Min node, update \(\beta_B\):

\[ \beta_B = \min(\beta_B, v_D) = \min(+\infty, 6) = 6 \]

  • Active bounds at B: \(\alpha_B = -\infty, \beta_B = 6\).
  • Check cutoff condition at B: Is \(\beta_B \le \alpha_B\)? \(6 \le -\infty\) is False. Continue search.
  1. Step 5: Evaluate Leaf E
  • Leaf E returns static value \(v_E = 5\).
  • Update Min Node B:

\[ \beta_B = \min(6, v_E) = \min(6, 5) = 5 \]

  • Both children of B are fully evaluated. Node B returns value \(v_B = 5\) to parent Node A.
  1. Step 6: Update Root Node A (Max)
  • Node A receives child value \(v_B = 5\).
  • Since A is a Max node, update \(\alpha_A\):

\[ \alpha_A = \max(\alpha_A, v_B) = \max(-\infty, 5) = 5 \]

  • Active bounds at A: \(\alpha_A = 5, \beta_A = +\infty\).
  1. Step 7: Traverse to Right Child C (Min)
  • Pass current bounds from A down to C: \(\alpha_C = 5\), \(\beta_C = +\infty\).
  1. Step 8: Evaluate Leaf F
  • Leaf F returns static value \(v_F = 2\).
  1. Step 9: Update Min Node C
  • Update \(\beta_C\):

\[ \beta_C = \min(\beta_C, v_F) = \min(+\infty, 2) = 2 \]

  • Active bounds at C: \(\alpha_C = 5, \beta_C = 2\).
  1. Step 10: Check Pruning Condition at Node C
  • Evaluate test: Is \(\beta_C \le \alpha_C\)?
  • Substitute active values: \(2 \le 5\) is TRUE!
  • PRUNING TRIGGERED! Immediately cut off remaining unvisited branches under Node C (prune Node G).
  • Mathematical Justification: Min at Node C can guarantee a value of at most 2 (\(\beta_C = 2\)). However, Max already has a guaranteed path through Node B yielding a score of 5 (\(\alpha_A = 5\)). Max will never select move C. Thus, evaluating Node G cannot alter the decision at root A.
  1. Final Root Return: Node A selects move B with Minimax value \(v_A = 5\).
Sense Check:

Full Minimax would evaluate all 4 leaves (D, E, F, G). Alpha-Beta evaluates only 3 leaves (D, E, F), skipping G while guaranteeing the exact same optimal choice (Move B, score 5).

8.2.5 Assumptions and Scope

Scope & Assumptions:

  • Zero-Sum Deterministic Environment: Applies to zero-sum, two-player games with full observability and deterministic transitions.
  • Depth-First Search Constraint: Requires strict depth-first left-to-right (in-order) tree traversal so that bounds propagate correctly from left subtrees to right subtrees.
  • Move Ordering Dependence: Computational efficiency ranges from \(\mathcal{O}(b^m)\) (no pruning under worst ordering) to \(\mathcal{O}(b^{m/2})\) (maximum pruning under optimal move ordering).

8.2.6 Common Pitfalls

Common Pitfalls:

  • Mistaking Pruning for Approximation: Alpha-Beta pruning is NOT an approximation. It yields the exact same root value as full Minimax.
  • Incorrect Bound Propagation: Failing to inherit parent \(\alpha\) and \(\beta\) bounds when traversing down to child nodes.
  • Flipping Cutoff Conditions: Writing \(\alpha \le \beta\) instead of \(\beta \le \alpha\) for a beta cutoff.
  • Ignoring Move Ordering: Expecting best-case performance without implementing move-ordering heuristics (such as evaluating captures or killer moves first).

8.2.7 Student Questions and Answers

Q: Does Alpha-Beta pruning guarantee that we reach the exact same decision as Minimax? A: Yes, absolutely. Alpha-Beta pruning is mathematically proven to return the exact same root decision and minimax value as full Minimax search. It only prunes branches that cannot influence the final decision.

Q: Does Alpha-Beta pruning always skip evaluating leaf nodes? A: No. If moves are ordered poorly (e.g., worst moves evaluated first), no pruning occurs, and the algorithm evaluates all \(\mathcal{O}(b^m)\) leaf nodes just like standard Minimax. Move ordering is critical to achieving the \(\mathcal{O}(b^{m/2})\) best-case complexity.

Q: How do we initialize alpha and beta values at the beginning of the search? A: Alpha (\(\alpha\)) is initialized to negative infinity (\(-\infty\)) for Max nodes, and Beta (\(\beta\)) is initialized to positive infinity (\(+\infty\)) for Min nodes at the root.

Q: In an exam, do we need to show step-by-step updates of alpha and beta for in-order traversal? A: Yes! You must explicitly state initial \(\alpha\) and \(\beta\) values at each node, show step-by-step updates as children are visited, draw a cut line across pruned branches, and write out the explicit inequality justification (e.g., "Pruned because \(\beta = 2 \le \alpha = 5\)").

8.2.8 Industry Applications

Alpha-Beta pruning forms the foundational backbone of world-class game engines for chess, checkers, and Othello. High-performance engines like Stockfish combine Alpha-Beta pruning with move-ordering heuristics (such as transposition tables, killer moves, history heuristics, and iterative deepening) to achieve effective branching factors near \(\sqrt{b}\), allowing search to depths of 20 to 30+ plies in real-time.

8.2.9 Exam Notes

Exam note: Alpha-Beta pruning is a guaranteed high-mark numerical question on the exam. Follow this 5-step execution plan:

  1. Label each depth level explicitly as Max or Min.
  2. Initialize \(\alpha = -\infty\) and \(\beta = +\infty\) at the root node.
  3. Perform strict left-to-right depth-first search.
  4. Record updated \(\alpha\) (at Max) or \(\beta\) (at Min) values after every child evaluation.
  5. Draw a clean cut line across any pruned branch and state the exact inequality: "Pruned because \(\beta \le \alpha\)" (with active numbers).

8.3 Monte Carlo Tree Search (MCTS)

8.3.1 Definition and Explanation

Hook: How did artificial intelligence master Go—a game with a branching factor of \(b \approx 250\) and more board positions than atoms in the universe, where professional human players relied on intuitive "feel" rather than computable static evaluation functions?

Intuition & Analogy: Imagine you are at a casino faced with a row of slot machines (a multi-armed bandit problem). You want to maximize your total winnings. If you spend all your money playing the one machine that paid out on your first spin, you might miss a far better machine nearby (over-exploitation). Conversely, if you try every single machine equally, you waste money on losing machines (over-exploration). Monte Carlo Tree Search (MCTS) solves this exact dilemma—balancing trying under-explored moves with focusing on moves that have proven track records of winning.

While Alpha-Beta pruning works exceptionally well for games with moderate branching factors and explicit static evaluation functions (like Chess), it degrades when applied to games with massive search spaces or games where constructing a hand-crafted static evaluation function is extremely difficult (such as Go or complex multi-agent simulations).

Monte Carlo Tree Search (MCTS) is a probabilistic heuristic search algorithm that evaluates game states by running randomized playout simulations (rollouts) down to terminal completion. Instead of requiring a domain-specific static evaluation function to score intermediate states, MCTS plays sample games out to the final outcome (win/loss/draw) and records empirical statistics.

MCTS builds an asymmetric search tree, dynamically focusing computational resources on promising branches while continuing to explore uncertain paths.

8.3.2 Symbol Registry

Symbol registry — Monte Carlo Tree Search

  • w — total number of winning simulation outcomes for a node — \(w\) — non-negative integer (\(\mathbb{N}_0\))
  • n — total number of simulation playouts passing through a node — \(n\) — non-negative integer (\(\mathbb{N}_0\))
  • ratio — win ratio / estimated node value — \(\frac{w}{n}\) — scalar in \([0, 1]\)
  • C — exploration coefficient parameter in UCB formula — \(C\) — scalar (\(\mathbb{R}^+\))
  • N_p — total visit count of the parent node — \(N_p\) — positive integer (\(\mathbb{N}^+\))

8.3.3 Algorithmic Formulation (The 4 Phases)

Monte Carlo Tree Search runs iteratively within an allocated time budget. Each iteration consists of four sequential phases executed in order:

  [1. Selection] ---> [2. Expansion] ---> [3. Simulation (Rollout)] ---> [4. Backpropagation]

Phase 1: Selection

Phase 1: Selection Starting at the root node, the algorithm navigates down the existing search tree by selecting child nodes that maximize a selection policy. The standard selection formula is the Upper Confidence Bound for Trees (UCT / UCB1):

\[ \text{UCT}(i) = \frac{w_i}{n_i} + C \sqrt{\frac{\ln N_p}{n_i}} \]

Where:

  • \(\frac{w_i}{n_i}\) is the Exploitation Term (the empirical win ratio of child node \(i\)).
  • \(C \sqrt{\frac{\ln N_p}{n_i}}\) is the Exploration Term (rewards nodes with few visits relative to parent visits \(N_p\)).
  • \(C > 0\) is the exploration constant (typically \(C = \sqrt{2}\)).

Selection continues iteratively down the tree until reaching a node that is not fully expanded (i.e., has unexplored legal child moves).

Phase 2: Expansion

Phase 2: Expansion Unless the selected node is a terminal state, the algorithm creates one or more new child nodes representing available unvisited legal actions. A newly expanded child node is initialized with zero win counts and zero playouts: \[ \frac{w}{n} = \frac{0}{0} \]

Phase 3: Simulation (Rollout)

Phase 3: Simulation (Rollout) From the newly expanded child node, a simulation playout is executed all the way to a terminal game state. Moves during rollout are chosen using a lightweight rollout policy (e.g., uniform random moves or simple heuristics). Crucially, no new tree nodes are created during simulation. Upon reaching a terminal state, the game outcome is evaluated (e.g., Win = 1, Loss = 0 from the active player's perspective).

Phase 4: Backpropagation

Phase 4: Backpropagation The simulation result is propagated backwards up the tree from the expanded child node to the root node along the path traversed in Phase 1:

  • Every node along the path increments its total visit count:

\[ n \leftarrow n + 1 \]

  • Every node where the simulation outcome was a win from that player's perspective increments its win count:

\[ w \leftarrow w + 1 \]

Termination and Final Action Selection

The 4-phase loop repeats continuously until the allocated search time expires. Upon timeout, MCTS selects the final action corresponding to the root child node with the highest total visit count (\(n\)) (or highest win ratio \(\frac{w}{n}\)).

8.3.4 Worked Examples and Walkthrough

Detailed MCTS Node Update Walkthrough

Consider a search node represented as \(\frac{w}{n}\):

  • Current active state at node: \(\frac{37}{79}\) (37 wins out of 79 playouts from White/Max's perspective).
  • Parent node state: \(\frac{60}{100}\) (60 wins out of 100 playouts).
Step-by-Step Execution of One MCTS Iteration:
  1. Step 1: Selection

Node \(\frac{37}{79}\) is selected during tree navigation because it yields the highest UCT score among its siblings.

  1. Step 2: Expansion

A new child node representing a candidate legal action is attached under \(\frac{37}{79}\). The new child is initialized to: \[ \text{Child State} = \frac{0}{0} \]

  1. Step 3: Simulation (Rollout)

A randomized simulation is launched from \(\frac{0}{0}\) down to a terminal game state. Let us analyze both possible simulation outcomes:

  • Case A (White Wins): The simulation returns Win (+1).
  • Expanded child updates to: \(\frac{1}{1}\).
  • Node \(\frac{37}{79}\) updates: \(n = 79 + 1 = 80\), \(w = 37 + 1 = 38 \rightarrow \mathbf{\frac{38}{80}}\).
  • Parent node \(\frac{60}{100}\) updates: \(n = 100 + 1 = 101\), \(w = 60 + 1 = 61 \rightarrow \mathbf{\frac{61}{101}}\).
  • Case B (Black Wins / White Loses): The simulation returns Loss (0 for White).
  • Expanded child updates to: \(\frac{0}{1}\).
  • Node \(\frac{37}{79}\) updates: \(n = 79 + 1 = 80\), win count unchanged: \(w = 37 \rightarrow \mathbf{\frac{37}{80}}\).
  • Parent node \(\frac{60}{100}\) updates: \(n = 100 + 1 = 101\), win count unchanged: \(w = 60 \rightarrow \mathbf{\frac{60}{101}}\).
Sense Check:

Visit counts (\(n\)) increment unconditionally for every ancestor node along the backpropagation path, while win counts (\(w\)) increment only when the simulation aligns with that node player's victory.

8.3.5 Assumptions and Scope

Scope & Assumptions:

  • Domain Independence: MCTS requires only game rules and terminal state evaluation; it does NOT require hand-crafted heuristic evaluation functions.
  • Asymmetric Tree Growth: MCTS grows the search tree asymmetrically, spending computation on promising subtrees rather than exploring uniformly.
  • Anytime Property: MCTS can be halted at any arbitrary millisecond, returning the current best move based on accumulated playouts.

8.3.6 Common Pitfalls

Common Pitfalls:

  • Expecting Sibling Sum Equality: Playout counts across sibling nodes do NOT need to sum up to the parent node total. Trees expand asymmetrically and some playouts occur before expansion.
  • Confusing Final Move Selection: At termination, MCTS selects the move with the highest visit count (\(n\)), NOT the node with the highest UCT score. UCT is used for in-tree selection, while visit count reflects robust search convergence.
  • Confounding Win Perspectives: Forgetting that win counts (\(w\)) must reflect victories relative to the player whose turn it is at that specific node level.

8.3.7 Student Questions and Answers

Q: What does the notation 0/0 signify in an MCTS diagram? A: The notation \(0/0\) denotes a newly expanded node during the expansion phase that has just been added to the search tree, prior to running its first simulation rollout (0 wins out of 0 playouts).

Q: Do total playout numbers across sibling nodes add up to the parent's playout count? A: Not necessarily. Because MCTS builds an asymmetric search tree through random rollouts and time-bounded iterations, numbers across sibling branches do not need to sum up to 1.0 or equal the exact parent count.

Q: How does MCTS decide which final move to play when the time limit expires? A: When the time limit elapses, MCTS returns the action leading to the child node with the highest visit count (\(n\)). High visit counts indicate that the UCT selection policy repeatedly selected this move as the most promising.

Q: Will we be required to calculate full numerical MCTS trees in the mid-semester exam? A: No full-fledged MCTS tree calculations will be required in the exam. You are expected to define the four core phases (Selection, Expansion, Simulation, Backpropagation), state the UCT formula, and explain how node values (\(w/n\)) update during backpropagation.

Alpha-Beta Pruning Algorithm

Must-know: Alpha-Beta pruning guarantees exact minimax decisions while reducing best-case time complexity from O(b^m) to O(b^(m/2)). Pruning occurs when beta <= alpha at a Min node or alpha>= beta at a Max node.

\[ \text{Pruning condition: } \beta \le \alpha \quad (\text{at Min}), \quad \alpha \ge \beta \quad (\text{at Max}) \]

⚠️ Top pitfall: Confusing alpha-beta pruning as an approximation, or failing to pass parent alpha/beta bounds down during tree traversal.
