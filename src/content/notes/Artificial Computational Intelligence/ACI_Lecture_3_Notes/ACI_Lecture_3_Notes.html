3.1.2 Recap of Intelligent Agents and Environments

An intelligent agent is an entity that perceives its environment through sensors and acts upon that environment using actuators. The agent function maps any given percept sequence to an action:

\[ f: \mathcal{P}^* \to \mathcal{A} \]

where \(\mathcal{P}^*\) is the set of all possible percept sequences and \(\mathcal{A}\) is the set of actions.

Agent behavior is formally evaluated through the PEAS framework:

  • Performance Measure (\(P\)): Scalar metric defining environmental success (e.g., cleanliness score, energy efficiency, safe arrival time).
  • Environment (\(E\)): External system context containing objects, constraints, and dynamic processes.
  • Actuators (\(A\)): Mechanisms executing actions (e.g., electric motors, steering columns, display screens).
  • Sensory Inputs (\(S\)): Transducers capturing environmental percepts (e.g., LiDAR sensors, cameras, infrared bumpers).

Environments dictate agent complexity along six fundamental axes:

  • Fully Observable vs. Partially Observable: Whether sensors capture complete environmental state at every instant.
  • Deterministic vs. Stochastic: Whether the next state \(s'\) is uniquely determined by current state \(s\) and action \(a\).
  • Episodic vs. Sequential: Whether current actions affect future decisions.
  • Static vs. Dynamic vs. Semi-Dynamic: Whether the environment changes while the agent deliberates.
  • Discrete vs. Continuous: Whether states, time steps, and actions belong to countable, distinct sets.
  • Single-Agent vs. Multi-Agent: Whether other entities operate as agents maximizing independent utility.

Agent Architectural Taxonomy:

  • Simple Reflex Agents: Action driven strictly by current percept via condition-action rules: \(s \to a\).
  • Model-Based Reflex Agents: Maintain internal state \(s_t = \text{UpdateState}(s_{t-1}, a_{t-1}, o_t)\) to operate under partial observability.
  • Goal-Based Agents: Incorporate explicit target states to evaluate action choices.
  • Utility-Based Agents: Use scalar utility functions \(U(s)\) to resolve competing goals and trade-offs under uncertainty.
  • Learning Agents: Separate learning element, performance element, critic, and problem generator to adapt over time.

3.1.3 The Five Components of Problem Formulation

Hook: How does an autonomous navigation system or chess-playing agent convert an infinitely complex physical world into a structured mathematical problem that a algorithm can solve? It abstracts the environment into a state graph.

Problem Formulation is the formal process of abstracting a real-world environment into a state-space graph defined by a 5-tuple \(\langle s_0, A(s), Result(s, a), GoalTest(s), c(s, a, s') \rangle\):

  1. Initial State (\(s_0\)): The starting state configuration of the agent, \(s_0 \in S\).
  2. Actions (\(A(s)\)): The set of legal moves available to the agent when residing in state \(s\).
  3. Transition Model (\(Result(s, a)\)): A function mapping state \(s\) and action \(a \in A(s)\) to a successor state \(s'\): \[ Result: S \times A \to S \]
  4. Goal Test (\(GoalTest(s)\)): A boolean function evaluating whether state \(s\) satisfies the goal criteria: \[ GoalTest: S \to \{\text{True}, \text{False}\} \]
  5. Path Cost (\(g(n)\)): A function assigning a non-negative real cost to a path of actions, defined recursively via step costs \(c(s, a, s') \ge 0\): \[ g(n) = \sum_{i=1}^{k} c(s_{i-1}, a_i, s_i) \]

Worked Example: Formulating the 8-Puzzle

Consider the classic 8-puzzle sliding tile game played on a \(3 \times 3\) grid.

  • State Space (\(S\)): Configuration of 8 numbered tiles (\(1..8\)) and 1 blank space (\(\square\)) on a \(3 \times 3\) grid. Total state space size is \(\frac{9!}{2} = 181,440\) reachable configurations.
  • Initial State (\(s_0\)): Any given valid grid configuration, e.g.: \[ \begin{bmatrix} 1 & 2 & 3 \\ 4 & \square & 6 \\ 7 & 5 & 8 \end{bmatrix} \]
  • Actions (\(A(s)\)): Defined as moving the blank space \(\square\): \(\{\text{Left}, \text{Right}, \text{Up}, \text{Down}\}\) (subject to grid boundary constraints).
  • Transition Model (\(Result(s, a)\)): Swaps the blank tile with the adjacent tile in direction \(a\). For \(a = \text{Right}\): \[ Result\left(\begin{bmatrix} 1 & 2 & 3 \\ 4 & \square & 6 \\ 7 & 5 & 8 \end{bmatrix}, \text{Right}\right) = \begin{bmatrix} 1 & 2 & 3 \\ 4 & 6 & \square \\ 7 & 5 & 8 \end{bmatrix} \]
  • Goal Test (\(GoalTest(s)\)): Checks if tiles match target sequence: \[ s_{\text{goal}} = \begin{bmatrix} 1 & 2 & 3 \\ 4 & 5 & 6 \\ 7 & 8 & \square \end{bmatrix} \]
  • Path Cost (\(g(n)\)): Number of tile moves executed. Each move step cost \(c(s, a, s') = 1\).

Sense Check: Path cost increases monotonically by 1 per step, making cost equal to path depth \(d\).

Assumptions & Scope (Abstraction Level): Problem formulation requires choosing the right level of abstraction. Including real-world physical details (e.g., exact finger pressure, tile friction, microsecond timing) creates an unsearchably large state space. An abstraction is valid if every abstract state path corresponds to a executable physical action path.

Common Pitfall: Confusing the physical world state with the search node representation. A search node contains parent pointers, depth \(d\), and path cost \(g(n)\), whereas an environment state captures only physical configuration.

Recap & Bridge: Problem formulation establishes the graph structure over which search algorithms operate. With states, actions, transition models, and path costs specified, uninformed search algorithms can systematically explore this graph without domain knowledge.

Real-World & Domain Connection: In automated robotics and vehicle route planning (e.g., GPS navigation), problem formulation defines intersections as states, roads as action transitions, turn delays/road lengths as step costs \(c(s, a, s')\), and destination matching as the goal test.

3.1.4 Symbol Registry — Problem Formulation Components

  • \(s_0\) — initial state configuration — state object \(\in S\)
  • \(A(s)\) — set of legal actions available in state \(s\) — set of action symbols
  • \(Result(s, a)\) — transition model returning successor state \(s'\) — function mapping \(S \times A \to S\)
  • \(GoalTest(s)\) — boolean function checking if state \(s\) is a goal — function mapping \(S \to \{\text{True}, \text{False}\}\)
  • \(g(n)\) — cumulative path cost from initial state \(s_0\) to node \(n\) — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(c(s, a, s')\) — step cost of executing action \(a\) from state \(s\) to state \(s'\) — scalar \(\in \mathbb{R}_{\ge 0}\)

3.2 Uninformed (Blind) Search Algorithms

3.2.1 Overview of Uninformed Search

Uninformed Search (also called blind search) algorithms generate search trees using only the state transitions, actions, and cost parameters specified in the problem formulation. They possess no problem-specific domain heuristics to evaluate how close an unexpanded node is to the goal.

Uninformed algorithms systematically traverse the state graph. They evaluate nodes strictly based on graph structure or accumulated path cost \(g(n)\).

3.2.2 Breadth-First Search (BFS)

Breadth-First Search (BFS) expands the shallowest unexpanded node in the search tree first. All nodes at depth level \(l\) are expanded before any nodes at depth level \(l+1\).

Frontier Data Structure: First-In, First-Out (FIFO) Queue.

1. Algorithm Specification (Procedural Spine)

  • Inputs: Graph / tree formulation with initial state \(s_0\), transition model \(Result(s, a)\), goal test function \(GoalTest(s)\).
  • Outputs: Solution path or failure signal.
  • Steps:
    1. Initialize Frontier as a FIFO queue containing root node \(s_0\). Initialize Explored set as empty.
    2. If Frontier is empty, return failure.
    3. Pop node \(n\) from front of Frontier.
    4. If \(GoalTest(n.\text{State})\) is true, return solution path leading to \(n\).
    5. Add \(n.\text{State}\) to Explored.
    6. For each action \(a \in A(n.\text{State})\):
      • Generate child node \(s' = Result(n.\text{State}, a)\).
      • If \(s'\) is not in Explored or Frontier, add \(s'\) to back of Frontier.

2. Trace & Execution Walkthrough

Consider a binary tree where initial node A has children B and C; node B has children D and E; node C has children F and G.

  1. Frontier = [A], Explored = {}
  2. Pop A. \(GoalTest(\text{A}) = \text{False}\). Explored = {A}. Generate B, C. Frontier = [B, C]
  3. Pop B. \(GoalTest(\text{B}) = \text{False}\). Explored = {A, B}. Generate D, E. Frontier = [C, D, E]
  4. Pop C. \(GoalTest(\text{C}) = \text{False}\). Explored = {A, B, C}. Generate F, G. Frontier = [D, E, F, G]
  5. Pop D, E, F... until goal is reached at depth level 2.

Complexity & Memory Pitfall:

  • Time Complexity: \(O(b^d)\), where \(b\) is the branching factor and \(d\) is the depth of the shallowest goal.
  • Space Complexity: \(O(b^d)\). Every generated node must remain stored in memory (in Frontier or Explored).
  • Memory Trap: If \(b = 10\) and an algorithm generates \(10^6\) nodes/sec (100 bytes/node), at depth \(d=12\), BFS requires over 1 Terabyte of RAM. Memory consumption, rather than execution time, is the primary failure mode of BFS.

3.2.3 Depth-First Search (DFS)

Depth-First Search (DFS) expands the deepest unexpanded node in the current search tree frontier first. It traverses down a single branch to maximum depth before backtracking.

Frontier Data Structure: Last-In, First-Out (LIFO) Stack.

Worked Example: Social Network Connectivity Check

Worked Example 1: Verifying Connection between Sunanda and Mukesh

Consider a social network graph used to verify whether person Sunanda is connected to person Mukesh through a chain of mutual friends.

  • Initial State: Node Sunanda.
  • Goal State: Node Mukesh.
  • Graph Connections:
    • Sunanda \(\to\) {Harish, Dave}
    • Harish \(\to\) {No unvisited friends} (leaf node)
    • Dave \(\to\) {Janita}
    • Janita \(\to\) {Mukesh}

Step-by-Step Stack Trace:

  1. Initialize: Push Sunanda to Stack. Stack = [Sunanda].
  2. Pop Sunanda: Unvisited neighbors are Harish and Dave. Push Dave, then push Harish. Stack = [Dave, Harish].
  3. Pop Harish: Harish has no unvisited connections. Reaches dead end (leaf node). Backtrack.
  4. Pop Dave: Expand Dave. Unvisited neighbor is Janita. Push Janita. Stack = [Janita].
  5. Pop Janita: Expand Janita. Unvisited neighbor is Mukesh. Push Mukesh. Stack = [Mukesh].
  6. Pop Mukesh: Goal test \(GoalTest(\text{Mukesh}) = \text{True}\).

Path returned: Sunanda \(\to\) Dave \(\to\) Janita \(\to\) Mukesh.

Sense Check: DFS reached the target goal by diving deep down Dave's branch after hitting a dead end on Harish's branch.

Assumptions & Scope (Infinite Loops in Graph Search): In tree search without duplicate state tracking, DFS can enter an infinite loop if cyclic paths exist (e.g., A \(\to\) B \(\to\) A). Graph search DFS must maintain an Explored set or depth limits to guarantee termination.

  • Space Complexity: \(O(b \cdot m)\), where \(m\) is the maximum depth. DFS requires storing only a single path from root to leaf plus unexpanded siblings.
  • Optimality: Non-optimal. DFS may find a goal at depth 100 on an early branch before inspecting a goal at depth 1 on a later branch.

3.2.4 Uniform Cost Search (UCS)

Uniform Cost Search (UCS) (Dijkstra's algorithm on trees) expands the unexpanded node \(n\) with the lowest cumulative path cost \(g(n)\) from the start node:

\[ g(n) = g(p) + c(p, a, n) \]

where \(g(p)\) is the path cost of parent node \(p\) and \(c(p, a, n)\) is the step cost of action \(a\) transitioning from \(p\) to \(n\).

Frontier Data Structure: Priority Queue sorted in ascending order of \(g(n)\).

Q: Why is the goal test in Uniform Cost Search applied strictly when a node is selected for EXPANSION (popped from the priority queue), rather than when it is first GENERATED?

A: Generating a goal node confirms that a path to the goal has been discovered, but does NOT guarantee it is the cheapest possible path. A cheaper path may still reside unexpanded in the priority queue. Applying the goal test at expansion guarantees that no unexpanded path in the priority queue has a lower cumulative cost than the popped node.

Worked Computation Walkthrough: Sibiu to Bucharest Route

Worked Example 2: Uniform Cost Search (Sibiu to Bucharest)

Find the minimum-cost path from initial node Sibiu to goal node Bucharest using edge costs:

  • Sibiu \(\to\) Rimnicu Vilcea: 80
  • Sibiu \(\to\) Fagaras: 99
  • Rimnicu Vilcea \(\to\) Pitesti: 97
  • Fagaras \(\to\) Bucharest: 211
  • Pitesti \(\to\) Bucharest: 101

Step-by-Step Priority Queue Trace:

  1. Initial State:
    • Pop: Sibiu (\(g=0\)).
    • Successors generated:
      • Rimnicu Vilcea: \(g = 0 + 80 = 80\)
      • Fagaras: \(g = 0 + 99 = 99\)
    • Frontier = [(Rimnicu Vilcea, g=80), (Fagaras, g=99)]
  2. Step 1:
    • Pop lowest cost node: Rimnicu Vilcea (\(g=80\)).
    • Successors generated:
      • Pitesti: \(g = 80 + 97 = 177\)
    • Frontier = [(Fagaras, g=99), (Pitesti, g=177)]
  3. Step 2:
    • Pop lowest cost node: Fagaras (\(g=99\)).
    • Successors generated:
      • Bucharest: \(g = 99 + 211 = 310\)
    • Frontier = [(Pitesti, g=177), (Bucharest [via Fagaras], g=310)]
    • Crucial Check: Goal node Bucharest is generated with cost 310, but search does not stop!
  4. Step 3:
    • Pop lowest cost node: Pitesti (\(g=177\)).
    • Successors generated:
      • Bucharest: \(g = 177 + 101 = 278\)
    • Update Frontier with lower cost path to Bucharest: [(Bucharest [via Pitesti], g=278)]
  5. Step 4:
    • Pop lowest cost node: Bucharest (\(g=278\)).
    • Goal test succeeds!

Final Output Path: Sibiu \(\to\) Rimnicu Vilcea \(\to\) Pitesti \(\to\) Bucharest. Total Path Cost \(g = 278\).

Sense Check: Testing at generation would have returned the sub-optimal path via Fagaras (cost 310). Goal test at expansion guaranteed finding the optimal path (cost 278).

3.2.5 Symbol Registry — Priority Queue Uniform Cost Search

  • \(g(n)\) — total cumulative path cost from start to node \(n\) — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(c(u, v)\) — edge step cost between node \(u\) and node \(v\) — scalar \(\in \mathbb{R}_{> 0}\)
  • \(S\) — set of explored nodes — set of state objects
  • \(Q\) — priority queue of frontier nodes sorted by ascending \(g(n)\) — min-heap data structure

3.2.6 Iterative Deepening Search (IDS) and Comparison

Iterative Deepening Search (IDS) combines the space efficiency of DFS with the completeness of BFS by repeatedly running Depth-Limited Search (DLS) with an increasing depth limit \(L = 0, 1, 2, \dots, d\).

Algorithm Comparison Matrix

Strategy Frontier Data Structure Complete? Optimal? Time Complexity Space Complexity
BFS FIFO Queue Yes (if \(b\) finite) Yes (if step cost = 1) \(O(b^d)\) \(O(b^d)\)
DFS LIFO Stack No (infinite spaces) No \(O(b^m)\) \(O(b \cdot m)\)
UCS Priority Queue (by \(g(n)\)) Yes (if cost \(\ge \epsilon > 0\)) Yes \(O(b^{1 + \lfloor C^* / \epsilon \rfloor})\) \(O(b^{1 + \lfloor C^* / \epsilon \rfloor})\)
IDS LIFO Stack (Iterative) Yes (if \(b\) finite) Yes (if step cost = 1) \(O(b^d)\) \(O(b \cdot d)\)

Recap & Bridge: While BFS, DFS, UCS, and IDS provide complete search mechanisms without domain knowledge, their exponential time and space requirements make them unfeasible for massive state spaces. Informed search algorithms solve this by utilizing heuristic functions \(h(n)\).

Real-World Connection: UCS forms the basis for Dijkstra's routing protocol in network routers, calculating lowest-latency packet delivery paths across global internet backbones.

3.3 Informed (Heuristic) Search Framework

3.3.1 Motivation for Informed Search

Hook: Uninformed search algorithms explore every direction equally—like a person searching for a missing key in a dark house by feeling every wall. How can an agent use domain knowledge to head straight toward the key? By using a heuristic.

Informed (Heuristic) Search algorithms utilize domain-specific knowledge to evaluate node quality. Rather than exploring blindly, they estimate the remaining cost to reach the goal using a heuristic function \(h(n)\), drastically pruning the search space.

3.3.2 The Heuristic Function h(n)

A heuristic function \(h(n)\) takes a search node \(n\) (or state \(s\)) and returns an estimated cost of the cheapest path from \(n\) to a goal state:

\[ h: S \to \mathbb{R}_{\ge 0} \]

Boundary Condition:

\[ h(n) \ge 0 \quad \text{for all } n, \quad \text{with } h(\text{goal}) = 0 \]

The heuristic value at any goal state must evaluate to exactly zero.

Professor's City Guide Analogy

Analogy — City Tour Guide: Think of a heuristic function like a seasoned local tour guide giving travel time estimates. When navigating through an unfamiliar city during peak hours, a guide provides estimates based on experience (e.g., estimating 20 minutes to reach the monument via side streets rather than 45 minutes via the main avenue).

While the guide's estimate might not match the exact physical travel time to the minute (due to unforeseen traffic lights or road work), it provides an effective guiding light. It drastically improves decision-making speed compared to driving down every road blindly.

Symbol Registry — Heuristic Function

  • \(h(n)\) — estimated cost from state at node \(n\) to target goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(h^*(n)\) — true actual cost of optimal path from node \(n\) to goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(n\) — state / search node object — state \(\in S\)
  • \(\text{goal}\) — target goal state — state \(\in S_{\text{goal}}\)

3.3.3 Comparison of Uninformed vs. Informed Search

Dimension Uninformed (Blind) Search Informed (Heuristic) Search
Information Domain Problem formulation only (\(s_0, A(s), Result, GoalTest, g(n)\)) Problem formulation + Domain heuristic function \(h(n)\)
Exploration Strategy Systematic traversal based on tree topology or path cost \(g(n)\) Selective exploration toward goal guided by estimated cost \(h(n)\)
Memory / Time Cost High exponential growth (\(O(b^d)\) or \(O(b^m)\)) Substantially reduced through domain pruning
Primary Examples Breadth-First Search (BFS), Depth-First Search (DFS), UCS, IDS Greedy Best-First Search (GBFS), A* Search

Assumptions & Scope of Heuristics: Heuristics must be computationally cheap to calculate. If computing \(h(n)\) takes longer than searching the state space blindly, the heuristic fails its purpose. A good heuristic relaxes constraints of the original problem (e.g., straight-line distance ignoring road obstacles, or Manhattan distance allowing tiles to overlap).

Common Pitfall: Confusing path cost so far \(g(n)\) with estimated cost to goal \(h(n)\). \(g(n)\) looks backward to the start node; \(h(n)\) looks forward to the goal node.

Recap & Bridge: Heuristic functions provide the mathematical foundation for informed search. Depending on how \(h(n)\) is combined with accumulated path cost \(g(n)\), we get Greedy Best-First Search (\(f(n) = h(n)\)) or A* Search (\(f(n) = g(n) + h(n)\)).

Real-World Connection: GPS navigation applications (Google Maps, Waze) use straight-line distance (Euclidean distance) or historical traffic speed profiles as heuristics to route vehicles efficiently across millions of road segments.

3.4 Greedy Best-First Search (GBFS)

3.4.1 Mathematical Formulation of GBFS

Greedy Best-First Search (GBFS) expands the node in the search frontier that is estimated to be closest to the goal. It evaluates nodes using strictly the heuristic estimate function:

\[ f(n) = h(n) \]

Frontier Data Structure: Priority Queue sorted in ascending order of \(h(n)\).

Evaluation Rationale: GBFS is called "greedy" because at every step it selects the node that looks best right now based on \(h(n)\). It completely ignores the path cost accumulated so far, \(g(n)\).

3.4.2 Symbol Registry — Greedy Best-First Search

  • \(f(n)\) — evaluation function score governing expansion priority — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(h(n)\) — heuristic estimated cost from node \(n\) to target goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(g(n)\) — cumulative path cost from start to node \(n\) (ignored by GBFS) — scalar \(\in \mathbb{R}_{\ge 0}\)

3.4.3 Worked Example 1: Romania Route Finding

  • Sibiu \(\to\) Fagaras: 99, Sibiu \(\to\) Rimnicu Vilcea: 80, Sibiu \(\to\) Oradea: 151
  • Fagaras \(\to\) Bucharest: 211
  • Rimnicu Vilcea \(\to\) Pitesti: 97, Pitesti \(\to\) Bucharest: 101

  1. Initial State: Start at Arad (\(f = h = 366\)).
    • Pop Arad. Successors generated:
      • Zerind: \(h = 374\)
      • Timisoara: \(h = 329\)
      • Sibiu: \(h = 253\)
    • Frontier = [(Sibiu, h=253), (Timisoara, h=329), (Zerind, h=374)]
  2. Step 1:
    • Pop lowest \(h\) node: Sibiu (\(h=253\)). Successors generated:
      • Arad: \(h = 366\)
      • Oradea: \(h = 380\)
      • Rimnicu Vilcea: \(h = 193\)
      • Fagaras: \(h = 176\)
    • Frontier = [(Fagaras, h=176), (Rimnicu Vilcea, h=193), (Timisoara, h=329), ...]

    • Pop lowest \(h\) node: Fagaras (\(h=176\)). Successors generated:
      • Sibiu: \(h = 253\)
      • Bucharest: \(h = 0\)

GBFS picked Fagaras over Rimnicu Vilcea because \(h(\text{Fagaras}) = 176\) appeared smaller than \(h(\text{Rimnicu}) = 193\), blind to accumulated path costs.

Worked Example 2: GBFS Execution on a 5-Node Graph

Consider a 5-node graph where Node 1 is the start state and Node 5 is the target goal state.

Heuristic Table \(h(n)\):
Node 1: 60, Node 2: 120, Node 3: 30, Node 4: 40, Node 5: 0 (Goal)

Edge Step Costs \(c(u, v)\):

  • (2, 5) = 125, (3, 5) = 125, (4, 5) = 50

    • Successors generated:
      • Node 2: \(h = 120\)
      • Node 3: \(h = 30\)
      • Node 4: \(h = 40\)
    • Frontier = [(Node 3, h=30), (Node 4, h=40), (Node 2, h=120)]
  2. Step 1: Pop lowest \(h\) node: Node 3 (\(h=30\)).
    • Successors generated:
      • Node 5: \(h = 0\)

3.4.5 Student Q&A and Non-Optimality of GBFS

Q: Why is the initial node's heuristic value \(h(1)=60\) ignored during the first decision step in Worked Example 2?

A: The start node's heuristic value \(h(1)\) simply measures the initial distance estimate of the starting state. Once Node 1 is popped and expanded, we evaluate its generated children (Nodes 2, 3, and 4) using their heuristic scores to determine which frontier branch to explore next.

Q: Is Greedy Best-First Search guaranteed to find an optimal solution?

A: No. GBFS is non-optimal. Because it relies exclusively on \(h(n)\), it can be deceived by misleading heuristic estimates that look locally attractive but lead to expensive global paths.

Common Pitfall: Treating GBFS as complete or optimal. On graphs with loops and without duplicate checking, GBFS can get stuck in infinite loops. Time and space complexity are \(O(b^m)\) in the worst case.

Recap & Bridge: GBFS is fast and memory-efficient when the heuristic is accurate, but its failure to track accumulated path cost \(g(n)\) sacrifices optimality. Combining \(g(n)\) and \(h(n)\) yields the optimal A* search algorithm.

Real-World Connection: GBFS principles are used in fast greedy route generators where rapid initial path discovery is prioritized over absolute cost minimization (e.g., initial draft routing in real-time gaming AI).

3.5 A* Search Algorithm

3.5.1 Mathematical Formulation of A*

A* Search is an informed search algorithm that evaluates nodes by combining the path cost incurred so far, \(g(n)\), and the estimated heuristic cost to the goal, \(h(n)\):

\[ f(n) = g(n) + h(n) \]

Frontier Data Structure: Priority Queue sorted in ascending order of \(f(n)\).

Core Intuition:

  • \(g(n)\): Cost incurred to reach node \(n\) from the start state (backward cost).
  • \(h(n)\): Estimated cost from node \(n\) to the nearest goal state (forward cost).
  • \(f(n)\): Total estimated cost of a path passing through node \(n\) to the goal.

A* avoids expanding paths that are already expensive (\(g(n)\) high) even if their remaining estimated heuristic distance (\(h(n)\)) appears small.

3.5.2 Symbol Registry — A* Search

  • \(f(n)\) — total estimated cost of optimal path through node \(n\) — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(g(n)\) — actual accumulated path cost from start to node \(n\) — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(h(n)\) — heuristic estimated cost from node \(n\) to goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(c(u, v)\) — step cost of action transitioning from node \(u\) to node \(v\) — scalar \(\in \mathbb{R}_{> 0}\)

Worked Example 1: A* Execution on 5-Node Graph

Find the optimal path from Node 1 (Start) to Node 5 (Goal) using A* Search (\(f(n) = g(n) + h(n)\)).

Graph Edge Step Costs \(c(u, v)\):

  • \(c(1,2) = 70\), \(c(1,3) = 125\), \(c(1,4) = 100\)
  • \(c(4,5) = 50\), \(c(2,5) = 125\), \(c(3,5) = 70\)

Heuristic Values \(h(n)\):
\(h(1) = 60\), \(h(2) = 120\), \(h(3) = 70\), \(h(4) = 40\), \(h(5) = 0\) (Goal)

Step-by-Step Priority Queue Trace:

  1. Initial State:
    • Pop Node 1 (\(g=0, h=60 \implies f=60\)).
    • Successors generated:
      • Node 2: \(g = 70, h = 120 \implies f = 70 + 120 = 190\)
      • Node 3: \(g = 125, h = 70 \implies f = 125 + 70 = 195\)
      • Node 4: \(g = 100, h = 40 \implies f = 100 + 40 = 140\)
    • Frontier = [(Node 4, f=140), (Node 2, f=190), (Node 3, f=195)]
  2. Step 1:
    • Pop lowest \(f\) node: Node 4 (\(f=140\)).

      • Node 5: \(g = 100 + 50 = 150, h = 0 \implies f = 150 + 0 = 150\)
    • Frontier = [(Node 5, f=150), (Node 2, f=190), (Node 3, f=195)]
  3. Step 2:
    • Pop lowest \(f\) node: Node 5 (\(f=150\)).
    • Goal test succeeds!

3.5.5 Student Q&A and Pitfalls in A* Execution

Warning — Frontier Expansion Order (Global Priority Queue): Students frequently commit the error of continuing down the local branch during manual graph tracing. At Step 3, after expanding Rimnicu Vilcea, Pitesti was added with \(f=417\). However, Fagaras already resided in the priority queue with \(f=415\). A* must pop Fagaras next because it maintains a single global priority queue across all active leaf nodes in the search tree.

Q: Why does A* switch from Pitesti to Fagaras at Step 3 during the Romania route search?

A: A* maintains a priority queue of ALL unexplored frontier leaf nodes across the entire search tree. Comparing all active leaf nodes reveals \(f(\text{Fagaras}) = 415\) is strictly smaller than \(f(\text{Pitesti}) = 417\). Expanding Fagaras first ensures that no cheaper path was hiding under Fagaras before committing to Pitesti.

Q: How was the final evaluation score of 150 calculated for Node 5 in Worked Example 1?

A: The total evaluation score is computed via \(f(5) = g(5) + h(5)\). The actual accumulated path cost to reach Node 5 along path 1 \(\to\) 4 \(\to\) 5 is \(g(5) = c(1,4) + c(4,5) = 100 + 50 = 150\). Since Node 5 is the goal state, its heuristic estimate is \(h(5) = 0\), giving \(f(5) = 150 + 0 = 150\).

Recap & Bridge: A* combines path cost tracking \(g(n)\) and goal distance estimation \(h(n)\) into a mathematically sound search strategy. Provided \(h(n)\) satisfies admissibility and consistency, A* guarantees finding the optimal path.

Real-World Connection: A* pathfinding forms the core engine for path calculation in video game AI (moving units across grid maps), robot arm motion planning, and autonomous vehicle navigation.

3.6 Heuristic Quality: Admissibility and Consistency

3.6.1 Admissibility Condition

Hook: What guarantees that A* Search won't accidentally pick a sub-optimal path and stop too early? The secret lies in using an admissible heuristic—an optimistic estimate that never overestimates the distance to the destination.

A heuristic function \(h(n)\) is admissible if it never overestimates the actual minimal cost to reach a goal state from node \(n\):

\[ h(n) \le h^*(n) \quad \text{for all } n \]

where \(h^*(n)\) is the true optimal path cost from node \(n\) to the nearest goal state.

Intuition — Optimism Principle: An admissible heuristic is optimistic. It tells the search algorithm that the goal is at most \(h(n)\) units away. Because A* trusts this optimistic estimate, it will never prematurely ignore a true optimal path.

Example of Admissibility — Straight-Line Distance (SLD): In geographical route planning, the Euclidean straight-line distance between any city \(n\) and the goal city is always \(\le\) the actual driving distance via roads, because roads curve around terrain and obstacles. Thus, \(h_{\text{SLD}}(n) \le h^*(n)\) holds universally.

3.6.2 Symbol Registry — Heuristic Quality Metrics

  • \(h(n)\) — heuristic estimated cost from node \(n\) to goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(h^*(n)\) — true minimal actual cost from node \(n\) to goal — scalar \(\in \mathbb{R}_{\ge 0}\)
  • \(c(n, a, n')\) — actual step cost of action \(a\) transitioning from \(n\) to \(n'\) — scalar \(\in \mathbb{R}_{> 0}\)
  • \(f(n)\) — total evaluation function score \(g(n) + h(n)\) — scalar \(\in \mathbb{R}_{\ge 0}\)

3.6.3 Consistency (Monotonicity) Condition

A heuristic function \(h(n)\) is consistent (or monotonic) if, for every node \(n\) and every successor \(n'\) generated by action \(a\), the estimated cost of reaching the goal from \(n\) is no greater than the step cost to \(n'\) plus the estimated cost of reaching the goal from \(n'\):

\[ h(n) \le c(n, a, n') + h(n') \]

This condition is a form of the triangle inequality applied to search graphs.

Monotonic Non-Decreasing \(f(n)\) Derivation: If \(h(n)\) is consistent, the evaluation scores \(f(n)\) along any path are guaranteed to be non-decreasing:

\[ \begin{aligned} f(n') &= g(n') + h(n') \\ &= g(n) + c(n, a, n') + h(n') \\ &\ge g(n) + h(n) \quad \text{(since } c(n, a, n') + h(n') \ge h(n)\text{)} \\ &= f(n) \end{aligned} \]

Therefore, \(f(n') \ge f(n)\).

3.6.4 Impact on Optimality and Expansion

Optimality Summary:

  1. Admissibility guarantees that A* Tree Search returns an optimal solution.
  2. Consistency guarantees that A* Graph Search returns an optimal solution without needing to re-expand any previously closed nodes. Every node popped for expansion is guaranteed to be reached via its optimal path.

Property Comparison Matrix

Property Admissibility Consistency (Monotonicity)
Mathematical Relation \(h(n) \le h^*(n)\) \(h(n) \le c(n, a, n') + h(n')\)
Geometric Intuition Optimistic bound (never overestimates) Triangle inequality along graph edges
Required Scope A* Tree Search Optimality A* Graph Search Optimality
Operational Impact Prevents skipping true optimal path Guarantees \(f(n)\) is non-decreasing; zero node re-expansions

Assumptions & Scope (Consistency vs Admissibility): Every consistent heuristic is admissible (provided \(h(\text{goal})=0\)), but not every admissible heuristic is consistent. In practice, almost all natural admissible heuristics (e.g., Manhattan distance, Straight-line distance) are also consistent.

Common Pitfall: Using an inadmissible heuristic (\(h(n) > h^*(n)\)). An inadmissible heuristic can cause A* to overestimate the cost of an optimal path, causing it to select a sub-optimal alternative path and lose its optimality guarantee.

Recap & Bridge: Admissibility and consistency provide the theoretical guarantee of A* Search optimality. When formulating heuristics for complex AI problems (such as the 8-puzzle or Rubik's Cube), proving these properties is a crucial requirement.

Real-World Connection: In automated logistics and VLSI circuit layout routing, consistent heuristics ensure that shortest wire paths are calculated in a single pass without expensive re-expansion iterations.

  • Transition Model (\(Result(s, a)\)): Returns adjacent cell \((x', y')\) if no wall exists; returns current cell \((x, y)\) if movement is blocked.

Exercise 3: Outpatient Clinic Appointment Scheduling

Formulate scheduling patient appointments across multiple medical specialists:

  • Initial State (\(s_0\)): Empty weekly calendar grid across all clinic doctors and consultation rooms.
  • Actions (\(A(s)\)): Assign unscheduled patient \(P_i\) to doctor \(D_j\) in time slot \(T_k\) and room \(R_m\).
  • Transition Model (\(Result(s, a)\)): Marks slot \(T_k\) for doctor \(D_j\) and room \(R_m\) as occupied and updates remaining unscheduled patient list.
  • Goal Test (\(GoalTest(s)\)): All patient requests scheduled with zero doctor/room overlap conflicts.
  • Path Cost (\(g(n)\)): Weighted penalty sum of patient wait times, doctor idle gaps, and over-time hours.

3.7.2 Graph Search Tracing Exercises

Graph Search Tracing Checklist for Exams: Given any state graph with edge costs and heuristic table \(h(n)\):

  1. BFS: Trace using FIFO Queue. Check goal at generation (or expansion per convention).
  2. DFS: Trace using LIFO Stack. Prevent cycles by tracking explored set.
  3. UCS: Trace using Priority Queue ordered by \(g(n)\). Apply goal test only when popped/expanded.
  4. GBFS: Trace using Priority Queue ordered by \(h(n)\).
  5. A* Search: Trace using Priority Queue ordered by \(f(n) = g(n) + h(n)\). Compare all global frontier leaf nodes before popping.
  6. Admissibility Check: Verify \(h(n) \le h^*(n)\) for all nodes.
  7. Consistency Check: Verify \(h(n) \le c(n, n') + h(n')\) for all directed edges \((n, n')\).
