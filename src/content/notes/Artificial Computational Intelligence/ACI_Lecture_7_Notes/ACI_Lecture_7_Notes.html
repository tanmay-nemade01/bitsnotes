Part I: Neural Architecture Search via Genetic Algorithms

7.1 The Human Bottleneck in Network Design

Deep neural networks have traditionally been designed manually by human experts. This manual design process presents three fundamental bottlenecks:

Core Insight: Why Automate Architecture Design?

Humans rely on trial and error, prior knowledge, and established patterns when designing architectures. While effective, this reliance inherently limits the exploration of novel architectures. In fields such as medical research and drug discovery, AI systems have already been observed to propose novel structures that human experts had never conceived — precisely because humans are constrained by their prior beliefs about what should work.

Additionally, as network complexity increases (deep architectures with hundreds of layers, skip connections, branching paths), manual optimisation becomes impractical. The combination of human cognitive bias and sheer architectural scale creates a compelling case for automated architecture search.

Neural Architecture Search (NAS) addresses these bottlenecks by using evolutionary algorithms — specifically genetic algorithms — to automatically discover high-performing neural network topologies. This represents a paradigm shift: instead of a human expert designing a single architecture, an evolutionary process explores thousands of candidate architectures in parallel, guided only by a fitness signal.

7.2 NEAT: NeuroEvolution of Augmenting Topologies

7.2.1 Core Representation

NEAT is the foundational method for evolving neural networks automatically. The acronym breaks down as:

  • NE — NeuroEvolution: using evolutionary algorithms on neural networks
  • AT — Augmenting Topologies: every evolved network can have a different topology (structure)

In NEAT, a neural network is represented as a graph where:

  • Nodes represent individual neurons
  • Edges represent weighted connections between neurons

7.2.2 The Evolutionary Process in NEAT

NEAT starts with a population of very simple networks — minimal connections, shallow structures. Over successive generations, it gradually adds new nodes and connections through crossover and mutation operations, allowing complexity to grow organically. This is a deliberate design choice: starting simple and complexifying through evolution promotes efficiency and avoids premature complexity in early generations.

A distinctive feature of NEAT is species grouping: after children are generated, they are grouped into species based on topological similarity (e.g., shallow networks with one or two layers in one species, deeper networks in another). When selecting parents for the next generation, diversity is preserved by sampling from different species, preventing any single species from dominating the population prematurely.

7.2.3 Critical Limitation of NEAT

Why NEAT Cannot Handle Modern Deep Learning

NEAT operates at the individual neuron level. Each node is a single neuron; each edge is a single connection. Modern AI systems, however, use deep architectures such as CNNs, LSTMs, and Transformers that require layer-wise design with complex internal structure. NEAT cannot generate full-fledged convolutional layers, recurrent layers, or attention mechanisms — it can only shuffle individual neurons around. This makes NEAT suitable for small, simple networks but ineffective for real-world deep learning problems.

7.3 DeepNEAT: Evolving Entire Layers

7.3.1 The Critical Abstraction Shift

DeepNEAT extends the NEAT framework by making one crucial change: each node now represents an entire layer, not just a single neuron. This is the key insight that enables evolution of deep architectures.

Each node in a DeepNEAT graph stores:

  • Layer type: Convolutional, Dense (Fully Connected), LSTM, Pooling, etc.
  • Hyperparameters: Filter size, kernel dimensions, stride, activation function, number of units

Edges in DeepNEAT define how layers are connected and represent the flow of data between them. When multiple inputs converge on a single node, they are combined using either concatenation or summation operations. When there is a size mismatch between connected layers, the architecture applies pooling or downsampling operations to ensure dimensional compatibility.

7.3.2 How DeepNEAT Builds a Network

The process begins with a chromosome represented as a graph — this serves as the initial population. For each node in the graph, a corresponding neural network layer is created, and all layers are connected based on the graph structure. The final output is a complete deep neural network, fully specified and ready for training.

7.3.3 The Limitation that Spawned CoDeepNEAT

DeepNEAT's Fatal Flaw: Randomness Without Reuse

Networks generated by DeepNEAT tend to be random and unstructured. Each generation produces entirely new layers with no mechanism to reuse previously evolved, successful structures. In contrast, modern hand-designed architectures like ResNet and Inception (GoogLeNet) use repeated, well-organised building blocks — residual blocks, inception modules — that are composed hierarchically. DeepNEAT fails to create repeatable patterns because it has no concept of a reusable module. Every new layer is generated from scratch, leading to inefficiency and a lack of structural coherence.

7.3.4 Benchmark Performance: CIFAR-10 Results

When evaluated on the CIFAR-10 image classification benchmark (50,000 training images, 10,000 test images, 32×32 colour pixels across 10 classes), CoDeepNEAT was initialised with populations of 25 blueprints and 45 modules. From these, 100 CNNs were assembled for fitness evaluation in every generation — each trained for only 8 epochs on a 42,500/7,500 train/validation split. After 72 generations of evolution, the best network was fully trained for 300 epochs and achieved a classification error of 7.3%, comparable to the 6.4% error from Bayesian hyperparameter optimisation (Snoek et al.). Notably, because only limited training could be done during evolution, the evolved network trains very fast — reaching 20% test error in just 12 epochs vs. over 30 for the baseline. The best evolved network exhibited the deep, repetitive modular structure characteristic of successful hand-designed CNNs.

7.4 CoDeepNEAT: Blueprints, Modules, and the Genotype-Phenotype Distinction

7.4.1 The Two-Part Evolutionary Separation

CoDeepNEAT improves DeepNEAT by separating evolution into two distinct parts, enabling both structured organisation and reuse. The algorithm draws inspiration from Hierarchical SANE and component-evolution approaches like ESP and CoSyNE. Two populations — modules and blueprints — are evolved separately using the same methods as DeepNEAT.

ComponentRoleAnalogy
Blueprint (Macro-architecture)A graph where each node contains a pointer to a particular module species. Defines the overall network skeleton.Architectural floor plan
Module (Micro-architecture)A graph representing a small, reusable neural subnetwork with specific layers and hyperparameters.Prefabricated building block

Why the Blueprint–Module Separation Is Powerful

Different researchers or subpopulations can independently evolve modules using genetic algorithms. Someone else (or another evolutionary process) can define the blueprint. When constructing the final network, you simply pick the best modules from the available pool and slot them into the blueprint placeholders. This mirrors the microservices architecture pattern: components are independently developed and then composed. Most importantly, once a module proves fruitful (high accuracy), it can be reused at multiple positions within the same network or across entirely different blueprints.

7.4.2 The CoDeepNEAT Algorithm in Detail

CoDeepNEAT follows the same fundamental process as NEAT: populations start with minimal complexity, and structure (nodes and edges) is added incrementally through mutation over generations. Historical markings (innovation numbers) determine how genes of two chromosomes line up during crossover. The population is divided into species based on a similarity metric, and each species grows proportionally to its fitness.

The key distinction from DeepNEAT is in fitness evaluation and attribution. During each generation, modules and blueprints are combined together to create assembled networks: each node in a blueprint is replaced with a module chosen randomly from the species to which that node points. If multiple blueprint nodes point to the same module species, the same module is used in all of them — this is what creates the repetitive structure. The assembled networks are trained and evaluated, but the fitness is attributed back to both blueprints and modules as the average fitness of all assembled networks containing that particular blueprint or module. This co-evolutionary credit assignment ensures that modules that contribute to high-performing assemblies across diverse blueprints rise in fitness.

7.4.3 Genotype vs. Phenotype: The Two-Stage Construction

This is the most critical conceptual distinction in CoDeepNEAT. Misunderstanding it leads to confusion about the entire approach.

Genotype (Representational Stage)

The genotype is the representation. It involves two parallel activities:

  • Blueprint creation: Evolving macro-structures — graphs where each node is a placeholder (a module species ID like M1, M2, M3), not an actual layer. The diamond node marks the input, the bottom node marks the output, and intermediate nodes (often shown in yellow) mark insertion points for modules.
  • Module creation: Running a full genetic algorithm pipeline to evolve small neural subnetworks. Each module is itself a mini-neural-network (e.g., Conv→ReLU→Pool or LSTM→Dense).

Every structural component — every module, every blueprint node — is assigned a unique innovation number (a persistent identifier akin to a database primary key). These innovation numbers enable correct alignment during crossover, ensuring that matching components from different parents are recombined meaningfully.

Phenotype (Construction Stage)

The phenotype is the actual, trainable deep neural network. It is assembled through four steps:

  1. Select a Blueprint — Choose one macro-architecture from the evolved population.
  2. Identify Nodes — Each node in the blueprint carries a module placeholder ID.
  3. Select Modules — For each placeholder, pick a module from the corresponding subpopulation (the modules evolved during the genotype stage).
  4. Replace and Connect — Each placeholder node is expanded into its full module (a small subnetwork). The edges of the blueprint dictate how data flows between these expanded modules. White nodes in the blueprint represent intermediate connection/flow points; yellow nodes represent the actual module insertion points.

Blueprint Visualisation Example

Consider a blueprint with structure: Input → M1 → M2 → M1 → Output. Here:

  • M1 appears twice — the same module type is reused at two positions.
  • A more complex blueprint might branch: Input feeds into both M1 and M2, their outputs merge into M3, and M3 feeds Output.
  • Each white (connection) node helps manage dimensionality and flow; each yellow node is where a module is expanded.

This reusability is exactly what modern architectures like ResNet exploit: the same residual block design is repeated many times. CoDeepNEAT brings this capability into the evolutionary framework.

7.5 The Genetic Algorithm Pipeline for NAS

With the blueprint–module framework established, we now walk through how genetic algorithms are applied to evolve the modules (and, in advanced cases, the blueprints themselves). This is the heart of the CoDeepNEAT approach.

7.5.1 Step 1: Population Initialisation

Evolution begins with a population of randomly generated simple neural network structures. These are the initial modules — small networks with minimal layers and basic connectivity. For example, a population of 100 simple networks might start with architectures like: a single convolutional layer with a small dense head, or a two-layer MLP. Starting simple allows gradual complexity growth through subsequent evolutionary operations and avoids unnecessary computational cost in early generations.

7.5.2 Step 2: Fitness Evaluation

Each candidate architecture (each module) is:

  1. Instantiated as an actual neural network.
  2. Trained using gradient descent — but only for a limited number of epochs (e.g., 5–10 epochs, not full convergence). The goal is to gauge architectural potential, not to fully train.
  3. Evaluated on a validation dataset to measure performance.

For a cat-vs-dog classification example with 10,000 labelled images, if a network correctly classifies 90 out of 100 validation images, its fitness is 0.90 (or 90%). If another module achieves 80%, its fitness is 0.80. This ensures evaluation is based on generalisation, not memorisation. Training time is deliberately kept minimal to make evolutionary search computationally tractable — the objective is to identify promising architectural patterns, not to produce a production-ready trained model at every generation.

When Does Phenotype Construction Happen?

A common point of confusion: phenotype construction (assembling the final network by plugging modules into blueprints) does not happen during the genetic algorithm phase. The genetic algorithm runs to completion over many generations, evolving high-fitness modules. Only after the evolutionary process has produced a set of promising modules does phenotype construction occur, using the best modules from the final generation. This prevents premature assembly around weak, early-generation modules.

7.5.3 Step 3: Parent Selection - Roulette Wheel

Parent architectures are selected using a probabilistic approach based on fitness values. This is the same roulette wheel (fitness-proportionate) selection used in standard genetic algorithms.

Given four architectures with fitness values:

  • Architecture A: 80% → proportional share in roulette wheel
  • Architecture B: 60% → smaller share
  • Architecture C: 40% → even smaller share
  • Architecture D: 20% → very small share

After normalising by the total fitness sum, A occupies a large chunk of the pie chart, B moderate, C small, and D tiny. When the roulette wheel is spun, A and B are selected multiple times (exploitation of promising architectures), C is selected occasionally, and D rarely (maintaining exploration). This balances exploitation (favouring proven architectures) with exploration (giving weaker architectures a chance to contribute genetic material that might prove valuable after recombination).

7.5.4 Step 4: Crossover (Recombination)

Two selected parent architectures are combined to produce offspring. Since each parent is itself a small neural network (a sequence of layers), crossover operates on the layer sequence.

One-Point Crossover on Layer Sequences

Parent 1: Conv → Pooling → Dense

Parent 2: Conv → Conv → Dense

With a crossover point after the first element:

Child 1: Conv → Conv → Dense (inherits deeper feature extraction from Parent 2)

Child 2: Conv → Pooling → Dense (retains the pooling pattern from Parent 1)

Innovation numbers assigned to each structural component ensure correct alignment during crossover: matching components (e.g., convolutional layers with similar function) are aligned, and extra layers present in one parent but not the other are inherited if they prove beneficial.

7.5.5 Step 5: Mutation

Mutation introduces random changes to explore novel architectures beyond what crossover alone can produce. Three types of mutation are applied to the child architectures:

  1. Add a new layer — Insert a convolutional, dense, or pooling layer that neither parent had.
  2. Add a new connection — Introduce a skip connection or a branching path not present in the parents.
  3. Modify hyperparameters — Change a filter size from \(3 \times 3\) to \(5 \times 5\), alter the activation function, or adjust the stride.

Mutation Impact Example

Original child architecture (post-crossover): Conv(\(3\times3\)) → Pooling → Dense → validation accuracy 85%

After mutating filter size: Conv(\(5\times5\)) → Pooling → Dense → validation accuracy 92%

The larger kernel captures larger patterns, improving the architecture's suitability for the task. This mutation is the step that ensures the child is not simply a copy of its parents — it carries a genuinely novel characteristic, mirroring how biological offspring can exhibit traits absent in either parent.

7.5.6 Step 6: Species Grouping (CoDeepNEAT Specific)

After mutation, the generated children are grouped into species based on similarity metrics — typically by network depth or topology similarity. For example, shallow networks (1–2 layers) form one species, medium-depth networks (3–5 layers) form another, and deep networks form a third.

This step is not part of vanilla genetic algorithms; it was introduced by the NEAT lineage. Its purpose is to preserve diversity across generations. When children become parents in the next generation, selection draws from multiple species rather than letting a single dominant species take over. This prevents premature convergence — the situation where all architectures in the population become near-identical too early, stifling further innovation.

7.5.7 Iteration and Termination

The entire generational cycle (fitness evaluation → selection → crossover → mutation → species grouping) repeats across multiple generations. A typical progression for a cat-vs-dog classifier might look like:

  • Generation 1: ~50% validation accuracy (random initial architectures)
  • Generation 20: ~75% accuracy (evolution has found promising patterns)
  • Generation 50: ~95% accuracy (near-optimal architecture discovered)

The final architecture is selected based on the highest validation performance across all generations. At that point, phenotype construction assembles the best modules into the blueprint, producing the deployed network.

7.6 Worked Example: Cat-vs-Dog Image Classification

Consider a 32×32×3 RGB input image (a cat photograph, though the system does not yet "know" this). The system has already completed its evolutionary phase and produced three promising modules: Module 1 (Conv + ReLU), Module 2 (Conv 5×5 + Pooling), and Module 3 (Dense). These modules were not manually designed — they were discovered through evolution.

7.6.1 The Feature Extraction Hierarchy

As the image passes through the evolved architecture, features are extracted in a progressive hierarchy that mirrors how biological vision systems operate:

  1. Layer 1 — Edge Detection (3×3 convolution): Detects basic edges and body outlines. Output: a feature map highlighting edges throughout the image.
  2. Layer 2 — Activation (ReLU): Applies the ReLU function \(f(x) = \max(0, x)\), introducing non-linearity and suppressing negative activations.
  3. Layer 3 — Texture Detection (5×5 convolution): Combines edges to detect mid-level patterns — fur texture, eye region, ear shape. The network begins distinguishing cat-like textures from dog-like textures.
  4. Layer 4 — Pooling (Max Pooling): Reduces spatial dimensions while retaining the strongest feature activations. The focus shifts to whether a feature is present (Boolean presence), not its exact spatial location — the max-pooling operation discards precise positional information.
  5. Higher Layers — Part/Object Detection: Detects composite features — triangular ears, small nose, whisker lines. These are the high-level features that distinguish a cat from a dog.
  6. Flatten + Dense: All extracted features are flattened into a vector and fed through dense layers that learn combinations: if whiskers AND triangular ears AND small nose → more likely a cat.
  7. Output Layer (Softmax): Produces a probability distribution — e.g., Cat: 0.92, Dog: 0.08. These probabilities sum to 1. The highest-confidence class is the prediction.

7.6.2 The Evolutionary Advantage

Suppose during evolution, three networks competed:

  • Network A: Detects only edges — accuracy 60%
  • Network B: Detects edges + fur/eyes — accuracy 85%
  • Network C: (Post-mutation of B, with an added skip connection) — accuracy 92%

Evolution selects Network C as the best and uses it as a parent for the next generation. This is the power of CoDeepNEAT: the system discovers which combinations of layers, connections, and hyperparameters yield the best performance — without any human specifying that a skip connection would help or that a 5×5 filter is better than a 3×3 filter for this dataset.

7.7 Worked Example: Image Captioning with CoDeepNEAT

Consider a company that wants to automatically generate captions for uploaded images. This is a real-world case study where CoDeepNEAT was deployed to build a captioning system for a major online magazine, with the goal of making images accessible to blind users through screen readers. The system evolves three categories of components:

  • CNN modules for image feature extraction
  • LSTM modules for sequential text generation
  • Blueprints that arrange these modules into a coherent architecture

7.7.1 Initial Setup

Three modules are available:

  • M1: CNN feature extractor (Conv → ReLU → Pool)
  • M2: LSTM layer for sequence generation
  • M3: Dense + Softmax output layer

The blueprint has three placeholders: M1 → M2 → M3, with M1 connecting to the input and M3 connecting to the output. The initial fitness values are measured using the BLEU score (Bilingual Evaluation Understudy — a metric that measures how close the generated caption is to human reference captions).

In the actual CoDeepNEAT implementation, the system starts even simpler: the initial population feeds image and text inputs to a shared embedding layer densely connected to a softmax output over words. From this minimal starting point, CoDeepNEAT evolves architectures that include fully connected layers, LSTM layers, sum layers, concatenation layers, and associated hyperparameters. The well-known Show and Tell image captioning architecture is within this search space, providing a baseline for comparison. Fitness is computed as the mean across three metrics — BLEU, METEOR, and CIDEr — normalised by their baseline values over a holdout set of 5,000 images (25,000 image-caption pairs).

7.7.2 One Complete Generation

Two candidate phenotype assemblies are initialised:

  • Network N1: M1(CNN) → M2(LSTM) → M3(Dense+Softmax) — BLEU: 0.45
  • Network N2: M1(CNN) → M1(CNN) → M3(Dense+Softmax) — BLEU: 0.62

N2 is identified as the best network (higher BLEU score). It is selected as a parent. From N2 and another parent, single-point crossover is applied to the layer sequences. The resulting child undergoes mutation — a \(3\times3\) filter is changed to \(5\times5\) — producing a new child that may achieve even higher BLEU scores. After several generations, CoDeepNEAT discovers the optimal combination of modules, the best blueprint structure, and the best hyperparameters — all automatically.

7.7.3 Results and the Evolved Architecture

In the actual case study, evolution ran for 37 generations with 100 networks trained per generation — each taking about one hour on approximately 100 GPUs in parallel. To keep costs reasonable, networks were trained for only six epochs on a random 100,000-image subset of the 500,000 MSCOCO image-caption pairs during evolution. This created strong evolutionary pressure toward networks that converge quickly: the best evolved architectures trained to near-convergence about 6 times faster than the baseline Show and Tell model.

The most fit architecture discovered was striking: it contained six LSTM layers, four summing merge layers, several skip connections, and a single module consisting of two LSTM layers merged by a sum that was repeated three times. Notably, there was a path from the input through dense layers directly to the output that bypassed all LSTM layers, giving the softmax a more direct view of the current input. This motif of skip connections with summing merges mirrors the residual architectures that are popular in deep learning — the evolution independently discovered a principle that human engineers had also found effective. When fully trained on the MSCOCO dataset, the evolved network improved over the hand-tuned baseline: BLEU-4 score of 29.1 vs. 27.7, CIDEr of 88.0 vs. 85.5.

Resource Intensity Consideration

CoDeepNEAT is computationally expensive. Running full genetic algorithms for 50+ generations, training each candidate architecture (even for limited epochs), and evaluating fitness requires substantial compute. However, this cost is concentrated in the genotype phase. Once a library of high-performing modules is built, they can be reused across many different blueprints and tasks, amortising the initial evolutionary cost. This is analogous to pre-training foundation models: the upfront investment is large, but the downstream reuse is economical. Furthermore, because limited training is used during evolution, the search is biased toward discovering architectures that are fast learners — a useful property in itself beyond raw accuracy.

7.7.4 NAS Across Search Strategies: A Broader Perspective

The NAS survey literature provides a useful framework for understanding where CoDeepNEAT fits within the broader field. NAS methods are categorised along three dimensions:

  • Search Space: CoDeepNEAT uses a multi-branch space with blueprint-defined macro-architecture and module-defined micro-architecture. More recent approaches use cell-based search spaces where architectures are built by stacking learned "cells" (small directed acyclic graphs of operations) in a predefined pattern. Cell-based spaces drastically reduce the search space size while enabling transferability across datasets — cells optimised on CIFAR-10 have been successfully transferred to ImageNet.
  • Search Strategy: CoDeepNEAT uses evolutionary algorithms (cooperative coevolution). Alternative strategies include reinforcement learning (treating architecture generation as a sequential decision process, e.g., using RNN controllers with policy gradient methods), Bayesian optimisation (using tree-based models like tree Parzen estimators to efficiently search high-dimensional conditional spaces), and gradient-based methods like DARTS, which use continuous relaxation of the discrete search space to enable direct gradient descent on architectural parameters.
  • Performance Estimation: CoDeepNEAT uses lower-fidelity estimates (limited training epochs, data subsets) to keep evolutionary search tractable. Other speedup techniques include learning curve extrapolation (predicting final performance from early training curves), network morphisms (warm-starting child networks by inheriting weights from parents), and one-shot models with weight sharing (treating all architectures as subgraphs of a supergraph, training the supergraph once, and evaluating subgraphs without separate training — reducing search from thousands of GPU days to just a few).

Notably, empirical comparisons suggest that when computational resources are equated, evolutionary methods and RL perform similarly well in final accuracy, with evolution often having better anytime performance and finding smaller models. Random search, while simple, achieves surprisingly competitive results in well-designed search spaces — though evolution and RL consistently outperform it by meaningful margins.

Part II: Adversarial Search and Game Playing

7.9 From Single-Agent to Multi-Agent Environments

7.9.1 What Changes with Multiple Agents?

Every search algorithm studied previously in this course — BFS, DFS, A*, genetic algorithms, local search — assumed a single agent operating in a passive environment. The agent selected actions; the environment responded deterministically. The agent's only concern was: "What action gets me closer to my goal?"

Adversarial search fundamentally changes this model. When two or more agents have conflicting goals, every action must be evaluated not only by what it achieves for the agent, but by how the opponent will respond. The question becomes: "If I make this move, what will my opponent do to reduce my chances of success?"

The Defining Characteristic of Adversarial Search

In adversarial settings, one player's gain is another player's loss. An agent cannot plan myopically — it must anticipate the opponent's best response at every step. This changes the entire computational approach from forward search to recursive game-tree evaluation.

7.9.2 Real-World Significance

Studying adversarial search is not merely about building better game-playing programs — though that is a valuable outcome. Games serve as simplified models of strategic interaction that appear throughout real life: negotiation, auctions, cybersecurity (attacker vs. defender), multi-agent reinforcement learning (where one agent critiques another), and competitive markets. The formalisms developed for adversarial search provide the mathematical foundation for reasoning about any scenario where intelligent agents pursue conflicting objectives.

7.10 Formalising a Game in AI

A game in the adversarial search framework is defined by six components. Note that in game-playing literature, the term move is used as a synonym for "action" and position as a synonym for "state."

  1. Initial State (\(S_0\)): The starting board configuration or situation. In Tic-Tac-Toe, this is the empty 3×3 grid.
  2. Player Function (\(\text{To-Move}(s)\) or \(\text{Player}(s)\)): Returns which player has the turn in state \(s\). Players alternate: MAX places X, MIN places O.
  3. Action Function (\(\text{Actions}(s)\)): Returns the set of legal moves in state \(s\). In Tic-Tac-Toe, this is the set of empty cells.
  4. Result Function (\(\text{Result}(s, a)\)): The transition model — returns the state that results from taking action \(a\) in state \(s\). Given a board with some X's and O's, placing an O in an empty cell produces a new board state.
  5. Terminal Test (\(\text{Is-Terminal}(s)\)): Returns true when the game is over and false otherwise. States where the game has ended are called terminal states. In Tic-Tac-Toe, the game ends when either player has three in a row (column, row, or diagonal) or when all nine cells are filled with no winner (draw).
  6. Utility Function (\(\text{Utility}(s, p)\)): Also called an objective function or payoff function. Assigns a numeric value to terminal states from player \(p\)'s perspective. For Tic-Tac-Toe from MAX's perspective: win = +1, loss = −1, draw = 0. Some games have a wider range of outcomes — for example, the payoffs in backgammon range from 0 to 192.

Together, the initial state, ACTIONS function, and RESULT function define the state space graph — a graph where the vertices are states, the edges are moves, and a state might be reached by multiple paths. We can then superimpose a search tree over part of that graph to determine what move to make.

Tic-Tac-Toe: Utility from Both Perspectives

Consider three terminal boards:

  • Board 1: X has three in a row (MAX wins) → From MAX's view: +1; From MIN's view: −1
  • Board 2: Full board, no winner → From MAX's view: 0; From MIN's view: 0
  • Board 3: O has three in a column (MIN wins) → From MAX's view: −1; From MIN's view: +1

The utility values are symmetric and opposite: when MAX gains +1, MIN loses −1, and vice versa. This is the mathematical expression of a zero-sum game.

7.11 Two-Player Zero-Sum Games

7.11.1 Definition and Intuition

A two-player zero-sum game is one where:

  • There are exactly two players — conventionally named MAX and MIN.
  • One player's gain is precisely the other player's loss: \(\text{Utility(MAX)} + \text{Utility(MIN)} = 0\) for every terminal state.
  • The players have exactly opposite goals: MAX wants to maximise the score; MIN wants to minimise it — which, from MIN's perspective, means maximising its own chance of winning.

Classic examples include Tic-Tac-Toe, Chess, Checkers, and Go. Beyond games, many real-world competitive scenarios are zero-sum: job interviews (one position, multiple candidates), promotions, winner-take-all auctions, and certain cybersecurity scenarios.

The Zero-Sum Property at Every Step

It is natural to think the zero-sum property only manifests at the end — when someone wins or loses. But the adversarial mindset applies at every intermediate move. When MAX considers a move, it must account for the fact that MIN will respond with the move that is worst for MAX. This recursive consideration of the opponent's optimal play is what gives the Minimax algorithm its name and its structure.

For example, in Tic-Tac-Toe, if MAX has two in a row with one empty cell remaining, MIN — on its turn — will block that cell rather than playing elsewhere, even though blocking does not directly move MIN closer to winning. MIN is acting to minimise MAX's score, which is the rational zero-sum behaviour.

7.11.2 Three-Player and Non-Zero-Sum Extensions

When games have more than two players, they are generally not zero-sum (one player's loss does not directly equal another single player's gain). In such cases, utility vectors replace scalar utilities: each player has its own utility component, e.g., \(\langle v_A, v_B, v_C \rangle\) for a three-player game. The minimax idea extends naturally: at a node where player C chooses, we back up the utility vector of the successor state with the highest value for C. Each player maximises only their own component at their turn, and the backed-up vector reflects the optimal outcome for whichever player is choosing at that level.

Multiplayer games introduce a dynamic absent from two-player zero-sum settings: alliances (formal or informal). Alliances can emerge purely from self-interested optimal play — if players A and B are both weak and C is strong, it is optimal for both A and B to attack C rather than each other. Once C weakens, the alliance's value dissolves, and A or B may break it. In non-zero-sum two-player games, collaboration can also occur naturally: if a terminal state gives both players the highest possible utility, both will cooperate to reach it.

7.12 Game Trees

7.12.1 Structure of a Game Tree

A game tree is a rooted tree that represents every sequence of moves from the initial state to terminal states. The game tree may be infinite if the state space itself is unbounded or if the rules of the game allow for infinitely repeating positions.

  • Nodes represent game states (board configurations).
  • Edges represent legal moves that transition from one state to another.
  • Levels alternate between players: depth 0 is MAX's turn, depth 1 is MIN's turn, depth 2 is MAX's turn, and so on.
  • Leaf nodes are terminal states — the game has ended at these positions.

A single move by one player that takes us one level deeper in the game tree is called a ply. When two players each make one move (one ply each), we say two ply have been completed. This terminology unambiguously distinguishes between a full "round" of play and an individual action by a single player.

7.12.2 Size and Tractability

For Tic-Tac-Toe, the full game tree has fewer than 9! = 362,880 terminal nodes (with only 5,478 distinct states) — small enough to enumerate completely. For Chess, the game tree has approximately \(10^{40}\) nodes — far beyond complete enumeration. Expert human players are believed to mentally explore 2–3 levels deep across many candidate moves. Computers can explore significantly more levels using pruning techniques. The challenge is not to generate the entire tree but to evaluate partial trees using heuristic estimates of non-terminal positions.

7.13 The Minimax Algorithm

7.13.1 Core Principle

The Minimax algorithm chooses the move that gives the best guaranteed outcome, assuming the opponent also plays optimally. This is the central guarantee:

The Minimax Guarantee

MAX does not simply choose the branch with the best possible outcome (that would be naive — the opponent would never allow it). Instead, MAX chooses the branch whose worst-case outcome is best. In other words: "If my opponent plays perfectly against me, what is the best score I can still guarantee?"

Minimax answers: "You may not reach the absolute best leaf value, but you will never fall below a certain guaranteed threshold."

Formally, the minimax value at a state \(s\) — written as MINIMAX(\(s\)) — is the utility for MAX assuming both players play optimally from that state onward. If MIN plays suboptimally, MAX will only do better. The minimax decision at the root is the action that leads to the state with the highest minimax value.

7.13.2 Formal Definition

The minimax value for any state \(s\) is computed recursively:

\[ \text{MINIMAX}(s) = \begin{cases} \text{Utility}(s, \text{MAX}) & \text{if Is-Terminal}(s) \\[6pt] \displaystyle\max_{a \in \text{Actions}(s)} \text{MINIMAX}(\text{Result}(s, a)) & \text{if To-Move}(s) = \text{MAX} \\[12pt] \displaystyle\min_{a \in \text{Actions}(s)} \text{MINIMAX}(\text{Result}(s, a)) & \text{if To-Move}(s) = \text{MIN} \end{cases} \]

At terminal nodes, the utility value is returned directly. At MAX nodes, we take the maximum over all child minimax values because MAX controls the action and will choose the one yielding the highest value. At MIN nodes, we take the minimum because MIN controls the action and will choose the one yielding the lowest value for MAX.

7.13.3 Algorithm Mechanics: Recursive Depth-First Traversal

Minimax uses a recursive depth-first traversal of the game tree, implemented through two mutually recursive functions — MAX-VALUE (for MAX's turn) and MIN-VALUE (for MIN's turn). The evaluation proceeds from the leaves upward:

  1. Initialisation: MAX-VALUE starts with \(v = -\infty\); MIN-VALUE starts with \(v = +\infty\).
  2. Traversal: Start at the root with MAX-VALUE, recursively descend to the leftmost leaf.
  3. At a leaf: The leaf's utility value becomes the candidate for its parent.
  4. At a MAX node: For each child, call MIN-VALUE. Take the maximum of all returned child values. The intuition: MAX controls this choice and will pick the child that gives the highest score.
  5. At a MIN node: For each child, call MAX-VALUE. Take the minimum of all returned child values. The intuition: MIN controls this choice and will pick the child that gives the lowest score for MAX.
  6. Back up: The value at the root is the minimax value — the best score MAX can guarantee. The corresponding action is the minimax decision.

7.13.4 Complexity Analysis

If the maximum depth of the game tree is \(m\) and there are \(b\) legal moves at each point (the branching factor), the time complexity of minimax is \(O(b^m)\) — exponential in the depth. The space complexity is \(O(bm)\) if all actions are generated at once, or \(O(m)\) if actions are generated one at a time. For chess, with branching factor ~35 and average depth ~80 ply, minimax would need to search \(35^{80} \approx 10^{123}\) states, which is completely infeasible. This exponential complexity is why practical implementations require pruning, depth limits, and heuristic evaluation functions.

Minimax — Annotated Example 1

Consider a two-level game tree with MAX at the root. The leaves have static values:

          [MAX - root]
         /            \
    [MIN]              [MIN]
   /    \             /    \
  4      7          2      6
  1. Left MIN node: \(\min(4, 7) = 4\) — MIN will block MAX from reaching 7.
  2. Right MIN node: \(\min(2, 6) = 2\) — MIN will block MAX from reaching 6.
  3. Root MAX node: \(\max(4, 2) = 4\) — MAX chooses the left branch.

Result: MAX's best move is the left branch, guaranteeing a value of at least 4. MAX might have hoped for 7, but MIN's optimal response forces the outcome to 4. The right branch would be even worse — MIN would force it to 2.

Minimax — Annotated Example 2 (Deeper Tree)

Consider a game tree with MAX at the root, alternating layers, and leaf values:

                    [MAX - A]
                   /          \
              [MIN - B]       [MIN - C]
             /    \           /    \
        [MAX-D]  [MAX-E]  [MAX-F] [MAX-G]
        /   \    /   \    /   \    /   \
      −1    8  −3   −1   2    1   −3    4
  1. MAX-D: \(\max(-1, 8) = 8\)
  2. MAX-E: \(\max(-3, -1) = -1\) (on the number line, −1 > −3)
  3. MAX-F: \(\max(2, 1) = 2\)
  4. MAX-G: \(\max(-3, 4) = 4\)
  5. MIN-B: \(\min(8, -1) = -1\) — MIN forces MAX to the worse outcome
  6. MIN-C: \(\min(2, 4) = 2\)
  7. MAX-A: \(\max(-1, 2) = 2\) — MAX chooses the right branch

Result: MAX guarantees a value of 2. Notice that 8 exists in the tree — a far better outcome — but MAX cannot force it because reaching 8 requires passing through MIN-B, which will route MAX to −1 instead. The algorithm automatically accounts for MIN's optimal counter-play.

Minimax — Deeper Tree with Propagation

Consider a 4-level tree (MAX → MIN → MAX → MIN → leaves):

                           [MAX - root]
                         /               \
                   [MIN-a]                [MIN-b]
                 /        \              /        \
            [MAX-c]     [MAX-d]     [MAX-e]     [MAX-f]
           /    \      /    \      /    \      /    \
       [MIN]  [MIN] [MIN]  [MIN] [MIN]  [MIN] [MIN]  [MIN]
       / \    / \   / \    / \   / \    / \   / \    / \
      8  7   3  9  7 10   8  6  1  8   8  5  9  6   7  5

Solving bottom-up:

  1. MIN leaves: \(\min(8,7)=7, \min(3,9)=3, \min(7,10)=7, \min(8,6)=6, \min(1,8)=1, \min(8,5)=5, \min(9,6)=6, \min(7,5)=5\)
  2. MAX-c: \(\max(7,3) = 7\)
  3. MAX-d: \(\max(7,6) = 7\)
  4. MAX-e: \(\max(1,5) = 5\)
  5. MAX-f: \(\max(6,5) = 6\)
  6. MIN-a: \(\min(7,7) = 7\)
  7. MIN-b: \(\min(5,6) = 5\)
  8. MAX-root: \(\max(7,5) = 7\)

Result: MAX guarantees 7. The absolute best leaf in the tree might be 10, but MIN's blocking prevents MAX from ever reaching it.

7.13.5 Initialisation Rationale: Why \(-\infty\) and \(+\infty\)?

The initialisation values are chosen to ensure that the first leaf value encountered always replaces the initial value:

  • MAX starts at \(-\infty\): The maximiser begins at the most negative possible value. Any real leaf value (e.g., \(-1\), \(3\), \(8\)) is greater than \(-\infty\), so it becomes the new baseline. The maximiser then tries to move rightward on the number line — toward more positive values — by comparing with subsequent children.
  • MIN starts at \(+\infty\): The minimiser begins at the most positive possible value. Any real leaf value is less than \(+\infty\), so it becomes the new baseline. The minimiser tries to move leftward — toward more negative values — by picking smaller child values.

This is a computational convenience that guarantees the first comparison always succeeds, regardless of the leaf values.

7.13.6 Minimax Is Recursive - Depth Does Not Change the Guarantee

Whether the game tree has 2 levels or 20, the Minimax guarantee remains identical: MAX will not end up in the worst possible outcome. The algorithm propagates values upward regardless of depth, with each layer faithfully representing the optimal play of the player whose turn it is. Deeper trees simply mean more layers of alternation — the logic at each node (maximise at MAX, minimise at MIN) remains unchanged.

7.14 Static Evaluation Functions

7.14.1 Motivation: Evaluating Non-Terminal Positions

In all the Minimax examples above, leaf nodes were assigned numeric values. But in a real game, we cannot always reach a terminal state — the search must be cut off at some depth. At that cutoff, we need a way to estimate the desirability of a non-terminal board position. This estimate is provided by a static evaluation function.

A static evaluation function is a domain-specific heuristic that maps a board state to a numeric score, estimating which player is in a stronger position. It is called "static" because it evaluates a single position in isolation, without looking ahead at future moves.

7.14.2 Material Balance: The Simplest Chess Evaluation

The most common static evaluation for chess assigns a material value to each piece type. This is the canonical example of a heuristic evaluation function: centuries of human chess-playing experience have established these approximate relative values.

PieceMaterial Value
Queen9
Rook5
Bishop3
Knight3
Pawn1

The static evaluation from a player's perspective is then the difference between their own total material and the opponent's total material. Mathematically, this is a weighted linear function — the simplest form of evaluation function:

\[ \text{Eval}(s) = w_1 f_1(s) + w_2 f_2(s) + \cdots + w_n f_n(s) = \sum_{i=1}^{n} w_i f_i(s) \]

Where each \(f_i(s)\) is a feature of the position (e.g., "number of white queens," "number of black pawns") and each \(w_i\) is the weight assigned to that feature. For material-only evaluation, the features are simply piece counts and the weights are the material values above. A secure advantage equivalent to a pawn gives a substantial likelihood of winning; a secure advantage equivalent to three pawns should give almost certain victory.

It is worth noting that the evaluation function need not be linearly correlated with the actual win probability — it only needs to be strongly correlated. If state \(s\) is twice as likely to produce a win as state \(s'\), we do not require \(\text{Eval}(s) = 2 \cdot \text{Eval}(s')\); we only require \(\text{Eval}(s) > \text{Eval}(s')\). This is because the evaluation is used to compare and rank moves, not to make probabilistic predictions.

Material Evaluation Example

Suppose at a given board position, Black has: 1 Queen (9), 1 Bishop (3), 1 Pawn (1) → total = 13.
White has: 2 Bishops (3+3) → total = 6.

From White's perspective: \(\text{Eval} = 6 - 13 = -7\)

This strongly negative evaluation indicates Black is dominant — more pieces on the board and the only Queen. Without looking ahead, a static evaluator would flag this as a position White should avoid. The evaluation confirms what a human player would immediately recognise: White is at a severe material disadvantage.

7.14.3 Generalising: Domain-Specific Heuristics

Static evaluation functions must be pre-defined for each game. While the material-balance example uses a simple weighted linear combination, real implementations often recognise that feature contributions are not independent. A pair of bishops might be worth more than twice the value of a single bishop (the bishop pair bonus), and a bishop is worth more in the endgame than in the opening — when move number is high or the number of remaining pieces is low. This leads to nonlinear evaluation functions that go beyond simple weighted sums.

Other factors beyond pure material count that can be incorporated:

  • Positional factors: Control of the centre, piece mobility, king safety.
  • Pawn structure: Doubled pawns, isolated pawns, passed pawns.
  • Temporal factors: Which player is closer to checkmate or to promoting a pawn?

For Tic-Tac-Toe, a simple static evaluation might count the number of rows, columns, and diagonals where a player has two marks and the third cell is still empty — a measure of how close each player is to winning.

Static Evaluation vs. Heuristic Functions

Static evaluation functions for adversarial search are conceptually analogous to the heuristic functions used in A* search and the fitness functions used in genetic algorithms. In all three cases, the function provides a numeric estimate of "goodness" for a given state without performing a full search from that state. The key difference is that static evaluations must account for both players' positions, while A* heuristics estimate distance to a single goal.

7.14.4 Connecting Static Evaluation to Minimax

When the game tree is too deep to explore to terminal states, the Minimax algorithm is run with a depth limit. At the cutoff depth, static evaluation values are computed for the non-terminal leaf nodes. Minimax then propagates these estimated values upward exactly as it would propagate true terminal utilities. The resulting root value is an estimate of the guaranteed score, whose accuracy depends on the quality of the static evaluation function. The modified algorithm is called Heuristic Minimax (\(\text{H-Minimax}(s, d)\)), where \(d\) is the current search depth and a cutoff test (Is-Cutoff) replaces the terminal test.

However, depth-limited search with static evaluation introduces a critical pitfall: the evaluation function should be applied only to positions that are quiescent — positions with no pending moves (such as an imminent queen capture) that would wildly swing the evaluation. If search is cut off at a non-quiescent position, the static evaluation may be highly misleading. For example, if White's queen is under attack and can be captured on the very next move, a material-only evaluation still counts the queen as White's asset. To handle this, programs employ a quiescence search: even after the depth limit is reached, the search continues for a restricted set of moves (typically capture moves) until a quiescent position is achieved.

A subtler problem is the horizon effect: when a player faces an unavoidable damaging move from the opponent, they may use delaying tactics (e.g., sacrificing pawns with checks) that push the damaging outcome beyond the search horizon. The program then sees only the delaying moves and mistakenly believes the damage has been avoided. One mitigation strategy is to allow singular extensions — moves that are "clearly better" than all alternatives receive extended search depth even beyond the normal cutoff, helping to see through delaying tactics and discover the true outcome lurking just over the horizon.

In the next session, we explore alpha-beta pruning — an optimisation that dramatically reduces the number of nodes Minimax must evaluate while preserving the exact same result. Alpha-beta pruning maintains bounds \(\alpha\) (the best value found so far for MAX along the current path) and \(\beta\) (the best value found so far for MIN), and prunes branches that cannot possibly influence the final decision. With perfect move ordering, alpha-beta can search a tree approximately twice as deep as plain minimax in the same amount of time.
