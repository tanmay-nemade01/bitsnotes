3.1 End-to-End Machine Learning Lifecycle

Machine learning operations brings machine learning together with operations, borrowing the best habits from DevOps and applying them to models. The same release discipline used for ordinary software — versioned builds, staged rollouts, health checks — gets pulled into model work so a model can move from an experiment to a service that clients trust. Ready-made platforms package this idea. Azure pairs its machine learning services with its DevOps tooling to give an MLOps path, and AWS offers an exclusive deployment suite for machine learning called SageMaker.

Hook: A model that scores 99 percent in a notebook can still fail every real client. What breaks between the notebook and the client — and which discipline stops it from breaking?

The gap between notebook and production is where MLOps lives. In a notebook, data sits still, one person runs the code, and a bad prediction costs nothing. In production, data keeps moving, many clients call at once, and a bad prediction can block a checkout or misprice risk. MLOps answers with release discipline: version each build, roll it out in stages, and check its health nonstop. Teams that already live on Azure use Azure Machine Learning with Azure DevOps pipelines, while teams on AWS serve and manage models through SageMaker endpoints.

3.1.1 Stages in Order

Work starts with the business owners or stakeholders sharing the actual problem and what they expect at the end. A team of data engineers, data scientists, and ML engineers then frames the ML problem, collects data, cleans it, and shapes the features that matter. Next comes algorithm choice — linear regression for a regression task, logistic regression, a random forest classifier, XGBoost, or an ensemble — followed by building the first version of the model. Data gets split into train, test, and a slice for evaluation, and the cycle repeats for many rounds until the model is fully functional. Once the model is ready it ships as a service: an endpoint URL with API access, where a client sends an input for inference and gets back a prediction.

The lifecycle in order: frame the problem, collect data, clean it, engineer features, pick an algorithm, split the data, train and iterate, deploy as an endpoint, then monitor. Each gate has a pass rule: framing needs a measurable target, data needs a quality check, training needs a held-out score above the bar, and deployment needs a health check before clients arrive.

Exam note: expect questions that walk this full order — frame, collect, clean, engineer features, pick an algorithm, split, iterate, deploy, monitor — and ask what happens at each gate. Recap: MLOps is release discipline for models, and every stage gates the next.

3.1.2 Health Checks and Observability

A deployed model needs a health check, called its state of health. The question is simple: is the model giving clients what they expect, every time? Sometimes a client calls and the model never answers, the classic status code 404, so teams insist on seeing status code 200 OK on every call. Once live, the team collects traces, logs, and metrics from the deployment cluster, which is model monitoring. Two open-source tools do most of this work and are often named as a pair: Prometheus and Grafana. Teams that want an exclusive stack can run the ELK stack — Elasticsearch, Logstash, and Kibana — and can add Loki to a Prometheus and Grafana setup. Think of it like a hospital monitor: the model is the patient, and the metrics stream is the heartbeat line the team watches around the clock.

Scope: A 200 OK status proves the endpoint answers; it says nothing about answer quality. A model can return 200 OK with predictions that are all wrong. Health checks guard availability, while accuracy, drift, and bias signals guard correctness — a team needs both before it trusts a deployment.

Latency, error rate, and prediction spread join the same dashboard. A sudden jump in average response time hints at an overloaded instance; a spike in 404 or 500 codes hints at a broken route or a crashed container; a shift in the prediction mix hints that the input world moved. Prometheus scrapes these numbers on a schedule, Grafana draws them as live panels, and Loki keeps the raw log lines behind each spike so the on-call engineer can trace a red panel back to its cause.

3.1.3 The Loop Never Runs Once

This lifecycle is iterative, never one-shot. When the deployed model answers but its answers are wrong, the team pings the data scientists, who spring into action and recheck the data, the preprocessing, and the algorithm fit. Only when the final model performs at 100 percent of what was agreed does the loop rest. One way to picture the rhythm is a relay race: the baton passes from business framing to data to modeling to deployment to monitoring, and any dropped handoff sends the baton back for another lap.

Pitfall: Treating deployment as the finish line. A team that ships and stops watching misses the slow decay in input quality that drags scores down over weeks. A second trap is paging the wrong squad: a wrong answer is a data science problem (recheck data and fit), while no answer at all is a platform problem (recheck routes and containers). Mixing the two wastes the first hour of every incident.

Recap: MLOps ports DevOps release discipline onto models so a notebook experiment can grow into a trusted service. Bridge: With the loop in view, the next stop is the step the lecture calls most important — framing the business problem before any data moves.

3.2 Framing the Business Problem

Understanding the problem is the most important step, because every problem is bespoke. Two clients may look similar from far away, yet no two problems are identical once work begins: the data differs, the daily routine of the business differs, and the value the client wants differs. The team has to learn the length, breadth, and depth of the problem, since shipping a deployment that adds no business value helps nobody. A useful habit is to start from a 10,000-feet view where everything looks trivial, then dive into the particulars, because the fine detail is where the true shape of the problem shows up.

Hook: Two shops both ask for a "demand forecast" and both hand over sales tables. One needs hourly bread counts for tomorrow morning; the other needs next-quarter warehouse space. Same request on the surface — so why would the same model fail one of them?

The answer sits in the particulars: different horizons, different costs of being wrong, different data rhythms. The 10,000-feet view lumps both asks into "forecasting" and hides those splits. Framing forces the team to name the decision the prediction will drive, who acts on it, how fast they must act, and what a miss costs. That detail decides the metric, the bar, and even whether machine learning is needed at all.

3.2.1 Goals Worth Chasing

The target has to be achievable with a plain path to production: feasible, viable, and doable in full. Technology keeps shifting and fresh challenges keep arriving, so the team thinks aloud about the best option that can actually be finished. Stakeholder expectations get nailed down early — what the business problem is, what value looks like, and how the team will satisfy the people who own the outcome. Midway surprises get absorbed rather than wished away: if the client asks for a process step to be streamlined so cycle time shrinks, the plan bends to include it.

Scope: A goal counts as well-framed only when it names a measurable outcome, a deadline, and an owner. "Improve recommendations" fails that test; "lift click-through on the home shelf by 2 points within one quarter for the storefront team" passes it. Vague goals drift with each new request, while measurable goals let the team say no to scope that breaks the bar.

Exam note: questions here test whether the goal is measurable and reachable, not just ambitious.

3.2.2 From Business Question to Machine Learning Task

Framing moves through a fixed order. First the requirement and the business question: what does the client need? Then feasibility: what data is in hand, what data is still needed, how many work hours and resources it takes, where the data comes from, how training and inference will run, and what a wrong prediction would cost. Then the team reviews proven or published work on matching problems for guidance. Then comes the metric and its bar, which depends on the use case — some tasks accept an error of 0.01 percent, stated in direct terms as one error in ten thousand predictions. The error rate \(e\) and accuracy \(a\) are complements, where \(e \in [0,1]\) is the share of wrong predictions and \(a \in [0,1]\) is the share of right ones:

\[e = 1 - a\]

so an allowed error of \(e = 0.0001\) means the bar is \(a = 0.9999\). For classification quality the standard scores apply: accuracy is correct predictions over all predictions, precision is true positives over all predicted positives, recall is true positives over all actual positives, and the F-score blends the two:

\[\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}, \quad \text{Precision} = \frac{TP}{TP + FP}, \quad \text{Recall} = \frac{TP}{TP + FN}, \quad F_1 = \frac{2 \cdot \text{Precision} \cdot \text{Recall}}{\text{Precision} + Recall}\]

where \(TP\), \(TN\), \(FP\), and \(FN\) count true positives, true negatives, false positives, and false negatives. Receiver operating curves and the confusion matrix sit beside these scores as further yardsticks the team agrees with stakeholders before modeling starts.

Reading the four scores: Accuracy (\(TP+TN\) over all four cells) answers "how often is the model right overall." Precision (\(TP\) over \(TP+FP\)) answers "when the model raises the alarm, how often is the alarm real." Recall (\(TP\) over \(TP+FN\)) answers "of all real cases, how many did the model catch." \(F_1\) blends precision and recall with their harmonic mean, so a model that games one side at the expense of the other cannot hide: with precision \(P=0.9\) and recall \(R=0.3\), the score is \(F_1 = 2 \cdot 0.9 \cdot 0.3/(0.9+0.3) = 0.54/1.2 = 0.45\), much closer to the weak side than an ordinary average of 0.6 would suggest.

Worked example — the 0.01 percent bar in counts: A fraud team scores \(n = 10{,}000\) transactions a day with an allowed error of \(e = 0.0001\). Expected misses per day \(= e \times n = 0.0001 \times 10{,}000 = 1\), so the bar means about one wrong call a day and accuracy \(a = 1 - e = 1 - 0.0001 = 0.9999\). If the same team grew to \(n = 100{,}000\) scored transactions a day, expected misses \(= 0.0001 \times 100{,}000 = 10\) a day at the same bar. Sense-check: a percentage bar is strict in rate but its daily cost scales with volume, which is why stakeholders must sign off on both the rate and the raw miss count.

Worked example — precision, recall, and \(F_1\) from a confusion table: A spam filter test yields \(TP = 80\) caught spam, \(FP = 20\) clean mails flagged, \(FN = 40\) spam missed, and \(TN = 860\) clean mails passed. Then accuracy \(= (80+860)/(80+860+20+40) = 940/1000 = 0.94\); precision \(= 80/(80+20) = 80/100 = 0.80\); recall \(= 80/(80+40) = 80/120 \approx 0.667\); and \(F_1 = 2 \cdot 0.80 \cdot 0.667/(0.80+0.667) \approx 1.067/1.467 \approx 0.727\). Sense-check: accuracy looks strong at 0.94, but recall near 0.67 shows one in three spam mails still slips through — exactly the gap \(F_1\) at 0.73 exposes.

Then the team defines the actual ML task from the business problem, names the pain points and critical features, and starts small with a proof of concept. That early build gets validated sitting with the subject matter experts on the client side, and only a build they accept as a good candidate moves to full development. Two build styles exist: throwaway prototyping, where the team learns from a prototype and then starts fresh, and evolutionary prototyping, where the prototype grows into the product. Sometimes the honest answer is that the business needs no ML at all — a set of plain business rules gives a better outcome — and the team should say so. The path to production stays hard even with a good prototype, because a model that behaved well in staging can act strange in production, crash, or underperform, so the team plans for trial and error and keeps stakeholders aligned throughout. Response pressure gets quantified early: if concurrent users grow from 1,000 to 100,000, a factor of one hundred, the model and its serving stack must scale without letting performance drop.

Pitfall 1: Picking the metric after the model is built, which lets the team crown whichever score looks best. Fix: agree the metric and its bar with stakeholders before training, and write down what a wrong prediction costs in money or delay. Pitfall 2: Growing a throwaway prototype into production because it "already works" in a demo. Throwaway code skips logging, tests, and version pins; evolving it carries that debt into production. If the plan is to ship the prototype, choose evolutionary prototyping from day one.

Fraud scoring teams set bars like 0.01 percent error because each miss costs money, while a media recommender may accept far looser bars because a weak suggestion only costs a scroll. That contrast is the whole point of framing: the use case sets the bar, the bar picks the metric, and the metric decides whether the proof of concept earns full development.

Recap: Framing turns a business ask into an ML task with a metric, a bar, and a proof of concept that experts accept. Bridge: Once the task is fixed, the team hunts for data — which arrives from everywhere and must be pulled into one consumable shape.

3.3 Data Collection and Ingestion

Data arrives from anywhere: a legacy database, a mainframe, a distant API, an edge server, a cloud bucket, or a distant GPU host. The art of data handling is turning those shapes into one consumable form, and data engineers play the central role, gathering inputs from every source and shaping them into the target dataset the model will consume.

Hook: A model is only as fresh as the slowest pipe feeding it. If click events arrive in milliseconds but the product catalog lands once a night, which prediction can the team trust at noon?

Only the prediction whose inputs are all fresh at serving time. A noon recommendation built on last night's catalog silently ignores every product added this morning. Ingestion design is really a freshness contract: name each source, its arrival rhythm, and the latest snapshot the model may use, then build the pipes so the slowest critical source still lands in time.

Exam note: expect a question that lists mixed sources and asks how they become one training-ready dataset.

3.3.1 Intake Patterns

Collection runs in three patterns. Streaming ingestion takes events as they arrive, batch ingestion lands data in chunks, and aggregation merges streams and batches into unified views. Kafka clusters carry streaming loads, while a hosted option on AWS is Kinesis. From there, extract-transform-load pipelines move the data, catalogs record what each feed means, a data lake holds the raw and shaped copies for processing, and databases such as MySQL, Snowflake, or Postgres serve the working copies. Data may be structured or unstructured, so the team keeps a full picture of the journey from first arrival to the moment a model consumes a row.

The three intake patterns and when each fits: Streaming suits signals that decay in seconds, such as fraud flags or live prices. Batch suits signals that settle on a schedule, such as nightly sales or end-of-day positions. Aggregation suits decisions that need both, such as a morning risk report built on overnight batches plus the first hour of live trades. Pick the pattern by how fast the decision goes stale, not by which tool the team likes most.

Scope: A catalog entry is load-bearing, not paperwork: owner, refresh cadence, schema version, and known gaps. Without it, two teams read the same lake path with different meanings of one column, and their models quietly disagree. Every feed merged in aggregation needs a catalog row before it enters the lake.

3.3.2 Preparing Data for Use

Preparation makes data ready to consume: preprocessing, exploratory analysis, and feature engineering. Exploratory data analysis means looking at the data with a deep lens through visualization — Tableau and Power BI are common choices — to spot the patterns that tables hide. Preparation tooling with no-code, low-code, or visual options cuts the cost of this interactive analysis. If this step drifts, inference later suffers, so the team treats preparation as load-bearing work rather than warm-up. Retail teams blend point-of-sale batches with clickstream events into one lake before any model sees them.

Pitfall 1: Skipping the visual pass and trusting summary statistics. Averages hide skew, gaps, and duplicated feeds that a single histogram exposes in seconds. Pitfall 2: Treating preparation as one-off janitor work. Every new source, schema change, or season reopens the same checks; teams that automate the checks catch the drift, while teams that eyeball it once ship stale assumptions into every later stage.

Recap: Ingestion turns scattered sources into one cataloged, consumable dataset with a known freshness contract. Bridge: Once the data lands in one place, cleaning decides whether it is fit to learn from — because no algorithm rescues bad inputs.

3.4 Data Preparation and Cleaning

Model quality tracks data quality directly: good data in, good model out, and the reverse just as fast. When the data is not in good shape, no algorithm rescues it. Cleaning then follows a fixed order — clean, then partition, then scale — followed by bias checks and augmentation, so each step builds on a sound base.

Hook: Two teams train the same model on the same raw lake. One scores 0.92 on launch; the other scores 0.71. Same algorithm, same data — what single step explains the gap?

Almost always the cleaning order. The losing team scaled before deduplicating, or tuned on rows that leaked from the test slice, so its high validation score measured memorization rather than learning. Cleaning is not cosmetic: it decides what the model is allowed to learn from.

3.4.1 Cleaning Steps in Order

Cleaning starts by taking stock of what is in hand. Lucky teams get a dataset with no missing values, no NaNs, and no outliers; most teams clean, balance, replace, impute, partition, scale, augment, and unbias. Concretely the team removes duplicates and irrelevant rows, fixes inaccurate entries, fills gaps with imputation, and cuts bias as part of the same pass. Then the data is split at random into three disjoint parts — train, validation, and test — written as:

\[D = D_{\text{train}} \cup D_{\text{val}} \cup D_{\text{test}}\]

where \(D\) is the full dataset and the three parts share no rows, so the model learns on \(D_{\text{train}}\), gets tuned against \(D_{\text{val}}\), and is judged on unseen \(D_{\text{test}}\). Scaling follows: normalization and standardization for algorithms that feel the shape of the data, such as K-nearest neighbors, K-means clustering, principal component analysis, and gradient descent, with extra standardization when many outliers are present. Finally the team balances the classes and, when data is scarce, synthesizes new rows from old ones — synthetic augmentation that regularizes training and trims overfitting, though large datasets still demand sizable time, compute, and work hours. Think of this order like prepping a kitchen: wash first, then sort, then measure, since measuring dirty produce wastes the whole recipe.

Why the order is clean, then partition, then scale: Deduplicate and impute first so the split works on honest rows. Split second so scaling statistics come from the training slice alone. Scale last so validation and test rows are transformed with training numbers, never their own. Any other order lets test information leak into training through shared means, shared neighbors, or twin rows.

Worked example — a clean split with honest scaling: A team holds \(n = 10{,}000\) labeled rows and splits 70/15/15, giving \(7{,}000\) train, \(1{,}500\) validation, \(1{,}500\) test. Step 1: drop 200 duplicate rows, leaving \(9{,}800\), then split into \(6{,}860\) / \(1{,}470\) / \(1{,}470\). Step 2: compute the training mean age \(\mu = 34.2\) years and standard deviation \(\sigma = 9.6\) on the \(6{,}860\) training rows only, then map every slice with \(z = (x - 34.2)/9.6\). A 44-year-old test customer becomes \(z = (44 - 34.2)/9.6 \approx 1.02\). Sense-check: test rows never set \(\mu\) or \(\sigma\), so the test score measures learning, not leakage.

Scope: Normalization (rescaling to a fixed range) and standardization (zero mean, unit spread) both assume the training slice represents deployment. Under heavy outliers the mean drifts, so robust scaling with medians wins; under shifting seasons even robust statistics go stale and the team must recompute them on fresh data. Scaling fixes geometry, never representativeness.

3.4.2 Leakage and Bias Traps

The trap to avoid is data leakage, where facts from the held-out test set creep into training and flatter the scores. The fix is procedural: drop duplicates before splitting, so no test row has a twin in the training rows. Bias gets the same strict treatment — detect it, mitigate it, and recheck, since biased inputs harden into wrong outputs.

Correction — "more data fixes weak data": A team argued that feeding extra rows would compensate for dirty labels. The professor rejected the trade: model quality tracks data quality directly, so volume amplifies whatever the labels teach — clean labels teach the pattern, dirty labels teach the noise. The fix is cleaning order, not row count; augmentation only helps after the base labels are sound.

Pitfall: Leaking through preprocessing — imputing with the full-column mean, selecting features on all rows, or balancing before the split. Each step peeks at held-out rows and inflates the score. The rule is one sentence: every number learned from data (means, encodings, selected features) is learned on the training slice and frozen before touching validation or test.

Exam note: leakage questions describe a pipeline and ask where the test facts slipped in; the answer is any step that peeks at held-out rows before the split. Recap: clean first, split into disjoint parts, scale with training statistics — and recheck bias at every pass.

Bridge: Clean, disjoint data is ready for its next upgrade — turning raw columns into features that carry real signal.

3.5 Feature Engineering and Feature Stores

A feature is one useful attribute of the data, and feature engineering is the craft of making raw columns model-ready: create, transform, extract, and select. This stage is very high value, because the right features carry more signal than a fancier algorithm on raw inputs.

Hook: Feed raw timestamps and free-text job titles into a model and it stalls; feed hour-of-day plus a clean job code and the same model jumps in score. Same rows, same algorithm — what changed?

The representation changed. Raw columns bury the pattern under noise — timestamps mix date with hour, titles mix seniority with typos. Engineering pulls the pattern to the surface: hour of day captures the commute rush, cleaned codes capture seniority, and the model finally sees what was always there. Features translate the world into a language the algorithm can read.

3.5.1 Create, Transform, Extract, Select

Creation builds fresh variables from existing ones for stronger prediction: one-hot encoding for categories, binning for ranges, splitting combined fields, calculated features from weights, Cartesian products of columns, and nonlinear transforms shaped by the domain. For one-hot encoding, a category \(c\) from \(K\) options becomes a vector \(\mathbf{x} \in \{0,1\}^K\) with a single 1 at position \(c\) and 0 elsewhere. Extraction then shrinks what is too wide: an \(N\)-dimensional row is reduced to a compact form so memory and compute stay sane, using methods such as PCA, ICA, and LDA. In deep learning this extraction happens inside the network itself, where layers of neurons learn the reduced form as part of training. Selection closes the loop by keeping only features that cut the error rate, scored with correlation matrices and contribution measures, while the rest are dropped. A credit model may bin ages into bands, one-hot encode job codes, and keep only the dozen features whose correlation with default survives selection.

The three extraction methods side by side: PCA (principal component analysis) keeps the directions of largest spread with no labels needed. ICA (independent component analysis) separates mixed signals into independent sources, such as voices in a crowded room. LDA (linear discriminant analysis) keeps the directions that best separate the labeled classes. Choice rule: no labels and wide rows points to PCA; mixed sources points to ICA; labeled classes and a separation goal points to LDA.

Worked example — one-hot plus binning on one customer: A customer is 34 years old with job code "teacher" among \(K = 4\) codes (driver, nurse, teacher, clerk). Binning maps age 34 into bands [18-25, 26-35, 36-50, 51+], giving band index 2 of 4. One-hot for the band is \([0, 1, 0, 0]\); one-hot for the job is \([0, 0, 1, 0]\). Concatenated, the customer becomes \([0, 1, 0, 0, 0, 0, 1, 0]\). Sense-check: exactly two 1s (one per field), every other slot 0 — the model now sees band and job as separate comparable switches.

Worked example — extraction that shrinks a wide row: A transaction row carries \(N = 1{,}000\) raw counters. PCA keeps the top \(d = 20\) directions of spread, so each row compresses from \(1{,}000\) numbers to \(20\) — a 50-fold cut in width. Memory for one million rows falls from about \(1{,}000 \times 10^6 = 10^9\) values to \(20 \times 10^6 = 2 \times 10^7\) values. Sense-check: downstream training runs roughly 50 times leaner per pass, and the kept directions hold the spread that mattered most.

Scope: Extraction keeps the strongest patterns and discards the rest — including rare but costly signals. A fraud flag that fires once in a million rows may vanish inside the top PCA directions. When rare classes carry the business cost, keep supervised selection (correlation with the target, LDA directions) alongside unsupervised compression, and confirm the rare signal survives the cut.

3.5.2 Online and Offline Stores

Finished features live in a feature store, and there are two kinds. The online store serves features at once for low-latency reads and real-time inference; the offline store serves batch scoring and end-of-day jobs where waiting is fine. Banking shows the split: end-of-day instrument runs across the whole bank can wait for the batch window, while a stock ticker that moves every second needs instant feature reads. The use case picks the store, and pipelines often feed both from the same preparation code.

Dimension Online store Offline store
Reads single-row, millisecond lookups bulk scans, minutes to hours
Writes fresh values on every event nightly or hourly batches
Serves live inference per request batch scoring, training backfills
Miss cost stale value poisons this prediction stale snapshot poisons the whole batch

Pitfall 1: Training on offline features and serving online cousins computed by different code — the classic train-serve skew. One pipeline must feed both stores or scores drift on day one. Pitfall 2: Picking the store by fashion instead of latency math. If the decision must land in 50 ms, the offline store cannot serve it; if the job runs overnight, paying for millisecond reads buys nothing.

Exam note: a question may give a latency need and ask which store fits — instant means online, overnight means offline. Recap: engineer (create, transform, extract, select), then serve each feature from the store whose latency matches its decision.

Bridge: Modeled features flow into training next, where the algorithm choice and its tuning knobs decide how far the signal carries.

3.6 Model Training, Tuning and Validation

Training runs the chosen algorithm on the prepared data and tunes it until the scores hold. The learning rate \(\eta\), a small positive step size, controls how far each update moves; the epoch count \(E\) counts full passes over the training data; hidden layers and their unit counts plus activation choices shape neural networks. Tuning these hyperparameters is what bends a generic algorithm onto the business problem at hand.

Hook: The same network trained twice can land once at 0.90 and once at 0.62. Same data, same code — which two knobs most often explain the split?

The learning rate and the training length. Too large a step size overshoots the valley and the loss swings or blows up; too small a step crawls and the run stops before learning finishes. Too few epochs underfit, too many memorize. Training is steering: the algorithm is the engine, the hyperparameters are the wheel, and tuning keeps the run on the road.

Exam note: expect tuning questions that name a symptom — slow learning, unstable loss — and ask which knob to turn first.

3.6.1 The Training Loop

The loop runs: pick features, write the code, pick the algorithm, train, debug and profile, validate with visualizations, tune hyperparameters, and pack the run as a training container. Training containers are custom images built on a base image, pushed to a local registry, and shared so every team trains the same version. The finished run emits the model artifact plus metadata into the model registry. Large training gets split two ways. Data parallelism slices the dataset into small batches spread across nodes, so each node trains on a fraction of the data and wall-clock time falls. Model parallelism slices the model itself across devices or nodes for models too big for one machine. Debugging runs alongside: profile for system bottlenecks, watch for overfitting and saturated activations such as ReLU, track vanishing gradients, and compare candidate models head to head on precision, recall, and accuracy before declaring a fit. No first run is a perfect fit, so the team plans many iterations as a matter of course.

Purpose: turn prepared features into a fitted model that holds on unseen rows. Inputs: versioned features, the algorithm choice, and a hyperparameter grid (\(\eta\), \(E\), depth, width, activation). Outputs: the artifact plus metadata (data snapshot, code version, scores). Steps: select, code, train, profile, validate, tune, pack — then repeat until the validation curve flattens instead of climbing.

Trace — data parallelism on a concrete run: A team trains on \(n = 1{,}000{,}000\) rows with \(p = 10\) nodes and a per-node batch of \(b = 1{,}000\) rows per step. Each step covers \(p \times b = 10 \times 1{,}000 = 10{,}000\) rows, so one epoch of \(1{,}000{,}000\) rows needs \(1{,}000{,}000/10{,}000 = 100\) steps. On one node the same epoch would need \(1{,}000{,}000/1{,}000 = 1{,}000\) steps. Sense-check: ten nodes cut the step count tenfold, minus the sync cost the team profiles per step.

Trace — learning rate symptom to fix: A run with \(\eta = 0.5\) swings loss 2.4, 1.1, 3.8, 0.9 across four steps — the classic overshoot signature. The team cuts \(\eta\) to \(0.05\) and loss falls steadily 2.4, 2.0, 1.7, 1.5. A second run with \(\eta = 0.0001\) barely moves loss 2.40, 2.39, 2.38 after three epochs — the crawl signature — so the team raises \(\eta\) toward 0.01 and adds epochs until validation flattens. Sense-check: swings mean shrink the step; stillness means grow it or train longer.

When to use which split: Data parallelism fits when the data is huge but the model fits on one device — add nodes, shrink wall-clock time. Model parallelism fits when the model itself outgrows one device — split layers across devices even for modest data. Alternatives for small budgets: fewer, larger batches on one GPU; mixed precision; or a smaller architecture that trains end to end without any split.

3.6.2 Gates Before Production

Before anything ships, the team holds data aside and checks the model offline: are the annotations right, do the scores clear the yardstick, does any slice fail? If training-level performance lags, retraining triggers at once — fresh cleansing, fresh data, or features rebuilt from scratch — because moving a weak model forward only moves the failure forward. A dry run through the pre-production pipeline rehearses every automated fetch from the online and offline stores plus continuous integration, delivery, testing, and training in phases. Manual governance then signs off that the model is fully tested and evaluated before it is released. Think of this gate like a flight check: the crew would rather find the fault on the ground than over the ocean.

Pitfall 1: Promoting on headline accuracy while one slice fails — a model at 0.94 overall can score 0.55 on the newest region. Slice the offline check by time, region, and segment before sign-off. Pitfall 2: Skipping the dry run because staging "looked fine." Staging hides fetch delays, permission gaps, and store mismatches that only the full pre-production path exercises.

Recap: train in a versioned container, split the work by data or by model size, tune \(\eta\) and \(E\) against validation, and pass the offline gate before release. Bridge: A tuned model still needs a durable home — a registry and a container that any team can rerun.

3.7 Model Registry, Serialization and Containers

A trained model is not shipped as loose code. It is saved, versioned, wrapped, and packed so any team can rerun the exact same artifact. Parallel squads — on-site and off-site groups sharing one delivery center — all pull the same version, which is why the registry copy is the source of truth rather than any one laptop.

Hook: A teammate reruns your training script and gets a different model. Same code, different weights — where did the run diverge, and which single habit prevents it?

The run diverged in something the script never pinned: the data snapshot, the library version, or the random seed. Saving loose code preserves none of those. The registry habit prevents it: store the artifact with its data, code, and parameters as one versioned bundle, so rerun means repulling the bundle instead of replaying memory.

3.7.1 Saving Versions That Teams Share

After training, the model version goes into a model registry with its data snapshot, code, and parameters. GitHub is not the place for this: it versions code with branches and merges, but it was never designed to store model artifacts. The registry is the dedicated counterpart — one versioned home for the artifact every team consumes — while code stays in Git and models stay in the registry. Getting this split right avoids the mix-up where a model binary lands in a code repo and nobody can reproduce the run. The registry split is a terminology contrast worth keeping straight: code versioning belongs in Git, while versioned model artifacts belong in the model registry.

Correction — "just commit the model to Git": A squad proposed versioning a 4 GB weight file with branches and merges. The lecture rejected the move: Git tracks line-based code diffs and balloons on binaries, so clones slow, diffs turn meaningless, and no two teams can tell which weights pair with which data. The replacement: code and configs live in Git; the artifact with its data snapshot, parameters, and metrics lives in the registry, and the registry version ID is the name every team cites.

Pitfall: Storing the weights but not the snapshot — the artifact without its data version is a name without an address. Log the dataset hash, the code commit, the seed, and the metric set with every registry entry, or a future retrain compares numbers that never shared a starting line.

3.7.2 From Serialized Model to Container

A model never deploys raw. The serialized form — a joblib or pickle file, an ONNX file, a PMML file, or an .h5 file for dense inputs such as images — joins the dataset snapshot and a wrapper application, and the three pack into one bundle: a container. Container engines for the job include Docker, Podman, CRI-O, Rocket, containerd, LXC, LXD, and Kata containers. Docker's community edition is free while production use needs a paid license under Mirantis, which took over Docker some years back; Podman works as an open equivalent of Docker and suits early builds. Model serving then leans on registries the team already knows: the public Docker Hub pattern for shared images, and a private local registry such as Quay.io for sensitive projects that must never sit on a public index. Banks keep model images in private registries so client data and weights never touch a public index.

The three serialization formats and when each fits: Pickle and joblib carry Python objects fast within one stack — fine for a team that trains and serves in the same Python version (joblib handles large NumPy arrays better). ONNX carries the computation graph across frameworks, so a PyTorch model can serve in a non-Python runtime. PMML carries classical models (trees, regression, clustering) as XML for scoring engines in banks and telcos. The .h5 (HDF5) form carries dense deep-learning weights, standard for image models moving between training and serving.

Worked example — what one registry entry holds: Version churn-v7 stores weights model.joblib (85 MB), dataset hash sha:9f31, code commit a4c2e1, parameters max_depth=6, eta=0.05, and metrics F1=0.81, recall=0.77. Any squad pulling churn-v7 reruns the same bytes on the same snapshot — no laptop lottery. Sense-check: change any one field and the version ID must change, or two different models share one name.

Pitfall 1: Shipping a raw pickle with no wrapper — the server then imports training-only code paths and breaks on the first odd input. Wrap inference in a small application with input checks, then pack all three parts. Pitfall 2: Pushing a sensitive image to a public hub for convenience. Once weights and schema leak, they cannot be unleaked; private registries such as Quay.io exist exactly for this boundary.

Recap: Git versions code; the registry versions artifacts; the container ships both plus the wrapper. Bridge: A packed model still needs a release pattern — who sees the new version first, and how the team pulls it back if it misbehaves.

3.8 Deployment Strategies for Production

Releasing a model means exposing an endpoint the client application calls, and the release pattern decides who sees the new version first. Four patterns cover almost every rollout: blue-green, canary, A/B testing, and shadow. The team picks by risk appetite — how many users may meet a bad model before anyone notices.

Hook: The new model beats the old one on every offline slice. Ship it to everyone at midnight — what is the cheapest way that decision turns into a morning-long outage?

One bad input shape in live traffic that never appeared offline: a longer text field, a new category code, an empty image. Full cutover hands that input to every user at once. Staged patterns exist so the first encounter involves five percent of traffic or zero users — never all of them.

Exam note: strategy questions usually describe a rollout and ask for its name, so learn the traffic shape of each.

Pattern Who sees the new version Exposure Roll back by
Blue-green all traffic after the switch full at flip time flipping back to blue
Shadow nobody (scores logged only) zero users deleting the shadow
Canary a small group first tiny share, then growing draining the canary
A/B testing split groups over weeks fixed shares per variant routing all to the winner

3.8.1 Blue-Green and Shadow

Blue-green keeps two identical production environments. Blue serves the live traffic while green hosts the new version under test; when green proves itself as a replacement, traffic shifts over part by part until green is the new live side. Red and black is used as a synonym for the same pair. Shadow runs the new version beside the old one in parallel: the old version keeps serving production while the new one digests the same inputs for testing and analysis only. Shadow is the cautious choice when the team wants evidence with zero user exposure. One warning travels with every rollout here: deployment is where the music starts, because a model that behaved in staging can turn strange in production — crashing, answering wrongly, or freezing — and the team must be ready with a path back.

Warning carried forward: "Deployment is where the music starts" — staging-calm models meet live shapes, live load, and live permissions for the first time. A model that behaved in staging can crash, freeze, or answer wrongly in production. Every pattern above must pair with a rehearsed rollback: keep the old environment warm, keep the old weights pinned, and name the single command that restores them.

Scope: Blue-green needs two full environments, so it doubles serving cost during the switch — fine for stateless APIs, painful for GPU-heavy models. Shadow needs mirrored traffic and doubled inference spend with no user impact at all, so it suits high-stakes scorers (credit, safety) where evidence must precede exposure. Neither pattern measures which version users prefer; that question belongs to A/B testing.

3.8.2 Canary and A/B Testing

Canary hands the new version to a small group first — a special interest or expert group that judges the candidate — and only a pass from them opens the full rollout. The traffic share stays tiny at first, such as a share \(f_{\text{new}} \in [0,1]\) of requests with \(f_{\text{new}} \ll 1\), where \(f_{\text{new}}\) is the fraction of live requests routed to the new version. The name carries a story: in earlier decades miners carried a caged canary deep underground, and because the small bird is sensitive to poisonous gas released during digging, its distress warned the crew to leave at once — the bird gave its life at gas levels humans could not yet feel, and modern gas sensors now do the same job. A/B testing widens the same idea to large groups over weeks or months, splitting a portion of traffic to variant A and the rest to variant B. Social platforms use it across regions, serving one variant in Asia-Pacific, another across EMEA, and another in the Americas while routing each audience accordingly. A checkout team canaries a pricing model on staff accounts, then A/B tests it across regions before full release.

Analogy kept: the miner's canary maps exactly onto the rollout — a small, sensitive group meets the danger first and its distress (error spikes, complaints, metric dips) warns the crew before the whole mine breathes the same air. The mapping breaks at one point: miners could not save the bird, but teams keep the old version warm and drain the canary at the first alarm.

Worked example — canary arithmetic: A checkout API serves \(n = 200{,}000\) requests a day. The team sets \(f_{\text{new}} = 0.02\), so the canary sees \(0.02 \times 200{,}000 = 4{,}000\) requests a day while \(196{,}000\) stay on the old version. The pass rule: error rate on the canary slice stays within 0.1 points of baseline for three days. Day-one canary errors \(= 0.008 \times 4{,}000 = 32\) versus baseline \(0.007 \times 4{,}000 = 28\) — a gap of 4 excess errors, inside tolerance, so the team grows \(f_{\text{new}}\) to 0.10. Sense-check: at most a few dozen users ever meet a bad canary, never hundreds of thousands.

Pitfall 1: Canarying on staff or friendly accounts and calling it representative — staff inputs differ from live traffic, so a staff-passed canary can still fail the public. Graduate from staff to a random live slice before full release. Pitfall 2: Reading A/B results after one day on a weekly cycle — weekend buyers differ from weekday buyers, so short tests enshrine day-of-week noise as a winner. Run A/B across full business cycles.

Recap: shadow proves with zero exposure, canary proves on a small slice, A/B proves preference at scale, blue-green flips the fleet. Bridge: Once live, every pattern needs the same watch — monitoring that catches drift before clients feel it.

3.9 Monitoring, Drift and Retraining

Once live, the model enters post-deployment monitoring: capture system data, spot trouble, and fire alerts before clients feel pain. Monitoring watches data quality, model quality, bias drift, feature attribution drift, explainability, and soundness — whether each prediction can be tested against what the team expects. This watch runs 24 hours a day, 365 days a year, because production never sleeps.

Hook: A model holds 0.98 accuracy at launch and nobody touches it for a year. Should the team celebrate the stability — or worry about it?

Worry. Inputs shift, tastes move, sensors age, and a frozen model silently drifts from the world it learned. Unmonitored stability is usually unmeasured decay. The teams that celebrate are the ones whose dashboards prove the score each day — not the ones who assume it.

Exam note: monitoring questions reward the team that names the exact signal — data, quality, bias, attribution — rather than answering "performance" in general.

3.9.1 What Gets Watched

The deployment cluster streams inputs, predictions, and serving health into the monitoring stack. An alarm manager watches the stream and publishes to every channel the on-call rotation needs: chat channel messages, text messages, and phone calls to the target groups that own the fix. Retraining and maintenance jobs get scheduled in lean hours so client productivity never takes the hit. If the alarm manager flags a violation, it launches the model update pipeline at once: reprepare the data, rerun the feature pipelines, retrain through integration, delivery, and training automation, and hand the fresh model back for inference. After retraining, the new version is rechecked for data quality, explainability, and bias before it is allowed near production.

The six watched signals and what each catches: Data quality (missing, out-of-range, or duplicated inputs) catches broken pipes. Model quality (accuracy, precision, recall on labeled samples) catches real decay. Bias drift catches slices that start failing while the headline holds. Feature attribution drift catches inputs whose influence moved — a sign the world changed even if scores have not yet. Explainability catches predictions no reviewer can justify. Soundness catches outputs outside testable bounds, such as negative prices or probabilities above one.

Worked example — the alarm path end to end: At 02:10 the prediction mix shifts: approvals fall from 62 percent to 41 percent in one hour while inputs hold steady. The alarm manager pages the owning group by chat at 02:11 and by phone at 02:16 under the escalation rule. A lean-hours retrain launches at 03:00 on the last 14 days of labeled data, and the challenger scores \(F_1 = 0.83\) versus the live model's \(0.71\) on the same slice. The challenger passes data quality and bias checks at 05:40 and takes 10 percent of traffic by 06:00. Sense-check: detection to mitigation inside one night, and clients never meet the degraded model at peak hours.

Scope: Monitoring proves the model matches its contract; it cannot prove the contract is right. If the business goal moved (new fraud shape, new price bands) while the metric stayed, green dashboards guard the wrong target. Review the metric and its bar alongside the signals each quarter, or the watch stays sharp on a stale mission.

3.9.2 Drift Math and the Retraining Loop

Drift is the slow poison. Picture a model scoring an accuracy of \(a_0 = 0.98\) at launch and sliding to \(a_1 = 0.60\) three months later, a drop of:

\[\Delta a = a_0 - a_1 = 0.98 - 0.60 = 0.38\]

thirty-eight percentage points gone. The recovery plan retrains on fresh data to climb back toward \(0.85\) to \(0.90\). Underneath sit two distinct failures. Data drift means the input distribution shifted; concept drift means the properties the model relies on changed; sometimes both arrive together, and model performance degrades either way. Because datasets go stale, the team defines retraining frequency up front, keeps the feature pipelines warm, and treats retraining as a standing loop rather than an emergency patch. Think of it like road upkeep: small cracks ignored through one season become potholes by the next, so the crew resurfaces on a schedule instead of waiting for a breakdown.

Data drift versus concept drift: Data drift moves the inputs — the same rule, new crowd (older customers, new devices, changed sensors). Concept drift moves the rule itself — the same inputs, new truth (fraudsters change tactics, tastes flip, prices re-anchor). Diagnosis decides the fix: data drift calls for fresh samples and reweighting, concept drift calls for relabeling and often reframing the task. When both arrive together, fix the inputs first so the new labels measure the new rule on honest data.

Worked example — drift arithmetic with the recovery climb: Launch accuracy \(a_0 = 0.98\) on \(n = 5{,}000\) weekly scored cases means \(0.98 \times 5{,}000 = 4{,}900\) right and \(100\) wrong. At \(a_1 = 0.60\) the same week yields \(0.60 \times 5{,}000 = 3{,}000\) right and \(2{,}000\) wrong — twenty times the weekly misses. Retraining lifts the model to \(a_2 = 0.88\): \(0.88 \times 5{,}000 = 4{,}400\) right, \(600\) wrong. Sense-check: the drop \(\Delta a = 0.38\) cost \(1{,}900\) extra weekly misses, and recovery to 0.88 reclaims \(1{,}400\) of them — worth the retrain, still short of launch, so the frequency review stays open.

Pitfall 1: Retraining on the same stale window and expecting fresh behavior — new runs on old data relearn old patterns. Refresh the window and recheck labels first. Pitfall 2: Retraining without holding the feature code fixed — changed features plus changed weights make the score gap unreadable. Pin the pipeline, change the data, and measure once.

Recap: watch six signals around the clock, page through the alarm manager, and retrain on fresh data in lean hours. Bridge: Retraining only works when the past is rebuildable — which needs lineage, pinned environments, and data the team is allowed to keep.

3.10 Lineage, Reproducibility and Infrastructure

When a model that once performed starts to sag, the team must rebuild the exact past: same data, same code, same environment, same point in time. Lineage tracking makes that possible by collecting references to every traceable change across models, data, and infrastructure resources. Without it, debugging is guesswork; with it, any version can be recreated and its behavior explained.

Hook: A regulator asks why a loan model denied one application last March. The team has the current model — is that enough to answer?

No. The current model learned on newer data with newer code in a newer environment. The answer needs the March bundle: the exact data snapshot, feature list, algorithm version, and platform image behind that single decision. Lineage is the receipt drawer that makes the answer possible months later.

3.10.1 Tracking Every Version

The lineage record covers the data snapshot with its metadata and values, the feature list, the algorithm code with feature and hyperparameters, the implementation around the model and pipeline, and the flow changes across runs. Training containers may number in the dozens across experiments, but the production container is always exactly one version at a given moment, written as \(N_{\text{train}} \geq 1\) training images versus \(N_{\text{prod}} = 1\) live image. If a swap is needed — a new algorithm for an old one — the team records how the newcomer behaves at that point in time and only proceeds when the record supports it. Environmental drift gets the same treatment: when the platform underneath shifts, the team rebuilds the environment rather than trusting memory.

What one lineage record holds: dataset hash plus row counts, feature list with versions, code commit plus hyperparameters, container image digest, platform versions, and the metric set that promoted it. With all six, any past decision replays byte for byte; missing any one, the replay is an approximation and the audit answer stays qualified.

Worked example — one live image among dozens: A squad runs \(N_{\text{train}} = 24\) training images across a quarter while production holds \(N_{\text{prod}} = 1\). In week 9 the live score dips; the team repulls image fraud-v6 (dataset sha:71ac, commit d902, \(F_1 = 0.83\)) and replays the failing day in a sandbox, reproducing the same 41 disputed denials. Sense-check: 24 candidates, one throne — and the throne's receipt makes the failure replayable instead of mysterious.

Scope: Lineage tracks what ran, not whether it was fair or legal. A perfectly reproduced pipeline can still reproduce a biased outcome. Pair the version record with bias and explainability checks per release, or reproducibility certifies the wrong answer with full precision.

3.10.2 Infrastructure as Code and Data Placement

Infrastructure as code defines compute, network, storage, and the application shape in versioned files, and automation then raises the platforms fast with fewer surprises. Terraform is the well-known tool here, now a paid product, with OpenTofu as its drop-in open fork. Placement follows sensitivity. If data must stay inside a region, it stays: when European rules kept customer data inside Europe, cloud vendors had to stand up capacity in-region rather than mirroring to other continents. Highly sensitive material — research data, personal identifiers, health records under HIPAA, card data under PCI DSS, and data under GDPR — stays on-premises in stores such as a private data lake, and private clouds cover teams that need cloud shape without public exposure. Ordinary, non-sensitive workloads may run on the public cloud. A hospital keeps training data on-premises under access controls while serving the approved model from a managed endpoint.

Placement rule in one line: sensitivity picks the home — regulated or identifying data stays on-premises or in-region; ordinary workloads may use the public cloud. Infrastructure as code makes the choice repeatable: the same versioned files raise a compliant region copy and a public copy without hand-tuned drift between them.

Pitfall: Declaring placement once and forgetting it — vendors change regions, laws change borders, and datasets gain sensitive columns over time. Reclassify data and re-attest placement each release, or a compliant design quietly becomes a violation one schema change later.

Recap: lineage pins data, code, features, and environment per version; infrastructure as code pins the platform; placement law pins where each may live. Bridge: With rebuildable versions in place, the lecture assembles the full serving map — the reference architecture that hosts them.

3.11 Supervised Learning Reference Architecture

A supervised learning system splits into production, training, and data processing rather than one client-server pair, and the reference layout names each part and its job. Because every use case is bespoke, teams treat the map as a starting sketch and reshape the layers around their own problem. The cast: an orchestrator that takes each request and delegates it, an evaluator that scores candidates, a model builder that holds the trained model and its versions, a featurizer that prepares the desired features, a server that hosts the model file behind the front end, a database that stores the working data, a monitoring stack that watches metrics, logs, and traces, and a ground truth collector that feeds labeling.

Hook: A phone app shows one answer box, so why does the system behind it need eight named parts instead of one model file?

Because one file cannot schedule work, score candidates, prepare features, serve traffic, log outcomes, and collect labels at once. Each part owns one failure mode: the featurizer owns bad inputs, the evaluator owns bad promotions, the server owns bad serving, the collector owns stale labels. When the answer goes wrong, the map says exactly which door to knock on.

3.11.1 Parts and Data Flow

A client — the application the end user touches from a tab, laptop, or phone — asks for a prediction. Food ordering apps such as Zomato, Uber Eats, or Swiggy show the shape: the phone is the client, the system behind it does the thinking. The orchestrator schedules the work, refreshing on a cadence such as weekly or on each call, and the model builder's candidate is evaluated on a test set kept secret and strictly isolated from training rows. The test prediction goes to the evaluator; a model deemed good enough passes to the model server, where an API exposes it; the client invokes that API and consumes the result. Domain logic lives in the front end, monitoring follows every invocation and response through one dashboard — a single pane of glass — and each production input, prediction, and outcome lands in the production database for the record. The same path serves search ranking, checkout pricing, and delivery estimates behind one API shape.

The request path in order: client call, front-end domain logic, orchestrator schedule, featurizer build, model server score, response to client, outcome logged to the database, monitoring over all of it. Training runs on a parallel track (builder, evaluator, ground truth) and only its promoted winner joins the serving path — never an untested candidate.

Scope: The test set behind the evaluator must stay secret and isolated — no training peeks, no tuning on it, no shared preprocessing statistics. A leaked test set turns the evaluator into a rubber stamp. Rotate and refresh the held-out slice as the world moves, or promotions certify yesterday's world.

3.11.2 Testing a New Model Without Harm

New versions never seize all traffic at once. When a fresh model looks better than the incumbent, the front end directs a growing share of prediction requests toward the new API while performance is watched, asking continuously whether the newcomer is making or breaking the experience. A stable newcomer that sustains its scores earns the full load; a shaky one gets pulled before damage spreads, and the system owners keep watching through the dashboard throughout. Delivery time shows why this care matters: a pizza chain once advertised that a pizza arriving after 30 minutes goes free, which turns the wait \(t\) minutes into a hard rule:

\[\text{free} \iff t > 30\]

so the business tracks every order's total count per day against its expected delivery time, tunes against misses, and only promotes models that protect the promise. The same progressive exposure that proves a model also protects the SLA it serves.

Worked example — the 30-minute promise as a promotion gate: A delivery model predicts arrival time \(t\) per order across \(n = 2{,}000\) daily orders. The business rule is free exactly when \(t > 30\). Week one: the challenger predicts \(t \le 30\) for \(1{,}900\) orders and \(t > 30\) for \(100\); actuals show \(120\) late arrivals, of which the challenger flagged \(90\) ahead of time. Caught-late rate \(= 90/120 = 0.75\); false-free rate \(= (100 - 90)/1{,}880 = 10/1{,}880 \approx 0.005\). The team promotes only because both numbers clear the agreed bars on a growing traffic share. Sense-check: the rule is binary, so the gate counts orders on each side — never an average that hides the free pizzas.

Pitfall: Promoting on prediction quality while ignoring the SLA the predictions protect. A time model can rank arrivals perfectly yet still miss the 30-minute promise if dispatch ignores it. Gate promotions on the business outcome (free pizzas per day), not only on model scores.

Recap: the reference map splits serving from training, routes every call through one monitored path, and promotes challengers by growing traffic shares. Bridge: The map names the parts; the next section opens the three hardest ones — labeling the truth, building at scale, and serving under load.

3.12 Ground Truth, Labeling and Serving Components

Behind the architecture sit the components that label the world, build the features, and serve the answers. Each has one job, and the system works because they stay decoupled: collection, labeling, evaluation, featurization, orchestration, building, serving, and display.

Hook: A spam filter improves every month without any engineer relabeling mail. Who teaches it — and what breaks the day that teacher goes silent?

The users teach it: every kept, deleted, or reported message is a fresh label flowing back through a feedback pipe. The day that pipe breaks, the model freezes on yesterday's tastes while spam moves on. Labeling is not a setup chore; it is the living input the whole system breathes.

3.12.1 Ground Truth Collection

The ground truth collector pins down the labels the model will learn from. Email shows the pattern: spam filters keep improving by watching which messages users tolerate, classifying and routing junk into a separate folder while blocking hostile mail. A property marketplace shows the slower version: a seller lists a home, buyers arrive on their own schedule, and the team waits — sales take weeks, users renew or cancel when budgets stop fitting, and only their real interactions settle the label. Because feedback has to flow back, a separate microservice carries user responses into the system so predictions keep matching reality. If that loop breaks and predictions go wrong, users lose trust, drop the subscription, and never return, which is why the collector is a first-class part rather than an afterthought.

Scope: Labels arrive on the world's schedule, not the sprint schedule. Property sales settle in weeks, subscription churn in months — training on premature labels teaches impatience as truth. Name each label's settling window before using it, and hold the training wait until the window closes.

3.12.2 Data Labeling at Scale

The data labeler attaches those ground truth tags to the flood of inputs. Spam detectors and object taggers automate the easy cases, and open tooling such as Label Studio speeds the manual remainder; managed options include a large cloud vendor's labeling service and Figure Eight. Manual labeling alone cannot cover modern volumes. One jet engine produces about 20 terabytes of data per hour, so a ten-hour flight, such as New Delhi to New York, generates:

\[V = r \cdot t = 20 \times 10 = 200\]

where \(r = 20\) terabytes per hour is the rate, \(t = 10\) hours is the flight time, and \(V = 200\) terabytes is the total. A double-deck A380 in economy layout can carry up to 840 passengers, each surrounded by crew, air traffic control, radio, GPS, and sensor streams that all need handling. No team labels billions of such records by hand; tooling plus outsourced pipelines carry the load. Aviation, autonomous driving, and large inbox providers all pair machine pre-labels with human review instead of pure manual tagging.

Worked example — why the jet math forces automation: One engine at \(r = 20\) TB/hour over \(t = 10\) hours yields \(V = 20 \times 10 = 200\) TB per engine. A twin-engine jet doubles that to \(400\) TB per flight. A reviewer Sustaining 50 cases an hour, 8 hours a day, clears \(400\) cases a day; \(400\) TB holds on the order of \(4 \times 10^8\) one-megabyte sensor frames, needing \(10^6\) reviewer-days by hand. Sense-check: manual-only labeling misses the fleet by six orders of magnitude — pre-labels plus sampled human review is the only schedule that fits.

Pitfall: Trusting pre-labels without sampling the hard tail — routine frames label well while rare failures (the ones that matter) label worst. Audit a stratified sample weighted toward rare, costly cases, or automation quietly teaches the model that nothing unusual ever happens.

3.12.3 Orchestration, Building and Serving

The evaluator keeps versions honest by comparing them apple to apple on the same tests, weighing short-term and long-term metric effects, checking that lag stays within its allowed limit, and rolling error distributions into the headline scores. Production monitoring then extends the same habit over time: acquire production inputs with their ground truth and predictions, store them, call the evaluator, and refresh the dashboard, with custom views built in libraries such as Streamlit or Gradio for drift and anomaly checks.

The featurizer shapes what the prediction API consumes: the full customer picture keyed by customer ID, compact numeric codes per customer, private stored data, interaction history over time, and the queries, aggregates, and logs their activity produces. The orchestrator runs the workflow that ties it together with a tool such as Apache Airflow, first built at Airbnb and open for any team to use: raw data splits into train, validation, and test sets, features get prepared, resource identifiers plus metrics flow to the model builder, and the optimal model comes back for a canary-style push into serving. Image pipelines augment along the way — resize, flip, crop, rotate, under-sample, over-sample — with sanitization verified before each stage. Whole ML runs can be defined as one pipeline on platforms such as Databricks, Google AI, or Azure AI, executed step by step across Docker containers under vanilla Kubernetes, the popular open orchestration choice, or under OpenShift from Red Hat, which adds a management layer for a price.

Purpose of the orchestrator: run the same steps in the same order on every trigger — split, prepare, build, evaluate, push — so a rerun replays a record instead of reinventing one. Inputs: raw data plus the pipeline definition with resource IDs. Outputs: a promoted model plus the run record. Trace on one run: Airflow splits the day's rows 70/15/15, the featurizer builds the customer picture, the builder fits three candidates, the evaluator scores all three on the frozen test slice, and only the winner takes the canary push. Cost: orchestration adds scheduling and storage overhead, and a chained pipeline stalls when one stage stalls — which is exactly why the dashboard watches each stage separately.

The model builder holds the optimal model with the metrics it was judged on, sometimes via automation such as BigML, and the artifact reaches users through an API with packaging the model server understands. The model server routes each API request to a healthy instance behind a highly available setup, since serving runs as a cluster rather than one box: many requests land in parallel, loads balance across instances, updates roll carefully, and predictions return as API responses. The front end keeps all of this a black box to the user, who only sees a request box and an answer. Inside it runs the domain logic — decisions, fallbacks for anomalous or hostile inputs such as injection attempts, live-model checks, and per-request logging of response time and prediction against the performance bar. The same serving shape powers inboxes, storefronts, and booking flows the team uses every day.

When to use which platform: Kubernetes fits teams that already run containers and want open control; OpenShift fits teams that will pay Red Hat for the management layer on top. Databricks, Google AI, and Azure AI fit teams that want the pipeline, builder, and serving pre-wired on one cloud. Alternatives for small starts: Airflow plus plain Docker on one host, growing into a cluster only when traffic forces it. Pitfall: serving one giant instance instead of a balanced cluster — one crash becomes a full outage, and rolling updates become downtime.

Recap: the collector waits for true labels, the labeler scales with machine pre-labels, the orchestrator replays the pipeline, and the server cluster answers behind one API. Bridge: Maps and components land faster when built by hand — which is how the course turns this lecture into practice.

3.13 How Practice Is Organized

Concepts land faster when each one is built, not just read. Eight linked lab exercises run end to end around an online shopping cart case called Car Twista: the first exercise produces an artifact or endpoint, the next builds on it, and the chain continues so the full breadth of MLOps gets covered in order. Learners work through them in sequence, repeating the lifecycle from framing to monitoring instead of meeting each stage once. Class time then uses separate fresh use cases for guided building, so learners meet new problems with support rather than repeating the same cart example.

The practice loop in one pass: frame the cart problem, ingest its events, clean and engineer features, train and tune, register and containerize, deploy by a staged pattern, monitor and retrain — then repeat with the next exercise building on the last artifact. Each lap reuses the same lifecycle with new depth, so the eighth exercise rehearses production habits, not first-day syntax.
