1.1 What MLOps Is: Machine Learning Meets DevOps

1.1.1 The core idea

Hook: A model can score 95% in a notebook on Friday and fail real users on Monday. Nothing about the math changed over the weekend — everything around the math did. That "everything around" is this course.

MLOps — short for machine learning operations — joins machine learning with DevOps so teams can build and deploy learning systems that survive contact with real users. The course assumes working ML knowledge and DevOps familiarity from the audience and focuses on the meeting point: production-ready ML models built by an ML team, deployed through the best practices of a CI/CD pipeline borrowed from DevOps. A model that scores well in a notebook is only the starting point. MLOps covers everything that turns that model into a dependable service.

The cohort itself shows why this framing matters. Participants join from quality assurance, data engineering, banking products, insurance and health insurance, pharmaceutical quality systems, geospatial and remote-sensing work, statistics consulting, mainframe healthcare systems, aerospace testing, automotive embedded systems, telecom migration, medical device software, enterprise platforms, data platforms, and wealth-management infrastructure. Some automate releases with GitHub Actions, some run Airflow and Snowflake pipelines, some serve models through Azure AI Foundry, and some have never deployed a model at all. The shared goal is the same: move ML out of the notebook and into production with engineering discipline.

Intuition — a recipe is not a restaurant: A notebook model is like a recipe that works once in your own kitchen. A production ML system is like running a restaurant off that recipe — hundreds of covers a night, ingredients that change with the season, staff who rotate, and health inspectors at the door. The recipe still matters, but success now depends on sourcing, timing, hygiene checks, and a kitchen that keeps working when one cook calls in sick. MLOps is the kitchen discipline around the recipe. The analogy breaks in one place: a restaurant serves the same dish every night, while an ML system serves predictions that must adapt as customer taste itself drifts.

CI/CD here means what it means in software: continuous integration (every change is built and tested automatically) plus continuous delivery (every passing change can ship to users quickly). MLOps borrows both, then stretches them to cover ML-specific artifacts — not just code, but data snapshots, feature definitions, model weights, and prompts. When any of those change, the pipeline rebuilds, retests, and redeploys, so the service stays fresh without heroic manual effort.

Q: I am joining to learn machine learning itself. Will this course teach ML from the start? A: No. ML is a separate course with its own syllabus. This course uses ML concepts and DevOps concepts together, under the name machine learning operations, and teaches how to deploy, serve, monitor, and retrain models. Anyone expecting ML theory from scratch should reset that expectation now and prepare to work with deployment instead.

1.1.2 Deployment strategies

A deployment strategy decides how a new model reaches users without breaking what already works. The standing rule is simple: never push a model straight into full production traffic in one big-bang release. Instead, teams pick a staged strategy that fits the use case and the client relationship.

Strategy How it works Damage if the new model is bad Pick it when
Canary release Send the new model a small slice of traffic first (say 5%), watch behavior, then widen Contained to the canary slice You want live-signal validation with a quick rollback path
Blue-green deployment Keep two identical production environments; flip traffic from old (blue) to new (green) once proven; instant rollback available Near zero after flip-back Downtime is unacceptable and you can afford double capacity briefly
Rolling update Replace model instances a few at a time so capacity never drops to zero Partial, fades as rollout proceeds You run many replicas and want zero-downtime refresh
A/B testing Route comparable user groups to different versions and compare measured outcomes before crowning a winner Bounded to group B The question is "which is better," not just "is it safe"
Shadow deployment Run the new model beside the live one on the same live requests, record predictions, never show them to users Zero user impact — pure observation You need production proof with no user risk at all

A canary release sends the new model to a small slice of traffic first, so damage stays contained while the team watches behavior. A blue-green deployment keeps two identical production environments side by side, flips traffic from the old (blue) to the new (green) once the new one proves itself, and keeps instant rollback available. A rolling update replaces model instances gradually, a few at a time, so capacity never drops to zero. A/B testing routes comparable user groups to different model versions and compares measured outcomes before crowning a winner. A shadow deployment runs the new model alongside the live one, feeds it the same live requests, records its predictions, and never shows those predictions to users — pure observation with zero user risk. Each of these patterns answers the same question: how do we deliver to the client while protecting the running system.

A concrete sense of scale helps: with 200,000 requests a day, a 5% canary exposes only 10,000 requests to the new model — enough to read real metrics, small enough that a broken model harms few users and rollback is a traffic switch, not a fire drill.

1.1.3 Serving models as products

A trained model sitting on disk helps nobody. Teams must expose a trained model as an endpoint URL, an API, or a web app so that someone can send inputs and get inference back. Much of modern practice treats the model as a service: the model stays behind a hosted endpoint, consumers call it on demand, and the provider owns scaling, uptime, and versioning. Serving is therefore a first-class skill, not an afterthought, and the course returns to serving tools and patterns repeatedly.

In practice the smallest honest deployment is a prediction endpoint. The pattern below shows the shape — a web handler that takes feature rows, calls the model, and returns scores — which the course later scales up with containers, orchestration, and managed endpoints:

# Minimal prediction service: the same shape every serving tool scales up
app = load_app()
MODEL = load_registered_model("churn-v3")  # pinned version, never "latest"

@app.route("/predict", methods=["POST"])
def predict():
    rows = request.get_json()["X"]       # 1. accept feature rows over HTTP
    scores = MODEL.predict(rows).tolist()  # 2. score with the pinned model
    return json.dumps({"y": scores}), 200  # 3. return predictions as JSON

Three details carry the MLOps lessons even at this size: the model is loaded once at startup rather than per request, the version is pinned so behavior is reproducible, and the input-output contract (feature rows in, scores out) is exactly what later gets versioned, tested, and monitored.

1.1.4 Retraining, versioning, and the model registry

Models age. After five or six months in production, incoming data shifts, inference quality slides, and the model needs retraining so its predictions stay trustworthy. A mature team therefore versions the model, versions the data that trained it, and keeps both inside a model registry — a central store where every model version is recorded, compared, and retrievable. Because any version can be pulled back, an older version can return to production if a newer one misbehaves.

Over time the model also evolves on purpose. Stakeholders file change requests, the team adds functionality, behavior changes, and production must absorb all of it without drama. Versioning plus a registry is what makes that evolution manageable instead of frightening.

Think of the registry as the team's memory: for each version it records which code, which data snapshot, and which parameters produced it, plus how it scored. When a retrained challenger beats the serving champion on the agreed metric, the challenger is promoted; when a promoted model misbehaves, the team rewinds to the last good version in minutes. Without that memory, every incident becomes archaeology.

Scope: This course assumes working ML knowledge and DevOps familiarity. It teaches deployment, serving, monitoring, and retraining — not ML theory from scratch. Teams are also assumed to own the full loop: the same group that trains the model is responsible for its behavior in production, which is why versioning and registries get so much weight.

1.1.5 Containers and orchestration

ML infrastructure spans cloud, edge devices, virtual machines, and containers, and containers carry most of the weight. A container bundles the application with its libraries and settings so it runs identically anywhere. A container engine builds and runs those containers. Docker is the best-known engine: Solomon Hykes introduced Docker to the world, and stewardship later passed to Mirantis. Because licensing and needs differ across teams, alternatives stay on the table, including Podman, CRI-O, Rocket, and containerd. The course standardizes on specific stable tool versions — a fixed Anaconda distribution, a fixed Docker Desktop, and VS Code — so every participant works in an identical environment and results reproduce across machines.

Why this matters for ML in particular: a model trained with one library version can break silently under another. A container freezes the whole stack — Python build, numerical libraries, system packages — so the artifact that passed tests is byte-for-byte the artifact that serves traffic. "Works on my laptop" stops being an excuse because the laptop and the server run the same box.

When containers multiply, teams need a container orchestration platform that schedules, scales, heals, and networks them. Vanilla Kubernetes is the default choice: Google ran Kubernetes internally for more than a decade for its own deployments, then released it to the community so everyone benefits. Teams that want a hardened distribution can pick alternatives such as OpenShift or another custom Kubernetes cluster. In ML terms, orchestration is what lets a serving deployment grow from two replicas at night to fifty during a sale, restart a crashed scorer without paging anyone, and roll a new model version across the fleet without dropping a request.

1.1.6 Functions as a deployment target

Functions-as-a-service lets a team deploy a small unit of logic that runs only when triggered and bills only while running. The capability is nearly identical across clouds with platform-specific details: AWS Lambda in the AWS ecosystem, Azure Functions on Microsoft Azure, and Google Cloud Functions on Google Cloud. These fit event-driven inference paths where keeping a server always warm would waste money — for example, a fraud check that fires a few thousand times a day rather than thousands of times a second.

The trade-off to remember: functions remove server management but add cold starts (the first request after idle waits while the platform wakes the function) and hard time limits. Steady high-volume traffic is usually cheaper and faster on a dedicated endpoint; spiky rare traffic favors functions.

Pitfalls: (1) Big-bang releases — shipping an unproven model to all traffic at once turns a reversible mistake into an outage. (2) Notebook-only validation — offline scores say nothing about latency, load, or drift. (3) Unversioned training data — without the data snapshot, no result can be reproduced or audited. (4) Always-warm servers for spiky workloads — paying for idle capacity that functions would bill at zero.

Recap: MLOps applies DevOps discipline — CI/CD, versioning, staged rollouts, containers, orchestration — to ML artifacts so a notebook score becomes a dependable service. Bridge: The first stop on that road is the full journey itself: the ML lifecycle that carries a model from notebook to mature system, covered next in 1.2.

A bank sharpening credit decisions, a hospital network validating device software, and a telecom team migrating legacy scoring all land in the same place: the model is the easy part, and operating it is the profession. That operating layer — deployment strategies, serving, versioning, containers — is where this course lives.

1.2 The Machine Learning Lifecycle and Production Pipelines

1.2.1 From notebook to mature system

Hook: Every production model you admire started as a scrappy notebook cell that printed a promising number. What separates the demo from the service is everything that happened after that print statement.

The ML lifecycle tracks a model from birth to maturity. It starts where most models start: a notebook or an IDE such as Jupyter, VS Code, or a similar editor, where a data scientist trains something promising. Then comes the long middle: hardening the code, wiring data inputs, adding tests, packaging the model, deploying it, watching it, and improving it with stakeholder feedback. Stakeholders stay involved through this transformation, shaping the model from what it was into what production needs. Understanding this path — where a model comes from, how it matures level by level, and who touches it along the way — is the precondition for every other topic in the course.

Intuition — growing up: Think of the notebook as childhood: fast, playful, no responsibilities. Hardening the code and wiring data inputs is adolescence: rules, chores, tests, consequences. Deployment is moving out: rent is due every day in the form of latency, uptime, and drift. Maturity means the model earns its keep under adult supervision — monitoring, retraining, stakeholder reviews. The analogy breaks where biology does not apply: software can be rolled back to childhood in minutes, and a "grown-up" model still needs constant supervision, unlike an adult.

In lifecycle terms the industry often talks about maturity levels: manual notebook work at the bottom, automated training pipelines in the middle, and fully automated CI/CD plus continuous retraining at the top. Each level adds reproducibility — the guarantee that the same code plus the same data produces the same model — and each level removes a class of midnight emergency.

1.2.2 Production pipelines with Airflow and Kubeflow

Hand-run notebooks cannot carry production. Teams build production-grade pipelines that move data and models through repeatable steps: ingest, validate, train, evaluate, package, deploy, and monitor. Apache Airflow and Kubeflow are the pipeline platforms named for this role. Pipelines make retraining routine instead of heroic, and they record exactly what ran, on which data, with which code, so any result can be reproduced and audited later.

Purpose: Turn a fragile sequence of manual steps into a scheduled, observable, rerunnable workflow that anyone on the team can trigger and audit.

Inputs and outputs: In come raw data sources, feature definitions, training code, and configuration. Out come a trained model artifact, an evaluation report, lineage metadata (what ran, on which data, with which code), and either a deployment or a diagnosed failure.

Steps:

  1. Ingest — pull raw data from stores and streams on schedule.
  2. Validate — check schema, ranges, and freshness before training; reject bad batches loudly rather than training on them quietly.
  3. Train — run versioned training code on the validated snapshot.
  4. Evaluate — score the candidate on held-out data plus business metrics; compare against the serving champion.
  5. Package — serialize the winner with its dependencies into a container image.
  6. Deploy — release through a staged strategy (canary, blue-green, shadow).
  7. Monitor — watch metrics and logs; feed drift signals back to step 1.

Trace — a nightly churn pipeline: At 2 a.m. Airflow wakes, pulls yesterday's subscription events, validates that no required column is missing, trains a candidate churn model, and scores it at 0.81 AUC against the champion's 0.79. The pipeline packages the candidate, deploys it to a 5% canary, and by morning the dashboard shows the canary holding its lead — promotion approved, lineage recorded.

Complexity and cost: Pipelines cost setup time and compute per run, and a badly designed one retrains on noise daily. They pay back by making the tenth retrain as boring as the first.

When to use and alternatives: Use Airflow for general scheduled workflows and Kubeflow when the workload is Kubernetes-native ML. A bare cron job plus scripts works for one model and one engineer — and breaks the week a second model arrives.

A retail demand forecaster illustrates the payoff: the consulting-built model from the companion reading shone at handoff and decayed within a year because nobody owned the loop. A pipeline would have caught the slide in weeks, retrained on fresh sales, and kept the "AI-powered" claim true.

Scope: Pipelines assume versioned code, versioned data snapshots, and an evaluation gate with a champion to beat. Without those three, automation just produces untrusted models faster.

Pitfalls: (1) Notebook copy-paste as a "pipeline" — manual steps get skipped under pressure. (2) Training on unvalidated data — one corrupt batch poisons the model. (3) No lineage — when results differ, nobody can say what changed. (4) Monitoring as an afterthought — a pipeline that deploys but never watches is half a pipeline.

Recap: The lifecycle matures a model from notebook to service, and pipelines — ingest through monitor with full lineage — make that maturity repeatable. Bridge: The first concrete step inside the pipeline is turning a trained model into a shippable file, which is where serialization and the packaged artifact in 1.3 come in.

Airflow schedules the retail forecaster's nightly retrain, Kubeflow runs the same steps Kubernetes-natively for the telecom team, and both write to a registry so the next section's packaging discussion has something real to wrap.

1.3 Packaging, Serializing, Serving, and Deployment Targets

1.3.1 Serialization formats and the packaged artifact

Hook: A model that exists only in RAM dies with the process. Shipping it means turning memory into a file — and the file format you pick decides who can read it, how fast it loads, and whether it survives the trip to production.

A model must leave memory and become a file before it can ship. Serialization — converting a trained model into a portable artifact — preserves the learned weights plus enough structure to reload and score later. Each format has its trade-offs, and the course names five: pickle files carrying the .pkl extension, joblib files favored for large numerical models, PMML for portable predictive-model exchange, ONNX for framework-neutral exchange, and H5 for hierarchical storage of deep-learning weights.

Format What it stores Strength Watch out for
Pickle (.pkl) Any Python object, including models Works with everything in Python Tied to Python versions; never load untrusted files
Joblib Large NumPy-backed models Faster and smaller than pickle for big arrays Still Python-centric
PMML Predictive models as XML Runs on many scoring engines Limited to classical model types
ONNX Model graph plus weights Moves models between frameworks (train in one, serve in another) Operator coverage varies by exporter
H5 Deep-learning weights hierarchically Standard home for large neural weights Needs the matching architecture code to reload

The team serializes the model, wraps it with its code and dependencies into a custom container image, and ships that image as one box holding data handling, model, and application together. That box — code, weights, libraries, config — is the unit that gets versioned, tested, and deployed, so the artifact that passed evaluation is exactly the artifact that serves traffic.

1.3.2 Where models run: private cloud, public cloud, and the edge

Deployment targets divide into private clouds, public clouds, and constrained devices. A private cloud such as OpenStack or OpenNebula keeps data and control inside the organization. Public clouds offer ready-made flavors — managed training, managed endpoints, and managed pipelines — at a price. Beyond the data center, models ship compressed into mobile devices, run on edge hardware, and even plug into a browser. The course keeps the open-source path prominent throughout: open tools give total control of the stack, the deepest customization, and no vendor toll, at the cost of owning every operational burden.

The decision comes down to four pressures pulling in different directions: cost (managed endpoints bill per hour and per request; self-hosted bills in engineer time), control (regulated data may never leave the building), latency (a face-unlock model cannot round-trip to a distant region), and data gravity (moving terabytes to the model is costlier than moving the model to the terabytes). A hospital network under strict data rules leans private; a startup validating an idea leans managed; a smart-glasses team has no choice but the edge.

1.3.3 Serving patterns: batch versus online

Batch prediction scores a settled pile of inputs on a schedule — nightly scoring of every customer, for example. Online prediction answers single requests immediately as they arrive. Use batch when answers can wait hours and the input set is known up front; use online when each request needs its own fresh answer in milliseconds.

Dimension Batch Online
When it runs On schedule (nightly, hourly) Per request, on demand
Latency budget Minutes to hours Milliseconds to seconds
Input Whole table at once One row or one event
Example Nightly churn scores for all customers Fraud check on each swipe
Failure mode A bad run wastes a night A bad deploy hurts users instantly

Streaming data pushes teams toward online serving: sources such as AWS Kinesis streams feed events continuously, and the model must answer each event with low delay. Static, dynamic, and streaming serving patterns each fit different latency and freshness needs, and the course pairs each with orchestration through Airflow and Kubeflow plus microservice packaging so the model, its data handling, and its API travel as one unit. A microservice here means the model plus a thin API wrapper deployed as its own independently scalable service — easy to update, easy to roll back, easy to blame correctly.

Worked example — nightly churn batch: A telecom team scores 2,000,000 subscribers every night. The batch job loads champion model v7 from the registry, reads the feature table, and writes one probability per subscriber. The run takes 40 minutes on 8 workers, flags 60,000 subscribers above 0.7 risk, and hands that list to the retention team by 6 a.m. Sense-check: 60,000 out of 2,000,000 is 3% — plausible for a targeted campaign, not a sign the model fired on everyone. The same model served online would answer each login in 50 ms instead — same weights, different plumbing.

Scope: Serialization preserves weights and structure, not the training environment — the container supplies that. Batch versus online is a latency and freshness decision, not a quality decision; a stale model is wrong in both modes.

Pitfalls: (1) Shipping pickle across Python versions — reloads fail or silently differ. (2) Training-serving skew — features computed differently at serve time than at train time. (3) Batch thinking for streaming data — yesterday's scores cannot answer this second's event. (4) Online serving without load testing — the first traffic spike becomes the load test.

Recap: Serialize into a portable format, wrap model plus code plus dependencies into one container image, and serve it batch or online on a target chosen for cost, control, latency, and data gravity. Bridge: Shipping is the midpoint, not the finish — once traffic flows, the model starts aging, which is why monitoring and retraining in 1.4 close the loop.

OpenStack and OpenNebula anchor private clouds, AWS SageMaker with Google Vertex AI and Azure ML cover managed deployment, AWS Kinesis feeds streaming events, and ONNX carries models across frameworks — each choice trading control against convenience.

1.4 Monitoring, Drift, Retraining, and Testing in Production

1.4.1 Watching the deployed model

Hook: Deployment day feels like the finish line. It is actually the day your model starts meeting data it never studied — and without monitoring, you will be the last to know it is failing.

Deployment is the midpoint, not the finish. Once a model serves traffic, the team monitors it continuously: metrics that quantify behavior, logs that record events, and the overall state of the application. If data drifts — the live inputs stop resembling the training inputs — inference quality slides with it. The team must notice the drift, judge the inference unacceptable, and trigger retraining. A model left unwatched silently goes stale, and stale predictions reach users dressed as confident answers.

Intuition — a smoke detector, not a fire extinguisher: Monitoring does not fix the model; it tells you there is smoke while the fire is still small. Metrics are the beeping alarm (prediction distributions shifting, error rates climbing), logs are the security footage (which requests, which features, which version). You still need the extinguisher — retraining — but without the detector you only discover the fire when users smell it. The analogy breaks in one place: a smoke detector watches one house, while model monitoring must separate three moving causes — the world changed, the pipeline broke, or the model itself decayed.

Drift comes in flavors worth naming. Data drift means the inputs changed (customers skew younger; a sensor recalibrates). Concept drift means the right answer for the same inputs changed (fraudsters invent new tricks; fashion moves on). Label drift means the outcome mix shifted even where the model is right. All three look identical in one dashboard — falling business numbers — which is why teams monitor inputs, predictions, and ground truth separately instead of watching accuracy alone.

1.4.2 Manual versus automated retraining

Manual retraining starts from a gut feeling: somebody senses the model looks off and orders a retrain. That approach depends on human vigilance and arrives late. Automated retraining wires drift signals directly to the pipeline: when monitored metrics cross a threshold, a fresh training run starts, the new candidate is evaluated, and redeployment follows with no human in the loop. The goal is sustained model quality — a model that stays trustworthy across months of shifting data rather than shining once at launch and fading quietly.

Retraining itself comes in two flavors. Stateless retraining trains from scratch on the accumulated data and replaces the old model wholesale. Stateful retraining continues from the existing model, updating it incrementally. Each suits different data volumes, training costs, and stability needs.

Stateless (from scratch) Stateful (incremental)
What happens Train fresh on all data, swap the model Keep training the live model on new data
Best when Data is modest, training is cheap, history matters equally Data is huge, training is costly, recent data matters most
Risk Slow and expensive per run Catastrophic forgetting — new data washes out old lessons
Example Weekly churn model on 2M rows Fraud model updated on each micro-batch of 1,024 transactions

How often to retrain has no universal answer — it depends on the domain (fraud and trading shift daily; voice recognition shifts rarely), the cost (a week-long pipeline for a 1% gain may not pay), and measured performance (retrain on signal, not on calendar). The disciplined answer is a threshold, not a schedule: define the metric, define the floor, retrain when the floor breaks.

1.4.3 Testing in production without breaking production

No team should experiment directly on live users, yet production behavior can only be proven in production. The resolution is a production-equivalent test setup plus staged strategies. Shadow deployments observe silently, canary releases expose a slice of traffic, and A/B tests compare versions on matched groups. Provisioning a cluster that mirrors production lets the team rehearse each strategy and read the results before touching the real traffic.

The ordering logic: shadow first (zero user risk, real traffic proof), canary next (small user risk, real outcome proof), A/B when the question is comparative (which version wins on the business metric). A mirror cluster sits underneath all three as the rehearsal room — load tests, config checks, and rollback drills happen there, never on live users.

1.4.4 The observability toolbox

Good monitoring needs tooling. Prometheus collects time-series metrics, Grafana turns those metrics into dashboards and alerts, and the ELK stack — Elasticsearch for search and storage, Logstash for log processing, and Kibana for visualization — handles the log side. Together they form the observability backbone: metrics show what is happening, logs show why, and dashboards put both in front of the humans responsible.

Worked example — catching drift on a grocery forecaster: A demand model trained on 2023 sales predicts 500 units of a perishable line per week. By mid-2024 Prometheus shows the prediction mean drifting from 500 to 640 while actual sales sit at 480 — a 33% over-forecast that spoils stock. The Grafana alert fires when the gap crosses 15% for two straight weeks; ELK logs reveal the cause — a new discount code changed buying patterns, a textbook data drift. The team triggers stateless retraining on the last six months, the candidate scores within 4% on holdout, and promotion restores the waste rate. Sense-check: a persistent one-directional gap (always over, never under) points at drift rather than noise — noise would scatter both ways.

Scope: Monitoring covers two levels — resource health (is the system alive) and model pertinence (are predictions still right). This section's retraining logic assumes labeled ground truth arrives fast enough to score against; where labels lag weeks, teams monitor input and prediction drift as proxies.

Pitfalls: (1) Watching accuracy alone — by the time labeled accuracy drops, users already suffered. (2) Manual retraining on gut feel — late, irregular, unaudited. (3) Stateful retraining without forgetting checks — the model learns the new season and forgets the old one. (4) Testing on live users without staging — an experiment is not a strategy.

Recap: Monitor inputs, predictions, and outcomes; fire retraining on thresholds, not hunches; prove releases with shadow, canary, and A/B in that order. Bridge: Managed clouds and the LLM wave reuse this exact loop with new instruments — token costs, faithfulness scores, agent traces — which is where 1.5 picks up.

The grocery chain that paid twice for its forecaster learned the lesson this section teaches: deployment without monitoring is a loan against future failures, and Prometheus with Grafana plus the ELK stack is how teams stop paying it.

1.5 Cloud Platforms, Large Language Models, and Agentic Operations

1.5.1 Cloud and constrained-target deployment

Hook: The same model can cost pennies or fortunes depending on where it runs — a click-through cloud endpoint, a phone chip, or a browser tab. Picking the target is an engineering decision with a price tag attached.

Managed clouds remove undifferentiated heavy lifting. AWS SageMaker offers a click-through path — subscribe, configure, deploy — with the platform handling machines, scaling, and serving. Google Vertex AI and the Azure ML platform offer the same bargain on their clouds. At the other extreme, constrained targets demand compression and frugality: models slimmed into mobile apps, pushed to edge devices, and embedded as browser plugins. Comparing service approaches across clouds and devices — cost, control, latency, and data gravity — is itself a learning outcome, because the right target depends on the use case, not on fashion.

The bargain is explicit: the cloud owns machines, patching, scaling, and uptime, and bills for all of it; the team owns nothing but the model and the bill. Self-hosted open-source stacks invert that — full control of versions, data residency, and customization, paid for in engineer hours. Regulated industries (banking, health insurance, pharma quality) often cannot take the first deal; a two-person startup validating an idea usually cannot afford the second.

1.5.2 Consuming large language models instead of training them

The field has shifted from training models to consuming them. A large language model arrives pretrained on trillions of parameters by someone else; the team consumes it for an application instead of training from zero. That shift changes the skill set: prompt design and prompt versioning (tracking exactly which prompt produced which behavior), experiment tracking across runs, retrieval-augmented generation pipelines that ground answers in retrieved documents, and evaluation of what the model actually did.

Retrieval-augmented generation, usually shortened to RAG, pairs a retriever over a knowledge store with a generator: the system fetches relevant passages, then writes an answer grounded in them. Embeddings — dense numeric vectors that capture meaning — and vector databases such as OpenSearch and FAISS supply the retrieval side. A vector database stores these meaning-vectors and answers "find passages closest in meaning to this question" in milliseconds, which is what lets a generator cite company docs instead of inventing facts.

How RAG answers a question: The user asks in plain words. The retriever converts the question to an embedding and pulls the top few passages from the vector store. The generator receives the question plus those passages and writes an answer tied to them. When it works, every claim traces to a retrieved source; when the retriever fails, the generator fluently invents — which is exactly the failure the next section's evaluation watches for.

1.5.3 LLM evaluation, cost, and serving

LLM evaluation watches failure modes that classical metrics miss. Hallucination means the model states falsehoods fluently; faithfulness measures whether the answer stays true to the retrieved context; responsibility asks whether the answer reasons carefully and safely from that context. Guardrails — checks wrapped around the model — enforce policy before an answer reaches a user. Serving adds economics: tokens cost money, so wasteful reuse hurts, and teams balance quantization (shrinking model weights to cheaper precision), batching, latency, and output quality. GPU-backed serving frameworks handle scale; Ollama keeps every model inside the local machine for free local control; vLLM-style high-throughput servers benchmark serving performance. Observability tools built for this world — Langfuse, LangSmith, and Arize Phoenix — trace token usage, cost, latency, and output drift per request, and CI/CD pipelines extend to prompts, models, and data alike.

Worked example — RAG cost on a support bot: A support assistant answers 10,000 questions a day. Each answer retrieves 4 passages (about 2,000 tokens of context) and generates 300 tokens. That is 23,000,000 tokens a day. At a representative price of 1 unit per million input tokens and 3 per million output tokens, the day costs roughly 20 plus 9, or about 29 units — nearly 900 a month before a single guardrail runs. Quantizing a self-hosted model, caching repeated questions, and trimming retrieval to 2 passages can cut that by half or more. Sense-check: retrieval dominates the bill here (2,000 of 2,300 tokens per answer), so the cheapest lever is retrieving less, not generating less.

Prompt versioning deserves emphasis because it is new to most teams: the prompt is now source code. Two runs with the same model and different prompts are different systems, so the prompt text, the model version, and the retrieved context must all be logged per run — otherwise no result reproduces and no failure can be replayed.

1.5.4 AgentOps: operating agentic workflows

Agentic AI brings a new operations layer. An agent plans multi-step work, calls tools, remembers context in memory, and acts toward a goal — and every one of those behaviors needs tracking. AgentOps covers the tooling and practice for agentic workflows: tracing each plan, tool call, and memory read; evaluating whether the agent reached its goal safely; and observing cost, latency, and failure across runs. Identity-aware workflow tracking ties each action to the agent and session that produced it, so failures can be replayed and fixed rather than shrugged at.

Where LLMOps watches one model call, AgentOps watches a whole chain: the plan the agent chose, each tool it invoked with what arguments, what it read from memory, what it cost, and where it went wrong. A support agent that books the wrong refund is not a "bad prediction" — it is a failed multi-step workflow, and only a full trace shows which step derailed it.

Scope: This section consumes pretrained models rather than training them — the operating skills (prompt versioning, RAG evaluation, cost control) assume the weights already exist. Quantization and batching trade small quality losses for large cost wins; the acceptable trade is a product decision, not a technical one.

Pitfalls: (1) Unversioned prompts — same model, different wording, irreproducible behavior. (2) Retrieval skipped to save cost — ungrounded generation hallucinates with confidence. (3) Token bills unread — per-request tracing exists precisely because costs hide in aggregate. (4) Agents without traces — a failed multi-step workflow cannot be debugged from its final answer.

Recap: Consume LLMs through versioned prompts and RAG, evaluate faithfulness and responsibility alongside accuracy, control token economics, and trace agentic workflows end to end. Bridge: These topics are not electives — they are modules six and seven of the course map laid out next in 1.6.

OpenSearch and FAISS index the vectors, LangChain assembles the pipelines, Langfuse with LangSmith and Arize Phoenix watch cost and drift, Ollama keeps experiments local and free, and the same CI/CD discipline from 1.1 now versions prompts as code.

1.6 Course Modules, Case Studies, Textbooks, and Outcomes

1.6.1 The seven modules

Hook: Seven modules, eight labs, three textbooks — and a map that tells you exactly which piece of the production puzzle each week solves.

The course runs through seven modules in order. The first module sets motivation and maturity: the three levels of MLOps, the ML lifecycle with its processes and capabilities, maturity models, the people and agile practices around them, the landscape of MLflow, Kubeflow, Airflow, and SageMaker, and case studies of platforms built by practitioners at scale — Uber built Michelangelo for its own in-house productivity, and Netflix and Spotify each run their own internal ML platforms. The second module covers experimentation and the model registry: experiment workflows, model versioning with metadata, the registry itself, and serialization formats from pickle and joblib through PMML, ONNX, and H5. The third module packs and ships: containers fusing data, model, and application; deployment patterns; serving with batch versus online predictions; orchestration with Airflow and Kubeflow; integrated ML platforms; and model-as-a-service offerings. The fourth module watches and heals: why models fail, drift detection, the Prometheus-Grafana-ELK observability toolbox, stateless versus stateful retraining, and testing in production through shadow, canary, and A/B strategies. The fifth module targets clouds and constrained devices: public-cloud managed deployment, edge, mobile, and browser targets. The sixth module introduces LLMOps: how operating large language models differs from conventional MLOps, the LLM lifecycle, cost-latency-token challenges, prompt versioning, RAG architecture, vector databases, evaluation with guardrails and faithfulness checks, GPU serving, quantization, and LLM observability. The final module takes on AgentOps: planning, tools, memory, tracking, observability, and evaluation of agentic workflows, with a hands-on tracing lab.

The industry cases are load-bearing, not decorative. Michelangelo shows what a ride-hailing giant builds when notebooks stop scaling: standardized training, serving, and monitoring for hundreds of teams. Netflix and Spotify show the same lesson from recommendations — internal platforms that let product teams ship models without each team reinventing deployment. When the course later asks participants to design for their own vertical, these are the reference architectures to argue against or borrow from.

1.6.2 Textbooks and references

Three textbooks anchor the reading, because no single book covers every topic. Introduction to MLOps and Designing Machine Learning Systems by Chip Huyen come from O'Reilly, and the LLM Engineer's Handbook covers the language-model half of the course. One additional reference book rounds out the shelf.

Exam note: Reading follows the modules, so match chapters to the module in progress rather than reading cover to cover.

Reading ahead cover-to-cover mixes vocabularies — classical metrics one week, token economics the next — and the exam tests module-grounded understanding.

1.6.3 Learning outcomes

By the end, each participant should be able to explain the infrastructure, tooling, and process maturity that production ML demands; carry a real-time use case from their own vertical — whether mainstream software, banking, insurance, retail, telecom, or healthcare — from experiment to deployed endpoint; build, containerize, and deploy an end-to-end pipeline with open-source tools under full personal control; monitor a deployed model, detect drift, and apply the right retraining; rehearse testing-in-production strategies without risking live traffic; compare serving approaches across cloud, edge, mobile, and browser targets as smart devices multiply — Meta is working with Ray-Ban on smart glasses that run models on the face itself; evaluate and operate production-grade RAG pipelines; and trace and evaluate an agentic workflow with AgentOps tooling.

Note the shape of that list: every outcome is a verb attached to an artifact — explain the maturity, carry a use case, build a pipeline, monitor a model, rehearse a strategy, compare targets, evaluate RAG, trace an agent. The exam and assignments test the same shape: show the working system and defend its choices, not recite definitions.

Scope: The seven-module sequence is cumulative — monitoring assumes packaging, LLMOps assumes serving, AgentOps assumes everything. Skipping ahead to agents without the deployment base leaves no foundation to trace against.

Recap: Seven modules from maturity to AgentOps, industry platforms as reference designs, module-matched reading, and eight demonstrable outcomes. Bridge: Outcomes are proven in labs, not lectures — the eight hands-on exercises in 1.7 are where the verbs above get practiced.

1.7 Laboratory Exercises, the Lab Portal, and the Practice Method

1.7.1 Eight labs mapped to the modules

Hook: Nobody learns deployment by watching slides. Eight labs — each tied to the module it proves — turn every concept in this lecture into something your hands have done.

Eight lab exercises carry the experiential half of the course, each mapped to the modules it exercises. The opening labs are warm-ups: MLflow experiment tracking with a Docker-backed registry, packaging, and orchestration pipelines. Model file formats get practiced through serialization tasks. Model deployment arrives via containerizing with Docker and serving through an Airflow pipeline. The next lab deploys and serves an ML model as a microservice with full serving patterns. Then comes monitoring and observability over deployed models with failure and drift analysis, followed by continual learning with A/B testing in production. A later lab puts a real-time predictive model onto a cloud service — SageMaker, Vertex AI, or an Azure equivalent. The LLM sequence covers API access with local-versus-cloud cost comparison, experiment tracking with RAG pipelines, vector databases with evaluation practice, LLM deployment with benchmarking and cost-latency trade-off analysis, and CI/CD with observability. The closing lab traces and evaluates an agentic workflow.

Exam note: The labs are warm-ups with real weight — assignment questions grow directly out of lab experience, so every lab finished is assignment preparation banked early.

1.7.2 Worked walkthrough: the first lab on experimentation and packaging

The first lab makes the pattern concrete. It is self-paced and offline, needs a laptop or desktop with full administrative credentials, and budgets about three hours. The storyline uses Cartoon Star, a fictional online retail store, with a three-person team sharing data science duties. The objective: set up MLflow, run experiments, and register models through the MLflow tracking UI.

The steps run in order. First create the environment for the operating system at hand — Linux and Windows paths are both documented step by step. Then launch the tracking server, run the provided code base, and watch autologging capture parameters, metrics, and artifacts without manual bookkeeping. Each run records who authored it, so teammates can compare configurations side by side: one member's data split against another's, one hyperparameter set against the next. The team compares runs, picks a winner, and registers it as the champion model. A champion-challenger setup then governs updates: the champion serves production while a challenger trains on new data or settings, and only a challenger that beats the champion earns promotion to the new champion. Small prescribed modifications — changed tags, changed parameters, a new data footprint — let each participant produce distinct results, and the timestamp, data footprint, and tags must be unique to each submission. The lab closes with a deliverable checklist confirming the run, the registered champion, and the comparison notes.

Worked example — the Cartoon Star champion round: The three teammates each log one run on the retail data. Teammate A logs a run tagged split=80-20, lr=0.05, scoring 0.82 accuracy; teammate B logs split=70-30, lr=0.05 at 0.80; teammate C logs split=80-20, lr=0.1 at 0.84. The tracking UI ranks all three side by side, and C's run becomes the champion and is registered as cartoon-star-v1. Next week a challenger trains on fresh transactions and scores 0.86 — it beats 0.84, so it is promoted to cartoon-star-v2 and the old champion stays in the registry for instant rollback. Sense-check: three runs, three distinct tag sets, one winner by number — exactly the comparison the deliverable checklist asks for, and no ties to argue about.

Q: I am new to Docker and GitHub. Can we get preliminary hands-on homework so we arrive prepared? A: Yes. Pick any small side use case and build it yourself to gain exposure before the sessions. A dedicated support channel for MLOps questions is available, so share queries there whenever stuck.

The advice generalizes: the side project need not be ML at all — containerizing any small app and pushing it to a personal repository teaches the Docker and Git moves the labs assume. Arriving with those moves fluent saves the three-hour budget for MLflow itself rather than for installation fights.

1.7.3 The lab portal and its rules

Lab work for graded submissions runs on a hosted lab portal reached through an institutional login ID. The machines are ephemeral virtual machines: everything outside the workspace disappears when the session shuts down, so all work must be saved under the workspace path at /home/username/workspace, which lives on persistent network storage and survives across boots. Sessions drop after fifteen idle minutes because the remote-desktop link resets, and a virtual machine terminates itself after sixty stopped minutes — so keep the browser tab open for its heartbeat and never walk away from a running machine. Each participant receives twenty hours of machine time for assignments, and every idle minute burns that balance, so stop the virtual machine as soon as the work ends. The base image runs Rocky Linux with the full stack preinstalled: Python, Jupyter, Keras, Matplotlib, Scikit-learn, SciPy, TensorFlow, Pandas, PyTorch, NumPy, plus a browser, VS Code, a terminal, MLflow run tracking, and MinIO object storage. First boots are cold and take one to three minutes. Source control has one hard rule: create Git and GitHub repositories under the institutional ID only — never use a personal or employer repository for lab or assignment work.

Three rules prevent most disasters: save under the workspace path or lose it, stop the machine when done or burn the twenty-hour budget idle, and keep coursework in institutional repositories so grading sees it and employers never do. The fifteen-minute idle drop and sixty-minute stopped termination are not annoyances — they are the cost controls that make hosted machines affordable.

Q: The portal login throws a 404 error. Has access been provisioned yet? A: Not yet. Backend mapping runs batch by batch across many cohorts, so provisioning takes time. Wait for the mapping to reach this batch rather than filing individual tickets, and expect access within the next couple of sessions.

Q: Should we wait quietly for portal access, or contact the infrastructure team directly? A: Waiting is correct. The backend team already has the request, a follow-up with the coordinator is scheduled, and access lands earliest through the normal queue. Festival holidays may add delay, so allow buffer time.

The two answers form one policy: provisioning is a batch queue, not a ticket queue. Filing individual tickets does not move a batch; it only loads the support channel. Use the waiting time on a personal laptop — which is exactly the practice method below.

1.7.4 The practice method: run everything twice

The strongest recommendation in the session is to run every lab twice: once on a personal laptop with full admin control, and once on the hosted portal. The first run is for learning — mistakes welcome, stumbles expected, half-finished state forgiven. The second run applies the lessons: the participant knows the tricky steps, avoids the earlier errors, and produces a clean reflected result on the graded environment. A story drives the point home: a famous stage magician, asked on his deathbed whether any secret remained untaught, told his successor son that the whole secret was practice — practice it, practice it, practice it. The analogy maps directly: lab fluency comes from repetition, not from watching.

Q: I joined late and need to catch up. What setup will help me learn fastest? A: Use a personal laptop with full administrative control and run all eight labs locally first, then reflect the work on the hosted portal. Doing it twice — learning through first-run mistakes, then repeating cleanly — builds the most confidence in the least time.

Scope: The double-run method assumes a personal machine with admin rights for run one; portal-only participants should still redo each lab rather than submitting a first attempt. The twenty-hour portal budget covers redoing, not idling.

Pitfalls: (1) Saving outside the workspace path — vanishes on shutdown. (2) Leaving the machine running — idle minutes burn the assignment budget. (3) Personal or employer repositories — grading cannot see them; use the institutional ID. (4) Submitting first-run work — the portal run should reflect lessons, not repeat mistakes.

Recap: Eight module-mapped labs, a Cartoon Star walkthrough that teaches champion-challenger discipline, strict portal rules, and a run-it-twice method that turns mistakes into preparation. Bridge: Labs are practice; assignments are graded — and confusing the two costs marks, which is exactly what 1.8 clarifies.

Doing it twice — learning through first-run mistakes, then repeating cleanly — builds the most confidence in the least time, whether catching up late or preparing for the assignments that grow directly out of lab experience.

1.8 Evaluation: Lab Exercises Are Not Assignments

1.8.1 The grading shape

Hook: No quizzes, no cushion — three evaluation windows carry the whole grade. Knowing their shape in week one is the difference between steady progress and a last-month scramble.

There are no quizzes in this course. Assignments carry the continuous-evaluation weight: the assignment component holds 30 percent, released in staggered windows of roughly seven to twenty-one days rather than on a fixed rhythm. A mid-semester component runs for 30 marks across two hours, and a comprehensive component carries 40 percent weightage.

Exam note: With no quizzes to cushion the grade, every assignment window matters — track release dates from the first week and never let a window slip.

The irregular windows are deliberate pressure: seven days for a short task, twenty-one for a long one, released when the matching labs land. A participant who finishes each lab as its module closes is always ready; one who defers labs meets every window unprepared.

1.8.2 Lab exercises versus assignments

The most repeated clarification in the session is vocabulary. Lab exercises are the eight practice tasks: self-explanatory, tutorial-style, done for fluency. Assignments are the separate graded evaluations built on top of that fluency. Calling a lab exercise a lab assignment muddles the two and costs grades through confusion, so the preferred term is always lab exercise for practice and assignment for graded work.

Q: Are lab exercises and assignments different components, or the same thing under two names? A: They are different. The eight exercises shown are lab exercises for practice. Assignments arrive separately as graded evaluations. Keep the names apart from the first session so preparation stays organized.

Q: Should assignments run on the hosted lab, or can we use notebook services instead? A: Lab only, no outside notebook service. The practical method is to develop outside and then run and reflect the work on the hosted lab, since grading and verification happen there.

Q: Do we work in groups for the assignments? A: No groups. Everyone comes to learn individually, and each person solves their own use case alone. Group setups from other courses do not apply here — this course keeps an individual-work rule throughout.

The three answers form one preparation policy: practice in the labs (individually, anywhere), prove it in the assignments (individually, on the hosted lab). Developing outside then reflecting onto the portal is allowed and encouraged — what matters is that the graded artifact runs where graders run it.

1.8.3 Integrity and submission discipline

Academic integrity gets explicit treatment because the labs make copying easy and detection easier. Each submission must carry unique evidence of authorship: distinct timestamps, distinct data footprints, and distinct tags. Submissions sharing identical markers count as copied work and are treated accordingly. The rule is stated once, directly, with the expectation that working professionals hold themselves to it without further policing.

The mechanism is worth understanding: prescribed small modifications (changed tags, changed parameters, a new data footprint) mean two honest submissions can never match exactly. Identical markers are therefore not a coincidence to explain but evidence of copying — the grading design makes authorship self-certifying.

Scope: Integrity here means demonstrable authorship, not just honest intent — timestamps, data footprints, and tags must differ because the work actually differed. Professional experience does not exempt anyone; it raises the bar.

Pitfalls: (1) Calling labs "assignments" — muddles preparation and costs grades. (2) Notebook-service submissions — graders verify on the hosted lab only. (3) Group work habits from other courses — this course is individual throughout. (4) Identical submission markers — treated as copied work, no further warning.

Recap: Thirty percent assignments in irregular windows, a mid-semester and a comprehensive component, labs for practice and assignments for grades, individual work verified on the hosted lab. Bridge: With the map (1.6), the practice (1.7), and the rules (1.8) all laid out, the lecture closes — carry one use case from your own vertical through every stage above, and the outcomes take care of themselves.

Track every window from week one, keep lab exercises and assignments in separate mental boxes, and let each submission's unique markers speak for its authorship.
