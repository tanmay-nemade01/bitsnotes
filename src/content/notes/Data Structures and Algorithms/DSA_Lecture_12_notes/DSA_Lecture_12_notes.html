12.1 Binary Tree Fundamentals and the Search Bottleneck

Why does storing data in a branching tree structure fail to speed up searching if elements are scattered randomly across nodes? When data has no governing spatial or numerical order, every branch remains a viable hiding spot, forcing any search procedure to inspect every node exhaustively.

A tree is a hierarchical data structure composed of nodes connected by directed or undirected edges. In contrast to linear data structures such as arrays and linked lists, where elements follow a single sequential order, trees organize data into parent-child relationships. Before introducing the binary search tree, we must establish the formal properties of general binary trees and analyze why searching an unordered binary tree is computationally expensive.

To build an intuitive picture, consider storing books across a labyrinth of rooms with branching corridors. If books are placed on shelves at random without any cataloging system, standing at an intersection provides no clue whether a desired title lies down the left hallway or the right hallway. You must search both corridors room by room, examining every book one by one. The physical branching creates the illusion of hierarchy, but without an ordering rule, the search remains fundamentally linear. The analogy breaks when considering computational memory: physical rooms have spatial layout and walking distance, whereas tree nodes are linked by memory pointers scattered arbitrarily across the heap.

12.1.1 Binary Tree Definition and Degree Constraints

A binary tree (a hierarchical tree structure where branching is capped at two), conventionally denoted \(T\), is a rooted data structure in which every node has at most two children. These children are ordered and referred to as the left child and the right child.

Formally, a binary tree \(T\) is defined recursively:

  1. Base Case: An empty set of nodes (represented as a null pointer, \(\emptyset\)) is a valid binary tree.
  2. Root Node: A single node \(r\) with no child nodes is a valid binary tree, where \(r\) acts as the root.
  3. Recursive Step: A node \(r\) possessing an ordered pair of subtrees \((T_L, T_R)\), where both the left subtree \(T_L\) and the right subtree \(T_R\) are themselves valid binary trees, forms a binary tree rooted at \(r\).

The degree of a node \(v\), written \(\deg(v)\), denotes the number of direct children connected to \(v\). In any binary tree:

\[ \deg(v) \le 2 \quad \forall v \in T \]

A node may have exactly zero children (a leaf node), one child (either a left child or a right child), or two children. The lecture notes confirm: "a binary tree... every node must have at most two child nodes... a node without any child sounds in the binary." No restrictions are placed on the data values stored within the nodes of an arbitrary binary tree; the definition governs solely the structural branching limit.

Let us clarify structural metrics associated with a binary tree \(T\) containing \(n\) nodes:

  • The depth of a node \(v\), \(\text{depth}(v)\), is the number of edges on the path from the root node to \(v\). The root has \(\text{depth}(\text{root}) = 0\).
  • The height of a tree, \(h\), is the maximum depth among all nodes in \(T\). For a tree with a single node, \(h = 0\); for an empty tree, \(h = -1\).
  • In a full or complete binary tree of height \(h\), the maximum number of nodes is given by:

\[ n_{\max} = \sum_{i=0}^{h} 2^i = 2^{h+1} - 1 \]

Conversely, the minimum height for a binary tree of \(n\) nodes occurs when each level is completely packed:

\[ h_{\min} = \lceil \log_2(n + 1) \rceil - 1 = \lfloor \log_2 n \rfloor \]

However, if each node has only one child, the tree degenerates into a linear chain with maximum height:

\[ h_{\max} = n - 1 \]

12.1.2 Tree Traversals and the Unordered Search Problem

To examine or process elements stored within a binary tree, we perform a tree traversal — an algorithmic procedure that visits every node in the tree exactly once. There are four standard traversal strategies:

  1. In-order traversal: Recursively visit the left subtree, visit the root node, and then visit the right subtree (\(\text{Left} \to \text{Root} \to \text{Right}\)).
  2. Pre-order traversal: Visit the root node first, recursively visit the left subtree, and then recursively visit the right subtree (\(\text{Root} \to \text{Left} \to \text{Right}\)).
  3. Post-order traversal: Recursively visit the left subtree, recursively visit the right subtree, and then visit the root node (\(\text{Left} \to \text{Right} \to \text{Root}\)).
  4. Level-order traversal: Visit nodes level by level from the root downward, visiting all nodes on level \(d\) from left to right before moving to level \(d + 1\).

The primary motivation for traversing a tree is to perform a search operation — determining whether a specific target key exists within the tree. In an arbitrary binary tree, data elements are arranged without any ordering rules. If we search for a specific value, such as 3 or 4, observing the value stored at the root provides zero information about whether the target key resides in the left subtree, in the right subtree, or nowhere in the tree. Because we cannot eliminate any branch, the search algorithm must systematically explore both subtrees.

12.1.3 Search Bottleneck: Why General Binary Trees Require O(n) Time

When searching an unordered binary tree containing \(n\) nodes, every single node may need to be visited before concluding whether the target element is present.

Let \(T(n)\) represent the worst-case number of node comparisons required to locate an element in an arbitrary binary tree of \(n\) nodes. Because no structural invariant directs the search path:

\[ T(n) = O(n) \]

where \(n \in \mathbb{N}\) is the total number of nodes in the binary tree. The verbal explanation emphasizes: "when I do a search operation in binary tree the time complexity can end up at order of n... because at most I have to travel almost all the nodes and finally I might get it... we do not have any structural kind of search... both left and right subtree has to be searched to get an answer."

This \(O(n)\) time complexity represents an undesirable computational bottleneck. An array of \(n\) elements can already be searched in \(O(n)\) time using simple linear search. Storing unordered data in a tree without an ordering property adds pointer overhead without yielding any computational speedup. To overcome this limitation, we introduce an ordering condition that allows the search algorithm to prune an entire subtree at every step.

Scope & Boundary: General binary trees impose solely the degree constraint \(\deg(v) \le 2\) on topology. They impose zero constraints on keys. So, algorithms that depend on pruning or divide-and-conquer cannot operate on arbitrary binary trees. When dynamic searches must run faster than \(O(n)\), using an unordered binary tree wastes memory on left and right pointers while providing no algorithmic advantage over a simple linked list.

12.1.4 Worked Examples: Traversal-Based Search in an Unordered Tree

Consider an unordered binary tree containing \(n = 6\) nodes with keys arranged as follows:

  • Root node: 12
  • Left child of 12: 8
  • Right child of 12: 5
  • Left child of 8: 3
  • Right child of 8: 14
  • Right child of 5: 4

Suppose we search for target key \(k = 4\):

  1. Visit Node 12 (Root): Compare \(12\) with target \(4\). Since \(12 \ne 4\), we cannot deduce which subtree holds 4 because the tree lacks an ordering rule. We must search both branches.
  2. Visit Node 8 (Left Child of 12): Compare \(8\) with \(4\). Since \(8 \ne 4\), continue exploring descendants of 8.
  3. Visit Node 3 (Left Child of 8): Compare \(3\) with \(4\). Since \(3 \ne 4\) and node 3 is a leaf, backtrack to node 8.
  4. Visit Node 14 (Right Child of 8): Compare \(14\) with \(4\). Since \(14 \ne 4\) and node 14 is a leaf, backtrack all the way to root 12. The entire left subtree is now exhausted without finding 4.
  5. Visit Node 5 (Right Child of 12): Compare \(5\) with \(4\). Since \(5 \ne 4\), explore the right child of 5.
  6. Visit Node 4 (Right Child of 5): Compare \(4\) with \(4\). Target found!

Because both subtrees had to be searched exhaustively, the search traversed every node, taking \(O(n)\) steps.

Result: Target key 4 is located after 6 comparisons, visiting all \(n = 6\) nodes in the tree. Sense-check: Without key ordering, observing that a parent does not equal the target gives zero information about whether the target lies in its left subtree, its right subtree, or neither. So, in the worst case, every single node must be examined.

Common Pitfalls:

  • Assuming binary structure implies fast search: Beginners often assume that any tree data structure automatically provides \(O(\log n)\) search time. A binary tree restricts branching degree, not value placement.
  • Premature pruning: Attempting to prune a branch in an unordered tree based on numerical comparison (e.g. assuming \(4 < 12\) means 4 must reside on the left) causes the search algorithm to miss valid keys placed on the right.

12.1.5 Student Questions and Answers

Q: Can a node have only one child or zero children and still be considered a binary tree? A: Yes, a binary tree requires at most two child nodes per parent node. A node with one child or zero children satisfies this condition completely. Even a single root node with no children constitutes a valid binary tree.

12.1.6 Exam Notes

Exam note: In examinations, distinguish strictly between the degree property of a general binary tree and that of a binary search tree. A question stating that a tree is a "binary tree" guarantees only the \(\le 2\) child node structural constraint, not any sorting or key ordering property.

Recap & Bridge: General binary trees organize data hierarchically but force brute-force exhaustive searches of \(O(n)\) time complexity when keys are unordered. To eliminate branches systematically during search, we impose a global key ordering invariant — transforming the general binary tree into a Binary Search Tree (Section 12.2).

12.1.7 Real-World & Domain Connections

In computer systems and compiler design, general binary trees frequently serve as Abstract Syntax Trees (ASTs) and algebraic expression trees. In an arithmetic expression tree for \((a + b) \times (c - d)\), interior nodes store mathematical operators while leaf nodes store operands. Here, the hierarchical tree topology encodes evaluation precedence and grammatical syntax rather than search keys. Evaluating or type-checking such expressions naturally requires visiting every node in \(O(n)\) time via post-order or in-order traversals. When fast dynamic searching, key lookups, and range queries are required, systems transition from general trees to ordered binary search trees.

12.2 Binary Search Tree Definition and Global Ordering Invariant

If you inspect every single node in a binary tree and find that it is larger than its immediate left child and smaller than its immediate right child, can you be certain that the entire tree is a valid binary search tree? Surprisingly, the answer is no — local parent-child compliance alone does not guarantee global tree validity.

A binary search tree (BST) is a binary tree with an imposed ordering condition that organizes data keys so that searching, insertion, and deletion can be performed efficiently. By establishing a consistent ordering invariant, the tree guarantees that a target value can be found by descending a single path from root to leaf, eliminating the need to search both subtrees.

To visualize how the invariant operates, consider an airport security checkpoint dividing passengers into two distinct corridors: domestic passengers with flight numbers below 20 turn left, while international passengers with flight numbers above 20 turn right. Inside the international wing, gates may further subdivide into regional flights (below 30) and long-haul flights (above 30). Even if a traveler at gate 25 correctly follows the local regional sign, if that gate was mistakenly built inside the domestic concourse, the entire airport transit protocol breaks down. The analogy breaks when considering physical geometry: airport travelers walk sequentially through hallways, whereas tree nodes are static memory records linked by pointers.

12.2.1 The Binary Search Tree Property

The fundamental ordering invariant of a binary search tree is defined relative to every node in the tree.

Let \(x\) be any node in a binary search tree \(T\). Let \(\text{key}(x)\) denote the scalar key stored at node \(x\):

  • For every node \(u\) located in the left subtree of \(x\), the key of \(u\) is strictly less than the key of \(x\):

\[ \text{key}(u) < \text{key}(x) \quad \forall u \in \text{LeftSubtree}(x) \]

  • For every node \(v\) located in the right subtree of \(x\), the key of \(v\) is strictly greater than the key of \(x\):

\[ \text{key}(v) > \text{key}(x) \quad \forall v \in \text{RightSubtree}(x) \]

where \(\text{LeftSubtree}(x)\) denotes the complete set of all descendant nodes reachable from the left child pointer of \(x\), and \(\text{RightSubtree}(x)\) denotes the set of all descendant nodes reachable from the right child pointer of \(x\).

The verbal description from the lecture states: "all the nodes whose value are less than 20 should be part of their left subtree... and all the values that are greater than 20 should be part of the right... from the root node, all the smaller child values will be on the left subtree and all the values that have got greater value than the root node will be on the right subtree."

Because this condition applies recursively to every node, every subtree of a binary search tree is itself a binary search tree. An immediate mathematical consequence of this property is that an in-order traversal of a binary search tree visits nodes in strictly increasing, sorted numerical order.

12.2.2 The Global Invariant Trap: Local Versus Global Validity

A critical conceptual trap in binary search trees is assuming that verifying parent-child relationships in isolation is enough to confirm BST validity. A tree is NOT a valid binary search tree merely because every node is greater than its immediate left child and less than its immediate right child. The BST property is a global invariant that must hold across all ancestor bounds.

The common misconception occurs when checking only a local parent-child condition: if a node is smaller than its immediate parent, one might assume the tree is valid. The necessary correction is that every node must obey the global invariant enforced by all of its ancestors. If a node is placed in the right subtree of an ancestor root \(R\), every value in that right subtree must remain strictly greater than \(R\), even if it correctly satisfies its immediate parent relationship.

The verbal explanation makes this distinction clear: "it's not only one instant but overall tree this property has to be valid... because two a value which is smaller than three which should be associated in the left subtree has somehow engrossed into right subtree that's the reason why we are calling it as no more a binary search."

Mathematically, for any node \(x\) located at depth \(d\), its key must fall within an open interval:

\[ \text{key}(x) \in (L_x, R_x) \]

where \(L_x\) is the tightest lower bound inherited from all ancestors for which \(x\) lies in the right subtree, and \(R_x\) is the tightest upper bound inherited from all ancestors for which \(x\) lies in the left subtree. For the root node, \(L_{\text{root}} = -\infty\) and \(R_{\text{root}} = \infty\). When descending to the left child, the upper bound tightens to \(R_{\text{left}} = \text{key}(x)\); when descending to the right child, the lower bound tightens to \(L_{\text{right}} = \text{key}(x)\).

Dimension Local Parent-Child Verification Global Invariant Verification
Condition Checked \(\text{key}(x.\text{left}) < \text{key}(x) < \text{key}(x.\text{right})\) \(\forall u \in \text{LeftSubtree}(x): \text{key}(u) < \text{key}(x)\) and \(\forall v \in \text{RightSubtree}(x): \text{key}(v) > \text{key}(x)\)
Ancestor Scope Immediate parent node only All transitive ancestors on the path from root to node
Mathematical Formulation Isolated node inequalities Bounded open interval \(\text{key}(x) \in (L_x, R_x)\)
Search Guarantee Fails; target may hide behind false branches Guarantees exact pruning of subtrees during descent

12.2.3 Handling Duplicate Keys Uniformly

In standard theoretical formulations, binary search tree keys are assumed to be distinct. However, practical applications frequently encounter duplicate keys. To handle duplicates without breaking the search property:

  1. A uniform convention must be established and maintained across the entire tree, such as placing all keys less than or equal to the node key in the left subtree:

\[ \text{key}(u) \le \text{key}(x) \quad \forall u \in \text{LeftSubtree}(x) \]

  1. Alternatively, duplicates can be stored uniformly in the right subtree:

\[ \text{key}(v) \ge \text{key}(x) \quad \forall v \in \text{RightSubtree}(x) \]

  1. Another widespread industry convention stores duplicate occurrences inside a frequency counter or linked list within the node itself, avoiding extra tree nodes.

The lecture notes emphasize consistency: "you impose a condition that less than or equal to... but this should be uniform throughout your binary search tree you cannot keep changing this." In addition, duplicate keys offer an early exit advantage: when searching for a duplicate key, if the key matches the root, the search stops immediately without descending further.

Scope & Assumptions:

  • Total Ordering: The BST property strictly assumes that elements belong to a totally ordered set supporting the trichotomy law (for any two keys \(a\) and \(b\), exactly one of \(a < b\), \(a = b\), or \(a > b\) holds true). If keys lack total ordering (such as complex numbers or floating-point NaN values), standard BST comparisons fail.
  • Uniformity of Duplicates: If duplicate routing switches between left and right dynamically during execution, duplicate searches may end early with false negative results.

12.2.4 Worked Examples: Valid and Invalid Binary Search Trees

#### Example 1: Step-by-Step Construction of Valid BST from Root 20

Consider building a binary search tree starting with root node 20 and inserting keys: \(\{15, 30, 10, 18, 25, 35\}\).

  1. Insert 15: Compare with root 20. Since \(15 < 20\), 15 is placed as the left child of 20.
  2. Insert 30: Compare with root 20. Since \(30 > 20\), 30 is placed as the right child of 20.
  3. Insert 10: Compare with root 20 (\(10 < 20\), go left). Compare with node 15 (\(10 < 15\), go left). Node 10 becomes the left child of 15.
  4. Evaluate Candidate Node 25 as Right Child of 15:
  • Does \(25 > 15\) hold? Yes.
  • However, node 15 resides in the left subtree of root 20. Every node in the left subtree of 20 must satisfy \(\text{key} < 20\). Since \(25 > 20\), placing 25 in the left subtree of 20 violates the global BST property.
  • So, 25 cannot be placed as the right child of 15. Instead, a valid key such as 18 satisfies \(15 < 18 < 20\) and can be placed as the right child of 15.
  1. Insert Remaining Nodes in the Right Subtree of 20:
  • Insert 25: Compare with root 20 (\(25 > 20\), go right). Compare with node 30 (\(25 < 30\), go left). Node 25 becomes the left child of 30. This is valid because \(20 < 25 < 30\).
  • Insert 35: Compare with root 20 (\(35 > 20\), go right). Compare with node 30 (\(35 > 30\), go right). Node 35 becomes the right child of 30. This is valid because \(35 > 30 > 20\).

The resulting tree is a valid binary search tree where all left subtree keys {10, 15, 18} < 20 and all right subtree keys {25, 30, 35} > 20.

Result: The assembled tree strictly maintains global bounds: Left keys \(\{10, 15, 18\} < 20\) and Right keys \(\{25, 30, 35\} > 20\). Sense-check: Performing an in-order traversal yields the sequence \([10, 15, 18, 20, 25, 30, 35]\), which is strictly sorted in ascending order.

#### Example 2: Counterexample of Invalid BST with Root 3

Consider a tree constructed with the following relationships:

  • Root node: 3
  • Left child of 3: 1 (valid, since \(1 < 3\))
  • Right child of 3: 6 (valid, since \(6 > 3\))
  • Left child of 6: 2
  • Right child of 6: 7

Let us evaluate node 6 in isolation:

  • Left child 2 is less than 6 (\(2 < 6\)).
  • Right child 7 is greater than 6 (\(7 > 6\)).
  • Locally, the subtree rooted at 6 appears to be a valid binary search tree.

However, inspect the entire tree with respect to root 3:

  • Node 2 is situated inside the right subtree of root 3.
  • By the global BST invariant, every node in the right subtree of root 3 must satisfy \(\text{key} > 3\).
  • Because 2 < 3, the invariant is broken. The tree is NOT a binary search tree.

Result: The tree is NOT a valid binary search tree due to node 2 violating the ancestor bound imposed by root 3. Sense-check: If a search algorithm searches for target key 2 starting from root 3, it compares \(2 < 3\) and branches left into node 1. Because node 2 was placed in the right subtree of 3, the search algorithm will conclude that key 2 does not exist in the tree. So, local validity without global validity completely breaks the search algorithm.

Common Pitfalls:

  • Local checking fallacy: Validating only node.left.key < node.key < node.right.key with an isolated recursive check. Valid validation requires tracking (min_allowed, max_allowed) intervals down the recursion.
  • Inconsistent duplicate handling: Inserting duplicate keys into the left subtree during one operation and into the right subtree during another operation, creating split branches where searches fail.

12.2.5 Student Questions and Answers

Q: If a subtree satisfies the binary search tree property locally, why is the overall tree not a binary search tree? A: The binary search tree property is a global invariant that must hold for every ancestor, not merely between immediate parent and child nodes. If node 2 is in the right subtree of root 3, every key in that subtree must be greater than 3. Because 2 is smaller than 3, the entire tree fails to be a binary search tree.

Q: Where should duplicate keys be stored if a key equal to the root is inserted? A: A uniform rule must be chosen and kept consistent throughout the tree. For instance, you can define the rule that keys less than or equal to the current node value always go to the left subtree. Whichever convention is selected, it must not change dynamically during tree operations.

12.2.6 Exam Notes

Exam note: Examination questions frequently present tree diagrams where every local parent-child pair is sorted, but a deeply nested leaf violates the bound of a distant ancestor. When verifying whether a given tree is a BST, always track the valid open interval \((\text{min\_val}, \text{max\_val})\) for each node starting from \((-\infty, \infty)\) at the root.

Recap & Bridge: The global BST invariant ensures that for any node \(x\), every key in its left subtree is smaller and every key in its right subtree is larger. This enables targeted pointer descent: to find the minimum or maximum element, an algorithm never needs to branch, but simply follows a single pointer chain (Section 12.3).

12.2.7 Real-World & Domain Connections

Relational database systems (such as PostgreSQL, MySQL, and SQLite) use the global BST invariant when compiling and executing SQL range queries (e.g. SELECT * FROM accounts WHERE balance BETWEEN 1000 AND 5000;). The storage engine evaluates query bounds against index ancestor intervals. Because the global invariant guarantees that no balance below 1000 can exist in any right subtree where the ancestor key is 1000, entire disk blocks and subtrees are pruned immediately without reading unnecessary pages from secondary storage.

12.3 Operations on Binary Search Trees and Extremum Queries

How do you locate the smallest or largest record among millions of entries in a tree without searching every branch? Because of the binary search tree invariant, you never need to backtrack or explore multiple branches: you simply follow a single pointer chain straight to the edge of the tree.

The ordered arrangement of a binary search tree enables a suite of fundamental operations that can be implemented through simple pointer navigation. Instead of comparing across all subtrees, an algorithm follows a deterministic descent path from the root.

To build an everyday mental model, imagine descending a mountain road system where every fork in the road is strictly graded: every left fork leads to a lower elevation, and every right fork leads to a higher elevation. To reach the lowest point in the entire mountain range, you take every left branch without hesitation, ignoring every right turn. You continue until no more left paths exist — you are at the absolute minimum elevation. Symmetrically, taking every right turn leads directly to the mountain peak. The analogy breaks down because physical roads can loop back or cross over, whereas tree pointer structures are strictly acyclic.

12.3.1 Primary BST Operations Overview

A binary search tree supports a comprehensive dictionary and priority interface. The primary operations include:

  1. Search (find(k)): Determines whether an element with key \(k\) exists in the tree and returns a pointer to its node, or null if absent.
  2. Find Minimum (find_min()): Locates the node storing the smallest key value in the tree.
  3. Find Maximum (find_max()): Locates the node storing the largest key value in the tree.
  4. Insertion (insert(k)): Adds a new node with key \(k\) into the tree while preserving the global BST ordering invariant.
  5. Deletion (delete(k)): Removes the node containing key \(k\) and restructures the pointers to maintain the BST invariant.
  6. Successor / Predecessor: Finds the immediate next larger or smaller element in sorted order.

12.3.2 Finding the Minimum Element

To find the minimum element in a binary search tree, we use the property that all smaller keys are situated to the left of any given node.

The pointer traversal strategy proceeds as follows:

  1. Start at the root node.
  2. Check if the current node has a left child.
  3. If a left child exists, move to that left child. Discard the right child and right subtree entirely.
  4. Repeat this step until reaching a node whose left pointer is null.
  5. The node with no left child is the leftmost node in the tree and contains the minimum key.

The verbal description from the lecture confirms: "the least leftmost element is the minimum one... I knew this. I have to only go to the left side to find a value less than 20. Once I come, I see: is there any left child? Yes, if there I'm traveling, I'll ignore the right. Same thing. I keep on ignoring right and go."

Formally, let \(T\) be a binary search tree rooted at \(r\), and let \(h\) denote the height of \(T\). The pointer descent is governed by the recurrence:

\[ \text{find\_min}(x) = \begin{cases} x & \text{if } x.\text{left} = \text{null} \\ \text{find\_min}(x.\text{left}) & \text{otherwise} \end{cases} \]

The time complexity of this pointer traversal is proportional to the tree height \(h\):

\[ T(n) = O(h) \]

where \(h\) is the height of the tree. In a balanced binary search tree, \(h = O(\log n)\). In a degenerate left-skewed tree, \(h = O(n)\). The space complexity is \(O(1)\) when implemented with a simple while-loop, or \(O(h)\) auxiliary stack space if implemented recursively.

12.3.3 Finding the Maximum Element and Traversal Direction

Finding the maximum element operates symmetrically to finding the minimum:

  1. Start at the root node.
  2. Check if the current node has a right child.
  3. If a right child exists, move to that right child and discard the left subtree.
  4. Repeat until reaching a node whose right pointer is null.
  5. This rightmost node contains the maximum key in the binary search tree.

Formally, the pointer descent recurrence is:

\[ \text{find\_max}(x) = \begin{cases} x & \text{if } x.\text{right} = \text{null} \\ \text{find\_max}(x.\text{right}) & \text{otherwise} \end{cases} \]

#### Traversal Order Perspective: In-Order Traversal

A fundamental property of binary search trees is that standard in-order traversal (\(\text{Left} \to \text{Root} \to \text{Right}\)) visits all nodes in strictly ascending sorted order.

  • Because in-order traversal begins by descending as far left as possible, the very first element output by an in-order traversal is the minimum element.
  • If we reverse the traversal order to \(\text{Right} \to \text{Root} \to \text{Left}\), nodes are visited in strictly descending sorted order. The very first element output by this reversed traversal is the maximum element.

The verbal intuition explains: "if you are using traversal, would you start with left as the traversal, or would you change it to right? Right... right root left... to achieve order of 1 for the first element visited."

12.3.4 Comparative Analysis: Binary Search Tree Versus Min-Heap

Students frequently ask whether a priority queue (min-heap) is preferable to a binary search tree because a min-heap retrieves the minimum in \(O(1)\) time.

A student inquired whether a min-heap should be used instead of a BST to find the minimum in \(O(1)\) time. The instructor corrected this misconception: a min-heap guarantees that the minimum element resides at the root in \(O(1)\) time, but a min-heap does not satisfy the total ordering property of a binary search tree.

The table below contrasts the algorithmic trade-offs between the two data structures:

Feature / Operation Binary Search Tree (Balanced) Binary Min-Heap
Ordering Property Total ordering: \(\text{left} < \text{root} < \text{right}\) Partial ordering: \(\text{parent} \le \text{children}\)
Find Minimum \(O(h) = O(\log n)\) (leftmost descent) \(O(1)\) (located directly at the root)
Find Maximum \(O(h) = O(\log n)\) (rightmost descent) \(O(n)\) (must scan all \(\lceil n/2 \rceil\) leaves)
Arbitrary Key Search \(O(h) = O(\log n)\) \(O(n)\) (linear scan; heap offers no left/right order)
Sorted Traversal \(O(n)\) via standard in-order traversal \(O(n \log n)\) via \(n\) repeated extract_min() calls
Primary Use Case Dynamic dictionaries, ordered sets, range queries Priority queues, scheduling, top-\(k\) extraction

Scope & Assumptions:

  • Non-Empty Tree: Both find_min and find_max assume the tree contains at least one node. Calling either function on an empty root (root == null) causes a null pointer dereference unless guarded by a defensive check.
  • Pointer Immutability: Pointer traversal assumes child pointers are immutable during the search. In concurrent multi-threaded environments, concurrent tree modifications require synchronization (such as reader-writer locks or lock-free leaf trees).

12.3.5 Worked Walkthrough: Pointer Traversal Versus In-Order Traversal

Consider a BST with root 20:

  • Left child of 20: 15; Right child of 20: 30
  • Left child of 15: 10; Right child of 15: 18
  • Left child of 30: 25; Right child of 30: 35

#### 1. Finding Minimum via Pointer Traversal:

  1. Initialize: current = root (20). Left child exists (15). Move left: current = 15. Discard right subtree rooted at 30.
  2. At node 15: Left child exists (10). Move left: current = 10. Discard right child 18.
  3. At node 10: Left child is null. Stop. Minimum element is 10.

Total steps: 2 edge traversals (height \(h = 2\)). Minimum element = 10.

#### 2. Finding Maximum via Pointer Traversal:

  1. Initialize: current = root (20). Right child exists (30). Move right: current = 30. Discard left subtree rooted at 15.
  2. At node 30: Right child exists (35). Move right: current = 35. Discard left child 25.
  3. At node 35: Right child is null. Stop.

Total steps: 2 edge traversals (height \(h = 2\)). Maximum element = 35.

#### 3. Traversal-Based Extremum Extraction:

  • Standard In-Order Traversal (\(\text{Left} \to \text{Root} \to \text{Right}\)):

Recursion descends left to 10, outputs [10, 15, 18, 20, 25, 30, 35]. The first element visited is the minimum: 10.

  • Reversed In-Order Traversal (\(\text{Right} \to \text{Root} \to \text{Left}\)):

Recursion descends right to 35, outputs [35, 30, 25, 20, 18, 15, 10]. The first element visited is the maximum: 35.

Sense-check: The pointer descent directly targets the first node that an in-order traversal visits, but executes in \(O(h)\) time with \(O(1)\) memory, without needing full tree traversal.

Common Pitfalls:

  • Assuming O(1) minimum access: Assuming a BST has \(O(1)\) minimum access like a min-heap. A BST requires \(O(h)\) time because it must traverse pointers down to the leftmost leaf.
  • Assuming O(log n) worst case: Quoting \(O(\log n)\) as the unconditional worst-case complexity for find_min or find_max. Unless the BST is guaranteed to be balanced (e.g. AVL or Red-Black), the tree height \(h\) may equal \(n\), causing the operation to take \(O(n)\) time.

12.3.6 Student Questions and Answers

Q: Can we use a min-heap instead of a binary search tree to find the minimum element in O(1) time? A: A min-heap does keep the minimum element at the root in O(1) time, but it does not maintain the binary search tree property. In a heap, there is no left-versus-right ordering between children. As a result, searching for an arbitrary key in a heap requires O(n) time, whereas a balanced binary search tree performs arbitrary searches in O(log n) time.

Q: If we want to find the maximum element using a traversal, should we use standard in-order traversal? A: Standard in-order traversal visits left-root-right, which gives the smallest element first. To find the maximum element immediately using a traversal, reverse the traversal order to right-root-left so that the rightmost maximum node is visited first.

12.3.7 Exam Notes

Exam note: Questions asking for the worst-case time complexity of find_min or find_max without specifying tree balance should be answered as \(O(h)\) or \(O(n)\), where \(h\) is the tree height. Stating \(O(\log n)\) is valid only when the binary search tree is explicitly guaranteed to be balanced.

Recap & Bridge: Finding the minimum and maximum in a binary search tree requires following leftmost or rightmost pointers, taking \(O(h)\) time. Because runtime is governed by tree height \(h\), keeping \(h\) small is essential. If incoming data arrives in sorted order, \(h\) explodes to \(n\), turning the tree into a pathological skewed tree (Section 12.4).

12.3.8 Real-World & Domain Connections

In operating system runtimes, task dispatchers use augmented binary search trees (such as the Linux Completely Fair Scheduler, CFS, which uses a Red-Black Tree) to schedule runnable processes. Processes are keyed by their accumulated execution time (vruntime). The scheduler invokes find_min() to select the next process to execute on the CPU. By caching a pointer to the leftmost leaf node, CFS retrieves the next process in \(O(1)\) time, while maintaining full \(O(\log n)\) tree insertions and deletions as processes run and sleep.

12.4 Degenerate Skewed Trees and Time Complexity Analysis

What happens when you insert an already-sorted dataset into a binary search tree? Rather than constructing a well-proportioned branching hierarchy, the tree quietly degenerates into a linear chain, wiping out every computational advantage over a linked list.

While binary search trees offer dramatic speedups over unordered trees under typical conditions, their performance depends directly on tree topology. When insertion patterns cause unbalanced growth, the tree degrades into a pathological structure known as a skewed tree.

To understand this degeneration, think of building a staircase. In an ideal building, staircases branch into symmetrical flights that quickly access multiple floors. However, if every single landing is built only turning left in a continuous spiral without any branching flights, the structure stretches out into a single, narrow vertical ladder. To reach the bottom rung, you must step on every single rung above it. Structurally and algorithmically, a skewed tree is identical to a singly linked list. The hierarchical branching advantage of a tree is completely lost. The analogy breaks because physical ladders occupy continuous three-dimensional space, whereas linked nodes exist as discrete pointers scattered across heap memory.

12.4.1 Skewed Binary Search Trees: Left-Skewed and Right-Skewed Trees

A skewed tree is a degenerate form of a binary tree where every internal node has exactly one child. Skewed trees fall into two categories:

  1. Left-skewed tree: Every internal node has exclusively a left child and no right child.
  2. Right-skewed tree: Every internal node has exclusively a right child and no left child.

The verbal description highlights: "the kind of that tree that you encountered this called as skew... all the elements are on one side... left skew tree because all my elements are towards the left."

Let \(n\) denote the total number of nodes in a skewed tree. The height \(h\) of a skewed tree is proportional to the number of nodes:

\[ h = n \]

(or \(h = n - 1\) edges). In contrast to a perfectly balanced binary tree where height grows logarithmically as \(h = \lfloor \log_2 n \rfloor\), a skewed tree stretches to maximum linear depth. Every node has an out-degree of 1 (except the single leaf, which has degree 0).

12.4.2 Step-by-Step Construction of a Skewed Tree

Consider inserting the descending sequence of keys:

\[ [10, 9, 8, 5, 4, 2, 1] \]

into an initially empty binary search tree:

  1. Insert 10: The tree is empty, so 10 becomes the root node.
  2. Insert 9: Compare 9 with root 10. Since \(9 < 10\), 9 is placed as the left child of 10.
  3. Insert 8: Compare 8 with 10 (\(8 < 10\), go left); compare 8 with 9 (\(8 < 9\), go left). Node 8 is placed as the left child of 9.
  4. Insert 5: Compare 5 with 10, then 9, then 8. Because \(5 < 8\), 5 is placed as the left child of 8.
  5. Insert 4: Compare 4 sequentially down the chain until reaching 5. Because \(4 < 5\), 4 is placed as the left child of 5.
  6. Insert 2: Compare 2 sequentially down the chain. Placed as the left child of 4.
  7. Insert 1: Compare 1 down the chain. Placed as the left child of 2.

At no point does any node acquire a right child. Every node has degree 1, forming a single linear strand:

\[ 10 \to 9 \to 8 \to 5 \to 4 \to 2 \to 1 \]

To search for key 1 in this tree, an algorithm must start at root 10 and traverse all 7 nodes sequentially, exactly like traversing a linked list.

12.4.3 Worst-Case Complexity: Big-O Versus Theta Notation

The recurrence relation describing the worst-case search time in a left-skewed tree of size \(n\) is:

\[ T(n) = T(n - 1) + O(1) \]

where \(T(n)\) represents the number of comparisons on an input of size \(n\), and \(O(1)\) is the constant time required to compare keys and follow a single pointer.

We solve this recurrence by unrolling step by step:

\[ \begin{aligned} T(n) &= T(n - 1) + c \\ &= \left(T(n - 2) + c\right) + c = T(n - 2) + 2c \\ &= \left(T(n - 3) + c\right) + 2c = T(n - 3) + 3c \\ &\ \ \vdots \\ &= T(1) + (n - 1)c \\ &= O(n) \end{aligned} \]

where \(c > 0\) is the constant cost of a single node comparison and pointer branch, and \(T(1) = O(1)\) is the base case cost.

The verbal confirmation notes: "search from the root node all the way till my travel to find out the minimum element, then what is the time complexity? Sagar, will I end up getting order of n time complexity? Yes."

#### Asymptotic Notation Distinction: Big-O Versus Theta

The lecture draws a vital distinction between upper-bound and tight-bound asymptotic notations:

  • Big-O notation (\(O(n)\)): Represents the asymptotic upper bound across all possible tree topologies. In textbooks, stating that BST search is \(O(n)\) describes the worst-case time complexity, which occurs when the tree degenerates into a skewed structure.
  • Theta notation (\(\Theta(\log n)\)): Represents the asymptotically tight bound for the average case when keys arrive in random order and the tree maintains balanced height.

The lecture instructs: "always remember order of n whenever if you read a book and they say it's order of n it means that it's the worst case time complexity they are defining... but the average case how should I write? Theta... big O talks about worst case and theta talks about average case."

Scope & Assumptions:

  • Unbalanced BST Vulnerability: Standard unaugmented BSTs make zero guarantees about balance. If input data is pre-sorted (e.g. timestamps, auto-incrementing IDs), the tree degrades into a linear chain without warning.
  • Remediation Requirement: When worst-case \(O(\log n)\) performance is mandatory regardless of input distribution, self-balancing trees (such as AVL trees or Red-Black trees) must be employed to enforce rebalancing rotations.

12.4.4 Worked Examples: Construction and Search in a Skewed Tree

Consider constructing a left-skewed tree from descending sequence 10, 9, 8, 5, 4, 2, 1:

  1. Insert 10: Forms root.
  2. Insert 9: \(9 < 10 \implies\) left child of 10.
  3. Insert 8: \(8 < 10 \implies\) left; \(8 < 9 \implies\) left child of 9.
  4. Insert 5: Follows left chain to become left child of 8.
  5. Insert 4: Follows left chain to become left child of 5.
  6. Insert 2: Follows left chain to become left child of 4.
  7. Insert 1: Follows left chain to become left child of 2.

At no point does any node acquire a right child. Every node has degree 1, forming a single linear strand.

#### Searching for Target Key 1:

  • Comparison 1: At node 10. \(1 < 10 \implies\) branch left.
  • Comparison 2: At node 9. \(1 < 9 \implies\) branch left.
  • Comparison 3: At node 8. \(1 < 8 \implies\) branch left.
  • Comparison 4: At node 5. \(1 < 5 \implies\) branch left.
  • Comparison 5: At node 4. \(1 < 4 \implies\) branch left.
  • Comparison 6: At node 2. \(1 < 2 \implies\) branch left.
  • Comparison 7: At node 1. \(1 == 1 \implies\) Match found!

Result: Locating the minimum element took 7 comparisons in a 7-node tree, exactly matching the \(O(n)\) traversal cost of a singly linked list. Sense-check: Because no right branches exist, each comparison eliminates only a single node rather than half the tree. The recurrence \(T(n) = T(n - 1) + O(1)\) unrolls to \(\sum_{i=1}^n c = O(n)\).

Common Pitfalls:

  • Assuming sorted input is optimal: In many algorithms (like binary search on an array), sorted input is ideal. In an unaugmented BST, sorted input triggers the absolute worst-case behavior!
  • Conflating Big-O and Theta: Quoting \(\Theta(n)\) as the average search time. BST search is \(\Theta(\log n)\) on average, but \(O(n)\) in the worst-case skewed scenario.

12.4.5 Student Questions and Answers

Q: If we choose 10 as the root node and insert smaller values, what will be on the right side? A: If all subsequent elements inserted are smaller than 10, no elements will ever be placed on the right side. The right child pointers of all nodes will remain null, resulting in a left-skewed binary search tree.

12.4.6 Exam Notes

Exam note: A classic exam question asks what BST topology results from inserting an already-sorted sequence of numbers (e.g., in ascending order). Ascending order creates a right-skewed tree of height \(n\), while descending order creates a left-skewed tree of height \(n\). In both scenarios, the search time degrades to \(O(n)\).

Recap & Bridge: Skewed trees highlight the danger of unbalanced pointer structures, where unrolled recurrences reveal linear \(O(n)\) complexity. Conversely, when a binary search tree remains balanced, each comparison discards half the remaining nodes, reducing search time down to \(\Theta(\log n)\) (Section 12.5).

12.4.7 Real-World & Domain Connections

In database query engines and key-value stores (such as RocksDB or LevelDB), data frequently arrives in sorted order (for example, time-series events or auto-incrementing transaction IDs). If an unaugmented binary search tree were used as the primary index, the structure would instantly collapse into a skewed tree, turning fast point-lookups into sequential scans across disk blocks. To protect systems against this pathology, database engines mandate self-balancing B+ trees and Red-Black trees that automatically perform pointer rotations when skew begins to form.

12.5 Binary Search Tree Search Algorithm and Recurrence Analysis

If you have a database or directory containing one million records, how many records do you actually need to inspect to find a specific key? Because every comparison in a balanced binary search tree cuts the remaining candidate records in half, you never need to check more than twenty records.

The primary computational justification for using a binary search tree is its ability to perform fast logarithmic searches by dividing the candidate search space in half at each step.

To picture this exponential reduction, consider the classic game of searching a printed telephone directory. When looking up a name, you do not read from page 1 sequentially. Instead, you open to the exact middle page. If your target name appears alphabetically later than the middle entry, you discard the entire first half of the directory. You then split the remaining half at its midpoint and repeat. After only 20 splits, a directory of over one million pages is reduced to a single target name (\(2^{20} = 1{,}048{,}576\)). The analogy breaks when modifying data: inserting a new page into a physical bound directory requires reprinting the book, whereas a binary search tree performs dynamic insertions and deletions in the same logarithmic time.

12.5.1 The BST Search Algorithm

Searching for a target value \(k\) in a binary search tree proceeds iteratively or recursively starting from the root node.

Algorithm: BST_Search(root, k)
Input: root node of BST, target key k
Output: pointer to node with key k, or NULL if not found

1. current = root
2. while current is not NULL:
3.     if k == current.key:
4.         return current               // Key found
5.     else if k < current.key:
6.         current = current.left       // Discard right subtree
7.     else:
8.         current = current.right      // Discard left subtree
9. return NULL                          // Key does not exist

At every step where \(k \ne \text{current.key}\), the algorithm evaluates whether \(k\) is smaller or larger than the current node key. Because of the BST invariant:

  • If \(k < \text{current.key}\), the target key cannot possibly exist in the right subtree. The right subtree is completely ignored.
  • If \(k > \text{current.key}\), the target key cannot possibly exist in the left subtree. The left subtree is completely ignored.

The iterative implementation executes with \(O(1)\) auxiliary memory. A recursive formulation requires \(O(h)\) call stack frames, where \(h\) is the tree height.

12.5.2 Recurrence Relation and Halving Analysis

When the binary search tree is reasonably balanced, each comparison discards about half of the remaining nodes:

\[ n \to \frac{n}{2} \to \frac{n}{4} \to \frac{n}{8} \to \dots \to \frac{n}{2^k} \to 1 \]

where \(n \in \mathbb{N}\) is the total number of nodes, and \(k\) is the number of comparison steps performed. The verbal explanation details: "when I start with n, in the next step I am coming to n by 2, again n by 4, again n by 8, all the way till n by 2 to the power k... it means that my time complexity of search operations in a binary search tree is being reduced from order of n to order of log n."

Setting the remaining problem size to 1:

\[ \frac{n}{2^k} = 1 \implies 2^k = n \implies k = \log_2 n \]

Formally, the divide-and-conquer recurrence relation for searching a balanced binary search tree is:

\[ T(n) = T\left(\frac{n}{2}\right) + O(1) \]

where \(T(n)\) is the running time on an input of size \(n\), and \(O(1)\) accounts for the single comparison and branch selection at the current node.

We solve this recurrence using the Master Theorem. The standard Master Theorem equation is:

\[ T(n) = a T\left(\frac{n}{b}\right) + f(n) \]

Here, the recurrence parameters are:

  • \(a = 1\) (we branch into exactly one subproblem: left or right, never both)
  • \(b = 2\) (the candidate search space is halved at each step)
  • \(f(n) = O(1) = \Theta(1)\) (constant comparison and pointer dereference work per node)

Now, evaluate the critical exponent:

\[ n^{\log_b a} = n^{\log_2 1} = n^0 = 1 \]

Since \(f(n) = \Theta(1) = \Theta\left(n^{\log_b a}\right)\), Case 2 of the Master Theorem applies directly:

\[ T(n) = \Theta\left(n^{\log_b a} \log n\right) = \Theta(1 \cdot \log n) = \Theta(\log n) \]

So the simple structural ordering condition reduces search time from linear \(O(n)\) down to logarithmic \(\Theta(\log n)\).

Scope & Assumptions:

  • Balance Dependency: The \(\Theta(\log n)\) tight bound strictly assumes tree balance. If insertions cause the tree to skew, the recurrence becomes \(T(n) = T(n - 1) + O(1)\), and search degrades to \(O(n)\).
  • Independent Subproblems: The Master Theorem applies here because search discards the non-selected subtree entirely (\(a = 1\)). In contrast, traversal-based searches that explore both branches require \(a = 2\), yielding \(T(n) = 2T(n/2) + O(1) \implies \Theta(n)\).

12.5.3 Worked Example: Searching for an Element in a Balanced BST

Consider a balanced BST containing keys \(\{10, 15, 18, 20, 25, 30, 35\}\) with root 20:

  • Left child of 20: 15; Right child of 20: 30
  • Left child of 15: 10; Right child of 15: 18
  • Left child of 30: 25; Right child of 30: 35

Search for target key \(k = 30\):

  1. Step 1: Compare target 30 with root 20.
  • Is \(30 == 20\)? No.
  • Is \(30 > 20\)? Yes. Move to the right child: current = 30.
  • The entire left subtree containing \(\{10, 15, 18\}\) is discarded in a single operation.
  1. Step 2: Compare target 30 with node 30.
  • Is \(30 == 30\)? Yes. Element found!
  • End search and return pointer to node 30.

The target was located in only 2 comparisons, compared to up to 7 comparisons required in an unordered list or degenerate tree.

Result: Target key 30 found in 2 comparisons. Sense-check: For \(n = 7\) nodes, a balanced binary tree has height \(h = \lfloor \log_2 7 \rfloor = 2\). The maximum number of comparisons to locate any key or declare it absent is \(h + 1 = 3\). The 2 comparisons performed confirm adherence to the logarithmic bound.

Common Pitfalls:

  • Omitting the Master Theorem base conditions: In academic examinations, students frequently write "by Master Theorem, \(O(\log n)\)" without specifying \(a = 1, b = 2, f(n) = \Theta(1)\) or checking Case 2.
  • Ignoring non-balanced cases: Quoting \(\Theta(\log n)\) as the time complexity without explicitly prefixing that the tree must be balanced.

12.5.4 Student Questions and Answers

Q: What is the time complexity if we start at the root, choose either left or right, and repeat until we find the element or reach a null pointer? A: The time complexity is O(log n) on average for a balanced tree because half of the candidate tree is discarded at each step. However, if the tree is skewed into a single line, the search time degrades to O(n) in the worst case.

12.5.5 Exam Notes

Exam note: When solving recurrence questions on exams, state the base recurrence \(T(n) = T(n/2) + O(1)\) explicitly before citing Master Theorem case 2. Be prepared to explain that \(\Theta(\log n)\) applies to the balanced average case, whereas \(O(n)\) applies to the worst-case skewed tree.

Recap & Bridge: BST search cuts runtime to \(\Theta(\log n)\) by halving the active tree at every step. While search and insertion are straightforward, deleting a node — especially one with two children — requires finding its immediate adjacent in-order neighbor to preserve tree connectivity (Section 12.6).

12.5.6 Real-World & Domain Connections

In high-throughput key-value storage engines and in-memory caches (such as Memcached, Redis sorted sets, and database buffer pools), balanced search trees index millions of memory records. When an incoming network request arrives with a key query, the storage engine runs binary search descent across CPU caches. Because each branch halves the search space, a tree with one billion records can be searched in about 30 pointer dereferences (\(\log_2 10^9 \approx 30\)), delivering microsecond-level query latencies.

12.6 In-Order Predecessor and In-Order Successor

If you must remove a critical hub node with two subtrees from a binary search tree, how do you choose a replacement node that keeps every single left and right branch valid? You replace it with its immediate sorted neighbor — its in-order predecessor or in-order successor.

The concepts of in-order predecessor and in-order successor are essential tools for navigating binary search trees and form the algorithmic foundation for the node deletion operation.

To understand why these nodes matter, imagine an organized marathon where runners line up in ascending bib order: \([10, 15, 18, 20, 25, 30, 35]\). If runner #20 must step off the course, who can take their exact physical slot without disrupting the sorted order of the remaining runners? Only runner #18 (the nearest runner behind them) or runner #25 (the nearest runner ahead of them). In a binary search tree, the in-order predecessor is the largest key that is smaller than the target, and the in-order successor is the smallest key that is larger than the target. The analogy breaks when moving between elements: runners stand in a single physical line, whereas BST nodes are linked through parent and child pointer graphs.

12.6.1 Concept and Purpose in Node Deletion

In an in-order traversal of a binary search tree, all keys appear in strictly sorted ascending order. For any node \(x\):

  • The in-order predecessor of \(x\), \(\text{pred}(x)\), is the node that immediately precedes \(x\) in the sorted in-order traversal:

\[ \text{pred}(x) = \arg\max_{u \in T} \{ \text{key}(u) \mid \text{key}(u) < \text{key}(x) \} \]

  • The in-order successor of \(x\), \(\text{succ}(x)\), is the node that immediately succeeds \(x\) in the sorted in-order traversal:

\[ \text{succ}(x) = \arg\min_{v \in T} \{ \text{key}(v) \mid \text{key}(v) > \text{key}(x) \} \]

where \(T\) is the binary search tree containing node \(x\).

These two nodes are critical when deleting a node \(x\) with two children. Deleting a node with two children cannot be performed by simply dropping pointers, as that would sever two disjoint subtrees. The standard deletion algorithm:

  1. Locates either the in-order predecessor \(\text{pred}(x)\) or the in-order successor \(\text{succ}(x)\).
  2. Copies the key of that predecessor or successor into node \(x\).
  3. Recursively deletes the predecessor or successor node from its original location. Because the predecessor (or successor) is an extremum within its subtree, it is guaranteed to have at most one child, reducing the problem to a trivial deletion case.

12.6.2 In-Order Predecessor Determination Rules

To determine the in-order predecessor of a node \(x\), we evaluate two mutually exclusive structural cases:

#### Case 1: Node \(x\) has a Left Subtree If node \(x\) has a non-empty left child (\(x.\text{left} \ne \text{null}\)), its in-order predecessor is the node containing the maximum value in its left subtree.

  • Procedure: Step once to the left child (\(x.\text{left}\)), then follow right child pointers as far as possible until reaching a node with no right child.
  • This rightmost node in the left subtree is the in-order predecessor:

\[ \text{pred}(x) = \text{find\_max}(x.\text{left}) \]

The verbal description from the lecture states: "for a node x if it has two children, then in order predecessor is the child that has got the maximum value in its left subtree... this is the maximum value in its left subtree."

#### Case 2: Node \(x\) does not have a Left Subtree If node \(x\) has no left child (\(x.\text{left} = \text{null}\)), its predecessor cannot be a descendant. Instead, it must be an ancestor.

  • Procedure: Ascend the tree following parent pointers. The in-order predecessor is the first left ancestor — the lowest ancestor of \(x\) whose right child is also an ancestor of \(x\) (or is \(x\) itself).
  • If ascending all the way to the root never involves a step from a right child, node \(x\) is the absolute minimum node in the tree and has no in-order predecessor.

The verbal description notes: "if your node doesn't have a left child then who will become the predecessor? The first left ancestor will become the predecessor."

12.6.3 In-Order Successor Determination Rules

Symmetrically, to determine the in-order successor of a node \(x\), we evaluate two structural cases:

#### Case 1: Node \(x\) has a Right Subtree If node \(x\) has a non-empty right child (\(x.\text{right} \ne \text{null}\)), its in-order successor is the node containing the minimum value in its right subtree.

  • Procedure: Step once to the right child (\(x.\text{right}\)), then follow left child pointers as far as possible until reaching a node with no left child.
  • This leftmost node in the right subtree is the in-order successor:

\[ \text{succ}(x) = \text{find\_min}(x.\text{right}) \]

The verbal explanation notes: "the node that is having the minimum value in its right subtree is a successor... in its right subtree this is the node that has got the minimum value that is the successor in order successor."

#### Case 2: Node \(x\) does not have a Right Subtree If node \(x\) has no right child (\(x.\text{right} = \text{null}\)):

  • Procedure: Ascend parent pointers until encountering the first right ancestor — the lowest ancestor of \(x\) whose left child is also an ancestor of \(x\) (or is \(x\) itself).
  • If ascending to the root never involves a step from a left child, node \(x\) is the absolute maximum node in the tree and has no in-order successor.

Scope & Assumptions:

  • Parent Pointer Requirement: Case 2 navigation (when the relevant subtree is null) requires either explicit parent pointers in each node or an auxiliary search stack recorded during the initial descent from the root.
  • Boundary Extremum Limits:
  • If \(x\) is the global minimum node in \(T\), \(\text{pred}(x) = \text{null}\).
  • If \(x\) is the global maximum node in \(T\), \(\text{succ}(x) = \text{null}\).

Algorithms must check for null before dereferencing predecessor or successor pointers.

12.6.4 Worked Example: Determining Predecessor and Successor

Consider the binary search tree:

  • Root: 20
  • Left subtree of 20: 15 (with left child 10 and right child 18)
  • Right subtree of 20: 30 (with left child 25 and right child 35)

The complete in-order traversal of this tree is:

\[ 10, 15, 18, 20, 25, 30, 35 \]

#### 1. Finding Predecessor and Successor for Root 20:

  • Node 20 has two children.
  • To find the in-order predecessor: Move to left child 15. In the left subtree, traverse right to find the maximum value. Node 18 has no right child. So, 18 is the in-order predecessor of 20. In the sorted sequence, 18 immediately precedes 20.
  • To find the in-order successor: Move to right child 30. In the right subtree, traverse left to find the minimum value. Node 25 has no left child. So, 25 is the in-order successor of 20. In the sorted sequence, 25 immediately succeeds 20.

#### 2. Finding Predecessor for Node 25 (No Left Child):

  • Node 25 has no left child.
  • Ascend to parent: parent of 25 is 30. Node 25 is the left child of 30, so 30 is larger than 25 (30 cannot be the predecessor).
  • Ascend to parent of 30: root 20. Node 30 is the right child of 20.
  • Because 20 is the first ancestor reached where the path comes from the right subtree, 20 is the first left ancestor.
  • So, the in-order predecessor of 25 is 20. Looking at the sorted sequence, 20 immediately precedes 25.

Result Summary:

  • Predecessor of 20: 18
  • Successor of 20: 25
  • Predecessor of 25: 20

Sense-check: Inspecting the sorted in-order sequence \([10, 15, 18, 20, 25, 30, 35]\) confirms that 18 immediately precedes 20, 25 immediately succeeds 20, and 20 immediately precedes 25.

Common Pitfalls:

  • The Parent Misconception: Assuming that a node's parent is automatically its predecessor. If the node has a left subtree, the predecessor is the maximum descendant in that left subtree, which is never the parent.
  • Confusing Predecessor and Successor Direction: Stepping right instead of left when searching for a predecessor descendant, which inadvertently locates an arbitrary descendant rather than the maximum smaller key.

12.6.5 Student Questions and Answers

Q: For a given node, is its parent always its in-order predecessor? A: No, the parent is not always the predecessor. If the node has two children, its in-order predecessor is the node with the maximum value in its left subtree, which is a descendant node rather than a parent. The parent can be an in-order predecessor only when the node has no left child and is itself a right child.

12.6.6 Exam Notes

Exam note: A common exam question asks students to identify the in-order predecessor or successor of a given node in a complex BST diagram. Always double-check by writing out the sorted in-order traversal of the keys: the predecessor is the immediate left neighbor, and the successor is the immediate right neighbor.

Recap & Bridge: Predecessor and successor rules provide deterministic \(O(h)\) lookups for adjacent sorted values. They solve the hardest case of BST node deletion by providing a safe single-child substitute. This algorithmic elegance underpins standard associative containers and database storage engines.

12.6.7 Real-World & Domain Connections

In database query engines and standard template libraries (such as C++ std::map and std::set), bidirectional iterators rely on predecessor and successor routines. When executing it++ or it-- on a std::map::iterator, the runtime does not perform an expensive tree search from the root. Instead, it applies these exact two-case pointer navigation rules from the current node. Although an individual successor step can take \(O(h)\) time in the worst case, traversing an entire tree of \(n\) nodes using successive calls visits each tree edge at most twice, yielding an optimal amortized time complexity of \(O(1)\) per step.

Key Industry Applications

While basic binary search trees risk degrading to \(O(n)\) performance under skewed insertion sequences, self-balancing BST variants (such as Red-Black Trees, AVL Trees, and B-Trees) form the core backbone of high-performance modern software infrastructure.

Database Indexing and Storage Engines

Relational database management systems (such as PostgreSQL, MySQL InnoDB, and SQLite) and NoSQL stores use tree-based index structures derived from BST concepts. Database indices allow disk-based storage engines to execute point queries (SELECT * WHERE id = 42) and range scans (WHERE age BETWEEN 20 AND 30) in logarithmic time rather than scanning millions of rows sequentially. While memory-resident algorithms use binary trees, disk storage scales this principle to multi-way balanced B+ trees to minimize disk read operations.

Associative Containers in Standard Libraries

Modern systems programming languages rely on balanced binary search trees to implement ordered associative containers:

  • In C++, the Standard Template Library (STL) implements std::map, std::set, std::multimap, and std::multiset using balanced Red-Black trees.
  • In Java, java.util.TreeMap and java.util.TreeSet are built directly upon Red-Black BST implementations.

These data structures guarantee \(O(\log n)\) search, insertion, and deletion while maintaining elements in continuous sorted order, enabling immediate predecessor and successor lookups.

Dynamic Sorting and Streaming Quantiles

In financial market ticker processing and telemetry stream analysis, systems must continuously maintain live sorted order over streaming data. Augmented binary search trees (order-statistic trees) store subtree node counts, allowing real-time retrieval of the median, minimum, maximum, and arbitrary percentiles in \(O(\log n)\) time as trades arrive.

Compilers and Symbol Tables

Compilers and interpreter runtimes use binary search trees to implement symbol tables during lexical analysis and parsing. Variable identifiers, function signatures, and lexical scopes are inserted into tree structures to allow instant identifier lookup and scope resolution during program compilation.

Exam Guidance Summary

High-Yield Exam Topics

  1. Global Versus Local Invariant Checking: Examination problems routinely present tree diagrams that satisfy local parent-child ordering but violate global ancestor bounds. Remember that a node in the right subtree of root \(R\) must satisfy \(\text{key} > R\), even if it is smaller than its immediate parent. Always track the open interval \((L_x, R_x)\) when verifying a binary search tree.
  2. Worst-Case Skewed Tree Analysis: Be prepared to explain how inserting sorted or reverse-sorted input into a standard BST produces a left-skewed or right-skewed degenerate tree with height \(h = n\) and search complexity \(O(n)\).
  3. Master Theorem Application for Balanced BST: Write out the divide-and-conquer recurrence \(T(n) = T(n/2) + O(1)\) and explicitly apply Master Theorem case 2 (\(a = 1, b = 2, f(n) = O(1)\)) to establish the \(\Theta(\log n)\) average-case bound.
  4. Predecessor and Successor Identification:
  • Node with two children: Predecessor is the maximum in the left subtree; Successor is the minimum in the right subtree.
  • Node without left/right children: Predecessor is the first left ancestor; Successor is the first right ancestor.
  1. Heap Versus BST Distinctions: Never confuse min-heaps with binary search trees. A min-heap offers \(O(1)\) access to the minimum element but does not maintain total key ordering, requiring \(O(n)\) time for general key search.
