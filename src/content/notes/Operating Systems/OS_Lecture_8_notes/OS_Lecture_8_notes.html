8.1 Concurrent Execution and Process Interaction

8.1.1 Why We Need Concurrent Execution

One CPU core can run only one instruction at a time. So how does a laptop with one processor play music, download a file, and run a compiler at the same time? The answer is concurrency — and this lecture is about what happens when the processes sharing the machine start touching the same data.

The goal is to make maximum use of the CPU and improve system efficiency. To reach that goal, we use multiprogramming or multiprocessing, and both of those need concurrent operation. Concurrency is what lets the machine keep working while one process waits. The question is how to achieve this concurrent cooperation in a uniprocessor system versus a multiprocessor system.

Three terms that look alike but are not the same:

  • Multiprogramming: many programs are kept loaded in main memory at once, and the CPU switches among them. If one process waits for input or output, the CPU starts another process instead of sitting idle. This is the classic way to get concurrency on a single-processor machine.
  • Multiprocessing: the system has more than one processor, and several processes genuinely run at the same time, one per processor.
  • Concurrent execution: several processes make progress in the same time span — either by taking turns (interleaving) or by running side by side (overlapping). "Concurrent" means overlapping in time; it does not automatically mean simultaneous in the same instant.

Both multiprogramming and multiprocessing depend on concurrency. Concurrency is what lets the machine keep working while one process waits — for example, while process A is blocked waiting for a disk read, process B can use the CPU to do arithmetic. Without concurrency, the CPU would sit empty during every wait, and a single slow input or output operation would stall the entire system.

8.1.2 Interleaved Execution in Uniprocessor Systems

In a uniprocessor system, processes execute in interleaved fashion, one after another: first P1, then some part of P2, then P3. This does not mean P1 finished completely. The scheduler may change the order at any time, so after P1 we may get P2 or we may get P3, even under FCFS (first-come, first-served) type scheduling. There is a delay in between each switch, and that delay reduces the efficiency of the system. Every context switch costs time, and the system does no useful work during that gap.

A context switch (changing the CPU from one process to another — saving one process's register values and program counter, loading the next process's) is pure overhead: while it happens, neither process makes progress.

Worked example: how much time do context switches waste?

Suppose three processes P1, P2, P3 share one CPU. The scheduler gives each process 5 milliseconds of CPU time at a time (a time quantum), then switches. Each context switch costs 1 millisecond.

  • The three processes together need 100 ms of useful CPU work: P1 needs 40 ms, P2 needs 35 ms, P3 needs 25 ms.
  • With a 5 ms quantum, the CPU does 5 ms of work, then switches, then 5 ms of work, then switches, and so on. Completing 100 ms of work needs 100 ÷ 5 = 20 switches.
  • Each switch costs 1 ms, so switching overhead = 20 × 1 ms = 20 ms.
  • Total time on the CPU = 100 ms (useful) + 20 ms (overhead) = 120 ms.

The system's efficiency is 100/120 ≈ 0.83, meaning about 83% of the CPU time went into real work and 17% went into switching.

Sense-check: fewer, longer slices mean fewer switches; if the quantum were 10 ms, only 10 switches would occur, so efficiency rises to 100/110 ≈ 0.91. The trade-off is that long slices make short processes wait longer — the delay between switches is the price of sharing the CPU.

A key point the professor stressed: interleaving does not mean a process runs to completion. Under FCFS, a process that arrives first is served first, but the scheduler can still decide how much of P1 runs before P2 gets a turn — the order in which processes get their turns can change at any time.

8.1.3 Overlapped Execution in Multiprocessor Systems

In a multiprocessor system the processes are overlapped. There is no delay between them, because at least one process is in execution on every processor. That leads to genuine concurrent execution: several processes make progress in the same instant, not just one at a time. With two processors, P1 can run on processor 1 while P2 runs on processor 2 in the very same clock cycle — the progress is not merely alternating, it is simultaneous.

Dimension Uniprocessor (multiprogramming) Multiprocessor (multiprocessing)
Kind of concurrency Interleaved: processes take turns Overlapped: processes run in parallel
Same-instant progress No, only one process at a time Yes, one process per processor at a time
Delay between processes Yes — every context switch costs time No — the other processor keeps working during any single-processor wait
Processor idle while one process waits CPU can be reused via switching Other processors keep running unaffected

When to pick which: a multiprocessor gives true parallelism and hides switch overhead, but it is more expensive and needs special care — two instruction streams can genuinely interleave at the hardware level, which is exactly why the synchronization tools in this lecture exist.

8.1.4 How Processes Interact

Processes interact in three ways. First, some processes are unaware of the existence of other processes; they just compete for the resources. Second, some processes are indirectly aware of each other, and they exhibit cooperation. Third, some processes are directly aware of each other and interact directly.

The three levels of process interaction:

  1. Competition (unaware): each process runs independently and only finds the others by competing for the same resource — two print jobs competing for one printer, two programs competing for memory. They do not know each other exists, but the operating system still must keep their use of the shared resource from colliding.
  2. Cooperation by sharing (indirectly aware): the processes know a shared object exists — a shared buffer, a shared file, a shared variable — and they coordinate through it. The producer and consumer of the next section are the classic example.
  3. Cooperation by communication (directly aware): the processes exchange information directly, through messages or signals, and each knows the other's identity.

Whatever the case, at the end of the day each of these processes competes for some resource, and that leads to deadlock, mutual exclusion, or starvation. All of those outcomes are examined below. Mutual exclusion is the safe condition we want to guarantee (at most one process inside the critical section at a time); deadlock and starvation are the failure modes we want to avoid — and all three can appear even in the simplest competition for a single resource.

Common traps in this section:

  • Concurrency is not parallelism. Interleaved execution is concurrent but never simultaneous; on a uniprocessor, "parallel" is impossible.
  • FCFS does not mean "finish what you started". Even a first-come-first-served scheduler can hand the CPU to another process mid-way; only the order of selection is first-come, not the completion.
  • Do not ignore context-switch cost. In the worked example above, 17% of the CPU time disappeared into switching — an efficiency question that appears often in exams.

The takeaway: concurrent execution of cooperating processes is the root cause of the problems that follow — a process may be kept waiting forever (starvation), every process may end up stuck (deadlock), or two processes may both enter a protected region (mutual exclusion violated). The rest of this lecture builds the machinery — critical sections, locks, semaphores, monitors — that keeps these outcomes under control.

8.2 Deadlock and Starvation

8.2.1 Waiting on a Resource: Starvation versus Deadlock

What is the difference between a process that waits forever alone and a system where everyone waits forever together? One is called starvation, the other deadlock — and telling them apart is one of the first exam questions in this module.

Take two processes, P1 and P2, though there may be many more. Both compete for the same resource R, and the resource is currently being used by one of them, or by another process altogether — two processes competing for one resource, with nothing forcing the holder to give it up. None of these processes stops using the resource. P1 needs R, so P1 has to wait, and we do not know how long. If the wait goes on indefinitely, or if some other process P3 also wants to access the same resource R and R is held by someone else, making P1 and P3 wait for a very long time, we call that starvation. Starvation is a process-level problem: a particular process is kept waiting forever.

  • Starvation (also called indefinite blocking): one specific process that needs a resource is overlooked again and again, so it waits for an unbounded time. The rest of the system may be working normally — only that process is stuck.
  • Deadlock: a set of two or more processes, each waiting for a resource or event that can only be supplied by another process in the same set, so all of them are permanently blocked. No process in the deadlocked set can make progress.
  • The one-resource picture: in starvation, the resource is eventually released — but somebody else always gets it first. In deadlock, the resource is never released, because whoever holds it is itself stuck.

If, instead, all the processes need the resource but the resource is currently unavailable, then everything has to wait, and that leads to deadlock. A deadlock can arise from any number of processes waiting for resources that are used by some other process or that are simply not available. The whole set of processes is stuck, not just one of them.

An everyday picture (from the reference texts): four cars arrive at a four-way stop at the same time, and each waits for the car on its right to move first. Each car holds one quadrant of the intersection and needs the quadrant another car holds. Every driver is waiting for an event only someone else can cause — nothing moves. That is a deadlock of the whole set. If only one car were waiting forever because the others keep going first, that would be starvation.

Scope — when does a "wait" become a problem?

  • The problems above assume the resource is never released by whoever holds it (or that the holder is always preferred). If the holder finishes quickly, a short wait is normal and harmless.
  • Starvation and deadlock are properties of long-run behavior: they are defined by "waiting indefinitely", not by "waiting for a while".
  • A waiting process can be a victim of its own priority: in priority-based systems a low-priority process can starve because higher-priority processes always win the resource (we return to this in the semaphore section with priority inversion).

8.2.2 Why Cooperating Processes Need Synchronization

These cooperating or computing processes always cause problems when they are executed concurrently. That is why we need synchronization.

Worked example: one resource, two waiters — starvation, then deadlock

Setup: there is one resource R. Processes P1, P2, P3 all need it.

Part A — starvation: P3 grabs R and keeps using it without ever releasing it. P1 asks for R and waits. Then P2 asks for R and waits. P1 and P2 are both waiting indefinitely: neither can enter the resource while R stays held, and nobody releases it. This indefinite wait of P1 and P2 is starvation — the two processes are blocked, while the holder P3 continues.

Part B — deadlock: now suppose the same competition involves every process in the system: P1 waits for R held by P2, P2 waits for R held by P3, and P3 waits for R held by P1. Each process is waiting for an event — a release — that only another waiting process can produce. None of them can proceed, because every release is waiting on another release. That is deadlock: the whole set is stuck, not just one process.

Sense-check: the difference is who waits. Starvation leaves one process (or a few) waiting forever while the system continues; deadlock freezes the whole set of processes, because every wait can only be ended by someone who is also waiting.

The takeaway: concurrent execution of cooperating processes is the root cause, and synchronization is the remedy we study for the rest of this material. Synchronization means imposing rules on how processes access shared resources — who may enter when, and who must wait — so that indefinite waits and whole-system freezes do not happen. The next sections build the vocabulary: the critical section, the race condition, and the three requirements any good synchronization solution must satisfy.

Recap: starvation is a single process waiting forever for a resource; deadlock is a whole set of processes waiting forever on each other. Both grow out of concurrent execution of cooperating processes, and both are exactly what synchronization mechanisms are designed to prevent. Next we look at the shared region of code that must be protected — the critical section.

8.3 The Critical Section and the Race Condition

8.3.1 Defining the Critical Section

Two processes update the same counter, and the final value depends on which one ran last. The result is wrong even though every instruction was correct. The place where the damage happens has a name — the critical section — and protecting it is the heart of process synchronization.

Synchronization means sharing resources among processes so that concurrent access to a shared resource can take place safely, minimizing the chance of inconsistent data. Whatever the processes, each one has some section of code — a code segment — that we call its critical section. Every process has its own critical section, and that is where the shared resource or shared variable is used.

Consider a variable a. Process P1 uses a, and process P2 also uses a. If both processes try to use the same variable at overlapping times, the data becomes inconsistent. The particular section of code that uses a is the critical section. The use of a shared resource must happen as an atomic action: it should not be done halfway, and the process should not leave and come back. Either the operation completes fully, or it does not happen at all. That kind of code segment is called a critical section. The workflow is: first define the critical section, then enforce mutual exclusion in order to get concurrency.

Every process that uses a shared resource has the same four-part shape:

  1. Entry section: code that asks permission to enter the critical section.
  2. Critical section: the segment where the shared variable or shared resource is actually used — this is the part that must not run while another process is inside its own critical section.
  3. Exit section: code that says permission is no longer needed.
  4. Remainder section: everything else the process does.

A race condition (the trouble we are guarding against) is a situation where several processes read and write the same data concurrently and the final result depends on the particular order in which the accesses happen. The critical-section problem is: design the entry/exit protocol so that this dependence disappears.

8.3.2 The Producer-Consumer Example and the Race Condition

The famous example is the producer-consumer problem. The producer continuously produces an item, and the consumer continuously consumes items until the buffer becomes empty. The two must be synchronized. If the consumer tries to consume an item when the producer has not produced any item, the action is not synchronized.

When processes share a common variable, the updation of that variable may not happen at the same time. It may happen at different times with different values, and that leads to inconsistent data. We call the counter an inconsistent variable here, because at the end the value of the counter with respect to the consumer is 5 (five), while with respect to the producer it may be a different value, 86 (eighty-six). One process's view of the shared counter and another process's view disagree, and that is the race condition. To solve the race condition, we solve the critical section problem.

Worked example: why "counter = counter + 1" is not one step

On a typical machine, the statement counter++ (used by the producer) is compiled into three machine instructions:

register1 = counter      ; load the current value
register1 = register1 + 1 ; add one
counter = register1      ; store the new value

and counter-- (used by the consumer) becomes:

register2 = counter
register2 = register2 - 1
counter = register2

Suppose counter holds 5. The producer and consumer run concurrently, and their instructions interleave like this:

Step Process Instruction counter after
T1 producer register1 = counter → 5 5
T2 consumer register2 = counter → 5 5
T3 producer register1 = 5 + 1 = 6 5
T4 consumer register2 = 5 − 1 = 4 5
T5 producer counter = 6 6
T6 consumer counter = 4 4

Both processes read the same old value 5, each computes its own result, and the last store wins. The final counter is 4 — meaning "four buffers full" when in fact five buffers are full. With a different interleaving (stores in the other order), the final value is 6.

The professor's version: the consumer's view of the counter settles on 5 (five) while the producer's view can settle on a totally different number such as 86 (eighty-six) — the two processes simply disagree about the shared counter's value. That disagreement is the race condition: the outcome depends on which process happened to store last, not on the logic of either process.

Sense-check: every individual instruction was executed correctly; the result is still wrong because the read-modify-write of the counter is not atomic. Making the read, the update, and the write one indivisible action — one critical section — fixes the race.

8.3.3 Atomic Actions in the Critical Section

The shared-variable access inside the critical section is atomic: it must either complete fully or not take place at all. It should not leave the shared data half-updated. This "all or nothing" property is the requirement that all synchronization solutions below are built to guarantee.

Scope — what atomicity covers and what it does not:

  • Atomicity is about the shared access, not the whole process: only the critical section needs the all-or-nothing guarantee; the rest of the process runs normally.
  • Atomic means "no other process can observe an intermediate state", not "the operation is fast". A slow but indivisible update is still atomic; a fast update interrupted halfway is not.
  • The interleaving in the worked example assumed a preemptive scheduler — one that may take the CPU away mid-statement. On a nonpreemptive system (a process runs until it blocks or finishes), races are less common, but on modern multicore machines two processes can genuinely run at the same moment on different cores, so atomicity must be enforced by the synchronization scheme, not hoped for.

Recap: the critical section is the code segment where a shared resource is used; the access inside it must be atomic (complete fully or not at all). When two processes interleave inside that region, the shared variable becomes inconsistent — the race condition. The next section states the three requirements a solution to the critical-section problem must satisfy.

8.4 Requirements of the Critical Section Problem

Any solution to the critical-section problem must satisfy three requirements — mutual exclusion, progress, and bounded waiting — and rests on one assumption about process speed. These three plus the assumption are the yardstick against which every mechanism in this lecture (Peterson's solution, hardware locks, semaphores, monitors) is measured.

8.4.1 Mutual Exclusion

The first requirement is mutual exclusion: if a process is executing in its critical section, no other process should be executing in that critical section. That word is very, very important. At most one process is ever inside the critical section at a time.

Mutual exclusion means that at any instant, at most one process occupies its critical section — the region where the shared variable is used. If P1 is inside its critical section, P2 must be kept out of its own critical section until P1 leaves. This directly kills the race condition of section 8.3: with mutual exclusion, two processes can no longer interleave their read-modify-write steps on the same shared counter.

8.4.2 Progress

The second requirement is progress: if no process is executing in the critical section and some process wishes to enter it, then the selection of the process that will enter cannot be postponed indefinitely. Some eligible process must eventually be allowed in; the system cannot dither forever over who goes next.

Progress is about the system not freezing between critical-section visits. The precise rule: if the critical section is empty and some processes want to enter, only those processes that are not in their remainder sections participate in choosing the next entrant, and the choice must happen — it cannot be put off forever. A solution that sometimes lets everyone in quickly but under one unlucky interleaving lets no one in at all fails the progress requirement.

8.4.3 Bounded Waiting

The third requirement is bounded waiting: there is a bound on the number of times every other process is allowed to enter its critical section after a process has made a request and before that request has been granted. A process that asks to enter cannot be overtaken forever; after a limited number of entrances by others, its request must be granted.

Bounded waiting is a fairness guarantee. Suppose P0 makes its request at time t. The requirement says there exists some fixed number k (depending on the system, for example the number of processes) such that between time t and the moment P0 finally enters, no other process can enter more than k times. Without bounded waiting, a scheme could satisfy mutual exclusion and progress yet still let a hungry process be overtaken forever — starvation in disguise.

Worked example: bounded waiting with three processes

Three processes P0, P1, P2 compete for the critical section. Suppose the protocol guarantees "after a process requests entry, no more than two other entries may happen before it gets in".

  • P0 requests at time 0. Entries that follow: P1 enters and leaves (1st entry), P2 enters and leaves (2nd entry). At that moment P0 must be granted entry — the bound is 2, and allowing a third entry by P1 would break the promise.
  • The bound does not say P0 enters quickly; P1 and P2 may be fast and enter many times before P0's request. It only limits what happens after the request.
  • If the protocol instead let P1 and P2 alternate forever while P0 starves, mutual exclusion and progress would both hold — yet the solution would still be unacceptable, precisely because bounded waiting is violated.

Sense-check: bounded waiting is the requirement that turns "someone eventually enters" (progress) into "this particular process eventually enters" (fairness).

8.4.4 The Speed Assumption

One assumption supports all three requirements: each process executes at a nonzero speed. There is no assumption about the relative speeds of the processes. A process may be fast or slow, but it cannot make zero progress forever on its own — any waiting that occurs must be due to the synchronization scheme, not because a process simply stopped.

Assumption: each process executes at a nonzero speed; nothing is assumed about the relative speeds of the processes.

  • What it buys: a solution must work whether P1 is ten times faster than P2 or the other way around — the correctness arguments may never rely on speed ratios.
  • What breaks if it fails: if a process can run at zero speed (never advancing on its own), no protocol can tell a "stuck process" from a "waiting process", and the three requirements become untestable. In real systems this matters for crash handling: a process that dies inside its critical section leaves the resource locked forever, and the remaining processes deadlock or starve.
  • Notice how the assumption fits the definition of starvation: a process that is merely slow is not starved — a process that is kept from the resource by the scheme is.

Recap: a correct solution needs mutual exclusion (at most one process inside), progress (if the section is empty and someone wants in, someone gets in — no infinite dithering), and bounded waiting (after a request, only a bounded number of other entries may precede yours), all under the assumption that every process runs at nonzero speed. The next section tests these yardsticks against the first solution, Peterson's algorithm, and against hardware locks.

8.5 Peterson's Solution and Hardware-Based Synchronization

8.5.1 Peterson's Solution

Can two processes coordinate purely with shared variables, with no help from the hardware? Peterson's solution says yes — in principle. It is the classic software answer to the critical-section problem, and its structure (a "flag" saying who wants in, a "turn" deciding who goes) reappears inside later solutions.

The first solution we looked at was Peterson's solution. It is a software-based solution and it is applicable only for two processes. It works in principle, but it could not satisfy the hardware constraints, so we moved on to hardware-based synchronization support.

The two processes are P0 and P1. They share two data items:

  • turn: an integer saying whose turn it is to enter the critical section. If turn == i, process Pi is allowed to enter.
  • flag[]: a Boolean array saying which process is ready to enter. If flag[i] is true, Pi is ready.

The structure of process Pi (with Pj the other process, \(j = 1 - i\)):

while (true) {
    flag[i] = true;          // I want to enter
    turn = j;                // but I give the turn to the other process
    while (flag[j] && turn == j);   // wait while the other is ready and it is their turn
    // critical section
    flag[i] = false;         // I am done; the other may enter
    // remainder section
}

The clever part is the pairing of the two statements before the wait loop. Setting flag[i] = true says "I want to enter"; setting turn = j says "if we both want in at the same time, you go first." The last process to write turn loses the race and waits. If Pj does not want to enter (flag[j] false), Pi walks straight through.

Worked example: Peterson's solution in action

Two processes P0 and P1 both try to enter the critical section.

Case 1 — only P0 wants in: P0 sets flag[0] = true, then turn = 1. The wait condition checks flag[1] — false — so the loop body does not run. P0 enters the critical section immediately, and later sets flag[0] = false on exit.

Case 2 — both want in at the same time: P0 sets flag[0] = true, turn = 1; P1 sets flag[1] = true, turn = 0. The last assignment to turn wins — say P1's, so turn = 0. P0 checks flag[1] (true) and turn == 1? No, turn == 0 — so P0 enters. P1 checks flag[0] (true) and turn == 0? Yes — so P1 waits in the loop. When P0 finishes and sets flag[0] = false, P1's loop condition fails and P1 enters. The same reasoning works in the opposite order: exactly one process is ever inside, and the other waits at most one full visit by its rival.

Why the three requirements hold: mutual exclusion, because both processes can be inside only if flag[0] == flag[1] == true while turn is both 0 and 1 — impossible. Progress, because the waiting process can only be stuck on flag[j] && turn == j, a condition that dissolves as soon as Pj finishes and clears its flag. Bounded waiting, because Pi sets turn = j once and never changes it while waiting, so Pj can enter at most once before Pi.

Sense-check: after P0 enters and leaves, P1 is guaranteed the next entry — no third process can cut in, because there are only two processes.

Peterson's solution works in principle, but it rests on the assumption that writes to flag and turn happen immediately and in order. Modern processors reorder instructions and cache writes, so without hardware guarantees Peterson's solution may fail in practice — the professor's point that the software solution could not satisfy the hardware constraints. The course takes the next step: hardware that offers locking directly.

8.5.2 Hardware Support: Locks and Atomic Instructions

For hardware-based support, the approach differs between a uniprocessor and a multiprocessor. In both cases we need a special atomic instruction.

  • Uniprocessor: the simple approach is to disable interrupts while the shared variable is being modified. With interrupts off, no preemption can occur, so the current sequence of instructions runs without interruption. This is exactly how nonpreemptive kernels protect their data. But the trick fails on multiprocessors: stopping interrupts on all processors is slow, and message-passing the request to every processor delays every critical-section entry.
  • Multiprocessor: many modern systems provide hardware instructions that test-and-modify a word, or swap two words, atomically — as one uninterruptible unit. Two instruction streams on two different CPUs can still interleave at the hardware level, so ordinary load/store instructions are not enough; the atomic instructions are.

Two atomic hardware instructions are the standard tools:

  • Test-and-set (TestAndSet(lock)): atomically reads the current value of the lock variable and sets it to true, returning the old value. "Test and set" in one indivisible step — no other process can slip between the reading and the setting.
  • Swap (Swap(a, b)): atomically exchanges the contents of two words — for example, a global lock variable and a process-local key.

The standard pattern uses locks: the process must acquire the lock, and only then may it enter the critical section; after finishing, it releases the lock. Race conditions are prevented by requiring that critical regions be protected by locks — acquire before entering, release on exit.

Worked example: mutual exclusion with TestAndSet

Shared: a Boolean lock, initialized to false. Each process Pi runs:

while (TestAndSet(lock)) ;   // spin: keep trying until the lock was false
// critical section
lock = false;                // release: let someone else in

Trace with two processes P1 and P2:

  1. lock = false initially.
  2. P1 executes TestAndSet(lock): returns false and sets lock = true. P1 leaves the loop and enters the critical section.
  3. P2 executes TestAndSet(lock): returns true (P1 holds the lock) and sets lock = true again. The return value true makes P2 keep looping — it spins.
  4. P1 finishes, sets lock = false.
  5. P2's next TestAndSet(lock) returns false and sets lock = true; P2 enters.

At no point are P1 and P2 both inside: the atomic read-and-set means exactly one process ever sees the "was false" answer that lets it through.

The Swap variant works the same way with a global lock = false and a local key = true: each process swaps lock and key; whoever gets back false in key has acquired the lock.

Sense-check: the instructions give mutual exclusion, but the simple lock version above does not give bounded waiting — a fast process can win the lock again and again while a slow one spins. The hardware answer for that is a ticket-based TestAndSet scheme that hands the lock to waiting processes in a cyclic order.

This hardware approach mainly serves the hardware cases where the software solution fails, especially for multiprocessor systems where more than one instruction stream can interleave at the hardware level.

Pitfalls in this section:

  • Peterson's solution is two-process only. Applying it to three processes breaks mutual exclusion; applying it to modern hardware can break it too, because of instruction reordering and caching.
  • A plain test-and-set lock can starve a process — it has no bounded waiting. A process unlucky at the race can spin forever while others keep grabbing the lock.
  • Busy-waiting cost: the spinning loop wastes CPU cycles. It is acceptable when the critical section is short (a few instructions), not when it is long — the wait-loop below (semaphores) will fix this with blocking.

8.6 Semaphores

8.6.1 What a Semaphore Is

A single integer variable, touched only by two atomic operations, can solve the critical-section problem cleanly — and can also be misused into deadlock and starvation. That variable is the semaphore, the workhorse of this entire module.

A semaphore is a synchronization tool implemented as an integer variable. It is a software tool: no special hardware instruction is needed to reason about it, only a guarantee that its two operations run atomically. We call a variable a semaphore because we can perform two atomic operations on it: wait and signal. Both operations are atomic, meaning once an operation starts it will be completed soon; it will not be interrupted halfway.

Semaphore \(S\): an integer variable that counts the availability of a resource. Apart from its initialization, it is accessed only through two standard atomic operations:

  • wait (originally called \(P\), from the Dutch proberen, "to test"): the attempt to take one unit of the resource.
  • signal (originally called \(V\), from verhogen, "to increment"): the release of one unit of the resource.

Atomicity matters for both: when one process modifies the semaphore value, no other process can simultaneously modify the same value, and the test of the value and the change of the value happen as one indivisible step. If wait and signal could interleave, two processes could both read "1" and both enter the critical section.

8.6.2 The wait and signal Operations

The wait operation checks the semaphore value and tries to reduce it. Wait also tells us how many processes are in need of the resource and are waiting to enter the critical section. The signal operation helps one of the processes already waiting to enter the critical section actually get in, by increasing the semaphore value. When the value increases by one, one of the processes that was suspended may resume its operation and enter the critical section. Which one resumes depends upon the system scheduler.

Intuition: think of the semaphore as the count of free parking spaces in a lot. wait = "I take one space; if there were none, I stand in the queue at the gate." signal = "I leave, freeing one space; the gate lets the first queued car in." The value of the counter is the number of spaces currently free — and if the counter goes negative, the magnitude tells you how many cars are queued.

8.6.3 Counting and Binary Semaphores

There are two kinds of semaphores. A counting semaphore can take any integer value; there is no restriction on the value. A binary semaphore can hold only two values, 0 and 1, and it is very simple to implement. The binary semaphore is also called a mutex lock, short for mutual exclusion lock.

  • Counting semaphore: \(S\) may be any integer. It controls access to a resource with several identical instances — initialize \(S\) to the number of available instances, wait on each use, signal on each release. When \(S\) reaches 0, all instances are in use and further waiters block.
  • Binary semaphore (mutex lock): \(S \in \{0, 1\}\). It protects one resource. Initialize to 1, wait before entering the critical section, signal after leaving. A value of 1 means "free", 0 means "held".
  • One nuance: with a mutex, the process that locks must be the one to unlock; with a binary semaphore, a different process may legally signal. This is why the course uses "mutex" for the critical-section lock.

We use it like this: initialize the mutex to 1, then perform the wait operation, then the signal operation. The wait tells a process that wishes to enter the critical section to wait right there; it cannot enter until the process already executing in the critical section performs the signal. That earlier process performed its own wait, got in, and by signaling lets one of the suspended processes — P1, P3, or P4, any number may be waiting — enter the critical section, after which that process signals in turn. This is the main idea behind the semaphore.

Worked example: a mutex with three waiting processes

Initialize mutex = 1. Process P1 wants the critical section.

  1. P1 executes wait(mutex): the value 1 drops to 0, and P1 enters the critical section.
  2. While P1 is inside, P3 executes wait(mutex): the value is 0, so P3 must wait. Then P4 executes wait(mutex): it must wait too. Two processes are now suspended, each hoping to enter.
  3. P1 finishes and executes signal(mutex): the value rises from 0 to 1, and one suspended process — say P3, as chosen by the scheduler — may resume and enter the critical section.
  4. P3 eventually executes signal(mutex), letting P4 in, and so on.

Sense-check: the value of mutex never goes above 1 and never below 0 in this usage, and exactly one process is inside the critical section at every instant — that is mutual exclusion built out of one integer and two operations.

8.6.4 Busy Waiting and Spin Locks

There is a catch: busy waiting. A process inside the critical section makes all the other processes wait. The waiting processes continuously spin on the semaphore value, staying in the same position while trying to enter the critical section. That spinning is called a spin lock, and it wastes processor cycles.

Busy waiting is the classic form of wait: a blocked process keeps re-checking the semaphore in a tight loop, burning CPU time while it waits. A semaphore implemented this way is called a spinlock, because the process "spins".

  • Cost: the wasted cycles could have been used by another process. On a single CPU shared by many processes, spin waiting wastes the time of every other process.
  • The one real advantage: no context switch is needed while waiting, so if the lock is expected to be held very briefly (a few instructions, typical of short kernel critical sections), spinning can be faster than blocking. Multiprocessor systems in particular can let one thread spin on one processor while another finishes on a different one.
  • The fix for general use is the block-and-wakeup design of the next subsection, which replaces the spinning loop with a waiting queue.

8.6.5 Block and Wakeup: Removing Busy Waiting

To remove busy waiting, we replace spinning with two operations, block and wakeup. The semaphore becomes a structure with two fields: the integer value and a pointer to the next record in a list. When the block operation runs, the process waiting to enter the critical section is placed into the waiting queue. The wakeup operation removes one of the processes from the waiting queue and puts it into the ready queue, so it can run again.

The semaphore is now a structure, not a bare integer:

  • an integer value — the availability count;
  • a list (queue) of processes waiting on this semaphore — realized in practice by a link field in each process control block.

When a process must wait, block switches its state to waiting and transfers control to the CPU scheduler, which picks another process — no CPU cycles are burned. When the resource is released, wakeup moves one waiting process from the waiting queue to the ready queue; the scheduler decides when it actually runs. Note that busy waiting is not fully eliminated: wait and signal themselves must still be atomic, and implementing that atomicity may use short spinlocks or interrupt disabling — but the application's critical section no longer spins.

8.6.6 The wait and signal Algorithms

With this structure, wait works as follows: it takes the address of the semaphore variable and decrements its integer value; if the value becomes negative, the process is put into the list and the block operation is invoked. Signal increments the value and then checks it: if the value is less than or equal to zero, it removes a process from the list and performs the wakeup operation, so one of the processes in the queue resumes execution.

\[ \text{wait}(S):\quad S \leftarrow S - 1;\ \text{if } S < 0 \text{ then block} \]

\[ \text{signal}(S):\quad S \leftarrow S + 1;\ \text{if } S \le 0 \text{ then wakeup} \]

In these formulas, \(S\) is the semaphore, an integer that counts the availability of the resource. A negative \(S\) means processes are queued: the magnitude of \(S\) is the number of waiting processes.

Worked example: reading the queue length off the value

Suppose S = 2 — two units of a resource are free.

  1. Process A: wait(S) → \(S = 1\). No block: A takes a unit.
  2. Process B: wait(S) → \(S = 0\). No block: B takes the last free unit.
  3. Process C: wait(S) → \(S = -1\). C blocks and joins the queue.
  4. Process D: wait(S) → \(S = -2\). D blocks and joins the queue.

The value \(-2\) is negative, and its magnitude, 2, is exactly the number of processes (C and D) waiting in the queue. Now A finishes and runs signal(S): \(S = -1\), which is \(\le 0\), so one process — say C — is removed from the list and woken. The queue now holds one process, and the value still says so: \(|S| = 1\).

Sense-check: under this blocking implementation, the semaphore value can go negative — unlike the busy-wait version where it never does — and the negative magnitude always reports the queue length.

A note on notation: some texts write these operations as \(P(S)\) and \(V(S)\) (from the original Dutch naming), or as semWait(S) and semSignal(S). The meaning is identical; this course uses wait(S) and signal(S).

8.6.7 Deadlock with Semaphores

Even with semaphores, deadlock can occur: two or more processes wait indefinitely for an event that can be caused only by one of the waiting processes.

Worked example: the classic two-semaphore deadlock

Two semaphores \(S\) and \(Q\), both initialized to 1, and two processes P0 and P1:

  • P0 performs wait(S) and then wait(Q).
  • P1 performs wait(Q) and then wait(S).

Trace: P0 runs first: wait(S) drops \(S\) from 1 to 0, and P0 continues. P1 runs: wait(Q) drops \(Q\) from 1 to 0, and P1 continues. Now:

  • P0 executes wait(Q): \(Q\) is 0, so P0 blocks. P0 can only be released by a signal(Q) — which only P1 can perform.
  • P1 executes wait(S): \(S\) is 0, so P1 blocks. P1 can only be released by a signal(S) — which only P0 can perform.

Each process is holding one semaphore and waiting for a signal on the other; each waits for the other, and neither can do any useful work. That is deadlock: P0's wait on Q can only be released by a signal(Q) that P1 would perform — but P1 is stuck in wait(S), which only P0 can release with signal(S).

Sense-check: the two processes performed their first waits in different orders (P0: S then Q; P1: Q then S). If both had acquired the two semaphores in the same order — P0 and P1 each doing wait(S) then wait(Q) — this deadlock could not arise. Ordering is the antidote.

The general statement: a set of processes is deadlocked when every process in the set is waiting for an event that can be caused only by another process in the set. With semaphores, the event in question is a signal operation that never comes.

8.6.8 Starvation and Priority Inversion

A process may never be removed from the semaphore queue in which it is suspended. If it has been suspended for a long time, we call it starvation or indefinite blocking. One trigger: if the waiting queue is served in LIFO (last-in, first-out) order, a long-suspended process may be overtaken forever. To prevent starvation or deadlock, we can use priority inversion handling. Priority inversion allows the lower-priority process to hold on and execute whenever it needs to, in the pattern of the higher-priority process: the lower-priority process assumes the higher priority by using the priority inheritance protocol.

Worked example: priority inversion with L, M, and H

Three processes with priorities in the order L < M < H (L low, M medium, H high), sharing resource R.

The inversion: L is in execution and holds R. M becomes runnable — M has medium priority, higher than L, so the scheduler preempts L and runs M. L is stuck holding R while M runs. Now H arrives: H needs R, but R is held by L, so H must wait for L — and L cannot run because M is running. The result: the highest-priority process H is blocked by the medium-priority process M, which never needed R at all. That should not happen — priority inversion: a high-priority process waits longer than a lower-priority one, indirectly.

The fix — priority inheritance: with the priority inheritance protocol, L inherits the priority of H, the highest priority in the picture, and keeps executing. If H arrives during that time, the next dispatch goes to H, not to M, because the tie is between M and H and the higher-priority process wins — H is served as soon as L finishes with R, and only then does M resume.

Sense-check: priority inheritance temporarily raises L's priority to H's level so that the medium-priority process cannot preempt the resource holder. When L releases R, its priority reverts to its original value, and H — not M — runs next.

The professor's honest caveat: priority inheritance is an emergency solution. Whenever a scheduling problem of this type arises, the priority inheritance protocol patches it, but the underlying problem is still there. The inversion scenario can still produce long delays; the protocol only guarantees that the highest-priority waiter eventually gets the resource.

Real-world context: priority inversion is not a textbook curiosity. In 1997 the Mars Pathfinder probe's rover, Sojourner, suffered repeated computer resets on Mars: a high-priority task was forced to wait on a shared resource held by a low-priority task that was itself preempted by medium-priority tasks. The fix was turning on the priority-inheritance option in the VxWorks operating system — remotely, on Mars.

Recap: a semaphore is an integer with two atomic operations — wait decrements and blocks when the value goes negative; signal increments and wakes a queued process when the value is at most zero. The blocking version removes busy waiting, but semaphores can still deadlock (opposite acquisition orders) and starve (LIFO queues), and priority inversion needs the priority inheritance protocol as an emergency patch. Next, the three classical problems show semaphores in real designs, starting with the bounded buffer.

8.7 The Bounded Buffer Problem

8.7.1 Problem Setup: Three Semaphores

The producer-consumer problem gets a precise answer: three semaphores and two short code sequences make it impossible for the consumer to eat an item that was never produced, or for the producer to overflow the buffer.

The first classical problem is the bounded buffer problem. Bounded means the number of buffers is limited: we have \(n\) buffers, and each buffer is capable of holding one item. We use three semaphore variables: mutex, full, and empty.

The three semaphores and their initial values:

  • mutex = 1 — the common one, guarding access to the buffer. It is a binary semaphore that allows only one process to operate on the buffer at a time, so that filling by the producer and consuming by the consumer do not overlap.
  • full = 0 — counts the items in the buffer. If full equals \(n\), the buffer is full of items. Initially 0, because there are no items yet.
  • empty = n — counts the free spaces. If \(n = 5\), five buffer spaces are free to be filled; each space taken by an item moves one unit from empty to full.

The invariant worth remembering: empty + full = n at every instant. Every free space is either empty (counted by empty) or occupied (counted by full).

8.7.2 The Producer Process

The producer is the one that produces an item and puts it into the buffer. It first performs a wait on empty and a wait on mutex. Wait on empty reduces empty from \(n\) to \(n - 1\), meaning an item is about to be put into the buffer. Wait on mutex secures the buffer for this producer alone. Then the producer adds the item to the buffer, performs a signal on mutex, which allows the consumer to access the buffer, and performs a signal on full, which increases the buffer's item count by one. If there were spaces for 5 items and one item was filled, full becomes 1, and four spaces remain.

\[ \text{producer:}\quad \text{wait}(empty);\ \text{wait}(mutex);\ \text{add item};\ \text{signal}(mutex);\ \text{signal}(full) \]

The order inside the critical section matters. wait(empty) comes first — it is the capacity check: if every space is full (empty = 0), the producer must wait here rather than inside the locked region. Only after confirming space does the producer lock the buffer with wait(mutex) to add the item without interference. signal(mutex) releases the buffer; signal(full) tells waiting consumers that a new item exists.

8.7.3 The Consumer Process

The consumer is just the reverse. It performs a wait on full and a wait on mutex, removes an item from the buffer, then signals mutex and signals empty. Wait on full reduces full from 1 to 0, meaning one item is going to be consumed and its occupied space is freed. Wait on mutex locks the buffer so the removal happens without interference. Signal on mutex unlocks it again, and signal on empty raises empty from \(n - 1\) back to \(n\), meaning there are spaces again for the producer to fill; the producer is now waiting for the next item to be consumed.

\[ \text{consumer:}\quad \text{wait}(full);\ \text{wait}(mutex);\ \text{remove item};\ \text{signal}(mutex);\ \text{signal}(empty) \]

The symmetry is deliberate: the producer's wait(empty) pairs with the consumer's signal(empty) (a space is created when an item is removed), and the producer's signal(full) pairs with the consumer's wait(full) (an item is created when one is added). Read another way, the producer produces full buffers for the consumer, and the consumer produces empty buffers for the producer.

8.7.4 A Walkthrough with Five Buffers

Worked example: five buffer spaces, filled by the producer and freed by the consumer

Setup: \(n = 5\). Initially full = 0 and empty = 5; mutex = 1.

Step 1 — the producer makes the first item:

Step Operation empty full Buffer
start — 5 0 all five spaces free
1 wait(empty) 4 0 producer holds a space
2 wait(mutex) 4 0 buffer locked
3 add item 4 0 one space now holds an item
4 signal(mutex) 4 0 buffer unlocked
5 signal(full) 4 1 one item is recorded

The buffer now holds one item and has four free spaces: full + empty = 1 + 4 = 5 = n. If the producer keeps producing until all five spaces are filled, empty reaches 0 and full reaches 5; the next producer's wait(empty) then blocks — the buffer cannot overflow.

Step 2 — the consumer takes the item:

Step Operation empty full Buffer
start — 4 1 one item, four spaces
1 wait(full) 4 0 consumer holds the item count
2 wait(mutex) 4 0 buffer locked
3 remove item 4 0 space freed
4 signal(mutex) 4 0 buffer unlocked
5 signal(empty) 5 0 a space returns

The buffer is empty again, and both semaphores have returned to their starting values.

Step 3 — the consumer tries too early: suppose the consumer runs first, before any item exists: wait(full) finds full = 0 and blocks the consumer. The producer later fills the buffer and signals full, releasing it. The consumer can never consume an item that was never produced, because wait(full) blocks whenever full is 0.

Sense-check: wait(empty) on the producer side blocks at 0 (no overflow), and wait(full) on the consumer side blocks at 0 (no underflow). Inside the buffer, wait(mutex)/signal(mutex) allow exactly one process at a time. All three failure modes — inconsistent updates, overflow, underflow — are prevented by the ordering of the three semaphores.

Pitfalls in the bounded buffer solution:

  • Swapping the two waits — doing wait(mutex) before wait(empty) — lets a producer lock the buffer while blocked on a full buffer; with several producers this can create deadlock-like behavior. The capacity check must come before the lock.
  • Forgetting signal after use — omitting signal(mutex) leaves the buffer locked forever and every other process starves.
  • Breaking the invariant — any design where empty + full \ne n after a cycle means an item was double-counted or lost.

Recap: the bounded buffer solution pairs three semaphores — mutex for exclusive access, full for items, empty for spaces — so the producer blocks on a full buffer and the consumer blocks on an empty one. The same three-semaphore pattern appears again in the reader-writer problem, with a twist: many readers are allowed in at once.

8.8 The Reader-Writer Problem

8.8.1 Problem Setup

Reading the same data is harmless — two people can read a newspaper at the same time. Writing is not: two writers, or a writer and a reader, at the same time is chaos. The reader-writer problem is how to allow the harmless case and forbid the chaotic one.

The second classical problem is the reader-writer problem. There is a common data set shared among many processes. Some processes only read the data set; they perform no update. Others both read and write. The problem appears when multiple readers read at the same time and only a single writer performs a write at the same time. Multiple readers reading together cause no problem, because they do not update any value: suppose \(a = 2\) and \(b = 5\), and many readers read this data — nothing changes, so anyone can read at any time, even simultaneously. The problem comes when a writer updates the data: \(b\) may be increased by 1 or decreased by 1, anything can happen. When a single writer, or many writers, try to access the same data, inconsistency threatens. How each reader or writer is selected depends upon the priority scheme.

  • Reader: a process that only reads the shared data set — it changes nothing, so any number of readers can read at the same time. In the example, if \(a = 2\) and \(b = 5\), ten readers may all read those values simultaneously without harm: the data set never changes while they read.
  • Writer: a process that updates the data set — \(b\) becomes 6 or 4, the record is rewritten. While a writer is mid-update, no other process may touch the data: a reader could otherwise see half an update, and a second writer could clobber the first. Writers need exclusive access.
  • The two rules of the problem: (1) readers may read concurrently with readers; (2) writers exclude everyone — readers and other writers alike.

8.8.2 The Writer Process

We use two semaphores: mutex, which protects the reader count, and a writer semaphore, which the lecture's discussion calls the writer lock and standard texts write as wrt. The writer semaphore is initialized to 1, and mutex is initialized to 1. The writer performs a wait on the writer semaphore, writes, then signals it. The wait reduces the writer semaphore from 1 to 0, which means there are no writers at present and the writing can be performed. The signal increases it back to 1, so another writer may try to write. Any number of writers W2, W3 may come; each must perform the wait and wait until one of the writers already executing in the critical section gives the signal. Only then does the value rise by 1 and one of the waiting writers enter.

\[ \text{writer:}\quad \text{wait}(wrt);\ \text{write data};\ \text{signal}(wrt) \]

This is a plain mutual-exclusion lock, exactly like the mutex of the bounded buffer problem: wrt = 1 means "no writer active". The interesting work happens on the reader side, where the writer lock is shared among all readers.

8.8.3 The Reader Process

For the readers we take one more variable: not a semaphore, just a count of how many readers are present, readcount. The reader first performs wait(mutex), because a writer may arrive at the same time and try to write, and that must not happen. Then readcount is incremented. If readcount is exactly 1 — the first reader — the reader performs wait on the writer semaphore, forcing any writer to wait while readers are in the critical section. Then the reader signals mutex and the reading takes place. When reading is complete, the reader performs wait(mutex) again, decrements readcount, and only when readcount reaches 0 — the last reader left — does it signal the writer semaphore, releasing the writer to enter the critical section. Finally it signals mutex, meaning any process, reader or writer, may now enter.

\[ \text{reader:}\quad \text{wait}(mutex);\ readcount \leftarrow readcount + 1;\ \text{if } readcount = 1 \text{ then wait}(wrt);\ \text{signal}(mutex);\ \text{read data};\ \text{wait}(mutex);\ readcount \leftarrow readcount - 1;\ \text{if } readcount = 0 \text{ then signal}(wrt);\ \text{signal}(mutex) \]

The trick is that only the first reader locks out the writers, and only the last reader lets them back in. Readers in between — readers 2, 3, 4 — never touch the writer semaphore at all: they only adjust readcount under mutex and then read concurrently.

Worked example: the first reader takes the writer lock, the last reader releases it

readcount starts at 0; mutex = 1; wrt = 1.

Reader R1 arrives (becomes the first reader):

  1. wait(mutex) → locks the counter (mutex = 0).
  2. readcount → 1.
  3. readcount == 1, so wait(wrt) → wrt = 0: any writer is now locked out.
  4. signal(mutex) → counter unlocked.
  5. R1 reads the data.

Reader R2 arrives while R1 is reading:

  1. wait(mutex), readcount → 2.
  2. readcount == 2 — not 1 — so no wait(wrt) is performed: the writer lock stays held from R1's visit.
  3. signal(mutex). R2 reads concurrently with R1. Note that R2 would never block on wrt while other readers are inside.

Reader R1 finishes (leaves R2 as the only reader):

  1. wait(mutex), readcount → 1.
  2. readcount == 1 — not 0 — so no signal(wrt) yet.
  3. signal(mutex).

Reader R2 finishes (the last reader):

  1. wait(mutex), readcount → 0.
  2. readcount == 0, so signal(wrt) → wrt = 1: a waiting writer may now enter.
  3. signal(mutex).

Sense-check: at every moment, at most one process holds wrt — either a single writer, or (through the first reader) the whole group of readers. Writers are excluded exactly while readers are present, and the writer lock is re-armed exactly when the last reader leaves.

8.8.4 The Two Variations and Starvation

When solving this problem we consider two variations. First variation: no reader should be kept waiting until a writer has permission to use the object. If multiple readers are present and no writer is running, none of them should wait; all readers enter the critical section and use it. Second variation: if one writer is ready, it should perform the write as soon as possible; in that case, the readers have to wait.

The starvation trade-off — either readers or writers suffer.

  • In the first variation (readers preferred), a stream of readers can keep arriving, and each new reader joins the group before the writer's wrt request can take effect — the writer has to wait, possibly forever: writers starve.
  • In the second variation (writers preferred), once a writer is ready, no new readers may start reading — a stream of writers can lock out the readers: readers starve.
  • The solution above implements the first variation. A fully fair design needs a priority or queueing scheme that alternates the two kinds of access.

Real-world: in some systems the kernel itself solves this problem by providing reader-writer locks — a lock acquired in either read mode (many holders allowed) or write mode (exclusive). Databases and file systems use exactly this pattern: many users may read a table concurrently, but a write locks out everyone else.

Recap: the reader-writer solution lets many readers in together by having the first reader take the writer lock and the last reader release it; the writer side is a plain lock. The cost is built-in: whichever side gets priority, the other side can starve. Next, the dining philosophers problem — where the resource allocation is the whole point, and deadlock is the trap.

8.9 The Dining Philosophers Problem

8.9.1 Problem Setup

Five philosophers, five chopsticks, one bowl of rice — and the rule that eating needs two chopsticks. The dining philosophers problem is a small stage on which the classic failure modes of concurrency — deadlock and starvation — play out, and it is a classic not because of its practical importance but because it represents a whole class of resource-allocation problems.

The third classical problem is the dining philosophers problem, and the name itself hints at the setting. Imagine a round table with five chairs and five philosophers. Their main activities are thinking and eating, and they do not interact with their neighbors. There are five chopsticks on the table. If a philosopher wants to eat, he tries to grab two chopsticks at a time — the one on his left-hand side and the one on his right-hand side — because he needs both chopsticks to eat. After eating, he releases the chopsticks, and the next neighbor can take them. At any time, only one can eat by grabbing the two chopsticks, but if they are not going to eat, they may hold only one chopstick, and only if the other one is free.

The shared data here is the bowl of rice — the data set that is shared — and the chopsticks. We have an array of chopsticks, each initialized to 1.

The pieces of the problem:

  • Five philosophers \(P_0, P_1, P_2, P_3, P_4\) sit around a circular table; each philosopher's neighbors are the two philosophers on either side.
  • Five chopsticks \(chopstick[0], \ldots, chopstick[4]\), one between each pair of neighbors. Each is a semaphore initialized to 1: "on the table and free".
  • A philosopher alternates between thinking (no shared resource, no synchronization needed) and eating (needs both the left chopstick and the right chopstick at the same time).
  • Two philosophers who are neighbors can never eat at the same time — the chopstick between them is shared.

8.9.2 The Philosopher's Structure

Philosopher \(i\) performs a wait on chopstick \(i\) and a wait on chopstick \((i+1) \bmod 5\) — the left-hand and right-hand chopsticks — then eats, then signals both chopsticks back.

\[ \text{philosopher } i:\quad \text{wait}(chopstick[i]);\ \text{wait}(chopstick[(i+1) \bmod 5]);\ \text{eat};\ \text{signal}(chopstick[i]);\ \text{signal}(chopstick[(i+1) \bmod 5]) \]

In this formula, \(\bmod\) is the modulo operation, which wraps the chopstick index around the round table: for philosopher 4, \((4 + 1) \bmod 5 = 0\), so his right chopstick is chopstick 0. The modulo makes the table circular — philosopher 4's "right" wraps back to the first chopstick, which sits between philosopher 4 and philosopher 0.

8.9.3 A Walkthrough with Philosopher 0

Worked example: philosopher 0 grabs chopstick 0 and chopstick 1

Philosopher 0 is hungry. He performs wait(chopstick[0]) — the chopstick between him and philosopher 4 — then wait(chopstick[1]) — the chopstick between him and philosopher 1.

What the neighbors can and cannot do:

  • Philosopher 4 needs chopstick[0] (his right chopstick, since \((4+1) \bmod 5 = 0\)) and chopstick[3]. While philosopher 0 holds chopstick[0], philosopher 4 cannot complete his pair — he cannot eat.
  • Philosopher 1 needs chopstick[1] (his left) and chopstick[2]. While philosopher 0 holds chopstick[1], philosopher 1 cannot complete his pair either.
  • Philosophers 2 and 3 are unaffected: their chopstick pairs, \((2,3)\) and \((3,4)\), are both free — neither is a neighbor of philosopher 0.

The sequence: philosopher 0 takes both chopsticks and eats. Both chopsticks stay in his hands for as long as he eats. When he finishes, he signals both — signal(chopstick[0]) and signal(chopstick[1]) — and whichever neighbor is ready — philosopher 4 or philosopher 1 — can grab the freed chopstick.

Sense-check: holding two chopsticks at once is the only way to eat, and it automatically blocks exactly the two neighbors — no two neighbors can ever be eating simultaneously.

8.9.4 Solutions to Avoid Deadlock

The naive version above has a deadly failure mode. Suppose all five philosophers become hungry at the same time and each grabs the left chopstick: chopstick[0] through chopstick[4] all become 0. Now each philosopher reaches for the right chopstick — and every right chopstick is already held by a neighbor. Each philosopher waits forever for a chopstick only a waiting philosopher can release. All five are deadlocked.

What possible solutions exist? The first is to allow at most four philosophers to sit at the table simultaneously. If all four try to pick the chopsticks, only one can be taken by each, and since each philosopher needs two chopsticks in order to eat, this still leaves a problem — the four may still deadlock on the single-chopstick pattern. The second solution is to allow a philosopher to pick up a chopstick only if both chopsticks are available, so a philosopher never sits holding exactly one chopstick while reaching for the second. The third is an asymmetric solution: make the odd philosophers pick up the first chopstick and then the other one in one order, and the even philosophers in the opposite order — for example, an odd philosopher like P1 takes his left chopstick first and then his right, while an even philosopher takes his right chopstick first.

Scope of the three remedies:

  • At most four at the table: guarantees at least one chopstick pair is free, so deadlock among the five becomes impossible — but it only reduces the risk in a four-philosopher configuration; with all four picking one chopstick each, two could still reach for the same second chopstick and wait.
  • Pick up both or neither (in a critical section): a philosopher never holds one chopstick while waiting for the second, so the "everyone holds one and waits for the other" cycle cannot form. This is the cleanest structural fix and the one the monitor solution of section 8.12 builds on.
  • Asymmetric ordering: odd philosophers pick left-then-right, even philosophers pick right-then-left. Because the order of acquisition differs, two neighbors cannot both grab the same first chopstick — the cycle breaks.
  • All three solutions prevent deadlock to some extent, but some deadlock risk remains. Also, if any one philosopher grabs both chopsticks and starts eating, we do not know how long he will take to finish, so the waiting neighbors wait for an unknown time, and that leads to starvation — a deadlock-free solution does not automatically eliminate starvation.

Recap: five philosophers share five chopsticks, each needing two at once; the naive grab-left-then-right scheme can deadlock when everyone holds one chopstick and waits for the other. The remedies — a seat limit, atomic two-chopstick pickup, or asymmetric ordering — reduce or remove the deadlock, but starvation remains possible. The monitor solution in section 8.12 removes the deadlock cleanly, at the price of leaving starvation.

8.10 Incorrect Use of Semaphores

Semaphores are correct tools used incorrectly. Swap the wait and the signal, forget one of them, or run two waits in a row — and the result is broken mutual exclusion, deadlock, or starvation. This section shows exactly how each misuse breaks down.

There are problems if we do not use the semaphore properly, and the order of the operations causes the trouble.

8.10.1 Signal Before Wait

The first incorrect use is performing signal first and then wait. If we make the signal first, it will allow some other process that is waiting to enter the critical section to do so immediately, and thereby inconsistent data will occur — it leads to chaos. That should not happen. Always perform wait followed by signal.

Worked example: signal before wait lets two processes into the critical section

Shared semaphore mutex, initialized to 1. Correctly written, every process runs wait(mutex) then signal(mutex) around its critical section. Now suppose P1 has the operations swapped: it runs signal(mutex) first and wait(mutex) second.

  1. P1 executes signal(mutex): the value rises from 1 to 2 — an impossible state for a mutex, since it records one more "free" unit than the resource can offer.
  2. P1 executes wait(mutex): the value drops from 2 to 1, and P1 enters the critical section.
  3. P2 — using the correct order — executes wait(mutex): the value drops from 1 to 0, and P2 also enters the critical section. Both processes are now inside, updating the shared data at the same time.

The bogus signal created a spare permission: one "enter" ticket that was never paid for. From then on, the mutual exclusion that the mutex was supposed to guarantee is broken — this is exactly how the counter of section 8.3 becomes inconsistent. The error may be discovered only if several processes are simultaneously active in the critical section, and it may not be reproducible — the worst kind of bug to debug.

Sense-check: wait must always come before the critical section and signal after it; any other order manufactures or destroys permissions.

8.10.2 Wait After Wait, and Missing Operations

The second incorrect use is wait followed by wait. And if every process performs wait alone, or signal alone, omitting one of the two, or omits both operations entirely, then all the processes will enter the critical section and all will try to correct — that is, update — the data, which leads to inconsistency. A worked example: if a process replaces the wait-signal pair around its critical section with two waits in a row, another process may never receive the signal it needs, and processes pile up waiting — that leads to deadlock and starvation. None of these misuses should happen, and this is exactly the motivation for the next construct: the monitor.

Worked example: wait after wait turns a release into a second request

Correct code for process A is wait(mutex); critical section; signal(mutex);. Mistaken code replaces the signal with a second wait: wait(mutex); critical section; wait(mutex);.

  1. A enters its critical section and then executes the second wait(mutex): the value drops from 0 to −1, and A blocks — waiting on the very lock it already holds.
  2. Process B executes wait(mutex): the value drops from −1 to −2, and B blocks too. Every later process joins the queue: processes pile up waiting, because the release that should have come from A never happens.
  3. Nobody can ever signal: A's own signal was replaced by the second wait, and everyone else is blocked waiting for a signal only A could issue. Result: deadlock, and any process behind a long queue faces starvation.

Missing operations: if a process omits wait(mutex) entirely, it walks straight into the critical section beside others — mutual exclusion is violated and the data become inconsistent. If it omits signal(mutex), the lock is never released — every other process starves. If it omits both, the process effectively ignores the protocol completely.

Sense-check: every enter must be matched by exactly one exit. Two waits in a row = a process holds a lock and then asks for it again; one wait with no signal = the lock leaks. Both turn correct semaphore code into deadlock or inconsistent data.

Recap: semaphore misuse — signal before wait, wait after wait, or a missing operation — breaks mutual exclusion or creates deadlock and starvation, and these timing errors can be hard to reproduce. The monitor, next, is the language-level construct built to make these misuses impossible by construction.

8.11 Monitors

8.11.1 What a Monitor Is

Semaphores are powerful but easy to misuse — section 8.10 showed the disasters. The monitor is the language-level answer: the compiler enforces the rule "only one process inside at a time", so the programmer cannot accidentally break it.

A monitor is an abstract data type that provides a high-level abstraction. It has variables and procedures inside it, but remember this rule: only one process can be actively present in the monitor at a time. You can assume it is like a class: the class has variable declarations, some procedures, and some initialization code for the variables. Similarly, a monitor has a monitor name, its declarations, some procedures, and some initialization code. This is the schematic view. We also have a queue of processes that are going to share the particular data. Initially some code will be executed to assign the initial values, then operations are performed. This is common for any process that wants to enter the critical section, but only one can enter at a time and perform the operation.

A monitor is an abstract data type (ADT): it packages private shared variables together with the procedures that operate on them, so processes cannot touch the shared data directly.

  • Monitor name + variable declarations: the shared variables that define the state (like the private fields of a class).
  • Procedures/functions: the only way to access those variables. A procedure inside the monitor can access only the monitor's own variables and its parameters.
  • Initialization code: runs once at the start to set the initial values (like a class constructor).
  • The rule: at most one process is active inside the monitor at a time. Processes wanting to enter line up in the monitor's entry queue; when the active process leaves, one queued process enters. The compiler and runtime enforce this — the programmer does not code the mutual exclusion by hand.

8.11.2 Condition Variables

Inside the monitor we can have some condition variables to perform the wait and signal operations. Take two condition variables, \(x\) and \(y\). There are two operations: wait and signal. A process that invokes \(x.\text{wait}()\) is suspended until an \(x.\text{signal}()\) happens. The \(x.\text{signal}()\) does the same thing a semaphore signal does, but with respect to a condition variable: it resumes one of the processes that has already invoked \(x.\text{wait}()\). If there has been no \(x.\text{wait}()\) on that variable, then the signal operation has no effect. With two condition variables we can have two different groups, one for \(x\) and one for \(y\), each performing wait and signal separately; then a process can access the shared data.

\[ x.\text{wait}(): \text{ suspend the invoking process until some process executes } x.\text{signal}() \]

\[ x.\text{signal}(): \text{ resume one process that previously invoked } x.\text{wait}();\ \text{no effect if none is waiting} \]

Condition variables \(x, y, \ldots\) are not counters — they are queues of waiting processes, attached to conditions ("the buffer is not empty", "the resource is free").

  • \(x.\text{wait}()\): the invoking process gives up the monitor and goes to sleep on condition \(x\).
  • \(x.\text{signal}()\): wakes exactly one process sleeping on \(x\).
  • No memory: unlike a semaphore's signal, a condition-variable signal with no waiting process is lost — it has no effect at all. This is the critical difference from semaphores, and the reason the condition must be re-checked after waking.

8.11.3 Signal and Wait versus Signal and Continue

Suppose process Q has invoked \(x.\text{wait}()\) and is suspended, and process P invokes \(x.\text{signal}()\). We naturally think Q will be resumed next, so P must wait. There are two options.

The first is signal and wait: P performs the signal and then waits — P has signaled and is now waiting — which allows Q to enter the monitor and use the code, and later P may wait for some other condition. The second is signal and continue: P has invoked the signal but continues executing in the monitor, and Q has to wait until P leaves the monitor or until P waits for some other condition. In both cases there are advantages, and the language implementing the monitor has to decide which option to use.

Aspect Signal and wait Signal and continue
Who runs next after P signals The woken process Q (P waits) P keeps running (Q waits)
When does Q get the monitor Immediately after P's signal When P leaves the monitor or waits
Risk P may wait a long time even though it was already inside By the time Q resumes, the condition it waited for may no longer hold — Q should re-check

When to pick which: signal-and-wait gives the woken process an immediate, unspoiled chance (used by Hoare-style monitors); signal-and-continue lets the signaling process finish its work first (Mesa-style). Java uses signal-and-continue-style semantics with notify(), which is why wait() calls in Java normally sit inside loops that re-test the condition.

8.11.4 Languages with Monitor Support

Many languages implement monitors: C#, Java, and many others, and even in Pascal — Concurrent Pascal — there is an implementation. In Concurrent Pascal, when P executes the signal, it must immediately leave the monitor, and the signaled process has to receive control. These things are done with respect to the condition variables. If we have a second condition variable \(y\), the same rules apply.

Pitfalls with condition variables:

  • Lost signal: signaling \(x\) when nobody is waiting on \(x\) does nothing. A process that waits after the signal has already happened will sleep forever — always wait before signal, and re-check the condition in a loop.
  • Forgetting the monitor rule: condition variables only work inside the monitor; calling them without holding the monitor's lock is a programming error.
  • Misreading signal-and-continue: in signal-and-continue languages, the woken process must re-verify its condition when it eventually runs — the condition may have changed while it slept.

Real-world: the monitor idea shows up directly in languages like Java and C#, where the language runtime guarantees that only one thread holds a monitor at a time. In Java, marking a method synchronized makes the object's lock guard the method body; wait() and notify() on the object correspond to the condition-variable operations. C# provides the same pattern through lock statements and Monitor primitives.

Recap: the monitor is a class-like abstract data type in which only one process is active at a time, with condition variables \(x\) providing wait and signal for processes that must sleep until a condition holds. Languages choose between signal-and-wait and signal-and-continue; Java, C#, and Concurrent Pascal all ship some form of monitors. Next, the monitor meets the philosophers: the clean deadlock-free solution to the dining philosophers problem.

8.12 Monitor Solution to the Dining Philosophers Problem

8.12.1 The State Array and Self Condition Variables

The monitor removes the deadlock from the dining philosophers: instead of grabbing chopsticks one at a time, a philosopher may pick up the chopsticks only if both are available — and the monitor's single-process rule makes that check atomic.

With the help of a monitor we can solve the dining philosophers problem. The aim of each philosopher is to pick up the chopsticks, eat, put down the chopsticks, and go back to thinking. When philosophers think there is no problem, so no synchronization is needed; synchronization matters only when they want to eat. They have to perform a pickup operation and a putdown operation with respect to a philosopher index \(i\).

The monitor is an abstract data type with initialization code and shared variables. The shared variables are state and self.

  • state: an enumeration with three values per philosopher — thinking, hungry, or eating. It is initialized to thinking for all five.
  • self: an array of condition variables — since we are talking about five philosophers, we have condition variables for five philosophers, self[0] through self[4]. A hungry philosopher who cannot get both chopsticks waits on her own self[i].
  • The two procedures, pickup(i) and putdown(i), have to be performed one after another; that is the main game. Only one philosopher process is active inside the monitor at a time, so the chopstick checks and state changes cannot interleave.

8.12.2 The pickup and putdown Procedures

When philosopher 0 wants to eat, he calls pickup(0). First his state is set to hungry. Being hungry alone is not enough — he needs the chopsticks — so we invoke a test function, test(i). The test checks whether both neighbors are not eating and whether this philosopher is hungry. The neighbors of philosopher \(i\) are \((i+4) \bmod 5\) and \((i+1) \bmod 5\). For philosopher 0 that is philosopher 4 and philosopher 1. If both neighbors are not eating and philosopher 0 is hungry, his state is set to eating, and then a signal is performed — self[i].signal() — because he was put in a waiting state initially. If the condition fails, the philosopher performs self[i].wait() and stays in the waiting state; not only one philosopher but several may be hungry and waiting, because only one process can be active inside the monitor at a time.

\[ \text{test}(i):\quad \text{if } \text{state}[(i+4) \bmod 5] \neq \text{eating} \wedge \text{state}[(i+1) \bmod 5] \neq \text{eating} \wedge \text{state}[i] = \text{hungry} \text{ then } \text{state}[i] \leftarrow \text{eating};\ \text{self}[i].\text{signal}() \]

In this formula, \(\wedge\) means "and": all three conditions must hold together — the left neighbor is not eating, the right neighbor is not eating, and philosopher \(i\) is hungry. The modulo arithmetic maps the circular table: \((i+4) \bmod 5\) is the left neighbor and \((i+1) \bmod 5\) the right neighbor, wrapping around at the ends.

When philosopher 0 has finished eating, he performs putdown(0). This sets his state to thinking, and then the same test operation is applied to his left-hand and right-hand neighbors, philosopher 4 and philosopher 1. For philosopher 4, the test checks \((4+4) \bmod 5 = 3\) and \((4+1) \bmod 5 = 0\): whether philosophers 3 and 0 are not eating and philosopher 4 is hungry. For philosopher 1, the test checks philosophers 0 and 2. If those conditions are satisfied, then either philosopher 4 or philosopher 1 comes to eat, and afterwards performs its own signal operation. This is how the dining philosophers problem is solved with monitors.

8.12.3 Walkthrough with Philosopher 0

Worked example: pickup and putdown with modulo neighbors for philosopher 0

Pickup: philosopher 0 calls pickup(0).

  1. state[0] ← hungry.
  2. test(0) runs: check left neighbor \((0+4) \bmod 5 = 4\), right neighbor \((0+1) \bmod 5 = 1\), and the philosopher himself.
  3. Suppose philosophers 4 and 1 are both not eating. The test's three conditions all hold: state[4] ≠ eating, state[1] ≠ eating, state[0] = hungry. So state[0] ← eating and self[0].signal() runs — with nobody actually waiting on self[0] yet, the signal has no effect (it exists to cover the waiting case in putdown). Philosopher 0 eats.

The failed case: suppose instead that philosopher 4 is eating. The test fails, so philosopher 0 executes self[0].wait() and stays suspended in the monitor. He waits until philosopher 4 puts down the chopsticks.

Putdown: philosopher 4 finishes eating and calls putdown(4).

  1. state[4] ← thinking.
  2. test(3): left neighbor \((3+4) \bmod 5 = 2\), right neighbor \((3+1) \bmod 5 = 4\), and philosopher 3. If 2 and 4 are not eating and 3 is hungry, state[3] ← eating and self[3].signal().
  3. test(0): left neighbor \((0+4) \bmod 5 = 4\), right neighbor \((0+1) \bmod 5 = 1\), and philosopher 0. Philosopher 0 is now hungry, and philosopher 4 (the only eater) has returned to thinking — the conditions hold. state[0] ← eating and self[0].signal() wakes philosopher 0, who resumes his pickup call and eats.

The putdown operation checks both neighbors with the modulo wrap: after philosopher 4's putdown, the test runs on philosophers 3 and 0, and the one whose conditions are satisfied (here, philosopher 0) is resumed by its own self signal.

Sense-check: at any time at least one process can always eat (someone is hungry with two non-eating neighbors), so no deadlock; and a philosopher is resumed only when both chopsticks are truly available — the "pick up both or neither" rule of section 8.9, made atomic by the monitor.

What the monitor solution fixes and what it does not:

  • No deadlock here, because at any time someone is eating and the others wait: the monitor's test guarantees a philosopher enters eating only when both chopsticks are free, so the "everyone holds one chopstick" cycle cannot form.
  • The remaining problem is starvation: a philosopher may eat for a long time, and that makes the others wait for a long time — the starvation problem persists even with the monitor solution. A deadlock-free solution does not automatically eliminate starvation.

Recap: the monitor version replaces per-chopstick grabs with a state machine — thinking, hungry, eating — and a test that admits a philosopher only when both neighbors are not eating; waiting philosophers sleep on their own condition variable self[i]. Deadlock disappears, starvation does not. Next: how the monitor itself is built out of semaphores.

8.13 Implementing Monitors with Semaphores

8.13.1 The mutex, next, and next_count Variables

A monitor is a language construct — but under the hood it can be built from the semaphores of section 8.6. Three shared variables are enough: a mutex to control entry, and a "next" semaphore plus a counter for processes that gave up the monitor temporarily.

A monitor itself can be implemented with the help of semaphores; the implementation uses three shared variables. We take a common variable mutex, and next to it we keep a semaphore next and a counter next_count.

  • mutex (a semaphore initialized to 1): the entrance gate. Every procedure call begins with wait(mutex) and ends with the exit routine below, so only one process is inside the monitor at a time — mutual exclusion, enforced by the semaphore.
  • next (a semaphore initialized to 0): a waiting room for processes that have been inside the monitor and must temporarily give it up — in particular, a process that just signaled a condition variable and must wait for the woken process to run.
  • next_count (an integer, initialized to 0): how many processes are currently suspended on next.
  • For every condition variable \(x\): a semaphore \(x\_sem\) (initialized to 0) and a counter \(x\_count\) (initialized to 0) counting how many processes are waiting on \(x\).

First, the wait operation on mutex is performed, so that a process trying to enter the critical section has to wait. When the process is inside, if next_count is greater than zero — which means some other process is waiting — we signal next, and the next person can enter the monitor. Otherwise we signal mutex, and any one of the processes may resume its operation. This maintains mutual exclusion.

\[ \text{exit monitor:}\quad \text{if } next\_count > 0 \text{ then } \text{signal}(next) \text{ else } \text{signal}(mutex) \]

The condition variables are implemented with their own counts. A process that wants to wait on condition variable \(x\) increments the count of processes waiting on \(x\), and if next_count is greater than zero it signals next, else it signals mutex; then it performs \(x.\text{wait}()\). When it resumes, it decrements the count. The signal operation on \(x\) checks whether the count of processes waiting on \(x\) is greater than zero; if so, next_count is incremented, \(x.\text{signal}()\) is executed to wake one waiting process, and the signaling process waits on next; after being resumed it decrements next_count.

\[ x.\text{signal}():\quad \text{if } x\_count > 0 \text{ then } next\_count \leftarrow next\_count + 1;\ x.\text{signal}();\ \text{wait}(next);\ next\_count \leftarrow next\_count - 1 \]

Worked example: a monitor round-trip with mutex, next, and next_count

State: mutex = 1, next = 0, next_count = 0, and for condition \(x\): x_sem = 0, x_count = 0.

Enter: process P calls a monitor procedure — wait(mutex) takes mutex from 1 to 0. P is inside; no one else can follow.

Condition wait: P needs a condition that does not hold and executes the wait implementation for \(x\): x_count goes from 0 to 1; next_count is 0, so signal(mutex) — the monitor is released for someone else; then wait(x_sem) suspends P. Since mutex was signaled, process Q may now enter the monitor.

Signal: Q, inside the monitor, finds the condition satisfied and executes the \(x\) signal implementation: x_count is 1, so next_count goes from 0 to 1, signal(x_sem) wakes P, and Q executes wait(next) — Q suspends on next. P resumes inside the monitor and finishes its work. On exit, P's procedure runs the exit routine: next_count is 1, so signal(next) wakes Q; Q resumes, decrements next_count back to 0, and finishes its own work. Q's exit routine then finds next_count = 0 and runs signal(mutex), releasing the monitor for the next process.

Sense-check: every release is routed to the right place — a waiting signaler gets next first, everyone else gets mutex; the counters keep the routing decision exact, and mutual exclusion is preserved at every step.

8.13.2 Conditional Wait with Priorities

When we have to resume processes, or put a process into the monitor for execution, and several processes are queued on the same condition variable \(x\), which process is resumed when \(x.\text{signal}()\) executes? Sometimes we may go for FCFS, meaning the process that has waited the longest is taken for execution. But that alone is not enough, so we go for conditional wait. Conditional wait uses an integer value that acts as a priority. The lower the value, the higher the priority, and that process is resumed next for execution. This is one solution when multiple processes are queued on the condition variable \(x\).

Worked example: conditional wait by priority value

Three processes wait on condition variable \(x\): P1 with priority value 5, P2 with priority value 2, P3 with priority value 4.

  • Under FCFS, the resume order is arrival order — say P1, then P2, then P3 — regardless of their priority values.
  • Under conditional wait, the value is stored with each suspended process, and when \(x.\text{signal}()\) runs, the process with the smallest priority value is resumed next: P2 (value 2) first, then P3 (value 4), then P1 (value 5).

The priority value is chosen by the process at the moment it executes wait — for example, the time it estimates it still needs the resource. The lower the value, the higher the priority, and that process is resumed next for execution.

Sense-check: conditional wait turns the resume order into a scheduling decision under the programmer's control — the integer stored with the suspended process decides who gets the monitor next.

Recap: the monitor's mutual exclusion is implemented by wait(mutex) on entry and the next_count > 0 ? signal(next) : signal(mutex) routine on exit; condition variables become x_sem/x_count pairs with the signaling process parking itself on next. When several processes wait on one condition, FCFS or a priority value (smallest first) decides the order. Next, the resource allocator puts this machinery to work — and shows the four ways monitor users can still go wrong.

8.14 The Resource Allocator and Problems with Monitors

8.14.1 The Resource Allocator Monitor

Give a single resource to whichever process needs it for the shortest time, let the others wait their turn — and make the whole allocation a monitor. That is the resource allocator, the practical payoff of the conditional wait from section 8.13.

Consider a monitor that acts as a resource allocator. Its main operations are acquire, access, and release. When a process wants to acquire the resource, we check whether the resource is busy; the time at which it enters to access the resource is important — the process that takes the shortest time to access the resource and finish is given priority. If the resource is busy, the process has to wait. Otherwise the busy flag is made true, and after acquiring the resource the process accesses it; on release, the busy flag is made false and \(x.\text{signal}()\) takes place, so that any other process that wishes to enter the monitor can do so.

The ResourceAllocator monitor controls one resource among competing processes.

  • Shared variable: a Boolean busy, initialized to false — "the resource is currently held".
  • Operation acquire: if busy is false, set busy = true and grant the resource. If busy is true, the process must wait — it cannot enter the critical section until the current holder releases the resource.
  • Operation access: use the resource.
  • Operation release: set busy = false and perform \(x.\text{signal}()\), so that any other process waiting on condition \(x\) may enter the monitor and acquire the resource.
  • The scheduling rule: each request carries a value — the time the process plans to use the resource — and the process that takes the shortest time to use the particular resource gets the highest priority (conditional wait with that time as the priority value).

Initially busy is false, so any process may acquire the resource or be allocated the resource.

Worked example: the busy flag in action

Three processes P1, P2, P3 request the single resource from the ResourceAllocator monitor. Their planned usage times: P1 — 10 ms, P2 — 3 ms, P3 — 7 ms.

  1. P1 calls acquire: busy is false, so busy = true and P1 is granted the resource.
  2. P2 calls acquire: busy is true, so P2 waits on condition \(x\). P3 calls acquire: busy is still true, so P3 waits on \(x\) too. Two processes are queued on the condition variable.
  3. P1 calls release: busy = false, then \(x.\text{signal}()\). The conditional wait picks the request with the smallest priority value — P2's 3 ms, the shortest planned use — so P2 resumes and is allocated the resource (the check at the top of acquire now finds busy = false and sets it true).
  4. When P2 finishes and releases, P3 (7 ms) is served next, then any later arrivals.

Sense-check: the busy flag answers "is the resource free?" and the conditional wait answers "who gets it first?"; the shortest planned use always wins the tie-break, exactly as the professor's rule states — remember always: the process that takes the shortest time to use the particular resource gets the highest priority.

8.14.2 Problems with Monitors

There are four problems to keep in mind with respect to monitors.

Worked example: one printer, one process, and two eternal waiters

Suppose there is exactly one printer in the system — a single shared resource. P1 acquires it and starts printing. While P1 uses the printer for a long time (a large print job), P2 and P3 arrive and request the printer. Both are placed in the waiting queue and cannot acquire the printer and use it. The single shared resource is blocked by one process — P1 — which never releases it.

If P1 never calls release (a bug, or a crash mid-job), P2 and P3 wait indefinitely: the resource allocator's busy flag stays true forever, and the condition variable never receives a signal that would let anyone in. That is the second monitor problem — a process may never release a resource — in its starkest form.

The four monitor problems to keep in mind:

  1. Access without permission: a process might access a resource without first gaining permission to enter it. If resource \(R\) is there and a process acquires it without permission, that is not correct, because without permission any number of processes may acquire the resource, and that leads to inconsistent data.
  2. Never releasing a resource: a process may be granted the resource and keep it for a long time, making other processes wait — the printer held by P1 keeps P2 and P3 waiting.
  3. Releasing an unrequested resource: a process might attempt to release a resource that it never requested — a phantom release that unbalances the allocator's bookkeeping.
  4. Requesting more than once without releasing: a process might request a resource more than once without releasing it — P1 is already using the printer and, at the same time, makes another request to acquire the printer again, while P2 and P3 are waiting.

The root cause: the monitor guarantees mutual exclusion inside its procedures, but it cannot force the sequence of calls (acquire → access → release) on the processes that use it. An uncooperative or buggy process can still break the protocol.

8.14.3 Combining Semaphores and Monitors

If we use a semaphore alone, it is also a problem: a semaphore alone cannot solve the problem fully. We can use the monitor along with the semaphore to achieve synchronization, and that combination works.

Key Industry Applications

Real-world: the bounded buffer problem is the classic producer-consumer pattern, the same design behind shared buffers and message queues in real systems where one set of threads produces data and another consumes it. Web servers, audio pipelines, and print spoolers all use this shape: a bounded queue decouples the producing side from the consuming side, and the empty/full counting lets the two sides run at different speeds without ever losing or duplicating items.

Real-world: the reader-writer problem maps directly to databases, file systems, and other shared data stores, where many readers may read concurrently but writes must be exclusive. Some operating system kernels solve the problem for applications by providing reader-writer locks — Solaris, for example, uses reader-writer locks to protect data that is read frequently but updated rarely, and database engines apply the same idea to allow concurrent reads of a table while a write gets exclusive access.

Real-world: the monitor is not only a textbook construct; it is implemented directly in programming languages. Java and C# provide monitor-like synchronization (synchronized methods and locks), and Concurrent Pascal was one of the earliest languages with native monitor support. When you write synchronized in Java or lock in C#, you are using the monitor rule — only one thread inside at a time — with condition variables available through wait/notify or the Monitor primitives.

Real-world: the priority inheritance protocol is an emergency scheduling mechanism used to resolve priority inversion, where a low-priority process holding a resource blocks a higher-priority process. The Mars Pathfinder rover's resets in 1997 were a famous case: enabling priority inheritance in the VxWorks operating system fixed a high-priority task starved by medium-priority preemption of a low-priority resource holder.

Real-world: the CPU-OS simulator is the tool used for the course assignment, where thread synchronization problems are implemented and observed on simulated CPUs. It lets you run the producer-consumer pattern, reader-writer locks, and other synchronization solutions, and watch the interleavings — and the races — on a model machine before you ever debug them on real hardware.

Concurrent Execution and Process Interaction

Must-know: Concurrency = processes making progress in the same time span; interleaved on a uniprocessor (with context-switch delay), overlapped on a multiprocessor (no delay). Processes interact by competition, sharing, or direct communication, ending in deadlock, mutual exclusion, or starvation.

⚠️ Top pitfall: Thinking concurrency means parallelism, or that FCFS scheduling makes a process run to completion.

Self-check: Why does every context switch reduce system efficiency, and how could the overhead be lowered?

Deadlock and Starvation

Must-know: Starvation = one process waits indefinitely (process-level); deadlock = the whole set of processes waits, each for an event only another waiting process can cause. Concurrent execution of cooperating processes is the root cause; synchronization is the remedy.

⚠️ Top pitfall: Calling any long wait a deadlock; deadlock requires the whole set to be stuck, with each process waiting on another member of the set.

Self-check: P3 holds R forever, P1 and P2 wait. Is that starvation or deadlock, and why?

Connects to: 8.1 Concurrent Execution and Process Interaction; 8.3 The Critical Section and the Race Condition; 8.6.7 Deadlock with Semaphores

The Critical Section and the Race Condition

Must-know: Critical section = the code segment that uses the shared resource; the access must be atomic - either it completes fully or it does not happen at all. Interleaved read-modify-write of a shared counter is a race condition (consumer sees 5, producer sees 86).

⚠️ Top pitfall: Thinking counter++ is one atomic step; on real hardware it is load, add, store - three steps that can interleave.

Self-check: With counter = 5, both processes read 5, then store their results. Which two final values are possible, and why?

Connects to: 8.2 Deadlock and Starvation; 8.4 Requirements of the Critical Section Problem

Requirements of the Critical Section Problem

Must-know: Three requirements: mutual exclusion - no other process may execute in the critical section while one process is inside; progress - selection of the next entrant cannot be postponed indefinitely; bounded waiting - only a bounded number of other entries after a request. Assumption: each process runs at nonzero speed.

⚠️ Top pitfall: Confusing progress (someone gets in) with bounded waiting (this particular process gets in within a bound); or forgetting the nonzero-speed assumption when analyzing correctness.

Self-check: A protocol lets P1 and P2 alternate forever while P0's request waits. Which requirement does it violate?

Connects to: 8.3 The Critical Section and the Race Condition; 8.5 Peterson's Solution and Hardware-Based Synchronization

Peterson's Solution and Hardware-Based Synchronization

Must-know: Peterson's solution: two processes share flag[] and turn; set flag[i]=true, turn=j, wait while flag[j] and turn==j. Satisfies all three requirements but only for two processes and not guaranteed on modern hardware. Hardware support: TestAndSet and Swap atomic instructions with acquire-lock/enter/release pattern.

⚠️ Top pitfall: Applying Peterson's solution to more than two processes, or assuming a plain test-and-set lock has bounded waiting - it can starve a process.

Self-check: In Peterson's solution, what does the last write to turn decide, and why can both processes never be inside simultaneously?

Connects to: 8.4 Requirements of the Critical Section Problem; 8.6 Semaphores

Semaphores

Must-know: wait(S): S = S - 1, block if S < 0; signal(S): S = S + 1, wakeup if S <= 0. Binary semaphore = mutex lock (values 0/1); counting semaphore = any integer. Blocking form removes busy waiting; negative S means |S| processes are queued. Deadlock arises when two processes wait on two semaphores in opposite orders; priority inheritance patches priority inversion.

\[\text{wait}(S):\quad S \leftarrow S - 1;\ \text{if } S < 0 \text{ then block}\qquad \text{signal}(S):\quad S \leftarrow S + 1;\ \text{if } S \le 0 \text{ then wakeup}\]

⚠️ Top pitfall: Waiting on multiple semaphores in different orders across processes (causes deadlock); or forgetting that the blocking-form value can go negative, with |S| equal to the queue length.

Self-check: S = 2, three processes wait on S one after another. What is S after each wait, and how many processes are queued?

Connects to: 8.2 Deadlock and Starvation; 8.4 Requirements of the Critical Section Problem; 8.7 The Bounded Buffer Problem; 8.10 Incorrect Use of Semaphores

The Bounded Buffer Problem

Must-know: Producer: wait(empty), wait(mutex), add item, signal(mutex), signal(full). Consumer: wait(full), wait(mutex), remove item, signal(mutex), signal(empty). Initial values mutex = 1, full = 0, empty = n; invariant empty + full = n.

\[\text{producer:}\quad \text{wait}(empty);\ \text{wait}(mutex);\ \text{add item};\ \text{signal}(mutex);\ \text{signal}(full)\]

⚠️ Top pitfall: Performing wait(mutex) before wait(empty)/wait(full): a process can hold the buffer lock while blocked, and the system can deadlock.

Self-check: With n = 5, the producer adds two items and the consumer removes one. What are empty and full, and does the invariant hold?

Connects to: 8.6 Semaphores; 8.8 The Reader-Writer Problem

The Reader-Writer Problem

Must-know: Writer: wait(wrt), write, signal(wrt). Reader: wait(mutex), readcount++, if readcount == 1 wait(wrt), signal(mutex), read, wait(mutex), readcount--, if readcount == 0 signal(wrt), signal(mutex). Only the first reader locks out writers; only the last releases them. First variation starves writers, second starves readers.

\[\text{writer:}\quad \text{wait}(wrt);\ \text{write data};\ \text{signal}(wrt)\]

⚠️ Top pitfall: Forgetting that only the first and last readers touch the writer semaphore - having every reader wait on wrt would serialize all readers and destroy concurrency.

Self-check: R1 and R2 are reading; R3 arrives. Does R3 wait on wrt? What happens when the last reader leaves?

Connects to: 8.6 Semaphores; 8.7 The Bounded Buffer Problem

The Dining Philosophers Problem

Must-know: Philosopher i: wait(chopstick[i]); wait(chopstick[(i+1) mod 5]); eat; signal(chopstick[i]); signal(chopstick[(i+1) mod 5]). All five grabbing the left chopstick first = deadlock. Remedies: at most 4 at the table, pick both chopsticks together, or asymmetric order (odd left-first, even right-first).

\[\text{philosopher } i:\quad \text{wait}(chopstick[i]);\ \text{wait}(chopstick[(i+1) \bmod 5]);\ \text{eat};\ \text{signal}(chopstick[i]);\ \text{signal}(chopstick[(i+1) \bmod 5])\]

⚠️ Top pitfall: Assuming the naive solution is safe: if all five philosophers grab their left chopstick simultaneously, everyone waits on the right chopstick forever - deadlock.

Self-check: Why does the asymmetric scheme (odd left-first, even right-first) break the deadlock cycle?

Connects to: 8.6 Semaphores; 8.12 Monitor Solution to the Dining Philosophers Problem

Incorrect Use of Semaphores

Must-know: Always perform wait followed by signal. Signal before wait lets other processes enter immediately and produces inconsistent data (chaos); wait after wait (or a missing signal) blocks everyone - deadlock and starvation. This motivates the monitor.

⚠️ Top pitfall: Thinking the compiler or runtime catches ordering mistakes - semaphore timing errors are rare and unreproducible, which makes them the hardest bugs to find.

Self-check: What is wrong with running signal(mutex) before wait(mutex), and what state does the mutex reach?

Connects to: 8.6 Semaphores; 8.11 Monitors

Monitors

Must-know: Monitor = abstract data type with only one process active at a time. Condition variable x: x.wait() suspends the invoking process until an x.signal(); x.signal() resumes one waiter and has no effect if none is waiting (unlike a semaphore, the signal is not remembered).

\[x.\text{wait}(): \text{ suspend the invoking process until some process executes } x.\text{signal}()\]

⚠️ Top pitfall: Assuming a condition-variable signal is remembered: if nobody is waiting on x, x.signal() has no effect and a later waiter sleeps forever - wait first, signal later, re-check in a loop.

Self-check: Why is x.signal() with no waiting process different from a semaphore signal, and what bug can it cause?

Connects to: 8.10 Incorrect Use of Semaphores; 8.12 Monitor Solution to the Dining Philosophers Problem

Monitor Solution to the Dining Philosophers Problem

Must-know: test(i): if state[(i+4) mod 5] != eating AND state[(i+1) mod 5] != eating AND state[i] == hungry then state[i] = eating and self[i].signal(). pickup sets hungry then tests; putdown sets thinking then tests both neighbors. Deadlock-free, but starvation remains possible.

\[\text{test}(i):\quad \text{if } \text{state}[(i+4) \bmod 5] \neq \text{eating} \wedge \text{state}[(i+1) \bmod 5] \neq \text{eating} \wedge \text{state}[i] = \text{hungry} \text{ then } \text{state}[i] \leftarrow \text{eating};\ \text{self}[i].\text{signal}()\]

⚠️ Top pitfall: Forgetting the modulo wrap: for philosopher 0 the right neighbor is (0+1) mod 5 = 1 and the left is (0+4) mod 5 = 4; the test must check both neighbors, not just one.

Self-check: Philosopher 4 puts down his chopsticks. Which two philosophers' test() calls are triggered, and what indices do they check?

Implementing Monitors with Semaphores

Must-know: Exit monitor: if next_count > 0 then signal(next) else signal(mutex). x.signal(): if x_count > 0 then next_count++, x.signal(), wait(next), next_count--. Conditional wait: the lower the priority value, the higher the priority; smallest value resumes next.

\[\text{exit monitor:}\quad \text{if } next\_count > 0 \text{ then } \text{signal}(next) \text{ else } \text{signal}(mutex)\]

⚠️ Top pitfall: Forgetting that the signaling process itself must wait on next (next_count++) while the woken process runs - otherwise two processes would be active in the monitor.
