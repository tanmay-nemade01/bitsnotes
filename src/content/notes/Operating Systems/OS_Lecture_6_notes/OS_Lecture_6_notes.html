6.1 The Criteria for CPU Scheduling

Every scheduling algorithm in this chapter will be judged by the same question: does it keep the CPU busy and finish processes quickly? Before looking at any algorithm, we need the yardstick — the set of numbers that tell us whether a scheduler is doing its job well.

Before any algorithm, we need the yardstick every scheduler is measured against. The main criterion is keeping CPU utilization high — the CPU should be as busy as possible, always executing something. If the CPU sits idle, utilization is poor. Utilization is achieved with the help of throughput: how many processes complete their execution per unit of time. We maximize throughput, and we minimize three time quantities: turnaround time, waiting time, and response time.

Why must all these times be watched? Because the total time a process spends in the system is not just its execution time. The process waits in the queue, enters the CPU for execution, and as soon as it enters the CPU it usually cannot finish immediately — it may go for I/O (often rendered "IBO" in the course materials), and while it is away, some other process comes for execution. All of that is part of the process's life cycle and must be counted. Turnaround time is the full journey: the time from arrival until the process completes and comes out. Waiting time is the time spent waiting in the ready queue. Response time is how soon the process first gets into the CPU after it arrives — measured from the rate of arrival and the rate at which it gets into the CPU.

6.1.1 The Aims of the Scheduler

The scheduler must serve all four quantities at once: keep the CPU busy (utilization), finish as many processes per unit time as possible (throughput), and keep the three times as small as possible. Each scheduling algorithm gets judged against these aims.

The aims, in one sentence: maximize CPU utilization and throughput; minimize turnaround time, waiting time, and response time. In most cases we optimize the average of a metric; for interactive systems we may instead want to minimize the maximum response time so that no single user gets badly treated. Two more practical facts:

  • Real systems run with utilization between about 40% (lightly loaded) and 90% (heavily loaded) — 100% is a theoretical ceiling.
  • The scheduling algorithm itself affects only the ready-queue waiting time. It cannot speed up the CPU execution of a process, and it cannot speed up I/O — so "waiting time" is the one metric the scheduler fully controls.

The process life cycle explains why the scheduler has four separate targets. A process does not walk in, run once, and leave. It arrives, sits in the ready queue, gets the CPU for a while, blocks for I/O, comes back, waits again, and only then completes. Every stop in that cycle adds time that the scheduler's choice of algorithm can influence — except the execution itself. That is why the course renders the I/O break as "IBO": the process leaves the CPU for input/output and later returns, and every return means somebody else has a turn.

6.1.2 The Metrics as Rules

The four metrics, written out as rules:

  • Turnaround time (TAT): completion time minus arrival time. If \(C\) is the completion time and \(A\) is the arrival time,

\[\text{TAT} = C - A\]

  • Waiting time (WT): turnaround time minus burst time. With burst time \(B\),

\[\text{WT} = \text{TAT} - B\]

  • Response time (RT): the first time the process enters the CPU, \(t_{\text{first}}\), minus arrival time,

\[\text{RT} = t_{\text{first}} - A\]

  • Throughput: the number of processes completed per unit of time,

\[\text{Throughput} = \frac{N_{\text{completed}}}{\text{total time taken to finish them all}}\]

These are the main aims of every scheduling algorithm, and the running question for each algorithm we study is whether it serves those aims: maximize throughput, minimize turnaround, waiting, and response.

Every symbol above carries a meaning that will be reused in every worked problem in this chapter, so fix them now:

  • \(C\) (completion time) — the instant the process finishes its last unit of work and leaves the system.
  • \(A\) (arrival time) — the instant the process enters the ready queue. Many exam problems use arrival time 0 for all processes, which shortens \(\text{TAT}\) to just \(C\), but never drop the \(A\) unless it is truly 0.
  • \(B\) (burst time) — the total CPU time the process needs, sometimes called its burst length.
  • \(t_{\text{first}}\) — the first moment the process actually gets the CPU; for a process that starts immediately, \(t_{\text{first}} = A\) and response time is 0.
  • \(N_{\text{completed}}\) — how many processes finished in the measured window.

A single-process example, fully worked. Suppose process P arrives at time \(A = 2\) and needs one CPU burst of \(B = 6\) time units. The CPU is busy with other processes until time 6, so P first enters the CPU at \(t_{\text{first}} = 6\), runs without interruption, and completes at \(C = 12\).

  1. Turnaround time: \(\text{TAT} = C - A = 12 - 2 = 10\) time units. The process spent 10 units inside the system in total.
  2. Waiting time: \(\text{WT} = \text{TAT} - B = 10 - 6 = 4\) time units. Check: P sat in the ready queue from time 2 to time 6 — that is exactly 4 units of waiting.
  3. Response time: \(\text{RT} = t_{\text{first}} - A = 6 - 2 = 4\) time units. P first touched the CPU 4 units after arriving.
  4. Throughput: if, alongside P, four other processes complete in the same 25-unit window, then throughput is \(5/25 = 0.2\) processes per unit time. The textbook frame: for long batch processes, throughput may be one process per hour; for short transactions, it can be ten processes per second.

Sense-check: waiting (4) and response (4) agree here because P executed in a single burst — it entered the CPU once and stayed. The moment a process is preempted or blocked mid-burst, waiting time grows (it accumulates every ready-queue stay) while response time freezes (only the first entry counts). This difference becomes important in the round robin section.

Visual intuition: draw a horizontal axis with time running left to right. Mark P's arrival tick at 2, its first CPU entry at 6, and its completion edge at 12. The span from 2 to 12 is turnaround time — the whole journey. The shaded gap between 2 and 6 is the ready-queue wait, which contributes to waiting time. The gap between 6 and 12 is real CPU execution. Now repeat the picture for a process that gets preempted: the waiting part becomes two shaded gaps instead of one, and the turnaround span stretches, while the response gap (arrival to first entry) stays exactly as short as before. That single picture explains why interactive systems care about response time more than about turnaround.

Scope — when these formulas apply: the worked tables in this course treat each process as a single CPU burst (one execution to completion), which is exactly how the textbook runs its examples. With multiple bursts, \(\text{WT} = \text{TAT} - B\) counts every ready-queue stay, so use the formula on the totals and do not try to read a per-burst story from it. The formulas also assume time is continuous and measured in the same unit throughout — mixing milliseconds and seconds in one table is a fast route to wrong averages.

With the scope of the formulas fixed, the traps that students actually hit in these tables come next.

Common beginner traps:

  1. Waiting time vs. response time. They are equal only when a process finishes inside its first CPU entry. Otherwise response time is a first-touch measure and waiting time is a total accumulation measure — one short, one long, both correct.
  2. Dropping the arrival time. \(\text{TAT} = C - A\), not \(C\). If arrivals are staggered (as in the worked examples of this lecture), using \(C\) alone inflates every turnaround number.
  3. Counting I/O time as waiting time. While a process does I/O, it is not in the ready queue. The scheduling algorithm cannot make I/O faster, so I/O time is part of the life cycle but not part of what the scheduler controls.
  4. Thinking throughput measures one process. Throughput is a batch rate — processes completed per unit of time. Many short processes can push throughput high while a single long process drags turnaround up; the two metrics can genuinely disagree about which scheduler is better.

Exam note: these definitions are the foundation of every scheduling problem — expect to apply completion time, turnaround time, waiting time, and response time in a worked table. Memorize the four rules exactly: \(\text{TAT} = C - A\), \(\text{WT} = \text{TAT} - B\), \(\text{RT} = t_{\text{first}} - A\), throughput = completed per unit time.

These metrics are not classroom decorations. Every operating system ships with performance monitors built on them: top and similar tools report utilization and load, interactive systems advertise response time, and batch schedulers are tuned for throughput. When we judge FCFS, SJF, priority, and round robin in the rest of this lecture, we are running exactly this yardstick on each candidate — the algorithm that maximizes throughput while minimizing the three times wins the comparison.

6.2 Review: FCFS and SJF

What happens when the scheduler just serves whoever arrived first? The shortest processes end up waiting behind the longest one — and the average waiting time climbs. That weakness has a name, and it appears in every FCFS system: the convoy effect.

6.2.1 First-Come-First-Serve and the Convoy Effect

First-come-first-serve (FCFS) is the simplest rule: the process that arrives first is executed first. It is easy to implement — the ready queue becomes a FIFO queue, each arriving process's control block is linked onto the tail, and whenever the CPU is free, the process at the head of the queue is allocated the CPU and removed. A classic picture: if arrival times are 0, 1, 2 — P1 arrives at 0, P2 at 1, P3 at 2 — and P1 takes 24 time units, then P1 runs first, followed by P2, followed by P3.

The convoy picture, fully worked. Processes P1, P2, P3 arrive at times 0, 1, 2 with bursts 24, 3, 3:

Process Arrival Burst Start Completion Waiting
P1 0 24 0 24 0
P2 1 3 24 27 24 − 1 = 23
P3 2 3 27 30 27 − 2 = 25

Gantt chart: P1 runs 0–24, P2 runs 24–27, P3 runs 27–30.

Average waiting time \(= (0 + 23 + 25)/3 = 48/3 = 16\) time units.

Sense-check: P2 and P3 needed only 3 units each, yet they sat in the queue for more than 20 units. If the short processes had arrived before the long one, the average would have been far lower — the ordering, not the work, is what punished them. This is the convoy effect in its simplest form.

The weakness shows up immediately in the average waiting time. Shorter processes have to wait for the longer process to complete before they get a chance. This drags the average up, and the effect has a name: the convoy effect — the short processes line up behind the long process like cars behind a slow truck. FCFS is also non-preemptive: once a process is taken into the CPU, it runs to full completion, and only then is it taken out. Because of that, the waiting time under FCFS tends to be more than under the other schedulers.

The professor's truck picture maps directly onto the metrics: the truck is the long process holding the CPU, the cars behind it are short processes with their response and waiting times piling up, and the traffic jam is the inflated average waiting time. The analogy stretches only so far — unlike a truck, a process cannot be overtaken on the road: FCFS never lets the short cars go around, which is precisely why the convoy forms. And the effect is not just a classroom curiosity: on a real system, a single CPU-bound process can park itself on the CPU while every I/O-bound process finishes its I/O, walks into the ready queue, and waits — with the I/O devices now sitting idle. The CPU and the I/O devices end up alternating between idle and saturated, which is the worst possible utilization pattern.

A practical point that follows: the workload should hold a balanced mix of CPU-bound and I/O-bound processes. If CPU-bound processes outnumber I/O-bound ones, or the other way around, the CPU alternates between being starved for work and being saturated; with a balanced mix the utilization stays even. That balance is one of the main aims of scheduling.

Pitfalls of FCFS:

  1. Treating FCFS as fair to short processes. Arrival order is the only rule; a 3-unit process that arrives one instant after a 24-unit process waits the full 24 units.
  2. Forgetting FCFS is non-preemptive. Once a process has the CPU, no new arrival can interrupt it — the running process keeps the CPU until it ends or asks for I/O.
  3. Ignoring the queue discipline in practice. A FIFO ready queue can still starve interactive users; FCFS is "particularly troublesome for time-sharing systems" because a single process can hold the CPU for a long stretch.
  4. Blaming the scheduler for I/O idle time. The convoy effect idles the I/O devices too, but the fix is a scheduling rule that lets short bursts go first — or a balanced mix of process types.

6.2.2 Shortest Job First and Shortest Remaining Time First

Shortest job first is the same family, called by either of two names depending on preemption: non-preemptive shortest job first (SJF), and preemptive shortest remaining time first (SRTF). SJF/SRTF gives the minimum average waiting time compared to the other scheduling algorithms. The throughput comes out the same in either version, since every process is completed within the same total span; what changes is how long each individual process waits, which depends on whether it is a short job or a long job.

SJF associates with each process the length of its next CPU burst; when the CPU is free, the process with the smallest burst is chosen, and ties are broken by FCFS. The textbook calls it "provably optimal": moving a short process ahead of a long one decreases the short process's waiting time more than it increases the long process's waiting time, so the average always drops. A stricter name would be "shortest next CPU burst first", since it is the next burst — not the total job — that decides.

SJF vs. FCFS, fully worked. Four processes arrive at time 0 in the order P1, P2, P3, P4 with bursts 6, 8, 7, 3:

  • FCFS order (arrival order): P1 0–6, P2 6–14, P3 14–21, P4 21–24. Waiting: 0, 6, 14, 21 → average \((0+6+14+21)/4 = 41/4 = 10.25\).
  • SJF order (shortest first): P4 (3) 0–3, P1 (6) 3–9, P3 (7) 9–16, P2 (8) 16–24. Waiting: P4 = 0, P1 = 3, P3 = 9, P2 = 16 → average \((0+3+9+16)/4 = 28/4 = 7\).

Sense-check: the same four processes, same total span of 24 units, but SJF cut the average waiting time from 10.25 to 7 — the 3-unit process no longer waits behind three longer ones.

The preemptive version — shortest remaining time first (SRTF) — preempts the running process the moment a newly arrived process has a shorter remaining time. The textbook runs the classic contrast: four processes with (arrival, burst) = P1(0, 8), P2(1, 4), P3(2, 9), P4(3, 5).

SRTF vs. non-preemptive SJF, fully worked.

SRTF gantt chart:

P1 P2 P4 P1 P3
0–1 1–5 5–10 10–17 17–26

Step by step: P1 starts at 0 (only process ready). At time 1, P2 arrives with burst 4 — P1's remaining 7 units are longer, so P1 is preempted and P2 runs. At time 2, P3 arrives with burst 9 (longer than P2's remaining 3 — no preemption). At time 3, P4 arrives with burst 5 (longer than P2's remaining 2 — no preemption). P2 finishes at 5. Now P4 (5) is the shortest remaining, so it runs 5–10. Then P1 (7) runs 10–17, and P3 (9) runs 17–26.

Waiting = completion − arrival − burst:

Process Completion Waiting
P1 17 17 − 0 − 8 = 9
P2 5 5 − 1 − 4 = 0
P3 26 26 − 2 − 9 = 15
P4 10 10 − 3 − 5 = 2

Average waiting \(= (9+0+15+2)/4 = 26/4 = 6.5\) ms.

Non-preemptive SJF on the same input: P1 runs 0–8 (it started first, so it cannot be interrupted), then P2 (4) 8–12, P4 (5) 12–17, P3 (9) 17–26. Waiting: 0, 7, 9, 15 → average \((0+7+9+15)/4 = 31/4 = 7.75\) ms.

Sense-check: preemption saved 1.25 ms of average waiting on average because P2 — short and arriving early — did not wait behind P1's whole 8-unit burst. The SRTF version wins whenever short processes arrive while a long one is running.

The catch with SJF: it assumes we know the length of the next CPU burst in advance. The tool used to predict that length is exponential averaging, which builds an estimate of the next burst from the history of previous bursts — already covered, and it applies directly here: if we can predict the next CPU burst, we can pick the shortest job correctly.

Exponential averaging — the recap that powers SJF. The prediction \(\tau_{n+1}\) for the next burst blends the most recent measured burst \(t_n\) with the previous prediction \(\tau_n\):

\[\tau_{n+1} = \alpha \cdot t_n + (1 - \alpha) \cdot \tau_n\]

  • \(\alpha = 0\): the prediction ignores the newest burst and keeps the old estimate (recent history is treated as noise).
  • \(\alpha = 1\): only the newest burst counts (the past is treated as irrelevant).
  • \(\alpha = 1/2\): newest burst and past history are weighted equally — the common default.

Expanding the recurrence shows why the name fits: each older burst's weight shrinks by a factor \((1-\alpha)\), so a weighted geometric series of history feeds the estimate. SJF can never be implemented exactly — the future burst is unknown — but with a good exponential average it can be approximated closely.

Recap and bridge. FCFS is the simplest, non-preemptive, and convoy-prone; SJF (non-preemptive) and SRTF (preemptive) minimize average waiting time but need the next burst length, which only exponential averaging can approximate. The comparison habit used here — same process set, two algorithms, one table of averages — is exactly the exam pattern, and it is the same habit we use next for priority scheduling, where the process set stays fixed and only the rule changes.

6.3 Priority Scheduling — Starvation and Aging

What happens when some processes are simply more important than others? The scheduler favors them — and the least important process may never run at all. That failure mode is called starvation, and the fix that operating systems actually use is aging.

6.3.1 The Priority Integer

In priority scheduling, every process is associated with a number — an integer, starting anywhere from zero upward. The rule of this class: the smallest integer has the highest priority. A process with priority 1 always outranks a process with priority 2, and so on.

Two details matter before any example. First, the convention: the course assumes low numbers mean high priority, and the textbook makes the same assumption — but some real systems do the reverse, so the direction of the ordering must be checked before solving any problem. Second, the source of the priority. Internal priorities are computed by the operating system from measurable quantities — time limits, memory requirements, number of open files, the ratio of average I/O burst to average CPU burst. External priorities are set from outside the system, by the importance of the process, the paying department, or administrative rules. Both feed the same scheduler.

The rule that runs priority scheduling: the CPU is allocated to the ready process with the highest priority, and equal-priority processes are served in FCFS order. Under this rule, SJF turns out to be a special case of priority scheduling — set each process's priority to the inverse of its (predicted) next CPU burst, and the scheduler automatically picks the shortest job. That one sentence connects the previous section to this one: SJF is just priority scheduling with a clever priority assignment.

6.3.2 Starvation

The natural failure mode is starvation: if the lowest-priority processes keep waiting, we cannot know when the other processes will finish and the low-priority ones will ever reach the CPU. Low-priority processes can wait indefinitely while higher-priority processes keep arriving and getting served.

The textbook calls starvation "indefinite blocking", and it is worth holding onto that phrase: a ready process that never gets the CPU is effectively blocked — not by I/O, but by the scheduler itself. In a heavily loaded system, a steady stream of high-priority arrivals can prevent a low-priority process from ever running. The real-system war story: when the IBM 7094 at MIT was shut down in 1973, operators found a low-priority process that had been submitted in 1967 and had still not run. Six years of waiting — that is starvation in its purest form.

6.3.3 Aging

The standard fix is aging. Every 15 minutes, the priority of a waiting process is increased, so its integer drops automatically toward the smallest value — the highest priority. Once the number reaches the top of the queue, the process is given the CPU for execution. Aging guarantees that even the lowest-priority process eventually runs.

Aging, fully worked. Suppose priorities run from 127 (lowest) down to 0 (highest), and a waiting process's priority number drops by 1 every 15 minutes.

  • A process at priority 127 reaches priority 0 after \(127 \times 15 = 1905\) minutes — that is 31.75 hours, so no process can starve for more than about a day and a half even in the worst case.
  • A process at priority 10 is guaranteed the CPU within \(10 \times 15 = 150\) minutes, or 2.5 hours, no matter how many high-priority processes keep arriving.

Sense-check: the guarantee is the point. Aging does not make the low-priority process fast; it puts a hard upper bound on how long it can wait, converting "possibly never" into "certainly within \(p \times 15\) minutes".

The intuition behind the mechanism: the priority integer is a counter of impatience. Every 15 minutes the waiting process's patience runs thinner, its number drops, and eventually it outranks everyone. The same idea reappears in later chapters under other names (a long wait in a low queue can promote a process to a higher queue), but the mechanism is always the same — wait time converts into urgency.

6.3.4 Preemptive and Non-preemptive

Priority scheduling also comes in non-preemptive and preemptive flavors. The non-preemptive version was worked last session; the preemptive version is what we build next.

The difference shows up exactly when a new process arrives while another is running. Non-preemptive priority scheduling simply places the new arrival at the head of the ready queue; the running process keeps the CPU until it finishes or blocks. Preemptive priority scheduling compares the new arrival's priority with the running process's priority on the spot — if the arrival's number is smaller (higher priority), the CPU is taken away from the current process and given to the new one.

Pitfalls of priority scheduling:

  1. Getting the convention backwards. In this course the smallest integer has the highest priority; assuming priority 1 is low priority inverts every gantt chart you draw.
  2. Forgetting that preemption happens on arrival. With preemptive priority, an arrival mid-burst can yank the CPU away — remaining work must be tracked, never restarted.
  3. Believing preemption fixes starvation. Preemption improves averages, but the lowest-priority process can still wait forever while higher-priority processes keep arriving; only aging removes the risk.
  4. Mixing internal and external priority sources without saying which is in force. The scheduler behaves the same either way, but the numbers mean different things — the exam problems use fixed priorities, so treat them as externally assigned.

Exam note: priority scheduling's exam-critical details are the convention (smallest integer = highest priority), the two flavors (preemptive vs. non-preemptive), and the starvation/aging pair — aging with the 15-minute increment and the eventual-run guarantee. 6.4 Preemptive Priority Scheduling — Worked Example

The same five processes are used for both versions, so the comparison is direct:

Process Arrival time Burst time Priority
P1 0 10 3
P2 1 1 1
P3 2 2 4
P4 3 1 5
P5 4 5 2

Remember the convention: smaller integer means higher priority, so the ranking from strongest to weakest is P2 (1), P5 (2), P1 (3), P3 (4), P4 (5). That ordering is the fixed reference for everything below.

6.4.1 The Non-preemptive Run (recap)

In the non-preemptive version, P1 arrives first at time 0 even though its priority 3 is not the highest. Since the algorithm is non-preemptive, P1 is given the CPU and must complete all 10 of its units before anything else runs. P2 arrives at time 1 with priority 1 — the highest — but it waits. By the time P1 finishes at time 10, every other process has arrived (all arrivals happen within times 0–4). From the remaining processes, the one with the highest priority runs next: P2 (priority 1, 1 unit), then P5 (priority 2, 5 units), then P3 (priority 4, 2 units), then P4 (priority 5, 1 unit).

This is where starvation shows up in a concrete form: even though the other processes arrived earlier, they wait indefinitely until all higher-priority processes complete. The non-preemptive run produced an average turnaround time of 64/5 = 12.8 ms and an average waiting time of 9 ms — the numbers we beat in the preemptive version.

The non-preemptive run in full. Gantt chart: P1 0–10, P2 10–11, P5 11–16, P3 16–18, P4 18–19.

Process Completion \(C\) Turnaround \(C - A\) Waiting \(\text{TAT} - B\)
P1 10 10 − 0 = 10 10 − 10 = 0
P2 11 11 − 1 = 10 10 − 1 = 9
P3 18 18 − 2 = 16 16 − 2 = 14
P4 19 19 − 3 = 16 16 − 1 = 15
P5 16 16 − 4 = 12 12 − 5 = 7

Sums: turnaround \(10+10+16+16+12 = 64\), average \(64/5 = 12.8\) ms. Waiting \(0+9+14+15+7 = 45\), average \(45/5 = 9\) ms.

Sense-check: P2 — the highest-priority process — still waited 9 ms because P1 was already running when it arrived and nothing could preempt P1. That is the signature of non-preemptive priority scheduling: the rule only decides who runs next, never who runs now.

6.4.2 Building the Gantt Chart for the Preemptive Run

Preemption changes the story at the first possible moment. P1 starts at time 0. At time 1, P2 arrives with priority 1 — higher than P1's 3 — so P1 is taken out of the CPU (it relinquishes the CPU voluntarily, though "voluntarily" here means the scheduler forces the swap) and P2 enters. P2's burst is only 1 unit, so it finishes at time 2.

From here the rule is: at every time unit, check the ready queue — every arrival can trigger a preemption. The OS maintains a queue of pending processes; whichever ready process has the smallest priority integer runs next.

  • Time 2: P3 arrives (priority 4), but P1's 3 beats it, so P1 resumes.
  • Time 3: P4 arrives (priority 5) — still lower than P1's 3, so P1 continues.
  • Time 4: P5 arrives with priority 2, which beats P1's 3. P1 is preempted again after having run only 3 of its 10 units; P5 enters.
  • P5 runs from 4 to 9 and completes fully (burst 5).
  • At 9, the remaining ready processes are P1 (7 units left), P3, and P4. P1 has the highest priority, so it resumes and runs its remaining 7 units, finishing at 16.
  • P3 runs next (priority 4) for its 2 units, 16–18.
  • P4 runs last (priority 5) for its 1 unit, 18–19.

The gantt chart:

\[ \begin{array}{|c|c|c|c|c|c|c|} \hline \text{P1} & \text{P2} & \text{P1} & \text{P5} & \text{P1} & \text{P3} & \text{P4} \\ 0\text{–}1 & 1\text{–}2 & 2\text{–}4 & 4\text{–}9 & 9\text{–}16 & 16\text{–}18 & 18\text{–}19 \\ \hline \end{array} \]

Two bookkeeping habits from this example are worth copying. First, track remaining burst as you go: P1 executed 3 units by time 4, so only 7 remain — never restart a preempted process for its full burst. Second, strike out processes as they finish and mark their remaining time 0, so the queue is always a true list of what is left.

Scope — how the preemptive rule is being applied here. The professor's rule for this example is "check the ready queue at every arrival; the ready process with the smallest priority integer runs". That makes this a strictly arrival-triggered preemptive priority schedule: preemption is considered at time 1 (P2 beats P1) and at time 4 (P5 beats P1), and at every other arrival the newcomer loses the comparison, so nothing changes. The chart above is exactly the schedule this rule produces.

6.4.3 Completion, Turnaround, Waiting, and Response Times

Completion time is the last instant at which the process finishes — even if it executed in several pieces, the final completion is what counts.

Process Completion \(C\) Turnaround \(\text{TAT} = C - A\) Waiting \(\text{WT} = \text{TAT} - B\) Response \(t_{\text{first}} - A\)
P1 16 16 − 0 = 16 16 − 10 = 6 0 − 0 = 0
P2 2 2 − 1 = 1 1 − 1 = 0 1 − 1 = 0
P3 18 18 − 2 = 16 16 − 2 = 14 16 − 2 = 14
P4 19 19 − 3 = 16 16 − 1 = 15 18 − 3 = 15
P5 9 9 − 4 = 5 5 − 5 = 0 4 − 4 = 0

Response time here is not the same as waiting time: response time is only the first entry into the CPU, so P3 arrives at 2 but first enters the CPU at 16, giving 14; P4 arrives at 3 but first enters at 18, giving 15.

Read the table twice, once per column family. The completion column is simply where each process's last slice ends: P2 at 2, P5 at 9, P1 at 16, P3 at 18, P4 at 19. The turnaround column then subtracts each arrival. The waiting column subtracts each burst — and the two processes with zero waiting (P2, P5) are exactly the ones whose entire burst ran in a single uninterrupted visit to the CPU. The response column is the sharpest signal of the scheduler's cruelty: P3 and P4 each waited 14–15 units before their very first CPU entry, because everything that outranked them ran first.

6.4.4 Averages and Throughput

6.5 Round Robin Scheduling

What if every process — long or short — got an equal, guaranteed turn at the CPU, over and over, in a circle? That is round robin, and its whole character follows from one number: the time quantum. The mnemonic the class uses: FCFS plus a time slice is equal to round robin scheduling.

6.5.1 Time Quantum and Context Switching

Round robin is one of the most famous scheduling terms, right alongside FCFS. The name says it: each process is given a certain fixed amount of time to execute in the CPU, and when that time is over, the next process present in the ready queue comes in. The fixed time given to the CPU per process is called the time quantum or time slice — the two names are interchangeable.

The guarantees: if \(n\) processes sit in the ready queue and the time quantum is \(q\), each process gets \(1/n\) of the CPU time, in at most \(q\) time units at a time. And no process has to wait longer than

\[(n - 1) \cdot q\]

time units — that is the longest stretch any process can wait between turns.

The \((n-1)q\) bound, worked. Five processes and a quantum of 20 ms. Each process gets up to 20 ms, and the queue cycles through all five processes before anyone returns: one full round takes \(5 \times 20 = 100\) ms, and a process waiting its turn can be delayed by at most the other four processes' slices, \((5-1) \times 20 = 80\) ms. With ten processes and a quantum of 10 ms, the bound is \((10-1) \times 10 = 90\) ms between turns.

Sense-check: the formula assumes every process actually uses its full quantum. A process that finishes early frees its slot, so the real worst case is at most \((n-1)q\) — never more.

The mechanics: the ready queue is treated as a circular queue. The scheduler picks the first process, sets a timer for one quantum, and dispatches. One of two things happens: the process's burst is shorter than the quantum, so it releases the CPU itself and the next process runs; or the timer goes off, an interrupt fires, a context switch is performed — the state of the running process is saved and the next process's state is loaded — and the preempted process is placed at the tail of the ready queue. Round robin is always preemptive, unless only one process is runnable.

The size of the quantum drives everything else:

  • If the quantum is large, the scheduler drifts into FCFS behavior. A quantum above the natural burst length means the process finishes anyway, so round robin degenerates into first-come-first-serve.
  • If the quantum is very small, every quantum boundary forces a context switch — saving the state of the current process and loading the state of the next one — and the overhead of switching from one process to another grows. With a 1 ms quantum, a new process is pulled in every millisecond, and the overhead dominates.

The example given for switch counts: a process whose execution takes 10 units under a quantum of 12 finishes inside its single quantum — zero context switches. Under a quantum of 6, the same process is switched out once and back in once, so two context switches occur. With a quantum of 1 ms and other processes waiting, the same 10-unit burst needs nine context switches. The mnemonic to remember:

FCFS plus a time slice is equal to round robin scheduling.

Why the switch count behaves that way. With quantum 12 and a 10-unit burst, the burst ends before the timer fires — the process never leaves the CPU, no save/load pair is needed. With quantum 6, the burst straddles two quanta: at time 6 the timer fires, the process's state is saved and the next process's state is loaded (switch 1); later the process comes back and the reverse save/load happens (switch 2). With quantum 1, the 10-unit burst is split into ten 1-unit slices, and each boundary between slices costs a save/load pair — nine boundaries, nine context switches. The theoretical extreme, a quantum approaching zero, is called processor sharing: each of \(n\) processes appears to own a processor running at \(1/n\) speed.

The cost is not theoretical. A context switch takes real time — the textbook's practical frame: if the context-switch time is about 10% of the quantum, then about 10% of the CPU time vanishes into switching. Modern systems keep quanta in the 10–100 ms range while a switch takes under 10 microseconds, so the fraction stays small — but shrink the quantum too far and the overhead eats the very responsiveness round robin exists to provide.

6.5.3 Choosing the Time Quantum

The average turnaround time varies with the time quantum, and the variation is not linear — it is zigzag. With a small quantum of 2, the average turnaround is high; at quantum 3 it drops; and as the quantum grows toward 5 and 7, the average turnaround climbs again. So the quantum must not be too large (FCFS behavior) and must not be too small (context-switch overhead).

Why the zigzag happens — three processes, same burst, two quanta. Take three processes, each needing 10 units, all arriving at time 0.

  • Quantum 10: each process finishes in its own single slice. Turnaround = 10, 20, 30 → average 20.
  • Quantum 1: the CPU cycles P1, P2, P3 one unit at a time for 10 rounds. P1 completes after 28 units (its last unit is in round 10), P2 at 29, P3 at 30 → average \( (28+29+30)/3 = 29 \), plus every round boundary paid a context switch.

Sense-check: doubling the quantum did not just double the turnaround — it reduced it, because whole processes stopped being chopped into ten pieces. The zigzag in the lecture's chart is the same phenomenon playing out across quantum sizes.

A practical guideline: about 80% of CPU bursts should be shorter than the time quantum. If the bursts are shorter than the quantum, the processes finish within their slice and no extra context switches are needed. Set the quantum so that the overwhelming majority of bursts fit inside it.

6.6 Multi-level Queue and Multi-level Feedback Queue Scheduling

FCFS, SJF, priority, and round robin each apply one rule to one queue. Real systems mix process types with conflicting needs — interactive users want fast response, batch jobs want throughput. What if the ready queue itself were split into several queues, each with its own algorithm? That is the idea behind multi-level queue scheduling.

6.6.1 Foreground and Background Queues

Multi-level queue scheduling splits the ready set into two queues: a foreground queue, where interactive processes execute, and a background queue, used only for batch-type processing. Each process is permanently assigned to one queue, and each queue has its own scheduling algorithm — for example, the foreground queue uses round robin while the background queue uses FCFS.

Permanent assignment is the defining feature: a process's queue is fixed when the process enters the system, based on a property such as process type, memory size, or priority. The foreground/background split is only the classic instance — any number of queues is possible, and each queue runs whatever algorithm fits its processes.

That leaves a second-level decision: scheduling between the queues. One option is to serve all foreground processes first and only then the background — but that starves the background queue, the same starvation we saw with priorities. The better option is to schedule between queues by time slice: each queue gets a fixed share of the CPU time, such as 80% for the foreground and 20% for the background. Within its share, a queue can execute at most a certain number of processes.

Starvation inside the queue hierarchy: giving the foreground queue absolute priority over the background queue reproduces exactly the starvation of section 6.3 — the background queue can wait forever behind a steady stream of interactive processes. The time-slice alternative (80% foreground, 20% background) guarantees the background queue a floor of CPU time, just as aging guarantees a floor for a starving process. This is the professor's explicit warning: serve all foreground processes first and the background queue starves; give each queue a share of the CPU time instead.

6.6.2 Queue Priorities

If the queues themselves are prioritized, the order runs from system-critical to user-level, roughly:

  1. System processes — the highest priority; initialization and configuration processes that keep the system running get first preference.
  2. Interactive processes — the user gives inputs and gets outputs, then gives more inputs; all real-time processes count as interactive.
  3. Interactive editing — processes where we change something: get output, do processing, then continue editing.
  4. Batch processes — a group of processes collected together and scheduled without being disturbed by any input or output.
  5. Student processes — user-executed processes get the lowest priority; the system and interactive work must be served first or the machine will not function properly.

How the five-level hierarchy behaves. Each queue has absolute priority over every queue below it: no process in the batch queue runs while any interactive-editing process is ready, and a process entering the interactive-editing queue preempts a running batch process on the spot. The ordering protects the machine's responsiveness — if system or interactive work is ever delayed by user-level work, the system appears frozen. The textbook frames the same five levels in exactly this order, from system processes down to student processes.

The full picture combines both decisions: inside each queue, the queue's own algorithm runs (round robin for interactive, FCFS for batch); between queues, either absolute priority (with its starvation risk) or time-slicing (80/20) applies. The two decisions are independent — a complete design specifies both.

6.6.3 Multi-level Feedback Queues

The multi-level feedback queue is a variation in which a process can move between queues. The scheduler that fixes the feedback behavior depends on three parameters: how many queues exist, which scheduling algorithm each queue uses, and when a process is upgraded from one queue to another or moved down from the first queue to the second.

The worked example uses three queues:

  • Queue 0: round robin with time quantum 8.
  • Queue 1: round robin with time quantum 16.
  • Queue 2: FCFS.

Every new process enters queue 0 first. It executes under round robin with quantum 8; if it finishes, it leaves the system. If it cannot finish within 8 time units, it is taken out of the CPU and placed in queue 1, where the quantum is doubled to 16. If it still does not complete within 16, it moves down to queue 2 and is served by FCFS. The queues themselves are served in strict priority order: all of Q0, then all of Q1, then Q2. This is the "feedback" — a process too big for the top queue is fed back to the next queue to execute. Exam note: the questions will be mostly based on the four schedulings — FCFS, SJF, priority, and round robin — with multi-level queue scheduling as the fifth topic covered here.

A trace through the three queues. Three processes arrive, with bursts 5, 20, and 30 units.

  • Burst 5: enters Q0, runs under round robin with quantum 8, finishes inside its first quantum — never leaves Q0.
  • Burst 20: enters Q0, uses its 8-unit quantum, does not finish (12 left), so it is demoted to Q1; there it gets a 16-unit quantum and finishes. Total service: 8 + 12 = 20, and it needed only two slices.
  • Burst 30: enters Q0, uses 8 (22 left), demoted to Q1, uses 16 (6 left), demoted to Q2, and runs under FCFS whenever Q0 and Q1 are empty, finishing its last 6 units there.

Sense-check: the feedback mechanism sorts processes by appetite. Short bursts are served with the fastest response in Q0; medium bursts get Q1; the longest bursts sink to Q2 and take leftover CPU. That is the textbook's summary: a process with a burst of 8 ms or less is served immediately, one needing 8–24 ms is served promptly but with lower priority, and longer processes automatically sink to FCFS.

A general multi-level feedback queue scheduler is defined by five parameters — the textbook's full list: the number of queues; the scheduling algorithm for each queue; the method used to decide when to upgrade a process to a higher-priority queue; the method used to decide when to demote a process to a lower-priority queue; and the method used to choose the queue a process enters when it needs service. The first two are enough to describe a design; the last three are what make it a feedback scheduler. The upgrade rule deserves special attention: a process that waits too long in a low queue can be promoted — this is aging in another costume, and it is what keeps the bottom queue from starving its residents.

Pitfalls of multi-level queue designs:

  1. Forgetting that plain multi-level queue assignment is permanent. A foreground process never becomes a background process mid-run; only the feedback variant moves processes between queues.
  2. Serving queues with absolute priority and calling it fair. Background work can starve; the professor's warning is explicit — give each queue a share of the CPU time instead.
  3. Mixing up the feedback direction. A process that overuses CPU is demoted (Q0 → Q1 → Q2), while waiting too long can promote it — the two rules pull in opposite directions and both exist.
  4. Skipping the "between queues" decision. Saying "queue 0 uses round robin" is only half a design; you must also say how the queues share the CPU, or the hierarchy is undefined.

Recap and bridge. Multi-level queue scheduling partitions the ready set into permanent queues (foreground/background, or the five-level system-to-student hierarchy) with an algorithm per queue and a rule between queues; the feedback variant adds movement, letting long bursts sink toward FCFS while aging-style upgrades protect the bottom queue. The one structural idea to carry forward: scheduling decisions nest — inside a queue, and between queues — and each level can reintroduce starvation if it is given absolute priority.

6.7 Thread Scheduling

Everything so far talked about scheduling processes. But on most operating systems the thing the CPU actually executes is a thread — and threads bring their own scheduling question: which of a process's many threads runs next, and who answers that question, the thread library or the kernel?

6.7.1 User-level and Kernel-level Threads

So far the discussion treated processes; now the same question is asked about threads. There are two kinds: user-level threads, which execute in user space, and kernel-level threads, which execute only at the kernel and have to be supported by the kernel — the kernel itself is part of the process, so kernel-level threads run under kernel supervision.

The thread models seen earlier are many-to-one, one-to-one, and many-to-many. In the many-to-one and many-to-many models, there is an intermediate level of placement: lightweight processes (LWPs). User-level threads are scheduled onto lightweight processors — the LWP sits between the user-level threads and the kernel-level threads — and from that queue the work is taken to the kernel level and executed. Scheduling user-level threads onto the lightweight processor is what makes the many-to-many model work.

The LWP as a virtual processor. From the thread library's point of view, an LWP appears to be a virtual processor on which the library can schedule a user thread to run; each LWP is attached to one kernel-level thread, and the kernel treats that kernel thread as a normal schedulable entity. The mapping chain in the many-to-many model is: user-level threads → LWP → kernel-level thread → CPU. If the kernel thread blocks on I/O, the LWP blocks too, and the user thread attached to it blocks with it — a fact that explains why a process with several LWPs can keep running while one of them waits.

The distinction matters because it decides who schedules what. The kernel cannot see user-level threads — they are managed entirely by the thread library in user space. The kernel can only schedule kernel-level threads. So in the many-to-many model the work splits into two decisions: the library picks which user thread occupies each LWP, and the kernel picks which kernel thread occupies each CPU. The one-to-one model collapses the chain — every user thread has its own kernel thread, and only the kernel's decision remains.

6.7.2 Contention Scopes: PCS and SCS

Thread scheduling then runs on two scopes:

  • Process contention scope (PCS) — the contention happens within the process: which of the process's own threads runs on the lightweight process. This is set by the programmer.
  • System contention scope (SCS) — the contention happens across the whole system: the kernel-level threads are scheduled onto the available CPUs, and the decision considers all threads present in the system — among 10, 15, or 20 threads, one is selected for a kernel thread to execute.

PCS and SCS are the two scheduling scopes a thread scheduler works with.

The two scopes on one machine. A process P runs five user threads, and the system holds 20 kernel-level threads in total (P's plus everyone else's).

  • Under PCS, the thread library decides which of P's five threads occupies each of P's LWPs — competition is only among P's own threads.
  • Under SCS, the kernel decides which of the 20 kernel-level threads runs on each CPU — competition is across the entire system.

Sense-check: PCS is decided by the programmer-controlled thread library (typically priority-based — the runnable user thread with the highest priority wins); SCS is decided by the kernel. Systems built on the one-to-one model, such as Windows and Linux, schedule entirely under SCS, because there is no LWP layer for a library-level choice to apply to.

6.7.3 pthread Scope APIs and Worker Threads

Each scope has a specification constant: pthread_scope_process for PCS and pthread_scope_system for SCS. Linux and macOS use exactly this configuration mechanism to specify whether a thread schedules under PCS or SCS.

The API flow goes: create the thread ID and thread attributes, initialize the attributes, get the scope, check that the call succeeded, then check whether the scope is process-related or system-related. If it is process-related, the program prints the scope and moves on to thread creation. Once PCS or SCS is set, we create that many threads with the help of an array, and each thread is joined at the end. Each created thread begins its work through the runner function — the thread's control starts there — and when the runner function completes, each thread has done its work and is joined. These are the worker threads: the threads that actually carry out the work in a multithreaded program.

The pthread machinery, function by function. The two POSIX calls are pthread_attr_setscope() and pthread_attr_getscope(): the first takes the thread attribute set and a scope value (PTHREAD_SCOPE_SYSTEM or PTHREAD_SCOPE_PROCESS) and stores the choice in the attribute; the second takes a pointer to an integer and fills it with the current scope setting. Both return nonzero on error, which is why the class's flow checks the return value after each call. The typical program then: initializes the attributes with pthread_attr_init(), queries the current scope, prints it, creates the desired number of threads from an array (each running the same runner function), and joins every created thread before ending. One platform caveat from the textbook: Linux and macOS allow only PTHREAD_SCOPE_SYSTEM — asking for process scope on those systems fails, because their one-to-one thread model leaves no LWP layer to schedule.

A worker-thread pattern in miniature. A program wants four jobs done concurrently. It creates an array of four thread identifiers, and in a loop creates four threads, all starting in the same runner function but each given its own job index. The runner function carries out the job — that is the thread's whole existence: start at the runner, do work, return. Back in the main thread, a loop joins each thread, which makes the program wait until that thread has finished before continuing. The four threads are worker threads: they do not manage anything, they simply execute the work handed to them.

Pitfalls of thread scheduling:

  1. Attributing the wrong decision to the wrong layer. PCS is the thread library's choice among one process's threads; SCS is the kernel's choice across all kernel-level threads. Saying "the kernel schedules user threads" is only true when the model maps one-to-one.
  2. Forgetting the LWP in many-to-many. User threads are not directly scheduled onto CPUs in that model — they go onto LWPs first, and the kernel schedules the LWPs' kernel threads.
  3. Ignoring scope support per platform. PTHREAD_SCOPE_PROCESS is not available everywhere; on Linux and macOS only PTHREAD_SCOPE_SYSTEM is honored.
  4. Skipping the error check after the scope call. Both pthread scope functions return nonzero on failure; the class's flow checks the return before trusting the attribute value.

Recap and bridge. Thread scheduling splits into PCS (thread library vs. the process's own threads, on LWPs) and SCS (kernel vs. all threads in the system); pthread_scope_process and pthread_scope_system are the constants that pick the scope, and worker threads started in a runner function and joined at the end are the standard way real programs put the choice to work. The scope idea carries into the next section unchanged: once multiple processors exist, the SCS decision itself becomes a multiprocessor scheduling problem.

6.8 Multiple-Processor Scheduling

One CPU means one decision at a time. With several CPUs, the scheduler becomes a team manager: several threads run at once, threads develop loyalties to processors, memory sits closer to some processors than others, and the workload must stay even. Each of those twists changes what "scheduling" means.

6.8.1 Single Processor, Multiple Processors, and Multiprocessing

The scheduling question changes when more than one CPU is available: with multiple CPUs, multiple threads can be placed for execution at the same time. With a single processor, the first thread must complete before the next thread's scheduling begins.

The lecture ties the single-processor contrast to asymmetric multiprocessing: one processor takes the role of the master, and the others simply execute. The textbook's definition runs in the same direction but states the split precisely — asymmetric multiprocessing (AMP) is the arrangement where a single master processor handles all scheduling decisions, I/O processing, and other system activities, while the other processors execute only user code. Its virtue is simplicity: only one processor touches the system data structures, so there is little need to coordinate shared data.

Symmetric multiprocessing (SMP) is the multi-processor arrangement: each processor is self-scheduling. Each processor has its own queue, or a common queue exists from which processes are picked and handed to processors for execution. With a common queue holding P1, P2, P3, processor 1 picks P1, processor 2 picks P2, and so on — you can think of the processes as threads for this picture. The core aim of symmetric multiprocessing is keeping every processor busy.

The two arrangements, side by side.

Asymmetric (AMP) Symmetric (SMP)
Who schedules one master processor makes all decisions every processor schedules itself
Other processors execute user code only run the scheduler too
Data structures touched by one processor — simple shared across processors — needs care
Risk master is a single point of failure two processors could pick the same process unless the queues are guarded

In SMP, two processors choosing the same process from a common queue is a real hazard: the queue access must be protected so processes are never lost or double-assigned. Virtually all modern operating systems — Windows, Linux, macOS, Solaris — support SMP. In the common-queue variant the aim is direct: processor 1 takes P1, processor 2 takes P2, each CPU stays busy; in the private-queue variant each processor manages its own list and the evenness of the load becomes a separate problem, solved by load balancing (section 6.8.3).

6.8.2 Processor Affinity and NUMA

A thread running on a processor tends to stay there: the process develops an affinity for the processor in which it is running. If a thread always executes on the same particular processor, that is soft affinity.

The lecture's wording for the two flavors runs opposite to the textbook convention, and both forms are worth knowing: the class used soft affinity for "always runs on the same processor", while the standard definition is the reverse — soft affinity is the policy of attempting to keep a process on the same processor without guaranteeing it, so migration remains possible, and hard affinity is the stronger policy in which a process specifies that it must not migrate to other processors (Linux provides system calls for exactly this). Whichever labels a text uses, the underlying reason for affinity is the same, and that is the part that matters: a process running on a processor warms that processor's cache with its data, and migration throws that warmth away.

The memory connection is why affinity matters. Each processor has its own attached memory; a thread reads its local memory fast. If the thread migrates to another processor — this processor P1, then moved to processor P2 — the data lives in the other processor's memory, and every access must cross to that memory. That remote access is slower, and the migration itself takes time. This arrangement is non-uniform memory access (NUMA): some memory is closer (faster) than other memory. Migration between processors slows the process down, which is why affinity is valuable.

Affinity and NUMA, in numbers. A thread's working set lives in the memory attached to processor 1; reading from that local memory costs, say, 1 unit per access. If the thread migrates to processor 2, every access to the same data now crosses the interconnect to processor 1's memory, costing 5 units per access — plus the migration itself (save state on P1, load on P2, invalidate and refill caches). Ten thousand such accesses turn a fast thread into a slow one purely because of where it sits.

Sense-check: the scheduler and the memory-placement algorithms must cooperate — a process with affinity to a CPU should get its memory on the board where that CPU lives, so that "local" stays local. When they work together, affinity is a performance feature; when they disagree, the same data becomes a remote-access penalty with every schedule.

6.8.3 Load Balancing

The constant requirement is that every CPU stays loaded. If one processor is heavily loaded while another is nearly idle, the workload is uneven. Load balancing distributes the workload evenly among processors, and it uses two mechanisms:

  • Push migration — periodically, the system pushes some process from a heavily loaded processor to a lighter one.
  • Pull migration — a lightly loaded or idle processor pulls a process from the heavily loaded processor. The class's phrasing for this second mechanism was "full migration"; the standard term used in every textbook is pull migration.

Push migration runs on a schedule — the system checks each processor's load periodically and evens out any imbalance it finds. Pull migration runs on demand — an idle processor goes looking for work and takes a waiting process from a busier one. The two are often implemented together: Linux runs its load-balancing algorithm every 200 milliseconds (push), or whenever a processor's run queue is empty (pull). Note when load balancing is needed at all: with a single common run queue, an idle processor simply takes the next process from the queue and balance is automatic; with private per-processor queues — the common modern design — imbalance can build up, and balancing mechanisms are required.

Load balancing vs. affinity — a real trade-off. Every migration that evens the load also breaks the thread's affinity: the process leaves its warm cache behind and, under NUMA, may start hitting remote memory. Push and pull migration work directly against the benefit affinity exists to provide. Systems differ in how they resolve the tension — some let an idle processor always pull, others move processes only when the imbalance exceeds a threshold. The lecture's warning stands: migration across processors is not free — context switching and NUMA remote memory access slow the thread down.

6.8.4 Multicore and Hardware Threads

Modern chips put multiple cores on one die. Each core carries a number of hardware threads, and each hardware thread can take one user-level thread and execute it. If a core has 8 hardware threads, that core can execute 8 threads at the same time — multiply by the number of cores on the chip. Multiple cores mean faster execution and less power consumption than scaling a single core.

Counting logical processors. The UltraSPARC T1 chip has 8 cores per chip and 4 hardware threads per core — from the operating system's point of view that is \(8 \times 4 = 32\) logical processors, even though the die is one physical chip. An Intel Itanium is a dual-core processor with two hardware-managed threads per core, giving 4 logical processors, and IBM's processors follow the same pattern with their own core and thread counts.

Sense-check: each hardware thread is a tiny processor with its own register set, which is why the OS sees it as a schedulable CPU. The scheduling now runs at two levels: the OS picks which software thread runs on each hardware thread (any of the algorithms of this chapter), and the core itself picks which hardware thread executes (the UltraSPARC T1 rotates its four hardware threads in round-robin fashion; the Itanium picks the thread with the higher urgency value among its two).

Real-world: the examples named are UltraSPARC, IBM, and Intel chips — each vendor has its own number of cores, and each core may have a different number of hardware threads; every hardware thread is capable of executing user threads. The advantage of many hardware threads is that there are always threads ready to execute. The unavoidable disadvantage is the time taken to switch from one core to another — that cost cannot be eliminated.

6.8.5 The Compute/Memory Stall Cycle

Picture a single processor. A thread computes — call that C — then it is taken out of the CPU for I/O or some interruption, and the processor enters a memory stall (M): the processor is idle, no work is done during the stall. Later the thread returns and computes again. Single-processor life is an alternating compute-and-memory-stall cycle, with the processor wasted during every stall.

The stall is not an exotic event. When a processor accesses memory and the data is not in cache — a cache miss — it can wait a significant fraction of its time for the data to arrive; in the textbook's estimate, a processor can spend up to 50% of its time waiting for memory. Every one of those stalled cycles is CPU time that computes nothing.

With multiple cores — two cores, say — one thread computes on the first core while another thread computes on the second. When one thread enters a memory stall, the other core's thread can still execute; and if both threads are stalled at different times, a thread that is free can be pushed onto the other core. During a memory stall there are chances for migration of a thread from one processor to another. But migration is not free: context switching and the overhead of placing the thread on the new processor still exist. That overhead is the known problem in multi-core systems.

Hiding the stall with hardware threads. A core with two hardware threads interleaves their execution: when thread 0 stalls waiting for memory, the core switches to thread 1 and keeps doing useful work. Two flavors exist: coarse-grained multithreading switches only on long-latency events like memory stalls (the switch is expensive — the pipeline must be flushed and refilled), while fine-grained (interleaved) multithreading switches at instruction-cycle boundaries (cheap, but needs extra switching logic in the chip). The compute/memory-stall cycle is the reason this hardware exists: with several threads on a core, a stall in one thread is another thread's turn.

Pitfalls of multiprocessor scheduling:

  1. Treating migration as free. Every migration costs a context switch, cache invalidation, and possibly NUMA remote access — the lecture's explicit warning is that this overhead cannot be eliminated.
  2. Balancing loads without honoring affinity. Push and pull migration fix unevenness but destroy cache warmth; the two goals trade off, and real systems tune the trade.
  3. Counting cores, not hardware threads. A chip's schedulable capacity is cores × hardware threads per core (UltraSPARC T1: 32 logical processors, not 8).
  4. Assuming one shared queue means no balancing needed. True, but only for the shared-queue variant; with private per-processor queues, imbalance is the default and balancing is required.

Recap and bridge. Multiprocessor scheduling adds three concerns on top of the single-CPU algorithms: SMP self-scheduling with shared-queue safety, processor affinity (cache warmth and NUMA local memory) that migration destroys, and load balancing via push and pull migration that fixes the imbalance but costs the affinity. On multicore chips, hardware threads hide the memory-stall cycle — the compute/stall alternation that wastes a single core. The same evaluation question that ends the process scheduling discussion — which algorithm is actually best? — is answered next.

6.9.1 Deterministic Modeling

Deterministic modeling means fixed and known: take a specific workload and compute each algorithm's performance on it. This is exactly what the worked examples did — processes arriving at known times with known burst times, then average waiting time, average turnaround time, everything computed per algorithm.

The comparison example: the same input given to FCFS yields an average waiting time of 28 ms; given to SJF (non-preemptive), 13 ms; given to round robin, 23 ms. Judged on these numbers, SJF is the optimal choice — analyze any problem and shortest job first gives the minimum average waiting time compared to the others. The catch remains: SJF needs the length of the next CPU burst, which is not known in advance; that is where exponential averaging returns.

6.9.2 Queuing Models and Little's Formula

The queuing model needs the process arrival times, the service rate of each queue, and how long processes wait in the queue. From these we compute the average queue length and the average waiting time using Little's formula from queuing theory. If \(n\) is the average queue length, \(w\) the average waiting time, and \(\lambda\) the average arrival rate into the queue, then

\[n = \lambda \cdot w\]

Little's formula applies for any arrival distribution and any scheduling algorithm. The class example: seven processes arrive per second, and 14 processes sit in the queue, so the average waiting time is \(w = n / \lambda = 14 / 7 = 2\) seconds — each process waits two seconds on average before reaching the CPU. The whole system stays healthy only if the queue length, the waiting time, and the arrival rate are all reasonable; when everything is optimal, the average waiting time stays low.

Why Little's formula holds for everything. Think of the queue as a pipe: processes flow in at rate \(\lambda\), and each one spends on average \(w\) time units inside. In steady state, the number inside the pipe at any moment is the inflow rate times the residence time — the same logic as a highway: 7 cars per second entering, each taking 2 seconds to pass a point, means \(7 \times 2 = 14\) cars on the stretch at any moment. The formula needs no assumption about the arrival distribution or the scheduling rule — that generality is what makes it a law of queuing theory rather than a property of one scheduler.

The practical limitation: the inputs are distributions, not exact values. Arrival and service distributions are often chosen because the mathematics is tractable rather than because they describe reality, and the model's independence assumptions may not hold — so queuing models are frequently approximations, and their answers should be read as estimates.

6.9.3 Simulation and Trace Tapes

Simulation builds a model of the system. A variable acts as the clock and increases over time; events are generated at probabilistically chosen clock values, based on random number generation feeding some distribution. The distribution can be mathematical — a Poisson distribution or a normal distribution — or empirical, drawn from the events actually observed. In the model, the processes under study are fed through the candidate CPU schedulers; when an event occurs, the affected process moves into the appropriate queue, and each scheduling algorithm is simulated with the help of the model.

The weakness: we know which algorithm to apply, but the order in which events occur is not known. The ordering is supplied by a trace tape — a record of the sequence of events, stating which event occurs at which point in time. With the trace tape, the simulation reproduces a real, recorded history. The outcome remains empirical, which is why the next method exists.

Clock, events, and tape — the simulation mechanics. The model is a program: a clock variable ticks forward, and at each tick the model checks whether a random-number generator says an arrival or an I/O completion should happen at this clock value — Poisson and normal distributions are the usual mathematical choices, or an empirically measured distribution of bursts can be used instead. Candidate schedulers are plugged into the same generated event stream, and each one's queue behavior is recorded. A trace tape then replaces the random generator with a real recorded sequence — which event, at which time — so the same history can be replayed against every candidate algorithm. The honest reading of the results: the simulation is only as good as the tape or the distribution, which is why its outcome stays empirical.

6.9.4 Implementation-Based Evaluation

Implementation-based evaluation skips the models: actually implement the scheduler and test it on a real system, measuring everything against the real workloads. It is the best method because it measures reality. Its problems: the risk is high and the cost is high. The environment varies — an implementation tuned for one system must be rewritten for the next processor architecture, adding more cost. Still, among the four methods, the implementation-based one is the best because we implement the scheduler and observe which one performs better on the real machine.

Scope — when each method is the right tool. Deterministic modeling is for textbook examples and controlled comparisons; queuing models are for systems whose arrival and service distributions are stable enough to estimate; simulation is for comparing candidates on realistic (or recorded) workloads without touching the real system; implementation-based evaluation is the ground truth but is expensive, risky, and bound to one architecture — every processor architecture change forces a new implementation. Pick the cheapest method that can answer the question honestly.
