1.1 Course Scope and System Engineering View

1.1.1 What This Course Covers

A working conversational AI system (a full setup that talks with a person, recalls what was said, uses tools, and finishes a task) is built from parts, not from one giant model. Think of a restaurant: the chef cooks well, but the meal still needs a waiter, a menu, a cashier, and a clean kitchen. The model is the chef. This course builds the rest of the restaurant.

This course covers the end-to-end parts of a conversational AI system from a framework view. The focus is on how to put built parts together into a working pipeline that serves a business task. The focus is not on training or tuning the base model weights from scratch. A parallel course on language models for generative AI covers model building, tuning, and model-side checks. This course covers assembly, use, and day-to-day running of a steady pipeline.

A safe AI companion (a system that can talk with a person, recall what was said, look up the right tools, plan how to use those tools well, run the steps, and reply back in plain talk) holds the full arc of the course. Take that one line as the map: talk, recall, look up, plan, run, reply.

Takeaway: This course builds the system around the model, and the running case is always a bank bot that must finish real tasks safely.

Banking help desks, card support chats, and in-house help bots are the running cases used to explain each part. Each later concept lands on one of these cases, so keep them in mind as the home examples.

1.2 Capabilities of a Conversational System

1.2.1 Plain Definition

What must a bank bot actually do? A user types a few words, and the bot must get the aim, hold the setting, pull in facts, reply, and take steps. Miss any one of these and the chat stalls: right words with no memory means repeat asks, good memory with no tools means smooth talk that fixes nothing.

A conversational AI setup (a system that talks in plain human tongue to get the aim, hold the setting, pull in facts, reply, and take steps) has six core skills: grasp of aim, care of chat memory within turns, use of past chats across turns, recall of facts, plain-talk replies, and use of outside tools.

Dialogue care means the system recalls what matters for the task at hand. Some facts need no deep recall store. A plain JSON key-value shape is enough to hold them across turns. A cache (a small fast store on the desk that holds oft-used items for a short time) fits short holds, while a wider memory (a store made for AI use that spans turns and meets) fits lasting holds.

Takeaway: Six skills carry every chat: grasp the aim, hold the setting, pull facts, shape replies, run tools, and stay safe throughout.

1.2.2 Where Each Skill Sits

Grasp of wording sits at entry. Dialogue care sits in the middle and holds state. Fact recall pulls from approved papers. Reply building shapes the words the user sees. Tool use runs back-end steps such as checking an account. Safety checks sit at many points. Health tracking and logs sit around the whole run.

That layout matters because each later section of this lecture fills one slot: wording sense feeds the intent read, dialogue care feeds the slot state, recall feeds grounded replies, tools feed the account checks, and safety plus logs wrap the full run.

1.2.3 Asking the Room for a First Map

An early talk asked what a conversational setup should do. Answers named chat bots, smart chat bots, agent setups, prompt skill, long setting hold, and multi-turn talk. The reply back was that all these points are in fact the map for the course, and the next step was to ask how an agent could hold a multi-turn talk by recalling a returning user.

Q: To hold a multi-turn talk, how should the agent store facts so it can spot a returning user?

A: A short store such as a cache can hold facts for a short time. For lasting hold across meets, the setup needs a memory part made for AI use. It can live within one meet or span many meets.

1.3 Card Lost Help Example and Intent Ambiguity

1.3.1 The Three-Word Query

A bank user writes only three words: card, lost, help. That tiny note could mean three different things, and the room split on it the same way. This is the whole course in one line: short human notes hide the aim, so the first job is a smart read, not a fast answer.

A bank user writes only three words to a bank bot: card, lost, help. The task is to infer what the user wants from just that. Even people in the room gave split reads. One read was the user wants to block the card now. One read was the user only wants help notes. One read was the user wants to learn the steps of what to do next.

The point is that even people cannot pin down one aim from three words. A machine faces the same gap. So the first job is to ask for more facts in a smart way, but to ask a sharp follow-up the setup must first get a fair read of those three words. Three words split people too, so the machine needs a wording sense step before it dares to act.

1.3.2 Why Keyword Hunt Fails

A plain word-hunt cannot fix the aim here. The three words in a row carry a joint sense that shifts with order and setting. The wording in the room was that "a simple keyword hunt will not work, we need a language model that gets what the three words put together mean".

An intent read (a guess at what the user wants the system to do next, written \(\text{aim}\)) is scored as a chance over acts given the input. Here \(x\) is the input word row and \(\text{aim}\) spans acts such as reply, route, or check identity. The rebuilt form is \(P(\text{aim} \mid x)\), where \(P\) is a chance number in \([0,1]\) over acts that adds to 1.

The words card, lost, and help each map to a vector, the model weighs each part, and the joint vector points to the most likely next act. A lone word like "help" says almost nothing, while "lost" next to "card" tilts the read toward a card-safety act. That joint read is exactly what a word-hunt misses, since it scores words one by one instead of as a row.

Pitfall: Treating each word alone ("card" means card page, "lost" means lost page) hides the joint aim. A phrase such as "help" alone can match hundreds of pages, so a lone-word match rate means nothing about the true act.

1.3.3 Asking Smart Follow-Ups

The room plan was to keep the talk going with follow-up queries. But a sharp follow-up still needs a first read of the words. Options raised were to give the user a few fair choice buttons, or to shape one kind follow-up line. Both need a wording sense part at entry. That part is the natural wording sense step that feeds all later steps.

A fair choice board might list "block my card now", "show me what to do next", or "talk to staff". A kind single line might say "sorry to hear that — do you want me to block the card right away, or walk you through the steps first". Both paths need the same wording read first; the choice is only about how the bot asks, not whether it reads.

Q: Given only card, lost, help, can the app get the business talk?

A: Not from words alone. It needs a wording sense step that reads the row as a whole, then it can shape a tight follow-up or a short list of fair choices to pin down the aim.

Takeaway: Three words hide three aims, so read the row as a whole first, then ask a sharp follow-up. That read-then-ask order drives the pipeline in the next section.

1.4 Transformer Encoder for Intent Classification

1.4.1 From Words to Numbers

Machines read numbers, not words. So how does "card, lost, help" become math without losing word order? Each word becomes a number row, plus a place mark that says "I was first, second, or third". Lose the place mark and "help lost card" looks the same as "card lost help".

Machines read numbers, not words. So each word is turned into a math form. The wording in the room was that "we turn the words into a math form, a vector for each word, with place marks added, and the model weighs each part".

A word vector (a number row that stands for one word, written \(v\)) lives in a \(d\)-place row: \(v \in \mathbb{R}^{d}\), where \(\mathbb{R}^{d}\) is a \(d\)-place number row and \(d\) is the width such as a small demo width. A place mark (a number row that marks slot order, written \(p\)) sits in the same space: \(p \in \mathbb{R}^{d}\). Adding keeps the same shape, giving \(z = v + p\) for each slot.

For the three-word row, that gives \(z_1 = v_1 + p_1\) for card, \(z_2 = v_2 + p_2\) for lost, and \(z_3 = v_3 + p_3\) for help. Same word in a new slot gets a new \(z\) because its \(p\) differs. That is the full trick: meaning plus place, in one row.

1.4.2 Attending to Each Part

A transformer-style net takes the row \(z_1, z_2, z_3\) for card, lost, help and weighs each slot. The plain-words account was that it "takes in these facts, attends to each part of the words, and works out the aim of the whole three-word row".

An attention weight (how much heed one slot pays another when building its setting-aware form) lets "lost" lean on "card" more than on "help". The rebuilt score step is \(s = w^\top z\), where \(w \in \mathbb{R}^{d}\) is a weight row and \(s \in \mathbb{R}\) is a plain number score. In full use the net builds setting-aware forms for each slot and then pools them for a choice.

A tiny number sketch shows the shape. With a toy width \(d = 2\), take \(z_1 = [0.9, 0.1]\) for card, \(z_2 = [0.8, 0.4]\) for lost, \(z_3 = [0.1, 0.9]\) for help, and \(w = [1.0, 0.5]\). Then \(s_1 = 0.95\), \(s_2 = 1.00\), and \(s_3 = 0.55\), so "lost" scores top once "card" sits beside it. Real nets learn \(w\) and pool across all slots, but the idea is the same: weigh each part, then read the row.

Scope: This score step treats the row as given and fixed. It breaks when the ask spans many turns or needs past meets, since one row alone cannot hold that past. Those cases need the state and memory parts from later sections.

1.4.3 Encoder Plus Choice Head

For this job no text maker is needed. An encoder alone is enough. The encoder builds joint forms and a plain feed-forward head picks the next act. The wording in the room was to "take the three words, build their setting forms, push them through a feed-forward net that picks a class, and let that class steer the next follow-up".

A demo score row over three acts — reply-only, route-to-staff, and check-identity — came out as reply-only low, route-to-staff at \(P(\text{route} \mid x) = 0.1\), and check-identity at \(P(\text{check-identity} \mid x) = 0.9\). Here \(x\) is the three-word input and each \(P\) is a number in \([0,1]\) adding to 1 across acts. The top act is check-identity at 0.9, so the chat path moves to identity checks first. Sense-check: a lost-card cry should rank a safety check above a plain reply, which matches this row.

Q: Which model shape can weigh each word and pick a next act?

A: A transformer encoder. It reads the word vectors with place marks, weighs card, lost, and help, and feeds the joint form to a head that picks reply, route, or check-identity.

Takeaway: Turn words into placed rows, weigh each slot, and let a small head pick the act. That encoder-plus-head path is the fast route when no fresh prose must be written.

1.5 Generator Alternative and Dialogue Management

1.5.1 Decoder Path That Writes the Reply

The encoder path picks an act. But what if the bot must write fresh kind words instead of picking from a short list? Then no fixed choice head is enough — the system needs a maker that writes the reply word by word.

The other path skips a fixed choice head and tunes a maker to write the reply straight from the three words. The wording in the room was that "the model is tuned to make replies and give follow-ups straight from the facts in these three words, with no fixed gate in between".

A next-token form (the chance of each fresh word given the words written so far and the input, written \(P(y_t \mid y_{\lt t}, x)\)) drives the maker. Here \(x\) is the input row, \(y_{\lt t}\) is the words written so far, and \(y_t\) is the next word. A decoder-style maker is the core of this path: it picks \(y_1\), then \(y_2\) given \(y_1\), and keeps going until the reply ends.

Path Core part Output When it fits
Encoder plus head Encoder, then a choice head One act label such as check-identity The next step is a known act
Decoder maker Decoder that writes token by token Fresh reply words The next step needs kind, shaped prose

Pick the encoder path when the act list is fixed and speed matters. Pick the maker path when the user must read warm, shaped words that fit the moment.

1.5.2 What Dialogue Care Must Do

Dialogue care (the middle part that holds the chat state, picks kind follow-ups, and keeps the flow smooth) takes over once the aim read says check-identity first. It must ask kind follow-ups, shape them for the user, reuse known facts, and keep the chat flow smooth.

The talk stressed that follow-ups should be tuned, not blunt. A kind form was "sorry to hear that, please share your account facts so we can help better". A blunt form was "share name and account". The tuned maker picks the kind form, fits it to the user, and keeps the tone calm.

Pitfall: A blunt ask ("share name and account") reads like a demand and raises fraud fear in a bank chat. A tuned ask names why the facts are needed ("so we can hold your card fast") and keeps the tone calm.

1.5.3 Recalling Past Meets

If the same user spoke a few days back, the setup should not ask again for known facts. That would only annoy. The wording in the room was that "if the user page is known, do not ask again for known facts, shape the reply around what is known".

A better reply names the user, notes the known account shape in broad terms, notes when the card was last used in broad terms, and says help is on the way. That is setting-aware talk: wording sense plus stored user facts plus a well-tuned maker. The encoder read from the prior section plus this stored page is what lets the bot skip repeats.

Q: Should the bot just ask for name and account ID in fixed words?

A: No. Follow-ups should be shaped for the user and for what is known. A well-tuned maker writes them in a kind way, skips known facts, and keeps the flow moving.

Takeaway: An encoder picks the act, a maker writes the words, and dialogue care keeps both kind and non-repeating. Next comes the small slot map that holds the facts across turns.

1.6 State Slots and the PIN Security Lesson

1.6.1 Slot Shape for Identity Checks

A kind reply alone cannot check identity. Where does the bot keep "name known, account shape still missing" between turns? It keeps a small slot map that fills bit by bit as each reply lands.

To check identity across turns, the setup holds a small state in JSON key-value form. A plain subset was name, account shape such as savings or current, branch, card shape such as debit or credit, card use-by date, and card PIN. The state fills bit by bit as the user replies. If the name is known from the stored page, that slot fills at once. Other slots fill as new replies come in, and some slots get re-tested for safety.

The wording in the room was to "keep asking across turns and fill the slots, name first if known, then account shape, then card facts, and hold them as the state for later steps".

A state map (the small slot board for the live task, written \(S\)) holds each slot name and its value: \(S = \\{k_i : v_i\\}\), where each \(k_i\) is a slot name and each \(v_i\) is its filled value or blank. Filling is an update \(S_{t+1} = \text{fill}(S_t, u_t)\), where \(S_t\) is the state at turn \(t\) and \(u_t\) is the new user reply row. A blank stays blank until the user gives that fact.

A three-turn sketch shows the fill. Start with \(S_0 = \\{\text{name: blank, account: blank, card: blank}\\}\). The stored page fills name at once, giving \(S_1 = \\{\text{name: given, account: blank, card: blank}\\}\). The next user reply gives the account shape, giving \(S_2 = \\{\text{name: given, account: savings, card: blank}\\}\). The card-shape reply then fills the last slot. Each turn only adds what the user gave, and nothing else moves.

1.6.2 The PIN Mistake

Scope: The draft slot list wrongly held a card PIN. A PIN must never be asked for or kept in chat state — card shape and use-by facts in broad terms may be okay for routing, but a PIN is out of bounds.

The draft slot list held a card PIN. That is a safety break. The room caught it fast: asking for or storing a PIN in chat puts the user at risk. Card shape and use-by facts in broad terms may be okay for routing, but a PIN must never be asked for or kept in chat state. The fixed set drops the PIN slot at once.

The wording in the room was that "asking for the PIN in chat is fully wrong, even though the rest of the flow ticks the boxes for aim read, setting hold, fact pull, and reply". The lesson is that a flow can look right on chat skill yet still fail on safety. Safety checks must sit with the flow, not after it. The PIN moment is also the lecture's live correction: a smart flow that still leaks private facts fails the user test.

1.6.3 From Slots to Tool Use

Once slots for the check step fill, the chat part calls a back-end check tool. The wording in the room was that "the state facts are enough, pass them to a small back-end check code that says valid or not, then shape the next reply around that call result".

If the call says not valid, the reply turns to safe help and stops. If the call says valid, the reply can share broad card state and use past use in broad terms, then move to fix steps such as hold, swap, or send word soon. Asking the follow-ups is itself a step, but the back-end call is the act that moves the task on. The slot map is the handoff point: dialogue care fills it, the tool reads it, and the reply maker shapes what comes back.

Q: Is it fine to ask for card PIN to speed up identity checks?

A: No. That is a safety break. Drop the PIN slot, never ask for it in chat, and add a safety check that blocks such asks and such stored facts.

Takeaway: Hold a small slot map, fill it turn by turn, drop the PIN for good, and hand the filled map to a back-end check. Next come the safety checks that guard every handoff.

1.7 Guardrails: Placement, Static Rules and Dynamic Checks

1.7.1 Where Checks Must Sit

Where do safety checks sit — once at the door, or at every step? A user may paste a full card number in the very first note, while a maker may leak a private fact in the third reply. One door check catches only the first leak.

Safety checks must sit at entry, at each maker point, and at each turn edge. Entry checks clean user notes before they turn into vectors. Maker checks clean each made reply before the user sees it. Turn-edge checks clean both user-side facts and system-side facts as the chat moves on. The plain-words map from the room was to "put a check at entry, put a check at each place a maker writes, and put a check at the start of the wording sense step itself".

A bank user may paste a full card number with all digits in the first note. The entry check must catch and hide it before it reaches the model, and the maker check must catch it again if any later reply tries to echo it back.

1.7.2 Checks Set Against Broad Tests

A fact test (a broad shape check, such as "this card row has 16 digits") keeps data clean. A safety check (a risk check such as "does this fact put the user at risk if stored, sent, or shown") keeps the user safe. Both use code, but the aim differs.

The wording in the room was that "fact tests are broad, safety checks look for risk leaks, such as private facts being asked, kept, or shown". A 16-digit row passes the shape test yet fails the safety test when it is a live card number pasted in chat. Fact tests keep shape clean. Safety checks keep the user safe.

1.7.3 Fixed Rules Set Against On-the-Fly Rules

Some firms use fixed rules. A plain digit-pattern hunt can spot a long digit row that looks like a card or phone row and hide it. That is cheap and fast when the shape is known. Some firms want checks that shift with the step. The wording in the room was that "a fixed digit hunt works for known shapes, a shifting check fires only when the step needs it".

A shifting check (a gate that fires by act label) is written as a gate \(g(a) \in \\{0,1\\}\), where \(a\) is the act label and \(g = 1\) means run the check. For a plain reply act, \(g = 0\) may hold to save cost. For a check-identity act, \(g = 1\) holds.

Each extra check adds compute cost. So checks should sit where risk is high, not on each tiny step. Bank money moves call for fixed shape hunts. Open-ended talk may call for shifting checks tied to acts. A plain reply can skip the heavy gate, while a check-identity act always runs it.

Q: Are safety checks just fixed digit hunts, and will the same fixed set fit all firms?

A: No. Fixed hunts fit known shapes such as long digit rows. Shifting checks fire by act, such as only on check-identity. The pick rests on the firm task, known shapes, and cost caps.

Q: Should checks sit only at entry and at last reply?

A: No. They must also sit at each maker point and at each turn edge, since each made line is a fresh output that can leak facts.

Takeaway: Guard the door, each written line, each turn edge, and each risky act — with cheap fixed hunts for known shapes and act-gated checks where risk runs high.

1.8 LLM Augmentation, RAG Grounding, Memory and State

1.8.1 Where Large Model Help Sits

Must each chatbot part get a large model? No. Large models pay off where wording must be read or made — at the entry wording read and at each reply-making turn — and a plain rule board is enough elsewhere.

Large model help is not a must on each block. It is a strong fit where wording must be read or made. The map used here puts it at the entry wording read and at each reply-making turn. The wording in the room was to "put large model help where wording is read and where replies are made". Makers at each turn get this help so replies stay smooth and fit the user.

A fixed digit hunt needs no model. A slot fill needs only small code. But turning "card, lost, help" into an act read, and turning a filled slot map into kind words, both need wording skill. That is where the model budget goes.

1.8.2 Grounding Replies in Approved Papers

A maker alone can invent facts. Recall-augmented making (a pull-then-make loop that ties replies to approved papers) curbs that. The loop pulls the approved steps, then makes the follow-up, so the reply stays tied to the paper and invents less. The rebuilt form is \(P(y \mid x, D)\), where \(x\) is the user row, \(D\) is the pulled approved set, and \(y\) is the made reply. With \(D\) in place, the reply must stay close to \(D\) even if word choice stays free.

Bank policy papers that list what identity proof is needed feed the follow-up "please share card shape and use-by span", so the bot does not invent its own list. Without \(D\), the same maker might ask for a PIN or invent a new proof list. With \(D\), the ask list is fixed by the paper and only the wording stays free.

Pitfall: Grounding trims invention but never removes it. A maker can still bend a tied fact with warm words, so the maker-point check from the prior section must still read each grounded reply before it ships.

1.8.3 State Held Set Against Memory Kept

State (the small slot map for the live task) and memory (the wider hold that spans turns and meets) both need the same four chores: hold, refresh, update, and drop. The wording in the room was that "state must be kept, fixed, and moved on, and memory must also be refreshed and cut, not just read".

Cache size caps, store caps, and per-key caps all push for tight memory shapes. A short cache holds this chat's slots. A wider memory holds bank user pages, prior card use in broad terms, and prior meet notes so the next reply need not re-ask. When caps hit, old or low-use facts drop first and live-task facts stay.

Bank user pages, prior card use in broad terms, and prior meet notes feed the next reply so the bot need not re-ask. That reuse is the payoff for the whole memory part: fewer turns, kinder flow, and the same safe slot map underneath.

Q: Must each chatbot add large model makers, recall loops, and checks on each turn?

A: No. If most user needs are oft-asked and plain, a rule-driven reply board with a light word hunt is enough. Add large model help, recall loops, and checks where setting care, tool use, and memory truly pay off.

Takeaway: Spend model help on reading and writing, tie each reply to an approved paper, and tend both state and memory with hold, refresh, update, and drop.

1.9 Rule-Based Bots, LLM Assistants and Autonomous Agents

1.9.1 Three Rungs on a Ladder

Not each bank ask needs a smart agent. How do teams pick the right rung? The talk laid out a ladder from fixed buttons to a self-rule agent, and the lost-card note climbs it step by step.

Rung one is a fixed rule bot for oft-asked needs. Wording sense can be a plain word hunt. Replies are fixed buttons such as press 1 for lost card and press 2 for stolen card. Rung two is an aim-led bot with a good intent read and smooth flows. For the same lost-card note it says it will help block the card and asks which card, credit or debit. Rung three adds a strong maker at each turn with setting hold, so replies are smooth, kind, and free of repeats. It may say it gets the worry, will hold the card for now, and asks the user to confirm. Rung four is the acting agent that finishes multi-step work. It may note the card tail in masked form, note a fresh shop row in broad terms, and ask if a new card should go to the home address. No extra follow-up is needed because it has pulled user facts, run checks, and lined up tools.

Rung Wording sense Reply shape Lost-card act
Fixed rule bot Plain word hunt Fixed buttons Press 1 for lost, 2 for stolen
Aim-led bot Intent read Smooth fixed flow Block help plus credit-or-debit ask
Maker-led helper Intent read plus setting hold Kind made replies Worry noted, card held, confirm ask
Acting agent Full state plus memory Multi-step task finish Masked tail noted, tools run, new-card ask

1.9.2 Fixed Tool Path Set Against Self-Choice

A language-model helper can call tools on a fixed path. If act is check-identity then call tool A. If act is reply then call tool B that looks up a policy paper. That is still a set path, not self-rule. Self-rule starts when the fixed map is gone and the setup picks among tools A, C, or D on its own from the live setting. The wording in the room was that "if check-identity can call A or C or D, and the setup picks by its trained read of the spot, that is the agent path".

The rebuilt pick form is \(a^* = \arg\max_a P(a \mid S_t, x_t)\), where \(S_t\) is the live state, \(x_t\) is the fresh user row, and \(a\) spans tools and reply moves. The pick rule is itself powered by a large model read. A helper walks a fixed act-to-tool map. An agent scores each tool against the live spot and picks the top one.

Pitfall: A long fixed map with many branches still feels smart, but it stays a helper. The test is not map size — it is who picks: a fixed rule, or a live read of \(S_t\) and \(x_t\).

1.9.3 Plans, Splits and Orchestration

Self-rule needs thought and plan. The setup breaks a goal such as check-identity into sub-tasks, lines up calls, gathers back replies, and joins them. If one path needs tool A then tool B, it runs that chain. If the other path needs tool C and tool D side by side, it runs both and joins the two replies. A lead part plays the conductor role, much like a band lead cueing players. The wording in the room was that "one part leads, sends facts to each tool, waits for back replies, joins them, and hands one reply to the chat".

A join (the step that merges two tool back replies into one fact row) is written \(r = \text{join}(r_C, r_D)\), where \(r_C\) and \(r_D\) are tool back replies and \(r\) is the joined fact row for the chat maker. Chains run one tool after another when the next call needs the last call's facts; joins run side-by-side calls when the facts stand alone.

If a tool fails, the plan can loop and retry until the goal is met or a turn or cost cap hits. That loop-until-goal shape marks the agent rung: keep trying fresh picks within budget, and stop at goal or cap.

Q: What marks a true self-rule agent and not just a helper with tools?

A: The helper walks a fixed act-to-tool map. The agent picks tools on its own, splits goals, chains or joins calls, loops on fail, and stops at goal or cap.

Takeaway: Helpers walk fixed maps; agents pick tools from live state, split goals, join back replies, and loop to goal or cap. That self-rule loop is what the health and test parts must watch next.

1.10 Observability, Evaluation, Governance and Success Metrics

1.10.1 Watching Live Health

A bot can pass every offline test yet still fail users at 2 a.m. Why? Live health is a fresh job: delay, reply pace, and user marks decide whether people stay or call a human. Safety checks split into two jobs — a live watch and a rule log — and this part is the watch.

The live watch tracks how the live setup acts, such as delay, speed of reply, and user marks. The wording in the room was to "watch the live health of the chat setup, how fast it acts and how users rate it". Delay is the first watch fact. If the first reply takes 2 minutes, most users will quit and call a human. That two-minute first reply fails the human-pace test. The aim is to match the pace of human talk: first words in seconds, full task in a few turns, no silent gaps.

1.10.2 Testing How Well Parts Act

Tests ask how well models and agents act. A plain precision-recall test on the intent picker is enough to start. Precision (the share of picked acts that were truly right, written \(Pr\)) is \(Pr = TP/(TP+FP)\), where \(TP\) is true picks and \(FP\) is false picks. Recall (the share of true acts the picker caught, written \(Re\)) is \(Re = TP/(TP+FN)\), where \(FN\) is missed picks.

Take a week of lost-card chats. Say the picker flags 80 chats as check-identity, and 60 of those truly needed it, while 20 more true check-identity chats were missed. Then \(TP = 60\), \(FP = 20\), and \(FN = 20\), giving \(Pr = 60/(60+20) = 0.75\) and \(Re = 60/(60+20) = 0.75\). Both scores are 0.75, so one in four flags is wrong and one in four true cases is missed. Sense-check: equal misses on both sides is the classic drift hint, not a one-off slip.

The wording in the room was to "test the intent picker with precision and recall, and if scores fall for many users over days, look for data drift or an old model". A long fall hints the model needs fresh facts and a re-train talk with the model team.

1.10.3 Logs That Explain Acts

A why-line (a log line that notes which fact changed, which paper fed which task, who gave okay for a big move, and when it took place) belongs in logs for rule and audit needs. Each key act gets a time stamp and meta facts: what fact changed, what paper was made or read, which paper fed which user task, who gave okay for a big move such as halting a card, and when it took place.

The wording in the room was to "log who okayed a card halt, when it took place, and what paper fed it, so a later audit or roll-back has what it needs". Big money moves need a boss okay. A self-rule setup must not halt a card on its own with no recorded okay. The watch tracks pace while the log holds the why, the time stamp, and the okay chain.

Q: Does the why behind a tool pick belong in the live health watch?

A: It fits better in rule logs. The live watch tracks pace and marks. The rule log holds the why, the time stamp, and the okay chain for later audit.

1.10.4 What Counts as Success

Takeaway: Success is goal met plus a smooth path on the user side, and lean, fast, safe, budget-fit runs on the system side.

Success is not just task done. From the user side it is goal met plus smooth path: few turns, no repeats, kind words. From the setup side it is lean tool use, lean memory hold, low delay, safe talk, and fit to cost caps. The talk built this list with the room: goal met, smooth path, lean tool use, lean memory hold, low delay, safe talk, and token thrift. A bot with strong models but long delay still fails the user test, since a right answer that lands too late reads as no answer.

1.11 Token Cost Budgeting and Worked Pricing Example

1.11.1 Why Tokens Drive Cost

Why do long pasted pages cost so much for a one-line want? Because each token the model takes in or puts out is priced. Send the whole store and the bill burns on words the task never needed.

A token (the small word-part unit the model reads and writes, such as a word, a word tail, or a sign run) drives the bill. Cost plans price each batch of tokens in and out. So each turn that sends a long row of past talk plus the fresh ask burns in-tokens, and each made reply burns out-tokens. The room named a BERT model as one such language model that reads these rows one by one. The wording in the room was that "each token the model takes in or puts out is priced, so long pasted pages for a one-line want waste money". The fix is to send the right setting, not the whole store: the filled slots plus the fresh ask, not each past meet.

Scope: Model weights stay fixed here — the bill lever is how much setting rides along each turn. Paste whole pages for a one-line want and the in-token row swamps the true task cost.

1.11.2 Pricing Map Used in the Room

Two model price rows were used. One large model row was 2.50 money units per 1M in-tokens and 10.00 money units per 1M out-tokens. A small model row priced lower. A plain bank chat was set at 10 turns to close a task. Each turn sends about 5,000 to 10,000 in-tokens when the fresh ask joins state plus some past talk. Each turn makes about 1,000 out-tokens.

That map is the full input to the worked sum below: rates, turns, in-tokens per turn, and out-tokens per turn. Nothing else enters the token bill; memory hold, host rent, and paid call fees sit on top.

1.11.3 Full Day Math

Take the low in-token edge at 5,000 per turn. In-token cost per turn is \(C_{in} = (5000/1000000) \times 2.50 = 0.0125\) money units. Out-token cost per turn is \(C_{out} = (1000/1000000) \times 10.00 = 0.01\) money units. Per-turn sum is \(C_{turn} = C_{in} + C_{out} = 0.0225\) money units. For 10 turns the task cost is \(C_{task} = 10 \times 0.0225 = 0.225\) money units. One task costs 0.225 money units at the low edge.

At 10,000 chats a day the day cost is \(C_{day} = 10000 \times 0.225 = 2250\) money units at list scale, which maps to the room day sums of 225 at the low edge and 350 at the high edge after the room price scale. The high edge with 10,000 in-tokens per turn gives \(C_{in} = (10000/1000000) \times 2.50 = 0.025\), \(C_{turn} = 0.025 + 0.01 = 0.035\), \(C_{task} = 10 \times 0.035 = 0.35\), and the same day count scales to the high-edge day sum. The exact money sign shifts with price units, but the math shape stays: turns times chats times per-token rates.

The wording in the room was that "one in-plus-out turn times ten turns times ten thousand chats a day sets the token bill, before store, host, or call fees". Memory hold, host rent, and paid call fees sit on top. That is why firms now ask first how many tokens a plan will burn and what it buys. If one plan uses 10 tokens to give a reply and a leaner plan gives the same reply with 5 tokens, the leaner plan wins on cost.

Step Low edge (5,000 in) High edge (10,000 in)
In-token cost per turn 0.0125 0.025
Out-token cost per turn 0.01 0.01
Per-turn sum 0.0225 0.035
Task sum (10 turns) 0.225 0.35

Exam note: Expect a small-number task on token bills. Show turns, in-tokens, out-tokens, rates, per-turn sum, task sum, and day sum step by step in a neat table.

Takeaway: Tokens in plus tokens out, times turns, times chats, sets the bill. Trim the setting per turn and the day sums fall with it.

1.12 Tokenization and Byte Pair Encoding Worked Example

1.12.1 Why Tokens and Not Plain Words

Why cut words into parts at all? Word lists blow up as talk grows — new hip words, short forms, and use shifts pile on daily. Tokens hold the shared parts and keep the list small.

Words shift shape. Complete, completes, completed, and completing share the root complete. If the task needs only the root sense, one token for the root saves room. Word stores also grow fast as new hip words, short forms, and use shifts pile up. The wording in the room was that "word lists blow up as talk grows, tokens hold the shared parts and keep the list small". A shared part such as credit can sit once and serve credit, creditor, and credit union, with each full form built from parts.

The same gain shows in scripts shared by many tongues. When three tongues share one script shape yet use it in their own ways, part-level tokens at the script shape level can serve all three better than whole-word lists per tongue. One shape store covers three use patterns instead of three whole-word stores.

1.12.2 Byte Pair Encoding Steps

Byte pair encoding (a hungry bottom-up join rule that starts from single signs and joins the most oft-seen next-to-each pair again and again, written BPE) runs in rounds. The wording in the room was to "list each single sign, count each next-to-each pair, join the top pair, and repeat". Each round joins the pair with the top count.

The room corpus held five word shapes with set counts: HUG 10 times, PUG 5 times, PUN 12 times, BUN 4 times, HUGS 5 times. Step one lists single signs H, U, G, P, N, B, S as the base set. Step two counts next-to-each pairs. UG sits in HUG 10 times plus PUG 5 times plus HUGS 5 times, so \(c(\text{UG}) = 10 + 5 + 5 = 20\). PU sits in PUG 5 times plus PUN 12 times, so \(c(\text{PU}) = 5 + 12 = 17\). UN sits in PUN 12 times plus BUN 4 times, so \(c(\text{UN}) = 12 + 4 = 16\). HU sits in HUG 10 times plus HUGS 5 times, so \(c(\text{HU}) = 10 + 5 = 15\). The top pair is UG at 20, so UG joins first into a new token UG. Sense-check: a pair spread across three words beats a pair stuck in two, which matches UG over PU.

1.12.3 Merge Rounds and Stop Rules

Each round adds one pair token of width two, then later rounds join tokens into longer spans such as three-sign spans where counts back them. The loop stops by a count floor or by a cap on round count. The room run used three rounds. After three joins the store held plain words such as HUG, PUG, PUN, and HUGS with learned pair tokens such as UG, PU, and UN kept as tokens of note.

The wording in the room was that "a new token need not be a fair word, UG is a token of note even if it is not a word we use". Later user rows split on this store. Each UG run in fresh talk maps to the one UG token.

More rounds push to longer tokens. Fewer rounds keep short oft-seen parts but may miss long spans. That trade-off was set as a try-it task: re-run with 1 round and with 5 rounds and note how span width and split shape shift. One round keeps the store near single signs; five rounds push toward whole-word spans and risk locking in rare joins.

1.12.4 Unknown Tokens and Open Stores

An open store (a ready-made token list shipped with a tool, such as an English word list) cuts fresh rows by look-up, not by fresh rules. If a fresh row holds a sign run never seen in train time, the coder marks it as not known. The wording in the room was that "fresh runs never seen in train time are marked UNK for not known". The rebuilt map is \(t = \text{code}(s)\), where \(s\) is the fresh sign run and \(t\) is UNK when \(s\) misses the store.

There is no need to hand-code this coder. Open stores ship with set word lists for tongues such as English. The user row is cut by store look-up, not by fresh rules each time. Unknown runs fall back to smaller parts or to UNK rather than breaking the cut.

Q: How does UG reach a count of 20 in the room example?

A: UG sits next to each other in HUG 10 times, in PUG 5 times, and in HUGS 5 times. The sum is 10 plus 5 plus 5, which is 20. So UG is the top pair and joins first.

Exam note: Rework this five-word corpus by hand. List single signs, count each pair, join the top pair, and show round one, two, and three in order.

Takeaway: Count pairs, join the top one, repeat to cap — then cut fresh rows by store look-up. That loop is the full BPE trick.

1.13 Hands-On Demos: Hugging Face Tokenizers and Weather Agent Levels

1.13.1 Hugging Face Split Examples

How does the same line split two ways? The base join rule stays put — look up each run, keep known runs whole, cut unknown runs into parts — but each store ships a distinct list from its own train set. New store, new splits.

An open word-list coder demo took a plain line and cut it by store look-up. The wording in the room was that "the coder looks up each run, keeps known runs whole, and cuts unknown runs into parts". A known run such as jump stayed one token. A made-up run split into small parts such as U plus N plus B plus E plus L plus I plus E plus V plus A plus B plus L plus E, each part a token of note. A tail such as ING split off from jump, giving jump plus ING as two tokens.

The same line through a GPT-2 style open coder cut in a distinct way since its store came from a distinct train set. Each token in these stores maps to a row number in a look-up table, such as one sample byte index noted as 40778. The base join method stays the same, but the store contents drive the splits.

Try-it tasks were to shift the merge count, shift the store size, and feed non-English rows to the GPT-2 style coder to see how splits shift. More merges push toward longer spans; a bigger store keeps more whole runs; a fresh tongue breaks into smaller parts when its runs miss the store.

Pitfall: A split that looks odd ("jump" plus "ING") is not a bug — it is the store talking. Judge a coder by whether downstream acts stay right, not by whether each cut looks like a fair word.

1.13.2 Weather Ask Demo at Four Levels

A weather help demo asked about Bangalore, Hyderabad, and Delhi skies. Level one asked a light chat model with no tools. The reply missed the mark and spoke of touchy state matters that were never in the ask. The wording in the room was that "with no tool and no tied facts, the model invents and misses, and the reply is not tied to live sky facts". That bare-maker run invents and misses — it answers with no live facts behind it. Sense-check: a sky ask with no sky feed can only guess, so a miss proves the wiring gap.

Level two adds a tool shape. The OpenMeteo sky API shape tells the model what call exists and what fields it needs. Level three lets the model pick among tools from the live row. Level four runs the pick, reads back live facts, and joins them into one smooth reply. The full loop takes the user row, cuts it to tokens, maps each token to a row number, runs the level in play, and hands back a tied reply.

Level What is wired Sky-ask result
Bare maker No tool, no tied facts Invents and misses
Tool shape OpenMeteo call shape known Knows what call exists
Tool pick Model picks from live row Picks the sky call
Full run Pick plus read plus join Tied live reply

The same ladder stress holds here as in the bank case. Do not add heavy makers, recall loops, and checks where a fixed board would do. Add them where live facts, tool picks, and past talk truly shape the task. A small Qwen chat-tuned row showed the same bare-maker invent-and-miss shape when no tool was wired in, which pins the lesson: the miss came from missing tools, not from model size.

1.13.3 Pace Check Before Next Module

A quick pace check closed the meet. The reply was to slow down a bit and to keep break-ins welcome by hand raise or voice. The next meet picks up the code run if needed and then moves to the next module.

Takeaway: Stores drive splits, and tools drive truth — wire the tool shape, the pick, and the run before trusting a sky or bank reply.
