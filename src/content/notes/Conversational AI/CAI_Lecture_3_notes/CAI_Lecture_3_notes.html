3.1 The Full System View

Hook: Two assistants can share the same language model and still behave like different species. One remembers your department, answers in seconds, and costs pennies. The other forgets your doctor, stalls for a minute, and burns budget. The difference is never the model alone. It is everything around the model.

A conversational system is much larger than the language model inside it. The model handles generation wherever generation is needed. Everything around it decides what the model gets to see, which work gets done, and what gets remembered. That surrounding system is the focus here.

Think of a car and its engine. The engine supplies raw power, but the driver never touches it directly. Gears, steering, brakes, mirrors, and the dashboard decide how that power reaches the road. A language model is the engine of a chatbot. Channels, managers, stores, tools, and logs are the rest of the car. This session studies the rest of the car. The mapping breaks where agency starts: unlike an engine, the model also makes language choices, so the system must also shape, check, and route what the model says.

Core idea: A conversational system is the whole product the user talks to, including channels, managers, stores, models, tools, and logs. A language model is one component inside it, called when text must be understood or generated. Wherever the word model appears in this session, it means a language model or large language model.

Earlier groundwork set up this view. First came the shift from simple rule-based setups to systems that reason through a request, with an example showing where answering without reasoning fails. Then came prompting techniques such as chain of thought and tree of thought, which turn a user request into a statement the system can process, including sharing the thought process itself. Then came structured output, especially JSON, which makes results easy to store, retrieve, and build state from, plus a first look at what happens when a system produces several candidate answers and must decode among them.

This session puts all of that together into one architectural picture. There are two broad halves. Part A is building the system: the components around the conversation that make it work, namely context, conversational state, memory, and orchestration flows. Each of these becomes a separate module later, so here each one gets its working definition and its place in the whole. Part B is choosing and running the model: a careful choice of language model plus the techniques around it decides whether a system performs well or falls short of a benchmark setup. Part B stays brief here. Each technique in it warrants a long separate discussion, so this session only sketches how each one helps or hurts a conversational use case, without going into full model-level optimization.

Half Question it answers What it covers Depth in this session
Part A: build the system What surrounds the model? Context, conversational state, memory, orchestration Full treatment, one module per piece
Part B: run the model Which model, run how? Model choice plus operating techniques Sketch only, full detail later

Pick the half that matches the symptom. Forgetting a doctor points at Part A, because some store or flow dropped the slot. A weak answer on a fair prompt points at Part B, because the model or its operating setup fell short. Cost and latency spikes can come from either half, which is why this session treats the three failure modes first: they teach which half to blame.

Recap: The model generates language; the system decides what the model sees, what work happens, and what persists. Bridge: Before naming any component, the next section earns the architecture the hard way, through three systems that fail without it.

Hospitals show why the split matters. A booking helper that forgets the doctor fails even with a strong model, because no store held the slot. Banks meet the same split with account types. Support desks meet it with reply-time targets. In each case the fix sits in Part A scaffolding, not in a larger model.

3.2 Three Failure Modes That Force Architecture

Hook: A hospital assistant asks for the doctor you just named. A booking reply takes a full minute. One chat turn costs triple its budget. None of these is a mystery about language. Each one is a missing piece of system design.

Forget, stall, and overspend. Those are the three failures. Each one maps to a part of the architecture that must exist. The rest of this session builds those parts.

3.2.1 A System That Forgets

Take a medical appointment booking helper run by a fictional hospital. A patient opens the chat and writes "book an appointment with Doctor X." Booking is a fixed task with subtasks, and the system knows in advance which slots it must collect: the doctor or department name, the date of the schedule, and the booking status. Internally it keeps something like a structured record so the machine can complete the work.

Now suppose the assistant replies by asking "do you have any preferred doctor." That question repeats information the patient already gave. The natural reaction is that something was lost. Either the system failed to collect the doctor name from the current message, or it collected a department such as dermatology a few turns back and then dropped it by the time the current turn arrived. The suggested cause is architectural: there is no managed, persisted state holding what must be filled, so historical detail with the needed information never gets documented properly. In a banking example the same failure looks like forgetting the account type. Here it looks like forgetting the preferred doctor even though it was provided.

Slots make forgetting visible. A booking task declares its record up front, for example intent book_appointment with slots for doctor, department, date, and status. Each turn fills what it can and leaves the rest marked as pending. When the doctor slot stays empty after the patient named Doctor X, the team sees a fill failure, not a language failure.

Worked example: the lost doctor. Turn 1: patient writes "book an appointment with Doctor X." Correct fill: doctor = Doctor X, department = pending, date = pending, status = collecting. Turn 2: assistant asks "do you have any preferred doctor." Diagnosis: the doctor slot still reads pending, so the fill from turn 1 never landed or never persisted. Fix: write the extracted value into managed state at the end of turn 1, then read it back before generating turn 2. Sense-check: a re-read of state before each reply would have shown doctor = Doctor X, so the repeat question could never fire. Result: the missing write is the bug.

Same shape, new field. A bank helper asks for the account type twice because the account-type slot never persisted. A travel helper asks for the city twice for the same reason. The symptom changes with the domain, but the cause stays the same: no store holds what must be filled.

Scope: Managed state helps fixed tasks with known slots. It does not help open chat with no task, where there is nothing to persist. Assumption: The slot list is set before the run. If the patient names a field the schema never declared, the system has nowhere to put it until the schema grows.

3.2.2 A System That Is Too Slow

Suppose the same patient writes "book an appointment for dermatology" and the assistant takes 60 seconds to respond, where a typical reply takes about 12 seconds. That delay is not desirable. One plausible cause is that every turn is pre-processed and then sent to a large language model, which must decode the request before the system can ask its clarifying question. Calling a large model on every turn can add latency depending on model performance.

The design answer is a service target with teeth. The spoken rule is "responses should take no more than 15 seconds," reconstructed as:

\[L \le 15\]

where \(L \in \mathbb{R}\) is the reply latency in seconds for one turn. If the threshold is crossed, the machine should time out rather than keep the user waiting, and reroute toward a different conversational path, for instance by asking the specific questions the assistant needs answered.

Latency is a budget, not a hope. \(L\) names the measured reply time for one turn in seconds. The number 15 names the service target in the same units. The inequality says every turn must land at or under target. A turn at 12 seconds passes. A turn at 60 seconds fails by 45 seconds, or four times the budget.

Worked example: 60 seconds against a 15-second target. Typical reply: \(L = 12\), and \(12 \le 15\) passes. Slow reply: \(L = 60\), and \(60 \le 15\) is false, so the turn breaches the target by \(60 - 15 = 45\) seconds. Action: stop waiting, time out the slow path, and send a narrow prompt such as "which department and date do you need." Result: the user gets a fast clarifying question instead of a stalled answer.

Pitfalls: A reply-time target only works with a timeout behind it. Without a cutoff, the target is a wish. Also, a big model on every turn is a choice, not a law. Fast paths such as slot checks and canned clarifications can skip the model entirely.

Real-world: support chatbots publish reply-time targets and fall back to narrow clarification prompts when the model path stalls.

3.2.3 A System That Costs Too Much

Suppose a single chat session is supposed to cost no more than $0.5 per user turn or per user conversation, in the spoken phrasing "no more than $0.5 per user's turn," reconstructed as:

\[C \le 0.5\]

where \(C \in \mathbb{R}\) is the cost in dollars for one turn or one conversation. Suppose the observed cost runs three times higher. The fault need not sit inside the language model. It can sit in how the system was designed.

Cost is a budget too. \(C\) names the measured spend in dollars for one turn or one conversation. The number 0.5 names the ceiling in the same units. Observed spend near \(C = 1.5\) breaks the ceiling by a factor of three: \(1.5 / 0.5 = 3\).

Worked example: triple spend from history fan-out. Budget: \(C \le 0.5\) dollars per turn. Observed: \(C = 1.5\) dollars, or three times the ceiling. Suspect: history handling that resends everything every time. If 10 prior turns ride along with message 11, and then all 12 ride along next turn, token spend grows with the pile, not with the new message. Cut the history to what the turn needs and re-measure. Result: the same model call costs less because the input is smaller.

The key suspect is history handling. Suppose 10 conversations preceded the current one. Should all 10 be collected, augmented onto the 11th message, and handed to the model, and then all 12 handed over at the next turn? A default design that keeps every turn and passes everything along every time will not work efficiently. The designer must plan which part of the history actually travels with each call. That planning question runs through the whole session.

Scope: The dollar ceiling covers inference input plus output for the turn under test. It does not cover training, storage, or staff time. Assumption: Per-token price stays fixed while history size varies, so input size drives the bill. If the vendor reprices, recheck the same inequality with the new rate.

Real-world: teams serving high-traffic assistants cap history per call because full-history fan-out is one of the fastest ways to triple an inference bill.

Recap: Forgetting means no managed state. Stalling means no latency target with a timeout. Overspending means no history plan. Exam note: Remember the 15-second latency target and the $0.5 cost ceiling as architecture triggers. Bridge: The next section names the three stores that stop the forgetting: context for the turn, conversational state for the task, and memory across sessions.

3.3 Context, Conversational State, and Memory

Hook: Why can an assistant greet you by name after a full logout, yet forget the doctor you named two minutes ago? Because name and doctor live in different stores with different lifetimes.

All three stores hold variable-value pairs or summaries of what happened before. They differ in how long each one lives.

3.3.1 Three Stores With Different Lifetimes

Context is what travels with a single turn. It is shared between turns and rebuilt at every turn, and it decides what actually reaches the language model on that call.

Conversational state is short-term state kept for the whole application run until the task finishes. If the user closes the chat by accident and reopens it while the same task is open, this store lets the run continue gracefully from where it stopped instead of starting over. Once the task completes and the session closes, these variables no longer need to persist in a long-term database.

Memory is long-term state across sessions, held in a back-end database. It keeps the small set of facts, observations, and preferences worth recalling later: what the user prefers, which language the user writes in, the tone that earned a thumbs-up, or a sentiment signal about how the assistant should respond. Even after a full logout and login, the preferred mode of communication, such as English, is still there.

One line per store: Context travels per turn and decides what the model reads now. Conversational state survives across turns within the task and carries the half-filled slots. Memory survives across sessions and carries the profile and preferences worth keeping.

A compact way to hold the boundary uses the context window \(W\), the maximum number of tokens the model accepts on one call. The spoken rule is "if the context window is exactly 3 tokens, then in this conversation only the first three tokens can be passed along, and the rest of the information is lost," reconstructed as:

\[|C| \le W, \quad W = 3\]

where \(C\) is the token sequence sent on the turn and \(W \in \mathbb{N}\) is the window size. The general point survives at realistic sizes: whatever is sent must fit the window, so the system must choose what travels and what gets condensed.

Worked example: a 3-token window. Suppose the turn needs four tokens: book, dermatology, Doctor, X. Here \(|C| = 4\) and \(W = 3\), so \(4 \le 3\) is false and one token must go. Keep book, Doctor, X and condense or drop dermatology, or replace a raw token with a shorter summary token. At a realistic size such as \(W = 10000\), the same test runs per call: count the tokens, and if \(|C| > W\), trim or condense until \(|C| \le W\). Result: the window decides what survives, so assembly is a selection task.

Think of a desk, a project folder, and a filing cabinet. Context is the desk: only what fits on top gets read right now. Conversational state is the project folder: everything for the open job, kept until the job closes. Memory is the filing cabinet: the few records worth keeping after the folder is thrown away. The mapping breaks on size: a real desk holds many pages, while a 3-token desk holds almost nothing, which is why the tiny number teaches the rule better than a realistic one.

Scope: The three-way split fits task-led helpers with repeat users. Assumption: Tasks end and sessions close, so short-term stores can be dropped. For a one-shot question with no task and no returning user, all three layers collapse into a single prompt.

3.3.2 Worked Examples

A patient closes the chat and reopens it later asking about a drug, in the spoken form "drug AAA is causing nausea, help." What persists between those two sessions is memory: cross-session preferences and profile-level facts. Contrast that with reopening the same booking task and writing "book that requested appointment." The task is unchanged across the two sessions, so the assistant should recall what was already collected and continue. That carry-over is conversational state, kept by the user-facing chat application for the session.

Worked example: AAA drug versus requested appointment. Case 1: the user returns and writes "drug AAA is causing nausea, help." The booking slots are gone, but memory still holds language = English and the standing caution around symptom advice. The assistant answers in English and routes toward practitioner-approved sources. Case 2: the user returns and writes "book that requested appointment." The booking task is still open, so conversational state still holds doctor = Doctor X and department = dermatology. The assistant resumes instead of restarting. Result: memory answers "who is this user" while state answers "where did this task stop."

The graceful version of that continuation fills rather than repeats. If dermatology and Doctor X were already collected and only the date is pending, the assistant should say something like "Yes, Doctor X is available," and then ask which date works, instead of asking for the department and doctor again.

Task completion moves slots to their terminal values. Suppose the patient writes "I want it today after 5 PM IST," the assistant checks Doctor X's schedule, and offers a 6 PM slot. The patient confirms. Then the date becomes 14th November and the status becomes completed or booked. At that point the short-term variables have done their job, which is why this store is called short-term state or short-term memory rather than a permanent record.

Worked example: slot values across three turns. Turn 1: doctor = Doctor X, department = dermatology, date = pending, status = collecting. Turn 2: patient adds "today after 5 PM IST" and the assistant offers 6 PM. Fill: date = 14th November (pending confirmation), status = confirming. Turn 3: patient confirms. Fill: date = 14th November, status = booked. Result: pending becomes confirmed and then booked, and the run can close.

A flight booking helper shows the context side. Its context holds the system instruction, meaning what may be shared with the model and what the model may return, plus constraints, plus the user message. Together the instruction and the message form the current direction for the response. As turns accumulate, earlier instructions and messages pile up, and the growing history must somehow be condensed into a meaningful summary rather than appended raw. There is a dedicated later treatment of how that condensing works.

3.3.3 Student Questions and Answers

Q: What is the difference between conversational state and memory, especially across sessions? A: Think of a class meeting. During the meeting, the open question under discussion stays live, and the discussion flows until the meeting ends. That is conversational state: short-term, gone once the meeting closes. If the same group meets again next week, the earlier question may be forgotten, but something about a participant can persist, for instance that someone asks attentive and meaningful questions. That persistent profile is memory: long-term traits and preferences that build up across meetings.

Q: If the user profile lives in long-term storage, does it also enter conversational state? A: Yes, a copy of it does. Generating the state for each turn needs the recent history plus the task plus the system details plus the profile. The stored profile is loaded and used on every turn so the system knows what to say next. The profile itself stays in the database as long-term storage. The rest of the conversational state typically lives only within the session, and in most applications the session copy is deleted afterward. So all four pieces meet during context building, but only the profile is guaranteed a permanent home.

The second answer is worth restating in one line: storage is long-term, but use is per-turn. The database keeps the profile; each turn borrows a copy of it.

3.3.4 Industry Applications

Hospital assistants keep department, doctor, date, and booking status as explicit slots so a dropped entity shows up as an empty field rather than a mystery. Travel helpers attach system instructions that state what the model may share and what it must withhold before any user message is processed. Support desks keep language and tone in memory so a returning user is greeted in the same mode without being asked again.

3.3.5 Exam Notes

Exam note: Be ready to separate the three stores by lifetime: context travels per turn, conversational state survives across turns within the task, memory survives across sessions. The AAA drug versus requested-appointment pair is a compact way to remember which is which. Bridge: The next section runs one full turn so the three stores can be seen moving together.

3.4 How the System Runs End to End

Hook: Follow one message from arrival to answer and the whole architecture stops being abstract. Every store and every check has a moment when it acts.

The moving parts work in one repeating loop. This section traces that loop as a procedure: what goes in, what each step does, and what comes out.

Purpose: Turn one user message into the right reply or action without losing state, breaking policy, or losing track of cost and latency. The loop exists because a language model on its own is memoryless and stateless: input goes in, output comes out, and nothing about variable-value pairs or slots is retained. Because of that, the surrounding system must persist everything worth keeping.

Inputs and outputs: Each turn takes in the user message, the stored history, the open task with its slots, the user profile, system instructions and constraints, and a session ID. Each turn puts out a reply or a next action, updated slots and history, profile or memory updates where due, and a log entry with latency, tokens, and cost.

Steps: The loop runs in five beats. First, the message arrives at the conversation manager, also called the dialogue manager, which owns states, memory, and context. It decides what persists in long-term memory, what sits in a fast cache, and what fills the slot pairs. Second, the manager loads what matters: prior history, the recognized task, the user profile, and prior constraints, then opens a trace under the session ID. Third, it builds the context: the standard system instruction, meaning what to do and what not to do, joins the current user message and the stored history to form a prompt. Prompt engineering is one part of this step, but context building is wider: memory, state, and constraints all enter the same package before anything reaches the model. Fourth, the language model processes the input and responds. That response can go straight back to the user, select an external tool or entity, or branch the work. In the medical illustration, one reply can trigger retrieval of policy documents, prior prescriptions, and visit history, orchestrating two or three tasks from a single turn. A reply can be a generation task or a classification of the next flow, meaning which path the conversation takes. Fifth, the system writes back: slots fill, history appends, memory updates where due, and the run is logged.

State lives outside the model by necessity. That is why memory, context handling, a dialogue or conversation manager, communication channels, and governance all belong to the architecture rather than to the model alone.

3.4.1 The Loop

The loop above is the whole section in miniature. Messages arrive at the conversation manager. The manager pulls out only the relevant stored material and augments the current message with it. Context gets built from instruction, message, and history. The model responds. The system writes back and logs.

3.4.2 Worked Example

Trace: makeup scheduling from arrival to log. Start: the student writes "help me with makeup scheduling." Load: the machine loads the history, recognizes the task as collecting examination details, and loads the profile, which records that responses should be in English. Build: it forms the prompt from the system prompt, the last several turns as set by the designer, and the current task in JSON form: examination slot, preferred day and time, and the justification for the makeup request. Model: the model asks the clarifying questions in human sentences and fills slots as answers arrive. Write back: once everything is in, the system updates the back end, for instance by submitting the case to the operations team under a support ticket such as ABC, or by writing the final examination slots to the student record. Log: finally it logs the run. The log is not only the completion status. It also records latency, token consumption, and cost economics where the designer instrumented them. Result: one message in, one answered task plus one audit trail out.

Trace: the same beats in the hospital case. First the message arrives. Then the machine loads the prior history, the recognized task, and the user profile, and opens a trace under the session ID. Then it builds a prompt with a role line such as "you are a patient support system," plus constraints such as never storing phone numbers or email addresses, plus the profile, recent history, and current booking task, all fitted into the model's window, for instance 10,000 tokens. Then the model generates the reply or the next action with tools. Then the system updates memory and history: a 6 PM IST confirmation becomes completed, slots fill, history appends, and the next step, such as closure and feedback, gets planned. Every increment leaves log traces under session identifiers such as 101 and 103, with the task tagged as appointment booking and user and doctor identifiers anonymized. Result: the same five beats, with the hospital slots and policy constraints swapped in.

Complexity stays linear in the work per turn: one load, one build, one model call, one write-back, one log entry. Cost grows with the size of the built context and the size of the model output, which is why later sections cap history instead of passing everything.

Pitfalls: Skipping the write-back is the classic bug: the reply looks right but the next turn starts from stale slots. Logging without anonymization is the classic policy bug: personal details leak into traces. A second trap is stuffing retrieval results into context without checking them, so one turn triggers policy documents, prescriptions, and visit history that the reply never needed.

When to use this loop, and the alternative: Use it for every task-led turn where state must survive. The alternative is a bare model call with no manager, no stores, and no logs. That fits one-shot questions with no follow-up, and it fails the moment a second turn refers back to the first.

Recap: Arrive, load, build, model, write back, log. The model is stateless, so the loop carries the state. Bridge: History is the heaviest item the loop loads, so the next section asks which part of it deserves to travel.

Hospitals run this loop on every booking turn. Universities run it on makeup requests. Support desks run it on every ticket reply. The domain changes the slots and constraints, but the five beats stay the same.

3.5 Dialogue History and Three Ways to Trim It

Hook: A patient cancels a visit, books a new one, and the assistant still talks about the cancelled visit. The history was complete. That was the problem.

History is useful until it is heavy, costly, or stale. This section names the three failure shapes, then gives three trims with a worked comparison.

3.5.1 Why Full History Fails

Appending every prior turn in raw textual form breaks for three distinct reasons. First there is the model limit. If the window holds 10,000 tokens and five conversations already push the prompt toward 50,000 tokens, the excess cannot be processed in one call. Second there is cost. Even when the call technically fits, token-level cost makes full-history passing expensive, so the designer must economize. Third there is relevance. Suppose the first five turns booked a gynecology visit, the patient cancelled it, and now asks for Doctor X in a different department. The task has turned 180 degrees. Passing the cancelled booking as if it were still live is not a capacity problem but an application behavior problem: stale turns can actively mislead the current decision.

Three limits, three different fixes: The window limit needs fewer tokens per call. The cost limit needs cheaper history per call. The relevance limit needs different history per call, because stale turns mislead even when they fit and even when they are cheap.

One remedy is to train the summarizer well enough to rewrite and overwrite: keep the current state and let it replace what no longer applies. But the deeper question stays architectural: which part of the history should the machine keep, and which part should it delete or compress.

Token growth makes the pressure visible. The spoken contrast is "as the turns of conversation increase, full history keeps adding tokens, while last-K turns or a rolling summary stays controlled," reconstructed as:

\[T(n) \approx n \cdot \bar{t}\]

where \(n \in \mathbb{N}\) is the number of turns kept, \(\bar{t} \in \mathbb{R}\) is the average tokens per turn, and \(T(n)\) is the prompt size in tokens. Full history grows with \(n\). A bounded window or a rolling summary keeps \(T(n)\) near a ceiling, empirically on the order of 1000 tokens in the sample comparison, while the full-history curve climbs steeply.

Worked example: token growth with real numbers. Take \(\bar{t} = 200\) tokens per turn. Full history at \(n = 5\) gives \(T(5) \approx 5 \times 200 = 1000\) tokens. At \(n = 50\) it gives \(T(50) \approx 50 \times 200 = 10000\) tokens, which fills the whole window before instructions or slots are added. A last-2 window caps at \(T \approx 2 \times 200 = 400\) tokens no matter how large \(n\) grows. A rolling summary caps near its summary length, on the order of 1000 tokens in the sample comparison. Result: full history grows with the past while bounded history stays near its cap.

Scope: The growth formula assumes turns of roughly equal size, so \(\bar{t}\) is a fair average. Assumption: Prompt size is dominated by history tokens. If instructions or retrieved documents dominate, trimming history alone will not bend the curve.

3.5.2 Three Trimming Strategies

The simplest control is a sliding window: keep only the previous \(N\) turns, such as the last two or three, and ignore everything older. This bounds the dialogue history length, controls the tokens sent, and respects the context window with minimal loss in the recent region. Its weakness is amnesia about older but still important facts. If three turns of emotional messages push out the department and doctor the patient named earlier, the booking loses what it needs.

The second control is summarization. At every turn the history passes through logic that compresses it into a meaningful short form rather than appending it. A hundred pages become a few sentences, trained to retain what matters. This handles the lost-department case far better than a raw window. The trade is cost: summarization itself often calls a generative system, so it is heavier than slicing the last \(N\) turns. Simplicity and compute economy point one way, accuracy the other, with cost covering both compute and memory.

The third control is retrieval. Instead of asking a generative model to compress everything, keep past turn embeddings and fetch only the relevant ones. Here each prior turn is embedded, the current query is embedded, and similarity decides what returns, much like retrieval-augmented generation where the documents are simply the earlier turns. Either the top \(K\) turns go straight into the recent-history slot, or they go through a summarization step first. For the headache question that follows a booking and a cancellation, the system retrieves the symptom turns and leaves the booking and cancellation turns out.

Strategy What travels Strength Weakness
Sliding window, last \(N\) The \(N\) most recent turns Simple, cheap, bounded Drops older but key facts
Summarization One evolving summary Keeps meaning, drops cancelled turns Costs a model call per update
Retrieval, top \(K\) The \(K\) most similar turns Fetches by need, skips stale turns Needs embeddings and a cutoff

So when should the builder pick which. When recent turns carry the task and older turns rarely matter, pick the window. When the task spans many turns and older facts stay live, pick summarization. When one turn refers back to a distant turn while the middle turns are noise, pick retrieval. That one-line rule is the whole selection guide.

Relevance uses cosine similarity between the current message and each prior turn. The spoken procedure is "convert the query into an embedding vector, do the same for each turn, and compare," reconstructed as:

\[\text{sim}(q, t_i) = \frac{q \cdot t_i}{\|q\| \, \|t_i\|}\]

where \(q \in \mathbb{R}^d\) is the current message embedding, \(t_i \in \mathbb{R}^d\) is the embedding of turn \(i\), and \(d \in \mathbb{N}\) is the embedding dimension. Turns are ranked by this score and only the relevant ones reach the context builder. Vectors labeled \(V_1, V_2, V_3\) in the discussion are instances of these turn and query embeddings.

Cosine similarity in words: Each piece of text becomes an arrow in \(d\)-dimensional space. The dot product \(q \cdot t_i\) grows when the arrows point the same way. Dividing by the two lengths \(\|q\|\) and \(\|t_i\|\) removes the effect of length, so a long turn does not win just for being long. The score is 1 for identical direction, 0 for unrelated direction, and negative for opposite direction. Rank all turns, keep the top \(K\), and drop the rest.

Worked example: similarity with tiny numbers. Work in \(d = 2\). Let the query be \(q = [1, 0]\). Let turn 1 be \(t_1 = [1, 0]\) (same direction), turn 2 be \(t_2 = [0, 1]\) (unrelated), and turn 3 be \(t_3 = [0.9, 0.1]\) (nearly same). Lengths: \(\|q\| = 1\), \(\|t_1\| = 1\), \(\|t_2\| = 1\), \(\|t_3\| = \sqrt{0.81 + 0.01} \approx 0.906\). Scores: \(\text{sim}(q, t_1) = 1/1 = 1.0\). \(\text{sim}(q, t_2) = 0/1 = 0.0\). \(\text{sim}(q, t_3) = 0.9/(1 \times 0.906) \approx 0.993\). With top \(K = 2\), turns 1 and 3 travel and turn 2 drops. Result: ranking by angle keeps the turns that point at the query.

Every turn is also stored as a message list the machine can scan: a role saying whether the line came from the system, the user, or the assistant, plus the content carrying the textual message. That role separation is what lets later logic tell who said what. More elaborate variants, including meaningful summaries held in a data store or vector database, arrive in a later module.

Pitfalls: A window of two forgets the department named four turns back. A summary can bake in a cancelled booking if it rewrites instead of overwriting. Retrieval with a bad cutoff either starves the model at \(K = 1\) or floods it at \(K = 50\). Always pair retrieval with a tested \(K\) and a slot check after the fill.

3.5.3 Worked Example

Worked example: cancelled gynecology booking, fresh dermatology request. Full history hands the model the booking, the cancellation, and the new request together, so the model must reason past the stale booking. A two-turn window keeps only the cancellation and the new request, which is cheaper but may drop the department if it was named earlier. Summarization keeps one evolving note: prior booking cancelled, current intent is a dermatology appointment with Doctor X. Retrieval scores each prior turn against the current message, keeps the dermatology and Doctor X turns, and leaves the cancelled gynecology turns out of the history slot. Result: summarization and retrieval both beat raw history, and retrieval wins when the middle turns are noise.

3.5.4 Student Questions and Answers

Q: How do sliding window, context window, and conversational state relate? If the window only keeps two turns, is everything older lost, and does the user logging back in lose everything too? A: They are different cuts. The context window dictates everything the machine assembles into a prompt and sends to the model on one call, not just history. Recent history is one part inside that package. The sliding window constrains only that part: with a window of two, the builder sees the previous two turns as its history, and with six it sees six. That recent history need not be raw turns either. It can be pre-processed, for instance by sending turns to a model for summarization and passing the summary forward. Conversational state is the wider short-term store around it, so the two window sizes are not the same thing.

Q: For retrieval, how does the system fetch only the relevant turns? Is it like tool routing where a description picks the tool? A: It is an information retrieval step over the turns. Think of retrieval-augmented generation with static documents replaced by turns. A document here means one turn, namely the consolidated user and assistant messages from that turn. The current user message is the query. Both the query and each turn become embedding vectors. Then the query vector is compared against each turn vector for similarity. If the current message resembles only the first turn and nothing about the recent turns, the builder receives just that first turn as its recent history instead of the whole dialogue. That selective fetch is the retrieval task.

The routing comparison inside the second question is close but not exact. Tool routing picks a destination by description. Turn retrieval ranks evidence by similarity. Both select, but one selects an action and the other selects memory.

3.5.5 Exam Notes

Exam note: The three-way contrast is load-bearing. Sliding window is simple and cheap but can drop older keys. Summarization preserves meaning but costs a model call. Retrieval fetches by similarity and pairs naturally with a top-\(K\) cutoff or a later summarizer. Bridge: History trims decide what the model reads; the next section decides what the system writes, through state tracking, slots, profiles, and logs.

3.6 State Tracking, Task State, User Profile, and Runtime Metadata

Hook: "Book that requested appointment." "That doctor is fine." "Cancel my previous preference." Every one of those sentences points backward. Something must resolve the pointer.

This is the largest store section: what the system writes, where it keeps it, who it belongs to, and what the machine records about itself.

3.6.1 Dialogue State Tracking and Coreference

For each task the system predefines the structured record it must fill, usually written as intent plus slots:

\[\text{state} = (\text{intent}, \{s_1, s_2, \dots, s_k\})\]

where the intent names the task, such as appointment booking or makeup examination registration, and each \(s_j\) is a named slot such as doctor, department, date, course, examination type, or reason. The spoken definition is "intent plus slot," with entities mapped onto the correct slots. Dialogue state tracking is the process that maintains this record across turns. At the end of the turn that names Doctor X, only the doctor slot is filled and the rest stay pending. At the end of the dermatology turn, the department slot fills too.

Worked example: slot fill across two turns. Declare intent book_appointment with slots doctor, department, date, status. Turn 1: "book an appointment with Doctor X" gives doctor = Doctor X, department = pending, date = pending, status = collecting. Turn 2: "dermatology, today after 5 PM IST" gives department = dermatology, date = 14th November (pending confirmation), status = confirming. Nothing else changes. Result: each turn writes only what it heard, and pending marks the remaining work.

Ambiguous references resolve against this record. When the user reopens and writes "book that requested appointment," the machine must recognize the earlier state, treat the phrase as pointing at the half-filled booking, and restore its pre-filled slots. When the user writes "that doctor is fine" or "cancel my previous preference, previously 5 PM onwards," the machine must bind those phrases to the right slots. That binding is coreference resolution, and it runs on every turn as part of tracking. The dialogue manager owns the whole job.

Coreference in one paragraph: A pronoun or pointer such as "that," "it," or "my previous preference" is an anaphor that needs an antecedent, meaning the earlier mention it refers to. Resolution picks the slot whose value matches in person, number, and sense: "that doctor" binds to the doctor slot, "5 PM onwards" binds to the date slot, and "that requested appointment" binds to the whole half-filled record. Agreement plus recency decides; the closest matching slot usually wins.

Worked example: three pointers, three bindings. State holds doctor = Doctor X, department = dermatology, date = 14th November (pending). Message 1: "book that requested appointment" binds to the full record, so the run resumes with all three slots intact. Message 2: "that doctor is fine" binds "that doctor" to the doctor slot, confirming Doctor X. Message 3: "cancel my previous preference, previously 5 PM onwards" binds the time phrase to the date slot, reopening date to pending. Result: no value is re-asked; each pointer updates exactly one slot.

Scope: Slot-plus-coreference tracking fits tasks with a known schema. Assumption: The schema lists every slot the task can need. A pointer to a field outside the schema has nowhere to land until the schema is extended.

3.6.2 Task State in Practice

Appointment booking decomposes into sub-steps, each with its own checks. Typical steps are validating the request, meaning the user, the doctor's existence, and the department's existence; checking the doctor's schedule and availability; confirming with both the administrator and the patient; and triggering follow-through such as emails or record updates. Intermediary steps can call several interfaces: one to check availability, another to confirm it, another to close and write the database. Missing slots get filled through clarifying questions, and a final confirmation decides whether the task set closes.

Worked example: booking pipeline with four gates. Gate 1, validate: user exists, Doctor X exists, dermatology exists. Gate 2, availability: Doctor X has 6 PM IST on 14th November. Gate 3, confirm: administrator holds the slot, patient accepts it. Gate 4, follow-through: email sent, record written, status set to booked. If gate 2 fails, the loop returns "no 6 PM slot" plus the next free time instead of advancing. Result: no step runs before its inputs are confirmed.

The makeup examination record has the same shape with different slots: course, examination type, and reason for the request, plus a confirmation step recording whether confirmation is still pending. Some tasks also carry an expiry. If the user abandons the makeup request because the problem got resolved elsewhere, there is no reason to hold the state forever, so the design drops it after a business-chosen duration.

Where each piece lives follows its lifetime. Task variables for the open booking sit in a fast cache until the session completes. Dialogue history lives until the session closes. Because an accidental closure from a system failure would wipe cached data, important tasks keep a copy in both cache and database, flushing to the database at intervals chosen by task importance.

Store Home Lifetime Example
Open task slots Fast cache Until the task closes doctor = Doctor X, status = confirming
Dialogue history Session store Until the session closes Six messages across three turns
Durable copy Database Across failures and sessions Booking record flushed every turn for critical tasks

3.6.3 User Profile and Privacy

A user profile carries who the user is for personalization purposes: the user identifier, category, authorizations over visible data, preferred language, and privacy choices. Some profile content is local to the session. If the conversation shows the user is suffering, the assistant should answer with empathy, but that momentary need does not belong in the permanent profile. Account-level facts do persist in the database as long-term memory, and each turn loads a copy of them alongside recent history, task, system details, and profile data so the next utterance stays personal.

Consent comes first. The pattern resembles a cookie banner asking whether to accept all, reject all, or accept only necessary items. The assistant asks what may be stored and whether data may be cached, and records answers such as cookie use or analytics use as preference fields. It keeps only the fields the conversation actually needs. If the user asks to delete the profile or specific items, the system removes them from the live history and from the persistent database. If analytics or cookie use is declined, personal details must never enter logs or traces.

Pitfalls: Writing a session mood into the permanent profile is a privacy bug: empathy now is not a trait forever. Keeping declined fields "just in case" is a consent bug. Logging phone numbers or emails for debugging is a trace bug. The rule is simple: store only what was allowed, keep only what the task needs, and delete on request from both live and durable copies.

3.6.4 Runtime Metadata

Runtime metadata is the machine's own audit trail: session identifiers, latencies, token counts, model versions, and prompt versions. A minimal entry logs the session ID with its latency. A fuller entry adds which language model served the turn, including its unique identifier or version after a rollout, plus session details, the prompt version, the number of input tokens, the number of output tokens, and latency statistics such as the maximum or the average across the conversation, depending on the design. Suppose a response was slow and the user complains that "last time the response was delayed." The team needs to know which response that means, whether the hospital system or the chatbot caused it, which component was involved, for instance a small availability-checking module, and how many tokens were processed. Session-tagged entries such as session 101 make that lookup possible. Some designs also track cost economics per turn in the same trail. No personal data enters these logs.

Worked example: reading a slow-turn complaint. Complaint: "last time the response was delayed." Lookup: session 101 shows input 8200 tokens, output 140 tokens, model version B, latency 60 seconds, availability-check module blamed. Compare: session 103 shows input 900 tokens, output 120 tokens, same model, latency 12 seconds. Diagnosis: the slow turn carried a large history and hit the slow submodule, so the fix is a history cap plus a timeout on that module. Result: the metadata names the turn, the cause, and the fix.

A three-turn makeup exchange shows the complete state in miniature. Three turns produce six messages, with user and assistant alternating, and the dialogue history holds all six. The task status holds the filled intent slots. The profile holds the user category and preferred communication mode. The metadata records the model used, the input and output token counts, the elapsed time, and the guarantee that no personal data was logged.

3.6.5 Student Questions and Answers

Q: The user profile sounds like long-term memory, yet it also appears inside conversational state. How can it be both? A: The profile is long-term memory in storage, and a copy of it participates in every turn of short-term reasoning. The builder needs the profile together with the recent history, the task, and the system details to produce the next conversational state. So the profile is read from the database each time and used immediately, while the bulk of the conversational state is session-local and typically deleted afterward.

Recap: Tracking maintains intent plus slots, coreference binds backward pointers, task state lives in cache with a durable copy, the profile persists by consent, and metadata audits everything without personal data. Bridge: With writes understood, the next section prices the reads: what enters the context and what each part costs.

3.7 Context Assembly and Token Budget

Hook: Every token sent to the model costs money and adds latency. So who decides which tokens deserve to go?

Context assembly builds the single package the model will read. Prompt engineering alone is not the whole step. The assembled context has six parts. System prompts and policies come first: the role instruction for how the model should behave, plus constraints such as not disclosing financial details, never promising that a makeup is guaranteed, and never resolving medical symptoms directly unless a practitioner approves. Task state and summary come next, with the current slot values and a digest of the dialogue so far. The current message follows as the user message. Retrieved knowledge follows that: the persistent user profile plus task documents such as medical policy files, prior prescriptions, and prior history. Recent turns get emphasis for personalization, either raw or condensed. Finally comes the reserved output portion: the response template, for instance a fixed acknowledgment that inputs are valid, that checking is in progress, and that the user should confirm a stated choice among categories.

3.7.1 What Enters the Context

Think of packing a small suitcase for one trip. The six parts are six kinds of items, and the budget is the weight limit. System instructions are the passport: mandatory and small. Task state is the ticket: mandatory. Retrieved knowledge is the guidebook: fetch only the pages for this city. Recent turns are clothes: take what fits, roll the rest into a summary. Reserved output is empty space left for souvenirs, meaning room the model needs to write its answer.

The budget view keeps this honest. The spoken warning is "every token that you send to the model costs money and adds latency," reconstructed as a token budget:

\[T_{total} = T_{sys} + T_{task} + T_{know} + T_{recent} + T_{out} \le B\]

where each \(T\) term counts tokens for one part, namely system instructions, task state, retrieved knowledge, recent turns, and reserved output, and \(B \in \mathbb{N}\) is the per-call token budget. In the sample split, system prompts stay small by careful curation while retrieved knowledge and recent turns dominate, with recent turns alone taking about thirty percent. Mandatory, trimmable, verbatim, and fetch-on-demand parts must be separated deliberately, and the full answers arrive across the later modules rather than in one sitting.

Reading the budget: \(T_{total}\) is the full input plus reserved output for one call. Each \(T\) term counts one part in tokens. \(B\) is the ceiling in the same units. The inequality says the packed suitcase must fit the weight limit, so when one part grows, another part must shrink.

Worked example: a 10,000-token budget split six ways. Take \(B = 10000\). Assign \(T_{sys} = 400\) for instructions, \(T_{task} = 600\) for slots plus summary, \(T_{know} = 3000\) for profile plus policy files, \(T_{recent} = 3000\) for recent turns at thirty percent, and \(T_{out} = 1000\) reserved for the reply. Sum: \(400 + 600 + 3000 + 3000 + 1000 = 8000\), and \(8000 \le 10000\) passes with 2000 tokens of headroom. Now double retrieved knowledge to 6000 without trimming: the sum becomes 11000, and \(11000 \le 10000\) is false. Fix: condense recent turns to 1500 or fetch fewer documents, then recheck. Result: the budget names exactly which part must shrink.

Scope: The six-part split fits task-led turns with retrieval and history. Assumption: Token counts add linearly and the price per token is fixed, so the sum predicts both fit and spend. If the vendor prices input and output differently, track the two sums separately.

3.7.2 Context Trimming Strategies Revisited

A raw conversation buffer sends all past chat plus the new prompt, which is highly inefficient. A windowed buffer keeps the previous \(K\) turns, with \(K = 2\) in the illustrated case. Summarization sends the dialogues to a generative helper, keeps the summary, and augments the new message with it. An empirical comparison plots the three: full history climbs steeply in tokens as turns grow, shown as the rising red curve, while last-\(K\) turns and rolling summary stay controlled, both well within 1000 tokens. The trade is the familiar one between compute, where cost covers compute plus memory, and accuracy. The designer chooses what the application can afford.

Buffer Tokens at 20 turns of 200 each Behavior
Raw, full history About 4000 and still climbing Fails the budget first
Windowed, \(K = 2\) About 400, flat Cheap, may drop key facts
Rolling summary Near summary length, flat Keeps meaning, costs a helper call

Worked example: which trim survives the budget. Budget \(B = 10000\) with fixed parts \(T_{sys} + T_{task} + T_{out} = 2000\). Room left for history plus knowledge: 8000 tokens. At 20 past turns of 200 tokens, raw history needs 4000 and leaves 4000 for knowledge. At 60 past turns it needs 12000 and already breaks the budget alone. The \(K = 2\) window needs 400 at any length. The rolling summary needs its summary length, well within 1000 in the sample comparison. Result: only the bounded trims survive long conversations.

Pitfalls: Reserving too little output space truncates the reply mid-template. Marking everything mandatory breaks the budget by construction. Fetching policy files, prescriptions, and visit history on a turn that needs none of them wastes the largest budget share. Mandatory, trimmable, verbatim, and fetch-on-demand labels must be set before the turn, not during it.

3.7.3 Student Questions and Answers

Q: Every greeting seems to reach the model and come back from it. If the model generates everything anyway, why pass history back through calls? Would it not be cheaper for the model to keep the history itself, perhaps with memory on the same server? A: A language model is only weights plus an input-output pass. The stored object is a large set of parameters learned from training data, and inference runs the curated weights over the input and produces the output. In, out, and nothing retained. Inputs and outputs are not stored by the model. Whether the model and the state share one server or two is a separate deployment question. Either way the state must live outside the weights, which is why language models are called stateless while the agent or system around them carries the state.

The server-sharing idea inside the question is a deployment detail, not a memory design. Same machine or two machines, the weights still keep nothing between calls. The manager carries the state in both layouts.

3.8 Layers, Observability, and Guardrails

Hook: A send button is the visible one percent of a chatbot. What stands between the tap and the answer?

Follow one message down the stack and back up. That walk is the whole section.

Purpose: Move a message from the user's screen to the right answer while enforcing identity, policy, and audit at every step. Layers separate duties so each failure has an owner: the channel owns input, the gateway owns identity and rate, the manager owns state, the orchestrator owns routing, the model owns language, tools own facts, and logs own proof.

Inputs and outputs: In comes a raw message plus credentials on a channel. Out goes a policy-checked reply or action, with state written back and a trace left behind. Between them, every layer either passes, enriches, blocks, or reroutes the request.

Steps: A conversation passes through stacked layers. The channel is the front end the user touches: a mobile app, the web, or any other surface. An API gateway authenticates each request, applies rate and token limits, and issues the session ID for the conversation. The conversation manager, also called the dialogue manager, loads and stores state at every turn, assembles data, and builds the context. The orchestrator, the piece of logic after assembly, decides the path: follow a fixed workflow, route to another agent or workflow, or keep asking clarifying questions. When model help is needed, the workflow consults the language model, which processes the inputs and returns filled structured output. The orchestrator then decides whether to answer, recall, or call something else, including external tools and retrieval stores, which themselves form a dedicated module.

Memory stores sit beneath the flow. Short-term content typically uses a cache and long-term content uses a database. The database choice is a design decision: a vector database for embedding-style recall, or a relational database fed by logic that converts structured output into the relational shape.

Security, observability, and guardrails cut across every layer. Latency and performance metrics, critical task state, and session details with personal data removed flow into logs and trace documents. Observability then supports tracing, auditing, and evaluation: which component caused a lag, whether an approved tool set was actually the set the model called, and whether the run stayed within policy. Governance for the organization rests on the same trail. Guardrails can sit anywhere they are needed: at the channel that accepts user text, or between assembly and the model, where personally identifying material gets removed or anonymized before anything reaches a third-party resource.

Trace: one booking message through the stack. Arrival: the mobile app sends "dermatology, today after 5 PM IST" with credentials. Gateway: identity checks out, rate passes, session 101 opens. Manager: loads doctor = Doctor X, adds the new date phrase, builds the context. Orchestrator: picks the booking workflow, not a branch route or an open loop. Model plus tools: availability check returns 6 PM IST. Guardrail: phone numbers stripped before any third-party call. Reply plus log: "Doctor X has 6 PM IST, shall I hold it" goes back, and the trace records input tokens, output tokens, latency, and the anonymized slot change. Result: five layers touched, one trace left, no personal data stored.

Read the same walk sideways when debugging. Receive and authenticate the message, with a guardrail stripping what should not travel. Load and augment data, plan the context, and let the planner or router choose between tools and a model consultation. Call the needed models. Hand the result back to the orchestrator for action, recall, or further calls. Check every reply against policy before it reaches the user. Log at each step.

Pitfalls: A guardrail only at the front misses what the model adds at the back, so check replies too. Logs with personal data turn an audit trail into a leak, so strip before writing. A vector store where a relational table fits adds recall machinery the task never needed.

When to use this stack, and the alternative: Use the full stack for products with users, policy, and audits. The alternative is a demo with a channel wired straight to a model. That answers questions fast and teaches nothing about identity, cost, or safety, so it cannot ship to patients or account holders.

Recap: Channel, gateway, manager, orchestrator, model, tools, stores, with guardrails and logs across all of them. Bridge: Layers name the path; the next section names the three shapes the path can take.

Banks run the same stack with account rules at the gateway. Hospitals run it with symptom-advice limits between assembly and the model. Support desks run it with reply-time alerts on the log stream. The policy text changes; the layering does not.

3.9 Orchestration Patterns

Hook: Three requests arrive: "book Doctor X for 6 PM," "my branch cannot do this, send it on," and "plan my whole conference trip." One fixed script cannot serve all three.

An orchestrator is the logic that controls how the conversation flows. Three patterns cover the space. Each one below uses the procedural spine: purpose, inputs and outputs, steps, a trace, cost, and when to use it.

3.9.1 Workflow

Purpose: Run a fixed task the same way every time, so regulated form-filling stays complete and auditable.

Inputs and outputs: In comes a task with known slots, such as doctor, department, date, and confirmation. Out comes a completed record plus follow-through such as notifications or database writes.

Steps: Appointment booking fits here: validate the request, check doctor availability and schedules, confirm with both the administrator and the patient, and trigger follow-through such as notifications or record updates. The conversation manager fills the slots at each step. Regulated form-filling work such as booking or makeup examination slots is the natural home of this pattern.

Trace: booking workflow on rails. Validate: Doctor X and dermatology exist. Check: 6 PM IST on 14th November is free. Confirm: administrator holds it, patient accepts it. Follow through: email sent, record set to booked. Result: four gates, no branching, full audit.

Complexity and cost stay flat per task: one pass through known steps with bounded history. When to use it: the steps are known before the run. The alternative is a free-form loop that re-plans what the form already dictates, which wastes calls and risks skipped checks.

3.9.2 Routing

Purpose: Send the request to the right place when one fixed path cannot cover the cases.

Inputs and outputs: In comes a message plus its context and permission limits. Out comes a destination: another branch, a human, or a chained workflow.

Steps: A router sends the request to the right place. Suppose availability checking is not an atomic step the current branch may perform, because booking spans several hospital branches and this agent's permissions cover only branch A. The run must wait and route the request to branch B. A small or large language model can read the conversational context and choose the branch. Or suppose the booking-only helper receives the AAA nausea question, which it must never answer. It should route to a human practitioner, asking the patient to wait while connecting to the on-call doctor. Sometimes several routes chain together, but the shape is the same: classify the need, then hand it to the right workflow.

Trace: two routes, one rule. Case 1: booking request arrives at branch A for a branch B doctor. Classifier reads permissions, holds the request, and hands it to the branch B workflow with slots attached. Case 2: "drug AAA is causing nausea" arrives at the booking helper. Classifier reads the booking-only scope, refuses to answer medically, and connects the on-call doctor. Result: same shape both times, classify then hand off.

Cost is one classification plus the chosen workflow. When to use it: the same request needs different destinations by branch, scope, or permission. The alternative is one giant workflow with every branch baked in, which turns brittle the moment a branch changes.

3.9.3 Agent Loop

Purpose: Keep choosing the next action when the actions cannot be fixed in advance.

Inputs and outputs: In comes an open goal with unknown sub-steps. Out comes a finished plan plus the trail of actions that built it.

Steps: In an agent loop the model chooses the next action repeatedly, because the actions cannot be fixed in advance. Open-ended multi-step problems live here. Suppose a doctor asks the helper to plan for conference ABC in country XYZ. That short request hides many steps. What is the conference and on which dates does it run. Where are the nearest commute and accommodation options. Do those conference dates clash with scheduled appointments. Should the doctor be asked to cancel one side or the other. No fixed form covers that spread, so an agent pipeline takes over and keeps choosing actions until the plan closes.

Trace: conference plan in five moves. Move 1: look up conference ABC dates. Move 2: list commute plus stay options near the venue. Move 3: pull the doctor's appointment calendar. Move 4: flag the clash on the middle day. Move 5: ask whether to cancel the clinic or skip the conference day, then hold the chosen bookings. Result: the plan emerges from the loop, not from a form.

Cost grows with the number of loop iterations, each one a model call with tools, so cap the iterations and stop on a clear done signal. When to use it: the sub-steps are unknown and depend on what each lookup returns. The alternative is a workflow that guesses the steps up front and breaks on the first surprise.

The selection guidance is deliberately conservative. When the domain is well understood, pick whichever pattern fits. When it is not, start with the simplest workflow, observe it in a test bed or with a subset of users, and add complexity only for edge cases the simple version cannot handle. Add autonomy only when the task requires it and the complexity justifies the cost. If one shared database already holds every branch, plain lookup beats a chain of tool calls.

Pitfalls: Routing everything through the agent loop turns a form into an expensive wander. Routing nothing turns a new branch into a dead end. Skipping the confirmation before a cancelling action is the costly version of the same bug. Match the pattern to the shape of the task, and re-check the shape when the task changes.

3.9.4 Student Questions and Answers

Q: How should I summarize what the orchestrator does? A: Call it the heart of the system: the logic that routes each request, sending it toward an intent handler, a tool, or another workflow. It either follows a fixed sequence, picks among destinations, or keeps the conversation going with clarifying questions until the next step is clear.

3.9.5 Exam Notes

Exam note: The three patterns map to three prompts. Fixed form-filling points to workflow. Same request, different destination, such as another branch or a human doctor, points to routing. A short request that unpacks into many unknown steps, such as the conference plan, points to the agent loop. Key Industry Applications

Hospital booking helpers expose doctor, department, date, and status as explicit slots so omissions are visible and recoverable. The same slot discipline in banking covers account type so the system never asks twice. Travel and support bots attach reply-time targets with timeout and reroute behavior when model calls stall, holding the 15-second line from section 3.2. High-traffic teams cap per-call history because full-history fan-out multiplies inference spend, holding the $0.5 line from the same section. Medical helpers pair retrieval over policy documents, prescriptions, and visit history with practitioner-approval policies before any symptom advice, combining retrieval from section 3.5 with guardrails from section 3.8. Multi-branch deployments route between branches on permission boundaries and escalate out-of-scope clinical questions to on-call staff, using the router from section 3.9. Programs roll out the simplest workflow to a user subset first and add routing or agent loops only for observed edge cases, following the conservative selection rule that closes the lecture.
