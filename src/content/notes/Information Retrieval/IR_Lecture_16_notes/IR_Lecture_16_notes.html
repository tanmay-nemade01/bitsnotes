16.1 Content-Based Image Retrieval and Colour Histograms

16.1.1 Image database, feature extraction and similarity matching

An image database — a stored set of images with precomputed descriptors — supports search by visual content rather than by surrounding words. A feature — a measurable visual property such as colour, texture, or shape — acts as the bridge between pixels and search. A query image — the image given at search time — goes through the same steps as the stored images.

Hook: Imagine you hand a librarian a photo of a sunset and ask for "more pictures that look like this" — no words, no tags, just the picture itself. How does the machine answer when there is nothing to read?

The answer is a fixed four-step pipeline, and the same shape returns for audio and video later in this lecture. First, take each stored image and run feature extraction. Second, store those features in a ready form, usually as vectors in an index. Third, take the query image and run the exact same feature extraction procedure — same code, same settings, same normalisation. Fourth, compute similarity between query features and each stored feature set. The stored image with the closest match becomes the top retrieval result.

The crucial discipline is symmetry: query and stored images must pass through identical extraction. If the store was built with one colour quantisation and the query uses another, the numbers no longer line up and even an identical image can miss.

Formal pipeline: Let \(x\) be an image and \(f(\cdot)\) be the feature mapping. Each stored image \(x_i\) is represented as \(v_i = f(x_i)\). A query \(q\) becomes \(v_q = f(q)\). Retrieval ranks stored items by a similarity score \(s(v_q, v_i)\), where a larger \(s\) means a closer visual match. The top result is \(\mathrm{argmax}_i \, s(v_q, v_i)\). Here \(v\) is a feature vector, \(f\) is fixed for the whole collection, and \(s\) is typically a cosine similarity or a negated distance.

Worked example — graded similarity: Three stored photos are compared against a query photo of a red striped ball on grass. Photo A shows the same ball from a slightly different angle (shape slightly off, colour and texture right) and scores highest, say \(s = 0.92\). Photo B shows a red smooth cube on grass (shape and texture off, colour right) and drops to \(s = 0.71\). Photo C shows a blue smooth box on sand (shape, colour, and texture all off) and falls to \(s = 0.34\). Best match is Photo A at 0.92. Sense-check: each extra cue that changes pushes the score down another step, which is exactly the graded fall shown in the lecture visuals.

The paint-swatches picture from the lecture carries the whole idea. Two swatches look close when their colour mixes sit near each other. Here the swatches are feature vectors and closeness is a similarity score. When shape alone differs, similarity drops a little. When shape and colour both differ, it drops more. When shape, colour, and texture all differ, similarity is lowest. That graded fall was shown with simple visual comparisons where one, two, then three cues changed.

Scope: This pipeline assumes the descriptor captures what the user cares about. A colour-only descriptor answers "more red things" well and answers "same object, different colour" badly. Colour, texture, and shape cues are complementary, and a real system combines them rather than trusting one alone.

Picture the score as a number line from 0 (nothing in common) to 1 (near-identical descriptors). Matches pile up near 1 only when all kept cues agree; each disagreeing cue drags the point left. That one-sentence picture explains every ranking in this section.

Pitfalls: Beginners often compare raw image files instead of extracted features — two identical-looking photos with different sizes or formats then look different to the machine. A second trap is extracting query features with different settings from the store. A third is reading a similarity of 0.7 as "70 percent the same object" — it means 70 percent alike under this descriptor, nothing more.

Recap: Image search turns pictures into comparable vectors with one shared mapping, then ranks by similarity. The same extract-then-compare shape powers the audio and video methods ahead.

Reverse image search and near-duplicate photo detection on the web are the direct deployment of this pipeline: upload a photo, get back visually close copies even when filenames and surrounding text differ completely.

16.1.2 Colour histograms in RGB and pixel binning

A colour histogram — a count of how often each colour range occurs in an image — gives a compact view of colour spread. An RGB value — a triple of red, green, and blue strengths — describes each pixel. Each channel ranges from 0 to 255, so pure black is \((0, 0, 0)\) and pure white is \((255, 255, 255)\).

Hook: How can a machine tell a sunset photo from a forest photo without knowing what a sun or a tree is? Count the colours — the sunset piles up in reds and oranges, the forest piles up in greens.

Think of binning like sorting coins into trays by year and then counting each tray. In pixel space we sort pixels by colour range and count frequencies. A tray is a bin: a fixed colour interval such as red strengths 0–63, 64–127, 128–191, 192–255. Sweep every pixel, drop it in its tray, and the row of tray counts is the histogram.

Formalize — RGB and histograms: Let a pixel colour be \(c = (r, g, b)\) where \(r\) is red strength, \(g\) is green strength, and \(b\) is blue strength, each in \([0, 255]\). White is \(c_{white} = (255, 255, 255)\) and black is \(c_{black} = (0, 0, 0)\). Partition each channel into \(B\) intervals (bins). A per-channel histogram \(h\) has entries \(h_j\) = number of pixels whose value falls in bin \(j\), for \(j = 1, \dots, B\). The three per-channel histograms together form the colour descriptor. A fuller joint version bins the RGB cube itself: with 4 splits per axis this gives \(4 \times 4 \times 4 = 64\) small 3D cells, and the share of pixels in each cell is the descriptor. Histograms are then normalised so images of different sizes stay comparable.

The RGB cube makes this concrete. One corner of the cube holds black at \((0, 0, 0)\). The opposite corner holds white at \((255, 255, 255)\). Pure red, green, and blue sit at their own corners, and every mixed colour sits somewhere inside the cube. The histogram records where the image mass sits in that cube — a sunset crowds one end, a forest crowds another.

Worked example — comparing two spectra: Take a query sunset photo Q and two stored photos A (another sunset) and B (a forest). Use 4 bins per channel. Suppose the red-channel histogram of Q is \([10, 20, 60, 110]\) pixel counts across the four trays, A is \([12, 22, 58, 108]\), and B is \([100, 60, 25, 15]\). Bin-by-bin gaps between Q and A are tiny (at most 2–3 per bin), while gaps between Q and B run to 90 in the outer bins. Summed absolute gaps give about 9 for Q–A versus about 280 for Q–B. Closest spectrum is A, so A wins. Sense-check: two sunsets share warm-heavy trays, so their counts must nearly match.

The verbal picture from the lecture is exactly this: plot the histogram for each colour scale and compare that RGB spectrum of the query image with the RGB spectrum of each stored image. The closest spectrum wins.

Scope: Colour histograms assume colour spread is a good stand-in for visual likeness. They hold when scenes differ in palette and break when two different scenes share a palette — a red flag and a red sunset have close histograms but different meaning. They also ignore layout: a red square on top of blue and a blue square on top of red give the same histogram.

Picture two bar charts side by side, tray number on the horizontal axis and pixel count on the vertical axis. The query sunset chart climbs steeply to the right (warm bins tall). The matching stored sunset climbs the same way, bars nearly overlapping. The forest chart climbs to the left instead. The takeaway in one line: overlapping bar shapes mean a match, mirrored shapes mean a miss.

Pitfalls: A common trap is comparing unnormalised counts between a thumbnail and a wall-sized photo — always normalise by total pixels first. Another is using too few bins (everything looks alike) or too many bins (nothing ever matches because near-identical shades fall in different trays). A third is forgetting that histograms discard positions, so layout queries need texture or shape cues as well.

Recap: RGB triples place every pixel in a colour cube, and the histogram counts how the image spreads across that cube — a compact, comparable spectrum per picture. The same count-then-compare habit returns in audio landmarks ahead.

Camera-roll search by colour ("show beach photos" via blue-plus-sand palettes) and stock-photo filtering by mood palette are everyday uses of this descriptor.

16.1.3 Feature vectors and single-modality scope

A feature vector — an ordered list of numbers describing one image — makes comparison concrete. Suppose an image is 30 by 30 pixels. Then each pixel value can serve as one feature, giving a long vector with one entry per pixel, \(30 \times 30 = 900\) numbers. Without normalisation, each entry ranges from 0 to 255.

Formalize: Let the image have \(n\) kept values \(x_1, x_2, \dots, x_n\). The feature vector is \(v = (x_1, x_2, \dots, x_n)\), where each \(x_j\) is one measured value (a grey level, one colour channel, or one histogram bin count). Here \(n\) is the descriptor length — 900 for a raw 30-by-30 grey image — and the vector lives in \(\mathbb{R}^n\). Two images are compared by comparing their vectors entry by entry.

Worked example — 30-by-30 vector: A 30-by-30 grey photo gives \(v \in \mathbb{R}^{900}\) with entries in \([0, 255]\). Suppose the first three pixels of stored image A are \([200, 202, 198]\) and of query Q are \([201, 200, 199]\). Entry gaps are \(|200-201| = 1\), \(|202-200| = 2\), \(|198-199| = 1\), totalling 4 over three entries — a tight match. A different image B with \([40, 35, 50]\) gives gaps of about 160 per entry. A is the near-duplicate; B is unrelated. Sense-check: near-identical pixels give near-zero gaps, so the sum stays small only for true lookalikes.

So really, what this says is simple. Pixels become numbers. Numbers become vectors. Vectors let us measure closeness with arithmetic.

At this point the scope is single modality. Text-to-text search is treated as done. Image-to-image search is treated as done. Text-to-image and image-to-text with mixed inputs belong to a later multimodal part. Audio and video build on the same feature-plus-similarity idea but need their own features — waveforms and spectra for audio, frames plus sound plus text for video.

Scope: Raw pixel vectors assume aligned, same-size images. They hold for near-duplicate detection and break under crops, rotations, or lighting shifts, which is why histograms and learned embeddings replace raw pixels in harder tasks.

Recap: A feature vector turns a picture into arithmetic-ready numbers; single-modality search compares vectors within one medium. Mixed text-image search needs the shared embedding space built later in this lecture.

16.1.4 Student Questions and Answers

Q: When we compare source and query, are both images, and is the check done at pixel level? How is the feature presented? Is it a vector? A: Yes — in this section both sides are images. The check is done on extracted features, not raw files. Features can be pixel by pixel: a 30-by-30 image gives one feature per pixel, stored as a vector from feature one to feature \(n\), here 900 entries. Without normalisation the entries range from 0 to 255. The confusion is natural because "pixel level" sounds like comparing files; the correction is that the machine compares the extracted vectors, which is why the same extraction must run on both sides.

Q: What if the source is an image and the query is words? Is that the multimodal case? A: Yes, that mix is multimodal. The path forward is a shared embedding space where text and images meet — one space, two encoders, closeness meaning shared meaning. That topic comes after single-modality image-to-image work, alongside audio work, and it is built in full later in this lecture with CLIP and ALIGN.

16.2 Audio Retrieval Tasks and Searchable Cues

16.2.1 What can be searched in audio

An audio snippet — a short piece of sound given as a query — is matched against a stored audio collection. Useful cues live in rhythm, in frequency patterns, in spoken words, in speaker traits, and in many related properties. A speaker trait can be as fine as a stammer that colours the voice. The retrieval problem is to find the audio track in the stored collection that shares those traits with the query.

Hook: Hold your phone up to a song in a noisy cafe and it names the track in seconds — yet the microphone heard chatter, clatter, and room echo the studio recording never had. What survives all that mess?

Sound comes from waveforms, so comparing waveforms directly feels natural. Yet a short noisy query against a large varied store makes raw waveform matching weak. Noise adds wiggles, compression reshapes peaks, reverberation smears time, and microphones colour frequencies. The system must therefore extract a form that stays stable when noise, compression, or room effects change the raw wave — the same extract-then-compare habit as image retrieval, with audio-native features.

Formalize — the audio retrieval contract: Let \(q(t)\) be the query waveform over time \(t\) and \(\{x_i(t)\}\) be stored tracks. Direct comparison \(q(t) \approx x_i(t)\) sample by sample fails under the distortions above. Instead each signal passes through a feature map \(g(\cdot)\) giving \(u_q = g(q)\) and \(u_i = g(x_i)\), and retrieval ranks by \(s(u_q, u_i)\). Here \(g\) is chosen per task: spectral peaks for exact-match, word sequences for speech content, voice-character statistics for speaker checks. The shared skeleton is identical; only \(g\) and \(s\) change.

Worked example — why waves fail but cues survive: A 5-second cafe recording of a chorus and the clean studio chorus look very different sample by sample — background chatter alone shifts hundreds of sample values. But both show strong energy at the same sung notes, say near 440 Hz and 660 Hz at the same relative times. A peak-based cue keeps those two ridges and discards the chatter. The waveform gap is large; the peak-pattern gap is small — so the cue matches where the wave does not. Sense-check: loud stable notes poke through noise while quiet detail drowns, so keeping only strong peaks is exactly right.

Scope: Waveform comparison assumes near-identical recording chains. That holds for lab duplicates and breaks in the field, where microphones, rooms, codecs, and background sounds all differ. Robust features assume at least some strong structure (pitched notes, repeated spectral ridges) survives — whispered or heavily masked queries can defeat even them.

Picture a wiggly line (waveform) next to a dark chart with a few bright horizontal ridges (spectrogram peaks). Noise scribbles all over the wiggly line but barely moves the bright ridges. One-line takeaway: search the ridges, not the scribble.

Pitfalls: Beginners try to match raw waves and conclude audio search is hopeless when noise breaks it. A second trap is using one cue for everything — word transcripts cannot name a hummed tune, and spectral peaks cannot tell who spoke. Match the cue to the question.

Recap: Audio search keeps the image-retrieval skeleton but swaps in sound-native cues — rhythm, spectra, words, voice traits — chosen for stability under real-world distortion. Each cue leads to its own task next.

16.2.2 Four task forms

First, fingerprinting — exact-match search from a short sample against a large collection — takes a few seconds of sound and looks for the same known item. Second, speech recognition — conversion of spoken content into searchable text — turns audio into words and then uses text search methods. Third, speaker identification — deciding who is speaking without caring what is said — focuses on voice traits. Fourth, spoken document retrieval — finding audio items whose content matches a text query — goes in the reverse direction from text to audio.

Inputs and outputs per task: Fingerprinting takes audio in and returns the same audio item (which song is this?). Speech recognition takes audio in and returns text (what was said?). Speaker identification takes audio in and returns a person label (who spoke?). Spoken document retrieval takes text in and returns audio items (which recordings mention this?). The arrows matter: the first three start from sound, the fourth starts from words.

Worked example — one clip, four questions: A 6-second voicemail says "meet at noon" in a distinctive stammering voice over cafe noise. Fingerprinting asks "is this exact recording already filed?" and should answer yes only for that file. Speech recognition should output the string "meet at noon". Speaker identification should output the caller's name regardless of the words. Spoken document retrieval starts instead from typed "meet at noon" and should return this voicemail among others with that content. Same clip, four different correct answers — because each task scores a different property. Sense-check: content, identity, and exact-identity are logically independent, so one number cannot serve all three.

Each task uses its own techniques and its own way of scoring success. Exact-match is scored by hit rate on known items. Word output is scored by transcription accuracy. Speaker labels are scored by identification accuracy across sessions. Text-to-audio is scored by ranking quality. The split matters because exact-match needs differ from who-is-speaking needs, and both differ from what-was-said needs.

Scope: These four cover the lecture's audio map, not all of audio processing. Music-genre tagging, emotion detection, and source separation exist but are out of scope here; the four were chosen because each maps cleanly onto a retrieval direction.

Recap: Name the arrow before picking the method — audio-to-same-audio, audio-to-text, audio-to-person, or text-to-audio. The next section shows why one similarity score cannot cover all four.

Phone song-naming, voicemail transcription, voice login, and podcast search by typed keywords are the four deployed faces of these four tasks.

16.2.3 Why one method cannot cover all audio needs

Exact-match wants near-identity despite noise. Speech-to-text wants word accuracy despite accents and vocab gaps. Speaker checks want stable voice traits across words, sessions, microphones, background sounds, and even illness. Text-to-audio wants to bridge words and sounds. A single similarity number cannot serve all four goals at once. This is why the field keeps separate pipelines that share only the broad idea of features plus comparison.

Intuition: Think of four different questions about the same letter: is this the exact same envelope, what does the letter say, who wrote it, and which letters mention sailing? One glance cannot answer all four — handwriting shape, word content, stylistic quirks, and topic index each need their own reading. Audio tasks split the same way.

Consider the trade directly. A fingerprint that ignores words is perfect for naming a song but useless for transcribing it. A word-only output that discards pitch is perfect for search-by-content but destroys the voice traits a speaker check needs. A speaker model that averages over words is robust to wording but blind to wording by design. Each pipeline throws away what its question does not need, so no single pipeline can keep everything.

Assumption: Each pipeline assumes its kept cue is stable while its discarded cues vary freely. Fingerprinting assumes spectral landmarks persist across codecs; speech models assume phonetic patterns persist across speakers; speaker models assume vocal-tract traits persist across words. Scope: When the assumption fails — landmarks drowned by noise, heavy accent outside training, a bad cold reshaping the throat — that pipeline degrades and a sibling pipeline will not rescue it.

Pitfalls: The classic exam trap is proposing "one universal audio similarity" for all four tasks. A second trap is scoring a speaker system by word accuracy or a transcription system by voice match — each task needs its own success measure. A third is forgetting illness, microphone, and room shifts when claiming a speaker model is finished.

Recap: Separate questions need separate features and separate scores; the shared skeleton is extract-then-compare, never one shared number. Fingerprinting is the sharpest illustration, so it comes first.

Studio duplicate detection, call-centre transcription, building voice access, and searchable meeting archives each buy a different pipeline for exactly this reason.

16.3 Audio Fingerprinting with Spectral Landmarks

16.3.1 Problem setup and distortions

Audio fingerprinting starts with a short query sample. It can be a bird call, a violin phrase, or any brief sound. The store holds many known items. The goal is a near-exact match — not the same words or the same speaker, but the same sound event.

Hook: Three seconds of a violin phrase, recorded on a phone across a noisy room from a compressed stream — and the app still names the exact recording. What fingerprint survives all three corruptions at once?

The query may carry background noise. It may be uncompressed while the store is compressed. The query may carry room reverberation and microphone distortion. All of these change the waveform shape while the underlying song or sound stays the same. That is why direct wave-to-wave comparison is not trusted here: two waves of the same song can look point-by-point different once noise, codecs, echo, and microphone colouring each add their own layer.

Purpose and I/O: The problem fingerprinting solves is exact-identity under distortion. Input is a short noisy query clip (a few seconds). Output is the identity of the matching stored item, or none. Stored items are assumed fairly clean; queries are allowed to be noisy, reverberant, differently coded, and differently transduced.

Worked example — bird call in wind: A stored nightingale phrase is clean. The field query adds wind hiss plus phone-microphone bass roll-off. Sample-by-sample the two waves share almost nothing — wind alone flips the sign of hundreds of samples. Yet the phrase's three dominant whistled notes still produce the tallest spectral ridges at the same relative times in both. A landmark method keeps those ridges and matches; a wave method drowns. Fingerprint matches; waveform misses. Sense-check: wind is broadband and weak per frequency, while whistles are narrow and strong, so peaks survive where averages do not.

Shazam is the named deployment: a mobile app that names a music item from a tiny heard snippet. It follows this same fingerprint idea and is worth trying after class — hearing it work in a noisy room is the fastest way to believe the robustness claim.

Scope: Fingerprinting assumes the query really is a distorted copy of something stored. It holds for identifying known recordings and breaks for哼ed tunes, covers by other artists, or brand-new sounds with no stored original — those need melody or content methods instead.

Recap: Short noisy query, large clean store, near-exact match wanted — so the method must keep only distortion-proof structure. Spectral landmarks are that structure.

16.3.2 Robust spectral landmarks and fingerprint creation

A spectral landmark — a strong frequency peak plus its time stamp — survives noise and coding changes better than raw samples. A fingerprint — a compact code built from those landmarks — is what gets indexed and compared.

Intuition: Think of mountain peaks on a foggy day. Fog hides small hills but the tall peaks still poke through. Strong spectral peaks play the same role in sound: noise and compression are the fog, and only the tallest energy ridges stay visible.

The verbal picture from the lecture is: capture strong frequency peaks with temporal values at time stamps T0, T1, and T2, then convert that landmark information alone into a fingerprint for matching against original fingerprints. In deployed systems these scatter plots of peaks are called constellation maps, because the surviving dots look like star constellations, and their positions stay put when codecs or background noise change.

Formalize: Let \(f\) be frequency in hertz and \(t\) be time in seconds. A landmark is a pair \(l = (f_{peak}, t_{peak})\) where \(f_{peak}\) is a local strong peak in the short-term spectrum and \(t_{peak}\) is its time stamp. A fingerprint \(F\) is a function of a set of landmarks:

\[ F = H(\{(f_1, t_1), (f_2, t_2), \dots, (f_n, t_n)\}) \]

where \(H\) is a hashing or encoding step that turns peak sets into compact codes, \(n\) is the count of kept peaks, \(f_i\) is the i-th peak frequency, and \(t_i\) is its time. Only the landmark set enters \(H\); raw samples do not. The hope is that stored items are fairly clean, free of heavy compression and strong microphone effects, so their fingerprints stay stable while query fingerprints bend but do not break.

How the code is built in practice: take the short-term spectrum over time, keep local maxima above a threshold, quantise their frequencies and time differences, and hash pairs or triplets of peaks into integers. Hashing matters because integer codes can be indexed like text terms — lookup is then near-instant even over millions of tracks.

Worked example — landmark hashing sketch: A 3-second query yields strong peaks at \((440, 0.4)\), \((660, 0.9)\), and \((880, 1.5)\), with frequencies in Hz and times in seconds. The encoder forms pairs such as \((440, 660, 0.5)\), where 0.5 is the time gap \(0.9 - 0.4\), and hashes each pair to an integer code. The stored chorus yields the same three peaks at \((440, 12.4)\), \((660, 12.9)\), \((880, 13.5)\) — absolute times differ but gaps match (0.5 and 0.6). Shared hashes fire; unrelated tracks share almost none. Matching hashes identify the track and even its offset (12.0 s in). Sense-check: relative gaps survive time shifts by construction, which is why absolute clock time never enters the code.

Picture a dark time-frequency chart, time on the horizontal axis in seconds and frequency on the vertical axis in hertz. A handful of bright dots (the kept peaks) form a sparse constellation; everything else is dim fog. The takeaway: the constellation shape is the song's signature, and fog cannot redraw it.

Scope: Landmarks assume music or pitched sound with stable strong tones. The method holds for songs, jingles, bird phrases, and violin lines, and weakens for whispers, pure drum clicks without tonal ridges, or extremely short sub-second queries with too few peaks to hash.

Pitfalls: Keeping too many weak peaks reintroduces noise sensitivity; keeping too few leaves nothing to hash. Using absolute times instead of relative gaps breaks matching under time shifts. Hashing raw samples instead of peaks throws away the whole robustness gain.

Recap: Strong peaks plus times, hashed into compact codes — that is the fingerprint. Matching those codes is the retrieval step next.

16.3.3 Matching expectation

Query landmarks become a query fingerprint. That code is compared with stored codes. The near-identical stored item should score highest — most shared hashes wins, with consistent time offsets as confirmation. The method does not try to understand words or speakers. It tries to recognise the same sound event again. That narrow goal is what makes it one of the most successful audio retrieval tools.

Worked example — scoring: A query yields 30 hash codes. Stored track A shares 24 with consistent offsets; track B shares 3 at scattered offsets; track C shares 1. Even though B is the same song covered by another band (similar notes, different recording), A is the same recording and wins by count plus offset consistency. Winner is A with 24 aligned hashes. Sense-check: chance hash collisions are rare, so a 24-vs-3 gap cannot happen by luck.

Scope: Matching assumes the store's fingerprints were built with the same peak picker and hash as the query. Mixed settings across store and query silently break counts.

Recap: Count shared landmark hashes, confirm their offsets line up, return the top scorer. Narrow question, sharp tool — the next section turns to the opposite goal of understanding words and voices.

Music naming, broadcast monitoring (which ad aired when), and duplicate-song detection in large catalogues all run on this matching step.

16.4 Speech Recognition and Speaker Identification

16.4.1 Speech recognition pipeline

Speech recognition — turning spoken audio into text — follows a clear conceptual flow even when modern systems rename the blocks. First, analyse the audio signal. Next, break it into parts. Then digitise it into computer-readable form. Then run a matching step that maps the coded audio to a text form. After that, standard text search methods apply.

Hook: A voicemail arrives as wiggles in air — how does it end up as searchable words you can Ctrl+F?

The same flow was described as signal, segmentation, representation, and decoding. Signal analysis cleans and frames the wave. Segmentation chops it into short pieces (frames or phones). Representation turns each piece into numbers the computer can compare. Decoding maps the number sequence onto words. Modern systems may merge or rename steps — an end-to-end net can swallow segmentation and representation into one block — but the path from wave to words stays intact.

Procedural spine — wave to words: The purpose is audio-in, text-out. Inputs are sampled waveforms plus acoustic and language knowledge; output is a word string. Steps: (1) analyse the signal — filter, frame into 10–30 ms windows; (2) segment — locate phone- or word-like units; (3) represent — encode each frame as features; (4) decode — find the most likely word sequence given acoustics plus language expectations. Each step's rationale is information bottlenecking: throw away speaker, channel, and noise detail while keeping linguistic content.

Worked example — "meet at noon": A 1-second clip of "noon" is framed into about 50 short windows. Frames 1–15 show nasal low-frequency energy (the "n"), frames 16–35 show a steady vowel ridge (the "oo"), frames 36–50 return to nasal energy. The decoder combines these acoustic scores with the language prior that "at noon" is likelier than "at moon" after "meet". Output string is "meet at noon". Sense-check: acoustics proposes sound-alikes, language picks the sensible phrase — neither alone is enough.

Here the direction is audio to text. That bridge is itself a multimodal step because the input modality differs from the output modality — sound in, words out — a preview of the text-image bridges later in the lecture.

Scope: Recognition assumes the speech sits within the system's acoustic and vocabulary coverage. It holds for clear speech in supported languages and accents, and degrades on heavy accents, rare names, overlapping talkers, and strong noise — the exact gaps the retrieval-oriented paths in the next section try to soften.

Pitfalls: Treating the decoder output as perfect text is the classic mistake — downstream search must tolerate word errors. A second trap is confusing this content question ("what was said?") with the identity question ("who said it?"), which needs different features entirely.

Recap: Wave, frames, features, words — a four-move bottlenecking that keeps language and discards the rest. Speaker identification keeps the opposite half.

Voicemail transcription, meeting captions, and searchable podcast archives are the direct deployments of this pipeline.

16.4.2 Speaker identification

Speaker identification — deciding who is speaking — ignores word content and listens for voice character. One path is speaker-dependent recognition. It works well for known voices when enough samples exist for each person. But collecting enough data for every member of a large population is impractical.

Intuition: Think of recognising a friend's handwriting versus reading their letter. Reading cares about the words; writer-spotting cares about slant, pressure, and loops across any words. Speaker identification is writer-spotting for voices.

The hard part is stability. Vocal traits must hold across different words, different sessions, different microphones, different background sounds, and even sickness that changes throat sound. A cold can shift the voice enough to fool a narrow model. So the features must average away wording and channel while keeping vocal-tract character — the exact opposite trade from speech recognition.

Another path uses a Gaussian mixture model — a weighted sum of Gaussian bumps used to model voice character in a statistical way — to represent speaker traits. The verbal picture from the lecture is: use a statistical Gaussian mixture approach to capture speaker characteristics for voice-to-voice matching.

Formalize — speaker GMM: Let \(x \in \mathbb{R}^d\) be a \(d\)-dimensional voice feature vector from a short frame, where \(d\) is the feature width (for example cepstral coefficients) and each frame covers a few tens of milliseconds. A speaker model with \(K\) components is:

\[ p(x) = \sum_{k=1}^{K} w_k \, \mathcal{N}(x \mid \mu_k, \Sigma_k) \]

where \(w_k\) is the weight of component \(k\) with \(\sum_{k=1}^{K} w_k = 1\) and \(w_k \ge 0\), \(\mu_k \in \mathbb{R}^d\) is the mean vector of component \(k\), \(\Sigma_k \in \mathbb{R}^{d \times d}\) is its covariance matrix, and \(\mathcal{N}\) denotes the Gaussian density:

\[ \mathcal{N}(x \mid \mu_k, \Sigma_k) = \frac{1}{(2\pi)^{d/2} \, |\Sigma_k|^{1/2}} \exp\left(-\frac{1}{2}(x - \mu_k)^\top \Sigma_k^{-1} (x - \mu_k)\right) \]

Different speakers get different sets of weights, means, and covariances. A new sample \(x_1, \dots, x_T\) is assigned to the speaker model that gives it the highest total likelihood \(\prod_{t=1}^{T} p(x_t)\). In words: each speaker owns a personal landscape of \(K\) bumps in voice-feature space, and the speaker whose landscape best explains the new frames wins.

Worked example — two speakers, tiny numbers: Use \(d = 1\) for sketch clarity with \(K = 2\) bumps each. Speaker A has bumps centred at \(\mu = 0\) and \(\mu = 10\) with equal weights 0.5. Speaker B has bumps at \(\mu = 5\) and \(\mu = 15\). A new frame arrives at \(x = 1\). Under A it sits near the \(\mu = 0\) bump, density high, weighted likelihood about 0.18. Under B the nearest bump is at 5, four units away, density near 0.0001. Over ten similar frames the product gap compounds enormously. New sample goes to Speaker A. Sense-check: frames near A's bumps and far from B's must favour A — likelihood arithmetic just formalises nearness.

Picture each speaker as a terrain of hills in feature space, hill positions set by \(\mu_k\), widths by \(\Sigma_k\), heights by \(w_k\). New voice frames fall like rain; the terrain that catches most water (highest likelihood) names the speaker. One-line takeaway: identity is landscape ownership, not word matching.

Scope: GMM speaker models assume enough per-speaker frames to fit \(K\) bumps and assume test conditions resemble training. They hold for closed-set checks with decent enrolment audio and break under strong channel shift, very short test clips, or open populations where the true speaker was never enrolled.

Pitfalls: Enrolling each speaker on one microphone and testing on another is the classic failure. Using too many components \(K\) for tiny enrolment data overfits — the bumps memorise the enrolment sentences instead of the voice. Forgetting that a cold, stress, or ageing shifts the landscape causes confident mislabels.

Recap: Model each voice as a weighted bump landscape; new audio goes to the landscape that best explains it. Content is deliberately ignored — which is exactly what the worked contrast next shows.

Phone voice login for known users and meeting diarisation ("who spoke when") are the standard deployments; large-population open-set search needs extra calibration beyond this core.

16.4.3 Worked sense of the two directions

Take a short voice note that says the same sentence as a stored note but from a different speaker. Speech recognition should output the same words for both. Speaker identification should output different names. The features and scores differ because the questions differ. One asks what was said. The other asks who said it.

Worked comparison: Stored note S (Speaker A): "open the vault". Query Q (Speaker B): "open the vault". Speech recogniser output for both: the string "open the vault" — same text, correct. Speaker scorer: likelihood of Q's frames under model A is low, under model B is high — different name, correct. A system that returns "same" for both questions, or "different" for both, fails one task by construction. Sense-check: same sentence, different throat — content matches, landscape does not.

16.5 Spoken Document Retrieval with Keyword and Phonetic Search

16.5.1 Task definition

Spoken document retrieval — finding audio items that match a text query — reverses the speech recognition direction. Speech recognition maps speech to text. Spoken document work maps text to audio. Two speech-specific paths are common: keyword spotting and phonetic recognition. Both are more tolerant than plain speech-to-text in retrieval settings, and the choice depends on what is handy for the task.

Hook: You type "vaccine" and want every call recording that mentions it — but half the calls were never transcribed, and the transcriber mangles new drug names anyway. How do you search sound with words when the auto-generated text cannot be trusted?

A standard recogniser can slip on names, technical words, accents, and noisy items — exactly the high-value queries (new products, people, places). The two retrieval-oriented paths try to stay useful even when full transcription is shaky: one hunts a fixed word list directly in audio, the other searches at the sound level so unknown words still have a spelling in sounds.

The reversal: Speech recognition is audio-in, text-out (transcribe everything, then search text). Spoken document retrieval is text-in, audio-out (start from the typed query, return matching recordings). The reversal matters because the query is known in advance — the system can tune detectors for those exact words or sounds instead of transcribing the whole archive perfectly.

Worked example — why the reversal helps: Archive holds 10,000 calls. Full transcription gets 80 percent of words right but mangles the new product name "Zelvonex" every time (out of vocabulary). A text query for "Zelvonex" over transcripts returns nothing. A retrieval-tuned path that listens for Zelvonex-like sound sequences directly in audio finds 40 true mentions at the cost of a few false alarms. Reversal plus tolerant matching returns 40 hits where text-index search returns 0. Sense-check: a detector for one query can beat a transcriber of everything on that query.

Scope: This task assumes the spoken content actually contains answerable mentions. It holds for meetings, calls, and broadcasts with real speech, and breaks for music or unintelligible audio where no word-level method has anything to grip.

Recap: Type words, get back audio — via keyword detectors or sound-level search, chosen for tolerance where full transcription is shaky. The two paths split next.

Podcast search by typed topic and compliance monitoring ("find calls mentioning refunds") are the standard deployments.

16.5.2 Keyword spotting

Keyword spotting — direct search for a small set of chosen words and phrases inside spoken material — looks only for its list. A whole keyword carries more information than a single speech sound, so a hit is a strong signal and cuts down on chance matches: matching a full "refund policy" pattern by accident is far less likely than matching one vowel.

Intuition: Think of scanning shelves for three specific book titles rather than reading every book. You move fast and rarely misfire — but a book you were not told to look for stays invisible even when it sits in front of you.

The limit is vocabulary. Users must pick queries from the system known vocabulary. A rare word such as a new vaccine name, a new person name, or an unexpected technical term may be missed entirely. That makes the method strong for focused monitoring, such as finding mentions of a defined product topic, but stiff for open-ended search. It stays domain specific by design — the lecture's explicit warning.

Worked example — brand monitoring: Watch-list is ["refund", "cancel", "supervisor"]. A 5-minute support call contains "refund" twice (clear) and the new plan name "Zelvonex" once. The spotter fires twice on "refund" with high confidence (long word, distinctive sounds) and correctly ignores chatter. Query "Zelvonex" was never in the list, so its mention passes silently. Known words: 2/2 found. Unknown word: 0/1. Sense-check: detectors only see what they were built to see — coverage is exact on-list and zero off-list.

Assumption: The watch-list is fixed and pronunciations are modelled. Scope: Holds for closed monitoring tasks with stable vocabulary (brand names, compliance phrases); breaks for open search where users invent queries, and for fast-changing vocabularies where new terms arrive weekly.

Picture a control panel with three lit buttons (the keywords) wired to alarms. Speech flows past; only those three patterns trip their alarms. One-line takeaway: strong alarms, narrow ears.

Pitfalls: Treating a miss as proof the word was never said — it may be off-list or mispronounced. Setting thresholds too loose floods reviewers with false alarms; too tight silences true mentions. Forgetting to rebuild detectors when the product vocabulary changes quietly rots performance.

Recap: Keyword spotting trades openness for precision on a fixed list — ideal for monitoring, wrong for exploration. Sound-level search makes the opposite trade next.

16.5.3 Phonetic recognition

Phonetic recognition — conversion of the signal into a sequence of speech sounds followed by search at sound level — keeps flexibility. The verbal picture from the lecture is: convert the signal into speech sounds and search at that level.

Intuition: Think of searching by pronunciation respelling instead of official spelling. A new surname you have never seen still has a guessable sound shape ("ZEL-voh-nex"), so you can hunt its sound even with no dictionary entry.

Unfamiliar words can still be approximated through their sound sequences. That helps with names and out-of-vocabulary terms with no domain wall — the direct fix for keyword spotting's blind spot. The pair bat and bet shows the trade. In some accents they sound near-identical, so the method can confuse them. Accents matter a lot. When words are spoken with clean articulation, sound-level search does good work. When sounds collide, mismatch grows.

Worked example — bat versus bet: The archive holds "place your bet" spoken in an accent where the vowel sits halfway between standard bat and bet. A text query for "bet" is converted to the sound pattern B-EH-T. The archive segment decodes to B-AE/EH-T with low confidence on the vowel. The sound-level score is a near-miss (one vowel step away) rather than a clean miss, so the segment ranks mid-list instead of vanishing. A second segment with carefully articulated "bet" ranks top. Flexible ranking: exact sound match first, near-sound neighbour second, unrelated audio last. Sense-check: sound distance degrades gracefully where spelling match is all-or-nothing.

Take bat versus bet as a concrete pair. A listener using spelling keeps them apart with ease. A listener using only coarse sounds may mix them when the vowel colours shift by accent. The same tension shapes retrieval: flexibility rises, but near-sound confusion rises too.

Accent sensitivity Moderate High (vowel shifts bite)

When to pick which: closed watch-list with stable terms — keyword spotting; open-ended or name-heavy search — phonetic; production systems often cascade both.

Scope: Phonetic search assumes the phone decoder is decent on the target accents. It holds for clean articulation in covered accents and degrades under heavy accent shift or noise, where phone strings themselves go wrong and errors compound.

Pitfalls: Reading a phone-string hit as proof the exact word was said — near-sounds inflate scores. Ignoring accent coverage when promising open-vocabulary search. Forgetting that short words (one or two sounds) match by chance far more often than long ones.

Recap: Sounds buy openness at the price of confusability — bat/bet is the whole trade in one syllable. Video next layers all these signals at once.

Monitoring a brand name across calls suits keyword spotting, while hunting for new person names across varied audio suits phonetic search — the lecture's recommended split.

16.6 Video Retrieval, Multimodality and Fusion

16.6.1 Why video is harder

Video retrieval — finding video material from varied queries — layers many signals at once. A video holds a sequence of images as frames over time. It holds an audio track. It holds editing structure such as cuts and scenes. It may hold captions and so text. Social material adds tags, comments, and sharing behaviour such as who shares to whom.

Hook: A single film clip holds faces, dialogue, music, captions, cuts, and a thousand comments — which one answers "find the moment she laughs after the plot twist"? Any single cue alone misses it.

Queries can be text, a tiny video clip, a single image, an audio snippet, spoken content, or even a person. A cameo search that asks at what time stamp a person appears and leaves is a fair request here — answerable only by faces plus time. Collections vary widely: films, recorded talks, short web clips, static scenes, dynamic scenes. Structure, quality, length, available metadata, caption presence, colour, and illumination all shift. No single cue is enough on its own.

Worked example — cameo timestamp: Query: "when does the guest chef first appear and leave in this 40-minute episode?" Frames alone find chef-like faces but cannot tell guest from host. Audio alone hears a new voice but cannot place it in time precisely. Captions alone name the guest but carry no timestamps. Combined, face matches cluster at 12:04–18:37, the voice track agrees, and the caption confirms the name. Answer is 12:04 in, 18:37 out — reachable only jointly. Sense-check: each cue eliminates a different wrong answer, so intersection beats any single list.

Scope: Video methods assume at least some of these streams exist and roughly align. They hold for produced video with shots, sound, and optional captions, and degrade for single-frame GIFs (no audio), silent CCTV (no speech), or uncaptioned shaky clips where each cue is thin.

Recap: Video is a bundle of image, audio, structure, text, and social streams over time — queries attack any of them, so retrieval must use all of them. Combining is the fusion problem next.

Film search by quote plus face, lecture search by slide plus spoken words, and short-clip search by caption are the everyday faces of this bundle.

16.6.2 Fusion challenge

Fusion — combining evidence from different modalities into one decision — is the added problem wherever multimedia appears. Each source brings some information. Frames alone may miss speech meaning. Audio alone may miss visual identity. Text alone may miss tone and setting.

Intuition: Think of three witnesses to one scene: one saw, one heard, one read the report. Each is half-right alone; the truth is the weighted agreement of all three. Fusion is the weighting rule.

Named fusion styles include early fusion, intermediate fusion, late fusion, and hybrid fusion. Early fusion joins features before scoring — concatenate frame, audio, and text vectors, then score once. Late fusion joins scores after separate scoring — rank by frames, rank by audio, rank by text, then merge the three ranked lists. Intermediate and hybrid forms mix the two at middle points or in combined schemes, for example fusing some streams early and merging the rest late. The right pick depends on data and task, but the need to use all evidence is constant.

Style Joins at Strength Weakness
Early Feature level Learns cross-modal interactions Needs aligned features; one bad stream pollutes all
Late Score level Robust; streams stay independent Misses fine cross-modal patterns
Intermediate / hybrid Middle or mixed Balances both More knobs, harder to tune

When to pick which: tightly synced streams with training data — early; heterogeneous streams with missing pieces — late; production multimodal stacks — hybrid.

Worked example — early vs late: A cooking clip query "sizzling pan close-up with host saying salt". Early fusion concatenates the sizzle-audio vector with the pan-frame vector and scores the joint pattern — top hit shows both together. Late fusion scores sizzle-only (top: any sizzling clip) and pan-only (top: any pan shot) then averages ranks — the clip with both still wins but by margin fusion rather than joint pattern. Both return the right clip; early is sharper when streams align, late is safer when one stream drops. Sense-check: joint features see co-occurrence; merged scores see agreement.

Scope: Fusion assumes the streams describe the same time window. It holds for aligned clips and breaks when captions lag, audio dubs mismatch video, or social tags describe reactions rather than content.

Recap: Fuse features for sharpness, fuse scores for safety, fuse hybrid for production. Raw video is too heavy to fuse directly, so an abstraction step comes first.

16.6.3 Compact abstraction and indexing pipeline

Raw video is too heavy to search directly — hours of frames times audio times text cannot be scanned per query. The conceptual pipeline first builds a compact abstraction: selected keyframes, shot boundaries, and brief summaries. That abstraction is then indexed so search runs fast. A user query meets the retrieval component, which compares the query against the index and returns relevant items. Each block hides many sub-blocks in practice, and deeper study needs focused articles on video search.

Procedural spine: Purpose is fast search over heavy video. Inputs are raw clips; outputs are ranked clips with timestamps. Steps: (1) segment into shots at cuts; (2) pick keyframes representing each shot; (3) extract per-shot features (visual, audio, caption text); (4) build summaries and an index over shots; (5) at query time, match against the index and return clips plus time offsets. Complexity drops from per-frame scan to per-shot lookup — the whole point.

Think of it like a book index plus chapter summaries. The summaries let a reader jump fast, and the index points to exact pages. Keyframes and shot maps play the same role for video: shots are chapters, keyframes are chapter illustrations, the index is the back-of-book finder.

Worked example — compression of effort: A 60-minute talk at 30 frames per second holds about 108,000 frames. Shot detection finds 120 shots; one keyframe each gives 120 images plus 120 caption chunks to index instead of 108,000 frames. A query "slide with precision-recall curve" matches keyframe 87 and returns timestamp 43:12. Search touches 120 items, not 108,000 — roughly a 900-fold reduction. Sense-check: shots change slowly, so one picture per shot loses little and saves enormously.

Scope: Abstraction assumes shots are coherent enough that one keyframe stands for the shot. It holds for talks, films, and edited clips, and weakens for fast-cut montages or single-take action where every second differs.

Recap: Shots, keyframes, index, match — video search is image-plus-audio-plus-text search over a compact shot abstraction. The next leap learns one shared space for text and images directly.

Lecture-video navigation by slide thumbnails, sports highlight search by event shots, and news-archive lookup by captioned segments all run on this pipeline.

16.7 Shared Embeddings for Text and Images

16.7.1 Paired learning idea

Multimodal retrieval — search across modalities such as images and text — can be learned directly from paired data rather than by bolting separate systems together by hand. Two widely used vision-language models here are CLIP and ALIGN. Both map images and text into one shared space so closeness means shared meaning.

Hook: Words and pixels live in different worlds — how can "frosty dogs" typed on a keyboard sit next to a photo of dogs in snow with no shared units at all?

The shift from earlier audio discussion matters. Earlier, one input gave the other output, such as audio in and text out: transcribe this, name that. Here both modalities are present during learning as pairs, and after learning either side can query the other. Give text and get text or image. Give image and get image or text. The pairing during training is what enables that freedom — the model learns the correspondence itself instead of receiving a hand-built bridge.

The paired contract: Training sees image-text pairs \((I, T)\) that belong together (a photo plus its caption). Two encoders \(E_{img}\) and \(E_{txt}\) map each side into \(\mathbb{R}^d\), giving \(v = E_{img}(I)\) and \(t = E_{txt}(T)\). Training pulls paired \((v, t)\) together and pushes unpaired ones apart. After training, any text can be compared with any image by position — the bridge is geometry, not rules.

Worked example — freedom after pairing: Training saw thousands of pairs like (snow-dog photo, "dogs in snow"). At test time, a fresh query "two dogs running across a frosty field" — never seen word-for-word — encodes near the snow-dog photo region. A fresh photo of dogs in snow, never seen, encodes near that same query. Text finds the photo and the photo finds the text with no extra training. Sense-check: pairing taught directions in meaning space, so new points land by meaning, not by memorised strings.

Scope: Paired learning assumes training pairs are mostly correct and cover the target concepts. It holds for web-scale photo-caption collections and weakens for concepts never paired (rare objects, specialist imagery) where the space has no anchor.

Recap: Learn one space from pairs; query from either side. The space's geometry is the whole trick, detailed next.

16.7.2 Geometry of meaning

The central idea is geometric. Similar concepts should sit in nearby regions of the shared space. The model does not store a dictionary that maps one image to one caption. It learns a layout where related image-text pairs sit close and unrelated pairs sit far.

Intuition: Think of a map of a city where similar shops cluster on the same streets — bakeries together, garages together. Nobody memorised every address; the layout itself answers "what is near this bakery?" Meaning space works the same way: position answers relatedness.

That layout brings three uses at once. Text can retrieve images. Images can retrieve descriptions. New combinations never seen during training can still be compared by position — a fresh caption about snow lands near snowy photos even when that exact sentence never appeared. Once the geometry is right, retrieval is nearest-neighbour search in meaning space: encode the query, find the closest stored points, return them.

Worked example — three points: In a toy 2D meaning space, the photo of dogs in snow sits at \((0.9, 0.8)\). The caption "dogs running in snow" sits at \((0.88, 0.82)\) — gap 0.03, near-identical. The caption "elephant in the savanna" sits at \((-0.7, -0.6)\) — gap over 2. A query for the first caption returns the photo first by a huge margin. Near paraphrases cluster; unrelated topics separate. Sense-check: distances mirror meanings, so ranking by distance ranks by meaning.

Scope: Geometry assumes the encoders were trained on diverse enough pairs to shape every region. Dense everyday regions (pets, streets, food) are well shaped; sparse expert regions (rare cells, satellite minutiae) stay lumpy and unreliable.

Recap: Closeness is meaning — neighbours are answers. Encoders plus a similarity number make that operational next.

16.7.3 Encoders and similarity

A text encoder — a module that turns tokens into a numeric vector — and an image encoder — a module that turns pixels into a numeric vector — are trained together so their outputs are directly comparable. Similarity is then measured in the shared space. CLIP work uses cosine similarity on normalised vectors, with Euclidean distance as an option when vectors are not normalised.

Formalize — the two similarities: Let \(a \in \mathbb{R}^d\) be an image embedding and \(b \in \mathbb{R}^d\) be a text embedding, where \(d\) is the shared dimension and both vectors lie in the same space by construction. Cosine similarity is:

\[ \mathrm{cos}(a, b) = \frac{a^\top b}{\|a\|_2 \, \|b\|_2} \]

where \(a^\top b = \sum_{j=1}^{d} a_j b_j\) is the dot product and \(\|x\|_2 = \sqrt{\sum_j x_j^2}\) is the Euclidean length. Cosine is the cosine of the angle between the vectors: 1 means same direction, 0 means right angle (unrelated), -1 means opposite. For unit-length vectors with \(\|a\|_2 = 1\) and \(\|b\|_2 = 1\), this reduces to \(\mathrm{cos}(a, b) = a^\top b\) — just the dot product. Euclidean distance is:

\[ d(a, b) = \|a - b\|_2 = \sqrt{\sum_{j=1}^{d} (a_j - b_j)^2} \]

where small distance means high similarity. The verbal picture from the lecture is: similar meanings should point in similar directions, and normalised embeddings let angle carry the signal.

Why normalise? Without normalisation a long vector (confident, bright image) looks more similar to everything by dot product alone. Dividing by lengths removes magnitude and keeps direction — meaning — as the signal. For unit vectors the two measures agree in ranking: closer angle means smaller Euclidean gap too, since \(\|a - b\|_2^2 = 2 - 2\,a^\top b\).

Worked example — numbers: Let \(a = (0.6, 0.8)\) (image, already unit length since \(\sqrt{0.36+0.64} = 1\)) and \(b = (0.55, 0.84)\) (matching caption, length about 1.00). Dot product is \(0.6 \times 0.55 + 0.8 \times 0.84 = 0.33 + 0.672 = 1.002\), so \(\mathrm{cos}(a,b) \approx 1.00\) — near-identical direction. A mismatched caption \(c = (-0.8, 0.6)\) gives \(0.6 \times (-0.8) + 0.8 \times 0.6 = -0.48 + 0.48 = 0.0\) — right angle, unrelated. Euclidean gaps agree: \(\|a-b\|_2 \approx 0.06\) versus \(\|a-c\|_2 \approx 1.41\). Match scores 1.00, mismatch 0.00 — clean separation. Sense-check: tiny angle gives cosine near 1 and gap near 0, as geometry demands.

Assumption: Cosine assumes direction carries meaning and magnitude does not — true only when training normalises outputs. Scope: Use cosine on normalised embeddings (the CLIP default); use Euclidean when vectors are unnormalised or when magnitude is meaningful. Mixing the two without checking normalisation is a standard bug.

Picture arrows from one origin: the image arrow and its caption arrow nearly overlap (tiny angle), while the unrelated caption arrow points sideways. One-line takeaway: small angle, big similarity.

Pitfalls: Forgetting to normalise before dot-product ranking lets long vectors dominate. Reading cosine 0 as "opposite" — it means unrelated; opposite is -1. Comparing embeddings from different models or dimensions (512 vs 768) as if they share a space.

Recap: Two encoders, one space, angle as meaning — cosine on unit vectors is the working similarity. CLIP is the full-scale build of this idea next.

Exam note: Be ready to write both formulas, reduce cosine to a dot product for unit vectors, and compute a 2D numeric case showing a match near 1 and a mismatch near 0.

16.8 CLIP Training, Architecture and Zero-Shot Classification

16.8.1 Training data and objective

CLIP — Contrastive Language-Image Pretraining, a model that links images and text in one space — was introduced in 2021 by an OpenAI team. It trained on about 400 million image-text description pairs collected from the web. The scale was driven by a zero-shot goal: classify or retrieve without task-specific training samples.

Hook: How do you build a classifier for categories you have never trained on — sketch photos, new backgrounds, classes with zero labelled examples?

The training objective is simple in words. For a batch of images and captions, the correct image-caption pair should sit close together while incorrect pairings should sit far apart. That push-pull shapes the geometry from the previous section: diagonal matches pull together, off-diagonal mismatches push apart, and the whole space organises by meaning.

A concrete pair makes it vivid. Caption text such as two dogs running across a frosty field and a photo showing dogs running in snow should land near each other. The same photo and a caption such as an elephant in the savanna should land far apart. Diagonal matches pull together. Off-diagonal mismatches push apart — the batch matrix picture that returns in the loss section below.

Worked example — pull and push: Batch of 3: images dogs, dolphins, trees with captions in the same order. Before training, dogs-photo to dogs-caption cosine is 0.1 and to dolphins-caption is 0.15 (wrong order). After contrastive training, dogs-to-dogs rises to 0.75 while dogs-to-dolphins falls to 0.05 and dogs-to-trees to 0.02. Diagonal 0.75 beats every off-diagonal — correct pairing wins. Sense-check: training only reshaped positions, yet ranking flipped from wrong to right.

CLIP-style search lets a shopper type a plain description and get matching product photos with no manual tags — the shop never labelled "frosty dogs", yet the geometry finds them.

Scope: Web-scale pairs assume breadth beats cleanliness. The objective holds for everyday visual concepts abundant online and weakens for fine expert distinctions (cell types, signatures) where web captions lack the vocabulary — a limit revisited below.

Recap: 400 million pairs plus a pull-matches, push-mismatches objective buys a space that answers unseen classes. Two encoders build that space next.

16.8.2 Dual-encoder architecture

CLIP uses two parallel branches. The text branch uses a transformer to encode a caption. Input words become tokens, the transformer processes them, and the result is a text embedding vector. The image branch uses a visual encoder such as a vision transformer or a residual network to encode pixels into an image embedding vector. Both branches output 512-dimensional embeddings in the same space.

Formalize: Let \(t \in \mathbb{R}^{512}\) be a text embedding and \(v \in \mathbb{R}^{512}\) be an image embedding, where 512 is the shared width. Training adjusts both encoders so matched pairs give high \(\mathrm{cos}(v, t)\) and mismatched pairs give low values. Raw inputs stay different — words versus pixels — but the outputs share units and scale, so comparison is apples to apples: both are 512-long unit vectors in one meaning space.

After training, encoders can be used alone or together. Image-only use can support caption ranking (encode a new photo, compare against stored caption vectors). Text-only use can support image search (encode a typed query, compare against stored photo vectors). Joint use supports fresh image-text comparison. This reuse is part of why the design is handy in practice — one training run serves three retrieval directions.

Worked example — reuse: Store 1 million product photos as 512-vectors offline. Query "red canvas sneakers, side view" encodes to \(t \in \mathbb{R}^{512}\), normalised. Cosine against all stored \(v\) values takes one matrix multiply; top-20 sneakers return in milliseconds. No classifier was trained on "sneakers". Search works with zero sneaker labels. Sense-check: the text encoder placed the query in the sneaker neighbourhood learned from web pairs, so neighbours are sneakers.

Scope: Dual encoders assume each side alone carries enough signal. They hold for caption-level matching and weaken for tasks needing fine cross-modal reasoning (counting objects, reading text in images), where joint-attention models do better at higher cost.

Recap: Two towers, one 512-wide space, three retrieval directions for free. The batch loss that trains the towers is next.

16.8.3 Batch comparison and symmetric loss

At training time a batch holds several images, such as dogs, dolphins, and trees, plus their captions. Both embedding sets are computed on a common scale. Every image-text similarity is scored, often with cosine on unit vectors. The diagonal cells hold matched pairs and should show high values. Off-diagonal cells hold mismatches and should show low values. Training gives high weight to the diagonal and low weight elsewhere, forcing the model to pick the right caption among many.

Inference reuses the same comparison. Encode image and text, normalise, compute a matrix of scaled dot products as similarity, then apply a symmetric cross-entropy loss during training that works in both directions. One direction asks each image to find its text. The other asks each text to find its image. Training both ways gives embeddings that serve image-to-text and text-to-image matching.

The verbal picture from the lecture is: compute scaled dot products for similarity, then apply cross-entropy in both image-to-text and text-to-image directions to learn bidirectional matching.

Formalize — symmetric contrastive loss: Let \(S \in \mathbb{R}^{N \times N}\) hold similarities for \(N\) images and \(N\) texts, with \(S_{i,j}\) the scaled dot product of image \(i\) with text \(j\) (embeddings normalised, then divided by a temperature scale). With temperature \(\tau > 0\), row-wise softmax for image-to-text is:

\[ P^{I \to T}_{i,j} = \frac{\exp(S_{i,j} / \tau)}{\sum_{k=1}^{N} \exp(S_{i,k} / \tau)} \]

where \(P^{I \to T}_{i,j}\) is the predicted probability that image \(i\) matches text \(j\), \(\tau\) is a positive scale that sharpens (small \(\tau\)) or softens (large \(\tau\)) the distribution, \(N\) is batch size, and \(\exp\) is the exponential. Column-wise softmax over the same \(S\) gives \(P^{T \to I}_{i,j}\), the probability that text \(j\) matches image \(i\). The symmetric loss is the mean cross-entropy of both directions against identity targets: each image's true caption is position \(i\), each caption's true image is position \(i\). Softmax turns scores into probabilities that sum to one, and the highest probability picks the answer. Standard form uses a learnable temperature (often via a logit scale of \(1/\tau\)); the lecture's brief wording matches this standard usage with \(\tau\) as the softening scale.

Why both directions? Training image-to-text alone can leave text-to-image weak (captions cluster but images do not separate). Averaging both forces the space to work symmetrically — every image finds its caption and every caption finds its image.

Worked example — 3-by-3 batch with numbers: Let \(N = 3\) with \(S/\tau\) rows: dogs-image \([4.0, 0.5, 0.2]\), dolphins-image \([0.3, 3.8, 0.1]\), trees-image \([0.0, 0.4, 3.5]\). Row softmax for dogs: \(\exp(4.0) = 54.6\), \(\exp(0.5) = 1.65\), \(\exp(0.2) = 1.22\); sum \(57.5\); probabilities \([0.95, 0.03, 0.02]\). Dogs image picks caption 1 at 0.95 — correct. Cross-entropy loss for this row is \(-\log(0.95) \approx 0.05\) (near zero). A confused row like \([1.0, 1.0, 1.0]\) gives \([0.33, 0.33, 0.33]\) and loss \(-\log(0.33) \approx 1.10\). Training pushes every row from 1.10 toward 0.05, and likewise every column. Sense-check: sharp diagonal probabilities mean near-zero loss; flat rows mean high loss — loss measures diagonal confidence directly.

Scope: The batch loss assumes each batch holds at most one correct caption per image. It holds for deduplicated web batches and weakens when near-duplicate captions collide in one batch (two valid "dog" captions force each other down) — large batches dilute but never fully remove this noise.

Pitfalls: Forgetting the temperature: raw dot products without \(\tau\) scaling give flat or spiky softmaxes that train poorly. Training one direction only and expecting symmetric retrieval. Reading \(P^{I \to T}\) as a calibrated real-world probability — it ranks within the batch, nothing more.

Recap: Score every pair, softmax rows and columns with temperature, push diagonals to probability 1 both ways. That bidirectional push is what makes zero-shot search work next.

16.8.4 Zero-shot classification, prompt wording and limits

Zero-shot classification — correct prediction with no explicit training examples for the target task — is a headline CLIP ability. Class names such as plane, car, dog, and bird become prompts such as a photo of a plane, a photo of a car, a photo of a dog, and a photo of a bird. The test image is encoded once. Each prompt is encoded. Similarities plus softmax give probabilities. The top probability names the image, so a dog photo scores highest with a photo of a dog.

Worked example — four prompts: Dog photo encodes to \(v\). Prompt similarities (cosine): "a photo of a plane" 0.05, "a photo of a car" 0.08, "a photo of a dog" 0.62, "a photo of a bird" 0.11. Softmax over the four (with temperature) gives roughly \([0.12, 0.13, 0.60, 0.15]\). Winner is "a photo of a dog" at 0.60 — correct with no dog training labels. Sense-check: the dog prompt outscores the rest by 0.5 in cosine, so any monotone softmax must crown it.

Wording matters a lot. A rich caption such as two dogs running on a frosty field is not the same string as a photo of a dog, and order and choice of words shift vectors. Language templates and multiple prompts help — averaging "a photo of a dog", "a picture of a dog", "a drawing of a dog" stabilises the class vector — with multiple encodings per class, at real compute cost. Comparisons against a residual baseline with 101 layers showed zero-shot CLIP ahead across many sets and shifts, from sketches to varied backgrounds to ImageNet and its second version. The training sweat pays off in breadth: robustness to style and background shifts is where zero-shot shines.

Limits are fair to state too. On narrow expert tasks with fine supervision, CLIP can trail specialist models. Examples named include signature matching, tumour versus non-tumour cell calls, handwritten digit sets, and satellite views where tiny errors cost a lot. Noisy web pairs may not capture the fine distinctions those tasks need. Counting prompts such as a photo of three objects versus four or five objects can also fail. CLIP-style shared codes can even guide image generation in diffusion setups that start from noise and refine step by step, but CLIP alone is not enough there.

Q: In the cross-entropy part, what do the image and text probability terms mean? Is it a dot product of image and text? What does capital T mean in the softmax view? A: Entropy measures impurity with sums of \(p \log p\) form, while cross-entropy compares predicted and target distributions with \(p \log q\) form in each direction, image-to-text and text-to-image. The dot product or scaled dot product supplies the raw similarity \(S_{i,j}\) that softmax turns into probabilities \(P^{I \to T}\) and \(P^{T \to I}\). Softmax matters because it maps scores to values that sum to one, so the top value can serve as the chosen caption — the worked 3-by-3 numbers above show exactly this. Capital \(T\) here is just the transpose/direction label (image-to-text vs text-to-image), not a new variable. Fine print of the paper symbols was left for close paper reading with code and examples, which is honest advice: notation varies across implementations.

Exam note: Zero-shot prompting with "a photo of" plus softmax probabilities is a likely conceptual plus numerical question — practise the 4-prompt worked numbers and the row-softmax formula with temperature.

Recap: Prompt each class, encode once, softmax similarities, take the top — breadth from web scale, limits on expert detail. ALIGN tests how far noisier, larger data pushes the same design.

16.9 ALIGN Learning from Noisy Web Pairs

16.9.1 Data idea and why noise helps

ALIGN — A Large-scale ImaGe Noisy-text Embeddings, a dual-encoder vision-language model — differs from CLIP mainly in data curation. Instead of carefully written captions plus language templates, it learns from a very large web collection of images with alternate text, about one billion pairs, with minimal cleaning. Vague, short, or loosely related descriptions are kept on purpose.

Hook: Real users type "Eiffel Tower snow", not "a snow-covered wrought-iron lattice tower at dusk" — so why train on elegant sentences nobody types?

That choice simulates real queries. A user may write Eiffel Tower and snow rather than a full sentence about a snow-covered tower. Training on noisy short strings builds tolerance for that style: the model learns that fragments, brand names, and loose associations still point somewhere. Volume carries reliability: many loose pairs together still teach stable links, because random noise cancels while repeated true associations accumulate over a billion examples.

Worked example — noise cancelling: The phrase "Eiffel Tower" appears with 50,000 tower photos (signal) plus 2,000 unrelated photos whose alt-text happened to mention Paris (noise). The tower direction gets pulled 50,000 times toward tower pixels and only 2,000 times elsewhere. Signal beats noise 25-to-1 by repetition. Sense-check: random wrong pairs point in random directions and average out; true pairs point consistently and add up.

Size About 400M curated pairs About 1B noisy alt-text pairs
Style Fuller captions, prompt templates Short fragments, raw alt-text
Cleaning Filtered for quality Minimal — noise kept deliberately
Strength Cleaner supervision per pair Better match to real terse queries

When to pick which style: clean caption tasks — CLIP curation; raw web-query tolerance — ALIGN noise.

Scope: Noisy training assumes volume overwhelms error. It holds at billion-pair scale with mostly-relevant alt-text and breaks for rare concepts with few pairs, where a handful of wrong labels can dominate.

Recap: Keep the noise, grow the data, match how people really type. The encoder design stays deliberately simple next.

16.9.2 Shared space and dual encoder

The core is again a simple dual encoder, not a complex fusion net. An image encoder and a text encoder train together so matched pairs land near each other. Paired text acts as fine-grained labels for images — every caption is a free, noisy class tag. Scale plus simplicity is the claimed contribution: at web scale, plain two-tower learning becomes highly capable, no cross-attention needed.

Formalize: Let \(v \in \mathbb{R}^d\) be an image code and \(t \in \mathbb{R}^d\) be a text code in shared width \(d\). Training raises \(\mathrm{cos}(v, t)\) for true pairs and lowers it for other pairs in the batch, same push-pull as CLIP but over far noisier pairs. In symbols, for a batch the objective rewards large \(\mathrm{cos}(v_i, t_i)\) on the diagonal and small \(\mathrm{cos}(v_i, t_j)\), \(j \ne i\), off it. Simplicity is the point: two towers, one cosine, web-scale repetition.

Worked example — fine-grained labels for free: Photo of Lombard Street carries alt-text "Lombard Street". No human labelled "hairpin road" or "San Francisco" — yet across thousands of such pairs the text tower learns that "Lombard", "hairpin", and "crooked street" queries all land near those photos. Each alt-text is a weak label; a billion weak labels equal strong coverage. Sense-check: labels need not be clean when they are plentiful and roughly right.

Scope: Dual encoders assume caption-level alignment suffices. They hold for retrieval by overall scene meaning and weaken for precise grounding (which pixel is which word) where joint models help.

Recap: Same two towers, noisier school, same cosine lesson — simplicity at scale. Retrieval behaviour shows what that schooling buys.

16.9.3 Retrieval behaviour and examples

Three behaviours were shown. Text-to-image: a night spider description retrieves the spider photo; a query naming a painter plus starry night pulls starry-style paintings; Lombard Street pulls matching street views; seagull in front of pulls gull scenes before landmarks such as a tall Paris tower and a famous bay bridge; heavy rain pulls rainy scenes with some dataset bias, which is acceptable when outputs stay valid. Image-to-text: a haystack house photo pulls related dwelling descriptions; a high-heel image pulls related fashion text; flower and butterfly images pull matching words. Joint text-plus-image: Eiffel Tower plus snow pulls a snowy tower view — the text edits the image query.

Worked example — joint query: Image query is a summer Eiffel Tower photo at \(v\). Text "snow" encodes to \(t_{snow}\). The joint query \(q = v + t_{snow}\) (normalised) shifts the point toward the snowy-tower neighbourhood. Stored snowy tower photo at \(v_{snow}\) gives \(\mathrm{cos}(q, v_{snow}) = 0.81\) versus summer-only neighbour at 0.55. Joint query returns the snowy view first. Sense-check: adding the snow direction must favour snowy stored items — vector arithmetic edits meaning.

The takeaway is tolerance for short vague inputs. The code captures overall phrase meaning well enough to return useful neighbours even when the query lacks background, foreground, or detail. Ambiguity remains, partly from data bias (rainy scenes skew to certain cities), but results stay on topic — acceptable when outputs stay valid, as the lecture notes.

Picture a query dot labelled "seagull in front of" landing in a cluster of gull photos, with tower and bridge photos as neighbouring clusters at larger distances. One-line takeaway: vague words still land in the right neighbourhood.

Pitfalls: Reading dataset bias as model understanding — rainy-scene skew reflects training photos, not meteorology. Expecting precise attribute binding (which gull, which tower) from a model trained on loose alt-text. Forgetting that joint text-plus-image arithmetic is approximate, not exact editing.

Recap: Noisy schooling buys tolerance: terse text, bare images, or both together all retrieve sensibly. Text-only neural retrieval faces the same meaning problem next, without any pixels at all.

Noisy alt-text training matches how people actually label web photos, so web image search benefits directly — the deployed payoff of this section.

16.10 Neural Retrieval and the Semantic Gap

16.10.1 Motivating example

A semantic gap — the divide between spelled words and meant ideas — breaks keyword search. Query text is best budget smartphones. Two stored items are D1 about affordable mobiles under 20K and D2 about history of smartphones. A reader expects D1 first. Yet budget never appears in D1 as a string, only affordable does. Spelling match alone cannot see that budget and affordable point to the same idea.

Hook: The best answer contains none of your query words — should the search engine return it first or miss it entirely?

The same point returns in plain words: neural search should grasp meaning, not just spelling. Both query and document become vectors in a meaning space, and closeness of numbers signals closeness of ideas. Budget and affordable must land near each other in that space even though their letters differ completely.

Worked example — the budget test: Query Q = "best budget smartphones". D1 = "affordable mobiles under 20K, great value" (no word "budget"). D2 = "history of smartphones, from early models to today" (has "smartphones"). Keyword overlap: Q–D1 shares 0 content words; Q–D2 shares 1 ("smartphones"). Keyword ranking returns D2 first — wrong. Meaning vectors: Q near the cheap-device region, D1 in the same region, D2 in the history region. Meaning ranking returns D1 first — right. Sense-check: the reader wanted cheap phones, not phone history, so the meaning answer matches intent.

Scope: The gap bites hardest on synonyms and paraphrases (budget/affordable, mobile/phone). It assumes the meaning space actually learned those equivalences; rare jargon absent from training stays gapped.

Recap: Spelling overlap is a proxy for meaning that fails on synonyms — vectors must carry the meaning directly. Traditional matching's full failure list is next.

16.10.2 Why traditional matching falls short

Traditional matching looks for plain keyword overlap and misses sense. Budget retrieves budget but not affordable or cheap. Queries are also short, often two or three tokens, while documents run hundreds of words long. Short inputs carry little context and can even add confusion when expanded — adding synonyms blindly drifts the query. Modern uses such as recommendation, RAG-style assistants, and large shop or web engines need both context and intent, not keywords alone.

A good retrieval model is expected to show semantic understanding, strength on rare inputs such as an uncommon vaccine name, strength on collection variants such as heart attack versus cardiac arrest and other clinical terms, steadiness across input lengths, tolerance for errors and spelling slips including phonetic fixes, and sensitivity to context such as health-related apple meaning fruit rather than a device brand. No traditional model meets that full list. That gap is where neural methods help, though the expectations apply to any fielded system — neural or not, these are the acceptance tests.

Think of the librarian analogy from the lecture. Traditional search is like a librarian who checks titles for exact words. Neural search is like a librarian who has read the books and knows what they mean. The second librarian can answer by content, not just by title spelling — and can tell fruit-apple queries from brand-apple queries by surrounding words.

Intuition — the six acceptance tests: (1) synonyms: budget finds affordable; (2) rare terms: a new vaccine name still retrieves; (3) variants: heart attack finds cardiac arrest; (4) length robustness: 2-word queries and 500-word documents compare fairly; (5) typo tolerance: "smatphone" still finds smartphones; (6) context: apple with orchard goes to fruit, apple with charger goes to the brand. Memorise these six — they organise every neural claim in this lecture.

Worked example — apple disambiguation: Query A "apple orchard harvest" and Query B "apple charger cable" share the word apple. Keyword search returns overlapping lists. Contextual vectors place A near fruit documents (orchard, harvest pull fruity) and B near device documents (charger, cable pull technical). Same word, different neighbourhoods — context splits them. Sense-check: surrounding words steer the vector, so identical spellings diverge by company kept.

Scope: Neural models assume training saw enough contexts to split senses. They hold for common polysemy (apple, bank) and weaken for brand-new senses or highly specialist jargon with few examples.

Pitfalls: Assuming neural search "understands" like a human — it matches distributional patterns, and adversarial paraphrases still fool it. Dropping keyword signals entirely: production systems keep BM25 alongside dense scores because exact matches (codes, names) still matter.

Recap: Six tests — synonyms, rare terms, variants, lengths, typos, context — define the bar keyword methods cannot clear. The paraphrase exercise makes the first test hands-on next.

16.10.3 Query paraphrase exercise

Q: For the query cheap air tickets, what are other ways users may ask the same thing? A: Options include economical flights, low-fare flights, budget airlines, and affordable flights. All four should return similar results, such as fare pages or airline lists. Keyword-only matching would treat each spelling as a different need (four different rankings), while meaning-based matching treats them as one need (one shared ranking). Several students converged on these same four paraphrases, which confirms the confusion is systematic, not individual — the vocabulary-mismatch problem is the norm for short commerce queries.

Worked example — four spellings, one need: Five typed queries: "cheap air tickets", "economical flights", "low-fare flights", "budget airlines", "affordable flights". Keyword overlap between the first and the others is at most 1 word ("flights" once, else 0). A keyword engine returns five different lists. Meaning vectors for all five cluster within cosine 0.85+ of each other, so one ranking serves all. One intent, one ranking — paraphrase-invariant. Sense-check: travellers mean the same trip however they phrase thrift, so identical results are correct behaviour.

Exam note: Budget versus affordable and cheap-tickets versus economical-flights paraphrases are ideal small examples for a meaning-versus-spelling question — practise writing both with expected rankings.

Recap: Paraphrases prove the gap is everyday, not exotic — and set up the two-stage machinery that closes it at web scale next.

16.11 Retrieve-and-Rerank Pipeline and Text Vectors

16.11.1 Two-stage pipeline

Neural search at web scale cannot run a heavy model over millions of items per query. The fix is retrieve then rerank. First, use a fast first stage such as BM25 or dense retrieval to pull a candidate set, say a thousand items from millions. Next, encode query and candidates with a deep encoder such as BERT into dense vectors. Then compute relevance scores between query vector and each document vector. Finally, reorder the thousand and show the top 10 or 20.

Hook: A heavy reader model takes 50 milliseconds per document — times 10 million documents, your query returns next week. How do real engines answer in half a second?

Document vectors are usually built offline — the whole collection is encoded once and stored. Query vectors are built live at search time, much like index building versus query serving in classic setups. The heavy learning sits in the encode-plus-score-plus-rerank steps. Most deployed engines follow this two-level design to bound time and space cost: cheap breadth first, expensive depth only on survivors.

Procedural spine: Purpose is web-scale neural ranking within latency budget. Inputs are the query plus a million-scale collection; outputs are top 10–20 items. Steps: (1) first-stage retrieval — BM25 or light dense scan returns ~1000 candidates; (2) encode — deep encoder embeds query live and looks up precomputed candidate vectors; (3) score — compute query-document similarities; (4) rerank — sort candidates and cut to top-k. Complexity falls from \(O(N)\) heavy encodings to \(O(1000)\) light scorings plus one query encoding.

Worked example — latency arithmetic: Collection \(N = 5{,}000{,}000\). Heavy scorer costs 20 ms per pair. Full scan costs \(5{,}000{,}000 \times 20\) ms \(\approx\) 27 hours per query — impossible. First stage returns 1000 candidates in 80 ms via index lookup. Scoring 1000 pairs costs \(1000 \times 20\) ms \(= 20\) s — still slow, so production uses faster dot-product scoring at ~0.01 ms per pair: 10 ms. Total \(\approx\) 80 + 10 + query-encode 30 \(= 120\) ms. Answer in ~0.1 s instead of 27 hours. Sense-check: the thousand-fold prefilter plus precomputed vectors is where all the savings live.

The verbal picture from the lecture is: generate candidates with a fast model, encode both sides with a deep model, score matches, and rerank to top results.

Scope: Two stages assume the first stage recalls the good answers (they survive into the 1000). It holds when BM25-plus-light-dense has high recall and breaks when the answer uses entirely different vocabulary with no bridge — the semantic-gap failure returns at stage one.

Pitfalls: Reranking only the top 1000 and claiming global optimality — answers ranked 1001+ are invisible. Encoding documents live per query instead of offline. Judging the pipeline by reranker quality alone while the first stage silently drops recall.

Recap: Cheap recall, expensive precision — candidates offline-indexed, query live, rerank the survivors. The vectors being ranked come in sparse and dense flavours next.

16.11.2 Sparse text vectors

An embedding — a numeric vector standing for text — can start sparse. A one-hot vector — a 0/1 vector marking word presence — puts 1 when a word occurs and 0 otherwise. A bag-of-words vector — a count vector over the vocabulary — stores frequencies instead of mere presence. A TF-IDF vector — term frequency times inverse document frequency — weights a term by its strength in the item times its rarity across the collection.

Formalize: Let \(V\) be vocabulary size. A document \(d\) becomes \(x \in \mathbb{R}^{V}\). One-hot sets \(x_j = 1\) if term \(j\) occurs else \(0\), where \(j\) indexes the vocabulary. Bag-of-words sets \(x_j = \mathrm{count}(j, d)\), the raw frequency of term \(j\) in \(d\). TF-IDF sets:

\[ x_j = \mathrm{tf}(j, d) \times \mathrm{idf}(j) \]

with \(\mathrm{idf}(j) = \log(N / \mathrm{df}_j)\) where \(\mathrm{tf}(j, d)\) is the frequency of term \(j\) in \(d\), \(N\) is collection size, \(\mathrm{df}_j\) is the count of items containing \(j\), and \(\log\) is the natural log unless stated otherwise. The verbal picture from the lecture is: term frequency tells how important the term is in the item, while inverse document frequency tells how rare it is across items — frequent-here plus rare-everywhere means discriminative.

Worked example — TF-IDF numbers: Collection \(N = 10{,}000\). Term "phone" appears in 1,000 docs: \(\mathrm{idf} = \log(10000/1000) = \log(10) \approx 2.30\). Term "the" appears in 9,900 docs: \(\mathrm{idf} = \log(10000/9900) \approx 0.01\). Document D mentions "phone" 3 times: \(x_{phone} = 3 \times 2.30 = 6.90\). It mentions "the" 5 times: \(x_{the} = 5 \times 0.01 = 0.05\). "phone" outweighs "the" 138-to-1 despite fewer mentions. Sense-check: rarity weighting must crush stopwords — 0.05 vs 6.90 confirms it.

Picture a very long mostly-zero row with rare spikes: positions for "the" and "and" sit near zero while "phone" and "affordable" spike tall. One-line takeaway: spikes mark what makes this document different.

Scope: Sparse vectors assume vocabulary overlap signals relevance. They hold for exact-term needs (codes, names, quoted phrases) and break on synonyms — the gap from the previous section — because "phone" and "mobile" are different axes with zero interaction.

Recap: Presence, counts, rarity-weighted counts — sparse vectors score spelling overlap well and meaning not at all. The tie that proves it is next.

16.11.3 Why counts tie and meaning breaks the tie

Take query budget phone with D1 affordable phones and D2 history of phones. Tokens are budget, phone, affordable, history. Sparse presence vectors give the query and both documents a 1 for phone, so both tie on the shared word while budget matches neither stored text. Retrieval cannot pick a winner from counts alone.

Intuition: Two students both mention "phone" once — one means cheap handsets, the other means phone history. Counting the word "phone" ties them; understanding the surrounding words breaks the tie.

Dense meaning vectors fix this with two sense axes: cheapness and device. The query budget phone scores high on both, such as 0.5 for cheapness and 0.53 for device in the lecture sketch. D1 with affordable plus phone scores high on both. D2 with history plus phone scores low on cheapness but high on device. Cosine on normalised vectors then ranks D1 above D2 with no tie. The location in space now carries sense, not just spelling overlap.

Formalize — tie broken: Let \(q\) be the query vector, \(d_1\) D1, \(d_2\) D2 (normalised). Then \(\mathrm{cos}(q, d_1) > \mathrm{cos}(q, d_2)\) because \(d_1\) aligns on both axes while \(d_2\) aligns on one. With the sketch numbers, \(q = (0.5, 0.53)\), \(d_1 = (0.48, 0.55)\), \(d_2 = (0.05, 0.60)\): \(\mathrm{cos}(q,d_1) \approx 0.999\) while \(\mathrm{cos}(q,d_2) \approx 0.78\). The verbal picture from the lecture is: with normalised vectors, cosine is the natural similarity because lengths match and only angles differ.

Worked example — full tie-break arithmetic: Normalise the three sketch vectors to unit length, then dot: \(q \cdot d_1 = 0.5 \times 0.48 + 0.53 \times 0.55 = 0.24 + 0.29 = 0.53\) before normalisation scaling, versus \(q \cdot d_2 = 0.5 \times 0.05 + 0.53 \times 0.60 = 0.025 + 0.318 = 0.343\). After dividing by lengths the gap persists: \(d_1\) outscores \(d_2\) by over 0.2 in cosine — decisive, no tie. Sense-check: shared cheapness axis contributes ~0.24 to D1 and ~0.02 to D2 — the meaning axis is the whole margin.

Scope: The two-axis sketch assumes cheapness and device-ness separate cleanly. Real embeddings use hundreds of entangled axes, but the principle — alignment on more shared sense directions wins — carries over exactly.

Exam note: The four-token tie plus the two-axis fix is a compact numerical to expect — practise the presence-vector tie (both score 1 on "phone") and the cosine break (D1 above D2).

Recap: Counts tie on shared spellings; sense axes break the tie by alignment. The embeddings behind those axes — static, contextual, and architectural — are next.

16.12 Embeddings and Neural Architectures for Search

16.12.1 Static versus contextual embeddings

Static embeddings — one fixed vector per word from models such as word2vec, GloVe, or fastText — give the same code wherever the word appears. The word apple gets one vector, such as \((5.33, 2.10)\) in a toy sketch, whether the sense is fruit or device. That is simple but blind to context.

Contextual embeddings — sense-sensitive vectors from models such as BERT, sentence transformers, or ELMo — compute the code from surrounding words. The same string gets different vectors in different sentences. The classic pair is I deposited money in the bank versus I sat at the river bank. The first bank points to a financial place. The second points to land by water. Static codes merge them. Contextual codes split them.

Hook: One spelling, two meanings — "bank" — so should the machine store one vector or two?

Worked example — bank split: Static: \(v(\text{bank}) = (2.0, 1.0)\) in both sentences — money and river queries both match both sentences equally, confusion guaranteed. Contextual: \(v(\text{bank} \mid \text{money, deposited}) = (2.8, 0.4)\) (financial corner) versus \(v(\text{bank} \mid \text{river, sat}) = (0.3, 2.9)\) (riverside corner). Query "open a bank account" lands at \((2.7, 0.5)\): cosine to the financial bank \(\approx 0.99\), to the riverside bank \(\approx 0.3\). Context splits what spelling merges. Sense-check: neighbours decide meaning, so identical strings diverge correctly.

Dimension Static (word2vec, GloVe, fastText) Contextual (BERT, ELMo)
Code per word One, fixed Many, per context
Apple fruit vs brand Merged Split by neighbours
Cost Cheap lookup Encoder run per sentence
Best for Stable terminology Polysemy, phrases, queries

When to pick which: large-scale first-stage with stable vocab — static; reranking and short ambiguous queries — contextual.

Scope: Contextual models assume enough surrounding words to disambiguate. They hold for sentences and paragraphs and weaken for single-word queries ("apple" alone), where there is no context to use — query expansion or click signals must help.

Recap: One vector per spelling versus one vector per usage — context splits senses. The networks that compute these vectors range from shallow to recurrent next.

16.12.2 Shallow, deep, feedforward, convolutional and recurrent forms

A shallow network — input plus one hidden layer plus output — is a light model. A deep network — input plus many hidden layers plus output — stacks more transforms. Each node takes inputs, applies weights and an activation function, and passes an output onward. A feedforward network — flow in one direction from input to output with no loops — can be shallow or deep. A convolutional network — filters that learn local patterns — picks up useful phrases such as machine learning as one unit in text. A recurrent network — word-by-word processing with a carried memory of what came before — tracks order. A long short-term memory network — an improved recurrent form — handles longer links more stably via gates that keep or drop memory.

Intuition: Think of reading styles: feedforward is glancing at a bag of words, convolutional is spotting familiar phrases with a highlighter, recurrent is reading left to right with notes in the margin, LSTM is the same reader with a better notebook that does not fade after ten pages.

Worked example — "machine learning" as a unit: Bag-of-words sees "machine" + "learning" separately and confuses "learning machine" (a studious robot?) with "machine learning". A convolutional filter of width 2 learns the pair as one pattern: window ["machine", "learning"] fires 1.0, window ["learning", "machine"] fires 0.1. A recurrent net reading left to right carries "machine" in memory when "learning" arrives, scoring the ordered pair high. Order-aware models separate the phrase from its reversal; bags cannot. Sense-check: meaning lives in order, so order-blind codes must fail this pair.

Scope: Each form assumes its bias fits the task: convolutions assume local phrases matter; recurrence assumes order matters; depth assumes data suffices to train it. Shallow feedforward holds for simple topical matching; long-range reasoning needs attention-based depth instead.

Recap: Depth adds transforms, convolutions add phrase-spotting, recurrence adds order memory with LSTM stabilising it. Attention generalises all three next.

16.12.3 Attention, transformers and autoencoders

Self-attention — weighting each word by its links to all other words in parallel — lets a model give the right focus per sentence. Models such as BERT and GPT use this idea from the attention-is-all-you-need line of work. A tiny pair shows why it matters. In an animal did not cross the road because it was tired, it points to the animal. In an animal did not cross the road because it was wide, it points to the road. Same word, different focus. Attention learns that shift — tired pulls "it" toward animal, wide pulls it toward road.

An autoencoder — a net that learns its own compact codes — replaces hand-built TF-IDF or BM25 features with learned ones. It has three parts: encoder, latent space, decoder. The encoder squeezes input, such as four units to three to two, into a small dense vector. The latent code should hold a meaningful summary. The decoder rebuilds the input from that code. Picture condensing a ten-page document into two sentences, then asking a friend to rebuild ten pages from those two. When the rebuild lands near the start, the two-sentence code was a good summary — that is the lecture's own analogy, and it is exact: reconstruction error trains the compressor. Variants include variational autoencoders and denoising autoencoders, the latter suiting noisy queries with spelling slips (trained to rebuild clean text from corrupted input). The pick follows the task: noisy input favours denoising forms.

Formalize — autoencoder contract: Let \(x \in \mathbb{R}^n\) be the input (for example a sparse term vector). Encoder \(E: \mathbb{R}^n \to \mathbb{R}^m\) with \(m \ll n\) gives \(z = E(x)\), the latent code. Decoder \(D: \mathbb{R}^m \to \mathbb{R}^n\) gives \(\hat{x} = D(z)\). Training minimises rebuild error \(\|x - \hat{x}\|_2^2\) over the collection. The squeezed \(z\) becomes the learned embedding — TF-IDF hand-design replaced by learned compression.

Worked example — 4-3-2 squeeze: Input \(x = (1, 0, 3, 2)\) (counts for four terms). Encoder maps to 3 units \((0.8, 1.9, 0.2)\), then to latent \(z = (1.4, 0.9)\) in \(\mathbb{R}^2\). Decoder rebuilds \(\hat{x} = (0.95, 0.05, 2.9, 2.1)\). Error is \((0.05)^2 + (0.05)^2 + (0.1)^2 + (0.1)^2 \approx 0.025\) — tiny. Two numbers carry the four-number content. Sense-check: near-zero rebuild error proves the 2D code kept what mattered. A denoising twin trained on corrupted \((1, 0, 0, 2)\) (dropped the 3) still rebuilds near \((1, 0, 3, 2)\) — typo tolerance learned, not programmed.

Picture attention as a spotlight each word shines on the others: in the tired-sentence the "it" spotlight lands on "animal"; flip one word to "wide" and the spotlight swings to "road". One-line takeaway: focus follows meaning, computed in parallel.

Scope: Attention assumes enough data and compute to learn pairwise links — powerful but hungry. Autoencoders assume rebuildable structure; they hold for topical compression and weaken when fine distinctions (negation, numbers) vanish in the squeeze.

Pitfalls: Treating attention weights as explanations — they show focus, not reasoning. Squeezing too hard (tiny \(m\)) destroys the distinctions retrieval needs. Using plain autoencoders on noisy queries instead of denoising variants.

Recap: Attention focuses by pairwise links; autoencoders learn codes by rebuild pressure. Twin networks apply the same-encoder idea to pair comparison next.

16.12.4 Siamese nets and the retrieval link

A Siamese network — twin subnets joined by shared weights, named after joined twins — compares two inputs with the same model. Phone face unlock is the stock example. Stored face traits are on file. A fresh camera image arrives. Both pass through identical nets with identical weights. Feature vectors emerge. A similarity score decides same or not. This is not one-to-millions airport search. It is one-to-one check of stored versus query face — verification, not identification across crowds.

Intuition: Think of weighing two parcels on the same scale. One scale, same calibration, comparable numbers — two different scales could disagree even on identical parcels. Shared weights are the shared scale.

The retrieval link is direct. Query-to-document comparison uses the same shared-weight idea: encode both sides the same way, then score closeness. CLIP's two towers are the fraternal-twin version (different architectures, shared space); a Siamese query-document scorer is the identical-twin version (same BERT both sides, shared weights). Up to this point every method retrieves and ranks items already in the store. The next step asks whether the system can also write the answer.

Worked example — face check numbers: Stored face vector \(s = (0.7, 0.7)\) (unit length), fresh photo \(q = (0.68, 0.73)\). Cosine is \(0.7 \times 0.68 + 0.7 \times 0.73 = 0.476 + 0.511 = 0.987\) — above a 0.9 threshold, same person, unlock. An impostor \(r = (-0.7, 0.7)\) gives \(0.7 \times (-0.7) + 0.7 \times 0.7 = 0.0\) — different person, stay locked. Sense-check: same face means tiny angle; different faces mean large angle — thresholding cosine decides correctly.

Twin nets suit face unlock, signature check, and near-duplicate image checks where the pair question is same or not.

Scope: Siamese checks assume the pair question is verification (is this the claimed item?). They hold for one-to-one checks and break for open one-to-many search without extra indexing — ranking millions by pair-scoring each is too slow without the two-stage pipeline.

Recap: Same net both sides, comparable vectors, thresholded similarity — the pair-comparison engine inside modern retrieval. Generative retrieval next asks that engine to also compose prose.

16.13 Generative Retrieval, RAG and Conversational Search

16.13.1 From ranked lists to written answers

Generative retrieval — answering with composed language rather than only a ranked list — changes the output contract. Traditional output says here are the documents, you read them. Generative output gives a direct answer in human-readable form. Keyword plus dense methods sit under the first. Large language models sit under the second. Web links versus chat answers is the everyday contrast.

Hook: Ten blue links or one direct paragraph — when is the paragraph better, and when is it dangerous?

Ranked lists still win where sources must be checked. Tumour imaging is the case raised: slices show where a mass starts and ends, and depth follows from slice count. A sentence claiming 5 mm depth cannot replace the slices a clinician must view — the measurement lives in the images, and a wrong number harms. Legal material and citation-heavy study behave the same way. Even chat models now attach citations that map each claim to a source, yet high-stakes work still returns to the underlying items. In short, use prose answers for speed and lists for proof.

Worked example — tumour depth: CT stack shows the mass on slices 12–16, each slice 1 mm apart: depth is \(16 - 12 + 1 = 5\) slices \(\approx\) 5 mm, verifiable by scrolling. A chat answer "depth 5 mm" states the same number but hides the slice evidence. A radiologist trusting the sentence without opening slices cannot catch a miscounted boundary. Sentence for speed, slices for proof — the list (slices) stays mandatory. Sense-check: numbers that decide treatment must be recheckable at the source.

Scope: Generative answers assume the question wants synthesis, not evidence inspection. They hold for how-to, overview, and draft questions, and break for diagnostic, legal, and scholarly claims where each assertion needs its source open.

Recap: Prose for speed, lists for proof — high stakes keep the sources. RAG is the architecture that serves both at once next.

16.13.2 RAG architecture and vector stores

RAG — Retrieval Augmented Generation, a retrieve-attach-generate loop — has three moves. Retrieval finds relevant chunks from a vector store. Augmentation attaches those chunks to the user question as context. Generation uses a large language model to write a grounded summary.

Procedural spine: Purpose is grounded prose with checkable sources. Inputs are the user question plus a document collection; outputs are an answer plus cited chunks. Steps: (1) chunk and embed every document offline into a vector database; (2) embed the live question with the same model; (3) retrieve top-k chunks by vector similarity; (4) augment — concatenate question plus chunks into one prompt; (5) generate — the language model writes the answer from that context. Rationale: the retriever supplies facts, the generator supplies fluency, and citations bind them.

A full pass looks like this. Knowledge items such as PDFs, word files, web pages, and tables form the document space. An example question is what are the benefits of renewable energy. Each document is embedded with a model such as BERT and stored in a vector database — a store built for millions of dense vectors with fast nearest-neighbour lookup. The live question goes through the same embedding model into a query vector. Vector comparison pulls top chunks. Question plus chunks go to a model such as Llama, GPT, or Gemini, which reads the context and returns a summary to the user.

Named stores include FAISS from Meta for similarity search, Pinecone, ChromaDB, and Milvus. Small laptop work often uses FAISS or ChromaDB with no extra cost or infra. Pinecone and Milvus lean on hosted or cloud setups with cost and ops needs.

Worked example — renewable-energy pass: Store holds 2,000 manual chunks as BERT vectors in ChromaDB. Query "benefits of renewable energy" embeds to \(q\). Top-3 chunks retrieved: C1 (solar cost falls 80 percent since 2010), C2 (wind now cheapest new power in many grids), C3 (air-quality gains). Prompt becomes question + C1–C3. The generator writes "Solar costs fell ~80 percent since 2010; wind is cheapest new capacity in many grids; both cut air pollution [C1][C2][C3]." Grounded summary with three retrievable citations. Sense-check: every claim traces to a chunk id — delete the chunks and the claims must go too.

Scope: RAG assumes the store holds the answer. It holds for manual-grounded, report-grounded, and archive-grounded questions, and breaks for questions beyond the collection — then the generator must say so, not invent.

Pitfalls: Embedding questions with a different model from documents silently breaks similarity. Chunking too large drowns the answer in irrelevant context; too small splits evidence across chunks. Skipping citations turns RAG back into ungrounded generation.

Recap: Embed once, retrieve top chunks, attach, generate with citations — fluency grounded in retrieval. Conversation adds history to the same loop next.

Support bots over manuals and paper QA over reports both follow this attach-then-write shape.

16.13.3 Conversational search and grounded answers

Conversational retrieval — multi-turn search that keeps history — differs from one-shot search where each query stands alone. A first question asks who is the CEO of a firm. A follow-up asks how old is he. He resolves to that CEO from history with no restating. A laptop request that returns three options followed by which of these has the longest battery stays within those three. Rewriting with context happens behind the scenes — the engine expands "he" and "these" before retrieval.

A chat-style pipeline has four stages: prompt understanding, retrieval, reasoning, and answer generation. The retriever fetches top passages with dense or BM25 methods. The language model reads question plus passages and drafts the reply. A grounded response — an answer where each claim traces to retrieved evidence — is the goal. Ungrounded generation — text without tied evidence — is where hallucination grows. That is why high-stakes flows keep the retrieved list alongside the prose.

Worked example — pronoun resolution: Turn 1: "Who is the CEO of Firm X?" retrieves profile chunk naming Ana Rao; answer "Ana Rao". Turn 2: "How old is he?" — naive retrieval searches "how old is he" and fails. Context-aware rewrite produces "How old is Ana Rao (CEO of Firm X)?" which retrieves the bio chunk stating age 52. History-aware rewrite returns 52; history-blind returns noise. Sense-check: pronouns carry no retrieval signal, so expansion to the named entity is mandatory before search.

Scope: Conversational state assumes coherent follow-ups. It holds for refining, comparing ("which of these"), and pronoun chains, and breaks on abrupt topic jumps where stale history pollutes the rewrite — good systems detect resets.

Recap: Keep history, rewrite with context, retrieve, then generate grounded — pronouns resolved before search, claims cited after. Answer styles formalise the last step next.

16.13.4 Question answering styles and closing Q and A

Extractive QA — copying the answer span from a source — returns exact text, such as a date line for when a monument was built, with the source open for check. Abstractive QA — writing a fresh sentence from understood material — returns a composed summary like most chat drafts. The wording may appear nowhere in the sources, which is also where hallucination can enter. Open-domain QA — retrieve-then-read over a huge collection such as the web or an encyclopedia — first pulls candidates then reads them for the answer. Medical and legal help favour extractive heavily cited replies. If abstractive wording is used there, strong citations are still required. Otherwise a pure retrieval list is safer.

Worked example — monument date: Question "When was the monument completed?" Stored source line: "The monument was completed on 14 March 1921." Extractive returns "14 March 1921" copied verbatim with the source open — checkable, safe. Abstractive returns "It was finished in the early 1920s" — true but lossy, and a freer draft might say "1919" with no source line behind it — fluent but risky. Sense-check: copying cannot invent dates; composing can.

Style Output Strength Risk
Extractive Copied span Verbatim, checkable Stiff, no synthesis
Abstractive Fresh sentence Fluent synthesis Hallucination
Open-domain Retrieve then read Web-scale coverage Pipeline errors compound

When to pick which: medical, legal, scholarly — extractive with citations; overviews and drafts — abstractive with citations; web-scale factoids — open-domain retrieve-then-read.

Q: Do RAG plus language models plus vector stores make the earlier course ideas pointless, since search feels instant now? A: No. A grounded summary still needs its retrieved list — the renewable-energy answer above is only as good as chunks C1–C3. Without a proper source, such as a research article for a technical claim, there is no reason to trust the prose. All of these tools sit on top of a retrieval base: chunking, embeddings, indexes, and ranking are the earlier course ideas doing the work. Traditional methods alone are not enough, and generative plus neural methods supply the polish, but the base remains retrieval. The confusion is natural because chat hides the retrieval step; the correction is that every grounded claim still cashes out in retrieved evidence.

Q: What follow-up would you suggest for deeper study or dissertation work? A: Pick the topic that pulled you most, such as audio search, multimodal links, CLIP-style learning, or neural ranking. Each is deep enough for full dissertation work — constellation hashing alone, or prompt-robustness in CLIP, or fusion strategies for video each fill a thesis. Match personal pull with a gap in the area, or with a problem from the host organisation, then go deep on that slice rather than skimming all of them.

Recap: Copy for proof, compose for fluency with citations, retrieve-then-read at web scale — and every style still stands on the retrieval base this whole lecture built.
