1.1 Why Graphs Matter: From Independent Records to Relations

Picture a doctor who must predict whether a patient will fall sick next week. The patient's file lists age, symptoms, and test results — everything looks ordinary. Yet the patient sat next to a COVID-positive colleague for three days. Which piece of information decides the prediction: the file, or the meeting?

Most machine learning starts with independent entities. Take patient data as an example. Each patient counts as one separate record. Each record carries its own attributes, such as age, symptoms, and test results. A standard model then reads these attributes and makes a prediction for that patient alone. One point needs care here. In these setups, each record is treated as if it has no link to any other record. The model never asks whether two patients met, spoke, or infected each other. Statisticians call this the IID assumption (independent and identically distributed records): every row stands alone, drawn from the same pool, with no row influencing another.

Real life rarely works that way. Many entities depend on each other through contact and interaction. The spread of COVID shows this well. COVID moved from person to person through meetings and close contact. No single patient record explains that spread on its own. The meetings between people carry the missing facts. So a model that reads each patient alone misses the main channel of the disease. The file says "healthy"; the contact history says "exposed". The contact history wins.

That gap is where graph data helps. Think of the difference between a class roster and a friendship map of the same class. The roster lists every student with grades and attendance — that is tabular data. The friendship map draws lines between students who study together — those lines are the extra channel. Graph data keeps the entities and also keeps the relationships between them. Both parts stay in the data. Both parts feed the prediction. When relationships shape the result, models that use them give more correct answers. A student of this topic must hold on to this baseline rule: use graph methods whenever the relationship between data points matters for the task.

Worked example. Two patients, A and B, have identical files: age 30, no symptoms, negative test. A tabular model scores both "low risk". Now add the relationship layer: patient A shared an office with a confirmed case for a week; patient B worked from home with no known contacts. A graph-aware reading keeps both files but adds the contact edges, so A moves to "high risk — test and isolate" while B stays "low risk". The files never changed; the edges carried the whole decision. Answer: identical rows, different edges, different predictions. Sense-check: if contacts never transmitted disease, the edges would add nothing — the method only helps because the relationship truly drives the outcome.

Scope: the graph view pays off only when relationships carry signal about the target. If rows truly do not influence each other — say, predicting the weight of apples on separate trees from soil samples — a table is enough and graph machinery adds cost without gain. The assumption underneath is dependence between records; when that assumption breaks, fall back to tabular models.

Two traps catch beginners here. First, treating every dataset as a graph just because edges exist — if the edges carry no signal about the target, they add noise and compute cost. Second, the reverse: flattening naturally linked data (contacts, citations, transactions) into rows and silently dropping the relationship column, which throws away the strongest predictor before training starts.

Graphs matter because relationships matter: keep the entities and the links, and reach for graph methods whenever the links shape the answer — a rule that sets up the formal definition of a graph next.

Friend suggestions, fraud rings, and outbreak tracing all run on this same insight: the row describes the entity, and the edges describe its world. Civil engineers check bridge load capacity against the structure of beams, not against single beams in isolation, and graph learning applies the same structural thinking to data.

1.2 Formal Definition of a Graph and Graph Data Files

Every network you will meet — friendships, citations, roads, molecules — reduces to the same two ingredients. What are those two ingredients, and what is the smallest example that still counts as a graph?

A graph (the formal object; the word "network" means the same thing in this course) is written as \(G = (V, E)\), where \(V\) is the set of vertices and \(E\) is the set of edges. The spoken form in class was "G, V, V", which meant \(G = (V, E)\) with \(V\) for vertices and \(E\) for edges — the second "V" was a slip of the tongue for \(E\). A vertex — also called a node — is one entity in the data, such as a person, a product, or a paper. An edge — also called a link or a connection — is one relationship between two entities, such as friendship, purchase, or citation. Keep the professor's mapping: vertex and node are synonyms, and edge, link, and connection are synonyms.

In plain words, the definition says this: a graph is a set of things plus a set of pairwise links between those things. The block form is:

\[ G = (V, E) \]

where \(V = \{v_1, v_2, \dots, v_n\}\) is the set of \(n\) nodes (\(n\) counts the vertices, so \(n = |V|\)) and \(E \subseteq V \times V\) is the set of edges between pairs of nodes (\(V \times V\) is the set of all ordered node pairs). For an undirected graph, each edge \(\{u, v\}\) has no arrow — curly braces mark an unordered pair. For a directed graph, each edge \((u, v)\) points from \(u\) to \(v\) — round brackets mark an ordered pair. Verified against the standard reference form \(G = \{V, E\}\) with \(N = |V|\) nodes and pairwise edge notation; the round-versus-curly convention above matches the lecture and the texts agree.

Worked example. Build the smallest interesting graph: three patients \(V = \{v_1, v_2, v_3\}\). Patient \(v_1\) met \(v_2\), and \(v_2\) met \(v_3\), but \(v_1\) never met \(v_3\). Then \(E = \{\{v_1, v_2\}, \{v_2, v_3\}\}\), so \(n = 3\) and \(|E| = 2\). Answer: \(G = (\{v_1, v_2, v_3\}, \{\{v_1, v_2\}, \{v_2, v_3\}\})\). Sense-check: two edges on three nodes leave one pair unlinked — exactly the missing \(v_1\)–\(v_3\) meeting.

Graph data on disk usually arrives as two files. One file holds the node data. It lists each node with its attributes, so a patient file might list patient IDs with age and symptoms. The other file holds the edge data. It lists which node connects to which other node, so a contact file might list pairs of patient IDs who met. A newcomer should always check both files. The node file alone hides the relationships. The edge file alone hides what each entity is.

Q: In my data, where do the nodes end and the edges begin?

A: The nodes are the entities with attributes, and the edges are the pairs that interact. When you download graph data, expect one node table and one connection table, and read them together. The confusion is natural because the same ID (say, patient 7) appears in both files — in the node file it carries age and symptoms, in the edge file it carries contact partners. The rule: attributes live in the node file, pairs live in the edge file.

Scope: the two-file layout is the common case, not a law. Some dumps ship a single JSON or XML file with both blocks inside, and some edge lists carry no node file at all (nodes are then just the IDs that appear in pairs). The assumption underneath — every edge endpoint names a known entity — breaks when IDs are misspelled across files, which silently creates phantom nodes.

Beginners trip on three points. First, hearing "G, V, V" and writing \(V\) twice — the pair is \((V, E)\). Second, reading only the edge file and treating bare IDs as full entities, which drops every attribute the model could use. Third, mixing the bracket convention: \(\{u, v\}\) for undirected pairs, \((u, v)\) for directed arrows.

A graph is things plus pairwise links, \(G = (V, E)\), shipped as node and edge files read together — and with that grammar fixed, the next section tours the four networks that carry the whole course.

Hospital contact tracing and fraud-team case files both live in this exact two-file shape: an entity roster plus a pair log, joined on IDs.

1.3 Networks Around Us: Social, E-commerce, Citation and Transport

Your friend list, your shopping cart, the papers you cite, and the roads you drive — four different worlds. What single data structure describes all four, and why does each one break ordinary tables?

Networks sit all around us. Four running examples carry through the whole course. Learn them once here; every later method will be tested against them.

First, social media. On Facebook or Instagram, each person is a node. Each friendship is an edge. These networks grow very large, with millions of nodes and millions of edges. Simple tools cannot scan that much linked data. Large linked data is one reason graph neural networks exist. A concrete anchor: friend suggestions on Facebook come from reading this friendship network — "people your friends know" is a two-hop neighbour query.

Second, e-commerce sites. Here the data holds more than one type of node. Products form one type, and users or accounts form another type. A user node links to each product that the user viewed or bought. Logistics or operations nodes can appear too. So one dataset can mix node types, and the links between users and products form the network to study. The reference texts call this shape a bipartite graph (two node families with edges only across families, here users on one side and items on the other). A concrete anchor: product suggestions on a shopping site come from reading these user–product links — "buyers of A also bought B" walks two hops across the bipartite split.

Q: What are the nodes on an e-commerce website?

A: Products are one type of node, and users or accounts are another type. The links run between users and the products they touch, so the data already mixes node types. Students expect one node kind, as in a friendship graph, but e-commerce is heterogeneous from the start — that is exactly the point the question surfaced.

Third, citation networks. Open a research paper and look at its references. Each reference points to an older paper on the same topic. So each paper is a node, and each reference is a directed edge from the citing paper to the cited paper. Searching a topic such as visual analytics on Google Scholar shows this well. One topic can hold thousands of papers, so the citation network grows huge. Reading it by hand is not possible. A concrete anchor: paper topic grouping and researcher-collaboration forecasts come from reading this citation network.

Q: How do we know a citation network is directed?

A: A citation points one way, from the new paper to the older paper it used. The reverse link does not exist unless the older paper is revised to cite back, which almost never happens. Time itself forces the arrow: a 2024 paper can cite a 2010 paper, but the 2010 paper cannot cite forward.

Fourth, transport networks. In a road network, each city is a node and each road is an edge between two cities. In an airline network, each airport is a node and each airway is an edge between two airports. Traffic and route study then becomes graph study. A concrete anchor: traffic forecasts on map applications come from reading this road network with its live attributes such as speed and congestion per segment.

Network Nodes Edges Directed? Why tables fail
Social People Friendships No Millions of links; dense neighbour queries
E-commerce Users + products Views, purchases No Two node types; signal lives across the split
Citation Papers References Yes — new cites old Thousands of papers; hand reading impossible
Transport Cities / airports Roads / airways Mostly no Live per-edge attributes; structure is the question

Worked example. Take a tiny citation network: papers \(P_1\) (2024), \(P_2\) (2022), \(P_3\) (2020). \(P_1\) cites \(P_2\) and \(P_3\); \(P_2\) cites \(P_3\). Edges: \((P_1, P_2)\), \((P_1, P_3)\), \((P_2, P_3)\). Now answer three questions. Which paper is most cited? Count incoming arrows: \(P_3\) has 2, \(P_2\) has 1, \(P_1\) has 0 — \(P_3\) wins. Which direction do all arrows point? From newer to older — forward in reading, backward in time. What breaks if you drop directions? \(P_1\) would look as cited as \(P_3\) — wrong ranking. Sense-check: the oldest foundational paper collects the most arrows, exactly as real citation counts behave.

Scope: these four cover the course's needs, not the universe. Molecules, knowledge graphs, and transaction nets follow the same grammar but add typed edges and attributes that these four keep simple. Also, "undirected" is a modelling choice: a road can be directed when it is one-way, and a friendship can be directed when it is a follow.

The classic beginner error is flattening node types: treating users and products as one interchangeable pile loses the bipartite structure that makes recommendations work. A second trap is dropping citation arrows and ranking by neighbour count — direction is the signal there, not degree.

Four networks — social, e-commerce, citation, transport — set the course vocabulary: same graph grammar, different node types and arrow rules — and the next section explains why ordinary deep learning cannot read them.

These four return constantly: friend and product suggestions, paper grouping, co-author forecasts, and live traffic prediction are the industry face of the same four graphs.

1.4 Why Graph Neural Networks: The Hard Problem and When to Use Them

Images sit on neat grids and sentences march in order — so a fixed filter slides across them with ease. What happens when the data has no grid, no order, and no fixed size at all?

Graph data poses a hard problem for standard deep learning. Images sit on fixed grids. Every picture has the same row-and-column shape, so a fixed filter slides across it with ease. Text carries an order. Each sentence is a sequence of words, and that order holds meaning with a fixed reference point. Graphs have neither comfort — the professor's own phrase for the missing grid and the missing order. A graph can hold any number of nodes. Its topology (the pattern of who links to whom) can take any shape. Standard deep models expect fixed grids or ordered sequences, so they cannot take such free-form data as is. That mismatch calls for special models, and graph neural networks fill that gap.

Two pressures force the move. First, the data is huge and keeps growing fast. Millions of linked records need models built for scale — remember the millions of nodes and edges in the social networks of the previous section. Second, the links themselves carry signal. On a shopping site, how a user touches products tells more than the user profile alone. In a contact network, who met whom tells more than each patient file alone. Models that read both nodes and links predict better. The working rule stays simple. Apply graph neural networks whenever relationships between data points shape the answer. Traditional machine learning treats each record alone. Graph learning treats each node plus its neighbours plus the wider structure.

At a high level, the pipeline looks like this. Graph data goes in. A graph neural network reads nodes, links, and structure. A prediction comes out with higher quality because links joined the input. Typical tasks include guessing new links, sorting nodes into groups, building or studying subgraphs, and spotting communities. Telecom tracking shows the same pattern. Analysts first mapped the trusted couriers around a key person, then watched those courier links. The key person avoided phones and passed notes through shared mail drafts. One courier's stray phone call exposed the location. The entities looked separate, but the links between them broke the case.

Worked example. Compare three inputs for one fraud-detection question: is account X a fake? A tabular model reads X's profile (age of account, posts per day) and scores 0.30 — looks clean. A grid model cannot even load the data because the friend count varies per account. A graph model reads X plus its neighbours: X connects to 40 accounts created this week that all link to each other and to no one else — a dense fake cluster. Score: 0.95 fake. Answer: the profile said clean, the neighbourhood said fraud, and the neighbourhood was right. Sense-check: if the neighbours were ordinary long-standing accounts, the graph score would fall back near the tabular one — the lift comes only from suspicious structure.

Q: If we make the network bigger and more complex, do we always get more correct results?

A: No. Correctness depends on many parts at once, not on size alone. A larger network slows down speed, and size trades off against other traits such as data fit and compute budget. The full detail of this trade-off belongs to a later session, which studies it in depth. Several students pressed this point, expecting "bigger is better" — the professor's correction stands: size is one lever among many, not a guarantee.

Scope: GNNs are the right tool when relationships shape the answer and the topology varies. They are the wrong tool when rows are truly independent, when the graph is tiny enough for hand rules, or when latency budgets forbid neighbour lookups. The assumption underneath — linked entities influence each other — must hold, or the extra machinery buys nothing.

Two pitfalls recur. First, "bigger network always wins" — size trades against speed and other traits, and the deferred session will quantify that trade-off. Second, feeding graph data into a standard dense network by padding every graph to one fixed size: padding destroys the topology signal and explodes memory, which is exactly the mismatch this section warns against.

Standard deep learning expects grids and sequences; graphs offer neither, so graph neural networks read nodes plus neighbours plus structure — and the next section asks where such graphs come from when the raw data is a plain table.

Fake-account detection, paper topic sorting, co-authorship forecasts, and fraud-team courier tracing are the named industry faces of this pipeline: entities that look separate until their links break the case.

1.5 From Tabular Data to Graph Data

Your course project hands you a plain CSV of sellers with sales figures — no links at all. Can you still use graph methods, and if so, where would the edges come from?

This course starts from graph data as input. The task is to design neural networks that read that graph data well. Still, a fair question arises. Must the data arrive as a graph, or can plain table data turn into a graph first? The answer is that both paths occur.

One path starts with a natural graph. Friendship links, citations, and roads already form graphs. The study reads them as is.

The other path starts with table rows and adds links between them. Patient records show how. Each patient row can stand alone for standard study. But patient meetings can also join the table as links, which turns the same rows into a graph for deeper study. The same trick works elsewhere. Bare text records can grow links into a knowledge graph. Marketing records for separate sellers can grow links from the reporting hierarchy of the organisation. Each added link must mean something real, such as contact, reporting, or purchase. A made-up edge — linking sellers alphabetically, say — adds noise, not signal.

Q: Must the input already be a graph, or can table data turn into a graph?

A: Both occur. This course studies given graph data and builds neural networks on it. But table data can also grow into graph data when links between rows add signal, as with patient contacts or reporting lines. Natural graphs and converted tables both feed the same methods. The student's worry was that the course might reject tabular starts — it does not, as long as the added edges mean something real.

A follow-up question asks about tools. Is there a ready-made tool that eats raw CSV or JSON rows and outputs a graph? The short answer is that no extra tool is needed for the core step. The connection table itself is the graph. When person A links to person D, that pair row is one edge. A shop log that says one buyer took item A and item B already holds link rows between buyers and items. Code that stores each login as JSON metadata still ends with the same pair rows at the back end. Later sections show representations that hold these rows with ease, and the in-class demos make the point concrete.

Q: Do we need a special tool to turn raw rows into a graph, or does the application team build one each time?

A: The relationship rows already form the graph, so no magic tool is required. A friendship pair or a buyer-item pair is an edge row. What the team builds is the intake code that reads its own JSON, CSV, or log format and stores those pair rows. The coming representation section then shows how plain pair rows become matrices, lists, or JSON graph files. Two students asked this in different words — one about raw rows, one about who builds the converter — and both got the same answer: pairs are edges, intake code is format-specific.

Worked example. A shop log holds three rows: buyer \(u_1\) took items \(a\) and \(b\); buyer \(u_2\) took item \(a\). Build the buyer–item graph. Nodes: \(V = \{u_1, u_2, a, b\}\). Edges: \((u_1, a)\), \((u_1, b)\), \((u_2, a)\). Now recommend for \(u_2\): \(u_2\) shares item \(a\) with \(u_1\), and \(u_1\) also took \(b\) — recommend \(b\) to \(u_2\). The log never named an edge; each "took" row already was one. Sense-check: if \(u_1\) had taken nothing in common with \(u_2\), no path would join them and no recommendation would follow — the method only fires through shared neighbours.

Scope: conversion is legitimate only when the invented edges carry real meaning — contact, reporting, purchase, citation. Edges manufactured from thin similarity ("same age, so linked") smuggle the label into the features and inflate results. The assumption underneath is that the link relation genuinely influences the target.

Two traps here. First, waiting for a universal CSV-to-graph button instead of writing the small intake script for your own format. Second, the opposite: linking every row to every similar row until the graph turns into a near-complete hairball where every node touches everything and no structure survives.

Graphs arrive two ways — born as networks or grown from tables by adding meaningful pair rows — and either way the pairs are the edges, which the next section turns into learned vector codes.

Seller reporting lines, patient contacts, and buyer–item logs are the everyday sources: the organisation chart, the meeting list, and the receipt roll already contain the edges.

1.6 Representation Learning, Embeddings and the GNN Pipeline

A graph with a thousand nodes has a thousand IDs and a thousand neighbourhoods. How do you squeeze all of that — features, friends, and structure — into a short list of numbers a classifier can actually read?

A large part of this course is representation learning. The input is graph data. The goal is to turn that graph data into features that models can use for prediction. Graphs hold three levels of matter: nodes, edges, and the whole graph. Each level may need its own features. So the study must learn how each level turns into numbers a model can read. Node-level codes answer "which users are alike"; edge-level codes answer "will this link form"; graph-level codes answer "is this molecule toxic".

An embedding (a dense vector code for a graph object) sits at the centre of this work. Take one node with its features. Map that node to a \(D\)-dimensional embedding, written as \(\mathbf{h}_v \in \mathbb{R}^D\), where \(v\) names the node, \(D\) is the embedding size (a small fixed number like 16 or 64), \(\mathbf{h}_v\) is the code vector itself, and \(\mathbb{R}^D\) is the space of real vectors with \(D\) entries. In plain words: each node becomes a list of \(D\) numbers. Nodes that play similar roles in the network should land close together in that space. Similar nodes get similar lists. At this stage, hold that idea lightly. Later sessions build it piece by piece.

Worked example. Four users with \(D = 2\): two football fans get codes \(\mathbf{h}_1 = [0.9, 0.1]\) and \(\mathbf{h}_2 = [0.8, 0.2]\); two cooking fans get \(\mathbf{h}_3 = [0.1, 0.9]\) and \(\mathbf{h}_4 = [0.2, 0.8]\). Distance between the football pair: \(\sqrt{(0.9-0.8)^2 + (0.1-0.2)^2} = \sqrt{0.02} \approx 0.14\). Distance across groups: \(\sqrt{(0.9-0.1)^2 + (0.1-0.9)^2} = \sqrt{1.28} \approx 1.13\). Answer: same-group distance 0.14, cross-group distance 1.13 — similar roles land close together. Sense-check: the gap (0.14 vs 1.13) is wide enough that a nearest-neighbour rule sorts all four correctly.

Graph neural networks learn these codes in a loop. They read each node's own features. They gather facts from each node's neighbours. They pool those neighbour facts together. They also weigh the shape of the graph itself. After rounds of pooling, the codes feed tasks such as node sorting, link guessing, whole-graph sorting, community spotting, and product suggestion. Each round mixes a wider ring of neighbours into every node code — round one sees direct friends, round two sees friends of friends. Picture a rumour spreading one street per day: after \(k\) days every house knows the news from \(k\) streets away, and GNN layers spread information the same way.

Exam note: most test questions in this course are application based. They probe whether you grasp a topic by asking you to use it, not by asking you to recite its lines. Expect indirect questions built on understanding — for instance, a question that hands you a small graph and asks which representation fits, rather than one that asks you to define the representation.

Exam note: the assessment mixes short quizzes, two assignments, a closed-book mid-semester test, and an end-semester test. The reading list names a few books, but no single book covers the full course chapter by chapter, so study from the taught material first and use the books as backup.

Scope: embeddings help when similarity in the task matches closeness in the graph — friends share tastes, cited papers share topics. When the target ignores neighbourhood (say, each node's label is a private coin flip), neighbour pooling adds noise. The assumption underneath is homophily-like regularity: neighbours carry information about each other.

Beginners treat the embedding as a magic fixed ID per node — it is not; it is learned and changes with training and context. A second trap is reading exam questions as definition-recall: the course tests use, so practise applying each idea to a fresh small graph instead of memorising sentences.

Representation learning turns nodes, edges, and whole graphs into short number lists with similar roles side by side, refined one neighbour-ring at a time — and the next section stores those graphs in the four code formats models actually read.

Recommender engines, fraud scorers, and molecular property predictors all consume these codes: the embedding table is the shared currency between the graph and the classifier.

1.7 Graph Representations: Adjacency Matrix, Adjacency List, Edge List and JSON

You have a graph on paper and a model that only reads arrays. Four storage formats compete for the job — which one do you pick when your graph has a million nodes but only a few edges each?

Graphs must live in code before models can read them. Four storage forms cover most needs. Each form suits some tasks and fails others.

1.7.1 Adjacency Matrix

An adjacency matrix (a square table of who links to whom) holds one row and one column per node. For a graph with \(N\) nodes, where \(N\) counts the vertices, the matrix \(A \in \{0, 1\}^{N \times N}\) has \(N\) rows and \(N\) columns (\(A\) is the table; \(A_{ij}\) is the single cell where row \(i\) meets column \(j\)). In plain words: a 6-node graph needs a 6 by 6 table. Row \(i\) and column \(j\) meet at cell \(A_{ij}\), where \(i\) names the row node and \(j\) names the column node. Set \(A_{ij} = 1\) when node \(i\) links to node \(j\), and \(A_{ij} = 0\) otherwise. For an undirected graph the table mirrors across its diagonal (\(A_{ij} = A_{ji}\)); for a directed graph it need not. This matches the reference definition \(A \in \{0, 1\}^{N \times N}\) with \(A_{ij} = 1\) exactly when \(v_i\) sits next to \(v_j\).

Worked example. Four friends: \(v_1\) links to \(v_2\) and \(v_3\); \(v_2\) links to \(v_1\) and \(v_3\); \(v_3\) links to \(v_1\), \(v_2\), \(v_4\); \(v_4\) links to \(v_3\). The table:

\[ A = \begin{bmatrix} 0 & 1 & 1 & 0 \\ 1 & 0 & 1 & 0 \\ 1 & 1 & 0 & 1 \\ 0 & 0 & 1 & 0 \end{bmatrix} \]

Row 3 reads \([1, 1, 0, 1]\): three ones, degree 3. Answer: degree of \(v_3\) is 3, read straight off row 3. Sense-check: the table mirrors across the diagonal, as an undirected friendship must.

The cost is space. The table always needs \(N^2\) cells, so the space need is:

\[ \text{space} = N^2 \text{ cells} \]

Most cells stay zero in real graphs, so much space goes to waste. Compute cost climbs too, because the whole table must sit in memory. So this form suits only small graphs, up to a few hundred nodes, and strains past about a thousand nodes. A million-node social graph would demand \(10^{12}\) cells — about a trillion entries for mostly zeros.

Q: Is the adjacency matrix limited because it only holds zeros and ones instead of chances?

A: The deeper limit is sparsity, not the zero-one style. With many nodes, the table grows as \(N^2\) and stays mostly empty. Memory and compute costs climb with it, so the form fits small graphs only. The student's hunch blamed the binary values, but a table of probabilities would still need \(N^2\) cells — the shape is the problem, not the entries.

1.7.2 Adjacency List

An adjacency list (a per-node list of neighbours) stores each node with the nodes it links to. Node \(v_1\) might list neighbour \(v_2\). Node \(v_2\) might list \(v_1\), \(v_3\), and \(v_4\). So each vertex gets one entry, and that entry names all its linked nodes. Node attributes fit with ease. Car nodes, for example, can carry extra columns for model and colour — each entry is a small record, so new fields slot in naturally.

Direction and edge detail cause trouble. A plain list does not show whether a link runs from \(v_1\) to \(v_2\) or the reverse. Edge weights and edge attributes also have no natural home. The list suits node attributes well but not edge attributes.

Q: Can the adjacency list show link direction or edge weights?

A: Not cleanly. Direction stays hidden, and weights have no fixed slot. You can bolt on tuples such as \((v_2, 10)\), where \(10\) is the weight, but lookups and math across many attributes turn messy. The same bolt-on works for the matrix form, so neither form wins here. The student's hope was a clean built-in slot — there is none, only workarounds.

A debate in class pushed this further. Storing a weight such as \(10\) in a matrix cell works for one attribute: write \(10\) instead of \(1\) at cell \((i, j)\). Tuples in a list work the same way. Both tricks store the facts. The real gap is compute. Pulling the second attribute of edge \((v_2, v_1)\) and matching it against edge \((v_2, v_4)\) means chasing pointers through nested lists. The same match in a flat edge table is one column scan. So storage is possible in both forms, but heavy comparison work runs slower.

Worked example. Store the four-friend graph above as lists: \(v_1 \to [v_2, v_3]\); \(v_2 \to [v_1, v_3]\); \(v_3 \to [v_1, v_2, v_4]\); \(v_4 \to [v_3]\). Storage: \(4\) entries plus \(8\) neighbour slots \(= 12\) items against the matrix's \(16\) cells — barely better here. Now scale up: a sparse million-node graph with 5 links each needs about \(5\) million slots as lists against \(10^{12}\) matrix cells. Answer: lists win by a factor of roughly 200,000 on sparse millions. Sense-check: the sparser the graph, the wider the gap — lists store only what exists.

1.7.3 Edge List

An edge list (a table with one row per edge) stores each link with its attributes. Columns might read source, target, attribute one, attribute two, attribute three, with as many attribute columns as needed. A weight such as \(10\), \(20\), or \(30\) sits in its own cell per row. Many edge attributes fit with ease — this is the natural home of per-link data.

Two limits bite. First, edge lookup is slow. To find one edge, the code may scan the whole list or sort and search it. Second, node attributes repeat badly. If node \(v_2\) with attribute value \(5\) touches 100 edges, that value \(5\) repeats across 100 rows unless a side table holds it once with a pointer. So the edge list suits edge attributes well but not node attributes.

Q: Can the edge list store weights, and can it store node attributes too?

A: Weights fit well as one more column per edge row. Node attributes fit only with waste or extra pointers, because each node value repeats on every edge row it touches. For node-heavy data, pair the edge table with a node table instead. That pairing — edge table plus node table — is exactly the two-file layout from the definition section.

Worked example. Three transfers with amounts: \((a, b, 10)\), \((b, c, 20)\), \((a, c, 30)\). Total flow out of \(a\): scan the source column, pick rows starting at \(a\) (\(10 + 30\)). Answer: outflow of \(a\) is \(40\). Now ask the reverse — "list every edge touching \(b\)" — and the code scans all rows because no index leads to \(b\). Answer: attribute math is one scan; neighbour lookup is a scan too. Sense-check: each row is self-contained, so filters are cheap but jumps are not.

1.7.4 JSON and Graph XML Files

A JSON graph file — a text file that nests node and edge records — joins both tables. Its node block might read \(v_1\) with name and age fields. Its edge block might read \((v_1, v_2)\) with weight fields. So one file holds node attributes and edge attributes together. Graph XML files play the same role. Reach for these forms when both attribute kinds matter at once — shipping a dataset, archiving a snapshot, or handing one file between teams rather than a folder of tables.

Scope: these four cover the lecture's needs. Weighted matrices replace \(1\) with the weight; directed lists order the pairs — both are supported extensions, not new formats. The assumption underneath every choice is fit-to-task: no single format wins on space, attributes, and lookup at once.

Three traps: reaching for the matrix on a million-node graph (memory dies at \(N^2\)); stuffing all attributes into one format instead of pairing an edge table with a node table; and scanning a raw edge list for repeated neighbour queries instead of building an index or adjacency list once.

Matrix for small dense graphs, lists for large sparse ones, edge tables for rich link attributes, JSON when both attribute kinds travel together — and the next section puts these formats to work on real datasets.

SNAP dumps arrive as edge lists, NetworkX prefers adjacency under the hood, and every dataset handoff in the wild is a JSON or CSV pair — format choice is daily practice, not theory.

1.8 Hands-on Graph Analysis: Datasets, NetworkX and Synthetic Graphs

You have never touched a graph library. Your first assignment: download one real network, print five numbers that describe it, then grow a fake 50-node graph for testing. Where do you click first, and what do the five numbers mean?

Study needs data and tools. The Stanford SNAP library is one popular source of network datasets. It groups data by type, so citation, social, and other networks each sit in their own shelf. A Facebook dataset there holds about 4000 nodes and about 88000 edges. Read as pairs, its rows look like \(0\)–\(1\) and \(0\)–\(173\), where each row is one edge. That row shape marks it as an edge list — node IDs paired per line with no attribute columns.

The NetworkX library in Python reads such files and reports graph traits. A first practice task runs like this. Download one network dataset. Load it with NetworkX. Print the node count \(N\), the edge count \(|E|\), the density, the average degree, and the largest degree in the graph. Zachary's Karate Club dataset is one handy choice, and many published studies use it as a baseline. In code the flow is: read_edgelist to load the pair rows, number_of_nodes and number_of_edges for \(N\) and \(|E|\), then density and degree for the rest.

Graph density — how tightly the graph links up — is the share of actual edges out of all possible edges. In plain words: count the edges you have, count the edges a complete graph would have, and divide. For an undirected graph with \(N\) nodes and \(|E|\) edges:

\[ D = \frac{|E|}{N(N-1)/2} = \frac{2|E|}{N(N-1)} \]

where \(D \in [0, 1]\) is the density (\(0\) is empty, \(1\) is complete), \(|E|\) counts the edges present, and \(N(N-1)/2\) counts all possible undirected pairs (each of the \(N\) nodes could join \(N - 1\) others, halved because each pair is counted twice). A score near \(1\) means dense links. A score near \(0\) means sparse links. The average degree — the mean link count per node — follows as:

\[ \langle k \rangle = \frac{2|E|}{N} \]

where \(\langle k \rangle\) is the mean degree and \(N\) counts the nodes. Each edge touches two nodes, so doubling the edge count before dividing gives the per-node mean. Both formulas are verified against the standard references: density as actual over possible pairs, average degree as \(2|E|/N\).

Worked example. A study group graph: \(N = 5\) students, \(|E| = 6\) friendships. Possible pairs: \(5 \times 4 / 2 = 10\). Density: \(D = 6/10 = 0.6\). Average degree: \(\langle k \rangle = 2 \times 6/5 = 2.4\). Largest degree: tally each student — say Ana has 4 links, the rest fewer — so max is 4. Answers: density 0.6, average degree 2.4, max degree 4. Sense-check: density 0.6 sits well above sparse social graphs (often below 0.01) — five friends with six ties is a tight group, as expected.

Q: What does graph density tell us?

A: It tells whether links are dense or sparse. Divide the actual edge count by the total possible edge count. High values mean a tightly tied graph, and low values mean a loosely tied one. The student's confusion was treating density as a property of single nodes — it is a whole-graph number in \([0, 1]\).

A second practice task builds synthetic data. Sometimes study needs a graph with fixed traits, such as 50 nodes and 200 edges, to test a new method. The Erdos–Renyi model grows such random graphs: fix \(N\), then keep each possible pair with probability \(p\) (so \(p = 200/1225 \approx 0.163\) for 50 nodes and 200 edges). The Barabasi model grows social-style graphs instead, where new nodes attach preferentially to already-popular nodes and hubs emerge. Learn both models, learn what traits each one yields, and practise growing graphs with chosen sizes. In NetworkX these are erdos_renyi_graph(n, p) and barabasi_albert_graph(n, m). Real-world: teams test fresh graph methods on synthetic graphs with known traits before trusting them on costly real data.

Worked trace. Grow the 50-node, 200-edge test graph with Erdos–Renyi: \(N = 50\), possible pairs \(= 50 \times 49/2 = 1225\), target \(|E| = 200\), so \(p = 200/1225 \approx 0.163\). Expected edges: \(1225 \times 0.163 \approx 200\). Expected average degree: \(2 \times 200/50 = 8\). Density: \(200/1225 \approx 0.163\). Answers: \(p \approx 0.163\), mean degree 8, density 0.163. Then grow a Barabasi twin with the same size: same \(N\) and \(|E|\) but a skewed degree histogram with a few hubs — same averages, different shape. Sense-check: equal edge counts give equal density and mean degree by construction; the difference hides in the max degree and the tail.

Scope: density and mean degree describe the whole graph only under the lecture's undirected reading; directed versions divide by \(N(N-1)\) instead. Synthetic models reproduce statistical shape, not real content — a 50-node random graph tests plumbing, never conclusions about real users.

Beginners mix up \(N(N-1)/2\) with \(N^2\) (dropping the halving), forget the factor of 2 in \(\langle k \rangle = 2|E|/N\), and feed directed SNAP files into undirected formulas. A second trap: testing only on synthetic graphs and declaring victory — synthetic traits are chosen, not discovered.

SNAP supplies real edge lists, NetworkX turns pairs into \(N\), \(|E|\), density, and degrees, and Erdos–Renyi plus Barabasi supply controlled test graphs — and the next section defines the degree itself, the number behind every one of those statistics.

Karate-club baselines, Facebook ego nets, and pre-launch synthetic stress tests are the working analyst's daily loop: measure the real graph, then stress the method on a fake one with known traits.

1.9 Degree, Weighted Degree, In-Degree and Out-Degree

In a room of ten people, one person shook six hands and another shook none. Who is the hub, who is the isolate — and what single number captures each person's connectedness?

The degree (the link count of one node) of node \(v\), written \(\deg(v)\), counts the edges incident on \(v\) — "incident" means touching the node. In plain words: count how many edges touch the node. The reference texts define it as \(d(v_i) = \sum_j A_{ij}\), the row sum of the adjacency matrix: each \(1\) in the row is one touching edge. A loop example tested this. With loop edges present, each loop still counts as incident on its node, and the degree adds them in. Concretely, the taught sketch showed node 3 touching 7 edge-ends in total — ordinary links plus loop contributions counted at their incident node — giving \(\deg(v_3) = 7\). Loops are rare in the course's later graphs, but the rule stands: count every incident touch.

The weighted degree (the weight sum at one node), also called strength and written \(s_3\) for node \(v_3\), adds weights instead of counting edges. If node \(v_3\) carries incident weights \(3\), \(1\), \(9\), \(7\), and \(6\), its weighted degree is:

\[ s_3 = 3 + 1 + 9 + 7 + 6 = 26 \]

where \(s_3\) is the weighted degree (strength) of node \(v_3\). In plain words: swap the count of edges for the sum of their weights. A node with few heavy links can outrank a node with many light ones — five meetings totalling 26 contact-hours beat ten meetings totalling 10.

Worked example. Call graph: \(v_3\) talks to \(v_1\) (3 min), \(v_2\) (1 min), \(v_4\) (9 min), \(v_5\) (7 min), \(v_6\) (6 min). Unweighted degree: 5 calls. Weighted degree: \(3 + 1 + 9 + 7 + 6 = \mathbf{26}\) minutes. Now compare \(v_7\) with ten 1-minute calls: degree 10 but strength 10. Answer: \(v_3\) has fewer calls (5 vs 10) yet larger strength (26 vs 10). Sense-check: a fraud analyst chasing total money flow ranks by strength; one counting distinct contacts ranks by degree — different questions, different winners.

Directed graphs split degree in two. The in-degree (the count of incoming edges) of node \(v\), written \(\deg^-(v)\), counts edges that point into \(v\). The out-degree (the count of outgoing edges) of node \(v\), written \(\deg^+(v)\), counts edges that leave \(v\). In the taught example, node \(v_1\) has \(\deg^-(v_1) = 2\) and \(\deg^+(v_1) = 1\). In plain words: two arrows enter it, and one arrow leaves it. Think of citations: in-degree is "how often cited" (prestige), out-degree is "how much it cites" (breadth).

Q: Do in-degree and out-degree apply when edges have no direction?

A: No. Undirected links carry no arrows. When a graph mixes in a direction-free edge, treat that edge as running both ways: count it once in the in-degree and once in the out-degree. The student's instinct was to leave such edges out of both counts — the lecture's rule keeps them in both, so no link goes uncounted.

Scope: plain degree fits unweighted graphs; strength fits weighted ones — never add raw counts and weights in one sum. In/out split needs arrows; on undirected graphs there is a single degree. The assumption underneath is one clean edge list: multi-edges and self-loops each follow the incident-touch rule above.

Beginners confuse degree with strength (counting calls vs counting minutes), forget the both-ways rule for stray undirected edges in directed tallies, and read in-degree as importance in every domain — in a road net, high in-degree may just mark a roundabout, not a capital.

Degree counts touches, strength sums weights, and arrows split the count into prestige (in) and breadth (out) — and the next section turns those per-node numbers into the graph's first great invariant.

Contact tracers rank by strength (total exposure-hours), citation analysts rank by in-degree (times cited), and spam hunters watch out-degree spikes (mass citers) — one vocabulary, three professions.

1.10 Handshaking Theorem and the Directed Variant

Ten people shake hands at a party — some shake many hands, some few. Without watching, can you still prove something exact about the total number of handshakes from the per-person counts alone?

The handshaking theorem (the degree sum rule for undirected graphs) says the sum of all degrees equals twice the edge count. With \(n\) nodes \(v_1, \dots, v_n\) and \(|E|\) edges:

\[ \sum_{i=1}^{n} \deg(v_i) = 2|E| \]

where \(\deg(v_i)\) is the degree of node \(v_i\) and \(|E|\) counts the edges. In plain words, spoken alongside the symbols: add up every node's degree, and you get twice the number of edges. Each edge serves two ends. It counts once at its first endpoint and once at its second endpoint. So every edge pays into the sum exactly twice. This fact is easy to feel with a small sketch. Walk the nodes, tally each touch, and each link shows up at both ends. The reference proof runs the same way: each edge \(\{v_i, v_j\}\) contributes exactly 2 to the double sum, so the total is \(2|E|\).

Worked example. Party of 4: Ana shakes 3 hands, Ben 2, Cara 2, Dan 1. Sum: \(3 + 2 + 2 + 1 = 8\). Edges: \(|E| = 8/2 = \mathbf{4}\) handshakes. Check by drawing: Ana–Ben, Ana–Cara, Ana–Dan, Ben–Cara gives degrees (3, 2, 2, 1). Answer: 4 handshakes. Sense-check: a non-even sum such as 7 would be impossible — no graph can realise it, which is exactly the parity test below.

The directed twin says total in-degree equals total out-degree:

\[ \sum_{i=1}^{n} \deg^-(v_i) = \sum_{i=1}^{n} \deg^+(v_i) \]

where \(\deg^-(v_i)\) and \(\deg^+(v_i)\) are the in-degree and out-degree of node \(v_i\). In plain words: every arrow leaves one node and enters another, so departures and arrivals balance. Note the directed form equates the two totals rather than doubling one count — each arrow pays once into each sum. One neat outcome follows for undirected graphs. The count of nodes with odd degree is always even. Each edge adds \(2\) to the total, so odd tallies must pair up. Try it: degrees (3, 2, 2, 1) have two odds; (3, 3, 1, 1) have four; you can never build a list with exactly one or three odds.

Worked example. A scraped degree file reads \([5, 4, 4, 3, 3, 1]\): six nodes, odd entries are 5, 3, 3, 1 — four odds, even count, passes. Sum: \(5 + 4 + 4 + 3 + 3 + 1 = 20\), so \(|E| = 10\). Now corrupt one digit in transit: \([5, 4, 4, 3, 3, 2]\) has three odds (5, 3, 3) — rejected without drawing anything. Answer: first file consistent with 10 edges; second file corrupt. Sense-check: a single flipped digit broke the even-odds rule, which is precisely why this one-line check guards download pipelines.

Scope: the doubling rule is for undirected graphs; directed graphs balance in against out instead. Self-loops follow the lecture's incident-touch convention from the degree section. The assumption underneath is a clean simple graph — multi-edges and loops must be counted by the same touch rule on both sides of the equation.

The recurring error is equating the degree sum with \(|E|\) instead of \(2|E|\) — forgetting each edge has two ends. A second trap: applying the odd-count parity rule to directed in/out lists, where it does not hold; parity governs undirected degree only.

Add every degree and you hold twice the edges; split by arrows and arrivals equal departures, with odd degrees always pairing up — and the next section asks the reverse question: which degree lists can exist at all?

Download validators, crawler sanity checks, and fraud-team ledger audits all run this two-second parity test before spending compute on the heavy analysis.

1.11 Havel-Hakimi Theorem and Degree Sequence Validity

Someone hands you the list \((7, 6, 5, 4, 4, 3, 2, 1)\) and claims a network has exactly these degrees. Is that even possible — and how do you decide without drawing a single edge?

The Havel-Hakimi theorem — the test for whether a degree list can form a graph — answers one question. Given a degree sequence, does any graph realise it? Drawing is tedious. Start with a high-degree node, hunt for partners, backtrack on clashes. The theorem swaps drawing for arithmetic.

A degree sequence — the list of all node degrees — such as \(d = (d_1, d_2, \dots, d_n)\) just names each node's degree. The test runs in rounds:

  1. Sort the sequence from large to small.
  2. Remove the first value. Call it \(d\).
  3. Subtract \(1\) from the next \(d\) values.
  4. Repeat. All zeros at the end means some graph fits the list. A negative value at any point means no graph fits.

Why does removing \(d\) and lowering the next \(d\) entries work? The removed node needs \(d\) distinct partners; wiring it to the \(d\) currently hungriest nodes can never hurt — if any wiring succeeds, this greedy wiring succeeds too. Repeating the step strips one node at a time until nothing (all zeros, realisable) or a contradiction (a \(-1\) or a \(d\) larger than the nodes left, impossible) remains.

Worked example. Test \(d = (7, 6, 5, 4, 4, 3, 2, 1)\). Eight nodes, so the maximum legal degree is \(7\) — the opening \(7\) is aggressive but not instantly fatal.

Round one: sort \((7, 6, 5, 4, 4, 3, 2, 1)\). Remove \(7\); lower the next seven values by one: \(6 \to 5\), \(5 \to 4\), \(4 \to 3\), \(4 \to 3\), \(3 \to 2\), \(2 \to 1\), \(1 \to 0\). That yields \((5, 4, 3, 3, 2, 1, 0)\).

Round two: sort \((5, 4, 3, 3, 2, 1, 0)\). Remove \(5\); lower the next five by one: \(4 \to 3\), \(3 \to 2\), \(3 \to 2\), \(2 \to 1\), \(1 \to 0\); the trailing \(0\) sits outside the window and stays. That yields \((3, 2, 2, 1, 0, 0)\).

Round three: sort \((3, 2, 2, 1, 0, 0)\). Remove \(3\); lower the next three by one: \(2 \to 1\), \(2 \to 1\), \(1 \to 0\). That yields \((1, 1, 0, 0, 0)\).

Round four: sort \((1, 1, 0, 0, 0)\). Remove \(1\); lower the next one by one: \(1 \to 0\). That yields \((0, 0, 0, 0)\) — all zeros.

Answer: the sequence is graphic; some 8-node graph carries exactly these degrees. Sense-check: the sum is \(7+6+5+4+4+3+2+1 = 32 = 2 \times 16\), so the handshaking parity passes with \(|E| = 16\) — consistent, not contradictory.

Broken lists fail fast. Take \((6, 5, 4, 3, 3, 1)\). Remove \(6\), which asks for six later values, but only five values remain. The list is invalid on the spot. Another list fails when a subtraction dips below zero. A \(-1\) anywhere means no graph can carry that sequence. Try \((3, 3, 3, 1)\): remove \(3\), lower the next three \((3 \to 2, 3 \to 2, 1 \to 0)\) giving \((2, 2, 0)\); remove \(2\), lower the next two \((2 \to 1, 0 \to -1)\) — the \(-1\) kills it.

Q: Why does removing 6 from a six-long list fail at once?

A: Removing a value \(d\) needs \(d\) later values to absorb the links. With only five values behind a \(6\), one link has nowhere to land. The sequence is invalid without further rounds. The student's hope was that later rounds might rescue it — they cannot, because the missing partner is a hard count, not a sorting artefact.

Q: In the worked run, why does the trailing zero stay zero instead of dropping to minus one?

A: Each round lowers only the next \(d\) values, not the whole row. Values past that window stay put. So a far zero outside the window keeps its zero while the window values drop by one. The confusion is natural — "subtract one" sounds global, but the theorem spends exactly \(d\) stubs, one per partner.

Scope: the test answers existence, not uniqueness — many graphs can share one sequence, and the theorem names none of them. It also assumes a simple graph (no loops, no multi-edges); degree lists that need loops fall outside this test. The opening \((7, 6, 5, 4, 4, 3, 2, 1)\) is realisable but extreme — a 7 inside 8 nodes forces a near-complete hub.

Beginners skip the re-sort between rounds (order matters — always wire the currently hungriest), lower the whole row instead of the next-\(d\) window, or read "all zeros" too early when unsorted leftovers hide a positive stub. Re-sort every round, count the window exactly.

Sort, strip the hub, spend its stubs on the hungriest partners, repeat — zeros mean buildable and \(-1\) means impossible — and the next section flips the lens from edges present to edges missing.

Degree-sequence validation guards every synthetic-graph pipeline and every scraped dataset: run Havel-Hakimi (or the handshaking parity first) before trusting a degree file.

1.12 Graph Complement and When Missing Links Matter

Fraud teams hunt for transactions that happened — but friend-suggestion teams hunt for friendships that do not exist yet. What graph holds exactly the links your data does not have?

The complement (the graph of the missing edges) of \(G\), written \(\bar{G}\), keeps the same vertices and flips the edges. In plain words: keep every node, drop every edge that \(G\) has, and add every edge that \(G\) lacks between distinct nodes. As a block:

\[ \bar{G} = (V, \bar{E}), \quad \bar{E} = \{\{u, v\} : u \ne v, \{u, v\} \notin E\} \]

where \(V\) is the shared node set (\(u \ne v\) excludes self-links), \(E\) holds the edges of \(G\), and \(\bar{E}\) holds exactly the non-edges of \(G\) between distinct nodes. Take nodes \(\{1, 2, 3, 4\}\) with only two edges present. The complement keeps nodes \(1\) through \(4\) and fills in the missing pairs. Self-links stay out.

Worked example. Four users \(\{1, 2, 3, 4\}\); friendships \(E = \{\{1,2\}, \{3,4\}\}\). All possible pairs: \(\binom{4}{2} = 6\). Missing pairs: \(\{1,3\}, \{1,4\}, \{2,3\}, \{2,4\}\) — four stranger pairs. So \(\bar{E}\) holds those four, and \(|\bar{E}| = 6 - 2 = \mathbf{4}\). Answer: the complement is the 4-edge stranger graph. Sense-check: a friend-suggestion engine scores exactly these four pairs and never re-suggests the two existing friendships.

Complements pay off when absent links matter more than present ones. In a social network, the study may need people who are not yet friends. In a device network, it may need pairs that never talk. Some proofs also run with less strain on the complement side. So when the question turns on who is missing, build \(\bar{G}\) and study that. A concrete anchor: friend-suggestion engines score non-edges, which are exactly the complement's edges, before ranking candidates.

Q: When would anyone compute a complement instead of using the graph as is?

A: When missing links carry the question. Finding strangers who might connect, or devices that never exchange data, means reading the absent edges. Proofs that simplify on the missing side give a third reason — a dense graph's complement is sparse, and sparse graphs are cheaper to reason about.

View Edges held Answers Example use
\(G\) Links present Who connects? Fraud rings, traffic routes
\(\bar{G}\) Links missing Who could connect? Friend suggestions, silent devices

Scope: the complement is defined here for simple undirected graphs without self-loops — the \(u \ne v\) guard matters. On directed graphs each ordered pair flips separately, doubling the bookkeeping. The assumption underneath is that "missing" is meaningful: in a nearly complete graph the complement is tiny and useful; in a sparse graph it is enormous and rarely built explicitly.

Beginners include self-loops in \(\bar{E}\) (the definition excludes them), or materialise the complement of a huge sparse graph and run out of memory — a sparse graph's complement is dense, so score candidates implicitly instead of building it.

\(\bar{G}\) keeps the nodes and flips the pairs — study it when the question is about who is missing — and the next section gives names to the strolls you take across either graph.

Friend suggestions, silent-device audits, and "researchers who never co-authored" queries all read the complement: the most valuable edge is often the one not yet drawn.

1.13 Walks, Trails, Paths and Random Walks

You stroll from friend to friend across a social graph, sometimes revisiting people, sometimes reusing roads. When does your stroll count as a walk, when as a trail, and when as a path — and why does a search engine care?

A walk (a stroll along linked edges) is a sequence of incident edges visited one after another. One example runs \(v_1 \to v_3 \to v_6 \to v_4 \to v_3 \to v_6\), where each arrow is one edge and each step starts where the last one ended. Both nodes and edges may repeat along the way. An open walk (a stroll with distinct ends) starts and ends at distinct nodes. A closed walk (a stroll that returns home) starts and ends at the same node. The reference definition agrees: a walk is an alternating node–edge sequence where each edge touches the nodes immediately before and after it. The length (the edge count of a walk) of a walk counts its edges. A walk over five edges has length \(5\). The same count rule gives the length of a trail or a path. Our example visits 5 edges, so its length is \(5\).

The word incident does real work here. An edge is incident on a node when it touches that node. A walk must chain incident edges: the next edge must leave from the node where you stand. Two loose edges such as \((v_1, v_3)\) and \((v_5, v_6)\) form no walk on their own, because no shared node joins them.

Q: Why say "incident edges" instead of just "edges"?

A: Because any walk must chain through shared nodes. Each step must touch the node where the last step stopped. Random unjoined edges cannot form a walk until a shared endpoint links them. The student's phrasing sounded simpler, but it silently drops the chaining rule that makes a walk a walk.

Worked example. Tiny map: edges \((v_1,v_3)\), \((v_3,v_6)\), \((v_6,v_4)\), \((v_4,v_3)\). Stroll \(v_1 \to v_3 \to v_6 \to v_4 \to v_3\): every step shares a node, length 4, node \(v_3\) repeats but no edge repeats — a trail, not a path. Now try \((v_1, v_3)\) then \((v_5, v_6)\): no shared node — no walk at all. Answers: first stroll is a length-4 trail; second pair is not a walk. Sense-check: chaining is the whole test — shared endpoints or nothing.

A random walk (a stroll with random turns) picks each next step by chance. It matters most on huge networks that no team can fully download. Web search ranking is the classic case. Pages are nodes, hyperlinks are edges, and key pages earn high rank. Early builders could not fetch the whole web, so they sampled it with random walks and ranked from the sample. Pages visited often by the wandering surfer score high; forgotten corners score low.

A city analogy makes the method vivid. Picture a city split into sectors with crossings at each junction. Stand at one edge of the city with a four-way random picker. Roll a one and step left. Roll a two and step right. Roll a three and step ahead. Roll a four and step back. Repeat at every junction for many days. With enough steps, the odds tilt toward covering nearly all roads. Few steps mean thin coverage, and many steps mean wide coverage. That trade-off is the heart of the method. Real-world: crawlers that sample vast page networks still lean on this idea before ranking pages.

A trail (a walk with no edge twice) visits no edge more than once while nodes may repeat. The chain \(v_1 \to v_3 \to v_6 \to v_4 \to v_3\) is a valid trail: node \(v_3\) repeats, but each edge appears once. A path (a walk with no repeats at all) forbids repeat nodes and repeat edges alike. The references state it identically: a trail has distinct edges, a path has distinct nodes (hence distinct edges too). In short: walks allow all repeats, trails ban edge repeats, and paths ban both.

Stroll Node repeats? Edge repeats? Example

Trail Allowed Banned \(v_1 \to v_3 \to v_6 \to v_4 \to v_3\)
Path Banned Banned \(v_1 \to v_3 \to v_6\)

Worked example. Classify three strolls on one map. \(W_1 = v_1 \to v_3 \to v_6 \to v_4 \to v_3 \to v_6\): \(v_3\) and edge \((v_3,v_6)\) repeat — walk only. \(W_2 = v_1 \to v_3 \to v_6 \to v_4 \to v_3\): \(v_3\) repeats, edges all distinct — trail. \(W_3 = v_1 \to v_3 \to v_6\): nothing repeats — path (and therefore also a trail and a walk). Answers: walk, trail, path. Sense-check: every path is a trail and every trail is a walk — the categories nest like bowls.

Scope: the lecture's walk/trail/path ladder assumes simple frame-able strolls; random walks add the extra assumption that each next step is chosen by chance among current neighbours, which needs a connected neighbourhood to keep moving. Length always counts edges, never nodes — a 3-node path has length 2.

Three confusions to kill: calling any connected edge pair a walk (needs chaining through a shared node), calling a node-repeating stroll a path (paths ban node repeats), and counting length in nodes (edges only). The professor's vocabulary correction — walks versus trails — exists precisely because students blur the edge-repeat rule.

Walks chain incident edges, length counts edges, random turns sample graphs too big to download, and trails ban edge repeats while paths ban all repeats — and the next section spends those rules on the two most famous named strolls.

Web crawlers, PageRank-style ranking, and fraud-team money-trail tracing all walk graphs: the stroll vocabulary is the working language of link analysis.

1.14 Euler Trails and Hamilton Cycles

Two classic puzzles: a postman who must walk every street exactly once, and a tourist who must visit every landmark exactly once. Same graph — but the two puzzles ban different repeats. Which is which?

An Eulerian circuit (a closed walk that spends every edge exactly once) starts and ends at the same vertex, may revisit vertices, never reuses an edge, and covers all edges. Three checks define it: vertices may repeat, edges must not repeat, and every edge must appear. The trimmed name for the open form is an Euler trail, which spends every edge once without demanding a shared start and end. Think postman: every street walked, legs may recross.

A Hamiltonian cycle (a closed loop through each vertex exactly once) is stricter. Neither vertices nor edges may repeat, except that the start and end meet at one node to close the loop. Where Euler cares about spending edges, Hamilton cares about visiting vertices. Think tourist: every landmark once, no backtracking allowed.

Euler trail/circuit Every edge Yes No Postman walking all streets
Hamilton path/cycle Every vertex No No Tourist visiting all landmarks

Worked example. Triangle graph: nodes \(\{a, b, c\}\), edges \(ab, bc, ca\). Euler circuit: \(a \to b \to c \to a\) spends all 3 edges, returns home — Eulerian, yes. Hamiltonian cycle: the same loop visits all 3 vertices exactly once and closes — Hamiltonian, yes. Now add a dangling leaf \(d\) hanging off \(a\) (edge \(ad\)). Euler circuit attempt: \(a \to b \to c \to a \to d\) spends all 4 edges but strands at \(d\) — open trail only, no closed circuit. Hamiltonian cycle attempt: visiting \(d\) forces entering via \(a\) and leaving via \(a\) — vertex \(a\) repeats, no Hamiltonian cycle. Answers: triangle has both; triangle-plus-leaf has an open Euler trail but no closed Euler circuit and no Hamiltonian cycle. Sense-check: the leaf breaks closure for Euler and forces a revisit for Hamilton — one tiny addition kills both closed forms.

Both ideas seed real tasks, so they earn self-study. Track down which problems call for Euler-style full-edge coverage and which call for Hamilton-style full-vertex visits. Practice task: name one use case for each, and state which repeat rule makes it fit. Strong answers: street-sweeping and snow-plough routing are Euler (every road covered, recrossing fine); delivery-dispatch visit lists and sightseeing itineraries are Hamilton (every stop once, repeats wasteful).

The signature mix-up is swapping the two: Euler is about edges, Hamilton about vertices. A second trap is assuming one implies the other — the triangle has both, but the triangle-plus-leaf shows they break independently.

Euler spends every edge and tolerates revisits; Hamilton visits every vertex exactly once — postman versus tourist — closing the lecture's walk from relations to named trails.
