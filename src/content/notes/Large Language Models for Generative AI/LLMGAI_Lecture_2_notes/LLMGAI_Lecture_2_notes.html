2.1 Recap: From Probabilistic Models to Transformer Building Blocks

A language model (a rule for scoring how likely a word string is) is an old idea wearing new clothes. The task never changed: given the words so far, find the probability of the next token. That single sentence — next-token prediction is the language modeling task — is the thread that ties n-grams to transformers together.

Hook: Imagine autocomplete on a phone keyboard. Every time it offers the next word, it is doing language modeling. A large language model is that same autocomplete idea, scaled to billions of parameters and trillions of training words.

The family tree is short. Early n-gram models (models that guess the next word from the last few words) counted word triples in text. Then came neural language models (models that turn words into vectors and pass them through a network), including models built on recurrent networks. Today the same next-token task runs on the transformer architecture, which handles whole sequences at once instead of one step at a time.

The building blocks of a large language model start before any transformer layer runs. First comes tokenization (splitting raw text into pieces called tokens, such as words or word parts). Many tokenization algorithms exist, and the popular ones today are byte pair encoding, variants of byte pair encoding, and byte-level byte pair encoding. The tokenizer reads the training corpus, builds a vocabulary of token pieces, and then converts every text into a list of token IDs — plain integers such as 1543 or 8921, one per token. Every published model ships with its own trained tokenizer vocabulary, because the IDs only make sense with the vocabulary that created them. Models reach users either through open channels as open-weight or open-source models, or through hosted APIs.

Token IDs then become vectors in two steps: token embeddings carry what the token is, and positional embeddings carry where it sits. Those two vectors add up to form the input that enters the transformer stack.

Recap: Language modeling means predicting the next token. Tokenizers built on byte pair encoding turn text into token IDs, token plus positional embeddings turn IDs into vectors, and the transformer turns those vectors into next-token probabilities. The next sections open each box in turn, starting with token embeddings.

2.2 Token Embeddings and the Learned Embedding Matrix

An embedding (a vector of numbers that stands in for one token) turns a token — which starts as characters from some language — into numbers, a vector of numbers. We do not convert each token into a single scalar value. We convert it into a vector of values where each dimension can represent some characteristic of that token. The example used in class is only for illustration, to build a feel for embedding dimensions: each dimension stands for one characteristic of the token. In reality we do not know what each dimension means, and the dimensions get trained automatically. There is no way to visualize what each dimension holds — for instance, given a diagram with an animal dimension, we cannot read off how much a word like cat scores, or what value sits in that vector cell. That picture is only an intuitive aid for what an embedding dimension is.

A helpful picture: think of each token as a person filling in a personality quiz with \(D\) questions. Each answer is one number, and the full answer sheet is the embedding. Like a real quiz, nobody labels question 37 as "loves mornings" — the meaning of each question is learned from data. The analogy breaks at one point: quiz questions are fixed by the quiz author, while embedding dimensions are learned freely during training.

There is an embedding layer that converts token IDs into embeddings, and those embeddings go in as input to the transformer architecture. Embeddings have one notable property in decoder-only models: the same word appearing in a different position gets the same embedding value. Position information is added separately, through the positional embedding.

The token embeddings are not fixed. These values are learned during model training, so the embeddings become trainable parameters. The embedding matrix is the trainable parameter here. A helpful comparison comes from image processing: with classical statistical image processing, filters had fixed values for every task, but when neural networks arrived, filters became learnable parameters, as in a convolutional neural network. In the same way, the embedding matrix that turns a token ID into a token embedding is a learnable parameter of the model.

Formalize — the embedding matrix. Let \(V\) (vocabulary size) be the number of distinct tokens, a large integer such as 128,000, and let \(D\) (embedding dimension, also called the model dimension) be the vector length per token, such as 4096. Both are fixed before training, and every entry of the table is learned by gradient descent.

\[E \in \mathbb{R}^{V \times D}\]

Each of the \(V\) rows is one token's \(D\)-dimensional vector. Looking up token ID \(t\) returns row \(t\) of \(E\), a vector in \(\mathbb{R}^{1 \times D}\). In words: the embedding layer is a table lookup, not a computation — the ID selects its row.

Worked example — "fox jumps over fox". Take the sentence "fox jumps over fox". The word fox appears in the first position and again in the fourth position. Both occurrences receive the same token embedding from the embedding layer, because the embedding depends only on token identity. What differs is the positional embedding: the two occurrences sit at different positions, so different positional vectors are added to the shared token embedding. The sum carries both what the word is and where it stands. Answer: identical token rows, different position rows, so different sums. Sense-check: if the sums were identical, the model could not tell the two foxes apart.

Scope: This identity-only lookup holds for the token embedding in decoder-only models. It breaks if position leaks in early — that is exactly what the positional embedding is for. A single scalar per token would also break here: one number cannot carry the many shades of meaning a token needs.

Pitfalls: Two traps catch beginners. First, the animal-dimension diagram is illustrative only — no real dimension is labeled, and reading values off it is meaningless. Second, there is one table, not one matrix per layer; the lookup happens once at the input, and later layers work on hidden states, not fresh lookups.

Q: Does the embedding matrix get derived layer by layer, and what would its size be for, say, four tokens?

A: The embedding matrix is a single learned table, not one matrix per layer. For one token the lookup returns a \(1 \times D\) row. When a sequence of \(N\) tokens is processed together, the stacked result is \(N \times D\). So four tokens give a \(4 \times D\) block. The parallel matrix view matters most during training, where whole sequences are processed at once; for single next-token prediction during inference, the \(1 \times D\) picture is the useful one. Several students asked this in different words — the confusion point is always whether depth means more tables.

Recap: Token IDs select rows of one learned \(V \times D\) table; identical tokens share rows, and position arrives separately. That separation sets up positional embeddings next.

2.3 Positional Embeddings: Sinusoidal, Learned, and Rotary

Because the same word gets the same token embedding wherever it appears, position must be injected separately, and that is the job of the positional embedding. Three eras matter. The original transformer used a sinusoidal positional embedding, covered in a deep learning course on transformers. Then came the era of learned positional embeddings: just as token embeddings are learned, the position embedding matrix is learned too, so GPT-2 and models of that era trained their position tables instead of using fixed sine waves. Today the popular choice is the rotary position embedding, which is taken up in a later session on transformer details.

Intuition: Think of name tags at a conference dinner. Everyone named Fox wears the same name tag (the token embedding), but each chair has a different seat number (the positional embedding). The seat number tells you who speaks first, even when two guests share a name. The analogy breaks where rotation does: rotary embeddings encode relative seats, not absolute chair numbers.

Formalize — how position joins the input. Let \(e_t \in \mathbb{R}^{1 \times D}\) be the token embedding for the token at position \(t\), and let \(p_t \in \mathbb{R}^{1 \times D}\) be its positional vector. The transformer input is the sum:

\[x_t = e_t + p_t\]

where \(x_t\) is the position-aware input row. In the sinusoidal era \(p_t\) is a fixed sine-wave pattern; in the learned era each \(p_t\) is a trained row like the token table; in the rotary era position acts inside attention as a rotation rather than a plain sum. The full rotary algebra belongs to the later transformer session.

Scope: Positional embeddings matter because attention by itself has no order — shuffle the inputs and plain attention gives shuffled outputs. Any sequence model therefore needs an explicit position signal. The choice of signal (fixed, learned, or rotary) changes long-sequence behavior but not the token table itself.

Pitfalls: Do not confuse the two tables. The token table is indexed by token ID and shared across positions; the position table (in the learned era) is indexed by position and shared across tokens. Also, rotary position handling is not a plain added vector — treating it as one will garble the later derivation.

Recap: Same token, same token vector — so position arrives as a second signal, evolving from fixed sine waves to learned tables to rotary rotations. With inputs now ordered, the model still needs an output end: the language modeling head.

2.4 Language Modeling Head: Unembedding Plus Softmax

The language modeling head, often called the LM head, is nothing but an unembedding layer plus a softmax layer. Picture a transformer block made of stacked layers. Inputs enter, and every input is transformed into a hidden state at every layer. Call the tokens \(w_1\) through \(w_n\): they pass through \(L\) transformer layers, and at the final layer each position holds a hidden representation of its token. For language modeling we pick up one position — for single-token prediction, the last token of the last layer — and on top of it we add the language modeling head. Once that head is attached, the transformer base becomes a language model.

Hook: A transformer without a head is like a library with no checkout desk — all the knowledge sits on the shelves, but nothing can leave. The LM head is the checkout desk: it converts the last hidden state into one probability per vocabulary word.

The output expected from the LM head is token probabilities. We have a vocabulary built during tokenizer training, and the head must output a probability for every token in the vocabulary — for the prediction of just one token, the next token. So indirectly, the head returns a probability distribution over all tokens in the vocabulary, and that distribution is the output of the language modeling head. From it we read the next-token prediction: the head predicts a token at the position where it is attached, namely the hidden representation of the last token of the last layer.

For the time being, the rule is simple: pick the highest-probability token, and that becomes the next predicted token. Picking the highest-probability token is called the greedy algorithm, or greedy decoding. Later sessions cover further decoding algorithms in depth, but greedy selection is the working rule here.

Formalize — softmax over logits. Let the last position's final hidden state be \(h \in \mathbb{R}^{1 \times D}\) (a \(1 \times D\) row vector), let the vocabulary size be \(V\), and let the logit (raw score per vocabulary token, before normalization) vector be \(z \in \mathbb{R}^{1 \times V}\). The softmax turns logits into probabilities:

\[p_i = \frac{\exp(z_i)}{\sum_{j=1}^{V} \exp(z_j)}\]

for each vocabulary index \(i = 1, \dots, V\), where \(h\) is the last position's final hidden state, \(z\) is the logit vector, and \(p_i\) is the predicted probability of token \(i\) being next. Softmax changes no dimensions, so its input must already be \(1 \times V\). In standard classification jargon the input to the softmax is called the logit, so the required object is a \(1 \times V\) logit vector. Each \(p_i\) lies in \([0,1]\) and the \(p_i\) values sum to 1. Greedy decoding then predicts \(\arg\max_i p_i\).

Worked example — tiny 3-word vocabulary. Suppose the vocabulary is {cat, sat, mat} and the head produces logits \(z = [2.0, 1.0, 0.0]\). Exponentiate: \([\exp(2.0), \exp(1.0), \exp(0.0)] \approx [7.39, 2.72, 1.00]\). Sum: \(7.39 + 2.72 + 1.00 = 11.11\). Divide: \(p \approx [0.665, 0.245, 0.090]\). Greedy pick: cat with probability 0.665. Sense-check: probabilities sum to about 1, and the largest logit won.

Scope: This head answers "how likely is each token" — one distribution per attached position. Choosing which token to emit is a separate decoding step. Greedy selection is the working rule here; sampling and search variants come later.

Pitfalls: Beginners merge the two halves. Softmax never picks a token — it only normalizes scores. And the head's output width is always \(V\), never \(D\); if your vector has \(D\) entries, the projection step is missing.

Q: Is unembedding the same as decoding?

A: No. Unembedding only maps the hidden state back to logits and then to a probability distribution through the softmax. Decoding — choosing which token to emit, by greedy selection or by a fancier rule — is a separate step that comes after. The softmax answers "how likely is each token"; decoding decides "which token do we output".

Recap: The LM head is unembedding plus softmax: a hidden vector becomes \(V\) raw logits, then \(V\) probabilities, and greedy decoding picks the max. The missing link is how a \(D\)-wide vector becomes a \(V\)-wide one — the projection matrix.

2.5 Logits, Dimensions, and the Projection Matrix

The output of the transformer at each position has size \(1 \times D\): one row, \(D\) embedding-dimension entries. If transformer internals are unfamiliar, the dimension discussion returns in the transformer session; for now, \(D\) is the embedding dimension, also called the model dimension. Every token is represented with \(D\) numbers, and the hidden layers keep giving a hidden representation of every token, so an input token of size \(1 \times D\) still has a \(1 \times D\) hidden representation at the final layer. But the logits need size \(1 \times V\), where \(V\) is the vocabulary size — very large — while \(D\) differs per model (GPT-2 used 768, and larger models use several thousand). Something must project \(D\) dimensions up to \(V\) dimensions, and scaling up needs a rule: multiply by a matrix and learn that matrix during training.

The dimension matching is plain linear algebra. Given an input of size \(1 \times D\) and a required output of size \(1 \times V\), the multiplying matrix must be \(D \times V\), because \((1 \times D)(D \times V) = 1 \times V\). So the hidden representation of the final layer — for single-token prediction, only the \(n\)-th token, a \(1 \times D\) row — is multiplied by an unembedding matrix of size \(D \times V\) to give the \(1 \times V\) logits, and the logits pass through the softmax to give the final prediction. These are the only two equations of the unembedding layer: project, then softmax.

Formalize — project then normalize. Let \(h \in \mathbb{R}^{1 \times D}\) be the last hidden row and \(W_{out} \in \mathbb{R}^{D \times V}\) the unembedding matrix. Then:

\[z = h W_{out}\]

\[p_i = \frac{\exp(z_i)}{\sum_{j=1}^{V} \exp(z_j)}\]

where \(z \in \mathbb{R}^{1 \times V}\) holds one raw logit per token and \(p_i\) is the next-token probability. Step one changes the width from \(D\) to \(V\); step two changes scores into probabilities without changing the width.

Worked dimension calculation. Suppose \(D = 4\) for illustration and the vocabulary holds \(V = 7\) tokens. The last hidden state is \(1 \times 4\). A \(4 \times 7\) unembedding matrix maps it to \(1 \times 7\) logits, one score per token, and the softmax turns those 7 scores into 7 probabilities that sum to 1. Concretely, if \(h = [1, 0, 2, -1]\) and the first column of \(W_{out}\) is \([1, 0, 0, 1]\), the first logit is \(1 \times 1 + 0 + 0 + (-1) \times 1 = 0\). Now scale up: with a sequence of \(N\) tokens processed together, every position is projected at once, so the output is \(N \times V\) — one distribution per position. That \(N \times V\) form is what parallel training uses; the \(1 \times V\) form is what single-step inference uses. Answer: \(1 \times 4\) times \(4 \times 7\) gives \(1 \times 7\).

Exam note: Expect numerical questions on these matrix sizes, since the dimension walk-through is exactly the kind of calculation that gets asked. Remember the pair: inference uses \(1 \times V\), parallel training uses \(N \times V\).

Scope: This \(D\)-to-\(V\) direction is an up-projection — the output is far wider than the input because the vocabulary is huge. A \(V \times D\) matrix here would be a shape error: \((1 \times D)(V \times D)\) does not multiply. If the inner dimensions disagree, the projection is backwards.

Pitfalls: Two slips recur. First, feeding a \(D\)-wide vector straight into softmax and expecting \(V\) probabilities — softmax never changes width. Second, mixing up the single-step \(1 \times V\) picture with the parallel \(N \times V\) picture; both are the same head applied at different numbers of positions.

Recap: Hidden states are \(D\)-wide, logits must be \(V\)-wide, so a learned \(D \times V\) matrix bridges them before softmax normalizes. The next question is whether that big matrix needs its own parameters — weight tying says no.

2.6 Weight Tying and the Parameter Count

The projection matrix is learnable, but the practice is not to add a fresh set of parameters. Instead, the transpose of the input embedding matrix is reused. In the input embedding layer the matrix \(E\) (of size \(V \times D\)) converts token IDs into token embeddings. Its transpose \(E^\top\) (of size \(D \times V\)) is exactly the shape the output side needs, so the same matrix serves both ends: convert IDs to embeddings on the way in, convert hidden states to logits on the way out. That reuse is why the layer is called unembedding, and the \(D\)-dimensional input projection to a \(V\)-dimensional output is called an up-projection.

Intuition: Think of a bilingual dictionary used in both directions. Looking up an English word gives its French translation (embedding: ID to vector); looking up the French side gives back English candidates (unembedding: hidden state to logits). One book serves both directions — printing a second mirrored copy would double the shelf space for no new knowledge.

Sharing has a second motive beyond saving parameters: the learned representation of a token should stay consistent. Take some token appearing in the input and the same token appearing as a prediction target in the output. We want one learned representation for that token, not one representation at the input embedding layer and a different one at the output. Using the same matrix — transposed only for dimensional matching — keeps the two ends tied together.

Formalize — one matrix, two directions. With shared table \(E \in \mathbb{R}^{V \times D}\) and last hidden row \(h \in \mathbb{R}^{1 \times D}\):

\[z = h E^\top\]

where \(E^\top \in \mathbb{R}^{D \times V}\) is the transpose used as the up-projection and \(z \in \mathbb{R}^{1 \times V}\) is the resulting logit vector. Check the shapes: \((1 \times D)(D \times V) = 1 \times V\). Tying means the same entry \(E_{i,k}\) scores token \(i\) on dimension \(k\) at input time and weights dimension \(k\) toward token \(i\) at output time.

Worked parameter count. Take a model with embedding dimension \(D = 4096\) and vocabulary size \(V = 128{,}000\) (the figures quoted for an 8-billion-parameter model in the Llama family). One \(V \times D\) matrix holds \(128{,}000 \times 4096 = 524{,}288{,}000\) entries, about 525 million parameters. Because the input and output sides share this one matrix through the transpose, those roughly 525 million parameters serve both the embedding and the unembedding step. A separate output matrix would add a second 525 million — over a billion embedding-adjacent parameters in total. Answer: tying saves about 525M parameters here.

Scope: Tying assumes the input representation and the output scoring want the same geometry — what makes a good input vector also makes a good output direction. Most decoder-only models accept this trade; some architectures untie the matrices to buy extra capacity at double the embedding cost.

Pitfalls: Transpose, not inverse. \(E^\top\) just flips rows and columns so the shapes fit; it does not undo the embedding. Also, \(E\) itself is \(V \times D\) while the projection needs \(D \times V\) — forgetting the transpose is the classic shape error in exam numerics.

Recap: One \(V \times D\) table does double duty — rows looked up on the way in, columns (via transpose) scored on the way out — saving hundreds of millions of parameters while keeping each token's representation consistent. With the head fully built, the next question is where it attaches during inference versus training.

2.7 Inference with the Last Token and Parallel Training

The diagram shown in class is inference: only the last position carries the language modeling head, because only the next token is being predicted. During training, by contrast, the head is applied at every position, so that next-token prediction — and the attention behind it — happens in parallel at all positions, the same way attention values are computed in parallel.

Hook: Inference is like finishing one sentence before starting the next — you must read your own last word to choose the following one. Training is like a teacher grading a whole worksheet at once, because the answer key (the true next words) is already printed.

A concrete walk-through makes the positions clear. Take the sentence "language modeling head: an unembedding layer". Tokens enter a stack of \(L\) decoder layers. At the first position sits "language", at the next "modeling", and the sequence unrolls: "language" is processed, "modeling" was the predicted token that goes in as input at the next step, then "head" is predicted and goes in, then "head" leads to predicting the colon, the colon leads onward, and so the chain continues — "unembedding" gets predicted, then "layer" gets predicted. During inference this happens token by token and only the last position matters at each step. During training the whole chain is available at once, so every position predicts its successor simultaneously.

Trace — three inference steps. Start with ["language", "modeling"]. Step 1: head on "modeling" predicts "head" — append it. Step 2: head on "head" (now last) predicts ":" — append it. Step 3: head on ":" predicts "an" — append it. Result: the sequence grows by one token per step, always from the current last position. Sense-check: earlier positions never change; only the tail extends.

Scope: The last-position rule is an inference rule. In training every position carries its own head and its own loss term, because the true successor of every position is known. Decoder-only masking keeps each position from peeking at the future it must predict.

Pitfalls: The unrolled diagram looks recurrent, but the mechanism is not an RNN: training computes all positions in parallel with masking, while RNNs must step through time even in training. Also, "last token" means last so far — the window slides forward with each generated token.

Q: Why do we need only the last token? Is this, like an RNN, predicting one token at each position?

A: This is a decoder-only architecture, and every position predicts its next token — the setup only looks RNN-like because the sequence unrolls in order. During inference we care about the last position because all earlier tokens are already fixed and only the next one is unknown. During training, every position predicts simultaneously, so no position is special.

Q: When a capability is described as model-decided, is it fixed at training time or decided at runtime?

A: It is fixed during training. When a publisher releases a model, whatever the training settled — dimensions, vocabulary, context length — is frozen in. Using the model cannot change it.

Recap: Train on all positions at once, generate from the last position one step at a time. The size of that position window has its own name: context length.

2.8 Context Length

Context length (the maximum number of tokens the model can process together) is the jargon for the maximum number of tokens the model can process together. With GPT-2 this length was 512 tokens. Take the input "tell me something about LLMs." — that is 6 tokens going in. The model then generates token by token: currently 2 tokens, "LLMs" and "are", are generated, and the next token gets generated after. How long generation can continue is governed by the context length: the input sequence length that the transformer can process together. In transformer terminology this is the input sequence length — the maximum input the transformer accepts. Today context lengths are very long, so many input tokens are processed simultaneously.

Intuition: Think of a desk with fixed width. Only so many pages fit on it at once; to read a longer document, older pages must slide off as new ones arrive. The desk width is the context length — once input plus output fill it, the model cannot see further back.

Formalize — one window, input plus output. Let \(C\) (context length) be the fixed maximum, \(n\) the input tokens, and \(m\) the generated tokens so far. Generation can continue only while:

\[n + m \le C\]

where all three count tokens, not words or characters. GPT-2 fixed \(C = 512\); modern models fix \(C\) in the thousands to hundreds of thousands. The limit covers input plus output combined.

Worked example — the 6-token prompt. Input "tell me something about LLMs." counts as 6 tokens. With 2 tokens generated so far ("LLMs", "are"), the window holds \(6 + 2 = 8\) tokens. On a \(C = 512\) model, \(512 - 8 = 504\) positions remain before the window fills. Answer: generation stops (or must slide) after 504 more tokens. Sense-check: the count mixes prompt and output, never prompt alone.

Scope: Context length is read off the model's model card — on Hugging Face or the publisher's website — exactly as one would look up any other model specification. It is fixed per released model, not per request.

Pitfalls: Context length is not memory of facts — a long window does not mean the model remembers training data verbatim. It is also not the training dataset size: trillions of training tokens flow through in many windows, as the next Q&A shows.

Q: Is context length a configurable parameter we can set when we use the model?

A: No. Only that much input plus output combined can be processed, and the limit is fixed for each model. Whatever the training fixed is what every user of the model gets. The trigger here was the natural hope that a setting could stretch the window — the correction is that the window is baked into the weights.

Q: When a model trains on trillions of tokens but its context is only a few thousand, how do the two numbers relate?

A: Context is how many tokens are held and processed together at one time — one batch window. The trillions of training tokens pass through in many such windows: total tokens divided by context-sized chunks, grouped into batches. So a 4K context with 30 trillion training tokens simply means a very large number of 4K windows seen during training, and the experimental sections of the published papers spell out the batching.

Recap: Context length is the fixed input-plus-output window — 512 in the GPT-2 era, far larger today. It bounds one sitting, not the whole training corpus. Next: what the model actually learns inside those windows — the pre-training objectives.

2.9 Pre-training Objectives: Masked, Span, and Causal

Training always needs an objective: a function defined on the task, from which a loss is defined, which gradient methods then reduce. Three objectives cover the three architecture families. Encoder-only models in the BERT family use masked language modeling: mask out certain words in the input text and predict them, like a fill-in-the-blank exercise where blanks can fall anywhere in the text at random. The encoder-decoder era, with the T5 architecture, masks consecutive tokens — a span — instead of single tokens, and predicts the whole span; this is span corruption, also called the denoising objective. Almost every model in current use is decoder-only, and its objective is causal language modeling, which is nothing but next-token prediction. Because this course concentrates on generative uses, masked modeling is background while causal modeling is the working objective.

Hook: Three teachers, three quiz styles. One blanks random words anywhere (masked). One blanks whole phrases (span). One covers only the last word and always asks "what comes next" (causal). Same skill — predicting words — but only the third trains a model to keep writing.

A second-law example shows the causal pattern. Input: "second law of robotics and column" — predict the next output, "robot". The output gets appended to the input: "second law of robotics, a robot". Then predict the next one. Every predicted next token is appended to the input before the following token is predicted. The fill-in-the-blank here is only at the end, unlike masked modeling where blanks sit anywhere.

A side-by-side contrast keeps the three straight:

Objective Architecture Blank placement Predicts
Masked modeling Encoder-only (BERT) Random positions anywhere Each masked token
Span corruption (denoising) Encoder-decoder (T5) Consecutive spans Whole span
Causal modeling Decoder-only End only Next token

When to pick which: use causal for generation, masked for understanding and filling gaps, span for sequence-to-sequence repair. This course lives in the causal column.

Scope: All three are language modeling because all three predict words — the difference is only where the blanks may fall and which direction the model may look. Causal models see only the past; masked models see both sides.

Pitfalls: Do not call masked modeling "not language modeling" just because it does not generate left to right. And do not assume blanks can fall anywhere in every objective — that freedom belongs to masked and span objectives only.

Q: Can a span or a mask fall anywhere? Is masked modeling just fill-in-the-blank too?

A: Yes — both are language modeling because both predict words. Masked modeling blanks out tokens anywhere in the text and trains the model to fill them during training (wrong guesses at first, correct ones as iterations proceed). Span corruption blanks consecutive tokens. Causal modeling blanks only the end: it always predicts the next token. The trigger was over-generalizing "anywhere" to every objective — the correction pins "anywhere" to masked and span, "end only" to causal.

Recap: Masked fills random blanks, span fills blanked phrases, causal predicts the next token — and generative work runs on causal. Training that causal predictor efficiently needs one more trick: teacher forcing.

2.10 Teacher Forcing and the Training Loss

During inference, the input at each position is the model's own previous prediction: the output of one step becomes the input to the next. That is the decoder-only architecture — output of the previous step feeds the next step — and it is necessarily sequential. Waiting for each token to be generated before feeding it back would make training extremely slow. But during training the entire corpus is already available. The input at each position can therefore be the true previous token rather than the model's guess, and with all true inputs in hand, attention and all the \( \hat{y} \) predictions compute in parallel — the red feedback connections of the inference diagram are simply removed. This is teacher forcing: it was introduced for RNNs, and it speeds up training by parallelizing it.

Purpose. Teacher forcing exists to make training parallel. Feeding true history instead of generated history removes the sequential bottleneck while keeping the prediction task identical.

Inputs and outputs. Inputs: the full true token sequence \(x_1, \dots, x_T\), where each position sees only the true tokens before it. Outputs: one predicted distribution \(\hat{y}_t\) per position, computed in a single parallel pass.

Steps. First, shift the true sequence right to form inputs (position \(t\) sees \(x_1, \dots, x_{t-1}\)). Second, run the masked model once to get all \(\hat{y}_t\) simultaneously. Third, score each \(\hat{y}_t\) against the true \(x_t\) with negative log-likelihood. Fourth, average over positions into one loss and step the optimizer. The mask is the load-bearing detail: without it, positions would peek at answers.

What remains is classical supervised machinery. The final layer is still a softmax producing \( \hat{y} \); the ground-truth token \(y\) is already known; and the two meet in a per-token negative log-likelihood — the classical cross-entropy loss — averaged over positions. Training reduces that average loss.

Formalize — average next-token loss. Let \(T\) (sequence length) be the number of token positions, \(x_t\) the true token at position \(t\), and \(p_\theta(x_t \mid x_1, \dots, x_{t-1})\) the model's predicted probability for that true token given all previous tokens:

\[L = -\frac{1}{T} \sum_{t=1}^{T} \log p_\theta(x_t \mid x_1, \dots, x_{t-1})\]

where \(L\) is the average next-token loss minimized during pre-training. Each term is large when the model assigns low probability to the true next token, small when it assigns high probability.

Trace — "So long and thanks for". Take the sentence "So long and thanks for" processed by a decoder-only model with a causal objective. At the position holding "So", the model outputs a distribution; the ground truth for that position is "long". At the position holding "long", the ground truth is "and", and so on down the line. Suppose the four true-next probabilities are \(0.5, 0.25, 0.8, 0.4\). The loss is \(-\frac{1}{4}(\log 0.5 + \log 0.25 + \log 0.8 + \log 0.4) \approx 0.86\). Because teacher forcing supplies every true input up front, all these \(\hat{y}\) distributions compute in parallel, one cross-entropy term is evaluated per position against its known ground truth, and the terms are averaged into a single loss for the gradient step. Answer: \(L \approx 0.86\). Sense-check: probabilities below 1 give positive loss, and the weakest link (0.25) dominates.

When to use vs. alternatives. Teacher forcing is the training-time choice whenever true sequences are available — always in pre-training. At inference there is no answer key, so the model must feed its own outputs. That gap (training on truth, testing on guesses) is a known skew, but the parallel speedup wins by orders of magnitude.

Pitfalls: Teacher forcing does not change the objective — the loss is still next-token cross-entropy. It only changes what feeds each position (truth instead of guesses) so computation parallelizes. Forgetting the causal mask while forcing would leak the answer into the input.

Recap: Train on true history in parallel, test on generated history in sequence — same loss, very different speed. That loss has a famous exponentiated cousin: perplexity.

2.11 Perplexity

Alongside the loss, the metric generally reported during training is perplexity, which is the exponential of the loss: \( \mathrm{PPL} = e^{L} \). (Equivalent forms exist; computing it from the loss this way is the working rule.) The lower the perplexity, the better the next-token prediction — lower perplexity means lower loss. When following the training of published models, perplexity is one of the numbers worth watching.

Intuition: Think of perplexity as the model's average number of live options. A perplexity of 1 means total certainty — one live option, the right word. A perplexity of 100 means the model hesitates among about a hundred plausible next words.

Formalize. Let \(L\) (average negative log-likelihood) be the loss from the previous section and \(e\) (Euler's number, about 2.718) the exponential base:

\[\mathrm{PPL} = e^{L}\]

where a model that assigns high probability to the true next tokens gets a small \(L\) and hence a perplexity near 1, while a confused model gets a large one. Boundary check: probabilities in \([0,1]\) give \(L \ge 0\), so \(\mathrm{PPL} \ge 1\) always — a perplexity below 1 is impossible and signals a bug.

Worked example — from loss to perplexity. Take the trace loss \(L \approx 0.86\) from the previous section: \(\mathrm{PPL} = e^{0.86} \approx 2.36\). Answer: about 2.4 live options per position. Sense-check: a perfect model gives \(e^0 = 1\); a uniform model over a 128,000-word vocabulary gives \(\mathrm{PPL} = 128{,}000\). Two landmarks anchor the scale: halve the loss and perplexity drops exponentially, not linearly.

Scope: Perplexity compares runs of the same tokenizer — different vocabularies make raw values incomparable. It also rewards fluent guessing, not truth: a confidently wrong model can look fluent while failing factuality.

Pitfalls: Lower is better, but 1 is the floor, not zero. And perplexity moves with the loss by construction — reporting both is convention, not two independent wins.

Recap: Perplexity is \(e^L\): average live options, floor 1, lower is better. With scoring settled, the view widens to the whole build — the modern LLM pipeline.

2.12 Modern LLM Development Pipeline

Classical machine learning has a training loop with gradient-descent optimizers and hyperparameters; LLM pre-training has the same loop, but the surrounding pipeline has grown. End to end, the stages are: pre-processing, pre-training, post-training, with optimization running across stages. The classical text steps — punctuation handling, casing choices — now sit beside filtering, synthetic data generation, and data mixing in the pre-processing pipeline. Pre-training itself runs in stages: long-context extension, continued pre-training, a high-quality stage, knowledge distillation. Post-training holds fine-tuning: supervised fine-tuning, reinforcement learning with human feedback, and direct preference optimization, which arrive after the mid-semester point. Modal alignment, or reference alignment, belongs here too. Once trained, the model is evaluated with standard procedures and its weights are saved or loaded.

Hook: Building a model today is less like baking one cake and more like running a food factory — sourcing ingredients, test kitchens, packaging lines. The oven (gradient descent) is unchanged; everything around it grew.

The older picture was simpler: text-only data through a simple pipeline, with one core pre-training objective — next-token prediction. The modern version feeds far more: books, web crawls, mathematics, code, multimodal data, synthetic data, all integrated. Training runs as a staged pipeline — first general knowledge, then capabilities like reasoning, then long-context handling — but at every stage, traditional or modern, the pre-training objective stays the same: next-token prediction. After pre-training comes post-training: instruction tuning and preference alignment, which turn the raw pre-trained model into something usable.

Scope: The staged picture describes frontier practice. Small or specialized builds may skip stages (no long-context extension, no distillation), but the order — clean data, then pre-train, then align — stays fixed.

Pitfalls: Do not mistake post-training for a new objective: instruction tuning and preference alignment reshape behavior, yet the pre-training stages underneath all optimize next-token prediction. Skipping evaluation before saving weights is the operational twin of that error.

Exam note: The staged nature of modern pre-training versus the classical single-stage picture is exactly the kind of contrast worth being able to draw. One loop, many stages, one pre-training objective throughout.

Recap: Pre-process, pre-train in stages, post-train to align, then evaluate — with optimization across all of it. The fuel for every stage is data that labels itself, which is the next topic.

2.13 Self-Supervised Learning

Supervised learning needs inputs \(X\) and labels \(Y\). In classical settings humans generate the labels, possibly with tool help, and then input plus label make supervision. In language modeling, what are the input and the label? Take raw text "language modeling head …": in one iteration the model input is "language" and the label is "modeling"; in the next iteration the input is "language modeling" and the label is "head"; and so on down the line. Nobody created these labels — they were already sitting in the text. The only work is a script that organizes raw text into input-output pairs, so the learning is called self-supervised: the supervised signal exists, but humans did not annotate it.

Intuition: Think of a textbook with the answers printed faintly on the next page. Cover the next page, guess, then uncover to check — the book supervises you, yet no teacher wrote a separate answer key. Rows of spreadsheet data are the opposite: every label cell starts blank until a human fills it.

This reframes dataset size. Every token in the corpus is a free training example, which is where the word "large" in large language models partly comes from. Structured data counts rows — ten thousand, fifty thousand, a lakh of rows; image work counts images. Text work counts training tokens, because each token is one training example. So model releases quote training tokens, not gigabytes: the token count is the dataset size.

The same self-supervised idea carries into fine-tuning, but with a difference: pre-training labels come free from raw text, while fine-tuning needs its own training examples with labels generated for the task. The pre-trained model holds general knowledge and language capability but is not yet useful for any particular task; further training — post-training, or fine-tuning — reshapes it into a classifier, an instruction follower, a personal assistant, a chatbot. Nothing is added architecturally in the basic picture: the same model keeps training on new data, the way transfer learning carried CNN knowledge forward, except here the whole model continues training rather than gaining new layers.

Scope: Self-supervision covers the signal source, not the absence of supervision — gradients still flow from a loss against targets. Free labels apply to raw-text pre-training; task fine-tuning pays for its labels separately.

Pitfalls: "No labels" is the common misread — there are labels at every position, just no annotators. And dataset size in tokens is not file size in gigabytes: tokenization and packing decide how bytes become countable examples.

Recap: Raw text is its own answer key — each token a free label — which is why token counts measure datasets. Turning that raw text into clean windows is the pipeline's next job.

2.14 Pre-training Data Pipeline

Suppose abundant resources and a sponsor are available and the goal is to train a new model from scratch. The pipeline starts with a raw corpus: web crawls, books, code, papers, open or licensed data — with licensing taken seriously, since data use without regard to privacy and ownership has led to disputes and court proceedings. Then, because nobody can hand-check every page, filters are designed. Heuristic if-then filters drop wrong-language text, very short documents, spam, or blocklisted sites, depending on what capabilities the model should have. A second family trains a small classifier on high-quality text and scores every document for quality. Then comes deduplication: the same paragraphs repeat across sites and books — news stories appear on every news site — and without removal the model would memorize repeated text, mistaking repetition for importance, while burning compute on zero new learning. Then personal information is stripped: emails, names, phone numbers, IDs. Then tokenization converts the cleaned corpus into tokens with any standard algorithm. Finally comes packing.

Purpose. The pipeline turns an untrusted, uneven web dump into fixed-size, high-signal training windows without leaking private or duplicated text into the weights.

Inputs and outputs. Inputs: raw documents of mixed length, language, and quality. Outputs: packed token windows of exactly the model's sequence length, separated by end markers, padded only at the very tail.

Steps. First, gather licensed raw text. Second, filter by heuristics and by a cheap quality classifier. Third, deduplicate repeated passages. Fourth, strip personal information. Fifth, tokenize. Sixth, pack short documents back to back with separator tokens. Deduplication theory runs deep — sentence-level versus paragraph-level removal trade recall against precision — and the assignment on picking up a raw PDF and running the pre-processing stages makes each step concrete.

Packing deserves care because documents vary in length — one with 100 tokens, another with 1000 — while the model processes a fixed input sequence length. Feeding a 100-token document alone into a 1000-token window wastes 900 positions on padding. Instead, documents are packed back to back with a separator token (end of sentence or end of document) between them, and padding appears only at the very end if at all. With GPT-2's 512-token window, several short documents share one window; with a 4096-token window, far more packs in. There is real theory behind deduplication — sentence-level versus paragraph-level removal — and the place to try these steps hands-on is the assignment on picking up a raw PDF and running the pre-processing stages.

Trace — packing 100 + 250 + 750 into 1000. Without packing: the 100-token document wastes 900 padding slots. With packing: lay down 100 tokens, one separator, 250 tokens, one separator, then 648 of the 750 tokens — the window fills at 1000 with 2 separators used. Result: one full window plus a 102-token remainder carried to the next window, instead of three mostly-empty windows. Sense-check: separators cost a few slots but padding collapses from ~1900 wasted slots to nearly zero.

Scope: Packing never crosses the separator blindly during training — attention masking keeps each document from reading its packed neighbor where the objective requires it. Heuristic filters are cheap and fast; classifier filters cost more but catch subtler quality issues.

Pitfalls: Skipping deduplication is the expensive error: repeated paragraphs look like important patterns to the loss and burn compute on zero new learning. Treating every bare number as private data is the opposite error — over-stripping deletes harmless statistics.

Q: With documents of 100, 250, and 750 tokens and a 1000-token window, is padding still needed under packing?

A: Padding is not gone entirely, but it shrinks dramatically. Without packing, a 100-token document wastes 900 positions. With packing, documents are concatenated with separator tokens — document, end marker, next document, end marker — and only leftover space at the very end takes padding.

Q: For removing personal information, can a model act as judge, or should that step stay heuristic? A bare number could be private data or just a statistic.

A: Both are possible, and the ambiguity is real: a number can be private or an ordinary value. A prompt-driven model can be tested for the task, but models are expensive at corpus scale. The cost-aware answer is to start with rules or a small trained classifier for identification and removal, and reserve model-as-judge machinery for stages where its judgment repays the cost. Always ask first whether the step genuinely needs a model.

Recap: Filter, dedupe, strip, tokenize, then pack with separators — padding survives only at the tail. Clean windows in hand, the next decision is what mix of data fills them.

2.15 Data Mixture, Curriculum, and Data Annealing

Training data arrives from many sources — web, books, scientific, mathematical, entertainment — and before pre-training begins, the team fixes the data mixture: what proportion of each data type goes in. The mixture can shift across stages, which is the data curriculum: start with easy, general material in large volume, then raise the share of specialized, high-quality data in later stages even though less of it exists. There is no fixed rule for the proportions; the decision follows the intended capabilities (more coding capability means more code data), data availability, and judgment.

Intuition: Think of coaching a runner. Early weeks are high-volume easy miles (general web text); the final weeks add scarce, sharp track sessions (math and code). The closing sharpening phase has its own name: data annealing.

Llama 3's 8-billion-parameter model illustrates the final stage, called data annealing: the learning rate is reduced gradually to zero while the share of high-quality data — math and code, upsampled by generating synthetic examples because genuine stocks are small — rises. Why lower the learning rate? Training is still training, with gradient-based updates. A small final dataset of high-quality examples could otherwise swing the weights violently: the model would memorize the new material and forget earlier learning. Shrinking updates keep the final stage stable. The small Llama 3 model improved on mathematics-related evaluations after annealing; a very large model in the same family showed little effect — a detail recorded in the long Llama 3 paper.

Formalize — annealing as schedule plus mix. Let \(\eta_t\) (learning rate at step \(t\)) decay toward zero across the final stage while the sampling weight of high-quality domains rises. Small \(\eta_t\) means small steps \(\Delta w = -\eta_t \nabla L\), so the precious final batches nudge rather than shove the weights. Annealing is therefore two coupled choices: cooler steps and richer data.

Scope: Mixture and curriculum are decided before training starts, when the team sits down to choose data — prompts belong to model usage, which comes long after. There is no universal proportion; capability targets and data stocks dictate the blend.

Pitfalls: Annealing on a tiny final set with a hot learning rate is the classic failure — violent swings that memorize the new data and erase earlier learning. And vocabulary gaps need explicit extension: finance terms missing from the table require new tokens and grown embedding matrices.

Q: Where do user prompts enter this picture of mixture and curriculum?

A: They do not — mixture and curriculum are decided before training starts, when the team sits down to choose data. Prompts belong to model usage, which comes long after the model is built.

Q: Does a lower learning rate help in most training features, or is annealing special?

A: The mechanism is general, not special: a smaller learning rate means smaller steps, hence smaller weight updates. Annealing exploits that general fact at a delicate moment — a small, precious final dataset — but learning-rate schedules that warm up and decay appear throughout classical training.

Q: Can new domain tokens, such as finance terms, extend the vocabulary during continued training?

A: Yes. If the existing vocabulary lacks specialized tokens, the vocabulary is extended to cover them, and the embedding tables grow accordingly.

Recap: Fix the mix, shift it across stages from general to specialized, and close with cool steps on rich data. With the data plan set, the budget question remains: how big a model does that data deserve.

2.16 Scaling Laws: Kaplan and Chinchilla

Two design questions open every build: how many parameters should the model have, and how large should the training data be? A bigger model with little data and a smaller model with much data are both affordable at the same budget, and compute costs real money — approximately \(C \approx 6ND\) floating-point operations for a dense transformer, with \(N\) parameters and \(D\) training tokens. Choosing blindly risks burning the whole budget on a bad combination. Scaling laws let a team train small, fit the loss curves, and extrapolate — predict the loss for bigger models, bigger datasets, or bigger budgets before spending.

Hook: Imagine buying a delivery fleet with a fixed budget: a few huge trucks with little fuel, or many small vans with full tanks. Scaling laws are the test-track runs that tell you which fleet delivers the most before you spend the full budget.

Kaplan's 2020 law came first and shaped GPT-3. It gives the loss as a function of parameters, training tokens, and compute budget, with fitted constants, so small experiments reveal how loss moves with each knob. GPT-3 fixed 96 layers and an embedding dimension of 12,288 — every token a 12,288-vector — and counted parameters with the rule \(12 \times (\text{layers}) \times d^2\): \(12 \times 96 \times 12288^2\), about 175 billion. Kaplan's guidance then set data near 300 billion tokens, roughly 1.7 tokens per parameter. That recipe — enormous by its day — now looks data-starved, and the model is too bulky to serve comfortably, which is why serving infrastructure is a separate topic.

Chinchilla (2022) redid the trade-off experimentally and mathematically: when compute rises tenfold, scale model size and data equally (about 3.2 times each), not the model fivefold and data twofold as Kaplan suggested. Its rule of thumb is 20 training tokens per parameter for the cheapest route to a given loss. Its proof was a 70-billion-parameter model on 1.4 trillion tokens that matched or beat the 175-billion-parameter GPT-3 trained on 300 billion tokens — a smaller model on far more data winning outright.

Formalize — the two budget rules. Training compute for a dense transformer scales as:

\[C \approx 6 N D\]

where \(C\) is training compute in floating-point operations, \(N\) is the parameter count, and \(D\) is the training token count. The factor 6 counts a forward plus backward pass per token per parameter. And the GPT-3 parameter count follows:

\[N \approx 12 \, n_{\text{layer}} \, d^2\]

where \(n_{\text{layer}}\) is the layer count (96 for GPT-3), \(d\) is the embedding dimension (12,288 for GPT-3), and \(N\) comes out near \(175 \times 10^9\).

Worked example — checking GPT-3's count. Compute \(d^2 = 12288^2 = 150{,}994{,}944\). Multiply by layers: \(96 \times 150{,}994{,}944 = 14{,}495{,}514{,}624\). Multiply by 12: \(12 \times 14{,}495{,}514{,}624 = 173{,}946{,}175{,}488\). Answer: about \(174 \times 10^9\), the quoted 175 billion. Sense-check: a 70B Chinchilla on 1.4T tokens gives \(1.4 \times 10^{12} / 70 \times 10^9 = 20\) tokens per parameter — the rule of thumb exactly.

Scope: These laws guide compute-optimal pre-training of dense transformers — they do not set inference cost, which favors smaller models even further. Blindly scaling one knob while starving the other burns the fixed budget.

Pitfalls: Reading 1.7 or 20 as physical law rather than fitted guidance. Each generation refits the constants; the durable lesson is the method (small runs, fit, extrapolate), not the numbers.

Recap: Kaplan said 1.7 tokens per parameter, Chinchilla said 20 — and the method behind both (train small, extrapolate, then commit) outlives the numbers. Modern practice has already moved far past both.

2.17 Compute-Optimal Training Beyond Chinchilla

Chinchilla's 20-tokens-per-parameter rule no longer describes practice. An 8-billion-parameter Llama 3 model trained on 15 trillion tokens — about 1900 tokens per parameter — and its long paper reports the team's own scaling experiments. The lesson is not that Chinchilla was wrong but that each generation refits the recipe.

Intuition: Speed limits get repainted when cars improve. Chinchilla's 20 was the right limit for its roads; wider data highways and cheaper miles moved the optimal cruising speed far higher. The sign-painting method — timed test runs — never changed.

New scaling frontiers have opened beside parameter-versus-data. Reasoning models introduce thinking tokens, so inference-time compute — how much thinking to allow — gets its own scaling law, worked out by teams including DeepSeek. Reinforcement-learning training compute gets another, with DeepSeek R1 named as a good paper on the topic. The method is always the same: run small experiments across the combinations, fit the behavior, extrapolate, and then fix the architecture — parameters and training tokens — with evidence instead of hope.

Scope: The 1900-tokens-per-parameter figure reflects abundant data and inference-friendly small models — training past the compute-optimal point on purpose because serving a small model is cheap. It does not repeal the trade-off; it re-prices it.

Pitfalls: Memorizing the algebra inside the scaling papers instead of the method. Exam questions target the approach (small experiments, then extrapolate) and the landmark numbers (Kaplan 1.7, Chinchilla 20, modern practice far higher).

Exam note: The takeaway is the method (small experiments, then extrapolate) and the landmark numbers (Kaplan 1.7, Chinchilla 20, modern practice far higher), not the algebra inside the papers.

Recap: Chinchilla's ratio was a refit of Kaplan, and modern ratios refit Chinchilla — with thinking tokens and RL compute opening new scaling axes. Data-rich small models are the current fashion; domain specialization is the next decision.

2.18 Domain Adaptation: Three Routes to a Domain Model

Foundation models pre-train on general text, but finance or healthcare work needs domain models, and three routes exist. Regular pre-training builds from scratch: design the architecture (perhaps consulting a scaling law), initialize random weights, and train on a domain-heavy dataset. Continued pre-training starts from an already pre-trained model with published weights and keeps training on a small domain corpus — the practical route, and the one exercised in the course assignment. Retraining on combined data merges the general and domain datasets and trains from scratch; it is valid but rarely popular given the cost.

Hook: Need a finance expert? Train a student from birth on bank reports (from scratch), send a graduate back for a finance degree (continued pre-training), or raise a child on a blended diet of news plus ledgers (combined retraining). The second path is cheapest when the graduate already exists.

Two finance models show the contrast. BloombergGPT (2023) went the from-scratch route at 50 billion parameters, following Chinchilla-style guidance: 345 billion general tokens plus 363 billion finance tokens, no base model. FinLlama (2024) continued pre-training from the 8-billion-parameter Llama 3, which already held general knowledge: only 18 billion general tokens plus 52 billion finance tokens, mixed about three to one, finance to general. The continued route needs far less domain data precisely because the base model brings the general knowledge along.

A side-by-side contrast:

Route Starts from Domain data needed Cost
Regular (from scratch) Random weights Huge (hundreds of billions) Highest
Continued pre-training Published base model Small (tens of billions) Lowest practical
Combined retraining Random weights, merged data Huge (general + domain) Rarely justified

When to pick which: continue from a strong base whenever one exists; build from scratch only for full control or licensing walls; merge-and-retrain almost never pays.

Scope: Continued pre-training keeps the existing layers and keeps training them — weights stay unfrozen, no new transformer layer is added. That freezing-and-layering pattern belongs to particular fine-tuning techniques, not to continued pre-training.

Pitfalls: Training on domain tokens alone mugs up the new material and overwrites old knowledge — catastrophic forgetting, which strikes fine-tuning as well. The fix is mixing general tokens back in (FinLlama kept about one quarter general). Domain data also reduces guessing on domain questions, but it is one route among several, not a hallucination cure by itself.

Q: If the base model already knows general material, why mix general tokens into continued pre-training at all?

A: Because training only on finance tokens makes the model mug up the recent data — memorize the new material and overwrite what it learned before, forgetting even simple general facts. Mixing in general tokens holds the old knowledge in place. This failure is called catastrophic forgetting, and it strikes fine-tuning as well as continued pre-training.

Q: In continued pre-training, are weights frozen or is a new layer added on top?

A: Neither. Continued pre-training keeps the existing model and the existing layers and keeps training them on the new dataset — the trainable weights, including the embedding tables, keep updating. No transformer layer is added; that kind of freezing and layering belongs to particular fine-tuning techniques, not to continued pre-training.

Q: Does continued pre-training on domain data reduce hallucination on domain questions?

A: In a loose sense, yes: a model that has absorbed domain material guesses less on domain questions. It is one practical route among several, and fine-tuning variants address the same goal differently.

Recap: From scratch, continue, or merge-and-retrain — with continued pre-training the practical winner, general tokens mixed in to hold old knowledge. The forgetting it guards against deserves its own section.

2.19 Catastrophic Forgetting and Learning-Rate Schedules

When a trained network learns new data such as finance text, weight updates overwrite the old ones — sometimes shifting the whole weight distribution — so recent data gets mugged up and earlier knowledge is lost. Three mitigations are used in practice. Data mixing, as FinLlama did with 25 percent general tokens, keeps old patterns in the gradient. A careful learning-rate schedule does the same dynamically. And parameter-efficient fine-tuning, with LoRA named as the example technique, limits which weights may move — full detail belongs to the fine-tuning sessions.

Intuition: Think of repainting one room while the rest of the house stays furnished. Data mixing keeps walking through the old rooms (old patterns stay in the gradient); a gentle schedule uses a small brush near finished walls; LoRA puts drop cloths over most furniture and paints only the trim.

The classical schedule is warm-up followed by decay: start the learning rate small, raise it gradually to its maximum (warm-up), then decay it slowly toward the end of training. Late training should make only small updates so the run stabilizes and converges with negligible weight changes, and stopping lands where updates are tiny. Continued pre-training for domain adaptation then repeats the pattern with re-warm-up and re-decay: the same rising-and-falling shape, replayed on the new data.

Scope: Warm-up avoids early violent steps when weights are raw; decay avoids late thrashing when weights are nearly done. Re-warm-up plus re-decay replays that protection on domain data instead of blasting a converged model with a hot rate.

Pitfalls: Resuming domain training at the old peak rate is the classic forgetting trigger. And schedule discipline cannot fully replace data mixing — tiny rates on pure domain data still drift the distribution eventually.

Recap: Mix old data in, warm up gently, decay to a quiet stop — and replay the shape for each domain round. Two published builds show the full recipe in action.

2.20 Case Study: Llama 3 405B Pre-training

Llama 3's largest model pre-trained in three stages. Initial pre-training captured general knowledge: about 15.6 trillion tokens at 8K context, with the batch size stepping up from 4 million to 8 million to 16 million tokens during training. Long-context pre-training then extended the model to 128K context using 800 billion tokens — a second stage devoted to long inputs. Data annealing closed the run: the learning rate fell to zero while the share of math and code data rose.

Hook: Fifteen trillion tokens is a library no human could shelve — so the builders hired librarians made of smaller models to sort it.

Its data filtering pipeline is the interesting part. Web data first passed heuristic filters — cleaning, deduplication, safety filters. Then the team's own Llama 2 model labeled the surviving documents as high or low quality, producing a small supervised dataset. On that dataset they trained cheap classifiers — an embedding-based classifier and a compact encoder-based classifier — and those classifiers scored the full web corpus into high and low quality. Using a model as judge for data filtering, with minimal human labeling, is now standard practice — though not every organization publishes its recipe, so much of the field's filtering stays undisclosed.

Scope: The stage order here is general knowledge, then long context, then annealing — Qwen's build orders its stages differently, which is normal. The durable pattern is staged training with a quality-closing phase, not any single order.

Pitfalls: Treating classifier filtering as perfect. Cheap judges inherit the biases of their small labeled samples, and undisclosed recipes elsewhere mean no universal quality bar exists.

Recap: General pre-training at 8K, long-context stretch to 128K, annealing to zero — with model-as-judge classifiers enforcing quality at web scale. Qwen's build runs the same playbook with different stage order.

2.21 Case Study: Qwen 3 Pre-training

Qwen 3 also trained in three stages, ordered differently: general first, reasoning second, long context third. The first stage used 30 trillion tokens at 4K context with multilingual coverage of 119 languages. The reasoning stage added STEM, code, and synthetic data for mathematical, scientific, and coding capabilities. The third stage stretched context from 4K to 32K. Total training reached about 36 trillion tokens — double the 18 trillion of Qwen 2.5, which covered 29 languages. Two data tricks stand out: PDF extraction with the team's own vision-language models, which read PDFs into text cheaply, and synthetic data from their own math and coder model variants, generating question-answer, coding, and mathematics examples. A final mixing ratio balanced educational value, safety, and the rest. The Qwen 3 technical report carries the full detail, as the long Llama papers do for their family.

Intuition: If Llama hired librarians to sort the shelves, Qwen also hired translators and textbook authors — vision models to ingest PDFs, and math/coder models to write fresh practice problems where genuine stocks ran thin.

Scope: The headline numbers (36T tokens, 119 languages) describe one frontier build, not a requirement. The transferable ideas are staged capabilities, cheap PDF ingestion, and synthetic gap-filling — all reusable at smaller scale.

Pitfalls: Synthetic data compounds errors if unchecked — generated problems need the same quality filtering as web text. And stage order is a choice, not a law: Qwen reasons before stretching context, Llama stretches before annealing.

Exam note: These case studies are background color for understanding staged modern pre-training, not memorization material — questions come from class material and discussions, and sample questions will show the pattern.

Recap: General multilingual base, reasoning enrichment, then context stretch — 36 trillion tokens with synthetic and PDF-mined ingredients. Two builds, one staged moral: general first, specialized later, quality always.

Key Industry Applications

Hugging Face hosts model cards, benchmarks, and monthly new open-model releases, making it the standard way to track the landscape and to look up any model's context length and specifications. A shared embedding matrix with transpose reuse (weight tying) keeps input and output token representations consistent while saving hundreds of millions of parameters, as the 525-million-parameter Llama tables show. Greedy decoding — emitting the highest-probability token — is the default generation rule behind every chat interface, with fancier decoding rules layered on later. Continued pre-training turns a general open-weight model into a finance, healthcare, or other domain model at a fraction of from-scratch cost, the FinLlama versus BloombergGPT contrast being the canonical example. Classifier-based filtering with a model as judge is how web-scale corpora become high-quality training data, the Llama 3 pipeline being the published reference. PDF extraction with vision-language models and synthetic data generation from existing math and coder models are now routine corpus-building tools, as the Qwen 3 build shows. Knowledge distillation — training a small model from a larger teacher, as done for a compact model in the Gemma family — compresses capability into deployable size, alongside the other optimization techniques of the modern pipeline.
