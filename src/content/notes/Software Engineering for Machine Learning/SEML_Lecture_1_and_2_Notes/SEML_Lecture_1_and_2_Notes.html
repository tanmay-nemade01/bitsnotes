1. Introduction: Why Software Engineering for ML?

Traditional software engineering (SE) has matured over four to five decades, producing well-established processes, tools, and best practices. Machine learning (ML), however, introduces fundamentally new challenges: the artefact you deploy is no longer just code — it is code + data + model. This course bridges the gap by applying proven SE principles to the ML lifecycle.

Building production ML systems is notoriously difficult: consultants report that 87% of ML projects fail and 53% never make it from prototype to production. Building an accurate model is hard enough, but building a product requires also collecting the right data, constructing the surrounding system, protecting users from model mistakes, and successfully deploying, scaling, and operating the service — all of which demand far more than just data science skills.

Core Thesis of This Course
Software Engineering → apply principles → Machine Learning

We take established SE best practices (requirements engineering, architecture, design patterns, CI/CD, testing, deployment, monitoring) and adapt them to ML systems where data and models are first-class citizens alongside code.

2. Software Engineering Foundations (Recap)

1-2.3 The Software Development Life Cycle (SDLC)

The SDLC is the structured process used to plan, develop, test, and deploy software systems. Over decades, various models have emerged:

Table 1: Common SDLC Models
ModelKey Characteristics
Waterfall Sequential phases (Requirements → Design → Code → Test → Deploy). Rigid; changes are costly after a phase completes.
Agile / Scrum Iterative sprints (2–4 weeks). Embraces changing requirements. Most widely used today.
DevOps Extends Agile with continuous integration and continuous deployment (CI/CD). Bridges dev and ops teams.

1-2.4 Code as the Central Artefact

In traditional SE, code is everything. The entire SDLC revolves around writing, testing, versioning, and deploying code.

  • Version control: Git / GitHub repositories.
  • Quality assurance: unit testing, integration testing, code reviews.
  • Configuration management, debugging, and bug fixing.
  • CI/CD pipelines for automated build, test, and deployment.
Key Insight
In software engineering, when the requirement changes, ultimately it is the code that must change. The changing variable deployed to production is the code alone.

In ML, there are three changing variables: code, data, and the model. This is the fundamental complexity increase.

1-2.5 Deterministic Nature of SE

Traditional software is deterministic: given the same input, the system always produces the same output. Programs follow explicit rules (if–else, loops, function calls).

Example: Swiggy Order Processing
When you place an order on Swiggy:
  1. The order is validated → payment is processed → restaurant is notified → delivery is assigned.
  2. Each step follows well-defined business rules.
  3. The system either succeeds or fails — there is no "90% chance your order went through."
This is functional correctness: every function works exactly as specified.

4. Machine Learning Foundations

1-2.8 What is Machine Learning?

Machine Learning is a subset of Artificial Intelligence where systems learn from data rather than being explicitly programmed with rules.

Definition
A model is a trained algorithm used to make predictions or decisions in the real world. It goes through stages: development → deployment → monitoring.

1-2.9 The Three Changing Variables in ML

This is the central complexity of ML compared to traditional SE:

Figure 3: Increasing complexity — from SE (1 variable) to ML (3 variables).
Software EngineeringData ScienceMachine Learning
Code Code + Data Code + Data + Model
  • Code: The algorithms, scripts, and infrastructure code.
  • Data: Training data, schema changes, structured/semi-structured/unstructured data, batch vs. real-time, data volume considerations.
  • Model: Which algorithms are used, hyperparameters, experiments, versioning of models.

1-2.10 The ML Pipeline

The ML pipeline is a structured workflow that takes raw data through to a deployed, monitored model:

Figure 4: The ML Pipeline with feedback loop for continuous improvement.
Manage DataTrain ModelEvaluate ModelDeploy ModelMonitor Model
Collect, Clean, EDA, Split Feature Eng., Algorithm Select Metrics, Compare Models Push to Production Observe, Improve

1-2.10.1 Stage 1: Manage Data

  • Collect data from various sources (databases, APIs, web scraping, sensors).
  • Explore the data (understand distributions, identify anomalies).
  • Cleanse the data (handle missing values, outliers, duplicates).
  • Prepare and split into training and test sets (commonly 70/30 or 80/20).
  • Optionally, use a three-way split: train / test / validation for real-world validation.

1-2.10.2 Stage 2: Train the Model

  • Identify the task type: classification, regression, clustering, etc.
  • Perform feature engineering (selecting, transforming, creating features).
  • Select algorithms based on the task:
    • Classification: Naive Bayes, SVM, Random Forest, Logistic Regression.
    • Regression: Linear Regression, Ridge, Lasso.
    • Deep Learning: LSTM, GRU (sequential data), CNN (vision tasks).
  • Multiple algorithms can be trained in parallel — the pipeline need not be purely sequential.
Training is Often Non-Deterministic
For many machine-learning algorithms, repeated training on the same data can produce slightly different models. This is because the learning process itself involves randomness (e.g., weight initialization, data shuffling). This has important implications for reproducibility and debugging — two training runs are rarely identical.

1-2.10.3 Stage 3: Evaluate the Model

  • Assess performance using appropriate metrics:
    • Classification: Confusion matrix, Precision, Recall, F1-score, AUC-ROC.
    • Regression: MSE, RMSE, MAE, R² score.
  • Compare multiple models and select the best performer.
  • The data scientist typically compares model metrics and decides which model to push to production.

1-2.10.4 Stage 4: Deploy the Model

  • Push the selected model to the production environment.
  • Deployment is not the end of the lifecycle — continuous monitoring is essential.

1-2.10.5 Stage 5: Monitor the Model

  • Continuously observe model outcomes and performance metrics.
  • Detect model drift (when the model's accuracy degrades over time as data distributions change).
  • Trigger retraining when performance drops below acceptable thresholds.
  • Observability tools and safety measures are critical here.
Sequential vs. Parallel Steps
Some steps are inherently sequential (you cannot do EDA before cleaning; you cannot create a model before EDA). However, algorithm selection and training can be done in parallel. After deployment, the feedback loop sends new insights back to earlier stages.

1-2.11 Pre-processing: Training Data vs. User Data

A crucial distinction exists between two types of pre-processing:

Table 2: Two Types of Data Pre-processing
AspectTraining Phase Pre-processingInference Phase Pre-processing
PurposeClean and prepare training dataClean and normalize user input before feeding to the model
WhenDuring model developmentDuring production, on every user request
ExampleHandling missing values, feature scalingCorrecting grammar in a ChatGPT prompt, normalizing tweet text
Example: ChatGPT Pre-processing
When you type a prompt into ChatGPT with grammatical errors, the system doesn't just pass your raw text to the model. A pre-processing layer cleans and normalizes your input (potentially before or during tokenization) before the model processes it. This is separate from the training-phase data cleaning.
The principle: Garbage In = Garbage Out.

5. ML Domains: NLP, Computer Vision, and Speech

Machine learning applications broadly fall into three domains based on the modality of data they process.

1-2.13 Natural Language Processing (NLP)

NLP deals with enabling machines to understand, interpret, and generate human language.

Key NLP Tasks:

  • Text Classification
  • Text Summarization
  • Named Entity Recognition (NER)
  • Text Generation
  • Machine Translation
  • Language Modelling
  • Question Answering
Example
When you ask ChatGPT a question and it provides a response, it is performing a question answering task. When Google Translate converts English to Hindi, it is performing machine translation.

1-2.14 Computer Vision (CV)

Computer Vision enables machines to interpret visual information from images and videos.

Key CV Tasks:

  • Object Detection
  • Face Recognition
  • Feature Extraction
  • Image Classification
  • Image Restoration / Colorization
  • Video Processing
Example: DigiYatra at Indian Airports
The DigiYatra application uses face recognition to verify travelers at airports. Earlier systems (circa 2020–21) required 10–15 photos per person using CNNs. Modern systems can recognize a person from a single photo, even taken from a side angle — demonstrating the rapid advancement in CV capabilities.

1-2.15 Speech Recognition

Speech recognition converts spoken language into text and enables voice-based interactions.

Key Tasks:

  • Automatic Speech Recognition (ASR) — converting speech to text.
  • Transcription services for meetings, call centers.
  • Voice assistants: Siri, Alexa, Google Assistant.
Multimodal AI: The Sophia Robot
The Sophia robot by Hanson Robotics combines all three domains:
  • Computer Vision: Facial tracking, recognition, and expressions.
  • NLP: Understanding and generating natural language; telling jokes and stories.
  • Speech Recognition: Understanding spoken input and responding verbally.
This is an example of multimodal AI — using multiple ML domains simultaneously. The compute requirements for such systems are enormous, typically requiring dedicated GPU hardware connected to cloud services.

6. Foundation Models and Large Language Models

1-2.16 What is a Foundation Model?

Definition
A Foundation Model is a large-scale ML model trained on a vast, diverse corpus of data. Like the foundation of a building, it provides a base upon which specialized models can be built. Foundation models are general-purpose and modality-agnostic.

Foundation models represent a fundamental shift in how ML projects operate. Instead of training a custom model for each task, organizations can use a single general-purpose model and instruct it to perform specific tasks through prompts. For example, rather than training a toxicity classifier on labeled examples, you can prompt a foundation model: "Answer only yes or no. Is the following sentence toxic: [input]."

Two common strategies customize foundation models for specific needs:

  • Fine-tuning: Further training a copy of the foundation model on domain-specific data (e.g., training on internal emails or gaming forum messages to understand specific jargon).
  • In-context learning: Providing additional information or examples directly in the prompt without modifying model weights — such as few-shot prompting, where several input-output examples are given before the actual query. Retrieval-Augmented Generation (RAG) is a popular form of in-context learning where internal documents are retrieved and included in the prompt.

8. Software Engineering vs. Machine Learning: Key Differences

There is an ongoing debate about whether ML fundamentally changes how we engineer software or whether we simply need to rigorously apply existing practices. The textbook's central conjecture is that ML projects tend to fall toward the more complex and riskier end of the software spectrum, calling for greater investment in rigorous engineering. We are not introducing entirely new challenges, but the use of ML amplifies complexity and risk — meaning we are less likely to get away with sloppy engineering practices.

1-2.18 Deterministic vs. Probabilistic

Figure 7: The fundamental paradigm difference between SE and ML.
Deterministic (SE)Probabilistic (ML)
  • If–else, loops, rules
  • Same input ⇒ same output
  • Example: Payment gateway processes or fails — no ambiguity
  • Rule-based execution
  • Probability-based predictions
  • Same input may yield different confidence scores
  • Example: "Pug dog 99.0%, Terrier 0.07%, Other 0.01%"
  • Highest probability is selected
Example: Dog Breed Classification
If you show an image of a pug to an ML model, it will not say "This is a pug" with 100% certainty. Instead, it outputs:
  • Pug: 99.0%
  • Terrier: 0.07%
  • Bulldog: 0.01%
  • …
The system selects the highest probability answer. This is fundamentally different from a traditional SE system where a function either returns a value or throws an error.

1-2.19 Why ML Requirements Must Be Well-Defined

Key Challenge
Many ML projects fail because requirements are not well-defined. Unlike SE where specifications are precise, ML requirements can be vague (e.g., "detect objects in an image" — but which objects?). If the training data doesn't contain dogs, the model cannot recognize dogs.

Impact: Poor requirements → wrong architecture → wrong model → wrong deployment → project failure.

This is why requirements engineering (covered from session 3 onwards) is critical for ML projects.

9. The Three AI Paradigms

Modern AI can be classified into three paradigms: Predictive, Generative, and Agentic.

1-2.20 Predictive AI

Predictive AI
Uses past data to predict future outcomes. This is the classical ML approach from the late 1990s to approximately 2018.

Characteristics:

  • Uses labeled historical data (e.g., Kaggle datasets like Titanic, Iris, Pima Indian Diabetes).
  • Applies classical ML algorithms (SVM, Random Forest, Logistic Regression, etc.) and early deep learning models.
  • Moderate training requirements — can work with datasets of 1,000+ rows.
  • Can run on CPUs; Google Colab free tier is sufficient.
  • Output: predictions/classifications based on learned patterns.
Example: Diabetes Prediction
Given a dataset of 1,000 patients (50% diabetic, 50% non-diabetic) with features like age, blood sugar level, BMI, etc.:
  1. Train multiple algorithms (SVM, Naive Bayes, Random Forest) on 70% of the data.
  2. Test on the remaining 30%.
  3. The trained model can now predict whether a new patient is likely diabetic or non-diabetic.
This is predictive AI — using historical data to predict future outcomes.

1-2.21 Generative AI

Generative AI
Creates new content (text, images, audio, video, code) based on learned patterns. Emerged strongly after Google's 2017 "Attention Is All You Need" paper and the transformer architecture.

Characteristics:

  • Trained on vast, diverse datasets (essentially the entire World Wide Web).
  • Requires massive computational resources (GPUs, TPUs).
  • Based on transformer architecture (BERT, GPT series).
  • Can generate text, code, images, and more.
  • Still probabilistic — uses next-token prediction under the hood.
Key Insight
Generative AI uses predictive AI under the hood. At its core, it still performs next-word/token prediction. The key differences are:
  • Scale of training data (20 pages vs. 20 books × 20 pages).
  • Computational power required.
  • Quality and diversity of outputs.

1-2.23 Agentic AI

Agentic AI
AI systems that can autonomously take actions, use tools, and interact with external systems (web search, APIs, databases) to accomplish goals. Represents the latest evolution in AI capabilities.

Key Capabilities:

  • Tool use: Can perform web searches, execute code, query databases.
  • Real-time data: Overcomes the training data cutoff limitation.
  • Autonomous planning: Can break down complex tasks into steps.
  • Multi-step reasoning: Can chain multiple actions together.
Example: How Agentic AI Solves the Training Cutoff Problem
Problem: ChatGPT (GPT-3.5, Nov 2022) was trained only until September 2021. If you asked "Who is the CM of Karnataka?" it could only answer based on 2021 data.

Agentic Solution: Modern systems use web search tools. Instead of guessing from stale training data, the agent performs a live web search, retrieves current information, and provides an accurate, up-to-date answer.

For coding tasks, it uses pre-trained knowledge (no web search needed). For real-time queries (election results, current events), it triggers a web search.

1-2.25 Is Probabilistic the Same as Generative?

Common Misconception
No! All ML models are probabilistic, but not all probabilistic models are generative.
  • A classification model (e.g., spam detection) is probabilistic but predictive, not generative.
  • A flight route optimization model uses probabilistic predictions (e.g., "Route A–B has 85% chance of profitability") but doesn't generate new content.
  • Generative models specifically create new data (text, images, audio) that didn't exist before.
Probabilistic ≠ Generative. Generative ⊂ Probabilistic.
