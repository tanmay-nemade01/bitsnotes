Chapter 1: MLflow Model Registry — Recap and Deep Dive

7.1 The Model Registry Pattern

The Model Registry pattern is a specialized form of the generic Registry pattern, tailored specifically to machine learning workflows. Its core purpose is to provide a centralized, versioned repository for trained ML models, along with all associated metadata that defines how each model version was produced. Unlike a simple file store, a model registry captures the complete provenance of each model artifact: the dataset used, the algorithm and hyperparameters chosen, the code that executed the pipeline, the evaluation metrics achieved, and the system-level performance characteristics observed during training.

Core Insight: In an ML system, three things can change between model versions: (1) the code (preprocessing logic, feature engineering, the training script itself), (2) the dataset (new data, data drift, schema changes), and (3) the algorithm or hyperparameters. A model registry must track all three dimensions of change, not just code as in a traditional software VCS like Git.

7.2 MLflow Registry in Practice

MLflow provides a built-in model registry that integrates directly with MLflow's experiment tracking capabilities. The registry operates on a concept of registered models — named entities that can have multiple versions. Each version represents a distinct training run with its associated artifacts.

Consider a text-classification pipeline for COVID patient discharge prediction using a Random Forest classifier. The pipeline involves:

  • Loading and preprocessing a structured dataset (covid_data.csv)
  • Training a Random Forest classifier on the preprocessed data
  • Evaluating the model using standard classification metrics: accuracy, precision, recall, and F1 score
  • Logging the trained model to the MLflow registry under the name COVID_discharge_RF_model

The registration step is accomplished via the MLflow tracking API. After running mlflow server --port 5000 to start the tracking server, the Python script executes the pipeline and calls the MLflow log-and-register functions. The model appears in the MLflow UI under the designated experiment with a unique run ID, timestamped registration date, and a version number.

7.2.1 Stage Management: Staging and Production

Each model version in the MLflow registry resides in exactly one of several lifecycle stages:

  • Staging: The model version is under evaluation — validated against holdout data, undergoing A/B testing, or awaiting sign-off before production deployment. Multiple versions can exist in staging simultaneously.
  • Production: The model version is actively serving predictions in the live system. Typically only one version occupies production at a time, though canary deployments can place traffic on multiple production versions.
  • Archived: Older versions that are no longer in active use but retained for auditability and rollback purposes.

Transitioning a model from staging to production is a deliberate, manual or policy-driven action — it is not automatic. This gating mechanism ensures that only validated models reach end users. Version numbers increment independently of the stage; you may have version 5 in staging while version 4 serves in production, with the option to swap them after validation.

7.2.2 What Gets Stored in a Registry Entry?

Each version in the registry captures an immutable snapshot of the training context:

  • Dataset identity: Which dataset was used (name, version, hash, or timestamp)? Data changes are a primary driver of model versioning.
  • Algorithm and hyperparameters: The model class (e.g., RandomForestClassifier) and all hyperparameter values (e.g., n_estimators=100, max_depth=10). These are classified as model parameters.
  • Learned weights: The trained model artifact itself — the serialized model object containing the fitted parameters.
  • Evaluation metrics: Accuracy, precision, recall, F1 score, AUC-ROC, and any custom metrics logged during training.
  • System parameters: Resource utilization during training — CPU usage percentage, memory consumption, execution time, and node identity if running in a distributed environment. These system parameters are distinct from model hyperparameters and provide operational observability.
Exam Tip: Distinguish between model parameters (hyperparameters you set before training — learning rate, tree depth, regularization strength) and system parameters (observed during training — CPU usage, memory footprint, wall-clock time). Both are stored in the registry but serve different purposes: model parameters for reproducibility, system parameters for resource planning and cost estimation.

7.3 The Registry Pattern Beyond MLflow

While MLflow provides one implementation, the Model Registry pattern is universal across MLOps platforms. AWS SageMaker Model Registry, Google Vertex AI Model Registry, and Azure ML Model Registry all implement the same conceptual pattern: versioned model artifacts with stage transitions and metadata tracking. The pattern also appears in custom internal platforms where organizations maintain their own registry implementations backed by object storage (S3, GCS) and metadata databases.

7.4 Separating Models from Business Logic

A crucial architectural principle when deploying ML in production systems is the clear separation of model inference from business logic. Model inference is naturally modular — it receives feature vectors and returns predictions, with no side effects between invocations. The code that interprets model predictions and drives user-facing features (business logic) usually uses different technologies, is developed by different teams, and evolves at a different pace. Embedding model code directly into business logic makes updates harder and risks breaking application behavior when the model changes.

This separation typically manifests in a three-tier architecture: the presentation tier handles user interaction, the logic tier implements business rules and workflow orchestration, and the data tier manages storage. The ML inference engine sits as a distinct component within or alongside the logic tier, called through a clean API. The pipeline infrastructure for training the model and collecting telemetry is also separated from the non-ML parts of the system. This isolation means the model can be updated, A/B tested, or rolled back independently — without modifying the business logic or the frontend.

7.5 Feature Stores and Training-Serving Skew

A hidden risk in any ML deployment is training–serving skew: the feature encoding code used during training must be identical to the code used during inference. Even minor inconsistencies — a different normalization range, a different ordering of color channels, a missing preprocessing step — can silently degrade prediction accuracy. The model does not crash; it simply produces wrong outputs. To prevent this, feature encoding code should be factored into a shared library imported by both the training pipeline and the inference service, and versioned together with the model artifact.

In large organizations, the same features are often reused across multiple models. A Feature Store (e.g., Feast, Tecton, AWS SageMaker Feature Store) solves two problems at once: it catalogs reusable feature-engineering code so that teams do not reimplement the same transformations, and it can precompute or cache expensive feature vectors. Feature stores decouple feature creation from model development and serving, enabling independent evolution of each. They are particularly valuable when features involve nontrivial computations — such as running another ML model for preprocessing, or executing complex database queries — and when consistency between training and inference is critical.

Real-World Example: A fraud detection team at a financial institution maintains a model registry where each version tracks: the transaction dataset window (e.g., "Q1 2026 transactions"), the XGBoost hyperparameters, the precision-recall curve at a 95% recall threshold, and the SageMaker training instance type and cost. When a new data window arrives, the team creates version N+1, evaluates it in staging for one week against live shadow traffic, and promotes it to production only after the precision-at-fixed-recall meets the SLA threshold of 85%.

Chapter 2: Batch versus Real-Time Serving Patterns

7.6 The Two Serving Paradigms

Once a model is trained and registered, it must be served — that is, made available to generate predictions for consumers. There are two fundamentally different serving patterns, and the choice between them is driven by business requirements, latency constraints, and operational cost considerations.

7.6.1 Batch Prediction (Offline Inference)

In batch prediction (also called offline prediction or asynchronous inference), data accumulates over a period of time — typically a day, a week, or a financial quarter — in a data store (database, data warehouse, S3 bucket, or data lake). At a scheduled time, a job is triggered that:

  1. Loads the accumulated data from the data store
  2. Loads the trained model into memory (the model is not kept resident in memory around the clock)
  3. Processes the entire batch through the model, generating predictions for all records
  4. Writes the predictions back to a data store (potentially a different one from the source)
  5. Unloads the model from memory to free resources

The predictions are then consumed by downstream applications — dashboards, recommendation engines that send daily emails, or nightly ETL workflows that enrich data warehouses with scored features.

Canonical Examples:
  • Customer Segmentation: A telecom provider accumulates new subscriber data throughout the day. At midnight, a batch job clusters all subscribers into prepaid/postpaid segments and purchasing behavior cohorts. The results feed into the next day's marketing campaign.
  • Product Recommendations: An e-commerce platform collects user browsing and purchase activity. A nightly batch job generates personalized product recommendations, which are cached and served the following day.
  • Credit Risk Scoring: A bank processes loan applications in batch at the end of each business day. The credit risk model scores all applicants, and results are reviewed by underwriters the next morning.
  • ETL (Extract, Transform, Load): This is the classic batch processing paradigm. Data is extracted from source systems, transformed through a series of computations (including ML model inference as one step), and loaded into a target data warehouse. The entire pipeline runs on a scheduler.
Key Characteristics of Batch Serving:
  • Model is loaded into memory only during the scheduled prediction window — not continuously resident
  • High throughput: millions of predictions processed in a single run
  • Latency is not critical: predictions may take minutes to hours
  • Cost-efficient: compute resources are provisioned only for the batch window
  • Fault tolerance is higher: if predictions are incorrect, they can be reviewed and corrected before reaching end users
  • Fits naturally into ETL pipelines and data warehouse workflows
  • Data reconciliation (checking for stuck or failed jobs, verifying record counts) must be performed periodically

7.6.2 Real-Time Prediction (Online Inference)

In real-time prediction (also called online inference, on-demand inference, or synchronous serving), the model is persistently loaded in memory and exposes a prediction API (typically REST or GRPC). When a client application sends a request containing the input features, the model immediately processes it and returns the prediction as a response — typically within milliseconds to low hundreds of milliseconds.

Behind the scenes, the architecture involves an API gateway that receives client requests, a model service that hosts the trained model in memory, and often additional infrastructure for load balancing, auto-scaling, and monitoring. This is the pattern we see in nearly all consumer-facing GenAI applications today.

Canonical Examples:
  • Fraud Detection: When a credit card transaction is swiped, the transaction details are immediately sent to a fraud detection model. The model returns a fraud probability within milliseconds, and the transaction is either approved or blocked in real time.
  • Dynamic Pricing: Ride-hailing apps (Uber, Ola) continuously adjust prices based on real-time supply and demand signals, weather conditions, time of day, and traffic patterns. The pricing model must respond within milliseconds to each ride request.
  • Spam Filtering: Incoming emails are classified as spam or not-spam before reaching the user's inbox. The classification must happen synchronously with email delivery.
  • ChatGPT and Generative AI: Every prompt sent to a large language model is a real-time inference request — the model processes the token stream and streams the response back to the user.
Key Characteristics of Real-Time Serving:
  • Model is always loaded in memory — 24 hours a day, 7 days a week, 365 days a year
  • Low latency: predictions typically returned in single-digit to low hundreds of milliseconds
  • Unpredictable request patterns: the service may receive zero requests for hours, then a sudden burst of millions of requests per second
  • Auto-scaling is essential: infrastructure must dynamically scale up and down based on traffic
  • Higher operational cost: compute resources are continuously allocated (or at least warm standby)
  • Failure impact is immediate: if the model hallucinates or produces incorrect output, it reaches the end user directly with no buffer for human review
  • Architecture typically uses API Gateway + Model Service + Load Balancer + Monitoring stack

7.7 Architectural Implications

The architectural complexity diverges significantly between the two patterns. For batch serving, a simpler architecture suffices: a database or data lake as the data store, a scheduler (cron, Airflow, SageMaker Batch Transform, or a Jenkins job), and a compute environment that loads the model, runs inference, and writes results. There is no need for an API gateway, message queue, sophisticated auto-scaling, or continuous health monitoring.

For real-time serving, the architecture must include: an API Gateway for request routing and authentication, a Prediction Service (often a microservice) that hosts the model, message queues (Kafka, RabbitMQ, SQS) for decoupling components and buffering requests during traffic spikes, auto-scaling policies to handle variable load, logging and monitoring for observability, and circuit breakers or retry mechanisms for fault tolerance. Many of the patterns discussed earlier in the course — Pipe-and-Filter, CQRS, Microservices, and Event-Driven architectures — are implementations of real-time serving.

7.8 When to Use Which?

Decision Heuristic: Ask one question — "Does the consumer of this prediction need the answer right now to complete their workflow?" If yes, use real-time serving. If the prediction can be pre-computed and cached, or if the consumer is a batch analytics pipeline, use batch serving.

The same organization can use both patterns for different use cases. Consider Twitter: for hate speech and racial discrimination detection, tweets must be classified in real time — severe violations require immediate action (content removal, account suspension, or escalation to law enforcement). The model classifies the tweet on ingestion. For sentiment analysis of tweets about a brand or product, however, Twitter can run a nightly batch job that aggregates all tweets from the day, runs sentiment classification, and generates aggregate reports — there is no immediate business need for per-tweet sentiment in real time.

7.9 Deployment Architecture Trade-offs: Server-Side vs. Client-Side

Beyond the batch/real-time decision, a second architectural dimension determines where the model runs. The choice between server-side and client-side deployment carries profound implications for latency, privacy, offline capability, update frequency, and operating costs.

7.9.1 Server-Side Model Deployment

When model inference runs on servers controlled by the application provider — whether in-house data centers or cloud infrastructure — other components (including user-facing devices) make predictions through remote procedure calls. Server-side deployment makes it easy to provision dedicated resources (GPUs, high-memory instances) and scale independently through autoscaling. For large foundation models, server-side deployment is typically the only option; the model simply cannot fit on a user device.

However, server-side deployment demands a persistent network connection. If inputs are large (images, audio, video), network bandwidth and latency become concerns. The round-trip network time adds to inference latency and varies unpredictably based on connection quality. For latency-critical applications — such as obstacle avoidance in drones or augmented reality overlays on smart glasses — the network overhead may be prohibitive. Server-side deployment also concentrates operating costs on the provider's infrastructure rather than distributing computation to user devices.

7.9.2 Client-Side Model Deployment

Deploying models directly on user-facing devices (mobile phones, smart glasses, embedded systems, browsers) eliminates network dependency entirely. Inference works offline, network latency is zero, and user data never leaves the device — a strong privacy guarantee. Frameworks like TensorFlow Lite for mobile apps and TensorFlow.js for browsers make client-side embedding practical for smaller models.

The trade-offs are significant. User devices may lack sufficient computational resources (GPU, memory, battery) for large models, leading to slower inference and inconsistent user experiences across heterogeneous hardware. Embedded models increase application download size and storage requirements. If users have physical access to the device, sophisticated attackers can potentially extract the model, raising intellectual property and adversarial attack concerns — it is far easier to craft malicious inputs with direct access to model internals than by probing a server-side API.

7.9.3 Hybrid and Cached-Prediction Deployments

Many production systems use hybrid strategies. A small, fast model runs on the client for common cases; when confidence is low or the input is novel, the request is forwarded to a larger server-side model. Voice-activated speakers exemplify this: a tiny on-device model detects the activation phrase ("Siri," "Alexa"), and only audio following the phrase is sent to the cloud. This is the two-phase prediction (or cascade) pattern. Another hybrid approach is deploying a lookup table of precomputed predictions to the client — if the input is covered by the table, the result is immediate; otherwise, a server request is made. This protects model internals while preserving offline capability for common queries.

7.9.4 Implications for Updates and Experimentation

Server-side deployments make updates trivial: replace the model behind an API endpoint without touching the client application. This enables rapid experimentation — different model variants can be served to different user segments through A/B testing, and telemetry can be collected continuously to monitor model behavior in production. If a newly deployed model degrades, it can be rolled back instantly.

Client-side updates are harder. Models embedded in applications require full application updates, which users may resist or delay — Facebook, for instance, limited mobile app updates to once every two weeks despite updating server-side models much more frequently. Separate model update mechanisms (downloading new model files without reinstalling the app) can help, but introduce the risk of combining model and application versions that were never tested together. Version skew between feature-encoding code and model artifacts is a real failure mode. Experimentation on client devices is also constrained: deploying different model versions to different devices offers little flexibility for rapid rollback, and telemetry may be buffered, compressed, or lost if the device is offline.

Decision Framework: Choose server-side deployment when models are large, updates are frequent, experimentation velocity matters, and a network connection is guaranteed. Choose client-side deployment when offline operation and privacy are paramount, models are small enough to run on-device, and updates are infrequent. Choose hybrid when both sets of requirements are partially met.

7.10 Failure Modes and Recovery

A critical operational difference between the two patterns lies in how failures are handled. In batch inference, if the model produces incorrect predictions, there is a buffer: the predictions sit in a database or data warehouse where they can be reviewed, audited, and corrected before any downstream action is taken. Data reconciliation processes can detect anomalies and trigger re-runs. In real-time inference, incorrect predictions reach end users immediately. There is no staging ground — the model's output directly drives decisions (blocking a transaction, showing a price, delivering a chatbot response).

This is why major LLM providers exercise extreme caution before deploying models for real-time inference. Historical precedent includes instances where real-time chatbots were pulled from production for months after exhibiting hallucination or harmful behavior, then re-released only after extensive fine-tuning and safety testing.

Chapter 3: Fundamentals of Agentic AI

7.11 From Predictive to Generative to Agentic

The evolution of AI can be understood through three progressively more autonomous paradigms:

  • Predictive AI: Systems that make classifications or regression predictions based on input features. The system processes an input through a model and returns a prediction — a single-turn, request-response interaction. Examples: churn prediction, credit scoring, image classification. These systems are typically stateless: each request is treated independently with no memory of prior interactions.
  • Generative AI: Systems that generate content — text, images, code, audio — in response to prompts. These support multi-turn interactions: the user can follow up, refine, or redirect based on previous responses. The system maintains conversational context (in-context memory) within the session. Examples: ChatGPT, DALL-E, GitHub Copilot's code completion.
  • Agentic AI: Systems that autonomously pursue complex goals over extended periods with limited direct human supervision. They decompose tasks into sub-tasks, use tools (APIs, web search, code execution) to interact with the external world, maintain persistent memory across sessions, and make multi-step decisions through reasoning. An agentic system does not merely respond to prompts — it acts in the world to achieve objectives.
Formal Definition: Agentic AI refers to AI systems that can autonomously pursue goals, make decisions, use tools, and take multi-step actions in the real world without step-by-step human instructions. The highest level of autonomy — where a single high-level prompt triggers a fully autonomous chain of actions — is an aspiration, not yet fully realized in production systems. Current agentic systems exhibit autonomy within bounded scopes.

7.12 Chatbot versus Agent: A Comparative View

To make the distinction concrete, consider the prompt: "Plan my trip to Goa for March."

7.12.1 Chatbot Response (Generative AI)

A chatbot generates text describing Goa's best beaches (Baga, Anjuna, Calangute), suggests a two-day itinerary, and lists popular restaurants. It responds based on its training data. The user must then take separate actions: open a flight booking website, search for hotels, compare prices, and manually make reservations. Each subsequent step requires a new prompt from the user.

7.12.2 Agent Response (Agentic AI)

An agentic system, given the same prompt, would:

  1. Search flights: Query flight APIs for available options from the user's default location to Goa for March dates
  2. Check hotels: Search hotel booking platforms, filter by budget and rating preferences
  3. Compare prices: Aggregate flight and hotel costs, rank combinations by total price and convenience
  4. Book reservations: Execute the booking (with explicit user permissions for financial transactions)
  5. Add to calendar: Create calendar entries with flight times, hotel check-in, and suggested activities

The agent uses tools (flight search API, hotel booking API, calendar API) and multi-step reasoning to chain actions toward the goal. The user provides the high-level intent; the agent handles execution.

Caution — Financial Transactions: Any step involving money (booking, purchasing) requires extremely careful safeguards. Agents can "go overboard" if prompts are not precisely constrained. Best practices include: requiring explicit user confirmation before any financial transaction, setting spending limits, and restricting tool permissions to read-only by default with write operations requiring additional authorization.

7.13 The Five Core Components of an AI Agent

Every agentic AI system, regardless of implementation framework, is composed of five essential components that work together to enable autonomous goal-directed behavior.

7.13.1 LLM Core - The Reasoning Engine

At the heart of every AI agent is a Large Language Model (or Small Language Model for resource-constrained applications). The LLM serves as the reasoning engine — it processes inputs, generates plans, decomposes goals, and produces outputs. In a multi-agent setup, different agents can use different LLMs: one agent might use GPT-4 for complex reasoning while another uses GPT-4o-mini for lightweight classification tasks.

The LLM's reasoning capability comes from chain-of-thought (CoT) reasoning: the model breaks a problem into sequential, logically connected steps before arriving at a final answer. When asked "Give me Python code for binary search with reasoning," the model internally thinks: "We need a sorted array. If the array is not sorted, the first step is sorting. Then we divide into two halves with a mid-point..." This chain of reasoning mirrors how a human would approach the problem in an interview — first stating assumptions, then methodically building the solution.

Chain-of-thought is essential for agents because it produces explainable plans. The intermediate reasoning steps can be inspected, validated, and even used as the plan decomposition for tool orchestration.

7.13.2 Memory - Persistence Across Interactions

By default, all LLM systems are stateless: each request is independent, with no memory of prior interactions. Memory architectures add persistence across four dimensions, which are covered in detail in Chapter 4.

7.13.3 Action Loop - Observe, Think, Act, Reflect

The agent operates in a continuous action loop:

  1. Observe: Receive input — a user prompt, an API response, a tool output, or an event from another agent
  2. Think: Reason about the observation using the LLM core and chain-of-thought — "What do I know? What is the current state? What should I do next?"
  3. Act: Execute an action — generate a response, call a tool, invoke another agent, or update memory
  4. Reflect: Evaluate the outcome — was the action successful? Did it move closer to the goal? Should the plan be adjusted?

This loop continues until the goal is achieved or a termination condition is met (timeout, maximum steps, explicit user halt). The loop is the engine of agent autonomy — it allows the agent to recover from errors, try alternative approaches, and adapt to new information without human intervention.

7.13.4 Tools - The Interface to the External World

An LLM's knowledge is bounded by its training data cutoff. To interact with the current, dynamic world, agents need tools — external functions or APIs that the agent can invoke. Common tools include:

  • Web Search: Retrieve current information, verify facts, or find sources. This is how modern LLMs answer questions about recent events — they were not trained on yesterday's news, but they can search for it.
  • Code Execution / Code Interpreter: Run Python (or other language) code in a sandboxed environment. Essential for data analysis, mathematical computation, or generating and testing code.
  • API Calls: Invoke external services — weather APIs, database queries, prediction services, CRM systems. The agent calls another microservice's API and incorporates the response.
  • File Operations: Read, write, and search files. Used by coding agents (Claude Code, Cursor) to navigate repositories and apply edits.
  • Image Generation / Shell Commands: Depending on the agent's purpose, additional tools provide specialized capabilities.
JSON as the Universal Tool Protocol: Most tool interactions use JSON as the data interchange format. The LLM generates a JSON object specifying the tool to invoke and its parameters. The agent runtime executes the tool call and returns the result as JSON. JSON has become the de facto standard because it is language-agnostic, human-readable, natively supported by all major cloud providers and LLM APIs, and trivially serializable for logging and debugging.

7.13.5 Planning - Task Decomposition

Planning is the agent's ability to decompose a high-level goal into a sequence of sub-tasks. It is the "divide and conquer" strategy applied by the LLM reasoning core. Given the goal "research the topic of agentic AI and produce a cited summary report," the planning component would decompose it into:

  1. Search the web for "agentic AI survey papers 2024-2026"
  2. Extract and rank the top 5 papers by relevance and citation count
  3. Read and summarize each paper's key contributions
  4. Identify common themes and disagreements across the papers
  5. Draft a 1000-word cited summary with proper references
  6. Validate citations against the original sources

Each sub-task becomes an action in the agent's loop. In a multi-agent system, different sub-tasks may be assigned to different specialized agents — a research agent searches, a summarization agent writes, and a validation agent checks references.

7.14 Agentic AI Applications in Production Today

While fully autonomous agents remain aspirational, bounded-scope agentic systems are already deployed in production:

  • Code Development Agents (Claude Code, GitHub Copilot, Cursor): Given a repository, these agents can write code, run tests, observe failures, iterate on fixes, and open pull requests. Behind the scenes, they orchestrate multiple sub-agents — a "developer agent" writes code, a "tester agent" generates and runs tests, and a "reviewer agent" validates the results.
  • Email Management Agents: Read inbox continuously, draft replies, flag urgent messages, and unsubscribe from junk. Most implementations stop short of fully autonomous replies — they draft responses and wait for human approval before sending.
  • Online Store Management: Monitor inventory, adjust pricing dynamically, respond to customer inquiries, and manage order fulfillment workflows.
  • Research Paper Analysis: Given a paper as input, agents validate claims, proofread, compare with related literature, assess strengths and weaknesses, and suggest improvements.

7.15 Multi-Agent Communication and the Need for Patterns

When multiple agents collaborate on a complex task, they must communicate — passing intermediate results, coordinating actions, handling failures, and maintaining shared state. This is where architectural patterns originally developed for distributed software systems become directly applicable to agentic AI workflows.

Two patterns are particularly promising: the Saga Pattern (for managing distributed transactions with rollback semantics across agents) and the Blackboard Pattern (for enabling agents to collaboratively build a solution on a shared knowledge repository). Both are covered in subsequent chapters.

7.16 Model Composition Patterns

Beyond agent orchestration, production ML systems routinely compose multiple models to solve problems that no single model can handle alone. Three well-established composition patterns encode reusable design knowledge.

7.16.1 Ensembles and Metamodels

Ensembles train multiple independent models for the same task. For a given input, all models produce predictions in parallel, and their results are aggregated — typically by averaging, majority vote, or taking the most conservative answer. Random forests are the classic example: hundreds of decision trees vote on the final classification. In our augmented-reality translation scenario, text recognized by multiple OCR models could be merged to reduce noise.

Metamodels (or model stacking) go one step further: instead of a hand-written aggregation rule, a separate ML model learns how to weight and combine the predictions of base models. A metamodel could learn which OCR model to trust under different lighting conditions or for different languages, producing more reliable composite predictions.

7.16.2 Sequential Decomposition

When a problem is too complex for a single model, it can be decomposed into a pipeline where each model contributes a different aspect. The translation scenario embodies this: rather than training an "image-to-translated-text" model, we decompose into OCR → Translation. Each sub-problem is more tractable, can be trained independently, and can be improved or replaced without retraining the entire pipeline. Large language model workflows follow the same principle — first extract relevant quotes from a document, then generate an answer based on those quotes, then refine. Domain knowledge about how to solve the problem guides the decomposition, and non-ML business logic (hand-written rules, database lookups) can be interleaved between model steps.

7.16.3 Cascade / Two-Phase Prediction

In the cascade pattern, multiple models are trained for the same problem, but inference proceeds sequentially rather than in parallel (as in ensembles). A small, fast model makes the first prediction; only if its confidence is low or a specific condition is met does a larger, more expensive model run. Voice-activated speakers exemplify this: a tiny on-device model continuously listens for the activation phrase; only audio segments after the phrase are forwarded to cloud-based speech recognition models. The cascade reduces inference costs — most predictions are served by the cheap model, and the expensive model is invoked only for challenging edge cases. This pattern is a natural fit for hybrid client-server deployments.

Mapping to Agentic Systems: These model composition patterns directly inform multi-agent architecture. Ensembles map to having multiple specialized agents vote on a decision. Sequential decomposition is the foundation of agent task decomposition — one agent researches, another summarizes, a third validates. Cascades map to agent routing: a lightweight classifier agent triages requests and forwards complex cases to more capable (and expensive) agents.

Chapter 4: Memory Architecture in Agentic Systems

7.17 Why Memory Matters

Stateless systems treat every request as independent — the same prompt yields the same response regardless of history. But effective agents must remember: the context of the current conversation, past interactions with a specific user, domain-specific knowledge, and the intermediate results of tool calls. Memory is what transforms a stateless LLM into a stateful agent.

7.18 The Four Types of Memory

7.18.1 In-Context / Working Memory

Scope: The current conversation or session
Persistence: Temporary — exists only within the active chat or workflow window
Purpose: Maintains the thread of conversation so the agent can refer to what was just discussed without the user repeating themselves

When a user uploads a PDF and says "summarize this," and then follows up with "make it shorter" or "reduce to 100 words," the agent must remember what "it" refers to. This is in-context memory — the conversation history is passed as context with each subsequent prompt. In-context memory is limited by the LLM's context window (e.g., 128K tokens for GPT-4o). When the context window is exceeded, older messages are truncated or summarized.

Analogy: In-context memory is like human working memory during a conversation — you remember what was said five minutes ago and can refer back to it, but once the conversation ends and you move to a different topic, those details fade. It is not a permanent record.

7.18.2 Semantic Knowledge Base

Scope: Global — shared across all users and all sessions
Persistence: Static or slowly changing — updated periodically through curation
Purpose: Provides domain-specific knowledge that the base LLM may not have been trained on

A semantic knowledge base is a curated, authoritative corpus of domain knowledge — medical textbooks, legal statutes, company policy documents, or product manuals. When a user asks a domain-specific question, the agent retrieves relevant passages from the knowledge base and uses them to ground its response (Retrieval-Augmented Generation, or RAG).

A common implementation is a fine-tuned model: take a base LLM (e.g., GPT-4) and fine-tune it on a domain-specific dataset (e.g., medical Q&A pairs). The resulting model has internalized the knowledge base and can answer domain questions without external retrieval. However, fine-tuning is expensive and static — updating the knowledge requires retraining. Vector-database-backed RAG is more common for dynamic knowledge.

Characteristics: Global (same answer for all users asking the same question), externally curated (human experts validate the knowledge), relatively static (updated on a quarterly or monthly cycle), and not personalized to individual users.

7.18.3 External / Episodic Memory

Scope: Per-user — personalized to each individual user's history
Persistence: Dynamic — updated continuously with each interaction
Purpose: Enables personalized, context-aware responses based on the user's identity and past interactions

Episodic memory is what makes a customer support chatbot say: "Based on your order #4521 from last Tuesday, I can see the shipping status is..." The agent retrieves this specific user's interaction history from a persistent store (typically a vector database) and uses it to personalize the response.

The distinction from the semantic knowledge base is critical: the knowledge base answers "What is the return policy?" (same for everyone), while episodic memory answers "What is the status of my return?" (unique to the user).

Implementation: A banking chatbot receives a customer ID with each request. It queries the vector database for this customer's recent transactions, previous support queries, and account history. The retrieved context is injected into the LLM prompt alongside the current question, enabling a personalized response. The vector database is updated after each interaction, making the memory dynamic and ever-growing.

7.18.4 Procedural Memory / Skills

Scope: Temporary — exists only for the duration of a tool call or a step in the agent workflow
Persistence: Ephemeral — may be passed to the next agent as a message, but not permanently stored
Purpose: Holds the intermediate results of tool invocations that need to be passed between agents or workflow steps

When an agent calls a weather API, the response (e.g., {"temperature": 32, "condition": "sunny"}) is stored temporarily in procedural memory. The next agent in the workflow — say, a trip-planner agent that needs weather information — reads this result from procedural memory. Procedural memory is essentially the state carried along the agent workflow pipeline.

Some frameworks classify procedural memory as a subset of in-context memory, since both are temporary. The distinction is that procedural memory specifically refers to tool-generated data that the agent would not have been able to produce from its training alone — it represents the agent's interaction with the external world.

7.19 Storage Strategies and Architectural Considerations

While there is no rigid prescription for how each memory type must be stored, practical considerations drive architectural choices:

  • Semantic knowledge base: Can be stored in a relational database or document store since it changes infrequently. No caching layer is typically needed — reads are infrequent (per-session, not per-request).
  • Episodic memory: Benefits from a vector database (Pinecone, ChromaDB, Weaviate, pgvector) because retrieval is semantic (find similar past interactions) and the store is write-heavy (every user interaction adds data). A caching layer may be necessary to handle high-frequency reads for active users.
  • In-context memory: Managed entirely within the LLM's context window. No external storage is required, though some systems persist conversation logs to a database for auditability.
  • Procedural memory: Typically handled in-memory within the agent runtime or passed via message queues between agents.
Archival Policies: The question of how long to retain episodic memory is organization-specific. Cloud providers offer effectively infinite storage (pay-as-you-go), so the constraint is not technical but policy-driven. Organizations must decide: how many months of user interaction history do we retain? When do we archive or delete? Regulations like GDPR also impose data retention and deletion requirements that must be encoded into the memory architecture.

7.20 Prompt Engineering as a Control Mechanism

A recurring concern with agentic systems is the runaway agent — an agent that enters an unbounded loop, makes excessive tool calls, or consumes tokens without converging to a solution. Proper prompt engineering is the primary mitigation:

  1. Identity Priming: Begin the prompt by telling the agent who it is — "You are a biomedical researcher with 20 years of experience." This constrains the agent's domain of operation and blocks out irrelevant actions.
  2. Response Limitations: Specify bounds — "Search flights and return only the two cheapest options." Without this, the agent might return 20-30 results, consuming unnecessary tokens.
  3. Output Specification: Define exactly what the output should be — "Return a 500-word cited summary report in JSON format." Ambiguous output expectations lead to verbose, unstructured responses.
  4. Token Budget Awareness: Start with small requests to gauge token consumption before scaling to larger tasks. If 100 results consume 1K tokens, 1 million results will consume roughly 10M tokens — a linear extrapolation that informs cost planning.

Chapter 5: The Saga Pattern

7.21 Architectural Thinking: Why Patterns Matter

Before diving into the Saga pattern itself, it is worth understanding why we study patterns at all. Software architecture is the part of the design process that focuses on early decisions that are most important for achieving a system's quality requirements — scalability, flexibility, reliability, security. These decisions are fundamental and hard to change later without a full redesign. Architectural patterns (like Saga) codify design knowledge: they name a common solution to a known problem, describe the trade-offs, and establish a shared vocabulary. When two engineers discuss "choreography-based Saga," they instantly understand the decentralized, event-driven structure and its implications without needing to describe every detail from scratch.

Quality requirements drive architecture. For Saga, the driving quality is data consistency in a distributed system. The trade-off is increased complexity and potential performance overhead in exchange for maintaining correctness across independent services. The same architectural thinking applies to ML-enabled systems: the choice between batch and real-time serving, server-side and client-side deployment, or orchestration and choreography is always driven by which qualities matter most for the specific system. There is no universal best architecture — only architectures that best serve a system's particular quality goals.

7.22 The Problem: Distributed Transactions

Consider ordering food through a delivery application. From the user's perspective, "ordering food" is a single action. But behind the scenes, it is a distributed transaction spanning multiple independent services, each with its own local database:

Step Transaction Microservice Compensating Transaction
T1 Create Order Order Service Cancel Order
T2 Process Payment Payment Service Refund Payment
T3 Update Inventory Inventory Service Restore Inventory
T4 Deliver Order Delivery Service Cancel Delivery

This is a distributed transaction because:

  • It spans multiple independent services, each with its own local database (relational, NoSQL, or any data store)
  • It is not a unitary transaction — it does not depend on a single flow or a single database
  • It has all-or-nothing semantics: if any step fails, the entire order is considered failed
  • The transaction may take hours, days, or even weeks to complete (e.g., physical shipping)
  • Any step can fail at any time, for any reason — payment gateway timeout, inventory stock-out, delivery unavailability
The Core Challenge: Each microservice commits its changes to its own local database. There is no global transaction coordinator that can issue a distributed COMMIT or ROLLBACK. If T4 (Deliver Order) fails, T1, T2, and T3 have already committed to their respective databases. How do we undo those committed changes?

7.23 The Saga Solution: Compensating Transactions

The Saga pattern solves this problem through compensating transactions — for every forward transaction \(T_n\), there exists a corresponding compensating transaction \(C_n\) that semantically undoes the effects of \(T_n\).

The rollback rule is strict: compensating transactions must execute in reverse order. If \(T_4\) fails, the compensation sequence is \(C_3 \rightarrow C_2 \rightarrow C_1\), where \(C_i\) compensates for \(T_i\).

Why reverse order? Because of causal dependencies: \(T_2\) (Process Payment) cannot be meaningfully rolled back until \(T_3\) (Update Inventory) has been undone — the payment was made to reserve inventory, so the inventory must be released before the payment is refunded. Reversing in any other order would create data inconsistencies.

Walkthrough — Failed Delivery:
  1. T1 (Create Order): COMMIT — order #4521 created in Order DB
  2. T2 (Process Payment): COMMIT — ₹250 debited in Payment DB
  3. T3 (Update Inventory): COMMIT — dosa count decremented in Inventory DB
  4. T4 (Deliver Order): FAILS — no delivery partner available
  5. C3 (Restore Inventory): Increment dosa count back in Inventory DB
  6. C2 (Refund Payment): Credit ₹250 back in Payment DB
  7. C1 (Cancel Order): Mark order #4521 as CANCELLED in Order DB

After compensation, all four databases are consistent — it is as if the order was never placed.

Why Not Automatic Database Rollback? In traditional monolithic applications with a single relational database, a transaction can be rolled back by the database engine. But in a microservices architecture, each service has its own database, and there is no distributed transaction coordinator (like a two-phase commit manager) that spans them. Each service independently commits to its local store. The only way to undo a committed local change is to execute business logic — a compensating transaction — that reverses the semantic effect.

7.24 Saga Participants and Communication

Each microservice in the chain is called a saga participant. Participants communicate through one of two mechanisms:

  • Synchronous communication: Direct API calls — REST over HTTP or GRPC. The caller waits for the callee's response before proceeding.
  • Asynchronous communication: Events published to a message broker (Kafka, RabbitMQ, Amazon SQS/SNS). The publisher emits an event and continues; the subscriber(s) consume the event and act on it.

The communication mechanism is the foundation for the two implementation modes of the Saga pattern: orchestration and choreography.

7.25 Orchestration-Based Saga

In orchestration, a centralized component called the orchestrator (or controller) manages the entire saga flow. The orchestrator:

  1. Receives the client request (e.g., "Place order #4521 for masala dosa")
  2. Knows the exact sequence of saga participants: T1 → T2 → T3 → T4
  3. Calls each participant in sequence, waiting for the response before calling the next
  4. If any participant returns failure, initiates compensation by calling compensating transactions in reverse order
  5. Informs the client of the final outcome (success or failure with details)

The orchestrator can communicate with participants using either synchronous calls (REST, GRPC) or asynchronous messaging — the pattern does not mandate a specific mechanism. The orchestrator is the sole entity that knows the entire workflow; individual participants only know their own step.

Analogy — Orchestra Conductor: The term "orchestrator" comes from orchestral music. In a symphony, the conductor stands at the center with a baton, directing each section (violins, cellos, brass, percussion) exactly when to play. Each musician knows their part, but only the conductor knows the full score — who plays when, at what tempo, and how sections transition. Similarly, the saga orchestrator knows the full transaction sequence and directs each service when to act.

7.26 Choreography-Based Saga

In choreography, there is no central coordinator. Each saga participant operates independently, communicating only through a shared message broker (event bus). The flow works as follows:

  1. Service A (Order Service) receives the client request, performs T1 (Create Order), commits to its local database, and publishes an "Order Created" event to the message broker
  2. Service B (Payment Service) subscribes to "Order Created" events. Upon receiving the event, it performs T2 (Process Payment), commits to its local database, and publishes a "Payment Processed" event
  3. Service C (Inventory Service) subscribes to "Payment Processed" events, performs T3, and publishes an "Inventory Updated" event
  4. Service D (Delivery Service) subscribes to "Inventory Updated" events and performs T4

Compensating transactions work the same way through events:

  1. If Service C fails, it publishes an "Inventory Update Failed" event
  2. Service B subscribes to this failure event and executes its compensating transaction (Refund Payment), publishing "Payment Refunded"
  3. Service A subscribes to "Payment Refunded" and executes Cancel Order
Key Distinction: In choreography, no participant knows about others. Service A does not know that Service B exists — it only knows that when it finishes creating an order, it publishes an event. What happens next is not its concern. This is the Event-Driven Architecture pattern in action: publish-subscribe with a message broker as the communication backbone.

7.27 Orchestration versus Choreography: Trade-offs

Dimension Orchestration Choreography
Control Centralized — orchestrator has full visibility Decentralized — no single point of control
Communication Flexible — synchronous (REST/GRPC) or asynchronous Mandatory — event-driven via message broker
Coupling Tighter — orchestrator knows all participants Looser — services only know about events, not each other
Debugging Easier — workflow is explicitly defined in one place Harder — workflow emerges from event chains; tracing requires distributed tracing tools
Scalability Orchestrator can become a bottleneck Highly scalable — services are independently deployable
Cost at Scale Tens of milliseconds per step — negligible for most workloads Event broker adds slight latency but enables massive parallelism
Modern Reality — Scale Has Outpaced the Concern: A common objection to the Saga pattern is that rollback through compensating transactions is slow. In practice, with modern cloud infrastructure, each saga step completes in milliseconds to low seconds. Even at massive scale (e.g., New Year's Eve on Swiggy/Zomato), cloud auto-scaling across multiple regions handles the load. The computational "waste" of rollback is negligible compared to the business value of maintaining data consistency. User experience failures are real — if a user has two bad experiences, they may switch to a competitor — but these are rare events in well-architected systems.

7.28 The Saga Pattern in Agentic AI Workflows

The Saga pattern, originally designed for microservices in e-commerce and banking, is now being adapted for multi-agent AI workflows. The mapping is natural:

  • Each AI agent becomes a saga participant — an independent service with its own LLM, its own memory (local state), and a specific sub-task
  • Agents communicate via messages or events — passing intermediate results, tool outputs, or failure notifications
  • If one agent fails (e.g., a web search returns no results, or a code execution times out), the workflow must compensate — the previous agent must adjust its output or try an alternative path

This is the frontier where traditional software engineering patterns meet the agentic AI paradigm. The principles are the same: decompose complex work into manageable units, define clear communication protocols, and handle failures gracefully with well-defined rollback semantics.

Looking Ahead: The Saga pattern and the Blackboard pattern will be explored in detail with code examples in subsequent sessions. These patterns form the foundation for building production-grade multi-agent systems where agents collaborate to solve problems that no single agent could handle alone.

7.29 Key Terminology Summary

  • Saga: A sequence of local transactions where each transaction updates data within a single service. No global transaction coordinator exists.
  • Saga Participant: A microservice that executes one transaction in the saga sequence.
  • Distributed Transaction: A transaction spanning multiple independent services, each with its own database. Has all-or-nothing semantics.
  • Compensating Transaction ($C_n$): A transaction that semantically undoes the effects of forward transaction $T_n$. Always named with verbs indicating reversal: cancel, refund, restore, delete.
  • Orchestrator: The centralized controller in orchestration-based saga that knows the full sequence and directs each participant.
  • Message Broker: The communication backbone in choreography-based saga (Kafka, RabbitMQ, SQS) through which services publish and subscribe to events.
