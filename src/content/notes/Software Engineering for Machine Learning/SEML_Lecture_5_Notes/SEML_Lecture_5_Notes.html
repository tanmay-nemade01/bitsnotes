Published: June 2, 2026
Level: postgraduate
Audience: Postgraduate students implementing pipe-and-filter, CQRS, RAG, and deployment patterns in ML system design.

Lecture Summary

Session 5 surveys reusable architectural patterns for ML systems, built from components (processing units) and connectors (communication channels). Real deployments typically combine multiple patterns.

Pipe-and-filter decomposes processing into sequential independent filters connected by pipes — familiar from Unix commands chained with |. Data flows from source through filters to sink, making it ideal for ETL, feature extraction, and batch scoring where each stage has a single responsibility.

CQRS (Command Query Responsibility Segregation) separates write-side operations (ingest, label, train, update indexes) from read-side operations (low-latency inference, dashboards). This split allows different storage and scaling strategies and introduces the strong vs eventual consistency trade-off. In ML, CQRS often maps to offline training writes versus online prediction reads.

RAG (Retrieval Augmented Generation) augments LLMs with external knowledge. The write pipeline ingests documents, chunks and embeds them, and stores vectors. The read pipeline retrieves relevant chunks at query time and conditions generation on them — reducing hallucination on domain-specific questions. LangChain is mentioned as a framework for orchestrating RAG chains.

The session concludes with monolith versus microservices: monoliths are simpler to debug but create scaling bottlenecks, while microservices enable independent deployment of components (e.g., separate reranker and generator services) but add operational complexity. Students should be able to sketch RAG flows, justify filter boundaries, and explain why separating commands and queries improves scalability.

Key Learning Objectives

  • Describe architectural patterns using components and connectors in ML contexts.
  • Apply pipe-and-filter to data ingestion, feature engineering, and batch inference pipelines.
  • Explain CQRS, consistency trade-offs, and mapping to ML training vs serving paths.
  • Design RAG write and read pipelines with embeddings, retrieval, and LLM generation.
  • Compare monolith and microservices deployments for ML systems and combine patterns appropriately.

Architectural Patterns — Introduction

What is an Architectural Pattern?

An architectural pattern is a general, reusable solution to a commonly occurring problem in software architecture within a given context. It is not a finished design; rather, it is a template describing how to organize components and connectors to solve a class of problems.

Software architects and designers have developed architectural patterns based on decades of experience and best practices. These patterns can be reused across multiple scenarios whenever a particular problem is encountered.

Components and Connectors

Every architectural pattern can be described in terms of two fundamental elements:

  • Components — The processing units that contain the business logic, computations, or transformations.
  • Connectors — The mechanisms that link components together, enabling data transfer and communication between them.
Key Insight

Real-world applications are almost always a combination of multiple architectural patterns. For instance, a microservices-based ML system may internally use pipe-and-filter for its data pipeline and CQRS for separating training from inference.

Quality Requirements Drive Architecture

The fundamental insight of software architecture is to seriously consider a system's quality requirements early and design the system to support those qualities. Once fundamental decisions are locked into the implementation, they are difficult to change. Architecture is the binding element that guides implementation to meet the system's quality requirements. In ML systems, common additional qualities of concern beyond traditional ones (scalability, security, modifiability) include accuracy, training and inference costs, reproducibility, fairness, and explainability.

The primary objective of architectural design is to make important decisions that support the key quality goals. For example, if availability is important, developers should consider redundancy and mechanisms to detect and resolve outages early. If getting to market quickly is more critical, intentionally relying on basic infrastructure may be worth the technical debt it accrues.

Architecture vs. Agility

There is a well-documented tension between architecture and agility. Planning and architecture help avoid costly mistakes, but too much architecture may slow down a project investing in qualities not relevant until the project is truly successful. Experienced architects navigate this space by focusing on key qualities early while preserving flexibility for later change — a skill equally or even more important when introducing ML components with many additional design decisions.

Pipe and Filter Pattern

Overview and History

The Pipe and Filter pattern is one of the oldest and most widely used architectural patterns, dating back to the 1970s. The entire Unix/Linux operating system is largely built on this pattern — commands like grep, ls, awk are chained together using the pipe (|) operator.

Pipe and Filter Pattern

A pattern in which a processing task is decomposed into a sequence of independent processing steps (filters) connected by channels (pipes). Data flows from a source, through one or more filters, and finally reaches a sink.

Architecture Diagram

Data Source → Filter 1 → Filter 2 → … → Filter n → Data Sink

Figure 1: Generic Pipe and Filter Architecture

Key Terminology

ElementDescription
Filter (Component)A self-contained processing unit that reads input, performs a transformation or computation, and produces output. Each filter should ideally be independent and reusable.
Pipe (Connector)A channel that transports data from the output of one filter to the input of the next. Traditionally, pipes perform no transformation — they only transfer data.
Data SourceThe origin of the data entering the pipeline (e.g., a CSV file, database, URL, camera feed).
Data SinkThe destination where the final processed output is delivered (e.g., display, file, cloud storage, dashboard).

Table 1: Pipe and Filter — Key Elements

Properties and Characteristics

  1. Modularity — Each filter is a self-contained module. Filters can be added, removed, or rearranged without affecting other filters.
  2. Reusability — A well-designed filter (e.g., a data-cleaning function) can be reused across multiple pipelines and data sets.
  3. Flexibility — The pipe (communication mechanism) can be changed independently. For example, switching from in-memory variable passing to REST APIs or message queues.
  4. Sequential by default — Traditionally, data flows sequentially from one filter to the next.
  5. Optional steps — Certain filters in the pipeline can be made optional (e.g., a scaling step may be skipped if the data set is small).

Non-ML Example: Image Processing Pipeline

Input Image → Pre-processing (Resize, Noise Reduction) → Feature Extraction (Edges, Shapes) → Apply Filter (Blur, Grayscale) → Output Image

Figure 2: Image Processing Pipeline as Pipe and Filter

In this example:

  • Filter 1 (Pre-processing): Resize, colour correction, noise reduction.
  • Filter 2 (Feature Extraction): Edge detection, shape identification.
  • Filter 3 (Apply Filter): Blur, grayscale, sharpen.
  • Sub-steps within a filter (e.g., resize and noise reduction) can either be within the same filter or separate filters — the pattern does not restrict this.

ML Example: Diabetes Prediction Pipeline

URL (CSV) → Input Filter (Load DF) → Cleaning Filter (Median Imputation) → Scaling Filter (Std. Scaler) [Optional] → Training Filter (LogReg) → Output (Accuracy, Report)

Figure 3: ML Pipeline (Pima Indian Diabetes Data Set) as Pipe and Filter

Pipeline Step-by-Step

  1. Data Source: Pima Indian Diabetes data set fetched from a URL.
  2. Input Filter: Load data into a Pandas DataFrame.
  3. Cleaning Filter: Handle missing values using median imputation.
  4. Scaling Filter (Optional): Apply StandardScaler for feature normalization.
  5. Training Filter: Split data (train/test), train a Logistic Regression model.
  6. Output (Data Sink): Display accuracy score and classification report.
Listing 1: Conceptual Python code for Pipe and Filter ML Pipeline 
# Each filter is a Python function (component)
# Variables between them act as pipes (connectors)

raw_data = input_filter(dataset_url)     # Pipe: raw_data
clean_data = cleaning_filter(raw_data)   # Pipe: clean_data
scaled_data = scaling_filter(clean_data) # Pipe: scaled_data
model, preds = training_filter(scaled_data) # Pipe: model, preds
output_filter(model, preds)              # Final output

Parallelism in Pipe and Filter

Although the pattern is sequential by default, modern implementations support parallelism in two ways:

(a) Replicas: A single filter can have N instances running in parallel (horizontal scaling). For example, 4 instances of a data-cleaning filter processing different partitions simultaneously.

(b) Fan-out: The output of one filter can be sent to multiple downstream filters (one-to-N mapping), similar to Unix's tee command.

Intelligent Pipes (Modern Extension)

In the traditional pattern, pipes perform no transformation. However, modern "intelligent pipes" (e.g., Apache Kafka, message queues) can perform lightweight transformations, routing, or filtering during data transfer. For most ML systems, the traditional definition suffices.

Pipeline Antipatterns

When pipelines are poorly engineered, they exhibit characteristic antipatterns that hinder automation and evolution:

  • Big-Ass Script Architecture — A single monolithic script containing all pipeline logic, with no modular decomposition. Hard to test, debug, and reuse.
  • Pipeline Jungles — A tangled web of scripts with unclear dependencies, where nobody remembers which scripts need to be run in what order.
  • Dead Experimental Code Paths — Abandoned experimental code left in the pipeline, making it unclear which code is active and which is obsolete.
  • Undeclared Consumers — Data dependencies between pipeline stages that are not explicitly documented or tracked, causing silent breakages when upstream changes.

Remedy: Modularize each pipeline stage with clear interfaces (inputs and outputs). This enables different data scientists to work on different stages independently, facilitates testing, and allows workflow orchestration tools to schedule and monitor each stage.

CQRS — Command Query Responsibility Segregation

Origin and Definition

The CQRS pattern has its roots in Bertrand Meyer's Command Query Separation (CQS) principle, introduced in the Eiffel programming language. The term CQRS was coined by Greg Young and has been a dominant pattern in modern application architecture for the past 15+ years.

CQRS Principle

Every method should either be a command that performs an action (changes state) or a query that returns data to the caller — but never both.

Commands vs. Queries

Command (Write)Query (Read)
PurposeChanges the state of a resourceRetrieves data without modification
HTTP VerbsPOST, PUT, DELETEGET
CRUD MappingCreate, Update, DeleteRead
FrequencyLess frequent (~25% of operations)Very frequent (~75% of operations)
OptimizationWrite-optimized storesRead-optimized stores, caches, CDNs

Table 3: Command vs. Query Comparison

Why Separate Commands and Queries?

Command Side (Write Operations): POST, PUT, DELETE, Train, Deploy, Ingest ↔ Query Side (Read Operations): GET, Predict, Monitor, Analyze (via Segregation from Shared Storage)

Figure 4: CQRS — Separation of Command and Query Responsibilities

  1. Performance: Read operations vastly outnumber writes (70–75% reads in most applications). Separating them allows independent optimization — e.g., caching and CDNs for reads.
  2. Scalability: Read and write paths can be scaled independently. Reads can use horizontal scaling with replicas; writes may use vertical scaling for strong consistency.
  3. Team Independence: Different teams can work on the command side (training, data ingestion) and query side (inference, monitoring) independently.
  4. Data Store Optimization: Write-optimized stores (relational DBs, write-ahead logs) vs. read-optimized stores (caches, materialized views, CDNs).

Real-World Examples

CQRS in Everyday Applications
  • Instagram: A user posts a reel (Command: POST). Millions of users scroll and view reels (Query: GET). The write path updates the database; the read path serves from distributed caches/CDNs.
  • Netflix: Content creators upload movies (Command). Viewers stream from the nearest CDN (Query). The origin server holds the master copy.
  • E-commerce (Swiggy/Zomato): Restaurant menus are updated infrequently (Command), but customers browse menus constantly (Query).
  • YouTube: Creators upload/edit/delete videos (Command). Viewers watch billions of videos daily (Query) served from globally distributed CDNs.

Strong Consistency vs. Eventual Consistency

CQRS is deeply connected to the consistency model of the underlying system.

Strong ConsistencyEventual Consistency
DefinitionAfter a write, all subsequent reads immediately reflect the updated dataAfter a write, different readers may temporarily see stale data, but eventually all will converge
LatencyHigher (must synchronize all replicas)Lower (reads can be served from any replica)
ScalingTypically vertical scalingTypically horizontal scaling
Use CaseBanking, financial transactionsSocial media, streaming platforms
Example"I transfer Rs. 100 — recipient sees it immediately""I post on Facebook — some friends see 100 likes, others see 98 temporarily"

Banking Domain Exception

Even within banking, eventual consistency exists in limited forms:

  • UPI Lite: Payments can be made offline; settlement occurs when back online.
  • Credit card networks: Visa/MasterCard may approve transactions within predefined limits when the issuer bank is unreachable, settling later.

However, core banking transactions use strong consistency by default.

CQRS in ML Systems

In machine learning systems, CQRS manifests as the separation between the development/training phase (command) and the inference/serving phase (query).

Command Side (Write): Data Ingestion → Data Processing → Feature Engineering → Model Training → Model Evaluation → Deployment → Model Registry, Feature Store

Query Side (Read): Prediction API, Metrics API, Analytics API, Dashboard, Model Monitoring ← Model Registry, Feature Store

ChatGPT and Eventual Consistency

When OpenAI releases a new model version (e.g., GPT-6.0), the model metadata is immediately updated in the central registry (Command). However, inference servers, edge regions, and CDNs across the world may take minutes to hours to synchronize (Eventual Consistency). Users near the origin may see the new model immediately, while others temporarily interact with the older version.

RAG — Retrieval Augmented Generation

What is RAG?

Retrieval Augmented Generation (RAG)

RAG is an architectural pattern for building AI-powered question-answering systems. It combines information retrieval from a private knowledge base with text generation from a Large Language Model (LLM) to produce accurate, context-grounded responses.

Why RAG Matters

Without RAG, an LLM answers only from its training data, which may be outdated or lack domain-specific knowledge. RAG augments the LLM's generation with retrieved context from your own documents, making responses:

  • Accurate — grounded in your actual data
  • Up-to-date — new documents can be added without retraining
  • Private — internal documents never leave your system
  • Traceable — responses include source references

RAG = Pipe and Filter + CQRS

RAG is a powerful illustration of how architectural patterns compose:

  • The ingestion pipeline (document → chunks → embeddings → vector DB) follows the Pipe and Filter pattern.
  • The query pipeline (user question → embedding → semantic search → LLM → answer) also follows Pipe and Filter.
  • The separation between the ingestion pipeline (Command/Write) and the query pipeline (Query/Read) follows CQRS.

RAG Architecture Diagram

Write Pipeline (Command): PDF / Docs → Extract Pages → Chunking (1000 chars, 200 overlap) → Embedding API → Vector Database

Read Pipeline (Query): User Question → Embedding API → Semantic Search → Context Retrieval → LLM (GPT, Gemini) → Generated Answer

Figure 6: Complete RAG Architecture showing Pipe-and-Filter + CQRS

Step-by-Step: Write Pipeline (Ingestion)

Step 1: Document Input — Accept input documents (PDF, Word, CSV, PPT, or any text).

Step 2: Page Extraction — Extract the text content from each page of the document.

Step 3: Chunking — Split the extracted text into fixed-size chunks.

  • Default chunk size: 1000 characters
  • Default overlap: 200 characters (ensures context continuity between chunks)
  • White spaces are removed during chunking
  • Multiple chunking strategies exist (character-based, sentence-based, semantic)

Step 4: Embedding — Convert each text chunk into a numerical vector (embedding) using an Embedding API.

  • Embedding APIs: OpenAI, Sentence Transformers, GloVe, FAISS, HuggingFace
  • Each chunk → one embedding vector

Step 5: Store in Vector Database — Store the chunk text, its embedding vector, and metadata (source file, page number, chunk ID) in a vector database.

  • Vector DBs: ChromaDB, Pinecone, FAISS, Weaviate, Milvus
  • ChromaDB uses SQLite internally for storage
What's Stored in the Vector Database?

Each record in the vector database contains:

  1. ID — Unique identifier for the chunk
  2. Document — The original text of the chunk
  3. Embedding — The numerical vector representation (e.g., [0.23, -0.14, 0.87, ...])
  4. Metadata — Source file name, page number, chunk position

Step-by-Step: Read Pipeline (Query)

Step 1: User Query — The user asks a question in natural language.

Step 2: Query Embedding — Convert the user's question into a vector using the same Embedding API used during ingestion.

Step 3: Semantic Search — Compare the query embedding against all stored embeddings in the vector database using similarity measures (cosine similarity, dot product).

Step 4: Context Retrieval — Retrieve the top-k most similar chunks (along with their original text and metadata).

Step 5: Prompt Construction — Construct a prompt containing:

  • The user's original question
  • The retrieved context chunks
  • Instructions to restrict the answer to the given context

Step 6: LLM Generation — Send the prompt to an LLM (GPT, Gemini, etc.), which generates a coherent, human-readable answer based only on the provided context.

Step 7: Answer with References — Return the generated answer along with source references (file name, page number) from the metadata.

RAG Restricts LLM to Context

In the prompt template, we explicitly instruct the LLM: "Answer only based on the context provided. Do not use your general knowledge." This ensures:

  • No hallucination from the LLM's training data
  • Responses are traceable to specific source documents
  • Ideal for enterprise/internal knowledge bases

Embeddings: Intuitive Explanation

What is an Embedding?

An embedding is a dense numerical vector that captures the semantic meaning of text. Texts with similar meanings have vectors that are close together in the vector space.

Intuitive Example of Embeddings

Consider these three sentences:

  1. "Virat Kohli scored a century against Australia."
  2. "The Indian batsman hit 100 runs in the match."
  3. "The stock market crashed by 500 points."

Sentences 1 and 2 are semantically similar — their embedding vectors will be close in vector space. Sentence 3 is unrelated — its vector will be far from the first two. This is how semantic search works: the user's question vector is compared with chunk vectors to find the most relevant chunks.

LangChain: The Pipe-and-Filter Framework for RAG

LangChain is a popular Python framework that implements the pipe-and-filter pattern for building RAG applications:

  • Lang = Language, Chain = Connecting components
  • Each step (chunking, embedding, retrieval, LLM call) is a filter
  • LangChain chains (connects) them so output of one is input to the next
  • Plug-and-play: Each component can be independently swapped
    • Change embedding model: OpenAI → HuggingFace
    • Change vector DB: ChromaDB → Pinecone
    • Change LLM: GPT-4 → Gemini
    • The pipeline structure remains the same; only the individual component changes

RAG Variants (Brief Overview)

Since its introduction (~2024), RAG has evolved into multiple variants:

  • Naive RAG — The basic architecture described above
  • Advanced RAG — Adds re-ranking, query rewriting, hybrid search
  • Modular RAG — Decouples components for maximum flexibility
  • Agentic RAG — Uses AI agents with tools (web search, calculators) alongside retrieval
  • Graph RAG — Uses knowledge graphs instead of/alongside vector stores
  • Multi-modal RAG — Handles images, videos, and audio alongside text

Real-world tools implementing RAG include Google's NotebookLM, which allows users to upload documents (PDF, PPT, etc.) and ask questions with sourced answers.

RAG as a Formal Design Pattern

RAG fits the structure of a formal design pattern: Name — Retrieval-Augmented Generation. Intent — Enable a generative model to produce more accurate answers using proprietary or recent information not used during training. Motivation — Generative models may hallucinate answers when factual information is available in documents but not in the model's training data. Solution — Decompose the problem into search and generation: locate relevant context via retrieval (traditional search or vector database), then provide search results as context in a prompt to the generative model. Trade-offs — Reduces hallucination and enables answers about recent/proprietary information without retraining. However, it requires nontrivial infrastructure, adds retrieval latency and inference cost, and the model may leak proprietary information from the context.

Monolith vs. Microservices Architecture (Introduction)

Monolith Architecture

Monolith Architecture

A monolith is a software architecture where all components of an application are tightly integrated into a single deployable unit. All modules (UI, business logic, data access) run in one process.

In the context of Pipe and Filter:

  • Each filter is a module (e.g., a Python function/class) within the same codebase.
  • The pipe is typically a variable or in-memory data structure passed between functions.
  • All filters run in the same process/application.

Microservices Architecture

Microservices Architecture

A microservices architecture decomposes an application into a collection of small, independently deployable services, each running in its own process and communicating via lightweight protocols (REST, gRPC, message queues).

In the context of Pipe and Filter:

  • Each filter is a separate microservice (its own process, container, or server).
  • The pipe is a network communication mechanism: REST API, gRPC, Kafka, RabbitMQ.
  • Filters are distributed across multiple nodes/servers.
Case Study: Twitter's Monolith-to-Microservices Redesign (2011–2012)

Twitter was originally built as a monolithic Ruby on Rails application by three friends. Once popular, it became slow and hard to scale. Developers introduced caches and bought more machines, but couldn't handle traffic spikes. Worse, changes that marginally improved performance often made the system harder to maintain and debug. Scaling was mostly achieved by buying more hardware, making operating costs unsustainable.

Twitter decided to completely redesign and reimplement the entire system with four explicit quality goals: (1) improve latency and operating cost, (2) improve reliability by isolating failures, (3) improve maintainability with clear module boundaries, and (4) improve modifiability to let small teams release features quickly. None of these goals could be achieved with the existing monolith. The redesign introduced a microservices architecture, replaced Ruby with Scala for performance, built a new distributed storage solution, and embedded reliability strategies (automated failover, monitoring, load balancing) into the infrastructure. While the new system was more complex and costly to develop, it served all four quality goals much better and was remarkably robust even when Twitter was later operated by a much smaller team.

Lesson: The key architecture decisions were driven by explicit quality goals. The monolithic design was appropriate for quick prototyping initially, but was not future-proof given how hard architectural decisions are to change later. This illustrates the core tension between up-front architecture and agility.

Designing for Change and Experimentation

A core design principle in software engineering is to anticipate change and design software so it is easy to change. The central idea is to encapsulate the part of the system likely to change within a module, with stable interfaces, so changes can happen locally without affecting other modules — the core idea of information hiding.

In ML-enabled systems, we can anticipate that models will change regularly: better feature engineering, new hyperparameters, updated ML libraries, new training data, or data/label drift. A "set and forget" approach — training a model once and never updating it — is widely considered an antipattern in production systems. Investing in automated, robust pipelines facilitates easy updates and rapid experimentation.

Models are natural modules that encapsulate internals behind a simple, stable interface (input format → prediction). Deploying models as microservices makes it particularly easy to replace a model with an updated version without changing the rest of the system. Similarly, pipeline stages with modular interfaces let different data scientists experiment with changes in different stages independently — e.g., improving data cleaning without rewriting feature engineering.

Workflow orchestration tools (Airflow, Metaflow, Luigi, Kubeflow) not only automate releases but also schedule multiple offline experiments, training and evaluating different model versions in parallel. Combined with telemetry, monitoring, and A/B testing infrastructure, this gives data scientists fast feedback from real production data.

Key Takeaways

  1. Every architecture can be understood through the lens of Components + Connectors.
  2. The Pipe and Filter pattern is the backbone of all data pipelines, ML pipelines, and workflow engines. Master this pattern and you understand Airflow, Prefect, Scikit-learn Pipeline, LangChain, Kedro, Kubeflow, and Metaflow.
  3. CQRS is essential for modern applications with high read-to-write ratios. In ML, it separates training/deployment (command) from inference/monitoring (query).
  4. RAG is not just an AI technique — it is an architectural pattern that elegantly combines Pipe-and-Filter and CQRS. Understanding the architecture helps you build, debug, and optimize RAG systems.
  5. Real applications are combinations of multiple patterns. A microservices-based RAG system uses Pipe-and-Filter, CQRS, and microservices simultaneously.
  6. Eventual consistency is acceptable for social media and ML model serving; strong consistency is required for financial transactions.
  7. Quality requirements drive architecture. Design decisions should be deliberately considered against quality goals (scalability, modifiability, accuracy, fairness, etc.) rather than emerging from ad hoc implementation choices. Twitter's redesign from monolith to microservices is a classic case study of this principle.
  8. The software engineering concepts (MLOps, LLMOps, AgentOps) build upon these foundational architectural patterns.
  9. Avoid pipeline antipatterns: big-ass script architecture, pipeline jungles, dead experimental code paths, and undeclared consumers. Modularize each pipeline stage with clear interfaces and automate with workflow orchestration tools.
