Software Engineering for Machine Learning

Saga Pattern for Distributed Transactions

📅 Published: 2026-06-13
🎓 Level: Postgraduate
👥 Audience: ML engineers and software architects building distributed agent-based systems

8.1 The Distributed Transaction Problem

You order a meal on a food delivery app. The app creates your order. The restaurant accepts it and starts cooking. Your payment goes through. The delivery person picks it up. Now ask: what if your payment fails after the kitchen has started preparing your food? The kitchen keeps cooking. You never get your food. The system is in an inconsistent state — ingredients consumed, labor wasted, no money charged.

The answer is not a simple database rollback. The problem spans multiple independent services. Each has its own data store. The order service, the restaurant service, the payment service, and the delivery service are all separate. Rolling back one leaves the others unaware. This is the distributed transaction problem. The Saga pattern solves it.

8.1.1 The idea in plain words

Imagine a relay race. Each runner hands off a baton to the next. If the fourth runner drops it, we do not just disqualify that runner. We reverse the entire relay. The third runner takes back the baton. Then the second. Then the first. The race result is wiped clean. That is what a Saga does. It breaks a long transaction into a chain of local steps. If any step fails, it walks back through the chain. Each completed step gets undone in reverse order.

8.1.2 Core Definition - The Saga Pattern

A Saga is a sequence of local transactions. Each updates data within a single service. Each publishes an event after completing. If a local transaction fails, the Saga runs compensating transactions. These undo the changes from preceding steps. The golden rule: all local transactions succeed, or none do.

8.1.3 Why ACID Is Not Enough in Microservices

In a monolithic application, transaction management is straightforward. Everything runs in one process. There is one database. The database provides ACID properties. Atomicity means all or nothing. Consistency means rules always hold. Isolation means concurrent transactions do not interfere. Durability means committed changes survive. A simple BEGIN and COMMIT handles everything.

Microservices break this model. Each microservice owns its own data store. One uses PostgreSQL, another uses MongoDB, a third uses DynamoDB. No single database can coordinate a cross-service rollback. The database-per-service pattern is essential for autonomy. But it makes distributed transactions a hard problem.

Choosing microservices over a monolithic design is itself an architectural decision — the kind that is fundamental and hard to change later without a full redesign. The microservices architecture is one of several common system structures. Others include client-server, multi-tier, event-based, data-flow (pipe-and-filter), and monolithic systems. Each brings different trade-offs for scalability, modifiability, and deployment independence. Microservices allow independent scaling and deployment but introduce the distributed transaction problem. The Saga pattern exists because architects deliberately chose this trade-off — accepting distributed coordination complexity in exchange for service autonomy and independent scalability.

Twitter's complete redesign in 2011–2012 illustrates how architectural decisions are hard to reverse. Originally built as a monolithic Ruby on Rails application, Twitter became slow and expensive to scale. Caches and more hardware couldn't fix the fundamental design. The team had to redesign the entire system from scratch — switching to a microservices architecture, replacing Ruby with Scala, and building a new distributed storage solution. The redesign was expensive but necessary because the original architectural decision (monolith) could not be incrementally evolved to meet new quality goals. This is why architects deliberate trade-offs early: once the system structure is baked in, changing it means rebuilding.

The Saga pattern is one of two pillars of microservices architecture. The other is CQRS, Command Query Responsibility Segregation. Saga is the standard answer when a business transaction spans multiple autonomous services.

8.1.4 The Anatomy of a Saga

Every service in a Saga is called a saga participant. Each participant runs its own local transaction. Each uses its own local data store. Communication between participants is either synchronous or asynchronous. Synchronous means REST API, gRPC, or GraphQL. Asynchronous means a message broker like Kafka or RabbitMQ.

Here is the crucial part: not every step will succeed. Failures are expected. When a failure occurs at step \(k\), the Saga runs compensating transactions. These are the undo operations. They run in reverse order: from step \(k-1\) down to step \(1\). All steps after the failure are never executed.

8.1.4.1 Worked Example - Ordering Masala Dosa

Given: A food delivery system with four services.

Success flow:

Step 1 — Create Order: Order Service inserts order #7891 with status "created".
INSERT INTO orders VALUES (7891, 'masala dosa', 'created')

Step 2 — Accept at Restaurant: Restaurant Service marks order #7891 as "accepted".
UPDATE restaurant_queue SET status = 'accepted' WHERE order_id = 7891

Step 3 — Process Payment: Payment Service charges 180.00 and records the transaction.
INSERT INTO payments VALUES (7891, 180.00, 'charged')

Step 4 — Assign Delivery: Delivery Service assigns rider #42.
INSERT INTO deliveries VALUES (7891, 'rider_42', 'assigned')

Final: All four services have consistent data. Saga success.

Failure flow (step 3 fails):

Steps 1 and 2 succeed. At step 3, the payment gateway returns "insufficient funds."

C3 — Refund Payment: No charge was made. Record "payment_failed" for audit.
UPDATE payments SET status = 'payment_failed' WHERE order_id = 7891

C2 — Cancel Restaurant Order: Tell the kitchen to stop cooking.
UPDATE restaurant_queue SET status = 'cancelled' WHERE order_id = 7891

C1 — Cancel Order: Mark the order cancelled and notify the customer.
UPDATE orders SET status = 'cancelled' WHERE order_id = 7891

Final: The system is back to a consistent state. No waste, no charge, customer informed.

Sense check: Without compensation, the kitchen keeps cooking food nobody pays for. The compensating chain prevents this waste. All or nothing.

8.1.5 The Compensation Chain in Detail

Compensating transactions always flow in reverse order. When \(T_{k}\) fails, we run \(C_{k}\) first. Then \(C_{k-1}\), \(C_{k-2}\), down to \(C_{1}\). Each compensation is the semantic opposite of its forward transaction.

Every transaction name should start with a verb followed by a noun. The compensating version uses the opposite verb on the same noun.

8.1.5.1 Verb+Noun Naming Pattern

Create Order → Cancel Order
Update Inventory → Restore Inventory
Make Payment → Refund Payment
Assign Rider → Unassign Rider

This pattern communicates which operations are pairs. A developer reading the service catalog can instantly spot every undo partner.

What a compensation actually does depends on what the forward transaction did. If the forward insert added a row, the compensation deletes it. If it updated a status from "pending" to "confirmed," the compensation reverts to "pending." If it created a file, the compensation deletes it. Each case is different.

8.1.5.2 Common Pitfalls

  • Assuming compensations always succeed. They can also fail. The database might be down. The external API might be unreachable. You need retry mechanisms and dead-letter queues.
  • Treating read-only ops as needing compensation. A knowledge base lookup that wrote nothing needs no undo. Compensation is only for writes.
  • Forgetting to track state across the chain. When many users run sagas at once, each needs a unique ID. An order ID or correlation ID must flow through every service and compensation.
  • Merging forward and compensating logic into one method. Prefer separate execute() and compensate() methods for clarity.

8.1.6 The Saga as a Design Pattern

The Saga is a design pattern — a named, reusable solution to a known problem with documented trade-offs. In software architecture, patterns codify design knowledge so engineers communicate at a higher level of abstraction rather than reinventing solutions. Saying "let's use the Saga pattern" compactly communicates the shape of the solution, the undo chain, and its known pitfalls. Patterns exist at all scales: from object-oriented patterns like Observer (decoupling notification), to architectural tactics like Heartbeat (detecting component unavailability via regular messages to a monitor), to ML-specific patterns like Feature Store (reusing feature engineering across training and serving) and Retrieval-Augmented Generation (pairing search with generative models to ground outputs in retrieved context). The Saga pattern sits at the architectural scale — it organizes distributed interactions across services.

8.1.7 Two Ways to Implement Saga

There are two styles: orchestration and choreography. Orchestration adds a central coordinator. This orchestrator calls each service in order. It receives responses and decides whether to proceed. Choreography removes the center. Each service knows only its neighbors. Coordination happens through events via a message broker.

These two styles map directly to two common architectural system structures. Orchestration follows the service-oriented architecture pattern — a centralized controller routing requests to self-contained services. Choreography follows the event-based architecture pattern — components listen for messages broadcast by others without knowing who consumes them. The choice between them is not just about workflow management; it is about which architectural style better serves the system's quality requirements.

The key: A Saga breaks a distributed transaction into local steps, each with its own undo. When any step fails, compensation flows in reverse. We now examine the two ways to build one — starting with orchestration, the more common production pattern.

Where this matters. The Saga pattern underpins every large-scale application you use daily. Food delivery platforms coordinate orders across restaurants, payments, and logistics. Ride-hailing apps synchronize ride requests, drivers, and payments. E-commerce manages carts, inventory, and shipping. Without Saga, one failure means data corruption. The pattern now extends to multi-agent AI. If one agent fails, the Saga prevents the rest from proceeding with bad state.

8.2 Orchestration-Based Saga

Picture a conductor leading an orchestra. She does not play an instrument. She knows the full score. She signals when violins enter and when brass swells. She recovers when a musician misses a cue. Musicians play only what and when the conductor signals. If the third movement goes wrong, the conductor can reset from an earlier measure.

This is orchestration. A dedicated orchestrator controls the entire transaction. It calls each service, receives the result, and decides the next action. The services know nothing about the broader workflow. They execute whatever the orchestrator tells them.

The impulse to centralize workflow control maps to a deeper architectural principle: decomposing a system into components that different teams can develop independently. The orchestrator-service boundary is the interface where responsibility divides. The orchestrator owns the sequence logic and failure recovery. Each service owns its domain. This separation is what lets teams work on individual services without understanding the full transaction. But it also means the orchestrator becomes an architecturally significant component — its design directly determines whether the system meets quality requirements like reliability, auditability, and modifiability.

8.2.1 Think of it like a project manager

A project manager tells workers what to do. She tells the electrician to wire the building. Then the plumber to install pipes. Then the painter to paint. If the plumber finds a leak that needs a wall torn out, she does not just stop. She tells the electrician to remove wiring from that wall. She calls a repair crew. No worker decides alone. The project manager holds the full plan. That is orchestration: one brain, many hands.

8.2.2 Core Definition - Orchestration Saga

An orchestration saga uses a centralized controller. The orchestrator maintains the execution sequence. It monitors each step's outcome. It triggers compensating transactions in reverse order on failure. The orchestrator is separate from the participating services. Each service exposes two operations: execute for the forward path and compensate for undo.

8.2.3 How Orchestration Works Step by Step

Let us trace a three-service saga. Service A validates a paper. Service B reviews it. Service C summarizes it. The orchestrator calls them in sequence. State is tracked in a JSON file called saga_state.json.

8.2.3.1 Worked Example - Research Paper Processing Pipeline

Given: Three agents: Validation, Review, and Summary. The orchestrator manages the workflow.

Initial state:

{
  "status": "running",
  "completed_agents": [],
  "metadata": {}
}

Step 1 — Validation: The orchestrator calls the Validation Agent. It reads the paper and sends it to an LLM. The prompt: "Validate this research paper. Respond with 'valid' or 'invalid'." The LLM checks for required sections. It returns "valid." The agent writes validation.txt. The orchestrator updates the state to include validation results.

Step 2 — Review: The orchestrator calls the Review Agent. The LLM prompt: "Identify strengths, weaknesses, and suggestions." The agent writes review.txt. State is updated.

Step 3 — Summary: The orchestrator calls the Summary Agent. The LLM prompt: "Summarize this paper in 300 words." The agent writes summary.txt. State is updated to "completed."

Final: Saga success. The outputs folder has three files. State shows "completed."

Failure variant — Summary Agent fails:

Steps 1 and 2 succeed. At step 3, the LLM API is unreachable. The orchestrator starts compensation.

C3: No file was written since the agent failed. State is updated.

C2: Review Agent deletes review.txt. It removes "review" from state.

C1: Validation Agent deletes validation.txt. It removes "validation" from state.

Final state:

{
  "status": "rolled_back",
  "completed_agents": [],
  "metadata": {}
}

Sense check: The system is back where it started. No partial outputs remain. If we had kept validation and review, the system would look complete when it was not.

8.2.4 The Orchestrator - Code Structure

The orchestrator is a class with a defined sequence of calls. Here is the essential structure:

class SagaOrchestrator:
    def __init__(self):
        self.state = {
            "status": "running",
            "completed_agents": [],
            "metadata": {}
        }

    def run(self, paper_text):
        validation = ValidationAgent()
        result = validation.execute(paper_text)
        self.update_state("validation", result)
        if result == "invalid":
            self.start_compensation_from("validation")
            return "rollback_complete"

        review = ReviewAgent()
        review.execute(paper_text)
        self.update_state("review", {})

        summary = SummaryAgent()
        try:
            summary.execute(paper_text)
            self.update_state("summary", {})
            self.state["status"] = "completed"
            return "saga_success"
        except Exception:
            self.start_compensation_from("summary")
            return "rollback_complete"

    def start_compensation_from(self, failed_agent):
        for agent_name in reversed(self.state["completed_agents"]):
            agent = self.get_agent(agent_name)
            agent.compensate()
            self.remove_agent_state(agent_name)
        self.state["status"] = "rolled_back"

The run method calls agents in sequence. Each agent has execute() and compensate() methods. The start_compensation_from method walks backward through completed agents. Only those that executed get compensated.

8.2.5 Agent Implementations

Here is the Review Agent as an example of the pattern:

class ReviewAgent:
    def execute(self, paper_text):
        prompt = """You are an academic reviewer.
        Identify strengths, weaknesses, and suggestions."""
        response = ask_llm(prompt, paper_text)
        write_to_file("outputs/review.txt", response)
        return {"status": "success"}

    def compensate(self):
        delete_file("outputs/review.txt")
        remove_from_state("review")

8.2.5.1 A critical insight about the orchestrator

The orchestrator itself can be an agent. The example above uses hardcoded logic. But the orchestrator could embed an LLM call. It could decide which agent to call next based on results. Current practice favors simple if-else sequencing. Flows are well-defined by business requirements. LLM-based orchestrators can hallucinate steps. As autonomy advances, more intelligent orchestrators will emerge.

8.2.6 AWS Step Functions

Cloud providers have productized orchestration. AWS Step Functions lets you define a state machine. It calls Lambda functions in sequence. It handles retries, timeouts, and error logic. The step function is the orchestrator. You configure it: "Call Order Lambda, then Inventory Lambda, then Payment Lambda. On failure, execute compensating Lambdas."

Step Functions handle the plumbing. You write only the business logic. The same pattern applies to Agent TKI systems. AWS Bedrock uses a supervisor agent as the orchestrator. It calls Agent 1, then Agent 2, then Agent 3. If Agent 3 fails, the supervisor triggers compensation for Agent 2, then Agent 1.

8.2.6.1 Common Pitfalls with Orchestration

  • The orchestrator is a single point of failure. If it crashes mid-flow, state is lost. Store the saga state in a durable database, not just memory. It must survive restarts.
  • Overloading the orchestrator with business logic. It should only handle sequencing. Business logic belongs in individual services.
  • Neglecting the API Gateway. Client requests hit the API Gateway first. It routes to the correct orchestrator. The orchestrator is one handler behind the gateway.
  • Assuming services must be called sequentially. One saga runs steps in order. But the orchestrator handles thousands of sagas in parallel. The parallelism comes from multi-tenancy.

The key: Orchestration gives centralized control. One component knows the full workflow. It is the dominant pattern because it provides a single place to monitor and debug. Now we turn to choreography — the decentralized alternative.

Where this matters. Orchestration powers most production systems. AWS Step Functions, Azure Durable Functions, and Google Cloud Workflows all follow this pattern. It maps to the service-oriented architecture style where a controller routes to independent services. Orchestration is preferred when transactions have many steps, branching logic, or need a single monitoring point — all common in ML pipelines where model training, validation, and deployment form a multi-step workflow that must be auditable. The central orchestrator also aligns with how ML teams divide work: a pipeline owner defines the sequence while specialists build individual model services behind stable interfaces.

8.3 Choreography-Based Saga

What if there was no conductor? Just musicians who listen to each other. The violinist finishes a phrase. That cue tells the cellist to begin. No one is in charge. The symphony plays in perfect order. This is choreography: coordination without a central controller.

In a choreography-based Saga, there is no orchestrator. Each service knows only its neighbors. It knows which events to publish and which to listen for. The transaction emerges from local interactions. Communication is event-driven through a message broker.

Choreography embodies information hiding, a core software engineering principle: isolate design decisions most likely to change so they can be modified without ripple effects across the system. Each service hides its internal logic behind an event interface. Adding a new participant means subscribing to existing events — no existing service code changes. This is why event-based architectures are attractive when teams anticipate frequent additions of new components. The trade-off is that no single place reveals the full workflow, which complicates debugging and auditing. Architects accept this cost when loose coupling is the highest-priority quality attribute.

8.3.1 Think of it like a relay race without a coach

Each runner watches the incoming runner. When Runner 1 hands off the baton, that act signals Runner 2 to start. If Runner 3 stumbles, she signals back to Runner 2. Runner 2 signals back to Runner 1. Each runner needs to know two things. Who hands to me? Who do I hand to? No central coordinator. The baton and the signals carry all the coordination.

8.3.2 Core Definition - Choreography Saga

A choreography saga coordinates through events. There is no central controller. Each participant publishes events when its local transaction completes. Other participants subscribe to those events. On failure, the failing participant publishes a failure event. This triggers compensating transactions in subscribers. The coordination lives in the event chain. No single component knows the full workflow.

8.3.3 How Choreography Works

Choreography uses a message broker. Kafka or RabbitMQ are common choices. The broker stores events and delivers them to subscribers. In the simplest design, it is a "dumb pipe." It does not contain workflow logic.

Each service is both a publisher and a subscriber. It produces events after completing work. It listens for events that trigger its work. The connections form a graph. Events are the edges. Services are the nodes.

8.3.3.1 Worked Example - Paper Pipeline with Choreography

Given: The same three agents from earlier. No orchestrator. Event-driven coordination.

Success flow — the event chain:

1. Paper submitted. Validation Agent receives "paper_submitted." It validates the paper. Result: valid. It writes validation.txt. It publishes event: "validated."

2. Review Agent receives "validated." It reviews the paper. It writes review.txt. It publishes event: "reviewed."

3. Summary Agent receives "reviewed." It summarizes the paper. It writes summary.txt. It publishes event: "summarized."

Final: Saga success. Event chain: paper_submitted → validated → reviewed → summarized.

Failure flow — Summary fails:

3f. Summary Agent fails. It deletes partial output. It publishes: "summary_compensated."

2c. Review Agent receives "summary_compensated." It deletes review.txt. It publishes: "review_compensated."

1c. Validation Agent receives "review_compensated." It deletes validation.txt. It publishes: "validation_compensated."

Final: Compensation chain in reverse: summary_compensated → review_compensated → validation_compensated. The system is back to its initial state.

8.3.4 Publisher-Subscriber Relationships

Each service needs to know three things. Which events it produces. Which events it consumes. What action to take for each consumed event.

For the three-agent pipeline, the relationship table looks like this:

ServiceSubscribes toPublishes (success)Publishes (failure)
Validation Agentpaper_submittedvalidated(none)
Review Agentvalidated, summary_compensatedreviewedreview_compensated
Summary Agentreviewedsummarizedsummary_compensated

Notice the Review Agent subscribes to two events. "validated" triggers the forward path. "summary_compensated" triggers the compensation path. The event type determines the action.

8.3.4.1 A critical distinction

In orchestration, one component knows the entire workflow. Services know nothing about each other. In choreography, no single component knows the whole. Each service knows only its neighbors. The architect holds the full picture. But at runtime, the workflow emerges from local reactions. Centralized intelligence gives auditability and control. Decentralized intelligence gives resilience and loose coupling.

8.3.5 When to Use Which Pattern

8.3.5.1 Decision Guide

Use choreography when:

  • You have few services (2–4)
  • The workflow is simple and linear
  • Teams want loose coupling
  • You already have a message broker

Use orchestration when:

  • You have many services (5+)
  • The workflow has branching logic
  • You need central monitoring and debugging
  • You want to reorder steps without changing services

Orchestration is far more common in production. Most platforms have dozens of microservices. Tracking event chains across 15+ services becomes unmanageable. With 15 services, each subscribing to events from several others, debugging a failed Saga is hard. You cannot see the full picture from any single place.

The two patterns are not mutually exclusive. A common hybrid uses orchestration for the top-level workflow. But communication between orchestrator and services is event-driven. This gives centralized control with loose coupling.

8.3.5.2 Common Pitfalls with Choreography

  • Losing track of the transaction. No single query answers "what is the state of order #7891?" You need distributed tracing or event logs.
  • Cyclic event dependencies. If A triggers B and B triggers A, you get an infinite loop. Careful topology design is essential.
  • Compensation message storms. A failed compensation can trigger another failed compensation. Retry logic is critical.
  • Assuming every event reaches every service. You control which services subscribe to which topics. There is no broadcast unless designed.

The key: Choreography removes the central coordinator. Coordination emerges through events. It is elegant for small systems but becomes unwieldy at scale. Most teams prefer orchestration beyond 4–5 services. Now we look at the mechanism that makes Saga work — compensating transactions.

Where this matters. Choreography maps to event-driven architectures. These dominate modern microservices and real-time data pipelines. If your organization uses Kafka, choreography extends your existing infrastructure. The pattern also appears in decentralized multi-agent systems. Agents coordinate through a shared channel, not a supervisor.

8.4 Compensating Transactions - The Undo Engine

Here is a simple question that gets complicated. What happens when the undo operation itself fails? You are rolling back a Saga. The payment failed. You cancel the restaurant order. You cancel the customer order. But halfway through, the restaurant database goes down. The compensation for step 2 failed. Now what?

This is not a corner case. In production with dozens of services, compensations fail regularly. The same network issues that caused the original failure strike the compensation chain too. Handling this is where the Saga pattern gets real.

8.4.1 Think of it like Ctrl+Z with network problems

In a text editor, Ctrl+Z is instant. It always works. Now imagine every Ctrl+Z required a remote server call. The server might be down. You would need retry. Press Ctrl+Z, it fails. Press again in 2 seconds, still fails. The editor queues the undo and retries with increasing delays. This is exactly what Saga compensation needs. Retry logic, dead-letter queues, and eventual consistency.

8.4.2 Core Definition - Compensating Transaction

A compensating transaction is the semantic inverse of a forward transaction. It undoes the state changes. It deletes inserted rows, reverts updated status fields, removes created files. Compensations always run in reverse chronological order. Services after the failure point are never executed.

8.4.3 The Verb+Noun Rule

Every transaction must be a verb+noun pair. Its compensation uses the opposite verb on the same noun. This forces developers to identify the undo during design. Not as an afterthought during failure handling.

8.4.3.1 Compensation Pair Design - Cab-Hailing Example

Given: A cab-hailing app with four saga steps.

Step 1: Create Ride Request → Cancel Ride Request
Insert a ride record. Status "requested." Compensate by setting status to "cancelled."

Step 2: Match Driver → Unmatch Driver
Assign driver #42. Set driver to "busy." Compensate by clearing the assignment and setting driver to "available."

Step 3: Estimate Fare → Void Fare Estimate
Calculate fare. Insert estimate record. Compensate by setting status to "voided."

Step 4: Charge Payment → Refund Payment
Call payment gateway. Record transaction. Compensate by issuing a refund.

Sense check: Every forward verb has an obvious compensating verb. Nouns stay constant. A new developer reading the catalog can see every undo pair at a glance.

8.4.4 Implementing Compensation

There are two approaches to structuring compensation code.

Approach 1 — Separate methods (recommended):

class PaymentService:
    def execute(self, order_id, amount):
        txn_id = payment_gateway.charge(order_id, amount)
        db.insert("payments", {
            "order_id": order_id, "amount": amount,
            "txn_id": txn_id, "status": "charged"
        })
        return {"txn_id": txn_id}

    def compensate(self, order_id, txn_id):
        payment_gateway.refund(txn_id)
        db.update("payments", {"order_id": order_id},
                  {"status": "refunded"})

Clean, testable, explicit. Each method does one thing.

Approach 2 — Single method with mode parameter (simpler):

class PaymentService:
    def process(self, order_id, amount, mode="execute"):
        if mode == "execute":
            txn_id = payment_gateway.charge(order_id, amount)
            status = "charged"
        elif mode == "compensate":
            txn_id = db.get_txn_id(order_id)
            payment_gateway.refund(txn_id)
            status = "refunded"
        db.update("payments", {"order_id": order_id},
                  {"status": status})

Approach 2 works for simple cases. Approach 1 scales better for complex logic. Industry prefers clean separation.

8.4.5 Retry and Idempotency

Compensations can fail. Network errors, service crashes, database unavailability. The answer is retry with increasing delays, plus idempotency.

Retry: When a compensation fails, retry with exponential backoff. One second, two seconds, four seconds, eight seconds. If it still fails, move to a dead-letter queue for manual resolution.

Idempotency: Running a compensation twice must produce the same result as once. If the compensation deletes a file that was already deleted, it should not error. It should check "file exists? delete. no? skip." This is critical because retries can deliver duplicate messages.

8.4.5.1 Common Pitfalls with Compensations

  • Not making compensations idempotent. Running twice could double-refund or attempt to delete a missing record. Always check current state.
  • Compensations that are too coarse. If the forward transaction touched five tables, undo all five. Missing partial updates leaves zombie data.
  • Assuming reads need compensation. Read-only operations need no undo. A validation check that wrote nothing gets skipped in the chain.
  • Using DELETE instead of UPDATE. For audit trails, update a status field to "cancelled" or "voided." Never physically delete. You need to know the transaction happened.

The key: Compensating transactions are the undo engine. They execute in reverse order. They must be idempotent. They need retry when they fail. The verb+noun discipline makes pairs explicit. Now we see how distributed transactions coordinate intelligent agents.

Where this matters. Retry and idempotency patterns appear in every distributed system. Message queues, event sourcing, and cloud function triggers all need them. Understanding compensation deeply helps you build reliable systems in any distributed context.

8.5 Saga in Agent TKI Systems

You are building a multi-agent AI system. Agent One validates a paper. Agent Two reviews it. Agent Three summarizes it. Each calls an LLM and produces output files. What if Agent Three's API goes down after Agents One and Two wrote results? You have partial inconsistent output. Validation and review exist, but no summary. There is no way to roll back.

This is the same distributed transaction problem. It happens between AI agents instead of microservices. The solution is the same: apply the Saga pattern.

Designing for change is a core architectural concern, especially in ML-enabled systems. Models constantly need updates — to fix mistakes, respond to data drift, incorporate new features, or adopt better ML techniques. An agent pipeline that cannot recover from partial failure blocks experimentation. Teams become afraid to deploy. The Saga pattern addresses this by guaranteeing that any agent update can be rolled back safely. The compensating chain is the safety net that enables rapid iteration with confidence. This mirrors the broader architectural principle: anticipate what will change and design the system so those changes stay local. The agent interface — each agent's commit() and compensate() contract — is the stable boundary that absorbs internal agent changes without affecting the orchestrator or other agents.

8.5.1 Think of it like a team of specialists

Three specialists work on a document. A fact-checker, a copy editor, and a summarizer. A project manager gives the document to the fact-checker first. If it passes, the copy editor gets it. If the copy editor finishes, the summarizer gets it. If the summarizer hits a corrupt section, the manager pulls the document back. The copy editor reverts changes. The fact-checker resets. The team works sequentially per document. They handle hundreds of documents in parallel. This is Saga for agents.

8.5.2 Core Definition - Saga for Agent TKI

A Saga for Agent TKI applies distributed transaction patterns to multi-agent coordination. A supervisor agent acts as orchestrator. It calls sub-agents in sequence. It monitors their outcomes. Each sub-agent performs a task and reports success or failure. On failure, the supervisor triggers compensating transactions. They undo the work of all previous agents in reverse order. The mechanism is identical to the microservices Saga.

8.5.3 The Agent as a Saga Participant

An AI agent in a Saga differs in one way. Instead of a fixed business function, its execute() method calls an LLM. The structure is the same. An execute method for the forward path. A compensate method for undo. State management through a shared store.

What makes an agent a saga participant is the contract. It must:
(1) Accept input from the orchestrator.
(2) Return clear success or failure.
(3) Document what state it changed.
(4) Provide a compensate method to undo those changes.

If an agent only performs read operations, it needs no compensation. A knowledge base lookup that writes nothing gets skipped. The Saga only compensates writes.

8.5.4 SQL vs. NoSQL for Agent State

How to store saga state is a key architectural decision. The shared store tracks completed agents, their outputs, and the status. A JSON file works for demos. Production needs a database. This is not just a storage question — it is a decision that determines how the system scales and how easily it can evolve.

In software architecture, storage decisions are often architecturally significant: they are fundamental, hard to change later, and directly determine whether the system meets its quality requirements. The choice between SQL and NoSQL constrains future flexibility, affects development speed, and influences how teams structure agent output.

Levels 3–4 (Bounded Agents): Agent output is constrained by a schema. Pydantic models or type hints define the fields. You know the data shape. A relational SQL database works well. You define columns and enforce constraints.

Levels 5–6 (Fully Autonomous Agents): The agent decides its output structure dynamically. It might return nested JSON of unknown depth. A NoSQL database is the natural fit. MongoDB or DynamoDB stores flexible documents. No schema migrations needed. New fields do not require ALTER TABLE.

Most agent systems today are levels 3–4. Outputs are bounded by Pydantic. SQL is viable and preferred for strong consistency. As autonomy advances, the path leads to NoSQL. Teams building for the future should plan for schema flexibility.

8.5.5 The Supervisor Agent

In production systems, the orchestrator is called a supervisor agent. The term suggests intelligence. The supervisor could decide dynamically which agent to call next. Based on the previous agent's output.

Current reality is more pragmatic. Most supervisors use hardcoded sequences. If-else logic, not LLM decisions. The reason is reliability. An LLM deciding the next step can hallucinate. It might choose the wrong agent. It might skip a required compensation. For mission-critical workflows, deterministic sequencing dominates. The LLM's intelligence lives in the agents. The orchestrator only sequences.

This may change. At higher autonomy, orchestrators may route dynamically. "If the paper is about NLP, route to the NLP reviewer." But compensation must stay deterministic. What to undo and in what order must never involve randomness.

8.5.5.1 Common Pitfalls with Agent Sagas

  • Using LLM as orchestrator without deterministic fallback. The sequencing logic must be deterministic. Even if agent work is intelligent.
  • Not constraining agent output. Use Pydantic models or schemas. Unconstrained LLM output may not be storable or parseable.
  • Forgetting LLM latency. Three agents each taking 10–30 seconds means over a minute per transaction. Design timeouts. Consider parallelizing independent agents.
  • Assuming Saga is only for microservices. The same principles apply to agent pipelines. Sequential local transactions. Compensating undo. All or nothing.

The key: The Saga pattern translates directly to Agent TKI. A supervisor orchestrator calls agents in sequence. Each agent performs an LLM task. Compensation undoes work on failure. The same principles — naming, idempotency, retry, state management — apply unchanged. Multi-agent systems inherit decades of distributed systems wisdom.

Where this matters. Multi-agent AI systems are not monolithic. They inherit the same architectural diversity as traditional software. A recommendation pipeline may need Saga for frequent model updates but can fall back to cached results if a step fails — reliability is negotiable. An autonomous driving system running dozens of models on constrained onboard hardware faces hard real-time requirements where compensating transactions must execute in milliseconds, not seconds. A privacy-focused on-device agent may run Saga entirely locally with no network. The Saga pattern is universal, but its implementation weight — retry policies, broker choice, state storage — must be tailored to the system's specific quality requirements. No two ML-enabled systems are architecturally identical. The architect's job is to understand which qualities matter most and design the Saga implementation to serve those qualities first.
