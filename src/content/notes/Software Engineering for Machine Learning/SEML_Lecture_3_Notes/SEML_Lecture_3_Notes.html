1. Architectural Decomposition of ML Systems

When building production-ready applications, a critical software engineering principle is to realize that the machine learning model itself is only a small component of the entire system. A system consists of both machine learning (ML) and non-machine learning (non-ML) components working in unison. Understanding the boundaries, interactions, and relative roles of these components is essential to successfully architecting software for machine learning.

3.1 The Anatomy of an ML System: Beyond the Model

In a production environment, the ML model is surrounded by a vast infrastructure of traditional software engineering modules. This layout is analogous to an iceberg: the model is the visible tip, but the majority of the code supports data ingestion, infrastructure management, monitoring, and integration.

Fundamentally, software — with or without ML — can only interact with the real world mediated through sensors and actuators. Software takes input data, processes it, and produces output data. It has no direct insight into real-world phenomena (e.g., whether a person actually fell) — it must rely on sensors or human data entry that translate reality more or less reliably. Similarly, output data only affects the world if interpreted by humans or actuators in the intended way. This World and Machine distinction is critical: to architect reliable ML systems, we must critically examine the assumptions linking real-world phenomena to software inputs and outputs, not just the code itself.

3.2 Case Study: Live Speech-to-Text Transcription in MS Teams

To illustrate this integration, let us examine a real-time transcription service, such as the live transcription feature built into Microsoft Teams during lectures.

Scenario: MS Teams Live Transcription

In a live lecture, when a speaker speaks, the system must process their audio in real time, generate an English text translation or transcript, and render it to the audience.

While the transcription itself relies on a sophisticated speech-to-text ML model, the application as a whole requires several non-ML software modules to function:

  • User Interface (UI): Captures audio/video feed from the speaker and displays the generated transcripts dynamically to the users.
  • User Account Management: Stores and validates user accounts (e.g., credentials and identity profiles like instructor@university.edu).
  • Audio Streaming and Upload Service: Handles real-time streaming packets of audio from the client to the cloud.
  • Enterprise Payments Module: Processes retail payments, subscriptions, or institutional licenses (e.g., university-wide enterprise licenses).
  • Database and Storage (DB): Persists records of lecture videos, generated text transcripts, and user data in cloud storage.
  • Azure Cloud Processing Unit: Manages compute nodes and worker processes (e.g., Microsoft Azure infrastructure).
  • Logging & Monitoring: Captures system events, errors, latency metrics, and usage statistics for administrators.

In this architecture, the Speech Recognition module is the ML component (performing predictive or sequence modeling). The other modules are traditional software engineering components. Together, they form the complete transcription system.

3.2.1 Core vs. Auxiliary ML Components

An ML component does not always need to be the central core of an application. It can serve in two capacities:

3.2.1.1 Core Components

The application cannot function without the ML model. If the model is down, the core service fails.

  • Example: The Speech Recognition module in a transcription tool. If the speech recognition model crashes, the system can no longer generate live text transcripts, rendering the transcription service completely non-functional.

3.2.1.2 Auxiliary (Supportive) Components

The application's core functionality is non-ML, but the ML model adds supportive or auxiliary capabilities.

  • Example: Tax Software with Audit Risk Prediction. The core of the software is tax computation (a highly complex, deterministic rule-based calculation system). The software computes taxes perfectly using hardcoded tax formulas. However, the system includes an auxiliary ML model that predicts the audit risk (the probability of the return being audited by tax authorities). This is an add-on value proposition. If the audit risk prediction model fails, the user can still calculate and file their tax return without issues.

3.3 The Machine Learning Pipeline: Decomposing the Stages

When we productionalize an ML component, it is supported by a comprehensive machine learning pipeline that runs behind the scenes:

These stages are defined as follows:

  1. Model Requirements: Formulating the business goal, determining suitability, and establishing performance targets.
  2. Data Collection: Gathering relevant historical datasets from internal databases or external sources.
  3. Data Cleansing: Filtering outliers, resolving missing values, and validating data types.
  4. Data Labeling: Mapping ground-truth outcomes to training instances (critical for supervised learning).
  5. Feature Engineering: Selecting, scaling, and transforming features to maximize mathematical representation.
  6. Model Training: Selecting algorithms, training candidates, and validating performance thresholds.
  7. Deployment: Containerizing, versioning, and deploying the model to serving nodes.
  8. Monitoring: Continuous observation of system resources and statistical characteristics in production.

3.5 Why Sprints and Agile Fail Data Science: The Exploratory Nature

Traditionally, attempts to force data science projects into standard Software Engineering Agile sprint models (e.g., 2-week cycles) fail. The reasons are structural:

  • Exploratory Nature: Traditional software tasks are deterministic: "Build a database table with these columns" has a clear, predictable completion timeline. In contrast, "Evaluate if our dataset has enough predictive power to classify credit risk with ≥ 85% accuracy" is highly experimental. The scientist must write experimental scripts, execute exploratory data analysis (EDA), try multiple algorithms, and evaluate models.
  • The EDDA Loop: This Experiment-Driven Data Development (EDDA) process is iterative and research-focused. Often, data scientists discover that the available data lacks correlation, triggering a return to the data collection or cleaning phase. Forcing this research workflow into rigid 2-week sprint boundaries leads to artificial shortcuts and low-quality models.

3.6 The Integration Interface: API-driven Deployments

The bridge between these two pipelines is typically established at the model integration phase. The trained ML model is deployed as an independent service (often containerized on a Kubernetes cluster) that exposes a standardized interface, such as an HTTP POST API endpoint.

Integration in Action: Healthcare Classifier

In a hospital setting, a patient admission app (written by software engineers using React/Node.js) collects data. To predict a patient's risk category, the app makes an API request:

  1. A nurse enters patient demographics and vitals into a tablet (non-ML front-end).
  2. The client application triggers an HTTP POST request containing a JSON payload to the ML model API endpoint.
  3. The model running in the cloud processes the payload and returns a prediction score (e.g., {"risk": "HIGH", "probability": 0.87}).
  4. The hospital management system consumes this response, flags the patient file, and triggers notification alerts for medical staff.

This decouples the deployment lifecycles of the core web app and the ML model services.

3.7 Data Drift, Concept Drift, and Continuous Retraining

Unlike traditional software modules, which remain static until the next code update, ML models face performance degradation in production over time due to shifts in the real-world environment.

3.7.1 Data Drift

Data drift occurs when the statistical properties of the input features change over time.

  • Example: A credit risk model was trained on applicants who primarily worked in manufacturing. During a major industrial shift, the customer base shifts towards gig-economy workers. The incoming income distribution and employment variables look statistically different from the training dataset.

3.7.2 Concept Drift

Concept drift occurs when the statistical relationship between the inputs and the target labels changes over time.

  • Example (COVID-19 patient outcomes): In Wave 1, older age was strongly correlated with high mortality. During Wave 2, the virus mutated (different symptom profiles, younger patients impacted), and hospitals introduced new therapeutics. A machine learning model trained on Wave 1 statistics to predict patient mortality will experience concept drift. The correlation between age and mortality has shifted, rendering the model inaccurate.

3.7.3 The Retraining Loop

To handle these shifts, the ML pipeline must establish a continuous monitoring and retraining loop. The system logs prediction inputs (serving data), matches them with actual outcomes (ground truth labels) over time, and triggers automated retraining when drift metric thresholds are breached.

3.8 Monitoring: System Metrics vs. ML Metrics

During operations, the systems are monitored using completely different metrics:

Designing Good Measures

Measurement is fundamental — Douglas Hubbard defines it as "a quantitatively expressed reduction of uncertainty based on one or more observations." Even seemingly intangible properties (quality, risk, security) are measurable if we care about them enough to make decisions based on them.

Every measure requires three ingredients:

  1. Measure: What we intend to capture (e.g., "customer satisfaction of subscribing attorneys").
  2. Data collection: What data is collected and how (e.g., monthly survey of 5% of attorneys).
  3. Operationalization: How the measure is computed from the data (e.g., average star rating).

The Goal-Question-Metric (GQM) approach helps avoid ad hoc measures: first identify the goal, then questions that answer whether the goal is met, then concrete measures that answer those questions. This top-down design ensures measurement activities are actually meaningful toward the goal.

Watch out for the streetlight effect — the temptation to use convenient proxies (e.g., counting chatbot messages) for difficult-to-measure concepts (e.g., user satisfaction), simply because the data is easily available. Also remember Goodhart's Law: "When a measure becomes a target, it ceases to be a good measure." Avoid using measures as incentives — humans and machines will find ways to game them.

3.9 Roles and Personas

Successful execution of an ML system requires clear division of labor and role specialization:

3.9.1 Software Engineer (SE)

Responsible for designing the overarching application architecture. This includes building user interfaces, microservices, and databases (e.g., PostgreSQL), setting up authentication modules, and integrating API layers.

  • Tech Stack: React, Node.js, Spring Boot, Python, SQL, REST/gRPC.

3.9.2 Data Scientist (DS)

Focuses on the statistical modeling phase. The DS conducts exploratory data analysis (EDA) to understand feature distributions, clean missing values, write feature engineering transformations, and train models.

  • Tech Stack: Python, R, Jupyter, Pandas, Scikit-Learn, TensorFlow, PyTorch.

3.9.3 Machine Learning Engineer (MLE)

Bridges the gap between data science and software engineering. The MLE has strong software engineering skills and handles the integration and deployment of model endpoints. They design MLOps pipelines, optimize inference latency, set up container orchestration, and version models and datasets.

  • Tech Stack: Docker, Kubernetes, MLflow, DVC, Feast, Triton Inference Server.

3. Case Study: Baidu Apollo Autonomous Driving (ADAS)

To understand how multiple ML and non-ML components cooperate under strict real-time constraints, let us examine the system architecture of the Baidu Apollo Autonomous Driving (ADAS — Advanced Driver Assistance Systems) platform.

3.10 Overview of Apollo Architecture: The Multi-Model System

In a production autonomous vehicle, there is no single "AI model" that drives the car. Instead, the vehicle's computer runs a complex system of hardware components, software filters, and approximately 28 ML models that must interact in unison to make steering, braking, and acceleration decisions.

3.11 Sensor Modalities and Input Paths

As shown in the flow, the vehicle leverages multiple sensor sources to construct a 360-degree view of its environment:

3.11.1 The Camera Path (Vision)

  • Captures raw high-frequency video frames.
  • Passes video through Image Pre-processing algorithms (resizing, edge enhancement, normalization).
  • Invokes multiple models simultaneously:
    • Traffic Light Perception: Classifies signal state (Red, Green, Yellow) using Convolutional Neural Networks (CNNs).
    • Lane Detection: Identifies road boundaries and lanes.
    • Camera Obstacle Detection: Identifies objects (e.g., using 3D CNNs or YOLO 3D variations).
  • Outputs pass through Post-processing filters to reduce prediction noise.

3.11.2 The LiDAR / Radar Path (Spatial)

  • Generates raw distance metrics and 3D spatial coordinate point clouds.
  • Pre-processes the point cloud data.
  • Uses spatial detection models to map pedestrians, physical barriers, and vehicles.
  • Filters and post-processes the findings.

3.11.3 Sensor Fusion and Multi-Source Data Integration

The control unit fuses the structured outputs of both the Camera and LiDAR pipelines. This enables the car to reason about its surroundings with high confidence, even if one path has noisy data.

3.12 Critical vs. Non-Critical Components in Automotive Systems

In complex configurations like Apollo, components are categorized based on their impact on safety:

  • Critical Components: Modules whose failure immediately impacts physical safety or causes system crashes.
    • Example: Obstacle detection, lane tracking, and brake control logic. A single failure or wrong prediction here can result in a crash.
  • Non-Critical Components: Modules whose failure might degrade the user experience but do not present immediate safety risks.
    • Example: On-screen route visualization, music controls, or climate adjustment widgets.

3.13 Levels of Autonomy in ADAS

Autonomous driving platforms are defined across Levels 0 to 5 based on the SAE (Society of Automotive Engineers) classification:

  • Level 0 (No Automation): The driver performs all driving tasks.
  • Level 1 (Driver Assistance): The vehicle can assist with steering or acceleration/deceleration (e.g., adaptive cruise control).
  • Level 2 (Partial Automation): The vehicle controls both steering and acceleration/deceleration simultaneously (e.g., lane keeping + cruise control). The human driver must monitor the environment at all times.
  • Level 3 (Conditional Automation): The system monitors the environment and handles steering/braking. The human driver is not required to monitor the road constantly but must be ready to intervene when prompted by the system.
  • Level 4 (High Automation): The system handles all driving tasks in specific conditions or regions (geo-fenced). The driver can go to sleep, and the system can stop safely if the driver does not take control.
  • Level 5 (Full Automation): The system drives under all road, traffic, and weather conditions. No steering wheel or pedals are required.

3.14 Fault Tolerance and Mitigation

Because the failure of an ML model (due to a bad prediction or system crash) in a critical module can be catastrophic, the system architecture must implement strict fault tolerance mechanisms. ML models are unreliable components — they may fail for unknown reasons at unknown times. Critically, model mistakes are not usually randomly distributed: a model may have 99.99% average accuracy yet consistently fail for specific subpopulations (e.g., wheelchair users in pedestrian detection). Multiple models trained on the same data tend to make similar mistakes, relying on the same spurious correlations. The following design strategies help mitigate these inherent risks:

3.14.1 Redundancy

Running multiple identical or complementary sensors and processing pipelines. If one camera is obscured, other cameras or LiDAR units cover the blind spot.

  • Example: Using both cameras and LiDAR. If heavy fog blinds the camera, the LiDAR/radar can still map distance and objects.
  • Important: Unlike hardware redundancy, software redundancy is less effective for ML — running multiple instances of the same model produces identical outputs. Even independently trained models on the same data often exhibit similar problems. Redundancy works best when combining substantially different sensor modalities (vision + LiDAR + radar + thermal).

3.14.2 Fallback

If a highly accurate neural network model fails or times out, the system automatically falls back to a simpler, deterministic, rule-based algorithm (or a lighter model) to guarantee safety.

  • Example: If a CNN-based traffic light detector fails to return a result within 10ms, the system falls back to a simple color-thresholding pixel calculation to check if red lights are present.
  • This is an instance of the doer-checker pattern: a secondary component (checker) monitors the primary component (doer) and intervenes with corrective action when a mistake is detected. The checker often relies on indirect signals — e.g., a gyro sensor detecting dangerous train lean rather than directly checking acceleration commands.

3.14.3 Graceful Degradation

Instead of shutting down completely, the system degrades its performance gracefully.

  • Example: If lane detection accuracy drops due to heavy fog, the car reduces its speed, increases distance thresholds to vehicles in front, and prompts the human driver to take control.
  • Example: If the LiDAR sensor fails, the train may continue operating with vision only, but at lower speeds with larger obstacle distance margins.

3.14.4 Guardrails and Isolation

Guardrails process model predictions through additional non-ML steps to catch and filter problematic outputs — e.g., filtering email response suggestions against a banned-word list, or platform screen doors in automated metro stations that prevent passengers from falling on tracks regardless of what the vision model detects. Containment and isolation ensures that unreliable, low-critical components (e.g., on-board advertisements) cannot impact high-critical components (e.g., train control), preventing fault propagation across the system.

3.15 Non-Ideal Scenarios: The Challenge of Indian Roads

During the lecture discussion, the professor addressed the challenge of applying level 4/5 autonomous vehicles to Indian roads (e.g., Delhi, Bangalore):

  • Erratic Pedestrian Behavior and Stray Animals: Models trained on clean, structured highway data struggle with the chaotic, unpredictable movements of pedestrians or stray animals.
  • Infrastructure Noise: Lack of lane discipline, sudden humps, and potholes represent noise.
  • Human-in-the-Loop Necessity: Because models cannot predict all edge cases, Level 3 and Level 4 architectures are used for Indian trials, ensuring a safety driver is ready to override the ML controls immediately. This illustrates a broader Human-AI interaction design principle — three common modes exist: Automate (system acts without user involvement, best when confidence is high or mistake cost is low), Prompt (system asks user to confirm, keeping humans in the loop but risking notification fatigue), and Organize/Annotate (system shows information or ranked suggestions but leaves final decisions to the user, least intrusive). High-stakes tasks that need accountability tend to keep humans in the loop.

4. When to Use Machine Learning

Machine learning is not a "silver bullet" for every software engineering challenge. It is expensive to build, computationally intensive to run, and hard to maintain. A core requirement engineering task is to determine whether a problem actually requires machine learning. Adopting ML when not needed introduces unnecessary complexity, cost, and risk — if simpler hand-coded algorithms or heuristics (e.g., recommending the most popular songs from artists a user already listens to) can solve the problem, that is often the wiser choice.

Prerequisite: The Application Must Tolerate Mistakes

ML models are fundamentally unreliable functions — they often work but sometimes make mistakes, and it can be hard to even define what "correct" means. Therefore, ML should only be used in applications that can tolerate mistakes. In non-critical settings like music recommendations, occasional poor suggestions are acceptable. In high-stakes settings like cancer prognosis, mitigation mechanisms (human-in-the-loop oversight, confirmation biopsies) can reduce risk to acceptable levels. But if correctness is essential and a specification of correct behavior exists that can be implemented with traditional code — as in accounting systems or airplane control signals — ML is not a good match.

3.16 Jeff Hilton's Three Rules of Thumb

Based on principles defined by Jeff Hilton and industry practices, there are three primary categories of problems where machine learning is the appropriate choice:

3.16.1 Intrinsically Hard Problems

Intrinsically hard problems are those where human beings can perform the task naturally, but writing a formal, step-by-step rule-based program is practically impossible.

  • Language Processing: English (or any human language) contains massive ambiguity, sarcasm, changing contexts, and cultural nuances.
    • The Rule-Based Failure: Early chatbots relied on manual grammar rules, dictionaries, and intent matching. This failed to capture semantic similarity. For instance, the sentences "Book me a slot with Dr. Smith" and "Can I see the doctor?" share no identical words, yet represent the same intent.
    • The ML Success: Transformer-based LLMs learn the representation and semantic context of language natively.
  • Computer Vision: Recognizing a dog or a traffic light in varying lighting, angles, weather (e.g., heavy fog in Delhi vs. sunny day in Bangalore), or environmental settings (e.g., Antarctica vs. city streets) cannot be modeled using static pixel-checking rules.

3.16.2 Big Problems (The Big Data Deluge)

Big problems are those where the sheer scale of data processing and personalization makes rule-based systems impossible. For such problems, hand-crafting a program might be possible in principle, but manually maintaining it becomes infeasible — resolving conflicts between multiple hard-coded rules and handling exceptions can be especially tedious. Automated learning of rules through ML may be far easier than writing and maintaining those rules manually.

Historical Example: The Failure of Hand-Curated Web Directories

In the early days of the internet, companies like Yahoo! manually curated directories of websites organized by category. This approach simply did not scale as the web grew — humans could not keep up with the volume of new sites. ML-based search engines (e.g., Google) have dominated ever since, automatically learning to rank and categorize pages from link structure and content signals.

The Big Data Deluge (Every 60 Seconds)

Every minute, global users generate:

  • 6.3 Million Google searches
  • 41.6 Million WhatsApp messages
  • 694K Instagram Reels played
  • ≈ 7,000 prompts submitted to ChatGPT

Recommending songs or videos to hundreds of millions of users from a library of tens of millions of tracks cannot be coded with static logic. The recommendation system must automatically digest user behavior signals (e.g., watching horror movies on a Friday night) and update its recommendation embeddings dynamically.

3.16.3 Time-Changing Problems

Time-changing problems are those where the underlying data patterns change continuously, making hard-coded rules obsolete. In music recommendations, individual preferences and music trends change over time, as does what music is available. Change is constant, and even if we had hardcoded recommendation rules, it would be tedious to update them regularly. ML models — combined with retraining and monitoring — can adapt where fixed rules cannot.

  • Fraud Detection: Credit card fraud patterns change constantly. A simple static rule like "Flag any transaction > INR 50,000" is easily bypassed by fraudsters who make multiple transactions of INR 49,000. It also annoys legitimate users. The model must learn dynamic behavior patterns based on user history, locations (urban vs. rural), and transaction contexts.

3.16.4 Continuous Learning and the Flywheel Effect

Machine learning is particularly effective in settings where we have continuous access to data and can improve and update the model over time. The ML flywheel effect describes a virtuous cycle: systems observe users over time to collect more data, which builds better models, which attract more users, producing even more data. For time-changing problems, continuous learning is essential — the system regularly needs fresh training data to retrain the model. Without access to data or no mechanism to observe data continuously, building an ML solution may not be feasible.

3.16.5 Costs, Benefits, and the Business Case

Ultimately, the decision to use ML comes down to comparing costs and benefits. Costs include initial data acquisition, model building, deployment, and ongoing operational expenses (hardware, energy, human oversight). Benefits can be substantial, especially when developing breakthrough capabilities that dominate markets — as TikTok's recommendation engine did by creating an entirely new social-media user experience. A useful framing from the book Prediction Machines views ML's key benefit as making predictions cheaper, which are then used as input for manual or automated decisions. Cheaper and more accurate predictions can replace human experts (e.g., record-store employees → automated music recommendations) or enable entirely new applications previously cost-prohibitive at scale. However, it is always worth asking: could a simple heuristic, a semi-manual solution, or even removing the feature entirely be better?

3.17 Deterministic vs. Probabilistic Systems

Traditional software systems are deterministic: given the same input, they always produce the same output. ML systems are probabilistic: their outputs are based on statistical confidence scores and learned representations.

3.18 Hyperparameters and LLM Behavior

A common student question: "Does an LLM like ChatGPT learn on the fly from user prompts, and is that why the accuracy seems to change over time?"

The professor clarifies:

  • On-the-fly learning: LLMs do not update their weights in real-time from a single chat prompt. Real-time updates could lead to model poisoning or instability.
  • Hyperparameter Tuning: The perceived change in behavior or improved accuracy in newer versions (e.g., GPT-5 over 3.5) is due to offline retraining on larger datasets and better hyperparameter tuning.
  • Context Windows: When you chat, the model maintains "context" (working memory) within the prompt's context window, allowing it to generate relevant responses.

Two key hyperparameters control this behavior:

  • Temperature (0 to 1): Controls randomness. Near 0, the model is highly deterministic (best for math/RAG). Near 1, it is highly creative but prone to hallucinations.
  • top_P (Nucleus Sampling): Restricts sampling to the cumulative probability threshold.

3.19 The API Token Pricing Model

For API-driven models, costs are calculated based on token counts across three layers:

Total Cost = Input Tokens + Context Tokens + Output Tokens

Example Token Calculation

Suppose you ask: "Who is the Prime Minister of India?" (≈ 7 input tokens).
The system answers: "Narendra Modi." (≈ 2 output tokens).
You are billed for 9 tokens.

If you upload a 2-page PDF document (≈ 1,500 context tokens) and ask: "Summarize this document" (≈ 3 input tokens), the LLM reads the context and generates a 50-word summary (≈ 60 output tokens). You are billed for:

1,500 (context) + 3 (input) + 60 (output) = 1,563 tokens

This shows why managing context window sizes is a key engineering and cost consideration.

5. Goal-Oriented Requirements Engineering (GR for ML)

To map high-level enterprise goals to concrete machine learning specifications, the University of Toronto (2021) introduced Goal-oriented Requirement Engineering for Machine Learning (GR for ML). Similar to how UML standardizes traditional software design, GR for ML provides a formal notation to model requirements in ML systems.

3.20 The Three Views of GR for ML

GR for ML organizes the system requirements into three distinct, complementary views:

  1. Business View: Identifies the business goals, stakeholders (actors), key decisions, and measurable indicators.
  2. Analytics Design View: Specifies the type of analytics (descriptive, predictive, prescriptive), choice of ML algorithms, and soft goals (quality attributes like robustness or interpretability).
  3. Data Preparation View: Specifies data cleansing steps, dimensionality reduction (PCA), and pre-processing transformations.

3.21 Business View: Symbols and Notation

The Business View uses the following standard symbols:

Table 2: GR for ML Business View Elements
Element Notation Description
Actor Stick Figure Stakeholder or role in the organization
Strategic Goal Ellipse High-level business goal
Decision Goal Ellipse with a (D) symbol Specific decision point that must be taken
Question Goal Ellipse with a (Q) symbol Specific question that must be answered to make the decision
Insight Box/Ellipse with an (I) symbol Data-driven prediction, classification, or analytic output
Indicator Segmented Box Measurable metric used to evaluate success

3.22 Running Example: Credit Risk Prediction in a Bank

Let us apply the GR for ML Business View to model a bank's credit risk prediction system.

Case Study: Credit Risk Prediction

Goal: Optimize loan processing decisions to control the bank's non-performing asset (NPA) rates.

  • Actor: Loan Processing Agent (bank employee).
  • Decision Goal (D): "Take a decision on credit application" (Approve/Reject).
  • Question Goal (Q): "What will be the credit risk of the current applicant?"
  • Insight (I): "Credit risk classification: HIGH/LOW" generated by a predictive model.

To define the insight, the Business View specifies the following structural parameters:

  1. Input: Applicant Profile (e.g., salary, credit score, age, region, employment type).
  2. Output: Risk Category (HIGH or LOW).
  3. Usage Frequency: Per Instance (the model is evaluated every time an applicant submits a loan request).
  4. Update Frequency: Monthly (the model is updated monthly with new data).
  5. Learning Period: 48 Months (the training process uses the last 4 years of historical loan data).

3.23 Goal Relationships: Support vs. Conflict

When capturing requirements, goals can either support or conflict with each other. These relationships must be identified early to guide architectural decisions. Importantly, goals exist at multiple layers, and misalignment between layers is a common source of project failure:

Layering Goals in an ML System

  1. Organizational Goals: Revenue, profit, stock price — or for non-profits, mission outcomes like reducing CO₂ emissions. Leading indicators (KPIs) like license renewals or customer satisfaction act as proxy measures.
  2. Product Goals: Concrete outcomes the product should produce — e.g., promoting attorneys, connecting potential clients with legal help, answering simple legal questions.
  3. User Goals: What various users want. Multiple user types may have different or even conflicting goals — attorneys want client leads; their clients want free legal advice.
  4. Model Goals: Optimizing prediction accuracy. The model's accuracy goal should serve the higher-level goals, not exist in isolation.

Critical Insight: Better model accuracy does not always translate to better business outcomes. Booking.com famously found that improved ML models in many experiments did not translate into improved hotel bookings. In a legal chatbot, more advanced legal knowledge might mean fewer clients contract attorneys — hurt the attorneys' satisfaction and thus the organizational goal.

  • Supporting Relationship (+): Achieving one goal positively influences another.
    • Example: High model accuracy supports positive User Experience.
  • Conflicting Relationship (−): Optimizing for one goal negatively impacts another.
    • Example 1: Accuracy vs. Latency. A larger, highly accurate deep ensemble model generates better predictions but increases response latency (e.g., 30 seconds vs. 1 second).
    • Example 2: Cost vs. Quality. Utilizing advanced commercial models (like GPT-5) improves answer quality but increases API token costs. Switching to smaller models (like GPT Nano or Mini) lowers costs but degrades quality.

6. Alternative Lifecycle Methodologies

While GR for ML is focused on Requirements Engineering, the overall development lifecycle of data mining and machine learning projects is often guided by other established industrial methodologies:

3.24 CRISP-DM

The Cross-Industry Standard Process for Data Mining consists of 6 iterative phases:

  1. Business Understanding: Focuses on understanding project objectives and requirements from a business perspective.
  2. Data Understanding: Involves initial data collection, data exploration, and data quality checks.
  3. Data Preparation: Prepares the final dataset through cleaning, transformation, and feature selection.
  4. Modeling: Selecting and applying modeling techniques and calibrating parameters.
  5. Evaluation: Evaluating the model against project business objectives.
  6. Deployment: Deploying model outputs or pipelines to production.

3.25 SEMMA

Developed by the SAS Institute, SEMMA focuses on:

  1. Sample: Extracting a representative sample from a large dataset.
  2. Explore: Conducting visual and statistical data exploration.
  3. Modify: Creating, selecting, and transforming variables.
  4. Model: Applying statistical and machine learning algorithms.
  5. Assess: Evaluating model utility and performance.

3.26 KDD

The Knowledge Discovery in Databases scientific process contains:

Selection → Pre-processing → Transformation → Data Mining → Interpretation/Evaluation

Quick Revision Checklist

  1. ML Model is a Small Part: A system consists of both ML components (e.g., Speech Recognition) and non-ML components (e.g., UI, DB, Accounts). Software can only interact with the world mediated through sensors and actuators — the World and Machine distinction highlights that assumptions linking real-world phenomena to software inputs/outputs must be critically examined.
  2. Core vs. Auxiliary ML: In transcription, speech recognition is a core ML component. In tax software, audit risk prediction is an auxiliary component.
  3. Separate Pipelines: Software engineering and ML pipelines are separated due to different cycle times (structured sprints vs. exploratory EDDA) and different versioning requirements.
  4. Integration Point: The pipelines integrate via API endpoints, such as containerized microservices exposing HTTP POST interfaces.
  5. Operational vs. Model Metrics: SE monitors system resources (CPU, latency); ML monitors classification quality (precision, recall, drift). Good measures require three ingredients: measure definition, data collection plan, and operationalization. The Goal-Question-Metric (GQM) approach avoids ad hoc measures. Beware the streetlight effect (using easy proxies for hard concepts) and Goodhart's Law (measures become bad targets when incentivized).
  6. Engineering Roles: Software Engineers build the application framework; Data Scientists build models; ML Engineers focus on integration, operations, and MLOps pipelines.
  7. Apollo ADAS Case Study: Uses ≈ 28 models in parallel. Separates Camera (vision) and LiDAR (spatial distance) paths into a central predictor/control unit.
  8. Mitigating Failures: Systems implement fault tolerance via Redundancy (sensor duplication — note that ML model redundancy is less effective than hardware redundancy), Fallback (doer-checker pattern, rule-based alternatives), Graceful Degradation, Guardrails (non-ML output filters), and Isolation (containing unreliable components). Model mistakes are not random — they cluster on specific subpopulations and inputs.
  9. Levels of Autonomy: Range from Level 0 (manual) to Level 5 (full automation). Most modern systems operate at Level 2, with humans in the loop for Levels 3–4.
  10. When to use ML: (1) Intrinsically hard problems (language/vision), (2) Big problems (scale/deluge — manual rule maintenance becomes infeasible), (3) Time-changing problems (evolving fraud patterns). Prerequisite: the application must tolerate mistakes. Also consider the ML flywheel effect (data → better models → more users → more data) and cost-benefit analysis — simpler heuristics or semi-manual solutions may be better.
  11. Token Cost Model: Calculated based on Input + Context + Output tokens.
  12. GR for ML Views: Business View, Analytics Design View, Data Preparation View.
  13. Business View Notation: Actor (stick figure), Strategic Goal (ellipse), Decision Goal (ellipse with D), Question Goal (ellipse with Q), Insight (ellipse/box with I), and Indicator (box).
  14. Goal Interactions: Goals can Support (+, e.g., accuracy and user experience) or Conflict (−, e.g., accuracy vs. latency, cost vs. quality). Goal layering: Organizational → Product → User → Model goals — better model accuracy does not always translate to better business outcomes. Misalignment between layers is a common project failure mode.
  15. Human-AI Interaction Modes: Automate (full autonomy), Prompt (user confirmation), Organize/Annotate (information display with user deciding). Design choice depends on mistake cost, prediction confidence, and user accountability needs.

Q: In the MS Teams transcription example, which module is the ML component?

Explanation: Live transcription relies on a learned speech-to-text model. UI, auth, streaming, billing, and monitoring are conventional software components wrapping the ML core.

Q: GR for ML 'Business View' primarily captures:

Explanation: The business view documents why the system exists — goals like approve/reject credit decisions — and who interacts with it, before analytics and data-prep views refine how goals are met.

Q: A time-changing problem (e.g., drifting user preferences) motivates ML because:

Explanation: When distributions shift over time, learned models — combined with retraining and monitoring — can adapt where fixed rules cannot.
