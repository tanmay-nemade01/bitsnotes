It starts with video as a time-indexed volume and a small hand-worked 3D convolution, then counts parameters, operations, and memory for a real 16-frame network, then factorizes the 3D box into a spatial plus temporal pair, and ends with clip settings, hybrid practice, and what follows after features.

8.1 Review and the Question 3D Convolution Answers

8.1.1 Where This Session Sits

The question that runs this whole session is simple: after each single layer, what is the size of the filtered output. Not the final label, not the whole network, just the map that comes out of one layer. Every kernel shape, sliding rule, parameter count, and operation count hangs off that answer.

The previous session covered three kinds of features and how video work reuses image work. Spatial features describe what one frame looks like: edges, textures, and regions in a single still image. Temporal features describe what changes between frames: movement and flicker along the time axis. Spatio-temporal features describe both at once: where something is and how it moves, in one pass. That session also touched ImageNet pre-training, which means starting from weights learned on millions of still images, and transfer learning, which means reusing those weights on video instead of training from nothing. It introduced temporal segment networks, which split a long video into a few segments, sample one short snippet from each, run a shared image network on each snippet, and average the scores, so a long video gets one verdict without watching every frame. And it laid out the two broad paths for video work: convolutional stacks that read space and time as volumes, and recurrent stacks that read frames as a sequence, plus combinations of the two.

This session opens the first path fully. It asks what a 3D convolution does across space and time, how to count its outputs, parameters, and operations by hand, and how a factorized alternative reaches similar power with fewer weights.

The plan follows the teaching order of the session. First, video as a time-indexed volume and the kernel as a box that spans frames. Then a toy hand computation with real numbers and the output-size rule. Then the loop structure that code actually runs, plus the hardware picture that decides wall-clock time. Then what the joint spatio-temporal view buys: direction, speed, and its transfer limits. Then the cost math on a real 16-frame network: parameters, operations, and memory. Then the factorized split with its double nonlinearity and the middle-width derivation. Finally clip settings, hybrid practice with domain experts, what comes after features, and the exam plan.

Exam note: parts of this session appear on the weekend exam, including numerical questions on output size and parameter counts. Practice the size rule input minus kernel plus one and the parameter rule with bias until both are automatic, because those two lines earn marks directly.

The size-first habit pays off everywhere later. When a later layer surprises you with a tiny map or a huge bill, the cause is almost always one of three things: the kernel extent along one axis, the stride that skips placements, or the channel counts that multiply everything. Fix the per-layer map first and the rest of the network stops being a mystery.

8.2 Video as a Time-Indexed Volume and the 3D Kernel Box

8.2.1 Frames Indexed by Time

A one-minute phone clip at 30 frames per second is already 900 images. How do you name each one so that code, math, and hand counting all agree on which frame is which.

Think of a video as a flipbook with numbered pages. A frame is one still image at one time stamp, which is one page of the flipbook. A clip is a short run of consecutive frames processed in one go, for example 16 frames, which is a small handful of pages torn out and studied together. The time index, written \(T\), names each page. The session uses \(T = 0\) for the first frame, \(T = 1\) for the second, and so on up to a capital \(T\) for the last frame. Zero-based indexing like this matches most code loops, where an array of length \(N\) has valid positions \(0\) through \(N - 1\).

A frame count, written \(N\), is the total number of still images in the video, a plain integer. A frame rate is how many frames the camera records per second, written fps. The count follows one line of arithmetic: seconds times frames per second.

\[N = S \times R\]

Here \(S\) is the duration in seconds, for example \(S = 60\), and \(R\) is the frame rate in frames per second, for example \(R = 30\). The spoken example fixes the numbers:

\[N = 60 \times 30 = 900\]

So the clip holds 900 frames. Where indexing starts at \(T = 0\), the valid indices run \(T = 0, 1, \ldots, 899\), which is 900 frames with the last index \(N - 1 = 899\). Where indexing starts at 1, the last index equals the count \(N\).

Picture a number line from 0 to 899 with one tick per frame. The horizontal axis is the index \(T\) with no units, just position in sequence. Each tick holds a full image. The takeaway is that the line has 900 ticks but the rightmost tick is labeled 899, and every off-by-one bug in video code lives in that gap between count and last label.

Scope: the count formula assumes a fixed frame rate with no dropped frames. If the camera drops frames or the rate varies, \(S \times R\) overcounts and the true \(N\) must be read from the file header. The zero-based convention \(0\) to \(N - 1\) applies to the code and size formulas in this session; if you switch to one-based counting, shift every loop bound and every index by one.

The index convention matters twice. Code loops use it to decide the last legal position, and the output-size formula depends on where counting starts. Settle it before any sliding begins.

8.2.2 The Kernel as a Box Spanning Three Frames

A 2D kernel is a flat window that slides over height and width. A 3D kernel is a box that also spans time, so at any moment it looks at several frames together and then shifts forward. The session's verbal picture was a cube that always covers three consecutive frames and then moves to the next three: at one placement the box reads frame \(t\), frame \(t+1\), and frame \(t+2\) together, then it steps forward in time.

A 3D kernel is a small box of learnable weights with three extents: temporal depth \(K_t\), height \(K_h\), and width \(K_w\). A kernel described as \(3 \times 3 \times 3\) in \(T \times H \times W\) order has depth \(K_t = 3\) frames, height \(K_h = 3\) pixels, and width \(K_w = 3\) pixels. A kernel with a \(5 \times 5\) spatial window and depth 3 in time is \(3 \times 5 \times 5\) in that order. The same holds for \(7 \times 7 \times 3\).

The depth of three is the running example, not a law of nature. Kernels of temporal depth 3, 5, or 7 all exist, and larger depths watch longer motion at higher cost. The point the session stresses is that the temporal depth is always stated. A bare \(3 \times 3\) says nothing about time; a full \(3 \times 3 \times 3\) tells the whole story.

Picture the box as a small glass cube sunk into a stack of transparencies, each transparency one frame. The cube always encloses three sheets at once, so whatever pattern it detects must explain all three sheets jointly. Slide the cube one sheet forward and it encloses a shifted triple. That joint enclosure is the whole selling point: the temporal axis carries the motion while the spatial axes carry position, edges, and texture, and one pass picks up both together.

Assumption: the box sees a local window in all three axes at once, so it can only model motion that fits inside its depth. A depth-3 kernel sees change across three frames, which at 30 fps is about a tenth of a second. Faster or longer gestures need either deeper kernels, stacked layers, or wider sampling, because a single shallow box simply never observes them.

8.2.3 Input Order and How Code States Shapes

The board order in the session was width, height, and total time span, which is how a person might describe a screen. The computation order flips it to time by height by width, written \(T \times H \times W\), where \(T\) is the number of frames in the clip, \(H\) is frame height in pixels, and \(W\) is frame width in pixels. The reason given is that the operation runs better in that layout: consecutive time steps sit next to each other in memory, so the sliding box streams through them cleanly.

The same flip applies to kernels. A 3D convolution layer is requested as a three-dimensional tensor, for example through a Conv3D-style layer call, with all three extents stated. In \(T \times H \times W\) order a \(3 \times 3\) spatial kernel of depth 3 is \(3 \times 3 \times 3\). A \(5 \times 5\) spatial kernel of depth 3 is \(3 \times 5 \times 5\) in that order. Forgetting the third extent is the common setup error: the layer needs height, width, and depth every time, and a 2D-shaped request will either fail or silently build the wrong operation.

Two traps catch beginners here. First, mixing the board order with the code order, so a \(5 \times 5 \times 3\) described on the board becomes a wrongly shaped tensor in code; always convert to \(T \times H \times W\) before calling the layer. Second, stating only the spatial window and letting the depth default to something unintended; write all three numbers every time and check the printed layer shape before training.

In practice, frameworks add two more axes around this core: a batch axis \(B\) for how many clips run together and a channel axis \(C\) for color or feature maps, giving shapes like \(B \times C \times T \times H \times W\). The session works with the \(T \times H \times W\) core and brings \(C\) back when counting parameters, which keeps the hand math clean without hiding the real tensor.

8.2.4 Twenty-Seven Weights per Kernel

A \(3 \times 3\) 2D kernel holds 9 learnable weights. A \(3 \times 3 \times 3\) 3D kernel holds 27 learnable weights, one per cell of the box. The verbal statement was that against 9 weights in 2D, each 3D kernel adds 27 weights:

A weight count per kernel, written \(P_{kernel}\), is the number of learnable numbers inside one box, an integer. For a box of depth \(K_t\), height \(K_h\), and width \(K_w\):

\[P_{kernel} = K_t \times K_h \times K_w\]

For the running example with \(K_t = 3\), \(K_h = 3\), \(K_w = 3\):

\[P_{kernel} = 3 \times 3 \times 3 = 27\]

Each of the 27 cells holds one number that training will tune. The number of layers and the number of kernels per layer stay as design choices, exactly as in 2D work.

To feel the scale, compare three boxes side by side. A \(3 \times 3\) flat window holds 9 weights, about the digits of a phone keypad. A \(3 \times 3 \times 3\) cube holds 27, about the letters of the alphabet. A \(5 \times 5 \times 3\) slab holds 75. Every kernel now costs about three times its 2D twin, and that factor compounds across layers and channels, which is why the session keeps returning to infrastructure, memory, and the factorization idea later.

Sports broadcast analysis uses exactly this joint box: one pass reads the positions of players and the direction they sprint, because the box sees the pitch layout and the frame-to-frame shift together. A per-frame detector alone would report dots; the box reports runs.

A video is a time-indexed stack of frames, the 3D kernel is a box that always spans several frames at once, shapes are stated in \(T \times H \times W\) order with all three extents, and one \(3 \times 3 \times 3\) box costs 27 weights. With that picture fixed, the next step is to slide the box by hand and watch one output number being born.

8.2.5 Student Questions and Answers

Q: Why is the last index 899 when the video has 900 frames?

A: A one-minute video at 60 seconds times 30 frames per second gives 900 frames in total, from \(N = 60 \times 30 = 900\). Indexing starts at \(T = 0\), so the indices run 0 to 899. The maximum index is one less than the count because the first frame takes index 0. If counting started at 1, the last index would be 900, but every loop bound and every size formula in this session assumes the zero-based form.

8.3 Worked 3D Convolution: Numbers, Sliding, and Output Size

8.3.1 The Toy Setup

Formulas feel abstract until you multiply real numbers by hand. This toy is small enough to hold in your head: three frames, one box, one output number at a time.

Think of the box as a cookie cutter pressed into a three-layer sandwich. Each layer is one frame, the cutter covers a \(3 \times 3\) patch on every layer at once, and the number stamped out depends on all three layers jointly. Lift the cutter, shift it one notch, press again: that is the next output number.

The worked example fixes every size. In \(T \times H \times W\) order the input volume is \(3 \times 4 \times 4\): temporal extent \(T_{in} = 3\) frames, height \(H_{in} = 4\) rows, width \(W_{in} = 4\) columns. The kernel is \(3 \times 3 \times 3\): depth \(K_t = 3\), height \(K_h = 3\), width \(K_w = 3\). Stride is 1 along every axis, with no padding, so the box shifts by exactly one pixel or one frame between placements.

The concrete numbers are chosen for mental math. The frame at \(T = 0\) was read out row by row as 2, 1, 0, 3 on the first row, 1, 3, 2, 1 on the second, 0, 2, 1, 0 on the third, and 1, 0, 3, 2 on the fourth. The kernel slice at \(T = 0\) uses the simple pattern with rows 1, 0, minus 1, then 0, 1, 0, then 1, 0, 1, chosen so that many products vanish. The frames at \(T = 1\) and \(T = 2\) carry their own numbers, including rows such as 3, 0, 0, 0 and 0, 2, 2, 2 at \(T = 1\), and the \(T = 2\) patch starting 1, 0, 2, 1 on its top rows. Zeros were placed on purpose so the element-wise products stay tractable by hand: wherever either the pixel or the weight is zero, the product dies immediately.

Picture the stack from the side: three \(4 \times 4\) sheets piled vertically with the \(3 \times 3 \times 3\) cube sitting in the top-left corner, covering rows 0 to 2 and columns 0 to 2 on all three sheets. The horizontal axes are pixel columns and rows; the vertical axis is time. The takeaway is that the cube never sees a single sheet alone, so every number it stamps out is joint evidence.

8.3.2 Mathematical Formulation

A convolution here means element-wise multiply followed by a sum. A stride is how far the box moves between placements; stride 1 means it shifts by one pixel or one frame at a time. The verbal rule was element-wise product, then take the sum, at each time step, then add the time steps. In other words: collapse each frame slice to a subtotal first, then collapse the subtotals across time into one number.

For one output position, let \(y\) be the single output number at one box placement, a scalar. Let \(b\) be the scalar bias for the filter, one learned number added at the end. Let \(x\) be the input pixel under the box, a scalar intensity, and \(k\) the kernel weight at the same offset, a scalar. Let \(dt\), \(dh\), \(dw\) be offsets running over the kernel depth, height, and width. The compact form is:

\[y = b + \sum_{dt} \sum_{dh} \sum_{dw} x \times k\]

The triple sum first collapses each frame slice, then the per-frame subtotals collapse across time into the one number \(y\).

With indices on the full map, the same operation names every position. Let \(y[t, h, w]\) be the output map value at clip position \(t\) and spatial position \((h, w)\). Let the input \(x\) have shape \(T_{in} \times H_{in} \times W_{in}\) with integer extents, and the kernel \(k\) shape \(K_t \times K_h \times K_w\). Let \(b \in \mathbb{R}\) be one scalar bias per filter. With stride 1 and no padding:

\[y[t, h, w] = b + \sum_{dt=0}^{K_t-1} \sum_{dh=0}^{K_h-1} \sum_{dw=0}^{K_w-1} x[t+dt, h+dh, w+dw] \times k[dt, dh, dw]\]

Every symbol is now pinned down: \(t, h, w\) locate the box corner in the input, \(dt, dh, dw\) walk inside the box, and the sums run over exactly the kernel extents \(K_t\), \(K_h\), \(K_w\). The bias \(b\) shifts the sum by one learned constant per filter; the toy works with \(b = 0\) so the arithmetic stays visible.

Compare the two forms directly. The compact form shows the mechanism in one glance: multiply, sum over the box, add bias. The indexed form shows where the box sits and which pixels enter. They are the same computation; the second just labels every seat. When the compact product \(x \times k\) is written, it means the indexed product \(x[t+dt, h+dh, w+dw] \times k[dt, dh, dw]\) at each offset, summed over all offsets.

Scope: both forms above assume stride 1 and no padding. With stride \(S > 1\), the input index becomes \(t \times S + dt\) rather than \(t + dt\), and placements skip ahead. With padding \(P\), the input is first bordered with \(P\) zeros per side, which changes the output size. The toy uses the simplest setting so the counting stays clean.

8.3.3 Step-by-Step Arithmetic at Position Zero-Zero

Place the box at the top-left corner of the three frames, covering rows 0 to 2 and columns 0 to 2 on each slice, with bias \(b = 0\). Work slice by slice.

Step 1, slice \(T = 0\). Multiply the \(3 \times 3\) input patch element-wise by the \(3 \times 3\) kernel slice and add the nine products. Most products vanish because either the pixel or the weight is zero. The live entries survive, and the session's trace reads two times one plus the rest zeros, giving a slice subtotal of 6.

Step 2, slice \(T = 1\). Repeat on the second frame's top-left patch with the second kernel slice. Its own live entries give a slice subtotal of 5.

Step 3, slice \(T = 2\). Repeat on the third frame's patch, the one starting 1, 0, 2, 1, with the third kernel slice. Call its subtotal \(s_2\).

Step 4, collapse across time. Add bias plus the three subtotals:

\[y[0, 0, 0] = b + 6 + 5 + s_2\]

With \(b = 0\) this is \(11 + s_2\). The session states the collapse as 11 from the completed slices at that point in the walk-through, with the third slice still being added in the live drawing, which matches \(6 + 5 = 11\) before \(s_2\) joins. The final output number is therefore \(11 + s_2\), one scalar at map position \((t, h, w) = (0, 0, 0)\).

Sense-check: each slice contributes at most 9 products of small integers, so a total in the low tens is the right size. A result in the hundreds would signal a misplaced patch or a forgotten zero.

A student catch during the walk-through corrected which frame patch belongs to \(T = 2\), distinguishing the 1, 0, 2, 1 patch from a neighboring row. The fix changed which numbers enter the products, which is exactly why the session insists on labeling every slice with its time index before multiplying. Time labels are not bookkeeping decoration; they decide the answer.

Three traps recur in hand work. First, multiplying a neighboring row by mistake, which is what the student catch above fixed; label the slice and the rows before touching numbers. Second, forgetting that zeros kill products, then adding phantom terms; cross out every product with a zero factor first. Third, dropping the bias or double-counting it; there is exactly one \(b\) per filter per placement, added once after all products.

8.3.4 Output Size Formula

The verbal rule was that output size along each axis is input minus kernel plus one. Let \(O\) be the output extent, \(I\) the input extent, and \(K\) the kernel extent along the same axis, with stride 1 and no padding:

An output extent, written \(O\), is how many box placements fit along one axis, an integer. With input extent \(I\) and kernel extent \(K\) on that axis:

\[O = I - K + 1\]

The logic is positional: the box corner can start at positions \(0\) through \(I - K\), which is \(I - K + 1\) distinct starts. Applied to all three axes of the toy:

\[O_T \times O_H \times O_W = (3 - 3 + 1) \times (4 - 3 + 1) \times (4 - 3 + 1) = 1 \times 2 \times 2\]

Here \(O_T = 1\) is the single temporal slot, while \(O_H = 2\) and \(O_W = 2\) are the two rows and two columns of placements. That is why the drawn feature map is \(1 \times 2 \times 2\): one collapsed time slot holding a \(2 \times 2\) spatial map.

The four spatial placements are concrete: the top-left patch just computed, the top-right patch shifted one column, and the two bottom patches shifted one row down. Stride 1 is what makes each shift exactly one pixel; stride 2 would halve the placements.

Picture the output as a single thin tray holding a \(2 \times 2\) grid. The horizontal axes of the drawing are output columns and rows; there is only one tray because the three input frames collapse to one temporal slot. The takeaway: time collapsed from 3 to 1 while space shrank from \(4 \times 4\) to \(2 \times 2\).

So the box has not yet touched the fourth frame of a four-frame input at this stage. The first output number consumes frames 0, 1, 2. Sliding the box one frame forward consumes frames 1, 2, 3 and yields the next temporal output. That sliding continues to the end of the clip, producing one output per window.

Checkout counters use the same rule: a scanner window of width \(K\) sliding over \(I\) items with step 1 reads \(I - K + 1\) distinct windows. Video convolution is that counter running in three axes at once.

One placement means element-wise multiply, sum within each slice, sum across slices, add one bias. The map size follows \(O = I - K + 1\) per axis, giving \(1 \times 2 \times 2\) here. With the toy fully worked, the next step is to see the loops that repeat this placement thousands of times and the hardware that decides how long that takes.

Exam note: output-size arithmetic of the form input minus kernel plus one is a likely numerical item. Write the per-axis line first, then substitute, then state the triple. Even a bare correct equation earns partial credit, so never skip writing it.

8.3.5 Student Questions and Answers

Q: The original input has four frames, so why does the output map show only one time slot?

A: The box has not slid into the later frames yet. The \(1 \times 2 \times 2\) map comes from the first three frames only, since \(O_T = 3 - 3 + 1 = 1\). Moving the box one frame forward brings in the fourth frame and produces the next temporal output. The drawn map is a snapshot after the first placement, not the final map after the full sweep.

Q: Which numbers belong to the frame at \(T = 2\) in the hand computation?

A: The patch starting 1, 0, 2, 1 belongs to \(T = 2\). Multiplying a neighboring row by mistake changes the slice subtotal and therefore the collapsed output, so each slice must be labeled with its time index before the element-wise products are formed. When in doubt, re-read the row labels rather than trusting memory of the drawing order.

8.4 Loop Structure, Answer-Script Analogy, and Parallel Hardware

8.4.1 The Nested Loops

The toy computed one number. A real clip needs thousands. What repeats the toy placement over the whole volume without missing a slot or double-counting one.

Think of mowing a lawn in three directions at once: walk along the length, and at each step mow a small patch by sweeping across its width and depth. The outer walk visits every placement; the inner sweep finishes one placement. Miss a row of the walk and a strip stays uncut; that is a skipped output position.

The purpose of the loop nest is to visit every output position once and, at each, accumulate the full kernel sum. The inputs are the clip volume of shape \(T_{in} \times H_{in} \times W_{in}\), the kernel of shape \(K_t \times K_h \times K_w\), the stride, and the bias \(b\). The output is the map of shape \(O_T \times O_H \times O_W\) from the size rule. The steps are two loop groups. Outer loops walk the output positions: over clip time \(t\), over output height \(h\), and over output width \(w\), each advancing by the stride. Inner loops walk the kernel: over depth \(dt\), height \(dh\), and width \(dw\), accumulating with a running sum of the form sum plus equals input times weight. In words: pick a small segment in each of the three frames, sweep that segment across time, finish one output number, then shift the whole box and repeat.

A minimal trace on the toy makes the order concrete. Outer position \((t, h, w) = (0, 0, 0)\): inner loops run \(dt = 0, 1, 2\), \(dh = 0, 1, 2\), \(dw = 0, 1, 2\), forming 27 products and their sum plus bias. Then the outer loops advance to \((0, 0, 1)\), the top-right patch, and the 27-product accumulation restarts. Then \((0, 1, 0)\) and \((0, 1, 1)\). Four placements, four output numbers, each built from its own 27 products. The arithmetic inside stays simple multiply-and-add throughout.

The loop count grows with kernel dimensionality. Each extra kernel axis adds another inner loop and multiplies the additions and multiplications. Going from a 2D window to a 3D box adds the whole \(dt\) loop, roughly tripling the inner work per placement before channels enter. The inner body never gets smarter; the iteration volume is what makes video convolution heavy.

8.4.2 The Answer-Script and Hall Analogies

Two extended analogies carry the batching idea, and both are kept because each lands a different half of it.

In the first, the full stack of answer scripts is the input, and one question at a time is the kernel. Checking five scripts per round for one question is one box placement: a fixed batch of items under one fixed probe. Finishing all fifty scripts takes ten rounds for that question. Then the checker moves to the next question, which is the next kernel: the probe changes, the stack stays. Each kernel minds only its own aspect, and one checker finally consolidates, which matches the later pooling and fully connected stages that merge per-filter evidence into one verdict.

In the second, many small tables are pushed together into one long hall table, scripts laid open in a row. One person checks the cover page and flips, the next checks question one down the whole row, then the question-two checker walks the same row. The table length sets how many scripts finish in one round. The analogy lands the same point from the hardware side: batching one operation across many items beats handling items one by one, but the batch width is set by physical capacity, not by wishful thinking.

Batching means applying the same operation to many items in one round instead of looping items one by one. The batch width is how many items one round covers. In the hall, the table length sets it. In code, memory and parallel units set it. Wider batches finish in fewer rounds, but only up to the physical ceiling.

Picture the hall from above: a long table as a horizontal bar, scripts as ticks along it, checkers as arrows walking the rows. The horizontal axis is items per round; the vertical axis is rounds to finish. Lengthen the table and the arrows finish in fewer passes. The takeaway is that throughput is a property of the table, not of any single checker working harder.

Consider a concrete walkthrough of the answer-script and hall batching setup with 50 total answer scripts evaluated across 10 exam questions (kernels).

Step 1, batching per question: The hall table accommodates 5 scripts simultaneously in one pass, representing a batch width of 5 scripts per placement. Finishing all 50 scripts for Question 1 requires: \[\text{Rounds} = \frac{50}{5} = \mathbf{10}\] ten successive rounds under the first question's rubric.

Step 2, total sequential passes: Across all 10 distinct questions, evaluating the entire stack sequentially requires: \[10 \times 10 = \mathbf{100}\] one hundred total rounds if executed by a single checker.

Step 3, parallel checker scaling: Introducing 4 parallel checkers (analogous to 4 GPU cores) allows 4 questions or placements to evaluate concurrently. The 10 questions now finish in: \[\lceil \frac{10}{4} \rceil \times 10 = 3 \times 10 = \mathbf{30}\] thirty parallel rounds instead of 100 rounds.

Sense-check: Upgrading to 8 parallel checkers reduces the question passes from 3 to 2, completing all scripts in 20 rounds without altering the underlying 100-check workload.

8.4.3 Hardware, GPUs, and Resource Ceilings

A graphics processor helps because each parallel unit behaves like one more checker in the hall. With eight units, eight kernels or eight placements can move at once. With only four units and ten questions, the early checkers must loop back and take later questions, so the work needs more rounds. Kernel count, placement count, and unit count jointly set the round count, which is why the session flags a conceptual exam question linking the three: resource limits decide wall-clock time as much as raw operation counts do.

Scope: parallelism speeds up the rounds but does not shrink the arithmetic. Eight checkers finish ten questions faster than four, yet the total checking work is identical. Likewise, GPUs cut time, not flops: the operation count from the cost section stays fixed no matter how many units share it. Budget time from units and rounds, and budget energy and heat from total operations.

The same ceiling logic governs memory, and the session warns that three different footprints can each run out on their own. Loading videos means holding decoded clips in memory. Holding the model means storing all weights. Keeping working memory means storing intermediate maps and gradients during training. Any one of the three can overflow before compute becomes the limit, and long clips inflate all three at once. Even inference, not just training, can run longer than expected on long inputs, because every extra frame multiplies placements, storage, and movement of data. Planning must budget both time and space.

Cloud GPU rental is the concrete instance students meet first: renting eight parallel units halves neither the bill nor the memory need automatically, because the provider charges for unit-hours and gigabyte-hours separately. Count rounds for time and bytes for memory, then rent to cover the larger of the two bottlenecks.

Outer loops visit every output position; inner loops finish one placement with multiply-and-add; batching covers many items per round up to a physical ceiling; parallel units cut rounds but not total work; and memory for videos, weights, and working space can each overflow independently. With the execution picture fixed, the next step is what all that execution buys: direction, speed, and joint features in one pass.

Exam note: expect a conceptual question linking kernel count to parallel units and rounds, since resource limits decide wall-clock time as much as operation counts do. Answer with the three numbers: work per placement, placements per round from unit count, rounds to finish.

8.4.4 Student Questions and Answers

Q: Does one kernel sweep the whole video or only a few frames at first?

A: The same kernel sweeps the whole duration. Each placement still covers only a few frames, typically three, but the outer time loop advances the box across the full clip, so every frame eventually passes under it. In code the time loop ends at the last frame of the video, so there is no physical table-length limit. The hall table has a physical limit, but the loop over frames does not. The limit that remains is memory and time, not reach.

Q: What does the collapsed output number represent, motion or appearance?

A: It is neither alone. The collapse fuses both, because the box multiplied spatial pattern weights and temporal change weights into one sum. The number therefore carries joint spatio-temporal evidence rather than a pure motion vector or a pure appearance score. Reading motion alone or appearance alone out of one collapsed number is the category error to avoid; later layers and later stages disentangle what this number fused.

8.5 One-Go Spatio-Temporal Features, Direction, Speed, and Transfer Limits

8.5.1 Capturing Movement and Position Together

A detector that sees frames one by one can say where a ball is in each photo. It cannot say which way the ball flies or how fast. What changes when the box watches three frames at once.

The cartoon used in the session is a hole with a character that moves between frames. A 2D pass reports positions frame by frame: far apart, then near, then near again. Each report is a dot on a map with no arrow. A 3D pass reports the positions plus how they change: direction, speed, and with depth, acceleration. The verbal claim was that the movement is captured and the static hole position is captured in the same pass. After each stage the three input frames collapse into one map, yet that map keeps temporal evidence about change, which is why smaller kernels catch finer detail: a compact box notices small shifts that a wide box would blur over.

A spatio-temporal feature is one number or vector that encodes where something is and how it moves, jointly. Direction uses sign: motion one way counts as positive and the opposite way as negative, on both the horizontal and vertical axes. Speed comes from how far the evidence shifts per frame: a large displacement between consecutive frames means fast, a small one means slow. Acceleration emerges across stacked layers, because layer two reads change-of-change from layer one's maps rather than from raw pixels.

A concrete pass makes the signs real. Suppose the character's horizontal center sits at columns 1, 3, and 4 across three frames. The frame-to-frame shifts are \(+2\) then \(+1\): positive, so rightward, and shrinking, so slowing. A vertical sequence of rows 5, 5, 2 gives shifts \(0\) then \(-3\): still, then sharply upward if up means decreasing row index. One layer reports these local shifts; it does not yet name the gesture.

Picture a position-against-time plot: the horizontal axis is frame index \(t\), the vertical axis is pixel column. A still object draws a flat line. Steady motion draws a straight slope, whose tilt is speed and whose rising or falling direction is sign. Bending in the line is acceleration. The takeaway is that the 3D map stores slopes and bends, not just dots, which is why collapsing three frames to one never meant throwing time away.

Traffic cameras use exactly this joint reading: one pass reports that a car sits in lane two and drifts leftward at a growing rate, which is position plus direction plus acceleration in a single verdict. A per-frame detector would need a separate tracker to recover the same story.

Scope: one layer's claim is modest, only local change over about three frames. Fine flicker inside a single frame gap is invisible if sampling skips it, and motion far larger than the kernel window aliases into confusing evidence. The joint view is powerful within its window and blind outside it; longer stories need stacks, wider sampling, or explicit tracking.

8.5.2 Depth Buys Dynamics

One layer sees a twitch; a stack sees a gesture. Layer one maps feed layer two, which feeds layer three, so deeper stages see longer-range quickening or slowing: layer one reports frame-to-frame shifts, layer two compares those shifts and reports speeding up or slowing down, layer three compares over still longer spans. The session stresses that this only works because every stage preserves the temporal axis until an explicit collapse or pooling step removes it. Pool away time too early and the deeper layers receive still images with no motion left to compare.

Compare the two failure modes directly. Collapse time at the first layer and the network becomes a bag of per-frame snapshots: great at textures, blind to rhythm. Preserve time through several layers and collapse only before classification, and the network spends its depth budget on dynamics: rhythm, tempo change, and direction reversal all remain visible. When to pick which is therefore a question about the task: still-scene labeling tolerates early collapse, while action, dance, or driving behavior demands late collapse.

Two pitfalls follow. First, assuming deeper always means better dynamics; depth without temporal preservation just builds a deeper still-image network. Second, reading acceleration out of a single layer; one shallow box reports velocity-scale change at best, and true change-of-change needs at least two stages of temporal evidence.

8.5.3 Transfer Across Domains

Q: Can 3D kernels trained on one video task be reused for another task the way 2D image weights are reused?

A: It transfers when the domains stay close, and it breaks when they do not. A network trained on car motion may carry over to train motion, because both show vehicle-like translation at related speeds: rigid bodies sliding along a heading with smooth tempo. The same weights may fail on dance with spins in place, or on animal motion versus vehicle motion, because the movement vocabulary differs. Judge closeness of the motion domains before assuming reuse, with full transfer discussion reserved for the upcoming module. Several students pressed variants of this reuse question, so this merged entry is the canonical answer.

The dance counterexample is concrete. Left-right steps share something with walking, so a translation-trained kernel finds familiar slopes. But spinning round and round at one spot has no counterpart in a translation-only source task: position barely moves while orientation whips around, so the learned direction and speed cues do not map. Animal-versus-vehicle motion raises the same doubt even though both involve movement: bounding gaits, wing beats, and wheel rolling trace different slope families on the position-time plot. Shared motion is not enough; the pattern of motion must match.

Think of it as accents, not just language. Two domains can both speak translation yet carry different accents of tempo, rhythm, and articulation. A kernel fluent in highway translation stutters in dance spin, just as a listener fluent in one accent strains at another. Match the accent before transferring.

One 3D pass fuses position with direction and speed, stacks turn local shifts into longer dynamics only while the temporal axis survives, and reuse across domains holds only where the motion vocabulary matches. With the power and its boundary clear, the next step is the bill: parameters, operations, and memory on a real network.

8.6 Parameter, FLOP, Memory, and Compute Cost of 3D Convolution

8.6.1 The First 3D Network Shape

The toy used one kernel. A real network stacks dozens of them over 16 frames. What does that stack look like, and why does everyone warn about its appetite.

The early 3D network discussed takes 16 frames of \(112 \times 112\) pixels in one go, written \(16 \times 112 \times 112\) in \(T \times H \times W\) order, then applies successive 3D convolution layers with 64, 128, and 256 kernels, ending in fully connected layers that emit class scores. The verbal summary was sixteen frames in, successive 3D layers with 64 up, then classification out. The shape above omits the channel axis; with color the leading channel count \(C_{in} = 3\) returns, giving a full input of \(3 \times 16 \times 112 \times 112\) in \(C \times T \times H \times W\) order.

The headline is parameter growth. Holding the spatial window at \(3 \times 3\), the 3D form carries 27 weights per input channel against 9 in 2D, so the count roughly triples before channels and filter counts even enter. This fused stack is widely called C3D, the canonical early 3D convolutional network for clips. That triple-then-multiply effect is why training from scratch demands serious infrastructure and why transfer learning becomes the motivating question: few labs can afford to learn tens of millions of video weights from nothing.

Picture the network as a funnel lying on its side. The wide mouth swallows a \(16 \times 112 \times 112\) block. Each 3D stage squeezes space and time while thickening the channel count from 64 toward 256, and the final fully connected neck squeezes everything to a short score vector. The horizontal axis is depth through the network; the vertical thickness is channels. The takeaway is that every stage of the funnel pays the tripled per-kernel price, so the bill compounds downward.

8.6.2 Mathematical Formulation of Parameters

Let \(C_{in}\) be the input channel count, a positive integer, and \(C_{out}\) the number of filters, also a positive integer. Let \(K_t\), \(K_h\), \(K_w\) be the kernel depth, height, and width. The verbal rule was channels times kernel volume per filter, times filter count, plus one bias per filter:

A layer parameter count, written \(P\), is the total learnable numbers in one convolution layer, an integer. Each of the \(C_{out}\) filters sees all \(C_{in}\) input channels through a \(K_t \times K_h \times K_w\) box, plus one bias:

\[P = C_{out} \times C_{in} \times K_t \times K_h \times K_w + C_{out}\]

The product \(C_{in} \times K_t \times K_h \times K_w\) is the weight count feeding one filter. Multiplying by \(C_{out}\) covers all filters. The trailing \(C_{out}\) adds one scalar bias per filter.

The worked instance sets \(C_{in} = 3\) color channels, clip \(16 \times 112 \times 112\), kernel \(3 \times 3 \times 3\), and \(C_{out} = 64\):

Substitute step by step. Weights per filter: \(C_{in} \times K_t \times K_h \times K_w = 3 \times 3 \times 3 \times 3 = 81\). All filters: \(64 \times 81 = 5184\) weights. Biases: one per filter, \(64\). Total:

\[P = 64 \times 3 \times 3 \times 3 \times 3 + 64 = 5184 + 64 = 5248\]

Each filter sees \(3 \times 27 = 81\) weights, times 64 filters gives 5184 weights, plus 64 biases gives 5248 parameters. A live slip first said 5284, then the room corrected it to 5248, which is kept here as the checked value. The correction itself is the lesson: always separate the weight product from the bias tail before adding, because the two terms confuse easily under time pressure.

Sense-check: 64 filters times roughly 80 weights each is roughly 5000, so 5248 lands in the right neighborhood. A total near 500 would mean a dropped channel factor; near 50000 would mean an extra zero.

Color inputs multiply the count by their 3 channels from the start, so the same layer on gray versus color differs by that factor before anything else changes. A gray-input twin of this layer would cost \(64 \times 1 \times 27 + 64 = 1792\), about a third. Channels are the quiet multiplier students forget most often.

8.6.3 Floating-Point Operations

Parameters count storage. Operations count work. The verbal rule was this many multiplications plus this many additions per output position, plus one bias addition. For one filter at one output position:

An operation count per position per filter, written \(F\), is the floating-point work to produce one output number from one filter, an integer. Each of the \(C_{in} \times K_t \times K_h \times K_w\) weights needs one multiplication and one addition, and the bias needs one final addition:

\[F = 2 \times C_{in} \times K_t \times K_h \times K_w + 1\]

The factor 2 counts one multiplication and one addition per weight. The trailing 1 is the single bias addition. With \(C_{out}\) filters, multiply by \(C_{out}\). With many output positions, multiply again by the output volume \(O_T \times O_H \times O_W\). That double multiplication is why the operation total climbs far faster than the parameter total when clips get longer or frames get larger.

Make it concrete on the running layer. Per position per filter: \(2 \times 3 \times 27 + 1 = 163\) operations. Times 64 filters: \(163 \times 64 = 10432\) operations per output position. Times every position in a \(16 \times 112 \times 112\)-derived output volume, and the total runs into the hundreds of millions for a single layer on a single clip. Parameters told you the suitcase weighs 5248 numbers; operations tell you the trip costs hundreds of millions of steps.

Assumption: the operation rule counts multiply-add pairs plus bias with stride 1 and no fused tricks. It ignores activation functions, pooling, normalization, and memory traffic, and hardware fusion can merge some steps. Treat \(F\) as the arithmetic floor for comparing architectures, not as a wall-clock prediction; time needs the unit-and-round analysis from the hardware section alongside it.

8.6.4 The Holistic View and Its Price

The session borrows a medicine comparison. Treating isolated organs one by one misses interactions, while a whole-person view weighs everything together. Likewise, separate edge, texture, and motion-vector stages miss joint structure that a single 3D pass sees at once: the way a texture moves is itself the clue, and no isolated stage owns it. The fused box is the whole-person doctor of video features.

But the whole-person visit costs more. The verbal warning was not only flops, also the memory footprint to load videos, hold the model, and keep working memory. Three bills arrive together: arithmetic operations, storage for weights and maps, and data movement between them. Even inference, not just training, can run longer than expected on long inputs, because every extra frame multiplies placements, storage, and movement of data. Planning must budget both time and space, and the memory warning is kept here as an essential manifest item because students routinely budget only the first.

A traffic control room makes the tradeoff tangible. A per-camera still-image detector plus a separate speed estimator is the organ-by-organ clinic: cheap, but blind to joint events like a vehicle swerving while braking. A fused 3D stack on the clip is the whole-person visit: it sees the swerve-brake Gestalt in one pass, yet needs the room's server, not a laptop, to hold 16 high-resolution frames and their maps at once.

A \(3 \times 3 \times 3\) layer with 3 input channels and 64 filters costs 5248 parameters, each output number costs \(2 \times C_{in} \times K_t \times K_h \times K_w + 1\) operations before the filter and position multipliers, and memory for videos, weights, and working space can each overflow on its own. With the bill itemized, the next step is the discount: splitting the box while keeping the joint power.

8.6.5 Student Questions and Answers

Q: With color channels, do we multiply the parameter count by three up front?

A: Yes. The per-filter weight count starts from \(C_{in}\) times kernel volume, so three color channels triple the weights against a single-channel input before filter count or bias enters. For the running layer that is \(3 \times 27 = 81\) weights per filter rather than 27. Forgetting \(C_{in}\) is the most common undercount in exam arithmetic.

8.7 Factorized R(2+1)D: Split, Double Nonlinearity, and the Intermediate Width M

8.7.1 Why Factorize

By 2015 to 2016 the tripled parameters, operations, and memory of full 3D convolution already hurt on period hardware. Could the same holistic power cost less.

The verbal goal was same spatio-temporal power with fewer parameters through an intermediate step. The answer is factorization: replace one \(3 \times 3 \times 3\) step with a 2D spatial step followed by a 1D temporal step, with a nonlinearity after each. This split form is called R(2+1)D: a 2D spatial convolution plus a 1D temporal convolution replacing one 3D convolution. The R marks a residual-style video block family; the (2+1)D marks the two-plus-one split.

The intermediate map is the hinge. The same input enters, a 2D convolution produces an in-between result that already encodes spatial structure per frame, and a 1D convolution over time turns it into the final map, which speaks in similar terms to the full-3D map. The factorization keeps the joint view while splitting the volume product into a sum of two smaller products: instead of paying depth times height times width at once, it pays height times width plus depth in sequence.

Factorization here means replacing one \(K_t \times K_h \times K_w\) convolution with a spatial convolution of shape \(1 \times K_h \times K_w\) followed by a temporal convolution of shape \(K_t \times 1 \times 1\), with a rectified linear unit after each step. The spatial step reads appearance within frames; the temporal step reads change across the middle maps. An intermediate channel count, written \(M\), is the number of maps between the two steps. It is a design setting, not a learned weight, and choosing it is the core of the derivation below.

Compare the two routes side by side. The fused route runs one heavy convolution then one nonlinearity: one bend in the function. The split route runs a light spatial convolution, a first nonlinearity, a light temporal convolution, then a second nonlinearity: two bends. The split keeps the joint view because the temporal step still mixes frames, but it mixes compact middle maps rather than raw pixels, which is where the saving comes from.

8.7.2 Parameter Math of the Split

The verbal split was 2D with 3 by 3 by 1 is 9 parameters, then 1D with 1 by 1 by 3 is 3 parameters, totaling 12 against 27. In \(T \times H \times W\) order the spatial step is \(1 \times 3 \times 3\) and the temporal step is \(3 \times 1 \times 1\):

A split weight count per channel, written \(P_{split}\), is the factorized pair's weights before channels and filter counts enter:

\[P_{split} = 9 + 3 = 12\]

Here 9 is the \(3 \times 3\) spatial window and 3 is the length-3 temporal window, against 27 for the fused box. The saving is more than half per channel, before channels and filter counts enter.

The extra win is expressiveness, and this is the point students underrate. The fused path applies one rectified linear unit, written \(\mathrm{ReLU}\), after its single convolution. The split path applies one \(\mathrm{ReLU}\) after the 2D step and another after the 1D step. A rectified linear unit keeps positive inputs and maps negatives to zero, which carves bends into the learned function. Two nonlinearities carve more bends than one, so the pair can express patterns the single step cannot, which is why the factorized form sometimes beats the fused form rather than merely matching it. Fewer weights plus more bends is the rare free lunch, paid for only by tuning the middle width.

Picture bending a wire. One bend makes an angle; two bends make a zigzag that can trace shapes one bend never could. The horizontal axis of the sketch is the input value, the vertical axis the output; each \(\mathrm{ReLU}\) adds one kink. The takeaway is that the split's second kink is representational power the fused form lacks at any parameter count.

Scope: the 9-against-27 comparison is per input channel with one middle map. Real layers multiply by \(C_{in}\), \(C_{out}\), and the middle width \(M\), which can shrink or erase the headline saving if \(M\) is set too large. The per-channel count motivates the split; the full counts with \(M\) below decide whether it actually saves.

8.7.3 Worked Derivation of the Intermediate Width

Fix the input as \(C_{in} = 3\) channels, \(T = 16\) frames, \(H = 112\), \(W = 112\), written \(3 \times 16 \times 112 \times 112\) in \(C \times T \times H \times W\) order, with target \(C_{out} = 64\) and kernel \(3 \times 3 \times 3\). The fused count from the prior section is \(P = 5248\). The question is how wide the middle can be before the pair costs as much as the fused box.

For the split, let the middle hold \(M\) channels. The 2D stage count follows the same parameter rule with the spatial kernel only. Let \(K_h = 3\) and \(K_w = 3\) be the spatial extents:

\[P_{2D} = M \times C_{in} \times K_h \times K_w + M = M \times 3 \times 3 \times 3 + M = 28 \times M\]

Here \(P_{2D}\) is the spatial-stage parameter count. The \(27M\) term is weights and the trailing \(M\) is one bias per middle map.

The 1D stage reads the \(M\) middle maps and writes 64 outputs with kernel depth \(K_t = 3\):

Let \(P_{1D}\) be the temporal-stage parameter count, with \(C_{out} = 64\) output maps and temporal extent \(K_t = 3\):

\[P_{1D} = C_{out} \times M \times K_t + C_{out} = 64 \times M \times 3 + 64 = 192 \times M + 64\]

The pair total is therefore:

\[P_{total} = P_{2D} + P_{1D} = 28 \times M + 192 \times M + 64 = 220 \times M + 64\]

Equating the pair to the fused budget gives the boundary value of \(M\):

Set the pair total equal to the fused count \(P = 5248\):

\[5248 = 220 \times M + 64\]

Subtracting 64 from both sides gives \(5248 - 64 = 5184\), so \(5184 = 220 \times M\). Dividing gives \(M = 5184 / 220\), which is about 23.56, rounded to 24. The verbal conclusion was at most 24 middle channels match the fused budget. Because the pair carries two nonlinearities, practice can drop below that ceiling. The session quotes the ceiling rule as:

\[M_{max} = 0.375 \times C_{out}\]

With \(C_{out} = 64\), that rule gives \(0.375 \times 64 = 24\), matching the derivation. Lower settings such as \(0.25 \times C_{out}\), which is 16 middle maps here, were reported as strong in the 2018 work, with the double-\(\mathrm{ReLU}\) effect credited for the gain. At \(M = 16\) the pair costs \(220 \times 16 + 64 = 3584\), about a third below the fused 5248. Neural architecture search over \(M\) on training and validation splits is the named route for picking the tradeoff point when resources allow.

Sense-check: \(M\) must be a positive integer no larger than a fraction of \(C_{out}\); a derived \(M\) above \(C_{out}\) would signal swapped coefficients, and a non-integer exact value is normal since channels quantize the boundary.

Two traps hide in this derivation. First, treating \(M = 24\) as the recommended setting rather than the ceiling; the equality only marks where the saving vanishes, and the benefit comes from dropping below it, for example to 16. Second, forgetting either bias tail: the \(+M\) in the spatial stage and the \(+64\) in the temporal stage both enter, and dropping them shifts the boundary by a full channel.

8.7.4 The French-Fries Analogy

The session tells a kitchen story to fix the mechanism. Deep-frying fries once, long and hot, is the fused path: one vessel, one long cook, one chance to get the texture right. Frying once to cook through, resting, then frying again at a lower temperature in a second vessel is the split path. The two-stage fries come out crisper in less effective time, because each stage has its own job and its own temperature.

Map it explicitly. The first fry is the spatial stage: it cooks the appearance through, turning raw pixels into per-frame structure. The rest between fries is the first \(\mathrm{ReLU}\): it sets the texture before the second cook. The second fry is the temporal stage: it crisps the dynamics, turning the middle maps into motion-aware features. The pair costs fewer parameters while gaining the extra nonlinearity crispness, just as the two fries cost less effective hot time while gaining crunch. Where the analogy breaks: fries cool between stages while middle maps never rest, and kitchen temperature has no learned weights, so do not push the mapping past mechanism into optimization.

8.7.5 Feature Vectors From Either Path

Both routes end the same way. Apply the 3D stack, or the factorized 2D plus 1D stack, to the clip, pool over space and time with an averaging step, and read out one vector. That feature vector is a compact numeric summary of the clip, typically one number per final channel. A global average pooling layer forms it by averaging each map to one number: a \(7 \times 7\) map becomes its mean, a 16-slot temporal map becomes its mean, and the stack of means is the vector. The vector then feeds whatever comes next: a neighbor classifier, a margin classifier, a video labeler, or an anomaly scorer.

So the factorization changes the kitchen, not the served dish. Downstream stages receive a vector of the same width either way; what differs is how many weights were spent cooking it and how many bends the function used. That interchangeability is why a team can swap fused blocks for split blocks without rewriting the classifier head.

One \(3 \times 3 \times 3\) step becomes a \(1 \times 3 \times 3\) spatial step plus a \(3 \times 1 \times 1\) temporal step with a \(\mathrm{ReLU}\) after each, costing \(220 \times M + 64\) against the fused 5248, with the ceiling at \(M = 24\) and practice favoring below it. With the efficient block derived, the last step is using it: clip settings, hybrid practice, downstream tasks, and the exam plan.

8.7.6 Student Questions and Answers

Q: Are the same weights reused across time in the factorized form?

A: The learned weights adapt across frames through training. The spatial weights are shared across frames within the 2D step, and the temporal weights mix the middle maps across time in the 1D step. Because the split adds a second nonlinearity, training can settle on sharper temporal weights than the single-shot form, so the schedule learned on one frame range carries across the clip.

Q: If equating the counts gives the same parameter total, where is the benefit?

A: The equality only sets the ceiling \(M = 24\). The benefit comes from dropping below it. Since \(M\) is a tunable setting and the pair has two nonlinearities, a smaller \(M\) such as 16 keeps quality while the total falls below the fused count, here 3584 against 5248. Equality marks the boundary; the operating point sits underneath it.

Q: Can the intermediate maps be read as objects before the temporal step?

A: Early middle maps read as numbers or heat colors, not as named things. After several stacked blocks the patterns grow legible, but the first middle layer alone rarely shows a clean object. Tracking and labeling get their own later stages rather than being forced onto that first middle map. Expecting object names at the hinge is the misreading to avoid.

8.8 Clips, Hybrid Practice, Downstream Tasks, and Exam Plan

8.8.1 Clip Length, Sampling, and Resolution

A network never watches a whole two-hour video at once. It watches a clip: a short window cut from the stream. How long should the window be, and what should it cost.

The clip length \(T\) is a first-class setting, not an afterthought. Shorter clips infer faster: fewer placements, smaller maps, less memory per batch. Longer clips carry richer motion dynamics: longer gestures, tempo changes, and direction reversals stay inside one window. The 16-frame, \(112 \times 112\) setting is one tradeoff point, not a fixed truth. It fits period hardware while holding enough motion for action-scale gestures at teaching resolution.

Higher or lower resolution and consecutive versus sampled frames are further dials. Raising resolution sharpens edges and small objects but multiplies every map quadratically. Lowering it speeds everything while risking fine detail. Taking 16 consecutive frames watches about half a second at 30 fps with full flicker fidelity. Taking 16 sampled frames, for example every third frame, spans a longer span, over a second and a half, at the cost of fine flicker: fast twitches between samples vanish. Pick consecutive sampling when the cue is a twitch, strided sampling when the cue is a gesture arc.

A clip is the \(T\)-frame window one forward pass consumes. Sampling stride is the gap between chosen frames: stride 1 takes consecutive frames, stride 3 takes every third frame. Resolution is the \(H \times W\) pixel size per frame. Longer \(T\), denser stride, and larger \(H \times W\) each raise fidelity and cost together; no dial moves quality without moving the bill.

Training choices layer on top. Training from scratch means learning all weights from random starts on video alone, which needs the most data and hardware. Starting from pre-trained weights means warming up from image or video weights and tuning, which is the usual budget route. Augmenting clips means manufacturing variants by cropping, flipping, scaling, or jittering time, which multiplies effective data without new footage. Whether to store augmented clips before training depends on budget: precomputing saves repeated decode work at the price of disk. The stated guideline is to finish cleaning and augmentation first, save those intermediate videos to local storage, and only then train, so the feature-learning stage never repeats the same decoding and warping work.

Picture a dial board with four sliders: clip length, resolution, sampling stride, and augmentation volume. Push any slider right and two meters rise together, accuracy potential and compute bill. The takeaway is that clip design is budget design, and the 16-frame point is one marked position on each slider, not the only one.

Scope: the 16-frame recipe suits short action clips of seconds. Hour-long surveillance or lecture footage needs a different front end, sparse candidate selection before any 3D stack runs, because no clip window covers hours and no GPU holds them. Match the window to the gesture scale; a window far shorter than the event sees fragments, and one far longer drowns the event in filler.

8.8.2 Hybrid Domain Plus Deep Learning Practice

The session argues that pure end-to-end work rarely wins on long real videos. The working recipe pairs a subject-matter expert with the model stack. The expert says what matters, for example that sampling every five minutes suffices for multi-hour material because the events of interest evolve slowly, and the builder turns that into sampling, augmentation, and architecture settings. The expert needs no computing background. The builder's skill is in asking questions that turn answers into settings: how fast does the event change, what does normal look like, which hours can be skipped outright.

The personal case discussed runs two to five hours per video, far beyond one-minute teaching clips. The temporal-first habit there is: catch the change across time, then analyze the changed frames in spatial detail. First find the minutes where something moves or shifts, then spend the expensive spatial machinery only on those candidates. The toolbox line sums it up: many tools exist, selection is the hard part, and what fits one data source may not fit another. A pipeline tuned for staged dance footage misfires on highway traffic, and both misfire on wildlife at night. Trial, patience, and staged work, such as spending one full day just getting ten uploads onto the server, beat rushing. Uploads, decoding, and storage are project stages with their own days on the calendar, not overhead to wish away.

Long-duration monitoring is the concrete instance: a two-hour feed must be cut to sparse candidate segments before any classifier runs, with a subject-matter expert setting the sampling cadence. On-campus answer-script batching returns as the throughput twin: table length caps the per-round throughput there just as upload bandwidth and GPU memory cap candidate throughput here.

Treat the expert as a sensor and the network as the lens: the expert decides where to point, the stack decides what the pointing reveals. Budget uploads and preprocessing as first-class stages, sample sparsely on slow material, and re-tune the toolbox per data source rather than porting pipelines blindly.

8.8.3 What Comes After Features

Feature extraction is only the front half. The back half is task-driven, and the session orders it by difficulty. Simple clip labeling comes first, for example dance scenes against fight scenes, or animal clips against cooking clips on one- to five-minute inputs: one label per clip, no boxes, no tracks. Then comes detection plus tracking of a chosen target, such as a lion, a tiger, a person of interest, or a car, which is the same machinery behind person and vehicle surveillance: boxes per frame linked across time into tracks. Then comes anomaly detection, where anomaly means deviation from learned normal behavior, so the system must learn normal first and flag the rest. A loitering figure in an empty corridor at 3 a.m. is anomalous only against a learned model of that corridor's normal hours; the same figure at noon is routine. Each step can chain the last: label the clip, detect the thing, track it across frames, and score the track for deviation.

The three downstream stages form a ladder. Classification answers what the clip shows. Detection plus tracking answers where the thing is in each frame and how its positions link across frames. Anomaly detection answers whether the linked behavior deviates from learned normal. Higher rungs assume the lower ones: no track without boxes, no deviation score without a normal model.

The session promises multiple routes to each goal. The spatio-temporal stack gives route one: direct, joint, teachable. Later routes will beat it on some tasks, through attention, two-stream fusion, or inflated image backbones, and that is expected. Route one teaches the continuous thread that later hacks presuppose; later routes teach the stronger hack. Learn the thread first, then the hack earns its keep.

Wildlife monitoring shows the ladder in one deployment: classify day versus night clips, detect and track the tiger across frames, then flag the track that paces the fence line as deviation from foraging normal. One feature stack feeds all three rungs.

Key Industry Applications

Joint spatio-temporal encoding powers action-clip systems that sort dance against fight scenes or animal against cooking videos on short inputs, reading position and motion in one pass rather than bolting a tracker onto a detector.

Vehicle motion models show both the promise and the boundary of transfer: weights learned on car translation often carry to train motion within the same motion family, yet fail on spins in place or animal gaits where the movement vocabulary changes, so deployment always starts by judging motion-domain closeness.

Person, intruder, and car tracking for surveillance builds on the same stack by chaining stages: label the clip, detect the target per frame, link boxes into tracks, and score tracks for deviation from learned normal, which is the ladder from classification through tracking to anomaly detection.

Long-feed monitoring pairs domain experts with the model stack: on two-hour feeds the expert sets a sparse sampling cadence, candidate segments are cut first, and the deep stack runs only on candidates, so sampling design decides feasibility before architecture does.

Graphics-processor parallelism sets throughput the way hall tables set checking rounds: each parallel unit behaves like one more checker, so kernel counts and unit counts jointly fix the round count, while video, weight, and working memory footprints each set independent capacity ceilings.

ImageNet pre-training and temporal segment networks remain the reuse and segmentation baselines that 3D and factorized stacks build on: warm-start appearance weights from still images, split long videos into sampled segments, and spend the expensive joint convolution where motion evidence actually lives.
