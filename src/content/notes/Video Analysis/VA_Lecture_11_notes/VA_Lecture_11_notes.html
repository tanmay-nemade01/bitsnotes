This lecture builds the full path from still-image detection to video tracking. It starts with what a bounding box means, shows why running a detector on each frame alone breaks down on real video, repairs detection with temporal information and optical flow, then develops single-object tracking from naive correlation through Siamese networks to SiamRPN, and finally lifts the machinery to multi-object tracking with detection-plus-association and the Hungarian algorithm.

11.1 Rigid Bodies, Detection, and Tracking

Why does video need its own machinery when image detectors already draw boxes well? Because a video is a sequence of frames, and the most important thing to look at in video is how an object moves or changes. Change here means three things: the position of the object, the direction it moves in, or any other kind of change in its state, such as entering or leaving the scene.

A rigid body (an object whose shape stays fixed while it moves, for example a ball in flight) keeps the same outline from frame to frame, so tracking reduces to finding where that fixed shape went. An elastic body (an object whose shape can deform under a small force, for example slime, with value like a blob that flows) changes outline even without moving, so a fixed rectangle is a poor model.

Think of slime or liquid mercury poured on a table: the blob spreads, splits, and re-merges. No fixed-width rectangle follows it for long. That is why this lecture sets elastic bodies aside and stays with rigid bodies — a basketball or football in flight, a person walking, or a car driving. Once such an object is detected, its shape is maintained from frame to frame, so the task reduces to finding where that fixed-shape object is and how it moves. The analogy breaks where people articulate: arms and legs swing, so a person is only approximately rigid, and the box must be loose enough to hold the limbs.

Two distinct tasks follow from this.

Detection (finding every object inside one frame on its own, written as a set of boxes plus class labels) answers where each object is in this frame. Tracking (carrying identities and states across frames, written as tracks with entry, motion, and exit) answers which object in this frame is the same as which object in the last frame. Detection uses only spatial data inside one frame; tracking adds temporal information, the relationship between frames.

Take a ball moving across frames. Detection localizes that ball inside each individual frame without asking how it changed between frames. The output of detection is always a bounding box, a rectangle drawn around the object, together with a class label saying what the object is — a ball, a person, a vehicle, and so on. Tracking takes those boxes and maintains state: did the object enter the scene, is it moving, is it exiting?

Because detection is a per-frame spatial task, a ready-made image detector can be used for it. The models named are YOLO and R-CNN variants such as Fast R-CNN and Mask R-CNN, with YOLO described as the de facto standard that most people reach for. A pre-trained YOLO trained on image data with 1000 classes detects balls, bicycles, cars, and everything else in that class list, drawing boxes with little extra work. Tracking is where the harder problem starts, because identity must be maintained over time. The simplest tracking case has only one instance of the class — one ball in a football or basketball sequence — so no disambiguation is needed. The harder case has many instances of the same class: players with jersey numbers 7, 10, and 13 are all of class person, and the detector returns a box for each of them, but tracking must give each instance its own identity number and carry those identities across frames.

A concrete pairing makes the split sharp. Suppose frame 12 contains three boxes labeled person. Detection stops there: three boxes, three class labels. Tracking continues: box A is P7 carried from frame 11, box B is P10 carried from frame 11, box C is a new entrant P13. If P7 leaves at frame 50, tracking closes that track rather than deleting the detection.

Scope: the rigid-body box model applies when shape change between frames is small compared with displacement — balls, cars, upright pedestrians at a distance. Assumption: width \(w\) and height \(h\) vary slowly, so a rectangle remains a faithful outline. When the assumption fails — a gymnast tumbling, a close-up player spreading arms wide — the box either cuts off limbs or fills with background, and segmentation or keypoint models fit better.

Picture the lecture's opening visual: a timeline of frames left to right, with the same ball shifted slightly in each frame and a rectangle snug around it. The horizontal axis is time in frames, the vertical axis is image position. The rectangles keep nearly the same size while their centers march forward — that flat size curve with a sloped center curve is the signature of rigid-body motion. The takeaway is that position changes while shape stays put.

A common trap is to treat tracking as repeated detection with new numbers each frame. New numbers each frame destroy identity: P7 becomes a stranger in every frame. Another trap is to treat an elastic object as rigid: the box fits in one frame and fails in the next, and the failure looks like motion when it is really deformation.

Rigid shape lets one rectangle follow an object across frames; detection draws the rectangle in each frame while tracking links those rectangles into identities with states. That link — from boxes to identities — is the bridge to applications next.

Sports officials use exactly this split: a detector finds the ball in each broadcast frame, while a tracker holds the ball's identity through blur and occlusion to rule on the line call. Across video analysis broadly, this detection-then-link pattern recurs in surveillance, traffic, and behavior analysis.

11.1.1 Bounding Box Representation

The rectangle around an object is written \((x, y, w, h)\), where the plain-language description is "x, y is the starting point of the box, and w and h are the width and height of the rectangle."

A bounding box (the smallest axis-aligned rectangle holding the object, written \((x, y, w, h)\) with values like \(x = 120\), \(y = 80\), \(w = 60\), \(h = 90\) pixels) localizes the object. Here \(x \in \mathbb{R}\) is the horizontal coordinate of the starting corner in pixels, \(y \in \mathbb{R}\) is the vertical coordinate of the starting corner in pixels, \(w \in \mathbb{R}^{+}\) is the width in pixels, and \(h \in \mathbb{R}^{+}\) is the height in pixels.

Every symbol is named on first use, and the remaining corners follow by arithmetic rather than by new measurement:

\[ x_2 = x + w, \quad y_2 = y + h \]

so the four corners are \((x, y)\), \((x+w, y)\), \((x, y+h)\), and \((x+w, y+h)\). A worked reading: a box at \((120, 80)\) with width \(60\) and height \(90\) spans columns 120 to 180 and rows 80 to 170, so its opposite corner sits at \((180, 170)\). A detector outputs one such box plus a class label per object in each frame. Sense-check: width and height must stay positive; a zero or negative value means the box prediction collapsed.

11.1.2 Student Questions and Answers

Q: Does tracking mean we stop detecting in every frame? A: No. Detection still happens per frame and gives boxes plus classes. Tracking adds the temporal layer on top: it links those per-frame boxes into identities with states such as entered, moving, or exited. The doubt is natural because tracking sounds like it replaces detection, but the correction is that tracking consumes detections — without fresh boxes each frame there is nothing to link.

11.2 Where Detection and Tracking Are Used

Why learn this machinery at all? Because three families of real tasks pay for it, and each one leans differently on detection versus tracking.

Which family needs every frame, and which can skip frames? Sports officiating needs every frame because one missed frame can flip a ruling; surveillance needs long trajectories because suspicion lives in motion patterns; autonomous driving needs real-time tracks because decisions cannot wait for the future.

11.2.1 Three Application Families

Sports analytics (measuring player and ball motion to guide coaching and rulings, for example ball-by-ball cricket trajectories) is the most intuitive. Tracking the movement of players and the ball supports post-match analysis, strategy changes for a particular player, and decision-making such as third-umpire style rulings. Here every frame matters, because a missed frame can mean a missed event — a goal-line touch lost between frames is lost for good.

Surveillance and security (watching crowds for abnormal motion, for example a plaza camera counting flows) is the second. The goal is to watch crowd movement and flag suspicious activity from motion patterns — for example, when everyone moves toward the exit and one person moves against that flow, that counter-flow motion is suspicious. This is a tracking task, since the judgment depends on trajectories, not on any single frame. One still image of a person proves nothing; a ten-second path walking against the crowd proves intent.

Autonomous vehicles and traffic management (following every nearby road user continuously, for example a highway stack tracking each car) form the third. A self-driving car or a roadside traffic system must track each car and each nearby object continuously. This is the real-time use case, where decisions must be made online with only past frames available — the car cannot peek at the next second before braking now.

A side-by-side contrast sharpens when to pick which emphasis. Sports analysis tolerates offline processing with heavy models since the match can be reviewed after the whistle. Surveillance tolerates near-online delays of seconds but needs long identity memory across occlusions. Driving allows no delay at all and must run lightweight models on past frames only, trading some accuracy for latency.

A common trap is to treat all three as detection problems. Detection alone suffices for counting people in one aerial photo, but it fails wherever the question is about motion — speed, direction, dwell, counter-flow — because those quantities exist only across frames.

Sports needs complete tracks for rulings, surveillance needs long trajectories for behavior, and driving needs instant tracks for control. All three motivate why per-frame boxes alone fall short, which is where the failure analysis goes next.

Stadium analytics firms sell per-player heat maps built from these tracks; city traffic control builds signal timings from vehicle trajectories; mall security builds loitering alerts from dwell paths. The domain placement is the same: wherever decisions depend on where things went, not just where they are, tracking pays.

11.2.2 Quick-Reference List

Sports analytics uses player and ball trajectories for strategy and officiating decisions, and keyframe-only shortcuts fail here because the decisive touch may live in the skipped frame. Surveillance systems detect suspicious behavior, such as a person moving against an exiting crowd, from trajectory patterns rather than single poses. Autonomous vehicles and traffic management systems track every surrounding vehicle and pedestrian in real time under strict latency budgets.

11.3 Why Per-Frame Detection Alone Fails on Video

If YOLO draws good boxes on photos, why not just run it on every frame and call the video solved? Because video adds motion, viewpoint, and time, and each one breaks the photo assumption.

What happens when the object smears, hides, shrinks, and then the box list blinks? Motion blur smears identity, occlusion hides the object, scale change shrinks or swells it, and the per-frame box list flickers as each frame is judged alone.

11.3.1 Blur, Occlusion, and Scale Variation

The first challenge is motion blur (smearing of fast motion within one exposure, for example a sprinting player's legs turning to streaks). When a person moves fast, each frame smears the appearance, and the blurred identity no longer matches what the detector learned. The concrete experience shared is that a person could not be tracked because motion blur corrupted every frame, and even retraining YOLO on that specific data still failed. Blur is therefore a major roadblock, not a detail that can be ignored. Retraining helps with new poses but cannot restore edges the exposure destroyed.

The second challenge is occlusion (hiding of the object behind scene geometry, for example a striker hidden behind a defender). One illustration is a person emerging from behind a tree: while the person is still partly behind the tree, the visible fragment is not enough to say whether it is a person or an animal. The driving illustration is sharper. From an aerial view, vehicle B sits in front of vehicle A and both are visible. From the ego view at the back, looking forward past vehicle A, vehicle B is hidden behind it, so the detector looking from behind cannot detect correctly. Occlusion is viewpoint-dependent: the same scene is easy from above and hard from behind. Like a hand covering part of a coin, the hidden part contributes no pixels, so no per-frame classifier can recover it from that frame alone.

The third challenge is scale variation (change in apparent size with distance, for example a near player filling 400 pixels while a far player spans 30). With a fixed camera, as in sports, objects near the camera look big — a footballer standing next to a corner camera may fill the frame or even be cut off — while the same player far from the camera looks tiny. Detection trained at one size then fails at the other extreme, both very near and very far. The remedy is to retrain or fine-tune the detector with samples from the deployment conditions rather than relying on the pre-trained model as is: collect near-camera and far-field crops from the actual stadium and mix them into training.

Scope: these three failures are properties of the video, not of one bad detector. Assumption: a per-frame detector assumes each frame shows a clean, fully visible, medium-scale object. When fast motion, crowding, or a fixed wide-angle camera breaks that assumption, per-frame scores collapse even for a strong backbone.

Picture the occlusion visual: two rectangles for the aerial view, both fully drawn, against one rectangle plus a dashed hidden outline for the ego view. The horizontal axis is road depth, the vertical axis is image height. The landmark is the crossover where the near car fully covers the far car. The takeaway: visibility is a function of viewpoint, not of object presence.

Beginners often blame the detector threshold when boxes vanish. Lowering the threshold under blur or occlusion mostly adds false boxes on background without recovering the true one. Another trap is to treat scale failure as a labeling error: adding more labels at one scale never fixes the other scale.

11.3.2 Flickering Object Lists

On top of these, naive per-frame detection produces inconsistent object lists (boxes that appear and vanish across frames though the object never left, for example IDs blinking 5, gone, 5). YOLO may detect an object in one frame, miss it in the next two, and pick it up again later, so objects flicker in and out of the list. The expected output is a stable per-frame list — frame one contains these objects, frame two contains these objects, frame three contains these objects — but the naive approach makes it look as though an object exited and re-entered when it was present all along.

A tiny trace makes it concrete. Frames 41 to 45 truly contain players P1 through P5. Naive output reads: frame 41 five boxes, frame 42 four boxes with P5 missing, frame 43 five boxes, frame 44 three boxes, frame 45 five boxes. Downstream logic then invents two exits and two entries that never happened, and any count, speed, or dwell statistic built on that list inherits the error.

Blur destroys features, occlusion removes pixels, scale shifts appearance, and per-frame judging turns all three into flicker. Smoothing those judgments with neighboring frames is the natural repair, taken up next.

Traffic cameras show the same flicker when a sign pole briefly splits a car into two visible halves; broadcast player trackers show it when a sprint smears a jersey number beyond recognition.

11.3.3 Student Questions and Answers

Q: Why not just use the pre-trained YOLO as is? A: Because of motion blur, occlusions, and scale variation in the deployment video. The pre-trained model was trained on clean images at particular scales, so on real video it misses objects or flickers. Fine-tuning on representative samples is usually required. Several students asked this in different words, and the canonical answer is the same: the domain gap between clean photos and stadium or road video is structural, not a threshold tweak.

11.4 Making Detection Video-Aware: Four Temporal Fixes

How can neighboring frames rescue a weak frame without smearing away the very motion being measured? Four fixes form a ladder from blunt smoothing to motion-compensated alignment.

If one frame is too blurred to trust, what do its neighbors know? Pooling borrows their features, consistency borrows their verdicts, keyframes skip the weak frames entirely, and flow warping first aligns the neighbors so borrowing does not blur motion.

The first fix is to average the features before detecting. Instead of detecting from each frame's features alone, gather the features from several frames, combine them with average pooling, max pooling, or attention-based pooling — any of the temporal pooling techniques — and run detection on the pooled features. The effect is to declare the object present across the frames even when individual frames are weak. The price is that motion gets washed out: averaging five frames blends the positions together, so where the object moved within that window is partly lost. Like blending five photos of a runner into one ghost image, the runner appears present everywhere and sharp nowhere.

The second fix is to enforce temporal consistency on the results. Run the detector per frame, then smooth the result list with a persistence rule: objects must exist continuously unless there is enough evidence they entered or left. In practice this means a threshold test — only if the evidence for entry or exit crosses a threshold is the object declared present or declared a false detection. Short flickers are thereby suppressed. A one-frame gap inside a ten-frame streak is filled; a one-frame flash with no neighbors is dropped.

The third fix is to detect only on keyframes. Pick representative frames, detect there, and skip the rest. This cuts computation, but whether it is acceptable depends on the task. For summarization or coarse analysis it can work. For detailed sports strategy analysis of one player, or for autonomous driving, it does not, because the object must be known everywhere. Skipping the exact frame of a goal-line touch is not a speedup but a failure.

The fourth fix is to guide detection with optical flow. Flow measures pixel motion between frames, and it is used to warp features from neighboring frames onto the current frame before averaging, so motion is compensated rather than blurred away. This is the most principled of the four and is detailed in the next section.

A comparison helps pick among them. Feature pooling is cheap and robust to brief blur but loses precise position. Consistency smoothing costs almost nothing and fixes flicker but cannot recover a long gap. Keyframes save the most compute but risk missing events. Flow warping preserves position best but pays the cost of flow estimation. When positions matter and compute allows, flow warping wins; when only presence matters on a budget, pooling plus consistency suffices.

11.4.1 Flow-Guided Feature Warping

Flow-guided aggregation starts exactly where naive averaging fails. Averaging raw features across frames discards movement; warping first aligns the frames and then averages, so the motion the object underwent is accounted for.

Optical flow (a per-pixel displacement field between two frames, written \((u, v)\) in pixels per frame-step, with value like \((6, -2)\) meaning six pixels right and two up) tells where each pixel moved. Warping (resampling one frame's features along that displacement field, written \(\tilde{F}_{T+k}\)) aligns the neighbor onto the reference before any averaging happens.

The setup uses a reference frame, generally frame one, or a fresh reference after a cut or a major scene change. From a frame at time \(T\) with features \(F_T\), take the next \(K\) frames \(T+1, T+2, \ldots, T+K\) and extract each frame's features. Compute the optical flow between the reference frame and each of these frames. The flow is a vector field saying where each pixel moved. Add the flow to the reference features to get a prediction of the neighbor's features, written \(\tilde{F}_{T+1}\) for the predicted features of frame \(T+1\). In words from the discussion: "from F T, if I add the flow, I will get a predicted value which is more or less F T plus one tilde — it is kind of an estimation." That prediction says where the object, for example the ball, is expected to be in the future frame. This alignment step is called warp. The warped features are then averaged, and that averaged feature vector feeds the detector. Because each neighbor was first warped onto the reference, the movement that plain averaging neglected is now included.

Formally, let \(F_T\) be the feature tensor of the reference frame with height \(H\), width \(W\), and \(C\) channels, and let \(\text{flow}(T \to T+k)\) be the flow field from frame \(T\) to frame \(T+k\) with two displacement components per spatial location. The warped prediction and the pooled feature are:

\[ \tilde{F}_{T+k} = \text{warp}(F_T, \text{flow}(T \to T+k)), \quad \bar{F} = \frac{1}{K}\sum_{k=1}^{K} \tilde{F}_{T+k} \]

Detection runs on \(\bar{F}\), possibly including \(F_T\) itself in the average. A numeric sketch: a ball feature at column 100 with flow \(+8\) pixels per frame warps to column 108 in frame \(T+1\) and 116 in frame \(T+2\); averaging after this shift keeps the peak sharp at the motion-compensated position instead of smearing it across 100 to 116.

Scope: warping helps when flow is reliable — moderate motion, textured regions, stable lighting. Assumption: the flow field correctly maps reference pixels to neighbor pixels. Under large occlusions, textureless walls, or sudden cuts, flow itself fails and warped features misalign, so a fresh reference must be chosen.

Picture the visual: two feature humps offset by motion, arrows of flow carrying the first hump onto the second, then one tall averaged hump. The horizontal axis is image position, the vertical axis is feature strength. The landmark is the aligned peak after warping versus the twin smeared peaks before it. The takeaway is that alignment before averaging preserves location.

A common trap is to warp boxes instead of features and expect the same gain: late box averaging cannot recover features lost to blur. Another trap is to average across a scene cut: frames from two shots share no motion, and their average is pure noise.

Warp-then-average borrows strength across frames while respecting motion, turning flickering per-frame verdicts into one stable video-aware verdict. Where the full video is not yet available, though, this recipe must change — which is the offline-online split next.

Broadcast slow-motion replay uses this idea to hold a sharp ball outline through blurred frames; dashcam enhancement aligns neighboring frames before denoising for the same reason.

11.4.2 Offline Versus Online Detection

Offline detection (seeing the whole video before deciding, using past plus future frames with heavy backbones like ResNet or Swin Transformer) maximizes accuracy. Online detection (deciding now from past frames only with lightweight models like YOLO Lite or MobileNet, with latency like 30 milliseconds per frame) meets real-time control at the cost of lookahead.

Everything above assumes offline processing: the whole video is available, so for any current frame both past and future frames exist and heavy models are affordable — EfficientNet, ResNet, or a Swin Transformer can be used for detection. Online or real-time detection, as in autonomous vehicles, faces two hard constraints. First, only past frames exist; future frames cannot be used, so any method depending on lookahead must be rethought. Second, the model must be lightweight: YOLO is already light, but real-time work may need YOLO Lite, MobileNet, or even lighter variants. Real-time video understanding is therefore always a three-way balancing act between latency, accuracy, and available compute: a heavier model buys accuracy with milliseconds that a braking car does not have.

Exam note: expect conceptual questions contrasting offline detection (past plus future frames, heavyweight backbones) against online detection (past frames only, lightweight backbones, latency-accuracy-compute tradeoff). Offline suits post-match review; online suits the driver's seat.

11.5 Single-Object Tracking: Setup and Metrics

How is following one ball different from finding boxes in every frame? Tracking starts from a known box and must produce the box in every later frame, and then those boxes must be scored honestly.

Given the ball's box in frame one, where is that same ball in frames two, three, and onward? Single-object tracking assumes exactly one instance per frame, so the only unknowns are position and size over time — identity is fixed by construction.

Tracking means following the movement of an object across frames. The input is a video sequence plus an initial bounding box. Frame one is the reference frame: objects are detected there with a simple detector such as YOLO, yielding a bounding box per object. A general notation numbers objects with subscript \(i\) and frames with subscript \(t\) (written \(T\) in places), so a box can carry both an object identity and a frame index, and an object can carry a class. For learning the concept, this is then grossly simplified: only one object exists per frame, so there is a single class and a single box per frame, and the subscript for the object can be dropped. The output is then simply one bounding box from each frame. The running example is ball tracking in football or basketball, where there is exactly one ball instance, serving purposes such as officiating decisions. Very few real use cases are this simple, but the simplification isolates the tracking idea before identity enters in multi-object tracking. This single-object setting is called SOT, and it does not scale by repetition to many objects, because the identity problem needs separate machinery — running one SOT tracker per player leaves cross-identity swaps unresolved.

11.5.1 Mathematical Formulation

Single-object tracking (following one known box through time, written \(B_1 \to B_2 \to \cdots\), with value like a ball box gliding across frames) starts from detection in frame one and predicts the same object's box thereafter. Let the frame index be \(t = 1, 2, \ldots\) and let the single box in frame \(t\) be \(B_t = (x_t, y_t, w_t, h_t)\), with \(x_t, y_t\) the starting corner and \(w_t, h_t\) the width and height in pixels.

Detection in frame one gives \(B_1\); tracking produces \(B_2, B_3, \ldots\) by following that object. Before simplification, a box would carry an object index \(i\), a class, and a frame index \(t\); under the single-object simplification only \(B_t\) remains. Concretely, \(B_1 = (120, 80, 60, 90)\) might become \(B_2 = (128, 81, 60, 90)\) as the ball drifts eight pixels right — same size, shifted center.

11.5.2 Robustness, Accuracy, and Overlap

Three measures judge single-object tracking, and they split on whether ground truth is needed. Ground truth, abbreviated GT (the recorded correct box per frame, for example a table stating the basketball center was at \((130, 85)\) in frame one and \((138, 86)\) in frame two), means the correct answers are already known.

Robustness (whether the tracker kept producing a box at all, written as a ratio near \(0.95\) on easy clips) needs ground truth only for the first frame. Accuracy (how close each box is to truth, written via IOU near \(0.8\) for a good frame) needs full ground truth in every scored frame.

Robustness asks whether the object was followed at all: in how many frames was this particular object tracked? With a football followed frame by frame, robustness is the simple ratio of the total number of detections to the total number of frames:

\[ \text{robustness} = \frac{\text{number of frames with a detection}}{\text{total number of frames}} \]

In the plain-language version: "total number of frames and total number of detections — simple ratio — that will tell me the robustness." A worked reading: 180 frames with a box out of 200 frames gives robustness \(180 / 200 = 0.90\). Robustness needs ground truth only for the first frame (to know what to follow); the rest is just whether the track continued.

Accuracy needs full ground truth, because it compares each detected box against the true box using intersection over union, abbreviated IOU (overlap area divided by union area, for example \(0.75\) meaning three-quarters shared). Let \(D\) be the set of pixels inside the detected box and \(G\) the set of pixels inside the ground-truth box. Then:

\[ \text{IOU} = \frac{|D \cap G|}{|D \cup G|} \]

where the plain-language description preserved alongside is "this is my ground truth and this is where my object was detected — this is the intersection part — divided by detection union ground truth — and this is in terms of pixels, the number of pixels." Here \(|\cdot|\) counts pixels. A worked reading: intersection 1200 pixels and union 1600 pixels give IOU \(1200/1600 = 0.75\). A large overlap gives an IOU near one; a false detection far from the truth gives an IOU near zero. Shape check: both numerator and denominator are pixel counts, so IOU is unitless and always lies in \([0, 1]\).

Each frame thus gets one IOU value for the tracked object. That continuous value is converted to a binary decision with a threshold: frames whose IOU sits above the threshold count as detected, and the rest count as errors. From that split comes the success rate (the fraction of frames with IOU above the threshold, for example 0.82 at threshold 0.5). The lecture also describes precision as computed over the low-IOU frames in this session's simplified framing. Keep both forms side by side: the lecture's working definition ties precision to the below-threshold error frames, while the standard tracking literature defines precision from center-location error (fraction of frames whose predicted center lies within, say, 20 pixels of truth) and success from IOU-threshold curves. Both need full ground truth, and getting ground truth on video is the hardest part of evaluation, which is why robustness — needing almost no ground truth — is the easy measure.

Picture the IOU visual: two overlapping rectangles, cross-hatched intersection in the middle, joint outline around both. The horizontal and vertical axes are image columns and rows in pixels. The landmark is the shared region: when it nearly equals the union, the tracker is locked on. The takeaway is that IOU turns box closeness into one number between zero and one.

Scope: robustness answers "did it keep going" under sparse labels; IOU-based accuracy answers "was it right" under dense labels. Assumption: robustness assumes a missing box means failure rather than correct absence — valid only in SOT where the object is always present.

A common trap is to report robustness as accuracy: a tracker that never drops the ball but trails ten pixels behind scores 1.0 on robustness and poorly on IOU. Another trap is to average IOU across frames with missing boxes without deciding how to score gaps — define the rule before comparing numbers.

Robustness counts survival, IOU measures alignment, and thresholding turns alignment into success and precision verdicts. With scoring settled, the simplest tracker — bare correlation — can be tried next.

Line judges live this split: noting that the ball was followed all rally long is robustness; certifying each bounce mark within millimeters is accuracy.

11.5.3 Student Questions and Answers

Q: What exactly is ground truth here? A: A pre-recorded table of correct answers: frame one has the basketball at this position, frame two at this position, and so on. With it, IOU-based accuracy, success rate, and precision can be computed. Without it, only robustness — whether the track continued — is measurable. Labeling every frame by hand is what makes ground truth the hardest part of video evaluation.

Exam note: be ready to define robustness as detections over frames, write the IOU formula as intersection pixels over union pixels, and explain which metrics need ground truth and why ground truth is hard to obtain. Also know the standard-literature pairing: success from IOU thresholds, precision from center error.

11.6 Naive Tracking by Correlation

What is the simplest tracker that could work, and where exactly does it break? Bare correlation is that baseline: memorize one pattern, slide it across the next frame, and call the peak the object.

If the ball barely moves between frames, why learn anything fancy? Just remember what the ball looked like in frame one and hunt for that same patch nearby in frame two.

11.6.1 Filter Behavior and Generalization Limit

Correlation-filter tracking (sliding a learned template across the next frame and reading the peak response, written as a Gaussian bump centered on the ball, with value like peak 0.95 at the true center) assumes small motion and fixed appearance. A classifier-style filter shapes the response into a Gaussian-like peak at the object's location, which conveniently detects simple objects such as a football or basketball.

The naive tracking approach is correlation with a trained filter, and it is worth understanding because everything later improves on it. In frame one the object is detected. In frame two the tracker assumes the object must be somewhere nearby and correlates the learned pattern against the new frame. Concretely, the filter holds the frame-one ball patch; each nearby patch in frame two is scored by dot-product similarity; the scores form a heat map with one bright hill; the hilltop is declared the new position. Like holding a stencil of the ball over the next frame and sliding it until the fit looks best, the method is direct and fast.

The limitation is generalization. A filter trained on one specific ball pattern — say a white football with particular markings — works only for that pattern. It will not transfer to a basketball, a cricket ball, or a tennis ball. Correlation tracking is therefore locked to one subset of appearances: it tracks what it was trained on and nothing else. Change the lighting, rotate the ball to show a new panel, or swap sports, and the memorized stencil no longer matches.

Scope: naive correlation fits short, slow, clean clips with one stable pattern. Assumption: appearance stays nearly constant and displacement stays inside the search window. Fast sprints, blur, occlusion, or a new ball design all break the stencil match at once.

Picture the response visual: a flat map with a single sharp hill over the ball. The horizontal axes are search-window columns and rows; the vertical axis is correlation score. The landmark is the lone peak near 1.0 with flat surroundings near 0. The takeaway is that a sharp lone peak means confident localization, while a flattened or double-peaked map means the stencil no longer fits.

A common trap is to enlarge the search window to fix failures: a bigger window under a bad stencil only adds more distractors. Another trap is to retrain the filter on each new ball from scratch per video — that recovers one clip at the cost of any generality.

Correlation shows the core tracking loop — memorize, slide, peak — but its memory is one fixed stencil. Learning a general notion of similarity instead of one stencil is the step Siamese networks take next.

Barcode scanners live at this level: one fixed pattern, one sensor distance, no generality needed — and video tracking needs far more.

11.7 Siamese Networks for Single-Object Tracking

How can a tracker follow a ball it has never seen before, without retraining on that ball? By learning similarity itself: one branch remembers the template, the twin branch scans the new frame, and their agreement votes for position.

Instead of memorizing this ball, can the network learn what "same object" looks like for any object? That is the shift from one stencil to a general similarity sense trained once on millions of pairs.

A Siamese network fixes the generalization problem with two identical branches called twin networks. Branch one receives a template, branch two receives the actual frame to search, each branch is a convolutional network, and the convolutional weights are shared, so there is no separate retraining per branch — the same parameters serve both sides. Like identical twins grading two essays with the same rubric, the branches apply exactly the same transformation, so their outputs are directly comparable. Each branch stops before classification, at the point where the fully connected layers would begin, and outputs extracted features. That feature output is called the embedding: a \(D\)-dimensional vector (in practice a tensor) describing the input in a space where similarity can be measured. The job is then to find the location in the search frame whose embedding is most similar to the template's embedding region.

The template is generally frame one of the video — the known appearance of the object. The other branch is the search branch and can be any frame \(T\) other than the template. Comparing the two embeddings is a similarity task, which places Siamese tracking under weakly supervised or semi-supervised learning rather than unsupervised learning: the template supervises the search, so if the template is wrong everything downstream goes wrong, and if it is right everything comes out well. A wrong initial box poisons the whole track; a clean one anchors it.

A helpful picture is a jigsaw puzzle. The picture on the box lid is the template, and one puzzle piece is the small template region. The search area is the scattered pieces, and the task is to find where that piece fits — the template could be anywhere inside the larger search region, and the network must find the most similar location. The backbone network doing the embedding can be AlexNet, which is shallow and was the starting point for Siamese trackers, or more commonly today ResNet-50. The two embeddings are written \(\phi(z)\) for the template embedding and \(\phi(x)\) for the search embedding, where \(z\) denotes the template input and \(x\) the search input. Here \(\phi\) is the shared-weight CNN, \(z\) is the \(127 \times 127 \times 3\) template crop, and \(x\) is the \(255 \times 255 \times 3\) search crop.

Cross-correlation response (similarity of the template embedding against every search location, written \(g\) of size \(17 \times 17\), with value like a peak of 0.9 at the true cell) turns matching into peak-finding. Similarity is measured by cross-correlation between the two embedding tensors plus a bias term \(b\):

\[ g = \phi(z) \star \phi(x) + b \]

where \(\star\) denotes cross-correlation, \(\phi(z)\) is the template embedding acting as the kernel, \(\phi(x)\) is the search embedding acting as the input, and \(b \in \mathbb{R}\) is a scalar bias. The plain-language version preserved alongside is: "phi of z cross correlation phi of x plus a bias b — that simple cross correlation is given." The output \(g\) is a response map whose peak marks the target; a simple \(\arg\max\) over the map finds the peak location, which is then mapped back to coordinates in the original search area to get the bounding box. Cosine similarity is explicitly not used here; cross-correlation is the measure.

Concretely, with AlexNet the template input is \(127 \times 127 \times 3\) and its embedding tensor is \(6 \times 6 \times 256\), while the search input is \(255 \times 255 \times 3\) and its embedding tensor is \(22 \times 22 \times 256\). Correlating the \(22 \times 22\) input with the \(6 \times 6\) kernel at stride one gives a \(17 \times 17\) response map, since \(22 - 6 + 1 = 17\). In words: "this is my kernel, this is my input — so 22 minus 6 plus 1 — it is just the normal convolution." Worked fully: each of the 256 channels correlates independently and sums, the \(6 \times 6\) window slides over 17 positions per side, \(17 \times 17 = 289\) scores result, the largest score's cell maps back through the network stride to image coordinates, and that center anchors the output box. Sense-check: a larger search tensor or smaller template tensor must grow the map; a \(17 \times 17\) map from these exact shapes confirms the arithmetic.

Training turns localization into a classification task over the search space: positions close enough to the true location get label \(y = 1\) (the "hot" region, like the hot-and-cold game where nearness means warm), and positions far away get \(y = 0\) (the "cold" region). Each location in the larger search space thus carries a binary label, ones near the target and zeros far from it. The training loss combines a logistic log loss over the score map with a contrastive pairing signal:

\[ \ell(y, v) = \log(1 + \exp(-y v)), \quad L = \frac{1}{|D|}\sum_{u \in D} \ell(y[u], v[u]) \]

where \(v[u]\) is the score at map cell \(u\), \(y[u] \in \{+1, -1\}\) is its hot-or-cold label, and \(D\) is the \(17 \times 17\) grid. Because comparison is involved, a plain log loss is not enough. Training combines a log loss, which says whether the object exists at a location, with a contrastive loss, which says whether the compared pair matches — the word contrastive comes from compare. Together they train the network both to find the object and to judge similarity correctly.

The standard Siamese network described here has variants called SiamFC and SiamRPN. SiamFC is the fully convolutional Siamese network with an AlexNet backbone — essentially what was just described. SiamFC is still used in some cases and is preferred up to a point, but it has limits that SiamRPN addresses next.

Scope: SiamFC shines for translation under mild appearance change with a fixed box shape. Assumption: the template from frame one stays representative and the object keeps roughly the same size and aspect. Long occlusions, drastic deformation, or large scale swings violate the fixed-template assumption and demand updates or proposals.

Picture the response visual: a dark \(17 \times 17\) grid with one glowing cell. The axes are search-window columns and rows in cells. The landmark is the lone bright peak against flat background scores. The takeaway is that similarity concentrated in one cell means a confident fix; scattered bright cells mean confusion.

A common trap is to feed the full first frame as the template: background floods the kernel and every background patch matches itself. Another trap is to read SiamFC as fully connected in the classifier sense — here FC means fully convolutional sliding-window search, not dense layers.

Shared twins plus cross-correlation turn tracking into similarity peak-finding that generalizes to unseen objects. The remaining gap is size and shape change, which multi-scale search patches and region proposals properly fix.

Face-verification logins use the same twin-embedding idea: enroll once, compare forever without retraining per pair.

11.7.1 Mathematical Formulation

Template input \(z\) (the frame-one crop, \(127 \times 127 \times 3\) for AlexNet), search input \(x\) (a later frame crop, \(255 \times 255 \times 3\)). Embeddings \(\phi(z) \in \mathbb{R}^{6 \times 6 \times 256}\) and \(\phi(x) \in \mathbb{R}^{22 \times 22 \times 256}\), where \(\phi\) is the shared-weight CNN. Response map \(g = \phi(z) \star \phi(x) + b\) of size \(17 \times 17\). Target location \((\hat{u}, \hat{v}) = \arg\max_{(u,v)} g(u, v)\), mapped back to search-area coordinates for the box. Training labels \(y(u,v) \in \{0, 1\}\), one near the true location and zero far away. Loss combines log loss with contrastive loss. Formally the per-map logistic form above is the reconciled training objective, with positive labels inside radius \(R\) of the center and negatives outside.

11.7.2 Student Questions and Answers

Q: Is the template the full first frame or the bounding box of the detected object? A: It is the detected object, not the full frame. The input crop is rescaled to the template size (127 by 127), but the content is the object box from frame one, and the search branch looks for that object inside the larger search area. Cropping plus context margin keeps the object dominant while adding a ring of background for discrimination.

11.7.3 Worked Examples

Example 1 — response map size. Template embedding \(6 \times 6\), search embedding \(22 \times 22\), stride one. Output size \(22 - 6 + 1 = 17\), so the response map is \(17 \times 17\) with 289 scores. The peak cell, say cell \((9, 11)\) with score 0.93, maps back through stride 8 to the image center offset and yields the box. Sense-check: 289 cells matches \(17^2\), and shrinking the template to \(5 \times 5\) would grow the map to \(18 \times 18\).

Example 2 — hot-and-cold labeling. Treat each search location as a guess in the hot-and-cold game. Cells within radius \(R\) of the true center (stride-adjusted) are labeled hot (\(y = 1\)); cells beyond are labeled cold (\(y = 0\)). Suppose the true center falls at cell \((8, 8)\): cells \((8, 8)\), \((8, 9)\), \((9, 8)\) score hot while corner cell \((0, 0)\) scores cold. The network learns to output hot exactly at the target, so at test time the hottest cell is the track.

11.8 Handling Scale: Multi-Scale Search and Penalties

What happens when the ball runs toward the camera and doubles in size? A fixed-size stencil keeps hunting at the old size and misses. Multi-scale search hunts at several sizes at once, with a penalty to keep the verdict honest.

If the object can appear big, medium, or small, why search only one size? Test all three sizes and let the penalized best score say which size actually won.

11.8.1 Searching Across Scales With Penalty Scores

Multi-scale search (running the same template-vs-search match at several rescalings, for example scales \(\{0.5, 1.0, 2.0\}\), with value like best penalized score at scale 2.0) catches size change. A scale penalty (a damping factor on large jumps, for example multiplying far-scale scores by \(0.97\)) stops rescaling artifacts from faking a win.

SiamFC as described searches at one scale, but objects change apparent size — the scale challenge from Section 11.3. The fix is a multi-scale search: the template is upscaled and downscaled (for example doubling to \(255 \times 255\) or halving toward \(64 \times 64\), though the exact factors can be anything, not necessarily 0.5 or 2), and the search runs at each scale on the assumption that at least one scale will catch the object. In the standard SiamFC recipe this means five scales \(1.025^{\{-2,-1,0,1,2\}}\) evaluated in one batched forward pass, with scale updated by damped interpolation (factor 0.35). Because rescaling changes the scores, a penalty is added so the network can tell at which scale the object was actually found — without the penalty the tracker could not attribute the detection to scale one, two, or three. A cosine window further damps large center jumps, and bicubic upsampling of the \(17 \times 17\) map to \(272 \times 272\) sharpens the peak before readout.

A worked sketch: scores before penalty read 0.70 at scale 0.5, 0.80 at scale 1.0, and 0.85 at scale 2.0. After penalizing the far scales, the ranking becomes 0.70, 0.80, 0.78, so scale 1.0 wins honestly instead of scale 2.0 winning on interpolation blur. Sense-check: without any penalty the largest scale often wins by smoothing alone, which is exactly the artifact the penalty removes.

Scope: scale search covers uniform growth and shrinkage — a ball approaching or receding. Assumption: width and height scale together. When width stretches while height shrinks (a player turning sideways, a car rotating), no uniform scale matches, and aspect-ratio handling is needed.

This mitigates missed detections across scales, but a limit remains: SiamFC handles scale changes, not aspect-ratio changes, where width and height scale differently. That gap motivates region proposals, which test multiple shapes per location rather than multiple sizes of one shape.

Scale search plus penalties extends the fixed stencil to approaching and receding targets, but shape change stays unsolved. Proposals that vary shape per location close that gap next.

Phone-camera zoom tracking uses the same trick: test a few zooms, penalize jumps, and lock the smoothest consistent size.

11.9 SiamRPN: Anchors, Two Heads, and the Combined Loss

How can one network test many shapes at every position and still run in real time? SiamRPN marries the Siamese similarity sense to a region proposal network: the template branch becomes a one-shot kernel predictor, and two heads score and refine every anchor.

Sliding one puzzle piece everywhere is slow and shape-blind. What if each spot offered five candidate shapes at once, with one judge scoring fit and another judge trimming edges? That is anchors plus two heads.

SiamRPN adds a region proposal network (RPN) — a concept that predates YOLO — to the Siamese design. Instead of correlating one template at one shape, the network proposes many candidate regions where the object might be and then selects the best candidate. Return to the jigsaw picture: SiamFC slides the piece around trying every position, while the RPN version first reasons that a piece with a straight edge must sit on the border, possibly rotated, narrowing the search to plausible areas before matching. Concretely, at each location the network lays down multiple anchor boxes — several boxes of different shapes centered at the same point — and evaluates all of them. An anchor box (a pre-set candidate shape at a location, for example five ratios at one center, with value like ratio 2.0 winning for a tall player) enumerates the plausible shapes so regression only trims rather than invents.

From there the network splits into two branches. The classification head outputs probability scores for each anchor: foreground versus background, i.e., how likely this anchor contains the object. The regression head predicts offsets relative to the anchor: how far the true box sits from the anchor position. For a location \((u, v)\) with an anchor box, the regression head outputs \((\Delta x, \Delta y, \Delta w, \Delta h)\), the shifts in center and size, and the predicted box is formed by adding these offsets to the anchor.

Box refinement (adjusting an anchor toward truth with learned offsets, written per-anchor as four deltas, with value like \((2.1, -1.4, 0.05, -0.03)\)) lets a few fixed shapes fit any nearby truth. The lecture states the update in additive teaching form:

\[ \hat{x} = x_{\text{anchor}} + \Delta x, \quad \hat{y} = y_{\text{anchor}} + \Delta y \]

with width and height adjusted by \(\Delta w\) and \(\Delta h\) relative to the anchor size. The standard SiamRPN parametrization behind this teaching form normalizes center shifts by anchor size and handles size multiplicatively:

\[ \delta_0 = \frac{T_x - A_x}{A_w}, \quad \delta_1 = \frac{T_y - A_y}{A_h}, \quad \delta_2 = \ln\frac{T_w}{A_w}, \quad \delta_3 = \ln\frac{T_h}{A_h} \]

\[ x_{\text{pro}} = x_{\text{an}} + dx_{\text{reg}} \times w_{\text{an}}, \quad y_{\text{pro}} = y_{\text{an}} + dy_{\text{reg}} \times h_{\text{an}}, \quad w_{\text{pro}} = w_{\text{an}} \times \exp(dw_{\text{reg}}), \quad h_{\text{pro}} = h_{\text{an}} \times \exp(dh_{\text{reg}}) \]

where \((A_x, A_y, A_w, A_h)\) is the anchor, \((T_x, T_y, T_w, T_h)\) is the ground truth, and \((dx, dy, dw, dh)\) are the head outputs. The lecture's additive sketch and the standard normalized-exponential form agree on centers up to the \(A_w, A_h\) scaling and on sizes up to the exponential; keep the lecture's symbols on the exam and recognize the standard form in references. The plain-language version preserved alongside is: "it will look at the anchor and relative to that anchor it will predict the offset — from this location, how much is the offset of delta x, delta y, delta w, delta h — that is what the regression head produces."

To cover multiple aspect ratios, each location \((u, v)\) carries several anchors — five is the typical number, with aspect ratios 0.33, 0.5, 1.0, 2.0, and 3.0. This set matches the SiamRPN reference choice of one scale with five ratios, confirming the lecture's list of ratios. If \(k\) denotes the number of anchors, the classification head produces \(2k\) scores per location (foreground and background for each of the \(k\) anchors) and the regression head produces \(4k\) values per location (four offsets for each of the \(k\) anchors). The ImageNet analogy given is that a 1000-class problem has \(k = 1000\) categories, hence 2000 classification scores and \(4k\) regression values per location in the corresponding formulation. Worked arithmetically with \(k = 5\): classification gives 10 scores and regression gives 20 values per location; over a \(17 \times 17\) map that is \(17 \times 17 \times 10 = 2890\) classification outputs and \(17 \times 17 \times 20 = 5780\) regression outputs.

The loss combines both heads. Classification uses a log loss; regression uses a smooth L1 loss. The total is:

\[ L = L_{\text{cls-log}} + \lambda \, L_{\text{reg-smooth-L1}} \]

where \(L_{\text{cls-log}}\) is the classification log loss (cross-entropy over foreground versus background), \(L_{\text{reg-smooth-L1}}\) is the regression smooth-L1 loss summed over the four normalized deltas, and \(\lambda\) is a balancing regularization factor whose lecture value is 1.2. Keep 1.2 as the lecture's stated constant for exam arithmetic; standard references leave \(\lambda\) as a tunable balancer (commonly near 1) without contradicting the lecture form. In words: "the total loss will be the classification log plus lambda loss regression — we are applying a regularization factor to balance out the loss." Positive anchors are those with IOU above 0.6 with truth and negatives below 0.3, capped per pair, which is why the two heads see balanced supervision.

Inference prunes to one-shot detection: the template branch runs once on frame one and its features become fixed convolution kernels; later frames run only the detection branch convolved with those kernels. A center window keeps only the middle \(7 \times 7\) anchor positions, a cosine window damps jumps, a size-ratio penalty damps shape jumps, and non-maximum suppression picks the final box with damped size update. That is why SiamRPN drops the five-scale test yet tracks shape better at 160 FPS.

Scope: SiamRPN fits single-target shape change with one template and fixed anchors. Assumption: the frame-one template stays representative and truth overlaps some anchor well. Long disappearance or a wholly new aspect outside the five ratios breaks coverage and needs re-detection.

Picture the anchor visual: one center point sprouting five rectangles — wide, square, tall — with the tall one glowing as foreground. The axes are local width and height in pixels. The landmark is the winning anchor's score pair \((0.92, 0.08)\) foreground versus background. The takeaway is that shape candidates turn one blind position into five shaped bets.

A common trap is to read \(k\) as class count: here \(k = 5\) anchors, not 5 or 1000 classes. Another trap is to expect the regression head to output boxes directly — it outputs deltas from anchors, and skipping the anchor-addition step misplaces every box.

Anchors enumerate shapes, the classification head picks foreground, the regression head trims to truth, and the combined loss trains both jointly. With single-object shape solved, the remaining problem is many objects with identities, which is where multi-object tracking begins.

Warehouse robots use this two-head pattern to pick boxes of varied aspect off conveyors without rescanning at five zooms.

11.9.1 Student Questions and Answers

Q: Why 4k values for regression? A: Because four offsets are regressed per anchor — delta x, delta y, delta w, delta h — and there are k anchors, so 4 times k values per location. With \(k = 5\) that is 20 numbers per cell. Classification gives two scores per anchor (foreground and background), hence 2k, or 10 per cell.

Q: Is five anchor boxes a fixed standard? A: No, it is a hyperparameter. There are only so many aspect ratios a camera setup produces, so the anchors are chosen from the expected acquisition hardware: what input device is used and what aspect ratios it yields determines the anchor set. Five is the usual choice, not a law — three under-covers tall players, seven risks overfitting.

Q: Here does k mean the number of classes? A: No. Here k is the anchor count (five anchors per location), not the classification category count. The ImageNet thousand-class mention was only an analogy for how the 2k and 4k counts arise. In tracking there are just two classes — foreground and background — times k anchors.

11.10 Multi-Object Tracking: Identities, Entry, Exit, and Occlusion

What changes when five players share the frame instead of one ball? Boxes are no longer enough — each box needs a durable name, a lifespan, and a defense against swaps.

One ball needs only positions; five players need names that survive crossings, substitutions, and bodies blocking bodies. Which box in this frame continues which name from the last frame?

Multi-object tracking (MOT) generalizes tracking to scenes with many objects of interest: detect all of them, build a trajectory for each, and keep a consistent label or identity per object. The basketball example carries the idea: several players share the frame, and the output must say that player 5 moved in this direction across these frames — not just that some person was somewhere. Each track therefore holds a bounding box plus an identity, and the box history for a track runs from the frame the person entered to the frame they exited. If player 5 is present from frame 1 to frame 300, the track records exactly that span. Like a teacher taking attendance each period and carrying each name forward, MOT keeps one roll call per identity across time.

11.10.1 Entry, Exit, and Re-Entry

Real games complicate this because players substitute and re-enter: player 5 may be visible for a stretch, leave the camera viewpoint (while still on the court), and come back later as the same player 5. The track must therefore maintain entry and exit states per identity rather than assuming one continuous appearance. A practical state machine holds tentative (seen once, awaiting confirmation over about three frames), confirmed (linked repeatedly), and deleted (unseen beyond a maximum age such as 30 frames) — a genuinely returning player then reopens or re-links rather than stealing another identity. Occlusion is now a severe, viewpoint-driven challenge: one player behind another is still in the frame, but only partly visible (partial occlusion) or fully hidden (full occlusion), and because nearer objects look larger, the chance that a near player occludes a farther one is high. A pick-and-roll where the screener's torso covers the ball-handler for six frames is partial occlusion turning briefly full.

Scope: entry-exit logic fits fixed-camera scenes with known borders and brief viewpoint gaps. Assumption: re-entry within the age limit with similar appearance is the same identity. Long bench stays or jersey changes break the assumption and need explicit re-identification.

11.10.2 Occlusion and Identity Switches

Identities cannot rely on physical tags — players do not run with stickers on their heads — and the obvious shortcut, jersey numbers, fails because numbers are large on the back but small or invisible from the front, so front and back views of the same player look completely different. The dominant failure is the identity switch: two players cross paths, the tracker holds P1 and P5 correctly until the crossing point, and afterward swaps them. Picture P1 driving left-to-right and P5 cutting right-to-left: at the crossing frame their boxes merge, and after separation the left-moving box wrongly keeps the P1 label. The same failure appears in crowd management, where one person disappears easily or two people look alike. A single identity can thus collect multiple labels over time through misdetection or failed association: the boxes are right but the linkage is wrong. This is the boxes-right-linkage-wrong signature — per-frame detection scored well while trajectories scored poorly.

A common trap is to judge MOT by detection accuracy alone: perfect boxes with swapped names still fail every downstream question about who went where. Another trap is to trust jersey numbers as IDs: numbers are viewpoint-gated features, present from behind and absent from the front.

MOT adds names, lifespans, and swap resistance on top of boxes. Splitting the job into per-frame detection plus cross-frame association isolates the hard part — linking — which the cost-minimization formulation tackles next.

Airport apron tracking faces identical swaps when two fuel trucks cross behind an aircraft; marathon timing mats add entry-exit gates for the same reason.

11.11 Tracking by Detection: Association as Cost Minimization

If detection already gives all boxes, what exactly remains? Deciding which box continues which track — an assignment problem with a price for every possible pairing and a rule that each box and each track is used exactly once.

Five tracks meet five new boxes: who goes with whom, and who is the stranger that needs a brand-new name? Price every pairing by overlap plus appearance, then buy the cheapest legal set of pairs.

The easiest multi-object approach splits the problem into two stages. Stage one is plain per-frame object detection, producing bounding boxes in frame one, two, three, four, five, and so on. Stage two is association: linking those boxes across frames into tracks, like forming a linked list through time, using the fact that an object stays near where it was. Detection can use any detector; the challenge sits entirely in association. This tracking-by-detection split is the leading practical paradigm because detector progress transfers directly while the linker stays small and fast.

11.11.1 The Association Question

The association question is concrete. Suppose five players were tracked as identities P1 through P5, and behind the camera's back a substitution happens. After frame 100, P5 is missing and a new detection appears that matches none of the old tracks. Working in frame 101 with five detections, each detection must be assigned: does the first detection go to track one or to some other track? A new person needs a new track; every detection in each frame must land on exactly one track, old or new. So the two constraints are that each detection belongs to only one track, and each track maps to only one detection. Like seating five guests at five labeled chairs with one newcomer and one empty chair, every guest sits exactly once and no chair takes two guests.

11.11.2 Mathematical Formulation

Data association (choosing the cheapest one-to-one pairing of tracks to detections, written as a binary matrix \(A\), with value like \(A_{2,4} = 1\) meaning track 2 takes detection 4) is a constrained minimization. Let \(A_{ij} \in \{0, 1\}\) be the association variable: one if detection \(j\) is assigned to track \(i\), zero otherwise — for example P1-to-track-1 is one while P1-to-track-2 and P1-to-track-3 are zero. Let \(C_{ij}\) be the cost of that pairing. The objective is the weighted sum:

\[ \min_{A} \sum_{i} \sum_{j} C_{ij} \, A_{ij} \]

subject to each detection used once \(\sum_i A_{ij} = 1\) and each track used once \(\sum_j A_{ij} = 1\). In words: "we are going to minimize this cost times association across all the i's and j's — assignment is either zero or one because one detection has only one track and one track has only one detection." A worked micro-reading: with two tracks and two detections, costs \(\begin{bmatrix}0.1 & 0.9\\0.8 & 0.2\end{bmatrix}\), the diagonal pairing costs 0.3 while the off-diagonal costs 1.7, so the diagonal wins.

11.11.3 Cost Terms and Solvers

The cost itself has two parts multiplied together. The first is the IOU distance from the track's box and the detection's box: compute the IOU overlap and subtract from one:

\[ C_{\text{IOU}}(i, j) = 1 - \text{IOU}(\text{box}_{\text{track } i}, \, \text{box}_{\text{detection } j}) \]

A worked reading: IOU 0.8 gives cost 0.2 (nearby, cheap), while IOU 0.1 gives cost 0.9 (far, expensive). The second is the appearance cost: take the feature vectors of the track and the detection, compute their cosine similarity, and subtract from one:

\[ C_{\text{app}}(i, j) = 1 - \cos(\text{feat}_{\text{track } i}, \, \text{feat}_{\text{detection } j}) \]

where the cosine operates on unit-normalized appearance descriptors, so identical looks give similarity 1 and cost 0. A worked reading: cosine 0.9 gives cost 0.1, cosine 0.2 gives cost 0.8. The combined cost is the product \(C_{ij} = C_{\text{IOU}}(i, j) \times C_{\text{app}}(i, j)\), and minimizing the association-weighted sum of this product gives the total assignment cost. The accompanying verbal explanation is: "take the product of these two and try to minimize the sum of the cost times the association — that will give you the total cost." The product matters: a pair must be both nearby and similar-looking to be cheap, so a nearby stranger or a far lookalike each pays highly. Richer online systems add motion gating (Mahalanobis distance with a chi-square gate) and blend costs as \(\lambda d_{\text{motion}} + (1-\lambda) d_{\text{app}}\) with cascade priority to young tracks; the lecture's product form is the clean teaching core of that family.

Several solvers exist for this matching: simple greedy matching (fast but naive), the Hungarian algorithm, network-flow or optimum-cost-flow formulations, and deep-learning-based matching. Greedy picks the cheapest pair first and can trap itself; the Hungarian algorithm guarantees the minimum total; flow formulations extend to whole batches offline. The Hungarian algorithm is taken up in detail next; the SORT tracker, which builds on exactly this association machinery, is announced as the next topic.

Scope: one-to-one assignment fits frames where each object yields exactly one detection. Assumption: detections are deduplicated and tracks are gated to plausible neighbors. Under heavy duplicates or long occlusions the square assignment breaks and needs new-track birth plus old-track death logic around it.

Picture the cost visual: a table with tracks as rows and detections as columns, low costs glowing along the intended diagonal. The axes are track index and detection index; cell values are combined costs. The landmark is the all-low diagonal versus one bright off-diagonal trap. The takeaway is that the cheapest legal full set, not the single cheapest cell, wins.

A common trap is to match each detection to its nearest track independently: two detections grab the same track and one track starves. Another trap is to add IOU and appearance costs when the lecture multiplies them — follow the product form on the exam.

Association prices every track-detection pair by overlap times appearance and buys the cheapest one-to-one set. Computing that cheapest set exactly is the Hungarian algorithm's job next.

Ride-share dispatch solves the same assignment nightly: drivers are tracks, riders are detections, pickup time is cost, and each side pairs exactly once.

11.11.4 Student Questions and Answers

Q: When a new detection matches nothing, do we force it onto an old track? A: No. Every detection must sit on exactly one track, but that track may be a newly opened one. A genuinely new person starts a new track instead of corrupting an existing identity. In practice the birth stays tentative for about three frames and dies if never re-matched, so detector flashes do not become permanent ghosts.

11.12 Solving the Assignment: The Hungarian Algorithm

How is the cheapest legal pairing actually computed without trying every permutation? The Hungarian algorithm reduces rows and columns to expose zeros, covers them, and reads the optimum off the zero pattern.

With three tracks and four detections there are dozens of legal sets — which set is provably cheapest? Subtract row and column minima until zeros mark the bargain cells, then cover and check.

The Hungarian algorithm was defined for the worker-task problem and transfers directly: workers become tracks, tasks become detections. With \(M\) detections and \(N\) tracks, each pair carries a cost \(C_{ij}\), and the task is to map each detection to one track minimizing total cost. The picture is a bipartite graph: detections form one set of nodes, tracks the other, edges carry the weights \(C_{ij}\), and the goal is the minimum-weight perfect matching under the one-to-one restriction. Like assigning three chefs to four orders where each chef takes one order and each chosen order goes to one chef, the graph forbids double-booking either side.

The steps are: start from the input cost matrix, do row reduction, do column reduction, cover the zeros with the minimum number of lines, run the optimality check, and update the matrix. The worked example makes each step concrete. The input is the cost matrix with tracks as rows \(i\) and detections as columns \(j\) (rows R, columns C). For row reduction, take each row's minimum — here 2, 1, and 2 — and subtract it from that row (R2 minus 1, R3 minus 2), which creates zeros; three zeros appear. For column reduction, take each column's minimum — here 0, 0, and 2 for the relevant columns — and subtract it from that column (C1 minus 2, C4 minus 2, others minus 0). Many more zeros appear. Then cover all zeros with the fewest lines: here three lines suffice, which signals optimality for the three tracks. Reading off the assignment gives detection 2, detection 3, and detection 4 matched to the three tracks at minimum cost, and summing those entries gives the total assignment cost. The closing remark is that all three tracks now have detections associated with them at the minimized total.

Row and column reduction (subtracting each row's then each column's minimum, written as matrix updates, with value like row minima \(\{2, 1, 2\}\)) preserves the optimal assignment while manufacturing zeros. Zero covering (drawing the fewest lines through all zeros, with value like three lines for three tracks) tests optimality: lines equal rows means the zero pattern already holds a complete cheapest pairing.

A full trace on the lecture's numbers runs as follows. Start from the input cost matrix. Row step: subtract 2 from row one, 1 from row two, 2 from row three — one zero per row, three zeros total, all entries non-negative. Column step: subtract each column minimum (0, 0, 2 on the relevant columns) — the matrix densifies with zeros. Cover step: the minimum line cover uses three lines, matching the three tracks, so the assignment is optimal and no matrix-update iteration is needed. Readout: detections 2, 3, and 4 pair with the three tracks, and their original costs sum to the minimum total. If cover lines had numbered fewer than rows, the standard update would subtract the uncovered minimum from uncovered cells and add it to doubly covered cells, then repeat — that loop is what guarantees termination at the optimum.

Scope: the Hungarian method fits small per-frame assignment with a complete cost table. Assumption: costs are finite and the matrix is prepared with gating (infeasible pairs set to a large cost) plus dummy handling for births and deaths. With hundreds of tracks, cubic complexity bites and cascade or greedy shortcuts trade optimality for speed.

A common trap is to stop after row reduction: without column reduction and covering, zeros may still admit no complete pairing. Another trap is to assign each row its first zero independently — two rows sharing one zero column need the covering logic to arbitrate.

Reduce rows, reduce columns, cover zeros, check count, read the pairing — three lines for three tracks certifies the cheapest track-to-detection set. That certified pairing is the engine inside SORT-style trackers previewed as the next topic.

Airlines solve crew-to-flight rostering with the same reducer: subtract, cover, and the cheapest legal roster drops out.

Example 1 — row reduction. Cost matrix rows have minima 2, 1, 2. Subtract each row's minimum from that row: row one minus 2, row two minus 1, row three minus 2. Result: one zero per row, three zeros total, with all entries non-negative. Sense-check: every row now contains at least one zero and no negative entry exists.

Example 2 — column reduction. In the row-reduced matrix the column minima are 0, 0, and 2 (for columns C1 through C4 as applicable). Subtract each column's minimum from that column. Result: a matrix dense with zeros, ready for zero-covering. Sense-check: every column now contains at least one zero.

Example 3 — zero covering and readout. The minimum line cover of all zeros uses three lines, matching the three tracks, so the assignment is optimal. Key Industry Applications

Sports analytics and officiating tracks players and the single ball for analysis, per-player strategy changes, and third-umpire style decisions; keyframe-only detection is insufficient here because every frame matters, and Siamese plus flow-warped detectors hold identities through blur at broadcast frame rates.

Detector deployment practice fine-tunes pre-trained YOLO and R-CNN family models (Fast R-CNN, Mask R-CNN) on deployment data to handle motion blur, occlusion, and scale variation; heavyweight backbones (EfficientNet, ResNet, Swin Transformer) are reserved for offline review, while AlexNet to ResNet-50 serve as Siamese embedding backbones and SiamRPN one-shot kernels give shape-accurate boxes without per-video retraining.
