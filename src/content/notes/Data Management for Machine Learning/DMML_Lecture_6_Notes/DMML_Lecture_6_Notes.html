Chapter 1: Introduction to Data Management for ML

6.1 Course Objectives

This course introduces the end-to-end data analysis pipeline for machine learning workloads on modern cloud platforms. The pipeline spans six essential stages that transform raw data into actionable business value:

🔑 The Six-Stage Data Pipeline for ML

  1. Data Collection — Ingesting raw data from diverse sources, including APIs, databases, streaming platforms, file uploads, IoT sensors, and third-party providers. In cloud architectures, this often involves services like AWS Kinesis (streaming), AWS DMS (Database Migration Service), or direct S3 uploads.
  2. Data Storage — Persisting large volumes in scalable, cost-efficient stores. The choice of storage medium (object store like S3, relational database like RDS, NoSQL like DynamoDB, or data warehouse like Redshift) depends on access patterns, latency requirements, and cost constraints.
  3. Data Analysis & Exploration (EDA) — Understanding distributions, correlations, and quality issues before modelling. This stage answers questions like "What is the range of trip distances?", "Are there missing values in fare_amount?", and "How are different payment types distributed?" Tools include Athena SQL, Python with Pandas in SageMaker notebooks, and visualisation tools like QuickSight.
  4. Data Cleaning & Correction — Handling missing values, outliers, and inconsistencies. For example, a taxi trip with a negative fare or a trip_distance of zero miles is likely erroneous and must be addressed. Strategies include imputation, filtering, and transformation.
  5. Data Processing & Transformation (ETL) — Converting raw data into ML-ready features. This includes feature engineering (creating derived columns like trip duration from pickup/dropoff times), normalisation, encoding categorical variables, and aggregating data at the right granularity for model training.
  6. Delivery to Business Objectives — Serving insights or model predictions to stakeholders. This could mean publishing a dashboard in Amazon QuickSight, exposing a model endpoint via SageMaker for real-time predictions, or generating scheduled reports delivered to business teams.

The curriculum balances theoretical foundations (data models, query languages, platform architectures) with practical, hands-on labs on AWS. Each lab session maps directly to one or more stages of this pipeline, ensuring students develop both conceptual understanding and operational skill.

6.2 Why Big Data Needs New Tools

Modern ML applications consume Big Data, characterised by the classic 3 V's (originally introduced by Doug Laney in 2001) and now commonly extended to 5 V's to capture the modern data landscape more completely:

📘 The 5 V's of Big Data

Volume — The sheer scale of data
Modern organisations routinely manage terabytes to petabytes of data. For context, a single New York City taxi dataset for one year can exceed 100 GB in raw CSV format. Multi-year, multi-city datasets can reach petabyte scale. Traditional RDBMS (Relational Database Management Systems) like PostgreSQL or MySQL, designed for single-server deployments, cannot scale economically to this level — they require expensive vertical scaling (bigger machines) rather than horizontal scaling (more machines). Cloud object stores like S3 handle petabyte scale as a matter of routine, with automatic replication and 99.999999999% (eleven 9's) durability.
Velocity — The speed of data arrival
Data arrives in real time (streaming) or near-real-time batches. Consider a ride-sharing platform: trip events, GPS pings, payment confirmations, and user ratings flow continuously. A traditional nightly ETL batch process cannot keep up. Streaming architectures using Apache Kafka, AWS Kinesis, or Apache Flink process data within milliseconds to seconds of arrival, enabling real-time dashboards, fraud detection, and dynamic pricing.
Variety — The diversity of data formats and structures
Data spans three broad categories: structured (tabular data in relational databases), semi-structured (JSON, XML, Avro — data with a flexible schema), and unstructured (text documents, images, video, audio). An ML pipeline for a taxi service might ingest structured trip records (CSV), semi-structured API responses (JSON), and unstructured data like driver photos or customer review text. A data lake accommodates all of these in their native formats.
Veracity — The uncertainty and quality of data
Not all data is trustworthy. Sensors malfunction, users enter incorrect information, and data pipelines introduce errors. In the taxi dataset, you might encounter trip_distances of zero, negative fares (data entry errors), or GPS coordinates in the middle of the ocean (sensor glitches). Veracity addresses the need for data quality assessment, cleaning, and provenance tracking so that models are not trained on misleading inputs.
Value — The actionable insight extracted
Value is the ultimate goal. All the infrastructure, storage, and processing is worthless unless it leads to better decisions, improved user experiences, or increased revenue. Value might mean identifying that credit card customers tip 20% more than cash customers (allowing targeted promotions), or predicting which drivers are likely to churn (enabling proactive retention). The cost of the data infrastructure must be justified by the value it enables.

Conventional tools designed a decade ago — single-server relational databases, on-premises Hadoop clusters requiring manual provisioning, and desktop-based ETL tools — are unsuitable for this scale along all five dimensions simultaneously. Cloud platforms like AWS provide managed, serverless, and auto-scaling services purpose-built for big-data workloads. The key shift is from owning and operating infrastructure to consuming data services on demand.

💡 Why "Cloud-Native" Matters Here

A cloud-native data architecture exploits three fundamental properties of the cloud: elasticity (scale up or down automatically based on load), managed services (the provider handles upgrades, patching, and redundancy), and pay-per-use pricing (no upfront hardware investment). This means a data pipeline that costs $50/month when idle can scale to $5,000/month during heavy processing — and you only pay for what you use.

Chapter 2: Amazon S3 — The Data Lake Foundation

6.4 What is Amazon S3?

Amazon Simple Storage Service (S3) is an object storage service that offers industry-leading scalability, data availability, security, and performance. Launched in 2006 as one of the very first AWS services, it is now the most common choice for building a data lake on AWS. S3 is fundamentally different from a file system or a block storage device: it is an object store, meaning you store entire objects (files) along with their metadata, and retrieve them via HTTP/HTTPS APIs using a unique key.

📘 Data Lake — Definition

A data lake is a centralised repository that stores all structured and unstructured data at any scale, in its native raw format. Unlike a data warehouse, which imposes a schema on write (you must define the table structure before loading data), a data lake uses schema on read (the schema is applied when you query the data, not when you store it). This distinction is fundamental:

  • Schema on Write (Data Warehouse): You must know the exact structure upfront. Loading data is slower and more rigid, but querying is fast and predictable. Think: Amazon Redshift, Snowflake. This is analogous to static (compile-time) type checking in programming languages — errors are caught at write time, before data enters the system.
  • Schema on Read (Data Lake): You dump raw data as-is. When you query, the engine interprets the schema. This is more flexible (you can reinterpret data later) but can be slower if not optimised with partitioning and columnar formats. Think: S3 + Athena. This is analogous to dynamic (runtime) type checking — the schema is implicit in the data and only interpreted when read. The trade-off: schema-on-read accommodates heterogeneous data (different records with different structures) and evolving schemas, but provides weaker guarantees about data consistency.

Real-world analogy: A data warehouse is like a filing cabinet where every document must be filed in the correct folder before it can be retrieved. A data lake is like a warehouse where you dump everything with a label, and you decide how to organise it later when you need it.

6.4.1 Key S3 Concepts

To work effectively with S3, you need to internalise four foundational concepts. These appear in every S3 interaction and form the vocabulary of data engineering on AWS:

  • Bucket — A logical container for objects. Bucket names are globally unique across all AWS accounts — no two AWS customers can have the same bucket name. This is because S3 bucket names form part of the DNS hostname (bucketname.s3.amazonaws.com). A single AWS account can create up to 100 buckets by default (soft limit, can be increased). Buckets are the top-level namespace; all objects live inside exactly one bucket.
  • Object — The fundamental entity stored in S3, consisting of three parts: (1) the data itself (the file contents — any sequence of bytes, from a few bytes to 5 TB per object), (2) metadata (key-value pairs describing the object, such as content type, creation date, and custom tags), and (3) a unique key (the identifier). Objects are immutable — to "modify" an object, you must upload a new version with the same key (if versioning is enabled, both versions are preserved). This immutability is a deliberate design choice: because S3 does not need to support in-place overwrites, locks, or change synchronisation, it can distribute data across thousands of disks and achieve massively parallel reads and writes. If versioning is enabled, old versions of an object are preserved with separate version IDs; the default key reference always points to the latest version. The trade-off is storage cost — each version stores the full object data, not a differential snapshot. Lifecycle policies can automatically expire old versions after a configurable period.
  • Key — The unique identifier (path) of an object within a bucket. Despite looking like a file path, it is simply a string. For example, taxi-data/2017/01/data.csv is just a single string that looks like a file path. The forward slashes have no special meaning to S3 itself, but tools like Athena and Glue can interpret them as partition boundaries — this is the foundation of partitioning. Keys are case-sensitive and can be up to 1024 bytes of UTF-8. Internally, S3 is a key-value store: it uses the key to locate the object, not a directory tree traversal. Operations like aws s3 ls that appear to list a "directory" are actually prefix-based key filters — potentially expensive on buckets with millions of objects.
  • Region — Buckets reside in a specific AWS geographic region (e.g., us-east-1, ap-south-1, eu-west-1). This decision matters for two practical reasons: latency (data closer to users and compute is faster to access) and compliance (some regulations like GDPR require data to stay within specific geographic boundaries). Objects are never replicated across regions unless you explicitly configure cross-region replication.

💡 Object Storage Internals — Why S3 Is So Durable and Scalable

Understanding why S3 achieves eleven 9's of durability helps you make informed architectural decisions. S3 distributes objects across multiple independent availability zones (physically separated data centres within a region). This is an example of distributed storage: instead of writing to a single disk on a single server, S3 replicates each object to at least three zones. Even if an entire zone goes offline (power failure, natural disaster), your data survives in the remaining zones.

Under the hood, S3 uses thousands of magnetic hard disk drives (HDDs) in clusters. Individual HDDs are cheap (~$0.03/GB) but relatively slow for random access (~4 ms latency, 50–500 IOPS). S3 compensates for individual disk slowness through massive parallelism: when you read an object, S3 reads from many disks simultaneously, achieving aggregate bandwidth of ~10 GB/s per connection. This is the same principle used in columnar databases like Redshift — parallelise across many disks to overcome the limitations of any single disk.

S3 offers strong read-after-write consistency (since December 2020): after a successful PUT, any subsequent GET will immediately return the new object. This was an upgrade from the previous eventual-consistency model and eliminates a major source of subtle bugs in data pipelines.

💡 The Lifecycle of ML Data in S3

In a mature ML pipeline, data naturally progresses through storage classes over its lifetime: Raw ingested data starts in S3 Standard (frequent access during initial EDA). After initial exploration, it may move to S3 Intelligent-Tiering (accessed less predictably). Old model training datasets and checkpoints eventually transition to S3 Glacier for archival (retained for model reproducibility, but rarely read). AWS S3 Lifecycle Policies automate these transitions based on object age — for example, transitioning objects to Glacier after 90 days of no access.

📝 Exam Note — S3's Dual Role

In the lab, S3 serves two distinct roles: (1) the source where the raw Yellow Taxi CSV data already resides, and (2) the destination where Athena writes its query results. Always remember: Athena is serverless — it has no built-in storage; you must configure an S3 output location. This is one of the most common configuration errors and a frequently tested exam concept. Think of S3 as the "disk" for Athena's serverless brain — without it, Athena has nowhere to write.

Chapter 3: AWS Glue — Metadata Catalog and ETL

6.5 What is AWS Glue?

AWS Glue is a fully managed ETL (Extract, Transform, Load) service. While the acronym "ETL" traditionally refers to moving and transforming data, in the Glue ecosystem it encompasses three distinct capabilities that together form the metadata and transformation backbone of a data lake:

  1. Glue Data Catalog — A persistent, Hive-compatible metadata repository that stores table definitions (schema, location, partition keys, serialisation formats). This is the central nervous system of the architecture. Every service that needs to understand what data is in S3 and how it is structured — Athena for querying, Redshift Spectrum for data warehouse queries, EMR for Spark jobs — reads from the same Glue Catalog. This shared metadata eliminates the problem of each tool maintaining its own, possibly inconsistent, schema definitions. Think of it as the card catalog in a library: the catalog tells you where each book is, what it is about, and how it is classified, but it does not contain the books themselves.
  2. Glue Crawlers — Automated agents that scan data in S3, infer schemas by examining the actual data, detect partitions based on key patterns (e.g., year=2017/month=01/), and populate the Data Catalog. Without crawlers, you would need to manually write a CREATE TABLE statement for every new dataset — impractical at scale. Crawlers handle format detection (CSV vs. JSON vs. Parquet), delimiter detection, and data type inference (string vs. int vs. timestamp).
  3. Glue ETL Jobs — Apache Spark-based jobs that transform data using Python or Scala scripts. These are auto-generated or custom-coded transformations that can clean, join, aggregate, and reshape data before it is used for ML. Glue ETL Jobs run on a managed Spark cluster — you provide the transformation logic, and Glue handles cluster provisioning, scaling, and teardown.

💡 ETL vs. ELT — Where Glue Fits in the Modern Pipeline

The traditional ETL (Extract → Transform → Load) pattern transforms data before loading it into the warehouse — necessary when the warehouse lacks the compute power to transform raw data in-place. Modern cloud data warehouses (Snowflake, Redshift, BigQuery) are columnar and massively parallel, enabling the ELT (Extract → Load → Transform) pattern: raw data is loaded first, then transformed inside the warehouse using SQL. ELT has become the dominant pattern because it separates responsibilities — data engineers focus on ingestion (extract + load), while analysts and analytics engineers own transformations in SQL they are comfortable with.

A common refinement is the EtLT sub-pattern (note the lowercase t): a lightweight transformation step between extraction and loading. This lowercase-t transformation handles tasks that are best done early — deduplication, URL parsing, masking sensitive data (e.g., PII for GDPR compliance) — without involving business logic. Glue ETL Jobs can serve as this lightweight in-flight transformation layer, preparing data for efficient warehouse loading.

In this lab's architecture, AWS Glue serves as the ETL backbone that extracts data from S3 (via the Data Catalog), applies transformations (via ETL Jobs), and loads cleaned data back to S3 or into a data warehouse. Athena then serves as the interactive query layer for ad-hoc exploration — an example of the ELT pattern where transformations can happen in-place using SQL.

6.6 Glue Database and Tables

📘 Glue Database — Logical Metadata Container

A Glue Database is a logical container (like a namespace) that organises related tables within the Glue Data Catalog. It does not store data; it stores metadata about data. This distinction is critical and widely misunderstood:

Intuition: If S3 is a warehouse full of boxes, the Glue Database is the inventory spreadsheet that says "Box #4521 contains 2017 taxi data, columns are: pickup_datetime (TIMESTAMP), trip_distance (DOUBLE), etc., and it is located at aisle 3, shelf B." You never open the inventory spreadsheet to find actual taxi records — you open it to find where to look.

6.6.1 Creating a Database (SQL in Athena)

In the lab, the database is created via Athena's query editor using standard Hive DDL (Data Definition Language). Hive DDL is used because the Glue Data Catalog is built on the Apache Hive metastore protocol — the same metadata standard used across the Hadoop ecosystem.

CREATE DATABASE taxi_data;

This single statement registers a new namespace called taxi_data in the Glue Data Catalog. All subsequent table definitions will live under this namespace. The database name becomes the prefix in fully qualified table references: taxi_data.yellow means "the table named yellow inside the database named taxi_data."

The CREATE TABLE statement in Athena uses the EXTERNAL keyword because the data lives outside the query engine — in S3. This is a fundamental concept:

🔑 EXTERNAL vs. MANAGED Tables

In the Hive/Hadoop ecosystem (from which Athena inherits its DDL), tables are either EXTERNAL or MANAGED (also called "internal"). An EXTERNAL table means: "I am defining a schema for data that already exists at this S3 location. If I drop this table, only the metadata definition is deleted — the actual data in S3 remains untouched." A MANAGED table would mean: "I own this data. If I drop this table, delete the data too." In Athena, all tables are effectively external because Athena is a query engine, not a storage engine — it never owns the data. The EXTERNAL keyword is explicit documentation of this fact and is considered best practice.

Line-by-line explanation:

  • IF NOT EXISTS — Idempotency guard: if the table already exists, don't throw an error. Essential for repeatable deployment scripts.
  • ROW FORMAT DELIMITED — Tells Athena that each row is separated by a newline and fields within each row are separated by a delimiter character.
  • FIELDS TERMINATED BY ',' — Specifies the delimiter as a comma (CSV). Could also be tab ('\t'), pipe ('|'), etc.
  • STORED AS TEXTFILE — The data is plain text (human-readable). Alternatives include PARQUET, ORC, AVRO, and JSON. Text is simple but the least efficient for query performance. In production data lakes, Parquet is the dominant choice: it is a binary, columnar format that achieves 5–10× compression over CSV through dictionary encoding, run-length encoding, and delta encoding. Parquet also embeds its schema in the file footer, making it self-describing — a reader can determine the column structure without external metadata. This is an example of a serialization format decision: the format you choose for storing data in S3 directly impacts Athena query cost, compression ratio, and schema evolvability.
  • LOCATION 's3://...' — The S3 path where the actual CSV files reside. This is where the data physically lives. The Glue Catalog only stores a pointer to this location.

⚠️ Common Pitfall — Wrong Database

Always qualify your table with the correct database name (taxi_data.yellow). If you accidentally create a table under the default database (by omitting the database prefix or not running USE taxi_data; first), it becomes default.yellow. Later, when queries reference taxi_data.yellow, Athena will respond with "table not found" — not because the table doesn't exist, but because it exists in a different namespace. This is one of the top five student mistakes in the lab. The fix: either qualify correctly, or use USE taxi_data; to set the current database context before creating tables.

6.6.3 Glue vs. DataBricks - Clarifying a Student Query

A student asked whether the lab uses DataBricks in the backend. The answer is no. While DataBricks is another popular platform for big-data analytics (built on Apache Spark and offering a unified analytics workspace with collaborative notebooks), this lab uses purely AWS-native services: S3 for storage, Glue for cataloging, and Athena for querying. Both ecosystems solve similar problems — the key difference is that the AWS-native stack is more deeply integrated with the broader AWS security, monitoring, and billing infrastructure. Understanding this lab's architecture gives you the foundation to evaluate when you might prefer one approach over the other in industry settings.

Chapter 4: Amazon Athena — Serverless Interactive Queries

6.7 What is Athena?

📘 Amazon Athena

Amazon Athena is a serverless, interactive query service that lets you analyse data directly in Amazon S3 using standard ANSI SQL. There is no infrastructure to manage — you do not provision servers, install software, or manage clusters. You point Athena at your data, write a SQL query, and get results in seconds to minutes, depending on data volume.

Athena is built on Presto (now known as Trino after the 2020 community fork), an open-source distributed SQL query engine originally developed at Facebook to handle petabyte-scale analytics across heterogeneous data sources. Presto/Trino was designed from the ground up to separate compute from storage — it is a query engine with no built-in storage, which is why Athena needs S3 for both reading data and writing results.

Athena supports many data formats natively: CSV, JSON, ORC, Parquet, and Avro. The choice of format has a dramatic impact on both query performance and cost, because:

  • CSV is row-oriented and uncompressed (or Gzip compressed, but not splittable) — Athena must scan every byte of every column, even if your query only uses two columns.
  • Parquet and ORC are columnar and compressed — Athena can read only the specific columns referenced in your query, and the compression (Snappy, Gzip, Zstd) reduces storage and scan volume.

💡 Row-Oriented vs. Column-Oriented Storage — Why It Matters for Athena

The physical layout of data on disk determines query performance. In row-oriented storage (CSV, JSON, traditional RDBMS), all columns of a single row are stored contiguously: [1, Alice, 28, 62000] [2, Bob, 34, 75000] .... This is ideal for transactional (OLTP) workloads — reading or writing an entire record in one I/O operation. However, when an analytical query like SELECT AVG(fare_amount) FROM taxi_data.yellow needs only one column, the row-oriented store must read every column of every row and discard the rest — wasted I/O.

In column-oriented storage (Parquet, ORC), all values of a single column are stored contiguously: fare_amount: [12.5, 8.0, 23.75, ...]. Athena reads only the fare_amount column chunk — a single contiguous block — skipping all other columns entirely. This yields 5–10× less data scanned. Additionally, columnar files achieve superior compression because values within a column share the same data type and often exhibit repetition or limited ranges, enabling efficient encoding (dictionary encoding, run-length encoding, delta encoding).

For the taxi dataset, converting the ~9.32 GB CSV table to Parquet could reduce scan volume to ~1–2 GB for the same queries, further cutting Athena costs by 80–90% beyond what partitioning alone achieves. Best practice for production data lakes: Snappy-compressed Parquet with hierarchical date partitioning.

6.7.1 "Serverless" Meaning - A Refresher

"Serverless" is one of the most misunderstood terms in cloud computing. It does not mean there are no servers. There are always servers — physical hardware somewhere in an AWS data centre — running your query. Serverless means that the user does not:

  • Provision or patch servers — No choosing instance types, no applying OS security patches, no configuring network settings.
  • Manage capacity or scaling — No deciding how many servers to run when or configuring auto-scaling groups. Athena automatically scales to thousands of parallel workers behind the scenes.
  • Pay for idle resources — No paying for EC2 instances sitting idle between queries. You pay only for the data scanned by each query — zero queries, zero cost.

The cloud provider handles all of the above. This shifts the engineering focus from infrastructure management to query and data design. The trade-off: you have less control over exactly how queries execute, but you gain dramatically simpler operations.

💡 Declarative SQL and the Query Optimizer — Why Athena Knows Best

Athena uses declarative SQL: you specify what data you want (via SELECT, WHERE, GROUP BY), not how to retrieve it. This is fundamentally different from an imperative approach where you would write loops, conditionals, and explicit I/O operations. The declarative approach gives Athena's cost-based query optimizer maximum freedom to choose the most efficient execution plan — it can reorder joins, choose between hash joins and merge joins, decide which partitions to scan, and parallelise operations across workers. If you later convert CSV data to Parquet or add a partition scheme, the same SQL query automatically runs faster because the optimizer detects the new structure — no code changes needed.

This separation of "what" from "how" is the same principle that makes SQL superior to imperative database APIs (like the historical IMS/CODASYL approaches). The query optimizer is built once by the engine team and benefits all queries — a general-purpose solution that outperforms hand-tuned access paths over time. For Athena, this means: focus on writing correct SQL with appropriate filters, and trust the engine to execute it efficiently.

6.8 Setting Up Athena - Output Location

Because Athena is serverless, it has no internal disk. You must tell it where to write query results:

  1. In the Athena console, navigate to the Query Editor.
  2. Click the Settings tab.
  3. Under Query result and encryption settings, click Manage.
  4. Browse S3 and select (or create) a bucket for results, e.g., s3://aws-athena-query-results-<account-id>-<region>/.
  5. Click Save.

📝 Exam & Lab Tip

If you skip this step and try to run a query, Athena will throw an error because it has no output location configured. This is a very common first-time mistake. The error message is explicit: "No output location. Please configure an output location in Settings." In production environments, you typically create a dedicated S3 bucket with a lifecycle policy that automatically deletes old query results (e.g., after 7 days) to keep costs manageable — query results are often only needed temporarily.

6.9 Running SQL Queries on Athena

Athena's query editor lets you write and execute SQL statements directly against Glue Catalog tables. The SQL dialect is Presto SQL, which is broadly ANSI SQL-compliant with some extensions. A typical analytical query from the lab:

SELECT DATE(pickup_datetime) AS trip_date,
       SUM(fare_amount) AS total_fare
FROM taxi_data.yellow
WHERE pickup_datetime BETWEEN TIMESTAMP '2017-01-01 00:00:00'
                          AND TIMESTAMP '2017-01-31 23:59:59'
GROUP BY DATE(pickup_datetime)
ORDER BY trip_date;

What this query does: It groups all taxi trips from January 2017 by day, sums the fare amounts for each day, and returns an ordered daily summary. Despite the WHERE clause filtering only January, Athena must scan the entire yellow table (9.32 GB) because there is no partition structure — the engine cannot know ahead of time which S3 files contain January data and which don't.

Result: Scanned ≈ 9.32 GB, returned ≈ 2 million rows, took ≈ 29 seconds.

6.9.1 Athena Pricing Model

Athena charges $5.00 per terabyte of data scanned (at the time of writing; prices may vary by region). This pricing model has a critical implication that shapes every design decision in a production data lake:

🔑 Why Partitioning Matters — It's Literally About Money

Since you pay per byte scanned, not per query and not per row returned, reducing the amount of data Athena must read directly reduces your cost. A query scanning 9.32 GB costs ≈ $0.047 at the $5/TB rate. If you run this query daily for a month, that's ~$1.41. If you run it for every analyst on a team of 10, that's ~$14/month for one query pattern. Multiply across dozens of query patterns and months of data, and unoptimised scan costs can become significant.

The critical insight: The same query on a properly partitioned table might scan 815 MB instead of 9.32 GB — a cost of ~$0.004 instead of ~$0.047. That's over a 91% reduction. For a data engineering team running hundreds of queries daily, the cost difference between a well-partitioned data lake and a flat one can be measured in thousands of dollars per year.

Chapter 5: Query Optimisation — Partitioning Strategies

6.10 Why Partition?

The full yellow table contains data for the entire year (and potentially multiple years). If your analysis only needs January data, scanning the whole table wastes two precious resources:

  • Time — Longer execution due to more I/O. Athena must open and read every S3 object in the table, even those containing December data you don't care about. In distributed systems, I/O is typically the bottleneck, not CPU.
  • Money — Athena charges per byte scanned. Scanning irrelevant data is literally throwing away money.

Partitioning divides a large table into smaller, independent chunks based on the value(s) of one or more columns (partition keys). When a query includes a filter on the partition key, Athena can prune entire partitions — it skips them entirely, never opening those files. This is called partition pruning and is the single most impactful optimisation technique for Athena.

💡 Data Temperature and Partition Design

Partition design is closely related to the concept of data temperature: hot data (frequently accessed, e.g., the current month's taxi trips) should be stored for fast retrieval in S3 Standard, while cold data (historical months rarely queried) can be transitioned to cheaper storage tiers. Hierarchical date partitioning naturally aligns with temperature — recent partitions are queried most often and stay hot, while older partitions are accessed infrequently and can be archived. AWS S3 Lifecycle Policies can automatically transition partition prefixes to cheaper tiers based on the last-access date, completing the cost optimisation loop that partition pruning starts.

💡 How Partition Pruning Works (Under the Hood)

When you partition by year=2017/month=01/, the S3 key structure looks like: s3://bucket/nyc-taxi-data/year=2017/month=01/file1.csv. When Athena receives a query with WHERE month = 1 AND year = 2017, it reads the Glue Catalog partition metadata (which maps each partition to its S3 prefix), identifies that only the year=2017/month=01/ prefix is relevant, and sends requests only to those S3 objects. The other 11 months' worth of data files are never read, never decompressed, never processed. This is not a "sampling" or "approximate" optimisation — it is an exact and lossless optimisation.

6.11 Horizontal Partitioning - By Date (Month)

The first optimisation in the lab creates a table that physically stores only January records by materialising a subset of the full table:

CREATE TABLE taxi_data.jan
WITH (
  format = 'CSV',
  external_location = 's3://your-bucket/taxi/jan/'
)
AS SELECT *
FROM taxi_data.yellow
WHERE pickup_datetime BETWEEN TIMESTAMP '2017-01-01 00:00:00'
                          AND TIMESTAMP '2017-01-31 23:59:59';

This is a CTAS (CREATE TABLE AS SELECT) operation. Unlike the earlier CREATE EXTERNAL TABLE which only registered metadata, CTAS physically copies the filtered data to a new S3 location. The new jan table is its own independent entity with its own S3 files.

Now, querying the jan table for the same aggregation:

SELECT DATE(pickup_datetime) AS trip_date,
       SUM(fare_amount) AS total_fare
FROM taxi_data.jan
GROUP BY DATE(pickup_datetime)
ORDER BY trip_date;

6.12 Vertical Partitioning - By Categorical Column (Payment Type)

The second optimisation partitions by a categorical attribute: payment_type. Despite the name, this is actually horizontal filtering (filtering rows by a column value), not vertical partitioning in the database-normalisation sense (splitting columns). In data lake terminology, any row-based splitting is called "partitioning."

📘 Partitioning by Category — "Sharding" by Attribute

Splitting rows such that each partition contains only rows matching a specific value of a categorical attribute. For example: all credit-card trips (payment_type = 1) in one table, all cash trips (payment_type = 2) in another. This is useful when different consumers consistently query one category — e.g., the fraud detection team always queries credit card trips, while the cash operations team only needs cash trips.

CREATE TABLE taxi_data.credit_card
WITH (
  format = 'CSV',
  external_location = 's3://your-bucket/taxi/credit_card/'
)
AS SELECT *
FROM taxi_data.yellow
WHERE payment_type = 1;   -- 1 = Credit Card

Now, querying for total credit-card fare:

-- From the FULL table (with WHERE clause) — scans 9.32 GB
SELECT SUM(total_amount) AS total_cc_fare
FROM taxi_data.yellow
WHERE payment_type = 1;

-- From the PARTITIONED table (no WHERE needed) — scans only 71 MB
SELECT SUM(total_amount) AS total_cc_fare
FROM taxi_data.credit_card;

Notice an important pattern: the first query on the full table with a WHERE clause still scans the entire table (9.32 GB) even though it only needs credit card rows. This is because there is no partition metadata to tell Athena "credit card rows are only in these specific S3 files." Without partitioning, Athena must scan everything and then filter — scan all, discard most. With partitioning, it scans only what is needed.

📝 Design Principle — Know Your Access Patterns

Partitioning is not free — you must design it upfront. A poorly chosen partition scheme can increase cost if queries often scan many partitions. Before partitioning, ask:

  • Which columns appear most often in WHERE clauses? These are your prime partition key candidates.
  • Which dimensions do users filter by repeatedly? Date ranges are almost always the first partition key for time-series data.
  • Can we partition by date (year/month/day) for time-series workloads? This is the most common pattern — hierarchical date partitioning.
  • Can we partition by category for workloads that always filter by type? Good for stable, low-cardinality categorical columns.

Anti-pattern: Partitioning by a high-cardinality column (e.g., trip_id with millions of unique values) creates millions of tiny partitions, which degrades query planning performance and increases Glue Catalog costs. Rule of thumb: aim for partition sizes in the 100 MB–1 GB range per partition.

6.12.1 Combined Partitioning

For large production tables, you would typically combine both strategies. Hierarchical partitioning uses multiple partition keys: year=2017/month=01/ creates a two-level tree where each month partition is a child of its year partition. Within each date partition, you might further classify data by payment_type:


s3://nyc-taxi-data/
  year=2017/
    month=01/
      payment_type=1/  ← All January 2017 credit card trips
      payment_type=2/  ← All January 2017 cash trips
    month=02/
      payment_type=1/
      payment_type=2/
    ...
  year=2018/
    month=01/
      ...

This enables queries like "total credit card fares for January 2017" to scan only the single most specific subdirectory (year=2017/month=01/payment_type=1/) — maximally efficient pruning. The trade-off is increased complexity in table management and a larger number of S3 objects. This is the foundation of a well-designed data lake table.

Chapter 6: Athena Views — Virtual Tables

6.13 What is a View?

📘 View (SQL) — Virtual Table

A view is a virtual table defined by a stored SQL query. It does not store data physically; each time you query the view, the underlying SQL is re-executed against the base tables. Think of a view as a saved query with a name — a macro that expands to the full query text whenever referenced.

Analogy: A view is like a shortcut on your desktop. The shortcut doesn't contain the actual file data — it just points to where the real file lives. When you double-click the shortcut, the operating system opens the actual file. Similarly, when you query a view, Athena executes the actual query stored in the view definition.

Views are useful when:

  • You have a complex query (joins, aggregates, filters) that is used repeatedly across different analyses and by different team members. Instead of copy-pasting 50 lines of SQL, users write SELECT * FROM my_view.
  • You want to simplify the interface for end users — business analysts who know basic SQL can query SELECT * FROM daily_revenue_summary instead of writing multi-table joins with aggregation logic.
  • You want a logical abstraction that can be updated without changing client code. If the underlying table structure changes, you update the view definition once, and all downstream queries automatically reflect the change (as long as the view's output columns remain the same).

6.14 Creating a View

CREATE VIEW taxi_data.cc_trips AS
SELECT *
FROM taxi_data.yellow
WHERE payment_type = 1;

Now a user can simply:

SELECT * FROM taxi_data.cc_trips;

⚠️ Important — View Performance (Critical Distinction)

A view does not improve query performance by itself! It merely saves the SQL text. When you query cc_trips, Athena still executes SELECT * FROM taxi_data.yellow WHERE payment_type = 1 against the base table, and it still scans the entire yellow table (~9.32 GB). The view provides interface simplification but zero performance benefit.

To get actual performance benefits, you must use partitioned tables (as shown in Chapter 5), not views. This is the #5 most common student mistake: assuming a view with a filter is as fast as a partitioned table. It is not.

6.15 Complex Views - Joins and Aggregates

Views become especially powerful when they encapsulate multi-table operations. Here is a view that creates a pre-aggregated comparison of credit card vs. cash revenue:

CREATE VIEW taxi_data.compare_pay AS
SELECT 'Credit Card' AS payment_method,
       SUM(total_amount) AS total_collected
FROM taxi_data.yellow
WHERE payment_type = 1
UNION ALL
SELECT 'Cash' AS payment_method,
       SUM(total_amount) AS total_collected
FROM taxi_data.yellow
WHERE payment_type = 2;

After creating this view, the user simply runs:

SELECT * FROM taxi_data.compare_pay;

And gets a clean, two-row summary — without writing any unions or aggregations. The complexity is encapsulated once and reused indefinitely.

📝 Views vs. Tables — Decision Guide

CriterionUse a ViewUse a Partitioned Table
Saves storage✅ Yes (no data duplication)❌ No (data copied to new S3 location)
Improves query speed❌ No (re-executes against base table)✅ Yes (scans only relevant subset)

Rule of thumb: Use views for simplicity and abstraction. Use partitioned tables for performance and cost. In production, you often use both — a view that selects from a partitioned table to combine the benefits of both approaches.

Chapter 7: AWS CloudFormation — Infrastructure as Code for Queries

6.16 The Problem: How Does an End User Run a Query?

So far, we have used Athena's interactive query editor — a web console designed for data engineers and analysts who know SQL, understand S3 paths, and are comfortable with the AWS console. But an end user — a business manager named "Mary" who needs a monthly revenue report — should not have to log into the AWS console, write SQL, and configure S3 locations. That is not her job, and it is not a scalable way to deliver data products.

The solution: package the query as a CloudFormation template that can be invoked programmatically via an API or a front-end application. This transforms a hand-crafted SQL query into a managed, version-controlled, auditable infrastructure resource.

6.17 What is AWS CloudFormation?

📘 CloudFormation — Infrastructure as Code

AWS CloudFormation is an Infrastructure as Code (IaC) service that lets you model, provision, and manage AWS resources by writing templates in JSON or YAML. A stack is the collection of resources created from a single template — it is the unit of deployment and lifecycle management.

Think of CloudFormation as: "Describe what resources you want, and AWS will create them in the right order with the right dependencies." You don't write a script that says "step 1: create this, step 2: create that." You write a declarative template that says "I want these resources with these properties," and CloudFormation figures out the correct provisioning order based on resource dependencies. This is the same declarative paradigm that makes SQL powerful for queries: you specify the desired outcome (what), and the engine determines the execution strategy (how). Just as Athena's query optimizer chooses the best execution plan from a declarative SQL statement, CloudFormation's provisioning engine resolves dependency ordering, parallel resource creation, and rollback strategies from a declarative template.

💡 Analogy to Microsoft Azure

If you are familiar with Microsoft Azure, CloudFormation is the AWS equivalent of Azure Resource Manager (ARM) templates. Both allow declarative resource provisioning using JSON templates. The newer AWS CDK (Cloud Development Kit) and Azure Bicep provide higher-level abstractions on top of these foundational IaC services. The concept is universal across cloud providers: define your infrastructure as code, version it in Git, and deploy it repeatably.

6.18 Creating a Named Query via CloudFormation

A Named Query in Athena is a saved SQL statement with a unique ID. It can be referenced and executed by authorised users without them needing to see or modify the SQL. This is the bridge between the data engineer (who writes the query) and the end user (who needs the results).

6.18.1 Step 1 - Write the Template

In the AWS Cloud9 IDE (a browser-based code editor integrated with AWS), create a file named athena-named-query.json:

{
  "AWSTemplateFormatVersion": "2010-09-09",
  "Description": "Athena named query for trips over $100",
  "Resources": {
    "AthenaNamedQuery": {
      "Type": "AWS::Athena::NamedQuery",
      "Properties": {
        "Database": "taxi_data",
        "Description": "Trips where total amount exceeds $100",
        "Name": "Fare_Over_100_USD",
        "QueryString": "SELECT trip_distance, payment_type, fare_amount, tip_amount, tolls_amount, total_amount FROM taxi_data.yellow WHERE total_amount > 100;"
      }
    }
  }
}

Template anatomy:

  • AWSTemplateFormatVersion — Specifies the template language version. "2010-09-09" is the current (and only valid) value.
  • Description — Human-readable description of what this stack does. Essential for maintainability when you have dozens of stacks.
  • Resources — The core section: every AWS resource you want to create, identified by a logical ID (AthenaNamedQuery in this case), with its type (AWS::Athena::NamedQuery) and properties.
  • QueryString — The actual SQL. Note that it must be properly escaped as a JSON string (double quotes inside the SQL escaped as \" in JSON).

📝 Best Practice — Document Your Queries

Always provide a meaningful Description and Name. In production environments, dozens of named queries may exist across multiple databases and teams. Clear naming conventions (Fare_Over_100_USD is much better than query1) prevent confusion and reduce the risk of accidentally modifying the wrong query.

6.18.2 Step 2 - Validate the Template

In the Cloud9 terminal, run:

aws cloudformation validate-template \
  --template-body file://athena-named-query.json

If the template is syntactically correct, AWS returns a JSON response with the template parameters and description. Do not proceed until validation passes. Validation checks for structural correctness (valid JSON), known resource types, and required properties — but does not check whether the SQL itself is valid (Athena checks that when the query is first executed).

6.18.3 Step 3 - Create the Stack

aws cloudformation create-stack \
  --stack-name athena-query-stack \
  --template-body file://athena-named-query.json

This provisions the named query resource. The output includes a Stack ID — an ARN (Amazon Resource Name) that uniquely identifies this deployment. If you later need to update or delete the stack, you reference it by this stack name.

6.18.4 Step 4 - Retrieve the Named Query ID

aws athena get-named-query \
  --named-query-id <query-id>

This returns the query metadata: name, description, SQL string, and database. Save the query ID — it is needed to grant access to end users and to reference the query programmatically from applications. Without it, the named query is effectively invisible.

6.18.5 Step 5 - Store the Query ID in a Variable

In the Cloud9 terminal (Linux/Unix shell):

NQ="<your-named-query-id>"
echo $NQ

⚠️ Shell Syntax Warning

In Bash, there must be no spaces around the = sign:

  • NQ="value" ← correct: assigns the string to the variable NQ
  • NQ = "value" ← error: Bash interprets NQ as a command to run, with = and "value" as arguments, resulting in "command not found"

This is one of the most common shell scripting mistakes, and the error message ("NQ: command not found") can be confusing if you don't know that Bash treats spaces as argument delimiters. Many experienced developers still make this mistake when switching between languages where spaces around = are allowed (Python, SQL, etc.).

Chapter 8: AWS IAM — Identity and Access Management

6.19 Why IAM?

The named query we created in Chapter 7 is only useful if the right users can execute it — and only the right users. Security is not an afterthought; it is a design constraint. AWS Identity and Access Management (IAM) provides fine-grained control over who (identity) can do what (action) on which AWS resources (resource). This triple — principal, action, resource — is the foundation of all AWS access control.

💡 The Shared Responsibility Model — Who Secures What?

AWS operates on a shared responsibility model that divides security into two domains:

  • Security of the cloud (AWS's responsibility): AWS protects the underlying infrastructure — hardware, software, networking, and facilities that run AWS services. This includes the physical security of data centres, the hypervisor layer, and the managed service engines (Athena, Glue, S3).
  • Security in the cloud (your responsibility): You are responsible for configuring IAM policies, encrypting data at rest and in transit, managing access keys, setting S3 bucket policies, and ensuring that your data pipeline follows the principle of least privilege. A misconfigured S3 bucket with public access is your vulnerability, not AWS's.

In this lab, every IAM configuration decision — which users belong to which groups, which policies are attached, which resources are accessible — is your responsibility. AWS provides the tools (IAM, CloudTrail for audit logging, IAM Access Analyzer); you must use them correctly. This mirrors the broader principle: data engineers are implicitly security engineers, and every data pipeline must be designed with security as a first-class concern.

6.20 Core IAM Concepts

📘 The Four IAM Building Blocks

User
An individual identity representing a person or application (e.g., "Mary", "Paolo", "reporting-service"). Each user has long-term credentials: an Access Key ID (public — like a username) and a Secret Access Key (private — like a password). Users are the most granular identity type; every action taken via the AWS CLI or SDK must be authenticated with credentials. Best practice: avoid creating IAM users for human users in production; use IAM Identity Center (formerly AWS SSO) with your corporate identity provider instead.
Group
A collection of users (e.g., "DataScientists", "DataEngineers", "Auditors"). Policies attached to a group automatically apply to all its members. Groups simplify permissions management: instead of attaching the same policy to 20 individual users, you attach it once to the group and add users to the group. Critical rule: groups are not nestable — a group cannot be a member of another group. Users can belong to up to 10 groups.
Role
An identity with permissions, but unlike a user, a role is intended to be assumed temporarily by users, applications, or AWS services. Roles use short-term credentials (automatically rotated, typically valid for 1–12 hours). Roles are the preferred mechanism for granting permissions to AWS services (e.g., allowing an EC2 instance to read S3), for cross-account access, and for federated users. Example: "Allow the reporting Lambda function to assume the AthenaQueryRole to execute named queries."
Policy
A JSON document that defines permissions using Allow or Deny statements on specific resources and actions. Policies are attached to users, groups, or roles. A policy is evaluated at request time; by default, all requests are implicitly denied, and only explicit Allow statements grant access. An explicit Deny always overrides any Allow. This is the least privilege security model.

  • Prefer temporary credentials via IAM Roles whenever possible. They auto-rotate and auto-expire, dramatically reducing the blast radius of a leaked credential.

6.22 Granting Access to the Named Query

6.23 How This Works in a Real Application

In a production web application, the flow extends to a multi-tier architecture:

  1. A front-end user (Mary) logs into the web app through a login page, typically using a corporate identity provider (Okta, Azure AD) federated with AWS IAM Identity Center.
  2. The web app authenticates Mary and maps her identity to her AWS credentials — either by assuming an IAM role scoped to her identity, or through a federation token.
  3. When Mary requests a report (e.g., "Show me trips over $100"), the backend calls the Athena named query using Mary's credentials. Crucially, the query executes under Mary's identity, not a shared service account. This preserves auditability — every query execution is logged in CloudTrail against the actual user who requested it.
  4. Athena performs an authorisation check: Does Mary have:
    • athena:GetNamedQuery permission on this specific named query?
    • athena:StartQueryExecution permission to run queries?
    • glue:GetTable permission on the underlying yellow table?
    • s3:GetObject permission on the source data bucket?
    • s3:PutObject permission on the output results bucket?
  5. If all permissions are present, the query runs and results are returned to the frontend.
  6. If any permission is missing, the request is denied with a descriptive error.

🔑 The Three-Layer Access Model — Summary

Access control for Athena queries requires all three service layers to be correctly configured:

  1. Athena — permission to execute queries (athena:StartQueryExecution) and access named queries (athena:GetNamedQuery).
  2. Glue Data Catalog — permission to read table metadata (glue:GetTable, glue:GetDatabase). Without this, Athena knows there is a named query but cannot resolve what tables it references.
  3. S3 — permission to read source data (s3:GetObject on the data bucket) and write query results (s3:PutObject on the output bucket). Without S3 read, there is no data to query. Without S3 write, results cannot be stored.

Missing any one layer causes a permissions failure. This is the principle of least privilege in action: each service independently enforces its own access boundary. A user who has Athena permissions but no Glue permissions cannot read table schemas and thus cannot meaningfully query anything. This layered security model ensures that permissions are not accidentally granted too broadly.

6.26 Data Validation in the Pipeline - Don't Trust, Verify

A production data pipeline is incomplete without data validation at each stage. The reference text Data Pipelines Pocket Reference (Ch. 8) provides a critical principle: "Validate early, validate often." Leaving validation to the end of a pipeline and tracing failures back to their origin is a worst-case scenario. In the context of this lab's architecture, validation should be applied at three points:

  1. After ingestion (S3 → Glue): Verify that the correct number of rows were loaded, no duplicates were introduced during ingestion, and critical columns contain no unexpected NULLs. For example, if the source system has 10 million taxi trips for January, the Glue-catalogued table should also have 10 million rows — a simple row-count check can catch silent ingestion failures (timeouts, partial loads, parsing errors with special characters).
  2. After transformation (partitioned tables): Verify that partitioned tables (e.g., jan, credit_card) contain the expected subset of rows. A z-score statistical check on daily row counts can flag unexpected drops or spikes — e.g., if yesterday's row count deviates by more than 1.645 standard deviations from the 30-day mean (90% confidence interval), something may have gone wrong upstream.
  3. After view/materialisation: Check that aggregated metrics (total revenue, average fare) fall within expected bounds. A sudden 50% drop in daily revenue is more likely a data quality issue than a real business change — unless it correlates with a known event (holiday, system outage).

In Athena, validation queries can be run as Named Queries via CloudFormation and scheduled via orchestration tools (AWS Step Functions, Apache Airflow). When a validation test fails, the pipeline can halt (for critical issues) or send an alert to a Slack channel (for informational warnings). The decision depends on business context: stale data is usually better than incorrect data.

6.27 ML Pipeline Considerations

When the end-to-end pipeline serves machine learning (not just analytics), several additional steps are required beyond what the lab covers:

  • Data versioning: Training data must be versioned so that models can be reproduced. If you retrain a model next month, you need to know exactly which dataset was used for the previous version. S3 versioning and tools like DVC (Data Version Control) support this.
  • Feature engineering as transformation: The transformation stage (Glue ETL Jobs or Athena SQL) must produce ML-ready features — numeric encodings of categorical variables, normalised values, derived features like trip_duration = dropoff - pickup. This is the bridge between raw data engineering and ML engineering.
  • Feedback loops: Production ML models generate prediction logs that should be ingested back into the pipeline for monitoring and retraining. For example, a fare prediction model's predictions should be compared against actual fares to detect data drift — when the statistical distribution of input features changes over time (e.g., a pandemic shifts trip patterns), silently degrading model accuracy.
  • Data quality directly affects model performance: Underfitting (model too simple for the data) and overfitting (model memorises noise) are both exacerbated by poor data quality. Clean, well-partitioned, well-validated data is the foundation of reliable ML — no amount of model architecture sophistication compensates for garbage input.

6.28 What Was NOT Covered But Is Relevant

This lab provides the essential foundation, but several important topics are worth self-study for production readiness:

  • Glue Crawlers — Automatically detect schema and partitions without manual CREATE TABLE statements. Crawlers read a sample of S3 data, infer column types, detect delimiter formats, and update the Glue Catalog. Essential for automated ingestion pipelines where data schemas evolve over time. Crawlers can run on a schedule (e.g., daily) to pick up new partitions.
  • Glue ETL Jobs — Spark-based transformations (Python/Scala) for complex data cleaning that goes beyond SQL. Use cases include: fuzzy deduplication of records, complex JSON/XML parsing, joining across disparate data sources, and generating training datasets for ML. Glue ETL Jobs auto-generate Spark code from a visual interface, which you can then customise.
  • Columnar formats (Parquet / ORC) — Storing data as Parquet or ORC (instead of CSV) further reduces data scanned because Athena can read only the needed columns. In a CSV scan, every byte of every column is read regardless of which columns your SELECT references. In Parquet, only the column chunks for the referenced columns are read. Combined with Snappy compression, Parquet files are typically 5–10× smaller than equivalent CSV files. This is the single most impactful storage-level optimisation for Athena.
  • Data compression — Gzip/Snappy/Zstd compression reduces storage costs and scan volumes. However, not all compression codecs are equal for query performance: Gzip is not splittable (a single compressed file must be decompressed by a single worker), while Snappy and LZ4 are splittable (allowing parallel decompression across workers). For Athena, Snappy-compressed Parquet is the recommended default.
  • Athena Workgroups — Isolate query execution and enforce cost controls per team or project. A Workgroup can set data scan limits (e.g., "no query may scan more than 10 GB"), enforce encryption settings, and track costs separately per team. This prevents a single runaway query from consuming the entire department's Athena budget.

6.31 Common Student Mistakes (from the Lab)

  1. Forgetting to set Athena output location — Athena has no internal storage; without an S3 output bucket, queries fail with "No output location configured." This is the single most common first-time error.
  2. Creating tables in the default database — Later queries referencing taxi_data fail because the table was created in default. Always explicitly qualify your database, or run USE taxi_data; first.
  3. Spaces around = in shell variables — In Bash, VAR = "val" is interpreted as running a command named VAR with arguments = and "val". The correct syntax is VAR="val" with no spaces.
  4. Not saving the Named Query ID — Without the ID, you cannot grant access to other users or reference the query programmatically. The named query is effectively orphaned. Always capture and store the query ID after creation.
  5. Assuming views improve performance — Views only save the SQL text; they do not reduce data scanned. Only partitioned tables physically separate data. Mixing up views and partitioned tables is the most conceptual mistake.

6.32 Conceptual Questions to Test Yourself

Self-Assessment Questions (with Answers)

Q1: Why does Athena need an S3 output location configured?

A: Athena is serverless — it has no persistent storage of its own. Query results must be written somewhere, and S3 is the designated location. Without it, Athena has nowhere to put the result set.

Q2: What is the difference between a Glue Database and an S3 bucket?

A: An S3 bucket stores the actual data (CSV, Parquet files containing rows and columns of values). A Glue Database stores metadata about the data (table names, column types, partition keys, and S3 location pointers — essentially a schema definition). The database itself contains zero data bytes. If you delete an S3 bucket, the data is gone. If you delete a Glue Database, only the metadata definitions are lost — the data in S3 remains intact.

Q3: When would you use a view instead of a partitioned table?

A: Use a view when you want to simplify a complex SQL query for end users but don't need performance gains (or can't afford data duplication — since partitioned tables create physical copies of data, consuming additional S3 storage). Use a partitioned table when query speed and cost reduction are priorities, and you are willing to accept the storage overhead of data duplication and the maintenance overhead of keeping partitions up to date. In production, you often use both together: a view that selects from a partitioned table.

Q4: What three AWS services must a user have IAM permissions for to successfully run an Athena query on Glue-catalogued S3 data?

A: (1) Athena — execute queries and access named queries. (2) Glue — read table metadata (table definitions, column types, partition information). Without Glue permissions, Athena knows a table exists but cannot resolve its schema. (3) S3 — read source data (the actual CSV/Parquet files being queried) and write output results (the query result set). Missing any one of these three causes a permissions failure.

Q5: A query on a full table scans 10 GB and costs $0.05. After partitioning by month, the same query scans 800 MB. What is the new cost?

A: Cost scales linearly with bytes scanned: (800 MB / 10,000 MB) × $0.05 = 0.08 × $0.05 = $0.004. This is a 92% cost reduction. The formula to memorise is: at $5/TB, cost = (GB scanned / 1000) × $5 = GB scanned × $0.005. So 0.8 GB × $0.005 = $0.004. This question tests understanding of the Athena pricing model and why partitioning has such dramatic financial impact at scale.
