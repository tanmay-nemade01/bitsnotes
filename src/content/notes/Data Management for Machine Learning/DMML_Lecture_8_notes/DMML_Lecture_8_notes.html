1. Data Sources and Categorization

Every data pipeline begins with a question: where did this data come from, and can I trust it?. Before you write a single line of ingestion code, you must answer this.

Imagine you receive a package with no return address.. You would hesitate to open it.. Data is the same.. Knowing the origin — who created it, where it lives, what format it takes — determines every validation check you will write downstream.

Think of data sources like ingredients in a kitchen.. A chef knows whether the vegetables came from their own garden (internal, primary), a trusted farmer's market (second-party), or a distant wholesaler (third-party).. The chef treats each source differently — washing garden vegetables lightly, but scrubbing wholesale produce thoroughly.. Data engineers apply the same principle: the trust you place in a data source determines how much validation it needs.

Data sources are categorized along five independent axes.. Every dataset can be placed on each axis simultaneously.

- Analog vs.. digital — Analog data (speech, physical measurements) requires conversion before a pipeline can process it.. NLP tools handle speech-to-text and text-to-speech.. - Internal vs.. external — Generated inside the organization vs.. sourced from outside.. - Primary vs.. secondary — Collected directly for this purpose vs.. repurposed from another use.. - Core vs.. business — Foundational system data (database logs, server metrics) vs.. business-process data (sales transactions, customer interactions).. - First-party, second-party, third-party — Your organization created it; a trusted partner created it; an external aggregator created it.

Real-world: The Indian government runs data.gov.in.. NASA publishes open datasets.. Many third-party sources are publicly available — but "public" does not mean "clean."

Common trap: Assuming third-party data is clean because it comes from a reputable source.. Even NASA datasets contain gaps, malformed records, and inconsistent units.. Always validate.. The source's reputation protects their brand, not your pipeline.

Another trap: Confusing "internal" with "trustworthy." Internal systems produce dirty data too — CRM systems with duplicate customer records, IoT sensors with calibration drift, legacy databases with missing timestamps.

Data formatting challenges multiply when systems don't follow standards:

- Malformatting — Data not structured as expected.. A CSV that suddenly switches to semicolons on row 4,793.

- Too-long text — The Welsh railway station name Llanfairpwllgwyngyllgogerychwyrndrobwllllantysiliogogogoch (58 characters) breaks any VARCHAR(50) column.

- Too-short codes — Country code "IN" alone, missing the full name "India." Is "IN" India or Indiana?

- Inconsistent representations — The same customer stored as "R.. Kumar" in one system and "Raja Kumar" in another.

Classify every data source across all five axes before designing its ingestion path.. The classification determines the validation rigor required.

These categorization decisions feed directly into database selection.. If you know your data is highly interconnected (like a social graph), you need a graph database.. If it arrives as a firehose of time-stamped sensor readings, you need a time series database.. That is our next step.

2. Database Types and Selection

Why Database Choice Matters

Picking the wrong database is like using a screwdriver to hammer a nail.. It might work for one record, but it will fail at scale.. The database you choose determines what questions you can ask of your data — and how fast you get answers.

Imagine you run a library.. If patrons only ever ask "Give me the book with ISBN X," a simple numbered shelf (key-value store) works perfectly.. If they ask "Find all books about medieval history published after 1950 with 'castle' in the title," you need a search engine.. If they ask "Show me the borrowing network — which borrowers influence each other's reading habits," you need a graph database.. Same books, different questions, different storage strategies.

Selection Decision Framework

Match the data's primary access pattern to the database type.. The primary access pattern is the most frequent or most performance-critical query the system must answer.

| If your primary operation is.... | Choose.... | Example system | |---|---|---| | Structured transactions, ACID guarantees needed | Relational (SQL) | PostgreSQL, MySQL | | Flexible schema, unstructured or semi-structured data | Key-Value / Document (NoSQL) | MongoDB, DynamoDB | | Column-heavy analytics, IoT sensor data | Column database | Cassandra, Bigtable | | Full-text keyword/phrase search across document bodies | Search database | Elasticsearch | | Time-stamped measurements, high-velocity temporal data | Time series database | InfluxDB, TimescaleDB | | Highly interconnected, relationship-heavy queries | Graph database | Neo4j |

Relational Databases and ACID

ACID is a promise.. When a bank transfers money from account A to account B, the database guarantees either both operations succeed (Atomicity), the database stays valid (Consistency), concurrent transfers don't interfere (Isolation), and once confirmed the transfer survives a power outage (Durability).

Relational databases organize data into tables with predefined schemas.. They use SQL for querying.. They excel when the structure of data is known in advance and relationships between entities are clear.

Column Databases

Most databases store rows together: all columns of row 1, then all columns of row 2.. A column database stores columns together: all values of column A, then all values of column B.. When your query only touches 3 columns out of 200, a column database reads only those 3 — dramatically faster for analytics.

Real-world: IoT deployments generate millions of temperature readings.. You almost never query "give me all 200 columns for sensor 7492 at timestamp T." You query "give me the temperature column for all sensors between 2 PM and 3 PM." Column databases optimize for exactly this pattern.

Search Databases

Scenario (from the exam): A customer wants to search 20 keywords across all product issues.. What database do you recommend?

Analysis: The primary operation is full-text search across document bodies.. The 20 keywords must be matched against issue descriptions, titles, and comments — not against structured fields with exact values.

Answer: A search database like Elasticsearch.. It indexes document bodies for keyword and phrase matching, supports relevance ranking, and handles 20-keyword queries efficiently.

Sense-check: A relational database could do this with LIKE '%keyword%' on every text column — but that would scan every row every time.. Elasticsearch builds inverted indices that make this near-instant.

Use cases: log analysis (very large transaction logs, customer-click logs, network logs), real-time monitoring, anomaly detection — any situation where the question is "find all records containing these terms."

Time Series Databases

Time series data has one defining characteristic: time is a first-class dimension.. Every measurement is meaningless without its timestamp.. Train location at T₁, T₂, T₃.. Temperature at every minute.. Stock price at every tick.

Time series databases optimize for. append-heavy writes (data arrives in time order), range queries over time windows, automatic downsampling (hourly averages from minute-level data), and retention policies (auto-delete data older than N days).

Graph Databases

In a relational database, asking "find all friends-of-friends who bought this product" requires multiple JOINs — each hop adding cost.. A graph database stores relationships as first-class citizens.. A 5-hop query is nearly as fast as a 1-hop query.

Real-world: Neo4j powers fraud detection systems where the pattern "account A → transacts with → account B → shares address with → account C → linked to → account A" reveals circular money flows that would be hard to spot in SQL.

API choice maps to database choice: GraphQL for complex interconnected queries (matching graph databases), REST for simpler CRUD operations.

Trap: Picking a database because it is "modern" or "popular." New is not better.. Match the database to the access pattern, not to the hype cycle.

Trap: Using one database for everything.. Real systems often use multiple databases — PostgreSQL for transactions, Elasticsearch for search, Redis for caching, Kafka for streaming.. This is called polyglot persistence.

The database selection question on the exam maps scenario keywords to database types.. Read the scenario for the primary operation — search?. time-based?. interconnected?. — and pick accordingly.. Two lines is enough.

3. Data Access Patterns

APIs: The Restaurant Menu

An API is a restaurant menu.. It tells you what is available (endpoints), what ingredients each dish contains (response schema), and how to order (HTTP methods).. You do not need to know how the kitchen works.. You only need the menu.

Three API types serve different needs:

- RESTful services — Standard HTTP.. Each URL represents a resource.. GET /customers/7492 returns customer 7492.. Simple, stateless, widely understood.

- RPC (Remote Procedure Call) — Call a remote function as if it were local.. getCustomerScore(7492) returns a score.. Simpler mental model but tighter coupling.

- GraphQL — You specify exactly which fields you want.. { customer(id: 7492) { name, orders { total } } } returns only name and order totals.. No over-fetching, no under-fetching.. Ideal for complex, nested queries.

Message Queues and Streaming

A message queue is a post office.. The producer drops a letter in the mailbox and walks away.. The postal service delivers it.. The recipient picks it up when ready.. Neither producer nor consumer needs to be available at the same time.

The publisher-subscriber pattern: a producer puts messages into a queue.. Subscribers (consumers) receive them.. This decouples systems — the producer does not wait for the consumer to process.. Instagram: a new song is published once; millions of subscribers receive it independently.

Streaming is the real-time variant.. Events flow continuously.. Use cases: backup snapshots, database replication, event tracking, autonomous vehicle sensor streams.

Data Sharing and RBAC

Role-Based Access Control (RBAC) ensures each role gets only the segment of data it needs.. Access can be controlled down to the table level and row level.. The retail banking team does not see credit card data.. The insurance team does not see retail data.

Collaborative Filtering

Most recommendation systems work on behavioral signals: clicks, scroll patterns, zoom behavior, pop-up dismissal, suggestion acceptance.. These implicit signals power collaborative filtering — "users who behaved like you also liked this."

Choose the access pattern based on coupling needs.. Tightly coupled, synchronous: REST/RPC.. Loosely coupled, asynchronous: message queues.. Real-time continuous: streaming.

4. Data Ingestion

What Ingestion Really Means

Data ingestion is where most effort in a modern data platform lives.. It is not glamorous.. It is the plumbing.. But without plumbing, the house floods.

Think of a river flowing into a reservoir.. Before the water reaches your tap, it passes through filters, treatment plants, and quality checks.. Data ingestion is the same — moving data from source to destination, with checks along the way.

Data ingestion is the process of moving data from source systems into storage in the data engineering lifecycle.. It is distinct from data integration, which combines data from multiple sources into a new, unified dataset.

ETL vs. ELT

ETL is "cook before storing." ELT is "store first, cook later." Both have their place.. The choice depends on whether you know the recipe in advance.

Imagine you receive a box of mixed vegetables.. ETL means you wash, chop, and sort them before putting them in the fridge — everything is ready when you need to cook.. But if you later decide to make a dish that needs whole vegetables, you cannot undo the chopping.. ELT means you store the box as-is and process when you know what you are cooking.. More flexible, but the fridge needs to hold everything.

- ETL (Extract, Transform, Load): Data is extracted from the source, transformed (cleaned, reshaped, aggregated), then loaded into the target.. The traditional approach.. Schema is enforced before storage (schema-on-write).. Requires significant rework when requirements change — because the transformation already happened.. - ELT (Extract, Load, Transform): Data is extracted, loaded into the target raw, then transformed later as needed.. Schema is applied at read time (schema-on-read).. Preferred for modern cloud data warehouses (Snowflake, BigQuery, Databricks) because storage is cheap and compute can scale on demand.

When to use ETL: A regulated financial report that must follow exactly the same transformation every quarter.. You know the output format.. You want consistency.. Transform once, validate thoroughly.

When to use ELT: A data science team exploring customer behavior.. They do not know which features they will need.. They may try 20 different aggregations.. Store raw data once.. Let them transform on demand.. If a transformation is wrong, reprocess from raw data — no need to re-extract.

Sense-check: ETL prioritizes consistency and control.. ELT prioritizes flexibility and agility.. Modern platforms increasingly favor ELT because cloud storage and compute are cheap and requirements change.

Batch Ingestion

Batch systems are typically a day behind.. A job starts at 8 PM, extracts the day's transactions, transforms them, and loads results by 4 AM.. Reports are available the next morning.

Real-world example from the professor: A financial services company ran nightly batch — 8-hour window, production support carrying pagers for 24×7 coverage.

Common batch patterns:

- Salesforce.com → API → data warehouse → Tableau / Power BI

- Twitter feed → API (with keys and access control) → sentiment analysis pipeline

Ingestion Parameters

Four design decisions shape every ingestion pipeline:

1.. Time-interval-based vs.. size-based triggers — Ingest every N minutes, or after M records accumulate.. During Black Friday or stock market surges, a time-interval approach may miss records while a size-based approach may trigger too frequently.. Choose based on data velocity.

2.. Full snapshot vs.. differential (incremental) — Pull all data every time, or only changes since the last pull.. Full snapshots are simpler but scale poorly.. Incremental pulls save bandwidth but require change-tracking mechanisms (timestamps, CDC logs).

3.. Batch insert vs.. batch update — Add new records only (append), or update existing records too (upsert).. Upserts are harder but necessary when source records change.

4.. Push vs.. pull — The publisher sends messages to the subscriber (push), or the subscriber requests only what it wants, when it wants (pull).. Pull is like ordering a customized Subway sandwich — you choose exactly what goes in.. Pull offers flexibility and cost savings.

Streaming Ingestion

For continuous, real-time data flows.. The autonomous vehicle example: every object in the camera frame — including shadows — must be classified in real time.. A shadow is an object to a self-driving car's vision system.. Distinguishing real obstacles from shadows requires massive streaming data processing with sub-second latency.

Late Arrival, Duplicates, and Out-of-Order Data

Late arrival data: Using a debit card abroad — the email notification arrived before the SMS, and the SMS arrived after the bank's verification call.. Ordering got disturbed because events entered an asynchronous queue (CDC events) with no predictability about which emerges first.

Duplicate messages: The same transaction notification delivered 2–3 times.. Was the transaction made multiple times, or was the notification duplicated?. Deduplication logic (idempotency keys, unique message IDs) is essential.

Out-of-order messages: Events arriving in a different sequence than they occurred.. Requires sequence-number-based ordering or watermark-based windowing in the consumer.

Replay and TTL

- Replay: The ability to replay a stream from a specific point in time.. RabbitMQ, Kafka, and Kinesis all support replay — at different granularities.

- Time to Live (TTL): How long an event record lives before being discarded.. Too short: messages disappear before processing.. Too long: backlog builds, intruders may exploit unprocessed messages.. Google Cloud: up to 7 days retention.. Amazon Kinesis: up to 365 days.. TTL is also a networking parameter in TCP/IP — the hop count before a packet dies (typically 30–64 hops).

Ingestion Methods Summary

Method When to Use
Direct DB connection Simple, controlled access
CDC (Change Data Capture) Incremental updates from source DB
APIs (REST, GraphQL, RPC) Third-party or SaaS data
Message queues Decoupled, async producer-consumer
Streaming (Kafka, Kinesis) Real-time, high-velocity data
Object storage (S3) File-based bulk ingestion
File export Batch transfers
SFTP / SCP Secure file transfer
Webhooks Event-driven push notifications

Ingestion is not one-size-fits-all.. The method, cadence, and validation all depend on the source system, the data velocity, and the downstream use case.. ETL favors consistency; ELT favors agility.. Know when to use each.

5. Data Contracts

The Handshake Before the Pipeline

Would you build a house without a contract with the builder?. Then why would you build a data pipeline without a contract with the data source?. A data contract is the handshake before the work begins.

Imagine you subscribe to a newspaper.. The contract says: daily delivery, before 7 AM, to your doorstep, in English.. If the paper arrives in Mandarin at 9 AM tossed into the bushes, the contract is violated.. Data contracts work the same way between data producers and data consumers.

A data contract is a written agreement between the owner of a source system and the team ingesting data from that system.. It is the data equivalent of a Service Level Agreement (SLA) or an Underpinning Contract (UPC) in IT service management.

A data contract specifies: - What kind of data is being extracted - The extraction method (full extract or incremental) - How often data will be extracted (frequency/cadence) - Who are the contacts for both the source system and the ingestion team - The schema, format, and expected volume

Storage and Practical Example

Data contracts should live in a well-known, easy-to-find location — a GitHub repository or an internal documentation site.. They are not "set and forget"; they are living documents that evolve as systems change.

Real scenario from the professor: A semiconductor equipment company working with Intel, Samsung, and ASM.. The contract covered only factory automation data (Manufacturing Execution System data).. Equipment-level data was explicitly excluded.

If the ingestion system accidentally collected equipment-level data, that would constitute: 1.. A data leakage — unintended data entering the pipeline 2.. A data contract violation — collecting data outside the agreed scope

Sense-check: The contract is not "you get all data." It is "you get exactly this data, this way, this often." Violating it has legal, security, and trust consequences.

When you use LinkedIn/Facebook and grant permissions ("Can we use this for advertisements?"), or when you add an MCP with an authentication key and expiry duration. that agreement is a data contract.. You are specifying what data may flow, for how long, and for what purpose.

Trap: Treating the data contract as a formality.. Without clear boundaries, scope creep happens.. "Oh, we also pulled this extra column — it seemed useful" is how leakage begins.

Trap: Not updating the contract when the source system changes.. A schema change in the source without a corresponding contract update means your pipeline may silently break or, worse, silently ingest wrong data.

No contract, no pipeline.. A data contract defines the boundaries of trust between producer and consumer.. Violate it, and everything downstream is suspect.

6. Data Lineage

Tracing Data's Journey

You would not eat food without knowing where it came from.. Data lineage is the "farm to table" tracking for your data.. It shows every stop, every transformation, every handoff.

Imagine tracing a river from its mountain spring, through tributaries, past dams and treatment plants, to your kitchen tap.. At each point, something may enter the water — minerals, pollutants, treatment chemicals.. Data lineage is the map of that entire journey for a dataset.

Data lineage is the documentation and visualization of data's journey through an organization.. It tracks: 1.. Where data originates (source systems) 2.. How it transforms as it moves through pipelines and teams 3.. Where it ultimately surfaces for end consumers (dashboards, reports, models)

Producing Data Lineage

The process requires:

1.. Identifying the data assets

2.. Tracking those assets from ingestion sources

3.. Documenting all sources and transformations

4.. Mapping the path of data as it moves through various pipelines

5.. Pinpointing where the data is served up — in dashboards and reports

Why It Matters

If a CEO sees a suspicious number on a dashboard, lineage answers: "Where did this number come from?. Which pipeline produced it?. Which source table?. Which transformation?. Who touched it last?"

Without lineage, debugging a data quality issue is archaeology — digging through layers of SQL, Python scripts, and undocumented transformations, hoping to find where it went wrong.. With lineage, it is a map with a "You are here" marker.

Trap: Assuming lineage is only for compliance.. Lineage is also for debugging, impact analysis ("if I change this source table, which 47 dashboards break?"), and trust.. If you cannot trace a number back to its source, you cannot fully trust it.

Data lineage is the GPS of your data platform.. Without it, you are navigating blind.

7. Data Governance

The Rules of the Road

Data governance is not bureaucracy.. It is seatbelts.. Nobody enjoys buckling up, but everyone is glad the seatbelt exists when things go wrong.

Think of a hospital.. Patient records are sensitive.. Only doctors treating a patient should see that patient's records.. The hospital has rules about who accesses what, how long records are kept, how they are secured, and what happens if there is a breach.. Data governance is the same set of rules for organizational data.

Data governance is a data management discipline focused on the quality, security, and availability of data.. It encompasses all the standards and regulatory frameworks that data pipelines must satisfy.

Key regulatory standards: - GDPR (General Data Protection Regulation). EU data privacy - HIPAA (Health Insurance Portability and Accountability Act) — US healthcare data - PII (Personally Identifiable Information) — any data that can identify an individual - PCI DSS (Payment Card Industry Data Security Standard) — credit card data - DRP (Disaster Recovery Planning) — business continuity - DPD (Data Protection Directive) — predecessor to GDPR

Trap: Treating governance as a "final check" before going live.. Governance must be designed into the pipeline from the start.. Retrofitting RBAC, audit logging, and data retention into an existing pipeline is far more expensive.

Trap: Confusing governance with a tool.. Governance tools (Collibra, Alation, Atlan) help, but governance is primarily a practice — policies, processes, and people.

Governance is the seatbelt.. Build it in from day one.. Regulations are the minimum standard, not the ceiling.

8. Pre-Ingestion Validation

The Gatekeeper Before the Gate

The professor tells a story: three fishes lived together.. One detected fishermen coming and escaped before they arrived.. The second, caught but understanding what happened, played dead and escaped.. The third did nothing and was killed.. The lesson: prevention is better than cure.. Validate before data enters the system.

Imagine airport security.. Before you board the plane, your ID is checked (presence), your bag goes through an X-ray (range. no prohibited items), your boarding pass format is verified (format), and you walk through a metal detector (type — are you carrying metal?).. Pre-ingestion validation is airport security for data.

The Four Pre-Ingestion Checks

Pre-ingestion validation happens before data enters the system — at data entry points: forms, APIs, ETL pipelines.. The focus is on cleanliness, schema compliance, and security.

1.. Presence checks — Are all mandatory fields present?. Is every required column populated?

Examples from the professor: - A country column must exist in every record - A date_of_birth column must have values. no NULLs - Monthly sales data must have a month value — a sales record without a month is useless

2.. Range checks — Are values within acceptable bounds?. Block values that make no sense.

Examples: - Blood pressure of -2 is a range violation. BP cannot be negative - Negative sales values should be rejected — you cannot sell negative quantity - Age of 347 is a range violation — reject or flag for review

3.. Format checks — Does the data conform to the expected format?

Examples: - Reject malformed reports where CSV suddenly switches to semicolons - Wrong date format: 03/04/2025 — is it March 4 or April 3?. If the system expects DD/MM/YYYY and gets MM/DD/YYYY, reject.. - Email field that contains no "@" sign

4.. Data type checks — Is the data numeric where it should be?. Non-numeric where appropriate?

Examples: - Reject "abc" in a numeric sales column - Reject a numeric value in a name field - Ensure ZIP codes are stored as strings (leading zeros matter. "02134" is not 2134)

Additional Pre-Ingestion Activities

- Block SQL injection attempts — Security validation at entry points.. Never trust user input.

- Alert admins when mandatory fields are missing — Automated notification, not silent failure.

- Ensure key columns have values — Primary keys and foreign keys must not be null.

The Header File Validation Pattern

The professor's real-world example: A batch ETL process for 10,000 transaction records worked like this:

1.. Source system sends two files: - Transaction detail file: 10,000 records - Header (summary) file: States "10,000 records expected. first record = X; last record = Y"

2.. Pre-ingestion validation: - Run wc -l (Unix word count) to count actual records in the detail file - Verify: exactly 10,000 records?. - Verify: first record matches header's "first record = X"?. - Verify: last record matches header's "last record = Y"?

3.. Decision: If all three checks pass → proceed with loading.. If any check fails → reject the entire file and alert the operations team.

Why this matters: A file with 9,987 records when 10,000 were expected means 13 records were lost in transit.. Loading partial data produces wrong reports.. Catching this before loading prevents downstream contamination.

Sense-check: This is a presence check (are all records present?) and a consistency check (does the detail match the header?) combined at the pre-ingestion stage.

Trap: Skipping pre-ingestion validation because "the source system already validates." Source systems validate for their own purposes, not yours.. A missing field may be fine for the CRM application (it substitutes a default) but catastrophic for your analytics pipeline.

Trap: Validating only format and type, forgetting presence and range.. All four checks matter.. A perfectly formatted negative sales number passes format and type checks — but fails range.

Trap: Silently dropping bad records instead of rejecting and alerting.. If bad data is dropped without notification, you build reports on incomplete data and never know.

The four pre-ingestion checks — presence, range, format, data type — are your first and most important line of defense.. Apply them at every data entry point.. Prevention is cheaper than cure.

9. Post-Ingestion Validation

After the Data Lands

Pre-ingestion validation is the airport security check.. Post-ingestion validation is the audit after the flight lands — did all passengers who checked in actually arrive?. Did any baggage go missing?. Is the flight log consistent with the manifest?

Once data is stored, a different set of questions emerges.. These are not about individual field validity (that was pre-ingestion).. They are about whether the data as a whole makes business sense.

The Three Post-Ingestion Checks

Post-ingestion validation happens after data is stored in pipelines or warehouses.. The focus is on business rules, statistical checks, and consistency.

1.. Consistency checks — Is data consistently represented across systems and over time?

Examples: - A start date must be before an end date.. If trip_start > trip_end, the record is inconsistent.. - Monthly totals must align with ledger totals.. If 12 monthly sales figures sum to ₹1.2 crore but the annual ledger says ₹1.5 crore, something is wrong.. - The same customer should have the same customer_id across all tables.

2.. Business rule verification — Do the ingested records satisfy business rules?

Examples: - Sales cannot be negative (same rule as pre-ingestion, now checked at aggregate level) - Missing months in a time series must be interpolated or flagged for review - Verify that sales totals match accounting ledgers - All orders must have a corresponding customer record (referential integrity)

3.. Statistical checks — Is the distribution as expected?

Examples: - Detect anomalies in time series — did sales suddenly spike 500% on a random Tuesday?. - Confirm referential integrity across tables. no orphan records - Verify no missing months in time series data - Check that mean, median, and standard deviation are within expected ranges

The Audit Table Pattern

The professor's example: After loading 10,000 records into the warehouse:

1.. An audit table records: date, time, and record count of every load — plus counts of inserts, updates, and deletes.. 2.. Post-ingestion: Run a query against the audit table: - All 10,000 records present for that date and time?. ✓ - How many were inserted?. How many updated?. How many deleted?. 3.. If counts match expectations → load verified.. If not → investigate the discrepancy.

Why an audit table? It is a separate, simple table that serves as an independent witness.. The audit table is not derived from the loaded data — it is written by the loading process itself.. This separation of concerns means a bug that corrupts the data cannot also corrupt the audit record.

Sense-check: This is post-ingestion consistency — the audit table independently confirms what was loaded matches what was expected.

Pre vs. Post: The Complete Picture

Aspect Pre-Ingestion Validation Post-Ingestion Validation
When Before data enters the system After data is stored
Where Data entry points: forms, APIs, ETL Pipelines, warehouse
Focus Cleanliness, schema compliance, security Business rules, statistical checks, consistency
Checks Presence, range, format, data type Consistency, business rules, statistical
Examples Reject malformed records, block SQL injection, ensure mandatory fields Verify totals match ledgers, detect anomalies, confirm referential integrity

Trap: Confusing pre-ingestion and post-ingestion checks.. A range check ("sales must be non-negative") is pre-ingestion if applied to individual records at entry, but post-ingestion if applied to aggregate totals in the warehouse.. The timing and granularity differ.

Trap: Having great pre-ingestion checks but skipping post-ingestion.. You caught the malformed records, but did you verify that the total loaded matches the total sent?. Pre-ingestion catches individual errors; post-ingestion catches systemic errors.

Pre-ingestion stops bad records from entering.. Post-ingestion confirms that what entered is complete, consistent, and business-rule-compliant.. Both are needed — neither replaces the other.

10. Data Quality Dimensions

Measuring What "Good" Means

"Good data" is like "good food" — it means different things to different people.. A data quality dimension is a specific lens through which you measure goodness.. You cannot improve what you do not measure.

Imagine buying a used car.. You check: Does the odometer reading seem accurate?. (Accuracy.) Are all the service records present?. (Completeness.) Do the records match across the service book and the dealer's database?. (Consistency.) Is the VIN valid?. (Validity.) Are the records recent?. (Timeliness.) Is this the only car with this VIN?. (Uniqueness.)

Data quality dimensions are measurement attributes of data that can be individually assessed, interpreted, and improved.. The ten core dimensions are:

1.. Accuracy — Values reflect reality.. Claiming to be in Chennai while in Luxembourg is inaccurate.. 2.. Completeness — No missing mandatory fields.. All required data is present.. 3.. Consistency — Same data across systems.. "R.. Kumar" and "Raja Kumar" should resolve to the same entity.. 4.. Validity — Matches schema and rules.. Data conforms to defined formats and constraints.. 5.. Timeliness — Data is up to date.. Freshness matters.. Stale data compromises validity.. 6.. Uniqueness — No duplicate records.. "Raja Kumar" and "R.. Kumar" — one person or two?. 7.. Integrity — Referential integrity across tables.. Every order has a customer.. Every transaction has an account.. 8.. Lineage — Can the data's origin and transformations be traced back?. 9.. Reliability — Can the data be trusted?. Would you bet your bonus on this number?. 10.. Accessibility — Can authorized users access the data when needed?

Additional Aspects

- Coverage — How much of the domain does the data represent?. Enough for modeling?

- Unbiased — Free from systematic skew in collection or labeling.

- Consistent labeling — Same label applied the same way across the dataset.

- Feedback loop awareness — Good data is not a result of the model itself.. If the model's predictions influence future labels, you have a feedback loop that can amplify errors.

Common Data Quality Problems

- Costly — Good data is expensive to acquire and maintain.. There is no free lunch.. - Noisy — Instrument errors, blurry images, incomplete records.. Signal vs.. noise.. - Low predictive power — Data exists but does not help the model.. More data ≠ better model.. - Outliers — Values outside the interquartile range, far from the mean.. One bad sensor can poison an entire dataset.. - Bias — Systematic skew.. Covered in detail in Section 14.. - Leakages — Unintended target information.. Covered in detail in Section 13.. - Outdated — Data drift makes old data irrelevant.. Covered in Section 15.

Data quality is multi-dimensional.. A dataset can score high on accuracy but low on completeness.. Measure each dimension independently.. The exam may ask you to identify which quality dimension a scenario describes.

11. Data Leakage

When the Answer Leaks Into the Question

If the chutney is bad but the idli is good, and you pour the chutney all over the idli without tasting it first — the entire idli becomes inedible.. Data leakage is pouring bad information over your entire model without realizing it.

Imagine studying for an exam where the answer key is accidentally printed on the back of every practice question.. You score 100% on practice tests.. You feel brilliant.. Then you sit the real exam — and fail.. The practice tests were contaminated with information that would never be available during the real exam.. Your model did the same thing.

Data leakage (also called target leakage or contamination) is the unintentional introduction of information about the target variable that should not be available at prediction time.. It affects every stage of the ML lifecycle — from data collection to model evaluation.

The Aloo Paratha Analogy

The professor's second analogy: A delicious aloo paratha with poorly boiled potatoes.. The paratha looks perfect from the outside — golden, crisp, beautiful.. But the filling is hard, undercooked, or too salty.. The entire dish collapses.. One bad dependency in your pipeline contaminates everything downstream.

Causes of Leakage

1.. Using the target variable in feature engineering — The most direct form.. You include tomorrow's stock price to predict today's movement.. 2.. Including future timestamps in training data — Training on data that contains information from after the prediction point.. If you are predicting Q3 sales and your features include Q4 economic indicators, you have leaked the future.. 3.. Improper train/test split — Test data accidentally introduced during training.. Split before any normalization or imputation — otherwise the test set's statistics leak into the training set.. 4.. Data dependencies where one column's error propagates — If column A is derived from column B, and column B contains target-related information, that relationship leaks through.

Concrete Example

Scenario: Predict a country's GDP based on area, population, and geographic region.

\[ \text{GDP} = f(\text{population}, \text{area}, \text{region}) \]

If the population column is incorrectly computed. say it uses a formula that itself depends on GDP (e.g., population estimates adjusted by economic activity indicators) — then population carries leaked GDP information.. The model appears to predict GDP well because one of its inputs already "knows" about GDP.

At prediction time in production, the population estimate would be different (not derived from GDP, since GDP is what you are predicting).. The model's real-world performance collapses.

Sense-check: Audit every feature.. Ask: "Will this exact value be available at prediction time, exactly as it appears in my training data?" If the answer is no, you may have leakage.

Prevention

- Strict train/test split enforcement — Split by time for temporal data.. Never shuffle temporal data randomly.

- Audit feature sources — Verify every feature is available at prediction time without target-derived information.

- Cross-validation with leakage detection — Use time-based cross-validation for time series.

- Capital analysis of each attribute — Trace every column back to its source.. Ask: "Is this column computed from something that happens after the prediction point?"

Trap: The model performs brilliantly in training and testing but fails in production.. This is the #1 symptom of leakage.. An overly optimistic model that cannot deliver in the real world.

Trap: Normalizing before splitting.. If you compute the mean and standard deviation of the entire dataset (train + test) and then normalize, the test set's statistics have leaked into the training process.. Always split first, then compute normalization parameters from the training set only.

Data leakage makes your model cheat on the practice exam.. It looks great until the real test.. Audit every feature for temporal validity and target independence.. When in doubt, ask: "Would this information exist at the moment of prediction?"

12. Data Bias

Systematic Error, Not Random Noise

Bias is not noise.. Noise is random — it averages out with enough data.. Bias is systematic — it pushes results consistently in one direction.. More data makes bias worse, not better.

Imagine a bathroom scale that always reads 2 kg too high.. That is bias.. Weigh yourself once: you are off by 2 kg.. Weigh yourself 100 times and average: you are still off by 2 kg.. More measurements did not help because the error is systematic, not random.

Bias is systematic error introduced into data collection, labeling, or interpretation that skews results in a particular direction.. Unlike random noise, bias does not diminish with larger sample sizes.

Types of Bias

- Omitted variable bias — A relevant factor is left out of the model.. Example: predicting house prices without including school district quality.. The model attributes the effect of schools to whatever correlated variable is present (e.g., square footage), producing biased coefficients.. - Sponsorship or funding bias — Research funded by a party with a stake in the outcome.. The professor noted: papers and experiments can be biased by who funds them.. - Label bias — Data labeled in a way that reflects the labeler's perspective.. A "6" vs.. a "9" depends on orientation.. Two labelers may disagree.. Systematic disagreement = bias.. - Selection bias — The sample is not representative of the population.. Only surveying people who visit your website misses everyone who doesn't.. - Collection bias — Data is not collected in a representative fashion.. IoT sensors only in urban areas; rural areas unrepresented.. - Implicit bias — Unconscious assumptions influence data handling.. "This column looks right" without verifying.. - Stereotype bias — The professor's example: "If Siemens provides the data, it must be correct." Assuming certain groups or systems are always right.. - Experimental bias — The experiment design itself introduces skew.. A/B test that runs only during weekdays misses weekend behavior.. - Reporting bias — Only certain results are reported.. The 1 successful experiment out of 20 gets published; the 19 failures disappear.

AI Fairness Principles

All AI systems should adhere to: Fairness, Accountability, and Trustworthiness.

Bias is systematic, not random.. More data amplifies bias — it does not fix it.. Audit collection, labeling, and sampling processes for all nine bias types.. Fairness is not an afterthought.

13. Data Drift

When the World Changes Under Your Model

A model is a snapshot of the world at training time.. The world keeps moving.. When the gap between the snapshot and reality grows too large, the model breaks.. That gap is drift.

Imagine you trained a model to predict taxi fares in 2019.. It learned that 3 km costs about ₹120.. Then fuel prices doubled, a new congestion charge was introduced, and ride-sharing surged.. Your model still predicts ₹120.. The world changed; your model did not.

Data drift is a growing mismatch between the data a model was trained on and the data it receives in production.. Once deployed, a model usually performs well for some time.. Over time, performance degrades as drift accumulates.

Types of Drift

Data Drift (Feature Drift)

The production data diverges from training data.. Two subtypes:

1.. Schema skew — Training and serving data do not conform to the same schema.. A feature column disappears, or a new one appears with a different name or type.. The model must be updated because its input contract has changed.

2.. Distribution skew — The statistical distribution of the data has changed.. New trends and patterns emerged that were not in the training data.

Distribution skew example: A real estate price prediction model built five years ago.. Training data had: median home price = ₹45 lakh, average square footage = 1,200.. Today's market: median = ₹82 lakh, average square footage = 1,500, and a new metro line changed neighborhood desirability rankings.. The model predicts ₹52 lakh for a home that sells for ₹90 lakh.. The distribution of every feature shifted.

Sense-check: The model is not "wrong" — it is answering 2019's question.. 2026 is asking a different question with different numbers.

Concept Drift

The relationship between input and output itself changes.

The professor's example: Your understanding of a concept on Day 1 vs.. after 16 lectures.. The mapping between the concept and your knowledge has shifted.. The same input ("What is data drift?") now maps to a different output (a richer, deeper answer).

Concept drift relates to concept hierarchy — the mental model of how ideas relate.. When the hierarchy shifts, the old mapping no longer applies.

Training-Serving Skew

A discrepancy between how data is handled in the training pipeline vs.. the serving pipeline.. The ideal practice: reuse the same feature engineering code.. Whatever code transformed features during training should be the exact same code used during deployment.. Different code paths → different transformations → different feature vectors → wrong predictions.

Drift Detection Approaches

Three categories:

1.. Model-based approach — Train a separate model to detect when the data distribution has shifted enough to warrant retraining.

2.. Statistical approach — Use statistical tests (KS test, chi-squared) to compare training and production distributions.

3.. Algorithm-based approach — Use dedicated drift-detection algorithms (ADWIN, DDM, Page-Hinkley).

Drift is inevitable.. The world changes.. Monitor for it, detect it early, and retrain before your users notice.. PSI and KL Divergence (next sections) are your primary measurement tools.

14. Population Stability Index (PSI)

Measuring Distribution Shift

PSI answers one question: "Has my population changed enough that I should worry?" It is the early warning system for model decay.

Imagine you manage a credit card approval model.. Your training data was from 2023: mostly salaried employees, stable economy, 8% default rate.. Now it is 2026: the economy shifted, gig workers are a larger share of applicants, default patterns changed.. Should you retrain?. PSI gives you a number to decide.

The Population Stability Index (PSI) is a statistical tool that measures how much the distribution of a variable changes between two datasets — typically training data and new production data.

\[ \text{PSI} = \sum_{i=1}^{n} (P_i - Q_i) \cdot \ln\left(\frac{P_i}{Q_i}\right) \]

Where: - \(n\) = number of bins (histogram buckets) - \(P_i\) = proportion of training data in bin \(i\) - \(Q_i\) = proportion of new data in bin \(i\) - \(\ln\) = natural logarithm

How PSI Works

1.. Take a variable (e.g., applicant age).

2.. Bin it into buckets: 18–25, 26–35, 36–50, 51+.

3.. Compute the proportion of training data in each bucket (\(P_i\)).

4.. Compute the proportion of new data in each bucket (\(Q_i\)).

5.. For each bucket, compute \((P_i - Q_i) \cdot \ln(P_i / Q_i)\).

6.. Sum across all buckets.

Interpretation

PSI Value Meaning Action
< 0.1 Low drift No action needed. Model is stable.
0.1 to 0.25 Moderate drift Monitor closely. Consider retraining soon.
> 0.25 Significant drift Retrain or recalibrate the model.

Example: Credit scoring model for loan applicants.

Training data (2023): 10,000 applicants across 4 age bins.. New data (2026): 8,000 applicants.

| Age Bin | Training % (\(P_i\)) | New % (\(Q_i\)) | \(P_i - Q_i\) | \(\ln(P_i/Q_i)\) | Term | |---|---|---|---|---|---| | 18–25 | 0.15 | 0.25 | -0.10 | -0.511 | 0.051 | | 26–35 | 0.35 | 0.30 | 0.05 | 0.154 | 0.008 | | 36–50 | 0.30 | 0.28 | 0.02 | 0.069 | 0.001 | | 51+ | 0.20 | 0.17 | 0.03 | 0.163 | 0.005 |

PSI = 0.051 + 0.008 + 0.001 + 0.005 = 0.065

Interpretation: PSI < 0.1 → Low drift.. The age distribution has not shifted significantly.. No immediate retraining needed.

Sense-check: The biggest shift was in the 18–25 bucket (15% → 25%), contributing most of the PSI.. The model team should investigate why younger applicants increased — but the overall shift is not yet alarming.

Applications

- Credit scoring — Did the applicant population change after new lending regulations?

- Customer segmentation — Have purchasing patterns shifted post-pandemic?

- Risk assessment — Does the risk model still reflect the current insured population?

Trap: PSI only measures distribution shift of individual variables.. It does not detect concept drift (when the relationship between variables changes while distributions stay the same).. Use PSI for feature-level drift; use model performance metrics for concept drift.

Trap: Small PSI does not mean "safe." If all variables show PSI < 0.1 but your model accuracy dropped 5%, concept drift is the likely culprit.

PSI is your early warning system.. Compute it regularly.. Treat PSI > 0.25 as a trigger for investigation and retraining.

15. KL Divergence (Kullback-Leibler Divergence)

Measuring Information Loss Between Distributions

Entropy measures surprise.. KL Divergence measures extra surprise when you use the wrong distribution to predict the right one.

Imagine you live in Chennai, where it rains about 85 days per year (probability of rain ≈ 0.23).. You travel to London, where it rains about 156 days per year (probability ≈ 0.43).. Every day in London, you are more surprised by rain than your Chennai-trained intuition expects.. KL Divergence quantifies that extra surprise.

KL Divergence (also called relative entropy) measures how one probability distribution \(Q\) diverges from a reference distribution \(P\).

\[ D_{KL}(P \parallel Q) = \sum_{x} P(x) \cdot \ln\left(\frac{P(x)}{Q(x)}\right) \]

Where: - \(P(x)\) = true probability of event \(x\) (reference distribution. your training data) - \(Q(x)\) = approximate probability of event \(x\) (comparison distribution — your production data) - \(\ln\) = natural logarithm - The sum runs over all possible events \(x\)

\(D_{KL}\) is always \(\geq 0\).. It equals 0 only when \(P = Q\) (the distributions are identical).. Unlike PSI, KL Divergence is not symmetric: \(D_{KL}(P \parallel Q) \neq D_{KL}(Q \parallel P)\).

Relationship to Entropy

Entropy measures the degree of disorder or impurity in a dataset.

A basket with 9 oranges and 1 apple has low entropy — it is mostly pure (you can predict "orange" with 90% confidence).. A basket with 5 oranges and 5 apples has high entropy — you are maximally uncertain.

Entropy formula: \(H(P) = -\sum P(x) \cdot \ln(P(x))\)

KL Divergence builds on entropy.. It measures the relative entropy between two distributions — the extra bits needed to encode data from \(P\) using a code optimized for \(Q\).

Use in Drift Detection

KL Divergence is an alternative to PSI for detecting distribution drift.. Compute \(D_{KL}(\text{training} \parallel \text{production})\) for each feature.. Large values indicate drift.

Example: Comparing customer purchase amounts.

Training data (\(P\)): purchase amounts in bins.. - $0–50: 40% - $50–200: 35% - $200–500: 20% - $500+: 5%

Production data (\(Q\)): - $0–50: 30% - $50–200: 30% - $200–500: 25% - $500+: 15%

Step-by-step: \[ \begin{aligned} D_{KL}(P \parallel Q) &= 0.40 \cdot \ln(0.40/0.30) + 0.35 \cdot \ln(0.35/0.30) + 0.20 \cdot \ln(0.20/0.25) + 0.05 \cdot \ln(0.05/0.15) \\ &= 0.40 \cdot 0.288 + 0.35 \cdot 0.154 + 0.20 \cdot (-0.223) + 0.05 \cdot (-1.099) \\ &= 0.115 + 0.054 - 0.045 - 0.055 \\ &= 0.069 \end{aligned} \]

Interpretation: \(D_{KL} = 0.069\) — a small divergence.. But note the $500+ bin: 5% → 15% (tripled).. Individual bin contribution may be more actionable than the aggregate number.

Sense-check: KL Divergence flagged the high-value customer segment shift even though the overall number is low.. Always inspect per-bin contributions.

Trap: KL Divergence is not symmetric.. \(D_{KL}(P \parallel Q) \neq D_{KL}(Q \parallel P)\).. Always use training data as \(P\) (the reference) and production data as \(Q\) (the comparison).. Using the reverse gives a different number and a different meaning.

Trap: KL Divergence is undefined when \(Q(x) = 0\) but \(P(x) > 0\) (\(\ln(P/0) = \infty\)).. In practice, add a small smoothing constant to avoid zero bins (Laplace smoothing).

KL Divergence answers: "How much information am I losing by assuming the old distribution still holds?" Use it alongside PSI.. PSI is symmetric and interpretable; KL Divergence has deeper information-theoretic foundations.. Choose based on your team's comfort and the reporting needs of stakeholders.

16. Data Profiling

Understanding What You Have Before Using It

You would not hire someone without reading their CV.. Data profiling is reading the CV of your dataset — what it contains, how it is structured, what shape it takes.

Just as a CV captures education, skills, certifications, and experience, data profiling captures summary statistics, data types, value distributions, and dependencies.

Data profiling is the process of understanding what the data is — its characteristics, metadata, and structure.

Key aspects: - Summary statistics (mean, median, min, max, standard deviation) - Data types per column - Value distributions (histograms, frequency counts) - Dependencies between fields (foreign keys, correlations) - Metadata about the dataset (row count, column count, creation date, source)

Profile every dataset before building a pipeline for it.. You cannot validate what you do not understand.

17. Skewness in Data

When the Bell Curve Leans

Skewness is asymmetry.. Most ML algorithms assume your data is symmetric (normally distributed).. When it is not, the algorithms still run — but their answers are wrong.

Imagine a seesaw.. With equal weight on both sides, it balances.. That is a symmetric distribution (mean = median).. Now put all the weight on one side — the seesaw tilts.. That is skewness.. Mean and median are no longer the same.. The mean gets pulled toward the long tail.

Skewness is asymmetry in a data distribution.

- Positive skew (right-skewed): Long tail on the right.. Mean > Median.. Example: income data — most people earn moderate amounts, a few earn enormously, pulling the mean above the median.. - Negative skew (left-skewed): Long tail on the left.. Mean < Median.. Example: age at death in developed countries — most people live to 70–85, fewer die young, pulling the mean below the median.

Detection

- Compute the skewness coefficient.. Zero = symmetric.. Positive = right-skewed.. Negative = left-skewed.

- Visualize with histograms and box plots.. A histogram shows the tail direction immediately.. A box plot shows asymmetry through the position of the median within the box.

Impact and Correction

Skewed data biases mean-based models.. Linear regression, PCA, and many clustering algorithms assume normality.. When the assumption breaks, predictions become systematically wrong.

Correction techniques: - Log transformation — \(\ln(x)\) for right-skewed data.. Compresses large values.. - Box-Cox transformation — A family of power transformations.. Finds the best power to make data normal.. - Standardization — \((x - \mu)/\sigma\).. Centers and scales but does not fix skewness.. - Normalization — Min-max scaling to [0, 1].. Does not fix skewness.

Check skewness before modeling.. If skewness is present, apply transformation.. Log-transform is the first thing to try for right-skewed data.

18. Worked Case Study — Retail Monthly Sales

The Scenario

A retail company imports monthly sales data from 200 stores.. Some records have missing months.. Others show negative sales values.. Reports are inconsistent.

Analysis

This is an ingestion validation problem.. The data is being imported, but the pipeline is not catching issues before or after they enter.. The fix is layered — pre-ingestion blocks bad records, post-ingestion catches systemic problems.

Pre-Ingestion Actions

1.. Presence check: Month is mandatory for monthly sales.. A sales record without a month value is meaningless — you cannot assign it to any reporting period.

- Action: Reject or flag records with NULL or missing month.. - Implementation: WHERE month IS NULL → reject batch or move to quarantine table.

2.. Range check: Sales cannot be negative.. A store cannot sell less than zero units or negative rupees.

- Action: Block negative values at entry.. - Implementation: IF sales_amount < 0 THEN reject.

3.. Format check: Month must be in the expected format (YYYY-MM).

- Action: Validate against regex pattern ^\d{4}-(0[1-9]|1[0-2])$.. - Implementation: Reject records where month does not match or parse to different formats.

4.. Data type check: Sales values must be numeric.

- Action: Reject non-numeric input (e.g., "N/A", "—", text).. - Implementation: IF NOT ISNUMERIC(sales_amount) THEN reject.

Post-Ingestion Actions

1.. Consistency check: Verify that monthly totals align with ledger totals.

- Compute: SUM of 12 monthly sales figures.. - Compare with: Annual total from accounting ledger.. - Tolerance: ±2% acceptable.. Beyond that → investigate.. - If 12 × monthly average ≠ annual total within tolerance → discrepancy.

2.. Business rule check: Sales cannot be negative at aggregate level.. Missing months must be flagged.

- For any month where sales are negative in aggregate → investigate (one store's negative might cancel another's positive, hiding the problem).. - Missing months: identify which store-month combinations are absent.. Flag for interpolation or manual review.

3.. Statistical check: Time series anomaly detection.

- Compute mean and standard deviation of monthly sales per store.. - Flag months where sales deviate more than 3 standard deviations from the store's mean.. - Visual check: plot each store's monthly sales as a line chart.. Look for sudden spikes, drops, or flatlines (which suggest missing data filled with a constant).

Tools

Third-party validation tools (Data Validation, SAP Pre-validation, Great Expectations) or custom validation scripts can automate these checks.. The key is that checks run automatically on every ingestion, not manually when someone remembers.

The retail case study integrates pre-ingestion (four checks), post-ingestion (three checks), and quality dimensions (completeness, accuracy, consistency) into one realistic scenario.. Expect exam questions in this format — a scenario described, and you map the relevant concepts.

Data Sources Categorization

Must-know: Classify every data source across five independent axes. Analog/digital, internal/external, primary/secondary, core/business, first/second/third-party. Classification determines validation rigor.

\[\text{Trust level} \propto \frac{1}{\text{Validation rigor required}}\]

⚠️ Top pitfall: Assuming third-party data is clean because it comes from a reputable source. Even NASA datasets contain gaps and inconsistent units. Always validate.

Self-check: A company imports customer data from a partner CRM. Is this internal or external? Primary or secondary? First, second, or third-party?

Database Selection

Must-know: Match primary access pattern to database type. Structured → relational, flexible → document, column analytics → column DB, search → Elasticsearch, time-stamped → time series, interconnected → graph. 20-keyword search maps to Elasticsearch.

\[\text{Primary access pattern} \rightarrow \text{Database type}\]

⚠️ Top pitfall: Picking a database because it is modern or popular rather than matching it to the access pattern. Use polyglot persistence — different databases for different workloads.

Self-check: A customer wants to search 20 keywords across all product issue descriptions. What database do you recommend and why?

Connects to: Data Access Patterns, Data Ingestion

Data Ingestion — ETL vs. ELT

Must-know: ETL transforms before loading (schema-on-write, consistency-first, known output). ELT loads raw then transforms (schema-on-read, flexibility-first, exploration). Four design decisions: time-interval vs size-based triggers, full snapshot vs differential, batch insert vs batch update, push vs pull.

\[\text{ETL: Extract} \rightarrow \text{Transform} \rightarrow \text{Load}\quad\quad\text{ELT: Extract} \rightarrow \text{Load} \rightarrow \text{Transform}\]

⚠️ Top pitfall: Using ETL when requirements are unknown (wastes rework) or ELT when strict governance is needed (compliance risk). Know when to use each.

Self-check: A data science team needs to explore customer behavior with unknown feature requirements. Should they use ETL or ELT? Why?

Connects to: Database Selection, Pre-Ingestion Validation, Post-Ingestion Validation

Data Contracts

Must-know: A written agreement between source system owner and ingestion team specifying: what data, extraction method, frequency/cadence, contacts, schema, format, and volume. Violating a contract (e.g., collecting equipment-level data when only factory automation data was agreed) is a data leakage and contract violation.

\[\text{Data contract} = \{\text{scope}, \text{method}, \text{frequency}, \text{contacts}, \text{schema}, \text{volume}\}\]

⚠️ Top pitfall: Treating the data contract as a formality. Scope creep — pulling extra columns 'because they seemed useful' — is how leakage begins. Update contracts when source systems change.

Self-check: An ingestion system accidentally collects equipment-level data when the contract only covers factory automation data. What two violations occurred?

Connects to: Data Lineage, Data Governance, Data Leakage

Data Lineage

Must-know: Documentation of data's journey: where it originates, how it transforms, where it surfaces. Produced by identifying assets, tracking from sources, documenting transformations, mapping pipeline paths, and pinpointing dashboards/reports. Answers: 'Where did this number come from?'

\[\text{Lineage} = \{\text{origin} \rightarrow \text{transformation}_1 \rightarrow \cdots \rightarrow \text{transformation}_n \rightarrow \text{consumption}\}\]

⚠️ Top pitfall: Assuming lineage is only for compliance. It is also for debugging, impact analysis, and trust. If you can't trace a number back to its source, you can't fully trust it.

Self-check: A CEO sees a suspicious number on a dashboard. How does data lineage help answer 'Where did this number come from?'

Connects to: Data Governance, Data Contracts, Data Quality Dimensions

Data Governance

Must-know: Standards and regulatory frameworks data pipelines must satisfy: GDPR (EU privacy), HIPAA (US healthcare), PII, PCI DSS (credit cards), DRP (disaster recovery). Governance must be designed into the pipeline from the start — not retrofitted.

\[\text{Governance} = \{\text{quality}, \text{security}, \text{availability}, \text{regulatory compliance}\}\]

⚠️ Top pitfall: Treating governance as a final check before going live. Retrofitting RBAC, audit logging, and retention into existing pipelines is far more expensive. Governance is a practice, not just a tool.

Self-check: What regulatory standard applies to healthcare data in the US? What standard applies to credit card data?

Connects to: Data Contracts, Data Lineage, RBAC

Pre-Ingestion Validation

Must-know: Four checks before data enters: presence (mandatory fields), range (bounds — BP can't be -2), format (email has @), data type (numeric fields). Also block SQL injection and alert on missing fields. Header file pattern verifies count, first, and last records.

\[\text{Pre-ingestion} = \{\text{Presence}, \text{Range}, \text{Format}, \text{Data type}\}\]

⚠️ Top pitfall: Skipping pre-ingestion because 'the source system already validates.' Source systems validate for their own purposes, not yours. Also: silently dropping bad records instead of rejecting and alerting.

Self-check: A monthly sales record has month = NULL and sales_amount = -500. Which pre-ingestion checks does it fail?

Connects to: Post-Ingestion Validation, Data Quality Dimensions, Data Contracts

Post-Ingestion Validation

Must-know: Three checks after data is stored: consistency (start < end, monthly totals = ledger), business rules (sales ≥ 0, referential integrity), statistical (anomaly detection, distribution checks). The audit table pattern: independently records what was loaded — separate from the loaded data itself.

\[\text{Post-ingestion} = \{\text{Consistency}, \text{Business rules}, \text{Statistical}\}\]

⚠️ Top pitfall: Confusing pre-ingestion and post-ingestion checks. A range check is pre-ingestion if applied at record entry; post-ingestion if applied at aggregate level. Both are needed — neither replaces the other.

Self-check: After loading 10,000 records, the audit table shows 9,987. What post-ingestion check caught this?

Connects to: Pre-Ingestion Validation, Data Quality Dimensions, ETL vs ELT

Data Quality Dimensions

Must-know: Ten dimensions. Accuracy (reflects reality), completeness (no missing fields), consistency (same across systems), validity (matches schema), timeliness (up to date), uniqueness (no duplicates). Plus integrity, lineage, reliability, accessibility. Measure each independently.

\[\text{Quality} = \bigcap_{d \in D} \text{dimension}_d,\quad D = \{\text{accuracy}, \text{completeness}, \ldots, \text{accessibility}\}\]

⚠️ Top pitfall: A dataset can score high on accuracy but low on completeness. Measure each dimension independently. The exam may ask which dimension a scenario describes.

Self-check: A dataset has all required fields populated but the values are systematically 10% too high. Which two quality dimensions are affected?

Connects to: Pre-Ingestion Validation, Post-Ingestion Validation, Data Bias

Data Leakage

Must-know: Unintentional introduction of target information that should not be available at prediction time. Causes: using target in features, including future timestamps, improper train/test split, error propagation through dependencies. #1 symptom: brilliant training performance, production failure. The aloo paratha analogy — looks perfect outside, undercooked filling ruins everything.

\[\text{Leakage check: Will this exact value be available at prediction time?}\]

⚠️ Top pitfall: Normalizing before splitting — the test set's statistics leak into training. Always split first, then compute normalization from training set only. Also: shuffling temporal data randomly.

Self-check: A model predicts Q3 sales using features that include Q4 economic indicators. What type of leakage is this?

Connects to: Data Bias, Data Drift, Pre-Ingestion Validation

Data Bias

Must-know: Systematic error that pushes results consistently in one direction — unlike noise, more data makes bias worse. Nine types: omitted variable, sponsorship, label, selection, collection, implicit, stereotype, experimental, reporting. AI must adhere to Fairness, Accountability, and Trustworthiness.

\[\text{Bias (systematic)} \neq \text{Noise (random)}\quad\text{More data amplifies bias — does not fix it}\]

⚠️ Top pitfall: Assuming more data fixes bias. Bias is systematic, not random. The bathroom scale that always reads 2 kg too high: weigh yourself 100 times, average is still 2 kg off.

Self-check: An A/B test runs only on weekdays. What type of bias does this introduce?

Connects to: Data Leakage, Data Drift, Data Quality Dimensions

Data Drift

Must-know: Growing mismatch between training and production data. Three types: data drift (schema skew — columns change; distribution skew — statistics shift), concept drift (input-output relationship changes), training-serving skew (different feature engineering code). Detect via model-based, statistical, or algorithm-based approaches.

\[\text{Drift} = P_{\text{train}}(X, y) \neq P_{\text{production}}(X, y)\]

⚠️ Top pitfall: Assuming the model is wrong when it's answering a different question. A 2019 house price model predicting 2026 prices is not broken — the world changed. Also: different code paths for training vs serving transform features differently.

Self-check: A model trained in 2019 predicts house prices. All feature distributions have shifted in production but the relationships are the same. What type of drift is this?

Connects to: PSI, KL Divergence, Data Leakage

Population Stability Index (PSI)

Must-know: Measures distribution shift of individual variables between training and new data. PSI < 0.1: low drift, no action. PSI 0.1-0.25: moderate drift, monitor. PSI > 0.25: significant drift, retrain. Formula: sum over bins of (P_i - Q_i) × ln(P_i/Q_i).

\[\text{PSI} = \sum_{i=1}^{n} (P_i - Q_i) \cdot \ln\left(\frac{P_i}{Q_i}\right)\]

⚠️ Top pitfall: PSI only measures distribution shift of individual variables — it does not detect concept drift. Small PSI with dropping accuracy means concept drift is the culprit.

Self-check: A credit scoring model has PSI = 0.32 for the applicant age feature. What action should the team take?

Connects to: KL Divergence, Data Drift, Post-Ingestion Validation

KL Divergence

Must-know: Measures information loss when using distribution Q to approximate P. Always ≥ 0; equals 0 only when P = Q. Not symmetric: D_KL(P∥Q) ≠ D_KL(Q∥P). Always use training as P (reference) and production as Q (comparison). Undefined when Q(x)=0 and P(x)>0 — use Laplace smoothing.

\[D_{KL}(P \parallel Q) = \sum_{x} P(x) \cdot \ln\left(\frac{P(x)}{Q(x)}\right)\]

⚠️ Top pitfall: Using the wrong order — D_KL(training ∥ production) ≠ D_KL(production ∥ training). Always use training as reference P. Also: KL is undefined when Q(x)=0 but P(x)>0 without smoothing.

Self-check: D_KL(P∥Q) = 0.069 for purchase amount distribution. Is this high or low drift? Should the team retrain?

Connects to: PSI, Data Drift, Entropy

Data Profiling

Must-know: Understanding what the data is before using it: summary statistics, data types, value distributions, dependencies, metadata. Profile every dataset before building a pipeline — you cannot validate what you don't understand.

\[\text{Profile} = \{\text{stats}, \text{types}, \text{distributions}, \text{dependencies}, \text{metadata}\}\]

⚠️ Top pitfall: Building a pipeline for data you haven't profiled. Surprises in data types, distributions, or missing values discovered mid-pipeline are far more costly to fix.

Connects to: Pre-Ingestion Validation, Data Quality Dimensions, Skewness

Skewness

Must-know: Asymmetry in data distribution. Positive (right) skew: mean > median (income data). Negative (left) skew: mean < median (age at death). Most ML algorithms assume normality. Fix with log transform (right-skewed), Box-Cox, or other transformations.

\[\text{Skewness coefficient: } \gamma = \frac{\frac{1}{n}\sum(x_i - \bar{x})^3}{\left(\frac{1}{n}\sum(x_i - \bar{x})^2\right)^{3/2}}\]

⚠️ Top pitfall: Using standardization (z-score) or min-max normalization to fix skewness — these center and scale but do not change the distribution shape. Use log or Box-Cox transforms instead.

Self-check: Income data has mean = 75,000 and median = 45,000. What type of skewness is present?

Connects to: Data Profiling, Data Quality Dimensions, PSI

Retail Sales Case Study — Complete Validation

Must-know: Integrates all checks. Pre-ingestion: presence (month), range (sales ≥ 0), format (YYYY-MM), data type (numeric). Post-ingestion: consistency (monthly = ledger), business rules (no negatives), statistical (3σ anomalies). Header file + audit table patterns work together.

\[\text{Validation pipeline} = \text{Pre-ingestion}_{4\text{ checks}} \rightarrow \text{Load} \rightarrow \text{Post-ingestion}_{3\text{ checks}} \rightarrow \text{Audit table verification}\]

⚠️ Top pitfall: Having great pre-ingestion but skipping post-ingestion. Pre-ingestion catches individual errors; post-ingestion catches systemic errors like ledger mismatches. Both are essential.

Self-check: A retail pipeline loads 200 stores' monthly sales. Pre-ingestion blocks negative values. Post-ingestion detects 12 monthly totals don't match the ledger. Which check caught the ledger mismatch?
