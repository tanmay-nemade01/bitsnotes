Chapter 1: Introduction and Foundations

1.1 Data Foundations

1.1.1 What is Data?

Before we discuss managing data, we must first understand what data is. In the simplest terms:

Data is a collection of raw, unprocessed facts, figures, symbols, or observations about the world. Data, by itself, carries no inherent meaning — it is simply a representation of something.

This definition is deceptively simple but profoundly important. Data is always mediated: it is a symbol or measurement that stands in for something in the real world. The number 1995 does not "mean" anything until we connect it to a referent. This is why the same raw value can serve completely different purposes depending on what it represents — and why context is everything.

Consider the number 1995. In isolation, it is just a number. It could represent:

  • A year of birth
  • A product price (₹1995)
  • A temperature reading (19.95°C)
  • A room number
  • The number of records in a dataset
  • A sensor reading from an industrial machine

Without context, data is meaningless. When we add context — "Birth year: 1995" — the data becomes information. This is the first step in the DIKW pyramid, which we explore below.

1.1.1.1 The TAVI Framework

One of the most important modern realizations about data is that it is not limited to numbers in tables. Data comes in many modalities, captured by the acronym TAVI:

TAVI stands for the four fundamental data modalities:

ModalityNameDescription / Examples
TTextDocuments, tweets, code, logs, emails, chat transcripts, web pages
AAudioSpeech recordings, music, podcasts, call center logs, environmental sounds
VVideoSurveillance footage, YouTube videos, dashcam feeds, medical imaging videos
IImagePhotographs, satellite imagery, X-rays, MRI scans, screenshots

Historically (25–30 years ago), most organizations only dealt with numerical and structured text data through Electronic Data Processing (EDP) teams. Anything beyond numbers was considered too difficult to process. Today, with advances in deep learning — CNNs for images (pioneered by LeCun, Krizhevsky et al.), RNNs and Transformers (Vaswani et al., 2017) for text and audio — we can extract value from all modalities. Modern embedding models like CLIP even bridge modalities, enabling text-to-image search. The TAVI framework reflects this reality: a modern data platform must handle all four, not just the structured subset.

1.1.2 The DIKW Pyramid

Data does not live in isolation. It feeds a hierarchy of increasing abstraction and value, known as the DIKW Pyramid:

The DIKW Pyramid (Data → Information → Knowledge → Wisdom) describes how raw observations are progressively refined into actionable insight. The model originated in the information science literature (Ackoff, 1989) and remains one of the most widely taught conceptual frameworks in data management.

The DIKW Pyramid: Data → Information → Knowledge → Wisdom

1.1.2.1 Detailed Breakdown

LevelDefinitionExample
Data Raw, unprocessed facts with no inherent meaning. Exist as isolated data points. 50, 200, 2
Information Data organized and given context; answers who, what, where, when. This is data that has been structured, categorized, and described. "I traveled 50 km, spent 200 INR, used 2 liters of petrol."
Knowledge Synthesized information revealing patterns, rules, and relationships; answers how. Knowledge involves connecting multiple pieces of information to derive a rule or generalization. "My bike gives 25 km/l mileage. Comparing with others: Honda gives 30 km/l, Apache gives 20 km/l."
Wisdom Deep understanding that enables sound judgment and decision-making; answers why and what to do. Wisdom incorporates values, ethics, and long-term thinking. "If I want the lowest running cost, I should choose the Honda. If I want performance, the Apache is better."
The DIKW Hierarchy with Concrete Examples

Key Insight: The higher you go in the pyramid, the more refined and abstract the content becomes, but also the more correct (reliable) it becomes, because noise and errors have been filtered out through successive levels of processing. Think of it this way: raw data often contains errors, outliers, and noise. As we process it into information (validating, cleaning), synthesize knowledge (cross-referencing, pattern-finding), and finally arrive at wisdom (testing against experience), each stage acts as a quality filter. This is why a seasoned expert's judgment (wisdom) is typically more reliable than a single raw measurement (data).

A common exam question: "Explain the DIKW pyramid with examples." Be prepared to define each level and give a concrete, real-world example that shows the progression from raw data to wisdom. Do not just list the four levels — demonstrate that you understand the transformations between them.

1.1.2.2 Types of Knowledge

The lecture made an important distinction between two types of knowledge. This distinction is crucial because organizations must manage both types differently:

  • Explicit Knowledge: Knowledge that is codified, documented, and easily transferable. Examples: textbooks, manuals, formulas, lecture slides, standard operating procedures, database schemas.
  • Tacit (Implicit) Knowledge: Knowledge that resides in people's minds, gained through experience. Hard to articulate and transfer. Examples: a doctor's diagnostic intuition, a musician's feel for rhythm, a senior DBA's instinct for query optimization, a data scientist's intuition about which features will matter.

Most organizations lose tremendous amounts of tacit knowledge when experienced employees leave or retire. This is sometimes called the "brain drain" problem. Data Management and Knowledge Management systems aim to capture and codify as much tacit knowledge as possible — through documentation, wikis, runbooks, and increasingly through AI-assisted knowledge extraction. This is one reason why data lineage and metadata management are critically important in modern data platforms.

1.1.3 Why Data Management for Machine Learning?

This is the central question of the course. The answer is both philosophical and practical, and it represents a fundamental shift in how we think about databases.

1.1.3.1 The Garbage-In, Garbage-Out (GIGO) Principle

Garbage In, Garbage Out (GIGO): The quality of output from any system is determined by the quality of its input. No matter how sophisticated your machine learning algorithm is, if you feed it poor-quality data, it will produce poor-quality results.

The GIGO principle has a long history — it originated in computer science in the 1950s and was popularized by IBM programmer George Fuechsel. But it takes on an especially urgent meaning in the machine learning era. In traditional software, if input data is wrong, the output is wrong for that transaction. With ML, bad training data produces a permanently degraded model that makes wrong predictions on all future transactions. The blast radius is enormous.

Imagine you are an expert swimmer. If the water is full of debris, floating obstacles, and thick sludge, your swimming skill becomes irrelevant — you cannot swim fast regardless of your technique. Similarly, an advanced deep learning model (like a Transformer or ResNet) cannot perform well if trained on messy, inconsistent, or irrelevant data. Case in point: In 2018, Amazon discovered that an internal recruiting ML model was biased against female candidates. The model had been trained on historical hiring data spanning 10 years — data that reflected pre-existing gender imbalances in the tech industry. The algorithm wasn't flawed; the training data was. GIGO in action.

1.1.3.2 The Role of Data in the ML Pipeline

A Machine Learning system is fundamentally a data processing pipeline. Every ML model is, at its core, a function that maps input data to output predictions. The quality and structure of the input data directly determines what the model learns:

The Machine Learning Pipeline: Raw Data → Preprocessing → Feature Engineering → ML Model → Predictions / Insights

Each stage of this pipeline depends on the output of the previous stage. A failure in any early stage cascades forward. This is known as the cascading failure pattern in data pipelines, and it is why data validation and monitoring at every stage are critical MLOps practices.

Why this course exists:

  • In the past (pre-AI era), databases were managed by humans. Humans ran SQL queries, viewed results, and made decisions. The machine simply executed logic.
  • Now, machines learn from data. We feed data to models, and models derive patterns autonomously. The machine's performance depends entirely on the data it receives.
  • Therefore, Data Management and Machine Learning must be synergized. Good data management enables good ML; good ML can also help manage data better (e.g., anomaly detection, data cleaning automation, metadata generation, automated schema inference).

This bidirectional relationship — data enables ML, ML improves data management — is sometimes called the data-ML flywheel. Better data → better model → better data insights → even better data → even better model.

1.1.3.3 Truths About Big Data

Modern data environments are characterized by several hard truths that every data practitioner must internalize. These are not merely theoretical — they are operational realities faced daily in industry:

  1. Volume: Terabytes to petabytes of data are generated daily. Walmart handles ~2.5 petabytes of data per hour from customer transactions alone. The Large Hadron Collider generates ~90 petabytes per year. Storage is cheap, but managing data at this scale creates entirely new classes of engineering problems.
  2. Velocity: Data streams in real-time from IoT devices, social media, financial transactions. Twitter processes ~500 million tweets per day. Stock exchanges handle millions of trades per second. Batch processing (daily ETL) is insufficient for use cases requiring sub-second latency.
  3. Variety: Data comes in all TAVI modalities and formats. A single healthcare organization may have: structured lab results in SQL tables, unstructured doctor's notes as free text, DICOM medical images, ECG waveform data, and HL7/FHIR message streams — all of which need to be correlated to understand a single patient.
  4. Data Silos: Data gets isolated within departments or teams, preventing a unified view. Silos lead to duplication, inconsistency, and delayed decision-making. A customer's address might exist in three different systems — CRM, billing, and support — each slightly different, with no single source of truth.
  5. Changing Priorities: The value of data changes over time. Yesterday's noise may be today's signal. During COVID-19, supply chain data that was previously low-priority suddenly became critically important.
  6. Aging Data: Data can become stale; what was relevant a year ago may no longer be valid. Models trained on pre-pandemic consumer behavior failed spectacularly in 2020–2021.

Data Silos are isolated pockets of data within an organization that are not easily accessible by other parts of the organization. They arise from organizational structure (departmental boundaries), incompatible systems (different vendors, different schemas), or lack of data governance. Silos prevent collaboration and lead to inconsistent decision-making. Data integration — breaking down silos through shared data platforms, APIs, and governance frameworks — is one of the hardest and most impactful challenges in enterprise data management.

Exam-relevant: Be able to list and explain the key challenges of modern data environments: the 3 V's (Volume, Velocity, Variety), data silos, and the GIGO principle. A good answer connects them: volume and velocity make it harder to catch data quality issues, which amplifies the GIGO risk.

Chapter 2: Data Quality

1.2 Data Quality Assessment

1.2.1 What Makes Data "High Quality"?

The quality of data is not a single attribute but a collection of dimensions or parameters. Like a doctor diagnosing a patient by checking multiple vital signs (temperature, blood pressure, heart rate, oxygen saturation), a data engineer must assess data across multiple quality dimensions. No single metric captures data quality — you need a dashboard.

Data Quality refers to the condition of a dataset based on factors such as accuracy, completeness, consistency, reliability, and whether it is fit for its intended purpose. Quality is always relative to the use case: data that is "high quality" for one application may be inadequate for another. A dataset of customer addresses updated last month is high quality for shipping products but low quality for real-time fraud detection.

1.2.2 The Core Quality Dimensions

The eight dimensions below form a comprehensive framework for assessing data quality. They are sometimes called the ACCVTUI dimensions (mnemonic: "Accuracy Comes Before Completeness; Validity, Timeliness, Uniqueness, Integrity").

DimensionDescriptionExample of Violation
Accuracy Data correctly reflects the real-world entity or event it represents. Accuracy is about correctness relative to ground truth. A customer's age recorded as 250 years. A temperature sensor reading 500°C in a server room.
Completeness All required data is present; no essential fields are missing. Completeness can be assessed at the record level or the field level. A customer record with the email field left blank. A sales transaction with no timestamp.
Consistency Data values are uniform and coherent across datasets and systems. The same entity should have the same attributes everywhere. One system records distance in km, another in miles for the same field. A customer's status is "Active" in CRM but "Inactive" in billing.
Validity Data conforms to specified formats, rules, or domain constraints. Validity checks whether data meets syntactic and semantic rules. A date field containing 32/13/2025. A phone number field containing alphabetic characters. An email field with no "@" sign.
Timeliness Data is up-to-date relative to the needs of the analysis. Timeliness is always relative to the consumption rate. Using last year's customer address for a delivery today. A stock trading model using prices delayed by 15 minutes.
Uniqueness No duplicate records exist for the same entity. A single real-world entity maps to exactly one record. The same customer appears three times with slight name variations: "John Doe", "J. Doe", "John D."
Integrity Referential relationships between data are maintained. Foreign key references resolve correctly. An order referencing a customer_id that does not exist in the customer table (orphan record).
Interpretability Data is clearly labeled and understandable. Metadata, documentation, and naming conventions make the data usable. A column named X1 with no documentation of what it represents. A dataset with no data dictionary.
The Eight Core Dimensions of Data Quality

Mnemonic: ACCVTUI — Accuracy, Completeness, Consistency, Validity, Timeliness, Uniqueness, Integrity, Interpretability. Remember this sequence — it is the checklist you should mentally run through every time you encounter a new dataset.

Real-world scenario: You are building a churn prediction model for a telecom company. You receive the customer dataset and find:

  • Some customers have no contract start date (Completeness issue)
  • Monthly charges are in USD for some rows, INR for others (Consistency issue)
  • A customer's tenure shows 500 months, but the company is only 10 years old (Accuracy issue)
  • Phone numbers contain alphabetic characters (Validity issue)
  • The same customer appears under John Doe, J. Doe, and John D. (Uniqueness issue)

You must fix ALL of these before training the model — otherwise, GIGO applies. If even 5% of your training data is bad, the model will learn from that noise, and its predictions on new data will be unreliable. For churn prediction, this could mean failing to identify at-risk customers (false negatives) or offering discounts to loyal customers who would have stayed anyway (false positives) — both costly errors.

1.2.3 Common Data Quality Issues and Fixes

IssueDescriptionCommon Fix
Missing Values Fields left empty or NULL. Can be MCAR (Missing Completely At Random), MAR (Missing At Random), or MNAR (Missing Not At Random). Imputation (fill with mean, median, mode, or constant); or remove the row/column if too sparse. The choice depends on the missingness mechanism.
Inconsistent Formats Same data represented differently across records or systems. Standardize to a single format (e.g., all dates as YYYY-MM-DD, all currencies in a single unit).
Duplicate Records Same entity recorded multiple times, often with minor variations. Deduplication using fuzzy matching (Levenshtein distance, Jaccard similarity) or exact keys. Tools like OpenRefine help with this.
Outliers Values far outside the expected range. Can be genuine or erroneous. Investigate; either remove if erroneous, or cap/transform (Winsorization, log transform) if genuine but extreme.
Unit Mismatch Different units for the same measure within a column. Convert all values to a common unit (e.g., all distances to kilometers, all currencies to a base currency).
Encoding Issues Corrupted characters from wrong encoding (e.g., Latin-1 is interpreted as UTF-8). Detect the actual encoding (using tools like chardet in Python) and convert to UTF-8 uniformly.
Frequent Data Quality Issues and Remediation Strategies

Data Imputation is the process of replacing missing data with substituted values. The choice of strategy matters and affects downstream analysis:

  • Mean/Median imputation for numerical columns — simple but reduces variance. Median is preferred if the distribution is skewed because it is robust to outliers.
  • Mode imputation for categorical columns — impute the most frequent category.
  • Forward/Backward fill for time-series data — assumes temporal continuity. Forward fill carries the last known value forward; backward fill uses the next known value.
  • K-Nearest Neighbors (KNN) imputation for more sophisticated filling — finds similar records and uses their values. Computationally more expensive but preserves relationships between features better than mean imputation.
  • Constant value (e.g., "Unknown" for missing categories) — simple but can introduce bias if "Unknown" becomes a meaningful category to the model.
  • Multiple Imputation: Generate several plausible imputed datasets and pool results — this accounts for imputation uncertainty and is considered the gold standard in statistical analysis.

Exam Tip: You may be given a sample dataset and asked to (a) identify data quality issues across all eight dimensions, and (b) propose remediation strategies with justification. Practice this skill with real datasets (Kaggle has many). The ability to "diagnose" data like a doctor is a core competency tested in this course. When proposing fixes, always justify why that specific strategy is appropriate for the specific issue — don't blindly apply mean imputation to every missing value.

Chapter 3: Types of Data

1.3 Data Classification

Data is broadly classified by the degree of organization it possesses. The three primary categories — and one hybrid — form a spectrum, not discrete bins. Understanding where your data falls on this spectrum helps you choose the right storage, processing, and analysis strategies.

1.3.1 Structured Data

Structured Data is data that adheres to a rigid, predefined schema — a blueprint that defines the organization, format, and constraints of the data. It is typically stored in relational databases in rows and columns (tables). Every record has exactly the same fields, with the same data types.

Examples of structured data:

  • Excel spreadsheets with defined column headers
  • SQL database tables (e.g., EMPLOYEES, ORDERS, PRODUCTS)
  • CSV files with consistent columns
  • Point-of-sale transaction records
  • Financial ledger entries (debits/credits with date, amount, account)
AdvantagesDisadvantages
Easy to query (SQL) with powerful JOINs and aggregations Rigid — schema changes (adding columns, changing types) are expensive and often require downtime
Fast retrieval and indexing (B-tree, hash indexes) Cannot capture complex, flexible relationships naturally
Strong data integrity (ACID transactions, constraints, foreign keys) Limited to predefined categories — sparse data wastes space
Simple to understand and visualize Does not naturally represent unstructured content like free text or images
Advantages and Disadvantages of Structured Data

1.3.1.1 Schemas

A Schema is the structural definition of a database. It specifies:

  • Tables and their names
  • Columns (attributes) and their data types (INT, VARCHAR, DATE, FLOAT, etc.)
  • Constraints (primary keys, foreign keys, unique, not null, check constraints)
  • Relationships between tables
  • Indexes for query optimization

In structured data, the schema is schema-on-write — you define the structure before you insert data. Any data that does not conform is rejected at write time. This is the defining characteristic of RDBMS systems.

1.3.2 Unstructured Data

Unstructured Data has no predefined schema or organizational structure. It does not fit neatly into rows and columns. It constitutes approximately 80–90% of all data generated today, and this percentage is growing as more human communication becomes digital.

Examples of unstructured data:

  • Social media posts (tweets, Facebook updates, Instagram captions)
  • News articles and blog posts
  • Audio recordings (podcasts, call center logs, voice memos)
  • Video files (surveillance, YouTube, TikTok)
  • Images (photographs, X-rays, satellite imagery, memes)
  • Raw text documents, PDFs, emails (body content)
  • Server logs (raw, before parsing)
AdvantagesDisadvantages
Highly flexible — stores literally anything without pre-definition Difficult to query and search; requires full-text indexing or vector search
Captures rich, nuanced human communication Requires preprocessing before ML use (NLP, OCR, speech-to-text, embedding extraction)
No schema design overhead — ingest first, structure later Storage and retrieval can be inefficient for point queries
Natural fit for human-generated content Hard to enforce data quality — no constraints at write time
Advantages and Disadvantages of Unstructured Data

1.3.3 Semi-Structured Data

Semi-structured Data contains some organizational markers (like tags, keys, or metadata) but does not conform to a rigid table structure. It is a middle ground between structured and unstructured data — structured enough to be machine-parsed reliably, but flexible enough to accommodate variation.

Examples:

  • JSON and XML files — nested key-value pairs, arrays, hierarchical structures
  • Emails (structured headers: To, From, Subject, Date; unstructured body with free-form text)
  • HTML web pages (tags provide structural markup; text content is free-form)
  • NoSQL document databases (MongoDB, CouchDB) — each document in a collection can have different fields
  • YAML configuration files — human-readable, indentation-based structure

Semi-structured data follows a schema-on-read approach — the structure is interpreted at the time of reading, not enforced at the time of writing. This provides flexibility while retaining some organizational benefits. A new field can be added to some documents without affecting others. This is the fundamental philosophy behind NoSQL document stores and data lakes: store now, schema later.

1.3.4 Quasi-Structured Data

Quasi-structured Data is loosely organized, often inconsistent, but still exhibits patterns that can be parsed and processed with some effort. It sits somewhere between semi-structured and unstructured data on the spectrum. The key insight is that it looks structured but isn't consistently so.

Examples:

  • Web server logs — format varies across servers (Apache vs. Nginx vs. IIS), and custom log formats are common
  • Clickstream data — varying query parameters, inconsistent field presence
  • System event logs — each application logs differently
  • Data scraped from websites with varying layouts across pages
  • Email bounce messages from different mail servers — each has a different format for the same error

Quasi means "apparently but not really." Quasi-structured data looks like it has structure but upon closer inspection is inconsistent. It often requires custom parsing logic, regular expressions, or log parsers (like Logstash, Fluentd) rather than being directly loadable into a structured system.

1.3.5 The Data Structure Spectrum

Rather than four discrete categories, it is more accurate to think of a continuum. At one extreme: rigid, validated, schema-on-write (RDBMS). At the other: free-form, no schema, human-friendly (raw video). Real-world data systems often sit somewhere in between.

Semi-StructuredJSON, XML, NoSQL, EmailSchema-on-readPossesses self-describing tags or markers, flexible.
Quasi-StructuredWeb Logs, Clickstream dataSchema-on-readLoosely formatted, requires parsing to extract structure.

The Data Structure Spectrum: trade-off between flexibility and queryability

A classic exam question: "Compare and contrast structured, semi-structured, and unstructured data. Provide two examples of each." Know the definitions, examples, and the trade-offs (flexibility vs. queryability). Be prepared to place quasi-structured data correctly on the spectrum and explain why it deserves its own category.

Chapter 4: Data Models

1.4 Data Models

1.4.1 What is a Data Model?

A Model is an abstract representation of something — a simplified version that captures the essential features while omitting irrelevant details. All models are wrong (they simplify reality), but some models are useful (they capture what matters for a particular purpose). A Data Model is a conceptual framework that defines how data is structured, stored, organized, and manipulated within a system.

Think of a model like a blueprint of a building. The blueprint is not the actual building — it is a representation that shows the structure, relationships between rooms, and layout. Similarly, a data model shows how data elements relate to each other without being the actual data. An architect uses one blueprint for plumbing and another for electrical; similarly, different data models serve different purposes.

Data models answer three fundamental questions:

  1. How is the data organized? (structure — what are the containers?)
  2. How are elements related? (relationships — how do entities connect?)
  3. How can we query and manipulate it? (operations — what questions can we ask?)

1.4.2 The Five Major Data Models

1.4.2.1 Relational Data Model

The Relational Model, introduced by E.F. Codd in his seminal 1970 paper "A Relational Model of Data for Large Shared Data Banks", organizes data into relations (tables). Each relation is a set of tuples (rows), and each tuple consists of attributes (columns). Data is manipulated using Structured Query Language (SQL). Codd's insight was to separate the logical organization of data from its physical storage — a radical idea at the time, when databases were tied to their physical disk layout.

TermMeaning
RelationA table (e.g., STUDENTS) — mathematically, a subset of the Cartesian product of domains
TupleA row in a table (a single record) — corresponds to a single entity instance
AttributeA column in a table (a field/property) — a named role in the relation
DomainThe set of allowable values for an attribute (e.g., AGE must be an integer between 0 and 150)
Primary KeyA unique identifier for each tuple — guarantees entity integrity
Foreign KeyAn attribute that references a primary key in another relation — guarantees referential integrity
Candidate KeyA minimal set of attributes that uniquely identifies each tuple (all candidate keys, one chosen as primary)

The normalized design eliminates duplication: each student exists once, each course exists once, and the many-to-many relationship between students and courses is modeled through the Enrollments junction table. Updates are now safe: changing an instructor name only requires updating one row in the Courses table.

Normalization is the process of organizing data to reduce redundancy and improve integrity. It involves decomposing tables into smaller, well-structured tables and defining relationships between them. The stages are called normal forms:

  • 1NF (First Normal Form): No repeating groups; every attribute is atomic (single-valued). Each cell contains exactly one value.
  • 2NF (Second Normal Form): 1NF + no partial dependency — every non-key attribute depends on the entire primary key, not just part of it. This matters for tables with composite keys.
  • 3NF (Third Normal Form): 2NF + no transitive dependency — non-key attributes depend only on the primary key, not on other non-key attributes. This eliminates cascading update anomalies.
  • BCNF (Boyce-Codd Normal Form): A stronger version of 3NF where every determinant must be a candidate key. Rarely needed in practice, but important for edge cases.
  • 4NF and 5NF: Deal with multi-valued dependencies and join dependencies. Mostly theoretical for real-world applications.

Practical guidance: For most applications, 3NF is the sweet spot — it provides strong data integrity with reasonable query complexity. Over-normalization (beyond BCNF) can lead to excessive JOINs and degraded query performance. Many data warehouses deliberately denormalize (star schema, snowflake schema) to optimize for read performance at the cost of some redundancy.

1.4.2.2 Hierarchical Data Model

The Hierarchical Model organizes data in a tree-like structure with parent-child relationships. Each child node has exactly one parent, forming a strict hierarchy (a 1:N relationship pattern). It is one of the oldest data models, dating back to IBM's Information Management System (IMS) in the 1960s, which was developed for the Apollo space program to manage the massive bill of materials for the Saturn V rocket.

A Hierarchical Data Model: Taxonomic Classification

Real-world uses:

  • XML documents — nested tags form a tree (root element with child elements)
  • Windows Registry Editor — keys and subkeys in a strict hierarchy (HKEY_LOCAL_MACHINE → SOFTWARE → Microsoft → ...)
  • File systems — folders containing subfolders (no file has two parent directories)
  • Organizational charts — CEO → VP → Director → Manager (each person has exactly one direct manager)
  • DNS hierarchy — root → TLD → domain → subdomain
AdvantagesDisadvantages
Simple and intuitive for naturally nested dataRigid — one parent per child; real-world relationships are often many-to-many
Fast traversal along hierarchy (parent-to-child, depth-first)Many-to-many relationships require data duplication or awkward pointer systems
Good for XML, configuration data, and document structuresRedundancy if data doesn't naturally fit the tree — cross-links are hard
Predictable access patternsQuerying across branches (e.g., "find all grandchildren of X that satisfy condition Y") requires procedural code, not declarative queries

1.4.2.3 Graph Data Model

The Graph Model represents data as nodes (entities or vertices) and edges (relationships or arcs). Unlike the hierarchical model, any node can connect to any other node, enabling rich, many-to-many relationship modeling. Both nodes and edges can have properties (key-value pairs), making this a property graph model. Graph theory, a branch of discrete mathematics dating back to Euler's 1736 solution to the Königsberg bridge problem, provides the formal foundation.

A Simple Graph Data Model: Customer → Order → Product ← Supplier

Popular graph databases and use cases:

  • Neo4j — the leading native graph database, uses Cypher query language
  • Amazon Neptune — AWS managed graph service supporting both Property Graph (Gremlin) and RDF (SPARQL)
  • Social networks: "Who are the friends of my friends?" (LinkedIn's People You May Know, Facebook's friend recommendations)
  • Recommendation engines: "People who bought X also bought Y" — collaborative filtering as graph traversal
  • Fraud detection: "Find circular payment patterns" — money-laundering rings often form cycles in transaction graphs
  • Knowledge graphs: Google's Knowledge Graph (500B+ facts about 5B+ entities), LinkedIn's Economic Graph
  • Network and IT operations: Dependency graphs, service topology maps, impact analysis

Graph databases excel at answering path-based queries (e.g., shortest path, friend-of-a-friend, graph traversal) that would require expensive recursive JOINs or Common Table Expressions (CTEs) in a relational database. In a relational database, finding all friends-of-friends at depth 3 could require multiple self-JOINs; in a graph database, it is a simple MATCH (a)-[:KNOWS*1..3]-(b) traversal. The performance difference is measured in orders of magnitude for deep traversals — this is known as the JOIN bomb problem in relational databases.

1.4.2.4 Document Data Model

The Document Model stores data as self-contained documents, typically in JSON, BSON (Binary JSON), or XML format. Documents are grouped into collections (analogous to tables, but without schema enforcement). Each document can have a different structure, providing schema flexibility. This is the dominant model in modern web and mobile application backends.

1.4.2.5 Key-Value Data Model

The Key-Value Model is the simplest data model — essentially a distributed hash map. Data is stored as a collection of key-value pairs, where each unique key maps to a value. The value can be a simple string, number, JSON object, or even a binary blob — the database treats it as opaque. Operations are minimal: get(key), put(key, value), delete(key). This simplicity enables extreme performance.

Key-Value Store Example (like Redis):

KeyValue

Keys are typically structured with colons as namespace separators (user:1001:name). This is a convention, not a database-enforced hierarchy — the database treats the key as an opaque string.

Popular key-value stores:

  • Redis — in-memory key-value store with optional persistence. Supports data structures beyond simple strings: lists, sets, sorted sets, hashes, streams. Widely used for caching, session management, rate limiting, and real-time leaderboards. Sub-millisecond latency.
  • Amazon DynamoDB — managed key-value and document database. The 2007 Dynamo paper (DeCandia et al.) launched the NoSQL movement. Provides predictable single-digit-millisecond performance at any scale.
  • etcd — distributed key-value store using the Raft consensus algorithm. Used by Kubernetes to store all cluster state. Strongly consistent.
  • Riak — distributed key-value database inspired by Amazon's Dynamo paper. Eventually consistent, highly available.

MongoDB is technically both a document database and a key-value store — each document is identified by a unique _id key, but the value is a rich JSON/BSON document rather than an opaque blob. You can use MongoDB as a simple key-value store (db.collection.findOne({_id: key})), but you get the added benefit of querying, indexing, and aggregating the document contents.

1.5.2 Row-Oriented vs. Column-Oriented Storage

This distinction is one of the most consequential design choices in data systems, and it maps directly to the OLTP vs. OLAP workload distinction:

  • Row-oriented storage: Data is stored row by row. All fields of a single record are stored contiguously on disk. Best for OLTP (Online Transaction Processing) where you frequently read/write entire records. Examples: CSV, Avro, most relational databases (MySQL, PostgreSQL).
  • Column-oriented storage: Data is stored column by column. All values for a single column across all rows are stored contiguously. Best for OLAP (Online Analytical Processing) where you aggregate over a few columns across millions of rows. Examples: Parquet, ORC, columnar databases (ClickHouse, Vertica, Amazon Redshift).

Why columnar storage is faster for analytics: When you run SELECT AVG(salary) FROM employees WHERE department = 'Engineering', a columnar store only reads two columns (salary and department) from disk, skipping all others. A row store reads every column of every row. If the table has 200 columns, the columnar store reads ~1% of the data the row store reads. Additionally, columnar formats compress much better because values within a single column tend to be similar (low cardinality columns like "department" compress extremely well with dictionary encoding).

Row-Oriented vs. Column-Oriented Storage Layout
  • OLTP (Online Transaction Processing): Frequent reads/writes of individual records, typically via primary key. High concurrency, many small transactions. Use row-oriented storage. Example: Banking system recording individual transactions, e-commerce checkout.
  • OLAP (Online Analytical Processing): Aggregate queries over large datasets. Few columns accessed per query, but millions of rows scanned. Use column-oriented storage. Example: "Average monthly sales per product category over the last 5 years, broken down by region."

Historical context: The term OLTP was coined by Jim Gray in the 1970s. OLAP was defined by E.F. Codd (the same Codd of the relational model) in 1993. The separation between these two workload types is a fundamental principle of data architecture — you typically do not run analytics directly on your operational database because it would slow down user-facing transactions. Instead, you replicate data to a separate analytical system (data warehouse, data lake).

Chapter 6: Data Processing Concepts

1.6 Data Processing Concepts

1.6.1 ETL vs. ELT

Two fundamental patterns for moving and transforming data. Understanding their evolution helps you understand the broader shift in data architecture over the past two decades.

  • ETL (Extract, Transform, Load): Data is extracted from sources, transformed (cleaned, enriched, aggregated, joined) on an intermediate processing server, and then loaded into the target system. Transformation happens before loading. This is the traditional approach, dominant from the 1990s through the 2010s, when data warehouses were expensive and you wanted to store only clean, processed data.
  • ELT (Extract, Load, Transform): Data is extracted and loaded into the target system first (as raw data), and then transformed in-place using the target system's compute power. Transformation happens after loading. This is the modern approach enabled by cloud data warehouses (Snowflake, BigQuery, Redshift Spectrum) that separate compute from storage and can scale elastically.
ETL vs. ELT Comparison

Why the shift to ELT? Cloud data warehouses offer massive, elastic compute that can be scaled up for transformation jobs and scaled down when idle. With ETL, you need to provision and maintain intermediate servers big enough for peak transformation workloads — and you pay for them 24/7. With ELT, the target warehouse handles the transformation, and you only pay for the compute you use. ELT also preserves the raw data, which is valuable for reprocessing — if you discover a bug in your transformation logic, you can re-transform from the raw data without re-extracting from source systems.

1.6.2 EDA: Exploratory Data Analysis

Exploratory Data Analysis (EDA) is the process of investigating datasets to discover patterns, spot anomalies, test hypotheses, and check assumptions using summary statistics and graphical representations. The term was coined by statistician John Tukey in his 1977 book Exploratory Data Analysis, where he argued that data analysis should be an investigative, iterative process rather than a purely confirmatory one. EDA is typically the first step after data collection in any data science or ML project — before building models, you must understand what is in your data.

  • Techniques: Histograms (distribution shape), box plots (outlier detection, quartile ranges), scatter plots (relationships between variables), correlation matrices (linear relationships), missing value heatmaps, pair plots, time series decomposition
  • Goal: Understand the data's structure, quality, and patterns before modeling. This understanding informs feature engineering, model selection, and data quality remediation.
  • Tools: Python (pandas, matplotlib, seaborn, plotly), R (ggplot2, dplyr), Excel (basic), Jupyter Notebooks (interactive environment)
  • Key outputs: Descriptive statistics (mean, median, std, min, max, quartiles), data types per column, missing value counts, correlation heatmap, distribution plots, and a prioritized list of data quality issues to fix

1.6.3 The ML Pipeline

An ML Pipeline is an end-to-end workflow that automates the flow of data into and through a machine learning model. It includes data ingestion, preprocessing, feature engineering, model training, evaluation, and deployment. Pipelines make ML workflows reproducible, testable, and maintainable — without them, you have fragile, manual, one-off processes that are impossible to debug or audit.

Data
Ingestion → Data
Preprocessing → Feature
Engineering → Model
Training → Evaluation → Deployment

↻ Iterate & Improve (feedback loop from Evaluation back to Feature Engineering)

A Typical Machine Learning Pipeline with Feedback Loop

Each stage has specific responsibilities:

  1. Data Ingestion: Collect raw data from sources (databases, APIs, files, streams). Handle authentication, rate limiting, incremental extraction, and data versioning. Tools: Apache Kafka, AWS Kinesis, Airbyte, Fivetran.
  2. Data Preprocessing: Clean and prepare data — handle missing values, remove duplicates, standardize formats, normalize/scale numerical features, encode categorical variables. This is where the data quality work from Chapter 2 is applied systematically.
  3. Feature Engineering: Transform raw fields into features that the model can learn from. Create interaction features, aggregate features, domain-specific transformations. This is often the most creative and high-impact stage — a well-engineered feature can beat a more complex model.
  4. Model Training: Select algorithm, split data (train/validation/test), train model, tune hyperparameters. Use cross-validation to get reliable performance estimates.
  5. Evaluation: Measure model performance on held-out test data using appropriate metrics (accuracy, precision, recall, F1, ROC-AUC, RMSE — depending on the problem type). Compare against baseline models. Check for overfitting and bias.
  6. Deployment: Package model, serve predictions via API, monitor performance in production, detect data drift and model drift, trigger retraining when needed. Tools: Docker, Kubernetes, MLflow, Seldon, BentoML.
