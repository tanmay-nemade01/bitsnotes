Markov Decision Processes and Dynamic Programming

5.1 MDP Review and Agent-Environment Interface

Hook: How do you teach a machine to make good decisions — not just now, but for the rest of its "life"? Reinforcement learning answers this with a formal math framework called a Markov Decision Process. Every RL algorithm you will ever see builds on this foundation.

5.1.1 Definition and Explanation

Intuition + Analogy: Think of an ice cream shop. You (the agent) walk in and pick a flavor (the action). The shop (the environment) hands you a cone and charges you (the reward). The shop's menu and your hunger level together form the state. An MDP is just a clean way to write down this loop: state → action → reward → new state.

Where the analogy breaks: in an MDP, the environment can be random. The same action in the same state might lead to different outcomes. Also, the agent cares about the total reward over time, not just today's cone.

A Markov Decision Process (MDP) is the mathematical framework for formulating reinforcement learning problems. It gives RL algorithms a formal structure to work within.

An MDP is defined by the tuple \((S, A, p, r, \gamma)\), where:

  • \(S\) — the state set — all possible situations the agent can face
  • \(A\) — the action set — all choices available to the agent (we sometimes write \(A(s)\) when the available actions depend on the state)
  • \(p(s', r | s, a)\) — the dynamics function — the probability of landing in state \(s'\) with reward \(r\) given you were in state \(s\) and took action \(a\). This function fully defines how the environment behaves.
  • \(r\) — the reward — a scalar signal the agent receives after each action
  • \(\gamma\) — the discount factor — a number in \([0, 1)\) that controls how much the agent values future rewards

The agent-environment boundary is a key concept. Everything the agent can control (its choices) sits on one side. Everything it cannot change sits on the other side — that is the environment. This includes the rules of the world, the reward function, and even the agent's own sensors and actuators (the agent cannot arbitrarily change its camera; it can only choose actions). The textbook puts it well: "anything that cannot be changed arbitrarily by the agent is considered to be outside of it."

At each time step \(t\), the agent and environment produce a trajectory:

\[ S_0, A_0, R_1, S_1, A_1, R_2, S_2, A_2, R_3, \ldots \]

The agent sees state \(S_t\), picks action \(A_t\), and the environment returns reward \(R_{t+1}\) and next state \(S_{t+1}\). This loop repeats.

The dynamics function satisfies:

\[ \sum_{s' \in S} \sum_{r \in R} p(s', r | s, a) = 1 \quad \text{for all } s \in S, \, a \in A(s) \]

From \(p\), we can derive:

  • State transition probabilities: \(p(s' | s, a) = \sum_{r} p(s', r | s, a)\)
  • Expected reward for state-action pairs: \(r(s, a) = \sum_{r} r \sum_{s'} p(s', r | s, a)\)

5.1.2 Symbol Registry

  • \(S\) — state set — finite set of all possible states
  • \(A\) or \(A(s)\) — action set — finite set of available actions (may depend on state)
  • \(p(s', r | s, a)\) — dynamics function — probability of next state \(s'\) and reward \(r\) given state \(s\) and action \(a\)
  • \(R_t\) — reward at time \(t\) — scalar
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(S_t\) — state at time \(t\) — element of \(S\)
  • \(A_t\) — action at time \(t\) — element of \(A\)

The Markov property means the future depends only on the current state, not on how you got there. Formally:

\[ P(S_{t+1} | S_t, A_t, S_{t-1}, A_{t-1}, \ldots) = P(S_{t+1} | S_t, A_t) \]

If the state captures all relevant history, the Markov property holds. This is a restriction on what counts as a state, not on the problem itself.

Core Definition: A finite MDP has finite sets \(S\), \(A\), and \(R\). The dynamics function \(p(s', r | s, a)\) gives a complete probability distribution over next states and rewards for every state-action pair. The Markov property ensures that \(p\) captures everything the environment needs to know.

5.1.3 Worked Examples

Example 1 — Traffic Control

  • State: Current traffic conditions at each intersection (queue lengths, signal phase)
  • Action: Which signal phase to activate (green for north-south, green for east-west, etc.)
  • Reward: A measure of traffic flow efficiency — higher throughput means higher reward
  • Dynamics: How traffic queues change based on signal choices and arrival rates

The Markov property holds if the state captures all current queue lengths and phases — we do not need to know what happened five minutes ago.

Example 2 — Atari Game (e.g., Pong)

  • State: The raw game frame (pixel values on screen)
  • Action: Controller inputs (up, down, or nothing)
  • Reward: Score change from the previous frame (+1 when you win a point, −1 when you lose)
  • Dynamics: The game engine determines how the ball and paddles move

The full pixel frame is Markov — it tells you everything about the current game situation.

Example 3 — Recycling Robot

A mobile robot collects empty soda cans in an office. Its battery has two distinguishable levels: high and low.

  • State: Battery level — \(S = \{\text{high}, \text{low}\}\)
  • Actions: \(A(\text{high}) = \{\text{search}, \text{wait}\}\); \(A(\text{low}) = \{\text{search}, \text{wait}, \text{recharge}\}\)
  • Reward: +1 per can collected, −3 if the battery depletes and the robot needs rescue

Transition dynamics (from the textbook):

State Action Next State Probability Expected Reward
high search high \(\alpha\) \(r_{\text{search}}\)
high search low \(1 - \alpha\) \(r_{\text{search}}\)
low search high \(1 - \beta\) \(-3\)
low search low \(\beta\) \(r_{\text{search}}\)
high wait high 1 \(r_{\text{wait}}\)
low wait low 1 \(r_{\text{wait}}\)
low recharge high 1 0

Here \(\alpha\) is the probability that searching keeps the battery high, and \(\beta\) is the probability that searching while low keeps it low (rather than depleting it). Note that \(r_{\text{search}} > r_{\text{wait}}\) — searching is more rewarding but riskier.

This table is the complete dynamics function \(p(s', r | s, a)\) for the recycling robot. Every row sums to 1 across next states for each state-action pair.

Assumptions & Scope:

  • Markov property: The state must capture everything relevant. If the robot's battery degrades over time and the state only tracks "high" vs "low", the Markov property is violated — you need to track battery age too.
  • Finite sets: The theory here assumes finite \(S\), \(A\), and \(R\). Continuous problems (like controlling a robot arm with real-valued angles) need extra machinery.
  • Known dynamics: DP methods assume you know \(p(s', r | s, a)\) exactly. Most real-world problems do not give you this, which is why model-free RL methods exist.

The agent-environment interface diagram works like this: the agent picks action \(A_t\), the environment responds with reward \(R_{t+1}\) and next state \(S_{t+1}\). This loop repeats at every time step.

Pitfalls:

  1. Misplacing the agent-environment boundary. The robot's motors and sensors are part of the environment, not the agent. The agent only makes high-level decisions.
  2. Confusing state with observation. The state is what the agent should know; the observation is what it actually sees. They differ in partially observable problems.
  3. Forgetting the Markov property is about the state, not the problem. You can always make a state Markov by including enough history — the question is whether your chosen state representation is rich enough.
  4. Thinking reward = "good behavior score." The reward defines the goal. If you reward the wrong thing, the agent optimizes the wrong thing.

Recap + Bridge: An MDP is a tuple \((S, A, p, r, \gamma)\) that formally describes any sequential decision-making problem. The agent acts, the environment responds, and the Markov property keeps things clean. Next, we need to talk about what "maximizing reward" actually means — that is the reward hypothesis.

An MDP is not just a toy model. Traffic engineers use it to optimize signal timing. Game AI researchers use it to train agents that play Atari games at superhuman level. Robotics teams use it to plan actions for warehouse robots. The framework is abstract enough to cover all of these, yet concrete enough to be computationally useful. It sits at the core of every RL algorithm — model-free methods just learn the dynamics instead of being given them.

5.2 Reward Hypothesis

Hook: What does a robot actually want? We cannot write down every rule for good behavior. Instead, we give it a single number — a reward signal — and let it figure out the rest. This idea, called the reward hypothesis, is the foundation of all RL goal-setting.

5.2.1 Definition and Explanation

Intuition + Analogy: Think of the reward signal as a report card. A student does not get told exactly how to study. They just see grades (rewards) after each test. Over time, the student figures out which study habits lead to good grades. The reward signal works the same way — it tells the agent what we want (high grade), not how to get it.

Where the analogy breaks: a report card comes infrequently. In RL, the reward arrives at every time step. And the agent must balance short-term and long-term rewards — like choosing to study now (boring, low immediate reward) for a better exam score later (high future reward).

The reward hypothesis states that all goals of an RL agent can be framed as the maximization of the expected value of the cumulative sum of a received scalar signal.

Formally, the agent's objective is to maximize the expected return:

\[ G_t = \sum_{k=0}^{\infty} \gamma^k R_{t+k+1} \]

where:

  • \(R_{t+k+1}\) — the reward received \(k+1\) steps after time \(t\) — scalar
  • \(\gamma\) — the discount factor — a scalar in \([0, 1)\) that controls how much future rewards matter relative to immediate ones
  • \(G_t\) — the return from time \(t\) — the total discounted reward the agent receives from that point onward

The agent chooses actions to maximize \(\mathbb{E}[G_t]\), the expected return.

Core Definition: The reward hypothesis says any goal we want an RL agent to achieve can be expressed as maximizing the expected cumulative discounted reward \(\mathbb{E}\!\left[\sum_{t=0}^{\infty} \gamma^t R_{t+1}\right]\). The reward signal is how we communicate what we want — not how to achieve it.

5.2.2 Symbol Registry

  • \(R_t\) — reward signal at time \(t\) — scalar
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(G_t\) — return (cumulative discounted reward from time \(t\)) — scalar

5.2.3 Key Concepts

Simple (undiscounted) sum: \(\sum_{t=0}^{\infty} R_t\) — adds every reward equally. This diverges to infinity if rewards are positive and the task never ends. Only works for tasks that end in finite time.

Discounted sum: \(\sum_{k=0}^{\infty} \gamma^k R_{t+k+1}\) — weights future rewards less. If \(\gamma = 0\), the agent only cares about the immediate reward. If \(\gamma\) is close to 1, the agent cares about rewards far into the future.

The discount factor \(\gamma\) has two roles:

  1. Mathematical: It keeps the infinite sum finite. If rewards are bounded and \(\gamma < 1\), the sum always converges.
  2. Behavioral: It encodes how much the agent values the future vs the present. A high \(\gamma\) makes the agent "far-sighted"; a low \(\gamma\) makes it "myopic."

The return at successive time steps satisfies a useful recursive relation:

\[ G_t = R_{t+1} + \gamma G_{t+1} \]

This means: today's return equals today's reward plus discounted tomorrow's return. You will use this relation constantly in RL derivations.

Worked Example: Discount Factor Effect

Suppose the agent receives reward \(R = +1\) at every time step.

  • With \(\gamma = 0\): \(G_0 = 1 + 0 + 0 + \cdots = 1\) (only the first reward counts)
  • With \(\gamma = 0.5\): \(G_0 = 1 + 0.5 + 0.25 + 0.125 + \cdots = \frac{1}{1 - 0.5} = 2\)
  • With \(\gamma = 0.9\): \(G_0 = 1 + 0.9 + 0.81 + \cdots = \frac{1}{1 - 0.9} = 10\)
  • With \(\gamma \to 1\): \(G_0 \to \infty\) — the sum diverges

The geometric series formula: for constant reward \(R\) and \(\gamma < 1\):

\[ G_t = \frac{R}{1 - \gamma} \]

If reward is +2 per step instead: \(G_t = \frac{2}{1 - \gamma}\). You can scale the reward to control the magnitude of the return.

Assumptions & Scope:

  • The reward must be a scalar. You cannot give the agent a vector of objectives directly. Multi-objective problems must be collapsed into a single number (e.g., weighted sum).
  • Reward defines the goal, not the behavior. If you reward a chess agent for capturing pieces, it might capture pieces and still lose the game. The reward must reflect the real goal (winning).
  • Discounting is not always needed. Episodic tasks (that always end) can use \(\gamma = 1\) because the sum is finite. Discounting is essential for continuing tasks to prevent infinite returns.

Pitfalls:

  1. Reward hacking. The agent finds a loophole to get high reward without doing what you intended. Example: a cleaning robot that hides mess instead of cleaning it.
  2. Confusing reward with information. The reward tells the agent what is good. Do not use it to tell the agent how to act — that goes in the policy or the state representation.
  3. Forgetting that discounting changes the problem. A task with \(\gamma = 0.9\) and the same task with \(\gamma = 0.99\) are different optimization problems. The optimal policy can change.

Recap + Bridge: The reward hypothesis says: give the agent a scalar reward signal, and let it maximize the cumulative discounted return \(G_t = \sum_{k=0}^{\infty} \gamma^k R_{t+k+1}\). The discount factor \(\gamma\) controls how far ahead the agent looks. But the return formula assumes the agent runs forever. What if the task naturally ends? That brings us to episodic vs continuing tasks.

This idea — compressing all goals into a single scalar signal — powers every RL system from game-playing AIs to robotic control. It is the reason RL can solve problems we do not know how to specify with explicit rules.

Q: Is the balancing of the pole continuous or episodic?

A: It can be modeled either way. If modeled as an episodic task, the episode ends when the pole falls. If modeled as a continuing task, it works irrespective of when the balance is lost. The continuing formulation is slightly more general.

Q: Is it possible that the agent continues to hold the pole infinitely?

A: If you give reward +1 for every time unit the pole is balanced, the undiscounted sum would be infinite (\(1 + 1 + 1 + \cdots\)). That is exactly why we use discounting. With \(\gamma < 1\), even an infinite stream of +1 rewards gives a finite return of \(\frac{1}{1 - \gamma}\). Alternatively, you can model it as a continuing task with reward 0 while balanced and \(-1\) when balance is lost — then the return is \(-\gamma^k\) where \(k\) is when the pole falls.

5.3 Episodic vs Continuing Tasks

Hook: Some games end — you win or lose, then start over. Other processes run forever — like managing a power grid. Reinforcement learning handles both, but the math changes depending on which type you are dealing with.

5.3.1 Definition and Explanation

Intuition + Analogy: An episodic task is like playing a board game. Each game is a self-contained episode. When it ends (you reach the finish), you reset and play again. A continuing task is like managing your household budget. There is no "end" — you just keep making financial decisions month after month, indefinitely.

Where the analogy breaks: in RL, even continuing tasks have a notion of "doing well." The agent still wants to maximize cumulative reward. The challenge is that the cumulative sum can grow without bound.

An episodic task has natural terminal states. The agent's experience breaks into episodes, each ending at a terminal state, followed by a reset. The return is a finite sum:

\[ G_t = R_{t+1} + R_{t+2} + \cdots + R_T \]

where \(T\) is the final time step of the episode.

A continuing task has no natural endpoint. The agent interacts indefinitely. Here, the undiscounted return would diverge, so we must use discounting:

\[ G_t = \sum_{k=0}^{\infty} \gamma^k R_{t+k+1} \]

with \(\gamma < 1\) to keep the sum finite.

5.3.2 Symbol Registry

  • \(G_t\) — return from time \(t\) — scalar (cumulative discounted reward)
  • \(T\) — terminal time step of an episode — positive integer
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(R_t\) — reward at time \(t\) — scalar

Core Definition: Episodic tasks end in a terminal state and restart; the return is a finite sum over one episode. Continuing tasks never end; the return must use discounting (\(\gamma < 1\)) to stay finite. The textbook unifies both cases by treating episode termination as entering a special absorbing state that transitions to itself with reward 0.

5.3.3 Worked Example: Cart-Pole Balancing

Episodic Formulation

The cart-pole problem: a cart moves left and right on a track, with a pole balanced on top. The goal is to keep the pole upright.

  • Episode start: Pole is balanced upright
  • Episode end: Pole falls past a critical angle, or cart runs off the track
  • Reward: \(R = +1\) for each time step the pole stays up
  • Return: \(G_0 = \sum_{t=0}^{T-1} 1 = T\) — the total number of steps before failure

The agent's goal is to maximize \(T\), the survival time.

If the pole is balanced forever (ideal case), \(T \to \infty\) and the return is infinite. This is fine for an episodic task — the agent simply never sees a terminal state.

Continuing Formulation

Same problem, but we treat it as a continuing task with discounting:

  • Reward: \(R = 0\) while the pole is balanced, \(R = -1\) when it falls
  • Return: If balance is lost at step \(k\), then \(G_0 = -\gamma^k\)

As \(k\) increases (longer balance), \(-\gamma^k\) approaches 0 (which is better — less negative). If the pole never falls, \(k \to \infty\) and \(G_0 = 0\) (the best possible outcome).

Key insight: With a constant reward of +1 per step and discounting, the return converges:

\[ G_t = \sum_{k=0}^{\infty} \gamma^k \cdot 1 = \frac{1}{1 - \gamma} \]

With \(\gamma = 0.9\): \(G_t = \frac{1}{0.1} = 10\). You can engineer the reward scale — doubling the reward doubles the return to \(\frac{2}{1 - \gamma}\).

Q: Can the cart-pole task be modeled as both episodic and continuing?

A: Yes. In the episodic version, the episode ends when the pole falls; reward is +1 per step; the return is the total steps before failure. In the continuing version, there is no endpoint; reward is 0 while balanced and −1 on failure; the return is \(-\gamma^k\) where \(k\) is the step when balance is lost. Both formulations lead the agent to balance the pole as long as possible. The continuing formulation handles the infinite-horizon case without the sum diverging.

Pitfalls:

  1. Using \(\gamma = 1\) in a continuing task. The return becomes infinite and the math breaks. Always use \(\gamma < 1\) for continuing tasks.
  2. Confusing the two formulations. An episodic task with \(R = +1\) per step and a continuing task with \(R = -1\) on failure are different problems with different optimal policies. Do not mix them up.
  3. Thinking episodes must be independent. In practice, the starting state of each episode may depend on how the previous one ended. The theory handles this, but be aware of it.

Recap + Bridge: Episodic tasks have natural endpoints; continuing tasks do not. Episodic tasks use undiscounted finite returns; continuing tasks need discounting to keep returns finite. The return formula \(G_t = R_{t+1} + \gamma G_{t+1}\) works for both. Next, we define what a policy is — the rule that tells the agent what action to take in each state.

The choice between episodic and continuing formulation affects everything downstream: the return, the value functions, and the algorithms. The textbook notes that the pole-balancing task can be modeled either way, and both are valid. The continuing formulation is slightly more general.

5.4 Policy

Hook: If an MDP is the world, a policy is the agent's playbook. Given any situation, the policy says what to do. It is the core object that RL algorithms try to learn.

5.4.1 Definition and Explanation

Intuition + Analogy: Think of a policy like your personal chess strategy. You have a rulebook: "If the opponent plays e4, I play e5. If they play d4, I play d5." The rulebook covers every possible board position. A deterministic policy is a fixed rulebook — one move per position. A stochastic policy adds probabilities — "70% of the time I play e5, 30% of the time I play c5." The stochastic version is useful for exploration and for games where unpredictability helps.

Where the analogy breaks: in chess, the "state" is the board position. In general RL, the state can be anything — sensor readings, game frames, battery levels.

A policy \(\pi\) defines the agent's behavior. It maps states to actions.

5.4.2 Symbol Registry

  • \(\pi\) — policy — function mapping states to actions (or action probabilities)
  • \(\pi(s)\) — deterministic policy — the single action chosen in state \(s\)
  • \(\pi(a|s)\) — stochastic policy — probability of taking action \(a\) in state \(s\), with \(\sum_a \pi(a|s) = 1\)
  • \(s\) — state — element of state set \(S\)
  • \(a\) — action — element of action set \(A\)

Core Definition:

  • A deterministic policy assigns one action to each state: \(\pi(s) = a\)
  • A stochastic policy assigns a probability distribution over actions for each state: \(\pi(a|s) = P(A_t = a \mid S_t = s)\), where \(\sum_{a} \pi(a|s) = 1\) for all \(s\)

The notation \(\pi(a|s)\) reads "the probability of action \(a\) given state \(s\) under policy \(\pi\)."

5.4.3 Example

Consider a grid where from state \(X\):

  • Going right leads to a high-value state
  • Going down leads to a low-value state

Stochastic policy:

  • \(\pi(\text{right}|X) = 0.9\) — the agent mostly goes right
  • \(\pi(\text{down}|X) = 0.1\) — but occasionally explores going down

Deterministic policy:

  • \(\pi(\text{right}|X) = 1.0\) — always go right
  • \(\pi(\text{down}|X) = 0\) — never go down

In diagrams, arrows show the dominant action under the policy. If multiple arrows appear from a state, the policy assigns positive probability to each.

Pitfalls:

  1. Confusing policy with value function. The policy says what to do. The value function says how good it is to be somewhere. They are different objects.
  2. Thinking a policy must be deterministic. Stochastic policies are essential for exploration and are the norm in many RL algorithms.
  3. Forgetting that \(\pi\) is a function, not a single decision. The policy covers every state, not just the current one.

Recap + Bridge: A policy \(\pi\) maps states to actions — either deterministically (\(\pi(s) = a\)) or stochastically (\(\pi(a|s)\)). It is the object RL algorithms try to optimize. To know how good a policy is, we need value functions. That comes next.

The policy is the central object in RL. Every algorithm — value-based, policy-based, or actor-critic — ultimately produces or improves a policy. Value-based methods compute values first and extract a policy from them. Policy-based methods optimize the policy directly. Both are different paths to the same goal: finding a good \(\pi\).

5.5 State Value Function (Vπ)

Hook: You are standing at a crossroads. One road leads to a busy city; the other leads to a desert. How do you know which road is better? You need a way to score each location. That is what a value function does — it assigns a number to every state that says "how good is it to be here?"

5.5.1 Definition and Explanation

Intuition + Analogy: Think of each state as a city on a map, and the value function as a "prosperity score" for each city. If you follow policy \(\pi\) (your travel plan), the score tells you the expected total reward you will collect starting from that city. A city near a gold mine (high-reward state) has a high score. A city in the middle of nowhere has a low score. The score depends on the policy — if your travel plan is bad, even a city near a gold mine might have a low score because you never reach it.

Where the analogy breaks: the value is not about the state alone. It depends on what you do after arriving. A state with two great next moves is better than the same state with two bad next moves, even though the immediate reward might be the same.

The state value function \(V_\pi(s)\) quantifies how good it is to be in state \(s\) when following policy \(\pi\). It is the expected return starting from \(s\) and following \(\pi\) thereafter.

Core Definition:

\[ V_\pi(s) = \mathbb{E}_\pi[G_t \mid S_t = s] = \mathbb{E}_\pi\!\left[\sum_{k=0}^{\infty} \gamma^k R_{t+k+1} \;\middle|\; S_t = s\right] \]

The subscript \(\pi\) means the expectation is taken over all actions chosen according to \(\pi\) and all environment transitions. The value of a state depends on how the agent behaves — change the policy, and the values change.

The value of a terminal state is always zero: \(V_\pi(\text{terminal}) = 0\).

5.5.2 Mathematical Formulation

The verbal description: "The value of state \(s\) under policy \(\pi\) is the expected cumulative discounted reward if you start in \(s\) and follow \(\pi\) from then on."

Expanding the return \(G_t\):

\[ V_\pi(s) = \mathbb{E}_\pi\!\left[\sum_{k=0}^{\infty} \gamma^k R_{t+k+1} \;\middle|\; S_t = s\right] \]

This sums over all possible future trajectories, each weighted by its probability under \(\pi\) and the environment dynamics \(p\).

5.5.3 Symbol Registry

  • \(V_\pi(s)\) — state value function under policy \(\pi\) — scalar
  • \(G_t\) — return from time \(t\) (cumulative discounted reward) — scalar
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(\pi\) — policy — function mapping states to action probabilities

5.5.4 Example with Numerical Values

Consider a grid where states have values under policy \(\pi\):

  • A state with \(V_\pi = 90\) is better than one with \(V_\pi = 50\)
  • The agent should prefer moving toward higher-valued states

What does a value of 70 mean? "If I am in this state and follow policy \(\pi\) from now on, the expected total discounted reward I will collect is 70."

The value depends on everything that happens after — not just the next step. If a state leads to a long chain of small rewards, it might have a higher value than a state that gives one big reward and then nothing.

In a grid world under an equiprobable random policy (each action equally likely), states near the edges have low or negative values (the agent often bumps into walls and gets −1 reward). States near special high-reward locations have high values.

Pitfalls:

  1. Thinking V depends only on the state. It depends on the policy too. The same state can have different values under different policies.
  2. Confusing V with immediate reward. \(V_\pi(s)\) is about all future rewards, not just the next one. A state with immediate reward 0 might have high value if it leads to great future rewards.
  3. Forgetting that V is an expectation. The actual return from a state will vary due to randomness in actions and transitions. \(V_\pi(s)\) is the average over many runs.

Recap + Bridge: The state value function \(V_\pi(s)\) tells you the expected return from state \(s\) under policy \(\pi\). It depends on the policy — change \(\pi\) and \(V\) changes. But \(V\) only tells you how good the state is. What if you want to know how good a specific action is from that state? That is the action value function \(Q_\pi\).

State values are the first building block for RL algorithms. Policy evaluation (covered later) computes \(V_\pi\) for a given policy. Policy improvement uses \(V_\pi\) to find a better policy. This cycle — evaluate, improve, repeat — drives all dynamic programming methods.

5.6 Action Value Function (Qπ)

Hook: You know the value of being in a city (state value). But you are at a fork in the road — one path goes north, another goes south. Which path is better? You need the value of each action, not just each state. That is what \(Q_\pi\) gives you.

5.6.1 Definition and Explanation

Intuition + Analogy: Think of GPS navigation. You type in your destination. The GPS does not just tell you "you are in a good location." It tells you the expected travel time for each possible route from where you are. The Q-function is that GPS — it tells you the expected return for each action you could take from your current state, assuming you follow policy \(\pi\) afterwards.

Where the analogy breaks: GPS gives you a deterministic answer (take this route). The Q-function accounts for randomness — the same action can lead to different outcomes, and \(Q\) averages over them.

The action value function \(Q_\pi(s, a)\) quantifies how good it is to take action \(a\) in state \(s\) and then follow policy \(\pi\) thereafter.

Core Definition:

\[ Q_\pi(s, a) = \mathbb{E}_\pi[G_t \mid S_t = s, A_t = a] = \mathbb{E}_\pi\!\left[\sum_{k=0}^{\infty} \gamma^k R_{t+k+1} \;\middle|\; S_t = s, A_t = a\right] \]

The key difference from \(V_\pi\): the expectation is conditioned on taking a specific action \(a\) at time \(t\). After that, the agent follows \(\pi\).

5.6.2 Symbol Registry

  • \(Q_\pi(s, a)\) — action value function under policy \(\pi\) — scalar
  • \(G_t\) — return from time \(t\) — scalar
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(\pi(a|s)\) — policy probability — scalar in \([0, 1]\)
  • \(V_\pi(s)\) — state value function — scalar, related by \(V_\pi(s) = \sum_a \pi(a|s) Q_\pi(s,a)\)

The relationship between \(V_\pi\) and \(Q_\pi\):

\[ V_\pi(s) = \sum_{a} \pi(a|s) \, Q_\pi(s, a) \]

The state value is the expected Q-value, weighted by the policy probabilities.

5.6.3 Mathematical Formulation

\[ Q_\pi(s, a) = \mathbb{E}_\pi[G_t \mid S_t = s, A_t = a] \]

This conditions on a specific action \(a\) being taken at time \(t\), then follows \(\pi\) for all later steps.

5.6.4 Why Q is Preferred Over V

Key advantage: When action outcomes are uncertain, knowing only state values (\(V\)) makes action selection hard. You would need to compute:

\[ \text{value of action } a = \sum_{s'} p(s'|s,a) \left[ r + \gamma V_\pi(s') \right] \]

for every action — which requires knowing the transition probabilities \(p\). With Q-values, you skip that step. Just look up \(Q(s, a)\) for each action and pick the highest.

The textbook puts it well: Q-values "effectively cache the results of all one-step-ahead searches."

Recycling Robot Example

From state "high":

  • Search: may lead to "high" (probability \(\alpha\)) or "low" (probability \(1-\alpha\))
  • Wait: stays in "high" (deterministic)

If you only know \(V(\text{high})\) and \(V(\text{low})\), computing which action is better requires knowing \(\alpha\), the transition probability. But if you know \(Q(\text{high}, \text{search})\) and \(Q(\text{high}, \text{wait})\), you just compare them:

  • Pick search if \(Q(\text{high}, \text{search}) > Q(\text{high}, \text{wait})\)
  • Pick wait otherwise

No transition probabilities needed at decision time. Q-values are "ready-made" decision tools.

When action outcomes are deterministic (pressing a brake always stops the car), \(V\) suffices because there is only one outcome per action. But when outcomes are stochastic, \(Q\) is far more practical.

Pitfalls:

  1. Confusing Q and V. \(V_\pi(s)\) is the value of being in state \(s\). \(Q_\pi(s, a)\) is the value of doing action \(a\) in state \(s\), then following \(\pi\). They are related but different.
  2. Forgetting that Q conditions on one action. After taking action \(a\), the agent follows \(\pi\). It does not keep picking the same action \(a\).
  3. Thinking Q requires no model. Computing Q from scratch still needs transition probabilities. The advantage is that once Q is known (computed or learned), using it for decisions requires no model.

Recap + Bridge: The action value function \(Q_\pi(s, a)\) tells you the expected return for taking action \(a\) in state \(s\) and then following \(\pi\). It is more useful than \(V_\pi\) for action selection because it directly compares actions without needing the environment model. Both \(V_\pi\) and \(Q_\pi\) satisfy recursive relationships called Bellman equations — that is what we tackle next.

Q: Why are we more interested in Q than V?

A: In problems where action outcomes are uncertain, computing the value of an action from \(V\) requires summing over all possible outcomes weighted by their transition probabilities — that needs a model. If you have pre-computed Q-values, action selection is trivial: just pick the action with the highest Q-value. The Q-values are "ready-made" decision tools. This is why Q-learning (a model-free method based on Q) became so popular.

The Q-function is central to many RL algorithms. Q-learning (Chapter 6 in the textbook) learns \(Q^*\) directly from experience without knowing the transition probabilities. Deep Q-Networks (DQN) approximate \(Q^*\) with neural networks to play Atari games. The concept extends from this simple definition to state-of-the-art methods.

5.7 Bellman Expectation Equation

Hook: You want to know the value of your current apartment. You could live there for years and track all the rewards. Or you could just ask: "What are the neighboring apartments worth, and how much do I enjoy the move?" That one-step lookahead gives you the answer. The Bellman equation makes this precise — it connects the value of a state to the values of its successor states.

5.7.1 Definition and Explanation

Intuition + Analogy: Think of planning dinner. Tonight's meal value depends on two things: how much you enjoy tonight's dinner (immediate reward), and how good tomorrow's meal options will be (discounted future value). The Bellman equation says: the value of being in state \(s\) equals the expected immediate reward plus the expected discounted value of wherever you end up next.

This is recursive — the value of \(s\) is expressed in terms of values of successor states \(s'\). Those successor values are in turn expressed in terms of their successors, and so on. The Bellman equation is the starting point for computing value functions.

The Bellman expectation equation defines \(V_\pi(s)\) recursively:

Core Definition:

\[ V_\pi(s) = \sum_{a} \pi(a|s) \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_\pi(s') \right] \]

Reading this step by step:

  1. Outer sum over actions \(a\): For each action, weight by \(\pi(a|s)\) — how likely the agent is to pick that action under the policy.
  2. Inner sum over next states \(s'\) and rewards \(r\): For each possible outcome, weight by \(p(s', r | s, a)\) — how likely the environment is to produce that outcome.
  3. Bracket \([r + \gamma V_\pi(s')]\): The immediate reward \(r\) plus the discounted value of the next state.

The equation has two sources of probability:

  • \(\pi(a|s)\) — the policy (agent's behavior)
  • \(p(s', r | s, a)\) — the dynamics (environment's behavior)

5.7.2 Mathematical Formulation

The full Bellman equation for \(V_\pi\):

\[ V_\pi(s) = \sum_{a} \pi(a|s) \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_\pi(s') \right] \]

This is a system of \(|S|\) linear equations in \(|S|\) unknowns (one equation per state). For a finite MDP, this system has a unique solution as long as \(\gamma < 1\) or eventual termination is guaranteed.

The textbook derives this from the return's recursive structure:

\[ V_\pi(s) = \mathbb{E}_\pi[G_t \mid S_t = s] = \mathbb{E}_\pi[R_{t+1} + \gamma G_{t+1} \mid S_t = s] \]

Using \(G_t = R_{t+1} + \gamma G_{t+1}\) (the recursive return relation), the expectation separates into the immediate reward and the discounted expected future value.

5.7.3 Symbol Registry

  • \(\pi(a|s)\) — probability of taking action \(a\) in state \(s\) under policy \(\pi\) — scalar in \([0,1]\)
  • \(p(s', r | s, a)\) — dynamics function — probability of transitioning to state \(s'\) with reward \(r\) given state \(s\) and action \(a\)
  • \(s'\) — next (successor) state — element of \(S\)
  • \(r\) — immediate reward — scalar

5.7.4 Understanding the Two Levels of Probability

The equation involves two distinct probability sources:

  1. Policy probability \(\pi(a|s)\): How likely the agent is to choose action \(a\) in state \(s\). This is under the agent's control — it defines the behavior.
  2. Model dynamics \(p(s', r | s, a)\): How likely the environment is to transition to state \(s'\) with reward \(r\). This is outside the agent's control — it defines the world.

If action outcomes are deterministic (action \(a\) always leads to exactly one state \(s'\) with reward \(r\)), the inner sum collapses to a single term — the dynamics probability is 1 for that outcome, and 0 for all others.

5.7.5 Backup Diagram

The backup diagram shows the recursive structure visually:

  • Open circles represent states (where you are)
  • Solid circles represent action choices (decision points)
  • From a state node, lines fan out to action nodes (one per possible action, weighted by \(\pi(a|s)\))
  • From each action node, lines fan out to successor state nodes (one per possible outcome, weighted by \(p(s', r | s, a)\))

The value flows backward: the value of the root state depends on the values at the leaves (successor states), plus the rewards along the edges.

5.7.6 Worked Example: Expressing V in Terms of Q

The state value can be written using Q-values:

\[ V_\pi(s) = \sum_{a} \pi(a|s) \, Q_\pi(s, a) \]

Numerical example: Suppose policy \(\pi\) gives:

Action \(\pi(a \mid s)\) \(Q_\pi(s, a)\)
up 0.7 10
right 0.1 20
down 0.1 15
left 0.1 20

\[ V_\pi(s) = 0.7 \times 10 + 0.1 \times 20 + 0.1 \times 15 + 0.1 \times 20 = 7 + 2 + 1.5 + 2 = \mathbf{12.5} \]

Sense-check: The policy heavily favors "up" (Q = 10), so the state value is close to 10. The other actions have higher Q-values but are chosen rarely, so they pull the average up slightly to 12.5. This makes sense.

5.7.7 Worked Example: Computing Q-Value

From state \(s\), take action "up". The Q-value depends on all possible outcomes:

Deterministic case: "up" always leads to one state with reward 20 and that state has value 70. With \(\gamma = 0.9\):

\[ Q(s, \text{up}) = 20 + 0.9 \times 70 = 20 + 63 = \mathbf{83} \]

Stochastic case: "up" leads to four possible outcomes:

Outcome Probability Reward Next state value Contribution
Go up \(p_1\) 20 70 \(p_1 \times (20 + 0.9 \times 70)\)
Go down \(p_2\) 10 100 \(p_2 \times (10 + 0.9 \times 100)\)
Go right \(p_3\) 30 80 \(p_3 \times (30 + 0.9 \times 80)\)
Go left \(p_4\) 20 100 \(p_4 \times (20 + 0.9 \times 100)\)

\[ Q(s, \text{up}) = \sum_{i=1}^{4} p_i \left[ r_i + \gamma V_\pi(s'_i) \right] \]

where \(p_1 + p_2 + p_3 + p_4 = 1\).

Assumptions & Scope:

  • Requires known dynamics. To compute \(V_\pi\) from the Bellman equation, you need \(p(s', r | s, a)\). In model-free RL, you do not have this — so you sample transitions instead.
  • Requires a defined policy. The Bellman equation is for a given \(\pi\). It evaluates that policy. Finding the best policy is a separate problem (Bellman optimality equation, Section 5.9).
  • Linear system. For \(|S|\) states, you have \(|S|\) equations in \(|S|\) unknowns. For small state spaces, you can solve directly. For large spaces, you use iterative methods (policy evaluation, covered in DP chapter).

Pitfalls:

  1. Confusing the Bellman expectation equation with the Bellman optimality equation. The expectation equation uses \(\sum_a \pi(a|s)\) — a weighted average over actions. The optimality equation uses \(\max_a\) — the best action. They look similar but solve different problems.
  2. Forgetting the two probability layers. The outer sum is over actions (policy probability). The inner sum is over outcomes (environment dynamics). Mixing them up leads to wrong formulas.
  3. Thinking V and Q are independent. They are tightly linked: \(V_\pi(s) = \sum_a \pi(a|s) Q_\pi(s,a)\) and \(Q_\pi(s,a) = \sum_{s',r} p(s',r|s,a)[r + \gamma V_\pi(s')]\). You can express one in terms of the other.

Recap + Bridge: The Bellman expectation equation connects the value of a state to the values of its successors through a one-step lookahead. It involves two probability layers: the policy and the dynamics. Solving this equation gives you \(V_\pi\) for a given policy. Next, we verify this equation by hand on a grid world example.

Q: We have two probabilities here — policy and model dynamics. What if each action leads to only one state?

A: Then the model dynamics probability is 1 for that single outcome. The branch collapses to a single path. You just multiply: probability of taking that action (from policy) times (reward + gamma times next state value). No inner sum needed.

Q: What does "expectation with respect to \(\pi\)" mean exactly?

A: It means the average is computed using \(\pi\)'s probability distribution over actions. If \(\pi(\text{up}|s) = 0.7\), then 70% of the weight goes to the "up" outcome. It is like computing your expected commute time using your historical driving habits — the expectation depends on your behavior pattern.

5.8 Grid World Example

Hook: The Bellman equation looks abstract. Let us make it concrete. We will build a small grid world, assign rewards, run an equiprobable policy, and verify the converged state values by hand. This is the kind of numerical exercise you will see on exams.

5.8.1 Problem Setup

Intuition + Analogy: Picture a small city grid. Most intersections are ordinary — walking from one to the next earns you nothing. But there are two special spots: a gold mine (State A, +10 reward) and a silver mine (State B, +5 reward). Stepping on either teleports you to a different location. Walking into a wall (off the grid) costs you −1 and you stay put.

The city is 4 rows by 4 columns. There are 4 actions in every state: up, down, left, right.

The grid world has these special rules:

  • State A (row 1, col 2): Any action gives reward +10 and teleports you to \(A'\) (row 3, col 1, value −1.3)
  • State B (row 1, col 4): Any action gives reward +5 and teleports you to \(B'\) (row 3, col 4)
  • Normal moves: Reward 0, move one cell in the chosen direction
  • Off-grid moves: If an action would move you off the grid, you stay in place and receive reward −1

The policy is equiprobable random: \(\pi(a|s) = 0.25\) for all four actions in every state.

5.8.2 Converged State Values

Using iterative policy evaluation (details covered in the DP chapter), the converged values under the equiprobable policy with \(\gamma = 0.9\) are:

Special values: \(V(A) = 8.8\), \(V(B) = 5.3\), \(V(A') = -0.4\).

  • \(\gamma\) — discount factor — 0.9 in this example
  • \(\pi(a|s)\) — policy probability — 0.25 for each action (equiprobable)

  • \(r\) — immediate reward — 0 (normal), +10 (state A), +5 (state B), −1 (off-grid)

  • States near A have high values (3.3, 3.0): They are close to the +10 reward. The agent is likely to stumble onto A soon.
  • Corner states have low values (−1.0, −1.6): From a corner, two of four actions hit the wall (−1 reward each). Under a random policy, the expected penalty per step is higher.

  • Left → cell (3,2), value −0.4: \(0 + 0.9 \times (-0.4) = -0.36\)

5.8.5 Worked Verification: Cell (1,2) — State A

Special state A at row 1, column 2. This state has special dynamics: every action gives reward +10 and teleports you to \(A'\) (value −1.3).

All four directions yield the same value:

\[ \text{Each action: } 10 + 0.9 \times (-1.3) = 10 - 1.17 = 8.83 \]

Since all four actions give the same value:

\[ V(1,2) = 0.25 \times 4 \times 8.83 = 8.83 \approx 8.8 \checkmark \]

This matches the converged value in the table. The value is less than 10 because the teleport destination \(A'\) has a negative value — the agent is likely to hit grid edges from there.

  1. Using wrong neighbor values. Always read the correct neighbor from the converged table. A single wrong digit cascades through the calculation.
  2. Forgetting that off-grid moves give −1 reward. If you move toward a wall, you stay put AND get −1. Do not treat it as reward 0.
  3. Confusing which cells are "special." Only A and B have custom dynamics. All other cells follow normal grid movement.

Recap + Bridge: The grid world example shows the Bellman equation in action. You can verify any cell's value by looking up its neighbors and applying one step of the equation. States near high-reward areas have high values; edge states have low values. This was for a given policy. What if we want the best policy? That requires the Bellman optimality equation.

Q: Can you verify a few more cells by hand?

A: Yes — try it. Pick a cell near B, a corner cell, and a cell adjacent to the grid boundary. The Bellman equation applies uniformly. The only differences are the rewards and successor state values. Working through these by hand builds the intuition you need for exams.

5.9 Optimal Policies and Optimal Value Functions

Hook: You know how to evaluate a policy. But is it the best policy? How do you find the strategy that squeezes the most reward out of every state? The answer lies in the Bellman optimality equation — the single most important equation in this lecture.

5.9.1 Definition and Explanation

Intuition + Analogy: Imagine you have a city map with driving times from every intersection to the airport. The "optimal value" of each intersection is the shortest possible driving time — not the time under some fixed route, but the best route from that spot. An optimal policy is the set of directions that achieves those shortest times from every intersection.

The key insight: with the optimal value function \(V^*\), you can find the best action at any state by looking just one step ahead. You do not need to plan the entire route — \(V^*\) already encodes all the future planning.

An optimal policy \(\pi^*\) is a policy whose value function is at least as good as every other policy in every state:

Core Definition:

Policy \(\pi\) is better than or equal to \(\pi'\) if and only if:

\[ V_\pi(s) \geq V_{\pi'}(s) \quad \forall s \in S \]

An optimal policy \(\pi^*\) satisfies \(V_{\pi^*}(s) \geq V_\pi(s)\) for all \(s\) and all policies \(\pi\).

The optimal state value function:

\[ V^*(s) = \max_\pi V_\pi(s) \quad \forall s \]

The optimal action value function:

\[ Q^*(s, a) = \max_\pi Q_\pi(s, a) \quad \forall s, a \]

For finite MDPs, at least one optimal policy always exists. All optimal policies share the same \(V^*\) and \(Q^*\).

5.9.2 Symbol Registry

  • \(\pi^*\) — optimal policy — function mapping states to action probabilities
  • \(V^*(s)\) — optimal state value function — scalar
  • \(Q^*(s, a)\) — optimal action value function — scalar

5.9.3 Bellman Optimality Equation

Bellman Optimality for \(V^*\):

\[ V^*(s) = \max_a \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V^*(s') \right] \]

Compare with the Bellman expectation equation:

\[ V_\pi(s) = \sum_a \pi(a|s) \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_\pi(s') \right] \]

The only difference: instead of the weighted average \(\sum_a \pi(a|s) \dots\), we take the maximum \(\max_a \dots\). This says: "at each state, pick the action that leads to the highest value. Do not average — just pick the best."

Bellman Optimality for \(Q^*\):

\[ Q^*(s, a) = \sum_{s', r} p(s', r | s, a) \left[ r + \gamma \max_{a'} Q^*(s', a') \right] \]

The relationship between \(V^*\) and \(Q^*\):

\[ V^*(s) = \max_a Q^*(s, a) \]

Once you have \(V^*\), finding an optimal policy is simple: at each state, pick any action that achieves the maximum in the Bellman optimality equation. Any policy that assigns nonzero probability only to these maximizing actions is optimal.

The textbook emphasizes: "any policy that is greedy with respect to the optimal evaluation function \(V^*\) is an optimal policy." This is the bridge between value functions and policies.

5.9.4 Worked Example: Computing Optimal Value

Using the grid world (Section 5.8) with \(\gamma = 0.9\):

To compute \(V^*\) at cell (1,1), evaluate each action:

  • Right → cell (1,2) = A, which gives +10 and teleports to \(A'\) (value −1.3): \(10 + 0.9 \times (-1.3) = 8.83\)
  • Down → cell (2,1), value 1.5 (under random policy, but for optimal we need \(V^*\)): Using the optimal values from the textbook's solution, \(V^*(2,1) = 19.8\): \(0 + 0.9 \times 19.8 = 17.82\)
  • Left → off-grid, stay at (1,1), reward −1: \(-1 + 0.9 \times V^*(1,1)\)
  • Up → off-grid, stay at (1,1), reward −1: \(-1 + 0.9 \times V^*(1,1)\)

Under the random policy, all four are weighted equally (×0.25). Under the optimal policy, the agent picks the action with the highest value — which is going down or right, depending on the exact \(V^*\) values.

Assumptions & Scope:

  • Requires known dynamics. The Bellman optimality equation needs \(p(s', r | s, a)\). In practice, you rarely have this. Model-free methods (Q-learning, SARSA) learn approximate optimal values from experience.
  • Nonlinear system. The \(\max\) operation makes this a system of nonlinear equations (unlike the Bellman expectation equation, which is linear). Solving it directly is harder — you typically use iterative methods like value iteration.
  • Multiple optimal policies may exist. If two actions tie for the best value at a state, any mixture of them is also optimal. The optimal value function \(V^*\) is unique, but \(\pi^*\) may not be.

Pitfalls:

  1. Confusing \(\max\) with \(\sum \pi(a|s)\). The Bellman expectation equation averages over actions (weighted by policy). The Bellman optimality equation picks the best action. One evaluates a policy; the other finds the best policy.
  2. Thinking you need \(V^*\) to act. With \(Q^*\), action selection is trivial: \(\pi^*(s) = \arg\max_a Q^*(s,a)\). No model needed at decision time.
  3. Forgetting that \(V^*\) is a fixed point. The Bellman optimality equation defines \(V^*\) implicitly. You solve for it iteratively — you cannot plug in unknown values and compute it directly.

Recap + Bridge: The optimal value functions \(V^*\) and \(Q^*\) give the best possible expected returns. The Bellman optimality equation replaces the policy-weighted average with a max. Once you have \(V^*\), any greedy policy is optimal. But how do you actually compute \(V^*\)? That is where value iteration comes in.

The Bellman optimality equation is the theoretical foundation of nearly all RL methods. Q-learning learns \(Q^*\) from experience. Policy gradient methods search for \(\pi^*\) directly. Dynamic programming solves for \(V^*\) when the model is known. Understanding this equation is the key to understanding the entire field.

5.10 Value Iteration Algorithm

Hook: You have the Bellman optimality equation — it tells you what \(V^*\) looks like. But it is a system of nonlinear equations you cannot solve directly. Value iteration is the practical algorithm that computes \(V^*\) by repeatedly applying the Bellman update until the values stop changing.

5.10.1 Definition and Explanation

Intuition + Analogy: Imagine you are estimating house prices in a neighborhood. You start with wild guesses. Then you visit each house and update its price based on what neighboring houses are worth. After one pass, your estimates are better. You keep making passes until the prices stabilize. Value iteration does the same thing with state values — it sweeps through all states, updates each one using the Bellman optimality equation, and repeats until convergence.

Where the analogy breaks: house prices depend on many factors. State values depend only on successor state values and immediate rewards — a clean recursive structure.

Value iteration computes optimal state values by iteratively applying the Bellman optimality equation. You start with initial values (typically zeros), repeatedly update every state, and stop when values converge.

Core Definition: Value iteration turns the Bellman optimality equation into an update rule:

\[ V_{k+1}(s) = \max_a \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_k(s') \right] \]

For arbitrary initial \(V_0\), the sequence \(\{V_k\}\) converges to \(V^*\) as \(k \to \infty\) (provided \(\gamma < 1\) or eventual termination is guaranteed).

Value iteration formally requires an infinite number of iterations to converge exactly to the optimal value function, so we infer convergence in practice by stopping once the value function changes by only a small amount in a single sweep across the state space.

To determine this computationally, the algorithm uses a small positive threshold parameter (often denoted as \(\theta\)) to define the desired accuracy of the estimation. During each iteration, the algorithm calculates the new value for each state and tracks the maximum absolute change in the estimated value across any state, denoted as \(\Delta\). We infer that the values have sufficiently converged when this maximum change \(\Delta\) is less than the threshold \(\theta\).

The professor's emphasis: "Understanding the algorithm is more important than memorizing it. If you understand it, you can adapt to different scenarios."

5.10.2 Algorithm

Pseudocode (not-in-place version):

Initialize V(s) = 0 for all states s

Repeat until convergence:
    Delta <- 0
    For each state s:
        v <- V(s)                                          # save old value
        V(s) <- max_a Sum_{s',r} p(s',r|s,a)[r + gamma*V(s')]  # Bellman update
        Delta <- max(Delta, |v - V(s)|)                    # track biggest change
    If Delta < theta:                                      # theta = stopping threshold
        Stop

Two loops:

  1. Outer loop: Repeat sweeps until the maximum value change \(\Delta < \theta\)
  2. Inner loop: For each state, compute the new value using the Bellman optimality update

Key parameters:

  • \(\theta\) (theta): A small threshold for stopping (e.g., \(10^{-4}\))
  • \(\Delta\) (delta): The maximum change in any state value during this sweep
  • \(\gamma\): Discount factor

Critical detail: This version uses the old values \(V_k(s')\) for successor states. It does not use values updated in the current sweep. This is the "not-in-place" version. The distinction matters for exams.

5.10.3 Symbol Registry

  • \(V_k(s)\) — value estimate for state \(s\) at iteration \(k\) — scalar
  • \(\Delta\) — maximum value change in one sweep — scalar
  • \(\theta\) — stopping threshold — small positive number (e.g., \(10^{-4}\))
  • \(\gamma\) — discount factor — scalar in \([0, 1)\)
  • \(p(s', r | s, a)\) — dynamics function — probability of next state and reward

5.10.4 Worked Example: Race Car Problem

Setup:

Three states: Cool, Warm, Overheated

Two actions: Slow, Fast

Transition dynamics:

From Cool:

  • Slow: Probability 1 → stay Cool, reward +1
  • Fast: Probability 0.5 → Warm, reward +2; Probability 0.5 → stay Cool, reward +2

From Warm:

  • Slow: Probability 0.5 → Cool, reward +1; Probability 0.5 → stay Warm, reward +1
  • Fast: Probability 1 → Overheated, reward −10

From Overheated: Terminal state, no actions. Value = 0.

5.10.5 Worked Computation: Iteration 1

Initial values: \(V_0(\text{Cool}) = 0\), \(V_0(\text{Warm}) = 0\), \(V_0(\text{Overheated}) = 0\)

Update Cool:

Action Slow:

\[ \text{Slow: } 1 \times (1 + 0.9 \times 0) = 1 \]

Action Fast:

\[ \text{Fast: } 0.5 \times (2 + 0.9 \times 0) + 0.5 \times (2 + 0.9 \times 0) = 1 + 1 = 2 \]

\[ V_1(\text{Cool}) = \max(1, 2) = \mathbf{2} \]

Update Warm:

Action Slow:

\[ \text{Slow: } 0.5 \times (1 + 0.9 \times 0) + 0.5 \times (1 + 0.9 \times 0) = 0.5 + 0.5 = 1 \]

Action Fast:

\[ \text{Fast: } 1 \times (-10 + 0.9 \times 0) = -10 \]

\[ V_1(\text{Warm}) = \max(1, -10) = \mathbf{1} \]

Overheated: No actions, \(V_1(\text{Overheated}) = \mathbf{0}\)

Iteration 1 result: Cool = 2, Warm = 1, Overheated = 0

Convergence check: \(\Delta = \max(|2-0|, |1-0|, |0-0|) = 2 > \theta\). Continue.

5.10.6 Worked Computation: Iteration 2

Using iteration 1 values (not in-place): \(V_1(\text{Cool}) = 2\), \(V_1(\text{Warm}) = 1\), \(V_1(\text{Overheated}) = 0\)

Update Cool:

Action Slow:

\[ 1 \times (1 + 0.9 \times 2) = 1 + 1.8 = 2.8 \]

Action Fast:

\[ 0.5 \times (2 + 0.9 \times 2) + 0.5 \times (2 + 0.9 \times 1) = 0.5 \times 3.8 + 0.5 \times 2.9 = 1.9 + 1.45 = 3.35 \]

\[ V_2(\text{Cool}) = \max(2.8, 3.35) = \mathbf{3.35} \]

Update Warm:

Action Slow:

\[ 0.5 \times (1 + 0.9 \times 2) + 0.5 \times (1 + 0.9 \times 1) = 0.5 \times 2.8 + 0.5 \times 1.9 = 1.4 + 0.95 = 2.35 \]

Action Fast:

\[ 1 \times (-10 + 0.9 \times 0) = -10 \]

\[ V_2(\text{Warm}) = \max(2.35, -10) = \mathbf{2.35} \]

Iteration 2 result: Cool = 3.35, Warm = 2.35, Overheated = 0

Convergence check: \(\Delta = \max(|3.35 - 2|, |2.35 - 1|, |0 - 0|) = 1.35 > \theta\). Continue iterating.

Trend: The values of Cool and Warm are growing because the "slow" action lets the agent stay in good states and accumulate reward. The fast action from Warm is terrible (−10), so the algorithm learns to avoid it. Over several more iterations, the values will converge.

5.10.7 In-Place vs Not-In-Place

Scope: Exam-critical distinction

Not-in-place version (used in the examples above): Uses the previous iteration's values for all successor states. You save all old values first, then compute all new values.

In-place version: Uses the most recently computed values. When computing Warm's new value, if Cool was already updated in this sweep, you use Cool's new value instead of the old one.

Why in-place converges faster: New information propagates immediately. If Cool's value improved, Warm's update benefits from that improvement right away — no need to wait for the next sweep.

Exam warning: Questions may specify either version. Read carefully. The update formula looks the same — the difference is whether you use \(V_k(s')\) or \(V_{k+1}(s')\) on the right-hand side.

Pitfalls:

  1. Using new values when told to use old ones. In the not-in-place version, save all old values before updating. Do not mix old and new within the same sweep.
  2. Forgetting that \(\theta\) controls accuracy, not correctness. A larger \(\theta\) means you stop earlier with less accurate values. A smaller \(\theta\) means more iterations but more accurate values.
  3. Not tracking \(\Delta\). Without convergence checking, the algorithm might run forever or stop too early.
  4. Confusing value iteration with policy evaluation. Policy evaluation computes \(V_\pi\) for a given policy (uses \(\sum_a \pi(a|s)\)). Value iteration computes \(V^*\) (uses \(\max_a\)). They look similar but solve different problems.

Recap + Bridge: Value iteration computes \(V^*\) by repeatedly applying the Bellman optimality update. It alternates between evaluating states (using the Bellman equation) and improving the implicit policy (the \(\max\) picks the best action). This is the simplest DP algorithm for finding optimal values. It is an example of a value-based algorithm — compute values first, extract policy second.

Q: Should we use the old values or the newly computed values?

A: The examples use the not-in-place version — always the old values from the previous iteration. The in-place version uses whatever values are most recent. In-place converges faster. Be careful in exams: the question will specify which version to use. If it says "not-in-place" or "synchronous", use old values. If it says "in-place" or "asynchronous", use the latest values.

Value iteration is one of the two main DP algorithms (the other being policy iteration, covered in the next lecture). It is the foundation for many model-free methods — Q-learning is essentially value iteration applied to learned Q-values instead of known transition probabilities. Understanding value iteration deeply makes every later algorithm in RL easier to grasp.

5.11 Value-Based vs Policy-Based Algorithms

Hook: You have seen value iteration compute optimal values and then extract a policy. But there is another approach: directly optimizing the policy without computing values at all. These two families — value-based and policy-based — are the two main roads in RL.

5.11.1 Definition and Explanation

Intuition + Analogy: Imagine learning chess two ways. The value-based approach: first learn to evaluate how good every board position is (assign a score), then pick the move that leads to the best-scoring position. The policy-based approach: directly learn which move to play in each position, without ever assigning scores. Both can work, but they have different strengths.

Where the analogy breaks: in practice, most modern methods combine both ideas (actor-critic methods). The division is conceptual, not a hard wall.

Core Definition:

Value-based algorithms:

  1. Compute value functions (\(V\), \(Q\), or both)
  2. Derive the policy from the values (e.g., pick the action with the highest Q-value)

Value iteration is a value-based DP algorithm: it computes \(V^*\), then extracts \(\pi^*\) by taking \(\arg\max_a\) at each state.

Policy-based algorithms (covered in later lectures):

  1. Directly parameterize the policy (e.g., a neural network that outputs action probabilities)
  2. Optimize the parameters to maximize expected return
  3. No explicit value function needed (though many methods use one as a baseline)

The distinction from the textbook: value-based methods "compute values first, then extract the policy, rather than directly optimizing the policy."

5.11.2 Symbol Registry

  • \(V^*(s)\) — optimal state value function — scalar
  • \(Q^*(s,a)\) — optimal action value function — scalar
  • \(\pi^*\) — optimal policy — function mapping states to action probabilities
  • \(\arg\max_a\) — the action \(a\) that maximizes the expression

Pitfalls:

  1. Thinking one is always better. Value-based methods are sample-efficient but struggle with continuous actions. Policy-based methods handle continuous actions naturally but can be less stable. Most practical systems combine both.
  2. Forgetting that value iteration IS a value-based method. It computes \(V^*\) and then reads off the policy. The \(\max\) in the update is the policy improvement step — it is implicit, not explicit.

Recap + Bridge: Value-based methods (like value iteration) compute values and extract a policy. Policy-based methods optimize the policy directly. This lecture focuses on value-based DP. The next lecture will cover policy iteration — another DP algorithm that alternates between full policy evaluation and policy improvement.

This conceptual split runs through all of RL. Q-learning and DQN are value-based. REINFORCE and PPO are policy-based. Actor-critic methods (A2C, SAC) sit in the middle, using both a value function and a policy. Understanding this taxonomy helps you place every algorithm you will encounter.

5.12 Dynamic Programming Overview

Hook: You now know the Bellman equations and value iteration. But these are just two tools in a larger toolbox called dynamic programming. DP is the family of algorithms that compute optimal policies when you know the full MDP model. It is the foundation that all of RL builds on.

5.12.1 Definition and Explanation

Intuition + Analogy: Think of DP as having a perfect map of a city. You know every road, every traffic light, every shortcut. With that map, you can plan the optimal route from any starting point to any destination. DP algorithms do exactly this — they use complete knowledge of the environment's dynamics to compute optimal behavior.

Where the analogy breaks: most real-world problems do not give you a perfect map. That is why we need model-free RL, which learns the map from experience. But DP tells us what the ideal solution looks like and gives us the update rules that model-free methods approximate.

Dynamic programming (DP) refers to a collection of algorithms that compute optimal policies given a perfect model of the environment as an MDP. The textbook defines DP as using "the key idea of value functions to organize and structure the search for good policies."

Core Definition: DP requires:

  1. A complete and accurate model of the environment — the dynamics function \(p(s', r | s, a)\)
  2. Enough computation to sweep through the state space

DP algorithms work by turning Bellman equations into update rules. When the updates stop changing values, convergence has occurred — the values satisfy the corresponding Bellman equation.

5.12.2 Key DP Concepts

Policy Evaluation (Prediction): Computing \(V_\pi\) for a given policy \(\pi\). The update rule is the Bellman expectation equation applied iteratively:

\[ V_{k+1}(s) = \sum_a \pi(a|s) \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_k(s') \right] \]

This converges to \(V_\pi\) as \(k \to \infty\). The textbook calls this iterative policy evaluation.

Policy Improvement: Given \(V_\pi\), derive a better policy \(\pi'\) by acting greedily:

\[ \pi'(s) = \arg\max_a \sum_{s', r} p(s', r | s, a) \left[ r + \gamma V_\pi(s') \right] \]

The policy improvement theorem guarantees: if \(\pi'\) is greedy with respect to \(V_\pi\), then \(V_{\pi'}(s) \geq V_\pi(s)\) for all \(s\). The new policy is at least as good as the old one.

5.12.3 Symbol Registry

  • \(V_\pi(s)\) — state value function under policy \(\pi\) — scalar
  • \(V^*(s)\) — optimal state value function — scalar
  • \(\pi^*\) — optimal policy — function mapping states to action probabilities
  • \(\pi'(s)\) — improved policy — function derived from acting greedily w.r.t. \(V_\pi\)

These two steps — evaluation and improvement — are the primitive building blocks of every DP algorithm.

The lecture covers two DP algorithms:

  • Value iteration (this lecture): Combines one sweep of policy evaluation with one sweep of policy improvement in a single update. Uses the \(\max\) over actions.
  • Policy iteration (next lecture): Alternates between full policy evaluation (run until convergence) and policy improvement. Each step is done completely before switching.

The textbook introduces generalized policy iteration (GPI) — the general idea of letting evaluation and improvement interact. Value iteration and policy iteration are special cases of GPI with different granularities.

DP is theoretically important but practically limited: it needs the full model and scales poorly to large state spaces. The textbook notes that DP methods can handle "millions of states" with modern computers, but problems like backgammon (\(10^{20}\) states) are out of reach. Model-free RL methods extend DP's ideas to problems where the model is unknown.

Pitfalls:

  1. Confusing policy evaluation with value iteration. Policy evaluation computes \(V_\pi\) for a fixed policy (uses \(\sum_a \pi(a|s)\)). Value iteration computes \(V^*\) (uses \(\max_a\)). They share the same structure but different operations over actions.
  2. Thinking DP is all of RL. DP is the foundation, but it requires a known model. Most practical RL is model-free.
  3. Forgetting that policy improvement is guaranteed. The greedy policy with respect to \(V_\pi\) is provably at least as good as \(\pi\). This is not a heuristic — it is a theorem.

Recap + Bridge: Dynamic programming is the family of algorithms that compute optimal policies from a known model. Its two building blocks — policy evaluation and policy improvement — appear in every RL method, even model-free ones. Value iteration (this lecture) combines them in one update. Policy iteration (next lecture) alternates between them. Understanding DP is essential because all of RL can be viewed as approximate DP.

DP methods are used in robotics (when the physics model is known), operations research (supply chain optimization), game AI (when the game tree is tractable), and as the theoretical backbone of every RL algorithm. The concepts of bootstrapping (updating estimates based on other estimates) and GPI carry directly into Q-learning, SARSA, and deep RL methods.

Exam Guidance Summary

Policy evaluation and policy improvement are two primitive steps present in every DP algorithm. Understanding these building blocks is critical — they appear in value iteration, policy iteration, and generalized policy iteration.

In-place vs not-in-place value iteration: Be careful to distinguish which version you are using. The not-in-place version uses old values from the previous sweep. The in-place version uses the most recently computed values. Questions may specify either one. The in-place version converges faster.

Bellman equation application: Expect numerical problems where you verify state values using the Bellman equation. Practice by hand: pick a state, look up neighbor values, apply the equation, check the result. The grid world example in Section 5.8 is your template.

Understanding the algorithm is more important than memorizing it. If you understand how value iteration works (apply Bellman optimality update, track convergence), you can adapt to different scenarios — different state spaces, different dynamics, different reward structures.

  • Solve practice problems from the notes to build facility with the computations. The race car problem and grid world verification are the types of questions to expect.
  • The notes cover the complete story and should be read with no omissions. Every section builds on the previous one.
  • Policy iteration is optional; value iteration is the main algorithm to know. Focus on understanding value iteration deeply — the update rule, the convergence criterion, and the in-place vs not-in-place distinction.

Key Industry Applications

  • Traffic control: The MDP framework models traffic signal optimization. States represent traffic conditions, actions are signal changes, and rewards reflect flow efficiency. City traffic systems use RL to learn signal timing policies that reduce congestion.
  • Atari games: The classic RL benchmark. States are raw game frames (pixels), actions are controller inputs, and rewards are score changes. Deep Q-Networks (DQN) use the MDP formulation to learn directly from pixels, achieving superhuman performance on many games.
  • Recycling robot: An MDP example for autonomous agents operating under resource constraints. The robot must balance exploration (searching for cans) against conservation (waiting or recharging) — a fundamental trade-off in RL.
  • Cart-pole balancing: Demonstrates episodic vs continuing task formulation. The same physical problem can be modeled either way, showing how the MDP framework is flexible. This is a standard testbed for RL algorithms.
  • Race car problem: Illustrates value iteration with a simple 3-state MDP (Cool, Warm, Overheated). The agent learns that driving fast is rewarding in the short term but risks overheating — a classic exploration-exploitation and risk-reward trade-off.
  • Dynamic programming in operations research: DP methods (policy iteration, value iteration) are used in supply chain management, inventory control, scheduling, and resource allocation — anywhere a known MDP model exists and the state space is tractable.

5.1 MDP Review and Agent-Environment Interface

Must know: An MDP is the tuple (S, A, p, r, gamma). The agent-environment boundary separates what the agent controls from what it cannot. The Markov property says the future depends only on the current state, not the path taken to reach it.

\[ p(s', r \mid s, a)\ \text{dynamics};\quad p(s'\mid s,a)=\sum_r p(s',r\mid s,a);\quad r(s,a)=\sum_r r\sum_{s'} p(s',r\mid s,a) \]

Pitfall: Placing the agent-environment boundary wrongly: the agent's sensors and actuators belong to the environment, not the agent. The agent only chooses actions.

Self-check: Write the MDP tuple and state in one sentence what each symbol represents.

Connects to: Reward hypothesis (5.2), Policy (5.4), State and action value functions (5.5, 5.6).

5.2 Reward Hypothesis

Must know: Every RL goal is framed as maximizing the expected cumulative discounted return G_t. The reward signal communicates WHAT we want, never HOW to achieve it.

\[ G_t = \sum_{k=0}^{\infty} \gamma^k R_{t+k+1};\quad G_t = R_{t+1} + \gamma G_{t+1} \]

Pitfall: Thinking the reward defines good behaviour. It defines the goal; reward hacking happens when you reward the wrong thing and the agent optimizes that instead.

Self-check: Why must the reward be a single scalar rather than a vector of objectives?

Connects to: Episodic vs continuing tasks (5.3), return appears in every value function (5.5, 5.6).

5.3 Episodic vs Continuing Tasks

Must know: Episodic tasks end at a terminal state and use a finite return. Continuing tasks never end, so discounting with gamma < 1 is required to keep the return finite.

\[ \text{episodic: } G_t = R_{t+1}+\cdots+R_T;\quad \text{continuing: } G_t = \sum_{k=0}^{\infty}\gamma^k R_{t+k+1} \]

Pitfall: Using gamma = 1 in a continuing task. The return then diverges to infinity and the math breaks.

Self-check: Can cart-pole balancing be modeled both episodically and as a continuing task? Yes — and both lead to balancing.

Connects to: Reward hypothesis (5.2), value functions (5.5).

5.4 Policy

Must know: A policy pi maps states to actions. Deterministic: pi(s) = a. Stochastic: pi(a|s) = P(A_t = a | S_t = s), with sum_a pi(a|s) = 1. It is the object RL algorithms optimize.

\[ \pi(a\mid s)=P(A_t=a\mid S_t=s),\quad \sum_a \pi(a\mid s)=1 \]

Pitfall: Confusing the policy (what to do) with the value function (how good a state is). They are different objects.

Self-check: Give one example of a deterministic policy and one of a stochastic policy.

Connects to: Value functions (5.5, 5.6), Bellman equations (5.7).

5.5 State Value Function V_pi

Must know: V_pi(s) is the expected return starting from state s and following policy pi thereafter. It depends on the policy: change pi and the values change. V_pi(terminal) = 0.

\[ V_\pi(s)=\mathbb{E}_\pi[G_t\mid S_t=s]=\mathbb{E}_\pi\!\left[\sum_{k=0}^{\infty}\gamma^k R_{t+k+1}\;\middle|\;S_t=s\right] \]

Pitfall: Thinking V depends only on the state. The same state can have very different values under different policies.

Self-check: Why can one state have a high value under a good policy but a low value under a bad one?

Connects to: Action value function Q_pi (5.6), Bellman expectation equation (5.7).

5.6 Action Value Function Q_pi

Must know: Q_pi(s,a) is the expected return for taking action a in state s then following pi. Q is preferred over V for action selection because, once known, it needs no model at decision time.

\[ Q_\pi(s,a)=\mathbb{E}_\pi[G_t\mid S_t=s,A_t=a];\quad V_\pi(s)=\sum_a \pi(a\mid s)\,Q_\pi(s,a) \]

Pitfall: Confusing Q (value of DOING action a) with V (value of BEING in state s). They are related but distinct.

Self-check: Why is Q more useful than V when action outcomes are stochastic?

Connects to: State value function (5.5), Bellman equations (5.7).

5.7 Bellman Expectation Equation

Must know: V_pi(s) equals the expected immediate reward plus the discounted expected value of successor states, averaging over both the policy and the dynamics. It is a system of |S| linear equations.

\[ V_\pi(s)=\sum_a \pi(a\mid s)\sum_{s',r} p(s',r\mid s,a)\,[r+\gamma V_\pi(s')] \]

Pitfall: Mixing up the two probability layers, or confusing this expectation equation (average over actions) with the optimality equation (max over actions).

Self-check: Name the two distinct probability sources in the Bellman expectation equation.

Connects to: V_pi (5.5), Q_pi (5.6), Bellman optimality (5.9).

5.8 Grid World Example

Must know: A concrete 4x4 grid world lets you verify the Bellman equation by hand under an equiprobable policy (pi = 0.25). States near high reward have high values; edge and corner states have low values.

\[ V(s)=\sum_a \pi(a\mid s)\sum_{s',r} p(s',r\mid s,a)\,[r+\gamma V(s')],\quad \pi(a\mid s)=0.25 \]

Pitfall: Reading the wrong neighbour value from the table, or forgetting that moving into a wall gives reward -1 and keeps you in place.

Self-check: Verify V(3,3) by looking up its four neighbours and applying one Bellman step.

Connects to: Bellman expectation equation (5.7).

5.9 Optimal Policies and Optimal Value Functions

Must know: An optimal policy pi* satisfies V_{pi*}(s) >= V_pi(s) for every s and every policy pi. V*(s) = max_pi V_pi(s). The Bellman optimality equation replaces the policy average with max_a.

\[ V^*(s)=\max_a \sum_{s',r} p(s',r\mid s,a)\,[r+\gamma V^*(s')];\quad V^*(s)=\max_a Q^*(s,a) \]

Pitfall: Confusing max_a (optimality) with the weighted average sum_a pi(a|s) (expectation). One finds the best policy; the other evaluates a fixed one.

Self-check: Once you have V*, how do you recover an optimal policy pi*? Act greedily with respect to V*.

Connects to: Bellman expectation (5.7), value iteration (5.10).

5.10 Value Iteration Algorithm

Must know: Value iteration repeatedly applies the Bellman optimality update V_{k+1}(s) = max_a [...] using old values, stopping when the largest change falls below theta. In-place uses the newest values and converges faster.

\[ V_{k+1}(s)=\max_a \sum_{s',r} p(s',r\mid s,a)\,[r+\gamma V_k(s')] \]

Pitfall: Mixing up in-place vs not-in-place: the difference is whether the right-hand side uses V_k(s') (old) or V_{k+1}(s') (newest). Exams specify which.

Self-check: Trace value iteration on the 3-state race car problem for two iterations by hand.

Connects to: Bellman optimality (5.9), dynamic programming (5.12), policy iteration (next lecture).

5.11 Value-Based vs Policy-Based Algorithms

Must know: Value-based methods compute value functions first, then extract a policy (value iteration is value-based). Policy-based methods optimize the policy directly, often with a neural network, and need no explicit value function.

\[ \text{value-based: } \pi^*(s)=\arg\max_a Q^*(s,a);\quad \text{policy-based: optimize } \pi_\theta \text{ directly} \]

Pitfall: Thinking one family is always superior. Most modern systems (actor-critic) combine both ideas.

Self-check: Is value iteration value-based or policy-based? Value-based.

Connects to: Value iteration (5.10), dynamic programming (5.12).

5.12 Dynamic Programming Overview

Must know: DP computes optimal policies from a known model using two building blocks: policy evaluation (compute V_pi) and policy improvement (act greedily w.r.t. V_pi). Value iteration fuses one sweep of each into a single update.

\[ \text{eval: } V_{k+1}(s)=\sum_a \pi(a\mid s)\sum_{s',r}p(s',r\mid s,a)[r+\gamma V_k(s')];\quad \pi'(s)=\arg\max_a \sum_{s',r}p(s',r\mid s,a)[r+\gamma V_\pi(s')] \]

Pitfall: Confusing policy evaluation (sum_a pi(a|s), fixed policy) with value iteration (max_a, optimal policy). They share structure but differ in the action operation.

Self-check: What are the two primitive steps that appear in every DP algorithm?

Connects to: Bellman equations (5.7, 5.9), value iteration (5.10).
