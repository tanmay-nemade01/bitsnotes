This set of notes covers the foundations of object-oriented analysis and design (OOAD). It explains why the approach exists, how requirements are captured with use cases, what failing projects teach us, which process models organize development, and how to find objects. It starts with a quick review of the core object-oriented vocabulary.

2.1 Quiz Recap: The Core Vocabulary of Objects

2.1.1 The Basic Vocabulary

The session opened by reviewing answers to a short quiz on object-oriented programming vocabulary. The questions were described as very simple. Students were told to write their answers rather than say them out loud, because the same style of question would come again in the same form.

What is the smallest set of words you must keep straight before you can talk about analysis and design? If two words name the same idea, mixing them later will look like two ideas.

The quiz treated several everyday names as one family.

  • Variables, fields, or attributes — all three names refer to the same thing: the data that a class stores. The accepted answer was "variables, fields or attributes".
  • Methods — the operations that work on those attributes. The pairing was stated directly: "this is attributes, and this is methods."
  • Interface — this was the accepted answer for more than one question. An interface (the published list of operations) declares what operations are available without saying how they are carried out.
  • Class — "the blueprint of an object." This answer was confirmed as correct.
  • Package — also confirmed correct. A package (a named group of related classes) keeps those classes together.
  • API — short for application programming interface, the last and simplest question of the quiz.

Think of a class as a cookie cutter and each object as a cookie. The cutter is the class. Each cookie is an instance. The icing colors are attributes. The way you decorate it is a method. The analogy breaks when one object must change another object's cutter; real software objects share a class definition, they do not each own a private blueprint.

Term map for the quiz. Attributes hold state. Methods change or report that state. An interface names the methods outsiders may call. A class is the blueprint. A package groups related classes. An API is the interface a library or service publishes to other programs.

2.1.2 Abstraction, Hiding, and Data Encapsulation

One quiz question produced a vocabulary correction that matters for the whole course, because three closely related words got tangled up.

Q: For the quiz question on hiding: one answer said "ignoring the details, focusing on what is really required". Is that hiding?

A: Ignoring the details and focusing on what is really required is abstraction, not hiding. Hiding internal data from the outside world and accessing it through publicly exposed methods is data encapsulation. And hiding does not mean only data hiding — hiding covers many things. The preferred term for "ignore details, keep what is required" is abstraction.

The key correction is that hiding is a broader idea than data hiding. Hiding internal data and letting the outside world touch it only through public methods is one specific use of hiding. That specific combination is called data encapsulation.

Picture a restaurant kitchen. Abstraction is reading the menu and not caring how the sauce is reduced. Hiding is keeping the kitchen door closed. Encapsulation is putting the recipe, the stove, and the cook's methods inside that kitchen, and letting diners order only through the waiter. The analogy breaks if the diner walks in and stirs the pot; that is the C-style "if you have the code, you have access to everything" problem taken up later.

Pitfall: Do not treat abstraction, hiding, and encapsulation as synonyms. Abstraction chooses what to talk about. Hiding restricts what outsiders can see. Encapsulation packs data with the methods that guard it.

2.1.3 Exam Notes

Exam note: Simple, quiz-style questions about this vocabulary — attributes, interface, class as blueprint, package, API, and the abstraction-versus-encapsulation distinction — will come in the quiz and in the exam. Students are expected to write their own answers.

Keep the three-word split ready: abstraction = focus; encapsulation = pack and protect; hiding = the wider family that includes more than data.

2.2 Object Orientation and the Real World

2.2.1 Modeling Reality with Objects

The main reason object orientation became popular is that it is very much connected to the real world. Our world is full of objects, and every activity in it gets done by objects cooperating. In software we create an abstraction of this reality and build objects "as our world is going on," instead of using the traditional methods built around functionality.

An object — the fundamental building block — has state and behavior. State is the data the object holds. Behavior is what the object can do. All the objects that share the same shape are described by a class (the blueprint from the quiz). Related classes can be combined into packages. Because we start from objects at the lowest level and assemble them into a system, this is a bottom-up approach.

In older software engineering practice, systems were decomposed with data flow diagrams (DFDs). In object-oriented analysis and design we do not use DFDs. We work at the object level and build the system out of objects.

If a classroom session is "happening," what is doing the work? The people, the desks, the projector, even the idea of "attendance" cooperate. Software that copies that picture starts from those participants, not from a list of functions such as takeAttendance().

Visual intuition: imagine a still photograph of a street. Each labeled blob (car, rider, traffic light) is a candidate object. Arrows between blobs are later collaborations. The takeaway is that the photo already has things with state (position, color) and behavior (move, signal). A DFD would instead show "traffic flow" as a pipeline of processes, which hides those things.

2.2.2 From Functions to Objects

The contrast with the old way of thinking was drawn sharply.

C versus Java as a thinking switch. In C programming, everything is a function. You decompose a program into functions and instructions: computeTax(), printReceipt(), saveFile(). In Java, everything is an object. You ask "what objects are in this problem, and what should each one do?" A Taxpayer object holds income (state) and can computeTax() (behavior). A Receipt object can print itself. Sense-check: both languages can call procedures, but the unit of thought changed from a function list to a cooperating set of objects.

Object orientation flips the first question. Instead of "what functions do we need?", we ask "what objects are in this problem?"

Scope: This C-versus-Java contrast is a teaching contrast, not a claim that C cannot model objects or that Java has no functions. It marks the shift from functional decomposition to object decomposition.

2.2.3 The Four Principles Across the Process

Once requirements are understood, the overall system is decomposed over the real world in terms of objects. Four principles are applied throughout the process:

  • abstraction — ignoring details and focusing on what is really required
  • encapsulation — packaging data with the methods that access it
  • inheritance — reusing and specializing classes
  • polymorphism — one interface, many implementations

The same four principles appear in analysis, in design, and in implementation.

Object orientation is popular because it models a world already made of objects. The process still starts with requirements, then finds objects, then applies the four principles at every later stage.

Banks, hospitals, and ride-hailing apps all have people, accounts, trips, and rules. Those named things survive from analysis into Java or C++ classes. That continuity is the practical payoff of modeling the real world.

2.3 The OOAD Roadmap: Requirements, Analysis, Design, and Implementation

2.3.1 Requirements Come First

Object orientation cannot begin without a clear problem. In mathematics we are given a problem statement and must understand it before we can write the answer. The same holds in English or any language — the problem must be understood well first. That is the analysis part. The method used to analyze and understand the requirements varies from person to person and from company to company, but understanding the requirements is non-negotiable.

At a high level we write down the functional requirements — the functionalities that should exist in the system. After the requirements are captured, we decompose the overall system over the real world into objects. In analysis, we stay in the problem domain only: we look at the problem as the user experiences it, not at code.

Would you solve an unseen math paper before reading the question? Requirements play that same first role. Pretty class diagrams that do not match what users asked for are still the wrong system.

2.3.2 From Analysis to Design to Implementation

The best part of object orientation is that objects appear in analysis, in design, and in implementation. Everywhere we work with objects.

  • Object-oriented analysis — identify objects from the problem statement, taking inspiration from the real-world requirements.
  • Object-oriented design — keep renaming and adding objects as the design matures.
  • Implementation — build the system with an object-oriented programming language.

The central job of the whole process is to identify the right set of objects, applying the object-oriented principles learned in programming courses. Requirements lead to a software solution, and finding objects is the necessary step in between.

Standard texts split the same path: analysis describes what the product should do; design decides how software objects collaborate; implementation writes the code. Experience on one pass can send you back to analysis. That loop is normal. It is not a failure of the first pass.

Assumption: Analysis stays in the problem domain. If you jump to tables, SQL, or GUI widgets too soon, you are already designing (or coding), and you will miss real-world objects.

2.3.3 UML: A Notation, Not a Programming Language

To represent and describe the system before it is implemented, we use the Unified Modeling Language (UML). UML is not a programming language — it is a notation through which we analyze, represent, and describe the system. Requirements usually arrive as words or very big text that is difficult to grasp, so throughout the course we design use case diagrams, class diagrams, and various other UML diagrams to make the system visible.

UML is a visual language for specifying, constructing, and documenting the artifacts of systems. It is the usual diagramming notation for object-oriented software. Knowing the notation is useful. Knowing how to think in objects is the skill that matters. A diagram tool does not make a design good.

Requirements first, then objects in analysis, then more objects in design, then an OO language in implementation. UML is the shared notation for those pictures, not a language you compile.

Teams use UML as a sketch on a whiteboard, as a more detailed blueprint, or rarely as a source for generated code. This course uses it as a way to see requirements and objects before Java or C++ code exists.

2.4 Use Case Analysis: Requirements as Stories

2.4.1 Why Use Case Analysis?

Requirements written as plain text are hard to understand, so we need an analysis technique to work on them. Use case analysis is that technique: a requirements analysis technique. It became a de facto standard for capturing and representing requirements because gathering and analyzing requirements was one of the most challenging aspects of software development.

Q: What do you mean by a use case?

A: Pick up a scenario and break it down — a scenario in which a program is required to run. It is not a test case. Use case analysis is a requirements analysis technique for gathering requirements, written in terms of the interaction of users with the system. One use case is a collection of scenarios, not just one scenario — it is a complete requirement, and you can relate it to a transaction, like a banking transaction that must be complete. A use case might look like a test case because both use the word "case," but the preferred term here is scenario: a path of using the system.

Two terms got separated right away: a use case is a scenario (a case in which a user is using the system), and it is not a test case. It also relates to the word "case" you already know from programming — the switch statement in C, Java, or C++ uses the keyword case.

A scenario is one path: success with cash, or failure because a card is declined. Informally, a use case is the collection of related success and failure scenarios that describe an actor using a system to support a goal. A complete bank withdrawal is like that: enough cash, wrong PIN, account frozen — several scenarios, one use case.

Use cases are text stories. The UML use-case diagram is only a map of names. The valuable work is writing the stories.

2.4.2 Users, Actors, and the Black-Box View

Earlier software projects failed because users were not given importance — their requirements were not taken properly, so people did not accept the products. Users are one of the most important parts of a system because they are the end users. We must involve them in requirements gathering and build the system as they want it; user satisfaction and usability testing are important aspects. The technique became popular, and a lot of the work on it was done by Ivar Jacobson, who has published many books on the subject, alongside the various books by Cockburn.

In a use case, the system is treated as a black box. We do not care what is inside; we only record the interactions between users and the system. The different users are called actors in use case analysis. Each actor plays a role outside the system and gets some benefit out of it, so we only capture those requirements where a user will get a benefit.

An actor is something with behavior: a person identified by role, another computer system, or an organization. The cashier is an actor. The payment network can be an actor. Draw actors as stick figures on a use-case diagram if you need a picture, but name them by role, not by a person's name.

Scope: Black-box use cases record who talks to the system and what value they get. They do not record class names, database tables, or algorithms. Those belong later.

2.4.3 Naming Use Cases: Verb + Noun

Use cases follow a fixed naming convention: verb + noun. We name a use case with an action and the thing the action applies to — withdraw money, deposit money, or, for a library, issue book. This makes it very clear what the use case does. Use cases can be written at a high level, and later expanded into more detailed use cases.

Good names include Withdraw Funds, Register Student in Seminar, and Deliver Shipment. Weak verbs such as "process," "perform," and "do" often hide the real action. Stakeholders say they withdraw funds; they rarely say they process a withdrawal transaction.

A use case is a collection of scenarios of using the system, not a test case. Actors sit outside a black box. Names start with a strong verb plus a noun.

2.5 The Standish Report: Why Software Projects Fail

2.5.1 Software versus Bridge Construction

Software development was often compared with bridge construction or building construction, and software architecture courses draw many similarities between the two. The comparison teaches a hard lesson. When bridges failed — late, over budget, or collapsing — people did case studies, thorough investigations, and careful reporting of every failure, so the next bridge was built perfectly. With software, when something failed, people just restarted; they did not study failures in a systematic manner. That gap is exactly why software engineering came into the picture: to make software development systematic, and to define models such as the waterfall model, which mirrors engineering disciplines but does not work very well for software.

If a bridge falls, investigators write a public report. If software fails, teams often quietly restart. The Standish work tried to do for software what failure reports did for bridges: count the damage and name the causes.

2.5.2 The Study and Its Numbers

The Standish report — also called the Standish CHAOS report — was published in 1995 (research often dated 1994, report circulated in 1995). It is a small report of about 15 to 20 pages. The researchers studied projects across the world, in different categories and case studies, and they interacted with 365 companies. Those respondents represented 8,380 applications. The main problems they found: projects not delivered on time, not delivered within budget, and poor software quality.

The session summarized overrun bands in spoken ranges: most cost overruns fell in the 20% to 100% range; some projects overran by 20% to 50%; a small share — about 5% of projects — exceeded 400%; about 60% of the projects overran in terms of cost; time overruns of 20% to 100%, and in some cases 200%, were common; many projects were never delivered on time.

The published CHAOS tables for challenged and failed projects give finer bands. Keep the classroom ranges for the exam story, and use the tables when you need the report's own numbers.

Students were asked to name reasons why projects failed, and the brainstorm produced: requirements not proper, user inputs not taken, poor risk management, infrastructure or code complexity, mistakes in design, bad design, poor fault tolerance, and lack of concurrency. Many projects also suffered from content deficiencies — the delivered product did not have the required features.

2.5.3 Success Factors and Failure Factors

The report evaluated project success factors and failure factors. The most important success factor was user involvement: projects where users were continuously involved were very successful. After that came, in order:

  1. Executive management support — top management, the people whose money goes into the system.
  2. A clear statement of requirements — what is really needed, not just what the client wants.
  3. Proper planning.
  4. Realistic expectations.
  5. Smaller milestones.
  6. Competent staff — people who own the project and have a clear vision and objectives; highly productive and professional people.

The report's own response shares for success were: user involvement 15.9%, executive management support 13.9%, clear statement of requirements 13.0%, proper planning 9.6%, realistic expectations 8.2%, smaller project milestones 7.7%, competent staff 7.2%, then ownership, clear vision, and hard-working staff.

On the failure side, the biggest group of reasons was about requirements: lack of user input, incomplete requirements, and changing requirements and specifications. Because changing requirements were the main problem, requirements must be managed. Other failure reasons: lack of executive support, technology incompetence (people not knowing how to implement), lack of resources, unrealistic expectations, and unclear objectives.

Software projects fail when user input is missing and requirements keep changing. Manage requirements. Involve users continuously. That is the warning the report exists to deliver.

2.5.4 Case Studies

The report contains case studies of individual projects, including the California Department of Motor Vehicles. In that story, a 1987 effort to rebuild driver-license and registration systems was cancelled by 1993 after about 45 million dollars had been spent, with many restarts. Many projects failed, but some succeeded as well. Students were told to read the full report — the failure and success factors are important material.

Exam note: Read the Standish report (1995). The success factors and failure factors it found are expected material. User involvement is first. Requirements problems dominate failure.

2.6 Software Process Models

2.6.1 The Named Models

Several software engineering process models were surveyed, and students were asked to study them (they are also covered in other courses):

  • Agile — very popular nowadays.
  • Waterfall — for study purposes only; it is not practical.
  • Spiral — a good model.
  • Incremental model — worth studying.
  • Rapid application development — another process model.

A process model is a planned rhythm for analysis, design, build, and check. Without a named rhythm, teams still work — they just hide the plan.

Agile values working software, customer collaboration, and change. Waterfall copies civil-engineering stages in a single pass; it is taught as history and as a contrast. Spiral puts risk analysis on repeating cycles. Incremental delivers slices of function. Rapid application development stresses short build cycles and user workshops.

2.6.2 Build and Fix

If you use no model at all, you are following what can be called the build and fix model: given the requirements, you just build it and fix it, with no analysis of requirements in between. This works for a small program and a small team of four or five people. Once the project is large and the software is complex, build and fix breaks down, and you must have a software development process model.

Scope: Build and fix is honest for a weekend script. It fails when many people, many requirements, and many failures must be tracked. Size and complexity, not fashion, force a named model.

2.6.3 The Unified Development Process and the Iterative Model

This course works on the unified development process model, which is very popular for object-oriented systems because it uses the best practices of current approaches: some part agile, some part waterfall, some part incremental. The most popular model for object orientation is the iterative model: repeatedly define the things, do the job, and repeat — each cycle refines the system.

The Unified Process is an iterative, use-case driven, architecture-centric process. An agile reading of it keeps documents light and iterates. Object-oriented analysis and design is usually taught inside that repeating cycle, not as one giant waterfall of diagrams.

Exam note: Study all the different process models — at least agile — so the approach is clear. Waterfall is for study purposes only.

2.7 Objects, Interfaces, and the Black-Box View

2.7.1 Reusable and Replaceable

Object orientation exists so that code can be reusable: with inheritance you do not need to write the same thing again and again, and components are replaceable. The big motivation was maintenance. With C and other procedural languages, maintenance was a huge challenge — testing, maintaining, and understanding somebody else's code is still very hard. The object-oriented answer is to treat finished components as black boxes.

Purpose of the black-box object. Outsiders depend on a published interface. They can reuse the component, or swap a new implementation, without rewriting callers. Maintenance cost drops because you do not have to read every internal line to use the thing.

2.7.2 The Car and the Steering Wheel

Think of a car. As a driver you use only the steering wheel, and you do not know anything about the engine — how it functions, the physics or mechanics behind it — and you do not need to know. Abstraction is the human way of managing the complexity of the world: for every complex thing, somebody has already worked on it and reduced the complexity, then handed you an interface through which you can use it.

Map the analogy: driver = client code; steering wheel = public interface; engine = private implementation. The analogy breaks if you must rebuild the engine to turn left; a good interface lets you change the engine without changing how you steer.

Visual intuition: a car dashboard is a row of controls (wheel, pedals, gear). Axes of the picture are "what the driver touches" versus "what is under the hood." The landmark is the steering wheel: one control, huge hidden machinery. Takeaway: complexity is managed by interfaces, not by forcing every user to be a mechanic.

2.7.3 APIs and Public Interfaces

The same idea powers application programming interfaces (APIs). Big companies provide APIs — for Google authentication and many other things — and we use those interfaces without going inside them. Objects work the same way: somebody builds an object and provides its public interface, and everyone else just uses it. If you want a new kind of object, you create it by extending that particular class and writing your own code — you never need to understand and change somebody else's code.

A restaurant menu is the same pattern: you order dishes by name; you do not walk into the kitchen. The menu is the API. The kitchen is the implementation.

Whenever we can relate a software idea to a real example, we learn it easily, because the world is full of objects — and so, at the object level, is our software.

Reusable, replaceable black boxes, the steering-wheel interface, and public APIs are one idea: talk to the interface, leave the engine alone.

2.8 Encapsulation: Packaging into a Capsule

2.8.1 Packaging Data and Methods into a Capsule

Encapsulation means packaging. You take the data part and the methods of an object and pack them together into one capsule, hiding what should be hidden. The purpose is control: people should not be able to make changes where changes are not required, and nobody should change things by mistake. Some things should be private, nicely packed together, and access should go through the public methods. This arrangement protects the data and helps in maintenance of the product.

The contrast with C is sharp: in C, if you have the code, you have access to everything. In Java it is not like that — for some features you simply do not allow somebody to make changes. That restriction is encapsulation.

Capsule rule. State lives with the operations that are allowed to touch it. Callers use public methods. Private fields stay inside. The point is not secrecy for its own sake. The point is to stop unwanted changes and to keep maintenance possible.

Medicine in a capsule is the everyday picture: the powder is data; the shell is the class boundary; the printed dose instructions are the public methods. The analogy breaks if someone cuts the capsule open and dumps the powder — that is reaching into private fields from outside.

In C, having the code means access to everything. Encapsulation stops unwanted changes and helps maintenance. Do not treat a public field as "simpler"; it throws away the capsule.

2.8.2 The Four Pillars of Object Orientation

The four pillars of object orientation are inheritance, polymorphism, encapsulation, and abstraction. Abstraction and encapsulation are very much connected — many people say they are the same — and inheritance and polymorphism are also closely connected.

They are not the same. Abstraction chooses which details to ignore. Encapsulation enforces that choice in the code structure. Inheritance shares a base and specializes. Polymorphism lets one interface reach many implementations.

Exam note: Read about the four pillars of object orientation: inheritance, polymorphism, encapsulation, and abstraction. This vocabulary is expected. Encapsulation is the capsule that packs data with methods and restricts access.

2.9 Polymorphism: One Interface, Many Implementations

2.9.1 Poly Means Many, Morph Means Forms

Polymorphism comes from poly meaning many and morph meaning forms. It can be written as: one interface, multiple implementations. The technical terms you covered in the object-oriented programming course — overloading and overriding — are the two mechanisms behind it. Method overriding and dynamic dispatch (deciding at runtime which implementation to run) are very important concepts of object-oriented programming.

The central point of object orientation is that you can separate the interface from the implementation — they are not tightly bound. In C and similar languages, every time you needed a new behavior you wrote a new function for everything. Here, you define one interface and provide multiple implementations of it.

Working definition. Polymorphism: one interface, many implementations. Overloading picks a method by compile-time signatures. Overriding plus dynamic dispatch picks a method by the runtime type of the object.

2.9.2 The USB Connector

USB connector. Think of a USB connector: one interface. You can connect a mouse, you can connect a keyboard, you can do many things with it — all through the same connector shape. The connector is the interface; each device is an implementation. Sense-check: you do not learn a new plug shape for each device; you learn one plug and many device behaviors behind it.

Tax law gives the same pattern in software, with a stable method name and a body that changes on a schedule.

2.9.3 The Income Tax Method

Income tax method. Take computeIncomeTax as a method. Every year the tax rules change, but the interface stays one — you always call the same method. Every year the implementation changes. One interface, many implementations, changing year after year. Sense-check: payroll code should not be rewritten at every call site when the Finance Act changes; only the tax object's internals should change.

Graphics code uses the same idea: one verb for many shapes.

2.9.4 Drawing Shapes and Common Base Classes

Draw a shape. To draw a shape, the user needs to remember only one thing: draw. Whatever object is passed in at runtime — a rectangle, a circle, a triangle — that object gets drawn. The user does not need to remember draw_rectangle or draw_triangle. If the runtime object is a circle, the circle's draw runs. Sense-check: adding a hexagon should not force every caller to learn draw_hexagon.

It is like a car: whether you drive a Hyundai, a Maruti, or a Ford, the interface is the same. In the same spirit, the commonalities between objects can be captured in a common base class, and the differences can be preserved through specialization.

Pitfall: Writing drawRectangle and drawTriangle as separate client calls looks simple and then explodes when shapes multiply. Keep one draw on the interface.

The Hyundai / Maruti / Ford steering layout is the same lesson in metal: shared controls, different engines.

Polymorphism is one interface, many implementations — USB, tax rules, and draw all say the same thing. Capture shared behavior in a base class; keep differences in the subtypes.

2.10 How to Find Objects

2.10.1 How Students Think About Objects

Identifying objects is the main challenge of the course, so the question was opened to the students.

Q: How do we identify objects in a system? Students answer how objects are identified.

A: One way: think about how the different use cases are going to interact with each other. Based on the use cases in the design, we identify how the use cases communicate, and we create an object for that — starting from the actors in the UML diagram. Users or actors are objects; the physical people play roles, so we call them roles. Anything which has properties or some behavior is an object. Raise the level of abstraction: anything with state and behavior is an object.

Q: Could we treat something like tables as objects?

A: A table can be an object, with attributes, and for the methods we can define the rules for inserting the data. But always raise your thinking to a higher level of abstraction — do not write your answers with respect to programming and coding. In that sense, we need to identify real-world objects and software objects.

Q: How to identify objects — is it whatever items I need to complete my activity? What all do I need to complete my activity?

A: Yes, in a very basic sense: whatever items you need to complete your activity are the objects you would need to perform your program. Look outside your window — what objects are participating in conducting this class? Any activity in the real world is done by various objects interacting and cooperating with each other, performing their roles, and getting the job done. Even the desk, the physical objects, the conceptual objects, even ideas or concepts — everyone plays a role. Anything which is having some state and behavior is an object. That is the definition of an object. The preferred term is object: a participant with state and behavior, found first in the real world, not first as a database table.

The last exchange matters most: the working definition of an object for this course is anything that has state and behavior, and the best way to find objects is to look at the real world and see what is participating in the activity.

2.10.2 Techniques and the System Boundary

Several techniques for finding objects were listed: noun phrase analysis of the problem statement, understanding the problem-domain nouns, identifying actors from use case analysis, and looking for anything that has properties or some behavior. Each object also carries responsibilities. There is no single method — how a company finds objects varies — but the techniques give you a starting point.

Noun-phrase lists are a start, not a machine. Domain experts still have to say which nouns are noteworthy.

The system is a closed domain, so we must define the system boundary. Actors come from outside the boundary and play their roles there; inside the boundary we identify the objects that do the work.

Sketch a large rectangle. Stick figures stand outside it. Ellipses (use cases) sit on the border. Boxes inside are system objects. The landmark is the rectangle edge: that edge decides who is an actor and who is an internal object.

2.10.3 Every Object Must Play a Role

Each object must play a role in the system.

Cricket team. Consider a cricket team: the squad has 15 players, but only 11 are chosen to play. The other four exist, but they are not playing any role in that game, so they are not part of the team. The same selection happens with objects: if something exists but plays no role in our system, we do not use it. That is abstraction in action. Sense-check: a stadium floodlight exists in the real world, but if our system never uses lighting, it is not an object in this model.

There should also be multiple instances of each object — one object that exists only once is a sign you should recheck the analysis. (A true singleton in design can still be valid later; in analysis, a unique "God" object is often a smell.)

2.10.4 Raise the Level of Abstraction

Students were warned not to think about objects only in terms of programming and coding. The design questions happen at a higher level of abstraction: identify the real-world objects first, then the software objects that model them. Design — what objects exist, how they coordinate and communicate to perform tasks — comes before implementation, and coding knowledge alone does not answer the analysis questions.

Find objects from roles, use cases, nouns, and state-plus-behavior. Draw a system boundary. Keep only objects that play a role, like the 11 who actually bat and bowl.

2.11 Symbol, Intention, and Extension

2.11.1 The Triplet: Symbol, Intention, Extension

A useful method for creating objects is the triplet symbol, intention, extension.

  • Symbol — the representation of the thing: a symbol or a concept.
  • Intention — the purpose the thing serves.
  • Extension — the number of objects, the instances: \(O_1\), \(O_2\), \(O_3\), and so on.

When it was described: there is some representation using a symbol or a concept, having some purpose, and multiple extensions. The purpose we call intention, and the extensions as \(O_1\), \(O_2\), \(O_3\) — the number of objects you would be creating. In set notation, the extension of a concept is the set of all object instances:

\[ E = \{O_1, O_2, O_3, \ldots\} \]

Here \(E\) is the extension (the set of instances). Each \(O_i\) is one object instance of the concept. The concept itself can be written as the triple \((\text{symbol}, \text{intention}, E)\).

Notation: many philosophy and knowledge-representation texts write intension (with an s) for the meaning or purpose of a concept, and extension for the set of things that fall under it. This lecture says intention for that purpose. Keep the lecture word on the exam. Treat intension as the same slot: why the concept exists.

For students, for bicycles, for cars: each has a physical representation, plays some role, and exists in a number of instances. That is the reason we define things this way.

Check the set: if you name three cars in a parking lot, \(E\) has three members. If \(E\) is empty, you have a concept with no instances yet. If \(E\) has one member only, re-read the cricket-team warning from the previous section.

2.11.2 The Specialization Question

A student's question about class hierarchies brought out the same triplet again.

Q: When we look at the activities and create the objects, these objects are actually the specialization, right? From the class hierarchy point of view, they specialize the object. But at implementation we have to look at the generalization — the basic properties in that class. For small programs we can think that way, but for larger complex programs we do not know what should be the base. Student asks about specialization and the base class. Is there any rule for that?

A: You have to wait for that — it will come in the design. First you need to understand how to go about it. Wait for design. We are working at a very high, abstract level of representation, a high level of abstraction first. In the real world, a car is there as an object: the car as a concept is represented by a symbol — a bumper and four wheels; the intention of a car is to travel from one location to another; and there are many different cars in the city, which are the extensions. That is the good set of objects we need to look at when we go for programming. The preferred term for the later hierarchy step is generalization: picking the base class is a design decision, not the first analysis move.

The lesson: the question of which class should be the base (generalization) belongs to the design phase. During analysis we work at the abstract level and simply collect the objects of the real world.

2.11.3 The Car Example

Car as symbol, intention, extension. The symbol of the car is its representation — a bumper and four wheels. The intention of the car is its purpose in the world: to travel from one location to another. The extensions are the number of different cars in the city, the set \(E\) of instances. When we go for programming, this set of objects is exactly what we look at. Sense-check: a drawing of a bumper and four wheels still means "car" even when the paint job differs; travel is still the purpose; the city's many cars are the extension.

Name the symbol, state the intention, collect the extension set \(E = \{O_1, O_2, O_3, \ldots\}\). Do not hunt for the base class until design.

2.12 Business Processes, Roles, and Collaboration

2.12.1 Business Process Analysis

Business process analysis is an important term for use case analysis: before doing use case analysis, you must do business process analysis. Requirements are broken down into business processes — a high-level breakdown of the functionalities you wish to have in the system. A system contains a large number of processes, but the ones people are interested in are those with business value.

University processes. The business processes include: taking admission, registering people into different courses, conducting the courses, giving grades out of the courses, and, after the semester evaluation, moving students to the next semester. The whole business activity runs from raw material to product, and each process adds value to the raw material. Sense-check: "admission" is a process with business value; "wipe a whiteboard" might happen, but it is not why the institution exists.

A food-service business shows the same pattern with a shorter chain from ingredients to a plated meal.

Restaurant processes. Waiters are there, raw material comes in, orders are taken, the chef builds the dish, and finally it is delivered to the table. A library has its own set of business activities. Sense-check: the restaurant exists to take orders and serve food at a profit (or other stated objective), not to maximize the number of spoons in a drawer.

The first step is to consider what the business must do at an overall level — a restaurant or a campus exists to meet its own business objective, such as making a profit.

2.12.2 Use Cases as Stories

All the business processes are then broken down into a number of use cases. When you do use case analysis, you write very simple English statements — you write use cases in the form of stories. As humans, we like to remember stories; people grasp requirements happily when they are told in an interesting manner. A use case is the business process told as a story. Whatever requirements the client gives must be rewritten into a simple story format.

2.12.3 Actors Are Roles

Within the stories, we identify the roles of the people involved in the business process. Actors are nothing but the roles of people: a head of the department, a faculty member, a student — these are all persons, but in the system we care about the role, not the individual. A role is one kind of generalization, not specific to any person; generalization and specialization emerge naturally as you do this work. The library system has roles such as customer, library assistant, programmer, and navigator; some physical sensors are also actors; in a carpool system the driver is a stakeholder role.

This is called domain analysis, and it is why we must value our users and the domain experts. As software engineers we need soft skills, and we cannot be experts in every domain — medical, mechanical, pharmacy — even though software exists everywhere. Do not try to become an expert in everything; get inputs from the people who are experts, value them, and they will tell you the real requirements. Interact with the different roles, collect the requirements, and do the complete analysis of how things are happening.

The same ideas apply to any system you can relate to — restaurant, campus, library system, carpooling system, or the Ola and Uber systems you use in the cities.

2.12.4 Collaboration and Responsibility Assignment

Now we connect the two things: business processes on one side, people on the other. Who does what? That connection is called collaboration. Once the roles are identified, we determine how each role fulfills the process and who executes which activities. Each object must have a responsibility. A person may have different roles at different times — somebody is the head of a department, somebody is a Dean, and each position comes with different roles to play.

Adding responsibilities to the software objects is called object-oriented design. The software objects are not exactly the same as the real-world objects we analyzed, but we take inspiration from the real world — like the carpooling system we can visualize in the real world — and then build from it. Responsibility assignment is a major job in object orientation, and it is the core of what we will do in design, working towards class diagrams.

Assignment: take a carpooling problem for a big society with 500 flats, where people travel to different locations and can carpool; identify the objects for that system.

Exam note: Read about business process analysis — how to break the whole system into business processes. It comes before use case analysis. Then write stories, name roles, and assign responsibility.

2.13 Prototyping: Confirming Requirements Early

2.13.1 A Sample System

Reality cannot be captured in text alone, and people are happier with diagrams or some kind of simulation. So in requirement analysis we create various kinds of prototypes. A prototype is a sample system: it has most of the qualities of the final product but probably not the entire set. It is a small, simulation-like thing that exists only to show the look and feel of the system. It is a throwaway prototype — the point is not to build on top of it, but to throw it away after it has done its job.

Why wait until the last sprint to learn that users hate the screen? A cheap fake of the look and feel pulls the real requirements forward in time.

2.13.2 Rapid Prototyping

The experience behind prototyping: people only start telling the real requirements once you show them the software — most requirements came when the product was given to the user. Prototypes were built with PowerPoint, with webpages, or with Visual Basic Windows code just so that people would start talking about it. That is why prototyping, and especially rapid prototyping, became very popular: you show what you understood, get confirmation, and collect more requirements. The prototype has no functionality — no computations, no algorithms — but it does show the flow of the system.

Scope: A throwaway prototype is not the first increment of the product. Do not ship it. Do not grow production algorithms inside the click-dummy unless you have explicitly chosen an evolutionary prototype, which this session did not.

2.13.3 Prototype or Proof of Concept?

The distinction between a prototype and a proof of concept came up directly.

Q: Is a prototype more of a proof of concept — the POC we talk about when implementation comes? A prototype could be a proof of concept.

A: A prototype can work as a proof of concept, but it is not a working product. It will not have the functionality; the computations and algorithms won't be there. It is only GUI buttons and all that would be there, through which the user or the end customer can say: these are the functionalities I want, or this is the look I want. Then we can work on that. The working product comes at a later stage; prototyping is the first step of analysis. The preferred term is prototype: a look-and-feel sample, which may serve as a proof of concept, but is not the working product.

Show a throwaway look-and-feel prototype early. Rapid tools (PowerPoint, webpages, Visual Basic) exist to start the conversation, not to become the product.

2.14 Use Case Analysis: Object-Oriented or Not?

2.14.1 The Question

Students were asked a direct question: is use case analysis an object-oriented technique or a non-object-oriented technique? Only two options were on the table.

The trap is popularity. Use cases show up in OO projects, in UML books, and in tools. That still does not make the technique itself object-oriented.

2.14.2 The Answer

Q: Is use case analysis an object-oriented technique or a non-object-oriented technique? Which of the two is correct?

A: There is no object orientation with respect to use cases. It is a de facto technique for requirement analysis. Object orientation comes into the picture when we start identifying objects and doing the abstraction, encapsulation, inheritance, and polymorphism. If these things are not there, there is no object orientation. The four principles applied to objects make a method object-oriented. Use cases alone do not.

Standard analysis texts say the same: use cases are an important requirements artifact, but they are not object-oriented. They emphasize an activity view.

A technique does not become object-oriented just because it is popular or because it is used in an object-oriented project. Object orientation starts only when objects are identified and the four principles are applied to them.

2.15 Activity Diagrams, Message Passing, and the Dice Game

2.15.1 Activity Diagrams Replace Data Flow Diagrams

In the business process work, the different activities of each business process are broken down into activity diagrams — the replacement for the data flow diagrams of old software engineering. They are also called process flow diagrams, and they are very popular. You break a business process into various activities and record which people participate in which activity in the organization.

A UML activity diagram shows sequential and parallel activities in a process. It is useful for business processes, workflows, data flows, and even complex algorithms. Notation includes actions, partitions (who does the step), forks and joins (parallel work), and object nodes. Once an action finishes, the next transition fires. The diagram can show both control flow and data flow.

Visual intuition: left-to-right or top-to-bottom boxes named "Take order," "Cook," "Serve." Swim lanes name Waiter and Chef. A fork splits "Cook" and "Prepare bill." A join waits for both. Takeaway: this is the process view that DFDs used to hold, now in UML.

2.15.2 From Objects to Classes

Once you identify the objects, you define their data attributes and their methods. The data attributes are identified from the domain. The methods are identified by message passing: in the real world, a lot of message passing happens when responsibilities are assigned and we decide who does what. From there we design the class diagrams, the use case diagrams, and various other UML diagrams throughout the system.

In design, a sequence diagram shows those messages. Software objects take inspiration from the domain, but they are not a copy of the real world. A real player rolls dice; a DiceGame object may send roll to Die objects instead.

2.15.3 The Dice Game Assignment

To see the big picture, take a very small example.

Dice game. A player rolls two dice, and if the total is 7, they win; otherwise they lose. Write a small object-oriented program for this problem statement — you may create a GUI or do whatever you want. It will be shown in the next session.

Worked trace with real faces: Die A shows 3, Die B shows 4. Sum: \(3 + 4 = 7\). Outcome: win. Another roll: 6 and 2 sum to 8, which is not 7, so lose. Sense-check: two six-sided dice can total 7 in several ways (1+6, 2+5, 3+4, and the swaps). The rule only cares about the total, not which die showed which face.

A brief use case: Play a Dice Game — Player requests to roll the dice. System presents results: if the dice face values total seven, player wins; otherwise, player loses. Domain concepts to look for: Player, Die, DiceGame. Design classes later need operations such as play, roll, and getFaceValue.

Exam note: Prepare the dice game object-oriented program (roll two dice, total 7 wins) for the next-session demonstration. Activity diagrams replace DFDs. Methods come from message passing.
