2.1 Why Systems Slow Down as Data Grows

Hook: A prototype that answers in a blink on a small sample can stall for hours on the full data. The code did not change. The data did. This section builds one working habit: before scaling anything, write down which quantities grow and how fast they grow.

A spreadsheet shows the pattern in miniature. With a few thousand rows everything feels instant. As the row count climbs toward 5 lakh rows (500,000 rows), the same file starts to lag. At about 1 million records the tool hits a hard wall: no more records can be added. The spreadsheet was never built for huge data, so a team that outgrows it must move to other techniques.

The same question comes up in model training. Take a predictive model such as a neural network for prediction or a random forest, or take the training of a transformer model. If the training records double from 1,000,000 to 2 million, what happens to training time? A practitioner should be able to estimate the answer before running anything. The estimate matters because compute becomes a bottleneck, and a compute bottleneck maps straight to cost. With a budget of 45 lakhs to 50 lakhs, a team must know where the money goes.

Training cost is not just about tokens. Storing intermediate results also costs memory and time, and one large item is the Adam optimizer state. Later sessions take up the optimizer state in detail. The full arc of the course adds parallelization, a deep look at transformer models, and different kinds of compute such as CPU, TPU, and GPU. Early sessions stay with fundamentals. The pace picks up after about the seventh or eighth session, when machine learning algorithms meet parallelization, and the material gets tougher around the tenth session. The keywords and what can be done with them carry over into practical work even when the later math gets heavy.

Intuition: Think of the spreadsheet as a single shopkeeper with a paper ledger. A short queue moves fast because each entry is one quick line. A festival crowd breaks the system because the ledger, the desk, and the shopkeeper's arms all have fixed size. Data systems behave the same way: every tool has a capacity, and past that capacity each new row costs more than the last. The analogy breaks at one point: the shopkeeper gets tired, while a computer slows for structural reasons — fixed memory, fixed bandwidth, and algorithms whose step count grows faster than the input.

2.1.1 Mathematical Formulation

There is no formula in this section. The working habit is the takeaway: before scaling data, write down which quantities grow and how fast they grow. The quantities to list are the input size (call it \(N\), the number of records), the memory need (how many bytes each record and each intermediate result holds), and the running time (how the step count changes when \(N\) doubles). Later sections give each quantity its own notation: \(O(N)\) style growth for time in section 2.2, \(O(N)\) style growth for memory in section 2.5, and arrival-rate arithmetic for serving systems in section 2.9. For now the discipline is qualitative: name the growing quantities, guess the shape of each curve (flat, steady climb, or steep climb), and check the guess with a small doubling test before paying for a large run.

The scaling habit, stated as a checklist: (1) name the input size \(N\); (2) name every quantity that grows with \(N\) — time, memory, and cost; (3) guess each growth shape before running; (4) test the guess by doubling a small input and measuring. A guess that survives a doubling test is worth trusting at ten times the size. A guess never tested is how a 45-lakh budget disappears.

2.1.2 Worked Examples

Example 1 — the spreadsheet wall. Start with 3,000 rows: every edit feels instant. Grow to 5 lakh rows (500,000 rows): scrolling lags and each recompute takes seconds. Push past about 1 million records: the tool refuses new records entirely. Answer: capacity, not speed, is the first wall — the fix is a bigger tool, not a faster machine. Sense-check: the same three stages (instant, lagging, refused) show up in every data tool, only the row counts change.

Example 2 — doubling the training data. Training records double from 1,000,000 to 2 million. Training time does not stay flat. If the algorithm scans each record once per pass, time roughly doubles. If the algorithm compares records pairwise, time roughly quadruples. Answer: the exact factor depends on the algorithm, which is why the sections below build the tools to estimate it. Sense-check: no algorithm finishes sooner on more data — any estimate below a factor of 1 is wrong on its face.

Scope: This habit applies whenever data size is the thing being scaled — larger tables, longer training sets, heavier request streams. Assumption: the tool and the algorithm stay fixed while the data grows. When the tool itself changes (a new engine, a new algorithm), re-measure from scratch instead of extending the old curve.

Pitfalls: (1) Trusting prototype timing — a 3,000-row demo says nothing about 3 million rows. (2) Blaming the machine — buying a faster box does not move a capacity wall. (3) Forgetting intermediates — raw data fits while optimizer state and saved activations overflow memory. Measure the full footprint, not just the input file.

Recap: Small data forgives every design choice; large data punishes unmeasured ones. Name the growing quantities now, and the time-growth tools of section 2.2 plus the memory tools of section 2.5 will turn the habit into arithmetic. Bridge: Section 2.2 starts with time — how to describe running time without depending on any particular laptop or server.

Real-world: a team that prototypes on a small extract in a spreadsheet and then points the same workflow at millions of rows learns this lesson fast — the prototype looks instant, and the full run stalls. Production teams therefore prototype at small scale but budget at large scale, pricing compute against a 45-to-50-lakh envelope and reserving headroom for optimizer state and intermediate storage before the first full training run.

2.2 Time Complexity and Big-O Thinking

Hook: The same program runs in seconds on a server and minutes on a laptop. Which timing is the truth about the algorithm? Neither — both timings describe the hardware. The question this section answers is how to describe the algorithm itself, in a way that stays fair as data grows.

Time complexity is the running time of an algorithm measured in a machine-neutral way. Wall-clock benchmarking on one laptop is the wrong tool. The same program runs faster on a server than on a laptop, so a stopwatch number says more about the hardware than about the algorithm. What a practitioner needs is a measure that stays fair while the data size grows.

That need shows up in every build. Teams code an algorithm, test it on a small set, and find it very fast. Then concurrent users increase, or the data set grows, and the same system turns useless. The fix is an asymptotic technique, and the most popular one is Big-O notation. Big-O describes the worst-case time: how the work grows as the input grows, in the hardest case.

Intuition: Think of Big-O as a shoe-size chart for algorithms. A stopwatch tells you how fast one runner sprinted today; the chart tells you how the shoe size grows with foot length for every runner, on every track. Concretely: \(O(1)\) means the work stays flat no matter how much data arrives (one lookup, one check); \(O(N)\) means the work grows step for step with the data (one scan); \(O(N^2)\) means the work grows like the area of a square (nested scans). The analogy breaks here: shoe sizes stop at fixed numbers, while growth curves keep separating — at a million items the gap between \(O(N)\) and \(O(N^2)\) is a factor of a million.

Three cases frame every estimate. The worst case is the slowest possible input, and Big-O reports it. The best case is the fastest possible input, called the lower bound or Omega. The average case sits in the middle. Searching gives the standard picture: finding the target in the first slot is the best case and takes order 1, written \(O(1)\); finding it in the middle is typical; finding it in the last slot, or missing it entirely, is the worst case and takes order \(N\), written \(O(N)\). The words say: with \(N\) items and a target in the last position, the search inspects all \(N\) items.

The plain-language quote behind the math is "if it is in the first, then it becomes order of 1" and "the worst case scenario is N, the last number, so it becomes order of N". The reconstructed math is \(T(N) = O(1)\) for the best case and \(T(N) = O(N)\) for the worst case, where \(T(N)\) is the running time on \(N\) items and \(N\) is the input size.

2.2.1 Mathematical Formulation

Formalize: Big-O notation keeps the shape of growth and drops hardware constants. A machine that executes \(10^9\) operations per second is a constant factor — it changes every timing by the same multiple, so it never changes which curve wins. Dropping constants, the standard growth ladder reads:

\[ \begin{aligned} O(1) \quad &\text{(flat: one step whatever the input)} \\ O(\log N) \quad &\text{(halving: each step discards half the work)} \\ O(N) \quad &\text{(scan: one step per item)} \\ O(N \log N) \quad &\text{(split and merge: } N \text{ items times } \log N \text{ levels)} \\ O(N^2) \quad &\text{(nested scan: } N \text{ passes of } N \text{ steps)} \\ O(N^3) \quad &\text{(triple nesting: } N \text{ layers of } N^2 \text{ work)} \end{aligned} \]

Each line names one curve; \(N\) is the input size throughout. The ladder is machine-neutral: a faster machine shifts every rung by the same multiple, and the comparison table in the sorting section stays valid across machines.

Big-O is the worst case by convention, Omega (written \(\Omega\)) is the best case, and the average case sits between them. For search: best case \(\Omega(1)\) (target in the first slot, one comparison), worst case \(O(N)\) (target last or absent, \(N\) comparisons). Average case for a uniformly placed target is about \(N/2\) comparisons — still order \(N\), because the constant \(1/2\) is dropped.

2.2.2 Worked Examples

Example 1 — the proof-of-concept trap. A proof of concept on 1,000 records feels fast. The same code on production data with many more records and many more concurrent users turns slow. Suppose the inner loop is \(O(N^2)\): at \(N = 1{,}000\) it performs about \(10^6\) steps (a blink), while at \(N = 100{,}000\) it performs about \(10^{10}\) steps (hours). Answer: the lesson is to estimate the curve before deploying, not after. Sense-check: if small-input timing is instant but the loop nesting is quadratic, production will stall — the curve, not the prototype, is the evidence.

Example 2 — reading nesting depth. Two nested loops over the input give order \(N\) squared, written \(O(N^2)\): the outer loop runs \(N\) times and each pass runs the inner loop \(N\) times, so \(N \times N = N^2\) steps. Three nested loops give order \(N\) cubed, written \(O(N^3)\): \(N \times N \times N\). Answer: read the nesting depth and map it to \(O(N)\), \(O(N^2)\), or \(O(N^3)\). Sense-check with \(N = 100\): single loop about 100 steps, double loop about 10,000, triple loop about 1,000,000 — each nesting level multiplies the work by \(N\).

Scope: Big-O compares growth shapes for large \(N\). Assumption: \(N\) is large enough that the leading term dominates constants. For tiny inputs a heavier-curve algorithm can still win (setup costs dominate), so always state the \(N\) range alongside the order.

Pitfalls: (1) Averaging away the worst case — production traffic sends the hardest inputs, so plan for Big-O, not the average. (2) Confusing best case with typical case — \(O(1)\) for "found in the first slot" says nothing about a full scan. (3) Rewriting correct math to chase a readability score — leave formulas and derivations untouched and fix only genuinely unclear prose.

Recap: Stopwatch timings describe hardware; Big-O describes the algorithm. Exam note: expect questions that ask for the order of a short code fragment with nested loops — read the nesting depth and map it to \(O(N)\), \(O(N^2)\), or \(O(N^3)\). Bridge: Section 2.3 puts the ladder to work on the first concrete pair: linear search versus binary search.

Real-world: a proof of concept on 1,000 records runs in a blink, gets approved, moves to production, and then slows to a crawl. The algorithm did not change. The input size did, and nobody estimated the growth curve. Production teams now gate every launch on a written growth estimate: state the order, plug in the production \(N\), and confirm the hardware budget before approving the rollout.

2.3 Searching: Linear Search and Binary Search

Hook: Finding one name in an unsorted pile of a million slips takes a million checks in the worst case. Finding it in a sorted, indexed register takes about twenty. Same data, same target — what changed? The search strategy, and the growth curve with it.

Linear search walks through a list one element at a time and checks each one against the target. It starts at the first element and continues until it finds the target value or runs out of items. With \(N\) numbers and a specific target, the worst case is order \(N\), written \(O(N)\), because the target may sit in the last slot.

The concrete numbers make the three cases vivid. Take a list containing values such as 32, 48, 64, 96, and 115. Searching for 32 finds it in the first record, so the cost is order 1. That is the lower bound, Omega. A value sitting near the middle gives the average case. Searching for 150, which is absent, or for a value in the last slot, forces a full scan and gives the worst case, Big-O. Searching for 64 lands somewhere in between and plays the role of the middle value, while 115 near the end plays the near-worst case.

Intuition: Linear search is checking every locker in a corridor in order; binary search is the number-guessing game where every answer of "higher" or "lower" throws away half the remaining range. The locker walk costs one step per locker. The guessing game costs one question per halving, so a million lockers need only about 20 questions (since \(2^{20} \approx 1{,}000{,}000\)). The analogy breaks at one requirement: the guessing game only works when the numbers are in order — on an unsorted pile, halving can silently throw away the target.

Binary search is the faster option when the list is sorted, and it works on anything orderable: numbers, names, or any ranked key. The method first sorts the data into ascending or descending order and indexes it. Then it compares the target with the middle element. When the target is smaller, the search continues in the left half; otherwise it continues in the right half. Each step throws away half of the remaining range, so the range keeps splitting into halves. The plain-language quote is "log of N is always smaller than N, so instead of doing a linear search, if I do a binary search, I can do it much faster". The reconstructed math is \(T(N) = O(\log N)\), where \(T(N)\) is the running time and \(N\) is the number of items. Each halving multiplies the remaining work by one half, and halving \(N\) items down to one takes about \(\log N\) steps.

2.3.1 Mathematical Formulation

Formalize: Linear search costs \(T(N) = O(N)\) in the worst case, where \(N\) is the number of elements, because every element may need one comparison. Binary search costs:

\[ T(N) = O(\log N) \]

where the logarithm (base 2) counts the halvings: after \(k\) halvings \(N / 2^k \approx 1\), so \(k \approx \log_2 N\). Since \(\log N\) stays far below \(N\) for large \(N\), sorting once and then binary-searching beats repeated linear scans whenever many lookups are planned. The sorting itself costs \(O(N \log N)\) (section 2.4), so the trade pays off when the number of lookups is large: total cost is one sort plus many cheap \(O(\log N)\) lookups instead of many expensive \(O(N)\) scans.

2.3.2 Worked Examples

Example 1 — best case. In a list holding 32, 48, 64, 96, and 115, searching for 32 hits the first slot. Comparisons used: 1. Answer: cost is order 1 — the best case (\(\Omega(1)\)). Sense-check: nothing can beat one comparison, so this is the floor.

Example 2 — middle case. Searching for 64 lands mid-list: comparisons against 32, 48, then 64 — three steps out of five. Answer: this is the average-type case, costing a fraction of \(N\) steps (about \(N/2\) for a uniformly placed target). Sense-check: halving the list roughly halves the steps, which matches the \(N/2\) average.

Example 3 — worst case. Searching for 150, which is not present, scans everything: five comparisons, no hit. A target in the last slot, such as 115 at the end, behaves the same way. Answer: cost is order \(N\) — the worst case. Sense-check: an absent target forces proof of absence, which needs every slot checked.

Example 4 — binary search trace. With the same values sorted as [32, 48, 64, 96, 115], search for 96. Step 1: middle element is 64; 96 is larger, so discard the left half [32, 48]. Step 2: remaining [64, 96, 115], middle is 96 — hit in 2 comparisons instead of 4. For \(N = 1{,}048{,}576 \approx 2^{20}\), the same halving needs at most 20 steps versus a million. Answer: the number of steps grows like \(\log N\) instead of \(N\). Sense-check: each step halves the range, and 20 halvings shrink a million to one.

Scope: Binary search applies only to sorted, orderable, randomly accessible data (arrays, indexed lists). Assumption: the sort order is correct and comparisons are cheap. On unsorted or linked data, the halving logic fails — either sort first or stay with linear search.

Pitfalls: (1) Binary-searching unsorted data — the most common bug; the answer looks plausible but is wrong. (2) Forgetting the sort cost — one lookup never justifies an \(O(N \log N)\) sort; the payoff needs many lookups. (3) Off-by-one boundaries in the halving loop — test on 1-element and 2-element lists, where boundary bugs always surface.

Recap: Linear search costs \(O(N)\) and works anywhere; binary search costs \(O(\log N)\) but demands sorted data. Bridge: Section 2.4 prices the sort itself — what it costs to get data into the order that binary search needs.

Real-world: database indexes, dictionary lookups, and feature-store key searches all rest on this split — write paths pay the sort cost once, and read paths collect \(O(\log N)\) lookups millions of times a day.

2.4 Sorting: Merge Sort and Bubble Sort

Hook: Sorting a million items can take 0.02 seconds or 17 minutes — same input, same machine, different algorithm. The gap is so wide that no hardware upgrade closes it. This section shows why the divide-and-conquer shape wins and the neighbor-swap shape loses.

Merge sort uses the divide-and-conquer strategy and runs in \(O(N \log N)\) time. It splits a list into two halves again and again until each sublist holds a single element, then merges the small sublists back while arranging their elements in sorted order. When data sizes run large, splitting first and merging later beats stepping through neighbors.

Bubble sort works the other way. It arranges elements by comparing adjacent elements again and again. When two neighbors sit in the wrong order for the chosen ascending or descending arrangement, it swaps them. After each complete pass, the largest remaining element lands in its correct position. The process repeats, pass after pass, until a full pass needs no swaps. The plain-language quote is "the process will continue until there are no swaps required". The reconstructed cost is \(T(N) = O(N^2)\), where \(T(N)\) is the running time and \(N\) is the number of items, because each of roughly \(N\) passes performs roughly \(N\) adjacent comparisons.

A salary example shows when each tool fits. Salaries from zero up to very large values across an entire population form a huge range. Repeatedly splitting that range into halves until each piece holds one element is the merge-sort shape. Stepping neighbor by neighbor across the whole population is the bubble-sort shape, and the cost explodes.

Intuition: Merge sort is organizing a marathon by splitting runners into small heats, ranking each heat, then merging ranked heats — each merge is one straight walk through both lists. Bubble sort is one long line where each person swaps with the neighbor ahead until the tallest drifts to the back, repeated for every position. The heat method touches each runner about \(\log N\) times; the line method touches each pair about once, which is \(N^2\) touches. The analogy breaks here: runners get tired, while merge cost stays steady because merging two sorted halves is always one linear pass.

2.4.1 Mathematical Formulation

Formalize: Merge sort costs \(T(N) = O(N \log N)\), where \(N\) is the input size: about \(\log N\) levels of splitting, each level doing about \(N\) merge work. Bubble sort adjacent-swap cost is \(T(N) = O(N^2)\): about \(N\) passes times about \(N\) comparisons per pass. The recurrence behind merge sort is:

\[ T(N) = 2T(N/2) + cN \]

where \(2T(N/2)\) is the cost of the two halves, \(cN\) is the linear merge step, and \(c\) is a constant. Unrolling level by level confirms the closed form:

\[ \begin{aligned} \text{Level 0: } & 1 \text{ problem of size } N, \text{ merge work } cN \\ \text{Level 1: } & 2 \text{ problems of size } N/2, \text{ merge work } 2 \cdot cN/2 = cN \\ \text{Level } k\text{: } & 2^k \text{ problems of size } N/2^k, \text{ merge work } 2^k \cdot cN/2^k = cN \\ \text{Levels total: } & \log_2 N, \text{ so } T(N) = cN \log_2 N = O(N \log N) \end{aligned} \]

Every level contributes the same \(cN\) merge work, and there are \(\log_2 N\) levels because halving \(N\) items down to singletons takes \(\log_2 N\) splits.

Comparison — when to pick which: merge sort wins on large unsorted data because \(N \log N\) grows far slower than \(N^2\); it pays extra memory for the merge buffers. Bubble sort fits only tiny or nearly sorted lists where one pass with no swaps exits early in \(O(N)\) time; on large random data its \(N^2\) adjacent swaps lose by orders of magnitude. Rule of thumb: default to the \(O(N \log N)\) divide-and-conquer sort, and reach for bubble sort only as a teaching example or a nearly sorted fast path.

2.4.2 Worked Examples

Example 1 — the doubling test. With 10 elements, a bubble sort run takes about 5 seconds. Doubling to 20 elements does not double the time to 10 seconds. Because the cost grows like \(N^2\), doubling the input multiplies the time by about four: \((20/10)^2 = 4\), so the run takes about \(5 \times 4 = 25\) seconds. At \(N = 30\) the factor is \((30/10)^2 = 9\), about 45 seconds. Answer: quadratic growth punishes every doubling — estimate with the square of the size ratio. Sense-check: any doubling that less than doubles the time would contradict the \(N^2\) shape, so a factor near 4 is the expected result.

Example 2 — merge sort finishes in about 0.02 seconds. On 1,000,000 items with a machine doing \(10^9\) operations per second: merge sort needs about \(N \log_2 N \approx 10^6 \times 20 = 2 \times 10^7\) operations, so \(2 \times 10^7 / 10^9 = 0.02\) seconds. Bubble sort needs about \(N^2 = 10^{12}\) comparisons, so \(10^{12} / 10^9 = 1000\) seconds, about 17 minutes. Answer: 0.02 seconds versus 17 minutes — the curve decides, not the hardware. Sense-check: a factor of 50,000 between the two matches \(N / \log N \approx 50{,}000\), so the arithmetic hangs together.

Example 3 — faster hardware does not flip the ranking. With a 10-times-faster processor (moving from a 1 GHz to a 10 GHz machine), the 17-minute bubble sort drops to about 1.7 minutes, while merge sort drops from 0.02 seconds to about 0.002 seconds. Answer: merge sort stays overwhelmingly faster — faster hardware shrinks every constant, but it never changes which curve wins. Sense-check: dividing both timings by 10 keeps the 50,000-to-1 ratio untouched.

Scope: The \(O(N \log N)\) bound assumes a comparison-based sort with random access to both halves. Assumption: merging is linear and splitting is free. Nearly sorted tiny lists are the exception where bubble sort's early exit can win — everywhere else the divide-and-conquer shape dominates.

Pitfalls: (1) Reading \(N^2\) growth as linear — doubling the input never doubles quadratic time, it quadruples it. (2) Ignoring merge memory — merge sort needs extra buffer space, so on tiny embedded devices the memory trade matters. (3) Sorting once per lookup — sort once, then search many times; re-sorting before every query throws the win away.

Recap: Splitting then merging costs \(N \log N\); repeated neighbor swaps cost \(N^2\). Exam note: expect a numerical comparison of exactly this kind — given \(N\), the orders, and the operations-per-second rate, work out each running time in a table and state which algorithm wins and by how much. Bridge: Section 2.5 adds the second axis — memory — because a fast algorithm that does not fit still fails.

Real-world: production data pipelines sort once with \(O(N \log N)\) methods and then serve millions of \(O(\log N)\) lookups; interview and exam tables that price 1,000,000 items at \(10^9\) operations per second exist to make exactly this ranking automatic.

2.5 Space Complexity and Memory Limits

Hook: An algorithm can be fast enough yet still fail — it simply does not fit. Time is one wall; memory is the other. This section prices the second wall before the course spends the rest of its budget on it.

Time is one axis. Memory is the other. Space complexity asks how storage grows as the input grows. With very large data sets, memory runs short, and short memory brings memory overflows. At the end of the course a practitioner should be able to answer tradeoff questions from first principles: with limited memory, is waiting 17 minutes acceptable, or should more memory be added? When an operation takes two days, does extra memory fix it, or is the algorithm the problem? Those answers separate practical understanding from theory.

A small-data story makes the wall concrete. Scale the problem 10 times larger: with 10,000 records needing about 4 GB, a 16 GB limit on the GPU, CPU, or TPU feels roomy. Scale the problem 10 times larger and the need hits about 40 GB, which the hardware does not have. That is where parallelization, clustering, and multiple GPUs enter the picture, and the course builds toward them.

Intuition: Memory is a parking lot with painted bays. Ten thousand cars need 4 GB of bays inside a 16 GB lot — comfortable. Ten times the cars need 40 GB of bays in the same lot — cars spill onto the street (overflow) or the town builds more lots (more GPUs, sharded data). The analogy breaks at one point: cars can circle the block, while a program that overflows its memory usually crashes instead of waiting politely.

Counting memory follows the same asymptotic habit as counting time. With \(K\) scalar values, each one byte, \(100K\) bytes of input need about \(100K\) units of storage, so memory grows linearly and the order is \(O(K)\). In general, \(N\) input elements need order \(N\) space, written \(O(N)\). A recursion algorithm holds one stack frame per depth level, so recursion depth \(d\) needs order \(d\) space, written \(O(d)\) — each nested call keeps its own frame alive until it returns, so \(d\) nested calls hold \(d\) frames. When input, scalars, and recursion depth all appear together, the combined need is the sum \(O(N + K + d)\), and tiny terms drop out: five scalar variables with no recursion leave pure \(O(N)\). Large \(N\) dominates, so order \(N\) is the practical starting point.

2.5.1 Mathematical Formulation

Formalize: Memory for \(K\) scalar values costs \(M(K) = O(K)\), where \(M\) is the memory need and \(K\) counts the scalars. Memory for \(N\) inputs costs \(M(N) = O(N)\). Combined needs add:

\[ M(N, K, d) = O(N + K + d) \]

where \(d\) is the recursion depth, and small constant terms are dropped. Naive dense matrix multiplication on \(n \times n\) matrices costs \(O(n^3)\) time: each of the \(n^2\) output entries sums over \(n\) products, so \(n^2 \times n = n^3\) multiply-add steps — the triple loop of section 2.2 in hardware form, and the reason section 2.6 moves this work onto GPUs.

2.5.2 Worked Examples

Example 1 — the 16 GB ceiling. 10,000 records need 4 GB inside a 16 GB limit: usage is \(4/16 = 25\%\), comfortable. Scaling 10 times pushes the need to about 40 GB against the same 16 GB ceiling: shortfall is \(40 - 16 = 24\) GB. Answer: the box cannot hold it, so the design must change — shard the data, add GPUs, or stream in chunks. Sense-check: linear scaling means 10 times the data needs 10 times the memory, so \(4 \times 10 = 40\) GB follows directly.

Example 2 — dropping constants. With scalar values at one byte each, \(K\) values need \(O(K)\) memory. Five extra variables add a constant 5 bytes: total \(O(N + 5) = O(N)\). With recursion depth \(d = 1{,}000\), the stack holds 1,000 frames: \(O(d)\) that survives because \(d\) grows with the input. Answer: keep every term that grows with the input, drop every fixed constant. Sense-check: at \(N = 10^6\), the 5-byte constant is 0.0005% of the total — dropping it changes nothing.

Scope: Space analysis covers working memory that must be live at once — inputs, intermediates, optimizer state, and call stacks. Assumption: each element and each live frame costs a fixed number of bytes. Streaming and checkpointing break the naive sum by reusing buffers, so state the buffering policy alongside the order.

Pitfalls: (1) Pricing inputs but forgetting intermediates — Adam optimizer state and saved activations can dwarf the raw data. (2) Confusing disk with memory — data that fits on disk can still overflow RAM by 10 times. (3) Treating recursion as free — depth \(d\) is a live stack of \(d\) frames, and deep recursion overflows long before the heap fills.

Recap: Memory adds across everything live at once: \(O(N + K + d)\), with constants dropped and growing terms kept. Bridge: Section 2.6 names the data shapes that fill this memory — scalars, vectors, and matrices — and shows why their multiplication moves to GPUs.

Real-world: a 10-times data scale-up that moves memory need from 4 GB to 40 GB against a 16 GB ceiling forces a redesign — parallel workers, sharded data, and more GPUs rather than hoping the same box copes. Capacity planning sheets that list inputs, optimizer state, and activation buffers side by side exist to catch the overflow before purchase orders go out.

2.6 Scalars, Vectors, Matrices and Why GPUs Help

Hook: A graphics card with thousands of weak cores beats a server processor with dozens of strong ones on AI workloads. Why would weaker cores win? Because matrix work is thousands of identical small sums — and that shape is exactly what a GPU is built to chew through.

Matrix multiplication is where GPUs pay off. An image can sit in memory as a matrix. A data batch can sit in memory as a matrix, exactly as happens inside transformer models. Most of the heavy work then becomes matrix multiplication: convolutional networks keep multiplying kernels, and transformer models keep multiplying large matrices. GPUs suit this work because each core does only basic mathematics, multiplication and addition, but the core count runs very high.

The vocabulary question comes first: what is a scalar and what is a vector? A scalar (a single value with no direction), written \(a\), might be \(a = 56\) — meaning one plain number. A vector (several scalars grouped together, carrying direction), written \(\mathbf{v}\), might be \(\mathbf{v} = [20, 30, 40]\) — meaning an arrow with three components. When the distinction between single values and grouped values is in place, the hardware story clicks: thousands of independent multiplications map cleanly onto thousands of GPU cores, while a single-threaded walk through the same operations crawls.

Counting cores shows the gap. A server-class processor may hold 32 computing elements, each built for two threads, so one CPU runs about 64 parallel computations. A GPU runs tens of thousands of threads. The shape of matrix work, the same small operation repeated across independent entries, is what lets those threads stay busy.

Q: What is a scalar and what is a vector? A: A scalar is a single value with no direction, such as 56. A vector is multiple scalar values grouped together, such as 20, 30, 40, and the group carries direction. Magnitude plus direction makes a vector, and vectors stack into the matrices that fill transformer models and image batches.

2.6.1 Mathematical Formulation

Formalize: A scalar is one number, \(a \in \mathbb{R}\), where \(\mathbb{R}\) is the set of real numbers and \(a\) is the value. A vector of \(K\) scalars is \(\mathbf{v} \in \mathbb{R}^K\), where \(\mathbf{v}\) is the grouped value and \(K\) is its length — remember the term-on-first-use pattern: an eigenvalue (how much its eigenvector stretches), written \(\lambda\), might be \(\lambda = 2\), meaning "twice as long". A matrix of data is \(X \in \mathbb{R}^{m \times n}\), where \(m\) counts rows and \(n\) counts columns. Memory for \(K\) scalars is \(O(K)\): linear in the count. Matrix product entries follow:

\[ C_{ij} = \sum_{k=1}^{n} A_{ik} B_{kj} \]

where \(A \in \mathbb{R}^{m \times n}\) is the left matrix, \(B \in \mathbb{R}^{n \times p}\) is the right matrix, \(C \in \mathbb{R}^{m \times p}\) is the result, and each of the \(m \times p\) outputs sums over \(n\) products — the \(O(n^3)\) triple loop for square matrices, now visibly made of independent per-entry sums.

2.6.2 Industry Applications

Worked shape — one entry, fully traced. Take \(A = [[1, 2], [3, 4]]\) and \(B = [[5, 6], [7, 8]]\). Entry \(C_{11} = 1 \times 5 + 2 \times 7 = 5 + 14 = \mathbf{19}\). Entry \(C_{12} = 1 \times 6 + 2 \times 8 = 6 + 16 = \mathbf{22}\). Each entry needs only its own row and column — no entry waits on another, so all four entries can run on four cores at once. Answer: independence per entry is what makes the work GPU-shaped. Sense-check: \(C_{11} = 19\) uses row 1 of \(A\) and column 1 of \(B\) only, confirming no cross-entry dependence.

Scope: GPU wins apply to data-parallel work — the same small operation repeated across independent entries. Assumption: entries do not depend on each other and arithmetic intensity beats memory movement. Serial chains with step-to-step dependence (section 2.12) gain nothing from more cores.

Pitfalls: (1) Counting cores instead of usable parallelism — 64 CPU threads beat thousands of GPU threads on serial code. (2) Ignoring data movement — shipping matrices to the GPU can cost more than the compute saves. (3) Mixing up vectors and scalars — a vector carries direction and stacks into matrices; treating grouped values as plain numbers breaks the shape bookkeeping.

Recap: Scalars group into vectors, vectors stack into matrices, and per-entry independence is why GPUs win matrix work. Bridge: Section 2.7 shows the price of grouping work — batching raises throughput while making each item wait.

Real-world: image pixels stored as matrices, data batches stored as matrices, convolutional kernel products, and transformer attention products all reduce to repeated multiplication and addition. That repetition is the reason GPU core counts matter more than single-core speed for these workloads.

2.7 Batch Size and the Bike-versus-Bus Trade-off

Hook: Would you rather leave now on a bike or wait for a bus that holds thirty people? The bike answers at once; the bus carries more people per trip. Every batch-size decision in machine learning is this choice in disguise.

A small story carries the whole batch-size idea. To reach the office, take a bike and go: the wait is zero and the latency is low. Or take a bus that refuses to leave until 30 people board: the wait is long and the latency is high. Batching in machine learning follows the same logic. Training a convolutional network on one image at a time costs about 10 milliseconds per image. Training with a batch size of 32 processes 32 images together, computes, and then averages the gradients, and the batch step costs about 40 milliseconds. The per-image arithmetic gets cheaper because the fixed costs spread across 32 images, but the first result waits for the whole batch.

Batching ties straight to money. The choice rests on compute, on memory, and, in parallel systems, on networking, which can also turn into the bottleneck. The practitioner hunts the slowest stage: is the bottleneck the algorithm, the compute, the memory, or the network bandwidth? Answering that question is the skill being built.

Intuition: The bike is batch size 1 — one rider, zero waiting, full road cost per rider. The bus is batch size 32 — thirty-two riders share one engine and one driver, so the cost per rider drops, but the first rider waits for the last to board. Map it explicitly: riders are images, boarding time is batch assembly, the engine is the GPU kernel launch, and the ticket price is milliseconds per image. The analogy breaks at one point: bus riders all arrive together, while batched images each wait a different amount — the first image waits longest, the last barely waits at all.

2.7.1 Mathematical Formulation

There is no new formula here. The quantities are per-item time, batch time, and the arrival of the first finished result. With one image per step at 10 milliseconds, 32 sequential steps cost about 320 milliseconds of work. With a batch of 32 finishing in about 40 milliseconds, the hardware does far more useful work per second, while the first image still waits for the batch to complete. Per-image cost falls from 10 milliseconds to \(40 / 32 = 1.25\) milliseconds — an 8-times throughput win — while first-result latency rises from 10 to 40 milliseconds. Throughput and latency move in opposite directions, which is exactly the split section 2.8 formalizes.

2.7.2 Worked Examples

Example 1 — the bike (batch size 1). One image per step at 10 milliseconds each: 32 images cost \(32 \times 10 = 320\) milliseconds of device time, and each result is ready 10 milliseconds after its own step starts. Answer: latency is minimal (10 ms per result) while the hardware sits lightly used. Sense-check: no waiting, no sharing — per-image cost equals the full step cost.

Example 2 — the bus (batch of 32). A batch of 32 images completes in about 40 milliseconds with gradients averaged: per-image cost is \(40 / 32 = \mathbf{1.25}\) milliseconds, so the batch finishes more images per second, but each image waits for its batch-mates. Answer: throughput rises 8 times (\(10 / 1.25\)) while first-image latency quadruples (10 ms to 40 ms). Sense-check: fixed launch costs spread over 32 images explain the win; the wait-for-the-batch rule explains the latency price.

Scope: Batching pays when fixed per-step costs (kernel launches, gradient syncs) dominate and memory holds the full batch. Assumption: all 32 images fit in device memory with their gradients. Past the memory limit the batch spills or crashes, and the throughput win vanishes.

Pitfalls: (1) Chasing batch size past the memory wall — a crashed run has zero throughput. (2) Forgetting the latency price — interactive products feel the 40 ms wait even when training throughput soars. (3) Blaming the algorithm for a bandwidth bottleneck — when networking is the slowest stage, bigger batches only lengthen the queue.

Recap: Batching trades first-result waiting time for images-per-second: 1.25 ms per image at the cost of a 40 ms wait. Bridge: Section 2.8 gives the two sides their formal names — latency and throughput — and shows why one never implies the other.

Real-world: single-image steps keep latency minimal while batch steps raise hardware use. The 32-image batch that averages gradients is the standard form of this trade, and the bus rule of waiting for 30 riders is its everyday twin.

2.8 Throughput, Latency and Time to First Token

Hook: A system can answer 5,000 requests a second yet keep every user waiting 8 seconds. Both numbers are true at once. How? Because speed has two faces — and this section names them.

Latency is the time from start to finish for one task. Ask a chat model a question and wait for the answer: the wait before anything useful arrives is latency. The first word out has its own name, time to first token. About 100 milliseconds is the target people want for simple recall such as a keyword search. For deeper agentic systems the wait can stretch to seconds: one deployed setup answered in about 1 second from one tool and about 8 seconds from another, where the 8-second delay was a deliberate choice to cut hardware cost. Cutting latency usually means horizontal scaling, which means more machines, which means more money.

Throughput is the number of tasks completed per unit time. A recommender system fielding 5,000 requests per second must answer each request inside about 100 milliseconds, and in the stricter telling inside about 500 milliseconds end to end. The phone-in-cart story shows why recommenders matter: a shopper who adds an Android phone gets offered a cover and a screen guard. Someone buying a high-value item for 1.5 lakhs still adds a 3,000-rupee case, even when another store sells it 500 rupees cheaper. The deeper logic goes further: shoppers with the same profile bucket buy similar baskets, so a buyer of a phone may also buy a T-shirt or a perfume. Here profile means the recommender cluster, not age or gender: a female buyer of an Android phone plus a T-shirt can sit in the same bucket as a male buyer with the same pattern.

The two metrics refuse to collapse into one. Latency is finish time minus start time. A task that starts at time zero and finishes at 2 seconds has a latency of 2 seconds. A task that starts at 1 second and finishes at 3 seconds also has a latency of \(3 - 1 = 2\) seconds. Throughput for a 0.25-second task is \(1 / 0.25 = 4\) tasks per second, so 100 such tasks complete at 4 per second. And low latency never guarantees high throughput, especially in parallel systems full of bottlenecks. Batch processing proves the split: handling 32 images at once raises throughput, while the first image still waits for the batch, so its latency stays put.

Intuition: Latency is how long one pizza takes to reach your table; throughput is how many pizzas the kitchen finishes per hour. A kitchen can bake 200 pizzas an hour (high throughput) while your pizza still takes 30 minutes (high latency) because it waits behind fifty orders. Time to first token is the waiter bringing bread while the pizza bakes — the first sign of progress, not the full meal. The analogy breaks here: pizzas are independent, while chat tokens arrive in sequence — the tenth token cannot come before the ninth is computed.

2.8.1 Mathematical Formulation

Formalize: Latency is \(L = T_{\text{finish}} - T_{\text{start}}\), where \(T_{\text{finish}}\) is the finish time, \(T_{\text{start}}\) is the start time, and \(L\) is the latency. Throughput is:

\[ X = N_{\text{tasks}} / T_{\text{total}} \]

where \(N_{\text{tasks}}\) is the completed count, \(T_{\text{total}}\) is the elapsed time, and \(X\) is the throughput. Ideal parallel throughput scales with worker count:

\[ X(N) = N \cdot X(1) \]

where \(N\) is the number of processing units (threads, cores, or GPU cores) and \(X(1)\) is single-unit throughput. Real systems fall short of this ideal because of serial parts and overhead — the gap Amdahl's law prices in section 2.10.

2.8.2 Worked Examples

Example 1 — the recommender budget. A recommender takes 5,000 requests per second with about a 100-millisecond budget each. Required completions per second: 5,000. Per-request deadline: 0.1 seconds. Capacity needed: \(5{,}000 \times 0.1 = 500\) concurrent slots. Answer: missing the budget breaks the product even when each answer is correct — capacity, not correctness, is the constraint. Sense-check: 500 slots times 10 turns per second each equals exactly 5,000.

Example 2 — the chatbot trade. A chat model returns its first token after about 8 seconds in one setup and about 1 second in another. The slower setup traded latency for lower hardware cost (fewer machines, longer queues). Answer: the 8-second setup is cheaper per token but feels broken; the 1-second setup costs more hardware. Sense-check: users abandon slow chats, so the cost saving only pays when answers are not interactive.

Example 3 — rate from unit time. A task needs 0.25 seconds. Throughput is \(1 / 0.25 = \mathbf{4}\) tasks per second, so 100 tasks flow at 4 per second when run back to back, taking \(100 / 4 = 25\) seconds total. Answer: unit time inverts directly into rate. Sense-check: 4 per second times 25 seconds equals 100 tasks — the books balance.

Example 4 — latency arithmetic. A task starting at 0 and finishing at 2 has latency \(2 - 0 = \mathbf{2}\) seconds. A task starting at 1 second and finishing at 3 seconds has latency \(3 - 1 = \mathbf{2}\) seconds. Answer: identical latencies despite different clocks — only the difference matters. Sense-check: shifting both endpoints by the same amount leaves the wait unchanged.

Student correction — low latency never guarantees high throughput: It is tempting to read "fast answers" as "many answers", but a single fast lane still serves one car at a time. The batch-of-32 proof settles it: throughput rises 8 times while first-image latency quadruples. The preferred mental model keeps two dials — one for wait, one for rate — and tunes each against its own budget.

Scope: Latency budgets govern one request; throughput budgets govern the stream. Assumption: measurements use the same operating point — mixing idle latency with loaded throughput hides the queue. Always state load alongside each number.

Pitfalls: (1) Reporting idle latency as the product number — queues multiply it under load. (2) Buying throughput to fix latency — more lanes do not shorten one trip. (3) Averaging away the tail — the 99th-percentile wait is what users remember, not the mean.

Recap: Latency is \(T_{\text{finish}} - T_{\text{start}}\) per task; throughput is tasks per second; time to first token is the latency users feel first. Bridge: Section 2.9 links the two dials through the queue — Little's law turns arrival rate and latency into the number of tasks stuck inside.

Real-world: chat products such as ChatGPT report time to first token because users feel it directly. Recommender systems provision for thousands of requests per second because the request stream never pauses.

2.9 Queuing Theory and Little's Law

Hook: Exam results release at noon — and by 12:05 the portal crawls. No code changed at noon. What changed is the arrival rate, and one small law predicts exactly how the crawl follows the crowd.

Throughput and latency connect through the number of tasks sitting in the system. The link is Little's law. Its plain-language form: the average number of tasks in the system equals the arrival rate times the average time each task spends inside. The reconstructed math is \(L = \lambda W\), where \(L\) is the average number of tasks in the system, \(\lambda\) is the arrival rate (throughput measured at the output, requests arriving per unit time), and \(W\) is the latency, the average time spent in the system. The companion reading used here is \(W = L / \lambda\), where latency equals tasks in system divided by arrival rate.

Exam results day shows the dynamics. The moment results release, everyone logs in at once and \(\lambda\) jumps. The arrival rate moves on its own: the system floods for a day or two then calms down. Each request still needs computing, and the queue keeps growing, which pushes latency up. When requests arrive at \(\lambda = 10\) per second and each spends \(W = 2\) seconds inside, the average load is \(L = 10 \times 2 = 20\) concurrent requests. The request enters, gets computed, and leaves, and on average 20 such requests share the system at any moment.

Intuition: Little's law is a supermarket at steady hour: shoppers arrive at \(\lambda\) per minute and each shops for \(W\) minutes, so the store holds \(L = \lambda \times W\) shoppers on average. Ten arrivals a minute times twenty minutes of shopping means 200 trolleys inside. Map it: arrivals are requests, shopping time is latency, trolleys in store are concurrent load. The analogy breaks at bursts — the law describes averages at steady state, not the minute the doors open and a thousand shoppers rush in at once.

The next model sharpens the picture for a single server with random arrivals and random service. The M/M/1 queuing formula reads \(W = 1 / (\mu - \lambda)\), where \(W\) is the average time in the system, \(\mu\) is the service rate (requests the server can finish per unit time), and \(\lambda\) is the arrival rate. As \(\lambda\) approaches \(\mu\), the denominator shrinks toward zero and \(W\) blows up toward infinity. Latency turns enormous: booking a train tatkal ticket means sitting in a queue, waiting, while the system crawls, and at some point the system can collapse outright. Queuing theory reaches beyond computer science into computer networks, manufacturing systems, and server workloads.

2.9.1 Mathematical Formulation

Formalize: Little's law is \(L = \lambda W\), equivalently \(W = L / \lambda\), where \(L\) is the average tasks in the system, \(\lambda\) is the arrival rate, and \(W\) is the average latency. The M/M/1 waiting-time formula is:

\[ W = 1 / (\mu - \lambda) \]

where \(\mu\) is the service rate. Stability needs \(\lambda < \mu\); when arrivals meet service capacity, the denominator hits zero and the wait grows without bound. A numerical spot-check: with \(\mu = 12\) and \(\lambda = 10\), \(W = 1/(12-10) = 0.5\) seconds; raising \(\lambda\) to 11 gives \(W = 1/(12-11) = 1\) second — one extra arrival per second doubles the wait, showing how steeply the curve bends near capacity.

2.9.2 Worked Examples

Example 1 — exam results at 10 per second. Requests arrive at \(\lambda = 10\) per second. Each spends \(W = 2\) seconds in the system. Average concurrent load is \(L = 10 \times 2 = \mathbf{20}\) requests. Answer: provision at least 20 slots or the queue grows without bound. Sense-check: each second brings 10 newcomers while 10 earlier ones are still inside their 2-second stay — 20 coexisting is exactly right.

Example 2 — the tatkal blowup. A single server with service rate \(\mu = 12\) per second faces arrival rate \(\lambda\) creeping from 8 to 11. At \(\lambda = 8\): \(W = 1/(12-8) = \mathbf{0.25}\) seconds. At \(\lambda = 11\): \(W = 1/(12-11) = \mathbf{1}\) second — four times the wait from a small arrival rise. At \(\lambda \to 12\) the denominator vanishes and the ticket queue barely moves. Answer: near capacity, tiny arrival growth explodes latency. Sense-check: halving the headroom from 4 to 1 multiplies the wait by 4 — the hyperbola shape, confirmed.

Scope: Little's law holds for any steady-state system — one server or many, any arrival pattern — but only as a long-run average. Assumption: arrivals and departures balance (stable system) and averages are taken over a long window. The M/M/1 formula further assumes random (Poisson) arrivals and random (exponential) service on a single server.

Pitfalls: (1) Applying averages to bursts — the results-day flood is transient, and steady-state math underestimates its peak queue. (2) Pushing \(\lambda\) past \(\mu\) and hoping — past capacity no average exists; the queue grows until something is dropped. (3) Confusing \(L\) with queue length — \(L\) counts tasks in service plus tasks waiting, not just the waiting line.

Recap: \(L = \lambda W\) ties load to arrival rate times latency, and \(W = 1/(\mu - \lambda)\) shows the wait exploding as arrivals meet capacity. Bridge: Section 2.10 asks the parallel-scale question — when more workers split the service, how much of the wait actually shrinks?

Real-world: exam-result portals, tatkal booking queues, and live traffic spikes all follow this pattern. Arrivals surge, queues build, latency climbs, and only extra service capacity or admission control brings the wait back down.

2.10 Speedup, Efficiency and Amdahl's Law

Hook: One GPU needs 45 days to train a job. With 8 GPUs, does the job finish in \(45 / 8\) days? Almost never. Something refuses to shrink — and naming that something is worth lakhs of rupees in hardware decisions.

One GPU needs 45 days to train a job. With 8 GPUs, does the job finish in \(45 / 8\) days? Almost never. The real gain is some factor \(X\), smaller than the worker count, and Amdahl's law explains why: every job mixes a serial part that cannot be parallelized with a parallel part that can.

The oven story makes the split unforgettable. Baking 100 kilos of vegetables needs chopping plus oven time. One person chops for 80 minutes and the oven runs 20 minutes, for 100 minutes total. With 4 people chopping, chopping drops to \(80 / 4 = 20\) minutes, but the oven still needs its 20 minutes. Total time is \(20 + 20 = 40\) minutes. Speedup is \(100 / 40 = 2.5\) times, not 4 times, because the oven is the fixed serial component. The parallelizable share is \(P = 0.8\) (80 minutes of 100), and the serial share is \(1 - P = 0.2\).

Intuition: Hiring more cooks never shortens the oven timer. Chopping scales with hands; baking scales with nothing — the oven holds what it holds for as long as it takes. Map it: cooks are workers, chopping is the parallel share \(P\), the oven timer is the serial share \(1 - P\). The analogy breaks at one point: cooks can also prep the next batch while baking runs (overlap), while strict Amdahl arithmetic assumes the serial slice blocks everything — pipelining softens the law without repealing it.

Speedup compares one worker against many. Its plain-language form: serial time divided by parallel time. The reconstructed math is \(S(N) = T_{\text{serial}} / T_{\text{parallel}}(N)\), where \(S(N)\) is the speedup on \(N\) workers, \(T_{\text{serial}}\) is the one-worker time, and \(T_{\text{parallel}}(N)\) is the \(N\)-worker time. A companion example: one core takes 100 seconds; four cores would ideally take 25 seconds, but other overheads add 5 seconds, so the real time is 30 seconds and \(S = 100 / 30 \approx 3.33\) against an ideal 4. Closing that gap is the optimization task.

Efficiency measures how well the workers are used. Its plain-language form: speedup divided by worker count. The reconstructed math is \(E(N) = S(N) / N\), where \(E(N)\) is the efficiency and \(N\) is the number of workers (cores or a multi-core system). Ideal efficiency is 1. Practice falls short, and the shortfall is the improvement target. Speedup should always satisfy \(S \le N\): linear speedup at \(S = N\) means every job is independent and identical with no overhead, \(S < N\) means parallel overhead eats part of the gain, and \(S > N\) is the rare superlinear case to be examined closely.

Amdahl's law turns the oven intuition into arithmetic. Let \(P\) be the parallelizable share of the program, a fraction between 0 and 1, and \(1 - P\) the share that must run sequentially. With nothing parallelizable \(P = 0\); with 20 percent parallelizable \(P = 0.2\). The speedup on \(N\) workers is \(S(N) = 1 / ((1 - P) + P/N)\), where the denominator adds the serial share to the shrunken parallel share. When the algorithm is not built for parallelization, most of it runs sequentially and extra compute sits idle. Raising the parallel share raises the speedup, and building algorithms with a larger parallel share is the point of the course.

2.10.1 Mathematical Formulation

Formalize: Amdahl's law is:

\[ S(N) = T_{\text{serial}} / T_{\text{parallel}} = 1 / ((1 - P) + P/N) \]

where \(P\) is the parallelizable fraction and \(N\) is the worker count — the denominator adds the serial slice that never shrinks to the parallel slice divided by \(N\). The derivation from first principles: one worker takes \(T_{\text{serial}}\); on \(N\) workers the serial slice \((1-P) \cdot T_{\text{serial}}\) stays whole while the parallel slice \(P \cdot T_{\text{serial}}\) divides by \(N\), so \(T_{\text{parallel}} = (1-P)T_{\text{serial}} + P T_{\text{serial}}/N\), and the ratio simplifies to the boxed form. The ceiling comes from letting \(N\) grow without bound:

\[ S_{\max} = 1 / (1 - P) \]

where \(S_{\max}\) is the maximum possible speedup. With \(P = 0.9\), the ceiling is \(S_{\max} = 1 / 0.1 = 10\): even infinite workers cannot beat 10 times, so a 10-second serial run bottoms out at 1 second. Efficiency is \(E(N) = S(N) / N\), with the ideal at 1 and real values below it.

2.10.2 Worked Examples

Example 1 — the oven run. Serial time 100 minutes with an 80-minute parallelizable share (\(P = 0.8\)). Four workers give \(1 / (0.2 + 0.8/4) = 1 / (0.2 + 0.2) = 1 / 0.4 = \mathbf{2.5}\) times speedup. Total time is 40 minutes, not 25. Answer: the serial 20 minutes caps the win. Sense-check: even infinite choppers leave the 20-minute bake, so no result below 20 minutes is possible — 40 clears that floor.

Example 2 — the 100-second job. A 100-second job with a 20-second serial share and an 80-second parallel share. Four workers do the parallel share in \(80 / 4 = 20\) seconds, plus the 20 serial seconds, for 40 seconds total. Speedup is \(100 / 40 = \mathbf{2.5}\). The same numbers drop straight into Amdahl's formula: \(1 / (0.2 + 0.8/4) = 2.5\). Answer: wall-clock arithmetic and the formula agree. Sense-check: both routes give 2.5, confirming the formula prices exactly the serial-plus-shrunken-parallel split.

Example 3 — the ceiling. With \(P = 0.9\), speedup cannot pass 10 no matter how many workers join. A 10-second serial run reaches 1 second with 10 workers (\(1/(0.1 + 0.9/10) = 1/0.19 \approx 5.3\); the ceiling binds as \(N\) grows), and adding 100 workers still leaves it near 1 second (\(1/(0.1 + 0.009) \approx 9.2\), asymptoting to 10). Answer: past the ceiling, workers buy almost nothing. Sense-check: as \(N \to \infty\), \(P/N \to 0\) and \(S \to 1/(1-P) = 10\) from below — no finite \(N\) crosses it.

Example 4 — overhead eats the ideal. One core takes 100 seconds; four cores take 30 seconds (25 seconds of split work plus 5 seconds of overhead). Speedup is \(100 / 30 \approx \mathbf{3.33}\) against the ideal 4; efficiency is \(3.33/4 \approx 0.83\). Answer: the 5-second overhead is the next optimization target. Sense-check: \(S = 3.33 < 4 = N\) confirms overhead, and no \(S > N\) superlinear surprise needs explaining here.

Example 5 — video rendering. Video rendering takes 200 minutes on one worker with frame rendering parallelized across 8 workers, yet speedup reaches only about 2.58 times instead of 8. The run drops to about \(200 / 2.58 \approx \mathbf{77.5}\) minutes. Answer: the serial share (encoding headers, final assembly) refuses to shrink. Sense-check: implied serial share from \(2.58 = 1/((1-P) + P/8)\) gives \(P \approx 0.7\) — a large serial tail, consistent with assembly-bound rendering.

Example 6 — large-model training. Large-model training on one worker with unbounded memory versus 8 workers follows the same law. With a typical \(P = 0.9\), \(S(8) = 1/(0.1 + 0.9/8) = 1/0.2125 \approx \mathbf{4.7}\) — barely half the worker count. Answer: the sequential part (data loading, gradient sync, checkpointing) cannot be reduced, so the 8-worker gain stays far below 8 times. Sense-check: \(4.7 < 8\) with efficiency \(4.7/8 \approx 0.59\) — exactly the expensive-idle-hardware pattern the course attacks.

Q: Does speedup grow linearly with workers, and what do the cases \(S = N\), \(S < N\), and \(S > N\) mean? A: No, speedup is not linear in practice. \(S = N\) is perfect speedup with independent identical jobs and no overhead. \(S < N\) means parallel overhead is present — the normal case. \(S > N\) is superlinear speedup, which calls for a closer look at caching (working sets that suddenly fit) or changed work before celebrating.

Scope: Amdahl's law prices fixed-size problems with a fixed serial share. Assumption: \(P\) stays constant as \(N\) grows and overhead beyond the serial share is ignored (section 2.13 adds it back). Growing problem sizes with \(N\) follow a different scaling argument — state which regime the estimate belongs to.

Pitfalls: (1) Dividing wall-clock by \(N\) and calling it speedup — speedup divides serial time by the real parallel time, overhead included. (2) Quoting \(S > N\) as a win without checking caching effects. (3) Buying workers before measuring \(P\) — with \(P = 0.5\) the ceiling is 2 no matter how many GPUs are rented.

Recap: Every job splits into a serial slice that never shrinks and a parallel slice that divides by \(N\); the ceiling \(1/(1-P)\) caps all spending. Exam note: a worked Amdahl example belongs in midterm preparation — practice substituting \(P\) and \(N\) into \(S(N) = 1/((1-P)+P/N)\) until the arithmetic is automatic. Bridge: Section 2.11 adds the missing price — per-worker overhead — and solves for the worker count where adding help starts hurting.

Real-world: single-GPU training that spans 45 days motivates multi-GPU runs, but the serial share caps the win. Buying workers without raising the parallelizable share leaves expensive hardware idle.

2.11 Picking the Best Number of Workers

Hook: More workers can make a job slower. At some count the extra hands cost more in coordination than they save in splitting — and past that point extra hardware is of no use. This section finds that count before the invoice does.

More workers can make a job slower. As workers join, each one must stay fed: memory should run near 90 percent use, CPU or GPU near 90 percent use, and bandwidth near 70 to 75 percent use. Bus standards (PCI bus, NVLink from NVIDIA), RAM speeds, and caches all decide how much useful work each added worker delivers. A small example sets the pattern with \(P = 0.95\), so the serial share is \(1 - P = 0.05\) with the serial slice taking about 300 milliseconds, and the per-worker overhead constant at \(C = 2\) milliseconds. Solving the tradeoff gives the worker count where time bottoms out. Moving from 3 GPUs to 4, or from 8 to 16, is then a calculation, not a guess: 8 GPUs cost about 12.5 lakhs a month, 16 cost about 25 lakhs, and running them at 50 percent efficiency wastes about 12.5 lakhs.

The derivation reads the system the way a map reads a drive. A trip readout says 30 minutes for 5 kilometers, but speed is not constant: signals slow the car, open stretches let it hit 80 kilometers per hour, and only the arrival time shows on the screen. Calculus takes a tiny time slice and studies behavior at that point. Likewise, total time as a function of worker count is \(T(N) = (1 - P) \cdot T_{\text{serial}} + P \cdot T_{\text{serial}} / N + C \cdot N\), where \(T_{\text{serial}}\) is the one-worker time, \(P\) is the parallelizable share, \(N\) is the worker count, and \(C\) is the overhead per added worker (communication plus synchronization). Differentiating and setting the first derivative to zero, \(dT/dN = 0\), gives the optimum \(N^* = \sqrt{P \cdot T_{\text{serial}} / C}\), where \(N^*\) is the best worker count. Plotted from 1 worker to 40, total time falls, flattens at the optimum, and then rises: beyond that point extra hardware is of no use.

The polynomial aside explains why closed forms stop helping. A second-order equation \(aX^2 + bX + c = 0\) gives two roots \(X_1\) and \(X_2\) deterministically. A third-order equation \(aX^3 + bX^2 + cX + d = 0\) gives three roots, and fourth-order equations still admit formulas, with classical elimination methods among the standard tools. Beyond fourth order the problem turns non-deterministic in closed form — no general formula using radicals exists (the Abel-Ruffini result) — so approximation takes over with iterative root-finding methods such as Newton-Raphson iteration. For stochastic gradient descent, the second-order picture still pays off: the sign of the curvature tells whether the step moves forward or backward.

Intuition: Choosing workers is staffing a kitchen. Each cook splits the chopping (parallel gain \(P \cdot T_{\text{serial}}/N\)) but also needs briefing, bench space, and cleanup (overhead \(C \cdot N\)). The first cooks pay for themselves; the twentieth costs more briefing than chopping saved. The valley bottom — where one more cook exactly stops paying — is \(N^*\). The analogy breaks here: cooks negotiate, while the formula assumes every worker adds the same fixed overhead \(C\) regardless of team size.

2.11.1 Mathematical Formulation

Formalize: Total time with linear overhead is:

\[ T(N) = (1 - P) \cdot T_{\text{serial}} + P \cdot T_{\text{serial}} / N + C \cdot N \]

where each symbol is defined above. The three terms read as serial time that never shrinks, parallel time that shrinks with \(N\), and overhead that grows with \(N\). The first-order condition \(dT/dN = 0\) gives the valley bottom step by step:

\[ \begin{aligned} dT/dN &= -P \cdot T_{\text{serial}} / N^2 + C &\text{(differentiating: serial term vanishes)} \\ 0 &= -P \cdot T_{\text{serial}} / (N^*)^2 + C &\text{(setting the slope to zero)} \\ (N^*)^2 &= P \cdot T_{\text{serial}} / C &\text{(rearranging)} \\ N^* &= \sqrt{P \cdot T_{\text{serial}} / C} &\text{(taking the positive root)} \end{aligned} \]

The second derivative \(d^2T/dN^2 = 2P \cdot T_{\text{serial}}/N^3\) is positive (all symbols are positive), confirming a minimum rather than a maximum. Dimensional check: \(P\) is unitless, \(T_{\text{serial}}\) is time, \(C\) is time per worker, so \(P \cdot T_{\text{serial}} / C\) has units of workers-squared — the square root yields a worker count, as required.

2.11.2 Worked Examples

Example 1 — solving for the valley. With \(P = 0.95\), serial share 0.05 taking 300 milliseconds (so \(T_{\text{serial}} = 300/0.05 = 6000\) ms), and \(C = 2\) milliseconds per worker: \(N^* = \sqrt{0.95 \times 6000 / 2} = \sqrt{2850} \approx \mathbf{53}\). The graph from 1 to 40 workers shows the valley bottom step by step — still falling at 40, flattening toward 53, then rising past it. Answer: adding workers helps until about 53, then coordination costs dominate. Sense-check: at \(N = 53\), parallel time \(0.95 \times 6000/53 \approx 108\) ms plus overhead \(2 \times 53 = 106\) ms — the two terms balance, exactly the valley condition.

Example 2 — the 12.5-lakh question. Moving training from 8 GPUs at about 12.5 lakhs a month to 16 GPUs at about 25 lakhs a month only pays when efficiency stays high. At 50 percent efficiency the extra 8 GPUs deliver 4 GPUs of real gain for 12.5 lakhs — the extra spend wastes about \(\mathbf{12.5}\) lakhs. Answer: compute \(N^*\) and \(E(N)\) first; rent second. Sense-check: 50% of 12.5 lakhs is 6.25 lakhs of useful work for 12.5 lakhs of rent — the waste claim follows directly.

Example 3 — why iteration takes over. Second-order polynomial \(aX^2 + bX + c = 0\) yields roots \(X_1, X_2\) via the quadratic formula. Third order \(aX^3 + bX^2 + cX + d = 0\) yields three roots via Cardano's formula. Fourth order still admits a formula (Ferrari's method). Fifth order and above need approximation: Newton-Raphson iteration \(X_{k+1} = X_k - f(X_k)/f'(X_k)\), repeated until the update stops changing. Answer: closed forms end at degree four; iteration carries degrees five and up. Sense-check: the course's own \(N^*\) came from calculus (derivatives), not from factoring — the same iterative spirit applied to optimization.

Scope: The square-root optimum assumes overhead grows linearly (\(C \cdot N\)) and \(P\) stays fixed. Assumption: every added worker adds the same \(C\). Superlinear overhead (all-to-all sync) pushes \(N^*\) lower — re-derive with the true overhead shape instead of trusting the square root.

Pitfalls: (1) Renting past \(N^*\) — every worker beyond the valley makes the job slower and more expensive. (2) Using nameplate utilization instead of effective \(P\) — memory at 90% with the bus stalled is not 90% useful work. (3) Treating the polynomial aside as trivia — "no closed form past degree four" is why the course optimizes iteratively instead of solving once.

Recap: Time is serial plus shrinking parallel plus growing overhead; the minimum sits at \(N^* = \sqrt{P \cdot T_{\text{serial}} / C}\). Exam note: a best-worker-count question fits a quiz or midterm — practice deriving \(N^*\) from \(T(N)\) by setting the first derivative to zero, and practice reading the optimum off the time-versus-workers graph. Bridge: Section 2.12 asks the design question behind \(P\) itself — how the work is split decides how large \(P\) can be.

Real-world: a training bill that doubles from 12.5 lakhs to 25 lakhs a month when moving from 8 to 16 GPUs forces the \(N^*\) calculation. Hardware without the arithmetic is gambling.

2.12 Parallelization Paradigms

Hook: One algorithm, ten idle GPUs, a billion records a day. The hardware is paid for and waiting. The only question — the million-dollar one — is how to split: by data, by task, by algorithm, or by some mix?

Parallelization means splitting work across \(N\) workers. The million-dollar question is how to split: by data, by task, by algorithm, or by some mix. Each paradigm below answers differently, and a fourth pillar, choosing the paradigm, decides among them.

Data parallelism repeats the same operation across different data elements. The mule-account hunt shows the scale: around 1 billion records a day with an algorithm that runs on a single GPU while 10 GPUs sit available. Splitting the billion records ten ways and handing each tenth to one GPU is data parallelism, and the map-then-reduce shape (mapping work out, reducing results back) organizes it. On a GPU one kernel launches many threads that work independently; on a CPU the threads do the same job. A server-class processor with 32 computing elements at two threads each runs about 64 parallel computations, while a GPU reaches tens of thousands. Data independence rules everything: each worker needs its own data, and when two workers need the same data the design must choose between sharing and replication. Replication replays the memory problem, with on-chip memory versus off-chip RAM, and the industry shift toward high-bandwidth memory (HBM) for GPUs over laptop RAM keeps memory scarce and expensive.

Task parallelism runs different tasks on the same data at the same time. Computing the mean and the median of one data set concurrently is the textbook shape.

Algorithm-specific parallelism opens up the algorithm itself. Random forest is the classic example: with the default of 100 trees and bagging (sampling with replacement), each tree trains independently. K-means clustering over the billion records leans on Lloyd's algorithm, the standard iterative procedure embedded in many packages, and beating it is a possible assignment: build an algorithm or framework that improves efficiency. Boosting resists this treatment because the error of the first pass becomes the input to the second pass, so the second pass waits on the first. That dependence makes boosting highly serial with \(P\) near 0 under Amdahl's law. The history tells the story: AdaBoost, the early gold standard from the days before GPUs (about 20 years back, when practitioners had no GPU support), could not be parallelized, and later methods such as LightGBM and XGBoost pushed further. The course teaches how to raise \(P\) toward values like 0.3 to 0.4 even for such stubborn algorithms.

The fourth pillar is choosing the paradigm: data parallelism, task parallelism, algorithm-specific parallelism, or a combination. That choice is the advanced skill. Managers should know what to look for and how to guide engineers; engineers should be able to code it. Simple neural networks already allow layer splitting across systems, and transformer architectures split models across workers as a matter of course. Once the splitting habit forms, parallel layouts feel easy.

Intuition: Splitting work is running a census. Data parallelism gives each counter a different district with the same questionnaire (same op, different data). Task parallelism gives each specialist the same district with a different form — one counts ages, another counts incomes (different tasks, same data). Algorithm-specific parallelism redesigns the questionnaire so counters stop waiting on each other. Choosing the paradigm is the census commissioner deciding which split fits the terrain. The analogy breaks here: districts are independent by construction, while real data shards share boundaries — and boundary data is where the overhead lives.

2.12.1 Mathematical Formulation

Formalize: Amdahl's law governs every paradigm choice: \(S(N) = 1 / ((1 - P) + P/N)\), where \(P\) is the parallelizable share. Data parallelism on fully independent elements pushes \(P\) toward 1. Boosting chains with pass-to-pass dependence keep \(P\) near 0. The paradigm decision is the decision that maximizes realized \(P\) after overhead: pick the split whose dependence structure leaves the largest independent share once communication and sync costs (section 2.13) are subtracted.

Comparison — when to pick which: data parallelism fits independent records (per-image ops, per-record scoring) and scales with shard count; it fails when workers need shared state. Task parallelism fits disjoint tasks on shared data (mean plus median in one pass) but rarely scales past a handful of tasks. Algorithm-specific parallelism fits ensemble and iterative methods whose independence is structural (random forests, Lloyd's iterations) but demands algorithm redesign for stubborn chains like boosting. Rule: default to data parallelism, add task parallelism where tasks are naturally disjoint, and invest in algorithm redesign only where \(P\) near 0 caps everything else.

2.12.2 Worked Examples

Example 1 — the billion-record split. 1 billion records split across 10 GPUs give each worker \(10^9 / 10 = \mathbf{100}\) million records. With a beautifully written single-GPU algorithm and ten idle GPUs beside it, the split is pure data parallelism plus a reduce step: 10 shards map in parallel, one reduction merges. Answer: wall-clock falls toward one-tenth plus the reduce cost. Sense-check: 10 shards of 100 million sum back to exactly 1 billion — no record lost, none doubled.

Example 2 — the forest of 100 trees. Random forest with 100 trees under bagging trains trees concurrently, matching the commonly cited default of 100 trees with the 300-dimension configuration guidance associated with Andrew Ng. Each tree is an independent worker-sized chunk: on 10 workers, each trains 10 trees, and wall-clock falls toward one-tenth of serial training plus aggregation. Answer: tree independence makes \(P\) near 1 — the ideal data-parallel citizen. Sense-check: bagging with replacement means no tree waits on another's output, so no serial chain exists to dispute the split.

Example 3 — the boosting wall. Boosting where pass two consumes the error of pass one forces serialization: pass \(k+1\) cannot start until pass \(k\) finishes. The parallelizable share sits near 0, so Amdahl's ceiling bites early — with \(P = 0.1\) and \(N = 10\), \(S = 1/(0.9 + 0.01) \approx \mathbf{1.1}\). Answer: ten workers buy almost nothing until the algorithm is redesigned. Sense-check: the dependence is structural (errors flow forward), so no shard count removes it — only the course techniques for lifting \(P\) toward 0.3–0.4 help.

Q: When derivations say a result holds for small \(N\), is writing \(N - 1\) instead of \(N\) acceptable? A: Yes for the small-data argument being made. The \(N - 1\) form stands in for \(N\) when proving behavior on small problem sizes, because the derivation only needs the small-size regime and skips the full general proof. Keep the substitution local to that argument — it is a small-size convenience, not a general identity.

Scope: Paradigm choice governs how \(P\) is maximized for a fixed workload. Assumption: workers are interchangeable and data reaches them (network and memory limits from sections 2.5 and 2.13 bind separately). Choosing data parallelism for dependent data silently reintroduces the serial chain it promised to remove.

Pitfalls: (1) Sharding dependent data and calling it data-parallel — boundary sharing becomes hidden serialization. (2) Replicating shared data on every worker — replaying the memory overflow of section 2.5. (3) Parallelizing the algorithm before profiling — if data parallelism already pushes \(P\) near 1, redesign effort buys nothing.

Recap: Split by data when records are independent, by task when tasks are disjoint, by algorithm redesign when dependence caps \(P\) — and the choice itself is the skill. Bridge: Section 2.13 prices what every split pays: the overhead taxes that Amdahl's clean formula leaves out.

Real-world: fraud detection over a billion daily transactions shards records across GPU fleets (data parallelism), random forests train 100 bagged trees concurrently (algorithm parallelism), and boosting pipelines expose the serial chains where paradigm choice matters most.

2.13 Overhead in Parallel Systems

Hook: Four workers should finish in a quarter of the time. They never do. The missing quarter went somewhere — this section finds every place it hides and names the tax each one charges.

Parallel runs pay taxes that serial runs never meet. One worker finishes early and idles while another lags. A finished worker hands its result to the next processor over a poor-bandwidth link. Two GPUs need the same data at once and collide. Barriers and locks serialize access: a mutex that guards shared data, a barrier that waits for every worker, and locks that block reads all stall progress. Some algorithms dodge the problem entirely: Hogwild!-style updates skip locking altogether. Overhead also splits by kind: compute overhead (time to finish the task), data overhead (time until data sits ready in cache), communication overhead (time to move data between systems), and synchronization overhead (time waiting on another worker). Cache behavior joins the list: a cache miss means the CPU asks for data that is not there, and efficiency falls with every miss.

Data-parallel training shows where the serial pieces hide. With one worker on the left and \(N\) workers on the right, the \(1 - P\) slice still runs serially while the \(N\) workers divide the rest. Somewhere a serial consolidation step, gathering and aggregating data from all workers, leaves other workers idle. From here on the standard term for a processor, GPU, thread, or core is worker, the smallest unit that works independently.

The working assumption for the speedup arithmetic in this section is generous: infinite bandwidth, with communication, signaling, synchronization, locks, and mutexes all ignored. Under that assumption speedup follows straight from Amdahl's first principles. The integer-division example carries the numbers: \(n = 10\) items with \(N = 4\) workers doing division only. The design question is how to split the 10 divisions so idle CPU time shrinks to the minimum.

Intuition: Overhead is a relay race run with cooked spaghetti for batons. Compute overhead is slow runners; data overhead is runners waiting for the baton to arrive at the exchange zone (cache); communication overhead is the handoff fumble across a windy gap (weak link); synchronization overhead is three fast runners standing idle because the fourth has not arrived at the barrier. Hogwild! is agreeing to run without batons at all. The analogy breaks here: batons never arrive corrupted, while lock-free updates can overwrite each other — the race stays fast only when overwrites are rare enough to ignore.

2.13.1 Mathematical Formulation

Formalize: Overhead-aware time is:

\[ T(N) = (1 - P) \cdot T_{\text{serial}} + P \cdot T_{\text{serial}} / N + T_{\text{overhead}} \]

where \(T_{\text{overhead}}\) is the time spent on communication plus synchronization (later separable into \(T_{\text{communication}} + T_{\text{synchronization}}\) depending on the problem), and the remaining symbols match the Amdahl section. Under the infinite-bandwidth assumption \(T_{\text{overhead}} = 0\) and the formula reduces to Amdahl's law. The section-2.11 linear model is the special case \(T_{\text{overhead}} = C \cdot N\). Splitting by kind:

\[ T_{\text{overhead}} = T_{\text{compute-tax}} + T_{\text{data}} + T_{\text{communication}} + T_{\text{synchronization}} \]

where each term is defined in the taxonomy below — four clocks that all run before the answer is ready.

2.13.2 Worked Examples

Example 1 — ten divisions, four workers. \(n = 10\) integer divisions across \(N = 4\) workers: the even split is 3 + 3 + 2 + 2. The two workers with 3 divisions set the pace; the two with 2 idle for one division-time waiting at the barrier. Answer: the split decides the speedup — balance the largest share, not the average. Sense-check: total work is fixed at 10 divisions, so the makespan is set by the max share (3), giving speedup \(10/3 \approx 3.3\) against the ideal 4.

Example 2 — the colliding GPUs. Two GPUs need the same data over a weak link. Transfer time (communication) plus lock waiting (synchronization) becomes the overhead term: if each transfer costs 50 ms and each lock wait costs 30 ms per step, \(T_{\text{overhead}} = 80\) ms per step rides on top of the split compute. Answer: shrink data movement (send gradients, not weights) or remove the lock (Hogwild!-style updates). Sense-check: when \(T_{\text{overhead}}\) rivals the per-worker compute, adding workers cannot help — the tax, not the split, sets the time.

Q: What are the pieces of overhead in practice? A: Compute overhead is the time to complete the task. Data overhead is the time until data is available in cache. Communication overhead is the transfer time between systems. Synchronization overhead is waiting on another worker. Total overhead is the sum seen from the time perspective, and each piece gets attacked separately. A Google-search-style budget of under 100 milliseconds forces hardware and software engineers to optimize all of them together.

Q: Does the serial-parallel split use the same time base for both shares? A: No. The serializable share maps to \(T_{\text{serial}}\)-style time while the parallelizable share divides by the worker count it is attached to. Each share follows its own scaling, which is why the two terms stay separate in the formula — merging them into one average would hide exactly the imbalance the integer-division example exposes.

Scope: The four-part taxonomy covers time taxes on a fixed worker count. Assumption: taxes add (they run back-to-back on the critical path). Overlapping communication with compute (pipelining) breaks pure addition — state the overlap before summing.

Pitfalls: (1) Optimizing compute while the barrier dominates — profile the four taxes before tuning any one. (2) Assuming infinite bandwidth in production math — the classroom assumption is generous by design; real links are not. (3) Locking shared data by default — check whether Hogwild!-style lock-free updates are safe before paying the mutex on every step.

Recap: Parallel time is serial plus split work plus four named taxes — compute, data, communication, synchronization. Bridge: Section 2.14 shows the most popular shape that pays all four taxes at scale: MapReduce, and the efficiency curve that turns its speedup into a buying decision.

Real-world: a Google search that answers in under 100 milliseconds exists because hardware and software engineers jointly attacked every overhead slice. Neither side alone could hit the budget.

2.14 MapReduce, Efficiency and the Cost Link

Hook: Speedup tells you how much faster. Efficiency tells you whether the speed was worth buying. A cluster can double its speedup while halving its value — this section draws the line where scaling earns and where it burns.

MapReduce is the popular architecture for data parallelism. Mapping assigns data to workers, and reducing consolidates every worker's output. The reduce step is the serial component: gathering intermediate data that also occupies memory. For a small concrete case with \(n = 16\) data points and \(N = 4\) workers, round one pairs workers (P1 with P2, P3 with P4) to combine partial results, and a further round consolidates the intermediate data into the final answer. The same memory discipline from the training discussion applies: just as practitioners watch inputs and outputs, they should watch optimizer-side memory such as Adam state and ask how to tune it to save memory.

Efficiency turns the speedup into a buying decision. Its plain-language form is speedup divided by worker count, \(E(N) = S(N) / N\). Cloud hardware must clear about 90 percent efficiency to justify its rent. The numbers show the decay: moving \(N\) from small values up to 64 drags efficiency from about 99.5 down to about 76.1, and at \(N = 1024\) only about 10 percent remains. An 8-CPU cloud setup at about 12.5 lakhs a month that scales poorly burns money the same way.

Data parallelism shines on concrete workloads. Image processing handles pixel-level data independently. Activation functions such as ReLU, the long-standing default for deep networks, and newer options such as GELU apply element by element. Batch inference groups queries together, runs the forward pass jointly, and the training side weighs how much of the forward propagation to save versus recompute. Gradient reduction, gathering per-worker gradients into one update, is the final goal of the data-parallel loop. The rule for all of them: data parallelism wins when each output depends only on its own input. Dependence between elements drags the speedup back down, and lifting speedup and efficiency under dependence is the open question.

Intuition: MapReduce is a national exam with district graders. Mapping hands each grader a stack of scripts (map phase, fully parallel). Reducing collects district totals into one national result — the head examiner adding up district sheets while every grader waits (serial reduce). Efficiency is marks per rupee of examiner salary: more graders grade faster, but the head examiner's desk is the bottleneck that decides whether the extra salaries were worth it. The analogy breaks here: exam scripts never change during grading, while gradient reduction feeds back into the next training round — the reduce output becomes the next map input.

2.14.1 Mathematical Formulation

Formalize: Map-phase work splits as \(n / N\) items per worker, where \(n\) is the data count and \(N\) is the worker count: with \(n = 16\) and \(N = 4\), each worker maps 4 items, and pairwise reduce rounds then fold 4 partials into 1 over \(\log_2 4 = 2\) serial-ish rounds. Efficiency is:

\[ E(N) = S(N) / N \]

where \(S(N)\) is the Amdahl speedup. The decay from about 99.5 at small \(N\) to about 76.1 at \(N = 64\) and about 10 percent at \(N = 1024\) is the cost curve that every scaling plan must face: speedup grows sublinearly while the divisor \(N\) grows linearly, so efficiency must fall.

2.14.2 Worked Examples

Example 1 — sixteen items, four workers. With \(n = 16\) data points and \(N = 4\) workers: each worker maps \(16/4 = \mathbf{4}\) items. Round one consolidates pairs of workers (P1+P2, P3+P4: 2 partials), round two folds the 2 partials into the answer. Answer: the intermediate folds are serial and memory-hungry — budget both. Sense-check: 4 workers times 4 items equals 16, and 2 reduce rounds match \(\log_2 4\).

Example 2 — the efficiency decay. Efficiency falls from about 99.5 to about 76.1 as \(N\) grows to 64, and collapses to about 10 percent at \(N = 1024\). At \(N = 1024\) with \(E = 0.10\), realized speedup is \(S = 0.10 \times 1024 \approx \mathbf{102}\) — a thousand paid workers doing the work of a hundred. Answer: chasing speedup without watching this curve spends budget for almost no gain. Sense-check: \(S \le N\) holds throughout (102 < 1024), confirming overhead rather than arithmetic error.

Example 3 — the data-parallel canon. Pixel-level image work, per-element ReLU or GELU, joint batch inference with forward and backward passes, and gradient reduction each map independent elements to independent workers. The forward-versus-recompute tradeoff for saved activations is the memory question inside the same loop: saving all activations costs memory (section 2.5), recomputing them costs time (section 2.2). Answer: independence per element is the entry ticket; the memory-time trade is the ongoing rent. Sense-check: ReLU on one pixel never reads its neighbor — the independence claim is verifiable per operation.
