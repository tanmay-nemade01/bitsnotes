# PostgreSQL Sequences

12.1 What a Sequence Is and How to Create One

12.1.1 Definition and Purpose

Hook: When ten people sign up at the same moment, where do ID numbers like user 1, user 2, and user 3 come from? Some shared counter must hand out a fresh number to each newcomer without ever repeating one.

A sequence (an ordered list of integers handed out one after another), written as a term formula below, is a database object that produces whole numbers in order. Tables use sequences to identify rows, to keep values unique, and to feed primary keys. Each call moves the list forward by a fixed step, so every caller gets a fresh number that no earlier caller received.

Intuition — the ticket roll at the counter: Picture a ticket roll at a busy service counter. Each customer tears off the next ticket: 41, 42, 43. Nobody receives the same number twice, and the numbers always move in the same direction. A sequence works the same way: every call tears off the next integer, which is why sequences fit primary keys and ID columns so well. The analogy breaks at one point: a ticket roll is paper, while a sequence lives inside the database, survives restarts, and serves hundreds of callers at the same time.

Formalize — the arithmetic walk. Every sequence follows one spoken rule: "start at S and add I each time." Written out, that rule becomes the term formula:

\[ a_n = S + (n-1) \times I \]

Here \(S\) is the start value (an integer, the first number handed out), \(n\) counts the call (a positive integer \(n = 1, 2, 3, \dots\)), \(I\) is the increment or step (an integer, positive for climbing lists and negative for falling lists), and \(a_n\) is the value handed out on call number \(n\).

Test the formula against the default list with \(S = 1\) and \(I = 1\):

\[ \begin{aligned} a_1 &= 1 + (1-1) \times 1 = 1 \\ a_2 &= 1 + (2-1) \times 1 = 2 \\ a_3 &= 1 + (3-1) \times 1 = 3 \end{aligned} \]

The arithmetic walk reproduces the 1, 2, 3 climb from the demo, so each symbol lines up with real behavior.

Picture the walk as a graph: the horizontal axis counts the call number \(n\) (1, 2, 3, …) and the vertical axis shows the handed-out value. The points sit on a straight line whose slope equals the step \(I\). A step of 1 gives a gentle staircase; a step of 50 gives a steep climb; a negative step slopes downward. The takeaway from the picture is that a sequence never curves or branches — it walks one straight staircase forever.

Scope: A sequence hands out integers only — no letters, no fractions, no formatted codes. It also promises uniqueness of handout, not a gap-free run: rolled-back transactions and server restarts can skip numbers, so invoice numbers that must never skip need a different design. Finally, currval reports the latest number handed out in your own session; a fresh session that never called nextval gets an error instead of a number.

Pitfalls: Beginners trip on three points. First, they expect 1, 2, 3 with no gaps and panic at a jump from 5 to 8 — gaps are normal and harmless for IDs. Second, they treat the list like a random-number source; a sequence is the opposite of random, it is fully predictable. Third, they assume reading the position moves the list; only nextval moves it, as section 12.2 shows.

Recap: A sequence is a shared ticket-roll counter that follows the arithmetic walk \(a_n = S + (n-1) \times I\). With the idea in place, the next step is to build one.

In daily production work, auto-generated IDs backed by sequences sit behind almost every user table, order table, and ticket table. Other databases chase the same goal with different packaging, and knowing the mapping helps when you switch systems: MySQL seals the counter inside the column with AUTO_INCREMENT instead of exposing a standalone object, Snowflake offers CREATE SEQUENCE with the same START and INCREMENT idea, and Spark-based Databricks tables lean on identity columns rather than sequence objects. The ticket-roll idea stays the same everywhere; only the syntax moves.

12.1.2 Creating a Sequence

The build statement is:

CREATE SEQUENCE IF NOT EXISTS test_seq;

IF NOT EXISTS — the guard clause that skips creation when the name is taken — is the only difference from the bare form CREATE SEQUENCE test_seq;. The guarded form checks whether the sequence already lives in the database and creates it only when it is missing. The bare form raises an error when the name is taken:

ERROR: relation "test_seq" already exists

That error is the reason setup scripts prefer the guard: a script that runs twice must not crash on its second run. After running the statement, open the database object tree, find the sequences section, and refresh it. The new entry test_seq appears there. Refreshing matters because the tree does not redraw itself on its own, so a fresh sequence stays invisible until you ask for a redraw.

12.1.3 Worked Example

Goal: Create test_seq and confirm it in the refreshed sequences list.

  1. Run CREATE SEQUENCE IF NOT EXISTS test_seq; — the database reports success.
  2. Open the database tree and go to the sequences section.
  3. Refresh the view so the tree redraws itself.
  4. Confirm test_seq is listed among the entries.

Result: the sequence exists and is ready to hand out numbers starting at 1. Sense-check: a bare CREATE SEQUENCE with no options always starts at 1 with a step of 1, so the first handout will be 1.

12.1.4 Student Questions and Answers

Q: What does IF NOT EXISTS change versus plain creation?

A: Plain CREATE SEQUENCE fails when the name is taken. Adding IF NOT EXISTS makes the statement check first and skip creation quietly when the sequence already exists.

12.2 Reading Numbers Out: nextval and currval

12.2.1 Moving Forward With nextval

Hook: The list exists but nobody has drawn a number yet. How does a caller ask for the next ticket — and what stops two callers from receiving the same one?

The function nextval — "next value", the call that advances the sequence and returns the new number — moves the list one step and hands back the result:

SELECT nextval('test_seq');

The first call returns 1. Run it again and it returns 2. Run it again and again and each run adds one more to the last value. That repeated climb is exactly why the function carries the name it does.

Formalize. Each nextval call moves the stored position forward and hands out the new value:

\[ next = current + I \]

Here \(current\) is the last value handed out (an integer) and \(I\) is the step, which is 1 by default. So when the stored position sits at 4, the next call hands out \(4 + 1 = 5\). Each call both advances the internal counter and returns the fresh value, which is why concurrent callers each get a different number: the database locks the counter for the instant it moves it.

12.2.2 Peeking With currval

The function currval — "current value", the call that reports the latest number without moving the list — shows where the sequence stands:

SELECT currval('test_seq');

When the list had climbed to 5, currval returned 5. After more nextval calls pushed the list to 10, currval returned 10. Running currval twice in a row gives the same answer both times because it never advances anything. So the pair splits the work cleanly: nextval adds numbers to the list, and currval reports the most current value.

Scope: currval is session-local. It reports the latest number that your session drew with nextval. In a brand-new session that has not called nextval yet, currval raises an error instead of guessing. Use currval right after an insert to learn the ID your own row received, never to spy on another session.

Pitfalls: The classic trap is treating currval as a second way to draw numbers. It is not: calling it ten times changes nothing. A second trap is calling currval before any nextval in a new session and being surprised by the error — the session must draw first, then peek.

Recap: nextval moves the list and hands out the fresh number; currval only reports the latest handout. Up next, setval jumps the list to a chosen spot.

In other databases the same two jobs appear under different names, which is worth knowing as a learner. MySQL hides both jobs inside AUTO_INCREMENT plus LAST_INSERT_ID(), so there is no separate "peek" call to memorize. Snowflake keeps SEQ.nextval for drawing and tracks the latest value per session much like PostgreSQL. The shared idea everywhere is one call that moves, one read that peeks.

12.2.3 Worked Example

Goal: Climb with nextval, then report the position with currval.

  1. Run SELECT nextval('test_seq'); — returns 1.
  2. Run it again — returns 2.
  3. Keep running it until the returned value is 5 (calls 3, 4, 5 hand out 3, 4, 5).
  4. Run SELECT currval('test_seq'); — returns 5 (peek, no movement).
  5. Run nextval several more times until the value reaches 10 (calls 6–10 hand out 6, 7, 8, 9, 10).
  6. Run SELECT currval('test_seq'); — returns 10.

Result: nextval climbed 1, 2, 3, 4, 5, then on to 10, while currval reported 5 and later 10 without moving anything. Sense-check: the peeked value always equals the most recent handout, so currval can never run ahead of nextval.

12.2.4 Student Questions and Answers

Q: Does currval change the sequence position?

A: No. Only nextval advances the list, while currval only reports the latest value. Repeated currval calls return the same number because nothing moves.

12.3 Setting a Sequence: setval and the is_called Flag

12.3.1 Pointing a Sequence at a Fresh Value

Hook: Imagine test rows ate up IDs 1 through 99, and real data must start at 100. Must you call nextval ninety-nine times, or can you jump the list there in one move?

setval — "set value", the function that points an existing sequence at a chosen number — resets the position of a list that already exists:

SELECT setval('test_seq', 100);

This works only on a sequence that already lives in the database. After this call, the next nextval call returns 101, then 102, 103, 104, 105 as calls continue. A later currval reports the latest handed-out value, such as 105. In short, setval lets us jump the list to any chosen spot instead of climbing there one call at a time.

Intuition — moving the ticket roll forward by hand: Picture the counter clerk lifting the ticket roll and skipping straight to ticket 100 because tickets 1–99 went to practice customers. The next real customer tears off 101. setval is that hand on the roll: it repositions the counter in one move rather than tearing off tickets one by one.

12.3.2 The Default Skip Behavior

Formalize. By default setval marks the given value as already used, so the next call skips past it:

\[ next = V + I \]

Here \(V\) is the value passed to setval (an integer) and \(I\) is the step (1 by default). That is why setval('test_seq', 100) is followed by 101 rather than by a repeat of 100. Under the hood the call stores last_value = 100 with the internal is_called flag set to true, meaning "100 already went out," so the next draw adds one step: \(100 + 1 = 101\).

12.3.3 Holding the Value With false

Sometimes we want the list to start exactly on the given value instead of skipping past it. A third true-or-false argument controls this:

SELECT setval('test_seq', 200, false);

With false, the system records 200 as not yet used. The next nextval call then returns exactly 200 instead of 201. Note the subtle detail: right after the setval call, currval still shows the older position (105 in the walkthrough) because no new number has been handed out yet. Only after nextval runs does currval report 200. Further nextval calls then climb 201, 202, 203, and so on.

Employees restart warning — the case where the newcomer hire must get the exact value: Picture an employees table whose IDs must restart at 200 so the next new hire receives employee ID 200 itself, not 201. Passing false gives exactly that outcome, while the default true would hand the newcomer 201. Use false whenever a specification says "the next row must carry exactly N."

Compare the two forms side by side:

Call Internal flag Next nextval returns Fits
setval('s', 200) (= true) 200 marked used 201 "Continue after 200"
setval('s', 200, false) 200 marked unused 200 "Restart exactly at 200"

Scope: setval jumps to any integer inside the sequence bounds, including backward. It runs at once and is never part of a transaction-safe ID scheme: rolling back your transaction does not roll back the jump. Never use setval to patch a live counter while inserts are running, or two writers can collide.

Pitfalls: The two classic mix-ups: first, expecting setval('s', 200) to hand out 200 next — it hands out 201 unless you add false. Second, expecting currval to show 200 right after the setval(..., false) call — it still shows the old position until nextval actually draws 200.

Recap: setval jumps the list; the default skips past the given value (\(next = V + I\)), while false pins the next draw exactly on it. Next, ALTER SEQUENCE rewrites the stored definition itself.

For reference across systems: MySQL achieves the same jump with ALTER TABLE t AUTO_INCREMENT = 200 (no true/false flag exists there), and Snowflake uses ALTER SEQUENCE ... RESTART WITH 200. Only PostgreSQL exposes the extra is_called choice, so when moving between systems, map "skip past" to the plain restart and "start exactly on" to PostgreSQL's false form.

12.3.4 Worked Example

Goal: Set the list to 100 with the skip, then pin it at 200 with false.

  1. Run SELECT setval('test_seq', 100); — the list now treats 100 as used.
  2. Run SELECT nextval('test_seq'); — returns 101, since \(100 + 1 = 101\).
  3. Keep calling nextval — returns 102, 103, 104, 105.
  4. Run SELECT currval('test_seq'); — returns 105.
  5. Run SELECT setval('test_seq', 200, false); — 200 is recorded as not yet used.
  6. Run SELECT currval('test_seq'); — still 105, since nothing new was handed out.
  7. Run SELECT nextval('test_seq'); — returns exactly 200.
  8. Run nextval again — returns 201, 202, 203.

Result: the default call skips past the set value, while the false call starts on it. Sense-check: after step 7, currval finally reads 200, confirming that only a draw — never a setval — makes a value current.

12.3.5 Student Questions and Answers

Q: Why does currval still show the old number after setval with false?

A: Because currval reports the last handed-out number, so the old value stays. The 200 becomes current only once nextval runs and hands it out.

Q: When should I pass false instead of leaving the default?

A: When the next row must carry the exact restart value itself. For an employees table restarting at 200, false suits the next hire identifier: the newcomer gets 200, while the default would give 201.

12.4 Restarting and Renaming With ALTER SEQUENCE

12.4.1 Restarting at a Chosen Value

Hook: setval jumps the counter, but the jump is a one-off function call. What if the restart should be baked into the sequence definition itself, so anyone reading the setup sees "this list begins at 100"?

While setval jumps the position through a function call, ALTER SEQUENCE changes the stored definition itself. To reset the list back to 100:

ALTER SEQUENCE test_seq RESTART WITH 100;

In the walkthrough the list had climbed to 206. Checking it first with SELECT nextval('test_seq'); showed 206. After the restart statement ran, the next nextval call returned exactly 100. The old climb is gone and counting starts over from the chosen value.

setval versus RESTART WITH — when to pick which. Both move the position, but they live in different layers. setval is a function call that jumps to a value at once, handy for quick fixes and ad-hoc resets. ALTER SEQUENCE ... RESTART WITH rewrites the stored sequence definition so the restart sticks as part of its setup — the right choice for migration scripts and repeatable setup, where the restart must be visible, reviewable, and re-runnable.

12.4.2 Renaming a Sequence

The same statement family renames a list:

ALTER SEQUENCE test_seq RENAME TO my_sequence;

After running it, refresh the sequences section of the object tree. The old name is gone and my_sequence stands in its place. Renaming through the graphical tool reaches the same result, as shown in the next section. A warning worth keeping: always confirm which entry is highlighted before renaming or restarting. These statements act at once on the named list — a rename aimed at the wrong entry renames the wrong entry, and there is no undo beyond renaming it back.

Scope: RESTART WITH accepts any integer inside the sequence bounds, forward or backward. Renaming updates the catalog name but does not rewrite column defaults that spell out the old name as text — if a column default says nextval('test_seq') and you rename the list to my_sequence, you must update that default by hand or inserts will fail.

Recap: ALTER SEQUENCE ... RESTART WITH resets the stored definition to a chosen value, and RENAME TO gives the list a new name. Next, the graphical tool performs the same edits by clicking.

12.4.3 Worked Example

Goal: Reset a list sitting at 206 back to 100, then rename it.

  1. Run SELECT nextval('test_seq'); — returns 206, confirming the climbed position.
  2. Run ALTER SEQUENCE test_seq RESTART WITH 100; — the stored definition now restarts at 100.
  3. Run SELECT nextval('test_seq'); — returns 100.
  4. Run ALTER SEQUENCE test_seq RENAME TO my_sequence; — the catalog entry is renamed.
  5. Refresh the sequences section and confirm my_sequence is listed, with test_seq gone.

Result: the list now counts from 100 under its new name. Sense-check: a second nextval returns 101, confirming the restart stuck and counting resumed normally.

12.4.4 Student Questions and Answers

Q: What is the difference between setval and RESTART WITH?

A: Both move the position. setval jumps at once as a function call, while RESTART WITH rewrites the stored definition so the restart sticks as part of its setup.

12.5 Changing a Sequence in the Graphical Tool

12.5.1 What the Properties Panel Shows

Hook: Not every fix happens in a script. When you just need to nudge one list — a bigger step, a new start — where do you click?

Everything the statements above do can also be done by pointing and clicking. Open the database tree, find the sequence, open its properties, and the panel shows the start value, the increment, the minimum, the maximum, the cache size, and whether the list cycles. Editing a field there rewrites the matching part of the definition.

Two fields that deserve a closer look. Cache — the count of numbers the server pre-assigns in memory for speed — means the database reserves a block of upcoming values at once instead of writing each draw to disk. A cache of 20 runs faster than a cache of 1, but a crash can lose the unused reserved block and leave a gap. Cycle — the switch that decides whether the list wraps around at its end — is covered in depth in section 12.8: on, the list restarts at its bound; off, it raises an error.

12.5.2 Generated SQL Stays Visible

The panel teaches the statement path: each edit in the panel writes out the matching SQL beside it, so the graphical path teaches the statement path. Watch that preview pane while you click — it shows exactly which ALTER SEQUENCE you would have typed, which makes the tool a trainer for scripts rather than a replacement for them.

In the walkthrough, setting the start to 200 with an increment of 20, a minimum of 1, the default maximum (the largest bigint value the system supports), and cycling switched on produced two statements. The first applied the start value to the sequence, and the second altered the definition with the new step of 20 plus cycling. Running nextval afterwards gave 220, then 240, 260, 280 with each further call, since \(next = current + 20\) each time. Step by step: \(200 + 20 = 220\), then \(220 + 20 = 240\), then \(240 + 20 = 260\), then \(260 + 20 = 280\).

Scope: Panel edits act at once on the live definition, exactly like their SQL twins — there is no draft mode. On a busy production database, prefer a reviewed script over clicking, because a typed statement can be tested, versioned, and re-run, while a click cannot.

Recap: The properties panel exposes every sequence knob — start, step, bounds, cache size, cycling — and previews the matching SQL as you click. Next, the full creation statement packs all of those knobs into one command.

12.5.3 Worked Example

Goal: Switch a list to steps of twenty with cycling in the panel.

  1. Open the sequence properties in the graphical tool.
  2. Set the start to 200 and the increment to 20.
  3. Set the minimum to 1 and leave the maximum at its default.
  4. Switch cycling on and save.
  5. Run SELECT nextval('test_seq'); — returns 220.
  6. Run it again — returns 240, then 260, then 280.

Result: the list now climbs twenty at a time and will wrap at its limit. Sense-check: each handout differs from the last by exactly 20, confirming the new step stuck.

12.5.4 Student Questions and Answers

Q: Should I use statements or the graphical tool for edits?

A: Both reach the same result either way, so pick what fits the task at hand. The tool suits quick one-off edits, while statements suit scripts that must run again and again.

12.6 START WITH, INCREMENT, MINVALUE, MAXVALUE

12.6.1 The Full Creation Form

Hook: So far every list started at 1 and climbed by 1. What if ticket numbers must start at 500, jump by 50, and never leave the 400–6000 band?

A fresh list can carry its whole shape in one statement:

CREATE SEQUENCE IF NOT EXISTS test_seq3
INCREMENT BY 50
MINVALUE 400
MAXVALUE 6000
START WITH 500;

What each clause does. START WITH sets the first number handed out. INCREMENT BY sets the step added on every call. MINVALUE sets the floor the list never drops below. MAXVALUE sets the ceiling it never climbs past. The four knobs together draw the staircase: where it begins, how steep it is, and where the walls stand.

The walkthrough first tried starting at 200 with a floor of 400, which cannot work: the start must sit inside the floor-to-ceiling range. The database rejects that combination with a bound error. Correcting the start to 500 fixed it, since 500 lies between 400 and 6000. The rule generalizes: for a climbing list the start must satisfy \(MINVALUE \le START \le MAXVALUE\); for a falling list the same check applies with the start near its maximum.

12.6.2 Watching the Steps Land

With the shape above, the spoken rule "start at 500 and add 50 each time" is the formula:

\[ a_n = 500 + (n-1) \times 50 \]

Here \(n\) counts the calls (1, 2, 3, …) and 50 is the step. The first nextval call returns 500. The next returns 550, since \(500 + 50 = 550\). The one after returns 600, since \(550 + 50 = 600\). The climb keeps adding 50 until it nears the 6000 ceiling: the last handout is 6000 itself, because \(500 + 110 \times 50 = 6000\) on call \(n = 111\).

12.6.3 What Happens at the Ceiling

Scope: When the list reaches its maximum, one of two things happens depending on the cycling switch covered in section 12.8: with cycling on, the list wraps and starts over; with cycling off, the next call raises an error instead of handing out a number. Choosing between them is a design decision, not an afterthought — wrap a repeating batch number, refuse a limited pool.

Recap: START WITH, INCREMENT BY, MINVALUE, and MAXVALUE draw the full staircase — first step, steepness, floor, ceiling. Next, the AS clause picks how wide each stored number is.

Dialect note for the cross-system learner: MySQL has no MINVALUE/MAXVALUE knobs on its auto counter — the ceiling is whatever the column type holds, so the "rejected start" lesson there becomes "pick a column type whose range covers your start." Snowflake mirrors the PostgreSQL knobs almost one for one, including START WITH and INCREMENT BY. Same staircase, slightly different dials.

12.6.4 Worked Example

Goal: Build a list from 500 climbing by 50 within its bounds.

  1. Run the CREATE SEQUENCE statement shown above.
  2. Refresh the sequences section and confirm test_seq3 is listed.
  3. Run SELECT nextval('test_seq3'); — returns 500.
  4. Run it again — returns 550, since \(500 + 50 = 550\).
  5. Run it again — returns 600, since \(550 + 50 = 600\).

Result: the list climbs 500, 550, 600, and keeps adding 50 per call up to 6000. Sense-check: the third handout matches \(a_3 = 500 + 2 \times 50 = 600\), so the staircase formula and the live list agree.

12.6.5 Student Questions and Answers

Q: Can the start sit outside the minimum and maximum?

A: No. The start must sit between the floor and the ceiling, so a start below the floor is rejected. A start of 200 with a floor of 400 fails, so the walkthrough moved the start to 500.

12.7 Sequence Data Types: SMALLINT, INTEGER, BIGINT

12.7.1 Choosing the Value Type

Hook: Every list so far counted 1, 2, 3 — but under the hood, how wide is each stored number? A table that will never pass 100 IDs has no business reserving room for 9 quintillion.

A sequence can store its numbers as a smallint (a 2-byte whole number), an integer (a 4-byte whole number, also written int), or a bigint (an 8-byte whole number). By default every new sequence uses bigint, so very large counts never overflow. Picking a smaller type saves space and keeps table shapes tidy when the counts will always stay small.

The three choices. The spoken choice "a small whole-number list" becomes the clause:

\[ type \in \{\text{SMALLINT}, \text{INTEGER}, \text{BIGINT}\} \]

with BIGINT as the default. Their ranges are fixed by the type system, not by the lecture: smallint spans \(-32768\) to \(+32767\), integer spans \(-2147483648\) to \(+2147483647\), and bigint spans about \(-9.2 \times 10^{18}\) to \(+9.2 \times 10^{18}\). Pick the smallest type whose range covers the largest value the list will ever reach — a 2-byte smallint for a lookup table with dozens of rows, a 4-byte integer for a users table with millions, the default 8-byte bigint when the ceiling is unknown.

Picture the storage as shelf width: smallint is a narrow 2-byte slot, integer a 4-byte slot, bigint a roomy 8-byte slot. Narrow slots pack more rows per disk page, which speeds up scans of huge tables. The takeaway: width costs bytes on every row, so size the slot to the job.

Scope: The type caps the list: a smallint list that reaches 32767 refuses to hand out 32768 and raises an overflow error instead. The type never changes the counting behavior below the cap — 1, 2, 3 look identical in all three types. Match the sequence type to its column type, or a counter that outgrows its column will break inserts.

Pitfalls: The two traps run in opposite directions. Oversizing wastes bytes on every row of a giant table (a bigint ID on a billion-row table costs 4 extra bytes per row versus integer — gigabytes of dead weight). Undersizing breaks the table the day the counter passes the cap, and widening a live column is painful. When in doubt, keep the bigint default; shrink only when the ceiling is genuinely known.

Recap: Sequences store smallint, integer, or bigint values — 2, 4, or 8 bytes wide — with bigint as the safe default. Next, a negative step turns the staircase into a slide.

Cross-system note: MySQL teaches the same sizing lesson through types like TINYINT and SMALLINT UNSIGNED paired with AUTO_INCREMENT — the Sakila sample database uses small unsigned counters for lookup tables and wider ones for big tables, exactly the "size the slot to the job" rule. The ranges above are the same standard limits in every system; only the spelling of the auto-counter differs.

12.7.2 The AS Clause

The build pattern stays the same; only the AS clause is new:

CREATE SEQUENCE IF NOT EXISTS test_seq_smallint AS SMALLINT;
CREATE SEQUENCE IF NOT EXISTS test_seq_int AS INT;
CREATE SEQUENCE IF NOT EXISTS test_seq_big AS BIGINT;

After running them, refresh the sequences section. All three lists appear. Calling SELECT nextval('test_seq_smallint'); returns 1, and further calls climb exactly like any other list. The only difference sits underneath: the stored value type.

12.7.3 Worked Example

Goal: Create one list per value type and count upward together.

  1. Run all three CREATE SEQUENCE statements above.
  2. Refresh the sequences section and confirm all three names appear.
  3. Run SELECT nextval('test_seq_smallint'); — returns 1.
  4. Run it again — returns 2.

Result: the smallint list counts 1, 2, 3 exactly like its larger siblings. Sense-check: drawing from the smallint, integer, and bigint lists in turn returns the same 1, 2, 3 run, confirming the type changes storage width, never the counting order.

12.7.4 Student Questions and Answers

Q: If they all count the same, why pick a smaller value type when counting matches?

A: To save space and keep table shapes tidy. When counts will always stay small, a smallint column holds them with fewer bytes than a bigint one.

12.8 Descending Sequences and CYCLE

12.8.1 The Default Climb

Hook: Every list so far climbed. But coupon books count down, not up. Can a sequence fall?

Every list built so far climbs: each call adds a positive step to the last value. A plain CREATE SEQUENCE seq_asc followed by nextval calls returns 1, then 2, then 3, each step adding \(+1\). The default is a staircase that rises — the next section flips it.

12.8.2 Building a Falling List

A negative step flips the direction. The walkthrough built one like this:

CREATE SEQUENCE seq_desc
INCREMENT BY -1
MINVALUE 1
MAXVALUE 3
START WITH 3
CYCLE;

Formalize. The spoken rule "start at 3, step down by 1, wrap at the floor" is the formula:

\[ a_n = 3 - (n-1) \]

with the wrap rule that after 1 comes 3 again. The first nextval call returns 3. The next returns 2, since \(3 - 1 = 2\). The next returns 1, since \(3 - 2 = 1\). Because the CYCLE switch is on, the call after that wraps back to 3, then 2, then 1, repeating the loop 3, 2, 1, 3, 2, 1 for as long as calls continue. Note the bounds logic flips for a falling list: the start sits at the maximum (3), the floor is the minimum (1), and the step is negative.

12.8.3 CYCLE Against NO CYCLE

Swapping the last clause to NO CYCLE keeps the same 3, 2, 1 walk but changes the ending. After 1 arrives, the next call raises an error stating that the list reached its minimum value of 1. Nothing wraps. Nothing repeats.

The monthly coupon analogy — why a refused handout is the right answer: Picture monthly coupons numbered 100 down to 1: as people claim them the count falls 100, 99, 98, down to 1, and with NO CYCLE the system refuses further handouts once 1 is gone. That refusal is the desired behavior there — no coupons remain, so none should be handed out. A personal leaning voiced alongside is to keep CYCLE in most cases, but the right call always depends on the task. Compare the two endings directly:

Switch After the last value… Fits
CYCLE Wraps back to the start (…1, then 3 again) Repeating batches, round-robin slots, test loops
NO CYCLE Raises an error and stops Limited pools: coupons, vouchers, one-shot ticket blocks

Scope: Cycling works at both ends: a climbing list that hits its maximum wraps to its minimum, and a falling list that hits its minimum wraps to its maximum. CYCLE never skips the bound value itself — 3, 2, 1 includes every number each loop. Never use CYCLE on a primary-key counter: wrapping reuses IDs that already exist in the table and breaks uniqueness.

Pitfalls: Two traps here. First, building a falling list but forgetting the bounds: INCREMENT BY -1 with the default start of 1 and no minimum fails, because a negative step needs START WITH at the top and an explicit MINVALUE. Second, cycling a key column and rediscovering old IDs — wrap-around plus unique keys equals duplicate-key errors.

Recap: A negative INCREMENT BY builds a falling list, and CYCLE loops it while NO CYCLE stops it with an error. Next, DROP SEQUENCE removes lists that are no longer needed.

12.8.4 Worked Example

Goal: Compare a wrapping falling list against a stopping one.

  1. Build seq_desc with CYCLE as shown above.
  2. Run SELECT nextval('seq_desc'); — returns 3, then 2, then 1.
  3. Run it once more — wraps back to 3.
  4. Build seq_desc_nocycle the same way but with NO CYCLE.
  5. Run nextval on it — returns 3, then 2, then 1.
  6. Run it once more — error: the minimum value 1 was reached.

Result: the cycling list loops 3, 2, 1 forever, while the other list stops with an error after 1. Sense-check: both lists hand out the identical 3, 2, 1 run first, so the only difference is what happens at the floor.

12.8.5 Student Questions and Answers

Q: How do I make a sequence count down instead of up?

A: Give it a negative INCREMENT BY step with matching bounds — the list then falls down. With START WITH 3, MINVALUE 1, and step −1, the list falls 3, 2, 1 instead of climbing.

Q: What is the difference between CYCLE and NO CYCLE behavior?

A: CYCLE wraps the list back to its start when it hits the end. NO CYCLE raises an error there instead, which fits cases like coupons that must run out.

12.9 Deleting a Sequence

12.9.1 The DROP Statement

Hook: Practice lists pile up fast. How do you remove one — and what makes the removal dangerous?

A list that is no longer needed leaves the database with:

DROP SEQUENCE test_seq2;
DROP SEQUENCE test_seq3;

In the walkthrough each statement removed its named list. After dropping, refresh the sequences section and confirm the name is gone. Confirming matters because a dropped list cannot be recovered — no recycle bin, no undo; the walkthrough stresses this twice.

The guard twin. Just as creation has IF NOT EXISTS, dropping has IF EXISTS: DROP SEQUENCE IF EXISTS test_seq2; skips quietly when the name is already gone instead of raising an error. Teardown scripts should always use the guard so a twice-run cleanup does not crash halfway through.

12.9.2 Deleting Through the Graphical Tool

The same result is one right-click away. Browse to the database, then schemas, then sequences, right-click the unwanted entry, and pick Delete/Drop. Read the confirmation prompt with care and make sure the highlighted name is truly the list meant for removal before pressing OK.

Scope: Dropping is instant and permanent, and it cascades into consequences: dropping the wrong list breaks every column default that points at it, so inserts on those tables fail from that moment on. Always double-check the highlighted name. Sequences tied to a column with OWNED BY (section 12.10) vanish on their own when their table or column is dropped — never drop those by hand unless the table is going too.

Recap: DROP SEQUENCE removes a list at once and forever, so confirm the highlighted name before you commit. Next, SERIAL columns let the database build and link a list automatically.

12.9.3 Worked Example

Goal: Remove lists by statement and by clicking.

  1. Run DROP SEQUENCE test_seq2; and watch the success message.
  2. Refresh the sequences section and confirm the name is gone.
  3. Run DROP SEQUENCE test_seq3; and confirm likewise.
  4. Right-click the descending list, pick Delete/Drop, read the confirmation prompt, check the highlighted name, and press OK.

Result: all three lists are gone from the database. Sense-check: a nextval call on any dropped name now fails with "relation does not exist," confirming the removal stuck.

12.9.4 Student Questions and Answers

Q: How do I confirm the drop worked?

A: Refresh the sequences section and look for the missing name. When the name no longer appears, the list is gone.

12.10 SERIAL Columns and Attaching a Sequence to a Table

12.10.1 How SERIAL Builds a Sequence for Us

Hook: Hand-linking a list to every ID column would get old fast. Is there a column type that builds its own counter?

The serial type — a shorthand column type that auto-creates a counting list behind the scenes — is the fastest path to numbered rows:

CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    username VARCHAR(50)
);

What SERIAL builds behind the scenes. Creating this table also creates a list named users_user_id_seq, following the pattern table name, underscore, column name, underscore, seq. The column carries the default:

\[ DEFAULT = nextval(\text{'users\_user\_id\_seq'}) \]

so every insert runs the list without being asked. Open the column properties and the definition panel shows exactly this default. Two facts anchor this behavior. First, the column must be serial for the system to build the list on its own. Second, the column default is always the nextval call on that list.

Inserting Adam gives user_id 1. Inserting Adnan gives 2, since \(1 + 1 = 2\). Each insert adds the default step of one. The generated list sits in the sequences section and can be altered like any other: running ALTER SEQUENCE users_user_id_seq RESTART WITH 100; makes the next inserted row carry 100.

Dialect map for the cross-system learner: PostgreSQL SERIAL is the same idea as MySQL AUTO_INCREMENT (sealed inside the column) and Snowflake AUTOINCREMENT/IDENTITY, but PostgreSQL alone exposes the helper as a real sequence you can inspect, restart, and rename. Newer PostgreSQL also offers GENERATED ... AS IDENTITY, the standards-style spelling of the same trick — prefer it in new tables, and read SERIAL as its older shorthand.

12.10.2 Attaching a List to an Existing Integer Column

Hook: The table already exists with a plain integer ID and a thousand rows. Rebuilding it is out of the question — can a counter be bolted on afterward?

When a table already exists with a plain integer column, linking a list takes two steps. Start with a table that has no auto-counting:

CREATE TABLE users2 (
    user2_id INT PRIMARY KEY,
    user2_name VARCHAR(50)
);

Checking this column's properties shows no default value, since plain INT builds nothing by itself.

Step one builds the list and ties its lifetime to the column with OWNED BY — the clause that deletes the list automatically when its table or column goes away:

CREATE SEQUENCE users2_user2_id_seq
START WITH 100
OWNED BY users2.user2_id;

Step two points the column default at the list:

ALTER TABLE users2
ALTER COLUMN user2_id
SET DEFAULT nextval('users2_user2_id_seq');

We keep the column as INT and only set its default to the list's next value. Reopen the column properties and the definition panel now shows the new default.

Scope: The two-step link fits empty or fresh tables best. On a table that already holds rows, new inserts draw from 100 while old rows keep their existing IDs — check for collisions first, and consider setval to jump past the highest existing ID. OWNED BY only ties lifetimes; it does not set the default for you, and the default alone does not tie lifetimes — both steps are needed.

Pitfalls: Skipping step two leaves a list that nobody calls: inserts then fail with missing-ID errors because the default is still empty. Skipping step one (pointing the default at a list owned by another table) works today but orphans the list when that other table is dropped. Always do both steps together.

Recap: SERIAL builds the list and the default in one move; a plain integer needs the manual two-step — OWNED BY, then SET DEFAULT nextval(...). Next, the catalog query lists every counter in the database.

12.10.3 Worked Example

Goal: Link a fresh list at 100 to the plain integer column, then insert rows.

  1. Create users2 with user2_id INT PRIMARY KEY as shown above.
  2. Run the CREATE SEQUENCE ... OWNED BY users2.user2_id statement.
  3. Refresh the sequences section and confirm users2_user2_id_seq is listed.
  4. Run the ALTER TABLE ... SET DEFAULT nextval(...) statement.
  5. Insert a row for Adam and run SELECT * FROM users2; — user2_id is 100.
  6. Insert a row for a second user and query again — the new user2_id is 101, since \(100 + 1 = 101\).

Result: the plain integer column now numbers rows 100, 101, 102 with each insert. Sense-check: the second insert drew exactly one step above the first, confirming the default fires on every insert without being named.

12.10.4 Student Questions and Answers

Q: Why does a serial column number itself but an integer column does not?

A: Serial builds a list plus its nextval default behind the scenes, while a plain integer builds nothing. Rows get numbers only after we link a list by hand with the two-step recipe.

Q: What are the two steps for linking a list to an existing column?

A: First create the sequence with OWNED BY pointing at the table and column. Then alter the column to SET DEFAULT nextval(...) on that sequence.

12.11 Listing All Sequences in a Database

12.11.1 Querying the System Catalog

Hook: After a semester of demos, the database holds a dozen stray counters. How do you take stock of all of them in one query?

Every list ever created is recorded in the system catalog table pg_class — the internal table that tracks all database objects. Lists carry the kind code 'S', so this query returns each list name:

SELECT sequence_name FROM pg_class WHERE relkind = 'S';

How the filter works. Here relkind — the object-kind code stored per catalog row — marks what each row is: tables carry 'r', indexes 'i', and sequences 'S'. The WHERE relkind = 'S' clause keeps only catalog rows whose object kind is a sequence. Without that filter the query would return tables, indexes, and every other stored object too. Running it against the working database returned all thirteen lists stored there, including ones behind other tables such as accounts and employees entries.

Scope: The catalog shows every sequence in the current database — including helper lists behind SERIAL columns and other tables you did not build by hand. It never shows counters from a different database. The thirteen-count result belongs to the demo database; your own count will differ.

12.11.2 Browsing in the Graphical Tool

The same thirteen lists appear by browsing to the database, then schemas, then sequences. A database with no lists shows an empty folder there. Both paths report the same set; the query suits scripts while browsing suits a fast visual check.

Recap: pg_class plus the 'S' kind filter lists every counter in one query, and the browser shows the same set by clicking. Next, one counter can feed two tables at once.

In daily production work, catalog queries like this one power stock-takes and cleanups, where teams list every auto-counter before a move or a release. Cross-system equivalents: Snowflake exposes SHOW SEQUENCES and an INFORMATION_SCHEMA.SEQUENCES view instead of pg_class, while MySQL has no standalone sequence objects at all — its counters hide inside AUTO_INCREMENT columns, so the stock-take there queries column metadata instead.

12.11.3 Worked Example

Goal: List every sequence in the working database two ways and count thirteen.

  1. Run SELECT sequence_name FROM pg_class WHERE relkind = 'S';.
  2. Count the returned rows — thirteen lists.
  3. Browse to the database, then schemas, then sequences in the tool.
  4. Confirm the same thirteen names appear.

Result: both paths agree on the full set of thirteen lists. Sense-check: serial-backed tables each contribute one hidden list, so the count exceeds the handful built by hand — the extras are the helpers behind accounts, employees, and similar tables.

12.11.4 Student Questions and Answers

Q: What does relkind = 'S' mean in the listing query?

A: It is a kind filter that keeps sequences and drops other stored objects. Each catalog row carries an object-kind code, and 'S' marks sequences, so the filter keeps only those rows.

12.12 Sharing One Sequence Between Two Tables

12.12.1 Why Share a Single List

Hook: Apples go in one table, mangoes in another — but headquarters wants one unbroken numbering run across both. How can two tables draw from the same ticket roll?

Two tables sometimes need numbers from one shared counter — for linked records, for cross-table references, or for any case where a number must be unique across both tables at once. One list feeding two defaults gives exactly that: each handout goes to exactly one row in exactly one table, so no number ever appears twice.

The shared-counter contract. Both columns carry the default:

\[ DEFAULT = nextval(\text{'common\_fruits\_seq'}) \]

Since every draw advances the single stored position, the apple that takes 100 moves the counter before the mango draws, so the mango receives 101. Uniqueness holds across the union of both tables — but neither table alone has a gap-free run, because the other table keeps interleaving its own draws.

12.12.2 Building the Shared List and Both Tables

First build the shared counter starting at 100:

CREATE SEQUENCE common_fruits_seq START WITH 100;

Refresh the sequences section and confirm common_fruits_seq is listed. Then point both table defaults at it:

CREATE TABLE apples (
    fruit_id INT DEFAULT nextval('common_fruits_seq') NOT NULL,
    fruit_name VARCHAR(50)
);

CREATE TABLE mangoes (
    fruit_id INT DEFAULT nextval('common_fruits_seq') NOT NULL,
    fruit_name VARCHAR(50)
);

Opening either column's properties shows the default on both, confirming the shared link. Note what is missing on purpose: no OWNED BY, because one list cannot be owned by two tables — ownership stays unset so neither table's removal drags the shared counter away unexpectedly.

Scope: The shared counter guarantees cross-table uniqueness, not per-table order: apples alone may read 100, 102, 105 while mangoes hold the numbers in between. Never attach OWNED BY to a shared list — dropping one table would delete the counter out from under the other. And never cycle a shared key counter, or both tables will eventually collide on reused numbers.

Recap: One list plus two nextval defaults yields one unbroken numbering run across both tables. Next, a text default turns bare numbers into prefixed IDs like ID1.

12.12.3 Worked Example

Goal: Prove the two tables draw from one shared counter.

  1. Create common_fruits_seq starting at 100.
  2. Create apples and mangoes with the defaults shown above.
  3. Run INSERT INTO apples (fruit_name) VALUES ('Big Apple');.
  4. Run SELECT * FROM apples; — fruit_id is 100.
  5. Run INSERT INTO mangoes (fruit_name) VALUES ('Big Mango');.
  6. Run SELECT * FROM mangoes; — fruit_id is 101, since the shared counter had already moved past 100.

Result: the apple took 100 and the mango took 101 from the same list, so the counter is truly shared. Sense-check: inserting a second apple next would yield 102, confirming the single counter keeps climbing no matter which table draws.

12.12.4 Student Questions and Answers

Q: How can two tables share one sequence?

A: Point both defaults at one shared counter list with DEFAULT nextval('common_fruits_seq'). Each insert in either table then draws the next number from that one shared counter, so the apple takes 100 and the mango takes 101 in turn.

12.13 Alphanumeric Sequences

12.13.1 The Problem With Plain Numbers

Hook: The support team wants ticket IDs like ID1, ID2, ID3. Can a sequence print letters?

Out of the box every sequence hands out bare numbers only: 1, 2, 3, and nothing else. But real ID schemes often need a text prefix, such as ID1, ID2, ID3. Since no sequence option prints letters, the fix pairs a plain numeric list with a text-building column default. The division of labor is strict: the sequence counts, the default formats.

12.13.2 Pairing a Prefix With nextval

Letters come from the column default joining the fixed prefix: the pattern is always 'PREFIX' || nextval('seq')::TEXT — fixed text, glued with ||, to the next number cast to text. Memorize that shape and you can mint any prefixed scheme.

The walkthrough first showed the default path: a contacts table with contact_id SERIAL PRIMARY KEY auto-builds contacts_contact_id_seq, and inserts for the first two contacts yield 1 and 2. Then it rebuilt the scheme from scratch for the prefixed form.

Step one drops the old table and builds a plain list:

DROP TABLE contacts;
CREATE SEQUENCE table_seq;

Refresh the sequences section and confirm table_seq is listed. Step two builds the table with a text column whose default glues the prefix to the next number:

CREATE TABLE contacts (
    contact_id TEXT NOT NULL DEFAULT 'ID' || nextval('table_seq')::TEXT,
    contact_name VARCHAR(150)
);

Reading the default expression. The default reads as: take the fixed text 'ID', convert the next list value to text with ::TEXT, and join them with || (the string-join operator). For the first draw the arithmetic is:

\[ \text{'ID'} + \text{str}(1) = \text{'ID1'} \]

The column must be TEXT (not integer) because its values mix letters and digits. Step three ties the list lifetime to the column:

ALTER SEQUENCE table_seq OWNED BY contacts.contact_id;

Reopen the column properties and the definition panel shows the text type with the prefix-plus-nextval default in place.

Scope: Prefixed IDs are strings, not numbers: they sort as text ('ID10' sorts before 'ID2'), they cannot be used in arithmetic, and range filters need care. The numeric list underneath still counts 1, 2, 3 — only the visible label carries the prefix.

Pitfalls: Two traps: declaring the ID column as integer (an integer column cannot hold 'ID1', so the insert fails — the column type must switch to text), and forgetting OWNED BY (dropping the contacts table then orphans table_seq in the catalog).

Recap: Sequences count, defaults format: 'ID' || nextval('table_seq')::TEXT mints ID1, ID2, ID3 with no insert-time code. That closes the lecture's arc from bare counters to human-friendly keys.

12.13.3 Worked Example

Goal: Mint prefixed IDs ID1 and ID2 on insert.

  1. Run DROP TABLE contacts; and CREATE SEQUENCE table_seq;.
  2. Create contacts with the prefixed default shown above.
  3. Run ALTER SEQUENCE table_seq OWNED BY contacts.contact_id;.
  4. Run INSERT INTO contacts (contact_name) VALUES ('Adnan');.
  5. Run SELECT * FROM contacts; — contact_id is ID1, since \(\text{'ID'} + \text{str}(1) = \text{'ID1'}\).
  6. Insert a second contact and query again — contact_id is ID2.

Result: each insert mints the next prefixed ID with no extra code at insert time. Sense-check: the numeric tails run 1, 2 in order, confirming the plain list underneath counts normally while the default adds the letters.

12.13.4 Student Questions and Answers

Q: Can a sequence itself store values like ID1?

A: No. Sequences hold numbers only, and the letters come from the default. The column default joins a fixed prefix to each numeric handout.

Q: Why must the prefixed ID column be text?

A: Because its values mix letters and digits, so they need a text column type. An integer column cannot hold 'ID1', so the column type switches to text while the counting still comes from the numeric list.

Exam Guidance Summary

No mark split, question pattern, or topic weight was stated anywhere in the source, so there is nothing to memorize on that front. The best preparation is hands-on: build a plain list, advance it with nextval, read it with currval, jump it with setval, restart it with ALTER SEQUENCE, and link it to a table default. Practice the exact-value restart with setval(..., false) until the difference from the default skip feels automatic — the default hands out \(V + 1\) while false hands out exactly \(V\). Rehearse the two-step table link — create with OWNED BY, then SET DEFAULT nextval(...) — plus the shared-list and prefixed-ID variants, since those combine every idea in one task. Expect to explain CYCLE versus NO CYCLE with the coupon case, and to read the type ranges (smallint \(-32768\) to \(+32767\), integer to about \(\pm 2.1 \times 10^9\), bigint to about \(\pm 9.2 \times 10^{18}\)) when asked why a smaller type was picked.

Key Industry Applications

Serial-backed ID columns number users, orders, contacts, and tickets in production systems with zero insert-time code — the default draws the next value on every insert. Shared counters hand out cross-table unique numbers for linked records such as fruit batches split across tables, where one list feeds two defaults so no number repeats. Prefixed IDs like ID1 and ID2 give human-friendly keys for contacts and support records by gluing a fixed prefix to each numeric handout. Falling bounded lists with NO CYCLE model limited pools such as monthly coupons counting 100 down to 1 and then refusing more once the pool is empty. Catalog queries over pg_class back stock-takes of every auto-counter before moves and releases, returning each list whose kind code is 'S'. The graphical administration tool pgAdmin supports one-off edits of start, step, bounds, cache, and cycling for teams that prefer clicking over scripting, while repeatable setups stay in versioned SQL scripts.
