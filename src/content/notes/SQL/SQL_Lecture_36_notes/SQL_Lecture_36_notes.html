36.1 Set-Based Retrieval and the Row-by-Row Problem

Can you execute a standard SQL query and ask the database engine to pause at row 14, jump ahead 3 rows, or step back 5 rows? Standard SQL queries operate on whole collections of data at once, returning an entire batch in one move rather than stepping through records one by one.

In relational database systems, SQL is founded on relational algebra. When a query runs, the database engine scans the requested tables, evaluates filter predicates, and delivers the matching records together as a single unified result set. That result set might contain thousands of rows, exactly one row, or zero rows. Crucially, the relational engine treats the result as an unordered mathematical bag or set. It does not provide an active, client-navigable row pointer inside a plain retrieval statement.

Think of set-based retrieval like receiving a sealed tray of files delivered to your desk. You receive the entire tray all at once. If you need to inspect the third document, mark it, flip back to the first document to verify a reference, and then discard the fifth document, the tray itself does not do this work for you. You need a finger or a bookmark to track your current position across the files. In database programming, a cursor acts as that movable bookmark.

The tension between set-based relational operations and row-at-a-time procedural processing is known in computer science as the impedance mismatch. While the database engine is optimized to process sets in bulk, host applications and complex business rules often require sequential, row-by-row decisions.

36.1.1 Mathematical Formulation of Result Sets

The core verbal principle is that a query produces a result set as filtered set of table rows. We begin with a database relation, evaluate a selection predicate across every tuple, and return the set of all tuples that satisfy that predicate.

Formally, let \(T\) denote the relation (table), which is a set or multiset of tuples: \[ T = \{r_1, r_2, \dots, r_m\} \] where each tuple \(r \in T\) represents a single row consisting of an attribute mapping over a defined schema.

Let \(P: T \to \{\text{true}, \text{false}\}\) be the selection predicate defined in the WHERE clause. The resulting relation \(R\) produced by the query is defined in set-builder notation as: \[ R = \{r \in T \mid P(r)\} \]

Here:

  • \(T\) is the source table (such as the movies table).
  • \(r\) is an individual tuple or row within the table.
  • \(P(r)\) is the boolean filter condition evaluated on row \(r\).
  • \(R\) is the final result set handed back to the caller.
  • \(n = |R|\) is the cardinality (row count) of the result set, where \(n \ge 0\).

When \(n = 0\), the result set is the empty set: \[ R = \emptyset \] In pure relational theory, \(R\) has no intrinsic ordering unless an explicit ORDER BY clause imposes a permutation. Even with an ORDER BY clause, the engine emits the entire ordered sequence as a bulk stream. Standard SQL does not provide interactive positional operators like FIRST, NEXT, or PRIOR directly on the SELECT statement itself. To establish a navigable position \(p\), where \(p \in \{1, 2, \dots, n\}\), a cursor must be opened over the result set.

36.1.2 Worked Examples: Full Scan and Empty Result Sets

The following examples demonstrate how the same query construct handles full table sets and empty match sets, highlighting the need for row-level position tracking.

Example 1: Full movies scan then empty movie id filter.

Consider a database table named movies containing film catalog data with columns movie_id (integer primary key), movie_name (text), release_date (date), and movie_length (integer minutes).

Step 1: The full table scan. We execute a query without any restrictive predicate:

SELECT * FROM movies;

Here, the filter condition evaluates to true for all rows: \[ P(r) = \text{true}, \quad \forall r \in T \] The engine scans the entire storage relation \(T\). If the table stores 53 movies, the resulting set \(R\) contains all 53 tuples: \[ |R| = 53 \] The database engine transmits all 53 rows to the client buffer in one operation. The result set empty match movies test is not met here because rows exist.

Step 2: The empty match filter. Next, we run a query targeting a specific non-existent record:

SELECT * FROM movies WHERE movie_id = 1000;

Here, the predicate is: \[ P(r) = (r.\text{movie\_id} = 1000) \] The storage engine evaluates the predicate across all records. Because the highest identifier in the sample database is below 1000, no row satisfies the condition: \[ R = \{r \in T \mid r.\text{movie\_id} = 1000\} = \emptyset \] The engine returns an empty result set with cardinality: \[ |R| = 0 \] This demonstrates that standard retrieval statements return sets of arbitrary size, from complete tables down to zero rows, governed strictly by the filter predicate.

Step 3: The row-by-row navigation gap. Suppose an application client receives the 53 rows from the full scan and now needs to execute the following sequence:

  1. Inspect row 1.
  2. Read row 2 and evaluate an external API check.
  3. Step backward to row 1 to modify a status flag based on row 2's outcome.
  4. Advance to row 5.

A plain SELECT statement cannot perform this navigation. Standard SQL provides no syntax such as SELECT NEXT or SELECT PRIOR 5 over an existing query execution. The client either has to load all 53 records into client-side RAM or declare a database cursor with a movable pointer \(p \in [1, n]\) to traverse the rows.

Common Pitfalls:

  1. Confusing Row Numbers with Identity: Believing that row 1 will always be the same row across separate query executions without an explicit ORDER BY clause. Database engines return rows according to physical disk layout or parallel scan threads unless an ordering key is established.
  2. Defaulting to Row-by-Row Loops: Using a cursor to perform simple transformations or filters that could be accomplished 100 times faster with a single set-based UPDATE or WHERE clause.
  3. Ignoring Empty Result Sets: Assuming a cursor will always fetch at least one row, leading to null pointer exceptions or improper loop initialization when a query matches zero rows.

36.1.5 Student Questions and Answers

Q: With a plain SELECT, how do I fetch the first row, then move to the next row or back five rows inside the same result?

A: A plain SELECT cannot do that. It executes declaratively and returns the whole matching set at once. To step forward, step back, or grab a small group of rows interactively, you must encapsulate the query inside a cursor. The cursor creates an active server-side pointer that allows you to step through rows sequentially or arbitrarily using directional fetch commands.

36.1.6 Real-World Applications and Field Placement

In enterprise database engineering, set-based operations are the default choice for data transformations, reporting queries, and high-throughput transaction processing. However, real-world batch data-change passes over large result sets frequently require procedural coordination. For instance, in financial payroll systems, an application might fetch five payroll records, calculate variable tax deductions using external payroll microservices, update the salary ledgers, and then step back to re-verify an audit hash before committing.

Procedural host environments such as Python, Java, Go, and legacy systems in COBOL or Fortran operate natively on sequential collections and arrays. Cursors provide the vital bridge connecting the set-based relational database engine to these row-at-a-time host environments.

Recap & Bridge: A standard SQL query returns an entire result set defined by \(R = \{r \in T \mid P(r)\}\), with no built-in mechanism to navigate between individual records. When business requirements demand sequential row inspection, procedural languages step in to manage ordered row-level logic.

36.2 Procedural and Non-Procedural Languages

Why do database developers combine declarative SQL with procedural code? If SQL can filter and aggregate millions of records with a single query, why do we need loops, conditional branching, and temporary variables?

In computer programming, languages generally fall into two broad execution models: declarative (non-procedural) and imperative (procedural). A non-procedural language specifies what result is desired while leaving the underlying algorithms, access paths, and execution sequence entirely to the database optimizer. Standard SQL is the quintessential non-procedural language. Conversely, a procedural language specifies what to do and how to do it step by step, dictating an explicit sequence of instructions, variable assignments, and flow control.

Think of it like handing over a tray of files analogy for set handoff. SQL acts as the research clerk who gathers all relevant documents from the archives and fills a physical tray. The clerk hands the whole tray to your desk at once. A procedural program then sits at the desk, picks up file one, inspects the date, stamps approval, picks up file two, detects a missing invoice, flags it for deletion, and moves systematically through the stack. SQL fills the tray; the procedural language conducts the orderly, step-by-step processing.

Because relational engines work on whole sets while applications frequently need row-by-row procedural sequence array host logic, database vendors build procedural extensions directly into their database engines.

36.2.1 Mathematical Formulation of Set-to-Sequence Mapping

The transition from a declarative query to a procedural program represents a mathematical mapping from an unordered set (or multiset) of tuples into an ordered sequence or indexed list.

Let \(R\) be the relational result set defined in Section 36.1: \[ R = \{r \in T \mid P(r)\} \] where \(|R| = n\). In pure set theory, elements of \(R\) have no fixed positional index.

When a procedural language opens a cursor over \(R\), it imposes a bijective indexing function \(\pi: \{1, 2, \dots, n\} \to R\), transforming the set into an ordered tuple sequence: \[ L = [r_1, r_2, \dots, r_n] \] where each row \(r_i = \pi(i)\) occupies a discrete position \(i \in \{1, 2, \dots, n\}\).

The procedural execution state can be modeled as a state machine: \[ S_i = \langle i, \sigma_i, \text{action}(r_i) \rangle \] Here:

  • \(L\) is the ordered sequence or list of rows exposed to the procedural runtime.
  • \(i\) is the current step index, with \(1 \le i \le n\).
  • \(\sigma_i\) represents the program memory state (variables, flags, accumulators) at step \(i\).
  • \(\text{action}(r_i)\) represents an imperative operation applied to row \(r_i\), such as updating a status field, calling a web service, or appending to an output buffer.

The procedural runtime dictates the order of step index \(i\): advancing forward (\(i \leftarrow i + 1\)), jumping to arbitrary indices, or terminating early based on intermediate state checks.

36.2.2 Worked Examples: Procedural Control Flows

The following examples highlight scenarios where declarative SQL alone is insufficient and procedural orchestration is required.

Example 1: Dependent multi-step data modifications. Consider a workflow that must process customer order cancellations:

  1. SELECT all pending orders older than 30 days into a cursor.
  2. For each order row \(r_i\):
  • Check an external inventory service to verify if items were restocked.
  • If restocked, INSERT an audit record into restock_log.
  • UPDATE the order status to 'CANCELLED'.
  • If the customer had VIP status, INSERT a loyalty credit coupon into customer_promos.
  • If the total amount was zero, DELETE the stale draft order.

Each verb executes in turn. Step \(k+1\) depends directly on the result of step \(k\). Plain SQL cannot easily branch across heterogeneous external dependencies without procedural control logic.

Example 2: Array hand-off to host languages. A database query pulls a candidate set of 1,000 film records from PostgreSQL. The result set is passed to a host program (such as Python, PHP, Java, or legacy business environments in COBOL and Fortran) as an array or collection of row objects.

  • In Python:
  cursor.execute("SELECT movie_name, release_date FROM movies")
  for row in cursor.fetchall():
      formatted = clean_title(row[0])
      push_to_elastic(formatted, row[1])
  • In COBOL / Fortran: The host program defines a fixed record structure, steps through the retrieved array using indexed memory offsets, applies formatting rules, and submits follow-up transactional writes to the mainframe database.

Example 3: Declarative "what" versus procedural "how".

  • Declarative (SQL): SELECT AVG(movie_length) FROM movies WHERE release_date >= '2000-01-01';

You specify what value you want (the average length). The optimizer chooses whether to use an index scan, a parallel sequential scan, or a hash aggregate.

  • Procedural (PL/pgSQL):

Initialize total := 0; count := 0; Loop through rows, adding each length to total and incrementing count. Compute avg := total / count; You specify every operational step and memory allocation manually.

36.2.6 Real-World Applications and Industry Placement

Modern software architectures balance declarative retrieval with procedural processing daily. In microservice ecosystems, a high-performance database query pulls a candidate set of customer accounts. A procedural service written in Python, Go, or Java consumes that array, performs credit scoring, validates fraud models against external REST APIs, and issues targeted transactional updates back to the database.

36.3 Cursor Lifecycle of Declare Open Fetch Close

What happens behind the scenes on the database server when you declare a cursor versus when you open it? Many developers assume declaring a cursor immediately queries the disk and locks table rows. In reality, declaring merely registers an execution plan; the actual data movement happens during the lifecycle stages that follow.

A database cursor is not a static object; it is an active server-side control structure that progresses through four strictly ordered lifecycle phases: Declare, Open, Fetch, and Close. Mastering this state progression is essential for both correct procedural programming and sound database memory management.

A reliable memory hook to remember these four verbs in order is: name it, fill it, read it, free it.

  1. Declare (Name it): Define the cursor identifier and attach it to a specific SELECT statement.
  2. Open (Fill it): Execute the query, evaluate parameters, and allocate server working memory.
  3. Fetch (Read it): Retrieve the current record into target variables and reposition the cursor pointer.
  4. Close (Free it): Release the temporary result set and return working memory back to the database engine.

Once a cursor is declared, it can be opened, fetched to completion, closed, and then reopened multiple times within the same procedural scope to re-evaluate the query against the latest table data.

36.3.1 Mathematical State-Machine Formulation

The cursor lifecycle can be formalized as a finite state automaton \(\mathcal{M} = \langle S, \Sigma, \delta, s_0, F \rangle\).

The state space consists of four discrete states: \[ S = \{\text{UNINITIALIZED}, \text{DECLARED}(Q), \text{OPEN}(R(Q), p), \text{CLOSED}(\emptyset)\} \]

The state transition function \(\delta: S \times \Sigma \to S\) is defined by the following formal rules: \[ \begin{aligned} \delta(\text{UNINITIALIZED}, \text{DECLARE}(Q)) &= \text{DECLARED}(Q) \\ \delta(\text{DECLARED}(Q), \text{OPEN}(\theta)) &= \text{OPEN}(R(Q, \theta), p_0) \\ \delta(\text{OPEN}(R, p), \text{FETCH}(d)) &= \text{OPEN}(R, p') \\ \delta(\text{OPEN}(R, p), \text{CLOSE}) &= \text{CLOSED}(\emptyset) \\ \delta(\text{CLOSED}(\emptyset), \text{OPEN}(\theta')) &= \text{OPEN}(R(Q, \theta'), p_0) \end{aligned} \]

Here:

  • \(Q\) represents the declarative SQL query specification.
  • \(\theta\) represents the input parameter vector evaluated at open time.
  • \(R(Q, \theta)\) is the active result set relation instantiated in server memory, with cardinality \(n = |R|\).
  • \(p\) is the positional coordinate of the cursor pointer.
  • \(p_0\) is the initial pointer position parked immediately before the first row (commonly modeled as index \(p = 0\)).
  • \(d\) is the fetch directional displacement (such as NEXT or PRIOR), producing new position \(p'\).
  • \(\emptyset\) denotes the null store where working buffers and server locks are released.

Calling FETCH on a cursor in the DECLARED or CLOSED state raises a runtime exception. Similarly, issuing OPEN on an already OPEN cursor triggers an error in standard SQL environments.

36.3.2 Worked Examples of the Lifecycle Stages

The following examples trace the internal state of the server during each lifecycle stage.

Example 1: Declare performs zero table I/O. Consider the declaration:

DECLARE cur_movies CURSOR FOR SELECT * FROM movies;

When this line executes, the PL/pgSQL parser registers the name cur_movies, verifies table and column identifiers against system catalogs, and stores the parse tree. No disk I/O occurs, no table blocks are read into buffer cache, and zero rows move. The cursor sits in state \(\text{DECLARED}(Q)\).

Example 2: Open executes the query and allocates memory. When the procedural block executes:

OPEN cur_movies;

The database engine invokes the query planner, binds any runtime parameters, allocates working memory (such as PostgreSQL work_mem), and prepares the result set \(R\). The pointer is initialized to \(p_0 = 0\) (before the first tuple). Server resources are actively held from this instant.

Example 3: Fetch advances the pointer and retrieves data. Suppose the result set contains \(n = 3\) films:

  1. FETCH NEXT FROM cur_movies INTO v_movie;

Pointer advances: \(p \leftarrow 0 + 1 = 1\). Tuple \(r_1\) is copied into variable v_movie. The status flag FOUND becomes TRUE.

  1. FETCH NEXT FROM cur_movies INTO v_movie;

Pointer advances: \(p \leftarrow 1 + 1 = 2\). Tuple \(r_2\) is copied. FOUND remains TRUE.

  1. FETCH NEXT FROM cur_movies INTO v_movie;

Pointer advances: \(p \leftarrow 2 + 1 = 3\). Tuple \(r_3\) is copied. FOUND remains TRUE.

  1. FETCH NEXT FROM cur_movies INTO v_movie;

Pointer advances beyond end of set: \(p \leftarrow 4 > n\). No row is retrieved. The engine sets NOT FOUND = TRUE (or FOUND = FALSE).

Example 4: Close frees memory, preparing for safe reopen.

CLOSE cur_movies;

The engine deallocates the working memory buffer, releases temporary spool files, and invalidates pointer \(p\). If subsequent code issues:

OPEN cur_movies;

The cursor re-enters state \(\text{OPEN}\), executing a fresh query snapshot against the base table. Any rows inserted or committed by concurrent transactions since the previous close are now visible.

36.3.3 Cross-Database Cursor Lifecycle Variations

While the Declare-Open-Fetch-Close pattern is standard, different database engines impose unique lifecycle requirements:

DBMS Lifecycle Steps Key Dialect Differences
PostgreSQL DECLARE \(\to\) OPEN \(\to\) FETCH \(\to\) CLOSE Unbound refcursor can be passed between functions and across transactions if created WITH HOLD. Cursors close automatically on transaction commit unless held.
MySQL DECLARE \(\to\) OPEN \(\to\) FETCH \(\to\) CLOSE Cursors must be declared strictly after variable declarations and before condition handlers in stored programs. MySQL cursors are forward-only and read-only.
Oracle CURSOR ... IS \(\to\) OPEN \(\to\) FETCH \(\to\) CLOSE Oracle provides explicit cursor attributes: %ISOPEN (checks if open), %FOUND (last fetch had row), %NOTFOUND (fetch was empty), and %ROWCOUNT (cumulative rows fetched).
SQL Server (T-SQL) DECLARE \(\to\) OPEN \(\to\) FETCH \(\to\) CLOSE \(\to\) DEALLOCATE Five-step lifecycle! CLOSE releases the active result set and locks, but retains the cursor definition. DEALLOCATE is mandatory to permanently remove the cursor reference from memory.
Snowflake DECLARE \(\to\) OPEN \(\to\) FETCH \(\to\) CLOSE Supported in Snowflake Scripting. Alternatively, FOR <record> IN <cursor> DO ... END FOR manages Open, Fetch, and Close automatically.

Scope & Assumptions: A cursor's result set is evaluated according to the transaction isolation level of the host session. In Read Committed isolation, opening a cursor takes a snapshot of the committed data at the exact moment of the OPEN call. Rows modified after the OPEN statement will not be seen during subsequent FETCH commands of that active cursor instance.

36.3.5 Student Questions and Answers

Q: Does declare already pull data from the table?

A: No. The declare stage only defines the cursor identifier, verifies the query syntax, and establishes parameter specifications. No disk I/O occurs and no data moves into memory until you issue the explicit OPEN command. Data access happens incrementally during FETCH, and working memory is released upon CLOSE.

36.3.6 Practical Engineering Tips and Resource Management

In production database systems, cursors consume dedicated memory inside the database server process. When building batch extraction jobs:

  • Always ensure that every code path that opens a cursor contains a corresponding CLOSE command. In languages with exception handling, place the CLOSE statement in a FINALLY block or exception trap.
  • In SQL Server (T-SQL), remember to issue both CLOSE and DEALLOCATE to avoid ghost cursor structures accumulating in memory.
  • When processing large datasets in PostgreSQL, consider whether an unbound refcursor returned to a client application (which fetches chunks of 500 rows at a time) is preferable to buffering all records in client RAM.

36.4 Creating Cursors in PostgreSQL

Can a single cursor variable point to completely different queries during the execution of a function, or must every cursor be permanently hardcoded to one specific SQL statement? PostgreSQL supports both patterns, giving engineers flexibility between static query optimization and dynamic query redirection.

In PostgreSQL and PL/pgSQL, cursors are created during the DECLARE section of a block or function. There are two primary architectural styles for cursor creation:

  1. Unbound Cursor (REFCURSOR): Declares a generic cursor variable that carries no predefined SQL query. The query is attached dynamically at execution time when the cursor is opened.
  2. Bound Cursor (CURSOR FOR query): Binds a unique cursor identifier directly to a specific SELECT statement at declaration time, optionally specifying parameter arguments and scrollability constraints.

Think of the distinction like shipping containers. An unbound refcursor is an empty, generic container. You can load it with cargo from warehouse A today, and later load it with completely different cargo from warehouse B. A bound cursor is a specialized, refrigerated container permanently configured and labeled for one specific route; it knows exactly what cargo it carries, though you can still adjust the destination temperature using input parameters.

36.4.1 Mathematical Formulation of Bound and Unbound Cursors

In formal programming language semantics, an unbound cursor represents a polymorphic reference pointer, whereas a bound cursor represents an evaluated triple comprising a name identifier, a query expression, and a parameter schema.

We define the bound cursor as name query params triple: \[ C_{\text{bound}} = \langle \text{identifier}, Q, \Theta \rangle \] where:

  • \(\text{identifier}\) is the unique name of the cursor within the transaction session.
  • \(Q\) is the declarative query expression SELECT ... FROM ... WHERE ....
  • \(\Theta = \langle \theta_1: \tau_1, \theta_2: \tau_2, \dots, \theta_k: \tau_k \rangle\) is an ordered vector of formal parameters, where \(\theta_j\) is a parameter variable and \(\tau_j\) is its PostgreSQL data type.

For an unbound cursor, the query and parameter bindings are undefined during declaration: \[ C_{\text{unbound}} = \text{refcursor} \]

#### Scrollability Constraints The cursor declaration specifies how pointer coordinate \(p_t\) may transition at step \(t+1\):

  • Under NO SCROLL (the default behavior):

\[ p_{t+1} \ge p_t \] The pointer can only advance monotonically forward.

  • Under SCROLL:

\[ p_{t+1} \in \{1, 2, \dots, n\} \] The pointer can jump to any arbitrary valid row index within the cardinality \(n = |R|\), permitting backward traversing (PRIOR, BACKWARD) and absolute index jumps (FIRST, LAST, ABSOLUTE).

36.4.2 Creation Style One: Refcursor Variable

The syntax to declare an unbound cursor is:

DECLARE
  cur_all_movies REFCURSOR;

Here:

  • cur_all_movies is the variable identifier.
  • REFCURSOR is the built-in PostgreSQL data type representing a cursor reference.

An unbound REFCURSOR variable stores a string reference to an underlying server cursor portal. It can be passed as an argument between PL/pgSQL functions or returned directly to an external client (such as a Python or Java application) across transaction boundaries. At the point of declaration, no query is executed and no query text is associated with the variable.

36.4.3 Creation Style Two: Bound Cursor and Column Projection

A bound cursor attaches a query directly to the cursor identifier:

DECLARE
  cur_all_movies CURSOR FOR SELECT * FROM movies;

While writing SELECT * is syntactically legal, production database standards strongly discourage wildcards in cursor definitions.

Star Query Warning on Wide Tables: Avoid declaring cursors with SELECT * FROM table. On wide enterprise tables containing dozens of columns, large text descriptions, JSONB payloads, or binary objects (TOAST data), a star query forces the database engine to pull all column attributes into the cursor working memory. This creates severe memory strain, exhausts server work_mem, triggers disk-based temporary file spilling, and increases serialization overhead. Always specify an explicit, minimal projection list:

DECLARE
  cur_all_movies CURSOR FOR
    SELECT movie_name, movie_length FROM movies;

36.4.4 Creation With Query Parameters

A bound cursor can accept formal arguments in parentheses immediately following the cursor name.

Worked Example: Year filtered cursor with custom year param.

Consider an application requirement to inspect films released during a specific calendar year. Rather than declaring multiple cursors or assembling raw SQL strings, we define a parameterized bound cursor.

Step 1: The parameterized cursor declaration.

DECLARE
  cur_movies_by_year CURSOR (custom_year integer) FOR
    SELECT movie_name, movie_length
    FROM movies
    WHERE EXTRACT(YEAR FROM release_date) = custom_year;

Step 2: Analysis of components.

  • cur_movies_by_year: The unique cursor identifier.
  • (custom_year integer): The parameter signature \(\Theta = \langle \text{custom\_year}: \text{integer} \rangle\). The parameter acts as a scoped constant inside the attached query.
  • FOR SELECT ...: The bound query specification \(Q\).
  • EXTRACT(YEAR FROM release_date) = custom_year: The selection predicate \(P(r, \theta)\) that filters rows based on the supplied parameter value.

Step 3: Parameter binding evaluation. When the cursor is later opened with an argument such as 2010: \[ \theta = (\text{custom\_year} \leftarrow 2010) \] The query engine substitutes 2010 into the plan: \[ R = \{r \in \text{movies} \mid \text{EXTRACT}(\text{YEAR FROM } r.\text{release\_date}) = 2010\} \] If the table has 8 movies from 2010, \(|R| = 8\). If reopened with custom_year := 2011, the same cursor structure refills with the 2011 cohort without recompiling the function.

Consider the pointer movement constraints along the discrete row coordinates \([1, n]\):

When NO SCROLL is active, the database engine can stream records from disk or network buffers and immediately discard previously read rows. Common Pitfalls:

  1. Unnecessary SCROLL Specifications: Adding SCROLL to every cursor by habit. This forces the server to buffer the entire result set, creating disk I/O bottlenecks on large datasets when only a forward pass was needed.
  2. Parameter Name Collisions: Naming a cursor parameter identically to an existing column in the table without table qualifying, leading to ambiguous column resolution bugs.
  3. Omitting Variable Semicolons: Omitting the terminating semicolon in the DECLARE section of PL/pgSQL blocks, causing syntax errors at the subsequent BEGIN token.

Exam note: Expect to write the complete cursor header from memory: cursor identifier, optional SCROLL keyword, bracket parameters with data types (param_name data_type), the FOR keyword, and the declarative SELECT statement. Ensure parameter names match identically between the bracket list and the WHERE clause.

These structural conventions ensure that PL/pgSQL can construct unambiguous query plans before the block enters its execution phase.

Recap & Bridge: PostgreSQL supports unbound refcursor variables and bound parameterized cursors formalized as \(C_{\text{bound}} = \langle \text{identifier}, Q, \Theta \rangle\). Once declared, cursors must be opened to evaluate queries and prepare data for retrieval.

36.5 Opening Cursors Bound Unbound and Dynamic

When a cursor opens, where does the data live? Does the database engine load every matching row directly into application memory, or does it construct an isolated server-side query portal? The answer determines how database memory scales under thousands of concurrent users.

The OPEN statement transitions a cursor from an idle definition into an active execution state. When OPEN executes, the database engine compiles the execution plan, evaluates argument expressions, binds parameters into query filters, allocates server-side buffer handles (known in PostgreSQL as a portal), and sets the pointer position immediately before the first tuple.

Think of OPEN like turning the key in an automobile's ignition. Declaring the cursor assembled the mechanical chassis and mapped out the navigation route. However, until you turn the key (OPEN), no electrical power flows, no fuel burns, and the wheels cannot turn. Once the engine starts, the vehicle sits in park with its odometer at zero (\(p = 0\)), ready to advance into traffic on the first tap of the accelerator pedal (FETCH).

PL/pgSQL accommodates three distinct operational opening patterns:

  1. Opening an unbound refcursor with a fixed SQL query.
  2. Opening an unbound refcursor with dynamic SQL generated as text at runtime using EXECUTE.
  3. Opening a bound cursor, passing values into its declared parameter slots.

36.5.1 Mathematical Formulation of Query Binding on Open

The act of opening a cursor evaluates the stored query expression against a parameter vector and instantiates the result relation.

Mathematically, the opening operator maps a cursor handle, a query specification, and a parameter vector into an active server portal: \[ \text{open}(C, Q, \Theta) \to \langle R(Q, \Theta), p_0 \rangle \]

We distinguish three formal evaluation mappings:

#### 1. Bound Cursor Evaluation For a bound cursor \(C_{\text{bound}} = \langle \text{name}, Q, \Theta \rangle\), the query \(Q\) is already fixed. Opening binds runtime arguments \(\vec{a} = \langle a_1, \dots, a_k \rangle\) into \(\Theta\): \[ \text{open}(C_{\text{bound}}, \vec{a}): R = \{r \in T \mid P(r, \vec{a})\}, \quad p \leftarrow 0 \]

#### 2. Unbound Cursor With Fixed Query For an unbound cursor \(C_{\text{unbound}} = \text{refcursor}\), the open statement supplies the declarative query \(Q_{\text{fixed}}\): \[ \text{open}(C_{\text{unbound}}, Q_{\text{fixed}}): R = \{r \in T \mid P_{\text{fixed}}(r)\}, \quad p \leftarrow 0 \]

#### 3. Dynamic Cursor Evaluation via EXECUTE When query text is assembled at runtime, the query string \(S_{\text{dyn}}\) is parsed dynamically, substituting bind parameters \(\vec{u} = \langle u_1, \dots, u_m \rangle\) passed through the USING clause: \[ \text{open}(C_{\text{unbound}}, \text{EXECUTE}(S_{\text{dyn}}, \vec{u})): R = \text{eval}(\text{parse}(S_{\text{dyn}}), \vec{u}), \quad p \leftarrow 0 \]

In all three cases, the initial pointer position is anchored at the origin coordinate \(p_0 = 0\), parked before the first record.

36.5.2 Opening an Unbound Cursor With a Fixed Query

An unbound refcursor variable can be attached to any standard SELECT query when opened.

Worked Example: American directors unbound open with fixed query.

Consider the directors table storing biographical information for film directors with columns: director_id (integer), first_name (varchar), last_name (varchar), date_of_birth (date), and nationality (varchar).

Step 1: Declaration.

DECLARE
  cur_directors_us REFCURSOR;

Step 2: Opening with fixed query.

OPEN cur_directors_us FOR
  SELECT first_name, last_name, date_of_birth
  FROM directors
  WHERE nationality = 'American';

Step 3: Execution mechanics.

  • Prior to this statement, cur_directors_us held no query association.
  • On execution, the engine evaluates the predicate \(r.\text{nationality} = \text{'American'}\).
  • If the table contains 28 American directors out of 100 total directors, the server portal instantiates the 28-row result relation:

\[ R = \{r \in \text{directors} \mid r.\text{nationality} = \text{'American'}\}, \quad |R| = 28 \]

  • To restrict movement to forward-only passes and minimize buffering overhead, NO SCROLL can be specified before FOR:
  OPEN cur_directors_us NO SCROLL FOR
    SELECT first_name, last_name, date_of_birth
    FROM directors
    WHERE nationality = 'American';

36.5.3 Opening an Unbound Cursor With a Dynamic Query

In reporting workflows and administrative utilities, the table name, filtering predicate, or sorting column may only be known at runtime. PL/pgSQL enables dynamic query execution via the EXECUTE clause.

DECLARE
  cur_directors_nat REFCURSOR;
  query_text text;
  filter_country text := 'American';
  sort_field text := 'last_name';
  -- Construct parameterized query string using bind-variable notation
  query_text := 'SELECT first_name, last_name, date_of_birth FROM directors ' ||
                'WHERE nationality = ' || quote_literal(filter_country) ||
                ' ORDER BY ' || quote_ident(sort_field);

  -- Open cursor dynamically
  OPEN cur_directors_nat FOR EXECUTE query_text;
END;

In this syntax:

  • query_text: A text variable storing the dynamically assembled SQL statement.
  • quote_literal(filter_country): Safely sanitizes string literals to prevent SQL injection vulnerabilities.
  • quote_ident(sort_field): Safely sanitizes identifiers (such as column names) that cannot be passed as standard literals.

36.5.4 Opening Bound Cursors With and Without Parameters

A bound cursor already encapsulates its query, so the OPEN statement requires no FOR clause.

#### Opening Without Parameters If the cursor was declared without arguments:

OPEN cur_all_movies;

The engine immediately evaluates the stored query and prepares the cursor portal.

#### Opening With Parameters When opening a parameterized cursor, argument values can be passed positionally or using named parameter syntax (:=):

-- Positional argument binding
OPEN cur_movies_by_year(2010);

-- Named argument binding
OPEN cur_movies_by_year(custom_year := 2010);

Named binding (custom_year := 2010) provides code clarity, especially when cursors accept multiple optional arguments with default values. The query engine substitutes the integer 2010 into the WHERE clause, restricting the cursor to the 2010 movie records.

36.6 Using a Cursor With Fetch and Move

What is the difference between fetching a row and moving across rows in a database cursor? While both instructions alter the active pointer position within the result set, one transfers data across memory buffers while the other executes a zero-copy pointer shift.

Once a cursor is in the OPEN state, the procedural program navigates and inspects records using two primary commands:

  • FETCH: Evaluates a directional offset, updates the pointer coordinate to the target row, and copies the column attributes into target variables or record structures.
  • MOVE: Repositions the internal cursor pointer to the target row without retrieving or copying any attribute data.

Think of the distinction as the pick up file versus slide finger intuition. Imagine standing in front of a cabinet filled with paper folders. Executing FETCH means reaching in, pulling the folder out of the cabinet, opening it, and copying data into your ledger. Executing MOVE means simply sliding your finger along the folder tabs to a new position without lifting a single sheet of paper. When you only need to reposition the pointer or test for existence, MOVE avoids the memory allocation and copying cost of a FETCH.

36.6.1 Mathematical Formulation of Fetch and Move Pointer Updates

The verbal rule is that FETCH performs a pointer update with target copy, while MOVE performs a pointer update alone.

Formally, let \(R = [r_1, r_2, \dots, r_n]\) be the materialized tuple sequence with cardinality \(n = |R|\). Let \(p \in \{0, 1, \dots, n, n+1\}\) be the pointer coordinate, where \(p = 0\) is before the first row and \(p = n+1\) is beyond the last row.

The formal update operators are defined as: \[ \text{fetch}(C, \text{direction}): \quad p \leftarrow \text{shift}(p, \text{direction}), \quad \text{target} \leftarrow r_p \] \[ \text{move}(C, \text{direction}): \quad p \leftarrow \text{shift}(p, \text{direction}) \]

The directional shift function \(\text{shift}(p, \text{dir})\) resolves coordinates as follows:

  • NEXT (default): \(p' = p + 1\)
  • PRIOR: \(p' = p - 1\)
  • FIRST: \(p' = 1\)
  • LAST: \(p' = n\)
  • `ABSOLUTE } k\):

\[ p' = \begin{cases} k & \text{if } k > 0 \\ n + k + 1 & \text{if } k < 0 \\ 0 & \text{if } k = 0 \end{cases} \]

  • `RELATIVE } k\): \(p' = p + k\)
  • `FORWARD } k\): \(p' = p + k \quad (k \ge 0)\)
  • `BACKWARD } k\): \(p' = p - k \quad (k \ge 0)\)

If the resulting coordinate \(p' < 1\) or \(p' > n\), the pointer is positioned out of bounds. In that event, target remains unchanged (or is set to null), and the runtime status variable FOUND is set to FALSE (NOT FOUND is set to TRUE).

36.6.2 Fetch Syntax and Target Variables

PL/pgSQL supports copying fetched data into either an ordered list of scalar variables or a single unified RECORD variable.

Worked Example: Fetch last row into title and date targets.

Consider a cursor cur_all_movies declared with the SCROLL option over the movies table containing 53 film records.

Step 1: Fetching into scalar targets.

DECLARE
  cur_all_movies SCROLL CURSOR FOR
    SELECT movie_name, release_date FROM movies ORDER BY release_date;
  movie_title text;
  movie_release_date date;
BEGIN
  OPEN cur_all_movies;

  -- Jump directly to the final record and copy attributes
  FETCH LAST FROM cur_all_movies INTO movie_title, movie_release_date;

  RAISE NOTICE 'Latest film: % released on %', movie_title, movie_release_date;
  CLOSE cur_all_movies;
END;

Execution trace:

  1. OPEN initializes \(p = 0\) over \(n = 53\) rows.
  2. FETCH LAST evaluates \(\text{shift}(0, \text{LAST}) = 53\). The pointer jumps directly to coordinate \(p = 53\).
  3. The engine copies tuple \(r_{53}\)'s movie_name into movie_title and release_date into movie_release_date.
  4. The notice displays the final movie.

Step 2: Fetching into a RECORD target. Rather than declaring separate scalar variables for every column, a single RECORD variable can receive the entire tuple:

DECLARE
  rec_movie RECORD;
BEGIN
  FETCH PRIOR FROM cur_all_movies INTO rec_movie;
  -- Access fields using dot notation
  RAISE NOTICE 'Prior movie: %', rec_movie.movie_name;
END;

Here, FETCH PRIOR decrements \(p \leftarrow 53 - 1 = 52\), loading row 52 into rec_movie.

36.6.3 Move Syntax for Zero-Copy Pointer Adjustments

When an application needs to skip records, verify that a minimum batch size exists, or rewind the pointer without paying the data serialization cost, MOVE is the optimal tool:

-- Advance one row forward (p <- p + 1)
MOVE cur_all_movies;

-- Jump pointer directly to the final record (p <- n)
MOVE LAST FROM cur_all_movies;

-- Step backward one row from current position (p <- p - 1)
MOVE RELATIVE -1 FROM cur_all_movies;

-- Skip four rows ahead from current position (p <- p + 4)
MOVE FORWARD 4 FROM cur_all_movies;

Because MOVE omits the INTO clause, no string copies or memory allocations occur on the client or procedural stack.

A frequent source of errors in PL/pgSQL is invoking a non-forward directional fetch on a cursor declared without SCROLL. The table below outlines the exact requirements:

Understanding directional movement allows developers to position the cursor at arbitrary records, setting up row-specific mutations.

36.7 Updating and Deleting the Positioned Row

How can you modify or delete the exact database row your cursor is currently inspecting without performing a redundant primary key search or risking a concurrency race condition? SQL provides a specialized clause designed specifically for cursor-positioned mutations: WHERE CURRENT OF.

When a cursor is positioned on a specific record through a previous FETCH command, that row can be altered or deleted directly using the clause:

WHERE CURRENT OF cursor_name;

This clause tells the database engine to resolve the physical storage address (in PostgreSQL, the Tuple Identifier or ctid) of the current row directly from the cursor portal. It bypasses primary key indexing and eliminates the need to execute a secondary SELECT or search filter.

Think of WHERE CURRENT OF like pointing your finger at a specific file folder on your desk and instructing an assistant: "Stamp approval on this exact folder." You do not need to read out the 16-digit serial number, search through the master catalog, and verify the file index again. You act directly where your finger is currently pointing.

Positioned updates and deletions are especially valuable in transactional batch cleaning routines where individual rows are inspected, validated against complex business rules, and conditionally updated in place.

36.7.1 Mathematical Formulation of Positioned Mutations

In relational storage systems, each tuple in relation \(T\) is associated with a physical disk locator \(\text{tid} \in \mathcal{T}\) (known as the Tuple ID or RowID). When a cursor opens over relation \(T\), it maintains a direct reference mapping \(\tau: [1, n] \to \mathcal{T}\) linking pointer coordinate \(p\) to its underlying physical record locator \(\tau(p)\).

We formalize positioned update and delete operators as follows:

#### Positioned Update \[ \text{update}(T, r_p, \Delta): \quad T \leftarrow (T \setminus \{\tau(p)\}) \cup \{\tau(p) \oplus \Delta\} \] where:

  • \(T\) is the base table being modified.
  • \(r_p\) is the row currently addressed at pointer position \(p\).
  • \(\tau(p)\) is the physical tuple identifier of row \(r_p\).
  • \(\Delta\) is the attribute assignment mapping (such as release_date = custom_year_value).
  • \(\oplus\) represents the tuple replacement operation on the storage page.

#### Positioned Delete \[ \text{delete}(T, r_p): \quad T \leftarrow T \setminus \{\tau(p)\} \] The engine removes the physical tuple \(\tau(p)\) from relation \(T\). Following a positioned deletion, the cursor pointer remains anchored at coordinate \(p\), but subsequent operations on the current row must account for the removal.

36.7.2 Worked Examples of Positioned Modifications

The examples below illustrate the complete implementation of positioned updates and deletions in PL/pgSQL.

Example 1: Positioned update. Suppose cursor cur_all_movies is declared with FOR UPDATE and is currently positioned on row 3:

DECLARE
  cur_all_movies CURSOR FOR
    SELECT movie_id, movie_name, release_date
    FROM movies
    FOR UPDATE;
  rec_movie RECORD;
BEGIN
  OPEN cur_all_movies;
  FETCH cur_all_movies INTO rec_movie; -- row 1
  FETCH cur_all_movies INTO rec_movie; -- row 2
  FETCH cur_all_movies INTO rec_movie; -- row 3

  -- Update only row 3 directly in place
  UPDATE movies
  SET release_date = '2025-01-01'
  WHERE CURRENT OF cur_all_movies;

  CLOSE cur_all_movies;
END;

Execution mechanics: The engine resolves the physical disk address of row 3 and writes the new release_date directly to the storage block. Rows 1, 2, and 4 through 53 remain completely untouched.

Example 2: Positioned delete. Suppose an audit check flags row 6 for removal:

-- Step pointer forward to row 6
MOVE ABSOLUTE 6 FROM cur_all_movies;

-- Delete the positioned row
DELETE FROM movies
WHERE CURRENT OF cur_all_movies;

The engine deletes row 6 from the movies table without needing WHERE movie_id = 6.

36.8 Closing Cursors and Resource Handling

What occurs inside the database server when an application opens a thousand cursors in a continuous loop and neglects to close them? In database administration, unclosed cursors are silent memory leaks that consume server working memory, retain row locks, and eventually exhaust system connection resources.

The CLOSE statement terminates the active state of an open cursor and relinquishes all associated server-side resources. The syntax is concise:

CLOSE cursor_name;

When CLOSE executes, the database engine destroys the active portal, releases temporary spool files from disk or memory buffers, and frees any metadata locks held on underlying relations. Closing a cursor does not destroy the cursor definition; the cursor remains declared and can be reopened immediately with identical or modified parameter values.

Think of closing a cursor like checking out of a hotel room. While you occupy the room (OPEN), the hotel cannot reassign the room to anyone else, utilities are active, and operating costs accrue. Checking out (CLOSE) hands back the key, clears the room, and ends the billing. If your business brings you back to town next month, you can check in again (OPEN), but holding onto the room while away wastes hotel capacity.

Because cursor execution holds dedicated memory allocations inside the database process, pairing every OPEN with a guaranteed CLOSE is a fundamental engineering discipline.

36.8.1 Mathematical Formulation of Resource Deallocation and Reopening

Let \(C\) denote an active cursor handle, and let \(M(C)\) represent the working memory (RAM buffers, work_mem, temporary spool blocks) allocated by the database engine to maintain the cursor portal.

When cursor \(C\) is in the OPEN state: \[ M(C) = M_{\text{portal}} + M_{\text{spool}}(n) > 0, \quad p \in [0, n+1] \] where \(n = |R|\) is the cardinality of the result relation.

The CLOSE operator maps the active portal to the empty store \(\emptyset\): \[ \text{close}(C): \quad \text{portal}(C) \leftarrow \emptyset, \quad M(C) \leftarrow 0, \quad p \leftarrow \bot \] where \(\bot\) represents the undefined pointer coordinate.

The cursor definition \(C_{\text{bound}} = \langle \text{identifier}, Q, \Theta \rangle\) remains registered in the procedural symbol table. Consequently, calling reopen invokes the OPEN transition again: \[ \text{reopen}(C, \Theta'): \quad \text{portal}(C) \leftarrow R(Q, \Theta'), \quad p \leftarrow 0 \] where \(\Theta'\) is a new parameter vector. Reopening queries the underlying tables anew, capturing any commits that occurred between CLOSE and the subsequent OPEN.

36.8.2 Worked Examples of Cursor Closure and Reopening

The examples below illustrate proper resource cleanup and safe cursor reuse.

Example 1: Basic close after single traversal.

DECLARE
  cur_all_movies CURSOR FOR SELECT movie_name FROM movies;
  v_title text;
BEGIN
  OPEN cur_all_movies;
  LOOP
    FETCH cur_all_movies INTO v_title;
    EXIT WHEN NOT FOUND;
    -- Process movie title
  END LOOP;

  -- Free server resources immediately upon loop completion
  CLOSE cur_all_movies;
END;

Example 2: Reopening a cursor to process multiple cohorts. A batch routine processes movies year by year using a single parameterized cursor:

DECLARE
  cur_by_year CURSOR (p_year integer) FOR
    SELECT movie_name FROM movies
    WHERE EXTRACT(YEAR FROM release_date) = p_year;
  v_title text;
  yr integer;
BEGIN
  FOR yr IN 2010..2012 LOOP
    OPEN cur_by_year(p_year := yr);
    RAISE NOTICE '--- PROCESSING YEAR % ---', yr;
    LOOP
      FETCH cur_by_year INTO v_title;
      EXIT WHEN NOT FOUND;
      RAISE NOTICE 'Title: %', v_title;
    END LOOP;
    -- Close cursor before next iteration opens it with a new year
    CLOSE cur_by_year;
  END LOOP;
END;

Execution trace:

  1. Iteration 1 (yr = 2010): Opens cursor, fetches 2010 movies, closes cursor. Memory is completely freed.
  2. Iteration 2 (yr = 2011): Reopens the same cursor structure for 2011 movies, walks rows, closes.
  3. Iteration 3 (yr = 2012): Reopens for 2012 movies, walks rows, closes.

This pattern reuses execution plans while keeping peak server memory footprint at the size of a single year's cohort.

36.9 Block That Lists All Movie Names Row by Row

How do you assemble an end-to-end procedural routine that coordinates variable declarations, cursor initialization, iterative row fetching, boundary termination, and output reporting? An anonymous PL/pgSQL block provides the ideal testbed for examining cursor mechanics in action.

An anonymous block (executed with the DO block syntax) allows developers to run procedural scripts directly without storing a permanent function in the database catalog. This complete program ties together all earlier concepts:

  1. Declaring a text accumulator, a record variable, and a bound cursor.
  2. Opening the cursor portal.
  3. Executing an iterative LOOP with FETCH into the record.
  4. Evaluating the EXIT WHEN NOT FOUND guard condition.
  5. Concatenating attributes into the master accumulator.
  6. Closing the cursor and printing the aggregated report using RAISE NOTICE.

Think of this title accumulator loop like stringing beads onto a necklace. You begin with an empty cord (\(\text{output\_text} = \text{''}\)). In each cycle of the loop, your hand reaches into the container (FETCH), verifies that beads remain (EXIT WHEN NOT FOUND), slips a spacer knot onto the string (', '), and slides the next bead into place (|| rec_movie.movie_name). When the container is empty, you tie off the clasp and display the completed necklace (RAISE NOTICE).

36.9.1 Mathematical Formulation of Recurrence Accumulation

The procedural loop formalizes a title accumulator loop over cursor rows, modeling string assembly as a recurrence relation over the sequence of tuples \(L = [r_1, r_2, \dots, r_n]\).

Let \(\text{out}_i\) represent the accumulated string buffer after processing \(i\) records: \[ \text{out}_0 = \epsilon \] \[ \text{out}_i = \begin{cases} t_1 & \text{for } i = 1 \\ \text{out}_{i-1} \mathbin{\Vert} \text{sep} \mathbin{\Vert} t_i & \text{for } 2 \le i \le n \end{cases} \]

where:

  • \(\epsilon\) represents the initial empty string (DEFAULT '').
  • \(t_i = \pi_{\text{movie\_name}}(r_i)\) is the extracted film title attribute of tuple \(r_i\).
  • \(\text{sep}\) is the delimiter string literal (such as ', ' or ' | ').
  • \(\Vert\) is the standard SQL string concatenation operator (||).
  • \(n = |R|\) is the total row count of the result set.

#### Loop Invariant and Termination The loop performs \(n + 1\) fetch evaluations in total:

  • For steps \(i = 1, 2, \dots, n\): FETCH retrieves row \(r_i\), the system status flag FOUND evaluates to TRUE, and the loop executes its body.
  • At step \(i = n + 1\): FETCH attempts to read past the final row. The engine sets FOUND = FALSE and NOT FOUND = TRUE. The condition EXIT WHEN NOT FOUND triggers immediately, breaking the loop before string concatenation occurs.

36.9.2 Declare Section Architecture

The anonymous block requires three distinct variables declared before the execution block begins:

DECLARE
  output_text text DEFAULT '';
  rec_movie RECORD;
  cur_all_movies CURSOR FOR
    SELECT * FROM movies ORDER BY movie_name;

Analysis of declaration components:

  • output_text text DEFAULT '': A variable-length string buffer initialized to empty.
  • rec_movie RECORD: A dynamically typed record structure that adapts its schema to match whatever columns are returned by the cursor query.
  • cur_all_movies CURSOR FOR ...: A bound cursor querying all records from the movies relation, sorted deterministically by title.

36.9.3 Execution Body: Open, Fetch Loop, Close, and Notice

The complete procedural execution body proceeds through a strictly ordered sequence of statements:

Worked Example: Loop fetch titles into accumulator with notice.

BEGIN
  -- 1. Initialize cursor portal and position pointer at p = 0
  OPEN cur_all_movies;

  -- 2. Traverse rows iteratively
  LOOP
    FETCH cur_all_movies INTO rec_movie;

    -- Exit guard: must immediately follow FETCH
    EXIT WHEN NOT FOUND;

    -- String concatenation logic
    IF output_text = '' THEN
      output_text := rec_movie.movie_name;
    ELSE
      output_text := output_text || ', ' || rec_movie.movie_name;
    END IF;
  END LOOP;

  -- 3. Release server portal memory
  CLOSE cur_all_movies;

  -- 4. Emit diagnostic output to client console
  RAISE NOTICE 'ALL MOVIE NAMES: %', output_text;
END;

Execution Trace:

  1. OPEN compiles the query and prepares 53 movie records.
  2. Iteration 1: Fetches "A Clockwork Orange". output_text becomes 'A Clockwork Orange'.
  3. Iteration 2: Fetches "Apocalypse Now". output_text becomes 'A Clockwork Orange, Apocalypse Now'.
  4. Iteration 3: Fetches "Battle Royale". Concatenates title.
  5. ... continues for all 53 films.
  6. Iteration 54: FETCH reaches end-of-file. NOT FOUND becomes TRUE. EXIT terminates the loop.
  7. CLOSE releases memory buffers.
  8. RAISE NOTICE outputs the single combined string containing all 53 movie names to the PostgreSQL message log.

While this procedural loop demonstrates fundamental cursor navigation, production database engineers evaluate whether a declarative set-based equivalent exists:

36.10 Parametric Cursor Function That Finds Star Titles by Year

Can you encapsulate cursor processing inside a reusable, callable database function that accepts runtime parameters and returns a compiled report? In PL/pgSQL, stored functions allow developers to package parameterized cursors into clean, modular database APIs.

In this capstone implementation, we wrap cursor logic into a permanent PostgreSQL stored function named get_movie_names_by_year. The function accepts a single integer input representing a target release year, opens a parameterized cursor to filter films from that year, applies an imperative procedural filter using LIKE '%Star%' to identify titles containing the keyword "Star", and returns a formatted text string containing title and year pairs.

Think of this workflow as a two-stage sifting process. The first stage uses the cursor's WHERE clause to perform a coarse mechanical sift, gathering all films released in the specified calendar year. The second stage uses a fine procedural mesh inside the loop (IF ... LIKE '%Star%') to inspect individual titles, keeping only franchise entries that match the keyword.

During the development of this function, an essential teaching moment occurs: a runtime crash caused by an alias mismatch between the query projection and the record variable field reads. Resolving this issue highlights the strict structural contract between SQL expressions and procedural records.

36.10.1 Mathematical Formulation of Two-Stage Filtering

The function formalizes a year slice then Star title subset filter across the relation \(T\) (movies).

Let \(y \in \mathbb{N}\) denote the input parameter custom_year. The two-stage filtering process is defined as:

#### Stage 1: The Year Slice (Database Optimizer Filter) \[ R_1 = \{r \in \text{movies} \mid \text{yr}(r) = y\} \] where \(\text{yr}(r) = \text{EXTRACT}(\text{YEAR FROM } r.\text{release\_date})\). This filter is pushed down directly to the storage engine through the cursor parameter.

#### Stage 2: The Keyword Subset (Procedural Loop Filter) \[ R_2 = \{r \in R_1 \mid \text{title}(r) \text{ LIKE } \text{'\%Star\%'}\} \] where \(\text{title}(r) = r.\text{movie\_name}\), and the SQL LIKE '%Star%' pattern matches any title containing "Star" at the beginning, middle, or end.

#### Output Formatting Recurrence Let \(\text{out}_k\) represent the formatted text buffer after inspecting \(k\) matching films from \(R_2\): \[ \text{out}_0 = \epsilon \] \[ \text{out}_k = \text{out}_{k-1} \mathbin{\Vert} \text{' | '} \mathbin{\Vert} \text{title}(r_k) \mathbin{\Vert} \text{' : '} \mathbin{\Vert} \text{yr}(r_k) \] The final returned text string concatenates each title and its release year separated by pipe and colon delimiters.

36.10.2 Function Header and Declaration Contract

The function is defined using standard PostgreSQL DDL:

CREATE OR REPLACE FUNCTION get_movie_names_by_year(custom_year integer)
RETURNS text AS
DECLARE
  movie_names text DEFAULT '';
  rec_movie RECORD;
  cur_movies_by_year CURSOR (custom_year integer) FOR
    SELECT movie_name, EXTRACT(YEAR FROM release_date) AS release_year
    FROM movies
    WHERE EXTRACT(YEAR FROM release_date) = custom_year;

Notice the query projection: EXTRACT(YEAR FROM release_date) AS release_year

The Alias Spelling Contract: When a query projects a computed expression (such as a date extraction or mathematical formula), it must assign an explicit column alias using AS alias_name. A PL/pgSQL dynamic RECORD variable inspects the query's column metadata at runtime to establish its field names. If you define the alias as release_year in the query, you must access it as rec_movie.release_year in procedural code. Any discrepancy between the query alias spelling and the procedural field read causes PostgreSQL to abort execution with a runtime missing field exception.

36.10.3 Body Architecture: Open, Filter Loop, Close, and Return

The body orchestrates cursor initialization, procedural keyword testing, and resource cleanup:

BEGIN
  -- Open cursor, passing the function parameter custom_year
  OPEN cur_movies_by_year(custom_year);

  LOOP
    FETCH cur_movies_by_year INTO rec_movie;
    EXIT WHEN NOT FOUND;

    -- Procedural pattern match for titles containing 'Star'
    IF rec_movie.movie_name LIKE '%Star%' THEN
      movie_names := movie_names || ' | ' || rec_movie.movie_name
                     || ' : ' || rec_movie.release_year;
    END IF;
  END LOOP;

  -- Free server memory
  CLOSE cur_movies_by_year;

  -- Return final assembled report
  RETURN movie_names;
END;
LANGUAGE plpgsql;

This clean architecture exemplifies the function year alias Star match structure.

  • Declare: Defines the cursor identifier, parameter signature, scrollability options, and attaches the query plan. Performs zero disk I/O.
  • Open: Compiles the query plan, binds argument values, instantiates the server portal, allocates working buffer memory, and positions pointer coordinate at \(p = 0\).
  • Fetch: Advances the pointer along directional coordinates and copies column values into target variables or records.
  • Close: Destroys the active portal and frees temporary server memory while retaining the cursor declaration for potential reopening.
  1. Creation Syntax Variations:
  • Unbound refcursor: DECLARE cur_name REFCURSOR; (Attached to queries later via OPEN cur_name FOR SELECT ...; or OPEN cur_name FOR EXECUTE ... USING ...;).
  • Bound Cursor: DECLARE cur_name CURSOR FOR SELECT ...;
  • Parameterized Bound Cursor:
     DECLARE cur_name CURSOR (param_name data_type) FOR
       SELECT ... FROM ... WHERE column_name = param_name;
  1. Directional Movement and the SCROLL Rule:
  • Cursors default to NO SCROLL, which permits only forward monotonic progression (NEXT, FORWARD count).
  • SCROLL is mandatory if your routine executes: PRIOR, FIRST, LAST, BACKWARD count, ABSOLUTE count, or negative RELATIVE count.
  • FETCH updates the pointer coordinate and copies data into target variables. MOVE shifts the pointer coordinate with zero memory copy.
  1. Positioned Updates and Deletions (WHERE CURRENT OF):
  • Syntax: UPDATE table_name SET col = val WHERE CURRENT OF cursor_name; and DELETE FROM table_name WHERE CURRENT OF cursor_name;.
  • Requires single-table queries declared with FOR UPDATE.
  • Note engine differences: Supported in PostgreSQL, Oracle, and SQL Server; not supported in MySQL (where cursors are strictly read-only) or in distributed engines (Snowflake, Databricks).
  1. Complete Program Structure (Anonymous Blocks and Stored Functions):
  • Anonymous block layout: DECLARE ... BEGIN OPEN ... LOOP FETCH ... EXIT WHEN NOT FOUND; ... END LOOP; CLOSE ... RAISE NOTICE ... END;.
  • Stored function parameterization: CREATE OR REPLACE FUNCTION func(param int) RETURNS text AS ... LANGUAGE plpgsql;.
  • The Alias Spelling Contract: Ensure column aliases projected in the cursor query match field reads on dynamic RECORD variables identically (AS release_year \(\to\) rec_movie.release_year).

Key Industry Applications

In enterprise software engineering and database administration, cursors serve as specialized tools for scenarios where pure declarative SQL cannot easily fulfill business or architectural constraints.

1. Large-Scale ETL and Memory-Constrained Batch Processing

When extracting millions of records from an OLTP database for ingestion into analytical lakes or search indexes (such as Elasticsearch), loading the entire result set into application RAM can exhaust server memory. By opening a server-side cursor and streaming chunks of 500 to 1,000 records at a time, microservices written in Python, Java, or Go maintain a constant, minimal memory footprint regardless of total table volume.

2. Mainframe Batch Modernization and Procedural Host Integration

Legacy banking, insurance, and telecommunications platforms built in COBOL and Fortran process transactional ledgers sequentially. During modernization initiatives, database cursors provide the exact interface required to bridge modern relational databases (such as PostgreSQL) with host application arrays, enabling row-by-row validation, tax calculation, and compliance stamping before final commitment.

3. Precision Data Remediation and Positioned In-Place Fixing

In production database maintenance, data corruption or schema migration errors occasionally require targeted, conditional remediation. When scripts must validate each record against an external API or complex heuristic before modifying data, using WHERE CURRENT OF enables safe, in-place updates without the latency, index scans, and lock contention of independent UPDATE statements.

4. Dynamic Administrative Reporting and Ad-Hoc Analytics

Database administrative consoles and reporting engines frequently allow users to sort by arbitrary columns or toggle filtering criteria dynamically. Utilizing dynamic cursors with OPEN ... FOR EXECUTE ... USING enables database engines to compile optimized execution plans on the fly while safeguarding against SQL injection attacks through parameterized bind variables.
