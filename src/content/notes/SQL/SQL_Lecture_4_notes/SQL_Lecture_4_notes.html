# Querying Data

4.1 Select All Data From a Table

4.1.1 Core Syntax and Meaning

Every query in this lecture answers one plain question: which table holds the data, and which pieces of it should come back? The star query is the simplest possible answer — everything from one table.

A SELECT statement (the command that reads rows from a table, written starting with the keyword SELECT) begins with the keyword SELECT, followed by the list of columns to return, followed by a FROM clause that names the table. To read every column and every row, put an asterisk character, also called the star, in the column list. The pattern is:

SELECT * FROM movies;

Read it as a plain request: get all records from the table named movies. Each statement ends with a semicolon, which tells the tool where one statement stops and the next begins. In the movies database used here, running that statement returns every column of the movies table: movie_id, movie_name, movie_length, movie_lang, movie_cert, release_date, and director_id. Scrolling the result grid shows 53 records in total. The same pattern works for the actors table:

SELECT * FROM actors;

That returns every column of actors: actor_id, first_name, last_name, gender, date_of_birth, add_date, and update_date, with all rows visible toward the bottom of the output grid.

Think of the star the way you think of a library request. Saying "bring me every field of every card in the movies drawer" is quick to say and easy to check — you count 53 cards and seven fields per card. Saying "bring me only the title field" takes more words up front but far less carrying. Both requests reach the same drawer; they differ only in how much they carry back.

The star form SELECT * FROM table_name; means: from the named table, return all columns of all rows. The * stands for the full column list, FROM names the source table, and the semicolon ends the statement. No filter, no sorting — just the whole table as stored.

A table name (the identifier after FROM, such as movies or actors) is not case sensitive in this setup. Writing MOVIES in capitals still matches the movies table, because the system resolves the name internally to the stored lowercase form. The advised habit is still to type the exact stored name with its usual lowercase spelling, so anyone reading the code sees the true object name at once.

SQL keywords are also case insensitive. These two statements return the same rows:

SELECT * FROM actors;
select * from actors;

SELECT in capitals equals select in lowercase. The shared habit in database work is to write every keyword in uppercase (SELECT, FROM, ORDER BY) so the structure stands out from table and column names at a glance. The first form above reads far more easily than the second, and that readability is the whole reason for the habit.

Identifier case handling differs between database systems, so carry the habit across even though the rule changes. PostgreSQL, used in this lecture, folds an unquoted name like MOVIES to lowercase movies before matching, which is why the capital form works here. Snowflake instead folds unquoted names to uppercase, so the same query still matches but for the opposite reason. MySQL matches table names using the host file system on some setups, so MOVIES can fail on one server and work on another. Databricks SQL is case-insensitive by default, so both spellings match. The portable habit is one rule everywhere: create tables in lowercase and always type the exact stored name.

4.1.2 How the Database Reads the Statement

Although we type SELECT first, the engine looks at the FROM clause before the SELECT list. Think of it like this: first it asks "which table holds the data", and only then "which columns of that table should I hand back". So the working order is FROM first, then SELECT. This order matters later when sorting and filtering enter the picture, because each later clause builds on the table picked out by FROM.

Picture the engine as a kitchen helper given the note "plate the titles from the movies shelf". The helper walks to the movies shelf first (FROM movies), and only then picks which jars to plate (SELECT). It never gathers plates before knowing which shelf to visit. Later clauses follow the same walk: filtering picks rows from the shelf visit, and sorting arranges whatever survived. Every clause builds on the shelf trip, never before it.

4.1.3 Worked Examples

Example 1 — all movies. Run SELECT * FROM movies; against the movies database. Check the output two ways: the header row lists all seven movie columns (movie_id, movie_name, movie_length, movie_lang, movie_cert, release_date, director_id), and the grid holds 53 records. Both checks confirm the star really did pull the full width and full length of the table. Sense-check: 53 header-to-grid matches mean nothing was trimmed — width (7 columns) times length (53 rows) is the whole table.

Example 2 — all actors. Run SELECT * FROM actors;. The header row lists actor_id, first_name, last_name, gender, date_of_birth, add_date, update_date, and the grid holds the full actor roster. Sense-check: the header names match the table design exactly, so the star added no hidden columns and dropped none.

Example 3 — case check on table names. Run SELECT * FROM MOVIES; with the table name in capitals. The same 53 movie rows come back, which shows name matching ignores case here. The header row is identical to the lowercase run, so only the spelling changed, never the answer.

Example 4 — case check on keywords. Run select * from actors; in all lowercase. The result matches the uppercase version exactly — same headers, same rows. Only readability changed: the eye must work harder to separate keywords from names.

Describe the result grid to fix the picture: the header row runs left to right across the seven movie columns, the row count sits at the bottom of the grid, and scrolling down walks through all 53 records. The takeaway is one line: the grid shows the full rectangle — every column wide, every row long.

4.1.4 Performance Warning

Scope: the star is safe for a quick look at a small table and for tasks that truly need every column. It turns costly the moment the table grows wide or the query runs inside application code on every page load. The boundary is need: if the task needs all columns, the star fits; if it needs two of two hundred, the star wastes the other 198 on every run.

The star is handy, but it carries a cost on wide tables. A single table can hold a large number of columns — imagine 200 columns — and SELECT * pulls every one of them across the connection on each run. That slows the database server, which must read and ship all that data, and it slows the program on the other end, whether that is a browser tool, a Python script, or a PHP page, because the program must receive and hold columns it never needed. Extra traffic between the database server and the application server drags down response time. There is a second, quieter cost: if a column is added to the table later, every SELECT * query silently starts returning a wider answer, and application code that expected a fixed shape can break without any query changing.

Application teams that fetch full wide rows for a page that shows only two fields pay for the other 198 fields on every request. A phone directory page that shows only names but fetches salaries, notes, photos, and audit stamps with each row is the classic case — the page looks light while the wire stays heavy. The fix is to name only the columns the task needs, which is the subject of the next section.

So the rule is simple: the star is fine when the task truly needs every column, but in all other cases name the columns outright. Use the star wisely, never by habit.

Common traps: using SELECT * inside application code that runs thousands of times a day; assuming the column order of SELECT * is a contract (it follows the table design and shifts when columns are added); and forgetting that large text or image columns ride along with the star even when no screen shows them.

4.1.5 Student Questions and Answers

Q: If the star returns everything anyway, why bother naming columns?

A: Because the star also ships everything. On a narrow table the difference is small, but on a wide table it adds server load and network traffic. Naming columns keeps each answer as small as the task allows. Several students asked this in different words — the shared confusion is treating "easy to type" as "cheap to run", when the star is only cheap to type.

The star reads the whole table — every column, every row — through SELECT * FROM table_name;, with FROM visited before SELECT. Next, naming columns trims that answer down to exactly what the task needs.

4.2 Selecting Specific Columns

4.2.1 Columns and Fields

The star carried the whole drawer back to your desk. Now the question flips: what if you only need the title card from each record? Naming columns is how you carry less and read faster.

A column (one named attribute of a table such as movie_id or movie_name, also called a field) is the unit you pick from. The two words mean the same thing in this setting — database designers tend to say column, while application forms and reports tend to say field. The syntax for reading chosen columns mirrors the star form, except the star is replaced by a comma-separated column list:

SELECT column_one, column_two FROM table_name;

Name each wanted column, separate names with commas, then give the FROM clause with the table name. The engine visits the table named in FROM first, then hands back only the listed columns, in the order listed. Listing last_name, first_name returns last name first — output order follows your list, not the table design.

SELECT col_a, col_b FROM t; returns only columns col_a and col_b from table t, left to right in the order written. Everything else in the row stays behind on the server, which is what trims traffic and reading time.

4.2.2 Worked Examples

Example 1 — one column from actors. To read only first names from the actors table, run:

SELECT first_name FROM actors;

The output grid shows a single column of first names drawn from the actors table. Sense-check: one header (first_name), one value per actor row, nothing else riding along.

Example 2 — two columns from actors. To read first and last names together, list both names with a comma:

SELECT first_name, last_name FROM actors;

The grid now shows two columns side by side, first name next to last name. Reverse the list to SELECT last_name, first_name FROM actors; and the columns swap sides — proof that your list order controls the display.

Example 3 — two columns from movies. Switch tables and pick the movie title plus its language:

SELECT movie_name, movie_lang FROM movies;

The grid shows movie titles beside language codes such as English, Chinese, and Japanese. Scanning down the pair, each title sits beside exactly one language — the pairing itself answers "which film is in which language" with no extra columns to skip.

Example 4 — learning from a typo. Changing the column to a name that does not exist, for instance movie_lang1 with an extra digit, stops the run with an error of the form "column movie_lang1 does not exist":

SELECT movie_name, movie_lang1 FROM movies;

The message names the bad column directly. The fix is to read the message, fix the spelling to movie_lang, and run again. Error text here is specific enough to point at the exact fault, so always read it before re-running. Beginners often retype the whole query from scratch; faster repair is to trust the named identifier and fix that one word.

Picture the answer grid for the two-column read: two headers across the top, one row per record below, nothing to scroll sideways. Compare that with the star grid from the prior section — seven headers and a sideways scroll. The takeaway is visible at once: fewer columns means a narrower, faster-to-scan answer.

4.2.3 Why Explicit Columns Are Good Practice

Scope: explicit lists are the default for program code, reports, and any query that runs more than once. The star keeps its place for quick exploration ("what columns does this table even have?") and for one-off checks where typing speed matters more than wire cost. Choose by repetition: run once while exploring, name columns when the query lives on.

Using explicit column names trims the load on the server and returns exactly the data the task needs — nothing extra to ship, store, or scan. That is why explicit lists beat the star in daily work. Three gains arrive together: less network traffic between database and application, less memory held by the receiving program, and a stable contract — adding a column to the table later does not silently widen answers the way SELECT * does. There are valid cases for the star, such as a quick full-table check during exploration, but for program code and repeated queries the named list is the safer default.

The habit crosses every database unchanged: PostgreSQL, MySQL, Snowflake, and Databricks all accept the same comma-separated list with the same meaning. A learner who masters the list form here carries it everywhere with no relearning.

Common traps: selecting a column that does not exist (read the error, fix the spelling); assuming the output follows table-design order instead of list order; and copying a star query into application code where a two-column list would do.

Q: What happens when a column name is misspelled?

A: The run stops and reports that the column does not exist, naming the misspelled identifier. Fix the spelling and run again. The error names the exact word, so repair means correcting that word — not rewriting the query.

Name exactly the columns the task needs, in display order, and let the error text point at any misspelling. Next, aliases relabel those headers so non-technical readers can scan them.

4.3 Column Aliases

4.3.1 Why Rename a Column for Display

Stored names are written for machines and engineers — lowercase, underscored, compact. Report readers need the same values under friendlier headers. How do you relabel the header without touching the stored table?

Stored column names follow a technical style: lowercase words joined by underscores, such as first_name, last_name, or date_of_birth. A reader outside the engineering team often finds that style hard to scan. A column alias (a short display name attached to a column in the output only, leaving stored data untouched) solves that gap without changing anything stored. The base pattern is:

SELECT column_name AS alias_name FROM table_name;

The AS keyword links the stored name to the display name. Think of it as a sticky note on a filing drawer: the drawer keeps its engraved label (first_name), while visitors read your note (First Name). Peel the note off — end the query — and the drawer label never changed.

An alias relabels one output header for one query. SELECT first_name AS firstname FROM actors; shows the same values under the header firstname, while the table still stores first_name. No data moves; only the header text changes.

For example, reading all actors with SELECT * FROM actors; shows headers like actor_id, first_name, last_name, date_of_birth, add_date, and update_date. Aliases let those headers appear in friendlier form while the stored names stay untouched.

4.3.2 Worked Examples

Example 1 — single-word alias. To show first_name as firstname, run:

SELECT first_name AS firstname FROM actors;

The values stay the same; only the header changes — every row still holds the same names, now under firstname. One detail: an unquoted alias folds to lowercase. Even when typed as firstName with a capital N, the header appears in all lowercase, because that is the default handling for a bare alias. Sense-check: compare the value column with the unaliased run — identical values, relabeled header.

Example 2 — forcing exact casing with double quotes. To keep the exact capital N in firstName, wrap the alias in double quotes:

SELECT first_name AS "firstName" FROM actors;

The header now keeps the typed casing exactly. The quotes mark the alias as a delimited identifier, which tells the engine to preserve every letter as typed instead of folding to lowercase.

Example 3 — alias with a space. To show two words such as First Name, double quotes are required:

SELECT first_name AS "First Name" FROM actors;

The header now reads First Name, which is far easier for a non-technical reader to parse than first_name. The broad rule: when an alias mixes words with a space, or mixes letters with other marks, wrap it in double quotes. Without quotes the engine would read the space as the end of the name and stop with a syntax error.

Example 4 — two aliases from movies. To present movie_name as MovieName and movie_lang as Language, run:

SELECT movie_name AS MovieName, movie_lang AS Language FROM movies;

The grid then shows a title column beside a language column with headers a business reader grasps at once. Note the folding detail again: unquoted MovieName displays folded to lowercase in this setup, so reach for "MovieName" in double quotes when the report must show the capital letters. For longer column lists, many writers place each column AS alias pair on its own line with a small indent, which keeps a wide query easy to scan:

SELECT
    movie_name AS MovieName,
    movie_lang AS Language
FROM movies;

The line breaks change nothing in the answer; they only help human eyes. A five-alias report written on one line is correct but unreadable; the same five pairs stacked one per line scan in seconds.

Quoting rules differ by system, so learn the local rule plus the portable core. PostgreSQL, Snowflake, Oracle, and Databricks all accept double quotes for delimited aliases exactly as shown here. MySQL instead uses backticks for identifiers (` First Name ) and treats double quotes as string marks unless its ANSI mode is on. The portable core is identical everywhere: AS` is optional, aliases never touch stored names, and single quotes never delimit an alias.

4.3.3 The AS Keyword Is Optional

The word AS may be dropped entirely:

SELECT movie_name MovieName, movie_lang Language FROM movies;

That form runs and returns the same headers. Many writers still keep AS in place, because in a long query the extra word marks the boundary between stored name and display name without any guesswork. Compare SELECT movie_name Language (did the writer rename, or list two columns with a missing comma?) against SELECT movie_name AS Language — the second reading is instant, the first needs a second look. In short lists both forms are fine; in long reports keep AS.

4.3.4 Single Quotes Do Not Work for Aliases

Trying single quotes around a multi-word alias fails:

SELECT first_name AS 'First Name' FROM actors;

The run stops with a syntax error near the quoted text. The reason is that single quotes mark a text value, not an identifier, so the engine reads the alias attempt as a misplaced value — it expects a header name and finds what looks like the string 'First Name' sitting where a name belongs. The fix is to use double quotes for aliases and keep single quotes for text values. So the takeaway is direct: never use single quotes for an alias; use double quotes when the alias has spaces or mixed casing.

Beginner traps: wrapping an alias in single quotes (syntax error — quotes have opposite jobs); forgetting double quotes around a spaced alias (the space ends the name early); assuming a bare alias keeps capitals (it folds to lowercase here, so quote it when casing matters); and dropping AS in a long list until no reader can tell names from aliases.

4.3.5 Student Questions and Answers

Q: Does the alias change the stored column name?

A: No. The alias only relabels the header in that one answer set. The table keeps its original column names — run the query again without the alias and the old header returns.

Q: Can the alias hold a space?

A: Yes, when wrapped in double quotes, as in "First Name". Without quotes a space is not allowed, because the engine reads the space as the end of the identifier.

Q: Is AS required?

A: No, it is optional and both forms run. Keeping it makes long queries easier to read because each alias stands out on its own.

Exam note: expect alias questions that test double quotes against single quotes, and whether AS can be dropped. Remember the one-line rule: double quotes rename, single quotes hold text values.

4.4 Expressions in the SELECT List

4.4.1 Building New Columns From Old Ones

So far every output column already existed in the table. What if the report needs a value the table never stored — a full name glued from two halves? Expressions build new columns from old ones, row by row.

An expression (a calculation or combination that produces a new value for each row, such as gluing two text columns together) can sit right in the SELECT list. The most used text operator here is the double pipe ||, called the concatenation operator, which glues two text values end to end. Think of it as thread stitching two name tapes into one: first tape, stitch, second tape. Start from the plain two-column read:

SELECT first_name, last_name FROM actors;

That shows the two parts separately. To glue them into one value, place the operator between them:

SELECT first_name || last_name FROM actors;

Each answer row now holds the two names joined with no gap — Tim plus Allen becomes TimAllen. To add a readable gap, glue in a single blank space between the two parts using a space inside single quotes:

SELECT first_name || ' ' || last_name FROM actors;

The ' ' is a one-character text value holding a blank, so the chain reads: first name, then a space, then last name. Each row now reads like a normal full name with one space between the parts — Tim Allen. Then attach an alias so the new column has a header:

SELECT first_name || ' ' || last_name AS "Full Name" FROM actors;

The || operator concatenates text left to right: first_name || ' ' || last_name builds one full-name value per row from three pieces. The result is a derived column (a column computed for the answer rather than stored in the table), so it needs an alias like "Full Name" to get a readable header.

The new column, a derived column — a column computed for the answer rather than stored in the table — now appears under the header Full Name. This same alias pattern from the prior section stretches naturally to computed columns, which is why later work leans on it so often. Arithmetic works the same way: SELECT movie_length / 60 ... would derive hours from stored minutes, with one computed value per row.

The || spelling is standard in PostgreSQL, Oracle, Snowflake, SQLite, and Databricks SQL, so the lecture form carries directly to those systems. MySQL is the exception worth knowing: there || means logical OR by default, so gluing text uses the CONCAT() function instead — SELECT CONCAT(first_name, ' ', last_name) AS "Full Name" FROM actors; returns the same answer. Snowflake and Databricks also accept CONCAT() as a synonym, so CONCAT() is the portable spelling when a query must run on both families.

Scope: expressions compute one value per row from that row's columns, constants, and single-row functions. They cannot reach across rows (totals and averages need grouping, a later lecture) and they inherit NULL behavior — gluing a NULL half yields NULL in most systems unless a fallback like COALESCE supplies a default.

4.4.2 SELECT Without a Table

A SELECT statement can also evaluate a bare calculation with no FROM clause at all. The engine simply computes the value and hands back a one-row answer. Examples:

SELECT 2 * 10;

Two times ten is twenty, so the answer row holds \(2 \times 10 = 20\).

SELECT 2 / 10;

Two divided by ten is zero in integer-style handling here, so the answer is \(2 / 10 = 0\). The zero comes from integer division: both inputs are whole numbers, so the engine returns the whole part of the quotient and drops the fraction. Ask for a decimal explicitly, as in SELECT 2.0 / 10;, and the answer becomes \(0.2\).

SELECT 10 / 2;

Ten divided by two is five, so the answer is \(10 / 2 = 5\).

These tiny runs show that the SELECT machinery doubles as a desk calculator: with a table it transforms stored rows, without a table it evaluates the given arithmetic directly. PostgreSQL and Snowflake allow the bare SELECT exactly as shown; MySQL and Databricks do too. Oracle is the outlier — it requires a dummy table, so the same check reads SELECT 2 * 10 FROM DUAL;. Division behavior also varies: MySQL returns \(0.2000\) for SELECT 2 / 10; instead of \(0\), because it divides in decimal rather than integer style. When an exercise answer depends on the zero-versus-fraction split, test the division on the target system before trusting it.

Worked check — full name plus arithmetic. Run SELECT first_name || ' ' || last_name AS "Full Name" FROM actors; and confirm three things: each row holds two names with exactly one space, the header reads Full Name, and the row count matches the plain two-column read. Then run SELECT 2 * 10; and confirm the single cell holds 20. Both checks pass when the operator glues text and the calculator path evaluates numbers.

Common traps: forgetting the ' ' separator and getting TimAllen; single-quoting the alias instead of double-quoting it (the alias error from the prior section returns); assuming 2 / 10 is \(0\) on every system (MySQL disagrees); and expecting || to glue text in MySQL, where it means OR.

4.4.3 Student Questions and Answers

Q: Can expressions run with no table named?

A: Yes. A statement such as SELECT 2 * 10; has no FROM clause and still returns a one-row answer holding the computed value. The engine evaluates the expression once and hands back a single row.

The SELECT list can compute — glue text with || (or CONCAT() in MySQL), alias the derived column, and even calculate with no table at all. Next, ORDER BY arranges the rows those queries return.

4.5 Sorting Rows With ORDER BY

4.5.1 The Problem ORDER BY Solves

A table stores rows; it never promises an order. Ask twice with no sorting and the rows can return in any sequence. When the reader needs oldest-first, newest-first, or A-to-Z, who guarantees the sequence?

A bare SELECT hands back rows in no promised order. When order matters — oldest film first, newest first, names A to Z — add an ORDER BY clause (the part of the statement that sorts the answer set, written after the FROM clause). The shape is:

SELECT * FROM table_name ORDER BY sort_expression ASC;

A sort expression (the column or list that controls the order, such as release_date or release_date, movie_name) follows the words ORDER BY. The direction word ASC means ascending (smallest to largest, oldest to newest, A to Z — the value \(1\) in ordinary counting order), while DESC means descending (largest to smallest, newest to oldest, Z to A).

ORDER BY sorts the final answer set after FROM and SELECT have built it. ORDER BY release_date ASC arranges rows oldest-first; swapping to DESC reverses the same rows newest-first. Leaving the direction off means ASC.

Picture a deck of film cards tossed on a table: without instruction the helper hands them over in whatever order they landed. ORDER BY release_date ASC is the instruction "line them up by date, earliest on top" — every card is still there, but now the sequence carries meaning.

4.5.2 Worked Examples on One Column

Example 1 — movies by release date, oldest first. The column release_date holds each film release day. To list every movie column with the oldest releases on top, run:

SELECT * FROM movies ORDER BY release_date ASC;

The top rows hold the earliest years and the bottom rows hold the latest ones. Sense-check: read the first and last dates — the first should be the smallest date in the table and the last the largest.

Example 2 — dropping ASC changes nothing. Running the same statement with no direction word:

SELECT * FROM movies ORDER BY release_date;

returns the same oldest-first layout, which shows the default direction is ascending. This default is universal: PostgreSQL, MySQL, Snowflake, and Databricks all sort ascending when the direction is omitted.

Example 3 — newest first. To flip the layout so the latest releases lead, use DESC:

SELECT * FROM movies ORDER BY release_date DESC;

Now the newest dates sit on top and the oldest sink to the bottom — the exact reverse of the ascending form. Compare first rows of the two runs: the ASC leader becomes the DESC trailer, confirming the flip is a pure reversal on one key.

4.5.3 Sorting on Several Columns

A sort key can list more than one column, separated by commas. Each listed column carries its own direction. To sort movies by release date newest-first and, within equal dates, by title A-to-Z, run:

SELECT * FROM movies ORDER BY release_date DESC, movie_name ASC;

The engine applies the keys left to right: it first groups rows by release_date in descending order, then within any shared date it arranges movie_name in ascending order. Think of a sports table sorted by points first, then by team name within equal points — the leftmost key dominates, later keys only break ties.

Switching the second key to descending:

SELECT * FROM movies ORDER BY release_date DESC, movie_name DESC;

re-arranges the within-date groups Z-to-A instead. Only the tied rows move; rows with different dates stay put, which proves the second key touches ties alone.

Flipping the key order itself changes the outcome even more:

SELECT * FROM movies ORDER BY movie_name ASC, release_date DESC;

Now titles lead A-to-Z, and only films sharing a title fall back to newest-first dates. So the lesson is that key order is part of the answer: leftmost key dominates, later keys only break ties left behind.

Multi-key sorting with independent directions works identically in PostgreSQL, MySQL, Snowflake, and Databricks — the lecture forms need no change across systems.

Scope: ORDER BY arranges the answer set; it never removes or merges rows, and without it no order is promised even if the output "usually" looks sorted. Sorting large answers costs time and memory, so production queries sort only the rows the reader needs.

4.5.4 Order of Work Inside the Statement

The engine builds the answer in stages: first FROM picks the table, then SELECT picks the columns, and only then ORDER BY arranges the rows. Think of sorting as the last pass over an already-chosen set of rows. That is why sort keys can name output columns — the rows and columns already exist by the time sorting begins. This staging is exactly why the next two sections work: aliases and expressions defined in SELECT already exist when ORDER BY runs, so sorting by them is legal.

Common traps: trusting the order of a query with no ORDER BY (any sequence is valid); writing the direction once for two keys and expecting it to cover both (ORDER BY a, b DESC leaves a ascending — each key needs its own word); and putting ORDER BY before FROM.

Q: What is the default sort direction?

A: Ascending. Leaving the direction word off behaves exactly like writing ASC — on every major system, not just this one.

Exam note: expect tasks that sort one column each way, then a two-column sort where key order and mixed directions change the result. State each key with its own direction, leftmost dominant first.

4.6 ORDER BY With an Alias

4.6.1 Setup: Rename Then Sort

Start from a plain read of actor names:

SELECT first_name, last_name FROM actors;

Attach an alias to the second column so last_name appears as surname:

SELECT first_name, last_name AS surname FROM actors;

The header for the second column now reads surname. Dropping AS also works:

SELECT first_name, last_name surname FROM actors;

Both spellings return the same renamed header, though keeping AS keeps long queries easier to scan. This recap of the alias section is deliberate: the alias must exist in SELECT before ORDER BY can use it, and the staging from the prior section (FROM, then SELECT, then ORDER BY) is what makes the next step legal.

4.6.2 Worked Examples

Example 1 — sort by the stored name ascending. Take the aliased query and append a sort on the stored column:

SELECT first_name, last_name AS surname FROM actors ORDER BY last_name;

With no direction word the layout is ascending by default, A-to-Z down the surname column. The header still reads surname — sorting by the stored name does not undo the relabeling.

Example 2 — sort by the stored name descending. Add the direction word:

SELECT first_name, last_name AS surname FROM actors ORDER BY last_name DESC;

Names starting with late letters now lead, and A names sink to the bottom. The first row of this run matches the last row of the ascending run, confirming a pure reversal.

Example 3 — sort by the alias itself. Replace the stored name in the sort key with the alias:

SELECT first_name, last_name AS surname FROM actors ORDER BY surname DESC;

The layout matches the prior descending run exactly, which shows the alias is a valid sort key. Removing the direction word:

SELECT first_name, last_name AS surname FROM actors ORDER BY surname;

gives the ascending form again. So both the stored name and its alias steer the sort, and the alias form is often the clearer read because the sort key matches the header the eye sees. Sorting by alias works in PostgreSQL, MySQL, Snowflake, and Databricks alike — it follows from the standard staging, not from a vendor extension.

Scope: an alias defined in SELECT is visible to ORDER BY in the same query, because sorting runs after column selection. It is not visible to WHERE in most systems, because filtering runs before selection — a limit that matters once filters enter the picture.

Picture the grid with the surname header: whether the sort key reads last_name or surname, the eye scans the same A-to-Z column. The alias-key spelling wins on readability because the word in ORDER BY matches the word above the column.

4.6.3 Student Questions and Answers

Q: Must the sort key repeat the stored column name?

A: No. The alias works as a sort key and gives the same order, so ORDER BY surname matches ORDER BY last_name here. Prefer the alias spelling when it matches the displayed header — the query then reads the way the grid looks.

Aliases defined in SELECT are fair sort keys, because ORDER BY runs last. Next, even computed values like function results can steer the sort.

4.7 ORDER BY on an Expression

4.7.1 Measuring Text Length With LENGTH

Columns and aliases both sort — but what if the ranking key exists nowhere in the table, like the length of each name? Sorting by a computed value closes that gap.

A sort key need not be a plain column; it can be a computed value such as a function result. The LENGTH function (written LENGTH(text), returning the count of characters in a text value — a name of \(3\) letters reports \(3\)) counts the characters in a text value. Start from the full actor read:

SELECT * FROM actors;

That shows actor_id, first_name, last_name, and the rest. To see each first name beside its length, run:

SELECT first_name, LENGTH(first_name) FROM actors;

A name like Tim with three characters reports a length of \(3\). The second output column arrives with a header derived from the function call, which can be relabeled with an alias for clarity if desired:

SELECT first_name, LENGTH(first_name) AS name_len FROM actors;

LENGTH(text) returns the character count of each value — LENGTH('Tim') is \(3\), LENGTH('Alexander') is \(9\). Placed in the SELECT list it displays the measure; placed in ORDER BY it ranks by the measure.

Spelling the length function across systems: PostgreSQL accepts LENGTH(), CHAR_LENGTH(), and CHARACTER_LENGTH() as synonyms — all count characters. Snowflake accepts LENGTH() and LEN(). Databricks SQL accepts length() and len(). MySQL splits the job: CHAR_LENGTH() counts characters while LENGTH() counts bytes, so the two agree on plain English names but differ on multibyte text such as 日本語, where one character can occupy three bytes. For this lecture's English names every spelling agrees; for international text prefer the character-counting form on each system.

4.7.2 Worked Example: Longest Names First

Example — longest names first. To arrange actors so the longest first names lead, sort by that same function result in descending order:

SELECT first_name, LENGTH(first_name) FROM actors ORDER BY LENGTH(first_name) DESC;

A nine-character name such as Alexander rises to the top with 9, followed by shorter names in shrinking order down toward 3-letter names like Tim. One empty value in the demo data sorts along with the rest; it can be removed if a clean list is needed, but it does not break the pattern. The mental model is direct: the engine first computes the length for every row, then sorts those computed lengths top to bottom. Sense-check: the length column reads non-increasing from top to bottom — each value is less than or equal to the one above it.

The alias spelling from the prior section works here too and reads more cleanly:

SELECT first_name, LENGTH(first_name) AS name_len FROM actors ORDER BY name_len DESC;

Same order, clearer sort key — the word in ORDER BY matches the header.

Picture the ranked grid: names on the left in mixed order, lengths on the right stepping down \(9, 8, 7, \ldots\). The shape is a staircase descending left to right, and its takeaway is one line: rank follows the computed number, not the alphabet.

4.7.3 Expressions Without a Table

Just as with plain arithmetic, expression queries need no table when the values are given directly:

SELECT 5 * 12;

Five times twelve is sixty, so the one-row answer is \(5 \times 12 = 60\). And:

SELECT 10 / 2;

gives \(10 / 2 = 5\). The takeaway is that expressions work in two places: wrapped around stored columns to reshape each row, or standing alone to compute a direct answer.

Live systems use this pattern constantly to rank by computed measures — name length here, but equally order totals, discounted prices, or full-name strings. A shop ranks products by ORDER BY price * quantity DESC to surface the highest-value lines; a directory ranks by ORDER BY LENGTH(bio) DESC to find the most documented entries. The mechanism never changes: compute per row, then sort the computed values.

Common traps: sorting by the function call in ORDER BY while selecting a differently-spelled expression (keep both spellings identical, or sort by the alias); forgetting DESC and getting shortest-first when longest was wanted; and assuming LENGTH() counts characters in MySQL, where it counts bytes.

Any per-row computation — a function result, arithmetic, even a glued string — can steer ORDER BY, because sorting runs after computation. Next, the positional shorthand trades names for numbers, with a trap attached.

4.8 ORDER BY by Column Name or Column Number

4.8.1 The Number Shortcut

Long select lists make sort keys tedious to retype — and a single typo breaks the sort. Is there a shorter way to point at a column you already listed?

A sort key can name a column or point at it by position. The position counts left to right across the SELECT list: in SELECT first_name, last_name, date_of_birth FROM actors, position \(1\) is first_name, position \(2\) is last_name, and position \(3\) is date_of_birth. The count covers only listed columns, starting at \(1\) — there is no position \(0\). Start from the full read:

SELECT * FROM actors;

To sort every record by first name A-to-Z and then by birth date newest-first, the name form is:

SELECT * FROM actors ORDER BY first_name ASC, date_of_birth DESC;

Rewriting the column list outright first makes the positions visible:

SELECT first_name, last_name, date_of_birth FROM actors ORDER BY first_name ASC, date_of_birth DESC;

That returns the wanted layout. The number form gives the same answer:

SELECT first_name, last_name, date_of_birth FROM actors ORDER BY 1 ASC, 3 DESC;

In ORDER BY, a number points at the SELECT list by position: ORDER BY 1 ASC, 3 DESC sorts by the first listed column ascending, then the third listed column descending. It is shorthand for the matching names — same rows, same order, fewer words.

Here \(1\) points at first_name and \(3\) points at date_of_birth. Both spellings sort identically, so the number is purely a shorthand for the name. Positional sorting is supported in PostgreSQL, MySQL, Snowflake, and Databricks SQL alike, which is why the lecture demo transfers directly — though all four vendors' documentation nudges writers toward names in saved code.

4.8.2 Worked Example Showing the Risk

Example — the reorder trap. The shorthand tracks positions, not names, so reordering the list silently re-points the numbers. If the list is flipped to last_name first:

SELECT last_name, first_name, date_of_birth FROM actors ORDER BY 1 ASC, 3 DESC;

then \(1\) now means last_name, and the whole answer re-sorts last-name-first. Nothing in the ORDER BY text changed, yet the order did — compare the first rows of the two runs and different surnames lead. That is the trap: a later edit to the column list can redirect every number without warning. Sense-check after any list edit: read position \(1\) aloud as its current column name and confirm it still names the intended key.

For that reason many writers prefer the name form in code that others will maintain, and keep numbers only for quick ad-hoc queries or very long lists where names feel heavy. A useful middle rule: numbers are fine in a throwaway check you run once, names are required in anything saved, shared, or scheduled. Note also that numbers cannot point at columns missing from the SELECT list the way names sometimes can — ORDER BY date_of_birth works even when the list shows only names, but ORDER BY 3 fails unless three columns are listed.

Common traps: editing the SELECT list and silently redirecting every number; numbering from \(0\) instead of \(1\); pointing past the end of the list (ORDER BY 5 on three columns errors); and mixing the two styles in one key list until no reader can tell which keys are names and which are positions.

Q: Do numbers and names sort the same?

A: Yes, when they point at the same columns. ORDER BY 1 ASC, 3 DESC matches ORDER BY first_name ASC, date_of_birth DESC for the three-column list above, until the list order changes. The match holds only while the list stays frozen — reorder the list and the numbers drift.

Positional keys are a shorthand for names, valid while the list order holds and risky the moment it changes. Next, missing values need their own placement rule before any sort can be trusted.

4.9 ORDER BY With NULL Values

4.9.1 What NULL Means for Sorting

Real tables have gaps — a missing phone number, an unrated film, a shipment date not yet known. When those gap rows meet a sort, where should they land: top, bottom, or wherever the system feels like?

A NULL marker (the absence of a value, meaning the data is missing or unknown — a blank that is not zero, not an empty string, and not the word "null") is not zero, not a blank string, and not the word null. It is the lack of any value at all. Comparing it is like asking "is an unanswered question higher or lower than 5?" — the question has no answer, so each system picks a convention. When sorted rows mix real values with NULL markers, the statement can pin the NULL group explicitly with two options: NULLS FIRST puts missing values at the top, and NULLS LAST pushes them to the bottom. The shape is:

SELECT column_list FROM table_name ORDER BY sort_expression ASC NULLS LAST;

NULLS FIRST pins gap rows to the top of the answer and NULLS LAST pins them to the bottom, independent of the ASC/DESC direction. Either direction word may pair with either placement, so all four blends (ASC NULLS FIRST, ASC NULLS LAST, DESC NULLS FIRST, DESC NULLS LAST) are available.

Either direction word (ASC or DESC) may pair with either NULL placement, so all four blends are available. In this setup (PostgreSQL behavior) the defaults are: ascending puts NULL markers last, descending puts them first — as if NULL were larger than every real value. Always state the placement explicitly when gaps are possible; defaults differ across systems (see the cross-system box below), so an unpinned sort orders gaps correctly here and wrongly on the next server.

Explicit NULLS FIRST / NULLS LAST is supported in PostgreSQL, Oracle, Snowflake, and Databricks SQL with the same spelling shown here. MySQL is the notable exception: it accepts no NULLS FIRST or NULLS LAST keywords at all, and instead treats NULL as the smallest value — ascending puts gaps first, descending puts them last, which is the mirror of this lecture. Queries that must run on MySQL pin gaps with a conditional key such as ORDER BY num IS NULL, num instead. SQL Server likewise lacks the keywords. The portable habit: always pin NULL placement on systems that allow it, and never assume one system's default holds elsewhere.

4.9.2 Worked Examples With a Demo Table

To see the behavior hands-on, build a tiny one-column table and fill it with a mix of numbers and a missing value:

CREATE TABLE demo_sorting (num INT);
INSERT INTO demo_sorting (num) VALUES (1), (2), (3), (NULL);

The first statement creates a practice table with a single integer column; the second loads four rows — three numbers and one gap. Refreshing the object list shows the new demo_sorting table with its single num column. A full read:

SELECT * FROM demo_sorting;

shows the three numbers with the NULL marker grouped at the end, which is the default display for this setup.

Example 1 — explicit ascending. Running:

SELECT * FROM demo_sorting ORDER BY num ASC;

returns the same layout — 1, 2, 3, then NULL — which confirms ascending is the default direction and that ascending parks gaps last in this setup.

Example 2 — a spelling pitfall. Writing the NULL option with a missing letter, as NULL LAST instead of NULLS LAST, stops with an error. The keyword is plural — NULLS with a final S — because it governs the whole group of gap rows, not one gap. The fix is one letter:

SELECT * FROM demo_sorting ORDER BY num NULLS LAST;

That form runs and matches the ascending layout, because ascending already places NULL markers last here. Stating it explicitly costs nothing and protects the query if the default ever changes.

Example 3 — missing values first. To pull the missing row to the top while keeping numbers ascending, run:

SELECT * FROM demo_sorting ORDER BY num NULLS FIRST;

The NULL row jumps to position one, followed by 1, 2, 3. Only the gap row moved; the numbers keep their ascending run, proving the option steers gaps alone.

Example 4 — descending defaults and overrides. Running:

SELECT * FROM demo_sorting ORDER BY num DESC;

places the NULL marker first by default, followed by 3, 2, 1. To push missing values to the bottom of a descending list instead, pair the direction with the matching option:

SELECT * FROM demo_sorting ORDER BY num DESC NULLS LAST;

Now 3, 2, 1 lead and the NULL marker closes the list. The same pairing extends to DESC NULLS FIRST when the top placement is wanted. Sense-check the four blends as a set: direction flips the numbers, placement parks the gap — the two controls never interfere.

Example 5 — cleanup. Once the trials are done, remove the demo object and refresh the list to confirm it is gone:

DROP TABLE demo_sorting;

Housekeeping like this keeps practice objects out of later work. A leftover demo table in a shared database confuses the next learner's table list and can collide with their own practice names.

Picture the four blends as one diagram: a vertical list with the gap row as a shaded card. ASC NULLS LAST reads 1-2-3-shaded; ASC NULLS FIRST reads shaded-1-2-3; DESC NULLS FIRST reads shaded-3-2-1; DESC NULLS LAST reads 3-2-1-shaded. The takeaway: direction orders the numbers, placement parks the shade.

4.9.3 Student Questions and Answers

Q: Where do missing values land if no NULL option is given?

A: In this setup ascending puts them last and descending puts them first. Adding NULLS FIRST or NULLS LAST pins the placement either way — and on MySQL the unpinned defaults run mirrored, so pinning is the only portable answer.

Q: Why did NULL LAST fail?

A: Because the keyword needs its final letter: NULLS LAST with an S. The singular form is a syntax error. Read the error position — it points at the misspelled option word itself.

Live tables often hold missing phone numbers, unrated items, or unshipped dates, so pinning NULL placement keeps reports and pages stable. A "newest shipments first" feed that lets gap rows float by system default shows unshipped orders on top in one database and buries them in another; DESC NULLS LAST shows newest real dates first on every supporting system.

Common traps: writing NULL LAST without the S; assuming the local default travels (MySQL mirrors it); pinning placement on MySQL with the keywords (unsupported — the statement errors); and confusing NULL with zero or blank, then "fixing" gaps by sorting as if they were values.

Exam note: expect a sort task on a column with missing values where the required answer names both the direction and the NULL placement. Write both words every time — direction plus NULLS FIRST or NULLS LAST.

4.10 Selecting Distinct Values

4.10.1 The DISTINCT Idea

Fifty-three film rows list only a handful of languages — but reading all 53 to count the languages is slow work. How do you collapse repeats and keep one of each?

A DISTINCT filter (the DISTINCT word right after SELECT, which keeps only one copy of each repeated value) collapses duplicates. The shape is:

SELECT DISTINCT column_name FROM table_name;

DISTINCT keeps one row per unique combination of the listed columns: one listed column answers "how many kinds of X", two columns answer "how many kinds of X-plus-Y pairs", and DISTINCT * answers "are any two full rows identical". The unit of uniqueness is always the whole returned row.

It accepts one column, several columns, or the star for whole rows. Each form answers a different "how many kinds" question, and the movie data shows each one well. Think of a stamp collector shaking duplicates out of a pile: one stamp per design survives, and what counts as "same design" depends on how many features you compare — color alone, color plus country, or the entire stamp.

4.10.2 Worked Examples

Example 1 — baseline counts. Start from the full movie read:

SELECT * FROM movies;

The grid holds 53 records. Then read languages alone:

SELECT movie_lang FROM movies;

The grid still holds 53 rows, but values repeat heavily — English beside English beside English, then Chinese runs, Japanese, and more. The repeats are the problem DISTINCT removes. Sense-check: same row count (53) with heavy repeats means the column carries few kinds across many rows.

Example 2 — unique languages. To keep one of each language, add the filter:

SELECT DISTINCT movie_lang FROM movies;

The 53 rows collapse to 8 unique languages. Arranging them A-to-Z by name or by position:

SELECT DISTINCT movie_lang FROM movies ORDER BY movie_lang;
SELECT DISTINCT movie_lang FROM movies ORDER BY 1;

lists Chinese, English, German, Japanese, Korean, Portuguese, Spanish, and Swedish. Both sort keys work because the output has a single column in position \(1\). The collapse from 53 to 8 is the payoff made visible: 45 duplicate rows folded away.

Example 3 — unique director identifiers. The same single-column pattern on the director column:

SELECT DISTINCT director_id FROM movies;

keeps 37 unique identifiers. The drop from 53 rows to 37 shows several directors made more than one film in the set — 16 repeat credits folded into their first occurrence.

Example 4 — distinct pairs. To keep unique language-plus-director pairs, name DISTINCT once and list both columns:

SELECT DISTINCT movie_lang, director_id FROM movies ORDER BY movie_lang;

Only the first column carries the DISTINCT word; the second is separated by a comma with no repeat of the word — writing DISTINCT twice is a syntax error. A reader may wonder why Chinese still appears on several rows after asking for distinct languages. The answer is that the filter now spans the pair: each returned row is a unique blend of language plus director, so one language can recur beside different directors. The unit of uniqueness is the whole row, not the first column alone. Concretely: (Chinese, director 7) and (Chinese, director 12) are different pairs, so both survive — the language half repeats while the pair stays unique.

Example 5 — distinct whole rows. To keep one copy of each fully identical row, pair the filter with the star:

SELECT DISTINCT * FROM movies;

Here all 53 rows survive, which shows no two movie rows are fully identical across every column — every film differs somewhere (id, title, date, or director). Adding a sort keeps the check tidy:

SELECT DISTINCT * FROM movies ORDER BY movie_id ASC;

The grid then runs in identifier order with each full row unique. The 53-to-53 non-collapse is itself the finding: a full-row duplicate audit comes back clean.

DISTINCT with one column, several columns, and the star behaves identically in PostgreSQL, MySQL, Snowflake, and Databricks SQL — the lecture forms transfer unchanged. Two extras are worth knowing once the core is solid. PostgreSQL offers DISTINCT ON (col) as a vendor extension that keeps one row per value of the named column while returning other columns too — handy, but non-portable, so exam and shared queries should stick to plain DISTINCT. And COUNT(DISTINCT movie_lang) folds the filter into an aggregate to return the number \(8\) directly instead of listing the eight rows — the counting companion to the listing learned here.

Scope: DISTINCT folds exact duplicates after all expressions are computed — trailing spaces and casing differences count as different values ('English' vs 'english ' survive as two rows). It never selects "one representative per group with extra detail"; that choice needs grouping or DISTINCT ON, not plain DISTINCT.

4.10.3 Student Questions and Answers

Q: Why does Chinese repeat in the two-column distinct answer?

A: Because uniqueness now covers the pair. Each language-plus-director blend is unique even when the language half repeats, so Chinese returns once per distinct director it pairs with. One column distinct answers "how many languages"; two columns answer "how many language-director blends" — different questions, different row counts.

Analysts use this filter daily to list live categories, count active makers, or audit whether full-row duplicates slipped into a load. A shop's category sidebar (SELECT DISTINCT category FROM products ORDER BY 1;), a count of active directors (\(37\) here), and a load check (SELECT DISTINCT * row count versus raw count) are the same three lecture forms wearing work clothes.

Common traps: repeating DISTINCT before the second column; expecting one row per first-column value in a two-column query (the pair trap); assuming DISTINCT ignores case or trims spaces; and sorting by a column that is not in the SELECT DISTINCT list on systems that forbid it.

Exam note: expect single-column, multi-column, and whole-row distinct tasks, plus the pair trap where one column repeats inside unique pairs. Name DISTINCT once, remember the whole row is the unit, and predict the collapse (53 to 8, 53 to 37, 53 to 53) before running.

Exam Guidance Summary

No single date or mark split is stated in this material, so plan around the skills themselves. Practice the star read on both movies and actors until the syntax needs no thought, and rehearse the staging — FROM first, then SELECT, then ORDER BY — until alias and expression sort keys feel inevitable rather than memorized. Practice named-column reads with one and two columns, predicting the header order before running, and rehearse fixing the "column does not exist" error by reading the message text. Drill aliases with AS, without AS, with double quotes for spaces and mixed casing (and backticks if you also work in MySQL), and the failing single-quote form so its error looks familiar. Drill the concatenation operator with and without the blank space, the derived-column alias, CONCAT() as the MySQL-portable twin, and bare arithmetic with no FROM — including the integer-division split (2 / 10 is \(0\) here, fractional on MySQL). Drill single-key sorts each way, the ascending default, two-key sorts with mixed directions and swapped key order, alias sort keys, expression sort keys with LENGTH (bytes versus characters on MySQL), numeric position keys with their reorder trap, NULL placement in all four direction blends, and the NULLS spelling with its final S — noting MySQL lacks the keywords entirely. Drill distinct on one column (53 to 8 languages), on pairs with the pair trap, on director counts (53 to 37), and on whole rows (53 to 53). For each drill, type the statement, predict the row order and headers, run it, and compare — prediction before execution is what turns syntax into skill.

Key Industry Applications

Friendly aliases feed reports and screens where business readers need plain headers rather than underscore-style stored names — every customer-facing export renames at the query layer instead of touching stored design. Explicit column lists cut traffic between database and application tiers, which keeps pages and services fast on wide tables; teams that fetch two of two hundred columns on every request feel the savings immediately. Concatenated full names and other derived columns power display fields built straight in the query layer, from directory listings to invoice headers, with CONCAT() covering the MySQL hosts. Multi-key sorting with mixed directions drives leaderboards, newest-first feeds, and A-to-Z directories, where the leftmost key sets the ranking and later keys break ties. Expression sorting by computed measures ranks items by totals, prices, or string length without extra code — the shop's highest-value lines surface from one ORDER BY on arithmetic. Pinned NULL placement steadies reports over sparse live data such as missing contact fields, unrated items, or unshipped dates, keeping gap rows parked where each audience expects them. Distinct lists back category filters, maker counts, and duplicate audits: storefront sidebars list live categories, studios count active directors, and load pipelines compare distinct-row counts against raw counts to catch doubled inserts. The PgAdmin grid used throughout — result headers, row counts, and scroll checks — mirrors the daily loop of writing a statement, reading headers and counts, and re-running after each fix.
