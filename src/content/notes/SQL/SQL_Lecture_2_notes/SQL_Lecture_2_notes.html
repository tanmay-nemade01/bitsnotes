Creating and Modifying Tables

Level: undergraduate
Audience: Undergraduate students learning SQL and table creation

Creating and Modifying Tables: building the movies database, linking tables with keys, choosing column types, loading sample data, and evolving schemas with pgAdmin and SQL.

2.1 Movie Database Overview

2.1.1 Tables and Their Roles

Why start with a map before building anything? Because a movies database tables overview saves hours later: when you know which table owns which fact, every CREATE TABLE, join, and load step falls into place.

The movies database lives inside pgAdmin under a database called movies. It holds five main tables that get used through many later exercises: actors, directors, movies, movies_actors, and movies_revenues. Each table has one clear job. The actors table keeps facts about each actor. The directors table keeps facts about each director. The movies table is more of a transaction table that keeps facts about each film. The movies_actors table links movies to actors. The movies_revenues table keeps money facts per movie.

In the actors table the columns are actor_id, first_name, last_name, gender, date_of_birth, plus add_date and update_date. In the directors table the columns are director_id, first_name, last_name, date_of_birth, nationality, plus add_date and update_date. In the movies table the columns are movie_id, movie_name, movie_length, movie_language, age_certificate, release_date, and director_id. In the movies_revenues table the columns are revenue_id, movie_id, revenues_domestic, and revenues_international. In the movies_actors table the columns are movie_id and actor_id.

Think of a film festival. Actors and directors are the people (the guests). A movie is the event that brings guests together on one stage. The sign-up sheet at the door records who appeared in which event, and the ticket desk records how much money each event made. That is exactly how actors, directors, movies, movies_actors, and movies_revenues fit together.

A useful way to think about it is that actors and directors are people tables, and people tables link through the movies transaction table. Movies is the event that brings people together, and revenues and movies_actors are link and outcome tables that hang off movies. That mental picture helps when new tables get added later. For example, if a later exercise adds a reviews table or an awards table, each new row still hangs off one movie_id, so the center of the map does not move.

A transaction table (one row per event, here one row per film in movies) sits at the center. Entity tables (actors, directors) describe the who. Link and outcome tables (movies_actors, movies_revenues) describe the pairings and the money that result from the event. This center-plus-satellites shape is the standard pattern in media catalogs, shops, and booking systems.

Across database systems this map looks the same. In Postgres the five tables live in the public schema of the movies database. In MySQL the same five tables live inside the movies schema with the same column names. In Snowflake and Databricks the same logical map applies, only the physical storage differs: Snowflake stores each table as micro-partitioned files with automatic indexing, while Databricks stores each table as Delta files with a transaction log. The table names and their roles stay fixed, so work learned here transfers directly.

Picture the map as a hub with spokes. The hub is movies. One spoke runs to directors, one spoke runs to movies_revenues, and one spoke runs through movies_actors out to actors. The takeaway in one line: people tables feed the center, and outcome tables hang off the center. Every later join follows these spokes.

2.1.2 Primary Keys and Foreign Keys at a Glance

Each people table and each main table has its own primary key. A primary key (a column whose value is unique for each row and belongs to that table) keeps every row addressable. So actor_id is the primary key of actors, director_id is the primary key of directors, movie_id is the primary key of movies, and revenue_id is the primary key of movies_revenues.

A primary key is the one column (or column pair) that names each row and never repeats within its table. A foreign key is a column in one table that points at the primary key of another table. The primary key owns the fact; the foreign key borrows the address.

A foreign key is a column in one table that points at the primary key of another table. It is how tables stay linked. In movies, director_id is a foreign key that points to director_id in directors. In movies_actors, movie_id points to movie_id in movies and actor_id points to actor_id in actors. So movies_actors carries two foreign keys. In movies_revenues, movie_id points to movie_id in movies. Domestic means revenue inside the US. International means revenue outside the US.

That REFERENCES check is not decoration. When a new movie row names director_id 5, the system confirms that directors holds a row with director_id 5; when a revenue row names movie_id 40, the system confirms that movies holds movie_id 40. When the target is missing, the insert is rejected instead of creating an orphan row that no join can ever reach.

Scope: primary keys promise uniqueness inside one table only. They do not promise that two tables use the same numbering. Actor 7 and movie 7 are unrelated numbers that happen to match. Assumption: foreign keys assume the parent row already exists. Load parents before children, or the check fails by design.

Cross-system note: the idea is identical everywhere, and only the declaration wording shifts. Postgres uses SERIAL PRIMARY KEY with a separate REFERENCES clause, MySQL uses INT AUTO_INCREMENT PRIMARY KEY with FOREIGN KEY REFERENCES, Snowflake often uses NUMBER AUTOINCREMENT PRIMARY KEY with REFERENCES, and Databricks Delta uses plain INT with FOREIGN KEY constraints that are informational (not enforced) in older runtimes. The lecture uses the Postgres form because the exercises run in pgAdmin against Postgres.

Exam note: be ready to name all four single-column primary keys (actor_id, director_id, movie_id, revenue_id), point out that movies_actors carries two foreign keys, and state that domestic means inside the US while international means outside the US.

2.1.3 Data Types Seen in a Quick Browse

Browsing the data shows the intended types. Movie length is an integer value such as hours or minutes of run time. Movie language is character or varchar with length 20. Age certificate is a short code such as PG, 12, 13, 15, and similar ratings. Release date is a date. Director_id is an integer that matches the serial key in directors. In movies_revenues, movie_id is an integer foreign key, and revenues_domestic and revenues_international are numeric values with decimal places.

An integer (whole-number count such as run time in minutes) suits lengths and keys. A character or varchar field (text with a fixed or capped length) suits names, languages, and short codes. A date field suits calendar days. A numeric field with decimals suits money with cents. Match the type to the shape of the fact.

Why these picks? Run time needs math (sort longest first, filter over 120 minutes), so it stays numeric. Language and age codes need pattern matching (all PG films, all English films), so they stay text with short caps such as VARCHAR(20) and VARCHAR(10). Money needs exact cents, so it stays NUMERIC rather than a float that can drift by a fraction of a cent. Dates need calendar math (films after 2010, films per year), so release_date stays DATE rather than text.

Per-system extras worth knowing: Postgres offers INT, VARCHAR(n), CHAR(n), DATE, and NUMERIC(p, s); MySQL offers the same family plus TEXT variants and DECIMAL as the synonym for NUMERIC; Snowflake maps these to NUMBER, VARCHAR, CHAR, DATE, and NUMERIC with flexible precision; Databricks Spark SQL uses INT, STRING, DATE, and DECIMAL. When one concept appears with extras in another system (for instance MySQL unsigned integers, or Postgres TEXT without a length cap), treat the extra as a dialect bonus on the same shared concept rather than a new topic.

Two traps show up early. First, storing a date or a money value as plain text breaks sorting and sums (text sorts 9 before 10, and text cannot be summed). Second, picking a length cap that is too tight (VARCHAR(10) for a film name) forces truncation or errors on real data. Browse first, then cap with headroom.

Movies is the hub, people tables feed it, and link plus revenue tables hang off it; keys name rows and link tables; types match the shape of each fact. That map carries through every build step next.

2.2 Creating the Movies Database and the Actors Table

2.2.1 Create Database in pgAdmin

How does a brand-new project get its own empty home? By creating one database container before any table exists.

Start in pgAdmin. The server shows built-in databases such as postgres plus any course databases. To make a new database, right-click on Databases, pick Create and then Database, and type movies as the name. Leave definition, tablespace, and security at defaults. The tool shows the SQL it will run. Save it. Then click on the new movies database to open it, go to Schemas, then public, then Tables. That is where new tables will appear.

Think of the server as an office building, each database as one office, each schema as a filing cabinet inside the office, and each table as one drawer. Creating the movies database rents one empty office; the public schema is the default cabinet; Tables is where the new drawers will slide in. This picture breaks at one point: unlike office drawers, tables enforce types and keys, so a wrong-shaped value never fits.

The same step in plain SQL is one line:

CREATE DATABASE movies;

Run it in the query tool connected to the server (not inside the movies database yet, since it does not exist until the statement finishes). Then refresh the Databases node and open movies, Schemas, public, Tables. In MySQL the twin step is CREATE DATABASE movies; followed by USE movies;. In Snowflake it is CREATE DATABASE movies; with a warehouse running. In Databricks it is CREATE SCHEMA movies; (schemas act as the database container). The lecture uses the pgAdmin click path because the course runs on Postgres.

Real-world: pgAdmin build scripts of this kind are used by teams to spin up a fresh dev or test database before loading sample data. A setup script creates the database, connects to it, then runs each CREATE TABLE file in order, so every teammate starts from the same empty shell.

Worked mini-check: after the Save click, the navigator must list movies beside postgres. Open movies, then Schemas, then public, then Tables. An empty Tables node with no error is the bolded pass signal: database ready, zero tables yet. When that node opens cleanly, the container step is done.

One container first (movies), then tables inside public. Refresh to confirm before moving on.

2.2.2 CREATE TABLE Syntax and First Table

Postgres creates a table with a fixed shape. Here is the CREATE TABLE actors statement used in the lecture:

CREATE TABLE actors (
  actor_id SERIAL PRIMARY KEY,
  first_name VARCHAR(150),
  last_name VARCHAR(150) NOT NULL,
  gender CHAR(1),
  date_of_birth DATE,
  add_date DATE,
  update_date DATE
);

The shape is always CREATE TABLE plus table name, then in parentheses a list of column name, column type, and any rules, with commas between columns and a semicolon at the end. To run it, select the movies database icon, open a new query window, paste the statement, and run it. Then right-click Tables and pick Refresh. The actors table appears with all columns listed.

CREATE TABLE declares the drawer and every divider at once: the table name, then one line per column with its name, its type, and its rules. Commas divide columns. The closing parenthesis plus semicolon ends the build. Nothing is stored yet; only the shape is stored.

A naming habit used here is to prefix the key with the table name, such as actor_id instead of bare id. That makes joins much easier to read later because movie_id and actor_id never get mixed up. Another habit is to join multi-word column names with an underscore, such as date_of_birth, first_name, and add_date. Some people use camel case such as dateOfBirth. Either style works as long as one style is used through the whole database. The lecture sticks with snake case (underscores) throughout, which matches Postgres habits and keeps every join column self-naming.

Per-system extras on the same shared concept: MySQL writes the key as actor_id INT AUTO_INCREMENT PRIMARY KEY instead of SERIAL. Snowflake writes actor_id NUMBER AUTOINCREMENT PRIMARY KEY (or IDENTITY). Databricks Spark SQL has no SERIAL type and uses INT with GENERATED ALWAYS AS IDENTITY in newer runtimes, or a plain INT filled by the load script. The column list shape with commas and types is the same in all four; only the auto-number keyword changes.

Trace the actors build line by line. actor_id SERIAL PRIMARY KEY reserves the auto-filled row number. first_name VARCHAR(150) and last_name VARCHAR(150) NOT NULL reserve two name slots with a 150-character cap, last name mandatory. gender CHAR(1) reserves one fixed character. date_of_birth DATE, add_date DATE, update_date DATE reserve three calendar slots. Run, Refresh Tables, and the bolded result: actors appears with 7 columns. That visible table is the worked proof.

Scope: CREATE TABLE sets the shape once. It does not insert rows and does not link tables by itself; keys and REFERENCES clauses do the linking. Assumption: the statement assumes the movies database is selected. Run it while connected to postgres by mistake and the table lands in the wrong database.

2.2.3 SERIAL Keys, VARCHAR Lengths, and NOT NULL

What fills the key when nobody types one? The type itself.

SERIAL is a Postgres type that fills in the next integer by itself. Each new row gets plus one without manual input. Marking actor_id as SERIAL PRIMARY KEY means it auto-fills and stays unique per row. Behind the scenes Postgres creates a sequence counter starting at 1 and attaches nextval to the column default, so the first insert gets 1, the next gets 2, and gaps appear only when an insert fails midway. VARCHAR needs a length in parentheses, such as VARCHAR(150) for first names and last names. CHAR(1) holds a short fixed code such as gender. DATE holds a calendar date.

Think of SERIAL as a ticket machine at a counter. Each new row pulls the next ticket (7, then 8, then 9) without asking. VARCHAR(150) is a name badge with room for 150 letters; most names use far less. CHAR(1) is a single-letter stamp such as M or F. DATE is a calendar stamp in YYYY-MM-DD form.

NOT NULL is a rule that forces a value. In the example, last_name is VARCHAR(150) NOT NULL, so every insert must supply a last name. First name has no such rule in the example, so it can stay empty. That split is a teaching choice: surnames drive sorting and credits, so they are mandatory here, while given names stay optional. In a real casting database both would usually be mandatory, which is a later design call.

Missing a comma between column lines is a common early error. The tool reports a syntax error near the next column. Adding the comma and running again fixes it. The missing comma syntax error fix is simple: read which column the error points at, look at the end of the line above it, and add the comma. A second early error is a misspelled type such as VARCHRA, which fails at run time the same way.

Dialect extras on this one concept: Postgres SERIAL has SMALLSERIAL, SERIAL, and BIGSERIAL (16, 32, and 64 bit). MySQL uses INT AUTO_INCREMENT (with TINYINT, INT, BIGINT sizes). Snowflake uses AUTOINCREMENT or IDENTITY with optional start and step. Databricks uses IDENTITY columns. NOT NULL and length caps work the same in all four.

Small-number trace: insert a row with only last_name supplied. The engine pulls ticket 1 for actor_id, stores the given last_name, leaves first_name empty, and stamps the dates supplied. Insert a second row and actor_id becomes 2 automatically. Try inserting with no last_name and the statement is rejected for violating NOT NULL. That accept-then-reject pair is the full behavior check.

Exam note: SERIAL auto-fills plus one and stays unique; VARCHAR needs its length; NOT NULL forces a value; a missing comma points at the next column.

2.2.4 Audit Columns Add Date and Update Date

Two extra date columns, add_date and update_date, track when a row was added and when it was last changed. They are simple to add and they pay off when fresh rows need review. A larger team setup can also add add_by as VARCHAR(100) to record who added the row. That gives who plus when for both creation and last change. For now the example keeps only add_date and update_date.

Audit columns (add_date, update_date, and optionally add_by) answer when and by whom without touching the business facts. They never drive joins; they drive debugging, refresh checks, and compliance reviews.

In this lecture the two columns are plain DATE fields filled by load scripts or by later UPDATE statements, not by automatic defaults. That is a starter pattern. Production Postgres often upgrades the pattern with DEFAULT CURRENT_DATE or with timestamp columns plus triggers that stamp update_date on every write. MySQL does the same with DEFAULT CURRENT_TIMESTAMP and ON UPDATE CURRENT_TIMESTAMP. Snowflake and Databricks pipelines usually stamp these columns in the load job itself. The lecture keeps the plain form so the CREATE TABLE actors statement stays readable, with SERIAL key and audit dates visible on one screen.

Picture the row as a library card with a Due-date slip stapled on the back. The front holds the facts (name, birth date). The slip holds add_date and update_date. Librarians never shelve by the slip, but they always check the slip when a card looks new or stale.

Audit dates only help when something writes them. A column that stays NULL forever is dead weight. Decide at build time who writes add_date on insert and who refreshes update_date on change, or the columns mislead instead of helping.

Concrete row: actor_id 1, first_name Penny, last_name Hofstadter, add_date 2024-01-10, update_date 2024-01-10. After a spelling fix, update_date moves to 2024-03-02 while add_date stays put. The sense-check: add_date never moves, update_date moves on every real change.

Build the container, declare the shape, let the key auto-fill, and staple on audit dates. Actors is now live and the same loop builds every table after it.

2.3 Creating the Directors Table

2.3.1 Build Statement Column by Column

The directors table build follows the same shape as actors, which is the point: once one people table works, the second is a near copy with one swapped column.

CREATE TABLE directors (
  director_id SERIAL PRIMARY KEY,
  first_name VARCHAR(150),
  last_name VARCHAR(150),
  date_of_birth DATE,
  nationality VARCHAR(20),
  add_date DATE,
  update_date DATE
);

Steps are open CREATE TABLE directors with parentheses, add director_id as SERIAL PRIMARY KEY for the auto-filled unique key, add first_name and last_name as VARCHAR(150), add date_of_birth as DATE, add nationality as VARCHAR(20), add add_date and update_date as DATE, close the parentheses, and run it. Refresh Tables to confirm that both actors and directors now show up.

A people-table template repeats: auto-filled key, two name fields, one birth date, one descriptor (gender in actors, nationality in directors), plus the two audit dates. Learn the template once and each new people table is a five-minute copy with small edits.

The one deliberate difference is nationality VARCHAR(20) replacing gender CHAR(1). Nationality needs a variable code or short name (US, UK, French, South Korean), so a capped VARCHAR fits better than a single fixed character. Length 20 leaves room for full short names while blocking paragraph-length entries. Everything else mirrors actors on purpose, including the audit pair, so later UNION-style comparisons and joins read the same way.

Dialect twins: MySQL writes director_id INT AUTO_INCREMENT PRIMARY KEY with nationality VARCHAR(20). Snowflake writes director_id NUMBER AUTOINCREMENT PRIMARY KEY. Databricks writes director_id INT with an IDENTITY default. The directors table build keeps the same columns and order in each system.

Build trace for directors: run the statement in a query tab on the movies database, then Refresh Tables. Both actors and directors now show up side by side, each with 7 columns. Insert one test director (first_name Alfred, last_name Hitchcock, nationality UK) and director_id fills itself with the next number. That two-table listing is the worked proof that the template copied cleanly.

Scope: this statement assumes actors already exists but does not depend on it; the two people tables are independent parents. Assumption: nationality stays a short label. When a project needs full country names plus codes, split to a separate countries table later instead of widening this column without end.

2.3.2 Check Structure With SELECT

An empty SELECT is a fast structure check:

SELECT * FROM directors;

Even with no rows it returns column headers with types. Director_id shows as integer because SERIAL stores integers. First name and last name show as character varying with length 150. Date of birth shows as date. Nationality shows as varchar 20. Add date and update date show as date. The same SELECT pattern works for every new table and shows right away if a type or length was typed wrong. A typo such as VARCHRA instead of VARCHAR throws an error at run time, and fixing the spelling then running again creates the table. That CREATE TABLE directors and SELECT structure check loop is the habit to keep: build, then immediately read back the shape.

Think of SELECT star on an empty table as shaking an empty box to hear the dividers rattle. No items fall out, but the shape answers back: how many slots, which labels, which sizes. When a divider is wrong (wrong length, wrong type), this shake exposes it before any data moves in.

In pgAdmin the headers appear in the result grid with the type line beneath each name. With psql the twin check is \d directors, which lists each column plus its default and any key. In MySQL the twin is DESCRIBE directors;. In Snowflake it is DESCRIBE TABLE directors;. In Databricks it is DESCRIBE TABLE directors;. All five answer the same question: did the stored shape match the typed statement?

Empty-table read-back: run SELECT star on fresh directors and read the header row. Expect director_id integer, first_name character varying(150), last_name character varying(150), date_of_birth date, nationality varchar(20), add_date date, update_date date. When every header matches, the structure check passes. When one header surprises you, drop or fix the table now, not after loading 37 directors.

SELECT star is a structure flashlight here, not a production query pattern. On wide or huge tables it drags back every column. For checks it is ideal; for application code, name only the columns needed.

Exam note: copy the people-table template, run the directors table build, then prove it with the empty SELECT structure check before loading any rows.

2.4 Creating the Movies Table With a Foreign Key

2.4.1 Movie Columns and Types

The movies table keeps one row per film:

CREATE TABLE movies (
  movie_id SERIAL PRIMARY KEY,
  movie_name VARCHAR(100) NOT NULL,
  movie_length INT,
  movie_language VARCHAR(20),
  age_certificate VARCHAR(10),
  release_date DATE,
  director_id INT REFERENCES directors (director_id)
);

Movie_id is SERIAL PRIMARY KEY. Movie_name is VARCHAR(100) NOT NULL because every film must have a name. Film names are short in practice so 100 is enough. Movie_length is INT for run time. Movie_language is VARCHAR(20). Age_certificate is VARCHAR(10) for codes such as PG-13. Release_date is DATE. Director_id is the link to directors and is covered next.

A NOT NULL name plus an auto key is the standard deal for catalog tables: the key names the row for the machine, the name field names it for humans, and the NOT NULL rule keeps anonymous rows out. Every other column then describes the item (length, language, certificate, date) or links it (director).

Why these caps? VARCHAR(100) for names fits long titles with headroom while blocking essay-length entries. VARCHAR(20) for language fits English, French, and similar labels. VARCHAR(10) for age_certificate fits PG, PG-13, 12, 15, R, and U without waste. INT for length supports minute math and sorting. DATE for release_date supports year filters and range queries. Each cap was picked by browsing real values first, then adding margin.

Dialect extras: MySQL writes movie_id INT AUTO_INCREMENT PRIMARY KEY and the same VARCHAR caps. Snowflake writes movie_id NUMBER AUTOINCREMENT PRIMARY KEY with VARCHAR (no length required, but caps still allowed). Databricks writes movie_id INT with STRING or VARCHAR for the text fields. The shared concept is one capped name, numeric length, short codes, one date, and one integer link.

Read-back check: after running the statement, run SELECT star FROM movies on the empty table. Expect movie_id integer key, movie_name varchar(100) mandatory, movie_length INT, movie_language varchar(20), age_certificate varchar(10), release_date date, director_id INT link. Try inserting a film with no name and the insert is rejected by NOT NULL. Insert one named film and the row sticks. That accept-reject pair proves the column rules.

Scope: VARCHAR caps guard shape, not truth. VARCHAR(10) accepts a wrong code such as ZZ with no complaint. Real code lists (allowed certificates, allowed languages) need a CHECK rule or a lookup table, which comes later.

2.4.2 REFERENCES Links Movies to Directors

A foreign key links two tables for data joins and checks. To build one, make a normal column with the same type as the target key, then add REFERENCES plus foreign table plus foreign column in parentheses. Here director_id is INT because director_id in directors is a serial integer. The clause REFERENCES directors (director_id) points it at directors. Keeping the same column name on both sides is a habit that makes INNER JOIN and other joins far easier to read. That movies REFERENCES directors link is the first live relationship in the database.

REFERENCES directors (director_id) turns a plain integer column into a guarded pointer. Every movies row must name a director_id that already exists in directors. The database checks each insert and each update, so joins never meet a dangling pointer.

After running the statement, right-click Tables and pick Refresh. The movies table appears with movie_id, movie_name, and the rest. Under Constraints a new entry named movies_director_id_fkey appears. That entry proves the foreign key was stored. Later join work builds on that constraint. The constraint name follows the Postgres default pattern of table, column, plus fkey, so movies plus director_id plus fkey becomes movies_director_id_fkey.

Picture a coat-check ticket. The movie row holds ticket 3. The directors table holds hook 3 with a real director hanging on it. The REFERENCES check is the attendant who refuses a ticket with no hook. Same-type plus same-name (INT to INT, director_id to director_id) is what lets the attendant match ticket to hook at a glance.

Per-system wording: Postgres uses the inline REFERENCES form shown here. MySQL prefers a table-level FOREIGN KEY (director_id) REFERENCES directors (director_id) line, often with ON DELETE and ON UPDATE rules. Snowflake accepts REFERENCES with the same spelling but enforces it only when the constraint is marked ENFORCED. Databricks Delta declares the FOREIGN KEY as metadata that guides the optimizer. The lecture keeps the Postgres inline form because pgAdmin shows the resulting movies_director_id_fkey constraint directly.

Link proof in three moves. First, insert a director and note the id, say 1. Second, insert a movie naming director_id 1 and the row is accepted. Third, try a movie naming director_id 9999 with no such director and the insert fails on the foreign key. Final state: one accepted movie tied to director 1, one rejected orphan, and movies_director_id_fkey visible under Constraints. That trio is the full worked check.

Two traps: typing the link as the wrong type (VARCHAR pointing at an INT key) fails or silently blocks the constraint, and loading movies before directors fails every row because no parent exists yet. Match the type, keep the name, and load directors first.

Exam note: state the REFERENCES recipe (same-type column plus REFERENCES table plus column), name the proof constraint movies_director_id_fkey, and explain why same-name links keep future joins readable.

2.5 Creating the Movies Revenues Table

2.5.1 Build Statement With Money Columns

The movies_revenues table keeps money per film:

CREATE TABLE movies_revenues (
  revenue_id SERIAL PRIMARY KEY,
  movie_id INT REFERENCES movies (movie_id),
  revenues_domestic NUMERIC(10, 2),
  revenues_international NUMERIC(10, 2)
);

Revenue_id is SERIAL PRIMARY KEY. Movie_id is INT with REFERENCES movies (movie_id) so each revenue row must match a real movie. Revenues_domestic and revenues_international are NUMERIC(10, 2), which means up to 10 digits in total with 2 digits after the decimal point for cents. Open a new query tab on the movies database, paste the statement, and run it. Refresh Tables and the new table appears. That CREATE TABLE movies_revenues with NUMERIC money columns is the complete money-table pattern.

Think of NUMERIC(10, 2) as a cash register with 10 digit wheels, where the last two wheels are locked as cents. A value such as 12345678.90 fits (8 digits plus 2 cents). A value needing 9 whole digits plus cents overflows. The register never rounds silently the way a float register can.

Why NUMERIC and not a float? Money needs exact cents. Float and real types store approximations, so repeated sums can drift by a cent. NUMERIC stores the exact decimal digits, so totals, taxes, and splits stay precise. The first number (precision 10) caps total stored digits; the second (scale 2) locks two of them as cents. Domestic here means inside the US and international means outside the US, so the two columns split one worldwide total into two audit-friendly parts.

Dialect extras on this shared concept: Postgres NUMERIC(10, 2) equals DECIMAL(10, 2). MySQL uses DECIMAL(10, 2) most often, with the same precision-scale meaning. Snowflake uses NUMBER(10, 2) or NUMERIC(10, 2) interchangeably. Databricks Spark SQL uses DECIMAL(10, 2). All four keep the same habit: exact decimal type for money, float types only for science and sensor readings.

Money fit check: 250000.75 fits NUMERIC(10, 2) with room to spare. 123456789.99 needs 9 whole digits plus 2 cents (11 digits) and is rejected as too wide. Insert a revenue row for a real movie_id and it sticks; insert one for a missing movie_id and REFERENCES blocks it. That width-plus-link pair is the worked proof.

Scope: NUMERIC(10, 2) caps size, not sign. Negative revenue still fits unless a CHECK rule blocks it. Assumption: one revenue row per movie is a data habit here, not a lock; nothing in this shape alone stops two rows for the same film. A UNIQUE rule on movie_id would lock one-to-one later.

2.5.2 Confirm Constraints and Types

Open Constraints under movies_revenues to see the movies_revenues_movie_id_fkey entry. That is the stored foreign key. Run a check query:

SELECT * FROM movies_revenues;

The header shows revenue_id as integer primary key, movie_id as integer foreign key, and both revenue columns as numeric with decimals. This check catches a wrong table name or wrong column name before data gets loaded. For instance, pointing at movie (singular) instead of movies, or at movieid without the underscore, fails at build time with a missing-relation error, which is far cheaper than finding it after loading 53 revenue rows.

A constraint entry is the stored proof that a rule survived the build. The primary key entry guards uniqueness; the movies_revenues_movie_id_fkey entry guards the parent link. Reading Constraints plus running the empty SELECT is the two-minute audit that every new table deserves.

Picture airport luggage tags. Revenue_id is the unique tag on each money bag. Movie_id is the destination tag that must match a real flight (a real movie). The Constraints tab is the tag scanner readout: one line per tag type. When the scanner shows both tags, the table can board data.

Audit trace: expand movies_revenues, then Constraints, and confirm movies_revenues_movie_id_fkey is listed. Run the empty SELECT and confirm revenue_id integer, movie_id integer, revenues_domestic numeric, revenues_international numeric. Both confirmations together mean the link and the money types are stored correctly.

Exam note: money stays NUMERIC with cents, every revenue row points at a real movie, and the fkey entry plus the empty SELECT prove both facts before loading.

2.6 Junction Table for Movies and Actors

2.6.1 Why a Junction Table Exists

One movie has many actors and one actor appears in many movies. That many-to-many link needs its own table. A junction table (a small table that mostly holds foreign keys from two other tables so they can act as one transaction table) solves exactly this. Here movies_actors holds only movie_id and actor_id. Later queries use it to list cast per film or films per actor.

Think of it like a sign-up sheet with two columns: which film and which actor. The sheet itself has no film facts and no people facts. It only records pairs. The sign-up sheet for movies actors pairs is the lecture image to keep: film in the left column, actor in the right column, one line per appearance. A film with six cast members takes six lines; an actor in three films takes three lines.

Why not just add actor columns to movies? Because casts vary in size. A wide table with actor_1 through actor_5 breaks on the sixth actor and wastes slots on a two-person film. The narrow sign-up sheet never cares how large the cast grows: more actors simply mean more lines, never more columns.

Notes here call this a long narrow table design rather than a wide fat table with one column per actor. The narrow pair design stays flexible when cast size changes. It also keeps facts in one place: film facts stay in movies, people facts stay in actors, and only the pairing lives in the middle. That split avoids repeating a film title once per actor or an actor name once per film.

The pattern is universal. MySQL course databases use film_actor the same way. Snowflake many-to-many joins use the same bridge shape. Databricks lakehouse designs call it a bridge table with the same two-key layout. The name changes (junction, bridge, link, association), but the narrow two-column job does not.

Many-to-many always gets a middle sheet with two links. Narrow pairs scale; wide actor columns do not.

2.6.2 Two Foreign Keys Plus a Composite Primary Key

Build it with two REFERENCES clauses and one composite key:

CREATE TABLE movies_actors (
  movie_id INT REFERENCES movies (movie_id),
  actor_id INT REFERENCES actors (actor_id),
  PRIMARY KEY (movie_id, actor_id)
);

Movie_id is INT pointing at movies. Actor_id is INT pointing at actors. The last line PRIMARY KEY (movie_id, actor_id) marks the pair as the key. Earlier tables put the primary key on one column such as movie_id in movies or actor_id in actors. Here the key spans two columns. That stops the same pair from being stored twice and helps the system find rows without a slow sequential scan over the whole table. After running, Refresh shows movies_actors plus two foreign key entries and one primary key entry under Constraints. That junction composite primary key is the heart of this section.

A composite primary key is a key made of two columns together. Neither column alone is unique here (one film repeats across many actors, one actor repeats across many films), but each pair appears once. The pair is the row name.

Walk the guards one by one. The first REFERENCES line rejects any movie_id with no matching movies row. The second REFERENCES line rejects any actor_id with no matching actors row. The PRIMARY KEY line rejects a repeated pair such as (10, 4) twice, while still allowing (10, 4) and (10, 5) side by side. Together the three lines mean every stored line names a real film, a real actor, and a fresh pairing.

Picture the sign-up sheet with a bouncer holding two lists plus a duplicate detector. The bouncer checks the film list, checks the actor list, then scans the sheet for the same pair. Only a new pair of known names gets a new line.

Dialect extras: Postgres uses the inline REFERENCES plus PRIMARY KEY pair form shown here. MySQL writes the same shape with FOREIGN KEY lines and may add an extra AUTO_INCREMENT id, though the pair key alone is cleaner for this case. Snowflake accepts the same pair-key spelling. Databricks Delta declares the pair key as informational. Only Postgres and MySQL enforce all three guards by default in these exercises.

A quick check query:

SELECT * FROM movies_actors;

Right now both key columns show as primary key columns. The empty result still proves the shape: two integer link columns, both flagged as key parts.

Pair-behavior trace on film 10 with actors 4 and 5. Insert (10, 4) and it sticks. Insert (10, 5) and it sticks, because the pair is new. Insert (10, 4) again and the build rejects the duplicate pair. Insert (9999, 4) with no such film and REFERENCES rejects the orphan. Those four moves prove both guards.

A junction table with its own extra id column and no pair key allows silent duplicates, which then double-count cast queries. When only the pair key guards the sheet, duplicates cannot sneak in. Keep the pair key even when an id column is added for tooling.

Exam note: two REFERENCES guard the names, one composite key guards the pair, and the sign-up sheet stays narrow no matter how casts grow.

2.7 Loading Sample Data in the Right Order

2.7.1 File Order and Insert Steps

Sample data ships as script files: directors.sql, actors.sql, movies.sql, movies_actors.sql, and movies_revenues.sql. Order matters because foreign keys block orphans. Load parent tables before child tables. The safe order used here is directors first, then actors, then movies, then movies_actors, then movies_revenues. That sample directors actors movies load sequence is the habit to memorize.

Parents before children means every referenced row exists before any row that points at it. Directors and actors are parents. Movies is a child of directors and a parent of the two tables after it. The junction and revenue tables are children of everything they point at, so they load last.

For each file, open a query editor on the movies database, use Open to load the file, select all, and run it. Each file holds INSERT INTO statements with the matching columns. A success message with a millisecond time means rows went in. Then verify with a count query such as SELECT * FROM directors. Repeat for each file in order. When a file lists explicit column names in its INSERT INTO line, keep that order aligned with the VALUES order; a swapped pair silently stores birth dates in name fields when types happen to allow it.

Why does the guard fire? Because REFERENCES checks each child row at insert time. A movies row naming director 12 fails when directors holds no 12. A junction row naming movie 40 fails when movies holds no 40. Loading in parent order turns every check green by arrival time.

Real-world: the same parent-before-child load order is standard in test fixtures and data restores where foreign keys are active. Backup tools usually dump parents first or disable checks during restore and re-check at the end for the same reason.

Load drill in order: run directors.sql and count 37. Run actors.sql and count 147. Run movies.sql and count 53. Run movies_actors.sql and count 70. Run movies_revenues.sql and count 53. The bolded pass signal is five green counts in that exact order. Run movies_actors.sql first on an empty database and the whole file fails on missing parents, which is the guard doing its job.

Scope: these scripts assume empty tables with matching shapes. Re-running a file without clearing the table doubles rows or collides on keys. Assumption: the query tab is connected to movies. Running a load file while connected to postgres fills the wrong database with look-alike tables.

2.7.2 Row Counts After Each Load

After running each script and checking with SELECT *, the counts seen are 37 rows in directors, 147 rows in actors, 53 rows in movies, 70 rows in movies_actors, and 53 rows in movies_revenues. Movies_actors has 70 pairs because many films have more than one actor. Movies_revenues has 53 rows because each of the 53 movies has one revenue row. If a child file runs before its parent, the REFERENCES check fails. Going back and loading in the listed order fixes it.

Read the counts as a story, not five lone numbers. 37 directors made 53 films, played by 147 actors across 70 cast pairings, with 53 money rows (one per film). When one number drifts (say 69 pairs instead of 70), exactly one pairing file missed a line, not the whole pipeline.

A sharper check than SELECT star is a count plus a join spot-check:

SELECT COUNT(*) FROM directors;
SELECT COUNT(*) FROM movies_actors;
SELECT m.movie_name, COUNT(a.actor_id) AS cast_size
FROM movies m
LEFT JOIN movies_actors a ON a.movie_id = m.movie_id
GROUP BY m.movie_name
ORDER BY cast_size DESC;

The first two confirm the headline counts. The third confirms the shape behind 70: most films show one or two cast rows, a few show more, and none show zero in this sample. In MySQL, Snowflake, and Databricks the same counts and the same COUNT star checks apply; only the file-open path differs (MySQL Workbench, Snowflake worksheets, Databricks notebooks).

Count audit: directors 37, actors 147, movies 53, movies_actors 70, movies_revenues 53. The sense-check: pairs exceed films because casts share films, while revenue rows equal films because money here is one row per film. When all five match, the load is done.

Exam note: load parents before children, then match the five counts 37, 147, 53, 70, 53. Out-of-order loads fail on REFERENCES by design.

2.8 Creating Tables With the pgAdmin GUI

2.8.1 Accounts Table Built by Clicks

What if you need a table but do not want to type SQL yet? The GUI can build a table without typing CREATE TABLE. Pick a practice database, right-click Tables, pick Create and then Table, and name it accounts. Keep owner as postgres and schema as public. Partition options can stay off for basic use. Then open the Columns tab and press the plus sign for each column. Those accounts GUI columns are the hands-on proof of this section.

Example columns are account_id as serial set as primary key by clicking the key toggle, username as character varying 100, user_password as character varying 50, user_email as character varying 255, add_date as timestamp with time zone, and update_date as timestamp with time zone. The GUI hides length boxes for types that need no length, which is a smart hint about which types take precision. Press Save. The accounts table appears. A check with SELECT * FROM accounts shows the empty table with new columns.

The GUI build runs the same CREATE TABLE underneath. Each plus-sign row becomes one column line; the key toggle becomes PRIMARY KEY; each length box becomes the (n) in VARCHAR(n). The SQL preview tab shows the generated statement before it runs.

Step-by-step with checkpoints: name the table accounts and confirm the name has no spaces. Add account_id serial, flip the primary-key toggle, and confirm the key icon lights up. Add username character varying 100, user_password character varying 50, and user_email character varying 255 with the wider cap for long addresses. Add add_date and update_date as timestamp with time zone so later apps can store exact moments, not just days. Open the SQL tab, read the generated CREATE TABLE once, then press Save and Refresh Tables.

The same click path exists elsewhere with different labels: MySQL Workbench uses Create Table with datatype pickers and PK checkboxes. Snowflake Snowsight worksheets favor typed SQL over clicks. Databricks uses Create Table from the catalog UI. The lecture uses pgAdmin because the course database is Postgres.

Click-trace for accounts: six plus-sign rows in the Columns tab, key toggle on account_id only, lengths 100, 50, and 255 on the three text fields, timestamp with time zone on both audit fields. Press Save and run SELECT star FROM accounts. The empty grid with 6 headers is the pass signal. Missing headers mean Save did not run; extra headers mean a stray plus-sign row slipped in.

GUI speed hides one risk: clicking Save on the wrong database builds a look-alike accounts table where nobody looks for it. Confirm the navigator path (practice database, public schema) before the first plus-sign click.

2.8.2 Data Types on Offer

The type drop-down shows char, bigint, boolean for true and false, character varying which is varchar, date, timestamp with or without time zone, integer, numeric with precision and scale for decimal places, real, smallint for small integers, text for very long text, time with or without time zone, json for semi-structured data, and uuid. JSON support in Postgres is strong and gets its own later topic. UUID is flagged as useful for tight secure keys and gets its own later topic. Later work also covers password storage methods, so plain character varying for passwords here is only a starter stand-in.

Think of the drop-down as a toolbox with small drawers. Small drawers (smallint, integer, bigint) hold whole numbers of different sizes. Glass jars (char, varchar, text) hold text of fixed, capped, or open length. Clocks (date, time, timestamp with or without time zone) hold calendar facts. The locked safe (numeric with precision and scale) holds exact money. The specialty drawers (boolean, json, uuid, real) each solve one focused job.

A few picks deserve a closer look. Boolean stores true and false natively, which beats CHAR(1) flags for readability. Text holds very long text with no cap, which suits bios and notes. Timestamp with time zone pins an exact moment across regions, which beats plain DATE for login and audit trails. JSON holds semi-structured payloads such as preferences or event blobs without new columns per field. UUID holds globally unique ids that stay hard to guess, which suits public-facing keys better than sequential SERIAL values.

Cross-system extras on the same shared concept: Postgres SERIAL and BIGSERIAL become MySQL INT AUTO_INCREMENT and BIGINT AUTO_INCREMENT, Snowflake NUMBER AUTOINCREMENT, and Databricks IDENTITY. Postgres character varying matches MySQL VARCHAR, Snowflake VARCHAR, and Databricks STRING or VARCHAR. Postgres NUMERIC matches MySQL DECIMAL, Snowflake NUMBER, and Databricks DECIMAL. Postgres JSON matches MySQL JSON, Snowflake VARIANT or OBJECT, and Databricks STRUCT or MAP types. Postgres UUID matches MySQL CHAR(36) storage in older setups and Snowflake or Databricks STRING storage for UUID text. One concept, four spellings; keep the Postgres spelling for this course and recognize the twins.

Type-matching drill: a login flag becomes boolean, a 200-word bio becomes text, a payment amount becomes numeric(10, 2), a login instant becomes timestamp with time zone, an app-settings blob becomes json, and a public API key becomes uuid. When each fact lands in its matching drawer, queries stay short and fast.

Plain character varying for user_password here is only a starter stand-in. Real systems never store raw passwords; they store salted hashes with a dedicated password-hashing function. Treat this column as a shape demo, not a security pattern.

Clicks build the same tables as typed SQL; the drop-down teaches which drawer fits which fact. Passwords, JSON, and UUID each get deeper coverage later.

2.9 Viewing Structure and Adding a Column

2.9.1 Two Ways to View Structure

There are two fast ways to see a table shape. One is to run SELECT * FROM accounts and read the headers. The other is to right-click the table, pick Properties, and open Columns to list every column. The Constraints tab shows the primary key, normally named accounts_pkey on account_id when it is serial. It also lists any foreign key, check, or unique entries. The Advanced tab shows autovacuum and related settings. The Security tab shows access rules. The SQL tab shows the internal SQL the system built for the table. Press Cancel to close without changes.

Headers plus Properties give two views of one truth. The SELECT headers show the live shape as queries see it. The Properties tabs show the stored rules behind that shape: keys in Constraints, tuning in Advanced, access in Security, and the full build text in the SQL tab.

Use the two views for different questions. Headers answer what columns exist right now. Columns tab answers each type plus length plus default plus NOT NULL flag. Constraints answers which key guards account_id (accounts_pkey when account_id is serial) and whether any foreign key, check, or unique rule exists. SQL tab answers what statement would rebuild this exact table, which is handy before a risky change. Advanced answers storage tuning such as autovacuum behavior. Security answers who may read or write.

The twins in other tools: psql uses \d accounts for the same readout. MySQL Workbench uses Table Inspector. Snowflake uses DESCRIBE TABLE accounts;. Databricks uses DESCRIBE TABLE accounts;. All five show columns plus keys; only the click path differs.

Two-view drill on accounts: run SELECT star and count 6 headers. Open Properties, then Columns, and count the same 6 rows with matching types. Open Constraints and confirm accounts_pkey on account_id. Open the SQL tab and read the generated CREATE TABLE text. When headers, Columns, Constraints, and SQL all agree, the structure read is complete.

Properties dialogs edit on Save. Opening to look is safe, but flipping a toggle and pressing Save by habit changes a live table. When only inspecting, press Cancel to close without changes.

2.9.2 Add Is Enabled With Default and NOT NULL

To add a column, right-click Columns under the table, pick Create and then Column, and name it is_enabled. Pick character varying with length 2. Save once to create it. Then right-click the new column, pick Properties, open Definition, set NOT NULL to Yes so every row must hold a value, and set Default to a quoted Y so new rows pre-fill with Y. That add is_enabled column with quoted default and NOT NULL sequence is the full pattern.

Adding a guarded flag takes three moves: create the slot (is_enabled varchar 2), require a value (NOT NULL), and pre-fill new rows (DEFAULT 'Y'). The default fills future inserts; the NOT NULL rule blocks empty writes.

A common snag is typing Y with no single quotes. The SQL tab then shows ALTER TABLE accounts ALTER COLUMN is_enabled SET DEFAULT Y with no quotes, and Save fails. Going back to Definition and typing 'Y' with quotes changes the SQL tab to SET DEFAULT 'Y' and Save works. The unquoted default Y save fails because Y without quotes reads as a column or keyword, not as the text value Y. The quoted 'Y' reads as text, so the default stores. To review, right-click accounts, pick Properties, open Columns to see is_enabled in the list, then open the single column to see its default. That two-level check is normal in pgAdmin.

The typed-SQL twin of the same two saves is:

ALTER TABLE accounts ADD COLUMN is_enabled VARCHAR(2);
ALTER TABLE accounts ALTER COLUMN is_enabled SET DEFAULT 'Y';
ALTER TABLE accounts ALTER COLUMN is_enabled SET NOT NULL;

MySQL, Snowflake, and Databricks accept the same ALTER TABLE ADD COLUMN shape with small spelling shifts (MySQL MODIFY COLUMN for later edits, Snowflake ALTER TABLE ADD COLUMN, Databricks ALTER TABLE ADD COLUMNS). The quoted-text rule holds in all four: text defaults need single quotes.

Default-behavior trace: with DEFAULT 'Y' plus NOT NULL stored, insert an account row without naming is_enabled and the new row shows is_enabled = 'Y'. Try inserting with is_enabled left empty under NOT NULL and no default, and the write is rejected. First Save creates the slot; second Save arms the guard. That pair proves the flag works.

Adding a NOT NULL column to a table that already holds rows needs a plan for old rows: backfill them first or add the column with a default in one move. Adding the bare column, then flipping NOT NULL with NULLs still present, fails on existing data.

Exam note: two views prove structure (headers plus Properties with accounts_pkey), and the flag pattern is create, then quote the default as 'Y', then require NOT NULL.

2.10 Rename, Drop, and Change Column Type

2.10.1 Rename a Column

Pick the column, right-click, pick Properties, and change Name. For example change add_date to add_date_new and Save, then change it back to add_date the same way. The SQL tab shows the behind-the-scenes form ALTER TABLE public.accounts RENAME add_date TO add_date_new. That statement is the same one used in the query tool. It is a handy path for small admin fixes. That rename drop column type trio starts here with the safest move.

RENAME relabels the slot without touching stored values. Data stays; only the header changes. Every query, view, and script that names the old header must move to the new header together.

The round-trip (rename out, rename back) is a practice drill that proves renames are cheap and reversible on empty or small tables. On live tables the same move needs a wider check: views, reports, application code, and load scripts that name add_date all break until they adopt the new label. Rename during a quiet window, update every caller, and re-run a smoke query after the change.

The typed twin is one line:

ALTER TABLE public.accounts RENAME add_date TO add_date_new;

MySQL spells a rename as CHANGE COLUMN or RENAME COLUMN depending on version. Snowflake uses RENAME COLUMN. Databricks uses RENAME COLUMN as well. The lecture keeps the pgAdmin click path plus the Postgres ALTER TABLE RENAME spelling because the SQL tab displays it directly.

Rename proof: rename add_date to add_date_new, Save, and run SELECT star FROM accounts. The header now shows add_date_new in place of add_date with values untouched. Rename it back and the header returns to add_date. Same data, new label, then label restored.

Scope: RENAME moves the label, not the meaning. Renaming user_password to password_hash without changing how values are stored misleads every later reader. Rename labels only when the new label still describes the stored values.

2.10.2 Drop a Column Safely

To practice a drop, first add a throwaway column such as add_by as character varying 100 and Save. Then find that exact row in the column list. The list highlight can sit on the wrong row, so check the name before acting. Right-click the add_by row, pick Delete or Drop, confirm when asked if add_by should be dropped, and press OK. Refresh and run SELECT * FROM accounts to confirm the column is gone. The same care applies to real data: always confirm the highlighted name matches the intended column. That confirm highlighted column name before drop habit is the main safety lesson.

Think of DROP as shredding one divider plus everything filed behind it. Values in that column vanish for every row at once, and no Undo brings them back. The two-second name check (read the highlighted row, read the confirm dialog, then press OK) is the whole safety system.

The typed twin is:

ALTER TABLE accounts DROP COLUMN add_by;

Practice flow in full: add add_by varchar 100, Save, verify it appears in headers, then drop exactly that row, confirm the dialog names add_by, press OK, Refresh, and re-run SELECT star to confirm 6 columns again with no add_by. On a copy of real data the same flow applies, plus a backup first. MySQL, Snowflake, and Databricks use the same DROP COLUMN spelling.

Drop drill: after adding add_by, headers count 7. Drop the add_by row, confirm the dialog reads add_by should be dropped, press OK, Refresh, and headers return to 6 with no add_by. The count down plus the missing header is the worked proof of a clean drop.

Never drop on a live table without a backup and a caller check. Reports, views, and inserts that name the dropped column fail from that moment on. Practice drops belong on throwaway columns and test databases.

2.10.3 Change Type Inside One Type Family

Types can shift inside pgAdmin when the start and end types are close. Example: is_enabled starts as character varying 2. To make it character 2, open the full table Properties, change the type cell to character, and Save. Confirm by reopening Properties and Columns. The reverse path also works per column: right-click is_enabled, pick Properties, change Definition back to character varying, check the SQL tab which reads ALTER TABLE public.accounts ALTER COLUMN is_enabled TYPE varchar, and Save. Now it reads as character varying again.

In-family type moves (varchar to text, varchar to character, integer to bigint) keep stored values readable because the bytes translate directly. Cross-family moves (numbers to dates, text codes to numbers) need explicit casts and a copy plan, so the GUI wisely refuses them.

Why the limit helps: character varying 2 to character 2 only changes padding behavior, so 'Y' stays 'Y'. A jump such as numeric to varchar risks failed casts on odd values, lost sorting behavior, and broken sums, so it belongs in a planned migration with checks, not a one-click toggle.

The drop-down only offers close kin such as character varying to text or character. It will not offer a jump such as numeric to varchar. That limit is by design. A cross-family change needs the query editor plus a data move plan: build a new table with the new type, copy rows across with casts, check counts, then swap. That fuller method gets its own later topic.

Typed twins for the in-family move:

ALTER TABLE public.accounts ALTER COLUMN is_enabled TYPE char(2);
ALTER TABLE public.accounts ALTER COLUMN is_enabled TYPE varchar(2);

MySQL uses MODIFY COLUMN for the same move, Snowflake uses ALTER COLUMN with compatible types, Databricks allows widening moves with ALTER COLUMN TYPE. The rename drop column type lesson ends here: rename and in-family changes are quick, drops are final, and cross-family moves wait for the copy-with-casts method.

Type-move trace: is_enabled as varchar(2) holds 'Y'. Convert to character(2), Save, and the value still reads 'Y' with padding rules changed. Convert back to varchar and the SQL tab shows ALTER COLUMN is_enabled TYPE varchar. Same value, new container, both moves confirmed in Properties.

Exam note: rename with RENAME, drop only the highlighted and confirmed column, and change types only inside one family in the GUI; cross-family moves need a copy with casts.

2.11 Deleting Tables From a Database

2.11.1 DROP TABLE by GUI and by SQL

Pick the database first, then open a query editor. For practice build a small table:

CREATE TABLE roles (
  role_id SERIAL PRIMARY KEY,
  role_name VARCHAR(100)
);

Refresh Tables to see roles. Run SELECT * FROM roles to confirm role_id as key and role_name as varchar 100. To remove it by clicks, right-click roles, pick Delete or Drop, and press OK. To remove it by SQL, run:

DROP TABLE roles;

A success message means it is gone. Running SELECT * FROM roles now fails with a does-not-exist error. Refresh Tables and roles is gone from the list. That CREATE roles practice table then DROP TABLE roles loop is the complete create-and-remove drill.

DROP TABLE removes the drawer, the dividers, and every filed item at once: the definition, all rows, plus indexes tied to the table. It is one statement with no Undo, which is why practice runs on a throwaway roles table.

Both paths do the same thing. The click path (Delete or Drop, then OK) suits one-off cleanup. The typed path (DROP TABLE roles;) suits scripts and repeatable teardowns. After either path, two checks prove removal: the SELECT fails with a does-not-exist error, and Refresh shows no roles node. When both agree, the table is truly gone rather than hidden by a stale navigator view.

Dialect notes: Postgres DROP TABLE roles; matches MySQL DROP TABLE roles;. Snowflake accepts the same spelling with optional CASCADE or RESTRICT. Databricks accepts DROP TABLE with the same spelling for managed tables (files removed) versus external tables (files kept). The lecture uses plain DROP TABLE on Postgres, which refuses the drop when a live view or foreign key depends on the table unless CASCADE is added.

Remove drill: create roles, Refresh, and confirm roles listed with 2 columns. Drop it by clicks or by SQL, then run SELECT star FROM roles and read the does-not-exist error. Refresh Tables and confirm roles missing from the list. Listed, then error, then missing: that sequence is the worked proof.

Scope: DROP TABLE on a parent with live children fails or, with CASCADE, removes the children silently depending on flags. Practice on roles is safe because nothing points at it. Production parents are never safe without the dependency check next.

2.11.2 Safety Rules Before a Drop

DROP TABLE is strong and fast, so care is needed on live systems. First test the drop in a test database. Then check for links such as foreign keys from other tables that point at this table. Removing a parent with live children can break queries and loads. So confirm no REFERENCES depend on it, or plan the child moves first. That caution is the main takeaway: easy to run, costly if run in the wrong place. Always test DROP TABLE and check foreign keys before touching a live table.

Think of DROP as demolishing a bridge pier while traffic still crosses. The test database is the scale model where demolition is free. The dependency check is the traffic survey: which roads (child tables, views, reports) still rest on this pier? Only when the model falls cleanly and the survey shows no traffic does the real pier come down.

Safety sequence in order: back up or snapshot first. List dependents by inspecting Constraints on child tables and any views that name the table. Move or drop children deliberately when the design calls for removal, or keep the parent when children must survive. Run the drop in the test database first and re-run the app smoke checks. Only then run it on the live database during a quiet window, and re-verify counts and joins after.

-- dependency-aware variants used beyond this lecture
DROP TABLE roles;
DROP TABLE IF EXISTS roles;
DROP TABLE roles CASCADE;

Plain DROP refuses when dependents exist. IF EXISTS skips the error when the table is already gone, which keeps scripts idempotent. CASCADE forces removal of dependents, which is powerful and dangerous in equal parts. The roles DROP TABLE safety lesson favors the first form on a throwaway table and saves the other two for scripted teardowns with backups.

Safety drill: in the test database, confirm no Constraints entry in any other table names roles. Run DROP TABLE roles there and re-run the smoke SELECT counts. Only when the test run shows no dependent errors is the live run even considered. That test-first gate is the behavior that exams and employers both reward.

Exam note: test DROP TABLE in a test database first, check foreign key links, and confirm removal with both the does-not-exist error and a refreshed table list.
