3.1 Creating a Practice Customers Table and Previewing Rows

Why build a tiny throwaway table before touching real customer data? Because every later write in this lecture can destroy or duplicate rows if you get it wrong, and a five-column practice table gives you a safe sandbox where mistakes cost nothing.

Think of the customers table as a sign-up sheet taped to a clipboard. Each column is a labeled blank on the form — first name, last name, mail, age — and each row is one filled-in form. The clipboard itself is the movies database: it can hold many sheets, and this lecture adds one small sheet just for practice.

The sheet analogy breaks in one useful way: a paper sheet lets anyone scribble anything in any blank, but a database column refuses facts that do not fit its type. That strictness is the whole point, and it is why this section names every type out loud.

3.1.1 Defining the customers table

A table (a named set of rows that all share the same columns) is created once and then read and changed many times. A column type (the rule that decides what fits in a column, for example short text or a whole number) is the guard on each blank. A primary key (the column whose value is different in every row, used to point at exactly one row) is how you pick rows safely later.

The practice build uses five columns. customer_id is the row key and the database fills it by itself. first_name and last_name hold short names. email holds a longer mail address. age holds a whole number:

CREATE TABLE customers (
  customer_id SERIAL PRIMARY KEY,
  first_name VARCHAR(50),
  last_name VARCHAR(50),
  email VARCHAR(150),
  age INT
);

SERIAL — a PostgreSQL shorthand that auto-fills 1, 2, 3, and so on for each new row. PRIMARY KEY — marks customer_id as one-of-a-kind; no two rows may share it and it is never empty. VARCHAR(n) — text with at most n characters, so VARCHAR(50) fits a name and VARCHAR(150) fits a long mail address. INT — a whole number such as 30 or 40, with no quotes around it.

In plain words: you are telling the database "make me a sheet with one self-numbering row number plus four blanks, and reject any name longer than its limit." Run this while connected to the movies database in your query editor. The tool answers with a short success note. That note means the empty sheet now exists. Refresh the table list, open the columns node, and confirm all five names and types before moving on.

The same idea wears different uniforms in other systems, and knowing the translations saves real debugging time. PostgreSQL accepts both the older SERIAL PRIMARY KEY used here and the newer standard form INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, which additionally blocks you from accidentally typing your own key value. MySQL has no SERIAL key in this sense; you write customer_id INT NOT NULL AUTO_INCREMENT PRIMARY KEY instead. Snowflake accepts INT AUTOINCREMENT or INT IDENTITY and treats almost every text column as variable-length VARCHAR even if you wrote CHAR, never padding with spaces. Databricks and Spark SQL support BIGINT GENERATED ALWAYS AS IDENTITY on newer runtimes. The lecture's SERIAL form is the PostgreSQL classroom version; for the same concept every other engine just spells "let the database number the rows" differently.

Type lengths also differ in strictness. In PostgreSQL and MySQL a VARCHAR(50) insert longer than 50 characters fails or is cut off, which is why the lecture gives mail addresses 150 characters while names get 50. In Snowflake the length is mostly a hint and the value still lands, but keeping the 50-versus-150 split is good design everywhere because it documents what you expect. INT behaves the same for this lecture in all four systems: whole numbers only, stored bare without quotes.

Worked build and check. Start connected to movies with no customers table. Step 1: run the CREATE TABLE block above. Expected result: a success note such as "query ran successfully" and a new customers entry in the table list. Step 2: expand the columns node and read the five entries — customer_id integer key, first_name 50-character text, last_name 50-character text, email 150-character text, age integer. Step 3: run SELECT * FROM customers; (covered next). Expected result: five column heads, zero data rows. That empty grid is the passing grade — it proves the sheet exists with the right shape. Sense-check: if the table list does not refresh, close and reopen the database node; the table is there, the browser view is just stale.

Picture the empty result as a grid: five labeled columns across the top, a single thin "no rows" band below. The horizontal axis is the column list, the vertical axis would be row numbers once rows arrive. Landmarks: the customer_id header carries a key icon in most editors, marking it as the row pointer. Takeaway: key icon plus five heads plus zero rows means "ready for inserts."

Scope: this practice table has no NOT NULL, no UNIQUE, and no foreign keys except the primary key itself. That keeps the lecture focused on writes, but it also means the table accepts half-empty rows (a customer with only a first name is fine here). A real customer table would add NOT NULL on required fields and UNIQUE on email. Assumption: you run each statement while connected to the movies database or schema. Run the same CREATE TABLE while connected to the wrong database and you build a look-alike table in the wrong place, then wonder why later reads come back empty.

Two traps catch almost everyone here. First, treating customer_id as a column you must fill during inserts — you must not; leave it out and the sequence fills 1, 2, 3 for you, but if you do force a value in PostgreSQL the sequence does not move and a later auto-insert can collide with your hand-typed number. Second, sizing email like a name: mail addresses with dots, plus-tags, and long domains easily pass 50 characters, so the lecture's 150 is deliberate. A third quiet trap is re-running CREATE TABLE after the table exists and reading the "already exists" error as a failure of your connection — it only means the sheet is already there; skip ahead to the read.

Recap: a typed five-column customers table with a self-filling key gives every later section a safe target, and SELECT * proves the shape before any data lands. Next, section 3.2 puts the first real row onto that empty grid with INSERT INTO.

Support teams, course sandboxes, and onboarding scripts all keep a scratch table exactly like this. They rehearse each new write here, read it back, and only then run the same shape against live tables — the same read-first, change, read-again loop this lecture drills from here on.

3.1.2 Reading all columns with SELECT star

A read-back (a SELECT run immediately before and after each write to prove what changed) is the cheapest safety tool in SQL. The star read is its simplest form.

SELECT asks for data, * means all columns, and FROM customers names the sheet:

SELECT * FROM customers;

Run it right after the build and you get heads with no rows. Run it after every insert, update, and delete in this lecture and the grid tells you exactly what that statement did.

The star form is identical in PostgreSQL, MySQL, Snowflake, and Databricks, which is why the lecture leans on it so heavily. The one cross-system difference worth knowing: production guides in every book warn against SELECT * inside application code or views, because adding a column later silently changes what the application receives. For classroom checks and admin eyeballing, though, SELECT * is exactly right — fast, complete, and honest.

Worked preview. Setup: fresh customers table, zero rows. Run SELECT * FROM customers;. Expected result: one header row showing customer_id | first_name | last_name | email | age and zero data rows. Now insert one row (section 3.2 does this) and run the same statement again. Expected result: the same heads plus one data row starting with 1. Sense-check: same heads both times, row count up by exactly one — that pairing is how you confirm each later write did what you meant.

SELECT * never changes data, so it is always safe to run — but on a table with millions of rows it can flood your editor. The habit to keep is: star-read freely on tiny practice tables, and add a LIMIT or a WHERE filter before star-reading a real table.

Recap: SELECT * FROM customers; is the before-and-after photograph for every write in this lecture. Bridge: with the empty photo taken, the next section adds the first person.

3.2 Inserting Rows with INSERT INTO and VALUES

How does a new person actually get onto the sheet? You hand the database one full row in a single statement, naming which blanks you are filling and giving the answers in the same order.

Think of INSERT as handing a filled-in form to a clerk through a window. The column list is the row of blank labels you point at — "first name, last name, mail, age" — and the VALUES list is your answers read out in that same order. If you read the answers in a different order than the labels, the clerk files them under the wrong labels without complaint.

That last sentence is the whole danger of this section, so the lecture repeats it in every example: order is a promise, not a suggestion.

3.2.1 Insert syntax and column to value order

An insert (a statement that adds one or more new rows) names its target once and then supplies values position by position.

The classroom shape names four columns and deliberately leaves out the self-filling key:

INSERT INTO customers (first_name, last_name, email, age)
VALUES ('Adnan', 'Wahid', 'ABC.com', 40);

INSERT INTO customers — the table receiving the row. The bracket list (first_name, last_name, email, age) — exactly which columns get facts, in order. VALUES (...) — the matching facts in the same order. Text facts wear single quotes ('Adnan'); whole numbers stand bare (40). customer_id is absent on purpose: the SERIAL sequence supplies 1 for the first row, 2 for the next, and so on.

The pairing is positional: first_name takes 'Adnan', last_name takes 'Wahid', email takes 'ABC.com', age takes 40. Swap any two values and the row still inserts — names in the age column fail only if the type rejects them, and two swapped short texts slip through silently. That silent wrong-filing is why the read-back habit matters.

Run the statement and the editor answers with a short success note, not the row. That note answers "did it land?" only. To see the row, run the photograph again:

SELECT * FROM customers;

Now the grid shows one data row: 1 | Adnan | Wahid | ABC.com | 40. The 1 is the database's own contribution.

Across systems the single-row shape is identical, and the extras are worth collecting in one place. Every engine in your shelf — PostgreSQL, MySQL, Snowflake, Databricks — accepts the column list plus VALUES form shown here, and all four accept multi-row inserts with comma-separated groups such as VALUES ('pen'), ('pencil') (section 3.9 uses exactly that). Omitting the column list entirely (INSERT INTO dept VALUES (50, 'X', 'Y')) works everywhere but is fragile: it forces you to supply every column in the table's stored order, so adding a column later breaks old statements — the cookbook explicitly warns against relying on it. Inserting defaults also varies usefully: any column you leave out of the list takes its DEFAULT (or empty if none), the keyword DEFAULT can be typed explicitly in the VALUES list on all brands, and PostgreSQL further offers INSERT INTO t DEFAULT VALUES for an all-defaults row while MySQL accepts the shorthand VALUES (). None of that changes the lecture row; it just means "leave out what the database should fill" generalizes beyond the key column.

Worked insert of Adnan Wahid. Setup: empty customers table from section 3.1. Goal: add one person with age 40. Step 1: type INSERT INTO customers (first_name, last_name, email, age) — four labels. Step 2: type VALUES ('Adnan', 'Wahid', 'ABC.com', 40) — four answers in the same order, texts quoted, number bare. Step 3: run. Expected result: success note, no grid. Step 4: run SELECT * FROM customers;. Expected result: exactly one row, customer_id 1, first name Adnan, last name Wahid, mail ABC.com, age 40. Sense-check: count the values (four) against the columns (four), then confirm the key is 1 — if the key is larger, an earlier attempt already consumed sequence numbers, which is normal and harmless.

Scope: this form adds literal rows typed by hand. It assumes the quoted texts fit their VARCHAR caps and the bare number fits INT. It does not check whether "Adnan Wahid" already exists — inserts happily store twins unless a UNIQUE guard or an upsert tail (section 3.9) says otherwise. Assumption: the column list and the values list have the same length and matching left-to-right order; the database enforces the count but not the meaning.

Visualize the statement as two parallel slots: four labeled slots on top, four answer cards below, connected by vertical lines 1-to-1, 2-to-2, 3-to-3, 4-to-4. The takeaway: any crossed line files a fact under the wrong label.

Three beginner traps live here. First, quoting the number ('40' instead of 40): most engines coerce it quietly today, but mixing quoted numbers into INT columns trains a habit that breaks on dates and math later. Second, leaving a text unquoted (ABC.com with no quotes) which the parser reads as a column name and rejects. Third, listing columns in one order and values in another — the classic silent corruption, caught only by the read-back.

Recap: INSERT INTO plus a matching ordered VALUES list adds the row, the sequence supplies the key, and SELECT * proves it. Exam note: expect to write this shape from memory with correct quote use and correct column-to-value order. Bridge: the next section breaks this pattern on purpose with a name that contains a quote mark.

Sign-up forms, bulk import jobs, and admin "add customer" buttons all end in this exact statement: the form fields become the column list, the user's typed answers become the values list, and the key is left for the database.

3.2.2 Worked insert of the first customer

This subsection is the same insert walked as a strict procedure, because on an exam and in a loader script the steps must run in order with nothing skipped.

Purpose: add exactly one new person to an empty practice table and prove the row landed with the key the database assigned.

Inputs are the table name, the four column names, and the four values; the output is one stored row plus the editor's success note. Steps: (1) name table and columns, (2) open VALUES and type the four facts in matching order, (3) close brackets and run, (4) read back with SELECT * and confirm key 1 with the four facts. The trace is the Adnan Wahid run above: empty grid, success note, then a one-row grid reading 1 | Adnan | Wahid | ABC.com | 40.

Second trace to lock the pattern. Insert a second person, say ('Sara', 'Khan', 's@k.com', 28), with the same column list. Expected result: success note, then SELECT * shows two rows with keys 1 and 2. Sense-check: the key went up by one and nothing about row 1 changed — inserts only add, they never touch existing rows.

Cost and scale: one single-row insert is instant on any engine; bulk loads of thousands of rows should use multi-row VALUES groups or a file-load command rather than thousands of single-row statements. When this tool fits: hand-typed rows, form submissions, and small seeds. The alternative for file-scale data is a bulk import, and for maybe-existing rows it is the upsert of section 3.9.

Recap: name, match, run, read back — four moves, same order every time. Bridge: now that clean inserts work, the lecture feeds the parser a hostile input.

3.3 Inserting Text That Contains a Single Quote

What happens when the fact itself contains the very mark SQL uses as packaging? A name like Bill O'Sullivan carries a single quote inside it, and since single quotes also say "the text starts here" and "the text ends here," the inner mark snaps the packaging open mid-word and the whole statement fails.

Think of single quotes as the padded envelope around a text value. One mark seals the left edge, one mark seals the right edge. A quote sitting inside the name is a sharp object poking the envelope from the inside — unless you wrap that sharp point with extra padding, the envelope tears at the wrong place and the clerk refuses the package.

The padding, in standard SQL, is simply a second quote mark in the same spot.

3.3.1 Doubling the inner quote

A string literal (text typed between single-quote marks, such as 'Adam') ends at the next lone single quote the parser meets. A syntax error near the inner mark (the database stopping before storing anything because the text boundary broke) is the guard doing its job, not a bug.

The failing first try looks innocent but breaks the boundary:

INSERT INTO customers (first_name)
VALUES ('Bill O'Sullivan');

The parser reads 'Bill O' as one complete text, then chokes on the leftover Sullivan' — stray words with no job. Nothing is stored. The fix doubles the inner mark:

INSERT INTO customers (first_name)
VALUES ('Bill O''Sullivan');

Count the marks: opening mark, Bill O, two marks pressed together, Sullivan, closing mark. The paired marks in the middle collapse into one stored quote, so the row holds Bill O'Sullivan with the mark intact. Confirm with SELECT * FROM customers;.

The doubled-quote rule is the portable core: it is the SQL standard and works unchanged in PostgreSQL, MySQL, Snowflake, and Databricks for ordinary values. Each shelf adds its own extras around that core, and a learner benefits from seeing them side by side. Snowflake additionally lets you wrap tricky text in dollar-sign quoting so inner quotes need no doubling at all — handy for long notes. PostgreSQL offers the same dollar-quoting plus an escape-string form (E'O\'Brien'). MySQL historically also accepts a backslash escape ('O\'Brien'), which the other engines reject or treat literally, so doubled quotes remain the only form you can carry between all four without thinking. Databricks follows the standard doubled form in SQL text, exactly as the lecture shows.

Worked error-to-fix. Setup: customers table from section 3.1. Goal: store first name Bill O'Sullivan. Step 1: run the single-mark form. Expected result: syntax error pointing at or just after O — and zero new rows on the read-back. Step 2: change the inner mark to two marks ('Bill O''Sullivan'). Step 3: run again. Expected result: success note. Step 4: run SELECT * FROM customers; and confirm the stored first name reads Bill O'Sullivan with one visible mark. Sense-check: two marks typed, one mark stored — if you see two marks in the grid, you tripled instead of doubling.

Picture the literal as a timeline of marks: open, letters, twin-peak in the middle, letters, close. The landmark is the twin-peak — the only place where two marks touch. Takeaway: twin-peak inside means data; lone marks at the edges mean packaging.

Scope: doubling works for single quotes inside single-quoted text, which covers names, streets, and notes — the lecture's cases. It does not apply to double quotes used as identifier wrappers, and it does not rescue a value that is too long for its VARCHAR cap. Assumption: the value is wrapped in single quotes; every engine here expects that for text.

Two traps persist. First, "fixing" the error by switching to double quotes around the value ("Bill O'Sullivan"): in PostgreSQL that means "a column named Bill O'Sullivan" and fails differently, so stay with single quotes and double the inner one. Second, doubling the wrong mark — doubling the opening or closing edge instead of the inner apostrophe — which just moves the syntax error one word over. When in doubt, count: every stored quote that came from typing needs exactly two typed marks.

Recap: one inner quote breaks the envelope, two typed together store as one, and the error before the fix proves the guard works. Exam note: expect a short task where a value holds a quote and you must show the doubled-mark form. Bridge: with hostile text tamed, the next section makes inserts talk back.

Sheet and form imports meet O'Brien, O'Sullivan, D'Souza, and "can't" daily, so every loader either doubles inner quotes, uses dollar-quoting where offered, or — best of all — passes values as bound parameters so the driver quotes for it. The lecture's hand-doubling teaches what the driver automates.

3.3.2 Worked fix from error to success

Treat the Sullivan insert as a four-move repair drill: break it, read the error, double the mark, prove the stored value.

Purpose: turn the parser's rejection into the exact evidence that the doubled form works, with the before-and-after grids as proof.

Inputs: the table plus the name Bill O'Sullivan. Outputs: first a syntax error with no new row, then a success note plus a row holding the single stored quote. Steps: (1) run the plain form and record the error position, (2) replace the inner ' with '', (3) rerun, (4) SELECT * and read the stored name character by character.

Trace with row counts. Before step 1, SELECT count(*) FROM customers; notes N rows. After the failing insert, the count is still N — the guard stored nothing. After the fixed insert, the count is N + 1 and the newest row's first name is Bill O'Sullivan. Sense-check: error plus unchanged count means safe rejection; success plus count-plus-one means the doubling was correct.

When to use this by hand versus automation: hand-doubling fits exams and one-off fixes; repeated loads should use parameters or file loaders that handle quoting for every row. The alternative forms (Snowflake dollar-sign quoting, Postgres dollar-quoting, MySQL backslash) are worth recognizing when reading other people's scripts but the doubled standard form is what to write.

Recap: the error is data protection, the doubled mark is the repair, and the count-plus-one is the receipt. Bridge: next, inserts start issuing receipts on their own.

3.4 Getting Inserted Rows Back with RETURNING

A plain insert answers "did it land?" but not "what exactly landed?" — and when the database invents the key and fills defaults behind your back, that second question matters. RETURNING tacks a read onto the write so the stored truth comes back in the same trip.

Think of RETURNING as the receipt the clerk prints at the moment they file your form. No receipt: you know the form went in but you must walk back and look it up. Full receipt (RETURNING *): you hold a copy of the whole filed form including the reference number the clerk stamped on it. Short receipt (RETURNING customer_id): you hold just the reference number for your next errand.

The professor's receipt analogy is the one to keep, because every later section reuses it for updates as well.

3.4.1 RETURNING star for the full row

A RETURNING clause (extra words at the end of a write that send the touched rows back as a result grid) turns a blind write into a confirmed one.

The full-echo shape asks for every stored column back:

INSERT INTO customers (first_name)
VALUES ('Adam')
RETURNING *;

RETURNING — send back the rows this statement touched. * — all columns, with database-filled values included. Contrast the three runs: inserting 'Adam' with no tail returns only a success note; inserting 'Joseph' with RETURNING * returns the whole stored row — fresh customer_id, first name Joseph, empty spots where no facts were given; inserting with a single-column tail returns just the key (next subsection). The echo shows the stored row, not a copy of your typing — the key in it is the database's own stamp.

Portability matters here more than anywhere else in the lecture. RETURNING on INSERT (and later on UPDATE and DELETE) is a PostgreSQL feature that Snowflake also supports, and the Practical SQL text calls it out explicitly as PostgreSQL-specific but shared with exactly these write statements. MySQL does not offer RETURNING on writes; the equivalent is asking for the last auto number with LAST_INSERT_ID() or re-reading with SELECT. Databricks and Spark SQL historically lack RETURNING on plain inserts as well and expect a follow-up read or the use of merge-output patterns. So the lecture's form is the PostgreSQL/Snowflake spelling — learn it cold for those engines, and translate to "insert, then fetch the id" on MySQL-flavored exams.

Worked three-way run. Setup: customers with a few rows. Run 1: INSERT INTO customers (first_name) VALUES ('Adam'); Expected: bare success note, no grid — run SELECT * yourself to find Adam. Run 2: the same statement for 'Joseph' with RETURNING *; Expected: a one-row grid showing the fresh customer_id, first name Joseph, and blanks elsewhere — that grid is the proof, no second query needed. Sense-check: the key in the echo matches the key you find on a later SELECT *; if it does not, you are looking at the wrong database connection.

Scope: RETURNING * echoes only rows this statement touched — one row for a single-row insert, several for a multi-row VALUES list. It assumes the client displays result grids for writes, which pgAdmin, psql, and Snowflake worksheets do. Assumption: unmentioned columns accept blanks or defaults; if a column were NOT NULL with no default, the insert would fail before any echo.

The common trap is reading the echo as "a copy of my input" and missing that defaults, timestamps, and keys in it came from the server. A second trap is stacking RETURNING onto a statement in MySQL or older Spark SQL and reading the resulting syntax error as a typo in the column name — it is a dialect gap, not a typo. Write RETURNING where the engine supports it, re-read where it does not.

Recap: RETURNING * converts a blind insert into a self-proving one by returning the stored row with server-filled values. Bridge: when only the new key is needed, the short receipt is cheaper.

Load-job logs use the full echo to record exactly what landed; sign-up handlers usually prefer the short echo, which is next.

3.4.2 RETURNING a single column

When the next step needs only the fresh key — adding an order for the same person, opening their profile screen — fetching the whole row wastes bandwidth and clutters logs.

Name just the key column in the tail:

INSERT INTO customers (first_name)
VALUES ('Joseph1')
RETURNING customer_id;

The result is a one-column, one-number grid: the fresh customer_id for Joseph1. Grab it and hand it to the next statement instead of running a second search for "which key did I just get?"

The idea ports even where the keyword does not: PostgreSQL and Snowflake spell it RETURNING customer_id; MySQL spells the same need as SELECT LAST_INSERT_ID() right after the insert; Databricks code typically captures the new key by re-reading on a unique business key. One concept, two spellings — the lecture drills the RETURNING spelling.

Worked key grab. Run the Joseph1 insert above with RETURNING customer_id;. Expected: a single value such as 7 (the exact number depends on how many rows precede it). Use it immediately: SELECT * FROM customers WHERE customer_id = 7; should show Joseph1. Sense-check: the echoed number finds exactly one row — zero rows means you are in the wrong database, more than one means the key is not actually unique and something deeper is wrong.

Picture a receipt torn in two: the long half lists every field, the short stub shows only the reference number. Same purchase, different paper. Takeaway: match the receipt size to the errand.

Recap: RETURNING customer_id is the short receipt — one number, ready for the next statement. Exam note: expect to add RETURNING * or RETURNING customer_id to an insert and state what each returns. Bridge: rows now exist with known keys, so the lecture turns to changing them in place.

Sign-up flows capture the short receipt to render the new account screen without a second lookup; audit-heavy loaders keep the long receipt for the log. Both save exactly one round trip per write, which is the entire economic argument for the clause.

3.5 Updating Rows with UPDATE SET WHERE

Stored facts go stale: people change mail addresses, ages tick up, flags flip. UPDATE rewrites facts inside rows that already exist — no new rows appear and no rows vanish; the grid keeps its shape while chosen cells change.

Think of UPDATE as an eraser plus a pen on the filed form. SET says which blanks to erase and what to write instead; WHERE says which forms in the drawer to pull out. Pull the wrong forms and you rewrite someone else's mail — which is why the lecture calls WHERE the safety lock on the drawer.

3.5.1 Single column update by key

An update (a statement that rewrites column values in existing rows) has three clauses that must appear in order: which table, what changes, which rows.

The one-column shape changes a single cell in a single row:

UPDATE customers
SET email = 'A2@b.com'
WHERE customer_id = 1;

UPDATE customers — the sheet to change. SET email = 'A2@b.com' — the column plus its new fact. WHERE customer_id = 1 — only the row whose key is 1. Check first with SELECT * FROM customers; and find row 1 (first name Adnan, last name Wahid). Run the update: success note. Read again: row 1 now shows mail A2@b.com and nothing else moved.

Filtering by the primary key is the safest habit because the key marks exactly one row — no more, no fewer. Filtering by a non-unique column such as first_name = 'Adam' could rewrite several Adams at once, which is sometimes intended but never accidental-proof. The lecture always filters updates by customer_id for exactly this reason.

The shape is identical in PostgreSQL, MySQL, Snowflake, and Databricks for single-table updates, which makes this the most portable statement in the lecture. The extras differ only when a second table joins the decision: standard SQL uses a subquery inside SET plus a WHERE EXISTS guard so non-matching rows are not blanked to empty, while PostgreSQL additionally offers a shorter UPDATE ... SET col = b.col FROM b WHERE ... form. You do not need either extension for this lecture — but recognizing them later prevents confusion when other scripts update from lookup tables.

Worked single-cell rewrite. Setup: row 1 holds Adnan Wahid with an older mail. Step 1: SELECT * FROM customers; and note the current mail. Step 2: run the update above. Expected: success note reporting one row touched. Step 3: read back. Expected: row 1 mail is A2@b.com, all other rows byte-identical. Sense-check: row count unchanged and exactly one row differs — if the count changed you ran an insert or delete by mistake; if many rows changed your WHERE was too broad or missing.

Scope: SET expressions run per touched row, so the new value can be a literal (as here) or an expression over the row's own old values. Assumption: the WHERE matches at least one row; a WHERE that matches nothing succeeds quietly with "0 rows updated," which looks like success but changed nothing — always check the touched-row count.

The classic trap is running the update, seeing "success," and never reading back — then discovering weeks later that the filter matched nothing. The second trap is quoting: text needs quotes, numbers do not, and swapping them either fails loudly or coerces silently depending on the engine. Always read the row count in the success note before the read-back.

Recap: one table, one SET pair, one key filter — exactly one cell changes. Bridge: real edits usually change two cells of the same row at once, which needs the comma form.

3.5.2 Multi column update in one statement

Editing mail and age in two statements would work but doubles the trips and risks a half-applied edit if the second statement fails. One statement with two pairs keeps the row consistent.

Keep one UPDATE, one SET, and join the pairs with commas:

UPDATE customers
SET email = 'A4@b.com',
    age = 30
WHERE customer_id = 1;

This goes to the row where customer_id is 1, sets email to A4@b.com, and sets age to 30 in the same touch. Read back with SELECT * FROM customers;: row 1 now shows mail A4@b.com and age 30 together. One statement, two fresh facts, one row.

Formatting tip the lecture models: one pair per line under a single SET. That layout makes a missing comma visible instantly, which matters because the parser's error for a missing comma points at the second pair, not at the absent comma itself.

Worked two-cell rewrite. Setup: row 1 currently shows mail A2@b.com with its earlier age. Run the statement above. Expected: success note for one row. Read back: row 1 reads A4@b.com / 30. Sense-check: both cells changed in the same row and no other row moved — if only one changed, the statement that ran was the old single-pair version, not this one.

Layout the statement as a small table in your head: one row selector (WHERE), two column assignments side by side. Takeaway: the comma is the "and also" between assignments.

Three slips dominate: writing SET twice (one per pair), dropping the comma between pairs, and — worst — dropping the WHERE entirely, which promotes this safe single-row edit into the all-rows rewrite of section 3.7. The guardrail is order: type WHERE first as a stand-in, then fill in SET, then run.

Recap: one SET, comma-split pairs, one key filter — the whole row edit lands atomically. Exam note: expect to write both the one-column and two-column forms with a key filter and to state why the key filter matters. Bridge: like inserts, updates can print their own receipt.

Profile-edit screens map directly onto this shape: the form sends the new mail and age, the session supplies the logged-in key, and the backend builds one UPDATE ... WHERE customer_id with comma-split pairs.

3.6 Returning the Updated Row with UPDATE RETURNING

On a wide table with thousands of rows, proving a one-row edit by re-reading everything is slow and noisy. Appending RETURNING * returns exactly the rows the update touched — the receipt for this edit and nothing else.

Would you walk back to the shelf to check the whole drawer after the clerk corrected one form? Or ask for the corrected form handed back across the counter? RETURNING * is the handover: the touched row comes back in the same trip that changed it.

3.6.1 Worked update with echo

A plain update and its echo twin differ by exactly one line, so this subsection walks them as a pair.

Purpose: change one customer's mail and see the changed row at once, without a second read. Inputs: the table, the new mail, the key filter. Output: the touched row itself.

The plain form takes two trips:

UPDATE customers
SET email = 'a@b.com'
WHERE customer_id = 3;

Run it, then SELECT * to find row 3 with its new mail — correct but chatty. The echo form adds the receipt line:

UPDATE customers
SET email = 'a@b.com'
WHERE customer_id = 3
RETURNING *;

Run it and the grid holds just the touched row: customer_id 3 with mail a@b.com. No other rows come back, however large the table is.

Setup for the walk: read the table, pick customer_id 3, note its current mail. Run the plain form first and observe the bare success note; read back and confirm row 3 changed. Then change the mail once more using the echo form and observe the single-row grid arriving with the success itself. That contrast — two trips versus one — is the entire lesson.

Worked echo trace. Before: row 3 mail is the older value. Statement: the echo block above. Expected result: one returned row reading 3 | ... | a@b.com | .... After: SELECT * confirms the same values, proving the echo was the stored truth rather than a preview. Sense-check: exactly one row echoed means the filter hit exactly one row; zero rows echoed means the key does not exist and nothing changed despite the "success" wording.

Portability matches section 3.4: PostgreSQL and Snowflake support RETURNING on UPDATE (Snowflake and Postgres also on DELETE), MySQL does not and expects a follow-up SELECT, and Databricks Spark SQL likewise expects a re-read. The Practical SQL text presents the RETURNING column_a, column_b form as the PostgreSQL-specific spelling usable across all three writes — the lecture's RETURNING * is simply its star variant. Cost aside, the echo also sharpens audit trails: the returned row can be logged with old-to-new context instead of logging "update ran somewhere."

Scope: the echo returns post-update values — the new mail, not the old one. If you need old-versus-new for an audit log, capture the old row with a SELECT before the update and pair it with this echo. Assumption: the filter matches; an echo of zero rows is a valid result meaning "nothing matched."

The trap here is running the echo on an engine without the feature and misreading the syntax error as a column typo — check the dialect first. A subtler trap is adding RETURNING * to a filter-free update (section 3.7) on a huge table and flooding the client with every row; scope the tail to the columns you need when the touch set is large.

Recap: RETURNING * on an update hands back only touched rows, collapsing check-into-change in one trip. Exam note: expect to append RETURNING * to an update and explain that only touched rows come back. Bridge: the next section removes the safety lock entirely and changes everything at once.

Admin consoles and fix-up scripts rely on this echo to log what changed — key plus fresh facts — without re-scanning tables that no longer fit on one screen.

3.7 Updating Every Row by Omitting WHERE

Sometimes the job really is "every row gets the same fresh fact": a new flag column starts empty and needs a starting value, or a policy flips one status for all accounts. Dropping WHERE turns the scalpel into a paint roller — the same SET lands on all rows at once.

Think of WHERE as the stencil over the wall. With the stencil cut for one account, paint hits one spot. With no stencil at all, the roller covers the whole wall in one pass. Both are legitimate paint jobs — the mistake is reaching for the roller while thinking you hold the stencil.

3.7.1 Adding a flag column and filling it

A flag column (a small status field such as is_enable holding Y or empty) is the lecture's vehicle for showing both scales side by side.

The column arrives through the visual editor: open customers, open columns, create is_enable as two-character text, save. A star read now shows the new empty column on every row — structure changed, data did not.

The single-row fill keeps the safety lock:

UPDATE customers
SET is_enable = 'Y'
WHERE customer_id = 1;

Read back: only row 1 shows Y. The all-rows fill drops the lock:

UPDATE customers
SET is_enable = 'Y';

Read back: every row shows Y. Same SET, minus WHERE, means all rows. Add the receipt when you want proof:

UPDATE customers
SET is_enable = 'Y'
RETURNING *;

Since every row was touched, every row comes back.

Walk it as a deliberate contrast drill. Step 1: add the column and read — all blanks. Step 2: run the filtered fill and read — exactly one Y. Step 3: run the filter-free fill and read — all Y. Each read is the evidence for the rule the lecture states once and tests forever: no WHERE means all rows change.

Worked two-scale trace. Setup: is_enable fresh and empty on, say, five rows. After the filtered statement, SELECT count(*) FROM customers WHERE is_enable = 'Y'; returns 1. After the filter-free statement, the same count returns 5, equal to the full table count. Sense-check: filtered count 1 proves the lock works; full count equal to table size proves the roller covered everything and skipped nothing.

The pattern is portable: filter-free UPDATE ... SET without WHERE rewrites all rows in PostgreSQL, MySQL, Snowflake, and Databricks alike — which is exactly why every shelf treats it as the headline danger. The Practical SQL text even shows the same move to backfill a whole copied column (SET st_copy = st; with no filter, touching all 6287 rows) and pauses to warn that on a very large table the operation takes real time and real space. Snowflake and Databricks users feel that cost most on warehouse-scale tables, where a careless all-rows rewrite also burns compute credits. Backfills and feature rollouts are the legitimate uses: switching a flag on for all accounts or seeding a new column with a starting value for old rows.

Scope: use the roller only when every row truly deserves the same value. It assumes you have already counted the rows and confirmed the database connection — test and live copies often share the same table name. Assumption: no concurrent writer is changing the same column mid-roll; on busy tables this statement locks or versions many rows at once.

Picture two grids: after the stencil, one cell lit among blanks; after the roller, the whole column lit. Landmark: the WHERE line present versus absent. Takeaway: that one line's presence is the entire difference between one and all.

Treat a missing WHERE as a choice, never an accident. The guardrail drill: run the single-row form first to prove the SET pair is spelled right, count the table, say the target out loud (which server, which database, which table), and only then remove the filter. The classic horror story — rehearsing on test, executing on live — happens because both copies are named customers.

Recap: one SET with a key filter fills one row; the same SET with no filter fills all rows, and RETURNING * echoes however many were touched. Exam note: expect to state the all-rows rule and to show both the single-row and all-row forms. Bridge: deletes obey the same lock, with even sharper teeth.

Feature rollouts flip flags for all accounts with this shape, and backfills seed new columns for old rows the same way — always after a count, always on the confirmed connection.

3.8 Deleting Rows with DELETE FROM and Safety Rules

Rows leave the table with DELETE FROM. With a filter it removes chosen rows; without one it empties the whole table while keeping the columns standing. Both forms act at once, ask nothing twice, and — by themselves — cannot be undone.

Think of WHERE as the seat belt for deletes. Buckled (WHERE customer_id = 9), you remove one seat. Unbuckled (no WHERE), you empty the whole car. The car itself — the table shape — stays parked outside either way.

3.8.1 Deleting chosen rows

A filtered delete (a DELETE FROM with a WHERE that names which rows go) is the everyday retire-account, cancel-order, remove-test-row statement.

The classroom shape removes exactly one customer:

DELETE FROM customers
WHERE customer_id = 9;

DELETE FROM customers — the table to trim. WHERE customer_id = 9 — only the row whose key is 9 goes. The drill: SELECT * first and confirm row 9 is the one you mean, run the delete, read again — row 9 is gone and no other row moved. Key numbers of the survivors stay as they were, so the missing 9 leaves a permanent gap. That gap is normal: auto-filled sequences are never reused, in PostgreSQL, MySQL, Snowflake, or Databricks.

Why keys leave gaps deserves one extra line, because students routinely "repair" the gap and cause collisions. The sequence counter only moves forward; deleting row 9 does not rewind it, and a failed insert still consumes a number. PostgreSQL documents this openly (a deleted id is never replaced, an aborted insert still increments), and MySQL's AUTO_INCREMENT, Snowflake's AUTOINCREMENT, and Databricks identity columns all behave the same. A gap is evidence the machinery works, not damage to fix.

Worked single-row removal. Setup: table holds rows including key 9. Step 1: SELECT * FROM customers; — confirm key 9 exists and note the total count N. Step 2: run the delete above. Expected: success note for one row. Step 3: read back. Expected: count is N − 1, key 9 absent, every other key present with identical facts. Sense-check: count down by exactly one and one key missing means a clean single removal; count unchanged means the key did not exist.

Scope: the delete removes whole rows, never single cells — to empty a cell, update it to blank instead. It assumes the filter names the intended rows; a filter on a non-unique column can remove several rows in one touch, which is correct only when that is the intent.

3.8.2 Deleting all rows and working safely

Clearing the practice table between groups is legitimate; clearing the live table by accident is a career story. Both use the same words minus the lock.

The full clear drops the filter:

DELETE FROM customers;

Read back with SELECT * FROM customers;: the heads remain, zero data rows come back. The table still exists — only its rows are gone.

That "heads remain, rows gone" distinction is exactly what separates DELETE from dropping the table, and every engine agrees on it. Two extras complete the cross-system picture. First, TRUNCATE is the faster full-clear cousin (TRUNCATE customers; / TRUNCATE TABLE customers;) that also resets auto-numbering on request (RESTART IDENTITY in PostgreSQL); the lecture stays with DELETE because the filtered and filter-free pair teaches the WHERE rule, but expect TRUNCATE wherever reset scripts need speed. Second, DELETE (like UPDATE) accepts RETURNING in PostgreSQL and Snowflake to echo removed rows for the log, while MySQL and Databricks expect a pre-delete SELECT saved as the audit record.

Worked full clear with safety drill. Setup: practice table with a few expendable rows. Step 1: SELECT count(*) FROM customers; — write down N. Step 2: state the target out loud: which server, which database, which table. Step 3: run DELETE FROM customers;. Expected: success note for N rows. Step 4: SELECT * shows heads, zero rows. Sense-check: zero rows plus intact heads means a clean wipe; "table does not exist" means you dropped rather than deleted — different statement, different recovery.

Safe habits are the real curriculum here, so rehearse them as a checklist: read before you delete and confirm the count; confirm the connection (test and live copies share the customers name, and a delete aimed at test rows but run on live removes real rows); run the narrow key-filtered delete first and re-read before any wide delete; keep a backup — the full clear cannot be undone by itself and rows return only from a copy such as CREATE TABLE backup AS SELECT * FROM customers;. The Practical SQL text makes that backup table the mandatory pre-step to every bulk fix for exactly this reason.

Picture the seat-belt grid again: buckled, one row highlighted for removal; unbuckled, every data row highlighted while the header row stays plain. Takeaway: the header never deletes — only data rows do.

Filter-free deletes are final without a backup, they lock or version many rows on busy tables, and on warehouse engines they can be surprisingly expensive — which is why live deletes pair with backups, access limits, and off-peak windows. Never test a wide delete on live data; prove the filter narrow first, then widen deliberately.

Recap: DELETE FROM ... WHERE key removes chosen rows and leaves gaps that are normal; bare DELETE FROM empties the table but keeps its shape, and neither undoes itself. Exam note: expect to write both the filtered delete and the full clear and to state that the full clear cannot be undone without a backup. Bridge: the final section removes the need to choose between adding and changing.

Retire-account jobs delete by key, training-room resets wipe practice rows with the filter-free form between groups, and live deletes always travel with backups and server checks — the movies practice tables stand in for all three.

3.9 Insert or Update in One Step with UPSERT and ON CONFLICT

Feeds resend rows. Users double-click submit. Retry logic replays the same file. A plain insert answers a duplicate with an error or — worse, where no guard exists — a twin row. Upsert (update-or-insert in one step: add the row when it is new, refresh or skip it when it clashes on a one-of-a-kind column) makes the replay safe to run twice.

Think of upsert as the clerk's standing instruction for repeat forms. "If this tag is new, file it. If the tag is already in the drawer, either leave the old form alone or refresh its date stamp — but never file a second copy." One statement carries both branches, so the caller never has to ask "is it there yet?" first.

3.9.1 Building the t_tags table

The demo needs a table where duplicates are impossible by construction, so the clash branch has something to fire on.

t_tags has three columns: a self-filling key, amust-be-one-of-a-kind tag, and a self-stamping time:

CREATE TABLE t_tags (
  id SERIAL PRIMARY KEY,
  tag TEXT UNIQUE,
  update_date TIMESTAMP DEFAULT now()
);

TEXT — free text with no fixed cap, right for tags of any length. UNIQUE — the guard: each tag string may appear only once in the whole table, and any second insert of pen collides with it. TIMESTAMP — calendar date plus clock time with zone info. DEFAULT now() — when no time is typed, the server stamps the current moment by itself.

Refresh the table list to see t_tags, then seed two rows with the multi-row form:

INSERT INTO t_tags (tag)
VALUES ('pen'), ('pencil');

Read back:

SELECT * FROM t_tags;

Two rows appear with keys 1 and 2, tags pen and pencil, and insert-moment stamps. Note the pen stamp (the lecture's run ends near 39.095) — later upserts move that stamp, and the movement is the evidence the clash branch ran.

The guard vocabulary ports with small spelling shifts. TEXT UNIQUE plus DEFAULT now() works as shown in PostgreSQL; MySQL spells the same trio as TEXT (or VARCHAR) with a UNIQUE index and TIMESTAMP DEFAULT CURRENT_TIMESTAMP; Snowflake accepts TEXT UNIQUE similarly with TIMESTAMP DEFAULT CURRENT_TIMESTAMP(); Databricks uses STRING UNIQUE-style constraints where supported with DEFAULT current_timestamp(). The concept never changes — one-of-a-kind column plus self-stamping time — only the clock function's parentheses do.

Worked seed and baseline. Setup: fresh t_tags. Step 1: run the build. Expected: success note, three columns visible. Step 2: run the two-row VALUES ('pen'), ('pencil') insert. Expected: success note for two rows — this comma-separated multi-row form works in PostgreSQL, MySQL, Snowflake, and Databricks alike. Step 3: SELECT * FROM t_tags;. Expected: two rows, keys 1 and 2, stamps showing the insert moment. Step 4: write down the pen stamp. Sense-check: two rows, distinct keys, pen older-or-equal to pencil — that baseline makes every later stamp movement meaningful.

Scope: the UNIQUE guard fires only on the exact guarded column (tag here) — a row with the same id but a different tag is a different clash, and unguarded columns accept twins freely. Assumption: the seed ran once; re-running the seed itself collides on pen, which is precisely what the next two subsections exploit on purpose.

The trap is seeding with explicit id values "to keep things tidy" — hand-typed keys desynchronize the sequence and later auto-inserts can collide. Seed only the tag column, as shown, and let both the key and the stamp fill themselves.

Recap: a guarded tag column plus a self-stamping clock gives duplicates somewhere to collide and refreshes something visible to prove it. Bridge: first, the quiet branch — collide and do nothing.

3.9.2 ON CONFLICT DO NOTHING

When the right answer to "already there?" is "then we are done," the tail says so in three words.

The upsert tail follows the values and names the guard plus the action:

INSERT INTO t_tags (tag)
VALUES ('pen')
ON CONFLICT (tag) DO NOTHING;

ON CONFLICT (tag) — when the new fact collides with the UNIQUE guard on tag. DO NOTHING — skip the insert, leave the old row untouched, raise no error. Run it and read back: still just pen and pencil, no third row, no error, and — critically — the pen stamp unmoved. That stillness proves nothing was rewritten. This is insert-if-missing: fresh values add, known values pass silently.

Worked quiet skip. Setup: t_tags holding pen (stamp T0) and pencil. Step 1: record T0. Step 2: run the DO NOTHING statement for 'pen'. Expected: success note, no error. Step 3: SELECT *. Expected: two rows, pen stamp still T0. Sense-check: same count plus same stamp equals a true skip; a moved stamp would mean the refresh branch ran instead.

Dialect map for this branch, kept tight because the exam tests the PostgreSQL spelling: PostgreSQL and its close cousins write ON CONFLICT (tag) DO NOTHING; MySQL expresses insert-if-missing as INSERT IGNORE INTO t_tags (tag) VALUES ('pen'); Snowflake and Databricks express the same sync as a MERGE ... WHEN NOT MATCHED THEN INSERT arm (the Snowflake chapter shows a full insert-update-delete MERGE in one statement). Same intent — add when fresh, ignore when known — four spellings. The lecture drills the ON CONFLICT spelling.

Recap: DO NOTHING turns a duplicate from an error into a silent pass with the old row and its stamp untouched. Bridge: when the duplicate should refresh the old row instead, the tail grows a SET list.

3.9.3 ON CONFLICT DO UPDATE with EXCLUDED

When the repeat carries fresher information — a new sighting time, a corrected label — the clash should update the old row rather than ignore the new facts. The attempted values arrive under the name EXCLUDED.

EXCLUDED (the table-like prefix holding the values this insert attempted, available only inside the clash branch) is the envelope just handed in: on conflict the old row stays, but any of its columns may be overwritten from the envelope.

The refresh-the-stamp form keeps the tag and moves the clock:

INSERT INTO t_tags (tag)
VALUES ('pen')
ON CONFLICT (tag) DO UPDATE
SET tag = EXCLUDED.tag,
    update_date = now();

Step by step: try to insert pen; the tag guard fires since pen exists; switch to update mode; set tag to the attempted EXCLUDED.tag (still pen); set update_date to now() at this run. Read back: tag still pen, key still 1, no new row — but the stamp moved (the lecture's run shifts from near 39.095 to near 18.17). That moved stamp is the proof the clash path updated instead of inserting.

The SET list decides the refresh, so reshaping works too. Sending 'pen1' when only pen and pencil exist inserts a genuine third row; resending a known tag while setting tag = EXCLUDED.tag plus extra text morphs the stored label (one demo turned stored pen into pen1 with the stamp moving near 19.95). The engine never improvises — whatever the SET pairs compute is exactly what the old row becomes. The full shape to memorize is: INSERT INTO table, column list, VALUES list, ON CONFLICT guard, then DO NOTHING or DO UPDATE SET pairs with an optional extra WHERE for conditional refreshes.

Worked refresh trace. Setup: pen stamp T0, key 1. Step 1: run the DO UPDATE block for 'pen'. Expected: success note. Step 2: SELECT * FROM t_tags WHERE tag = 'pen';. Expected: one row, key 1, stamp T1 later than T0. Sense-check: same key, same tag, later stamp — update-in-place confirmed; a new key would mean a twin slipped past the guard. Second trace: run the block for 'pen1'. Expected: a third row appears with its own fresh stamp, proving fresh values still insert through the same statement.

Cross-engine twins of the refresh branch: MySQL writes it as INSERT INTO t_tags (tag) VALUES ('pen') ON DUPLICATE KEY UPDATE update_date = NOW(); Snowflake and Databricks write it as the WHEN MATCHED THEN UPDATE SET ... arm of MERGE. The EXCLUDED prefix itself is the PostgreSQL spelling (other Postgres docs sometimes show it as the proposed-row alias) — when translating, "the attempted values" is the phrase to carry across.

Envision the drawer: the old pen form sits in place while the clerk copies the date line off the new envelope onto it and files the envelope away. Landmark: the key never moves. Takeaway: clash plus SET rewrites in place; only genuinely new tags grow the table.

Scope: the clash branch fires only on guard violations (UNIQUE, primary key); ordinary non-conflicting inserts never touch it. It assumes the guarded column is named exactly in ON CONFLICT (tag) — naming the wrong column silently matches nothing and the statement fails with a duplicate error instead of refreshing. Assumption: now() means server time at execution; two rapid runs can share a stamp on coarse clocks, so wait a beat between demo runs if your stamps look frozen.

Two traps close the lecture. First, writing SET tag = tag (no EXCLUDED) which copies the old value onto itself and refreshes nothing but the clock — harmless here, misleading elsewhere. Second, expecting DO UPDATE to change the key: keys of surviving rows never change on conflict; only the SET-listed columns do.

Recap: ON CONFLICT (tag) DO UPDATE SET ... EXCLUDED ... replays safely — new tags insert, known tags refresh in place with the key untouched. Exam note: expect to write both tails from memory, name the guarded column, and explain EXCLUDED as the attempted new values. Bridge: the appendices collect every exam shape and every live-system home for these writes.

Tag feeds, click streams, counters, last-seen stamps, and retry-safe loaders all live on this statement: replay the same file without twin rows, refresh times on each repeat, and let the guard — not application code — arbitrate the race.

Exam Guidance Summary

No mark split or paper pattern was stated in this material. The checks below follow the tasks shown, with the cross-engine spellings a learner should keep beside the lecture form.

Write INSERT INTO with matching column and value order, correct quote use for text, and bare numbers for age. Show the read-back with SELECT *. Multi-row VALUES ('a'), ('b') works on all four shelf engines; omitting the column list works but forces full-row positional values and breaks when columns are added later.

Show the doubled-quote fix for a value like Bill O'Sullivan and state that the doubled mark stores as one quote. Snowflake's dollar-sign wrap and MySQL's backslash escape are worth recognizing, but the doubled standard form is the portable answer.

Add RETURNING * to an insert to echo the full stored row and RETURNING customer_id to echo only the new key. State when each fits: full row for logs, key only for the next statement. PostgreSQL and Snowflake support the clause; on MySQL fetch the id with LAST_INSERT_ID() and on Databricks re-read instead.

Write UPDATE ... SET ... WHERE customer_id = n for one column and for two columns with a comma between pairs. Pick rows by key. Append RETURNING * to an update and state that only touched rows come back. Updates from a second table use a subquery or (PostgreSQL) a FROM arm, but single-table keyed updates are identical everywhere.

State the all-rows rule: no WHERE means all rows change for UPDATE and all rows go for DELETE FROM. Show both the filtered and filter-free forms. Count first, confirm the connection, and keep a backup table (CREATE TABLE ... AS SELECT *) before any wide write. TRUNCATE is the faster full-clear cousin that can also restart the key sequence.

Write both upsert tails: ON CONFLICT (tag) DO NOTHING and ON CONFLICT (tag) DO UPDATE SET tag = EXCLUDED.tag, update_date = now(). Explain EXCLUDED as the attempted values and UNIQUE on tag as the clash guard. MySQL spells these INSERT IGNORE and ON DUPLICATE KEY UPDATE; Snowflake and Databricks spell the same sync as MERGE arms.

Final check: every shape above runs, reads back, and names its guard — key for updates and deletes, unique tag for upserts, doubled quotes for hostile text.

Key Industry Applications

Practice tables in a test database let teams trial each write before running it on live customer data. The movies database and its customers and t_tags tables stand in for these live cases throughout the lecture.

Sign-up and import jobs map form fields to the insert column list and user input to the values list, leaving the auto-filled key to the database. PostgreSQL numbers keys with SERIAL or standard IDENTITY, MySQL with AUTO_INCREMENT, Snowflake with AUTOINCREMENT/IDENTITY, and Databricks with identity columns — one concept, four spellings, same loader code shape.

Sheet and form imports meet quoted names like O'Brien and O'Sullivan daily, so loaders use the doubled-quote standard form (or dollar-quoting and bound parameters where offered) or the load fails on those rows.

Sign-up flows grab the fresh key with RETURNING customer_id for the next screen (or LAST_INSERT_ID() on MySQL), while load jobs log the full echo with RETURNING *. Either way one round trip is saved per write.

Profile edit screens build one UPDATE ... WHERE customer_id with the logged-in key and comma-split pairs for mail and age. Admin consoles use UPDATE ... RETURNING * to show and log only the touched rows on wide tables, avoiding full re-scans.

Feature flags and backfills use filter-free updates to switch is_enable to Y or fill a new column for all rows at once — always after a count and on the confirmed connection.

Account-retire jobs delete by key, training-room resets use filter-free deletes (or fast TRUNCATE) to wipe practice rows, and live deletes pair with backups and server checks. Tag feeds and retry-safe loaders use ON CONFLICT DO NOTHING for insert-if-missing and DO UPDATE with EXCLUDED to refresh stamps without twin rows — MySQL shops write the same logic as ON DUPLICATE KEY UPDATE, Snowflake and Databricks shops as MERGE.

Through-line: sandbox first, filter by key, read back every write, and let guards (PRIMARY KEY, UNIQUE, backups) rather than memory arbitrate the dangerous cases.
