29.1 Limits of LIKE and the Goal of Full Text Search

Why does a database that can join a million rows in a blink still stumble when you ask it whether a speech is "about dogs"? This section sets up that puzzle and names the prize: a search that reads for sense, not just spelling.

A LIKE pattern — a match test where percent signs stand for any run of characters — finds rows where a column holds a given substring. A first demo runs a select with a LIKE test on a movie name column for the word star and gets back three rows. Nothing surprising happens: the engine walks each value row by row and keeps the ones whose letters line up.

Think of LIKE as a magnifying glass dragged letter by letter across each shelf. It is faithful to spelling and blind to sense. That is exactly right for short tidy labels such as a movie name, and exactly wrong for long free wording such as a speech, a union address, a market call report, or an article abstract.

A full text search — a method that looks inside the full wording of stored documents rather than only inside short metadata fields — covers one document or a whole collection held in a full text database. Metadata means short labels such as title, abstract, author name, country of origin, or a chosen section. Full wording means the entire text itself. Search engines work this way: they scan huge piles of wording and return the documents that hold the wanted terms.

Picture a table of text documents. These are not tidy columns such as movie id and movie name. Each row holds a whole speech or report, hundreds or thousands of words long. The task is to learn whether certain words sit inside them. LIKE can still scan a text column that holds a long document, but the row-based design calls for more than a raw substring scan, for three concrete reasons.

First, nouns with double senses. Take the nouns dog and fox in singular form:

SELECT * FROM films WHERE title LIKE '%dog%';
SELECT * FROM films WHERE title LIKE '%fox%';

The same test also returns rows such as dog villa and fox trot. Those rows hold the letters as part of a longer name, yet they are not about the animal nouns dog and fox. The intent was the animal sense, and LIKE cannot tell the senses apart because it never parses words at all — it only matches letter runs.

Second, word forms. Take the word query. When the stored form is the plural queries, a plain LIKE test for query misses it. The two forms point to the same idea to a large extent, yet the letter patterns differ. A reader might reach for a regular expression here. Regular expressions are strong — ~, ~*, regexp_match(), and substring(... from ...) can catch many variants — yet they still match letters, not sense, and they run slowly over huge documents, even with indexes in place, because each pattern must be tested against raw text.

Third, verb tenses. Take the verb jump. Its forms include jump, jumped, and jumping. A search for jump finds only that exact letter run and misses jumped and jumping. The only fix inside LIKE is to list each form with OR tests or to pack the forms in an array and scan the whole document for each one. That scans the full document itself once per form, which is slow and brittle: miss one tense and you silently lose rows.

A semantic vector — a language aware form of the words in a document that keeps meaning and drops noise — is the way out. Instead of scanning the full wording at query time, the system turns the wording into this compact form once and then scans only the compact form. Small glue words such as I, am, and is carry no search sense, so they fall away. Word groups such as jump, jumped, and jumping map to one shared base form. Punctuation falls away too. That is work a human reader does with ease: you hear "jumping" and think "jump". The task is to give the database the same skill, ahead of time, so every later query reuses it.

The trade is simple to state. Exact letter fidelity goes down a little — you can no longer ask "where exactly was the comma" from this store — while speed and sense-match quality over huge text go up by a large factor. PostgreSQL calls this compact form a tsvector, built once and scanned forever after.

29.1.1 What Full Text Search Covers

Full text search looks at the whole document wording. Metadata search looks only at short labels such as author or title. A speech or a market report is a document. A movie id is metadata. The module uses speeches and reports as running cases where the full wording matters, because the interesting question — did the president dwell on war and peace, did the call keep returning to defense — lives inside the paragraphs, not in the title line.

A useful mental picture: metadata search asks "which folder is labelled X", while full text search opens every folder and reads the pages. The rest of the module builds the machinery that makes opening every folder affordable.

29.1.2 Where LIKE Breaks Down

LIKE matches letter patterns. It cannot group singular and plural forms. It cannot group verb tenses. It cannot skip longer names that merely hold the same letters, such as fox inside fox trot. It also scans the raw text each time, so cost grows with document size: double the speeches and you roughly double the letters scanned per query.

Scope: LIKE is still the right tool when you need exact substring control — finding every title that literally contains Jr. or every code that starts with SO17. Its promise is letter fidelity, and its limit is that it promises nothing about words, senses, or speed over documents. When the ask is "about this idea, in any wording", step up to full text search.

A side note for learners coming from other engines, since the same pain shows up everywhere. In MySQL, LIKE '%word%' has the identical blind spots, and its answer is a different machine: a FULLTEXT index queried with MATCH(col) AGAINST('word' IN NATURAL LANGUAGE MODE) or IN BOOLEAN MODE, with its own stopword list and minimum token length instead of lexemes and positions. In Snowflake and Databricks/Spark SQL there is no built-in tsvector at all: you lean on LIKE, ILIKE, CONTAINS, RLIKE/REGEXP, or you tokenize yourself with SPLIT plus FLATTEN/EXPLODE, and true sense-aware search moves to Cortex Search or Vector Search outside plain SQL. The gaps named here — plurals, tenses, glue words — are the reason all of those engines built something beyond LIKE. PostgreSQL's version is what this module teaches.

29.1.3 The Semantic Vector Idea

A semantic vector keeps one base form per word group and drops glue words and punctuation. Later sections show how this compact form gets built with to_tsvector and scanned with to_tsquery plus the @@ match sign. For now hold the shape in mind: sorted base forms, each tagged with the word slots where it appeared, ready for fast sense-to-sense comparison.

Search engines, market report parsing, and review search all rest on this same trade of a little letter fidelity for a large gain in speed and recall. A review search that folds "loved", "loves", and "loving" into one base counts the feeling once and completely, instead of three times half-heartedly.

A LIKE test matches letters row by row; a semantic vector matches senses from a compact store built once. When a question turns on word forms, tenses, or animal-versus-dance senses of the same letters, LIKE is the wrong unit and the vector is the right one.

29.2 Introducing tsvector

How do you teach a database that washes, washed, and washing are the same ask? PostgreSQL answers with two new types: one for the document side and one for the request side. This section builds the document side.

PostgreSQL ships with a strong full text engine. It adds two data types for text search. The first is tsvector — the type that holds wording to be searched in a tuned, sorted form. The plain speech for it is vector. The second is tsquery — the type that holds the search request with its terms and logic. The plain speech for it is query. The vector holds the document side. The query holds the request side.

Think of the vector as a book index prepared before anyone asks a question, and the query as the question a reader brings later. The index lists each important word once, alphabetically, with the page numbers where it appears. Looking up a question in the index beats rereading the book every time.

The vector type does two things. First, it cuts wording down to a sorted list of lexemes — base word units that carry sense, with suffix driven variants folded together. A lexeme is a word with its suffix forms stripped: the forms washes, washed, and washing all land on wash. Second, it drops stop words — short glue words such as the, is, or, and, a, and with that add almost no search sense. Punctuation such as dots and commas falls away for the same reason. Nobody gains by scanning for a dot across a huge store.

A builder function makes vectors. Its name is to_tsvector — the function that turns plain wording into tsvector form. It takes the wording, with an optional language tag in front, as in to_tsvector('english', speech_text). The short name ts stands for text search. A one word call looks like this:

SELECT to_tsvector('washes');
SELECT to_tsvector('washed');
SELECT to_tsvector('washing');

Each of the three calls returns the same lexeme, namely wash with position marker 1, rendered as 'wash':1. The marker after the colon gives the word slot inside the source wording. Since each call holds one word, each marker reads 1. The store is alphabetical, and each entry carries its source slot. Think of the stored pair as base form plus slot list — exactly the index entry plus page numbers.

Positions count every token including stop words, which surprises beginners. In This is a test, the surviving lexeme test carries position 4, not 1, because This(1) is(2) a(3) test(4) were all counted before the glue was dropped. That kept-slot numbering is what later makes "word A followed by word B" checks exact.

29.2.1 Lexemes and Stop Words

A lexeme folds suffix variants into one base. Walk, walks, walked, and walking share a base. Sit and sitting share a base. Stop words never reach the store. In the test This is a test, only test lands in the vector. In the test This is a with no content word, the vector holds nothing at all, because this, is, and a carry no search sense. In This is an amazing story, the store keeps amaze for amazing and story for story — the ING tail falls away through the English stemming rules. PostgreSQL also folds case, so PostgresSQL lands in lower case form.

The language tag controls both foldings. to_tsvector('english', ...) applies English stemming and the English stop list; spanish, german, french, and the other installed configurations apply their own. Passing simple instead skips stemming: it lowercases and drops a minimal stop list but keeps word forms distinct, which is handy when exact tokens such as product codes matter more than sense. You can list installed configurations with SELECT cfgname FROM pg_ts_config;.

Exam note: tests on this topic often ask which tokens survive vector building and which fall away as stop words or punctuation. The rule to rehearse: content words survive as lowercased lexemes with kept-slot positions; glue words (I, am, is, the, a, with, to, over, you) and punctuation never reach the store; suffix variants of one root share one entry.

How other engines differ, briefly, so you place this idea correctly. MySQL's FULLTEXT index also drops stopwords and short tokens, but its stoplist and minimum token length (innodb_ft_min_token_size, default 3, and innodb_ft_server_stopword_table) decide survival instead of a stemming dictionary, and the stored form is an inverted list hidden inside the index rather than a visible tsvector column you can SELECT. Snowflake and Databricks/Spark SQL expose no lexeme type: SPLIT(text, ' ') plus LOWER plus filtering against your own stop list is the hand-rolled equivalent, and stemming needs an external library or Cortex/ML step. Same goal — a compact searchable form — with PostgreSQL giving you the most transparent version.

29.2.2 Worked Examples

Example 1 — one word, three forms. Run to_tsvector on washes, then on washed, then on washing. Setup is one plain word per call. Substitution is the function call itself. Each run returns 'wash':1. The end result is a one-entry vector in each case. The point is that suffixes do not split the search: three spellings, one stored base, so one later query finds all three. Sense-check: change the input to wash itself and the output is identical, confirming the fold is stable.

Example 2 — the sentence The quick brown fox jumps over the lazy dog. The vector keeps brown, dog, fox, jump, lazy, and quick. The word jumps maps to jump. The words the and over fall away as glue. The dot falls away. The rendered vector reads 'brown':3 'dog':9 'fox':4 'jump':5 'lazy':8 'quick':2. The entries sit in alpha order, each with its source slot: slot 1 was the, slot 2 was quick, slot 3 was brown, slot 4 was fox, slot 5 was jumps, slot 6 was over, slot 7 was the, slot 8 was lazy, slot 9 was dog. So brown shows slot 3, dog shows slot 9, fox shows slot 4, jump shows slot 5, lazy shows slot 8, and quick shows slot 2. A common slip is to read the alpha order as source order. The fix is to read the number after the colon for source order and the alpha run for store order. Sense-check: jump at 5 sits right after fox at 4, matching the original word order, so the slots survived correctly.

Example 3 — the sentence Hey, wait, I am walking across the sitting room to sit with you. The vector keeps across at slot 6, hey at slot 1, room at slot 9, sit at slots 8 and 11, wait at slot 2, and walk at slot 5, rendered as 'across':6 'hey':1 'room':9 'sit':8,11 'wait':2 'walk':5. The form sitting at slot 8 and the form sit at slot 11 share the entry sit — one lexeme, two positions. The comma falls away. The words I, am, the, to, with, and you fall away as glue. Notice walk sits at 5 even though walking was the fifth content-carrying idea only after counting glue: Hey(1), wait(2), I(3), am(4), walking(5), across(6). Try more forms at your end — walks, walked — and watch how each maps to the same base with its own slot. Sense-check: eleven input tokens collapse to six stored entries, so the store is roughly half the size before any scaling.

29.2.3 Why Vectors Run Fast

A vector stores each base form once plus its slots. A later search scans this short sorted list, not the raw wording. Meaning match replaces letter match. That is why jump finds jumped, and why fox skips fox trot. The alphabetical sort makes lookup logarithmic rather than linear, and the slot lists make nearness checks arithmetic on small integers rather than rescans of paragraphs.

Picture the shelf analogy again: without the index you reread every book per question; with it you open the index, find jump, and jump straight to pages 5, 8, and 11. The next section turns to the request side — tsquery — that asks questions against these vectors.

Scope: vectors are built with one language configuration, and that choice sticks to the stored form. Mixing to_tsvector('english', ...) rows with to_tsvector('french', ...) rows in one column silently mixes two stemming rules, so later queries behave unevenly. The assumption is one language per column; multilingual stores need one vector column per language or the simple configuration plus outside handling.

29.3 Using tsquery with Operators

The document side is indexed. Now the reader walks in with a question. This section builds that question side and the five kinds of logic it can carry.

The to_tsquery function — the builder that turns plain request wording into tsquery form — takes the words to check against a stored vector. A tiny match test pairs a vector with a query through the @@ sign, which reads as matches. One side holds This is a lamp as a vector; the other side holds lamp as a query; the test returns true. Swap the request to lamp1 and the same test returns false. Either side can later be a table column, which the next section uses at scale.

SELECT to_tsvector('english', 'I am walking across the sitting room')
  @@ to_tsquery('english', 'walking & sitting');  -- true
SELECT to_tsvector('english', 'I am walking across the sitting room')
  @@ to_tsquery('english', 'walking & running');  -- false

Both sides pass through the same lexeme step, so walking meets walk and sitting meets sit before any comparison happens. That shared normalization is the whole trick: document and question are translated into the same dialect, then compared.

The query side has five logic forms. The @@ sign tests a match. The ampersand & reads as AND. The pipe | reads as OR. The exclamation mark ! reads as NOT, a negation. A distance form reads as followed by, with <-> for side by side words and <N> for words N slots apart. These forms mix freely, and parentheses set the run order. With them, huge wording stores stay fast and precise, because each arm resolves to a slot list and the logic just combines lists.

A compact operator map to keep beside you:

Ask in English Query text Reads as
fox 'fox' single term
fox AND dog 'fox & dog' both present anywhere
fox OR tiger `'fox \ tiger'` at least one present
NOT tiger / without roads '!tiger', 'transportation & !roads' barred term absent
military directly followed by defense 'military <-> defense' adjacent, in order
sphinx within 2 slots before quartz 'sphinx <2> quartz' ordered nearness

When to pick which: reach for & when every term must appear somewhere, | when any one suffices, ! to carve a topic out, and <-> / <N> when word order or closeness is the claim — "military defense" the phrase versus "military ... defense" pages apart.

29.3.1 The Match Operator

Build a vector from the quick brown fox sentence and test the request fox. The result is true. Test foxes and the result is still true, because both map to the same lexeme. Test fox trot and the result is false. The store is smart enough not to match a mere letter prefix: fox the animal and fox trot the dance land on distinct lexeme paths, so the first pair meets and the second pair does not. That is a step past LIKE, which would have matched the shared letters in both cases.

Test jump against a vector that holds jump. The result is true. Test jumping or jumped and the result is still true. The request side runs through the same lexeme step, so all three forms meet at one base. The match is sense to sense, not raw letters to raw letters.

Note the asymmetry beginners trip on: to_tsquery('fox trot') with a bare space is a syntax fault, not an AND. The builder wants an explicit link — 'fox & trot'. A bare space leaves the link unclear, so the parse fails. Always write the operator.

29.3.2 Worked Examples

Example 1 — single term true and false. The vector holds This is a lamp, which stores 'lamp':4. The query holds lamp, normalized to 'lamp'. The @@ test returns true. Change the query to lamp1 — a distinct token that normalizes to 'lamp1', which is absent from the vector — and the test returns false. Setup is one vector plus one request; the end answer is a boolean. Sense-check: a true arm plus a present lexeme means true; swap in an absent lexeme and the same shape flips to false.

Example 2 — AND with fox and dog. The English ask is fox AND dog. The query form is 'fox & dog'. Run it against the quick brown fox vector, which holds both fox and dog. Both arms are true, so the whole test is true. Each arm is scored alone against the slot store, then joined — which is why arm order never matters for &.

Example 3 — OR with fox or tiger. The English ask is fox OR tiger. The query form is 'fox | tiger'. The vector holds fox but no tiger. One true arm is enough for OR, so the whole test is true. Sense-check: flip the vector to one holding neither term and the same query returns false, confirming OR needs at least one hit.

Example 4 — NOT with tiger and dog. The form '!tiger' reads as no tiger. Against a vector with no tiger, the test is true. The form '!dog' against a vector with dog is false, because the barred term is present. A fuller carve-out reads 'transportation & !roads': keep every row with transportation, then remove the ones that also mention roads. In the speeches data that shape returns 15 rows. Sense-check: !roads alone on a roads-free vector is true, which is why NOT almost always rides with an AND partner — alone it matches nearly everything.

Example 5 — mixed logic with fox, dog, tiger, and king. The English ask is fox AND dog OR tiger AND NOT king. The query form is 'fox & dog | tiger & !king'. Parentheses make the aim sharp, as in '(fox & dog) | (tiger & !king)'. Against the quick brown fox vector the result is true via the left arm. The rule is to bracket mixed AND and OR asks so the run order stays clear, exactly as with arithmetic AND/OR in a WHERE clause. Sense-check: evaluate each bracket alone first — left is true, right is false — then OR the two, giving true.

Cross-engine readers should note the dialect change without a concept change. MySQL's boolean mode writes the same ideas differently: +fox +dog for AND-like required terms, fox tiger for OR-like, -king for NOT, and "military defense" in double quotes for the phrase. Snowflake and Spark SQL express the same logic with plain boolean SQL over CONTAINS/RLIKE predicates rather than a query type: WHERE CONTAINS(text,'fox') AND NOT CONTAINS(text,'king'). Learn the PostgreSQL spelling here; the thought transfers everywhere.

29.3.3 Student Questions and Answers

Q: Why does foxes match fox but fox trot does not, when both start with fox? A: The match runs on lexemes, not on letter prefixes. Fox and foxes share one animal sense base, so both normalize to 'fox' and meet. Fox trot is a distinct dance sense with its own base path ('fox' & 'trot' as two lexemes, or a separate compound entry depending on configuration), so a single-term ask for 'fox' against that fuller vector behaves differently from a prefix scan. LIKE would have matched the shared letters in both cases; the lexeme path keeps the senses apart. Several students asked variants of this — the confusion point is always prefix thinking versus lexeme thinking.

Q: Why does jumping match a stored jump? A: Both the stored wording and the request wording pass through the same base form step. Jump, jumped, jumping, and jumps all map to jump, on both the to_tsvector side and the to_tsquery side. The @@ test then links equal bases. The match is sense to sense, not raw letters to raw letters.

29.3.4 Practical Tips

Keep requests in lower case plain words and let the builder fold the forms. Bracket each mixed logic ask. Test each arm alone before mixing arms, so a false arm is easy to spot — run 'fox', then 'dog', then 'fox & dog'. When a query string comes from a user or an app, prefer plainto_tsquery('...') (which inserts & between words automatically) or phraseto_tsquery for phrase input over hand-concatenating operators, to avoid the bare-space syntax fault.

Scope: to_tsquery expects operator-linked input and throws on sloppy spacing; plainto_tsquery and websearch_to_tsquery accept raw human typing instead. The assumption behind to_tsquery is that you, the query author, supply the logic. When the input is untrusted user text, that assumption fails — switch builders rather than string-hacking quotes around user words.

Product search and help center search use this same AND OR NOT mix to cut huge result piles down to the useful few, and news search leans on the distance form for phrase fidelity.

One vector plus one query plus @@ gives a boolean; &, |, !, and <->/<N> combine booleans and slot lists into precise asks. Normalize both sides with the same language, write every link explicitly, and bracket mixed logic.

29.4 Full Text Search Within a Table

Single SELECT probes prove the idea. Real work needs the pattern at table scale: raw text beside its vector twin, filled once, filtered forever. This section builds that working table.

A working table pairs raw wording with its vector twin. The build used here is a table named docs with a serial id column doc_id, a raw wording column doc_text, and a vector column doc_tsv of tsvector type. Keep both columns: the raw side stays readable for humans and headline clips, while the vector side stays fast for matching.

CREATE TABLE docs (
  doc_id SERIAL PRIMARY KEY,
  doc_text TEXT,
  doc_tsv TSVECTOR
);

Rows go in through the raw wording column only. The vector column starts empty — NULL until you fill it. A check with SELECT * shows the raw wording present and the vector side blank. Then an update fills the vector twin from the raw wording:

UPDATE docs SET doc_tsv = to_tsvector(doc_text);

A fresh SELECT shows each raw sentence next to its tuned vector. The sentence Five boxing wizards jump quickly stores box, five, jump, quick, and wizard in alpha order with slots: 'box':2 'five':1 'jump':4 'quick':5 'wizard':3. Boxing maps to box. Wizards maps to wizard. Quickly maps to quick. Small glue and dots fall away.

A search then scans the vector column and filters with a query:

SELECT doc_id, doc_text FROM docs
WHERE doc_tsv @@ to_tsquery('jump');

Rows with jump, jumps, or jumped all return, since all share the jump base. The scan never touches the raw wording for the match. It uses the lexeme plus slot store, which is the speed source. The boolean per row drives the filter, just like any WHERE test — @@ returns true or false per row, and WHERE keeps the true ones.

For production tables, replace the one-off UPDATE with a self-maintaining column so new rows never sit unindexed: either a stored generated column (doc_tsv TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', doc_text)) STORED) or a trigger that refreshes doc_tsv on INSERT and UPDATE. The lecture's explicit UPDATE is the clearest way to see the twin being born; the generated column is how you keep it alive without remembering.

29.4.1 AND Searches Over Rows

The ask jump AND quick uses the form 'jump & quick'. Two rows return, each holding both bases. One holds jump with quickly, the other holds jump with quick — both normalize to 'quick', so both pass. Each arm is true, so each row passes. AND means both present anywhere in the row, in any order, at any distance. Both 'jump & quick' and 'quick & jump' return the same rows, because each arm is scored alone and then joined.

29.4.2 Worked Examples

Example 1 — side by side words. The ask is jump directly followed by quick. The form uses the distance sign with a dash, written as 'jump <-> quick'. Against the docs rows, only Five boxing wizards jump quickly passes, because there jump sits at slot 4 right before quick at slot 5. The check reads the stored slots, not the raw letters. Sense-check: a row holding both words paragraphs apart passes 'jump & quick' but fails 'jump <-> quick', confirming the distance form tests order plus adjacency, not mere co-presence.

Example 2 — words with a gap. The ask is sphinx near quartz in the sentence Jackdaws love my big sphinx of quartz. The stored slots put sphinx at 5 and quartz at 7 in one row reading (Jackdaws(1) love(2) my(3) big(4) sphinx(5) of(6) quartz(7), with light glue possibly dropped but slots kept). The ask 'sphinx <2> quartz' reads as sphinx followed by quartz with two slots between the start points, since 7 minus 5 is 2. The row returns. Change the gap to 3 and a longer span row returns, where the slot math reads 4 minus 1 — start slots 1 and 4, span 3. The number between the angle marks sets the allowed span between start positions. Sense-check: <1> would demand adjacency (span 1) and would fail here, since the span is 2; widening to <3> admits it again.

Example 3 — order matters. Swap the ask to 'quartz <2> sphinx'. No row returns. Quartz sits at the higher slot and sphinx at the lower slot, so a low to high scan finds nothing: the distance form only runs forward from the first term's slot to the second term's slot. A backward ask with the higher slot first finds no forward path. By contrast, plain AND is order free, as shown above. Sense-check: if the sentence were reversed to ... quartz ... sphinx, the swapped query would start passing — the failure is about direction, not vocabulary.

29.4.3 Student Questions and Answers

Q: Why does the gap number read 2 when sphinx and quartz look one word apart? A: The number counts the span between start slots, not the words in between. With sphinx at slot 5 and quartz at slot 7, the span is 7 minus 5, which is 2. The one word between them (of at 6) plus one gives the span. The slot list inside the vector makes this math direct: subtract the two positions after the colons.

Q: Why does swapping the two terms break the distance ask but not the AND ask? A: The distance form scans forward from the first term slot to the second term slot. A backward ask with the higher slot first finds no forward path. AND scores each term alone, so term order plays no role. Several students hit this; the fix is to remember that <-> and <N> carry an arrow of direction while & and | do not.

29.4.4 Practical Tips

Store raw wording and vector side by side, so the raw side stays readable and the vector side stays fast. Fill the vector column with one UPDATE after bulk loads. Name the vector column with a short clear name, such as doc_tsv, to keep later queries short. Build distance asks by first confirming each arm with &, then tightening to <-> or <N>, so a zero-row result unambiguously means "too strict" rather than "term missing".

Exam note: expect a task that builds a table, fills the vector column, and then runs match, AND, and distance asks with booleans to explain. The flow to rehearse: CREATE TABLE with a TSVECTOR column, INSERT raw text, UPDATE ... SET tsv = to_tsvector(...), WHERE tsv @@ to_tsquery(...), and slot subtraction for any <N> ask.

29.5 Setup Presidents Speeches Data

Toy sentences prove the machinery. Now the module loads a real corpus: 35 presidential speeches from the 1940s onward, long enough that raw scanning hurts and vectors earn their keep.

The table is named docs_president. It holds a serial id, a name column of 100 characters, a speech title, a speech date, a raw wording column speech_text, and a vector column speech_tsv of tsvector type. The raw column feeds humans; the vector column feeds the engine.

CREATE TABLE docs_president (
  doc_id SERIAL PRIMARY KEY,
  president VARCHAR(100),
  title TEXT,
  speech_date DATE,
  speech_text TEXT,
  speech_tsv TSVECTOR
);

A properties check on the vector column (in psql, \d docs_president) shows the tsvector type. The speech rows arrive from a CSV file named presidents_speeches.csv through a COPY step at the terminal. The file uses pipe marks between fields and has no header row, with @ as the quote character because speeches themselves contain commas and double quotes. The load step names the target columns in order:

COPY docs_president (president, title, speech_date, speech_text)
FROM 'presidents_speeches.csv'
WITH (FORMAT csv, DELIMITER '|', HEADER off, QUOTE '@');

Run from the folder that holds the file, or give the full path — server-side COPY reads from the server's filesystem, so a "file not found" almost always means the path is client-relative instead of server-relative (use \copy in psql for client-side files). A row count check should show 35 loaded rows. A quick SELECT shows name, title, date, and full wording per row.

The vector twin is then filled with an explicit English tag:

UPDATE docs_president
SET speech_tsv = to_tsvector('english', speech_text);

The two inputs to the builder are the language name and the source column. Earlier demos skipped the tag and took the default configuration; here naming 'english' locks the stemming and stop rules so the store stays steady when more tongues arrive later. A fresh SELECT shows the raw wording next to a long tuned vector per speech.

29.5.1 The GIN Index

A plain table scan over vectors is still slow at scale — every query would deserialize every vector. The default B-tree index suits numbers and short keys, not lexeme lists. The docs point to a GIN index — a generalized inverted index that keeps one entry per lexeme plus the rows and slots where it appears, so matches land much faster. Picture the book index again, but now shared across all 35 speeches: one entry for war pointing at every speech and slot that holds it.

The build looks like this:

CREATE INDEX idx_docs_president_tsv
ON docs_president USING gin (speech_tsv);

A refresh of the index list shows the new GIN entry. Each lexeme points straight to its rows and slots. That is why later term, AND, and distance asks stay quick over 35 long speeches with no query change — the same WHERE speech_tsv @@ ... shape automatically uses the index once it exists.

GIN trades slower writes for much faster reads: each INSERT or UPDATE now maintains the lexeme entries, which pays off as soon as reads outnumber writes, the usual case for a speech archive. For bulk loads, create the index after the COPY plus UPDATE so the index builds once rather than row by row.

Other engines solve the same "scan is slow" problem differently, which is worth one paragraph as a learner. MySQL builds its FULLTEXT index at table definition or via ALTER TABLE ... ADD FULLTEXT INDEX, and queries must use MATCH ... AGAINST to touch it — a plain WHERE text LIKE never will. Snowflake leans on micro-partition pruning plus explicit Search Optimization Service rather than a lexeme index, and Databricks leans on Delta data skipping plus Photon, with true text-relevance search delegated to Vector Search endpoints. Same need — avoid full scans — with PostgreSQL's GIN being the most hands-on version you build yourself.

29.5.2 Worked Examples

Example 1 — load check. After COPY, run SELECT count(*) FROM docs_president;. The count reads 35. A SELECT * shows the name, title, date, raw wording, and empty (NULL) vector before the UPDATE, then a full vector after the UPDATE. Setup is the file plus the COPY options; the substitution is the UPDATE; the end state is every row with both twins filled. Sense-check: any row whose vector is still NULL after the UPDATE was missed by the SET — recount NULLs with WHERE speech_tsv IS NULL and you should get zero.

Example 2 — index check. After CREATE INDEX, open the table index list (\di in psql or the indexes tab in a GUI). The GIN entry on speech_tsv is present. Later asks use it with no query change: EXPLAIN on a @@ filter now shows a Bitmap Index Scan over the GIN entries instead of a Seq Scan. Sense-check: run the same WHERE speech_tsv @@ to_tsquery('war') before and after indexing — identical rows, visibly faster plan.

29.5.3 Student Questions and Answers

Q: Why pass english to to_tsvector when the earlier demos skipped it? A: The language tag picks the lexeme and stop word rules. English folds plurals and tenses one way, while other tongues fold their own way — spanish, german, french each ship their own dictionaries. Naming it keeps the speech store steady when more tongues arrive later, instead of silently inheriting whatever the database default configuration happens to be.

Q: Why not keep the default B-tree index for the vector column? A: A B-tree suits ordered scalar keys such as numbers and dates, where "less than" means something. A vector holds a bag of lexemes with slot lists, where ordering across whole vectors is meaningless. The GIN form links each lexeme to its rows, which fits that bag shape and speeds term asks; a B-tree over the whole vector value would almost never match a @@ predicate.

Load raw text with COPY using the file's real delimiter, header, and quote settings; fill the twin with an explicit language tag; index the twin with GIN after the load. From here on, every analysis query is just WHERE speech_tsv @@ ... over an indexed store.

29.6 Analyzing Presidents Speeches Text Data

Vectors built, GIN in place — now the payoff: story-style asks over 35 speeches. Who raised which theme, when, and in what words? This section runs those asks and shows the matching passage so readers trust each hit.

A base ask picks name, title, and date from docs_president and filters the vector column with a query. The ask for world looks like this:

SELECT president, title, speech_date FROM docs_president
WHERE speech_tsv @@ to_tsquery('world');

Rows from Truman, Eisenhower, Kennedy, and Johnson return, among others. A sort by speech date (ORDER BY speech_date) lines them in time order. The same shape counts 29 rows for humanity and 34 rows for war. Each count can seed a chart of who raised a theme and when.

Counts are the fastest story seed: wrap the filter in count(*) grouped by president and you get a theme timeline with one query per theme. But single terms are only the start.

A two word ask needs query logic, not bare words. The ask for war and peace written as 'war peace' with a gap fails with a syntax fault, because the builder wants an explicit link — to_tsquery has no rule for a bare space. The fixed form is 'war & peace'. It returns 34 rows. Each returned row holds both bases somewhere in its wording. The two terms can sit far apart; side by side order is a separate ask covered below.

The ask 'god & bless' returns 8 rows, with Truman once, Kennedy twice, and Johnson three times among them. The counts turn into a theme story with little extra work: group, count, sort, and the "who blessed most" claim writes itself.

29.6.1 Worked Examples

Example 1 — war and peace. Setup is the vector column plus the query 'war & peace'. The run returns 34 rows. Each row scores true on war and true on peace, each arm checked alone against the slot store. The takeaway is that AND means both present anywhere, not next to each other. Sense-check: run 'war' alone (34 rows) and 'peace' alone, then confirm the AND count is at most the smaller of the two — set logic holds.

Example 2 — adjacent pair military defense. The ask 'military <-> defense' reads as military directly followed by defense. Four rows return, with Eisenhower three times across 1956, 1958, and 1959, plus Nixon once. The slot lists drive the test: only rows where a military slot sits exactly one below a defense slot pass. No raw wording scan is needed. Note the lexeme forgiveness working silently — a stored military defenses still matches, since defenses folds to defense. Sense-check: loosen to 'military & defense' and the count can only grow, since adjacency implies co-presence but not the reverse.

Example 3 — headline context. The ts_headline function — the helper that shows where a match sits inside raw wording — takes the raw wording column and the same query and returns a short clip with marks around the hit terms. The base form looks like this:

SELECT ts_headline(speech_text, to_tsquery('military <-> defense'))
FROM docs_president
WHERE speech_tsv @@ to_tsquery('military <-> defense');

A returned clip reads like military defense are designed to protect and more, with bold marks around the two hits. Note the first argument is the raw speech_text, not the vector — headline works from readable wording. The default marks use ... bold tags, which turn bold in HTML output. A custom mark form passes extra settings with StartSel and StopSel labels:

SELECT ts_headline(
  speech_text,
  to_tsquery('military <-> defense'),
  'StartSel = <, StopSel = >'
)
FROM docs_president
WHERE speech_tsv @@ to_tsquery('military <-> defense');

The same clip then shows the hits wrapped in angle marks instead of bold tags. The docs list more dials such as MinWords and MaxWords, which bound clip length, and MaxFragments, which caps how many clips per row return — for example 'StartSel = <, StopSel = >, MinWords=5, MaxWords=7, MaxFragments=1' keeps one tight seven-word window per speech. Always use the same query in ts_headline as in the WHERE filter, or the highlighted words will drift from the matched rows. Sense-check: a clip that highlights neither term signals a query mismatch between the two calls — compare them first.

For reference across engines: MySQL shows context by returning the raw column and highlighting in the app, since MATCH ... AGAINST returns relevance but no clip function; Snowflake and Databricks likewise return raw text and format highlights outside SQL. PostgreSQL's ts_headline doing it inside the query is a genuine convenience — one reason news search and help search prototypes start here.

29.6.2 Student Questions and Answers

Q: Why does war peace with a space fail while war and peace logic works? A: The query builder needs an explicit link sign between terms. A bare space leaves the link unclear, so the parse fails. The form 'war & peace' names the AND link, and the run then succeeds. When the input is raw human typing rather than your own logic, switch to plainto_tsquery('war peace'), which inserts the & links automatically.

Q: Does war and peace in one row mean the two words sit side by side? A: No. AND only asks that both bases sit somewhere in the row, pages apart if need be. The distance form with angle marks — 'war <-> peace' for adjacent, 'war <N> peace' for near — is the tool for side by side or near asks. Pick AND for "both themes raised", distance for "raised together".

29.6.3 Practical Tips

Build one ask at a time and count rows before adding clips. Add ORDER BY speech_date for time stories. Use ts_headline only on the rows that pass — put the @@ test in WHERE and the headline in SELECT — so the clip work stays small. When a theme count looks surprising, headline two or three rows before charting: a single odd sense of a word can inflate a whole series.

Exam note: be ready to turn a theme count into a one line story claim, such as which leader raised a theme most often. The rehearsed shape is filter with @@, group or count, order by date, and headline one clip per row to show the evidence.

29.7 Ranking and Normalizing Text Results

Matching says which speeches qualify. Ranking says which qualify most. This section scores the hits so the densest fit rises to the top — and then corrects for speech length so long speeches stop winning by sheer size.

The ts_rank function — the scorer that orders matched rows by how well the wording fits the query — takes the vector column and the query and returns a number column, often named score. Think of it as a relevance thermometer: more hits, and hits closer together, read hotter.

SELECT president, title, speech_date,
  ts_rank(speech_tsv, to_tsquery('military <-> defense')) AS score
FROM docs_president
WHERE speech_tsv @@ to_tsquery('military <-> defense');

Three rows return with scores near 0.09, 0.58, and 0.19. The raw run lists them in store order. Add ORDER BY score DESC and the densest fit rises to the top, with the 1958 Eisenhower row first, then the 1959 row, then the rest. The score blends how often the terms hit and where they sit. A sibling function, ts_rank_cd, weighs cover density — how close the hit terms cluster — more strongly, which suits phrase-like asks.

The score is arbitrary across queries: a 0.58 for military-defense cannot be compared with a 0.35 for war-security-threat-enemy. It orders rows within one ask only. That limitation matters the moment you compare themes against each other — rank inside each ask, never across asks.

Long speeches can tilt raw scores, since more wording means more chances to hit. A third input to ts_rank sets a normalization choice — a setting that scales the score by length so long and short speeches sit on fair terms. The call shape is ts_rank with vector, query, and a number flag, as in ts_rank(search_speech_text, to_tsquery('english', 'war & security & threat & enemy'), 1). The flag 1 divides by document length; the documentation lists further flags for unique-word scaling and related options. With the length flag set, the same rows rescale and the order can shift: a raw top row near 0.35 can fall behind a shorter dense speech once size stops ruling. The exact numbers shift with the flag, yet the aim stays fixed — length stops ruling the order.

The textbook's four-term demo makes the effect concrete. Unnormalized, Clinton's 1997 message tops near 0.358, partly because it is one of the longest speeches in the table; normalized by length with flag 1, Bush's 2004 speech moves to the top near 0.000103 while Truman's 1946 message drops out of the top five. Three of five rows survive both orderings — a reassuring sign those three deserve a closer read whatever the scaling.

29.7.1 Worked Examples

Example 1 — plain rank. Run the military defense ask with ts_rank and no flag. Three rows return with raw scores near 0.09, 0.58, and 0.19. Add ORDER BY score DESC. The top row is the tightest term fit — the 1958 Eisenhower row. Setup is the same WHERE filter as the match query; the substitution is adding the rank expression to SELECT; the end state is the same rows, honestly ordered. Sense-check: the WHERE filter and the rank call carry the identical query string, so every scored row is a matched row and no matched row lacks a score.

Example 2 — length scaled rank. Rerun with the length flag passed as the third input, ts_rank(speech_tsv, to_tsquery('...'), 1). Scores rescale into a far smaller range and the order can shift, as the Clinton-versus-Bush swap shows. The lesson is to name the flag used, since each flag answers a distinct fair-compare ask. Market call parsing and investor note search use this same rank plus headline pairing to spot key phrases, count hits, and link hit bursts to price moves — one analytics team applies the same vector plus rank plus GIN stack to call reports for exactly this reason: raw hit counts favor long calls, normalized scores favor dense ones. Sense-check: the normalized order should still contain mostly the same rows as the raw order — a total reshuffle hints at a flag or query typo rather than a length effect.

Cross-engine placement in one paragraph: MySQL's MATCH ... AGAINST returns its own relevance score with no normalization flag — length handling is baked into its natural-language formula, and boolean mode scores 0/1 style. Snowflake and Databricks rank with explicit SQL you write yourself, such as hit counts over token arrays or ORDER BY on computed frequencies, or delegate to Cortex/Vector Search similarity scores. PostgreSQL sits in the middle: a real scorer with a visible length dial you must learn to turn.

29.7.2 Student Questions and Answers

Q: Why does a very long speech sometimes outscore a short sharp one? A: Raw rank counts hits, and long wording holds more hit chances — twice the paragraphs means roughly twice the rolls of the dice. The length flag scales for size, dividing by length, so a short speech with dense hits can rise past a long speech with sparse hits. Reach for normalization whenever speeches differ a lot in length.

Q: What inputs does ts_rank need at a minimum? A: It needs the vector column and the query: ts_rank(speech_tsv, to_tsquery('...')). The alias score (AS score) names the output so ORDER BY score DESC can sort it. The third flag input is optional and only shapes length scaling; the WHERE clause with the same @@ query is what filters, while rank only orders.

29.7.3 Practical Tips

Always pair ts_rank with the same query used in the WHERE test, or the scores will drift from the filter — a row can score highly on a query it was never filtered by. Show ts_headline clips next to scores so readers trust the order: score says how much, headline shows where. Keep the GIN index in place, since rank runs after the fast match slice narrows the rows. Cap exploratory ranking with LIMIT 5 while tuning, then remove it for the final story.

Scope: rank values compare rows within one query only. The assumption behind ORDER BY score DESC is a single fixed query over comparable documents. Comparing a 0.58 from one ask with a 0.35 from another, or ranking unnormalized scores across wildly different lengths, breaks that assumption — normalize first, and never sort across asks.

Exam note: expect a rank task that asks for the function inputs, the alias, the DESC order step, and the reason length scaling matters. Rehearse the full shape: ts_rank(vector, query[, flag]) AS score in SELECT, the identical @@ query in WHERE, ORDER BY score DESC, and one sentence on why flag 1 exists — fair comparison across lengths.

Exam Guidance Summary

No mark split or paper pattern was stated. The testable moves are steady across sections, and they reward hands-on rehearsal over memorized definitions.

Exam note: know which tokens survive to_tsvector and which fall away as stop words, suffixes, case, or punctuation — content words survive as lowercased lexemes with kept-slot positions, glue and punctuation do not. Know the five query forms: match with @@, AND with ampersand, OR with pipe, NOT with exclamation, and distance with angle marks plus dash or gap number. Know that distance asks run low slot to high slot and fail backward, while AND and OR are order free. Know the table flow: create docs with a tsvector column, COPY or INSERT raw wording, UPDATE the vector twin with to_tsvector, add a GIN index with USING gin, filter with WHERE vector @@ query, show clips with ts_headline, and order with ts_rank plus ORDER BY score DESC. Know the COPY fields for the speeches case: pipe delimiter, CSV shape, no header, and at sign quote mark. Know the ts_headline dials StartSel and StopSel with MinWords, MaxWords, and MaxFragments, and the rank length flag idea behind the third ts_rank argument.

A practical revision drill: rebuild the small docs table from memory, fill it, and run one match, one AND, one OR, one NOT, one <->, and one <N> ask, predicting each boolean before running. Then load the speeches shape, run 'war & peace', headline 'military <-> defense', and rank with and without the length flag. If every step behaves as predicted, the module is examination-ready.

Key Industry Applications

Web search engines scan tuned term stores rather than raw pages for each ask — the production great-grandchild of the tsvector plus GIN pattern built here. Help centers and product search mix AND, OR, NOT, and near asks to cut huge piles to the useful few, typically with phrase and proximity operators doing the precision work. News search shows headline clips with hit marks so readers see why a row matched, exactly the ts_headline role. Market call and investor note parsing counts theme hits across quarters and links bursts to price moves, pairing rank plus headline to separate dense signal from long-winded noise. Review and survey mining folds plural and tense forms to one base so counts stay whole across "loved", "loves", and "loving". Tools such as Elasticsearch and the PostgreSQL text engine share this vector plus inverted index design — learn it once here and the commercial dashboards read as familiar dialects.
