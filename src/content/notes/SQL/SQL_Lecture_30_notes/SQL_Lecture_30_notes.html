30.1 What Partitioning Is and Why It Matters

30.1.1 Core Idea in Plain Words

A partition (one slice of a large logical table, stored as its own physical table) lets PostgreSQL store a huge table as a set of related physical tables while you keep querying one logical name. You take one master table and break it into smaller chunks that stay linked to each other. Each chunk holds a meaningful slice, for example all office products in one slice and all house products in another slice. The slices are designed so they are easy to manage on their own.

Think of a very big pie cut into smaller, meaningful pieces so that when you want the best piece you know exactly where it is. The plate is the master table name you query; each slice is a partition holding only its share. The picture captures the whole design goal: do not scan everything when you only need one slice. Where the analogy breaks: unlike pie slices you eat once, partitions stay linked and the engine can re-combine any subset on demand.

A single table with 60 million product rows cannot be scanned end to end for every ad hoc filter such as product name starting with A. Partitioning gives each filter a chance to touch only the matching slice. Administrative work gets the same win: one slice can be vacuumed, reindexed, backed up, or dropped while the rest stay online, and cold slices can live on cheaper storage while hot slices stay on fast disks.

Partitioning in this lecture is horizontal partitioning: entire rows go to exactly one slice based on a partition key (the column whose values decide which slice holds each row) plus a partitioning function (the rule applied to the key, such as a date range, a value list, or a hash). Every slice shares the same columns and types; the data subsets never overlap.

A partitioned table is a virtual routing layer. The master name holds the definition and the routing rules; the slices hold the rows and carry their own physical indexes. Users query the master name exactly as before, and the optimizer decides which slices to visit.

30.1.2 How the Engine Uses Partitions

When a table is partitioned well, the query optimizer scans only the data needed to satisfy a given condition instead of scanning all contents of the large table. If your condition points at one category table, the engine reads only that table. This skipping step is called partition pruning (checking the query filter against slice bounds and dropping every slice that cannot hold a match). If you ask for everything with no condition, it still has to visit every slice and combine the results with an Append step, so the design only pays off when queries filter on the partition key.

A surprise for newcomers: the master table itself holds no rows. You run SELECT against the master name and you get rows back, yet SELECT ... FROM ONLY master returns zero rows. The rows live in the partitions. The master name is a routing layer that plans which slice to hit based on your criteria. ONLY is the diagnostic keyword that restricts a query to the named table alone, skipping all linked slices, so SELECT * FROM ONLY employees_range proving empty is how you confirm the router holds nothing.

Run this filter against a 60-million-row products table:

SELECT * FROM products WHERE product_name LIKE 'A%';

With no partition, that filter scans 60 million records. With a good partition design on category, it scans only the slice that can hold A names. Final answer: one slice scanned instead of 60 million rows. Sense-check: if the filter does not match the partition key, for example filtering by price on a category-partitioned table, every slice is still visited and no time is saved.

The same routing applies to writes. An INSERT through the master name is routed to the one slice whose bound accepts the new row; an UPDATE that changes the key value moves the row between slices; a DELETE through the master removes the row from whichever slice holds it.

30.1.3 When Partitioning Pays

Partitioning is a performance feature for very large tables. It shines when the size of the table exceeds the size of physical memory available to PostgreSQL, or more simply once full scans, index builds, vacuum runs, statistics refreshes, or backups stop fitting comfortably in maintenance windows — typically past a few million rows. Small tables with six rows or a few thousand rows do not need it; the extra planning cost buys nothing. Tables that keep growing toward tens of millions of rows should be split early, with attention to how data arrives and how it will be queried.

PostgreSQL version 12 added many improvements in this area, including better handling around integrity and partition management. The design rule stays the same across versions: define a good partition key and good bounds, and the optimizer will exclude partitions that cannot affect what you read or write.

Scope: partitioning pays when queries filter on the partition key and slices are sized so one slice fits the working set. It does not pay for tiny tables, for queries that never mention the key, or for designs with hundreds of near-empty slices, where planning overhead wipes out the savings.

How other systems differ on this same idea, in one place: MySQL uses the same manual range, list, and hash designs with its own PARTITION BY RANGE (yearweek(sale_date)) style syntax and a spillover MAXVALUE slice, so the mental model transfers directly. Snowflake needs no manual slices at all: it breaks tables automatically into small micro-partitions (roughly 50 to 500 MB each) with min-max metadata per slice, and pruning happens silently behind the same WHERE clause. Databricks Delta Lake sits in between with manual PARTITIONED BY on write plus automatic file-skipping and liquid clustering that plays the same role as pruning. The rest of this lecture uses the PostgreSQL declarative form, which is the one you must write by hand.

Exam note: expect questions that ask why a full scan of 60 million rows is wasteful and how partitioning avoids it by pruning to one slice. Answer with three parts: the master holds zero rows, the WHERE clause on the partition key selects the slice, and a bare SELECT * with no filter still fans out to every slice.

30.2 Table Inheritance Foundation

30.2.1 Parent and Child in Plain Words

An inheritance link (a child table that picks up all columns of a parent table) is the older PostgreSQL mechanism that partitioning builds on. In object-oriented terms, a subclass inherits properties of a parent class. In PostgreSQL, a table inherits columns from its parent table. Modern declarative partitioning (PARTITION BY ...) replaced this manual style in version 10, but the lecture walks it first because every partitioned master behaves like a parent: reads against the parent combine parent plus child rows, and writes against the parent reach into the matching child storage.

Picture a company form template (the parent) photocopied to every branch office (the children). Each branch copy starts with the same fields, and head office can collect all branches by asking for the template name. Where the picture breaks: unlike photocopies, the database children stay live-linked, so a query on the parent name automatically pulls in child rows unless you write ONLY.

The demonstration uses two tables. The parent is called master with three columns: pk as integer primary key, tag as text, and pattern as integer. The child is called master_child and it inherits from master without re-listing columns.

CREATE TABLE master (
  pk INTEGER PRIMARY KEY,
  tag TEXT,
  pattern INTEGER
);

CREATE TABLE master_child () INHERITS (master);

In the graphical browser, the parent shows an arrow pointing right and the child shows an arrow pointing left. The child lists the same columns pk, tag, pattern. That visual cue tells you an inheritance link exists.

30.2.2 Constraints Are Not Inherited Automatically

Columns are inherited, but constraints are not copied in the same step. Right after creation, the parent has a primary key and the child shows no primary key under its constraints. You must add it by hand so the two shapes match exactly:

ALTER TABLE master_child ADD CONSTRAINT master_pk PRIMARY KEY (pk);

After a refresh, both tables show the same primary key mapping. This step matters because later partition work assumes parent and slice share the same shape and the same uniqueness rules.

Scope: in legacy inheritance you must replicate keys, checks, and indexes on every child by hand and add routing CHECK constraints yourself; the engine will not stop a wrong-slice row. In declarative partitioning (sections 30.4 onward) indexes created on the master propagate automatically, but unique keys must still include the partition key column.

A common beginner trap is assuming a CHECK (pattern BETWEEN 0 AND 100) on the parent protects the child. It does not under inheritance: each child enforces only its own constraints, so a legacy partition design needs the bound repeated on every child plus constraint exclusion enabled before the planner can skip slices.

30.2.3 Seeing Inheritance From the Terminal

From psql connected to the learning database as user postgres, you can inspect the link:

\d master
\D+ master

The output lists table structure plus a line such as number of child tables: 1, and names master_child as the child. The access method shows as heap. When many tables exist, this terminal view is faster than clicking through the browser tree. \d master shows columns, indexes, and the child list; the + variant adds size and description detail. For declarative tables the equivalent check is \d+ employees_range, which instead lists the partition key and the attached slice names.

30.2.4 Worked Examples With Insert Update and Delete

Insert one row into the parent and one row into the child:

INSERT INTO master (pk, tag, pattern) VALUES (1, 'Apple pen', 0);
INSERT INTO master_child (pk, tag, pattern) VALUES (2, 'pen pencil', 0);

SELECT * FROM master;
SELECT * FROM master_child;
SELECT * FROM ONLY master;
SELECT * FROM ONLY master_child;

Trace each read step by step. After the two inserts the physical stores hold: parent {1}, child {2}. SELECT * FROM master_child returns one row (pk = 2). SELECT * FROM master returns two rows (pk = 1 plus pk = 2 pulled up from the child). SELECT * FROM ONLY master returns one row, only the row physically stored in the parent. ONLY is a diagnostic aid: it shows what a single table holds without pulling in linked rows. Sense-check: master-through reads equal parent-only rows plus all child rows.

Update through the parent name:

UPDATE master SET tag = 'monitor' WHERE pk = 2;

The row with pk = 2 lives in the child, yet updating via the parent name changes it in the child. Reading the parent shows pen plus monitor. Reading the child shows the updated monitor row. The operation touches only the child storage; the parent storage is unchanged.

Delete through the parent name:

DELETE FROM master WHERE pk = 2;

The child row disappears. The parent shows one row left (pk = 1). The child shows zero rows. ONLY confirms the same split.

The takeaway: operations issued against the parent propagate to the matching child, and reads against the parent combine parent plus child rows. Partitioning uses exactly this behavior, with added rules that route each row to the right slice.

30.2.5 Dropping Tables With Dependents

A plain drop fails while a dependent exists:

DROP TABLE master;
-- cannot drop table master because other objects depend on it
-- table master_child depends on table master

You can drop the child first, or use cascade:

DROP TABLE master CASCADE;

Cascade removes the parent and all child tables and their data in one shot, with no per-table confirmation. On a production server always list dependents first (\d master), drop or detach the child explicitly, and reserve CASCADE for throwaway practice databases.

A parent read fans out to every child; an ONLY read stays local; parent writes land in the matching child store. Declarative partitioning keeps this exact fan-out idea and adds automatic key-based routing, which is why every later section insists on writing through the master name.

30.3 Three Partition Types at a Glance

30.3.1 Range List and Hash

PostgreSQL offers three partition methods: range, list, and hash. Later sections work each one with full syntax, but the high-level split helps you pick:

  • Range partition — the table is split by ranges on a key column or set of columns, with no overlap between ranges assigned to different partitions. Dates are the most frequent use. You might split by year, with one slice holding 2020-01-01 through 2020-12-31 and the next holding 2019-01-01 through 2019-12-31. Bounds are half-open (FROM inclusive, TO exclusive), so the year-2000 slice is FROM ('2000-01-01') TO ('2001-01-01').
  • List partition — the table is split by explicitly listing which key values belong in each partition. A country table with a country code column might have one slice for US, one for UK, and one for JP. One slice may hold several values (for example all of UK, DE, IT, FR, ES in one EU bucket), and any key type supporting equality comparison works.
  • Hash partition — the table is split by modulus and remainder on a key, spreading rows across many slices when no single column gives a clean logical split. For three buckets you declare modulus 3 with remainders 0, 1, and 2; the engine hashes the key and drops each row into its remainder bucket.

Pick by asking one question: what do users filter on? Dates they range over point to range; a short known value list they test with = points to list; no clean business split but a table too big to keep whole points to hash for even spreading.

Comparison across systems, kept to what changes your choice: PostgreSQL and MySQL both offer all three manual methods with near-identical thinking, differing only in DDL spelling (MySQL writes PARTITION BY RANGE (yearweek(sale_date)) with VALUES LESS THAN, PostgreSQL writes PARTITION BY RANGE (birth_date) with FOR VALUES FROM ... TO ...). MySQL range gets a built-in MAXVALUE catch-all while MySQL list has none, which is why the lecture adds an explicit DEFAULT slice for PostgreSQL list designs. Snowflake and Databricks need no method choice from you for mechanics: Snowflake micro-partitions and Delta Lake file-skipping prune on any filter column automatically, so the range-versus-list-versus-hash decision there is about file layout and clustering, not about writing slice DDL.

Match three workloads to methods. A sales table queried with WHERE sale_date BETWEEN '2020-01-01' AND '2020-01-31' wants range on sale_date (one monthly slice scanned). A users table queried with WHERE country_code = 'US' wants list on country_code (one country slice scanned). A log table with no repeating filter column but 500 million rows wants hash on id into 8 buckets (each physical table roughly one-eighth the size). Sense-check: a hash design never helps a country filter, and a list design never helps a date-range filter.

Range for ordered spans (usually dates), list for known enumerable values, hash for even spreading with no business boundary. The rest of the lecture builds each one from CREATE TABLE ... PARTITION BY through plans, so learn this chooser first and the syntax second.

30.4 Partition by Range

30.4.1 Core Idea and Design Choices

A range partition (a split where each slice owns a FROM value up to but not including a TO value, with no overlap) fits dates best. You can build daily slices with 365 partitions, yearly slices, monthly slices, or multi-level splits such as year then month then day. Daily splits are possible but not recommended for most teams because they create many slices. A flat monthly design often runs faster than a deep year-month-day hierarchy, though a multi-level design can reduce planning time in some shapes. Match the grain to your queries: if users ask by year, partition by year; if they ask by month, partition by month.

Picture a filing cabinet with one drawer per year. A request for March 2001 opens only the 2001 drawer. The drawer labels must tile the timeline with no gaps and no overlaps, or a letter falls behind the cabinet (insert error) or fits two drawers (ambiguous routing, rejected at DDL time).

Values must not overlap between ranges. For dates, the upper bound is exclusive, so always add one extra day. For year 2000, use FROM ('2000-01-01') TO ('2001-01-01'), never TO ('2000-12-31'). A row dated 2000-12-31 then fits, while 2001-01-01 starts the next slice at FROM ('2001-01-01') TO ('2002-01-01'). The TO ('2000-12-31') form silently orphans New Year's Eve rows, which is the single most repeated range bug in this lecture.

Scope: range needs an ordered key (dates, timestamps, numbers) and queries that filter with =, BETWEEN, <, or > on that key. Equality on an unrelated column gets no pruning. Keep slice counts in the tens, not hundreds: 365 daily slices add planning and catalog cost that a 12-slice monthly design avoids.

30.4.2 Creating the Master Table

The master table is called employees_range with an id as bigserial for millions of rows, birth_date as date not null, and country_code as varchar(2) not null. The extra clause PARTITION BY RANGE names the key:

CREATE TABLE employees_range (
  id BIGSERIAL,
  birth_date DATE NOT NULL,
  country_code VARCHAR(2) NOT NULL
) PARTITION BY RANGE (birth_date);

No primary key or index is added yet; indexes get their own treatment later. In the browser, the new table shows a partition icon after the index node. Plain tables such as customers show no such icon. That icon is a quick way to tell a partitioned table apart.

SELECT * FROM employees_range returns no rows at first. SELECT * FROM ONLY employees_range also returns no rows. MySQL readers note the spelling difference only: the same weekly design there reads PARTITION BY RANGE (yearweek(sale_date)) with PARTITION s1 VALUES LESS THAN (202002) slices, versus PostgreSQL FOR VALUES FROM ... TO .... Snowflake and Databricks users write no slice DDL at all for this step.

30.4.3 Creating Yearly Slices

Each slice attaches to the master with PARTITION OF plus FOR VALUES FROM ... TO ...:

CREATE TABLE employees_range_2000 PARTITION OF employees_range
  FOR VALUES FROM ('2000-01-01') TO ('2001-01-01)');

CREATE TABLE employees_range_2001 PARTITION OF employees_range
  FOR VALUES FROM ('2001-01-01') TO ('2002-01-01');

Note the first statement as demonstrated carries an extra closing parenthesis; the working form closes each string literal once, as in the second statement. Keep the master name as a prefix plus the slice label, such as _2000 and _2001, so a long list stays readable. Each slice shows the same columns id, birth_date, country_code. After refresh, the master lists one partition, then two partitions.

Overlapping bounds are rejected at creation time, but gaps are allowed and fail later at insert time with no partition of relation ... found for row. Always tile ranges edge to edge (TO of one equals FROM of the next) or add a default slice to catch strays.

30.4.4 Worked Examples With Insert Update and Delete

Insert through the master name only, never directly into the slice:

INSERT INTO employees_range (birth_date, country_code) VALUES
  ('2000-01-01', 'US'),
  ('2000-01-02', 'US'),
  ('2000-12-15', 'US'),
  ('2001-03-10', 'US');

Trace the routing. SELECT * FROM employees_range shows four rows. SELECT * FROM ONLY employees_range shows zero rows, proving the master stores nothing and the engine moved each row to its slice. SELECT * FROM employees_range_2000 shows three rows (the two January plus the December date, all below the exclusive 2001-01-01 bound). SELECT * FROM employees_range_2001 shows one row (March 2001). Sense-check: master-visible rows always equal the sum across slices, 3 + 1 = 4.

Update through the master name and the row can move slices:

UPDATE employees_range SET birth_date = '2001-10-10' WHERE id = 1;

The master still shows four rows, with the first now dated in 2001. The 2000 slice drops from three rows to two. The 2001 slice grows from one row to two. ONLY queries confirm the new counts. This cross-slice move (row migration) only works when written through the master; writing directly into employees_range_2000 with a 2001 date is rejected by that slice's check constraint.

Delete through the master name:

DELETE FROM employees_range WHERE id = 1;

The master drops to three rows. The 2000 slice holds one row in this walkthrough state and the 2001 slice holds one row after the earlier move plus delete sequence. The exact counts depend on order, but the pattern is stable: deletes issued on the master remove the row from whichever slice holds it.

Exam note: expect to explain why inserts, updates, and deletes should target the master name so routing stays correct. One line: only the master knows all bounds, so only master-issued writes can route, migrate, or prune correctly.

30.4.5 Reading the Plan

Without a filter, the plan must visit every slice:

SELECT * FROM employees_range;

The graphical Explain with F7 shows scans of employees_range_2000 plus employees_range_2001 combined with Append. That is the same cost as an unpartitioned table and defeats the purpose. With 100 million rows across many slices, a bare SELECT * is expensive.

With a filter on the key, the plan prunes to one slice:

SELECT * FROM employees_range WHERE birth_date = '2000-01-02';

Explain shows a direct scan of employees_range_2000 only. No other slice is touched. Final answer: one slice scanned instead of two. That single-slice access is the whole payoff of range design, and the same pruning idea appears in every engine: PostgreSQL EXPLAIN dropping slices, MySQL EXPLAIN PARTITIONS listing one slice, Snowflake skipping micro-partitions via min-max metadata.

Visual to carry: picture the plan tree going from a wide fan (one branch per slice under Append) to a single narrow branch when the WHERE birth_date = ... filter is added. The axes are slices versus rows scanned; the landmark is the Append node collapsing to one child; the takeaway is that the filter, not the table size, controls the cost.

30.5 Partition by List

30.5.1 Core Idea and When It Fits

A list partition (a split where you explicitly list which key values live in each slice) fits columns with known, enumerable values that support equality comparison. Country codes such as US, UK, DE, IT, FR, ES, JP are a textbook case. Month names from January to December are another. Any data type that allows equality comparison can serve as the key, and composite keys with more than one column are allowed.

Picture labeled mailboxes, one per country or one per region. A letter addressed US drops into the US box; a letter for an unlisted country has nowhere to go until you add a catch-all box (the default partition in section 30.7).

Use list when you know the values up front and users filter on them in the WHERE clause. If the business logic says most queries filter by country code, partition by country code. Range-filtered queries (BETWEEN, <) on this column gain nothing; equality filters (=, IN) gain everything.

30.5.2 Creating the Master Table

The master is called employees_list with id bigserial, birth_date date not null, and country_code varchar(2) not null, partitioned by list on country code:

CREATE TABLE employees_list (
  id BIGSERIAL,
  birth_date DATE NOT NULL,
  country_code VARCHAR(2) NOT NULL
) PARTITION BY LIST (country_code);

After refresh, the browser shows the partition icon with zero slices. A plain table such as customers shows no partition node. That contrast confirms the new table is partitioned. The MySQL spelling of the same idea is PARTITION BY LIST COLUMNS (geo_region_cd) with PARTITION europe VALUES IN ('EUR_E','EUR_W'); PostgreSQL folds the attach into PARTITION OF ... FOR VALUES IN (...) instead.

30.5.3 Creating Slices With Single and Multiple Values

One slice holds a single value:

CREATE TABLE employees_list_us PARTITION OF employees_list
  FOR VALUES IN ('US');

Any row with country code US lands in employees_list_us. Keep the value in the slice name for fast visual scanning.

One slice can hold many values, for example all Europe codes in one EU slice:

CREATE TABLE employees_list_eu PARTITION OF employees_list
  FOR VALUES IN ('UK', 'DE', 'IT', 'FR', 'ES');

Any row with UK, DE, IT, FR, or ES lands in employees_list_eu. This grouping is handy when one region grows fast and may later need sub-slices (split EU into per-country slices or sub-partition by hash, as section 30.8 does). No primary key or index is defined yet; those come later. After refresh, the master lists two slices, US and EU.

Scope: each distinct value may belong to exactly one slice; listing the same value twice is rejected. Values are matched exactly, so 'us' does not land in a 'US' slice unless the data is cleaned first. Any unlisted value (JP, SP, a typo) errors until a default slice exists.

30.5.4 Worked Examples With Insert Update and Delete

Insert through the master name:

INSERT INTO employees_list (id, birth_date, country_code) VALUES
  (1, '2000-01-01', 'US'),
  (2, '2000-02-01', 'US'),
  (3, '2001-05-10', 'UK'),
  (4, '2001-06-12', 'DK');

Trace the routing as walked in the lecture. Here DK stands in for Denmark and routes to the EU slice in this walkthrough because the EU slice is treated as the Europe bucket. SELECT * FROM employees_list shows four rows. SELECT * FROM employees_list_us shows two US rows. SELECT * FROM employees_list_eu shows two rows (UK plus Denmark). SELECT * FROM ONLY employees_list shows zero rows, proving the master is a router, not a store. Sense-check: 2 + 2 = 4 across slices.

Note for careful readers: the DDL above lists only UK, DE, IT, FR, ES in the EU slice, so a literal DK insert would fail with a partition-missing error until DK is added to the EU list or a default slice exists (section 30.7). The lecture treats DK as covered by the Europe bucket for the walkthrough; in your own schema, add the value explicitly first.

Update through the master name and the row moves slices:

UPDATE employees_list SET country_code = 'US' WHERE id = 4;

The Denmark row with id = 4 becomes US. The master still shows four rows, now with three US codes and one UK code. The US slice grows from two rows to three. The EU slice shrinks from two rows to one. Always run such changes on the master name. Editing a slice directly breaks the routing idea because the definition lives on the master; worse, the slice's own check constraint rejects the out-of-range value.

Delete through the master name:

DELETE FROM employees_list WHERE id = 2;

The id = 2 US row disappears. The master shows three rows. The US slice drops from three rows to two. The EU slice still shows one row. Insert, update, and delete all filter by the list definition and place each row in its slice.

30.5.5 Reading the Plan

Without a filter, the plan visits every slice:

SELECT * FROM employees_list;

Explain shows scans of the EU slice plus the US slice plus combining steps. Because no WHERE clause guides the optimizer, it cannot prune, so it scans all partitions just like an unpartitioned table.

With a filter on the key, the plan prunes:

SELECT * FROM employees_list WHERE country_code = 'US';
SELECT * FROM employees_list WHERE country_code = 'UK';

The first prunes to employees_list_us; the second prunes to employees_list_eu. The graphical plan shows a sequential scan limited to that one slice. EXPLAIN SELECT ... in text form shows the same split: bare selects scan US plus EU plus default when present, while filtered selects scan only the matching slice. With millions of rows split into ten to forty slices, pruning turns a huge scan into a small slice read. Final answer: filtered queries touch one slice; unfiltered queries touch all of them.

Exam note: never use bare SELECT * from a partitioned master in a performance answer; always add a WHERE clause on the partition key. One line: no key filter means no pruning even when the pruning switch is on.

30.6 Partition by Hash

30.6.1 Core Idea and When It Fits

A hash partition (a split by modulus M and remainder N for each slice) spreads rows into many smaller, roughly even buckets when no column gives a clean logical split. If you cannot find a field that users filter on and that divides the data in a meaningful way, hash lets you shrink each physical table without imposing a business meaning on the boundary.

Picture dealing cards to three players round-robin by a shuffled deck order (the hash), not by suit. Each player ends with about the same pile, but asking for "all hearts" still means checking every pile. That is hash partitioning: even piles, no business meaning per pile.

The rule is simple: pick how many slices you want as the modulus, then number remainders from zero upward. For three slices, use modulus 3 with remainders 0, 1, 2. The engine hashes the key and assigns each new row to the matching remainder bucket. Hash works best when the key column has many distinct values (ids, customer keys); with only two or three distinct values the buckets skew.

Use hash to cut table size by spreading rows, not to answer business filters such as country or year. If users filter by country code, list is a better match than hash. MySQL expresses the same idea as PARTITION BY HASH (cust_id) PARTITIONS 4 and spreads 16 test rows roughly 4-5-3-4 across buckets; PostgreSQL spells out each bucket with MODULUS and REMAINDER but the even-spread result is the same.

30.6.2 Creating the Master and Three Buckets

The master is called employees_hash with the same three columns, partitioned by hash on id:

CREATE TABLE employees_hash (
  id BIGSERIAL,
  birth_date DATE NOT NULL,
  country_code VARCHAR(2) NOT NULL
) PARTITION BY HASH (id);

The browser shows the partition icon. Then create three buckets with the same modulus and distinct remainders:

CREATE TABLE employees_hash_1 PARTITION OF employees_hash
  FOR VALUES WITH (MODULUS 3, REMAINDER 0);

CREATE TABLE employees_hash_2 PARTITION OF employees_hash
  FOR VALUES WITH (MODULUS 3, REMAINDER 1);

CREATE TABLE employees_hash_3 PARTITION OF employees_hash
  FOR VALUES WITH (MODULUS 3, REMAINDER 2);

Names such as _1, _2, _3 carry no business meaning here; they only label bucket one, two, and three. Each bucket shows no constraint yet. SELECT from the master and from each bucket returns no rows before loading.

Scope: every bucket sharing one modulus must cover every remainder exactly once (0, 1, 2 for modulus 3). A missing remainder silently funnels those rows into an error at insert time; a duplicated remainder is rejected at DDL time. Buckets cannot be added one at a time later without re-hashing: growing from 3 to 4 buckets redistributes nearly every row.

30.6.3 Worked Examples With Insert Update and Delete

Insert through the master name:

INSERT INTO employees_hash (id, birth_date, country_code) VALUES
  (1, '2000-01-01', 'US'),
  (2, '2000-02-01', 'UK'),
  (3, '2001-05-10', 'UK');

SELECT * FROM employees_hash shows three rows. Each bucket shows about one row. SELECT * FROM ONLY employees_hash shows zero rows. Bucket labels do not encode the id; an id of 3 does not have to live in bucket 3. The engine spreads rows roughly evenly based on the hash of id, not on the digits you see. Sense-check: with three rows and three buckets the even outcome is 1 + 1 + 1, and larger loads converge toward one-third each as long as id values are distinct.

Update through the master name:

UPDATE employees_hash SET country_code = 'US' WHERE id = 3;

The master shows the change. Only the bucket that holds id = 3 is affected; other buckets keep their rows unchanged. The engine goes straight to where the key lives instead of scanning every bucket. Note this stays in-bucket because country_code is not the hash key; changing id itself would migrate the row to a different bucket.

Delete through the master name:

DELETE FROM employees_hash WHERE id = 2;

The master drops to two rows. The bucket that held id = 2 becomes empty. The other two buckets keep one row each.

30.6.4 Reading the Plan and Key Discipline

Without a filter, the plan scans all buckets:

SELECT * FROM employees_hash;

Explain shows sequential scans of all three hash tables combined. That matches an unpartitioned cost because no partition key guides the choice.

With a filter on the hash key, the plan prunes:

SELECT * FROM employees_hash WHERE id = 1;

Explain touches only the bucket that holds that hash, for example employees_hash_3 in the demo. With a filter on a non-key column, pruning fails:

SELECT * FROM employees_hash WHERE country_code = 'US';

The engine does not know how country code maps to hash buckets, so it scans hash 1 plus hash 2 plus hash 3 and then applies the country filter. That full scan shows why design and query shape must match: a hash on id helps id filters, while country filters want a list design on country code. From personal preference shared in the lesson, list with known values ranks first for clarity, range for dates ranks next, and hash ranks last but stays powerful for even spreading.

Hash spreads rows evenly across buckets but prunes only on the hashed key. Memorize the chooser: filter by id goes to hash on id; filter by country goes to list; filter by date goes to range. A hash design queried without its key is a full fan-out every time.

30.7 Default Partition

30.7.1 Core Idea in Plain Words

A default partition (a catch-all slice that receives every row matching no other slice) prevents insert failures when new values appear. Without it, inserting a value with no matching slice raises no partition of relation ... found for row, naming the failing key such as country code JP. Exactly one default slice is allowed per master, and it also catches range gaps and out-of-span dates, not just unlisted list values.

Picture the mailroom catch-all tray for letters with unknown postcodes. Without the tray every unknown letter bounces; with it, the room keeps running while you watch which codes pile up and deserve their own box.

MySQL comparison worth one line: MySQL range designs get a built-in VALUES LESS THAN (MAXVALUE) spillover but MySQL list designs get none, so new values error the same way; the PostgreSQL DEFAULT slice is the portable fix for both range and list masters. Snowflake and Databricks never raise this error because slices are automatic.

30.7.2 Worked Example With Japan Rows

Start from employees_list with US and EU slices only. This insert has no home:

INSERT INTO employees_list (id, birth_date, country_code)
VALUES (10, '2001-01-01', 'JP');
-- no partition of relation employees_list found for row
-- partition key of failing row contains country_code JP

Read the error literally: relation employees_list owns no slice whose bound contains JP. Adding one slice per country would create hundreds of tiny tables, many nearly empty. The cleaner fix is one default slice:

CREATE TABLE employees_list_default PARTITION OF employees_list DEFAULT;

No FOR VALUES list is needed. Any value absent from US and EU lands here. Keep default in the name because the browser does not badge which slice is the catch-all. After refresh the master shows three slices: US, EU, and default. Re-running the Japan insert now succeeds. SELECT * FROM employees_list shows the new row at the end. SELECT * FROM employees_list_us shows only US rows. SELECT * FROM employees_list_eu shows only Europe rows. SELECT * FROM employees_list_default shows the Japan row. Adding another uncovered code such as Sri Lanka also lands in default, giving two rows there. Sense-check: master total equals US plus EU plus default.

Watch default growth the way you watch a catch-all tray. If one code repeats often inside default, that repetition signals it is time to promote that code to its own slice: create the dedicated slice, move or re-route those rows, and the default shrinks back to true strays. A default slice holding half the table means the design missed a first-class value.

A default slice disables some fast path operations: adding a new slice later must scan the default to relocate any rows that now belong to the newcomer, and bulk detach flows slow down the same way. Keep the default small and promote hot values promptly.

Exam note: always plan a default slice when using list or range so users never see a partition-missing error. Memorize CREATE TABLE ... PARTITION OF parent DEFAULT; with no FOR VALUES clause, plus the promotion rule: repeated values graduate out of default into their own slice.

30.8 Multi-Level Partitioning

30.8.1 Core Idea and Caution

A sub-partition (a partition under a partition) lets one slice act as a parent for finer slices. You might hold US rows in one top slice and split a fast-growing EU slice into EU_1, EU_2, and finer buckets. PostgreSQL allows mixing methods, for example list on top and hash below, or range on top and range below for year-then-month splits.

Picture the filing cabinet again, but the EU drawer now contains its own dividers. A query for one UK customer opens the cabinet, then the EU drawer, then one divider. Each added level narrows the search but adds a label the planner must read.

Caution with ranges: it is easy to create a large number of tiny or empty sub-slices. Each extra slice adds entries to system tables and adds time and memory to planning and execution, which can slow queries. When that happens, widen the interval from days to months, quarters, half-years, or years, or pick a method that creates fewer slices. Naming matters even more here; plan names like master, _US, _EU, _EU_1 before you build. The book's composite example shows the same explosion concretely: 6 range partitions times 4 hash sub-partitions equals 24 physical tables for one logical name, which is why flat monthly designs often beat deep year-month-day trees.

Scope: sub-partition only the hot branch. If US holds a trickle and EU holds the flood, divide EU and leave US flat. Splitting every branch symmetrically multiplies empty slices and planning cost for no pruning gain.

30.8.2 Worked Example With List on Top and Hash Below

Build a fresh master called employees_master with the same three columns, partitioned by list on country code:

CREATE TABLE employees_master (
  id BIGSERIAL,
  birth_date DATE NOT NULL,
  country_code VARCHAR(2) NOT NULL
) PARTITION BY LIST (country_code);

The browser properties confirm partitioning by list on country code.

Create the US top slice as a plain slice:

CREATE TABLE employees_master_us PARTITION OF employees_master
  FOR VALUES IN ('US');

Create the EU top slice as a partitioned parent in one step, holding UK, IT, FR, ES values and sub-partitioned by hash on id:

CREATE TABLE employees_master_eu PARTITION OF employees_master
  FOR VALUES IN ('UK', 'IT', 'FR', 'ES')
  PARTITION BY HASH (id);

The EU table properties now show a partition tab with hash on id, while the US table shows no further partition tab. That contrast tells you EU is both a slice and a parent.

Create three hash buckets under EU:

CREATE TABLE employees_master_eu_1 PARTITION OF employees_master_eu
  FOR VALUES WITH (MODULUS 3, REMAINDER 0);

CREATE TABLE employees_master_eu_2 PARTITION OF employees_master_eu
  FOR VALUES WITH (MODULUS 3, REMAINDER 1);

CREATE TABLE employees_master_eu_3 PARTITION OF employees_master_eu
  FOR VALUES WITH (MODULUS 3, REMAINDER 2);

The master properties list US plus EU, and the EU properties list its three buckets. Insert through the top master name:

INSERT INTO employees_master (id, birth_date, country_code) VALUES
  (1, '2000-01-01', 'US'),
  (2, '2000-02-01', 'US'),
  (3, '2001-05-10', 'UK'),
  (4, '2001-06-12', 'UK');

SELECT * FROM employees_master shows four rows. SELECT * FROM ONLY employees_master shows zero rows because the top master is only a router. SELECT * FROM employees_master_us shows two US rows. SELECT * FROM employees_master_eu shows zero rows with ONLY semantics because EU is now a router too; its rows live one level down. Its buckets show one row plus one row plus zero rows in this run, matching the two UK rows spread by hash. Sense-check: 2 (US) + 1 + 1 + 0 (EU branch) = 4. You can drop from the same tree, but take care on live data.

MySQL names this same idea composite partitioning (PARTITION BY RANGE ... SUBPARTITION BY HASH), where querying PARTITION (s3) reads four sub-slices and querying PARTITION (s3_h3) reads one. The mechanics differ in spelling; the lesson is shared: prune top-down, and only the branch matching every filter level stays open.

30.9 Attaching and Detaching Partitions

30.9.1 Attaching a New Slice

Suppose Singapore with code SP must join employees_list, which currently holds EU plus US. Build and attach in one CREATE step by naming the parent and the new value:

CREATE TABLE employees_list_sp PARTITION OF employees_list
  FOR VALUES IN ('SP');

Picture adding a new labeled mailbox to the wall and telling the sorter its rule in the same motion. From that moment every SP letter routes itself; no existing mail moves.

Keep the value in the name so the slice purpose is plain. After refresh the master shows three slices including SP. Then load through the master:

INSERT INTO employees_list (id, birth_date, country_code)
VALUES (10, '2020-01-01', 'SP');

SELECT * FROM employees_list;
SELECT * FROM employees_list_us;
SELECT * FROM employees_list_eu;
SELECT * FROM employees_list_sp;

The master shows the new SP row at the end. The US slice shows only US. The EU slice shows only Europe such as UK. The new SP slice shows the Singapore row just added. Attach plus insert keeps routing intact because the definition lives with the parent. The two-step alternative, creating a standalone table then running ALTER TABLE ... ATTACH PARTITION ... FOR VALUES IN ('SP'), scans the table to validate every row first, so the one-step CREATE ... PARTITION OF is cheaper for empty newcomers. Final state: three slices, SP holding one row. Sense-check with ONLY on each slice if counts look off.

The MySQL equivalent of growing a design is ALTER TABLE sales REORGANIZE PARTITION s999 INTO (...) for ranges or REORGANIZE PARTITION asia INTO (...) for lists; PostgreSQL instead attaches a fresh slice with no reorganization of neighbors, which is why pre-creating future range slices is cheap here.

30.9.2 Detaching a Slice

To remove a slice from routing without dropping its stored rows from the database, detach it:

ALTER TABLE employees_list DETACH PARTITION employees_list_sp;

After refresh the master shows two slices again. The detached table remains as a standalone table holding its rows, queryable by its own name but invisible through the master. That makes detach the safe retention and archive move: detach last year's slice, back it up or drop it on its own schedule, and the live master never locks the hot slices. Re-attach later with ALTER TABLE ... ATTACH PARTITION ... if the data returns, paying one validation scan of that slice.

Detaching is instant metadata surgery, but readers with open transactions may still see the old shape until they commit. Run attach and detach off-peak, confirm slice counts with ONLY queries before and after, and never detach the slice holding live writable keys without redirecting those writes first.

Attach with CREATE TABLE ... PARTITION OF ...; detach with ALTER TABLE ... DETACH PARTITION .... Attach adds future capacity, detach parks history, and neither move touches the rows in the surviving slices.

30.10 Changing Range Bounds Safely

30.10.1 Core Idea in Plain Words

A bound change (widening or narrowing the FROM to TO interval that a range slice owns) is needed when the first design leaves a gap. Version 10 onward supports partitioning, but split and merge helpers are missing, so the safe pattern is detach, change bounds, then attach again inside one transaction block. The transaction holds an access-exclusive lock that blocks a second session from adding a conflicting range or inserting a clashing row mid-move.

Picture repainting parking-bay lines while cars keep arriving. You cone off the bay (detach), repaint wider lines (new bounds), reopen it (attach), all under one supervisor's whistle (the transaction) so nobody parks on wet paint.

30.10.2 Worked Example With a Gap From 100 to 200

Build a small master t1 with two integer columns a and b, partitioned by range on a:

CREATE TABLE t1 (a INTEGER, b INTEGER) PARTITION BY RANGE (a);

CREATE TABLE t1_p1 PARTITION OF t1 FOR VALUES FROM (0) TO (100);
CREATE TABLE t1_p2 PARTITION OF t1 FOR VALUES FROM (200) TO (300);

The gap from 100 to 200 is deliberate. Loading inside a slice works:

INSERT INTO t1 (a, b) VALUES (1, 1);
SELECT * FROM t1;
SELECT * FROM t1_p1;
SELECT * FROM t1_p2;
SELECT * FROM ONLY t1;

t1 shows one row (1, 1), t1_p1 shows it, t1_p2 shows none, and ONLY t1 shows none. Loading inside the gap fails:

INSERT INTO t1 (a, b) VALUES (150, 150);
-- no partition of relation t1 found for row

Final answer: rows 0-99 route to p1, rows 200-299 route to p2, and 150 has no home. The error names the relation and the failing key, which is your cue to widen a bound or add the missing slice. Sense-check: bounds are half-open, so 100 already belongs to the gap, not to p1.

30.10.3 Safe Detach Alter and Attach in a Transaction

Widen t1_p1 from 0-100 to 0-200 so 150 has a home. Do all three steps between BEGIN and COMMIT so the table stays guarded while bounds move:

BEGIN;
ALTER TABLE t1 DETACH PARTITION t1_p1;
ALTER TABLE t1 ATTACH PARTITION t1_p1 FOR VALUES FROM (0) TO (200);
COMMIT;

Detaching alone removes the slice from routing but leaves its stored table in the database. Attaching again checks every row in that slice against the new constraint, which means a full scan of that slice; on a huge slice that scan costs time, so schedule bound moves off-peak. If the block hits an error, the session reports the current transaction as aborted, so run ROLLBACK and retry the BEGIN ... COMMIT block cleanly. After commit, properties show 0 to 200 plus 200 to 300, and the earlier failing insert of 150 now succeeds.

Never widen past your neighbor: TO (250) here would overlap p2's FROM (200) and the attach is rejected. Widen exactly to the neighbor's FROM, and keep the half-open rule in mind so 200 still belongs to p2, not p1.

Exam note: state the three steps in order — detach, alter bounds, attach — wrapped in a transaction. Add the cost line: attach revalidates with a full slice scan, and any error aborts the block, so ROLLBACK and retry cleanly.

30.11 Indexes on Partitioned Tables

30.11.1 Core Idea in Plain Words

An index on a partitioned master (one CREATE INDEX on the parent name) automatically builds the same index on every attached slice. There is no single physical index that spans all slices; each slice gets its own matching index. Plan for that storage and build time on large masters. In the book's vocabulary these are local indexes (one per slice, useful when queries name the partition key) as opposed to global indexes (one structure spanning all slices, useful for non-key lookups); PostgreSQL declarative partitioning builds local ones.

Picture ordering one stamp for the company and the print shop automatically cutting a matching stamp for every branch. There is still no master stamp that covers all branches at once; each branch stamps its own mail with its own copy.

A second rule shapes every unique index: a primary key or any unique index must include the column named in PARTITION BY. A unique on id alone is rejected when the master is partitioned by list on country code. The reason is physical: each slice enforces uniqueness only inside itself, so without the slice discriminator in the key, two slices could each hold id = 7 and no single check would catch the clash.

30.11.2 Worked Example With a Rejected and Then Accepted Index

Start from employees_list with no indexes on master or slices. This attempt fails:

CREATE UNIQUE INDEX id_u ON employees_list (id);
-- unique constraint on table employees_list lacks column country_code
-- which is part of the partition key

Read the error as the rule statement: the key lacks country_code, the partition key. The fix adds the partition key as a second column:

CREATE UNIQUE INDEX employees_list_id_country_code_u
  ON employees_list (id, country_code);

After refresh, the master shows the new unique index on id, country_code. Each slice shows its own copy with the same two columns. Queries that filter on that pair now benefit in every slice. Final state: one logical unique index, N physical copies, enforced per slice but safe globally because the key carries the slice value. Sense-check: inserting (7, 'US') and (7, 'UK') is legal (different slices, different full keys), while inserting (7, 'US') twice is rejected inside the US slice.

Why the extra column is required: each slice is an independent table, so uniqueness across the whole logical table can only be enforced when the key carries the slice discriminator. Without country code in the key, two slices could each hold the same id with no way to stop the clash.

Deleting the master index removes the copies too. Re-running the same CREATE UNIQUE INDEX brings them back. On a huge master, both build and drop take time, so avoid them during peak use. The same caution covers attaching a slice with missing indexes: creating on the parent normally propagates, but confirm every slice carries the set after each attach, or one branch silently runs unindexed.

Exam note: if asked to create a primary key or unique index on a partitioned table, always include the partition key column in the column list. Memorize the pair (id, country_code) and the one-line reason: per-slice enforcement needs the slice value inside the key.

30.12 Partition Pruning

30.12.1 Core Idea in Plain Words

Partition pruning (using the partition key to pick which slice to scan) is the switch that makes partitioning fast. When pruning is on and the query filters on the key, the engine reads only the matching slice. When pruning is off or the query has no key filter, the engine scans all slices and combines them. Older setups call the same behavior constraint exclusion; the modern enable_partition_pruning switch covers declarative tables the same way.

Check and flip the switch in the session:

SHOW enable_partition_pruning;
SET enable_partition_pruning = OFF;
SET enable_partition_pruning = ON;

Picture a receptionist who reads the department on each envelope and walks only to that floor. Switch pruning off and the same receptionist photocopies the letter to every floor and lets each floor throw its copy away. Same result, wildly different step count.

The demo starts with the value on, which is the production default. Keep it on everywhere except narrow debugging sessions where you want to prove pruning was responsible for a fast plan.

30.12.2 Worked Examples With the Switch On and Off

With pruning on, a bare read touches everything:

SELECT * FROM employees_list;

Explain with F7 shows scans of all slices combined with Append, because no WHERE clause tells the planner which slice can be skipped. This is the correct plan for the question asked, and also the proof that partitioning without key filters buys nothing.

With pruning on plus a key filter, the plan narrows:

SELECT * FROM employees_list WHERE country_code = 'US';

Explain connects straight to employees_list_us. The partition key identifies the slice to scan, so a ten-slice table reads roughly one-tenth the data. Turn pruning off and repeat the same filtered query:

SET enable_partition_pruning = OFF;
SELECT * FROM employees_list WHERE country_code = 'US';

Explain now scans all tables such as EU plus US and then filters, a pure sequential pass over every slice. Turn pruning back on and the same query prunes to US again. Final answer: same query, one slice with pruning on, all slices with pruning off. Sense-check by toggling the switch and re-running EXPLAIN without changing the query.

Two pruning killers beyond the switch: a filter on the wrong column (country filter on a hash-by-id table scans everything), and an unstable expression the planner cannot evaluate at plan time (a volatile function around the key hides the value, so keep key filters plain and put the key first among AND conditions). Snowflake micro-partition skipping and Delta Lake file skipping obey the same rule: a selective WHERE on a well-clustered column prunes files; a filter on an unrelated column reads everything.

Exam note: link pruning to the WHERE clause; no key filter means no pruning even when the switch is on. Memorize the toggle pair SET enable_partition_pruning = OFF / ON and the one-line diagnosis: filtered query still scanning all slices means the switch is off or the filter misses the key.

30.13 Choosing a Partition Key

30.13.1 Review Raw Data First

Picking the key is the most critical step, and it starts before any CREATE statement. Study raw history plus samples, not only what already sits in the database, because samples can hide formats such as numbers mixed with letters. Spreadsheet tools and pivot aids help review highs, lows, averages, date spans, numeric spans, and how values spread across days, weeks, months, and case variants. Note how the candidate table joins to other tables, since a key that helps one table but breaks common joins is a poor pick.

Treat key choice like choosing the chapter titles of a textbook before writing it. Good titles match how readers search; bad titles match only how the author filed drafts. The readers here are your queries, so their WHERE clauses vote on the titles.

Concretely, pull the raw feed files, not just the loaded table: check for mixed-case country codes (us versus US), free-text statuses with typos, dates stored as strings in two formats, and null keys that would need a default slice. A key candidate that needs heavy cleaning first is a weak candidate no matter how often queries mention it.

30.13.2 Review Queries and Rank Common Fields

List every query that touches the table: single-table selects, multi-table joins, procedures, subqueries, and common table expressions. Rank them from simple to advanced, then flip the view and weigh the advanced ones most because they carry more joins and more filter columns. An advanced nightly report joining orders to customers on date and region outvotes a trivial lookup by id.

Collect the filter columns from each query on paper first, then move them to a sheet. Count appearances: if order date, country code, and status keep showing up, those are starting candidates. Rank by count so the most-used columns rise to the top ten, then narrow to the top five after deeper checks. The lecture's pencil-first habit is deliberate: tallying by hand forces you to read each WHERE clause instead of skimming, and the sheet then preserves the ranking for the team review.

Scope: a column that appears often but only inside functions (WHERE year(order_date) = 2020, WHERE lower(status) = 'x') is a weaker candidate than a column tested directly, because wrapped filters prune poorly. Prefer keys your queries test directly with =, IN, or BETWEEN.

30.13.3 Check Ranges and Test Before Committing

For each top candidate, profile its span. For order date, find min and max to see the time window. For country code, list distinct values to see the slice count; a full ISO list near 300 codes means near 300 slices if you split per code, which may be too many. For each key value, count rows with GROUP BY to see whether daily, weekly, monthly, or yearly grain spreads evenly.

SELECT MIN(order_date), MAX(order_date) FROM orders;
SELECT DISTINCT country_code FROM orders;
SELECT order_date, COUNT(*) FROM orders GROUP BY order_date;
SELECT country_code, COUNT(*) FROM orders GROUP BY country_code;

Read the four probes as a decision table. Min-max sets the outer bounds (how many yearly slices the timeline needs). Distinct counts set the slice total (20 regions is comfortable, 300 raw codes is not, so group codes into regions or sub-partition). Grouped counts reveal skew: one country holding 80 percent of rows warns that its slice will outgrow the rest and needs sub-partitioning or a different key. Build the top two or three designs in a test environment and measure query speed before committing. Final answer: the key with selective filters, tileable bounds, and even spread wins. A filter such as WHERE order_date = ... votes for order date, while WHERE country_code = ... votes for country code.

The lesson favors starting on paper with a pencil, then moving tallies to a sheet for ranking and range checks. Join behavior gets the last vote: when two tables join, partitioning both on the join key unlocks partition-wise joins where matching slices join pairwise instead of one giant join, so a key shared with the biggest join partner beats an equally popular single-table filter.

30.14 Sizing Partitions

30.14.1 Measure Boundaries Uniques and Counts

Sizing asks how many slices and how big each slice should be. Run min and max on the candidate key to learn its outer bounds. Dates get min and max; numbers can add averages too. Run distinct counts to learn slice totals; distinct country codes tell you whether list means 20, 30, or 300 tables, and each table costs physical space. Run grouped counts to learn spread:

SELECT MIN(order_date), MAX(order_date) FROM orders;
SELECT DISTINCT country_code FROM orders;
SELECT order_date, COUNT(*) FROM orders GROUP BY order_date;
SELECT country_code, COUNT(*) FROM orders GROUP BY country_code;

Work the probes on a sample orders table. Suppose min-max returns 2015-01-01 to 2024-12-31 (ten years), distinct codes return 40 regions, and grouped counts show the top region holding half the rows while most hold slivers. The read: yearly slices give 10 tables, monthly slices give 120, and the skewed region needs grouping or sub-partitioning before it becomes one giant slice. Grouped counts show whether rows spread evenly by day, week, month, or year, and whether one country dwarfs the rest. Final answer: pick the grain whose busiest slice still fits maintenance windows and whose total count stays in the tens. Uneven spread warns you that one slice will outgrow the rest.

Keep the overhead rule beside these numbers: ten to twenty slices add little planning cost, while hundreds add a large cost in catalog entries, planner time, and memory. A 300-code raw list therefore wants region buckets (as the lecture's US and EU slices show) rather than one slice per code.

30.14.2 Plan for Growth

Estimate insert pace, then project two to five years forward with headroom. For example, turn daily insert counts into monthly totals using 28 to 30 business days, then add 5 to 15 percent growth for busier days. Create slices for that future span up front so the router never stalls. A concrete pass: 50,000 rows per day times 30 days is 1.5 million per month; plus 10 percent headroom is about 1.65 million per monthly slice; times 24 months of hot data sets the recent window, with older years kept coarse.

Dates allow flexible grain: keep eight cold years in two or three coarse slices while splitting the hot last two years by month, or group three months per slice as quarters or half-years. Cold history is rarely filtered finely, so coarse slices cost nothing at query time and save hundreds of catalog entries. A table with only 1,000 rows does not qualify for partitioning, while one with millions of rows does; the projection tells you when the line will be crossed, so re-run these probes yearly and split the grain finer only when a slice outgrows its window.

Pre-creating future slices is cheap, but pre-creating hundreds of daily slices years ahead is not: empty slices still cost planning time on every query. Create the next few periods plus a default catch-all, and roll forward on a schedule instead of building the whole decade on day one.

30.15 Why Partitioning Pays Off

30.15.1 Faster Reads and Writes

Partitioning cuts the number of index blocks the engine must walk to find a row. Instead of a full sequential scan, a filtered query goes straight to the slice for year 2020 or the matching key value. In one analytics setup with terabytes of stock-market rows partitioned by symbol plus date on a yearly grain, that direct routing gave a large query speedup: a symbol-and-date filter opened one yearly symbol slice instead of scanning terabytes.

Picture a library that shelves books by year instead of one giant pile. A request for 2020 reviews walks to one bay; without the bays every request re-shelves the whole building in its head first.

Writes benefit too. Inserts, updates, and deletes route to one slice, so each operation touches less data and locks a smaller object. Bulk loads show the same effect: loading a 500 gigabyte file or 6 to 20 billion rows into a well-partitioned master ran much faster than loading into a single giant table, because each incoming row landed in its small target slice with a small index to maintain rather than one giant index to rebalance. Partition-wise joins add a further win when both join sides share the key: matching slices join pairwise in parallel instead of one monster join.

30.15.2 Cheaper Maintenance

Old ranges can be removed by dropping one slice instead of running DELETE ... WHERE ... over a giant table, which can run nearly forever while holding locks and generating dead rows. DROP or DETACH of a historical slice is a metadata move plus file cleanup; the mass DELETE is row-by-row work plus vacuum afterward. Historical pruning is cheaper for the same reason: detach last year's slice to archive storage and the live master shrinks instantly.

Storage handling also improves because updates and deletes keep old row versions around until cleanup; smaller slices mean less leftover work for vacuum, and one slice can be vacuumed or frozen while the rest serve traffic. Reindexing one slice takes a fraction of the time of rebuilding one giant index, since each slice carries its own smaller index. Backups and statistics refreshes parallelize the same way: refresh stats on the hot recent slices nightly while freezing statistics on sealed historical slices.

Three maintenance wins teams feel first: retention by dropping one old yearly or monthly slice instead of mass deletes, slice-sized reindex and vacuum windows that fit maintenance slots, and faster bulk ingest landing row-by-row into small slices. A seven-year financial retention rule becomes seven yearly drops, one per year, instead of seven years of DELETE ... WHERE date < ... statements.

Partitioning pays three times: reads prune to one slice, writes land in one small index, and history leaves by whole-slice drops. If a workload gets none of these three, it does not need partitioning yet.

30.16 Common Partitioning Mistakes

30.16.1 Settings Indexes Permissions and Query Shape

Keep this checklist on hand when a partitioned design feels slow. Each item is a full fan-out or a silent correctness gap, so walk the list top to bottom before redesigning the key:

  • Leave pruning and exclusion disabled. If constraint exclusion stays off (or enable_partition_pruning is off on modern versions), every query visits every slice, which is a sequential scan of the whole logical table. Keep the exclusion behavior enabled and confirm with SHOW enable_partition_pruning.
  • Miss indexes or constraints on slices. Replicate the same indexes and constraints from the master to every slice so each independent table enforces the same rules. Creating on the parent normally propagates, but check after every attach, because a standalone-then-attached table brings only the indexes it already has.
  • Mismatch permissions. If the master allows a query but a slice denies it, the query can fail in odd ways, including mid-plan permission errors that mention a slice name the user never typed. Grant the same rights on each slice as on the parent, and re-grant after every attach.
  • Skip the partition key in queries. Queries that never filter on the key get no pruning. Always include the key as a plain filter, and put it first when several AND or OR conditions appear, so the planner sees the slice choice right away. Parametric filters such as changing current-date functions optimize poorly for the same reason; keep the key filter simple and stable, computing volatile values once into a plain literal or parameter before the query.
  • Ignore slice count in overhead. Overhead grows with slice count. Ten to twenty slices add little planning cost, while hundreds add a large cost in plan time, memory, and catalog pressure. Size list, range, and hash counts with that trade-off in view, and widen the grain or group values when counts explode.

The costliest error is a well-built partitioned table queried without its key, which turns every read into a full fan-out. The second costliest is hundreds of near-empty slices: each query pays planning tax on all of them before reading any rows. Fix query shape first, slice count second, and settings last.

Debug in order: run SHOW enable_partition_pruning (expect on), run EXPLAIN on the slow query and count slice branches under Append (expect one for a keyed filter), compare slice index lists against the master (expect identical sets), and test the same filter with a literal in place of any function call (a speedup means the expression blocked pruning). Final answer for most slow-partition tickets: restore the key filter, not the hardware.

Exam Guidance Summary

  • Explain the 60-million-row products case: a bare filter scans everything, while a partitioned design scans one slice based on the WHERE clause on the partition key.
  • State when partitioning fits: very huge tables past a few million rows, tables larger than physical memory, not small tables with hundreds or thousands of rows.
  • Show ONLY to prove the master holds zero rows while slices hold the data: SELECT * FROM ONLY master returns the locally stored rows only.
  • For range, memorize the exclusive upper bound pattern FROM ('2000-01-01') TO ('2001-01-01') and the no-overlap, no-gap tiling rule.
  • For list, memorize PARTITION BY LIST (country_code) plus FOR VALUES IN (...) with single-value ('US') and multi-value ('UK', 'DE', 'IT', 'FR', 'ES') forms.
  • For hash, memorize PARTITION BY HASH (id) plus FOR VALUES WITH (MODULUS 3, REMAINDER 0/1/2) starting at remainder zero, and that pruning needs a filter on the hashed key.
  • For default, memorize PARTITION OF parent DEFAULT as the catch-all that avoids partition-missing errors, plus promoting hot values into their own slices.
  • For maintenance, memorize attach via CREATE TABLE ... PARTITION OF ..., detach via ALTER TABLE ... DETACH PARTITION ..., and bound changes via detach plus attach inside BEGIN ... COMMIT, noting the attach validation scan cost and the ROLLBACK retry on abort.
  • For indexes, memorize that unique indexes must include the partition key, for example (id, country_code), because each slice enforces uniqueness locally.
  • For pruning, link enable_partition_pruning on versus off to single-slice versus all-slice plans, and stress that a missing WHERE key means no pruning.
  • For key choice and sizing, list raw-data review, query ranking with advanced queries weighted most, range plus distinct plus grouped counts, and two-to-five-year growth headroom with the tens-of-slices budget.
  • For advantages, cite fewer index blocks, direct slice reads, partition-wise joins, fast drop-a-slice retention, cheaper vacuum and reindex, faster writes, and faster bulk loads up to billions of rows.
  • For mistakes, cite disabled exclusion or pruning, missing slice indexes, mismatched permissions, key-less queries, unstable parametric filters, and too many slices.

Key Industry Applications

  • 60-million-row products filtering by name prefix routes to one category slice instead of scanning all rows.
  • Time-series order and birth-date tables use yearly and monthly range slices for date-filtered reads, with cold years kept coarse and hot months split fine.
  • Country-code tables use list slices such as US and EU buckets for region-filtered reads, with new codes landing in a default catch-all until promoted.
  • Even spreading of key-less tables uses hash buckets with modulus and remainder for smaller physical sizes and parallel-friendly writes.
  • Terabyte-scale stock-market analytics partitioned by symbol plus yearly date for fast symbol-date reads and partition-wise joins.
  • Bulk ingest of 500 gigabyte files and 6-to-20-billion-row loads into partitioned masters for fast landing into small per-slice indexes.
  • Retention by dropping or detaching one old yearly or monthly slice instead of mass deletes, with cheaper vacuum, frozen statistics on sealed slices, and reindex per slice.
  • Cross-system carryover: MySQL weekly range and region list designs prune the same way, Snowflake micro-partitions skip files automatically behind identical WHERE clauses, and Delta Lake partition-plus-clustering layouts answer the same date and region filters without hand-built slice DDL.
