5.1 Types of Operators in SQL

5.1.1 What an Operator Is and Why It Matters

Hook: Every filter you write in this lecture answers one plain question — which rows stay and which rows go? Operators are the words and symbols that state that question so the database can run it row by row.

An operator — a special keyword or symbol used together with SQL clauses — lets us compare field values, pick a subset of rows, or do arithmetic. Three broad families appear through this whole lesson. A comparison operator tests one value against another. A logical operator joins or negates whole conditions. An arithmetic operator does simple math on numeric columns.

Think of it like three toolboxes on one bench. Comparison tools answer "is this equal, bigger, smaller?" Logical tools answer "must both parts hold, or is one enough, or is the value inside this list or range or pattern?" Arithmetic tools answer "what is the sum, difference, product, quotient, remainder?" Complex queries mix all three toolboxes at once.

To make the bench picture concrete, picture a movie catalog table with 53 rows. A comparison operator picks one shelf, for example \(movie\_length > 100\). A logical operator joins two shelf tests, for example \(movie\_lang = 'English'\ AND\ age\_certificate = '18'\). An arithmetic operator builds a new number first and then filters on it, for example \(revenues\_domestic - revenues\_international > 100\). The three toolboxes stay separate in meaning even when one WHERE line uses all three at once.

Recap: Operators fall into three families — comparison tests one value against another, logical joins or negates whole tests, arithmetic builds new numbers. The rest of this lecture walks the families one by one, then mixes them.

5.1.2 Comparison Operators

The comparison family uses six forms. Equal to is written \(=\). Greater than is \(>\). Less than is \(<\). Greater than or equal to is \(>=\) with the equal sign on the right side. Less than or equal to is \(<=\) with the equal sign on the right side. Not equal to has two spellings that mean the same thing, \(<>\) and \(!=\), and both are accepted for ordinary filtering.

The notation rule for the two-sided forms matters. The equal sign always sits on the right, as in \(>=\) and \(<=\). A reversed form with the equal sign on the left is a syntax error. That detail returns later when filtering movie length.

Formalize — the six comparison forms: each test takes a left value and a right value and returns true or false per row. \(col = value\) keeps exact matches. \(col > value\) and \(col < value\) keep one strict side. \(col >= value\) and \(col <= value\) keep the side plus the edge itself. \(col <> value\) and \(col != value\) keep everything except the stated value. The two not-equal spellings give the same rows in PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks. The \(<>\) form is the SQL standard; the \(!=\) form is a widely supported extra, so both pass in this lesson while \(<>\) stays the portable pick across database systems.

Cross-database note: the \(!=\) spelling works in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server, but a few strict standard-only systems accept only \(<>\). When you move queries between systems, prefer \(<>\) for not-equal so the line runs everywhere with no edit.

Pitfalls: writing \(=>\) or \(=<\) with the equal sign on the left fails in every system tested here — the parser reads it as a different token and raises a syntax error. Quoting the wrong side also fails: numbers stay bare (\(movie\_length > 100\)) while text and dates need single quotes (\(movie\_lang = 'English'\)). The quote rules get full treatment in 5.2 and 5.8.

5.1.3 Logical Operators

The logical family includes \(AND\), \(OR\), \(LIKE\), \(IN\), \(BETWEEN\), and related pattern, list, and range tests. \(ILIKE\) is the case-insensitive cousin of \(LIKE\). \(NOT\ IN\), \(NOT\ BETWEEN\), and \(IS\ NOT\ NULL\) negate the matching test. \(IS\ NULL\) checks for missing values. Each logical test returns true or false for every row, and only rows with true pass the filter.

A useful mental picture is that comparison works inside one condition, for example \(movie\_length > 100\), while logical work joins conditions or widens one condition into a list, range, or pattern, for example \(movie\_lang\ IN\ ('English', 'Chinese', 'Japanese')\).

Formalize — what each logical word does: \(AND\) keeps a row only when both sides hold. \(OR\) keeps a row when at least one side holds. \(IN\) is short for a chain of \(OR\) tests on one column. \(BETWEEN\) is short for a pair of \(AND\) tests forming one closed range. \(LIKE\) and \(ILIKE\) test text against a pattern with \(%\) and \(_\) wildcards. \(IS\ NULL\) tests for a missing marker, which plain \(=\) can never match. Each of these gets its own section later (5.3 through 5.15), so treat this list as a map rather than the full lesson.

Cross-database note: \(ILIKE\) runs as written in PostgreSQL, Snowflake, and Databricks. MySQL and SQL Server have no \(ILIKE\) keyword — there you write \(LOWER(first\_name)\ LIKE\ '%tim%'\) or use a case-insensitive collation to get the same rows. \(IS\ NULL\) and \(IS\ NOT\ NULL\) are standard and run unchanged in every system in this lesson.

Picture the logic as a row-by-row vote. For each of the 53 movie rows, every logical test votes true or false. WHERE keeps only the rows whose final vote is true. This vote picture explains why a filter can return zero rows with no error (section 5.3): every row simply voted false.

5.1.4 Arithmetic Operators

The arithmetic family is plain math. Addition is \(+\). Subtraction is \(-\). Division is \(/\). Multiplication is \(*\). Modulus, the remainder after division, is \(\%\). Modulus helps when grouping rows into buckets or testing divisibility, for example keeping every second row or checking even against odd identifiers.

Real-world: arithmetic plus filtering drives top-N money lists, such as sorting domestic revenue and keeping only the first ten rows.

Worked mini-example — modulus buckets: \(actor\_id\ \%\ 2 = 0\) keeps even identifiers (2, 4, 6) while \(actor\_id\ \%\ 2 = 1\) keeps odd ones (1, 3, 5). A delivery team can split a 200-row audit batch into two 100-row halves this way with no extra table. The final answer for identifier 7 is odd, since 7 divided by 2 leaves remainder 1. Sense-check: even plus odd covers all rows, so the two counts must add back to the full table count.

Cross-database note: \(+\), \(-\), \(*\), \(/\) run the same in PostgreSQL, MySQL, Snowflake, and Databricks. Two extras differ by system and are worth knowing: integer division of \(7 / 2\) gives 3 in PostgreSQL and MySQL integer math but 3.5 in some decimal contexts, so cast or multiply by 1.0 when you need the decimal part; the modulus sign \(%\) is standard in PostgreSQL and MySQL, while SQL Server also accepts it and Oracle buries it in a MOD function instead.

Scope: arithmetic operators build numbers — they do not filter by themselves. A bare \(revenues\_domestic - revenues\_international\) in a SELECT list only shows the new number. It becomes a filter only when paired with a comparison, as in \(revenues\_domestic - revenues\_international > 50\). Division by zero returns an error or NULL depending on the system, so guard money-per-minute math with a \(movie\_length > 0\) test.

Recap and bridge: comparison picks rows, logical joins the picks, arithmetic builds numbers to pick on. With the map in hand, the next section puts the WHERE clause to work on real text filters.

5.2 WHERE Clause Basics and Text Filtering

5.2.1 Role of WHERE

Hook: A SELECT without WHERE reads the whole shelf. How do you ask for only the English movies and get exactly 38 rows back?

The WHERE clause — the part of a SELECT statement that keeps only rows meeting stated conditions — limits results, filters rows by a stated test, and teams with comparison, logical, and arithmetic operators. The base shape is \(SELECT\ column\_list\ FROM\ table\_name\ WHERE\ condition\). The condition runs row by row against the table named after FROM.

A good habit taught here is to build step by step. Run \(SELECT\ *\ FROM\ movies\) first to see all 53 rows. Add one condition. Run again. Add the next condition. Run again. Small steps make faults easy to spot.

SELECT * FROM movies;
SELECT * FROM movies WHERE movie_lang = 'English';

Formalize — the WHERE contract: FROM names the table, WHERE states one true-or-false test per row, SELECT picks which columns of the kept rows to show. The test may use any operator family from 5.1. Rows voting true stay; rows voting false or unknown drop out. Unknown arises with NULL (full story in 5.14), which is why \(movie\_lang = 'English'\) drops both non-English rows and rows with no language value at all.

Cross-database note: the WHERE shape above runs unchanged in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. Quoting differs at the edges: single quotes for text are standard everywhere, while double quotes mean identifiers in PostgreSQL but also accept text in MySQL default mode — a portability trap covered in 5.2.2.

5.2.2 Single-Condition Text Filter

Text in a condition must sit inside single quotes. The column \(movie\_lang\), a text column holding values such as English, Japanese, and Chinese, shows the rule.

The working form is \(movie\_lang = 'English'\). It returns 38 rows, every English-language movie in the table. The same shape with \(movie\_lang = 'Japanese'\) returns every Japanese-language movie.

SELECT * FROM movies WHERE movie_lang = 'English';
SELECT * FROM movies WHERE movie_lang = 'Japanese';

Three failed trials teach the quote rule from the failure side. Writing \(movie\_lang = English\) with no quotes makes the system treat English as a column name and raises "column English does not exist". Writing \(movie\_lang = "English"\) with double quotes fails the same way, because double quotes also point at identifiers rather than text values in this setup. Writing the value with mismatched quoting around only part of the test fails as well. Only single quotes mark the value as text. Left side holds the column, right side holds quoted text, with \(=\) kindly joining them.

Formalize — the quote rule: a text literal (a fixed word typed into the query, such as \('English'\)) must sit in single quotes. An identifier (a table or column name, such as \(movie\_lang\)) must sit bare or in double quotes. No quotes around English means the parser hunts for a column named English and reports it missing. Double quotes around English mean the same hunt in PostgreSQL, Snowflake, and Databricks. Single quotes flip the reading from name to value, so \(movie\_lang = 'English'\) compares the column against the word English.

Cross-database extra: MySQL in its default mode accepts \("English"\) as text, so the double-quote trial that fails in PostgreSQL would pass in MySQL. Snowflake follows the standard (double quotes are identifiers) but also lets you set string handling per session. The portable habit that runs everywhere is single quotes for every text value, always — then the query never depends on which mode a server happens to use.

Describe the result shape as a picture: the 38-row English answer keeps the same columns as the full 53-row table, with every row showing English under \(movie\_lang\). No new columns appear and no rows change — WHERE only removes rows.

Scope: single quotes wrap text and dates, never column names. Writing \(movie\_lang = 'movie\_lang'\) compares the column against the fixed word movie_lang and returns zero rows. Writing \('movie\_lang' = 'English'\) compares two fixed words and returns either all rows or no rows. Keep columns bare on the left and literals quoted on the right.

5.2.3 Student Questions and Answers

Q: Why does English without quotes act like a column and raise "does not exist"? A: Without quotes the parser reads English as an identifier, so it looks for a column named English, fails to find it, and reports a missing column. Single quotes switch the reading from identifier to text value, so \(movie\_lang = 'English'\) compares the column against the word English.

Q: Do double quotes work for text? A: No, double quotes fail here the same way as no quotes. Use single quotes for text values such as \('English'\) and \('Japanese'\). The reason is the identifier rule above: in PostgreSQL, Snowflake, and Databricks, double quotes always point at object names. Learners moving between MySQL and PostgreSQL hit this most, since MySQL default mode is lenient about double quotes while PostgreSQL is strict.

5.2.4 Worked Examples

Example 1 — all English movies: Run \(SELECT\ *\ FROM\ movies\). Count 53 rows. Then run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\). Result is 38 rows. Every returned row shows English in \(movie\_lang\). Final count 38. Sense-check: 38 of 53 leaves 15 non-English rows, which matches the not-equal count in 5.8.

Example 2 — all Japanese movies: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'Japanese'\). Result holds only rows where \(movie\_lang\) is Japanese. Every row in the answer shows Japanese and no English or Chinese row slips in. Sense-check: English plus Japanese plus Chinese must add back to 53 when NULLs are absent.

Example 3 — failed quote trials: Run the no-quote form, see the missing-column error. Run the double-quote form, see the same error. Run the single-quote form, see 38 correct rows. The contrast locks in the rule. The three-step order matters: see the full table first, then the error, then the fix, so the error message attaches to its cause.

Pitfalls: the two most common early faults are forgetting quotes on text (\(movie\_lang = English\)) and borrowing double quotes from other languages (\(movie\_lang = "English"\)). A third fault is quoting the column itself (\( 'movie\_lang' = 'English'\)). All three return errors or zero rows, never a partial answer — so an empty answer on a text filter almost always means a quoting fault rather than missing data.

Exam note: quote handling for text is a classic early fault, so practice the three forms and their error messages until the single-quote form is automatic. Single quotes for text, bare columns on the left, and the step-by-step build (full table, one condition, run) form the safety net for every later section.

Recap and bridge: WHERE keeps rows whose test votes true, and text tests need single quotes. The next section adds a second test with AND and shows how the row count can only stay level or fall.

5.3 AND Operator for Multiple Conditions

5.3.1 Meaning of AND

Hook: 38 English movies is still a big shelf. How do you ask for English movies that also carry certificate 18 — and land on exactly 4 rows?

The AND operator — a logical join that keeps a row only when every joined condition is true — narrows results. Both sides must hold. The shape is \(condition\_1\ AND\ condition\_2\). With \(movie\_lang = 'English'\ AND\ age\_certificate = '18'\), a row must be English and carry certificate 18 at the same time.

SELECT * FROM movies
WHERE movie_lang = 'English' AND age_certificate = '18';

Note that \(age\_certificate\) here is stored as text, a character varying field, so its value also needs single quotes even though it looks numeric: \(age\_certificate = '18'\).

Formalize — AND as a two-vote test: each row takes two true-or-false votes, one per side. The row stays only on true plus true. True plus false drops. False plus true drops. False plus false drops. If either side is unknown (NULL), the row drops as well — there is no half-pass. This is why adding conditions with AND can only hold the count steady or push it down, never up.

Cross-database note: AND runs the same in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. What differs is the type rule behind \(age\_certificate = '18'\): PostgreSQL and Snowflake are strict about comparing text columns with quoted literals, while MySQL silently converts \('18' = 18\) and still matches. The portable habit is to quote exactly what the column stores — quoted \('18'\) for the character varying certificate column here, bare \(8\) for the integer \(director\_id\) column below.

Picture the AND gate from the lesson: a gate with two locks that both must open. Each condition is one lock. A row passes only when its own key opens both locks at once.

Scope: AND narrows within one row — it never pairs two different rows. \(movie\_lang = 'English'\ AND\ movie\_lang = 'Chinese'\) on one row asks for a single cell holding both words at once, so it returns zero rows. The either-or ask across rows needs OR (5.4) or IN (5.11).

5.3.2 Worked Examples

Example 1 — English movies with certificate 18: Start from \(SELECT\ *\ FROM\ movies\). Add \(WHERE\ movie\_lang = 'English'\) and confirm 38 rows. Extend to \(WHERE\ movie\_lang = 'English'\ AND\ age\_certificate = '18'\). Result drops to 4 rows. Each of the four shows English in the language column and 18 in the certificate column. Final count 4. Sense-check: 4 is below 38, as AND requires — a count above 38 here would signal a typo such as OR in place of AND.

Example 2 — Japanese movies with certificate 18: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'Japanese'\ AND\ age\_certificate = '18'\). Result is 2 rows. Both rows show Japanese plus 18, and no English row can slip in because the first lock blocks it. Final count 2.

Example 3 — English movies with a given director: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\ AND\ director\_id = 8\). Rows return for director 8. Change the test to \(director\_id = 10\) and no rows return, because no English movie in the data carries director 10. The empty result is correct behavior, not a broken query. It shows that AND can filter down to zero rows when the two demands never meet in one row. Note \(director\_id\) is integer, so \(8\) and \(10\) stay bare with no quotes — the mirror of the quoted \('18'\) certificate rule above.

Pitfalls: quoting the integer (\(director\_id = '8'\)) still runs here but teaches a weak habit that breaks on typed columns elsewhere; quoting the wrong side of the certificate (\(age\_certificate = 18\) bare) can miss or error depending on system strictness. A second trap is reading an empty AND answer as a broken query — check the data mix first (is there any English row by director 10 at all?) before rewriting the syntax.

5.3.3 Student Questions and Answers

Q: Why did the first single-condition run return 38 rows and the AND run only 4? A: The first test keeps every English movie. The AND test adds a second demand, certificate 18, so only rows meeting both demands stay. Four rows meet both. Each added AND lock can only remove rows, so the count path 53 to 38 to 4 shows the narrowing in action.

Exam note: when an AND query returns zero rows, check the data for that mix before assuming a syntax fault. The director 10 against English case is the model. Empty is a legal answer — it means no single row opened both locks.

Recap and bridge: AND narrows to the overlap of its tests. The next section flips to OR, which widens to the union instead.

5.4 OR Operator for Either-Or Choice

5.4.1 Meaning of OR

Hook: What if the shelf ask is "English or Chinese, either will do" — how does the count move the other way, from 38 up to 43?

The OR operator — a logical join that keeps a row when at least one joined condition is true — widens results. The shape is \(condition\_1\ OR\ condition\_2\). With \(movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\), English rows pass, Chinese rows pass, and all other languages drop out.

SELECT * FROM movies
WHERE movie_lang = 'English' OR movie_lang = 'Chinese';

Think of AND as a gate with two locks that both must open, and OR as a hall with two doors where either door lets the row through.

Formalize — OR as a one-vote-wins test: each row votes on both sides. True plus true stays (counted once, never twice). True plus false stays. False plus true stays. Only false plus false drops. This is why OR counts run at or above each single side: English alone gives 38, English-or-Chinese gives 43, so Chinese adds exactly 5 rows. The same-truth table appears in every database book because the logic is shared across systems.

Cross-database note: OR is standard and runs unchanged in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. Performance guidance is also shared: long OR chains on one column (\(a = 1\ OR\ a = 2\ OR\ a = 3\)) run the same rows as \(a\ IN\ (1, 2, 3)\) but read worse, so later sections replace them with IN (5.11).

Ask Join Count direction Lesson count
English and certificate 18 AND narrows to overlap 38 down to 4
English or Chinese OR widens to union 38 up to 43
English and Chinese (one row) AND on one column always empty 0

5.4.2 Worked Examples

Example 1 — English or Chinese movies: Run \(SELECT\ *\ FROM\ movies\) to see English, Japanese, and Chinese values under \(movie\_lang\). Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\). Result is 43 rows, a mix of English and Chinese only. Final count 43. Sense-check: 43 minus 38 gives 5 Chinese rows, and 53 minus 43 leaves 10 rows in other languages — both remainders are positive, so no language group went negative.

Example 2 — reading the mix with ORDER BY: Add \(ORDER\ BY\ movie\_lang\) in ascending order. Chinese rows sort first because C comes before E, then English rows follow. The sort makes the either-or mix easy to scan. The same ordering idea is used with \(ORDER\ BY\ movie\_lang\) after the AND-OR mixes later. Run it as \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\ ORDER\ BY\ movie\_lang\) and confirm the C-before-E grouping by eye.

Example 3 — OR against AND contrast: The pair \(movie\_lang = 'English'\ AND\ director\_id = 8\) narrows to the overlap. The pair \(movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\) widens to the union. Holding both shapes side by side helps fix which join the task needs. A quick self-test: if the wanted count sits below each single side, reach for AND; if it sits above, reach for OR.

Real-world: OR lists answer "any of these choices" tasks, such as pulling catalog rows in any of several languages or statuses in one pass. A storefront language picker (English, Chinese, Japanese) and an order-status board (shipped, delivered, returned) both map to one OR line rather than three separate queries merged by hand.

Pitfalls: repeating the column on every arm is required — \(movie\_lang = 'English'\ OR\ 'Chinese'\) is a syntax error because the second arm has no left side. A second trap is mixing AND and OR on one line without brackets; the count then follows precedence rules instead of reading order (full story in 5.5). Always bracket mixed lines.

Recap and bridge: OR widens to the union — one true vote is enough. The next section shows what breaks when AND and OR share one line with no brackets.

5.5 Combining AND and OR with Parentheses

5.5.1 The Core Problem

Hook: "English or Chinese movies with certificate 12" sounds like one ask — so why do three bracket-free spellings give 42, 12, and 11 rows?

Mixing AND and OR without brackets gives surprising row counts because AND binds tighter than OR. The intended task here is English or Chinese movies whose certificate is 12, written with the certificate test applied to the whole language union: \((movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese')\ AND\ age\_certificate = '12'\). Without brackets the system reads the line in its own order and the certificate test lands on only part of the union.

SELECT * FROM movies
WHERE (movie_lang = 'English' OR movie_lang = 'Chinese')
  AND age_certificate = '12'
ORDER BY movie_lang;

Formalize — precedence as arithmetic: AND binds first the way multiplication binds before addition. \(a\ OR\ b\ AND\ c\) always parses as \(a\ OR\ (b\ AND\ c)\), never as \((a\ OR\ b)\ AND\ c\). Brackets override the default the way they do in arithmetic: \((a\ OR\ b)\ AND\ c\) forces the union first, then trims by the certificate test. The rule is shared across PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server, so bracket habits transfer directly between systems.

Visual check: draw the wanted set as two language circles (English, Chinese) merged into one union bubble, then shade only the certificate-12 slice of that bubble. The bracket-free lines shade a different slice — one full circle plus a slice of the other — which is why stray PG and 15 rows leak in.

5.5.2 Worked Examples

Example 1 — English or Chinese alone: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\). Result is 43 rows. Add \(ORDER\ BY\ movie\_lang\) to group Chinese first, then English. Final count 43. This is the baseline union before any certificate test touches it.

Example 2 — certificate test with no brackets: Run \(WHERE\ movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\ AND\ age\_certificate = '12'\). Because AND goes first, this reads as English rows plus the subset of Chinese rows with certificate 12. Counts stay high and unwanted certificates such as PG and 15 still appear. One run shows 42 rows with mixed certificates, which proves the filter did not apply as intended. The bare English arm (38 rows) passes untouched, so the certificate test trims only the 5 Chinese rows.

Example 3 — swapping the order: Run \(WHERE\ movie\_lang = 'English'\ AND\ age\_certificate = '12'\ OR\ movie\_lang = 'Chinese'\). This reads as English rows with certificate 12 plus all Chinese rows. A run shows 12 rows but certificate 15 still leaks in through the bare Chinese arm, so the fault remains. Final count 12. The leak is the tell: any certificate value outside 12 in the answer proves one arm escaped the certificate test.

Example 4 — the bracketed form: Run \(WHERE\ (movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese')\ AND\ age\_certificate = '12'\ ORDER\ BY\ movie\_lang\). Result drops to 11 rows. Only Chinese and English appear, and every row shows certificate 12. Brackets force the OR union to finish first, then AND trims that union by certificate. Final count 11. Sense-check: 11 sits below both 42 and 12, as the fully trimmed set must.

The takeaway is direct: order of AND and OR changes output, and brackets state the intended order. Always bracket mixed AND-OR lines so later readers see the grouping at a glance.

Spelling Parsed as Rows Leak signal
English OR Chinese union baseline 43 none
English OR Chinese AND cert 12 English plus (Chinese with 12) 42 PG and 15 present
English AND cert 12 OR Chinese (English with 12) plus Chinese 12 15 present
(English OR Chinese) AND cert 12 union trimmed by 12 11 none, all rows show 12

5.5.3 Student Questions and Answers

Q: Why did certificate 12 still let PG and 15 rows through? A: Without brackets the certificate test binds only to the nearest AND arm. The bare OR arm has no certificate test, so its rows pass untouched. Brackets wrap the whole language union, so the certificate test trims every row in that union. Scanning the certificate column of the answer is the fastest check: any value outside 12 means the brackets sit wrong.

Exam note: mixed AND-OR without brackets is a favorite trap. Practice rewriting the same three lines with brackets in different places and predicting the count shift from 43 to 42 to 12 to 11. The AND-first rule (AND as multiplication, OR as addition) predicts each count before you run.

Recap and bridge: brackets state the intended grouping when AND meets OR. The next section fixes a different kind of position fault — where the whole WHERE clause is allowed to sit.

5.6 Clause Position and Logical Execution Order

5.6.1 WHERE Must Sit After FROM and Before ORDER BY

Hook: The same words in a different order can flip a query from 38 rows to a syntax error — which slot does WHERE actually own?

Clause order is fixed. FROM comes first, then WHERE, then SELECT projection in logical terms, then ORDER BY last. Two failed moves prove the slot.

The shape \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\) runs and returns English rows. Moving WHERE before FROM, as in \(SELECT\ *\ WHERE\ movie\_lang = 'English'\ FROM\ movies\), raises a syntax error near FROM. The system rejects WHERE before FROM.

SELECT * FROM movies WHERE movie_lang = 'English';

The shape \(SELECT\ *\ FROM\ movies\ WHERE\ age\_certificate = '15'\ ORDER\ BY\ movie\_lang\) runs. Moving WHERE after ORDER BY, with ORDER BY placed before the WHERE line, raises an error. WHERE works only before ORDER BY.

SELECT * FROM movies WHERE age_certificate = '15' ORDER BY movie_lang;

So the working pipeline is first FROM pulls the table, then WHERE filters rows such as \(movie\_lang = 'English'\), then SELECT keeps the columns, then ORDER BY sorts what is left. The same slot rule explains a later FETCH fault: FETCH must sit after ORDER BY because it acts like LIMIT at the end of the line, and placing FETCH before ORDER BY raises a syntax error at ORDER.

Formalize — written order against logical order: you type \(SELECT\) first, but the system reasons FROM first. FROM pulls the source rows. WHERE drops the rows that fail the test. SELECT trims the kept rows to the asked columns. ORDER BY sorts what remains. LIMIT, OFFSET, and FETCH cap or page that sorted remainder. Any clause typed outside its slot (WHERE before FROM, WHERE after ORDER BY, FETCH before ORDER BY) fails before any row is read.

Cross-database note: the FROM–WHERE–ORDER BY slot order is standard and identical in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. What differs is only the cap keyword at the end (LIMIT in PostgreSQL and MySQL, FETCH in standard SQL and Oracle, TOP in SQL Server), never the WHERE slot itself.

5.6.2 Logical Run Behind a Plain SELECT

Take \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang = 'English'\ ORDER\ BY\ movie\_lang\). Behind the run, the system first takes all rows from movies. Next it keeps only rows where \(movie\_lang = 'English'\). Next it projects the SELECT columns, here all columns. Last it sorts by \(movie\_lang\). Thinking in this FROM, WHERE, SELECT, ORDER BY order helps place each new clause in its legal slot.

Trace on four toy rows: input rows hold languages English, Chinese, English, Japanese. FROM pulls all four. WHERE \(movie\_lang = 'English'\) keeps rows 1 and 3, dropping 2 and 4. SELECT \(*\) keeps all columns of rows 1 and 3. ORDER BY \(movie\_lang\) leaves the two English rows in place (equal keys keep input order). Final answer 2 rows. Sense-check: the output count never exceeds the input count at any step.

Picture the pipeline as a packing line: FROM unloads the full crate (53 rows), WHERE tosses out the pieces that fail inspection (down to 38), SELECT repacks only the asked columns, ORDER BY lines the kept boxes up by label. Each station only sees what the station before it passed on.

Pitfalls: typing SELECT first tricks newcomers into thinking SELECT runs first — it does not. That is why SELECT aliases are invisible to WHERE (full story in 5.7) and why ORDER BY can sort by a SELECT alias while WHERE cannot. A second trap is placing LIMIT or FETCH before ORDER BY to "save work"; the parser rejects it, since capping happens after sorting by definition.

5.6.3 Student Questions and Answers

Q: Can WHERE go before FROM or after ORDER BY? A: No to both. WHERE before FROM fails near FROM. WHERE after ORDER BY fails as well. Keep FROM first, WHERE second, ORDER BY last. When the error pointer lands on FROM or ORDER, look one clause to the left — a misplaced WHERE is usually sitting there.

Recap and bridge: FROM pulls, WHERE filters, SELECT projects, ORDER BY sorts — in that logical order, always. The next section uses that order to explain why SELECT aliases stay invisible to WHERE.

5.7 Column Aliases and WHERE

5.7.1 The Alias Rule

Hook: The header says surname — so why does WHERE surname = 'Allen' answer "column surname does not exist"?

A column alias — a short rename made in the SELECT list with AS, such as \(last\_name\ AS\ surname\) — changes the display header but cannot be used inside WHERE at the same query level. WHERE runs logically before SELECT projection, so the alias does not yet exist when WHERE filters.

The actors table shows the rule. \(SELECT\ first\_name, last\_name\ FROM\ actors\) returns two columns. \(SELECT\ first\_name, last\_name\ AS\ surname\ FROM\ actors\) shows the second header as surname. Filtering with the true column works: \(SELECT\ first\_name, last\_name\ FROM\ actors\ WHERE\ last\_name = 'Allen'\) returns the matching row. Filtering with the alias fails: \(WHERE\ surname = 'Allen'\) raises "column surname does not exist". Restoring \(last\_name\) makes it work again.

SELECT first_name, last_name FROM actors WHERE last_name = 'Allen';
SELECT first_name, last_name AS surname FROM actors WHERE last_name = 'Allen';
-- fails: SELECT first_name, last_name AS surname FROM actors WHERE surname = 'Allen';

The path around the limit is a subquery, where the inner query first creates the alias and the outer query then filters on it. That shape is noted here and built in full in later work on subqueries.

SELECT first_name, surname FROM
  (SELECT first_name, last_name AS surname FROM actors) AS t
WHERE surname = 'Allen';

Formalize — why the alias is late: the logical order from 5.6 runs FROM, then WHERE, then SELECT. The alias \(surname\) is born in the SELECT step, one step after WHERE has already finished. At filter time only true stored columns such as \(last\_name\) exist. The subquery works around it by splitting the job into two levels: the inner level runs its own SELECT first and hands a finished \(surname\) column outward, so the outer WHERE sees it as a real input column.

Cross-database note: the alias rule is standard and holds in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. Two extras differ by system: MySQL and Snowflake allow ORDER BY to use the alias (sorting runs after SELECT), and some systems allow GROUP BY to use it while PostgreSQL does not. The exam-safe rule stays narrow — never use a SELECT alias in WHERE at the same level, in any system.

Scope: the ban covers only the same query level. Outer queries, ORDER BY, and later processing steps can all use the alias freely. Table aliases (FROM actors AS a) are different: they are born in FROM, so WHERE can use them at once, as in \(WHERE\ a.last\_name = 'Allen'\).

Worked example — surname alias rejected, true column works: Run \(SELECT\ first\_name, last\_name\ AS\ surname\ FROM\ actors\) and confirm the second header reads surname. Then run \(SELECT\ first\_name, last\_name\ FROM\ actors\ WHERE\ last\_name = 'Allen'\) and confirm the matching row returns. Then run the alias form with \(WHERE\ surname = 'Allen'\) and confirm it raises "column surname does not exist". Restore \(last\_name\) and the row returns again. Final lesson: headers display late, filters run early.

5.7.2 Student Questions and Answers

Q: If surname shows as the header, why does WHERE reject it? A: The header is made in SELECT, which runs logically after WHERE. At filter time only true column names such as \(last\_name\) exist. A subquery creates the alias first in its inner step, so an outer WHERE can then see it. The display you see belongs to the last step, not the step that filters.

Exam note: alias-in-WHERE is a short trap question. Remember the order FROM, WHERE, SELECT. Aliases belong to SELECT, so WHERE cannot see them. When a question shows a header name inside WHERE, the fix is either the true column or a subquery wrapper.

Recap and bridge: SELECT aliases are display names born too late for WHERE. The next section returns to plain comparisons — this time on numbers, dates, and alphabetically ordered text.

5.8 Comparison Operators on Numbers Dates and Text

5.8.1 Number Filters on Movie Length

Hook: 48 of 53 movies run longer than 100 minutes — which single line isolates them, and what happens when the equal sign slides to the wrong side?

Numeric columns take bare numbers with no quotes. The column \(movie\_length\), an integer, carries the demos. \(movie\_length > 100\) returns 48 rows, every movie longer than 100 minutes. Adding \(ORDER\ BY\ movie\_length\) ascending lines the values up from just above 100 upward, with values such as 102, 104, 127, and 168 easy to scan.

SELECT * FROM movies WHERE movie_length > 100 ORDER BY movie_length;

Variants follow the same shape. \(movie\_length >= 100\) adds the boundary and returns every row at 100 or above. \(movie\_length < 100\) returns only rows below 100, such as 99 and 98. \(movie\_length <= 100\) returns rows at or below 100.

The equal-sign placement rule matters here. \(movie\_length >= 100\) with the equal sign on the right runs. Flipping it so the equal sign sits on the left raises a syntax error. The fix is to restore \(>=\) and \(<=\) with the equal sign on the right.

Quoting numbers is tolerated but not needed. \(movie\_length > 100\) and \(movie\_length > '100'\) return the same 48 rows for plain integers. The cleaner style omits quotes for simple numeric compares and keeps quotes for text and dates. If a numeric-looking value ever contains spaces or odd marks, quotes become needed, but plain integers stay bare.

Formalize — number compare contract: an integer column (whole-number storage, such as \(movie\_length\)) compares against a bare numeric literal with no quotes. The six signs from 5.1 keep their plain math meaning, and \(>=\) plus \(<=\) include the edge row itself. Type-strict systems (PostgreSQL, Snowflake) convert a quoted \('100'\) for plain integers without complaint, but the habit to keep is bare numbers for numbers — it survives every later section on money math and range tests.

Pitfalls: \(=>\) and \(=<\) fail everywhere; only \(>=\) and \(<=\) run. A second trap is quoting when the number carries decimals — \(102.10\) must keep its point, since \('102'\) would drop the cents. Money columns in 5.12 show why the point matters.

Worked example — movie length above 100: Run \(SELECT\ *\ FROM\ movies\) and count 53 rows. Run \(movie\_length > 100\) and confirm 48 rows return with values such as 102, 104, 127, and 168 at the ordered head. Run \(movie\_length >= 100\) to add the boundary row, then \(movie\_length < 100\) to see only rows such as 99 and 98. Final counts 48 above, 5 at or below. Sense-check: the two sides must add back to 53.

5.8.2 Date Filters and Storage Shape

Dates need two things: knowledge of the stored shape and single quotes around the literal. Dates in the movies table follow year-month-day with dashes, \(YYYY-MM-DD\), for example \(1999-12-31\) for 31 December 1999 and \(2000-12-31\) for 31 December 2000. Month 01 means January, 02 means February, 08 August, 12 December.

The column \(release\_date\) carries the demos. First inspect with \(SELECT\ *\ FROM\ movies\) and \(ORDER\ BY\ release\_date\) ascending to see old rows such as 1939 and 1979 at the top and newer rows such as 2001 and 2003 lower down. Then filter for recent rows with \(release\_date > '1999-12-31'\). That test returns movies after 31 December 1999, with 2001 rows onward coming back. Tightening to \(release\_date > '2000-12-31'\) returns movies after 31 December 2000. In this data no 2000-year movie sits between the two cutoffs, so both cutoffs return the same set starting in 2001.

SELECT * FROM movies ORDER BY release_date;
SELECT * FROM movies WHERE release_date > '1999-12-31';
SELECT * FROM movies WHERE release_date > '2000-12-31';

Leaving quotes off a date breaks the test. Writing \(release\_date = 1999-12-31\) with no quotes makes the system read the literal as arithmetic on integers rather than as a date, so nothing matches. Wrapping the literal restores the date reading: \(release\_date > '1999-12-31'\). The rule is short: dates always take single quotes, and the literal must match the stored \(YYYY-MM-DD\) shape.

Formalize — why dates must be quoted: a date literal (a calendar value typed into the query) needs single quotes so the parser reads it as one value. Bare \(1999-12-31\) parses as \(1999\) minus \(12\) minus \(31\), which equals 1956 — a number, not a date — so the date-against-number compare matches nothing. Quoted \('1999-12-31'\) in \(YYYY-MM-DD\) shape parses as 31 December 1999 and compares date against date.

Cross-database extra: PostgreSQL, Snowflake, Databricks, and MySQL all read \('YYYY-MM-DD'\) dates, but each adds its own date helpers — MySQL accepts slashes and short forms more freely, Snowflake auto-detects several formats per session, Databricks leans on TO_DATE for odd shapes, and SQL Server prefers explicit CAST or CONVERT for safety. The portable exam habit is the full quoted \(YYYY-MM-DD\) form, which runs everywhere with no conversion call.

Picture the date line as a timeline: 1939 and 1979 sit far left, 1999-12-31 is a gate near the right end, and only the 2001-and-later dots pass the \(>\) gate. Moving the gate to 2000-12-31 changes nothing here because no dot sits between the two gates.

5.8.3 Text Ordered Alphabetically

Comparison signs also work on text, tested against letter order rather than size. \(movie\_lang > 'English'\) compares each language value against English in A-to-Z order and returns rows sorted after E. With \(ORDER\ BY\ movie\_lang\) the effect is plain: German with G, Japanese with J, Portuguese with P, Spanish with S, and Swedish follow English. \(movie\_lang < 'English'\) returns the other side, with Chinese, whose C comes before E, coming back. This is not a normal business filter, but it shows that text compares by alphabet using the same \(>\) and \(<\) signs.

Not-equal has two equal spellings. \(movie\_lang <> 'English'\) and \(movie\_lang != 'English'\) each return the same 15 rows, every movie except English. Adding \(ORDER\ BY\ movie\_lang\) groups Chinese, German, Japanese, and the rest while English stays out. Forgetting quotes repeats the old fault: \(movie\_lang > English\) with no quotes raises "column English does not exist", and adding single quotes fixes it.

SELECT * FROM movies WHERE movie_lang > 'English' ORDER BY movie_lang;
SELECT * FROM movies WHERE movie_lang <> 'English' ORDER BY movie_lang;
SELECT * FROM movies WHERE movie_lang != 'English' ORDER BY movie_lang;

Formalize — text ordering: text compares by collation order (plain A-to-Z in this lesson), letter by letter from the left. First letters decide unless tied; ties move to the second letter. Case matters: capital letters sort apart from small ones, so LIKE and ILIKE in 5.13 exist to control that split. Not-equal \(<>\) and \(!=\) return the complement of \(=\), which is why \(38 + 15 = 53\) adds back to the full table.

Cross-database note: A-to-Z order is nearly standard, but case handling differs — PostgreSQL sorts capitals before small letters by default, MySQL default collation mixes them case-insensitively, Snowflake follows session collation. The counts here transfer, but exact row order for mixed-case text can shift between systems unless ORDER BY names an explicit collation.

Scope: text \(>\) and \(<\) are teaching tools, not business filters — real language picks use \(=\) or IN (5.11). Case and trailing spaces can flip text compares silently, so production text filters pair the compare with explicit case handling (ILIKE or LOWER) from 5.13.

5.8.4 Student Questions and Answers

Q: Why does the date test need quotes while plain numbers do not? A: A bare date such as 1999-12-31 reads as numbers with minus signs, not as a calendar value. Quotes mark it as one date literal such as \('1999-12-31'\), so the compare runs date against date. Plain integers such as \(100\) already read as numbers, so \(movie\_length > 100\) needs no quotes.

Q: Why does text greater than English return German and Japanese? A: Text compares by A-to-Z order. G for German and J for Japanese sort after E for English, so \(movie\_lang > 'English'\) keeps them. C for Chinese sorts before E, so it returns under \(movie\_lang < 'English'\) instead. The first letter decides unless two values share it.

Recap and bridge: numbers stay bare, dates take quoted \(YYYY-MM-DD\), text compares A-to-Z with the same six signs. The next two sections cap and page the sorted answer with LIMIT, OFFSET, and FETCH.

5.9 LIMIT and OFFSET for Top N and Paging

5.9.1 LIMIT Shape and Purpose

Hook: Sorting 53 movies longest-first answers "which is longest?" — but how do you answer "which five are longest?" without reading all 53?

The LIMIT clause — a row cap written as \(LIMIT\ n\) where \(n\) is a plain count such as 5 or 10 — keeps only the first \(n\) rows of the sorted result and drops the rest. It trims server load and answers top-N tasks. The shape is \(SELECT\ column\_list\ FROM\ table\_name\ ORDER\ BY\ column\_name\ LIMIT\ n\), with ORDER BY optional but strongly advised so the "top" has a stated meaning.

SELECT * FROM movies ORDER BY movie_length DESC LIMIT 5;

Without LIMIT, \(SELECT\ *\ FROM\ movies\) returns all 53 rows. With \(ORDER\ BY\ movie\_name\ LIMIT\ 10\), the same alphabetic list stops after the first 10 rows. Changing the cap to 20 keeps the first 20. The cap always counts from the first row of the ordered set.

Formalize — LIMIT as a post-sort cut: ORDER BY fixes the row order first, then LIMIT keeps rows 1 through \(n\) and drops the rest. With no ORDER BY the "first \(n\)" means whatever order the storage returns, which can shift between runs — so the exam-safe shape always pairs LIMIT with an explicit ORDER BY. LIMIT runs last in the logical pipeline (after FROM, WHERE, SELECT, ORDER BY), which is why it can cap any filtered and sorted set from earlier sections.

Cross-database note: LIMIT runs as written in PostgreSQL, MySQL, Snowflake, and Databricks. SQL Server uses \(TOP\ 5\) instead of LIMIT, and Oracle plus DB2 use \(FETCH\ FIRST\ 5\ ROWS\ ONLY\) (full story in 5.10). Databricks accepts both LIMIT and FETCH, so LIMIT lines port freely between the systems in this lesson except SQL Server, where TOP is the rewrite.

Visual check: draw the sorted list as a vertical bar of 53 slots, longest (168) at top. LIMIT 5 draws a cut line under slot 5 — everything above stays, everything below drops. Changing to LIMIT 10 slides the cut line down five slots.

Scope: LIMIT caps rows, never columns — use the SELECT list for columns. LIMIT without ORDER BY is legal but means "any 5 rows", which suits sampling but never leaderboards. For pages past the head of the list, pair LIMIT with OFFSET (5.9.2, Example 5).

5.9.2 Worked Examples

Example 1 — five longest movies: Run \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ movie\_length\ DESC\). Without a cap all 53 rows return, longest first with values such as 168 and 165 at the top. Ascending is the default, so DESC is needed for biggest-first. Add \(LIMIT\ 5\). The five longest rows return and the rest drop. The lesson is to sort first, check the full order, then cap. Final answer 5 rows, headed by 168. Sense-check: every kept length must sit at or above every dropped length.

Example 2 — five oldest American directors: Inspect \(SELECT\ *\ FROM\ directors\). Sort births oldest-first with \(ORDER\ BY\ date\_of\_birth\) ascending, which is the default, so rows such as 1889 and 1905 lead. Add \(WHERE\ nationality = 'American'\) to keep only American directors while holding the birth sort. Add \(LIMIT\ 5\) to keep the five oldest. Flipping the sort to \(ORDER\ BY\ date\_of\_birth\ DESC\) with the same WHERE and LIMIT returns the five youngest instead, with years such as 1979, 1970, 1969, 1966, and 1963 leading. The pair shows how sort direction picks oldest against youngest while LIMIT picks how many. Build order taught here: filter, then sort, then cap.

Example 3 — ten youngest female actors: Run \(SELECT\ *\ FROM\ actors\) and note the \(gender\) column with F and M plus \(date\_of\_birth\). Filter with \(WHERE\ gender = 'F'\). Sort youngest-first with \(ORDER\ BY\ date\_of\_birth\ DESC\), because youngest means latest birth date. Check the lead rows, with dates such as 1995 onward at the top. Add \(LIMIT\ 10\) to keep the ten youngest. The step order filter, sort, cap keeps the build safe. Final answer 10 rows. Sense-check: the earliest birth in the answer must still sit later than every dropped female birth.

Example 4 — ten most and ten least domestic earners: Read \(SELECT\ *\ FROM\ movies\_revenues\) and note \(revenues\_domestic\). Sort biggest-first with \(ORDER\ BY\ revenues\_domestic\ DESC\ NULLS\ LAST\ LIMIT\ 10\). The \(NULLS\ LAST\) push matters because missing revenues would else sit at the top of a DESC sort. Leaders such as 659 and 461 then head the list. For the weak end, sort smallest-first with \(ORDER\ BY\ revenues\_domestic\ LIMIT\ 10\), ascending by default. Small values such as 0.3, 0.5, and 1.1 head that list. The same table, sort, and cap shape answers both ends. Final answers 10 rows each.

Cross-database extra on NULLS LAST: PostgreSQL, Snowflake, Oracle, and Databricks accept \(NULLS\ LAST\) as written. MySQL has no \(NULLS\ LAST\) keyword — there you write \(ORDER\ BY\ revenues\_domestic\ IS\ NULL,\ revenues\_domestic\ DESC\) to push missing values down. When porting the money-leader query to MySQL, that two-key sort is the rewrite.

Example 5 — paging with OFFSET: The OFFSET clause — a skip written as \(OFFSET\ m\) that drops the first \(m\) rows before LIMIT counts — pages past the head of the list. The shape is \(LIMIT\ n\ OFFSET\ m\). Take \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ movie\_id\). With \(LIMIT\ 5\) alone, identifiers 1, 2, 3, 4, 5 return. With \(LIMIT\ 5\ OFFSET\ 4\), the first four rows drop and identifiers 5, 6, 7, 8, 9 return. OFFSET counts rows skipped, not the identifier to start on: \(OFFSET\ 4\) skips four rows and starts on the fifth row in the ordered set, and \(OFFSET\ 5\) skips five rows and starts on the sixth. A money paging case does the same: \(SELECT\ *\ FROM\ movies\_revenues\ ORDER\ BY\ revenues\_domestic\ DESC\ NULLS\ LAST\ LIMIT\ 5\ OFFSET\ 5\) skips the top five earners and returns the next five, starting around revenue row 21 in the demo. Final identifier answer 5, 6, 7, 8, 9. Sense-check: LIMIT 5 still returns exactly 5 rows — OFFSET changes which five, never how many.

Real-world: LIMIT plus OFFSET pages catalog screens, leaderboards, and audit batches without pulling the full table each time. Page 1 is LIMIT 10 OFFSET 0, page 2 is LIMIT 10 OFFSET 10, page 3 is LIMIT 10 OFFSET 20 — the OFFSET climbs by the page size while LIMIT holds steady.

5.9.3 Student Questions and Answers

Q: Does OFFSET 4 start on identifier 4? A: No. OFFSET counts skipped rows in the ordered result. OFFSET 4 drops four rows and starts on the fifth row, so with \(ORDER\ BY\ movie\_id\) the returned identifiers are 5, 6, 7, 8, 9. Think "skip 4, keep the next 5" rather than "start at 4".

Q: Why add NULLS LAST on the revenue sort? A: Missing revenue values would else head a biggest-first sort and use up LIMIT slots. NULLS LAST pushes missing values to the bottom so true leaders such as 659 fill the kept rows. Without it the "top 10" answer can hold NULLs instead of money leaders.

Recap and bridge: ORDER BY sorts, LIMIT caps, OFFSET pages — always in that end-of-query order. The next section teaches FETCH, the standard-SQL twin of LIMIT.

5.10 FETCH as the Standard Form of LIMIT

5.10.1 Syntax and Defaults

Hook: LIMIT answers top-N in four words — what is the portable standard-SQL spelling that Oracle, DB2, and exam setters expect instead?

The FETCH clause — a standard-SQL row cap written after ORDER BY — matches LIMIT in effect and follows standard syntax more closely. The shape is \(OFFSET\ start\ \{ROW | ROWS\}\ FETCH\ \{FIRST | NEXT\}\ row\_count\ \{ROW | ROWS\}\ ONLY\). The start value must be zero or positive and defaults to zero. If the start sits past the end of the result, no rows return.

SELECT * FROM movies ORDER BY movie_length DESC FETCH FIRST 5 ROWS ONLY;

Small wording points help. \(FIRST\) and \(NEXT\) mean the same thing to the parser. \(ROW\) and \(ROWS\) mean the same thing as well. \(FIRST\) is the default, so a bare row count still reads as first rows. The clause must sit after ORDER BY at the end of the statement, in the same end slot where LIMIT sits.

Formalize — FETCH word by word: OFFSET \(start\) skips rows (default 0, must be zero or positive). \(FETCH\ FIRST\) or \(FETCH\ NEXT\) takes rows (identical meaning — FIRST suits page starts, NEXT suits continued pages). \(row\_count\) states how many. \(ROW\) or \(ROWS\) is grammar glue (singular for 1, plural otherwise, but both parse for any count). \(ONLY\) closes the clause. If the skip passes the end of the set, the answer is legally empty — the same empty-is-valid rule from 5.3.

Cross-database note: FETCH is the SQL standard path and runs in PostgreSQL, Oracle, DB2, Snowflake, and Databricks. MySQL (through version 8.0) has no FETCH support — LIMIT is the only path there. SQL Server uses a twin spelling \(OFFSET\ 5\ ROWS\ FETCH\ NEXT\ 5\ ROWS\ ONLY\) that requires an ORDER BY. For this lesson the portable rule is short: FETCH for standard-form asks, LIMIT for short-cap asks, TOP when writing for SQL Server.

System Top-5 spelling Paging spelling
PostgreSQL, Snowflake, Databricks LIMIT 5 or FETCH FIRST 5 ROWS ONLY LIMIT 5 OFFSET 5 or OFFSET 5 ROWS FETCH NEXT 5 ROWS ONLY
MySQL LIMIT 5 LIMIT 5 OFFSET 5
Oracle, DB2 FETCH FIRST 5 ROWS ONLY OFFSET 5 ROWS FETCH NEXT 5 ROWS ONLY
SQL Server TOP 5 OFFSET 5 ROWS FETCH NEXT 5 ROWS ONLY

5.10.2 Worked Examples

Example 1 — first row of movies: Run \(SELECT\ *\ FROM\ movies\). Add \(FETCH\ FIRST\ 1\ ROW\ ONLY\). One row returns. Changing the count to 5 as \(FETCH\ FIRST\ 5\ ROWS\ ONLY\) returns rows 1 through 5. Final counts 1 then 5. Sense-check: FETCH 1 returns exactly one row — the singular ROW matches the count.

Example 2 — five longest movies: Run \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ movie\_length\ DESC\). Placing \(FETCH\ FIRST\ 5\ ROWS\ ONLY\) before ORDER BY raises a syntax error near ORDER, which proves FETCH belongs last. Moving it after ORDER BY as \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ movie\_length\ DESC\ FETCH\ FIRST\ 5\ ROWS\ ONLY\) returns the five longest rows with 168 leading. Final answer 5 rows, same set as LIMIT 5 in 5.9. The failed-then-fixed order is the teaching point: the error pointer on ORDER means FETCH sits too early.

Example 3 — five oldest American directors: Use the directors table with \(WHERE\ nationality = 'American'\ ORDER\ BY\ date\_of\_birth\) ascending, then add \(FETCH\ FIRST\ 5\ ROWS\ ONLY\). Rows from 1889 onward return. Same five rows as the LIMIT form in 5.9 — only the cap keyword changed.

Example 4 — ten youngest female actors: Run \(SELECT\ *\ FROM\ actors\ WHERE\ gender = 'F'\ ORDER\ BY\ date\_of\_birth\ DESC\ FETCH\ FIRST\ 10\ ROWS\ ONLY\). Ten rows return with the latest birth dates first, such as 1995 and 1994 leading. Final answer 10 rows. Ascending would flip the answer to the ten oldest, so DESC carries the meaning here.

Example 5 — five long movies starting at the fifth row: Sort long-first with \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ movie\_length\ DESC\). The fifth row in that order is the pivot, with titles around Fifth Element and City of God used as markers in the demo. Add \(OFFSET\ 5\ ROWS\ FETCH\ FIRST\ 5\ ROWS\ ONLY\). The run skips to the fifth-row zone and returns the next five long movies. OFFSET may sit before or after FETCH in this form and still run, but keeping the end order ORDER BY, OFFSET, FETCH is the clearest habit. Final answer 5 rows starting past the head of the long-first list.

Pitfalls: FETCH before ORDER BY always fails — the error near ORDER is the signal to move FETCH last. A second trap is a negative OFFSET, which the parser rejects at once. A third is expecting FETCH in MySQL, where only LIMIT runs — check the target system before choosing the keyword.

5.10.3 Student Questions and Answers

Q: Can FETCH sit before ORDER BY? A: No. FETCH before ORDER BY raises a syntax error near ORDER. Keep ORDER BY first and FETCH last, as in \(ORDER\ BY\ movie\_length\ DESC\ FETCH\ FIRST\ 5\ ROWS\ ONLY\). The same slot rule from 5.6 applies: sort first, cap last.

Exam note: LIMIT and FETCH answer the same top-N need. If the task asks for standard form, reach for FETCH. If it asks for the short cap, reach for LIMIT. Pairs like "rewrite this LIMIT as FETCH" test only the keyword swap plus the ORDER BY-last slot.

Recap and bridge: FETCH equals LIMIT in meaning with standard-SQL wording. The next section replaces long OR chains with the compact IN list.

5.11 IN and NOT IN for List Checks

5.11.1 Meaning and Return Shape

Hook: Three languages need three OR arms today — what happens when the choice list grows to ten?

The IN operator — a list test written as \(value\ IN\ (list)\) — returns true when the tested value matches any entry in the list. The NOT IN operator — written as \(value\ NOT\ IN\ (list)\) — returns true only when the value matches none of the entries. The tested value may be a column such as \(movie\_lang\) or \(director\_id\). The list holds literal choices such as \('English', 'Chinese', 'Japanese'\) or \((13, 10)\). IN replaces long OR chains with one compact line.

SELECT * FROM movies
WHERE movie_lang IN ('English', 'Chinese', 'Japanese')
ORDER BY movie_lang;

Formalize — IN as folded OR: \(movie\_lang\ IN\ ('English', 'Chinese', 'Japanese')\) means exactly \(movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\ OR\ movie\_lang = 'Japanese'\). Each row checks its own value against every list entry and stays on the first match. \(NOT\ IN\) is the mirror: the row stays only when no entry matches. The rewrite runs the same rows in every system, which is why style guides prefer IN past two choices — one column name, one list, no repeated arms.

Cross-database note: IN and NOT IN are standard and run unchanged in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server. The NOT IN plus NULL trap is also shared: if the list holds a NULL, \(NOT\ IN\) matches nothing at all (because no value can prove itself different from unknown). Later NULL work in 5.14 explains the unknown logic behind that trap.

Picture IN as a guest list at a door: the row shows its \(movie\_lang\) badge, the checker scans the list, match means entry. NOT IN flips the door — listed badges are turned away and only unlisted ones pass.

5.11.2 Worked Examples

Example 1 — English, Chinese, and Japanese movies: The long form chains \(WHERE\ movie\_lang = 'English'\ OR\ movie\_lang = 'Chinese'\ OR\ movie\_lang = 'Japanese'\) and returns the wanted union. The compact form is \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_lang\ IN\ ('English', 'Chinese', 'Japanese')\ ORDER\ BY\ movie\_lang\). It returns the same union, grouped Chinese, English, Japanese by the sort. Adding Spanish to the list is one extra literal rather than a whole new OR arm. The system checks each row's \(movie\_lang\) against the list and keeps matches. Sense-check: the IN count must equal the three-arm OR count exactly — any gap means a list literal is misspelled.

Example 2 — certificates 12 and PG: Run \(SELECT\ *\ FROM\ movies\ WHERE\ age\_certificate\ IN\ ('12', 'PG')\ ORDER\ BY\ age\_certificate\). PG rows return and 12 rows return where present. A trial with \('13', 'PG'\) shows PG rows but no 13 rows, because no 13 value exists in the data. A trial with \('12', '13'\) refines the check. Text-styled codes take quotes even when they look numeric, because \(age\_certificate\) is character varying. The missing-13 trial is the teaching point: a list entry with no data behind it silently matches nothing — no error, just fewer rows.

Example 3 — directors not 13 or 10: Run \(SELECT\ *\ FROM\ movies\ WHERE\ director\_id\ NOT\ IN\ (13, 10)\ ORDER\ BY\ director\_id\). Returned identifiers run 1, 2, 3 through 9, then jump past 10, run 11, 12, then jump past 13. Both quoted \('13', '10'\) and bare \((13, 10)\) return the same set here because \(director\_id\) is integer and the values are plain integers. The cleaner style for pure integers omits quotes. The jumps at 10 and 13 are the visual proof: NOT IN punches exactly those two holes in the identifier line.

Example 4 — actors past the first four: Run \(SELECT\ *\ FROM\ actors\ WHERE\ actor\_id\ NOT\ IN\ (1, 2, 3, 4)\ ORDER\ BY\ actor\_id\). Rows start at 5, 6, 7, 8 and run onward. Integer lists stay bare with no quotes. Final check: no returned \(actor\_id\) sits at or below 4.

Real-world: IN lists answer "any of these SKUs, zones, or tags" pulls in one filter instead of many OR arms. A search page with tick boxes (English, Chinese, Japanese) maps each tick to one more list literal, so the query grows by words rather than by arms.

Pitfalls: quoting text-styled codes is required — \(age\_certificate\ IN\ (12, PG)\) without quotes fails, since PG is not a number. A second trap is the empty list \(IN\ ()\), which the parser rejects. A third is stuffing NULL into a NOT IN list, which empties the whole answer for the unknown-logic reason noted above — use \(IS\ NOT\ NULL\) guards from 5.14 when NULLs may be present.

5.11.3 Student Questions and Answers

Q: Why use IN when OR already works? A: OR repeats the column on every arm, so ten choices need ten arms. IN names the column once as \(movie\_lang\ IN\ ('English', 'Chinese', 'Japanese')\) and holds all choices in one list, which is shorter to write and easier to extend. Both spellings return the same rows — IN wins on reading, not on meaning.

Q: Do numbers in IN need quotes? A: Plain integers such as \((13, 10)\) run fine bare and match quoted forms. Text values such as \('English'\) and text-styled codes such as \('12'\) must keep single quotes. Match the quotes to the stored type: bare for integer columns, quoted for text columns, even when the text looks numeric.

Recap and bridge: IN folds OR chains on one column into a single list; NOT IN keeps the complement. The next section folds AND pairs on one column into a single range with BETWEEN.

5.12 BETWEEN and NOT BETWEEN for Range Checks

5.12.1 Meaning and Boundary Rule

Hook: "Births from 1991 through 1995" needs two compares — is there a one-phrase spelling that also settles whether the edge years count?

The BETWEEN operator — a range test written as \(value\ BETWEEN\ low\ AND\ high\) — keeps a row when the value sits on or between the two bounds. The bounds are inclusive: low itself and high itself both pass. The test is true when \(value >= low\ AND\ value <= high\) holds, and false outside that span. NOT BETWEEN keeps the complement, every row outside the inclusive span.

SELECT * FROM actors
WHERE date_of_birth BETWEEN '1991-01-01' AND '1995-12-31';

BETWEEN fits numbers and dates best, though text ranges are legal. Date and text literals take single quotes. Pure numbers stay bare.

Formalize — the inclusive contract: \(x\ BETWEEN\ low\ AND\ high\) is exactly \(x >= low\ AND\ x <= high\). Low must sit at or below high — a flipped range (\(BETWEEN\ 300\ AND\ 100\)) matches nothing, since no value can sit at once above 300 and below 100. \(NOT\ BETWEEN\) is exactly \(x < low\ OR\ x > high\), the outside mirror. The rewrite is standard across PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server, so boundary questions have one answer everywhere.

Visual check: draw the number line with low and high as closed dots (filled circles). BETWEEN shades the segment between them including both dots. NOT BETWEEN shades both outer rays excluding both dots. The closed-dot picture is the memory hook for "edges count".

Cross-database extra: all five systems treat BETWEEN as inclusive, but date edges need care — \(BETWEEN\ '1998-01-01'\ AND\ '2002-12-31'\) includes the whole end day only when the column holds plain dates; for timestamp columns holding hours and minutes, rows late on 31 December 2002 slip past the midnight edge, so production date ranges often use \(>=\ start\ AND\ <\ day\_after\_end\) instead. Snowflake adds \(BETWEEN\ SYMMETRIC\), which auto-orders flipped bounds rather than returning empty.

5.12.2 Worked Examples

Example 1 — actor births from 1991 to 1995: Inspect \(SELECT\ *\ FROM\ actors\ ORDER\ BY\ date\_of\_birth\) ascending. Then run \(SELECT\ *\ FROM\ actors\ WHERE\ date\_of\_birth\ BETWEEN\ '1991-01-01'\ AND\ '1995-12-31'\). Seven rows return, every birth from 1 January 1991 through 31 December 1995 inclusive. Final count 7. Sense-check: a birth exactly on 1991-01-01 or 1995-12-31 would still count — that edge rule is tested directly in Example 3.

Example 2 — movie releases from 1998 to 2002: Inspect \(SELECT\ *\ FROM\ movies\ ORDER\ BY\ release\_date\). Then run \(SELECT\ *\ FROM\ movies\ WHERE\ release\_date\ BETWEEN\ '1998-01-01'\ AND\ '2002-12-31'\). Only releases inside that window return. Earlier than 1998 and later than 2002 drop out. The inspect-then-filter order matters: the sorted scan shows where the window edges fall before the range trims to them.

Example 3 — domestic revenue from 100 to 300: Inspect \(SELECT\ *\ FROM\ movies\_revenues\ ORDER\ BY\ revenues\_domestic\). Then run \(SELECT\ *\ FROM\ movies\_revenues\ WHERE\ revenues\_domestic\ BETWEEN\ 100\ AND\ 300\). Rows such as 102.10 through 290.30 return. A second run with \(BETWEEN\ 102.10\ AND\ 290.30\) still returns both edge rows, which proves edges are inclusive. To exclude an edge, move the bound outward or switch to strict \(>\) and \(<\) compares. Final proof both edges kept. Money stays bare (no quotes) since the column is numeric.

Example 4 — movie length 100 to 200 and its outside: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_length\ BETWEEN\ 100\ AND\ 200\ ORDER\ BY\ movie\_length\). Rows from 100 through 200 return. Change to \(WHERE\ movie\_length\ NOT\ BETWEEN\ 100\ AND\ 200\ ORDER\ BY\ movie\_length\). Now only rows below 100 such as 87 and 99 plus rows above 200 return. The pair shows NOT BETWEEN as the outside mirror. Sense-check: the two answers must add back to the full table count with no overlap — a row cannot sit both inside and outside one range.

Example 5 — BETWEEN rewritten as two compares: Run \(SELECT\ *\ FROM\ movies\ WHERE\ movie\_length >= 100\ AND\ movie\_length <= 200\ ORDER\ BY\ movie\_length\). It returns exactly the same set as \(movie\_length\ BETWEEN\ 100\ AND\ 200\). BETWEEN is shorter to read and states one range check, while the long form checks each edge alone. The range form may also run faster because it states one span test rather than two separate column tests. When an exam asks for the rewrite, this pair is the answer verbatim.

Pitfalls: flipping the bounds (\(BETWEEN\ 200\ AND\ 100\)) returns zero rows with no error — always put the smaller value first. A second trap is quoting numbers (\(BETWEEN\ '100'\ AND\ '200'\)) out of habit from text filters; it runs here but breaks the type habit. A third is using BETWEEN on timestamps with a date-only end edge and losing the end day's late rows (see the cross-database note above).

5.12.3 Student Questions and Answers

Q: Are the BETWEEN edges included? A: Yes. \(BETWEEN\ 102.10\ AND\ 290.30\) returns rows holding exactly 102.10 and exactly 290.30. The test means \(value >= low\ AND\ value <= high\). Closed dots, not open ones.

Exam note: boundary inclusion is the most tested BETWEEN detail. Memorize the rewrite \(BETWEEN\ low\ AND\ high\) equals \(>=\ low\ AND\ <=\ high\). A flipped-bounds variant (high first, low second) is the standard follow-up trap — it returns nothing.

Recap and bridge: BETWEEN folds a closed \(>=\) plus \(<=\) pair into one range; NOT BETWEEN keeps the outside. The next section moves from exact and range matches to pattern matches with LIKE and ILIKE.

5.13 LIKE and ILIKE Pattern Matching

5.13.1 Wildcards and Return Shape

Hook: You remember the name holds "Tim" but not the full spelling — how do you pull Tim Allen without knowing his surname?

The LIKE operator — a case-sensitive pattern test — and the ILIKE operator — its case-insensitive twin — search text by pattern and return true or false per row. Two wildcards build patterns. Percent \(%\) matches any run of zero or more characters. Underscore \(_\) matches exactly one character, so two underscores match exactly two. The shape is \(value\ LIKE\ 'pattern'\) or \(value\ ILIKE\ 'pattern'\), with the pattern in single quotes.

SELECT * FROM actors WHERE first_name LIKE 'A%' ORDER BY first_name;
SELECT * FROM actors WHERE first_name ILIKE '%tim%';

Pattern position carries the meaning. \('A%'\) means starts with A. \( '%a'\) means ends with a. \('%Tim%'\) means holds Tim anywhere. \('_____'\) with five underscores means exactly five characters. \('_L%'\) means any first character, L second, then anything. LIKE is case sensitive, so \('Tim'\) and \('tim'\) differ. ILIKE ignores case, so both spellings match.

Formalize — the two-wildcard contract: \(%\) covers any run including the empty run, so \('A%'\) matches both "A" and "Alice". \(_\) covers exactly one character, so \('_____'\) (five underscores) matches "Alice" and "James" but never "Al" or "George". Fixed letters in the pattern must match exactly (under LIKE) at their pinned slots. LIKE folds nothing — case, accents, and spaces all count. ILIKE folds case only, so \('%tim%'\) matches "Tim", "tim", and "TIM" but still requires the letters t-i-m in order.

Cross-database note: LIKE runs everywhere with the same \(%\) and \(_\) wildcards. ILIKE runs as written in PostgreSQL, Snowflake, and Databricks. MySQL and SQL Server have no ILIKE — there you write \(LOWER(first\_name)\ LIKE\ '%tim%'\) or pick a case-insensitive collation. The escape rule is also shared: to search a real percent or underscore, prefix it with an escape character, as in \(LIKE\ '%!%%'\ ESCAPE\ '!'\) for a trailing real percent sign.

Visual check: lay the pattern under the word like a stencil. Each fixed letter must show through its slot; each \(_\) covers one hidden letter; each \(%\) stretches over any leftover run. The stencil picture explains why \(%e_\) needs an e with at least one letter behind it.

5.13.2 Worked Examples with Fixed Text

Fixed-text stencil demos: Fixed demos with \(SELECT\ 'hello'\ LIKE\ 'hello'\) return true because the strings match exactly. \(SELECT\ 'hello'\ LIKE\ 'H%'\) returns true because H leads and \(%\) covers ello. \(SELECT\ 'hello'\ LIKE\ '%e%'\) returns true because e sits inside hello. \(SELECT\ 'hello'\ LIKE\ 'hell%'\) returns true because hell leads and \(%\) covers o. \(SELECT\ 'hello'\ LIKE\ '%ll'\) returns false, because the pattern demands the string end at ll while hello ends at lo, so the missing o breaks the match. Underscore demos: \(SELECT\ 'hello'\ LIKE\ '_ello'\) returns true because one wildcard covers h. A two-underscore plus one-wildcard mix also returns true when the fixed middle letters line up. A \(%\) plus \(_\) mix such as \(%e_\) returns true on hello because e appears with one trailing character o behind it. Final tallies six true, one false — the single false (\(%ll\)) is the stencil lesson: ends-with means the tail must match exactly.

5.13.3 Worked Examples on the Actors Table

Example 1 — first name starts with capital A: Run \(SELECT\ *\ FROM\ actors\ ORDER\ BY\ first\_name\). Then run \(SELECT\ *\ FROM\ actors\ WHERE\ first\_name\ LIKE\ 'A%'\ ORDER\ BY\ first\_name\). Every returned first name starts with capital A. Flipping the pattern to \('%A'\) changes the meaning to ends with A and returns a different set. Using \('%A%'\) means holds capital A anywhere, which is broader still. A lowercase \('a%'\) on first names misses capital-A names under LIKE, which leads to the case lesson below. The three-pattern ladder (\('A%'\), \('%A'\), \('%A%'\)) shows starts-with, ends-with, holds in one scan.

Example 2 — last name ends with lowercase a: Run \(SELECT\ *\ FROM\ actors\ WHERE\ last\_name\ LIKE\ '%a'\ ORDER\ BY\ last\_name\). Names ending in small a return, including rows such as Molina and Kurosawa-style endings noted in the demo. The trailing \(%\) on the left means any head, and the fixed a means the tail. Case matters: \('%A'\) with capital A would return a different set.

Example 3 — first name is exactly five letters: Five underscores \( '_____'\) state exactly five characters. Run \(SELECT\ *\ FROM\ actors\ WHERE\ first\_name\ LIKE\ '_____'\). It returns 38 rows, with five-letter names such as Alice, James, and Jason in the set, while six-letter names drop out. Each underscore counts one character, so the count of underscores is the length test. Final count 38. Sense-check: a four-underscore pattern would return four-letter names instead — the underscore count is the ruler.

Example 4 — L in second place: Two candidate patterns show why position matters. \(WHERE\ first\_name\ LIKE\ '%L%'\) means L anywhere, so it returns Bill with L third plus many others with L scattered. \(WHERE\ first\_name\ LIKE\ '_L%'\ ORDER\ BY\ first\_name\) means any one first character, L second, then anything, so only true second-place L names return. The underscore pins the slot while \(%\) floats. The Bill row is the proof: present in the first answer, absent from the second.

Example 5 — case sensitivity and ILIKE: Run \(SELECT\ *\ FROM\ actors\ WHERE\ first\_name\ LIKE\ '%Tim%'\). It returns Tim Allen for capital-T Tim. Run the same with lowercase \('%tim%'\) under LIKE. No rows return, which proves LIKE is case sensitive. Run \(SELECT\ *\ FROM\ actors\ WHERE\ first\_name\ ILIKE\ '%tim%'\). Tim Allen returns again, which proves ILIKE ignores case. Prefer ILIKE when missing a row over case would be worse than extra matches, and prefer LIKE when the exact capital shape is part of the task. MySQL and SQL Server rewrites: \(LOWER(first\_name)\ LIKE\ '%tim%'\) gives the same row.

Pattern search cost is the closing caution. LIKE and ILIKE scans on huge text tables can run slowly because pattern checks test row by row. Indexes and other search aids, covered later, can speed them. Leading-wildcard patterns (\(\%tim%\)) are the slowest shape since no index order can prune them; prefix patterns (\('A%'\)) can still use a plain index.

5.13.4 Student Questions and Answers

Q: Why did lowercase tim miss Tim Allen under LIKE but find him under ILIKE? A: LIKE compares exact letter shape, so small-t tim differs from capital-T Tim and returns no rows. ILIKE folds case, so \(first\_name\ ILIKE\ '%tim%'\) matches Tim Allen. The stencil is identical — only the case folding changes.

Q: When should I use underscore against percent? A: Use underscore when the slot count matters, as in \( '_____'\) for exactly five letters or \('_L%'\) for L strictly second. Use percent when only presence or affix matters, as in \('A%'\) for starts with A or \('%a'\) for ends with a. Count slots with \(_\); float over runs with \(%\).

Real-world: pattern search powers name lookup, prefix completion, suffix grouping, and fixed-length code checks. A search box that completes after two letters runs \('AB%'\), a postal-code validator for five fixed slots runs \('_____'\), and a "find Tim in any case" box runs \(ILIKE\ '%tim%'\) (or the LOWER-LIKE rewrite outside PostgreSQL-family systems).

Recap and bridge: \(%\) floats, \(_\) pins, LIKE is strict on case, ILIKE folds it. The next section handles the value that no pattern can match — the missing marker NULL.

5.14 IS NULL and IS NOT NULL for Missing Values

5.14.1 Meaning of NULL

Hook: One actor row has no birth date at all — which test finds it when \(=\) finds nothing?

NULL — a marker for missing or not-applicable data — is not zero, not blank text, and not a date. The IS NULL operator keeps only rows where the tested column holds NULL. The IS NOT NULL operator keeps only rows where the column holds any real value. The shape is \(column\_name\ IS\ NULL\) or \(column\_name\ IS\ NOT\ NULL\). Each test returns true or false per row.

SELECT * FROM actors WHERE date_of_birth IS NULL;
SELECT * FROM movies_revenues WHERE revenues_domestic IS NOT NULL;

Formalize — the unknown logic: NULL means unknown, and any compare against unknown stays unknown rather than true or false. \(date\_of\_birth = NULL\) is unknown for every row, so WHERE (which keeps only true) returns nothing — not even the NULL rows. \(IS\ NULL\) skips the compare and asks directly "is this cell marked missing?", which votes a clean true or false per row. \(IS\ NOT\ NULL\) is the exact mirror. The logic is standard across PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server with no spelling differences.

Cross-database note: the IS NULL spelling is identical everywhere, but NULL sort position differs — PostgreSQL sorts NULLs last on ascending by default, MySQL sorts them first, Snowflake follows the ORDER direction. That is why money sorts in 5.9 add explicit \(NULLS\ LAST\) rather than trusting defaults. A second shared trap: \(NOT\ IN\) lists holding NULL (5.11) go empty for the same unknown logic — filter NULLs out first when mixing the two.

Picture NULL as a blank sticker on a file: \(=\) tries to read the sticker as a value and fails, while IS NULL checks for the sticker itself.

Scope: IS NULL tests one column for the missing marker — it never compares two values. \(revenues\_domestic\ IS\ NULL\) asks about the domestic cell only. To test "either column missing" use OR across two IS NULL tests; for "both missing" use AND (Example 4 below). NULL needs its own operator rather than \(=\) in every position.

5.14.2 Worked Examples

Example 1 — actors missing a birth date: Run \(SELECT\ *\ FROM\ actors\) and \(ORDER\ BY\ date\_of\_birth\) to push the missing value into view. One row for Zhang Jin Zhao shows NULL in \(date\_of\_birth\). Run \(SELECT\ *\ FROM\ actors\ WHERE\ date\_of\_birth\ IS\ NULL\). That single row returns. Final answer 1 row. Sense-check: the complement \(IS\ NOT\ NULL\) must return all remaining actor rows.

Example 2 — missing birth date or missing first name: Inspect \(ORDER\ BY\ first\_name\) to surface row 147 with a missing \(first\_name\). Run \(SELECT\ *\ FROM\ actors\ WHERE\ date\_of\_birth\ IS\ NULL\ OR\ first\_name\ IS\ NULL\). Both the birth-missing row and the name-missing row 147 return, because OR keeps rows where either arm is true. Final answer 2 rows. Swap OR to AND and the answer shrinks to rows missing both at once (possibly zero) — the either-against-both contrast from 5.3 and 5.4 returns here.

Example 3 — movies with missing domestic revenue: Read \(SELECT\ *\ FROM\ movies\_revenues\) and \(ORDER\ BY\ revenues\_domestic\) to group missing values. Run \(SELECT\ *\ FROM\ movies\_revenues\ WHERE\ revenues\_domestic\ IS\ NULL\). Only rows with missing domestic revenue return. The sorted scan first shows the NULL group bunched at one end, so the filter result can be checked by eye.

Example 4 — missing domestic or missing international: Run \(SELECT\ *\ FROM\ movies\_revenues\ WHERE\ revenues\_domestic\ IS\ NULL\ OR\ revenues\_international\ IS\ NULL\). Every row missing at least one of the two returns. Change OR to AND as \(WHERE\ revenues\_domestic\ IS\ NULL\ AND\ revenues\_international\ IS\ NULL\). Now only rows missing both return, a much smaller set. The OR-against-AND pair shows how the join word controls "either missing" against "both missing". Sense-check: the AND answer must sit inside the OR answer — every both-missing row is also either-missing.

Example 5 — present domestic revenue: Run \(SELECT\ *\ FROM\ movies\_revenues\ WHERE\ revenues\_domestic\ IS\ NOT\ NULL\). Rows with real domestic numbers return and NULL rows drop out. IS NOT NULL is the direct mirror of IS NULL. Pair it with Example 3: the two counts must add back to the full revenues table count.

Example 6 — failed equality trials: Four wrong shapes prove why IS NULL exists. \(WHERE\ date\_of\_birth = NULL\) returns no rows because NULL never equals anything, not even itself. \(WHERE\ date\_of\_birth = 'null'\) compares a date column against the four-letter text null and raises an invalid-input type error. \(WHERE\ date\_of\_birth = ''\) with an empty quote pair fails on type mismatch for a date field. \(WHERE\ date\_of\_birth = ' '\) with a blank space fails the same way. Only \(date\_of\_birth\ IS\ NULL\) states the missing-value test in legal form. Left type and right type must align, and NULL needs its own operator rather than \(=\) instead. Final lesson: quoted null, empty quotes, and blank space are all real text values, never the missing marker.

Pitfalls: the top fault is \(=\) NULL, which runs with no error but returns zero rows — silence rather than a message. The second is quoted \('null'\) on typed columns, which errors on dates but quietly matches nothing on text. The third is assuming an empty string equals NULL: in PostgreSQL and Snowflake they differ, while Oracle treats empty strings as NULL — check the target system before relying on either.

5.14.3 Student Questions and Answers

Q: Why does equals NULL return nothing instead of the missing rows? A: NULL marks unknown, and unknown never equals unknown, so \(date\_of\_birth = NULL\) is never true. \(date\_of\_birth\ IS\ NULL\) is the dedicated missing-value test and returns the Zhang row. WHERE keeps only true votes, and \(=\) NULL never votes true.

Q: Why do quoted null and empty quotes fail on a date column? A: The left side is a date while the right side is text or empty text, so types clash and the system raises invalid input. IS NULL avoids a right-side literal entirely. Match types on both sides of every compare, and reach for IS NULL whenever the ask is about missing data.

Recap and bridge: NULL is a missing marker, never a value — only IS NULL and IS NOT NULL can test it. The last content section joins text end to end, where NULL handling splits three tools apart.

5.15 Concatenation with Pipes CONCAT and CONCAT_WS

5.15.1 Three Forms

Hook: Two money columns need one clean "22.20 | 1.30" label — which join tool keeps the label readable when one side is missing?

Joining text end to end uses three tools. The pipe pair \(||\) joins two values directly, as in \('hello'\ ||\ ' '\ ||\ 'world'\). The CONCAT function — \(CONCAT(value\_1, value\_2, ...)\) — joins its inputs in order with an optional separator passed as one of the inputs, such as a space or a pipe mark. The CONCAT_WS function — \(CONCAT\_WS(separator, value\_1, value\_2, ...)\) with WS meaning with separator — takes the separator once up front and then joins the values, skipping NULL inputs.

SELECT 'hello' || ' ' || 'world';
SELECT CONCAT('hello', ' ', 'world');
SELECT CONCAT_WS('|', revenues_domestic, revenues_international) AS profits
FROM movies_revenues;

Quick fixed demos fix the spacing idea. \(SELECT\ 'hello'\ ||\ 'world'\) returns helloworld with no gap. Adding a space part as \(SELECT\ 'hello'\ ||\ ' '\ ||\ 'world'\) returns hello world with one gap. The separator is just another joined piece.

Formalize — the three signatures: \(a\ ||\ b\) joins two values with the standard pipe operator (chain for more). \(CONCAT(a, b, c)\) joins any count in order — separators are passed as ordinary inputs between the values. \(CONCAT\_WS(sep, a, b, c)\) names the separator once first, then joins any count, placing \(sep\) only between live (non-NULL) values. The WS form is why money-pair reports over gappy columns prefer it: no live value on one side means no stray separator.

Cross-database note: keep one version per system while the meaning stays shared. The \(||\) pipes are standard in PostgreSQL, Snowflake, Oracle, SQLite, and Databricks. MySQL treats \(||\) as OR unless the PIPES_AS_CONCAT mode is on — there CONCAT is the safe spelling. CONCAT runs in PostgreSQL, MySQL, Snowflake, Databricks, and SQL Server (2012 onward). CONCAT_WS started in MySQL, then reached PostgreSQL (9.1 onward), SQL Server (2017 onward), Snowflake, and Databricks — so the WS form in this lesson ports everywhere except older SQL Server builds.

5.15.2 NULL Handling and Worked Revenue Cases

NULL handling splits the three tools. With pipes, any NULL poisons the whole join: \(SELECT\ 'hello'\ ||\ NULL\ ||\ 'world'\) returns NULL, wiping out the good text on both sides. Writing the four-letter text 'null' instead, as in \('hello'\ ||\ 'null'\ ||\ 'world'\), keeps text and returns hellonullworld, because quoted 'null' is plain text rather than missing data.

Fixed NULL demos: \(SELECT\ 'hello'\ ||\ NULL\ ||\ 'world'\) returns NULL — final answer NULL. \(SELECT\ 'hello'\ ||\ 'null'\ ||\ 'world'\) returns hellonullworld — final answer hellonullworld. The pair proves quoted 'null' is ordinary text while bare NULL is the missing marker from 5.14. Sense-check: any pipe chain touching a real NULL must come back NULL, never partial text.

The \(movies\_revenues\) table, with NULL cells in \(revenues\_domestic\) and \(revenues\_international\), shows the practical split. Reading \(SELECT\ revenues\_domestic, revenues\_international\ FROM\ movies\_revenues\) surfaces the gaps. Joining with \(SELECT\ CONCAT(revenues\_domestic, revenues\_international)\ AS\ profits\ FROM\ movies\_revenues\) glues pairs with no gap, so values such as 22.20 and 1.30 fuse. Adding a separator inside CONCAT, such as a space or a pipe mark, spaces the pair for reading. Rows where one side is NULL still show the live side, but rows where both sides are NULL still render the bare separator, such as a lone pipe with nothing around it, which reads poorly.

\(CONCAT\_WS\) fixes the separator fault by skipping NULL cells. \(SELECT\ CONCAT\_WS('|', revenues\_domestic, revenues\_international)\ AS\ profits\ FROM\ movies\_revenues\) places the pipe only between live values. A both-NULL row yields empty rather than a stray pipe. A one-NULL row yields just its live value with no dangling separator. That skip rule is why \(CONCAT\_WS\) is the safer pick for reporting over gappy money columns.

Revenue-pair trace on three toy rows: row A holds 22.20 and 1.30, row B holds 50.00 and NULL, row C holds NULL and NULL. Pipes give "22.20 | 1.30", NULL, NULL. CONCAT with a pipe piece gives "22.20|1.30", "50.00|", "|". CONCAT_WS with \(|\) gives "22.20|1.30", "50.00", empty. Final readable answers come only from the WS form — no stray pipes, no wiped rows.

Scope: concatenation joins display text — it never turns text back into numbers. A glued "22.201.30" cannot be summed until split and cast. Numbers entering CONCAT convert to text silently in most systems, so explicit CAST is the safe habit before joining money with labels. Also note CONCAT_WS skips only true NULLs, never empty strings — an empty-string side still earns its separators.

5.15.3 Student Questions and Answers

Q: Why did pipes turn hello plus NULL plus world into NULL? A: Pipes propagate missing data, so \( 'hello'\ ||\ NULL\ ||\ 'world'\) has one unknown part and the whole result becomes unknown NULL. CONCAT keeps live parts, and CONCAT_WS further skips NULL parts when placing separators. The tool choice decides whether one gap wipes the row, leaves a dangling separator, or vanishes cleanly.

Real-world: CONCAT_WS builds clean display fields such as city plus country labels and money-pair reports where some cells are empty. A "domestic | international" revenue label, a "city, country" header, and a "first plus last name" display all use one WS call rather than nested case logic per column.

Recap and bridge: pipes wipe on NULL, CONCAT keeps live sides, CONCAT_WS skips gaps with no stray separators. That closes the operator tour — the appendices now collect the exam lines and the industry uses in one place.

AND Operator for Multiple Conditions

Must-know: AND keeps a row only when every joined condition is true, so counts only narrow; quoted '18' matches the text certificate column

\[ movie\_lang = 'English' \; AND \; age\_certificate = '18' \;\rightarrow\; 4 \; rows \]

Top pitfall: An empty AND answer means no row met both demands, not a broken query; check the data mix first

OR Operator for Either-Or Choice

Must-know: OR keeps a row when at least one condition holds, so counts widen to the union

\[ movie\_lang = 'English' \; OR \; movie\_lang = 'Chinese' \;\rightarrow\; 43 \; rows \]

Top pitfall: Every OR arm needs its own column; mixing AND and OR without brackets follows precedence, not reading order

Clause Position and Logical Execution Order

Must-know: Logical order is FROM, WHERE, SELECT, ORDER BY; WHERE sits after FROM and before ORDER BY or the query fails

\[ FROM \;\rightarrow\; WHERE \;\rightarrow\; SELECT \;\rightarrow\; ORDER \; BY \]

Top pitfall: Typing SELECT first tricks readers into thinking SELECT runs first; it runs third, after FROM and WHERE

Column Aliases and WHERE

Must-know: SELECT aliases are born after WHERE runs, so same-level WHERE cannot see them; a subquery wrapper exposes them

\[ last\_name \; AS \; surname \;\rightarrow\; WHERE \; sees \; only \; last\_name \]

Top pitfall: Using a SELECT alias in same-level WHERE raises column does not exist; use the true column or a subquery

LIMIT and OFFSET for Top N and Paging

Must-know: ORDER BY sorts, LIMIT caps to n rows, OFFSET skips m rows first; NULLS LAST keeps true money leaders in DESC sorts

\[ ORDER \; BY \; col \; LIMIT \; n \; OFFSET \; m \]

Top pitfall: OFFSET counts skipped rows, not identifiers; LIMIT without ORDER BY means any n rows

FETCH as the Standard Form of LIMIT

Must-know: FETCH matches LIMIT in meaning with standard-SQL wording and must sit after ORDER BY; FIRST/NEXT and ROW/ROWS are equivalent

\[ OFFSET \; start \; ROWS \; FETCH \; FIRST \; n \; ROWS \; ONLY \]

Top pitfall: FETCH before ORDER BY fails near ORDER; MySQL has no FETCH so LIMIT is the only path there

IN and NOT IN for List Checks

Must-know: IN folds OR chains on one column into a compact list; NOT IN keeps the complement; bare integers but quoted text codes

\[ movie\_lang \; IN \; ('English', 'Chinese', 'Japanese') \]

Top pitfall: Text codes like '12' need quotes; a NULL inside a NOT IN list empties the whole answer

BETWEEN and NOT BETWEEN for Range Checks

Must-know: BETWEEN edges are inclusive and rewrite as >= plus <=; NOT BETWEEN keeps the outside mirror

\[ value \; BETWEEN \; low \; AND \; high \;=\; value >= low \; AND \; value <= high \]

Top pitfall: Flipped bounds (BETWEEN 200 AND 100) return zero rows; timestamp end edges can lose late-day rows

LIKE and ILIKE Pattern Matching

Must-know: % floats over any run, _ pins exactly one slot; LIKE is case sensitive, ILIKE folds case; five underscores test length five

\[ value \; LIKE \; 'pattern' \;\;|\;\; value \; ILIKE \; 'pattern' \]

Top pitfall: Lowercase tim misses Tim Allen under LIKE; leading-% patterns cannot use plain indexes and run slowly

IS NULL and IS NOT NULL for Missing Values

Must-know: NULL is unknown, never equal to anything; only IS NULL and IS NOT NULL test it; OR across IS NULL tests means either missing, AND means both

\[ column\_name \; IS \; NULL \;\;|\;\; column\_name \; IS \; NOT \; NULL \]

Top pitfall: = NULL silently returns zero rows; quoted null and empty quotes are real text, never the missing marker

Self-check: Why does WHERE date_of_birth = NULL return no rows?

Concatenation with Pipes CONCAT and CONCAT_WS

Must-know: Pipes wipe on NULL, CONCAT keeps live sides, CONCAT_WS skips gaps with no stray separators; quoted null is plain text

\[ CONCAT\_WS('|', \; revenues\_domestic, \; revenues\_international) \]

Top pitfall: Pipe chains wipe to NULL on one gap; CONCAT leaves stray separators on both-NULL rows; only CONCAT_WS stays clean
