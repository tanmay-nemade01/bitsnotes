Triggers are the database's way of reacting by itself. Instead of trusting every application, script, and manual fix to remember the same follow-on step, you teach the table once — "whenever this kind of write happens, do this" — and the database keeps that promise on every path. This lecture builds that skill from the ground up: what a trigger is, when it runs, how many times it runs, where it is allowed, why teams love and fear it, the exact two-step creation pattern, and then a full set of working builds — name-change auditing, insert-time repair, generic guard routines, truncate guards, universal JSON auditing, conditional guards, primary-key guards — closing with cautious-use habits and server-level event triggers that watch schema changes themselves.

35.1 What a Trigger Is

35.1.1 Definition and automatic firing

A trigger answers one question before any syntax: who calls this code? Nobody in the application does. The database itself calls it, every time the watched data change happens.

A trigger — a stored routine that starts by itself when a data change happens — sits at the center of this topic. A general dictionary meaning says a trigger is any event that sets a course of action in motion. The PostgreSQL meaning is sharper: a PostgreSQL trigger is a function that invokes automatically whenever an event tied to a table, a view, or a foreign table occurs.

Think of a motion-sensor light in a hallway. You wire it once, and from then on anyone walking past gets light without flipping a switch. A trigger is wired the same way: you define it once with CREATE FUNCTION plus CREATE TRIGGER, and from then on every matching write wakes it. Where the everyday analogy breaks is that a hallway light cannot change the person walking past, while a BEFORE trigger can rewrite the row itself before it lands.

Two ideas carry the whole definition. First, a trigger is at heart a function, more exactly a special user-defined function, not a plain SQL expression. It lives in the database, it has a body block, and it can hold branching, notices, exceptions, and inserts into other tables. Second, it fires by itself. Nobody calls it per row in application code. The database calls it when the linked event happens. That self-starting habit is why one helpful comparison calls a trigger a cron job: define it once, and from then on it wakes itself whenever its condition arrives. The cron-job picture helps for "runs without a caller" but breaks on timing — a cron job wakes on a clock, while a trigger wakes on a data event.

A PostgreSQL trigger is a special user-defined function bound to a table, view, or foreign table that the database invokes automatically on INSERT, UPDATE, DELETE, or TRUNCATE, with timing BEFORE, AFTER, or INSTEAD OF deciding whether it runs ahead of, behind, or in place of the event.

A user-defined function — a routine stored in the database and written by a database user — differs from a trigger in exactly this calling habit. A user-defined function waits until someone calls it inside a procedure or a query, for example SELECT percent_change(110, 108, 2). A trigger never waits for a manual call. It listens for its event, which is one of insert, update, delete, or truncate, and then it runs. That is the single sentence that separates the two: functions wait to be called, triggers listen and fire.

Picture the flow as a small timeline. Application issues UPDATE players SET name = 'Linda Two' WHERE player_id = 2. The database notices a trigger is bound to UPDATE on players, pauses the write for a moment, runs the trigger function with the old and new row images available, and then completes or cancels the write depending on what the function returned. The application never mentioned the trigger by name.

Across database systems the same idea wears different clothes, and keeping one version in mind saves confusion later. In PostgreSQL the worker is a function returning the special trigger type written in plpgsql (never plain SQL), bound with EXECUTE PROCEDURE. In MySQL the worker is written inline in the CREATE TRIGGER body with FOR EACH ROW only — there is no separate function step and no statement-level form. In SQL Server the worker reads set-like inserted and deleted tables instead of per-row NEW and OLD, and there is no BEFORE timing, only AFTER and INSTEAD OF. Snowflake and Databricks/Spark SQL offer no classic row triggers at all; the matching pattern there is Streams plus Tasks or Delta Live Table expectations. The common core is identical — automatic code on a data change — and only the spelling changes.

Exam note: Be able to state the definition cold: a trigger is a special user-defined function the database fires by itself on insert, update, delete, or truncate. The contrast the checker wants is "function waits for a call, trigger listens for an event."

One-line recap: a trigger is self-firing database code bound to a data change. That idea now needs its vocabulary — which events, which targets, and which timing — taken up next.

35.1.2 Events and targets

An event — the data change a trigger listens for — is one of four operations in ordinary PostgreSQL work: INSERT, UPDATE, DELETE, or TRUNCATE. Adding rows, changing rows, removing rows, or emptying a table fast can each wake a trigger. There is deliberately no fifth event for reading: a SELECT only looks at rows, so there is nothing for the trigger to react to.

A trigger can attach to a single table, a view, or a foreign table. It is not limited to base tables. As long as rows flow through a table, a view, or a foreign table, and something should happen when rows are about to be added, changed, removed, or emptied, a trigger can hold that something. The reference table in a later section spells out which timing and level each event allows on tables versus views. The headline to carry forward: insert, update, and delete are the flexible everyday events on tables and views, while truncate is the narrow, tables-only, statement-only case.

Suppose a players table gets one INSERT of two rows, one UPDATE of one row, and one TRUNCATE in the same afternoon. A trigger bound to INSERT fires on the first statement only. A trigger bound to UPDATE fires on the second only. A trigger bound to TRUNCATE fires on the third only. Each event wakes only its own listeners — binding to the wrong event is the same as having no trigger at all.

In MySQL the event list is shorter: INSERT, UPDATE, and DELETE only, with no TRUNCATE trigger event, while SQL Server likewise has no truncate trigger and Snowflake has no row-trigger events whatsoever.

Recap: Events are insert, update, delete, or truncate; targets are a table, view, or foreign table. The next step is timing — whether the code runs before, after, or instead of that event.

35.1.3 Before, after and instead of timing

Trigger timing answers when the routine runs relative to its event. There are three choices: BEFORE, AFTER, and INSTEAD OF.

BEFORE runs ahead of the event and may reshape or skip the row. AFTER runs once the change is stored and every change is visible, so it is the home of follow-on work. INSTEAD OF replaces the event action entirely and matters most on views.

A BEFORE trigger runs ahead of the event: before insert, before update, before delete, or before truncate. Running ahead gives it two strong powers. It can skip the operation for the current row, so a row that should not be written simply is not written — the later delete guard does exactly this by returning null. It can also change the row being inserted or updated, for example doubling a value or scaling it by ten, by assigning to fields of the NEW image and returning NEW. Later hands-on work shows both powers: a temperature check rewrites an out-of-range value before it lands, and a delete guard cancels the delete before it touches the table. The limit to remember: only a BEFORE trigger can reshape the landing row; an AFTER trigger arrives too late.

An AFTER trigger runs once the row operation has finished and the change sits in the table. All the changes are visible to the trigger at that point. That makes AFTER the natural place for follow-on work driven by business rules: copy the new row into an orders table, recompute a count and store it elsewhere, or re-check the fresh row and raise an error when a custom rule is broken. Because the row is already stored, the trigger can read exactly what landed and then act on it. The grades-audit pattern in the companion book uses this shape — AFTER UPDATE ... FOR EACH ROW compares OLD.grade with NEW.grade and inserts a history row only when they differ.

An INSTEAD OF trigger replaces the event operation instead of running ahead of it or behind it. Rather than letting the row-level action proceed normally, the trigger does something fully different in its place. This path matters most on views, where a direct insert, update, or delete may have no single base-table meaning, so the trigger supplies the real behavior. A view joining two tables cannot be inserted into directly; an INSTEAD OF INSERT trigger splits the incoming row into the two correct base-table writes.

Walk a temperature reading of negative one hundred through both timings. With BEFORE INSERT, the function sees NEW.temperature = -100, rewrites it to 0, returns NEW, and the table stores 0. With AFTER INSERT, the table already stores -100 before the function runs, so the function can only log it, raise an error, or write elsewhere — it cannot silently reshape the stored value. Timing is the whole difference.

Dialect note worth keeping: MySQL supports BEFORE and AFTER but not INSTEAD OF; SQL Server supports AFTER and INSTEAD OF but not BEFORE. PostgreSQL is the system in this lecture that offers all three.

Scope: BEFORE is the only timing that can modify NEW and have the change land. Assumption: the trigger runs inside the same transaction as the firing statement, so raising an exception rolls the statement back. What breaks if ignored: putting repair logic in an AFTER trigger and wondering why stored values never change.

Recap: Before reshapes or skips, after follows up on stored rows, instead-of substitutes behavior on views. With timing fixed, the remaining question is order when several triggers share one table.

35.1.4 Execution order and unlimited triggers

There is no fixed cap on how many triggers a table may carry. Any number is allowed. When several triggers share one table, their firing order is fully fixed and easy to plan around: alphabetical order by trigger name.

The cycle is always: every BEFORE trigger in alphabetical order, then the row or statement action itself, then every AFTER trigger in alphabetical order. Names are execution order, not decoration.

The full cycle runs in three stages. First, every BEFORE trigger fires, in alphabetical order by name. Next, the database performs the row operation the trigger was fired for, meaning the insert, update, delete, or truncate step itself. Then every AFTER trigger fires, again in alphabetical order by name. Because names decide order, careful naming is part of trigger design rather than decoration. An audit trigger that must see the last state, for example, needs a name that sorts after any trigger that can still reshape the row. Concretely, aaa_fix_temp always runs before zzz_log_temp on the same event and timing.

Two BEFORE INSERT triggers share t_temperature_log: b_repair clamps impossible readings to zero and m_audit logs the landing value. Insert -100. b_repair runs first and rewrites NEW to 0; m_audit then sees 0, not -100. Swap the names and the audit would log -100 before the repair — same rows, wrong history. Sense-check: the logger must sort last.

Real-world: database administrators lean on this fixed order when they stack validation, repair, and logging triggers on one busy table. Payroll estates, for instance, run a repair trigger first, a rule-check trigger second, and the audit logger last so the log always reflects the final stored row.

Pitfalls: Relying on creation order instead of alphabetical order — creation order does not decide firing order. Giving repair and audit triggers names that sort the wrong way round, so the audit captures the pre-repair value. Forgetting that the operation itself sits between the before set and the after set when reasoning about what each trigger can see.

Recap: Unlimited triggers per table, alphabetical within each timing band, action in the middle. That ordering rule explains why naming conventions like trg_ plus a sortable suffix are worth enforcing. Next comes the boundary with stored procedures.

35.1.5 Triggers versus stored procedures

Q: Is a trigger just another name for a user-defined function we call ourselves? A: No. A user-defined function waits for a manual call inside a procedure or query. A trigger is a special user-defined function that the database invokes by itself whenever its linked insert, update, delete, or truncate event occurs, with before, after, or instead-of timing deciding exactly when. The trigger also takes no declared parameter list — it learns what happened through NEW, OLD, and trigger variables.

Two traits set triggers apart from stored procedures. First, users cannot run a trigger by hand. There is no fire-this-trigger-now command. A trigger runs only through normal data operations: insert, update, delete, or truncate, paired with its before, after, or instead-of timing. Testing a trigger therefore always means running a write and watching what happens, never calling the trigger directly. Second, a trigger cannot receive parameters the way a stored procedure can. A stored procedure declares parameters and callers pass values. A trigger receives no argument list; it learns what happened through built-in row images called NEW and OLD and through trigger variables described in later sections. The one exception that proves the rule is the WHEN-plus-argument pattern later in this lecture, where a fixed literal travels in TG_ARGV — still not a per-call parameter.

Dimension Stored procedure / function Trigger
How it starts Caller invokes it with SELECT, CALL, or EXECUTE Database fires it on a data event
Parameters Declared parameters, caller passes values No argument list; reads NEW, OLD, trigger variables
Manual run Yes, any time No — only via a real write
Return Value, result set, or status NEW, OLD, NULL, or nothing, with cancel/continue meaning

Recap: Procedures wait for callers with parameters; triggers listen for events and read row images. That completes the definition arc — next, how often the trigger runs per statement.

35.2 Row-Level and Statement-Level Triggers

35.2.1 Row-level triggers

Ask first: does this rule need to see each row's own values? If yes — one name against one old name, one temperature against one floor — the trigger must visit each row separately.

A row-level trigger — a trigger declared with FOR EACH ROW so it runs once per touched row — handles each affected row on its own. Declare the trigger with the row option and the trigger function is called for every row the event changes. Updating twenty rows with a row-level update trigger calls the function twenty times, once per row. That per-row visit is what makes row-level triggers the right home for checks and repairs that depend on single-row values, such as comparing a new name against an old name or clamping one temperature reading.

FOR EACH ROW means one function call per affected row, with that row's NEW and OLD images available. Use it whenever the decision needs single-row values.

Inside a row-level call the function sees exactly one row's before image (OLD) and after image (NEW): on INSERT, only NEW is present; on DELETE, only OLD; on UPDATE, both. Returning NEW lets the row proceed (possibly edited in a BEFORE trigger), returning NULL in a BEFORE row trigger skips just that row, and returning NULL in an AFTER row trigger is allowed but the row is already stored.

UPDATE players SET name = name WHERE player_id IN (1, 2, ... 20) touches 20 rows with a FOR EACH ROW audit trigger bound. The function runs 20 times, once per player, each time comparing that player's own OLD.name with NEW.name. Updating one row to an identical value still costs one call — the IF NEW.name <> OLD.name guard inside decides whether to log.

Dialect note: MySQL triggers are always row-level (FOR EACH ROW is the only form), while SQL Server fires once per statement but exposes all affected rows at once through inserted/deleted sets. PostgreSQL gives you the choice explicitly.

Recap: Row level visits every row with its own images. Its partner — one visit per whole statement — comes next.

35.2.2 Statement-level triggers

A statement-level trigger — a trigger declared with FOR EACH STATEMENT so it runs once per SQL statement no matter how many rows move — behaves the opposite way. The trigger function runs a single time for the whole statement even when hundreds of rows change. That single visit is the right home for batch work: validate a whole set of inserted rows together instead of row by row, keep statement-wide counts, or enforce a time-window rule without paying per-row cost. The count of visits and the moment of the visit are the whole difference between the two kinds: statement level runs once, row level runs per row.

Think of it like a roll call versus a headcount. Row level calls every name. Statement level counts the room once. The roll-call picture maps exactly: roll call touches each person (row images available), headcount looks at the room once (no per-row images, only statement facts like timing, operation, and arguments).

FOR EACH STATEMENT means one function call per firing statement. Use it for batch checks, statement-wide counts, and time-window guards where per-row values do not matter.

A statement-level function has no per-row NEW/OLD to read — asking for them is a classic error. What it does have is the trigger-variable bundle covered later: operation, timing, schema, table, and any passed arguments. That is why the Friday-afternoon guard in this lecture uses statement level: the rule cares about "is it Friday afternoon right now," not about any single task row.

UPDATE players SET name = UPPER(name) touches 200 rows. With FOR EACH ROW, the function runs 200 times. With FOR EACH STATEMENT, it runs once. For a rule like "block all writes on Friday afternoon," the statement form does one clock check instead of two hundred identical clock checks — same verdict, far less work. Sense-check: cost scales with statements, not rows.

Scope: Statement level cannot see or edit individual NEW/OLD rows. Assumption: it fires even when the statement touches zero rows (a DELETE matching nothing still fires statement triggers). What breaks if ignored: writing a per-row repair as a statement trigger and finding no row images to fix.

Recap: Statement level runs once per statement for batch and clock rules; row level runs per row for value rules. The cost and visibility trade is the bridge into the reference table of what is allowed where.

35.2.3 Student Questions and Answers

Q: Updating twenty rows fires the trigger twenty times or just once? A: It depends on the declaration. With FOR EACH ROW the function runs twenty times, once per row. With FOR EACH STATEMENT it runs exactly once for the whole update statement, regardless of row count. Several students asked this in different words — the confusion point is always "does the trigger follow rows or statements," and the answer is always "read the FOR EACH clause."

35.3 Trigger Reference Table

35.3.1 How to read the table

Before writing any trigger, ask three questions in order: when (before, after, instead-of), what (insert, update, delete, truncate), and at what grain on which target (row or statement, table or view)? The reference table is the answer key.

A trigger reference table belongs on the desk whenever new triggers are planned. Read it with timing down one side (BEFORE, AFTER, INSTEAD OF), events across the next axis (INSERT, UPDATE, DELETE, TRUNCATE), and level plus target as the last axis: row level versus statement level, on tables versus views.

The headline pattern: BEFORE and AFTER on insert, update, and delete are flexible — row level on tables, statement level on tables and views. TRUNCATE is always narrow — statement level on tables only, never row level, never on views. INSTEAD OF belongs to views.

The headline pattern is simple. BEFORE triggers on insert, update, and delete work at row level on tables, and at statement level on tables and views. BEFORE on truncate works only at statement level on tables, never at row level. AFTER triggers on insert, update, and delete work at row level on tables, and at statement level on tables and views. AFTER on truncate works only at statement level on tables, never at row level and never on views. TRUNCATE is the narrow case throughout: statement level and tables only.

Put another way, before and after triggers on insert, update, and delete are the flexible everyday tools on tables and views at both levels, while truncate triggers always stay at statement level on tables. Keeping this table close prevents wasted effort such as asking for a row-level truncate trigger, which PostgreSQL rejects with an explicit "row triggers on TRUNCATE are not supported" error — the exact failure the truncate-guard demo hits on its first attempt.

Picture the table as a grid in words. Down the left edge run the three timings. Across the top run the four events. Each cell then answers "row on table? statement on table? statement on view?" Mark every truncate-row cell with a cross — that column never allows row level. Mark every view cell in the truncate column with a cross as well. Everything else in the insert, update, and delete columns is a tick. One glance then tells you whether a planned trigger can exist before you write a line of function code.

Dialect extras worth filing in the margin rather than memorizing as new topics: MySQL has no truncate-trigger cell and no statement-level cells at all; SQL Server has no before row at all and reads affected rows from inserted/deleted; Snowflake and Databricks have no cells in this grid because they have no row triggers — auditing there moves to Streams, Change Data Feed, or append-only history tables.

Pitfalls: Requesting FOR EACH ROW with TRUNCATE — always rejected. Requesting any trigger on a view for TRUNCATE — rejected. Assuming INSTEAD OF works on plain tables — it is a view technique. Forgetting that BEFORE statement triggers on views exist but cannot supply row images.

Recap: Insert, update, and delete are flexible; truncate is statement-on-table only. With the grid memorized, two worked cell readings lock it in.

35.3.2 Worked reading of two cells

First reading: a BEFORE trigger on INSERT at row level on a table is allowed. That is the temperature-clamp pattern used later: check each incoming reading and fix it before it lands. Concretely, CREATE TRIGGER trg_temperature_value_check_at_insert BEFORE INSERT ON t_temperature_log FOR EACH ROW builds cleanly because the before-insert-row-on-table cell is a tick.

Second reading: a BEFORE trigger on TRUNCATE at row level is not allowed. The matching statement-level form on a table is the one to use, as the truncate-guard example shows when its first row-level attempt fails and the statement-level form succeeds. Concretely, ... AFTER TRUNCATE ON test_delete FOR EACH ROW is rejected, while the identical statement ending FOR EACH STATEMENT builds and then blocks the emptying with the worker exception.

Sense-check for both: if the cell needs per-row images (clamping one reading), it must be a row cell; if the event has no rows to visit (truncate sweeps the whole table at once), it must be a statement cell.

The bridge from here is judgment: knowing what is allowed says nothing about what is wise, which is exactly what the pros-and-cons tour covers next.

35.4 Pros and Cons of Triggers

35.4.1 Advantages

Why do teams reach for triggers at all? Because some rules must hold no matter which application, script, or manual fix touches the data — and only code that fires by itself can promise that.

Triggers are not hard to start writing because they read like stored procedures. Anyone at ease with procedures can move to triggers with a short learning step, which helps database teams adopt them fast. The body uses the same BEGIN ... END, IF ... END IF, RAISE NOTICE, and INSERT vocabulary, so the first trigger is mostly a matter of learning the two-step wrapper and the NEW/OLD images.

The wins cluster around five ideas: easy adoption from procedures, automatic auditing, thin callers over tested routines, batch validation across row sets, cross-database referential care, and always-on follow-on logic including summary recursion.

Basic auditing is the classic win. Using the deleted-row image and the inserted-row image inside trigger code, a small routine can copy removed or changed content into an audit table. A players table holds current names while a players-audit table grows a log of every rename. Deletes land in the audit copy. Updates store the change from old name to new name. That log answers who-changed-what questions without touching application code. The companion-book grades example shows the same shape: an AFTER UPDATE ... FOR EACH ROW function compares NEW.grade <> OLD.grade and inserts (OLD.student_id, OLD.course_id, now(), OLD.course, OLD.grade, NEW.grade) into history only when the grade really changed.

Trigger code can also call stored procedures and functions. Heavy logic lives in a tested procedure or function, and the trigger stays a thin caller. That split keeps trigger bodies short and lets one tested routine serve many triggers — for example one generic cancel worker bound to deletes, truncates, and key-column updates across several tables.

Batch validation is another win. Instead of checking one row at a time, trigger code can hold the inserted set and the deleted set and check the batch together. The inserted set mirrors rows about to land. The deleted set mirrors rows about to leave. Set checks across those images catch cross-row breaks with less per-row load. In PostgreSQL the per-row spelling uses NEW/OLD plus statement-level aggregation; in SQL Server the same idea is spelled directly as the inserted and deleted tables.

Cross-database referential care is a further win. Built-in constraints link objects inside one database with ease. Across databases they cannot reach. Because trigger code can call procedures and functions that point at objects in other databases, a trigger can mimic constraint behavior across that gap and keep data sound on both sides — for instance blocking an order insert when the matching customer row in a second database is missing.

Triggers also act as steel barriers that always run once defined and tested. When a column needs a complex default, or when a write to one table must always adjust another table, a trigger guarantees the follow-on step happens on every insert, update, or delete. That always-on habit is also what makes recursion useful: one write to a base table can wake further trigger instances that push summaries into several tables, which solves self-referencing and summary-table patterns such as daily counters maintained from a tweet-activity feed.

Real-world: human-resources and salary tables use always-on triggers so no pay change slips past the audit copy. Payroll auditors trust this precisely because the trigger cannot be bypassed by writing a new application path that forgets to log.

A shop writes orders through three paths: a web app, a bulk loader, and occasional manual fixes. Without a trigger, all three paths must remember to decrement stock and write the audit row — three chances to forget. With one AFTER INSERT trigger on orders, a single order for 5 units of item 7 decrements stock by 5 and appends one audit row no matter which path wrote it. The follow-on work happens once per write, on every write.

Recap: Triggers earn their keep wherever "on every write, without exception" is the requirement. The price of that promise is the disadvantage list next.

35.4.2 Disadvantages

Triggers hide from clients. They are invisible until something odd happens, such as an insert that reports success yet never appears in the table because a trigger quietly skipped it. Strict naming rules and written docs are the fix: with clear names and a trigger list per table, the hidden logic stays findable. Querying the catalog for triggers per table before debugging a "successful write that vanished" should become reflex.

Scope: Every disadvantage below is a cost of the always-on promise, not a reason to avoid triggers. Assumption: trigger bodies run inside the firing transaction, so slow or chained triggers slow the user's own write.

Triggers add time to every linked statement. The statement does not end until trigger work ends. A long or tangled trigger body therefore slows the user-facing write and can stall a busy production system. Small bodies help, as does splitting one giant trigger into several focused triggers that each do one task. On estates ingesting millions of rows per minute, even a few milliseconds of per-row trigger work multiplies into a visible slowdown — the companion performance study shows an insert benchmark slowing measurably once a per-row trigger is attached, while the trigger-free update path stays flat.

Audit-by-trigger can log too much. Because triggers always fire, an audit trigger captures changes from every path, including one-off manual fixes, not just the single procedure meant for auditing. Extra cleanup deletes or extra branch logic then become necessary, and both cost speed. An OUTPUT-style path may fit better when only one procedure should be audited. Choose deliberately: full-trail auditing wants the trigger; single-procedure auditing wants the narrower capture.

Nested triggers are hard to trace. One trigger wakes a second, which wakes a third, and the chain burns time and server load while resisting step-through tracing. Recursive triggers are harder still. These costs never outweigh trigger power when triggers are planned, named, secured, and kept short, but they punish careless stacking. A summary-table trigger that writes to a table with its own trigger is the classic surprise chain.

Pitfalls: Giant trigger bodies doing five jobs — split them. No per-table trigger inventory, so the next developer debugs blind. Audit triggers without the IF NEW.col <> OLD.col guard, logging every no-change touch. Unbounded nesting where table A fires table B fires table A.

Real-world: warehousing teams cap trigger chains explicitly and prefer a notify-then-materialize pattern — a tiny trigger sends a notification payload while an outside worker does the heavy counter math — keeping the write path lean.

Recap: Hidden logic, added latency, over-logging, and hard-to-trace chains are the four prices. Naming, small bodies, guarded logging, and planned chains pay them down. That judgment frames the Q&A that follows.

35.4.3 Student Questions and Answers

Q: If triggers always run, will an audit trigger capture one-off manual fixes too, not just planned procedure writes? A: Yes. That always-on behavior is the point and the price. Either accept the wider log, add branch logic that filters by path at some speed cost, or pick a narrower capture method when only one procedure should be audited. Several students circled this same worry — "can I audit just one path?" — and the answer is always a deliberate choice between full-trail (trigger) and narrow (procedure-level capture).

35.5 Trigger Key Points

35.5.1 No trigger on SELECT

If nothing changes, nothing fires. That single sentence rules out an entire category of mistaken trigger designs.

There is no trigger on a SELECT statement. The reason is direct: SELECT reads rows without changing them. Since trigger events are insert, update, delete, and truncate, a read has nothing for a trigger to attach to. Views are the fitting tool when read paths need shaping — a view with security_barrier and WITH LOCAL CHECK OPTION reshapes what readers see and what writers may write, without any trigger on the read itself.

Trigger events are writers only: INSERT, UPDATE, DELETE, TRUNCATE. Reads use views, not triggers.

The cross-system picture is consistent with one useful extra: MySQL likewise has no SELECT triggers, SQL Server has no SELECT triggers, and Snowflake/Databricks monitoring of reads moves to query-history views and access logs rather than triggers. If the goal is "log every read of the salary table," the answer in every system is an audit log at the access layer, not a row trigger.

A team asks for "a trigger that emails the manager whenever anyone views the pay table." The correct response is that no such trigger can exist — SELECT is not an event. The working substitute is a view exposing only safe columns plus access logging outside the row-trigger system. Sense-check: reading leaves no NEW or OLD behind, so there is nothing for trigger logic to hold.

Recap: No read event means no read trigger; shape reads with views. The companion fact is how many write triggers can coexist.

35.5.2 Many triggers, alphabetical order, many actions

Many triggers may share one table, view, or foreign table, subject to the reference table. All BEFORE triggers run first in alphabetical order, then the row or statement action runs, then all AFTER triggers run in alphabetical order. User-defined functions are welcome inside trigger bodies: build the function first, then bind it with a CREATE TRIGGER statement that names it. One trigger may also serve many actions, so a single trigger can listen for insert, update, and delete together instead of needing three near-twin triggers.

Three facts to carry: unlimited triggers per target within the reference-table limits, alphabetical firing inside each timing band with the action in the middle, and one trigger able to listen to several events at once (AFTER INSERT OR UPDATE OR DELETE).

Concretely, CREATE TRIGGER trg_audit_trigger AFTER INSERT OR UPDATE OR DELETE ON audit FOR EACH ROW is one trigger doing the work of three. Inside, the TG_OP variable tells the function which of the three woke it, so the same body can fill the old image only on update-or-delete and the new image only on insert-or-update. Naming stays load-bearing: when a repair trigger and a logging trigger share the event, the repair name must sort first.

Pitfalls: Creating three near-identical triggers where one multi-event trigger would do — triple the maintenance. Naming the logger so it sorts before the repairer and then trusting the log. Calling a trigger where the function name belongs in EXECUTE PROCEDURE.

Real-world: estates with dozens of triggers per busy table keep a per-table trigger register — name, timing, event, level, function, purpose — precisely because "many triggers" plus "alphabetical" makes order a design artifact worth writing down.

Recap: Many triggers, alphabetical bands, multi-action bindings. With the rules complete, the next section turns rules into the two-step build.

35.6 Steps to Create a Trigger

35.6.1 Step one: create the trigger function

Every PostgreSQL trigger is built in the same two moves: first the worker, then the wiring. Memorizing that order prevents the most common beginner error — trying to create the trigger before its function exists.

Every PostgreSQL trigger takes two steps. First, build a trigger function with CREATE FUNCTION. Second, bind that function to a table, view, or foreign table with CREATE TRIGGER. PostgreSQL insists on this order: the binding names a function that must already exist.

The function shape used throughout this topic is:

CREATE FUNCTION trigger_function_name() RETURNS trigger
LANGUAGE plpgsql AS
-- dollar-quoted body with BEGIN ... END block;
-- trigger logic for insert, update, delete, or truncate lives here;

The worker is an ordinary plpgsql function with one special mark: RETURNS trigger. Inside, a BEGIN ... END block holds the row logic, and the final RETURN decides the outcome — RETURN NEW lets the row proceed, RETURN NULL in a BEFORE trigger skips it, RETURN OLD suits deletes.

Name the function, declare that it returns the special trigger type, pick plpgsql as the language, and place the logic between the start and end of the body block. This routine is not yet a trigger. It is the worker a trigger will call. Plain SQL cannot be used here — trigger workers need the procedural features (IF, RAISE, assignment to NEW) that only plpgsql or another procedural language provides. The companion grades function shows the full spelling with a dollar-quoted body holding a BEGIN END block, an IF guard comparing NEW grade with OLD grade, an INSERT into history, and a final RETURN.

Name workers with an fn_ prefix (fn_players_name_changes_log) and triggers with a trg_ prefix (trg_players_name_changes) so the two roles never get confused at a glance. In MySQL this step looks different — the logic sits inline in CREATE TRIGGER with no separate function — but in PostgreSQL the split is mandatory and is what makes one tested worker reusable across many bindings.

Recap: Step one builds a RETURNS trigger worker in plpgsql. Step two wires it to a table.

35.6.2 Step two: bind it with CREATE TRIGGER

The binding shape is:

CREATE TRIGGER trigger_name
BEFORE INSERT ON table_name
FOR EACH ROW
EXECUTE PROCEDURE trigger_function_name();

The binding answers five questions in order: which trigger name (fixes alphabetical order), when (BEFORE/AFTER/INSTEAD OF), what (INSERT/UPDATE/DELETE/TRUNCATE, possibly several with OR), on what target, at what grain (FOR EACH ROW or FOR EACH STATEMENT), calling which worker.

Read it line by line. CREATE TRIGGER plus a name creates the trigger and fixes its alphabetical slot. The timing word BEFORE or AFTER fixes when it fires. The event word INSERT, UPDATE, DELETE, or TRUNCATE fixes what wakes it. The ON clause fixes the table, view, or foreign table. FOR EACH ROW picks row level while FOR EACH STATEMENT picks statement level. The last EXECUTE PROCEDURE line names the function built in step one. A common slip is naming another trigger there; the slot needs the function name, followed by empty parentheses when no trigger argument is passed. Modern PostgreSQL also accepts EXECUTE FUNCTION as the spelling; both invoke the same worker.

Bind the audit worker to the players table: CREATE TRIGGER trg_players_name_changes BEFORE UPDATE ON players FOR EACH ROW EXECUTE PROCEDURE fn_players_name_changes_log();. Insert two rows — nothing fires (wrong event). Update player 2 from Linda to Linda Two — the function runs once, sees NEW.name <> OLD.name, inserts one audit row holding Linda, and returns NEW so the master row becomes Linda Two. The two steps compose exactly as designed.

Column-scoped and conditional variants reuse the same shape: AFTER UPDATE OF id ON pk_table narrows the event to one column, WHEN (condition) narrows firing to matching rows, and EXECUTE PROCEDURE fn_cancel_with_message('...') passes a fixed literal into TG_ARGV[0].

Pitfalls: Binding before the function exists — create the worker first. Putting the trigger name where the function name belongs in the last line. Choosing AFTER when the job needs to reshape NEW — only BEFORE can do that. Forgetting FOR EACH ROW versus FOR EACH STATEMENT and then wondering why row images are missing.

Recap: Worker first, wiring second, five answers in the binding. With the pattern memorized, the players audit is the first full build.

35.6.3 Student Questions and Answers

Q: Which part of the statement picks row level versus statement level? A: The FOR EACH ROW clause picks row level and the FOR EACH STATEMENT clause picks statement level. Everything else in the statement stays the same shape. When in doubt, read just that clause — it alone decides whether the function runs per row or once per statement.

35.7 Data Auditing with a Players Trigger

35.7.1 Setup tables

Every audit design starts with the same split: one table holds the living truth, a second table holds the history. Keeping them separate means history never pollutes live reads.

The auditing pattern needs two tables. The master table holds live data:

CREATE TABLE players (
  player_id SERIAL PRIMARY KEY,
  name VARCHAR(100)
);

The audit table holds history:

CREATE TABLE players_audit (
  audit_id SERIAL PRIMARY KEY,
  player_id INT NOT NULL,
  name VARCHAR(100),
  edit_date TIMESTAMP
);

The players table is the current roster — one row per player, always fresh. The players_audit table is the diary — one row per rename, keeping the replaced name plus when it was replaced. The surrogate audit_id keeps history rows distinct even when one player is renamed many times. The work runs in the movies database under the movies schema in the source demo. Refreshing the table list shows both tables with their columns before any function work starts.

Master holds now (players); audit holds then (players_audit). The audit row stores the replaced value, not the fresh one, so the chain of past names stays readable.

Recap: Two tables, two roles — live versus history. Next, the worker that moves data between them.

35.7.2 Audit function with NEW and OLD

OLD is the row as it stood before the write; NEW is the row as it will be stored. On UPDATE both exist; on INSERT only NEW; on DELETE only OLD. The audit guard IF NEW.name <> OLD.name logs only genuine renames.

Trigger row images arrive as two names. OLD means the row as it stood before the update. NEW means the fresh row that will be stored. The audit logic compares the name column across those two images. When the names match, nothing is logged. When they differ, the old row is copied to the audit table.

CREATE OR REPLACE FUNCTION fn_players_name_changes_log()
RETURNS trigger LANGUAGE plpgsql AS
-- body block;
-- IF NEW.name is not equal to OLD.name THEN
--   INSERT INTO players_audit(player_id, name, edit_date)
--   VALUES (OLD.player_id, OLD.name, NEW.edit_date_source);
-- END IF;
-- RETURN NEW;

Line by line: the header declares a trigger worker in plpgsql; the IF NEW.name <> OLD.name THEN ... END IF guard skips no-change touches; the INSERT targets the audit table, never the master; OLD.player_id carries identity because the key itself is not changing; OLD.name carries the replaced value; the timestamp comes from the new image (in fuller builds, now()); the closing RETURN NEW hands the updated master row back so the rename lands.

Key details: the function returns the trigger type in plpgsql. The IF block ends with END IF. The insert targets the audit table, never the master table. Player identity comes from OLD.player_id because the key itself is not changing. The stored name is OLD.name, so the audit copy keeps the value being replaced. The edit moment comes from the new image. The last step returns NEW so the updated master row flows back to the caller. A two-column variant is also possible: keep both an old-name column holding OLD.name and a new-name column holding NEW.name so one audit row shows the full rename in one glance.

After creation the routine appears in the function list as a trigger function, with its full BEGIN ... END block visible in its properties. The companion grades build uses the identical skeleton with RETURN NULL in an AFTER trigger — both spellings are correct; BEFORE returns NEW to continue, AFTER row triggers may return NULL since the row is already stored.

Dialect extras, kept short: MySQL would write IF NEW.name <> OLD.name THEN inline in the trigger body with no separate function; SQL Server would join inserted against deleted on the key to find renames across the whole set at once.

Pitfalls: Logging inside a trigger that writes to its own master table without care — recursion. Forgetting the IF guard and logging every no-change touch. Storing NEW.name where the design needs OLD.name, so history shows the future instead of the past.

Recap: Compare images, copy the old value on genuine change, return to continue. The worker is ready to bind.

35.7.3 Binding trigger and live test

Bind the function to the master table with a row-level before-update trigger:

CREATE TRIGGER trg_players_name_changes
BEFORE UPDATE ON players
FOR EACH ROW
EXECUTE PROCEDURE fn_players_name_changes_log();

The name starts with a trigger prefix, the timing is BEFORE, the event is UPDATE, the target is players, the level is FOR EACH ROW, and the last line calls the audit function. Naming the function with an fn prefix and the trigger with a trg prefix keeps the two roles apart at a glance.

Live test one: insert two master rows named Adam and Linda. The trigger stays quiet because its event is update, not insert. A read of players shows both rows and nothing new lands in the audit table — 0 audit rows.

Live test two: run an update that renames player two from Linda to Linda Two. The function sees NEW.name differ from OLD.name, so it inserts an audit row holding player two, the name Linda, and the edit moment. A read of players shows Linda Two. A read of players_audit shows the captured Linda row — 1 history row.

Live test three: rename the same player to Linda Three. The audit table gains a second history row tracing Linda Two to Linda Three — 2 history rows. It stores the prior value, not the fresh value, so the chain of past names stays intact.

Live test four: run an update that writes Linda Three over Linda Three with no real change. The IF test finds the images equal, so no audit row is added — still 2 rows. Removing the IF test would log every touch even when nothing changed, which shows why the guard matters. Sense-check: history grows only on genuine renames.

Recap: Update-only binding, per-row visits, guard-controlled logging. The Q&A below locks in the two facts students trip on.

35.7.4 Student Questions and Answers

Q: Will plain inserts into the players table fill the audit table? A: No. The trigger listens for update only, so inserts land in the master table with no audit side effect. To audit inserts too, bind AFTER INSERT OR UPDATE or add a second trigger.

Q: Why does the audit row hold the old name instead of the new name? A: The audit copy answers what was replaced. Storing OLD.name preserves the prior value. A two-column form can store both OLD.name and NEW.name when the full rename must sit in one row.

35.8 Modify Data at INSERT Time

35.8.1 Temperature table and rule

This is the moment triggers stop being passive watchers. Here the trigger reaches into the incoming row and fixes it before storage.

This pattern proves triggers can reshape incoming rows, not just watch them. A log table stores sensor readings:

CREATE TABLE t_temperature_log (
  temperature_log_id SERIAL PRIMARY KEY,
  add_date TIMESTAMP,
  temperature NUMERIC
);

A short t prefix marks a table at a glance, matching a naming habit where views and materialized views get their own prefixes in large estates. The business rule for the demo: any inserted temperature below negative thirty is replaced with zero before it lands. Values at or above that floor pass through untouched. Negative thirty is the plausibility floor for this sensor — anything colder is treated as a faulty reading rather than real weather.

Visualize a number line from -100 to +30 with a gate at -30. Readings landing right of the gate walk through unchanged; readings landing left of the gate are carried to zero before they enter the table. One-sentence takeaway: the trigger is a gate, not a camera.

Recap: One log table, one floor rule — below -30 becomes zero. Next, the worker that enforces it.

35.8.2 Function using NEW

Insert and update triggers supply NEW; update and delete triggers supply OLD. Since this trigger watches inserts, the code reads and rewrites NEW, then returns it.

Insert and update triggers always supply a NEW image. Update and delete triggers supply an OLD image. Those images hold the row about to change. Since this trigger watches inserts, the code reads NEW.

CREATE OR REPLACE FUNCTION fn_temperature_value_check_at_insert()
RETURNS trigger LANGUAGE plpgsql AS
-- body block;
-- IF NEW.temperature is less than negative thirty THEN
--   NEW.temperature becomes zero;
-- END IF;
-- RETURN NEW;

In full plpgsql the core is IF NEW.temperature < -30 THEN NEW.temperature := 0; END IF; RETURN NEW;. The assignment operator is :=, not =. The body declares the trigger return type, uses plpgsql, wraps logic in a BEGIN ... END block, guards the rewrite with an IF ... END IF pair, and returns the possibly edited NEW row. An early run fails on a small assignment slip where the comparison line is written without the assignment, and fixing that line to assign zero makes the function build. Checking the function list confirms both demo functions now exist with their full blocks visible.

The companion temperature-classification function shows the same NEW-rewrite idea at larger scale: a CASE on NEW.max_temp assigns NEW.max_temp_group to Hot, Warm, Pleasant, Cold, Frigid, Inhumane, or No reading, then RETURN NEW — one insert lands with its label already attached, no second update needed.

Pitfalls: Writing NEW.temperature = 0 (a comparison) instead of NEW.temperature := 0 (an assignment) — the function builds or misbehaves. Returning NULL here by mistake, which would silently skip every insert. Expecting OLD on an insert — it does not exist.

Recap: Read NEW, rewrite it with :=, return it. Binding decides whether the rewrite lands.

35.8.3 Binding trigger and live test

CREATE TRIGGER trg_temperature_value_check_at_insert
BEFORE INSERT ON t_temperature_log
FOR EACH ROW
EXECUTE PROCEDURE fn_temperature_value_check_at_insert();

Timing must be BEFORE. An AFTER trigger would arrive after the row is already stored, which is too late to reshape the landing value. Event is INSERT, target is the temperature log, level is FOR EACH ROW so every reading is checked, and the last line calls the check function.

Live run: insert a reading of ten with a date of 2020-10-01. It passes because ten is above the floor — stored 10. Insert twenty. It passes for the same reason — stored 20. Insert negative one hundred. The statement still reports success with no error, yet a read of the table shows zero in that row because the trigger rewrote it — stored 0. Insert negative ten. It stays negative ten because negative ten sits above negative thirty — stored -10. The chain proves the point: allowed values land as written, while values below the floor arrive reshaped by database logic. Sense-check: four inserts, four stored rows, exactly one rewritten.

Recap: BEFORE INSERT ... FOR EACH ROW is the only binding that can clamp landing values. The Q&A cements the timing rule.

35.8.4 Student Questions and Answers

Q: Should this check run before or after the insert? A: Before. Only a BEFORE INSERT trigger can reshape the row ahead of storage. An after trigger would see a row that is already stored. If the job is "fix it silently," choose before; if the job is "log it or reject it loudly," after plus an exception also works.

35.9 Trigger Variables Display

35.9.1 Generic display function

When a write behaves oddly, the first question is "which trigger, on what table, at what timing, for which operation?" A display routine prints exactly those answers.

Triggers know a lot about themselves through built-in variables. A single generic display function can surface them, which also aids tracing when a write behaves oddly. The demo names it trigger_variables_display, returns the trigger type in plpgsql, opens a BEGIN ... END block, and returns the NEW row at the end.

The reusable bundle: trigger name (TG_NAME), table name (TG_TABLE_NAME), schema (TG_TABLE_SCHEMA), timing (TG_WHEN: before, after, instead-of), level (TG_LEVEL: row or statement), operation (TG_OP: insert, update, delete, truncate), plus argument count (TG_NARGS) and values (TG_ARGV). NEW/OLD carry the row; these carry the context.

Inside the block, RAISE NOTICE lines print text plus one variable each: trigger name from the name variable, relation name for the table the trigger runs on, table schema for the schema, the when value holding before, after, or instead-of timing, the level holding row or statement, the operation holding insert, update, delete, or truncate, plus argument count and argument values. Copy the block, run it, refresh the function list, and the display routine is ready to bind to many tables, views, or foreign tables rather than one. Because it never hard-codes a table or column, the same worker traces any target.

Recap: One generic worker surfaces every context variable. Binding it shows the bundle live.

35.9.2 Binding after insert and reading output

CREATE TRIGGER trigger_variable_display

FOR EACH ROW
EXECUTE PROCEDURE trigger_variables_display();

This binding uses AFTER INSERT at row level on the temperature log, in contrast to the earlier before-insert check on the same table. Note the ordering lesson live here: the before-check trigger (alphabetically earlier or not, both run in before band) already clamped the value, so the after-display sees the final stored row. Real-world: support teams bind this display worker temporarily to a misbehaving table, run one failing write, read the notice bundle, then drop it — a five-minute trace that beats guessing.

35.10 Disallow DELETE on a Table

35.10.1 Generic cancel function

Some tables must accept new rows and edits but never lose a row — staff, pay, ledger history. A guard trigger gives that policy an on-off switch that permission grants cannot match for speed.

Some tables accept adds and edits but must never lose rows, for example sensitive staff or pay tables. One path is to remove delete rights from all users including the public schema. A trigger path reaches the same end with easier on-off control: drop or enable the trigger instead of re-granting many rights.

Test bed:

CREATE TABLE test_delete (id INT);

Insert two rows with identifiers one and two. The goal: adds and edits stay legal while deletes always fail.

The generic worker branches on the timing variable: on AFTER it raises a hard exception naming operation, schema, and table; otherwise it raises a soft notice; outside the branch it returns null to cancel the row operation.

The generic worker is named along the lines of a cancel-operation routine. It returns the trigger type in plpgsql with a body block. Its core reads the when variable, which holds before, after, or instead-of. When the value is after, it raises an exception naming the blocked action: the operation variable for delete, plus table schema, a dot, and table name, so users see they are not allowed to delete rows in public dot test-delete. When the value is anything else, it raises a softer notice saying the delete on that row, schema, and table will not happen. Outside the branch it returns null, which cancels the operation. In full spelling the core reads IF TG_WHEN = 'AFTER' THEN RAISE EXCEPTION 'You are not allowed to % rows in %.%', TG_OP, TG_TABLE_SCHEMA, TG_TABLE_NAME; ELSE RAISE NOTICE 'Delete on row in %.% will not happen.', TG_TABLE_SCHEMA, TG_TABLE_NAME; END IF; RETURN NULL;.

Recap: One worker, two branches, null return cancels. The two bindings below exercise each branch.

35.10.2 After-delete binding and live test

CREATE TRIGGER trg_disallow_delete
AFTER DELETE ON test_delete
FOR EACH ROW
EXECUTE PROCEDURE generic_cancel_op();

Deleting the row with identifier one now raises the exception path: not allowed to delete rows in public dot test-delete, with delete drawn from the operation variable, public from the schema variable, and test-delete from the table variable. A follow-on read shows both rows still present — 2 rows before, 2 rows after — because the null return cancels the work even on the after path and the exception rolls the statement back. Sense-check: the delete reports an error, never silent success, so callers know the policy blocked them.

Recap: The after binding is the loud guard — an exception the caller cannot miss. The before binding is its quiet twin.

35.10.3 Before-delete binding and live test

A second trigger on the same table proves the other branch:

CREATE TRIGGER trigger_skip_delete
BEFORE DELETE ON test_delete
FOR EACH ROW
EXECUTE PROCEDURE generic_cancel_op();

Deleting again now takes the notice path instead of the exception path, because the when value is before rather than after. The notice says the delete on the row in public dot test-delete will not happen, built from the same operation, schema, and table variables. A follow-on read again shows rows one and two intact — still 2 rows. The before trigger cancels the delete, so the after trigger further down the chain is never reached: before band first, action skipped, after band skipped. The same worker shape extends to update guards and insert guards: change the listened operation and the same before-or-after branch blocks edits or adds on tables whose content must stay fixed. For example, BEFORE UPDATE with the same worker freezes edits while leaving deletes legal.

Pitfalls: Binding both guards at once in production and getting double messages — use one branch per policy. Expecting the after guard to run when a before guard already cancelled — cancelled means the chain stops. Using a notice where callers need a hard error — silent skips hide policy from applications that check only error codes.

Real-world: payroll estates keep the exception branch live and the notice branch for staging, so test runs show what would be blocked without aborting the batch.

Recap: Before is the quiet skip, after is the loud abort; one worker serves both. The Q&A captures why the demo builds both.

35.10.4 Student Questions and Answers

Q: Why build two delete triggers on one small test table? A: To show both branches of one generic worker. The after binding raises the hard exception branch, while the before binding raises the softer notice branch and stops the chain before the after trigger is reached. In real estates you deploy one of the two, matched to whether callers must see an error or just a notice.

35.11 Disallow TRUNCATE on a Table

35.11.1 Why truncate needs its own guard

Blocking single-row deletes feels safe — until one TRUNCATE empties the whole table in a blink. That command needs its own guard because it never visits rows one by one.

A truncate — a fast command that drops every row of a set of tables at once — matches an unqualified delete in effect but runs faster because it skips the row scan, and it gives disk space back at once with no later vacuum step. That speed suits large tables, yet it also means the delete guard alone is not enough: emptying the test table with a truncate call would sweep all rows away even while single-row deletes stay blocked. Extra care on production data is wise before any truncate test, with fresh rows re-added after trials.

Truncate sweeps the table as one statement-level event with no per-row images. It cannot be skipped by returning null from a row trigger — only a statement-level guard that raises an error stops it.

Unlike row-level delete guards, truncate cannot be skipped by returning null from a row-level before trigger. The working guard raises an error when truncate is tried. Picture truncate as draining a tank with one valve turn rather than bailing it cup by cup: there are no cups (rows) for a row trigger to intercept, only the valve turn (statement) to guard.

MySQL and SQL Server sharpen the contrast: neither offers a truncate trigger event at all, so the equivalent protection there must come from permissions or DDL guards. PostgreSQL is the system here that lets a trigger watch truncate — strictly at statement level.

Recap: Delete guards do not cover truncate; a statement-level error guard does. The live test proves the level rule.

35.11.2 Statement-level guard and live test

A first attempt binds the generic cancel worker at row level:

CREATE TRIGGER trg_disallow_truncate
AFTER TRUNCATE ON test_delete
FOR EACH ROW
EXECUTE PROCEDURE generic_cancel_op();

PostgreSQL rejects it: truncate with a row trigger is not supported. The reference table explains why: truncate lives only at statement level. Switching the last level clause fixes it:

CREATE TRIGGER trg_disallow_truncate
AFTER TRUNCATE ON test_delete
FOR EACH STATEMENT
EXECUTE PROCEDURE generic_cancel_op();

Trying to empty the table now raises the worker exception: not allowed to truncate rows in public test dot test-delete, with truncate drawn from the operation variable and the schema plus table names drawn from their variables. Because the when value is after, the exception branch fires and the emptying never completes. Before the attempt the table holds 2 rows; after the blocked attempt it still holds 2 rows. The failed row-level attempt plus the working statement-level attempt together are the proof that the reference-table cell for truncate is statement-only. Sense-check: if the error message names TRUNCATE and the table, the guard caught the right event at the right level.

Pitfalls: Re-trying FOR EACH ROW with truncate hoping a different timing helps — no timing allows it. Testing truncate guards on production tables — always use a scratch copy with re-added rows. Forgetting that TRUNCATE ... CASCADE and multi-table truncate still arrive as truncate events the same guard catches.

Real-world: data-warehouse teams bind truncate guards to every curated table so a stray script cannot wipe a fact table that took hours to load, while leaving staging tables unguarded for fast reloads.

Recap: Truncate demands FOR EACH STATEMENT; the rejected row form is itself the lesson. Next, the same guard-worker idea grows into a universal audit logger.

35.12 Universal Audit Trigger

35.12.1 Audit tables and captured fields

What if one audit worker could serve every table — narrow or wide, today and next year — without rewrites? Storing whole rows as JSON makes that possible.

A reusable audit trigger logs data changes in a steady, open way. Three facts form the minimum capture: who changed the data as a user name, when it changed as an add, edit, or event moment, and which operation changed it among insert, update, and delete.

Master table:

CREATE TABLE audit (id INT);

Audit log:

CREATE TABLE audit_log (
  username TEXT,
  add_time TIMESTAMP,
  table_name TEXT,
  operation TEXT,
  row_before JSON,
  row_after JSON
);

Six columns capture everything: acting user, UTC moment, dotted table name, operation, before-row as JSON, after-row as JSON. JSON is the trick that keeps one log shape fitting every source table.

User name comes from the session user of the current session, so the logged-in account that ran the write is stored. Time is normalized with the current timestamp shifted to the UTC zone, which keeps daylight-saving behavior steady across regions. Table identity joins trigger variables for table schema and table name with a dot, yielding values such as public dot audit. Operation comes from the operation variable. The before and after row images come from OLD and NEW, converted from row form to JSON form with the row-to-JSON helper so one generic shape fits any table: whatever columns the source row holds arrive as key-value pairs in the log. A row (id=1) lands as {"id": 1}; a wider row with ten columns lands as ten keys — no log-schema change needed.

The JSON choice is what makes the worker universal. Once built, it can attach to any table that needs auditing, capturing prior and fresh images without per-table column edits. The companion audit build shows the older per-column spelling with hstore and populate_record; JSON is the same idea in the modern, widely supported form.

Recap: Who, when, which table, which operation, before JSON, after JSON. Next, the function that fills them.

35.12.2 Function with OLD-row and NEW-row images

NEW and OLD are empty in opposite corners: no OLD on insert, no NEW on delete. Two guarded blocks respect that split, filling a null-started JSON holder only when its image exists.

NEW and OLD are empty in opposite corners: there is no OLD image on insert and no NEW image on delete. The function respects that split with two guarded blocks.

CREATE OR REPLACE FUNCTION fn_audit_trigger()
RETURNS trigger LANGUAGE plpgsql AS
-- declare old_row JSON set to null, new_row JSON set to null;
-- body block;
-- IF operation is in update or delete THEN old_row becomes row-to-JSON of OLD;
-- END IF;
-- IF operation is in insert or update THEN new_row becomes row-to-JSON of NEW;
-- END IF;
-- INSERT INTO audit_log(username, add_time, table_name, operation, row_before, row_after)
-- VALUES (session user, current timestamp at time zone UTC,
--   table schema joined with dot to table name, operation, old_row, new_row);
-- RETURN NEW;

Build order: declare two JSON holders starting at null, fill the old holder only on update or delete from OLD, fill the new holder only on insert or update from NEW, insert one log row with all six fields, and return NEW to hand control back. Comments inside the block label each stage so later readers see the plan at once. In full spelling the guards read IF TG_OP IN ('UPDATE','DELETE') THEN old_row := row_to_json(OLD); END IF; and IF TG_OP IN ('INSERT','UPDATE') THEN new_row := row_to_json(NEW); END IF;, with the log insert using session_user, current_timestamp AT TIME ZONE 'UTC', and TG_TABLE_SCHEMA || '.' || TG_TABLE_NAME.

Pitfalls: Calling row_to_json(OLD) on an insert where OLD is null — guard first. Declaring the holders without null starts and then writing null-handling branches by hand. Returning NULL in a BEFORE audit and accidentally cancelling the business write being audited.

Recap: Guarded JSON capture handles all three operations with one body. Binding makes it live.

35.12.3 One trigger for three operations and live test

CREATE TRIGGER trg_audit_trigger
AFTER INSERT OR UPDATE OR DELETE ON audit
FOR EACH ROW
EXECUTE PROCEDURE fn_audit_trigger();

One trigger covers three operations at row level after the change, bound to the master audit table. Alphabetical naming care matters here because later triggers can reshape rows before this logger sees them — the logger name should sort after any repair trigger on the same table.

Live run: insert identifier one. The master table gains one row. The log gains an insert entry with the logged-in user, a UTC moment with fractional seconds, table name public dot audit, operation insert, an empty before image, and an after image holding the fresh row as key-value pairs — row_before = null, row_after = {"id": 1}. The master row leaves while the log gains a delete entry whose before image holds two and whose after image is empty — {"id": 2} then null. Insert, update, and delete logging all check out, and the same worker can move to pay tables or any prized table by changing only the bound table. Sense-check: four writes produce exactly four log rows with the null on the correct side each time.

Real-world: finance and health estates attach this one worker to every regulated table, so auditors get a uniform six-column trail across the whole database instead of a different log shape per table.

Recap: One multi-event trigger plus JSON images equals a universal logger. The Q&A nails why JSON beats named columns.

35.12.4 Student Questions and Answers

Q: Why convert whole rows to JSON instead of logging named columns? A: JSON keeps the worker generic. Any source row, short or wide, lands as key-value pairs, so the same function and log shape serve every table without rewrites. 35.13 Conditional Triggers with WHEN

35.13.1 Rules of the WHEN clause

Sometimes the trigger should not fire on every write, only on writes matching a quick test — a value, a clock reading, a column comparison. WHEN adds that filter without touching the function.

A conditional trigger — a trigger whose statement carries a WHEN clause so the function runs only when the clause is true — filters firings without extra code in the function. The WHEN expression must yield a boolean. True runs the function. False, or a null turned to false by the trigger, skips the call. Subqueries are barred because a subquery would need testing before the trigger function is called. Column tests and function tests on columns are welcome.

WHEN (boolean expression) gates firing per row or per statement: true fires, false or null skips. Allowed: column comparisons and functions on columns or clock. Barred: subqueries.

In row-level triggers the expression may reference OLD and NEW, so WHEN (OLD.balance IS DISTINCT FROM NEW.balance) fires only on genuine balance changes — a declarative version of the IF guard inside the players audit. In statement-level triggers it may reference clock and session facts, as the Friday guard does. The null rule matters: WHEN (NEW.note = 'urgent') skips rows where note is null, because null is treated as false here.

Recap: WHEN filters cheaply outside the function; booleans and column tests yes, subqueries no. The Friday policy shows all three new tools at once.

35.13.2 Friday-afternoon policy design

Demo policy: no insert, update, delete, or truncate on a tasks table during Friday afternoon. Three fresh tools combine here: a WHEN event condition, statement level instead of row level, and a passed parameter inside the execute-procedure call.

Master table:

CREATE TABLE my_task (
  task_id SERIAL PRIMARY KEY,
  task TEXT
);

Generic worker:

CREATE OR REPLACE FUNCTION fn_cancel_with_message()
RETURNS trigger LANGUAGE plpgsql AS
-- body block;
-- RAISE EXCEPTION with a message slot filled from trigger argument zero;
-- RETURN NULL;

The worker reads its fixed message from the trigger argument (TG_ARGV[0]), raises it as an exception, and returns null. The binding supplies a different message per table without changing the function.

The worker shows a message and returns null to cancel. It reads the passed message through the trigger argument variable at index zero. An early draft fails because the raise line names the argument variable with no message text; raise needs a text slot first, such as a percent-sign format specifier, followed by the argument. Adding the format specifier slot fixes the build. In full spelling: RAISE EXCEPTION '%', TG_ARGV[0]; RETURN NULL;.

Trigger statement with condition, statement level, and parameter:

CREATE TRIGGER trg_no_update_on_friday_afternoon
BEFORE INSERT OR UPDATE OR DELETE OR TRUNCATE ON my_task
FOR EACH STATEMENT
WHEN (EXTRACT(DOW FROM CURRENT_TIMESTAMP) equals five
  AND CURRENT_TIME is later than twelve hundred hours)
EXECUTE PROCEDURE fn_cancel_with_message('No updates are allowed at Friday afternoon, rest now.');

Timing is before, events span insert, update, delete, and truncate so no path slips around the guard, target is the tasks table, level is statement, and the call passes a custom message that lands in trigger argument zero. The WHEN clause checks two facts: the day-of-week number drawn from the current timestamp equals five for Friday, and the current time sits past twelve hundred for afternoon. Only when both hold does the function run and raise. In real syntax the condition reads WHEN (EXTRACT(DOW FROM CURRENT_TIMESTAMP) = 5 AND CURRENT_TIME > TIME '12:00'). Statement level is deliberate: the rule cares about the clock moment, not per-row values, so one check per statement beats per-row checks.

Pitfalls: Putting the message variable in RAISE with no format specifier — the build fails. Using row-level WHEN (OLD.x ...) tests in a statement trigger where no row images exist. Listing only one event and leaving a side door (for example guarding inserts but forgetting truncates).

Recap: Condition plus statement grain plus parameter equals a reusable time-window guard. The live test shows both its quiet and firing states.

35.13.3 Live test and trigger drop

Day check first: extracting day-of-week and time from the current timestamp shows Tuesday in the demo run, so an insert lands normally and a read shows task one stored — 1 task row, no error. The guard stays quiet because its condition is false. To see the guard fire, the day test is switched to the current day value while the clock already reads past midday. A second insert then fails with the passed message about no updates on Friday afternoon — 0 new rows, exception carrying the custom text. The guard message can be reworded for any quiet window, such as blocking night writes after half past eight in the evening on a central database, by changing only the literal in the binding.

A trigger leaves through a drop call:

DROP TRIGGER trg_no_update_on_friday_afternoon ON my_task;

Dropping clears the table for later work and confirms the pattern: condition plus statement level plus parameter makes a flexible time-window guard. Sense-check: after the drop, the same insert succeeds again — proof the block came from the trigger, not the table.

Real-world: shared estates use this exact shape for maintenance windows — "no schema-touched writes on the central tables after 20:30" — with the message naming the on-call channel.

Recap: Quiet on Tuesday, firing on Friday afternoon, removable with one drop. The Q&A isolates the two rules students quote back.

35.13.4 Student Questions and Answers

Q: Why is a subquery banned inside WHEN? A: The subquery would need evaluation before the trigger function is called, which the trigger path does not support. Keep WHEN to column and function tests that yield true, false, or null. Move set logic inside the function body instead.

Q: Why use statement level for a time-window guard? A: The rule cares about the statement moment, not per-row values. One statement-level check blocks the whole write at lower cost than waking per row. Use row level only when the condition needs OLD or NEW.

35.14 Disallow Changes on a Primary Key

35.14.1 Table and column-level trigger

Keys label rows and anchor every reference pointing at them. Letting a key drift breaks joins, foreign keys, and history at once — so the safest design freezes keys after insert.

A primary key — the central column whose values label each row and anchor references — must often stay fixed after insert. The same shape guards any single column that must never change, such as a national ID, an employee number, or a ledger sequence.

CREATE TABLE pk_table (
  id SERIAL PRIMARY KEY,
  t TEXT
);

Insert two rows with text values T1 and T2. Reads show identifiers one and two beside their texts. The goal: inserts and deletes stay legal while any update touching the key column fails. Note the deliberate scope: edits to t remain free; only edits touching id are blocked. That precision is what column scoping buys over a blunt whole-row update guard.

UPDATE OF column_name narrows the trigger to writes that touch listed columns. Updates to other columns pass through untouched.

Recap: One key table, one frozen column, everything else free. The binding enforces exactly that.

35.14.2 Column-scoped binding and live test

Reuse the generic cancel worker and bind it to the key column only:

CREATE TRIGGER trg_disallow_pk_change
AFTER UPDATE OF id ON pk_table
FOR EACH ROW
EXECUTE PROCEDURE generic_cancel_op();

The AFTER UPDATE OF id phrase scopes the trigger to edits of the identifier column on the key table at row level. Trying to move identifier one to one hundred raises the worker exception: not allowed to update rows in the schema and table, drawn from the operation, schema, and table variables. Reads confirm the key is unchanged — still identifiers 1 and 2. Meanwhile UPDATE pk_table SET t = 'T9' WHERE id = 1 succeeds because it never touches id. Swap the column name and table name in the same shape to freeze any other single column, for example AFTER UPDATE OF salary_band ON staff. Sense-check: the guard fires on key-touching writes only, which is exactly the policy.

Dialect extras in one place: MySQL reaches the same end with BEFORE UPDATE ... IF NEW.id <> OLD.id THEN SIGNAL ... inline; SQL Server tests IF UPDATE(id) inside the trigger body. PostgreSQL's UPDATE OF id spelling is the cleanest of the three because the filter lives in the binding, not the body.

Pitfalls: Guarding the whole row with plain UPDATE when only the key must freeze — blocks legitimate edits to sibling columns. Rewriting keys inside trigger code instead of guarding them — the cautious-use section bans exactly that. Forgetting the guard does not cover deletes — add a delete guard separately if rows must never leave.

Real-world: order-number, invoice-number, and medical-record tables all freeze their keys this way so downstream references never dangle.

Recap: UPDATE OF id freezes one column and leaves the rest editable. That precision closes the guard series; what remains is the discipline of using guards well.

35.15 Cautious Use of Triggers

35.15.1 Good habits

Triggers repay care and punish haste. Every habit below is a scar someone earned — learn them here instead of in production at 2 a.m.

Triggers repay care and punish haste. They shine for auditing, logging, complex checks, and copy work, yet careless use breeds faults that resist tracing. Four habits keep them safe.

Four habits: never rewrite key or unique columns inside trigger code; never update tables being read in the same transaction; never read tables being updated in the same transaction; never pile heavy aggregation onto the updated table's write path.

First, never use triggers to rewrite key columns: primary keys, foreign keys, or unique columns. Guarding those columns against change is wise, as the prior section shows. Actively rewriting them inside trigger code is not. A trigger that silently renumbers keys orphans every foreign reference pointing at the old value.

Second, never update rows in tables being read during the same transaction. Third, never read from a table while that same table is updating inside the same transaction. Both patterns tangle reads and writes in one unit of work and invite wrong or half-fresh results — the classic mutating-table tangle where the trigger sees a half-written state and derives a confident wrong answer.

Fourth, keep heavy sums and rollups away from the table being updated. Aggregating or summarizing the same table mid-update piles heavy math onto a write path that should stay lean. Push the rollup to a statement-level after trigger on a summary table, a materialized view refresh, or an outside worker fed by notifications instead.

Scale adds weight to every habit. On a large estate taking in millions of rows minute by minute, trigger work on the write path can slow the whole flow. Planning, lean bodies, and purpose-built extensions for PostgreSQL ease that load. Use triggers where they earn their keep and leave them out where simpler paths do — a check constraint beats a trigger for "salary must be positive," a default beats a trigger for "fill created_at," and a foreign key beats a trigger for same-database references.

A team aggregates order totals inside a BEFORE UPDATE row trigger on the orders table itself: each of 10,000 row updates re-sums the table. Writes crawl. The fix moves the rollup out of the row path — a thin AFTER trigger sends a notification while a worker refreshes the summary once per batch. Same totals, write path stays lean. Sense-check: per-row work must be constant-time; anything scanning the table belongs outside the row trigger.

Pitfalls: Using triggers where constraints, defaults, or foreign keys already answer — heavier and harder to see. Letting trigger bodies grow into multi-page procedures — split and delegate to tested functions. Skipping the per-table trigger register on a busy table — the next incident review will ask for it.

Real-world: mature teams review every new trigger against this four-habit list plus a load test on production-sized writes before it ships, and they schedule periodic trigger audits because estates drift.

Exam note: Memorize the four habits as "no key rewrites, no write-while-reading, no read-while-writing, no heavy rollups on the write path." They are compact, quotable, and exactly the kind of list a checker rewards. With discipline covered, the lecture steps up from row triggers to server-level event triggers.

35.16 Event Triggers

35.16.1 How event triggers differ

Row triggers watch data — inserts, updates, deletes. Event triggers watch the database itself — creates, alters, drops. Different sky, different radar.

An event trigger — a server-level trigger that watches system events instead of binding to one table — stands apart from the row triggers above. Regular triggers bind to a table, view, or foreign table and watch row events. Event triggers bind to no table. They watch system-level data-definition moments across the server, which is why they carry the event name.

Event triggers are table-free, system-wide watchers of data-definition moments. They fire on command start, command end, table rewrite, and drop-object events, with before-or-after timing only and no instead-of form.

Five traits define them. They are data-specific and system-specific rather than table-bound. They catch system-level events. They allow before or after timing only, with no instead-of form. Their functions may use any language except SQL. They stay off in single-user mode by default, though a superuser may enable them. The language rule has a practical edge: plpgsql, plpython3u, or C are welcome, but plain SQL is not, because event-trigger logic needs procedural branching the SQL language cannot express.

The dialect picture is a genuine PostgreSQL extra: MySQL has no event triggers (its EVENTS are time schedulers, a different feature sharing only the name), SQL Server's counterpart is DDL triggers scoped to a database or server, and Snowflake/Databricks cover the ground with account-usage views and audit logs rather than triggers. Learning event triggers here is learning a PostgreSQL-only stewardship tool.

Recap: No table, system events, before-or-after only, any language but SQL. Next, what stewards use them for.

35.16.2 Usage settings

Event triggers suit database stewardship tasks. An audit trail of schema changes sends every create, alter, and drop note to one master log. Change prevention blocks risky table operations through trigger logic rather than table bindings. Scoped data-definition rights open or close whole command families for developer or support groups based on policy. Start and stop hooks aid speed study and fault tracing at server and query level by marking process edges. Copy hooks carry changed definitions toward a far site for replication, and chaining hooks cascade follow-on work. The next sections build the audit and prevention cases by hand.

A shared estate runs fifty developers against one database. Without event triggers, a dropped column is discovered when applications break. With an audit event trigger, the same DROP TABLE writes one log row — who, which command tag, when — and the team traces it the same afternoon. Prevention goes one step further: a start hook raises an exception for CREATE TABLE inside business hours, so the risky command never lands at all.

Recap: Audit trails, change prevention, scoped rights, study hooks, copy and chaining hooks. Creation rules make them buildable.

35.16.3 Creation rules

Three rules: the function must exist first, it must return event_trigger (never trigger or a row), and it returns no row value at all — the type alone signals the role.

An event trigger mirrors normal trigger creation with three special rules. First, a function must exist before the trigger can call it. Second, that function must return the special type event_trigger, not the plain trigger type of row triggers. Third, the function needs no row return: no null, new, or old value must come back. The return type only signals that the routine runs as an event trigger. Marking the function SECURITY DEFINER lets it run with definer rights so ordinary users cannot see or dodge the watcher while their true identity is still captured via session user.

Many event triggers may coexist, and they run in alphabetical order by name, so naming discipline carries over. Conditional event triggers are welcome through a WHEN clause with the same shape as row triggers, but the tests use low-level event facts such as command tags rather than subqueries. A trigger never runs inside a failed transaction: when a command fails, its linked start and end hooks do not run. When a start hook itself fails, the command never runs and no further event trigger fires. When an end hook fails, the data-definition effect rolls back, keeping the database sound just as any aborted transaction would.

Pitfalls: Declaring RETURNS trigger on an event function — must be event_trigger. Returning NEW or NULL as if it were a row trigger — return nothing. Trying CREATE OR REPLACE EVENT TRIGGER to reshape a watcher — only drop plus rebuild changes it. Testing guards on the live catalog instead of a scratch schema.

Recap: Worker first, event_trigger type, no row return, alphabetical co-existence. The events and variables give the worker its facts.

35.16.4 Events and variables

Four events: command start (before create, alter, drop), command end (after), table rewrite (before a rebuild forced by alter), drop-object (before the end step for drops). Two variables: the tag (which command, never the full text) and the event name.

Four events exist. A command-start event fires ahead of a create, alter, or drop command. A command-end event fires right after such a command finishes. A table-rewrite event fires just ahead of a table rebuild forced by commands such as alter-table or alter-type actions, a newer special case in PostgreSQL. A drop event fires just ahead of the command-end step for commands that drop database objects such as schemas, tables, or types. In short: start runs before typing enter takes effect, end runs after the work lands, rewrite guards rebuilds, and drop guards removals.

Two variables carry the facts functions need. The tag variable holds the command tag only, such as create table, drop table, or alter table, never the full command text. The event variable holds the event name: command start, command end, drop, or table rewrite. Later builds test the tag to limit a trigger to create-table work and log the event name for the trail. In code these arrive as tg_tag and tg_event, and the WHEN TAG IN ('CREATE TABLE') clause tests the tag before the function even runs.

CREATE TABLE t1 (id INT) with a start watcher scoped to CREATE TABLE: the tag reads CREATE TABLE, the event reads ddl_command_start, the function logs both plus the user and the moment. An ALTER TABLE in the same session does not wake this watcher — wrong tag, no fire. That tag test is what keeps the audit log focused instead of noisy.

Recap: Start, end, rewrite, drop; tag plus event name. The Q&A closes the two facts students misquote.

35.16.5 Student Questions and Answers

Q: Can an event-trigger function use plain SQL as its language? A: No. It may use any language except SQL, with plpgsql used throughout these builds. Plain SQL cannot express the branching an event guard needs.

Q: What happens when the data-definition command itself fails? A: Nothing further fires. A failed command skips its linked hooks, a failed start hook stops the command, and a failed end hook rolls the definition effect back. The database stays sound because hooks live inside the same transaction discipline as the command.

35.17 Audit Event Trigger Build

35.17.1 Log table and function

Who created that table, with which command, and when? One small log plus one watcher answers that for the whole server.

The audit-trail event trigger captures create, alter, and drop activity, here narrowed to table creation for clarity.

Log table:

CREATE TABLE audit_ddl (
  audit_id SERIAL PRIMARY KEY,
  username TEXT,
  event TEXT,
  ddl_command TEXT,
  ddl_add_time TIMESTAMPTZ
);

Event function:

CREATE OR REPLACE FUNCTION fn_event_audit_ddl()
RETURNS event_trigger LANGUAGE plpgsql SECURITY DEFINER AS
-- body block;
-- INSERT INTO audit_ddl(username, event, ddl_command, ddl_add_time)
-- VALUES (session user, event variable, tag variable, now);
-- RAISE NOTICE 'DDL activity is added';

Four logged facts: acting user, event name, command tag, moment. SECURITY DEFINER lets the watcher run with elevated rights while still recording the true caller.

The routine returns the event_trigger type in plpgsql and adds a security-definer mark so it runs with definer rights like a superuser. That mark hides the watcher from ordinary users while still capturing the true acting account through the session-user value. Event name comes from the event variable, command tag from the tag variable. Time uses now. No row value returns. An early draft misses the colon after the raise-notice text and fails to build; adding the colon fixes it — the correct line reads RAISE NOTICE 'DDL activity is added: %', tg_tag;. The built routine appears in the trigger-function list with its full block and comments intact.

Pitfalls: Forgetting the comma and format specifier in RAISE NOTICE — the classic build failure here. Declaring RETURNS trigger instead of RETURNS event_trigger. Expecting the full SQL text in the log — only the tag is available, by design.

Recap: Log table plus definer-rights watcher. Binding decides how wide the net is.

35.17.2 With and without WHEN, plus live test

Plain binding with no condition:

CREATE EVENT TRIGGER trg_event_audit_ddl
ON ddl_command_start
EXECUTE PROCEDURE fn_event_audit_ddl();

Event triggers bind to events, not tables, so the ON slot names the command-start event. This form logs every alter, create, and drop start.

Scoped binding with a tag condition:

CREATE EVENT TRIGGER trg_event_audit_ddl
ON ddl_command_start
WHEN TAG IN ('CREATE TABLE')
EXECUTE PROCEDURE fn_event_audit_ddl();

The WHEN TAG IN clause narrows the watcher to create-table work. More tags such as drop table or alter table can join the list.

Live test: the log starts empty — 0 rows. Creating a small test table both builds the table and prints the notice that DDL activity is added with the create-table tag. A read of the log shows the acting user, the command-start event, the create-table tag, and the moment — 1 row. An ALTER TABLE in the scoped form adds nothing, proving the tag filter. Cleanup uses a drop call:

DROP EVENT TRIGGER trg_event_audit_ddl;

Dropping matters because only a drop plus rebuild can change a trigger body; a replace-function call alone cannot reshape the bound trigger. Clearing the watcher also frees the schema for later builds. Sense-check: after the drop, creating another table writes no log row — the watcher is truly gone.

Real-world: platform teams keep the scoped audit watcher permanently live on production catalogs, giving every schema-change review a who-did-what trail without manual reporting.

Recap: Unscoped logs everything, tag-scoped logs one family, drop removes the watcher. The same skeleton next enforces a policy instead of just logging.

35.18 Prevent Schema Changes by Policy

35.18.1 Policy function

Logging tells you who changed the schema. Prevention stops the change from landing at all — but only if the hook runs before the command takes effect.

Policy: no tables created between nine in the morning and four in the afternoon. The same shape can guard a whole schema or single tables.

CREATE OR REPLACE FUNCTION fn_event_abort_create_table()
RETURNS event_trigger LANGUAGE plpgsql SECURITY DEFINER AS
-- declare current_hour INT;
-- current_hour becomes EXTRACT(HOUR FROM NOW);
-- body block;
-- IF current_hour is between nine and sixteen THEN
--   RAISE EXCEPTION 'Tables are not allowed to be created during 9 AM to 4 PM.';
-- END IF;

Read the clock, compare against the window, raise an exception inside it. Because the watcher sits on command start, the exception aborts the create before anything lands.

The routine returns event_trigger in plpgsql with a security-definer mark for superuser-level run rights, declares an integer holder for the hour, fills it by extracting the hour from now, and raises an exception inside the nine-to-sixteen window. No value returns. In full spelling the core is current_hour := EXTRACT(HOUR FROM NOW()); IF current_hour BETWEEN 9 AND 16 THEN RAISE EXCEPTION 'Tables are not allowed to be created during 9 AM to 4 PM.'; END IF;. The built routine appears in the function list ready to bind.

Recap: Clock read plus windowed exception. The trigger places it on the start event.

35.18.2 Event trigger and live test

CREATE EVENT TRIGGER trg_event_abort_create_table
ON ddl_command_start
WHEN TAG IN ('CREATE TABLE')
EXECUTE PROCEDURE fn_event_abort_create_table();

The watcher uses command start, because only a start hook can stop a create before it lands, plus the create-table tag condition and the abort worker. An end hook would arrive after the table already exists — correct for logging, useless for prevention.

Live test: a first create succeeds because the clock reads twenty-two, which is ten at night outside the window. Reading the hour from now confirms twenty-two. To see the guard fire, the window test is moved to cover twenty-two and the worker is rebuilt. A second create then fails with the polite exception that tables are not allowed in the window, and the table list confirms no third test table was built — still 2 test tables, never 3. When trials end, drop the event trigger so later work can create tables freely:

DROP EVENT TRIGGER trg_event_abort_create_table;

The normal-trigger drop twin removes row triggers by choice in the same housekeeping spirit. Sense-check: after the drop the identical create succeeds, proving the block was the watcher and not a permission.

Pitfalls: Binding prevention to command end instead of start — the table lands before the guard speaks. Leaving test windows in place after the demo — later creates fail mysteriously. Forgetting the tag filter so the window blocks alters and drops the policy never meant to touch.

Real-world: release teams enforce exactly this shape during business hours — schema changes queue outside the window while data writes flow normally — keeping shared estates stable when most users are active.

Exam note: Be able to explain why prevention needs ddl_command_start: start hooks can abort, end hooks can only record. That one sentence separates the audit build from the policy build and closes the lecture arc.
