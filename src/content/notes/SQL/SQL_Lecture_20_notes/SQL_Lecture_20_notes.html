# Exploring Array Functions

20.1 Arrays, Cardinality, and Element Access

20.1.1 What an array is

Hook: Why keep three phone numbers for one customer in a single cell instead of three rows? An ordered list inside one column answers that need — as long as position carries meaning.

An array (an ordered collection of values kept in fixed positions) is the starting point for everything in this set of notes. Think of a row of numbered mailboxes: mailbox 1, mailbox 2, mailbox 3. Each box holds its own letters, and swapping the contents of box 1 and box 3 changes who gets what. Order matters in the same way here. The first slot, the second slot, and the third slot each hold their own value, and shuffling the slots changes the meaning of the collection. An array can hold numbers, text, dates, or other values, as long as every element shares the array's base type. That single-base-type rule is strict: one array never mixes integers with text.

Formalize: array shape and cardinality. Write an array as \(A = [a_1, a_2, \dots, a_n]\), where each \(a_i\) is one element and \(n\) counts the slots. The cardinality of an array (the total count of elements it holds) is written \(card(A) = n\), where \(A\) is the array and \(n \in \mathbb{N}_0\) is a count that may be zero. An empty array \(A = []\) has cardinality \(card(A) = 0\). Any array that holds values has cardinality above zero. In short, the spoken rule from the session was: an array with empty values gives zero, and an array with values gives a count above zero. The cardinality of an array equals its element count.

PostgreSQL arrays are one-typed and one-based, and that pairing shapes every later section. Other systems split on both points, so keep the contrast in mind from the start.

System Array type rule Indexing Literal shape
PostgreSQL One base type per array Starts at 1 ARRAY[1,2,3]
Snowflake ARRAY of mixed VARIANT values Starts at 0 [123, 'ABC']
Databricks / Spark SQL Typed ARRAY<...> Starts at 0, access with arr[0] array(1,2,3)
MySQL No true array type; use JSON or a child table Path-based, not positional JSON_ARRAY(1,2,3)

Scope: The cardinality idea travels across systems, but the syntax does not. cardinality() and subscripts such as \(customers[2]\) are PostgreSQL here. Snowflake measures length with ARRAY_SIZE, Databricks with size(), and MySQL counts JSON elements with JSON_LENGTH. When a feed mixes text and numbers freely, that mixed shape points away from PostgreSQL arrays toward JSONB or Snowflake VARIANT.

Picture a number line of slots: positions 1, 2, 3 marked left to right, each holding one value, with an empty array drawn as a row of zero boxes. The takeaway from the picture is that cardinality counts boxes, never the values inside them.

Pitfalls: Treating an array like an unordered bag is the first trap — order is part of the data, so sorting or shuffling slots changes answers. Expecting mixed types in one PostgreSQL array is the second trap — the engine rejects or coerces them, while Snowflake would accept the same mix. Reading cardinality as the largest value is the third trap — cardinality counts slots, so \([10, 20, 30]\) has cardinality 3 even though 30 is the largest value.

Recap: An array is an ordered, one-typed list; cardinality counts its slots. That count feeds every size function in 20.7, and the positional idea feeds subscript reads next.

Logistics teams use ordered arrays for multi-stop delivery routes, where stop 1, stop 2, and stop 3 must stay in visit order. Telecom shops keep several phone numbers per customer in one array cell for the same reason. Both cases belong to the broader field of denormalized modeling, where a short ordered list lives inside the row instead of a joined child table.

20.1.2 Reading one element with a subscript

You reach a single element by placing its position, called a subscript, in square brackets after the array name. For an array named \(customers\), the expression \(customers[2] = a_2\) reads the second element. A subscript of three reads the third element, and a subscript of four reads the fourth element. The general shape is \(A[i] = a_i\), where \(i\) is an integer position starting at one and \(a_i\) is the element parked in slot \(i\). A subscript read of the i-th array element always names the array, the slot, and the value together.

Formalize: subscript reads. For \(A = [a_1, a_2, \dots, a_n]\) and an integer \(i\) with \(1 \le i \le n\), define the read \(A[i] = a_i\). Reading past the last slot gives NULL, not an error, which matters for the gap hunt in 20.14. This one-based rule is a PostgreSQL habit worth locking in early, because most general-purpose languages start at zero and that mismatch causes real bugs later: Python, PHP, Node.js, and Go all count from zero, so slot two here is slot one there.

Pitfalls: Carrying a zero-based habit into PostgreSQL is the main trap — customers[0] never holds the first name. Guessing a value for an out-of-range slot is the second trap — the engine returns NULL, which then poisons comparisons silently. Forgetting which end counts first is the third trap — subscripts always count from the left starting at one.

Recap: \(A[i] = a_i\) with \(i\) starting at one. Slot reads power the phone lookups in 20.14 and the position functions in 20.8. Exam note: PostgreSQL arrays start at one while Python, PHP, Node.js, and Go start at zero; rehearse the February-at-slot-two case from 20.8.

20.1.3 Worked examples

Worked examples. Example 1: name the cardinality. Take \(A = [10, 20, 30]\). Count the slots: first, second, third. So \(card(A) = 3\). Sense-check: three boxes, three values, count 3.

Example 2: name the empty case. Take \(A = []\). There is nothing to count. So \(card(A) = 0\). Sense-check: zero boxes always give zero.

Example 3: read by subscript. Take \(customers = [\text{Ali}, \text{Bina}, \text{Cid}]\). Then \(customers[1] = \text{Ali}\), \(customers[2] = \text{Bina}\), and \(customers[3] = \text{Cid}\). Sense-check: three names in order land in slots 1, 2, 3 with no shift.

20.2 Constructing Ranges

20.2.1 Range types and bound notation

Hook: How do you store "January 1 up to but not including January 31" without listing thirty days? A range holds the two endpoints plus a rule about each endpoint.

A range (a span of values between a lower bound and an upper bound) comes in several type flavors. The session names an integer range (int4range), a numeric range (numrange), and a date range (daterange), plus a range built from a timestamp expression plus an interval (tsrange). Each range stores a lower bound, written \(l\), and an upper bound, written \(u\). PostgreSQL also ships tstzrange and int8range in the same family, while multiranges cover split spans the session never uses.

Formalize: four bound shapes. How the endpoints behave is set by the brackets. A square bracket means the bound is closed, so the endpoint value belongs to the range. A parenthesis means the bound is open, so the endpoint value is left out. That gives four shapes: \([l, u]\) closed on both sides, \([l, u)\) closed below and open above, \((l, u]\) open below and closed above, and \((l, u)\) open on both sides. The constructor shape is range_type(l, u, 'flags'), where the flag string picks the bracket pair. The spoken rule from the session was exactly this: square brackets read as closed, parentheses read as open, and the left and right sides are chosen on their own. Four open and closed bound shapes cover every range in the session.

Discrete ranges normalize their bounds: [1, 6] over integers behaves like [1, 7) because 6 plus one step reaches the same edge. That explains why close-open is the default — it is the canonical display, not a data loss.

Bound flag Rendered shape Lower \(l\) Upper \(u\)
default \([l, u)\) kept left out
'[]' \([l, u]\) kept kept
'(]' \((l, u]\) left out kept
'()' \((l, u)\) left out left out

Scope: Range types with bound flags are a PostgreSQL specialty. MySQL has no range type — use BETWEEN or two columns. Snowflake has no range type either — its :daterange is only a Snowsight dashboard filter, not a stored value. Databricks and Spark SQL express the same span with two timestamp columns plus a BETWEEN check.

Picture a line segment from \(l\) to \(u\): solid dots mark closed ends that belong to the span, hollow dots mark open ends that sit just outside it. The takeaway is that each endpoint is decided on its own, so mixed shapes like \([l, u)\) are normal.

Pitfalls: Reading (1, 6) as holding 1 and 6 is the first trap — open ends exclude the endpoint itself. Assuming the default keeps both ends is the second trap — the default drops the upper end. Typing a stray comma into the three-argument constructor is the third trap — it breaks the call before any range is built, and removing the comma fixes the run.

Recap: A range stores \(l\) and \(u\) plus one open-or-closed choice per side; close-open is the default. Bounds feed the contains checks in 20.4 and 20.5.

Hotel booking systems store each stay as a date range so checkout day stays free for the next guest. Subscription billing stores each plan as a timestamp range plus an interval for the same reason. Both belong to validity modeling, where spans rather than single dates carry the business fact.

20.2.2 Worked examples

Worked examples. Example 1: default integer range. Run SELECT int4range(1, 6); with no bound flags. No third argument means the default close-open display applies. The system renders \([1, 6)\), closed below and open above, because close-open is the default behavior. Sense-check: 1 belongs, 6 does not, integers 1 through 5 are inside.

Example 2: closed numeric range. Run SELECT numrange(1, 6, '[]'); after asking for closed bounds on both sides. The first attempt errors on a stray comma in the statement, and removing the comma fixes it. The result renders \([1, 6]\), closed on both sides. Sense-check: both endpoints now belong, so 6 is inside.

Example 3: open date range. Run SELECT daterange('2010-01-01', '2020-12-20', '()'); with open bounds on both sides. The range skips the first day and runs up to the closing date, so the opening endpoint stays out of the span. Sense-check: January 1, 2010 is excluded while January 2, 2010 is inside.

Example 4: timestamp plus interval. Run SELECT tsrange(localtimestamp, localtimestamp + interval '8 days', '(]');. The spoken description was "local timestamp plus an interval of eight days," rendered with an open start and a closed end, so the start instant is left out while the end instant eight days out is kept in. Sense-check: the span covers just over eight days of instants ending exactly at the computed timestamp.

20.2.3 Questions and answers

Q: What does SELECT int4range(1, 6) show when no bound flags are given? A: It shows close-open, \([1, 6)\). The lower bound is closed and the upper bound is open, and that is the default. Think of it as the canonical display: 1 is in, 6 is out, integers 1 through 5 fill the span.

20.3 Constructing Arrays

20.3.1 The ARRAY keyword and type inference

Hook: What turns a bare list 1, 2, 3, 4 into a real array value the engine can store? One constructor word plus brackets.

An array literal is built with the ARRAY keyword (the constructor word that turns a bracketed value list into a true array) followed by square brackets holding values split by commas. The shape is ARRAY[value_1, value_2, value_3, value_4]. When the values carry no explicit type tag, PostgreSQL reads the values and picks a type on its own. This guessing step is called type inference (the system assigning a data type from the shape of the values). Integers infer to integer, decimals infer to numeric, and date expressions infer to date. An explicit cast such as ::float[] overrides the guess.

Formalize: constructor plus cast. The build rule is ARRAY[...] first, cast second: ARRAY[1, 2, 3, 4] builds an integer[], while ARRAY[1.5, 2.5, 3.5]::float[] builds a floating-point array shown as double precision. Date arithmetic stays inside the brackets: ARRAY[current_date, current_date + 5] builds a two-element date array where slot one holds today and slot two holds five days out. Snowflake builds the same idea with bare brackets [123, 'ABC'] over mixed VARIANT values, Databricks with array(1, 2, 3), and MySQL with JSON_ARRAY(1, 2, 3) since it has no native array type.

Scope: ARRAY[...] with ::type[] casts is PostgreSQL syntax. Do not carry it into Snowflake, Databricks, or MySQL — each builds arrays or JSON arrays its own way. Inference also picks the common type of the list, so mixing an integer with a decimal promotes the whole array to the wider type.

Picture a factory line: raw values enter on a belt, the ARRAY gate packs them into one box, and a type label is stamped on the box — guessed when missing, honored when supplied. The takeaway is that the label decides every later operation on the box.

Pitfalls: Forgetting the ARRAY keyword and writing bare [1,2,3] is the first trap — PostgreSQL reads bare brackets as subscripts, not constructors. Trusting inference for money or precise decimals is the second trap — cast explicitly instead. Mixing text with numbers and expecting the mix to survive is the third trap — PostgreSQL keeps one base type.

Recap: ARRAY[...] builds the array; inference guesses the type; casts override it. Constructor-built arrays feed every operator and function from 20.4 through 20.11.

Order-entry systems build ARRAY literals for line-item batches before inserting them. Analytics loaders build date arrays from current_date arithmetic for rolling windows. Both sit inside data staging, where quick literal arrays carry test and batch values into tables.

20.3.2 Worked examples

Worked examples. Example 1: plain integers. Run SELECT ARRAY[1, 2, 3, 4]; with no type tag. The system reads 1, 2, 3, 4 as integers and returns an integer array. Sense-check: four whole numbers with no decimals infer to integer.

Example 2: forced floating point. Run SELECT ARRAY[1.5, 2.5, 3.5]::float[]; with an explicit float tag. The system returns a floating-point array, shown as double precision, instead of an integer array. Sense-check: decimals plus an explicit tag always beat the integer guess.

Example 3: date array. Run SELECT ARRAY[current_date, current_date + 5];. The first slot holds the current date and the second slot holds five days past the current date, so the result is a two-element date array. Sense-check: today plus five days is still a date, so both slots share the date type.

20.4 Comparison Operators on Arrays and Ranges

20.4.1 How array comparison works

Hook: Two ordered lists look almost identical — how does the engine decide which one is "less" without a human eyeballing each slot?

Six comparison operators apply to whole arrays: \(=\) equals, \(<>\) not equal, \(<\) less than, \(>\) greater than, \(<=\) less than or equal, and \(>=\) greater than or equal. Each statement has a left-hand array, an operator, and a right-hand array, and the outcome is a single boolean. The engine weighs the left side against the right side element by element, \(A = [a_1, \dots, a_n]\) against \(B = [b_1, \dots, b_m]\), and reports \(true\) or \(false\).

Formalize: element-wise ordering. Comparison walks slots left to right and decides at the first slot that differs — the same lexicographic rule dictionaries use for words. Equality needs every slot to match: \(A = B\) exactly when \(n = m\) and \(a_i = b_i\) for every \(i\). Ordering finds the first \(k\) with \(a_k \ne b_k\) and orders by that pair; only when one array is a strict prefix of the other does length decide. So a shorter array counts as less than a longer array when it is a prefix of it: \(|A| < |B| \Rightarrow A < B\) where \(|A|\) is the element count of \(A\), and that shorter-is-less rule from the session covers the prefix case seen in the demo. Upper and lower bounds feed the same weighing step, so the engine can order arrays of different lengths without looking at any outside table. With \(>=\), the equals sign always sits on the right side of the bracket.

Scope: Whole-array <, >, <=, >= comparisons are PostgreSQL array semantics. Snowflake ARRAY and Databricks arrays compare with different rules or need ARRAY_SIZE plus element checks, and MySQL JSON arrays need JSON_CONTAINS or path tests. The PostgreSQL ordering rule assumes matching base types — mixed-type comparisons coerce or fail.

Picture two words in a dictionary: compare first letters, move right on ties, and the shorter word wins only when it is a prefix of the longer one. Arrays order the same way, slot by slot.

Pitfalls: Reading "shorter is less" as a universal length rule is the first trap — element values at the first differing slot decide first, and length only breaks prefix ties. Writing => instead of >= is the second trap — the equals sign always sits on the right side of the bracket. Expecting = to mean "shares any element" is the third trap — that is overlap (&&), covered in 20.5, not equality.

Recap: Arrays compare slot by slot with length breaking prefix ties; all six operators return one boolean. Ordering contrasts with the sharing tests (@>, <@, &&) in 20.5.

Version-control systems order change batches element by element the same way. Leaderboards rank score vectors slot by slot before falling back to length. Both belong to lexicographic ranking, where position-weighted order decides before size does.

20.4.2 Worked examples

Worked examples. Example 1: equal arrays. Run SELECT ARRAY[1,2,3,4,5] = ARRAY[1,2,3,4,5];. Every slot matches, so the result is \(true\). Sense-check: identical lists are equal.

Example 2: unequal arrays. Run SELECT ARRAY[1,2,3,4] = ARRAY[2,3,4,5]; after dropping the leading one on the right side. Slot one already differs (1 versus 2), so the result is \(false\). Sense-check: the first differing slot decides immediately.

Example 3: not-equal check. Run SELECT ARRAY[1,2,3,4,5] <> ARRAY[2,3,4,5];. The two sides differ, so the \(<>\) test reports \(true\). Repeating the same array on both sides of \(<>\) reports \(false\). Sense-check: different lists are not equal; identical lists are.

Example 4: ordering. Run SELECT ARRAY[1,2,3,4] < ARRAY[2,3,4,5];. Slot one decides (1 is less than 2), so the result is \(true\), and \(<=\) also reports \(true\). Run SELECT ARRAY[1,2,3,4] > ARRAY[2,3,4,5];. The left side is not heavier, so the result is \(false\), and \(>=\) reports \(false\) too. A side note from the session: with \(>=\), the equals sign always sits on the right side of the bracket. Sense-check: the lighter first slot carries the whole comparison.

Example 5: range contains with integers. Run SELECT int4range(1, 4) @> int4range(2, 3);. The span 1 to 4 holds the span 2 to 3, so the @> contains check reports \(true\). Sense-check: the inner span sits fully inside the outer one.

Example 6: range contains with dates. Run SELECT daterange(current_date, current_date + 30) @> current_date + 15;. The thirty-day span holds the date fifteen days out, so the result is \(true\). With January 1 as the start, plus thirty days reaches into February while plus fifteen days lands January 16, and January 16 sits inside the wider span. Sense-check: day 15 of a 30-day span is always inside.

Example 7: numeric range contains. Run SELECT numrange(1.0, 4.0) @> numrange(1.6, 4.0);. The wider numeric span 1.0 to 4.0 holds the inner span 1.6 to 4.0, so the @> check reports \(true\). Sense-check: both inner endpoints sit inside the outer endpoints, so containment holds.

20.4.3 Questions and answers

Q: Is ARRAY[1,2,3,4] less than ARRAY[2,3,4,5] when both hold four elements? A: Yes, the < test reports true. Slot one decides at once (1 is less than 2), so both < and <= report true while > and >= report false. Equal lengths never block the slot-by-slot walk.

Q: Does a thirty-day date range starting today contain today plus fifteen days? A: Yes, it reports true. The fifteen-day mark falls inside the wider thirty-day span, so the right-hand value sits within the left-hand range. Day 15 is strictly between day 0 and day 30.

20.5 Inclusion Operators

20.5.1 Contains, contained-by, and overlap

Hook: Equality asks "are these lists identical?" — but what asks "is every item of this list hiding inside that one?"

Three inclusion operators test how two arrays or two ranges share members. The @> operator means contains — every member of the right side appears in the left side, written \(A \supseteq B\). The <@ operator means contained by — every member of the left side appears in the right side, written \(A \subseteq B\). The && operator means overlap — the two sides share at least one member, written \(A \cap B \neq \emptyset\). Each test reads the left side and the right side together and returns a boolean. The same three symbols work on ranges: @> asks whether one span holds another, and && asks whether two spans share any ground.

Formalize: three sharing relations. For arrays \(A\) and \(B\): contains is \(A \supseteq B\) (every element of \(B\) sits in \(A\)); contained-by is \(A \subseteq B\) (every element of \(A\) sits in \(B\)); overlap is \(A \cap B \neq \emptyset\) (at least one shared element). Contains and contained-by are mirrors: \(A \supseteq B\) exactly when \(B \subseteq A\). Order inside the arrays never matters for these tests — only membership does, which is what separates them from the positional comparisons in 20.4.

Operator Name Set reading Array example that passes
@> contains \(A \supseteq B\) ARRAY[1,2,3,4] @> ARRAY[2,3,4]
<@ contained by \(A \subseteq B\) ARRAY['A','B'] <@ ARRAY['A','B']
&& overlap \(A \cap B \neq \emptyset\) ARRAY[1,2,3,4] && ARRAY[2,3,4]

Scope: @>, <@, and && over arrays and ranges are PostgreSQL operators. Snowflake tests array membership with ARRAY_CONTAINS and flattens with FLATTEN; Databricks uses array_contains and arrays_overlap; MySQL JSON arrays use JSON_CONTAINS and JSON_OVERLAPS. The set intuition travels; the symbols do not.

Picture two circles: one fully inside the other means contains, two circles touching in the middle means overlap, two circles apart means no overlap. The takeaway is that contains needs full coverage while overlap needs just one shared point.

Pitfalls: Pointing @> the wrong way is the first trap — the wide side always sits on the open mouth of the symbol. Reading overlap as full containment is the second trap — one shared member is enough for &&. Expecting position to matter is the third trap — [1,2] contains [2,1] because membership ignores order.

Recap: @> needs every right member on the left, <@ is its mirror, and && needs one shared member. Inclusion tests complement the ordering tests in 20.4 and power the row hunts in 20.18.

Access-control lists check whether a user's permission array contains every required scope with @>. Tag systems check whether two articles overlap on at least one tag with &&. Both belong to membership filtering, where sharing rather than order decides the answer.

20.5.2 Worked examples

Worked examples. Example 1: integer contains. Run SELECT ARRAY[1,2,3,4] @> ARRAY[2,3,4];. The values 2, 3, 4 all appear on the left, so the result is \(true\). Sense-check: every right member is found on the left.

Example 2: text contained-by. Run SELECT ARRAY['A','B'] <@ ARRAY['A','B'];. Reading right to left, every left member appears on the right, so the result is \(true\). Trying a member such as C behaves the same way when it is present, while a fully different set of values reports \(false\). Sense-check: identical sets contain each other both ways.

Example 3: overlap true case. Run SELECT ARRAY[1,2,3,4] && ARRAY[2,3,4];. The values 2, 3, 4 sit in both arrays, so the overlap test reports \(true\). Sense-check: three shared members are more than the one needed.

Example 4: overlap false case. Run the same shape against a fully different set of numbers. Nothing is shared, so the result is \(false\). Sense-check: disjoint sets never overlap.

Example 5: range contains again. Run SELECT int4range(1, 4) @> int4range(2, 3);. The span 2 to 3 sits inside 1 to 4, so the result is \(true\). Sense-check: both inner endpoints sit inside the outer span.

Example 6: date contains again. Run SELECT daterange(current_date, current_date + 30) @> current_date + 15;. The current-date-plus-thirty-days span contains current-date-plus-fifteen-days, so the result is \(true\). Sense-check: day 15 of a 30-day span is inside.

Example 7: numeric overlap. Run SELECT numrange(1.6, 4.2) && numrange(0.0, 4.0);. The pair 1.6 to 4.2 against 0 to 4 shares the whole stretch 1.6 to 4.0, so the && test reports \(true\). Sense-check: shared ground exists, so overlap passes even though neither span holds the other.

20.5.3 Questions and answers

Q: Does ARRAY[1,2,3,4] contain ARRAY[2,3,4]? A: Yes, true. The values 2, 3, and 4 each appear in the left array, so the @> contains test passes. Order plays no role — membership alone decides.

20.6 Array Concatenation with Operators and Functions

20.6.1 Joining two arrays

Hook: Two batches arrive separately — morning codes and evening codes. How do you glue them into one list without rebuilding the table?

The || operator, called the concatenation operator (the joining link that glues arrays end to end), merges two arrays into one. For \(A = [a_1, a_2]\) and \(B = [b_1, b_2]\), the join is \(A \mathbin{||} B = [a_1, a_2, b_1, b_2]\). The same join is sold as a built-in function named array_cat, which takes the two arrays inside parentheses split by a comma: array_cat(A, B). Curly braces in the output mark array values, with the element type shown inside. Concatenation never sorts or drops repeats — it parks the left array first and the right array after it.

Formalize: array-array join. For \(A = [a_1, \dots, a_n]\) and \(B = [b_1, \dots, b_m]\), the concatenation join of two arrays end to end is \(A \mathbin{||} B = [a_1, \dots, a_n, b_1, \dots, b_m]\), with total length \(n + m\). The function twin array_cat(A, B) returns the identical value. Joining stays valid when the two sides differ in type (the engine resolves a common type), so integers and strings can mix through the join methods even though keeping one shared type is the tidy habit. Snowflake concatenates with ARRAY_CAT, Databricks with concat or array_union, and MySQL merges JSON arrays with JSON_MERGE_PRESERVE.

Scope: || between arrays plus array_cat is the PostgreSQL spelling. The same || glues text in PostgreSQL but means logical OR in MySQL, so read the operator by context. Mixed-type joins resolve to a common type rather than a truly mixed array — genuinely mixed feeds belong in JSONB or Snowflake VARIANT.

Picture two trains coupling: cars \(a_1, a_2\) keep their order, cars \(b_1, b_2\) keep theirs, and the joined train is simply both in sequence. The takeaway is that concatenation preserves order and repeats.

Pitfalls: Expecting concatenation to drop duplicates is the first trap — repeats survive, unlike UNION. Reading the result as sorted is the second trap — the left array always comes first. Mixing types and expecting the tidy single-type habit to hold is the third trap — the join succeeds but the type widens.

Recap: || and array_cat(A, B) glue two arrays end to end with length \(n + m\). Array-array joins pair with the element-at-an-end joins next.

Staging tables glue an old batch of product codes to a new batch of codes with this join before loading. Event pipelines append each hour's tag array to the running day array the same way. Both belong to batch assembly, where separate arrivals merge into one ordered list.

20.6.2 Worked examples

Worked examples. Example 1: operator join. Run SELECT ARRAY[1,2,3] || ARRAY[4,5,6];. Left cars 1, 2, 3 couple with right cars 4, 5, 6. The result is the joined integer array \(\{1,2,3,4,5,6\}\). Sense-check: three plus three slots give six slots in order.

Example 2: function join. Run SELECT array_cat(ARRAY[1,2,3], ARRAY[4,5,6]);. Same two arrays inside the function call. The result matches the operator form exactly: \(\{1,2,3,4,5,6\}\). Sense-check: operator and function are twins.

Example 3: mixed types allowed. Join an integer array with a text array through either join method. The call stays valid and the engine resolves a common type, so integers and strings can mix through the join methods even though keeping one shared type is the tidy habit. Sense-check: the join never rejects on type alone — it widens instead.

20.6.3 Adding one element at the start or the end

One element joins an array through the same || link. Placing the element on the left, as in 4 || ARRAY[1,2,3], parks the new value at the front and yields {4,1,2,3}. Placing the element on the right, as in ARRAY[1,2,3,4] || 4, parks the new value at the back. Two built-ins mirror the two ends: array_prepend(element, array) adds at the front, and array_append(array, element) adds at the back. Notice the flipped argument order. Prepend wants the element first and the array second, while append wants the array first and the element second. Handing prepend the array first raises an error, because the function reads its inputs in a fixed order. That flipped prepend argument order, which errors on array-first calls, is the session's flagged annoyance.

Worked examples. Example 4: prepend pair. Run SELECT array_prepend(4, ARRAY[1,2,3]);. Element 4 goes first, array second. The result is \(\{4,1,2,3\}\), matching the 4 || ARRAY[1,2,3] form. Sense-check: front parking puts 4 before 1.

Example 5: append pair. Run SELECT array_append(ARRAY[1,2,3], 4);. Array first, element 4 second. The result is \(\{1,2,3,4\}\), matching the ARRAY[1,2,3] || 4 form. Sense-check: back parking puts 4 after 3.

Scope: array_prepend and array_append take scalars plus arrays in PostgreSQL. Snowflake grows arrays with ARRAY_APPEND and ARRAY_PREPEND in the same flipped order; Databricks uses array_prepend and array_append too. Exam note: array_prepend reads the element first while array_append reads the array first; rehearse the flipped order.

20.7 Array Metadata Functions

20.7.1 Dimensions, length, bounds, and size

Hook: A packed box arrives with no label. How do you ask the box itself how many compartments it has and how full each one is?

Arrays carry facts about their own shape, and a family of metadata functions (helpers that report on size and layout rather than on stored values) reads those facts out. The array_ndims function reports the count of dimensions, written \(ndims(A) = d\), and always returns an integer. The N stands for number and the D for dimension. The array_dims function reports the same layout as text, such as [1:2][1:1], instead of as an integer. The array_length function reports the length of one requested dimension, written \(len(A, 1) = n\), and always returns an integer. The array_lower and array_upper functions report the lower and upper bound of one requested dimension, each returning an integer. The cardinality function reports the total element count, written \(card(A) = n\).

Formalize: the six shape readers. For an array \(A\) and a dimension \(k\): \(ndims(A) = d\) counts dimensions; \(array\_dims(A)\) prints the same layout as text like [1:2][1:1]; \(len(A, k) = n\) counts slots in dimension \(k\); \(array\_lower(A, k)\) and \(array\_upper(A, k)\) give the slot bounds of dimension \(k\); and \(card(A) = n\) counts every element across all dimensions. Dimension count, requested length, bounds, and cardinality together describe any layout. An untyped empty literal such as '{}' errors on a length check because the engine cannot pin down the element type — cast it ('{}'::int[]) and the length returns NULL, because no data sits inside. For one-dimensional arrays, length and cardinality agree.

Function Reads Returns on ARRAY[1,2,3,4]
array_ndims(A) dimension count 1
array_dims(A) text layout [1:4]
array_length(A, 1) slots in dimension 1 4
array_lower(A, 1) / array_upper(A, 1) slot bounds 1 / 4
cardinality(A) total elements 4

Scope: These six names are PostgreSQL. Snowflake reports shape with ARRAY_SIZE and inspects bounds via FLATTEN output columns; Databricks uses size(); MySQL counts JSON elements with JSON_LENGTH. Only PostgreSQL needs the empty-literal cast before measuring.

Picture a warehouse rack: array_ndims counts how many axes the rack has, array_dims prints the shelf labels, array_length counts boxes on one shelf, bounds give the first and last shelf numbers, and cardinality counts every box in the rack. The takeaway is that each function answers one shape question and never reads stored values.

Pitfalls: Asking for a missing dimension is the first trap — array_length(A, 2) on a one-dimensional array returns NULL, not zero. Reading NULL length as "empty" is the second trap — it means "no such dimension," while the cast empty array also yields NULL for "no data." Expecting bounds to reflect values is the third trap — swapping an element to 40 keeps the upper bound at 4, because slots not values are counted.

Recap: Six readers report dimensions, layout text, per-dimension length and bounds, and total cardinality. Shape answers feed the search and modification functions in 20.8 and 20.9.

Warehouse systems probe pallet arrays for dimension counts before unpacking. Ingestion monitors use cardinality to flag short or swollen batches. Both belong to shape auditing, where size metadata gates the heavier value logic.

20.7.2 Worked examples

Worked examples. Example 1: dimension count of a nested pair. Run SELECT array_ndims(ARRAY[[1,2]]);. The nested block reads as two dimensions, so the result is 2. Sense-check: a list inside a list needs two axes.

Example 2: wider nested blocks. Run SELECT array_ndims(ARRAY[[1,2,3],[4,5,6]]);. More elements sit inside, but the layout still has two blocks, so the dimension count stays 2. A three-block nesting reports 3. Sense-check: width never adds dimensions — only nesting does.

Example 3: text layout. Run SELECT array_dims(ARRAY[[1,2]]);. The result is text shaped like [1:2][1:1], one chunk per dimension. Sense-check: two chunks confirm two dimensions.

Example 4: plain length. Run SELECT array_length(ARRAY[1,2,3,4], 1);. The first dimension holds four slots, so the result is 4. Sense-check: four slots give length 4.

Example 5: empty array needs a cast. Run SELECT array_length('{}', 1); with no type tag and the engine complains it cannot pin down the element type. Cast it with SELECT array_length('{}'::int[], 1); and the result is NULL, because no data sits inside. Sense-check: typed-but-empty means "nothing to measure."

Example 6: values do not matter. A length check over negative values behaves the same as over positive values, because the function counts slots and never reads the stored numbers. Sense-check: shape readers ignore values by design.

Example 7: lower bound. Run SELECT array_lower(ARRAY[1,2,3,4], 1);. The requested dimension starts at slot one, so the result is 1. A two-element array reports 1 the same way. Sense-check: default arrays always start at one.

Example 8: upper bound. Run SELECT array_upper(ARRAY[1,2,3,4], 1);. Four slots sit in the dimension, so the result is 4. Swapping an element value to 40 and rerunning still reports 4, which proves the function counts dimension slots and never compares stored values. Sense-check: values change, shape stays.

Example 9: cardinality. Run SELECT cardinality(ARRAY[1,2,3,4]);. The result is 4. Adding one more element lifts it to 5. Length and cardinality track each other closely here, with cardinality reading as the total element count of the array. Sense-check: one-dimensional length and total count agree.

20.8 Array Search Functions

20.8.1 First match with array_position

Hook: A wanted code hides somewhere in a thousand-element array. How do you ask for its slot number instead of scanning by eye?

The array_position function returns the subscript of the first hit for a wanted value, written \(pos(A, x) = i\), where \(A\) is a one-dimensional array, \(x\) is the wanted element, and \(i\) is the slot number of its first appearance. An optional third input sets the slot where the hunt starts, so the call reads array_position(array, element, start). The array must be one-dimensional. Multi-dimensional hunting needs different methods. A clean miss returns NULL.

Formalize: first-hit search. For one-dimensional \(A = [a_1, \dots, a_n]\) and wanted \(x\), define \(pos(A, x) = i\) as the smallest \(i\) with \(a_i = x\), or NULL when no slot matches. The three-argument form \(pos(A, x, s)\) starts the walk at slot \(s\) instead of slot one. Indexing starts at one in PostgreSQL. That single fact explains most confusion, because Python, PHP, Node.js, and Go all start at zero. In those languages February in a four-month list would sit at slot one, but here it sits at slot two. The zero-based habit from Python and PHP fails here — PostgreSQL starts at one.

Scope: array_position is PostgreSQL. Snowflake finds positions with ARRAY_POSITION (zero-based) or ARRAY_CONTAINS for a boolean; Databricks uses array_position (one-based like PostgreSQL); MySQL searches JSON arrays with JSON_SEARCH or MEMBER OF. Always check the base before porting a slot number.

Picture a row of lockers numbered from 1: open each door left to right, stop at the first locker holding the wanted jersey. The takeaway is that the search stops at the first hit and later twins are never opened.

Pitfalls: Quoting a number like '3' when the array holds integers is the first trap — types must match. Expecting later duplicates to appear is the second trap — only the first hit returns. Forgetting the start slot counts from one is the third trap — start 3 means "slot three onward," not "skip three."

Recap: \(pos(A, x) = i\) gives the first slot holding \(x\), counting from one, or NULL on a miss. First-hit logic pairs with the all-hits twin next.

Fraud teams probe transaction-code arrays to find where a flagged code first lands. Feature pipelines check the slot of a category inside long subquery-built arrays. Both belong to positional lookup, where "where first" matters more than "whether."

20.8.2 Worked examples

Worked examples. Example 1: month hunt. Run SELECT array_position(ARRAY['January','February','March','April'], 'February');. Walk: January misses, February hits. The result is 2: January is first, February is second. Sense-check: one-based counting puts February at two.

Example 2: number hunt. Run SELECT array_position(ARRAY[1,2,3,4], 3); with no quotes around the numeric value. Counting 1, 2, 3 gives the result 3. Sense-check: the third slot holds 3.

Example 3: duplicates keep the first hit only. Take ARRAY[1,2,2,3,4], where 2 appears twice. Run SELECT array_position(ARRAY[1,2,2,3,4], 2);. The result is 2, the first appearance, and the later twin is skipped. Sense-check: the walk stops at the first 2. A long array arriving from a subquery can be probed this way to find where a wanted code first lands.

Example 4: start slot shifts the answer. Run SELECT array_position(ARRAY[1,2,2,3,4], 2, 3); with the hunt starting at slot three. Slots one and two are never opened. The result is 3, the twin that sits at or past the start slot. Sense-check: starting at three skips the first twin.

20.8.3 All matches with array_positions

The plural array_positions function returns every slot holding the wanted value, written \(posns(A, x) = \{i, j\}\). The call reads array_positions(array, element). It returns an array of slot numbers, so a clean miss gives an empty array rather than NULL.

Worked examples. Example 5: twin hunt. Run SELECT array_positions(ARRAY[1,2,2,3,4], 2);. Slots two and three both hold 2. The result is \(\{2,3\}\), both slots holding 2. Sense-check: every twin is reported.

Example 6: clean miss. Run SELECT array_positions(ARRAY[1,2,2,3,4], 10);. Nothing matches, so the result is empty. Sense-check: no hit means no slots, not a NULL.

20.8.4 Questions and answers

Q: Why does February come back as position 2 instead of position 1? A: PostgreSQL arrays start at one, so January is first and February is second. A zero-based language would call February slot one, but here slot one is January and slot two is February.

Q: What happens when the wanted value appears twice? A: array_position reports only the first appearance, such as slot 2 for the twin 2s in ARRAY[1,2,2,3,4]. A start argument of 3 moves the answer to slot 3, and array_positions reports every hit as {2,3}.

20.9 Array Modification Functions

20.9.1 Quick review of the set

Hook: The list is almost right — one code too many, one value outdated. Which helpers fix a list without rewriting it?

Five helpers reshape arrays: array_cat glues two arrays, array_append parks one element at the back, array_prepend parks one element at the front, array_remove drops every copy of a value, and array_replace swaps every copy of one value for another. Removal and replacement each demand a one-dimensional array. The flipped prepend argument order — element first, array second, unlike append — is flagged as an annoyance a later version may line up.

Formalize: the five reshapers. For arrays \(A, B\) and elements \(x, y\): array_cat(A, B) glues end to end; array_append(A, x) parks \(x\) at the back; array_prepend(x, A) parks \(x\) at the front with the element first; array_remove(A, x) drops every slot holding \(x\); array_replace(A, x, y) swaps every \(x\) for \(y\). Removal and replacement are all-copies operations: twin values all leave or all swap, never just the first. Snowflake mirrors cat, append, and prepend with ARRAY_CAT, ARRAY_APPEND, and ARRAY_PREPEND; Databricks offers concat, array_append, and array_remove; MySQL edits JSON arrays with JSON_ARRAY_APPEND, JSON_REMOVE, and JSON_REPLACE.

Scope: These five names with all-copies removal and replacement semantics are PostgreSQL. Ports exist elsewhere but spellings and copy-rules differ, so verify before assuming twin handling travels.

Picture an editor's desk: glue two strips together, tape a card to either end, lift every red card off the strip, or swap every red card for a blue one. The takeaway is that cat, append, and prepend grow the list while remove and replace clean it in full.

Pitfalls: Calling array_prepend array-first is the first trap — it errors because the element must come first. Expecting array_remove to drop only one copy is the second trap — every copy leaves. Swapping argument order in array_replace is the third trap — old value first, new value second.

Recap: Five helpers glue, grow at either end, drop all copies, or swap all copies — all on one-dimensional arrays. Modification functions pair with the concatenation operators in 20.6 and the slot updates in 20.15. Exam note: array_prepend reads the element first while array_append reads the array first; rehearse the flipped order.

Catalog teams append each season's new tags and remove discontinued codes in one pass. Notification systems prepend urgent flags and replace stale status values across user arrays. Both belong to list maintenance, where whole-list edits beat row-by-row rewrites.

20.9.2 Worked examples

Worked examples. Example 1: gluing month names. Run SELECT array_cat(ARRAY['January','February'], ARRAY['March','April']);. Both sides are string arrays. The result is \(\{January,February,March,April\}\). Sense-check: two plus two slots give four in order.

Example 2: append at the back. Run SELECT array_append(ARRAY[1,2,3], 4);. The integer array grows to \(\{1,2,3,4\}\), with 4 parked at the end inside curly braces. Sense-check: the new value lands after 3.

Example 3: prepend at the front. Run SELECT array_prepend(4, ARRAY[1,2,3]);. The element comes first and the array second, which is the reverse of append, and the result is \(\{4,1,2,3\}\). The session flags this flip as an annoyance: prepend ought to read the array first like append does, and a later version may line them up. Sense-check: the new value lands before 1.

Example 4: drop a value. Run SELECT array_remove(ARRAY[1,2,3,4], 4);. The 4 leaves and \(\{1,2,3\}\) remains. With twin 4s in the array, every copy leaves, because the function drops all elements equal to the given value. Sense-check: no copy of 4 survives.

Example 5: swap a value. Run SELECT array_replace(ARRAY[1,2,3,4], 2, 10); where 2 is the old value and 10 is the new value. The result is \(\{1,10,3,4\}\). With twin 2s, each one swaps, giving \(\{1,10,10,3,4\}\). Sense-check: every old value becomes the new one.

20.10 Comparing Arrays with IN, NOT IN, ALL, ANY, and SOME

20.10.1 The IN operator

Hook: Four separate OR tests for one value is noisy. What single word replaces the whole chain?

The IN operator (a short test that passes when the left value matches anything on the right) reads expression IN (value_1, value_2, value_3, value_4). The right side is a bracketed list of plain scalar values. The result is \(true\) when the left side equals any one member of the right side, written \(\exists v \in R : e = v\), where \(e\) is the left value and \(R\) is the right list. In short, IN is short for a chain of OR tests: \(e = v_1\) OR \(e = v_2\) OR \(e = v_3\) OR \(e = v_4\).

Formalize: IN as exists-match. For left value \(e\) and list \(R = \{v_1, v_2, v_3, v_4\}\): \(e \text{ IN } R\) is \(true\) exactly when \(\exists v \in R : e = v\). One hit carries; zero hits fail. The right side here is a scalar list in parentheses — not an array — which separates IN from the ANY array form in 20.10.5. IN as exists-match pairs with NOT IN as for-all differ below.

Scope: IN with a scalar list is portable across PostgreSQL, MySQL, Snowflake, and Databricks. The ANY(array) twin below is PostgreSQL-flavored; other engines prefer IN with a subquery or array_contains.

Pitfalls: Writing IN ARRAY[...] without ANY is the first trap — IN wants a parenthesized scalar list here. Expecting IN against an empty list to pass is the second trap — no members means no hit. Mixing types across the list is the third trap — coercion rules decide, not intuition.

Recap: IN passes on any single match — one hit is enough. It pairs with its mirror NOT IN next.

20.10.2 Worked examples with IN

Worked examples. Example 1: a hit. Run SELECT 20 IN (1, 2, 20, 40);. Walking the list: 20 against 1 misses, 20 against 2 misses, 20 against 20 hits, 20 against 40 misses. One hit is enough, so the result is \(true\). Sense-check: the third slot carries the test.

Example 2: a miss. Run SELECT 25 IN (1, 2, 20, 40);. Walking the list: 25 against 1, 2, 20, and 40 all miss. With no hit anywhere, the result is \(false\). Sense-check: zero hits always fail.

20.10.3 The NOT IN operator

NOT IN is the mirror image. It reads expression NOT IN (value_1, value_2, ...), and the result is \(true\) only when the left side differs from every member of the right side, written \(\forall v \in R : e \neq v\). In short, NOT IN is short for a chain of AND tests: \(e \neq v_1\) AND \(e \neq v_2\) AND so on, where every link must hold.

Worked examples. Example 3: a present value fails. Run SELECT 20 NOT IN (1, 2, 20, 40);. The 20-against-20 link breaks the chain, so the result is \(false\). Sense-check: one match sinks the whole AND chain.

Example 4: an absent value passes. Run SELECT 25 NOT IN (1, 2, 20, 40);. Walking the list: 25 against 1, 2, 20, and 40 all differ, so every link holds and the result is \(true\). Sense-check: four differences pass four links.

Scope: NOT IN with a NULL anywhere in the list returns NULL, not true or false, in every major engine — a classic three-valued-logic trap. The session's lists hold no NULL, so the walkthroughs stay two-valued; keep NULL out of NOT IN lists or switch to NOT EXISTS.

20.10.4 The ALL operator

Hook: What test demands unanimous agreement — every element, no exceptions?

The ALL operator (a strict test that passes only when every element agrees) reads expression operator ALL (array). The right side must yield an array value. The engine sets the left value against each element with the given operator, and the result is \(true\) when every single test passes, written \(\forall v \in R : e \oplus v\), where \(\oplus\) is the chosen operator. An empty array also yields \(true\), while any single \(false\) link sinks the whole result. ALL as for-all pass pairs with ANY as exists-hit below.

Worked examples. Example 5: not all equal. Run SELECT 25 = ALL(ARRAY[20,25,30,35,40]);. Since 25 misses 20, 30, 35, and 40, the result is \(false\). Sense-check: four misses sink the strict test.

Example 6: all equal. Run SELECT 25 = ALL(ARRAY[25,25]);. Both links hold, 25 against 25 and 25 against 25, so the result is \(true\). Sense-check: unanimous agreement passes.

Scope: ALL(array) is PostgreSQL syntax. MySQL expresses the same idea with ALL (subquery); Snowflake and Databricks lean on array_contains, higher-order functions, or subqueries instead.

20.10.5 The ANY and SOME operators

Hook: What test passes on a single friendly vote instead of demanding unanimity?

The ANY operator (a light test that passes on a single hit) reads expression operator ANY (array). The right side must yield an array. The result is \(true\) when any one test passes, written \(\exists v \in R : e \oplus v\), and \(false\) when no hit turns up, empty array included. SOME is the identical twin of ANY — same call, same answer, different word.

Worked examples. Example 7: one hit carries. Run SELECT 25 = ANY(ARRAY[1,2,25]);. Walking the array: 25 against 1 misses, 25 against 2 misses, 25 against 25 hits. One hit is enough, so the result is \(true\). Sense-check: the third slot carries the test.

Example 8: no hit sinks. Run SELECT 20 = ANY(ARRAY[1,2,25]);. Walking the array: 20 against 1, 2, and 25 all miss, so the result is \(false\). Sense-check: zero hits fail, empty array included.

Example 9: NULL in the mix. Run SELECT 25 = ANY(ARRAY[1,2,25,NULL]);. The walk gives miss, miss, hit on 25, then NULL. The single hit carries, so the result is \(true\). Sense-check: one real hit outweighs the NULL.

Example 10: not-equal with ANY. Run SELECT 25 <> ANY(ARRAY[1,2,25,NULL]);. The walk gives \(true\) on 25 against 1 and 25 against 2, \(false\) on 25 against 25, and NULL last. Hits exist, so the result is \(true\). Sense-check: not-equal needs just one differing slot.

Example 11: SOME matches ANY. Run SELECT 25 = SOME(ARRAY[1,2,3,4]);. Nothing matches, so the result is \(false\). Adding 25 to the array flips it: 25 against 1, 2, 3, 4 all miss, 25 against 25 hits, so the result is \(true\). Sense-check: SOME and ANY always agree.

Picture a jury: ALL needs every juror to vote yes, ANY needs just one yes, IN is ANY with =, and NOT IN needs every juror to vote no. The takeaway is that strictness runs ALL, NOT IN at the top and ANY, IN, SOME at the bottom.

Pitfalls: Reading <> ALL as "differs from one" is the first trap — it means "differs from every one." Reading = ANY with only NULLs as false is the second trap — with no real hit the answer is NULL, not false. Forgetting SOME exists is the third trap — it is ANY under another name. Exam note: IN passes on any hit, NOT IN needs every link to differ, ALL needs every link to pass, and ANY or SOME passes on one hit; rehearse the 20-against-25 walkthroughs.

Recap: ANY and SOME pass on one hit; ALL needs every hit; IN and NOT IN are the =-flavored list twins. Quantifier logic feeds the ANY(phones) row hunts in 20.14 and 20.18.

Fraud filters flag a transaction when its code matches ANY watch-list array. Allow-list checks pass a login only when its region matches ALL permitted-region tests. Both belong to membership screening, where one hit versus every hit decides the outcome.

20.10.6 Questions and answers

Q: Why does SELECT 20 IN (1, 2, 20, 40) report true while 25 reports false? A: IN passes on any single match. The value 20 meets 20 at the third slot, so it reports true. The value 25 meets nothing at any slot, so it reports false.

Q: Why does SELECT 25 NOT IN (1, 2, 20, 40) report true while 20 reports false? A: NOT IN needs every link to differ. The value 25 differs from all four members, so it reports true. The value 20 meets 20, which breaks the chain, so it reports false.

Q: How does NULL inside an ANY array change the answer? A: One real hit still carries. In 25 = ANY(ARRAY[1,2,25,NULL]), the 25-against-25 hit outweighs the NULL, so the result stays true. With no real hit at all, the answer would be NULL rather than false.

20.11 Formatting and Converting Arrays

20.11.1 Splitting text with string_to_array

Hook: A CSV feed arrives as one long text line. How do you cut it into array slots at every comma — and mark the gaps as genuinely missing?

The string_to_array function splits one text value into array elements at a supplied delimiter (the split mark that sets where one element ends and the next starts), with an optional null string that maps chosen text to NULL. The call reads string_to_array(text, delimiter, null_string). The first input is plain text in single quotes with no array brackets, the second input is the split mark, and the third input is optional. When the third input matches a field, that field becomes NULL instead of text.

Formalize: split plus null mapping. For text \(T\), delimiter \(d\), and null string \(s\): string_to_array(T, d) cuts \(T\) at every \(d\) into array slots; string_to_array(T, d, s) additionally rewrites every field equal to \(s\) as NULL. NULL beats empty here on purpose: telling "no data" apart from "blank data" inside arrays is hard, and NULL marks the gap without doubt. Snowflake splits with SPLIT or STRTOK_TO_ARRAY, Databricks with split(), and MySQL has no direct twin — use nested SUBSTRING_INDEX or a JSON-table unpack.

Scope: string_to_array with a null-string third argument is PostgreSQL. Ports split text but handle the null mapping differently, so verify the third-argument behavior before porting a feed loader.

Picture scissors cutting a ribbon at every marked line, with flagged segments dropped into a "missing" bin instead of the pile. The takeaway is that the delimiter sets the cuts and the null string sets the bin.

Pitfalls: Passing the wrong delimiter and getting one giant element is the first trap — the split mark must match the feed. Forgetting that an empty field and a NULL field differ is the second trap — only the null string creates NULL. Expecting the function to trim spaces is the third trap — spaces ride along into the slots.

Recap: string_to_array(text, delimiter, null_string) cuts text into slots and maps the null string to NULL. Splitting pairs with the melting twin next.

Stock feeds split symbol lines at commas while nulling every non-ETF mark through the null-string input. Log loaders split pipe-delimited lines and null out empty slots the same way. Both belong to feed parsing, where flat text becomes structured slots with honest gaps.

20.11.2 Worked examples with string_to_array

Worked examples. Example 1: comma split. Run SELECT string_to_array('1,2,3,4', ',');. The engine cuts at each comma and returns the array \(\{1,2,3,4\}\). Sense-check: three commas make four slots.

Example 2: pipe split. Run the same text with '|' as the split mark. Quoting shifts to fit the new mark, and the elements land in the array the same way. Sense-check: the mark changes, the slot logic does not.

Example 3: mapping a word to NULL. Run SELECT string_to_array('1,2,3,4,ABC', ',', 'ABC');. The engine converts the text to an array at the commas, hunts for ABC, and swaps it to NULL. A feed of stock symbols can keep ETF marks and null out every non-ETF mark this way. Sense-check: four values survive, one becomes missing.

Example 4: empty slot to NULL. Run SELECT string_to_array('1,2,3,4,,6', ',', '');. The engine finds the empty slot between the commas and swaps it to NULL, giving \(\{1,2,3,4,NULL,6\}\). NULL beats empty here on purpose: telling "no data" apart from "blank data" inside arrays is hard, and NULL marks the gap without doubt. Sense-check: the double comma becomes an honest gap.

20.11.3 Gluing arrays with array_to_string

The reverse helper array_to_string melts an array back into one text value at a supplied split mark, with an optional null string that rewrites NULLs. The call reads array_to_string(array, delimiter, null_string). With no third input, NULL slots drop out silently; with one, every NULL prints as the given sentinel.

Worked examples. Example 5: basic melt. Run SELECT array_to_string(ARRAY[1,2,3,4], '|');. The elements join into the text '1|2|3|4'. The output is pure text now, not an array, which is the whole point of the flip. Sense-check: four slots become one delimited line.

Example 6: other marks. Swapping the mark to a dollar sign or a comma re-joins the same elements with the new glue. Sense-check: the mark is only glue, never data.

Example 7: NULLs with no rewrite rule. Run SELECT array_to_string(ARRAY[1,2,NULL,4], '|'); with no third input. The NULL slot drops out silently. Sense-check: missing data vanishes from the line.

Example 8: NULLs with a rewrite rule. Run SELECT array_to_string(ARRAY[1,2,NULL,4], '|', 'empty__data');. Every NULL slot now prints as empty__data. A loader written in Python, PHP, or Go can scan for that sentinel word and run its own missing-data step, which makes these two helpers a strong pair for CSV-style feeds moving into normalized tables. Sense-check: the gap stays visible as a sentinel instead of vanishing. Exam note: NULL beats empty inside arrays, and the null-string inputs of both conversion helpers control the swap; rehearse the ABC and empty-slot cases.

20.12 Using Arrays in Tables

20.12.1 Declaring an array column

Hook: One teacher owns three phone numbers. Do you really need a whole phone table — or can one column hold the list?

PostgreSQL lets one column hold an array of any valid data type: built-in types, user-defined types, and enumerated types all qualify. Every base type ships with a companion array type. An integer base gives an integer array type, and a character base gives a character array type. The declaration trick is small: add square brackets to the base type. A name column typed varchar(100) holds one value, while name varchar(100)[] holds many values in one column. The ARRAY keyword form (phones text ARRAY) declares the identical type.

Formalize: two declaration spellings. phones text[] and phones text ARRAY both declare a one-dimensional text array column; the column view shows the base type plus array brackets either way. Any base type works — integer[], date[], custom domains, enums — because every base type ships with a companion array type. Snowflake stores the same idea in ARRAY or VARIANT columns, Databricks in ARRAY<STRING>, and MySQL in JSON columns since it has no native array type.

Scope: Bracket and ARRAY-keyword column declarations are PostgreSQL. Other engines need their own column types for the same model, and the companion-array-type idea does not travel to MySQL.

Picture a contact card with one name line and a phone box holding several numbered lines inside. The takeaway is that the column holds a list, not a scalar, while the rest of the row stays flat.

Pitfalls: Declaring text[1] and expecting a one-phone cap is the first trap — sizes never bind (see 20.16). Storing huge arrays per row and then joining on elements is the second trap — a child table scales better. Assuming the column view preserves [1] or [][] exactly is the third trap — PostgreSQL normalizes the display.

Recap: Append [] or ARRAY to any base type to declare an array column. Declarations feed the inserts in 20.13 and the queries in 20.14.

20.13 Inserting Data into Array Columns

20.13.1 Quoting rules for literals and constructors

Hook: The column is ready — but do phone numbers wrapped in dashes go in with single quotes, double quotes, or curly braces?

Two habits cover every insert. Wrap the array in single quotes, or use the ARRAY constructor instead. For non-text data such as numbers, pair the single quotes with curly braces: '{"1,2"}' in shape, or '{' || value_1 || ',' || value_2 || '}' in spirit — single quotes outside, curly braces inside, commas between values. The constructor twin reads ARRAY[1, 2], with square brackets and commas.

Formalize: quote-style pairing. Text data adds one more layer. Inside curly braces, each string takes double quotes: '{"value1","value2"}'. Inside the ARRAY constructor, each string takes single quotes instead: ARRAY['value1','value2']. Mixing the two styles trips the engine, so matching the quote style to the wrapper is the habit that keeps inserts clean. Curly braces pair with double quotes, constructor pairs with single quotes — that pairing is the session's quote-style rule.

Scope: Literal-plus-constructor quoting is PostgreSQL array syntax. Snowflake inserts use bracket literals or ARRAY_CONSTRUCT; Databricks uses array(...); MySQL inserts JSON arrays with JSON_ARRAY or a JSON string.

Picture two envelopes: the curly-brace envelope needs double-quote stamps on each item, while the ARRAY[...] envelope needs single-quote stamps. The takeaway is that the wrapper picks the stamp — never mix them.

Pitfalls: Wrapping constructor strings in double quotes is the first trap — ARRAY["a"] reads as a column name, not text. Forgetting inner double quotes inside a literal is the second trap — '{"a,b"}' parses as one element, not two. Storing dash-filled phone numbers as numbers is the third trap — they are text, so quote each one.

Recap: Literals pair curly braces with double quotes; constructors pair square brackets with single quotes. Clean inserts feed the reads in 20.14 and the updates in 20.15.

Onboarding scripts insert each new teacher with an ARRAY[...] constructor for phones. Bulk loaders insert literal '{"...","..."}' rows for backfills. Both belong to batch insertion, where the quote habit decides whether a load passes or fails row one.

20.13.2 Worked examples

Worked examples. Example 1: one teacher through the constructor. Run INSERT INTO teachers (name, phones) VALUES ('Adam', ARRAY['111-222-3333','444-555-6666']);. The phone strings look numeric and carry dashes, but the whole number reads as text, so single quotes wrap each one. One contact now owns two phones, which is the charm of arrays in a table. Sense-check: one row inserted, two phones inside.

Example 2: two teachers through literals. Run INSERT INTO teachers (name, phones) VALUES ('Linda', '{"111-222-3333"}'), ('Jeff', '{"111-222-3333","444-555-6666"}');. Curly braces pair with double quotes every time, and practice locks the pairing in. Sense-check: Linda holds one number, Jeff holds two, both rows insert together.

20.14 Querying Array Data

20.14.1 Reading whole arrays and single slots

Hook: Every teacher's phones sit packed in one cell. How do you list them all — and how do you find the one teacher with no backup number?

Plain reads need no new syntax. SELECT name, phones FROM teachers; lists every name with its phone array, where each phone cell opens to show its first and second numbers, and SELECT * FROM teachers; adds the id column to the same picture. Single slots come out through subscripts: phones[1] is the first number and phones[2] is the second number, always starting at one. The first slot is one in PostgreSQL but zero in other languages — the same one-based contrast from 20.1 and 20.8.

Formalize: three read shapes. Whole-array reads (SELECT name, phones) return the packed list per row. Slot reads (phones[1], phones[2]) return one scalar per row, with NULL for missing slots. Whole-array hunts ('wanted' = ANY(phones)) test every slot of every row without naming a slot number. Slot filters (WHERE phones[1] = '...') test one named slot per row. Snowflake reads slots with zero-based phones[0] or GET, Databricks with phones[0] or element_at(phones, 1), and MySQL hunts JSON arrays with MEMBER OF or JSON_CONTAINS.

Scope: phones[1] one-based subscripts and = ANY(phones) hunts are the PostgreSQL spellings used here. Port the idea, not the index, when moving to zero-based engines.

Picture a filing cabinet: open a drawer to see the whole folder (whole array), pull one numbered tab (slot read), or ask the clerk to check every tab in every drawer for a name (ANY hunt). The takeaway is that each read shape answers a different question.

Pitfalls: Testing phones[2] = NULL instead of IS NULL is the first trap — equality never matches NULL. Naming slot zero is the second trap — PostgreSQL slots start at one. Using a slot filter when any slot would do is the third trap — ANY hunts the whole array without guessing positions.

Recap: Read whole arrays, named slots, or the whole array via ANY — with IS NULL finding the gaps. Slot reads power the updates in 20.15 and the unpacks in 20.17.

Support teams audit backup numbers with WHERE phones[2] IS NULL. Fraud teams hunt a stolen card number across every slot with = ANY(phones). Both belong to coverage querying, where missing-slot and any-slot tests find rows a plain equality would miss.

20.14.2 Worked examples

Worked examples. Example 1: all first numbers. Run SELECT name, phones[1] FROM teachers;. Every teacher's first phone prints: Adam's, Linda's, and Jeff's. Sense-check: slot one exists on every row.

Example 2: all second numbers. Run SELECT name, phones[2] FROM teachers;. Adam's and Jeff's second numbers print, while Linda's prints NULL because she holds no second number. Sense-check: a missing slot reads as NULL.

Example 3: hunting gaps. Run SELECT name FROM teachers WHERE phones[2] IS NULL;. Linda comes back. Any shop that wants a primary plus backup number per person can run this shape to find holders with no backup. Sense-check: only the short row qualifies.

Example 4: filtering on a slot. Run SELECT * FROM teachers WHERE phones[1] = '111-222-3333';. The engine sets the first slot against the wanted text and Adam comes back. Sense-check: the named slot decides per row.

Example 5: hunting the whole array with ANY. Run SELECT * FROM teachers WHERE '111-222-3333' = ANY(phones);. The wanted text is set against every slot of every row, and Adam comes back again without naming a slot number. Sense-check: any slot can carry the match.

20.14.3 Questions and answers

Q: How do you find teachers missing a second phone number? A: Read the second slot and test for NULL with WHERE phones[2] IS NULL. Linda holds only one number, so her second slot is NULL and her row comes back.

20.15 Modifying Array Data

20.15.1 Updating one slot with UPDATE

Hook: Linda finally gets a second number and Adam changes his first. Do you rewrite the whole array — or touch just one slot?

Slot edits ride the normal UPDATE shape: name the table, SET the field plus its subscript to the new value, and pin the row with WHERE. The pattern is UPDATE teachers SET phones[2] = 'new-value' WHERE teacher_id = 2;. The same shape both adds a missing slot and rewrites a filled one: assigning past the end extends the array, assigning inside it overwrites.

Formalize: subscript assignment. UPDATE teachers SET phones[k] = v WHERE ... sets slot \(k\) of the matched rows to \(v\), counting from one. Gaps between the old end and \(k\) fill with NULL. Whole-array rewrites (SET phones = ARRAY[...]) replace the list at once, while array_append and array_remove variants grow or shrink it — see 20.9 for those function forms. Snowflake updates array elements via ARRAY functions plus full-column rewrite or FLATTEN-rebuild; Databricks rewrites with higher-order transform; MySQL edits JSON arrays with JSON_SET, JSON_REPLACE, or JSON_ARRAY_APPEND.

Scope: Subscript UPDATE (SET phones[2] = ...) is PostgreSQL. Other engines rewrite the array value or use JSON modifiers instead of touching one slot in place.

Picture a numbered parking row: repaint the number on bay 2 without moving the other cars, or extend the row with a new bay when the car count grows. The takeaway is that one slot changes while the rest of the row, pinned by WHERE, stays put.

Pitfalls: Forgetting WHERE and rewriting every row's slot is the first trap — always pin the row. Counting from zero is the second trap — slot two here is index one elsewhere. Assigning far past the end is the third trap — the engine pads the gap with NULLs silently.

Recap: UPDATE ... SET phones[k] = v WHERE ... adds or rewrites one one-based slot. Slot edits pair with the function reshapers in 20.9 and the table inserts in 20.13.

CRM teams add a backup number to one contact with a slot-two update. Ops teams rewrite a stale primary number with a slot-one update. Both belong to in-place list repair, where one slot changes without rebuilding the row.

20.15.2 Worked examples

Worked examples. Example 1: giving Linda a second number. Run UPDATE teachers SET phones[2] = '801-234-5678' WHERE teacher_id = 2;. Linda held one number before, and a fresh read shows two: the old 111-222-3333 plus the new 801-234-5678. Sense-check: a missing slot becomes a filled one on exactly one row.

Example 2: rewriting Adam's first number. Run UPDATE teachers SET phones[1] = '888-222-3333' WHERE teacher_id = 1;. A fresh read shows 888-222-3333 parked in slot one for Adam. Sense-check: a filled slot is overwritten on exactly one row.

20.16 Declared Array Sizes Are Ignored

20.16.1 The one-phone limit that never holds

Hook: The declaration says "one phone only" — but two numbers slide in with no error. Is the cap broken, or was it never real?

Array size caps in declarations carry no weight in PostgreSQL. Writing phones text[1] says "one phone only" in plain SQL, yet the engine stores whatever arrives. The spoken verdict from the session was blunt: dimensions are ignored, which reads as a blessing once you see the demo. One-phone declaration expected to error but two numbers store fine — that silent pass is the session's flagged warning.

Formalize: declarations without enforcement. phones text[1], phones text[2], or any bracket count all declare the same type: an unbounded one-dimensional text[]. The column view confirms it by showing a plain text array type with no size. The engine keeps every element it gets no matter what count sits in the brackets, so [1], [2], or any other count changes nothing. Enforce real caps with CHECK (cardinality(phones) <= 1) instead of brackets.

Scope: Ignored sizes are PostgreSQL behavior. Snowflake ARRAY caps at 16 MB total, not element count; Databricks arrays are unbounded; MySQL JSON arrays are unbounded. Only CHECK constraints enforce counts portably.

Picture a doorway sign reading "one guest only" with no bouncer — two guests walk in and nobody stops them. The takeaway is that the sign documents intent but enforces nothing.

Pitfalls: Trusting [1] as validation is the first trap — inserts never fail on count. Reading the column view as proof of a cap is the second trap — it normalizes to a plain array type. Forgetting the CHECK alternative is the third trap — only cardinality checks bind.

Recap: Declared sizes document but never bind; only CHECK constraints cap an array. Exam note: declared array sizes never bind — a [1] cap still stores two phones — is the most testable surprise; rehearse it with the teachers2 demo. This contrasts with the declarations in 20.12 that do bind the base type.

Form designers who write text[1] expecting validation must add the CHECK instead. Migration teams porting fixed-size arrays from stricter engines hit the same silent pass. Both belong to constraint modeling, where declarations describe and checks enforce.

20.16.2 Worked examples

Worked examples. Example 1: building the capped table. Run CREATE TABLE teachers2 (teacher_id serial PRIMARY KEY, name varchar(150), phones text[1]);. The [1] tag aims to cap the field at one phone. The column view still shows a plain text array type. Sense-check: the display already drops the cap.

Example 2: breaking the cap. Run INSERT INTO teachers2 (name, phones) VALUES ('Adam', ARRAY['111-222-3333','444-555-6666']); with two numbers against a cap of one. By the declared rule this should error, but it reports success. A follow-up SELECT * FROM teachers2; shows both numbers in the row. Sense-check: the silent pass proves sizes never bind.

Example 3: the cap never binds at any size. Declaring [2] or any other count changes nothing, because the engine keeps every element it gets no matter what count sits in the brackets. Sense-check: no bracket number alters storage.

20.17 Displaying All Array Elements with unnest

20.17.1 From one packed row to many plain rows

Hook: Phones are stacked inside one cell per teacher. How do you lay every number out as its own row for review?

Array elements normally pack into one row: one teacher id, one name, and every phone stacked in a single cell. The unnest function unpacks the stack into a row set, one row per element. The call reads unnest(phones), wrapped around the array column, so SELECT teacher_id, name, unnest(phones) FROM teachers; prints each teacher once per phone. The id and name repeat while the phone changes, and the packed text values now behave like a plain table.

Formalize: packed rows to row sets. For a row \((id, name, [p_1, p_2])\), unnest(phones) yields two rows: \((id, name, p_1)\) and \((id, name, p_2)\). Non-array columns repeat per element; each array element gets its own row. Pairing the unpack with DISTINCT exposes duplicate numbers shared across people, and ORDER BY on the unpacked column lines them for review. Snowflake unpacks with TABLE(FLATTEN(...)), Databricks with explode(phones), and MySQL unpacks JSON arrays with JSON_TABLE.

Scope: unnest(array_col) in the select list is the PostgreSQL spelling here. Ports return similar row sets but need lateral or table-function syntax (FLATTEN, explode, JSON_TABLE), so carry the idea across with fresh syntax.

Picture a stacked inbox tray: lift each letter out and lay it on the desk in its own row, copying the owner's name onto every letter. The takeaway is that one packed row becomes as many plain rows as there are elements.

Pitfalls: Forgetting that unnest multiplies rows is the first trap — joins after it fan out. Sorting by position number instead of the unpacked column is the second trap — ORDER BY 3 here targets the phone value. Expecting NULL arrays to yield rows is the third trap — empty or NULL arrays yield no rows.

Recap: unnest(phones) turns each element into its own row with the row's other columns repeated. Unpacked rows feed audits, dedup checks, and cleanup passes.

Data-quality teams unpack phone arrays with unnest plus DISTINCT to expose numbers shared across people. Migration teams unpack arrays into reviewable rows before loading a normalized child table. Both belong to array normalization checks, where packed lists become countable rows.

20.17.2 Worked examples

Worked examples. Example 1: full unpack. Run SELECT teacher_id, name, unnest(phones) FROM teachers;. Jeff's two numbers print on two rows, Linda's numbers print across her rows, and Adam's two numbers print on two rows. Sense-check: each phone owns exactly one row.

Example 2: sorted unpack. Run SELECT teacher_id, name, unnest(phones) FROM teachers ORDER BY 3;. Sorting by the third column lines the phone numbers in rising order, which makes eyeballing easier. Pairing the unpack with DISTINCT exposes duplicate numbers shared across people, and the ordered form turns the array column into reviewable rows for cleanup work. Sense-check: the same rows return, now ordered by phone value.

20.18 Multi-Dimensional Arrays

20.18.1 Grades paired with years

Hook: Each student needs a grade kept next to its year — 90 with 2020, 80 with 2019. How does one array field hold linked pairs?

Earlier tables held one value per slot. A multi-dimensional array (a grid where each entry holds more than one linked value) holds linked pairs instead. The session's model case is a student grade kept next to its year: 90 with 2020, then 80 with 2019 for the next student. Each entry carries an X and a Y, the grade and the year, inside one array field. Double-bracket design (int[][]) shows as a single bracket pair in the column view, which is normal PostgreSQL display behavior while the design intent stays two-dimensional.

Formalize: paired storage and axis reads. student_grade int[][] declares the two-dimensional integer grid. Each row stores one pair such as '{90,2020}': slot one is the grade axis, slot two is the year axis. SELECT student_grade[1] prints every grade with no years; SELECT student_grade[2] prints every year with no grades. Year hunts work two ways: WHERE student_grade @> '{2020}' (contains, both sides read as text) or WHERE 2020 = ANY(student_grade) (whole-array hunt) — either tool fits, so the business case picks. Grade filters read the axis: WHERE student_grade[1] > 70 keeps rows above 70, tightening to > 80 leaves only the 90 row. Key-value style layouts are possible too, but grade-plus-year keeps the model simple and strong.

Scope: True multi-dimensional int[][] arrays with axis subscripts are PostgreSQL. Snowflake nests arrays inside VARIANT and reaches elements with zero-based [0] paths; Databricks nests ARRAY<ARRAY<INT>>; MySQL nests JSON arrays with path expressions. Port the pairing idea with each engine's nesting syntax.

Picture a spreadsheet with two columns — grade in column one, year in column two — folded into a single cell per student. Reading axis one shows the grade column; reading axis two shows the year column. The takeaway is that position inside the pair carries the meaning.

Pitfalls: Swapping the pair order is the first trap — writing 2020 first and 90 second stores 2020 as the grade with no error, the silent order swap from 20.19. Mixing pair widths is the second trap — every entry should carry the same element count. Hunting years without quotes in the contains form is the third trap — '{2020}' reads as text on both sides.

Recap: One int[][] field holds grade-plus-year pairs; axis subscripts, contains, ANY, and axis filters read them. Paired storage contrasts with the separate-grades-table alternative: the same figures could live in a grades table with one grade column, one year column, and a student id link, which suits heavy insert loads and tangled joins, while the array suits compact reads — pick by weighing insert volume against read volume and query tangle.

Athletics systems store score-plus-season pairs per player for compact season reads. Survey tools store rating-plus-wave pairs per respondent the same way. Both belong to paired-attribute modeling, where two linked numbers travel as one entry until write volume forces a child table.

20.18.2 Worked examples

Worked examples. Example 1: building the grid table. Run CREATE TABLE students (student_id serial PRIMARY KEY, student_name varchar(100), student_grade int[][]);. The doubled brackets mark two dimensions on an integer array. The column view shows a single bracket pair, which is normal PostgreSQL display behavior, while the design intent stays two-dimensional. Sense-check: the design is two-dimensional even when the display is not.

Example 2: first pair insert. Run INSERT INTO students (student_name, student_grade) VALUES ('1', '{90,2020}');. The curly braces hold the grade first and the year second, split by a comma. A follow-up SELECT * FROM students; shows 90,2020 in the grade cell. Sense-check: grade 90 pairs with year 2020.

Example 3: more pairs. Run INSERT INTO students (student_name, student_grade) VALUES ('2', '{80,2019}'), ('3', '{70,2019}'), ('4', '{60,2020}');. A fresh read shows one integer pair per row, each with two dimensions inside. Key-value style layouts are possible too, but grade-plus-year keeps the model simple and strong. Sense-check: four students, four pairs, one shape.

Example 4: reading one axis. Run SELECT student_grade[1] FROM students;. Slot one of each pair prints every grade with no years. Run SELECT student_grade[2] FROM students;. Slot two prints every year with no grades. Sense-check: each axis reads cleanly on its own.

Example 5: hunting a year with contains. Run SELECT * FROM students WHERE student_grade @> '{2020}';. Both sides read as text, so the year sits in quotes and brackets, and every row holding 2020 comes back. Sense-check: the 90 and 60 rows qualify.

Example 6: hunting a year with ANY. Run SELECT * FROM students WHERE 2020 = ANY(student_grade);. The wanted value is set against the grade field of each row, and the same 2020 rows come back. Either tool fits, so the business case picks. Sense-check: both hunts agree.

Example 7: filtering the grade axis. Run SELECT * FROM students WHERE student_grade[1] > 70;. Rows above 70 come back. Tightening to student_grade[1] > 80 leaves only the 90 row. The same figures could live in a separate grades table with one grade column, one year column, and a student id link, which suits heavy insert loads and tangled joins, while the array suits compact reads. Pick by weighing insert volume against read volume and query tangle. Sense-check: the axis filter isolates the top scorer.

Q: How do you list every student tied to the year 2020? A: Either WHERE student_grade @> '{2020}' or WHERE 2020 = ANY(student_grade) works. Both return the rows whose pair holds 2020, so pick whichever fits the surrounding query.

Q: How do you list students scoring above 80? A: Filter the grade axis with WHERE student_grade[1] > 80. Slot one holds the grade, so only the 90 row comes back.

20.19 Array Versus JSONB

20.19.1 How to choose

Hook: Same contact list, two storage shapes — a tight array or a flexible JSONB document. Which one earns its place?

No single rule picks the winner. The choice tracks the business case through four design questions: how inserts run, how edits run, how deletes run, and how searches run. Storage size, index cost, and planner behavior round out the picture, and the habit grows easier with practice and normalization work.

Formalize: the four-question test. Ask inserts (bulk loads or trickles?), edits (whole-list rewrites or surgical key updates?), deletes (drop a slot or drop a key?), and searches (positional, membership, or path queries?). Then weigh storage size, index cost, and planner behavior: arrays store less on disk with a large gap, both take GIN indexes, and the planner gathers content stats for arrays (NULL counts, top and bottom grades) while it gathers none of that for JSON. Arrays versus JSONB strengths, weaknesses, and picks all hang on these questions.

Scope: This array-versus-JSONB trade is PostgreSQL. Elsewhere the same choice reappears as ARRAY versus VARIANT/OBJECT in Snowflake, ARRAY versus MAP/STRUCT in Databricks, and normalized tables versus JSON in MySQL. The questions travel; the type names change.

Recap: Four workload questions plus size, index, and planner behavior pick the winner per case. The questions frame the strengths and weaknesses next.

20.19.2 Array strengths

Arrays are easy to set up: name the base type, add brackets or the ARRAY keyword, and single or double dimensions follow. They store less than JSONB on disk, which is a large gap between the two. They support multiple dimensions, with the wrinkle that each entry should carry the same element count. They take GIN indexes, which lift query speed a lot. And the planner makes sharper calls with arrays, because it gathers stats on the contents — NULL counts, top grades, bottom grades — while it gathers none of that for JSON. Simple lists such as country codes and product categories fit arrays well, and repeated marks such as several ratings on one value fit too, since duplication is welcome.

Worked contrast. Store country codes ARRAY['US','IN','BR'] as text[]: one typed column, small footprint, GIN-indexable, planner-visible. The same list in JSONB costs more bytes and hides stats from the planner. Sense-check: short, uniform, repeated-friendly lists favor arrays.

20.19.3 Array weaknesses

Every array keeps one base type, so integers stay integers and characters stay characters, with no mixing inside. Incoming feeds are rarely that tidy, mixing text and numbers freely, and mixed feeds point at JSONB instead. Arrays also demand a strict input order with no safety net: writing 2020 first and 90 second stores 2020 as the grade and 90 as the year without any error, and the queries downstream quietly break. Grade-year swap stores silently with no error and breaks queries — that silent order swap is the session's flagged warning. Exam note: the one-type rule and the silent order swap are the two array traps to rehearse until they feel automatic.

Scope: The single-type plus positional-order trap is PostgreSQL arrays specifically. Snowflake ARRAY of VARIANT accepts mixes, and JSONB labels every value with a key so order stops mattering.

20.19.4 JSONB strengths

JSONB brings the JSON toolkit plus extra query operators, including its own concatenation step, where plain JSON search paths stay narrow. It supports indexing for speed the same way arrays do, through GIN. And its WHERE clauses read lighter: a JSONB test names the column, the operator, and the value straight away, while the array twin wraps the value in a dummy ARRAY[...] constructor to line the two sides up. Skipping that wrapper trims noise and lifts readability.

Worked contrast. Test a contact flag with WHERE doc @> '{"email_only_hours": true}': column, operator, value, done. The array twin must wrap the wanted value in ARRAY[...] first. Sense-check: fewer wrappers mean lighter reads.

20.19.5 JSONB weaknesses and best-fit cases

JSONB parses incoming text into binary form, so writes run slower than plain JSON writes, while reads run very fast. Feeds that write rarely and read often favor JSONB for that reason. JSONB also lets key order drift: 90-first-2020-second may print flipped, because the format keeps no order promise. Key-value style fixes it, since each value rides with its key no matter where the pair lands. Contact rows with first name, last name, phone, address, birth date, and image, plus one-off flags such as email-only-at-certain-hours, fit JSONB well, because mixed types share one field and reads stay quick.

Ignoring GIN on either side is the third trap — both index the same way. Exam note: arrays keep one base type and demand a strict input order with no error on swaps; rehearse the 2020-as-grade trap.

Recap: Uniform, ordered, compact, stats-visible lists favor arrays; mixed, keyed, write-rare, read-often documents favor JSONB. Run every new case through the four workload questions.

Country-code and category lists plus repeated ratings on one value are natural array fits. Mixed-type contact rows with one-off email flags are natural JSONB fits for write-rare, read-often loads. GIN indexes on array fields and planner stats (NULL counts, top and bottom grades) round out the performance picture.
