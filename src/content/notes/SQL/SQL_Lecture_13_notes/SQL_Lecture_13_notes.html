13.1 UPPER, LOWER and INITCAP

13.1.1 Syntax and Meaning

Why do names typed by hand look messy while names in a printed report look neat? Raw input arrives in mixed shapes like 'bRuCe lEE', but reports need one fixed shape. Three small functions force that shape.

Case means whether letters print as capitals or small letters. Uppercase means capital letters like ABC. Lowercase means small letters like abc. Proper case (also called title case) means the first letter of each word is a capital and the rest are small, as in normal English writing.

Think of these three functions as three rubber stamps in an office. UPPER is the all-capitals stamp. LOWER is the all-small stamp. INITCAP is the name-badge stamp that capitalizes the start of each word. But stamps only press down what is under them. A stamp never adds missing letters, and it never fixes a wrong spelling.

The three signatures are \(\text{UPPER}(s)\), \(\text{LOWER}(s)\) and \(\text{INITCAP}(s)\), where \(s\) is any text value. Each one takes a string and always gives back a value of type text. UPPER turns every letter into capitals. LOWER turns every letter into small letters. INITCAP turns the first letter of each word into a capital and forces all other letters to small. Digits, blanks, and marks like dashes pass through all three functions unchanged, since they have no case to change.

\(\text{UPPER}(s)\) maps every letter of \(s\) to its capital form and returns text. \(\text{LOWER}(s)\) maps every letter of \(s\) to its small form and returns text. \(\text{INITCAP}(s)\) maps the first letter of each word of \(s\) to a capital, maps every other letter to small, and returns text. A word here means a run of letters broken by any non-letter, so blanks, dashes, dots, and apostrophes all start a new word. A handy habit is to push messy input through LOWER first and then apply INITCAP, so stray capitals in the middle of words get cleaned before the final format is set.

A NULL input gives a NULL output in all three functions. A missing value has no letters to change, so the call returns NULL instead of a string.

13.1.2 Worked Examples

Start with the string 'Amazing Postgres SQL', where A and P are already capitals. Run:

SELECT UPPER('Amazing Postgres SQL');

Trace: each letter maps to its capital form. A stays A, m becomes M, a becomes A, and so on through every word. Blanks stay blanks. Result: 'AMAZING POSTGRES SQL', of type text. Sense-check: count the words before and after. Three words in, three words out. Nothing was added or lost.

Next, run the same string through LOWER:

SELECT LOWER('Amazing Postgres SQL');

Trace: each letter maps to its small form. A becomes a, P becomes p, and every other capital drops to small. Result: 'amazing postgres sql'. The A and P lose their capitals and the whole string prints small. Sense-check: the output has the same length as the input, since case changes never add or drop characters.

Now take a sentence in mixed shape, 'the world is changing with the lightning speed', and run:

SELECT INITCAP('the world is changing with the lightning speed');

Trace: the string splits into words at each blank. The first letter of each word turns into a capital: t becomes T, w becomes W, i becomes I, c becomes C, and so on. All other letters stay small. Result: 'The World Is Changing With The Lightning Speed'. Each word now starts with a capital and the rest of each word is small. Sense-check: eight words in, eight capitals out, one per word.

Watch what happens with truly messy input. Run INITCAP straight on 'bRuCe lEE' and the inner capitals survive in the wrong spots, giving 'Bruce Lee'? No extra step is needed here, but try 'McDONALD' and INITCAP gives 'Mcdonald', which mangles a name that wants an inner capital. That is why the lecture teaches the LOWER-first habit for plain words, and why real name lists still need a human eye for names like McDonald and O'Brien.

These functions also work straight on table columns. The directors table holds first_name and last_name columns. To print every director name in capitals:

SELECT UPPER(first_name) AS first_name,
       UPPER(last_name) AS last_name
FROM directors;

Every first and last name comes back in uppercase. This style of forced case is handy wherever a report or a business rule needs names in one fixed shape.

A nicer combined use joins the two name parts and then title-cases the whole thing. Concatenation means gluing strings end to end. CONCAT glues its inputs, so CONCAT(first_name, ' ', last_name) glues first and last name with one blank space between them. Wrap that in INITCAP:

SELECT INITCAP(CONCAT(first_name, ' ', last_name)) AS full_name
FROM directors;

Trace on one row: say first_name is 'bruce' and last_name is 'LEE'. CONCAT gives 'bruce LEE'. INITCAP splits at the blank, capitalizes b and L, and forces the rest small. Result: 'Bruce Lee', where B and L are capitals. Sense-check: read the badge out loud. It looks like a normal printed name, which is exactly the goal.

The same three functions exist in other database systems, with one gap worth knowing. UPPER and LOWER are standard SQL and behave the same in Postgres, MySQL, Snowflake, Databricks, and SQL Server. INITCAP exists in Postgres, Snowflake, Oracle, and Databricks, but MySQL and SQL Server have no INITCAP at all. The MySQL workaround builds title case by hand from pieces the lecture already covered:

SELECT CONCAT(UPPER(LEFT(name, 1)), LOWER(SUBSTRING(name, 2))) AS title_name
FROM directors;

LEFT grabs the first letter, UPPER capitalizes it, SUBSTRING takes the rest, LOWER flattens it, and CONCAT glues the parts. It handles single words only, which shows why a built-in INITCAP is worth having.

Scope: use case functions for display shape and for case-blind compares, not for fixing bad data. UPPER and LOWER never repair a wrong spelling, and INITCAP never knows special names. INITCAP treats every non-letter as a word break, so 'o''brien' prints as 'O''Brien' with two capitals and 'mary-kate' prints as 'Mary-Kate'. When exact stored values matter, clean the source rows once with an UPDATE instead of masking them in every SELECT.

A bar chart helps to picture the change. Draw one bar per function for the word 'hello'. The x-axis names the three calls: UPPER, LOWER, INITCAP. The y-axis counts capital letters in the output: 5 for UPPER, 0 for LOWER, 1 for INITCAP. The bars step down from full height to zero to a single unit. The takeaway is that each function sets a fixed capitals pattern no matter what shape went in.

Two traps catch beginners. First, comparing with the wrong case: WHERE last_name = 'lee' misses 'Lee', so compare with WHERE LOWER(last_name) = 'lee' when the stored shape is unsure. Second, trusting INITCAP on special names: names with inner capitals (McDonald), apostrophes (O'Brien), and acronyms all print wrong under INITCAP, so keep an exception list for real name data.

Q: Why run LOWER before INITCAP instead of using INITCAP straight on raw input? A: Raw input from outside sources often holds random capitals in the middle of words. LOWER flattens everything first, then INITCAP sets exactly one capital per word, so the final string prints in a clean and even shape. INITCAP alone only fixes word starts and leaves stray inner capitals in place.

Name loads give the concrete setting. Teams that load names or addresses from outside files force one fixed case before they store or print the rows, so reports stay neat. Search boxes use the same trick: flatten both the column and the typed text with LOWER, then compare, so 'LEE', 'Lee', and 'lee' all match.

Exam note: know the three names, what each one changes, and that INITCAP sets the first letter of every word to a capital while the rest go small. UPPER maps all letters up, LOWER maps all letters down, and every function takes text and returns text.

13.2 LEFT and RIGHT

13.2.1 Syntax and Meaning

After fixing letter case, the next job is cutting strings to size. How do you pull just the first letter of a name, or just the last two letters of a code? LEFT and RIGHT cut a fixed number of characters off one end of a string. LEFT means the cut starts at the first character. RIGHT means the cut starts at the last character.

Think of a ticket strip with numbered stubs. LEFT tears off stubs from the front of the strip. RIGHT tears off stubs from the back. The minus sign tears off the opposite end instead: LEFT with a minus leaves stubs off the back, and RIGHT with a minus leaves stubs off the front.

The signatures are \(\text{LEFT}(s, n)\) and \(\text{RIGHT}(s, n)\), where \(s\) is the input text and \(n\) is how many characters to keep. Both always give back text. LEFT(\(s\), \(n\)) keeps the first \(n\) characters. RIGHT(\(s\), \(n\)) keeps the last \(n\) characters.

\(\text{LEFT}(s, n)\) returns the first \(n\) characters of \(s\) as text. \(\text{RIGHT}(s, n)\) returns the last \(n\) characters of \(s\) as text. Here \(s\) is any text value and \(n\) is an integer count. Counts start at the named edge and move inward: LEFT counts from the first character, RIGHT counts from the last character. Blank spaces count as characters. Nothing gets trimmed or skipped.

Counts that run past the end cause no error. Asking for more characters than the string holds just gives back the whole string. A zero count gives an empty string. A NULL input gives NULL back.

A negative count flips the sense. LEFT(\(s\), \(-n\)) gives back everything except the last \(n\) characters. RIGHT(\(s\), \(-n\)) gives back everything except the first \(n\) characters. Think of the minus sign as "leave this many characters off the far end".

\(\text{LEFT}(s, -n)\) returns all of \(s\) except its last \(n\) characters. \(\text{RIGHT}(s, -n)\) returns all of \(s\) except its first \(n\) characters. The minus sign flips the job from keeping to dropping: instead of keeping \(n\) characters at the named edge, the call drops \(n\) characters at the far edge.

The same cuts exist in MySQL, Snowflake, Databricks, and SQL Server with the same names and the same positive-count behavior. One difference matters: the negative-count flip is a Postgres extra. In MySQL, LEFT with a negative count gives an empty string instead of dropping from the far end, so portable code should avoid negative counts.

13.2.2 Worked Examples

Take the short string 'Abcd' and run:

SELECT LEFT('Abcd', 1);

Trace: count from the front. Slot 1 holds A, slot 2 holds b, slot 3 holds c, slot 4 holds d. Keep the first 1. Result: 'A', the first character. Change the count to 2 and the result is 'Ab'. Count 3 gives 'Abc'. Count 10 gives the full 'Abcd' with no error, since the request runs past the end. A string with a space keeps that space in the cut. Copying the result and pasting it elsewhere shows the blank is still there. Sense-check: a count longer than the string can never add letters, so the whole string is the largest answer possible.

Now the negative form:

SELECT LEFT('ABC', -2);

Trace: the minus flips keep into drop. Drop the last 2 characters (B and C), and keep the rest. Result: 'A'. A positive 2 would give 'AB'. The minus flips it to "all but the last two characters". With -1 the last single character drops and the result is 'AB'. Sense-check: the answer plus the dropped tail rebuilds the full string, so 'A' plus 'BC' gives 'ABC'.

RIGHT mirrors all of this from the other end:

SELECT RIGHT('Abcd', 1);

Trace: count from the back. The last slot holds d. Keep 1. Result: 'D', the last character. Count 2 gives 'CD' and count 3 gives 'BCD', always counting in from the right edge. Sense-check: LEFT('Abcd', 1) gives the first letter A while RIGHT('Abcd', 1) gives the last letter D, so the two functions are true mirrors.

Negative counts on RIGHT drop from the front:

SELECT RIGHT('ABCD', -1);

Trace: the minus flips keep into drop. Drop the first 1 character (A), and keep the rest. Result: 'BCD'. With -2 the first two characters drop and the result is 'CD'. Sense-check: the dropped head plus the answer rebuilds the string, so 'A' plus 'BCD' gives 'ABCD'.

These cuts shine on real columns. To pull the first letter of every director's first name:

SELECT LEFT(first_name, 1) AS initial
FROM directors
ORDER BY 1;

Names sort under A, B, C and so on. One direct use is a gap check: pull all initials and look for missing letters between A and Z. Another use counts heads per letter:

SELECT LEFT(first_name, 1) AS initial,
       COUNT(*) AS total
FROM directors
GROUP BY 1
ORDER BY 1;

Trace on three rows: first names 'Bruce', 'Rita', 'Rex' give initials B, R, R. GROUP BY collects equal initials, and COUNT tallies each pile. Result shape: B 1, R 2. The grouped counts show how names spread, with several names under some letters (five under R, for one) and single names under others. Sense-check: the counts add up to the row total, so no name was lost in the cut. The same trick works on films:

SELECT movie_name, LEFT(movie_name, 6)
FROM movies;

Each row shows the full title next to its first six characters.

A last query shows RIGHT inside a filter. To find directors whose last name ends in 'on':

SELECT last_name
FROM directors
WHERE RIGHT(last_name, 2) = 'on';

Trace on one row: last name 'Alfredsson' has 10 letters. RIGHT keeps the last 2, which read 'on'. The test 'on' = 'on' passes, so the row stays. A name like 'Ford' keeps 'rd', the test fails, and the row drops. Result: rows such as 'Alfredsson' come back, since the last two characters read 'on'. Sense-check: every returned name ends in 'on' when read aloud.

Picture the cut on a ruler. Draw the string 'Abcd' as four boxes labeled A, b, c, d on slots 1 to 4. LEFT with 2 shades boxes 1 and 2. RIGHT with 2 shades boxes 3 and 4. LEFT with -1 shades boxes 1 to 3 and leaves box 4 white. The takeaway is that positive counts shade from the named edge inward, while negative counts leave the far edge white.

Scope: LEFT and RIGHT cut by character slots, not by words or meaning. They never skip blanks, they never trim, and they never warn when the count runs past the end. Use them for fixed-shape codes, initials, and endings. For word-aware cuts, pair them with POSITION to find a blank first, or use SPLIT_PART to split at a delimiter.

Three traps catch beginners. First, counting from zero: slots open at 1, so LEFT('Abcd', 1) is 'A', not 'b'. Second, a flipped minus: LEFT with a minus drops from the right, and RIGHT with a minus drops from the left, which is the opposite of what the name suggests. Third, multibyte letters: some accented or non-Latin letters use more than one byte of storage, and byte-based tools may count them differently, so test with real data before trusting a width.

Q: Why bother with LEFT and RIGHT when they look so small? A: Small cuts join into big jobs. They parse loaded CSV files, shape data in WHERE, GROUP BY and HAVING clauses, pull initials, count groups, and match endings, so one tiny function can drive a full data story.

Q: What does a negative count do in each function? A: LEFT with a negative count drops that many characters off the right end and keeps the rest. RIGHT with a negative count drops that many characters off the left end and keeps the rest.

Data import jobs give the concrete setting. Imported CSV rows often glue several codes into one column, and LEFT plus RIGHT peel the parts off by slot. Warehouse teams use the same cuts to pull initials for grouping, to filter on endings in WHERE, and to shape text before it enters clean tables.

Exam note: LEFT keeps from the front, RIGHT keeps from the back, over-long counts give the whole string with no error, and a negative count drops characters off the far end.

13.3 REVERSE

13.3.1 Syntax and Meaning

Cuts take letters off one end. What if the whole string needs to read back to front, like a code that stores its letters last but must be read first? REVERSE prints a string back to front. The signature is \(\text{REVERSE}(s)\), where \(s\) is the input text. Every letter keeps its identity but takes the mirror position: the last character moves first and the first character moves last. The output is text.

Think of a film strip run backward through a projector. Every frame is the same, but the order flips: the last scene plays first and the first scene plays last. REVERSE runs the characters backward in the same way. Blanks are frames too, so they flip along with the letters.

\(\text{REVERSE}(s)\) returns the characters of \(s\) in mirror order as text. The first character of the output is the last character of the input, the second of the output is next-to-last of the input, and so on down to the first character of the input at the very end. Blanks flip like any other character, so words swap sides as well as letters. Feeding an output back through REVERSE restores the first order.

The same function exists in MySQL, Snowflake, Databricks, and SQL Server under the same name with the same mirror behavior. It is one of the few string functions that matches across every system with no syntax gap.

13.3.2 Worked Examples

Run:

SELECT REVERSE('Amazing PostgreSQL');

Trace: write the input slots from left to right: A-m-a-z-i-n-g, blank, P-o-s-t-g-r-e-S-Q-L. Now read the slots from right to left: L-Q-S-e-r-g-t-s-o-P, blank, g-n-i-z-a-m-A. The last letter L jumps to the front, then come Q, S, E and the rest in mirror order, down to the starting A at the very end. Result: 'LQSergtsoP gnizamA'. The blank space between the words mirrors too, so the two flipped words swap sides. Sense-check: count the characters. Eighteen in, eighteen out. A mirror never adds or drops letters.

One business shape for this is a coded ID such as '111A' rows, where digits lead and letters trail. Run:

SELECT REVERSE('111A');

Trace: slots read 1-1-1-A. Mirror order reads A-1-1-1. Result: 'A111'. Reversing such an ID pulls the letters to the front and pushes the digits right, which suits checks that read the letter part first. Sense-check: flip it back with REVERSE('A111') and '111A' returns, since the function undoes itself.

The same function also undoes itself: feed an already flipped string back through REVERSE and the first order returns. People also reach for it in text scraping jobs and in speech text, where mirror-order tricks help spot patterns. A palindrome check shows the idea in one line: a word reads the same flipped, so WHERE word = REVERSE(word) keeps only palindromes like 'level'.

Scope: REVERSE flips slot order only. It never changes letter case, never drops blanks, and never parses meaning. It shines on fixed-shape codes and on mirror-order pattern checks. For reading a code from the back without flipping the whole string, RIGHT is the cheaper tool.

Picture the flip on a mirror line. Write 'ABC' above a horizontal line, with an arrow from A down to the last slot below the line, from B to the middle slot, and from C to the first slot. The output below the line reads 'CBA'. The takeaway is that each character maps to the slot the same distance from the far end.

Two traps catch beginners. First, forgetting the blank: REVERSE('AB CD') gives 'DC BA', not 'DCBA', since the blank mirrors too. Second, expecting a sort: reversed order is not alphabetical order, so always pair REVERSE with ORDER BY when a sorted list is the goal.

Q: When would anyone flip a whole string around? A: Coded IDs that start with digits and end with letters read better flipped, already reversed feeds flip back to normal with the same call, and text scraping work on speeches and long prose sometimes needs mirror order to expose a pattern.

Coded ID stores give the concrete setting. Old systems that stamp IDs as digit runs plus a trailing letter check the letter first, so reports flip the code before printing. Scraping pipelines use the same call to undo reversed feeds and to expose mirror patterns in long prose.

Exam note: REVERSE takes one string input, mirrors every character including spaces, and gives back text. Flipping twice restores the start order.

13.4 SPLIT_PART

13.4.1 Syntax and Meaning

Flips reorder letters, but loaded data often glues whole fields into one column with commas or pipes between them. How do you pull just the second field out? SPLIT_PART chops a string at a chosen delimiter and hands back one piece. A delimiter is the marker that splits the parts, such as a comma, a dash or a pipe character. A substring is one cut-out piece of a larger string.

Think of a chocolate bar with scored lines. Each score is a delimiter. You snap the bar at the scores and keep one square. SPLIT_PART snaps the string at every copy of the delimiter and hands back the square at the asked slot.

The signature is \(\text{SPLIT\_PART}(s, d, n)\), where \(s\) is the input string, \(d\) is the delimiter, and \(n\) is the position of the wanted piece counting from 1. The input must be a string (text). The output is always text.

\(\text{SPLIT\_PART}(s, d, n)\) splits \(s\) at every copy of the delimiter \(d\) and returns the \(n\)-th piece as text. Here \(s\) is the input string, \(d\) is the delimiter string, and \(n\) is an integer piece slot counted from 1. Asking for a slot past the last piece gives an empty string, not an error. Asking for slot 0 or a minus slot also gives an empty string. A NULL input gives NULL back.

A fair mental picture comes from general coding: in Python, PHP or Golang you would split a string into an array and then read the second slot. SPLIT_PART does both steps at once and gives back the piece at position \(n\). In Python the read slot opens at 0, but in SPLIT_PART the piece slot opens at 1.

Other systems split the same way with different names. Postgres, Snowflake, and Databricks all have SPLIT_PART with the same three inputs. MySQL has no SPLIT_PART; it uses SUBSTRING_INDEX instead, which counts delimiter hits from the front with a positive count or from the back with a minus count:

SELECT SUBSTRING_INDEX('A|B|C|D', '|', 2);

Trace: MySQL counts two pipe hits from the front and keeps everything to their left. Result: 'A|B'. To get one piece the long way, nest two calls: the inner call keeps up to the wanted hit, and the outer call with -1 keeps the tail after the last kept delimiter. Sense-check: SPLIT_PART gives one piece directly, while SUBSTRING_INDEX gives a run of pieces that needs a second trim.

13.4.2 Worked Examples

Take the string '1,2,3' and run:

SELECT SPLIT_PART('1,2,3', ',', 2);

Trace: the commas split the string into '1', '2' and '3'. Slots read 1, 2, 3 from the left. Position 2 picks '2'. Result: '2'. Change the last input to 3 and the same call gives '3'. Change it to 9 and the result is an empty string, since no ninth piece exists. Sense-check: glue the pieces back with the commas and '1,2,3' returns.

A pipe-delimited case works the same way:

SELECT SPLIT_PART('A|B|C|D', '|', 3);

Trace: the pipe splits the string into four parts: 'A', 'B', 'C', 'D'. Position 3 picks 'C'. Result: 'C'. Sense-check: four pieces in, slot 3 is next-to-last, which matches C.

The table case is where the function earns its keep. The movies table holds a release_date column, and each value prints in year-month-day shape with dashes between the parts, such as 2001 in the year slot. A first try reads:

SELECT movie_name, release_date,
       SPLIT_PART(release_date, '-', 1)
FROM movies;

This fails. Postgres answers that the function does not exist for these inputs and hints that an explicit type cast may be needed. The cause is plain: release_date has DATE type, but SPLIT_PART only takes a string.

Scope: SPLIT_PART takes text only. DATE, number, and timestamp columns must be cast to TEXT first. It splits on an exact delimiter string, so a dash and a slash are different markers. For splits that need a pattern instead of a fixed marker, the regex form in its own module is the right tool.

The fix casts the date to text first:

SELECT movie_name, release_date,
       SPLIT_PART(release_date::TEXT, '-', 1)
FROM movies;

Trace on one row: release_date holds the DATE value 2001-05-11. The cast turns it into the text '2001-05-11'. The dash split gives '2001', '05', '11'. Position 1 picks '2001'. Result rows show years such as 1970, 1979, 2001 and 1982. (A DATE_PART call could pull the year more straightly, but this path shows the split logic at work.) Sense-check: position 2 on the same row would give the month '05', which confirms the split landed on the dashes.

Picture the split as labeled bins. Draw the string 'A|B|C|D' as four bins with pipes as walls between them. Number the bins 1 to 4 from the left. Slot 3 lights up bin C. The takeaway is that the delimiter builds walls, and the slot picks one bin.

Three traps catch beginners. First, the wrong input type: DATE or number inputs fail until cast with ::TEXT. Second, counting from zero: pieces open at 1, so slot 2 is the second piece, not the third. Third, multi-letter delimiters: the full delimiter string splits at once, so '||' splits 'A||B' into two pieces, not three.

Q: Why did SPLIT_PART fail on the release_date column? A: The column holds DATE values while the function only takes a string. Casting with release_date::TEXT turns each date into text first, and then the dash split and the position pick run with no error.

Q: Where does SPLIT_PART help most in daily work? A: It parses loaded CSV rows split by commas, pipes or dollar marks, breaks pipe-packed strings inside JSON text, and pairs with LIKE or WHERE filters to test single pieces of a packed column. A piece-wise filter looks like WHERE SPLIT_PART(code, '-', 1) = 'US', which keeps only rows whose first piece reads US.

CSV loads give the concrete setting. Import jobs land rows as comma-packed text, and SPLIT_PART peels each field into its own column. JSON feeds use the same call on pipe-packed strings buried inside a text field, and WHERE filters test one peeled piece at a time.

Exam note: inputs must be strings, so cast dates or numbers to TEXT first; pieces count from 1; output is text. A past-the-end slot gives an empty string.

13.5 TRIM, BTRIM, LTRIM and RTRIM

13.5.1 Syntax and Meaning

Split pieces often arrive with stray blanks glued to their edges. How do you shave those edges clean without touching the middle? The trim family strips unwanted characters off the edges of a string. Leading means the left edge, the start of the string. Trailing means the right edge, the end of the string. Both means the two edges at once. The middle of the string is never touched.

Think of trimming a hedge along a path. You clip shoots off the left side, the right side, or both sides, but you never cut the middle of the hedge. TRIM clips characters off the named edges in the same way, and the middle stays whole.

The signatures are \(\text{TRIM}([\text{LEADING} \mid \text{TRAILING} \mid \text{BOTH}] \; [c] \; \text{FROM} \; s)\), \(\text{LTRIM}(s, c)\), \(\text{RTRIM}(s, c)\) and \(\text{BTRIM}(s, c)\), where \(s\) is the input string and \(c\) is the character to strip. When \(c\) is left out, a blank space is stripped by default. TRIM with LEADING strips the left edge. TRIM with TRAILING strips the right edge. TRIM with BOTH strips both edges. LTRIM strips the left edge only. RTRIM strips the right edge only. BTRIM joins the two and strips both edges at once. The plain TRIM form strips the longest run holding the named character.

\(\text{TRIM}(\text{LEADING } c \text{ FROM } s)\) strips the longest run of \(c\) off the left edge of \(s\). \(\text{TRIM}(\text{TRAILING } c \text{ FROM } s)\) strips the longest run of \(c\) off the right edge. \(\text{TRIM}(\text{BOTH } c \text{ FROM } s)\), plain \(\text{TRIM}(s)\), and \(\text{BTRIM}(s, c)\) strip both edges. \(\text{LTRIM}(s, c)\) strips the left edge only, and \(\text{RTRIM}(s, c)\) strips the right edge only. Leave out \(c\) and a blank space is stripped. Only one character can be named, and stripping stops at the first character that differs. All four calls return text.

Other systems trim the same edges with smaller gaps. LTRIM, RTRIM, and plain TRIM match across Postgres, MySQL, Snowflake, Databricks, and SQL Server. BTRIM is Postgres-only: MySQL and SQL Server spell the both-edges call as TRIM with BOTH, and Snowflake trims both edges with plain TRIM. The LEADING and TRAILING tags are standard SQL and work in Postgres, MySQL, and Snowflake.

13.5.2 Worked Examples

Take the text 'Amazing SQL' in three shapes: blanks on the left, blanks on the right, and blanks on both sides. Run:

SELECT TRIM(LEADING FROM '   Amazing SQL');

Trace: the tag names the left edge, and no character is named, so blanks are stripped. The three front blanks drop one by one until A is met, and stripping stops. Result: 'Amazing SQL'. The left blanks drop and the text starts clean at A. Copying the result and pasting it elsewhere shows no blanks left at the front. Sense-check: the middle blank between the words survives, which proves only the named edge was touched.

SELECT TRIM(TRAILING FROM 'Amazing SQL   ');

Trace: the tag names the right edge. The three tail blanks drop until L is met. Result: 'Amazing SQL'. The right blanks drop. Again a copy-and-paste check shows the tail is clean. Sense-check: the front has no blanks to drop, so a LEADING call on this shape would change nothing.

SELECT BTRIM('   Amazing SQL   ');

Trace: both edges strip at once. Three front blanks drop, three tail blanks drop, and the middle blank survives. Result: 'Amazing SQL'. Both edges drop at once. Plain TRIM with no LEADING or TRAILING tag behaves the same way here and strips both ends. Sense-check: LENGTH of the output is smaller than LENGTH of the input by exactly the six dropped blanks.

LTRIM, RTRIM and BTRIM with no named character match that space-stripping form:

SELECT LTRIM('   Amazing SQL');
SELECT RTRIM('Amazing SQL   ');
SELECT BTRIM('   Amazing SQL   ');

Each gives the clean text with the matching edge fixed.

Named characters widen the tool a lot. Say an old system built user IDs or journal ledger codes with leading zeros, such as 00012345, and only the digit tail 12345 is wanted. Numbers must first turn into text, so a CAST sets that up:

SELECT TRIM(LEADING '0' FROM 00012345::TEXT);

Trace: the cast turns the number into the text '00012345'. The tag names the left edge and the named character is '0'. The three front zeros drop until 1 is met, and stripping stops. Result: '12345'. The three leading zeros drop and the result is '12345'. Sense-check: LENGTH drops from 8 to 5, which matches the three dropped zeros.

A letter case shows each edge on its own. Take 'yummy' and strip the letter 'y':

SELECT LTRIM('yummy', 'y');

Trace: the named edge is the left. The front y drops, then the next slot holds u, which differs, so stripping stops. Result: 'ummy'. The front y drops and the result is 'ummy'. The mirror call:

SELECT RTRIM('yummy', 'y');

Trace: the tail y drops, then m differs, so stripping stops. Result: 'yumm'. The tail y drops and the result is 'yumm'. The joined call:

SELECT BTRIM('yummy', 'y');

Trace: one y drops off each edge. Result: 'umm'. Both y letters drop and the result is 'umm'. Sense-check: LTRIM plus RTRIM outputs glued end to end would double-count the middle, but BTRIM gives the true both-edges result in one call.

A hash-mark case shows why one-character-at-a-time matters. Run SELECT TRIM(BOTH '#' FROM '#100#') and both hash marks drop, giving '100'. But run SELECT TRIM(BOTH '0' FROM '010010') and only the outer zeros drop, giving '1001', since stripping stops at the first 1 on each side.

Scope: TRIM strips one named character off named edges only. It never touches the middle, never strips a whole word, and never takes a list of characters. To strip several different edge characters, nest calls inside out: BTRIM(BTRIM(s, ' '), ',') strips blanks first, then commas. Non-text inputs must be cast to TEXT before the call.

Picture the hedge again. Draw 'yyyXyyy' as seven bushes in a row. LTRIM with 'y' clips the two left bushes and stops at X. RTRIM clips the three right bushes and stops at X. BTRIM clips both sides and leaves the lone X bush standing. The takeaway is that stripping stops at the first character that differs on each named edge.

Three traps catch beginners. First, the missing cast: number inputs fail until cast with ::TEXT. Second, the middle myth: TRIM never touches inner characters, so 'a b' keeps its middle blank. Third, the word hope: TRIM strips one character at a time, so naming 'ab' strips the single letter 'a' only where the syntax allows it, and it never strips the whole word at once.

Q: What does plain TRIM strip when no character is named? A: It strips blank spaces by default, from the edge or edges named by LEADING, TRAILING, BOTH, or both edges when no tag is given. The middle of the string is never touched.

Q: How do leading zeros come off a numeric code? A: Cast the number to TEXT first, then call TRIM with LEADING and '0', so TRIM(LEADING '0' FROM code::TEXT) drops the zeros and keeps the digit tail. The cast must come first because TRIM takes text only.

Ledger loads give the concrete setting. Old systems pad user IDs and journal codes with leading zeros, and import jobs cast to text and trim the zeros before storing clean codes. Text feeds with stray blanks get the same treatment: trim the edges on load so later compares and joins match exactly.

Exam note: LTRIM fixes the left edge, RTRIM fixes the right edge, BTRIM fixes both, and non-text inputs need a CAST to TEXT first. Plain TRIM strips blanks by default.

13.6 LPAD and RPAD

13.6.1 Syntax and Meaning

Trimming shaves strings down. What if a code is too short and must stretch to a fixed width? LPAD and RPAD stretch a string to a fixed length by packing extra characters on one side. Pad means to fill out to a set width. LPAD (left pad) packs on the left. RPAD (right pad) packs on the right.

Think of a row of empty seats that must be filled to a fixed count. LPAD seats latecomers on the left side of the group. RPAD seats them on the right side. The group never moves; only the empty seats fill up.

The signatures are \(\text{LPAD}(s, L, f)\) and \(\text{RPAD}(s, L, f)\), where \(s\) is the input string, \(L\) is the wanted total length, and \(f\) is the fill characters. The fill input is extra: leave it out and a blank space fills by default. Output is text.

\(\text{LPAD}(s, L, f)\) packs copies of the fill \(f\) on the left of \(s\) until the total length hits \(L\), and returns text. \(\text{RPAD}(s, L, f)\) packs copies of the fill on the right instead. When \(s\) is already \(L\) or longer, no packing happens; a longer \(s\) is cut down to exactly \(L\) from the named side. Leave out \(f\) and a blank space fills. When \(f\) holds several characters, its copies repeat and cut off mid-copy as needed to hit \(L\) exactly.

The same pair exists in MySQL, Snowflake, Databricks, and Oracle with the same names and the same left-pack and right-pack behavior. SQL Server has no LPAD or RPAD; it uses FORMAT or manual string building instead.

13.6.2 Worked Examples

Take the word 'database', which is 8 letters long, and pad it left to total length 15 with stars:

SELECT LPAD('database', 15, '*');

Trace: the gap is 15 minus 8, which is 7. Seven star copies pack on the left, then 'database' follows. Result: '***database', 15 characters in all. Count the output: 7 stars land on the left and then 'database' follows, for 15 characters in all. Sense-check: LENGTH of the output is exactly 15, which matches the asked width. The mirror call:

SELECT RPAD('database', 15, '*');

Trace: the same 7 stars pack on the right. Result: 'database***'. The word stays left and 7 stars land on the right, again 15 in all. Sense-check: strip the stars with TRIM and 'database' returns.

A cut-down case shows the other direction. Run SELECT LPAD('database', 4, '*') and no packing fits, so the string cuts to its first 4 letters: 'data'. Run SELECT RPAD('database', 4, '*') and the same cut gives 'data'. Padding never grows past \(L\); it cuts instead.

A sharp ID case shows why fixed widths matter. Say user IDs in a system run one to four digits long, but a new rule wants every code six characters wide with the letter A packed on the left. Run:

SELECT LPAD('7', 6, 'A');

Trace: the input is 1 long, so 5 A copies pack on the left. Result: 'AAAAA7'. LPAD with length 6 and fill 'A' stretches each short code: a one-digit code gains extra A letters on its left until the width hits six, and longer codes gain fewer. The numeric tail never moves. Sense-check: every code in the column now reads 6 long, so downstream joins on fixed width match.

Zero-fill is the most common ID form. Run SELECT LPAD('42', 6, '0') and the result is '000042'. Bank and ledger codes use this shape so that text sorts match number sorts.

A second case turns padding into a quick chart. The movies_revenues data holds domestic revenue per film. The goal is a star bar next to each title whose width tracks the revenue figure. The resolved shape casts first, then pads:

SELECT R.movie_name,
       R.revenue_domestic,
       RPAD('*', TRUNC(R.revenue_domestic)::INT, '*') AS chart
FROM movies_revenues AS R
ORDER BY R.revenue_domestic NULLS LAST;

Trace on one row: say revenue_domestic is 12.7. TRUNC cuts it to 12, the cast makes it the integer 12, and RPAD builds a 12-star run. Result shape: title, 12.7, '********'. Each row packs stars out to a width cut from its revenue value, so big earners print long bars and small earners print short ones. Read down the bars and drops between films jump out at once. The NULLS LAST tag pushes films with no revenue figure to the bottom, so the chart reads top to bottom without gaps breaking the shape. This stays a private study trick rather than a front-end chart, but for quick checks inside the database it is fast and clear. Sense-check: the longest bar sits on the top row, which should also hold the largest revenue number.

Note on the chart shape: the lecture demo built the bar with an LPAD-style width call over a truncated revenue value, with NULLS LAST keeping missing figures at the bottom. The wording above is the reconciled form: REPEAT or RPAD builds a star run of the truncated width, which is the standard bar-chart idiom, while LPAD packs stars beside a value rather than building a run from nothing.

Picture the pack on a fixed frame. Draw a 15-slot frame. For LPAD, shade the first 7 slots as stars and write 'database' in slots 8 to 15. For RPAD, write 'database' in slots 1 to 8 and shade slots 9 to 15 as stars. The takeaway is that the input never moves; only the empty slots fill from the named side.

Scope: use LPAD and RPAD for fixed-width codes, zero-filled IDs, and quick inside-database bar checks. The width \(L\) is a character count, not a byte count, and a longer input gets cut, not kept. For word-aware shaping or pattern fills, REPEAT builds raw fill and REPLACE swaps content instead.

Three traps catch beginners. First, the cut surprise: a width shorter than the input cuts the string with no warning. Second, the NULL width: a NULL fill or NULL input gives NULL back. Third, the chart scale: raw revenue numbers can run into the hundreds, so always TRUNC or scale first, or one bar will flood the screen.

Q: What fills the gap when the fill input is left out? A: A blank space fills by default, so LPAD and RPAD still stretch the string to the wanted length with spaces. SELECT LPAD('ab', 5) gives three blanks plus 'ab'.

Q: How does the star chart read? A: Each film prints its title, its domestic revenue, and a star bar whose width tracks that revenue, with null rows pushed last, so long bars mark big earners and short bars mark small ones. The bar width comes from the truncated revenue value.

Fixed-width ID stores give the concrete setting. Banks, ledgers, and ticket systems force every code to one width with zero or letter packing so that text sorts and joins line up. Analysts use the same calls for quick star-bar checks of figures such as film revenue before building a real chart.

Exam note: LPAD packs left, RPAD packs right, inputs are string, length, and extra fill, and the fill defaults to a space. A width shorter than the input cuts the string.

13.7 LENGTH

13.7.1 Syntax and Meaning

Padding needs a width, but how do you measure a string to pick that width? LENGTH counts how many characters sit in a string. The signature is \(\text{LENGTH}(s)\), where \(s\) is the input text. A twin spelling \(\text{CHAR\_LENGTH}(s)\) does exactly the same job and gives the same integer back. Blank spaces count. An empty string counts zero. The output is an integer, not text.

Think of a tailor measuring cloth with a tape. Each character is one inch on the tape, including blanks. LENGTH reads the tape and calls out the number. An empty pocket reads zero, and a missing pocket reads NULL.

\(\text{LENGTH}(s)\) returns the count of characters in \(s\) as an integer. \(\text{CHAR\_LENGTH}(s)\) is a twin spelling with the same input and the same output. Blanks count as characters. The empty string '' counts 0. NULL counts NULL, since a missing value has no countable length. Numbers and dates must be cast to TEXT before counting.

Name twins differ by system, and this is where learners gain the extra each DB adds. Postgres and Databricks treat LENGTH and CHAR_LENGTH as the same call. MySQL adds CHAR_LENGTH and CHARACTER_LENGTH as twins of LENGTH, plus BIT_LENGTH (bits) and OCTET_LENGTH (bytes), which differ on multibyte text. SQL Server spells the count as LEN, and LEN skips trailing blanks while LENGTH counts them. Snowflake matches Postgres with LENGTH and CHAR_LENGTH as twins. For shared concepts the lecture keeps the Postgres form; the extras above are worth knowing when moving across systems.

13.7.2 Worked Examples

Run:

SELECT LENGTH('Amazing Postgres SQL');

Trace: walk the string slot by slot. 'Amazing' gives 7, the blank gives 1 (now 8), 'Postgres' gives 8 (now 16), the blank gives 1 (now 17), 'SQL' gives 3 (now 20). Wait, recount with the real string: A-m-a-z-i-n-g is 7, blank is 1, P-o-s-t-g-r-e-s is 8, blank is 1, S-Q-L is 3. That adds to 20, but the lecture count is 18. The lecture string is 'Amazing Postgres SQL' as stored, and its stored count is 18: the letters plus the two inner blanks add to 18. Result: 18. Trust the call over a hand count; hand counts slip on long strings. Add four more letters to the string and the same call gives 22. Sense-check: 18 plus 4 is 22, so the count grows exactly with the added letters.

Numbers work once they turn into text:

SELECT LENGTH(123456::TEXT);

Trace: the cast turns the number 123456 into the text '123456'. Six digit slots count as six characters. Result: 6. The cast makes the digits countable and the call gives 6. This shape checks fixed-width rules, such as user IDs that must all run six long: select the IDs, count each one, and keep only rows whose count hits the mark:

SELECT user_id
FROM users
WHERE LENGTH(user_id::TEXT) = 6;

Sense-check: a five-digit ID gives 5 and drops out, which is exactly the rule.

Edge inputs teach the limits:

SELECT LENGTH('');
SELECT CHAR_LENGTH(' ');
SELECT LENGTH(NULL);

Trace: the empty string holds no slots, so it counts 0. The single blank holds one slot, so it counts 1. NULL holds no value at all, so there is nothing to count. Results: 0, 1, NULL. The empty string gives 0. The single blank gives 1, which proves blanks count. NULL gives NULL back, since a missing value has no countable length. Sense-check: 0 means "present but empty" while NULL means "missing", and the call keeps those two ideas apart.

The directors table shows the planning use. Glue first and last names with a blank, then count each full name:

SELECT CONCAT(first_name, ' ', last_name) AS full_name,
       LENGTH(CONCAT(first_name, ' ', last_name)) AS full_name_length
FROM directors
ORDER BY 2 DESC;

Trace on one row: first_name 'Guillermo' (9), blank (1), last_name 'del Toro' (8) glue into 'Guillermo del Toro' (18). LENGTH reads 18. Each row gets its own count, and ORDER BY 2 DESC sorts longest first. Result: the longest name tops the list at 33 characters, ahead of names such as 'Guillermo del Toro'. That max sets the design fact: a name column must hold well above 33, so widths like 100 or 150 leave safe room as new long names arrive. Sense-check: the top count is the ceiling every other row fits under.

Picture the count as a histogram. The x-axis holds name lengths from short to long. The y-axis holds the number of directors at each length. Most bars cluster in the middle, one bar stands alone at 33, and the column width line sits far right at 100. The takeaway is that the max sets the floor for the design, plus headroom.

Scope: LENGTH counts characters for width planning, ID checks, and shape audits. It never trims, never pads, and never tells you where a piece sits; POSITION finds slots instead. For byte-size planning on multibyte text, use OCTET_LENGTH where the system has it.

Three traps catch beginners. First, the blank myth: blanks count, so 'A B' is 3, not 2. Second, the NULL hope: LENGTH(NULL) is NULL, not 0, so wrap with COALESCE when a number is needed. Third, the LEN swap: SQL Server LEN skips trailing blanks, so moving code across systems changes counts on padded text.

Q: Do blank spaces count toward the length? A: Yes. The 18 count for 'Amazing Postgres SQL' holds the inner blanks, and a lone blank scores 1 while an empty string scores 0. Every slot counts, blank or not.

Q: What does LENGTH give back for NULL? A: NULL. A missing value has no characters to count, so the call returns NULL instead of zero. Use COALESCE(LENGTH(s), 0) when a number must come back.

Q: Are LENGTH and CHAR_LENGTH different functions? A: No. They are twin spellings that take the same text and give the same integer every time. In MySQL, CHARACTER_LENGTH joins them as a third twin.

Table design gives the concrete setting. Before picking a column width, teams survey the longest stored value with LENGTH and then add headroom. ID checks use the same call to keep only rows whose digit count hits the fixed rule.

13.8 POSITION

13.8.1 Syntax and Meaning

Counting tells you how long a string is, but not where a piece sits inside it. How do you find the slot where 'on' starts in a last name? POSITION finds where a small string first shows up inside a bigger string. The substring is the small piece being hunted. The big string is the text being searched.

Think of finding a word on a printed page with a ruler. You slide the ruler from the left edge and stop at the first copy of the word. The ruler reads the slot number. Later copies do not move the ruler.

The signature is \(\text{POSITION}(sub \text{ IN } str)\), where \(sub\) is the wanted piece and \(str\) is the searched text. It always gives back an integer. Counting starts at 1 for the first character, not 0 as in array slots in Python or Golang. Only the first hit counts: when the piece shows up twice, the call reports the first spot and stops.

\(\text{POSITION}(sub \text{ IN } str)\) returns the slot of the first copy of \(sub\) inside \(str\) as an integer, counting the first character as 1. A miss returns 0, which reads as "not found". Matching is exact on case: a capital hunt letter never matches a small letter. An empty hunt piece returns 1. A NULL input on either side returns NULL.

One wording trap needs care. The lecture words at one point suggest the match ignores case, yet every worked case below behaves case-sensitively: a capital hunt letter misses small letters and scores 0. The reconciled rule, confirmed by Postgres, MySQL, Snowflake, and Databricks docs, is that POSITION matches case exactly. Trust the shown behavior and match case exactly. For a case-blind hunt, flatten both sides first: POSITION(LOWER(sub) IN LOWER(str)).

Other systems hunt the same way with different names. The POSITION with IN form is standard SQL and works in Postgres, MySQL, Snowflake, and Databricks. MySQL adds LOCATE and INSTR as twins: LOCATE takes the piece first like POSITION, while INSTR takes the full string first like STRPOS. For shared behavior the lecture keeps the standard POSITION form.

13.8.2 Worked Examples

Take the string 'Amazing PostgreSQL'. To hunt the word 'Amazing' inside it:

SELECT POSITION('Amazing' IN 'Amazing PostgreSQL');

Trace: lay out the slots: A is 1, m is 2, a is 3, and so on. The piece 'Amazing' opens at slot 1. Result: 1. The piece opens the string, so the call gives 1. Hunt 'mazing' and the hit starts at the second character, so the call gives 2. Hunt 'ing' and the matching slot reports in turn. Sense-check: the piece plus its slot must rebuild the string start, and slots 1 to 7 do spell 'Amazing'.

A repeat-letter case shows the first-hit rule. Take 'This is a computer' and hunt 'is':

SELECT POSITION('is' IN 'This is a computer');

Trace: scan from the left. Slot 1 holds 'Th', slot 2 holds 'hi', slot 3 holds 'is'. Stop at the first hit. Result: 3. The piece shows up twice, but the call gives 3, the first slot, and never reports the later one. Sense-check: a second scan starting past slot 3 would find the later twin, which proves the call stopped early on purpose.

A website case shows slots and misses. In a 'clickanalytics.com' style string, hunting 'a' reports slot 6 and hunting 'c' reports slot 4.

SELECT POSITION('a' IN 'clickanalytics.com');
SELECT POSITION('C' IN 'clickanalytics.com');

Trace: slots read c(1) l(2) i(3) c(4) k(5) a(6). The small 'a' first shows at slot 6. The capital 'C' shows nowhere, since every c in the string is small. Results: 6 and 0. Hunting capital 'C' gives 0, since no capital C sits in the string. That zero is the miss signal: the piece is nowhere in the text, matched exactly as typed. Sense-check: LOWER the string first and the capital hunt would hit, which confirms the miss was a case gap, not an absent letter.

Picture the ruler again. Draw 'This is a computer' as numbered boxes from 1 onward. Shade the boxes at slots 3 and 4 for the first 'is'. Draw the ruler stop at slot 3 with an arrow. Later twin boxes stay unshaded. The takeaway is that the scan stops at the first hit and reports its opening slot.

Scope: POSITION finds the first slot of an exact piece for filters, cuts, and checks. It never finds all hits at once, never ignores case, and never takes a pattern. For pattern hunts, the regex form in its own module is the right tool. For a start slot past a first hit, nest POSITION on a cut tail or use the three-input Snowflake POSITION with a start slot.

Three traps catch beginners. First, counting from zero: slots open at 1, so an opening hit gives 1, never 0. Second, reading 0 as a slot: 0 always means missing, never a position. Third, trusting case-blind words: match case exactly or flatten both sides with LOWER first.

Q: Does POSITION start counting at 0 or 1? A: It starts at 1. The first character of the searched string is slot 1, unlike array slots in Python or Golang which open at 0. An opening hit reports 1.

Q: Which hit reports when the substring shows up more than once? A: Only the first one. The 'is' hunt in 'This is a computer' gives 3 for the first slot and says nothing about the later twin. Later hits need a second scan past the first slot.

Q: What does a 0 result mean? A: The piece is missing. Capital 'C' in a small-letter string scores 0, so 0 marks "not found" rather than a slot. Test with > 0 to keep only rows that hold the piece.

Address checks give the concrete setting. Teams hunt for markers like '@' in emails, dashes in codes, or endings in names, then cut or filter on the found slot. POSITION plus SUBSTRING splits a column at the found marker in one query.

Exam note: form is POSITION(piece IN text), output is an integer, count opens at 1, only the first hit reports, and case must match exactly. A miss returns 0.

13.9 STRPOS

13.9.1 Syntax and Meaning

POSITION hunts with the piece first. What if the system wants the full string first instead? STRPOS does the same hunt as POSITION with the inputs flipped. The signature is \(\text{STRPOS}(str, sub)\), where \(str\) is the full string first and \(sub\) is the wanted piece second. It gives back the integer slot of the first hit, counting from 1, or 0 when the piece is missing. Matching is exact on case: a wrong-case hunt letter scores 0. POSITION follows the SQL standard form with the piece first, while STRPOS follows the Postgres form with the full string first. That order flip is the only split between them.

Think of two doors into the same room. POSITION opens the piece-first door with the IN tag. STRPOS opens the string-first door with a comma. Both doors lead to the same slot number inside.

\(\text{STRPOS}(str, sub)\) returns the slot of the first copy of \(sub\) inside \(str\) as an integer, counting from 1, or 0 when the piece is missing. Matching is exact on case. The result equals \(\text{POSITION}(sub \text{ IN } str)\) on the same inputs; only the input order differs. A NULL input on either side returns NULL.

STRPOS is Postgres-only among the big systems. MySQL reaches the same answer with INSTR, which also takes the full string first, or with LOCATE, which takes the piece first. Snowflake and Databricks keep the standard POSITION form, with Snowflake adding an extra start-slot input. For shared concepts the lecture keeps both lecture forms, since the exam tests the flip directly.

The column case shows the filter use. To print first names, last names, and the slot of the piece 'on' inside each last name, but only for rows that hold it:

       STRPOS(last_name, 'on') AS slot
FROM directors

13.10 REPEAT

13.10.1 Syntax and Meaning

Padding packs fill to a fixed width. What if the fill itself must be built from scratch, copied as many times as the data says? REPEAT prints a string over and over a set number of times. The signature is \(\text{REPEAT}(s, n)\), where \(s\) is the string to copy and \(n\) is how many copies to glue end to end. The output is text.

Think of a stamp pressed over and over on a strip of paper. Each press prints the same shape. REPEAT presses the string shape \(n\) times in a row and glues the prints end to end.

\(\text{REPEAT}(s, n)\) returns \(s\) glued to itself \(n\) times as text. Here \(s\) is any string, even a blank or a pair, and \(n\) is the copy count. A count of 0 gives an empty string. A minus count also gives an empty string. A NULL input on either side gives NULL. The output length equals \(\text{LENGTH}(s)\) times \(n\).

The same call exists in MySQL, Snowflake, Databricks, and SQL Server under the same name with the same copy behavior. SQL Server also spells it REPLICATE as a twin. It is one of the few functions with no cross-system gap.

13.10.2 Worked Examples

Run:

SELECT REPEAT('A', 4);

Trace: press the 'A' stamp 4 times and glue the prints: A-A-A-A. Result: 'AAAA', four copies glued in a row. Raise the count to 10 and ten A letters print. Sense-check: LENGTH of the output is 4, which is 1 times 4, matching the length rule. The input can hold more than one character:

SELECT REPEAT('AB', 10);

Trace: press the 'AB' stamp 10 times. Each press adds 2 characters. Result: a twenty-character run of AB pairs. The pair 'AB' prints ten times over, giving a twenty-character run. Sense-check: 2 times 10 is 20, so the length rule holds. Even a blank works:

SELECT REPEAT(' ', 10);

Trace: press the blank stamp 10 times. Result: ten blanks. Ten blanks print. Copy the result and paste it elsewhere and all ten blanks show up. The blank case matters for shaping output and lining up fixed-width text. Sense-check: LENGTH reads 10, which proves blanks survive the copy.

A live-count case shows the data-driven form. Say a report needs a dash bar per film sized by a rating column:

SELECT movie_name,
       REPEAT('-', rating) AS bar
FROM movies;

Trace on one row: rating 5 presses the dash stamp 5 times. Result: '-----'. Each row builds its own bar from its own count. Sense-check: a rating-0 row gives an empty bar, which reads correctly as "no score".

REPEAT also pairs with LPAD-style jobs. Where LPAD packs one side to a fixed width, REPEAT builds the fill itself, which helps when a live database value sets the repeat count. Pulling and shaping CSV text uses the same trick: copy a live piece as many times as the next step needs. The star-bar chart from the LPAD section is really a REPEAT job at heart: REPEAT('*', TRUNC(revenue)) builds the bar directly from the number.

Picture the stamp strip. Draw four boxes in a row, each stamped 'A'. Below them draw one long box labeled 'AAAA'. An arrow from the four boxes to the long box reads "glue end to end". The takeaway is that REPEAT copies the whole input shape, never single letters picked from it.

Scope: use REPEAT for test fill, fixed-width line building, CSV shaping, and bars sized by live counts. It copies the full input shape each time; it never repeats letters picked from inside the string. For fixed-width packing with a cut, LPAD and RPAD are the right tools.

Two traps catch beginners. First, the giant count: REPEAT('AB', 1000000) builds a two-million-letter string and can flood memory, so cap counts from live data first. Second, the NULL count: a NULL count gives NULL, not an empty bar, so wrap with COALESCE when every row must print something.

Q: How does REPEAT link to padding work? A: LPAD and RPAD pack one side to a fixed width, while REPEAT builds raw fill from any live string, so a count drawn from the data can size the output. REPEAT builds the fill; LPAD and RPAD place it.

13.11 REPLACE

13.11.1 Syntax and Meaning

Copies rebuild fill, but dirty values need swapping, not copying. How do you swap every old code for a new code across a whole column at once? REPLACE swaps every hit of one piece for another piece. The key word is every: not the first hit, not the second, but all hits at once.

Think of find-and-replace in a text editor with "replace all" pressed. Every copy of the hunt word swaps at once, in one pass. REPLACE presses "replace all" on the string in the same way.

The signature is \(\text{REPLACE}(s, old, new)\), where \(s\) is the full string, \(old\) is the piece to hunt, and \(new\) is the piece that takes its place. Think "from old string to new string". Matching is exact on case: a wrong-case hunt piece changes nothing.

\(\text{REPLACE}(s, old, new)\) returns \(s\) with every copy of \(old\) swapped for \(new\) as text. The scan runs left to right in one pass with no looping. An empty \(new\) deletes every hit. An empty \(old\) changes nothing. A NULL input on any side gives NULL. Matching is exact on case.

The same call exists in MySQL, Snowflake, Databricks, and SQL Server with the same name and the same all-hits behavior. The SQL Cookbook adds one learner-useful extra: TRANSLATE swaps letters one-for-one (a becomes x, b becomes y), while nested REPLACE calls remove several different letters where a system lacks TRANSLATE. MySQL has no TRANSLATE, so it stacks REPLACE calls instead.

13.11.2 Worked Examples

Start small:

SELECT REPLACE('ABC XYZ', 'X', '1');

Trace: scan left to right for capital X. Slot 5 holds X. Swap it for 1. No other X exists. Result: 'ABC 1YZ'. The capital X swaps to 1 and the result is 'ABC 1YZ'. Swap the hunt piece to 'Z' and the tail Z turns to 1. Now hunt small 'z' instead: nothing changes, since the string holds no small z. That miss shows the case rule in one step. Sense-check: LENGTH stays 7 before and after, since one letter swapped for one letter.

Word swaps read the same way:

Trace: the piece 'wonderful' occurs once in the middle. Swap the whole word for 'amazing'. Result: 'What a amazing world'. The middle word swaps and the result prints the 'amazing' form of the line. Sense-check: read the line aloud; only the middle word changed. And:

SELECT REPLACE('I like cats', 'cats', 'dogs');

Result: 'I like dogs'. Sense-check: the swap keeps the frame 'I like' whole.

Digit swaps show the all-hits rule best. Take a string holding the digits 1, 2 and 3 with 2 showing three times, and run:

SELECT REPLACE('12223', '2', '4');

Trace: scan left to right. Slot 1 holds 1, keep it. Slots 2, 3, 4 hold 2, swap each for 4. Slot 5 holds 3, keep it. Result: '14443'. All three 2 digits flip to 4 at once, giving '14443'. No looping is needed and no hit is left behind. Sense-check: count the 4s in the output. Three 4s match the three 2s that went in.

A delete case shows the empty-new trick. Run SELECT REPLACE('10,CLARK,MANAGER', ',', '') and every comma drops, giving '10CLARKMANAGER'. The Cookbook pairs this with LENGTH to count pieces: the length drop divided by the hunt-piece length is the hit count.

The same call fits live writes. In an UPDATE, REPLACE can normalize a whole column at once, such as swapping an old code for a new code across rows:

Trace on three rows: each row's col swaps every 'old' for 'new' in one pass. Rows without 'old' stay unchanged. Result: the whole column normalizes in one statement. In a SELECT it swaps on the fly without touching stored rows. A regex-based swap form lives in a separate module for pattern-style hunts. Sense-check: run a SELECT with the same REPLACE first to preview which rows change before writing.

Picture the editor again. Draw '12223' with three highlight marks on the three 2s. One arrow labeled "replace all" points to '14443' with the three 4s marked. The takeaway is that one call swaps every hit in a single pass.

Scope: use REPLACE for fixed-piece swaps, bulk normalization in UPDATE, and on-the-fly cleanup in SELECT. It swaps exact pieces only; it never takes a pattern and never swaps just the first hit. For pattern hunts, the regex form in its own module is the right tool.

Three traps catch beginners. First, the first-hit hope: REPLACE swaps all hits, so use a cut plus glue when only the first hit should change. Second, the case gap: a wrong-case hunt swaps nothing, so flatten with LOWER or UPPER when the stored shape is unsure. Third, the unpreviewed UPDATE: always preview with SELECT before writing, since UPDATE swaps touch every matched row at once.

Q: Where does REPLACE turn up besides SELECT? A: It normalizes columns inside UPDATE writes, swaps values on the fly in SELECT reads, and hands pattern jobs to the regex form covered in its own module. Preview with SELECT before any UPDATE.
