45.1 Listing Database Users and Database Sizes With and Without Indexes

Every index you add to speed up read queries acts like an extra appendix added to the back of a printed encyclopedia. While the extra index allows researchers to jump to topics instantly, it demands physical paper, thickens the binding, and forces librarians to update multiple registries every time a single fact changes.

PostgreSQL manages database security, user access, and storage footprint through internal system catalogs and administrative functions. Database administrators must regularly inspect active user roles, review permission flags, and track database storage growth. Using administrative tools like pgAdmin or the psql interactive terminal, administrators can query the pg_user system catalog view and database size functions for routine housekeeping.

45.1.1 Querying User Accounts and Privileges in pg_user

User accounts in PostgreSQL represent authorization roles that can log into the database cluster. The system catalog view pg_user provides access to information about database users. When querying pg_user, the system returns records detailing each user's identifiers and administrative capabilities.

SELECT * FROM pg_user;

In a standard installation, the system provides default accounts alongside user-created roles:

  • postgres: The default administrative superuser created during cluster initialization. The system assigns it a specific user ID (usesysid).
  • adam: A standard user account created by an administrator.

The pg_user catalog view exposes key permission attributes for each account:

  • usecreatedb: A boolean flag indicating whether the user can create new databases. Both postgres and adam hold this privilege in our environment.
  • usesuper: A boolean flag indicating superuser status. The postgres user has superuser access (usesuper = true), granting full administrative rights across the entire cluster. In contrast, adam does not have superuser privileges (usesuper = false).
  • userepl: A boolean flag specifying whether the user can initiate streaming replication connections or put the system into backup mode. The postgres user has replication permissions, whereas standard users typically do not.
  • valuntil: An expiration timestamp indicating password validity. If set to infinity, the user's password never expires. When configured with a specific date and time, the user cannot access the system after that date passes.

Regularly auditing pg_user is vital for system housekeeping, identifying dormant accounts, and enforcing access control policies.

Cross-Database Architectural Comparison: User Management & Metadata

Different relational engines structure user catalogs and authorization metadata differently:

  • PostgreSQL: Stores cluster-wide login roles in pg_authid, exposed safely via pg_user and pg_roles. Passwords use SCRAM-SHA-256 or MD5 hashes.
  • MySQL: Stores accounts in mysql.user, requiring both a username and a client host mask (such as 'adam'@'localhost' or 'adam'@'%').
  • Snowflake: Manages cloud identities globally through SHOW USERS;. Privileges attach strictly to roles rather than directly to users, enforcing pure Role-Based Access Control (RBAC).
  • Databricks: Governs user accounts and service principals through Unity Catalog (system.information_schema and account-level SCIM APIs), decoupling table authorization from the underlying compute clusters.

45.1.2 Measuring Database Sizes Using pg_database and pg_size_pretty

PostgreSQL stores database metadata in the pg_database master catalog. To measure the storage footprint of each database, administrators combine the pg_database_size() function with pg_size_pretty(). The pg_database_size() function accepts a database name or object identifier (OID) and returns its total on-disk size in raw bytes. The pg_size_pretty() function formats raw byte counts into human-readable units, such as kilobytes (KB) or megabytes (MB).

SELECT datname AS database_name,
       pg_size_pretty(pg_database_size(datname)) AS database_size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;

Executing this query in pgAdmin reveals the storage footprints of active databases:

  • learning: An active application database occupying about 12 MB.
  • hr: A human resources database occupying 8361 KB.
  • postgres: The default initial database created by the system.
  • template1 and template0: Internal template databases used by PostgreSQL as prototypes when executing CREATE DATABASE.

The reported database size represents total physical disk consumption, incorporating all table heap files, system catalogs, and indexes.

45.1.3 Worked Example: Measuring Index Overhead on Database Size

Indexes accelerate query performance, but they require physical disk storage. We evaluate the physical storage overhead of a secondary B-tree index by measuring database size before and after index creation on the employees table in the hr database.

Worked Example: Calculating Index Storage Overhead on Disk

Problem Statement: Measure the exact physical storage impact of adding a secondary B-tree index on the job_id column of the employees table in the hr database, and determine how many 8 KB pages were allocated.

Step 1: Record baseline database size Query the initial size of the hr database:

SELECT pg_size_pretty(pg_database_size('hr'));
  • Baseline database size (\(S_{\text{pre}}\)): 8361 KB.

Step 2: Create a B-tree index Apply a secondary B-tree index on the job_id column of the employees table using the mnemonic convention idx_<table_name>_<column_name>. Because an index named idx_employees_job_id already exists from an earlier session, create idx_employees_job_id_2:

CREATE INDEX idx_employees_job_id_2 ON employees (job_id);

Step 3: Measure post-creation database size and compute delta Re-run the database size query against pg_database:

SELECT pg_size_pretty(pg_database_size('hr'));
  • Post-creation database size (\(S_{\text{post}}\)): 8377 KB.

Step 4: Compute storage growth and page allocation Compute the change in storage size \(\Delta S\): \[ \Delta S = S_{\text{post}} - S_{\text{pre}} \] where:

  • \(\Delta S\) is the change in storage size,
  • \(S_{\text{post}}\) is the size after index creation (8377 KB),
  • \(S_{\text{pre}}\) is the baseline size before index creation (8361 KB).

Substituting the values: \[ \Delta S = 8377\text{ KB} - 8361\text{ KB} = 16\text{ KB} \]

Because PostgreSQL organizes on-disk storage into fixed 8 KB pages (\(P_{\text{size}} = 8\text{ KB}\)), calculate the number of new pages allocated (\(N_{\text{new\_pages}}\)): \[ N_{\text{new\_pages}} = \frac{\Delta S}{P_{\text{size}}} = \frac{16\text{ KB}}{8\text{ KB}} = 2\text{ pages} \] The 16 KB increase reflects the allocation of two 8 KB disk pages: one meta/root page and one initial leaf structure page.

Sense Check: The resulting delta of 16 KB is an exact integer multiple of the 8 KB PostgreSQL block size (\(2 \times 8\text{ KB} = 16\text{ KB}\)), confirming standard physical page allocation.

Scope & Assumptions: The Hidden Cost of Secondary Indexes

Creating an index is not a free optimization:

  1. Write Amplification: Every subsequent INSERT, DELETE, and non-HOT UPDATE on the employees table must synchronously update both the heap table and the idx_employees_job_id_2 B-tree index.
  2. Buffer Cache Contention: Index pages consume space in PostgreSQL's shared buffer pool (shared_buffers), potentially displacing frequently read table pages.
  3. Storage Bloat: In high-write workloads, B-tree page splits can lead to index bloat, where pages remain partially filled and consume disproportionate disk space.

Common Pitfalls:

  • Blind Over-Indexing: Creating indexes on low-cardinality columns (such as boolean flags) where sequential scans are faster than index scans.
  • Ignoring Write Penalties: Forgetting that tables with heavy batch inserts slow down dramatically if laden with multiple secondary indexes.
  • Expecting Immediate Space Recovery: Dropping an index reclaims disk space immediately for that specific index file, but deleting indexed rows does not automatically shrink index files on disk without a REINDEX or VACUUM FULL.

Recap & Bridge: Secondary indexes provide rapid key lookups at the cost of measurable physical disk growth and write-time maintenance overhead. Tracking database size through pg_database_size() and pg_size_pretty() gives engineers concrete visibility into this storage trade-off before and after DDL changes.

Exam note: Expect questions asking how to calculate storage growth following DDL operations such as CREATE INDEX. Always express the storage delta as \(\Delta S = S_{\text{post}} - S_{\text{pre}}\) and verify whether the resulting growth aligns with multiples of the engine's page size (8 KB in PostgreSQL, 16 KB in MySQL InnoDB).

45.1.4 Student Questions and Answers

Q: Does creating an index affect the overall database size, and how can we verify the physical overhead?

A: Yes, an index is an independent physical structure on disk that consumes storage space. You can verify this overhead by running pg_size_pretty(pg_database_size('hr')) before and after executing CREATE INDEX. In our environment, creating a single column index increased the database size from 8361 KB to 8377 KB, adding 16 KB of index pages (exactly two 8 KB pages).

45.2 Inspecting Tables, Views, and Information Schema Metadata

A database view is like a tinted glass window looking into several rooms of a house. While anyone looking through the window can easily inspect the furniture inside, throwing a new chair at the glass window will not magically place the chair into the correct bedroom—unless an automated robotic handler stands at the window to route the furniture appropriately.

PostgreSQL adheres strictly to the ANSI SQL standard by providing the information_schema. This standardized schema consists of metadata views that expose structural details about schemas, tables, views, columns, and constraints across the database without requiring direct queries against cryptic, engine-specific low-level system catalogs.

45.2.1 Querying Base Tables and Views in information_schema.tables

The system view information_schema.tables lists all relations defined within the current catalog. To inspect relation definitions in the public schema, administrators query:

SELECT table_catalog,
       table_schema,
       table_name,
       table_type,
       is_insertable_into,
       commit_action
FROM information_schema.tables
WHERE table_schema = 'public';

Key columns returned by this query include:

  • table_catalog: The name of the database containing the relation.
  • table_schema: The schema namespace owning the relation (such as public).
  • table_name: The identifier of the table or view.
  • table_type: Distinguishes physical relations (BASE TABLE) from virtual query layers (VIEW) and temporary relations (LOCAL TEMPORARY).
  • is_insertable_into: An ANSI standard indicator (YES or NO) stating whether direct SQL INSERT statements are permitted.
  • commit_action: Details persistence behavior for temporary relations when transactions commit (such as PRESERVE ROWS or DELETE ROWS).

Adopting clear naming standards—such as prefixing virtual relations with v_ (for instance, v_directors or v_all_actors_and_directors)—allows development teams and data integration tools to immediately differentiate virtual views from physical base tables.

45.2.2 Inspecting View Definitions and Updatability Rules in information_schema.views

The view information_schema.views exposes the architectural properties and underlying source SQL definitions of all views created in the database:

SELECT table_schema,
       table_name,
       view_definition,
       check_option,
       is_updatable,
       is_insertable_into,
       is_trigger_updatable,
       is_trigger_deletable,
       is_trigger_insertable_into
FROM information_schema.views
WHERE table_schema = 'public';

Important architectural properties exposed include:

  • view_definition: The exact SELECT query statement defining the view, allowing database engineers to extract, audit, and reconstruct view logic dynamically.
  • check_option: Indicates whether CHECK OPTION (CASCADED, LOCAL, or NONE) was specified during creation. When enabled, rows inserted or updated through the view must satisfy the view's filtering conditions.
  • is_updatable: Indicates whether the view permits UPDATE and DELETE statements (YES or NO).
  • is_insertable_into: Indicates whether new records can be inserted directly through the view (YES or NO).
  • Trigger status columns (is_trigger_updatable, is_trigger_deletable, is_trigger_insertable_into): Indicate whether INSTEAD OF triggers exist on the view to handle write operations on otherwise non-updatable structures.

The ANSI SQL-92 and PostgreSQL updatability rules strictly govern whether a view allows write operations:

  1. Single-Table Views: A view defined over exactly one base table without aggregate functions (SUM, AVG), grouping clauses (GROUP BY, HAVING), window functions, DISTINCT, or set operations (UNION, EXCEPT) is automatically updatable and insertable. For example, a filtered view on directors reports is_insertable_into = YES and is_updatable = YES.
  2. Multi-Table Join Views: When a view joins multiple tables (such as v_all_actors_and_directors, which combines actors and directors), the query planner cannot determine how to distribute inserted values without ambiguity. Consequently, PostgreSQL reports is_insertable_into = NO and is_updatable = NO.

Worked Example: Inspecting View Definitions and Updatability Across Schemas

Problem Statement: Inspect the information_schema.views metadata for both user-defined views in public and internal system views in information_schema to evaluate view logic and write permissions.

Step 1: Inspect user view updatability Query the public schema views to evaluate whether joined views allow direct modifications:

SELECT table_name,
       is_updatable,
       is_insertable_into,
       is_trigger_insertable_into
FROM information_schema.views
WHERE table_schema = 'public';
  • For single-table view v_directors: is_updatable = YES, is_insertable_into = YES, is_trigger_insertable_into = NO.
  • For multi-table join view v_all_actors_and_directors: is_updatable = NO, is_insertable_into = NO, is_trigger_insertable_into = NO.

Step 2: Inspect source query definition Retrieve the underlying query defining v_directors:

SELECT view_definition
FROM information_schema.views
WHERE table_name = 'v_directors';
  • Output: SELECT directors.director_id, directors.first_name, directors.last_name FROM directors;

Step 3: Check for INSTEAD OF trigger resolution To enable inserts on v_all_actors_and_directors, attach an INSTEAD OF INSERT trigger. Once attached, is_trigger_insertable_into flips from NO to YES, permitting client insert operations.

Sense Check: The metadata values (YES vs NO) conform directly to the relational algebra requirement: single base table projections preserve row identities, whereas multi-table joins require explicit trigger routing.

45.2.3 Querying Internal System Views and Exploring Standard SQL Structures

PostgreSQL implements the entire information_schema by querying its own internal system views and catalogs:

SELECT table_name, view_definition
FROM information_schema.views
WHERE table_schema = 'information_schema';

This query returns 61 distinct internal system views. Reviewing their view_definition columns reveals standard ANSI SQL statements utilizing inner joins, outer joins, subqueries, and CASE expressions over underlying PostgreSQL catalogs like pg_class, pg_attribute, pg_type, and pg_namespace. This elegant design proves that the database engine uses the exact same relational query language to expose its own internal metadata as application developers use for business logic.

Cross-Database Architectural Comparison: Views & Updatability

How different database platforms handle view metadata and updatability:

  • PostgreSQL: Follows ANSI standard updatability rules. Supports INSTEAD OF triggers for INSERT, UPDATE, and DELETE on complex views.
  • MySQL: Supports information_schema.views. Multi-table views can sometimes be updated if the update statement references columns from exactly one base table in the join and adheres to key-preserved table rules. However, MySQL does NOT support INSTEAD OF triggers on views; non-updatable complex views cannot be made insertable via triggers.
  • Snowflake: Supports information_schema.views and SHOW VIEWS;. As a cloud analytical warehouse, Snowflake views are strictly read-only (SELECT only). Snowflake provides Secure Views (CREATE SECURE VIEW), which prevent query optimizations from exposing internal data to unauthorized users through error messages or timing analysis.
  • Databricks: Exposes system.information_schema.views in Unity Catalog. Spark SQL views are virtual logical plans and are strictly read-only. Modifying underlying data requires writing to Delta Lake tables directly.

Scope & Assumptions: View Updatability Boundaries An automatically updatable view must satisfy all of the following conditions:

  1. Exactly one entry in the FROM clause (a base table or another updatable view).
  2. No WITH, DISTINCT, GROUP BY, HAVING, LIMIT, or OFFSET clauses in the query definition.
  3. No set operations (UNION, INTERSECT, EXCEPT).
  4. Select list contains direct column references (not expressions, mathematical calculations, or aggregate functions).

Common Pitfalls:

  • Assuming Multi-Table Views Are Writable: Attempting an INSERT into a joined view without an INSTEAD OF trigger results in a runtime error: ERROR: cannot insert into view ....
  • Forgetting WITH CHECK OPTION: Creating an updatable view with a WHERE filter without WITH CHECK OPTION allows users to insert rows that immediately vanish from the view because they fail the filter condition.
  • Overlooking Performance Overhead: Relying on views nested inside other views can create complex query execution plans if the query planner cannot collapse the subqueries into the outer query.

Recap & Bridge: The information_schema.tables and information_schema.views views provide a vendor-portable, declarative interface to inspect relation structures and view definitions. While single-table views are automatically writable, multi-table join views require explicit procedural routing via triggers.

Exam note: Be prepared to determine whether a view is automatically updatable versus requiring an INSTEAD OF trigger based on the presence of joins, aggregates, or set operations.

45.2.4 Student Questions and Answers

Q: Why does is_insertable_into show NO for multi-table join views, and can records ever be inserted through them?

A: Many developers hold the misconception that multi-table join views are insertable just like single-table base views. However, when a view joins multiple underlying tables, the database cannot determine how to distribute inserted column values across distinct base tables without ambiguity. Therefore, PostgreSQL sets is_insertable_into = NO. Records can only be inserted through a multi-table join view if an administrator creates explicit INSTEAD OF triggers on the view to intercept incoming writes and route the data into the appropriate base tables.

45.3 Retrieving Column Metadata from Information Schema

Running SELECT * FROM table LIMIT 1 to find out what columns exist in a database is like hiring a moving truck to deliver a single mystery crate just to read the shipping label. In contrast, querying information_schema.columns reads the warehouse manifest directly in a fraction of a millisecond without loading a single byte of table row data into memory.

When managing complex schemas or developing database automation tools, engineers need to inspect column definitions programmatically. The ANSI standard view information_schema.columns provides a comprehensive catalog of column-level properties across all tables and views in the database.

45.3.1 Querying Column Details via information_schema.columns

To inspect the structural layout of a table, administrators query information_schema.columns filtering by the target table name and schema:

SELECT column_name,
       data_type,
       ordinal_position,
       is_nullable,
       column_default,
       udt_name
FROM information_schema.columns
WHERE table_name = 'movies'
ORDER BY ordinal_position ASC;

Key attributes returned by this metadata query include:

  • column_name: The identifier of the column, such as movie_id, name, or length.
  • data_type: The standardized SQL data type, such as integer or character varying.
  • ordinal_position: The 1-based sequential position of each column in the table definition (e.g., column 1, 2, 3).
  • is_nullable: A boolean string (YES or NO) indicating whether the column permits null values.
  • column_default: The default expression or sequence generator attached to the column.
  • udt_name: The internal user-defined or native type identifier used by PostgreSQL's type system (e.g., int4, varchar).

Worked Example: Querying Column Details for Movies and Directors Tables

Problem Statement: Retrieve complete structural metadata, data types, and ordinal positions for the movies and directors tables to prepare for an automated data pipeline integration.

Step 1: Inspect the movies table layout Execute a column metadata query against movies:

SELECT column_name,
       data_type,
       ordinal_position,
       is_nullable
FROM information_schema.columns
WHERE table_name = 'movies'
ORDER BY ordinal_position;

Results:

  1. movie_id: integer, ordinal position 1, is_nullable = NO (Primary Key).
  2. name: character varying, ordinal position 2, is_nullable = NO.
  3. length: integer, ordinal position 3, is_nullable = YES.

Step 2: Inspect the directors table layout Execute a corresponding query against directors:

SELECT column_name,
       data_type,
       ordinal_position,
       is_nullable
FROM information_schema.columns
WHERE table_name = 'directors'
ORDER BY ordinal_position;

Results:

  1. director_id: integer, ordinal position 1.
  2. first_name: character varying, ordinal position 2.
  3. last_name: character varying, ordinal position 3.
  4. date_of_birth: date, ordinal position 4.
  5. nationality: character varying, ordinal position 5.

Sense Check: The query returns schema architecture alone without touching table heap pages on disk, providing an exact, zero-overhead structural inventory.

45.3.2 Practical Applications for Schema Comparison and Automation

While executing SELECT * FROM table LIMIT 1 shows column names alongside sample data, querying information_schema.columns provides distinct advantages:

  1. Automated Schema Comparison: Programmatic scripts compare information_schema.columns across development, staging, and production databases to instantly flag missing columns, mismatched data types, or altered nullability constraints.
  2. Dynamic Code Generation: Object-relational mapping (ORM) libraries, code generators, and database migration tools query column metadata to assemble dynamic INSERT, UPDATE, and SELECT statements at runtime.
  3. ETL Pipeline Validation: Data ingestion pipelines query column definitions to validate schema compatibility and data type alignment prior to executing large batch ingest operations.

Cross-Database Architectural Comparison: Column Metadata Inspection

How column structural metadata is accessed across database platforms:

  • PostgreSQL: Implements standard information_schema.columns. In the psql shell, \d <table_name> queries the underlying catalogs pg_attribute, pg_class, and pg_type.
  • MySQL: Provides information_schema.columns with engine-specific extensions such as COLUMN_TYPE (displaying complete precision e.g. varchar(255) or enum('A','B')), COLUMN_KEY (PRI, UNI, MUL), and EXTRA (e.g. auto_increment). MySQL developers also frequently use DESCRIBE <table_name>; or SHOW COLUMNS FROM <table_name>;.
  • Snowflake: Supports information_schema.columns, including Snowflake-native semi-structured data types like VARIANT, ARRAY, and OBJECT. Snowflake also provides DESCRIBE TABLE <table_name>;.
  • Databricks: Exposes system.information_schema.columns via Unity Catalog. In Apache Spark / Delta Lake, developers query column metadata with DESCRIBE EXTENDED <table_name>;, which displays column comments, partition designations, and schema evolution properties.

Scope & Assumptions: Case Sensitivity in Metadata Filters By default, the ANSI SQL standard and PostgreSQL store unquoted identifiers in lowercase. When filtering information_schema.columns:

  • In PostgreSQL: WHERE table_name = 'movies' matches table movies. If the table was created with double quotes (e.g., CREATE TABLE "Movies"), the filter must match the exact case: WHERE table_name = 'Movies'.
  • In Oracle: Identifiers default to uppercase (WHERE table_name = 'MOVIES').
  • In MySQL: Table name case sensitivity depends on the underlying host operating system filesystem (lower_case_table_names).

Common Pitfalls:

  • Relying on Ordinal Positions in Production Queries: Assuming that columns will always maintain the same ordinal position over time. Adding a column or modifying a schema can alter column sequences, which breaks applications relying on position-based indices rather than column names.
  • Using SELECT * in Production Code: Querying all columns instead of explicit projections increases network bandwidth consumption, defeats index-only scans, and causes application failures when new columns are added.

Recap & Bridge: Querying information_schema.columns enables robust, programmatic schema validation and automation without incurring the I/O cost of reading table data. Next, we explore system information functions that expose session-level identity and environment runtime parameters.

Exam note: Remember that information_schema.columns allows you to extract data types, nullability, default values, and ordinal positions programmatically across relations without loading physical row records.

45.3.3 Student Questions and Answers

Q: Why should we query information_schema.columns instead of running SELECT * to inspect table columns?

A: Running SELECT * retrieves row data from disk pages rather than architectural metadata. In contrast, querying information_schema.columns returns exact data types, nullability, character lengths, default expressions, and ordinal positions without loading table data into memory, making it ideal for automated schema comparisons, dynamic query generation, and zero-I/O structural validation.

45.4 Inspecting System Metadata via System Information Functions

Think of session identities like security badges in a high-security research facility. The badge you swipe at the main entrance identifies who entered the facility (session_user). However, when you step inside a sterile cleanroom and put on the lead apron of a radiation technician to trigger a specialized instrument (SECURITY DEFINER), your active operating authority (current_user) becomes that technician—even though the building entry log still records your original badge.

PostgreSQL provides built-in system information functions that report current session states, active catalog namespaces, and server build characteristics. These functions provide immediate diagnostic visibility into the operating identity and environmental runtime configuration of any database connection.

45.4.1 Session and Catalog Information Functions

A single SQL statement can inspect the primary identifiers governing the current execution context:

SELECT current_catalog,
       current_database(),
       current_schema,
       current_user,
       session_user;

These functions return the active connection properties:

  • current_catalog: The name of the current database catalog (e.g., movies). In PostgreSQL, an instance contains databases, and in ANSI SQL terminology, a catalog and a database are synonymous.
  • current_database(): The name of the active database, returning the identical value as current_catalog.
  • current_schema: The current default schema namespace used for resolving unqualified relation names (typically public).
  • current_user: The user identifier under which active permission checks are evaluated (e.g., postgres).
  • session_user: The user identifier that initially authenticated and established the physical client connection to the server.

Under typical interactive queries, current_user and session_user are identical. However, when executing stored procedures or functions defined with SECURITY DEFINER, current_user temporarily switches to the role of the procedure's owner. Similarly, executing SET ROLE <role_name> changes the effective current_user while leaving session_user anchored to the original authenticated login.

Worked Example: Inspecting Session Metadata and Server Release Details

Problem Statement: Retrieve active connection metadata, evaluate role delegation states, and inspect compiler specifications for the running PostgreSQL server instance.

Step 1: Query session identifiers Execute the session diagnostic query:

SELECT current_catalog AS catalog_name,
       current_database() AS database_name,
       current_schema AS default_schema,
       current_user AS effective_user,
       session_user AS authenticated_user;

Results:

  • catalog_name: movies
  • database_name: movies
  • default_schema: public
  • effective_user: postgres
  • authenticated_user: postgres

Step 2: Inspect server compilation and architecture Execute the version() function:

SELECT version();

Result: PostgreSQL 12.4 on x86_64-apple-darwin19.6.0, compiled by Apple LLVM version 12.0.0 (clang-1200.0.32.2), 64-bit

Analysis of version output:

  • Server Release: PostgreSQL 12.4.
  • Host Platform: 64-bit Darwin (macOS) architecture.
  • Compiler: Apple LLVM Clang compiler.

Sense Check: The session query confirms that the database and catalog represent the same logical namespace (movies), and the compiler metadata confirms a 64-bit server build.

45.4.2 Server Version and Compilation Metadata

The version() function returns a detailed string containing the exact major and minor release number, host operating system architecture, and C compiler release used to build the server binary.

When writing automated deployment scripts or database migration utilities, relying on parsing version() text can be cumbersome. For programmatic version comparisons, PostgreSQL also provides configuration parameters:

  • SHOW server_version;: Returns the clean version string (e.g., 12.4).
  • SHOW server_version_num;: Returns an integer (e.g., 120004), allowing automated scripts to perform mathematical comparisons like server_version_num >= 120000 to verify feature availability before running modern SQL constructs.

Cross-Database Architectural Comparison: Session & Identity Functions

How different database engines expose session identities and version metadata:

  • PostgreSQL: Catalog and database are synonymous (current_catalog = current_database()). Schemas live inside databases. Distinguishes current_user from session_user.
  • MySQL: Treats database and schema as synonymous (DATABASE() returns the active schema). Does not have a separate catalog layer. Exposes USER() (the client connection string user@host) and CURRENT_USER() (the resolved privilege entry matched in mysql.user). Uses VERSION().
  • Snowflake: Exposes multi-tier hierarchy functions: CURRENT_ORGANIZATION_NAME(), CURRENT_ACCOUNT(), CURRENT_DATABASE(), CURRENT_SCHEMA(), CURRENT_WAREHOUSE(), CURRENT_ROLE(), CURRENT_USER(), and CURRENT_VERSION().
  • Databricks: In Unity Catalog, supports current_catalog(), current_database() / current_schema(), and current_user(). Spark SQL separates the 3-level namespace: catalog.schema.table.

Scope & Assumptions: SECURITY DEFINER Execution Risks When a function runs with SECURITY DEFINER:

  1. The function executes with the permissions of the user who created the function, not the user calling it.
  2. If the function does not explicitly specify a fixed search_path (e.g., SET search_path = pg_catalog, public), a malicious user can create temporary tables or functions matching names in the procedure, hijacking execution via search path spoofing.

Common Pitfalls:

  • Confusing Database and Schema: In PostgreSQL, a database is a physical catalog barrier (you cannot directly join across different databases in a single query without foreign data wrappers), whereas schemas are logical namespaces inside a database that can be joined effortlessly.
  • Relying on session_user for Permissions: Checking authorization against session_user instead of current_user leads to security flaws during role impersonation or nested procedure execution.

Recap & Bridge: System information functions provide vital telemetry about connection credentials and server architecture. Understanding the operational divergence between current_user and session_user is crucial for auditing privilege boundaries, which leads directly to checking granular object permissions in the next section.

45.5 Checking Permissions and Privileges Across Databases, Schemas, Tables, and Columns

Database permissions resemble the concentric security perimeters of a commercial bank. Holding an entry key card to the bank's front lobby (database CONNECT) does not grant access to the subterranean vault hallway (schema USAGE). Reaching the vault hallway does not unlock an individual safety deposit box (table SELECT), and unlocking a box does not allow you to rewrite the certified deeds inside (column UPDATE).

Database security administration requires validating access privileges across various database scopes. PostgreSQL offers built-in privilege inquiry functions that accept object names and return boolean values (true or false). These functions eliminate the need to parse raw access control lists (ACLs) stored in system catalogs like pg_class.relacl.

45.5.1 Built-in Privilege Verification Functions

Privilege inquiry functions operate across four hierarchical levels, allowing administrators to audit the entire security chain:

  1. Database Level: has_database_privilege([user,] database, privilege)
  • Evaluates privileges such as CREATE, CONNECT, or TEMPORARY.
  • Example: Checking if the current session can create schemas within the hr database:
     SELECT has_database_privilege('hr', 'CREATE');

Returns true for administrative accounts and false for unprivileged roles.

  1. Schema Level: has_schema_privilege([user,] schema, privilege)
  • Evaluates USAGE and CREATE privileges.
  • USAGE allows looking up objects within the target schema.
  • CREATE allows creating new relations, functions, and views within the schema.
  • Example: Checking permissions in the public schema:
     SELECT has_schema_privilege('public', 'USAGE');  -- returns true
     SELECT has_schema_privilege('public', 'CREATE'); -- returns true
  1. Table Level: has_table_privilege([user,] table, privilege)
  • Evaluates relation-level operations: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, and TRIGGER.
  • Example: Checking insert permissions on the movies table:
     SELECT has_table_privilege('movies', 'INSERT'); -- returns true
  1. Column Level:
  • has_any_column_privilege([user,] table, privilege): Tests whether the user holds the specified privilege on at least one column of the relation.
     SELECT has_any_column_privilege('movies', 'SELECT'); -- returns true
  • has_column_privilege([user,] table, column, privilege): Tests whether a specific user holds the privilege on an explicit, named column.

45.5.2 Checking User-Specific and Column-Level Permissions

When auditing security policies for specific users, administrators pass the target role name as the first argument to has_column_privilege():

  1. Testing the administrative superuser account postgres:
   SELECT has_column_privilege('postgres', 'movies', 'movie_name', 'UPDATE');

Returns true. Superusers bypass standard permission checks and retain unrestricted access across all objects.

  1. Testing the standard user account adam:
   SELECT has_column_privilege('adam', 'movies', 'movie_name', 'UPDATE');

Returns false. Because adam was not explicitly granted column-level UPDATE privileges on movie_name, the function returns false.

45.5.3 Worked Example: Verifying Privileges for Superusers and Standard Users

Worked Example: Auditing Column Update Privileges for Superuser and Standard Roles

Problem Statement: Execute an automated security audit on the movies relation to verify whether standard user adam and superuser postgres possess update rights on the sensitive column movie_name.

Scenario Setup:

  • Table: movies
  • Target Column: movie_name
  • Operation: UPDATE
  • Roles evaluated: postgres (superuser) and adam (standard user)

Step 1: Audit superuser permissions Execute the column privilege function for role postgres:

SELECT has_column_privilege('postgres', 'movies', 'movie_name', 'UPDATE') AS postgres_can_update;
  • Result: true. By virtue of usesuper = true, the superuser account can update any column across any relation.

Step 2: Audit standard user permissions Execute the column privilege function for role adam:

SELECT has_column_privilege('adam', 'movies', 'movie_name', 'UPDATE') AS adam_can_update;
  • Result: false. The standard user does not have update grants on this column.

Step 3: Audit broad table access Verify whether adam has read access on any column in the relation:

SELECT has_any_column_privilege('adam', 'movies', 'SELECT') AS adam_can_read_any;
  • Result: true. User adam can read data from the table, but column writes are strictly blocked.

Sense Check: The permission disparity demonstrates fine-grained access control: read visibility on a table does not imply column-level write authorization.

Cross-Database Architectural Comparison: Privilege Auditing

How permissions and privilege auditing compare across database platforms:

  • PostgreSQL: Offers built-in boolean verification functions (has_table_privilege, has_column_privilege, etc.) that can be embedded directly in SELECT expressions, making automated security scans extraordinarily concise.
  • MySQL: Lacks built-in boolean privilege inquiry functions. Administrators must inspect SHOW GRANTS FOR 'user'@'host' or run queries against mysql.tables_priv, mysql.columns_priv, or information_schema.table_privileges.
  • Snowflake: Relies entirely on Role-Based Access Control (RBAC). Users inherit privileges from roles. Privileges are audited via SHOW GRANTS TO USER <user>, SHOW GRANTS ON TABLE <table_name>, or querying SNOWFLAKE.ACCOUNT_USAGE.GRANTS_TO_ROLES. Column-level masking is managed declaratively via Masking Policies.
  • Databricks: In Unity Catalog, permissions are audited with SHOW GRANTS ON TABLE <table_name>; and queried via system.information_schema.table_privileges. Column-level security uses column masks and row filters attached to Unity Catalog tables.

Scope & Assumptions: Privilege Inheritance via Roles PostgreSQL supports role inheritance (INHERIT). When has_table_privilege('adam', 'movies', 'SELECT') evaluates to true, adam might not have been granted the permission directly; rather, adam may belong to a group role (such as analysts) that holds the grant. The privilege functions automatically traverse the full role inheritance graph.

Common Pitfalls:

  • Relying on Default PUBLIC Privileges: Forgetting that historical PostgreSQL versions granted CREATE on the public schema to the pseudo-role PUBLIC, potentially allowing untrusted users to create rogue relations.
  • Conflating has_any_column_privilege with Full Table Access: Assuming that has_any_column_privilege('adam', 'movies', 'SELECT') = true means the user can read all columns. The user might only have access to a single non-sensitive column.
  • Neglecting Automated Escalation Audits: Failing to automate privilege checking scripts leaves databases vulnerable to undetected privilege creep and unauthorized permission escalation.

Recap & Bridge: PostgreSQL's built-in privilege verification functions provide a powerful, programmable mechanism to audit access rights across databases, schemas, tables, and individual columns. Exam note: Remember that has_any_column_privilege checks whether access exists on at least one column of a table, whereas has_column_privilege tests an explicit user, table, and column combination.

45.5.4 Student Questions and Answers

A: has_any_column_privilege checks whether a user holds access to at least one column in a table, making it ideal for high-level read authorization checks. In contrast, has_column_privilege checks access on an explicit user, table, and column, which is essential for fine-grained security auditing such as verifying column-level update or select restrictions.

45.6 System Administration and Configuration Functions

Modifying runtime configuration parameters in a database session is like adjusting the digital thermostat in a rental car. While turning the dial changes the cabin temperature for your personal journey (set_config), it does not permanently rebuild the car's factory engine settings (postgresql.conf). Meanwhile, built-in server file functions act like an internal diagnostic port under the dashboard—immensely powerful for certified technicians, but heavily secured to prevent unauthorized drivers from tampering with the vehicle's computer.

PostgreSQL provides system administration functions to inspect run-time configuration parameters, dynamically alter session settings, and interact with the host operating system's filesystem directly through SQL.

45.6.1 Inspecting and Modifying Server Configuration Parameters

PostgreSQL parameters govern connection limits, memory allocations (such as work_mem and maintenance_work_mem), and regional localization. Two primary administrative functions manage these parameters dynamically:

  1. current_setting(setting_name): Returns the current active value of a configuration parameter.
   SELECT current_setting('TimeZone');

In our demonstration environment, this query returns America/New_York.

  1. set_config(setting_name, new_value, is_local): Modifies a configuration parameter programmatically.
  • setting_name: The identifier of the parameter to update.
  • new_value: The new string value to assign.
  • is_local: A boolean flag controlling duration scope. Setting is_local = false applies the change to the entire remaining duration of the client session. Setting is_local = true restricts the change strictly to the active transaction block, automatically reverting when the transaction commits or aborts.

For example, adjusting the session time zone to Indian Standard Time (IST):

SELECT set_config('TimeZone', 'IST', false);

Similarly, administrators can adjust the session time zone to Singapore or UTC.

45.6.2 Built-in Server File Access and Directory Functions

PostgreSQL includes built-in functions under pg_catalog that allow privileged roles to inspect and read files on the database server's filesystem:

  1. pg_stat_file(filename): Returns filesystem metadata about a file on the host server. The returned record includes file size in bytes, last access timestamp (atime), last modification timestamp (mtime), status change timestamp (ctime), creation timestamp, and a boolean flag indicating whether the path represents a directory (isdir).
   SELECT pg_stat_file('/etc/aliases');
  1. pg_read_file(filename [, offset, length]): Reads text content directly from a specified file on the server filesystem.
   SELECT pg_read_file('/etc/aliases');

Expanding the returned text field displays the entire raw file contents.

  1. pg_ls_dir(dirname): Returns the list of filenames and subdirectories within a target server directory, mirroring the standard Unix ls command.
   SELECT pg_ls_dir('/tmp');

This query lists temporary files and socket descriptors created on the host machine.

Cross-Database Architectural Comparison: Configuration & Host File Operations

How server configuration and host file operations are managed across database platforms:

  • PostgreSQL: Exposes current_setting() and set_config(). Built-in file functions (pg_read_file, pg_ls_dir, pg_stat_file) allow superusers or roles granted pg_read_server_files to inspect server paths.
  • MySQL: Configuration is inspected via @@session.<name> / @@global.<name> or SHOW VARIABLES LIKE ..., and modified with SET [GLOBAL|SESSION] <name> = <val>.   • Using SQL for Complex ETL File Processing: While built-in server file functions offer quick utility for administrative inspection, dedicated scripting languages like Python or external ETL tools are far better suited for complex file parsing, transformation, and directory synchronization.
  • Misunderstanding is_local in set_config: Setting is_local = true outside an explicit transaction block (BEGIN ... COMMIT) has no persistent effect because the implicit single-statement transaction ends immediately.

45.7 Monitoring Active and Running Queries via pg_stat_activity

Think of pg_stat_activity like an air traffic control radar screen. Rather than inspecting the airport parking lot after planes have landed, the radar screen tracks every aircraft currently airborne—displaying its flight identification number (pid), the airline pilot (usename), how long it has been in the air (query_start), and whether it is cruising smoothly or stalled on the runway holding up traffic.

Monitoring real-time query execution is essential for maintaining database health, identifying long-running transactions, and resolving resource contention. The pg_stat_activity view serves as PostgreSQL's primary diagnostic tool for monitoring active client connections, server background workers, and running SQL statements. In administrative interfaces like pgAdmin, administrators can monitor these active processes through graphical dashboards.

45.7.1 Querying Active Backend Sessions in pg_stat_activity

The pg_stat_activity view contains one record per server process, detailing network connection attributes, client addresses, transaction start times, and execution states.

To view queries currently executing on the server, administrators filter out idle connections and exclude the monitoring query itself:

SELECT pid,
       age(clock_timestamp(), query_start) AS age,
       usename,
       state,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE state != 'idle'
  AND query NOT ILIKE '%pg_stat_activity%'
ORDER BY query_start DESC;

Key columns in this monitoring query include:

  • pid: The operating system process ID of the backend server process handling the client connection.
  • age: The elapsed execution duration since query processing commenced, calculated dynamically using age(clock_timestamp(), query_start).
  • usename: The database user running the statement (such as postgres or adam).
  • state: The operational status of the backend (e.g., active, idle, idle in transaction, or fastpath function call).
  • wait_event_type and wait_event: Indicates whether the backend is blocked waiting on an operating system lock, client network read, or disk I/O.
  • query: The complete SQL statement currently executing.

45.8 Terminating Running and Idle Processes

Canceling a database operation versus terminating a session is like clicking "Cancel Download" in a web browser versus yanking the computer's power cord from the electrical outlet. Clicking "Cancel" (pg_cancel_backend) halts the file transfer while preserving the network connection for subsequent requests. Yanking the cord (pg_terminate_backend) instantly severs the network socket, kills the process, and destroys any unsaved in-memory state.

When queries hang indefinitely, consume excessive CPU or memory, or lock critical business tables, database administrators must intervene to halt execution. PostgreSQL provides two distinct administrative functions to manage runaway sessions: pg_cancel_backend() and pg_terminate_backend().

45.8.1 Canceling Queries Gracefully with pg_cancel_backend

The pg_cancel_backend(pid) function cancels the SQL statement currently executing on the specified backend process while leaving the underlying client connection intact:

SELECT pg_cancel_backend(17420);

When this function executes:

  1. The PostgreSQL server process sends an interrupt signal (SIGINT) to the target backend process (pid = 17420).
  2. The target backend safely stops query execution and returns a standard error to the client: ERROR: canceling statement due to user request.
  3. The network socket and client session remain fully active, allowing the application or connection pooler to reuse the connection and submit subsequent queries.
  4. The function returns boolean true if the cancellation signal was successfully dispatched.

Because query cancellation preserves client connections, it is always the preferred first line of defense.

45.8.2 Forcibly Terminating Idle and Hanging Sessions with pg_terminate_backend

If a runaway query fails to respond to pg_cancel_backend() within a reasonable timeout, or if a connection remains stuck in idle in transaction holding table locks, administrators invoke pg_terminate_backend(pid):

SELECT pg_terminate_backend(17420);

When executed:

  1. The server issues a termination signal (SIGTERM) to the target backend process.
  2. The server forcibly severs the client TCP socket and closes the backend process entirely.
  3. Any active transaction in the terminated session is rolled back immediately, releasing all table locks and memory buffers.
  4. The client receives a disconnection error: FATAL: terminating connection due to administrator command.
  5. The function returns boolean true.

To identify idle or problematic connections that may require administrative intervention, administrators query:

SELECT pid,
       age(clock_timestamp(), state_change) AS idle_duration,
       usename,
       state,
       query
FROM pg_stat_activity
WHERE state IN ('idle', 'idle in transaction')
ORDER BY state_change ASC;

Cross-Database Architectural Comparison: Process & Query Termination

How query cancellation and session termination compare across database engines:

  • PostgreSQL: Offers pg_cancel_backend(pid) (soft SIGINT statement cancel) versus pg_terminate_backend(pid) (hard SIGTERM connection severing).
  • MySQL: Provides KILL QUERY <id>; to cancel the active SQL statement without disconnecting the user, versus KILL [CONNECTION] <id>; to terminate the connection and thread completely.
  • Snowflake: Provides SELECT SYSTEM\$CANCEL_QUERY('<query_id>'); to cancel an active query by its unique Query ID without interrupting the user's session or warehouse. To cancel all queries across a user session, administrators use ALTER USER <user> ABORT ALL QUERIES;.
  • Databricks: In Spark SQL, jobs and stages can be canceled via the Spark UI or programmatically via sc.cancelJobGroup(groupId). In Databricks SQL warehouses, active statements are halted via the REST API endpoint POST /api/2.0/sql/statements/{statement_id}/cancel.

Scope & Assumptions: Escalation Hierarchy Always adhere to the operational escalation protocol:

  1. Attempt pg_cancel_backend() first to avoid severing client application connections.
  2. If the query does not halt after a grace period (e.g., 10–30 seconds), escalate to pg_terminate_backend().
  3. NEVER execute kill -9 (SIGKILL) on a PostgreSQL backend process from the host operating system. Doing so bypasses PostgreSQL shared memory cleanup, causing the postmaster to immediately crash all backends and enter database crash recovery to protect data integrity.

Common Pitfalls:

  • Prematurely Terminating Connection Pools: Using pg_terminate_backend() on application connections managed by connection poolers (like PgBouncer) forces the pooler to drop and reconnect backend sockets, causing latency spikes for end users.
  • Ignoring Rollback Overhead: Terminating a large batch transaction that has updated millions of rows requires the backend to perform undo processing and rollback work, which may take considerable time before the locks are fully released.

Recap & Bridge: Graceful query cancellation with pg_cancel_backend protects client network sessions while freeing CPU resources; forceful termination with pg_terminate_backend should be reserved for unresponsive backends and lock-holding idle transactions. Exam note: Always remember that pg_cancel_backend cancels only the currently executing query while keeping the connection open, whereas pg_terminate_backend completely severs the client connection and terminates the backend process.

45.9 Monitoring Live and Dead Tuples for Table Health

Think of PostgreSQL's MVCC storage model like an architect's drafting bulletin board where pencil erasers are strictly forbidden. When an architect updates a room dimension, rather than erasing the existing blueprint (which would instantly blind anyone currently reading it), they pin a brand new sticky note over the old sketch and mark the previous sketch as obsolete. Over time, the bulletin board fills with discarded paper (dead tuples). The cleaning staff (VACUUM) must regularly peel away the discarded notes to free up board space for future drafts.

PostgreSQL uses Multi-Version Concurrency Control (MVCC) to deliver high concurrency and robust transaction isolation without read-write locking conflicts. Under MVCC, updating or deleting rows produces multiple versions of records called tuples. Monitoring live and dead tuples is critical for managing table bloat, maintaining query performance, and ensuring timely vacuuming.

45.9.1 Understanding Tuples, MVCC, and Row Bloat

In PostgreSQL internal architecture:

  • A physical row stored on a disk page is known as a tuple.
  • Live Tuples: Row versions that are currently active, valid, and visible to concurrent database transactions.
  • Dead Tuples: Obsolete row versions created when rows are deleted via DELETE or superseded by updated values via UPDATE.

Because writers never block readers, a SQL UPDATE statement in PostgreSQL does not modify existing data on disk in place. Instead, it inserts an entirely new tuple version into the table heap and marks the original tuple as dead by setting its transaction expiration identifier (xmax). Similarly, a DELETE statement simply stamps xmax on the target tuple without immediately reclaiming its disk space.

Dead tuples continue occupying disk pages until PostgreSQL's VACUUM process sweeps the relation, reclaiming dead tuple space and registering it in the relation's Free Space Map (FSM) so future INSERT and UPDATE statements can reuse the space.

45.9.2 Querying Live and Dead Tuples in pg_stat_user_tables

The pg_stat_user_tables system catalog view tracks access statistics, vacuum timestamps, and tuple counts for each table in the active database:

SELECT relname AS table_name,
       n_live_tup AS live_tuples,
       n_dead_tup AS dead_tuples,
       last_vacuum,
       last_autovacuum,
       last_analyze,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

Key diagnostic columns include:

  • relname: The relation name (table).
  • n_live_tup: The estimated count of live tuples currently accessible to queries.
  • n_dead_tup: The estimated count of dead tuples waiting to be purged by vacuuming.
  • last_autovacuum: The timestamp when the automatic background vacuum daemon last cleaned the table.
  • last_autoanalyze: The timestamp when the table's query planner statistics were last updated.

When n_dead_tup accumulates significantly relative to n_live_tup, the table suffers from table bloat. Sequential scans are forced to read dead tuples from disk into PostgreSQL's buffer cache (shared_buffers), degrading query performance and wasting server memory.

Worked Example: Querying Live and Dead Tuples for Table Bloat Analysis

Problem Statement: Analyze tuple health across user tables in pg_stat_user_tables, calculate the dead tuple ratio for the employees table following a batch update, and evaluate whether autovacuum thresholds are met.

Step 1: Inspect tuple distribution Query pg_stat_user_tables for the employees relation:

SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum

Results:

  • relname: employees

  • n_dead_tup: 45

Step 2: Calculate dead tuple bloat percentage Define the dead tuple bloat ratio: \[ R_{\text{dead}} = \frac{n_{\text{dead}}}{n_{\text{live}} + n_{\text{dead}}} \times 100\% \] where:

  • \(n_{\text{dead}} = 45\) is the dead tuple count,
  • \(n_{\text{live}} = 107\) is the live tuple count.

Substitute the values: \[ R_{\text{dead}} = \frac{45}{107 + 45} \times 100\% = \frac{45}{152} \times 100\% \approx 29.61\% \]

Step 3: Evaluate autovacuum trigger conditions By default, PostgreSQL triggers autovacuum when: \[ n_{\text{dead}} \ge \text{autovacuum\_vacuum\_threshold} + (\text{autovacuum\_vacuum\_scale\_factor} \times n_{\text{live}}) \] With standard settings (threshold = 50, scale factor = 0.2): \[ \text{Trigger Target} = 50 + (0.2 \times 107) = 50 + 21.4 = 71.4\text{ tuples} \] Because \(n_{\text{dead}} = 45 < 71.4\), autovacuum has not yet fired. An administrator can execute a manual VACUUM employees; to reclaim the 45 dead tuples immediately.

Sense Check: A 29.6% dead tuple ratio confirms that nearly one-third of the row space on disk holds obsolete data, demonstrating the direct need for vacuum maintenance.

Cross-Database Architectural Comparison: Concurrency Control & Row Version Cleanup

How row updates and obsolete version cleanup are handled across database architectures:

  • PostgreSQL: Stores old and new tuple versions directly inside the table heap data pages. Reclaiming dead tuple space requires background VACUUM (which marks space in the Free Space Map for reuse) or VACUUM FULL (which rewrites the physical table to return space to the OS).
  • MySQL (InnoDB): Does NOT leave dead row versions in the table heap pages! In InnoDB, updates modify the row in-place within the clustered B-tree index page and write the previous version to an Undo Log in the undo tablespace. A background Purge Thread discards undo log entries when older transactions finish. Disk bloat is addressed via OPTIMIZE TABLE.
  • Snowflake: Micro-partitions are strictly immutable. Updates write new micro-partitions and flag old ones as obsolete. Obsolete partitions are retained for Time Travel (1–90 days) and Fail-Safe (7 days), after which Snowflake's internal background service purges them automatically without manual DBA intervention.
  • Databricks (Delta Lake): Data files (Parquet) are immutable. Updates write new Parquet files and log transaction metadata in _delta_log/. Old Parquet files remain on cloud storage to support time travel until purged via VACUUM <table_name> [RETAIN <num> HOURS];.

Scope & Assumptions: Standard VACUUM vs VACUUM FULL

  1. Standard VACUUM: Cleans dead tuples and marks space reusable for future inserts in the same table, but does NOT return disk space to the host operating system (unless trailing pages at the end of the file happen to become completely empty).
  2. VACUUM FULL: Rebuilds the entire table into a new physical file on disk and returns unused space to the host OS. However, it takes an exclusive table lock (AccessExclusiveLock), blocking all concurrent reads and writes.

Common Pitfalls:

  • Disabling Autovacuum: Turning off autovacuum (autovacuum = off) causes dead tuples to accumulate unchecked, leading to massive table and index bloat that degrades disk I/O and cache efficiency.
  • Long-Running Transactions Blocking Vacuum: An uncommitted transaction in idle in transaction state holds back the transaction horizon (xmin). As a result, VACUUM cannot remove any dead tuples generated after that transaction began, causing cluster-wide bloat.

Recap & Bridge: Monitoring n_dead_tup in pg_stat_user_tables ensures database tables remain lean and query scans remain performant. Next, we delve into the physical storage layout on disk, examining how tables, pages, and tuple headers are organized in the filesystem.

Exam note: Remember that UPDATE and DELETE operations create obsolete tuple versions under MVCC, which appear as n_dead_tup in pg_stat_user_tables and require VACUUM to clean up and prevent table bloat.

45.10 Physical Storage Architecture and File Layout of PostgreSQL Tables

Think of PostgreSQL's physical storage layout like a multi-volume library encyclopedia. Rather than binding a 50,000-page manuscript into a single colossal volume that would snap the physical bookshelf (exceeding operating system file size limits), the publisher divides the work into 1 GB book volumes (.1, .2, .3). Inside each volume, every leaf is a standardized 8 KB sheet of paper. If an illustration is too large to fit onto an 8 KB sheet, the library prints a small thumbnail reference on the page and files the giant foldout in an auxiliary map cabinet (TOAST).

PostgreSQL maps logical database entities—databases, schemas, tables, and indexes—to physical files and directories on the host operating system's filesystem. Understanding this layout is essential for capacity planning, backup architecture, and low-level database performance tuning.

45.10.1 Locating the Data Directory and Physical Table Files

PostgreSQL stores all cluster data, transaction logs, and configuration files within a designated directory hierarchy:

  1. Locating the Cluster Data Directory

To find the root of the active database cluster, administrators query SHOW data_directory; in pgAdmin or the psql shell:

   SHOW data_directory;

In our demonstration environment, the cluster resides at: /Library/PostgreSQL/12/data.

Operating system permissions on this directory tree are strictly locked down. By default, only the postgres operating system user possesses read and write permissions (0700 or 0750). All other operating system accounts are denied access, preventing unauthorized file inspection.

  1. Locating Relation Files

To identify the physical file corresponding to an individual table on disk, administrators invoke pg_relation_filepath():

   SELECT pg_relation_filepath('employees');

This returns the relative path beneath the cluster's data_directory: base/16735/16826.

This path breaks down into three architectural components:

  • base: The subdirectory containing all databases stored within PostgreSQL's default tablespace (pg_default).
  • 16735: The unique Object Identifier (OID) of the database containing the relation (queryable via pg_database).
  • 16826: The physical file node number (relfilenode) assigned to the employees table (queryable via pg_class).

45.10.2 Table Segmentation and 1 GB File Chunks

Historically, various operating systems and filesystems (such as FAT32 or early Unix kernels) imposed strict 2 GB file size boundaries. To guarantee portability and avoid filesystem limits, PostgreSQL divides relation storage into fixed 1 GB physical segments:

  • The initial segment is named directly after the table's relfilenode without a file extension (e.g., 16826).
  • When a table grows beyond 1 GB, PostgreSQL allocates a second physical segment named <relfilenode>.1 (e.g., 16826.1).
  • Subsequent 1 GB segments follow sequential numeric extensions: <relfilenode>.2, <relfilenode>.3, and onward.

45.10.3 Page Layout and Mathematical Page Count Calculation

Each 1 GB physical segment is structured into fixed 8 KB (8192 bytes) disk blocks known as pages. A page is the atomic unit of I/O between disk storage and PostgreSQL's shared memory buffer pool (shared_buffers). When reading a single row, PostgreSQL loads its entire 8 KB page into memory; when writing or updating a row, the entire page is modified in RAM, marked dirty, and later flushed to disk by background checkpointer workers.

We compute the exact mathematical page count contained within a standard 1 GB file segment. One gigabyte equals 1024 megabytes, and each megabyte equals 1024 kilobytes: \[ 1\text{ GB} = 1024 \times 1024\text{ KB} = 1,048,576\text{ KB} \] where 1 GB represents the segment file size and 1,048,576 KB is its total kilobyte capacity.

Dividing total capacity by the 8 KB page size yields the page count per 1 GB segment: \[ N_{\text{pages}} = \frac{1,048,576\text{ KB}}{8\text{ KB}} = 131,072\text{ pages} \] where \(N_{\text{pages}}\) is the total page count per 1 GB segment. These pages are indexed sequentially from page 0 through page 131,071.

Worked Example: Calculating Segment Boundaries and Total Page Counts for a 1.5 GB Table

Problem Statement: Determine the physical file allocation, segment boundary offsets, and total 8 KB page count for a PostgreSQL table that has grown to exactly 1.5 GB on disk.

Step 1: Determine file segmentation Because the table size (1.5 GB) exceeds the 1 GB segment limit, PostgreSQL splits the table across two physical files on disk:

  • Segment 0 (<relfilenode>): 1.0 GB in size.
  • Segment 1 (<relfilenode>.1): 0.5 GB in size.

Step 2: Calculate pages in Segment 0 From the standard 1 GB capacity formula: \[ N_{\text{seg0}} = \frac{1,048,576\text{ KB}}{8\text{ KB}} = 131,072\text{ pages} \] Pages in Segment 0 are addressed from block number 0 to block number 131,071.

Step 3: Calculate pages in Segment 1 Convert 0.5 GB into kilobytes: \[ 0.5\text{ GB} = 512\text{ MB} = 512 \times 1024\text{ KB} = 524,288\text{ KB} \] Divide by the 8 KB block size: \[ N_{\text{seg1}} = \frac{524,288\text{ KB}}{8\text{ KB}} = 65,536\text{ pages} \] Pages in Segment 1 are addressed from block number 131,072 through block number 196,607.

Step 4: Compute total table page count Sum the page counts across both segments: \[ N_{\text{total}} = N_{\text{seg0}} + N_{\text{seg1}} = 131,072 + 65,536 = 196,608\text{ pages} \] where \(N_{\text{total}}\) is the total page count across the 1.5 GB relation.

Sense Check: Direct mathematical verification: \(1.5 \times 131,072\text{ pages/GB} = 196,608\text{ pages}\), which matches the segment summation exactly.

45.10.4 Page and Tuple Internal Format: Headers, Offsets, and TOAST

Every 8 KB page maintains an internal layout optimized for fast tuple retrieval and variable-length data handling:

  1. Page Header: Occupies exactly 24 bytes at the beginning of the page. It records vital recovery and space management metadata:
  • pd_lsn: Log Sequence Number of the last Write-Ahead Log (WAL) record affecting this page.
  • pd_checksum: Page integrity verification hash.
  • pd_lower: Byte offset pointing to the end of the line pointer array.
  • pd_upper: Byte offset pointing to the start of the unallocated free space immediately preceding the tuple data.
  • pd_special: Pointer to index-specific special space at the end of the page (in index pages).
  1. Line Pointers (Item Identifiers): An array of 4-byte pointers immediately following the page header. Each line pointer contains a byte offset pointing to the physical location of a tuple on the page.
  1. Free Space: Centered between the line pointer array and the tuple data. As new tuples arrive, line pointers grow downwards from the top, while tuple data grows upwards from the bottom, causing free space in the middle to shrink.
  1. Tuples (Rows): Stored starting from the end of the page and growing backwards towards the page header.

Each tuple contains:

  • Tuple Header: Approximately 23 bytes (standard HeapTupleHeaderData) containing MVCC metadata:
  • t_xmin: The transaction ID of the inserting transaction.
  • t_xmax: The transaction ID of the deleting or updating transaction (0 for active live rows).
  • t_cid: Command identifier within the transaction.
  • t_ctid: Physical tuple identifier ((block_number, offset)) pointing to itself or to the newer tuple version created by an update.
  • t_infomask and t_infomask2: Bitmasks recording visibility flags, attribute counts, and NULL bitmaps.
  • Field Data:
  • Fixed-width attributes: Stored inline at deterministic byte offsets.
  • Variable-width attributes: Stored inline with a length prefix.
  • TOAST (The Oversized-Attribute Storage Technique): A single PostgreSQL page cannot span multiple blocks. When a tuple's variable-width attributes cause the total row size to exceed the TOAST threshold (typically ~2 KB, or one-quarter of a page), PostgreSQL automatically compresses the attribute. If the compressed value still exceeds the threshold, PostgreSQL moves the data out-of-line into a separate, auxiliary TOAST table, storing a compact 18-byte pointer in the main row.

Cross-Database Architectural Comparison: Storage Files, Page Sizes & Out-of-Line Storage

How physical storage layout compares across relational and cloud engines:

  • PostgreSQL: 8 KB default page size, 1 GB file segmentation (base/<db_oid>/<relfilenode>, .1, .2), 24-byte page header, 23-byte tuple header, and TOAST tables for oversized attributes.
  • MySQL (InnoDB): Standard page size is 16 KB (configurable to 4 KB, 8 KB, 32 KB, or 64 KB). Tablespace files (.ibd) do not segment into 1 GB files by default, growing up to 64 TB per tablespace. Pages are grouped into extents (64 pages = 1 MB). In the modern DYNAMIC row format, oversized columns larger than half a page store a 20-byte pointer in the clustered index page, moving the overflow data out-of-line into uncompressed overflow pages.
  • Oracle Database: Standard block size is 8 KB (configurable from 2 KB to 32 KB). Manages storage in extents and segments across datafiles. Smallfile tablespaces support files up to 32 GB, while Bigfile tablespaces support single files up to 128 TB. Oversized binary and character data is managed out-of-line via LOB (Large Object) storage segments (SECUREFILE or BASICFILE).
  • Snowflake: Entirely cloud-native and columnar. Does not use fixed 8 KB or 16 KB pages. Tables are stored as immutable, columnar micro-partitions (50 MB to 500 MB uncompressed, compressed to ~16 MB). Because attributes are stored in separate columnar slices rather than row tuples, oversized attributes do not require TOAST tables.
  • Databricks (Delta Lake): Organizes data into Apache Parquet files (typically 128 MB to 1 GB) on cloud object storage (Amazon S3, ADLS, GCS). Features columnar storage with dictionary encoding, run-length encoding, and Snappy compression, tracked via the _delta_log transaction ledger.

Scope & Assumptions: TOAST Overhead and Access Patterns While TOAST transparently handles large attributes (such as JSON blobs, text documents, or images), reading a TOASTed attribute requires secondary I/O to read the out-of-line TOAST table. If queries frequently scan a table containing large TOASTed columns without needing those columns, ensure the query explicitly selects only the required fields (SELECT id, name) rather than SELECT * to avoid fetching TOAST blocks into memory.

Common Pitfalls:

  • Assuming relfilenode Never Changes: The relfilenode assigned to a table matches its initial OID upon creation, but operations like TRUNCATE, VACUUM FULL, and REINDEX allocate a brand new physical file and change the relfilenode. Always use pg_relation_filepath() to find the current physical file.
  • Neglecting TOAST Storage in Size Calculations: Querying pg_relation_size('table') reports only the main heap file size, omitting the TOAST table and indexes. To measure complete physical footprint, always use pg_total_relation_size('table').

Recap & Bridge: PostgreSQL's physical storage architecture balances operating system portability through 1 GB file segmentation with low-level page and tuple structures designed for MVCC and out-of-line TOAST management. This low-level storage model underpins the diagnostic, operational, and maintenance concepts covered across this lecture.
