# JSON with PostgreSQL

21.1 What JSON Is and Why It Matters

21.1.1 Definition and History

JSON is a light text format for storing and moving data between programs. Turning live program objects into that movable text is called serialization, and it is the core job JSON was built to serve.

What if a Python script, a web page, and a phone app could all read the same data file with no translation layer in between? That shared reading is the promise JSON makes.

An everyday picture helps. Think of a JSON document as a parcel covered in labels. Each label names one item inside the parcel, and the item sits right next to its label. Anyone who picks up the parcel can read the labels and know what is inside without asking the sender for a separate packing list. The mapping is direct: keys are the labels, values are the contents, and the parcel is the object that holds them. The picture breaks in one place: a real parcel service never checks what you packed, while a database can be told to reject text that breaks JSON rules.

JSON (how much a value stretches is not relevant here; the letters stand for JavaScript Object Notation) is text shaped by two structures. An object (a set of name and value pairs with no fixed order) holds facts such as a title and a year. An array (an ordered list of values) holds sequences such as a list of genres. A value (the data stored under one name) is one of six shapes: a string, a number, a boolean, null, an object, or an array.

JSON grew as a lighter choice next to XML. The contrast is worth seeing side by side:

Dimension XML JSON
Value wrapper Open and close tags around every value Double quotes for names and strings, bare form for numbers
Separators Tag names repeated at both ends One colon between name and value, one comma between pairs
Size Larger, because tags repeat Smaller, because marks are single characters
Reading Needs a tag-aware parser Readable in any text editor

The name linked with making JSON popular is Douglas Crockford, who used it at a company called State Software around 2001. A large web company started using JSON in web services in 2005, and another large web company offered JSON in a data web protocol in 2006. From that point use spread fast. Public APIs from the Twitter API, Yahoo, and Google all support JSON for fetching public data and building apps. In 2016 the SQL standard added JSON syntax definitions, but each database still ships its own function names, so spellings learned here for PostgreSQL will look close yet not identical in MySQL, Snowflake, or Databricks.

21.1.2 Serialization and Semi-Structured Data

Serialization (turning in-memory structures and objects into a shape that fits in a file, a memory buffer, or a network message) is the core job JSON serves. The reverse step, parsing, reads that text back into structures the program can use. The same text can rest in a file or a database column for storage, and the same text can travel across a network link for exchange between client and server.

JSON suits semi-structured data (data where each record can hold different fields, nested parts, or lists without a fixed flat table shape). A book record with a title, an author, and a list of prices is a good case. A contact with address parts and phone lists is another. One film object may carry a rating while the next film object leaves rating out, and both shapes stay valid. That flex is the point: new keys can appear on one record without rebuilding any table.

{
  "title": "The Incredibles",
  "year": 2004,
  "rating": { "MPAA": "PG" },
  "genre": ["animation", "action", "sci-fi"]
}

Here title is a string, year is a bare number, rating is a nested object, and genre is an array of strings. Each value carries its field name next to it, so the text is self-describing: a person opening the file sees what each part means with no separate schema sheet.

Picture the shape as a filing card that grows its own new lines. A classic table is a printed form with fixed boxes; every row gets the same boxes. A JSON card starts with a few lines and sprouts more lines whenever one record needs them. The takeaway in one line: tables fix the shape first, JSON lets each record shape itself.

Scope: JSON columns fit three cases well: records that need ad-hoc keys per row, related facts that would otherwise need a whole extra table, and payloads fetched from outside systems that must be studied before being split into tables. Assumption: keys stay spelled the same way and value types stay stable. When keys vanish or a number arrives as text, every query built on the old shape needs repair.

Three situations from practice show where the fit is good. A research group tagging papers lets one user add a chemical-names key and another add a food-names key on different rows. An employees table keeps name columns fixed and parks awards or metrics in one JSON column for the few staff who have them. A loader pulls a month of earthquake reports from a web API and studies the JSON first, splitting it into tables only later.

JSON is light labeled text for storing and moving records that refuse one fixed shape. Next, the exact marks that keep that text valid.

Web servers send JSON to web apps, mobile apps, and partner systems because almost every language ships a parser for it, which keeps one shared shape from the database row all the way to the screen.

21.1.3 Student Questions and Answers

Q: Is JSON only for transport, or also for storage? A: Both. The same text can sit in a file or database column for storage, and the same text can move across a network link for exchange between client and server.

21.2 JSON Syntax Rules

21.2.1 Name and Value Pairs

Every JSON fact is a name-value pair (a field name in double quotes, then a colon, then a value). Single quotes do not count for the name. The colon splits name from value.

How does a machine tell a label apart from the thing it labels? JSON answers with marks alone: quotes mean label or text, bare form means number, and the colon sits between the two jobs.

Name-value pairs with double quotes form the base of all JSON. The name always sits in double quotes. The value shape decides its own dress:

  • Text values sit in double quotes: "country": "USA".
  • Numbers sit bare with no quotes: "product_id": 101.
  • Booleans sit bare as true or false.
  • Empty sits bare as null.
{
  "first_name": "Adnan",
  "country": "USA",
  "product_id": 101
}

Here first_name and country are text values, so they sit in double quotes. product_id is a number, so it sits bare with no quotes.

Worked check with four value shapes. Read this object key by key:

{
  "title": "Sample Book",
  "price": 20.59,
  "bestseller": true,
  "discount": null
}

title shows a string, so it keeps double quotes. price shows a number with a decimal part kept exact as 20.59, so it stays bare. bestseller shows a boolean, so it stays bare as true. discount shows null, which means no value present, not zero and not an empty string. Sense-check: four pairs, three commas, every name quoted, only the string value quoted. The object is valid.

21.2.2 Commas, Objects and Arrays

A comma splits one pair from the next. Missing commas or extra trailing commas break parsing, so each split needs care. The last pair before a closing brace takes no comma.

Objects sit inside curly braces { }. An object holds zero or more pairs. One pair alone is still an object. Two pairs need one comma between them. Arrays sit inside square brackets [ ]. An array holds an ordered list of values, and those values can be objects. Braces hold named fields, while brackets hold ordered items. In short: braces build objects with named fields, and brackets build arrays with ordered items.

{
  "contacts": [
    { "first_name": "Adnan", "last_name": "Waheed" },
    { "first_name": "Adam", "last_name": "Limbered" },
    { "first_name": "Ali", "last_name": "Baba" }
  ]
}

Here contacts is the outer name. Its value is an array. Inside the array sit three objects, each with first_name and last_name, split by commas. This is the contacts array with three first-name last-name objects inside brackets: count three objects, two commas between them, and one comma-free close before the bracket shuts.

Picture braces as a labeled filing box and brackets as a numbered shelf. The box answers "what is it" by name. The shelf answers "which one" by spot. Arrays often hold objects, so the two marks work as a team: the shelf holds boxes, and each box carries its own labels.

Scope: this brace-object and bracket-array split is shared across databases. MySQL, Snowflake, Databricks, and SQLite all read the same marks. What differs is only the function names each system uses to query them, so syntax learned here transfers and only the query verbs need relearning.

21.2.3 Nesting Objects Inside Objects and Arrays

Both forms nest. An object can hold another object. An object can hold an array. An array can hold objects that themselves hold arrays. Nesting book details with a publisher object and a prices array shows the full mix:

{
  "title": "The Lord of the Rings",
  "author": "J.R.R.",
  "details": {
    "publisher": "ABC Publisher"
  },
  "prices": [
    { "type": "paperback", "price": 20.59 },
    { "type": "kindle edition", "price": 9.99 }
  ]
}

title and author are plain pairs. details is a nested object holding publisher. prices is an array holding two objects, each with type and price: paperback at 20.59 and kindle edition at 9.99. This mix mirrors real book data: fixed facts on top, grouped facts nested, repeatable price options in a list.

A common slip is to use single quotes for names or to drop the comma between pairs. Keeping double quotes for names and text values, bare form for numbers and booleans, and commas only between items, avoids most parse faults. Picture the shape as a tree: the trunk object splits into branch keys, and some branches end in leaves while others sprout whole new limbs.

Names stay quoted, numbers stay bare, braces name fields, brackets order items, and both nest freely. Next, how PostgreSQL stores these documents.

21.2.4 Student Questions and Answers

Q: Do numbers need quotes like text does? A: No. Numbers stay written bare while field names and text values use double quotes. "price": 20.59 is right. "price": "20.59" would turn it into text.

Student confusion here is natural because names always wear quotes. The rule to carry forward: quotes mark names and text, bare form marks numbers, booleans, and null.

Q: What is the difference between braces and brackets? A: Braces build named objects while brackets build ordered arrays holding objects. Use braces for fields with names and brackets for lists with order.

21.3 JSON and JSONB Storage in PostgreSQL

21.3.1 Native Support Since Version 9.2

PostgreSQL 9.2 ships native JSON types, with many functions and operators for working with stored documents. Application code sends a JSON string to the database marked as a JSON type, and reads it back in JSON form. That path lets web code in Python, PHP, React, or Angular keep one shared shape from table to API.

Why keep flexible JSON inside a strict table at all? Because it gives both strengths at once: the table brings keys, joins, and transactions, while the JSON column brings per-row freedom for traits that do not fit every row.

Client-server apps keep rows in tables for safe storage, then expose chosen rows as JSON for APIs and front ends. Picture a warehouse with fixed shelves and one open corkboard: the shelves hold boxes every item needs, while the corkboard pins extra notes that only some items carry.

Other systems solve the same need with their own storage shape. MySQL offers a single JSON type with path functions such as JSON_EXTRACT instead of arrows. Snowflake stores semi-structured payloads in a VARIANT column read with dot-and-colon paths and flattened with FLATTEN. Databricks SQL parses JSON strings with from_json and builds them with to_json. The idea transfers across all four; only the spelling of the read changes.

21.3.2 Text Storage Against Binary Storage

Two types store JSON: json and jsonb. The trailing b stands for binary.

The json type keeps the document much as typed, as text, as long as it is valid JSON. White space stays. Key order stays. Repeated keys stay close to input. The jsonb type parses the document and stores a binary form tuned for search. White space is dropped. The shape is packed for fast field lookup and index use. So white space is kept in json text against trimmed packed binary in jsonb.

That split drives four practical gaps:

Dimension json jsonb
Storage form Text, close to typed input Parsed binary, packed for search
White space Kept, layout preserved Trimmed, gaps removed
Function range Smaller set of JSON functions and operators Full set of JSON functions and operators
Index support No GIN or full-text index path Full-text search indexing and GIN indexing

Search speed follows from the same split. jsonb parses once at write time, so later field reads and index builds run fast. json keeps input as is, which makes raw writes light but later field work slower because each read must parse again. For most app work with search, filters, and indexes, jsonb is the favored pick. The demo set in this lecture uses jsonb for that reason: speed of field operators, broad function support, and index options. One trade to note: when two copies of one key sit in a single object, json preserves each repeated pair while jsonb keeps only the last, so exact-duplicate input is the rare case for json.

Scope: jsonb fits reads, filters, and indexed search. json fits the narrow case where exact input text, key order, or duplicate keys must be preserved. Assumption: documents are valid JSON on write; invalid text is rejected by both types instead of being stored.

Exam note: Compare json against jsonb on storage form, white space, function range, and index support: text storage with kept white space and a small function set against binary storage with trimmed packed form, the full set, and GIN support.

21.3.3 Student Questions and Answers

Q: Which type should I pick for a new table, json or jsonb? A: Pick jsonb for filtering, search, and indexing. Pick json only to keep exact input text with white space when you need little field search.

21.4 Representing JSON Objects and Casting Text

21.4.1 Single Quotes Outside, Double Quotes Inside

In PostgreSQL every JSON literal starts life as text. The outer wrapper uses single quotes to mark text. The inner JSON names and text values use double quotes per JSON rules.

SELECT '{"title": "The Lord of the Rings"}';

This runs, but the result column types as text. The braces match JSON shape, yet the database still treats the value as plain text with no JSON behavior. Brace text is treated as plain text until marked with a json or jsonb cast, so no field operator will accept it yet.

Picture two envelopes. The outer SQL envelope is sealed with single quotes. The inner JSON letter is written with double quotes. The database reads the envelope first, so the letter inside cannot act like JSON until the envelope is re-marked with a cast.

21.4.2 Cast to JSON or JSONB

Casting (telling the database to treat a value as a new type) turns that text into a JSON value. Two casts matter here: ::json and ::jsonb.

Worked cast demo. Run the text form first, then both casts:

SELECT '{"title": "The Lord of the Rings"}';
SELECT '{"title": "The Lord of the Rings"}'::json;
SELECT '{"title": "The Lord of the Rings"}'::jsonb;

The first returns plain text with no JSON behavior. The second casts brace title text to json, keeping white space. Adding extra spaces and line breaks keeps them in the stored form, which helps when exact input layout must stay. The third casts the same text to jsonb, trimming gaps and packing the form for fast work. Both casts turn text into JSON; only the storage differs.

A follow-on test adds a second pair on a new line:

SELECT '{"title": "The Lord of the Rings", "author": "J.R.R."}'::jsonb;

Even with the pair split across lines in the typed text, the jsonb result returns packed without the extra gaps. That packing is part of why later field reads and index builds run faster. Cast brace title text to json keeping white space and to jsonb trimming gaps: same keys and values, different stored shape.

Other systems mark text as JSON their own way. Snowflake parses strings with PARSE_JSON (or the forgiving TRY_PARSE_JSON, which returns null on bad input instead of failing), MySQL validates with CAST(... AS JSON), and Databricks SQL parses with from_json plus a schema. The shared lesson holds everywhere: brace text is plain text until some explicit mark promotes it to JSON.

Exam note: Mark brace text ::json or ::jsonb before field reads work. Without the cast the value stays text; with it, field operators accept it.

21.4.3 Student Questions and Answers

Q: Why does my brace text behave like plain text? A: Without a cast, brace text is plain text. Add a json or jsonb cast for field operators, keeping white space with json and packing with jsonb.

21.5 Creating Tables with JSONB and Inserting Records

21.5.1 Table Definition

A table can mix plain columns with a JSONB column. A common shape uses a serial key plus one JSONB body:

CREATE TABLE books (
  book_id SERIAL PRIMARY KEY,
  book_info JSONB
);

book_id is a serial primary key that numbers each row. book_info holds the full JSON document per row, so each book can carry title, author, and later extra keys without altering the table shape. The key stays rigid for joins and ordering while the body stays free for traits that vary per row.

Why not split title and author into plain columns? For two fixed fields that would work well. The JSONB body pays off once traits vary: one book gains a pages count, another gains a category, and the table never needs rebuilding.

21.5.2 Single Row Insert

JSON in an INSERT is still written as text inside single quotes, with inner double quotes for JSON names and text values:

Worked single-row insert. Write one JSON object per new row:

INSERT INTO books (book_info)
VALUES ('{"title": "book title one", "author": "author one"}');

Both pairs sit in one object, split by a comma. Indent style does not change meaning; it only helps reading while building multi-row scripts. Check content with:

SELECT * FROM books;

The first row returns book_id plus a book_info document holding title and author. One object in, one row stored.

21.5.3 Multi Row Insert

The same shape repeats for more rows, one JSON object per row:

INSERT INTO books (book_info)
VALUES
  ('{"title": "title two", "author": "author two"}'),
  ('{"title": "title three", "author": "author three"}'),
  ('{"title": "title four", "author": "author four"}');

Each parenthesized item maps to one new row. After this batch the table holds four rows: the single-row insert plus these three. A follow-on SELECT * FROM books; lists all four documents. The books table with its serial key and JSONB body plus single and multi-row inserts is now loaded and ready for field reads.

Product catalogs, book stores, and contact stores use one JSONB column for flexible traits while keeping a plain key for joins and ordering. That hybrid is the standard industry shape: rigid keys outside, free-form facts inside.

A serial key numbers each row while the JSONB body carries per-item facts, loaded one object per row. Next, reading fields back out with arrows.

21.6 Selecting Fields with Arrow Operators and Filtering

21.6.1 The Two Arrow Forms

Two operators read fields from a JSONB column. The single arrow -> returns a JSON object field with its JSON quoting kept. The double arrow ->> returns the same field as plain text with quotes stripped. The single arrow keeps JSON quoting while the double arrow strips quotes to plain text.

Which arrow hands you something you can print, and which hands you something you can keep querying as JSON? That single question decides every arrow choice in this lecture.

Worked arrow reads on the books table. Run all three and compare the title column:

SELECT book_info FROM books;
SELECT book_info -> 'title' FROM books;
SELECT book_info ->> 'title' FROM books;

The first lists whole documents. The second lists titles still wrapped in double quotes because the result stays JSON. The third lists titles as bare text because the double arrow unwraps to text. So the single-arrow title read keeps quotes against the double-arrow bare text read. Same key, two result types.

Key names in these reads use single quotes: -> 'title', ->> 'author'. Forgetting those quotes triggers a fault, since the database then looks for a column named title instead of a JSON key.

Aliased reads keep output neat:

SELECT
  book_info ->> 'title' AS title,
  book_info ->> 'author' AS author
FROM books;

Both columns now return as text without JSON quotes, ready for display or export. Other systems spell the same read differently: MySQL uses JSON_EXTRACT plus JSON_UNQUOTE for the text form, Snowflake uses a colon path with dot notation, and Databricks SQL uses get_json_object with a dollar path. The two-result idea is shared; only the marks change.

21.6.2 Filtering on JSON Keys

A WHERE clause must point inside the JSON column, not at a bare key name. This fails because no plain column named author exists:

SELECT book_info ->> 'title' AS title,
       book_info ->> 'author' AS author
FROM books
WHERE author = 'author one';

The fix names the JSON path:

SELECT book_info ->> 'title' AS title,
       book_info ->> 'author' AS author
FROM books
WHERE book_info ->> 'author' = 'author one';

Here book_info ->> 'author' pulls text from inside each document, then compares that text to 'author one'. The double arrow matters: text-to-text comparison works as typed. Using the single arrow here would compare JSON-quoted text against bare text and miss or fault, a theme that returns in the update demo.

Scope: filters, LIKE, casts, and text compare need the ->> text form. Keep the -> JSON form only when the result feeds further JSON work such as chaining another operator or indexing into an array.

Exam note: Arrow drill — the single arrow keeps JSON quotes, the double arrow gives text for filters and LIKE. When a filter faults or misses, check the arrow first.

21.6.3 Student Questions and Answers

Q: Why did my filter say column author does not exist? A: The key lives inside book_info, not as its own column, so point at the path with the double arrow in the WHERE clause: book_info ->> 'author' = 'author one'.

The confusion is natural because the alias author looks like a column. But aliases cannot be reused in the same WHERE clause, so the full JSON path must be repeated there.

Q: When do I use the single arrow read and when the double arrow read? A: The single arrow keeps JSON form with quotes for further JSON work. The double arrow gives plain text for display, LIKE, casts, or text comparison.

21.7 Updating and Deleting Keys, Fields and Array Elements

21.7.1 Inserting a Work Row

A fresh row sets up the update drills:

INSERT INTO books (book_info)
VALUES ('{"title": "book title ten", "author": "author ten"}');
SELECT * FROM books;

The new row pairs title ten with author ten. Every drill below scopes to this row with a WHERE filter, then proves the change with a read.

21.7.2 Replacing a Value with the Concatenation Operator

The || concatenation operator (a mark that merges two JSONB values into one) merges JSONB values. When the added object holds a key that already exists, the new value replaces the old one. When the key is new, the pair is added. That one mark serves both edit and extend jobs.

Worked value replacement. Change author ten to a new name while touching only that row:

UPDATE books
SET book_info = book_info || '{"author": "Adnan"}'
WHERE book_info ->> 'author' = 'author ten';

The WHERE form uses ->> so both sides are text. An early try with -> fails with an invalid input syntax fault for type json, because the left side still carries JSON double quotes while the right side is bare text. So the single-arrow filter faults on quoted JSON and the fix switches to double-arrow text. After the run, a SELECT shows the same row now holding author Adnan. One merge, one value replaced, other keys untouched.

That quote mismatch is a prime learning point: single arrow keeps JSON quoting, double arrow gives text. Filters that compare to typed text almost always need the double arrow.

21.7.3 Returning Affected Rows and Editing Titles

RETURNING * lists only rows touched by the write, which beats re-reading the whole table:

UPDATE books
SET book_info = book_info || '{"title": "future 1.0"}'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

Only the Adnan row returns, now with the new title. The concatenation replaces author ten with the new name and edits the title with returning rows, all in one scoped pass.

21.7.4 Adding New Keys and Multiple Pairs

The same || mark adds fresh keys. Adding a boolean flag:

UPDATE books
SET book_info = book_info || '{"bestseller": true}'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

The row now holds title, author, and "bestseller": true. The boolean stays bare, with no quotes, per JSON rules.

Adding two pairs at once follows the same comma rule as plain JSON:

UPDATE books
SET book_info = book_info || '{"category": "signs", "pages": 320}'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

Title, author, category, pages, and bestseller now sit in one document. Any set of pairs inside one pair of braces merges in one pass. MySQL reaches the same result with JSON_SET or JSON_INSERT, and Snowflake rewrites with OBJECT_INSERT, but the merge-or-add idea is the same everywhere.

21.7.5 Deleting a Top Level Key with Minus

The - operator drops a top level key by name:

UPDATE books
SET book_info = book_info - 'bestseller'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

The key name sits in single quotes after -. After the run, pages, title, author, and category stay, while bestseller is gone. So minus drops the bestseller key while the rest of the document survives intact.

21.7.6 Adding and Pruning Nested Arrays by Path

Arrays nest inside documents with brackets. Adding a location list:

UPDATE books
SET book_info = book_info || '{"availability_locations": ["New York", "New Jersey"]}'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

availability_locations is the key. Its value is an array of two text items split by a comma.

Array spots count from zero: first item is spot 0, second is spot 1. To drop one array item by path, use #- with a path array holding the key plus the spot number:

UPDATE books
SET book_info = book_info #- '{availability_locations,1}'
WHERE book_info ->> 'author' = 'Adnan'
RETURNING *;

Spot 1, New Jersey, leaves the document, while New York stays. The same - form from the prior section would drop a whole top key such as pages, while #- reaches inside a nested path to drop one array slot. So minus drops the bestseller key while the path operator drops the New Jersey array slot: whole-key delete against surgical slot delete.

Exam note: Write drill with concatenation, minus key drop, and path drop operators. Practice the four marks as a set: -> keeps JSON quotes, ->> gives text, || adds or replaces, - drops a key, #- drops by path.

21.7.7 Student Questions and Answers

Q: Why did my update filter fault on author ten? A: The filter used the single arrow with JSON quotes against bare text. Switch to the double arrow text match, book_info ->> 'author' = 'author ten', then the || merge applies.

Q: How do I choose between minus and path deletes? A: Minus drops a whole top key while the path operator drops one array slot by spot. Use - 'pages' for the key and #- '{availability_locations,1}' for the slot.

21.8 Creating JSON from Tables with row_to_json

21.8.1 Whole Rows to JSON

The row_to_json function turns a row into a key-value JSON object, which helps when table data must move to an API or app that speaks JSON.

Tables store well but clients speak JSON, so who does the translation? This function does: one call turns each stored row into a ready-to-ship object.

Worked whole-row conversion. Compare table form against JSON form:

SELECT * FROM directors;
SELECT row_to_json(directors) FROM directors;

The first lists 38 rows in table form. The second lists the same rows as JSON objects with keys such as director_id, first_name, last_name, date_of_birth, nationality, and date fields. That JSON list can feed an API, an export file, or a client app without hand mapping each column. Same 38 rows, two shapes.

Service back ends pull rows from PostgreSQL, turn them with row_to_json, and serve them to web and mobile clients over HTTP. Snowflake builds the same payload with OBJECT_CONSTRUCT, and Databricks SQL with to_json on a struct, but the bridge job is identical.

21.8.2 Chosen Columns Through a Subquery

To ship only some columns, shape them first in a subquery, alias it, then wrap with row_to_json:

SELECT row_to_json(t)
FROM (
  SELECT director_id, first_name, last_name, nationality
  FROM directors
) AS t;

The inner query picks four columns. The outer call turns each shaped row into JSON holding only those four keys. The alias t names the shaped row source that feeds the function. Whole directors rows go to JSON and chosen columns pass through the aliased subquery, so wide storage stays while narrow views ship.

This pattern scales to real service work: keep table storage wide, but expose a narrow JSON view with only the fields each client needs. Fewer keys per payload means smaller responses and less accidental data exposure.

row_to_json bridges stored rows and JSON-speaking clients, whole or narrowed. Next, building JSON values from scratch with constructor functions.

21.8.3 Student Questions and Answers

Q: Why turn table rows into JSON at all? A: Tables store well, but web clients and APIs trade in JSON. row_to_json bridges the two without rewriting field names by hand.

21.9 Building Arrays and Objects with JSON Functions

21.9.1 json_build_array for Mixed Lists

json_build_array takes values split by commas and returns a JSON array:

Worked array builds. Run both and compare the element types:

SELECT json_build_array(1, 2, 3, 4, 5);
SELECT json_build_array(1, 2, 3, 4, 5, 6, 'hi');

The first returns [1,2,3,4,5]. The second mixes numbers with the text 'hi', showing that one array can hold more than one type. Build the array with mixed numbers and text: one call, one ordered list.

21.9.2 json_build_object for Alternating Keys and Values

json_build_object takes alternating keys and values, so the argument count must be even. Inputs read as alternating key and value, so an odd count leaves one key unmatched.

SELECT json_build_object(1, 2, 3, 4, 5, 6, 7);

Seven inputs fault because the list must pair each key with a value. Adding one more value fixes the shape:

SELECT json_build_object(1, 2, 3, 4, 5, 6, 7, 8);

Now 1 maps to 2, 3 maps to 4, and so on through alternating pairs.

With text keys the same rule holds:

SELECT json_build_object('name', 'Adnan', 'email', 'abc@abc.com');

name maps to Adnan and email maps to the address. Each item sits in single quotes at the SQL level, with text values following JSON text shape inside. Build the object with alternating keys and values: even count in, paired object out.

21.9.3 json_object for Split Key and Value Lists

json_object takes keys as one group and values as a second group, each wrapped in braces:

SELECT json_object('{name,email}', '{Adnan,abc@abc.com}');

The first brace group lists keys. The second lists matching values in the same order. The result pairs name with Adnan and email with the address, the same mapping as the prior call but built from two parallel lists. Pick json_build_object when keys and values arrive interleaved, and json_object when they arrive as two ready-made lists.

MySQL users meet the same pair under the names JSON_ARRAY and JSON_OBJECT, while Snowflake spells them ARRAY_CONSTRUCT and OBJECT_CONSTRUCT. Same alternating-or-parallel choice, different labels.

Exam note: json_build_object needs an even argument count of alternating keys and values; an odd count faults until the missing pair value is added. json_object takes a key group plus a value group instead.

21.9.4 Student Questions and Answers

Q: Why does json_build_object complain about an even number of elements? A: Inputs read as alternating key and value, so an odd count leaves one key unmatched. Add the missing value to close the last pair.

21.10 Building Documents with Aggregates and Handling Nulls

21.10.1 Document Table and Director Plus Movie Shape

A document table holds one JSON body per item:

CREATE TABLE directors_docs (
  id SERIAL PRIMARY KEY,
  body JSON
);

id numbers each document. body holds the whole JSON paper for one director, including nested movie lists.

How do many movie rows become one nested list inside one director paper? A correlated subquery gathers each director's own movies, and an aggregate packs them into a single array.

The build starts from plain columns:

SELECT director_id, first_name, last_name, date_of_birth, nationality
FROM directors;

A correlated subquery then gathers each director's movies as a JSON array with json_agg:

Worked document build. Pack each director plus their movies into one array:

SELECT
  director_id, first_name, last_name, date_of_birth, nationality,
  (SELECT json_agg(x)
   FROM (SELECT movie_name FROM movies WHERE movies.director_id = directors.director_id) AS x
  ) AS all_movies
FROM directors;

The inner query finds movies whose director_id matches the outer director row. json_agg packs those movie names into one JSON array aliased all_movies. A director with three movies shows three packed items. Director plus movie documents packed with the json_agg correlated subquery: one row per director, one array per row.

Wrapping the shaped row with row_to_json, casting toward jsonb for packed handling, and inserting into directors_docs(body) stores each director paper as one body value:

INSERT INTO directors_docs (body)
SELECT row_to_json(a)::jsonb
FROM (
  SELECT
    director_id, first_name, last_name, date_of_birth, nationality,
    (SELECT json_agg(x)
     FROM (SELECT movie_name FROM movies WHERE movies.director_id = directors.director_id) AS x
    ) AS all_movies
  FROM directors
) AS a;
SELECT * FROM directors_docs;

Each body now holds director facts plus an all_movies array in key-value form. Snowflake packs the same nested list with ARRAY_AGG inside OBJECT_CONSTRUCT, and Databricks SQL with collect_list inside a struct, but the correlate-then-pack flow is the same.

21.10.2 Null Arrays and the Empty Array Fix

One director, id 38, has no movies, so the aggregate yields null for all_movies. That lone null later breaks set-returning array reads such as jsonb_array_elements, which cannot pull elements from a scalar null and faults with cannot extract elements from a scalar. A plain IS NOT NULL filter on the shaped column still leaves the fault in place when other rows carry scalar shapes, so the lasting fix writes an empty array [] at build time.

Count array items per director, then branch with CASE:

DELETE FROM directors_docs;

clears the table for a clean rebuild. Then the movie subquery is paired with a count, and zero counts map to an empty array while other counts keep the packed array. In sketch form:

CASE WHEN COUNT(x) = 0 THEN '[]' ELSE json_agg(x) END AS all_movies

After re-insert and re-check, the last row shows [] in place of null. The follow-on read now works:

SELECT jsonb_array_elements(body -> 'all_movies')
FROM directors_docs;

With no null arrays left, each array unpacks to its member elements without the scalar fault. Cannot extract elements from scalar null is fixed by the empty-array CASE rebuild: stored null is scalar, so rebuild the row with an empty array using CASE on the count.

Exam note: Null arrays break unpacking. Rebuild empty sets as an empty array with CASE on the count before calling array element functions.

21.10.3 Student Questions and Answers

Q: Why does array unpacking fault even after I filter nulls? A: The stored null is scalar, so rebuild the row with an empty array using CASE on the count. The stored all_movies for the empty director is still a scalar null, and element unpacking cannot read a scalar.

Filtering at read time cannot help because the stored value itself is the wrong shape. The repair belongs at build time, where the empty set becomes [].

Q: Where does all_movies come from? A: A correlated subquery matches movies.director_id to the outer directors.director_id, packs names with json_agg, and labels the packed list all_movies.

21.11 Reading Documents: Length, Keys, Each and To Record

21.11.1 Counting Array Members with jsonb_array_length

jsonb_array_length counts items in a named array node inside a JSONB body:

Worked count and rank. Count array members with array length and rank directors descending:

SELECT *, jsonb_array_length(body, 'all_movies') AS total_movies
FROM directors_docs;

body names the JSONB field. 'all_movies' names the array node inside it. The alias total_movies holds the count per director, such as three for a director with three films. Sorting by that count ranks output:

SELECT *, jsonb_array_length(body, 'all_movies') AS total_movies
FROM directors_docs
ORDER BY total_movies DESC;

Rows now run from most movies to fewest, a handy top-director list built straight from stored documents. Count first, sort second, leaders on top.

21.11.2 Listing Keys with jsonb_object_keys

jsonb_object_keys lists key names per row. Note the json form faults on this jsonb body, so the jsonb form is the one to call:

SELECT jsonb_object_keys(body) FROM directors_docs;

Adding plain columns shows which row each key set belongs to:

SELECT *, jsonb_object_keys(body) FROM directors_docs;

Each document row fans out to its keys: director_id, first_name, last_name, all_movies, nationality, and sibling fields. This quick key list helps when documents vary and the reader must confirm which keys each paper holds. Body is jsonb, so call jsonb_object_keys matching the stored type family: match the function family to the stored type.

21.11.3 Key-Value Rows with jsonb_each

jsonb_each turns one document into key-value rows. It needs the table plus field, aliased for column reads:

SELECT j.key, j.value
FROM directors_docs, jsonb_each(directors_docs.body) AS j;

jsonb_each(directors_docs.body) splits the body. The alias j exposes key and value columns. Output lists facts such as director id values, first names, last names, and movie arrays, one pair per line across all papers. Picture unstacking a filing card into a pile of single-line slips: each slip carries one key and one value.

21.11.4 Back to Tables with jsonb_to_record

jsonb_to_record turns documents back into table rows, but it needs a column list because a record return must declare types:

SELECT j.*
FROM directors_docs, jsonb_to_record(directors_docs.body)
  AS j(director_id INT, first_name VARCHAR(255), nationality VARCHAR(100));

Without that list the call faults with column definition list required for function returning record. With the list, output returns in normal table shape with typed columns for id, first name, and nationality. More columns join the list the same way when wider table output is needed. The record return needs named columns with types before the document maps into the table, since a record has no fixed shape until columns and types are named.

Exam note: Pair each reader with its need: jsonb_array_length for counts, jsonb_object_keys for key names, jsonb_each for key-value rows, jsonb_to_record plus a typed column list for table output.

21.11.5 Student Questions and Answers

Q: Why does my object-keys call fault on a body column? A: Body is jsonb, so call jsonb_object_keys matching the stored type family. The json form faults on a jsonb body, so match the function family to the stored type.

Q: Why does jsonb_to_record ask for a column list? A: The record return needs named columns with types before the document maps into the table. List each wanted column with its type in the alias, then the document maps into that table shape.

21.12 Existence and Containment Search Operators

21.12.1 Existence Operator Question Mark

The ? existence operator (a mark that tests whether text is present at a named node) tests whether a text key or value is present at a named node. To find first name John in the papers table:

SELECT * FROM directors_docs WHERE body -> 'first_name' ? 'John';

body -> 'first_name' points at the node. ? 'John' tests for that value. Matching rows return with John in first name.

Dropping the node fails:

SELECT * FROM directors_docs WHERE body ? 'John';

The whole body holds many keys, so a bare test finds no direct hit and returns no rows. The node path matters: point at the exact field that holds the wanted value.

Why point at a node instead of searching the whole paper? Because ? checks one level only: a key at the top level, or a value inside the named array. The whole body is many levels at once, so a bare test finds no direct hit.

The same operator expects text on both sides. Searching a numeric node as text misses:

SELECT * FROM directors_docs WHERE body -> 'director_id' ? '1';

Even with a director id 1 present, no rows return because director_id stores a number while ? compares as text. Existence compares as text while the stored id is a number, so numeric search needs the containment path in the next section.

21.12.2 Containment Operator At Sign with Greater Sign

The @> containment operator (a mark that tests whether the left document holds the right key-value shape) tests whether the left document holds the right key-value shape. For text it looks like this:

SELECT * FROM directors_docs WHERE body @> '{"first_name": "John"}';

The right side sits in single quotes as text, with inner braces marking an object and double quotes marking JSON names and text values. Matching rows return. Quoted text id matches the stored bare number only when shapes line up, so containment mirrors the exact stored shape.

Numeric search drops the inner double quotes around the number to mirror stored shape:

SELECT * FROM directors_docs WHERE body @> '{"director_id": 1}';

With 1 bare, the row for director id 1 returns. Wrapping it as "1" would miss, because quoted "1" is text while stored 1 is a number. Use containment with a bare number such as '{"director_id": 1}' so shapes line up. Mirroring exact stored shape, quotes for text and bare for numbers, is the rule. MySQL answers the same need with JSON_CONTAINS or MEMBER OF, but the mirror-the-shape rule is identical.

21.12.3 Containment Inside Arrays

all_movies is an array of objects, so array search starts with brackets then braces. To find the film Toy Story:

Worked array containment. Mirror the stored array-of-objects nesting exactly:

SELECT * FROM directors_docs
WHERE body -> 'all_movies' @> '[{"movie_name": "Toy Story"}]';

body -> 'all_movies' points at the array node. The right side opens with [ for the array, then { for the object holding movie_name. An early try without the inner braces faults; a try with braces outside brackets also faults. Brackets outside plus braces inside mirror that nesting, and then the match returns. Containment search for Toy Story inside the all_movies array of objects succeeds.

Exam note: ? needs a node path and text-to-text shape; @> must mirror stored shape, with bare numbers for numeric fields and '[{"movie_name": "Toy Story"}]' for arrays of objects.

21.12.4 Student Questions and Answers

Q: Why does existence search miss a numeric id I can see in the table? A: Existence compares as text while the stored id is a number. Use containment with a bare number such as '{"director_id": 1}' so shapes line up.

Q: Why does my movie search fault before it even filters? A: Stored movies are an array of objects, so the search shape needs brackets outside and braces inside: '[{"movie_name": "Toy Story"}]'. That mirror of the nesting stops the fault.

21.13 Combined SQL Search and JSONB Indexing with GIN

21.13.1 Text Search with LIKE Needs Text Output

SQL verbs such as LIKE work on text, so the JSON read must use the double arrow that strips JSON quotes. To find first names starting with capital J:

SELECT * FROM directors_docs WHERE body -> 'first_name' LIKE 'J%';

This faults with operator does not exist for jsonb against unknown, because the left side is still JSON with quotes. LIKE needs text, but the single arrow hands JSON with quotes. Switching to text output fixes it:

SELECT * FROM directors_docs WHERE body ->> 'first_name' LIKE 'J%';

->> hands plain text to LIKE, and 'J%' matches every name opening with capital J. Use the double arrow text form body ->> 'first_name' LIKE 'J%' so the left side is plain text.

21.13.2 Numeric Compare Needs a Cast, IN Lists Follow

Pulling a numeric id as text then comparing to a number faults for type mismatch. Parenthesize the text read and cast to integer:

SELECT * FROM directors_docs WHERE (body ->> 'director_id')::INT > 2;

Both sides are now numbers, and rows with id above 2 return. The double arrow hands text, so wrap and cast to integer before compare or IN.

The same cast shape feeds an IN list:

SELECT * FROM directors_docs WHERE (body ->> 'director_id')::INT IN (1, 2, 3, 4, 5, 10);

Rows whose cast id sits in that list return. EXPLAIN on these reads shows a sequential scan across stored papers, which reads every row and slows as data grows. Why does numeric compare fault on the id when the id looks like a number? Because ->> hands text while the literal is an integer, and text against integer mismatches until the cast aligns both sides.

21.13.3 GIN Index on a Large Contacts Sample

GIN (how an index stores keys is its design: Generalized Inverted Index) speeds full-text and key-element search by storing each key once plus the row spots where it occurs. One key in many papers still sits once in the index with its spot list, which keeps the index packed and lookups fast. This index path arrived in PostgreSQL 9.4.

Worked index timing on 20,000 papers. A drill sample uses a file named contacts_docs.sql from a zipped sample-data pack, built with fake rows from a tool named Faker.js. The loader drops and remakes a table shaped like this:

DROP TABLE IF EXISTS contacts_docs;
CREATE TABLE contacts_docs (
  contact_id SERIAL PRIMARY KEY,
  body JSONB NOT NULL
);

Loading that file stores about 20,000 contact papers, each with first name, last name, contact facts, and an address array holding city and street. Search for first name John with containment:

SELECT * FROM contacts_docs WHERE body @> '{"first_name": "John"}';

Nine rows return. Time the read with planner tools for the baseline:

EXPLAIN SELECT * FROM contacts_docs WHERE body @> '{"first_name": "John"}';
EXPLAIN ANALYZE SELECT * FROM contacts_docs WHERE body @> '{"first_name": "John"}';

EXPLAIN shows the plan with a sequential scan and filter. EXPLAIN ANALYZE runs the plan and reports time, about 10.10 milliseconds on the demo box, with small shifts between runs. The scan touches all 20,000 papers with no index in play. Add a plain GIN index on the whole body:

CREATE INDEX id_gin ON contacts_docs USING GIN (body);

Build time runs near one second plus a few milliseconds. Re-running the timed search drops to about 0.276 milliseconds, a sharp gain against the 10 millisecond baseline. Check size with:

SELECT pg_relation_size('id_gin') AS index_size;

It reports about 3664 KB, near three megabytes for 20,000 papers. GIN index on 20,000 contacts papers with timing and size ladder: 10 milliseconds down to 0.276 milliseconds at 3664 KB.

21.13.4 Costs, jsonb_path_ops and Key Indexes

GIN builds can cost time and space on complex papers because the build must walk each document for keys and row spots. Bloated GIN forms cost more still, and size tracks data size and shape.

A leaner GIN form adds jsonb_path_ops, tuned for path containment search:

CREATE INDEX id_gin_path ON contacts_docs USING GIN (body jsonb_path_ops);

Size falls to about 2512 KB, near two megabytes, below the plain GIN size for the same body column.

Narrowing further to one key cuts size hard. An index on first name alone:

CREATE INDEX id_gin_firstname ON contacts_docs USING GIN ((body -> 'first_name') jsonb_path_ops);

reports about 288 KB, well under one megabyte. Search scoped to that key then runs against a far smaller index. The lesson scales: index the whole body when search spans many keys, add jsonb_path_ops for leaner containment, and index hot keys alone when one field draws most reads. Worth it for repeated key search over large sets, trading build size for reads: build time and index size buy much faster repeated lookups, and path ops plus key-scoped forms trim that size cost.

Exam note: GIN timing story — near 10 milliseconds sequential versus near 0.276 milliseconds indexed on 20,000 rows — plus the size ladder near 3664 KB plain, near 2512 KB with path ops, and near 288 KB for one key.

21.13.5 Student Questions and Answers

Q: Why does LIKE fault on a JSONB field? A: LIKE needs text, but the single arrow hands JSON. Use the double arrow text form body ->> 'first_name' LIKE 'J%' so the left side is plain text.

Q: Why does numeric compare fault when the id looks like a number? A: The double arrow hands text, so wrap and cast to integer before compare or IN: (body ->> 'director_id')::INT aligns both sides as numbers.

Q: When is GIN worth the cost? A: Worth it for repeated key search over large sets, trading build size for reads. It trades build time and index size for much faster reads, and path ops plus key-scoped forms trim that size cost.

Exam Guidance Summary

  • Compare json against jsonb: storage as text against binary, white space kept against trimmed, small function set against full set, no full-text index path against GIN and full-text support.
  • Cast drill: mark brace text ::json or ::jsonb before field reads work, since brace text treated as plain text until marked with a json or jsonb cast.
  • Arrow drill: single arrow keeps JSON quotes, double arrow gives text for filters and LIKE. Filters, LIKE, and text compare need ->>.
  • Write drill: || adds or replaces, - 'key' drops a top key, #- '{key,spot}' drops an array slot by zero-based spot, with concatenation, minus key drop, and path drop operators as one set.
  • Build drill: json_build_object needs an even argument count of alternating keys and values, since inputs read as alternating key and value. json_object takes a key group plus a value group.
  • Null drill: null arrays break unpacking, since stored null is scalar, so rebuild empty sets as an empty array with CASE on the count, or jsonb_array_elements faults on scalar null with cannot extract elements from a scalar.
  • Reader drill: jsonb_array_length for counts, jsonb_object_keys for key names matching the stored type family, jsonb_each for key-value rows, jsonb_to_record with a typed column list for table output, since the record return needs named columns with types.
  • Search drill: ? needs a node path and text-to-text shape, since existence compares as text. @> must mirror stored shape, with bare numbers for numeric fields, such as '{"director_id": 1}', and '[{"movie_name": "Toy Story"}]' for arrays of objects with brackets outside and braces inside.
  • Index drill: EXPLAIN shows sequential scan, EXPLAIN ANALYZE reports time. GIN timing story near 10 milliseconds sequential versus near 0.276 milliseconds indexed on 20,000 rows, with sizes near 3664 KB plain, near 2512 KB with jsonb_path_ops, and near 288 KB for one key.

Key Industry Applications

  • Web APIs trade JSON between servers and web, mobile, and partner apps, with the Twitter API, Yahoo, and Google data APIs as cited cases. Douglas Crockford popularized the format from 2001, and broad web service adoption followed in 2005 and 2006.
  • Service back ends store wide rows in PostgreSQL, with PostgreSQL 9.2 native JSON types and the PostgreSQL 9.4 GIN index path, and expose narrow JSON views with row_to_json for HTTP clients.
  • Catalog, bookstore, and contact stores keep flexible traits in one JSONB column while keeping plain keys for joins and order. Bulk sample loads use generated packs such as Faker.js output shaped into SQL inserts, as in the contacts_docs.sql drill with about 20,000 papers.
  • Full-text and key search over large document sets uses GIN, with jsonb_path_ops and key-scoped indexes to hold size down. MySQL answers the same needs with JSON_EXTRACT and JSON_CONTAINS, Snowflake with VARIANT columns, PARSE_JSON, and FLATTEN, and Databricks SQL with from_json and to_json.
