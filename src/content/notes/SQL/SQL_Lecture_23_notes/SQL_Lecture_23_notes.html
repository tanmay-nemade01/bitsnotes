23.1 View Fundamentals and Mental Models

23.1.1 What a view is

Why would a database let you query something that stores nothing? That puzzle opens this lecture.

A view answers it: it is a saved question, not a saved answer. You store the question text once, and the system asks the live tables again on each read.

A view (a saved query that behaves like a table) is a database object that stores the text of a SELECT statement, not the rows that statement returns. When the view runs, it goes back to the base tables and fetches fresh rows each time.

Think of a view like a shortcut. A shortcut on a desktop does not hold a copy of a file. It holds the path, and each double-click opens the live file. A view works the same way. It holds the path, which is the query text, and each access runs that query against live tables. The shortcut image breaks at one point: a broken shortcut points nowhere, while a view always points at named tables, so dropping a base table breaks the view in a loud and visible way.

A view holds query text. A base table holds rows. Each read of a plain view runs the stored text against the current base rows and returns the result. Nothing is copied and nothing goes stale, because nothing is stored.

A second helpful image is don't repeat yourself. When the same long query is needed every day or every month, or a hundred times in a row, writing it out each time wastes time and invites typing slips. Saving it once under a short name and calling that name again and again keeps work fast and tidy. The gain is the same as saving a long address as a contact name: one correct copy, many short uses.

In the movies database used here, views live under the database, then schemas, then the public schema, then the views folder. Once made, a view name can be used almost anywhere a table name can be used, across the whole database structure. That means it can sit in a FROM clause, sit inside a join, sit under another view, feed a filter, or feed a sort.

A base table (the real table a view reads from) stays the source of truth. A virtual table (the view itself) has no separate stored rows, except for one special kind described later. It builds its rows on the fly from the base tables. If a base row changes, the next view read shows the change with no extra step.

Across databases the same core holds with small twists. PostgreSQL, MySQL, Snowflake, and Databricks all let a view name stand where a table name stands in a SELECT. Snowflake adds a secure view form that also hides the view text from users without the right role. Databricks adds session-scoped temp views that vanish when the session ends. The lecture default here is the plain shared view, which all four systems support.

23.1.2 Why views help

Views help in four direct ways.

First, they remove repeat work. Write a query once, only once, and read the result when needed. A long statement with joins, subqueries, or recursive logic becomes one short name. A monthly report query with five joins becomes SELECT * FROM v_monthly_report.

Second, they cut clutter. A table may have many columns, but a given task may need only three. A view can show only movie name, movie length, and release date from the movies table, hiding the rest. One table can feed ten or fifteen views, each cut to a different need. Each team sees a small clean shape instead of a wide raw table.

Third, they shape access for safety. Because a view can mix and match columns from one table or from many tables, it can expose only what a given group may see. A classic case is staff data. Programmers may need first name, last name, and date of birth, but not salary. A view that leaves salary out lets them work without seeing pay data. In the same way, permission can be granted on a view that holds only the allowed columns, while the full table stays locked down.

Scope: a plain column-dropping view hides values from honest queries, but it is not a full lock by itself. Pair it with revoked rights on the base table so users must come through the view. Assumption: the safety gain holds only when the base table is private and the view is the granted path.

Fourth, they compose. A view can join to a plain table or to another view. Views can nest inside new views, so a small tested piece can become part of a larger build. Test the join once, save it, then build the filter view on top of it.

Picture a set of building blocks. Each small view is one tested block. A larger view snaps blocks together. A fault in one block is fixed in one place, and every stack built on it picks up the fix.

Pitfall: stacking too many views can hide heavy work. Two or three views that each hide a big join can turn one short outer query into a slow run. Keep nesting shallow for hot paths, and check run time when a view feeds another view.

Staff and payroll systems show the pattern in real life. They often expose a salary-free view of an employee table to developers, while a payroll group gets a wider view. The same base table serves both, with no copied data to drift out of sync. Marketing teams get masked email views in the same way, with the first two and last four characters kept and the middle hidden.

Exam note: be ready to state the one-line core idea in your own words: a plain view stores the query, not the data, and always reads live rows.

23.1.3 Student Questions and Answers

Q: If a view looks like a table, does it hold a copy of the rows?

A: No. A plain view holds only the query text. Each time it is read, it runs that text and returns the latest rows from the base tables. Only the special materialized kind holds stored rows.

Many students trip on this point because the tool shows a view with columns just like a table. The fix is to check the properties pane: a table lists stored rows and size, while a plain view lists stored SQL text.

Q: Where do views sit in the database tree?

A: Under the database, then schemas, then the schema such as public, then the views list. Each new view appears there after a refresh, with its columns shown beneath it.

If the new name is missing, hit refresh on the views folder first. The view is saved even when the list on screen is stale.

A plain view is a named live query. It saves typing, trims wide tables to task-sized shapes, gates who sees what, and snaps together into larger builds. The next part turns that idea into build syntax.

23.2 Creating and Querying Views

23.2.1 Syntax of CREATE OR REPLACE VIEW

How do you turn a tested SELECT into a reusable name? One build verb does it.

Test the SELECT first until the rows look right. Then put CREATE OR REPLACE VIEW name AS in front of it. That order keeps faults in the query, not in the view wrapper.

The build pattern is:

CREATE OR REPLACE VIEW view_name AS query;

CREATE makes a new view. Adding OR REPLACE tells the system to overwrite a view with the same name if one already exists. view_name is the short name to call later. After AS comes any statement that could run as a SELECT, including plain selects, selects with subqueries, selects with joins, and more.

CREATE VIEW fails when the name is taken. CREATE OR REPLACE VIEW overwrites the same name within strict shape rules. The AS query part can hold filters, joins, set stacks, grouping, and subqueries, as long as the output column list is valid.

A naming habit used here is to start view names with v_ or v, for example v_movie_quick or v_movies_directors_all. The prefix makes it easy to tell at a glance whether FROM points at a table or a view. Snowflake guides use a _vw suffix for the same reason. Either form works. Pick one form per project and keep it.

Across databases the same pattern holds. MySQL also accepts CREATE OR REPLACE VIEW plus an optional ALGORITHM hint and a WITH CHECK OPTION tail. Snowflake accepts CREATE VIEW and CREATE SECURE VIEW with the same select body. Databricks accepts plain views plus TEMP VIEW forms that live only in the session. The lecture uses the shared core that all of them run.

23.2.2 Worked Examples

Example 1: a narrow view on the movies table. The goal is to keep only movie name, movie length, and release date, because those three are checked again and again.

Step 1 — test the plain select:

SELECT movie_name, movie_length, release_date
FROM movies;

Check that three columns come back with sane dates and lengths. If the list is wrong here, the view will copy the fault.

Step 2 — wrap it as a view:

CREATE OR REPLACE VIEW v_movie_quick AS
SELECT movie_name, movie_length, release_date
FROM movies;

Step 3 — confirm: the run returns a success note, not a data grid. Refresh the views list. v_movie_quick appears with its three columns. Its properties show the stored SQL text, owner, and schema.

Sense-check: SELECT * FROM v_movie_quick must return the same rows as the Step 1 select.

Example 2: movies joined to directors. The movies table holds a director_id that points at the director_id primary key in the directors table. The join is tested first:

SELECT *
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id;

That returns every column from both tables. Wrapping that exact SELECT * form as a view fails with a duplicate-column error, because director_id now appears more than once and a view will not accept the same column name twice.

Pitfall: SELECT * is fine for a quick test, but it is a trap inside a join view. Shared key names come in twice, and the view build stops. Always switch to a named column list before saving a join as a view.

The fix is to name each needed column once:

SELECT
  mv.movie_id,
  mv.movie_name,
  mv.movie_length,
  mv.movie_lang,
  mv.age_certificate,
  mv.release_date,
  mv.director_id,
  d.first_name,
  d.last_name,
  d.date_of_birth,
  d.nationality
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id;

Once that select runs clean, it is saved:

CREATE OR REPLACE VIEW v_movies_directors_all AS
SELECT
  mv.movie_id,
  mv.movie_name,
  mv.movie_length,
  mv.movie_lang,
  mv.age_certificate,
  mv.release_date,
  mv.director_id,
  d.first_name,
  d.last_name,
  d.date_of_birth,
  d.nationality
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id;

A side gain appears here. Table column order is fixed at table build time, but a view can list columns in any order wanted. If length should read before name, the select list can put it there. The view also renames for free with AS: d.first_name AS director_first_name would give readers a clearer label.

23.2.3 Reading data through a view

Reading a view uses the same shape as reading a table, with the view name where the table name would go:

SELECT * FROM v_movie_quick;

The system takes the stored query, runs it, and shows the rows. The same holds for the join view:

SELECT * FROM v_movies_directors_all;

Filters, sorts, grouping, and joins all work on top of the view name. The outer query treats the view output as its input rows.

A view call is a macro run: the stored text is merged into the outer query and the whole thing runs against base tables. That is why outer WHERE, ORDER BY, and GROUP BY clauses keep working on views.

In the visual tool, a view can be opened by going to the database, then schemas, then views, then right-click for properties. Properties show the name, owner, schema, stored SQL, and security settings. The definition tab is the place to copy the stored text when a read looks wrong.

23.2.4 Student Questions and Answers

Q: I wrapped SELECT * from a join into a view and got an error about a column appearing more than once. What went wrong?

A: The two tables share a column name, here director_id, so SELECT * brings it in twice. A view needs each output column to appear only once. List each wanted column by name, keep director_id from one side only, and then the CREATE VIEW runs.

Q: How do I know the view saved if no rows came back?

A: CREATE VIEW returns a success note, not a data grid. Refresh the views list. The new name appears there with its columns, and its properties show the stored query text.

Build views in two moves: test the SELECT, then wrap it. Name join columns one by one, read views like tables, and use the properties pane as the source of truth.

23.3 Renaming and Deleting Views, Ownership and Permissions

23.3.1 Renaming a view

A view name is just a label on stored SQL, so changing the label is cheap and safe.

The rename pattern is:

ALTER VIEW view_name RENAME TO new_view_name;

For example:

ALTER VIEW v_movie_quick RENAME TO v_movie_quick_2;

Trace the rename: before the run the views list shows v_movie_quick. Run the ALTER VIEW line. Refresh the views folder. The list now shows v_movie_quick_2 with the same three columns and the same stored SQL. Any query that used the old name now fails, so update saved reports that point at it.

After a refresh, the views list shows the new name. The same change can be made with a right-click, then properties, then editing the name field. The SQL pane in properties mirrors the same stored statement that the query editor would run. Both paths change only the name. The stored query text stays the same.

23.3.2 Who may rename

Only the owner may rename a view. This is easy to trip over. If the view owner is set to one account, say Adam, and a session logs in as a different account, an ALTER VIEW ... RENAME TO ... attempt stops with a must-be-owner message. Even a superuser session can mask this during a demo, so the check shown here logs in through a terminal session as the non-owner to prove the block is real.

The terminal pattern used is:

-- login as a named user against the movies database, then try:
ALTER VIEW v_movie_quick RENAME TO v_movie_quick_2;
-- result when run as a non-owner: must be owner of view

View rights follow ownership. The account listed as owner in the properties pane can alter, rename, and drop. Other accounts get a must-be-owner stop until the owner grants rights or hands over ownership.

The takeaway is plain: rename, alter, and drop rights follow ownership. Make sure the active account owns the view before trying to change its shape or name. In team work this means the account that builds shared views should be a shared role, not one person, so renames do not stall when someone is away.

Pitfall: testing rights from a superuser account hides the block. A superuser can often pass checks that a normal app account would fail. Always re-test renames and drops from the real app account before shipping rights scripts.

23.3.3 Deleting a view

The drop pattern is:

DROP VIEW v_movie_quick;

It runs at once and returns a success note with timing. A refresh then shows one fewer view in the list. Dropping a view never deletes base table rows. It only removes the saved query text.

Scope: DROP VIEW removes the label and the stored text. Base tables, other views, and saved data stay in place. But any view or report built on top of the dropped name breaks at its next run, so check dependents first.

The query editor gives no are-you-sure prompt. It just runs. For that reason, many people prefer to delete through the visual tool, where right-click then delete opens a confirm prompt. That pause helps when the target might be a row, a column, a whole table, a schema, or a view. The rule of thumb is simple: use the prompt path for anything that deletes, and type DROP only when sure.

Drops can be made safer in scripts with a guard clause. PostgreSQL accepts DROP VIEW IF EXISTS v_movie_quick, which skips the run with a notice instead of an error when the name is already gone. MySQL and Snowflake accept the same IF EXISTS tail. Use it in setup scripts that may run twice.

23.3.4 Student Questions and Answers

Q: I am logged in but ALTER VIEW says I must be the owner. Why?

A: The view belongs to a different account. Only the owner account can rename or alter it. Log in as the owner, or have the owner make the change or hand over ownership, then retry.

Q: DROP VIEW ran with no warning. Is that normal?

A: Yes. The query editor runs drops at once with no confirm step. To get a confirm step, delete from the visual tool with right-click then delete.

Rename with ALTER VIEW ... RENAME TO ..., drop with DROP VIEW, and check ownership first. Scripted drops should carry IF EXISTS so re-runs stay clean.

23.4 Filtering and Composing Views

23.4.1 Filters on a single-table view

Why save a broad view when each report needs a different slice? Because the broad part is written once and each slice adds one small filter.

Build the shared filter into the view. Add the changing filter at read time. Each report then stays two lines instead of ten.

A view can be filtered after it is built, just like a table. The pattern is to build a broad view once, then add WHERE and ORDER BY at read time.

Example: all movies released after 1997. First the base rows are eyed with:

SELECT * FROM movies ORDER BY release_date DESC;

Then a cutoff is added. Dates in the demo use a text form such as 1997-12-31 inside quotes, with >= to keep the boundary day:

SELECT * FROM movies
WHERE release_date >= '1997-12-31'
ORDER BY release_date DESC;

Wrap the tested filter as a view:

CREATE OR REPLACE VIEW v_movies_after_1997 AS
SELECT * FROM movies
WHERE release_date >= '1997-12-31';

Now each narrow read is short:

SELECT * FROM v_movies_after_1997
WHERE movie_lang = 'English';
SELECT * FROM v_movies_after_1997
WHERE movie_lang = 'English'
AND age_certificate = '12';

Sense-check: the two-filter read must match the one-shot query with all three conditions on movies. The view only moved the date test inside.

The same result without a view would repeat the date filter and the base select each time. With the view, the repeat part is written once and the changing part stays small. When the cutoff moves, one view edit fixes every report.

Scope: outer filters stack on top of the view filter with AND logic. A row must pass both the stored WHERE and the outer WHERE to show. The view cannot widen its own filter at read time, only narrow it.

23.4.2 Filters on a join view

The same trick removes repeated join text. Instead of rewriting an INNER JOIN between movies and directors each time, read the saved join view and filter it:

SELECT * FROM v_movies_directors_all
WHERE nationality IN ('American', 'Japanese');

Without the view, the same ask needs the full join plus aliases plus the filter:

SELECT *
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id
WHERE d.nationality IN ('American', 'Japanese');

A pleasant side effect is that reads on the view can name the plain column, such as nationality, with no table alias. The view already fixed the join and the aliasing inside, so the outer query stays clean. Report writers need not know which base table held the column.

Ask Without view With view
Filter joined rows Repeat join, aliases, keys, filter View name plus filter
Who must know the join keys Every report writer Only the view builder
Typo surface Large Small

When to pick which: use the join view for every repeated join. Inline the join only for one-off asks where saving a view would add clutter.

23.4.3 A view with UNION of two tables

A UNION ALL (a stack that keeps every row from each side, including repeats) can also sit inside a view. The case here gathers all people tied to films, meaning actors plus directors, with first name and last name from each.

Step one pulls actors:

SELECT actor_id, first_name, last_name
FROM actors;

Step two pulls directors:

SELECT director_id, first_name, last_name
FROM directors;

A UNION ALL stack needs the same column count and matched types on each side. Column names come from the first side. A fixed text label on each side keeps the source after the stack.

Step three stacks them and tags each row so readers can tell its source. A fixed text column is added on each side:

SELECT first_name, last_name, 'actor' AS people_type
FROM actors
UNION ALL
SELECT first_name, last_name, 'director' AS people_type
FROM directors;

That returns 185 rows in the demo. Then it is saved:

CREATE VIEW v_all_actors_directors AS
SELECT first_name, last_name, 'actor' AS people_type
FROM actors
UNION ALL
SELECT first_name, last_name, 'director' AS people_type
FROM directors;

Reads stay short:

SELECT * FROM v_all_actors_directors
ORDER BY people_type, first_name;

Filters also work on the stacked view:

SELECT * FROM v_all_actors_directors
WHERE first_name = 'John';

A wider prefix search uses a pattern match for names starting with J, which returns 20 rows in the demo. The people_type column still shows whether each John is an actor or a director. Use UNION instead of UNION ALL only when exact duplicate rows must collapse into one. The plain UNION form pays a sort cost, so keep ALL when repeats are fine or the label column already splits them.

23.4.4 One view across three tables

Movies, directors, and movie revenues can be served through one view. The links are: movies to directors on director_id, and movie revenues to movies on movie_id.

The three-way join is tested first:

SELECT *
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id
INNER JOIN movies_revenues AS r
ON r.movie_id = mv.movie_id;

Trying to save that SELECT * form as a view fails, because movie_id now appears more than once. The same column-specified-more-than-once error from the two-table case comes back. The fix is the same: pick each column once by name.

CREATE VIEW v_movies_directors_revenues AS
SELECT
  mv.movie_id,
  mv.movie_name,
  mv.movie_length,
  mv.movie_lang,
  mv.age_certificate,
  mv.release_date,
  d.first_name,
  d.last_name,
  d.nationality,
  d.date_of_birth,
  r.revenues_domestic,
  r.revenues_international
FROM movies AS mv
INNER JOIN directors AS d
ON d.director_id = mv.director_id
INNER JOIN movies_revenues AS r
ON r.movie_id = mv.movie_id;

Read and filter with no join text:

SELECT * FROM v_movies_directors_revenues;
-- 53 rows in the demo
SELECT * FROM v_movies_directors_revenues
WHERE age_certificate = '12';

Sense-check: the 53-row count must match the raw three-way join count. If it drifts, a base table changed, not the view.

The with-view form is a few lines. The without-view form repeats the whole join plus the filter, which is long and easy to mistype. Apps also gain: the app sends a short select and the database owns the join logic, so a key change is fixed in one view, not in ten app files.

23.4.5 Student Questions and Answers

Q: Do I have to repeat the join and aliases when I filter a join view?

A: No. Put the join and aliases inside the view once. Then filter the view by plain column names such as nationality or age_certificate, with no aliases in the outer query.

Q: How do I tell actors apart from directors inside a UNION view?

A: Add a fixed text column on each side, for example 'actor' and 'director' as people_type. After stacking with UNION ALL, each row carries its source label.

Test the select, wrap it, then filter the short name. Name join columns one by one, label union sides, and let the view carry the join keys.

23.5 Changing View Shape and Replace Rules

23.5.1 The core limit

Can a stored view gain, lose, or shuffle columns in place? Only within tight rules.

PostgreSQL treats the stored column list as a contract. CREATE OR REPLACE VIEW may append new columns at the end. It may not drop a stored column or shuffle stored order in place. Reorder or removal needs a rebuild under a swapped name or a drop plus rebuild.

PostgreSQL will not remove a column from a stored view in place by a simple column-drop. The stored query must keep producing the same columns it produced before, unless the view is rebuilt. In practice there are three ways to change shape: rename the old view aside and build the new one, drop and rebuild, or use CREATE OR REPLACE within its strict rules.

MySQL follows the same shape rule for replace, and Snowflake shares the same habit: views freeze column metadata at build time, so base-table changes do not rewrite the view on their own. If a used base column is dropped, the view goes invalid until it is rebuilt.

23.5.2 Reordering columns

Start from a simple directors view:

CREATE VIEW v_directors AS
SELECT first_name, last_name
FROM directors;

Goal: show last name first. Trying to flip the order in place with plain CREATE VIEW and the same name stops with a relation-already-exists error.

Working path — build the wanted order under a new name:

CREATE VIEW v_directors_new AS
SELECT last_name, first_name
FROM directors;

Then drop or rename the old view and rename the new one back to the wanted name. The demo does exactly this dance: rename the first view to an old name, build the flipped view, check both in the list, then clean up and rename back so the main name again holds first name then last name.

Sense-check: after the swap, SELECT * FROM v_directors shows the new order and the properties pane shows the new stored text.

The path shown is to shuffle names: build the wanted order under a new name or rename the old one aside, then build. Name swaps are instant because only the label moves. No rows are copied.

23.5.3 Removing a column

The same rebuild idea applies. From a two-column view, a one-column view is made by building fresh:

SELECT * FROM v_directors;
-- shows first_name, last_name

To keep only first name, rename or drop the old view, then:

CREATE VIEW v_directors AS
SELECT first_name
FROM directors;

A refresh shows a single column inside. There is no in-place column removal that keeps the same stored query. Rename-aside or drop-then-build is the working method.

Pitfall: reports that read the view by position (SELECT * into fixed slots) break silently when a column is dropped. Reports that name columns keep working. Always name columns in reports that read shared views.

23.5.4 Adding a column at the end

New columns may be appended at the end of the column list with OR REPLACE. Start from the two-column view, then run the base table check:

SELECT first_name, last_name, nationality
FROM directors;

Then replace:

CREATE OR REPLACE VIEW v_directors AS
SELECT first_name, last_name, nationality
FROM directors;

A refresh shows the new nationality column added after the old ones. But order changes in the middle are blocked. Trying to move nationality into the middle, for example between first name and last name, stops with a cannot-change-order style error that names the view columns. The rule is: OR REPLACE can add columns at the end, but it cannot change the name order of the columns already there. Leaving plain CREATE VIEW without OR REPLACE on an existing name also stops with a relation-already-exists error, which is a reminder that OR REPLACE is the part that permits overwriting.

Teams that publish views to reports use this rule on purpose. They often add new fields only at the end, so old reports that read by position keep working. A middle insert would shift every slot after it and break those readers.

Scope: OR REPLACE keeps current dependents alive when it succeeds. Drop plus rebuild breaks dependents until the name returns. Prefer replace for end-appends, and save drop-rebuild for true reshapes done in a quiet window.

23.5.5 Student Questions and Answers

Q: Can I move a column into the middle of a stored view with OR REPLACE?

A: No. New columns can be added at the end, but the order of the stored columns cannot be changed in place. To reorder, build a new view with the wanted order and swap names, or drop and rebuild.

Q: Why does plain CREATE VIEW fail when the name already exists?

A: Plain CREATE will not overwrite. Add OR REPLACE to overwrite within its rules, or use a fresh name.

Append at the end with replace. Rebuild with a name swap for reorders and removals. Name columns in every reader so shape edits stay safe.

23.6 Regular Views Stay Live

23.6.1 No stored rows

What happens to a view when the base table gains a row? Nothing needs to happen, because the view stored no rows at all.

A plain view (the normal kind, not materialized) stores no rows on disk. It stores the query and runs it on each read, so it always shows the latest base-table rows.

This is the line that splits plain views from snapshots. A plain view pays query time on each read and returns fresh rows. A snapshot pays storage plus a refresh beat and returns cached rows. Fresh plus slow versus fast plus stale is the whole trade.

Visualize a window, not a photo. A photo freezes a scene. A window shows the live street each time you look. A plain view is the window. A materialized view is the photo, updated only when someone takes a new shot.

23.6.2 Worked Examples

Start with the directors view:

SELECT * FROM v_directors;
-- 38 rows in the demo: first_name, last_name, nationality

Add a row to the base table, not to the view:

INSERT INTO directors (first_name)
VALUES ('test_name_one');

Check the base table:

SELECT * FROM directors;
-- new row appears at the end

Read the view again:

SELECT * FROM v_directors;
-- new row appears at the end of the view as well

No refresh step was needed. The view picked up the new row because it re-ran its query.

Clean up. Find the test row id, here 39 in the demo, and delete from the base table:

DELETE FROM directors
WHERE director_id = 39;

Both the base table read and the view read now show no test row. The view again mirrors the base at once.

Sense-check: base count and view count move together on every step. If they ever differ, the view has its own filter or join that hides some base rows.

The same live behavior explains the earlier join reads. Each SELECT * FROM v_movies_directors_all re-joins movies and directors at that moment, so inserts, updates, and deletes in either base show up right away. The price of that freshness is run time. Each read pays the cost of going to the tables and running the query again.

Scope: live reads suit small lookup tables and per-team column slices where fresh rows matter more than speed. Heavy joins over large tables read through a plain view on each hit can feel slow. That is the signal to cache the result as a snapshot instead.

Live views suit small lookup tables and per-team column slices where fresh rows matter more than speed.

Exam note: state the contrast in one line: plain views give fresh rows on every read but pay query time on every read.

23.6.3 Student Questions and Answers

Q: I added a row to the base table. Why did the view change with no refresh?

A: A plain view has no stored copy. It re-runs its query on each read, so new, changed, or deleted base rows show up at once.

Prove liveness the same way each time: count the view, change the base, count the view again. The counts track each other with no refresh call.

23.7 Updatable Views and Their Strict Rules

23.7.1 What updatable means

Reads through a view are free. Writes through a view are earned by keeping the view shape simple.

An updatable view (a view that accepts writes that land in the base table) looks like a table for INSERT, UPDATE, and DELETE. The system passes each write to the one base table behind the view. No rows ever rest in the view itself.

An updatable view lets INSERT, UPDATE, and DELETE run against the view name, with the change passed through to the single base table or single updatable view behind it. Reads still work, but the point of this shape is writes. Support staff can fix a name through a narrow view without ever opening the full table.

Snowflake draws a harder line here than PostgreSQL: in Snowflake, views are read-only and no write passes through at all. MySQL sits closer to PostgreSQL but blocks inserts when the view holds derived columns. The lecture rules below are the PostgreSQL form used in the demo.

23.7.2 The five rules

Keep the view to plain columns from one source and the write path stays open. Add crunching, shaping, or a second source and the path closes.

One, the query must have a single FROM entry. That entry can be one table or one updatable view, so nesting is allowed, but only one source at the top.

Two, the top level of the query cannot hold crunching or shaping clauses. That means no DISTINCT, no GROUP BY, no HAVING, no LIMIT, no OFFSET, no UNION, no INTERSECT, and no EXCEPT. Window clauses with WITH in the demo wording also fall in this blocked set at the top.

Three, the select list cannot hold window functions, set-returning functions, or aggregate functions such as SUM, COUNT, AVG, MIN, or MAX on columns. The view is meant to pass plain column writes through, not to compute over groups.

Four, the allowed write verbs are INSERT, UPDATE, and DELETE, each with a WHERE filter as needed. Reads use the same view name with plain SELECT.

Five, the writer needs the matching right on the view itself. No right on the base table is needed when the view right is in place. That split is a strong safety gain. A user can be given write rights on a narrow view only, with no direct rights on the full table.

Picture a mail slot cut into one door. Plain columns from one table are the open slot: letters pass through to the room behind. Aggregates, grouping, and second tables board the slot shut. The slot shape decides, not the person posting the letter.

23.7.3 Worked Examples

Build a narrow updatable view on directors with plain columns only:

CREATE OR REPLACE VIEW vu_directors AS
SELECT first_name, last_name
FROM directors;

Refresh the views list to confirm it. Then insert through the view, not the table:

INSERT INTO vu_directors (first_name, last_name)
VALUES ('dir_one', 'dir_one'), ('dir_two', 'dir_two');

Read through the view:

SELECT * FROM vu_directors;
-- new rows appear at the end

Read the base table:

SELECT * FROM directors;
-- same new rows appear, because the view passed them through

Delete through the view with a filter:

DELETE FROM vu_directors
WHERE first_name = 'dir_one';

The view read then shows the first test row gone. Repeating for the second test value clears both. The base table mirrors each change.

Sense-check: counts in the view and in directors rise by two after the insert and fall back after the deletes. The view stored nothing in between.

The properties pane for the view shows the stored query under definition and the owner under security. As long as ownership and view rights are right, writes pass through even without base-table rights.

Pitfall: a derived column such as a masked email or a computed total is not writable even when the rest of the view is. Updates to that column stop with a not-updatable error. Worse, in MySQL a derived column can block inserts into the whole view even when the insert skips that column. Keep write views to raw columns only.

Help-desk tools show the value in real life. They often write through a narrow view that exposes only safe columns, so agents can fix names without touching pay or key fields.

Exam note: learn the blocked list cold: one FROM, no distinct, group, having, limit, offset, union, intersect, except at the top, and no window, set-returning, or aggregate functions in the select list.

23.7.4 Student Questions and Answers

Q: Can I put COUNT or GROUP BY in an updatable view?

A: No. Aggregates in the select list and grouping or set shaping at the top block the updatable path. Keep the query to plain columns from a single source, then INSERT, UPDATE, and DELETE can pass through.

Q: Does a writer need rights on the base table too?

A: No. The matching right on the view is enough. That is why narrow updatable views are handy for safe delegated writes.

One source, plain columns, no shaping: that is the full recipe for a writable view. Break any part and reads still work but writes stop.

23.8 Guarding Writes with Check Options

23.8.1 The hole without a check

A sliced view shows some rows and hides the rest. Without a guard, writes through that view can land rows the view itself will never show again.

A plain updatable view checks the shape of a write, not its content. It passes the row to the base table even when the row fails the view filter. That silent split is the hole.

Demo setup uses a small countries table:

CREATE TABLE countries (
  country_id SERIAL,
  country_code VARCHAR(4),
  city_name VARCHAR(100)
);

Seed rows:

INSERT INTO countries (country_code, city_name)
VALUES ('US', 'New York'), ('US', 'Boston'), ('UK', 'London');

A US-only view:

CREATE VIEW v_cities_us AS
SELECT country_id, country_code, city_name
FROM countries
WHERE country_code = 'US';

Reading the view shows two rows. Reading the base shows three. Insert a US city through the view:

INSERT INTO v_cities_us (country_code, city_name)
VALUES ('US', 'California');

The view read now shows California. So far so good. Now insert a UK city through the same US-only view:

INSERT INTO v_cities_us (country_code, city_name)
VALUES ('UK', 'Manchester');

It succeeds with no check in place. The view read still shows only US rows, so Manchester seems to vanish. But the base read proves it landed:

SELECT * FROM countries;
-- Manchester is present in the base, absent from the view

Sense-check: base count is now five while the view shows three. The gap of two hidden rows is the leak.

That split is the safety hole. A user or app can add rows through a sliced view that the same view will never show again. Reports built on the view undercount, while the base keeps growing.

23.8.2 WITH CHECK OPTION

A CHECK OPTION (a guard that forces writes through a view to meet the view filter) closes that hole. Rebuild the same view with the guard at the end:

CREATE OR REPLACE VIEW v_cities_us AS
SELECT country_id, country_code, city_name
FROM countries
WHERE country_code = 'US'
WITH CHECK OPTION;

WITH CHECK OPTION turns the view filter into a write rule. Every INSERT or UPDATE through the view must produce a row that the view itself would show. Out-of-view rows are rejected with a check-option error that names the view.

Now the same UK insert is rejected with a new-row-violates-check-option message that names the view. An update that would move a row out of the view is rejected the same way:

UPDATE v_cities_us
SET country_code = 'UK'
WHERE city_name = 'New York';
-- rejected: row violates check option

A US insert still passes:

INSERT INTO v_cities_us (country_code, city_name)
VALUES ('US', 'Chicago');
-- succeeds and shows in the view

In short, with the guard, every insert, update, or delete through the view must meet the view condition. Without it, out-of-view rows can slip into the base unseen. MySQL carries the same tail on its views, so this guard ports across systems. Snowflake needs no such guard because its views take no writes at all.

23.8.3 LOCAL versus CASCADED on nested views

Views can nest, and then the question is how far the guard reaches. Two forms answer it.

Start with a base view for cities starting with C:

CREATE OR REPLACE VIEW v_cities_c AS
SELECT country_id, country_code, city_name
FROM countries
WHERE city_name LIKE 'C%';

In the demo this shows California and Chicago, both US rows. Then build a second view on top of the first that keeps only US rows, first with the local form:

CREATE OR REPLACE VIEW v_cities_c_us AS
SELECT country_id, country_code, city_name
FROM v_cities_c
WHERE country_code = 'US'
WITH LOCAL CHECK OPTION;

LOCAL means check only the current view filter.

Insert a US city starting with C:

INSERT INTO v_cities_c_us (country_code, city_name)
VALUES ('US', 'Connecticut');
-- succeeds, shows in the view

Insert a US city starting with L:

INSERT INTO v_cities_c_us (country_code, city_name)
VALUES ('US', 'Los Angeles');
-- succeeds at write time, but never shows in the view

The base read proves Los Angeles landed. The top view hides it because its own source view only holds C names, yet LOCAL never looked up that far. It checked only country code equals US, which passed.

Now swap the guard to the cascaded form:

CREATE OR REPLACE VIEW v_cities_c_us AS
SELECT country_id, country_code, city_name
FROM v_cities_c
WHERE country_code = 'US'
WITH CASCADED CHECK OPTION;

CASCADED means check this view plus every view beneath it, going up the chain.

Retry a US city not starting with C:

INSERT INTO v_cities_c_us (country_code, city_name)
VALUES ('US', 'Boston');
-- rejected: new row violates check option for view v_cities_c

It passes the local US test but fails the lower C-name test, so it is blocked. Insert a US city starting with C:

INSERT INTO v_cities_c_us (country_code, city_name)
VALUES ('US', 'Clearwater');
-- succeeds and shows in the view

It passes both levels, so it lands and shows.

Memory hook: local looks only here, cascaded climbs the whole stack. PostgreSQL uses CASCADED as the default when the keyword is skipped, so say LOCAL out loud whenever the narrow check is truly wanted.

Pitfall: LOCAL on the top view still enforces a lower view guard when that lower view itself carries a check option. The leak only happens when the lower view has no guard at all. Always check the full stack, not just the top label, before trusting a nested write path.

23.8.4 Student Questions and Answers

Q: I added Manchester through a US-only view and now I cannot see it in that view. Where did it go?

A: It went into the base table but not into the view filter. Without WITH CHECK OPTION, the write succeeds even though the row fails the view condition. Add the check guard to block such writes, so only US rows can pass through the US view.

Q: What is the gap between LOCAL and CASCADED when views nest?

A: LOCAL checks only the top view filter, so Los Angeles passed the US test even though its name broke the lower C-name view. CASCADED checks the top view and all views below it, so Boston was blocked for breaking the lower C-name test while Clearwater passed both.

Guard every sliced write view with a check option. Use LOCAL for the top slice only and CASCADED for the whole stack.

23.9 Materialized Views in Depth

23.9.1 Concept and contrast

What if a view query is too heavy to rerun on each read? Save its answer and serve the saved copy.

A plain view is a live window onto base tables. A materialized view is a dated photo of the answer. The window is always fresh and always costs a fresh look. The photo is fast to pass around but ages until the next shot.

A materialized view (a stored snapshot of a query result that is refreshed on demand) runs its query once, saves the output rows, and serves those saved rows until the next refresh. That is the flip of a plain view, which re-runs its query on every read.

Plain view: fresh rows on each read, full query cost on each read. Materialized view: fast reads from saved rows, stale risk until the next refresh. Pick freshness for small live slices and snapshots for heavy repeated reads.

The trade is freshness against speed. Plain views give fresh rows each time but pay full query time each time, since they revisit base tables, joins, and functions. Materialized views give fast reads from saved rows but serve cached rows that can go stale. They shine for heavy, costly queries: deep joins, unions, filters, and math over large tables, where on-the-fly runs would feel slow to users.

A practical shape is to run the heavy work once, save it, and show the saved result with a delay note such as updated every two hours. Users get fast pages, and the delay is stated up front. Stock correlation over tens of thousands of symbols is a good fit: compute once, serve many reads, refresh on a beat.

A materialized view also behaves much like a table after it is built. Indexes can be added, keys can be set, and upkeep verbs such as vacuum and analyze apply. That matters because these snapshots are often refreshed often.

Across databases the refresh story splits. PostgreSQL refreshes on demand with REFRESH MATERIALIZED VIEW, and the concurrent form needs a unique index. Snowflake refreshes materialized views on its own in the background but charges storage plus upkeep. Databricks SQL offers materialized views with scheduled refresh pipelines. MySQL has no native materialized view at all, so teams there hand-roll snapshot tables. The lecture demo is the PostgreSQL on-demand form.

Click dashboards, market screens, and currency or commodity boards show the pattern in real life. They often read from materialized snapshots refreshed by a cron beat, rather than joining huge raw tables on each page hit.

Exam note: one line to hold: plain view equals fresh rows plus query cost each read, materialized view equals fast cached rows plus stale risk until refresh.

23.9.2 Creation with data or no data

The build pattern is:

CREATE MATERIALIZED VIEW IF NOT EXISTS view_name AS query
WITH DATA;

WITH DATA runs the query at build time and loads the output rows at once. WITH NO DATA builds an empty shell with the right columns but no rows. That shell cannot be read until it is filled, and a read attempt stops with a has-not-been-populated message plus a hint to run refresh.

Example on directors. Test the select first:

SELECT first_name, last_name
FROM directors;

Then save it filled:

CREATE MATERIALIZED VIEW IF NOT EXISTS mv_directors AS
SELECT first_name, last_name
FROM directors
WITH DATA;

Reading it looks like a table read:

SELECT * FROM mv_directors;

To show the empty form, build a second one:

CREATE MATERIALIZED VIEW IF NOT EXISTS mv_directors_no_data AS
SELECT first_name, last_name
FROM directors
WITH NO DATA;

A read at once:

SELECT * FROM mv_directors_no_data;
-- stopped: materialized view has not been populated

Fill it with:

REFRESH MATERIALIZED VIEW mv_directors_no_data;

A repeat read then returns the rows pulled from the base table at refresh time. Sense-check: row counts in the snapshot match the base select count at the moment of refresh, not at the moment of reading.

In the visual tree it sits under schemas, then public, then materialized views. The mv_ prefix keeps snapshots apart from plain v_ views at a glance.

23.9.3 Refresh and drop

Refresh re-runs the stored query and swaps in the new snapshot:

REFRESH MATERIALIZED VIEW mv_directors;

The plain refresh locks the snapshot while it rebuilds, so reads wait. The concurrent form avoids that lock:

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_my_data;

CONCURRENTLY builds a temp copy, compares versions, and applies only the changed rows, so reads can continue during the rebuild. It needs a unique index on the snapshot, described later. The working habit is: build once with data, which locks while it fills, then use the concurrent refresh after that to stay open for readers.

Scope: plain refresh is simpler and works with no index, but it blocks readers during the rebuild. Concurrent refresh keeps readers flowing but stops at once when the unique index is missing. Choose plain for quiet windows and concurrent for live traffic.

Drop uses its own verb:

DROP MATERIALIZED VIEW mv_directors_no_data;

As with all drops, care is needed. Drop plus rebuild acts like a table drop plus rebuild and gives up the stay-open-while-refreshing gain. Check for dependent objects and load effects before dropping on a live system.

23.9.4 Student Questions and Answers

Q: Why is my new materialized view unreadable with a not-populated message?

A: It was built WITH NO DATA, so it is an empty shell. Run REFRESH MATERIALIZED VIEW with its name to load rows, then read it again.

Q: How do I refresh without blocking readers?

A: Use REFRESH MATERIALIZED VIEW CONCURRENTLY with the view name. It needs a unique index on the view, but it lets queries continue while the new snapshot builds.

Build filled with WITH DATA for instant reads. Build empty with WITH NO DATA only when the first fill must wait. Refresh plain in quiet windows and concurrently on live sites.

23.10 Running and Guarding Materialized Snapshots

23.10.1 Writes go to the base, not the snapshot

Can you fix a typo by editing the snapshot? No. The snapshot is sealed. Only the base is writable.

Rows cannot be written straight into a materialized view. All three write verbs stop the same way.

INSERT INTO mv_directors (first_name, last_name)
VALUES ('dir_one', 'dir_two');
-- stopped: cannot change materialized view
DELETE FROM mv_directors WHERE first_name = 'dir_one';
-- stopped: cannot change materialized view
UPDATE mv_directors SET first_name = 'dir_one'
WHERE first_name = 'dir_one';
-- stopped: cannot change materialized view

The path is: change the base table or base query, then refresh. Add rows to directors, then:

REFRESH MATERIALIZED VIEW mv_directors;
SELECT * FROM mv_directors;
-- new rows now show

Sense-check: the snapshot count moves only on refresh. Base edits between refreshes stay invisible to snapshot readers by design.

Snapshot writes flow one way: base edit first, refresh second, snapshot read third. Direct writes to the snapshot name always stop. This one-way flow is what keeps cached reads fast and safe.

By contrast, the plain narrow view vu_directors from the earlier part does accept writes and passes them to directors at once. That contrast is worth holding: plain views can pass writes through when their strict rules are met, while snapshots never accept direct writes and only move on refresh. Housekeeping in the demo removes test ids such as 43, 44, and 45 from directors with a single DELETE ... WHERE director_id IN (...) so later queries start clean.

23.10.2 How to tell if a snapshot holds rows

An app that reads a snapshot on a timer needs a cheap populated check that does not trigger the not-populated error. The system catalog holds that flag. The pattern reads the populated marker for the named view:

SELECT relispopulated
FROM pg_class
WHERE relname = 'mv_directors';

A true value means rows are loaded. A false value means a refresh is still needed. This is handy when fills run from a cron beat and readers need to know whether the snapshot is ready yet. Dashboards can show a loading note while the flag is false instead of crashing on a read.

23.10.3 Why a snapshot can beat a plain table redo

The same cached result could be built by hand with tables: build a temp copy from the source, insert new rows there, drop the old table, and rename the temp into place. That is four careful steps, and the drop plus rename window can lock readers out.

The snapshot path is two steps:

CREATE MATERIALIZED VIEW IF NOT EXISTS mv_my_data AS
SELECT ... FROM ... WHERE ...
WITH DATA;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_my_data;

The concurrent refresh builds a temp update, diffs the two versions, and writes only the changed rows, with no long lock. Reads can continue during the rebuild. The one hard need is a unique index on the snapshot, or the concurrent form stops and asks for one.

Path Steps Reader lock Changed-row diff
Hand table swap Temp, fill, drop, rename Locked at swap Manual
Plain refresh One refresh call Locked during rebuild Full swap
Concurrent refresh One refresh call plus unique index Open during rebuild System diff

When to pick which: hand tables fit shops that need full custom control. Concurrent snapshots fit live boards that must stay readable during each beat.

23.10.4 Downsides and care points

Snapshots depend on their base tables and add links that must be managed. When base columns, indexes, or shapes change through add, edit, or delete work, each dependent snapshot must be reviewed and kept in line. In a shop with huge tables feeding many apps and teams, that care can turn heavy, since every team must grasp links that may sit outside its own app. In such spots a plain table copy may fit better. The choice stays case by case.

Scope: each snapshot adds a link to track. A base column rename, a dropped index, or a type change can stale or break every snapshot built on it. Review linked snapshots in the same change ticket as the base edit, not after.

A memory hook used here is M for manage. Materialized starts with M, and M means manage the links. Good design up front, plus a naming plan with a prefix such as mv_, keeps the set easy to track.

Teams that refresh market or click snapshots on a fast beat show the care in real life. They pair each snapshot with a unique index and a stated delay, so readers know the data is cached and writers know where writes must go.

23.10.5 Student Questions and Answers

Q: Can I fix a typo by updating the materialized view directly?

A: No. Direct INSERT, UPDATE, and DELETE on a snapshot all stop with a cannot-change message. Fix the base table, then run REFRESH MATERIALIZED VIEW so the snapshot picks up the fix.

Q: What breaks if I change base table columns without checking snapshots?

A: Dependent snapshots can drift or fail, since they link to the old shape. Review and manage each linked snapshot whenever base columns or indexes change.

Write to the base, refresh the snapshot, then read. Track each snapshot link with an mv_ name and a unique index so live refreshes stay open.

23.11 Live Build, Catalog Checks, and Index Gaps

23.11.1 Worked Examples: page-click snapshots

How does a heavy click feed become a fast trend board? Raw table first, sums second, snapshot third, daily slice fourth, index plus cron beat last.

The full arc runs in five moves: make the raw table, load test rows with set math, sum by day and page, save the sums as snapshots, then shrink the refresh to a daily slice with a unique index.

This build shows the full arc on a fake click feed: make a raw table, load 10,000 rows with set math, sum it up, save the sums as snapshots, and refresh on a daily slice.

Make the raw table:

CREATE TABLE page_clicks (
  record_id SERIAL,
  page TEXT,
  click_time TIMESTAMP,
  user_id BIGINT
);

Load 10,000 test rows in one shot. Page names cycle through three sites, click time uses the current time, user ids spread from 1 to 1000 with a random step, and a series from 1 to 1000 drives the row count:

INSERT INTO page_clicks (page, click_time, user_id)
SELECT
  CASE (FLOOR(RANDOM() * 3))::INT
    WHEN 0 THEN 'click_analytics'
    WHEN 1 THEN 'click_apis'
    ELSE 'google'
  END,
  NOW(),
  (FLOOR(RANDOM() * 1000) + 1)::BIGINT
FROM GENERATE_SERIES(1, 10000) AS seq;

That generator is a handy load-test tool. It can be reshaped to stress other tables, views, and schemas before real traffic arrives.

Check the load:

SELECT * FROM page_clicks;
-- 10,000 rows in the demo

Sum clicks by page. The day of each click is cut from the timestamp, then rows group by day and page:

SELECT DATE(click_time) AS day, page, COUNT(*) AS total_clicks
FROM page_clicks
GROUP BY DATE(click_time), page;

In the demo that returns three rows, roughly 2500 for the first site, 4000 plus for the second, and 2400 plus for the third. Save it as a snapshot:

CREATE MATERIALIZED VIEW mv_page_clicks AS
SELECT DATE(click_time) AS day, page, COUNT(*) AS total_clicks
FROM page_clicks
GROUP BY DATE(click_time), page
WITH DATA;

Read and refresh:

SELECT * FROM mv_page_clicks;
REFRESH MATERIALIZED VIEW mv_page_clicks;

Sense-check: the three snapshot rows add up to about 10,000 clicks. A large gap means the load step misfired.

As days pile up, a full-history refresh locks more work and takes longer. The fix is a daily slice that keeps only today. The filter keeps clicks from the start of today up to but not including tomorrow:

SELECT DATE(click_time) AS day, page, COUNT(*) AS cnt
FROM page_clicks
WHERE click_time >= DATE(NOW())
AND click_time < DATE(NOW() + INTERVAL '1 day')
GROUP BY DATE(click_time), page;

Save that as a daily snapshot:

CREATE MATERIALIZED VIEW mv_page_clicks_daily AS
SELECT DATE(click_time) AS day, page, COUNT(*) AS cnt
FROM page_clicks
WHERE click_time >= DATE(NOW())
AND click_time < DATE(NOW() + INTERVAL '1 day')
GROUP BY DATE(click_time), page
WITH DATA;

A plain refresh works, but a concurrent refresh is the goal on a live site so reads keep flowing. The first concurrent try stops with a cannot-refresh-concurrently message that asks for a unique index with no where clause. The fix is to add one on the natural key, here day plus page:

CREATE UNIQUE INDEX id_mv_page_clicks_daily_day_page
ON mv_page_clicks_daily (day, page);

Then:

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_page_clicks_daily;
-- now succeeds

The live habit is: build the daily snapshot once, add the unique index at once, then set a cron beat to refresh concurrently each day. Readers can keep hitting the raw table or the snapshot while the rebuild runs.

Click, stock, index, currency, and commodity boards show this shape in real life. They often run a cron beat that pulls from a master table into small daily snapshots for fast trend reads.

23.11.2 Listing snapshots and finding missing indexes

The visual tool shows snapshots under the database, then schemas, then public, then materialized views. For scripts, functions, or triggers, a catalog read gives the same list. The pattern reads the system class table and keeps rows whose kind marks a materialized view, sorted by name:

SELECT relname
FROM pg_class
WHERE relkind = 'm'
ORDER BY 1;

The catalog table pg_class marks each object by kind. The mark m means materialized view. The flag relispopulated tells whether rows are loaded yet. Together they give a full snapshot health check from plain SQL.

In the demo that lists the built snapshots such as directors and page-click sets. Any extra sort or filter can wrap the same core.

A second catalog pattern finds snapshots that still lack a unique index and so cannot use the concurrent refresh. It joins the class, index, and target tables, keeps materialized kinds, and excludes those with a valid unique link. In the demo it returns four names, including the page-clicks snapshot, the directors snapshot, and the no-data directors snapshot. Opening each in the visual tool and checking its index tab confirms the gap: no index entry exists. On a large estate with hundreds of snapshots, many built by scripts on demand, this check is the fast way to catch which ones still need their unique key before the next concurrent beat.

Pitfall: a snapshot without a unique index still works, but only with locking refreshes. The gap stays silent until traffic peaks and readers start waiting. Run the missing-index scan before launch, not after complaints.

Platform teams show the fix in real life. They run the missing-index check on a schedule, so newly scripted snapshots get their unique keys before traffic needs concurrent refreshes.

23.11.3 Student Questions and Answers

Q: My concurrent refresh asks for a unique index. What should I index?

A: Index the natural key of the snapshot rows. For the daily click snapshot that is day plus page. Build the unique index on those columns, then the concurrent refresh runs.

Q: How do I list snapshots inside a script instead of clicking the tree?

A: Read the system class table and keep the materialized kind, ordered by name. That returns every snapshot in the database for use in functions, checks, or triggers.

Build the snapshot, key it on its natural grain, refresh it concurrently on a beat, and scan the catalog for missing keys. That loop keeps trend boards fast and open.

Exam Guidance Summary

Exam note: plain view core: stores query text, stores no rows, reads live each time. Say it in one line and give the shortcut image.

Exam note: naming and shape: use a v_ prefix to spot views fast, list join columns by name, and never let the same column name appear twice in a view select. The director_id and movie_id duplicate errors are the classic test traps.

Exam note: rename, drop, and rights: ALTER VIEW ... RENAME TO ... and DROP VIEW ... need ownership, drops in the editor run with no confirm, and non-owners get a must-be-owner stop. Prefer the prompted visual delete for live work and IF EXISTS in scripts.

Exam note: filters and builds: single-table filters, join filters, UNION ALL with a source label column, and three-table joins all follow the same test-select-then-wrap flow. Outer filters stack with stored filters and need no aliases.

Exam note: shape changes: new columns can be added at the end with OR REPLACE, but column order cannot be changed in place, and plain CREATE will not overwrite. Reorders and removals need a name-swap rebuild or drop plus rebuild.

Exam note: live proof: insert then delete a test row in the base and read the plain view after each step to show it mirrors at once. Base and view counts move together with no refresh call.

Exam note: updatable rules: one FROM, no distinct, group, having, limit, offset, union, intersect, or except at the top, no window, set-returning, or aggregate functions in the select list, writes are insert, update, delete with where filters, and view rights are enough with no base-table rights needed.

Exam note: check guards: plain sliced views leak out-of-view writes into the base, WITH CHECK OPTION blocks them, LOCAL checks only the top view, and CASCADED checks the whole chain. Manchester, Los Angeles, Boston, and Clearwater are the four demo probes to remember.

Exam note: snapshots: built with CREATE MATERIALIZED VIEW ... WITH DATA or WITH NO DATA, read like tables, filled or refilled with REFRESH, dropped with DROP MATERIALIZED VIEW, never accept direct writes, and need a unique index for CONCURRENTLY.

Exam note: daily slice and catalog: cut heavy snapshots to a daily filter, add the unique key on day plus page, refresh on a cron beat, list snapshots from the class table with kind m, check the populated flag before reads, and scan for missing unique keys.

Key Industry Applications

Team-scoped staff views that hide salary while sharing names and dates keep developers moving without exposing pay. Payroll keeps the base table private and grants each team only its sliced view.

Report builders save long join and subquery logic once as views, then let each report filter the short name instead of copying long SQL. A join fix lands in one view and reaches every report at once.

Labeled UNION ALL views that merge actors and directors with a source tag feed people-search boxes from one short name. The people_type label keeps each row source clear after the stack.

Three-table revenue views that join movies, directors, and revenues serve one-row-per-film feeds to apps with no join code in the app. The app sends a short select and the database owns the keys.

Narrow updatable views let support staff fix names through safe columns with no direct rights on full tables. Agents get write rights on the view only, so pay and key fields stay out of reach.

CHECK OPTION guards keep sliced country or city views clean by rejecting rows that would vanish from the same view. The US-only view takes US rows and stops UK rows at the door.

Nested LOCAL and CASCADED guards let multi-layer city views enforce only the top slice or the whole stack as the business need asks. Local fits single-slice gates while cascaded fits stacked business rules.

Materialized snapshots cache heavy joins and sums for fast page loads, with a stated delay such as refreshed every two hours. Readers see speed plus a clear freshness note.

Daily click snapshots with unique keys on day plus page, refreshed concurrently from a cron beat, drive trend boards for sites, stocks, indexes, currencies, and commodities while raw tables stay open for writes. The catalog scan for missing keys keeps new snapshots ready before traffic peaks.
