SQL

Exploring Stored Procedures

Published: 2026-09-23
Level: postgraduate
Audience: Postgraduate students in SQL and Database Systems

This lecture explores stored procedures in relational database systems, examining their execution model, transaction control, return behavior using INOUT parameters, and safe administration habits.

34.1 Functions Compared With Stored Procedures

A user-defined function — a routine built with CREATE FUNCTION or CREATE OR REPLACE FUNCTION — and a stored procedure — a routine built with CREATE OR REPLACE PROCEDURE — look alike at first glance. Both hold named blocks of database code. Both accept parameters. Both live on the server. The differences that count show up in three places: transaction control, return behaviour, and the way each one is called.

Hook: Why do databases need two kinds of routines that look almost the same? Because one is built to answer questions inside queries, and the other is built to change data safely as one sealed unit.

Think of a function as a calculator taped to a conveyor belt. Each row passes by, the calculator reads it, and it drops an answer back onto the belt. Think of a procedure as a work crew that steps onto the floor, locks the doors, moves several heavy boxes, and then unlocks the doors only when all boxes sit in the right place. The calculator must never lock the doors. The crew must never try to ride the belt. That split explains almost every rule below. Where the work-crew picture breaks: a crew can still hand back a short receipt at the end, and a procedure does that with an INOUT receipt slip rather than a RETURN value.

34.1.1 The Transaction Divide

The single biggest difference is transaction control. Inside a function, starting a transaction is not allowed. A BEGIN block inside a function body is only a grouping block for statements. It is not a transaction boundary. Writing something like START TRANSACTION or COMMIT in there is rejected. That rule shapes every design choice that follows.

A stored procedure supports transactions. BEGIN inside a procedure opens a real transaction, and COMMIT closes it. When the whole run succeeds, the work commits as one unit. When something fails partway, nothing commits. That guarantee is the main reason teams reach for procedures over functions. Money movement, stock changes, and any multi-step write that must succeed or fail together belong in a procedure for exactly this reason.

Formalize — transaction control: a transaction (a group of writes that must all succeed or all roll back) can only live in a procedure in PostgreSQL-style systems. In a function, BEGIN means "group these lines". In a procedure, BEGIN means "start a protected unit" and COMMIT means "seal it for good". The same keywords change meaning with the routine type, so read them in context.

Picture the risk as a timeline. Without a transaction, session A subtracts 100 from Adam at time T1, session B reads the tables at time T2 and sees a world where 100 has vanished, then session A adds 100 to Linda at time T3. The horizontal axis is time, the vertical axis is total money seen by an outsider. Without a seal, the line dips down between T1 and T3. With BEGIN plus COMMIT, outsiders wait outside the locked room and only ever see the flat line at 200. The takeaway: the seal removes the dip.

Scope: use a procedure with an explicit transaction when two or more writes must stay in step under parallel use — transfers, stock moves, ledger postings. Assumption: the database runs with parallel sessions that can read while you write. If only one session ever touches the tables, bare updates look correct in a test but still teach the wrong habit for live use.

Across databases, the core split stays the same and only details shift. In PostgreSQL, functions cannot run transaction commands at all, while procedures can. In Snowflake, the same idea holds with tighter house rules: a procedure called inside an outer transaction can add work to that transaction but cannot end it with COMMIT or ROLLBACK, and a transaction started inside a procedure must be closed inside that same procedure. In MySQL, the same pattern holds — functions return a value and suit reads inside queries, while procedures are invoked with CALL and suit grouped writes. Keep the PostgreSQL form for this lecture and treat the Snowflake transaction house rules as an extra guardrail when you move systems.

34.1.2 Return Behaviour and the Bare RETURN

By default a stored procedure returns no value. The word RETURN followed by an expression or value is not allowed in a procedure body. Writing RETURN 5 or RETURN total_count is rejected. Functions return values. Procedures do not.

One narrow use of RETURN still exists. A bare RETURN with no expression stops the procedure at once. Control leaves the body right there, and later statements do not run. Think of it as an early exit door rather than a way to send data back. A later segment shows the one supported way to get a value out: an INOUT parameter that carries data back to the caller.

A common mix-up is to treat bare RETURN as "return nothing on purpose" versus "send back an empty result". It is neither. It is a stop sign. Code after it never runs. When you need an answer back — a count, a flag, a total — do not reach for RETURN at all. Add an INOUT parameter and fill it with SELECT ... INTO, as shown in 34.4.

The cross-database extra matters here. In PostgreSQL-style procedures for this lecture, no RETURN value is allowed. In Snowflake, every procedure must declare what it returns — a number, a string, an OBJECT document, or even a full TABLE result set built from a RESULTSET variable. The Snowflake habit of ending with a RETURN of a success string or a row count has no direct match in the lecture form. So hold two pictures: lecture form means no RETURN value, INOUT carries answers out; Snowflake form means a declared RETURNS type plus an explicit RETURN, including table-shaped answers.

34.1.3 How Each One Is Called

Functions slot into SELECT statements. A function call can sit in a select list or a FROM clause next to window tools such as lag, and it runs row by row as the query reads data. Stored procedures never work that way. CALL my_procedure can not appear inside a SELECT list. The only way to run a procedure is on its own as a statement.

Two calling forms exist. The common one is implicit execution: CALL followed by the procedure name plus any arguments, such as CALL pr_money_transfer(1, 2, 100). The other is explicit execution: an EXECUTE command naming the procedure with its options. Both run the same compiled body. The point to hold onto is simple: functions are called from queries, while procedures are called as standalone statements, as often as needed.

Worked call contrast: to run the lecture transfer, write CALL pr_money_transfer(1, 2, 100); as its own statement — sender rec_id 1, receiver rec_id 2, amount 100. Try to place that CALL inside SELECT CALL pr_money_transfer(1, 2, 100); and it fails, because procedures cannot ride inside queries. By contrast, a function such as SELECT my_func(balance) FROM t_accounts; is legal and runs once per row. Sense-check: if the call sits inside SELECT, it must be a function; if it starts with CALL on its own line, it is a procedure.

In Snowflake the same ban holds: a stored procedure cannot be called from inside a SELECT, while a user-defined function can. Snowflake adds one useful twist for capturing answers: CALL get_avg_balance(12000, 30); shows the answer directly, and CALL ins_country_monthly_sales(:name, :year) INTO :doc; pours the returned document into a variable inside a script. Keep the lecture CALL form as the base and treat the INTO capture as the Snowflake extra for scripts.

34.1.4 Speed, Parameters, Declarations, and Shape

Procedures are compiled units stored on the server. The source is compiled once at creation time, and every later CALL runs that compiled form. Functions recompile at run time on each call. That repeated compile step costs time. For hot paths that run hundreds or thousands of times, the compiled procedure tends to run much faster.

A procedure may or may not take parameters. Supply sender, receiver, and amount, or supply nothing at all and just run the bare name. A procedure with no arguments is called a static stored procedure — fixed work with fixed inputs. A procedure that takes parameter values is called a dynamic stored procedure — the same body behaves differently for different inputs. The static-versus-dynamic split is only about arguments, not about speed or storage.

The declaration section is also optional. When the body needs local variables, they go in a DECLARE block above BEGIN, exactly as in functions. When no locals are needed, the DECLARE block is left out entirely and nothing breaks.

The standard shape of a procedure follows the function shape with small swaps:

CREATE OR REPLACE PROCEDURE pr_example(sender INT, receiver INT)
AS \$\$
DECLARE
  -- local variables go here when needed
BEGIN
  -- procedure statements go here
END;
\$\$
LANGUAGE plpgsql;

Read it line by line. CREATE OR REPLACE PROCEDURE names the routine and lists its parameters. AS followed by a pair of dollar-quote markers opens the body string. LANGUAGE plpgsql picks the procedural language. DECLARE holds locals when they exist. BEGIN and END wrap the statements that do the work. The beauty of this layout is how little new syntax it asks for: anyone who has written a function already knows nearly every line.

Parameter modes differ by system, and that is worth naming once. The lecture uses plain INT and DECIMAL inputs plus INOUT for answers back. MySQL spells the mode in front of each name — IN for values going in, OUT for values coming out, INOUT for both — such as IN p_sender INT. Snowflake leans on bind variables with a colon prefix inside SQL text, such as WHERE region_name = :p_region_name, and tracks changed rows with SQLROWCOUNT. Keep the lecture header as written and read the colon prefix and SQLROWCOUNT as Snowflake-only extras.

Pitfalls: (1) writing COMMIT inside a function and wondering why it is rejected — BEGIN there is only grouping; (2) writing RETURN total_count; inside a procedure — use an INOUT parameter plus SELECT ... INTO instead; (3) placing CALL inside a SELECT list — CALL must stand alone; (4) mixing up static versus dynamic — no arguments means fixed work, not faster storage.

Recap and bridge: functions answer per-row questions inside SELECT and cannot seal transactions, while procedures run as standalone CALL units that can seal grouped writes — and the money-transfer build next puts that seal to work.

Procedures earn their keep wherever many callers share one write path: payment services that move funds, order pipelines that post ledger rows, admin tools that run nightly reconciliations. The shared sealed path keeps every caller on the same code, which is the theme 34.3 expands.

34.2 A Money-Transfer Procedure With a Transaction

Moving money between two accounts is the classic case for a transaction. Take 100 from Adam, add 100 to Linda, and make sure no other session can ever see a middle state where the money has left Adam but not yet reached Linda. This segment builds that transfer as a stored procedure, from empty table to verified balances.

Hook: What stops a second app from reading your transfer halfway through, when the money is neither here nor there? A sealed transaction that hides the middle state.

Think of the transfer as swapping a 100-unit weight between two pans of a balance scale. Lift from the left pan and the scale tips; set onto the right pan and it levels again at the same total. An outsider must only ever see the level scale, never the tipped middle. BEGIN locks the viewing room, the two UPDATE steps move the weight, COMMIT reopens the room with the scale level.

34.2.1 The Sample Accounts Table

Work happens in the Northwind database. Northwind is a long-used sample database for learning queries, and a small accounts table keeps the transfer logic easy to watch. The table is called t_accounts and holds three columns. A serial primary key — an auto-numbered integer that uniquely tags each row — called rec_id tags each account. A varchar — variable-length text — called name holds the holder name and rejects missing values. A decimal — an exact fixed-point number for money — called balance stores dollars with two places after the point and also rejects missing values.

CREATE TABLE t_accounts (
  rec_id  SERIAL PRIMARY KEY,
  name    VARCHAR NOT NULL,
  balance DECIMAL(15, 2) NOT NULL
);

Here DECIMAL(15, 2) means up to 15 digits in total with 2 after the point. Money needs that exactness: floating-point types round, while decimal types do not. After creation, a schema refresh shows the new table with all three columns in place.

Two rows seed the test. Adam opens with 100. Linda opens with 100.

INSERT INTO t_accounts (name, balance) VALUES ('Adam', 100.00);
INSERT INTO t_accounts (name, balance) VALUES ('Linda', 100.00);

A quick SELECT confirms the start state:

rec_id name balance
1 Adam 100.00
2 Linda 100.00

Small numbers are picked on purpose. With both balances at 100, a transfer of 100 leaves Adam at zero and Linda at double, so every wrong step shows up at once. Joint total at seed time is \(100 + 100 = 200\), the baseline every later check compares against.

Worked setup — t_accounts creation and seeding: run the CREATE TABLE once, refresh the schema tree, then run the two INSERT rows. Confirm with SELECT rec_id, name, balance FROM t_accounts ORDER BY rec_id; which must show two rows: (1, Adam, 100.00) and (2, Linda, 100.00). Joint total is \(100 + 100 = 200\). Sense-check: if you see only one row or a total other than 200, a seed INSERT did not run.

Across databases the table shape is the same idea with small type-name shifts. PostgreSQL here uses SERIAL plus DECIMAL(15, 2). Snowflake sample tables use NUMBER plus VARCHAR with lengths in brackets. MySQL uses INT AUTO_INCREMENT plus DECIMAL(15, 2). Keep the lecture DDL as written; when you move systems, swap only the auto-number keyword and keep NOT NULL plus the exact decimal for money.

34.2.2 Header and Parameters

The procedure is named pr_money_transfer, with pr marking it as a procedure. Three input parameters arrive with each call. The sender — the rec_id of the account losing money — is an INT. The receiver — the rec_id of the account gaining money — is an INT. The amount — how much money moves — is a decimal value. Integer IDs are used because rec_id is a serial key. A decimal amount is used because money needs exact places after the point.

CREATE OR REPLACE PROCEDURE pr_money_transfer(
  sender INT,
  receiver INT,
  amount DECIMAL
)
AS \$\$
BEGIN
  -- transfer statements go here, wrapped as one transaction
END;
\$\$
LANGUAGE plpgsql;

Header map: sender INT is the debit key, receiver INT is the credit key, amount DECIMAL is the money size in the same units as balance. Dollar-quote markers AS \$\$ ... \$\$ wrap the body as a string so inner semicolons do not end the CREATE early. LANGUAGE plpgsql picks the procedural language used through this lecture.

Snowflake procedures add two header extras worth knowing but not mixing into this build: a RETURNS clause that names what comes back (for example RETURNS OBJECT for a document of row counts, or RETURNS TABLE with column names for a result set) and overloaded copies of the same name with different parameter types, such as one copy taking a region name and a second copy taking a region key. MySQL headers spell IN, OUT, or INOUT before each name. The lecture header stays as written; treat RETURNS, overloading, and explicit IN/OUT tags as system extras.

34.2.3 The Two Updates

The transfer needs two writes. First take money from the sender, then give the same money to the receiver. The spoken form of the first write is "balance minus amount, for the sender row". Written as LaTeX, where \(balance_{sender,old}\) is the sender balance before the write in DECIMAL(15, 2), \(amount\) is the transfer size in the same money units, and \(balance_{sender,new}\) is the sender balance after the write:

\[balance_{sender,new} = balance_{sender,old} - amount\]

The SQL matches the math line for line:

UPDATE t_accounts
SET balance = balance - amount
WHERE rec_id = sender;

SET balance = balance - amount reads the current balance, subtracts the transfer size, and stores the result. WHERE rec_id = sender pins the write to exactly one row. Without that filter, every account in the table would lose money, so the filter carries real weight.

The spoken form of the second write is "balance plus amount, for the receiver row". While building it, the first attempt reused a minus sign — "balance minus amount plus amount" — and was at once corrected to a plain plus, because money arriving at the receiver must grow the balance, not shrink it. That slip-and-fix is worth keeping: the two writes must use opposite signs, or money silently appears or vanishes. The corrected LaTeX, where \(balance_{receiver,old}\) is the receiver balance before the write and \(balance_{receiver,new}\) is the balance after:

\[balance_{receiver,new} = balance_{receiver,old} + amount\]

UPDATE t_accounts
SET balance = balance + amount
WHERE rec_id = receiver;

A useful check ties both writes together. Money only moves here. Nothing is created and nothing is destroyed. So the combined total stays fixed. With \(T\) as the joint total in money units:

\[T = balance_{sender} + balance_{receiver} = \text{constant}\]

Before the transfer, \(T = 100 + 100 = 200\). After a correct transfer, the two balances must still add to 200. Any other total proves a sign error or a missing write.

Run the numbers twice to lock the pattern. Correct run with amount 100: sender \(100 - 100 = 0\), receiver \(100 + 100 = 200\), total \(0 + 200 = 200\). Broken run if both lines used minus: sender \(100 - 100 = 0\), receiver \(100 - 100 = 0\), total \(0 + 0 = 0\) — 100 units vanished, which flags the sign slip at once. Broken run with missing WHERE: every row loses 100, so totals collapse across the whole table. The invariant catches all three failure shapes.

34.2.4 Why the Transaction Wrapper Matters

Two bare UPDATE statements already move money, and a single test run looks fine. The trouble starts when the procedure runs in a live system. Picture a second application, or even a second query window, touching the same rows while this transfer is halfway done. It can read Adam after the subtraction but before Linda gains the money. It can write a balance that this transfer then overwrites. The end picture drifts from the true picture: balances that add to the wrong total, or two sessions each believing they saw the latest value.

The fix is to wrap both writes in one transaction. The spoken rule is "BEGIN opens it, COMMIT seals it". BEGIN takes effect first and locks the touched rows under this procedure, so other sessions wait instead of barging in. Both UPDATE statements then run under full control of this procedure. Only when everything succeeds does COMMIT write the result for good. Either both balances change or neither does. There is no middle state that anyone else can see.

BEGIN
  UPDATE t_accounts
  SET balance = balance - amount
  WHERE rec_id = sender;

  UPDATE t_accounts
  SET balance = balance + amount
  WHERE rec_id = receiver;
COMMIT;

That BEGIN-plus-COMMIT pair is the heart of the whole segment. Data integrity — the promise that stored data always tells a true story — rests on it. A separate in-depth treatment of transactions exists for locking modes and failure paths, and it is worth reading next. The one-line version here is enough to build on: wrap grouped writes, then commit once.

Scope: the BEGIN-plus-COMMIT seal covers grouped writes that must move together. Assumption: either all steps succeed or the unit rolls back. Bare updates without the seal pass a solo test yet fail under parallel sessions through dirty reads and lost writes. Snowflake adds the house rule that an inner transaction must close in the same procedure that opened it, often paired with an EXCEPTION block that runs ROLLBACK and re-raises the error — a useful production extra around the same seal.

34.2.5 Calling the Procedure and Reading the Result

The procedure runs through CALL, never through SELECT:

CALL pr_money_transfer(1, 2, 100);

The three arguments read left to right: sender rec_id 1 (Adam), receiver rec_id 2 (Linda), amount 100. Then a plain read shows the effect:

SELECT * FROM t_accounts;
rec_id name balance
1 Adam 0.00
2 Linda 200.00

Adam gave 100: \(100 - 100 = 0\). Linda gained 100: \(100 + 100 = 200\). Joint total: \(0 + 200 = 200\), matching the starting 200, so the invariant check passes. The whole run behaved as one sealed unit, and that sealed-unit behaviour is exactly what procedures are for.

Worked transfer — CALL and verify: start from Adam 100.00 and Linda 100.00. Run CALL pr_money_transfer(1, 2, 100);. Then run SELECT rec_id, name, balance FROM t_accounts ORDER BY rec_id;. You must see Adam 0.00 and Linda 200.00. Check the math: sender \(100 - 100 = 0\), receiver \(100 + 100 = 200\), joint \(0 + 200 = 200\). Sense-check: total still 200, so money moved without appearing or vanishing. Any other total means a sign slip or a missing WHERE filter.

Pitfalls: (1) dropping the WHERE filter and updating every row; (2) copying the minus sign onto the receiver line — the receiver must use plus; (3) testing solo without the seal and shipping that form to a live system with parallel readers; (4) reading the seed table in 34.2.1 as Adam 100 and Linda 200 — Linda starts at 100, and 200 is the after-state.

Recap and bridge: two opposite-sign UPDATE writes move the money, BEGIN plus COMMIT seals them into one unit, and the joint-total check proves the move — and the same seal idea explains why teams trust procedures, which is the topic of the next section.

Bank ledgers, payment rails, and stock systems all reuse this sealed-move shape: debit one row, credit a second row, hide the middle, verify the total. Snowflake teams wrap the same pair with transaction plus EXCEPTION rollback and return a small OBJECT document of rows deleted and inserted; the lecture form keeps the seal lean with BEGIN plus COMMIT.

34.3 Why Stored Procedures Are Used

Seven reasons come up again and again. Each one answers a different pain: repeated logic drifting apart, painful schema changes, slow hot paths, open data access, half-done writes, copied queries, and hostile input. Together they explain why teams move shared write logic into procedures.

Hook: What happens when five apps each keep their own copy of the same five-step money move — and tax rules change next month? Procedures answer by keeping one shared copy that every caller reuses.

Think of shared logic as a kitchen recipe card pinned to the wall. Without the card, five cooks each guess the order of spices and every plate tastes different. With the card, every plate tastes the same even when the head cook rewrites one line. The procedure is that card. Where the picture breaks: a recipe card never locks the kitchen doors, while a procedure also seals its steps inside a transaction.

34.3.1 One Shared Copy of the Logic

First, procedures keep data consistent by storing a series of steps once instead of rebuilding them in every script. When every database administrator, developer, and application calls the same procedure, the same code runs every time. No copy drifts. No one forgets a step. The rule for changing data lives in one place, and every caller inherits it.

Second, procedures simplify complex work by packing it into a single easy unit. A five-step reconciliation becomes one CALL with a few arguments. Callers do not need to know the order of the steps or the names of the staging columns. They call the unit and trust the order inside.

Think of it like a kitchen recipe card. Without the card, five cooks each guess the order of spices. With the card pinned to the wall, every plate tastes the same. The procedure is that card.

A second everyday picture helps for the packing idea: a TV remote. Viewers press one power button instead of rewiring the set each time. The CALL is the button, the procedure body is the wiring hidden inside. Learners who hold both pictures — recipe card for sameness, remote for hidden steps — rarely mix up consistency with simplicity again.

Worked sharing case: three tools need the same month-end reconciliation — an admin script, a developer API, and a reporting job. Without a procedure, each tool pastes its own five-step SQL and one tool soon skips step 4. With CALL pr_month_close(2024, 12);, all three run the same five steps in the same order. Change the rule once inside the procedure and all three callers pick it up with no edits at their call sites. Sense-check: one edit point, many safe callers — that is the sharing win.

34.3.2 Easier Change Management and Security

Third, and this one is large, procedures simplify change management. Columns get renamed. Business rules shift. Tax logic updates. Without procedures, every script, report, and application that touches the changed table needs its own edit. With procedures, only the procedure body changes. Every caller keeps working untouched. For that reason procedures are the best seat for database-level change handling: one edit point, many safe callers.

Fourth, procedures tighten security by sitting between callers and raw tables. Grant callers the right to run the procedure while withholding direct write rights on the tables underneath. Fewer hands touch raw rows, so the chance of corrupt data and breached access drops. The procedure checks the inputs, applies the rules, and writes in the approved shape. Direct table access can not promise any of that.

Picture change management as rewiring behind a wall socket. Users keep plugging into the same socket shape while an electrician swaps the wires behind it. The CALL signature is the socket face; the body is the wiring. Security adds a locked cabinet around the wiring: callers get a key to the socket, not a key to the cabinet. Snowflake and MySQL teams use the same socket idea — share the procedure, hide the base tables, hand out EXECUTE or CALL rights only.

34.3.3 Speed From Compiled Server Objects

Fifth, procedures put transactions to full use. The accounts transfer in the prior segment showed the pattern: grouped writes sealed by COMMIT so integrity holds even under parallel use. Skipping the transaction leaves users staring at half-updated views with no way to know what is true. Sealing grouped writes is treated here as a correctness duty, not a speed trick.

Sixth, procedures run fast because they are compiled objects stored on the server. Two facts combine. They live on the server, so no source text travels at call time. They compile once at creation, so the parsing and planning work happens a single time. Later calls run the stored compiled form directly. A procedure compiled a month ago runs today with no fresh compile, unless the program text itself changed — in which case one recompile refreshes it, and later calls are fast again. Functions, by contrast, pay compile work at run time on each call. Call something thousands of times and the gap shows.

See the speed gap with numbers. A nightly job that calls a balance routine 10,000 times pays the parse-and-plan cost 10,000 times in function form but about once in procedure form. Even if each parse costs only a few milliseconds, the saved time adds up to minutes per run. That is why hot paths — payment posting, order intake, meter readings — tend to live in procedures.

Scope: the speed win applies to hot paths called many times with the same shape. Assumption: the body stays stable so the compiled form gets reused. A one-off report run once a month gains little from compiling, and a body edited daily pays recompile often. Match the tool to the call rate.

34.3.4 Modularity and Injection Safety With Input Checks

Seventh, procedures bring modularity. When near-identical queries appear in several places, they collapse into one parameterized procedure. Callers type one short CALL instead of pasting long SQL. Shorter call sites mean fewer typos and one maintenance point later. Repeated query text is a standing invitation to write the procedure.

Eighth, procedures cut down hostile-input risk, including SQL injection — smuggled database commands hidden inside input text that trick the database into running them. Because the procedure body is precompiled, input values arrive as data rather than as extra code, which shrinks the attack surface. But parameters alone do not finish the job. The standing rule here is blunt: anything that touches data gets checked again and again. A mistyped value or a crafted input can still slip through a careless procedure. So validate inputs inside the procedure, recheck them, and never assume the caller sent clean data. Injection flaws have bitten large production systems through trusted-looking inputs, so server teams treat input checks as a duty, not a decoration.

Pitfalls: (1) trusting parameters as clean — always validate type, range, and length inside the body; (2) building SQL by gluing input text into a query string — this reopens the injection hole that precompiled bodies close, and Snowflake EXECUTE IMMEDIATE strings need the same care; (3) pasting the same long query in many tools instead of folding it into one CALL; (4) treating the transaction seal as a speed trick — it is a correctness seal first.

Snowflake adds two modularity extras that fit the same idea without changing the lecture base. Overloaded procedures let one name serve two caller habits — for example one copy taking a region name and a second copy taking a region key, with the second copy looking up the name and calling the first copy to avoid duplicate code. Dynamic SQL through EXECUTE IMMEDIATE lets one procedure serve many tables by building a query string for key and name columns found in INFORMATION_SCHEMA. Keep the lecture CALL shape and read overloading plus dynamic SQL as ways to reuse even more.

Recap and bridge: one shared copy keeps callers in step, one edit point eases change, a locked cabinet tightens access, a compiled seal keeps writes true and hot paths fast, and short CALLs plus strict input checks keep code tidy and hostile input out — and the INOUT pattern next shows how such a sealed unit still hands an answer back.

Teams that post payments, feed dashboards from one count routine, or gate writes behind checked procedures all lean on the same set: shared code, sealed writes, fast reuse, checked inputs.

34.4 Returning a Value Through an INOUT Parameter

Procedures return nothing on their own, yet callers often need an answer back: did it work, how many rows changed, what total came out. The supported path is an INOUT parameter — a parameter marked INOUT that travels into the procedure, picks up a value inside, and travels back out to the caller. This segment builds a live case: count every row in the orders table and hand the total back.

Hook: If RETURN with a value is banned, how does a sealed procedure still tell you the order count is 830? It hands you a receipt slip that went in blank and comes back filled.

Think of INOUT as a coat-check ticket. You hand over a ticket marked 0 at the door. Staff hang your coat, write 830 on the ticket stub inside, and hand the same ticket back at pickup. The ticket went in empty and came back full, with no loudspeaker announcement. SELECT ... INTO is the pen that writes the number onto the ticket.

34.4.1 The INOUT Idea

An INOUT parameter starts with a default, often zero, and ends holding the result. The caller passes no query text. The procedure runs its SELECT internally, pours the answer into the INOUT variable with SELECT ... INTO, and the caller reads the variable after CALL returns. No RETURN statement appears anywhere. The INTO assignment does the whole job.

Formalize — INOUT round trip: an INOUT parameter (a header variable that carries a value in and carries the answer out) follows three steps. First, the header sets a start value such as INOUT total_count INT DEFAULT 0. Second, the body fills it with SELECT COUNT(*) INTO total_count FROM orders;. Third, CALL returns and the caller reads total_count. No RETURN keyword appears at any step.

The shape only fits single-row answers. A bare COUNT always yields exactly one row, so SELECT ... INTO has exactly one place to pour. A query that yields many rows needs a different shape — a result-set return in systems that allow it — and cannot pour into one integer. That fit is why the order-count case works with no extra DECLARE block.

Across databases, keep the lecture INOUT as the base and note the extras. MySQL spells the same idea as IN, OUT, or INOUT before each header name, and callers read OUT values through session variables. Snowflake instead declares a RETURNS type and ends with an explicit RETURN — a number, a string such as success text, an OBJECT document with row counts, or a TABLE result set built from a RESULTSET variable and handed back with RETURN TABLE(v_results);. Snowflake scripts also capture a CALL answer with CALL proc(...) INTO :var;. The lecture needs none of that extra machinery; one integer INOUT covers counts, flags, and totals.

34.4.2 Building the Order-Count Procedure

The goal is plain: total number of orders in the orders table. Order counts feed dashboards, capacity plans, and end-of-day reports, so a one-call count that any tool can reuse earns its keep fast.

CREATE OR REPLACE PROCEDURE pr_orders_count(
  INOUT total_count INT DEFAULT 0
)
AS \$\$
BEGIN
  SELECT COUNT(*) INTO total_count FROM orders;
END;
\$\$
LANGUAGE plpgsql;

34.4.3 Calling It and Reading the Answer

SELECT can not run this routine. The call form is:

CALL pr_orders_count();

No argument is supplied because the INOUT parameter defaults to zero. After the call, the procedure hands back total_count holding 830. The caller asked for one number and got one number. That round trip — default in, computed value out, no RETURN keyword — is the only supported way to return data from a procedure, and it covers most real needs: status flags, row counts, computed totals.

Scope: INOUT fits single-value answers — counts, totals, status codes. Assumption: the inner SELECT yields one row. A bare aggregate such as COUNT always qualifies. A multi-row SELECT without an aggregate does not fit one integer and needs a set-returning shape available in other systems, not a plain INOUT integer here.

Q: If procedures can not return values, is there really no way to get an answer back, for example to confirm the run worked? A: There is exactly one supported way in this lecture form: add an INOUT parameter. Give it a name, a type, and a default such as zero. Inside the body, fill it with SELECT ... INTO instead of using RETURN. After CALL, read the parameter. The order-count case shows the full loop: INOUT total_count starts at 0, the count query pours 830 into it, and the caller reads 830 back. Snowflake extras use a declared RETURNS type with an explicit RETURN instead, but the lecture path stays INOUT-only.

Pitfalls: (1) writing RETURN total_count; — rejected in this form, use SELECT ... INTO; (2) trying SELECT pr_orders_count(); — CALL must stand alone; (3) pointing SELECT ... INTO at a multi-row query — the single-row pour fails, so keep aggregates or single-row lookups for INOUT; (4) mismatching the integer type between the header and the count — restate INT and rebuild when the build complains.

Recap and bridge: a ticket marked 0 goes in, SELECT ... INTO writes 830 on it, CALL hands it back — and with answers covered, only safe removal is left, which is the DROP step next.

Hold that ticket picture for the exam: default in, single-row pour inside, read back after CALL, no RETURN keyword anywhere.

34.5 Dropping a Procedure Safely

Removing a procedure takes one statement, and that shortness is exactly why it deserves care. A dropped procedure is gone at once, and with the wrong option its dependents go with it.

Hook: Why does a one-line DROP deserve slow, deliberate attention? Because one careless word can pull views, triggers, and routines down with it.

Think of DROP as pulling a load-bearing card from a card tower. Pull one free-standing card and nothing moves. Pull a card that other cards lean on with CASCADE and whole levels fall. The safe habit is to walk around the tower first, move each leaning card by hand, and only then lift the target card.

34.5.1 Syntax and Overloads

The base form mirrors other DROP statements:

DROP PROCEDURE procedure_name;

Three add-ons tune it. IF EXISTS skips the error when the name is missing, so repeat runs stay quiet. An argument list picks one overload when several procedures share a name with different parameters — DROP PROCEDURE pr_calc(INT) removes only the integer variant and leaves the rest standing. RESTRICT blocks the drop when other objects depend on the procedure, and it is the default. CASCADE does the opposite: it removes the procedure plus every dependent object beneath it in one sweep.

Overload map: an overload (two routines sharing one name with different parameter types) needs a signature to drop safely. DROP PROCEDURE pr_calc(INT); names both the routine and its type list, so only the integer copy falls. Without the type list, the database cannot tell which copy you mean. Snowflake procedures use this overload habit often — for example a sales loader with a name-based copy and a key-based copy — so the signature form is the portable habit to keep.

Across databases the base stays put. PostgreSQL uses DROP PROCEDURE name; with IF EXISTS, signature, RESTRICT, and CASCADE exactly as above. Snowflake uses the same DROP shape for its procedures. MySQL uses DROP PROCEDURE IF EXISTS name; in the same spirit. Keep the lecture line as written and read IF EXISTS as the repeat-safe extra every system shares.

34.5.2 The CASCADE Warning

CASCADE deserves a frank warning. It is quick, and it is dangerous. Dependent views, triggers, or routines vanish without a second prompt, and rebuilding them from memory after the fact is painful. The working rule stated here is firm: never CASCADE a drop and hope for the best. Walk to each child object, remove or repoint it by hand, confirm nothing important is lost, and only then drop the procedure itself. Anything starting with the word DROP gets slow, deliberate attention.

Picture the blast radius as concentric rings. The center is the procedure name. The first ring holds direct dependents — a dashboard view, a trigger, a second routine that calls this one. The second ring holds dependents of those dependents. RESTRICT stops at the first ring and refuses the drop, which is safe. CASCADE burns through every ring in one sweep with no prompt, which is why production teams treat it as a last resort after manual cleanup.

Scope: RESTRICT is the default guard and the right choice when you are unsure what leans on the procedure. Assumption: dependency metadata is complete, so the block triggers when children exist. CASCADE fits only a throwaway sandbox where every dependent may fall, never a shared production schema.

34.5.3 Worked Drop of the Order-Count Procedure

All procedures sit under the schema tree beneath the Procedures node, where both the transfer routine and pr_orders_count are listed. Removing the order-count routine takes one statement:

DROP PROCEDURE pr_orders_count;

A refresh of the Procedures node confirms the entry is gone. No CASCADE, no argument list needed here — one name, one routine, one quiet removal. The transfer procedure stays listed and keeps working. Short task, done with eyes open.

Worked drop — pr_orders_count removal: open the schema tree to the Procedures node and confirm both pr_money_transfer and pr_orders_count are listed. Run DROP PROCEDURE pr_orders_count; as its own statement. Refresh the Procedures node and confirm pr_orders_count is gone while pr_money_transfer still stands. For a repeat-safe script form, use DROP PROCEDURE IF EXISTS pr_orders_count;. Sense-check: one name gone, dependents untouched, sibling routine still callable.

Pitfalls: (1) reaching for CASCADE by habit and losing views and triggers silently; (2) dropping without a signature when overloads share a name — name the type list; (3) skipping the refresh check and assuming the drop worked; (4) dropping the shared transfer routine when only the count routine was meant to fall — read the name twice before running.

Recap and bridge: name the exact routine, prefer IF EXISTS for scripts and RESTRICT for safety, clear children by hand, and verify in the Procedures node — and with removal covered, the lecture closes with review lists for exams and production.

Safe DROP habits protect nightly jobs, dashboards, and payment paths that all lean on shared procedures: remove only what you named, keep the sibling routines running, and leave dependents standing.

Key Industry Applications

Bank-style money transfer between named accounts shows why grouped writes must commit as one unit, the same pattern behind payment and ledger systems. A reusable order-count procedure feeds dashboards and daily reports from one shared routine instead of pasted SQL in every tool. Shared procedures give every administrator, developer, and application the same code path, which is how teams keep production data consistent. Compiling once on the server keeps hot paths fast under heavy call volume. Precompiled bodies plus strict input checks shrink SQL injection risk in systems that accept outside input.

Warehouse teams reuse the same sealed pattern at larger scale: delete the stale slice for one region and year, insert the fresh aggregate rows, commit once, and hand back a small document of rows deleted and inserted. Overloaded copies let callers pass either a region name or a region key while sharing one core body. Result-set procedures feed downstream queries through table functions or result scans, and dynamic SQL extends one routine across many key-and-name tables. The lecture transfer and count are the lean base forms; these scaled uses show where the same ideas land in production.
