# PostgreSQL Transactions

39.1 What Is a Transaction

A bank moves 500 from savings to checking. The debit lands, then the power dies before the credit. Where is the money? A transaction is the mechanism that makes this question always have a safe answer: either both halves land, or neither does.

39.1.1 A Bundle of Steps That Acts as One Unit

A transaction (a named group of database commands that must succeed or fail together) is the core unit of safe change in PostgreSQL. The short working definition is simple: a transaction is a list of PostgreSQL commands run against the database to change stored information. A deeper way to say the same thing is that a transaction bundles many steps or operations into a single unit. Those steps are mostly add, edit, and delete operations, with reads such as view mixed in, and the bundle turns them into one thing.

A plain-words picture helps. Think of hiring one van to move apartments in a single trip. The boxes are the statements, the trip is the transaction, and the rule is strict: either every box arrives at the new flat, or the van never leaves the old one. There is no outcome where half the furniture sits on the curb. The picture breaks in one place: a van cannot rewind time, while a database can, through ROLLBACK, return to the exact state it held before the trip began.

A transaction bundles multiple steps or operations into a single all-or-nothing operation. At the end of the run, whatever was intended must get done completely. If any problem appears in the middle, after part of the transaction has already run, the system rolls back to the original state, as if the half-finished work never happened. That definition gets enlarged later when ACID properties enter the picture, but the all-or-nothing spine never changes.

39.1.2 Why Changing Data Is the Moment of Danger

A database is most open to damage while someone is changing it. The risky operations are add, edit, delete, and view. Done correctly, they add information and value. Done incorrectly, or done in a deliberately wrong way, they damage the stored information. That is why change operations count as the most vulnerable events in database work.

A second danger comes from failure in mid-change. When a software failure, a hardware failure, or any surprise failure strikes while a change is still in progress, the database can land in an indeterminate state (a half-written condition stuck somewhere between before and after the change). The leftover information belongs neither to the old state nor to the new one, and the database cannot be trusted until that ambiguity is resolved. Transactions exist to remove exactly this ambiguity: either the whole bundle lands, or the database returns to where it started.

Picture the failure on a number line. Before the change the balance reads 100, after the change it should read 50, and a crash mid-write can leave a value that is neither a true 100 nor a true 50. Every later query built on that half-written value spreads the damage. The takeaway is one line: reads can wait, but writes must be atomic, so every write travels inside a transaction.

39.1.3 The Four Transaction Commands

SQL offers four main transaction commands. The first two carry the all-or-nothing promise. COMMIT (the command that makes the work of a transaction permanent) tells the system that everything just done should be kept. ROLLBACK (the command that reverses a transaction back to its original state) tells PostgreSQL to undo everything done since the transaction began. Accidental damage, such as a DELETE typed during a round of INSERTs, and intentional damage, such as a hostile user reaching stored rows, are both answered with these two commands.

Command Plain meaning When to use it
COMMIT Keep everything in this bundle All statements ran as intended
ROLLBACK Undo everything back to BEGIN Any error, doubt, or attack appears
GRANT Give a privilege on an object to a user or group A new role needs access
REVOKE Take that privilege away Access should end

The other two commands manage access rights. GRANT gives privileges on an object to a user or a group of users, and REVOKE takes those privileges away. Privileges can apply at row level, table level, or column level. Together the four commands guard the database against both accidental and intentional harm.

A note on naming, kept alongside the session's version: the session groups all four as transaction commands, and that grouping is what the exam follows. Standard texts file GRANT and REVOKE under access control rather than transaction control, while BEGIN, COMMIT, and ROLLBACK form the transaction-control core. Both framings agree on behavior: GRANT opens a door, REVOKE closes it, and neither one commits or undoes data.

39.1.4 Closing the Window of Vulnerability

Hardware and software problems are a fact of daily life that nobody can prevent. A cluster can go down, connectivity can drop, a hard drive can fail, a glitch can surface, or a freshly installed PostgreSQL extension can corrupt records or block access to transactions. Each of these leaves the database open to damage, and that is the hard reality every design must accept.

Modern database systems shrink this exposure by closing the window of vulnerability as far as possible. The method is strict: every operation that affects the database runs inside a transaction, and all of those operations are committed together, at once, at the end of the transaction. Statements are gathered into a single bundle, the bundle runs, and then the session either commits the whole bundle at the end or rolls it back to its original state. This single discipline, everything inside a transaction with one joint commit at the end, is how the system keeps a crash from leaving half-written data behind.

Scope: the all-or-nothing promise holds only where the storage layer supports transactions. In PostgreSQL it always does. In MySQL it depends on the engine: InnoDB tables give full transaction support with row-level locking, while MyISAM tables ignore transaction commands, so a ROLLBACK there restores nothing. The session rule "every change inside a transaction" assumes a transactional engine underneath.

39.1.5 Corruption Without Any Failure: Many Users, One Table

Damage does not need a crash. In a single-user setup, and even more in a multi-user setup, corruption and wrong results are possible with no hardware or software failure at all. Picture an application reached by a thousand users, or a hundred thousand: two or more of them will eventually touch the same table, the same row, or the same column value at the same time. That overlap is a factual certainty at scale, and the interaction between simultaneous users of one table can cause serious data problems.

Walk through one overlap. User A reads a balance of 100 and plans to subtract 50. User B reads the same 100 and plans to subtract 30. A writes 50, B writes 70, and one update silently wipes out the other, even though every disk and cable worked perfectly. The fix is the same discipline from a different angle. By restricting changes so they happen only inside transactions, SQL keeps concurrent users from corrupting each other. Every operation still lands in a single transaction, and that single-transaction rule resolves the multi-user hazard. Transactions are an integral and critical part of PostgreSQL, and of every database system: they answer crashes, mistakes, hostile input, and concurrent access with one mechanism.

Two traps catch beginners here. First, treating transactions as crash-only armor and skipping them for "small" edits, while the concurrent-user hazard strikes small edits hardest. Second, treating GRANT and REVOKE as substitutes for transactions: access control decides who may touch a row, but only the transaction decides whether a half-finished touch survives.

Exam note: define a transaction as a bundle of steps forming a single all-or-nothing unit, and name COMMIT as the permanent-write command and ROLLBACK as the restore-original-state command. Rehearse the moving-van picture: boxes are statements, the trip is the transaction, and half-delivered is not an option.

A transaction is a bundle, the bundle is all-or-nothing, and the rule covers crashes, mistakes, hostile input, and concurrent users alike. The next section opens the hood and shows the machinery, the log file, that makes the promise hold.

39.2 How SQL Protects the Database During a Transaction

How does the database "remember" work it decided to forget? It keeps a private diary of every step, then reads that diary backward. That diary is the log file, and it is the whole reason ROLLBACK can be exact.

39.2.1 The Log File: Recording Every Operation

Protection starts with memory of what happened. During a transaction, whether the work is adding a record, editing a record, deleting a record, or even reading one, SQL records every operation performed on the data in a log file. Each action on the data gets a matching entry in that log. This logging is continuous and automatic, and it is the foundation everything else stands on: without a faithful log, there would be no way back.

The log file is the transaction's memory: one entry per operation, written as the work happens, so a later ROLLBACK can replay it in reverse and restore the exact prior state. PostgreSQL implements this diary as its write-ahead log, a durable record consulted during crash recovery before any table is trusted.

Think of an accountant's pencil-first ledger. Nothing reaches the inked final books until every pencil line is checked, and if a page tears mid-entry the accountant erases back to the last inked total. The analogy breaks at one edge: paper cannot record reads usefully, while the session's log conceptually covers reads too, even though only the write entries drive the undo.

39.2.2 The BEGIN, Statements, and COMMIT Block

A transaction block has a fixed shape: it opens with a BEGIN statement, continues with the working statements such as INSERT and UPDATE, and closes with COMMIT. In the normal path there is no crash: the system reads BEGIN, runs the INSERT and the UPDATE, reaches COMMIT, applies the changes at once, and the database is updated.

Track the two paths through one block. Normal path: BEGIN opens, INSERT and UPDATE run, COMMIT arrives, and every change lands at once. Crash path: BEGIN opens, INSERT and UPDATE run, and then a crash lands before COMMIT is reached. The crash can be a software glitch, a hardware glitch, an accidental mistake, an intentional attack, or two users colliding on the same record. Anything that interrupts counts. The system reads that interruption, understands that the transaction did not finish, and refuses to commit. The transaction simply ends without applying anything, and the session then issues ROLLBACK to restore the original state. Nothing half-written survives. Sense-check: a block with no COMMIT must leave the tables exactly as they were, no matter how much work ran inside it.

A cross-database note, kept secondary to the session's PostgreSQL flow: MySQL and SQL Server spell the opener as START TRANSACTION or BEGIN TRANSACTION, Snowflake accepts BEGIN TRANSACTION, and Oracle opens a transaction implicitly with the first statement. Different spellings, same block: open, work, then one joint close.

39.2.3 Rollback Works the Log in Reverse

ROLLBACK knows the way home because of the log file from 39.2.1. Since SQL recorded every operation during the transaction, the rollback process walks that log in reverse, undoing each action in turn: it undoes the INSERT, it undoes the UPDATE, and it undoes whatever else the block contains. Step by step, the reversal returns the database to the state it held before BEGIN.

Picture rewinding a recorded tape. The last action recorded is the first one erased, then the one before it, until the tape sits exactly where BEGIN pressed record. So the protection rule fits in one paragraph. SQL guards the database by insisting on a clean run up to the end of COMMIT: with no interruption, COMMIT writes everything. With a problem anywhere before COMMIT finishes, ROLLBACK returns the system to its original state. COMMIT writes, ROLLBACK restores, and the log file is the map that makes restoration exact.

Scope: the guarantee covers the transaction's own bundle, not work committed earlier. ROLLBACK cannot reach back past BEGIN, and once COMMIT lands, the change is permanent and needs a new compensating transaction to reverse. Beginners also misread "refuses to commit" as automatic cleanup: an interrupted block still needs an explicit ROLLBACK (or crash recovery) to release its locks and state.

Commit writes the whole bundle, rollback replays the log in reverse, and no COMMIT means nothing survives. That diary-then-rewind mechanism is what the ACID properties formalize next.

The log makes undo exact, the block gives undo a shape, and the rewind makes undo complete. The next section names the four properties this machinery must deliver.

39.3 ACID Properties

Chemists pour acid on metal and watch it bubble. Database designers want the opposite: a database with ACID that never bubbles, never foams, and never leaves a half-dissolved row behind. The joke lands because the acronym promises exactly that kind of resistance to corrosion.

39.3.1 The Acronym and the All-or-Nothing Goal

Database designers say they want their database to have ACID. The joke that follows is obligatory: nobody is pouring chemicals into the server or turning stored rows into a bubbly mess. ACID is an acronym, and it names four characteristics a database needs to stay free of corruption. Atomicity is the A, consistency is the C, isolation is the I, and durability is the D. All four must hold at once.

Think of the whole set as all-or-nothing, like zero and one. Either every intended change lands completely, leaving everything good and consistent, or a problem anywhere sends the database back to its original state. That binary outcome is the goal of every database designer and administrator, and the four properties below are how the goal is reached.

ACID names the four properties a corruption-free database must hold at once: atomicity (one indivisible unit), consistency (valid state to valid state), isolation (concurrent transactions kept separate), and durability (the settled state survives what follows).

39.3.2 Atomicity: the Whole Transaction Is One Indivisible Thing

Atomicity (the rule that a transaction counts as one indivisible unit) has nothing to do with atoms in physics. It means the entire transaction is treated as an individual unit. A transaction bundles commands together and the bundle acts as one thing, exactly as 39.1 described.

There are only two legal endings. Either the bundle runs in its entirety, totally and completely, and COMMIT makes it permanent, or a problem appears and ROLLBACK restores the database to its original pre-transaction state. Partial success is not an option: the unit either lands whole or vanishes whole.

Run the classic transfer from the companion texts: move 500 out of account 9988 and into account 9989. Step one debits 9988 only when the balance covers it; step two credits 9989; only when both updates report exactly one row changed does COMMIT fire. Any miss fires ROLLBACK instead, and the 500 never leaves its starting account. Sense-check: after the run, the money is either fully moved or fully where it began, never in between.

39.3.3 Consistency: the Books Must Balance Before and After

Consistency (the rule that the database moves from one valid state to another valid state) does not mean one fixed global rule. Its exact meaning shifts from application to application because it follows the business case. The classic illustration is a bank transfer. Money moves from account one to account two, and the business rule says the combined total across both accounts must be the same at the end of the transaction as at the start. Add funds on one side, subtract on the other, and the two sides stay balanced: the left-hand value equals the right-hand value.

In plain words: whatever the books say together before the move, they must say together after it, or the transaction must not happen. In symbols, write \(T\) for the combined total, \(B_1\) for the balance of the first account, and \(B_2\) for the balance of the second account, all in whole currency units. The spoken rule from the session was "the total of both accounts stays the same at the end", which becomes:

\[ T_{before} = B_1 + B_2 = T_{after} \]

That one line is the whole idea: consistency means a balanced position before the transaction and the same balanced position after it.

Move 500 between two accounts that hold 800 and 200, so \(T_{before} = 800 + 200 = 1000\). Debit the first to 300, credit the second to 700, and \(T_{after} = 300 + 700 = 1000\). The total never moved, only its split did. Sense-check: if the two sides sum to anything other than 1000, consistency failed and the transaction must roll back.

39.3.4 Isolation: Concurrent Transactions Must Not Touch Each Other

Isolation (the rule that each concurrent transaction runs in its own private world) answers the multi-user hazard from 39.1.5. A busy system runs hundreds of transactions in parallel: one user inserts a record, a second user deletes a record, a third user reads a different record. Three separate transactions, all alive at once. In an ACID database these parallel transactions must be totally cut off from one another, each running in its own domain.

Total isolation is achieved by serialization: transactions are ordered so that each one runs as if the others were not there, even while they overlap in time. No parallel transaction leaks into another. A handy mental picture offered in the session is the Unix background process: each daemon runs its own job separately, unconcerned with what its companion daemons are doing. Transactions behave the same way, separate, self-contained, mutually unaware, and serialization is the mechanism that keeps them so.

Practical systems tune how strict that separation is. PostgreSQL defaults to read committed, where each statement sees only committed data, and offers repeatable read and serializable for work that must hold one snapshot, such as online backups with pg_dump. Snowflake pins its engine at read committed: a statement never sees uncommitted changes from another session, though statements inside one transaction do see that transaction's own earlier writes. MySQL's InnoDB adds row-level locking with versioning so readers get a consistent view without blocking writers. The session's core claim stays fixed across all three: one transaction never disturbs another before COMMIT.

39.3.5 Durability: After COMMIT or ROLLBACK, the State Holds

Durability (the promise that the settled state survives what comes next) begins where the transaction ends. After a transaction has committed, or after it has rolled back to its original state, the database must be countable-on: it sits in its proper state and it holds up-to-date data, the latest and greatest version of the truth.

The guarantee reaches past crashes. Even if the system suffers a hard crash, a software outage, or an accidental change after COMMIT but before the data reaches disk, a well-designed durable system still restores the proper state on recovery. During restart the server rolls back every incomplete transaction it finds and replays every committed one from the log, so committed work is never lost and uncommitted work never leaks in. Commit strategy, rollback strategy, and storage design all feed into this, but the outward promise is single: once the transaction settles, by commit or by rollback, the database stays in that settled, current state no matter what failure follows. Atomicity, consistency, and isolation decide the correct outcome; durability makes the outcome stick.

Two confusions recur. First, durability does not mean "written to disk the instant COMMIT returns"; it means the committed state can always be rebuilt on recovery, even from the log. Second, rolling back to the original state is also a settled, durable outcome: durability protects the agreed state, whichever way the transaction settled.

Exam note: expand ACID as atomicity, consistency, isolation, and durability, with one line on each: whole-unit execution, balance preserved before and after, concurrent transactions kept separate by serialization, and the settled state surviving crashes. Anchor each property to its session image: the indivisible bundle, the balanced books, the Unix daemons, the countable-on state.

Atomicity decides the unit, consistency guards the books, isolation guards the neighbors, and durability guards tomorrow. The next section builds the small banking table every later proof will run against.

39.4 Transaction Setup: the Accounts Table

Every later proof needs a stage small enough to check by hand. Three holders, three equal balances, one table: any moved coin shows up at once, and any vanished coin does too.

39.4.1 Creating the Table

All later demonstrations run against one small famous table built for exactly this purpose: an accounts table that mimics a simplified banking application. The build statement creates a table named accounts with three columns. The account_id (the row's unique serial number) is a serial primary key. The name (the holder label written as text) is a varchar that may not be null. The balance (the money held, counted in whole units) is an integer that may not be null, since every later exercise moves this value up and down.

Build the stage with one statement. The spoken description behind it was "create table accounts with account id serial primary key, name varchar not null, and balance integer not null":

\[ CREATE\ TABLE\ accounts\ (account\_id\ SERIAL\ PRIMARY\ KEY,\ name\ VARCHAR\ NOT\ NULL,\ balance\ INTEGER\ NOT\ NULL) \]

After creating it, a refresh of the table list in the browser tool confirms the new table is present. A cross-database footnote for later reference: SERIAL is PostgreSQL's auto-numbering shorthand, MySQL spells the same idea as AUTO_INCREMENT, and Snowflake and Databricks use AUTOINCREMENT or identity columns. Same role in every engine, a counter that fills the key for each new row.

39.4.2 Seeding Three Equal Balances

With the table in place, three test rows go in. The spoken form was "insert into accounts name and balance: Adam 100, Bob 100, Linda 100", which becomes:

\[ INSERT\ INTO\ accounts\ (name,\ balance)\ VALUES\ (\text{'Adam'},\ 100),\ (\text{'Bob'},\ 100),\ (\text{'Linda'},\ 100) \]

Every holder starts with a balance of 100, so the opening position reads Adam 100, Bob 100, Linda 100. A quick read of the table confirms all three rows, and the combined total is \(100 + 100 + 100 = 300\), the consistency baseline every later transfer must preserve. Sense-check: three rows, three equal balances, total 300. This tiny balanced table is the stage for every transaction experiment that follows: updates will move the balances, commits will keep the moves, and rollbacks will erase them.

Equal opening balances are a lab convenience, not a rule. Real ledgers open uneven, and nothing in transaction logic needs equal starts. Also, this single-row-per-holder layout is a teaching stand-in: production systems record each movement as its own row in a separate transaction table, exactly as the companion exercises do with their account-plus-transaction pairs.

Create the accounts table with a serial key, a non-null name, and a non-null balance, then seed Adam, Bob, and Linda at 100 each. That 300-total stage is the fixed backdrop for the two-connection proofs next.

The stage holds three holders at 100 each. The next section opens two windows onto it and shows that one window's uncommitted work stays invisible in the other.

39.5 Transaction Analysis with Two Connections

One table, two windows, one uncommitted edit. Why does the left window show 50 while the right window still shows 100? The answer is the most examinable minute of the whole lecture.

39.5.1 Connections, Query Editors, and the Idle Indicator

Every user reaches the database through a connection, and in the pgAdmin browser tool each new query editor opens a fresh connection window. Opening a second editor means two live connections to the same server and the same movies database. The dashboard view confirms this: after a refresh it lists the open sessions, each with its own session number, alongside the system's own background session.

A connection (one live session between a client window and the server) carries its own transaction state. Each editor carries a small status icon with a precise vocabulary. Before any transaction starts, hovering over the icon reports that the session is idle with no current transaction. That idle message is the baseline for everything that follows: it means the connection is live but no transaction block is open. Real-world: pgAdmin is the graphical administration tool used throughout these exercises to open editors, watch session state, and inspect the dashboard session list.

39.5.2 The Invisible Transaction Behind Every Single Statement

Running a lone statement such as a read of the whole accounts table leaves the icon unchanged: still idle, still no current transaction. The reason is that PostgreSQL wraps the statement silently. Behind the scenes the server adds BEGIN before the statement and COMMIT after it, so the lone command runs as its own complete transaction: open, run, commit, done, without the writer typing either keyword. On a higher level, every single command carries its own invisible BEGIN and COMMIT pair, with finer internal detail below that the session does not need to manage by hand.

This is the autocommit behavior the companion texts name: with autocommit on, each lone statement commits itself. Snowflake shows the same default through its AUTOCOMMIT session parameter, MySQL through SET AUTOCOMMIT=0 to switch it off, and Oracle by instead keeping a transaction open until an explicit close. The exercise that matters is triggering BEGIN and COMMIT by hand to watch the effect. Label the first editor connection one and the second editor connection two, and the stage is set.

39.5.3 BEGIN, a Failed Statement, and Rescue by ROLLBACK

Connection one opens a block by running BEGIN. The icon changes at once, and its message changes with it: the session is idle but now inside a valid transaction block. That message means every command from here on belongs to one single transaction. Opening BEGIN in connection two produces the same change there, which confirms the indicator tracks each connection independently.

The first update attempt in connection one carries a deliberate-looking flaw: the statement text is missing a letter, so the command fails. The failure teaches the strictest rule of transaction blocks. Because an error struck inside the block before it ended, the system aborts the whole transaction and ignores everything after the failure. Even a corrected retyped UPDATE in the same block is refused with the message that the current transaction is aborted and commands are ignored until the end of the transaction block. The status icon agrees, now reporting an idle session inside a failed transaction block.

A missing-letter failure teaches the aborted-block rule: one failed statement inside a block aborts the block, and ROLLBACK is the rescue that clears it so a fresh BEGIN can start clean work. Only one escape exists: ROLLBACK. Running it returns a success message, kills the poisoned block, and restores the normal idle state with no open transaction. The lesson is worth keeping word for word: any failed statement inside a block aborts the block, and ROLLBACK is the rescue that clears it so a fresh BEGIN can start clean work. Retrying the fixed statement without rolling back first never works; the block stays dead until ROLLBACK clears it.

39.5.4 Update, Read-Your-Own-Write, and Cross-Connection Visibility

With the block cleared, connection one opens a new transaction with BEGIN and runs a clean update. The spoken form was "update accounts set balance equal to balance minus 50 where name is Adam", taking Adam from 100 to 50, which becomes:

\[ B_{Adam}' = B_{Adam} - 50 = 100 - 50 = 50 \]

where \(B_{Adam}\) is Adam's starting balance in whole units and \(B_{Adam}'\) is his balance after the update. The command reports success, but nothing has been committed yet, so the change is not yet written to the table for everyone.

Read the table now from inside connection one: Adam shows 50. That is the read-your-own-write effect: the open transaction sees its own uncommitted work. Switch to connection two and read the same table: Adam still shows 100, the original state. Without COMMIT, every other connection keeps seeing the old data. Run COMMIT in connection one to write the block to the table, and a fresh read in connection two now shows Adam at 50. Sense-check: own window sees the new value, other windows see the old value, and after COMMIT both windows agree.

The full cycle is this: open with BEGIN, send the statements that form the block, close with COMMIT so all changes land in the accounts table. Between BEGIN and COMMIT, one transaction never disturbs another because each connection lives in its own separate world.

Exam note: rehearse the two-connection visibility story: an uncommitted update is visible in its own connection at the new value and in every other connection at the old value until COMMIT. Pair it with the aborted-block rule: one failed statement poisons its whole block so that only ROLLBACK clears it. Together they exercise atomicity, isolation, and durability in one scenario.

Two windows, two views, one COMMIT that merges them. The next section isolates the aborted-block rule and drills the contrast between errors inside and outside a block.

39.6 Fixing an Aborted Transaction

The same typo fails twice. The first time nothing breaks. The second time the whole session freezes. What changed between the two failures? Only one thing: an open BEGIN.

39.6.1 An Error Outside Any Block Harms Nothing

A failing query run with no open transaction is harmless. With the connection idle and no BEGIN issued, a query against a nonexistent table fails with a "relation does not exist" error, and the very next valid read of the accounts table runs perfectly. Each statement outside a block lives in its own invisible transaction, as 39.5.2 showed, so one statement's failure cannot poison its neighbors. The system simply moves on.

Run the harmless case step by step: with no block open, query a table that does not exist and collect the "relation does not exist" error. Then immediately read the accounts table: Adam, Bob, and Linda return at their settled values with a success message. Sense-check: the lone failed statement died alone because autocommit wrapped it as its own one-statement transaction and rolled back only that statement.

39.6.2 The Same Error Inside a Block Poisons Everything

The picture flips the moment BEGIN opens a valid block. Running the same bad table reference inside the block produces the same "relation does not exist" error, but now a following known-good read of the accounts table is refused with "current transaction is aborted, commands ignored until end of the transaction block". The block is valid in shape yet dead in effect: the error aborted it, and every further command in it is ignored.

Run the fatal case step by step: open with BEGIN, query the same nonexistent table, and collect the same "relation does not exist" error. Then read the accounts table and collect the "current transaction is aborted" refusal instead of rows. Run ROLLBACK, watch the success message return the icon to idle, then BEGIN again, run the correct statements, and COMMIT when the work should land. Sense-check: the identical typo is harmless alone and fatal inside a block, and ROLLBACK is the savior here, the single keyword that clears an aborted transaction so clean work can restart.

The contrast between the two cases is the point to remember: outside a block an error dies alone, while inside a block an error kills the block and only ROLLBACK revives the session.

Three traps surround this rule. First, retyping the corrected statement inside the dead block without rolling back: PostgreSQL ignores it, every time. Second, assuming COMMIT can close a poisoned block: it cannot, because there is nothing committable left. Third, reaching for a savepoint after the abort: savepoints rescue work before an error, not after a block-wide abort.

Exam note: rehearse the aborted-block rule that one failed statement poisons its whole block so that only ROLLBACK clears it. The contrast is the proof: the same bad table reference is harmless outside a block and fatal inside one.

Errors outside a block die alone; errors inside a block kill the block. The next section raises the stakes from a typo to a full crash and shows the server performing the rescue itself.

39.7 Fixing Transactions on Crash

Unplug the machine mid-edit. When the screens come back, does the half-written 150 survive, or does the old 200 return? This exercise answers by pulling the plug on purpose.

39.7.1 Resetting the Table and Opening an Uncommitted Update

Crashes come in every flavor: hardware, software, connection loss, intentional or not, and this exercise rehearses one. First everything is brought into sync: all balances are updated to 200, and a read confirms Adam, Bob, and Linda each hold 200. Connection one then runs BEGIN, turning its icon into the familiar valid-transaction-block state.

Inside that open block, connection one updates Adam downward by 50. In symbols, with \(B_{Adam} = 200\) as the synced balance:

\[ B_{Adam}' = B_{Adam} - 50 = 200 - 50 = 150 \]

A read inside connection one shows Adam at 150, exactly as intended. But COMMIT is deliberately withheld: the new value is visible in this connection only and has not been written to disk. The database now holds a live uncommitted change, the precise situation a crash loves to find.

39.7.2 Simulating the Crash and Watching Automatic Rollback

The crash is simulated by destroying the connections themselves. From the dashboard view the two open sessions are selected and deleted, so both query-editor windows lose their link to the server. Reading from the first editor now reports that the connection is already closed: it is no longer a valid session.

The second editor tells the rest of the story. Attempt a read there: first it reports a dead connection too, then the tool offers to continue and establish a new connection. Accept that offer, which reconnects the editor and runs the read, and every holder, including Adam, shows 200. The uncommitted 150 has vanished. PostgreSQL itself stepped in during the crash and ran ROLLBACK internally, restoring the last settled transaction state without any manual command. Sense-check: a change that never reached COMMIT must read as if it never happened, and here 200, not 150, is the only correct answer.

The exercise closes the loop on the whole ACID tour. The manual COMMIT writes data to the table when the writer chooses; the manual ROLLBACK undoes a block when the writer chooses; and when a crash removes the writer entirely, PostgreSQL performs the rollback on its own. Atomicity held because the half-done update vanished whole, isolation held because each editor lived in its own session, and durability held because the database came back to its proper up-to-date state after the failure. The companion texts add the restart corollary: on recovery the server rolls back every incomplete transaction it finds and replays committed ones from the log, so ending a session with pending work rolls back, never forward.

Scope: automatic rollback restores the last settled state, not the writer's intent. Work the writer meant to commit but never committed is gone, by design. The defense is procedural, from the companion best practices: resolve every transaction with COMMIT or ROLLBACK before ending a session, and never leave meaningful work uncommitted across a DDL statement or a disconnect.

Deleted sessions prove the crash rule: PostgreSQL performs the rollback automatically, and the uncommitted 150 vanishes while the settled 200 holds. Manual COMMIT writes when the writer chooses, manual ROLLBACK undoes when the writer chooses, and crash recovery chooses rollback on the writer's behalf.

Crashes cannot create half-states: uncommitted work vanishes, settled work holds. The next section softens the all-or-nothing edge for long transactions that need to keep part of their work.

39.8 Partial Rollback with Savepoints

A ten-step transfer runs nine steps perfectly, then step ten turns out wrong. Must the nine good steps die with it? Savepoints say no: mark the good ground as you go, and retreat only to the last good mark.

39.8.1 Why Full ROLLBACK Is Not Enough

Plain COMMIT and ROLLBACK act on the entire transaction: COMMIT writes everything in the block, ROLLBACK undoes everything in the block. In a larger realistic application that all-or-all choice can be too coarse. A session may want to keep the early part of a long transaction while discarding only the later part: a partial rollback to an intermediate stage. That need is the entire reason savepoints exist.

A concrete case from the companion texts: retire product XYZ and close its accounts in one transaction. If the retirement succeeds but the account-closing turns out wrong, plain ROLLBACK would also erase the good retirement. A savepoint between the two steps keeps the retirement while discarding only the closing.

39.8.2 Named Markers at Strategic Positions

The mechanism is a marker dropped at a strategic position inside the transaction block. Each marker marks a stage of the work: state one, state two, state three, and a later rollback can return exactly to that marked stage instead of to the very beginning. In PostgreSQL these placeholders are called savepoints (named marks to which the writer can roll a transaction back).

Both directions need only one short statement each. To plant a mark, with \(s\) standing for the chosen savepoint name:

\[ SAVEPOINT\ s \]

To return to it:

\[ ROLLBACK\ TO\ s \]

The name must be unique within the transaction so the system knows precisely which stage is meant. The spoken syntax taught in the session was "savepoint, then the savepoint name" for planting and "rollback to, then the savepoint name" for returning, and the two statements above are the direct rendering of those spoken forms.

Dialect notes, kept brief so the PostgreSQL form stays primary: standard SQL and MySQL use SAVEPOINT name with ROLLBACK TO SAVEPOINT name, Snowflake and Databricks follow the same SAVEPOINT / ROLLBACK TO SAVEPOINT shape, and SQL Server spells the pair as SAVE TRANSACTION name with ROLLBACK TRANSACTION name. One engine family, small spelling shifts.

39.8.3 Anatomy of a Block with a Savepoint

A full block using a savepoint reads as a fixed skeleton. BEGIN opens the block. A valid statement, a read, an update, an insert, anything legal, does the first piece of work. Then SAVEPOINT marks the spot, for instance under the name savepoint one, and everything achieved so far is captured under that name. A later statement follows, possibly a mistaken one, as the next section's exercise will show, and when the mistake surfaces the session issues ROLLBACK TO that savepoint name. Everything below the mark is discarded while everything above it survives, all still inside the uncommitted block. That skeleton, BEGIN, work, SAVEPOINT, more work, targeted ROLLBACK TO, is the pattern to recognize in every savepoint exercise.

Two companion rules complete the picture. Despite the name, nothing is saved when a savepoint is created: the transaction stays open and uncommitted, and only a final COMMIT makes anything permanent. And a bare ROLLBACK with no name ignores every savepoint and undoes the entire transaction, so the mark must be named to be used.

Savepoints rescue valid-but-unwanted work inside a live block; they cannot revive a block that an error already aborted. Plant marks before risky steps, not after failures, and give each mark a unique name, because a repeated name leaves the rollback target ambiguous.

The savepoint skeleton is BEGIN, work, SAVEPOINT with a unique name, more work, then ROLLBACK TO that name to keep the early work and drop the late work. The next section runs that skeleton against Adam's balance.

Full rollback is all-or-nothing; savepoints add a marked middle. The next section plants one mark, makes one mistake below it, and retreats exactly to the mark.

39.9 Using SAVEPOINT Inside a Transaction

Adam sits at 200. One good debit, one marked snapshot, one regretted second debit. Can a single command bring back the 150 without touching the good work above it? Watch the mark do exactly that.

39.9.1 The First Update and Its Snapshot

The exercise opens on the familiar accounts table with every holder at 200. Connection one runs BEGIN and its icon confirms a valid transaction block. The first statement subtracts 50 from Adam's balance, with \(B_{Adam} = 200\):

\[ B_{Adam}' = B_{Adam} - 50 = 200 - 50 = 150 \]

A read confirms Adam at 150, the intended result. At this exact stage the session captures a snapshot of the block by planting a savepoint:

\[ SAVEPOINT\ first\_update \]

The command reports success, and everything the block has achieved so far is now saved under the name first update: a system snapshot of this intermediate transaction state. Sense-check: 200 minus 50 is 150, the read agrees, and the mark now guards that value.

39.9.2 A Business-Logic Mistake and ROLLBACK TO

Below the savepoint the session runs a second update that subtracts another 50 from Adam, followed by a confirming read. In symbols, with \(B_{Adam}' = 150\) as the snapshotted value:

\[ B_{Adam}'' = B_{Adam}' - 50 = 150 - 50 = 100 \]

The statement itself is valid SQL and runs without error, but the business logic rejects it. Suppose the rules say Adam's balance must not drop that second time: the value should stay at the snapshotted 150, not fall to 100. Deleting valid work by hand would be clumsy; the savepoint makes it one command:

\[ ROLLBACK\ TO\ first\_update \]

Crucially, no COMMIT has happened yet, and that is exactly when ROLLBACK TO is available. Running it discards everything below the mark, and a fresh read shows Adam back at 150. A closing COMMIT then writes that restored state permanently to the table, and a final read confirms Adam at 150. The savepoint absorbed a fully legal but unwanted change. Sense-check: the second debit is gone, the first debit stands, and the committed value is 150.

39.9.3 Stacking Many Savepoints and Naming Them Well

The pattern scales. A complex transaction with many updates can hold as many savepoints as the writer likes, and more is better: each extra mark is another safe restoration stage, so rollback control lands exactly where it is needed. Savepoints can be planted repeatedly and ROLLBACK TO can be used repeatedly within a single block, which makes the feature genuinely powerful rather than a one-shot trick.

Names deserve care because they are the handles grabbed during an incident. A practical convention is to prefix marks and stamp the time or the step purpose into the name: first update, second update, or a timestamped label, so that in a long block each name announces what it protects. Think of trail cairns on a long hike: each cairn marks verified ground, and a wrong turn costs only the steps since the last cairn, not the whole trail. The standing advice is twofold: create as many savepoints as the transaction has meaningful stages, and name each one so its purpose is obvious at rollback time.

Good marks share three habits. First, unique names inside the block, because a duplicate name blurs the retreat target. Second, marks before risky steps, not after, because a savepoint records ground already verified. Third, a closing COMMIT or ROLLBACK still ends the block: marks alone save nothing to disk.

Exam note: practice the savepoint pair SAVEPOINT with a unique name and ROLLBACK TO that name, including the advice to plant many well-named savepoints across a long transaction. Rehearse the numbers: 200 down to 150, marked, down to 100, retreated to 150, committed at 150.

One mark kept the good debit and erased the bad one. The lecture's arc is complete: bundle the work, log the work, guard it with ACID, prove it with two windows, survive errors and crashes, and mark long trails with savepoints.

Key Industry Applications

PostgreSQL is the production open-source database running every exercise here: transactions, ACID guarantees, savepoints, and the pgAdmin workflow all sit inside it. Banks and payment systems run the same bundle logic at scale, where a transfer debits one ledger and credits another inside a single transaction so money can never vanish between the two halves.

pgAdmin is the graphical administration tool used to open query editors as separate connections, read each session's idle or in-block status icon, list live sessions on the dashboard, and reconnect automatically after a dropped session. Operations teams use the same session view in production to spot long-open transactions, blocked writers, and locks before they stall an application.

Simplified banking ledgers, modeled by the accounts table with holder names and integer balances, are the canonical industry setting for transfers where consistency means the combined total never changes. Booking systems, stock control, and wallet services copy the pattern: check the balance, move the amount, keep the total, commit once.

High-traffic multi-user applications with thousands of simultaneous users depend on transaction isolation so concurrent readers and writers on the same rows never corrupt each other. PostgreSQL leans on multi-version concurrency with read committed as the default plus repeatable read and serializable for snapshots and strict orderings; Snowflake pins reads to committed data; MySQL's InnoDB pairs row-level locking with versioning. Different engines, same goal the session drilled: one transaction never disturbs another before COMMIT.

Unix background processes served as the session's own analogy for isolation: independent daemons doing their own jobs, mutually unaware, exactly like serialized transactions. The analogy travels well to job queues and microservices, where each worker owns its unit of work and a failed worker's partial output is discarded rather than merged.
