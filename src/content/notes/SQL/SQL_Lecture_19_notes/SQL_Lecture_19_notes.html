# PostgreSQL Schemas

This lecture explains how PostgreSQL organizes a database with schemas: what a schema is, how to create, rename, drop, move, and copy schemas, how the search path resolves short table names, what the system catalog holds, and how schema privileges control who can see and build what.

19.1 What Is a Schema

Why does one database hold hundreds of tables without collapsing into chaos? Because PostgreSQL never stores tables in a flat pile. It sorts them into named folders called schemas, and every query, grant, and backup follows those folders.

A schema (a named namespace inside a database that holds database objects, for example human_resources) is the main way PostgreSQL keeps a database organized. Think of a database as an office building, each schema as one floor, and each table as one room on that floor. Two floors can each have a room called "Meeting Room" without confusion, because the floor name keeps them apart. The analogy breaks in one place: unlike floors, schemas are also security borders, so the floor you may enter decides which rooms you may open.

A database can hold one schema or many schemas, and each schema belongs to exactly one database. Inside a schema live named objects such as tables, views, indexes, data types, functions, stored procedures, operators, materialized views, and foreign tables. When the object browser is opened under a schema, each of these object kinds gets its own folder: tables sit under tables, views under views, functions under functions, and so on. Each index defined on a table also belongs to the schema, so a schema gives a full picture of the structure of a database.

A schema is a namespace: a label that turns a bare object name such as employees into an exact address such as human_resources.employees. Every schema name inside one database must be unique. Two schemas in the same database cannot share a name, so creating a second schema called public when public already exists fails. There is no fixed cap on how many schemas one database may hold. The practical rule is to create as many as can still be managed from a database administration point of view.

Schemas pay off in three ways. First, they group related objects into logical units that are easy to grasp. Human resources tables can live together in a schema called human_resources, while internal application tables sit in a separate internal schema. Second, schemas let many people share one database without stepping on each other. Different users keep their tables in different schemas, yet from the application side everything still belongs to the same database, which helps both application design and day-to-day management. Third, and most important for large systems, schemas limit who can touch what. Instead of handing out rights table by table, rights are shaped at the schema level so that only approved users reach the tables inside.

An analytics company runs close to 600 tables and keeps them usable by sorting them into several schemas, then granting each group of users access only to the schemas they need. Picture three schemas: sales, hr, and internal. The sales team is granted entry to sales only, the HR team to hr only, and the platform team to internal only. One database, three audiences, no accidental cross-reads. The takeaway: schemas turn 600 loose tables into three labeled drawers with three separate keys.

PostgreSQL creates a schema called public automatically for every new database. Nothing has to be typed to get it. It simply appears under the new database with its folders for tables, views, data types, functions, procedures, materialized views, foreign tables, and indexes ready to fill.

A powerful detail is that two different schemas may each hold an object with the same name. The public schema can hold an employees table while a sales schema holds its own employees table, and the two do not clash because the schema name keeps them apart. Later sections use this exact setup for hands-on practice.

Assumption: schema names are unique per database, not per server. Two databases may each contain a schema called sales with no conflict, because each schema lives inside exactly one database. Scope: a schema never spans databases. A query in database hr cannot reach into a schema of database test by naming the schema alone; it must connect to that database first.

Picture the layout as a tree. The database name sits at the top. One branch per schema hangs below it (public, sales, human_resources). Under each schema branch, one twig per object kind (tables, views, functions) fans out, and the tables hang as leaves. The one-sentence takeaway: every object has exactly one path from the root, so no two leaves share a full address.

Newcomers expect a schema to behave like a MySQL database (a separate container with its own login). In PostgreSQL it does not: it is a folder inside the current database, and connections, backups, and logins attach at the database level. A second trap is reusing the pg_ prefix for your own tables; that prefix belongs to system tables, so a user table called pg_orders invites confusion with the catalog. A third trap is assuming schemas cap out at some small number; they do not, but every extra schema is one more namespace to grant, back up, and document.

Q: What kinds of objects does a schema actually contain? A: Tables, views, indexes, data types, functions, stored procedures, operators, materialized views, and foreign tables. Each kind sits in its own folder under the schema, and every index on a table belongs there too. Several students asked this in different words, and the answer is the same list every time: if PostgreSQL can name it inside a database, a schema can hold it.

A schema is the one-database, many-folder organizer: unique names, a free public folder in every new database, and same-named tables kept apart by their schema prefix. That prefix is what every later section qualifies, moves, grants, and compares.

Across databases the same word shifts meaning, so keep one version in mind. In MySQL, CREATE SCHEMA is a synonym for CREATE DATABASE; there is no namespace layer between database and table. In SQL Server, schemas sit inside a database much like PostgreSQL (dbo plays the role public plays). In Snowflake, the hierarchy grows one level taller: organization, then database, then schema, then object, and queries address objects as database.schema.table. The lecture's PostgreSQL picture — database, then schema, then object — is the middle case.

19.1.1 Definition and Contained Objects

A schema is a namespace that contains named database objects. The object list is wide: tables, views, indexes, data types, functions, stored procedures, operators, materialized views, and foreign tables. Browsing a schema shows one folder per object kind, so the layout of the whole database is visible at a glance. Because indexes live inside the schema as well, opening a table reveals its index set right where the table sits.

19.1.2 Benefits of Organizing With Schemas

Three gains keep coming back. Logical grouping puts related tables side by side, for example all human resources tables under human_resources. Shared use without interference lets many users work in one database, each inside their own schema, while applications still see a single database. Access control turns schemas into security borders: rights granted or withheld at the schema level decide which users reach the objects inside. For anyone running hundreds of tables, that third gain is the one that keeps the system safe.

19.1.3 The Default Public Schema and Uniqueness Rules

Each new database arrives with a built-in schema named public. Each schema name in a database must be unique, so a duplicate public is rejected. One database may hold as many schemas as remain manageable. And two schemas may reuse the same object name freely, since the schema prefix keeps every reference exact.

19.2 Creating, Renaming, and Dropping Schemas

How do you add a new folder, relabel one, or throw one away? PostgreSQL gives three one-line statements, and pgAdmin gives three matching clicks. The catch is that typed drops never ask twice.

Every schema operation lands in whichever database the session is connected to. Think of the query editor as a worker standing inside one building: every folder they build goes into that building, never the one next door. Before typing anything, check the connection bar and confirm it names the intended database.

Purpose: create a new namespace, relabel an existing one, or remove one. Inputs: the schema name (and for renames, the new name). Output: the schema appears, is relabeled, or disappears after a refresh.

CREATE SCHEMA sales;
CREATE SCHEMA human_resources;
ALTER SCHEMA sales RENAME TO programming;
DROP SCHEMA programming;

Run each statement in a query editor connected to the target database, then refresh the schema list. Creating sales beside public gives two schemas; adding human_resources gives three. Renaming sales to programming keeps every object and changes only the label. Dropping programming removes the schema entry.

Start in a database holding only public. Run CREATE SCHEMA sales; and refresh: the list now shows public and sales. Run CREATE SCHEMA human_resources; and refresh: three schemas. Run ALTER SCHEMA sales RENAME TO programming; and refresh: sales is gone and programming stands in its place. Run DROP SCHEMA programming; and refresh: two schemas remain. Each step confirmed by a refresh; nothing hidden.

A schema may even share its name with the database itself. A database called air can hold a schema called air with no trouble. What fails is a true duplicate: asking for a schema called air when a schema called air already exists in that database is rejected, because schema names must stay unique inside one database.

-- Allowed: schema name matches the database name.
CREATE SCHEMA air;
-- Rejected: a schema called air already exists here.
CREATE SCHEMA air;

Scope: DROP SCHEMA without extra options removes only an empty schema. If the schema still holds tables, the statement fails rather than deleting data silently. Assumption: the examples below drop schemas that are empty or confirmed empty first; dropping a schema full of loaded tables needs an explicit cascade choice and a backup, which is why the safety habit matters.

The graphical tool asks for confirmation before it drops anything, while the query editor runs the drop at once with no prompt. That split is worth remembering. Typed drops act fast and give no second chance, so extra care belongs around every DROP SCHEMA, especially when the schema holds key tables full of data and indexes. Many people prefer the graphical tool for drops precisely because the confirmation dialog guards against a slip.

Three traps recur. First, running CREATE SCHEMA while connected to the wrong database builds the schema in the wrong place; always check the connection first. Second, typing DROP SCHEMA in the query editor on a schema full of data removes the namespace without a confirmation dialog, so verify the database, the name, and the contents first. Third, assuming a rename moves or copies objects; it does neither, it only relabels the same container with everything inside untouched.

Q: Why would anyone run drops in the graphical tool instead of the query editor? A: The graphical tool asks for confirmation before it removes a schema, while the query editor runs DROP SCHEMA at once with no prompt. Under a schema full of loaded tables and indexes, that extra question can save a whole dataset.

Exam note: Know CREATE SCHEMA name, ALTER SCHEMA old RENAME TO new, and DROP SCHEMA name cold, plus the fact that query-editor drops run without confirmation. The rename-vs-duplicate distinction (same name as the database is fine, duplicate schema name is rejected) is the detail most likely to be tested.

Real teams use schemas as release and access boundaries: a staging schema holds the next version of every table while public serves the live app, and only the deploy role may write to either. The three statements above are the entire vocabulary for managing those boundaries day to day.

Cross-database notes worth keeping: PostgreSQL and SQL Server both support CREATE SCHEMA, ALTER SCHEMA, and DROP SCHEMA with nearly identical shapes. MySQL uses CREATE SCHEMA as an alias for CREATE DATABASE instead, so there is no separate rename-a-namespace step. Snowflake matches PostgreSQL closely (CREATE SCHEMA sales;, ALTER SCHEMA sales RENAME TO programming;, DROP SCHEMA programming;) and adds USE SCHEMA sales; to pick the working schema. Since the concepts are the same and only the keyword alias differs, keep the PostgreSQL form.

19.2.1 CREATE SCHEMA Through the Query Editor

Point the query editor at the target database first. Then type CREATE SCHEMA followed by the chosen name and run it. Refresh the schema list to confirm the new entry. Build a second schema the same way when a new logical group is needed, and remember that a schema name may match the database name but never duplicate an existing schema name.

19.2.2 RENAME With ALTER SCHEMA

Type ALTER SCHEMA, then the current name, then RENAME TO with the new name. Run it and refresh. The schema keeps all of its objects and only its label changes, as the sales-to-programming rename shows.

19.2.3 DROP SCHEMA and Safety Habits

Type DROP SCHEMA with the schema name and run it. The schema disappears on refresh. Because the query editor never asks twice, double-check the database, the schema name, and what lives inside before running a drop.

19.2.4 Same Operations in the Graphical Tool

In pgAdmin, right-click the database, open the create menu, and pick the schema option. Typing a name such as air shows the exact SQL it is about to run, which is CREATE SCHEMA with ownership set to the postgres superuser account, and saving adds the schema. Creating tables inside works the same way: right-click tables, add a table such as employees, and define columns such as an employee_id serial primary key plus first_name and last_name text columns of length 100. Refreshing shows the new table inside its schema. Deleting means right-clicking the schema and confirming the drop dialog. Renaming means right-clicking the schema, opening properties, and typing the new name, for example switching air to human_resources. Every create, rename, and drop done by typing has a matching point-and-click path.

19.3 Schema Hierarchy and Three-Part Names

Once tables are spread across schemas, two questions shape everything: where does each object physically sit, and how is it named in a query. Remember the office-building picture: the building is the database, each floor is a schema, each room is a table. The full address always names all three.

The physical nesting runs server, then cluster (when one exists), then database, then schema, then the object itself: a table, an index, a view, a function, a stored procedure, or any other kind. The naming rule mirrors that nesting. A fully qualified name starts with the database, adds a dot, then the schema, then another dot, then the object name: database.schema.object.

A database called hr holds a schema called public, and inside sits a table called employees. The full address of that table reads hr.public.employees: database, dot, schema, dot, table. Query it in full as:

SELECT * FROM hr.public.employees;

or in short as:

SELECT * FROM employees;

Both return the same rows, because the search path fills in the missing public part. A table called employees inside a schema called human_resources is reached as database, then human_resources, then employees, and running that query returns its own rows, which differ from the rows of the public table of the same name. Same table name, different schema prefix, different answer.

Every new database proves the pattern at once, because PostgreSQL builds the public schema for it without being asked. Creating a database called test and opening its schema folder shows public already waiting inside.

Reaching a table outside public needs the fuller address. That contrast is the whole point of the hierarchy: identical table names stay separate because their schema prefixes differ.

Assumption: the three-part form database.schema.table is a teaching address. Inside a PostgreSQL query, the engine resolves two-part names (schema.table); the database part is fixed by the connection, and cross-database references need extensions such as dblink or foreign data wrappers. Scope: within one connected database, schema.table is always exact, and the bare table name is exact only when the search path resolves it to one schema.

Picture a street address: hr is the city, public is the street, employees is the house number. Drop the city and street and the post office guesses from a default list (the search path). Guess right and the letter arrives; guess wrong and it lands at the wrong house with the same number on a different street.

The classic trap is writing SELECT * FROM employees; while two schemas each hold an employees table and assuming it reads "the" table. There is no single table; the search path picks one and ignores the other. Always qualify (human_resources.employees vs public.employees) whenever duplicates exist or the query must be unambiguous.

Q: How do you reach a table that lives in a schema other than public? A: Name the database, then the schema, then the table, joined with dots, as in hr.public.employees. Tables in public allow the short form because the search path fills in the missing part, but tables elsewhere need their fuller address.

Exam note: Write any object address as database, dot, schema, dot, object (hr.public.employees). Short names are a convenience the search path provides, not a second address.

Snowflake uses the same three-part shape literally (database.schema.table, for example learning_sql.public.employee), because its hierarchy is database, then schema, then object. MySQL collapses one level (database.table, since schema means database there). SQL Server matches PostgreSQL with an optional server prefix (server.database.schema.table). Keep the lecture's hr.public.employees pattern as the canonical shape.

19.3.1 Physical Nesting From Server to Object

Start at the server that hosts the data, move into the database, then into the schema, and land on the object. Databases always exist in this chain, schemas always sit inside exactly one database, and objects always sit inside exactly one schema. Holding that chain in mind makes every address in the next section read naturally.

19.3.2 Database, Schema, and Object in Queries

Queries spell the chain with dots: database, dot, schema, dot, object name. The hr.public.employees pattern shows the shape, and the human_resources variant shows how the middle part swaps when the target table lives elsewhere. Short names work only because the search path quietly adds the missing schema, which the search-path section explains in full.

19.3.3 Seeing the Default Public Schema in a New Database

Create a database called test, open it, and look at its schema folder. The public schema is already there with no setup step. That automatic public schema is why short table names keep working in fresh databases from the very first query.

19.4 Moving a Table to a New Schema

Tables are not pinned to the schema where they are born. Moving one is a single statement, but the statement has one detail that trips everyone the first time: the table on the left must carry its current address, not just its name.

Purpose: relocate a table (with its data, indexes, and constraints) from one schema to another without copying rows. Inputs: the currently qualified table name and the destination schema. Output: the table vanishes from the source schema folder and appears in the destination folder.

ALTER TABLE human_resources.orders SET SCHEMA public;

Type ALTER TABLE, then the table name, then SET SCHEMA with the destination schema. The shape never changes no matter which two schemas are involved. Refresh both schema folders after running it to confirm the table left one home and arrived in the other.

Two schemas exist: human_resources and public. A small table called orders is built inside human_resources with a single order_id serial primary key column. Run:

ALTER TABLE human_resources.orders SET SCHEMA public;

Refresh the tables folder under human_resources: it shows nothing. Refresh under public: orders sits there. The reverse move spells symmetrically:

ALTER TABLE public.orders SET SCHEMA human_resources;

The table keeps every row and index; only its schema address changes.

The detail that trips people up is the name on the left side of the statement. Because the orders table starts outside public, writing bare orders is not enough. The table must be named with its home schema first, human_resources.orders, and then SET SCHEMA points at the destination. That qualification tells the system exactly which orders table is meant, which matters as soon as two schemas hold tables of the same name.

Assumption: both schemas already exist and no table with the same name already sits in the destination; a collision there is rejected. Scope: the move carries dependent objects (indexes, constraints) with the table, but views, functions, or foreign keys that name the old address may need attention. Moving one table never moves a whole schema; bulk moves need one statement per table or a dump-and-restore pass.

pgAdmin offers the same move with clicks. Right-click the table, open properties, and find the schema drop-down next to the table name and owner. Switching the drop-down from public to human_resources shows the exact SQL it is about to run (ALTER TABLE public.orders SET SCHEMA human_resources;). Saving runs it, and the table lands in the new schema. The same drop-down moves tables in the other direction just as easily. Later material extends the idea from one table to moving a whole set of tables at once.

Two traps: running the move with a bare table name while the table lives outside public (the engine looks in the wrong schema and reports the table missing), and forgetting to refresh both schema folders so the table looks duplicated or lost when it actually moved cleanly.

Always qualify the moving table with its current schema (human_resources.orders), then name the destination after SET SCHEMA. Refresh both folders to confirm the move.

19.4.1 ALTER TABLE ... SET SCHEMA Syntax

Type ALTER TABLE, then the table name, then SET SCHEMA with the destination schema. The shape never changes no matter which two schemas are involved. Refresh both schema folders after running it to confirm the table left one home and arrived in the other.

19.4.2 Qualifying the Table Name

When the table starts outside public, prefix it with its schema: human_resources.orders rather than bare orders. That prefix removes all doubt about which table moves. The habit also protects every other statement that touches tables in non-public schemas.

19.4.3 Moving Tables in the Graphical Tool

Open the table properties in pgAdmin, change the schema drop-down, and check the preview SQL before saving. The preview always shows the same ALTER TABLE ... SET SCHEMA statement the query editor would run, so the clicks teach the syntax while they do the work.

19.5 Schema Search Path

In daily work, tables are named without any schema prefix. Queries say SELECT * FROM orders instead of spelling out the long database-dot-schema-dot-table form. That short style works because public sits in the schema search path. What happens when the short name could mean two different tables? The path order decides, silently.

The search path (the ordered list of schemas the system scans, in order, whenever an object name arrives without a schema attached, for example human_resources, public) is what turns a bare table name into a real address. Think of the old DOS program path, or the Python and PHP application path: a list of places to look, tried one after another, first hit wins. The analogy breaks in one way that matters: the wrong hit does not raise an error, it returns the wrong table's rows.

Two commands reveal the current setup. SELECT current_schema shows which schema the session treats as current; in the demo it answers public. SHOW search_path shows the whole list; the demo answers with two entries: a per-user entry that stands for the login name, followed by public. That first entry always means whoever is logged in right now. Since the demo logs in as postgres, the system first looks for a schema called postgres, finds none, and moves on to public, where it runs the query as public.orders. Logged in as adam, the system would first try a schema called adam before falling back to public.

SELECT current_schema;
SHOW search_path;

Type SELECT * FROM orders while the current schema is public. The system runs it, in effect, as SELECT * FROM public.orders: it adds current-schema, dot, table name behind the scenes. Now move the orders table into human_resources and rerun the same short query. It fails with a does-not-exist error, because neither the login-name slot nor public holds that table anymore. Same spelling, different schema contents, success turns into failure. That is the search path at work.

Adding a schema to the path takes one statement:

SET search_path TO human_resources, public;

Running SHOW search_path afterwards confirms both entries. The login-name entry drops out here because the statement spelled out exactly which schemas are wanted. Bringing it back is easy by listing it first:

SET search_path TO postgres, human_resources, public;

Now three entries are searched in order. With human_resources on the path, tables inside it need no prefix. A scratch table called test1 built in public and then moved into human_resources answers a bare SELECT * FROM test1 with no qualification at all.

Order decides ties, and ties happen. Build a table called test1 in public with a column called id2, add the value 1 to it, and keep a second table also called test1 in human_resources with no rows. The short query SELECT * FROM test1 now has two candidates. With the path set to login name, then human_resources, then public, the system finds the human_resources copy first and returns its empty set, while the public copy with its row never gets consulted. Flip the path so public comes before human_resources and the same short query returns the row. The spelling never changed. Only the order changed, and the answer changed with it. So whenever two schemas share a table name, the first schema in the path wins, and anyone reading the result must know which schema answered.

Assumption: the path is per session; SET search_path affects the current connection only unless saved as a database or role default. Scope: the path resolves unqualified names only. A qualified name (human_resources.test1) always bypasses the path and hits exactly that schema, which is why qualifying is the safe habit in scripts and application code.

Leaving public out of the path breaks public tables. With the path set to human_resources alone, SHOW search_path confirms public is gone, and a query against a public-only table fails with a relation-does-not-exist error. The rule that follows is blunt: when the database uses the default public schema, keep public in the search path, or every public table turns unreachable by its short name.

Three traps: dropping public from the path and losing every public table by short name; relying on path order with duplicate table names and reading the wrong copy's rows; and assuming SET search_path persists across sessions when it resets on reconnect (use ALTER DATABASE ... SET search_path or ALTER ROLE ... SET search_path for a durable default).

Q: What happens when the same table name exists in two schemas? A: The first schema listed in the search path wins, so path order decides which table answers. Flip public ahead of human_resources and the same short query returns different rows. Several students circled this confusion, and the demo's empty-vs-one-row test1 pair is the canonical proof.

Exam note: View with SHOW search_path, change with SET search_path TO a, b, keep public listed, and remember first-listed wins ties. Be ready to predict which test1 copy answers for a given path order.

Production code usually qualifies security-sensitive tables (billing.charges, never bare charges) and reserves short names for interactive exploration, precisely because a path change elsewhere can silently reroute a bare name. When the default must stick, ALTER DATABASE f1db SET search_path TO f1db, public; bakes the order into the database itself.

19.5.1 Short Names and Fully Qualified Names

A fully qualified name spells database, dot, schema, dot, object. A short name gives only the object and lets the search path fill in the schema. Short names dominate real code because they stay readable, and they stay correct only while the path lists the right schemas.

19.5.2 Viewing the Current Schema and Full Path

Run SELECT current_schema to see the session schema, which reads public in the demo. Run SHOW search_path to see the full ordered list, which reads as the login-name entry followed by public. The system tries each entry in turn and runs the query against the first schema that holds the named object.

19.5.3 Adding a Schema to the Path

Run SET search_path TO with the wanted schemas separated by commas, for example human_resources, public. Confirm with SHOW search_path. Re-add the login-name entry first in the list when the per-user slot is still wanted. From then on, tables in the newly added schema answer short names.

19.5.4 Why Order Matters: Same Table Name in Two Schemas

Two tables both called test1, one per schema, prove that order is load-bearing. Login name, then human_resources, then public returns the empty human_resources copy. Login name, then public, then human_resources returns the public row. Same spelling, different answer, decided purely by which schema the path tries first.

19.5.5 Always Keep Public in the Path

Drop public from the path and short queries against public-only tables fail with relation-does-not-exist errors. Any database that stores objects in the automatic public schema should list public in its path, or those objects stay reachable only through fully qualified names.

19.6 Altering Schema Ownership

Every schema has an owner, and ownership can change hands with one statement. Who owns the folder decides who controls it by default, so handing a schema to a new owner is really handing over its front door.

Purpose: transfer control of a schema to another user or role. Inputs: the schema name and the new owner name. Output: the owner field on the schema changes; the objects inside stay where they are.

ALTER SCHEMA human_resources OWNER TO adam;

Type ALTER SCHEMA, then the schema name, then OWNER TO with the new owner name. Run it and check the schema properties to confirm the owner changed. The adam handoff in the demo is the pattern to copy for any user or role.

The demo database holds two schemas, human_resources and public, both owned by the postgres superuser account. A second login role called adam already exists from earlier setup. Run ALTER SCHEMA human_resources OWNER TO adam;, then open the schema properties: the owner field now reads adam. Hand it back in pgAdmin by right-clicking the schema, opening properties, switching ownership to postgres, and saving: reopening properties shows postgres again. One line moves it out, one drop-down moves it back.

Assumption: the new owner role already exists; the statement does not create users. Scope: ownership of the schema is not ownership of every table inside it. Tables keep their own owners (whoever built each table), so a full handoff may need table-level grants or ownership changes alongside the schema change.

Picture ownership as holding the master key to a floor: the floor owner decides who gets room keys, but each room still records who furnished it. Changing the floor's master key does not rewrite every room's inventory card.

The trap is assuming the new schema owner automatically gains full rights on every table inside. Table rights are a second lock (the privileges section proves this with USAGE alone failing at the table door). After an ownership change, verify table-level access separately.

ALTER SCHEMA name OWNER TO new_owner moves the schema; pgAdmin properties move it back. Confirm in properties, and remember tables keep their own owners.

19.6.1 ALTER SCHEMA ... OWNER TO Syntax

Type ALTER SCHEMA, then the schema name, then OWNER TO with the new owner name. Run it and check the schema properties to confirm the owner changed. The adam handoff in the demo is the pattern to copy for any user or role.

19.6.2 Changing Ownership in the Graphical Tool

Right-click the schema in pgAdmin, open properties, change the ownership field, and save. The dialog writes the same ownership change the typed statement performs, which makes it a safe way to hand schemas back and forth while learning.

19.7 Duplicating a Schema With All Data

PostgreSQL has no single "copy schema" statement. Copying a whole schema, structure plus rows, takes three moves: freeze the source into a file, rename the original out of the way, and replay the file so the copy lands under the original name.

Purpose: produce two schemas with identical tables and rows. Inputs: the source schema name and a scratch database to work in. Output: the original data under a renamed schema plus a rebuilt copy under the original name. Steps: (1) dump the source schema to a file, (2) rename the original schema, (3) restore the file.

The demo runs inside a scratch database called test_schema. Creating that database and opening a query editor connected to it is the mandatory first step, because every later command must run against test_schema rather than the previous database.

Seed the demo: inside the automatic public schema of test_schema, build a songs table with a song_id serial primary key and a song_title text column of length 100. Insert two rows, Counting Star and Rolling On. A short SELECT * FROM songs confirms both rows with no schema prefix, because the session sits in test_schema with public on its path. One subtle trap: running the CREATE TABLE while still connected to the wrong database fails, so reconnect the editor to test_schema first. Two rows confirmed before the copy begins.

Step one is the dump. The pg_dump backup utility copies the public schema, data included, into a file called dump.sql:

pg_dump -D test_schema -h localhost -U postgres -N public > dump.sql

The flags name the database, the host, the login user, and the schema to copy. Typing the password when asked runs the dump, and opening dump.sql in a text viewer shows every statement needed to rebuild the schema: the table definition for public.songs plus the inserted rows with their titles. That file is the full frozen copy.

Step two renames the original out of the way. In pgAdmin, the public schema properties change its name to old_schema and save. Now the database holds old_schema with the live songs table, and the name public stands free.

Step three restores the file with the psql command-line client:

psql -h localhost -U postgres -d test_schema -f dump.sql

The flags name the host, the user, the target database, and the file to replay. Running it rebuilds a fresh public schema from the dump. Refreshing the schema list shows two schemas side by side: old_schema, the renamed original, and a new public, the restored copy. Checking both songs tables shows the same titles in each: Counting Star and Rolling On in public.songs and the identical rows under old_schema. The schema now exists twice with matching data, which is exactly what duplicating a schema means.

Assumption: pg_dump and psql run from the operating-system shell (command prompt or terminal), not inside the SQL query editor; pasting them into a query window fails. Scope: the dump captures the named schema plus its data, not the whole cluster. Other databases, roles, and server settings are untouched. Large schemas produce large files, so confirm disk space and confirm dump.sql holds both the table definition and the rows before renaming anything.

Picture the process as photocopying a labeled binder. pg_dump photocopies every page into a stack (dump.sql). Renaming the original binder to old_schema frees the old label. psql feeds the photocopy stack through the printer under the freed label, producing a second binder with the same pages.

Three traps end demos early: dumping while connected to the wrong database (the file comes out empty or stale); renaming before verifying the dump file (the only good copy may be corrupt); and typing pg_dump/psql into the SQL editor instead of the shell. Verify connection, verify file, then rename.

Dump with pg_dump, free the name by renaming to old_schema, restore with psql -f dump.sql, then query both copies to prove the rows match. Shell for dump and restore, SQL editor only for the seed and the checks.

MySQL reaches the same goal with mysqldump db > dump.sql plus mysql db < dump.sql, and backs whole databases rather than one schema at a time. Snowflake skips files entirely: CREATE SCHEMA copy CLONE original; duplicates structure and data in one step (zero-copy clone). Since the lecture's PostgreSQL path is the only file-based one, keep dump, rename, restore as the canonical three moves.

19.7.1 Dumping the Source Schema With pg_dump

Run pg_dump against the right database with the host, user, and schema flags, redirecting output to dump.sql. The password prompt completes the login. Open the file and confirm it holds both the table definition and the row data before moving on, since everything downstream depends on that file.

19.7.2 Renaming the Original Schema

Rename public to old_schema through the schema properties dialog and save. This frees the public name so the restore can recreate it, while the live data stays safe under old_schema.

19.7.3 Restoring the Dump With psql

Run psql with host, user, database, and file flags pointing at dump.sql. Refresh the schema list and confirm both schemas exist, then query songs in each to confirm the rows match. Matching titles in both copies close out the proof.

19.8 System Catalog Schema

Beyond public and every hand-built schema, each database holds a catalog schema that belongs to the system itself. PostgreSQL keeps metadata (data about data: what exists, how it is shaped, how it connects) about the database and the cluster inside that catalog. The engine reads and writes those records to track its own state, and outside tools and processes read the same records to learn what is going on inside the database.

The catalog holds system tables plus every built-in data type, function, and operator. Every system table name starts with the prefix pg_, so giving user tables that same prefix invites clashes and is best avoided. The information_schema companion schema exposes the current database through standard SQL views over tables, functions, procedures, and every other defined object.

One catalog, named pg_catalog, enjoys a special place in name lookup. It behaves as if it always stands first in the search path, even when SHOW search_path lists only the login-name entry and public. So a short name resolves against built-in objects before anything else. That default can be reshaped: listing pg_catalog first, then the login-name entry, then public keeps built-ins on top explicitly, while listing the login-name entry, then public, then pg_catalog last lets user objects with colliding names win over built-ins instead. The SET search_path TO statement from the earlier section controls the order. The choice belongs to the application logic: keep built-ins first for safety, or push user names ahead when overrides are intended.

List every schema through the standard view:

SELECT * FROM information_schema.schemata;

One of the returned rows names pg_catalog, which is how its presence is confirmed, alongside public and every hand-built schema. Filter to one database's tables the same way the books do:

SELECT table_name, table_type
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY 1;

The catalog answers with rows; no guesswork about what exists.

The closing rule is firm: look at the catalog, never reshape it. PostgreSQL manages those tables itself, exactly as an application manages its own storage, and hand edits invite corruption. Changes there are reserved for absolute emergencies, and even then a rebuild likely follows. Viewing is always safe. Touching is not.

Assumption: catalog contents differ per database for database-local objects, while cluster-wide state lives in shared catalog tables. Scope: information_schema shows the current database only; to audit another database, connect to it first. Queries against the catalog see committed metadata, so uncommitted DDL in another session may not appear yet.

Picture the catalog as the building's wiring closet with a glass door: every circuit is labeled and visible (pg_tables, pg_proc, information_schema.columns), and anyone may read the labels, but only the building engineer (PostgreSQL itself) may rewire. Reaching through the glass with your own screwdriver shorts the building.

Two traps: naming a user table with the pg_ prefix and colliding with a future system table, and hand-editing catalog rows (UPDATE pg_class ...) instead of using ALTER/CREATE statements. The first creates confusing name resolution; the second can corrupt the database beyond repair.

pg_catalog is the implicit first entry of the search path; information_schema is the read-only standard window into objects; hand edits to either are forbidden. Query freely, alter never.

Every major database ships the same window with its own extras. MySQL and SQL Server expose information_schema views per the SQL standard (information_schema.tables, .columns, .schemata), exactly as the lecture uses them. Snowflake keeps information_schema per database and adds a GET_DDL('table','public.employee') function plus account-level history views. Since the standard views behave the same everywhere, keep the lecture's SELECT * FROM information_schema.schemata; as the portable inventory query.

19.8.1 Metadata, System Tables, and Built-In Objects

The catalog stores metadata about the database and cluster, and it carries the system tables together with all built-in types, functions, and operators. The engine leans on these records to run, and external processes read them to inspect the database from outside.

19.8.2 pg_catalog and the Search Path

The pg_catalog schema is searched first even when the path never names it. SHOW search_path confirms the visible list while the catalog quietly leads it. Explicit ordering through SET search_path TO can place user names ahead of built-ins when overrides are wanted, or keep the catalog first for the safe default.

19.8.3 Viewing Schemas Through information_schema

The information_schema system schema presents database objects as views. Querying information_schema.schemata lists every schema, and the pg_catalog row in the answer confirms the catalog sits alongside public and the rest.

19.8.4 Hands Off the Catalog

PostgreSQL owns the catalog tables and maintains them without help. Treat them as view-only. The pg_ prefix stays reserved for the system, and user objects take other names so no conflict ever arises.

19.9 Comparing Tables and Columns Across Two Schemas

Schemas drift. One team adds a column to its copy of test1, another renames one, and suddenly two same-named tables no longer match. A long but methodical query compares column names between two schemas and reports every column missing on either side, so drift becomes a readable list instead of a mystery.

Purpose: audit two schemas for column-level drift. Inputs: the two schema names. Output: one row per table-and-column combination that exists on one side only. Steps: (1) read each schema's table-column pairs from information_schema, (2) FULL JOIN the halves on table plus column name, (3) keep only one-sided rows with COALESCE labels.

The demo runs in a database holding a public schema and a human_resources schema, each with its own table called test1. The public copy carries a column called id2, while the human_resources copy carries a column called id. Same table name, different columns: exactly the drift this query is built to catch.

Each half reads one schema from the information_schema views. Either half can carry ORDER BY table_name to keep the output readable, and running one half alone shows the full column roll call: countries, departments, employees, and finally test1 with its id2, which confirms the raw material is correct before the halves are joined.

-- Half one: every table-column pair in public.
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public'
ORDER BY table_name;
-- Half two: the same for human_resources.
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'human_resources'
ORDER BY table_name;

The halves meet in a FULL JOIN on matching table name plus matching column name. Matches mean agreement and fall away; one-sided rows survive as the differences. The WHERE clause keeps only rows where one side came back empty, and COALESCE prints whichever side has a value, relabeled schema_one and schema_two. Run each half alone first; trustworthy halves make a trustworthy join.

Running the full statement turns the abstract shape into concrete answers. The jobs table appears with an empty slot on one side, meaning it exists in one schema and has no counterpart in the other. The test1 rows split: id shows as present in one schema copy and missing in the other, while id2 mirrors the gap in reverse. Adding a name column of length 100 to both copies and rerunning makes those name rows vanish from the report, because a column present on both sides is not a difference. Renaming one copy to name_hr brings a fresh report row that ties test1 to name_hr on the human_resources side only, which shows how the report attributes each gap to its schema. That loop (add a column, rerun, watch the row appear or disappear) is how the query earns trust.

Assumption: both schemas live in the currently connected database, and the comparison is by name only (table name plus column name), not by type or length. Scope: the report catches missing tables and missing columns; it does not catch a same-named column whose type changed from int to text. Type drift needs a second comparison over data_type and character_maximum_length.

Picture two printed inventories side by side, one per warehouse. A clerk draws lines between identical rows (same table, same column). Every row with no line is circled: present in warehouse one only, or warehouse two only. The FULL JOIN draws the lines; the WHERE ... IS NULL filter circles the leftovers.

Two traps: joining on table name alone (columns with the same name in different tables falsely match), and forgetting ORDER BY table_name, column_name so the gap list scatters and a missing column hides in the noise. Always join on both names and always sort.

Read each schema from information_schema.columns, FULL JOIN on table plus column, filter to one-sided rows, label with COALESCE. The add-rerun loop (matching name vanishes, renamed name_hr surfaces) is the proof the audit works.

The same information_schema.columns query powers deployment checks in every database: MySQL teams count columns per table before and after a release, Snowflake teams diff columns between schemas the same way. Since the view shape is standard, the lecture's join pattern ports directly.

19.9.1 Reading Column Lists From information_schema

Each half selects table and column names from the information_schema views filtered to one schema. Running each half on its own, ordered by table name, confirms the inputs: public contributes test1 with id2 among its columns, while human_resources contributes test1 with id. Trustworthy halves make a trustworthy join.

19.9.2 FULL JOIN on Table and Column Names

The two halves join fully on matching table name plus matching column name. Matches mean agreement and fall away in the next step, while one-sided rows survive as the differences worth reporting.

19.9.3 COALESCE Labels and Missing-Column Filter

COALESCE picks the first non-empty table and column names for display, aliased with simple names, with each side tagged as schema_one and schema_two. The filter keeps rows where either side is empty, so only genuinely missing columns reach the output, ordered by table and column for easy scanning.

19.9.4 Growing the Demo: Matching and Mismatching Columns

Identical name columns on both sides stay silent in the report, while a renamed name_hr on one side surfaces as a one-sided row. Each edit plus rerun sharpens the picture of which columns drifted and where, which is the day-to-day value of the query.

19.10 Schemas and Privileges

Schema rights decide who reaches what, and the model is strict: by default, users touch only objects in schemas they own. Opening someone else's schema takes two separate keys, and the demo turns each key alone to show it is not enough.

Two rights govern the gate. USAGE opens a schema so its objects can be reached. CREATE allows building new objects such as tables inside the schema. Holding one without the other gives only half the power.

GRANT USAGE ON SCHEMA private TO adam;
GRANT SELECT ON ALL TABLES IN SCHEMA private TO adam;
GRANT CREATE ON SCHEMA private TO adam;

USAGE opens the schema door, table grants such as SELECT open each table, and CREATE on the schema allows building inside it. Users start with access only to schemas they own, so every cross-schema reach needs an explicit grant.

The setup builds a schema called private with postgres as owner, plus a tiny table t1 holding a serial id primary key. A login role called adam plays the outsider. Connect as adam and try:

SELECT * FROM private.t1;

The answer is permission denied for schema private: Adam cannot even step through the door. Grant USAGE ON SCHEMA private TO adam, reconnect, and retry: the failure moves one level deeper to permission denied for the table itself. The schema door opens but the table stays shut. Add GRANT SELECT ON ALL TABLES IN SCHEMA private TO adam (read-only: no inserts, edits, or deletes), reconnect, and retry: the read succeeds and returns the empty set, since t1 holds no rows. Two locks, two keys, each failure proving which lock is still shut.

Creation rights follow the same two-level logic. Trying to build a table as adam fails:

CREATE TABLE private.abc (id int);

The denial this time is a schema-level refusal. A natural first guess, granting CREATE on all tables in the schema, is rejected with an invalid-privilege complaint, because CREATE on tables is not a valid table right. The real fix grants CREATE on the schema itself:

GRANT CREATE ON SCHEMA private TO adam;

The schema security view now shows both USAGE and CREATE beside adam. Reconnecting and retrying the CREATE TABLE succeeds, and the abc table appears under private with adam as its owner, since whoever builds an object owns it.

One default rounds out the picture and carries a warning. Every user starts out holding both USAGE and CREATE on the public schema. From a security point of view, that default deserves a plan: decide deliberately who should keep those public rights instead of leaving the open door unexamined.

Assumption: the adam role already exists and the demo reconnects as adam after each grant so the new rights take effect in a fresh session. Scope: GRANT SELECT ON ALL TABLES IN SCHEMA covers existing tables only; tables created later need a fresh grant or an ALTER DEFAULT PRIVILEGES rule. Revoking works symmetrically with REVOKE.

Picture a gated community: USAGE is the gate pass that lets Adam drive in, SELECT is the house key for one house, CREATE is the building permit for a new house. A gate pass without a house key leaves him in the driveway; a house key without a gate pass leaves him at the fence.

Three traps: granting USAGE and expecting tables to open (the table lock is separate); granting CREATE on tables instead of on the schema (rejected as an invalid privilege); and inheriting the open USAGE-plus-CREATE default on public without review, which lets every user build and read in the shared schema.

Q: USAGE was granted, so why is the table still closed? A: USAGE opens the schema door, while table rights such as SELECT open each table, so both grants are needed. The demo proves it: after USAGE alone the error moves from the schema to the table, and only the added SELECT grant lets the read succeed.

Exam note: USAGE reaches, CREATE builds, SELECT reads; schema-level and table-level locks are independent; CREATE is granted on the schema never on tables; and the open default on public must be deliberately reviewed.

Privilege views close the loop across databases: MySQL and SQL Server expose information_schema.table_privileges and schema_privileges showing who holds what, and Snowflake mirrors the model with USAGE ON SCHEMA plus SELECT ON ALL TABLES IN SCHEMA. Since the two-lock shape is shared, keep the lecture's private/adam walkthrough as the canonical example.

19.10.1 USAGE and CREATE Rights

USAGE means reaching objects inside a schema the user does not own. CREATE means building new objects inside it. Users start with access only to schemas they own, so every cross-schema reach needs an explicit grant of one or both rights.

19.10.2 Granting USAGE, Then Table Rights

GRANT USAGE ON SCHEMA private TO adam opens the schema, yet SELECT * FROM private.t1 still fails on table rights. GRANT SELECT ON ALL TABLES IN SCHEMA private TO adam then opens reads across the schema. The two-step failure-then-success run proves the schema lock and the table lock are independent.

19.10.3 Granting CREATE at Schema Level

CREATE TABLE private.abc as adam fails until the schema-level CREATE right arrives. The fix is GRANT CREATE ON SCHEMA private TO adam, never a table-level CREATE, which the system rejects as invalid. With both USAGE and CREATE beside adam in the security view, the build succeeds and adam owns the new table.

19.10.4 Default Rights on Public

Every user begins with USAGE and CREATE on public. That open default is convenient and risky at once, so access plans should review it on purpose rather than inherit it by accident.

Exam Guidance Summary

No mark split or question pattern is stated, so this section gathers the points stressed hardest for study focus. Schema-name uniqueness inside one database, the automatic public schema in every new database, and the database-dot-schema-dot-object address shape open the topic. CREATE SCHEMA, ALTER SCHEMA with RENAME TO and OWNER TO, DROP SCHEMA, and ALTER TABLE with SET SCHEMA form the core statement set, with the schema-qualified table name as the detail most likely to slip. The search path carries the deepest behavior: viewing it with SHOW search_path, changing it with SET search_path TO, keeping public listed, and letting the first listed schema win ties between same-named tables. Privileges close the topic: USAGE opens a schema, CREATE builds inside it, table grants such as SELECT open individual tables, the schema-level CREATE grant is the only valid way to allow builds, and the open USAGE-plus-CREATE default on public deserves a deliberate review.

Exam note: If time is short, drill the statement set (CREATE / ALTER RENAME / ALTER OWNER / DROP / SET SCHEMA), the search-path trio (SHOW, SET, first-wins), and the privilege trio (USAGE, CREATE, SELECT) with the private/adam failure sequence as the proof.

Key Industry Applications

An analytics company with close to 600 tables sorts them into schemas and grants each user group entry only to the schemas it needs, which keeps a giant estate both navigable and safe. Human resources tables live together in a human_resources schema while internal application data sits apart, so each audience meets exactly its own tables. Many users share one database without interference by working in separate schemas that still read as one database to applications. pgAdmin runs every schema create, rename, drop, ownership change, and table move both as clicks and as preview SQL, so daily administration and syntax learning happen in the same window. pg_dump freezes a schema with its rows into a dump file while psql replays that file, giving a portable copy-and-restore path for whole schemas. information_schema views expose tables, columns, functions, and procedures to queries, which powers audits such as the two-schema column comparison and the schema inventory listing.
