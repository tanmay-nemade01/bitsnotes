# Window Functions

27.1 Window Idea Compared With Aggregation

27.1.1 Aggregation flattens rows

Every query in this lecture answers one question first: should the output keep one row per detail record, or collapse records into group summaries? If you need per-row detail beside a group value, you need a window. If you need only the group value, an aggregate is enough.

An aggregate function — a function such as SUM, MIN, MAX, or AVG that takes many rows and returns one value — flattens data. Take three rows of detail. Apply SUM. The three rows collapse into one row. Take ten rows that belong to one group. They collapse into one row. Take twenty rows. They also collapse into one row. Take millions of rows. They still collapse into one row per group. The detail rows lose their separate identity in the output. Only the grouped value remains.

Think of a paper shredder with a counter on top. You feed in a stack of receipts. Out comes a single slip that reads "total: 412". The individual receipts are gone from the output. That is exactly what SELECT SUM(x) FROM t does, and what GROUP BY does once per group.

A group average (the mean of the values in one group) is the sum of the group divided by the count of the group. Written with \(x_i\) for the i-th value in a group of \(n\) rows, where \(n\) is a positive integer count of rows and \(x_i\) is a numeric value such as an import amount:

\[AVG = \frac{1}{n}\sum_{i=1}^{n} x_i\]

The symbol \(\sum_{i=1}^{n}\) means add up all \(n\) values from the first to the last, then divide by \(n\). The verbal description from the material is "average of all the values in the group".

Worked example — group average from scratch. Four yearly export figures for one country, in millions: 100, 200, 300, 400.

Step 1 — count the rows: \(n = 4\). Step 2 — add them: \(100 + 200 + 300 + 400 = 1000\). Step 3 — divide by the count: \(1000 / 4 = \mathbf{250}\).

The plain aggregate query returns exactly one row holding 250. The four input rows no longer appear anywhere in the output. Sense-check: 250 sits halfway between the smallest (100) and largest (400), which is what a symmetric set should give.

27.1.2 Windows keep row identity

A window function — a calculation across a set of table rows that are related to the current row — keeps every row. It still aggregates. It still partitions. It still summarizes. But it does not flatten. Each row keeps its own identity in the output. Group A, group B, and group C each keep their rows. The window adds a new column beside the detail.

The lecture frames this with the separate-room picture: place each group inside its own separate room. Inside that room the function can aggregate, move to the first record, move to the last record, or summarize the whole room. The rows stay visible, and the calculation sits next to them. That image — many rows go in, the same number of rows come out, with extra computed columns — is the core mental model for the full lecture. The mapping is direct: each room is one partition, the people inside are the rows of that partition, and the whiteboard value written beside every person is the window result.

A common interpretation is that windows "group" the same way aggregates do. The key correction is that windows never collapse rows. They compare the current row with the rest of its group. If an aggregate is a shredder, a window is a teaching assistant who walks down the rows of a classroom, reads each student's paper, and writes the class average in the margin of every paper. Every paper comes back. Every paper now carries one extra number.

The output row-count rule is the fastest way to tell the two apart: with aggregates, \(m\) input rows in a group produce 1 output row; with windows, \(m\) input rows produce \(m\) output rows. Time series dashboards use this shape because each date row stays on screen while running totals and moving averages appear beside it.

Scope: windows run after grouping, filtering, and joining are finished, so a window sees the result rows of the query, not the raw stored table. Assumption: the rows the function may see are exactly the rows of the current partition in the current result set — nothing outside the partition leaks in. What breaks: if you filter rows away with WHERE before the window runs, the window never sees them, and every partition value shifts.

Two traps show up at once here. First, writing GROUP BY country plus AVG(exports) and expecting the detail rows to survive — they will not, because GROUP BY collapses. Second, adding a window column and expecting fewer rows back — the row count never changes, so a 4326-row input still returns 4326 rows no matter how many window columns you add.

27.1.3 Formal shape of OVER

The basic syntax pairs any aggregate with an OVER clause:

SELECT country, year, exports,
       AVG(exports) OVER () AS avg_exports
FROM trades;

Here country is a text column, year is an integer column, and exports is a numeric column holding a money amount. AVG(exports) OVER () means average exports over the whole table because the parentheses after OVER are empty. No GROUP BY is needed. Every input row produces exactly one output row.

The keyword OVER is what turns an ordinary aggregate into a window function. Read AVG(exports) OVER () as "the average of exports, computed over the window described in the parentheses, and stamped onto each row". The empty parentheses mean the window is the full result set.

Dimension GROUP BY aggregate Window with OVER
Output rows per group of \(m\) rows 1 \(m\)
Detail columns beside the result Lost Kept
Needs GROUP BY Yes, for per-group values No, PARTITION BY splits instead
Typical use Report totals Compare each row against its group

When to pick which: pick GROUP BY when the question asks "one number per group". Pick a window when the question asks "each row plus its group number", such as each country's exports beside the world average.

Worked example — global mean beside detail rows with empty OVER. Three export values: 10, 20, 30.

Step 1 — the window is the whole set, so the function sees all three rows. Step 2 — average: \((10 + 20 + 30) / 3 = \mathbf{20}\). Step 3 — stamp 20 onto every row. Output: (10, 20), (20, 20), (30, 20).

Each row keeps its own exports value, and the shared mean 20 sits beside it. Sense-check: the mean column is identical on all three rows, which is exactly what one shared window should produce.

Q: What is a window, in plain terms? A: A window is the set of rows the function sees when it computes the value for the current row. With empty OVER parentheses the window is the full result set. With PARTITION BY the window is one group. With ORDER BY plus a frame clause the window is a slice around the current row.

Exam note: expect questions that ask for the difference between GROUP BY output row counts and window output row counts. State the row-count rule first (aggregates collapse, windows preserve), then give the example.

Aggregation collapses many rows into one value per group, while a window stamps a group value onto every row without collapsing. Next, the trades table gives both ideas a concrete dataset to work on.

27.2 Global Trades Dataset Setup

27.2.1 Source and table shape

Every query in this lecture runs against one practice table. Learn its five columns now and the rest of the lecture reads like variations on a theme: same table, same columns, new clause each time.

The practice data comes from Comtrade UN, the public trade statistics site. The prepared copy holds imports and exports by region, country, and year. Values are money amounts in dollars. The set is refined for teaching, so exact figures may differ from the live site. Browse the site, download a slice, and repeat every query below on a fresh slice to build fluency.

The table is created once:

CREATE TABLE trades (
  region  TEXT,
  country TEXT,
  year    INTEGER,
  imports NUMERIC(50, 0),
  exports NUMERIC(50, 0)
);

Here region is a text label such as Asia, country is a text label such as Japan, year is an integer calendar year, and imports and exports are large whole-number money amounts. The definition uses NUMERIC(50, 0), meaning up to 50 digits with zero decimal places — room for the largest national trade totals with no fractional cents.

A table definition (the CREATE TABLE statement that names each column and its type) is a contract: it fixes what each row must hold before any data arrives. This one promises two text columns (region, country), one integer (year), and two big whole-number money columns (imports, exports). Every later query trusts that contract — AVG(exports) works because exports is numeric, and PARTITION BY country works because country repeats across years.

Data arrives as a file of INSERT statements named trades dot SQL. Download it, open a query editor on the Northwind database, load the file, and run it. Refresh the object tree and the new trades table appears. A right-click refresh makes it visible if it does not show at once. PostgreSQL is the named database engine used for every query.

Dialect note: the shape transfers across engines with small renames. NUMERIC(50, 0) also works in MySQL, Snowflake, and Databricks (MySQL treats it like a wide DECIMAL). TEXT works in PostgreSQL and MySQL; in Snowflake and Databricks the same idea is written as VARCHAR or STRING.

Assumption: from here on, all import and export figures are read as millions unless a query says otherwise, because the material rewrites the stored values (see 27.2.3). Scope: exact digits come from a refined teaching copy, so compare your numbers against the live Comtrade UN site for shape (which region leads) rather than for exact equality.

27.2.2 Size and coverage

A full scan returns 4326 rows:

SELECT COUNT(*) FROM trades;
SELECT MIN(year), MAX(year) FROM trades;
SELECT DISTINCT region FROM trades ORDER BY region;
SELECT DISTINCT country FROM trades ORDER BY country;

The year range runs from 1988 to 2019. There are nine distinct regions: Africa, Asia, Caribbean, Central America, Europe, Middle East, North America, Oceania, and South America. There are 206 distinct countries, including Japan, Kenya, USA, and United Kingdom. The trades table with region, country, and year columns is the working set for everything that follows.

Worked example — USA country filter with year ordering. Ask for one country's full history:

SELECT * FROM trades WHERE country = 'USA' ORDER BY year;

That returns about 29 records starting near 1991, one row per year, each row holding that year's imports and exports. The WHERE keeps only USA rows; the ORDER BY lays them oldest-first so running calculations later meet years in sequence. Sense-check: about 29 rows for years 1991 through 2019 matches one row per year, so no years are silently missing.

One mapping quirk to know: in this teaching copy USA appears under a South America region label, and a Vietnam row appears where it should not. Treat those as data entry quirks in a teaching copy, not as facts about the world. Queries that group by region inherit the quirk, which is why South America looks oversized in some grouped runs below.

The two-by-three analogy used in the material helps here: two text columns plus three numeric columns describe many tables. A school district table could hold district name, school name, year, total students, passes, and failures. A forest table could hold region, country, year, tree counts planted, and tree counts lost. The same window patterns apply to all of them — swap the column names and every query in this lecture still runs.

27.2.3 Readable millions

Raw values are hard to compare because they carry many digits. Dividing by one million and rounding to two decimals makes them readable:

SELECT imports / 1000000.0 AS imports_m, exports / 1000000.0 AS exports_m
FROM trades;
SELECT ROUND(imports / 1000000.0, 2) AS imports_m FROM trades;

The divisor 1000000.0 is one million written with a decimal point so division keeps decimals instead of truncating to whole numbers. ROUND(value, 2) keeps two digits after the point. The material then rewrites the stored values permanently:

UPDATE trades SET imports = imports / 1000000;
UPDATE trades SET exports = exports / 1000000;
SELECT * FROM trades;

After the update every value is in millions. Because the columns are NUMERIC(50, 0) the stored results are whole numbers. From this point onward in the material, all import and export figures are read as millions.

Two traps in one statement. First, imports / 1000000 with whole-number columns truncates in some engines, while imports / 1000000.0 keeps decimals — the .0 matters whenever you need fractional millions. Second, the UPDATE rewrites stored data permanently, so run it once; running it twice would divide by a million twice and shrink every figure a million-fold.

Exam note: when a question asks for millions, show the division and the ROUND in the query rather than formatting only on screen.

The trades table holds 4326 rows across 9 regions, 206 countries, and years 1988 to 2019, with money stored in millions. With the dataset fixed, the next step is reading its global shape with plain aggregates.

27.3 Aggregate Queries Before Windows

27.3.1 Global bands

Before any window appears, the lecture tells the global story first: how small is the smallest trader, how big is the biggest, and where does the average sit? Every window later is just one of these numbers stamped beside detail rows.

The first story is the global band: smallest, largest, and mean value across all countries and years. The plain-language request is "minimum, maximum, and average of imports and exports globally". With \(n = 4326\) rows, where each \(x_i\) is one row's import or export figure:

\[MIN = \min_i(x_i), \quad MAX = \max_i(x_i), \quad AVG = \frac{1}{n}\sum_{i=1}^{n} x_i\]

The symbol \(\min_i\) means take the smallest value across all rows, \(\max_i\) the largest, and the average is the familiar sum divided by count.

SELECT MIN(imports) AS min_imp, MAX(imports) AS max_imp, AVG(imports) AS avg_imp,
       MIN(exports) AS min_exp, MAX(exports) AS max_exp, AVG(exports) AS avg_exp
FROM trades;

Worked example — global band in one row. The query returns a single row with six numbers. One run shows a maximum import near 2611432490157 in raw units and a mean import near 73325290068 in raw units, which become about 2611432 and 73325 in millions. The exact digits matter less than the band idea: the minimum, maximum, and mean across 206 countries describe the full spread, from the tiniest trader to the largest economy, with the mean marking the center. Sense-check: the mean sits well below the maximum, which is expected when a few giant traders pull the top far above the typical country.

Wrapping with ROUND with zero decimals cleans the display:

SELECT ROUND(MIN(imports), 0) AS min_imp, ROUND(MAX(imports), 0) AS max_imp,
       ROUND(AVG(imports), 0) AS avg_imp
FROM trades;

ROUND(value, 0) drops all decimals, so million-scale figures print as plain integers.

27.3.2 Grouped bands by region

Adding a region column and GROUP BY gives one band per region:

SELECT region,
       ROUND(MIN(imports), 0) AS min_imp,
       ROUND(MAX(imports), 0) AS max_imp,
       ROUND(AVG(imports), 0) AS avg_imp
FROM trades
GROUP BY region
ORDER BY 3 DESC;

Here region is the grouping key, ORDER BY 3 DESC sorts by the third output column from large to small, and each output row is one region. Region averages with aggregate bands are the baseline that later window partitions will mirror row by row.

Worked example — regional import bands with descending maximum. The query returns nine rows, one per region, each holding that region's minimum, maximum, and mean imports. Sorting by the maximum shows South America on top for imports in this copy, followed by Asia and Europe, with Caribbean also high — a ranking inflated by the teaching-copy quirk that parks USA rows under South America. Switching the aggregate to exports puts Asia on top. Adding a year filter keeps Asia on top for year 2010 onward and for year 2015 onward:

SELECT region, ROUND(AVG(exports), 0) AS avg_exp
FROM trades
WHERE year >= 2010
GROUP BY region
ORDER BY 2 DESC;

The WHERE runs before grouping, so only recent years feed each region's mean. Sense-check: Asia leading both the full-period and recent-period export tables is consistent — the same set of large exporters drives both.

One question leads to the next: which countries drive the South America export figure. List them directly:

SELECT DISTINCT country FROM trades WHERE region = 'South America';

That returns seven countries in this copy, including Argentina, Uruguay, Ecuador, Guyana, and Haiti. Regional import and export bands of this kind feed trade briefings that ask which region buys most and which region sells most.

A minimum of zero means some country-year row in that region recorded no imports — a real data point, possibly a missing report, not a broken query. The trap is "fixing" the query when the data is what it is; instead, pull the detail rows for that region and year to confirm.

Q: Why does a regional minimum show zero? A: A zero minimum means at least one country-year row in that region recorded zero imports. It is a data point, not an error in the query. Check the detail rows for that region and year to confirm.

Plain aggregates give the global band in one row and the per-region bands in nine rows — the numbers every later window will reuse. The next step adds grand-total rows to grouped output without writing a second query.

27.4 ROLLUP CUBE and GROUPING SETS

27.4.1 ROLLUP with one column

Grouped queries answer "one row per group", but reports usually need one more row: the grand total at the bottom. ROLLUP adds that row without a second query.

GROUP BY turns many rows into one row per group. Reports often need the per-group rows plus one grand summary row. ROLLUP adds that summary row in a single query. The plain-language request is "average imports per region plus the overall average". With \(G\) regions indexed by \(g\), where \(n_g\) counts rows in region \(g\) and \(x_i\) is one import figure:

\[a_g = \frac{1}{n_g}\sum_{i \in g} x_i, \quad a_{all} = \frac{1}{n}\sum_{i=1}^{n} x_i\]

Each \(a_g\) averages only its own region's rows; \(a_{all}\) averages all \(n\) rows across regions.

SELECT region, ROUND(AVG(imports), 2) AS avg_imp
FROM trades
GROUP BY ROLLUP (region);

Worked example — ROLLUP grand average with NULL summary row. The query returns nine region rows plus one extra row where region is NULL. That NULL row is not missing data — it is the marker for the grand average, about 73.33 in billions in the worked run, sitting beside per-region values such as North America near 38 and South America near 300 in the same units. Without ROLLUP two queries would be needed: one grouped query plus one ungrouped grand-average query. With ROLLUP one query returns both. Sense-check: the grand average falls between the smallest and largest region averages, which must hold for any mean of group means weighted by row counts.

Sort to taste:

SELECT region, ROUND(AVG(imports), 2) AS avg_imp
FROM trades
GROUP BY ROLLUP (region)
ORDER BY region;

With ascending region order the NULL summary row sorts last. With descending order on the average column the grand mean lands in rank order among regions, which shows where the overall mean sits in the distribution.

The NULL trap matters: if a real region value could itself be NULL, the summary row becomes ambiguous. The portable fix is GROUPING(region), which returns 1 on summary rows and 0 on real data rows — supported in PostgreSQL, Snowflake, Databricks, and MySQL 8 (MySQL uses GROUPING() the same way).

Exam note: when a question asks for per-group rows plus a grand total or grand mean in one statement, reach for ROLLUP and name the NULL summary row in the answer.

27.4.2 ROLLUP with two columns

ROLLUP accepts more than one column. Each extra column adds one more summary level, building a hierarchy from detail up to grand total. The worked filter uses four countries: USA, Argentina, Singapore, and Brazil.

SELECT region, country, ROUND(AVG(imports), 2) AS avg_imp
FROM trades
WHERE country IN ('USA', 'Argentina', 'Singapore', 'Brazil')
GROUP BY ROLLUP (region, country);

Worked example — three levels in one result. The output holds three levels at once. Detail rows hold one region plus one country. Middle rows hold one region with NULL country and give that region subtotal average. The first row has NULL region and NULL country and holds the overall average of the filtered set, about 482.35 in the run. In the run South America, Europe, and Africa each get their own subtotal row. Sense-check: every subtotal sits between its own detail rows' values and the grand average only if the groups are similar in size — otherwise the grand average leans toward the biggest group, which is correct weighting, not an error.

A front-end chart can bind directly to this shape: detail rows feed the bars and subtotal rows feed the group headers. Single-query report feeds for web applications use this shape to avoid extra round trips between client and server.

27.4.3 CUBE for all combos

ROLLUP builds a hierarchy. CUBE builds every combo. With \(k\) columns CUBE builds \(2^k\) grouping sets: each column is either in or out, and the two choices multiply. With three columns C1, C2, C3 the sets are (C1, C2, C3), (C1, C2), (C1, C3), (C2, C3), (C1), (C2), (C3), and the grand total. The verbal description is "all possible grouping sets for the listed columns". The count is:

\[sets = 2^k\]

where \(k\) is the count of columns inside CUBE. For \(k = 2\) that gives 4 sets: both columns, each column alone, and the grand total.

The worked query uses region and country with a four-country filter:

SELECT region, country, ROUND(AVG(imports) / 1000000000.0, 2) AS avg_b
FROM trades
WHERE country IN ('USA', 'France', 'Germany', 'Brazil')
GROUP BY CUBE (region, country);

Worked example — every slice at once. The divisor 1000000000.0 converts millions to billions for display. Output holds the grand average on top, then region-plus-country detail rows such as Europe plus France and South America plus Brazil, then region-only rows for South America and Europe, then country-only rows for USA, Germany, France, and Brazil. One statement replaces a stack of separate grouped queries. Sense-check: the row with both columns NULL is the grand average and must equal the plain ungrouped AVG(imports) over the same four-country filter — run that single aggregate to confirm.

Use CUBE when the report needs slicing by every combo rather than one fixed hierarchy.

Dialect note: CUBE (and ROLLUP and GROUPING SETS) work in PostgreSQL, Snowflake, Databricks, and MySQL 8 with the same syntax. In Snowflake and Databricks the four sets above can also be reached through the equivalent GROUP BY ALL-style listings, but CUBE itself is portable.

27.4.4 GROUPING SETS for hand-picked combos

GROUPING SETS lists exactly the combos wanted, in the order wanted. Empty parentheses mean the grand total. The worked rewrite of the CUBE query is:

SELECT region, country, ROUND(AVG(imports) / 1000000000.0, 2) AS avg_b
FROM trades
WHERE country IN ('USA', 'France', 'Germany', 'Brazil')
GROUP BY GROUPING SETS ((), (region, country), (region), (country));

Swapping the last two entries puts country rows above region rows without changing the math. That ordering control is the advantage over CUBE. A single query replaces stacked union queries: the equivalent without this feature would be three SELECT statements joined by UNION ALL — one grand-average SELECT with no grouping columns, one grouped by region and country, and one grouped by region alone. GROUPING SETS performs that union internally. Use it for time series rollups where only some levels matter.

Dialect note: the UNION ALL rewrite is the portable fallback on engines with partial support, and it runs everywhere including older MySQL. Where GROUPING SETS exists (PostgreSQL, Snowflake, Databricks, MySQL 8), prefer it: one scan instead of three, and the ordering follows the listed sets.

27.4.5 Cost check with EXPLAIN

Grouping choices have costs. Prefix the query with EXPLAIN or EXPLAIN ANALYZE to see the plan:

EXPLAIN SELECT region, country, ROUND(AVG(imports), 2)
FROM trades
WHERE country IN ('USA', 'France', 'Germany', 'Brazil')
GROUP BY GROUPING SETS ((), (region, country), (region), (country));

The plan in the material uses a Mixed Aggregate over a sequential scan of trades with the four-country filter, about 115 rows in and 99 rows out, with hash keys on region and country. Toggling the planner switch changes the strategy:

SHOW enable_hashagg;
SET enable_hashagg = OFF;
EXPLAIN ANALYZE SELECT region, country, ROUND(AVG(imports), 2)
FROM trades
WHERE country IN ('USA', 'France', 'Germany', 'Brazil')
GROUP BY GROUPING SETS ((), (region, country), (region), (country));
SET enable_hashagg = ON;

Worked example — reading the two plans. With the switch off the plan uses a Group Aggregate with planning near 0.201 ms and execution near 11.686 ms. With the switch on the Mixed Aggregate plan shows planning near 0.102 ms and execution near 1.272 ms, so the mixed plan wins on this data — roughly nine times faster at execution. The table has no indexes in the material, so adding an index on the filter column or the grouping columns could lower times further depending on the filter. Sense-check: planning time stays under a millisecond in both plans, so the gap is all execution — the sort-based Group Aggregate loses to hashing on this small filtered set.

EXPLAIN shows the plan without running the query; EXPLAIN ANALYZE runs it and reports real timing. Always restore the switch afterward (SET enable_hashagg = ON), or later queries in the session will keep the slower plan.

Exam note: when asked how to compare grouping strategies, show EXPLAIN ANALYZE output for both settings and quote planning time plus execution time.

Scope: the timing verdict (Mixed Aggregate wins) holds for this small filtered set with no indexes. Assumption: row counts stay near 115 in and 99 out. What breaks: on a far larger table, or with an index on country, the ranking can flip — always re-measure rather than quoting these milliseconds as universal.

ROLLUP adds hierarchical subtotals, CUBE adds every combo, and GROUPING SETS lists exactly the combos wanted — all in one scan. Next, FILTER puts different row subsets into different columns of the same output row.

27.5 FILTER Clause Selective Aggregation

27.5.1 Syntax and meaning

What if one output row needs three different averages — all years, old years, recent years — side by side? A plain WHERE can only keep one subset at a time. FILTER gives each aggregate its own private WHERE.

The FILTER clause — an optional WHERE-like condition attached to one aggregate — passes only chosen rows into that aggregate. Other aggregates in the same SELECT keep their own rows. Without it, mixed conditions would need common table expressions, self joins, or several round trips. The syntax is:

SELECT region,
       AVG(exports) AS avg_all,
       AVG(exports) FILTER (WHERE year < 1995) AS avg_old,
       AVG(exports) FILTER (WHERE year >= 1995) AS avg_latest
FROM trades
GROUP BY ROLLUP (region);

Here avg_all uses every year, avg_old uses only rows with year below 1995, and avg_latest uses rows with year 1995 onward. Each FILTER holds its own WHERE inside parentheses. The top row with NULL region is the grand summary from ROLLUP, and each FILTER applies at that level too. One statement returns three side-by-side means per region. The verbal description is "average exports for all periods, for old years, and for latest years".

A filtered average (the mean over only the rows that pass the FILTER condition) follows the same sum-over-count shape on a smaller row set. For the old bucket with row set \(S_{old} = \{i : year_i < 1995\}\), where \(x_i\) is the export value and \(|S_{old}|\) counts rows in the old bucket:

\[AVG_{old} = \frac{1}{|S_{old}|}\sum_{i \in S_{old}} x_i\]

The symbol \(|S_{old}|\) means the number of rows in the old-year set. The same shape with \(S_{latest} = \{i : year_i \ge 1995\}\) gives \(AVG_{latest}\).

Worked example — old versus latest export means with FILTER. Suppose a region holds four rows: exports 100 and 200 before 1995, 300 and 400 from 1995 onward.

Step 1 — avg_all sees all four: \((100 + 200 + 300 + 400) / 4 = \mathbf{250}\). Step 2 — avg_old sees only the first two: \((100 + 200) / 2 = \mathbf{150}\). Step 3 — avg_latest sees only the last two: \((300 + 400) / 2 = \mathbf{350}\).

One output row carries 250, 150, 350 side by side. Sense-check: the all-years mean (250) falls between the old mean (150) and the latest mean (350), which must hold whenever the two buckets partition the full set.

Dialect note: FILTER is native in PostgreSQL, Snowflake, and Databricks/Spark SQL with exactly this syntax. MySQL does not support FILTER — the portable rewrite is AVG(CASE WHEN year < 1995 THEN exports END), which feeds NULLs (ignored by AVG) for rows outside the bucket. Snowflake additionally offers PIVOT for the same side-by-side layout, but FILTER stays closer to the lecture query.

27.5.2 Why it matters

FILTER solves the case where columns in one output row need different input rows. A plain WHERE would cut rows for every column at once. FILTER cuts rows per aggregate. The old-versus-latest split above is the canonical demo: one grouped scan, three means, no joins. Later windows reuse the same FILTER idea inside OVER partitions — for example, a partitioned average over only recent years. Cohort reports that compare all-time, legacy-period, and recent-period means in one row per segment use FILTER for exactly this reason.

The classic trap is writing WHERE year < 1995 and wondering why the "latest" column vanished: WHERE removes rows for every aggregate, while FILTER removes them per aggregate. A second trap is NULL handling — FILTER drops non-matching rows before aggregation, while the CASE WHEN rewrite feeds NULLs that most aggregates skip; both give the same mean, but COUNT(*) versus COUNT(exports) would differ, so match the rewrite to the aggregate.

FILTER gives each aggregate its own row subset, so one grouped scan returns all-period, old-period, and recent-period means side by side. With per-column subsets in hand, the next step keeps detail rows alive with OVER and PARTITION BY.

27.6 OVER PARTITION BY and ORDER BY Basics

27.6.1 OVER with no partition

The simplest window has no PARTITION BY at all: the whole result set is one window, so every row gets stamped with the same global value. This is the fastest way to put "you are here" context beside each record.

An aggregate plus OVER with empty parentheses sees the whole table. The worked global mean of exports is about 72443407670 in raw units. Placing it beside detail rows gives instant context:

SELECT country, year, imports, exports,
       AVG(exports) OVER () AS avg_exports
FROM trades;

Every row carries the same avg_exports value. One row might show exports of 3758850935 beside the global mean 7244340760 in the same units used in that run. The reader compares the row against the world in one glance. A plain GROUP BY cannot produce this shape because it would collapse the detail rows. The verbal description is "current exports beside average exports for the whole set".

Worked example — global mean beside detail rows. Three rows with exports 10, 20, 30 and an empty OVER window.

Step 1 — the window covers all three rows, so the mean is \((10 + 20 + 30) / 3 = 20\). Step 2 — stamp 20 onto row 1: (10, 20). Step 3 — stamp 20 onto rows 2 and 3: (20, 20), (30, 20).

Three rows in, three rows out, each carrying its own value plus the shared mean. Sense-check: the mean column never varies, which confirms a single whole-table window.

Q: Why does the same average repeat on every row? A: The window has no PARTITION BY, so every row shares one window: the full table. The function computes once over that window and stamps the result on each row. Add PARTITION BY to give each group its own value.

27.6.2 PARTITION BY a column

PARTITION BY splits the window into one group per value. The average then restarts per group:

SELECT country, year, imports, exports,
       AVG(exports) OVER (PARTITION BY country) AS avg_by_country
FROM trades;

A partitioned average (the mean restarted inside each partition) applies the group-average formula separately per group. For country \(c\), where \(n_c\) counts rows for that country and \(x_i\) is an export value:

\[AVG_c = \frac{1}{n_c}\sum_{i \in c} x_i\]

The symbol \(i \in c\) means "rows belonging to country \(c\)". Each partition gets its own \(n_c\) and its own sum — the lecture's separate-room picture, one room per country.

Afghanistan rows share the Afghanistan mean. Albania rows share the Albania mean. Andorra rows share the Andorra mean. Scanning down the output, the average column changes exactly at each country boundary. Comparing exports against the same-country mean is now direct. The verbal description is "average exports for each respective country".

Worked example — two partitions, two means. Country A exports: 100, 200. Country B exports: 300, 400, 500.

Step 1 — partition A mean: \((100 + 200) / 2 = \mathbf{150}\), stamped on both A rows. Step 2 — partition B mean: \((300 + 400 + 500) / 3 = \mathbf{400}\), stamped on all three B rows. Step 3 — output has five rows: (A, 100, 150), (A, 200, 150), (B, 300, 400), (B, 400, 400), (B, 500, 400).

Sense-check: the mean changes exactly at the A-to-B boundary and never mixes values across the boundary — partitions are sealed rooms.

27.6.3 PARTITION BY an expression

The partition key can be an expression, not only a bare column. The worked variant partitions by a year condition:

SELECT country, year, exports,
       AVG(exports) OVER (PARTITION BY (year <= 2000)) AS avg_by_era
FROM trades;

Rows with year 2000 or earlier share one mean. Later rows share another. In the run the Afghanistan-side value near 819 reflects its era bucket. The lesson: OVER accepts a column name, a list of columns, or an expression. Use a column for per-group means. Use an expression for per-era or per-flag means — for example PARTITION BY (year <= 2000), PARTITION BY region, year, or PARTITION BY CASE WHEN exports > 1000 THEN 'big' ELSE 'small' END. No partition means whole-table means.

Dialect note: expression partitions work identically in PostgreSQL, Snowflake, Databricks, and MySQL 8. One engine difference: MySQL 8 requires the window's ORDER BY expression to be orderable the same way, and boolean expressions like year <= 2000 evaluate to 0/1 — the partition still splits into two groups, just labeled 0 and 1.

27.6.4 ORDER BY inside the window

ORDER BY inside OVER sorts rows within each partition before the function sees them. The worked MIN and MAX demo uses two countries and years after 2001:

SELECT country, year, exports,
       MIN(exports) OVER (PARTITION BY country ORDER BY year) AS run_min,
       MAX(exports) OVER (PARTITION BY country ORDER BY year) AS run_max
FROM trades
WHERE country IN ('USA', 'France') AND year > 2001;

The clause PARTITION BY country makes one group per country. ORDER BY year sorts each group by year. Then the aggregate runs cumulatively: at each row it sees the current row plus all earlier rows in that partition. That default cumulative behavior is the key point of this section and is explained further under frames — the unwritten default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.

Worked example — running maximum across an ordered country partition. The USA walk-through in the material uses exports 693068 in 2002, 724737 in 2003, and larger values after.

Step 1 — at the first USA row the window holds one row, so MIN and MAX both equal 693068. Step 2 — at the second row the window holds 693068 and 724737, so MIN stays 693068 while MAX becomes 724737. Step 3 — at the third row the window holds three values and MAX moves to the largest of the three. By 2007 the window holds all USA rows from 2002 through 2007 and MAX reports the largest among them.

France rows behave the same way starting near 3048 on their first row. An Excel sheet in the material draws these growing windows row by row. Sense-check: the running MAX never decreases as years advance — a cumulative maximum over a growing set can only stay flat or rise.

Scope: always include ORDER BY here when row order matters. Assumption: without it the engine uses input order, which may look random, and the "running" columns become meaningless. What breaks: ties in the ordering column interact with the RANGE default (peer rows join the frame together) — use ROWS framing from 27.7 when position, not peer value, must decide.

Exam note: when a question asks for running minimum or running maximum over time, write PARTITION BY the entity plus ORDER BY the time column and state the cumulative default.

Empty OVER stamps one global value on every row, PARTITION BY restarts the value per group, and ORDER BY turns the window cumulative. Next, explicit frames shrink the window from "everything so far" to a sliding slice.

27.7 Sliding Windows Frames ROWS Versus RANGE

27.7.1 Moving average with ROWS BETWEEN

Cumulative windows grow without bound — by the last row the "running" average covers the whole history. A frame cuts the window down to a sliding slice, such as one row on each side of the current row.

A frame — the slice of rows around the current row that the function may see — turns a cumulative window into a sliding one. The keywords are ROWS, BETWEEN, PRECEDING, FOLLOWING, and CURRENT ROW. The moving-average demo asks for the mean of the prior row, the current row, and the next row within each country:

SELECT country, year, exports,
       AVG(exports) OVER (
         PARTITION BY country ORDER BY year
         ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
       ) AS moving_avg
FROM trades
WHERE country IN ('USA', 'France') AND year BETWEEN 2001 AND 2010;

A three-point moving average (the mean of the prior, current, and next values) smooths a series by averaging each point with its neighbors. For row \(t\) with values \(x_{t-1}, x_t, x_{t+1}\), where \(x_t\) is the current row's exports and the neighbors are the adjacent years in the same partition:

\[MA_t = \frac{x_{t-1} + x_t + x_{t+1}}{3}\]

At the edges the frame shrinks: the first row of a partition has no prior row, so its frame holds only current plus next (divide by 2); the last row holds prior plus current (divide by 2).

Worked example — three-row moving average with preceding and following. At a middle France row with current exports 304892, prior 289599, and next 358132:

Step 1 — collect the frame: (289599, 304892, 358132). Step 2 — add: \(289599 + 304892 + 358132 = 952623\). Step 3 — divide by 3: \(952623 / 3 = \mathbf{317541}\).

At the first row of the partition the frame holds only current plus next, so the divisor drops to 2. Sense-check: the smoothed value 317541 sits between the smallest (289599) and largest (358132) frame members — a mean always lands inside its inputs' range.

Change the offsets to widen the slide: 10 PRECEDING AND 10 FOLLOWING takes ten rows each side. Add EXCLUDE CURRENT ROW to drop the center:

SELECT country, year, exports,
       AVG(exports) OVER (
         PARTITION BY country ORDER BY year
         ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING EXCLUDE CURRENT ROW
       ) AS moving_avg_no_center
FROM trades
WHERE country IN ('USA', 'France') AND year BETWEEN 2001 AND 2010;

In the USA run the plain three-row version repeats 693068 across the first rows while the excluded-center version shows 693068 then 724737 then 6930 on successive rows, because the center value no longer counts. Three-point and multi-point moving means of this form smooth time series such as sales, traffic, and prices.

Dialect note: EXCLUDE CURRENT ROW (and EXCLUDE GROUP, EXCLUDE TIES, EXCLUDE NO OTHERS) is supported in PostgreSQL and Snowflake. Databricks/Spark SQL and MySQL 8 do not support EXCLUDE — the portable rewrite averages the two neighbors explicitly, e.g. (LAG(x) OVER w + LEAD(x) OVER w) / 2.0.

27.7.2 Frame vocabulary

Frames need a small vocabulary. UNBOUNDED PRECEDING means everything above the current row. UNBOUNDED FOLLOWING means everything below the current row. CURRENT ROW means the row being computed. A number plus PRECEDING or FOLLOWING means that many rows away. Zero FOLLOWING adds nothing below. The general shape is:

ROWS BETWEEN <start> AND <end>
RANGE BETWEEN <start> AND <end>

Common starts and ends are UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING, and UNBOUNDED FOLLOWING. If no frame is written and ORDER BY is present, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, meaning current row plus everything above it. If no ORDER BY and no frame and no partition are written, the frame is the whole set. The Excel walk in the material numbers rows 1 to 10 and shades the frame at row 3, row 4, row 5, row 10, and other positions for each variant — shaded frame rows show sliding window contents, and redrawing that shading by hand once fixes the vocabulary permanently.

27.7.3 Seeing frames with array aggregate

The array_agg function collects frame contents into a visible list, which makes frames concrete. With generate_series producing test rows, each query below shows exactly which values the frame holds:

SELECT x, array_agg(x) OVER (ORDER BY x) AS frame_contents
FROM generate_series(1, 3) AS g(x);

Output is 1 then (1, 2) then (1, 2, 3), which matches the default of UNBOUNDED PRECEDING through CURRENT ROW. Changing the frame changes the lists:

SELECT x, array_agg(x) OVER (
  ORDER BY x ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
) AS frame_contents
FROM generate_series(1, 3) AS g(x);

Output is (1, 2, 3) then (2, 3) then (3). A whole-table frame with no ORDER BY repeats (1, 2, 3) on every row:

SELECT x, array_agg(x) OVER () AS whole,
       SUM(x) OVER () AS total,
       x / SUM(x) OVER () AS share
FROM generate_series(1, 3) AS g(x);

A share of total (one row's fraction of the whole column) divides the row by the grand sum. For value \(x\), where the denominator sums the whole set:

\[share = \frac{x}{\sum_j x_j}\]

The denominator \(\sum_j x_j\) adds every row's value once. Here total is 6 on every row because 1 plus 2 plus 3 equals 6. Casting to float gives shares 0.16, 0.33, and 0.50. The verbal description is "total sum of the column and each row proportion of that total in one statement". This single-statement total-plus-share pattern is one of the most reused window idioms.

Worked example — total and share in one statement. Values 1, 2, 3.

Step 1 — grand total: \(1 + 2 + 3 = \mathbf{6}\), stamped on every row. Step 2 — row shares: \(1/6 \approx \mathbf{0.16}\), \(2/6 \approx \mathbf{0.33}\), \(3/6 = \mathbf{0.50}\). Step 3 — add the shares: \(0.16 + 0.33 + 0.50 \approx \mathbf{1.00}\).

Sense-check: shares of a total must sum to 1 (up to rounding) — if they do not, the denominator missed rows.

Dialect note: generate_series is PostgreSQL syntax. Snowflake uses TABLE(FLATTEN(...)) or a small VALUES list for the same demo; Databricks uses SEQUENCE(1, 3) or EXPLODE(SEQUENCE(1,3)); MySQL 8 has no series generator, so a four-row VALUES CTE (as in 27.10.7) plays the same role.

27.7.4 ROWS versus RANGE with duplicates

ROWS counts physical rows. RANGE groups peer rows that share the same ORDER BY value and takes the whole peer group at once. The demo builds duplicates with integer division:

SELECT x, x / 3 AS y,
       array_agg(x) OVER (ORDER BY x ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS rows1,
       array_agg(x) OVER (ORDER BY x RANGE BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS range1
FROM generate_series(1, 10) AS g(x);

Here x runs 1 to 10 with unique values, so ROWS and RANGE agree. The difference appears when ordering by the duplicate column y, which holds 0, 0, 1, 1, 1, 2, 2, 2, 3, 3. ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING takes exactly one neighbor each side: at a middle row the list might read (0, 0, 1). RANGE with the same offsets takes the full peer groups: the list grows to (0, 0, 1, 1, 1) because every row sharing the boundary value joins the frame.

Scope: the rule to memorize is that when the ORDER BY key has duplicates, RANGE pulls the entire duplicate group while ROWS processes neighbors one at a time. Assumption: RANGE offsets compare ORDER BY values (value-based), ROWS offsets count positions (position-based). What breaks: numeric RANGE offsets on date or timestamp keys need INTERVAL units in PostgreSQL (RANGE BETWEEN INTERVAL '1 day' PRECEDING AND CURRENT ROW), and MySQL 8 supports only UNBOUNDED and CURRENT ROW frames with RANGE — numbered RANGE offsets require ROWS mode there.

Pick RANGE for peer-group logic (all rows sharing a year move together) and ROWS for positional logic (exactly one neighbor each side).

Frames turn cumulative windows into sliding ones: ROWS counts positions, RANGE pulls whole peer groups, and array_agg makes any frame's contents visible. Next, named windows let several functions share one frame definition.

27.8 Named Windows WINDOW Clause and Frame Rules

27.8.1 One named window reused

Copying a long OVER block into five columns works once, then becomes a maintenance trap: changing the frame means editing all five copies. A named window defines the partition, order, and frame a single time and lets every column share it.

The WINDOW clause — a named window definition placed after WHERE and GROUP BY — lets several aggregates share one partition, ordering, and frame. It also lets one query hold several differently defined windows. The worked MIN plus MAX per year for USA from 2000 onward uses one shared name W:

SELECT country, year, exports,
       MIN(exports) OVER W AS win_min,
       MAX(exports) OVER W AS win_max
FROM trades
WHERE country = 'USA' AND year >= 2000
WINDOW W AS (ORDER BY year);

Worked example — shared named window for minimum and maximum. With only ORDER BY year and no explicit frame, the default RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW applies, so each row's frame holds that year plus all earlier USA years.

Step 1 — at the 2001 row the frame holds one row, so MIN and MAX both show the single export near 729080. Step 2 — at the next row the frame holds two rows with exports 729080 and 693068, so MIN drops to 693068 while MAX stays at 729080. Step 3 — at the third row the frame holds three rows and MAX moves to the largest of the three. At the fourth row MAX moves again.

The same W feeds both aggregates, so one definition drives two columns. Sense-check: at every row MIN is less than or equal to MAX — if a row ever shows MIN above MAX, the two columns read different frames and the shared definition broke.

Think of W like a saved view of the window: define once, reference many times. A saved window defined once and referenced many times keeps queries short and guarantees every column reads the same rows.

Dialect note: the WINDOW clause is portable — PostgreSQL, Snowflake, Databricks/Spark SQL, and MySQL 8 all accept WINDOW w AS (...) with the same placement after WHERE, GROUP BY, and HAVING.

27.8.2 Central frame edits

Because both aggregates reference W, editing the frame in W changes both columns at once. The working frame from the prior section is:

WINDOW W AS (ORDER BY year ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

Changing it to one row up and two rows down gives a sliding shape for both MIN and MAX:

WINDOW W AS (ORDER BY year ROWS BETWEEN 1 PRECEDING AND 2 FOLLOWING)

Rerun the same SELECT and both output columns shift to the new sliding frame. That single-edit propagation is the practical payoff of named windows. Each named window can carry its own PARTITION BY, its own ORDER BY, and its own frame, so one query can mix a cumulative window W with a sliding window W2 without repeating long OVER blocks:

SELECT country, year, exports,
       MAX(exports) OVER W AS cumul_max,
       AVG(exports) OVER W2 AS slide_avg
FROM trades
WHERE country = 'USA' AND year >= 2000
WINDOW W AS (ORDER BY year),
       W2 AS (ORDER BY year ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING);

Scope: a name defined in WINDOW can be referenced by any number of OVER clauses, and one query can define several names. Assumption: each name carries a complete triple — partition, order, frame — and columns sharing a name always read identical rows. What breaks: editing W to test a new frame silently changes every column that references it, so re-check each column's numbers after a central edit instead of assuming only one column moved.

27.8.3 Frame order rules and errors

Two ordering rules cause most errors. First, UNBOUNDED PRECEDING must come first. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW is valid. ROWS BETWEEN CURRENT ROW AND UNBOUNDED PRECEDING fails with a frame-bound error because the start cannot follow the end — the frame's start edge must sit at or above its end edge. Second, a window name that already carries a frame cannot be copied with extra frame pieces inside OVER. The failing shape puts a frame both in WINDOW W and in OVER W plus ROWS BETWEEN. The fix is to keep the frame in exactly one place: either fully inside WINDOW W with bare OVER W references, or fully inside each OVER with a frameless WINDOW W. After the fix the query runs and both aggregates follow the single frame.

Three frame errors and their fixes in one place. Start-after-end (BETWEEN CURRENT ROW AND UNBOUNDED PRECEDING) fails — swap the edges. Double frame definition (frame in both WINDOW and OVER) fails — keep it in one place. Missing ORDER BY with a ROWS frame runs but scrambles positions — add the ordering column.

Exam note: when a frame query fails, check start-before-end order first, then check that the frame is defined only once.

Named windows define the partition, order, and frame once and share them across columns, with central edits propagating everywhere. Next, ranking functions turn ordered windows into numbered leaderboards.

27.9 Ranking NTILE and ROW NUMBER

27.9.1 RANK with gaps and DENSE RANK without gaps

Ranking answers "who is first, second, third" — but ties force a choice: do the numbers skip (sport standings: 1, 2, 2, 4) or stay tight (1, 2, 2, 3)? RANK skips, DENSE RANK does not.

RANK — a window function that numbers rows from 1 by the requested ordering — leaves gaps after ties. DENSE RANK numbers the same way but without gaps. Both restart at 1 per window. The worked top-exports query for USA orders by exports:

SELECT year, exports, RANK() OVER (ORDER BY exports) AS r
FROM trades WHERE country = 'USA';
SELECT year, exports, RANK() OVER (ORDER BY exports DESC) AS r
FROM trades WHERE country = 'USA';

Ascending order ranks smallest exports first. Descending order puts the largest year, 2018 in the run, at rank 1. Pulling the top ten adds LIMIT 10. Pulling exactly rank 5 wraps the query, because window results cannot be filtered in the same SELECT level:

SELECT * FROM (
  SELECT year, exports, RANK() OVER (ORDER BY exports DESC) AS r
  FROM trades WHERE country = 'USA'
) AS t WHERE r = 5;

Worked example — gap versus no gap on tied salaries. The employees-table demo makes the gap rule visible. Salaries 24000, 17000, 17000, 14000:

Step 1 — order descending: 24000 first, the two 17000 rows tied, 14000 last. Step 2 — RANK hands out 1, 2, 2, then skips to 4, because two rows consumed positions 2 and 3. Step 3 — DENSE RANK hands out 1, 2, 2, then 3, with no skip.

SELECT first_name, salary,
       RANK() OVER W AS rnk, DENSE_RANK() OVER W AS dense_rnk
FROM employees
WINDOW W AS (ORDER BY salary DESC);

Sense-check: under RANK the largest rank equals the row count (4); under DENSE RANK it equals the distinct-value count (3). Use RANK when the report must show how many rows were skipped by ties. Use DENSE RANK when the report needs a tight 1, 2, 3 sequence for filtering or display. The verbal description is "rank rows with number labels starting at one within each window". Sport-style ranks show ties consuming positions — shared second place pushes the next athlete to fourth.

Q: When should DENSE RANK be preferred? A: Prefer DENSE RANK when downstream logic filters on rank values such as rank 2 or rank 5 and gaps would silently drop labels. Prefer RANK when the audience expects sport-style ranks where ties consume positions.

Dialect note: RANK and DENSE_RANK are identical in PostgreSQL, Snowflake, Databricks, and MySQL 8. Snowflake adds a time-saver here: QUALIFY r <= 5 filters rank results without the subquery wrap — elsewhere, keep the wrap.

27.9.2 NTILE buckets

NTILE — a window function that splits ordered rows into a requested count of near-equal buckets — labels each row with its bucket number starting at 1. The bucket count cannot be zero or null. If rows do not divide evenly, bucket sizes differ by at most one. Ten rows into five buckets give two rows each. Eleven rows into five buckets give sizes that differ by one.

Bucket sizing (how NTILE distributes rows across buckets) follows one rule: with \(n\) rows and \(b\) buckets, the base size is \(q = n // b\) (integer division), and the first \(n \% b\) buckets hold one extra row. For \(n = 19\) and \(b = 4\): \(q = 4\), remainder \(3\), so the first three buckets hold 5 rows and the last holds 4 — five 1s, five 2s, five 3s, four 4s.

The worked USA query splits post-2000 exports into four buckets:

SELECT year, exports, NTILE(4) OVER (ORDER BY exports) AS bucket
FROM trades WHERE country = 'USA' AND year > 2000;

With 19 rows the run shows five 1s, five 2s, five 3s, and four 4s. Changing to NTILE(5) or moving the cutoff to 1998 with 21 rows reshuffles the counts but keeps the near-equal rule. Adding PARTITION BY restarts buckets per group:

SELECT country, year, exports,
       NTILE(5) OVER (PARTITION BY country ORDER BY exports) AS bucket
FROM trades
WHERE country IN ('USA', 'France', 'Belgium') AND year > 2000;

Belgium rows get buckets 1 through 5, then France rows restart at 1. Partitioning by year instead mixes countries within each year bucket. Filtering to one bucket uses a subquery:

SELECT * FROM (
  SELECT country, year, exports,
         NTILE(5) OVER (PARTITION BY country ORDER BY exports) AS bucket
  FROM trades
  WHERE country IN ('USA', 'France', 'Belgium') AND year > 2000
) AS t WHERE bucket = 2;

Worked example — quartile buckets on 11 rows. NTILE(4) over 11 ordered rows: \(q = 11 // 4 = 2\), remainder \(11 \% 4 = 3\).

Step 1 — the first 3 buckets hold \(2 + 1 = 3\) rows each. Step 2 — the last bucket holds 2 rows: sizes 3, 3, 3, 2. Step 3 — labels: rows 1-3 get bucket 1, rows 4-6 bucket 2, rows 7-9 bucket 3, rows 10-11 bucket 4.

Sense-check: sizes differ by at most one (3 versus 2), which is the NTILE guarantee. Histogram bins and test-score bands use NTILE when each band must hold about the same count of rows.

27.9.3 ROW NUMBER basics and syntax

ROW NUMBER — a window function that stamps each row with a unique sequential integer starting at 1 — gives every result row a virtual ID. Unlike RANK, ties never share a number: every row gets its own distinct integer. The full shape is:

SELECT ROW_NUMBER() OVER (PARTITION BY col1, col2 ORDER BY col3, col4) AS rn
FROM some_table;

PARTITION BY is optional. Without it the whole result set is one partition and numbers run 1 through the full count. With it each partition restarts at 1. ORDER BY sets the order in which numbers are handed out, ascending or descending. The set of rows the function operates over is called the window. That one sentence — the rules in which ROW NUMBER operates are called the window — unlocks the rest: change the window, change the numbering.

Worked example — numbering joined salary rows. The employees-plus-departments join demo selects first name, last name, salary, and department name, then numbers by salary:

SELECT e.first_name, e.last_name, e.salary, d.department_name,
       ROW_NUMBER() OVER (ORDER BY e.salary) AS rn
FROM employees AS e
INNER JOIN departments AS d ON d.department_id = e.department_id;

Here e aliases employees, d aliases departments, and the join key department_id is a primary key on one side and a foreign key on the other. Ordering by last name instead renumbers alphabetically. Without PARTITION BY the numbers run 1 to 107 in the run. Reversing fields is instructive: PARTITION BY salary with ORDER BY department name groups equal salaries together and sorts names inside, while the original groups departments and sorts salaries inside. Sense-check: the largest number equals the row count (107) — ROW NUMBER never gaps and never repeats within a partition.

A frequent syntax error is writing ORDER BY before PARTITION BY inside OVER. The required order is PARTITION BY first, ORDER BY second. Swapping them back fixes the error.

27.9.4 Nth record per group

Numbering per group makes "give me the Nth row of each group" easy. The worked request is the fourth import per country by year, then the second-highest salary per department:

SELECT country, year, imports,
       ROW_NUMBER() OVER (PARTITION BY country ORDER BY year) AS rn
FROM trades;

Albania rows number 1, 2, 3, 4 in year order. Every country restarts at 1. Wrapping in a subquery and filtering gives exactly the fourth row per country:

SELECT * FROM (
  SELECT country, year, imports,
         ROW_NUMBER() OVER (PARTITION BY country ORDER BY year) AS rn
  FROM trades
) AS t WHERE rn = 4;

Worked example — fourth row per country with subquery filter. Sorting that result by imports shows USA on top, then Germany, United Kingdom, France, and China. Adding year filters such as year 2000 onward or 2010 onward moves China to second place in the later window. The same pattern on salaries uses descending order:

SELECT * FROM (
  SELECT e.first_name, e.last_name, e.salary, d.department_name,
         ROW_NUMBER() OVER (PARTITION BY d.department_name ORDER BY e.salary DESC) AS rn
  FROM employees AS e
  INNER JOIN departments AS d ON d.department_id = e.department_id
) AS t WHERE rn = 2;

Rank 2 in each department is the second-highest paid person. In the executive group the run shows 24000 at rank 1 and 17000 at rank 2. Sense-check: each department contributes exactly one row to the output — if any department appears twice, the partition key missed a value.

Exam note: when a question asks for Nth per group, write PARTITION BY the group plus ORDER BY the ranking key, wrap in a subquery, and filter on the number. Window results cannot be filtered in the same SELECT level, so the wrap is required.

Dialect note: Snowflake's QUALIFY replaces the wrap (QUALIFY ROW_NUMBER() OVER (...) = 4). Databricks supports the wrap and also LIMIT-per-group via other constructs, but the subquery pattern is portable everywhere including MySQL 8.

27.9.5 DISTINCT pitfall and pagination

ROW NUMBER runs before DISTINCT, which surprises newcomers. Starting from 107 salary rows, SELECT DISTINCT salary gives 57 rows. Adding ROW NUMBER in the same SELECT level brings back 107 rows with duplicates such as repeated 17000 values, because numbering happens first and makes every row distinct. The fix nests the DISTINCT inside:

SELECT salary, ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn
FROM (SELECT DISTINCT salary FROM employees) AS t
ORDER BY salary DESC;

Now numbering applies to the 57 distinct salaries. Pagination uses the same wrap idea. Number by department and salary, then keep rows 6 through 10:

SELECT * FROM (
  SELECT e.first_name, e.last_name, e.salary, d.department_name,
         ROW_NUMBER() OVER (PARTITION BY d.department_name ORDER BY e.salary) AS rn
  FROM employees AS e
  INNER JOIN departments AS d ON d.department_id = e.department_id
) AS t WHERE rn BETWEEN 6 AND 10;

The run returns 12 rows across departments. A simpler salary-only version orders all salaries descending, numbers them, and keeps the same 6-to-10 slice, which shows rows 1 to 5 on the first page and rows 6 to 10 on the second. That is the classic page-by-number technique.

Two evaluation-order traps. First, DISTINCT after numbering never deduplicates, because the unique numbers already made every row distinct — dedupe in an inner query, number outside. Second, LIMIT applies after numbering too, so ROW_NUMBER() ... LIMIT 5 numbers everything and then keeps five rows; for per-group top-N, filter on the number in the outer query instead.

Dialect note: production pagination on large tables usually uses keyset seeking (WHERE (salary, id) < (...)) or LIMIT/OFFSET rather than numbering all rows — Databricks and MySQL both optimize LIMIT/OFFSET better than full numbering plus a BETWEEN filter. The ROW_NUMBER wrap remains the portable classroom pattern and the right tool when page boundaries must restart per group.

27.9.6 Group rank plus global rank

Two named windows give two ranks side by side: rank inside the department and rank across everyone:

SELECT e.first_name, e.salary, d.department_id,
       RANK() OVER w_dept AS dept_rank,
       RANK() OVER w_all AS global_rank
FROM employees AS e
INNER JOIN departments AS d ON d.department_id = e.department_id
WINDOW w_dept AS (PARTITION BY d.department_id ORDER BY e.salary DESC),
       w_all AS (ORDER BY e.salary DESC);

Without ORDER BY inside w_dept every row shows rank 1, which is the visible proof that ordering matters — with no ordering key every row ties for first. With descending salary order the department ranks read 1, 2, 3 within each department. The global window has no PARTITION BY, so it ranks all 107 people at once. In the run Kimberly is rank 1 in her department but 45th globally, while Michael is rank 1 in his two-person group and 6th globally. One query answers both "best in group" and "best overall".

RANK skips after ties, DENSE RANK stays tight, NTILE deals near-equal buckets, and ROW NUMBER hands every row a unique ID — with Nth-per-group and pagination falling out of the wrap-and-filter pattern. Next, row-hopping functions read neighbors directly.

27.10 LEAD LAG FIRST LAST Totals Correlation and WITH

27.10.1 LEAD and LAG movement

Ranking numbers rows; LEAD and LAG read across rows. LEAD peeks at a later row, LAG peeks at an earlier one — the building blocks of every "compare with yesterday" query.

LEAD reads a later row. LAG reads an earlier row. Both take an expression, an offset, and an optional default for edges. The shapes are:

LEAD(expr, offset, default) OVER (PARTITION BY grp ORDER BY ord)
LAG(expr, offset, default) OVER (PARTITION BY grp ORDER BY ord)

Here expr is a column or calculation, offset is a positive integer count of rows to jump, and default fills in when the jump leaves the partition. If no default is given, out-of-range jumps return NULL. On row 3, LEAD with offset 2 reads row 5. On row 4, LAG with offset 2 reads row 2. On row 6, LAG with offset 2 reads row 4. The verbal description is "move lines within the result set forward for LEAD and backward for LAG".

Worked example — LEAD offsets on Belgium exports. The Belgium exports walk makes it visible: with LEAD offset 1 the first row value 178867 shows next-row 187839 beside it, then 190309, then 215803. With offset 2 the first row jumps two rows to 190309 and the second row jumps to 215803. Reversing ORDER BY to descending flips which physical row counts as next — "later" always means later in the window ordering, not later in the table. Sense-check: the last row's LEAD is NULL (nothing follows it) and the first row's LAG is NULL (nothing precedes it); any non-NULL there means the partition leaked.

The multi-country version partitions so jumps never cross groups:

SELECT country, year, exports,
       LAG(exports, 1) OVER (PARTITION BY country ORDER BY year) AS prev_exp,
       LEAD(exports, 1) OVER (PARTITION BY country ORDER BY year) AS next_exp
FROM trades
WHERE country IN ('USA', 'Belgium') AND year > 2010;

Belgium rows order 2011, 2012, onward with LAG showing the prior year and NULL on the first Belgium row. USA rows form their own group, so the first USA row shows NULL rather than a Belgium value. Partitioning by year instead mixes countries within each year and reorders the whole output by year. Click Analytics uses LEAD and LAG for day-over-day stock percent change from current date to prior date.

Dialect note: LEAD/LAG with offsets and defaults work identically in PostgreSQL, Snowflake, Databricks, and MySQL 8. Snowflake additionally allows LEAD/LAG to ignore NULLs (IGNORE NULLS), handy for sparse series — elsewhere, fill gaps in a prior step.

27.10.2 Salary versus next and prior values

The employees demo compares each salary with its neighbor by ordering salaries descending:

SELECT first_name, salary,
       salary - LEAD(salary, 1) OVER (ORDER BY salary DESC) AS diff_next
FROM employees ORDER BY salary DESC;

Worked example — gaps between neighboring salaries. Steven at 24000 minus Lex at 17000 gives 7000. Lex 17000 minus 17000 gives 0 — a tie produces a zero gap, not a NULL. The next pair 17000 minus 14000 gives 3000. The LAG mirror reads upward: Steven has NULL above him, Lex minus Steven gives negative 7000. Offset 2 skips one row each time, which changes every difference. Sense-check: all gaps between consecutive descending salaries are zero or positive; a negative gap means the ordering flipped somewhere.

The same idea answers hiring questions: order by hire date and difference the salaries to see whether later hires earn more or less, or group by month to find pay pockets. The frame clause ROWS BETWEEN with offsets can sit in the same OVER when the comparison needs a wider slice. The classic day-over-day percent change is one line further: (salary - LAG(salary) OVER w) / LAG(salary) OVER w * 100.

27.10.3 FIRST VALUE LAST VALUE and least comparison

FIRST VALUE returns the first value of the frame. LAST VALUE returns the last value of the frame. NTH VALUE returns any chosen position. To compare everyone against the least-paid person, build one giant frame holding all rows sorted descending, then read its last value:

SELECT first_name, salary,
       LAST_VALUE(salary) OVER W AS least_pay,
       salary - LAST_VALUE(salary) OVER W AS more_than_least
FROM employees
WINDOW W AS (ORDER BY salary DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);

A gap from the minimum (how much more one row earns than the lowest-paid row) subtracts the frame's last value from each salary. With \(L\) the least pay and \(x\) one salary:

\[more = x - L, \quad pct = \frac{x - L}{L} \times 100\]

The symbol \(L\) is LAST VALUE over the full frame — fixed at 2100 on every row — and \(pct\) scales the gap as a percentage of that minimum.

Worked example — least pay comparison with LAST VALUE frame. The frame from UNBOUNDED PRECEDING to UNBOUNDED FOLLOWING holds every row, so LAST VALUE is the minimum salary 2100 on every row. Steven 24000 minus 2100 gives 21900 more. A 17000 salary minus 2100 gives 14900 more. The least-paid person shows 0. The percent version:

SELECT first_name, salary,
       ROUND((salary - LAST_VALUE(salary) OVER W) / LAST_VALUE(salary) OVER W * 100, 2) AS pct_more
FROM employees
WINDOW W AS (ORDER BY salary DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);

Steven lands near 1042.85 percent more. Lex lands near 709 percent more. Sense-check: the minimum row's gap and percent are both exactly 0 — any other value means the frame missed the true last row.

The full frame matters: with the default frame ending at CURRENT ROW, LAST VALUE would crawl instead of staying fixed at 2100 — each row would see a different "last" value. Swap in FIRST VALUE with the same frame to compare against the highest salary instead.

Dialect note: FIRST_VALUE, LAST_VALUE, and NTH_VALUE exist in PostgreSQL, Snowflake, Databricks, and MySQL 8 with the same syntax. The crawling-LAST_VALUE trap is identical everywhere: always pair LAST_VALUE with an explicit ROWS BETWEEN ... AND UNBOUNDED FOLLOWING frame unless the crawl is intended.

27.10.4 Totals shares and cumulative sums

A bare OVER with SUM gives the grand total on every row. Dividing the row by that total gives its share:

SELECT first_name, salary,
       SUM(salary) OVER () AS total_sal,
       ROUND(salary / SUM(salary) OVER () * 100, 2) AS pct_sal
FROM employees ORDER BY 4 DESC;

A salary share (one person's fraction of total payroll, as a percent) divides the row by the grand total. With \(total = \sum_j salary_j\) summing every salary:

\[pct = \frac{salary}{total} \times 100\]

Steven takes about 3 percent of the total. Lex and Nina follow. TJ near 2100 takes about 0.30 percent. The plain-group alternative would need a separate totals query plus application math, so the window saves a full pass.

Cumulative totals add ORDER BY plus an expanding frame:

SELECT first_name, salary,
       SUM(salary) OVER (ORDER BY salary DESC
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumul
FROM employees;

Worked example — cumulative payroll from the top. At Steven the frame holds one row, so cumulative equals his salary alone. At the next 17000 row the frame holds both top rows and cumulative reads their sum. Further rows keep adding as rows join, building the running payroll total down the salary ladder. The same ROWS BETWEEN pattern works for running averages and counts. Sense-check: the final row's cumulative equals the grand total from the bare-OVER query — two paths to one number must agree.

Cumulative return series for stocks, bonds, and exchange traded funds use exactly this expanding frame over time order.

27.10.5 CORR between imports and exports

CORR — the correlation function returning the correlation coefficient between two numeric columns — reports a number from negative 1 to positive 1. Positive 1 is the strongest up-up link: when one number rises the other rises. Negative 1 is the strongest up-down link: when one rises the other falls. Values near zero mean weak linkage. The bounds are:

\[-1 \le CORR(y, x) \le 1\]

where \(y\) is the first column and \(x\) is the second column. The coefficient is symmetric in practice — swapping the two columns gives the same strength — and it measures linear linkage only, so a strong curve with no straight-line trend can still score near zero.

The country-level query is:

SELECT country, CORR(imports, exports) AS corr_ie
FROM trades GROUP BY country
ORDER BY 2 DESC NULLS LAST;

Worked example — import-export linkage by country. NULLS LAST pushes unknown correlations to the bottom. Small Caribbean rows show 1.0, followed by Netherlands, New Zealand, Belgium, and Mexico with strong positive linkage. Named large traders read France 0.99, Singapore slightly below, USA 0.9792, Japan 0.9733, Brazil 0.96. Negative tails include Libya, Samoa Island, Dominica, Tajikistan with missing data, and French Polynesia near negative 0.63, meaning imports up pairs with exports down there. Sense-check: the big balanced traders all score above 0.95 — imports and exports growing together over decades is exactly what a near-1 coefficient should show; a near-zero score on a major trader would deserve a second look at the data.

Market desks compare S and P 500 index levels against exchange traded fund prices with the same coefficient before modeling.

Dialect note: CORR as an aggregate exists in PostgreSQL, Snowflake, and Databricks. As a window (CORR(...) OVER (...)) it works in PostgreSQL and Snowflake. MySQL has no CORR function — the portable path is computing the coefficient from SUM/AVG/STDDEV parts, or correlating in application code. Practical SQL's statistics chapter covers the manual pieces.

27.10.6 Group averages with PARTITION BY

Partitioned averages put each person beside their department mean plus the gap:

SELECT e.first_name, e.salary, e.department_id,
       ROUND(AVG(e.salary) OVER (PARTITION BY e.department_id), 2) AS dept_avg,
       ROUND(e.salary - AVG(e.salary) OVER (PARTITION BY e.department_id), 2) AS diff_avg
FROM employees AS e
ORDER BY e.department_id, e.salary DESC;

Department 20 averages about 9500. Department 30 averages about 4150. Department 50 averages about 3475.56. Department 40 averages about 6500. Michael at 13000 in the two-person group sits 3500 above the 9500 mean while Pat sits 3500 below it. Sorting by department then salary descending turns the output into a ready report: highest earner per group on top with the gap beside each name. The verbal description is "salary versus average salary within the department and the difference".

Scope: the gap column sums to zero within each partition (above-average and below-average gaps cancel) — a fast correctness check. Assumption: every row belongs to exactly one department partition. What breaks: NULL department IDs form their own partition in PostgreSQL, so unassigned staff average together; filter or coalesce them before reporting.

27.10.7 WITH for hand-made data and custom order

The WITH clause — a named temporary result defined once then used like a table — builds data that is not stored anywhere. The tiny demo defines four numbers and aggregates them:

WITH num(mynum) AS (VALUES (1), (2), (3), (4))
SELECT MAX(mynum) AS mx, MIN(mynum) AS mn FROM num;

Here num is the temporary table name and mynum is its one column. No table is created on disk. The query returns mx 4 and mn 1. Application code often prepares such value lists at runtime, then joins or aggregates them in the same statement.

Custom ordering uses the same trick. A small item table holds pen, paper, pencil, book, and printer with serial IDs 1 to 5:

CREATE TABLE t_order (id SERIAL PRIMARY KEY, item VARCHAR(100));
INSERT INTO t_order (item) VALUES ('pen'), ('paper'), ('pencil'), ('book'), ('printer');

Alphabetical ORDER BY cannot produce the requested display order book, pencil, pen, printer, paper. A mapping table supplies the order, then a join plus ORDER BY applies it:

WITH t_data(list_order, item) AS (
  VALUES (1, 'book'), (2, 'pencil'), (3, 'pen'), (4, 'printer'), (5, 'paper')
)
SELECT t_order.id, t_order.item, t_data.list_order
FROM t_order JOIN t_data ON t_data.item = t_order.item
ORDER BY t_data.list_order;

Output reads book 1, pencil 2, pen 3, printer 4, paper 5. The application layer usually maintains the mapping list. For thousands of rows a stored mapping table may serve better, but the pattern is the same: map, join, sort.

Dialect note: WITH (non-recursive) is portable across PostgreSQL, Snowflake, Databricks, and MySQL 8. The VALUES-list form AS (VALUES ...) with a column alias works in PostgreSQL and Snowflake; Databricks and MySQL prefer AS (SELECT 1 AS ...) UNION ALL ... spelling for hand-made rows — same result, different wrapping.

27.10.8 Scope summary and planning tips

Two scopes organize every function. Frame scope computes at row level inside one frame: FIRST VALUE gives the first frame value, LAST VALUE the last frame value, NTH VALUE any chosen position, and generic aggregates such as SUM, AVG, MIN, MAX summarize the frame. Partition scope splits rows first. Its row-access functions are LAG for the row before, LEAD for the row after, and ROW NUMBER for the current row number. Its ranking functions are RANK with gaps, DENSE RANK without gaps, NTILE for bucket counts suited to histograms, CUME DIST for cumulative distribution, and PERCENT RANK for score rank. The iron rule: a window never reads rows outside its own partition. Without PARTITION BY the whole set is one partition. A window defined once and referenced many times (the WINDOW clause) keeps multi-column queries consistent.

Plan in this order. First decide the split: PARTITION BY creates the groups, for example gender or department or country or year. Second decide the sort: ORDER BY sets the sequence inside each group, and it changes FIRST VALUE, LAST VALUE, RANK, and running totals. Third decide the row handling: ROWS for positional frames, RANGE for peer-group frames, or RANK versus DENSE RANK for label logic. Fourth define the frame edges: ROWS BETWEEN with UNBOUNDED PRECEDING, numbered offsets, CURRENT ROW, UNBOUNDED FOLLOWING, and EXCLUDE CURRENT ROW as needed. Each named window carries its own triple of partition, order, and frame, so W and W2 can differ completely in one query. Match the function to the scope: frame-level needs for first, last, or Nth values, partition-level needs for neighbor moves and ranks.

Dialect extras worth knowing, kept strictly in support of lecture topics: Snowflake's QUALIFY filters window results without a subquery wrap (same rows as the wrap-and-filter pattern, less nesting). Snowflake and Databricks PIVOT/UNPIVOT reshape grouped output into wide reports, complementing ROLLUP/CUBE tall output. PostgreSQL's FILTER (WHERE ...) also works inside window aggregates (SUM(x) FILTER (WHERE ...) OVER (...)) — a narrow extra over the lecture's grouped FILTER. CUME_DIST and PERCENT_RANK (named in the scope summary) rank by relative position: CUME_DIST gives the fraction of rows at or below the current row, PERCENT_RANK scales rank as (rank − 1) / (rows − 1) — same OVER syntax as RANK, portable across all five engines.

LEAD and LAG hop between rows, FIRST and LAST VALUE read frame edges, SUM OVER gives totals and shares, CORR scores linkage, and WITH builds hand-made tables — all planned as partition, then order, then frame.
