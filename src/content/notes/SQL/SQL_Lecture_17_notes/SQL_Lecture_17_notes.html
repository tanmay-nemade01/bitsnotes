# Joining Multiple Tables

17.1 INNER JOIN Fundamentals

Hook — why joins decide everything: one table holds films, another holds directors. Neither table answers "who directed this film?" alone. You glue them together on a shared id, and only the pairs that match survive. Master this one idea and every later join (LEFT, RIGHT, FULL, SELF) becomes a small variation.

An INNER JOIN answers questions that span two tables. You use it every time you need columns from both sides in one row — film title plus director name, order plus customer, student plus grade.

17.1.1 What a Join Does

A join attaches columns from two or more tables into one result by matching values in a shared column. In PostgreSQL the shared column is, as a rule, the primary key of the first table paired with the matching foreign key in the second table. A primary key is the single column that stays unique for each row of its table. A foreign key is that same value carried into a second table so rows there can point back to the parent row.

Intuition — zipper analogy: think of each table as one side of a zipper. Each tooth is an id value. The join slides down both sides and locks only teeth of equal size: movie tooth director_id = 1 locks with director tooth director_id = 1. Teeth with no twin stay open and fall out of an INNER JOIN result. Break point: the analogy breaks when ids repeat — one director tooth can lock many movie teeth (one-to-many), which a real zipper cannot do.

That zipper picture explains the strict keep-only-matches rule. Rows can still be read from each table on their own, but the joined result drops every pair whose values do not match. That "keep only matching pairs" behavior is what sets INNER JOIN apart from every outer join later in this set of notes.

The two-table pattern reads like this:

SELECT m.movie_id, m.movie_name
FROM movies AS m
INNER JOIN directors AS d
  ON m.director_id = d.director_id;

In plain words the query says: take each row of movies, keep it only when its director id value has an exact twin in the directors table, and glue the two rows side by side. The spoken form behind the predicate is "movies dot director id equals directors dot director id".

Formalize — the INNER JOIN predicate (17.1.formula.1): the reconstructed predicate is \(m.director\_id = d.director\_id\), where \(m\) is one row of the movies table and \(d\) is one row of the directors table.

Step-by-step logic:

  1. Pick a pair \((m, d)\) — one movie row and one director row.
  2. Read \(m.director\_id\) — the foreign key stored on the movie.
  3. Read \(d.director\_id\) — the primary key stored on the director.
  4. Keep the pair only if the test \[m.director\_id = d.director\_id\] is true; otherwise discard it.
  5. For each kept pair, output one glued row with columns from both sides.

Either direction of the equality works, meaning \(movies.director\_id = directors.director\_id\) and the reversed form give the same pairs. The bare word JOIN means the same as INNER JOIN in every major database, so FROM movies JOIN directors is identical.

Picture the result as a matching grid. Put movie rows down the left axis and director rows across the top axis. Each cell is a candidate pair. The shape is a sparse dot field — only the diagonal-like cells where ids are equal get a dot. The landmark is the shared id column acting as the ruler on both axes. The takeaway: INNER JOIN paints dots only on exact matches and erases everything else.

Cross-DB note that helps here: PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL all accept both JOIN and INNER JOIN with identical meaning, and all accept the same ON m.director_id = d.director_id syntax. Keep this common form — you need no dialect change for basic inner joins.

17.1.2 The Movies and Directors Tables

The worked schema uses two tables. Movies holds movie id as its primary key plus movie name, length, language, age certificate, release date, and director id. Director id inside movies is the foreign key. Directors holds director id as its primary key plus first name, last name, date of birth, nationality, and update columns.

A quick ordered look at the data sets the scene:

SELECT * FROM movies ORDER BY director_id;
SELECT * FROM directors;

The movies side shows director id values such as 1, 2, and 3 repeating down the rows. The directors side shows those same ids once each, for example id 1 belonging to Tomas Alfredson. The common ground is the pair movies dot director id and directors dot director id.

In a cinema-booking application — for example a Netflix-style catalog service — this is exactly how a title page shows the film plus its director: the movies row carries facts about the film, the directors row carries facts about the person, and the join assembles the page in one query.

Scope: this section covers only INNER JOIN with an equality (=) predicate on integer ids. It does not cover outer joins that keep unmatched rows, non-equal conditions (ranges, LIKE), or joins on mismatched types (that is Section 17.4). All examples use the movies/directors lecture schema in PostgreSQL-compatible syntax.

17.1.3 Worked Examples

The lecture builds four examples in order. Each one fixes the previous gap, so read them as a chain rather than isolated tricks.

Example 1 (17.1.example.1) — first join with qualified names. The first attempt selects movie id, movie name, and director id from movies and joins directors ON movies.director_id = directors.director_id. It fails with "column reference director_id is ambiguous" because both tables own a column of that name and the unqualified select list does not say which one to print. The fix qualifies the wanted column with its table name:

SELECT movies.movie_id, movies.movie_name, movies.director_id
FROM movies
INNER JOIN directors
  ON movies.director_id = directors.director_id;

Steps: (1) list wanted columns; (2) run and read the ambiguous-column error; (3) prefix every shared column as table.column. Final answer: the qualified query runs and returns one row per matched film. Sense-check: row count cannot exceed the movies count, because each movie matches at most one director.

Qualification is the habit to lock in now. Whenever two joined tables share a column name, prefix every shared column in the select list with table name dot column name. The ON clause itself is always qualified on both sides.

Example 2 (17.1.example.2) — pulling a column from the second table. Movie id and director id alone do not tell who directed the film, so the next step adds the director first name from the second table. The working habit shown is to leave a blank gap in the select list between the first table columns and the second table columns so the eye can see which table each column comes from:

SELECT movies.movie_id,
       movies.movie_name,
       movies.director_id,
       directors.first_name
FROM movies
INNER JOIN directors
  ON movies.director_id = directors.director_id;

Running it brings back rows such as Stanley, Francis, and Kenji next to their films. Final answer: each film now prints alongside its director's first name. Sense-check: pick one film you know and confirm the name beside it looks right; if every name is shifted, the ON columns are wrong.

Notice the select list groups movies columns first, then a visual gap, then directors columns. That layout costs nothing and makes 3-table queries readable later.

Example 3 (17.1.example.3) — table aliases and the 500-table shop story. Long table names typed on every column turn messy fast, and a shop with hundreds of tables — one story mentions a stock database with around 500 tables kept on a planning sheet with one agreed short alias per table — needs short stable aliases. The alias pattern puts one short name after each table in FROM and JOIN and then uses it everywhere:

SELECT mv.movie_id, mv.movie_name, d.first_name
FROM movies AS mv
INNER JOIN directors AS d
  ON mv.director_id = d.director_id;

Here mv stands for movies and d for directors. The same query without aliases returns the same rows, but the aliased form reads faster. Final answer: aliased and unaliased forms return identical pairs; prefer the aliased form. Sense-check: run both and compare row counts — they must match exactly.

Two cautions come with it. Never pick a reserved word such as select as an alias. And keep each alias stable across the whole database so movies is always mv and directors is always d, never d2 in the next query. In PostgreSQL, aliases written with double quotes preserve case (AS "mv"), while MySQL uses backticks and SQL Server uses brackets — so stick to plain lowercase aliases and you stay portable everywhere including Snowflake and Spark SQL.

Aliases are local nicknames for one query only; they do not rename the table on disk. Once you write FROM movies AS mv, you must use mv, not movies, for the rest of that query in most dialects.

Example 4 (17.1.example.4) — filtering the joined result on both sides. Filters sit after the whole join in a WHERE clause and use the alias, not the full table name. To keep only English-language films and show the language column while checking, then drop it:

SELECT mv.movie_name, d.first_name
FROM movies AS mv
INNER JOIN directors AS d
  ON mv.director_id = d.director_id
WHERE mv.movie_lang = 'English';

Battle Royale, a Japanese-language film, drops out under this filter. Because the tables are joined, filtering can reach into either side, for instance adding AND d.director_id = 3 keeps only English films by that one director. Final answer: the filter keeps only English films (Battle Royale excluded), and adding the directors-side condition narrows to director 3. Sense-check: the filtered count must be smaller than the unfiltered count; if it grows, the AND became an OR by mistake.

The order is fixed: FROM + JOIN ... ON first builds the glued rows, then WHERE keeps the wanted subset. Never put the filter inside ON for an inner join exercise unless the task asks for it — keep join conditions in ON and row filters in WHERE.

17.1.4 Student Questions and Answers

Student confusion clusters around the same three points, so they are answered together in the lecture's own words, deduplicated.

Q: The error says column reference director_id is ambiguous. Which director_id does the database want? \ A: Both tables own a column called director_id, so the bare name points at two places at once. Prefix it as movies.director_id or directors.director_id (or mv.director_id / d.director_id once aliased) and the error goes away. This is professor-flagged: always qualify shared names.

Q: The two queries, one with full table names and one with mv and d aliases, look different. Do they return the same rows? \ A: Yes. An alias is only a short name for the table inside that one query. The pairs, the columns, and the row count stay the same, and the aliased form is picked for speed of reading.

Q: After joining, can I filter on the directors side too, or only on movies? \ A: Either side. Once the tables are joined, WHERE can test movies columns such as movie_lang and directors columns such as director_id in the same clause — for example WHERE mv.movie_lang = 'English' AND d.director_id = 3.

That last answer surprises beginners: after the join there is one wide virtual row, so WHERE sees every column from every table at once.

Pitfalls (professor-flagged in bold): (1) Unqualified shared column — selecting bare director_id when both tables own it always raises the ambiguous-column error; qualify every shared name. (2) Reserved-word or drifting aliases — AS select breaks parsing, and renaming d to d2 in the next query confuses the whole team; fix one short alias per table on the planning sheet. (3) Filtering before joining in your head — beginners read WHERE first; the engine joins first, then filters, so a filter cannot rescue a wrong ON condition.

17.1.5 Column Lists Versus Star

A shortcut worth knowing is table name dot star, as in mv.*, which pulls every column of that table. Running it on the join returns the full wide row from both tables at once. Database administrators use dot star for a fast eyeball check of the data, but reports and application queries should name each column one by one. Star pulls every column across the wire, grows the result far past what the screen needs, and can slow the server and the application.

SELECT mv.*, d.first_name
FROM movies AS mv
INNER JOIN directors AS d
  ON mv.director_id = d.director_id;

Use mv.* while exploring, then replace it with the exact column list before you save or submit. A retail stock-control team with that 500-table database does exactly this: SELECT * at the console to inspect, explicit columns in every saved report.

Exam note: name explicit columns in graded answers and never answer with star. A grader can see exactly which columns were asked for only when each one is named. If the question asks for movie name and director first name, write exactly those two columns with aliases — extra columns can lose marks.

17.1.6 Recap and Bridge

You now own the core motion: build glued rows with ON, disambiguate with table.column, shorten with stable aliases, filter with WHERE on either side, and list explicit columns.

Recap + bridge: INNER JOIN keeps only pairs with \(m.director\_id = d.director\_id\); qualify shared columns, alias once (mv, d), filter after the join, and project explicit columns. Next, Section 17.2 shortens this pattern with USING when both sides share the same column name and chains a third table (movies_revenues) onto the result.

17.2 INNER JOIN with USING and Multi-Table Chains

Hook — stop typing the same column twice: when both tables call the shared column director_id, writing ON movies.director_id = directors.director_id repeats yourself. USING (director_id) says the same thing in three words and cleans up the output too. Learn when you can shorten and when you must spell it out.

USING is a shortcut, not a new join type. It returns exactly the same matching rows as ON, but you type less and the result looks tidier. You then reuse the same idea to chain a third table.

17.2.1 The USING Form

USING is a shorter join form allowed only when both tables share the same column name. Instead of naming both sides with ON, the query names the shared column once:

SELECT t1.col1, t2.col1
FROM table1
INNER JOIN table2 USING (col1);

A join key is the column (or columns) whose equal values decide which rows pair up. ON accepts any join key, even when the two names differ. USING accepts only one case: the join key has exactly the same name on both sides.

Intuition — shared nickname analogy: imagine two clubs both call their membership card "member card". You can say "match by member card" once and everyone understands. That is USING. If one club calls it "member card" and the other calls it "client code", you must spell out "club-A member card equals club-B client code". That is ON. Break point: the analogy breaks because USING also changes the displayed result (one shared column, placed first), while a shared nickname in real life does not merge two cards into one.

The display rule is the part beginners miss. ON keeps both copies of the shared column, so you see movies.director_id and directors.director_id side by side. USING merges them into a single column and prints it first.

Formalize — the USING rule (17.2.formula.1): the reconstructed meaning is \(t1.col1 = t2.col1\) with the extra display rule that the shared column prints once, first.

Step-by-step logic:

  1. Check the precondition: both tables own a column spelled exactly \(col1\).
  2. Form candidate pairs \((t1, t2)\) — one row from each table.
  3. Keep only pairs where \[t1.col1 = t2.col1\] is true.
  4. Project the output as one merged \(col1\) column first, then the remaining columns of each table.
  5. No table aliases are needed for the join key itself, because you never write table.column for it.

Applied form: INNER JOIN ... USING (director_id) means \(movies.director\_id = directors.director\_id\) plus "show director_id once, at the front".

Picture the output table to feel the difference. Put output column position along the horizontal axis and row number down the vertical axis. With ON, the shape starts with two identical id bars (two director_id columns) followed by the film and director details. With USING, the shape starts with one single id bar at position 1, then the same details. The landmark is column 1: if it holds the merged shared key, you used USING. The takeaway: same rows, cleaner front column.

Applied to the worked schema, where both tables own director id:

SELECT * FROM movies
INNER JOIN directors USING (director_id);

The director id column comes out first, then the directors columns, then the movies columns. The classic ON form below returns the same rows:

SELECT * FROM movies
INNER JOIN directors
  ON movies.director_id = directors.director_id;

The USING form wins on brevity whenever the shared name exists. Highly practical advice from the lesson: reach for USING first when the column names match, and fall back to ON when they differ or when the match needs an expression such as a cast or a calculation.

Scope: this section covers only USING on a single same-named equality key plus chaining inner joins. Scope: it does not cover multi-column USING (a, b), outer joins with USING, or same-named columns that mean different things (where merging would hide a mistake). All examples use PostgreSQL-compatible syntax.

Cross-DB note worth keeping: PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL all support USING, and all follow the same output rule — the shared column appears once. MySQL and PostgreSQL also support NATURAL JOIN, which auto-uses every same-named column, but SQL Server has no NATURAL JOIN at all, so this course sticks to explicit USING or ON. The bare word JOIN still means INNER JOIN in every one of these systems.

17.2.2 Worked Examples

The lecture joins the money table next, then chains all three tables. Follow the chain one link at a time.

Example 1 (17.2.example.1) — movies to movies revenues. The revenue table shares movie_id with movies, so the join is one short line:

SELECT * FROM movies
INNER JOIN movies_revenues USING (movie_id);

Steps: (1) confirm both tables own movie_id spelled identically; (2) write USING (movie_id) instead of the longer ON equality; (3) run and read left to right — merged movie_id first, then film details, then revenue details. Movie id, movie name, and the domestic and international revenue columns land in one row per film with all values intact. Final answer: one row per film carrying both revenue figures, keyed by a single leading movie_id. Sense-check: every movie_id appears once; if you see the same film twice, a duplicate key slipped into the revenue table.

The revenue table in this lecture is movies_revenues with one row per film. That one-to-one shape is why the row count stays stable here, unlike the many-to-one movies-to-directors join.

Example 2 (17.2.example.2) — chaining three tables. Movies joins directors on director id, then that result joins movies revenues on movie id:

SELECT * FROM movies
INNER JOIN directors USING (director_id)
INNER JOIN movies_revenues USING (movie_id);

Steps: (1) join movies to directors on director_id — this builds wide film-plus-director rows; (2) join that running result to movies_revenues on movie_id; (3) check that each USING names the link between the table just added and the chain so far. Each USING names the link between the table just added and the chain so far. The run returns one wide row per film carrying its director details, nationality, date of birth, and both revenue figures. Final answer: one wide row per film with director facts plus both revenue figures. Sense-check: count rows — it must still equal the count of revenue rows that have a matching film, since INNER JOIN drops anything unmatched.

Think left to right: the database glues tables in the order you list them. Table 1 plus table 2 becomes a virtual table, then table 3 joins that virtual table. In a real box-office dashboard — for example a studio finance report that lists each title, its director, and its domestic plus international gross — this three-table chain is the exact query behind the page. And if the link columns had different names (say movies.id versus revenues.film_no), you would keep the same chain shape but write each link with ON instead of USING.

17.2.3 Student Questions and Answers

The class asked whether the shortcut hides anything and whether chains can grow longer.

Q: USING and ON gave the same rows. Is there any hidden difference? \ A: The row set matches. The visible difference is that USING prints the shared column once at the front and needs no aliases, while ON prints both copies. Pick USING for shared names and ON for everything else.

Q: Can more than two tables be chained in one query? \ A: Yes. Add one more INNER JOIN plus its own USING or ON for each new table, naming the shared column with the table already in the chain each time. The three-table movies, directors, and revenues query is the template.

A useful follow-on habit: when a chain mixes both forms, put a comment beside each ON explaining why USING could not apply (different names or an expression). Future readers will thank you.

Pitfalls (professor-flagged in bold): (1) Using USING when names merely look alike — director_id versus directorid or different meanings of id silently joins the wrong pairs; verify spelling and meaning first. (2) Expecting two shared columns with USING — you get one merged column, so SELECT director_id after USING is unambiguous but SELECT movies.director_id may error in some systems; select the bare merged name. (3) Chaining without checking each link — if the second join key is wrong, the whole wide row collapses to zero rows; test each two-table link alone before adding the third.

17.2.4 Recap and Bridge

USING shortens the inner join when the key name matches on both sides and tidies the output to one leading key column.

Recap + bridge: USING (col) means \(t1.col = t2.col\) plus "print col once, first"; use ON whenever names differ or logic gets complex, and chain tables left to right with one join key per link. Next, Section 17.3 keeps this three-table chain but adds the working pattern professionals live in: join first, filter with WHERE, pick columns, then sort and limit.

17.3 INNER JOIN with Filtered Data

Hook — the professional pattern in one line: real queries are never just a join. You join everything you need, throw away rows you do not want, keep only the columns the report needs, and sort the survivors. Join, filter, select, sort — that four-beat rhythm answers almost every business question in this lecture.

This section turns the three-table chain into a reusable template. The tables are the same as before — movies, directors, movies_revenues — but now each query also filters, computes, sorts, and caps the output.

17.3.1 Three-Table Filter Pattern

The reusable pattern is: join first, filter second, pick columns last, sort at the very end. Aliases stay short throughout, with mv for movies, d for directors, and r for movies revenues:

SELECT mv.movie_name, d.first_name, d.last_name, r.revenues_domestic
FROM movies AS mv
INNER JOIN directors AS d
  ON mv.director_id = d.director_id
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id
WHERE mv.movie_lang = 'Japanese';

In plain words: glue the three tables on their shared ids, keep only the rows passing the filter, then print just the wanted columns. The select list groups columns by table with gaps between the groups so the source of each column stays visible.

Intuition — factory line analogy: imagine a conveyor belt with four stations. Station 1 (JOIN) bolts film, director, and revenue parts into one wide item. Station 2 (WHERE) kicks defective or unwanted items off the belt. Station 3 (SELECT) polishes only the faces the customer sees. Station 4 (ORDER BY + LIMIT) lines the finished items up tallest-first and boxes the top few. Break point: on a real line every item passes every station once, but SQL logically builds all joins before any filter — you cannot filter a table before it has been joined into the belt.

That order matters because WHERE sees the whole glued row. You can filter on any table's column — language from movies, revenue from revenues — in a single WHERE clause.

Formalize — the join-filter-select-sort pipeline: for tables \(mv\), \(d\), and \(r\):

  1. Join: keep triples \((mv, d, r)\) where \[mv.director\_id = d.director\_id\] and \[mv.movie\_id = r.movie\_id\].
  2. Filter: keep only triples where the WHERE test (for example \(mv.movie\_lang = 'Japanese'\)) is true.
  3. Project: print only the listed SELECT columns, grouped by source table.
  4. Sort and cap: apply ORDER BY to the projected rows, then LIMIT keeps the first rows and discards the rest.

Every symbol: \(mv\) is one movies row, \(d\) is one directors row, \(r\) is one revenues row, and each subscript (\(director\_id\), \(movie\_id\), \(movie\_lang\)) names the column read from that row.

Picture a funnel to remember the row counts. Draw processing stage on the horizontal axis (join, filter, sort, limit) and surviving row count on the vertical axis. The shape starts high after the join, steps down at each filter, stays flat through sorting, and gets sliced flat by LIMIT. The landmark is the filter step — the steepest drop. The takeaway: joins widen rows (more columns), filters shorten the table (fewer rows), and LIMIT only ever trims the top.

Cross-DB note: this whole pattern — INNER JOIN ... ON, WHERE, ORDER BY, LIMIT — runs unchanged in PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL. The one dialect wrinkle arrives in the sort: NULLS LAST is native in PostgreSQL, Snowflake, and Spark SQL, while MySQL needs a workaround (shown in Example 3) because it has no NULLS LAST keywords.

17.3.2 Worked Examples

The three examples grow in difficulty: one filter, then two filters plus a sort, then a computed column plus a date range plus a null-safe sort plus a cap.

Example 1 (17.3.example.1) — Japanese movies with director names and domestic revenue. The three joins above run first and return matched rows such as movie id 13 paired with 13 and 23 paired with 23 across the tables. The WHERE clause on mv.movie_lang = 'Japanese' keeps only Japanese rows. The final select list prints mv.movie_name, d.first_name, d.last_name, and r.revenues_domestic.

Steps: (1) join all three tables on both id links; (2) apply the single = filter on language; (3) project the four wanted columns. Final answer: one row per Japanese film with its director's full name and domestic gross. Sense-check: every printed language (if you add it temporarily) must read Japanese — a single English row means the filter string is misspelled.

Use plain = when one column must equal exactly one value. That is the rule behind the next example's contrast with IN.

Example 2 (17.3.example.2) — English, Chinese, and Japanese movies with domestic revenue above 100. Two filters stack with AND. The language filter uses IN with a list because one column must match any of several values:

WHERE mv.movie_lang IN ('English', 'Chinese', 'Japanese')
  AND r.revenues_domestic > 100;

Rows with small revenues such as 22 drop out. The select list prints movie name, director first and last names, and domestic revenue. An ORDER BY on the fourth select column in descending order floats the top earner to the top:

ORDER BY 4 DESC;

Titanic lands on top, followed by Star Wars and Spider-Man. Referring to a select column by its position number is the ordering trick used here. Final answer: Titanic is the top earner above 100, then Star Wars, then Spider-Man. Sense-check: read the printed revenue column top to bottom — values must strictly descend; any rise means the sort direction flipped.

IN ('English', 'Chinese', 'Japanese') is shorthand for three OR tests on the same column. ORDER BY 4 means "sort by the 4th item of my select list" — here the domestic revenue — so you avoid retyping the long name. A streaming service uses this exact shape for a "top-grossing titles by region" shelf: filter languages with IN, filter revenue with >, sort by revenue position, show the top rows.

Example 3 (17.3.example.3) — top most profitable films from 2005 through 2008. The wanted columns are movie name, director first and last names, movie language, domestic revenue, international revenue, and a computed total. The spoken form is "add revenues domestic and revenues international together to get the total revenue".

SELECT mv.movie_name, d.first_name, d.last_name,
       mv.movie_lang, r.revenues_domestic, r.revenues_international,
       r.revenues_domestic + r.revenues_international AS "total_revenue",
       mv.release_date
FROM movies AS mv
INNER JOIN directors AS d
  ON mv.director_id = d.director_id
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id
WHERE mv.release_date BETWEEN '2005-01-01' AND '2008-12-31'
ORDER BY 7 DESC NULLS LAST
LIMIT 10;

Steps: (1) join all three tables; (2) keep rows with release date inside the full-year window BETWEEN '2005-01-01' AND '2008-12-31' — note both bounds are inclusive and cover the whole first and last days; (3) compute column 7 as domestic plus international; (4) sort by column 7 tallest-first with missing revenues sunk to the bottom; (5) keep the first 10. The BETWEEN bounds run from the first day of 2005 to the last day of 2008. Nine rows qualify, so LIMIT 10 returns the same nine while still capping the output as asked. The release date column is added during build time to check the bounds, and the same join, filter, order, limit chain delivers the answer. Final answer: the 9 qualifying 2005–2008 films ranked by total revenue, top 10 cap satisfied. Sense-check: every printed release date must fall inside 2005–2008, and any row with a blank total must sit below all numbered totals.

Now the formula behind column 7, reconciled with the manifest item 17.3.formula.1.

Formalize — total revenue (17.3.formula.1): the reconstruction is \(total = domestic + international\), where \(domestic\) is the home-market revenue figure (r.revenues_domestic), \(international\) is the abroad revenue figure (r.revenues_international), and \(total\) is their sum in the same money units, displayed as:

\[total = domestic + international\]

NULLS LAST guards the sort: any film with a missing revenue has a NULL total, and without the keywords some systems float those blank rows to the top of a DESC sort. LIMIT 10 then keeps the first 10 surviving rows. MySQL workaround where NULLS LAST is unavailable: ORDER BY (total_revenue IS NULL), total_revenue DESC LIMIT 10 — the IS NULL expression sorts 0 (known) before 1 (missing), reproducing nulls-last behavior.

Double-quoted "total_revenue" follows PostgreSQL aliasing (double quotes for identifiers); MySQL would use backticks and SQL Server brackets, but a plain unquoted AS total_revenue works in all four systems including Snowflake and Spark SQL.

17.3.3 Student Questions and Answers

Two questions recur: when to use IN, and what the bare number in ORDER BY means.

Q: Why use IN for the languages but a plain equals for Japanese alone? \ A: One single value takes a plain equals. Several candidate values for the same column take IN with the list in parentheses. Both sit in WHERE after the joins.

Q: What does ORDER BY 4 mean? \ A: It sorts by the fourth item of the select list, here the domestic revenue, instead of repeating the long column name. DESC puts the largest value first. ORDER BY 7 DESC NULLS LAST in the third example works the same way on the computed total.

Positional ORDER BY is convenient but fragile: adding a column to the select list renumbers everything. Professionals use it in quick analysis and switch to explicit names (ORDER BY total_revenue DESC NULLS LAST) in saved reports.

Pitfalls (professor-flagged in bold): (1) BETWEEN bounds that clip the year — writing BETWEEN '2005-01-01' AND '2008-01-01' silently drops almost all of 2008; always bound full years as first-day to last-day. (2) Forgetting NULLS LAST on a DESC money sort — blank-revenue films can outrank real earners; append NULLS LAST (or the MySQL IS NULL workaround). (3) Sorting by a wrong position number — after editing the select list, ORDER BY 4 may point at a name column; recount positions or switch to the column name.

Exam note: BETWEEN with full year bounds, ORDER BY with a column position plus NULLS LAST, and LIMIT form a favorite exam chain. Practice writing all three from memory on the three-table join: filter dates first, compute the total, sort position DESC NULLS LAST, cap with LIMIT.

You can now run the full professional rhythm on three tables: chain the joins, stack WHERE filters, compute new columns, sort null-safely, and cap.

17.4 Joining Columns with Different Data Types

Hook — identical values, refused match: both columns say 1 and 2, both are called test, and the join still explodes with "operator does not exist". The database does not compare what your eyes see — it compares typed values, and an integer 1 is a different species from the text '1'. One CAST fixes it, and this section shows both directions plus the live proof.

Type mismatches appear constantly in real pipelines: a CSV import lands as text, the master table holds integers, and the join between them fails until someone unifies the types. Learn the error message by heart and you will diagnose it in seconds.

17.4.1 The Type Match Rule

A join predicate can only compare two columns whose data types agree. An integer column and a varchar column holding digits look alike to the eye but the database refuses the match. The two test tables make the point: t1 holds a column called test typed as integer, and t2 holds a column also called test typed as varchar(10).

The naive join fails:

SELECT * FROM t1
INNER JOIN t2 ON t1.test = t2.test;

The error reads "operator does not exist: integer = character varying", with the hint to add an explicit type cast. A data type is the declared species of a column (INT counts and calculates; VARCHAR stores text). The = operator only exists between two values of the same species, so the engine stops rather than guessing.

Intuition — plug-socket analogy: an integer plug cannot enter a text socket even if both are labeled "test". CAST is the travel adapter: it reshapes one side's plug so both fit the same socket. Casting text to integer means "read these digits as numbers"; casting integer to text means "treat these numbers as labels". Break point: a real adapter never destroys the plug, but CAST('hello' AS INT) fails outright — non-numeric text has no number to become.

That failure case is the safety feature. Rather than silently dropping or inventing matches, PostgreSQL demands you state which reading you mean.

Formalize — the type match rule and both CAST fixes (17.4.formula.1): the spoken advice is "you might need to add explicit type cast", and the reconstructed fix wraps one side in CAST so both sides share a type. Every symbol: \(t1.test\) is the integer-side value, \(t2.test\) is the varchar-side value.

Option A — compare as integers (reconciled formula 17.4.formula.1):

\[t1.test = CAST(t2.test\ AS\ INT)\]

Option B — compare as text:

\[CAST(t1.test\ AS\ VARCHAR) = t2.test\]

Step-by-step logic:

  1. Read the error: left type integer, right type character varying — no = operator spans that gap.
  2. Choose the shared target type: INT when every text value is digits (numeric comparison, so 2 > 10 is false); VARCHAR when text may hold non-digits (alphabetical comparison, so '10' < '2').
  3. Wrap exactly one side in CAST(... AS <target>).
  4. The = now sees two values of one species and pairs equal ones normally.

Picture a sorting line to lock in the choice. Draw the comparison type on the horizontal axis (number line versus dictionary order) and match result on the vertical axis. Integer comparison lays values on a number line — 2 sits far below 10. Text comparison files them like words in a dictionary — '10' files before '2' because '1' comes first. The landmark is the pair (2, 10): numbers say 2 < 10, text says '10' < '2'. The takeaway: the cast direction changes ordering and sometimes which rows match, so choose deliberately.

Cross-DB note: CAST(x AS INT) and CAST(x AS VARCHAR) are standard and run in PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL alike — keep this one version. Dialects differ only at the edges: SQL Server prefers CONVERT/TRY_CAST, and string concatenation uses || in PostgreSQL but CONCAT() in MySQL. For this lesson the portable CAST is all you need.

17.4.2 Worked Examples

The lecture shows both cast directions and then proves the behavior on live rows including a deliberately non-numeric value.

Example 1 (17.4.example.1a) — cast the varchar side to integer. The right side values turn into integers, the left side already is, and the equality can run:

SELECT * FROM t1
INNER JOIN t2 ON t1.test = CAST(t2.test AS INT);

Steps: (1) confirm t1.test is integer and t2.test is varchar; (2) wrap the varchar side so both sides are INT; (3) run — digit pairs match numerically. Final answer: digit rows pair 1-to-1 and 2-to-2 as integers. Sense-check: a value like '007' would match integer 7 here — leading zeros vanish in numeric reading, which confirms the integer direction worked.

Prefer this direction whenever the text column is guaranteed numeric (imported ids, year strings). Numeric comparison then sorts and filters the way users expect.

Example 2 (17.4.example.1b) — cast the integer side to varchar instead. Same idea in the other direction, with both sides compared as character values:

SELECT * FROM t1
INNER JOIN t2 ON CAST(t1.test AS VARCHAR) = t2.test;

Steps: (1) wrap the integer side so both sides are text; (2) run — values compare character by character. Final answer: digit rows still pair, now under text comparison. Sense-check: integer 7 becomes '7', which no longer equals '007' — if that pair stops matching, you have proven the comparison is textual.

Prefer this direction when the text side may hold letters or codes (order numbers like 'A12', padded codes like '007') that must never be forced into numbers. A warehouse system that joins integer shelf ids to scanned barcode strings uses exactly this cast.

Example 3 (17.4.example.1c) — live data check with a true-string row. Inserting 1 and 2 into t1 and 1 and 2 into t2, then joining with the cast, matches 1 to 1 and 2 to 2 across the type gap:

INSERT INTO t1 (test) VALUES (1), (2);
INSERT INTO t2 (test) VALUES ('1'), ('2');
SELECT * FROM t1
INNER JOIN t2 ON t1.test = CAST(t2.test AS INT);
-- returns pairs (1,'1') and (2,'2')

Adding a true string value to t2 widens that table:

INSERT INTO t2 (test) VALUES ('hello');

and the join keeps matching the digit pairs while leaving the non-numeric row unmatched on the integer reading — worse, if the engine tries to cast 'hello' to INT it raises an invalid-input error rather than silently skipping. Final answer: digit pairs (1, 2) match across the type gap; the 'hello' row never matches numerically and can error the cast. Sense-check: the joined count equals the count of purely numeric shared values — any extra row means a string slipped through as text comparison instead.

This is why production pipelines validate before casting: a single 'hello' in a million-row import can abort the whole join. Defensive variants (TRY_CAST in SQL Server, TRY_CAST/TRY_TO_NUMBER in Snowflake, a digit-pattern pre-filter on t2.test in PostgreSQL) quarantine bad rows first — but the exam expects the plain CAST form shown above.

17.4.3 Student Questions and Answers

One question dominates, because the failure looks impossible at first glance.

Q: The columns are both called test and hold 1 and 2. Why does the join still fail? \ A: The names match but the types do not. One side is integer and the other is varchar, and the equals operator needs the same type on both sides. CAST one side to the other type and the match works — CAST(t2.test AS INT) for numeric comparison, or CAST(t1.test AS VARCHAR) for text comparison.

Remember: same name is never enough. The ON clause checks names for columns but the = operator checks types for values — both must agree.

Pitfalls (professor-flagged in bold): (1) Casting the wrong side for the data — casting a text column full of codes to INT crashes on the first letter; inspect with SELECT DISTINCT test FROM t2 before choosing. (2) Assuming '10' = '2' behaves numerically under text cast — as strings, '10' < '2', so range filters after a varchar cast misbehave; cast to INT when ordering matters. (3) Reading "operator does not exist" as a typo — beginners recheck spelling, but integer = character varying in the message names the real culprit: the type gap, fixed only by CAST.

Exam note: the "operator does not exist, add explicit type cast" error is a strong exam signal. Write the CAST on the correct side and state the final shared type — e.g. "CAST(t2.test AS INT) so both sides are integer and \(t1.test = CAST(t2.test\ AS\ INT)\)". If the question includes a non-numeric row, state that it cannot match under the integer reading.

17.4.4 Recap and Bridge

Type agreement is a precondition, not a detail: no shared type, no equality, no join.

Recap + bridge: = needs one type on both sides — read the operator does not exist: integer = character varying error, then unify with \[t1.test = CAST(t2.test\ AS\ INT)\] (numeric) or \[CAST(t1.test\ AS\ VARCHAR) = t2.test\] (textual), and prove it with the live 1-to-1, 2-to-2 plus true-string check. 17.5 LEFT JOIN Mechanics

Hook — why LEFT JOIN runs every report: an INNER JOIN drops anything without a partner. But a shop manager asks "show me all products, even the ones with no sales yet." A teacher asks "show me all students, even those with no grade." LEFT JOIN answers that question. It keeps the whole left table and fills gaps with NULLs so nothing on the watched side goes missing.

LEFT JOIN is the first outer join in this lecture. You use it when one table is the master list that must survive whole, and the second table only adds extra detail where it exists.

17.5.1 Definition and Syntax

A LEFT JOIN keeps every row of the left table, which means the table named in FROM. Each left row looks for a twin in the right table using the ON condition. When a twin exists, the two rows glue side by side. When no twin exists, the left row still prints, and every right-side column prints NULL. NULL here means "no value here" — not zero, not blank text, but the absence of a match.

The template is:

SELECT table1.col1, table2.col1
FROM table1
LEFT JOIN table2
  ON table1.col1 = table2.col1;

That is why it is called left: the left, or first, table always survives whole. The right table only contributes where it can.

Intuition — class-list analogy: think of the left table as the class attendance list and the right table as the homework pile turned in. You walk down the attendance list name by name. If homework sits in the pile for that name, you staple it beside the name. If no homework exists, you leave the name on the list and clip an empty sleeve marked NULL. Nobody gets crossed off the attendance list. Break point: the analogy breaks when one left row matches many right rows — one student with three homework sheets repeats three times in the output, which never happens on a paper attendance list.

The staple-or-empty-sleeve picture gives you the left-preserved rule in one sentence: every left row appears at least once, matched or not.

Formalize — the left-preserved rule: let \(L\) be one row of the left table and \(R\) be one row of the right table. Keep the pair \((L, R)\) only when the test \[L.key = R.key\] is true. Then:

  1. For each \(L\), find all \(R\) rows where \(L.key = R.key\).
  2. If at least one twin exists, output one glued row per twin.
  3. If no twin exists, output \(L\) once with NULL in every \(R\) column.
  4. Never drop \(L\); never invent an \(R\).

So the output row count is always at least the left-table count: \(count(result) \ge count(left)\). It grows above that only when left rows have multiple twins.

Picture the result as two columns of dots. Put left ids down the vertical axis (1, 2, 3, 5) and right ids across the horizontal axis. Draw a line wherever ids are equal. The shape is mostly a clean diagonal for 1, 2, 3, plus one lonely left dot at 5 with no line leaving it — that lonely dot prints with NULLs. The landmark is id 5 (mic), the only left value with no partner. The takeaway: LEFT JOIN preserves the whole vertical axis and marks orphans with NULL.

LEFT and RIGHT JOIN support is universal: PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL all accept the same LEFT JOIN ... ON syntax used here, so you keep one common version.

Scope: this section covers only LEFT JOIN on an equality key with small product tables. It does not cover filtering the joined result, grouping and totals (that is Section 17.7), direction swaps (Section 17.6), or RIGHT and FULL joins (Sections 17.8–17.9). All examples use the left_products / right_products lecture tables in PostgreSQL-compatible syntax.

17.5.2 Worked Examples

The lecture builds the idea in two steps: first construct tables with deliberate gaps, then join and read the NULLs. Always inspect each table alone before you join — that habit makes the NULLs explain themselves.

Example 1 (17.5.example.1, part 1) — building the demo tables. Two small product tables make each join type visible:

CREATE TABLE left_products (
  product_id SERIAL PRIMARY KEY,
  product_name VARCHAR(100)
);
CREATE TABLE right_products (
  product_id SERIAL PRIMARY KEY,
  product_name VARCHAR(100)
);

INSERT INTO left_products (product_id, product_name) VALUES
  (1, 'computers'),
  (2, 'laptops'),
  (3, 'monitors'),
  (5, 'mics');

INSERT INTO right_products (product_id, product_name) VALUES
  (1, 'computers'),
  (2, 'laptops'),
  (3, 'monitors'),
  (4, 'pen'),
  (6, 'paper');

Steps: (1) create both tables; (2) load the left side with four rows and a deliberate gap — ids 1, 2, 3, 5, so id 4 is missing; (3) load the right side with five rows — ids 1, 2, 3 matched plus extras pen and paper under changed ids 4 and 6; (4) run SELECT * FROM left_products; and confirm 4 rows; (5) run SELECT * FROM right_products; and confirm 5 rows. Final answer: left holds 4 rows (computers, laptops, monitors, mics) and right holds 5 rows (computers, laptops, monitors, pen, paper), with the id gap plus mismatched extras guaranteeing unmatched rows on each side. Sense-check: if both tables held identical ids, no NULL could ever appear — the gap is the whole point.

The gap plus the mismatched extras are deliberate. They force unmatched rows on each side so LEFT, RIGHT, and FULL joins each tell a different story on the same data.

Example 2 (17.5.example.1, part 2) — the LEFT JOIN itself on the shared product id:

SELECT *
FROM left_products
LEFT JOIN right_products
  ON left_products.product_id = right_products.product_id;

Steps: (1) read the FROM table — left_products with 4 rows, so expect at least 4 output rows; (2) for id 1 (computers), find twin id 1 on the right and glue them; (3) repeat for id 2 (laptops) and id 3 (monitors); (4) for id 5 (mics), search the right side, find no id 5, and print the left row with NULL in every right_products column; (5) count the output. Final answer: all 4 left rows return — computers, laptops, monitors matched, and mics beside NULLs on the right because the right table holds no mic. Sense-check: left count 4 equals output count 4, and exactly one row carries right-side NULLs — the orphan you planted in Example 1.

Checking each table alone first, then comparing with the joined output, proves the rule: the left side is complete and only matching right rows attach. In a Shopify-style store catalog, this is exactly the "list all products with their latest sale, including products never sold" report — the mic row with NULLs flags the product that needs marketing follow-up.

Pitfalls (professor-flagged in bold): (1) Reading NULL as zero or blank — NULL means no twin row existed; treating it as 0 in a later SUM silently corrupts totals. (2) Joining before looking — skipping the SELECT * check on each table leaves you guessing which side the NULL came from; always count each side first (4 left, 5 right here). (3) Expecting extras from the right to appear — pen and paper live only on the right and never appear in a LEFT JOIN; beginners keep hunting for them in the output.

17.5.3 Student Questions and Answers

One question comes up every time the mic row appears, so it is answered here in the lecture's own words, deduplicated.

Q: Why does the mic row show empty cells on the right side? \ A: Mic (id 5) exists only in the left table, so there is no right row to attach. The database prints NULL for every right-side column of that row instead of dropping the left row. That NULL is the signal "left row preserved, no twin found" (17.5.qna.1).

Once you read NULL as "no twin," every later outer-join result decodes itself: preserved side survives, other side goes NULL where it cannot match.

You now own the left-preserved motion: count the left table, join on the shared key, and read right-side NULLs as orphans.

Recap + bridge: LEFT JOIN keeps all left rows and attaches only matching right rows, printing NULL where id 5 (mics) has no twin — 4 rows in, 4 rows out. 17.6 LEFT JOIN Direction and Unmatched Rows

Hook — the FROM table is the promise: LEFT JOIN always protects the table in FROM. Swap the two tables and you swap the promise. The lecture proves it with a live insert: one new director with no films changes one direction's count and leaves the other frozen. If you remember only one sentence from this section, remember "FROM survives."

Direction means choice of preserved table. You choose it deliberately every time you place a table in FROM versus in JOIN. This section shows why the choice matters even when both directions accidentally return the same count at first.

17.6.1 Table Order Decides the Output

In a LEFT JOIN the FROM table is the preserved one, so swapping the two tables changes the meaning. The lesson proves it on movies and directors, whose shared link is director id. A director id is the primary key of directors carried as a foreign key inside movies, so each film points at exactly one director while one director can own many films.

The directors-first form keeps every director:

SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id;

This keeps all 37 directors and fans out to 53 rows because some directors made several films and their name repeats once per film. A director with three films prints three rows; a director with no films prints one row with NULL movie cells.

Intuition — host-and-guest analogy: think of the FROM table as the host who invited everyone on their list, and the joined table as guests who may or may not show up. You read down the host list: for each host, you seat every guest who matches, or you leave an empty chair (NULL) when nobody comes. Swapping the tables elects a new host with a new list. Break point: the analogy breaks when one host matches many guests — the host's name repeats on several chairs, which never happens with a real guest list where each host appears once.

That host picture explains why row counts fan out. One-to-many matches multiply the host's rows: 37 hosts become 53 seated rows.

Formalize — the FROM-decides rule: in FROM A LEFT JOIN B ON A.key = B.key, table \(A\) is preserved. For each row \(a\) in \(A\), output one row per matching \(b\) where \[a.key = b.key\], or one row with NULL \(b\) columns when no match exists. Swap to FROM B LEFT JOIN A and table \(B\) is preserved instead. The two forms agree only when every row on both sides finds at least one twin; the moment one orphan exists, the counts split.

Picture the join as a fan-out chart. Put host rows down the vertical axis (37 director names) and guest matches stretching right along the horizontal axis (0, 1, 2, or 3 films each). The shape is a ragged bar chart — most bars short, a few long for prolific directors. The landmark is the zero-length bar: a director with no films and NULL guests. The takeaway: the vertical axis always survives whole, and long bars explain why 37 hosts become 53 rows.

Cross-DB note: this FROM-decides behavior is identical in PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL — LEFT JOIN always preserves the left table in every engine, so the 37-versus-53 logic ports unchanged.

Scope: this section covers only LEFT JOIN direction on the directors / movies lecture tables (37 directors, 53 films before the insert). It does not cover WHERE filters (Section 17.7), RIGHT JOIN mirrors (Section 17.8), or aggregate roll-ups. All queries use PostgreSQL-compatible aliasing (AS d, AS mv).

Reversing to FROM movies LEFT JOIN directors keeps all movies instead and also lands on 53 rows here, since every film currently has a director. The matching count is a coincidence, not proof that direction is irrelevant — the next example breaks the tie.

17.6.2 Worked Examples

The lecture runs one controlled experiment: add a single orphan row, re-run both directions, and watch only one direction move. Always count each table alone first so the new row cannot hide.

Example 1 — both directions before the insert (baseline 37 / 53). Run the two counts:

SELECT COUNT(*) FROM directors;
SELECT COUNT(*) FROM movies;
SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id;
SELECT mv.movie_name, d.first_name, d.last_name
FROM movies AS mv
LEFT JOIN directors AS d
  ON mv.director_id = d.director_id;

Steps: (1) confirm \(count(directors) = 37\) and \(count(movies) = 53\); (2) run directors-first and count 53 output rows — every director present, prolific names repeated; (3) run movies-first and count 53 output rows — every film present with its director. Final answer: both directions return 53 rows before the insert because no orphan exists yet on either side. Sense-check: when both counts match the movies count exactly, suspect full pairing — then add an orphan to test the rule.

The tie sets the trap. Beginners conclude direction never matters. The insert springs the trap.

Example 2 (17.6.example.1) — proving the FROM table rules with a fresh insert. A brand-new director with no films is added:

INSERT INTO directors (first_name, last_name, date_of_birth, nationality)
VALUES ('James', 'David', '2010-01-01', 'American');

Steps: (1) insert James David, a director row with a fresh id and zero films; (2) recount with SELECT COUNT(*) FROM directors; and confirm \(37 + 1 = 38\) directors while movies stays at 53; (3) re-run directors-first LEFT JOIN and count rows: \(53 + 1 = 54\), with the newcomer sitting beside NULL movie cells; (4) re-run movies-first LEFT JOIN and count rows: still 53, because the movies side gained nothing and the newcomer has no film to match; (5) sort both outputs by first name with ORDER BY d.first_name; and confirm James David appears only in the directors-first form. Final answer: directors-first grows 53 → 54 while movies-first stays at 53, and the first-name sort proves James David survives only when directors is in FROM. Sense-check: the directors-first count must equal old count plus one; if it did not move, the insert failed or the wrong table sits in FROM.

In a hospital-records application — for example an Epic-style patient roster joined to lab visits — this is the "show all patients including those with no visits yet" versus "show all visits including patient details" choice. Picking the wrong FROM silently drops the very people (like James David) the report was meant to catch.

Pitfalls (professor-flagged in bold): (1) Declaring direction irrelevant after one tie — 53 = 53 was luck from fully paired data; one orphan splits the counts. (2) Forgetting to recount after INSERT — without the fresh COUNT(*) of 38 directors, the 54-row result looks like an error instead of proof. (3) Reading the question stem backwards — "for each director" demands directors in FROM; putting movies in FROM answers a different question even when the column list looks identical.

17.6.4 Recap and Bridge

You now read direction fluently: FROM names the survivors, orphans expose the difference, and the question stem tells you which side to preserve.

17.7 LEFT JOIN with Filters, Grouping, and Totals

Hook — from listing rows to answering money questions: Sections 17.5–17.6 listed rows. Managers rarely want a 54-row list — they want one row per director with a number beside it: how many films, how much revenue, who earns most. This section turns the directors-first LEFT JOIN into that roll-up with WHERE, GROUP BY, COUNT, SUM, ORDER BY, and HAVING.

A roll-up collapses many joined rows into one summary row per group. You build it in a fixed order: join first, optionally filter with WHERE, group with GROUP BY, aggregate with COUNT or SUM, sort with ORDER BY, and cut groups with HAVING. Each clause answers a different question, so learn them as a chain.

17.7.1 Filtering the Joined Rows

WHERE applies after the join, so it can narrow the preserved rows. Starting from the directors-first LEFT JOIN printing first name, last name, movie name, and movie language, the English-plus-Chinese cut is:

SELECT d.first_name, d.last_name, mv.movie_name, mv.movie_lang
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id
WHERE mv.movie_lang IN ('English', 'Chinese');

Only films in those two languages survive. The IN list is the right tool whenever one column must match any of several values — it replaces a chain of OR conditions with one short test.

Intuition — sieve-then-sort-trays analogy: think of the join as pouring 54 mixed beads (one per director-film pair) into a tray, WHERE as a sieve that keeps only English and Chinese beads (43 survive), and GROUP BY as sorting the survivors into one tray compartment per director. COUNT then counts beads per compartment and SUM weighs them. Break point: the analogy breaks because a real sieve cannot resurrect beads — once WHERE drops the NULL-extended rows (directors with no English/Chinese film), no later clause brings them back, which is exactly the filter-collapse warning of Section 17.8.

That sieve picture fixes the clause order in memory: join pours, WHERE sieves rows, GROUP BY sorts into compartments, aggregates measure each compartment.

Formalize — the two roll-up formulas: the count version (17.7.formula.1) is \(COUNT(*)\) per \((first\_name, last\_name)\) group — count every joined row inside each director compartment. The revenue version (17.7.formula.2) is \(total = SUM(domestic + international)\) per director group, with \(domestic\) and \(international\) in the same money units so the addition is valid.

Step-by-step logic:

  1. Join directors to movies (and to movies_revenues for the money version) — 54 rows.
  2. Apply WHERE if present — keep only rows passing the test.
  3. Partition surviving rows by \((d.first\_name, d.last\_name)\) — one compartment per director.
  4. Inside each compartment compute \(COUNT(*)\) or \(SUM(r.revenues\_domestic + r.revenues\_international)\).
  5. Sort compartments with ORDER BY; drop whole compartments with HAVING.

The GROUP BY rule behind step 3: every plain (non-aggregated) column in the select list must also sit in GROUP BY, otherwise the database cannot pick a single value per compartment.

Picture the grouped result as a bar chart. Put directors along the horizontal axis (38 names) and the aggregate up the vertical axis (film count, or dollars of total revenue). The shape is a descending staircase after ORDER BY ... DESC — tall bars left (busiest or richest directors), short bars right, with NULL-total directors sunk to the far right under NULLS LAST. The landmark is the leftmost bar (top director) and the flat zero/NULL tail. The takeaway: grouping turns 54 scattered rows into 38 comparable bars, and sorting plus NULLS LAST puts the winners first and the unknowns last.

Cross-DB note on filter behavior: WHERE-after-outer-join collapse works the same everywhere — PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL all apply WHERE after the join, so a filter on the far table removes NULL-extended rows in every engine. Keep one common syntax here.

Scope: this section covers WHERE ... IN, GROUP BY with COUNT(*), double-quoted aliases, SUM across a second LEFT JOIN, ORDER BY with position and NULLS LAST, and HAVING on the directors (38 rows) / movies (53 films) / movies_revenues lecture schema. It does not cover RIGHT JOIN mirrors (Section 17.8) or multi-table bridge chains (Section 17.9). Syntax is PostgreSQL-compatible with cross-DB notes inline.

17.7.2 Counting Films per Director

Counting uses GROUP BY on the director name with COUNT of rows. Build it in two passes: first run SELECT * through the join to confirm 54 rows, then shape the final columns. The grouping rule that trips everyone is that every plain column in the select list must also sit in GROUP BY. Keeping movie name in the list without grouping by it raises "movie name must appear in the GROUP BY clause", and the fix is to drop the per-film column and count instead.

Example 1 (17.7.example.1; 17.7.formula.1) — films per director, 54 rows into 38 groups. The failing attempt selects d.first_name, d.last_name, mv.movie_name, COUNT(*) and groups only by the two name columns; the engine rejects the bare per-film column. The fixed query is:

SELECT d.first_name, d.last_name, COUNT(*) AS "total_movies"
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id
GROUP BY d.first_name, d.last_name
ORDER BY COUNT(*) DESC;

Steps: (1) run the star join and confirm 54 rows from 38 directors; (2) write the grouped query with only first_name, last_name as plain columns and both in GROUP BY; (3) alias the count with double quotes — AS "total_movies" — because single quotes around an alias raise an error (17.7.moment.1); (4) run and count 38 output rows, one per director, matching the 38-row directors table exactly; (5) read the top under the descending sort — the busiest directors such as Wes Anderson and Stanley lead. Final answer: 38 rows, one per director, ordered busiest-first by \(COUNT(*)\) per \((first\_name, last\_name)\). Sense-check: 38 output rows must equal the directors count (38), and the top COUNT(*) values must sum plausibly toward 54 plus one NULL-row director (James David with count 1 from his NULL-extended row).

Note the alias rule tucked inside that example. In PostgreSQL, a column alias with lowercase and underscores needs double quotes (AS "total_movies"); single quotes (AS 'total_movies') fail because single quotes mean a string literal. MySQL is lenient by default but strict with ONLY_FULL_GROUP_BY semantics for grouping; Snowflake and Databricks/Spark SQL accept the same double-quoted alias, so the double-quote form is the portable habit.

A sibling filter from the same lecture keeps all directors but only American, Chinese, and Japanese nationalities:

SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id
WHERE d.nationality IN ('American', 'Chinese', 'Japanese');

The directors-first LEFT JOIN then returns its nationality-filtered rows with their film titles beside them — same join, same IN tool, this time sieving on the preserved side (d.nationality) rather than the far side.

17.7.3 Totals with SUM, ORDER, and HAVING

The revenue version chains two LEFT JOINs — directors to movies on director id, and movies to movies revenues on movie id — then sums both revenue columns per director. The spoken form is "sum revenues domestic plus revenues international as total revenue", reconstructed as \(total = SUM(domestic + international)\) per director group, with \(domestic\) and \(international\) in the same money units.

Example 2 (17.7.example.2; 17.7.formula.2) — revenue per director with NULLS LAST and HAVING. Unaliased first attempts fail with "column first name must appear in GROUP BY or aggregate", and adding the two name columns to GROUP BY fixes it:

SELECT d.first_name, d.last_name,
       SUM(r.revenues_domestic + r.revenues_international) AS "total_revenue"
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id
LEFT JOIN movies_revenues AS r
  ON r.movie_id = mv.movie_id
GROUP BY d.first_name, d.last_name
ORDER BY 3 DESC NULLS LAST;

Steps: (1) chain both LEFT JOINs and confirm the wide rows; (2) group by d.first_name, d.last_name so the two plain columns satisfy the GROUP BY rule; (3) compute \(SUM(domestic + international)\) per group as "total_revenue"; (4) sort with ORDER BY 3 DESC — position 3 is the total — so the richest directors come first, with NULLS LAST sinking directors with no revenue to the bottom; (5) read the top — Sam Raimi, James Cameron, and George Lucas sit near the top; (6) add the earner cut:

HAVING SUM(r.revenues_domestic + r.revenues_international) > 0;

and re-run: the row count falls from 38 to 29 earners, and tighter follow-up filters push it down near 18. Directors with no films or zero revenue stay visible until HAVING removes them, which is exactly the LEFT JOIN promise. Final answer: 38 totals sorted richest-first with NULLs last; \(HAVING > 0\) keeps 29 earners (≈18 under tighter cuts). Sense-check: 38 groups before HAVING must match the directors count; after HAVING > 0 the count can only shrink, never grow — if it grows, the HAVING expression differs from the SELECT expression.

ORDER BY 3 means "sort by the third select item" and works in PostgreSQL, MySQL, Snowflake, and Spark SQL alike. NULLS LAST is native in PostgreSQL, Snowflake, and Spark SQL; MySQL lacks it, so the portable workaround there is ORDER BY (total IS NULL), total DESC — NULLs sort as 1 (last) under ascending first key. GROUP BY strictness also differs: PostgreSQL always enforces the every-plain-column-in-GROUP BY rule, while MySQL enforces it only with ONLY_FULL_GROUP_BY enabled (default in modern MySQL, but toggleable) — with it off, MySQL silently picks an arbitrary value instead of erroring, which hides the bug the lecture wants you to see.

In a Warner Bros.–style studio finance dashboard, this query is the slate roll-up: one row per director with lifetime gross beside the name, NULLs-last so unreleased projects sink to the bottom, and the HAVING > 0 variant as the "earners only" board view.

Pitfalls (professor-flagged in bold): (1) Single-quoted alias — AS 'total_movies' errors; use double quotes AS "total_movies". (2) Bare per-film column with GROUP BY — selecting mv.movie_name without grouping by it fails in PostgreSQL; drop it and print the aggregate. (3) WHERE versus HAVING mix-up — WHERE sieves joined rows before grouping and cannot use aggregates; HAVING cuts groups after aggregation and repeats the full SUM(...) expression. (4) Forgetting NULLS LAST — without it, NULL totals float where you least expect and bury the real ranking.

Student confusion clusters around the two grouping surprises, answered here in the lecture's own words, deduplicated.

17.8 RIGHT JOIN

Hook — the mirror you rarely type but must read: RIGHT JOIN keeps the second table whole instead of the first. Production code almost always rewrites it as a LEFT JOIN with swapped tables, yet exams, legacy reports, and auto-generated queries still show RIGHT JOIN. If you can read it fluently — preserved side, NULL side, filter-collapse — you can answer every "list all movies" question from either direction.

RIGHT JOIN is the mirror of LEFT JOIN. It keeps every row of the right, or second, table and attaches only matching rows from the left table. When a right row has no left twin, the left-side columns show NULL. The preserved side flips; everything else about outer-join logic stays identical.

17.8.1 Definition and Syntax

RIGHT JOIN is the mirror of LEFT JOIN. It keeps every row of the right, or second, table and attaches only matching rows from the left table. When a right row has no left twin, the left-side columns show NULL:

SELECT table1.col1, table2.col1
FROM table1
RIGHT JOIN table2
  ON table1.col1 = table2.col1;

So LEFT keeps table one whole, RIGHT keeps table two whole, and both print NULL where no match exists. The rewrite to memorize is A RIGHT JOIN B = B LEFT JOIN A — same rows, same NULLs, only the written order differs.

Intuition — mirror-image attendance list analogy: reuse the Section 17.5 class list, but now the homework pile is the protected list. Walk down the right-side list entry by entry: staple the matching left row beside it, or clip an empty NULL sleeve on the left when no match exists. The left-only entry (mic) never gets visited and vanishes. Break point: the analogy breaks the same way — one right entry with many left twins repeats across several rows, so "walk the list once" really means "print once per match plus once per orphan."

That mirror picture gives the right-preserved rule in one sentence: every right row appears at least once, matched or not, and left orphans disappear.

Formalize — the mirror rule: in FROM A RIGHT JOIN B ON A.key = B.key, table \(B\) is preserved. For each row \(b\) in \(B\), output one row per matching \(a\) where \[a.key = b.key\], or one row with NULL \(a\) columns when no match exists. Consequences: \(count(result) \ge count(right)\); left-only values never print; and FROM A RIGHT JOIN B returns exactly the rows of FROM B LEFT JOIN A.

Picture the result as the Section 17.5 dot chart mirrored. Put right ids down the vertical axis (1, 2, 3, 4, 6) and left ids across the horizontal axis. Lines connect 1, 2, 3; the right-only dots at 4 (pen) and 6 (paper) print with left-side NULLs; the left-only dot at 5 (mic) has no row on the vertical axis and vanishes. The landmark pair is pen/paper present with NULLs versus mic absent. The takeaway: RIGHT JOIN preserves the second axis and erases left orphans.

Cross-DB note: RIGHT JOIN syntax itself is universal — PostgreSQL, MySQL, Snowflake, and Databricks/Spark SQL all accept the same RIGHT JOIN ... ON form, so keep one common version. What differs is never the mirror rule, only adjacent details already met (alias quoting, NULLS LAST support) that carry over unchanged.

Scope: this section covers RIGHT JOIN as the mirror of LEFT JOIN on the left_products / right_products tables and the directors (38 rows after the James David insert) / movies (53 films) lecture tables. It does not introduce new aggregate functions — counts and sums here replay Section 17.7 from the right side. Syntax is PostgreSQL-compatible.

17.8.2 Worked Examples

The lecture replays the LEFT JOIN story from the right side in four steps: products, movies preserved, filter-collapse, then counts and earners. Count each table alone first so every NULL has an alibi.

Example 1 (17.8.example.1) — products: all five right rows survive, mic vanishes. With left products first and right products second:

SELECT *
FROM left_products
RIGHT JOIN right_products
  ON left_products.product_id = right_products.product_id;

Steps: (1) confirm 4 left rows and 5 right rows with standalone SELECT * queries; (2) run the RIGHT JOIN and count output rows: 5, matching the right side; (3) read matched rows — computers, laptops, monitors glued on ids 1, 2, 3; (4) read orphan rows — pen (id 4) and paper (id 6) beside NULL left columns; (5) confirm mic (id 5) appears nowhere, because it lives only on the left. Final answer: 5 rows — 3 matched plus pen and paper with left-side NULLs; mic vanishes. Sense-check: output count must equal the right-table count (5); if mic appears, the query is a LEFT or FULL join, not RIGHT.

Checking the right table alone first confirms all five right rows survived — the mirror of the Section 17.5 habit.

Example 2 (17.8.example.2) — movies preserved (53 films) and the reversed 54-row form. Asking for all movies means movies must be the preserved side, so it goes second:

SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
RIGHT JOIN movies AS mv
  ON mv.director_id = d.director_id;

Steps: (1) confirm 38 directors and 53 movies after the James David insert; (2) run directors-RIGHT-movies and count: all 53 films return with their directors — James David has no film, so he contributes no row here; (3) flip the tables so directors is second:

FROM movies AS mv
RIGHT JOIN directors AS d
  ON mv.director_id = d.director_id;

and count: 54 rows instead of 38, because directors with several films repeat once per film and James David with no film still appears beside NULLs; (4) add ORDER BY d.first_name; to both and show James David present only when directors is the preserved side and absent when movies is. Final answer: movies-second preserves 53 films (James missing); directors-second preserves 38 directors fanned to 54 rows (James present with NULLs). Ordering by first name is the proof technique to reuse: the sort-by-first-name test exposes exactly which side survived.

Example 3 — filters can erase the outer-join effect (filter-collapse to 43 rows both ways). Add a language filter to either the LEFT or the RIGHT form of the same query:

SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
LEFT JOIN movies AS mv
  ON mv.director_id = d.director_id
WHERE mv.movie_lang IN ('English', 'Chinese');

SELECT d.first_name, d.last_name, mv.movie_name
FROM directors AS d
RIGHT JOIN movies AS mv
  ON mv.director_id = d.director_id
WHERE mv.movie_lang IN ('English', 'Chinese');

Steps: (1) run the unfiltered LEFT form — 54 rows with James David beside NULLs; (2) add the WHERE and recount: 43 English-and-Chinese rows, because the clause runs after the join and drops every NULL-extended row whose movie_lang is NULL; (3) run the RIGHT form with the same WHERE and recount: the same 43 rows; (4) remove WHERE from either form and confirm the full 54 returns with James David restored. Final answer: both forms converge on the same 43 filtered rows; removing WHERE restores 54. Sense-check: if LEFT and RIGHT agree exactly, look for a WHERE on the far table — it silently converts the outer join into an inner-like result (17.8.moment.1).

This collapse behaves identically in PostgreSQL, MySQL, Snowflake, and Spark SQL: WHERE always runs after the join in every engine, so the 43-row convergence ports unchanged. To filter yet keep orphans, move the condition into the ON clause or add OR mv.movie_lang IS NULL.

Example 4 — counts (37 rows, James missing) and HAVING earners from the right side. Counting films per director with movies as the preserved right table:

SELECT d.first_name, d.last_name, COUNT(*) AS "total_movies"
FROM directors AS d
RIGHT JOIN movies AS mv
  ON mv.director_id = d.director_id
GROUP BY d.first_name, d.last_name
ORDER BY COUNT(*) DESC;

Steps: (1) run and count groups: 37 rows, because only directors owning at least one of the 53 films form groups — James David is missing since he has no film to preserve him; (2) compare with the Section 17.7 LEFT count of 38 — the one-row gap is exactly James David; (3) replay the revenue roll-up with RIGHT JOINs through movies_revenues, group by director, and add HAVING SUM(r.revenues_domestic + r.revenues_international) > 100 to keep earners only; (4) confirm directors with no films, such as Robert Wise in the worked run, appear only before the HAVING cut. Final answer: RIGHT-side count gives 37 groups (James excluded); the RIGHT-side revenue roll-up with HAVING keeps earners above 100 only. Sense-check: LEFT count (38) minus RIGHT count (37) must equal the orphan-director count (1) — if the gap is larger, a second filter is hiding in WHERE.

In an Airbnb-style marketplace report — all listings with their latest booking, versus all hosts with their listings — this is the daily choice between "preserve listings" (RIGHT-style, every listing visible even with a missing host record) and "preserve hosts" (LEFT-style, every host visible even with zero listings), with the HAVING variant as the earners leaderboard.

Pitfalls (professor-flagged in bold): (1) Expecting 38 from directors-on-the-right — repeats from prolific directors push it to 54; preserved count is a floor, not a ceiling. (2) Calling LEFT and RIGHT the same join after the 43-row tie — they converge only because WHERE ate the distinguishing NULL rows. (3) Filtering orphans away by accident — any WHERE on the far table (movie_lang, revenue) drops NULL-extended rows; test with and without the filter. (4) Rewriting RIGHT as LEFT incorrectly — A RIGHT JOIN B equals B LEFT JOIN A with tables swapped, not the same order with the keyword changed.

17.9 FULL JOIN and Multi-Table Joins

17.9.1 FULL JOIN Definition and Syntax

Hook — why FULL JOIN exists: LEFT JOIN saves the left table. RIGHT JOIN saves the right table. But what if you cannot afford to lose either side — every product, every director, matched or not? That is exactly when you reach for FULL JOIN.

FULL JOIN keeps every row from both tables at once. Rows that match on the ON condition glue together into one combined row. Rows with no partner still appear, with NULLs filling the missing side. In plain words: nobody is dropped.

Think of two class attendance lists taped side by side. Names on both lists share one line. A name found only on the left list still gets a line, with the right side left blank. A name found only on the right list still gets a line, with the left side left blank.

Analogy — two shopping lists: you and a friend each bring a list. You merge them so nothing is lost. Shared items appear once with both notes attached. Your-only items stay with a blank beside them. Friend-only items stay with a blank on your side.

Break point: if INNER JOIN is "only shared friends" and LEFT JOIN is "all my friends plus shared details", then FULL JOIN is "everybody I know plus everybody you know". Pause and say it in your own words before reading on.

FULL JOIN — formal rule: FULL JOIN (also written FULL OUTER JOIN) returns matched rows plus left-only rows plus right-only rows. Unmatched left rows carry NULLs on right columns; unmatched right rows carry NULLs on left columns. Syntax:

SELECT table1.col1, table2.col1
FROM table1
FULL JOIN table2
  ON table1.col1 = table2.col1;

The ON condition works exactly like other joins — usually an equality on a shared key such as product_id or director_id.

Visually, picture a Venn diagram with two overlapping circles. INNER JOIN is only the overlap. LEFT JOIN is the whole left circle. RIGHT JOIN is the whole right circle. FULL JOIN is both circles together — overlap plus both outer crescents. The outer crescents are where the NULLs live.

Scope: this section covers FULL JOIN with an equality match plus the general multi-table inner-join chain. It does not cover filtering quirks of WHERE on outer joins in depth (see Sections 17.7–17.8) or OUTER JOIN with USING/NATURAL variants (see Section 17.11). Examples use PostgreSQL, where FULL JOIN and FULL OUTER JOIN both work.

Cross-DB note: FULL OUTER JOIN works in PostgreSQL, Snowflake, and Databricks/Spark SQL. It does not work in MySQL — MySQL rejects the FULL JOIN keyword entirely. In MySQL you rewrite it as a LEFT JOIN plus UNION with a RIGHT JOIN (or second LEFT JOIN reversed). Keep this rewrite in your pocket for interviews that switch dialects.

17.9.2 Worked Examples

Example 1 — products FULL JOIN gives 6 rows. The left table has 4 rows (computers, laptops, monitors, mic). The right table has 5 rows (computers, laptops, monitors, pen, paper).

SELECT l.product_name, r.product_name
FROM left_products AS l
FULL JOIN right_products AS r
  ON l.product_id = r.product_id;

Matched: computers, laptops, monitors glue together — 3 rows. Left-only: mic has no right partner, so the right columns are NULL — 1 row. Right-only: pen and paper have no left partner, so the left columns are NULL — 2 rows. Final answer: \(3 + 1 + 2 = 6\) rows. Sense-check: the result must be at least as large as the bigger table (5), and here it is exactly one larger because both sides contribute orphans.

Reversing the tables — right table first, left table second — returns the same 6 rows. Neither side is dropped, so order cannot remove rows. Only which NULLs sit on which side flips.

Example 2 — movies and directors: 54 vs 53. Join movies to directors on director_id:

SELECT mv.movie_name, d.first_name, d.last_name
FROM movies AS mv
FULL JOIN directors AS d
  ON mv.director_id = d.director_id;

Final answer: 54 rows with FULL JOIN. The extra row is James David, a director with no film. He appears beside NULL movie columns. Swap to INNER JOIN and the count drops to 53 rows, because that one unmatched director has no pair and is discarded. Sense-check: \(54 - 53 = 1\), and that \(1\) is exactly the one filmless director — the whole gap.

Filters slice the same FULL JOIN. Adding WHERE movie_language IN ('English','Chinese') narrows it to 43 rows. Adding Japanese to the list (IN ('English','Chinese','Japanese')) widens it to 47 rows. Removing WHERE restores all 54 rows. The lesson is simple: WHERE runs after the join, so it can hide the NULL rows that FULL JOIN worked to keep.

Example 3 — the multi-table pattern: one JOIN plus its own ON per new table. To add a third table, append one more JOIN line with its own ON. Link the new table to whichever table already in the chain owns the shared column:

SELECT table1.col, table2.col, table3.col
FROM table1
JOIN table2 ON table1.col = table2.col
JOIN table3 ON table3.col = table2.col;

Each ON only talks about two tables — the newcomer and its parent in the chain. Repeat the pattern for a fourth, fifth, or tenth table. Final answer: \(N\) tables need \(N - 1\) JOIN clauses. Sense-check with 5 tables: you should count 4 JOIN ... ON ... lines.

Now watch how that pattern handles a real five-table chain with a bridge in the middle.

Example 4 — five-table chain through a bridge table. Movies, directors, and revenues join as before. Then actors enter through the bridge table movies_actors. A bridge table exists because actors and movies are many-to-many: one film has many actors, one actor appears in many films. The bridge turns that into two one-to-many steps.

SELECT *
FROM actors AS ac
JOIN movies_actors AS ma ON ma.actor_id = ac.actor_id
JOIN movies AS mv ON mv.movie_id = ma.movie_id
JOIN directors AS d ON mv.director_id = d.director_id
JOIN movies_revenues AS r ON r.movie_id = mv.movie_id;

Read the chain left to right: actors links to movies_actors on actor_id; movies_actors links to movies on movie_id; movies links to directors on director_id; movies_revenues links to movies on movie_id. One early attempt links movies to directors on movie_id by mistake, and the error gives it away because the directors table holds no movie_id. Pointing that ON at the movies table (mv.director_id = d.director_id) fixes it. Final answer: the fixed query runs and returns the full five-table row set. Sense-check: if an ON column does not exist in one of the two tables named, you have pointed the link at the wrong parent — re-read the chain.

Reordering the tables, such as starting from directors or moving revenues last, returns the same rows with the columns in a new left-to-right order. So join order changes display order, not membership, for inner joins. Start from whichever table reads best.

Pitfalls: (1) Expecting FULL JOIN to sort or deduplicate — it does neither; add ORDER BY or DISTINCT explicitly. (2) Writing the five-table chain with a wrong parent in ON, especially directors.movie_id which does not exist — always check the column belongs to both sides named. (3) Trying FULL JOIN in MySQL and hitting a syntax error — rewrite as LEFT JOIN UNION RIGHT JOIN. (4) Forgetting that a WHERE filter on one side can silently erase the NULL rows you kept.

The bridge-table pattern is universal — PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks all model many-to-many links the same way, with a small join table holding two foreign keys. Once you spot the bridge (movies_actors), the five-table query becomes four short hops.

Example 5 — bare JOIN means INNER JOIN. Rewriting every JOIN in the five-table query as INNER JOIN and re-running returns the same row count, the same columns, and the same values:

SELECT *
FROM actors AS ac
INNER JOIN movies_actors AS ma ON ma.actor_id = ac.actor_id
INNER JOIN movies AS mv ON mv.movie_id = ma.movie_id
INNER JOIN directors AS d ON mv.director_id = d.director_id
INNER JOIN movies_revenues AS r ON r.movie_id = mv.movie_id;

Final answer: bare JOIN and INNER JOIN are interchangeable in PostgreSQL. Sense-check: if counts ever differ between the two spellings, you have a typo elsewhere — the keyword is not the cause.

In production, a film-analytics team at a studio like Netflix joins exactly this kind of chain — titles to credits (bridge) to people to box-office — to answer "which actors drive revenue per director". The chain is long but each hop is one shared key.

17.10 SELF JOIN

17.10.1 Definition and Syntax

Hook — the table meets itself: how do you find films with the same length, employees sharing a manager, or rows that pair up inside one list? A normal join needs two tables, but here there is only one. The trick is to photocopy the table and join the copy to the original — that is a SELF JOIN.

A SELF JOIN compares rows inside one single table by listing that table twice under two different aliases. Typical uses are hierarchical data (employee and manager in one staff table) and row-to-row comparison inside the same table (films sharing a length).

Picture a single classroom list. You copy it onto a second sheet, label one "left copy" and the other "right copy", then draw lines between matching rows across the two sheets. The lines are the join — the paper just happens to hold the same names twice.

Analogy — doubles tennis with a mirror: one player practices against a mirror. The real player is t1, the mirror player is t2. Every shot from t1 meets a response from t2, even though there is really one person. The aliases are the labels "real" and "mirror".

Break point: before reading the syntax, ask yourself — if both copies have the same column names, how would the database know which copy you mean? That puzzle is exactly why aliases are mandatory.

SELF JOIN — formal rule: list the same table twice with two different aliases, then join the aliases on any comparison. The aliases are mandatory — without t1 and t2 every column reference is ambiguous:

SELECT ...
FROM table_name AS t1
INNER JOIN table_name AS t2
  ON t1.col = t2.col;

The ON condition can compare any two columns or expressions, as long as both sides share a data type.

Visually, imagine the table stacked twice — top copy t1, bottom copy t2 — with matching lines drawn between rows. For an equality on the key, every row connects straight across to itself. For a comparison like equal lengths, rows connect sideways to every twin with the same value, forming little clusters.

Scope: this section covers SELF JOIN with INNER JOIN on one table, the mandatory-alias rule, the same-type rule for the ON comparison, the same-length film-pairs query with its <> refinement, and the director-block ordering trick. It does not cover self-referencing hierarchies with LEFT JOIN for root rows (managers with no boss), which use the same alias idea with an outer join.

17.10.2 Worked Examples

Example 1 — self-pairing sanity check on products. List the small products table as t1 and again as t2, matching on the key:

SELECT t1.product_name, t2.product_name
FROM left_products AS t1
INNER JOIN left_products AS t2
  ON t1.product_id = t2.product_id;

Computer pairs with computer, monitor with monitor, mic with mic. Each row meets itself — a one-to-one pairing. Final answer: one output row per input row. Sense-check: a key-to-key self-match must return exactly the table's row count; anything else means the ON is wrong.

Nothing useful comes out yet — this query just proves the machinery works. But it is the fastest way to confirm your aliases are wired correctly before writing the real comparison.

Example 2 — the type rule still applies inside one table. Trying ON t1.product_name = t2.product_id mixes varchar with integer and fails with an operator-does-not-exist error. Casting the id side to varchar lets the query run:

SELECT t1.product_name, t2.product_name
FROM left_products AS t1
INNER JOIN left_products AS t2
  ON t1.product_name = CAST(t2.product_id AS VARCHAR);

Still nothing matches — no product id reads the same as a name like "computer". Final answer: 0 rows, but the query runs. Sense-check: CAST fixes the error, not the logic. Takeaway: the ON condition can be any expression, but both sides of the equals must share a type.

Pitfalls: forgetting one alias (or giving both copies the same alias) brings back the "ambiguous" error immediately. Mixing types across the ON without CAST fails the same way as a two-table join. And matching on a non-unique column like length explodes the row count — that is the point, but beginners mistake it for a bug.

Now the payoff query — the same alias machinery, but matching on a shared attribute instead of the key.

Example 3 — directors self-paired on the key. Listing directors as t1 and t2 with ON t1.director_id = t2.director_id again pairs each director with themselves. It is the same one-to-one check as Example 1, on a bigger table. Final answer: one row per director. Sense-check: same count as the directors table itself.

This confirms the pattern transfers to any table before the sideways matching begins.

Example 4 — film pairs with the same length. This is where SELF JOIN earns its keep. List movies twice, print both names plus the shared length, and match on length:

SELECT t1.movie_name, t2.movie_name, t1.movie_length
FROM movies AS t1
INNER JOIN movies AS t2
  ON t1.movie_length = t2.movie_length
ORDER BY t1.movie_length DESC;

Spider-Man 3 pairs with A Clockwork Orange, Apocalypse Now pairs with its length twins, and Battle Royale, Blade Runner, Gladiator, City of Men, There Will Be Blood, Life of Others, and Darjeeling Limited surface in matching pairs. Final answer (raw): every film paired with itself plus every length-twin, longest first. Sense-check: any film with a unique length still appears once, paired with itself.

The raw form repeats names and pairs each film with itself, so the refined form pushes a not-equal test into the ON clause:

ON t1.movie_length = t2.movie_length
AND t1.movie_name <> t2.movie_name

Self-pairs fail the <> test and fall out while true distinct pairs stay, and the descending sort puts the longest shared length, 168 minutes, on top. Final answer: distinct film pairs only, headed by the 168-minute pair. Sense-check: the top row's length column must read 168; if a film still pairs with itself, the <> line is missing or compares the wrong column.

The same-alias trick works in every dialect — PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks all require the two aliases. No database lets you self-join bare.

Example 5 — hierarchical directors-and-films display. Listing movies twice with a twist, ON t1.director_id = t2.movie_id, then ordering by t2.director_id, stacks the output like a tree: each director-id heading followed by its films. A second ordering by movie name within each group files each director's films alphabetically:

SELECT t1.movie_name, t2.movie_name
FROM movies AS t1
INNER JOIN movies AS t2
  ON t1.director_id = t2.movie_id
ORDER BY t2.director_id, t2.movie_name;

One director block reads Goldfish, Crouching Tiger, Life of Pi while another reads Grand Budapest, Rushmore, Darjeeling. Final answer: same rows, tree-shaped order. Sense-check: rows group in director-id blocks; if the blocks scatter, the first ORDER BY key is wrong.

Note this is a display trick, not a true hierarchy — it borrows numeric overlap between the two id columns to force grouping. A real employee-manager hierarchy would join employee.manager_id = manager.employee_id on the same key meaning.

17.10.3 Student Questions and Answers

Q: Why list the same table twice? Can I self join without aliases? A: No. The two copies need the names t1 and t2 so the ON clause can say which copy each column comes from. Without aliases the references stay ambiguous and the query cannot run — the mirror needs its label.

The second common question is about the clutter the raw pairs query produces.

Q: The same-length pairs include each film matched to itself. How do I drop those? A: Add a not-equal test on the names inside ON: t1.movie_name <> t2.movie_name. Self-pairs fail that test and fall out while genuine pairs between two different films stay. Keep it in ON, not WHERE, so the rule reads as part of the pairing.

Recap + bridge: SELF JOIN = one table, two aliases (t1, t2), any well-typed ON between them. Key-to-key pairs each row with itself (sanity check); attribute-to-attribute (length) finds twins, refined with <> so films never pair with themselves and the 168-minute pair tops the sort. Next, Section 17.11 covers the joins with no match at all (CROSS), the join that guesses the match (NATURAL), and the FULL OUTER + COALESCE merge.

17.11 CROSS JOIN, NATURAL JOIN, and the COALESCE Append Pattern

17.11.1 CROSS JOIN and the Cartesian Product

Hook — the join with no match: every join so far matched rows on a shared key. CROSS JOIN throws the key away. It pairs every row on the left with every row on the right — the full grid. When is that ever useful, and why can it crash a server?

A CROSS JOIN builds the Cartesian product: each left row meets each right row once. If the left table holds \(n\) rows and the right holds \(m\) rows, the result holds:

\[rows = n \times m\]

With 1000 rows on each side that grid reaches about a million rows. That one formula explains both the power and the danger of CROSS JOIN.

Picture a multiplication table. Left rows are the row labels, right rows are the column labels, and every cell where they cross is one output row. Four left labels and five right labels make a \(4 \times 5\) sheet of 20 cells.

Analogy — every shirt with every color: a shop sells 4 shirt styles and 5 colors. To print the full checklist you pair each style with each color: small-red, small-blue, and so on until every combination is listed. That checklist is a CROSS JOIN.

Break point: before reading on, guess — if the shop adds one more style, how many rows does the checklist gain? (Hint: one full pass over all colors.) Hold that thought and check it against the \(n \times m\) rule below.

CROSS JOIN — formal rule: CROSS JOIN returns all \(n \times m\) combinations and takes no ON and no predicate. Syntax:

SELECT * FROM left_products
CROSS JOIN right_products;

Because there is no matching condition, every left row repeats beside the full right table before the next left row begins.

Visually, the output reads in blocks. Row one of the left (computers) prints beside every right row first, then laptops runs the same full pass, then monitors, then mics. The left table is the outer loop; the right table is the inner loop.

Example 1 — four against five gives 20. The four-row left table against the five-row right table returns \(4 \times 5 = 20\) rows. Computers appears 5 times (once per right row), then laptops 5 times, then monitors, then mics. Final answer: 20 rows. Sense-check: \(4 \times 5 = 20\) — if you get 9, you added instead of multiplying.

Swapping the tables still returns 20 rows but the display flips: now the right-table rows lead and the left rows cycle inside. So order never changes the count yet always changes which table leads the grid.

Two spellings give the same grid. The comma form with no clause at all:

SELECT * FROM left_products, right_products;

and the boolean-true form:

SELECT * FROM left_products
INNER JOIN right_products ON TRUE;

Both return the same 20 rows in table-one-leads order. Final answer: comma, CROSS JOIN, and ON TRUE are three spellings of one grid. Sense-check: all three return 20 rows here; if one returns fewer, a leftover WHERE or ON filter crept in.

That equivalence holds everywhere — PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks all accept the comma form and the CROSS JOIN keyword, and all treat ON TRUE as "keep everything".

Example 2 — scale-up to 5586. Joining 147 actors against 38 directors returns \(147 \times 38 = 5586\) rows, computed as \(147 \times 38 = 5586\) (since \(150 \times 38 = 5700\) minus \(3 \times 38 = 114\)). Reversing to directors first keeps 5586 rows with the grid flipped. Final answer: 5586 rows either way. Sense-check: estimate \(150 \times 40 = 6000\); 5586 sits just below, which looks right.

Pitfalls — the 250k warning: never run CROSS JOIN unless the grid is truly wanted, because two ordinary 250000-row tables would aim at \(250000 \times 250000\) = 62.5 billion result rows and crush the server. Beginners also write CROSS JOIN ... ON ... — CROSS JOIN takes no ON; if you want a condition, use INNER JOIN. The sane use is small-grid generation such as pairing every shirt style with every color for a checklist. A retail chain like Zara builds exactly these small grids to plan size-by-color stock lists — hundreds of rows, never billions.

17.11.2 NATURAL JOIN

A NATURAL JOIN builds the join predicate by itself from columns that share a name in both tables. You write no ON and no column list — the database finds the same-named columns and equates them all.

Analogy — auto-handshake: imagine two teams told to "pair up people with the same badge number" without naming the badge column. They just look for matching labels. NATURAL JOIN does that with column names: same name means same handshake.

NATURAL JOIN — formal rule: NATURAL JOIN equates all shared-name columns and can wrap an inner, left, or right join. A bare NATURAL JOIN defaults to inner:

SELECT * FROM table1
NATURAL JOIN table2;

NATURAL LEFT JOIN and NATURAL RIGHT JOIN keep the outer side's unmatched rows with NULLs, just like their ON-based cousins.

Visually, NATURAL JOIN draws its lines only where the column labels match. If both tables carry product_id and product_name, both must be equal for a row to match — a two-column handshake, not one.

Example — products and movies twins. On the products tables, bare NATURAL JOIN matches on the shared columns and returns computers, laptops, and monitors. Spelling it NATURAL INNER JOIN returns the same rows, NATURAL LEFT JOIN adds mic from the left, and NATURAL RIGHT JOIN adds pen and paper from the right. The inner form equals this USING form exactly:

SELECT * FROM left_products
INNER JOIN right_products USING (product_id, product_name);

On movies and directors the shared name is director_id, so SELECT * FROM movies NATURAL JOIN directors pairs on it with no ON written. NATURAL LEFT JOIN keeps all 53 movies while NATURAL RIGHT JOIN with directors second reaches 54 by keeping James David beside NULLs, since directors with several films repeat and the filmless director still appears. Final answer: same counts as the ON versions (53 inner, 54 right) with no predicate typed. Sense-check: if NATURAL returns fewer rows than the ON version, an extra shared column you forgot about is narrowing the match.

Cross-DB note: NATURAL JOIN works in MySQL, PostgreSQL, and Snowflake, but SQL Server does not support it — there you must write the USING-equivalent as ON explicitly. Even where it works, many teams ban it in production because renaming a column silently changes the join.

Pitfalls: trusting NATURAL JOIN after a schema change — adding a same-named audit column like created_at to both tables suddenly forces it into the match and empties the result. Prefer explicit ON or USING whenever the query must survive renames. Also note NATURAL JOIN prints shared columns once, so SELECT * column order differs from the ON form.

17.11.3 Appending Tables with Different Columns

Hook — two feeds, one table: table1 tracks dates plus three metrics; table2 tracks dates plus five metrics. Their dates overlap but their columns differ. How do you stack them into one clean daily row without losing any date?

Two staging tables with mismatched columns merge with FULL OUTER JOIN plus COALESCE, where COALESCE picks the first non-NULL value of its list. Table1 holds add_date plus column1 through column3 as integers. Table2 holds add_date plus column1 through column5 as integers. Sample rows give table1 (2020-01-01: 1, 2, 3) and (2020-01-02: 4, 5, 6), and table2 (2020-01-01: NULL, 7, 8, 9, 10), (2020-01-02: 11, 12, 13, 14, 15), (2020-01-03: 16, 17, 18, 19, 20). The business rule is that table1 values win wherever both tables have a date, while column4 and column5 always come from table2.

COALESCE — formal rule: COALESCE(a, b) returns a unless a is NULL, in which case it returns b. The spoken form "COALESCE picks the first non-null value" reconstructs as \(COALESCE(t1.col,\ t2.col)\), where \(t1.col\) is the table1 value and \(t2.col\) is the table2 fallback. COALESCE is standard SQL and works identically in PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks. The merge query is:

SELECT COALESCE(t1.add_date, t2.add_date) AS add_date,
       COALESCE(t1.column1, t2.column1) AS column1,
       COALESCE(t1.column2, t2.column2) AS column2,
       COALESCE(t1.column3, t2.column3) AS column3,
       t2.column4, t2.column5
FROM table1 AS t1
FULL OUTER JOIN table2 AS t2
  ON t1.add_date = t2.add_date;

FULL OUTER JOIN on the date keeps table1-only, shared, and table2-only dates; each COALESCE then prefers table1's value with table2 as fallback.

A quick probe of SELECT COALESCE(100, 2) returning 100 shows the first-value-wins habit before it goes into the query: the first argument is not NULL, so it wins immediately.

Example — three dates merge. The result reads: 2020-01-01 keeps 1, 2, 3 from table1 with 9, 10 appended from table2 (table2's NULL in column1 loses to table1's 1); 2020-01-02 keeps 4, 5, 6 from table1 with 14, 15 appended; 2020-01-03 copies 16 through 20 straight from table2. Final answer: 3 merged rows — (01-01: 1, 2, 3, 9, 10), (01-02: 4, 5, 6, 14, 15), (01-03: 16, 17, 18, 19, 20). Sense-check: shared dates show table1's numbers, and the table2-only date survives — if 01-03 vanished, the join was INNER instead of FULL OUTER.

FULL OUTER matters because an inner join would drop the table2-only date (2020-01-03) while a left join would drop nothing here only by luck of the sample. In MySQL, which rejects FULL OUTER JOIN, rewrite this merge as a LEFT JOIN UNION RIGHT JOIN with the same COALESCE list.

Scope and pitfalls: this pattern assumes one row per date per table — duplicate dates would fan out into a mini Cartesian grid. Argument order in COALESCE is the priority order: COALESCE(t1, t2) lets table1 win, while swapping to COALESCE(t2, t1) silently flips the business rule. A data team at a shop like Shopify merges daily sales feeds exactly this way when two loads cover overlapping days with different columns.

17.11.4 Student Questions and Answers

Q: CROSS JOIN has no ON. How does the database know which rows match? A: It does not match at all. It pairs every left row with every right row, so four against five gives \(4 \times 5 = 20\) rows. Reach for the comma or ON TRUE spellings only when that full grid is the goal.

The same question returns in count form, so it is worth answering once more from the size angle.

Q: Why does swapping the CROSS JOIN tables keep 20 rows but show a different list? A: The count is fixed at left rows times right rows either way (\(n \times m\) commutes). Only the display order flips, since the first-named table always leads and the second table cycles inside each lead row.

Students then ask how a join with no written predicate can match anything.

Q: NATURAL JOIN wrote no column at all. Which column did it use? A: The shared name. On movies and directors that is director_id, and on the products tables those are the same-named id and name columns. Shared names are the whole trigger — rename one and the join changes.

Finally, the merge query raises the priority question.

Q: In the append query, why does table1 win on shared dates? A: COALESCE reads its list left to right and keeps the first value that is not NULL. With table1 first in every COALESCE call, its values beat table2 wherever both exist, while table2-only dates still flow through the FULL OUTER JOIN. The probe COALESCE(100, 2) = 100 proves first-non-NULL wins.

Exam note: state the Cartesian size formula \(rows = n \times m\) and compute the worked \(147 \times 38 = 5586\) case. For NATURAL JOIN, name the shared column that fires the implicit match. For the append pattern, write COALESCE with table1 first and join with FULL OUTER JOIN on the date.

Exam answers that name the formula, plug in the numbers, and state which table's values win score full marks even before the SQL is read.

Recap + bridge: CROSS JOIN builds the \(n \times m\) grid (\(4 \times 5 = 20\), \(147 \times 38 = 5586\), and 62.5 billion at 250k-squared, so small checklists only); order flips display, never count, and comma / ON TRUE are the same grid. NATURAL JOIN matches implicit shared names (with USING as its explicit twin). COALESCE(t1, t2) + FULL OUTER JOIN on date merges mismatched feeds with first-source wins (01-01, 01-02 from table1, 01-03 from table2). That closes the join family — Section 12 collects the exam rules that span all of them.

Exam Guidance Summary

Choosing the right join is the first decision in every exam answer. Inner joins keep only pairs with equal ON values, so unmatched rows vanish, while LEFT JOIN keeps the first table whole, RIGHT JOIN keeps the second table whole, and FULL JOIN keeps both, with NULLs marking missing twins everywhere. Before writing any SQL, read the question stem for the preserved table: "for each director" means directors belong in FROM on the preserved side, and "list all movies" means movies sit on the preserved side.

Name explicit columns in answers and avoid SELECT *, since graders check named columns and star output hides intent. Table aliases such as mv, d, and r must be defined once and used in every clause including WHERE, GROUP BY, and ORDER BY. The "ambiguous column" error always means a shared name needs its table prefix, and the "operator does not exist, add explicit type cast" error always means a CAST must unify the two sides before the equals can run.

Exam note: GROUP BY queries must list every plain select column in GROUP BY, alias with double quotes, and pair COUNT or SUM with ORDER BY plus NULLS LAST for ranked answers. BETWEEN bounds need full dates such as 2005-01-01 to 2008-12-31, IN takes multi-value lists, HAVING filters groups after aggregation, and LIMIT caps the final rows. BETWEEN with full year bounds, ORDER BY column position plus NULLS LAST, and LIMIT form a favorite exam chain on the three-table join.

A WHERE filter on the far table can collapse an outer join into inner-like output, so check whether NULL rows should survive before filtering. State the Cartesian size formula \(rows = n \times m\) and compute the \(147 \times 38 = 5586\) case wherever CROSS JOIN appears.

Key Industry Applications

Short stable aliases per table keep large production databases readable, with one agreed alias sheet shared by the team. Dot-star serves fast data checks by administrators, while shipped reports and application queries name columns to cut load and protect speed.

Primary-key to foreign-key links, such as director_id carried from directors into movies, are the standard backbone of relational design. Bridge tables such as movies_actors resolve many-to-many links into joinable one-to-many steps across five-table queries, the same pattern behind credits tables in streaming catalogs and order-line tables in retail systems.

Per-group counts, revenue sums, top-earner sorts, and HAVING cuts are the daily shape of management roll-ups and bestseller lists. CROSS JOIN grids build small checklists such as every shirt style against every color, but the same grid on 250000-row tables would target billions of rows and must stay off production servers. COALESCE with FULL OUTER JOIN merges staged feeds by date with a first-source-wins rule, a standard pattern when two loads cover overlapping days with different columns.
