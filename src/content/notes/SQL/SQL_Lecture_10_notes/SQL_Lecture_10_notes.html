# User-Defined Data Types

10.1 Domain Data Types (CREATE DOMAIN)

How can a database architect ensure that customer codes, account balances, and validation checks obey the exact same rules across dozens of tables without copying and pasting CHECK constraints into every table definition?

10.1.1 Core Syntax and Schema Scope

A database schema often requires consistent column rules across multiple tables. In standard relational design, developers define character or integer columns repeatedly. They duplicate length rules, nullability checks, and value range constraints across many tables. When business requirements change, developers must locate and alter every duplicated constraint individually. This repetition creates maintenance overhead and invites subtle data integrity bugs.

Domains help database designers standardize types in one central schema. Instead of typing the same rules repeatedly, you define them once. Any table in the database schema can then use that domain. PostgreSQL provides user-defined domains to solve this repetition. A domain (a constrained user-defined data type), written as a schema object, is a custom type based on an underlying base type. It bundles optional default values, NOT NULL constraints, and CHECK constraints into a single reusable definition.

Analogy — Shared Classes in Software Design: Domains function like shared classes in Model-View-Controller (MVC) software engineering. In object-oriented programming, developers define validation rules inside a shared model class rather than rewriting validation checks inside every controller. Any part of the application that instantiates the class inherits those rules automatically. Similarly, a PostgreSQL domain defines validation rules once in the database catalog. Any table column defined with that domain enforces those exact rules.

Where the analogy breaks: Unlike object-oriented classes, database domains cannot encapsulate executable methods or maintain internal state transitions. They operate strictly as declarative validation filters on scalar values during data insertion, updating, or type casting.

Formally, a domain \(D\) is defined as a subset of an underlying base type \(T\) constrained by a boolean predicate \(P\): \[ D = \{ v \in T \mid P(v) \} \] where \(D\) is the user-defined domain type, \(T\) is the base SQL data type (such as \(\text{VARCHAR}\) or \(\text{INT}\)), and \(P(v)\) is a boolean predicate evaluated on candidate value \(v\). The verbal description states that a domain creates a custom data type with a range, optional default, NOT NULL, or check constraint.

When a candidate value \(v\) is supplied during an INSERT, UPDATE, or explicit cast, the database evaluates \(P(v)\). If \(P(v)\) evaluates to TRUE, the value is accepted. If \(P(v)\) evaluates to UNKNOWN (such as when \(v\) is NULL), the value is accepted unless the domain explicitly includes a NOT NULL constraint. If \(P(v)\) evaluates to FALSE, the database aborts the transaction and rejects the candidate value.

Domains are strictly schema-bound. When you create a domain within a schema such as public, it resides exclusively in that schema. Queries and table definitions running in another schema cannot reference the domain without explicit schema qualification (e.g., public.domain_name). Furthermore, domains return a single scalar value. This single-value property distinguishes them from composite types, which bundle multiple distinct fields. The default value for any new domain is NULL unless specified otherwise with an explicit DEFAULT clause.

The general SQL syntax for creating a domain is:

CREATE DOMAIN <domain_name> AS <base_type>
    [DEFAULT <default_value>]
    [NOT NULL]
    [CHECK (<predicate>)];

The AS keyword is optional in standard PostgreSQL syntax. For example, writing CREATE DOMAIN my_type INT; works identically to CREATE DOMAIN my_type AS INT;.

10.1.2 Reusable Constraints and Table Usage

Consider a database schema where multiple tables store street address data in locations throughout a city. You want every address column across all tables to stay under 100 characters. You also want to disallow null values consistently. Instead of defining VARCHAR(100) NOT NULL on every table, we define a reusable domain named ADR.

Worked Example — ADR Domain and Table Mapping:

We create the ADR domain based on VARCHAR(100):

CREATE DOMAIN ADR AS VARCHAR(100) NOT NULL;

We now create a locations table that assigns the ADR domain to its address column:

CREATE TABLE locations (
    address ADR
);

In pgAdmin, expanding the locations table columns displays the data type of column address as ADR, rather than generic character varying.

Test 1: Insertion syntax and error recovery If we execute an insert without specifying the target column name:

INSERT INTO locations VALUES ('123 London');

PostgreSQL raises a syntax error near London. This occurs because the parser expects explicit target column binding when inserting into tables with single-column domain types. We resolve this syntax error by explicitly naming the target column:

INSERT INTO locations (address) VALUES ('123 London');

Querying the table confirms the stored row:

SELECT * FROM locations;

The query returns '123 London'.

Test 2: Length constraint enforcement Next, we attempt to insert a string that exceeds the 100-character boundary:

INSERT INTO locations (address)
VALUES ('This street address string is intentionally written to be exceptionally long, far exceeding the one hundred character limit established on the underlying domain definition.');

PostgreSQL rejects the row immediately with the following violation:

ERROR: value too long for type character varying(100)

Even though the locations table did not declare VARCHAR(100) directly in its CREATE TABLE statement, PostgreSQL enforces the underlying domain parameters.

Sense-check: The domain successfully centralizes both the length boundary (100 characters) and nullability check (NOT NULL), enforcing them across all referencing tables.

We can also use domains to restrict numerical values. For example, suppose an inventory or accounting system requires positive quantities. We define the validation predicate: \[ P(v) = (v > 0) \quad \text{where } v \in \mathbb{Z} \] where \(v\) is an integer value and \(P(v)\) evaluates to true when \(v\) is strictly positive. The verbal description states that the check constraint ensures the value is greater than zero.

Worked Example — Positive Numeric Range Enforcement:

We create the positive_numeric domain with an explicit check constraint:

CREATE DOMAIN positive_numeric AS INT NOT NULL CHECK (VALUE > 0);

Here, the keyword VALUE refers to the candidate data item being validated.

We create a sample table referencing this domain:

CREATE TABLE sample (
    sample_id SERIAL PRIMARY KEY,
    value_num positive_numeric
);

Step 1: Inserting a valid positive integer

INSERT INTO sample (value_num) VALUES (10);

The integer \(10\) satisfies \(10 > 0\). The row inserts cleanly into the table.

Step 2: Testing a negative integer

INSERT INTO sample (value_num) VALUES (-10);

Because \(-10 \le 0\), the predicate evaluates to FALSE. PostgreSQL rejects the transaction:

ERROR: value for domain positive_numeric violates check constraint "positive_numeric_check"

The check constraint prevents negative numbers across all tables that use positive_numeric.

Sense-check: The check constraint acts as an impenetrable barrier at the type level, preventing invalid data from ever reaching the storage engine.

10.1.3 Pattern Validation Using Regular Expressions

Domains can enforce complex string patterns using POSIX regular expressions. Placing regular expressions inside domains avoids duplicating complex regex logic across tables and prevents regex drift across application services.

Worked Example — Postal Code and Email Validation via Regex:

Case 1: US Postal Code Validation We define a domain named us_postal_code using the POSIX regex match operator ~. The pattern verifies that the candidate string consists of exactly five numeric digits:

CREATE DOMAIN us_postal_code AS TEXT CHECK (VALUE ~ '^\d{5}\$');

We create an addresses table referencing the domain:

CREATE TABLE addresses (
    address_id SERIAL PRIMARY KEY,
    postal_code us_postal_code
);

We insert a valid 5-digit postal code:

INSERT INTO addresses (postal_code) VALUES ('11000');

The string '11000' matches ^\d{5}\$, so the insert succeeds.

Next, we attempt to insert an alphabetic string:

INSERT INTO addresses (postal_code) VALUES ('ABCDE');

PostgreSQL rejects the insert with a check constraint violation because 'ABCDE' fails the regex check.

Extended Regex Note: In production environments, postal codes may require standard ZIP+4 format. We can extend the domain definition using a logical OR condition:

CREATE DOMAIN us_postal_code_extended AS TEXT
CHECK (
    VALUE ~ '^\d{5}\$'
    OR
    VALUE ~ '^\d{5}-\d{4}\$'
);

Case 2: Email Format Validation We create a proper_email domain to validate basic email structures:

CREATE DOMAIN proper_email AS VARCHAR(150)
CHECK (VALUE ~ '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\$');

We create a client_names table using proper_email:

CREATE TABLE client_names (
    client_name_id SERIAL PRIMARY KEY,
    email proper_email
);

Inserting 'a@b.com' satisfies the regular expression and succeeds:

INSERT INTO client_names (email) VALUES ('a@b.com');

Inserting 'invalid_email' fails the pattern check:

INSERT INTO client_names (email) VALUES ('invalid_email');

PostgreSQL rejects the row immediately with a constraint violation.

Sense-check: The domain guarantees that every email stored across all client tables adheres to the company format standard.

10.1.4 Value Sets and Enumerated Checks

Domains can also restrict column inputs to a discrete set of allowed literal values using the CHECK (VALUE IN (...)) clause.

Formally, set membership is defined as: \[ v \in S \quad \text{where } S = \{\text{'red'}, \text{'green'}, \text{'blue'}\} \] where \(S\) is the finite set of allowed string literals and \(v\) is the candidate input value. The verbal description states that valid colors are checked against a list containing only red, green, and blue.

Worked Example — Discrete Set Validation:

We create the valid_color domain:

CREATE DOMAIN valid_color AS VARCHAR(10) CHECK (VALUE IN ('red', 'green', 'blue'));

We create a colors table:

CREATE TABLE colors (
    color valid_color
);

We insert valid colors:

INSERT INTO colors (color) VALUES ('red');
INSERT INTO colors (color) VALUES ('green');

Both rows insert successfully because 'red' and 'green' belong to set \(S\).

Now we attempt to insert 'orange':

INSERT INTO colors (color) VALUES ('orange');

PostgreSQL blocks the command:

ERROR: value for domain valid_color violates check constraint "valid_color_check"

We can also apply this technique to user accounts and session tracking:

CREATE DOMAIN user_status AS VARCHAR(10) CHECK (VALUE IN ('enable', 'disable', 'temp'));

CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    status user_status
);

Any boolean expression can follow the CHECK clause. This enables numeric ranges, regular expressions, and set membership checks to be combined freely.

10.1.5 Catalog Inspection and Safe Deletion

You can inspect existing domains visually through pgAdmin or programmatically by querying the PostgreSQL system catalogs. In pgAdmin, expand Schemas, expand public, and select Domains to view domain attributes, base types, and constraints.

Programmatically, you can query pg_type joined with pg_namespace:

SELECT t.typname AS domain_name,
       pg_catalog.format_type(t.typbasetype, t.typtypmod) AS base_type
FROM pg_type t
JOIN pg_namespace n ON t.typnamespace = n.oid
WHERE t.typtype = 'd' AND n.nspname = 'public';

In pg_type, the column typtype stores 'd' to designate a domain data type (distinguishing it from base types 'b', composite types 'c', and enums 'e').

Deleting domains requires extreme caution. The standard drop syntax is:

DROP DOMAIN <domain_name> [CASCADE | RESTRICT];

By default, PostgreSQL uses RESTRICT. If any table column currently uses the domain, the drop operation fails:

DROP DOMAIN positive_numeric;

PostgreSQL refuses to delete the object:

ERROR: cannot drop type positive_numeric because other objects depend on it
DETAIL: column value_num of table sample depends on type positive_numeric

Adding CASCADE forces the drop:

DROP DOMAIN positive_numeric CASCADE;

DANGER — CASCADE Drops Table Columns: Running DROP DOMAIN ... CASCADE automatically drops every table column that depends on the domain! In the sample table, the entire value_num column is dropped, destroying all stored data permanently. Never execute CASCADE when dropping domains in production environments.

Worked Example — Safe Domain Removal Migration:

To delete a domain safely without losing table columns or data, execute the following four-step migration sequence:

Step 1: Inspect dependent objects Query the system catalogs to identify every table and column referencing valid_color.

Step 2: Alter dependent columns to a standard base type Convert each referencing column to its underlying primitive base type:

ALTER TABLE colors ALTER COLUMN color TYPE VARCHAR(10);

This detaches the column from the domain while preserving all stored values.

Step 3: Drop the domain safely without CASCADE

DROP DOMAIN valid_color;

Because no dependent columns remain, the drop operation succeeds cleanly.

Step 4: Verify data integrity

SELECT * FROM colors;

All existing records remain intact and readable.

10.1.6 Architectural Scope and Cross-Engine Comparisons

Scope and Boundaries:

  • Scalar limitation: Domains wrap exactly one scalar base type. They cannot store multi-attribute tuples or structured record trees.
  • Evaluation timing: Constraints are evaluated only when data is explicitly assigned, inserted, updated, or cast to the domain.
  • Cross-row / Cross-table restrictions: A domain CHECK constraint can evaluate only the candidate value (VALUE). It cannot query other columns, reference other tables, or call non-immutable subqueries.

Visualizing Domain Architecture: Think of a database column as a three-tiered pipeline:

  1. Base Storage Layer (Bottom): The primitive engine type (such as VARCHAR or INT) determining physical disk representation and byte width.
  2. Domain Validation Layer (Middle): The custom constraint gate enforcing defaults, nullability rules, and check predicates.
  3. Application Table Layer (Top): The table schemas (locations, addresses, users) declaring columns typed as the domain. Any data reaching the storage layer must pass through the validation gate.

Cross-Engine Implementation Differences: Different database engines take fundamentally different approaches to reusable type constraints:

Database Engine Domain Support Syntax / Mechanism Constraint Enforcement
PostgreSQL Full Native Support CREATE DOMAIN name AS base_type CHECK (...) Enforced strictly at schema level across all tables.
MySQL No Native Domains Column-level CHECK constraints or triggers No standalone domain object. Constraints must be defined per table (col INT CHECK (col > 0)).
Snowflake No Native Domains Table-level constraints (NOT NULL, CHECK) CHECK constraints in Snowflake are informational only (unenforced by default engine).
Databricks / Spark SQL No Native Domains Delta Lake column constraints (ALTER TABLE ... ADD CONSTRAINT) Enforced on write per Delta table; no shared schema type.

Common Pitfalls:

  1. Cascading Column Loss: Running DROP DOMAIN ... CASCADE in production, which silently drops dependent columns and deletes business data.
  2. Unqualified Schema Calls: Creating a domain in public and attempting to reference it from another schema without prefixing public.domain_name.
  3. Overly Restrictive Regex: Writing regex checks (e.g., postal code or email) that reject valid international formats or whitespace-trimmed inputs.
  4. Permissive Nulls: Forgetting that domains permit NULL values by default unless explicitly declared with NOT NULL.

Recap + Bridge: A domain encapsulates a single scalar base type with reusable check constraints and default values, standardizing validation across tables. But what if your application needs to group multiple related fields—such as a street, city, and postal code—into a single cohesive record type? For multi-attribute data structures, PostgreSQL provides composite types, which we examine next in Section 10.2.

Real-World & Domain Connection: In enterprise architectures, centralizing domain definitions like proper_email, us_postal_code, and currency_code ensures company-wide data standardization across multiple microservices sharing a PostgreSQL database. For example, financial compliance systems use domains to guarantee that monetary transaction columns across billing, payroll, and invoicing tables never store negative amounts or unapproved ISO currency symbols.

Exam note: Questions frequently test whether a domain can be used outside its schema; remember that domains are schema-scoped and only accessible within their schema unless qualified. Additionally, be prepared to explain why DROP DOMAIN ... CASCADE is dangerous (it drops dependent columns) and how to safely migrate away from a domain using ALTER TABLE ... ALTER COLUMN TYPE.

10.1.7 Student Questions and Answers

Q: Why did INSERT INTO locations VALUES ('123 London'); trigger a syntax error when inserting into the locations table?

A: The query omitted the target column name, causing a syntax error near London. Explicitly specifying the column name as INSERT INTO locations (address) VALUES ('123 London'); resolves the syntax error and allows the domain to validate the value.

A second common point of confusion arises when administrators attempt to remove domains that are currently in use:

Q: Can we use DROP DOMAIN positive_numeric CASCADE to remove a domain currently in use by tables?

A: Using CASCADE is dangerous in production because it automatically deletes every dependent table column along with its data. To drop a domain safely, first alter dependent columns to a base type like INT, and then execute DROP DOMAIN without CASCADE.

10.2 Composite Data Types (CREATE TYPE ... AS)

Why should an architect flatten a cohesive real-world entity—such as a street address, geographic coordinate pair, or monetary amount with currency—into multiple disconnected table columns when SQL can bundle them into a single structured record type?

10.2.1 Record Structure and Relational Representation

A domain wraps a single base type with constraints. In contrast, a composite type (a structured user-defined record type), written as a schema-level type, bundles multiple named fields into a single cohesive data unit. A composite type contains a list of field names, each paired with its own heterogeneous data type. Unlike scalar domains, a composite type represents and returns multiple values within a single table column.

Analogy — C-Structs and Application Data Classes: Think of a composite type as a struct in C or a @dataclass in Python. Instead of passing four separate parameters around your program for street, city, state, and postal code, you declare a single Address struct. In PostgreSQL, a composite type packages those related attributes under a single identifier in the database catalog. Any table column, stored procedure argument, or function return value can use that composite type directly.

Where the analogy breaks: In programming languages, structs exist temporarily in application memory. In PostgreSQL, composite types are persistent relational objects in the schema catalog. They can be indexed, queried with subfield operators, and joined across relational algebra queries.

Formally, a composite type \(C\) represents the Cartesian product of its attribute domains: \[ C = T_1 \times T_2 \times \dots \times T_n \] where \(C\) is the composite tuple type and \(T_i\) is the data type of the \(i\)-th attribute for \(i \in \{1, \dots, n\}\). The verbal description states that a composite data type is a list of field names with their corresponding data types that can return multiple values.

An individual value \(c \in C\) is an ordered tuple of attribute values: \[ c = (v_1, v_2, \dots, v_n) \quad \text{where } v_i \in T_i \cup \{\text{NULL}\} \] Composite types can serve as column data types in relational tables. They can also serve as argument types or return types in user-defined stored functions and procedures.

10.2.2 Defining Composite Types and Table Schema

To create a composite type, use the CREATE TYPE ... AS command, specifying each field name and its corresponding data type.

Worked Example — Address Composite Type and Table Integration:

We create an address composite type containing a city and a country:

CREATE TYPE address AS (
    city VARCHAR(50),
    country VARCHAR(20)
);

In pgAdmin, composite types appear under Schemas, expand public, and open Types.

We now create a companies table using this definition:

CREATE TABLE companies (
    camp_id SERIAL PRIMARY KEY,
    address address
);

The address column now holds composite records rather than primitive scalars. PostgreSQL treats this column as a composite object, preventing developers from accidentally altering the column directly to an incompatible primitive type such as integer without explicit conversion.

10.2.3 Data Insertion Using the ROW Constructor

When inserting data into a composite column, use the SQL standard ROW(...) constructor. The constructor bundles comma-separated scalar values into a composite record matching the type definition.

Worked Example — Inserting Composite Records:

We insert two company records into the companies table:

INSERT INTO companies (address) VALUES (ROW('London', 'UK'));
INSERT INTO companies (address) VALUES (ROW('New York', 'US'));

The ROW constructor bundles distinct values into composite records. While PostgreSQL allows omitting the word ROW in certain literal contexts, writing ROW(...) is standard SQL and prevents parser ambiguity.

Querying the entire table:

SELECT * FROM companies;

PostgreSQL outputs composite values enclosed in parentheses:

 camp_id |      address      
---------+-------------------
       1 | ("London",UK)
       2 | ("New York",US)

Values containing spaces or special punctuation (such as "London" and "New York") are automatically quoted inside the parenthesis representation.

Sense-check: The two distinct attributes (city and country) are successfully stored and retrieved as a single composite value within the address column.

10.2.4 Field Access and Disambiguation Syntax

To select an individual field from a composite column, use dot notation. You must wrap the composite column name in parentheses:

SELECT (address).country FROM companies;
SELECT (address).city FROM companies;

The parentheses prevent confusion between column.field and table.column. If you write SELECT address.country FROM companies;, PostgreSQL interprets address as a table name and country as a column name. Because no table named address exists in the FROM clause, PostgreSQL raises a syntax error.

When joining multiple tables or writing complex queries, add the table name inside the parentheses:

SELECT (companies.address).country FROM companies;

This syntax provides disambiguation between table name, composite column, and field.

Worked Example — Inventory Filtering on Composite Attributes:

We define a second composite type, inventory_item, containing product information:

CREATE TYPE inventory_item AS (
    product_name VARCHAR(200),
    supplier_id INT,
    price NUMERIC
);

We create an inventory table:

CREATE TABLE inventory (
    inventory_id SERIAL PRIMARY KEY,
    item inventory_item
);

We insert records using the ROW constructor:

INSERT INTO inventory (item) VALUES (ROW('pen', 10, 4.99));
INSERT INTO inventory (item) VALUES (ROW('paper', 20, 10.99));

We can filter rows using a WHERE condition on an individual composite field. Formally, this relational selection is written as: \[ \sigma_{(item).price < 5.00}(\text{inventory}) \] where \(\sigma\) represents the relational selection operator filtering rows where attribute \(price\) of composite attribute \(item\) is strictly less than \(5.00\). The verbal description states that we filter the inventory table to see items where the price is less than five dollars.

We execute the query:

SELECT (item).product_name FROM inventory WHERE (item).price < 5.00;

Output:

 product_name 
--------------
 pen

The query evaluates \((4.99 < 5.00) = \text{TRUE}\) and returns 'pen'.

If we filter for prices greater than 3.99:

SELECT (item).product_name FROM inventory WHERE (item).price > 3.99;

Output:

 product_name 
--------------
 pen
 paper

Both rows satisfy the predicate since \(4.99 > 3.99\) and \(10.99 > 3.99\).

Sense-check: Subfield extraction inside filtering predicates works identically to standard table column operations, provided parentheses surround the composite column.

10.2.5 Modifying Attributes, Schemas, and Ownership

PostgreSQL allows modifying existing composite types using the ALTER TYPE command.

Worked Example — Composite Type Lifecycle Operations:

We create a sample composite type:

CREATE TYPE my_address AS (
    city VARCHAR(50),
    country VARCHAR(20)
);

Operation 1: Renaming the type

ALTER TYPE my_address RENAME TO my_underscore_address;

Operation 2: Changing type ownership

ALTER TYPE my_underscore_address OWNER TO app_admin;
ALTER TYPE my_underscore_address OWNER TO postgres;

Operation 3: Moving the type to another schema

CREATE SCHEMA test_sqm;
ALTER TYPE my_underscore_address SET SCHEMA test_sqm;

Operation 4: Adding an attribute to the composite type

ALTER TYPE test_sqm.my_underscore_address ADD ATTRIBUTE street_address VARCHAR(150);

Always prefix the type name with its schema name when the type resides outside public.

10.2.6 Scope, Architectural Boundaries, and Cross-Engine Comparisons

Scope and Boundaries:

  • No Direct Column Constraints: In standard PostgreSQL, you cannot attach NOT NULL, PRIMARY KEY, or CHECK constraints directly to individual subfields inside a CREATE TYPE statement. Any constraints must be enforced at the table level using table-level check constraints on the composite column.
  • Relational Normalization: Composite types should represent tightly coupled attributes (such as 2D/3D points or address coordinates). They should not be used to bypass normalization for one-to-many relationships, which belong in separate tables with foreign keys.

Visualizing Composite Records in Table Storage: A standard table stores primitive columns as sequential values in the row tuple header. When a composite type is introduced:

  1. Outer Row Header: Contains column pointers for the main table.
  2. Composite Field Payload: The composite column contains an internal tuple descriptor packing the subfield values (city, country).
  3. Subfield Accessor: The SQL parser resolves (table.column).subfield by looking up the composite type's catalog definition and extracting the attribute at the matching byte offset.

Cross-Engine Implementation Differences: Support for structured composite types varies significantly across modern database engines:

Database Engine Composite Type Support Syntax / Constructor Subfield Access Syntax
PostgreSQL Native User-Defined Types CREATE TYPE name AS (...)
ROW('London', 'UK')		 (address).city
(companies.address).city
MySQL No Composite Types Not supported. Uses JSON type or flattened columns. JSON_EXTRACT(col, '\$.city')
or col->>'\$.city'

or address['city']
Databricks / Spark SQL Native STRUCT Type STRUCT<city: STRING, country: STRING>

(Standard dot notation without parentheses)

Common Pitfalls:

  1. Missing Parentheses in Selection: Writing SELECT address.city FROM companies; instead of SELECT (address).city FROM companies;, which causes parser syntax errors.
  2. Missing Table Qualifier in Joins: In multi-table joins, writing SELECT (address).city can cause ambiguity if multiple tables have an address column. Disambiguate by writing SELECT (companies.address).city.
  3. Overusing Composites for Relational Data: Packaging entities that require independent lifecycle management or foreign key references into composite types rather than normalized tables.

Recap + Bridge: Composite types group heterogeneous fields into a single structured record, providing clean encapsulation for multi-attribute entities. However, what if your application does not need multi-field records, but instead requires a column to strictly allow a static, ordered list of discrete labels (such as currency codes or workflow states)? For this requirement, PostgreSQL provides Enumerated Data Types (ENUMs), which we explore in Section 10.3.

Real-World & Domain Connection: Composite types such as address or inventory_item allow e-commerce, logistics, and enterprise resource planning (ERP) platforms to package related fields into cohesive table columns. For instance, shipping services store origin and destination addresses as composite records, simplifying stored procedures and ensuring that address attributes are always transferred together.

Exam note: Remember the mandatory parentheses in (column_name).field_name; writing column_name.field_name without parentheses is a common exam trick that causes syntax errors. Also remember that when qualifying with a table name, both table and column must be enclosed in parentheses: (companies.address).country.

10.2.7 Student Questions and Answers

Q: Why does querying SELECT address.country FROM companies; produce an error or unexpected behavior?

A: The parser interprets address.country as table.column rather than composite_column.field. You must enclose the composite column in parentheses, writing SELECT (address).country FROM companies; to extract the subfield.

A second question often arises regarding how values must be passed during insert operations:

Q: How should multiple values be formatted when inserting a row into a table with a composite column?

A: Use the ROW(...) constructor syntax, such as ROW('London', 'UK'), within the VALUES clause. This constructor bundles the distinct values into a single composite record matching the type definition.

10.3 Enumerated Data Types (CREATE TYPE ... AS ENUM)

How can a database enforce that a status column allows only 'pending', 'approved', or 'declined' while consuming only 4 bytes of storage per row, maintaining natural workflow ordering, and eliminating the CPU overhead of repetitive string comparisons?

10.3.1 Enum Definition and Range Inspection

An enumerated data type (enum), written as a schema-level type, is a custom data type comprising a static, ordered set of textual labels. Enums provide compile-time type safety at the schema layer, preventing invalid strings from being inserted into table columns. Internally, PostgreSQL stores each enum value as a compact 4-byte integer identifier pointing to the system catalog, while presenting the value to queries and client applications as a readable text string.

Analogy — Symbolic Enums in Programming Languages: Think of an enum in SQL like an enum in C, Java, or TypeScript. Rather than passing arbitrary string literals like "pending" and "approved" across your code—which risks spelling mistakes like "Pending" or "apprved"—you define a discrete set of constants. The compiler checks every assignment. Similarly, PostgreSQL verifies every enum value against the catalog, rejecting unlisted strings immediately.

Where the analogy breaks: In application code, modifying an enum is as simple as editing a source file and recompiling. In a database, enum definitions are persistent catalog rows referenced by millions of table rows. Adding values in-place is supported, but dropping a value requires recreating the type.

Formally, an enum \(E\) is an ordered, finite sequence of unique textual labels: \[ E = \langle e_1, e_2, \dots, e_k \rangle \quad \text{with strict order } e_1 < e_2 < \dots < e_k \] where \(E\) is the enumerated type, \(k\) is the total number of labels, and each \(e_i\) represents a distinct identifier in the ordered domain. The verbal description states that we create a currency enum data type with currency values USD, EUR, and GBP.

The sequence in which enum labels are defined establishes their sorting order. Because \(e_1 < e_2 < \dots < e_k\), comparison operators (<, <=, >, >=) evaluate labels based on their defined position rather than their lexicographical (alphabetical) order. For example, in \(E = \langle \text{'USD'}, \text{'EUR'}, \text{'GBP'} \rangle\), the predicate ('USD' < 'EUR') evaluates to TRUE.

Worked Example — Currency Enum Definition and Range Inspection:

We create the currency enum type:

CREATE TYPE currency AS ENUM ('USD', 'EUR', 'GBP');

To inspect all valid labels of an enum programmatically, use the built-in enum_range() function:

SELECT enum_range(NULL::currency);

Output:

      enum_range       
-----------------------
 {USD,EUR,GBP}

We can append new values to the enum using ALTER TYPE ... ADD VALUE:

ALTER TYPE currency ADD VALUE 'CHF' AFTER 'EUR';

Querying enum_range(NULL::currency) confirms the updated sequence:

SELECT enum_range(NULL::currency);

Output:

        enum_range         
---------------------------
 {USD,EUR,CHF,GBP}

Sense-check: The new label 'CHF' was inserted between 'EUR' and 'GBP', preserving positional ordering.

10.3.2 Table Integration and Default Column Values

Once created, an enum type can be assigned to columns in any table within the database.

Worked Example — Table Integration and Default Column Values:

Case 1: Stocks Table Integration We integrate the currency enum into a stocks table:

CREATE TABLE stocks (
    stock_id SERIAL PRIMARY KEY,
    stock_currency currency
);

We insert valid currencies:

INSERT INTO stocks (stock_currency) VALUES ('USD');
INSERT INTO stocks (stock_currency) VALUES ('CHF');

Both records insert cleanly. If we attempt to insert an invalid or unlisted currency string:

INSERT INTO stocks (stock_currency) VALUES ('USD1');

PostgreSQL aborts the transaction immediately:

ERROR: invalid input value for enum currency: "USD1"

Case 2: Workflow Table with Default Status We can assign a default enum value to a column during table creation. We define a status enum:

CREATE TYPE status AS ENUM ('pending', 'approved', 'declined');

We create a cron_jobs table where the status column defaults to 'pending':

CREATE TABLE cron_jobs (
    cron_job_id INT PRIMARY KEY,
    status status DEFAULT 'pending'
);

We insert rows without supplying a value for the status column:

INSERT INTO cron_jobs (cron_job_id) VALUES (1);
INSERT INTO cron_jobs (cron_job_id) VALUES (2);

Both rows automatically receive 'pending' as their default status. We can also override the default with an explicit valid value:

INSERT INTO cron_jobs (cron_job_id, status) VALUES (3, 'approved');

However, inserting an unlisted value fails:

INSERT INTO cron_jobs (cron_job_id, status) VALUES (4, 'completed');

PostgreSQL raises an error because 'completed' is not part of the status enum.

Dropping Unused Enum Types: If an enum type is no longer referenced by any table column or database object, it can be dropped using DROP TYPE:

CREATE TYPE sample_type AS ENUM ('A', 'B', 'C', '1', '2', '3');
DROP TYPE sample_type;

Sense-check: Enums enforce type constraints at write time, preventing invalid strings from entering default or explicit column values.

10.3.3 Modifying Enum Values In-Place

PostgreSQL provides flexible commands to modify enum labels without recreating the type, including renaming labels and inserting new labels at precise positions.

Worked Example — In-Place Label Renaming and Positional Insertion:

We create a my_colors enum:

CREATE TYPE my_colors AS ENUM ('green', 'red', 'blue');

Step 1: Renaming an existing value We rename the label 'red' to 'orange':

ALTER TYPE my_colors RENAME VALUE 'red' TO 'orange';

Querying enum_range(NULL::my_colors) displays:

 {green,orange,blue}

Existing table rows holding the old label 'red' automatically reflect 'orange' because the underlying internal integer OID remains unchanged.

Step 2: Adding a value before an existing label

ALTER TYPE my_colors ADD VALUE 'red' BEFORE 'green';

The range becomes:

 {red,green,orange,blue}

Step 3: Adding a value after an existing label

ALTER TYPE my_colors ADD VALUE 'purple' AFTER 'green';

The final positional range is:

 {red,green,purple,orange,blue}

Attempting to add a label that already exists raises an error, ensuring label uniqueness.

10.3.4 Production Migration Strategy for Dropping Enum Values

While PostgreSQL allows adding and renaming enum values in-place, it does not provide an ALTER TYPE ... DROP VALUE command. When business logic deprecates an existing enum value, administrators must execute a 5-stage production migration.

Purpose of the 5-Stage Migration: PostgreSQL prevents dropping enum values directly because system catalogs (pg_enum) and existing table row pages rely on the internal OIDs assigned to each label. Dropping a label in-place could corrupt stored disk pages or invalidate active indexes. The 5-stage migration replaces the legacy enum type safely without table recreation or data corruption.

Inputs, Outputs, and Type Coercion:

  • Input: A jobs table using status_enum with labels 'queued', 'waiting', 'running', 'done'.
  • Target: Remove 'waiting' and map all existing waiting jobs to 'running'.
  • Output: A jobs table using updated status_enum containing only 'queued', 'running', 'done'.

The type conversion between distinct enum objects requires an explicit two-step cast function: \[ f_{\text{cast}}(v) = (v::\text{text})::E_{\text{new}} \] where \(v \in E_{\text{old}}\) is the initial enumerated value, coerced first to intermediate type \(\text{text}\), and then cast to target type \(E_{\text{new}}\). The verbal description states that PostgreSQL cannot convert directly between two user-defined enums. It requires an intermediate cast to text using the USING clause.

Worked Example — Executing the 5-Stage Migration:

We set up the initial schema and test data:

CREATE TYPE status_enum AS ENUM ('queued', 'waiting', 'running', 'done');

CREATE TABLE jobs (
    job_id SERIAL PRIMARY KEY,
    job_status status_enum
);

INSERT INTO jobs (job_status) VALUES ('queued'), ('waiting'), ('running'), ('done');

Stage 1: Update existing table rows Eliminate references to the deprecated value by reassigning them:

UPDATE jobs SET job_status = 'running' WHERE job_status = 'waiting';

Stage 2: Rename the legacy enum type

ALTER TYPE status_enum RENAME TO status_enum_old;

Stage 3: Create the replacement enum type Create the new type containing only active labels:

CREATE TYPE status_enum AS ENUM ('queued', 'running', 'done');

Stage 4: Alter the table column with an intermediate text cast

ALTER TABLE jobs
ALTER COLUMN job_status TYPE status_enum
USING job_status::text::status_enum;

Direct conversion between status_enum_old and status_enum fails because PostgreSQL treats them as distinct types. The ::text::status_enum bridge converts each label to an intermediate string and then to the new enum.

Stage 5: Drop the legacy enum type

DROP TYPE status_enum_old;

We verify the final state:

SELECT * FROM jobs;

Output:

 job_id | job_status 
--------+------------
      1 | queued
      2 | running
      3 | running
      4 | done

Sense-check: The table now uses the updated enum without data loss, and all former 'waiting' records are safely reassigned to 'running'.

10.3.5 Idempotent Type Creation via PL/pgSQL

Standard SQL lacks a CREATE TYPE IF NOT EXISTS statement. When automated continuous integration (CI) or deployment pipelines execute database migration scripts, running CREATE TYPE on a type that already exists causes an error and aborts the deployment.

Worked Example — Idempotent Type Creation:

To ensure deployment scripts can be executed repeatedly without failing, use a conditional PL/pgSQL procedural block. The block queries the pg_type catalog before attempting creation:

DO '
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = \'sample_composite_type\') THEN
        CREATE TYPE sample_composite_type AS (a TEXT, b INT);
    END IF;
END;
' LANGUAGE plpgsql;

On the initial deployment run, pg_type contains no matching entry, and PostgreSQL creates sample_composite_type. On subsequent runs, the IF NOT EXISTS check evaluates to false, and the block exits cleanly without errors.

10.3.6 Scope, Architectural Boundaries, and Cross-Engine Comparisons

Scope and Boundaries:

  • Static vs Dynamic Sets: Enums are optimized for small, static lists (fewer than 50 values) that rarely change, such as workflow states, cardinal directions, or currency symbols.
  • When to Use Reference Tables Instead: If allowed values change frequently, require multilingual descriptions, or need foreign key relationships to other tables, use a normalized reference table with a primary key instead of an enum.
  • Storage and Indexing: Each enum value occupies only 4 bytes of disk space per table row, making enum columns significantly faster to index (B-tree) and compare than raw VARCHAR strings.

Visualizing Enum Storage in PostgreSQL:

  1. Catalog Layer (pg_enum): Contains rows mapping (enumtypid, enumsortorder, enumlabel).
  2. Table Storage Layer: Each row in a user table stores a 4-byte OID pointing to the corresponding pg_enum entry.
  3. Display Layer: During query projection (SELECT), the engine resolves the 4-byte OID to its text label string.

Cross-Engine Implementation Differences: Support for enumerated data types differs sharply across major database systems:

Database Engine Enum Support Definition Mechanism Dropping / Modifying Values
PostgreSQL Standalone Schema Object CREATE TYPE name AS ENUM (...) (reusable across all tables) ADD VALUE / RENAME VALUE in-place; dropping values requires 5-stage migration.
MySQL Column-Level Data Type col ENUM('a', 'b', 'c') defined directly in CREATE TABLE Modified directly via ALTER TABLE tbl MODIFY COLUMN col ENUM(...).
Snowflake No Native Enum Type Enforced via CHECK (col IN ('a', 'b', 'c')) or lookup tables Handled via table constraint replacement or lookup table updates.
Databricks / Spark SQL No Native Enum Type Stored as STRING with Delta Lake table CHECK constraints Handled via ALTER TABLE tbl ADD/DROP CONSTRAINT.

Common Pitfalls:

  1. Attempting Direct Drop: Searching for or trying to run ALTER TYPE ... DROP VALUE, which does not exist in PostgreSQL.
  2. Omitting the Intermediate Text Cast: Running ALTER COLUMN col TYPE new_enum USING col::new_enum without casting through text, which raises a type conversion error.
  3. Alphabetical Sorting Assumption: Assuming enum values sort alphabetically in ORDER BY clauses; enums always sort according to their declared positional order in CREATE TYPE.
  4. Enum Bloat: Adding hundreds of volatile labels to an enum instead of using a standard relational lookup table.

Recap + Bridge: Enumerated types deliver high performance and compile-time type safety for discrete label sequences. Combined with Domains (which constrain single scalar base types) and Composite Types (which group multiple heterogeneous fields into records), PostgreSQL provides a robust, extensible type system for complex data modeling.

Real-World & Domain Connection: The 5-stage enum migration strategy is standard DevOps practice in high-availability financial, healthcare, and e-commerce platforms to avoid downtime. For example, payment processing pipelines use enums to represent transaction states ('authorized', 'captured', 'refunded', 'chargeback'), ensuring high-speed index lookups while preventing invalid state transitions.

Exam note: Be prepared to write the five-step production migration sequence for removing an enum value, specifically highlighting the USING column::text::new_enum cast. Also remember how to create types idempotently in PL/pgSQL by querying pg_type.

10.3.7 Student Questions and Answers

Q: Why does PostgreSQL not provide an ALTER TYPE ... DROP VALUE command, and how do we remove an enum value safely?

A: PostgreSQL does not support dropping enum values directly because labels are referenced in system catalogs. To remove a value, first update existing table rows. Next, rename the old enum and create a new enum without the unwanted value. Then alter the table column using an intermediate cast through text. Finally, drop the old enum.

A second question frequently arises when developers attempt to alter an existing column to a new enum type:

Q: Why is USING job_status::text::status_enum required when altering a column to a newly created enum?

A: PostgreSQL cannot directly cast between two distinct user-defined enum types even if they share identical label names. Casting first to text converts the enum label into an intermediate string, which can then be safely converted into the new enum type.

Exam Guidance Summary

  • Domain Scope: Domains are schema-bound. A domain defined in public cannot be accessed in another schema without qualification (public.domain_name).
  • Dropping Domains with CASCADE: Executing DROP DOMAIN ... CASCADE deletes all dependent table columns and their data. Always alter dependent columns to base types first before dropping the domain.
  • Composite Column Parentheses: Wrap composite column names in parentheses when extracting fields: (address).city. Omitting parentheses causes syntax errors because the parser interprets address.city as table.column.
  • Disambiguating Table and Composite Field: Place both table and column inside parentheses when joining or qualifying: (companies.address).city.
  • Inserting Composite Records: Always use the SQL standard ROW(...) constructor when inserting values into composite columns: ROW('London', 'UK').
  • Enum In-Place Additions: Enums allow adding values before or after existing elements using ALTER TYPE ... ADD VALUE 'val' BEFORE 'existing' or AFTER 'existing'.
  • Enum Dropping Workaround: PostgreSQL lacks ALTER TYPE ... DROP VALUE. To drop enum values, execute the 5-stage migration: update table rows, rename the old enum, create the new enum, alter the column with USING column::text::new_enum, and drop the old enum.
  • Idempotent Type Creation: Because PostgreSQL lacks CREATE TYPE IF NOT EXISTS, wrap type creation in a conditional PL/pgSQL block querying pg_type to ensure deployment scripts run idempotently.

Key Industry Applications

  • Centralized Data Standardization: Domains like proper_email and us_postal_code centralize validation rules, ensuring data integrity across application services and preventing data drift in microservice architectures.
  • Cohesive Data Modeling: Composite types like address and inventory_item package related attributes together, simplifying table designs and stored procedure parameters in enterprise platforms.
  • Safe Schema Migrations: The five-step enum replacement pattern enables database administrators to alter production enums without table locks or data loss in high-availability environments.
  • Automated Deployment Scripts: Using PL/pgSQL blocks to check pg_type enables idempotent database migrations in continuous deployment (CI/CD) pipelines.
