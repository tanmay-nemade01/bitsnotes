# Grouping Data

16.1 Using GROUP BY

16.1.1 What GROUP BY Does

Hook: How do you turn a flat list of 53 movies into a one-line-per-language report — counts, averages, longest titles — with a single query and no spreadsheet?

A GROUP BY clause (a part of a SELECT statement that splits the returned rows into groups built around shared values) is one of the most powerful tools in SQL and PostgreSQL. Its job is simple to state: take all the rows that a SELECT statement returns and divide them into groups built around the values in one column. Once the rows sit in groups, an aggregate function (a function such as COUNT, SUM, MIN, MAX, or AVG that turns many values into one single value) runs separately on each group. So instead of one answer for the whole table, there is one answer per group.

Intuition: Think of it like sorting mail into pigeonholes. Every movie goes into the pigeonhole marked with its language, and then each pigeonhole gets counted, averaged, or summed on its own. The mapping is exact: pigeonhole labels are the distinct grouping-column values, letters inside one pigeonhole are the rows of that group, and the clerk tallying each pigeonhole separately is the aggregate function running per group. The analogy breaks in one place: a clerk could tally letters across pigeonholes, but an aggregate in a grouped query only ever sees the rows of its own group. Hold onto this split-then-compute picture, because every later clause in these notes — HAVING, ORDER BY on aggregates, NULL handling — hangs off the same idea.

Formalize: A grouped query has two moving parts. The grouping column (named in GROUP BY) decides how rows are cut into sets, and the aggregate call (in the SELECT list) reduces each set to one value. With no GROUP BY clause there is a single implicit group — every row in the table — so a lone aggregate returns one grand answer for the whole table. Adding GROUP BY makes the groups explicit: one group per distinct value (or value combination) of the grouping column, and one aggregate answer per group. One more property matters from the start. GROUP BY wipes out duplicate values in the result, so it behaves much like DISTINCT: when rows collapse into a group, only one row per group comes back out.

Picture the result as a small bar chart. The horizontal axis lists the groups — Portuguese, German, English, Chinese, Japanese — and the vertical axis shows the aggregate, such as the count of movies. Each bar is one group, its height is the per-group answer, and the grand total is the sum of all bar heights. The takeaway: grouping never changes the underlying rows, it only changes the level at which they are reported.

Scope: GROUP BY applies after raw-row filtering and before output shaping, so it sees exactly the rows WHERE leaves behind. Assumption: the grouping column's values define the groups — rows with equal values land together, and rows whose grouping value is missing gather into one NULL group (the full story is in 16.7). Aggregates inside a grouped query run per group and skip missing inputs, so a NULL movie length never drags an average down; it is simply left out of that group's math.

Grouped aggregates answer "how much per category" questions: rentals per customer, payments per customer, films per actor. Rental records stored at one row per rental become one row per customer with a count beside it — the same split-then-compute idea, moved up to a coarser grain. Streaming catalogs, sales ledgers, and engagement logs all get summarized this way before anyone plots or thresholds them.

16.1.2 Core Syntax

Syntax: The basic query shape with an aggregate over a grouped column looks like this:

SELECT column_1, AGGREGATE_FUNCTION(column_2)
FROM table_name
GROUP BY column_1;

Here column_1 is the grouping column — the one whose values define the groups — and it can be a list of columns as well. AGGREGATE_FUNCTION here is not a real function name. It is a stand-in for a real aggregate such as COUNT, SUM, MIN, MAX, or AVG, and column_2 is the column that the aggregate reads. In words the demo says things like "count of movie language", written \(\text{COUNT}\) applied to a column, or "average of movie length", written \(\text{AVG}\) applied to a column. The grouping column named right after SELECT must also appear in the GROUP BY line. That is a hard rule, not a style tip: the GROUP BY line tells the engine which column builds the groups, so leaving it out is an error.

Line by line: the SELECT list names one bare grouping column plus one aggregate call; FROM picks the table; GROUP BY repeats the bare column so the engine knows how to cut the rows. Any bare column in SELECT that is missing from GROUP BY fails with the message that the column must appear in the GROUP BY clause or sit inside an aggregate function.

Across databases this shape is the same, with small extras worth knowing. MySQL enforces the bare-column rule strictly when its ONLY_FULL_GROUP_BY mode is on (the default in modern versions) and rejects loose queries. PostgreSQL is strict too, but it excuses extra bare columns that are functionally dependent on the grouping key — grouping by a primary key lets you select other columns of that same table. Snowflake and Databricks accept the standard shape and additionally offer GROUP BY ALL, which groups by every non-aggregate SELECT item automatically. The common core never changes: bare columns must be grouped, aggregates compute per group.

Pitfalls: Writing the aggregate without GROUP BY gives one grand total and no groups — correct syntax, wrong question. Adding the bare column without the GROUP BY line fails outright. And naming a literal function called AGGREGATE_FUNCTION fails too, since it is only a stand-in name in these notes.

16.1.3 Worked Examples on the Movies Table

Every example below runs on a movies table with 53 rows. The grouping columns used are movie_lang, which holds values such as Portuguese, German, English, Chinese, and Japanese, and age_certificate, which holds values such as PG, 12, 15, and 18.

Worked example — count of movies per language with bare-column error fix. The starting point is SELECT * FROM movies, which returns all 53 rows. The goal is a total count grouped by movie language, so the aggregate is COUNT on movie_lang, written \(\text{COUNT}\). The first attempt selects only the aggregate and gets a single grand total of 53, with no groups at all. The fix adds movie_lang to the SELECT list, separated by a comma — and that alone fails, because a bare column next to an aggregate must appear in a GROUP BY line. The error message says exactly that: the column must appear in the GROUP BY clause or sit inside an aggregate function. Adding GROUP BY movie_lang completes the query:

SELECT movie_lang, COUNT(movie_lang)
FROM movies
GROUP BY movie_lang;

Now each language forms one group with its own count. English has 38 movies, and Portuguese, German, Chinese, Japanese, and the rest each report their own totals. Sense-check: the per-language counts add back up to the grand total of 53.

Worked example — average movie length per language with ascending sort. The aggregate is AVG on movie_length, written \(\text{AVG}\). Running AVG alone over the whole table gives one grand average of about 126. Adding movie_lang to the SELECT list plus GROUP BY movie_lang splits that single number into one average per language. An ORDER BY movie_lang on top sorts the groups in ascending order so Chinese, English, German, and the rest appear alphabetically. Chinese averages about 121 and English about 126. The pattern is always the same: name the grouping column, aggregate the measured column, group by the grouping column. Sense-check: each per-language average sits inside the range of that language's own film lengths.

Worked example — total movie length per age certificate with grand total split. Here the aggregate is SUM on movie_length, written \(\text{SUM}\), and the grouping column is age_certificate. SUM alone over all rows gives a grand total of 6685. Adding age_certificate to the SELECT list with GROUP BY age_certificate breaks that total apart so PG, 18, 12, and each remaining certificate shows its own summed length. Sense-check: the per-certificate sums add back up to the grand total of 6685.

Worked example — min-max length per language with MAX-ordered ranking. Two aggregates can sit side by side: MIN on movie_length, written \(\text{MIN}\), and MAX on movie_length, written \(\text{MAX}\). Over the whole table the minimum is 87 and the maximum is 168. Adding movie_lang with GROUP BY movie_lang gives both numbers per language, so Portuguese and every other language each show their own shortest and longest titles. Copying the MAX expression into ORDER BY sorts the groups by longest title in ascending order first — 98, 120, and upward — and flipping to DESC puts the 168 group on top, followed by German, Portuguese, and Chinese. This is the data-story payoff: one small query ranks whole languages by their longest films. Sense-check: no per-language maximum can exceed the overall maximum of 168.

Worked example — GROUP BY with no aggregate dedupes like DISTINCT. Selecting movie_lang from movies with GROUP BY movie_length and no aggregate is legal. Compare SELECT movie_length FROM movies, which returns all 53 rows including repeats such as 112 appearing twice and paired values like 115 and 117, against the grouped version, which returns each length only once. An ORDER BY movie_length makes the duplicates in the raw list easy to spot — starting at 87 with visible doubles — while the grouped list holds unique values only. So yes, GROUP BY can run without any aggregate, and when it does it dedupes like DISTINCT. Sense-check: the grouped list is shorter than 53 rows whenever any length repeats.

Per-language counts, per-certificate totals, and shortest-versus-longest rankings turn a flat 53-row movie list into reports a content team can act on — which languages dominate the catalog and where the longest titles sit.

16.1.4 Student Questions and Answers

Q: Can GROUP BY run without any aggregate function? A: Yes. Grouping by a column with no aggregate returns each distinct value once, because GROUP BY wipes out duplicates much like DISTINCT does — one row per group comes back.

Q: Why does adding a plain column next to an aggregate fail? A: A bare column beside an aggregate must appear in the GROUP BY line. The error message says the column has to sit in the GROUP BY clause or inside an aggregate function, because the engine needs to know which column builds the groups.

Recap: GROUP BY splits rows into one set per distinct grouping value and runs each aggregate separately on every set — split, then compute. Exam note: expect to write grouped aggregate queries from scratch — counts, averages, sums, and min-max pairs per group — with GROUP BY covering every bare column. Next, 16.2 stretches the same rule across several grouping columns and adds ORDER BY and WHERE to the mix.

16.2 GROUP BY with Multiple Columns, ORDER BY, and WHERE

16.2.1 Every SELECT Column Must Be Grouped or Aggregated

Hook: One grouping column cuts the table into slices — but what if the question needs a grid, one cell per language-and-certificate pair? How many columns can GROUP BY cut by at once?

The rule from the previous section generalizes. Take a working query such as MIN and MAX of movie length grouped by movie language, then delete the GROUP BY line while keeping movie_lang in the SELECT list. The query fails with the same message: the movie_lang column must appear in the GROUP BY clause or be used in an aggregate function. There is no way around it. Any column that stands bare in the SELECT list — outside any aggregate — must be named in GROUP BY, because that line is what tells the engine how to cut the rows into groups. In words the check reads "bare columns must be grouped", written \(\text{GROUP BY}\) over every bare column.

Formalize: Grouping by several columns builds one group per distinct value combination — language-plus-certificate pairs such as English-with-15 or Chinese-with-12. To average movie length grouped by both movie language and age certificate, both movie_lang and age_certificate stand in the SELECT list, so both must appear in the single GROUP BY line:

SELECT movie_lang, age_certificate, AVG(movie_length) AS average
FROM movies
GROUP BY movie_lang, age_certificate;

The aggregate here is AVG on movie_length, written \(\text{AVG}\). Leaving either column out of GROUP BY fails. Grouping on only one of the two is rejected for the same reason: the engine was asked for groups cut by two columns but told how to cut by one.

Imagine the groups as a grid: languages down the rows, certificates across the columns, one cell per pair, one average inside each cell. Adding a second grouping column subdivides every slice into smaller cells, so group counts multiply. The standard is strict here: SQL demands syntactic purity and ignores what it knows about primary keys, so every bare SELECT expression's columns must appear in GROUP BY even when a key would logically determine them.

Scope: Multi-column grouping only subdivides — it can never merge groups that one column alone would keep apart. Assumption: the combination of grouping values is what defines a group, so two rows sharing a language but holding different certificates belong to different groups.

Two-column customer reports (last name plus first name), tour results (tournament, location, match, team), and grade averages (category plus student) all follow the identical grid pattern.

Q: Can a bare column sit in the SELECT list with an aggregate but no GROUP BY line? A: No. The engine rejects it and says the column must appear in the GROUP BY clause or inside an aggregate function. Every bare SELECT column has to be named in GROUP BY, with no escape.

16.2.2 Worked Examples with Two Grouping Columns, ORDER BY, and WHERE

Worked example — average length by language and certificate with positional ORDER BY. Start from AVG(movie_length) over the whole table, which gives a grand average of 126.13. Add movie_lang plus GROUP BY movie_lang to get one average per language. Then add age_certificate to the SELECT list — which fails until age_certificate also joins the GROUP BY line. The finished query returns rows such as Chinese with certificate 12, Chinese with certificate 15, English with PG, 12, 15, and so on, each carrying its own average. An ORDER BY movie_lang gathers Chinese, English, German, and Japanese rows together for easy reading. Giving the average an alias such as average and ordering by position — ORDER BY 1, 2, 3, where the numbers point at the first, second, and third SELECT columns — sorts by language, then certificate, then average. Flipping to DESC surfaces the top rows, with a certificate-15 group averaging about 136 sitting at the highest end. Sense-check: every two-column average lies within the range of its own cell's films.

Worked example — WHERE filter above GROUP BY for films longer than 100. To average movie length by language and certificate but only for films longer than 100, the filter is WHERE movie_length > 100. Placing WHERE after GROUP BY breaks with a syntax error near WHERE. Moving the WHERE line above GROUP BY fixes it:

SELECT movie_lang, age_certificate, AVG(movie_length)
FROM movies
WHERE movie_length > 100
GROUP BY movie_lang, age_certificate;

Word order in SQL is load-bearing: filters on raw rows come before the rows are cut into groups. An ORDER BY can sit at the end, but an ORDER BY that names a column missing from the SELECT list fails in a grouped query — the fix is to include that column in the SELECT list so the sort key exists in the grouped output. Sense-check: the filtered averages sit at or above 100, since shorter films never entered the groups.

Worked example — type mismatch warning: quoting the text certificate. Filtering grouped averages to a single certificate starts as WHERE age_certificate = 10 with no quotes. That fails with an operator error, because age_certificate is character varying (text) while 10 is numeric — text on the left and a number on the right do not compare. Quoting the value so both sides are text fixes the query and rows come back. The lesson sticks to every typed comparison: the left side and the right side of the equals sign must share a data type. Sense-check: the returned rows all show the quoted certificate value.

Worked example — director head counts per nationality sorted largest first. COUNT on all rows, written \(\text{COUNT(*)}\), reports 37 directors in total. Adding nationality to the SELECT list plus GROUP BY nationality splits the head count into one row per nationality. An ORDER BY 2 DESC sorts by the second column — the count — from largest to smallest, showing American directors on top followed by British directors, and an alias such as total_directors turns the output into a tidy report:

SELECT nationality, COUNT(*) AS total_directors
FROM directors
GROUP BY nationality
ORDER BY 2 DESC;

Sense-check: the per-nationality counts add back up to 37. Note the COUNT choice: COUNT(*) counts every row in the group, while COUNT of a column counts only its non-missing values.

Worked example — summed length per certificate-language pair with top pair on top. SUM on movie_length, written \(\text{SUM}\), gives the grand total first. Adding age_certificate with GROUP BY age_certificate gives one total per certificate. Adding movie_lang as a second grouping column gives one total per certificate-language pair — the summed length of English certificate-15 titles, for instance. An ORDER BY 3 DESC sorts by the third column, the sum, so the biggest pair lands on top: English titles with certificate 15 hold the highest total length. Sense-check: the pair totals add back up to the grand total.

Copying an aggregate expression such as SUM(movie_length) into the GROUP BY line fails — aggregates are banned inside GROUP BY. The way out is the HAVING clause, which filters on aggregate results after grouping and is covered in its own section.

Head counts per nationality, totals per certificate-language pair, and top-by-average rankings are exactly the shape of catalog and people reports — small grouped queries that answer "who leads" and "where is the bulk" in one pass.

16.2.3 Student Questions and Answers

Q: Can WHERE come after GROUP BY? A: No. WHERE placed after GROUP BY raises a syntax error, because row filters run before rows are cut into groups. WHERE always sits above the GROUP BY line.

Q: Why does comparing a text certificate column to a bare number fail? A: Because the two sides of the equals sign have different types — text on the left, numeric on the right. Quoting the value makes both sides text and the comparison works.

Q: Can GROUP BY name an aggregate expression? A: No. Aggregates are not allowed in GROUP BY. To filter on an aggregate result, use the HAVING clause instead.

Pitfalls: Ordering by a column that is not in the SELECT list fails in a grouped query — include it so the sort key exists. Positional ORDER BY (ORDER BY 1, 2, 3) is compact but fragile: adding a column renumbers every position, so aliases are safer in reports others will maintain. And grouping output only looks sorted because some engines sort internally first — never rely on it; state ORDER BY explicitly.

Recap: Every bare SELECT column must appear in GROUP BY, no matter how many there are; WHERE filters raw rows above the GROUP BY line; ORDER BY arranges finished groups at the end. Exam note: every bare SELECT column must appear in GROUP BY, and WHERE sits before GROUP BY while HAVING sits after it. The clause order behind these rules gets its full treatment in 16.3.

16.3 Order of Execution with GROUP BY

16.3.1 The Eight-Step Order

Hook: The query is written SELECT first — so why does an ORDER BY column missing from SELECT break a grouped query, and why does WHERE refuse to sit after GROUP BY? Because the engine does not read top to bottom.

Formalize: PostgreSQL does not run the clauses in the order they are written. For a grouped query the engine works through eight steps in this fixed order: FROM first, then WHERE, then GROUP BY, then HAVING, then SELECT, then DISTINCT, then ORDER BY, and finally LIMIT. FROM picks the table. WHERE keeps or drops raw rows. GROUP BY cuts the survivors into group sets. HAVING filters those group sets further. SELECT then builds the output columns from what remains. DISTINCT drops duplicate output rows. ORDER BY sorts the output. LIMIT trims the output to the requested row count. In compact words the chain reads "filter rows, cut groups, filter groups, then shape, sort, and trim", written \(\text{FROM} \rightarrow \text{WHERE} \rightarrow \text{GROUP BY} \rightarrow \text{HAVING} \rightarrow \text{SELECT} \rightarrow \text{DISTINCT} \rightarrow \text{ORDER BY} \rightarrow \text{LIMIT}\).

Think of an assembly line with eight stations. Each station only sees what the previous station passed on: WHERE never sees groups because none exist yet, HAVING never sees SELECT aliases because they are minted one station later, and ORDER BY sees only finished output columns. That single image predicts every placement error in this lecture.

Scope: This chain describes a grouped query with all clauses present; queries without GROUP BY or HAVING simply skip those stations. Assumption: logical order is fixed across standard SQL engines (PostgreSQL, MySQL, SQL Server, Snowflake, Databricks), even though each engine's physical plan — hashes, sorts, indexes — differs under the hood.

The same station order explains the textbook cases: GROUP BY runs after WHERE (so WHERE cannot test aggregates), and HAVING runs after GROUP BY (so it filters finished groups, as 16.4 shows in full).

16.3.2 Why the Order Matters

This order explains three behaviors seen in the demos. First, WHERE must precede GROUP BY in the written query because row filtering happens before group cutting — a WHERE line below GROUP BY is a station out of sequence and breaks. Second, HAVING sits between GROUP BY and SELECT because it filters finished groups before output columns are built — which is also why SELECT aliases do not exist yet when HAVING runs. Third, ORDER BY and LIMIT come last because they arrange and trim finished output rows, which is why ORDER BY can sort by an aggregate or alias but cannot reach back to raw columns that SELECT dropped. Once this chain is memorized, every placement error in the section above stops looking random: each clause simply runs in its slot.

One practical consequence: put selective row filters in WHERE rather than HAVING wherever both could work. Filtering west-coast states before grouping avoids computing totals for every other state only to throw them away — the engine does less grouping work when fewer rows arrive at the GROUP BY station.

Recap: FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT — rows are picked, trimmed, grouped, group-trimmed, shaped, deduped, sorted, cut. Exam note: expect to place WHERE, GROUP BY, HAVING, and ORDER BY in valid order and to explain why a misplaced clause fails. With the chain in hand, 16.4 puts the HAVING station to work.

16.4 Filtering Groups with HAVING

16.4.1 What HAVING Does

Hook: WHERE can drop short films before grouping — but how do you drop entire languages whose combined total is too small? That needs a filter that runs after the groups exist.

Formalize: A HAVING clause (a filter that keeps or drops whole groups based on an aggregate result) is how conditions on grouped data are expressed. It is used with GROUP BY to set a search condition on a group or an aggregate, and it always works on the aggregate result rather than on raw table columns. Two facts shape everything about it. First, HAVING computes over the aggregate function, never over a plain column. Second, column aliases cannot be used inside HAVING, because HAVING runs before the SELECT clause that creates those aliases — by the time HAVING filters, the alias name does not exist yet. The syntax shape is:

SELECT column_1, AGGREGATE_FUNCTION(column_2)
FROM table_name
GROUP BY column_1
HAVING AGGREGATE_FUNCTION(column_2) > value;

AGGREGATE_FUNCTION here is again a stand-in for a real aggregate such as SUM, MIN, MAX, or COUNT — there is no function literally named AGGREGATE_FUNCTION. The condition can use equals, greater than, greater-or-equal, AND combinations, and any similar comparison, always wrapped around an aggregate call. In words the pattern reads "filter groups by their aggregate", written \(\text{HAVING}\) over an aggregate expression.

Back at the pigeonhole picture: WHERE turns away individual letters before sorting, while HAVING inspects each full pigeonhole's tally and throws out whole pigeonholes that miss the bar. Same verb (filter), different object (rows versus groups), different station on the line.

Scope: HAVING needs grouped input to be meaningful — without GROUP BY it treats all surviving rows as one single group. Assumption: the HAVING condition must reference grouping columns or aggregate calls over the groups; a bare non-grouped column has no single value inside a group and does not belong there.

Threshold reports are the home turf: customers with 40 or more rentals, actors with more than 9 qualifying films, order totals above a cutoff, bowlers averaging above 155. In each case the aggregate is computed per group first, then the bar applies to the group answers.

16.4.2 Worked Examples with HAVING

Worked example — movie languages whose summed length tops 200. Start from SELECT * FROM movies, then narrow to the two items of interest: movie_lang and movie_length. SUM on movie_length, written \(\text{SUM}\), over the whole table gives the grand total first. Adding movie_lang with GROUP BY movie_lang produces one summed length per language. An ORDER BY on the sum in ascending order lays the groups out low to high — and also exposes a misspelled ORDER BY key immediately, because the engine complains about the unknown column name. The goal is languages whose group total is greater than 200, so a HAVING line on the aggregate does the filtering. Placing HAVING after GROUP BY but before ORDER BY is required; sliding it below ORDER BY breaks:

SELECT movie_lang, SUM(movie_length)
FROM movies
GROUP BY movie_lang
HAVING SUM(movie_length) > 200
ORDER BY 2;

The engine first builds one group per language, then keeps only groups whose summed length clears 200. Small groups such as 98, 128, and 165 drop out, and the survivors come back ordered. Sense-check: every surviving row shows a second column above 200.

Worked example — directors whose summed movie length tops 200. This demo stays on the movies table and uses its director_id column rather than joining the directors table — joins arrive in later material, so the grouping key here is the raw director identifier. Selecting director_id plus movie_length shows the two working columns. Wrapping movie_length in SUM at once fails, because the bare director_id column now needs GROUP BY director_id. The grouped form gives one total per director identifier — director 29 totals 148, another totals 138, another 237 — with 37 unique directors and no repeats. An ORDER BY director_id lines them up 1, 2, 3, 4, 5 downward for easy scanning. Then the HAVING line keeps only directors whose group total clears 200:

SELECT director_id, SUM(movie_length)
FROM movies
GROUP BY director_id
HAVING SUM(movie_length) > 200
ORDER BY 2 DESC;

Ordering by the second column descending puts the heaviest director on top: director 17 leads, followed by directors 6, 26, 13, and the rest. Note the standing rule once more — the HAVING condition always repeats the full aggregate call, never a shortcut. Sense-check: every listed total reads above 200, and the column runs largest-first.

Worked example — aliases fail inside HAVING. Giving SUM(movie_length) an alias such as total_movie_length and then writing HAVING total_movie_length > 200 feels natural, and it fails. The alias is born in SELECT, but HAVING runs before SELECT, so the name is unknown when HAVING filters. The fix is to spell the aggregate out again — HAVING SUM(movie_length) > 200 — and the query runs. This single failure teaches the execution order better than any diagram. Sense-check: the fixed query returns exactly the groups the aliased version intended.

Languages with more than 200 hours and directors with more than 200 hours of output are threshold reports — keep only the groups that clear a bar, and the bar always sits on an aggregate.

16.4.3 Student Questions and Answers

Q: Does HAVING filter raw columns or aggregate results? A: Aggregate results. HAVING computes on the aggregate function over each finished group, not on the plain table columns.

Q: Can a SELECT alias be reused inside HAVING? A: No. HAVING runs before the SELECT clause that creates the alias, so the alias name does not exist yet when HAVING filters. The full aggregate call has to be repeated.

Q: Where does the HAVING line sit? A: After the GROUP BY line and before any ORDER BY line. Placing HAVING below ORDER BY breaks the query.

Pitfalls: Putting an aggregate in WHERE fails because the groups do not exist yet at that station. Putting a bare WHERE-style column test in HAVING misses the point — HAVING judges group tallies, not individual rows. And repeating the aggregate expression (rather than aliasing) is mandatory in PostgreSQL and most engines; only a few, such as MySQL, informally tolerate aliases.

Recap: HAVING keeps or drops finished groups by testing their aggregate values — rows are filtered by WHERE first, groups by HAVING after. Exam note: HAVING always repeats the full aggregate call because aliases are unavailable there, and aggregates never appear in WHERE or in GROUP BY. Next, 16.5 re-reads the full execution chain with the HAVING station in place.

16.5 Order of Execution with HAVING

16.5.1 The Full Chain

Formalize: PostgreSQL evaluates HAVING after FROM, WHERE, and GROUP BY, and before SELECT, DISTINCT, ORDER BY, and LIMIT. Spelled out: FROM picks the table, WHERE filters raw rows, GROUP BY cuts the survivors into group sets, HAVING filters those group sets once more, SELECT builds the output columns, DISTINCT drops duplicate outputs, ORDER BY sorts, and LIMIT trims. In compact words the chain reads "table, row filter, group cut, group filter, then shape, sort, and trim", written \(\text{FROM} \rightarrow \text{WHERE} \rightarrow \text{GROUP BY} \rightarrow \text{HAVING} \rightarrow \text{SELECT} \rightarrow \text{DISTINCT} \rightarrow \text{ORDER BY} \rightarrow \text{LIMIT}\).

The only change from the 16.3 chain is one station made explicit: HAVING sits immediately after GROUP BY because it needs finished groups, and immediately before SELECT because output columns (and their aliases) do not exist yet. Everything else keeps its slot.

Scope: HAVING runs even when no explicit GROUP BY is written — the whole surviving row set counts as one group. Assumption: each station's input is the previous station's output, so no clause can see anything minted downstream.

16.5.2 Reading the Chain

Each slot earns its place. WHERE trims individual rows before groups exist. GROUP BY builds the sets. HAVING trims whole sets using aggregate math. SELECT shapes columns and mints aliases. DISTINCT, ORDER BY, and LIMIT polish finished output. The alias failure in the previous section is the cleanest proof: an alias minted in the SELECT slot cannot be spent one slot earlier in the HAVING slot.

Recap: Remember the chain as four pairs — pick and trim rows (FROM, WHERE), build and trim groups (GROUP BY, HAVING), shape and dedupe output (SELECT, DISTINCT), sort and cut (ORDER BY, LIMIT). With the chain complete, 16.6 stages the head-to-head: WHERE versus HAVING on the same task.

16.6 HAVING versus WHERE

16.6.1 The Core Difference

Hook: Two queries, same table, same number 200 — one keeps big languages, the other keeps long films. Which filter ran before grouping, and which ran after?

HAVING and WHERE both filter, but they filter different things at different times. WHERE works on plain SELECT columns — individual raw rows before any grouping. HAVING works on result groups — finished group sets with their aggregate values. In one line: WHERE trims rows, HAVING trims groups. In words the split reads "row filter first, group filter after", written \(\text{WHERE}\) on raw columns and \(\text{HAVING}\) on aggregates.

Dimension WHERE HAVING
What it tests Single raw rows Finished groups with aggregate values
When it runs Before GROUP BY cuts rows into sets After GROUP BY builds the sets
What it can name Plain columns Grouping columns and aggregate calls
Typical use Drop unwanted rows early (films of 100 or less) Keep groups clearing a bar (language totals above 200)

Pick WHERE when the question is about individual rows, HAVING when it is about group tallies. When both filters appear, WHERE runs first to shrink the input, then HAVING judges what remains.

Scope: The two filters compose — a query can and often should use both, WHERE to pre-trim rows and HAVING to threshold the resulting groups. Assumption: aggregates collapse groups, so they can only be tested once groups exist; that is why an aggregate inside WHERE is rejected by definition.

16.6.2 Worked Comparison on Movie Languages

Worked example — HAVING route keeping language groups whose sum clears 200. The shared task is movie languages whose summed length tops 200. The HAVING route starts from SUM(movie_length), written \(\text{SUM}\), adds movie_lang with GROUP BY movie_lang so English, Chinese, Japanese, Portuguese, and German each report a group total, sorts with ORDER BY 2 DESC to put the heaviest language on top, and then keeps groups whose total clears 200:

SELECT movie_lang, SUM(movie_length)
FROM movies
GROUP BY movie_lang
HAVING SUM(movie_length) > 200
ORDER BY 2 DESC;

English, Chinese, Japanese, and Portuguese survive. German totals about 165 and drops out. The key fact is what got summed: every individual film counted toward its language total first, and only then did the 200-bar apply to the group sums. No single film was judged against 200 on its own. Sense-check: each surviving total reads above 200 and German's 165 sits below the bar.

Worked example — WHERE pre-filter contrast answering a different question. Now the WHERE attempts. Swapping HAVING for WHERE while keeping the aggregate — WHERE SUM(movie_length) > 200 — fails outright with an aggregates-not-allowed error. By definition an aggregate collapses groups, while WHERE can only test individual columns, so the two cannot mix. Dropping SUM and writing WHERE movie_length > 100 runs fine and still groups — but it answers a different question: it first throws away every film of 100 or less, then groups and sums only the long survivors. That pre-trimmed total is not the same as summing everything and keeping groups above 200. The normal pattern is therefore: use WHERE to massage and pre-filter raw rows first, group them, and then apply HAVING to the grouped result. Sense-check: with short films excluded, the WHERE version's group totals can only stay the same or shrink relative to the HAVING version's.

Beyond the lecture's comparison, the textbook's performance angle is worth keeping: when a filter could sit in either clause (such as a state list), WHERE is the cheaper home, because it discards rows before the engine does any grouping work. And one textbook trap to remember: a HAVING COUNT threshold silently drops zero-count categories (the groups never formed), so "fewer than three, including zero" needs a different construction — an outer join or a per-category subquery — rather than a plain HAVING.

16.6.3 Student Questions and Answers

Q: Why can't WHERE test an aggregate such as SUM? A: Because aggregates collapse groups while WHERE tests single raw rows. The engine rejects aggregates in WHERE — group math belongs to HAVING, which runs after the groups exist.

Q: WHERE movie_length > 100 with GROUP BY runs fine — is that the same as HAVING SUM(movie_length) > 200? A: No. The WHERE version drops short films first and then groups only the survivors, while the HAVING version sums every film into groups and then keeps groups whose total clears 200. Pre-filtering rows and post-filtering groups answer different questions.

Recap: WHERE trims rows before grouping; HAVING trims groups after aggregation — same verb, different object, different station. Exam note: expect a HAVING-versus-WHERE comparison that turns on row filtering before grouping versus group filtering after aggregation. 16.7 Handling NULL Values with GROUP BY

16.7.1 Setup: A Test Table with NULL Departments

Hook: Every grouping column so far held tidy values — but real tables have blanks. Do all the missing departments pile into one group, scatter, or crash the query?

Real tables carry NULLs, and grouping columns are no exception. A NULL (a missing value standing in for unknown or unset data — not zero, not blank text, just absent) can sit inside the very column being grouped, and the demo builds a small table to show exactly what happens. The table is called employee_test:

CREATE TABLE employee_test (
  employee_id SERIAL PRIMARY KEY,
  employee_name VARCHAR(100),
  department VARCHAR(100),
  salary INTEGER
);

Here employee_id is a serial primary key (a self-counting integer that uniquely tags each row — SERIAL means the engine fills the next number automatically), employee_name and department are variable text fields up to 100 characters, and salary is an integer. A refresh of the table list shows employee_test with these four columns, and a SELECT * FROM employee_test confirms the table starts empty.

The table is then filled with rows for employee_name, department, and salary where some departments are deliberately NULL. John works in finance at 2500. Mary has no department (NULL) at 3000. Adam has no department (NULL) at 4000. More rows follow the same pattern, so the finished table holds two NULL departments alongside real ones such as finance and IT. The standing advice is to type the insert at your own keyboard before reading on — running it yourself makes the NULL behavior stick.

Scope: This demo isolates NULLs in the grouping column; NULLs inside aggregated columns behave differently — most aggregates skip them rather than grouping them. Assumption: missing departments are genuinely unknown, so gathering them into one visible group is honest reporting rather than inventing data.

Missing-value grouping is a data-quality staple: unassigned tickets, unmapped regions, unrated films — every one of them forms a group the report should show, not hide.

16.7.2 Worked Examples: Grouping and Relabeling NULLs

Worked example — ordering exposes the NULLs. SELECT * FROM employee_test shows every row, and ORDER BY department lines departments up with the NULL rows pushed to the end. Trimming the column list to employee_name, department, and salary keeps the display tight while the two NULL department cells stay visible. Sense-check: Mary and Adam both show empty department cells, confirming the test data is set up right.

Worked example — counting employees per department with NULL group of two. The question is how many employees sit in each group — finance, IT, and the NULL group. The aggregate is COUNT, written \(\text{COUNT}\), over the rows, with department kept as the bare grouping column and an alias such as total_employees on the count:

SELECT department, COUNT(*) AS total_employees
FROM employee_test
GROUP BY department;

Forgetting GROUP BY fails, because the bare department column next to an aggregate must be grouped. With the GROUP BY line in place the query runs with no trouble at all: each real department reports its head count, and the NULL department appears as its own group with a count of two — Mary and Adam. An ORDER BY department then arranges the groups ascending or descending as preferred. The takeaway is reassuring: GROUP BY does not choke on NULLs; it gathers all the missing values into one group like any other value. Sense-check: the group counts add back up to the table's row total.

Worked example — COALESCE relabel of NULL group to visible fallback text. A bare NULL in a report is easy to misread, so the goal is to swap it for visible text such as "No department" while leaving real values untouched. The tool is COALESCE (a function that takes a source column and a fallback value, shows the source value when one exists, and shows the fallback when the source is NULL — first non-missing value wins). In words the call reads "department if present, else fallback text", written \(\text{COALESCE}\) over the department column:

SELECT COALESCE(department, 'No department') AS department,
       COUNT(*) AS total_employees
FROM employee_test
GROUP BY department;

Finance, IT, and the rest display unchanged, while the NULL group now reads as "No department" with its count of two. Because the default sort is ascending, the relabeled group sorts to the top where no report reader can miss it. The query keeps working if someone later fills in real departments for Mary and Adam — the fallback simply stops triggering — and it doubles as a data-quality net, since any fresh NULL department immediately shows up under the visible label. Sense-check: the counts are identical to the un-relabeled query; only the label changed.

Two companion facts from the reference books sharpen the picture. First, COUNT(*) counts rows while COUNT of a column counts only its non-missing values — so a NULL inside an aggregated column is skipped by SUM, AVG, MIN, MAX, and COUNT of that column. Second, dialects agree on the core here: PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks all gather NULL grouping values into one group, and all offer COALESCE (plus dialect extras such as IFNULL in MySQL or NVL in Oracle-style systems) for the relabel. The common core never changes: NULLs group together, and COALESCE makes them readable.

Head-count-by-department reports with a labeled fallback keep people reports honest — missing assignments surface as "No department" instead of hiding inside a blank cell.

16.7.3 Student Questions and Answers

Q: Does GROUP BY break when the grouping column holds NULLs? A: No. All rows with a NULL grouping value gather into one NULL group, and aggregates such as COUNT run over it normally — the demo group holds two employees.

Q: How do missing values get a readable label in grouped output? A: Wrap the column in COALESCE with fallback text, as in COALESCE(department, 'No department'). Real values pass through untouched and NULLs display the fallback.

Recap: NULL grouping values form one group like any other value, and COALESCE relabels that group for human readers. That closes the concept arc — from splitting rows (16.1–16.2), through execution order and group filtering (16.3–16.6), to missing values (16.7).

Key Industry Applications

Catalog reporting: per-language counts, per-certificate totals, and longest-title rankings compress a flat title list into decisions about where a catalog is strong — the same shape as rentals-per-customer summaries that surface the best customers for targeted offers.

People reporting: head counts per nationality and per department, sorted largest-first with positional ORDER BY and aliases, are the standard shape of workforce summaries, from directors by nationality to employees by department.

Threshold reporting: HAVING-based cutoffs such as group totals above 200 keep only the groups that clear a bar — languages, directors, or departments worth a closer look — mirroring real filters like customers with 40 or more rentals or agents above a commission floor.

Data-quality reporting: grouping on nullable columns plus a COALESCE fallback label turns missing assignments into a visible "No department" row instead of a silent blank, so fresh gaps in department, region, or category data surface on sight.

Using GROUP BY

Must-know: GROUP BY cuts rows into groups by distinct values; each aggregate runs per group; bare columns must be grouped.

\[\text{groups} = \text{distinct values of GROUP BY column} \rightarrow \text{one aggregate answer per group}\]

⚠️ Top pitfall: Adding a bare column next to an aggregate without GROUP BY fails; aggregates alone return one grand total.

Self-check: What does COUNT per language return that a lone COUNT does not?

Connects to: 16.2, 16.4

GROUP BY with Multiple Columns, ORDER BY, and WHERE

Must-know: Every bare SELECT column must appear in GROUP BY; WHERE sits before GROUP BY and HAVING sits after it.

\[\text{SELECT bare cols} \subseteq \text{GROUP BY cols} \;\; \text{WHERE} \rightarrow \text{GROUP BY}\]

⚠️ Top pitfall: WHERE after GROUP BY breaks; text compared to a bare number fails until quoted; aggregates are banned in GROUP BY.

Self-check: Why does adding age_certificate to SELECT fail until it joins GROUP BY?

Connects to: 16.1, 16.3

Order of Execution with GROUP BY

Must-know: FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT is the fixed execution order.

\[\text{FROM} \rightarrow \text{WHERE} \rightarrow \text{GROUP BY} \rightarrow \text{HAVING} \rightarrow \text{SELECT} \rightarrow \text{DISTINCT} \rightarrow \text{ORDER BY} \rightarrow \text{LIMIT}\]

⚠️ Top pitfall: Misplaced clauses fail because each clause runs in its fixed slot, not in written order.

Self-check: Why can HAVING not see a SELECT alias?

Connects to: 16.2, 16.4

Filtering Groups with HAVING

Must-know: HAVING always repeats the full aggregate call because aliases are unavailable; aggregates never appear in WHERE or GROUP BY.

\[\text{HAVING } \text{AGG}(col) \; op \; value \;\; \text{over each finished group}\]

⚠️ Top pitfall: Reusing a SELECT alias in HAVING fails because HAVING runs before SELECT mints aliases.

Self-check: Where does HAVING sit relative to GROUP BY and ORDER BY?

Connects to: 16.3, 16.5, 16.6

Order of Execution with HAVING

Must-know: HAVING filters group sets after GROUP BY and before SELECT builds aliases.

\[\text{FROM} \rightarrow \text{WHERE} \rightarrow \text{GROUP BY} \rightarrow \text{HAVING} \rightarrow \text{SELECT} \rightarrow \text{DISTINCT} \rightarrow \text{ORDER BY} \rightarrow \text{LIMIT}\]

⚠️ Top pitfall: Spending a SELECT alias one station early in HAVING fails by construction.

Self-check: Which station mints aliases and which station filters groups?
