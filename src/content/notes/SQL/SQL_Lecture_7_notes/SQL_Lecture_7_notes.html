7.1 Creating a Fresh Practice Table in a New Database

7.1.1 Why Start Fresh Instead of Reusing Existing Tables

Work on table changes is easier to follow when it happens on a brand-new table. Why risk a table you still need? A throwaway copy lets you try every reshape verb without fear.

Work on table changes is easier to follow when it happens on a brand-new table. Existing tables such as movies or human-resource learning tables stay untouched for later select practice. A new database called mydata holds the practice tables. It starts empty with no tables inside. All of the structure changes happen there, so nothing else breaks. In short: create a new database and a fresh practice table so later select practice stays safe.

There is a practical reason behind this habit. Changes to a table shape can lock the table or reject old rows. A rename or a type change takes a short lock, and a new NOT NULL or UNIQUE rule scans every old row and fails if one row does not fit. Practice on a throwaway table keeps the tables needed for later select practice safe and clean. Database teams use the same habit in real work: they test a migration on a copy or a staging database first, then run it on the live database only after it passes.

A script window is one useful way to work. One window can hold several SQL commands in a row. The earlier approach used one admin tab per action. The script approach puts creation, changes, and checks in a single place where each block can be picked and run on its own. Highlight one block, run it, check the result, then move to the next block. Keep each change paired with a SELECT * check so you can see the before and after side by side.

Exam note: Be ready to explain why you create a fresh practice table in a new database: shape changes can lock the table or fail on old rows, so a throwaway table protects later work.

7.1.2 Building the Persons Table With a Primary Key

A primary key (the one column, or group of columns, that names each row) is written with PRIMARY KEY next to the column. It means two things at once: no two rows may share the value, and no row may leave it empty.

The first table is called persons. It stores one row per person with an identifier plus a first name and a last name. The identifier column is personid. It is an integer and it is the primary key, which means each row must have a different value and no row may leave it empty. The first name is variable character text and it may not be empty. The last name is variable character text with length 20 and it may not be empty.

CREATE TABLE persons (
  personid INT PRIMARY KEY,
  firstname VARCHAR NOT NULL,
  lastname VARCHAR(20) NOT NULL
);

Run only that block. Refresh the object list and the new persons table appears. Its columns are personid, firstname, and lastname, with a primary-key rule on personid. The database mydata now holds this persons table with its primary key in place.

Variable character text is written as VARCHAR in most systems and as VARCHAR2 in some others. The meaning is the same here: text of changing length up to a limit. PostgreSQL, MySQL, SQL Server, Snowflake, and Databricks Spark SQL all accept VARCHAR or VARCHAR(n). Oracle is the odd one out: it prefers VARCHAR2, and its docs ask you to use VARCHAR2 instead of VARCHAR. For this lecture the two spellings mean the same thing. If no length is given, as in firstname VARCHAR NOT NULL, PostgreSQL treats it as text of any length, while MySQL asks for a length in most versions, so VARCHAR(50) is the safer shared form.

Think of this table as a blank roster. The roster shape is fixed at creation time. Every later change keeps the stored rows but reshapes the roster itself. That reshape action is what the rest of this material covers. The blank roster stays blank until rows arrive, and the reshape verbs in sections 7.2 to 7.7 all act on this same persons table.

Build it yourself. Create a database called mydata, open a script window, paste the CREATE TABLE persons block above, and run only that block. Refresh the object browser. You should see mydata with one table, persons, holding three columns: personid with a key mark, firstname, and lastname. Run SELECT * FROM persons; and you get an empty result with those three headings. That empty grid is your blank roster, ready for reshape practice. Empty grid with three headings means the build worked.

Picture the shape as a small grid drawing. Columns run left to right: personid, firstname, lastname. Rows are empty slots waiting below. The key mark sits on personid. Each later section adds, renames, or guards a column of this same drawing, so the takeaway is simple: one roster, many reshapes.

Scope: CREATE TABLE fixes the shape once. It does not add rows. Adding rows is an INSERT step, covered later. Assumption: column names are plain lowercase with no spaces, so no quoted names are needed.

Two small traps catch new learners here. First, running the whole script at once instead of one block at a time hides which step failed. Run one block, refresh, check, then continue. Second, forgetting the refresh step makes it look as if the table was never made. The table is there; the browser list just needs a refresh click.

7.1.3 Student Questions and Answers

Q: Why create a whole new database and table just to practice changes?

A: Changes to a table shape can lock the table or reject old rows. Practice on a throwaway table keeps the tables needed for later select practice safe and clean. To put it as a rule: create a new database called mydata and a new practice table there, because a throwaway practice table protects the movies and learning tables you still need for select practice.

Recap: A fresh mydata database plus a persons table with a primary key gives you a safe blank roster. The next step grows that roster with new columns.

7.2 Adding New Columns to an Existing Table

7.2.1 The ADD COLUMN Pattern

How do you grow a table without rebuilding it? You reshape it in place with ALTER TABLE, and the reshape keeps every old row.

An existing table grows with the ALTER TABLE plus ADD COLUMN pattern. The table name comes first, then the new column name, then its type and rules. The new column appears on every row. If the table already holds rows, the system must know what to put in the new slots. That is why the type plus a rule such as NOT NULL, UNIQUE, or a DEFAULT matters: it tells the system what belongs in the new slots for old rows and for later inserts.

The add-column shape is:

ALTER TABLE table_name
ADD COLUMN column_name data_type rules;

ALTER TABLE names the roster to reshape. ADD COLUMN names the new field plus its type and rules. Run it once and every row gains one more slot.

The first addition is an age column. It is an integer and it may not be empty:

ALTER TABLE persons
ADD COLUMN age INT NOT NULL;

Run it, refresh, and age appears. A quick check also works:

SELECT * FROM persons;

The result lists personid, firstname, lastname, and the new age column. Start with three columns, add age as an integer column, then read the table back: the output gains a fourth column called age.

A note on what fills old slots: on an empty persons table there is nothing to fill, so the statement passes at once. On a table that already holds rows, PostgreSQL and most systems either need a default value for the new column or they fill old slots with empty (NULL) marks when the column allows them. Adding age INT NOT NULL to a table that already has rows and no default can fail on PostgreSQL, because the system has no value to put in the old slots. The safe classroom habit is to add the column, then check with SELECT *, exactly as the lecture does.

Across systems the core verbs stay the same. PostgreSQL uses ADD COLUMN age INT NOT NULL. MySQL accepts the same line, and also lets you place the column with ADD COLUMN age INT NOT NULL AFTER firstname or FIRST. SQL Server uses ADD age INT NOT NULL (the word COLUMN is optional). Oracle uses ADD (age NUMBER NOT NULL) with NUMBER in place of INT. Snowflake and Databricks accept the plain ADD COLUMN form. Keep the one shared form from the lecture unless you need a placed column in MySQL.

Scope: ADD COLUMN only widens the shape. It never renames, never drops, and never changes a type. Assumption: the new column name is fresh and does not clash with a name that is already there.

7.2.2 Adding Nationality and Email in One Step

The same pattern adds a nationality column as variable character text of length 20 that may not be empty:

ALTER TABLE persons
ADD COLUMN nationality VARCHAR(20) NOT NULL;

Two columns can be added in a single statement. The next change adds nationality and email together. Email is variable character text of length 100 and it must hold a different value on every row:

ALTER TABLE persons
ADD COLUMN nationality VARCHAR(20) NOT NULL,
ADD COLUMN email VARCHAR(100) UNIQUE;

Run it and refresh. The table now shows personid, firstname, lastname, age, nationality, and email. The UNIQUE rule on email means the system turns away any second row that repeats an address already stored. In other words, add nationality plus email with a uniqueness rule on email in one multi-add step, and the table gains both columns at once.

A common reading slip is hearing ADD COLUMN as a single fixed phrase. The working shape is ALTER TABLE plus the table name plus one or more ADD COLUMN clauses. One clause adds one column. Two clauses add two columns at once. The key phrase that adds a column inside a table that already exists is ADD COLUMN, and it follows ALTER TABLE plus the table name, then names the new column with its type and rules.

Picture the roster drawing again. It started with three columns. After the age add it has four. After the nationality add it has five. After the two-clause add it has six: personid, firstname, lastname, age, nationality, email. Each step widens the same grid; no row is lost, and the new cells wait for values.

Pitfall: adding NOT NULL to a filled table with no default is the most common failure here. On an empty practice table it passes, but on a live table with rows it can be rejected. The fix is to add the column with a default first, or to allow empty slots and fill them with an update before adding the rule.

7.2.3 Worked Examples

Example 1, add age as an integer column then read the table. Start with three columns (personid, firstname, lastname). Run ALTER TABLE persons ADD COLUMN age INT NOT NULL;. Run SELECT * FROM persons;. The output gains a fourth column called age. Four headings means the add worked.

Example 2, add nationality. Run ALTER TABLE persons ADD COLUMN nationality VARCHAR(20) NOT NULL;. Run SELECT * FROM persons;. The output gains a fifth column called nationality. Five headings means the second add worked.

Example 3, add nationality and email with a unique rule together. Run the two-clause block that adds nationality plus email with email VARCHAR(100) UNIQUE. Run SELECT * FROM persons;. The output gains both columns at once, and email carries the unique rule, so a repeated email address will be turned away later. Six headings plus a unique mark on email means the multi-add worked.

Each of these follows the same proof habit: change the shape, then read the table. Keep that pair together and a marker can see the change at once.

7.2.4 Student Questions and Answers

Q: What is the key phrase that adds a column inside a table that already exists?

A: ADD COLUMN is the key phrase. It follows ALTER TABLE plus the table name, then names the new column with its type and rules. One ADD COLUMN clause adds one column; two clauses add two columns at once, as in the nationality plus email multi-add.

Recap: ALTER TABLE persons ADD COLUMN ... grows the roster in place, one clause per column. Next you rename and drop parts of that same roster without losing rows.

7.3 Renaming Tables and Columns and Dropping Columns

7.3.1 Renaming a Whole Table

What if the table name itself was a poor pick? You do not copy rows anywhere. You rename the container and the rows ride along.

A table name changes with ALTER TABLE plus RENAME TO plus the new name. To switch persons to users:

ALTER TABLE persons RENAME TO users;

Run it and refresh. The users table appears in place of persons. To switch back:

ALTER TABLE users RENAME TO persons;

Run it, refresh, and persons is back. The rows and columns stay the same. Only the container name changes. This is handy during a rename test or when a team agrees on a better table name after creation. In short: rename the table persons to users and back, and the stored rows stay the same.

The rename-table shape is ALTER TABLE old_name RENAME TO new_name;. Old rows, columns, and rules stay attached to the new name. Nothing is copied and nothing is lost.

Across systems this verb is stable, with one extra spelling to know. PostgreSQL, MySQL 8, Snowflake, and Databricks all accept ALTER TABLE persons RENAME TO users;. MySQL also offers the older stand-alone form RENAME TABLE persons TO users;, which can rename several tables at once. Oracle accepts the ALTER TABLE ... RENAME TO ... form too. Keep the lecture form; reach for RENAME TABLE only when you must move several MySQL tables in one step.

Scope: a rename changes the name only. Views, stored code, and app queries that still use the old name will fail until they are updated. Assumption: no other object already uses the new name.

7.3.2 Renaming a Column

A column name changes with ALTER TABLE plus RENAME COLUMN plus the old name plus TO plus the new name. To change age to personage:

ALTER TABLE persons RENAME COLUMN age TO personage;

Refresh and the column now reads personage. The stored values stay in place. Only the label changes. Code that refers to the old name must be updated to the new name, or it will fail to find the column. So rename the column age to personage and the values stay where they were.

The rename-column shape is ALTER TABLE table_name RENAME COLUMN old_name TO new_name;. Values stay in place; only the label moves.

One cross-system note matters here. PostgreSQL, Snowflake, and MySQL 8 support RENAME COLUMN exactly as written. Older MySQL versions do not, and they ask for CHANGE COLUMN age personage INT NOT NULL;, which repeats the type alongside the new name. SQL Server uses a stored call, sp_rename 'persons.age', 'personage', 'COLUMN';. Oracle accepts ALTER TABLE persons RENAME COLUMN age TO personage;. When in doubt, use the lecture form first; it works on the classroom PostgreSQL setup.

7.3.3 Dropping a Column

The drop-column shape is ALTER TABLE table_name DROP COLUMN column_name;. The column and every value inside it leave the table for good.

A column leaves the table with ALTER TABLE plus DROP COLUMN plus the column name. To remove personage:

ALTER TABLE persons DROP COLUMN personage;

Run it and the column is gone from the shape and from every row. Dropped data does not come back on its own, so this action needs care on a live table. On a large live table the drop may also take a lock while the system marks the column as gone, so teams run it in a quiet window. For practice it is easy to add the column again:

ALTER TABLE persons ADD COLUMN age VARCHAR(10);

Then a full read shows the shape again:

SELECT * FROM persons;

The result lists personid, firstname, lastname, nationality, email, and age, with age currently stored as variable character text of length 10. That text-typed age sets up the cast lesson in the next section.

Trace the rename-then-drop loop on the same roster. Start from persons with an age column. Run ALTER TABLE persons RENAME TO users; and refresh: users appears, persons is gone, rows unchanged. Run ALTER TABLE users RENAME TO persons; and refresh: persons is back. Run ALTER TABLE persons RENAME COLUMN age TO personage; and refresh: the column reads personage with values in place. Run ALTER TABLE persons DROP COLUMN personage; and the column is gone from the shape and from every row. Add it back with ALTER TABLE persons ADD COLUMN age VARCHAR(10); and read with SELECT *;. Seeing users flip back to persons, then personage vanish, then age return as text, proves each verb worked.

Pitfall: dropping is the only verb here that destroys data. A rename can be undone by renaming back, but a dropped column needs a restore from backup. Always back up or test on a copy before dropping on a live table.

7.3.4 Student Questions and Answers

Q: What is the difference between renaming a table and renaming a column?

A: Renaming a table changes the whole container name with RENAME TO. Renaming a column targets one field with RENAME COLUMN plus old name TO new name. In both cases the stored rows stay the same. Rename the table persons to users to move the container; rename the column age to personage to relabel one field.

Recap: Rename moves a name, drop removes a field. Rows survive a rename but do not survive a drop. Next the lecture changes a column type, where text age must become a true number.

7.4 Changing a Column Data Type With Explicit Casting

7.4.1 From Text Age to Integer Age

Why does age work better as a number than as text? Try asking for everyone older than 30 when ages are stored as text, and the comparison sorts like words, not numbers.

Age works better as a whole number than as text. Numbers allow range checks and math. Text does not. With text, '9' sorts after '40' because the check runs letter by letter, and age + 1 fails or glues strings instead of adding. The age column above is variable character text of length 10. The goal is to turn it into an integer.

The change pattern is ALTER TABLE plus the table name plus ALTER COLUMN plus the column name plus TYPE plus the new type:

ALTER TABLE persons ALTER COLUMN age TYPE INTEGER;

On a Postgres-style system this direct attempt fails with a helpful message: column age cannot be cast automatically to type integer, with a hint to use USING age integer. Text-to-number is not automatic because stored text might not parse as a number. The system asks for an explicit cast instruction. A value such as '40' would parse fine, but a value such as 'forty' or '40 years' would not, so Postgres refuses to guess and asks you to state the rule.

The fix adds a USING clause that tells the system how to convert each old value:

ALTER TABLE persons ALTER COLUMN age TYPE INTEGER USING age::integer;

The double-colon form age colon colon integer reads as take age and cast it to integer. Run it and the change succeeds. A full read confirms the new shape:

SELECT * FROM persons;

Age is now an integer column. So change the text age column to integer with an explicit cast, using the USING form after the cast message.

The Postgres type-change shape is ALTER TABLE t ALTER COLUMN c TYPE new_type USING expression;. The USING part states how each old value becomes a new value. Without it, risky changes such as text to number are rejected.

Work the failing-then-passing pair. With age stored as VARCHAR(10), run ALTER TABLE persons ALTER COLUMN age TYPE INTEGER;. It fails: column age cannot be cast automatically to type integer, with a hint to use USING age integer. Now run ALTER TABLE persons ALTER COLUMN age TYPE INTEGER USING age::integer;. It passes. Run SELECT * FROM persons; and age reads as an integer column. Fail message first, then success with USING, proves the rule.

Think of type change as pouring values from one jar into another. Text to number needs a stated rule for what counts as a number. That pouring image is the lecture intuition: the jar shape changes, each value is poured through the USING filter, and anything that does not fit the filter stops the whole pour.

Scope: the USING cast runs on every stored row. If even one text value cannot parse as a number, the whole statement fails and the column stays as it was. Assumption: every stored age value is plain digits such as '40'.

Across systems the spelling splits. PostgreSQL uses the ALTER COLUMN ... TYPE ... USING form above. MySQL instead uses MODIFY COLUMN age INT; or CHANGE COLUMN age age INT; and converts values on its own without a USING clause. SQL Server uses ALTER COLUMN age INT; and fails if a value does not convert. Oracle uses MODIFY (age NUMBER);. Snowflake and Databricks accept ALTER COLUMN ... TYPE style changes with their own cast rules. The lesson travels: Postgres asks for the cast in words, others convert quietly, but the risk of a bad value is the same everywhere.

7.4.2 Moving Back From Integer to Text

The reverse move needs no extra cast instruction. Integer values always have a plain text form, so the system accepts the change directly:

ALTER TABLE persons ALTER COLUMN age TYPE VARCHAR(20);

Run it and age becomes variable character text of length 20. Change it back to integer with the USING form to keep the preferred shape, then read the table once more to confirm age is integer again. In short: changing INTEGER back to VARCHAR works without USING, because every integer already has a direct text spelling.

Picture the two jars again. Number to text needs no extra rule because every number already spells out as text: 40 becomes '40' with no choice to make. Text to number needs a rule because '40' could mean 40, while 'forty' has no number form at all.

Pitfall: widening text length on the way back matters. Moving to VARCHAR(20) keeps room for later values. Moving to VARCHAR(1) would cut longer values short or fail, so always pick a length that fits the longest value you plan to store.

7.4.3 Student Questions and Answers

Q: Why did the first try at changing VARCHAR age to INTEGER fail?

A: The system cannot guess how to read every text value as a number. It asks for an explicit conversion with USING age colon colon integer. That clause converts each stored text value to integer during the reshape. The error message column age cannot be cast automatically names the problem, and the USING age integer hint names the fix.

Q: Why does changing INTEGER back to VARCHAR work without USING?

A: Every integer already has a direct text spelling. No extra conversion rule is needed, so the plain TYPE change is accepted. Number to text always fits; text to number only fits when the text spells digits.

Recap: Text to number needs a stated USING cast; number to text needs none. Next you give a column a standing default and prove it with a fresh insert.

7.5 Setting a Default Value and Proving It With an Insert

7.5.1 Adding a Flag Column

How do you mark every person active without typing the same letter on every insert? You add the flag column first, then give it a standing value.

A new flag column called isenabled tracks whether a person row is active. It is variable character text of length 1, meant to hold Y:

ALTER TABLE persons ADD COLUMN isenabled VARCHAR(1);

Check the shape:

SELECT * FROM persons;

The new isenabled column appears. Existing rows show empty slots there until a value is supplied. Old rows keep whatever they held, which right now is an empty mark, because the default you are about to add only affects new rows.

A short design note: a one-letter VARCHAR(1) flag with Y is the lecture pick because it is easy to read in a demo. Many real teams instead use a true-false BOOLEAN column with default TRUE on PostgreSQL, a TINYINT(1) on MySQL, or a single-letter check-guarded flag as in section 7.7. The mechanics below stay the same whichever type you pick.

7.5.2 Giving the Column a Standing Default

A default (a standing value the system writes when an insert leaves the column out) is set with ALTER TABLE t ALTER COLUMN c SET DEFAULT value;. Later inserts that skip the column get the standing value for free.

A default is a standing value the system writes when an insert leaves the column out. The goal here is that every new person is active unless stated otherwise, so the default for isenabled is Y. The pattern is ALTER TABLE plus ALTER COLUMN plus the column name plus SET DEFAULT plus the value:

ALTER TABLE persons ALTER COLUMN isenabled SET DEFAULT 'Y';

Run it and the rule is stored on the column shape. A plain read still shows old rows as they were. The default affects new rows that skip the column. It does not rewrite old empty slots; those keep their old marks until an update fills them.

Scope: the default fires only when an insert skips the column or asks for DEFAULT. It does not fire when the insert names the column with an empty mark. Assumption: the default value fits the column type, here 'Y' inside a VARCHAR(1).

Cross-system spelling is close. PostgreSQL uses the lecture form above. MySQL uses ALTER TABLE persons ALTER COLUMN isenabled SET DEFAULT 'Y'; too, and also accepts ALTER TABLE persons MODIFY isenabled VARCHAR(1) DEFAULT 'Y';. SQL Server and Oracle accept a named default guard with ADD CONSTRAINT ... DEFAULT 'Y' FOR isenabled. Snowflake and Databricks accept SET DEFAULT in the same shape. The proof pattern below works on all of them.

7.5.3 Proving the Default With a Real Row

Prove the default with a real row that skips the flag. Insert John Benjamin without naming isenabled:

INSERT INTO persons (firstname, lastname, nationality, age)
VALUES ('John', 'Benjamin', 'US', 40);

The row is added. Now read the table:

SELECT * FROM persons;

The new John Benjamin row appears with nationality US and age 40. Its isenabled slot holds Y even though the insert never mentioned that column. That Y came from the default rule. This is the standard proof pattern: set the default, insert without the column, read back, and confirm the default value landed in the new row. Seeing Y on the John Benjamin row proves the default fired.

Try the two nearby cases to fix the idea. Insert one more row that names the flag as 'N' and it keeps 'N'; the default steps aside when you supply a value. Insert a row that names the flag with no value at all and it stores an empty mark on systems that allow it, because naming the column beats the default. The rule of thumb: skip the column to get the default, name the column to override it.

To remove the rule later, run ALTER TABLE persons ALTER COLUMN isenabled DROP DEFAULT;. New rows then store empty marks when they skip the column, while rows that already got 'Y' keep it.

7.5.4 Student Questions and Answers

Q: Does SET DEFAULT rewrite old rows that already have empty slots?

A: No. The default fills new rows that skip the column. Old rows keep whatever they already hold until they are updated directly. The John Benjamin insert proves it: only the new row gained Y from the default, while older rows stayed as they were.

Recap: Add the flag, set its default to Y, then insert John Benjamin without the flag and read back Y. Next you guard a whole column with a UNIQUE rule on a second table.

7.6 Adding a UNIQUE Constraint to an Existing Column

7.6.1 Building the Weblinks Table

What if each web address should appear only once? You build a small links table first, then add the guard that stops repeats.

A second practice table called weblinks stores web addresses and how they should open. It has a link identifier, a link address, and a link target. The identifier is a serial auto-number and the primary key. The address is variable character text up to length 255 and it may not be empty. The target is variable character text of length 20:

CREATE TABLE weblinks (
  linkid SERIAL PRIMARY KEY,
  linkurl VARCHAR(255) NOT NULL,
  linktarget VARCHAR(20)
);

Check the empty shape:

SELECT * FROM weblinks;

The table lists linkid, linkurl, and linktarget.

A serial auto-number (a counter the system fills on each insert) is spelled SERIAL on PostgreSQL, AUTO_INCREMENT on MySQL, IDENTITY on SQL Server, AUTOINCREMENT on Snowflake, and GENERATED ALWAYS AS IDENTITY on Databricks. The lecture uses SERIAL, so the classroom form is linkid SERIAL PRIMARY KEY.

So the weblinks table uses a serial primary key for linkid, a required linkurl address, and an optional linktarget. Keep that shape in mind; the UNIQUE guard in 7.6.3 lands on linkurl.

7.6.2 Storing a First Address

Add one row with an address and a target:

INSERT INTO weblinks (linkurl, linktarget)
VALUES ('http://www.google.com', 'blank');

Read the table and the row appears. Real-world: a links table like this sits behind bookmarks, menus, or content lists where each address should appear once. The linkid fills itself with 1, the address stores the google address, and the target stores blank.

Seed the table before guarding it. Run the google insert above, then SELECT * FROM weblinks;. You should see one row: linkid 1, linkurl the google address, linktarget blank. One row with linkid 1 means the seed worked and the table is ready for its UNIQUE rule.

7.6.3 Naming and Adding the Unique Rule

A UNIQUE rule (a guard that forces each value in a column to appear only once) is added with ALTER TABLE t ADD CONSTRAINT name UNIQUE (column);. Pick a plain name that states the table plus the column plus the rule kind.

A UNIQUE rule forces each value in a column to appear only once. The pattern on an existing table is ALTER TABLE plus ADD CONSTRAINT plus a chosen rule name plus UNIQUE plus the column in brackets:

ALTER TABLE weblinks
ADD CONSTRAINT unique_web_url UNIQUE (linkurl);

The rule name unique_web_url is a free choice. Pick a name that states the table plus the column plus the rule kind. Run it and the system accepts the rule because the stored addresses are distinct so far. Read the table to confirm the shape is unchanged. The rule is silent until a repeat arrives. That silent-until-repeat shape is the key warning from the lecture: nothing looks different until a duplicate insert tests it.

Behind the scenes the system builds a lookup index on linkurl so it can spot a repeat fast. That is why adding the rule on a huge table can take a while: every old row is checked for distinct addresses first. If two old rows already share an address, the add fails and names the offending value, and you must clean the repeats before trying again.

Across systems the shared form works on PostgreSQL, Snowflake, Databricks, Oracle, and SQL Server. MySQL accepts it too, and also offers the shorter ALTER TABLE weblinks ADD UNIQUE (linkurl); and CREATE UNIQUE INDEX unique_web_url ON weblinks (linkurl);. Keep the named-constraint form from the lecture; the name you pick is the name later error messages will quote.

Scope: UNIQUE stops repeats in new inserts and in updates, but it allows several empty marks in most systems, since empty is treated as unknown rather than equal. Assumption: stored addresses are already distinct when the rule is added.

7.6.4 Seeing the Rule Reject a Repeat

Prove the rule with one failing repeat and one passing fresh value. Try to store the same google address a second time:

INSERT INTO weblinks (linkurl, linktarget)
VALUES ('http://www.google.com', 'blank');

The system turns it away. The message states that a duplicate key breaks the unique rule named unique_web_url. Change the address and the same shape succeeds:

INSERT INTO weblinks (linkurl, linktarget)
VALUES ('http://www.amazon.com', 'blank');

Read the table. Two rows appear with two distinct addresses: the google row and the amazon row. That is the full loop: create, insert, add rule, prove a repeat fails, prove a fresh value passes. One duplicate rejected plus two distinct rows stored means the UNIQUE guard works.

Picture the guard as a door bouncer with a guest list. The first google address walks in. The second google address is stopped at the door and the bouncer names the list, unique_web_url. The amazon address is new, so it walks in. The takeaway: create the weblinks table, store a first address, add the unique rule with a plain name, then watch a duplicate address fail while a fresh address passes.

Pitfall: letter case and extra spaces can fool the eye. 'HTTP://www.google.com' and 'http://www.google.com ' may count as different values on some setups, so repeats slip through. Clean addresses on the way in or add a lowercased guarded column if case must not matter.

7.6.5 Student Questions and Answers

Q: Can the constraint name be anything?

A: Yes. The name is a free choice, so pick a plain label such as unique_web_url that names the table and the guarded column. The system uses that name in later error messages, which is why a plain name that states the table and column pays off when a duplicate key breaks the rule.

Recap: A named UNIQUE guard on linkurl stays quiet until a repeat arrives, then rejects it by name. Next a CHECK guard limits a flag to only Y or N.

7.7 Limiting a Column to Allowed Values With a CHECK Rule

7.7.1 Adding a Flag Column to Weblinks

What if a flag column should hold only Y or N, and a stray Q must never get in? You add the column first with no limits, then bolt on the guard.

Add an isenabled column to weblinks as variable character text of length 2:

ALTER TABLE weblinks ADD COLUMN isenabled VARCHAR(2);

Read the table. Existing rows show empty slots in the new column. Add a row that fills the flag with Y, using an address such as a video service address. Read again and the Y value appears on the new row. The column now exists and holds plain text with no limits yet.

This two-step order is on purpose. It shows the unsafe middle state: a plain text column accepts anything, including Q, until the CHECK guard arrives. Seeing that gap makes the value of the guard clear.

7.7.2 Writing the CHECK Rule for Y or N Only

A CHECK rule (a row-by-row test the system runs on every insert and update) is added with ALTER TABLE t ADD CHECK (test);. Here the test is an allowed set written as an IN list.

The goal is to accept only Y for yes and N for no in isenabled. Any other letter should fail. The pattern is ALTER TABLE plus ADD CHECK plus the allowed set written as an IN list:

ALTER TABLE weblinks ADD CHECK (isenabled IN ('Y', 'N'));

In words, the verbal rule is: alter the weblinks table and add a check so that isenabled must be within Y and N, where Y means yes and N means no. Run it and the rule is stored. The stored rows already hold Y or empty slots, so the rule is accepted. Empty slots pass because a CHECK test that sees an empty mark treats it as unknown rather than false, which is the standard SQL habit.

A named form works the same and reads better in error messages: ALTER TABLE weblinks ADD CONSTRAINT weblinks_isenabled_yn CHECK (isenabled IN ('Y','N'));. PostgreSQL, Snowflake, Databricks, Oracle, and SQL Server all accept the named form. MySQL parses CHECK for years but only enforces it from version 8.0.16 onward, so on older MySQL setups a bad letter would slip through. Keep the lecture form for classroom work; use the named form in real work so the failure names your rule.

Scope: the guard watches inserts and updates on rows where the flag holds a value. It does not rewrite old rows and it lets empty marks through. Assumption: existing rows hold only Y, N, or empty marks when the rule is added, or the add itself is rejected.

7.7.3 Proving the Rule Blocks Bad Input

Prove the CHECK rule with one bad insert that fails and one good insert that passes. Try a row with Q in the flag slot and the system rejects it. The message states that the new row breaks the check rule on weblinks for isenabled. Replace Q with Y or N and the same insert succeeds:

INSERT INTO weblinks (linkurl, linktarget, isenabled)
VALUES ('http://www.example-city.com', 'blank', 'Y');

Read the table and the new row appears with its valid flag. Rejected Q plus a stored Y proves the insert guard works.

Now prove the same guard watches updates, not just inserts. Set row one to Y:

UPDATE weblinks SET isenabled = 'Y' WHERE linkid = 1;

Read the table and row one shows Y. Try to set row three to an outside value and the system rejects the update with the same check message. Set it to N instead and it succeeds:

UPDATE weblinks SET isenabled = 'N' WHERE linkid = 3;

Read once more and the valid value is stored. That bad flag update fails while the good update passes, so the guard covers both doors. Real-world: flag columns like this guard status fields across products, so bad codes never reach stored data.

Picture the guard as a gate with two allowed badges, Y and N. An insert carrying Q is turned away at the gate. An update that swaps a badge to Q is turned away too. Only Y and N badges reach the stored rows. The one-line takeaway: the CHECK guard watches updates just as it watches inserts, and valid values are stored while outside values fail.

Exam note: Practice the UNIQUE named constraint and the CHECK IN list side by side, each with one passing and one failing insert. For CHECK, also rehearse one bad update that fails and one good update that passes.

Pitfall: two traps recur here. First, forgetting that updates are guarded too, so a later cleanup script that writes Q fails even though its insert once passed. Second, relying on CHECK on a very old MySQL setup where the rule is parsed but not enforced. On current systems the guard holds; on old ones it stays silent.

7.7.4 Student Questions and Answers

Q: Does a CHECK rule guard updates too, or only new inserts?

A: It guards both. An update that writes an outside value such as Q fails with the same check message. An update that writes Y or N passes and the stored row changes. Setting row one to Y passes, setting a row to Q fails, and setting row three to N passes.

Q: What does the failing-row message mean when it names the check rule?

A: It names the table plus the guarded column plus the check rule. That name points straight to which rule turned the row away and which value was not in the allowed set. When the message names weblinks and the isenabled check, read it as the Y-or-N gate rejecting the Q value.

Recap: A CHECK IN list of Y and N keeps the isenabled flag clean on both inserts and updates. You have now reshaped, defaulted, and guarded tables end to end.

Exam Guidance Summary

Practice the reshape verbs until each pair of change plus check runs from memory. Create a table with a primary key, then grow it with ADD COLUMN including multi-column adds and a UNIQUE column. Rename a table with RENAME TO, rename a column with RENAME COLUMN old name TO new name, and remove a column with DROP COLUMN. Change a text column to integer with ALTER COLUMN TYPE INTEGER USING age integer after seeing the cast message that the column cannot be cast automatically, and change integer back to text without USING. Give a column a standing value with ALTER COLUMN SET DEFAULT, then prove it by inserting a row that skips the column and reading it back, as with the John Benjamin row that gained Y. Name a UNIQUE rule with ADD CONSTRAINT plus a plain name plus UNIQUE plus the column, as with unique_web_url on linkurl, then prove it with one repeat that fails and one fresh value that passes, such as the duplicate google address that fails and the fresh amazon address that passes. Limit a flag to Y or N with ADD CHECK plus an IN list, then prove it with one bad insert that fails, one good insert that passes, and one bad update that fails. Practice the UNIQUE named constraint and CHECK IN list with passing and failing inserts until both guards feel routine.

Exam note: Keep each statement plus its before-and-after SELECT read together so the marker can see the change. Run one block at a time, refresh the object list, and read the table after every reshape.

Key Industry Applications

Roster and account tables grow new fields over time, so ADD COLUMN is routine schema upkeep. A shop adds a loyalty flag, a school adds a nationality field, and each add lands on live rows without a rebuild. Rename actions support clean naming as products grow, with table renames for whole containers and column renames for single fields when a team settles on clearer terms. DROP COLUMN retires fields that are no longer needed, with care because stored values go with it and no undo brings them back without a backup. Text-to-number casts with an explicit USING rule appear during data cleanup on Postgres-style systems when ages, counts, or amounts arrive as text, while MySQL and SQL Server convert with their own MODIFY and ALTER COLUMN spellings. Default flags such as isenabled with a standing Y value mark new accounts active without extra insert code, so every fresh row starts in the right state. UNIQUE rules on emails and addresses stop repeat entries in user and bookmark stores, backed by a lookup index that also speeds checks. CHECK rules with Y-or-N lists guard status flags so only valid codes reach stored rows, on both inserts and updates. A database administrator uses all of these guards to keep incoming data clean at the door, testing each reshape on a copy in the mydata habit before touching live tables.

Work habit: Test every reshape on a throwaway copy first. Change, read back, prove the guard with one failing and one passing row, then ship the same steps to the live table.
