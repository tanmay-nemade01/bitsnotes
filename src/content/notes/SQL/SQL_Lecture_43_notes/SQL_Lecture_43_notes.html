# Managing PostgreSQL Security

43.1 Security Concepts and Six Levels

Who should be allowed to see the salary column — and who should not even know the database exists? Every access decision in this lecture answers that question at one of six levels.

Security is a central duty of database administration. A database often holds sensitive facts — pay, phone numbers, customer mails — that must not reach everyone, so access is shaped with care. The person in charge of a database decides who may reach the system and at what level, granting rights on parts of the system and revoking them when the job changes. That same administrator can even grant or revoke the right to grant or revoke rights, which is a strong power to hand out with care, since a holder can pass access on to others.

A role (a named set of zero or more rights that can be handed to many people who need the same level of access) is the unit of security in PostgreSQL. Roles are everything in this system. A username (one kind of sign-in identity that marks a person or program allowed to run one or more functions on a database) is not the only kind of grant. In PostgreSQL the words user and role describe almost the same object: a role with the sign-in flag acts as a user, and a role without it acts as a group. That is why the CREATE ROLE and CREATE USER forms look the same.

In a large group with many people, handing rights to each person one by one takes long and invites mistakes: one forgotten REVOKE leaves a door open after someone changes teams. Roles fix that. Everyone who fills the same job gets the same rights through the role, and joiners or leavers only need membership changes. People who guard a building share one set of rights, while people who work as sales clerks share a different set — the same idea as an office key card that opens only the floors your job needs.

The six levels, widest to narrowest. Each level carries its own rights, and a missing right at a higher level blocks the path even when lower-level rights exist:

  1. Instance level — everything under one server install, including every database in that install. Rights cover sign-in, role management, database creation, and replication.
  2. Database level — one database such as a movies database or an HR database. Rights cover who may connect (CONNECT), who may build schemas (CREATE), and temporary-table rights (TEMPORARY/TEMP).
  3. Schema level — what sits right under one schema such as public. Rights cover seeing the schema (USAGE) and building objects inside it (CREATE for tables, views, types, functions).
  4. Table level — single tables, so one person may read only an actors table while another may also read a directors table. Rights cover SELECT, INSERT, UPDATE, DELETE, TRUNCATE, TRIGGER, and REFERENCES.
  5. Column level — single columns, so a person may read actor id, first name and last name but not gender or date of birth. Rights cover SELECT, INSERT, UPDATE, and REFERENCES on named columns; there is no column-level DELETE.
  6. Row level — which rows of a table a person may see, opened by policies after row control is enabled. Row control is fine grained and strong.

Grants always flow through the same chain: a role must hold the higher-level pass before the lower-level right can act. Later parts show this twice — CONNECT on the database must exist before schema rights matter, and USAGE on the schema must exist before table reads return rows. Keep that chain in mind: CONNECT plus USAGE plus picked table, column, and row rights.

How other databases split the same idea: the concept is common, so one version is enough, with extras noted once here. MySQL grants on *.* (server), db.* (database), table, and column levels with GRANT SELECT ON db.tbl TO user, but has no native row-level policies — row limits are built with views or application filters. Snowflake and Databricks Unity Catalog use role-based access with shareable roles, plus row access policies and column masking policies as separate objects rather than per-table CREATE POLICY lines. SQL Server mirrors PostgreSQL most closely with logins, database users, roles, and row-level security predicates. The lecture demos use PostgreSQL syntax throughout.

Picture the six levels as six nested fences around a vault. The outer fence is the instance gate, then one fence per building (database), per room (schema), per cabinet (table), per drawer (column), and finally a filter on which folders inside the drawer each badge may pull (row). A badge that opens a drawer is useless without the gate key — that is the higher-level dependency. The one-sentence takeaway: always check the outer fence first when access fails.

Scope: the six-level model describes PostgreSQL object rights plus row policies. It does not cover network rules, operating-system file rights, or connection encryption — those sit outside the database and still need setup. Assumption: one server install holds the databases in the demo, and the public schema holds the demo tables. Names and defaults shift across installs, so confirm them with \z and the admin tree before granting.

Pitfalls. Handing rights person by person instead of through group roles — the first staff change leaves stale grants behind. Granting the right to grant rights (WITH GRANT OPTION, or membership in a superuser group) to ordinary users — they can then widen their own access. Forgetting that defaults start open: fresh installs let almost anyone connect and build until REVOKE ALL ... FROM PUBLIC locks the base.

Recap: roles are the unit of PostgreSQL security, users and roles are the same object with different flags, and six nested levels from instance to row shape every grant. Next, the instance level puts this model to work with five role attributes.

Teams in firms use group roles per job family so joiners and leavers only need membership changes, not fresh grants on every table. Audits then read role membership instead of hundreds of per-person grants, which is the pattern every later section repeats.

43.1.1 Six Levels in Order

The order from widest to narrowest is instance, database, schema, table, column, row. Instance rights reach all databases under one server. Database rights stay inside one database. Schema rights stay inside one schema such as public. Table rights stay on named tables. Column rights stay on named columns. Row rights stay on rows that meet a rule. When rights at a higher level are missing, lower-level rights alone do not open the path, as later examples show with CONNECT and USAGE: a role with table SELECT but no database CONNECT still gets permission denied at the door.

43.1.2 Roles, Users and Groups

A role named hr might hold the rights needed by HR staff, while a role named programmers holds a different set. A user such as john can then be added as a member of hr with GRANT hr TO john, and a user such as linda can be added as a member of programmers. Membership is how one grant reaches many people: rights given to the group flow to each member that inherits them. In the admin tool, a single-person icon marks a sign-in user and a group icon marks a group role, which gives a fast visual split between the two kinds. Prefer group roles for every job family and keep single-person grants rare — that single habit makes every later revoke safe.

43.2 Instance Level Security and Role Attributes

The instance gate opens every database at once. What single flag would you never hand to an ordinary group — and why does the demo start by handing out nothing at all?

Instance level is the top of the tree. For a PostgreSQL 12 server install with five databases inside, instance rights reach all five databases at once. Because the reach is so wide, grants here need care. A group with top rights on the instance can touch everything beneath, so the lecture builds its first groups with every power switched off and adds rights back only where needed.

Think of instance rights as the master key to the whole office block rather than one room. A room key opens one database; the master key opens all five. That is why the demo groups start keyless: a master key is cut only after the need is proven.

Five role attributes. Each can be set or negated with NO:

  • Superuser — full power: open databases, drop databases, build tables and schemas, bypass most permission checks. Belongs to very few accounts.
  • CreateDB (CREATEDB / NOCREATEDB) — the right to build whole databases.
  • CreateRole (CREATEROLE / NOCREATEROLE) — the right to build and change roles, the rights bundles for databases, tables, rows, and columns.
  • Login (LOGIN / NOLOGIN) — the right to sign in and start a session. Group roles normally carry NOLOGIN; sign-in users carry LOGIN.
  • Replication (REPLICATION / NOREPLICATION) — the right to stream data for physical copies across systems.

The build form lists flags side by side with spaces between them:

CREATE ROLE role_name WITH NOSUPERUSER NOCREATEDB NOCREATEROLE NOLOGIN;

Two extra role properties appear in the admin preview and matter here. INHERIT means the role picks up rights from groups it belongs to and is on by default. The connection cap \[ \text{CONNECTION LIMIT} = -1 \] means no cap on concurrent sign-ins for that role, where \(-1\) is the marker for unlimited.

A first group called hr was built with no superuser power, no database build power, no role build power, and no sign-in. A second group called programmers was built the same way. After building, a refresh of the login and group roles node in the admin tool shows both roles with the group icon. Opening properties and then the definition view confirms the stored flags: no sign-in, no superuser, no role build, no database build.

Worked example — two group roles with no powers. Setup: a privileged account on a server with several databases.

  1. Run CREATE ROLE hr WITH NOSUPERUSER NOCREATEDB NOCREATEROLE NOLOGIN;
  2. Run CREATE ROLE programmers WITH NOSUPERUSER NOCREATEDB NOCREATEROLE NOLOGIN;
  3. In the admin tool, refresh the login and group roles node. Both names show with the group icon.
  4. Open each role, view properties and the definition tab, and confirm Can login is off and superuser, role build, and database build are off.
  5. In a terminal, try psql -U hr. The server asks for a password for hr. Since no password was set and sign-in is off, no password can pass and sign-in cannot complete.

Sense-check: the failure is the expected result — a group with NOLOGIN and no password is not meant for direct sign-in; members sign in with their own accounts and inherit the group rights.

Across databases the same flags have different names, noted once here and not repeated: MySQL uses SUPER, CREATE USER, and REPLICATION SLAVE/CLIENT privileges with CREATE USER 'x'@'host' plus GRANT; Snowflake grants ACCOUNTADMIN-level powers through roles rather than per-login flags; SQL Server uses server roles such as dbcreator and securityadmin. The PostgreSQL form above is the one the exam tasks use.

Scope: instance attributes gate the whole install, not single tables. They never replace CONNECT, USAGE, or table grants — a superuser bypasses checks, but every ordinary role still needs the lower-level chain. Assumption: roles inherit group rights (INHERIT on). With NOINHERIT, a member must run SET ROLE group_name before group rights apply, which the demo does not use.

Pitfalls. Giving SUPERUSER to an application or analyst account — one stolen password then owns every database. Giving CREATEROLE widely — a holder can grant themselves into any group. Setting a password on a NOLOGIN group and sharing it — that turns a group into a shared login that cannot be audited per person.

Recap: instance attributes are the widest switch, so the safe start is every flag negated and no sign-in for groups. Next, sign-in users get passwords and join these groups through membership.

43.2.1 Instance Attributes in Full

The five flags shape the whole instance. Superuser bypasses most checks, so it belongs to very few accounts. CreateDB lets a role add whole databases. CreateRole lets a role add or change roles. Login lets a role start a session. Replication lets a role stream data for copies. Negated forms (NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOLOGIN, NOREPLICATION) remove each power in plain terms and are the safe default for new groups.

43.2.2 Worked Example: Two Group Roles With No Powers

Setup: build a group hr and a group programmers, each with negated rights. Run CREATE ROLE hr WITH NOSUPERUSER NOCREATEDB NOCREATEROLE NOLOGIN; and CREATE ROLE programmers WITH NOSUPERUSER NOCREATEDB NOCREATEROLE NOLOGIN;. Check: refresh the login and group roles node. Both names show with the group icon. Open each, view properties and definition, and confirm Can login is off and superuser, role build and database build are off. Then try psql -U hr and see the password prompt fail, since no password exists and sign-in is off — the locked base every later level copies.

43.3 Users, Passwords and Group Membership

A user with no rights on a database just signed in anyway. Was the grant system broken — or was the starting line drawn in the wrong place?

Sign-in users are built the same way as roles, with a password added. Two users were built, john and linda:

CREATE ROLE john WITH NOSUPERUSER NOCREATEDB NOCREATEROLE LOGIN PASSWORD '123';
CREATE USER linda WITH NOSUPERUSER NOCREATEDB NOCREATEROLE LOGIN PASSWORD '123';

CREATE ROLE ... WITH LOGIN and CREATE USER ... do the same work here — both create a sign-in identity with the flags shown. A missing quote in the first try gave a password error, and fixing the quotes let both builds pass. A refresh showed john and linda with the single-person icon. Their property views showed no superuser, no role build, no database build, sign-in allowed, and a stored password. Demo passwords such as 123 are placeholders; live systems need long random secrets stored outside the notes.

A first sign-in test ran psql -U john -d hr with password 123. It passed. That result raised a fair question: no rights on the hr database had been granted to john, so why did sign-in pass. The reason is the default PUBLIC path, which lets almost anyone sign in until rights are tightened. PUBLIC is a built-in pseudo-role that includes every current and future role, so a grant to PUBLIC is a grant to the world.

Lock first, then grant. The fix starts from zero. Run as a privileged account:

REVOKE ALL ON DATABASE hr FROM PUBLIC;

Then the same psql -U john -d hr try ends with permission denied for the database. That is the locked base to build on. Membership then links users to groups:

GRANT hr TO john;
GRANT programmers TO linda;

In plain terms, john now belongs to hr and linda belongs to programmers. Rights given to the group now reach the member through inheritance. This lock-then-grant order repeats at every level: revoke wide rights, then add narrow rights per group.

Think of PUBLIC as the building lobby with the front door wedged open. REVOKE ALL ... FROM PUBLIC un-wedges it, and each later GRANT cuts a badge for one group only. The analogy breaks in one place: PUBLIC can never be deleted or emptied of future users, so the revoke must be repeated on each new database and schema rather than done once.

Worked example — locked base then membership. Setup: users john and linda exist with sign-in and passwords, and the hr database exists.

  1. As a privileged account, run REVOKE ALL ON DATABASE hr FROM PUBLIC;
  2. Try psql -U john -d hr and see permission denied — the lock holds.
  3. Run GRANT hr TO john; and GRANT programmers TO linda;
  4. Confirm in the admin tool membership tab that each user lists its group.

Sense-check: sign-in still fails until the group itself gets CONNECT in the next section — membership alone grants no database pass; it only routes future group grants to the member.

Scope: GRANT group TO user passes membership, not object rights directly. The member gains whatever the group holds, now and in the future, as long as INHERIT is on. Assumption: the demo runs each revoke as a superuser or database owner. An ordinary role cannot revoke rights it does not own.

Q: If john had no rights on the hr database, why did the first sign-in still pass? A: The default PUBLIC path still allowed sign-in — several students hit this same surprise. After REVOKE ALL ON DATABASE hr FROM PUBLIC, the same sign-in is denied. The lesson is to set rights to zero first, then add back only what each group needs.

Pitfalls. Creating users before locking PUBLIC and forgetting the revoke — the lobby stays open. Using weak demo passwords in a live copy — 123 belongs in notes, not in production. Granting membership in the wrong direction (GRANT john TO hr) — that would make the group a member of the user instead of the reverse.

Recap: users are roles with LOGIN plus a password, PUBLIC starts open, and the safe pattern is revoke-all then narrow membership grants. Next, the same lock-then-grant pattern opens one database at a time. Exam note: expect a task that revokes from PUBLIC first and then grants membership — the order is the tested point, not just the two lines.

43.3.1 Worked Example: Locked Base Then Membership

Setup: users john and linda exist with sign-in and passwords. The hr database exists. Run REVOKE ALL ON DATABASE hr FROM PUBLIC. Try sign-in as john and see denial. Then run the two GRANT ... TO ... lines above. This order matters: lock first, then grant with care. That pattern repeats at every level: revoke wide rights, then add narrow rights.

Q: If john had no rights on the hr database, why did the first sign-in still pass? A: The default PUBLIC path still allowed sign-in. After REVOKE ALL ON DATABASE hr FROM PUBLIC, the same sign-in is denied. The lesson is to set rights to zero first, then add back only what each group needs.

43.4 Creating Roles With pgAdmin

Typing five-flag CREATE ROLE lines is slow and error prone. Where can you build the same role with checkboxes — and still read the exact SQL before it runs?

The same instance roles can be built in the admin tool without typing the full form. Under the PostgreSQL 12 node, collapse to the login and group roles node, right click, and pick create login or group role. A clear name helps later readers, such as instance_viewer, instance_editor, or a superuser group. The instance_ prefix keeps instance-wide roles apart from database or schema roles when dozens pile up.

For an instance_viewer group, the definition holds no password and the rights hold sign-in only: no superuser, no role build, no database build, inherit rights from a parent role left on, streaming replication off. The SQL preview shows the true form:

CREATE ROLE instance_viewer WITH LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE INHERIT NOREPLICATION CONNECTION LIMIT -1;

Here \[ \text{CONNECTION LIMIT} = -1 \] means no cap on concurrent sign-ins for that role, where \(-1\) is the marker for unlimited. A positive number caps sessions; -1 leaves them uncapped. Save stores the role, and properties confirm the flags.

Three reference builds. Each is created the same way — definition tab, privileges tab, SQL preview, save, then properties check:

  • Viewer — LOGIN only. Safe sight without change power; the default pick for analysts.
  • Editor — LOGIN plus CREATEDB plus CREATEROLE. Can add databases and roles, so it suits a junior admin, not an analyst.
  • Superuser group — LOGIN SUPERUSER CREATEDB CREATEROLE REPLICATION. Everything flips on; membership here is ownership of the install.

Members are added on the membership tab of the group properties. A user such as adam or a whole group such as programmers can be dropped into a group, which nests one grant inside another.

Always read the SQL preview before saving: it is the same CREATE ROLE line a terminal would run, and it catches a wrongly ticked box before the role exists. Other databases offer the same GUI path with different names — MySQL Workbench user accounts, Snowflake Snowsight roles, Databricks account console groups — but the preview-then-save habit transfers unchanged.

Worked example — three instance roles. Setup: admin tool open on the server node.

  1. Create instance_viewer with sign-in only; read the SQL preview showing LOGIN ... CONNECTION LIMIT -1; save; confirm flags in properties.
  2. Create instance_editor with sign-in plus database and role build; read the matching preview; save; confirm.
  3. Create the superuser group with superuser on and the rest flipped on; save; confirm.
  4. On the membership tab of a group, add adam or the programmers group and save.

Sense-check: instance_viewer can sign in but cannot create anything; the editor can create databases and roles; only the superuser group can replicate and bypass checks.

Scope: the admin tool writes the same SQL the terminal accepts — it adds no extra safety. A wrong tick writes a wrong role either way. Assumption: the operator holds rights to create roles. Without CREATEROLE or superuser, the save fails with permission denied.

Pitfalls. Dropping a whole group such as programmers into the superuser group to "fix" one denied query — every member becomes a superuser. Skipping the SQL preview — the one screen that shows the true flags before they take effect. Vague names such as group1 — unreadable six months later during an audit.

Recap: pgAdmin builds identical roles through checkboxes, the SQL preview is the source of truth, and instance_-prefixed names plus the membership tab keep wide roles auditable. Next, database-level grants narrow the same roles to one database.

Naming roles by level and job, such as instance_viewer, keeps audits fast when many roles pile up: a reviewer sees the reach from the name before opening any tab.

43.4.1 Worked Example: Three Instance Roles

Build instance_viewer with sign-in only, instance_editor with sign-in plus database and role build, and a superuser group with all powers. After each build, read the SQL preview before saving, then open properties and confirm the stored flags. Then add a member on the membership tab and save.

43.5 Database Level Security

Your badge opens the building lobby — but can it also build a new room? Reaching a database and changing it are two separate grants.

Database rights live inside one database. Under a PostgreSQL 12 instance with five databases, picking the hr database sets the scope. Three rights matter here. Create (CREATE) lets a role build new schemas inside that database, such as public_1 or a test_schema, plus tables inside. Connect (CONNECT) lets a group role open that database. Temporary (TEMPORARY, shown as TEMP) lets a role build short-lived temp tables, a more advanced topic the lecture names but does not demo.

Think of CONNECT as the door key and CREATE as the building permit. The key gets you into the lobby; only the permit lets you add rooms. Holding one without the other explains every surprise in this section.

Grant form — connect first, create second:

GRANT CONNECT ON DATABASE hr TO hr;
GRANT CONNECT ON DATABASE hr TO programmers;

After both grants, a terminal check as john (member of hr) passed with psql -U john -d hr and password 123. A schema build was then tried with CREATE SCHEMA test_schema;. It failed with permission denied for the database. The role could connect but not build. The missing right was CREATE:

GRANT CREATE ON DATABASE hr TO hr;
GRANT CREATE ON DATABASE hr TO programmers;

After sign-out and sign-in again as john so the session picks up the new rights, CREATE SCHEMA test_schema passed, and the admin tree showed the new schema next to public. A matching check as linda also passed: connect worked, CREATE SCHEMA test_schema2 worked, and refresh showed test_schema2. If new rights seem ignored, sign out and in again before concluding the grant failed.

The split transfers across systems with one syntax swap: MySQL uses GRANT ALL ON hr.* style database grants and has no separate CONNECT (any authenticated user reaches the server); Snowflake grants USAGE on a database plus CREATE SCHEMA; SQL Server grants CONNECT on the database in the same words as here. The concept — reach versus change — stays put.

Worked example — connect then create. Setup: groups hr and programmers exist, users linked as before, base locked with REVOKE ALL ON DATABASE hr FROM PUBLIC.

  1. Run the two CONNECT grants; sign in as john; confirm the connection opens.
  2. Try CREATE SCHEMA test_schema and see permission denied — the door is open but the permit is missing.
  3. Run the two CREATE grants; sign out and in; retry the build; see success in the terminal and the new schema in the admin tree.
  4. Repeat the connect plus build pair as linda with test_schema2.

Sense-check: each step isolates one right — connection success proves CONNECT, build success proves CREATE.

Scope: database rights stay inside the named database. Rights on hr never open the movies database next door. Assumption: john inherits through hr membership (INHERIT on) and re-signs in after grants. Rights granted mid-session may not show until the next sign-in.

Q: Why could john connect but not build a schema? A: CONNECT only opens the door. CREATE on the database adds the right to add schemas. Both grants are needed before CREATE SCHEMA can pass — the most common two-step in this lecture.

Pitfalls. Granting CREATE without CONNECT and testing only the build — the failure looks like a schema problem but is a door problem. Granting database CREATE to analyst groups — they can then add whole schemas of shadow tables. Leaving demo schemas such as test_schema behind — later sections inherit the clutter.

Recap: CONNECT opens one database, CREATE changes it, TEMPORARY covers temp tables, and re-sign-in applies new grants. Next, schema rights repeat the same door-versus-build split one level down. Exam note: expect a hands-on task that grants CONNECT then CREATE and asks why the first build failed — answer with the exact missing-grant line.

43.5.1 Worked Example: Connect Then Create

Setup: groups hr and programmers exist, users linked as before. Run the two CONNECT grants, sign in as john, and confirm connection. Try CREATE SCHEMA test_schema and see denial. Run the two CREATE grants, sign out and in, retry the build, and see success. Repeat the connect plus build pair as linda with test_schema2. Each step shows the split between reaching a database and changing it.

43.5.2 Student Questions and Answers

Q: Why could john connect but not build a schema? A: CONNECT only opens the door. CREATE on the database adds the right to add schemas. Both grants are needed before CREATE SCHEMA can pass.

43.6 Schema Level Security

A brand-new user with zero schema grants just created a table. Did the grant system fail — or did the schema start life wide open?

Schema rights sit right under the database. Inside the hr database the public schema holds the tables, so rights on public shape everything under it. Two rights matter. Create (CREATE) lets a role build tables, functions, procedures, sequences, triggers, types, and views under the schema. Usage (USAGE) lets a role see the schema and its objects only, without building. The rule of thumb: USAGE is sight, CREATE is construction.

The start state surprised a tester. A user called adam signed in with psql -U adam -d hr and password welcome, then ran CREATE TABLE t_test (id INT);. It passed even though no schema rights had been granted to adam. The default was too open — fresh schemas grant USAGE and CREATE to PUBLIC, so anyone who can connect can also build. The fix is the level-zero pattern: remove wide rights first.

REVOKE ALL ON SCHEMA public FROM PUBLIC;

This must run while placed in the hr database so it hits the right public schema — every database has its own public. The test table was then dropped through the admin tool to leave a clean base. A fresh sign-in as adam and a retry of the same CREATE TABLE now ends with permission denied for schema public. The base is locked.

Narrow grants per role. Two fresh roles were built:

CREATE ROLE sales WITH NOSUPERUSER NOCREATEDB NOCREATEROLE LOGIN PASSWORD 'welcome';
CREATE ROLE tech WITH NOSUPERUSER NOCREATEDB NOCREATEROLE LOGIN PASSWORD 'welcome';

Rights were then added so tech may view and build under public, while sales may only view:

GRANT CREATE ON SCHEMA public TO tech;
GRANT USAGE ON SCHEMA public TO tech;
GRANT USAGE ON SCHEMA public TO sales;

Note the dependency: CREATE without USAGE is useless, since a role that cannot see the schema cannot build in it — always grant USAGE beside CREATE.

A sign-in as tech first failed with permission denied for the database, which pointed to a missing higher-level right. Fresh roles had no CONNECT on the hr database — the same chain as before. The fix:

GRANT CONNECT ON DATABASE hr TO tech;
GRANT CONNECT ON DATABASE hr TO sales;

After that, sign-in as tech passed and CREATE TABLE tt1 (id INT) passed, with refresh showing the table. Cleanup dropped the table. Sign-in as sales passed, but CREATE TABLE t2 (id INT) ended with permission denied for schema public. That split is exactly the plan: tech can build, sales can only view.

Picture a floor plan: CONNECT is the elevator to the floor, USAGE is the corridor you may walk, CREATE is the permit to add rooms off that corridor. sales may walk the corridor; tech may also build. The one-sentence takeaway: corridor before construction, elevator before corridor.

Worked example — level zero then narrow grants. Setup: adam can build without a grant in hr.

  1. Run REVOKE ALL ON SCHEMA public FROM PUBLIC inside hr; drop the stray t_test table.
  2. Confirm adam can no longer build — permission denied for schema public.
  3. Build sales and tech; grant USAGE plus CREATE to tech, USAGE only to sales.
  4. Grant CONNECT ON DATABASE hr to both; sign in as each; tech builds tt1 while sales is denied on t2; drop test tables.

Sense-check: two denials prove two different gates — database denial means missing CONNECT, schema denial means missing CREATE.

Scope: schema rights cover object creation and visibility in that schema only. Table reads and writes still need their own grants in the next section. Assumption: work happens inside the hr database. Running the revoke while connected elsewhere locks the wrong public schema and leaves hr open.

Q: Why did tech get permission denied for the database right after schema rights were granted? A: Schema rights alone do not open the database door — the elevator was missing. Once GRANT CONNECT ON DATABASE hr TO tech runs, sign-in passes and the schema rights take effect. Always diagnose upward: database, then schema, then table.

Pitfalls. Revoking on the wrong database's public schema — the demo database stays open while another locks. Granting CREATE without USAGE — builds fail in a schema the role cannot see. Leaving stray demo tables (t_test, tt1) behind — they confuse later table-level checks.

Recap: lock the schema to zero, grant USAGE for sight and CREATE for building, and keep the CONNECT link from the level above. Next, table rights decide reads and writes object by object. Exam note: expect a task that revokes schema rights from PUBLIC, grants USAGE versus USAGE plus CREATE, and asks why one role builds while the other is denied.

43.6.1 Worked Example: Level Zero Then Narrow Grants

Setup: adam can build without a grant. Run REVOKE ALL ON SCHEMA public FROM PUBLIC in hr, drop the stray table, and confirm adam can no longer build. Build sales and tech, add USAGE plus CREATE for tech and USAGE only for sales, add CONNECT on the database for both, then test builds as each role. Keep the pattern in mind: lock the schema, then grant per role.

43.6.2 Student Questions and Answers

Q: Why did tech get permission denied for the database right after schema rights were granted? A: Schema rights alone do not open the database door. The role also needs CONNECT on the database. Once GRANT CONNECT ON DATABASE hr TO tech runs, sign-in passes and the schema rights take effect.

43.7 Table Level Security

Two analysts can both read the sales table — but only one may change it. How do you grant sight to everyone and the pen to one group?

Table rights name what a role may do to rows and frames. Seven rights apply: Select reads rows, as in SELECT * FROM countries. Insert adds rows, as in INSERT INTO regions VALUES (...). Update changes rows, as in UPDATE regions SET region_name = .... Delete removes rows with a filter. Truncate clears a table at once and runs very fast on huge tables with millions of rows, so it needs extra care since it can flush all data in one move. Trigger lets a role build triggers on the table. Reference (REFERENCES) lets a role build foreign key links that point to the table — withholding it blocks new foreign keys even when reads pass.

Think of a paper ledger: SELECT is reading it, INSERT/UPDATE/DELETE are writing in it with a pen, TRUNCATE is feeding the whole book to a shredder in one second, and TRIGGER/REFERENCES are wiring the ledger to ring a bell or anchor other ledgers to it. Sight is cheap to share; the shredder key is not.

Wide versus narrow grant forms. Grants can hit all tables in a schema at once or one table only:

GRANT SELECT ON ALL TABLES IN SCHEMA public TO sales;
GRANT INSERT ON TABLE employees TO tech;

The wide form reaches every present table in the named schema in one move — note it covers existing tables only, so tables created later need a fresh grant or an ALTER DEFAULT PRIVILEGES rule. The narrow form names one table. Both forms were used: sales got select on all tables in public, while tech got select on all tables in public, plus individual rights on employees:

GRANT SELECT ON ALL TABLES IN SCHEMA public TO tech;
GRANT INSERT ON TABLE employees TO tech;
GRANT UPDATE ON TABLE employees TO tech;
GRANT DELETE ON TABLE employees TO tech;

Wide reads for view-only groups are common, while wide writes are risky. TRUNCATE and TRIGGER deserve the most care among the seven, since one can wipe data fast and the other can add auto-run logic.

Checks as sales with password welcome showed reads pass and writes fail. SELECT * FROM countries and SELECT * FROM employees LIMIT 2 both returned rows. But INSERT INTO regions (region_name) VALUES ('test') ended with permission denied for table regions, since sales holds read only.

Checks as tech showed the same split in a finer way. SELECT * FROM regions passed. INSERT INTO regions (region_name) VALUES ('test') failed, since tech holds write rights only on employees, not on regions. The employees table needs a full key — employee id, last name, email, hire date and job id are required — so a short insert with only first name fails on a row rule, not on rights. To keep the demo simple, write rights were also added on regions:

GRANT INSERT ON TABLE regions TO tech;
GRANT UPDATE ON TABLE regions TO tech;
GRANT DELETE ON TABLE regions TO tech;

Worked example — sales reads, tech writes on picked tables. Setup: sales holds select on all tables in public; tech holds select on all plus insert, update and delete on employees and later on regions.

  1. Sign in as sales: read countries and employees — both pass; try a write on regions — denied.
  2. Sign in as tech: read regions — passes; try a write on regions — denied until the regions write grants run.
  3. After a fresh sign-in so the new rights apply, run INSERT INTO regions (region_id, region_name) VALUES (10, 'test');, read it back with SELECT * FROM regions;, then clean up with DELETE FROM regions WHERE region_id = 10;
  4. Confirm reads, writes and cleanup all worked on regions.

Sense-check: denial on one table with success on another proves per-table scoping — the grant names the table, not the schema.

MySQL and Snowflake extras, noted once: MySQL uses the same SELECT/INSERT/UPDATE/DELETE words but grants them as GRANT SELECT, INSERT ON hr.employees TO 'tech'@'%' and has no TRUNCATE-as-privilege split; Snowflake expresses the same split as SELECT versus INSERT/UPDATE/DELETE/TRUNCATE on tables within schemas, managed through roles. The PostgreSQL wide/narrow forms above are the exam syntax.

Scope: table rights assume the CONNECT plus USAGE chain already holds. Without those, even a full table grant cannot be reached. Assumption: the wide grant covers tables that exist now. Remember follow-up grants or default privileges for tables added later.

Pitfalls. Handing wide write rights (INSERT/UPDATE/DELETE on all tables) to everyone for convenience — one mistake rewrites the whole schema. Confusing a constraint failure with a rights failure on employees — missing NOT NULL columns fail even with full rights. Granting TRUNCATE beside DELETE without thought — TRUNCATE skips row filters and is far faster and more final.

Recap: seven table rights split sight from change, the wide form covers current tables in a schema, the narrow form names one table, and TRUNCATE/TRIGGER need the most care. Next, column rights narrow the same reads and writes to picked columns. Exam note: expect a task that grants SELECT ON ALL TABLES IN SCHEMA to one group and INSERT/UPDATE/DELETE ON TABLE x to another, then asks which writes pass where.

The closing caution stands: avoid handing wide write rights on all tables to everyone. Plan per group and per table.

43.8 Column Level Security

The sales team needs names and mails but must never see pay. How do you share a table while hiding two of its columns?

Column rights narrow reads and writes to picked columns. Four rights apply on columns: Select reads from the column, Insert writes into the column, Update changes facts in the column, and Reference allows pointing to the column as a foreign key. There is no delete right at column level — deletes remove whole rows, so they stay at table level. The form names the columns in brackets:

GRANT SELECT (employee_id, first_name, last_name, email) ON employees TO sales;

The employees table holds sensitive facts such as salary and phone number. HR may need those columns, while other groups must not see them. Yet an earlier wide grant had given sales select on all tables, which means all columns too. A check as sales with SELECT * FROM employees returned everything, including salary facts. That is not fit for live use.

Revoke wide, grant narrow. The level-zero fix removes the wide read first:

REVOKE SELECT ON ALL TABLES IN SCHEMA public FROM sales;

A fresh sign-in as sales and a retry of SELECT * FROM employees now ends with permission denied for the table. Then the narrow column grant above runs. A retry of SELECT * FROM employees still fails, which puzzles first-time users. The reason is plain: without rights on all columns, a star query cannot pass, since the star expands to every column including ungranted ones. Picked columns must be named:

SELECT first_name FROM employees;

That passes. But SELECT first_name, job_id FROM employees; fails with permission denied, since job_id was not granted. The database message here is terse, but the rule is steady: name only granted columns.

Think of the table as a personnel file with some pages stapled shut. A star query asks for the whole file including stapled pages, so it is refused; naming allowed pages gets exactly those pages. The staple is the missing column grant.

The same logic shapes writes. SELECT * FROM regions as sales first failed for lack of any rights, so a small read grant ran with GRANT SELECT (region_id, region_name) ON regions TO sales; and reads then passed. An update try with UPDATE regions SET region_name = 'Asia1' WHERE region_id = 3; was denied. The fix grants the single column write with GRANT UPDATE (region_name) ON regions TO sales;. The same update then passed, and SELECT region_id, region_name FROM regions showed Asia1. Cleanup set the value back, since demo writes must not drift the shared data.

Other databases agree on the shape with local syntax, noted once: MySQL uses GRANT SELECT (col) ON tbl, Snowflake and Databricks more often mask columns with masking policies while keeping base selects, and SQL Server supports GRANT SELECT ON OBJECT::dbo.employees(salary) style column grants plus DENY. The PostgreSQL bracket form above is the exam syntax.

Worked example — hide salary and phone. Setup: sales can read all of employees.

  1. Revoke the wide select; sign in fresh as sales; confirm SELECT * FROM employees is denied.
  2. Grant select on employee_id, first_name, last_name, email only; confirm SELECT * FROM employees still fails (star needs all columns) while SELECT first_name FROM employees passes.
  3. Show that adding an ungranted column (job_id) breaks the query.
  4. On regions, grant SELECT (region_id, region_name), confirm reads, fail an update, grant UPDATE (region_name), pass the update, verify Asia1, and revert.

Sense-check: every failure names the ungranted column — the error points at the staple, not at the whole file.

Scope: column grants ride on top of table reach — the role still needs CONNECT plus USAGE and must not be blocked by a deny-all row policy. Assumption: no row policy hides the tested rows. If a row policy is on, zero rows can mimic a column denial; check \z and policies before concluding.

Q: After granting four columns, why does SELECT * FROM employees still fail? A: Star needs rights on all columns. With only four granted columns, queries must name those columns one by one, such as SELECT first_name FROM employees. Any query that names an ungranted column is denied — the expected behavior, not a bug.

Pitfalls. Leaving the earlier wide table grant in place beside the column grant — the wide grant wins and salary stays visible. Selecting star in application code after narrowing — every star query breaks at once. Forgetting to revert demo writes such as Asia1 — later row counts and filters inherit the drift.

Recap: four column rights name brackets of allowed columns, star needs all columns, and writes narrow to one column the same way. Next, row policies narrow the same tables to picked rows. Exam note: expect a task that revokes wide select, grants named columns, and asks why star fails while named queries pass.

43.9 Row Level Security Foundations and Policies

A table with nineteen jobs just returned zero rows — and nothing was deleted. What single switch hides every row until a written rule opens a path?

Row control limits which rows a role may see, even when table reads are allowed. It stays off until turned on per table:

ALTER TABLE jobs ENABLE ROW LEVEL SECURITY;

Once on, the base rule is deny all: nobody can reach any row until a policy opens a path — and that includes the table owner unless a policy or BYPASSRLS covers them, so test as the target role, not as the superuser. That default can mislead, since SELECT * FROM jobs returns zero rows and looks like an empty table when rights are in fact the cause. For that reason, rights changes deserve a written record outside the database: zero rows after enabling is a rights signal, not proof of empty data.

A first demo used the jobs table with job id, job title, minimum salary and maximum salary. sales first got a plain table read with GRANT SELECT ON TABLE jobs TO sales;. A check as sales returned all rows. Then ALTER TABLE jobs ENABLE ROW LEVEL SECURITY ran. The same check returned zero rows, which confirms the deny-all base.

Policies open picked rows. The build form is:

CREATE POLICY policy_name ON table_name FOR SELECT TO role_name USING (expression);

Here the expression (a row filter that must return true for the row to pass) can be any WHERE-style test, such as a cap on salary. A first query showed ten rows meet \[ \text{max\_salary} \ge 10000 \], where \( \text{max\_salary} \) is the top pay for the job and \(10000\) is the cutoff. The policy ran:

CREATE POLICY p_jobs_sales_maxsalary_10000 ON jobs FOR SELECT TO sales USING (max_salary >= 10000);

A fresh check as sales returned the ten rows, and ORDER BY max_salary showed values from 10000 upward. Lower rows stayed hidden.

More than one policy may sit on the same table. By default their filters join with OR, so the end set grows. If one policy returns two rows and another returns ten, the end set holds twelve. A second policy for sales used \[ \text{min\_salary} \ge 4000 \], where \( \text{min\_salary} \) is the floor pay for the job. A preview query showed about fifteen rows, with values such as 9000 and 8500 in the mix:

CREATE POLICY p_jobs_sales_minsalary_4000 ON jobs FOR SELECT TO sales USING (min_salary >= 4000);

After this second policy, checks as sales returned fifteen rows, which matches an OR of the two filters:

\[ (\text{max\_salary} \ge 10000) \lor (\text{min\_salary} \ge 4000) \]

where \( \lor \) means or. Ordering by minimum salary showed values from 4000 upward, with some rows below 10000 in maximum salary now present through the second arm.

An AND join needs the AS RESTRICTIVE mark. The plain build joins with OR (permissive policies add rows), while a restrictive policy must also pass. The drop form is DROP POLICY p_jobs_sales_minsalary_4000 ON jobs;. After the drop, checks fell back to ten rows. A rebuild with the mark ran:

CREATE POLICY p_jobs_sales_minsalary_4000 ON jobs FOR SELECT TO sales AS RESTRICTIVE USING (min_salary >= 4000);

Checks then held at ten rows, since both arms must now pass:

\[ (\text{max\_salary} \ge 10000) \land (\text{min\_salary} \ge 4000) \]

where \( \land \) means and. Chains of OR and AND can be mixed with care across many policies: permissive policies widen with OR, each restrictive policy narrows with AND.

Picture each policy as a sieve stacked over the table. Permissive sieves sit side by side — a grain passing any one of them falls through (OR). A restrictive sieve sits below them all — every grain must also pass it (AND). The one-sentence takeaway: permissive adds, restrictive filters.

Worked example — enable, deny all, then two policies. Setup: sales can read jobs (all rows visible).

  1. Run ALTER TABLE jobs ENABLE ROW LEVEL SECURITY; check as sales — zero rows (deny all).
  2. Add the max-salary policy; check — ten rows with max_salary from 10000 upward.
  3. Add the min-salary policy as permissive; check — fifteen rows (the OR set).
  4. Drop the second policy; check — back to ten rows.
  5. Rebuild it AS RESTRICTIVE; check — the AND set (rows passing both arms).

Sense-check: each count change proves one rule — zero for deny-all, growth for OR, shrinkage for AND.

Cross-database note, once: MySQL has no CREATE POLICY — the same slice is built with views (CREATE VIEW sales_jobs AS SELECT ... WHERE max_salary >= 10000) plus grants on the view. Snowflake uses CREATE ROW ACCESS POLICY ... AS (col) RETURNS BOOLEAN -> col >= 10000 attached with ADD ROW ACCESS POLICY, and Databricks Unity Catalog uses CREATE ROW FILTER. The OR/AND join logic here is PostgreSQL's permissive/restrictive model.

Scope: policies in this section cover SELECT for sales on jobs. Separate policies are needed per command (INSERT, UPDATE, DELETE) and per role — a SELECT policy never opens writes. Assumption: checks run as sales after each change. The superuser still sees all rows, so verifying as the owner hides the effect.

Q: After turning on row control, why does the table look empty? A: The base rule is deny all — a warning several students needed. Zero rows means no policy has opened a path yet, not that the facts are gone. No TRUNCATE or reload is needed. Add a policy and the picked rows return.

Pitfalls. Enabling row control and stopping before any policy — every user including the owner sees zero rows. Stacking many permissive policies without realizing they OR — the visible set only grows. Forgetting FOR SELECT versus FOR ALL scope — a read policy never covers writes.

Recap: enable flips the base to deny-all, permissive policies OR, restrictive policies AND, and row counts trace each rule. Next, a CURRENT_USER policy replaces fixed cutoffs with per-person rows. Exam note: expect a task that enables row control, predicts zero rows, then writes a USING filter and predicts the count — plus one OR versus AS RESTRICTIVE comparison.

43.10 Row Policies With CURRENT USER

Fixed pay cutoffs served one table — but what if each person should see only rows stamped with their own name, across fifty or five hundred names?

A fixed cutoff works for pay bands, but many tables need per-person rows. One path keys the filter to the signed-in name with the built-in CURRENT_USER, which returns the active role name as text. A demo table held user facts:

CREATE TABLE t_user_data (username VARCHAR, tag VARCHAR);
INSERT INTO t_user_data VALUES ('sales', 's1'), ('sales', 's2'), ('tech', 't1'), ('tech', 't2');

As the superuser postgres, SELECT * FROM t_user_data showed all rows. As sales, the same query first failed with permission denied for the table, since no table read had been granted. The fix granted reads widely for the demo with GRANT SELECT ON TABLE t_user_data TO PUBLIC;. Checks as sales then showed all rows, including tech rows. The goal was the reverse: each signed-in role should see only its own rows.

One policy keyed to the signed-in name. Row control was turned on:

ALTER TABLE t_user_data ENABLE ROW LEVEL SECURITY;

Checks as sales then showed zero rows through the deny-all base. A policy keyed to the signed-in name then ran. As postgres, SELECT CURRENT_USER returns the active name, so the same call returns sales when signed in as sales:

CREATE POLICY p_userdata_by_username ON t_user_data FOR ALL TO PUBLIC USING (username = CURRENT_USER);

Here \[ \text{username} = \text{CURRENT\_USER} \] means the row passes when the name stored in the row matches the active signed-in name. After the build, checks as sales returned only the two sales rows (s1, s2), and checks as tech returned only the tech rows (t1, t2).

Think of a mailroom with pigeonholes: the policy is the rule "take only envelopes stamped with your badge name." One rule serves the whole wall — no per-person list needed. The rule breaks where one database login is shared by many humans (a web app pool), which the next section fixes with session markers.

Worked example — two rows per role. Setup: table t_user_data holds two sales rows and two tech rows.

  1. Grant reads; confirm each role sees all rows (too open).
  2. Enable row control; confirm zero rows as sales (deny all).
  3. Add the CURRENT_USER policy; sign in as sales — two rows (s1, s2); sign in as tech — two rows (t1, t2).
  4. Confirm as postgres that all rows still exist — the filter hides, never deletes.

Sense-check: row counts per role prove the filter keys on the session name, not on stored data alone.

This path fits well when each database role maps to one person. With fifty or hundreds of names, writing one policy per name would still be heavy, but a single CURRENT_USER rule covers all of them at once. Other systems spell it differently — SQL Server uses SUSER_SNAME() or USER_NAME(), MySQL leans on CURRENT_USER() inside views, Snowflake uses CURRENT_USER()/CURRENT_ROLE() in row access policies — the keyed-to-session-name idea is shared, and here the spelling is PostgreSQL's.

Scope: FOR ALL TO PUBLIC here covers all commands for every role through one name-matching rule. Writes also filter on the same expression, so an insert with a foreign username is rejected. Assumption: each human signs in as their own role. Shared logins all return the same CURRENT_USER and all see the same slice.

Pitfalls. Testing only as the superuser — owners bypass or precede policies depending on settings, so the slice looks wrong. Storing display names instead of exact role names in username — one case or space mismatch hides every row. Using this pattern behind a pooled app login — all app users share one slice (see the next section).

Recap: username = CURRENT_USER turns one policy into per-person slices with zero per-name rules. Next, session variables carry the same idea to thousands of app users behind one login.

43.11 Row Policies for Application Users With Session Variables

A web app funnels ten thousand users through one database login. How can one policy still show each user only their own rows?

Many web apps hold thousands of app users behind one database sign-in, so one database role per app user is not workable. The goal stays the same — each app user sees only its own rows — but the key must come from the app session, not from the database sign-in name.

A session variable (a per-connection setting fixed by the app when a user arrives) fills that gap. When app user one arrives, the app sets its marker to one. When app user two arrives, the app sets its marker to two. The policy then keys rows to that marker with current_setting. Think of it as a cloakroom token: the counter (database login) is shared, but the token number (session marker) decides which coat (rows) you get.

Policy keyed to a session marker. The demo reused t_user_data. Reads for all were confirmed, and the old name-keyed policy was dropped:

DROP POLICY IF EXISTS p_userdata_by_username ON t_user_data;

A new policy keyed to a session marker ran:

CREATE POLICY p_userdata_by_session ON t_user_data FOR ALL TO PUBLIC USING (username = current_setting('app.username'));

Here \[ \text{username} = \text{current\_setting}(\text{app.username}) \] means the row passes when the stored name matches the session marker named app.username. Row control was confirmed on with ALTER TABLE t_user_data ENABLE ROW LEVEL SECURITY;.

A check as sales without a marker failed with an unrecognized setting, since the session held no app.username value. Careful apps avoid that hard error with a two-argument fallback such as current_setting('app.username', true), which returns NULL instead of failing — but the lecture models the strict form so the missing-marker failure is visible. The app-side step was then modeled by hand:

SET app.username = 'sales';
SELECT * FROM t_user_data;

Only sales rows returned. Then SET app.username = 'tech'; followed by SELECT * FROM t_user_data; returned only tech rows. One policy now serves any number of app users, since the app sets the marker per arrival — the trusted app, not the end user, controls the SET.

Worked example — one policy for many app users. Setup: old policy dropped, new session-keyed policy in place, row control on.

  1. Sign in as sales with no marker; see the missing-setting error — proof the filter needs the token.
  2. Run SET app.username = 'sales'; read; see only sales rows.
  3. Run SET app.username = 'tech'; read; see only tech rows.
  4. Confirm the policy count stays at one while the served users are unbounded.

Sense-check: flipping one SET line flips the visible slice — the session marker, not the login, steers the rows.

Snowflake and Databricks extras, once: Snowflake reads the same context with CURRENT_STATEMENT() or session variables inside row access policies, and Databricks reads current_user() orUnity Catalog session context. The PostgreSQL spelling here is current_setting('app.username') plus SET.

Scope: the marker is per connection, so pooled connections must set it on every checkout — a reused connection with a stale marker leaks the previous user's rows. Assumption: the app sets the marker before any query and never lets the end user run raw SET. Trust sits in the app tier, not in the browser.

Pitfalls. Forgetting the SET on a pooled connection — the next user inherits the last marker. Letting clients send their own SET — any user can claim any name. Using the strict one-argument current_setting with no fallback — sessions without the marker error out instead of showing zero rows.

Recap: current_setting('app.username') moves the row key from the database login to the app session, so one policy serves unlimited app users. Next, dropping policies and disabling control unwinds the whole stack.

Multi-firm systems keep all firms in one table and add a firm marker per session, so each firm reads only its own rows — the same token pattern with app.firm_id instead of a username.

Run SET app.username = 'sales', read, and see only sales rows. Run SET app.username = 'tech', read, and see only tech rows. That flip shows how the app can steer rows per user.

43.12 Dropping Policies and Disabling Row Control

The last policy on a table was just dropped — yet the table still returns zero rows. Is the data gone, or is a second switch still on?

A policy is removed by name:

DROP POLICY IF EXISTS policy_name ON table_name;

More than one policy on a table is removed one by one — there is no drop-all in one line. If the last policy goes while row control stays on through ALTER TABLE ... ENABLE ROW LEVEL SECURITY, the deny-all base still applies, so nobody can reach any row. That state needs a plan: either keep a policy or turn control off. Think of policies as sieves and the enable switch as the frame: removing every sieve from a mounted frame still blocks the flow — the frame itself must come off.

Two separate removals. Control is turned off with:

ALTER TABLE t_user_data DISABLE ROW LEVEL SECURITY;

This switch works whether or not policies still exist — leftover policy definitions stay stored but stop filtering once control is off. After dropping the last session policy on t_user_data, checks showed zero rows through deny-all. After the disable line, the same checks showed all rows again through plain table rights. The two steps show the split between policy removal and control removal.

Worked example — drop then disable. Setup: session policy in place on t_user_data with row control on.

  1. Drop it with the DROP POLICY form; check as sales — zero rows (deny-all with no policies, not missing data).
  2. Run the DISABLE ROW LEVEL SECURITY form; check again — all rows return through plain SELECT rights.
  3. Confirm with \z t_user_data that table grants never changed — only the row layer moved.

Sense-check: zero rows after step 1 plus full rows after step 2 proves the two switches are independent.

Scope: DISABLE restores plain table/column rights for everyone holding them — it does not revoke those grants. Re-lock with table revokes if open reads are unwanted. Assumption: the operator owns the table or holds suitable rights; ordinary roles cannot drop policies or flip the switch.

Pitfalls. Dropping the last policy on a live table and leaving control enabled — the application sees an "empty" table at peak hours. Disabling control to debug and forgetting to re-enable — the table stays wide open. Assuming DROP POLICY deletes data — it only removes the filter rule.

Recap: DROP POLICY removes one rule, deny-all persists while enabled with zero policies, and DISABLE ROW LEVEL SECURITY restores plain rights. Next, \z inspects the whole rights stack in one view.

43.13 Inspecting Permissions

Before changing any grant, where can you read the whole rights stack — table grants, column grants, and row filters — in a single screen?

The \z admin command (the same as \dp) shows stored rights on a table. Sign-in for the check used psql -U postgres -h localhost -d hr with password welcome. Then \z jobs shows the schema name, the rights string, and any row policies. Letter codes read as: r for select or read, a for insert or append, w for update or write, d for delete, D for truncate, x for reference, t for trigger. So a string such as arwdDxt decodes to full rights: append, read, write, delete, truncate, reference, trigger. An entry such as sales=r/postgres reads as "role sales holds read (r), granted by postgres".

Reading the two demo lines. In the demo, postgres held full rights such as arwdDxt on jobs, while tech and sales held read only (r) on jobs. Policy lines beneath showed the sales max-salary rule with its filter \[ \text{max\_salary} \ge 10000 \] and the role it binds to — that line joins the grant view to the row-policy view. A second look with \z employees showed postgres with full rights, tech with arwd for select, insert, update and delete, and column lines showing sales read rights on employee_id, first_name and last_name. That one view joins table, column and policy facts, so no grant is added blind.

Think of \z output as the badge-reader log posted on the vault door: each line names who holds which key and which sieve hangs below. The one-sentence takeaway: read the log before cutting a new key.

Worked example — read a rights line. Setup: signed in as postgres on hr.

  1. Run \z jobs and parse each block: schema, table, rights string, role, policy name, policy kind (permissive or restrictive), and filter.
  2. Run \z employees and pick out the column grants for sales beside the table grants (arwd) for tech.
  3. Match each line to a known grant: r for the wide reads, arwd for the picked-table writes, column lines for the bracket grants, policy lines for the USING filters.

Sense-check: every grant issued in earlier sections has exactly one visible line — a missing line means the grant never landed or went to the wrong object.

Programmatic extras, noted once since the lecture uses the terminal form: the same facts live in information_schema.role_table_grants, information_schema.role_column_grants, and pg_policies, which MySQL (SHOW GRANTS, INFORMATION_SCHEMA), Snowflake (SHOW GRANTS, ACCESS_HISTORY), and Databricks (SHOW GRANTS ON TABLE) mirror in their own catalogs. One view is enough per system; \z is this lecture's.

Scope: \z shows object grants and policy definitions, not instance attributes or the CONNECT chain — check role properties and database grants separately. Assumption: output is read as the object owner or a privileged role; some policy expressions may hide from unprivileged viewers.

Pitfalls. Misreading arwdDxt as a word instead of letter codes — decode letter by letter. Confusing the grantor (/postgres) with the grantee — the name before = holds the right. Skipping \z before a new grant — duplicate or contradictory grants pile up silently.

Recap: \z joins schema, rights string, role, column lines, and policy filters in one screen — the pre-change audit for every grant. Next, row rules add a performance cost worth measuring.

43.13.1 Worked Example: Read a Rights Line

Run \z jobs and parse each block: schema, table, rights string, role, policy name, policy kind, and filter. Then run \z employees and pick out the column grants for sales beside the table grants for tech. Use this view before changing rights, so no grant is added blind.

43.14 Row Level Security Performance

Row rules are invisible filters on every query. What does an invisible WHERE clause cost across ten million rows — and twenty stacked policies?

Row rules are strong but not free. Each policy expression acts as a must-pass WHERE arm added to every query on that table. A policy is in effect a required filter that trims the active user down to the picked slice of facts — the planner cannot skip it even when the user's own WHERE clause looks selective.

Passing that filter costs a scan. Each row must meet the WHERE arm to pass, so a SELECT * over millions of rows pays a check per row. More policies mean more WHERE checks per row on each query, so ten or twenty policies on a huge table can weigh heavily. Think of each policy as one more toll booth on a highway: one booth slows every car slightly, twenty booths in a row jam the road.

Why plans change. Order of checks also matters. The system aims to run policy checks before user-given filters so guarded facts cannot leak through a crafted filter — a safe order that can still shape plans, since indexes chosen for the user's filter may not serve the policy arm. Joins across many guarded large tables with foreign keys need extra review, since guarded joins have shown slowdowns. Build paths in PostgreSQL 10 and later handle this much better through inlining of policy expressions, but the shape of the plan still needs a look.

A steady habit helps: run EXPLAIN ANALYZE on guarded queries, watch how the planner treats the policy arms (look for extra filter nodes and row-count drops at the policy step), and tune indexes and join order. Larger or more tangled policies tend to cost more, so keep each expression as tight as the rule allows — an equality on an indexed marker beats a function call on an unindexed expression every time.

Guarded multi-firm tables with per-firm reads use tight equality filters on indexed firm markers to hold join costs down: USING (firm_id = current_setting('app.firm_id')::int) with an index on firm_id turns the policy arm into an index lookup instead of a full scan. Snowflake and Databricks carry the same cost under different names — row access policies and row filters both add per-row evaluation — so the tight-equality-plus-index rule transfers unchanged.

Scope: this section states design rules, not measured timings — each workload needs its own EXPLAIN ANALYZE before and after a policy change. Assumption: policies are simple boolean expressions over row data. Calls to slow functions, subqueries, or untrusted external checks inside a policy multiply the per-row cost.

Pitfalls. Stacking ten or twenty policies on a huge fact table — per-row checks multiply. Writing policy filters with function calls on unindexed columns — the planner cannot use an index it cannot see. Skipping EXPLAIN ANALYZE after adding a guarded join — the slowdown surfaces in production instead of review.

Recap: every policy is a mandatory WHERE arm with per-row cost, safe-first ordering shapes plans, and tight indexed equality plus EXPLAIN ANALYZE keeps guarded queries fast. Next, column encryption guards facts that rights alone cannot hide. Exam note: expect a question on why guarded queries slow down and which two habits — tight filters and plan measurement — control the cost.

43.14.1 Design Rules That Keep Queries Fast

Keep each policy filter short. Limit the count of policies per huge table. Watch joins between guarded tables. Measure with EXPLAIN ANALYZE before and after a policy change. Row control stays a sound pick when these costs sit in the plan from the start.

43.15 Encrypted Data in Columns With pgcrypto

Rights decide who may open the drawer — but the backup tape holds every drawer at once. What guards the mails when the bytes themselves leave the server?

Some facts need more than rights: they need scrambling at rest. The pgcrypto add-on brings that power. Turn it on once per database:

CREATE EXTENSION pgcrypto;

A rerun reports the add-on already exists, which is normal. Think of rights as the locked drawer and encryption as writing the letters inside in code: even someone holding the drawer (a backup, an admin peeking at raw pages) reads only cipher bytes without the key.

A demo table held mails:

CREATE TABLE e_users (id SERIAL PRIMARY KEY, email VARCHAR NOT NULL UNIQUE);

The length was left open on purpose, since scrambled bytes can run longer than plain text and a tight cap such as VARCHAR(30) could break writes. A refresh showed the table with id and email columns in plain form. The trick is that the column itself stays plain while the facts placed inside are scrambled. Every write scrambles first, and reads unscramble on demand — the column type does not change, only the bytes stored in it.

Scramble on write, unscramble on read. Two helpers do the work: pgp_sym_encrypt scrambles and pgp_sym_decrypt unscrambles with a shared secret key. A write looks like:

INSERT INTO e_users (email) VALUES (pgp_sym_encrypt('a1@b1.com', 'long-secret-key'));
INSERT INTO e_users (email) VALUES (pgp_sym_encrypt('a2@b1.com', 'long-secret-key'));

Here the first input is the plain mail and the second input is the shared secret key. Because symmetric encryption uses a random session key per call, even the same plain mail stores different bytes per write — so the UNIQUE rule on the scrambled form cannot catch duplicate mails and should not be relied on for dedupe here. A SELECT * FROM e_users then shows long scrambled byte strings with no readable mail, which is the point: admins and onlookers see bytes, not addresses. A read unscrambles with the same key:

SELECT pgp_sym_decrypt(email::bytea, 'long-secret-key') FROM e_users;

The stored bytes cast to bytea feed the helper with the key, and plain mails return. Note the return type is text only after decryption — comparisons, sorts, and LIKE on the raw column match cipher bytes, not mails.

Cross-database extras, once: MySQL offers AES_ENCRYPT/AES_DECRYPT with a similar shared key, Snowflake offers ENCRYPT/DECRYPT plus Tri-Secret and Always Encrypted style client-side paths, and Databricks leans on storage-side encryption plus column masks. The shared-secret symmetric pattern here is common; only the function names change.

Worked example — scramble two mails then read them back. Setup: add-on on, table e_users built with open VARCHAR.

  1. Insert two mails with pgp_sym_encrypt and the same secret key.
  2. Run SELECT * FROM e_users and see only long byte strings — no readable mail.
  3. Run the pgp_sym_decrypt read with the key and see both plain mails return.
  4. Confirm the round trip: bytes at rest, plain text only through the key.

Sense-check: unreadable bytes without the key plus exact mails with it proves the column path end to end.

Scope: pgcrypto guards bytes at rest against storage-level readers. It does not replace grants — anyone with the key and SELECT still reads plain mails. Assumption: the key travels and rests outside the demo notes. Demo keys such as long-secret-key never belong in live code or logs.

Pitfalls. Guard the key on the wire: send it over SSL or a private net, never in the open — a sniffed key undoes every byte. Remember scrambling happens inside the database, so plain facts cross the link and can sit in memory; memory-dump theft is a true risk, which client-side encryption would avoid. Expect slower sorts and filters: unscramble runs per row across the table, so sort or filter on a scrambled column runs slowly — keep searchable columns plain and encrypt only the sensitive payload.

Recap: CREATE EXTENSION pgcrypto plus pgp_sym_encrypt/pgp_sym_decrypt scrambles column bytes at rest, with key handling and per-row cost as the two lasting cautions. That closes the six levels plus encryption: rights shape who reaches what, scrambling guards what leaves the disk. Exam note: expect a task that enables the extension, inserts with pgp_sym_encrypt, reads back with pgp_sym_decrypt plus the ::bytea cast, and states two cautions (key over SSL, slow filtered sorts).

Setup: add-on on, table e_users built with open VARCHAR. Insert two mails with pgp_sym_encrypt and the same secret key. Run SELECT * FROM e_users and see only bytes. Run the pgp_sym_decrypt read with the key and see plain mails return. That round trip proves the column path end to end.

Exam Guidance Summary

No mark split or fixed question list was stated in this material. The steady signals for study and review are: start every level from zero rights with REVOKE ALL ... FROM PUBLIC before adding grants; keep the chain CONNECT on the database plus USAGE on the schema plus picked table and column rights, since a missing link blocks the path; favor narrow table and column grants over wide ones, and treat TRUNCATE, TRIGGER and salary or phone columns with added care; for row rules, keep in mind that turning control on flips the base to deny all, plain OR joins many permissive policies while AS RESTRICTIVE joins with AND, and zero rows often means rights rather than missing facts; for key handling, guard the secret key on the wire over SSL and expect slower sorts and filters on scrambled columns.

Exam note: expect hands-on tasks that ask for the exact grant form per level, such as connect on a database, usage on a schema, select on all tables in a schema, select on picked columns with named-column queries, and a row policy with a USING filter — each paired with a re-sign-in and a count or denial check.

Key Industry Applications

Job-family group roles let firms onboard staff with membership changes only — joiners gain one membership, leavers lose it, and no per-table grant is ever rewritten. View-only roles such as instance_viewer and sales reads give analysts safe sight without write risk, while per-table writes such as tech on employees and regions keep data entry tight to named tables. Column limits hide pay and phone facts from groups that do not need them, so payroll and sales share one table with different visible slices.

Row policies with pay bands, CURRENT_USER keys, and session markers such as app.username let multi-user apps and multi-firm stores keep each party to its own rows from a single shared table — one policy per pattern instead of one rule per user. pgcrypto with pgp_sym_encrypt and pgp_sym_decrypt guards mails and other sensitive columns at rest, with keys moved over SSL and searchable columns kept plain for speed. Audits and speed reviews in live systems run on \z checks, EXPLAIN ANALYZE plans, and the admin tool views for roles, members and flags.
