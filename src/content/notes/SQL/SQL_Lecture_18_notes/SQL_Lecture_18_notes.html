18.1 UNION with Filters and Conditions

18.1.1 Meaning and Basic Shape of UNION

Why would anyone run two queries when one question is being asked? Because sometimes the answer lives in two different tables. Directors sit in one table, actors in another, and the question — "give me all these people in one list" — spans both. That is the hook for this whole lecture: one list, two homes.

A UNION (a set operator that stacks the rows of two queries into one result) takes the output of a first SELECT and appends the output of a second SELECT. The plain-language idea is simple: run query one, run query two, then pile both answer sets into a single list. Think of two paper attendance registers from two classrooms being copied, page after page, into one combined register. The copying is positional — first column lands on first column — and at the end any fully identical lines are kept only once.

Think of UNION as stapling two printed lists together and then crossing out exact duplicate lines. The staple is positional: column one goes onto column one, column two onto column two. Where this everyday picture breaks: paper lists keep duplicates unless you cross them out by hand, while plain UNION always removes them automatically.

In set terms, when \(D\) is the row set returned by the first query and \(A\) is the row set returned by the second query, the combined result is

\[ R = D \cup A \]

Here \(D\) and \(A\) are multisets of rows, \(\cup\) is set union, and \(R\) is the stacked result with duplicate rows removed. Plain UNION removes duplicates, so a row that appears in both answers shows up only once in \(R\). Row-count consequence: the size of \(R\) is at most the sum of the two side sizes, and it is strictly smaller whenever the two sides share at least one identical row.

The two queries join with the keyword UNION placed between them:

SELECT first_name, last_name FROM directors
UNION
SELECT first_name, last_name FROM actors;

Each side names a table — \(directors\) holds one group of people and \(actors\) holds another — and each side picks the same kind of columns, here \(first\_name\) (given name text) and \(last\_name\) (family name text).

Worked example — the smallest possible UNION. Side one returns 2 rows: (Ab, Cole) and (Alec, Gu). Side two returns 2 rows: (Ab, Cole) and (Milan, No). Stacking gives 3 rows, not 4: (Ab, Cole) appears in both sides but survives only once, so the answer is 3 rows — (Ab, Cole), (Alec, Gu), (Milan, No). Sense-check: 2 + 2 − 1 shared = 3, which matches.

Building each SELECT on its own and running it on its own before combining is the working habit shown throughout: test side one, test side two, then stack them. That habit catches wrong columns and wrong filters early, while each query is still small enough to check by eye.

Scope: UNION stacks rows; it never matches or joins them side by side the way a JOIN does. Rows line up by column position, not by column name, so two same-named columns in different positions still land on each other. The operator applies after each side is fully computed, which is why filters belong inside the sides (next section) and the sort belongs at the very end (section 18.1.3).

A concrete picture for the shape of the result: imagine a two-column grid with \(first\_name\) on the horizontal reading order and one row per person down the page. Directors fill the top block of rows, actors fill the block below, and one shared name that sat in both blocks now occupies a single row. Takeaway: the grid grows downward, never sideways.

Two traps beginners hit immediately. First, stacking queries that select different kinds of columns — names on top, birth dates below — runs without error but produces a nonsense column; UNION checks positions and compatible types, not meaning. Second, assuming duplicates survive: if the same (first_name, last_name) pair sits in both tables, plain UNION reports it once, and counting rows afterward will disagree with the sum of the two sides.

UNION stacks two tested SELECTs into one deduplicated list, \(R = D \cup A\), lining columns up by position. Its sibling UNION ALL (section 18.1.2's comparison) keeps every row including duplicates. Next, filters move inside each side so each table contributes only its qualifying rows.

Picture two conveyor belts — one carrying director cards, one carrying actor cards — each passing its own checkpoint before both belts drop their survivors into a single bin. That checkpoint-per-belt image is exactly the next section.

18.1.2 Filtering Each Side with WHERE

A WHERE clause (a filter that keeps only rows meeting a stated test) can sit inside either side of a UNION, or inside both sides at once. Each SELECT filters its own table first, and UNION then stacks the two filtered lists. This is how one request can mix different conditions from different tables in a single answer — nationality logic on the directors side, gender logic on the actors side, combined into one list.

The execution order is fixed: filter first, stack second. When \(D_f\) is the filtered directors set and \(A_f\) is the filtered actors set, the answer is

\[ R = D_f \cup A_f \]

not a filter applied after stacking. That ordering is what lets each side use completely different columns in its test — \(nationality\) on one side, \(gender\) on the other — because by stacking time both sides expose only the shared output columns.

The first full task combines directors of certain nationalities with female actors. The directors side keeps only rows whose \(nationality\) (country label stored as text) belongs to a short list:

SELECT first_name, last_name, nationality FROM directors
WHERE nationality IN ('American', 'Chinese', 'Japanese');

An IN list (a shorthand for several OR tests, written as \(IN\) followed by quoted values in parentheses) checks whether \(nationality\) equals any one of the three listed values. Saying nationality IN ('American', 'Chinese', 'Japanese') is exactly saying nationality equals American, or Chinese, or Japanese. The \(nationality\) column was added to the select list during the build purely so the eye could confirm the filter: every returned row shows American, Chinese, or Japanese, which proves the filter works before the UNION step.

The actors side keeps only rows whose \(gender\) (single-letter code stored as text) marks a female actor:

SELECT first_name, last_name, gender FROM actors
WHERE gender = 'F';

Here \(gender\) is the code column and \('F'\) is the quoted literal meaning female. Again an extra column, \(gender\), was shown during the build just to confirm that every row really is marked F, and then removed once the check passed. Stacking the two tested sides gives:

SELECT first_name, last_name FROM directors
WHERE nationality IN ('American', 'Chinese', 'Japanese')
UNION
SELECT first_name, last_name FROM actors
WHERE gender = 'F';

Worked example — nationality plus gender, 73 records. Run the directors side alone and confirm every visible nationality reads American, Chinese, or Japanese. Run the actors side alone and confirm every visible gender reads F. Remove the check columns, stack with UNION, and the combined answer holds 73 records: qualifying directors plus female actors, duplicates gone. Sense-check: the total cannot exceed the sum of the two side counts, and falls short of it by exactly the number of shared names.

A second task follows the same shape with a date test. It asks for directors and actors born after 1990. The actors side carries the filter on \(date\_of\_birth\) (birth date stored as a date value):

SELECT first_name, last_name FROM actors
WHERE date_of_birth > '1990-12-31';

The date literal uses the standard ISO form \('1990-12-31'\) — four-digit year, two-digit month, two-digit day in quotes — the same written form used across the reference texts for date values. The \(>\) sign means strictly later than that date, so anyone born exactly on 1990-12-31 would not qualify. With the cutoff at the end of 1990 only one row, James David, came back. Moving the cutoff back to 1970 returned three rows, which confirmed the comparison was live and responding — changing the cutoff changed the count, so the filter is genuinely driving the result.

Worked example — birth-date cutoff, 57 records. The directors side runs with no filter at all — all 38 directors — and is stacked against the filtered actors side. The actors side keeps only rows with \(date\_of\_birth\) later than the cutoff. With \(date\_of\_birth\) added to both select lists for checking, and the combined rows sorted by birth date oldest first, 57 records come back, each one born after the cutoff. Sense-check: 57 is larger than 38, so the filtered actors side must contribute 19 or more rows depending on overlap — the stack genuinely mixes both tables.

UNION versus UNION ALL deserves a side-by-side stop, because the lecture's dedupe behavior is only half the story. Plain UNION sorts the combined set and removes duplicates; UNION ALL skips both steps, so its row count always equals the sum of the two sides and it runs faster since the server never checks for overlap. Pick UNION when the question wants a clean distinct list ("all people"); pick UNION ALL when duplicates are meaningful or when speed matters on large feeds ("all transactions, keep every line"). Every major database — PostgreSQL, MySQL, Snowflake, Databricks — supports both spellings.

Scope: each WHERE belongs to its own SELECT and sees only that side's table. A filter naming a column that exists solely on the other side fails on the side where it sits. Also, the extra check columns (\(nationality\), \(gender\), \(date\_of\_birth\)) must be removed before stacking unless both sides carry them — leaving a check column on one side only re-triggers the column-count error of section 18.1.5.

Three pitfalls cluster here. First, writing one WHERE after the whole UNION hoping it filters both sides — it cannot; each side needs its own. Second, comparing dates as bare numbers or unquoted text instead of the quoted ISO form, which invites silent mis-comparison. Third, forgetting that \(>\) excludes the boundary itself: "born after 1990" with cutoff '1990-12-31' excludes anyone born on that exact day; use \(>=\) when the boundary counts.

Exam note: expect to hand-trace a UNION where each side has its own WHERE — filter each side independently, then stack and dedupe. Remember the order: filter first, stack second, sort last. The next section answers the two questions every stacked list raises: where did each row come from, and in what order should the answer read?

18.1.3 Tagging Source Rows and Sorting the Combined Result

Once rows from two tables sit in one list, a natural doubt appears: which row came from which table. The fix is a literal tag column (an extra output column filled with a fixed quoted word instead of table data) added to each side:

SELECT first_name, last_name, 'directors' AS source_table FROM directors
WHERE nationality IN ('American', 'Chinese', 'Japanese')
UNION
SELECT first_name, last_name, 'actors' AS source_table FROM actors
WHERE gender = 'F';

Here \(source\_table\) is the alias (display name) of the new column, \('directors'\) is the fixed word stamped on every row from the first query, and \('actors'\) is the fixed word stamped on every row from the second query. Running this shows each row carrying its origin label, so the mix can be read row by row. Think of a baggage tag tied to every suitcase before two flights' luggage shares one carousel: the tag, not memory, says which flight each bag came from.

A literal tag works because UNION only requires matching column counts and compatible types — nothing says every output column must come from a table. A quoted fixed word like \('directors'\) is a text value like any other, so it occupies a column slot legally. Both sides must add the tag in the same position, or the labels land in different columns and the lineage signal scrambles.

Worked example — stamped rows, read row by row. Side one emits (Ab, Cole, 'directors'); side two emits (Milan, No, 'actors'). After stacking, each row carries its origin label: Ab Cole reads directors, Milan No reads actors. Sense-check: filtering the combined answer on \(source\_table =\) 'directors' must return exactly the first side's rows — if it does, the tags are correctly aligned.

An ORDER BY (a sort instruction naming the column to sort on) goes at the very end of the whole UNION, never inside one side, because it sorts the combined result:

SELECT first_name, last_name FROM directors
WHERE nationality IN ('American', 'Chinese', 'Japanese')
UNION
SELECT first_name, last_name FROM actors
WHERE gender = 'F'
ORDER BY first_name;

Worked example — one sort for the whole stack, 171 records. Sorted by \(first\_name\) from the top, the answer lists 171 unique records, opening with names such as Ab, Adrian, and Alec. The same end-placement rule applied to the birth-date task: ORDER BY on \(date\_of\_birth\) in ascending order arranged the 57 combined rows oldest first, with a value such as 1982 shading the early rows. Sense-check: the earliest rows carry the smallest dates and the opening names sit at the very start of the alphabet — both confirm the sort ran over the combined list, not one side.

The sort rule generalizes: ORDER BY sits after the last SELECT and may name an output column or its position; it arranges the finished stack. That is why a sort placed inside one side either errors or sorts only to be re-merged — the combined result is the only thing worth ordering.

Scope: the tag column changes duplicate behavior — two otherwise identical rows from different tables now differ in their tag, so UNION keeps both. Tag first and the dedupe count grows; that is usually the point (lineage beats compactness), but it means tagged and untagged versions of the "same" UNION legitimately return different counts. ORDER BY sees only output-column names, so sorting by a table-only column that was projected away fails.

Two classic mistakes: placing ORDER BY inside the first SELECT, which the database reads as an instruction for that side alone rather than the stack; and tagging only one side, which changes the column counts to 3-versus-2 and raises the column-count error instead of labeling anything. Tag both sides in the same slot, sort once at the end.

Stamp each side with a literal tag in the same position to keep lineage, then sort once at the very end — 171 unique rows from A onward is what a correctly tagged and sorted stack looks like. Merging contact lists from two systems with a source tag on each row is the everyday version of exactly this move, and it recurs whenever customer or staff data from separate stores must stay traceable after the merge. Next, names get filtered by shape rather than exact value.

18.1.4 Pattern Matching with LIKE and Case Sensitivity

Exact matches answer "who is named Ab"; patterns answer "whose name starts with A" — a question no list of \(=\) tests can ask compactly. A LIKE pattern (a text match built with the keyword \(LIKE\) plus wildcard signs) filters names by shape instead of exact value. The task here asks for directors and actors whose first name starts with A. The pattern \('A\%'\) pairs a capital A with the wildcard \(\%\), where \(\%\) (percent sign) stands for any run of characters, including none. So \('A\%'\) reads as: capital A first, then anything.

SELECT first_name, last_name FROM directors
WHERE first_name LIKE 'A%'
UNION
SELECT first_name, last_name FROM actors
WHERE first_name LIKE 'A%';

The wildcard \(\%\) matches any sequence of characters, including the empty sequence, so \('A\%'\) accepts "A", "Ab", and "Adrian" alike — every value whose first character is capital A. The position of \(\%\) decides the question: trailing \(\%\) asks "starts with", leading \(\%\) asks "ends with", and wrapping \(\%\) on both sides asks "contains". A second wildcard, the underscore \(\_\,\) matches exactly one character, so \('A\_'\) would mean "capital A followed by exactly one more character".

Worked example — starts-with-A on both sides. Applied to both sides, the filter returns names opening with capital A — Ab and Alec among them. Two contrasts sharpen the pattern's meaning. First, swapping to lowercase \('a\%'\) returns nothing, because the match is case sensitive: lowercase a does not equal stored capital A. Second, moving the wildcard to both sides as \('%a\%'\) changes the question entirely — it now reads as "the letter a anywhere inside the name" — and rows such as Paul, Thomas, James, France, and Francis flood in. Sense-check: every row in the first answer starts with A, every row in the second contains an a somewhere — position of \(\%\) fully explains both lists.

That pair of trials is worth keeping side by side: the position of \(\%\) decides the question being asked.

Case sensitivity differs by database, and this is the lecture's main cross-database wrinkle. The lecture's database matches case sensitively, as does PostgreSQL, where LIKE is case sensitive and ILIKE is the case-insensitive sibling (first_name ILIKE 'a%' would have matched Ab and Alec). MySQL is the odd one out: with its usual case-insensitive collations, LIKE 'a%' matches capital-A names too. So the "lowercase returns nothing" result travels with PostgreSQL-style databases but not automatically with MySQL — always check the collation before relying on case behavior.

Scope: LIKE tests text columns; applying it to numbers or dates forces a conversion the database may or may not perform. Leading wildcards (\('%a\%'\)) cannot use an ordinary index on the column, so "contains" searches slow down on large tables — a genuine scoping limit, not a beginner slip. LIKE patterns are also exact about what they do not do: \(\%\) never crosses into regular-expression territory (no character classes or repetitions).

Picture a library card catalog drawer labeled "A": trailing-\(\%\) pulls exactly that drawer, while wrapped-\(\%\) rifles every drawer in the room for any card mentioning "a". Takeaway: narrow the wildcard to the narrowest question that suffices.

Beginners most often misplace the wildcard and then distrust the right answer — "contains" results look wrong only because "starts with" was intended. The second trap is quoting: the pattern must be a quoted string, so an unquoted LIKE A% is a syntax error, not a pattern. Third, forgetting case: on a case-sensitive database, searching \('a\%'\) when the data holds capitals silently returns zero rows with no error to explain why.

LIKE filters by shape — trailing \(\%\) for "starts with", wrapped \(\%\) for "contains" — and case behavior follows the database, with PostgreSQL offering ILIKE as the insensitive twin. Up next is the rule that guards every UNION ever written: both sides must return the same number of columns.

18.1.5 Same Column Count Rule

Every SELECT in a UNION must return the same number of columns. Trying to stack a four-column top query against a three-column bottom query — the demo added \(date\_of\_birth\) to the directors side only — fails with the error "Each UNION query must have the same number of columns." The fix is direct: give both sides the same columns, adding the matching column to the short side, and the stack then runs — 173 records in the demo.

The rule exists because UNION aligns columns purely by position: slot one with slot one, slot two with slot two. With unequal counts some slot would have no partner, so the database refuses the stack instead of guessing. Treat counting columns as a pre-flight check, not a debugging step — count first, then combine.

Worked example — the four-versus-three failure and fix. Side one selects \(first\_name\), \(last\_name\), \(nationality\), \(date\_of\_birth\) (four columns); side two selects \(first\_name\), \(last\_name\), \(gender\) (three columns). The stack fails with the column-count error. Adding the fourth column to the short side makes it four-versus-four, and the stack runs: 173 records. Sense-check: the count changes from the earlier 171 because the extra column distinguishes rows that previously looked identical — finer rows, fewer collapsed duplicates.

Scope: matching counts are necessary but not enough on their own — aligned slots must also carry compatible types (text onto text, dates onto dates), or the database rejects or implicitly converts the mismatch. Column names need not match across sides; the combined output takes its headings from the first SELECT, so a well-named first side doubles as the report's header row.

The recurring mistake is the leftover check column: a debugging column added to one side during testing (\(nationality\) shown to verify a filter) that never gets removed — or never gets mirrored — before stacking. Any column-count error should trigger one reflex: diff the two select lists slot by slot until the unpaired slot shows itself.

Exam note: when shown two SELECTs, count the columns on each side before anything else — a mismatch means the error fires before a single row is examined. And where tables genuinely differ in shape rather than by a leftover column, positional counting alone cannot save the query; that genuine mismatch is the subject of section 18.2, which turns NULL into a padding tool.

18.2 UNION Tables with Different Numbers of Columns

18.2.1 Building the Mismatched Tables

What happens when the two tables genuinely differ in shape — not by a leftover debugging column, but by design? Then counting first (the lesson of 18.1.5) reveals a real mismatch, and the query needs a padding technique rather than a cleanup. This section builds that exact bind from scratch: a first table with two integer columns and a second table with one integer column.

Why would tables ever differ this way? Because real feeds do: a legacy export carries two fields per record while a newer feed carries one, yet the monthly report needs a single combined list. The demo's tiny integer tables stand in for exactly that uneven-feed situation.

CREATE TABLE table_one (
  column_one INT,
  column_two INT
);

CREATE TABLE table_two (
  column_three INT
);

A CREATE TABLE (a statement that defines a new table by naming it and listing its columns with types) makes \(table\_one\) with \(column\_one\) and \(column\_two\), both \(INT\) (whole-number type), and \(table\_two\) with only \(column\_three\), also \(INT\).

Checking each side alone confirms the shapes before any stacking is attempted:

SELECT column_one, column_two FROM table_one;
SELECT column_three FROM table_two;

The first SELECT returns two columns, the second returns one. Writing UNION between them at this point fails with the same column-count error met in the previous section: each UNION query must have the same number of columns. The shapes do not line up, so the stack is refused — and rightly so, since slot two of the first side would have no partner.

Worked example — the refusal, step by step. Create both tables. Run side one alone: two columns come back. Run side two alone: one column comes back. Write UNION between them and the database refuses with the column-count error — zero rows, one error message. Sense-check: 2 versus 1 means one slot unpaired, so refusal is the only consistent behavior.

Scope: CREATE TABLE here builds throwaway scaffolding for the demo, not production schema — no keys, no constraints, minimal types. The mismatch is deliberate and structural: no column can simply be dropped from the wide side without losing data, so padding (next section) is the honest fix rather than trimming.

The beginner trap is "fixing" the error by deleting the extra column from the wide side's SELECT. The query then runs — but it silently discards data that the report was supposed to carry. A refused UNION is the database protecting the answer's completeness; the correct reflex is to pad the narrow side up, never to cut the wide side down.

Two genuine shapes — a two-column table and a one-column table — cannot stack as written, and the database says so. Padding the short side with NULL is the technique that follows, turning refusal into a clean merged list.

18.2.2 Padding with NULL to Align Columns

A NULL (a marker meaning "no value here" rather than zero or blank text) pads the short side so both queries return the same number of columns. The trick adds a NULL-filled column with an alias matching the missing slot:

SELECT column_one, column_two FROM table_one
UNION
SELECT column_three, NULL AS column_one FROM table_two;

Here \(column\_three\) is the real stored value from the second table, \(NULL\) is the empty filler in the second slot, and \(AS\ column\_one\) labels the filler column so the combined output reads cleanly.

In set terms, when \(T_1\) holds pairs and \(T_2\) holds single values, padding lifts each single value \(v\) into a pair \((v, NULL)\) so the union lines up slot by slot:

\[ R = T_1 \cup \{(v, NULL) \mid v \in T_2\} \]

The padded pair carries the real value in slot one and declared emptiness in slot two — NULL is not zero, not blank text, not a guess; it is the database's explicit "no value here" marker, which is exactly what an absent field means.

Worked example — padded merge. Suppose \(table\_one\) holds (1, 10) and (2, 20), while \(table\_two\) holds 5 and 7. The padded side emits (5, NULL) and (7, NULL). Stacking gives four rows: (1, 10), (2, 20), (5, NULL), (7, NULL). Sense-check: every row now has two slots, real values sit where they belong, and the NULLs mark precisely the fields the narrow feed never had.

Think of a form with two boxes where some respondents received a one-box version: padding writes "left blank" in the missing box rather than inventing an answer. Where the picture breaks: on paper "left blank" is handwriting, while NULL is a first-class database value with its own three-valued logic — NULL = NULL is never true, a fact that matters the moment padded rows meet later filters or joins.

Cross-database portability is the quiet bonus here. Positional NULL padding works identically in PostgreSQL, MySQL, Snowflake, and Databricks — no dialect offers a "pad automatically" shortcut, and none needs one, because an explicit NULL in the select list is already the portable idiom. Where dialects differ is only in adjacent areas: Oracle names its difference operator MINUS rather than EXCEPT, and older MySQL versions emulate INTERSECT and EXCEPT with joins or subqueries — but NULL padding itself travels unchanged.

Scope: padding preserves layout at the cost of introducing NULLs downstream — aggregates like AVG skip NULLs, and comparisons against the padded column need IS NULL rather than \(=\) NULL. Pad with a typed NULL (CAST(NULL AS INT)) when the database cannot infer the filler column's type, and prefer a meaningful default (0, 'unknown') only when the business genuinely defines one; otherwise NULL's honesty beats an invented stand-in.

Picture the merged report as a two-column ledger: wide-table rows fill both columns with ink, narrow-table rows fill slot one with ink and stamp slot two "no value". Takeaway: one layout, honest gaps.

Two pitfalls: padding in the wrong slot (filler first, value second) silently scrambles every row — slot order must mirror the wide side exactly. And forgetting the alias, which leaves the filler column with a blank or generated heading in the report; harmless to execution, sloppy in output.

NULL padding lifts narrow rows into the wide shape so UNION lines up slot by slot — the standard move when merging uneven feeds into one shared report layout. With the technique shown, the scaffolding tables have served their purpose and should leave the workspace as they found it.

18.2.3 Cleanup with DROP TABLE

Demo tables should not linger after they served their purpose. A DROP TABLE (a statement that deletes a whole table definition and its rows) removes the scaffolding:

DROP TABLE table_one;
DROP TABLE table_two;

Worked example — create, show, drop. After the padded UNION runs and its result is recorded, both DROPs execute, and refreshing the table list confirms both names are gone — zero leftover tables, workspace exactly as found. Sense-check: the technique lives on in the query text, which needs no tables to remain behind.

Scope: DROP TABLE is absolute — definition and rows vanish together, with no undo short of a backup. In this demo the tables hold throwaway integers, so dropping is safe; against real data the same statement destroys real rows. The habit transfers with a guardrail: create, show the technique, then drop only what you created, and double-check the name before executing.

The one pitfall is over-cleanup: dropping a table the demo did not create, or dropping before the final result was captured. Work in order — verify the merged output first, drop second, refresh the list third.

Exam note: a question that builds uneven tables, pads with NULL, and cleans up tests three behaviors in sequence — the column-count refusal, the NULL-lifted union, and tidy teardown. The same three-step rhythm (scaffold, technique, cleanup) is worth reproducing exactly. From here the lecture turns from stacking rows to comparing lists: INTERSECT keeps what two tables share.

18.3 INTERSECT with Tables

18.3.1 Meaning, Conditions, and Syntax

Stacking asked "what do we have altogether"; intersecting asks the opposite — "what do these two lists share." An INTERSECT (a set operator that returns only rows present in both query results) answers exactly that overlap question. Two warehouse inventories, two customer stores, two people tables: the shared entries are the answer.

Think of two overlapping circles drawn on paper — the lens-shaped middle where they cross. Each circle is one query's answer; the lens is INTERSECT's. Where the picture breaks: paper circles show members loosely, while SQL compares whole rows exactly — every column must match, not just a glanceable name.

In set terms, when \(L\) is the row set from the first query and \(P\) is the row set from the second query, the answer is

\[ R = L \cap P \]

where \(\cap\) is set intersection and \(R\) holds exactly the rows found in both \(L\) and \(P\). Two conditions gate its use. First, the order and the number of columns in the select lists of all queries must match. Second, the columns in matching positions must carry compatible data types. If either condition fails, the operator refuses before examining a single row.

The syntax places the keyword between two queries:

SELECT column_one, column_two FROM table_one
INTERSECT
SELECT column_one, column_two FROM table_two;

The first SELECT is query one, INTERSECT is the operator, and the second SELECT is query two. The result holds shared rows only, and it holds each shared row once — INTERSECT returns distinct rows, so duplicates collapse even when the same row repeats inside one side.

Worked example — the collapse rule in miniature. Side one returns (laptop), (laptop), (mics); side two returns (laptop), (monitors). The overlap is (laptop) alone, and despite appearing twice on side one, the answer is one row: laptop. Sense-check: shared and listed once — that single-each behavior is the signature of INTERSECT.

A portability flag belongs here. PostgreSQL, Snowflake, Databricks, and SQL Server all spell the operator INTERSECT as the lecture does. Oracle agrees on INTERSECT too (its divergence is only EXCEPT, which it calls MINUS). MySQL is the exception: older versions lack INTERSECT entirely and emulate the overlap with an INNER JOIN or an IN-subquery — a workaround worth knowing when a query must run on MySQL.

Scope: INTERSECT compares full rows, not keys — a product matching on \(product\_id\) but differing on \(product\_name\) is not shared and drops out. NULL handling follows distinctness semantics: two rows that are NULL in the same slot count as matching for set operators, unlike the never-true NULL = NULL in ordinary WHERE tests. And unlike EXCEPT, INTERSECT is symmetric: swapping the sides leaves the answer unchanged.

Picture the result grid with \(product\_id\) across and one row per product down: rows present in both source grids stay lit, every one-sided row goes dark, and doubled rows merge into a single lit line. Takeaway: overlap only, once each.

Beginners typically err in two ways: selecting different column counts on the two sides and meeting the refusal (the same positional rule as UNION applies), or expecting duplicates to survive because "the row really appears twice" — set operators always dedupe, so multiplicity never carries through.

INTERSECT keeps exactly the shared distinct rows, \(R = L \cap P\), with matching counts and compatible types as entry conditions. Two walkthroughs now prove the behavior: first on product tables, then on people tables.

18.3.2 Product Tables Walkthrough

The first walkthrough pits two product lists against each other: \(left\_products\) (the left-side product table) and \(right\_products\) (the right-side product table). Each side selects the same two columns, \(product\_id\) (numeric product key) and \(product\_name\) (product label text):

SELECT product_id, product_name FROM left_products
INTERSECT
SELECT product_id, product_name FROM right_products;

Worked example — three shared products. Read side one alone: it contains laptop, computers, monitors, mics. Read side two alone: it contains laptop, computers, monitors, and other rows but no mics. Intersecting keeps only rows present in both, so the answer is exactly three records: laptop, computers, and monitors. The walkthrough then presses on the duplicate question: does a row that repeats still repeat in the answer. It does not — laptop listed twice on one side still returns once. Sense-check: three shared names in, three rows out, each exactly once.

That single-each behavior is the signature of INTERSECT: shared and distinct at the same time.

Scope: the answer's three rows are meaningful only because both sides project the same two columns. Projecting \(product\_name\) alone would merge products that share a name but differ in id; projecting extra columns would split rows that currently match. Choose the column list to define what "same product" means before intersecting.

The trap here is reading the answer as "products only in the left table" — that is EXCEPT's job (section 18.4), and mics, the one-sided row, is precisely the row INTERSECT drops. Shared means present in both; everything else vanishes.

Three shared products in, three rows out, each once — the product walkthrough is the canonical INTERSECT trace to reproduce by hand. The people walkthrough next shows the same operator answering a genuinely investigative question: who appears in both tables?

18.3.3 Shared Names Across Directors and Actors

The second walkthrough asks how many people share a first and last name across the \(directors\) and \(actors\) tables — someone who both directs and acts. Each side is built and run alone first:

SELECT first_name, last_name FROM directors;
SELECT first_name, last_name FROM actors;

The directors side shows names such as Thomas and Pauls; the actors side shows names such as Milan. Stacking them with INTERSECT keeps only the names found on both sides:

SELECT first_name, last_name FROM directors
INTERSECT
SELECT first_name, last_name FROM actors;

Worked example — two double-career names. Running each side alone establishes the inputs: dozens of directors, dozens of actors. Intersecting keeps only full (first_name, last_name) pairs present in both, so two names survive: Bruce Lee and Terry Jones. Sorting sharpens the check — ORDER BY on \(first\_name\) at the end arranges the answer so Bruce Lee reads in order, and running the same sort against the actors table alone confirms Bruce Lee sits there too. Sense-check: each survivor is verifiable in both sources independently, so trust in the operator is earned rather than assumed.

The confirmation loop matters: the shared name is seen in the answer, then seen again in each source, so trust in the operator is earned rather than assumed.

Scope: matching on (first_name, last_name) finds name-sharers, not proven same humans — two different people can share a name, and one person billed differently across tables ("Bruce Lee" vs "Bruce Jun-Fan Lee") will not match. INTERSECT proves shared rows, and the leap from shared rows to shared identity needs a stable key like an id column before it is safe.

A name matching on first name alone would flood the answer with false cousins; the walkthrough's two-column match is what keeps Bruce Lee and Terry Jones meaningful. Always match on the fullest natural key available — fewer columns means more accidental collisions.

Exam note: expect to trace INTERSECT on small two-table inputs and to state the dedupe rule — shared rows collapse to one each even when repeated inside a side. Finding shared keys across two stores, from matching customer names to overlapping product codes before a merge, is exactly what INTERSECT is built for. The mirror operator follows: EXCEPT keeps what the first list has and the second lacks.

18.4 EXCEPT with Tables

18.4.1 Meaning, Conditions, and Syntax

If INTERSECT keeps the overlap, EXCEPT keeps the remainder: "what is in list one but missing from list two." An EXCEPT (a set operator that returns rows of the first query that do not appear in the second) answers exactly that one-sided question — stock in this warehouse but not that one, records in yesterday's feed but missing today.

Think of yesterday's attendance sheet with today's absentees crossed off — except the crossing runs the other way: keep the names on sheet one that never appear on sheet two. Where the picture breaks: crossing off is manual and order-free, while EXCEPT is directional — swapping the sheets asks the opposite question and gives a different answer.

In set terms, when \(F\) is the row set from the first query and \(S\) is the row set from the second query, the answer is

\[ R = F \setminus S \]

where \(\setminus\) is set difference and \(R\) holds exactly the rows of \(F\) with any row also found in \(S\) removed. Order matters here in a way it does not for UNION or INTERSECT: swapping the two queries changes the question, because "in first but not second" points one way only. The same two conditions apply: the order and number of columns across the select lists must match, and matching columns must carry compatible types.

The syntax is:

SELECT column_list FROM table_one
EXCEPT
SELECT column_list FROM table_two;

The first SELECT is query one, EXCEPT is the operator, and the second SELECT is query two. The result keeps rows of query one that never show up in query two — distinct, as with all set operators.

Worked example — direction decides everything. Side one holds (laptop), (mics); side two holds (laptop). Then side one EXCEPT side two gives one row: mics, while the swapped side two EXCEPT side one gives zero rows: laptop is cancelled by side one. Sense-check: same inputs, opposite questions, opposite answers — direction is content, not decoration.

Dialect names diverge here more than anywhere else in the lecture. PostgreSQL, Snowflake, Databricks, and SQL Server spell it EXCEPT as shown. Oracle spells the identical operator MINUS — same semantics, different keyword. Older MySQL versions offer neither and emulate the difference with a NOT IN subquery or a LEFT JOIN filtered on NULL, which additionally requires care around NULL handling and duplicate elimination that EXCEPT performs automatically.

Scope: EXCEPT subtracts whole rows by equality across all projected columns — narrowing or widening the column list redefines what counts as "the same row" and changes the survivors. Like INTERSECT, it treats two NULLs in the same slot as matching for set-comparison purposes. And it returns distinct rows: a one-sided row repeated three times in side one still appears once.

Picture the two-circle diagram again, but now only the left crescent stays lit — everything in the lens and everything in the right circle goes dark. Takeaway: first list minus any trace of the second.

The dominant pitfall is assuming symmetry: running A EXCEPT B and believing B EXCEPT A gives the same rows. It does not — each direction is a different question. The second trap is projecting too few columns, which makes distinct entities look equal so genuinely one-sided rows get wrongly subtracted away.

EXCEPT keeps first-query rows absent from the second, \(R = F \setminus S\), and swapping sides changes the answer. Two walkthroughs ground the rule: products first, then people with a filtered second side.

18.4.2 Product Tables Walkthrough

The walkthrough returns to \(left\_products\) and \(right\_products\) with the same column pair, \(product\_id\) and \(product\_name\):

SELECT product_id, product_name FROM left_products
EXCEPT
SELECT product_id, product_name FROM right_products;

Worked example — mics stands alone. Reading each side alone first sets up the punch line: the first answer contains mics, while the second answer has no mics anywhere. Computers, laptop, and monitors appear in both, so EXCEPT strips them away, and mics — present in the first query, absent from the second — is the row left standing. Running the query returns one row: mics. Sense-check by eye against both source lists: everything shared cancels out, and only the truly one-sided row remains, which is why this example sticks.

Spotting items stocked in one warehouse but not another, or records present in yesterday's feed but missing today, follows this exact pattern: broad inventory minus the other inventory, survivors tell the story.

Scope: the one-row answer depends on projecting (\(product\_id\), \(product\_name\)) together — matching on names alone would risk merging distinct products that happen to share a label. Reversing the query would instead surface rows only in the right table, a different business question ("what does the other warehouse hold that we lack").

Do not confuse the survivor with the overlap: mics is precisely the row INTERSECT would drop. When hand-tracing, first circle the shared rows, then cross them out — whatever of side one remains uncrossed is the EXCEPT answer.

One-sided mics survives while every shared product cancels — the canonical EXCEPT trace. The people walkthrough next adds the lecture's most reusable shape: a broad first query minus a carefully narrowed second query.

18.4.3 Directors Against Actors with a Filtered Second Query

The next walkthrough compares names across \(directors\) and \(actors\) on \(first\_name\) and \(last\_name\):

SELECT first_name, last_name FROM directors
EXCEPT
SELECT first_name, last_name FROM actors;

Each side is built and run alone first so the inputs are known, then EXCEPT keeps the director names that never appear among actors. Adding ORDER BY on \(first\_name\) at the end sorts the answer for reading, and names such as Bruce surface in the sorted output for checking.

The final task layers a filter onto the second query: list all director first and last names unless the same first name sits among female actors. The directors side stays wide open while the actors side narrows to females only:

SELECT first_name, last_name FROM directors
EXCEPT
SELECT first_name, last_name FROM actors
WHERE gender = 'F';

Here \(gender\) is the code column and \('F'\) is the quoted literal meaning female, the same convention met earlier.

Worked example — broad minus narrowed, 38 survivors. Run alone, the filtered actors side returns 49 female-actor rows. The full EXCEPT then removes from the directors list any name colliding with that female set, leaving 38 rows. Sense-check: the survivor count can never exceed the directors-side count, and every survivor is absent from the 49-row female set — change the WHERE on the second side and the survivors change with it, proving the narrowing filter decides everything.

The shape is worth naming because it recurs constantly: a broad first query minus a carefully narrowed second query. The narrowing WHERE decides everything — change the filter on the second side and the survivors change with it. So the working order is always the same: build side one, build and test the filtered side two, then subtract. Test the narrow side alone first (49 rows confirmed) so a typo in the filter cannot silently empty or flood the final answer.

Scope: the subtraction compares full (first_name, last_name) pairs — a director sharing only a first name with a female actor still survives, because the pair differs. This is deliberate pair-equality semantics, and it means the English phrasing ("unless the same first name sits among female actors") must be read through the projected columns: sameness means sameness of the whole projected row.

The failure mode to memorize: an untested filter on side two. A misspelled literal (\(gender =\) 'Female' instead of 'F') returns zero rows, and subtracting zero rows returns the whole directors table — a plausible-looking but entirely wrong answer. Building and testing side two alone is the guardrail.

Exam note: expect to trace "broad minus narrowed" by hand — run the filter on side two, circle collisions, cross them from side one, count survivors. The narrowing WHERE is the entire question. Exam Guidance Summary

No grading pointers, mark splits, or question-pattern hints were stated alongside these operators. The durable study cues are the behaviors most likely to be tested by hand-tracing:

  • UNION stacks and dedupes while ORDER BY sits at the very end — filter each side first, stack second, sort last.
  • Mismatched column counts fail unless NULL pads the short side in the matching slot.
  • INTERSECT keeps only shared distinct rows — duplicates collapse to one each, and swapping sides changes nothing.
  • EXCEPT keeps rows of the first query absent from the second, so swapping sides changes the answer — broad-minus-narrowed is the shape to practice.

Exam note: expect to trace small two-table inputs for each of the four operators and to spot the column-count error before running. The winning routine is fixed: count columns, run each side alone, combine, verify counts against the side sizes.

Key Industry Applications

Merged people lists from two systems with a literal source tag stamped on each row keep lineage visible after the stack — the standard first step when joining customer or staff data from separate stores.

Uneven exports padded with NULL preserve one shared report layout when feeds carry different fields — a legacy two-field feed stacked against a newer one-field feed without inventing data.

Matching identifiers across stores with INTERSECT finds overlap before a merge — shared customer names, overlapping product codes, common keys confirmed in both systems first.

Subtracting feeds with EXCEPT surfaces one-sided rows such as warehouse-only stock or records missing from the latest extract — yesterday's feed minus today's feed tells exactly what disappeared.
