# Exploring Stock Markets Data

42.1 Selecting First and Last Records in a Table

42.1.1 Overview and Table Schema

A stock exchange produces thousands of price ticks a day, but an analyst usually wants just the edges of the story: when did coverage of this stock begin, and what happened most recently? This section builds the simplest tool for that job — sort the rows by date, then keep only the first few.

A relational table (a named set of rows, each row holding values for a fixed list of columns) is the home of the market data in this lecture. Browsing the stock price dataset and inspecting the schema columns shows how the data is laid out. The table under study is stock_prices, where each row captures one security's trading metrics for one trading day. Its columns are:

Column Meaning
price_id An integer primary key, written price_id, that uniquely identifies one price record; e.g. price_id = 1042 means "record number 1042"
symbol_id A numeric foreign key, written symbol_id, identifying the equity ticker or company; e.g. symbol_id = 1 means "the first tracked stock"
price_date The calendar date of the trading session, written price_date; e.g. 2020-08-28
open The opening market price at the start of the day
high The highest price reached during the session
low The lowest price recorded during the session
close The final settlement or closing price for the session
change_for_day The absolute price movement relative to the prior trading day
return_day The fractional or percentage return realized over the day

Think of the table as a laundry basket of daily bank statements with no staples or page numbers. Shaking the basket never arranges anything: a relational table is an unordered set (a collection with no built-in sequence) by default, so the database returns rows in no guaranteed order unless the query says how to sort. Filtering to one stock isolates its trajectory:

SELECT * FROM stock_prices WHERE symbol_id = 1;

This returns exactly 2,682 rows — every recorded trading day for that one symbol — in an arbitrary order.

42.1.2 Ordering and Limiting Records

An ordering clause, written ORDER BY price_date ASC, sorts the result rows by a column before they are returned. ASC means ascending (oldest to newest); DESC means descending (newest to oldest). A limit clause, written LIMIT 10, keeps only the first 10 rows of that sorted result and discards the rest.

Sorting the symbol's history oldest-first looks like this:

SELECT * FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date ASC;

The output opens with 2010-01-04, 2010-01-05, 2010-01-06, 2010-01-07, and 2010-01-08 — the earliest recorded trading days. Keeping only the first ten rows gives a quick peek at the start of the series:

SELECT * FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date ASC
LIMIT 10;

Exactly 10 rows return, all from January 2010. Retrieving the last ten records using descending order and LIMIT reveals the most recent market activity:

SELECT * FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date DESC
LIMIT 10;

DESC puts the newest trading dates on top and LIMIT 10 keeps the top 10. A healthy habit showed in the lecture is to sanity-check an extreme by dropping the LIMIT temporarily: the full descending query also opens with 2020-08-28, confirming the limited query truly shows the latest dates rather than an arbitrary slice.

SQL evaluates these clauses in a fixed order — WHERE filters first, then ORDER BY sorts, then LIMIT trims — so the limit always applies to the sorted rows, never to random storage order.

42.1.3 Offset Pagination Mechanics

An offset clause, written OFFSET 10, tells the database to skip a fixed number of rows from the top of the sorted result before returning anything. Combined as LIMIT k OFFSET o, the query skips \(o\) rows and then returns at most \(k\) rows — one "page" of data.

To fetch the second page of 10 records in newest-first order — descending pagination where OFFSET skips the newest records and returns the subsequent slice:

SELECT * FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date DESC
LIMIT 10 OFFSET 10;

The engine sorts all 2,682 rows newest-first, skips the 10 newest (which end at 2020-08-17), and returns the next 10 starting with 2020-08-14, 2020-08-13, and earlier. The same mechanism works in chronological order:

SELECT * FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date ASC
LIMIT 10 OFFSET 10;

This skips the first 10 days of January 2010 and shows records starting from 2010-01-19 onward. The everyday picture is a book with numbered pages: LIMIT is the page size and OFFSET is how many lines you thumb past before you start reading. The picture breaks in one way — unlike a printed book, a table has no fixed page order, which is why the ORDER BY must pin the sequence down first.

42.1.4 Mathematical Formulation of Offset Pagination

Page arithmetic turns a page number into the skip-and-take pair the database needs. Let \(p \in \mathbb{Z}^+\) be the 1-based page number (page 1, page 2, and so on), and let \(k \in \mathbb{Z}^+\) be the page size, the number of records per page. The offset \(O \in \mathbb{N}\) (rows skipped) and the limit \(L \in \mathbb{Z}^+\) (rows returned) are:

\[ O = (p - 1) \cdot k \]

\[ L = k \]

The rows returned are exactly those whose 1-based position \(i\) in the sorted result satisfies:

\[ O + 1 \le i \le O + L \]

Checking with the lecture's numbers, page \(p = 2\) of size \(k = 10\): \(O = (2 - 1) \times 10 = 10\) and \(L = 10\), so rows 11 through 20 are extracted — precisely what LIMIT 10 OFFSET 10 returns. As a boundary check, page \(p = 1\) gives \(O = 0\), i.e. skip nothing, which matches LIMIT 10 with no offset.

Scope: This window arithmetic assumes a stable sort order. If two rows tie on the sort key (two trades stamped with the same price_date), their relative order is undefined and a row can appear on two pages or on none. The fix is a tiebreaker column — sort by ORDER BY price_date, price_id — so every row has a unique position.

Assumption: OFFSET counts rows from the current result of the query, not from any permanent storage position. Deleting or inserting rows between page requests shifts every window, so deep OFFSET pagination on live tables can skip or repeat rows. For tables that change under you, prefer keyset pagination (Section 42.1.9).

42.1.5 Worked Examples

Example 42.1.1 — Browsing stock prices for symbol 1. We run SELECT * FROM stock_prices WHERE symbol_id = 1;. The database scans the table, keeps the 2,682 rows with symbol_id = 1, and returns all nine columns. Answer: 2,682 unordered rows. Sense-check: one symbol over roughly ten years of ~260 trading days per year gives about 2,600 rows, so the count looks right.

Example 42.1.2 — Chronological sorting with ASC. We run the same filter with ORDER BY price_date ASC;. The output begins 2010-01-04, 2010-01-05, 2010-01-06, 2010-01-07, 2010-01-08. Answer: oldest trading day is 2010-01-04. Sense-check: consecutive early-January dates with weekend gaps missing is exactly what a trading calendar looks like.

Example 42.1.3 — Retrieving the first 10 records. Adding LIMIT 10 to the ascending query returns exactly 10 rows from January 2010. Answer: 10 rows, the earliest trading days. Sense-check: LIMIT 10 on 2,682 sorted rows must return rows 1–10, which matches the formula with \(p = 1\), \(k = 10\).

Example 42.1.4 — Retrieving the last 10 records. We run the filter with ORDER BY price_date DESC LIMIT 10;. Answer: 10 rows ending on 2020-08-28, the newest date. Sense-check: the next example confirms this date independently.

Example 42.1.5 — Validating latest dates without LIMIT. We comment out LIMIT 10 and rerun the descending query over all 2,682 rows. The first row still shows 2020-08-28. Answer: 2020-08-28 confirmed as the table maximum. Sense-check: the limited and unlimited queries agree on the top row, so the limit trimmed nothing it should have kept.

Example 42.1.6 — Descending pagination with OFFSET 10. We run ... ORDER BY price_date DESC LIMIT 10 OFFSET 10;. The 10 newest rows (through 2020-08-17) are skipped; results start at 2020-08-14, 2020-08-13, and earlier. Answer: rows 11–20 newest-first. Sense-check: \(O + 1 = 11\) through \(O + L = 20\) — a full page of 10.

Example 42.1.7 — Ascending pagination with OFFSET 10. We run ... ORDER BY price_date ASC LIMIT 10 OFFSET 10;. The first 10 January days are skipped; results start at 2010-01-19. Answer: rows 11–20 oldest-first. Sense-check: about two trading weeks skipped lands mid-January, which is where 2010-01-19 falls.

42.1.6 Student Questions and Answers

Q: How can we verify that LIMIT 10 with ORDER BY price_date DESC returns true table extremes rather than arbitrary rows?

A: Remove or comment out the LIMIT clause and look at the very first row of the full descending result. It shows 2020-08-28 — exactly the top row of the limited query — proving the limit kept genuine extremes. The trick generalizes: whenever a LIMIT result looks suspicious, rerun without it and compare the boundary rows.

Q: What happens if we specify OFFSET without an ORDER BY clause?

A: The database treats the table as an unordered multiset, so it may return rows in whatever physical order is cheapest — and that order can change between executions. Two page requests can then skip different rows, showing some rows twice and others never. This is the single most expensive pagination bug: always pair OFFSET with ORDER BY.

42.1.7 Industry Applications

Trading consoles and market-data dashboards page through enormous tick feeds with LIMIT and OFFSET, serving history in chunks of 50 or 100 rows so mobile clients stay within memory and bandwidth budgets. The same pair backs almost every web API with paged results — page 3 of size 25 is just LIMIT 25 OFFSET 50.

Picture a brokerage app's price-history screen: each downward scroll fires the next LIMIT/OFFSET page, and the chart stitches the pages together. If the developers forgot ORDER BY, the chart would shuffle on every scroll — the exact failure the Q&A above warns about.

42.1.8 Exam Notes

Exam note: In any query-writing question that asks for extremes or pages, always write both ORDER BY and LIMIT (plus OFFSET for pages). LIMIT without ORDER BY on an unordered table is non-deterministic and loses marks. State the sort direction explicitly — ASC for earliest, DESC for latest.

42.1.9 Cross-Database Row-Limiting Variants

Every database limits rows, but the keywords differ — and examiners love testing whether you know your dialect. PostgreSQL and MySQL share the LIMIT/OFFSET form used in this lecture; the rest of the family says the same thing differently.

Database First 10 newest rows Second page of 10
PostgreSQL, MySQL ... ORDER BY price_date DESC LIMIT 10 ... LIMIT 10 OFFSET 10
Snowflake ... ORDER BY price_date DESC LIMIT 10 (also accepts TOP 10) ... LIMIT 10 OFFSET 10
Databricks (Spark SQL) ... ORDER BY price_date DESC LIMIT 10 ... LIMIT 10 OFFSET 10
SQL Server SELECT TOP 10 ... ORDER BY price_date DESC ... ORDER BY price_date OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY
Oracle, DB2 ... ORDER BY price_date DESC FETCH FIRST 10 ROWS ONLY ... ORDER BY price_date OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY

Two extras worth knowing. First, the standard-SQL OFFSET n ROWS FETCH NEXT k ROWS ONLY form also works in PostgreSQL, so FETCH FIRST 10 ROWS ONLY is a portable spelling of LIMIT 10. Second, SQL Server's TOP cannot skip — there is no TOP ... OFFSET — so pages there must use the OFFSET/FETCH form. Oracle's older ROWNUM trick (WHERE rownum <= 10) applies before sorting and so returns the wrong 10 rows unless wrapped in a subquery; prefer FETCH FIRST.

Recap: ORDER BY fixes the sequence, DESC puts the newest first, LIMIT trims to a page, and OFFSET skips to the page you want, with page \(p\) of size \(k\) starting at row \((p-1)\cdot k + 1\). With row edges mastered, the next section answers the harder question: the first and last date for every stock at once.

42.2 Finding First and Last Records per Group

42.2.1 Group Aggregation Concepts

Querying one stock at a time works for a single ticker, but a portfolio holds hundreds. How do you get the trading lifespan — first and last date — of every company with one query instead of hundreds?

The answer is grouping. Formulating the requirement: identify the first and last price dates for every symbol — that is, determine the active trading span of every company in the table — the question an analyst asks before any per-stock deep dive. An aggregate function (a function that collapses many rows into one summary value, such as MIN() or MAX()) works together with a grouping clause, written GROUP BY symbol_id, which partitions the table into one bucket per distinct value before aggregating. Applied to dates, MIN(price_date) yields the earliest calendar date in a bucket and MAX(price_date) the latest.

SELECT symbol_id, MIN(price_date) AS first_date
FROM stock_prices
GROUP BY symbol_id;

Step by step: the engine partitions all rows by symbol_id — one bucket per company — then evaluates MIN(price_date) inside each bucket, and finally emits one summary row per symbol with its earliest date. The bucket picture is a mailroom sorting letters into pigeonholes by recipient before weighing each hole's bundle: partition first, summarize second. The picture breaks if you forget the partition — then every letter lands in one bin and you get a single table-wide minimum.

42.2.2 Mathematical Formulation of Group Extrema

Let \(R\) denote the stock_prices relation. Each tuple \(r \in R\) carries an entity attribute \(r.\text{symbol\_id}\) and a temporal attribute \(r.\text{price\_date}\). Let \(S = \{ r.\text{symbol\_id} \mid r \in R \}\) be the set of distinct symbol identifiers. For any symbol \(s \in S\), the group partition is:

\[ G_s = \{ r \in R \mid r.\text{symbol\_id} = s \} \]

The earliest and latest price dates for symbol \(s\) are:

\[ t_{\min}(s) = \min_{r \in G_s} (r.\text{price\_date}) \]

\[ t_{\max}(s) = \max_{r \in G_s} (r.\text{price\_date}) \]

where \(t_{\min}(s)\) is the first trading date and \(t_{\max}(s)\) the last. Two properties fall out immediately. First, the partitions are disjoint and cover the table: every row belongs to exactly one \(G_s\), so no row is double-counted and none is missed. Second, a plain MIN(price_date) with no GROUP BY is the degenerate case of a single bucket \(G = R\) — one row out, the table-wide extreme.

Scope: MIN and MAX ignore NULL values. If a symbol's dates contain NULLs, they are silently excluded, and a symbol with only NULL dates yields a NULL extreme rather than an error. If missing dates must be reported rather than skipped, filter or coalesce them explicitly.

42.2.3 Worked Examples and Result Verification

Example 42.2.1 — Inspecting table structure with LIMIT. We run SELECT * FROM stock_prices LIMIT 10;. The output confirms columns price_id, symbol_id, price_date, open, high, low, close, and friends. Answer: schema confirmed, sample of 10 rows. Sense-check: LIMIT without ORDER BY is fine here because we want any 10 rows, not extremes.

Example 42.2.2 — Finding earliest price date per symbol using MIN. We run SELECT symbol_id, MIN(price_date) FROM stock_prices GROUP BY symbol_id;. The result shows symbol 11 starting on 2010-01-04 and symbol 8 on 2014-03-27. Answer: per-symbol first dates, e.g. 11 → 2010-01-04, 8 → 2014-03-27. Sense-check: symbol 8 listing years later is plausible — a later IPO or index inclusion — and the next example verifies both dates independently.

Example 42.2.3 — Verifying earliest dates with single-symbol queries. Verifying minimum date accuracy with filtered single-symbol queries: we run SELECT * FROM stock_prices WHERE symbol_id = 11 ORDER BY price_date ASC; — first row 2010-01-04. Repeating for symbol_id = 8 gives 2014-03-27. Answer: both match the aggregate output exactly. Sense-check: spot-checking an aggregate against a filtered single-group query is the standard verification pattern of this lecture.

Example 42.2.4 — Finding latest price date per symbol using MAX. Swapping in MAX with an alias:

SELECT symbol_id, MAX(price_date) AS price_date
FROM stock_prices
GROUP BY symbol_id;

Both symbols 11 and 8 report 2020-08-28. Answer: last date 2020-08-28 for both symbols. Sense-check: a shared latest date means both stocks were still trading when the dataset snapshot was taken.

Example 42.2.5 — Verifying latest dates with descending single-symbol queries. We run SELECT * FROM stock_prices WHERE symbol_id = 11 ORDER BY price_date DESC; — top row 2020-08-28; same for symbol 8. Answer: aggregate maxima confirmed. Sense-check: ascending checks verify minima, descending checks verify maxima — always match the sort direction to the extreme.

The alias in Example 42.2.4 deserves a note: MAX(price_date) AS price_date renames the output column only. Aliases are cosmetic labels on the result; they change nothing about how grouping or aggregation works.

42.2.4 Student Questions and Answers

Q: Why do we need GROUP BY symbol_id when calling MIN(price_date) or MAX(price_date)?

A: Without GROUP BY, the aggregate sees one giant bucket — the whole table — and returns a single overall date. Grouping partitions the rows by company symbol first, producing the minimum and maximum date separately for each individual company: MIN/MAX is evaluated inside each company's bucket, giving one extreme per company. One bucket means one answer; \(n\) buckets mean \(n\) answers.

Q: Can we use column aliases in the GROUP BY clause or in later queries?

A: Standard SQL evaluates clauses in the order FROM → WHERE → GROUP BY → SELECT, so when grouping happens, SELECT aliases such as AS price_date do not exist yet — grouping must name base columns like symbol_id. (MySQL and a few dialects bend this rule and accept aliases in GROUP BY, but portable queries use the original column names.) Aliases are safe to use one step later, in ORDER BY, which runs after SELECT.

A comparison the lecture implies but never states outright: filtering one symbol with WHERE plus ORDER BY/LIMIT (Section 42.1) answers "the edges of this stock"; GROUP BY with MIN/MAX answers "the edges of every stock." Use the first when you need full rows (prices, volumes) at the boundary; use the second when you need one summary row per group. When you need full rows per group — the entire earliest record, not just its date — neither suffices, and the right tools are window functions (ROW_NUMBER() OVER (PARTITION BY symbol_id ORDER BY price_date)) or a lateral join, which later lectures cover.

42.2.5 Industry Applications

Market-data pipelines run MIN(price_date) / MAX(price_date) grouped by ticker to reconstruct each asset's active lifespan: the minimum reveals IPO or index-inclusion dates, the maximum reveals the latest coverage or a delisting. Risk teams join these spans against corporate-action calendars — a symbol whose maximum date suddenly stops advancing is a delisting candidate worth investigating.

42.2.6 Exam Notes

Exam note: Every non-aggregated column in the SELECT list (here symbol_id) must appear in the GROUP BY clause. Omitting it is a syntax error in standard SQL and PostgreSQL. Conversely, never put an aggregate like MIN(price_date) inside GROUP BY — aggregates belong in SELECT (or HAVING), grouping keys belong in GROUP BY.

Recap: GROUP BY partitions rows into per-symbol buckets and MIN/MAX summarize each bucket into one row, with the partitions disjoint and exhaustive. Next, the lecture switches gears from rows to arithmetic: computing cube roots inside PostgreSQL itself.

42.3 Calculating Cube Roots in PostgreSQL

42.3.1 The PostgreSQL CBRT Function

Stock prices span orders of magnitude — a penny stock at 2 and a blue chip at 2,000 — and that spread can destabilize statistical models. What if you could compress the scale with a single function call inside the query, no export to Python needed?

PostgreSQL ships a built-in cube-root function, written cbrt(numeric), that evaluates the cube root of its argument directly in SQL. Introducing it with the lecture's own framing: mathematical cube root computations that analysts use for nonlinear numeric transformations without leaving the database. On a constant:

SELECT cbrt(4) AS cube_root;

PostgreSQL returns about 1.5874010519681994. On a column, the function maps over every row:

SELECT close, cbrt(close) AS cube_root
FROM stock_prices
WHERE symbol_id = 1
ORDER BY price_date DESC;

Each closing price appears alongside its cube root, newest day first. Testing on a scalar literal before applying a function to a whole column — exactly the lecture's order — is deliberate: a one-row check catches type errors and surprises before they multiply across 2,682 rows.

42.3.2 Mathematical Formulation of Cube Root

Let \(x \in \mathbb{R}\) be a real numeric input. The cube root \(y \in \mathbb{R}\) is the unique real number satisfying:

\[ y = \operatorname{cbrt}(x) = \sqrt[3]{x} = x^{\frac{1}{3}} \]

such that:

\[ y^3 = y \cdot y \cdot y = x \]

where \(x\) is the input value and \(y\) is its cube root. The function maps all reals to all reals:

\[ \operatorname{cbrt}: \mathbb{R} \to \mathbb{R} \]

Uniqueness is what separates it from the square root: every real \(x\) has exactly one real cube root, while negative numbers have no real square root. Sign is preserved — if \(x > 0\) then \(y > 0\); if \(x < 0\) then \(y < 0\), because cubing a negative stays negative, e.g. \((-2)^3 = -8\). Zero maps to zero.

Evaluating the lecture's numbers: for \(x = 4\),

\[ \operatorname{cbrt}(4) = 4^{\frac{1}{3}} \approx 1.5874 \]

since \((1.5874)^3 \approx 3.9999 \approx 4\). For the closing price \(x = 13.59\),

\[ \operatorname{cbrt}(13.59) = (13.59)^{\frac{1}{3}} \approx 2.3860 \]

since \((2.3860)^3 \approx 13.589 \approx 13.59\). The full sixteen-digit output 1.5874010519681994 is double-precision display, not extra accuracy in the market data — prices quoted to cents deserve at most four significant figures in the root.

Scope: cbrt accepts any numeric type — integers, numeric, double precision — and returns double precision. Extremely large inputs (near \(10^{308}\)) can overflow when cubed back for verification, and NULL in means NULL out, so wrap nullable columns in COALESCE if a downstream model cannot tolerate missing values.

42.3.3 Worked Examples on Scalars and Table Columns

Example 42.3.1 — Cube root of scalar literal 4. We run SELECT cbrt(4) AS cube_root;. PostgreSQL evaluates the constant expression and returns 1.5874010519681994. Answer: ≈ 1.5874. Sense-check: \(1.5^3 = 3.375\) and \(1.6^3 = 4.096\), so the answer must lie between 1.5 and 1.6 — and it does.

Example 42.3.2 — Computing cube root on the close column. We run the SELECT close, cbrt(close) query filtered to symbol_id = 1 in descending date order. Every row carries its original price plus the transformed value. Answer: 2,682 transformed rows, newest first. Sense-check: the row holding close = 13.59 shows 2.386, which the next example reproduces from the literal alone.

Example 42.3.3 — Manual scalar verification of the table calculation. Verifying the column calculation against the scalar literal value 13.59 confirms the accuracy of the column transformation: we run SELECT cbrt(13.59) AS cube_root; and get 2.386, matching the table query's output for that price. Answer: column computation verified. Sense-check: \((2.386)^3 \approx 13.59\) closes the loop — literal, column, and hand arithmetic all agree.

42.3.4 Student Questions and Answers

Q: Why would a financial analyst compute the cube root of a stock price using cbrt(close)?

A: Price data is heavy-tailed: a few spikes dominate the variance, and variance grows with price level. A cube-root power transformation (a nonlinear rescaling \(x \mapsto x^{1/3}\) that compresses large values more than small ones) pulls extreme spikes inward and stabilizes variance for downstream models. Unlike the logarithm, the cube root stays defined at zero and on negative returns, so no rows are lost or need patching.

Q: How does cbrt(x) differ from using the power operator x ^ (1.0 / 3.0) in PostgreSQL?

A: For positive inputs both agree, but cbrt is a dedicated C library routine that handles negatives correctly — cbrt(-8) returns -2, while (-8) ^ (1.0/3.0) returns NULL (or an error, depending on the function variant) because fractional powers of negatives leave the reals. cbrt is also faster and clearer in intent: one function call says "cube root" where the power form makes the reader verify the exponent.

42.3.5 Industry Applications

Quantitative desks apply root transforms like cbrt during feature engineering: compressing prices into tighter ranges tames positive skew, stabilizes gradients, and speeds neural-network convergence on trading models. Doing it in SQL keeps the transform inside the data warehouse — versioned, auditable, and applied identically in training and serving — rather than buried in a notebook.

42.3.6 Exam Notes

Exam note: Expect cbrt(x) tested alongside arithmetic operators in SELECT expressions, on both literals and columns. Know that it accepts integer, numeric, and double-precision inputs, returns double precision, and — unlike sqrt — accepts negative inputs.

42.3.7 Cross-Database Cube-Root and Power Variants

PostgreSQL is generous here: it offers both the cbrt() function and the ||/ cube-root operator, so SELECT ||/ 10; and SELECT cbrt(10); compute the same value (likewise |/ 10 and sqrt(10) for square roots). When only one dialect's syntax is allowed, prefer cbrt() — it reads clearly everywhere the function exists.

Database Cube root of close Notes
PostgreSQL cbrt(close) or ||/ close cbrt handles negatives; ^ (1.0/3.0) does not
MySQL CBRT(close) (v8+) or POWER(close, 1.0/3.0) Older MySQL has no CBRT() — use POWER; negatives return NULL
Snowflake CBRT(close) Also supports POW(close, 1.0/3); negatives return NULL via POW but CBRT handles them
Databricks (Spark SQL) CBRT(close) Same CBRT spelling; POWER/POW as fallback
SQL Server POWER(close, 1.0/3.0) No CBRT() — POWER on negatives errors, so guard with SIGN/CASE
Oracle CBRT(close) or POWER(close, 1.0/3) Both spellings available

The portable-but-careful pattern is POWER(x, 1.0/3.0), which runs almost everywhere but fails or goes NULL on negative inputs in most dialects. Where the data can be negative — returns, spreads, differences — reach for the native CBRT() first and test on your platform's literal (SELECT CBRT(-8)) before trusting a whole-column transform.

Recap: cbrt is PostgreSQL's one-call cube root — defined on all reals, sign-preserving, and verified literal-first before column-wide use, with a native CBRT() twin in most other databases and POWER(x, 1/3) as the portable fallback. That closes the lecture's three arcs: paging rows, summarizing groups, and transforming values in place.

Exam Guidance Summary

  • Pagination and row selection: Always combine LIMIT and OFFSET with an explicit ORDER BY clause — ASC for earliest rows, DESC for latest. Writing LIMIT without ORDER BY produces non-deterministic results on unordered tables and loses marks. For tied sort keys add a tiebreaker column such as price_id.
  • Group aggregations: When writing GROUP BY queries, every column in the SELECT list that is not wrapped in an aggregate function (such as MIN or MAX) must be listed in the GROUP BY clause. Group on base column names, since standard SQL evaluates GROUP BY before SELECT aliases exist.
  • Verification techniques: Confirm boundary conditions by running isolated single-entity queries or by removing LIMIT to check that extrema match expected dates. Test math functions on scalar literals (e.g. SELECT cbrt(4)) before applying them to whole columns.
  • PostgreSQL math functions: PostgreSQL provides built-in mathematical functions like cbrt(numeric) usable on numeric literals or column expressions directly in SELECT queries. cbrt accepts negative inputs, unlike sqrt or fractional POWER, and the ||/ operator is an equivalent PostgreSQL spelling.

Key Industry Applications

  • Trading systems and web pagination: Trading dashboards paginate massive market tick feeds using LIMIT and OFFSET to deliver responsive user experiences, serving history in chunks that fit mobile memory and bandwidth budgets. The OFFSET n ROWS FETCH NEXT k ROWS ONLY spelling carries the same pattern to Oracle, DB2, and SQL Server.
  • Asset lifecycle analytics: Quantitative analysts compute MIN(price_date) and MAX(price_date) grouped by ticker symbol to trace corporate listing lifespans and historical coverage windows — IPO dates from the minima, delisting signals from maxima that stop advancing.
  • Feature engineering in quantitative trading: Quantitative engineers apply cbrt transformations to stabilize variance and normalize heavy-tailed asset price distributions for algorithmic trading models, keeping the transform inside the warehouse so training and serving agree. Most platforms spell it CBRT(); elsewhere POWER(x, 1.0/3.0) is the fallback for non-negative data.

\[ y = \operatorname{cbrt}(x) = x^{\frac{1}{3}}, \quad y^3 = x \]

⚠️ Top pitfall: Fractional POWER fails on negatives; use native cbrt/CBRT for negative inputs.

Self-check: What is cbrt(-8)? -2, since (-2)^3 = -8.

Exam Guidance Summary

Must-know: Always pair LIMIT/OFFSET with ORDER BY; GROUP BY must list bare SELECT columns.

⚠️ Top pitfall: LIMIT without ORDER BY is non-deterministic.

Self-check: Why pair LIMIT with ORDER BY? Tables are unordered sets.
