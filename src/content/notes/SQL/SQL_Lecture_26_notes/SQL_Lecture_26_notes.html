# Grouping Sets

This lecture shows how to get detail rows, subtotals, and a grand total from one query. It uses two small tables, courses and inventory, plus three tools: ROLLUP, GROUPING, and CASE with COALESCE for clean labels.

26.1 Introduction to Summarization and Grouping Sets

26.1.1 What Summarization Means

A summary answers a big question in a few rows. It hides row-level detail and keeps only the story, such as a total, an average, or a count per group.

A summarization, meaning a high level overview that replaces many detail rows with a few result rows, is the goal when thousands of input rows must turn into a small set of story-telling numbers. Aggregation removes the detail that lies below the summary. It groups rows into a total, an average, a minimum, a maximum, or a count. The point is a bird's eye view. A reader of a summary does not check each row beneath it. The reader wants the extracted story.

A subtotal, meaning a total for one group plus a grand total across all groups in the same result, is one common form of summarization for numeric data. An inventory case makes this concrete. Given products with categories and subcategories, a subtotal answers how many units sit in each category and how many sit in total. Subtotals deal with numeric measures such as units sold, quantity on hand, or sales value, broken down by a grouping column.

So summarization means less data, but with a point of view that pulls the story out of the data. Subtotals plus grand totals are that story in this lecture.

Picture a sales table with 10,000 order lines. No one reads all 10,000 lines. A manager asks three things. How much did we sell. How much per region. How much per store in each region. That is detail plus subtotal plus grand total in one view. That view is what this lecture builds.

Inventory reporting by product category and subcategory is one live use. Course sales reporting by course level is a second use. Sales summaries by region and store form a third use.

Exam note: Be ready to define summarization and subtotal in plain words. Summarization swaps many detail rows for a few story rows. A subtotal is a per-group total shown next to the grand total.

26.1.2 GROUP BY and the Idea of a Grouping Set

GROUP BY, meaning the SQL clause that puts rows with the same column values into one group so an aggregate such as SUM, MIN, or MAX can run per group, produces one grouping level at a time. A grouping set, meaning one set of columns used for grouping, can appear next to other grouping sets in the same result when ROLLUP or GROUPING SETS is used.

In plain words, GROUP BY works in two steps. First it groups the data together by shared column values. Then it applies aggregate functions like sum and minimum and maximum based on a column, and produces data in terms of groups.

The math form for a grouped sum is:

\[ \text{grouped\_total}(g) = \sum_{i \in g} x_i \]

Here \(g\) is one group value such as one course level, \(x_i\) is the numeric measure for row \(i\) in that group, and the sum runs over all rows \(i\) in \(g\). For example, if \(g\) is basic and its rows hold 200 units, then the grouped total is 200.

A grouping set goes one step further. Within a single result set, data can be split into grouping sets. One set might be empty, written as \(()\), meaning grand total. One set might be a single column, such as category, meaning per-category total. One set might be two columns, such as category plus subcategory, meaning per-category plus per-item detail. Summarization needs grouping sets because a plain GROUP BY gives only one grouping level at a time.

Think of sorting laundry. Plain GROUP BY puts socks in one pile and shirts in another pile and stops. Grouping sets give at the same time the pile counts, the drawer counts, and the whole-closet count, all laid out in one view. The pile is the detail. The drawer is the subtotal. The closet is the grand total.

Where the laundry picture breaks: clothes sit in only one pile, but a SQL row can feed many grouping sets at once. One sale counts toward its item detail, its category subtotal, and the grand total. That reuse is why one ROLLUP query can replace three separate GROUP BY queries.

Assumptions matter here. GROUP BY expects clean group keys. NULL keys group together. Mixed text case splits groups unless normalized. Numeric measures should be non-null or wrapped so nulls do not poison sums. If these fail, totals look wrong even though the syntax is right.

Scope: GROUP BY plus SUM fits additive measures such as units sold, quantity, or sales value. It does not fit medians or distinct counts in the same simple way. Subtotals of ratios need care, since the ratio of sums is not the sum of ratios.

A chart helps. Picture bars for each category. The x-axis lists categories such as furniture and equipment. The y-axis shows summed quantity. Detail bars show each subcategory. A wider bar behind them shows the category subtotal. One full-width bar shows the grand total. Takeaway: detail bars add up to their subtotal bar, and subtotal bars add up to the grand total bar.

26.1.3 ROLLUP as a Shorthand for Multiple Grouping Sets

ROLLUP, meaning a subclass of the GROUP BY clause that defines several grouping sets in one short expression, is a shorthand for a fixed hierarchy of subtotals. It rolls from right to left, so column order controls which subtotals appear.

In plain words, ROLLUP is a powerful function, a subclass of group by clause, that offers a shorthand of defining multiple group sets. The pattern for two columns \(a\) and \(b\) is:

\[ \text{ROLLUP}(a, b) \equiv \text{GROUP BY } (a,b) \cup \text{GROUP BY } (a) \cup \text{GROUP BY } () \]

Here \(a\) is the first grouping column such as course level or category, \(b\) is the second grouping column such as course name or subcategory, \((a,b)\) keeps detail rows, \((a)\) adds per-\(a\) subtotals, and \(()\) adds the grand total row. With \(n\) columns in ROLLUP there are \(n + 1\) levels.

A concrete rule follows. ROLLUP(category, subcategory) gives detail by category plus subcategory, then subtotal by category, then grand total. Swap the order to ROLLUP(subcategory, category) and the middle level changes to subtotal by subcategory. Order matters.

The promise used through the rest of the material is that ROLLUP computes subtotals and grand totals together with detail rows in one query.

Dialect notes help here since syntax differs by system but logic stays the same. PostgreSQL, Oracle, Snowflake, Databricks, and Postgres-based systems use GROUP BY ROLLUP(a, b). Oracle also accepts the same form. MySQL and older SQL Server code use GROUP BY a, b WITH ROLLUP. Newer SQL Server also accepts GROUP BY ROLLUP(a, b). For one-column rollups, COALESCE(job, 'TOTAL') can label the total row in MySQL and PostgreSQL, while CASE WHEN GROUPING(job) = 1 works across Oracle, DB2, SQL Server, PostgreSQL, and Snowflake. Keep one version for shared logic, and note the alternate spelling when moving code between systems.

Two close cousins deserve one line each. CUBE builds all combos, not just the hierarchy, so CUBE(a, b) gives \((a,b)\), \((a)\), \((b)\), and \(()\). GROUPING SETS lists exactly the sets wanted, such as GROUPING SETS ((a,b), (a), ()) to mimic ROLLUP, or GROUPING SETS ((a), (b)) for a non-hierarchical pick. ROLLUP is the best pick for ordered hierarchies like category to subcategory or level to course.

Worked sketch: take sales by region \(a\) and store \(b\) with two regions. Plain GROUP BY gives either per-store detail or per-region totals. ROLLUP(a, b) gives all three at once: per-store detail rows, one subtotal row per region, and one grand total row. With 2 regions this adds 2 subtotal rows plus 1 grand total row. Sense-check: region subtotals add to the grand total, and store details add to their region subtotal.

Assumption: ROLLUP assumes a hierarchy where the left column contains the right column in a report sense. Category contains subcategory. Course level contains course name. If columns are unrelated, such as city and job title, ROLLUP still runs but the middle subtotal may confuse readers. Then GROUPING SETS or CUBE often fits better.

Visualize the hierarchy as a tree. The root is the grand total. Branches are categories. Leaves are subcategories or items. ROLLUP walks this tree and emits a sum at each level: leaf sums, branch sums, root sum. One-sentence takeaway: ROLLUP reads the tree top to bottom and prints totals bottom to top.

Common traps: adding ROLLUP but forgetting that NULL now has two meanings, real missing value versus computed subtotal; listing columns in the wrong order and getting subtotals on the wrong level; expecting ROLLUP to sort output by itself, when sort needs an explicit ORDER BY.

Recap: GROUP BY gives one level. Grouping sets give many levels in one result. ROLLUP is the short way to ask for a hierarchy of sets. Bridge: next the courses table turns this idea into real numbers, with basic 200, premium 450, and grand total 650 as anchors.

Real use: retail chains roll store to city to region to national total in one nightly job. Schools roll course to level to full catalog. Warehouses roll product to subcategory to category to full stock. One query feeds a dashboard section plus its subtotal line plus its grand total line.

26.1.4 Student Questions and Answers

Q: If GROUP BY already aggregates, why do we need grouping sets? Several students asked this in different words.

A: GROUP BY gives one level at a time, either detail per item or total per category. Grouping sets give several levels in one result, meaning detail rows, per-category subtotals, and the grand total together. That combined view is what a summary report needs. Without it you would run three queries and glue them with UNION ALL.

A follow-up doubt often sounds like: can UNION ALL replace ROLLUP. It can, and that is in fact how MySQL users worked around missing GROUPING SETS in older versions. But UNION ALL needs three full scans and manual NULL padding, while ROLLUP scans once and builds all levels together. So pick ROLLUP for hierarchies, GROUPING SETS for custom picks, and UNION ALL only when the system lacks both.

26.2 Subtotals on Grouping Sets with Courses Table

26.2.1 Building the Courses Test Table

The courses table, meaning a small test table with course identifier, course name, course level, and units sold, holds the detail that later queries summarize. Detail data means every row stays visible before any aggregate runs.

The definition used is:

CREATE TABLE courses (
  course_id   INTEGER PRIMARY KEY,
  course_name VARCHAR(100),
  course_level VARCHAR(100),
  sold        INTEGER
);

Here \(\text{course\_id}\) is the integer primary key, \(\text{course\_name}\) is the course title text, \(\text{course\_level}\) is the category label such as basic or premium, and \(\text{sold}\) is the integer count of units sold.

Sample rows for the walkthrough include a premium course on machine learning with Python with 100 units sold, a basic course on introductory Python with 200 units sold, and extra premium rows with values such as 100 and 250. Exact inserted titles beyond those two include short sample names, but the numeric story stays fixed. The anchor math only needs the per-level sums shown below.

The ordered detail view used for teaching lists level first, then name, then units:

SELECT course_level, course_name, sold
FROM courses
ORDER BY course_level, course_name;

This shows basic rows together and premium rows together. This complete row list is called detail data. Every single row is visible. A business need then arises: how many total courses per each course level were sold. That question moves the work from listing to grouping.

Think of a shop shelf. Detail is every single pack on the shelf. Summary is the shelf label that says basic shelf holds 200 packs and premium shelf holds 450 packs. Same stock, less reading.

Scope: This test table is tiny on purpose. Four columns and a handful of rows let you check each total by hand. In a real sales table with millions of rows you would add indexes on grouping columns and test on a sample first, but the grouping logic stays the same.

26.2.2 Total per Course Level with SUM and GROUP BY

The hook here is a repeated label problem. Group by two columns and the word premium repeats on many rows. How do you get one clean row per level.

The per-level total is an aggregate of the form:

\[ \text{total\_sold}(level) = \sum_{i: level_i = level} \text{sold}_i \]

Here \(\text{sold}_i\) is the units sold for row \(i\) and \(level\) is one fixed course level value. In words, this is the total units sold for each course level using sum of sold units grouped by course level and course name, then later grouped by level alone.

The first attempt groups by both columns:

SELECT course_level, course_name, SUM(sold) AS "total sold"
FROM courses
GROUP BY course_level, course_name;

This returns one row per distinct level plus name pair, for example premium plus one title gives 100, basic plus one title gives 200, premium plus another title gives 100, premium plus another title gives 250. The level labels repeat. Premium appears on several rows. Basic appears on its own rows. This is still detail-heavy. It answers per-course totals, not per-level totals.

Removing course name gives the compact per-level total:

SELECT course_level, SUM(sold) AS "total sold"
FROM courses
GROUP BY course_level;

The result is basic with total 200 and premium with total 450. The arithmetic is:

\[ \text{total\_basic} = 200 \]

\[ \text{total\_premium} = 100 + 100 + 250 = 450 \]

\[ \text{grand\_total} = 200 + 450 = 650 \]

Check the last line by addition: 200 plus 450 equals 650. These three numbers, 200, 450, and 650, anchor every later ROLLUP result and are worth noting down before moving on. If any later query shows a different premium total or a different grand total, the grouping or the data changed.

Worked mini-case: start from detail rows 100, 200, 100, 250. Group by level. Basic bucket gets only 200, so basic total is 200. Premium bucket gets 100 plus 100 plus 250, which is 450. Add both buckets for 650. Sense-check: 650 equals the sum of all four detail values, so no sale was lost or double counted.

Dialect note: this plain GROUP BY runs the same on PostgreSQL, MySQL, Snowflake, Databricks, Oracle, and SQL Server. Aliases with a space need double quotes in PostgreSQL and Oracle, backticks or single handling in MySQL, and brackets or quotes in SQL Server. The lecture uses "total sold" with double quotes, which suits PostgreSQL.

Common traps: keeping course name in SELECT while grouping only by level, which fails on strict systems; grouping by level plus name and mistaking per-course rows for per-level totals; forgetting that SUM ignores NULL, so a NULL sold value silently drops out instead of acting as zero.

26.2.3 Full ROLLUP for Detail Plus Subtotals Plus Grand Total

Full ROLLUP on both columns, meaning GROUP BY ROLLUP with course level then course name inside, returns detail rows plus one subtotal row per level plus one grand total row in a single pass.

The query is:

SELECT course_level, course_name, SUM(sold) AS "total sold"
FROM courses
GROUP BY ROLLUP(course_level, course_name);

In words, put course level and course name both inside rollup so data is parsed into group sets for course level and course name together. The grouping-set expansion is:

\[ \text{ROLLUP}(\text{course\_level}, \text{course\_name}) \equiv \{(\text{course\_level}, \text{course\_name}), (\text{course\_level}), ()\} \]

The three sets map to three row types. Set \((\text{course\_level}, \text{course\_name})\) keeps detail rows such as premium plus Python ML with 100. Set \((\text{course\_level})\) adds per-level subtotals, namely basic 200 and premium 450. Set \(()\) adds the grand total 650.

The result adds three extra rows to the detail. One row has both grouping columns empty and shows the grand total 650. One row has course name empty and course level basic and shows 200. One row has course name empty and course level premium and shows 450. In words, one grand total row plus one subtotal row per course level. If a third level such as advanced existed, there would be one more subtotal row for advanced plus the same single grand total. So with \(k\) distinct levels, full ROLLUP adds \(k\) subtotal rows plus 1 grand total row.

Sort behavior needs care. When ORDER BY is omitted, the grand total can appear first, followed by the per-level rows, since the system returns grouping sets in its own processing order. When ORDER BY course level and course name is added, the output reads in a more natural report order: basic detail rows, then basic subtotal, then premium detail rows, then premium subtotal, then the final grand total row. NULL keys sort last in PostgreSQL by default, which pushes the grand total to the end under ORDER BY.

Worked trace on the anchor data: detail rows give 100, 200, 100, 250. Full ROLLUP emits those four detail rows, then basic subtotal 200, then premium subtotal 450, then grand total 650. Count the added rows: 2 subtotals plus 1 grand total equals 3 extra rows. Sense-check: 200 plus 450 equals 650, so subtotals reconcile to the grand total.

Picture the output as a receipt. Item lines are detail. A bold line after each level is the subtotal. The last bold line is the grand total. Takeaway: one query prints the whole receipt, not just the item lines.

Dialect extras: PostgreSQL and Oracle use GROUP BY ROLLUP(course_level, course_name). Snowflake and Databricks accept the same spelling. SQL Server accepts both GROUP BY ROLLUP(course_level, course_name) and the older GROUP BY course_level, course_name WITH ROLLUP. MySQL uses GROUP BY course_level, course_name WITH ROLLUP. Same rows come back, only the keywords move.

Assumption: Full ROLLUP assumes you want every hierarchy level. If you only want subtotals without detail, or only one level, full ROLLUP returns more rows than needed. Then a narrower grouping with fewer sets trims the output.

26.2.4 Partial ROLLUP with GROUP BY Plus ROLLUP

A partial rollup, meaning a GROUP BY on one column plus a ROLLUP on the remaining column, keeps one column fully grouped while rolling up only the second. It is the tool for per-level blocks without a separate grand total set.

The query is:

SELECT course_level, course_name, SUM(sold) AS "total sold"
FROM courses
GROUP BY course_level, ROLLUP(course_name)
ORDER BY course_level, course_name;

In words, keep course level in group by and put course name inside rollup. The grouping-set expansion is:

\[ \text{GROUP BY } (\text{course\_level}), \text{ROLLUP}(\text{course\_name}) \equiv \{(\text{course\_level}, \text{course\_name}), (\text{course\_level})\} \]

There is no empty \(()\) set here, so this form gives per-level subtotals plus detail rows but organizes them per level without a separate grand total row in the same sense as the full rollup. With ORDER BY, the report reads as single basic item with 200, then a basic subtotal row, then all premium items listed, then a premium total of 450, then a final total line produced by the ordering. The teaching point is that moving a column into or out of ROLLUP changes which subtotal rows appear.

A useful contrast pair captures the lesson: small grouping change, big report change. Full ROLLUP with two columns gives detail plus per-level subtotals plus grand total. Partial grouping with one fixed column plus ROLLUP on the second gives detail plus per-level subtotals organized level by level.

Form Grouping sets Extra rows Best use
Full ROLLUP(level, name) Detail, per-level, grand total \(k\) subtotals plus 1 grand total One-shot report with final total
Partial level, ROLLUP(name) Detail, per-level \(k\) subtotals, no separate grand set Level-by-level blocks, grand handled in app or second pass

When to pick which: pick full ROLLUP when the page needs its own grand total line. Pick partial when each level is processed on its own, such as paging by level or feeding per-level cards in a dashboard.

Common traps: reading the last partial subtotal as the grand total when basic has only one row; forgetting ORDER BY so level blocks interleave; adding a third column outside ROLLUP and then wondering why no grand total appears, when the answer is the missing \(()\) set.

Recap: anchors are basic 200, premium 450, grand total 650. Full ROLLUP adds 3 rows. Partial keeps detail plus per-level subtotals. Bridge: the same pattern repeats on inventory data, where furniture 30, equipment 20, and grand total 50 play the anchor role.

26.2.5 Worked Examples

Example 1 — per-level totals from detail. Start from the ordered detail. Apply SUM grouped by level alone. Basic gives 200. Premium gives 100 plus 100 plus 250, which is 450. Add them for grand total 650. No rounding. No hidden steps. Check: sum of all detail equals 650, so the split is complete.

Example 2 — full ROLLUP in one query. Run the ROLLUP query on course level and course name without ORDER BY. Find the row with both columns empty showing 650. Find the basic subtotal row showing 200. Find the premium subtotal row showing 450. Re-run with ORDER BY to see the same numbers arranged as a readable report: basic items, basic 200, premium items, premium 450, grand 650.

Example 3 — partial ROLLUP. Run GROUP BY course level plus ROLLUP on course name with ORDER BY. Verify basic detail plus basic subtotal appear first, premium detail rows appear next, premium subtotal of 450 follows, and the closing total line completes the summary. Compare row counts with full ROLLUP to feel the missing \(()\) set.

26.2.6 Student Questions and Answers

Q: The grouped query repeats premium on many rows. How do we get a single value per level?

A: Drop course name from the select and group only by course level. Then SUM runs once per level. That gives basic 200 and premium 450 as single rows. The repeat happened because grouping by level plus name keeps each course apart.

Q: Can one query show detail rows and summary rows together?

A: Yes. Wrap the grouping columns in ROLLUP. One query then returns detail rows for each level plus name pair, one subtotal row per level, and one grand total row for all levels. That is GROUP BY ROLLUP(course_level, course_name) in PostgreSQL, or GROUP BY course_level, course_name WITH ROLLUP in MySQL.

Q: What is the difference between full ROLLUP and partial ROLLUP here?

A: Full ROLLUP on course level and course name creates detail plus per-level subtotals plus grand total. Partial form with course level fixed and ROLLUP only on course name creates detail plus per-level subtotals organized level by level. The choice of which columns sit inside ROLLUP controls which extra rows appear.

Exam note: Keep anchor numbers courses basic 200, premium 450, grand total 650. Expect to compute which extra rows ROLLUP adds: full adds per-level subtotals plus grand total, partial adds per-level subtotals only.

26.3 Adding Subtotals with ROLLUP on Inventory Data

26.3.1 Building the Inventory Test Table

The inventory table, meaning a second test table with identifier, category, subcategory, product, and quantity, repeats the ROLLUP lesson on a two-level product hierarchy. Category is the top group. Subcategory is the second group.

The definition used is:

CREATE TABLE inventory (
  inventory_id INTEGER PRIMARY KEY,
  category     VARCHAR(100) NOT NULL,
  subcategory  VARCHAR(100) NOT NULL,
  product      VARCHAR(100),
  quantity     INTEGER
);

Here \(\text{inventory\_id}\) is the integer primary key, \(\text{category}\) is the top group such as furniture or equipment, \(\text{subcategory}\) is the second group such as chair, desk, computer, or monitor, \(\text{product}\) is the item name such as black chair, brown chair, blue desk, PC, Mac, or Dell monitor, and \(\text{quantity}\) is the integer count.

Sample content uses two main categories. Furniture has subcategories chair and desk. Equipment has subcategories computer and monitor. Products include black chair, brown chair, blue desk, Mac, PC, and Dell monitor, each with a quantity such as 10. The exact per-product split is less important than the two anchor totals verified by separate GROUP BY queries: furniture total quantity 30 and equipment total quantity 20. Their sum is:

\[ \text{total\_furniture} = 30 \]

\[ \text{total\_equipment} = 20 \]

\[ \text{grand\_total} = 30 + 20 = 50 \]

Check: 30 plus 20 equals 50. Keep 30, 20, and 50 handy. Every ROLLUP row later must match one of them.

A quick check query is:

SELECT * FROM inventory;

followed by an ordered grouped view:

SELECT category, subcategory, SUM(quantity) AS quantity
FROM inventory
GROUP BY category, subcategory
ORDER BY category, subcategory;

This shows equipment rows together and furniture rows together, with repeated category labels. Removing subcategory and grouping by category alone gives the two anchor numbers 30 and 20 used to validate the later ROLLUP output.

Why a second table at all. Courses showed level to course. Inventory shows category to subcategory to product. Same ROLLUP shape, new labels. Seeing the same math twice helps lock the pattern: detail, subtotal, grand total.

Scope: NOT NULL on category and subcategory matters. It guarantees that any NULL in ROLLUP output must be a computed subtotal marker, not a real missing value. Without NOT NULL you need GROUPING to tell the two NULL meanings apart, which is the next section.

26.3.2 GROUP BY Category and Subcategory

Grouped sum by two columns, meaning one total per category plus subcategory pair, shows clean detail but no subtotal rows and no grand total row.

The grouped sum has the form:

\[ \text{total\_qty}(\text{category}, \text{subcategory}) = \sum_{i \in (\text{category}, \text{subcategory})} \text{quantity}_i \]

Here \(\text{quantity}_i\) is the quantity for row \(i\) and the sum runs over rows sharing the same category and subcategory. In words, group the data by category and subcategory, meaning break the product down by category and subcategory, and sum quantity.

The query is:

SELECT category, subcategory, SUM(quantity) AS quantity
FROM inventory
GROUP BY category, subcategory
ORDER BY category, subcategory;

This is a clean grouped view but it has no subtotal rows and no grand total row. Each row is one category plus subcategory pair. To see subtotals per category and a final total, ROLLUP is needed.

Picture a stock sheet. Each line shows one subcategory count. No line says furniture total. No line says store total. The manager must add by hand. That hand addition is what ROLLUP automates next.

Common traps: stopping here and adding subtotals in a spreadsheet, which drifts out of date; sorting without ORDER BY and assuming category blocks stay together; summing the grouped output again without care and double counting detail plus subtotal rows later.

26.3.3 ROLLUP on Category and Subcategory

Hook: one query should print the stock lines plus the category totals plus the store total. ROLLUP does all three at once.

The ROLLUP query borrows the same select and moves both grouping columns inside ROLLUP:

SELECT category, subcategory, SUM(quantity) AS quantity
FROM inventory
GROUP BY ROLLUP(category, subcategory);

In words, move these two columns in the rollup and that will cause the system to create group sets on category and subcategory. The expansion is:

\[ \text{ROLLUP}(\text{category}, \text{subcategory}) \equiv \{(\text{category}, \text{subcategory}), (\text{category}), ()\} \]

Three extra rows appear. One row has both category and subcategory empty and shows grand total 50. One row has subcategory empty and category furniture and shows 30. One row has subcategory empty and category equipment and shows 20. The empty cells appear as NULL in the raw output. The numbers match the separately verified anchor totals, which builds trust: 30 plus 20 equals the grand total 50.

Adding ORDER BY arranges the report so the grand total with empty keys sorts last:

SELECT category, subcategory, SUM(quantity) AS quantity
FROM inventory
GROUP BY ROLLUP(category, subcategory)
ORDER BY category, subcategory;

The ordered report reads as equipment detail rows, then an equipment subtotal row of 20, then furniture detail rows, then a furniture subtotal row of 30, then the final grand total row of 50. ROLLUP dissects the data, puts it in group sets for category and subcategory, calculates the sums, and adds the empty rows with NULL markers.

This is the NULL marker problem in plain sight. A reader cannot tell at a glance whether an empty cell means missing data or a computed subtotal. That motivates the GROUPING function covered next. The fix there replaces markers with labels such as subtotal and grand total.

Worked cross-check: group by category alone first. Furniture sums to 30. Equipment sums to 20. Grand sum is 50. Now run ROLLUP. The row with empty subcategory plus furniture shows 30, matching the furniture anchor. The row with empty subcategory plus equipment shows 20, matching the equipment anchor. The row with both columns empty shows 50, matching 30 plus 20. Sense-check passes, so the ROLLUP output is trusted.

Dialect extras: PostgreSQL, Snowflake, Oracle, Databricks use GROUP BY ROLLUP(category, subcategory). MySQL uses GROUP BY category, subcategory WITH ROLLUP. SQL Server accepts both spellings in recent versions. Snowflake also supports GROUP BY ROLLUP plus GROUPING_ID for multi-column flags, while Databricks Spark SQL supports ROLLUP, CUBE, and GROUPING SETS with GROUPING and GROUPING_ID. Same 50, 30, 20 logic everywhere.

Visualize the stock tree. Root is 50 units. Furniture branch holds 30. Equipment branch holds 20. Leaves are chair, desk, computer, monitor counts. ROLLUP prints leaves, then branch sums, then root sum. One-sentence takeaway: leaves add to branches, branches add to root.

Assumption: ROLLUP treats NULL as the subtotal marker. This read is safe here because category and subcategory are NOT NULL. If nullable columns held real NULLs, you must use GROUPING to separate real NULL from marker NULL instead of testing IS NULL.

Recap: ROLLUP on category and subcategory adds furniture 30, equipment 20, and grand total 50 to the detail. Bridge: labels are still missing, since subtotal rows show empty cells, so GROUPING plus CASE plus COALESCE step in next to make the report readable.

26.3.4 Worked Examples

Example 1 — anchor totals. Group by category and subcategory, note repeated furniture and equipment labels, then group by category alone to get furniture 30 and equipment 20. Add them to get 50. Keep these three numbers for comparison. They are the answer key for every later query.

Example 2 — ROLLUP without ORDER BY. Run the ROLLUP query, find the row with both columns empty showing 50, find the furniture row with empty subcategory showing 30, find the equipment row with empty subcategory showing 20, and confirm each matches its anchor total. If output order looks odd, that is normal without ORDER BY.

Example 3 — ROLLUP with ORDER BY. Re-run with ORDER BY category and subcategory, trace equipment items to equipment subtotal 20, furniture items to furniture subtotal 30, and the last row to grand total 50. Note that NULL keys sort last, which places the grand total at the end. Sense-check: 20 plus 30 equals 50.

26.3.5 Student Questions and Answers

Q: What if we want the subtotal for each category plus a final total, not just grouped detail?

A: Use ROLLUP on category and subcategory. It adds one grand total row with both columns empty and one subtotal row per category with subcategory empty, alongside the detail rows. That is three extra rows here: furniture 30, equipment 20, grand total 50.

Q: How do we know the ROLLUP totals are right? Several students asked this in different words.

A: Cross-check. Group by category alone first and note furniture 30 and equipment 20. Then run ROLLUP and confirm the same 30 and 20 appear as subtotal rows and 50 appears as the grand total. If they match, trust the ROLLUP. If not, check filters, joins, or NULL handling before blaming ROLLUP.

Q: Why do empty cells appear in the ROLLUP output?

A: ROLLUP uses empty markers for the level being totalled. Both columns empty means grand total. Subcategory empty with category filled means that category subtotal. These markers are later replaced with readable labels using GROUPING plus CASE plus COALESCE. Empty here means rolled up, not missing.

Exam note: Keep anchor numbers inventory furniture 30, equipment 20, grand total 50. Expect to map empty markers to grand total and subtotals, and to state which grouping set each extra row came from.

26.4 Using GROUPING with ROLLUP for Readable Reports

26.4.1 What the GROUPING Function Returns

GROUPING, meaning a function that works together with ROLLUP and returns 1 for a subtotal or total row on the given column and 0 otherwise, tells computed summary rows apart from ordinary detail rows. It is the highlighter that marks which rows are summaries.

In words, grouping always returns either 0 or 1, where 0 means not a subtotal row for the given column and 1 means this row represents a subtotal or total for that column. The logic form is:

\[ \text{GROUPING}(c) = \begin{cases} 1 & \text{if row is a subtotal or total for column } c \\ 0 & \text{otherwise} \end{cases} \]

Here \(c\) is the grouping column under test, such as category or subcategory. For a detail row, both flags are 0. For a category subtotal, the subcategory flag is 1. For the grand total, both flags are 1.

The diagnostic query adds two extra columns:

SELECT category, subcategory, SUM(quantity) AS quantity,
       GROUPING(category) AS "category grouping",
       GROUPING(subcategory) AS "subcategory grouping"
FROM inventory
GROUP BY ROLLUP(category, subcategory)
ORDER BY category, subcategory;

Detail rows show 0 and 0. The equipment subtotal row carries a 1 marker and quantity 20. The furniture subtotal row carries a 1 marker and quantity 30. The final grand total row carries 1 and 1 with quantity 50. A 1 means think of this row as the subtotal or total row. A 0 means no total on that column for that row.

Think of GROUPING as a highlighter pen. It does not change the numbers. It marks which rows are summary rows so later formatting can label them.

Why not just test for NULL. Because NULL has two meanings once ROLLUP runs: real missing value versus computed subtotal marker. GROUPING separates them. If a product truly had NULL category, category IS NULL would fire on both real and summary rows, but GROUPING(category) = 1 fires only on summary rows. That is the whole reason the function exists.

Dialect extras: Oracle, DB2, SQL Server, PostgreSQL, Snowflake, and Databricks all ship GROUPING(col). SQL Server and Oracle also ship GROUPING_ID(a, b), which packs several flags into one number for quick CASE tests. MySQL with WITH ROLLUP historically leaned on COALESCE(col, 'TOTAL') for the one-column case, and newer MySQL adds GROUPING() as well. Same idea everywhere: 0 keeps the value, 1 prints a label.

Scope: GROUPING only has meaning with ROLLUP, CUBE, or GROUPING SETS in the same GROUP BY. Used with a plain GROUP BY it always returns 0. Also pass the exact grouping column, not an alias or expression, or the flag misfires.

Picture a table with two extra marker columns. Detail lines show 0, 0. Subtotal lines show a 1 in the rolled column. Grand total shows 1, 1. Takeaway: read the 1s to find summary rows without guessing from NULLs.

26.4.2 Replacing NULL Markers with Labels Using CASE and COALESCE

Raw ROLLUP leaves NULL markers that confuse readers. Two tools clean the report. COALESCE supplies the visible value. CASE supplies the summary label based on GROUPING output.

A COALESCE, meaning a function that returns the first non-empty value, so a real column value prints when present and a fallback prints otherwise, handles plain columns. A CASE, meaning an expression that tests GROUPING output and returns a label such as subtotal or grand total, handles summary rows.

A first partial CASE tested only the category level:

SELECT category, subcategory, SUM(quantity) AS quantity,
  CASE WHEN GROUPING(category) = 1 THEN 'grand total' ELSE '' END AS subtotal
FROM inventory
GROUP BY ROLLUP(category, subcategory)
ORDER BY category, subcategory;

When \(\text{GROUPING}(\text{category}) = 1\), the row is labelled grand total with quantity 50. Other rows keep an empty marker for that column while the fuller report is built. This step isolates one formatting move before building the full report.

The fuller report targets four visible columns: category, subcategory, quantity, and a subtotal or total label column. The pattern for the category display column is:

CASE
  WHEN GROUPING(category) = 1 THEN 'grand total'
  WHEN GROUPING(subcategory) = 1 THEN 'subtotal'
  ELSE category
END AS category

In words, if grouping for category is one, make this row grand total, if grouping for subcategory is one, make it subtotal, otherwise print the actual category. The same idea applies to the subcategory display column, where a real subcategory value prints when present and a fallback prints otherwise. COALESCE is used for the straightforward columns where no special summary label is needed:

COALESCE(category, 'value') AS category_display

adapted per column so that quoted field names are not confused with string literals. A teaching fix is highlighted here: quoted identifiers with double quotes refer to columns, while single-quoted text is a literal label. Using double quotes around a label where a column value was intended caused the label to repeat instead of showing equipment and furniture names. Replacing the quoted literal with the actual column reference fixed the report.

The final readable query has this shape:

SELECT
  CASE
    WHEN GROUPING(category) = 1 THEN 'grand total'
    WHEN GROUPING(subcategory) = 1 THEN 'subtotal'
    ELSE category
  END AS category,
  subcategory,
  SUM(quantity) AS quantity
FROM inventory
GROUP BY ROLLUP(category, subcategory)
ORDER BY category, subcategory;

Extended with COALESCE on the subcategory display column and a dedicated subtotal label column, the ordered output reads as equipment plus computer 10, equipment plus monitor 10, equipment subtotal 20, furniture chair and desk detail rows, furniture subtotal 30, and grand total 50. The GROUPING value of 1 triggers the replacement of that row with the subtotal or grand total label. That is why the labels appear exactly on the summary rows.

Order of WHEN branches matters. Test grand total first, then subtotal, then ELSE value. If subtotal is tested first, the grand total row also matches the subtotal test and gets the wrong label. This is a classic CASE order bug.

Common traps: using double quotes for labels, which turns 'subtotal' into "subtotal" identifier and repeats or errors; swapping CASE branch order so grand total prints as subtotal; wrapping the GROUPING column in COALESCE before testing, which hides the 1 flag; forgetting ELSE so detail rows turn NULL.

Cross-system recipe card: PostgreSQL uses GROUP BY ROLLUP(a) plus COALESCE(a, 'TOTAL') or CASE WHEN GROUPING(a)=1. Oracle and DB2 use GROUP BY ROLLUP(a) plus CASE WHEN GROUPING(a)=0. SQL Server and MySQL with WITH ROLLUP use COALESCE(a, 'TOTAL'), with GROUPING(a) as the safer test when NULLs exist. Snowflake and Databricks use GROUP BY ROLLUP(a, b) plus GROUPING(a) or GROUPING_ID(a, b). Keep the lecture pattern as the base, swap only the ROLLUP spelling per system.

Real use: sales summary pages where each section ends with a subtotal line and the page ends with a grand total line, stock reports where each category closes with a category total, course dashboards where each level closes with a level total.

Recap: GROUPING returns 0 for detail and 1 for summary. CASE turns 1 into grand total or subtotal text. COALESCE fills plain values. Bridge: worked cases next lock the 20, 30, 50 mapping so the flags can be read at speed.

The equipment summary row shows a 1 marker with quantity 20. The furniture summary row shows a 1 marker with quantity 30. The last row shows 1 markers with quantity 50. 26.4.4 Student Questions and Answers

Q: The ROLLUP output shows NULL values. How do we handle those empty cells?

A: Add GROUPING columns to mark summary rows, then use CASE to return grand total or subtotal labels when the marker is 1, and use COALESCE to show the real column value otherwise. The empty markers are then replaced with readable labels. Never filter NULLs away, since that would delete the subtotal rows themselves.

Q: What do 0 and 1 from GROUPING mean?

A: 0 means this row is not a total for the given column. 1 means this row represents a subtotal or total for that column. The equipment and furniture summary rows show 1 with quantities 20 and 30, and the last row shows 1 markers with quantity 50. Think highlighter: 1 means highlighted as summary.

Q: Why did the category names disappear and only the label text repeat?

A: Double quotes were used around a literal where an actual column reference was needed. Double-quoted text is treated as an identifier, single-quoted text as a literal label. Using the real category column reference restores equipment and furniture names in the output. Fix: ELSE category with no quotes, and 'subtotal' with single quotes for text.

Exam note: Be ready to read GROUPING flags at speed: 0 keeps the value, 1 prints the label. Also be ready to spot the quote bug: double quotes name a column, single quotes make text.
