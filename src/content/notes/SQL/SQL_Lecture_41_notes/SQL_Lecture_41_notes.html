# Using Human Resource (HR) Database

41.1 Relational Database Architecture and Schema Design

Architectural Motivation: How does a multinational enterprise track thousands of employees, organizational reporting hierarchies, and global office locations without producing redundant data or dangerous update anomalies? By partitioning business entities into normalized reference lookup and operational transaction tables linked by strict referential constraints.

In enterprise information systems, relational database architecture organizes business entities into specialized, normalized tables. Instead of storing all company records in a single flat spreadsheet, an enterprise schema separates master domain entities from dynamic workforce transactions.

Filing Cabinet Analogy: Think of the Human Resource schema as an organizational filing cabinet divided into two distinct drawers:

  1. Master Reference Catalogs: Static reference lookup tables that define the enterprise landscape (such as geographic regions, countries, office locations, and job classifications).
  2. Dynamic Operational Ledgers: Operational transaction tables that log active workforce events (such as current employee assignments and chronological job role transitions).

Where the analogy breaks: A physical folder allows duplicate or misplaced papers; a relational database engine uses foreign key constraints and index lookups to strictly prohibit unlinked or orphaned records.

41.1.1 Schema Hierarchy and Table Roles

The standard Human Resource (HR) schema partitions corporate personnel records into seven interrelated tables. These tables divide naturally into reference lookup tables and operational transaction tables.

Reference lookup tables store relatively static master entities that provide business context for company operations:

  • regions: Stores global geographic regions, such as the Americas, Europe, Middle East, and Africa.
  • countries: Records sovereign nations mapped to global regions, such as the United States, United Kingdom, and Singapore.
  • locations: Contains physical street addresses, postal codes, and facility cities for company offices.
  • departments: Lists organizational business units, including Sales, Marketing, and Information Technology (IT).
  • jobs: Defines job role classifications and administrative titles across the enterprise, such as programmer, administrative assistant, or sales representative.

Operational transaction tables record active events, assignments, and personnel movement over time:

  • employees: The central operational table in the enterprise schema. It records comprehensive employee records and transactional attributes: unique employee identifier, first name, last name, corporate email address, contact phone number, hire date, assigned job identifier, salary, commission percentage, direct reporting manager identifier, and assigned department identifier.
  • job_history: Records internal workforce transitions and historical assignments. Whenever an employee transfers between departments or transitions to a different job role, this table records the historical details. It tracks the employee identifier, assignment start date, assignment end date, former job identifier, and former department identifier.

41.1.2 Primary and Foreign Key Relationships

Relational databases enforce data integrity through primary and foreign keys. A primary key is a column or set of columns that uniquely identifies each individual record within a table, guaranteeing entity integrity. A foreign key is a column that references the primary key of another table, establishing a referential constraint between parent and child tables.

Core Referential Schema: The primary keys across the HR database include:

  • regions: region_id
  • countries: country_id
  • locations: location_id
  • departments: department_id
  • jobs: job_id
  • employees: employee_id
  • job_history: Composite primary key composed of (employee_id, start_date). A worker can hold multiple roles throughout their career, but can only start a given role on one unique date.

Foreign keys link tables across the schema:

  • countries.region_id references regions.region_id.
  • locations.country_id references countries.country_id.
  • departments.location_id references locations.location_id.
  • employees.job_id references jobs.job_id.
  • employees.department_id references departments.department_id.
  • employees.manager_id references employees.employee_id. This creates a self-referential foreign key where a manager is also an employee within the same table.
  • job_history.employee_id references employees.employee_id.
  • job_history.job_id references jobs.job_id.
  • job_history.department_id references departments.department_id.

The relational schema graph below visualizes how references cascade through the enterprise hierarchy:

Scope & Assumptions:

  • Entity Integrity: Primary key columns cannot contain NULL values. In composite primary keys, no component column can be NULL.
  • Referential Integrity: A foreign key must either match an existing primary key value in the parent table or be NULL. Setting manager_id to NULL represents the top of the reporting hierarchy (the president).

41.1.3 Inspecting Job History and Employee Transactions

To inspect table installations, queries select records and sort them chronologically.

Worked Example 41.1.1 — Inspecting Job History Transitions: To view all records in job_history:

SELECT * FROM job_history;

Sorting by start_date in ascending order presents career transitions chronologically:

SELECT * FROM job_history 
ORDER BY start_date ASC;

Sorting in descending order highlights the most recent personnel transitions:

SELECT * FROM job_history 
ORDER BY start_date DESC;

Sample Output Interpretation: An employee who began as an IT programmer on 2001-01-13 and transferred to a database administrator role on 2006-03-24 appears with two distinct rows in job_history. Sorting by start_date DESC immediately surfaces the 2006 transition at the top of the ledger.

Querying the central employees table displays personnel demographics and compensation:

SELECT * FROM employees;

We can filter employees earning substantial compensation. For instance, to locate employees with an annual salary strictly greater than 10,000 USD:

SELECT * FROM employees 
WHERE salary > 10000;

This filter returns 15 qualifying employee records. If we raise the threshold to 20,000 USD or higher:

SELECT * FROM employees 
WHERE salary >= 20000;

Only a single record satisfies this condition: the company president, earning an annual salary of 24,000 USD.

The verbal description of this threshold evaluation is: "see employee whereby the salary salary of the employee is greater than 10000 and this will give me all the employee there are 15 employees and if I wanted to look at let's say anybody who's paid 20000 or more of course there's only one".

Formal Mathematical Formulation: The compensation threshold predicate is defined as: \[ S > 10000 \quad \text{and} \quad S \ge 20000 \] where \(S \in \mathbb{R}^+\) represents the annual employee salary in USD. The set of qualifying employees for the strict threshold is: \[ E_{> 10000} = \{ e \in \text{Employees} \mid S(e) > 10000 \}, \quad |E_{> 10000}| = 15 \] and for the executive threshold: \[ E_{\ge 20000} = \{ e \in \text{Employees} \mid S(e) \ge 20000 \}, \quad |E_{\ge 20000}| = 1 \] The single qualifying record in \(E_{\ge 20000}\) corresponds to the corporate president.

Common Pitfalls:

  1. Confusing Primary Keys with Unique Foreign Keys: Assuming that because an employee exists in job_history, employee_id alone can serve as the primary key. If an employee transfers roles twice, a single-column primary key on employee_id rejects the second transfer as a duplicate key violation.
  2. Circular Reporting References: Setting an employee as their own manager or creating cyclical managerial loops (A manages B, B manages A). While relational foreign keys permit valid self-references, application logic or check constraints must guard against circular hierarchies.

41.1.4 Student Questions and Answers

Q: Why does the job history table require both employee ID and start date as its primary key?

A: An employee can transfer between roles multiple times over their tenure. If employee ID alone served as the primary key, the table could store only a single historical record per worker. Pairing employee ID with start date forms a composite primary key that uniquely tracks each distinct career assignment.

41.1.6 Industry Applications

Enterprise relational database systems (such as Oracle, PostgreSQL, MySQL, and Microsoft SQL Server) use this standard HR schema structure as the reference architecture for Human Resource Information Systems (HRIS) and Enterprise Resource Planning (ERP) platforms like SAP and Workday. Core operational modules rely on normalized tables to prevent update anomalies: when a department relocates, updating its city in locations automatically updates the effective location for all assigned employees without touching individual worker records.

41.1.7 Exam Notes

Exam note: Database normalization questions often ask students to identify primary and foreign keys in the HR schema, specifically pointing out composite primary keys like (employee_id, start_date) in job_history and self-referencing foreign keys like manager_id in employees. Remember that a composite primary key requires all constituent columns to be non-null and jointly unique across all rows.

41.2 Column Slicing, Arithmetic Expressions, and Aliases

Business Reporting Motivation: Raw database tables store column names with technical snake_case identifiers such as first_name and hire_date. How can business analysts present polished executive reports and compute real-time financial metrics—such as percentage bonuses or monthly payroll disbursements—without altering the underlying database schema? By projecting specific columns, applying scalar arithmetic operators, and assigning clean column aliases.

Querying a database requires projecting only the columns required by downstream consumers, rather than indiscriminately retrieving entire tables with SELECT *. Furthermore, database engines allow calculating new derived columns on the fly through arithmetic expressions and formatting them with user-friendly presentation labels.

Camera Lens and Price Tag Analogy: Think of the SELECT projection list as a customizable camera lens:

  1. Column Slicing: The lens zooms in on only the relevant fields, filtering out unneeded attributes from the wider table.
  2. Column Aliases: Just as a store manager sticks a clean label over an item's internal warehouse barcode, an alias renames a cryptic column header for presentation without changing the underlying product code in the catalog.
  3. Arithmetic Expressions: Live currency converters that recalculate prices into new currencies or tax brackets before showing them to the customer.

Where the analogy breaks: A physical price tag must be hand-applied to each item; a SQL expression transforms millions of database records in parallel during query execution.

41.2.1 Column Aliases for Business Presentation

Database column names often use abbreviated snake_case identifiers, such as first_name and last_name. For stakeholder dashboards and business reporting, SQL provides column aliases using the AS keyword to rename columns in query results without modifying the underlying database schema.

In PostgreSQL and ANSI SQL, when an alias contains whitespace, we enclose it in double quotation marks:

Worked Example 41.2.1 — Formatting Column Aliases for Business Presentation:

SELECT 
    first_name AS "First Name", 
    last_name AS "Last Name" 
FROM employees;

Output Format:

 First Name  |  Last Name  
-------------+-------------
 Steven      | King
 Neena       | Kochhar
 Lex         | De Haan

PostgreSQL also allows omitting the AS keyword and supplying the alias directly after the column name (e.g., first_name "First Name"). However, explicitly writing AS makes query intent clear and prevents confusing an omitted comma with an intended alias.

41.2.2 Arithmetic Expressions and Percentage Computations

Columns containing numeric values support standard arithmetic calculations (+, -, *, /) inside the SELECT clause. For example, during annual compensation reviews, management can calculate a 15% salary increase or bonus across all staff.

The verbal description of this computation is: "take the salary column and just simply multiply by 0.15 which is a 15 percent and this will give me the 15 percent of the salary".

Formal Mathematical Formulation: The percentage bonus computation formula is defined as: \[ S_{\text{bonus}} = S \times r \] where \(S \in \mathbb{R}^+\) is the base employee salary in USD, \(r \in [0, 1]\) is the fractional multiplier (\(r = 0.15\) for a 15% rate), and \(S_{\text{bonus}} \in \mathbb{R}^+\) is the resulting bonus compensation amount.

Worked Example 41.2.2 — Computing Percentage Bonus and Positional Ordering: The SQL query computes this value using a multiplier and assigns an alias:

SELECT 
    first_name, 
    last_name, 
    salary, 
    salary * 0.15 AS salary_15_pct 
FROM employees;

For an employee with base salary \(S = 24000 \text{ USD}\): \[ S_{\text{bonus}} = 24000 \times 0.15 = \mathbf{3600.00 \text{ USD}} \] For a 30% adjustment, we substitute the multiplier with 0.30:

SELECT 
    first_name, 
    last_name, 
    salary, 
    salary * 0.30 AS salary_30_pct 
FROM employees;

To rank employees by bonus amount in descending order, we can sort by column ordinal position 4:

SELECT 
    first_name, 
    last_name, 
    salary, 
    salary * 0.15 AS salary_15_pct 
FROM employees 
ORDER BY 4 DESC;

Sense Check: The company president receives the largest bonus of 3,600 USD on a 24,000 USD base salary, correctly appearing as the first record.

41.2.3 Monthly Salary Calculation and Rounding

The base salary in the employees table reflects annual compensation. To calculate monthly payroll disbursements across the enterprise, we divide the annual figure by 12 calendar months and round the result to two decimal places.

The verbal description of this computation is: "divide the salary because we are looking for from annual number to monthly number so we are going to divide this to 12 which is the total number of months in the year".

Formal Mathematical Formulation: The monthly salary division and rounding formula is: \[ S_{\text{monthly}} = \text{round}\left(\frac{S_{\text{annual}}}{M}, 2\right) \] where \(S_{\text{annual}} \in \mathbb{R}^+\) represents the annual employee salary in USD, \(M = 12 \in \mathbb{Z}^+\) is the number of calendar months in a year, and \(S_{\text{monthly}} \in \mathbb{R}^+\) is the computed monthly wage rounded to two decimal places.

Worked Example 41.2.3 — Monthly Payroll Disbursements: The SQL query applies the ROUND function:

SELECT 
    first_name, 
    last_name, 
    salary, 
    ROUND(salary / 12.0, 2) AS monthly_salary 
FROM employees;

For the company president earning \(S_{\text{annual}} = 24000 \text{ USD}\): \[ S_{\text{monthly}} = \text{round}\left(\frac{24000}{12}, 2\right) = \mathbf{2000.00 \text{ USD}} \] For an employee earning \(S_{\text{annual}} = 17000 \text{ USD}\): \[ S_{\text{monthly}} = \text{round}\left(\frac{17000}{12}, 2\right) = \text{round}(1416.6666..., 2) = \mathbf{1416.67 \text{ USD}} \] Sense Check: Multiplying 1,416.67 USD by 12 gives 17,000.04 USD, confirming precision to within four cents before payroll ledger reconciliation.

41.2.4 Positional Ordering in Queries

SQL allows ordering query outputs by referencing the numeric ordinal position of selected expressions rather than repeating full column names or alias strings. For example, to sort employees by the 15% bonus calculation in descending order, we can reference column position 4:

SELECT 
    first_name, 
    last_name, 
    salary, 
    salary * 0.15 AS salary_15_pct 
FROM employees 
ORDER BY 4 DESC;

In this query, the president receives the highest bonus amount of 3,600 USD on a 24,000 USD base salary. Similarly, when reviewing monthly compensation, we can sort by the third column:

SELECT 
    first_name, 
    last_name, 
    ROUND(salary / 12.0, 2) AS monthly_salary 
FROM employees 
ORDER BY 3 DESC;

This places the highest monthly salary of 2,000.00 USD at the top.

The diagram below illustrates the logical query execution pipeline and explains why aliases are visible in ORDER BY but not in WHERE:

1. FROM / JOIN     --> Identifies tables and joins rows
2. WHERE           --> Filters rows (aliases NOT yet visible!)
3. GROUP BY        --> Aggregates rows into groups
4. HAVING          --> Filters summarized groups
5. SELECT          --> Evaluates arithmetic expressions and creates ALIASES
6. ORDER BY        --> Sorts output (aliases and positional ordinals ARE visible!)
7. LIMIT / OFFSET  --> Restricts returned row count

Scope & Assumptions:

  • Integer Division Truncation: In PostgreSQL and Microsoft SQL Server, dividing an integer by an integer performs integer truncation (e.g., 17000 / 12 yields 1416 rather than 1416.666...). Dividing by a decimal literal (12.0) or explicitly casting via CAST(salary AS numeric) forces accurate floating-point arithmetic.
  • Alias Scope Boundary: A column alias defined in the SELECT clause cannot be referenced inside the WHERE clause because the database processes WHERE row filters before constructing SELECT projections.

Common Pitfalls:

  1. Single Quotes vs. Double Quotes: Enclosing aliases in single quotes (e.g., AS 'First Name') is non-standard in PostgreSQL and treats the identifier as a string literal constant rather than a valid column identifier. Standard ANSI SQL requires double quotes for identifiers containing whitespace.
  2. Positional Ordering Fragility: Writing ORDER BY 3 or ORDER BY 4 is convenient for quick ad-hoc queries at the command line, but dangerous in production ETL pipelines. If a colleague adds a new column to the SELECT list, column 4 silently points to an unintended attribute, corrupting sort order without throwing a syntax error.

41.2.5 Student Questions and Answers

Q: Why does SQL allow ordering by numeric column numbers such as order by 3 or 4 instead of writing column names?

A: The number corresponds to the ordinal position of the column in the SELECT list. While convenient for quick interactive command-line analysis, production queries should specify explicit column names or aliases to prevent silent bugs if someone reorders the SELECT list later.

41.2.7 Industry Applications

Financial reporting engines, payroll calculation pipelines, and billing systems rely on SQL arithmetic expressions and precision rounding functions to generate payslips and invoices with strict currency accuracy. For example, enterprise platforms like Workday and Stripe calculate prorated monthly compensation, tax withholdings, and bonus incentives directly within database projection queries to minimize network data transfer.

41.2.8 Exam Notes

Exam note: Exam questions frequently test scalar arithmetic operations in SELECT lists and verify whether students remember to use the ROUND function to limit floating point currency figures to two decimal places. Always be prepared to explain why WHERE cannot filter on a SELECT alias, and note that ROUND(val, 2) prevents decimal overflow in financial ledger outputs.

41.3 Single-Row String Functions and Pattern Matching

Data Cleansing Motivation: Real-world enterprise databases rarely contain pristine text. Contact lists arrive with mixed capitalization, irregular formatting, and embedded domain suffixes. How can data engineers clean, standardize, and filter alphanumeric attributes using native SQL? By leveraging single-row scalar string functions and wildcard pattern matching.

Single-row functions operate on individual values row by row, returning exactly one transformed value for each input record. In text processing, these functions enable slicing character sequences, altering letter case, locating delimiter offsets, and substituting substrings.

Carpenter's Measuring Tape and Stencil Analogy: Think of string functions as tools in a precision workshop:

  1. LENGTH & SUBSTR: A measuring tape and handsaw that measure total character length and cut a board to exact specifications.
  2. UPPER & INITCAP: Industrial stencils that paint clean, uniform lettering across every nameplate regardless of how roughly the raw wood was marked.
  3. LIKE Wildcards: Sorting templates where % acts as an expandable accordion matching any length of excess material, while _ acts as a rigid single-notch gauge matching exactly one peg.

Where the analogy breaks: Physical cutting permanently consumes lumber; SQL string functions produce projected copies in memory, preserving the original stored data intact on disk until explicit UPDATE statements are committed.

41.3.1 String Length and Substring Extraction

The LENGTH function counts the total number of characters in a string:

SELECT 
    first_name, 
    email, 
    LENGTH(email) AS email_length 
FROM employees;

Measuring character length helps identify unusually long entries, such as corporate emails containing 28 or 23 characters, which may signal formatting anomalies or combined address fields during ETL ingestion.

To extract a contiguous portion of a string, SQL provides SUBSTR (or SUBSTRING). The function accepts the source string, a starting index (1-based), and the extraction character count:

SELECT 
    first_name, 
    SUBSTR(email, 1, 5) AS email_prefix 
FROM employees;

This returns the first five characters of each employee's email address.

41.3.2 Stripping Email Suffixes with String Reversal

Data cleaning often requires removing fixed trailing suffixes, such as discarding the last four characters (.com) from an email address.

The verbal description of this computation is: "take length calculate the email length and we are going to minus from the total number of length which is the 28 minus the four to get to minus the number of character we don't want from the right hand side of the string".

Formal Mathematical Formulation: The substring extraction length formula for dropping suffix characters is: \[ k = L - d \] where \(L \in \mathbb{Z}^+\) is the total character length of the source string, \(d = 4 \in \mathbb{Z}^+\) is the count of suffix characters to drop, and \(k \in \mathbb{Z}^+\) is the remaining character length extracted from index 1.

Worked Example 41.3.1 — Suffix Stripping with SUBSTR and LENGTH: We combine SUBSTR and LENGTH to truncate trailing characters dynamically:

SELECT 
    first_name, 
    email, 
    SUBSTR(email, 1, LENGTH(email) - 4) AS extracted_email 
FROM employees;

Step-by-Step Character Walkthrough:

  • Source email: SKING@CORP.COM
  • Total length: \(L = \text{LENGTH}(\text{'SKING@CORP.COM'}) = 14\)
  • Subtraction: \(k = 14 - 4 = \mathbf{10}\)
  • Extraction: \(\text{SUBSTR}(\text{'SKING@CORP.COM'}, 1, 10) = \mathbf{\text{'SKING@CORP'}}\)
  • Sense Check: The four trailing characters '.com' are discarded, leaving the root corporate identifier intact.

An alternative approach uses the REVERSE function. The REVERSE function inverts character order:

SELECT 
    email, 
    REVERSE(email) AS reverse_email 
FROM employees;

For example, company.com inverts to moc.ynapmoc.

Worked Example 41.3.2 — Suffix Stripping via Reverse-Substring Pipeline: To strip the four-character .com suffix, we reverse the string, extract starting at position 5 (skipping moc.), and reverse the result back:

SELECT 
    email, 
    REVERSE(SUBSTR(REVERSE(email), 5)) AS extracted_email 
FROM employees;

Transformation Pipeline Trace:

  1. Input string: executive@enterprise.com
  2. First reversal: REVERSE(...) \(\to\) moc.esirpretne@evitucexe
  3. Offset extraction: SUBSTR(..., 5) \(\to\) esirpretne@evitucexe (drops positions 1–4: moc.)
  4. Final reversal: REVERSE(...) \(\to\) \mathbf{\text{executive@enterprise}}

Both the length-subtraction and reversal methods yield identical, clean email prefixes.

41.3.3 Case Conversion Functions: UPPER, LOWER, and INITCAP

Case standardization ensures consistent presentation and reliable equality matching:

  • UPPER: Converts all characters in a string to uppercase.
  • LOWER: Converts all characters in a string to lowercase.
  • INITCAP: Formats text in title case, capitalizing the first letter of each word while setting subsequent characters to lowercase.

Worked Example 41.3.3 — Casing Standardization across Person Records:

SELECT 
    first_name, 
    UPPER(first_name) AS upper_name, 
    LOWER(first_name) AS lower_name, 
    INITCAP(first_name) AS initcap_name 
FROM employees;

Output Formatting:

 first_name | upper_name | lower_name | initcap_name 
------------+------------+------------+--------------
 STEVEN     | STEVEN     | steven     | Steven
 neena      | NEENA      | neena      | Neena
 Lex        | LEX        | lex        | Lex

To extract leading characters from personal names, SUBSTRING works smoothly with case operations:

SELECT 
    SUBSTRING(first_name, 1, 3) AS short_name 
FROM employees;

For Steven, this returns Ste.

41.3.4 Locating Substrings with the POSITION Function

The POSITION function locates the index of a target substring within a source string, returning a 1-based character position. If the search string is absent, POSITION returns 0.

Worked Example 41.3.4 — Locating Specific Characters at Given Offsets: To locate the uppercase letter 'C' within employee last names:

SELECT 
    last_name, 
    POSITION('C' IN last_name) AS c_position 
FROM employees;

Names without an uppercase 'C' produce 0. Names like Cambrault produce 1. To filter for employees who contain an uppercase 'C' at the third character position or greater:

SELECT 
    first_name, 
    last_name 
FROM employees 
WHERE POSITION('C' IN last_name) >= 3;

This filter returns Samuel McCain, where the uppercase character 'C' appears at character position 3.

41.3.5 In-Place String Replacement in UPDATE Statements

The REPLACE function substitutes all occurrences of a search string with a replacement string:

REPLACE(source_column, 'search_string', 'replacement_string')

Worked Example 41.3.5 — Updating Phone Number Substrings: When updating database tables, we pair REPLACE with a WHERE clause containing LIKE to avoid rewriting rows that do not require changes:

UPDATE employees 
SET phone_number = REPLACE(phone_number, '123', '888') 
WHERE phone_number LIKE '%123%';

This query updates only the records where the phone number contains the substring 123, replacing those digits with 888. Omitting the WHERE clause would force the database engine to touch and lock every row in the table, creating unnecessary transaction log overhead and index bloat.

41.3.6 Wildcard Matching with LIKE and Exact Length Filtering

The LIKE operator performs pattern matching using wildcard characters:

  • %: Matches zero or more arbitrary characters.
  • _: Matches exactly one single character.

To find employees whose first names begin with 'A', 'C', or 'M':

SELECT 
    first_name, 
    last_name 
FROM employees 
WHERE first_name LIKE 'A%' 
   OR first_name LIKE 'C%' 
   OR first_name LIKE 'M%' 
ORDER BY first_name ASC;

Worked Example 41.3.6 — Exact Length Filtering with Underscore Wildcards: To match names with an exact character length, we can use either single-character underscores or the LENGTH function. For example, to display last names containing exactly six characters:

SELECT last_name 
FROM employees 
WHERE last_name LIKE '______';

Six underscores match exactly six characters. The equivalent query using LENGTH is:

SELECT last_name 
FROM employees 
WHERE LENGTH(last_name) = 6;

Both queries return employees such as Austin. To find eight-character names, we expand the pattern to eight underscores or specify LENGTH(last_name) = 8.

Scope & Assumptions:

  • 1-Based Indexing: Standard SQL string indexing begins at position 1, not 0. A starting index of 1 selects the very first character of the string.
  • Escape Sequences: If you need to search for a literal % or _ character, you must escape it using the ESCAPE clause (e.g., WHERE discount_code LIKE '%\%%' ESCAPE '\').

Common Pitfalls:

  1. The LIKE 'A' Trap: Searching with LIKE 'A' looks for a name that consists solely of the single letter 'A', failing to match Alexander or Adam. You must append % (LIKE 'A%') to permit following characters.
  2. Case Sensitivity Pitfall: In PostgreSQL, LIKE is strictly case-sensitive. Searching LIKE 'a%' fails to match 'Austin'. Use ILIKE in PostgreSQL for case-insensitive pattern matching, or wrap the column in LOWER(name) LIKE 'a%'.

41.3.7 Student Questions and Answers

Q: Why does searching with LIKE 'A' fail to find names starting with letter A such as Alexander or Adam?

A: Searching without wildcards looks for an exact literal match of the single character 'A'. Searching with LIKE 'A' fails because it requires the exact single character. So we must append the percent wildcard symbol as in LIKE 'A%' to match any trailing characters.

41.4 Filtering Predicates and Range Conditions

Conditional Search Motivation: Enterprise databases hold millions of rows, but business queries target precise slices: employees in specific business units, salaries outside defined wage bands, or records with active supervisory relationships. How does SQL express complex multi-condition filters cleanly while safeguarding against subtle null-handling bugs? By using set filtering (IN, NOT IN) and boundary range operators (BETWEEN, NOT BETWEEN).

Filtering predicates in the WHERE clause evaluate boolean truth conditions for each candidate row. Rows evaluating to TRUE are retained; rows evaluating to FALSE or UNKNOWN (due to three-valued SQL logic) are discarded before any grouping or projection takes place.

Club Gatekeeper and Security Checkpoint Analogy: Think of filtering predicates as security checkpoints at an office facility:

  1. IN Predicate: An authorized guest list. If an employee's department badge matches any department code on the list, they pass through.
  2. BETWEEN Predicate: A physical clearance gate that checks height or vehicle weight against an allowed boundary span \([a, b]\). Any vehicle meeting or touching the boundary posts is permitted.
  3. NULL Boundary Checks: A visitor arriving with no badge at all. They cannot be verified on the whitelist or the blacklist, causing NOT IN logic to halt the queue if three-valued logic is misunderstood.

Where the analogy breaks: A human gatekeeper might exercise discretion when information is missing; a SQL query optimizer applies rigorous mathematical logic, immediately rejecting rows where truth evaluates to UNKNOWN.

41.4.1 Set Membership Filtering with IN and NOT IN

The IN predicate tests whether a column value matches any item within a specified list of literals. This membership testing replaces multiple chained OR conditions with a concise expression.

Worked Example 41.4.1 — Department Whitelisting with IN: To select employees working in department 30 or department 100, sorted by department:

SELECT 
    first_name, 
    last_name, 
    department_id 
FROM employees 
WHERE department_id IN (30, 100) 
ORDER BY department_id ASC;

Equivalent expanded boolean logic:

WHERE department_id = 30 OR department_id = 100

Using IN (30, 100) is far more concise and readable, especially when filtering across dozens of identifiers.

Conversely, the NOT IN predicate excludes rows belonging to the specified set:

SELECT 
    first_name, 
    last_name, 
    department_id 
FROM employees 
WHERE department_id NOT IN (30, 100);

41.4.2 Boundary Filtering with BETWEEN and NOT BETWEEN

The BETWEEN operator filters values within a closed numeric, date, or text range. SQL range conditions are strictly inclusive of both boundary endpoints.

Formal Mathematical Formulation: The set exclusion and range exclusion predicate formula is defined as: \[ D \notin \{30, 100\} \quad \land \quad S \notin [10000, 20000] \] where \(D \in \mathbb{Z}^+\) represents the department identifier, \(S \in \mathbb{R}^+\) represents the annual employee salary in USD, and \([10000, 20000]\) represents the closed inclusive salary interval.

Worked Example 41.4.2 — Compound Department and Salary Exclusion: To locate employees whose annual salary falls strictly outside the range of 10,000 USD to 20,000 USD, while also excluding departments 30 and 100:

SELECT 
    first_name, 
    last_name, 
    salary, 
    department_id 
FROM employees 
WHERE department_id NOT IN (30, 100) 
  AND salary NOT BETWEEN 10000 AND 20000;

Boundary Analysis:

  • An employee in department 50 with \(S = 9000\) is included (\(9000 < 10000\)).
  • An employee in department 80 with \(S = 10000\) is excluded (boundary value 10,000 is inside the closed interval \([10000, 20000]\)).
  • An employee in department 90 with \(S = 24000\) (president) is included (\(24000 > 20000\)).
  • Any employee in department 30 or 100 is excluded regardless of salary.

41.4.3 Handling Null and Non-Zero Manager Identifiers

In relational tables, unassigned attributes produce NULL values. For example, the top executive has no supervisor, resulting in a NULL in manager_id. To filter out records without a valid manager:

Worked Example 41.4.3 — Filtering Valid Manager Identifiers:

SELECT 
    employee_id, 
    first_name, 
    last_name, 
    manager_id 
FROM employees 
WHERE manager_id IS NOT NULL 
  AND manager_id != 0;

This condition guarantees that subsequent managerial analyses evaluate only valid supervisor-subordinate relationships, filtering out both unset nulls and legacy dummy sentinel zero values.

Scope & Assumptions:

  • Inclusive Range Boundaries: x BETWEEN a AND b expands algebraically to x >= a AND x <= b. If a > b (e.g., BETWEEN 20000 AND 10000), the predicate evaluates to FALSE for all non-null values.
  • Three-Valued Logic (3VL): SQL comparisons against NULL evaluate to UNKNOWN. In a WHERE filter, only rows evaluating to TRUE pass through; rows evaluating to FALSE or UNKNOWN are filtered out.

Common Pitfalls:

  1. The NOT IN (NULL) Catastrophe: If the exclusion set contains a NULL (e.g., department_id NOT IN (30, 100, NULL)), SQL expands this to:

\[ \text{dept} \ne 30 \land \text{dept} \ne 100 \land \text{dept} \ne \text{NULL} \] Because dept != NULL evaluates to UNKNOWN, the entire AND conjunction evaluates to UNKNOWN, resulting in zero rows returned across the entire table! Always ensure exclusion sets contain no nulls, or use NOT EXISTS.

  1. Timestamp BETWEEN Traps: Using BETWEEN '2023-01-01' AND '2023-01-31' on a TIMESTAMP column excludes any events occurring on January 31st after 00:00:00.000 because string date literals cast to midnight. Use half-open intervals (>= '2023-01-01' AND < '2023-02-01') instead.

41.4.4 Student Questions and Answers

Q: Is the BETWEEN operator in SQL inclusive or exclusive of its endpoints, or does assuming the BETWEEN operator excludes boundary values cause filtering bugs?

A: Assuming the BETWEEN operator excludes boundary values is a common beginner misconception. The BETWEEN operator is strictly inclusive of both boundary values. Writing salary BETWEEN 10000 AND 20000 matches any salary where 10000 <= salary <= 20000. Conversely, NOT BETWEEN excludes both boundary values, returning rows strictly less than 10000 or strictly greater than 20000.

41.5 Summary Aggregations and Statistical Calculations

Executive Intelligence Motivation: C-suite leadership rarely inspects individual row records; they need macro-level KPIs: what is our total corporate payroll obligation, what is our average salary, and how many distinct job titles exist across our workforce? How does SQL collapse millions of operational transactions into authoritative statistical summaries? Through aggregate functions and deduplicated cardinality counting.

Aggregate functions compute a single summary statistic over an entire table or subset of rows. By folding sets of values into scalar metrics, aggregations provide the mathematical foundation for business intelligence dashboards and executive financial reporting.

Funnel and Sieve Analogy: Think of SQL aggregations as funnels and sorting sieves:

  1. SUM, AVG, MIN, MAX: A funnel that accepts thousands of individual employee pay slips and condenses them into a single ledger card containing the boundary extremes, gross sum, and arithmetic mean.
  2. COUNT(*): A turnstile clicker that counts every person passing through the gate regardless of who they are.
  3. COUNT(DISTINCT): A specialized sieve with an internal memory bank. When an employee with the badge 'IT_PROG' passes through, it increments the count; when subsequent employees with 'IT_PROG' arrive, the sieve recognizes the duplicate badge and lets them pass without incrementing the counter.

Where the analogy breaks: A physical sieve gets clogged at high volume; database engines use in-memory hash tables and B-trees to deduplicate distinct keys at wire speed.

41.5.1 Summary Aggregate Metrics: MAX, MIN, SUM, and AVG

Aggregate functions compute a single summary statistic over a set of rows across the enterprise. Standard aggregate functions include:

  • MAX: Returns the largest value in a set.
  • MIN: Returns the smallest value in a set.
  • SUM: Returns the arithmetic sum of numeric values.
  • AVG: Returns the arithmetic mean of numeric values.

Formal Mathematical Formulation: The arithmetic mean sample salary formula is defined as: \[ \bar{S} = \frac{1}{N} \sum_{i=1}^{N} S_i \] where \(N \in \mathbb{Z}^+\) is the count of non-null employee salary records, \(S_i \in \mathbb{R}^+\) represents the salary of employee \(i\), and \(\bar{S} \in \mathbb{R}^+\) is the sample mean salary.

Worked Example 41.5.1 — Summarizing Compensation Metrics across Employees: To summarize compensation across the entire enterprise:

SELECT 
    MAX(salary) AS max_salary, 
    MIN(salary) AS min_salary, 
    SUM(salary) AS total_salary, 
    AVG(salary) AS average_salary 
FROM employees;

Database Output Across 107 Workers:

  • Maximum salary: \(24000.00 \text{ USD}\) (president)
  • Minimum salary: \(2100.00 \text{ USD}\)
  • Total salary sum: \(691400.00 \text{ USD}\)
  • Raw average salary: \(\frac{691400}{107} \approx 6461.68224299... \text{ USD}\)

41.5.2 Precision Rounding of Monetary Averages

Computing an average over monetary data often produces values with extended fractional digits. The raw average salary in the HR database produces about 6461.68224 USD. To format this figure for financial ledgers, we apply the ROUND function with a precision of two decimal places:

SELECT 
    ROUND(MAX(salary), 2) AS max_salary, 
    ROUND(MIN(salary), 2) AS min_salary, 
    ROUND(SUM(salary), 2) AS total_salary, 
    ROUND(AVG(salary), 2) AS average_salary 
FROM employees;

This produces a formatted average salary of 6,461.68 USD.

41.5.3 Distinct Value Counting vs. Total Row Counting

The COUNT function tallies the number of rows returned by a query. However, counting all rows differs fundamentally from counting distinct categories.

Reviewing the job_id column reveals repeated role assignments across personnel:

SELECT job_id FROM employees;

To retrieve unique job classifications without duplicates, we use the DISTINCT keyword:

SELECT DISTINCT job_id FROM employees;

Worked Example 41.5.2 — Counting Unique Job Designations: To calculate the total number of unique designations available in the company, we wrap DISTINCT inside COUNT:

SELECT COUNT(DISTINCT job_id) AS "Unique Designation" 
FROM employees;

This query returns 19 unique job designations across the enterprise.

Worked Example 41.5.3 — Verifying Total Workforce Size: To verify the overall workforce size alongside the average salary, we query COUNT(*):

SELECT 
    ROUND(AVG(salary), 2) AS average_salary, 
    COUNT(*) AS total_employees 
FROM employees;

Output Summary:

 average_salary | total_employees 
----------------+-----------------
        6461.68 |             107

This query confirms that the enterprise employs exactly 107 workers, with an overall average salary of 6,461.68 USD. Running SELECT * FROM employees; confirms that the table contains 107 rows.

Scope & Assumptions:

  • Null Handling in Aggregates: Aggregate functions (SUM, AVG, MIN, MAX, COUNT(col)) strictly ignore NULL values during calculation. For instance, if an employee has a NULL salary, AVG divides by \(N - 1\), not \(N\).
  • The Zero-Row Fallback: Running SUM, AVG, MIN, or MAX on an empty set returns NULL. However, running COUNT(*) or COUNT(col) on an empty set returns 0.

Common Pitfalls:

  1. Confusing COUNT(*) with COUNT(column): COUNT(*) counts all rows returned by the query regardless of contents. COUNT(column) counts only rows where the specified column contains a non-null value. If 5 employees have NULL commission percentages out of 100 rows, COUNT(*) returns 100 while COUNT(commission_pct) returns 95.
  2. Unrounded Floating Averages: Displaying raw floating-point averages on financial statements. In accounting ledgers, unrounded numbers like 6461.68224 fail financial validation audits; always apply ROUND(..., 2).

41.5.4 Student Questions and Answers

Q: What is the difference between COUNT(*) and COUNT(DISTINCT job_id)?

A: COUNT(*) counts every qualifying row returned by the query, including duplicate values across rows. In contrast, COUNT(DISTINCT job_id) first filters the set down to unique, distinct non-null job identifiers and then counts that deduplicated set, yielding 19 unique designations rather than 107 total rows.

41.6 Grouped Aggregations, Having Filters, and Array Aggregation

Segmented Analytics Motivation: An enterprise cannot set compensation policies by looking only at overall corporate averages; HR directors need breakdown metrics: what is the average salary within each department, which job roles exhibit extreme wage dispersion, and which departments have enough staff to justify specialized management? How does SQL divide tables into categorical subsets and filter aggregated group summaries? Through the GROUP BY and HAVING clauses, augmented by array aggregation.

In enterprise reporting, data rarely remains at the global table level. The GROUP BY clause collapses rows into homogeneous buckets based on shared categorical keys, while the HAVING clause filters those aggregated buckets according to group-level summary conditions.

Sorting Mailboxes and Post-Sorting Filter Analogy: Think of grouped aggregation as a postal sorting facility:

  1. WHERE Filter (Pre-Sort Screening): Security personnel screen incoming letters at the loading dock, shredding damaged or unauthorized envelopes before they enter the building.
  2. GROUP BY (Mailbox Partitioning): Workers place each surviving letter into a designated department mailbox slot (e.g., Department 30, Department 50, Department 100).
  3. Aggregate Evaluation (Weighing the Boxes): Once all letters are distributed into their pigeonholes, workers calculate the count, total weight, or average postage per box.
  4. HAVING Filter (Dispatch Threshold): The supervisor inspects the sorted mailboxes and dispatches only those holding more than 10 letters, leaving under-threshold boxes for later.
  5. ARRAY_AGG (Bundle Packing): Instead of calculating a single scalar weight, workers bundle all employee tracking numbers from a mailbox into a single organized carton.

Where the analogy breaks: Physical sorting is sequential; SQL query execution engines use parallel hash-aggregation and multi-threaded partition scans to group millions of records in fractions of a second.

41.6.1 Grouping Rows with GROUP BY

The GROUP BY clause partitions table records into subsets based on matching values in one or more grouping columns. When GROUP BY is present, aggregate functions evaluate separately within each subset.

To summarize salaries by department across the company:

SELECT 
    department_id, 
    MAX(salary) AS max_salary, 
    MIN(salary) AS min_salary, 
    SUM(salary) AS total_salary, 
    ROUND(AVG(salary), 2) AS average_salary 
FROM employees 
GROUP BY department_id;

Every non-aggregated column appearing in the SELECT list must be included in the GROUP BY clause. Omitting a selected column from GROUP BY causes a database execution error because the database engine cannot determine which individual row value to display for a multi-row group.

41.6.2 Wage Range Calculations across Job Roles

We can combine multiple aggregate expressions to calculate statistical dispersion. The wage spread within a job role is the difference between its highest and lowest paid workers.

The verbal description of this computation is: "the difference between the maximum and minimum salary is 21900 max salary minus min salary".

Across the entire company, the overall wage spread is: \[ 24000 - 2100 = 21900 \text{ USD} \]

Formal Mathematical Formulation: The wage range spread formula within job groups is defined as: \[ \Delta S_j = \max_{k \in G_j}(S_k) - \min_{k \in G_j}(S_k) \] where \(G_j\) denotes the set of employees assigned to job role \(j\), \(S_k \in \mathbb{R}^+\) is the salary of employee \(k\), and \(\Delta S_j \in \mathbb{R}^+\) is the wage difference within job role \(j\).

Worked Example 41.6.1 — Wage Range Spread across Job Classifications: To calculate the salary spread for each job role:

SELECT 
    job_id, 
    MAX(salary) AS max_salary, 
    MIN(salary) AS min_salary, 
    MAX(salary) - MIN(salary) AS difference 
FROM employees 
GROUP BY job_id;

Sample Department Breakdown:

  • For SA_REP (Sales Representative): \(\max = 11500\), \(\min = 6000\), \(\Delta S = 11500 - 6000 = \mathbf{5500 \text{ USD}}\).
  • For IT_PROG (Programmer): \(\max = 9000\), \(\min = 4200\), \(\Delta S = 9000 - 4200 = \mathbf{4800 \text{ USD}}\).
  • For AD_PRES (President): \(\max = 24000\), \(\min = 24000\), \(\Delta S = 24000 - 24000 = \mathbf{0 \text{ USD}}\).

Worked Example 41.6.2 — Lowest Salary Paid per Direct Manager: Similarly, we can evaluate compensation paid by managers. To determine the lowest salary paid by each manager, excluding null or zero manager IDs:

SELECT 
    manager_id, 
    MIN(salary) AS min_salary 
FROM employees 
WHERE manager_id IS NOT NULL 
  AND manager_id != 0 
GROUP BY manager_id 
ORDER BY min_salary ASC;

Sorting in ascending order reveals that the lowest paid subordinate in the company receives 2,100 USD. Manager 120 pays a minimum salary of 2,200 USD. Sorting in descending order reveals that manager 102 pays a minimum salary of 9,000 USD to subordinates.

41.6.3 Filtering Aggregated Groups with HAVING

SQL enforces a strict distinction between row-level filtering and group-level filtering:

  • WHERE: Filters individual rows before grouping and aggregation occur.
  • HAVING: Filters summarized groups after grouping and aggregation occur.

Worked Example 41.6.3 — Filtering High-Headcount Departments: Suppose management wants to analyze average department salaries, but only for departments employing more than 10 workers:

SELECT 
    department_id, 
    ROUND(AVG(salary), 2) AS average_salary, 
    COUNT(*) AS total_employees 
FROM employees 
GROUP BY department_id 
HAVING COUNT(*) > 10 
ORDER BY total_employees DESC;

The HAVING clause eliminates smaller departments (such as department 10, 60, or 90) from the output, displaying only major operational units like department 50 (Shipping with 45 employees) and department 80 (Sales with 34 employees).

Worked Example 41.6.4 — Pre-Filtering Rows with WHERE before Grouping: When filtering criteria depend on individual row values rather than group summaries, we apply WHERE. For example, to calculate the average salary for each job post while excluding IT programmers:

SELECT 
    job_id, 
    ROUND(AVG(salary), 0) AS average_salary 
FROM employees 
WHERE job_id != 'IT_PROG' 
GROUP BY job_id 
ORDER BY 2 DESC;

Here, WHERE job_id != 'IT_PROG' removes programmer records before calculating averages, ensuring their compensation does not influence the resulting job averages.

Worked Example 41.6.5 — Filtering Roles with Executive Compensation: To identify job roles where the maximum salary reaches or exceeds 5,000 USD:

SELECT 
    job_id, 
    MAX(salary) AS max_salary 
FROM employees 
GROUP BY job_id 
HAVING MAX(salary) >= 5000;

This filter confirms that programmers reach a maximum salary of 9,000 USD and human resource representatives reach 6,500 USD.

41.6.4 Array Aggregation for Grouped Entity Lists

In addition to computing scalar statistical values, PostgreSQL provides advanced aggregate functions such as ARRAY_AGG. The ARRAY_AGG function collects values from grouped rows into a structured array.

Worked Example 41.6.6 — Grouping Employee Identifiers with ARRAY_AGG: To list all employee IDs working within each job classification:

SELECT 
    job_id, 
    ARRAY_AGG(employee_id) AS all_employees_ids 
FROM employees 
GROUP BY job_id;

Instead of returning multiple rows per job, this query produces a single row per job classification containing a structured array of employee IDs:

  job_id   |          all_employees_ids          
-----------+-------------------------------------
 IT_PROG   | {103,104,105,106,107}
 SA_REP    | {150,151,152,153,154,155,...}
 AD_PRES   | {100}

This structured representation simplifies client-side entity deserialization and avoids duplicate key transmissions over API layers.

Scope & Assumptions:

  • Execution Order Dependency: Aggregate expressions cannot appear in the WHERE clause because WHERE filters rows before groups exist. Writing WHERE AVG(salary) > 5000 causes an immediate SQL syntax error.
  • HAVING Clause Redundancies: While SQL permits placing non-aggregate row filters in HAVING (e.g., HAVING department_id = 50), this is an anti-pattern. Filtering in WHERE discards rows earlier, reducing memory footprint and accelerating query execution.

Common Pitfalls:

  1. Attempting to Filter Aggregates with WHERE: Trying to write WHERE COUNT(*) > 10 instead of HAVING COUNT(*) > 10. The database parser will throw an error: aggregate functions are not allowed in WHERE.
  2. Missing GROUP BY Columns: Selecting a column that is neither wrapped in an aggregate function nor present in the GROUP BY clause. Standard SQL engines reject this query to preserve relational determinism.

41.6.5 Student Questions and Answers

Q: Why can we not use a WHERE clause to filter out departments with fewer than 10 employees, and why does attempting to filter aggregated group counts using a WHERE clause fail?

A: Attempting to filter aggregated group counts using a WHERE clause fails because the WHERE clause evaluates individual rows before grouping while filtering summarized groups after aggregation requires the HAVING clause. At the time WHERE executes, the database engine does not yet know the total row count of each department group.

  • The composite primary key (employee_id, start_date) in job_history, which enables an employee to hold multiple historical roles over time while preventing duplicate records on the same starting date.
  • The self-referencing foreign key manager_id in employees, which points back to employees.employee_id and contains a NULL for the top executive.
  • SQL Execution Order & Clause Visibility: Understand the canonical query evaluation lifecycle:

\[ \text{FROM} \;\to\; \text{WHERE} \;\to\; \text{GROUP BY} \;\to\; \text{HAVING} \;\to\; \text{SELECT} \;\to\; \text{ORDER BY} \;\to\; \text{LIMIT} \] Because WHERE executes before SELECT, column aliases defined in SELECT cannot be referenced in WHERE. However, ORDER BY executes after SELECT, allowing sort operations on column aliases or ordinal positions.

  • WHERE vs. HAVING Rules: Row-level filtering predicates belong strictly in WHERE. Group-level aggregate filters (e.g., COUNT(*) > 10 or AVG(salary) >= 5000) belong strictly in HAVING. Placing aggregate functions in the WHERE clause causes an immediate SQL syntax compilation error.
  • Range Predicates & Nullability: Remember that BETWEEN val1 AND val2 is strictly inclusive of both endpoints. Conversely, NOT BETWEEN val1 AND val2 excludes both endpoints. Be vigilant with NOT IN: if the exclusion list contains even a single NULL value, the condition evaluates to UNKNOWN and returns zero rows across the entire table.
  • String Parsing & Wildcard Matching: Distinguish between the multi-character wildcard % (matches zero or more arbitrary characters) and the single-character wildcard _ (matches exactly one character). Remember that string indexing in standard SQL functions (SUBSTR, POSITION) is 1-based, and POSITION returns 0 when a substring is not found.
  • Aggregation & Null Handling: Every non-aggregated column appearing in the SELECT list must be included in the GROUP BY clause. COUNT(*) counts all rows returned by the query regardless of contents, whereas COUNT(column) counts only rows where the specified column is non-null. Always apply ROUND(..., 2) to format monetary averages and percentage bonuses for financial accuracy.

Key Industry Applications

  • Human Resource Information Systems (HRIS) & Enterprise Resource Planning (ERP): Enterprise platforms like Workday, Oracle HCM, SAP SuccessFactors, and ServiceNow use normalized relational database architectures with strict primary and foreign key constraints to model global workforce transitions, organizational reporting hierarchies, and multi-region business units. By isolating geographic and departmental lookups from transactional employee records, enterprise schemas eliminate update anomalies when organizational restructuring occurs.
  • Automated Payroll Engines & Billing Pipelines: High-volume financial disbursement systems (such as ADP, Stripe, and Workday Payroll) rely on SQL scalar arithmetic expressions and currency precision rounding functions (ROUND) to calculate monthly salaries, percentage performance bonuses, and tax withholdings. Enforcing floating-point arithmetic safety (salary / 12.0) guarantees audit-proof balance sheets without integer truncation discrepancies.
  • Data Cleansing & Extract-Transform-Load (ETL) Pipelines: Text manipulation functions (SUBSTR, REPLACE, UPPER, LOWER, INITCAP, POSITION) standardize unformatted contact data, scrub Personally Identifiable Information (PII), and harmonize email domain suffixes across legacy databases during cloud migrations to Snowflake, Databricks, or AWS Redshift.
  • Executive Business Intelligence (BI) & Analytical Warehousing: Modern BI visualization tools (such as Tableau, PowerBI, Looker, and Metabase) translate user-facing dashboard filters into SQL queries utilizing GROUP BY, HAVING, COUNT(DISTINCT ...), and array aggregation (ARRAY_AGG) to analyze employee headcount distributions, detect departmental salary inequities, and audit compliance with labor regulations.
