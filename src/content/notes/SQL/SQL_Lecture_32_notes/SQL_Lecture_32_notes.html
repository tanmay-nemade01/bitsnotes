32.1 Creating the First SQL Function

32.1.1 The Basic Structure

What if a query you run ten times a day could be saved under a name and called with one line? That is exactly what a SQL function buys: a stored, named query with inputs, one output contract, and a body the engine runs on demand.

SQL functions are the easiest way to write functions in PostgreSQL. Any SQL command can live inside them, from a one-line arithmetic select to a long multi-table query. Think of a function as a labeled recipe card: the card lists the dish name, the ingredients it needs, what comes out, and the steps. The basic shape looks like this:

CREATE OR REPLACE FUNCTION fn_mysum(a integer, b integer)
RETURNS integer AS
$body$
  SELECT $1 + $2;
$body$
LANGUAGE SQL;

Read it piece by piece. CREATE OR REPLACE FUNCTION (the statement that builds the function, replacing any same-signature version instead of raising an error) comes first. Then comes the function name with its parameter list in parentheses: here fn_mysum takes a and b, each declared as integer. After the parameters, RETURNS states the output type — integer here, or void when nothing comes back. The body sits between dollar-quoting markers ($body$ here), and the trailing LANGUAGE SQL tells PostgreSQL which language the body is written in.

A SQL-language function has five parts: the CREATE OR REPLACE FUNCTION header, the name plus typed parameter list, the RETURNS output contract, the dollar-quoted body holding SQL statements, and the LANGUAGE SQL tag. Every part after the name is a promise the engine checks: the parameters fix how the call must look, and RETURNS fixes what shape the answer must take.

Three procedural languages ship built in: SQL, C, and PL/pgSQL. SQL is the simplest because the body is plain SQL with positional inputs. C is for low-level extensions, and PL/pgSQL adds variables, loops, and conditionals. This whole module stays with the SQL variant, which covers a large share of everyday reporting and data-cleaning work without any procedural machinery.

A naming habit pays off early. Prefixing personal functions, for example with fn_, keeps them visually apart from the many built-in system functions in the function browser. Variants such as a database name plus fn work the same way. Pick one scheme and stay with it, because the function list grows fast and a shared prefix makes personal functions easy to find. Later sections extend this into fn_api_ for report-facing helpers and fn_internal_ for operator helpers.

Across databases the same idea wears different syntax, and keeping one version is enough when the idea matches. In MySQL a function body uses BEGIN ... END with a DELIMITER switch and needs flags such as DETERMINISTIC, and there is no dollar quoting. In Snowflake a SQL UDF body is usually a single-quoted expression string rather than a dollar-quoted block. In Databricks SQL the CREATE FUNCTION ... RETURN shape is close in spirit. The PostgreSQL form below is the one this module drills; the cross-database point to carry along is only where behavior differs, such as MySQL requiring a return value in every function path.

32.1.2 Positional Parameters Dollar One and Dollar Two

Inside a SQL function body, input parameters are addressed by position: $1 is the first input, $2 the second, and so on. The demo function takes two integers and returns their sum with a plain SELECT $1 + $2. The names declared in the parameter list (a, b) document intent, while the body refers to the values by position. So a and $1 are the same value at run time, and b and $2 are the same value — the name is for readers, the position is for the engine.

Once the CREATE statement reports success, the function appears in the schema browser under functions. Its property panel mirrors the declaration back: owner, schema (typically public), language SQL, return type integer, and the argument list integer, integer. The panel also exposes volatility settings and an estimated execution cost. Volatility tells the planner whether the function always returns the same answer for the same inputs (IMMUTABLE), depends only on database state (STABLE), or can return a fresh answer on every call (VOLATILE). Cost tells the planner how expensive one call is. A cheap lookup keeps a low cost; an expensive computation deserves a higher number so the query planner can account for it. Those planner details come up again with query planning, but the fields are worth noticing from day one.

Scope: SQL-language functions shine for queries parameterized by a few inputs: filters, aggregates, lookups. Assumption: inputs arrive positionally and the body is a plain query, so there are no variables, loops, or branches here. When logic needs row-by-row decisions or error handling, that is the signal to reach for PL/pgSQL instead of forcing it into SQL.

Picture the call as filling numbered slots. SELECT fn_mysum(1, 2) drops 1 into slot $1 and 2 into slot $2, then the body computes 1 + 2. Change the call to SELECT fn_mysum(10, 20) and the same body computes 10 + 20. The body never changes; only the slot contents do.

32.1.3 Calling a Function

Functions are used through SELECT, unlike procedures which need an explicit call statement. That single fact decides how you test: every function in this module is exercised with a SELECT call, and many later functions also appear inside bigger queries or in the FROM clause.

Build the adder, then run it twice. First create it with the statement from 32.1.1. Then call SELECT fn_mysum(1, 2); — the engine binds $1 = 1 and $2 = 2, runs SELECT 1 + 2, and returns 3. Call SELECT fn_mysum(10, 20); — now $1 = 10 and $2 = 20, the body runs SELECT 10 + 20, and the answer is 30. Sense-check: both answers equal ordinary addition, so the function adds two integers and returns their sum.

The call must supply arguments matching the declared types. Calling fn_mysum with no arguments fails with an error saying no function matches the given name and argument types, possibly suggesting an explicit type cast. That message looks alarming the first time, but the cause is plain: the engine cannot find a zero-argument version of a function that was declared with two integer parameters. PostgreSQL allows several functions to share one name with different signatures (overloading), so matching uses the name plus the argument types together, not the name alone.

Q: Why does calling the new function without arguments fail, even though the function name is spelled right? A: PostgreSQL matches a call by name plus argument types. Since the function was declared with two integer parameters, a call with no arguments matches nothing, and the engine reports that no function matches the given name and argument types. Passing two integers fixes it at once.

32.1.4 The Body Is a String

One design point deserves emphasis because it gives PostgreSQL functions much of their power. The code inside the body is passed to the engine as a string. That string layer turns the function into a black box for the execution machinery: anything the chosen language can express may travel inside that string, from trivial selects to long dynamic statements built up piece by piece. Other database engines attach function code directly to the statement instead of passing it as a string, so this flexibility is a genuine differentiator. Never underrate what can ride inside that string.

A kitchen analogy helps: the CREATE FUNCTION line is the menu entry with the dish name and portion promise, while the string body is the sealed recipe envelope handed to the kitchen. The menu never changes, but the envelope can hold a one-line recipe or a banquet plan. The analogy breaks at one point: a kitchen reads intent, while the engine parses text strictly, so a typo inside the string fails at run time rather than being smoothed over.

Recap: a SQL function is a named, typed, stored query — header, parameters, return contract, string body, language tag. Bridge: the string-body idea explains the next section directly, because passing code as a string is exactly why quoting rules matter so much.

In day-to-day work this pattern shows up wherever a team repeats a query: dashboards call fn_api_* names instead of pasting SQL, and data-quality jobs call audit functions on a schedule. Storefront counters, admin health pages, and account summaries all read more cleanly when the SQL lives in one named place.

32.2 Dollar Quoting

32.2.1 The Escaping Problem

What breaks first when a function body itself contains quotes? The quoting around the body, not the logic inside it.

Wrapping the body in single quotes works until the body itself contains quotes. A string constant such as I am a string constant already forces escaping when passed as a quoted literal, and a function whose logic contains quoted text gets painful fast: every inner quote needs escaping, and the statement becomes hard to read and easy to break. A body with one WHERE country = 'NA' filter inside single-quote wrapping needs each inner quote doubled, and a body with several such filters turns into an escaping puzzle where one missed quote fails the whole statement.

Take a body that filters on a text value, for example SELECT * FROM employees WHERE country = 'NA'. Wrapped in single quotes, the outer quotes clash with the inner 'NA' quotes, so each inner quote must be doubled to ''NA''. The statement still runs, but reading it means counting quotes instead of reading logic — and the takeaway is that the escaping burden grows with every quoted literal added. Sense-check: if adding one filter doubles the quoting work, a body with three filters is already unmaintainable.

Snowflake is the useful contrast here rather than a second version of the same rule: its SQL UDF bodies are single-quoted expression strings (for example 'p_width * p_length'), so Snowflake authors keep living with the single-quote wrapping that PostgreSQL authors escape through dollar quoting. Same function idea, different quoting habit — and that is why PostgreSQL's answer below is worth learning as a PostgreSQL-specific tool.

32.2.2 Dollar Dollar and Dollar Body

The fix is dollar quoting. Instead of opening and closing the body with single quotes, open and close it with $$:

CREATE OR REPLACE FUNCTION fn_mysum(a integer, b integer)
RETURNS integer AS
$$
  SELECT $1 + $2;
$$
LANGUAGE SQL;

Dollar quoting (a body delimiter made of dollar signs instead of single quotes, written $$ or with a tag such as $body$) passes everything between the markers to the engine untouched, so inner single quotes need no escaping. The opening and closing markers must match exactly, or creation fails.

Everything between the markers travels to the engine untouched, so inner single quotes need no escaping. SELECT fn_mysum(10, 20) still returns 30, exactly as before — the quoting changed, the logic did not.

One collision remains. In Perl and in Bash-style scripting, $$ already means something (the process id), so code in those languages can clash with bare $$ markers. The answer is a tagged marker such as $body$:

CREATE OR REPLACE FUNCTION fn_mysum(a integer, b integer)
RETURNS integer AS
$body$
  SELECT $1 + $2;
$body$
LANGUAGE SQL;

Convert the country-update body to dollar quoting. With $$ ... $$ markers around UPDATE employees SET country = 'NA' WHERE country IS NULL, the 'NA' quotes pass through untouched and the statement stays readable. If the body itself ever contained a $$ sequence (a Perl snippet would), switching the markers to $body$ ... $body$ removes the clash. The working rule is to default to $$ and reach for a tag only on collision. Sense-check: the query result is identical under both markers, so quoting is pure packaging.

Scope: dollar quoting is the default habit for every function body from here on. Assumption: the tag is arbitrary text between dollars, so pick something readable ($body$, $func$) and keep it consistent. A mismatched pair ($body$ opened, $$ closed) is the classic failure — the engine waits for the true closing tag and reports an unterminated string.

From here on, dollar quoting is the default habit for every function body, with tagged variants kept in reserve for bodies that contain conflicting dollar sequences.

Recap: single quotes break down as bodies gain quoted literals; $$ fixes it and $body$ fixes the leftover clash. Bridge: with quoting settled, the module can now move through the return-type ladder, starting with functions that return nothing at all.

32.3 Functions Returning Nothing

32.3.1 Returns Void

When should a function promise no answer at all? When its job is to change the database, not to report a value — a cleanup sweep, a stamp-down of missing fields, a status flip.

A function that runs a statement but sends nothing back declares RETURNS void. void (a return type meaning no result comes back, only an empty marker) turns the function into an action: it acts, then returns an empty display. This is one point on a spectrum the module keeps extending: return nothing, return a single value, return a composite row, return a set of rows, return a full table.

RETURNS void marks an action-only function. The body runs INSERT, UPDATE, or DELETE work, the caller invokes it with SELECT function_name(), and the only visible result is an empty marker — the real effect is the changed rows.

Picture a light switch versus a thermometer. A thermometer function returns a reading (a single value). A light-switch function flips state and reports nothing beyond "done". The analogy breaks in one place: a real switch gives tactile feedback, while a void function gives only the empty marker, so confirming the effect means querying the table afterward.

Scope: void fits maintenance writes with no inputs or with filter inputs. Assumption: the caller checks the side effect separately, since the return value carries no information. Do not use void when the caller needs the new value back — that needs a scalar or composite return instead.

32.3.2 Worked Example: Filling Empty Country Values

The demo runs against the Northwind database and its employees table, which carries columns such as employee name, city, region, and country. The task: find every employee whose country is empty and stamp it NA.

Create the sweep, seed a test row, run it, and verify. The function body is one UPDATE:

CREATE OR REPLACE FUNCTION fn_employees_update_country()
RETURNS void AS
$$
  UPDATE employees
  SET country = 'NA'
  WHERE country IS NULL;
$$
LANGUAGE SQL;

No parameters are declared because none are needed. After creating it, refresh the function browser to confirm it exists, then seed the test: set one employee's country to null (say the row with employee id 1) and browse the table to confirm the null sits in the listing. Run SELECT fn_employees_update_country(); — the call returns an empty (null) display, which is exactly what void promises, while the update itself has run. Browse again: the null is now NA. Then restore the original value (USA for that row) so later queries and demos see clean data. Sense-check: exactly one row changed from null to NA, so the filter hit only empty countries. Housekeeping like that matters: one demo's leftover null becomes the next demo's mystery bug.

Recap: void means action without an answer, verified by re-reading the table. Bridge: the next rung on the ladder returns a single value — and with a value comes the strictest contract in the module, the return-type match.

Nightly cleanup jobs, backfill sweeps, and flag resets across orders, customers, and catalog tables all fit this mold: one named action, run on schedule, confirmed by a follow-up query.

32.4 Functions Returning a Single Value

32.4.1 The Return Type Contract

Why would a function create cleanly and then explode on its very first call? Because creation checks syntax while the first call checks the type promise.

The shape is familiar; the one load-bearing detail is that the declared return type must match what the query actually produces:

CREATE OR REPLACE FUNCTION fn_product_min_price()
RETURNS real AS
$$
  SELECT MIN(unit_price) FROM products;
$$
LANGUAGE SQL;

The return type contract (the rule that the RETURNS declaration must equal the true type of the query result) is checked at call time, not at creation time. Creation accepts a wrong declaration silently; the first call fails with a return-type mismatch naming the declared versus actual types.

Northwind-style catalog work leans on exactly these one-value helpers — cheapest item, priciest item, biggest order — because a dashboard can call them by name instead of repeating long queries. Think of each as a labeled gauge on a control panel: one gauge reads the minimum price, another the maximum, and the dashboard never sees the SQL behind the needle. The analogy breaks only in that a gauge is wired once, while a function must re-prove its wiring (the type contract) on every call.

Scope: scalar functions fit single-number answers: minima, maxima, counts, totals. Assumption: the body's single column has one knowable type — read it off the column or expression before writing the declaration. Guessing integer for a real column or a double precision sum is the most common failure in this module.

32.4.2 Worked Example: Cheapest and Priciest Product

Browsing products ordered by unit_price ascending shows the cheapest item at 2.5 and the priciest near 263.5. The unit price column has type real, so the function must declare RETURNS real.

Declare wrong, watch it fail, fix with one word. First declare RETURNS integer and create — creation succeeds. Call SELECT fn_product_min_price() and it fails with a return-type mismatch: declared integer, actual real. Change the single word to RETURNS real, recreate, and call again — the answer is 2.5, matching the bottom of the ascending browse. The mirror function needs no new ideas:

CREATE OR REPLACE FUNCTION fn_product_max_price()
RETURNS real AS
$$
  SELECT MAX(unit_price) FROM products;
$$
LANGUAGE SQL;

It returns 263.5, matching the top of the ascending browse. Sense-check: min sits below every other price and max sits above them, so both ends of the browse agree with the functions.

Q: The function was created without errors, so why does calling it complain about a type mismatch? A: Creation only checks syntax, not the type contract. The mismatch surfaces at call time, when the engine compares the declared return type against what the query truly yields. Aligning the declaration with the real column type (real here, not integer) resolves it.

Exam note: return-type mismatches are a favorite trap — when a function fails right after creation, compare the declared type against the true column type first.

32.4.3 Worked Example: Biggest and Smallest Order

The order_details table holds one row per line item with order id, product id, unit price, and quantity. Some orders span two rows (line items such as quantities 1, 2, 4, 8 appear twice for one order), so per-order totals need aggregation. The line-item amount is unit price times quantity, and the plan groups by order id, sums the amounts, and takes the maximum through a subquery:

Build per-order totals inside, keep the extreme outside. The inner query sums each order's lines; the outer query keeps the largest:

CREATE OR REPLACE FUNCTION fn_biggest_order()
RETURNS double precision AS
$$
  SELECT MAX(order_amount) FROM (
    SELECT SUM(unit_price * quantity) AS order_amount
    FROM order_details
    GROUP BY order_id
  ) AS total_amount;
$$
LANGUAGE SQL;

Step through it: the inner GROUP BY order_id collapses every order's lines into one total (for example an order with lines of 40 and 60 yields 100). The outer MAX keeps the largest of those totals. Note the type journey: an early RETURNS real draft fails because the summed amount arrives as double precision, so the declaration changes to double precision. SELECT fn_biggest_order() returns 17250. Swapping MAX for MIN with the same body yields the smallest order, 12.50. Sense-check: the biggest total dwarfs a typical order and the smallest is a single cheap line, so both extremes sit where intuition puts them. The lesson compounds: each aggregate or arithmetic expression has its own true type, and the declaration must follow the expression, not the other way round.

COUNT(*) arrives as bigint, MIN/MAX over a real column stay real, and SUM over real money expressions widens to double precision. Guessing the narrower type is the trap; reading the expression's true type is the fix.

Recap: scalar functions live or die on the return-type contract — creation forgives, the first call does not. Bridge: with single values solid, the next step packages the same mold as named APIs that whole reports can call.

Cheapest-item, priciest-item, and biggest-order gauges back catalog dashboards and storefront highlights directly: one name per number, refreshed by calling the function instead of redeploying application code.

32.5 API-Style Count Functions

32.5.1 One Function Per Business Question

What happens when five reports each paste their own copy of "how many customers"? They drift apart. What happens when all five call one name? They stay in agreement forever.

A function can serve as a tiny named API for an application: instead of pasting a long query into every report, the report calls a name. The convention used here prefixes such helpers with fn_api_, so customer-facing helpers sort together and read as an intentional public surface rather than stray experiments. Three near-identical helpers show the pattern.

An API-style function (a scalar helper named fn_api_* that answers one business question, such as a total count) hides the table and the aggregate behind a stable name. Reports call the name; only the function body knows the SQL.

Start from the raw query, narrow it, wrap it, call it. Getting the customer count starts from SELECT * FROM customers (91 rows) and narrows to SELECT COUNT(*) FROM customers. A count returns bigint, so the function declares RETURNS bigint:

CREATE OR REPLACE FUNCTION fn_api_get_total_customers()
RETURNS bigint AS
$$
  SELECT COUNT(*) FROM customers;
$$
LANGUAGE SQL;

SELECT fn_api_get_total_customers() returns 91. The same mold gives fn_api_get_total_products (77 rows from the products table) and fn_api_get_total_orders (830 order rows), each returning bigint. Because each returns a single row and column, any of them can also slot into a larger query as a subquery — for example comparing one customer's order count against the 830-order total. Sense-check: each function answer equals its raw COUNT(*) run by hand, so the wrappers add naming without changing numbers.

Think of the three helpers as labeled jars on a shelf: one jar holds the customer total, one the product total, one the order total. A report grabs a jar instead of counting the warehouse. The analogy breaks where freshness matters: a jar's contents sit still, while each function call recounts live, so the numbers never go stale.

Scope: one function per business question works while each question is a single aggregate. Assumption: the underlying tables keep their meaning — renaming a table or redefining "active customer" means updating the function once, which is exactly the maintenance win. The failure mode is letting near-duplicate helpers (fn_api_get_total_customers, fn_total_customers) multiply; one canonical name per question avoids that drift.

Totals like these feed admin dashboards, health checks, and storefront counters directly — one name per number, no duplicated SQL across the codebase. MySQL teams reach the same shape with a DETERMINISTIC READS SQL DATA function returning a count, and Snowflake teams with a scalar SQL UDF — the PostgreSQL RETURNS bigint wrapper here is one dialect's packaging of the same named-number idea.

Recap: one business question, one fn_api_* name, one bigint answer. Bridge: the identical mold doubles as a data-quality monitor — the next section points it at empty fields instead of totals.

32.6 Data-Health Count Functions

32.6.1 Counting Empty Fields

How do you notice a catalog quietly rotting — 22 missing fax numbers today, 60 missing regions next month? You stop eyeballing tables and start calling audit functions that return the rot as a number.

The same one-value mold doubles as a data-quality monitor. Instead of re-running an audit query by hand, a scheduled job or an administrator calls a named function and watches the number.

A data-health function (a scalar count over a WHERE ... IS NULL filter, wrapped in an fn_api_* name) turns "how dirty is this column" into a callable number. The filter names the gap; the count sizes it; the schedule watches it move.

Audit fax, then audit region, and compare the scale of the two gaps. The fax audit looks for customers with no fax number:

CREATE OR REPLACE FUNCTION fn_api_total_customers_empty_fax()
RETURNS bigint AS
$$
  SELECT COUNT(*) FROM customers WHERE fax IS NULL;
$$
LANGUAGE SQL;

Browsing shows 22 customers with null fax, and the function returns 22. The region audit follows the same lines with WHERE region IS NULL and returns 60 — a far larger gap, and exactly the kind of figure that should prompt a cleanup pass. Sense-check: 22 of 91 customers missing fax is plausible for a catalog where fax is optional, while 60 of 91 missing region signals a genuinely under-filled column rather than a few stragglers.

Picture each audit as a smoke detector wired to one column. The detector does not fix the wiring; it reports a number, and a rising number pages someone. The analogy breaks at response time: a smoke detector screams on its own, while an audit function only answers when called, so the schedule (nightly job, weekly review) is part of the design.

Scope: null-count audits fit optional-but-expected columns such as fax and region. Assumption: null genuinely means missing — if a column uses empty strings or sentinel values instead, the IS NULL filter undercounts and the audit lies. Check the column's missing-value convention before trusting the number.

Pushing repetitive audit checks into functions means they can run on a schedule, get owned by a database administrator, and keep the database healthy without anyone remembering the underlying SQL. The Databricks-side cousin is a scheduled query counting nulls per partition; the idea travels, only the scheduler syntax changes.

Recap: aim the count mold at IS NULL filters and gaps become callable numbers. Bridge: so far every function answers a fixed question — the next step takes an input and answers it per customer.

32.7 Parameterized Totals per Customer

32.7.1 Naming Inputs to Avoid Collisions

What goes wrong when a parameter is named exactly like the column it filters? The engine can no longer tell your input apart from the table's own field.

Parameters arrive by position ($1, $2), but giving each a clear declared name keeps bodies readable. One sharp habit: prefix parameter names (for example p_customerid) so they cannot be confused with real column names such as customer_id. A bare parameter named customer_id sitting next to a column called customer_id is a mix-up waiting to happen; the p_ prefix removes the ambiguity at a glance.

The p_ prefix convention marks every parameter as an input (p_customerid) distinct from the column it compares against (customer_id). The body still binds positionally, but readers — and future editors — see at a glance which side of WHERE customer_id = p_customerid is the table and which is the caller.

The customer id column in customers (the primary key) is character-typed, so the parameter must be declared with the matching character type. Declaring it integer while the column holds character codes fails the call the same way a wrong RETURNS type does — the contract lesson from 32.4 applies to inputs as well as outputs.

Named parameters also differ usefully across databases without changing the lesson: MySQL names parameters and references them by name in the body, Snowflake's SQL UDFs reference named parameters directly in the expression, and PostgreSQL SQL functions declare names but bind by position. Same readability goal, different binding rule — and the p_ prefix habit pays off in all three.

32.7.2 Worked Example: Total Orders by Customer

The question: how many orders has one customer placed? Joining orders to customers with a natural join over the shared customer id yields all 830 orders joined with customer data. Filtering to one id (VINET in the demo) leaves 5 rows, and wrapping the filtered query in COUNT(*) gives the answer 5.

Develop with a literal, then swap in the parameter. First run the join with a hard-coded 'VINET' filter and confirm 5 rows, then wrap it in COUNT(*) and confirm the answer 5. Only then generalize:

CREATE OR REPLACE FUNCTION fn_api_customer_total_orders(p_customerid bpchar)
RETURNS bigint AS
$$
  SELECT COUNT(*)
  FROM orders NATURAL JOIN customers
  WHERE customer_id = p_customerid;
$$
LANGUAGE SQL;

The WHERE clause compares the column against the parameter instead of a hard-coded literal — that single substitution is what turns a one-off query into a reusable function. SELECT fn_api_customer_total_orders('VINET') returns 5. A second probe with another customer id returns 0, and a direct WHERE customer_id = check against the tables confirms the zero is genuine, not a bug — that customer simply has no orders. Sense-check: VINET's 5 sits comfortably inside the 830-order total, and the zero case proves the function reports absence honestly instead of erroring. The reusable form beats the hard-coded form every time: any id goes in, the right count comes out, and the function composes as a subquery inside still larger queries.

A natural join merges same-named columns silently, which is convenient until two tables share more than the intended key. If a join ever returns a surprising row count, expand it to an explicit ON clause and confirm the join keys before blaming the parameter.

Recap: prefix parameters with p_, match the column's type, develop on a literal, then swap in the name. Bridge: one customer plus one filter gave a count — the next problem needs three tables and a money expression to find that customer's largest order.

Per-customer totals power account pages ("your 5 orders"), support consoles, and loyalty tiers: one function, every customer id, no per-customer SQL pasted anywhere.

32.8 Largest Order per Customer

32.8.1 Building Across Three Tables

How do you find one customer's biggest order when prices live in one table, quantities in another, and the customer link in a third? You join all three, price every line, then let a subquery decide.

The task grows teeth: for a given customer, find their largest single order amount. Three tables cooperate — orders (the order header), order_details (unit price, quantity, discount per line), and products (names). Exploration starts wide (SELECT * with natural joins across all three), then narrows to one customer (ALFKI, 12 line rows), then to the columns that matter: order id, customer id, product name, unit price, quantity.

Each line's total follows the spoken recipe — take unit price times quantity, subtract the discount field:

\[ \text{line\_total} = (\text{unit\_price} \times \text{quantity}) - \text{discount} \]

where \(\text{unit\_price}\) is the per-unit price of the line item (real), \(\text{quantity}\) is the number of units on that line (smallint), and \(\text{discount}\) is the line discount amount in the same money units. The spoken description is "unit price into quantity, minus the discount field"; the formula above is the reconciled form of exactly that recipe. Concretely, a line with unit price 40, quantity 3, and discount 5 prices as \((40 \times 3) - 5 = 115\).

The line-total expression (unit_price * quantity - discount) is the money atom of this module: every per-order and per-product total below sums this expression over different groupings. Read the type off the expression — the product of real and smallint widened by summation arrives as double precision, which is why the functions below declare RETURNS double precision.

Eyeballing ALFKI's lines suggests candidates near 878 and near 1084 (one order combining 683.74, 377, and 23.75 lines), but eyeballing is not an answer — the query must decide. That discipline (explore on literals, decide with aggregation) repeats in every layered function from here on.

32.8.2 The Subquery That Decides

The inner query sums line totals per order for the chosen customer; the outer query keeps the maximum:

Sum per order inside, keep the maximum outside. Build the inner query first on a hard-coded 'ALFKI' filter, confirm one row per order id with plausible totals, then wrap it:

CREATE OR REPLACE FUNCTION fn_api_customer_largest_order(p_customerid bpchar)
RETURNS double precision AS
$$
  SELECT MAX(order_amount) FROM (
    SELECT SUM(unit_price * quantity - discount) AS order_amount
    FROM order_details NATURAL JOIN orders
    WHERE orders.customer_id = p_customerid
    GROUP BY orders.order_id
  ) AS total_amount;
$$
LANGUAGE SQL;

The inner GROUP BY orders.order_id turns ALFKI's 12 lines into one total per order; the outer MAX keeps the largest, near 1085. Sense-check: the winning total equals the sum of its known lines (683.74 + 377 + 23.75 lands near 1084), so the aggregate agrees with hand addition.

Two stumbles on the way carry the real teaching. First, declaring RETURNS bigint fails because the summed amount arrives as double precision — the familiar type-contract lesson from 32.4, now with aggregates. Second, forgetting the WHERE clause against the parameter returns the global maximum (17249-ish across all customers) instead of ALFKI's own figure near 1085. The parameter must actually be used; declaring it is not enough. With both fixed, the function returns the customer's true largest order.

A missing customer filter is the silent killer: the query runs, the number looks plausible, and it is completely wrong — some other customer's order. Whenever a parameterized aggregate returns a suspiciously round or large figure, check the WHERE clause before doubting the math.

Exam note: "correct query, wrong scope" bugs — right aggregates, missing filter — are exactly what examiners love to plant. Always confirm the parameter appears in the WHERE clause, not just the signature.

Largest-order figures feed account summaries, credit reviews, and "your biggest purchase" highlights — anywhere one customer id must produce one money number backed by three joined tables.

32.9 Most Ordered Product per Customer

32.9.1 Thinking in Quantities, Not Prices

What does a customer buy most — measured in units, not money? That one-word switch from "priciest" to "most" changes the grouping, the aggregate, and the answer.

A sibling question: which product has a given customer ordered most? The output is a product name (character type), the input a customer id. The measure here is total quantity per product, not money — a deliberate contrast with 32.8, where money was the point. Sketching the joins first (orders natural-joined to order_details, plus products for names) and eyeballing one demo customer (11 order lines) shows the trap: one order id can carry three different products, so grouping must be by product, not by order.

Question Measure Group by Aggregate
Largest order (32.8) money per order order_id SUM(price * qty - discount), then MAX
Most ordered product (this section) units per product product_id SUM(quantity), then top-ranked

When to pick which: money-per-order answers "how big"; units-per-product answers "what habit". A customer whose largest order was a single expensive machine may still order one cheap part most often — the two questions give different winners by design.

Rank-then-name is a three-layer shape: the inner layer aggregates and ranks (GROUP BY product_id, ORDER BY total DESC, LIMIT 1), the middle layer extracts the winning id, and the outer layer maps the id to a display name through the dimension table.

32.9.2 Layered Subqueries With Limit One

The inner query sums quantity per product id for the customer and orders the sums descending:

Build inside-out, testing each layer on a literal customer id before wrapping it. Layer one ranks products by units:

SELECT product_id, SUM(quantity) AS total_quantity
FROM order_details NATURAL JOIN orders
WHERE orders.customer_id = p_customerid
GROUP BY product_id
ORDER BY 2 DESC
LIMIT 1;

For the demo customer the top of that listing shows product id 34 with total quantity 20 (several products tie near 20, and later work will return all ties as multiple rows — for now the function keeps just the first). LIMIT 1 is doing honest work: the question asks for the single most-ordered product. Layer two keeps just that winning id; layer three maps it to a name:

CREATE OR REPLACE FUNCTION fn_api_customer_most_ordered_product(p_customerid bpchar)
RETURNS varchar AS
$$
  SELECT product_name FROM products
  WHERE product_id IN (
    SELECT product_id FROM (
      SELECT product_id, SUM(quantity) AS total_quantity
      FROM order_details NATURAL JOIN orders
      WHERE orders.customer_id = p_customerid
      GROUP BY product_id
      ORDER BY 2 DESC
      LIMIT 1
    ) AS product_order
  );
$$
LANGUAGE SQL;

Hard-code the customer id while developing, confirm the winning id by hand, then swap in p_customerid at the end. Sense-check: the returned name belongs to the id that topped the ranked listing, so the name lookup did not drift to a neighboring row.

Recommendation-style questions ("what does this customer buy most?") reduce to exactly this shape — group, sum, rank, map back to a name. The same three layers serve "most watched show", "most ordered dish", and "most visited page" once the tables change.

Scope: LIMIT 1 answers "the single winner" and silently drops ties. Assumption: one winner is acceptable for now. When ties matter (two products both at 20 units), the fix is a set-returning variant that keeps every top-ranked row instead of truncating — exactly the SETOF shape the module reaches in 32.11.

Recap: quantities group by product, money groups by order — pick the grouping that matches the question, then rank and name. Bridge: single-value answers are exhausted now; the next rung returns a whole row at once.

32.10 Composite Results

32.10.1 Returns With a Table Name

What if the answer is not one number but an entire order — id, date, customer, freight, all at once? Then the return type is the table itself.

A function that returns one whole row declares RETURNS with the table name. A composite value (one whole row packed as a single value, shown as field values separated by commas inside parentheses with text fields in double quotes) is what comes back. The demo fetches the latest order:

Fetch the latest order as one packed row. Sorting by date descending and, as a tiebreak, by order id descending guarantees the truly latest row when several orders share a date:

CREATE OR REPLACE FUNCTION fn_api_latest_order()
RETURNS orders AS
$$
  SELECT * FROM orders
  ORDER BY order_date DESC, order_id DESC
  LIMIT 1;
$$
LANGUAGE SQL;

SELECT fn_api_latest_order() returns order 11077 in composite form, something like (11077, ..., "1998-05-06", ...). Adding LIMIT 1 is deliberate: the query promises one row, so the query should ask for exactly one and spare the server useless work. Sense-check: 11077 sits at the very top of the date-descending browse, so no later order exists.

RETURNS orders promises exactly one orders row. The contract has two halves: the query must yield the table's full column set in order (SELECT * does this naturally), and it must yield exactly one row (LIMIT 1 plus a total ordering enforces this).

Picture the composite as a packed suitcase: everything for one order zipped into a single value. Convenient to carry, awkward to search — which is why the next subsection unpacks it three ways. Snowflake's parallel is a table function returning a shaped row set; PostgreSQL's composite is the single-row end of that same spectrum.

32.10.2 Three Ways to Unpack a Composite

The raw composite is honest but awkward, so three access styles unpack it. First, expand the whole row into table form by wrapping the call in parentheses and adding .*:

SELECT (fn_api_latest_order()).*;

All three styles agree on order 11077. The .* form lays the full row out as a readable table. Dot notation picks one field: (fn_api_latest_order()).order_id returns 11077 and (fn_api_latest_order()).customer_id returns that order's customer. Functional style puts the field first: order_id(fn_api_latest_order()) and customer_id(fn_api_latest_order()) return the same two values. The choice is readability at the call site, and the sense-check is that all three agree field for field.

Second, pick one field with dot notation: (fn_api_latest_order()).order_id or (fn_api_latest_order()).customer_id. Third, use functional style with the field name first: order_id(fn_api_latest_order()), customer_id(fn_api_latest_order()). All three agree; the choice is readability at the call site.

The parentheses around the call are load-bearing: (fn_api_latest_order()).* works, while fn_api_latest_order().* parses the .* against the wrong target. Forgetting the outer pair is the most common syntax slip in this section.

32.10.3 Worked Example: Latest Order in a Date Range

Parameters compose naturally with composites. The range variant takes two dates and keeps the same ordering:

Pin the window, keep the ordering, cross-check by hand. The function filters with BETWEEN and orders exactly as before:

CREATE OR REPLACE FUNCTION fn_api_order_latest_by_date_range(p_from date, p_to date)
RETURNS orders AS
$$
  SELECT * FROM orders
  WHERE order_date BETWEEN p_from AND p_to
  ORDER BY order_date DESC, order_id DESC
  LIMIT 1;
$$
LANGUAGE SQL;

Calling it over an early-1997 window returns order 11070; narrowing the window to October 1997 returns 10700. Each answer cross-checks by running the equivalent plain SELECT with the same bounds — the function and the hand-written query agree, which is how trust in a new function gets built. The table-form wrapper (fn_api_order_latest_by_date_range(...)).* keeps the output readable. Sense-check: each returned order's date falls inside its window and no same-window row sorts above it.

32.10.4 Worked Example: Most Recently Hired Employee

The same mold fits the employees table via its hire date:

Same shape, new table, one ordering column. Hire dates rarely tie, so a single descending sort suffices:

CREATE OR REPLACE FUNCTION fn_api_employee_latest_hire()
RETURNS employees AS
$$
  SELECT * FROM employees
  ORDER BY hire_date DESC
  LIMIT 1;
$$
LANGUAGE SQL;

The query surfaces employee 9 (hired in 1994); the function returns that row in composite form, and the .* wrapper lays it out as a table. Single-field access works as before: (fn_api_employee_latest_hire()).first_name, or functional style first_name(fn_api_employee_latest_hire()). Sense-check: no employee row carries a later hire date, so employee 9 is genuinely the most recent hire.

Recap: a table name as the return type packs one full row; .*, dot access, and functional style unpack it. Bridge: one row generalizes to many rows next — the declaration grows one word, SETOF.

Latest-order and latest-hire lookups back "newest activity" panels and onboarding reports: one call, one full row, unpacked at the call site.

32.11 Set-Returning Functions

32.11.1 Returns Setof With a Table Name

What changes when the answer is not one row but every row matching a filter — all hires from 1993, all products above a threshold? The return type becomes a set.

When the answer is many rows, the declaration becomes RETURNS SETOF plus the table name. SETOF (a return-type modifier meaning zero or more rows of the named shape) turns the function from a single-row lookup into a parameterized report. The demo lists every employee hired in a given year:

Filter by year, develop on a literal, then parameterize. EXTRACT(YEAR FROM hire_date) pulls the calendar year out of each hire date for comparison against the integer parameter:

CREATE OR REPLACE FUNCTION fn_employees_hire_by_year(p_year integer)
RETURNS SETOF employees AS
$$
  SELECT * FROM employees
  WHERE EXTRACT(YEAR FROM hire_date) = p_year;
$$
LANGUAGE SQL;

Develop with a hard-coded year first (WHERE EXTRACT(YEAR FROM hire_date) = 1992) to confirm the filter, then swap in p_year. Calling with 1992 returns two rows; 1993 returns three. Appending .* — SELECT (fn_employees_hire_by_year(1992)).* — lays the set out as a readable table. Sense-check: the row counts match hand-run SELECT counts for those years, so the parameterization did not leak or drop rows.

RETURNS SETOF employees promises any number of full employees rows. The body is an ordinary filtered SELECT; the function adds the input (here the year) and the name. Callers treat the result as a row source, not a single value.

32.11.2 Worked Example: Products Above a Sales Threshold

A richer set-returning function lists every product whose total sales clear an input amount. The inner query aggregates per product from order_details, using the line-total recipe of unit price times quantity minus discount:

Aggregate per product, filter with HAVING, map ids to rows. Build the inner query on a hard-coded threshold first:

SELECT product_id, SUM(unit_price * quantity - discount) AS product_total_sale
FROM order_details
GROUP BY product_id
HAVING SUM(unit_price * quantity - discount) > p_amount;

Two SQL rules bite here and both are worth memorizing. First, the alias product_total_sale cannot appear in HAVING — the full expression must be repeated, because HAVING is evaluated before the select-list alias exists. Second, the development rhythm stays the same: hard-code a threshold (testing shows one product clears a high bar, forty clear a low one), confirm, then substitute the parameter. The outer layer turns qualifying ids into full product rows:

CREATE OR REPLACE FUNCTION fn_api_products_total_amount(p_amount integer)
RETURNS SETOF products AS
$$
  SELECT * FROM products
  WHERE product_id IN (
    SELECT product_id FROM (
      SELECT product_id, SUM(unit_price * quantity - discount) AS product_total_sale
      FROM order_details
      GROUP BY product_id
      HAVING SUM(unit_price * quantity - discount) > p_amount
    ) AS t1
  );
$$
LANGUAGE SQL;

A threshold of 100000 leaves a single product (id 38); a threshold of 1 leaves dozens. The .* wrapper again renders the set as a table. Sense-check: id 38's summed sales exceed 100000 by hand addition, and lowering the bar only adds rows, never removes the qualifier — monotonic behavior confirms the filter direction.

Scope: HAVING filters groups after aggregation; WHERE filters rows before it. Assumption: the threshold compares against the summed expression, so it belongs in HAVING with the full expression repeated. Putting the aggregate condition in WHERE fails outright — aggregates do not exist yet at that stage.

Exam note: HAVING with a repeated expression (no aliases) plus an IN subquery is a compact, testable pattern — expect it in applied questions. Bridge: a function returning rows can do more than sit behind SELECT — it can stand in the FROM clause as a table.

Hire-year cohorts and sales-threshold product lists are ready-made team reports: human resources calls one name with a year, merchandising calls another with a money bar, and neither rewrites the joins.

32.12 Functions as Table Sources

32.12.1 Select From a Function

Why call a function and then pick columns, when you can query the function as if it were a table? That is the second calling convention, and it composes.

So far every call has looked like SELECT function_name(args). But a set-returning function can also sit in the FROM clause and behave like a table:

Query the function like a table. The function runs, yields its rows, and the outer query picks columns exactly as if a real table stood there:

SELECT first_name, last_name
FROM fn_employees_hire_by_year(1993);

This returns the three 1993 hires by name. Asking for hire_date as well, or restricting to chosen columns of the product-threshold function (SELECT product_id, product_name FROM fn_api_products_total_amount(10000)), works identically — the outer query filters and sorts the function's output freely. Sense-check: the names match the SELECT-style call row for row, so the two conventions agree.

A set-returning function in FROM is a parameterized view: the arguments fix the slice (which year, which threshold), and the outer query treats the result as an ordinary row source with selectable columns, WHERE filters, and ORDER BY.

Picture a vending machine versus a buffet. SELECT fn(...) is the vending slot: one packaged item drops out. SELECT ... FROM fn(...) is the buffet: the function lays out the tray, and the outer query takes the columns it wants. The analogy breaks on freshness: both forms run the function live, so neither is a stale copy.

This is how teams ship curated datasets — the function hides the joins and the business rules, and analysts query a clean name with plain SELECT ... FROM. Snowflake leans on the same idea for table functions joined to other tables, and Databricks SQL composes table-valued functions identically; only the creation syntax differs per engine.

Scope: only set-returning functions belong in FROM. A scalar function placed there yields one row with one column, which parses but confuses every reader — keep scalars behind SELECT and sets in FROM.

Recap: SELECT fn(args) fetches the value; SELECT ... FROM fn(args) queries the set. Bridge: the final return shape generalizes further — instead of borrowing a table's shape, the function declares its own columns.

32.13 Column Order in Returns Table

32.13.1 The Declaration Must Mirror the Query

What happens when the declaration lists money first and quantity second, but the query emits them the other way round? The engine trusts positions, not names — and the answers come out silently swapped.

RETURNS TABLE functions declare each output column with its type, and the declaration must mirror the query output column for column, in the same order, with matching types. Reordering the declared columns while leaving the query untouched breaks the contract. The engine answers with a return-type mismatch naming the offending position — actual smallint where double precision was declared at column five, for example.

The mirror rule (the RETURNS TABLE column list must match the query's select list position by position in order and type) is mechanical and absolute. Column names do not rescue a mis-ordered declaration; positions decide.

Swap two declared columns and watch position five complain. Suppose the query emits (order_id, customer_id, product_name, unit_price, quantity, total) where quantity is smallint and total is double precision. Declaring the last two as (total_order double precision, quantity smallint) — money before count — fails with a mismatch at the fifth position: actual smallint where double precision was declared. Restoring the declaration to (quantity smallint, total_order double precision) fixes it, and the call returns correctly shaped rows. Sense-check: each column's values now sit under the right header, with counts looking like counts and money looking like money.

Even a well-meant cast at the wrong position is dangerous: it can line up a quantity column against a money column and silently produce nonsense shaped like success. The rule is mechanical and absolute: declare columns in exactly the order the query emits them. A mismatch error is good news — it means the engine caught the swap; a silent misalignment is the real danger, so eyeball the first rows after every new RETURNS TABLE function.

(The same material appears twice in the source material with identical wording; it is consolidated here rather than repeated.)

Recap: positions decide, names do not — mirror the query exactly. Bridge: order is one of three RETURNS TABLE rules; the next section adds "declare every column" and puts all three to work.

32.14 Full Returns Table Functions

32.14.1 Declaring Every Column

What if the report needs six columns, but the declaration lists five? The engine refuses — a shaped result must be fully described.

RETURNS TABLE turns a function into a shaped result set with named, typed columns. The non-negotiable companion rule: declare all columns. If the query emits six columns, the declaration lists six columns with their true types — omitting one fails with a mismatch (the statement returns too many columns for the declared record).

A RETURNS TABLE declaration is a full schema for the result: every emitted column appears once, in query order, with its true type. Together with the mirror rule from 32.13 and type matching from 32.4, this forms the testable trio — order, completeness, types.

Snowflake's table functions follow the same contract with a RETURNS TABLE(col type, ...) clause and a single wrapped query, and Databricks SQL shapes results similarly. The PostgreSQL habit transfers directly: read each column's type off a hand-run query, then write the declaration to match.

32.14.2 Worked Example: Top Orders per Customer

The goal: given a customer id and a row limit, return that customer's top orders with order id, customer id, product name, unit price, quantity, and a computed total. Exploration joins order_details to orders to products with natural joins, filters to one customer, and orders by the line total descending.

Develop on literals, read the types off the result, then declare. First run the join with a sample id and a limit of 2, then 10, eyeballing the ranking (173, 126, 115, 114, ...) to confirm the ordering is genuinely descending. Read each column's true type off that result, and only then write the declaration to match:

CREATE OR REPLACE FUNCTION fn_api_customer_top_orders(p_customerid bpchar, p_limit integer)
RETURNS TABLE (
  order_id smallint,
  customer_id bpchar,
  product_name varchar,
  unit_price real,
  quantity smallint,
  total_order double precision
) AS
$$
  SELECT orders.order_id, orders.customer_id, products.product_name,
         order_details.unit_price, order_details.quantity,
         (order_details.unit_price * order_details.quantity - order_details.discount) AS total_order
  FROM order_details NATURAL JOIN orders NATURAL JOIN products
  WHERE orders.customer_id = p_customerid
  ORDER BY (order_details.unit_price * order_details.quantity - order_details.discount) DESC
  LIMIT p_limit;
$$
LANGUAGE SQL;

Calls read naturally: SELECT * FROM fn_api_customer_top_orders('VINET', 10) lists ten rows; changing 10 to 1 or 2 returns just the top one or two. Sense-check: the first row's total equals its unit price times quantity minus discount by hand arithmetic, and every row carries the requested customer id. Two construction traps are worth memorizing. Forgetting the type on one parameter (p_limit integer) fails creation with "customer id does not exist"-style confusion — every parameter needs its type spelled out. And when the return shape must change (dropping the total column, say), CREATE OR REPLACE refuses with a row-type complaint: drop the function first, then recreate it. That two-step is normal, not a bug.

CREATE OR REPLACE cannot change an existing function's return row type. Any reshape — adding, dropping, or retyping a column — requires DROP FUNCTION first, then a fresh CREATE. Trying to replace in place wastes a debugging cycle; dropping first is the documented path.

Exam note: the trio of RETURNS TABLE rules — mirror the order, declare every column, match every type — is directly testable, and the drop-before-reshape requirement is an easy follow-up question. Bridge: with shapes mastered, one convenience remains — parameters that carry their own fallbacks.

Top-N per-customer tables drive account pages and "your largest purchases" widgets: one function, a customer id, a row cap, and a fully shaped answer the front end renders directly.

32.15 Default Parameter Values

32.15.1 The Syntax and Its One Rule

What if most callers pass the same value — a 7 percent lift, a limit of 10 — and only occasional callers differ? Give the parameter a fallback so routine calls stay short.

A parameter can carry a fallback used when the caller omits it: declare the name, the type, then DEFAULT plus the value. A default parameter (an input with a stored fallback, written name type DEFAULT value) lets callers omit trailing arguments.

Omit two arguments and watch the fallbacks fire. The adder with two defaulted inputs:

CREATE OR REPLACE FUNCTION fn_sum_three(x integer, y integer DEFAULT 10, z integer DEFAULT 10)
RETURNS integer AS
$$
  SELECT x + y + z;
$$
LANGUAGE SQL;

In ordinary prose this computes:

\[ x + y + z \]

where \(x\), \(y\), and \(z\) are the three integer inputs. SELECT fn_sum_three(1, 2, 3) binds all three and returns 6. SELECT fn_sum_three(1) binds \(x = 1\) while \(y\) and \(z\) fall back to 10 each, computing \(1 + 10 + 10\) for 21. Sense-check: 21 equals 1 plus two tens, so the missing arguments genuinely defaulted rather than erroring.

The one default rule: once a parameter has a default, every parameter after it must have one too. Removing the default from z while y keeps its default fails creation — parameters after one with a default value must also have defaults. Likewise a bare DEFAULT with no value is a syntax error.

The practical dodge: push the defaulted parameters to the end of the list so the fewest declarations need defaults. Note a related gotcha — altering the parameter list of an existing function generally means dropping and recreating it rather than replacing in place, the same drop-before-reshape lesson from 32.14.

MySQL expresses the same idea only partially (procedure parameters take IN/OUT modes without inline defaults in older versions, so callers pass everything), while Snowflake and Databricks SQL accept DEFAULT on function parameters much like PostgreSQL. The trailing-defaults rule is the portable takeaway: defaults chain to the end of the list or they fail.

32.15.2 Worked Example: A 7 Percent Price Lift

The products table carries unit prices, and the task is a function that reprices each row upward by a percentage defaulting to 7 percent. The verbal recipe — take the unit price, multiply by the increase factor, divide by 100 — reconstructs as:

\[ \text{new\_price} = \text{unit\_price} \times \frac{\text{pct}}{100} \]

where \(\text{unit\_price}\) is the product's current price (real), \(\text{pct}\) is the numeric increase factor defaulting to 107, and the result is double precision. The narration says "7 percent" throughout with default 107 in the code; one passing mention of "10 percent" is a slip, and 107 matches a 7 percent lift (\(100 + 7\)), so the reconciled formula above uses 107. Concretely, a price of 18 reprices as \(18 \times 107 / 100 = 19.26\).

The function's first parameter is a whole products row, so the body can reference its columns directly:

Pass a whole row, omit the percentage, let 107 apply. The row-typed first parameter accepts products.* at the call site:

CREATE OR REPLACE FUNCTION fn_api_new_price(p_products products, p_pct numeric DEFAULT 107)
RETURNS double precision AS
$$
  SELECT p_products.unit_price * p_pct / 100;
$$
LANGUAGE SQL;

Used as a computed column, it sits beside the raw price:

SELECT product_id, product_name, unit_price,
       fn_api_new_price(products.*) AS new_price
FROM products;

Each row's price grows by the factor: 18 becomes 19.26, 19 becomes 20.33, 10 becomes 10.7. Passing products.* feeds the entire row where the function expects a products value, and omitting the second argument lets the 107 default apply. Sense-check: each new price equals its old price times 1.07, so the factor is a genuine 7 percent lift. Repricing, fee-adding, and tax-inclusive columns all fit this mold — one defaulted function, reused across every report that needs the adjusted figure.

A row-typed parameter plus SELECT fn(...) computes one row per call; used as a select-list expression over a table it computes per row, which is the intent here. The trap is calling it bare (SELECT fn_api_new_price(...)) with no row value — the engine has nothing to price. Always feed it alias.* from a real table reference.

Recap: defaults shorten routine calls; trailing position is mandatory; row-typed inputs compose as computed columns. Bridge: parameters can also wrap views — the next section adds the one thing views lack, an input.

32.16 Functions Over Views

32.16.1 A View of Server Activity

Views rank every active query, but a view cannot take a "top N" argument. What adds the input without duplicating the view logic? A thin function on top.

Functions need not read tables directly — a view works just as well, which makes views a handy staging layer for logic the function then parameterizes. The demo builds an operations view over pg_stat_activity, the system view that exposes live server processes. pg_stat_activity (a built-in PostgreSQL system view listing every live backend with its process id, user, current query, and timings) is the raw feed; the view below shapes it.

Shape the raw feed into a ranked activity view. Filtering to active state and keeping process id, user name, current query, query start time, plus a run-time column (current timestamp minus query start), ordered by run time descending, surfaces the longest-running statements first:

CREATE OR REPLACE VIEW vw_active_queries AS
SELECT pid, usename, query, query_start,
       (NOW() - query_start) AS run_time
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY 4 DESC;

With a single developer connected, the view shows just one or two rows; on a busy server the same view ranks every active process by how long it has been running. Sense-check: the top row's run time is the largest interval, so the ordering genuinely surfaces the longest-running statement first.

The view owns the shaping (which columns, which filter, which ordering); the function, added next, owns the parameterization (how many rows). Keeping those two jobs separate means the ranking logic lives in exactly one place.

32.16.2 Parameterizing the View With a Function

The function wraps the view and adds the one thing views lack — an input, here a row cap:

Wrap the view, pass a cap, read it two ways. The wrapper is three lines:

CREATE OR REPLACE FUNCTION fn_internal_active_queries(p_limit integer)
RETURNS SETOF vw_active_queries AS
$$
  SELECT * FROM vw_active_queries LIMIT p_limit;
$$
LANGUAGE SQL;

The internal prefix signals audience: this helper is for operators, not for customer-facing code. SELECT fn_internal_active_queries(10) returns the ten longest-running statements in composite form; the FROM style (SELECT * FROM fn_internal_active_queries(10)) renders the same answer as a table. Sense-check: both forms return the same ten rows in the same order, so the calling convention changes packaging, not content.

Operations teams live in views like this — wrapping them in functions adds pagination, filtering, and a stable name the on-call runbook can quote. The same layered shape serves slow-query dashboards, lock monitors, and connection audits: shape once in a view, slice per need with a function.

RETURNS SETOF vw_active_queries pins the function to the view's current column set. Altering the view's columns without recreating the function invites a row-type mismatch at call time — change both together, and re-verify with a capped call.

Recap: views shape, functions parameterize — one view plus a thin wrapper beats duplicated logic. Bridge: the module closes with the full life cycle: creating was the start, dropping is the end.

32.17 Dropping Functions

32.17.1 Drop Function Syntax

How do you remove exactly one overload when three functions share a name — without taking the dependents down with it? The argument list picks the target; the cascade flag picks the blast radius.

Removing a function uses a short statement with three optional refinements:

DROP FUNCTION IF EXISTS fn_name(argument_types) CASCADE;
DROP FUNCTION IF EXISTS fn_name(argument_types) RESTRICT;

DROP FUNCTION takes three independent options: IF EXISTS softens a missing target from an error to a notice, the parenthesized argument types select which overload goes, and CASCADE versus RESTRICT decides whether dependents fall with it or block the drop.

IF EXISTS turns a missing function from an error into a notice — a save point for scripts that may run twice. The argument list selects which overload goes: because PostgreSQL allows several functions to share one name with different parameters, the types in parentheses say exactly which one is meant. DROP FUNCTION fn_mysum(integer, integer) removes only the two-integer adder, leaving any same-named variant with different types untouched. When the name is unique within its schema, the list may be omitted; supplying a wrong or empty list then fails with "function does not exist," which is really a complaint about the signature, not the name.

CASCADE drops dependent objects along with the function, and RESTRICT refuses the drop while dependents exist. Treat CASCADE as a red flag. The safer practice is to remove dependents deliberately, one by one, down to the root — the same caution applies to dropping tables, views, and anything else with dependents. Keep function names globally unique across schemas and document them; a unique name plus a careful drop is how functions disappear without collateral damage.

MySQL's DROP FUNCTION IF EXISTS and Snowflake's DROP FUNCTION ... (signature) rhyme with this shape; the portable caution is identical — cascade flags deserve a second look in every engine.

Scope: RESTRICT is the safe default — it refuses rather than destroys. Assumption: you know the dependents before dropping. When unsure, query the dependency catalog (or attempt the RESTRICT drop and read the refusal) instead of gambling on CASCADE.

32.17.2 Worked Example: Create, Call, Drop

A small adder carries the whole life cycle:

Create it, prove it, remove it, prove it is gone. The adder uses named parameters in the body here (SQL functions accept the names for readability while binding positionally):

CREATE OR REPLACE FUNCTION fn_sum(x integer, y integer)
RETURNS integer AS
$$
  SELECT x + y;
$$
LANGUAGE SQL;

SELECT fn_sum(1, 2) returns 3. Then DROP FUNCTION fn_sum; removes it (unique name, no dependents, so neither argument list nor cascade is needed), and calling it again fails with "function does not exist" — the expected epitaph. Sense-check: the create-call-drop-call sequence proves both directions — the function worked while present and is truly absent afterward, not merely hidden.

Recap: create with a contract, call by name plus types, drop by exact signature with RESTRICT unless you mean otherwise. That life cycle — declaration, parameterized use, careful removal — is the whole module in miniature.

Adder-style throwaway functions are the standard scratch workflow: prototype in the database, verify against hand queries, then drop or promote to a documented fn_api_* name.

Exam Guidance Summary

Return-type discipline dominates this module's testable surface. Expect questions that hand over a function with a wrongly declared return type (integer declared, real or double precision produced) and ask for the fix — creation succeeds, the first call fails, and the repair is aligning the declaration with the true column or expression type. Expect the aggregate-to-type pairings too: COUNT pairs with bigint, while summed money expressions arrive as double precision.

Exam note: the RETURNS TABLE trio — columns in query order, every column declared, every type matched — plus the drop-before-reshape requirement round out the high-yield list. A changed parameter list or return shape usually means drop plus recreate, not replace in place.

Parameter rules are short and checkable: defaults must extend to the end of the list, and a changed parameter list usually means drop plus recreate. Composite access styles ((.*), dot-field, functional form) and the FROM-clause table-source form are natural multiple-choice or short-answer targets. Scope bugs — right aggregates with a missing customer filter returning the global maximum — are the classic applied trap: always check that the parameter appears in the WHERE clause. Finally, HAVING with a repeated expression (aliases are invisible there) plus an IN subquery is a compact pattern worth recognizing on sight.

Exam note: when a function fails right after creation, compare the declared type against the true column type first; when a parameterized aggregate returns a suspiciously large figure, check the WHERE clause before doubting the math.

Key Industry Applications

One-value API helpers (customer, product, and order totals) back dashboards and storefront counters so application code calls names instead of repeating SQL. A merchandising dashboard calls fn_api_get_total_products for its headline count, and an admin health page polls the order total — each number recomputed live on every call, never pasted and left to rot.

Data-health counters (empty fax, empty region) run on a schedule under a database administrator's ownership to keep catalog data clean. The fax audit returning 22 and the region audit returning 60 are triage inputs: the small gap gets a manual pass, the large gap triggers a cleanup project, and the trend over weeks shows whether quality is improving.

Per-customer analytics (order counts, largest order, most-ordered product, top-N orders) power account pages and recommendation-style features. VINET's 5 orders, ALFKI's largest order near 1085, and the most-ordered product name all render on one customer profile from three tiny calls. The repricing function extends the pattern to computed columns: every product row gains a 7 percent-lifted price without duplicating the arithmetic across reports.

Operations views over pg_stat_activity wrapped in parameterized functions give on-call engineers a stable, paginated window into live server load. The runbook quotes fn_internal_active_queries(10) instead of a five-line query, and the same wrapper shape serves lock monitors and slow-query reviews — shape once in a view, slice per need with a function.
