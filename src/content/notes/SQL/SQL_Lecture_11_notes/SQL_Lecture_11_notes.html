# Explore PostgreSQL Constraints

11.1 Introduction to Constraints

Why should a database enforce rules if modern applications already validate user input before sending it across the network? What happens when multiple microservices, background ETL jobs, or direct database administration scripts write to the same table?

A constraint — a declarative rule that incoming data must satisfy — acts as the ultimate gatekeeper for a relational database. Think of it like a strict security guard stationed at the door of a restricted building. Every incoming row and every updated value must present valid credentials that satisfy the stated criteria. When the data satisfies the rule, the gatekeeper lets it through and commits the transaction. When the data violates the rule, the gatekeeper refuses entry, aborts the write, and returns a descriptive error code. This mechanism ensures that invalid or corrupt data never enters the storage layer.

The fundamental motivation for database constraints is rooted in business logic and systemic data integrity. What counts as "invalid" depends entirely on the operating rules of the organization. A business may require that every customer has a unique email address, employee salaries remain strictly greater than zero, order dates never occur in the future, and every line item references an existing product in the catalog. Declaring these requirements as constraints inside the database guarantees consistency regardless of which external application, script, or user executes the write.

In relational database theory, integrity constraints are categorized into three core tiers:

  1. Domain Integrity: Restricts the values that can appear in a given column (data types, NOT NULL, and CHECK constraints).
  2. Entity Integrity: Ensures that every row in a table is uniquely identifiable and not duplicated (PRIMARY KEY and UNIQUE constraints).
  3. Referential Integrity: Ensures that relationships between tables remain consistent and prevents orphaned child records (FOREIGN KEY constraints).

11.1.1 Table Level and Column Level

Constraints can be defined at two distinct structural levels: the column level and the table level.

  1. Column-Level Constraints: A column-level constraint is declared directly alongside a single column definition during table creation. It applies exclusively to that individual column.
   CREATE TABLE employees (
       employee_id INT PRIMARY KEY,
       email TEXT UNIQUE,
       salary NUMERIC(10, 2) CHECK (salary > 0)
   );
  1. Table-Level Constraints: A table-level constraint is declared after all table columns have been defined. Table-level syntax is mandatory whenever a constraint spans two or more columns (such as composite primary keys or cross-column checks), and it allows database administrators to assign explicit, meaningful names to each constraint using the CONSTRAINT keyword.
   CREATE TABLE employees (
       employee_id INT,
       first_name TEXT,
       last_name TEXT,
       email TEXT,
       salary NUMERIC(10, 2),
       CONSTRAINT pk_employees PRIMARY KEY (employee_id),
       CONSTRAINT uq_employees_email UNIQUE (email),
       CONSTRAINT chk_salary_positive CHECK (salary > 0)
   );

In database architecture, column-level rules guard individual fields, while table-level rules define relational shapes and multi-column combinations.

11.1.2 The Main Constraint Types in PostgreSQL

Six foundational constraint types appear across database systems:

  • NOT NULL: Prevents NULL (missing/unknown) values from being stored in a column. Primarily declared as a column-level rule.
  • UNIQUE: Guarantees that all non-null values in a column (or combination of columns) remain distinct across all rows.
  • DEFAULT: Supplies an automatic fallback value when an INSERT statement omits that column. (Technically a column default definition, often grouped with constraints).
  • PRIMARY KEY: The definitive entity identifier for a table. Combines UNIQUE and NOT NULL properties into a single enforced rule.
  • FOREIGN KEY: Enforces referential integrity by establishing a parent-child relationship between tables, ensuring child rows reference valid parent keys.
  • CHECK: Enforces an arbitrary Boolean expression; incoming rows are accepted only if the condition evaluates to TRUE or UNKNOWN.

11.1.3 Worked Examples

#### Worked Example 1: Refusing Duplicate Email Records (UNIQUE Constraint)

  • Business Rule: Every customer in the system must possess a distinct email address.
  • Setup:
  CREATE TABLE customers (
      customer_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      email TEXT UNIQUE
  );
  • Execution:
  1. Insert initial valid customer:
     INSERT INTO customers (email) VALUES ('ada@example.com');
     -- Output: INSERT 0 1 (Success)
  1. Attempt to insert a second customer with the identical email:
     INSERT INTO customers (email) VALUES ('ada@example.com');
  • Result: PostgreSQL rejects the second write and throws an error:

ERROR: duplicate key value violates unique constraint "customers_email_key" DETAIL: Key (email)=(ada@example.com) already exists.

  • Sense Check: The gatekeeper inspected the incoming 'ada@example.com', matched it against the internal index, and blocked duplicate insertion.

#### Worked Example 2: Enforcing Valid Pay Ranges (CHECK Constraint)

  • Business Rule: Employee compensation must be strictly positive (greater than zero).
  • Setup:
  CREATE TABLE staff (
      staff_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      name TEXT NOT NULL,
      salary NUMERIC(10, 2) CHECK (salary > 0)
  );
  • Execution:
  1. Insert staff member with positive pay:
     INSERT INTO staff (name, salary) VALUES ('Alice', 100.00);
     -- Output: INSERT 0 1 (Success)
  1. Attempt to insert staff member with negative pay:
     INSERT INTO staff (name, salary) VALUES ('Bob', -100.00);
  • Result: PostgreSQL immediately terminates the statement:

ERROR: new row for relation "staff" violates check constraint "staff_salary_check" DETAIL: Failing row contains (2, Bob, -100.00).

  • Sense Check: The expression salary > 0 evaluated to FALSE for -100.00, preventing corruption of financial records.

Scope & Common Pitfalls:

  • Relying Exclusively on Application Validation: Validating user input only in frontend JavaScript or backend application code leaves the database vulnerable to bulk ETL scripts, third-party connectors, or administrative SQL queries that bypass the application layer.
  • Over-constraining Without Business Consensus: Applying overzealous constraints (e.g., rigid regex phone checks) before data schemas mature can disrupt customer onboarding and cause unnecessary production transaction rollbacks.

Q: What decides whether data is invalid? A: Business logic decides. The organization defines the operational rules of the domain, and the database constraint translates that logic into a deterministic test. PostgreSQL then evaluates the test and blocks any row that fails.

Constraints form the primary defense perimeter of database integrity. While column-level constraints protect single fields, table-level constraints enforce complex multi-column and relational invariants across the entire schema. The simplest and most ubiquitous of these guards is NOT NULL, which eliminates missing data ambiguities.

#### Real-World & Domain Connection In production banking and e-commerce platforms, constraints prevent severe financial discrepancies. E-commerce systems rely on CHECK (quantity > 0) and FOREIGN KEY (product_id) REFERENCES products(id) to ensure orders cannot buy negative inventory or link to ghost items. Financial ledgers use constraints to verify that debit and credit amounts remain strictly positive, ensuring accounting equations hold true at the physical database layer.

11.2 NOT NULL Constraint

If a customer submits an online registration form and leaves their phone number blank, does that mean they do not own a phone, or that they simply chose not to disclose it? How does a database distinguish between a value that is zero, a value that is empty text, and a value that is completely missing?

In relational database systems, NULL represents an unknown, missing, or inapplicable data state. It is fundamentally distinct from an empty string '' or the numeric value 0. An empty string is a concrete, known character sequence containing zero characters. Zero is a precise, known integer on the number line. In contrast, NULL signifies that no data exists or the information is unknown.

Because NULL signifies missing information, standard comparison operators cannot evaluate it using standard two-valued logic. In SQL three-valued logic (3VL: TRUE, FALSE, UNKNOWN), any direct comparison with NULL using equality or inequality operators (such as tag = NULL or tag != NULL) yields UNKNOWN. To deterministically test whether an attribute holds a value or is absent, SQL provides the dedicated Boolean operators IS NULL and IS NOT NULL.

The governing invariant of the NOT NULL constraint requires that for every tuple in relation \(R\), the attribute value must be present: \[ \text{Valid}(x) \iff (x \text{ IS NOT NULL}) \] where \(x\) denotes the candidate attribute value. If \(x\) is NULL, the expression evaluates to FALSE, the write is rejected, and the database issues a constraint violation error.

11.2.1 Syntax for a New Table

The column-level syntax for enforcing non-nullability during table creation is:

CREATE TABLE table_name (
    column_name data_type NOT NULL
);

In this definition, NOT NULL is declared immediately after the data type. PostgreSQL binds the non-null requirement to the column's catalog entry, ensuring that every subsequent INSERT and UPDATE validates the condition \(x \text{ IS NOT NULL}\).

11.2.2 Creating and Inspecting a Sample Table

Consider a demonstration table named table_n_n (short for table not null):

CREATE TABLE table_n_n (
    id SERIAL PRIMARY KEY,
    tag TEXT NOT NULL
);

Here, id is an auto-incrementing surrogate primary key, and tag is a variable-length text attribute marked NOT NULL.

SELECT * FROM table_n_n;

Initially, the table contains zero rows, but the metadata catalog records attnotnull = true for tag.

In pgAdmin, database administrators can verify this rule via two visual inspection paths:

  1. Column Properties: In the Object Browser, navigate to Schemas → public → Tables → table_n_n → Columns. Right-click tag and select Properties. Under the Definition tab, the Not Null? switch displays Yes.
  2. Table Properties: Right-click table_n_n, select Properties, and switch to the Columns tab. Both id (via its primary key definition) and tag show a checkmark under the Not Null column.

While graphical tools allow toggling this setting, production database changes should always be executed through version-controlled DDL scripts.

11.2.3 Worked Examples

#### Worked Examples: Testing Values Against NOT NULL

  • Test 1: Inserting Valid Non-Empty Text
  INSERT INTO table_n_n (tag) VALUES ('Adam');
  SELECT * FROM table_n_n;
  • Result: Success (INSERT 0 1). One row stored with tag = 'Adam'. The predicate 'Adam' IS NOT NULL evaluates to TRUE.
  • Test 2: Inserting an Explicit NULL
  INSERT INTO table_n_n (tag) VALUES (NULL);
  • Result: Transaction aborted.

ERROR: null value in column "tag" of relation "table_n_n" violates not-null constraint DETAIL: Failing row contains (2, null).

  • Sense Check: The predicate NULL IS NOT NULL evaluates to FALSE, so the engine blocks the write.
  • Test 3: Inserting an Empty String ('')
  INSERT INTO table_n_n (tag) VALUES ('');
  SELECT * FROM table_n_n;
  • Result: Success (INSERT 0 1). A row is stored containing an empty string.
  • Analysis: To many beginners, this result comes as a surprise. In PostgreSQL, an empty string is a valid text value of length zero (LENGTH('') = 0). Because it is a known value, '' IS NOT NULL evaluates to TRUE.
  • Test 4: Inserting the Character Zero ('0')
  INSERT INTO table_n_n (tag) VALUES ('0');
  • Result: Success (INSERT 0 1). The string '0' is stored. The character '0' is concrete data and satisfies the non-null requirement.

Scope & Engine-Specific Pitfall: Empty Strings vs. NULL: In PostgreSQL, MySQL, SQLite, Snowflake, and SQL Server, '' (empty string) and NULL are completely separate values. However, in Oracle Database, an empty string '' is automatically treated as NULL! An insert of '' into a NOT NULL column succeeds in PostgreSQL but raises ORA-01400: cannot insert NULL into (...) in Oracle. When migrating schemas between engines, always account for this behavioral divergence.

11.2.4 Student Questions and Answers

Q: Why did an empty string go in when NULL was blocked? A: Missing unknown empty string known passes. NULL represents an unknown, unrecorded state where data is absent. An empty string '' is a known, present string that happens to have zero characters. Because the NOT NULL constraint checks exclusively that the value is not missing (tag IS NOT NULL), '' passes while NULL fails. If a business rule also forbids empty strings, you must combine NOT NULL with a CHECK (LENGTH(TRIM(tag)) > 0) constraint.

Q: Where do all constraints live for a table in pgAdmin? A: Under the Constraints tree node within the table's hierarchy in pgAdmin. Primary key, unique, check, and foreign key constraints appear there. Note that column-level NOT NULL constraints are stored as column attributes rather than separate constraint objects in the main constraints tree.

11.2.5 Adding NOT NULL to an Existing Table

In evolving schemas, columns often start nullable and require a NOT NULL constraint later.

Consider a table initialized without the constraint:

CREATE TABLE table_n_n2 (
    id SERIAL PRIMARY KEY,
    tag2 TEXT
);

To retrofit this column with a non-null requirement, execute an ALTER TABLE statement:

ALTER TABLE table_n_n2 ALTER COLUMN tag2 SET NOT NULL;

#### Multi-Database Syntax Comparison for Modifying Nullability

Engine Add NOT NULL Syntax Drop NOT NULL Syntax
PostgreSQL ALTER TABLE t ALTER COLUMN c SET NOT NULL; ALTER TABLE t ALTER COLUMN c DROP NOT NULL;
MySQL ALTER TABLE t MODIFY COLUMN c TEXT NOT NULL; ALTER TABLE t MODIFY COLUMN c TEXT NULL;
Snowflake ALTER TABLE t ALTER COLUMN c SET NOT NULL; ALTER TABLE t ALTER COLUMN c DROP NOT NULL;
Databricks (Delta) ALTER TABLE t ALTER COLUMN c SET NOT NULL; ALTER TABLE t ALTER COLUMN c DROP NOT NULL;

Operational Trap: Existing NULL Rows Block ALTER TABLE: If table_n_n2 already contains rows where tag2 IS NULL, executing ALTER TABLE table_n_n2 ALTER COLUMN tag2 SET NOT NULL; will immediately fail with: ERROR: column "tag2" of relation "table_n_n2" contains null values Before setting NOT NULL, you must backfill or sanitize existing rows:

UPDATE table_n_n2 SET tag2 = 'Default Tag' WHERE tag2 IS NULL;
ALTER TABLE table_n_n2 ALTER COLUMN tag2 SET NOT NULL;

NOT NULL guarantees data completeness at the field level, but it does not validate format or uniqueness. When rows must also be distinguishable from one another without duplicates, the relational model applies the UNIQUE constraint.

#### Real-World & Domain Connection In identity verification and compliance systems, columns such as ssn, tax_id, and legal_name are mandatory. A missing tax_id in a payroll processing engine can prevent automated tax filing, resulting in hefty regulatory fines. Ensuring columns are declared NOT NULL from the outset protects downstream reporting pipelines from runtime null-pointer exceptions.

11.3 UNIQUE Constraint

What happens when two users attempt to register simultaneously using the same email address? Without a strict database rule, a race condition could allow duplicate accounts, corrupting billing records and user identity. How does the database guarantee distinctness across concurrent transactions?

A UNIQUE constraint — a rule that values must not repeat — guarantees that all non-null values stored in a column or group of columns remain distinct across the entire table. Think of it as a strict "no-copies" rule. Every time an application attempts to write a new row or update an existing row, the database checks the candidate value against all values already stored in that column. If a match is found, PostgreSQL raises a duplicate key error and immediately rolls back the operation.

Under the hood, PostgreSQL enforces a UNIQUE constraint by automatically creating a unique B-tree index on the designated column or columns. This allows the engine to detect collisions in \(O(\log n)\) time via index lookup, rather than performing an expensive \(O(n)\) sequential scan of the entire table on every write.

Formally, for a relation \(R\) and a single attribute \(A\), the UNIQUE constraint asserts: \[ \forall t_i, t_j \in R, \quad (i \neq j \land t_i[A] \text{ IS NOT NULL} \land t_j[A] \text{ IS NOT NULL}) \implies t_i[A] \neq t_j[A] \] When extended to a composite set of attributes \((A_1, A_2, \dots, A_k)\), the constraint guarantees that the tuple of values across all specified columns is distinct: \[ \forall t_i, t_j \in R, \quad i \neq j \implies (t_i[A_1], t_i[A_2], \dots, t_i[A_k]) \neq (t_j[A_1], t_j[A_2], \dots, t_j[A_k]) \] for all rows where the composite key is fully defined.

11.3.1 Syntax for a Single Column

The single-column form is declared inline during table definition:

CREATE TABLE table_name (
    column_name data_type UNIQUE
);

PostgreSQL assigns a default identifier following the convention: \[ \text{table\_name} + \text{"\_"} + \text{column\_name} + \text{"\_key"} \] For example, a UNIQUE constraint on the email column of table_emails is named table_emails_email_key.

11.3.2 Sample Table With Email Addresses

Consider a user contact table where each email address must be distinct:

CREATE TABLE table_emails (
    id SERIAL PRIMARY KEY,
    email TEXT UNIQUE
);

Here, id serves as an auto-numbering surrogate primary key, and email is guarded by the unique constraint. In pgAdmin, refreshing the object browser reveals:

  1. In the Columns node: email is typed as text.
  2. In the Constraints node: alongside table_emails_pkey, an entry named table_emails_email_key appears.
  3. In the Indexes node: a matching unique index table_emails_email_key exists, confirming that PostgreSQL implemented the constraint using an underlying B-tree structure.

11.3.3 Worked Examples

#### Worked Examples: Single-Column Uniqueness

  • Test 1: Inserting Initial Unique Record
  SELECT * FROM table_emails; -- Returns 0 rows
  INSERT INTO table_emails (email) VALUES ('a@b.com');
  SELECT * FROM table_emails;
  • Result: Success (INSERT 0 1). One row exists with email = 'a@b.com'.
  • Test 2: Inserting an Exact Duplicate
  INSERT INTO table_emails (email) VALUES ('a@b.com');
  • Result: Transaction aborted.

ERROR: duplicate key value violates unique constraint "table_emails_email_key" DETAIL: Key (email)=(a@b.com) already exists.

  • Sense Check: The value 'a@b.com' was found in the B-tree index. The engine rejected the second write, preserving the invariant \(email_i \neq email_j\).

11.3.4 UNIQUE on Multiple Columns

In real-world data models, individual columns frequently repeat while their combined pairing must remain strictly unique. Consider a product catalog where a short product code and product name must form a distinct combination.

First, create the table without constraints:

CREATE TABLE table_products (
    id SERIAL PRIMARY KEY,
    product_code VARCHAR(10),
    product_name TEXT
);

To enforce uniqueness across the pair on an existing table, use ALTER TABLE:

ALTER TABLE table_products
ADD CONSTRAINT unique_product_code
UNIQUE (product_code, product_name);

The composite condition evaluated on every incoming tuple is: \[ (code, name)_{\text{new}} \neq (code, name)_{\text{old}} \quad \forall \, \text{existing tuples in } R \]

#### Worked Examples: Multi-Column Composite Uniqueness

  • Step 1: Insert Initial Pair
  INSERT INTO table_products (product_code, product_name) VALUES ('A', 'Apple');
  -- Result: Success (INSERT 0 1)
  • Step 2: Re-insert Identical Pair
  INSERT INTO table_products (product_code, product_name) VALUES ('A', 'Apple');
  • Result: Rejected with error:

ERROR: duplicate key value violates unique constraint "unique_product_code" DETAIL: Key (product_code, product_name)=(A, Apple) already exists.

  • Step 3: Same Name, Different Code
  INSERT INTO table_products (product_code, product_name) VALUES ('1', 'Apple');
  -- Result: Success (INSERT 0 1)
  • Analysis: While 'Apple' repeats, the composite pair ('1', 'Apple') does not match ('A', 'Apple').
  • Step 4: Permuted Order ('Apple', 'A')
  INSERT INTO table_products (product_code, product_name) VALUES ('Apple', 'A');
  -- Result: Success (INSERT 0 1)
  • Analysis: The pair order is strictly positional: ('Apple', 'A') \(\neq\) ('A', 'Apple'). The engine compares the composite vector as an ordered sequence.

#### Multi-Database Behavior: NULLs and Uniqueness

How database engines handle NULL in UNIQUE columns varies significantly across platforms:

Engine Allows Multiple NULLs in UNIQUE Column? Enforcement Behavior

MySQL (InnoDB) Yes (Multiple NULLs permitted in unique index). Strictly enforced.
SQL Server No by default (allows only one NULL!). Must use filtered unique index WHERE col IS NOT NULL to allow multiple. Strictly enforced.

Common Pitfall: Assuming UNIQUE Implies NOT NULL: A common misconception is that adding UNIQUE automatically forbids NULL values. In PostgreSQL, a column with a UNIQUE constraint can contain hundreds of NULL rows because each NULL is treated as distinct/unknown. If a column must be both unique and mandatory, you must explicitly declare UNIQUE NOT NULL or designate it as a PRIMARY KEY.

11.3.5 Student Questions and Answers

Q: Does the check run on updates too, or only on inserts? A: Both insert update checked duplicate error. The unique constraint is evaluated on every write operation—both INSERT and UPDATE. If an UPDATE statement modifies a row's column to a value that already exists in another row, the engine blocks the update and returns the duplicate key violation error.

Q: Will Apple plus A collide with A plus Apple? A: No. The pair order concatenated whole comparison treats the composite key as an ordered tuple. Because ('A', 'Apple') \(\neq\) ('Apple', 'A'), the second pair is distinct and successfully commits.

The UNIQUE constraint prevents duplicate data values while still permitting NULLs. When an attribute must uniquely identify a row and never be missing, or when an application needs a standard fallback value when data is omitted, databases combine uniqueness with the DEFAULT constraint and PRIMARY KEY.

#### Real-World & Domain Connection In identity management, systems use UNIQUE constraints on user handles, tax identifiers, and email addresses to guarantee that single individuals cannot spawn duplicate profile identities. In multi-tenant SaaS platforms, multi-column uniqueness UNIQUE (tenant_id, user_email) ensures that email addresses remain unique within an individual organization while allowing the same email across separate tenant organizations.

11.4 DEFAULT Constraint

When a customer registers on an application, should the client code have to explicitly supply account_status = 'ACTIVE', created_at = NOW(), and retry_count = 0 on every single insert? What happens if an insert omits a column entirely?

A DEFAULT constraint — a predefined fallback value automatically applied when an insert omits a column — enables the database to populate missing fields autonomously. When an application constructs a new tuple and specifies values for only a subset of table attributes, the unmentioned columns automatically adopt their declared default values. If no default was ever declared on the column, the SQL standard dictates that the column falls back to NULL.

Understanding this fallback behavior is critical: omitting a column from an INSERT statement never inserts an empty string '' or the integer 0 by magic; it yields NULL unless an explicit default is configured.

Formally, when a tuple \(t\) is inserted into a relation \(R\), the assigned value for attribute \(C\) follows the piecewise evaluation: \[ \text{Value}(C) = \begin{cases} v_{\text{input}}, & \text{if } C \in \text{Columns}(\text{INSERT}) \land v_{\text{input}} \neq \text{DEFAULT} \\ d_C, & \text{if } C \notin \text{Columns}(\text{INSERT}) \lor v_{\text{input}} = \text{DEFAULT} \end{cases} \] where \(d_C\) represents the defined default expression. If no explicit default clause is declared for attribute \(C\), the relational engine applies the implicit default: \[ d_C = \text{NULL} \]

11.4.1 Syntax for a New Table

During table creation, a default is declared inline immediately after the column's data type:

CREATE TABLE table_name (
    column_name data_type DEFAULT default_value
);

For instance, declaring a status flag with a fallback value of 'Y':

is_enabled VARCHAR DEFAULT 'Y'

Here, is_enabled is a variable-length string column whose domain includes 'Y', 'N', and NULL, with an automatic fallback to 'Y'.

11.4.2 Sample Employees Table

Consider a personnel table managing active employee records:

CREATE TABLE employees (
    employee_id SERIAL PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    is_enabled VARCHAR DEFAULT 'Y'
);

In this schema:

  • employee_id is managed by an underlying sequence (via SERIAL).
  • first_name and last_name have no explicit defaults; their implicit default is NULL.
  • is_enabled defaults to 'Y' whenever an insert omits it.

In pgAdmin, executing SELECT * FROM employees; confirms the schema structure. Under the column properties for is_enabled, the Default field displays 'Y'::character varying.

11.4.3 Worked Examples

#### Worked Examples: Manipulating Column Defaults

  • Test 1: Omitting the Column on Insert (Initial Default 'Y')
  INSERT INTO employees (first_name, last_name) VALUES ('John', 'Adams');
  SELECT * FROM employees;
  • Result: Success. The newly created row contains ('John', 'Adams', 'Y').
  • Analysis: Because is_enabled was omitted from the column list, the engine evaluated the default clause and substituted 'Y', satisfying:

\[ is\_enabled = \text{'Y'} \quad \text{(fallback for missing input)} \]

  • Test 2: Modifying the Default Value on an Existing Table

To update business logic so that new employees start in an inactive state ('N'), alter the column definition:

  ALTER TABLE employees ALTER COLUMN is_enabled SET DEFAULT 'N';
  INSERT INTO employees (first_name, last_name) VALUES ('John', 'Adams');
  SELECT * FROM employees;
  • Result: The second row shows is_enabled = 'N'.
  • Analysis: The column default was updated from \(d_C = \text{'Y'}\) to \(d_C = \text{'N'}\). Existing rows remain unchanged, while all future inserts adopt 'N'.
  • Test 3: Dropping the Default (Reverting to NULL)

To remove the default entirely:

  ALTER TABLE employees ALTER COLUMN is_enabled DROP DEFAULT;
  INSERT INTO employees (first_name, last_name) VALUES ('Abigail', 'Adams');
  SELECT * FROM employees;
  • Result: The third row records NULL for is_enabled.
  • Analysis: With no default defined, the column reverts to the engine's implicit rule:

\[ is\_enabled = \text{NULL} \quad \text{(fallback when default is dropped)} \]

#### Multi-Database Behavior: Column Defaults

Engine Dynamic Defaults (Expressions / Functions) Retroactive Behavior
PostgreSQL Full expression support: DEFAULT CURRENT_TIMESTAMP, DEFAULT gen_random_uuid(). Does not modify existing rows.
MySQL MySQL 8.0.13+ supports expression defaults wrapped in parentheses: DEFAULT (CURRENT_DATE + INTERVAL 1 YEAR). Older versions permitted only literal constants. Does not modify existing rows.
Snowflake Supports sequences (seq.NEXTVAL) and scalar functions (CURRENT_TIMESTAMP()). Does not modify existing rows.
Databricks (Delta) Supported via Delta Lake column defaults (DEFAULT <expr>). Metadata-only; evaluates on write.

Scope & Common Trap: Explicit NULL Overrides the Default: A frequent source of application bugs occurs when developers pass an explicit NULL expecting the database default to take over:

INSERT INTO employees (first_name, last_name, is_enabled) VALUES ('Samuel', 'Adams', NULL);

In this scenario, is_enabled is set to NULL, not 'Y'. The default triggers only when the column is completely omitted from the write statement or when the explicit SQL keyword DEFAULT is supplied:

INSERT INTO employees (first_name, last_name, is_enabled) VALUES ('Samuel', 'Adams', DEFAULT);

11.4.4 Student Questions and Answers

Q: What happens when a column has no default and the insert skips it? A: Implicit NULL until SET DEFAULT changes. PostgreSQL automatically stores NULL because the ANSI SQL standard defines NULL as the universal implicit default for all unassigned attributes. If the column is additionally guarded by NOT NULL without an explicit default, omitting it causes the write to fail with a not-null constraint violation.

Q: Is the same ALTER pattern used for all three steps? A: Yes. The unified DDL pattern is ALTER TABLE <table_name> ALTER COLUMN <column_name> .... Follow with SET DEFAULT <val> to install or update a default, and DROP DEFAULT to remove it.

DEFAULT streamlines data ingestion by automatically populating standard values when inputs are omitted. However, while DEFAULT, NOT NULL, and UNIQUE protect individual fields and uniqueness, establishing an absolute, unambiguous identity for every tuple requires the PRIMARY KEY constraint.

#### Real-World & Domain Connection In audit logging and microservice architectures, default expressions are universally used for temporal tracking. Columns such as created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP and record_uuid UUID DEFAULT gen_random_uuid() ensure that immutable audit trails and globally unique event IDs are generated deterministically at the database layer without relying on synchronized system clocks across application servers.

11.5 PRIMARY KEY Constraint

In a table with ten million customer records, how does the database guarantee that every single row is uniquely addressable without ambiguity? What prevents two records from claiming the exact same identity?

A PRIMARY KEY constraint — a foundational relational rule establishing that each row in a table must possess an unambiguous, unique entity identity — defines the primary identifier for every record. While a table may declare multiple UNIQUE columns (candidate keys), relational theory and SQL allow exactly one primary key per table. That single primary key may comprise a single column or a composite collection of columns (composite primary key).

A primary key enforces two inviolable properties simultaneously:

  1. Uniqueness: No two distinct rows can share the same primary key value. Picture a street with 100 houses numbered sequentially from 1 to 100. Mail delivery works seamlessly because each house has a distinct number. If two houses shared number 10, direct addressing breaks down completely.
  2. Non-nullability: A primary key strictly forbids NULL values. A missing key means an entity without an identity, violating entity integrity.

Formally, for relation \(R\) with primary key attribute set \(K\), the constraint combines uniqueness and non-nullability: \[ \text{PK}(K) \iff \left( \forall t_i, t_j \in R, \; i \neq j \implies t_i[K] \neq t_j[K] \right) \land \left( \forall t \in R, \; \forall A \in K, \; t[A] \text{ IS NOT NULL} \right) \] In operational terms: \[ \text{PRIMARY KEY} \equiv \text{UNIQUE} \land \text{NOT NULL} \] where every row must have \(pk_i \neq pk_j\) for distinct rows and \(pk \text{ IS NOT NULL}\).

11.5.1 Syntax for a Single Column

A single-column primary key can be declared inline at the column level:

CREATE TABLE table_name (
    column_name data_type PRIMARY KEY
);

When declared without an explicit name, PostgreSQL automatically assigns a default constraint identifier: \[ \text{table\_name} + \text{"\_pkey"} \]

11.5.4 Adding and Dropping a Primary Key on an Existing Table

To remove an existing primary key in PostgreSQL, use ALTER TABLE ... DROP CONSTRAINT:

ALTER TABLE table_items DROP CONSTRAINT table_items_pkey;

Once dropped, the constraint node becomes empty and the column loses its unique enforcement. To restore the primary key on the existing table:

ALTER TABLE table_items ADD PRIMARY KEY (item_id);

To configure a composite primary key spanning multiple columns, specify the comma-separated column list inside parentheses:

ALTER TABLE table_items DROP CONSTRAINT table_items_pkey;
ALTER TABLE table_items ADD PRIMARY KEY (item_id, item_name);

Under this composite configuration, attempting to insert (2, 'pen') fails because the combined pair already exists, but inserting (2, 'pencil') succeeds because the composite tuple is unique.

Scope & Architectural Pitfall: Natural Keys vs. Surrogate Keys:

  • Natural Keys (e.g., SSN, driver's license number) represent real-world data. If the real-world value changes, updating foreign keys across millions of child records is expensive.
  • Surrogate Keys (e.g., auto-incrementing integers or UUIDs) have no business meaning and remain immutable.
  • Integer Overflow: An INTEGER type caps at \(2,147,483,647\) (2.14 billion). For high-throughput tables (such as transactional ledgers or IoT logs), always declare surrogate keys as BIGINT to prevent catastrophic key-exhaustion outages.

Exam note: Know duplicate error texts for UNIQUE and PRIMARY KEY and ALTER forms:

  • In PostgreSQL, both constraints raise a duplicate key error, but the constraint name identifies the origin:
  • UNIQUE error: ERROR: duplicate key value violates unique constraint "<table_name>_<col>_key"
  • PRIMARY KEY error: ERROR: duplicate key value violates unique constraint "<table_name>_pkey"
  • For ALTER forms, PostgreSQL drops primary keys using ALTER TABLE <table> DROP CONSTRAINT <constraint_name>; and adds them using ALTER TABLE <table> ADD PRIMARY KEY (<cols>);. Notice that MySQL uses ALTER TABLE <table> DROP PRIMARY KEY; without specifying the constraint name.

11.6 Composite PRIMARY KEY on Multiple Columns

In a university course enrollment system, a single student enrolls in many courses, and a single course contains many students. If neither student_id nor course_id is unique on its own, how do we uniquely identify each enrollment record without adding an artificial surrogate key?

A composite primary key — a primary key constructed from a combination of two or more columns — solves data modeling scenarios where no individual column guarantees uniqueness in isolation. Think of it like geographic coordinates on a map: a single line of latitude circles the entire globe, and a single line of longitude runs from pole to pole. Neither coordinate identifies a location by itself, but the pairing (latitude, longitude) pinpoints an exact location on Earth.

In relational modeling, many-to-many junction tables (such as student course enrollments, order line items, or role-permission mappings) rely on composite keys to enforce that a specific pairing occurs at most once.

Formally, for relation \(R\) with composite primary key \(K = \{A_1, A_2\}\), the constraint asserts that no two distinct tuples share the identical combination of attribute values: \[ \forall t_i, t_j \in R, \; i \neq j \implies (t_i[A_1], t_i[A_2]) \neq (t_j[A_1], t_j[A_2]) \] accompanied by the non-null invariant across all composite members: \[ \forall t \in R, \quad (t[A_1] \text{ IS NOT NULL}) \land (t[A_2] \text{ IS NOT NULL}) \] For a grades relation with attributes course_id and student_id, every incoming row must satisfy: \[ (\text{course\_id}, \text{student\_id})_{\text{new}} \neq (\text{course\_id}, \text{student\_id})_{\text{old}} \quad \forall \, \text{existing tuples in } R \]

11.6.1 Grades Table and Why Single Columns Fail

To understand why composite keys are necessary, consider a student grading table:

CREATE TABLE t_grades (
    course_id VARCHAR(100) NOT NULL,
    student_id VARCHAR(100) NOT NULL,
    grade INTEGER NOT NULL
);

INSERT INTO t_grades (course_id, student_id, grade) VALUES
    ('math', 'S1', 50),
    ('chemistry', 'S1', 70),
    ('english', 'S2', 70),
    ('physics', 'S1', 80);

Examining each individual column demonstrates why none can serve as a single-column primary key:

  1. course_id repeats as soon as student S2 takes 'math'.
  2. student_id repeats immediately because student S1 takes 'math', 'chemistry', and 'physics'.
  3. grade repeats whenever multiple students achieve the same mark (e.g., 70 in chemistry and english).

No single column satisfies the distinctness requirement.

11.6.2 Building the Composite Key

By combining course_id and student_id, each pair becomes distinct: ('math', 'S1') differs from ('math', 'S2'), and ('chemistry', 'S1') differs from ('physics', 'S1').

To declare a composite primary key, table-level syntax is mandatory:

DROP TABLE t_grades;

CREATE TABLE t_grades (
    course_id VARCHAR(100) NOT NULL,
    student_id VARCHAR(100) NOT NULL,
    grade INTEGER NOT NULL,
    PRIMARY KEY (course_id, student_id)
);

In pgAdmin, navigating to t_grades → Constraints displays t_grades_pkey, whose definition lists both course_id and student_id.

Index Column Ordering Rule (The Left-Prefix Principle): When PostgreSQL builds the underlying composite B-tree index for PRIMARY KEY (course_id, student_id), it organizes the index tree sorted first by course_id, then by student_id.

  • Queries filtering by WHERE course_id = 'math' can leverage this index.
  • Queries filtering by WHERE course_id = 'math' AND student_id = 'S1' can leverage this index.
  • Queries filtering only by WHERE student_id = 'S1' cannot efficiently use this index and may resort to a sequential table scan!

Always place the column most frequently queried or with higher filtering selectivity as the leading column in the composite key.

11.7 FOREIGN KEY Constraint Concept

What prevents an e-commerce database from creating an order for a customer who does not exist, or assigning an inventory item to a vendor who was deleted months ago? How do relational databases ensure that links between separate tables never break?

A FOREIGN KEY constraint — a declarative rule requiring that values in a column of one table must correspond to valid primary key or unique key values in another table — is the foundational mechanism for enforcing referential integrity across a relational schema. It ensures that relationships between tables remain synchronized, preventing data from drifting into an inconsistent state.

In relational terminology, two tables participate in this relationship:

  • The Referencing Table (often termed the child table): The table containing the foreign key column that points outward.
  • The Referenced Table (often termed the parent table): The table providing the authoritative primary or unique key being pointed to.

The shared key column acts as a relational bridge between the two entities.

Formally, let \(R_c\) be the referencing (child) relation with foreign key attribute \(FK\), and \(R_p\) be the referenced (parent) relation with primary key attribute \(PK\). Referential integrity asserts: \[ \forall t_c \in R_c, \quad (t_c[FK] \text{ IS NOT NULL}) \implies \exists t_p \in R_p \text{ such that } t_c[FK] = t_p[PK] \] Unless explicitly declared NOT NULL, a foreign key column permits NULL values. A NULL foreign key represents an unassigned relationship, whereas any non-null value must exist in the referenced parent table.

11.7.1 Syntax Shape

When creating a new table with a foreign key constraint, the constraint can be defined at the column level or table level:

-- Column-level syntax:
CREATE TABLE child_table (
    child_id INT PRIMARY KEY,
    parent_id INT REFERENCES parent_table (parent_id)
);

-- Table-level syntax (recommended for explicit naming):
CREATE TABLE child_table (
    child_id INT PRIMARY KEY,
    parent_id INT,
    CONSTRAINT fk_child_parent FOREIGN KEY (parent_id) 
        REFERENCES parent_table (parent_id)
);

11.8 Tables Without Foreign Keys

If a table accepts an insert without throwing an error, does that mean the data is valid? What happens when an order record points to customer ID 99999, but customer 99999 exists nowhere in the system? Why is silent data corruption far more dangerous than an explicit database failure?

To understand the indispensable role of foreign keys, we must examine the catastrophic data corruption that occurs when related tables are built without them. In an unconstrained database, integer columns that represent relationships are treated by the engine as plain, isolated numbers. The database engine does not infer relationships from column names; unless explicitly instructed via a FOREIGN KEY constraint, it allows any arbitrary integer to be stored.

An orphaned record occurs when a child table contains a foreign key value that corresponds to no existing record in the parent table. Picture a delivery package stamped with a street address that does not exist in any postal directory: the package cannot be delivered, cannot be returned, and remains lost in transit. In database systems, orphaned records break reports, corrupt financial statements, and cause queries to return misleading results.

Formally, in the absence of a foreign key constraint between referencing relation \(t\_\text{products}\) and referenced relation \(t\_\text{suppliers}\), the domain of supplier_id in products is simply the set of all integers: \[ \text{supplier\_id} \in \mathbb{Z} \] A tuple \(t_c\) becomes an orphan when its referencing attribute points to a non-existent entity: \[ \text{Orphan}(t_c) \iff t_c[\text{supplier\_id}] \notin \pi_{\text{supplier\_id}}(t\_\text{suppliers}) \] When an orphan row exists, any standard relational join: \[ t\_\text{products} \bowtie_{\text{supplier\_id}} t\_\text{suppliers} \] silently excludes the orphan tuple, causing physical inventory items to disappear from standard business reports.

11.8.1 Building Two Standalone Tables

To observe this breakdown firsthand, construct t_products and t_suppliers without establishing any foreign key constraint:

CREATE TABLE t_products (
    product_id INTEGER PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    supplier_id INTEGER NOT NULL
);

CREATE TABLE t_suppliers (
    supplier_id INTEGER PRIMARY KEY,
    supplier_name VARCHAR(100) NOT NULL
);

In this initial configuration:

  • Both tables have independent primary keys.
  • supplier_id in t_products is marked NOT NULL, but it possesses no relational link to t_suppliers.

11.8.3 The Takeaway

Without a foreign key constraint, the database engine enforces no relational boundaries. It verifies only that 10 is a valid integer. Data integrity and referential integrity are completely lost, leaving the schema vulnerable to orphaned records, broken joins, and phantom entities.

Q: Why is supplier 10 a problem when the insert succeeded? A: No rule blocked missing vendor nowhere. A successful insert statement merely confirms that the row satisfied syntactic data typing and column-level nullability. In business reality, vendor 10 does not exist. The product record points to a non-existent entity, producing orphaned rows that corrupt inventory tracking and break reporting joins.

Permitting tables to exist without foreign key constraints invites silent data corruption. To eliminate orphaned rows and protect relational consistency, the schema must formally declare foreign keys using REFERENCES.

#### Real-World & Domain Connection In retail banking, orphaned records can lead to regulatory disaster. If a transaction record is created without a foreign key to a valid customer account, funds can be debited from an external payment gateway without being credited to any ledger in the bank, leading to unresolved ledger imbalances and severe AML (Anti-Money Laundering) compliance fines.

11.9 Creating Foreign Key Constraints

If table A contains a foreign key pointing to table B, which table must be created first in the database? What happens if an automated deployment script executes the CREATE TABLE statements in the reverse order?

To eliminate the risk of orphaned data demonstrated in the previous section, the database schema must be rebuilt with formal foreign key constraints in place. When a foreign key is declared, PostgreSQL binds the two tables in its system catalog (pg_constraint), intercepting every write to ensure that pointers never resolve into a void.

Creating related tables requires strict adherence to dependency order: you cannot anchor a suspension bridge cable in mid-air. The anchor tower must be constructed on solid ground before any cables can attach to it. Similarly, in relational DDL, the referenced table providing the primary key must exist in the catalog before the referencing table can declare a foreign key pointing to it.

In relational database design, the creation sequence follows a topological sort of the schema graph:

  1. Referenced Table (Source / Target): Must be defined and created first, establishing its primary or unique key.
  2. Referencing Table (Dependent): Created second, declaring its local foreign key column with the REFERENCES clause.

When tearing down or resetting schemas, the reverse order is mandatory: drop the referencing child table first, then drop the referenced parent table (or execute DROP TABLE ... CASCADE).

11.9.1 Order of Work

To implement the constraint on our demonstration schema, drop the existing unlinked tables in dependency order:

DROP TABLE IF EXISTS t_products;
DROP TABLE IF EXISTS t_suppliers;

First, create the referenced source table:

CREATE TABLE t_suppliers (
    supplier_id INTEGER PRIMARY KEY,
    supplier_name VARCHAR(100) NOT NULL
);

Next, create the referencing table, embedding the FOREIGN KEY declaration:

CREATE TABLE t_products (
    product_id INTEGER PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    supplier_id INTEGER NOT NULL,
    FOREIGN KEY (supplier_id) REFERENCES t_suppliers (supplier_id)
);

Here, supplier_id in t_products is the local foreign key, and supplier_id in t_suppliers is the referenced primary key. Both attributes share the matching INTEGER data type.

11.9.2 How PostgreSQL Names and Shows the Link

In pgAdmin's Object Browser:

  • On t_suppliers: Only the primary key constraint t_suppliers_pkey appears under the Constraints node.
  • On t_products: Two constraint entries appear:
  1. t_products_pkey (the product primary key).
  2. t_products_supplier_id_fkey (the foreign key, indicated by a distinct linked-key icon).

When declared without an explicit name, PostgreSQL constructs the foreign key identifier according to the canonical pattern: \[ \text{table\_name} + \text{"\_"} + \text{column\_name} + \text{"\_fkey"} \] Opening the properties of t_products_supplier_id_fkey displays:

  • Local Column: supplier_id (the referencing column in t_products).
  • Referenced Table: t_suppliers (the target table).
  • Referenced Column: supplier_id (the authoritative key in t_suppliers).

11.9.3 Parent, Child, and Longer Chains

In the classroom demonstration, t_products is referred to as the parent table because it holds the foreign key column, while t_suppliers is referred to as the child or foreign table because it is the source being pointed to. In formal relational literature, t_products is the referencing table and t_suppliers is the referenced table.

Relational schemas frequently extend this relationship into multi-tier referential chains:

  [t_countries] <--- (FK) --- [t_suppliers] <--- (FK) --- [t_products] <--- (FK) --- [t_order_items]

In this four-tier chain, t_suppliers acts as a referencing table to t_countries while simultaneously serving as a referenced table for t_products. Referential integrity is enforced across every link along the directed acyclic graph (DAG).

11.10 Foreign Keys Maintain Referential Integrity

What happens if an administrator attempts to delete a vendor who currently supplies fifty active products in a retail catalog? Should the database permit the vendor to vanish, stranding fifty products with invalid supplier references, or should it intervene and abort the deletion?

A foreign key enforces referential integrity — the guarantee that cross-table pointers always correspond to genuine, existing records in the referenced table. The governing operational rule is simple: values entered into the referencing (child) column must already exist in the referenced (parent) primary key column.

This creates a bidirectional safeguard:

  1. Child Write Protection: Every INSERT and UPDATE on the referencing table is checked. If the incoming foreign key value is not present in the parent table, the operation is blocked.
  2. Parent Delete Protection: Every DELETE and primary-key UPDATE on the referenced table is checked. If any existing child row still references that parent key, the database refuses the deletion, preventing orphaned records.

Think of this like a university library checkout system ("source first borrow practice loop"): a student cannot borrow a book unless their student ID already exists in the active student registry. Conversely, the university registrar cannot delete a student's record from the university system if that student still has unreturned library books checked out.

Formally, referential integrity requires that the set of foreign key values in referencing relation \(R_c\) is a subset of the primary key values in referenced relation \(R_p\): \[ \pi_{FK}(R_c) \setminus \{\text{NULL}\} \subseteq \pi_{PK}(R_p) \] For our products and suppliers schema, every write operation on t_products evaluates the set-membership test: \[ \text{supplier\_id}_{\text{new}} \in \text{source\_ids} \] where \(\text{source\_ids} = \{ s[\text{supplier\_id}] \mid s \in t\_\text{suppliers} \}\).

11.10.1 Insert Flow: Source First

Because the referencing table borrows key values from the referenced table, data ingestion must always load the source table first:

INSERT INTO t_suppliers (supplier_id, supplier_name) VALUES
    (1, 'supplier one'),
    (2, 'supplier two');

INSERT INTO t_products (product_id, product_name, supplier_id) VALUES
    (1, 'pen', 1),
    (2, 'paper', 2);

Both product inserts succeed because 1 and 2 exist in \(\text{source\_ids} = \{1, 2\}\).

  • Result: Statement rejected with error:

  • Resolution: Remove or reassign the referencing child row first:
    DELETE FROM t_products WHERE product_id = 3;
    DELETE FROM t_suppliers WHERE supplier_id = 100;
    -- Now succeeds because no child points to supplier 100.
  • Test 3: Updating Child to a Valid Existing Vendor

Exam note: Practice referential checks on insert update and delete:

  • An INSERT into a child table fails if the referenced key does not exist in the parent table.
  • An UPDATE on a child table's foreign key column fails if the new key does not exist in the parent table.
  • A DELETE on a parent table fails if any child row references that parent key (unless ON DELETE CASCADE or ON DELETE SET NULL is configured).
  • An UPDATE on a parent table's primary key fails if child rows reference that key (unless ON UPDATE CASCADE is configured).

When maintenance or schema migrations require temporarily altering these relationships, constraints can be dropped or added via ALTER TABLE.

#### Real-World & Domain Connection In core banking and payment processing, referential integrity prevents catastrophic double-entry accounting errors. When a user closes a bank account, foreign key rules prevent the account from being purged while unsettled transactions, pending direct debits, or active credit card authorizations still point to it, ensuring an immutable legal audit trail.

11.11 Dropping a Constraint

What happens when an urgent schema migration or bulk ETL data loading job requires removing a constraint on a production table processing thousands of transactions per second? How do database administrators safely drop constraints without exposing the database to data corruption?

Removing an active constraint from a relational table is executed via the ALTER TABLE statement combined with the DROP CONSTRAINT clause. Whether removing a primary key, a unique constraint, a check constraint, or a foreign key, the operational syntax targets the constraint by its catalog identifier.

Temporarily dropping a constraint is a common administrative procedure during high-throughput bulk migrations. Validating constraints on every single row during a multi-gigabyte data import introduces substantial CPU and I/O overhead. Database administrators frequently drop constraints prior to bulk data loading, perform the load at maximum throughput, and re-establish the constraints once the import concludes.

In PostgreSQL, the universal syntax for removing named constraints is:

ALTER TABLE table_name DROP CONSTRAINT [IF EXISTS] constraint_name [RESTRICT | CASCADE];
  • IF EXISTS: Suppresses an error if the constraint does not exist.
  • RESTRICT (default): Prevents dropping the constraint if other database objects depend on it.
  • CASCADE: Automatically drops any dependent objects (such as foreign keys in other tables that reference the primary key being dropped).

Note that dropping a NOT NULL constraint uses column-level syntax rather than DROP CONSTRAINT:

ALTER TABLE table_name ALTER COLUMN column_name DROP NOT NULL;

11.11.1 Care on Live Tables

Executing ALTER TABLE ... DROP CONSTRAINT acquires an ACCESS EXCLUSIVE lock on the target relation in PostgreSQL. While dropping a constraint executes nearly instantaneously in the system catalog, the lock briefly blocks all concurrent reads and writes until the DDL transaction finishes.

Furthermore, dropping a foreign key temporarily removes the relational guardrails. If concurrent application writes land while the constraint is absent, invalid or orphaned rows can slip into the database undetected—exactly like the unconstrained demonstration in Section 11.8.

#### Worked Example: Dropping a Constraint Safely Inside a Transaction

  • Scenario: Removing t_products_supplier_id_fkey to perform maintenance.
  • Execution:
  -- Step 1: Drop the foreign key constraint
  ALTER TABLE t_products DROP CONSTRAINT t_products_supplier_id_fkey;

  -- Step 2: Verify removal in PostgreSQL system catalog
  SELECT conname, contype 
  FROM pg_constraint 
  WHERE conrelid = 't_products'::regclass;
  • Result: t_products_supplier_id_fkey is purged from pg_constraint.
  • Production Best Practice (Transactional Encapsulation):

To prevent invalid data from slipping in during maintenance, encapsulate the removal and maintenance within an explicit transaction:

  BEGIN;
  -- Lock table and drop constraint
  ALTER TABLE t_products DROP CONSTRAINT t_products_supplier_id_fkey;
  -- Perform required bulk maintenance operations
  -- Re-add constraint before committing
  COMMIT;
  • Sense Check: The removal DROP CONSTRAINT lock transaction ensures that either the entire maintenance window succeeds under isolation or rolls back completely.

#### Real-World & Domain Connection In high-performance data warehousing and ETL pipelines, loading hundreds of millions of rows with active foreign key and unique constraints can cause ETL jobs to take hours or fail from lock contention. Production pipelines routinely execute a pre-load script dropping foreign keys, run high-speed parallel COPY operations, and execute a post-load script re-enabling constraints with batch validation.

11.12 Adding a Foreign Key to an Existing Table

What happens if you attempt to add a foreign key constraint to an existing table that already contains millions of rows, some of which are orphaned records? How can a database administrator safely establish referential integrity on legacy datasets without incurring hours of downtime?

When a relational schema evolves or when constraints are re-established following bulk data imports, database administrators apply ALTER TABLE combined with ADD CONSTRAINT. This command retroactively attaches referential integrity rules to existing tables, binding local attributes to remote referenced keys.

Unlike table creation where the schema starts empty, adding a foreign key to an existing populated table forces the database engine to perform an exhaustive validation scan of every existing record. If even a single row in the local table contains a foreign key value that does not exist in the referenced target table, the entire ALTER TABLE operation aborts, rolls back, and raises a constraint violation error.

When adding a foreign key to an existing table, PostgreSQL binds the local attribute to the remote referenced primary key: \[ \text{Local}(FK) = t\_\text{products}.\text{supplier\_id} \quad \longrightarrow \quad \text{Reference}(PK) = t\_\text{suppliers}.\text{supplier\_id} \] The engine verifies the relational validity condition across all existing tuples: \[ \forall t \in t\_\text{products}, \quad (t[\text{supplier\_id}] \text{ IS NOT NULL}) \implies t[\text{supplier\_id}] \in \pi_{\text{supplier\_id}}(t\_\text{suppliers}) \] If this predicate evaluates to FALSE for any row, the constraint cannot be created until the offending child rows are either sanitized, re-assigned, or deleted.

11.12.1 Worked Example

The general syntax for retroactively adding a named foreign key constraint is:

ALTER TABLE table_name
ADD CONSTRAINT constraint_name
FOREIGN KEY (local_column) REFERENCES foreign_table (foreign_column);

#### Worked Example: Re-Adding Foreign Key with Local and Reference Binding

  • Scenario: The demonstration table t_products previously had its constraint removed. We now re-establish the link using standard PostgreSQL naming conventions:
  ALTER TABLE t_products
  ADD CONSTRAINT t_products_supplier_id_fkey
  FOREIGN KEY (supplier_id) REFERENCES t_suppliers (supplier_id);
  • Verification: In pgAdmin, navigate to t_products → Constraints → t_products_supplier_id_fkey and open Properties:
  • Local Column: supplier_id in t_products (the local parent/referencing column).
  • Reference Table: t_suppliers.
  • Reference Column: supplier_id in t_suppliers.
  • Sense Check: The local parent supplier reference supplier link is restored. Any future insert or update on t_products will immediately validate against t_suppliers.

#### Advanced PostgreSQL Production Pattern: NOT VALID and VALIDATE CONSTRAINT

On multi-gigabyte production tables, running ALTER TABLE ... ADD CONSTRAINT can hold an exclusive table lock for minutes or hours while verifying existing rows. PostgreSQL provides a zero-downtime two-phase pattern:

-- Phase 1: Add constraint without scanning existing rows (instantaneous lock)
ALTER TABLE t_products
ADD CONSTRAINT t_products_supplier_id_fkey
FOREIGN KEY (supplier_id) REFERENCES t_suppliers (supplier_id)
NOT VALID;

-- Phase 2: Validate existing rows in background without blocking concurrent writes
ALTER TABLE t_products
VALIDATE CONSTRAINT t_products_supplier_id_fkey;

Adding foreign keys to existing tables restores referential integrity across relational boundaries. While primary and foreign keys govern identity and cross-table linkages, validating arbitrary business logic—such as numeric ranges, text patterns, and date intervals—is handled by the versatile CHECK constraint.

#### Real-World & Domain Connection During zero-downtime database migrations in financial systems (e.g., transitioning from monolithic databases to microservices), database engineers use ADD CONSTRAINT ... 11.13 CHECK Constraint Introduction

Can an employee have a negative salary, an account balance with negative pennies, or a product return date that occurs before the purchase date? How does a database enforce custom domain rules beyond basic data types?

A CHECK constraint — a declarative rule that validates incoming data against an arbitrary Boolean expression — empowers database designers to define custom business rules directly in the table definition. While data types restrict values to broad categories (such as integers or text), a CHECK constraint restricts values to specific, valid subsets (such as salary > 0, discount BETWEEN 0 AND 100, or status IN ('Active', 'Pending', 'Archived')).

Every time an INSERT or UPDATE operation executes, the database evaluates the Boolean expression for the incoming row. If the condition evaluates to TRUE or UNKNOWN (under three-valued logic), PostgreSQL accepts the write. If the condition evaluates strictly to FALSE, the engine rejects the transaction and raises a constraint violation error.

Formally, for any candidate tuple \(t\) in relation \(R\), the CHECK constraint evaluates a Boolean predicate \(\phi(t)\): \[ \text{Valid}(t) \iff \phi(t) \in \{\text{TRUE}, \text{UNKNOWN}\} \] For a salary column requiring pay to remain above zero: \[ \text{Valid}(\text{salary}) \iff (\text{salary} > 0) \] Under SQL three-valued logic (3VL), if \(\text{salary} = 5000\), the predicate yields TRUE (passes). If \(\text{salary} = -100\), the predicate yields FALSE (fails and aborts). If \(\text{salary} = \text{NULL}\), the comparison \(\text{NULL} > 0\) yields UNKNOWN, which passes the check constraint.

11.13.1 Core Properties

The core architectural properties of CHECK constraints include:

  1. Specific Value Criteria: Defines granular domain limits on columns, such as \(salary > 0\) or rating BETWEEN 1 AND 5.
  2. Boolean Evaluation on Writes: Evaluated deterministically during every INSERT and UPDATE. SELECT queries never trigger constraint validation.
  3. Deterministic Rejection: Rejects violating rows with an error specifying the table, column, and constraint name.
  4. Scope Boundaries: A CHECK constraint can evaluate multiple columns within the same row, but it cannot reference other rows in the same table, query other tables, or execute subqueries.

#### Worked Example: Salary Boolean Insert and Update Violation

  • Setup: Create a table enforcing that employee pay remains strictly positive:
  CREATE TABLE staff_salaries (
      staff_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
      staff_name TEXT NOT NULL,
      salary NUMERIC(10, 2) CHECK (salary > 0)
  );
  • Test 1: Valid Positive Salary
  INSERT INTO staff_salaries (staff_name, salary) VALUES ('Alice', 5000.00);
  -- Result: Success (INSERT 0 1). 5000.00 > 0 evaluates to TRUE.
  • Test 2: Invalid Negative Salary on Insert
  INSERT INTO staff_salaries (staff_name, salary) VALUES ('Bob', -500.00);
  • Result: Statement rejected with error:

ERROR: new row for relation "staff_salaries" violates check constraint "staff_salaries_salary_check" DETAIL: Failing row contains (2, Bob, -500.00).

  • Test 3: Invalid Zero Salary on Update
  UPDATE staff_salaries SET salary = 0 WHERE staff_id = 1;
  • Result: Statement rejected with error:

ERROR: new row for relation "staff_salaries" violates check constraint "staff_salaries_salary_check" DETAIL: Failing row contains (1, Alice, 0.00).

  • Sense Check: The expression salary > 0 evaluated to FALSE for both -500.00 and 0.00, successfully blocking corrupt financial records on both insert and update.

#### Multi-Database Behavior: CHECK Constraints

Database Engine CHECK Constraint Support & Enforcement Notes
PostgreSQL Strictly enforced across all versions. Evaluates on write; supports table-level multi-column checks.
MySQL Enforced only in MySQL 8.0.16+! Major Historical Gotcha: Prior to 8.0.16, MySQL parsed CHECK syntax without error but silently ignored it, allowing invalid data to be inserted!
Snowflake Not supported. Snowflake does not support CHECK constraints; validation must occur in ETL (e.g. dbt tests).

The NULL Loophole in CHECK Constraints: Because CHECK constraints pass when an expression evaluates to UNKNOWN, inserting NULL into a column with CHECK (salary > 0) succeeds! The database tests NULL > 0, which yields UNKNOWN, and because it is not FALSE, the write commits. To guarantee that a column is both present and satisfies the condition, always combine NOT NULL with CHECK:

salary NUMERIC(10, 2) NOT NULL CHECK (salary > 0)

CHECK constraints guarantee domain-level validity by enforcing deterministic Boolean rules on writes. To see how CHECK constraints handle multiple columns and complex business logic during table creation, we explore multi-column checks on a new table in the next section.

#### Real-World & Domain Connection In airline ticketing and reservation platforms, CHECK constraints enforce core temporal and geographic invariants: CHECK (departure_time < arrival_time) and CHECK (seat_number SIMILAR TO '[0-9]{1,2}[A-F]'). These database-level guards prevent scheduling anomalies and seat assignment corruption before data reaches booking engines.

11.14 CHECK Constraint on a New Table

Can an employee join a company before they are born? Can an individual be recorded as born in the year 1750 and actively employed today? How do databases evaluate relationships between multiple columns within the same row?

When designing a new schema, CHECK constraints can be integrated directly into the CREATE TABLE definition to establish baseline business invariants. While basic constraints validate individual values against static boundaries, CHECK constraints can compare multiple columns within the same row, ensuring logical coherence across related fields.

By defining constraints at table creation, the database guarantees that corrupt or impossible data never enters the storage layer, eliminating the need for complex, defensive application-side data validation.

Formally, when defining a staff relation with birth dates, join dates, and compensation, the database evaluates three concurrent Boolean predicates for each tuple \(t\): \[ \begin{aligned} \phi_1(t) &\equiv t[\text{birth\_date}] > \text{DATE '1900-01-01'} \\ \phi_2(t) &\equiv t[\text{join\_date}] > t[\text{birth\_date}] \\ \phi_3(t) &\equiv t[\text{salary}] > 0 \end{aligned} \] The composite admission rule requires that all constraints satisfy the non-false condition: \[ \text{Valid}(t) \iff \big(\phi_1(t) \in \{\text{TRUE}, \text{UNKNOWN}\}\big) \land \big(\phi_2(t) \in \{\text{TRUE}, \text{UNKNOWN}\}\big) \land \big(\phi_3(t) \in \{\text{TRUE}, \text{UNKNOWN}\}\big) \] If any condition evaluates to FALSE, the write is aborted.

11.14.1 Sample Staff Table

Construct a staff table enforcing historical cutoff dates, chronological sequence, and positive compensation:

CREATE TABLE staff (
    staff_id SERIAL PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    birth_date DATE CHECK (birth_date > DATE '1900-01-01'),
    join_date DATE CHECK (join_date > birth_date),
    salary NUMERIC CHECK (salary > 0)
);

In this schema:

  • birth_date must occur after January 1, 1900, establishing a reasonable historical boundary.
  • join_date must be strictly greater than birth_date, preventing chronological paradoxes where an employee joins before their birth date.
  • salary must be strictly positive.

In pgAdmin, executing SELECT * FROM staff; confirms the schema structure, while expanding staff → Constraints reveals the three generated check constraints: staff_birth_date_check, staff_join_date_check, and staff_salary_check.

11.15 CHECK Constraint Add Rename Drop on an Existing Table

As corporate pricing strategies and discount policies evolve, how do database administrators update, rename, or retire complex business validation rules on live tables without corrupting existing historical sales data?

In operational databases, business rules change frequently. A company may introduce seasonal discount ceilings, update tax boundaries, or restructure promotional pricing. Managing these evolving business rules requires mastering the complete DDL lifecycle for CHECK constraints on existing tables: creating multi-part conditions, renaming constraints for improved semantic clarity, dropping retired constraints, and replacing them with updated validation logic.

Unlike single-column checks, multi-part check constraints evaluate compound expressions connected by logical operators (AND, OR, NOT). This allows the database to enforce relational invariants across multiple related numeric, date, or text columns simultaneously.

Formally, consider a retail pricing relation with attributes price and discount. A robust pricing policy asserts that price must be positive, discount must be non-negative, and the discount must never exceed or equal the retail price: \[ \text{Valid}(\text{price}, \text{discount}) \iff (\text{price} > 0) \land (\text{discount} \ge 0) \land (\text{price} > \text{discount}) \] Under Boolean conjunction, if even a single condition evaluates to FALSE, the entire composite expression evaluates to FALSE: \[ \text{TRUE} \land \text{TRUE} \land \text{FALSE} = \text{FALSE} \] causing PostgreSQL to abort the transaction and reject the write.

11.15.1 Price Table With No Check

Begin by constructing a demonstration table without check constraints:

CREATE TABLE prices (
    price_id SERIAL PRIMARY KEY,
    product_id INTEGER,
    price NUMERIC NOT NULL,
    discount NUMERIC NOT NULL,
    valid_from DATE NOT NULL
);

In this schema:

  • price_id is the primary key.
  • price, discount, and valid_from are mandatory (NOT NULL).
  • Initially, only prices_pkey appears under the Constraints node in pgAdmin.

11.15.2 Adding a Multi-Part Check

To attach a multi-part check constraint to the existing table, use ALTER TABLE ... ADD CONSTRAINT:

ALTER TABLE prices
ADD CONSTRAINT price_check
CHECK (price > 0 AND discount >= 0 AND price > discount);

This statement validates the three-part rule:

  1. price > 0: The product cannot be free or negative.
  2. discount >= 0: The discount cannot be negative.
  3. price > discount: The discount cannot exceed or match the retail price, ensuring a positive net sale price.

11.15.3 Worked Examples

#### Worked Examples: Multi-Part CHECK Validation

  • Test 1: Valid Price and Discount Record
  INSERT INTO prices (product_id, price, discount, valid_from)
  VALUES (1, 100, 20, DATE '2020-10-01');
  SELECT * FROM prices;
  • Result: Success (INSERT 0 1).
  • Evaluation: \(100 > 0 \implies \text{TRUE}\), \(20 \ge 0 \implies \text{TRUE}\), and \(100 > 20 \implies \text{TRUE}\). All conditions hold.
  • Test 2: Discount Greater Than Retail Price
  INSERT INTO prices (product_id, price, discount, valid_from)
  VALUES (2, 100, 120, DATE '2020-10-01');
  • Result: Statement rejected with error:

ERROR: new row for relation "prices" violates check constraint "price_check" DETAIL: Failing row contains (2, 2, 100, 120, 2020-10-01).

  • Analysis: While 100 > 0 and 120 >= 0 are true, \(100 > 120\) evaluates to FALSE. The compound AND fails immediately.

11.15.4 Rename and Drop

Over time, database administrators may need to standardize naming conventions or retire outdated checks.

#### Renaming a Constraint To rename an existing constraint in PostgreSQL without dropping and recreating it:

ALTER TABLE prices RENAME CONSTRAINT price_check TO price_discount_check;

Refreshing pgAdmin's Constraints node displays the updated identifier price_discount_check.

#### Dropping and Replacing a Constraint To remove the constraint:

ALTER TABLE prices DROP CONSTRAINT price_discount_check;

With the old rule removed, a new, revised constraint can be installed:

ALTER TABLE prices
ADD CONSTRAINT discount_check
CHECK (discount > 10);

This complete administrative cycle demonstrates how schemas adapt to changing business requirements through declarative DDL.

Operational Trap: Retaining Data Consistency During Drops: Dropping a check constraint leaves the table temporarily unprotected. If an application requires migrating from one check constraint to another on a live production system, always add the new constraint before dropping the old one (or execute both statements within an atomic transaction block) to prevent invalid data from being inserted during the transition window.

CHECK constraints provide declarative, mathematically rigorous protection for domain logic and multi-column invariants. Mastering ADD, RENAME, and DROP operations equips database professionals to evolve schemas safely in production environments.

Invariants like CHECK (sale_price < list_price AND sale_price >= wholesale_cost) prevent automated repricing algorithms from accidentally selling merchandise below cost during flash sales.

Exam Guidance Summary

Key Examinable Concepts & Core Invariants

  1. Gatekeeper Levels & Taxonomy:
  • Understand the difference between column-level constraints (declared beside a single column) and table-level constraints (declared after all columns; required for composite keys and cross-column checks).
  • The five foundational constraints: NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, and CHECK.
  1. Nullability & Three-Valued Logic:
  • NULL represents unknown or missing information. It is strictly distinct from empty strings ('') and numeric zero (0).
  • Equality checks like col = NULL yield UNKNOWN. Only IS NULL and IS NOT NULL produce deterministic Boolean outputs.
  • NOT NULL rejects NULL but accepts empty strings ''.
  • CHECK constraints evaluate expressions under three-valued logic: they pass on TRUE and UNKNOWN, failing only on FALSE. Consequently, CHECK (salary > 0) permits NULL unless combined with NOT NULL.
  1. Entity Uniqueness & Error Message Text:
  • UNIQUE permits multiple NULL values under ANSI SQL (and PostgreSQL default behavior) because NULL != NULL.
  • PRIMARY KEY combines UNIQUE and NOT NULL into a single entity identifier. A table can have multiple unique keys, but only one primary key.
  • Know the standard PostgreSQL error message formats:
  • UNIQUE error: ERROR: duplicate key value violates unique constraint "<table_name>_<column_name>_key"
  • PRIMARY KEY error: ERROR: duplicate key value violates unique constraint "<table_name>_pkey"
  1. Referential Integrity & Dependency Order:
  • The referenced (parent) table must be created before the referencing (child) table.
  • DDL teardown requires reverse order: drop the referencing child table first, then drop the referenced parent table (or use DROP TABLE ... CASCADE).
  • Referential checks are bidirectional:
  • INSERT or UPDATE on child: foreign key must exist in parent table (or be NULL).
  • DELETE or UPDATE on parent: fails if active child rows reference the target key (under default RESTRICT / NO ACTION).
  1. Essential DDL Syntax Patterns:
  • Add NOT NULL: ALTER TABLE t ALTER COLUMN c SET NOT NULL;
  • Drop NOT NULL: ALTER TABLE t ALTER COLUMN c DROP NOT NULL;
  • Set Default: ALTER TABLE t ALTER COLUMN c SET DEFAULT <val>;
  • Drop Default: ALTER TABLE t ALTER COLUMN c DROP DEFAULT;
  • Add Constraint: ALTER TABLE t ADD CONSTRAINT <name> <TYPE> (...);
  • Drop Constraint: ALTER TABLE t DROP CONSTRAINT <name>;
  • Rename Constraint: ALTER TABLE t RENAME CONSTRAINT <old> TO <new>;

Key Industry Applications

Practical Deployments of Constraints in Enterprise Architecture

  1. Financial Ledgers and Core Banking Systems:
  • Double-entry bookkeeping requires that every debit corresponds to an exact credit, and transaction amounts must remain strictly positive (CHECK (amount > 0)).
  • PRIMARY KEY and FOREIGN KEY constraints guarantee that financial journal entries cannot be created without referencing a valid chart of accounts, and accounts cannot be deleted while unsettled transactions remain linked to them.
  1. Healthcare Information Systems & HIPAA Compliance:
  • Patient master indexes rely on NOT NULL for mandatory identifiers (ssn, date_of_birth, legal_name) and UNIQUE constraints on medical record numbers (MRNs) to eliminate the risk of patient chart misidentification.
  • Cross-column CHECK (discharge_date >= admission_date) ensures that hospitalization records remain chronologically sound for medical billing and clinical reporting.
  1. E-Commerce and Global Supply Chain Logistics:
  • Order fulfillment systems depend on foreign keys between orders, order_items, and products to prevent orphaned purchases.
  • Composite keys PRIMARY KEY (order_id, product_id) eliminate duplicate line items within an individual order.
  • Multi-part pricing rules CHECK (sale_price <= regular_price AND sale_price >= wholesale_cost) safeguard retail margins against automated repricing errors.
  1. Multi-Tenant SaaS Identity & Authentication:
  • Multi-tenant cloud platforms enforce data isolation using composite uniqueness: UNIQUE (tenant_id, email) allows users across different corporate tenants to share email addresses while guaranteeing absolute distinctness within each tenant organization.
  • DEFAULT constraints supply standard security flags (is_active DEFAULT TRUE, failed_login_attempts DEFAULT 0) to newly provisioned accounts.
  1. Human Resources & Enterprise Resource Planning (ERP):
  • Enterprise systems enforce organizational hierarchies and payroll validity using CHECK (salary > 0) and CHECK (join_date > birth_date).
  • Foreign keys enforce reporting relationships, ensuring that an employee's manager_id points to an active employee record.
