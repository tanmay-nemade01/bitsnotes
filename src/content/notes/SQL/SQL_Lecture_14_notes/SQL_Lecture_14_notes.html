# Aggregate Functions

14.1 Counting Results with COUNT

14.1.1 What COUNT Does

Hook: Almost every data question starts with "how many?" — how many movies, how many English titles, how many directors. Before any total, average, or ranking, you need a trustworthy headcount. COUNT is that headcount.

An aggregate function (a function that takes many rows and returns one single answer) collapses a whole column of rows into one number. COUNT is the simplest of the family: many rows in, one headcount out. Think of a teacher taking attendance. The teacher can count every desk with a student in it — that is \(\text{COUNT}(\ast)\). Or the teacher can count only the students who handed in a homework slip — that is \(\text{COUNT}(\text{column})\). If every student handed in a slip, both counts agree. If some slips are missing, the two counts differ, and the difference itself tells you something. The analogy breaks in one place: a teacher sees empty desks, but COUNT never shows you which rows were skipped — it only returns the final number, so you must check the raw rows yourself when the count surprises you.

The two basic forms. Star, written as \(\ast\), means all columns, so \(\text{COUNT}(\ast)\) counts rows no matter what sits inside them. \(\text{COUNT}(\text{column})\) counts non-missing entries in one named column and silently skips NULL:

SELECT COUNT(*) FROM movies;
SELECT COUNT(movie_length) FROM movies;

The spoken forms in the lesson are "select count star from table name" and "select count and then the column name of choice from table name". The NULL rule is confirmed by the standard reference demo: a table holding \(\{1, 3, 5, \text{NULL}\}\) returns \(\text{COUNT}(\ast) = 4\) but \(\text{COUNT}(\text{val}) = 3\). So \(\text{COUNT}(\ast)\) counts rows, \(\text{COUNT}(\text{column})\) counts values.

Worked example — how many movies? The lesson table movies is checked two ways. First the aggregate:

SELECT COUNT(*) FROM movies;

Result: \(n = 53\). Then the eyeball check:

SELECT * FROM movies;

This lists 53 rows, the last numbered 53. Both paths agree: 53 and 53. Next, one column is counted:

SELECT COUNT(movie_length) FROM movies;

Result: \(n = 53\). The column count matches the row count, which means movie_length has no missing entries in this table. Sense-check: if any movie had a NULL length, the column count would come out lower than 53 — a mismatch that is itself a clue about data quality.

Scope: \(\text{COUNT}(\ast)\) counts every row, including a row where every column is NULL. \(\text{COUNT}(\text{column})\) ignores NULL entries in that column only. On an empty table, or a WHERE filter that matches nothing, COUNT returns \(0\), never NULL. (SUM and AVG behave differently there — they return NULL — which is why the zero-versus-NULL distinction matters later.)

Picture the operation as a funnel: 53 rows pour in at the top, the filter holes (NULLs, or a WHERE condition) let some through, and exactly one number drips out the bottom. The funnel never shows which rows passed — that is why the lesson pairs every COUNT with a SELECT * eyeball check.

Pitfalls: First, assuming \(\text{COUNT}(\text{column})\) always equals \(\text{COUNT}(\ast)\) — true here (\(53 = 53\)) only because this column has no NULLs; on real data the two routinely differ. Second, a wrong column name or wrong quote style fails before any counting happens, so the lesson's habit of listing rows first catches the typo while it is still cheap.

Recap: COUNT turns many rows into one headcount — \(\text{COUNT}(\ast)\) counts rows, \(\text{COUNT}(\text{column})\) counts non-missing entries. Next, the DISTINCT form answers a sharper question: not "how many entries" but "how many different entries".

Counting rows is a daily reporting step everywhere: how many titles per language, how many orders per status, how many users per plan. Streaming and warehouse teams run the same headcount shape on tables with billions of rows — the syntax is identical, only the table is bigger.

14.1.2 COUNT Without DISTINCT and With DISTINCT

Hook: "53 movies" and "8 languages" describe the same column — one counts entries, the other counts kinds. Knowing which question you were asked is half the battle.

Plain COUNT counts every row, repeats included. DISTINCT removes repeats first and then counts each different value once. The spoken syntax is "count distinct and the column name in brackets":

SELECT COUNT(movie_lang) FROM movies;
SELECT COUNT(DISTINCT movie_lang) FROM movies;

The working rule. Use \(\text{COUNT}(\ast)\) for "how many rows". Use \(\text{COUNT}(\text{column})\) for "how many entries in this column". Use \(\text{COUNT}(\text{DISTINCT column})\) for "how many different values". Internally the engine first collapses repeats into a set of unique values and then counts the set — duplicates never reach the counter.

Worked example — languages: 53 versus 8. The plain count:

SELECT COUNT(movie_lang) FROM movies;

Result: \(n = 53\) — every row counted, repeats included. The distinct count:

SELECT COUNT(DISTINCT movie_lang) FROM movies;

Result: \(n = 8\). The check is SELECT * FROM movies: the movie_lang column shows English repeated dozens of times, then Japanese, Chinese, and others. That repeat pattern is why 53 collapses to 8. In plain words, 53 tells how many rows exist, 8 tells how many kinds of language exist.

Worked example — directors: 53 versus 37. First the plain count:

SELECT COUNT(director_id) FROM movies;

Result: \(n = 53\). Then:

SELECT COUNT(DISTINCT director_id) FROM movies;

Result: \(n = 37\). So 53 movie rows share 37 different directors — some directors made more than one movie in the table. Sense-check: 37 is well below 53 but well above 1, exactly what a table with a few repeat directors should show.

Across databases the core is identical, with two extras worth knowing. MySQL also allows multi-column distinct counts such as \(\text{COUNT}(\text{DISTINCT a, b})\), which counts unique pairs; PostgreSQL accepts only one expression there, so pairs are counted by concatenating or by grouping in a subquery instead. At the other extreme, Snowflake and Databricks add approximate distinct counters (for example \(\text{APPROX\_COUNT\_DISTINCT}\)) built for billion-row tables where an exact answer is slow and a near-exact answer is enough. Same question, three dialects: exact single-column everywhere, multi-column in MySQL, approximate at warehouse scale.

Scope: DISTINCT treats all NULLs as one repeated value: many NULLs collapse to a single counted entry under \(\text{COUNT}(\text{DISTINCT column})\), while plain \(\text{COUNT}(\text{column})\) skips NULLs entirely. DISTINCT also sorts or hashes the values behind the scenes, so on very large tables it costs more than a plain COUNT.

Imagine dumping 53 labeled marbles into a tray, then picking out one marble of each color: the tray held 53 marbles but your hand holds 8. The tray is the column; your hand is the DISTINCT set.

Pitfalls: First, reading a DISTINCT answer as a row count — 8 is not "8 movies", it is "8 kinds". Second, expecting DISTINCT to show which values repeat; it only returns the number, so list the values with SELECT DISTINCT movie_lang when you need the names.

Recap: Plain COUNT counts rows including repeats; COUNT DISTINCT counts each different value once — 53 versus 8 for languages, 53 versus 37 for directors. Next, WHERE narrows which rows get counted at all.

Exam note: When a question asks for "how many different" or "how many unique", DISTINCT is needed. Without that word, plain COUNT is needed. The lesson's number pairs to recall are 53 rows versus 8 languages and 53 rows versus 37 directors.

14.1.3 COUNT With a WHERE Filter

Hook: Totals for the whole table are rarely what anyone wants — the real question is almost always "how many of these?", and WHERE draws the boundary around "these".

COUNT pairs with WHERE to count only rows that meet a condition. The lesson counts English movies and Japanese movies in the movie_lang column, writing the value in single quotes: movie_lang = 'English'.

Filter-then-count. WHERE runs before the aggregate: the engine first keeps only matching rows, then counts them. The two queries are:

SELECT COUNT(*) FROM movies WHERE movie_lang = 'English';
SELECT COUNT(*) FROM movies WHERE movie_lang = 'Japanese';

Worked example — English: 38. The full data is viewed first with SELECT * FROM movies, then the filter is added:

SELECT COUNT(*) FROM movies WHERE movie_lang = 'English';

Result: \(n = 38\). Check: SELECT * FROM movies WHERE movie_lang = 'English' lists English rows only, and the listed rows tally to 38. So 38 of the 53 movies are in English.

Worked example — Japanese: 4.

SELECT COUNT(*) FROM movies WHERE movie_lang = 'Japanese';

Result: \(n = 4\). Check with sorting:

SELECT * FROM movies ORDER BY movie_lang;

Sorting is ascending unless stated otherwise, so the 4 Japanese rows sit grouped together in the sorted list — matching the count of 4. Sense-check: \(38 + 4 = 42\), leaving 11 movies for the remaining 6 languages, which fits a table where English dominates.

The lesson makes a small habit of this double-check: run the COUNT, then list the rows with SELECT * plus the same WHERE or ORDER BY, and confirm the tally by eye. For English the pair is 38 and 38; for Japanese it is 4 and 4. That habit catches wrong column names and wrong quote use early, while the fix is still a one-character edit. One cross-database caution: text matching is case-sensitive in PostgreSQL ('English' does not match 'english'), while MySQL's default collation matches case-insensitively — so the identical query can return different counts on different engines, and casing bugs hide there.

Scope: WHERE filters rows before aggregation, so a filter that matches nothing yields a count of \(0\). COUNT with WHERE answers "how many in this slice" but never shows the slice — pair it with the SELECT * listing whenever the number looks surprising.

Picture a sieve held over the 53 rows: only rows stamped "English" fall through, 38 of them, and the counter clicks once per falling row.

Pitfalls: First, double quotes around 'English' — string values need single quotes; in PostgreSQL double quotes mean an identifier (a column or table name) and the query fails or, worse, compares against the wrong thing. Second, a trailing space or different capitalisation ('english') silently matches zero rows on case-sensitive engines, returning a confident-looking 0.

Recap: WHERE narrows the rows before COUNT counts them — 38 English and 4 Japanese out of 53. The bridge forward: counting tells how many; SUM, next, tells how much in total.

Counting rows by group is a daily reporting step: how many titles per language, how many orders per status, how many users per plan. COUNT with WHERE is the simplest form of that report, and COUNT DISTINCT answers the follow-up question of how many groups exist at all.

14.2 Totals with SUM

14.2.1 What SUM Does

Hook: Counting says a shop sold 53 items — but the owner wants to know the money in the till. SUM turns a column of numbers into that one total.

SUM adds up all the numbers in a column and returns one total. The spoken syntax is "select sum and the column name from the table name":

SELECT SUM(revenue_domestic) FROM movies_revenues;

Here \(\text{revenue\_domestic}\) is the domestic money column and \(\text{movies\_revenues}\) is the table holding \(\text{movie\_id}\), domestic money, and international money. Think of a cash register tape: each sale prints one line, and at closing time the register adds every line into a single Z-total. SUM is that closing-time addition — many printed lines in, one total out. The analogy breaks where repeats and missing lines are concerned: a register adds every line including duplicates, while SUM DISTINCT and NULL-skipping (covered below) deliberately leave some lines out.

The total as a sum. In symbols, with \(r_i\) for the domestic revenue of row \(i\) and \(n\) rows in the table:

\[ \text{total} = \sum_{i=1}^{n} r_i \]

NULL entries contribute nothing and are skipped, not treated as zero.

Worked example — total domestic money. The lesson builds up in layers so each step can be eyeballed. Raw money rows:

SELECT * FROM movies_revenues;

One column alone:

SELECT revenue_domestic FROM movies_revenues;

Then the wrap:

SELECT SUM(revenue_domestic) FROM movies_revenues;

Result: \(5719.50\). That is the total domestic money across all movies in the table. Sense-check: with 53 movies averaging a little over 100 each, a total near 5700 lands exactly where rough arithmetic predicts.

Scope: SUM runs on numeric columns only and silently skips NULL rows. On an empty set, or a filter matching nothing, SUM returns NULL — not zero — because "no rows to add" is unknown, not zero. Any arithmetic on that NULL total stays NULL downstream.

Picture the column as a vertical stack of coins, one per row; SUM sweeps the whole stack into a single pile and weighs it. The weigh-in reports one number and hides which coins went in — so the lesson builds up in layers.

Pitfalls: First, a NULL total where zero was expected — the empty-set NULL above. Second, assuming the total double-checks the rows; it does not, so keep the raw-column SELECT around until the number looks sane.

Recap: SUM sweeps a numeric column into one total — \(5719.50\) for domestic revenue here — skipping NULLs. Next, WHERE limits which rows join the pile before adding.

14.2.2 SUM With WHERE

Hook: A total over everything answers "how much altogether" — but managers ask "how much from the big earners?" WHERE answers by letting only chosen rows into the sum.

A WHERE clause limits which rows get added. The lesson asks for total domestic money only where that money is greater than 200:

SELECT SUM(revenue_domestic) FROM movies_revenues
WHERE revenue_domestic > 200;

Filter-then-add. The engine first discards every row with domestic revenue at or below 200, then adds the survivors. The comparison order is: filter rows, then aggregate — never the reverse.

Worked example — big earners only. Unfiltered total: \(5719.50\). Filtered:

SELECT SUM(revenue_domestic) FROM movies_revenues
WHERE revenue_domestic > 200;

Result: \(3425\). The filtered total is smaller because rows with 28, 83, and other small amounts are left out; only rows above 200 go into the sum. Sense-check: the dropped small rows must account for \(5719.50 - 3425 = 2294.50\), a plausible pile of small earners.

A small stumble is kept in the lesson because it teaches a real fix: the first try used movies_revenue without the final S and raised an error. Changing it to movies_revenues fixed it and the query ran. The fix is simple — the table name in FROM must match the real table name letter for letter.

Scope: The condition is evaluated per row before any adding happens, so rows failing the test contribute nothing — not even zero. A filter that matches no rows makes SUM return NULL rather than 0.

Pitfalls: First, the missing-S typo above — silent-looking names that do not exist fail loudly; copy the table name from a working query instead of retyping it. Second, comparing with the wrong threshold direction (< for >), which swaps "big earners" for "small earners" and returns a total that looks reasonable but answers the wrong question.

Recap: WHERE trims the rows before SUM adds them — \(3425\) for earners above 200 versus \(5719.50\) overall. The same filter-then-aggregate shape returns next, applied to movie lengths for one language.

14.2.3 SUM Over Movie Length for One Language

Hook: The same two-step dance — slice, then total — works on any numeric column. Here the "money" is minutes of film, and the slice is English titles.

The task adds up movie lengths, but only for English movies. The table is movies, the length column is movie_length, and the filter is movie_lang = 'English'. With \(L_i\) for each English movie length:

\[ \text{total\_length} = \sum_{i=1}^{38} L_i \]

The four-step guard. The lesson builds the query in layers so the row count can be verified before the total is trusted:

SELECT * FROM movies;
SELECT movie_length FROM movies;
SELECT movie_length FROM movies WHERE movie_lang = 'English';
SELECT SUM(movie_length) FROM movies WHERE movie_lang = 'English';

Worked example — total English length. The third query returns 38 rows, matching the earlier COUNT of 38 English movies out of 53 total. The fourth query adds those 38 lengths together and reports a total a little over 4000. Sense-check: \(38 \times 126 \approx 4800\) at the English average near 127 — a total in the low thousands is exactly right, and anything under 3000 or over 6500 would signal a wrong filter.

Scope: The 38-row confirmation is the load-bearing step — it proves the filter kept the intended slice. When the filter step is skipped, the sum silently covers all 53 rows by mistake; when it is kept, the count of 38 acts as a guard.

Imagine filling a bucket only from the English-labeled tap: first count the cups (38 rows), then pour them all in and measure once. Skipping the count means never knowing whether the wrong tap was open.

Pitfalls: First, summing before filtering — the all-53 total looks plausible and is completely wrong for the question asked. Second, reusing a stale row count after the data changes; re-run the COUNT guard whenever the table may have grown.

Recap: Slice to 38 English rows, confirm the count, then SUM — total length a little over 4000. Next, the boundary of SUM itself: what happens when the column is not numeric at all.

14.2.4 SUM Only Works on Numbers

Hook: What is the "total" of a column of movie titles? The question sounds absurd — and the database agrees, loudly.

The lesson tries to sum names to show the edge:

SELECT SUM(movie_name) FROM movies;

This fails. The error says no function matches SUM on character varying — in plain words, there is no SUM for text.

Numbers only. The movie_name column holds text (type character varying); movie_length holds whole numbers (integer). SUM accepts integer, numeric, and other number types and rejects text, dates, and booleans. Change the column back to movie_length and the same query shape works. Later lessons cover converting text into numbers first, but the normal choice is to keep SUM on numeric columns and not force it onto names.

Worked example — the failing sum. Run the name version, read the error naming character varying, swap in the length column:

SELECT SUM(movie_length) FROM movies;

Result: a proper numeric total instead of an error. The error message itself is the answer: it names the offending type (character varying), pointing straight at the column to change or convert. Sense-check: any SUM that errors on type grounds is a column-choice problem, never a syntax problem.

Cross-database note, one version only since the rule is the same everywhere: PostgreSQL rejects \(\text{SUM}(\text{text})\) with "function sum(character varying) does not exist"; MySQL instead coerces silently, summing leading numbers and treating pure text as 0 — same query, different engines, and the MySQL version returns a misleading number rather than a helpful error. Snowflake and Databricks reject text input like PostgreSQL does. The safe habit transfers everywhere: check the column type first, convert explicitly if conversion is truly needed.

Scope: SUM accepts every numeric type (integer, bigint, numeric/decimal, float) but nothing else — no text, no dates, no booleans. Explicit conversion (casting) can bridge the gap, but only when the text genuinely holds numbers.

Pitfalls: First, trusting a coerced total on engines that silently convert text — a column of titles summing to 0 looks like an answer but is garbage. Second, forcing text into SUM without a business need; the lesson calls this poor practice even where a cast would technically work.

Recap: SUM runs on numbers and rejects text — the error names the type to fix. Next, DISTINCT changes which numbers join the sum even when every value is numeric.

14.2.5 SUM With DISTINCT

Hook: Two identical revenue figures walk into a total — should both pay? Usually yes. But when the question is about distinct price tiers, the duplicate should enter only once.

SUM DISTINCT drops repeat values before adding. The spoken form is "sum space distinct and the expression":

SELECT SUM(revenue_domestic) FROM movies_revenues;
SELECT SUM(DISTINCT revenue_domestic) FROM movies_revenues;

Count every copy versus count each value once. Plain SUM adds all 53 entries including duplicates; SUM DISTINCT first collapses repeats into a set of unique values, then adds the set. With \(v\) for a repeated value: plain SUM adds \(v + v\) while DISTINCT adds \(v\) once. Missing (NULL) values are skipped by both forms.

Worked example — the 11.10 gap. Plain SUM: \(5719.50\). DISTINCT SUM: \(5708.40\). The difference is \(5719.50 - 5708.40 = 11.10\). The detective step sorts the column:

SELECT * FROM movies_revenues ORDER BY revenue_domestic;

ORDER BY with no direction sorts small to large. Scrolling that sorted list shows the value \(11.10\) appearing twice. Plain SUM adds both copies; SUM DISTINCT keeps one copy and skips the other, so the total drops by exactly \(11.10\). Sense-check: the gap equals one occurrence of a duplicated value — if the gap matched no visible duplicate, the data (not the query) would need a second look.

Scope: DISTINCT here has two effects: repeat values are used once, and missing values are skipped. The repeat part is shown by the \(11.10\) pair; the missing-value part returns later with AVG and column addition. DISTINCT rarely belongs in money totals — it answers "total of distinct price points", a real but unusual need when repeats would skew a list of unique tiers.

Pitfalls: First, reaching for DISTINCT by default — plain SUM is the correct money total; DISTINCT understates it whenever any value repeats. Second, reading the gap between two SUM answers as an error rather than a clue: when two SUM answers differ by a small sum, sorting the column and scanning for pairs is the fastest check.

Recap: SUM DISTINCT adds each different value once — \(5708.40\) versus \(5719.50\), with the \(11.10\) duplicate explaining the gap. The bridge forward: SUM totals numbers only, while MIN and MAX next bracket any ordered column — numbers, dates, even text.

Exam note: When two SUM answers differ by a small sum, look for a repeated value in the sorted column. Sorting the column and scanning for pairs is the fastest check. And SUM with WHERE answers "total for this slice" — money totals, run-time totals, and length totals are the standard business sums.

14.3 Minimum and Maximum with MIN and MAX

14.3.1 What MIN and MAX Do

Hook: Before any fancy analysis, every analyst asks the same two questions: what is the smallest, and what is the largest? One pair of functions answers both in a single number each.

MIN returns the smallest value; MAX returns the largest value. The spoken syntax is "select min and the column name from the table name", and the same shape for MAX:

SELECT MIN(movie_length) FROM movies;
SELECT MAX(movie_length) FROM movies;

The lesson opens with a plain question: what is the longest movie in the movies table? The length column movie_length holds whole numbers. Think of lining up all 53 movies by length like runners at a starting line ordered by height — MIN photographs the shortest runner, MAX photographs the tallest. Neither tells you anything about the runners in the middle; for the middle you need AVG, covered next.

Ends of the ordering. For numbers \(x_i\), MIN is the least and MAX is the greatest:

\[ \text{shortest} = \min_i x_i, \quad \text{longest} = \max_i x_i \]

NULL entries are ignored — the ends are found among the values actually present.

Worked example — longest is 168. First the column is viewed:

SELECT movie_length FROM movies;

Then sorted to see the ends by eye:

SELECT movie_length FROM movies ORDER BY movie_length DESC;

DESC means large to small, and the top row is \(168\). Then the single-answer form:

SELECT MAX(movie_length) FROM movies;

Result: \(168\).

Worked example — shortest is 87. Sort small to large:

SELECT movie_length FROM movies ORDER BY movie_length ASC;

ASC means small to large and is also the default when no direction is written. The top row is \(87\). Then:

SELECT MIN(movie_length) FROM movies;

Result: \(87\). The pair brackets the whole column: every length sits between 87 and 168. Sense-check: the sorted-column top rows and the MIN/MAX answers agree in both directions — if they ever disagreed, a NULL handling surprise or a wrong column would be the suspect.

Scope: MIN and MAX ignore NULLs, work on numbers, dates, and text alike, and return one of the values actually present — never an invented midpoint. On an empty set they return NULL.

Pitfalls: First, confusing the value with the row: MAX returns 168, not the movie title that runs 168 minutes — fetching the title beside the extreme needs GROUP BY or a subquery, a later topic. Second, assuming MIN/MAX describe the middle; they bracket, they never summarise.

Recap: MIN and MAX return the two ends — 87 and 168 here — ignoring NULLs. Next, WHERE narrows the contest to one slice, such as English titles only.

14.3.2 MIN and MAX With a Language Filter

Hook: "Longest movie overall" is trivia; "longest English movie" is a programming decision. The filter turns a party fact into a business answer.

Add a WHERE condition and the extremes are computed over the slice only. Steps for the longest English movie:

SELECT * FROM movies WHERE movie_lang = 'English';
SELECT MAX(movie_length) FROM movies WHERE movie_lang = 'English';

Extremes of a slice. There are 38 English rows, and MAX over that slice is a different question from MAX over all 53 — the slice can only tie or shrink the overall extreme, never exceed it.

Worked example — longest English: 168.

SELECT MAX(movie_length) FROM movies WHERE movie_lang = 'English';

Result: \(168\) — the longest English movie is also 168 long, tying the overall longest. Check by sorting the filtered rows:

SELECT * FROM movies WHERE movie_lang = 'English'
ORDER BY movie_length DESC;

The first row shows 168, matching the MAX answer. Sense-check: a slice extreme must sit inside the overall bracket \([87, 168]\) — 168 qualifies exactly at the edge.

Worked example — dates: latest English, first Chinese. Dates order the same way because order still has meaning. Latest English release:

SELECT MAX(release_date) FROM movies WHERE movie_lang = 'English';

Result: \(2017\text{-}11\text{-}10\) ("Three Billboards Outside Ebbing, Missouri"), matching the top row of the same rows sorted by release_date DESC. First Chinese release:

SELECT MIN(release_date) FROM movies WHERE movie_lang = 'Chinese';

Result: \(1972\text{-}06\text{-}01\) ("Way of the Dragon"), matching the top row sorted ASC over the 5 Chinese movies. The matching MAX for Chinese is \(2004\), so the Chinese range runs from 1972 to 2004. In symbols, for dates \(d\):

\[ \text{first} = \min d, \quad \text{latest} = \max d \]

Sense-check: 1972 precedes 2004 precedes 2017 — the three answers sit in a sensible chronological order across the two slices.

The lesson notes that GROUP BY will later let one query show the date plus the movie name beside it; for now MIN and MAX return just the single end value. One cross-database extra that helps as a learner: MySQL's \(\text{GREATEST}(\cdot)\) and \(\text{LEAST}(\cdot)\) look similar but are not aggregates — they take the extreme across columns within one row (for example the later of two date columns per movie), while MIN/MAX take the extreme down a column across rows. Same words, perpendicular directions; keep them straight.

Scope: MIN/MAX with WHERE describe the slice only — 38 English rows here, 5 Chinese rows there. Comparing extremes across slices of very different sizes (38 versus 5) is legitimate but thin evidence; the smaller slice's range is naturally narrower.

Pitfalls: First, reading "first" as MAX — "first" and "oldest" mean MIN on dates, "latest" and "newest" mean MAX. Second, mixing date formats in the filter so the slice silently drops rows; the extreme of a half-missing slice is a wrong-looking right answer.

Recap: WHERE plus MIN/MAX gives slice extremes — longest English 168, latest English 2017-11-10, first Chinese 1972-06-01. Next, the same two functions on text, where "largest" stops meaning size.

14.3.3 MIN and MAX on Text

Hook: Ask for the MAX of a pile of titles and you will not get the longest title — you will get the one that wins the dictionary. Same function, new meaning.

MIN and MAX also run on text, but the meaning shifts from size to letter order. The columns movie_name and movie_lang hold text. Numbers sort by size; text sorts A to Z. Think of a library shelf: the leftmost book is MIN, the rightmost is MAX — thickness never matters, only shelf position.

Letter order, not length. The check sorts names A to Z:

SELECT * FROM movies ORDER BY movie_name ASC;
SELECT MAX(movie_name) FROM movies;
SELECT MIN(movie_name) FROM movies;

MIN lines up with ASC (A and B first); MAX lines up with DESC (Z, Y, X, W first). The full string decides, not just the first letter — "A Clockwork Orange" beats other A names because the second and third letters also count in the order. Collation (the database's sorting rulebook) decides ties between cases and accents, and it differs slightly between engines.

Worked example — first and last titles. First row of the A-to-Z sort: "A Clockwork Orange". Last rows sit near W, including "Way of the Dragon" and "Watchmen". Then:

SELECT MAX(movie_name) FROM movies;

Result: "Way of the Dragon" — the last name in A-to-Z order, the W end. And:

SELECT MIN(movie_name) FROM movies;

Result: "A Clockwork Orange" — the first name in A-to-Z order, the A end. Sense-check: A comes before W, and both answers sit at the visible ends of the sorted listing — neither is the longest or shortest string, which is exactly the point.

So the type rule across the lesson is: SUM and AVG need numbers, while MIN and MAX work on numbers, dates, and text. On numbers they give smallest and largest; on dates they give first and latest; on text they give first and last in letter order. Cross-database sameness is the good news here — this rule holds in PostgreSQL, MySQL, Snowflake, and Databricks alike — with one learner-useful extra: where letter order surprises you (lowercase sorting after uppercase, accented letters landing oddly), the cause is the database's collation setting, adjustable per column or per query in every one of these engines.

Scope: Text extremes follow the engine's collation, not pure alphabet intuition — case, accents, and numbers-inside-text sort by rules that vary between PostgreSQL, MySQL, Snowflake, and Databricks. For portable logic, compare folded (uppercased) values explicitly.

Pitfalls: First and biggest: reading MAX on text as "longest string" — it means last in letter order. Second, assuming "A Clockwork Orange" wins on its first letter alone; ordering compares the whole string left to right.

Recap: On text, MIN is first in letter order and MAX is last — "A Clockwork Orange" to "Way of the Dragon". The bridge forward: MIN/MAX bracket any column, but neither describes the middle — AVG, next, does.

Exam note: When a question says "latest", use MAX on the date. When it says "first" or "oldest", use MIN on the date. When it gives text, recall that MAX means last letter order, not longest string. MIN and MAX bracket any column fast — shortest and longest run time, first and latest release — often the first step before a deeper split by group.

14.4 Averages with AVG

14.4.1 What AVG Does

Hook: Extremes tell you the walls of the room; the average tells you where everyone is standing. One number summarises the typical movie in the whole table.

AVG adds up a set of numbers and divides by how many there are, returning one single answer. A set here means a list of numbers. The spoken syntax is "select avg column name from table name", and the lesson's spoken definition is "average function calculates average value on a given set":

SELECT AVG(movie_length) FROM movies;

Think of 53 people pooling their cash and then splitting it evenly: the pool is the SUM, the headcount is the COUNT, and each person's share afterward is the AVG. That picture also explains the NULL rule coming later — a person who never put money in is simply not at the table when the split happens.

Sum divided by count. With \(x_i\) for each length and \(n = 53\):

\[ \text{avg} = \frac{1}{n}\sum_{i=1}^{n} x_i \]

NULL entries are left out of both the sum and the divisor. One type fact is stressed: AVG always returns a numeric value, even when the input column holds whole numbers.

Worked example — average length 126.13. Build-up shown:

SELECT * FROM movies;
SELECT movie_length FROM movies;
SELECT movie_length FROM movies ORDER BY movie_length ASC;
SELECT AVG(movie_length) FROM movies;

The sorted view runs from \(87\) up to \(168\) across 53 rows, with values like 91 and 120 in the middle. The AVG over all of them is \(126.13\) (with more digits after the point). Sense-check: 126 sits comfortably between the walls 87 and 168, a touch above the midpoint 127.5's neighborhood — exactly where a roughly symmetric spread should average. And movie_length stores whole numbers while the answer \(126.13\) has a point part — input type whole number, output type numeric — which matters when the answer feeds more math later.

Scope: AVG accepts numeric columns only, ignores NULLs in both numerator and denominator, and returns a numeric/decimal type even for integer input. On an empty set it returns NULL, not zero.

Picture a balance point on a number line from 87 to 168: the 53 values are weights, and 126.13 is where the line balances. Outliers pull the balance; the middle values anchor it.

Pitfalls: First, treating the average as a value that must exist in the data — 126.13 appears in no row, and that is normal. Second, feeding the AVG output into integer math downstream and losing the point part; keep the numeric type until the final display.

Recap: AVG pools the column and splits evenly — \(126.13\) across all 53 titles, numeric output from whole-number input. Next, the same average over one language slice, where comparison becomes the story.

14.4.2 AVG for One Language Slice

Hook: One average describes; two averages compare. English versus Chinese typical length is a miniature business report in a single query.

Add WHERE to slice before averaging:

SELECT AVG(movie_length) FROM movies WHERE movie_lang = 'English';

Slice, then average. The engine keeps only the matching rows and averages those — the divisor is the slice size, not the table size. The combined form runs two aggregates side by side:

SELECT AVG(movie_length), SUM(movie_length) FROM movies
WHERE movie_lang = 'English';

Worked example — English 126.94, Chinese 121. English result: about \(126.947\). Chinese result: \(121\). So in this table the Chinese average sits below the English average — the lesson's small business read is "what is a typical English movie length in this data". The combined form for English returns AVG about \(126.94\) and SUM about \(4826\) — the total hours across English titles. Swap the filter to Chinese and both answers shrink because only 5 rows feed the math. Sense-check: \(4826 / 38 \approx 127\), which reproduces the AVG — the two aggregates corroborate each other, and any pair that fails this division check has a wrong filter or a NULL surprise.

The function is framed as part of SQL analytics: the aggregate set used for business analysis — compare one slice with another through a single typical value. Same two functions, different slices, and the gap tells a story about the data.

Scope: Averages over slices of very different sizes (38 English versus 5 Chinese) carry very different weight — the 5-row average swings wildly with a single unusual title. Compare the numbers, but report the slice sizes beside them.

Pitfalls: First, averaging the averages — the overall 126.13 is not the mean of 126.94 and 121, because the slices hold different row counts. Second, forgetting that WHERE runs before AVG, so a mistyped language value averages an empty set and returns NULL instead of an error.

Recap: AVG with WHERE gives the slice's typical value — 126.94 English, 121 Chinese, with SUM 4826 corroborating via division. Next, DISTINCT changes the question from "average of all rows" to "average of distinct values".

14.4.3 AVG With DISTINCT

Hook: If three movies each run 117 minutes, should 117 count three times or once? Both answers are defensible — they just answer different questions.

Plain AVG uses every row; AVG DISTINCT drops repeats first, then averages the survivors. The spoken form is "average space distinct":

SELECT AVG(movie_length) FROM movies WHERE movie_lang = 'English';
SELECT AVG(DISTINCT movie_length) FROM movies WHERE movie_lang = 'English';

All rows versus unique values. With \(U\) for the set of unique lengths:

\[ \text{avg\_distinct} = \frac{1}{|U|}\sum_{v \in U} v \]

Plain AVG feeds all 38 numbers into the sum and divides by 38; DISTINCT feeds each different length once and divides by the count of different lengths.

Worked example — 126.94 versus 127.74. Plain form over 38 English rows: \(126.9476\) in full. The sorted check:

SELECT movie_length FROM movies WHERE movie_lang = 'English'
ORDER BY movie_length ASC;

That list runs from 87 up to 168 with many repeats: 117 appears three times, 119 appears twice, 168 appears twice. DISTINCT form: \(127.74\). The gap comes only from dropping repeat lengths and averaging the unique set. Sense-check: repeats cluster at 117–119, below the mean, so removing their extra weight should nudge the average up — and 127.74 is indeed above 126.94. The direction of the shift confirms the mechanism.

Scope: "Average of all rows" and "average of distinct values" are two different questions with two different answers here (126.94 versus 127.74). DISTINCT answers the rarer question — the typical length tier, not the typical movie — and stating which question was asked is part of the answer.

Pitfalls: First, using DISTINCT to "clean" data — it does not remove errors, only genuine repeats, and it silently changes the question. Second, comparing a DISTINCT average from one slice with a plain average from another; the two are different statistics and their gap means nothing.

Recap: AVG DISTINCT averages the unique set — 127.74 versus 126.94, with low-end repeats explaining the upward nudge. Next, the two boundaries of AVG: text it rejects, NULLs it skips.

14.4.4 AVG Rejects Text and Skips Missing Values

Hook: Two traps share one section because both spring from the same instinct: feeding AVG something it cannot eat — words, or holes where numbers should be.

AVG on names fails, the same edge as SUM:

SELECT AVG(movie_name) FROM movies;

movie_name is text. The error says no function matches AVG on character varying — in plain words, AVG has no form for text. There are paths that change text into numbers first (covered in later lessons on data-type change), but the normal rule stands: AVG is for numbers, and the lesson adds that forcing text into AVG without a business need is poor practice. Cross-database sameness with one MySQL-flavored warning: MySQL coerces instead of erroring, averaging leading numerics and treating pure text as 0 — a silent wrong number where PostgreSQL gives a loud helpful error — while Snowflake and Databricks reject text like PostgreSQL does.

Skipped, not zeroed. Missing values get a full demo with a fresh table:

CREATE TABLE demo_avg (numb INT);
INSERT INTO demo_avg (numb) VALUES (1), (2), (3), (NULL);
SELECT * FROM demo_avg;

Rows: \(1\), \(2\), \(3\), NULL. Then:

SELECT AVG(numb) FROM demo_avg;

The rule: AVG skips NULL rows — it averages 1, 2, 3 and leaves NULL out of both the sum and the divisor. So the math is \((1 + 2 + 3) / 3 = 2\), not divided by 4. The table is then removed:

DROP TABLE demo_avg;

A refresh confirms the table is gone. This matches the standard reference behavior exactly: adding a NULL row to \(\{1, 3, 5\}\) leaves SUM at 9 and AVG at 3.0000 while only \(\text{COUNT}(\ast)\) moves.

Worked example — the NULL that does not drag. Values in: 1, 2, 3, NULL. Sum of survivors: \(1 + 2 + 3 = 6\). Divisor: 3, not 4. Result: \(2\). The wrong version — treating NULL as zero — would give \((1 + 2 + 3 + 0)/4 = 1.5\), a smaller wrong mean and the classic trap. Sense-check: removing a missing entry should never move the average, and 2 is exactly the average of \(\{1, 2, 3\}\) alone.

Scope: Every aggregate except \(\text{COUNT}(\ast)\) ignores NULLs: SUM, AVG, MIN, MAX, and \(\text{COUNT}(\text{column})\) all skip missing entries. The NULL rule keeps missing data from dragging the mean down — but it also means an average over mostly-missing data describes only the survivors.

Pitfalls: First, treating NULL as zero — the 1.5-versus-2 trap above. Second, assuming the error on text means broken syntax; the syntax is fine, the column type is the problem, and the error names it (character varying).

Recap: AVG rejects text and skips NULLs — \((1+2+3)/3 = 2\), never divided by 4. The bridge forward: aggregates collapse columns, but the five arithmetic operators next build new values within each row before any collapsing happens.

Exam note: AVG output type is numeric even for whole-number input. AVG skips NULL — it does not treat NULL as zero, and treating it as zero gives a smaller wrong mean. Typical value per group is a core report: AVG with WHERE gives the slice, AVG with DISTINCT gives the unique-tier view.

14.5 Combining Columns with Mathematical Operators

14.5.1 The Five Operators

Hook: Aggregates answer questions about columns; operators answer questions about rows. Before collapsing anything, you can add, subtract, and divide within each row — and one of the five operators is a famous trap.

Five signs combine numbers: plus for addition, minus for subtraction, division sign, star for multiplication, and percent for modulus, also called remainder. Division versus modulus is flagged as the pair people mix up. Think of a pocket calculator with five big buttons: four do what every shopper expects, and the fifth (%) answers "after dealing out equal shares, what is left in my hand?"

One row in, one value out. Unlike aggregates, operators work row by row — no collapsing, no grouping. Each is shown with plain numbers first:

SELECT 2 + 10 AS addition;
SELECT 2 - 10 AS subtraction;
SELECT 10 / 2 AS divide;
SELECT 2 * 10 AS multiply;
SELECT 15 % 2 AS modulus_test;

Results: \(2 + 10 = 12\); \(2 - 10 = -8\) (swapping to a larger first number gives a plus answer); \(10 / 2 = 5\). In symbols:

\[ 12 = 2 + 10, \quad -8 = 2 - 10, \quad 5 = 10 / 2, \quad 20 = 2 \times 10 \]

Worked example — integer division traps 11 / 2.

SELECT 11 / 2;

Result: \(5\). The true quotient is \(5.5\), but whole-number input gives whole-number output, so the point part is cut — not rounded, cut (truncated toward zero for positive values). The fix casts toward numeric with the double-colon shape:

SELECT 11::numeric / 2;

That returns \(5.50\). The cause is named now, with full type-change detail deferred to a later lesson: whole-number math yields whole-number form in this engine. The same idea is shown with \(2.56\) and with a value like 23: when point values feed the math, the answer keeps point digits. Sense-check: \(5 \times 2 = 10 \ne 11\) exposes the lost half instantly — whenever a division result times the divisor misses the dividend, truncation ate the remainder.

Worked example — modulus keeps the remainder.

SELECT 14 % 2;
SELECT 15 % 2;

\(14 / 2 = 7\) with no remainder, so \(14 \bmod 2 = 0\). \(15 / 2 = 7\) with remainder \(1\), so \(15 \bmod 2 = 1\). In symbols:

\[ 14 \bmod 2 = 0, \quad 15 \bmod 2 = 1 \]

So division answers "how many times", modulus answers "what is left over".

Dialect extras, kept tight since the lesson engine is PostgreSQL-flavored: the double-colon cast (11::numeric) is PostgreSQL's shorthand — the portable equivalent is \(\text{CAST}(11 \text{ AS NUMERIC})\), which works in MySQL, Snowflake, and Databricks too. For remainders, MySQL and Oracle Database provide a \(\text{MOD}(10, 4)\) function form (yielding 2), and MySQL even accepts real numbers (\(\text{MOD}(22.75, 5) = 2.75\)); SQL Server has no \(\text{MOD}\) function and, like PostgreSQL, uses the % operator instead (\(10 \% 4 = 2\)). Same remainder, three spellings: % in PostgreSQL and SQL Server, \(\text{MOD}(\cdot)\) in MySQL and Oracle, \(\text{MOD}(\cdot)\) also in Snowflake and Databricks.

Scope: Integer division truncation applies when both operands are whole numbers — one numeric operand is enough to keep the point part. Modulus needs integer-like operands for the classroom meaning; on floats its behavior varies by engine, so keep it to whole numbers unless the docs for your engine say otherwise.

Pitfalls: First, expecting \(11 / 2 = 5.5\) from whole-number inputs — the engine cuts to 5 with no warning. Second, swapping division and modulus: / counts full shares, % reports the leftover; asking one when you mean the other is the flagged mix-up.

Recap: Five row-wise operators — +, -, /, *, % — with integer division truncating (11/2 is 5 until cast to 5.50) and modulus returning the leftover. Next, the operators combine two real columns into a per-row total.

14.5.2 Adding Two Columns Into a Total

Hook: Domestic plus international revenue per title is the business's real number — and it lives in no column until you build it from two.

The movies_revenues table holds movie_id, revenue_domestic, and revenue_international. Some rows hold NULL in one money column. The task: add the two money columns into one total per movie — row by row, not collapsed.

Per-row expression with an alias. View first, then build:

SELECT * FROM movies_revenues;
SELECT movie_id, revenue_domestic, revenue_international FROM movies_revenues;

All 53 rows show three columns. Then the sum expression with an alias:

SELECT movie_id, revenue_domestic, revenue_international,
  (revenue_domestic + revenue_international) AS "total_revenue"
FROM movies_revenues;

The spoken steps are "do a comma and a bracket and add revenues domestic plus revenues international as total revenue". The alias uses double quotes, "total_revenue", so the name holds together as one label. In symbols, with \(d\) for domestic and \(g\) for international:

\[ \text{total} = d + g, \quad \text{and if either is NULL, total is NULL} \]

Worked example — the NULL that eats a total. One row shows domestic \(28.10\) with a total of NULL — because the other money entry on that row is NULL. The rule: number plus NULL gives NULL. The engine skips the math for that row instead of treating the missing entry as zero. Sense-check: \(28.10 + \text{unknown}\) is genuinely unknown, not 28.10 — the NULL total is the honest answer, and any report needing a number there must decide explicitly (for example with \(\text{COALESCE}\)) rather than silently zero-filling.

Later lessons cover casting and grouping to handle these rows, but the default is named now. One portable extra for the toolkit: \(\text{COALESCE}(g, 0)\) substitutes 0 for a missing entry, so \(d + \text{COALESCE}(g, 0)\) totals the row instead of NULL-ing it — available with identical spelling in PostgreSQL, MySQL, Snowflake, and Databricks. Same concept as the lesson's rule; the function is the opt-in override.

Scope: NULL spreads through every arithmetic operator, not just +: NULL minus, times, or divided by anything is NULL. This is the row-wise mirror of the aggregate rule — aggregates skip NULLs, but row arithmetic propagates them.

Pitfalls: First, unquoted multi-word aliases — without the quotes the engine can misread the alias, so quote "total_revenue" exactly as shown. Second, assuming a missing entry counts as zero; it counts as unknown, and the whole row's total becomes unknown with it.

Recap: Two columns add row-wise into "total_revenue", but number plus NULL gives NULL — the \(28.10\) row proves it. Next, the computed total feeds sorting and filtering, where NULLs cause a second surprise.

14.5.3 Sorting and Filtering the Computed Total

Hook: A per-row total you cannot rank or filter is a dead number. Two SQL tricks — positional sorting and NULL-aware ordering — bring it to life.

The computed total can feed ORDER BY by column position. Here the select list is 1: movie_id, 2: revenue_domestic, 3: revenue_international, 4: the total expression — so position 4 means the total:

SELECT movie_id, revenue_domestic, revenue_international,
  (revenue_domestic + revenue_international) AS "total_revenue"
FROM movies_revenues
ORDER BY 4 DESC;

Position, direction, NULL placement. DESC puts large totals first. But NULL totals sort first too, hiding the real top movie — the fix is NULLS LAST:

SELECT movie_id, revenue_domestic, revenue_international,
  (revenue_domestic + revenue_international) AS "total_revenue"
FROM movies_revenues
ORDER BY 4 DESC NULLS LAST;

Now the true largest totals lead and all NULL rows sit at the bottom. WHERE can also filter on the math expression to drop NULL totals:

SELECT movie_id, revenue_domestic, revenue_international,
  (revenue_domestic + revenue_international) AS "total_revenue"
FROM movies_revenues
WHERE (revenue_domestic + revenue_international) IS NOT NULL;

After this filter no NULL totals remain.

Worked example — ranking the true top movie. Unadorned ORDER BY 4 DESC: the top row is a NULL total masquerading as the leader — the lesson's top row sits at movie 48 only after the fix. Add NULLS LAST: genuine largest totals lead, NULL rows sink to the bottom. Add the WHERE variant: NULL totals vanish from the output entirely. Sense-check: the IS NOT NULL row count plus the count of NULL-total rows must equal 53 — the two filters partition the table with no gaps and no overlaps.

The lesson notes that later, with subqueries, the alias "total_revenue" can be referenced by name instead of repeating the whole expression — but for now the full expression is repeated in WHERE, because WHERE cannot see SELECT aliases at the same query level. Portability note: positional ORDER BY 4 and NULLS LAST both work in PostgreSQL; MySQL accepts the position but has no NULLS LAST keyword (NULLs sort first for DESC there, so the WHERE filter or a - trick does the job); Snowflake and Databricks support both spellings as shown.

Scope: ORDER BY position numbers refer to select-list order — 4 means the fourth listed item — so editing the SELECT list silently renumbers every positional reference. Prefer the alias name wherever the engine allows it; keep positions for quick ad-hoc ranking only.

Pitfalls: First, ranking without NULLS LAST and crowning a NULL as the top movie. Second, referencing the "total_revenue" alias inside WHERE at the same level — the engine rejects it, so repeat the full expression until subqueries arrive.

Recap: Rank the computed total with ORDER BY 4 DESC NULLS LAST so real totals lead, and filter NULL totals with the full expression plus IS NOT NULL. Per-row math before aggregating is standard — domestic plus international per title, price plus tax per line — then sort high to low with NULLS LAST so missing data never poses as the top row.

Exam note: ORDER BY position number refers to the select list order, so 4 means the fourth listed item. NULLS LAST is the guard when the sorted column can hold NULL. And integer math keeps integer form: 11 divided by 2 shows 5 until a numeric cast gives 5.50; modulus gives the remainder (14 mod 2 is 0, 15 mod 2 is 1).

Exam Guidance Summary

COUNT with no condition counts rows; COUNT DISTINCT counts kinds. When the question wording says "different" or "unique", DISTINCT is needed — the lesson pair to recall is 53 rows versus 8 languages and 53 rows versus 37 directors. With WHERE, the filter runs first: 38 English and 4 Japanese out of 53, each double-checked against a SELECT * listing.

Exam note: SUM and AVG accept numbers only — text input raises a missing-function error naming character varying (PostgreSQL, Snowflake, and Databricks error loudly; MySQL coerces silently, which is more dangerous). AVG output is numeric even when the input column holds whole numbers (\(126.13\) from integer lengths). MIN and MAX accept numbers, dates, and text: on dates, latest is MAX and first is MIN (\(2017\text{-}11\text{-}10\) latest English, \(1972\text{-}06\text{-}01\) first Chinese); on text, MAX is last letter order and MIN is first letter order ("Way of the Dragon" versus "A Clockwork Orange"), not longest or shortest string.

Exam note: NULL handling splits by function shape. AVG and SUM skip NULL rows, so 1, 2, 3, NULL averages over 3 rows (\((1+2+3)/3 = 2\)); \(\text{COUNT}(\ast)\) counts the NULL row while \(\text{COUNT}(\text{column})\) skips it. Column addition spreads NULL, so number plus NULL gives NULL (the \(28.10\) row totals NULL). Sorting with possible NULL needs NULLS LAST when the goal is a true top row. Integer math keeps integer form: 11 divided by 2 shows 5 until a numeric cast (11::numeric, portably \(\text{CAST}(11 \text{ AS NUMERIC})\)) gives 5.50. Modulus gives the remainder: 14 mod 2 is 0, 15 mod 2 is 1. ORDER BY with a number refers to select-list position (4 means the fourth listed item).

Key Industry Applications

Language and director tallies drive catalog reporting: COUNT per language gives 38 English and 4 Japanese from 53 titles, while COUNT DISTINCT gives 8 languages and 37 directors. The same shape reports orders per status, users per plan, and suppliers per nation — the headcount-then-kinds pair (53 versus 8) is the standard first page of any content or commerce dashboard.

Money and length totals feed finance and programming decisions. Total domestic money is 5719.50 across all rows and 3425 for the slice above 200; total English length is over 4000 across 38 titles. Domestic plus international per title gives a per-movie total used for ranking, with the top movie found by sorting the total high to low under NULLS LAST — the same per-line-math-then-rank pattern prices order lines with tax, scores leads, and prioritises backlogs in every reporting stack.

Brackets and typical values compress a column into plannable numbers. Lengths run from a MIN of 87 to a MAX of 168; Chinese releases run from 1972 to 2004, with the English latest at 2017-11-10. Average length is 126.13 overall, 126.94 for English, 121 for Chinese, and 127.74 for distinct English lengths. Those single numbers let a team compare slices, set a typical run time for a new title, and spot the slice — like the 5-title Chinese set — whose small size makes its average fragile. At warehouse scale the same aggregates run unchanged, with approximate distinct counters (Snowflake, Databricks) trading exactness for speed on billion-row tallies.
