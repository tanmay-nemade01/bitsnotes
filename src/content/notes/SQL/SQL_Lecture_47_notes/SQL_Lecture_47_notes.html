47.1 Custom Index Methods With Operator Classes

What if a phone book were sorted by the last four digits of every number instead of by name? That is exactly what this section builds: a PostgreSQL index that orders Social Security numbers by their tail first, without touching the stored rows.

An index (a helper structure the database uses to find rows fast, without scanning the whole table) in PostgreSQL is best seen as a framework rather than a fixed structure. The built-in access method (the engine part that knows how to walk a tree, here btree) knows how to walk a tree and compare keys, but the meaning of "smaller" and "larger" can be supplied by the user through an operator class (a named bundle that ties ordering operators and a comparison function to one data type for one access method). That opening makes it possible to index the same stored text in a new order without changing the stored rows at all. The session builds one full example around United States Social Security numbers of the shape 111-11-0100, where the goal is an index ordered by the last group first instead of the usual left-to-right text order.

Think of it like a library that keeps the books on the shelves in acquisition order but maintains a separate card catalog sorted by title. The books never move; only the catalog cards are rewritten into title order. Here the stored ssn values are the books, and the canonical rewritten keys are the catalog cards.

47.1.1 Why a plain index cannot order by the tail of a value

A Social Security number such as 111-11-0100 is stored here as plain text (a variable-length character string, for example '111-11-0100') in a one-column table called ssn. A default B-tree index on that column compares whole strings from the first character onward, so rows come back grouped by their leading digits: all values starting with 111 sort together, then values starting with 222, no matter what tail digits follow. The working example uses two families of sample rows, one shaped like 111-11-0100 with tails 0100, 0140, 0160, and one shaped like 222-22-0120 with tails near 0120, and a plain ORDER BY ssn returns them in leading-digit order, for example 111-11-0140 before 222-22-0120 even though 0140 is greater than 0120.

The request is different: sort and look up by the last four digits first, then by the rest. A stock index cannot do that because it never reorders characters before comparing. So the work proceeds in four stages: first a canonicalizing function that rewrites each value into index order, second a three-way comparison function built on that canonical form, third an operator class that binds the comparison to the B-tree access method, and fourth a CREATE INDEX statement that names the new operator class. Each stage is tested on its own before the next one is built.

The four-stage build. Stage 1 rewrites each value with fn_fix_ssn into a tail-first key. Stage 2 compares two rewritten keys with ssn_compare returning \(-1\), \(0\), or \(1\). Stage 3 registers operators plus the comparator in a new operator class. Stage 4 creates idx_ssn on the column using that class.

The contrast below pins down why each stage is needed.

Dimension Plain B-tree on ssn Custom tail-first index
Compared value Stored string as-is, for example 111-11-0100 Rewritten key, for example 010011111
Sort priority Leading digits dominate Last four digits dominate
Partial-tail lookup Full scan or filter after scan Index can serve tail-first order directly
Extra objects None Two functions plus one operator class

Pick the plain index when queries filter or sort by the full value left to right. Pick the custom class when the access pattern is tail-first, such as "find everyone whose number ends in 0120".

Fraud review, call-center lookup, and benefits desks often search partial identifiers such as the last four digits of a national number. A tail-first index matches that access pattern instead of forcing a full scan. The same pattern recurs in other domains: case-insensitive name search rewrites Smith to smith before comparing, phone search strips spaces and dashes, and unit-normalized search converts 5 km and 5000 m into one comparable scale.

Supporting cross-database note: this operator-class mechanism is PostgreSQL-specific. MySQL has B-tree indexes but no user-defined operator classes; the closest equivalent there is a functional key part or a stored generated column holding the rewritten value with a plain index on it, for example a generated column ssn_tail defined as the tail-first expression. Snowflake and Databricks/Spark SQL likewise have no CREATE OPERATOR CLASS; Snowflake relies on micro-partitions plus clustering keys, and Databricks relies on partitioning, Z-ordering, and file skipping rather than custom comparators. If the same tail-first idea is needed there, rewrite the value in a view or derived column and sort or filter on that. The lecture's four-stage PostgreSQL build below is the PostgreSQL version of a portable idea: canonicalize, then compare, then index.

47.1.2 Canonicalizing function fn_fix_ssn

A phone number written as (555) 123-4567 and one written as 5551234567 reach the same person, but a naive string sort treats them as unrelated. The fix used here is to rewrite every value into one canonical spelling before comparing, the way a post office rewrites every address into postcode-first order before sorting mail.

The first step moves the sortable part to the front and strips punctuation so comparison is a plain string comparison. In plain words, the function takes one text input holding a value shaped like AAA-BB-CCCC, pulls characters from position 8 onward as the new head, then appends characters 1 through 7 with dashes removed. For 111-11-0100 the head from position 8 is 0100 and the cleaned prefix is 11111, giving the canonical key 010011111. The analogy breaks at one point: mail sorting changes the physical route, while this rewrite never touches stored rows and only changes the index key.

Canonical key definition. Let \(s\) be the stored text value such as 111-11-0100. Let \(tail\) be the substring from position 8 onward, written inline as \(tail = substring(s, 8)\). Let \(head\) be the cleaned prefix, written as \(head = replace(substring(s, 1, 7), -, empty)\) where \(-\) is the dash character and \(empty\) is the zero-length string that deletes each dash. The full canonical key is the concatenation of the two parts:

\[ canonical(s) = substring(s, 8) \text{ followed by } replace(substring(s, 1, 7), \text{-}, \text{empty}) \]

Here \(s\) is the stored value, \(substring(s, 8)\) means characters from position 8 to the end with positions counted from 1 including dashes, and \(replace\) with \(empty\) deletes every dash. For \(s = \text{111-11-0100}\), the result is \(\text{010011111}\).

Position arithmetic shows why 8 and 7 are the right constants. Lay out 111-11-0100 with 1-based positions:

Positions 1-3 4 5-6 7 8-11
Characters 111 - 11 - 0100

So characters 1 through 7 are 111-11- (seven characters including two dashes) and characters 8 onward are the four-digit tail. Stripping dashes from the seven-character prefix leaves five digits, and appending gives a nine-character key of the shape CCCCAAAAA. Two worked substitutions: 111-11-0100 gives head 0100 plus cleaned prefix 11111, giving 010011111; 222-22-0120 gives head 0120 plus cleaned prefix 22222, giving 012022222. Since 0100 sorts before 0120 as plain text, the new order groups by tail first.

The build proceeds interactively: first a SELECT substring(...) test on position 8 to confirm the tail extraction, then a SELECT replace(substring(... from 1 for 7), '-', '') test to confirm dash removal, and only then the combined RETURN. Written with single-quoted bodies to keep the draft free of dollar quoting, the function reads:

CREATE OR REPLACE FUNCTION fn_fix_ssn(first_arg text)
RETURNS text AS
'SELECT substring(first_arg from 8)
    || replace(substring(first_arg from 1 for 7), ''-'', '''')'
LANGUAGE sql IMMUTABLE;

Line by line: first_arg text names one input of type text; RETURNS text declares a text result; the body concatenates with || the tail part and the dash-stripped prefix part; LANGUAGE sql marks it a plain SQL function; IMMUTABLE promises the output depends only on the input. The alternate spoken form wraps the same RETURN expression in a plpgsql block with BEGIN and END, which behaves identically for this expression.

Trace: fn_fix_ssn('111-11-0100'). Step 1: substring('111-11-0100' from 8) gives 0100. Step 2: substring('111-11-0100' from 1 for 7) gives 111-11-, and replace(..., '-', '') gives 11111. Step 3: 0100 || 11111 gives 010011111. Sense-check: the tail now leads, so ordering by canonical key is ordering by tail first.

Scope: this rewrite assumes every value has exactly the shape AAA-BB-CCCC with dashes at positions 4 and 7. Assumption: the tail is always four characters starting at position 8. If a row holds a malformed value such as 111110100 with no dashes or a short tail, the position constants pick the wrong characters and the index order becomes meaningless. A production version would validate the shape with a check constraint or a regular expression before indexing.

Picture the effect as two columns side by side: the left column lists stored values 111-11-0160, 111-11-0100, 222-22-0120 in leading-digit order, while the right column lists their keys 016011111, 010011111, 012022222. Draw an arrow from each stored value to its key, then sort by the right column: 010011111, 012022222, 016011111. The takeaway is that sorting keys reorders the rows tail-first while stored values never move.

Pitfalls. Testing only one input family hides the bug where positions are off by one; always test at least one 111-* and one 222-* value. Forgetting IMMUTABLE blocks the function from index use, because only immutable functions may appear in an index definition since the stored key must never change for the same input. Using substring with 0-based counting (as in some other databases) shifts every character; in PostgreSQL positions start at 1.

A quick check applies the function to the whole table with SELECT fn_fix_ssn(ssn) FROM ssn, confirming rows such as 111-11-0100 mapping to a key headed by 0100 and 222-22-0120 mapping to a key headed by 0120. Stored rows stay untouched; only the index key is rewritten. In MySQL the same check would read SELECT CONCAT(SUBSTRING(ssn, 8), REPLACE(SUBSTRING(ssn, 1, 7), '-', '')) FROM ssn, since MySQL spells the functions SUBSTRING and REPLACE with commas rather than FROM/FOR keywords; Snowflake and Databricks also support SUBSTRING/SUBSTR plus REPLACE, so the rewrite expression ports with small syntax changes even though the operator-class wrapper does not.

Exam note: be ready to write the canonicalizing expression from memory with substring and replace, to state the position constants 8 and 7 with the AAA-BB-CCCC layout, and to give one input-to-key mapping such as 111-11-0100 to 010011111.

47.1.3 Three-way comparison function ssn_compare

Indexing comes down to pairwise comparison, so the next function answers one question for any two inputs: which canonical key sorts first. The strategy uses three branches over the canonical form: when the fixed form of the first input is less than the fixed form of the second input, return minus one; when it is greater, return one; otherwise return zero. In plain words, "less" means earlier in tail-first order and "greater" means later in tail-first order. This is the same sign convention as C's strcmp or Java's compareTo: negative for first-earlier, positive for first-later, zero for tie.

Three-way sign rule. Let \(a\) and \(b\) be text inputs such as 111-11-0100 and 222-22-0120. Let \(c(x)\) be the canonical key \(canonical(x)\) from the previous section. Let \(cmp(a, b)\) be the integer sign result defined by:

\[ cmp(a, b) = -1 \text{ when } c(a) < c(b), \text{ } 1 \text{ when } c(a) > c(b), \text{ } 0 \text{ otherwise} \]

Here \(<\) and \(>\) are plain text ordering on the canonical keys, \(-1\) means the first key sorts earlier, \(1\) means it sorts later, and \(0\) means the canonical keys tie.

The first cut of the function is written to return text on purpose so the later failure is visible. Its shape, again with single-quoted body text, is:

CREATE OR REPLACE FUNCTION ssn_compare(first_arg text, second_arg text)
RETURNS text AS
'SELECT CASE
    WHEN fn_fix_ssn(first_arg) < fn_fix_ssn(second_arg) THEN ''-1''
    WHEN fn_fix_ssn(first_arg) > fn_fix_ssn(second_arg) THEN ''1''
    ELSE ''0'' END'
LANGUAGE sql IMMUTABLE;

Each WHEN arm compares the two canonical keys and yields a quoted text digit. The alternate spoken form spells the same logic as IF and ELSIF branches inside plpgsql: an IF branch returning minus one for the less-than case, an ELSIF branch returning one for the greater-than case, and a final ELSE returning zero. Live tests pass pairs such as 111-11-0100 against 222-22-0120 and get minus one because the canonical head 0100 is less than 0120, then reverse the argument order and get one. Equal inputs give zero. The function works as a value test at this point, but it is not yet usable as a B-tree comparator because its declared return type is text.

Trace: ssn_compare('111-11-0100', '222-22-0120'). Step 1: canonicalize both, giving 010011111 and 012022222. Step 2: compare as text, where 0100... < 0120... holds. Step 3: take the first WHEN arm, giving -1. Reversed call ssn_compare('222-22-0120', '111-11-0100') takes the second arm and gives 1; identical inputs fall to ELSE and give 0. Sense-check: the sign always answers "which tail sorts first".

That mismatch is deliberate pedagogy. The CREATE OPERATOR CLASS step below fails with "B-tree comparison function must return integer", which names the exact contract: a B-tree comparator takes two keys and must return type integer (a whole-number sign value with minus one for less, zero for equal, and one for greater). The fix drops the old function and re-creates it with RETURNS integer and unquoted numeric results minus one, zero, and one:

DROP FUNCTION ssn_compare(text, text);
CREATE OR REPLACE FUNCTION ssn_compare(first_arg text, second_arg text)
RETURNS integer AS
'SELECT CASE
    WHEN fn_fix_ssn(first_arg) < fn_fix_ssn(second_arg) THEN -1
    WHEN fn_fix_ssn(first_arg) > fn_fix_ssn(second_arg) THEN 1
    ELSE 0 END'
LANGUAGE sql IMMUTABLE;

After the fix, the same pair of calls returns integer minus one in one direction and integer one in the reverse direction. The displayed digits look identical to the text version, but the declared type now satisfies the support-function contract. DROP FUNCTION ... CASCADE is needed if the half-built operator class already depends on the old function name, because the class holds a dependency link to the function.

Scope: the comparator inherits the canonicalizer's shape assumption and adds one more: text ordering on canonical keys must match the intended numeric-tail order, which holds here because every tail is zero-padded to four digits. Assumption: equal canonical keys mean interchangeable rows for ordering. If two distinct stored values ever canonicalized to the same key, they would tie at \(0\) and the index would treat them as peers.

Pitfalls. Returning quoted '-1' instead of bare -1 is the headline trap: same printed digits, wrong type, rejected by the B-tree contract. Re-creating the function without dropping first can leave the old signature behind when argument types differ; always check signatures. Marking the comparator volatile or stable instead of immutable also breaks index use.

Exam note: state the three-branch sign rule with integer returns, explain why a boolean is not enough (a B-tree needs earlier, equal, and later to walk the tree), and explain the "must return integer" error plus its drop-and-recreate fix.

47.1.4 Operator class and B-tree index build

An operator class (the bundle named here opclass_ssn_ops1) tells a named access method which operators and which support function belong together for a given data type. Here the access method is btree, the data type is text, and the new class is named opclass_ssn_ops1. Inside the class body, strategy numbers 1 through 5 bind the five ordering operators and support number 1 names the comparison function:

CREATE OPERATOR CLASS opclass_ssn_ops1
FOR TYPE text USING btree AS
    OPERATOR 1 < ,
    OPERATOR 2 <= ,
    OPERATOR 3 = ,
    OPERATOR 4 >= ,
    OPERATOR 5 > ,
    FUNCTION 1 ssn_compare(text, text);

Strategy-to-operator map. Number 1 binds \(<\) (less than), 2 binds \(<=\) (less than or equal), 3 binds \(=\) (equal), 4 binds \(>=\) (greater than or equal), and 5 binds \(>\) (greater than). FUNCTION 1 is the B-tree support slot for three-way comparison, filled here by ssn_compare over two text inputs. Strategy numbers are the B-tree's fixed vocabulary; the class just fills each slot.

Each OPERATOR line maps a strategy number to a familiar sign. Running this body while ssn_compare still returns text reproduces the integer-return error on purpose; after the function is fixed to return integer, the same statement succeeds. The pgAdmin check refreshes the operator-class list and shows the class properties with its five operators plus the one support function, which is the click-level audit for review and handover.

With the class in place, the index itself is one line that names the column and the class together:

CREATE INDEX idx_ssn ON ssn (ssn opclass_ssn_ops1);

Before this statement the table properties show no index under the ssn table; afterward a refresh shows idx_ssn with its definition on column ssn using the new operator class. The hierarchy matters: canonicalizing function first, then comparison function, then operator class, then index. Skipping the class and naming the column alone would fall back to default text ordering and lose the tail-first behavior.

Trace: build order with the deliberate failure. Step 1: create ssn_compare returning text and run CREATE OPERATOR CLASS, giving the error B-tree comparison function must return integer. Step 2: run DROP FUNCTION ssn_compare(text, text) CASCADE to remove the dependent linkage, re-create with RETURNS integer, and re-test to integer -1 and 1. Step 3: re-run CREATE OPERATOR CLASS, which now succeeds, then run CREATE INDEX idx_ssn. Sense-check: the error is the contract speaking, and CASCADE is needed because the class already depends on the function name.

Picture the dependency chain as four stacked boxes with arrows pointing down: fn_fix_ssn at the bottom, ssn_compare above it, opclass_ssn_ops1 above that, idx_ssn at the top. Each box rests on the one below, so rebuilding a lower box forces everything above it to be rechecked. The takeaway is that the build order is load-bearing, not cosmetic.

Pitfalls. Naming the index column without the class silently uses default ordering and the demo appears to "work" while sorting wrong. Reusing the class name without dropping the old class first raises a duplicate-object error. Forgetting FOR TYPE text USING btree binds the class to the wrong type or method, so later CREATE INDEX cannot find it.

Cross-database supporting note: MySQL, Snowflake, and Databricks have no CREATE OPERATOR CLASS statement. In MySQL the portable substitute is an expression or generated-column index such as INDEX ((SUBSTRING(...))) on recent versions, or a stored generated column plus a plain index. In Snowflake and Databricks the substitute is a derived column in a view or materialized result with clustering or sorting on that column. The PostgreSQL class is worth learning as the PostgreSQL spelling of "teach the index a new sort order", with generated-column indexes as its sibling elsewhere.

47.1.5 Planner control and reading EXPLAIN output

PostgreSQL normally prefers a sequential scan for tiny tables, so the session first shows the default plan with a plain ORDER BY ssn producing a sequential scan with sort key ssn, then changes the planner switch to force the new path during testing:

SHOW enable_seqscan;
SET enable_seqscan = OFF;
SHOW enable_seqscan;

Planner switch. Let \(enable\_seqscan\) be a boolean planner switch where ON allows sequential scans and OFF steers the planner toward index scans when a usable index exists. SHOW reports the current value; SET changes it for the current session. It never changes data, only plan choice.

With the switch off, a probe such as SELECT * FROM ssn WHERE ssn = '111-11-0100' produces an Index Scan using idx_ssn with an Index Cond on the ssn column, and the message pane reports rows handled through that scan. That plan line is the proof that the custom path is reachable. Concretely, an EXPLAIN line reading Index Scan using idx_ssn on ssn with Index Cond: (ssn = '111-11-0100'::text) means the planner walked the custom tree; a line reading Seq Scan on ssn means it scanned every row and the index was bypassed.

Trace: index-use proof. Step 1: with enable_seqscan = ON, run EXPLAIN SELECT * FROM ssn WHERE ssn = '111-11-0100' and see Seq Scan on ssn. Step 2: run SET enable_seqscan = OFF and re-run the same EXPLAIN, now seeing Index Scan using idx_ssn. Step 3: run SET enable_seqscan = ON to restore normal planning. Sense-check: the plan changes with no query rewrite, which shows the index is genuinely usable.

Scope: enable_seqscan = OFF is strictly a demonstration aid that forbids one plan shape so the new path becomes visible on a tiny table. Assumption: on a large production table the planner would pick the index on its own when selective. Leaving the switch off in a shared database would distort every later plan, so the toggle must be reverted immediately after the demo.

The session stresses housekeeping: turn the switch back on afterward with SET enable_seqscan = ON and confirm with SHOW so later queries plan normally.

Exam note: expect a build-order question such as naming the four stages function, comparison, operator class, index, or explaining why the comparator must return integer rather than text, plus reading one EXPLAIN line to say whether the custom index was used.

47.1.6 Worked Examples

Example 1: canonical key for 111-11-0100. Setup takes stored text \(s = \text{111-11-0100}\). Step one extracts \(substring(s, 8) = \text{0100}\). Step two extracts \(substring(s, 1, 7) = \text{111-11-}\) and applies \(replace(\text{111-11-}, \text{-}, \text{empty}) = \text{11111}\). Step three concatenates to canonical(s) = 010011111. Sense-check: the tail now leads, so ordering by canonical key is ordering by tail first.

Example 2: pairwise comparison of 111-11-0100 and 222-22-0120. Setup fixes both inputs: the first maps to a key headed by 0100 and the second to a key headed by 0120. Substitution into the sign rule gives \(c(a) = \text{0100...}\) and \(c(b) = \text{0120...}\) with \(c(a) < c(b)\) as text. The result is cmp(a, b) = -1. Reversing the inputs gives cmp(b, a) = 1, and identical inputs give 0. Sense-check: minus one means first sorts earlier, one means first sorts later, zero means identical canonical keys.

The two examples above use the example-box callout back to back with this prose between them so the boxes stay scannable; the next two continue the same staged pattern.

Example 3: failing then fixed operator class. Setup creates ssn_compare returning text and runs CREATE OPERATOR CLASS. The result is the error B-tree comparison function must return integer. Correction drops the function with DROP FUNCTION ssn_compare(text, text) CASCADE to remove the dependent half-built linkage, re-creates it with RETURNS integer, re-tests to integer -1 and integer 1, and re-runs CREATE OPERATOR CLASS successfully. Sense-check: the error is the contract speaking, and CASCADE is needed because the class already depends on the function name.

Example 4: index use proof. Setup has table ssn with sample rows and index idx_ssn built with the new class. Step one runs EXPLAIN on the equality probe with enable_seqscan on and sees a sequential scan. Step two sets enable_seqscan to OFF and re-runs EXPLAIN, now seeing Index Scan using idx_ssn with an index condition. Step three resets the switch to ON. Sense-check: the plan change with no query rewrite shows the index is genuinely usable.

47.1.7 Student Questions and Answers

Q: Why can a normal index not sort by the last part of the number? A: A normal text index compares the whole stored string from the first character, so leading digits dominate. To lead with the tail, rewrite each value into a canonical key with the tail first and index that derived order through a custom operator class.

Q: Why does the comparison function return minus one, zero, or one instead of true or false? A: A B-tree needs three outcomes for every pair: earlier, equal, or later. Minus one marks the first key earlier, one marks it later, and zero marks equality, and the access method uses those signs to walk the tree. A boolean could only answer equality, never ordering.

The two answers above are separated by this prose so the violet callouts do not run together; the remaining two answers follow the same question-and-resolution shape.

Q: Why did the operator class fail with "must return integer" when the text version already returned minus one? A: The displayed characters matched but the declared type did not. The B-tree support contract requires return type integer, so a function returning the text value minus one is rejected even though it prints the same digits. Re-creating the function with RETURNS integer satisfies the contract.

Q: Why turn enable_seqscan off, and should it stay off? A: Small tables default to sequential scans, which hides the new index during a demo. Setting the switch off forces the planner to show the index path, and switching it back on afterward restores normal planning. It is a test scaffold, never a permanent setting.

Custom operator classes separate what is stored from how it sorts: one rewrite function puts the tail first, one integer comparator orders rewritten keys, one class registers the order with the B-tree, and one index applies it. That separation is what carries forward into the next section, where a different kind of user-defined object, an aggregate, separates per-row folding from per-group reporting.

47.2 User-Defined Aggregate Functions

Built-in sum and avg hide a small machine: start somewhere, fold in one row at a time, then report once per group. What if a taxi meter with a flagfall plus a per-kilometer rate could be packaged as its own sum-like function? This section builds exactly that.

PostgreSQL lets users add new aggregate functions (functions that accept rows grouped by a key and return one value per group, such as sum or avg) that behave like built-ins: they accept rows grouped by a key and return one value per group. The session builds a taxi-fare aggregate from scratch, including the two helper functions it needs, and then checks it against a hand-written query so the new function earns trust.

Think of the aggregate as a cash register that opens each trip with 5 dollars already in the drawer, adds the fare for each leg as it arrives, and prints one receipt per trip at the end. The drawer contents between legs are the running state; the printed receipt is the final result.

47.2.1 Aggregate anatomy: initcond, stype, sfunc, finalfunc

CREATE AGGREGATE takes a name, one or more input argument types, and four defining pieces. INITCOND (the starting value before any row is seen, here 5, meaning a 5-dollar flagfall charged the moment a rider steps in) sets the opening state. STYPE (the data type of the running intermediate state, here numeric for money with decimals) declares what the drawer holds. SFUNC (the state transition function called once per input row, folding the current row into the running state, here taxi_all_rows) does the per-row folding. FINALFUNC (the last function called once per group, turning the final state into the reported result, here taxi_trip_sum) prints the receipt. In the taxi build the transition function is named taxi_all_rows and the final function is named taxi_trip_sum.

Loop plus finish. Start each group at \(state_0 = 5\), update once per row with \(state_{k} = sfunc(state_{k-1}, km_k, rate)\), then report \(result = finalfunc(state_n)\) where \(state_0\) is the opening state in dollars, \(km_k\) is the kilometers of row \(k\) in the group, \(rate\) is the 2.5-dollar per-kilometer price, and \(n\) is the row count of the group. The spoken wording calls SFUNC the "function for each row" and FINALFUNC the "function for each group", which maps directly onto that loop. Groups here come from GROUP BY trip, so with two trip ids the final function runs twice and returns two rows.

The closed form and the stepwise form always agree for this fare shape:

\[ fare(g) = 5 + 2.5 \times \sum_{i \in g} km_i \]

where \(g\) is one trip group and \(km_i\) ranges over that group's rows, while the aggregate reaches the same value stepwise through \(state_0 = 5\) and \(state_k = state_{k-1} + km_k \times 2.5\). The left side is what a hand-written query computes in one shot; the right side is what the aggregate computes row by row.

Fare meters, utility billing, and delivery pricing all combine a fixed boarding or connection charge with a per-unit rate, which is exactly the shape INITCOND plus per-row accumulation computes. The same skeleton also covers running totals with a starting balance, loyalty points with a sign-up bonus, and parcel pricing with a base fee plus per-kilogram charge.

Supporting cross-database note: this four-piece CREATE AGGREGATE spelling is PostgreSQL-specific. MySQL has no CREATE AGGREGATE; the portable substitute is a stored function or application-side accumulation, or the closed-form query 5 + 2.5 * SUM(kilometer) with GROUP BY. Snowflake supports user-defined aggregate functions through JavaScript or Java handlers, and Databricks/Spark SQL supports them through Scala, Java, or Python aggregators, but both spell the pieces differently (handler code plus registration rather than SFUNC/FINALFUNC SQL functions). The lecture's anatomy below is the PostgreSQL version of a portable idea: opening state, per-row fold, per-group finish. The fare numbers stay identical everywhere because the arithmetic is shared; only the registration syntax changes.

Exam note: define INITCOND, STYPE, SFUNC, and FINALFUNC in one line each, and state how many times each runs: INITCOND once per group as a value, SFUNC once per row, FINALFUNC once per group.

47.2.2 Taxi-fare scenario and sample table

The scenario fixes two money facts: boarding costs 5 dollars and each kilometer costs 2.5 dollars, so a ride of \(km\) kilometers in a single row would cost \(fare = 5 + 2.5 \times km\), where \(km\) is the distance in kilometers, \(5\) is the flagfall in dollars, and \(2.5\) is the rate in dollars per kilometer. The aggregate generalizes that to multi-row trips by starting at 5 once per trip and adding 2.5 per kilometer for every row in the trip. The sample table is:

CREATE TABLE taxi (
    id_trip int,
    kilometer numeric
);

Here \(id\_trip\) is an integer trip label and \(kilometer\) is a numeric distance with decimals. Inserted rows deliberately interleave two trips so grouping matters: trip 1 holds 3.5, 4.2, 1.2, and 3.5 kilometers, while trip 2 holds 1.8 and 3.2 kilometers. A plain SELECT * FROM taxi shows six rows across the two trips, and the aggregate must return one fare per trip: 36.00 dollars for trip 1 and 17.50 dollars for trip 2 under the stated rates. Those two numbers become the acceptance test.

Acceptance numbers up front. Trip 1 total distance is \(3.5 + 4.2 + 1.2 + 3.5 = 12.4\) km, so \(fare = 5 + 2.5 \times 12.4 = 5 + 31.00 =\) 36.00. Trip 2 total distance is \(1.8 + 3.2 = 5.0\) km, so \(fare = 5 + 2.5 \times 5.0 = 5 + 12.50 =\) 17.50. Any correct aggregate must print exactly these two values. Sense-check: trip 1 is longer, so its fare is higher, and both exceed the bare flagfall.

Interleaving matters because it proves grouping works: rows arrive mixed together, yet each row's kilometers must land in exactly one trip's drawer. A query without GROUP BY would collapse everything into one fare, which is the classic beginner slip this dataset is designed to catch.

Picture the table as six boarding passes shuffled in a pile, each stamped with a trip number and a leg distance. Sorting the pile into two stacks by trip number and then running the cash-register loop on each stack gives two receipts. The takeaway is that GROUP BY id_trip is the sorting-into-stacks step, and everything after it runs per stack.

47.2.3 Row-level transition function

The transition function takes everything accumulated so far plus the current row and returns the new accumulation. Its three numeric inputs are the running state, the current row kilometers, and the per-kilometer rate, and its result is numeric. In plain words from the session, it "takes all the intermediate values from all the previous calls and data from the current row". Written with a single-quoted body:

CREATE OR REPLACE FUNCTION taxi_all_rows(state numeric, km numeric, rate numeric)
RETURNS numeric AS
'SELECT state + km * rate'
LANGUAGE sql IMMUTABLE;

Per-row fold. Let \(state\) be the running fare so far in dollars, \(km\) be the current row distance in kilometers, and \(rate\) be the dollars-per-kilometer price. One call computes:

\[ new\_state(state, km, rate) = state + km \times rate \]

The expression adds only the current row share to the running total. Multiplication binds first, so \(km \times rate\) is the leg fare and adding \(state\) carries the past forward.

Line by line: the three inputs arrive in order as running state, row kilometers, and rate; RETURNS numeric keeps money with decimals; the body is a single SELECT of the fold expression; LANGUAGE sql IMMUTABLE marks it safe for repeated use inside an aggregate.

Trace: trip 1 starting from 5. After 3.5 km the state is \(5 + 3.5 \times 2.5 = 5 + 8.75 =\) 13.75. After 4.2 km it grows by \(4.2 \times 2.5 = 10.50\) to 24.25. After 1.2 km it grows by \(1.2 \times 2.5 = 3.00\) to 27.25. After the second 3.5 km it grows by another 8.75, landing at 36.00. For trip 2 the same walk starts at 5, adds \(1.8 \times 2.5 = 4.50\) to reach 9.50, then adds \(3.2 \times 2.5 = 8.00\), landing at 17.50. Sense-check: the 5 enters only once, and each call adds just its row's share.

A common wrong reading is that the function adds a fresh 5 per row; the walk shows 5 enters only once through INITCOND, and each call adds just \(km \times rate\). The counter-example in the worked examples quantifies that overshoot so the distinction sticks.

Scope: this transition assumes non-negative distances and a fixed non-negative rate passed per call. Assumption: rows within a group can fold in any order because addition commutes, so \(a + b = b + a\) keeps the total order-independent. If the fold involved a non-commutative step such as string concatenation in arrival order, row order would need an ORDER BY inside the aggregate.

Pitfalls. Swapping the argument order (rate where kilometers belong) silently computes the wrong leg fare with no type error, since all three inputs share type numeric. Forgetting that rate is an argument and hard-coding 2.5 inside the body removes flexibility and breaks the later two-argument aggregate call. Using integer instead of numeric truncates money decimals.

47.2.4 Group-level final function

The final function runs once per group on the finished state and returns the group answer. The teaching version does no extra math so the accumulation logic stays visible:

CREATE OR REPLACE FUNCTION taxi_trip_sum(final_state numeric)
RETURNS numeric AS
'SELECT final_state'
LANGUAGE sql IMMUTABLE;

Per-group report. Let \(final\_state\) be the numeric accumulation handed over after the last row of the group. The function returns that same numeric fare unchanged, written as \(result = final\_state\). It runs once per group, so with two trip groups present it is invoked twice and yields two output rows.

Here \(final\_state\) is the drawer contents after the last leg, and the result is that same value. The session notes that rounding or extra charges could live here, but they are left out to keep the two-function split crisp: the first function folds rows, the second reports groups. Real extensions that belong in FINALFUNC include round(final_state, 2) for cents, adding a night surcharge, applying a discount threshold, or casting to a display type; each keeps SFUNC untouched, which is the point of the split.

This prose separates the two same-family callouts: the identity-function choice above is pedagogy, while the production variations live in this paragraph rather than in a second box. The design lesson is that per-row logic and per-group finishing evolve independently.

Pitfalls. Putting per-row math in FINALFUNC double-counts or under-counts, because FINALFUNC sees only the finished total, never individual rows. Returning a different type than STYPE without declaring it breaks the aggregate registration. Adding the flagfall here as well as in INITCOND charges it twice.

47.2.5 CREATE AGGREGATE and full-query use

With helpers ready, one statement registers the aggregate by naming its inputs and its four defining pieces:

CREATE AGGREGATE fare_taxi(numeric, numeric) (
    INITCOND = '5',
    STYPE = numeric,
    SFUNC = taxi_all_rows,
    FINALFUNC = taxi_trip_sum
);

Registration. The name fare_taxi takes two numeric inputs (kilometers, then per-kilometer price), starts each group at 5 quoted as a string literal per the syntax, carries numeric state, folds rows with taxi_all_rows, and finishes groups with taxi_trip_sum. The quoted '5' is parsed into numeric state at first use; the quotes are required syntax even though the value is numeric.

Using it looks like any built-in aggregate with a GROUP BY key:

SELECT id_trip, fare_taxi(kilometer, 2.5)
FROM taxi
GROUP BY id_trip
ORDER BY id_trip;

Here \(kilometer\) is the per-row column and 2.5 is the rate argument in dollars per kilometer, so each group computes \(5 + 2.5 \times \sum km\) over its rows. The reported answers are 36.00 for trip 1 and 17.50 for trip 2. Trust comes from a side-by-side manual query that writes the same arithmetic without the new function:

SELECT id_trip, 5 + 2.5 * sum(kilometer)
FROM taxi
GROUP BY id_trip
ORDER BY id_trip;

Both queries return the identical pair 36.00 and 17.50, which confirms the aggregate folds each row exactly once and charges the flagfall exactly once per group. The manual form states the closed form directly:

\[ fare(g) = 5 + 2.5 \times \sum_{i \in g} km_i \]

where \(g\) is one trip group and \(km_i\) ranges over that group's rows, while the aggregate reaches the same value stepwise through \(state_0 = 5\) and \(state_k = state_{k-1} + km_k \times 2.5\). Seeing both forms agree is the closing check.

Trace: the two queries side by side. Aggregate path for trip 1: \(5 \to 13.75 \to 24.25 \to 27.25 \to\) 36.00. Manual path for trip 1: \(5 + 2.5 \times 12.4 =\) 36.00. Aggregate path for trip 2: \(5 \to 9.50 \to\) 17.50. Manual path for trip 2: \(5 + 2.5 \times 5.0 =\) 17.50. Sense-check: stepwise folding and one-shot summation agree on both groups.

Picture execution as two lanes merging at the finish: the left lane folds row by row through SFUNC, the right lane sums first then multiplies once, and both lanes pass through the same FINALFUNC gate to print receipts. The takeaway is that the aggregate is a packaged loop that must reproduce the closed form exactly.

Pitfalls. Omitting GROUP BY collapses all trips into one fare, hiding the per-group behavior the test is built to verify. Passing only one argument to a two-argument aggregate raises an arity error, since the rate has no default. Quoting INITCOND wrong (bare 5 instead of '5') fails registration on strict servers. Forgetting ORDER BY id_trip returns correct fares in an unpredictable row order.

Cross-database supporting note: the manual cross-check query 5 + 2.5 * SUM(kilometer) ... GROUP BY runs unchanged in MySQL, Snowflake, and Databricks/Spark SQL, which is why the lecture uses it as the acceptance test. Only the CREATE AGGREGATE wrapper is PostgreSQL-only. A learner moving to MySQL would keep the closed-form query and optionally wrap it in a view; moving to Snowflake or Databricks would keep the same query and reach for their native UDAF frameworks only when the fold logic outgrows plain SQL.

Exam note: expect a parts question asking what INITCOND, STYPE, SFUNC, and FINALFUNC each supply, or a trace asking for the running state after each row of a small group, plus a cross-check of an aggregate answer against the closed form \(5 + rate \times sum\).

47.2.6 Worked Examples

Example 1: trip 1 fare through the transition function. Setup fixes rate 2.5 and rows 3.5, 4.2, 1.2, 3.5 with \(state_0 = 5\). Step one gives \(state_1 = 5 + 3.5 \times 2.5 = 5 + 8.75 =\) 13.75. Step two gives \(state_2 = 13.75 + 4.2 \times 2.5 = 13.75 + 10.50 =\) 24.25. Step three gives \(state_3 = 24.25 + 1.2 \times 2.5 = 24.25 + 3.00 =\) 27.25. Step four gives \(state_4 = 27.25 + 3.5 \times 2.5 = 27.25 + 8.75 =\) 36.00. The final function reports 36.00. Sense-check: each row contributes only its kilometer share, and the single 5 at the start is never repeated.

Example 2: trip 2 fare and the closed-form cross-check. Setup fixes rows 1.8 and 3.2 with the same rate. Accumulation gives \(state_1 = 5 + 1.8 \times 2.5 =\) 9.50 and \(state_2 = 9.50 + 3.2 \times 2.5 =\) 17.50. Closed form gives \(fare = 5 + 2.5 \times (1.8 + 3.2) = 5 + 2.5 \times 5.0 = 5 + 12.50 =\) 17.50. Sense-check: stepwise folding and one-shot summation agree, which is the acceptance test run live.

The first two examples establish the correct behavior; the third shows the characteristic failure mode so the INITCOND lesson sticks.

Example 3: what goes wrong if the flagfall is folded per row. Setup mistakenly adds 5 inside SFUNC on every call. For trip 2 the trace would give \(5 + 5 + 4.50 =\) 14.50 after row one and \(14.50 + 5 + 8.00 =\) 27.50 after row two instead of 17.50. Sense-check: this overshoot shows why INITCOND exists, namely to inject the starting value once per group rather than once per row.

47.2.7 Student Questions and Answers

Q: What does each of INITCOND, STYPE, SFUNC, and FINALFUNC actually do? A: INITCOND sets the starting state before any row is seen, here 5 dollars. STYPE declares the running-state type, here numeric. SFUNC folds one row into the running state and runs once per row. FINALFUNC turns the finished state into the answer and runs once per group.

Q: Why does the transition function need three inputs when each row has only one kilometer value? A: It needs the past, the present row, and the rate together: the running state carries the past, the kilometer column carries the present row, and the rate argument carries the 2.5 price. With fewer than three it could not add the current row share to the correct running total.

The two answers above cover structure and arity; the final answer covers trust in the result.

Q: How do we know the new aggregate is correct and not double-counting the 5 dollars? A: Run the manual query with 5 plus 2.5 times the summed kilometers alongside the new aggregate grouped the same way. Both return 36.00 for trip 1 and 17.50 for trip 2, so the flagfall lands once per group and each row lands once.

Aggregates package a loop plus a finish: INITCOND opens each group's drawer, SFUNC folds every row exactly once, FINALFUNC prints one receipt per group, and the closed-form query certifies the totals. Together with the previous section's separate-what-is-stored-from-how-it-sorts lesson, the lecture shows two faces of PostgreSQL extensibility: new orderings and new computations, each built from small immutable helpers plus one registration statement.

Exam Guidance Summary

No mark split or paper pattern is stated in this session, so guidance here is about likely question shapes rather than weightage. For custom indexes, be ready to list the four build stages in order (canonicalizing function, three-way comparison, operator class, index), to write the canonicalizing expression with substring and replace including the position constants 8 and 7, to state the three-branch sign rule with integer returns, to map strategy numbers 1 through 5 to their comparison signs, and to explain the integer-return error and its CASCADE fix. For aggregates, be ready to define INITCOND, STYPE, SFUNC, and FINALFUNC in one line each, to trace running state row by row from a given start value such as the trip 1 walk from 5 to 36.00, and to cross-check an aggregate answer against the closed form \(5 + rate \times sum\) with the 36.00 and 17.50 acceptance pair.

Exam note: practical checks favor two proofs: EXPLAIN showing the index scan after disabling sequential scans (then resetting enable_seqscan to ON), and identical manual versus aggregate totals for the taxi data. Always state that only immutable helpers may back an index.

Key Industry Applications

Partial-identifier search such as last-four-digits lookup in fraud review, telecom, and service desks motivates tail-first custom indexes: the access pattern asks for the tail first, so the index sorts tail first instead of forcing a full scan. Fare meters, ride-hailing billing, utility metering, and parcel pricing all pair a fixed boarding or connection charge with a per-unit rate, which is the exact INITCOND plus SFUNC shape with a 5-dollar flagfall and a 2.5-dollar rate in the lecture's example.

Domain-ordered indexes such as case-insensitive, locale-aware, or unit-normalized orderings reuse the same canonicalize-then-compare pattern with a different rewrite function: the rewrite changes, while the compare, class, and index stages stay the same.

The pgAdmin operator-class and index property panes give a click-level audit of class name, access method, column, and support function for review and handover. EXPLAIN plan review with Index Scan versus sequential scan lines is the standard proof that a new access path is picked up by the planner, in demos and in production reviews alike.
