9.1 The TO_CHAR Function

Why convert data to text? Raw database storage formats—whether internal 64-bit timestamps or binary floating-point numbers—are optimized for storage efficiency and algebraic calculation, not human readability. How can an application reliably transform an unformatted integer like 100870 or an ISO timestamp like 1972-02-02 into localized, presentation-ready strings such as '\$100,870.00' or 'Wed, 02 Feb 1972' directly inside the query engine?

9.1.1 Purpose and Syntax

The TO_CHAR function converts various data types into a formatted character string. Its output is always of the text data type. The function accepts inputs including a timestamp, an interval, an integer, a double precision number, or a numeric value.

Think of a format mask like a physical stencil or metal template laid over raw numbers or dates. If the stencil has cutouts matching the data digits, the characters pass through cleanly into the output string. If the raw value has fewer digits than the stencil, the remaining spaces are padded; if the raw value has more whole digits than the stencil can accommodate, the template cannot fit the digits.

The classroom explanation highlights this core design:

"The two char function provide us the capability to convert a timestamp, an interval, an integer, a double precision, or a numeric value to a string. That's why it's called two char character to a string. The syntax is very much similar to the other conversion function, i.e. to underscore char you have an expression and then you define your format... two char always return a value in text data type."

Formal Function Signature: \[ \text{TO\_CHAR}(e, f) \to s \] where:

  • \(e \in \mathcal{T}_{\text{input}}\) represents the input expression from the set of supported data types \(\mathcal{T}_{\text{input}} = \{\text{timestamp}, \text{interval}, \text{integer}, \text{double precision}, \text{numeric}\}\).
  • \(f \in \text{text}\) denotes the format pattern mask string.
  • \(s \in \text{text}\) is the resulting formatted character string.

9.1.2 Format Model Specifiers for Numbers and Dates

Format strings use specific pattern characters. They define how numbers and dates appear in the resulting string.

For numeric values, the primary format specifiers include:

  • 9: Represents a value digit position. If a digit exists here, PostgreSQL prints it. If no digit exists, it omits leading zeros and reserves a space for a positive sign.
  • 0: Represents a digit position with leading zeros. If no digit exists here, PostgreSQL displays a zero.
  • .: Represents a period decimal point separator.
  • D: Represents a decimal point separator that uses active locale settings.
  • ,: Represents a comma thousand grouping separator.
  • G: Represents a group separator that uses active locale settings.
  • \$: Places a fixed dollar currency symbol prefix at the start of the formatted number.
  • FM: Prefix modifier ("Fill Mode") that suppresses leading padding spaces and trailing zeroes.

For timestamp and date values, common format specifiers include:

  • YYYY: Year in four digits (such as 2020).
  • YY: Year in two digits (such as 20).
  • MM: Month number from 01 to 12.
  • MONTH: Full uppercase English month name (such as MARCH).
  • Month: Full capitalized English month name (such as March).
  • month: Full lowercase English month name (such as march).
  • MON: Abbreviated uppercase month name (such as MAR).
  • Mon: Abbreviated capitalized month name (such as Mar).
  • DD: Day of the month from 01 to 31.
  • DAY: Full uppercase day of the week (such as WEDNESDAY).
  • Day: Full capitalized day of the week (such as Wednesday).
  • day: Full lowercase day of the week (such as wednesday).
  • DY: Abbreviated day of the week (such as Wed).
  • HH24: Hour of the day in 24-hour time, ranging from 00 to 23.
  • HH or HH12: Hour of the day in 12-hour time, ranging from 01 to 12.
  • MI: Minute within the hour, ranging from 00 to 59.
  • SS: Second within the minute, ranging from 00 to 59.

9.1.3 Worked Examples

The following walkthroughs show how TO_CHAR operates across numbers, tables, and timestamps.

Example 1: Converting an integer to a string with digit masks and handling format overflow.

We begin with the integer value 100870. We convert this integer into a formatted character string using digit specifiers.

SELECT TO_CHAR(100870, '999999');

The format pattern contains six 9 specifiers. These six placeholders match the six digits in 100870. The query returns ' 100870'. The leading space reserves room for an optional positive sign.

Next, we test what happens when we add an extra digit placeholder:

SELECT TO_CHAR(100870, '9999999');

PostgreSQL aligns digits from right to left. Because the format mask provides seven positions for six digits, an extra leading space appears.

Now we test a format pattern with fewer placeholders than digits:

SELECT TO_CHAR(100870, '9999');

The format mask has only four digit slots, but the input integer has six digits. PostgreSQL cannot display the full value. It returns '#######'. When the integer length exceeds the provided format mask, PostgreSQL outputs hash marks instead of truncating numbers.

Sense check: If you see hash marks ('#######'), the format mask is smaller than the underlying number.

Example 2: Reformatting dates from a movie database table.

In a movie database, the movies table contains a release_date column stored in standard ISO format (YYYY-MM-DD). We want to display the date in other formats.

SELECT 
    release_date,
    TO_CHAR(release_date, 'DD/MM/YYYY') AS formatted_date_slash,
    TO_CHAR(release_date, 'Dy, DD Mon YYYY') AS formatted_date_text
FROM movies;

Take a record with a release_date of 1972-02-02:

  1. The first expression TO_CHAR(release_date, 'DD/MM/YYYY') reorders the date components. It prints the day first, then the month, then the year, returning '02/02/1972'.
  2. The second expression TO_CHAR(release_date, 'Dy, DD Mon YYYY') resolves the day of the week. Because February 2, 1972 was a Wednesday, Dy outputs 'Wed'. The full expression returns 'Wed, 02 Feb 1972'.

Take another record with a release_date of 1979-08-15: The query outputs '15/08/1979' and 'Wed, 15 Aug 1979'. Both resulting columns are of data type text.

Sense check: The expressions reorder the components without altering the underlying calendar day.

Example 3: Extracting time components from a timestamp literal.

We have a timestamp literal '2020-01-01 10:30:45'::timestamp. We want to isolate the time portion and exclude the date.

SELECT TO_CHAR('2020-01-01 10:30:45'::timestamp, 'HH24:MI:SS');

The specifier HH24 extracts the hour 10. The specifier MI extracts the minutes 30. The specifier SS extracts the seconds 45. The query returns '10:30:45'.

If we update the literal to '2020-01-01 10:30:59'::timestamp, the query returns '10:30:59'.

Sense check: The date portion is completely excluded from the resulting string.

Example 4: Formatting financial currency with dollar prefix, locale decimal, and null handling.

In the movie database, the revenues_domestic column holds numeric earnings. We want to format these earnings as currency strings with a leading dollar sign and two decimal places.

SELECT 
    movie_id,
    revenues_domestic,
    TO_CHAR(revenues_domestic, '\$99999D99') AS formatted_revenue
FROM movies;

Walkthrough of the format mask '\$99999D99':

  1. The \$ specifier places a fixed dollar symbol at the start of the output string.
  2. The five 9 specifiers reserve five digit positions for the integer portion.
  3. The D specifier prints the locale decimal separator, which is a period in standard US locale.
  4. The two trailing 9 specifiers print two decimal places.

If a row contains a NULL value in revenues_domestic, PostgreSQL returns NULL. It does not print a lone dollar sign or raise an error.

Digit padding starts from right to left with excess placeholders creating leading spaces. When the number has fewer than five digits, spaces appear between \$ and the first digit. Removing an unneeded 9 placeholder shifts the digits closer to the currency symbol.

If the revenue number exceeds five integer digits, the output displays as hash marks (#). If we need four decimal places, we extend the format mask to '\$99999D9999'.

Sense check: NULL values safely evaluate to NULL; insufficient integer slots produce hash marks.

Assumptions & Scope:

  • Input Type Scope: TO_CHAR operates on numeric, temporal, or interval data. Arbitrary types must be cast before passing into TO_CHAR.
  • Output Immutability: The return value is always text. You cannot perform numeric calculations or interval math directly on the returned string.
  • Locale Dependence: Specifiers like D, G, and month/day names (Month, Day) depend on the session's active locale (lc_time and lc_numeric).

#### Visual Intuition: Stencil Alignment and Digit Masking Picture the format mask as a row of labeled physical slots lined up from right to left around a decimal pivot point:

Input Number:               1 0 0 8 7 0
Format Mask:         [sign] [9] [9] [9] [9] [9] [9]
Output String:       [' ']  [1] [0] [0] [8] [7] [0]  --> ' 100870'

Input Number:               1 0 0 8 7 0 (6 digits)
Format Mask:         [sign] [9] [9] [9] [9]          (4 slots)
Output String:              [#] [#] [#] [#] [#] [#]  --> '#######' (Overflow!)

The right-to-left alignment guarantees that units, tens, and hundreds line up correctly. When the integer has fewer digits than available slots, empty leading slots become spaces. If the number has more whole digits than slots, the engine refuses to silently truncate high-order magnitude, returning '#######' to signal visual overflow.

Common Pitfalls:

  1. Confusing MM and MI: MM represents the calendar month number (01–12), whereas MI represents minutes (00–59). Writing 'YYYY-MM-DD HH24:MM:SS' formats the minute field with the month value.
  2. Integer Mask Overflow (#######): Under-allocating 9 specifiers for numeric fields causes PostgreSQL to return hash marks rather than truncating digits.
  3. Unexpected Leading Spaces: Because 9 reserves a slot for an optional positive sign, '999' on input 123 returns ' 123'. To eliminate the leading sign space, prefix the mask with FM (e.g., 'FM999').
  4. Hardcoding Commas vs Locales: Using , and . instead of G and D fails to adapt to international numbering conventions.

9.1.4 Student Questions and Answers

Q: What happens when a numeric value has more digits than the format pattern specifies in TO_CHAR? A: PostgreSQL displays a string of hash symbols instead of the number indicating length exceeds format mask. This avoids silently displaying a truncated, misleading number.

Q: How does TO_CHAR handle NULL values when formatting database columns like revenues_domestic? A: PostgreSQL handles NULL values gracefully by returning NULL without throwing an error or rendering a dangling currency symbol.

9.1.5 Industry Applications and Best Practices

  • Real-world: Financial reporting dashboards use TO_CHAR to turn raw numeric columns into formatted currency strings with thousand separators and dollar symbols.
  • Real-world: User interfaces format database ISO dates into localized date strings (Dy, DD Mon YYYY) for customer displays.
  • Real-world: Log parsing pipelines isolate the time of day from event timestamps using 'HH24:MI:SS' to aggregate hourly traffic.

9.1.6 Exam Notes

Exam note:

  • Remember that TO_CHAR always returns a text data type and overflow results in hash marks.
  • Do not confuse MM (month number) with MI (minutes) in date-time format strings.
  • When formatting numbers with currency symbols, ensure the format mask includes enough 9 placeholders to avoid hash overflow.

Recap & Bridge: TO_CHAR converts numbers and dates into text. However, incoming data often requires the reverse operation: converting formatted character strings back into numbers. This leads directly to TO_NUMBER.

9.2 The TO_NUMBER Function

Why is parsing text numbers fraught with peril? When importing raw data feeds, values rarely arrive as clean integers or floats. Instead, they arrive wrapped in localized currency symbols (\$, €), group commas (1,234,567), or non-standard decimal formats. How does a database reliably parse these strings into exact numeric values without risking data loss?

9.2.1 Purpose and Syntax

The TO_NUMBER function parses a formatted character string and converts it into a numeric data type. It is the inverse operation of formatting numbers with TO_CHAR.

Think of TO_NUMBER as an optical scanner calibrated with a specific template. Each slot in the template instructs the engine what character type to expect and how to interpret it. If the template is calibrated correctly, characters are parsed into their exact mathematical digit positions. However, if the template omits the decimal marker or misplaces a separator, digits slide into unintended registers, multiplying numbers by powers of ten.

The classroom explanation captures this inverse conversion:

"The Postgres two number function, convert a character string to a numeric value. That's why it's called two number. Anything that you want to convert to a number... The format is very simple. Two underscore number. You define your string and you define your format over here."

Formal Function Signature: \[ \text{TO\_NUMBER}(s, f) \to n \] where:

  • \(s \in \text{text}\) is the input character string containing numeric data.
  • \(f \in \text{text}\) is the format pattern string describing the string structure.
  • \(n \in \text{numeric}\) is the parsed numeric value.

9.2.2 Numeric Format Model Specifiers

The format string tells PostgreSQL how to interpret characters in the incoming string.

The primary format specifiers include:

  • 9: Matches a digit position. It specifies the expected number of digits.
  • 0: Matches a digit position with leading zeros.
  • .: Matches a period decimal point separator.
  • D: Matches a decimal point separator that uses the active locale.
  • ,: Matches a comma group separator.
  • G: Matches a group separator that uses the active locale (such as a thousands separator).
  • S: Matches a sign anchored to the number using the active locale, handling leading or trailing plus or minus signs.
  • L: Matches a currency symbol that uses the active locale (such as \$).

9.2.3 Worked Examples

The following walkthroughs show how TO_NUMBER parses plain strings, signed values, currency amounts, and grouped numbers.

Example 1: Basic decimal string parsing and mask truncation.

We begin with the string '1420.89'. We parse it with a matching format mask:

SELECT TO_NUMBER('1420.89', '9999.99');

The four 9 placeholders match 1420. The period matches .. The two trailing 9 placeholders match 89. The query returns 1420.89 as a numeric value.

Now we remove one decimal placeholder from the format string:

SELECT TO_NUMBER('1420.89', '9999.9');

The query returns 1420.8. The second decimal digit is omitted.

If we remove the decimal specifiers completely:

SELECT TO_NUMBER('1420.89', '9999');

The query returns 1420. PostgreSQL omits the decimal separator and drops the fractional portion.

Sense check: The function parses only what is explicitly specified in the format mask and drops the unmapped fractional portion.

Example 2: Parsing negative numbers with group separators and trailing sign anchors.

We have a string '10,625.78-' containing a thousands comma, period, and trailing minus sign.

SELECT TO_NUMBER('10,625.78-', '99G999D99S');

Walkthrough of the format mask '99G999D99S':

  1. 99 matches the initial digits 10.
  2. G matches the locale group separator comma ,.
  3. 999 matches 625.
  4. D matches the locale decimal separator ..
  5. 99 matches 78.
  6. S matches and consumes the trailing minus sign -.

The query returns -10625.78 as a signed numeric value.

Sense check: The S anchor correctly consumes the trailing minus sign and produces a signed negative number.

Example 3: Parsing currency strings with locale currency symbols.

We have a currency string '\$1420.64'. We want to convert it to a number.

SELECT TO_NUMBER('\$1420.64', 'L9999');

The L specifier matches the locale currency symbol \$. The four 9 specifiers match 1420. The query returns 1420. The cents are dropped because the mask omitted decimals.

To preserve the fractional cents, we include the decimal specifier:

SELECT TO_NUMBER('\$1420.64', 'L9999.99');
-- Or using locale decimal D:
SELECT TO_NUMBER('\$1420.64', 'L9999D99');

Both queries return 1420.64.

Sense check: To preserve cents, the format mask must explicitly include decimal specifiers.

Example 4: Trap with group separators versus decimal separators causing inflated numbers.

Take the string '1,234,567.89'.

If we write a format mask that omits the decimal separator:

SELECT TO_NUMBER('1,234,567.89', '9G999G999');

The query returns 1234567. The .89 portion is ignored.

However, if we mistakenly treat the decimal digits as extra integer positions:

SELECT TO_NUMBER('1,234,567.89', '9G999G9999');

The query returns 12345678. The period is skipped and 8 is read as a whole digit. Format string mismatches on decimals can cause silent data corruption where decimals become whole numbers. A database outputs exactly what you specify in the mask so every separator must match the input.

To parse the string correctly, specify the decimal point:

SELECT TO_NUMBER('1,234,567.89', '9G999G999.99');
-- Or using locale decimal D:
SELECT TO_NUMBER('1,234,567.89', '9G999G999D99');

Both queries return 1234567.89.

Sense check: Matching every separator avoids data corruption and ensures accurate decimal values.

Example 5: Converting large monetary numbers into clean numeric values.

We have a formatted monetary string '1,978,299.78'. We convert it into a clean numeric value:

SELECT TO_NUMBER('1,978,299.78', '9G999G999D99');

The specifier 9 matches 1, G matches the first comma, and 999 matches 978. Next, G matches the second comma, 999 matches 299, D matches the decimal point, and 99 matches 78. The query returns 1978299.78 as numeric.

Sense check: The query converts the formatted monetary string into a clean numeric value ready for arithmetic.

Assumptions & Scope:

  • Strict Pattern Alignment: In PostgreSQL, the input string must match the pattern defined by the mask. If non-numeric characters appear in positions where digits are expected, PostgreSQL throws a runtime error.
  • Locale Sensitivity: D, G, L, and S depend on server locale configuration (lc_numeric).
  • Data Type Output: The output is always of type numeric.

#### Visual Intuition: The Decimal Alignment Trap Understanding how TO_NUMBER aligns characters explains why omitting decimal specifiers can cause drastic data inflation:

String:         1 , 2 3 4 , 5 6 7 . 8 9
Mask 1:         9 G 9 9 9 G 9 9 9 . 9 9
Match:          1   2 3 4   5 6 7 . 8 9  ==> 1234567.89  (CORRECT)

String:         1 , 2 3 4 , 5 6 7 . 8 9
Mask 2:         9 G 9 9 9 G 9 9 9 9
Match:          1   2 3 4   5 6 7 [.] 8  ==> 12345678    (CORRUPTED: 10x inflation!)
                                   ^ period skipped, digit consumed as integer

Because 9 positions consume the next available digit character, omitting the decimal specifier causes the parser to skip punctuation and swallow the first decimal digit as a whole number.

Common Pitfalls:

  1. Omitted Decimal Specifier: Omitting . or D when decimals exist causes truncation (dropping cents) or silent integer inflation.
  2. Hardcoding Commas vs Locales: Using , instead of G fails when processing numbers formatted under other locales.
  3. Mismatched Digit Counts: Specifying fewer 9 slots than the integer string possesses can cause parsing to stop prematurely.
  4. Ignoring Trailing Signs: Accounting strings formatted with trailing signs require the S anchor at the end of the format mask.

Q: What happens if you omit the decimal point in a format string when parsing a number with decimals like '1,234,567.89'? A: Omitting the decimal separator causes PostgreSQL to either drop fractional digits or misinterpret them as extra whole digits creating an unintended huge number.

9.2.5 Industry Applications and Best Practices

  • Real-world: ETL pipelines ingesting raw text CSV files parse currency strings and formatted numbers into native numeric database columns using TO_NUMBER.
  • Real-world: Internationalized systems use G and D specifiers to parse European number strings where commas act as decimals and periods act as group separators.
  • Real-world: Accounting ledger imports parse financial strings with trailing minus signs using the S anchor to record debit balances accurately.

9.2.6 Exam Notes

Exam note:

  • The output of TO_NUMBER is always numeric and missing decimal specifiers will silently drop decimals.
  • Remember that G represents group separators and D represents decimal points under the active locale.
  • Watch out for format patterns that lack decimal specifiers when parsing fractional strings.

Recap & Bridge: While TO_NUMBER handles numeric values, temporal data requires a different conversion mechanism to account for dates, leap years, and calendar hierarchies. This brings us to TO_DATE.

9.3 The TO_DATE Function

Why doesn't a database just guess what date a string represents? Consider the string '02/03/2024'. Does that represent the 3rd of the second month, or the 2nd of the third month? In different regions, conventions differ. Without an explicit format mask, automated parsing relies on server settings that can quietly swap day and month values. How does TO_DATE eliminate this ambiguity while enforcing strict integrity?

9.3.1 Purpose and Syntax

The TO_DATE function converts a character string into a PostgreSQL date data type. It parses the input text according to a supplied format mask.

The formal mapping signature is defined as: \[ \text{TO\_DATE}(s, f) \to d \] where \(s \in \text{text}\) is the input string representing a date, \(f \in \text{text}\) is the format pattern string describing the input structure, and \(d \in \text{date}\) is the resulting date value in standard \(\text{YYYY-MM-DD}\) format.

Verbal explanation from the classroom:

"PostgreSQL to date function is to help you to convert a string to a date format date format... to underscore date you have a text whichever the string that you want to provide and then you define a format... date format is always in year, month and date."

Formal Function Signature: \[ \text{TO\_DATE}(s, f) \to d \] where:

  • \(s \in \text{text}\) is the input string representing a date.
  • \(f \in \text{text}\) is the format pattern string describing the input structure.
  • \(d \in \text{date}\) is the resulting date value in standard \(\text{YYYY-MM-DD}\) format.

9.3.2 Date Format Patterns and Behavioral Semantics

The format string tells PostgreSQL how to read the string, not how to display the result. The returned value is an internal date type. PostgreSQL displays date values in the standard ISO-8601 format (YYYY-MM-DD), subject to server configuration behavior.

Common date format specifiers include:

  • YYYY: Year in four digits.
  • YY: Year in two digits.
  • MM: Month number from 01 to 12.
  • MONTH: Full uppercase English month name (such as JANUARY).
  • Month: Full capitalized English month name (such as January).
  • MON: Abbreviated uppercase month name (such as JAN).
  • Mon: Abbreviated capitalized month name (such as Jan).
  • DD: Day of the month from 01 to 31.
  • DAY: Full uppercase day name (such as MONDAY).
  • Day: Full capitalized day name (such as Monday).
  • DY: Abbreviated day name (such as Mon).

9.3.3 Worked Examples

The following walkthroughs show how TO_DATE parses formatted date strings, unseparated digits, and text month names, alongside handling out-of-range calendar errors.

Example 1: Parsing date strings with slashes.

We have a string '2020/10/22' containing date components separated by slashes.

SELECT TO_DATE('2020/10/22', 'YYYY/MM/DD');

The placeholder YYYY matches 2020, MM matches 10, and DD matches 22. The query returns 2020-10-22 as a date value.

Sense check: The slashes in the mask match the slashes in the string, producing a clean date.

Example 2: Parsing continuous unseparated numeric strings.

We have a continuous string of numbers '02211999' without slashes or hyphens.

SELECT TO_DATE('02211999', 'MMDDYYYY');

The mask assigns the first two digits 02 to month MM, the next two digits 21 to day DD, and the final four digits 1999 to year YYYY. The query returns 1999-02-21.

Sense check: Continuous unseparated numbers are sliced according to pattern widths.

Example 3: Date validation errors and out-of-range calendar handling.

PostgreSQL checks whether the parsed date exists on the calendar.

Date validation errors occur when attempting to parse an out-of-range calendar date:

SELECT TO_DATE('02341999', 'MMDDYYYY');

PostgreSQL raises an error: date/time field value out of range. There is no 34th day in any month.

Similarly, testing February 31:

SELECT TO_DATE('02311999', 'MMDDYYYY');

PostgreSQL raises an out-of-range error because February never has 31 days.

Testing February 30 in a leap year:

SELECT TO_DATE('20200230', 'YYYYMMDD');

PostgreSQL raises an out-of-range error because February has at most 29 days.

Correcting the day to a valid date:

SELECT TO_DATE('20200225', 'YYYYMMDD');

The query returns 2020-02-25.

PostgreSQL provides minimal error messages like field value out of range without identifying component failure. It does not state whether the day, month, or year was the invalid part.

Sense check: Out-of-range calendar values trigger runtime exceptions.

Example 4: Parsing full English month names.

We have a string 'March 07 2019' with a full English month name.

SELECT TO_DATE('March 07 2019', 'Month DD YYYY');

In a database query, the mask maps 'March' to Month, '07' to DD, and '2019' to YYYY. The query returns 2019-03-07. The output is in standard database date format, not the input string format.

Sense check: The result is a standard date value, not a formatted string.

Assumptions & Scope:

  • No Time Component: The date data type stores only calendar dates. Any time components present in the input string are ignored.
  • Strict Gregorian Calendar Rules: Out-of-range dates cause fatal runtime exceptions in PostgreSQL.
  • Display Independence: Changing the format mask in TO_DATE does not alter how the returned date looks in your client.

#### Visual Intuition: Format Mask Slicing and Date Gate When TO_DATE executes, characters are matched to specifier widths and verified against calendar boundaries:

Raw String:       [0] [2]   [2] [1]   [1] [9] [9] [9]
Format Mask:      [ M M ]   [ D D ]   [ Y Y Y Y ]
Extracted Units:  Month=2   Day=21    Year=1999
                     \         |         /
              +-------------------------------+
              |   Calendar Integrity Check    |  --> Valid date? YES
              +-------------------------------+
                               |
                        Internal Date:
                         1999-02-21

If the extracted day was 34, the check fails immediately, stopping execution with date/time field value out of range.

Common Pitfalls:

  1. Expecting Custom Output Strings: Writing TO_DATE(str, 'DD/MM/YYYY') and expecting the query result to display with slashes. TO_DATE returns a date, not a string. To display slashes, use TO_CHAR.
  2. Assuming Lenient Error Handling: Relying on TO_DATE to return NULL on bad dates. In PostgreSQL, invalid dates abort the query.
  3. Month/Day Position Swaps: Mixing up MM/DD/YYYY and DD/MM/YYYY on dates where the day is less than or equal to 12.

9.4 The TO_TIMESTAMP Function

Why is parsing timestamps more complex than parsing dates? A calendar date is a single point on a wall calendar, but a timestamp captures a precise instant. When an application receives a string like '2020-10-28 10:30:25', how does a database resolve components without crashing or corrupting temporal chronology?

9.4.1 Purpose and Syntax

The TO_TIMESTAMP function converts a character string into a timestamp with time zone (timestamptz) data type based on a specified format mask.

The formal mapping signature is defined as: \[ \text{TO\_TIMESTAMP}(s, f) \to t \] where \(s \in \text{text}\) is the input string representing a timestamp, \(f \in \text{text}\) is the format pattern string, and \(t \in \text{timestamptz}\) is the resulting timestamp value including session time zone offset.

Verbal explanation from the classroom:

"The postgres to timestamp function is to convert a string to a time based on a specific format... to underscore timestamp we define the timestamp over here as a string and then we define the format... timestamp with time zone over here that is why he is adding my time zone."

Formal Function Signature: \[ \text{TO\_TIMESTAMP}(s, f) \to t \] where:

  • \(s \in \text{text}\) is the input string representing a timestamp.
  • \(f \in \text{text}\) is the format pattern string.
  • \(t \in \text{timestamptz}\) is the resulting timestamp value including session time zone offset.

9.4.2 Timestamp Patterns, Defaults, and Time Zone Semantics

Format specifiers for TO_TIMESTAMP include:

  • YYYY: Year in four digits.
  • YY: Year in two digits.
  • MM: Month number from 01 to 12.
  • DD: Day of the month from 01 to 31.
  • DAY, Day, day: Day names in uppercase, capitalized, or lowercase.
  • DY, Dy, dy: Abbreviated day names.
  • HH or HH12: Hour of the day in 12-hour format (01 to 12).
  • HH24: Hour of the day in 24-hour format (00 to 23).
  • MI: Minute within the hour (00 to 59).
  • SS: Second within the minute (00 to 59).

Key behavioral semantics:

  1. Time zone attachment: The function returns timestamptz. PostgreSQL appends the current database session's UTC offset (such as -04 for US Eastern Daylight Time).
  2. Whitespace skipping: TO_TIMESTAMP automatically skips multiple consecutive whitespace characters in the input string.
  3. Default values for omitted fields: Omitted timestamp components default missing days to the first of the month and time parts to midnight. If the day DD is omitted from the format, PostgreSQL defaults the day to 01. If time components (HH, MI, SS) are omitted, PostgreSQL defaults them to 00:00:00.

9.4.3 Worked Examples

The following walkthroughs show how TO_TIMESTAMP parses complete timestamps, handles omitted components, and validates hour ranges.

Example 1: Parsing a full timestamp string with explicit date, time, and session time zone offset.

We have a complete date and time string '2020-10-28 10:30:25'.

SELECT TO_TIMESTAMP('2020-10-28 10:30:25', 'YYYY-MM-DD HH:MI:SS');

Walkthrough:

  1. YYYY matches 2020.
  2. MM matches 10.
  3. DD matches 28.
  4. HH matches 10.
  5. MI matches 30.
  6. SS matches 25.

The query returns '2020-10-28 10:30:25-04'. The -04 offset reflects the database session's local time zone.

Sense check: The explicit components are parsed and the session offset is attached.

Example 2: Automatic whitespace skipping and default population of omitted day and time fields.

We have a string '2020 05' containing multiple spaces between year and month, with no day or time specified.

SELECT TO_TIMESTAMP('2020   05', 'YYYY   MM');

Walkthrough:

  1. PostgreSQL skips the extra spaces.
  2. 2020 is parsed as year YYYY.
  3. 05 is parsed as month MM.
  4. Because day DD was not specified in the format, PostgreSQL defaults the day to 01.
  5. Because time components were not specified, hour, minute, and second default to 00:00:00.

The query returns '2020-05-01 00:00:00-04'.

Sense check: The engine skips whitespace and defaults omitted days to 01 and time to midnight.

Example 3: Validating hour ranges with HH24 and handling out-of-range errors.

We have a string '2020-01-01 32:08:00' containing an invalid hour 32.

SELECT TO_TIMESTAMP('2020-01-01 32:08:00', 'YYYY-MM-DD HH24:MI:SS');

PostgreSQL raises an error: date/time field value out of range. The specifier HH24 accepts hours strictly from 0 to 23 and higher values trigger out of range errors. The value 32 is outside this valid range.

To fix the query, we supply a valid hour within 0 to 23:

SELECT TO_TIMESTAMP('2020-01-01 23:08:00', 'YYYY-MM-DD HH24:MI:SS');

The query returns '2020-01-01 23:08:00-04'.

Sense check: Hour validation strictly requires values between 0 and 23 for HH24.

Assumptions & Scope:

  • Implicit Session Time Zone: TO_TIMESTAMP attaches the server session's current time zone.
  • Hour Boundaries: HH24 accepts hours strictly from 0 to 23.
  • Returned Type: The returned value is of data type timestamptz.

#### Visual Intuition: Timeline Anchoring and Default Backfill When components are missing from a timestamp string, PostgreSQL fills the gaps by assuming the earliest possible instant:

Input:         "2020   05"
Format:        "YYYY   MM"
Parsed:        Year = 2020, Month = 05

Missing Field Backfill:
- Day:         [DD]       --> Defaults to 01
- Time:        [HH:MI:SS] --> Defaults to 00:00:00
- Timezone:    [TZ]       --> Inherits Session Offset (-04)

Timeline Anchor:
[2020-05-01 00:00:00-04] =====================================> (UTC Timeline)

By anchoring omitted days to 01 and times to 00:00:00, TO_TIMESTAMP ensures that partial temporal strings resolve to deterministic moments.

Common Pitfalls:

  1. Hour Specifier Mismatch (HH vs HH24): Using HH for an hour like 15 triggers an out-of-range error. Always use HH24 for 24-hour time strings.
  2. Assuming timestamp without time zone: TO_TIMESTAMP in PostgreSQL always returns timestamptz.
  3. Minute/Month Confusion: Using MM for minutes instead of MI causes the month to overwrite the minutes position.

Core Rules to Memorize

  • Data type return rules:
  • TO_CHAR always returns text.
  • TO_NUMBER always returns numeric.
  • TO_DATE always returns date (displayed in standard ISO-8601 format: YYYY-MM-DD).
  • TO_TIMESTAMP always returns timestamp with time zone (timestamptz).
  • Format specifier distinctions:
  • MM represents month numbers (01 to 12).
  • MI represents minutes (00 to 59).
  • HH or HH12 represents 12-hour clock hours (01 to 12).
  • HH24 represents 24-hour clock hours (00 to 23).
  • DD represents day of month (01 to 31).
  • DY represents abbreviated day of week (Mon to Sun).
  • Format mismatch pitfalls:
  • In TO_CHAR, if an integer has more digits than the format mask provides, PostgreSQL returns hash marks (#).
  • In TO_NUMBER, omitting decimal specifiers drops fractional values or inflates integers by reading decimals as whole digits.
  • In TO_DATE and TO_TIMESTAMP, out-of-range calendar values (such as February 30 or hour 32) throw runtime exceptions rather than returning NULL.
  • Default filling rules:
  • In TO_TIMESTAMP, omitted day fields default to 01.
  • In TO_TIMESTAMP, omitted hour, minute, and second fields default to 00:00:00.
  • In TO_TIMESTAMP, the database session's active UTC offset is automatically appended.
