Introduction to PostgreSQL

Published: 2026-09-22
Level: undergraduate
Audience: Undergraduate students learning SQL and PostgreSQL setup

Introduction to PostgreSQL: installing the server, linking pgAdmin, creating a training login and practice databases, and loading sample data.

1.1 Installing PostgreSQL on Mac

1.1.1 Where to Get the Installer

A PostgreSQL server (the database engine that stores data and answers queries, for example postgres running on port 5432) is different from the tools used to talk to it. pgAdmin 4 (a visual workspace for managing servers, databases, and queries, for example the browser tree on the left and the Query Tool on the right) is the visual tool used most in this course. Stack Builder (an extra add-on installer that fetches drivers and extensions, for example a spatial PostGIS pack) is optional. Command Line Tools (terminal programs such as psql, for example running psql -U adam -d learning) let a user run SQL from a terminal.

Think of the server as a library building and pgAdmin as the front desk. The building holds every book, while the desk is where requests are placed. If the desk is closed, the books are still inside, so reinstalling pgAdmin alone never deletes data.

To install on Mac, go to the postgresql.org website (also reachable as postgres.org) and pick Download. Pick Mac for the operating system. Pick the installer download offered from the server side list, which leads to the EDB builds. In this session the version used is 12.4 for Mac. Download that file to the Mac. Double-click the downloaded file to start setup. Confirm with Open when asked, then enter the Mac password when asked.

A version number such as 12.4 means major release 12 with fix 4. Minor fixes are safe to accept, while major jumps such as 12 to 13 can change behavior, so course steps name the exact build used.

Where the analogy breaks: a library has one front desk, but one Mac can run several PostgreSQL versions side by side, each on its own port, so the "building" can be duplicated.

Other ways to get PostgreSQL on Mac that do the same job: Postgres.app (a small self-contained app), Homebrew with brew install postgresql, or MacPorts. These are handy alternatives, but this course follows the EDB installer so every screen matches.

Exam note: The Mac path in this course is postgresql.org, Download, Mac, EDB installer, version 12.4. Version numbers mark which build the steps were tested on.

1.1.2 Setup Steps on Mac

The setup wizard asks for an install location first. Keep the default unless there is a strong reason to change it, because moving the data folder later breaks the service path. The component list includes PostgreSQL server, pgAdmin 4, Stack Builder, and Command Line Tools. Keep them selected and pick Next, so the visual tool and terminal tools arrive together.

A superuser (the top-level account, named postgres by default, that can do anything on the server, for example postgres creating or erasing any database) is set with a password during install. A port (a number where the server listens for incoming links, for example 5432) defaults to 5432. A locale (a setting for language and sorting rules, for example how ORDER BY name sorts accented letters) defaults to the system locale.

Next the wizard asks for a superuser password. On a personal Mac any password is fine for practice, but write it down because pgAdmin asks for it on every first link. On a shared or cloud server, such as Amazon or Google servers, use a long strong password that is unique to that server.

Scope: The "any password is fine" advice applies only to a personal practice Mac with no outside network access. It breaks on any shared, office, or cloud machine, where a weak postgres password lets anyone on the network take over every database.

Next the wizard asks for a port. The default is 5432. Keep 5432 and pick Next, unless another PostgreSQL copy already uses it. Next the wizard asks for a locale. Keep the default and pick Next, so sorting matches the Mac. The last screen shows a recap of all choices. Read it once, then pick Next to run the install.

How install choices differ on other systems: MySQL on Mac uses its own DMG or Homebrew installer with a root password plus a choice of strong-password rules, Snowflake needs no installer at all because the server lives in the cloud and only a browser login to Snowsight is needed, and Databricks likewise needs no local install because queries run on a workspace cluster. The common idea is the same (pick server location, admin account, and client tool), but only PostgreSQL and MySQL put a real server on the local machine.

Two traps beginners hit here. First, forgetting the superuser password means pgAdmin cannot link, and the fix is a password reset through the operating-system account, not a reinstall. Second, changing the port to a random number without noting it means every later link attempt fails, so keep 5432 unless there is a real clash.

1.1.3 Worked Examples

Worked example — full Mac install path. Start at postgresql.org. Pick Download. Pick Mac. Pick Download the installer. Pick Mac again. Pick version 12.4. Wait for the download to finish and check the file size looks complete. Double-click the file. Pick Open on the security prompt. Enter the Mac password. Pick Next on the welcome screen. Accept the install folder. Keep PostgreSQL server, pgAdmin 4, Stack Builder, and Command Line Tools selected. Pick Next. Type the superuser password and repeat it. Pick Next. Keep port 5432. Pick Next. Keep the default locale. Pick Next. Check the recap screen line by line. Pick Next to install and wait for the progress bar. Done when the completion screen shows. Sense-check: pgAdmin 4 opens from Applications and the server node appears in the tree, which proves the engine is running.

One-line recap: the Mac install is download from postgresql.org, run the EDB wizard with defaults plus a noted superuser password, and keep port 5432. That ready engine is what the Windows steps mirror next, only with an exe and a data-folder question added.

1.2 Installing PostgreSQL on Windows

1.2.1 Where to Get the Installer

To install on Windows, go to postgresql.org and pick Download. This opens a page with Linux, Mac, Windows, Solaris, and BSD options. Pick the Windows icon. This opens a Windows installer page supplied by EDB, the main build source. Pick Download the installer. Pick the right build for the machine, 32-bit or 64-bit. In this session versions 10 through 13 are named as options, with 13 as the newest at the time. Download the exe file and wait for the browser to finish. Double-click the exe to start the setup wizard.

Think of EDB as the publishing house that prints the same book for each computer shape. The story inside (PostgreSQL itself) is identical, but the cover (32-bit or 64-bit exe) must match the shelf it sits on. A 64-bit PC needs the 64-bit file.

Check the machine shape first: on Windows open Settings, System, About, and read System type. Pick the matching exe. When the browser finishes, the file is usually a few hundred megabytes. If it is only a few kilobytes, the download was cut short, so download again rather than running a broken file.

How downloads differ on other systems: MySQL on Windows uses the MySQL Installer bundle (which offers server, Workbench, and connectors in one wizard), Snowflake has nothing to download because Snowsight runs in a browser and SnowSQL is an optional extra, and Databricks is reached through a workspace URL with no local engine. Only PostgreSQL and MySQL ask for a 32-bit or 64-bit choice, because only they run a local server process.

Exam note: EDB supplies the Windows installer builds, and the 32-bit or 64-bit pick must match the machine. Version numbers such as 10 through 13 mark which builds were current when the steps were recorded.

1.2.2 Setup Steps on Windows

The wizard collects four things in order: folders (where the program and where the data live), components (which tools to add), the superuser password (for the built-in postgres account), and the port (default 5432). Each screen builds on the last, so going back to fix a folder is cheaper than reinstalling later.

The first screen says welcome to the PostgreSQL setup wizard. Pick Next. Pick an install folder on the PC and pick Next. Pick components: PostgreSQL Server, pgAdmin 4, Stack Builder, and Command Line Tools. Keep all of them selected and pick Next. Pick a data folder when asked, or keep the suggested one, and pick Next. The data folder is where table files actually live, so it needs free disk space and should not sit inside a synced cloud folder that locks files.

Next type a database superuser password. The default superuser name is postgres. Type the password twice and pick Next, and store it somewhere safe. Next keep the port as 5432, which is the default, and pick Next. The next screen shows a pre-install recap with install folder, data folder, port, database name, user name, and locale. Check it. Go back to fix a mistake, or pick Next. The next screen says ready to install. Pick Next to start the install. When it ends, the screen says completing the setup wizard. Stack Builder may be offered to fetch extra drivers and tools. This course does not use Stack Builder, so it can be left as is. Pick Finish.

Two traps here. First, installing the data folder under OneDrive or Dropbox causes file locks and a server that will not start, so keep it on a plain local disk. Second, unchecking Command Line Tools to "save space" removes psql and the SQL Shell used later, so keep all four boxes checked.

1.2.3 First Launch of pgAdmin on Windows

On the Windows PC type pgAdmin and open pgAdmin 4. This is a desktop app that runs in a browser window. On first start the left pane is a browser tree for servers. The right pane shows a welcome view with dashboard and properties. To link the new server, click the plus sign on Servers, then the plus sign under it. A node such as PostgreSQL 10, 11, or 12 appears based on the installed version. Click that node. Type the master superuser password set during install. Pick OK. The tree then opens to show the server, all default databases, and their objects. The install is then done.

If the password prompt loops, the usual cause is typing the Windows login password instead of the postgres superuser password set in the wizard. Retype the database password, not the Windows one. If the server node shows a red cross, right-click it, pick Connect, and try again rather than creating a second server entry.

1.2.4 Worked Examples

Worked example 1 — Windows download path. Open postgresql.org. Pick Download. Pick Windows. Pick Download the installer on the EDB page. Pick the 64-bit file for version 10 on a 64-bit PC as a sample case. Wait for the exe to finish (a few hundred megabytes). Double-click the exe and approve the Windows prompt. Done when the welcome screen shows. Sense-check: the file name contains the version and windows-x64, which proves the build matches the machine.

Worked example 2 — Windows wizard path. Welcome screen, pick Next. Set install folder, pick Next. Keep all four components checked, pick Next. Set data folder, pick Next. Set superuser password twice, pick Next. Keep port 5432, pick Next. Check the recap (folders, port, locale, superuser name), pick Next. Pick Next on the ready screen and wait. Pick Finish on the done screen, leaving Stack Builder unchecked. Open pgAdmin 4, open Servers, open the version node, type the password, pick OK. Done when the server tree expands to show databases. Sense-check: the postgres default database is visible, which proves the engine answered with the right password.

One-line recap: the Windows path is the same engine as Mac with an exe, a data folder, and a pgAdmin first link at the end. With the server linked, the next step is learning the pgAdmin panes used for daily work.

1.3 Configuring pgAdmin 4 and Connecting to the Server

1.3.1 Main Parts of pgAdmin

On Mac open Finder, open Applications, and open the PostgreSQL folder. It holds Application Stack Builder, full server docs, pgAdmin 4, a reload-configuration app, and SQL Shell. SQL Shell (terminal-based entry for SQL commands, for example psql asking for server, database, port, and user in turn) is the keyboard route to the same server. pgAdmin 4 (the visual tool used most in this course, for example clicking Tables under schemas, public) is the mouse route used most in this course. Double-click pgAdmin 4 to start it. On first start it asks for the superuser password set during install. Type it to continue.

Think of pgAdmin and SQL Shell as two doors into the same room. One door is wide glass (pgAdmin with trees, grids, and buttons) and the other is a narrow keyhole (SQL Shell with typed commands). Both open onto the same tables, so a table made in one shows in the other after a refresh.

The left pane lists all linked servers in a browser tree: server, databases, schemas, tables, columns. The right pane shows running queries, dashboards, and object details for whatever is picked on the left. Test servers from past trials may still show in the list alongside the fresh PostgreSQL 12 server. Old entries are harmless, but remove or ignore them so queries land on the right server.

The matching tools on other systems do the same job with different names: MySQL Workbench (visual trees plus a query tab), Snowflake Snowsight (browser worksheets plus history) with SnowSQL as its terminal twin, and the Databricks SQL editor or a notebook cell. The habit transfers: pick the server or warehouse, pick the database, open an editor, run, read output.

Two traps here. First, opening pgAdmin but forgetting which server node is active means queries run on the wrong database, so always glance at the tree highlight before running. Second, SQL Shell asks for each link detail with defaults in brackets, and pressing Enter through them with the wrong database picked leads to a confusing "relation does not exist" error later.

1.3.2 Linking the Local Server

Click the server icon in the left pane. Find the PostgreSQL 12 node for the local Mac install. Click it. Type the superuser password when asked and pick OK. The link then opens and the server is ready for work. From here databases, logins, groups, tables, and queries can be managed.

A server link (a saved set of host, port, and user, for example localhost, 5432, postgres) plus authentication (proving identity with the password) is what turns the tree from grey to live. A grey node with a cross means no live link is open yet, not that the database is missing.

The server runs on localhost (this same machine) at port 5432. If the link fails with "connection refused", the server process is not running, so start the PostgreSQL service first. If it fails with "password authentication failed", the password typed is not the superuser password from install. Save the password in pgAdmin only on a personal machine, never on a shared one.

1.3.3 Worked Examples

Worked example — Mac pgAdmin first run. Finder, Applications, PostgreSQL folder, double-click pgAdmin 4. Type the superuser password on the startup prompt. In the left pane click Servers. Click PostgreSQL 12. Type the password again on the link prompt. Pick OK. Done when the server node expands to show Databases, Login/Group Roles, and Tablespaces. Sense-check: expanding Databases shows the default postgres database, which proves the link is live.

One-line recap: pgAdmin is the visual door and SQL Shell the terminal door into the same local server, linked with the superuser password on port 5432. With the link live, the next step is making a safer daily login than the superuser.

1.4 Creating a Database User and Role Privileges

1.4.1 Why Make a New Login

A login role (a named account that can link to the server, for example adam with LOGIN) is what a person uses day to day. A group role (a named holder of rights shared by many logins, for example analysts granted to several people) can hold many logins. The fresh install has only the postgres superuser and a default postgres database with a schema but no tables yet. A new training login keeps daily work apart from the superuser account, so a typo cannot erase the whole server.

Think of the superuser as the building master key and the training login as a room key. Daily work needs only the room key, so the master key stays in a drawer. Using the master key for practice invites accidents that the room key simply cannot cause.

To make one, open the database tree, find Login and Group Roles, right-click, and pick Create Login or Group Role. Type Adam as the login name for this course. PostgreSQL folds unquoted names to lower case, so Adam typed in the dialog becomes adam in SQL, which is why the preview shows adam.

How other systems split the same idea: MySQL separates users from grants with CREATE USER 'adam'@'localhost' IDENTIFIED BY 'secret' followed by GRANT lines, Snowflake separates them further with CREATE USER adam, CREATE ROLE analyst, GRANT ROLE analyst TO USER adam, plus warehouse grants, and Databricks with Unity Catalog uses account-level principals granted on catalogs and schemas. PostgreSQL packs login ability and rights into one ROLE row, which is compact but easy to over-grant, so the course keeps Adam deliberately weak.

1.4.2 Password and Privilege Settings

Under Definition set a password for Adam. Passwords are sensitive, so pick a stable strong value. Expiry and other password options can be left as is for practice.

Under Privileges set what Adam may do. CanLogin (permission to link, LOGIN, for example adam allowed to connect) set to yes lets Adam link to the server. Superuser (unlimited power, SUPERUSER, for example allowed to drop any database) set to yes would let the account do anything, such as make or remove databases at will. For Adam keep Superuser as no. CreateRoles (permission to make more roles, CREATEROLE, for example adding new users) would let Adam make more roles, so keep it as no for now. CreateDB (permission to make databases, CREATEDB, for example creating the learning database) set to yes lets Adam make training databases, which this course needs, so set it to yes. Update Catalogs is a high-level right and stays off. Inherit rights from parent roles, such as pg_monitor, stays on by default, which means Adam picks up rights of groups it joins. Initiate streaming replication and backup stays off, since single-machine practice does not need copy links across servers. Membership and Parameters hold group links and per-user settings for later advanced use and stay as is.

Scope: This flag set (login yes, superuser no, create-role no, create-database yes, replication no) fits a local training login only. It breaks as a model for shared or production accounts, where create-database is usually withheld and access is granted per database instead.

Two traps here. First, ticking Superuser "to avoid permission errors" hands Adam the master key and removes the safety this whole step builds. Second, forgetting to tick CreateDB means every later CREATE DATABASE fails with "permission denied", which looks like broken SQL but is just a missing flag.

1.4.3 The SQL Preview and Save

The SQL tab shows the exact command the tool will run based on the picked options. It is a CREATE ROLE line for adam with login rights, no superuser rights, create-database rights, no create-role rights, inherit rights, no replication rights, limited links, and the typed password:

CREATE ROLE adam WITH
    LOGIN
    NOSUPERUSER
    CREATEDB
    NOCREATEROLE
    INHERIT
    NOREPLICATION
    CONNECTION LIMIT -1
    PASSWORD 'secret-password-here';

CREATE USER adam would mean the same thing, because in PostgreSQL CREATE USER is just shorthand for CREATE ROLE ... WITH LOGIN. Pick Save to make the login. The new Adam node then shows in the tree. Right-click and pick Properties at any time to check CanLogin, CreateDB, and other flags. This login is then used to link, make databases, make tables, and run queries.

The equivalent one-liners elsewhere, kept here for recognition only: MySQL uses CREATE USER plus GRANT CREATE ON *.* TO 'adam'@'localhost', Snowflake uses CREATE USER plus GRANT CREATE DATABASE ON ACCOUNT TO ROLE analyst, and Databricks grants CREATE SCHEMA on a catalog. Same intent (let the trainee build practice stores but not rule the server), different spelling.

1.4.4 Worked Examples

Worked example — make login Adam. Right-click Login and Group Roles. Pick Create. Name it Adam. Set the password under Definition. Set CanLogin yes. Set Superuser no. Set CreateDB yes. Set CreateRole no. Keep Inherit yes. Keep Replication no. Read the SQL preview and confirm it says LOGIN, NOSUPERUSER, CREATEDB. Pick Save. Right-click the new node, pick Properties, and confirm the flags stuck. Done when adam lists under Login/Group Roles. Sense-check: linking as adam and running CREATE DATABASE try_once; followed by DROP DATABASE try_once; proves CreateDB works without superuser power.

One-line recap: Adam is a login-only, create-database-only training key that keeps daily work away from the superuser. That safer account now owns the practice databases built next.

1.5 Creating Databases, Encoding and Schemas

1.5.1 Make a Database Named learning

A database (a named store that holds schemas and tables, for example learning holding practice tables) sits above schemas and tables. A schema (a folder inside a database that groups tables, for example public.customers) groups tables inside one database. The public schema (the default schema made in each new database, for example where customers lands unless another schema is named) is made in each new database automatically.

Think of the server as an office block, each database as one office, each schema as a filing cabinet, and each table as a drawer. Queries name the drawer, the cabinet keeps drawers tidy, and offices keep clients apart so practice tables never spill into the default postgres office.

To make one, click the Databases icon. One default database named postgres is there from the install and should be left alone for utilities. Right-click Databases and pick Create Database. Name it learning. The owner defaults to postgres from the install. Change owner to Adam, the new training user, so daily tables belong to the daily account. Notes or comments can be added but are not needed.

The matching SQL the dialog builds is:

CREATE DATABASE learning
    OWNER = adam
    ENCODING = 'UTF8'
    CONNECTION LIMIT = -1;

1.5.2 Encoding, Locale and Limits

Encoding (how text bytes are stored, for example UTF8 holding the byte pattern for Arabic or Chinese characters) sets how text bytes are stored. UTF-8 is the common choice and holds non-ASCII text such as Chinese and Arabic. Keep UTF-8, because changing it later needs a rebuild. Tablespace (where files live on disk, for example the default pg_default) sets where files live on disk and stays default here. Collation (sort order, for example whether ORDER BY name puts Å after Z) sets sort order. Character type (character rules, for example what counts as a letter in pattern matches) sets character rules. Keep all defaults for now. Connection limit (how many links may open at once, for example -1) sets how many links may open at once. Minus one means no cap, or unlimited links. Keep minus one. Security, Parameters, and other advanced tabs stay as is for now.

Encoding is chosen once at database birth and cannot be changed in place. Collation and character type likewise stick for the life of the database. That is why the course pauses on these tabs even though it keeps every default: a wrong pick here is paid for with a full rebuild later.

The SQL tab again shows the exact command: create a database named learning, owned by Adam, with UTF-8 encoding and unlimited links. Pick Save to make it. The new node shows with a cross mark until first link, which only means it has not been opened yet. Click it to link. Under it, under schemas, the public schema is there by default. More schemas can be added later to group tables in a tidy way, for example a sales schema beside hr. For now all training tables go under public, under Tables.

How the same step looks elsewhere: MySQL writes CREATE DATABASE learning CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci, where the utf8mb4 extra matters because plain utf8 in MySQL cannot hold emoji, Snowflake writes CREATE DATABASE learning; plus CREATE SCHEMA learning.public; with no encoding pick at all because storage is managed UTF-8 by the cloud, and Databricks writes CREATE SCHEMA learning; (with DATABASE accepted as a synonym) often with a LOCATION path. The shared habit is one practice store owned by the training user; only PostgreSQL exposes tablespace and connection-limit knobs at this screen.

Scope: Keeping every default is right for local practice. It breaks for real multi-language or hosted stores, where collation, connection limit, and owner need deliberate picks before any table is built.

Two traps here. First, building training tables in the default postgres database instead of learning piles unrelated tables together and confuses every later lesson. Second, leaving the owner as postgres means Adam later hits permission errors on its own tables, so set owner to Adam before saving.

Exam note: Default port 5432, encoding UTF-8 for mixed-language text, and connection limit minus one meaning unlimited are short facts worth memorizing together.

1.5.3 Worked Examples

Worked example — make learning database. Right-click Databases. Pick Create Database. Type learning. Set owner to Adam. Keep encoding UTF-8. Keep tablespace, collation, and character type as is. Keep connection limit at minus one. Read the SQL preview and confirm owner, encoding, and limit. Pick Save. Click the new node to link. Open schemas, public, Tables to confirm the spot for new tables. Done when learning, schemas, public, Tables shows an empty table list ready for loads. Sense-check: the SQL preview names adam as owner and UTF8 as encoding, which proves the flags landed before saving.

One-line recap: a database is the office, the schema the cabinet, UTF-8 plus owner Adam plus unlimited links the safe practice setup. With the empty office ready, the next step is opening the Query Tool that fills its drawers.

1.6 Running Queries in the pgAdmin Query Tool

1.6.1 Opening the Query Editor

A query (a SQL command sent to a database, for example SELECT * FROM customers;) is the unit of work. The Query Editor (the pgAdmin pane where queries are typed, for example a blank tab tied to learning) is where queries are typed. Data output (the grid below that shows picked rows, for example columns and rows returned by a SELECT) is where answers appear.

Think of the Query Editor as a calculator with a paper tape. Typing is free, nothing happens until Run is pressed, and the tape (data output plus messages) records exactly what the engine returned, including errors.

To run a query, pick a database in the left tree, such as learning. Click the Query Editor icon. The tool opens a blank editor tied to that database, and the header names the database so mistakes are visible. Type SELECT queries or other PostgreSQL commands there. End each statement with a semicolon, which marks the end of the command. Pick Run with the play button or F5. The picked rows show in the data output pane below, while notices and timings show in the messages tab beside it.

The same loop on other systems: MySQL Workbench opens a query tab with the same run button, Snowflake Snowsight opens a worksheet with a run arrow and requires USE SCHEMA learning_sql.public; first, and Databricks runs SQL from a SQL-editor query or a notebook cell attached to a cluster or warehouse. The habit is identical everywhere: confirm the database, type, end with a semicolon, run, read output.

Two traps here. First, running with the wrong database highlighted (for example postgres instead of learning) returns "relation does not exist" even though the table is fine elsewhere. Second, dropping the semicolon works sometimes in pgAdmin but fails in SnowSQL and scripts, so always end statements with one.

1.6.2 Tabs, Dashboard and Properties

More than one editor can stay open at once. Click the Query Editor icon again to open a new tab. Each tab can run its own SQL against its own database link. Side-by-side tabs help weigh two outputs from two SQL lines, for example an old query beside a rewritten one.

Pick a database and pick Dashboard to get a quick view of sessions, live transfers, and database health. Properties shows table details such as encoding set at build time, stats, and links to other objects. These views are more advanced and return later in the course, so for now treat Dashboard as a health glance and Properties as a fact sheet, not as daily tools.

1.6.3 Worked Examples

Worked example 1 — open an editor on learning. In the left tree pick the learning database. Click the Query Editor icon. Confirm the tab header says learning. Type SELECT 1; as a smoke test. Pick Run. Done when the data output grid shows one row with 1. Sense-check: the 1 proves the editor is tied to a live database and the run loop works before real tables exist.

Worked example 2 — weigh two queries. Open one editor tab and run the first query. Open a second editor tab and run the second query. Weigh the two output grids side by side, checking row counts and column values. Done when both grids are visible and the difference is named. Sense-check: matching headers with different rows proves the tabs are independent and neither overwrote the other.

One-line recap: pick the database, open the editor, end statements with a semicolon, run, and read the grid. That loop is how every sample table in the next step gets loaded and checked.

1.7 Loading Sample Data and Starter Databases

1.7.1 Loading Single SQL Files

A .sql file (a text file with table-build and row-add commands, for example customers.sql holding CREATE TABLE plus INSERT rows) is how course data ships. To load one, open pgAdmin, pick the target database, open the Query Tool, and make sure the editor is empty. Pick the Open File icon. Move to the folder with the course download files. Pick a file and pick Select. The editor then fills with the file text. Pick Run and wait for the messages tab to say the run finished. The table is built and filled. To confirm, right-click Tables and pick Refresh. The new table name then shows. Clear the editor with Select All and Delete. Answer yes if asked to confirm clear. Repeat for the next file.

Think of each .sql file as a flat-pack furniture box. Opening the file tips every part onto the floor (the editor), Run turns the screws, and Refresh opens the room door to reveal the finished shelf. Skipping Refresh is like never opening the door: the shelf exists but stays invisible.

For the learning database the course gives three files. First load customers.sql. It builds a customer table with sample rows and a primary key. Run it, refresh, and check the customer table. Clear the editor. Next load products.sql. It builds a products table with sample rows and a primary key. Run it, refresh, and check. Clear the editor. Next load purchases.sql. It builds a purchases table with sample rows plus primary and foreign keys. A primary key (a column or set of columns that marks each row as unique, for example customer_id with no repeats) marks each row as unique. A foreign key (a column that points to a primary key in another table to link rows across tables, for example purchases.customer_id pointing at customers.customer_id) links rows across tables. Run it, refresh, and check that customers, products, and purchases all show with their columns.

Load order matters here: customers and products first, purchases last, because the foreign keys in purchases need their parent rows to exist. Running purchases first fails with a key error, which is a load-order problem, not broken SQL.

How bulk loads differ elsewhere, kept here as recognition: MySQL can run the same script from Workbench or with SOURCE file.sql, and large CSVs often use LOAD DATA INFILE, Snowflake stages files then runs COPY INTO table FROM @stage, and Databricks uses COPY INTO or Auto Loader from cloud storage. The shared rule is identical: point at the right database, run, refresh, confirm row counts.

Two traps here. First, loading a file while the editor header names the wrong database scatters tables into postgres or HR instead of learning. Second, forgetting Refresh after a good run leads to re-running the same script and hitting "already exists" errors for tables that are actually fine.

1.7.2 Human Resources Database

The HR database (a small staff sample with staff, jobs, departments, and places, for example the employees table joined to departments) is the classic Oracle-style practice set reused here. To load it, make a fresh database. Right-click Databases, pick Create Database, name it HR, set owner to Adam, and pick Save. Pick the new HR node so the next query runs there. Open the Query Tool and check that the header shows the HR link, because every later step depends on that header.

Get the course zip from the downloads, unzip it, open the folder, and find hr.sql. Use Open File to load hr.sql into the editor. Pick Run. The run builds tables and adds rows. Notices about missing tables, such as table region does not exist, are normal on a fresh first run. The script first tries to drop old tables with lines like DROP TABLE IF EXISTS guards. Since none exist yet, it prints a notice. Run the same script a second time and the notice goes away because the tables now exist to drop and rebuild. To confirm, refresh Tables under schemas. The tables countries, departments, employees, job_history, jobs, locations, and regions show with their columns.

Worked example — HR from scratch. Make HR owned by adam. Open the Query Tool on HR and confirm the header. Load hr.sql. Run once and note the region-table notice. Run again and note the notice is gone. Refresh Tables. Done when seven tables (countries, departments, employees, job_history, jobs, locations, regions) show with columns. Open schemas, then Tables. About 14 tables now show. Open orders to check order rows and columns. Open employees to check staff rows. The 14 tables and their rows are then ready for many PostgreSQL queries, such as multi-table links and subqueries.

A fresh view may show more or fewer sibling databases based on which prior videos were done. That is fine. As long as Northwind builds with its tables, the rest can be built in their own steps.

One cross-system note worth keeping: primary and foreign keys in PostgreSQL and MySQL are enforced (bad rows are rejected), while in Snowflake they are declared but informational for the optimizer, and Databricks adds FOREIGN KEY support mainly on Delta with its own limits. So the purchases and Northwind key errors seen here during practice are real guards in PostgreSQL that would pass silently in Snowflake.

1.8 Dropping Databases with Safety Rules

1.8.1 Syntax and Permission

To drop a database (erase it fully from the server, for example removing db_test with every table inside) means to erase it fully from the server. The form is DROP DATABASE followed by the name. A longer form adds IF EXISTS before the name. IF EXISTS (a guard that tells the server to skip errors when the named database is not there, for example DROP DATABASE IF EXISTS db_test) tells the server to skip errors when the named database is not there. Without it, dropping a missing name raises an error. With it, the run ends quietly with a notice when there is nothing to drop.

The two core lines are CREATE DATABASE plus name to make, and DROP DATABASE plus name to erase, with the IF EXISTS guard when the name may already be gone:

CREATE DATABASE db_test;
DROP DATABASE IF EXISTS db_test;

Only superusers and the database owner may run DROP DATABASE. This is a permission rule, so a plain user link cannot erase databases owned by others. Trying it as a stranger fails with a permission error, which is the server protecting other owners.

The DROP family is risky by design. DROP TABLE, DROP VIEW, DROP SCHEMA, DROP DATABASE, and similar forms all erase at once with no undo and no recycle bin. Extra care is needed each time any DROP line is run. Check that no live use needs the target, that it is not a work database, and that the name is typed right before picking Run. Active links block the erase, so disconnect query tabs on that database first.

How the guard spells elsewhere: MySQL accepts DROP DATABASE IF EXISTS db_test with DROP SCHEMA as a synonym, Snowflake uses DROP DATABASE IF EXISTS db_test, and Databricks uses DROP DATABASE IF EXISTS db_test CASCADE (or DROP SCHEMA ... CASCADE) because without CASCADE a non-empty schema refuses to drop. Same safety idea everywhere, slightly different keywords, and no undo anywhere.

Scope: IF EXISTS guards against a missing name only. It does not guard against a wrong name that happens to exist, so typing a live database name with the guard still erases it without complaint.

Two traps here. First, running DROP while still linked to the target database fails or, worse, running it while linked to the wrong database erases the wrong store, so confirm both the statement text and the header database. Second, assuming a dropped database can be restored from pgAdmin history is false: only a real backup file can bring it back.

Exam note: Keep the DROP syntax, the IF EXISTS guard, and the owner-or-superuser rule together. They are short facts that are easy to test, and the no-undo warning is the reason examiners ask about them.

1.8.2 Creating and Removing a Test Database

A test database (a throwaway store just to try the syntax, for example db_test made and erased in one sitting) is the safe way to practice. To make one, the form is CREATE DATABASE followed by the name. In this session the name is db_test. Type CREATE DATABASE db_test; and Run. The run ends well in a few milliseconds. Right-click Databases and pick Refresh. The new db_test node shows with a cross mark, which means no live link is open to it yet, not that anything failed.

To remove it, type DROP DATABASE db_test; and Run. Before picking Run, pause and check the name twice, since the erase cannot be undone. After the run ends well, right-click Databases and pick Refresh again. The db_test node is gone.

So the two core lines are CREATE DATABASE plus name to make, and DROP DATABASE plus name to erase, with the IF EXISTS option when the name may already be gone.

1.8.3 Worked Examples

Worked example 1 — make then erase db_test. Run CREATE DATABASE db_test; and wait for success. Refresh Databases to confirm the new node. Run DROP DATABASE db_test; after re-reading the name. Refresh Databases to confirm it is gone. Done when the node appears and then disappears across the two refreshes. Sense-check: the appear-then-gone pair proves both the make and the erase paths plus the refresh habit.

Worked example 2 — safe form with guard. Run DROP DATABASE IF EXISTS db_test; to avoid an error when db_test is already gone. Run it twice in a row: the first may drop, the second ends quietly. Done when the second run reports success with a notice instead of an error. Sense-check: the quiet second run proves the guard works for scripts that must be re-runnable.

One-line recap: make with CREATE, erase with DROP, guard scripts with IF EXISTS, and only the owner or a superuser may erase. That caution closes the setup arc and leaves the practice stores ready for querying.

Key Industry Applications

PostgreSQL installers from postgresql.org through EDB builds are the standard on-premise start, while MySQL Installer, cloud sign-ups for Snowflake, and workspace provisioning for Databricks are the parallel starts elsewhere. pgAdmin 4 is the visual client for daily PostgreSQL work, with MySQL Workbench, Snowflake Snowsight with SnowSQL, and the Databricks SQL editor as its counterparts. SQL Shell is the terminal client for the same server when the visual tool is too slow or unavailable. Cloud servers such as Amazon and Google instances need strong superuser passwords and locked-down ports, never practice passwords. UTF-8 is the common standard for mixed-language text, with MySQL needing the utf8mb4 variant for full emoji cover and Snowflake and Databricks handling it by default. Northwind, a Microsoft sample, is reused here for PostgreSQL practice on links, subqueries, and functions, and it appears in MySQL and SQL Server courses for the same reason. HR tables model staff, jobs, departments, and places, a miniature human-resources system used to practice joins and grouping. Stock symbols, types, and prices model public market data for query practice, the same facts-plus-lookup shape analysts meet in finance feeds.
