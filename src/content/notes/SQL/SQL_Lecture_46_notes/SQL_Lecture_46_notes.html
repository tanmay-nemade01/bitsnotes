46.1 Creating New Tables With SELECT INTO and WHERE

46.1.1 Idea and Syntax

What if a query could leave a brand-new table behind as its answer, instead of just flashing rows on the screen?

A common task is to make a new table straight from the rows returned by a query. In PostgreSQL the SELECT ... INTO form does two jobs at once. It creates a fresh table and fills it with the query result. No separate CREATE TABLE step is needed first.

Think of taking a photo of a bookshelf and getting an actual second bookshelf holding copies of just the books you pointed at. The original shelf keeps every book. The new shelf holds only the copies. That is SELECT INTO: a snapshot query that leaves a real table behind. The picture breaks down in one place: unlike a photo, the copy is live data you can update, join, and index on its own.

The shape of the statement is simple. List the columns wanted after SELECT. Put INTO plus the new table name next. Then give the source with FROM plus the old table name. Add WHERE plus a condition when only some rows should move over.

SELECT column_list
INTO new_table_name
FROM original_table_name
WHERE condition;

An asterisk * means all columns. A new table gets the same column names, matching column types, and the stored values from the rows that pass the filter. Later queries can read that new table like any other table.

What exactly carries over, and what does not? Column names, data types, and the copied row values carry over. Constraints, primary keys, foreign keys, indexes, and default values do not carry over. The new table is a plain table with plain columns. If the new movies_pg table needs its own primary key or index later, add it with a separate ALTER TABLE or CREATE INDEX step.

Across database systems the same idea wears different names, which helps when moving between them. PostgreSQL and SQL Server both accept SELECT ... INTO new_table FROM .... MySQL does not use SELECT INTO for making tables; it uses CREATE TABLE new_table AS SELECT ... instead (in MySQL, SELECT ... INTO means writing into variables or an output file). Snowflake and Databricks also use the CREATE TABLE ... AS SELECT form, usually called CTAS. Oracle uses CTAS as well. So SELECT INTO in this lecture is the PostgreSQL spelling of a widely shared idea.

Scope: SELECT INTO works when the target table does not exist yet. If movies_pg already exists, the statement stops with an error instead of appending. To add rows to an existing table, use INSERT INTO ... SELECT ... instead. Assumption: the role running the command has permission to create tables in the current schema, and the new table lands in the same schema as the session default unless the name is schema-qualified.

Two traps catch beginners. First, running the statement twice fails the second time, because the table now exists; drop the table or pick a new name before re-running. Second, inside a PL/pgSQL code block, SELECT ... INTO takes a different meaning: it stores values into declared variables instead of making a table. Keep the table-making form in plain SQL sessions, and use CREATE TABLE AS inside procedural code when a real table is wanted.

SELECT INTO builds a fresh table from a query result in one step, copying column names, types, and matching rows, but no constraints or indexes. Next, the same form stretches to joins, computed columns, sorting, and saved subqueries.

46.1.2 Worked Example Filtering English Movies Rated PG

The movies table holds one row per film. One of its columns is age_certificate, which stores values such as PG. The goal is a smaller table called movies_pg that holds only English-language films whose age rating is PG.

First the full table is inspected, to see the certificate values before filtering:

SELECT * FROM movies;

The output shows every movie plus its age certificate column. The rows of interest are the ones where that column equals PG.

Then the new table is built in one step:

SELECT *
INTO movies_pg
FROM movies
WHERE age_certificate = 'PG';

The command reports success. A check of the table list shows movies_pg sitting next to the other tables, with the same columns carried over.

Its content is confirmed with:

SELECT * FROM movies_pg;

Every row returned carries a PG rating. The rest of the films stay only in the original movies table. Nothing is removed from the source. The operation copies matching rows into the new home. Sense-check: counting rows in both tables shows the new table holds fewer rows than the source, and every certificate value in the new table reads PG.

Picture the result as a bar chart of film counts by certificate, with one bar per rating. The source table shows the full chart. The new table shows only the PG bar, lifted out into its own chart with the same column labels. The takeaway: filtering plus saving gives a stable slice that later queries can read without repeating the filter.

Reporting teams use this pattern daily. A marketing analyst pulls this week's PG-rated English titles into a small table, then builds charts and follow-up joins from that stable slice while the main catalog keeps changing underneath.

46.1.3 Student Questions and Answers

Q: Does SELECT INTO delete or move rows out of the old table?

A: No. The source table keeps all its rows. Matching rows are copied into the new table. The source stays complete. The word INTO describes where copies land, not a move. To remove rows from the source, a separate DELETE statement is needed.

46.2 SELECT INTO With JOIN, Computed Columns, ORDER BY, and Subqueries

46.2.1 Combining Tables and Shaping the Result Before Saving

What if the saved table needs columns that exist nowhere yet, like a total that must be computed first?

SELECT INTO is not limited to one table plus WHERE. Joins, column arithmetic, sorting, null handling, limits, and subqueries all work inside it. That makes it a short path from an analytic question to a saved result table.

The pattern used here has three parts. An inner query joins sources, builds a computed column, sorts, and trims. An outer SELECT * INTO new_table FROM (inner_query) AS alias wrapper saves that shaped result.

The computed column in this part is total revenue (domestic plus overseas takings for one film), written total_revenue. The verbal rule is total revenue equals domestic revenue plus international revenue. With \(revenues\_domestic\) for home-market takings and \(revenues\_international\) for overseas takings, both in money units, and \(total\_revenue\) for their sum, also in money units:

\[total\_revenue = revenues\_domestic + revenues\_international\]

Take a tiny case: a film with \(revenues\_domestic = 100\) and \(revenues\_international = 50\) gives \(total\_revenue = 100 + 50 = 150\). When either input is missing (NULL), the sum is missing too, which is why null placement in sorting matters below.

Sorting uses a column position number, with NULLS LAST pushing missing values to the end, and LIMIT 10 keeping only the first ten rows. The alias on the subquery is required. Without it PostgreSQL stops with an error.

Why does NULLS LAST matter here? A film with no reported revenue would otherwise float into the top ten on some systems and push a real earner out. The professor's point is that missing revenue must never crowd the top ten, so nulls are pinned to the bottom. Note a cross-system detail that helps when switching databases: null ordering defaults differ. In PostgreSQL, nulls sort first on descending sorts unless told otherwise; in MySQL, nulls sort first on ascending sorts. Writing NULLS LAST out in full keeps the intent fixed on every system that accepts the keywords. On MySQL, which lacks the keywords, the same effect takes an ORDER BY total_revenue IS NULL, total_revenue DESC shape.

Scope: positional sorting such as ORDER BY 5 counts columns left to right in the select list, starting at 1. It works in PostgreSQL, but it is fragile: adding one column shifts every position after it, exactly as happens in this lecture when the sort key moves from 7 to 8. Assumption: the inner query returns its columns in a fixed order, so the position number points at the intended column. Prefer naming the alias (ORDER BY total_revenue DESC NULLS LAST) in saved work, since names survive column additions.

Any full query, including joins, arithmetic, sorting, and limits, can be wrapped in SELECT INTO to freeze its answer as a table. Next, that pattern runs on real movie and revenue tables.

46.2.2 Worked Example Top Ten Movies by Total Revenue

Two tables matter here. The movies table is aliased mv and holds identifiers such as movie_id and movie_name. The movies_revenues table is aliased r and holds movie_id, revenues_domestic, and revenues_international. The shared key is the movie identifier.

The join is built first with SELECT * to confirm the link works:

SELECT *
FROM movies AS mv
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id;

The combined rows show names beside their domestic and overseas figures. Every movie identifier on the left finds its money row on the right.

Then the column list is narrowed and the computed column is added:

SELECT
  mv.movie_id,
  mv.movie_name,
  r.revenues_domestic,
  r.revenues_international,
  r.revenues_domestic + r.revenues_international AS total_revenue
FROM movies AS mv
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id
ORDER BY 5 DESC NULLS LAST
LIMIT 10;

Position 5 is the new total_revenue column. DESC puts the biggest earners first. NULLS LAST sends rows with missing revenue to the bottom so they never crowd the top ten. LIMIT 10 cuts the list after ten rows, ending at the film Jaws in this data set. Trace one row: if a film shows domestic 200 and international 120, its stored total reads 320.

That finished query becomes the inner part of a save step:

SELECT *
INTO top_ten_movies
FROM (
  SELECT
    mv.movie_id,
    mv.movie_name,
    r.revenues_domestic,
    r.revenues_international,
    r.revenues_domestic + r.revenues_international AS total_revenue
  FROM movies AS mv
  INNER JOIN movies_revenues AS r
    ON mv.movie_id = r.movie_id
  ORDER BY 5 DESC NULLS LAST
  LIMIT 10
) AS top_movies;

After a refresh the table top_ten_movies appears. Browsing it with SELECT * FROM top_ten_movies; shows the ten rows up to Jaws, including the stored total_revenue values. Sense-check: the saved table holds exactly ten rows, and reading its totals from top to bottom shows values falling, with no missing total in the list.

46.2.3 Worked Example Top Ten Directors With Joined Names

The same revenue logic extends to three tables by adding directors, aliased d. The link from films to people is the director identifier: mv.director_id matches the director key in d. One early attempt wrote the join against the wrong alias, then fixed it to join movies to directors on the director identifier. That fix connects all three sources: movies, revenues, and directors.

Director columns are added beside the film columns:

SELECT
  mv.movie_id,
  mv.movie_name,
  d.director_id,
  d.director_first_name,
  r.revenues_domestic,
  r.revenues_international,
  r.revenues_domestic + r.revenues_international AS total_revenue
FROM movies AS mv
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id
INNER JOIN directors AS d
  ON mv.director_id = d.director_id
ORDER BY 7 DESC NULLS LAST
LIMIT 10;

When a last-name column joins the list, the computed total shifts one place to the right, so the sort key moves from position 7 to position 8:

SELECT
  mv.movie_id,
  mv.movie_name,
  d.director_id,
  d.director_first_name,
  d.director_last_name,
  r.revenues_domestic,
  r.revenues_international,
  r.revenues_domestic + r.revenues_international AS total_revenue
FROM movies AS mv
INNER JOIN movies_revenues AS r
  ON mv.movie_id = r.movie_id
INNER JOIN directors AS d
  ON mv.director_id = d.director_id
ORDER BY 8 DESC NULLS LAST
LIMIT 10;

This shift is the live demo of why positional sorting is fragile: one added name column renumbers the total.

The save wrapper follows the same shape, this time into top_ten_directors:

SELECT *
INTO top_ten_directors
FROM (
  SELECT
    mv.movie_id,
    mv.movie_name,
    d.director_id,
    d.director_first_name,
    d.director_last_name,
    r.revenues_domestic,
    r.revenues_international,
    r.revenues_domestic + r.revenues_international AS total_revenue
  FROM movies AS mv
  INNER JOIN movies_revenues AS r
    ON mv.movie_id = r.movie_id
  INNER JOIN directors AS d
    ON mv.director_id = d.director_id
  ORDER BY 8 DESC NULLS LAST
  LIMIT 10
) AS top_dirs;

A first try left off the alias after the closing bracket. PostgreSQL answered with an error of the form subquery in FROM must have an alias. Adding AS top_dirs makes the same statement succeed. Refreshing the table list shows top_ten_directors, and SELECT * FROM top_ten_directors; returns the ten director rows with names and totals. Sense-check: ten rows, names present beside each total, totals falling down the list.

The alias rule travels well: PostgreSQL and MySQL both demand an alias on every subquery in FROM. SQL Server, Snowflake, and Databricks Spark SQL accept the same aliased form, so writing the alias always keeps the query portable.

46.2.4 Student Questions and Answers

Q: Can SELECT INTO combine joins, sorting, computed columns, and limits in one step?

A: Yes. The inner query can hold joins, arithmetic such as domestic plus international revenue, ORDER BY with NULLS LAST, and LIMIT. The outer SELECT INTO then saves that whole shaped result. Several students asked versions of this, and the answer is the same each time: shape first, save second.

Q: Why did the subquery version fail with a missing alias error?

A: PostgreSQL requires every subquery in FROM to carry an alias. Adding a name such as AS top_dirs after the closing bracket fixes it. The query then runs and the new table is created. The alias gives the database a name for the temporary result it must read from.

46.2.5 Practical Notes

Saving a top-ten profitable-films table is a standard reporting step. Analysts keep the query result as a table so charts and follow-up joins read from stable data while the source catalog keeps changing. A dashboard that reads top_ten_movies never slows down the live revenue feed, and re-running the month-end report gives the same frozen ten.

One caution carries over from the source: SELECT INTO in its plain SQL form behaves differently inside procedural code blocks, where INTO takes another meaning. In PL/pgSQL, SELECT ... INTO some_variable stores one row into a variable instead of creating a table. Keep the table-making form in plain SQL sessions. Inside functions and procedures, prefer CREATE TABLE ... AS SELECT ... for making tables, and reserve SELECT INTO for variable assignment.

Joins, arithmetic, ordering with null control, limits, and aliased subqueries all fit inside a saved query, so the analytic question and the stored answer stay one step. Next, a second copy form duplicates tables with or without their rows.

46.3 Duplicating a Table With and Without Data

46.3.1 CREATE TABLE AS and WITH NO DATA

Need a practice copy of a table to try risky operations on, without touching the real data?

A second way to copy a table is CREATE TABLE ... AS followed by a SELECT. With a plain SELECT * the structure and all rows move over. With WITH NO DATA added at the end, only the structure moves over and the new table starts empty.

CREATE TABLE new_table AS
SELECT * FROM original_table;
CREATE TABLE new_table AS
SELECT * FROM original_table
WITH NO DATA;

Think of the first as photocopying pages plus words, and the second as photocopying blank lined paper with the same margins. Column names and types carry across in both cases. Like SELECT INTO, this form copies names, types, and values, but not constraints, keys, indexes, or defaults.

How do the two copy forms compare? SELECT INTO new_table FROM ... and CREATE TABLE new_table AS SELECT ... do nearly the same job in PostgreSQL. CREATE TABLE AS is the more standard spelling across systems, and it alone offers extras such as WITH NO DATA and IF NOT EXISTS. For an empty framed copy on systems without WITH NO DATA, the portable trick from the SQL Cookbook is a condition that is never true: CREATE TABLE jobs3 AS SELECT * FROM jobs WHERE 1 = 0;. On SQL Server the matching empty-copy trick is SELECT * INTO jobs3 FROM jobs WHERE 1 = 0;. IBM Db2 offers a dedicated CREATE TABLE ... LIKE form for copying structure. And MySQL, which lacks SELECT INTO for tables, uses CREATE TABLE ... AS SELECT ... or CREATE TABLE ... LIKE ... for both jobs. Snowflake and Databricks use CTAS widely, with options such as CREATE TABLE ... CLONE (Snowflake zero-copy clone) going even further.

Scope: WITH NO DATA copies the shape but runs the query without moving rows, so it is cheap even on huge tables. Assumption: the target name is free, and constraints must be re-added by hand afterward if the copy needs them.

The common trap is assuming the copy is a full twin. It is not: no primary key, no foreign keys, no unique rules, no defaults, and no indexes come along. A duplicate built for load testing may run slower than the original simply because its indexes are missing.

CREATE TABLE AS clones a table with or without its rows, giving a safe sandbox or an empty frame on demand. Next, outside data enters through CSV import.

46.3.2 Worked Example Copying the Jobs Table Both Ways

The jobs table is the source. A look first confirms 19 rows:

SELECT * FROM jobs;

A full copy called jobs2 is made with:

CREATE TABLE jobs2 AS
SELECT * FROM jobs;

After refresh, jobs2 sits in the table list with matching columns such as the job identifier. Reading it back:

SELECT * FROM jobs2;

returns the same 19 rows. Structure and content both match: 19 source rows in, 19 copy rows out.

A structure-only copy called jobs3 is made with:

CREATE TABLE jobs3 AS
SELECT * FROM jobs
WITH NO DATA;

Its columns match the source exactly. Reading it back:

SELECT * FROM jobs3;

returns zero rows. The frame is there with no rows inside: same columns, 0 rows. Sense-check: comparing counts gives 19 for the source, 19 for jobs2, and 0 for jobs3, which is exactly the expected pattern.

Cleanup uses drops to keep the database tidy:

DROP TABLE jobs2;
DROP TABLE jobs3;

Test copies like jobs2 serve real duty: trying a bulk update or a schema change on the copy first shows what would break, while the live table stays safe.

46.3.3 Student Questions and Answers

Q: How do we check that a full copy worked and an empty copy stayed empty?

A: Compare row counts. SELECT * FROM jobs2 should return 19 rows like the source. SELECT * FROM jobs3 should return zero rows with matching columns. A count query such as SELECT COUNT(*) FROM jobs2; gives the same proof in one number.

46.4 Importing Data From CSV Files

46.4.1 Steps and Preparation

A vendor sends 249 country codes in a spreadsheet file. How do those rows get inside the database without 249 hand-typed inserts?

Bringing comma-separated values into PostgreSQL takes two stages. First create a receiving table with fitting types. Then load the file with the psql meta-command \copy, giving the target columns, the file path, the delimiter, and a header flag when the first line holds names.

The two stages are: (1) create the receiving table (choose a key plus columns with types sized to the data), and (2) run the load (name the table, name the columns, point at the file, state the delimiter, and say whether a header line leads the file). The sample file is country_iso_code.csv, taken from the course resource attachment. It holds about 268 rows, one per place, with the last row for Zimbabwe reading as name Zimbabwe, two-letter code ZW, three-letter code ZWE, region Africa, and subregion Sub-Saharan Africa. Its first line is a header row, so the load must skip it as names rather than read it as data.

A practical tip runs through the whole task. Know the file path before opening the terminal. The simplest path is to start the terminal in the folder that holds the downloaded file, so the file name alone is enough. Paths look different on Windows and Mac, so quote the full path when one is needed.

The \copy versus COPY split deserves a plain telling, since it confuses every beginner once. COPY is a server-side SQL command: the database server reads the file, so the file must sit where the server can reach it, and only privileged roles may run it. \copy is a psql client-side helper: the terminal session reads the file from the user's own machine and streams the rows to the server, so any role with insert rights can load its own files. In class, \copy is the right call.

Across systems the loader changes name but the two-stage shape stays. MySQL uses LOAD DATA INFILE 'file.csv' INTO TABLE ... FIELDS TERMINATED BY ',' IGNORE 1 LINES;. Snowflake loads from named stages with COPY INTO countries FROM @my_stage/country_iso_code.csv FILE_FORMAT = (TYPE = CSV SKIP_HEADER = 1);. Databricks Spark SQL uses COPY INTO countries FROM 'path/country_iso_code.csv' FILEFORMAT = CSV FORMAT_OPTIONS ('header' = 'true');. Learning the PostgreSQL flags first makes each of these read as the same idea: file, delimiter, header, target columns.

Scope: the column list in the \copy call must match the file's columns in order, and types must fit: a two-letter code column of width 2 rejects a three-letter value. Assumption: the file uses one row per line, commas between values, and quoted fields where a value itself holds a comma.

Three traps recur. A wrong delimiter loads whole lines into the first column. A missing HEADER flag loads the header names as a bogus country row. A wrong file path fails before any row moves, so confirm the path with a directory listing before launching the load.

CSV import is create-then-load: fit the table to the file, then stream the file in with delimiter and header flags. Next, that flow runs end to end on real country data.

46.4.2 Worked Example Building and Loading the Country Code Table

The receiving table is created with a serial key plus text fields sized to the codes:

CREATE TABLE countries_iso_code (
  country_id SERIAL PRIMARY KEY,
  country_name VARCHAR(255),
  iso_code_2 VARCHAR(2),
  iso_code_3 VARCHAR(3),
  region VARCHAR(200),
  sub_region VARCHAR(200)
);

Note the column list in the load below leaves out country_id: the serial key fills itself, so the file needs only the five data columns.

After refresh the empty countries_iso_code table appears under the movies database. Then a terminal session connects to the right database:

psql -h localhost -d movies -U postgres

with password welcome in this setup. Inside that session the load names the table, the columns, the file, the comma delimiter, and the header flag:

\copy countries_iso_code(country_name, iso_code_2, iso_code_3, region, sub_region)
FROM 'country_iso_code.csv'
DELIMITER ','
CSV HEADER;

The report says 249 rows copied into the table. A read-back confirms it:

SELECT * FROM countries_iso_code;

The rows include identifiers plus names, two-letter and three-letter codes, regions, and subregions. The final rows show Zimbabwe with ZW, ZWE, Africa, and Sub-Saharan Africa. Sense-check: the serial keys run unbroken from 1 upward, every two-letter code is exactly two characters, and the last row reads Zimbabwe, so the file landed in the right columns.

Picture a funnel diagram: the wide top is the raw CSV file, the narrow neck is the five named columns plus delimiter and header flags, and the clean stream below is 249 typed rows landing in the table. The takeaway: the flags are the neck of the funnel, and each one must match the file.

This two-stage create-then-copy flow is the normal way teams seed reference tables such as country codes. A data team downloads the vendor file, fits a lookup table to it once, and reloads the file on each vendor update.

46.4.3 Student Questions and Answers

Q: Must the terminal be able to reach the CSV file path?

A: Yes. Start the terminal in the file folder or pass the full quoted path in the FROM string. Without a reachable path the \copy step cannot find the file. A quick directory listing before the load proves the file is visible.

Q: How does the loader know the first line is a header?

A: Add CSV HEADER. That tells the loader to treat the first line as column names and start reading data from the second line. Without it, the header names land as a fake first country row.

46.5 Exporting Data From a Table to CSV

46.5.1 COPY TO With Delimiter and Header

The country table is clean and curated. How does a copy of it reach a colleague who only has a spreadsheet?

Export is the mirror of import. The COPY command names the table, gives TO plus a quoted file path, and sets the delimiter and header choice. With DELIMITER ',' values are separated by commas. With CSV HEADER the first output line holds column names taken from the table.

COPY countries_iso_code
TO 'my_countries_iso_code.csv'
DELIMITER ','
CSV HEADER;

In an interactive terminal session the same call starts with \copy instead of COPY:

\copy countries_iso_code
TO 'my_countries_iso_code.csv'
DELIMITER ','
CSV HEADER;

Use \copy when working inside psql as an ordinary user: the file lands on the client machine, where it can be opened at once. Use server-side COPY only when the file should land on the database server's own disk and the role holds the needed privilege. To export a filtered slice instead of the whole table, replace the table name with a query: COPY (SELECT * FROM countries_iso_code WHERE region = 'Africa') TO 'africa.csv' DELIMITER ',' CSV HEADER;.

Other systems mirror the idea with their own verbs. MySQL writes files with SELECT * FROM countries INTO OUTFILE 'my_countries.csv' FIELDS TERMINATED BY ',' ENCLOSED BY '\"' LINES TERMINATED BY '\n';. Snowflake unloads with COPY INTO @my_stage/my_countries.csv FROM countries FILE_FORMAT = (TYPE = CSV HEADER = TRUE);. Databricks writes with COPY (SELECT * FROM countries) TO 'path/my_countries' FILEFORMAT = CSV. Same mirror, different spelling.

Scope: server-side COPY TO needs a path the server process can write and rights to write there; client-side \copy TO needs only a path the terminal user can write. Assumption: commas inside values are quoted on write so the round trip reads them back correctly.

Two traps: exporting with server-side COPY to a client-only path fails with a permission error, and exporting without HEADER hands the colleague a file whose first data row looks like headings. Match the command to the machine and keep the header flag.

Export mirrors import: name the table or query, point TO a path, and set delimiter plus header. Next, attention turns to cleaning repeats out of tables.

46.5.2 Worked Example Writing 249 Country Rows to a New File

Logged into the movies database from the terminal, the export of the full country table is run as above. The report says 249 rows copied out. Listing files shows my_countries_iso_code.csv now present. Opening it in an editor such as Vim shows the header line first, then comma-separated data rows from the table. Sense-check: the file's line count equals 249 data lines plus 1 header line, and the import count (249) matches the export count (249), closing the round trip exactly.

That round trip, CSV in, table work, CSV out, keeps outside tools and the database in step. Teams export reference extracts this way before sharing them with spreadsheet users or loading them elsewhere.

46.6 Finding and Deleting Duplicate Rows

46.6.1 Spotting Repeats With GROUP BY and HAVING

A customer table holds the same email twice. Before deleting anything, how do you prove which values repeat?

A repeat means the same value appears in more than one row. The quick detector groups by the value column, counts rows per group with \(count(\ast)\), and keeps groups whose count is greater than one:

\[count(\ast) > 1\]

In words, keep only colors whose row count is greater than one. That shortlist names the duplicated values without yet touching them.

The detector reads in three moves: GROUP BY color gathers one bucket per value, COUNT(*) counts rows inside each bucket (here \(count(\ast)\) counts every row in the bucket), and HAVING COUNT(*) > 1 keeps only buckets with at least two rows. HAVING filters groups after grouping, while WHERE filters rows before grouping, which is why the count test belongs in HAVING.

Why prove first? Deleting by hunch risks wiping rows that only look alike. The grouped count is the proof: it returns the duplicated values and their counts, so the delete step that follows has a named target and an expected survivor count.

Scope: this detector answers "which single-column values repeat". When sameness spans several columns, group by the full column set or switch to the window-function lister in 46.6.3. Assumption: NULL values group together in PostgreSQL, so two missing colors count as a repeated group; decide beforehand whether missing values are true repeats.

Group, count, and keep counts above one: that shortlist is the safe target list for every delete that follows. Next, the detector and the delete run on a tiny table.

46.6.2 Worked Example Small Colors Table and Self-Join Delete

A tiny demo table is built:

CREATE TABLE colors (
  color_id SERIAL PRIMARY KEY,
  color VARCHAR(100)
);

It starts empty. Inserts add blue once, green twice, red once, and yellow once:

INSERT INTO colors (color) VALUES
  ('blue'),
  ('green'),
  ('green'),
  ('red'),
  ('yellow');

Reading it back:

SELECT * FROM colors;

shows blue on identifier 1, then green on identifiers 2 and 3, then red on 4 and yellow on 5.

The detector query is:

SELECT color, COUNT(*)
FROM colors
GROUP BY color
HAVING COUNT(*) > 1
ORDER BY color;

It returns one row: green with count 2. That matches the two green rows seen above. Every other color counts 1 and drops out.

Removal on a small table uses DELETE ... USING as a self-join. Table a is the candidate to delete. Table b is the same table used as a partner. Rows drop when the first identifier is smaller and the color matches:

DELETE FROM colors AS a
USING colors AS b
WHERE a.color_id < b.color_id
  AND a.color = b.color;

Trace the green pair: row 2 finds partner row 3 with a smaller identifier, so row 2 drops. Row 3 finds no partner with a larger identifier, so row 3 stays. After success, SELECT * FROM colors; shows one green left, and it carries the larger identifier 3. The smaller identifier went away because the condition kept the later copy. The kept-versus-removed choice follows straight from the less-than direction: flip < to > and the earlier copy survives instead. Sense-check: four rows remain, one per color, and the surviving green carries identifier 3.

Picture the pair as two numbered tickets for the same seat. The rule tears up the lower-numbered ticket and keeps the higher one. The takeaway: the comparison direction picks the survivor.

Other systems delete repeats with their own spelling. MySQL joins the table to itself in a multi-table delete: DELETE a FROM colors a JOIN colors b ON a.color = b.color AND a.color_id < b.color_id;. SQL Server and Snowflake typically number rows in a common table expression and delete the extras: WITH d AS (SELECT color_id, ROW_NUMBER() OVER (PARTITION BY color ORDER BY color_id) AS n FROM colors) DELETE FROM d WHERE n > 1; (SQL Server form). Databricks Delta Lake uses MERGE or a rewrite for the same job. The PostgreSQL DELETE ... USING here is one dialect of a shared pattern: pair up equal values, keep one, drop the rest.

Always back up before a delete: CREATE TABLE colors_backup AS SELECT * FROM colors; costs one line and buys back every mistake. On a live table, test the pairing as a SELECT first, then convert it to the DELETE.

46.6.3 Worked Example Listing Repeats in Larger Tables With a Window Function

For wider tables the grouped count is less handy, because all columns matter, not one. The stronger lister numbers rows inside each value group with the ROW_NUMBER window function, partitioned by the target columns and ordered by the identifier:

SELECT *
FROM (
  SELECT
    color_id,
    color,
    ROW_NUMBER() OVER (
      PARTITION BY color
      ORDER BY color_id ASC
    ) AS dup_row
  FROM colors
) AS dupes
WHERE dupes.dup_row > 1;

In words, restart numbering at 1 for each color, in identifier order, and keep numbered rows greater than one. Those kept rows are the extra copies. Here \(dup\_row\) is the position number inside each color group: the first green gets 1, the second gets 2, and only numbers above 1 are extras.

Trace it on greens at identifiers 3, 6, and 7: the numbering gives 3 a dup_row of 1, 6 a dup_row of 2, and 7 a dup_row of 3, so the outer filter returns identifiers 6 and 7 as the extra copies.

To show it, another green is inserted, so greens sit on identifiers 3, 6, and 7. Running the window lister flags the later copies. Targeted deletes then clear chosen extras one by one:

DELETE FROM colors WHERE color_id = 7;
SELECT * FROM colors;

now shows greens on 3 and 6 only. Repeating the delete for identifier 6 leaves one green. Sense-check: one green remains with the smallest identifier, and the grouped detector now returns zero rows. The table is dropped at the end for tidy housekeeping:

DROP TABLE colors;

46.6.4 Student Questions and Answers

Q: How do we first prove which values repeat before deleting anything?

A: Run the grouped count with HAVING COUNT(*) > 1 for one column, or the ROW_NUMBER partitioned list for full-row repeats. Both return only the extra copies, so the delete step stays safe. Prove first, delete second, verify third.

Q: Why did one green survive with the larger identifier after the self-join delete?

A: The condition a.color_id < b.color_id deletes the earlier partner and keeps the later one. The survivor holds the larger identifier by design. Reversing the comparison would keep the earlier copy instead.

Duplicates fall to a fixed routine: prove with a count or a window listing, delete the extras, verify one survivor. Next, the lecture turns to why tables grow even when rows are removed.

46.7 How Inserts, Updates, and Deletes Change Table Size

46.7.1 Three Operations and Why Size Moves

A table loses a thousand rows to a delete, yet its file size does not shrink. Where did the space go?

Everyday table work falls into three kinds: adding rows with insert, changing values with update, and removing rows with delete. Each kind touches storage, so table size answers by growing or, less directly, holding steady.

Insert (adding brand-new rows) is the plain case. New rows land on disk, so size grows with the added data. Update (changing values in existing rows) and delete (removing rows) behave less directly in PostgreSQL. An update keeps the old row image and adds a fresh row image with the new value. A delete hides the row from later reads yet leaves its image on disk for a while. The leftover images have a name: dead rows (also called dead tuples, since a tuple is the internal name for a stored row). They linger because concurrent transactions, rollback, and savepoints may still need older versions.

The design reason is multi-version concurrency: readers must keep seeing a steady snapshot while writers change values. So PostgreSQL writes the new version beside the old one instead of overwriting in place. Old versions turn invisible to new readers the moment no running transaction can still see them, but their bytes wait for the cleaner.

That is why a delete may not hand space back at once, and why a small logical change can still push physical size up. More dead rows mean a bigger footprint until cleanup runs.

Other systems handle old versions differently, which explains why this story is PostgreSQL-flavored. MySQL's InnoDB keeps old versions in a rollback area and purges them with a background purge thread rather than leaving dead rows inside the table file. Snowflake stores data in immutable micro-partitions and rewrites them on change, with all cleanup automatic and invisible. Databricks Delta Lake writes new file versions on change and cleans old files with its own VACUUM retention command, which is a different command with the same name. The shared lesson holds everywhere: updates cost more storage than their new values suggest.

Scope: dead-row buildup applies to write-heavy PostgreSQL tables; read-mostly lookup tables barely accumulate any. Assumption: concurrent transactions and rollback support stay on, which is the normal running state.

The classic trap is sizing disk for live rows only. A table with heavy daily updates can hold nearly twice its live data in dead images, so capacity plans must use the write mix, not just the row count.

Inserts add live bytes; updates and deletes leave dead images beside the live ones until cleanup. Next, a tiny picture makes the doubling concrete.

46.7.2 Worked Picture of an Update Leaving Two Images

Picture one live row holding a value. An update that adds one to it writes a second image with the raised value. Readers see only the new image. Storage for a time holds both: the old dead image plus the new live image. So one row becomes two stored images holding one visible value.

A later delete follows the same pattern from the reader side: the row vanishes from results, while its disk image waits as a dead row until the engine reclaims it. Zero visible rows, one stored image. Sense-check: visible rows and stored images are different counts, and only the cleaner reunites them.

46.7.3 Student Questions and Answers

Q: Why does deleting rows not shrink the table right away?

A: Deleted images stay on disk as dead rows until cleanup. They are unseen by queries but still take space. Later vacuum work reclaims that space for reuse. The delete hides rows from readers at once but frees bytes only when the cleaner runs.

Every update doubles one row's footprint for a while, and every delete hides without freeing, which sets up the measuring tools next.

46.8 Tracking Table Size Through Insert and Update

46.8.1 Size Functions and a Test Table

By what number can you watch a table swell and prove the dead-row story is real?

Two functions report size. The verbal rule is the pretty size equals the formatted total relation size for the named table. With \(s\_bytes\) for the raw byte count from \(pg\_total\_relation\_size\) and \(s\_pretty\) for the human text from \(pg\_size\_pretty\):

\[s\_pretty = pg\_size\_pretty(pg\_total\_relation\_size('table\_vacuum'))\]

\(pg\_total\_relation\_size\) counts the table plus its helper objects such as indexes and free-space maps, in bytes. \(pg\_size\_pretty\) turns a byte count into text such as 736 kB or 11 MB. Raw bytes suit checks. The pretty text suits eyes, showing values such as 0 bytes, 736 kB, 2152 kB, 5688 kB, and 11 MB.

Two companion functions round out the family for later reference: \(pg\_relation\_size\) counts only the main table file, and \(pg\_table\_size\) counts the table plus its free-space map and visibility map but not indexes. The lecture's choice, the total, is the fullest measure and the right one for capacity watching.

A minimal test table isolates the effect:

CREATE TABLE table_vacuum (
  id INTEGER
);

It starts with one integer column and zero rows:

SELECT * FROM table_vacuum;

Both size calls agree at the start:

SELECT pg_total_relation_size('table_vacuum');
SELECT pg_size_pretty(pg_total_relation_size('table_vacuum'));

Each reports 0 bytes on the empty table. An empty table with no pages yet costs nothing measurable, which gives a clean zero baseline.

Scope: these functions report physical bytes, not row counts; equal row counts can still differ in bytes when widths or dead rows differ. Assumption: the name passed is the exact table name in the current schema.

Two calls give the full physical size in bytes and in readable text, starting from zero. Next, inserts walk the size upward.

46.8.2 Worked Example Inserts Grow Size Step by Step

Rows are added in bulk with generate_series, which produces a run of numbers to insert. Here \(generate\_series(1, 20000)\) is a number generator yielding the integers 1 through 20000 as rows:

INSERT INTO table_vacuum
SELECT * FROM generate_series(1, 20000);

Size climbs to 736 kB. A second similar load lifts it to 2152 kB. A larger push toward about 100000 rows and beyond lifts it to 5688 kB. Each insert adds live rows, so growth tracks the added data. Reads at this stage show around 160000 rows of plain numbers. Sense-check: every load raises the size, and no load doubles it, because each insert adds only live images with no dead ones.

Picture a staircase chart with load number on the horizontal axis and table size on the vertical: three steps rising to 5688 kB, each step sized by its fresh rows. The takeaway: insert growth is steady and proportional.

46.8.3 Worked Example One Small Update Nearly Doubles Size

With size sitting at 5688 kB, a single statement adds one to every identifier:

UPDATE table_vacuum SET id = id + 1;

Values shift by one: 1 becomes 2, 2 becomes 3, and so on. Nothing else changes in meaning. Yet size jumps to about 11 MB, close to double. The old images remain as dead rows beside the new live images, so one logical pass costs nearly one full extra copy on disk: about 160000 live images plus about 160000 dead images. Heavier expressions or wider rows would push the cost higher still. Sense-check: the values moved by exactly one, the row count did not change, but the bytes nearly doubled, which fingerprints dead rows as the cause.

The lesson is practical. On tables with frequent updates, dead-row storage can climb fast enough to need watching. Without monitoring, growth can press toward server strain. Backend and database roles plan capacity around write mix, not just live row counts.

Exam note: expect questions that link update to dead rows and near-doubling of size, plus the contrast that insert growth tracks new rows while update growth keeps old plus new images.

46.9 The Autovacuum Background Process

46.9.1 What Runs, When, and Why It Should Stay On

Who cleans up dead rows at 3 a.m. when nobody is logged in?

PostgreSQL ships a background cleaner called autovacuum. It wakes on its own, by default about every minute, and tidies bookkeeping when many rows changed. It needs no hand trigger. Settings can shift its timing or switch it off for special clusters and scheduled-maintenance designs, but the guidance is to leave it on. Switching it off without a replacement plan invites bloat.

Autovacuum (the automatic background cleaner) watches each table's churn and runs a VACUUM pass plus an ANALYZE pass when thresholds trip. ANALYZE (the statistics gatherer) samples table contents so the query planner can pick fast execution plans. Autovacuum has no visual panel. Its footprints live in statistics views. It also runs analyze work beside cleaning, gathering table content facts that help the planner pick fast execution plans.

Why the paired analyze? Cleaning changes what the table looks like, and the planner's old row-count guesses go stale. Refreshing the facts in the same pass keeps later queries on good plans for free.

Scope: autovacuum marks dead-row space reusable inside the table; it does not hand bytes back to the operating system. Tables stay the same file size after its pass. Assumption: default settings with no long-stuck transaction blocking cleanup; an open transaction that never closes can pin dead rows no cleaner can touch.

The standing trap is switching autovacuum off to "save" background work. The cleanup debt then compounds: queries slow on bloated pages, transaction IDs age toward wraparound danger, and the eventual manual cleanup takes far longer than the background passes would have.

Autovacuum plus auto-analyze run on their own about every minute, keeping space reusable and planner facts fresh. Next, its footprints show up in the statistics view.

46.9.2 Worked Example Watching Autovacuum on the Test Table

The view pg_stat_all_tables holds per-table facts across 168 tables in this database, including indexes, tuple counts, and storage notes. The columns of interest are the table name, last hand-run vacuum time, last autovacuum time, last hand-run analyze time, last auto analyze time, hand vacuum count, and auto vacuum count:

SELECT
  relname,
  last_vacuum,
  last_autovacuum,
  last_analyze,
  last_autoanalyze,
  vacuum_count,
  autovacuum_count
FROM pg_stat_all_tables
WHERE relname = 'table_vacuum';

One reading shows last autovacuum around 11:30:28 with timezone offset minus five, auto vacuum count 1, and a matching auto analyze stamp. The story fits the workload. Fresh inserts add only live rows, so no dead-row load appears. The later full-table update creates dead images, which prompts the single autovacuum pass plus its paired analyze.

Running the same broad update again, then waiting past the one-minute rhythm and re-reading the view, shows a second autovacuum stamp near 11:55:30 with auto vacuum count 2 and a fresh auto analyze stamp. The cleaner did wake twice. Sense-check: each full-table update is followed, after about a minute, by one more autovacuum count plus a matching auto-analyze stamp.

Yet size still reads 11 MB after both passes. Autovacuum marked dead-row space as reusable for later writes without handing the bytes back to the operating system. That split, tidy inside, same size outside, sets up the next part on hand-run vacuum forms.

46.9.3 Student Questions and Answers

Q: If autovacuum ran twice, why is the table still 11 MB?

A: Autovacuum frees dead-row space for future rows inside the table but does not return disk bytes to the system. Size stays level until a stronger form such as VACUUM FULL rewrites the table. Inside-tidy and outside-smaller are two different jobs.

Q: Why does auto analyze appear beside autovacuum stamps?

A: The background pass gathers content facts at the same time. Those facts feed the planner so later queries get better execution plans. Cleaning and fact-gathering travel together by design.

The background cleaner reuses space inside and refreshes planner facts, but shrinking the file takes the stronger hand-run form next.

46.10 Reclaiming Space With Hand-Run VACUUM

46.10.1 Syntax Choices FULL, FREEZE, VERBOSE, and ANALYZE

Autovacuum tidies inside but never shrinks the file. What command actually hands bytes back?

The hand-run form names options plus an optional target:

VACUUM [FULL | FREEZE | VERBOSE] [ANALYZE] table_name;

FULL (the rewriting form) rebuilds the full table content into a new file, drops dead images, and gives bytes back. It needs an exclusive lock, so writes wait while it holds the table. FREEZE (the version-freezing form) aggressively freezes old row versions so later cleanup can drop them. Freezing already happens under FULL, so naming both adds nothing. VERBOSE (the reporting flag) prints a per-table activity report, including removable and non-removable row counts, page counts, and dead-row notes. ANALYZE (the fact-refreshing flag) refreshes planner facts during the same pass, and column names can narrow which columns it studies. Leaving off the table name aims the command at every table in the database, which is heavy on a 30-plus-table movies database and calls for care.

Two guardrails matter. A role needs vacuum permission on the target; a superuser naturally has it, while narrower roles need grants. And vacuum cannot run inside a transaction block or function transaction. It must run as its own command.

How does this map to other systems? MySQL has no VACUUM: routine InnoDB purge runs automatically, and OPTIMIZE TABLE rebuilds a table the way VACUUM FULL does, also locking it. Snowflake needs no vacuum at all: micro-partition maintenance is fully automatic. Databricks has a VACUUM command with a different meaning: it deletes old data files past a retention window (default seven days) and never touches live rows, so running it to "shrink after an update" would be a category error there.

Scope: plain VACUUM is the safe routine pass with light locking; VACUUM FULL is the heavy rewrite with an exclusive lock that blocks writers. Assumption: no long-open transaction pins the dead rows, and the session runs the command outside any transaction block.

Two mistakes hurt most. Running a database-wide VACUUM FULL on a live system locks every table it rewrites. And wrapping VACUUM with other writes inside BEGIN ... COMMIT fails outright, since the command refuses to run inside a transaction.

Plain vacuum reuses space gently; FULL rewrites and returns bytes at the price of an exclusive lock. Next, both run on the test table.

46.10.2 Worked Example From Plain VACUUM to VACUUM FULL

Starting size is 11 MB with hand-run counts at zero. A first pass asks for a report on the test table:

VACUUM VERBOSE table_vacuum;

Output notes items such as zero removable rows in one line, counts of non-removable versions, page totals near 1416 pages, and dead-row detail. The stats view now shows a hand-run stamp near 12:02 with vacuum count 1, while auto analyze history stays as before. Running once more lifts the hand count to 2 with a fresh stamp. Size still reads 11 MB. The plain form marked space reusable inside without returning bytes.

The stronger form follows:

VACUUM VERBOSE FULL table_vacuum;

It reports success. The stats view shows a new hand stamp near 12:20 with an updated count. Size now reads 5664 kB, close to the pre-update level. The dead images are gone and only live rows remain: 11 MB down to 5664 kB, about half. Sense-check: the size after FULL lands near the pre-update 5688 kB mark, confirming the extra copy was the dead images.

A database-wide rewrite would be:

VACUUM FULL;

It is not run here because it would lock and rewrite many tables at once. The maintenance pattern for live systems is to warn users, allow an hour or two, serve reads from a backup copy, run the full pass, then switch work back to the cleaned copy.

46.10.3 Student Questions and Answers

Q: When should we pick plain VACUUM and when VACUUM FULL?

A: Pick plain vacuum for routine marking of dead-row space for reuse with light locking. Pick VACUUM FULL when disk bytes must come back, accepting longer time and an exclusive table lock.

Q: Can VACUUM run inside a transaction block with other writes?

A: No. It must run outside a transaction. It also needs vacuum permission on the target table.

Production teams schedule full rewrites as maintenance windows with standby serving, since the exclusive lock blocks updates on the target table.

Exam note: expect items on option meanings, the lock cost of FULL, the permission need, and the bar on running vacuum inside a transaction.

46.11 Auto Generated Columns

46.11.1 GENERATED ALWAYS AS STORED on One Row

What if a column could automatically calculate and update its own value whenever other fields in the row change, without writing a single line of trigger code?

Some columns should always mirror other columns in the same row. A generated column states that rule once in the table definition, and the database engine guarantees that rule stays true on every insert and update. People also call these computed columns or virtual columns, and the mental model is a view narrowed to a single column inside a table. Support in PostgreSQL arrived with PostgreSQL version 12 and later.

Think of a live spreadsheet formula cell inside each row, such as =A2*B2. Whenever you type new numbers into cells A2 or B2, the product cell instantly recalculates. Generated columns bring this exact automated calculation inside the database engine. The analogy breaks in one key physical detail: unlike a spreadsheet where formulas compute in memory on the fly, PostgreSQL physically serializes the evaluated bytes onto disk inside each row tuple during write operations because of the STORED keyword.

The column definition names the column, specifies its data type, adds the clause GENERATED ALWAYS AS with an enclosing bracketed expression, and ends with the mandatory keyword STORED:

CREATE TABLE t (
  w REAL,
  h REAL,
  area REAL GENERATED ALWAYS AS (w * h) STORED
);

In words, area (the two-dimensional surface measurement), written \(area\), equals width (horizontal dimension), written \(w\), multiplied by height (vertical dimension), written \(h\), evaluated strictly on the same row. With \(w\) and \(h\) representing real-number dimensions, and \(area\) representing their product:

\[area = w \times h\]

Every symbol in this governing expression is row-local:

  • \(w \in \mathbb{R}\) is the input width column.
  • \(h \in \mathbb{R}\) is the input height column.
  • \(area \in \mathbb{R}\) is the resulting stored product.

Historically, maintaining derived values required writing custom BEFORE INSERT OR UPDATE PL/pgSQL triggers. Triggers carried noticeable overhead: each insert or update invoked a procedural function context switch, multiplied maintenance complexity, and introduced potential transaction latency. Generated columns replace slower trigger logic cleanly, embedding the calculation directly into PostgreSQL's core tuple-forming C routines.

Different database engines handle computed columns with distinct syntax and storage defaults:

Database Engine Syntax Keyword Storage Mode Support Default Behavior Can Act as Partition Key?
PostgreSQL (12+) GENERATED ALWAYS AS (expr) STORED STORED only Requires explicit STORED No (prohibited)
MySQL (5.7+ / 8.0+) `[GENERATED ALWAYS] AS (expr) [VIRTUAL \ STORED]` VIRTUAL or STORED VIRTUAL (computed on read, 0 disk bytes) Yes (with restrictions)
SQL Server (T-SQL) AS (expr) [PERSISTED] Virtual or PERSISTED Virtual (computed on read) Yes (when PERSISTED)
Oracle [GENERATED ALWAYS] AS (expr) [VIRTUAL] VIRTUAL (default) VIRTUAL Yes
Databricks (Spark SQL) GENERATED ALWAYS AS (expr) Stored in Delta Lake parquet Stored metadata / files Yes (standard for date partitioning)

Notice the practical differences:

  • In MySQL, computed columns default to VIRTUAL, meaning they consume zero disk storage and compute dynamically during queries; specifying STORED physically writes them.
  • In SQL Server, omitting PERSISTED keeps the column virtual; adding PERSISTED writes it to disk like PostgreSQL's STORED.
  • In Databricks / Delta Lake, generated columns are routinely used as partition keys (e.g., deriving event_date DATE GENERATED ALWAYS AS (CAST(event_time AS DATE)) to partition large data lakes). In contrast, PostgreSQL explicitly bars generated columns from being partition keys for partitioned tables.

Scope: In PostgreSQL, the value must persist with STORED. On-the-fly computation at read time (VIRTUAL) is not supported. Assumption: The generating expression must be strictly IMMUTABLE. It must always return the exact same output for the same input values. It cannot call volatile functions (such as random() or clock_timestamp()) or stable functions (such as CURRENT_DATE or now()), cannot execute subqueries, and cannot reach into adjacent rows using window functions or aggregate functions. Also, a generated column cannot reference another generated column, so chaining one generated result into another is barred.

Picture the physical storage layout on disk: PostgreSQL writes 8 KB heap pages where each tuple contains a 23-byte HeapTupleHeader followed by attribute columns. Because STORED is specified, the engine allocates physical bytes for \(area\) in every tuple alongside \(w\) and \(h\). When you read rows, the engine performs zero math—it simply reads the pre-calculated bytes directly from disk or shared buffers.

Common pitfalls catch developers:

  1. Direct Value Assignment: Attempting to supply a value directly in an insert statement (INSERT INTO t (w, h, area) VALUES (2, 5, 10);) fails with an error: cannot insert into column "area" (detail: Column "area" is a generated column). Always omit generated columns from insert lists, or supply DEFAULT.
  2. Volatile Functions: Attempting to generate a timestamp column using now() or CURRENT_TIMESTAMP fails at creation time because the function is not immutable.
  3. Attempted Chaining: Writing col_c GENERATED ALWAYS AS (col_b * 2) STORED where col_b is itself generated fails because generated columns cannot read other generated columns.

Generated columns automate row-local calculations directly within the storage engine, replacing complex triggers with declarative, immutable expressions. Next, we verify this behavior with real numerical inputs.

46.11.2 Worked Example Area From Width and Height

To observe automatic evaluation, table t is created with width and height inputs:

CREATE TABLE t (
  w REAL,
  h REAL,
  area REAL GENERATED ALWAYS AS (w * h) STORED
);

Inspect the empty table:

SELECT * FROM t;

Column metadata confirms the area expression is active. We insert real dimensions without naming area:

INSERT INTO t (w, h) VALUES (1, 2);

Reading back the row:

SELECT * FROM t;

Output:

 w | h | area 
---+---+------
 1 | 2 |    2

Since \(1 \times 2 = \mathbf{2}\), the engine computed and stored 2.

Now insert a second row with equal dimensions:

INSERT INTO t (w, h) VALUES (2, 2);

Output:

 w | h | area 
---+---+------
 1 | 2 |    2
 2 | 2 |    4

Since \(2 \times 2 = \mathbf{4}\), the engine stored 4.

Next, test update synchronization by updating the width of the first row from 1 to 10:

UPDATE t SET w = 10 WHERE w = 1;

Reading back the table:

SELECT * FROM t;

Output:

 w  | h | area 
----+---+------
  2 | 2 |    4
 10 | 2 |   20

The touched row automatically refreshed from 2 to 20 (\(10 \times 2 = \mathbf{20}\)). No manual recalculation or trigger was invoked. Sense-check: Every stored area value matches the mathematical product of w and h on that exact row.

46.11.3 Worked Example Price Times Volume and Search Vectors

A market analytics pattern pairs trade ticks with total dollar value. With closing price, written \(close\), traded share volume, written \(volume\), and dollar trade volume, written \(price\_volume\):

\[price\_volume = close \times volume\]

Where:

  • \(close \in \mathbb{R}^+\) is the closing asset price per unit.
  • \(volume \in \mathbb{N}\) is the quantity of units exchanged.
  • \(price\_volume \in \mathbb{R}^+\) is the total transacted value.

Consider a securities table storing daily trading records:

CREATE TABLE daily_stock_trades (
  trade_date DATE,
  ticker VARCHAR(10),
  close NUMERIC(10, 2),
  volume BIGINT,
  price_volume NUMERIC(18, 2) GENERATED ALWAYS AS (close * volume) STORED
);

Inserting a row with \(close = 150.50\) and \(volume = 1000\):

INSERT INTO daily_stock_trades (trade_date, ticker, close, volume)
VALUES ('2026-09-22', 'GOOGL', 150.50, 1000);

The stored price_volume immediately evaluates to 150500.00 (\(150.50 \times 1000 = \mathbf{150500.00}\)). Analytics queries aggregate total transacted volume directly without executing runtime multiplication across millions of records. Sense-check: Dividing \(150500.00\) by \(1000\) recovers the original closing price of \(150.50\).

In text search applications, generated columns maintain pre-parsed lexeme dictionaries alongside raw prose. On a presidential speeches table named docs_president, an added column holds tsvector values built from the speech_text column:

ALTER TABLE docs_president
ADD COLUMN speech_text_tsv TSVECTOR
GENERATED ALWAYS AS (to_tsvector('english', speech_text)) STORED;

In words, the new column equals the English text-search vector of the speech text on the same row. In earlier database versions, keeping search vectors synchronized required application-level updates or complex triggers.

With this generated definition, whenever an analyst inserts a speech or edits speech text in speech_text, PostgreSQL automatically parses the English words, strips stop words, normalizes stems, and writes the resulting tsvector into speech_text_tsv. A Generalized Inverted Index (GIN) can then be created directly on speech_text_tsv for sub-millisecond full-text queries:

CREATE INDEX idx_docs_president_tsv ON docs_president USING GIN(speech_text_tsv);

Querying SELECT * FROM docs_president; shows the raw text sitting beside its lexeme vector, ready for fast full-text matching using the @@ match operator.

46.11.4 Copy and Dump Behavior

Backup and bulk-copy operations handle generated columns with specific conventions. Because generated values are fully deterministic and can be reconstructed from input columns, utilities prioritize compact transfer:

  • Standard COPY t TO STDOUT skips generated columns by default.
  • Standard pg_dump omits generated column data from INSERT or copy streams, restoring only the schema definition and source data to minimize dump size and avoid insertion errors.

When an export must include generated values (e.g., for external ingestion into business intelligence tools or spreadsheets), copy a query result instead of the bare table:

COPY (SELECT * FROM t) TO STDOUT;

This select-then-copy path forces the engine to serialize all projected attributes, including generated columns, into the resulting CSV or text stream.

46.11.5 Student Questions and Answers

Q: Can a generated column read the row above or chain from another generated column?

A: No to both. Expressions stay strictly on the current row and read plain base columns only. They cannot look across rows (no window functions, self-joins, or lag/lead offsets) and cannot name another generated column in their expression definition.

Q: Can generated columns be indexed or used as partition keys?

A: Yes to indexing; no to partitioning. Because PostgreSQL generated columns are STORED, you can create standard B-tree, Hash, or GIN indexes directly on them (e.g., CREATE INDEX ON t(area);). However, PostgreSQL explicitly prohibits using a generated column as a table partition key.

Real-world: Enterprise schemas rely on generated columns for row-local derived facts such as physical dimensions, price times volume in financial ledgers, and text-search vectors that must remain perfectly synchronized with source data without procedural trigger maintenance.

Exam note: Memorize the exact definition syntax GENERATED ALWAYS AS (...) STORED and the PostgreSQL version 12 baseline. Remember the core rules: expressions must be immutable and row-local, chaining generated columns is prohibited, standard B-tree indexing is permitted, but serving as a partition key is strictly forbidden. Finally, remember that standard COPY and pg_dump omit generated values, requiring the COPY (SELECT * FROM table) TO ... pattern when complete output is needed.

  • Understand that SELECT column_list INTO new_table FROM source WHERE condition; creates and populates a new relation in a single atomic step.
  • Memorize what carries over: column names, underlying data types, and matching row values. Memorize what does not carry over: primary keys, foreign keys, constraints, default values, and indexes.
  • Remember the subquery rule: when wrapping complex queries (joins, computed columns, ORDER BY NULLS LAST, LIMIT), PostgreSQL strictly requires an explicit table alias for the subquery in the FROM clause (e.g., FROM (...) AS subq;).
  • Contrast CREATE TABLE new_table AS SELECT * FROM source; (full data copy) with CREATE TABLE new_table AS SELECT * FROM source WITH NO DATA; (schema-only structural skeleton returning zero rows).
  • Data Ingestion and Egestion Mechanics (COPY vs \copy):
  • Distinguish execution environments: standard COPY runs server-side (requiring server filesystem access and superuser/elevated permissions), whereas \copy is a client-side psql meta-command running with client privileges.
  • Know the mandatory syntax parameters: DELIMITER ',' and CSV HEADER. Remember that omitting CSV HEADER on import erroneously ingests column header labels as a data row, and omitting it on export generates a headless CSV file.
  • When loading into tables with SERIAL PRIMARY KEY, provide an explicit column list in \copy omitting the auto-increment column so the sequence generator assigns unique keys automatically.
  • Duplicate Detection and Deletion Algorithms:
  • For single-column duplication checks, use aggregate grouping: SELECT col, COUNT(*) FROM t GROUP BY col HAVING COUNT(*) > 1;.
  • For comprehensive multi-column duplicate identification, employ window ranking: ROW_NUMBER() OVER (PARTITION BY col1, col2 ORDER BY id ASC) AS dup_row, filtering where dup_row > 1.
  • In self-join deletions (DELETE FROM colors a USING colors b WHERE a.color = b.color AND a.color_id < b.color_id;), understand the direction of inequality: a.color_id < b.color_id removes the earlier/lower identifier and preserves the later/larger identifier.
  • Physical Storage, MVCC Bloat, and Update Amplification:
  • Understand PostgreSQL's Multi-Version Concurrency Control (MVCC) write model: UPDATE does not overwrite data in place; it writes a new live row version and flags the previous version as a dead tuple. DELETE simply flags tuples as dead.
  • In exam questions addressing table size changes, link a full-table UPDATE to an immediate near-doubling of physical disk storage (e.g., 5.6 MB expanding to ~11 MB), because both dead and live tuples coexist in heap pages.
  • Measure table footprint using pg_total_relation_size('table_name') for raw bytes and format human-readable outputs using pg_size_pretty(...).
  • Autovacuum Daemon and Hand-Run Maintenance:
  • Remember that the autovacuum daemon awakens about once per minute, tracks modification thresholds in pg_stat_all_tables, cleans dead tuples, and updates query planner statistics via paired auto-analyze.
  • Critical distinction: standard VACUUM and autovacuum do NOT return disk space to the operating system. They reclaim dead space internally within the Free Space Map (FSM) so future inserts and updates can reuse those slots without growing the file.
  • Memorize the constraints and costs of VACUUM FULL:
  • VACUUM FULL physically rewrites the entire relation into new disk files, returning unused blocks to the host OS.
  • It requires an aggressive ACCESS EXCLUSIVE table lock that blocks all reads and writes for the duration of the rewrite.
  • It requires explicit table ownership or superuser permissions.
  • VACUUM cannot run inside a multi-statement transaction block (BEGIN ... COMMIT); attempting to do so triggers an immediate execution error.
  • Generated Columns Architecture (PostgreSQL 12+):
  • Memorize the definition signature: col_name data_type GENERATED ALWAYS AS (expression) STORED.
  • Note the version baseline: introduced in PostgreSQL 12.
  • Enforce the four strict operational constraints:
  1. Expressions must be strictly IMMUTABLE (deterministic; functions like now() or random() are forbidden).
  2. Expressions are strictly row-local (no window functions, aggregates, or cross-row references).
  3. Chaining generated columns (referencing another generated column) is barred.
  4. Prohibited from serving as a partition key for partitioned tables.
  • Understand export behavior: standard COPY t TO STDOUT and pg_dump omit generated column values to optimize transfer. To force export of generated values, execute a query-based copy: COPY (SELECT * FROM t) TO STDOUT;.

Key Industry Applications

Table creation patterns, high-throughput bulk ingestion, deduplication pipelines, MVCC storage management, and declarative generated columns serve as the structural backbone of enterprise data platforms, Site Reliability Engineering (SRE), and analytical systems:

  • Materialized Analytic Snapshots & Isolated Reporting Marts:
  • In enterprise Business Intelligence (BI) environments (e.g., Tableau, Power BI, Looker), generating reporting tables via SELECT INTO or CREATE TABLE AS SELECT (CTAS) freezes complex multi-table joins, revenue computations, and filtered subsets into dedicated tables.
  • This architecture isolates resource-intensive reporting queries from primary Online Transaction Processing (OLTP) databases, providing analysts with consistent, immutable snapshot data while eliminating repeated join overhead across millions of rows.
  • Automated Reference Data Provisioning & Cloud ETL Pipelines:
  • In microservice provisioning and automated cloud deployments (using Docker, Kubernetes, Terraform, or Flyway), seeding standard lookup tables (such as ISO country codes, currency mappings, and geographic zones) is performed via client-side \copy.
  • Data engineering workflows routinely bridge relational databases and cloud object stores (Amazon S3, Google Cloud Storage, Azure Blob Storage) by running COPY ... TO '...' CSV HEADER to dump clean tabular extracts that feed downstream data lake engines such as Snowflake, Databricks Delta Lake, or BigQuery.
  • Master Data Management (MDM) & Automated Deduplication Engines:
  • Customer 360, e-commerce catalog syncs, and financial reconciliation engines frequently ingest redundant records from third-party vendor APIs or distributed event streams.
  • Data quality frameworks use partitioned ranking (ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)) and targeted self-join deletions (DELETE ... USING) to eliminate duplicate customer identities, order items, or inventory entries, preserving the single most recent or authoritative "golden record" prior to downstream analytics.
  • SRE Capacity Planning & MVCC Bloat Telemetry:
  • Database Reliability Engineers (DBREs) continuously monitor table footprints using pg_total_relation_size() and pg_stat_all_tables.
  • In update-heavy transactional systems (such as ride-sharing driver location tracking, order fulfillment state machines, or auction bidding platforms), high-frequency UPDATE operations produce massive dead-tuple volume, causing relations to double in physical footprint. Engineers tune autovacuum thresholds (autovacuum_vacuum_scale_factor, autovacuum_vacuum_cost_limit) to ensure continuous in-place space reuse and prevent catastrophic disk exhaustion.
  • Production Maintenance Windows & Physical Storage Reclamation:
  • Following massive historical data purges (such as multi-million-row GDPR compliance deletions, quarterly audit log expiries, or financial year-end partition drops), standard vacuuming marks pages reusable but cannot shrink the OS file.
  • Enterprise infrastructure teams coordinate off-peak maintenance windows, redirecting application read traffic to warm standby replicas while executing VACUUM FULL on primary tables. This operation physically rewrites relations, eliminates filesystem fragmentation, reclaims hundreds of gigabytes of cloud block storage, and rebuilds bloated indexes.
  • Declarative Financial Analytics & Automated Full-Text Search:
  • Quantitative finance ledgers and algorithmic trading databases use GENERATED ALWAYS AS (close * volume) STORED to maintain exact transaction value metrics directly inside heap tuples, avoiding application-side calculation drift and trigger latency.
  • Document management systems, enterprise knowledge bases, and legal archives (such as presidential speech corpuses or customer support logs) use GENERATED ALWAYS AS (to_tsvector('english', speech_text)) STORED paired with Generalized Inverted Indexes (GIN). This declarative approach guarantees that text-search vectors remain perfectly synchronized with raw text inputs upon every write without custom trigger maintenance.

Below is the distilled, exam-ready core. Every entry comes from the full explanation above. Use this section for rapid review; return to the main notes when a point needs more context.

Creating New Tables With SELECT INTO and WHERE

Must-know: SELECT INTO creates and fills a new table in one step; it copies names, types, and matching rows but no constraints or indexes

⚠️ Top pitfall: Re-running SELECT INTO fails because the target table now exists; inside PL/pgSQL, INTO means variable assignment, not table creation

Self-check: What happens to the source table when SELECT INTO copies some of its rows?

Connects to: 46.2, 46.3

SELECT INTO With JOIN, Computed Columns, ORDER BY, and Subqueries

Must-know: Any shaped query (joins, arithmetic, ORDER BY NULLS LAST, LIMIT) can be frozen into a table via SELECT INTO FROM (subquery) AS alias

\[total\_revenue = revenues\_domestic + revenues\_international\]

⚠️ Top pitfall: Forgetting the subquery alias, or using ORDER BY positions that shift when columns are added

Self-check: Why must the subquery in FROM carry an alias?

Connects to: 46.1, 46.3

Duplicating a Table With and Without Data

Must-know: CREATE TABLE AS copies structure plus rows; WITH NO DATA copies structure only; neither copies constraints or indexes

⚠️ Top pitfall: Assuming constraints, keys, and indexes carry over; they do not

Self-check: How do you make an empty structural copy of a table?

Connects to: 46.1, 46.2

Importing Data From CSV Files

Must-know: CSV import is create-then-\copy with explicit column list, DELIMITER, and CSV HEADER; \copy is client-side, COPY is server-side

⚠️ Top pitfall: Forgetting CSV HEADER loads header names as a fake data row; wrong delimiter stuffs whole lines into one column

Self-check: Why does the \copy column list leave out the SERIAL key?

Connects to: 46.5

Exporting Data From a Table to CSV

Must-know: COPY/\copy TO with DELIMITER and CSV HEADER mirrors import; counts in and out must match on a full round trip

⚠️ Top pitfall: Using server-side COPY to a client-only path fails; omitting HEADER ships a headerless file

Self-check: When should you use \copy TO instead of COPY TO?

Connects to: 46.4

Finding and Deleting Duplicate Rows

Must-know: HAVING COUNT(*) > 1 proves single-column repeats; ROW_NUMBER partitioned listing proves full-row repeats; DELETE USING with < keeps the later copy

\[count(\ast) > 1\]

⚠️ Top pitfall: Deleting before proving repeats; forgetting that NULLs group together

Self-check: What does dup_row > 1 select in the window-function lister?

Connects to: 46.7

How Inserts, Updates, and Deletes Change Table Size

Must-know: UPDATE writes a new row image and keeps the old as a dead row; DELETE hides the row but leaves its image until vacuum

⚠️ Top pitfall: Sizing disk for live rows only while updates quietly double the footprint

Self-check: After updating every row once, how many stored images exist per visible row?

Connects to: 46.6, 46.8, 46.9

Tracking Table Size Through Insert and Update

Must-know: Inserts grow size proportionally; one full-table UPDATE nearly doubles bytes by adding a dead image per row

\[s\_pretty = pg\_size\_pretty(pg\_total\_relation\_size('table\_vacuum'))\]

⚠️ Top pitfall: Reading equal row counts as equal bytes when dead rows differ

Self-check: Why did 160000 updated rows nearly double the table instead of adding a little?

Connects to: 46.7, 46.9

The Autovacuum Background Process

Must-know: Autovacuum runs about every minute, marks dead space reusable inside, pairs with auto-analyze, and never returns bytes to the OS

⚠️ Top pitfall: Expecting autovacuum to shrink the file; it only reuses space inside

Self-check: After two autovacuum passes the table still reads 11 MB. Why?

Connects to: 46.8, 46.10

Reclaiming Space With Hand-Run VACUUM

Must-know: Plain VACUUM reuses space inside with light locking; VACUUM FULL rewrites the table, returns bytes, needs exclusive lock, permission, and no enclosing transaction

⚠️ Top pitfall: Running database-wide VACUUM FULL on a live system or wrapping VACUUM in a transaction block

Self-check: Why did size stay 11 MB after plain VACUUM but drop to 5664 kB after VACUUM FULL?

Connects to: 46.9, 46.8

Auto Generated Columns

Must-know: GENERATED ALWAYS AS (expr) STORED requires PostgreSQL 12+, must be row-local and immutable, cannot chain generated columns, allows B-tree indexing but prohibits partition keys, and requires SELECT-wrapping for COPY/dump export.

\[area = w \times h\]

⚠️ Top pitfall: Attempting direct insertion into generated columns, using volatile functions like now(), or expecting COPY/pg_dump to output generated values without a query wrapper.

Self-check: Why does standard COPY t TO STDOUT omit generated columns by default, and how do you include them?

Connects to: 46.1, 46.2, 46.10

Exam Guidance Summary

Must-know: Key examinable facts: SELECT INTO copies data without constraints, subqueries in FROM require aliases, UPDATE doubles table footprint under MVCC, autovacuum reuses FSM space without OS return, VACUUM FULL takes exclusive locks and cannot run in transactions, and GENERATED ALWAYS AS STORED requires immutable row-local logic.

\[total\_revenue = revenues\_domestic + revenues\_international\]

⚠️ Top pitfall: Running VACUUM FULL during live production traffic, executing VACUUM inside a transaction, or attempting to chain generated columns.

Self-check: Why does a table updated across all rows nearly double in physical storage size?
