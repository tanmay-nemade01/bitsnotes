# Using Regular Expressions for Text Patterns

28.1 Turning Text into Structured Data with String Functions

28.1.1 Unstructured Text as a Source of Rows and Columns

A speech, a press release, a report, or a product description looks free-form at first glance. It has no rows and columns. Yet it holds quantities, names, dates, codes, and categories that can be pulled out and counted. The core move in this module is simple: take a raw string, shape it with built-in functions, then match patterns inside it with regular expressions.

A free-form paragraph is really a packed table waiting to be unpacked. Ask of any text: what here is a date, what is a name, what is a code, and what separator tells them apart? Once you can name those, a string function plus a pattern can turn each one into its own column or row.

PostgreSQL ships with more than 50 built-in string functions. Some belong to the SQL standard. Some are specific to PostgreSQL. The lesson starts with a handful of them because pattern matching works best after the text is cleaned. Case differences, extra spaces, and length surprises all break a match. Fix them first.

That ordering is deliberate and worth making explicit. A pattern such as December \d{2}, \d{4} fails on december 10, 2020 for case alone, fails on ' December 10, 2020 ' for padding alone, and fails on a truncated column for length alone. Cleaning first means each later pattern sees a stable target. Think of it as preparing a surface before stencilling: the stencil is only as good as the surface beneath it.

Crime reports from a sheriff's department near Washington, DC show why this matters. Each pasted block holds a date, a time, a street address, a city, a crime type, a description, and a case code, but with inconsistent spacing, mixed abbreviations such as Sq., Plz., Dr., Ter., and Rd., and occasional double dates such as 4/16/17-4/17/17. No import tool splits that cleanly on its own. Standardizing case, trimming spaces, and checking length turns that mess into input a pattern can trust.

Real-world work follows the same rhythm everywhere: log files, CSV imports, stock symbols, employee tables, and customer feeds all arrive messy. Analysts who mine speeches, reports, and press releases first normalize text into rows and columns, then count, group, and filter. After the database and queries are set up, the same queries run again each day on fresh downloads, so the one-time cleaning effort pays for itself many times over.

Across databases the idea is identical even though the function names shift slightly. PostgreSQL, Snowflake, Databricks Spark SQL, and MySQL all provide UPPER and LOWER. PostgreSQL, Snowflake, and Databricks provide INITCAP; MySQL does not, so MySQL users build it with CONCAT(UPPER(LEFT(s,1)), LOWER(SUBSTRING(s,2))) or handle it in application code. For length, PostgreSQL prefers CHAR_LENGTH, MySQL distinguishes CHAR_LENGTH in characters from LENGTH in bytes, Snowflake treats LENGTH and LEN alike, and Databricks Spark SQL uses length. Keep one version in your answer and note the alias only where it saves confusion.

Exam note: Be ready to explain in one sentence why cleaning comes before matching: a correct pattern still misses when case, padding, or truncation differs. That justification appears in hands-on stems alongside the function rewrites.

28.1.2 Case Formatting with UPPER, LOWER, and INITCAP

An UPPER — a function that maps every letter to upper case — is written UPPER(text). It takes one string and returns the same string with all letters capitalized. Numbers and symbols pass through unchanged, so UPPER('Neal7') returns NEAL7.

UPPER(text) returns every alphabetical character in upper case. LOWER(text) returns every alphabetical character in lower case. INITCAP(text) returns the first letter of each word in upper case and the rest in lower case. All three take one string and return one string.

SELECT UPPER('world');
-- WORLD

SELECT UPPER('world peace');
-- WORLD PEACE

Every character changes, not just the first letter. Spaces stay. This matters when codes must match. A stock symbol stored as aapl will not join cleanly against AAPL until one side is normalized. Normalizing on the way in is cheaper than debugging a join that silently drops rows.

A LOWER — the mirror image that maps every letter to lower case — is written LOWER(text).

SELECT LOWER('WORLD PEACE');
-- world peace

Use it to normalize free-form input before comparison or grouping. If half the rows say World and half say WORLD, grouping by the raw column splits one group into two. Grouping by LOWER(column) brings them together. The same trick applies in filters: WHERE LOWER(city) = 'sterling' catches Sterling, STERLING, and sterling alike.

An INITCAP — a function that uppercases the first letter of each word and lowercases the rest — is written INITCAP(text). The name comes from "initialize capital letter".

SELECT INITCAP('at the end of the month');
-- At The End Of The Month

Each word starts with a capital letter. This is handy for display names, city names, and titles pulled from lower-case feeds.

Run the three side by side on one value to feel the difference:

SELECT UPPER('Practical SQL');   -- PRACTICAL SQL
SELECT LOWER('Practical SQL');   -- practical sql
SELECT INITCAP('Practical SQL'); -- Practical Sql

The last line surprises many learners: INITCAP('Practical SQL') returns Practical Sql, not Practical SQL, because the function does not recognize acronyms. It lowercases everything except word initials. That behaviour is straight from the reference text and is a favourite exam trap.

Scope: UPPER and LOWER are ANSI SQL standard and behave the same in PostgreSQL, MySQL, Snowflake, and Databricks. INITCAP is PostgreSQL-specific in the standard sense but Snowflake and Databricks also ship it; MySQL has no INITCAP at all. Capitalization also depends on locale and language, so results on non-English text can vary. Never assume INITCAP preserves acronyms, hyphenated names, or mixed-case brands.

A compact visual helps. Picture three name badges printed from the same typed slip maria lopez: the UPPER badge reads MARIA LOPEZ, the LOWER badge reads maria lopez, and the INITCAP badge reads Maria Lopez. Same slip, three presentations. The takeaway is one sentence: pick the presentation that matches the next step, joins and groups want uniform case, display wants initial capitals.

Two beginner traps recur. First, expecting only the first letter to change under UPPER; in fact every letter changes. Second, expecting INITCAP to be smart about SQL, McDonald, or O'Brien; it is not, so proofread display output before shipping it.

Exam note: Expect hands-on rewrites where you must pick the right case function and predict the exact output including spaces. Write the answer character by character, spaces included, and double-check acronyms under INITCAP.

28.1.3 Length Info with CHAR_LENGTH

A character length — how many characters a string holds including spaces — is read with CHAR_LENGTH(text). An older spelling CHARACTER_LENGTH(text) does the same thing.

CHAR_LENGTH(text) counts characters, including spaces. CHARACTER_LENGTH(text) is the same function under its longer SQL-standard name. A space counts as one, leading and trailing padding counts too, and an empty string has length 0.

SELECT CHAR_LENGTH('world');
-- 5

SELECT CHAR_LENGTH('world peace');
-- 11

Count it out: w(1) o(2) r(3) l(4) d(5) gives 5. For world peace, the space counts as one, so the total reaches 11. That space rule trips up many first attempts.

Audit a column before sizing a new one:

SELECT MAX(CHAR_LENGTH(first_name)) FROM employee;
-- say 12, so size the new column at 12 or above plus margin

SELECT first_name, CHAR_LENGTH(first_name) AS n
FROM employee ORDER BY n DESC LIMIT 5;
-- surfaces the longest names first

The second query is the diagnostic version of the first: it shows which values drive the maximum, so a single stray padded value does not silently dictate the design.

The lesson prefers CHAR_LENGTH over LENGTH because LENGTH can return different numbers case by case in some setups. The reference makes this precise: with multibyte encodings covering Chinese, Japanese, or Korean characters, length() can differ from char_length(), and PostgreSQL also has a length variant that measures binary strings. When you want a stable character count, reach for CHAR_LENGTH.

Cross-database note in one place: MySQL's CHAR_LENGTH counts characters while LENGTH counts bytes, so LENGTH('é') can exceed CHAR_LENGTH('é') under utf8; Snowflake's LENGTH and LEN both count characters; Databricks Spark SQL's length counts characters with octet_length for bytes. Same concept, different name for the byte count. For this lecture, CHAR_LENGTH is the portable answer for characters.

Scope: Length counts what is stored, not what you meant to store. Padded values, invisible tabs, and multibyte characters all inflate the count. If the count looks one too high, suspect padding before suspecting the function.

Recap: CHAR_LENGTH answers "how many characters, spaces included" and MAX(CHAR_LENGTH(col)) answers "how wide must the new column be". That bridges directly into trimming next: once you know values are too long, you clean the edges and measure again.

28.1.4 Cleaning Edges with TRIM and Nesting Functions

A TRIM — a function that strips leading and trailing spaces — is written TRIM(text). With no extra arguments it removes spaces at both ends by default.

TRIM(string) removes leading and trailing spaces. TRIM(chars FROM string), TRIM(LEADING ... ), TRIM(TRAILING ... ), plus LTRIM and RTRIM, narrow the removal to chosen characters or one side. Functions nest inside out: the inner call runs first and its result feeds the outer call.

SELECT TRIM('  Adama  ');
-- Adama

The inner text stays. Only the outer padding goes. The lesson shows a variant with the name Adam where leading and trailing blanks vanish after the call.

The fuller reference form repays one extra look because exam stems sometimes use it:

SELECT TRIM('s' FROM 'socks');            -- ock
SELECT TRIM(TRAILING 's' FROM 'socks');   -- sock
SELECT CHAR_LENGTH(TRIM(' Pat '));        -- 3

Reading left to right: name the characters, name the side, name the string. Omit the characters and spaces are assumed; omit the side and both sides are assumed.

Functions nest. The inner call runs first, the outer call runs on its result. To get the true length of a padded value, trim first, then measure:

SELECT CHAR_LENGTH(TRIM(' Adam'));
-- 5

SELECT CHAR_LENGTH(' Adam');
-- 6

Without TRIM, the leading space counts and the answer is 6. With TRIM, the answer is 5. That one-character gap breaks joins, filters, and length checks in real loads. The same nesting pattern generalizes: SELECT CHAR_LENGTH(TRIM(' Pat ')); returns 3, the letters in Pat, because trimming runs before counting.

Think of it like washing fruit before weighing it. The weight you care about is the fruit, not the packaging. Trim the packaging, then measure. The analogy breaks at one point worth stating: washing never removes part of the fruit, but TRIM('s' FROM 'socks') removes real letters when told to, so always check which characters were named.

Real-world cleaning leans on this daily: CSV fields often carry stray spaces from manual entry. Trimming on import stops ' Adam' and 'Adam' from becoming two different people. Column-width audits pair the two steps as well: measure with CHAR_LENGTH, trim, measure again, and the difference is the padding cost.

TRIM touches only the edges. Inner double spaces such as 'Ada m' survive untouched; collapsing those needs REPLACE or a regex. Also, TRIM without arguments does not strip tabs or newlines in every database, so bulk-load patterns sometimes name \t and \n explicitly or follow with a regex pass.

Recap: Clean edges first with TRIM, then measure with CHAR_LENGTH, then match with a pattern. That wash-weigh-stencil order carries into every later section, where a single stray space decides match versus miss.

28.1.5 Student Questions and Answers

Q: Why bother with such simple case and trim helpers when the real goal is pattern matching?

A: Because raw text rarely matches a neat pattern on the first try. A trailing space, a mixed-case code, or a hidden length difference makes a correct pattern miss. These small helpers shape the text so the later regex sees a stable target. Several students raised versions of this question, and the lesson's answer is consistent: cleaning is what makes the later one-line patterns possible at all.

28.2 Regular Expression Notation Basics

28.2.1 What a Regular Expression Describes

A regular expression — also shortened to regex — is a compact notation language that describes a text pattern. If a code looks like four digits, then a hyphen, then two more digits, you can write that shape once and reuse it to filter rows, pull fields out, or tidy values.

Why a pattern instead of a literal? A literal such as '2020' finds one value. A pattern such as \d{4} finds any four-digit year. Patterns state the form data should have, so one expression covers every value with that shape.

You can use that notation in a WHERE clause to keep only matching rows, or in a dedicated function to pull and reshape the matched slice. Patterns matter because they state the form data should have, not just one literal value.

Think of it like a stencil. A literal match finds one exact word. A regex stencil finds any word with the same shape. The analogy breaks at one useful point: a physical stencil has a fixed size, while a regex stencil stretches with quantifiers such as + and {1,2}, so one stencil covers 7 p.m. and 10 p.m. alike.

Real-world use is portable far beyond SQL: the same notation works in Python, PHP, and many text editors. Time spent here pays off across tools, not just in SQL. Regex testers such as regexr.com let you try each symbol live before running it inside a query.

Recap: A regex describes a reusable shape, used either to filter rows in WHERE or to extract and reshape text in functions. That filter-versus-extract split organizes the rest of the lecture.

28.2.2 Single-Character Building Blocks

A dot — written . — is a wildcard that finds any single character except a newline. It can stand for a letter, a digit, or a symbol. A to Z or 0 to 9 are typical occupants of that slot.

One symbol matches exactly one character unless a quantifier extends it. . matches any character except newline. [FGz] matches one of the listed characters. [a-z] matches one character in the range. [^a-z] matches one character outside the range. \w matches [A-Za-z0-9_], \d matches [0-9], \s matches a space, \t a tab, \n a newline, and \r a carriage return.

Square brackets define a set. [FGz] means one character that is capital F, capital G, or lower-case z. Only those three pass.

A hyphen inside brackets defines a range or series:

  • [a-z] means any one lower-case letter from a through z.
  • [A-Z] means any one upper-case letter from A through Z.

A caret as the first symbol inside brackets negates the set. [^a-z] means any character that is not a lower-case a through z. The caret flips the sense from "allow these" to "block these".

Shorthand classes save writing:

  • \w means any word character or underscore. It matches the same set as [A-Za-z0-9_]. That is upper-case A to Z, lower-case a to z, digits 0 to 9, plus _.
  • \d means any digit, the same as [0-9].
  • \t means a tab.
  • \s means a space. The lesson states it as "space" in the table.
  • \n means a newline character.
  • \r means a carriage return character.

Newline and carriage-return forms show up a lot when parsing files or bulk-loading CSV data into PostgreSQL. A file break that looks empty still holds \n or \r, and a pattern must name it to split correctly. Crime-report parsing leans on this directly: the hour always starts on a new line, so patterns use \n(\d{4}) to step over the line break before capturing the digits.

Read each as "one character, with a rule about which one":

-- [FGz] on 'F' passes, on 'H' fails
-- [a-z] on 'm' passes, on 'M' fails
-- [^a-z] on 'M' passes, on 'm' fails
-- \w on 'A', '7', '_' passes; on ' ' or '-' fails
-- \d on '8' passes, on 'A' fails

The space and dash failures under \w explain why \w+ stops at the first space in the movie sentence later.

Cross-database note: \d, \w, and \s work in PostgreSQL POSIX regex, and the bracket forms [0-9], [A-Za-z0-9_] work everywhere including MySQL, Snowflake, and Databricks. POSIX classes such as [[:digit:]] and [[:alpha:]] are the most portable spelling across PostgreSQL, MySQL, and Snowflake. If a pattern must run on several engines, prefer the bracket or POSIX-class spelling.

Two traps dominate. First, . does not cross a newline, so a dot-star pattern stops at a line break unless newlines are handled. Second, \s in full regex means any whitespace, but this lesson's table narrows it to "space" — on the exam, follow the lesson's table and treat it as the space character.

28.2.3 Anchors for Start and End

A caret outside brackets anchors to the start. ^A means capital A at the very start of the string, not just anywhere inside.

^ at the front of a pattern pins the match to the start of the string. $ at the end pins it to the end. ^\w+ reads "word characters at the start" and \w+.$ reads "word characters plus one trailing character at the end".

A dollar sign anchors to the end. In escaped markdown form it appears as \$. A\$ means capital A at the very end of the string.

Write them in code as:

-- ^A : A at start
-- A\$ : A at end

Getting these two mixed up is a classic early slip. Caret inside [^...] negates a set. Caret outside at the front anchors to the start. Same mark, different job based on place.

Picture a labelled shelf: ^ is the left bookend and $ is the right bookend. Without bookends a book can sit anywhere; with both, only a full-shelf fit passes. The takeaway: anchors decide whether a slice may match or the whole string must.

Do not confuse the SQL-escape with the pattern. In markdown and some clients $ is written \$ to survive formatting, but inside the database pattern it is plain $. Writing a literal backslash before $ in the query changes the meaning.

28.2.4 Repetition with Question Mark, Star, Plus, and Braces

Repetition always applies to the item right before it:

Quantifiers extend the item immediately to their left. ? means 0 or 1 time. * means 0 or more times. + means 1 or more times. {m} means exactly m times. {m,n} means between m and n times.

  • ? means get the preceding match 0 or 1 time. The item may be absent or appear once, no more.
  • * means get the preceding match 0 or more times. It can be absent or repeat without a fixed cap.
  • + means get the preceding match 1 or more times. Unlike ? and *, zero is not allowed. At least one must be there. Think of the plus shape as "one and then some".
  • {m} means get the preceding match exactly m times. {4} means exactly four in a row.
  • {m,n} means get the preceding match between m and n times. {10,20} means at least 10 and at most 20.

So . plus * as .* means any run of characters. . plus + as .+ means a non-empty run. \d{4} means exactly four digits, the shape of a year like 2020.

Map each to a concrete question:

-- \d{4}      : is there a four-digit year here? (2020 passes, 20 fails)
-- \d{1,2}    : is there a one- or two-digit hour? (7 and 10 pass, 100 fails)
-- a+         : one or more a's (finds 'aa' inside 'aardvark')
-- May \d, \d{4} : month, space, digit, comma, space, year (May 2, 2024)

The last line shows quantifiers combining with literals: each space and comma is still load-bearing around the counted digits.

Scope: A quantifier binds only to the single item on its left. ab+ repeats b, not ab; (ab)+ repeats the group. Forgetting the parentheses is the most common reason a "repeat the word" pattern repeats only its last letter.

28.2.5 Choice and Grouping with Pipe and Parentheses

A pipe denotes alternation, an either-or choice. A|B means find A or find B.

a|b matches either side. (...) groups an expression and reports the matched slice as a capture group. (?:...) groups for precedence without reporting a separate capture, so the full match is returned instead of the inner piece.

Parentheses create a capture group or set precedence. (A|B) groups the choice so a later quantifier or surrounding text applies to the whole group.

Adding ?: at the front of a group makes it non-capturing. (?:A|B) still groups for matching order, but it tells the engine not to report that slice as a separate captured piece. That detail matters in SUBSTRING and REGEXP_MATCHES where groups become output columns.

The time pattern from the reference shows why ?: exists:

-- \d{1,2} (a|p).m.     groups but reports only the inner letter
-- \d{1,2} (?:a|p).m.   groups and returns the full '7 p.m.'

Same match position, different reported slice. Use the plain group when the inner piece is the goal, such as extracting an hour with \/\d{2}\n(\d{4}); use (?:...) when the whole stencil is the goal, such as a street suffix list (?:Sq.|Plz.|Dr.|Ter.|Rd.).

Crime-report patterns reuse this shape at scale: (?:C0|SO)[0-9]+ matches either case-number prefix without splitting the report, while (\d{1,2}\/\d{1,2}\/\d{2}) captures just the date after a hyphen. One groups silently, the other captures loudly.

Exam note: Memorize this table cold. Later tasks assume you can read ., \w, \d, ^, $, ?, *, +, {m}, {m,n}, |, (...), and (?:...) without pausing. Recap: single-character symbols name what may sit in one slot, anchors name where the match must sit, quantifiers name how many times, and groups name what gets reported.

28.2.6 Student Questions and Answers

Q: Why do single-character symbols feel hard at first?

A: Because one mark carries a lot of sense and its sense shifts with place. A caret negates inside brackets but anchors outside. A dollar anchors to the end. Parentheses group, but (?:...) groups without reporting. Practice on short strings makes each mark stick. The lesson urges repeated hands-on runs rather than rote recall alone.

28.3 SIMILAR TO Operator

28.3.1 Where SIMILAR TO Sits Among Three Pattern Paths

PostgreSQL offers three ways to match text. One is POSIX regular expressions with tilde operators. The second is LIKE. The third is the SIMILAR TO operator, added in 1999.

Which matcher should you reach for? LIKE answers simple contains-questions with % and _. POSIX tilde answers tight shape-questions with full regex. SIMILAR TO answers SQL-standard shape-questions that must cover the whole value.

SIMILAR TO returns true or false based on whether its pattern matches the given string. It looks like LIKE, but it reads the pattern with the SQL standard sense of regex. That standard sense is a cross between LIKE notation and common regex notation.

expression SIMILAR TO pattern returns true only when the pattern matches the entire string, first character to last. _ matches any single character, like . in regex. % matches any string including the empty string, like .* in regex.

The key limit: SIMILAR TO succeeds only if the pattern matches the entire string. Common regex can match a slice inside a longer string. SIMILAR TO cannot. The whole value must fit the pattern from first character to last character.

Like LIKE, SIMILAR TO uses underscore and percent as wildcards:

  • _ stands for any single character. It lines up with . in common regex.
  • % stands for any string, including an empty one. It lines up with .* in common regex.

A compact comparison helps. LIKE 's%' finds values starting with s; SIMILAR TO 's%' does the same but can also add regex branches such as %(s|e)% in the middle. POSIX 's' with ~ finds s anywhere, while SIMILAR TO 's' finds only the one-letter value s. The takeaway: when the stem says "entire string must match", think SIMILAR TO; when it says "substring may match", think tilde.

Cross-database note: PostgreSQL and Snowflake support SIMILAR TO. MySQL has no SIMILAR TO; use REGEXP or RLIKE instead. Databricks Spark SQL has no SIMILAR TO; use LIKE, RLIKE, or REGEXP. If a pattern must port, write it in POSIX or LIKE form, not SIMILAR TO form.

Scope: Because the whole-string rule forces broad % wrappers on large tables, this form can be an expensive query when no helpful index exists. Use it with care on big columns, and prefer a leading literal plus an index where possible.

28.3.2 Worked Examples

Each example uses SELECT <value> SIMILAR TO <pattern> and returns true or false.

Exact match, same case:

SELECT 'same' SIMILAR TO 'same';
-- true

The pattern covers the whole string, so it passes. No wildcard is needed when value and pattern are identical.

Same letters, different case on the first letter:

SELECT 'same' SIMILAR TO 'Same';
-- false

Only the first letter differs, s versus S. Matching is case sensitive here. Since the entire string must match, one letter is enough to fail. This shows the whole-string rule in action. A partial view would say "the last three letters match", but SIMILAR TO still says false.

Single-letter pattern against a longer value:

SELECT 'same' SIMILAR TO 's';
-- false

s alone does not cover a, m, e, so the whole-string test fails. This is the sharpest contrast with tilde: 'same' ~ 's' would be true because a slice suffices there.

Leading letter plus open tail:

SELECT 'same' SIMILAR TO 's%';
-- true

s fixes the first character. % accepts any tail, here ame. The full string is now covered, so the result flips to true. Sense-check: cover the head literally, let % absorb the rest.

Reversed wildcard:

SELECT 'same' SIMILAR TO '%s';
-- false

%s means some head followed by s at the end. But same ends with e, not s. So it fails. By contrast, a pattern that leaves the tail open passes:

SELECT 'same' SIMILAR TO 'same%';
-- true

same covers the head and % accepts an empty tail. An empty tail is allowed. That empty-tail rule surprises beginners, so state it plainly: % may match nothing at all.

Two-letter head plus open tail:

SELECT 'same' SIMILAR TO 'sa%';
-- true

sa fixes the first two characters. % takes me.

Alternation with pipe inside brackets or parens:

SELECT 'same' SIMILAR TO '%(s|e)%';
-- true

Read it as: any head, then either s or e, then any tail. Since same holds both letters, one branch hits and the whole-string cover holds because of the leading and trailing %.

A trap follows. A pattern like '(m|e)%' looks for m or e at the start, but same starts with s. The head fails, so the result is false even though m and e appear later. Place of the group matters as much as its letters. If the group sits at the front without a leading %, the match must start there.

Three pitfalls decide most marks here. First, forgetting the whole-string rule and answering as if a slice suffices. Second, ignoring case: Same versus same fails. Third, confusing _ with %: _ covers exactly one character, % covers any run including empty. When stuck, cover the string left to right and ask what each token consumes.

Exam note: Expect true-or-false drills on SIMILAR TO where the whole-string rule plus case sensitivity decides the answer. Watch _ versus % and watch where % sits.

28.3.3 Student Questions and Answers

Q: Why did %s fail while s% passed for the same value?

A: Because place matters under the whole-string rule. s% pins s to the front, which fits same. %s pins s to the back, but same ends with e. The wildcard % cannot move a pinned letter to a new spot. It only fills the open side.

28.4 POSIX Regular Expressions with Tilde Operators

28.4.1 Three Matching Styles and Cost Hints

A POSIX regular expression — a special text form that states a search shape — is the most flexible of the three matching styles in PostgreSQL. The three are POSIX regex, SIMILAR TO, and LIKE.

When is POSIX the right pick? When the question names a shape such as "contains lade or lare" or "contains ash but not Wash". LIKE cannot express either-or branches; POSIX expresses them in one predicate.

LIKE and SIMILAR TO lean heavily on an index on the searched column. Without that index they can be quite heavy to run. POSIX matching is often liked for its power and is relatively faster than the other two in many runs, but the lesson stresses that speed depends case by case. Test on your own data and shape.

A real county-name filter from the reference shows the power gap:

SELECT county_name FROM us_counties_pop_est_2019
WHERE county_name ~* '(lade|lare)' ORDER BY county_name;
-- Bladen, Clare, Clarendon, Glades, Langlade, Philadelphia, Talladega, Tulare

SELECT county_name FROM us_counties_pop_est_2019
WHERE county_name ~* 'ash' AND county_name !~ 'Wash' ORDER BY county_name;
-- Ashe, Ashland, Ashley, Ashtabula, Nash, Wabash, Wabasha (no Wash...)

Neither query is expressible in one LIKE without a long OR chain. That is the practical reason teams start with POSIX tilde forms for tight patterns, keep LIKE for simple % hunts, and reserve SIMILAR TO for SQL-standard shapes. Index the searched column when the table is large.

Scope: Tilde operators are PostgreSQL-specific. MySQL uses REGEXP / RLIKE and REGEXP_LIKE, Snowflake uses REGEXP_LIKE / RLIKE, and Databricks Spark SQL uses RLIKE / REGEXP. Speed claims do not port either: always test on your own data and shape rather than assuming POSIX is fastest everywhere.

28.4.2 The Four Tilde Forms

A tilde operator — a short mark that tests a regex against a string or a slice of it and returns true or false — comes in four forms:

~ matches case-sensitively. ~* matches case-insensitively. !~ asserts no case-sensitive match. !~* asserts no case-insensitive match. All four return true or false and succeed on a substring, unlike SIMILAR TO.

  • ~ means match regular expression, case sensitive.
  • ~* means match regular expression, case insensitive. The star marks the insensitive form.
  • !~ means do not match regular expression, case sensitive.
  • !~* means do not match regular expression, case insensitive.

Think of two splits. One split is match versus do-not-match, marked by the leading !. The other split is case sensitive versus case insensitive, marked by the trailing *. Answer those two questions in order and the operator names itself.

28.4.3 Worked Examples

Case-sensitive match:

SELECT 'same' ~ 'same';
-- true

Both sides agree in case and letters, so the case-sensitive test passes.

The star-flag pair is the cleanest way to feel case handling:

SELECT 'Same' ~* 'same';
-- true (case ignored, S matches s)

SELECT 'Same' ~ 'same';
-- false (case counts, S does not equal s)

Only the operator changed; value and pattern stayed fixed, and the answer flipped. Sense-check: if the stem mentions "case-insensitive", look for the star.

Negated case-sensitive test:

SELECT 'Same' !~ 'same';
-- true

Read !~ as "does not match". Since 'Same' does not match 'same' under case-sensitive rules, the "does not match" claim is true.

Negated case-insensitive test:

SELECT 'Same' !~* 'same';
-- false

Under case-insensitive rules they do match, so the "does not match" claim is false.

Negation plus case-insensitivity is the most misread combination. Expand it in words before answering: !~* asks "is it true that these do NOT match when case is ignored?" If they match loosely, the negated claim is false.

Exam note: Learn to read the four marks at speed. ~ versus ~* flips case handling. Leading ! flips true to false. A test stem may change only one mark and ask for the new result. Recap: tilde tests a slice and returns a Boolean, while the next section's SUBSTRING returns the slice itself.

28.4.4 Student Questions and Answers

Q: How do I keep the four tilde forms straight?

A: Split them into two choices. First ask: match or do-not-match. No mark means match, ! means do-not-match. Then ask: does case count. No star means it counts, star means it does not. Combine the two answers to name the operator.

28.5 SUBSTRING with Regular Expressions

28.5.1 Shape of the Call

A SUBSTRING with regex — a function form that pulls the matched slice out of a string — is written:

SELECT SUBSTRING(string_text FROM 'pattern');

SUBSTRING(string FROM 'pattern') applies a POSIX pattern and returns the matched slice, not true or false. With no capture group it returns the whole match; with a capture group it returns the grouped piece.

The first part is the source string. After FROM comes the POSIX pattern. The function returns the slice that matches, not true or false.

The running source in the lesson is a single sentence used for every drill:

The movie will start at 8 p.m. on December 10th, 2020.

Note the details. 8 then a space then p.m. with dots. December then a space then 10th, with a comma, then a space, then 2020 with a closing dot. One missing space, dot, or comma breaks an exact pattern. Absolute shape matters.

Treat that movie sentence as a practice workbench. Every drill below reuses it, so run each pattern against it in order: first character, whole string, word runs, digits, time, month, full date. Small cumulative runs teach more than one long guess.

Keep the notation table close while you work. Dot, \w, \d, *, +, braces, anchors, groups, and pipes all appear below.

Cross-database note: this SUBSTRING ... FROM 'pattern' form is PostgreSQL-specific. MySQL uses REGEXP_SUBSTR(str, pattern), Snowflake uses REGEXP_SUBSTR, and Databricks Spark SQL uses regexp_extract(str, pattern, group). The patterns themselves transfer; only the wrapper changes.

28.5.2 Dot, Star, and Plus on the Movie Sentence

A lone dot pulls the first character:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '.');
-- T

. matches any single character except a newline, so the first slot T comes back.

To pull the whole sentence, pair dot with star. * means 0 or more of the prior item, so .* means any run of characters:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '.*');
-- The movie will start at 8 p.m. on December 10th, 2020.

In LIKE terms, . lines up with _ for one character, and .* lines up with % for any run. In regex you write . and .*. In LIKE you write _ and %.

To pull everything from a fixed word onward, name the word then add .+. + means 1 or more of the prior item:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM 'movie.+');
-- movie will start at 8 p.m. on December 10th, 2020.

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM 'will.+');
-- will start at 8 p.m. on December 10th, 2020.

The fixed head pins the start. .+ takes a non-empty tail. Change the head and the tail start moves with it.

Scope: .+ requires at least one trailing character. A pattern such as movie.+ fails when movie is the last word with nothing after it, while movie.* would still match. Pick + for "must continue" and * for "may end here".

28.5.3 Word Runs with Backslash-w

\w means any word character or underscore, the same set as [A-Za-z0-9_]. A lone \w pulls the first such character:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\w');
-- T

Add + for one or more word characters from the start:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\w+');
-- The

The run stops at the first space because a space is not a word character. That stop rule is the point: \w+ reads one word, not the sentence.

To pull the last word, anchor to the end with \$:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\w+\$');
-- 2020

More strictly the tail in the source is 2020. with a closing dot. A pure \w+ at the end grabs the digit run 2020. The lesson notes the dot rides along in some displays because the source ends with a dot. The key move is the anchor: \w+ alone grabs from the front, \w+\$ grabs at the back. Direction flips with the anchor.

Visualize a sliding window: without $ the window starts at the left and stops at the first space; with $ the window docks at the right end and reads backward to the last space. Takeaway in one line: the same \w+ reads the first word or the last word depending only on the anchor.

28.5.4 Digits, Counts, and the Year

\d means any digit, the same as [0-9]:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d');
-- 8

The first digit in the sentence is 8, so it comes back first.

{m} fixes the count. Two digits in a row:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d{2}');
-- 10

Here 10 is the first place where two digits sit side by side. A lone 8 has no neighbor digit, so the engine skips past it to 10.

Four digits in a row for the year:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d{4}');
-- 2020

Three in a row finds no match in this sentence, so it returns nothing. That empty result is itself a check. If you ask for \d{3} here, no three-digit block exists, so no slice comes back. Count must fit the data.

First-hit-wins surprises beginners: \d{1,2} on this sentence returns 8, not 10 or 2020, because scanning starts at the left. To reach a later number, pin more context around the pattern, such as the month name or the time prefix.

28.5.5 Time Slice with a Group and a Non-Capturing Mark

Goal: pull 8 p.m. as one slice, and later reuse the same shape for 10 p.m. or 8 a.m..

Capture (...) when the inner piece is the wanted output; use non-capturing (?:...) when the whole stencil is the wanted output. The time drill needs the whole 8 p.m., so it ends with (?:a|p).

First pass pins one-or-two digits. {1,2} means between one and two of the prior item:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d{1,2}');
-- 8

The 8 comes back. With 10 in the same sentence, \d{1,2} would also catch 10 if the engine reached it, but the first hit wins here.

Next add the meridiem choice. (a|p) means a or p:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d{1,2} (a|p).m.');
-- 8 p

The tail is short because the plain group reports its inner capture and the dots need care. The lesson builds step by step so the gap is easy to see. The fix adds ?: to group without splitting the report:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM '\d{1,2} (?:a|p).m.');
-- 8 p.m.

Now the full 8 p.m. comes back as one slice. Swap the source digit to 10 and the same shape returns 10 p.m.. The pipe inside handles a or p, so 8 a.m. fits the same stencil. A pipe means either side may hit. Since the sentence holds p.m., the p branch hits.

Build regex shapes piece by piece and run after each addition. That stepwise habit keeps a long pattern readable. The reference time example generalizes the same stencil as \d{1,2} (?:a.m.|p.m.) for the 7 p.m. case.

28.5.6 Month Choice and Full Date Build

Month choice uses the same pipe idea:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM 'December');
-- December

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM 'November|December');
-- December

With source holding December, the second branch hits. Point the same pattern at a sentence holding November and the first branch hits instead. Point it at a sentence with neither, and nothing comes back. Either side must be true.

Full date adds day digits, a comma, a space, and the year:

SELECT SUBSTRING('The movie will start at 8 p.m. on December 10th, 2020.' FROM 'December \d{2}, \d{4}');
-- December 10, 2020 with surrounding marks as stored

Read the pattern left to right: fixed word December, one space, two digits, one comma, one space, four digits. Each space and comma is load-bearing. Drop the space after the comma and the whole match fails. That strictness is why the lesson repeats that pattern matching is absolute. One space can decide true versus empty.

The source in the lesson shows 10th with th letters. In a strict run, \d{2} grabs 10 and the th needs its own handling if you want it in the output. The core point stands: name each separator exactly as stored. A production variant would add (?:th|st|nd|rd)? after \d{2} to absorb ordinal suffixes.

Real-world payoff: event lines, air times, and due dates hide in prose just like this. A date stencil plus a time stencil turns a paragraph of listings into sortable fields, and the same stencils feed the crime-report extraction where dates look like \d{1,2}\/\d{1,2}\/\d{2} with an escaped slash.

Recap: SUBSTRING ... FROM returns the slice; tilde returns the verdict. Build date and time stencils left to right, test each token as added, and anchor or capture only to steer which slice is reported.

28.5.7 Student Questions and Answers

Q: How should I practice these long patterns without getting lost?

A: Take one sentence and slice it many ways. Pull the first letter, then the first word, then the last word, then the digits, then the time, then the date. Build each pattern one token at a time and run it before adding the next token. Dozens of small runs on one string teach more than one long run on many strings.

28.6 REGEXP_MATCHES Function

28.6.1 Shape, Flags, and Array Output

A REGEXP_MATCHES — a function that matches a regex against a source string and returns each matching slice as text — is written:

SELECT REGEXP_MATCHES(source_string, 'pattern');
SELECT REGEXP_MATCHES(source_string, 'pattern', 'flags');

REGEXP_MATCHES(source, pattern [, flags]) returns the matched text, not a Boolean. Flag g means global: return every hit as its own row. Flag i means case-insensitive. Each hit arrives wrapped as a one-element array such as {Postgres}.

Flags are optional. Two matter most here:

  • g means global search. Without it only the first hit comes back. With it every hit comes back as its own row.
  • i means match without regard to case.

Unlike tilde and SIMILAR TO, which return true or false, this function returns the actual matched text. Each hit arrives in an array wrapper shown with curly brackets like {Postgres}. Two hits arrive as two rows, each holding a one-element array.

The reference sibling REGEXP_MATCH (singular, PostgreSQL 10 and later) returns only the first hit as an array, while REGEXP_MATCHES (plural) with g returns all hits. Crime-date extraction uses both: singular for the first date, plural with g to reveal the second date on the same incident.

Cross-database note: MySQL has no REGEXP_MATCHES; use REGEXP_SUBSTR and REGEXP_INSTR. Snowflake uses REGEXP_SUBSTR plus REGEXP_COUNT. Databricks Spark SQL uses regexp_extract for one group and regexp_extract_all for every hit. The g-versus-first-hit distinction exists on every engine under a different name.

28.6.2 Hashtag Words with Global Search

Source string holds display tags:

Amazing #Postgres #SQL

The question behind this drill: how do you harvest every tagged word, not just the first? The answer has two halves: a pattern that names one tag, plus the g flag that repeats the search over the rest of the string.

First pattern aims at a hash plus word letters:

SELECT REGEXP_MATCHES('Amazing #Postgres #SQL', '#([A-Za-z0-9_]+)');
-- {Postgres}  (first hit only)

Step through it: # pins the hash mark. (...) opens a capture that reports the word. [A-Za-z0-9_] allows upper-case, lower-case, digits, and underscore. + takes one or more of those. Without a flag, only the first tag comes back.

Add g for all hits:

SELECT REGEXP_MATCHES('Amazing #Postgres #SQL', '#([A-Za-z0-9_]+)', 'g');
-- {Postgres}
-- {SQL}

Now both tags return, one per row. The only change is the third argument 'g', and the row count moves from one to two. That contrast is the fastest way to grasp global search. Sense-check: one row per hit, brackets per row.

The result set shows two rows. Each row holds curly brackets, which mark an array value. Two rows plus brackets means two matches, each wrapped as an array. To store the bare word, unwrap with [1], as in (REGEXP_MATCHES(...))[1] or the singular (REGEXP_MATCH(...))[1].

28.6.3 Group Capture on Short Strings

A group can split one string into reported parts. Take source x y z with a pattern that captures x then two single characters:

SELECT REGEXP_MATCHES('x y z', '(x)(..)');
-- {x," y"}

Read it as: (x) captures the leading x. (..) captures the next two characters, here a space plus y. Output splits the source into two reported slices. Change the dot count and the split point moves. One dot takes one extra character. Two dots take two.

The lesson stresses writing the pattern to fit the exact gap. In x y z, after x there are two slots before z takes over: a space and y. That is why two dots line up. Miscount the gap and the split lands in the wrong place or fails.

Scope: Dots count separators too. A space is a character, so (..) after x consumes y, not y z. When a split lands one slot off, recount the gaps including spaces before blaming the engine.

28.6.4 Either-Or Search for Words

Pipe search finds one of two words. Source line:

my cat always jumps around

Pattern:

SELECT REGEXP_MATCHES('my cat always jumps around', '(cat|dog)');
-- {cat}

cat|dog means cat or dog. The source holds cat, so that branch hits and the function returns {cat} in array form. Point the same pattern at a line holding dog and it returns {dog}. Point it at a line with neither and nothing comes back. One true branch is enough because the pipe needs only one side to hit.

The county-name filter (lade|lare) is the same idea at table scale: one branch per spelling variant, wrapped in parentheses so the rest of the pattern applies to the whole choice.

28.6.5 Code Slices with Dashes

Source holds mixed letters, digits, and dashes, shown in the lesson as a shape like A111 B222-C style runs. The drill builds the slice in steps.

Letters only:

SELECT REGEXP_MATCHES('A111-B222-C', '[A-Z]', 'g');
-- {A}
-- {B}
-- {C}

[A-Z] allows only capitals. Digits fall away. Each capital returns on its own row under g.

Allow dashes too:

SELECT REGEXP_MATCHES('A111-B222-C', '[A-Z-]', 'g');
-- {A}
-- {-}
-- {B}
-- {-}
-- {C}

Now - passes as well, so dashes appear as their own hits. Note the hyphen sits last inside the brackets, which keeps it a literal dash rather than a range marker.

Ask for 0 or 1 of the prior set with ?:

SELECT REGEXP_MATCHES('A111-B222-C', '[A-Z-]?', 'g');
-- {-A} style slices that pair each dash with its letter

? means 0 or 1 time. Applied after a dash-letter set, it favors short dash + letter slices like -B and -C. The lesson lands on -A -B -C style output as the goal: the right-hand code letters kept with their dashes, digits dropped.

Real-world payoff: order codes, ticket tags, and serial runs often mix letters, digits, and separators in one field. A tight class plus a quantifier pulls the keepers and drops the rest without manual edits.

Recap: REGEXP_MATCHES answers "show me the slices". Default shows the first slice; g shows every slice as its own array row; groups decide how each slice is split. That sets up the next function, which edits the slices in place.

28.6.6 Student Questions and Answers

Q: Why did the second hashtag miss until the flag was added?

A: Because the default run stops after the first hit. The pattern was correct for both tags, but the engine was told to report once. Adding g tells it to keep scanning and report every hit, so the second tag appears as a second row.

28.7 REGEXP_REPLACE Function

28.7.1 Shape, Flags, and Back References

A REGEXP_REPLACE — a function that swaps each slice matching a regex with a new slice — is written:

SELECT REGEXP_REPLACE(source_text, 'pattern', 'replacement');
SELECT REGEXP_REPLACE(source_text, 'pattern', 'replacement', 'flags');

REGEXP_REPLACE(source, pattern, replacement [, flags]) returns a new string with the swap applied; stored data is unchanged. Flag g replaces every hit instead of the first only; flag i ignores case. Back reference \1 replays group one, \2 replays group two, in the order the groups open.

Inputs in order: source, pattern, replacement text, optional flags. Flags reuse g for all occurrences and i for case-insensitive matching. The function returns a new string with the swap applied. The source itself is unchanged in storage.

Swaps use back references. \1 means the text caught by the first group, \2 the text caught by the second group, and so on. So replacement '\2 \1' flips group one and group two with a space between.

Cross-database note: every engine here has this function, but the flag spelling differs. PostgreSQL passes 'g' and 'i' as a fourth argument. MySQL's REGEXP_REPLACE takes an optional position, occurrence, and match_type such as 'c' or 'i'. Snowflake's REGEXP_REPLACE takes optional occurrence, count, and parameters such as 'i'. Databricks Spark SQL's regexp_replace(str, pattern, rep) replaces all hits by default. Same idea, different fourth argument — check the target engine before porting.

28.7.2 Swapping First and Last Names

Source holds two words:

Adnan Wahid

The puzzle: two words are stored in the wrong order and must be flipped without retyping them. Capture each word as a group, then replay the groups in reverse order in the replacement.

Goal: flip to Wahid Adnan.

Pattern with two groups:

SELECT REGEXP_REPLACE('Adnan Wahid', '(.*) (.*)', '\2 \1');
-- Wahid Adnan

Step through it: (.*) grabs a run of any characters as group one. A literal space separates the words. (.*) grabs the rest as group two. Replacement '\2 \1' writes group two, a space, then group one. Group one Adnan moves to the back. Group two Wahid moves to the front. Sense-check: count the groups left to right, then read the replacement numbers right to left.

. plus * does the heavy lifting. . takes any character except a newline. * repeats it 0 or more times. Together .* takes a whole word here because the space in the middle stops the first group and starts the second.

The same shape generalizes. With three words, '\3 \2 \1' would reverse all three. The numbers always point back to group order in the pattern.

Greedy .* grabs as much as it can, so on three words (.*) (.*) puts the first two words in group one and only the last word in group two. For strict two-word names that is fine; for messier input, prefer (\w+) (\w+) or ([A-Za-z]+) classes that stop at spaces.

28.7.3 Scrubbing Digits or Letters with POSIX Classes

Source mixes letters and digits:

ABCD12345xyz

To keep letters and drop digits, match digits and replace with an empty string under global scope:

SELECT REGEXP_REPLACE('ABCD12345xyz', '[[:digit:]]', '', 'g');
-- ABCDxyz

[[:digit:]] is the POSIX class for digits. Each digit is replaced by nothing. g makes the swap hit every digit, not just the first. Without g, only the first digit would vanish and the result would read ABCD2345xyz. That one-flag gap is a classic slip, so pair a "drop all" goal with g every time.

Reverse the job to keep digits and drop letters with the alpha class:

SELECT REGEXP_REPLACE('ABCD12345xyz', '[[:alpha:]]', '', 'g');
-- 12345

[[:alpha:]] matches letters. Replacing each with nothing leaves the digit run 12345. Small case note: lower-case xyz also counts as alpha, so it drops too. The class covers both cases.

Prefer [[:digit:]] and [[:alpha:]] over \d and [A-Za-z] when the query must port: the POSIX classes work in PostgreSQL, MySQL, and Snowflake alike, while \d needs an escape or compatibility mode in some clients. Databricks Spark SQL accepts both \d and [0-9].

Real-world split: feeds that pack text and numbers into one CSV field split cleanly this way. One pass sends letters to a name field. A second pass sends digits to a code field. The reference date fix REGEXP_REPLACE('05/12/2024', '\d{4}', '2023') returning 05/12/2023 is the same move with a non-empty replacement.

28.7.4 Fixing a Year Inside a Date Line

Source holds a date-like run with 2019 where 2020 should be. First attempt names a single digit without a count:

SELECT REGEXP_REPLACE('2019 10 10', '\d', '2020');
-- 20202019 tail with leftover digits

Only the first digit 2 is swapped for 2020, leaving 019 behind. The result looks doubled and wrong. The pattern was too narrow and the flag too tight.

Fix it by naming all four digits with braces:

SELECT REGEXP_REPLACE('2019 10 10', '\d{4}', '2020');
-- 2020 10 10

\d{4} means exactly four digits in a row. Now the whole 2019 matches as one block and the replacement lands cleanly. The same brace lesson from SUBSTRING returns here: count must fit the block you want to change.

Two half-fix patterns recur on exams. A right pattern without g fixes only the first occurrence. A pattern without {m} fixes only one character of a block. When a corrected string looks almost right but doubled or partially scrubbed, check the count braces first, then the g flag.

Exam note: Watch for stems where the pattern is right but g is missing, or the count braces are missing. Both produce a half-fixed string that looks almost correct. Recap: replace answers "rewrite the slices": capture with groups, replay with \1 and \2, count with braces, repeat with g.

28.7.5 Student Questions and Answers

Q: Why did the digit scrub leave digits behind on the first run?

A: Because two pieces were missing. The replacement text was empty as planned, but the pattern named only part of the target or the run lacked g. With g absent, only the first hit changes. With braces absent, only one digit changes. Add the right class plus g plus the right count, and the full run clears in one pass.

28.8 REGEXP_SPLIT_TO_TABLE Function

28.8.1 Splitting a Delimited String into Rows

A REGEXP_SPLIT_TO_TABLE — a function that cuts a string on each regex hit and returns each piece as its own row — is written:

SELECT REGEXP_SPLIT_TO_TABLE('1,2,3,4', ',');
-- 1
-- 2
-- 3
-- 4

REGEXP_SPLIT_TO_TABLE(string, pattern) cuts on every regex hit and returns one text row per piece. The delimiter is consumed: commas vanish, pieces remain. No flag is needed for the basic cut.

The comma pattern marks each cut. Four pieces come back on four rows. Output type is text. The split needs no extra flag for this basic cut.

When does a split beat a match? When the goal is every piece, not one slice. Matches pull the interesting spans; splits discard the separators and keep everything else as rows ready to join, filter, and count.

Cross-database note: this set-returning form is PostgreSQL-specific. Snowflake uses SPLIT(str, delim) plus FLATTEN to explode to rows, Databricks Spark SQL uses split(str, pattern) to an array plus EXPLODE to rows, and MySQL uses SUBSTRING_INDEX in versions without a native split. Same cut, different wrapper.

28.8.2 Names Split by Comma Versus Space

Comma cut on names:

SELECT REGEXP_SPLIT_TO_TABLE('Adnan,James,Linda', ',');
-- Adnan
-- James
-- Linda

Three names, two commas, three rows. Each comma vanishes and each name lands on its own row. Sense-check: pieces always number one more than delimiters when no delimiter is doubled.

Change the source so a space sits after a comma, or change the pattern to a space, and the cut moves. The function cuts exactly where the pattern hits, nothing more. A pattern of ',' will not cut on spaces. A pattern of ' ' will not cut on commas. That strictness helps when a field mixes both marks. Pick the mark you want to split on and name it exactly.

A robust real-world variant handles the common ', ' mix explicitly:

SELECT REGEXP_SPLIT_TO_TABLE('Adnan, James, Linda', ',\s*');
-- Adnan
-- James
-- Linda

Here ,\s* consumes the comma plus any following spaces, so no leading blanks survive on the later rows. The reference crime loader uses the same thinking when splitting 'Four,score,and,seven,years,ago' on commas into six rows.

Watch for leftover padding: splitting 'Adnan, James' on ',' alone leaves ' James' with a leading space, which then fails a join against 'James'. Trim after splitting or include \s* in the pattern.

Real-world payoff: tag lists, multi-value CSV cells, and pasted name runs often arrive as one cell. Splitting to rows turns one packed cell into a set that can join, filter, and count.

Recap: Name the cut mark exactly, expect pieces to outnumber delimiters by one, and clean padding either in the pattern or right after. That row-shaped result feeds directly into the array twin next.

28.8.3 Student Questions and Answers

Q: What type comes back from this split?

A: Text rows. Each piece is a text value on its own row. That shape feeds directly into filters and joins without an extra cast in most drills.

28.9 REGEXP_SPLIT_TO_ARRAY Function

28.9.1 Splitting a Delimited String into an Array

A REGEXP_SPLIT_TO_ARRAY — the array twin of the prior split — cuts on each regex hit but returns one array instead of many rows. It is written:

SELECT REGEXP_SPLIT_TO_ARRAY('Adnan,James,Linda', ',');
-- {Adnan,James,Linda}

REGEXP_SPLIT_TO_ARRAY(string, pattern) cuts on the same marks but returns one array in one row. Curly brackets mark the array, and the column type reads as text array rather than text.

Same input, different container. The prior function gave three rows. This one gives one row holding a three-element array. Curly brackets mark the array. The header in the admin tool also labels the column as text array, which confirms the type.

Space cut works the same way:

SELECT REGEXP_SPLIT_TO_ARRAY('Adnan James Linda', ' ');
-- {Adnan,James,Linda}

With spaces as the pattern, each space marks a cut and the three names land as three array entries. The reference twin splits 'Phil Mike Tony Steve' on spaces into {Phil,Mike,Tony,Steve} the same way.

Cross-database note: Databricks Spark SQL's split(str, delim) returns an array natively, Snowflake's SPLIT returns an array, and MySQL has no direct array-split equivalent. The PostgreSQL array form is therefore the closest to the Databricks and Snowflake spelling.

28.9.2 Proving the Result Is an Array

Wrap the split with ARRAY_LENGTH to count entries:

SELECT ARRAY_LENGTH(REGEXP_SPLIT_TO_ARRAY('Adnan James Linda', ' '), 1);
-- 3

Three names give length 3. If the value were plain text, this length call would not apply in the same way. The 3 confirms an array with three slots. The second argument 1 names the first and only dimension; one-dimensional arrays always use 1 here.

The admin display gives a second proof. The type label reads text array and the value shows curly brackets around the three names. Both signs point to array, not rows. Wrap-and-count plus header-plus-brackets together make the proof airtight.

Pick rows versus array by downstream need. Need to join each piece as its own record. Split to table. Need to keep the set together in one cell for later array ops. Split to array.

A one-line decision rule: exploding to rows suits per-piece joins and filters; keeping an array suits per-record counts with ARRAY_LENGTH and membership tests without exploding the row count.

Real-world use: keeping tokens as an array helps when a single record owns many tags and you want to count tags per record with ARRAY_LENGTH or test membership without exploding rows.

Arrays index from 1 in PostgreSQL, so the first tag is arr[1], not arr[0]. Off-by-one indexing is the most common error right after proving the array exists.

Recap: Same cut mark, two containers. Table form multiplies rows for joins; array form keeps one row for per-record array ops. That closes the lecture's arc from cleaning text to filtering, extracting, rewriting, and finally reshaping it.

28.9.3 Student Questions and Answers

Q: When should I use the array form instead of the table form?

A: Use the table form when each piece must become its own row for joins or filters. Use the array form when the pieces belong together as one set on one record and you plan array ops like length or membership tests. Same cut mark, different container for different next steps.

  • Hands-on case rewrites: predict UPPER, LOWER, and INITCAP output exactly, spaces included. Remember INITCAP('Practical SQL') gives Practical Sql because acronyms are not preserved.
  • Length checks: CHAR_LENGTH('world') is 5, CHAR_LENGTH('world peace') is 11 because the space counts. Trimmed versus raw length differs by the padding count. Prefer CHAR_LENGTH for a stable character count.
  • SIMILAR TO true-or-false drills: the pattern must cover the whole string. Case counts. _ is one character, % is any tail including empty. Watch where % sits: s% pins the front, %s pins the back.
  • Tilde drills: ~ is case sensitive, ~* ignores case, ! flips match to do-not-match. One-mark changes flip the answer. Tilde matches a slice; SIMILAR TO must cover the whole string.
  • SUBSTRING ... FROM 'pattern' pulls: . first character, .* full string, \w first word character, \w+ first word, \w+$ last word, \d first digit, \d{2} first two-digit block, \d{4} year block, \d{1,2} (?:a|p).m. time slice, November|December month choice, December \d{2}, \d{4} full date with exact spaces and comma.
  • REGEXP_MATCHES returns text arrays with curly brackets. Default is first hit only. g returns all hits as extra rows. i ignores case. Unwrap with [1] when a plain value is needed.
  • REGEXP_REPLACE needs source, pattern, replacement, optional flags. \1 and \2 point back to groups. Use g to change all hits. Use {m} counts so a year swaps as a block. Only the returned string changes; storage is untouched.
  • Splits: comma or space pattern decides the cut. Table form gives rows for joins and filters. Array form gives {...} for per-record sets, and ARRAY_LENGTH(..., 1) proves the count.
  • Study move: rerun every pattern on the movie sentence plus the hashtag, name, and code strings until each token reads at speed. Build each long pattern one token at a time.

Key Industry Applications

  • Real-world: normalizing stock symbols and employee names with UPPER, LOWER, INITCAP, and TRIM before joins and groups. Snowflake and Databricks share INITCAP; MySQL builds it from UPPER, LOWER, and SUBSTRING.
  • Real-world: auditing column widths and cleaning CSV padding with CHAR_LENGTH plus TRIM. MySQL counts bytes with LENGTH versus characters with CHAR_LENGTH; Snowflake and Databricks count characters with LENGTH.
  • Real-world: shared regex skill across PostgreSQL, Python, PHP, and text editors for tag search and file parsing.
  • Real-world: splitting newline and carriage-return heavy loads with \n and \r patterns during bulk import, then combining extracted dates and times into timestamps for analysis.
  • Real-world: filtering rows in WHERE with tilde, LIKE, and SIMILAR TO shapes, with an index on the searched column for large tables. MySQL uses REGEXP and Snowflake and Databricks use RLIKE where PostgreSQL uses tilde.
  • Real-world: pulling show times and calendar dates from prose with SUBSTRING time and date stencils. MySQL uses REGEXP_SUBSTR, Snowflake uses REGEXP_SUBSTR, and Databricks uses regexp_extract for the same patterns.
  • Real-world: harvesting hashtags and code tags with REGEXP_MATCHES plus g for full coverage. Databricks uses regexp_extract_all and Snowflake uses REGEXP_SUBSTR loops for the global equivalent.
  • Real-world: swapping name order, scrubbing digits versus letters, and fixing year blocks with REGEXP_REPLACE and POSIX classes [[:digit:]] and [[:alpha:]], which port across PostgreSQL, MySQL, and Snowflake.
  • Real-world: exploding multi-value cells to rows with REGEXP_SPLIT_TO_TABLE or keeping tag sets together with REGEXP_SPLIT_TO_ARRAY plus ARRAY_LENGTH counts. Snowflake pairs SPLIT with FLATTEN; Databricks pairs split with EXPLODE.

Turning Text into Structured Data with String Functions

Must-know: Clean raw strings with UPPER, LOWER, INITCAP, and TRIM before pattern matching; predict outputs exactly with spaces included (e.g., INITCAP('Practical SQL') yields Practical Sql).

⚠️ Top pitfall: Applying regex directly to dirty or un-trimmed text, causing silent pattern misses due to leading/trailing whitespace or unexpected case.

Self-check: Why does INITCAP('Practical SQL') produce 'Practical Sql' instead of preserving the uppercase 'SQL'?

Connects to: 28.2, 28.3

Regular Expression Notation Basics

Must-know: A regular expression is a stencil describing text shape; single characters match literals, dot matches any character, brackets match character sets, caret outside brackets anchors to start, dollar anchors to end, and caret inside brackets negates.

⚠️ Top pitfall: Confusing caret position: ^ outside brackets anchors the start of string, whereas [^...] inside brackets negates the enclosed characters.

Self-check: What does the pattern ^[0-9] assert about a target string?

Connects to: 28.1, 28.3, 28.4

SIMILAR TO Operator

Must-know: SIMILAR TO evaluates SQL standard regular expressions and requires the pattern to match the entire string from beginning to end; uses % for any sequence and _ for single character.

⚠️ Top pitfall: Forgetting that SIMILAR TO must cover the whole string, unlike POSIX tilde matching which searches for substrings anywhere.

Self-check: Why does 'bat' SIMILAR TO 'b' return FALSE while 'bat' ~ 'b' returns TRUE?

Connects to: 28.2, 28.4

POSIX Regular Expressions with Tilde Operators

Must-know: Understand the four tilde operators: ~ (case-sensitive match), ~* (case-insensitive match), !~ (case-sensitive non-match), and !~* (case-insensitive non-match); POSIX operators match anywhere within the string by default.

⚠️ Top pitfall: Using ~ expecting case-insensitive behavior, or forgetting that ! flips match to non-match.

Self-check: Which operator tests whether a column does NOT contain a case-insensitive pattern?

Connects to: 28.3, 28.5

SUBSTRING with Regular Expressions

Must-know: SUBSTRING(string FROM pattern) extracts the first substring matching a POSIX regular expression; spaces and punctuation in the pattern must match the target text exactly.

⚠️ Top pitfall: Missing a literal space or punctuation mark in the pattern (e.g., omitting the comma or space in 'December \d{2}, \d{4}'), resulting in NULL.

Self-check: What value does SUBSTRING('Invoice 1234' FROM '\d+') return?

Connects to: 28.2, 28.4, 28.6

REGEXP_MATCHES Function

Must-know: REGEXP_MATCHES returns matched substrings as a text array (text[]); by default it stops at the first match; include the 'g' flag to return all matches as multiple rows.

⚠️ Top pitfall: Expecting a plain text string instead of a text array, or omitting the 'g' flag and missing subsequent matches in the string.

Self-check: How do you extract all hashtag occurrences from a string using REGEXP_MATCHES?

Connects to: 28.5, 28.7

REGEXP_REPLACE Function

Must-know: REGEXP_REPLACE(source, pattern, replacement [, flags]) swaps matched text using backreferences \1, \2 for capture groups; supply 'g' flag to replace all occurrences.

⚠️ Top pitfall: Omitting the 'g' flag so only the first matching pattern is replaced, leaving later matches unchanged.

Self-check: How do you swap 'First Last' into 'Last, First' using REGEXP_REPLACE?

Connects to: 28.5, 28.6

REGEXP_SPLIT_TO_TABLE Function

Must-know: REGEXP_SPLIT_TO_TABLE splits a delimited string into a set of rows (one row per split token), making text elements immediately filterable and joinable via SQL.

⚠️ Top pitfall: Using REGEXP_SPLIT_TO_TABLE when an array structure is required for storage or cardinality functions like ARRAY_LENGTH.

Self-check: What data structure does REGEXP_SPLIT_TO_TABLE produce from a comma-delimited string?

Connects to: 28.9

REGEXP_SPLIT_TO_ARRAY Function

Must-know: REGEXP_SPLIT_TO_ARRAY divides a delimited string into a PostgreSQL array of text elements (text[]), enabling array subscripting [1] and ARRAY_LENGTH inspection.

⚠️ Top pitfall: Confusing 1-based PostgreSQL array indexing with 0-based programming languages.

Self-check: How do you determine the number of elements produced by REGEXP_SPLIT_TO_ARRAY?

Connects to: 28.8
